公共部门智能体 AI：安全部署自主智能体

原标题：Public-Sector Agentic AI: Deploying Autonomous Agents Safely

Gain America · 2026-07-28 · 约 11 分钟读完

摘要

Gain America 撰文讨论政府场景下的 AI Agent 部署：Agent 能多步执行任务（处理案件、起草决定、分流民众请求），但必须配合人在回路、审计日志及 FedRAMP、StateRAMP/GovRAMP、CJIS 等合规框架。2026 年调查显示 53% 的联邦机构在试点 agentic AI，但试点常因生产预算缺失、授权（ATO）断层、隐私范围不匹配、缺少可回放审计记录等部署问题而搁浅，而非模型能力不足。文章以弗吉尼亚州 Executive Order 51 监管精简试点为例，主张从内部、可逆、低风险用例起步，并通过配备前沿部署工程师等人才解决落地问题。

要点

  • 政府 AI Agent 与聊天机器人的区别在于能自主执行多步操作。
  • OMB M-25-21 将影响民众权利的用途列为高风险 AI，要求人在回路与影响评估。
  • NIST 红队测试显示针对 Agent 的新型攻击成功率高达 81%。
  • 弗吉尼亚州 EO 51 试点用 Agent 审查法规矛盾与冗余，人工复核每条建议。
  • 试点失败主因是预算、授权与审计等部署问题，而非模型能力。

政府中的智能体 AI：面向公众服务的智能体、人在回路的控制机制、CJIS 和 FedRAMP 防护措施，以及配备能够交付经得起考验的智能体的工程师。

公共部门智能体 AI 是指在政府机构内部执行多步骤操作的 AI Agent 的部署——分类处理案件、起草裁定文书、分流公众请求——并在人在回路的控制、审计日志，以及与所有其他涉及公共数据的系统相同的 FedRAMP、StateRAMP/GovRAMP 和 CJIS 防护措施下运行。

智能体浪潮迅速席卷了政府部门。2026 年一项针对 200 多名联邦 IT 高管的调查显示，53% 的机构已经在探索或试点智能体 AI，另有 15% 正在实施。但一个引人注目的智能体演示与机构内获得授权的生产级智能体之间存在巨大差距——这是交付能力的差距，而非模型能力的差距。Gain America 的使命正是弥合这一差距：我们配备并部署前沿部署工程师、MLOps 团队以及持有安全许可、具备公共部门经验的人才，他们能够构建受治理、可观测、经得起审计的智能体，而无需机构承担其本就无力负担的前沿实验室级别薪酬。

AI Agent 在政府中的适用场景：公众服务、案件处理和后台运营

AI Agent 与聊天机器人的决定性区别在于：它会行动。它不仅仅是回答有关许可证的问题——它还可以查询申请人的档案、核对缺失的文件、起草补正通知，并将其提交审批。这一能力正是智能体在政府中具有价值的原因，也正是它们需要比简单助手更多控制的原因。智能体能够发挥价值的工作流程具有共同特征——高业务量、明显的积压、受规则约束的决策，以及能够对最终决定负责的人类。

公众服务智能体。 这是最清晰的切入点。一个覆盖网页、电话和聊天渠道的智能体可以回答有关许可证、税收、执照和资格的问题，然后采取下一步行动——提交请求、查询状态、预约时间——而不是只给公众一个电话号码。这是我们政府 AI 部署指南中所述的公众聊天机器人的自然演进，也是风险最低的起点，因为大多数操作是可逆的且以读取为主。

案件分类处理。 福利项目——医疗补助、失业救济、SNAP、住房、退伍军人服务——产生的案件量受密集规则约束。智能体可以预审申请、标示缺失文件、交叉核对资格标准，并为案件工作人员起草待批准或驳回的裁定文书。此时风险显著上升：智能体的输出会影响某人的福利，因此人类的参与不可或缺。这正是人在回路的 AI Agent 成为架构核心而非事后补充的地方——模型提出建议，人来做出决定。

后台运营。采购受理、档案调阅请求、FOIA（信息自由法）处理、IT 工单路由以及内部知识查询都非常适合采用 AI Agent，因为它们属于内部事务、边界清晰且可审计。一个在文档档案库中起草 FOIA 回复，或将采购请求路由到正确审批链的 Agent，能够在不直接触及公民权利的情况下压缩积压工作。这类场景通常会将多个专用 Agent 串联起来——我们的多 Agent 编排模式指南针对受监管环境对这一模式进行了详细拆解。

为什么人在回路和审计轨迹在公共部门是不可妥协的

在商业环境中，一个偶尔出错的 Agent 只是一张支持工单。而在政府中，一个出错的 Agent 可能错误地拒绝福利申请、错误地路由执法行动，或泄露受保护的数据——而且机构必须能够在事后证明，是谁或什么做出了该决定以及为什么。这一项要求就重塑了整个架构。

联邦政策对此有明确规定。OMB 备忘录 M-25-21（2025 年 4 月）将面向公民和影响权利的用途归类为高影响 AI，并强制要求实施最低限度的风险管理实践：部署前测试、AI 影响评估、持续的性能监控、人工监督与干预、一致的救济或申诉渠道，以及公众反馈。一个自主做出资格认定建议的 Agent 就是典型的高影响用例——这些实践不是可选的指导建议，而是底线要求。

大多数机构发现审计轨迹问题时已经太晚了。Agent 在演示中运行良好，随后进入小规模试点，直到投入生产才有人提出：我们能否还原 Agent 对该公民档案采取该行动的原因？如果答案是否定的，该项目就无法晋级。

审计轨迹是更难的那一半。跨分布式工具执行操作的自主 Agent 所生成的日志，与人类用户或脚本化工作流生成的日志有着本质区别——它是一条由模型推理、工具调用、任务委派和中间决策构成的链条。在 2026 年的一项治理调查中，近 90% 的受访者表示他们要求对每一项 Agent 操作进行日志记录和审计轨迹留存，超过 80% 的受访者要求配备自动化策略检查和防护机制。构建这种结构化、可回放的轨迹是一项生产工程，而这正是 agentic deployment 以及 AgentOps observability 中可观测性实践所涵盖的内容。没有决策日志的 Agent 不是一个受治理的 Agent——它只是一个界面美观的潜在风险。

恰当设计的人在回路并非走过场。它意味着 AI Agent 在明确的权限边界内运行：它可以自主执行读取和起草类操作，但任何会改变选民状态、花钱或涉及执法的操作都必须暂停等待人工批准——并且要呈现完整上下文，让审核者能够真正做出判断，而不只是点击确认。这一边界是一项设计决策，必须通过工程手段融入 Agent 的工具权限中，而不能事后补加。

合规护栏：面向智能体系统的 FedRAMP、StateRAMP 和 CJIS

智能体 AI 并没有自己单独的合规体系——它继承的是已经规范政府云和数据的相关框架，并在此基础上叠加针对 Agent 的专项控制。能否正确搭建这一体系，正是试点与生产系统之间的分水岭。

FedRAMP（联邦层面）。 Agent 运行所在的云平台必须获得 FedRAMP 授权。2025 年 3 月启动的 FedRAMP 20x 计划大幅压缩了授权周期，并且截至 2025 年 8 月，已将 AI 云服务的授权列为优先事项。但平台获得授权只是必要条件，而非充分条件——智能体用例仍需自身的运营授权（Authority to Operate）以及 M-25-21 风险实践。具体机制详见我们的 FedRAMP AI 合规指南。

StateRAMP / GovRAMP（州和地方层面）。 州、地方、部落和教育领域的采购方使用与之并行的框架，该框架于 2025 年由 StateRAMP 更名为 GovRAMP，并已被二十多个州采纳为采购要求。SLED 路径及其与 FedRAMP 的差异详见 StateRAMP 和 GovRAMP AI 合规。

CJIS（司法和执法领域）。 任何接触刑事司法信息的 Agent——例如检察官办公室内的案件处理 Agent、警察局内的档案管理 Agent——都必须满足 CJIS 安全策略在访问控制、加密和审计方面的要求。Agent 的存在使问题复杂化，因为它们代表用户跨多个系统执行操作；委托链本身也必须遵守 CJIS 边界。关于这在实际部署中如何落地，请参阅 CJIS 合规 AI。

在上述三者之上叠加的是 NIST AI 风险管理框架，这是如今大多数机构无论司法辖区如何都期望遵循的治理词汇。NIST 的 AI 标准与创新中心于 2026 年 2 月正式启动了 AI Agent 标准计划，其实证红队测试发现，针对 AI Agent 的新型攻击成功率达 81%，而针对基线防御的攻击成功率仅为 11%——这一鲜明信号表明，针对 Agent 的专项护栏（工具授权、委托链完整性、提示注入防御）如今已是首要安全议题，而非边缘情况。这些威胁是 智能体 AI 安全以及更广泛的 AI Agent 安全最佳实践的主题。

弗吉尼亚州的智能体 AI 试点与各州新兴做法

表明智能体 AI 正在真正进入政府工作的最具体信号来自弗吉尼亚州。2025 年 7 月，州长 Glenn Youngkin 签署了第 51 号行政命令，启动了该州所称的全美首个智能体 AI 监管精简试点。该智能体并非面向民众的聊天机器人，而是扫描弗吉尼亚州已发布的法规和指南，标记法规中的矛盾之处、识别冗余内容，并提出精简后的措辞建议——这建立在此前已将监管要求削减约 27%、并将指南文件字数减少近一半的指令基础之上。该命令还要求行政部门各机构今后在常规监管审查中使用 AI。

弗吉尼亚州的案例具有两点借鉴意义。首先，它选择了一个内部、低民众风险的首个用例——审查该州自身的规则——这正是那种有边界、可审计、能够在生产环境中经受考验的工作流。其次，该试点是与一家专业的第三方技术合作伙伴共同开展的，同时保留对每项建议的人工审查，这一模式正被其他州密切关注。有关该州的采购和部署具体情况，请参阅我们的弗吉尼亚州政府合同 AI 咨询和弗吉尼亚州政府 AI 部署指南。

弗吉尼亚州的经验教训并不是“用智能体处理法规”，而是：从智能体的操作属于内部且可逆的场景入手，对每项建议都保留人工审查，并在让智能体接触民众福利事务之前，先证明其审计追踪的可靠性。

其他州也在趋同于类似的模式——优先内部用例、对重要输出进行人工审查，并通过现有采购渠道而非新设渠道进行采购。贯穿各州做法的共同主线是：成功者都把范围限定得很窄，并大量部署监控手段。

失败模式：为什么政府智能体试点会停滞

政府中的智能体试点很少因为模型不够聪明而失败。它们的失败源于那些阻碍所有公共部门 AI 的常见壁垒——而自主性使这些问题更加尖锐。尽早识别这些问题，正是试点得以落地与沦为“试点炼狱”中一员的区别所在。

  • 生产资金断崖。 试点获得的是创新基金的资金，而其中从未包含将智能体投入生产运行的预算。当试点成功时，却没有一条有资金支持的路径让它“转正”。这是最常见的单一杀手。
  • ATO / FedRAMP 断崖。 试点运行在未经授权的沙箱中。迁移到真实的民众数据意味着需要团队从未评估过的授权流程，时间线也随之超出财年。
  • 数据隐私范围不匹配。 智能体内置的控制措施覆盖了试点数据，却无法覆盖其必须大规模处理的数据。在受调查的大多数机构中，官员们都指出现有的数据隐私政策是采用生成式 AI 的真正障碍。
  • 缺乏结构化的审计追踪。 Agent 能运行，但不会生成可回放其决策过程的记录——因此当审查者、审计员或法院提出要求时，该机构无法证明其履行了监督职责。系统在技术上可用，在法律上却不可用。
  • 试点重叠，缺乏统一的成功标准。 多个团队并行开展 agent 实验，却没有对“生产就绪”的统一定义，因此谁也无法提出规模化推广的依据。

这些不是模型问题，而是部署、授权和人员配置问题——与我们的政府 AI 项目为何失败和AI Agent 为何无法进入生产环境两篇分析从不同角度得出的诊断一致。其中每一个问题都是可以预见的，而每一个问题都能由曾经交付过受治理 agent 的人来解决。

配备能够部署受治理、可观测 agent 的工程师

上述每一种失败模式都指向同一个缺失要素：能够构建不仅能力强而且受治理的 agent 的工程师——权限范围受控、有人工把关、全程留痕，并与机构的遗留系统对接。这种技能组合非常稀缺，而机构无法靠薪资赢得它。一名资深 AI 工程师或前沿部署工程师的总薪酬是联邦 GS 薪级表和大多数州薪级区间无法匹敌的，而前沿实验室正在积极吸纳这类人才——这正是企业 AI 人才缺口最尖锐的体现。

为此而设的岗位正是前沿部署工程师——他们深入机构的环境中，负责界定范围、构建并交付生产系统，而不是从外部提供建议。FDE 模式正是在政府合同中开创的，并且几乎完美契合 agent 化部署：将获得授权的模型连接到大型机案件系统，在实际实施中执行 CJIS 或 M-25-21 控制要求，构建审计追踪，并在真实的民众数据上设定人机协同的边界。请参阅面向政府的前沿部署工程师了解该角色如何适应公共部门的约束，以及什么是前沿部署工程师了解完整定义。

人员增援颠覆了机构无法取胜的招聘算术。机构不再发布职位需求、等待六到十二个月让一位拥有安全许可的候选人接受低于市场水平的录用，而是直接购买部署能力：经过审查的工程师在整个项目周期内以约定的费率入驻，招聘和留任风险由合作方承担。人员增援与招聘的权衡在公共部门明显偏向增援模式，市场格局则已在政府 AI 人员配置公司中梳理。

这正是 Gain America 的使命，直白地说：我们招募、审核并派遣具备 FDE 水准、随时可投入公共部门的工程师——在工作需要时持有安全许可——进入各政府机构以及服务这些机构的主承包商，包括以分包商身份为主承包商提供人才。机构由此获得嵌入式交付能力，把一个有前景的 AI Agent 试点转变为受治理、可观测、已获授权的生产系统。AI Agent 浪潮已经证明了技术能力。剩下的是部署——而在政府领域，部署首先是一个人员配置问题。

常见问题

什么是公共部门 AI Agent？

公共部门 AI Agent 是指能够规划并执行多步骤操作的 AI 系统——查询记录、起草裁定、分派案件处理、调用机构 API——代表政府机构行事，而不仅仅是回答单个问题。在政府中，这些 Agent 几乎总是在人在回路的控制下运行：Agent 提议并执行低风险步骤，但任何影响公民权利或福利的重大决策都必须由人来批准。

根据现行联邦政策，政府允许使用 AI Agent 吗？

允许。OMB 备忘录 M-25-21 和 M-25-22（2025 年 4 月）对联邦 AI 采用持鼓励创新的立场，但它们将面向公民和影响权利的用途归类为“高影响 AI”，须遵守最低限度的风险管理实践：部署前测试、AI 影响评估、持续监控、人工监督与干预，以及申诉机制。涉及福利、执法或资格认定的 AI Agent 系统完全在这些要求范围之内。

为什么政府的 AI Agent 试点在进入生产阶段前停滞不前？

大多数政府 Agent 试点停滞不前，问题不在模型质量，而在于通往生产环境的路径：没有获批的生产预算、试点从未规划过的 FedRAMP 或 ATO 门槛、数据隐私政策未覆盖 Agent 需要大规模处理的数据，以及后期才发现系统无法生成结构化的决策审计记录。2026 年的一项联邦调查显示，53% 的机构正在探索或试点 AI Agent，但由于上述原因，试点往往无法顺利转正。

政府中的 AI Agent 适用哪些合规框架？

联邦部署需要通过云平台的 FedRAMP 授权，以及针对具体用例的 OMB M-25-21 风险管理实践。州和地方部署使用 StateRAMP/GovRAMP。涉及刑事司法信息的司法和执法 Agent 必须满足 CJIS 要求。在所有这些框架之上，NIST AI 风险管理框架——以及 NIST 于 2026 年 2 月启动的新兴 AI Agent 标准计划——提供了各机构如今所期望的治理语言。

政府机构如何为 AI Agent 部署配置人员？

由于机构无法匹敌前沿实验室的薪酬水平，大多数机构通过人员增补而非直接招聘来弥补差距。Gain America 负责招募、审查并嵌入前沿部署工程师——在工作需要时提供安全许可——他们将受治理、可观测的 AI Agent 接入机构的遗留系统，构建审计追踪，并对 Agent 在生产环境中是否有效运行承担责任。
