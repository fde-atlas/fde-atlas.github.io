我们构建的技术所面临的最大风险

原标题：Biggest risks of the technology we build

FDE Interview Prep · 2026 · 约 2 分钟读完

摘要

这是一篇 FDE 面试练习题，主题是如何回答“你所构建技术的最大风险”。文章强调答案必须结合具体产品在客户系统中的实际触达范围，而非泛泛而谈。建议指出最高风险并给出工程机制，如工具权限最小化、不可逆操作需人工审批、上线前用客户真实案例建评测集、可测试的关闭手段，并明确自己拒绝的底线与内部升级路径。文章还提醒避免空谈社会风险、推卸责任或一味夸赞公司。

要点

  • 风险分析须基于产品在客户系统中的具体触达范围。
  • 每个高风险需配机制：权限最小化、不可逆操作人工审批。
  • 上线前用客户真实案例建评测集，并指定离场后的负责人。
  • 明确会拒绝的请求及内部升级对象，而非独自对抗客户。
  • 可引用 ElevenLabs 关于前沿部署工程失败模式的文章作对照。

如何作答

面试官在考察你是否了解产品在客户系统内部做了什么，以及你的关切能否转化为工程习惯。一个适用于该类别中任何公司的回答都是不合格的。

  • 指出产品触及了什么。“你的 Agent 读取客服工单，并可以通过客户的计费 API 发起退款”对应一套风险清单；“你的平台跨部门整合某机构的案件记录”对应另一套，其中的风险是超出必要范围的访问权限，以及数据被用于未经任何人批准的用途。
  • 针对你将参与的部署，选出你认为最应优先关注的两项风险，说明原因，并为每一项给出机制。不是“幻觉”，而是“退款政策并不存在，但 Agent 却给出了退款状态，而客户被据此约束”。不是“安全”，而是“入站邮件中的文本被一个拥有写入权限的 Agent 当作指令来解读”。说明谁会受到伤害：终端用户、客户，还是双方之外的某人。
  • 为每一项给出一线实践，作为第一周的工作。工具权限按任务范围限定，不可逆操作须经人工批准。在上线之前，基于客户的真实案例构建评测集，并在你离开后指定明确的负责人。一种经过测试的关闭 Agent 的方法。
  • 说明你的底线在哪里，并清楚交易压力最终会落在你身上。说出你会拒绝的请求，例如为了达成吞吐量目标而取消对不可逆操作的人工批准，以及你会向自己公司内部的哪个人上报，而不是独自在客户面前表明立场。
  • 将其与他们发布的关于自身部署的内容联系起来。例如，ElevenLabs 关于其前沿部署工程经验教训的文章，将提示词歧义、工具误用和上报流程漂移列为 Agent 部署中反复出现的失败模式。来源 1构建持久可用的语音 Agent：前沿部署工程的一些经验教训发布方ElevenLabs来源类型公司博客说明你的哪项实践回应了他们的某一条，或者你会在哪里更进一步。

陷阱是写成社论：空谈社会风险，却没有任何内容能改变你周一要构建的东西。

追问

一旦你的第一个回答摆上桌面，面试官接下来可能会问的问题。

  • 在你部署过的东西中，你见过哪些风险真的出了问题？之后你做了什么改变？
  • 客户希望取消人工批准环节以达成吞吐量目标。这一周你会怎么做？
  • 在我们目前处理这些风险的某项方式上，你会在哪里提出异议？

回答容易出错的地方

  • 罗列偏见、虚假信息或失业等头条风险却没有给出任何机制，因此答案无法推导出客户现场的工程师会有任何不同的做法。
  • 把风险转交给别人（“政策团队负责这个”），于是一线实践就变成了“照指南执行”。
  • 通过声称公司已经解决了这个问题，把提问变成赞美。

用两分钟回答这个问题

写出你会大声说出的答案。计时从你说出第一个字开始。
