摘要

这篇面向 FDE 面试的 SQL 指南指出，Rippling、Notion、Databricks 的职位描述及 Palantir、Salesforce 候选人反馈均显示 SQL 会出现在考核中。文章用 SQLite 实测四个窗口函数模式：累计求和、组内取最新一行、环比变化和会话切分，并逐一指出默认 RANGE 帧、并列排序、WHERE 中不能过滤窗口函数、缺失周期等易错陷阱，最后给出解释查询的四步话术和七项自查清单。

要点

  • Rippling、Notion、Databricks 职位提及 SQL，Palantir 与 Salesforce 候选人报告考核含 SQL。
  • 累计求和陷阱：默认 RANGE 帧使同日订单总额相同，需显式写 ROWS 帧并加 id 决胜。
  • 取每组最新一行须用 ROW_NUMBER 加决胜键，且过滤要放在外层查询。
  • LAG 的“上一行”不等于“上一周期”，缺失周会把多周变化误当一周。
  • 会话切分用 LAG 标记间隔超阈值的首行，再以累计求和编号会话。

一分钟了解窗口函数：分区、排序与帧

窗口函数基于一组相关行为每一行计算一个值，并且保留所有行。

GROUP BY

会折叠行；窗口不会。这正是使用窗口函数的全部理由。

每个窗口最多有三个部分：

  • 分区：哪些行属于一组。PARTITION BY cust 会为每个客户重新开始计算。
  • 排序：分区内的顺序。ORDER BY day 让“前一个”和“到目前为止”有了意义。
  • 帧：当前行周围的哪些行参与计算。ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW 意思是“从第一行到当前这一行”。

如果只记住一件事，请记住这一点：使用

ORDER BY

且不指定帧时，默认帧是

RANGE

，而不是

ROWS

。这是 SQL 标准，SQLite、PostgreSQL 和 Snowflake 在

SUM

上都遵循它。第一个模式会说明这为什么重要。

每个客户的累计总额，以及并列值带来的帧陷阱

题目是：“显示每个客户的收入累计总额。”下面是一个很小的 orders 表，其中

acme

有两笔订单发生在同一天。

CREATE TABLE orders
  (id INT, cust TEXT, day TEXT, amt INT);
INSERT INTO orders VALUES
  (1, 'acme', '2026-03-01', 7),
  (2, 'acme', '2026-03-02', 8),
  (3, 'acme', '2026-03-02', 7),
  (4, 'bolt', '2026-03-01', 5);

看起来正确的第一版草稿：

SELECT id, cust, day, amt,
  SUM(amt) OVER (
    PARTITION BY cust
    ORDER BY day
  ) AS running
FROM orders;

在你读到

acme

行之前，它看起来都是对的：

idamt默认帧ROWS 帧
1777
282215
372222

订单 2 和 3 在同一天，所以在默认

RANGE

帧下它们是并列的，每一行的总额都包含对方。两者都显示 22。如果问题是“每笔订单之后的余额”，那就是错的。

SQLite documentation on window frames

,

PostgreSQL’s window function calls

和

Snowflake’s window function syntax

都描述了这种默认行为。

修复方法是明确写出帧，并给排序加一个打破并列的依据：

SUM(amt) OVER (
  PARTITION BY cust
  ORDER BY day, id
  ROWS BETWEEN UNBOUNDED PRECEDING
    AND CURRENT ROW
) AS running

现在

acme

总额依次为 7、15、22。如果

id

中没有

ORDER BY

,

ROWS

仍会打破并列，但顺序由引擎随意决定，因此数字在不同运行之间可能会变化。

通常更好的做法是先询问数据的粒度。如果客户想要每个客户每天一个数字，先在 CTE 中聚合出每日行，再在其上使用窗口函数。每天只有一行时就没有并列，两种帧的结果也一致。

七行移动平均就是同一个窗口加上

AVG

和

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW

。与下面的

LAG

一样，它按行计数而不是按天计数，所以要先填补缺失的日期。

这样说：“我按客户分区，让每个客户的累计值重新开始，按 day 和 id 排序，使并列行有固定顺序，并且我用 ROWS 来写窗口帧，因为默认的 RANGE 帧会给并列行相同的累计值。”

在累计求和问题上练习它，该问题还为没有订单的日期添加了日期骨架。

用 ROW_NUMBER 获取每组最新的一行

提示词：“对每个工单，返回其当前状态。”历史表中每次变更占一行，而一个自动化程序在同一分钟内为工单 101 写入了两次变更。

CREATE TABLE events (id INT,
  ticket INT, status TEXT, at TEXT);
INSERT INTO events VALUES
  (1, 101, 'open', '09:00'),
  (2, 101, 'pending', '10:00'),
  (3, 101, 'solved', '10:00'),
  (4, 102, 'open', '09:30');
SELECT ticket, status, at
FROM (
  SELECT ticket, status, at,
    ROW_NUMBER() OVER (
      PARTITION BY ticket
      ORDER BY at DESC, id DESC
    ) AS rn
  FROM events
) AS ranked
WHERE rn = 1;

工单 101 有

open

在

09:00

，然后

pending

和

solved

都在

10:00

，id 分别为 2 和 3。查询为 101 返回

solved

，为 102 返回

open

：每个工单一行。

下面是工单 101 用两种方式编号的结果，其中

RANK

仅按

at DESC

排序：

statusatRANKROW_NUMBER
solved10:0011
pending10:0012
open09:0033

有三点使它是正确的：

  • 用 ROW_NUMBER，而不是 RANK。在工单 101 上，ROW_NUMBER 把两个 10:00 的行编号为 1 和 2。RANK 给两者都是 1，所以按 rank 为一过滤会把重复行带回来。DENSE_RANK 也是一样，只是并列后不留空隙。
  • 要有一个打破并列的依据。当我们不带 id DESC 运行时，SQLite 碰巧选中了 pending。这不是 SQLite 的 bug；而是这条查询从未说明哪一行胜出。
  • 过滤要放在外层。WHERE 在窗口函数计算之前运行，所以 WHERE ROW_NUMBER() OVER (...) = 1 会报“misuse of ”错误。先在子查询或 CTE 中计算编号，然后再过滤。

把

rn = 1

改成

rn <= 3

，同一查询就会返回每组的前三行。

一个诱人但错误的答案是基于最大时间戳做回连。在这份数据上，它为工单 101 同时返回

pending

和

solved

：两个工单返回了三行。

这样说：“我用 ROW_NUMBER 把每个工单的行从新到旧编号，用事件 id 打破并列，然后保留第一行。ROW_NUMBER 从不重复编号，所以即使两次变更共享同一时间戳，每个工单也恰好得到一行。”

然后问一个能让你听起来像为客户做过这件事的问题：“更大的 id 是意味着变更发生得更晚，还是只是加载得更晚？”每个工单的最新状态问题会讲解这个追问以及规模化版本。

用 LAG 计算与上次的差异

提示词：“展示每个账户活跃席位的周环比变化。”

LAG

从窗口中的上一行读取一个值。

SELECT acct, wk, n,
  n - LAG(n) OVER (
    PARTITION BY acct
    ORDER BY wk
  ) AS delta
FROM seats;
acctweekseatsdelta
acme2026-03-0240null
acme2026-03-09466
acme2026-03-2331-15

有两个细节要明确说出来。

第一行是 null。没有上一行，所以

LAG

返回 null，减法的结果也是 null。这通常是正确的：“没有变化”和“没有更早的数据”是不同的事实。如果客户想要一个数字，

LAG(n, 1, 0)

可以提供默认值，但那样第一周就会显示为

+40

，先表示认同，再在你上线之前验证它。

“上一行”不等于“上周”。 看看日期：某一周的

2026-03-16

数据缺失，所以这个

-15

实际上是两周的降幅，却表现得像一周。在有人把它画上图表之前，把

LAG(wk)

放在差值旁边，或者检查一下间隔。如果每一周都必须出现，先构建一个周历表，然后对它做左连接。

这样说： “LAG 按周顺序给我同一账户的上一行，所以差值是本周减去我们有数据的最近一周。如果周可能缺失，我会先补齐它们，否则两周的变化看起来就像一周的变化。”

通过事件之间的间隔对事件进行会话化

题目是：“把页面浏览分组为会话，30 分钟不活动即结束一个会话。”这是一个 gaps and islands 问题，它结合了上面的两种模式：

LAG

找出间隔，一个运行中的

SUM

把它们转换成会话编号。

CREATE TABLE views
  (id INT, usr TEXT, ts TEXT);
INSERT INTO views VALUES
  (1, 'u1', '2026-03-02 10:00'),
  (2, 'u1', '2026-03-02 10:10'),
  (3, 'u1', '2026-03-02 10:40'),
  (4, 'u1', '2026-03-02 11:25');
WITH flagged AS (
  SELECT id, usr, ts,
    CASE WHEN unixepoch(ts)
      - unixepoch(LAG(ts) OVER w)
      <= 1800
    THEN 0 ELSE 1 END AS new_sess
  FROM views
  WINDOW w AS
    (PARTITION BY usr ORDER BY ts, id)
),
numbered AS (
  SELECT *, SUM(new_sess) OVER (
    PARTITION BY usr ORDER BY ts, id
    ROWS BETWEEN UNBOUNDED PRECEDING
      AND CURRENT ROW
  ) AS sess
  FROM flagged
)
SELECT usr, sess, MIN(ts) AS started,
  COUNT(*) AS views
FROM numbered
GROUP BY usr, sess;

在这些视图上，标志依次为 1、0、0、1，运行总和给出会话 1、1、1、2。从

10:10

改成

10:40

的间隔正好是 1800 秒，所以它留在第一个会话中；到

11:25

的 45 分钟间隔则开启一个新会话。

需要指出的要点：

  • 第一个视图自带标志。 LAG 在用户的第一行返回 null，比较结果为 null，CASE 落到 ELSE 1。不需要特殊处理。
  • 边界是一个决策。 正好等于阈值的间隔算同一个会话吗？先问清楚，然后写出 <= 或 < 来匹配。
  • 处处都要按用户分区。 不这样做的话，一个用户的第一行会延续另一个用户的会话。
  • unixepoch() 需要 SQLite 3.38.0 或更高版本。 在 PostgreSQL 中，用时间戳相减并与时间间隔比较；在 Snowflake 中，使用 DATEDIFF('second', ...)；在 BigQuery 中，使用 TIMESTAMP_DIFF(..., SECOND)。
这样说： “当与用户上一次浏览的间隔超过阈值时，我把该行标记为会话开始，然后对这些标志做运行总和来给会话编号。按用户和这个编号分组，每个会话就得到一行。”

会话化问题 还包含后续追问：如何处理从不归于安静的会话的上限，以及如何每小时对新行进行会话化。

如何口头解释一个窗口查询

面试官能读懂你的 SQL。他们看不到的是你是否知道它为什么有效。每次都使用同样的四个要点：

  • 粒度。 “输入是每笔订单一行；输出是每笔订单一行，并带有运行余额。”
  • 分区。 “按客户分区，所以每个客户都重新开始。”
  • 排序与并列。 “按天排序，再按 id 排序，所以每次运行的顺序都一致。”
  • 框架或过滤。 “框架从第一行到当前行，明确写出”或“在外层查询中保留第一行”。

然后以你会如何验证来收尾：“行数应该与输入一致，”或“结果应该每张工单一行，所以我会把它与

COUNT(DISTINCT ticket)

。”一个你能主动说出的检查点，比一个你无法解释的巧妙查询更有价值。

如果数据来自客户，说明你会问他们什么。“哪个时区定义一天？”和“两个变更可以共享同一个时间戳吗？”是 FDE 在第一次通话中就会问的问题。要演练这一半，并有模拟客户向你提问，可以试试免费 AI 练习案例。

在你说完成之前要做的七项检查

在你说完成之前

  • 你分区了吗？缺少 PARTITION BY 会给出跨所有客户的一个累计总和。
  • 排序是唯一的吗？在时间戳后加上 id，否则并列的行会以引擎任意选择的顺序返回，而且这个顺序在不同运行之间可能变化。
  • 你写窗口帧了吗？存在并列时，默认的 RANGE 帧会给并列行相同的总和。
  • 你用 ROW_NUMBER 保留一行了吗？RANK 会保留所有并列行。
  • 窗口过滤放在外层查询了吗？在 WHERE 中使用窗口函数会报错。
  • “上一行”是否意味着“上一周期”？缺失的周会让 LAG 的 Delta 变成多周的变化。
  • 你是在窗口之前还是之后聚合？说明是哪种，以及为什么。

另一个错误与语法无关：窗口上游的连接可能在窗口运行之前就使行数翻倍，之后每个累计总和都会被夸大。发现并修复连接扇出介绍了能发现这一问题的行数检查。

ROW_NUMBER、RANK 和 DENSE_RANK 有什么区别？

三者都在窗口内为行编号。ROW_NUMBER 会给并列的行分配不同的编号，因此当你必须每组只保留一行时应使用它。RANK 给并列的行分配相同编号，并跳过其后的编号；DENSE_RANK 给并列的行分配相同编号且不留空缺。

能在 WHERE 中对窗口函数进行过滤吗？

不能。WHERE 在窗口函数计算之前执行，因此需要先在子查询或 CTE 中计算窗口，再在外层查询中过滤。一些数据仓库为此提供了 QUALIFY 子句；SQLite 没有，所以要掌握子查询的写法。
