FDE 与工程师的区别是什么？比较职责范围、技术水平和转型路径

原标题：FDEとエンジニアの違いは？責任範囲・技術水準・移り方を比較

FDE総研 · 2026-07-23 · 约 9 分钟读完

摘要

这篇来自 FDE 总研（VACAN Technologies 运营）的文章，以 Palantir 官方博客和 The Pragmatic Engineer 的一手资料为依据，比较 FDE 与普通软件工程师（SWE）的差异。文章认为两者的区别不在技术高低，而在价值方向：SWE 是“一个能力服务众多客户”，FDE 则是“一个客户解决多种问题”。文章从责任范围、技术水准、转型路径等维度展开，指出 FDE 起点在客户问题发现、终点在现场落地，失败的定义是“能跑但没人用”。以 Anthropic 招聘要求为例，说明 FDE 仍需扎实的 Python 实现能力，客户沟通只是叠加项。最后给出 SWE 转 FDE 的建议：无需推倒重来，补足与客户共同定义需求、对成果负责的经验即可。

要点

  • FDE 与 SWE 的差异是价值方向而非技术高低。
  • FDE 起于客户问题发现，终于现场落地成果。
  • Anthropic 招聘要求高 Python 实现力为前提。
  • FDE 角色类似初创 CTO，需自行做取舍决策。
  • SWE 转 FDE 是在既有技术上扩展职责范围。

FDE和普通工程师的区别是什么？

FDE与普通SWE的区别不在于技术水平的高低，而在于Palantir官方博客所指出的“单一客户还是众多客户”这一价值方向。

FDE（Forward Deployed Engineer）与普通软件工程师（SWE）所使用的技术和语言有重叠。FDE总研（运营方：VACAN Technologies）用“价值方向”“职责范围”“技术水平”“成长路径”这四个相同的标尺来比较两者。因为如果用“哪一方技术水平更高”来比较，容易误解FDE这一职业。

FDE和SWE的价值交付方式有何不同？

SWE是将一个功能扩展到众多客户。FDE则是将单一客户面临的多个问题，逐一转化为功能。

按照Palantir的原始定义，普通的Dev（SWE）是“one capability, many customers”，而FDE（内部称呼Delta）是“one customer, many capabilities”（Palantir官方博客）。

视角FDE普通的SWE
判断的标尺这个客户的问题能否真正解决这个功能对众多用户是否具有通用性
优先考虑的事在眼前的现场取得成果不增加产品整体的复杂度
容易产生的观感容易被产品方认为“缺乏通用性”容易被现场方认为“不好用”

即使同样是“好的实现”这句话，FDE和SWE所指的内容也不同。这不是谁对谁错的问题，只是承担的方向不同。事先共享这一前提，也有助于理解FDE和SWE在同一组织中共事时产生的摩擦。

FDE是在哪里诞生的职业？

FDE是2010年代前期在Palantir诞生的职业，据报道到2016年前后其人数还多于普通的SWE。

这一经过由The Pragmatic Engineer报道。Palantir的客户是政府机构和大企业，需求尚未确定的现场是常态。

时期·事件内容可以读出的信息
2010年代前期FDE在Palantir诞生为应对需求不明确的现场而设立的职业
到2016年前后FDE的人数超过普通的SWE在现场解决问题曾是事业的主战场
近年出现在Anthropic等其他公司的招聘中作为一种职业正在Palantir之外扩展

从这一经过可以看出，FDE不是“也负责客户应对的工程师”，而是“为了在需求不明确的现场取得成果的职业”。如果需求从一开始就明确，就没有必要把工程师派驻到客户现场。

职责范围有何不同？

对照Palantir官方博客的定义，FDE的责任延伸到客户的成果，比在实现规格时即告完成的SWE范围更广一层。

工作的起点、成果物、失败的定义都与SWE不同。

用表格比较FDE和SWE的职责范围？

从起点、成果物、失败的定义、工作的里程碑来比较，FDE比SWE更早开始，也更晚结束。

视角FDE普通的SWE
对象深入单一客户广泛覆盖众多客户/用户
起点发现并重新定义客户的问题给定的规格和需求
成果物在客户现场运行并落地的实现通用产品的功能
所需能力实现＋客户沟通＋领域理解实现、设计
失败的定义即使能运行，现场也不使用无法按规格运行
工作的里程碑在客户现场取得成果之时代码被合并、发布之时
打个比方类似创业公司CTO功能开发的专家

差异尤其大的是“起点”和“失败的定义”。SWE是在规格已给定的状态下开始工作。FDE则从与客户一起探索“究竟应该做什么”开始，并且即使按规格运行，如果现场不使用也视为失败。

为什么说FDE“类似创业公司CTO”？

FDE以少数人承担从问题定义到实现、落地的全过程，判断也由自己做出，因此被称为接近CTO的角色。

在Palantir，FDE被定位为以小团队端到端地承担疑难项目的角色，接近创业公司的CTO（The Pragmatic Engineer）。“CTO式”所指的不是头衔的高低，而是决策的范围。

  • 决定不做什么
  • 重新调整优先级
  • 判断技术上的妥协可以允许到什么程度

由于没有人来保证规格是否合理，判断的依据就是自己在现场确认过的事实。职责范围的广度与权限的广度是成套的。

FDE所需的技术水平如何？

从Anthropic官方招聘来看，FDE以具备高水平的Python实现能力为前提，在此基础上再叠加客户应对能力，因此技术水平并不降低。

“即使不擅长技术，只要擅长客户应对就能胜任FDE”，这是一种常见的误解。

Anthropic的FDE招聘有哪些要求？

Anthropic 的 FDE 招聘在 Python 高水平实现能力的基础上，还要求具备 LLM 生产环境运营经验与 high agency。

Anthropic 官方招聘中列出的要求有以下 4 项。

  • Python 的高水平实现能力
  • LLM 的生产环境运营经验（高级提示词设计与 Agent 开发）
  • 在模糊性中推进的 high agency
  • 与客户进行 discovery 的能力

与普通工程师的差异在于第 2～4 项。第 1 项的实现能力是与普通 SWE 共同的基础，即使有客户 discovery 这一项，实现能力的要求也不会消失。

FDE 是写代码的职位吗？

FDE 是写代码的职位。需要自己设计、实现、测试工作流，并在客户的系统上构建生产应用。

客户沟通与领域理解，是为了正确决定“做什么”的手段。如果“听”的人和“做”的人是分开的，在现场获得的直观感受就会有一部分在整理成需求文档的过程中流失。FDE 由一人同时承担两者，根据客户的反应当场修改实现。

与 SIer、咨询、PdM 相比，哪些人不适合 FDE？

用 FDE 总研的比较维度“起点与成果的划分”将 FDE 与 SIer、咨询、PdM 并列比较时，FDE 的不同之处在于由一人承担从问题发现到实现与落地。

与相近职位的区别，不看头衔，而是看“从哪里开始、在哪里结束工作”，就不容易混淆。

FDE 与 SIer、咨询、PdM 有什么不同？

FDE 的特点是连实现都由自己承担，并以客户现场的成果来评价，这是它与以提案和确定规格为主的职位的分界线。

职位主要起点是否自己实现详细比较
FDE客户问题的发现与重新定义是FDE 工程师是什么
普通 SWE被给定的规格与需求是本文的比较表
SIer合同中约定的需求视体制而定FDE 与 SIer 的区别
咨询客户的经营与业务问题原则上不FDE 与咨询的区别
PdM自家产品的问题否FDE 与 PdM 的区别

什么样的人不适合 FDE？

想在规格确定后专注于实现的人，或想把一个功能打磨给大量用户使用的人，更适合普通的 SWE。

FDE 是“one customer, many capabilities”的职位，追求高通用性设计的工作不会成为核心。对于在规格模糊的情况下被要求做出判断感到负担的人，或想避免以现场使用情况来衡量成果的人，FDE 也不太适合。这不是优劣之分，而是承担方向的不同。

答案会因工作年限、现职、英语能力和企业规模而不同吗？

Anthropic 官方招聘的要求以能力项目为主，FDE 总研不看年限，而是以实现能力以及是否有在客户身边做出判断的经验来区分前提。

工作年限的要求因招聘而异，应聘前请务必在招聘原文中确认。

工作年限和现职会如何影响准备方式？

实现经验较浅的人优先补足 Python 的生产实现能力，SIer、外包出身的人优先补足与客户共同制定规格的经验，这是捷径。

现职与经历能派上用场的需要补足的
自研产品的 SWE推进到生产环境的实现能力客户 discovery、确认现场落地情况
SIer、外包开发与客户沟通的经验自己实现的经验、重新定义需求的经验
实现经验较浅的人业务或领域的理解Python 的高水平实现能力（第 1 层）

零经验者的路径在零经验能转职成为 FDE 吗？中有介绍。

英语能力和企业规模会有什么影响？

本文参考的 Palantir、Anthropic 的一手信息以英文发布，若想争取海外企业的 FDE 职位，读懂英文招聘是前提。

关于企业规模，Palantir 的 FDE 诞生于政府机构和大企业“需求无法确定的现场”这一经过（The Pragmatic Engineer）可作为判断依据。比起规模大小，请确认目标客户的需求是否尚未确定。招聘信息的阅读方法在FDE 招聘的寻找方法与招聘信息的阅读方法中有总结。

如何从 SWE 转向 FDE？

Anthropic 官方招聘同样以 Python 的实现能力为基础，在 SWE 经验之上加上与客户共同制定规格的经验，就能转向 FDE。

不需要从零开始。把什么能派上用场、什么还欠缺分开来考虑，准备起来会更容易。

SWE 的经验在 FDE 中如何发挥作用？

FDE 是以 SWE 的实现能力为基础的职位。产品开发的经验不会白费，会作为前提条件直接发挥作用。

设计、实现、测试功能并推向生产环境的一系列工作，是 SWE 在现场已经经历过的。转向 FDE 不是抛弃技术的“换乘”，而更接近在现有技术之上扩大职责范围的“扩展”。

转型中欠缺的是哪种经验？

欠缺的不是技术，而是在需求确定之前就与客户沟通、并对成果负责的“广度”方面的经验。

练习场景具体行动与 FDE 工作的联系
开发之前以实现者的身份列席需求定义会议问题的发现与重新定义
开发之前参与对客户或用户的访谈客户 discovery
开发之后发布后亲自确认是否在现场被使用对现场落地负责到底

这些都是能在现在的职场积累的经验。“做出来的实现没有被使用”的经历直接关系到 FDE 的“失败的定义”，因此可以成为面试中直接讲述的素材。面试准备在FDE 面试对策中有讲解。
