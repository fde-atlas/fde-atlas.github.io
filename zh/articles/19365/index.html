循环工程入门｜让自主 AI Agent 持续运转的 Harness 设计体系

摘要

这篇来自 FDX株式会社 的文章系统介绍了“循环工程”：一种让 AI Agent 以观测→判断→行动的方式持续、安全运行的护栏设计方法。文章认为 2026 年自主 Agent 进入业务运营，得益于长任务模型（如 Claude Opus 4.7）、Anthropic 的 harness 设计指南以及 Karpathy 的 autoresearch 思想。核心设计包括三层循环结构、四种停止条件（成功、预算超限、连续验证失败、外部中断），以及按 Hook（毫秒）→pre-commit（秒）→CI（分钟）→人工（小时）分层的验证体系，原则是把反馈尽量前移到最快的层级。文中还给出部分成功可接受、按季度清理护栏等实践建议，指出堆砌提示词、无限重试、未经验证的委托等反模式，并对比了 LangGraph、Claude Agent SDK 与 Claude Code 的实现取舍。末尾介绍 FDX 由 FDE 提供从设计到内制移交的陪跑服务。

要点

  • 循环工程指为观测→判断→行动的循环设计护栏，含停止条件、验证与预算管理。
  • 2026 年自主 Agent 普及归因于长任务模型、Anthropic harness 指南与 Karpathy 思想。
  • 停止条件有四种：成功达成、预算超限、连续验证失败、外部中断，需组合使用。
  • 验证按 Hook、pre-commit、CI、人工四层设计，反馈越快越好。
  • 反模式包括堆保险提示词、无限重试和未验证就采信子 Agent 结果。

什么是循环工程（3行要点）

  • 循环工程 = 设计让“观测 → 判断 → 行动”的反复迭代持续安全运行的技术框架。在 Agent 本体（模型 + 提示词）之外，加入停止条件 / 验证 / 预算管理。
  • 2026 年自主 Agent 的业务运用迅速普及，背景有三个：Claude Opus 4.7 等能胜任长任务的模型问世、Anthropic 的 harness 文章使设计方针正式化、Karpathy 式 autoresearch 思想渗透到企业界。
  • 设计的核心是“把反馈汇聚到最快的层级”。用确定性的工具（linter / 测试 / 类型检查）来矫正模型，无需增加提示词就能保证质量。

为什么 2026 年自主 Agent 的运营得以普及

三个因素叠加的结果，2026 年将自主 Agent 用于业务运营的企业迅速增多。

因素1：能胜任长任务的模型问世

Claude Opus 4.7、OpenAI o-series、Gemini 3 Pro 等具备内部自我验证能力的模型进入了正式运营阶段。即使减少失败时的重试，在数个循环内完成任务的概率也大幅提升。

因素2：Anthropic 的 harness 设计文章

Anthropic Engineering Blog 的 "Harness design for long-running application development" 发布后，“用测试而非文档来强制执行”这一框架设计方针正式确立。这使得企业更容易将其采纳为质量保证的内部标准。

因素3：Karpathy 式 "autoresearch" 思想的渗透

Andrej Karpathy 提出的“Modify → Verify → Keep / Discard → Repeat”自主研究循环，被证明也可应用于编程以外的领域（市场营销 / 客户支持 / 法律调研）。由此，业务循环的设计方法得以扩展。

循环的三层结构

Agent 循环由观测、判断、行动三层构成。每循环一周依次经过这三层，行动层的结果返回到下一轮的观测层。任何一层薄弱都会破坏整个循环的可靠性，因此需要明确每一层应设计什么。

观测层（Observation Layer）

  • state：当前任务状态 / 已完成步骤 / 剩余任务
  • memory：过去的对话 / 知识库 / RAG 结果
  • tool result：上次 tool call 的返回值 / 错误 / 副作用日志

观测层的设计等同于 上下文窗口的管理。如果塞入所有历史记录，判断层就会摇摆不定，因此需要摘要、筛选和压缩（参考：LLM 节省 token 的 5 种模式）。

判断层（Decision Layer）

  • 模型查看观测层并判断下一步行动
  • 提示词由判断方针（系统提示词）和当前观测（用户消息）构成
  • 是否在此插入 "reasoning" / "extended thinking" 取决于任务复杂度

判断层的质量取决于 观测层的信号 / 噪声比。比起增加提示词，浓缩观测层的信号更有效。

行动层（Action Layer）

  • tool call（外部 API / 文件操作 / 命令执行）
  • side effect（数据库更新 / 发送邮件 / 支付）
  • 自我更新（写入内存 / 保存学习数据）

行动层包含 所有伴随副作用的操作。尤其是数据库 / 邮件 / 支付等不可撤销的操作，惯例是在行动层内加入“防护”。

停止条件的 4 种模式

如果不设计循环“何时停止”，就会陷入失控、成本超支或无限循环。停止时机大致分为 4 类，实际运营中通常不是单独使用，而是组合设置。从理想的停止方式（成功），到需要避免的停止方式（预算超支、连续失败），再到从外部停止的途径（中断），都要一应俱全。

模式1：达成成功条件

  • 业务需求已满足（达成 KPI / 任务完成）
  • 例：工单创建完成 / 代码已编写且测试通过 / 报告已生成

这是最理想的停止原因。成功条件应设计为可用数值 / boolean 进行机器判定。

模式2：预算超支（token / time / cost）

  • 达到设定的 token / 执行时间 / 成本上限
  • 例：单任务超过 50,000 token / 10 分钟 / $5 时停止

企业运营中必不可少。没有预算上限的循环，会在边缘案例中产生指数级的成本爆炸。

模式3：验证失败连续发生

  • 重试也无法修复的错误连续发生N次
  • 例如：重试上限2次（Stripe经验）/ 同一测试连续3次失败

“无限重试会降低LLM的质量”是许多企业的经验法则。失败2〜3次后升级给人工处理。

模式4：外部中断

  • 用户明确中断
  • 来自其他进程的停止信号
  • 紧急情况下的终止开关

必须保留人工操作员介入的途径。完全自主会使故障时的恢复变得困难。

验证框架的分层设计

循环的质量取决于验证框架的响应速度。原则是“把反馈尽量放到最快的层”。

Tier 1：Hook（毫秒级）

  • 文件编辑后的即时lint / format
  • tool call前的参数校验
  • 副作用防护（阻止向特定path写入）

能在毫秒级完成判定的验证交给Hook处理。仅此一项就能减少80%“明显违规”的错误。

Tier 2：pre-commit / pre-action（秒级）

  • 类型检查 / 静态分析
  • 轻量单元测试
  • 业务规则违规检查

秒级完成的验证。在Agent执行commit / action之前运行。

Tier 3：CI（分钟级）

  • 集成测试 / E2E测试
  • 安全扫描
  • 构建验证

分钟级完成。在相当于pull request的时机运行。Agent等待CI结果后再进行下一步判断。

Tier 4：人工评审（小时 / 天）

  • 架构决策
  • 业务逻辑的合理性
  • 伦理 / 合规检查

只聚焦于只有人工才能判定的议题。如果这一层过多会增加运营负担，因此能在Tier 1〜3吸收的部分要彻底自动化。

原则：按Hook(ms) > pre-commit(s) > CI(min) > 人工(h)的顺序，把验证尽量放到更快的层。这样可以在最小化人工负担的同时提升质量。

运营技巧与反模式

技巧1：框架盘点（每季度）

对每条规则 / Hook / 约束，每季度追问一次“模型改进后是否已不再需要”。移除不必要的护栏。

过度约束会降低性能。对于模型已能自行规避的错误，应移除相应的Hook。

技巧2：接受部分成功

追求“100%完成”时，修正循环3次就会浪费大量token，结果却一无所获。以80%完成度交给人工，比追求100%而浪费token更合理（Stripe / Anthropic的经验法则）。

采用允许部分成功的设计后，Agent的运行效率会大幅提升。

技巧3：用测试 / 类型定义而非说明文档来表达信息

CLAUDE.md / AGENTS.md等说明文档有时会被模型跳过。而测试 / 类型定义即使模型不读，CI也能检测出违规。

Agent导致的错误要通过测试或lint规则防止复发。复利效应很大。

反模式1：在提示词中增加保险性措辞

“请仔细检查”“请再次确认”之类的保险性措辞，会与模型的内部验证重复，诱发过度循环。不要加入新规则 / 提示词中。

反模式2：用无限重试掩盖根本原因

如停止条件的模式3所述，对同一错误的重试应在几次后终止，升级给人工处理才是标准做法。无限重试不仅会降低LLM的输出质量，还会让本应修复的根本原因隐藏在重试次数的背后。

反模式3：未经验证的委托

不经验证就采纳子Agent的结果。如果轻信子Agent的“自以为完成了”，后续就会产生回退返工。

委托之后，务必通过实际执行结果（测试 / 日志 / 界面）验证行为。

FAQ

Q1. 与多Agent有何区别？

循环工程处理的是“单一Agent / 单一循环的安全运营”的设计思想。多Agent处理的是“多个Agent之间的协作 / 分工”。

两者是互补关系，多 Agent 中的各子 Agent 也分别是循环工程的对象。详情请参阅「多 Agent 实现指南」。

Q2. 用 LangGraph 还是 Claude Agent SDK 来实现？

取决于业务需求。

  • 状态迁移复杂（人工介入 / 分支众多 / 审计要求高）：选 LangGraph。可用状态机明确表达
  • 简单实现 / 快速上线：选 Claude Agent SDK。Anthropic 官方 SDK
  • 编码工作自动化：选 Claude Code。与编辑器集成及现有 dev tool 的亲和性高

Q3. 停止条件由谁决定？

业务需求 + 经营判断。不要仅由技术方决定。

  • 成功条件 → 业务负责人
  • 预算上限 → CFO / 事业负责人
  • 重试次数 → SRE / 平台工程师
  • 人工升级标准 → 遵循业务 SOP

Q4. 人工介入放在哪里？

有以下 3 种类型。

  • Approval Gate：在副作用较大的操作（删除数据库 / 大额支付 / 客户通知）之前要求审批
  • Fallback Gate：在出错 / 置信度下降时交由人工判断
  • Audit Gate：完成后由人工抽样审查

相比完全自动化，适当加入人工介入的运营质量更高。

Q5. 失败时的回滚设计怎么做？

按以下 3 个层级设计。

  • State Snapshot：在每个节点 / 步骤执行前保存 state。失败时可回退
  • Side Effect Compensation：如果产生了副作用，实现补偿事务（邮件撤回通知 / 数据库回滚）
  • Manual Recovery：当完全自动回滚难以实现时，向人工操作员提示“发生了什么”“从哪里重新开始”

总结

  • 循环工程是一种设计 Harness 的技术，用于让“观测→判断→行动”的迭代安全地持续运行
  • 停止条件应组合使用成功达成、预算超支、验证连续 fail、外部中断这 4 种模式来设置
  • 验证 Harness 应按 Hook（毫秒）→pre-commit（秒）→CI（分钟）→人工（小时）的层级设计，并将反馈尽量集中到最快的层级
  • 接受部分成功、Harness 的季度盘点、通过测试 / 类型定义进行信息表达是运营的关键
  • 添加免责措辞、无限重试、无验证的委托是典型的反模式
  • FDX株式会社由 FDE 提供从循环的 3 层设计到运营陪伴、内部移交的全流程支持
