AI Token 节省 5 种模式｜削减 LLM 成本 50~80% 的生产环境设计

摘要

这篇来自FDX株式会社的文章面向LLM生产环境成本失控的工程与业务负责人，提出五种可组合的省钱模式：提示词缓存（效果最大、难度低）、上下文压缩、按难度从小到大分级调用模型、批处理API（约五折）、以及用规则或传统解析器替代LLM抽取。作者称组合使用可削减50%至80%成本。文章还强调预算应实现为硬上限，超限即快速失败并告警，配合月度四项指标（如每成果成本、缓存命中率）和每月只上一项措施的改进循环，并列举了塞满上下文窗口、全用高端模型、不用缓存三大反模式。

要点

  • 五种模式组合可降低LLM生产成本50%至80%。
  • 提示词缓存效果最大，缓存读取单价仅为输入的10%。
  • 分级调用模型：第一层小模型精度约80%即可省70%至90%。
  • 预算须实现为硬上限，超限快速失败并即时通知。
  • 每月只实施一项优化，用四项指标衡量效果。

Token成本的基础：输入／输出／缓存3层

截至2026年，主要LLM的定价体系呈3层结构。

层内容相对单价（参考）
输入token作为提示词发送给模型的token1.0x（基准）
输出token模型生成的token3〜5x（比输入更贵）
缓存写入写入提示词缓存1.25x（输入+25%）
缓存读取从缓存读取0.1x（输入的10%）

要点如下。

  • 输出token最贵，因此压缩输出、或在输出后重新摘要的设计很有效
  • 缓存读取仅为输入的10%。在重复使用相同提示词的生产运营中，活用缓存效果最大
  • 相比长提示词+短输出，短提示词+短输出更便宜。其次是上下文压缩

各家定价体系的对比见LLM API比较。

5种节省模式

模式1：提示词缓存（效果最大／应用难度：低）

Anthropic／OpenAI／Google均提供缓存功能。缓存命中时可以以输入的10〜25%读取。

实现方法如下。

  • 将系统提示词／公共指令／较大的RAG结果指定为缓存对象
  • Anthropic需显式指定 cache_control: { type: "ephemeral" }（TTL 5分钟）
  • OpenAI／Google为自动缓存（TTL 24小时）

典型效果：Agent运营／聊天机器人可降低30〜60%成本。提示词越长效果越明显。

注意事项如下。

  • 若5分钟内未复用，缓存失效 → 成本增加（缓存写入多出的25%被浪费）
  • 含长时间休眠的循环无法命中缓存 → 建议将循环设计在270秒以内

模式2：上下文压缩（中等效果／应用难度：中）

压缩会话历史／RAG结果／系统提示词。

实现方法如下。

  • 摘要压缩：先用小模型（Haiku／GPT-4 mini）对长文摘要，再传给主模型
  • 裁剪：仅保留最近N轮，更早的内容替换为摘要
  • 结构化抽取：将自然语言转换为JSON／YAML以减少token

典型效果：聊天运营中降低20〜40%。会话越长效果越明显。

注意事项如下。

  • 压缩导致信息丢失会降低判断质量 → 重要约束／数值用结构化字段保留
  • 摘要模型本身也有成本 → 仅当与主模型的差额能回本时才值得

模式3：模型分级使用（小→大升级）（高效果／应用难度：中）

根据任务难度切换模型。

实现方法如下。

  • 第1阶段：用Haiku／GPT mini／Gemini Flash做判断／抽取／简单应答
  • 第2阶段：仅将判定为“困难”的案例升级到Opus／GPT／Gemini Pro
  • 只要第1阶段精度达到80%左右，整体成本可降低70〜90%

典型效果：客服支持／文档分类中降低50〜80%。

注意事项如下。

  • 路由判定模型出错时，升级率会上升
  • 需要持续测量第1阶段模型的精度

判定自动化在LLM路由中有详细介绍。

模式4：批处理／批处理API（中等效果／应用难度：低）

牺牲实时性以换取大幅单价折扣。

实现方法如下。

  • OpenAI／Anthropic／Google均提供批处理API
  • 比常规API便宜50%（OpenAI／Anthropic）
  • 完成最长需24小时（实际通常几小时内完成）

典型效果：以每日批处理运行的业务（报告生成／文档摘要／数据抽取）可降低40〜50%。

注意事项如下。

  • 不适用于需要实时性的用例
  • 需要另行设计批处理完成通知／失败时的重试

模式5：从LLM抽取转向自建抽取（高效果／应用难度：高）

将使用 LLM 进行抽取的处理替换为基于规则 / 现有库的实现。

实现方法如下。

  • 邮件抽取：不用 LLM，而是用 email-parser 库抽取 From/To/主题
  • PDF 文本抽取：不用 LLM，而是用 pdfplumber / unstructured 抽取 → 仅在后段使用 LLM
  • JSON / CSV 解析：不用 LLM，而是用标准解析器处理
  • 语言判定 / 情感分析：用小型分类模型（FastText / DistilBERT）替代

典型效果：抽取类业务可削减 70〜95%。但覆盖范围有限。

注意事项如下。

  • 并非所有环节都能脱离 LLM 抽取 → 难以结构化的场景仍保留 LLM
  • 抽取管线的维护成本会增加 → 仅长期运营的项目才能收回投入

预算管理框架的设计

将预算上限作为 Hard Ceiling 处理

预算不是“目标值”，而是作为 Hard Ceiling（绝对上限） 来实现。

const budget = { total: 50_000, spent: 0 }
async function callLLM(prompt: string) {
  if (budget.spent >= budget.total) throw new Error("Budget exceeded")
  const result = await llm.call(prompt)
  budget.spent += result.usage.input_tokens + result.usage.output_tokens
  return result
}

如果采用宽松的上限（“目标 X 元，实际 Y 元时报告”），在边缘场景下会导致成本呈指数级爆炸。Hard Ceiling 是运营安全的最低底线。

超限时的行为（fail fast / 降级 / 通知）

预算超限时的行为有 3 种模式。

  • fail fast：立即报错停止。企业环境下的推荐做法
  • 降级：从高端模型切换到小型模型继续运行。适用于成本敏感度中等的业务
  • 仅通知：超限后继续运行，通过 Slack 通知由人工判断。仅适用于原型阶段

生产运营的原则是 fail fast + 即时通知。降级存在精度下降的风险。

月度预算与每日突发控制

预算管理分两个层级进行。

  • 月度预算：会计年度的预算额度（由管理层批准）
  • 每日突发控制：将每日上限设为月度的 1/30 × 2〜3 倍。避免月初就耗尽预算

如果没有每日突发控制，月初一周就会消耗月度预算的 80%，月末则陷入功能停摆状态。

实测与改进循环

度量指标

指标计算目标
Cache hit rate缓存读取 token / 全部输入 token50% 以上（运营 3 个月后）
Avg tokens per task全部 token / 任务数取决于任务特性（基准值按月复核）
Cost per outcome月度成本 / 业务 KPI 改善量与业务 KPI 联动设定目标
Escalation rate高端模型调用 / 全部调用20〜30%（分模型运营时）

改进循环（月度）

  • 度量：通过月度仪表盘将上述 4 项指标可视化
  • 分析：识别成本最高的 Top 10 用例
  • 假设：探讨 5 种模式中哪一种适用
  • 实现：只试验其中一项并测量效果（A/B 测试 1〜2 周）
  • 上线推广 / 盘点：有效果就上线，没效果就撤回

同时投入多项措施会导致效果无法判别。原则是每月一项措施。

三种反模式

反模式 1：把 context window 塞满

“Claude 的上下文有 1M 可用，那就全塞进去”是最吃亏的模式。输入 token 虽然比输出便宜，但即便如此，100K 输入在无缓存的情况下每次调用也要 $0.3〜1。

规避方法：只保留最小必要的上下文。通过 RAG / 检索只获取所需部分。

反模式 2：所有请求都用高端模型处理

“全用 Opus 就能保证质量”是单价 50 倍的模型选择。月度成本会变成 10〜30 倍。

规避方法：分类 / 抽取 / 简单应答交给小型模型，高端模型只在需要判断的场景调用。

反模式 3：不利用缓存进行反复调用

每次都发送相同的系统提示、不使用缓存功能的实现，等于把本可以 0.1x 解决的开销按 1x 支付。

规避方法：显式启用提示缓存。Anthropic 中

cache_control

指定相应参数。

FAQ

Q1. 提示缓存除了 Anthropic 之外也能用吗？

能用。

  • Anthropic：显式指定缓存点（5 分钟 TTL，收费）
  • OpenAI：自动缓存（GPT-4 起，24 小时 TTL，免费）
  • Google Gemini：显式缓存（可指定时长，收费 / 也有免费的自动缓存版本）

实现自由度以 Anthropic 最高，但自动缓存方面 OpenAI / Google 更方便。生产运营中应构建一层抽象，屏蔽各提供商之间的实现差异。

Q2. 应该从哪个指标开始度量？

首先应关注 Cost per outcome（每单位业务 KPI 改善的成本）。其次用 Avg tokens per task 识别离群值。Cache hit rate 是衡量中期改进空间的指标。

只看 Total cost 看不出改进空间。务必用 "per X" 相除后再评估。

Q3. 如何自动化分模型使用的判定？

有以下 3 种模式。

  • 基于规则：根据输入长度 / 元数据分支（简单 / 灵活性低）
  • 小型分类模型：用 DistilBERT 等判定（中速 / 中精度）
  • 小型 LLM 判定：用 Haiku 等判定 → 必要时再用 Opus（成本中等，精度高）

标准做法是：先用规则起步，积累运营数据后再进化为小型 LLM 判定。

Q4. Batch API 能便宜多少？

OpenAI / Anthropic 是 5 折，Google 则 取决于时期和 SKU。应用于每日批处理业务（报告 / 数据提取 / 文档摘要）后，可立即省下一半。

只应用于能容忍最长 24 小时延迟的业务。实时业务无法使用。

Q5. 成本管理应该由谁负责？

责任应分为以下 3 个层级。

  • CFO / 经营层：审批月度、年度预算 / 盘点
  • AX 推进负责人：评估各举措的 ROI / 分配预算
  • SRE / 平台工程师：实现层面的成本优化 / 每日监控

3 个层级中任何一环缺失，成本管理就会崩溃。尤其是“CFO 批准了但 SRE 没有落实”是最常见的模式。

Q6. 超出月度预算时该如何应对？

按以下 3 个步骤应对。

  • 立即：以 fail fast 方式停止或降级服务
  • 24 小时内：查明原因（特定用例的突发用量 / 提示词变更导致的用量爆炸 / Bug）
  • 月内：永久性对策（重新审视提示词 / 增加模型分工使用 / 调整预算额度）

预算超支应按故障处理。执行事故报告 / 复盘（Postmortem），并将防止再发的措施制度化。

总结

  • LLM 成本由输入 / 输出 / 缓存 3 层结构构成，输出 Token 最贵，缓存读取最便宜
  • 通过提示词缓存、上下文压缩、模型分工使用、批处理、转向自建提取这 5 种模式，可削减 50～80%
  • 预算应实现为 Hard Ceiling（绝对上限），生产运营中原则上采用 fail fast＋即时通知
  • 每月测量 Cost per outcome 等 4 项指标，以“每月一项举措”的节奏运转改进循环
  • 上下文全部塞入、所有请求都用高端模型、未利用缓存，是三大反模式
  • FDX 株式会社提供从现状成本诊断到预算管理框架的实现与改进循环陪跑的全程支持
