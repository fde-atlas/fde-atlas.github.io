企业级 AI Agent 平台：一位 FDE 的入围测试

原标题：Enterprise AI Agent Platforms: An FDE's Shortlist Test

Zarif Automates · 2026-06-11 · 约 9 分钟读完

摘要

文章面向前沿部署工程师，比较五个企业级 AI Agent 平台：Microsoft Copilot Studio、Salesforce Agentforce、LangSmith Deployment、Amazon Bedrock AgentCore Runtime 和 Gemini Enterprise Agent Platform 的 Agent Runtime。作者基于 2026 年 9 月 17 日核查的官方文档，不做实测评分，而是围绕三个关键问题展开：谁批准了变更、哪个账户实际执行、写入成功但确认丢失时如何处理。文章给出统一的验收测试场景（含幂等性、会话隔离、回滚等），并建议按“文档声称、试点演示、未解决”三类归类供应商声明，从同一工作负载估算成本，最后以可交接的运维方案作为选型标准。

要点

  • 比较五个平台：Copilot Studio、Agentforce、LangSmith Deployment、AgentCore Runtime、Agent Runtime。
  • 核心问题是：谁批准变更、哪个账户执行、确认丢失怎么办。
  • 基于官方文档而非实测，无评分，文档核查于 2026 年 9 月 17 日。
  • 给出统一验收场景，覆盖幂等性、会话隔离、版本冲突与回滚。
  • 建议按文档声称、演示、未解决三档归类，并估算同一工作负载的成本。

本文从谁来执行操作、保存了什么、如何连接以及由谁来运维这几个维度对比五个企业级 Agent 平台，并给出一个可以提供给每位入围者的试点测试。

客户想要一个 Agent，能够查看账户、建议变更并更新 CRM。很多平台都能为此展示一场漂亮的演示。

难的部分在后面，当客户提出三个问题时：谁批准了这次变更？到底是哪个账户完成了它？如果更新已经执行但确认信息从未返回，会发生什么？

这些问题应该决定你的入围清单。平台可以提供有用的组件：运行 Agent 的地方、将其连接到其他系统的方式，以及对它被允许做什么的控制。但前沿部署工程师仍然需要把这些组件接入客户的实际工作流程，并证明客户的团队能够让它持续运行。

本指南基于 2026 年 9 月 17 日核查的官方文档，对比了五个起点。没有人针对这些厂商做过实际动手的基准测试，也没有星级评分。文末的试点是一个你可以向客户提议的测试，而不是某次测试的结果。

明确客户需要拥有什么

这里实际上有三种选择，它们很容易被混为一谈：

  • 工作发生的业务应用，例如 Salesforce 或 Microsoft 365。
  • 决定 Agent 行为方式的代码或配置。
  • 日常运行 Agent 的服务。

一家厂商可能同时提供这三者，也可能需要混合使用多家。选择一个框架并不能决定 Agent 在哪里运行；付费购买运行环境也不能决定它的工具被允许做什么。

客户场景起点实施问题
Power Platform 和 Microsoft 工作流中的 AgentMicrosoft Copilot Studio哪个环境、连接器身份和数据策略管控实际操作？

客户已经在使用的平台是合理的首选，因为他们的管理员已经知道如何运维它。但这并不意味着它默认胜出。对每一个符合客户限制的选项，都要给予相同的工作流和相同的故障场景进行测试。

Copilot Studio：检查环境和操作身份

当客户希望智能体贴近其 Microsoft 和 Power Platform 工作时，Copilot Studio 是合理的选择。Microsoft 的治理文档说明了数据策略如何控制登录、知识源、操作、连接器、Web 请求，以及智能体可以发布到哪里。这些文档还涵盖了以用户自身凭据运行的工具。参见 Copilot Studio 安全与治理。

需要问的问题是：每一步用的是哪个账户。一个人可以登录聊天，而其背后的操作却通过另一个连接运行。把这一点记录下来。然后用一位可以查看记录但无权编辑的员工来测试。

让环境管理员参与试点。检查三件事：

  • 测试环境中允许的连接器在生产环境中也被允许。
  • 你计划发布到的渠道是被允许的。
  • 当操作失败时，支持团队能看到出了什么问题。

不要假设一项认证或现有的 Microsoft 合同就能覆盖你设置的每一个数据流。

当业务团队和平台管理员能够共同负责这个工作流时，这个选项值得一看。当前沿部署工程师离开后，应该有一种经过测试的部署方式，以及一个指定的负责人来处理断开的连接。而不是一个只能在构建者个人账户下运行的演示。

Agentforce：将推理与明确的业务操作连接起来

Salesforce 当前的指南将 Agentforce Script 描述为固定规则与模型推理的结合。它把操作、指令以及智能体可以看到的信息视为需要分别设计的内容。这非常适合已经存在于 Salesforce 记录和流程中的工作。参见 Agentforce 实施指南。

对于试点，选择一个狭窄的操作，比如为支持工单建议一个类别。在编写任何智能体指令之前，先明确：

  • 它需要哪条记录，
  • 它允许选择哪些值，
  • 该操作在什么情况下才被允许，以及
  • 审批如何运作。

然后在智能体查看客户记录和执行操作之间，更改该客户记录。看看会发生什么。

智能体选择了一个操作，并不意味着该操作适合这位客户，也不意味着该用户有权执行它。检查该操作以什么权限运行，以及底层应用中的规则。要证明工作已完成，请使用业务系统中保存的记录。智能体说“完成”是不够的。

将这一个工作流与任何更大的数据项目分开。问清楚这个试点实际需要哪些产品、权限和付费许可证。小型试点应该在有人为生产环境购买这些之前就把它们暴露出来。

LangSmith Deployment：审慎选择托管责任

LangChain 目前的文档将其生产服务称为 LangSmith Deployment。它负责处理在步骤之间保持状态、流式输出或暂停等待人工审核的 Agent 运行。LangGraph 是可以使用它的框架之一。

文档描述了三种托管方式：托管的 Cloud、独立的 Agent Server，或自托管平台。它们的区别在于由谁来运行控制平面、运行时及其背后的存储。参见 LangSmith Deployment。

这一区别比“支持自托管”这个勾选项重要得多。使用独立服务器时，团队需要自己运行基础设施及其依赖的服务。使用托管方案时，团队仍然需要了解应用数据和追踪数据最终存放在哪里、登录如何设置，以及服务协议涵盖哪些内容。

让客户的工程和运维负责人参与这一决策。向他们展示四件事：一次暂停等待审核的运行、一次被中断的运行、一次更新，以及一次回滚。解释哪些状态会保留下来，以及应用的新版本如何处理旧版本保存的状态。

这适合想要掌控自定义 Agent 代码并能持续维护的团队。托管服务可以减少基础设施工作，但它不会替你完成应用的权限检查、测试或升级计划。

AgentCore Runtime：会话隔离仍需要应用层面的责任归属

Amazon Bedrock AgentCore Runtime 运行你自己的 Agent 和工具代码。AWS 表示它兼容不同的框架和模型提供商，并附带身份和监控功能。本节只讨论运行时，不涉及 Bedrock 名下的其他内容。参见 AgentCore Runtime。

会话文档中有最有用的细节。AgentCore 不会检查哪个用户拥有哪个会话 ID，这需要你的后端来跟踪。此外，默认情况下，存储在 Agent 机器上的任何内容都是临时的。如果需要持久保存，你必须自己构建该存储。参见 AgentCore sessions。

直接对这两点进行测试。提交他人会话 ID 的用户绝不能看到那个人的对话。已批准的变更绝不能依赖于临时磁盘的存留。将聊天历史与已批准内容和已执行操作的永久记录分开保存。

对于已经在使用 AWS 的客户，这可能与其团队现有的技能相匹配。前沿部署工程师仍应分别梳理四件事：谁在调用进来、Agent 对外调用时使用什么凭证、谁拥有每个会话，以及谁可以修改每条业务记录。将一个会话的机器与另一个会话的机器隔离开，并不意味着其中的一切操作都是被允许的。

Google 的 Agent Runtime：验证你的应用将要部署所依据的契约

Google 目前的文档将 Agent Runtime 归入 Gemini Enterprise Agent Platform。他们描述了托管部署、登录与权限设置，以及对不同语言和框架的支持，前提是应用符合运行时要求的格式。某些框架获得的内置支持比其他框架更多。参见 Agent Runtime 概述。

部署文档列出了多种接入方式，包括源文件、Dockerfile 或容器镜像。请选择客户构建与发布流程能够重复使用的方式。记录运行时格式、依赖项、区域、应用的身份，以及它所访问的每个资源上的权限。参见 部署 Agent。

最有价值的测试是这样的：从一个有版本号的构建全新部署。分别由一个有权限的用户和一个无权限的用户发送请求，并确认第二个请求被拒绝。然后切断 Agent 所需的某个数据源的访问权限，观察失败情况。在你笔记本上能跑通的调用，并不能证明已部署的 Agent 拥有正确的访问权限。

这适合那些应用和运维已经在 Google Cloud 上运行的团队。请核实实际的服务设置。不要假设概述中的每个功能在你的区域或协议下都可用。

给每个入围者相同的验收测试

使用虚假的客户记录和一个可撤销的测试操作。Agent 读取一条记录，引用适用的政策，建议一个类别变更，然后等待批准。在应用变更之前，执行写入的部分会检查该记录自批准以来是否未被更改。

对每个候选者保持任务一致。否则，一个更炫的演示可能仅仅因为使用了更简单的数据或更宽泛的权限而显得更好。

场景验收证据
有效请求和已批准的提案正确的记录状态、政策引用、批准人和持久化执行回执
用户可以读取但不能编辑读取成功。变更被应用边界拒绝
用户提交另一个会话或记录 ID无法访问其他用户的上下文或记录
记录在批准后发生变更版本冲突。过期的批准不会被复用
下游写入成功但其响应丢失使用受支持的幂等键或状态查询进行对账，而不是盲目重复写入
流程在等待审核时重启存储的提案及其批准状态仍可查看
模型或工具服务不可用有界停止、清晰的未解决状态和指定的恢复负责人
检索到的文本指示 Agent 忽略其规则不扩大权限或不执行未经批准的操作
新的应用版本未通过评测展示回滚操作，并解释任何状态迁移

其中一行值得用通俗语言解释一下。假设对 CRM 的更新已经执行成功，但确认成功的回复却丢失了。如果 Agent 只是简单地重试，可能会导致同一变更被执行两次。稳妥的做法是先检查第一次操作是否已生效，可以通过状态查询或系统认可的唯一键来确认。这就是幂等性的含义。

该表格列出的是需要展示的内容，并不声称任何平台开箱即用即可通过。如果某个平台需要额外工作才能通过某一行，请把这部分工作计算在内。

比较留给客户的工作量

用该客户写下的需求来评估入围方案，而不是用通用的评分标准。把每一项声明归入以下三个类别之一：

  • 已记录： 供应商声称可以做到。
  • 已演示： 你在试点中亲眼看到它正常工作。
  • 未解决： 目前还没有人展示过。

在试点或合同评审将其推进之前，供应商的声明始终停留在第一个类别。

用同一套工作负载为所有方案估算成本：模型调用、工具调用、运行时间、存储、追踪、重试以及人工审核时间。再加上构建成本和持续运行成本。标注哪些价格已写入合同、哪些是估算值、哪些仍未知。融资新闻和客户数量回答不了这些问题中的任何一个。

交接内容应包括：

  • 带版本号的应用，
  • 数据流向以及各账户职责的图表，
  • 测试用例及其结果，
  • 如何发布以及如何回滚，
  • 谁接收告警，以及
  • 一份事故处理手册。

指定一个无需等待构建者就能关闭故障操作的人。

那么，从哪里开始。从客户已经在使用的平台入手。把候选列表缩减到满足其必备需求的选项。在扩大范围之前先运行小范围试点。然后选择客户能够理解并自行处理其故障的那个方案，而不仅仅是成功运行表现最好的那个。

要将这一选择与整个构建过程的其他部分联系起来，请阅读 FDE 实战手册、知识管理试点 和 文档处理指南。
