Palantir 的本体（Ontology）是什么？从结构与 FDE 的设计步骤进行实务解说

原标题：Palantirのオントロジーとは？構造とFDEの設計手順を実務解説

FDE総研 · 2026-08-20 · 约 14 分钟读完

摘要

这篇日文文章面向实务者解释 Palantir Foundry 的本体（Ontology）：它不是学术上的概念分类，而是把业务实体、关系与可执行操作映射到真实数据上的可运行业务模型。文章说明其由对象型、链接型、动作型、函数（及属性）构成，并强调 FDE 的工作重心不是做仪表盘，而是本体设计——从现场访谈中提取名词与动词、识别判断发生点、以最小配置（约3至5个对象型）起步并用真实数据验证。文章还指出常见失败模式：照搬既有数据库表结构、过度建模、权限设计延后、数据鲜度不足与知识个人化。作者认为本体设计本质是通用数据建模能力的延伸，即使不用 Foundry 也值得练习。

要点

  • 本体是把业务实体、关系、操作接到真实数据的可执行模型，不是概念词典。
  • FDE 应先做本体设计而非可视化，否则后续应用与 AI 都要返工。
  • 设计流程：访谈提取名词动词、定位判断点、先做3至5个对象型再用数据验证。
  • 典型失败：照搬数据库表、建模过宽、权限延后、数据鲜度与个人化问题。
  • 本体设计是通用数据建模能力的应用，无 Foundry 也可用纸面练习。

Palantir 的本体（Ontology）是什么？

Palantir 的本体是在数据平台上重新定义业务实体、关系和操作的统一语义层。

Palantir Foundry 中的本体（Ontology），是指将散落在表格和文件中的数据，翻译成“客户”“配送班次”“设备”“作业指示”等业务实体（对象）、它们之间的关系，以及可执行操作的形式。从技术上讲，它是叠加在数据层之上的抽象层，但其实务意义更接近于“将现场人员使用的语言与系统中的列名一一重新对应起来的工作”（出处：Palantir Docs「Ontology」 https://www.palantir.com/docs/foundry/ontology/overview/ ）。

从外部看 FDE（Forward Deployed Engineer）的工作，有时会觉得是“在客户现场制作仪表盘的人”，但在 Palantir 类型的项目中，FDE 最初投入时间的往往不是可视化，而是本体设计。现场经常分享的经验是：如果这部分没有打好基础就继续推进，后续的应用和 AI 都容易返工。

它与哲学、信息科学中的“本体”有何不同？

Palantir 的本体不是概念分类的描述，而是实际数据与处理相连接的可执行业务模型。

在信息科学的语境中，本体指的是将概念及其关系形式化描述的知识体系，常与 RDF、OWL 等描述语言结合在一起讨论。Palantir 的本体借鉴了这一思路，但目的不同。已定义的“配送班次”这一对象类型，会与从实际数据源同步而来的行相关联；执行“取消班次”这一动作时，就会发生写回。也就是说，它不是用于阅读的词典，而是驱动业务的实体。

这种差异也体现在所需的技能上。相比学术性的分类精细程度，判断标准是“用这个定义，明天的现场运营能否运转起来”。如果优先追求定义的优美而舍弃现场的例外处理，最终还是会留下 Excel 的双重管理。反之，如果把现场的所有例外都作为属性纳入，模型又会过度膨胀。在这两者之间划出界线的工作，正是本体设计的实务本身。

为什么 Palantir 将本体置于核心？

因为数据集成、应用和 AI 三者可以引用同一套定义，从而避免各现场重复开发。

在 Palantir 的产品构成中，Foundry 承担数据集成和运营基础，其上叠加着使用 LLM 的 Palantir AIP 层（出处：Palantir「Platforms」 https://www.palantir.com/platforms/ ）。这一构成之所以成立，是因为 AIP 侧的逻辑和 Agent 所引用的对象，不是原始表格，而是本体上的对象和动作。

换句话说，本体是一项投资，其目的是“只要一次性定义好，可视化、自动化和 AI 就都能复用同一个基础”。反之，如果每个项目都各自堆砌独立的 SQL 和仪表盘，这种复用就无法发挥作用。FDE 的成果是止步于一次性的交付物，还是成为可以带给下一位客户的资产，其分水岭也在这里。

本体由什么样的结构构成？

本体由对象类型、链接类型、动作类型和函数四个要素构成，各自的角色划分明确。

即使说“要对业务建模”，如果不掌握结构也无从下手。Foundry 的本体可以按照名词（对象类型）、名词之间的关系（链接类型）、动词（动作类型）、计算（函数）这样清晰的对应关系来整理。有时再加上对象类型所附带的属性，用五个词汇来说明。

对象类型、链接类型、动作类型有什么区别？

对象类型对应业务中的名词，链接类型对应名词之间的关系，动作类型对应改变状态的动词。

构成要素角色业务中的对应具体例子（零售、物流）设计时的主要论点
对象类型定义业务实体名词门店、商品、配送班次、作业指示粒度和主键放在哪里
属性实体的属性名词的性质班次的预计出发时间、延误分类是否区分实测值和估计值
链接类型实体之间的关系关系班次 ↔ 装载商品、门店 ↔ 负责人一对多还是多对多、是否保留历史
动作类型改变状态的操作动词取消班次、重新分配负责人谁可以执行、写回什么
函数派生值、判定逻辑计算计算延误风险评分预先计算还是运行时计算

现场讨论拖得久的通常是对象类型的粒度问题。是按“配送班次”计数，还是按“配送班次的区间”计数，会让后续的链接和动作全部改变。这属于业务判断而非技术判断，因此一般认为FDE不应独断决定，而是让现场负责人展示实际的报表和运营规则，在此基础上敲定更稳妥。往往只需确认报表的每一行代表什么，粒度的讨论就能迅速收敛。

本体（Ontology）与数据管道是如何连接的？

通过将管道整理好的数据集与对象类型对应起来，本体便拥有了实际数据。

在Foundry中，流程是从源系统进行摄取和整理，使用Pipeline Builder或Code Repositories完成，然后将其输出的数据集映射到本体上的对象类型（出处：Palantir Docs https://www.palantir.com/docs/foundry/）。因此，本体设计与上游的数据整备状况密不可分。

实务上的注意点是，“想放入本体的定义”与“现实数据能填充的字段”必然存在偏差。先写完理想定义再发现某些字段填不上，这种返工很容易发生，因此常见的做法是在设计的同时用样本数据确认能否填充，这样推进更快。填不上的字段不要直接删掉，而是明确标记为“保留”，并与客户方共享哪些系统改造后才能填充，这将成为下一阶段投资判断的依据。

FDE如何设计与实现本体？

FDE通过业务访谈提取名词和动词，先以最小构成进行定义，再通过现场使用加以验证。

FDE的本体设计并非先完成文档再进入实现的瀑布式，而是以小规模构建、让现场试用并逐步削减的方式为主。验证的指标不是设计文档的评审，而是现场是否真的打开了页面，这是与传统需求定义的重大区别。

从业务访谈到对象定义的步骤是什么？

基本做法是将现场的语言分解为名词和动词，优先将发生判断的环节对象化。

  • 让业务流程以口头方式讲述 — 不是看操作手册，而是让负责人讲述实际是如何运作的。手册中没有记载的例外处理会在这里浮现。
  • 写出名词和动词 — 将对话中出现的“班次”“单据”“退回”“分配”原样列为候选。不要用自己的语言改述术语。
  • 确定判断发生的位置。人们犹豫、确认、打电话的环节，就是动作类型和函数的候选
  • 定义最小数量的对象类型 — 最初控制在3～5个左右。这个数字只是经验性的参考，会随业务规模而变化。
  • 用实际数据尝试映射 — 确认定义的属性能由现有系统的哪些列填充，填不上的字段标记为保留。
  • 展示给现场并修正术语 — 如果现场负责人阅读定义的对象名称后没有违和感，翻译就是成功的。

很多人认为，这一流程中最有价值的是第三步“发现发生判断的位置”。仅仅将数据可视化，现有BI也能做到，但能否将判断作为动作放到平台上，直接关系到使用本体的意义。反过来说，如果访谈中一个判断点都没有出现的业务，其本体化的优先级可能较低。

动作和权限FDE能决定到什么程度？

动作的执行权限应与业务上的责任分界一致，FDE原则上只做提案，决策权留在客户方。

动作类型涉及写回操作，因此“谁能按下这个按钮”的设计本身就是安全设计。技术上可以用权限组进行细粒度控制，但需要判断的不是技术，而是业务侧的责任范围。现场的采购负责人是否可以直接更新库存数量、是否需要插入审批环节，这类议题不应由FDE单独决定。

另一方面，如果将权限设计完全推给客户，讨论容易停滞。对FDE来说，比较现实的做法是提出一个照搬现有业务规则的初稿方案：“现行纸质流程中是这个人盖章，所以是否可以把动作权限集中在同一个人身上”。只把无法映射到纸质流程的新动作，重新提交给客户方决策，这样议题就能聚焦。

如何让现场使用建好的本体？

不能让用户直接操作对象，而需要通过业务页面或API嵌入到日常的工作流程中。

定义好的本体，可以通过Workshop这类应用构建功能作为业务页面提供，也可以使用Ontology SDK（OSDK）从外部应用进行引用和操作（出处：Palantir Docs https://www.palantir.com/docs/foundry/）。这里重要的是，要摒弃让现场人员学习数据探索工具用法的思路。

无法落地的典型情况是：虽然建成了优秀的本体，但现场最终仍像以前一样用邮件和电话处理工作。需要在设计阶段就倒推：页面能否嵌入现有的工作流程中，负责人每天是否有多次打开它的理由。像“晨会前必定打开的页面”这样，与既有习惯绑定，落地会更快。

引入本体时容易在哪里踩坑？

照搬现有表结构、过度构建、权限设计延后，这三者是典型的失败模式。

本体作为概念容易理解，但在实现中同样的失败容易反复出现。其中很多只要事先了解这些模式就能避免。

直接照搬现有数据库的表会发生什么？

系统层面的规范化结构被带入，形成与现场语言不一致、无人使用的模型。

核心系统的表设计往往不是由业务含义决定，而是由事务处理的效率决定。如果将其原样照搬到对象类型上，就会出现“T_ORDER_HEADER”和“T_ORDER_DETAIL”作为两个对象并列的结果。现场负责人把“订单”当作一个整体来处理，而在平台上却被拆成了两个。

以迁移源的结构作为底稿本身是高效的，但一定要加入一个用现场的语言重新命名和调整粒度的工序。如果对象型只是把表名翻译成了日语，那就可以视为没有真正完成翻译的信号。

过度构建的本体（Ontology）为什么会停止运转？

如果把定义对象扩展得过大，数据更新和维护就会跟不上，最终变成一个不被信任的基础。

常见问题症状发生原因可采取的对策
照搬表结构对象名与现场用语不一致直接沿用上游设计用现场的语言重新定义命名和粒度
构建过度已定义的对象大部分未被使用一开始就追求全面覆盖缩小到第一条业务线所需的范围
权限问题被延后在正式部署前夕才出现公开范围的讨论只从功能层面推进 Action 设计在定义 Action 的同时确定执行者
忽视数据新鲜度页面上的数字与现场的实际感受有偏差未在管道侧确定更新频率从业务判断所需的更新间隔倒推
依赖特定个人定义变更只能由特定的 FDE 完成设计意图未被文档化与客户方的负责人共享定义的理由

影响尤其大的是第4行的数据新鲜度。即使本体本身的定义是正确的，如果数字是半天前的，现场人员还是会相信自己手头的信息。一旦“那个页面不可靠”的评价固化下来，即使从技术上修复了，使用率也很难恢复。最初的部署范围可以窄一些，限定在能保证数据新鲜度的范围内会更安全。第5行的依赖特定个人，其原因也往往不是定义本身，而是没有留下“为什么采用这个粒度”的记录。

学习本体应该从哪里入手？

通过官方文档掌握术语，同时并行练习对自己身边的业务进行建模，这是捷径。

由于 Palantir Foundry 缺少个人可以自由使用的环境，把学习分为“概念理解”和“建模反复练习”两部分推进是比较现实的做法。

Palantir 的官方教材应该从哪里开始？

从 Palantir Docs 的本体概览入手，先阅读对象型和 Action 型，效率最高。

Palantir 公开了产品文档，关于 Foundry 的本体，可以阅读各构成要素的说明（出处：Palantir Docs https://www.palantir.com/docs/foundry/ontology/overview/ ）。由于功能名和术语可能会更新，建议在通过文章或书籍掌握概念之后，养成在官方文档中确认当前称谓的习惯。此外，Palantir 在官方网站上发布了学习和实践项目的介绍，如果想寻找接触实际环境的机会，查看该页面最为可靠。

阅读顺序上，（1）本体概览、（2）对象型与属性、（3）链接型、（4）Action 型、（5）与 AIP 的关系，这样比较容易理解。如果一上来就从 AIP 或 Agent 入手，就会在看不到所依赖的基础的情况下，术语越积越多。

如果手头没有 Foundry，可以用什么替代？

以自己的业务或身边的服务为题材，在纸上定义对象、链接和 Action 的练习是有效的。

本体设计的核心不是特定产品的操作，而是把业务分解为名词和动词的思维方式。这种训练即使没有 Foundry 也能进行。例如，以平时使用的公司内部系统为题材，写出5个对象型、3个链接型、3个 Action 型。在此基础上，进一步明确“这个 Action 由谁执行”“这个属性实际可以从哪个系统获取”，就能切身体会到设计时容易卡住的地方。

在技术方面，数据建模的基础（规范化、主键设计、SCD 等历史管理）、SQL 和 Python，以及 dbt 这类转换工具的经验，都可以直接迁移使用。本体设计看起来是 Palantir 特有的工作，实际上它是通用数据建模能力的广泛应用。对于想成为 FDE 的工程师来说，无论能否拿到 Palantir 的 offer，这都是一个值得投资、几乎不会亏的领域。
