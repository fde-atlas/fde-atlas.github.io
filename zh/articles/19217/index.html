Kepler 如何开展前沿部署工程

原标题：How Forward Deployed Engineering is done Kepler

AI Engineer · 2026-04-30 · 约 11 分钟读完

摘要

Vinoo Ganesh 在 AI Engineer World's Fair 2026 的演讲中，以 Palantir 时期的真实案例阐述前沿部署工程：一个空日期导致 Cassandra 需 14TB 内存启动、47 页需求文档最终被一个 Slack 告警替代、Parquet 迁移因缺少查看器被搁置一年。他主张 FDE 不是售前角色，而是产品策略：深入现场发现真实问题，把一次性修复沉淀为可复用的产品能力，并明确支持边界与所有权。

要点

  • FDE 应被视为产品策略，而非按合同规模筛选客户的角色。
  • 空日期默认 Unix 纪元，导致 230 万个 keyspace 与 14TB 内存需求。
  • 47 页仪表盘需求被四小时上线的 Slack 告警方案取代。
  • 补建 Parquet 查看器后，迁移两天内获批，管道耗时从 17 小时降至约 2 小时。
  • 临时脚本可能存活多年，交付前须明确支持边界与归属。

现场团队应该帮助构建什么样的产品？

当你本应部署的产品还不存在时，前沿部署工程师该做什么？在 Ganesh 讲述的 2013 年前后的 Palantir 中，这就是最初的难题。前沿部署工程后来成为一种市场推广策略，但催生 Foundry 的那些工作，最初是为了发现并构建产品本身。

Ganesh 是通过可横向扩展的存储系统以及伊拉克和阿富汗（包括巴格拉姆）的部署工作进入这一领域的。问题在于如何让软件在关键环境中为操作人员真正可用。他创建了 Project Frontline，这是一个轮岗项目，将软件工程师调入前沿部署工作。据 Ganesh 介绍，约有 350 名工程师参与过该项目，其中包括后来加入 OpenAI、Anthropic 和 xAI 的人。随后他在 Citadel 建立了类似的项目，目标是构建帮助投资组合经理创造 alpha 的数据和软件产品。

他展示的 Shyam Sankar 的一篇帖子将 FDE 定位为一种产品策略，而非一个岗位。实际区别在于评估标准：FDE 应该发现机会并将客户解决方案泛化为产品能力，而不仅仅是按市值或合同规模来筛选客户。这正是 Ganesh 在 Kepler 与创始工程师 Susanna 一起采用的方法。

一个空白日期酿成存储灾难

Palantir 的内部 Phoenix 项目旨在公司迈向大数据时存储交易信息。团队在封闭环境中设计它，完全不了解其将要摄取数据的金融客户。对于一家大型金融机构，该设计使用按时间分桶的键空间来简化数据保留和滚动移除：旧数据可以通过停用其桶来删除。该设计在其假设条件下运行良好，但真实数据打破了这些假设。

空白日期被默认为 Unix 纪元，即 1970 年 1 月 1 日。随后保留逻辑试图为该日期到 2013 年之间的每十分钟区间创建一个窗口。一个缺失的值变成了分配数十年存储结构的指令。Ganesh 回忆起 230 万个 keyspace、每个 Cassandra 文件句柄 5 MB 的开销，以及 14 TB 内存的启动需求。这些数字是他事后对事故的回忆，并非通用的 Cassandra 容量规划规则；仅所述数量与每句柄开销相乘就已达 11.5 个十进制 TB，报告总数中其余部分仍无法解释。

没有其他团队可以呼叫来让这次部署成功。这次故障暴露的不仅是客户调研的缺失：工程师们在设计系统时，没有共同承担在客户环境中将其构建起来的责任。嵌入式所有权改变了产品团队学到什么、必须修复什么。 接下来的四条现场经验将展开这一区别。

找到仪表盘背后的决策

在一家货运与调度公司，运营副总裁提供了一份 47 页的需求文档，要求定制一个包含 14 项指标和下钻式警报的仪表盘。开发预计需要三个月。团队花了四个月来界定项目范围，直到一位工程师碰巧在探亲途中到访现场，问道：“周一早上你拿到这些信息后做的第一件事是什么？”

实际的运营流程远比所要求的 BI 系统简单：检查卡车是否晚点，然后打电话给调度安排应对。一条 Slack 警报就能提供触发这项工作的信号。Ganesh 表示，团队在四个小时内端到端地解决了调度问题。这一介入通过明确信息的用途改变了项目范围。

在构建之前，先弄清三件事：

  • 目标： 客户想要达成什么？
  • 下一步行动： 客户收到答案或解决方案之后会发生什么？
  • 当前方法： 客户现在是如何解决这个问题的？

仪表盘只是一种可能的实现方式。运营目标决定了它是否必要。

这就是现场工程中的 XY 问题：客户描述的是一个拟议的解决方案，而工程师必须还原其背后真正的问题。Ganesh 的经验法则是：当实际修复所需时间不到一天时，就构建、交付并闭环。一个有边界的修复不需要演变成扩展的产品愿景，也不需要新一轮的产品管理协调。

定义问题还能让团队对解决方案拥有主导权，并为决定下一步做什么提供依据。这解释了 FDE 在早期销售中的价值：小而成功的修复能赢得信任，进而接触到更深层次的问题。他们的价值并不取决于是否是特别善于社交的工程师。Ganesh 将 Foundry 能够跨行业通用的能力归因于数万小时的这类一线工作——解决具体问题，然后提炼出应纳入共享产品的能力。

这次数据迁移缺少了一个查看器

另一位客户每天在 S3 存储桶中接收约一 TB 的数据，给交付管道带来了压力。工程团队提议用 Apache Parquet 取代大型 CSV 交付，以降低管道、计算和数据成本。一位数据质量工程师反对这次迁移长达约一年。反复解释技术上的好处也无法消除她的反对意见。

一次现场走访让这个缺失的需求显现出来。她将 CSV 文件从 S3 下载到自己的 Windows 电脑上，双击打开，然后抽查数据。在她现有的工作流程中，Parquet 没有可以直接打开的等效查看工具。更换格式会移除一个必不可少的检查步骤。团队当晚就构建了一个 Parquet 查看器。

Ganesh 说迁移在随后两天内就获得批准，并大致回忆起管道执行时间从 17 小时降到了约两小时。他还提到数据成本有所降低，但没有给出具体数字。促成这一转变的关键是一个保留了用户检查数据能力的查看器；一旦该工作流程在迁移后得以保留，管道优化就能继续推进。

观察工作过程能产生与询问某人是否喜欢某个提议功能截然不同的证据。要留意：

  • 重复： 同一项任务在一小时、一天或一周内被反复执行。
  • 手动转移： 在不同工具之间复制粘贴。
  • 烦躁： 用户将某个步骤描述为他们不得不勉强去做的事情。
  • 上下文切换： 为完成一项工作而在工具或标签页之间来回切换。
  • 等待： 任务进行到一半时掏出手机，这可能表明软件缓慢或令人厌烦。

这些是调查工作流程的线索，而不是某个特定解决方案的自动证明。

一个有用的开场问题是：“你早上最烦的是什么？”解决一个小而反复出现的烦恼，会改变用户第二天的工作，并让你得以了解那些应当塑造产品的痛点。Maria 的巡检工作流程之所以被发现，是因为团队就在客户的办公楼里。Ganesh 把现场工牌和承包商邮箱地址形容为“许可证”，让你得以发现工作实际是如何开展的。他坚持亲身到场，源于从伊拉克和阿富汗到帕洛阿尔托和旧金山办公室的各类部署经历：定期的调研和远程会议室无法让常驻人员所看到的一切暴露出来。

把相互冲突的词汇转化为本体

在一家物流组织中，不同团队对同一个实体使用了不同的名称：

团队术语
销售Customer
运营Client
财务Billing entity
开发人员Org ID

这些差异导致了集成失败、数据质量问题和断裂的流水线。每个团队的语言在其自身环境中都说得通；当信息在团队之间流转时，困难才显现出来。

Ganesh 将本体描述为对这种人类协调问题的回应，而不是把所有东西塞进 Elasticsearch 并强加模式的结果。名词定义实体；动词定义操作。现场工程师必须发现两者，并决定软件如何表达它们。据他回忆，这位客户最终选定了“customers”；其他组织可能会以 ID 为准进行规范化。即使是像日活跃用户这样看似已经确立的指标，对产品团队而言可能意味着高质量的活动，而对 InfoSec 来说只是登录人数。

产品采用也会传播词汇。Ganesh 指出了诸如 skills 和 MCP 等术语的流行，包括将 MCP 术语宽泛地用于带提示词的函数调用。工程任务在于识别哪些短语被过度使用，以及含义在哪里发生了变化。追踪集成路径——Snowflake 到 Databricks、Palantir 到 Tableau，或 Anthropic 到 SAP——并找到翻译层。然后确定系统边界，以及那些不能被简单替换的记录系统。

同样的纪律也适用于 AI 故障报告。如果客户说某个 agent 一直失败，首先要弄清楚“agent”在该系统中指的是什么：一个提示词、一系列步骤，还是其他某种行为单元。定义这些术语能让问题具体到足以建模。一旦这些定义在平台上被固化，用户就可以用同一套词汇来推理后续问题。这就是 Ganesh 锁定论的基础：产品成为组织描述其工作的语言。

Foundry 本体 让这些定义成为可复用平台的一部分。在 Ganesh 的历史叙述中，正是这一基础让后来一代负责市场推广的 FDE 能够集成客户数据并销售现有产品。而构建这一基础的工程师们，首先需要通过部署工作去发现实体、操作和边界。

那个挥之不去的数据保留脚本

一位客户需要数据保留功能，于是 Ganesh 写了一个快速的 Groovy 脚本作为临时解决方案。它解决了眼前的问题，但并非为生产环境而设计。Ganesh 说，12 个月后，这个脚本已经蔓延到一家拥有近 10 万名员工的客户内部的多个部署中。这个关联如此持久，以至于成了他在 Palantir 的绰号；在他的婚礼上，宾客们甚至穿着印有这个绰号的 T 恤。

团队修复了一个问题，却没有确定最终状态，也没有把解决方案转化为产品能力。结果，这个临时方案被支持了多年。这就是把 FDE 简单定义为“让客户成功”所隐藏的失败模式：客户可以从中受益，而产品却不断累积负担，几乎没有获得可复用的能力。

快速交付，同时明确支持边界

Ganesh 将客户成功的工作分配给解决方案架构师，并对 FDE 提出额外的产品构建义务。在交付之前，明确支持边界：

  • 未来事故： 这是否可能在六个月后引发凌晨 2 点的紧急电话？
  • 产品权衡： 即时的缓解措施是否会在整个产品中产生不断累积的维护成本？
  • 交接： 工程师离开时，系统交给谁——客户、另一家机构，还是另一位 FDE？
  • 故障责任： 系统出问题时谁来响应，有哪些关键任务的工作依赖于它？
  • 处置： 这个修复应该进入核心产品，还是应该被丢弃？

即使是快速实现，也需要对其生命周期和负责人做出决策。

对于数据保留工具，一个有用的实现边界是将筛选过期记录与删除它们分开。下面的 Groovy 示例让保留建议可见，但不执行删除。它使用固定的截止日期，并拒绝缺失的日期，而不是默默将其视为陈旧数据：

groovy

import java.time.Instant

List<Map> proposeRetention(List<Map> records, Instant cutoff) {
    records.collect { record ->
        if (!(record.createdAt instanceof Instant)) {
            throw new IllegalArgumentException(
                "Missing or invalid createdAt for ${record.id}"
            )
        }
        [
            id: record.id,
            createdAt: record.createdAt,
            proposedAction: record.createdAt.isBefore(cutoff)
                ? 'DELETE'
                : 'KEEP'
        ]
    }
}

def records = [
    [id: 'tx-1', createdAt: Instant.parse('2025-01-01T00:00:00Z')],
    [id: 'tx-2', createdAt: Instant.parse('2025-07-01T00:00:00Z')]
]
def cutoff = Instant.parse('2025-06-01T00:00:00Z')
def proposal = proposeRetention(records, cutoff)
proposal.each { println "${it.id}: ${it.proposedAction}" }

这里，

tx-1

被建议删除，且

tx-2

用于保存；两条记录都不会被删除。这种分离创建了一种所有者可以检查并交接的东西。它并不能替代已部署的留存系统所需的关于授权、执行和故障处理的决策。

危险的假设是，仅仅因为代码被称作临时的，其有用性就会过期。Ganesh 提到在 IBM 大型机上运行了几十年的 COBOL，以此提醒人们软件的寿命可以远远超出其最初的用途。他的规划原则是：交付时假定该解决方案将运行 18 个月。这个时间跨度迫使人们区分“能赢得客户好感的修复”与“属于核心产品的能力”。

评估哪些内容进入了产品

如果需求收集、定期研究和记录的洞察都没有改变产品，那它们是不够的。Frontline 标准将探索与交付联系在一起：重新定义问题，进入客户的工作场所，去工作实际发生的地方。Ganesh 的例子包括阿富汗、伊拉克、索马里，以及一位在石油钻井平台上工作的同事。实地部署是接触软件必须支持的运营现实的一种手段。

这位工程师随后在离开前交付了修复方案，在产品生态系统中对其负责，并将观察到的问题转化为可复用的名词和动词。负责意味着出问题时接听电话，必要时出差。评估的问题是哪些内容交付进了产品，而不仅仅是工程师学到了什么。 这就形成了实地接触与更强共享平台之间的闭环。

Ganesh 用它所支持的决策来论证这一共享平台的价值：Citadel 的投资组合经理交易数亿美元，Palantir 的作战人员环境，以及商业客户的运营。在 Kepler，他将 FDE 作为产品开发的延伸来应用，以打造客户会持续使用的产品，因为这些产品解决了重大的问题。

公司所处的阶段很重要。成熟的 Palantir 可以围绕多年构建的产品基础部署工程师。早期公司必须首先发现能让这些部署发挥作用的产品。在产品基础尚未建立之前，将 FDE 主要当作市场推广的延伸，可能会在缺乏可复用产品支撑的情况下扩展针对客户的定制工作。
