摘要

这篇 Fatskills 学习指南面向 FDE，讲解现场技术写作的三类文档：runbook、事故报告和用户指南。文章通过银行欺诈检测模型等场景，给出具体写作步骤、示例命令和常见错误清单，并附面试题与实战教训，强调文档应在部署前写好、事先测试并考虑离线环境。

要点

  • Runbook 应在部署前编写、测试并放在运维易找到的位置。
  • 事故报告需含时间线、根因分析和带责任人的行动项。
  • 用户指南要面向非技术用户，避免术语并配截图。
  • 事故报告应使用无指责语言，聚焦系统而非个人。
  • 涉密离线环境需提前准备打印版文档并测试离线访问。

面向一线的技术写作（运行手册、事故报告、用户指南）

这是什么

一线的技术写作不在于精美的文档——而在于在出问题时挽救生命、任务或数百万美元的停机损失。作为一名 FDE，你会撰写： - 运行手册，用于自动化恢复步骤（例如，“当 GPU 节点在凌晨 3 点崩溃时如何重启机密 ML 流水线”）。 - 事故报告，用于解释为什么卫星数据流在实时行动中中断（以及如何预防）。 - 用户指南，面向从未接触过命令行的操作员（例如，“如何在不暴露 PII 的情况下将无人机影像上传到安全隔离区”）。

一线案例：你正在一个灾难响应总部现场。向一线救援人员提供实时洪水地图的数据流水线出现故障。客户的运营团队陷入恐慌。你上周编写的运行手册里有回滚部署所需的确切 kubectl 命令，但它埋在一份 50 页的文档里。你随后撰写的事故报告揭示了根本原因：一条配置错误的防火墙规则阻塞了 API 网关。现在你正在重写用户指南，加入一个 3 步的“防火墙检查”章节——因为下一个 FDE 不会再有时间来调试这个问题。

关键术语与概念

运行手册：用于从故障中恢复的分步操作手册（例如，“当主节点宕机时如何恢复 PostgreSQL 数据库”）。通常包括：

触发条件（例如，“告警：CPU > 95% 持续 5 分钟”）。

命令（例如，systemctl restart nginx）。

决策树（例如，“如果 df -h 显示 /var 使用率超过 90%，则运行 logrotate”）。

接入客户网络的权限（例如，“没有 ACO，你的笔记本电脑无法连接到机密隔离区”）。

一线规则：到达现场之前，务必先索取 ACO。

分步流程 / 一线流程

1. 编写运行手册（在火情发生之前）

场景：你正在向一家银行的本地集群部署实时欺诈检测模型。该模型每 3 天因 OOM 错误崩溃一次。你需要为银行的运营团队编写一份运行手册。

广告

步骤：1. 复现故障（在预发布环境中）：bash # 通过用过多数据运行模型来触发 OOM python train.py --batch-size 1000000 2. 记录修复方法（用 Markdown）：```markdown # 欺诈模型 OOM 恢复

触发条件：告警 container_memory_usage_bytes > 90% 持续 5 分钟。

## Steps 1. SSH into the bastion host: bash ssh [email protected] -i ~/.ssh/bank_key 2. Check pod status: bash kubectl get pods -n fraud-detection 3. If pod is OOMKilled, scale down and restart: bash kubectl scale deployment fraud-model --replicas=0 -n fraud-detection kubectl scale deployment fraud-model --replicas=1 -n fraud-detection 4. Validate: bash kubectl logs -n fraud-detection <pod-name> | grep "Model loaded" ``` 3. Test the runbook (have a teammate follow it blindly—if they fail, rewrite). 4. Store it where ops can find it (e.g., Git repo, Confluence, or a printed copy in the ops center).

2. 撰写事故报告（在火扑灭之后）

场景：银行的反欺诈模型在向 CFO 进行现场演示时宕机了。运维团队修复了问题，但 CFO 要求一份事后复盘报告。

步骤： 1. 收集数据（时间线、日志、截图）： bash # 获取最近一小时的 Pod 事件 kubectl get events -n fraud-detection --sort-by='.metadata.creationTimestamp' | tail -n 20 2. 撰写时间线（在 Google Doc 或 GitHub Issue 中）： ## 时间线 - 14:00 UTC：CFO 演示开始。 - 14:02 UTC：模型 Pod 崩溃（OOMKilled）。 - 14:03 UTC：运维团队收到 PagerDuty 告警。 - 14:05 UTC：运维执行 kubectl scale（按照运维手册）。 - 14:07 UTC：模型恢复上线。 3. 根因分析（RCA）： - 发生了什么？为了演示增大了模型的批处理大小，导致 OOM。 - 为什么？演示前没有进行负载测试。 - 如何预防？添加演示前检查清单（例如“以 2 倍预期负载进行测试”）。 4. 行动项（指定负责人和截止日期）： | 行动项 | 负责人 | 截止日期 | |-------------|-------|----------| | 在运维手册中添加演示前负载测试 | Alice | 2024-06-01 | | 为演示环境设置 OOM 告警 | Bob | 2024-05-25 | 5. 与利益相关者分享（CFO、运维团队、你的经理）。

3. 撰写用户指南（面向非工程师）

场景：银行的反欺诈分析师需要使用你的新仪表板，但他们从未用过命令行界面。

步骤： 1. 访谈一位用户（问：“你打开仪表板后做的第一件事是什么？”）。 2. 按照他们的技能水平撰写（避免使用“API endpoint”之类的行话）： ```markdown # 反欺诈仪表板用户指南

## 如何筛选交易 1. 点击日期范围选择器（右上角）。 2. 选择“最近 7 天”。 3. 点击应用。

## 故障排除 - 问题：“没有数据显示。” - 解决方法：检查你的 VPN 连接（参见 VPN 指南）。 ` 3. 添加截图（代码片段使用carbon.now.sh，图表使用draw.io）。 4. 与非技术用户一起测试（例如让 CFO 的助理试用）。 5. 以他们偏好的格式发布（例如隔离网络使用 PDF，企业环境使用 Confluence）。

常见错误

错误

改正方法

原因

事后才写文档

在部署到生产环境之前先写好运维手册。

如果系统在凌晨 3 点崩溃，你不会记得修复方法。

假设用户懂你的行话

在术语表中定义“pod”、“enclave”等术语。

银行的欺诈分析师不懂 Kubernetes。

不测试操作手册

让一位同事在没有你帮助的情况下按照操作手册执行。

如果他们无法解决问题，这份操作手册就没有用处。

把重点埋在事故报告深处

把根本原因放在第一段。

高管不会读到第 1 页之后的内容。

在事故报告中使用“我们”或“他们”

使用无指责的语言（例如，“防火墙规则被错误配置了”）。

事故报告关注的是系统，而不是人。

FDE 面试 / 实战经验洞察

1. “范围蔓延”陷阱

面试官：“你在客户现场，客户要求一个不在原始范围内的功能。你会如何回应？”现场回答：1. 澄清需求：“能带我了解一下这对任务的影响吗？如果不加这个功能会怎样？” 2. 评估风险：“这个变更需要重新进行系统 ATO 认证，需要 30 天。这会成为上线的阻碍吗？” 3. 提出替代方案：“我们可以把这个作为第二阶段的项目，或者暂时先提供一个手动流程。” 4. 记录决策：更新决策日志和用户指南以反映这一变更。

广告

原因：客户往往不了解范围变更的代价（例如，重新进行系统 ATO 认证）。你的职责是在让客户满意的同时保护任务本身。

2. “物理隔离环境文档”噩梦

实战经历：你要部署到一个没有互联网的涉密网络。你带了一个装有文档的 U 盘，但客户的安全团队禁止一切外部存储介质。现在你既没有操作手册，也没有用户指南和事故报告。

现场经验：- 始终携带关键文档的打印版（例如操作手册、ATO 认证材料）。- 在到达之前，把文档托管在客户的内部 Wiki 上（例如 Confluence、SharePoint）。- 测试离线访问（例如下载操作手册的 PDF 并在涉密机器上打开）。

快速检测问题

1. 你正在为一个数据管道编写操作手册，该管道在输入 CSV 出现新列时每次都会失败。你的操作手册第一步应该是什么？

回答：“使用 pandas.read_csv(..., nrows=5) 检查输入模式中是否存在意外的列，并记录不匹配的情况。”解析：在调试管道之前，务必先验证输入。

2. 你在客户现场，客户的运维团队说：“仪表盘坏了。”他们不给你日志或错误信息。你会怎么做？

回答：“询问：‘出问题时你们在做什么？能给我看一张截图吗？’然后检查浏览器控制台（F12 → Console）中的错误。”解析：非技术用户往往描述的是症状，而不是根本原因。先复现问题。

3. 你正在为一次系统宕机撰写事故报告。根本原因是一条配置错误的防火墙规则。你会在报告中如何表述？

回答：“防火墙规则 DENY 10.0.0.0/8 已被应用，阻断了 API 与数据库之间的流量。”解释：无指责的语言聚焦于系统本身，而不是犯错的个人。
