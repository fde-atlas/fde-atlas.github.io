你的 FDE 现场面试就在下周：如何利用剩下的这几天

原标题：Your FDE onsite is next week: how to spend the days you have

FDE Interview Prep · 2026-09-25 · 约 12 分钟读完

摘要

这篇文章是一份 FDE（前沿部署工程师）现场面试的短期备考指南，针对只剩几天时间的候选人。作者主张先用一天做无 AI、限时、录音的自我诊断，找出技术与客户沟通两方面的弱项，再按弱项安排中间几天的限时练习、项目深挖和故事演练，考前一天只做完整彩排而不学新内容。文中引用 Baseten 的“双重门槛”招聘标准，以及 Google 和 Reddit 上候选人因技术深度不足被拒的案例，强调沟通能力无法弥补技术短板。

要点

  • 第一天做限时、无 AI、录音的诊断，找出最弱环节。
  • Baseten 等公司采用“双重门槛”：技术标准与产品直觉并重。
  • 两份候选人报告显示沟通好但技术不够深仍会被拒。
  • 中间几天按弱项排优先级：编码、案例、项目深挖、故事。
  • 考前一天只做完整彩排，面试当天早晨保持简单。

招聘官的邮件说你的现场面试就在下周。你只有几天而不是几周，诱惑是把所有东西一次性全打开：一本新的系统设计书、一份长长的题目清单、公司写过的每一篇博客。别这样做。第一天用来做一个简短的自测，全程不用 AI，找出你在工作的哪一半更弱。中间几天针对这个短板做限时练习，同时深入复盘你自己的项目，并把你的故事大声讲出来。面试前一天做排练而不是临时抱佛脚，面试当天上午保持平淡。这篇文章是 FDE 面试指南的短期突击版，后者完整覆盖了每一轮面试。

第 1 天：诊断

第 1 天回答一个问题：在真实条件下你最薄弱的环节在哪里？一次限时尝试比任何自我评估都更能说明问题。

第零步：询问招聘人员面试流程包含哪些环节

在做任何事之前，先发一封邮件。本周之后的每个选择都取决于这个答案：

能否分享一下面试有几轮、每轮时长、编程所用的语言或环境，以及是否有环节允许使用 AI 工具？

在等待回复期间，先根据现有信息做计划，然后删掉下面与你的面试流程不符的环节。

诊断任务的规则：

  • 不用 AI。 不用助手，不用能替你写函数的自动补全，不开聊天窗口。Google 公布的招聘流程说明面试期间不允许使用 AI 工具。来源 6Our hiring process - Google Careers发布方Google来源类型公司招聘页面 Anthropic 对现场面试的要求是除非 Anthropic 另有说明，否则不得使用 AI 辅助。来源 7Guidance on Candidates' AI Usage发布方Anthropic来源类型公司网站 无论如何，请了解你所在雇主的规定，并在练习时不使用 AI。关于各公司各阶段 AI 规则的课程梳理了谁允许什么。
  • 限时。 使用招聘人员告诉你的环节时长。如果没给，就选一次连续作答，计时器结束时停止。
  • 出声并录音。 用手机录语音备忘录。今晚你会回听，这段录音是你这一周做出的最有用的东西。

你没见过的算法题

选一道你从未做过的中等难度题目。最慢端点问题就不错：解析 Web 服务器日志，按 p95 延迟报告最慢的端点。它看起来像热身题，但在解析任何数据之前，你必须先出声定义一些概念，而这正是值得练习的部分。做完之前不要看它的框架。

修复非你所写代码中的 bug

客户工作意味着要阅读别人写的代码。这里有一个小 bug。客户的抱怨：“导出总是提前停止。最后一批记录永远到不了。”

def fetch_all(get_page):
    items, cursor = [], None
    while True:
        page = get_page(cursor)
        cursor = page["next"]
        if cursor is None:
            break
        items.extend(page["items"])
    return items

找出 bug，并写出一个在这段代码上会失败的测试。设一个 10 分钟的计时器。答案在下面。

答案

循环在添加该页的条目之前就在最后一页处中断了。所以最后一页总是丢失，而只有一页记录的客户会得到一个空导出。先写测试：

def test_last_page_is_kept():
    a = {"next": "p2",
         "items": [1, 2]}
    b = {"next": None,
         "items": [3]}
    pages = {None: a, "p2": b}
    assert fetch_all(pages.get) == [1, 2, 3]

它在旧代码上会失败，旧代码返回

[1, 2]

。修复方法是在检查游标之前调用

items.extend(page["items"])

。然后添加一个只有一页数据的第二个测试，因为那位客户正是什么都得不到的人。

你要评分的不是你是否找到了 bug，而是你工作的顺序：你是否在改代码之前先用测试复现了它，你是否说出了客户看到的现象？如果想要更难的题目，陌生 bug 问题在 Pro 版中。

客户案例

两份报告都关注技术深度，其中一位发帖人已经通过了编程环节。所以技术方面在这里有两个任务，后面的项目深挖则考察你必须解释清楚的深度。客户方面仍然需要一次真实的测量。\/try 上的免费案例让你在十分钟倒计时内，针对一个 AI 客户运行建筑许可案例，评分会引用你自己的原话。先冷启动跑一遍，然后在阅读其他任何内容之前先看评分。

根据录音为你的第 1 天打分

  • 算法：你是否在计时内解出了题目？
  • 算法：你是否在写代码之前说明了假设（输入格式、什么算作端点、取哪个百分位）？
  • 算法：你是否在没人要求的情况下主动说明了时间和空间复杂度？
  • 算法：是否出现了你不希望面试官经历的沉默？
  • Bug：你是否在修改代码之前先写了一个会失败的测试？
  • Bug：你是否说明了客户的体验，而不仅仅是代码做了什么？
  • 案例：你是否在提出任何方案之前先问了为什么？
  • 案例：你是否承诺了自己无法兑现的事情？

解读你的诊断：先弥补哪个短板

你的录音会暴露不止一个弱点，而你有时间弥补一两个。以下是我们排序的方法（这是我们的方法，不是雇主的评分标准）。

你看到的问题时间花在哪里
卡在算法上每天一道限时编程题
解出来了，但全程沉默把旧题大声重新解一遍
靠猜修好了 bug每次修复都先写一个会失败的测试
在案例中立刻提出方案每天一个案例，然后看它的评分
承诺了无法兑现的日期重放案例中的艰难时刻
全部干净利落项目深挖和故事

先弥补会终结整个流程的短板。一个沉默但正确的解法比一个卡住的解法更容易在几天内修复，而在构建之前先问为什么可以在一个晚上练成。无法得出可用的解法需要最多的练习，所以如果你属于这种情况，编程每天排在第一位，其他一切都围绕它压缩。

中间的日子：案例、编程、你的项目、故事

每个中间日有四个板块：你的短板、一个案例或编程、你的项目、你的故事。诊断结果决定哪个板块排在最前——趁你精力充沛时进行，并占用最多时间。这个分配是我们的方法，不是雇主的规则。我们的中间日是 90 分钟的第一板块，然后是 45 分钟的案例或编程板块、30 分钟的项目板块和 20 分钟的故事板块。加上休息，时间一到就停止。以下是一个第 1 天暴露出编程短板的人的示例周计划：

天第一板块短板块（按顺序）
第 1 天诊断回听录音，填写清单
第 2 天编程，限时案例、项目草稿、故事
第 3 天编程，限时案例、项目、故事
第 4 天编程，限时案例、项目、故事（录音）
第 5 天案例编程、项目大声讲、故事
面试前一天完整彩排不学新内容

如果你的短板是案例，就调换两栏：每天先做案例，并在短时间段里做一道限时编程题。

天数不够？四天的话，去掉第 4 天，把它的故事移到第 5 天。三天的话，保留第 1 天、一个编程日（同时完成项目草稿）以及面试前一天。诊断和彩排绝不能省。

限时案例

如果你的面试流程有案例或角色扮演环节，这是最开放的一轮：一个客户问题、一份模糊的需求、一个计时器。先读一遍一页纸方法，然后开始练案例。每次练完，挑出得分最低的一项，只针对这个改进点再练一次。对于角色扮演环节，客户轮概览说明了第一分钟该说什么。

第一分钟大概是这样：

  • 客户：“审批流程太慢了。给我们做一个仪表盘。”
  • 糟糕的开场：“好的，你们有哪些数据？”
  • 有力的开场：“在选工具之前，哪个环节的延误最伤，谁在承受这个延误？如果三周内我们只能做对一件事，那是什么？”

有力的开场把仪表盘当作对解决方案的猜测，而不是目标，并追问真正重要的结果。这样第一句话就满足了“先问为什么再提方案”这一条。

常见错误：只读案例资料而不动手练。只有计时器能告诉你真实水平。

编程

让练习匹配目标公司的考察内容。FDE 编程轮考察什么按公司逐家梳理了证据：算法题、实际构建、读别人的代码或借助 AI 的构建。然后，每道题都要：

  • 在优化之前，先把暴力解法大声说出来；
  • 在面试官开口之前，主动说明复杂度；
  • 写一个能用手工验算的数字测试；
  • 说出一个真实客户数据会破坏的点。

最后这个习惯是编程轮中另一个常见的考察点。比如：“我暂时用邮箱作为键。如果 CRM 里有联系人 ID，我会改用它，因为一个人有两个邮箱地址就会被重复计数。”

项目深挖

如果你的面试流程有项目深挖环节，这是唯一一轮由你自己挑选材料的，所以也是几天内最容易准备的。项目深挖问题会问到问题背景、你的设计、出了什么问题以及你会怎么改。按下面方式准备：

  • 凭记忆在纸上画出架构，然后对照真实系统检查。
  • 写下你自己测出来的数字：负载、延迟、成本、错误率。只要真实数据。
  • 选出你现在会改变的一个决策，并说明原因。
  • 写下你最害怕的三个追问，并逐一大声回答。

价值就在“恐惧清单”里。如果你最怕的问题是“为什么选那个数据库？”，你的回答应该从约束条件说起，而不是品牌：“我们需要在订单和支付之间支持事务，而且团队已经在用 Postgres。”

把故事大声讲出来

写下几个故事：一件你端到端负责的事、一次属于你的失败、一个难缠的利益相关者、一次你改变主意的经历。然后把每个故事大声说出来，录音，反复删减，直到它在一分钟左右落地，并在结尾有结果。

用同样的方式练习你的自我介绍。每位新面试官可能最先听到它。以“为什么想要这个职位”结尾，而不是以你上一份工作结尾。

常见的错误是：写好了故事却从不说出来。一个读起来不错的故事往往讲起来太长，把结果埋没了，还漏掉了你做出决策的那部分。

面试前一天：排练，不要突击

你今天学的东西明天不可能稳定到能用，而新话题大多只会增加疑虑。

  • 完整跑一次模拟。 一个案例、一道编程题和一个故事，连续进行，计时，录音录像。那篇模拟面试的文章讲了如何自己组织一次。
  • 做一张卡片。 写上你项目的数据、每个故事的第一句话，以及你要问每位面试官的问题。今晚读一遍，早上再读一遍。
  • 安排好后勤。 地址或链接、各轮的顺序、如果知道的话还有面试官的名字、充满电的笔记本电脑，以及如果有远程环节，可用的摄像头和麦克风。
  • 早点收工。 今晚再多做一道题不会改变明天的表现，但休息好的头脑可能会。

现场面试当天早上

保持平淡而温暖。

  • 大声做一道简单题，那种不假思索就能完成的题，让声音和双手配合起来。
  • 把自我介绍大声说一遍。
  • 重读一遍你的卡片。仅此而已。
  • 如果有远程环节，在开始前关闭所有 AI 工具和所有不需要的标签页。

轮次之间，重置状态。不要在脑子里回放上一轮：下一位面试官并不在场，把糟糕的一轮带进好的一轮，正是让一次失误变成两次的原因。关于常见失误及其补救方法，见常见错误那篇文章。

三句值得提前准备的话，因为它们能挽救整轮面试：

  • “开始之前，让我先确认一下目标是否正确。”
  • “我会先做简单版本，然后告诉你它在哪里会出问题。”
  • “这个我还不知道。但我会这样去弄清楚。”

想让每一天都被安排好？五天计划

如果你不想自己规划每一天，五天计划会为你设定每天的任务块，基于同样的理念：先测量，然后在计时下练习薄弱环节。

无论你选择哪条路，都不要让第一天溜走。今天就到 /try 运行免费案例，让分数告诉你本周剩下的时间该怎么安排。如果诊断显示免费材料没有覆盖的短板，Pro 提供 7 天免费试用（覆盖本周），可解锁所有课程和参考答案，包括上面的陌生 bug 题。

人们常问的问题

我能在一周内准备好 FDE 现场面试吗？

如果你把时间花在各轮考察的内容上而不是学新材料，就能准备得不错：先做诊断，然后针对你最弱的一轮进行限时练习，深入剖析你的项目，并把你的故事大声讲出来。

FDE 现场面试前一天我该做什么？

排练，不要学新材料：做一次限时模拟，包含一个案例、一道编程题和一个故事；准备一张卡片，写上你项目的数据和故事开场白；安排好后勤事宜；早点结束。
