延迟预算

原标题：Latency budget

FDE Interview Prep · 2026 · 约 2 分钟读完

摘要

这篇文章讲解延迟预算：先根据用户需求设定总时长上限，再分配到请求经过的各步骤，并按 p95/p99 尾部而非仅中位数来规划。文章引用 Dean 和 Barroso 的《The Tail at Scale》说明扇出请求会被最慢调用拖慢，并针对模型调用拆分首 token 时间与输出时间，强调 Agent 场景需限制步数。文中引用 Cursor 与 Cohere 的 FDE 职位说明该主题在生产质量中的位置，最后建议用分步追踪定位慢点，并给客户量化的提速选项。

要点

  • 延迟预算应从用户需求出发设定总上限，再分配到各步骤。
  • 必须预算 p95/p99 尾部延迟，扇出请求会被最慢调用拖慢。
  • 模型调用可拆为首 token 时间与输出时间，缩短输出常是最便宜的优化。
  • Agent 步骤串行且数量不定，不限制步数则预算无意义。
  • 排查慢问题时先要分步追踪，优先查看模型调用。

全文

请求可能耗费的总时间，分配在其经过的各个步骤上，既测量中位数，也测量慢尾部分。

也称为尾延迟

根据用户需求设定总时间，然后分配给请求经过的各个步骤，例如检索 150ms + 重排 100ms + 模型 1200ms + 开销 50ms <= p95 下 1500ms。除了中位数，还要为尾部（p95 或 p99）做预算，因为扇出的请求要等待最慢的调用：100 个并行调用各自有 1% 的概率错过 p99，那么 1 - 0.99^100 ≈ 0.63 的请求会碰到至少一个慢调用（Dean 和 Barroso，The Tail at Scale）。

对于模型调用，还要进一步拆分该步骤：首 token 时间随提示词增长，其余部分是输出 token 数乘以每 token 时间，因此限制或缩短输出往往是最划算的改进。在 AI Agent 中，步骤串行运行且数量不定，所以必须限制步骤数，否则预算就是空谈。各步骤 p95 之和通常会高估端到端 p95；应测量端到端尾部，并利用各步骤的追踪数据找出该削减哪一步。

截至 2026 年 9 月，Cursor 的职位列表在 FDE 所负责的生产质量中列出了延迟与成本的权衡，而 Cohere 的 Agentic Platform FDE 职位要求建立评测框架，在衡量准确性和安全性的同时衡量 Agent 延迟。来源 1前沿部署工程师发布方Cursor（Ashby 招聘板）来源类型公司招聘板来源 2前沿部署工程师，Agentic Platform发布方Cohere（Ashby 招聘板）来源类型公司招聘信息 当客户说助手很慢时，先要求提供各步骤的追踪数据再猜测，并优先查看模型调用。然后提出各种方案及其代价（缩短输出、流式输出首 token、缓存稳定的提示词前缀、将简单请求路由到更小的模型、减少检索的上下文），并用客户自己系统的数据让他们在更快和更准确之间做选择。
