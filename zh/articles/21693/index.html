法律 DMS 连接器：iManage 访问与信息隔离墙

原标题：Legal DMS connector: iManage access and ethical walls

FDE Times · 2026-10-26 · 约 6 分钟读完

摘要

文章以 Legora 的 FDE 招聘为切入点，指出在律所场景中，连接器比模型更关键。iManage 等文档管理系统仍是唯一权威数据源，权限与道德墙决定谁能看到哪些文件。作者提出共享接口加各 DMS 适配器的架构，强调每次调用都携带用户身份、由 DMS 过滤权限，并给出六格权限测试矩阵与常见复用性错误。

要点

  • DMS 仍是权威数据源，连接器不得复制文档。
  • 权限由 DMS 决定，道德墙泄露属严重事故。
  • 共享接口加适配器，连接方式可从 REST 换到 MCP。
  • 每次调用携带用户身份，禁止服务账号。
  • 六格权限矩阵应在每次权限变更后重跑。

Legora 的 FDE 招聘启事表明，iManage 等文档系统仍然是记录系统，而每个案件上的访问权限决定了要构建什么。

简要概述

  • Legora 的 FDE 招聘启事要求掌握 iManage、SharePoint 或 NetDocuments、SSO（SAML、OIDC）、REST 和 webhooks 的知识，并赋予编写可复用连接器的职责。
  • 第一条规则：原始 DMS 仍然是记录系统。DMS 权限和律所的信息隔离墙决定每个人可以检索哪些文档。
  • 连接方式可能从 API 转向 MCP，但权限控制和共享界面必须保持不变。

在一家希望合伙人能够查询存储在 iManage 中的案件文档的律师事务所的首次技术会议上，模型几乎不会被提及。IT 负责人只问一个问题：如果律师 A 被隔离墙隔离在案件 X 之外，你的系统会不会向 A 展示案件 X 的哪怕一页内容？

这份工作正是从这个问题开始的。Legora 将其前沿部署工程师职位描述为处于产品工程和客户成功之间。该工程师在部署期间和部署之后与企业客户并肩工作，编写将 Legora 平台连接到客户系统的生产代码。

招聘启事明确列出了你需要掌握的知识：iManage、SharePoint 或 NetDocuments 等文档管理系统、通过 SAML 和 OIDC 实现的 SSO，以及 REST 风格的 API 和 webhooks。

它还赋予一项具体职责：构建和维护连接器、自动化脚本和可复用工具，以便后续部署运行得更快。

这项技能并非 Legora 独有。它可以迁移到任何向拥有敏感数据的行业销售软件的公司。

谁拥有文档？

当 Legora 于 2026 年 10 月推出其集成生态系统时，它强调了一个原则：律师可以在 Legora 内浏览、搜索和处理案件文档，但底层平台仍然是记录系统。这看起来像是写给市场团队的一句话。在实践中，它是连接器最重要的设计要求。

这一原则带来两个后果。DMS 保存每份文档的正式副本，包括其版本、元数据和编辑历史，因此连接器不得创建会逐渐偏离原始文档的副本。而且访问权限由 DMS 决定，而不是由你决定。

据 LawNext 报道，在 iManage 集成中，iManage 权限决定每个用户可以检索的内容。Artificial Lawyer 也报道称，律所已经实施的信息隔离墙和安全限制决定了 Legora 可以访问的内容。

信息隔离墙会在存在利益冲突时阻止律师访问某个文件。一份文档穿过这道墙是严重事故，远超普通 bug 的范畴。

一个界面，多个适配器

为什么招聘广告要强调“可复用”这个词？一家律所用 iManage，下一家用 NetDocuments，再下一家把所有东西都放在 SharePoint 里。如果每次都从零开始，你的经验永远无法积累。

一个合理的划分是：为应用提供一个统一的共享接口，底层为每个 DMS 分别配置一个适配器。下面的示意图展示了这一设计；它并非 Legora 的代码：

from typing import Protocol

class DMSConnector(Protocol):
    def search(self, user: UserIdentity, query: str,
               matter_id: str | None = None) -> list[DocRef]: ...
    def fetch(self, user: UserIdentity, doc: DocRef) -> DocContent: ...
    def handle_event(self, event: dict) -> None: ...  # webhook: doc moved, permission changed

class IManageAdapter:
    def search(self, user, query, matter_id=None):
        token = self.tokens.for_user(user)  # user's own token, never a service account
        return self.client.search(query, matter=matter_id, auth=token)

    def fetch(self, user, doc):
        token = self.tokens.for_user(user)
        # the DMS checks permissions again on every read
        return self.client.get_document(doc.id, auth=token)

    def handle_event(self, event):
        if event["type"] in ("permission_changed", "document_moved"):
            # drop results computed under the old permissions
            self.cache.invalidate(matter_id=event["matter_id"])

关键的细节在于

UserIdentity

出现在每个函数中。每次调用都携带请求者的身份，该身份来自 SSO（SAML 或 OIDC），适配器使用同一身份去调用 DMS。DMS 随后根据该人的权限对搜索和打开操作进行过滤，你无需重新实现访问控制逻辑。

当连接方式发生变化时，这一设计也能带来回报。据 LawNext 报道，Legora 已通过 API 与 iManage 集成，并计划连接 iManage MCP Server。

生态系统发布公告还提到，iManage 和 NetDocuments 已通过 Model Context Protocol 实现知识与搜索方面的连接。如果连接类型只存在于适配器中，你就可以更换适配器，而无需改动接口或权限测试。

上线前的六格矩阵

伦理隔离墙的测试方式应当与安全测试一样。设想一个包含两个案件和三名律师的场景。An 负责案件 1001。Binh 负责案件 1002。Chi 是律所的一名律师，从未参与过案件 1001，但由于利益冲突，被伦理隔离墙挡在该案件之外。

用户在案件 1001 中搜索在案件 1002 中搜索
An返回结果为空
Binh为空返回结果
Chi（被隔离墙挡在 1001 之外）为空，即使输入确切的文档名称为空

三个人乘以两个案件共六个格子，每个格子都是一项自动化测试。最重要的格子是 Chi 在案件 1001 中的那一格。如果搜索索引是用一个能读取所有内容的公共服务账号构建的，那一格几乎肯定会返回结果，这意味着发生了泄露。

每次权限变更后都要重新运行这个矩阵。在 DMS 中将 An 从案件 1001 中移除，将 webhook 事件发送到

handle_event

，然后检查 An 的下一次搜索是否返回为空。这正是过期缓存容易悄悄引发问题的地方。

在客户现场的端到端工作

Legora 让其 FDE 负责整个技术范围界定工作，从收集需求到设计集成架构。在律所，范围界定会议应回答四个问题：用的是哪个 DMS，是云端还是本地部署？SSO 使用 SAML 还是 OIDC？伦理隔离墙在哪里配置？DMS 在权限变更时是否会发出 webhook？

之后，工作顺序应该是：接口、适配器、身份映射、测试矩阵、Webhook 处理，然后才是问答功能。很多团队反其道而行，因为问答功能在演示中更出彩。但一次数据泄露就足以让你丢掉合同。

最后一步——也是最常被跳过的一步——是把你的经验反馈给工程团队和产品团队。Legora 的招聘启事中写道，FDE 会与这两个团队合作，共同改进集成和共享产品。

如果你发现自己连续为三个客户编写相同的权限组映射，那就说明它应该被放进标准连接器中。

让连接器无法复用的错误

最常见的错误是把整个 DMS 复制到一个单独的存储中以加快搜索速度。这违反了两条原则：副本会偏离权威数据源，而且权限会在复制的那一刻被冻结。

第二个错误是让客户特定的逻辑渗入共享接口，比如一个名为

matter_code_format_firmB

的字段。所有差异都应该放在适配器或配置文件中。

第三个错误是跳过身份映射。SSO 中的电子邮箱和 DMS 中的用户名并不总是匹配的。只要映射错一个人，测试矩阵就变得毫无意义。

在简历上展示这项技能

阅读 FDE 招聘启事时，留意诸如“可复用连接器”、具体的 DMS 产品名称、SAML/OIDC 和 Webhook 等字眼。这些信号表明该工作偏向集成而非演示。

在简历上，不要只写“集成了 SharePoint”。要写明你构建了一个连接器，在多次部署中复用了它，用明确数量的测试用例测试了权限，并且没有让任何文档穿透信息隔离墙。招聘人员看到这句话，就会明白你真正回答了 IT 负责人的问题。

模型会不断变化，连接方式也会不断变化，从 REST 到 MCP，再到未来的任何标准。但“谁可以查看什么”这个问题不会变，而用测试而非承诺来回答这个问题的 FDE，才是客户信任的人。
