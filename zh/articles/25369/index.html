Microsoft 365 Copilot 导入支持｜购买许可证之前需要准备的事项

原标题：Microsoft 365 Copilotの導入支援｜ライセンスの前に整えること

FDE Consulting · 2026-11-08 · 约 8 分钟读完

摘要

这篇日文文章指出，企业在采购 Microsoft 365 Copilot 许可证之前，应先完成权限、网络、规则等内部准备，否则许可证会闲置。作者基于 Microsoft 官方文档，梳理了免费 Copilot Chat 与付费版的差异、许可证与网络等技术要件、文件权限整理的顺序、试点部门的选择与使用率测量方法，并划分了哪些工作适合外包、哪些必须由企业内部决定。

要点

  • 持有 Microsoft 365 许可证的用户可免费使用 Copilot Chat，访问内部数据才需付费许可证。
  • 付费版会通过 Microsoft Graph 自动引用邮件、文件等内部数据，权限过松会导致机密资料出现在回答中。
  • 技术要件包括 Entra ID 账户、Exchange Online、OneDrive，以及放行 *.cloud.microsoft 域名。
  • 建议先让全员用 Copilot Chat，再从资料参照需求多的部门开始加购付费许可证。
  • 试点效果应先记录会议纪要、邮件回复所耗工时，再用管理中心的利用率报告对比。

决定引入 Microsoft 365 Copilot 后，首先想到的往往是询价许可证。然而，并不是从分配许可证的那天起所有人就会开始使用。如果公司内部文件的权限、网络设置、谁用来做什么都还没确定，买来的许可证就会闲置，一个月又一个月地过去。

下面以 Microsoft 的文档为基础，按顺序列出在购买许可证之前需要在公司内部准备好的事项。在委托导入支持公司之前先读一读，更容易决定哪些环节交给外部、哪些环节由公司内部承担。信息泄露与权限设置已单独整理在 Microsoft 365 Copilot 的安全性中。另外，Microsoft 365 Copilot 现已更名为 Microsoft Copilot。本文仍沿用搜索量较高的旧名称。

先弄清 Copilot Chat 与付费版 Copilot 的区别

首先要确认的是，是否真的需要额外的许可证。根据 Microsoft 的说明，持有相应 Microsoft 365 许可证的用户，无需额外许可证即可使用 Copilot Chat。

区别在于如何使用公司内部的数据。Copilot Chat 的回答主要基于 Web 信息。要使用公司内部的数据，需要上传文件，或使用 Teams 和 Outlook 中打开的内容。持有额外许可证的用户可以通过 Microsoft Graph 自动引用邮件、文件、会议、日历等公司内部数据。Word、Excel、PowerPoint 中的 Copilot，只要有额外许可证也可以优先使用。

确认事项Copilot Chat（无额外许可证）Microsoft 365 Copilot（有额外许可证）
回答所用的信息主要为 Web。公司内部文档需自行提供Web 以及本人有权查看的公司内部数据
在 Word 和 Excel 中使用视合同而定，可能无法使用，或受拥挤程度限制而成为标准访问可优先使用
适合的用法文章草稿、摘要、查询资料基于过往邮件和资料的工作
需先准备的事项使用规则使用规则之外，还有公司内部文件的权限

表格右下角占了导入工作量的大部分。持有额外许可证的人，只需向 Copilot 询问，就能找到自己有权查看的公司内部数据。如果在权限设置仍然宽松的情况下交付，本不该被看到的资料就会出现在回答中。

在我看来，先让所有人使用 Copilot Chat，再从需要参考公司内部过往资料较多的部门开始追加付费许可证，这样的顺序阻力最小。如果正在与 ChatGPT 等其他生成式 AI 一并比较，可以参考 ChatGPT 的公司内部使用的步骤。

购买许可证前需确认的要件

Copilot 除了许可证之外，还有其他必须满足的要件。我从 Microsoft 的要件页面中摘出了导入前需要确认的项目。

项目Microsoft 的要件公司内部需确认的事项
原有许可证需要有相应的 Microsoft 365 等合同现有合同是否属于 Copilot 的适用范围
账户需要 Microsoft Entra ID 的工作账户使用者是否全部以公司账户登录
邮件使用邮件和日历的功能需要 Exchange Online 邮箱邮件是否仍存放在公司内部服务器上
文件部分功能需要 OneDrive 账户个人文件是否存放在 OneDrive 中
会议要在会后使用会议内容，需要设置文字记录或录制公司内部是否允许会议文字记录
网络允许 *.cloud.microsoft 整个域名是否被代理或防火墙拦截

关于原有许可证，Microsoft 的许可证页面列出的适用对象包括 Microsoft 365 E3、E5、Business Standard、Business Premium 等。面向中小企业的 Microsoft Copilot Business 适用于使用者不超过 300 人的组织，按年签订合同。超过 300 人的组织需使用面向大企业的合同。适用合同和条件可能发生变化，购买前请在 Microsoft 的服务说明和价格页面确认。

网络方面容易被忽视。Microsoft 表示，

*.cloud.microsoft

不支持只允许其中部分 URL 的设置。如果在网络边界拦截 WebSocket 通信，或检查 TLS 通信的设备妨碍连接，Copilot 的功能可能无法运行。建议提前把这一要件交给信息系统部门或网络维护公司。

管理角色也有需要决定的事项。Microsoft 提供了 AI 管理员角色，无需全局管理员权限即可管理 Copilot 和 AI 功能。决定由谁负责 Copilot 的设置，并为其赋予该角色，就可以避免增加全局管理员。

先整理公司内部文件的权限

满足要件后，接下来是公司内部文件的权限。根据 Microsoft 的说明，Copilot 只会显示使用者至少拥有查看权限的公司内部数据。虽然不会出现新的可见内容，但一直向全公司共享的文件，只需向 Copilot 询问即可找到。

Microsoft 的要件页面虽然表示这并非强制，但强烈建议在使用 Copilot 之前先打好数据管理的基础。其列举的三项是：纠正过度共享的状态、确定保护数据的初始设置、以及法规合规，使用的工具是 SharePoint Advanced Management 和 Microsoft Purview。SharePoint Advanced Management 包含在 Copilot 的许可证中。

先检查哪些网站、如何附加机密标签、以及如何使用在检查完成前不让特定网站出现在Copilot回答中的设置，这些内容已写在Microsoft 365 Copilot的安全性中。这里想说的是顺序。权限检查应在向全员发放许可证之前，至少完成最先发放部门的部分。如果先发给全员再开始检查，那么在修复发现的问题之前，你就得选择是停用已发放的许可证，还是让员工带着问题继续使用。

使用规则也应在同一时期制定。包括：可以输入什么内容、生成的文本在对外发布前由谁确认、遇到问题时向谁咨询。规则的写法已总结在AI使用规程的制定方法中。

选择试点部门，衡量使用情况

我认为许可证不宜一次性发给全员，最好先在一两个部门试点。选择时要看以下三点。

选择时的考量理由
用于撰写邮件、会议、资料的时间较长Copilot能协助的工作较多
已完成所涉文件权限的检查可以避免带着权限问题开始使用
部门负责人愿意承担报告使用结果的任务可以用数字来决定是否推广

试点期间，要用数字来观察使用情况。在Microsoft 365管理中心的Copilot使用情况报告中，可以查看持有许可证的人数、其中实际使用的人数及其比例，时间范围可选最近7天、28天、90天、180天。还可以一览查看各应用的使用情况以及每个人的最后使用日期。

统计方式是有规定的。根据Microsoft的说明，仅在Word功能区中选择图标打开Copilot界面并不算使用，只有发送提示词才算被计为使用。此外，某一天的使用情况通常要到当天结束约48小时后才会出现在报告中。开始使用的第二天看到数字偏低时不必慌张。

报告只能看出是否使用，无法看出工作时间是否减少。按我的看法，最好在试点前先统计目标部门每周花在会议纪要和邮件回复上的时间，试点后再用同样的方法重新统计。对于最后使用日期较早的人，要询问其不使用的原因。是不会用，还是没有可用的场景，下一步的做法会因此不同。

Microsoft已公开面向用户的培训资料以及面向公司内部的告知邮件范文，作为导入指南。在从零开始制作培训内容之前，可以先将其修改为适合公司内部使用。

委托外部导入支持公司的范围

对于以上工作，我划分了哪些可以委托给外部。下表是我的整理。

工作是否容易委托理由
许可证对象与要求的确认容易委托阅读Microsoft的文档即可决定
网络、应用、Teams的设置容易委托工作步骤是固定的
文件权限的检查及修复方案部分委托检查可以委托外部，但允许谁查看只能由公司内部决定
使用规则方案可委托，决定权在公司内部需要与公司内部其他规程保持一致
试点部门与使用业务的选择由公司内部决定了解业务的是公司内部的人
效果的衡量方式及是否推广的判断由公司内部决定要让决定预算的人认可这些数字

比较支持公司时，要确认对方是只承接表中上方的工作，还是能协助到根据公司内部业务定制使用方式为止。如果进一步深入到用Copilot Studio制作面向公司内部的Agent、与外部系统对接等定制开发，则需要与设置工作不同的能力。

这种一边审视公司内部业务与系统、一边深入现场进行定制开发的角色，被称为FDE（Forward Deployed Engineer）。关于这一职位是什么，已写在FDEとは中。委托外部公司时的比较方法已总结在FDE支援会社の選び方中。
