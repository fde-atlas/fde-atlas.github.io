技术探索：问题与数据剖析

原标题：Technical Discovery: Questions and Data Profiling

DataDank · 2026-10-31 · 约 4 分钟读完

摘要

这是 DataDank FDE 课程第二课，讲前沿部署工程师如何做技术发现：通过提问弄清真实问题、相关人员和系统数据，并在第一周用 Python 对客户真实数据样本做画像，发现重复、空值、格式不一致等问题，最后形成一页书面总结并获客户确认，为后续试点打基础。

要点

  • 技术发现分两部分：问对问题和尽早查看真实数据。
  • 提问应覆盖问题本身、使用者和维护者、数据来源与合规规则。
  • 客户描述的数据往往比实际干净，应第一周就自行画像样本。
  • 文中示例用 Python 检查工单导出的重复、空值和日期格式问题。
  • 发现阶段应以一页书面总结收尾，含风险与责任人，并获书面确认。

如何与客户开展技术调研：该问哪些问题、如何梳理系统与数据，以及如何在第一周用可运行的 Python 对客户数据进行剖析。

本页内容

技术调研是客户合作的第一阶段：弄清楚真正需要解决的是什么问题、涉及哪些系统和数据、可能出现什么问题。好的调研能为后续节省数周时间。它包含两个部分：提出正确的问题和尽早查看真实数据。

需要问的问题

问题本身

  • 这项工作应该改进什么决策或任务？目前由谁来做？怎么做？
  • 目前如何衡量成功？达到什么数字才值得做这个项目？
  • 如果什么都不做，会发生什么？

相关人员

  • 谁会日常使用这个解决方案？谁是项目发起人？谁必须审批安全和数据访问？
  • 你们这边之后由谁负责维护它？

系统与数据

  • 所需数据存放在哪里？如何访问（API、数据库、文件）？数据有多新？
  • 哪些字段重要？它们的取值是什么含义？是否存在已知问题？
  • 适用哪些规则：个人数据、数据存储位置、保留期限、审批要求？

把答案记录下来，并发回给客户确认。第一周发现的误解，代价最低。

第一周剖析真实数据

人们描述自己的数据时，往往会说得比实际更干净。请客户提供一个小而真实的样本，比如几千行的导出文件，然后自己动手剖析。下面的示例检查一份支持工单导出数据中的重复项、空值、不一致的取值和混乱的日期格式：

import csv, io
from collections import Counter

# A small extract the customer sent in week one (in real life: a CSV export or a read-only database view)
EXPORT = """ticket_id,created_at,customer_email,category,priority,resolved_at
T-1,2026-10-01 09:12,[email protected],Billing,High,2026-10-01 11:40
T-2,2026-10-01 10:05,[email protected],billing,,2026-10-03 16:00
T-3,2026-10-02 14:30,,Delivery,Low,
T-4,02/10/2026 15:00,[email protected],Delivery,Medium,2026-10-02 18:20
T-2,2026-10-01 10:05,[email protected],billing,,2026-10-03 16:00
T-5,2026-10-03 08:45,[email protected],Returns,Urgent,2026-10-03 09:30
"""

rows = list(csv.DictReader(io.StringIO(EXPORT)))
print(f"rows: {len(rows)}, columns: {list(rows[0])}")
dupes = [k for k, n in Counter(r["ticket_id"] for r in rows).items() if n > 1]
print("duplicate ticket ids:", dupes)
for col in rows[0]:
    values = [r[col] for r in rows]
    blank = sum(v == "" for v in values)
    distinct = sorted(set(v for v in values if v))
    note = f", values: {distinct}" if len(distinct) <= 5 else ""
    print(f"  {col:15} blanks={blank}{note}")
odd_dates = [r["ticket_id"] for r in rows if r["created_at"] and not r["created_at"][:4].isdigit()]
print("dates not in YYYY-MM-DD format:", odd_dates)

几秒钟内，这份剖析就向客户提出了五个问题：

  • 为什么 T-2 是重复的？
  • 优先级为空是什么意思？
  • “billing”和“Billing”是同一个值吗？
  • “02/10/2026”是 10 月 2 日还是 2 月 10 日？
  • 解决日期为空是否意味着工单仍未关闭？

每个答案都会成为集成中的一条规则。参见客户数据集成。

调研总结

调研结束时，输出一页纸的总结：

  • 问题：用客户自己的话描述，以及成功衡量标准。
  • 用户与负责人。
  • 系统与数据：包括访问方式和已知问题。
  • 约束条件：安全、隐私、截止日期。
  • 风险与待解决问题：每项都指定负责人。

在确定概念验证范围之前，先获得书面确认。

常见错误

  • 把第一个请求直接当作问题本身。
  • 轻信对数据的描述，而不剖析样本。
  • 过晚申请访问权限，导致项目因审批而停滞。
  • 没有书面总结，导致不同的人记住的约定各不相同。

核心要点

探索阶段旨在找出真正的问题、相关人员以及数据的现状。询问要改进的决策是什么以及如何衡量成功，在第一周对真实数据样本进行剖析，并撰写一份简短的总结，列出风险，由客户确认。下一步：规划概念验证。
