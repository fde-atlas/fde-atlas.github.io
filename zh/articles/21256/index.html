GenAI 基础知识

1. 什么是生成式 AI？它与传统机器学习有何不同？

答案： 生成式 AI 通过学习训练数据的分布并从中采样来生成新内容（文本、代码、图像、音频）。传统监督式机器学习通常将输入映射到固定的标签或数值：是否欺诈、价格、流失评分。大语言模型的训练目标是预测下一个 token，而这一单一目标在大规模训练下，无需为每个任务单独建模，就能实现摘要、翻译、信息抽取、推理和代码生成。生成式输出是开放式的，更难评分，因此测试、防护栏和监控成为一等公民的工作。

2. 什么是 token？为什么工程师要关心 token 数量？

答案： Token 是模型读取和写入的基本单位，通常是由分词器（如字节对编码）产生的子词片段。常见的英文单词可能是一个 token；而生僻词、数字或代码可能是多个。Token 数量影响工程师需要负责的四件事：成本（API 按输入和输出 token 计费，费率往往不同）、延迟（输出 token 是逐个生成的）、上下文限制（所有内容必须装得下）以及截断 bug。不同模型使用不同的分词器，因此同一个提示词在不同供应商那里的 token 数量也不同。

真实案例： 泰卢固语、印地语或混合的印地英语文本通常每个词分出的 token 数比英语多，因此面向印度客户的客服机器人可能比英语负载测试所显示的成本更高、响应更慢。相关机制在 tokens 和上下文窗口详解 中有介绍。

3. 什么是上下文窗口？超出它会发生什么？

回答： 上下文窗口是模型在单次请求中能处理的最大 token 数，它包括系统提示词、对话历史、检索到的文档、工具定义以及正在生成的输出。如果超出它，API 要么拒绝请求，要么你的框架会静默截断某些内容，通常是最早的消息或文档的末尾。更大的窗口并不是免费的：长上下文成本更高、延迟更大，而且模型对长提示词中间部分信息的利用不如开头或结尾可靠。

4. 什么是嵌入（embeddings）？它们在 GenAI 系统中有哪些用途？

回答： 嵌入是一种表示文本（或图像）语义的稠密向量，使语义相似的内容在向量空间中彼此靠近，通常用余弦相似度或点积进行比较。在 GenAI 系统中，嵌入支撑着 RAG 的语义搜索、去重、用户查询聚类、路由（判断这是什么意图？）、语义缓存和推荐。生产环境中需要注意的规则：查询和文档必须使用同一个模型进行嵌入；更换嵌入模型意味着要对整个语料库重新嵌入；嵌入捕捉的是主题相似性，而不是真实性或时效性。更深入的机制请参见 embeddings 详解。

5. 解释 temperature、top-p 和 top-k。

回答： 在每一步，模型都会生成一个词表上的概率分布，这些参数控制下一个 token 如何被采样。Temperature 对 logits 进行缩放：低值使分布更尖锐、输出更可重复；高值使分布更平坦、增加多样性。Top-k 将采样限制在概率最高的 k 个 token；top-p（核采样）则限制在累计概率达到 p 的最小集合。对于抽取、分类和工具调用，我会把 temperature 调低；对于头脑风暴或营销文案变体，我会调高它。通常你只需调 temperature 或 top-p 之一，不要同时大幅调整两者。

面试提示： 提到 temperature 为零并不能保证托管 API 上多次调用输出完全一致，而且某些推理模型会固定或忽略采样参数，因此请查阅当前提供商的文档。

6. 为什么 LLM 的输出是非确定性的？你如何围绕这一点进行设计？

回答： 采样显然是原因之一，但即使使用贪婪解码，批处理、GPU 上的浮点运算顺序以及提供商的静默模型更新也可能改变输出。你应该围绕它进行设计，而不是与之对抗：在提供商允许的情况下固定模型版本，对确定性任务保持低温度，用 schema 校验输出，让下游操作具备幂等性，并在分布上评估（测试集的通过率、关键案例的多次重复运行），而不是只看单个示例。

7. 基础模型、指令微调模型和推理模型之间有什么区别？

回答： 基础模型通过下一词预测进行预训练，只会续写文本，天然不具备对话能力。指令微调（对话）模型通过监督示例和偏好优化进一步训练，因此能遵循指令、使用对话格式并拒绝不安全请求。推理模型被训练为在回答前花费额外的 token 来推演问题，这有助于多步数学、规划、复杂代码和分析，但代价是延迟和 token 消耗。几乎所有应用开发都使用指令微调模型或推理模型；基础模型主要在你进行微调时才重要。

8. 预训练知识和上下文知识有什么区别？

回答： 预训练知识是模型从训练数据中吸收的内容：覆盖面广、在截止日期后冻结、无法归因于具体来源，也不了解你的私有数据。上下文知识是你在请求时放入提示词的内容：检索到的文档、工具结果、用户画像、今天的日期。企业应用应把预训练知识视为语言能力和通用推理能力，把上下文视为事实的来源。当答案必须是最新的、私有的或可引用的，它必须来自上下文。

提示词与上下文工程

9. 对于生产应用，什么样的系统提示词才算好？

回答： 好的系统提示词是一份规格说明，而不是一种感觉。它应说明角色和受众、任务边界、应信任哪些来源、信息缺失时该怎么做（“说明你不知道并提供升级途径”）、输出格式、语气，以及硬性约束，例如绝不提供投资建议。它应在 Git 中进行版本管理，像代码一样接受评审，并在每次更改前针对评测集进行测试。

面试提示： 永远不要声称系统提示词是一种安全控制。它塑造行为，但坚定的用户或被注入的文档可以覆盖它；真正的强制执行应放在代码和权限中。

10. 零样本、少样本和思维链提示：分别应该在什么时候使用？

回答： 对于能力强的模型处理清晰任务，零样本（仅指令）是默认选择。少样本会添加少量输入输出示例，当模型在格式、语气或边界情况处理上出错时，这是最快的修复方法；选择的示例应覆盖难点情况而非简单情况，并注意模型照搬示例内容的问题。思维链要求模型在回答前逐步推理；它对标准模型处理多步骤问题有帮助，而推理模型已在内部完成这一过程，通常不需要那么明确的提示。在生产环境中，我通常要求将推理放在单独的字段中或对用户隐藏，然后只解析最终答案。

11. 什么是上下文工程，它与提示词工程有何不同？

回答： 提示词工程是把指令措辞写好。上下文工程是设计模型在每次调用时看到的所有内容：哪些指令、哪些检索到的文档、哪些工具定义、多少历史记录、什么记忆、什么用户和权限数据，以什么顺序、在什么 token 预算内。随着应用变得多轮化并使用工具，大多数质量问题从措辞转移到了上下文：检索到错误的分块、过时的历史记录、工具过多、指令冲突。上下文工程把上下文窗口当作由代码组装的稀缺资源来对待。我们的上下文工程指南有更深入的讲解。

12. 在长对话中如何管理对话历史？

回答： 保留最近几轮的原文，用滚动摘要替换较早的轮次，并将持久事实（用户偏好、案例 ID）存储在对话记录之外的结构化状态中，只注入当前轮次所需的内容。大力精简工具输出；三轮之前的完整 JSON API 响应很少有用。为每个部分设置 token 预算，确保历史记录永远不会挤掉指令或检索到的证据。

13. 如何对提示词变更进行版本管理、测试和发布？

回答： 提示词存放在源代码管理或提示词注册表中，附带版本、负责人和变更说明。每次变更都要在离线评测集（黄金问题、边界情况、对抗性输入）上运行，且不得使既定指标回退。然后逐步发布：影子或金丝雀流量，比较线上信号（如点踩率、升级率和每次请求的成本），并保留即时回滚能力。LangSmith 或 Langfuse 等工具有助于追踪哪个提示词版本产生了哪个响应。

14. 什么是提示词链，什么时候它比一个大提示词更好？

回答： 提示词链将一个任务拆分为多个步骤，每个步骤使用各自专注的提示词，由代码将上一步的输出传递给下一步：先分类，再提取，然后起草，最后检查。当各步骤需要不同的模型、不同的温度参数或不同的校验方式时，当你想单独测试和观察每个步骤时，或者当一个廉价的步骤可以短路一个昂贵的步骤时，它优于一个巨大的提示词。代价是更多的调用次数和更高的延迟。如果单次调用在你的评测集上已经足够准确，就保持简单；只有当你能证明质量或可控性有提升时才使用链式结构。

结构化输出与函数调用

15. 如何从 LLM 获得可靠的结构化输出（JSON）？

回答： 按可靠性排序：优先使用提供商提供的模式约束结构化输出功能（如果可用，解码会被限制在你的 JSON 模式内），否则使用 JSON 模式并在提示词中加入模式，再否则仅依靠指令和示例。无论采用哪种方法，都要在代码中使用 Pydantic 之类的工具进行校验，失败时将校验错误包含在内进行重试，然后优雅地降级。保持模式小而扁平，类别使用枚举，可选字段要明确声明，以免模型擅自编造值。

面试提示： 要指出模式约束的是结构，而不是真实性。一个完全合法的 JSON 对象仍可能包含虚构的保单号，因此字段级的业务校验仍然必要。更多内容见 函数调用与结构化输出。

16. 端到端地解释函数调用（工具调用）。

回答： 你向模型发送对话内容以及一组工具定义：名称、描述和参数的 JSON 模式。如果模型判断需要某个工具，它会返回结构化的工具调用而不是文本。由你的应用程序（而非模型）校验参数、检查权限、执行函数或 API，并将结果作为工具消息返回。模型随后给出回答或调用另一个工具。模型从不直接接触你的系统；它只是提出调用请求。

User msg + tool schemas
   → LLM proposes tool_call(args)
   → App validates args + checks permission
   → App executes API / DB query
   → Tool result back to LLM
   → LLM writes final answer (or next call)

17. 如何为 LLM 设计好的工具？

回答： 围绕用户意图设计工具，而不是围绕你的原始 API 接口。相比几十个单薄的封装，更应提供少数几个命名清晰、描述明确的工具（“get_order_status：当客户询问订单位置时使用”）。使用带类型、受约束的参数（枚举、ID、日期格式），返回只包含模型所需字段的紧凑结果，返回模型可以据此行动的有用错误信息，并将读取工具与写入工具分开。写操作需要幂等键、基于终端用户身份的权限检查，对于高影响操作还需要人工审批。上下文中工具过多会降低选择准确性并消耗 token。

18. 相对于函数调用，MCP 处于什么位置？

回答： 函数调用是模型层面的机制：模型发出结构化的调用。MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年底推出的开放协议，用于标准化 AI 应用如何发现和使用服务器暴露的工具、资源和提示词。团队无需在每个应用中手工编写每个集成，只需将某个能力（例如 ServiceNow 或 Jira）一次性暴露为 MCP 服务器，任何支持 MCP 的客户端都可以使用它。MCP 并不能免除身份验证、授权、输入校验或审计的需要；它只是将这些底层管道标准化。

模型选择与路由

19. 如何为企业用例选择 LLM？

回答： 从任务和约束出发，而不是从排行榜出发。列出需求：在你自己的评测集上的质量、延迟目标、在预期请求量下的单次请求成本、上下文长度、工具调用和结构化输出支持、多语言需求、数据驻留和合同条款、在你已批准的云平台上的可用性（Amazon Bedrock、Microsoft Foundry 中的 Azure OpenAI、Google Cloud 上的 Gemini），以及是否需要自托管。筛选出两三个模型，运行相同的评测，选择在达到质量门槛的前提下最便宜的那个。

面试提示： 正确说出平台名称能体现你对行业动态的了解：Azure AI Foundry 现已更名为 Microsoft Foundry，Google 已将 Vertex AI 品牌重塑为 Gemini Enterprise Agent Platform。在引用功能之前，请先查阅最新文档。

20. 推理模型还是快速模型：如何决策？

回答： 当任务定义明确且较短时，使用快速、更便宜的模型：分类、抽取、改写、基于检索上下文的简单问答、路由。当任务需要多步规划、复杂分析、棘手的代码或调和相互矛盾的证据，且用户能容忍额外的几秒等待时，使用推理模型。用证据来决策：在评测集上同时运行两种模型，比较质量、延迟和每个正确答案的成本。通常正确的设计是两者结合：用推理模型进行规划或处理困难案例，用快速模型处理高吞吐量的步骤。

21. 什么是模型路由？你会如何实现它？

回答： 模型路由根据难度、意图、成本或策略将每个请求发送到最合适的模型。实现方式从简单规则（意图 X 发送到小模型），到轻量级分类器或嵌入相似度路由器，再到级联模式——先由便宜模型作答，当置信度不足或校验器失败时再升级。一些平台提供托管路由，例如 Amazon Bedrock 在同一模型家族内的智能提示词路由。路由器本身也需要评测：衡量它把难题发送给弱模型的频率，因为如果不专门检查，这类错误是看不见的。

22. 什么时候小语言模型是正确的选择？

答： 小型语言模型适合范围狭窄、调用量大的任务（分类、PII 检测、意图路由、从已知格式中提取）、严格的延迟预算、设备端或本地部署，以及数据不能离开受控环境的场景。它们运行和微调成本更低，量化版本可以在普通硬件上运行。但它们在开放式推理、长上下文和广泛的世界知识方面较弱。

23. 托管 API 还是自托管开放权重模型：有哪些权衡？

答： 托管 API 提供前沿模型质量、无需 GPU 运维以及弹性扩展，但你需要接受按 token 计费、供应商速率限制、模型弃用时间表以及数据处理协议。自托管开放权重模型（使用 Kubernetes 上的 vLLM 等服务器）可以让你掌控数据、版本和定制化，在稳定的高流量下也可能更便宜，但你需要自行负责 GPU 容量规划、扩缩容、补丁更新、安全以及每次升级的评测。许多企业先在现有云账户内使用托管云模型服务，仅在数据驻留、成本或定制化需求足以支撑时才自托管特定模型。

RAG 基础

24. 什么是 RAG，为什么它是企业级 GenAI 的默认模式？

答： 检索增强生成（RAG）在查询时从你自己的数据源中检索相关内容，并将其放入提示词中，使模型基于这些证据作答，理想情况下还附带引用。它是默认模式，因为企业问题依赖于模型从未见过的私有且不断变化的信息（政策、合同、工单、产品文档），而且 RAG 让你可以通过重新索引而非重新训练来更新知识、执行文档级权限控制并展示来源。可以先从 什么是 RAG 开始，关于检索、分块和评测问题的深入内容，请参阅我们的 RAG 面试题指南。

25. 请梳理 RAG 流水线的各个阶段。

答： 有两条流水线。数据摄取：连接数据源、解析文档（包括表格和扫描版 PDF）、清洗、分块、附加元数据（来源、日期、所有者、访问组）、生成嵌入并建立索引。查询：可选地重写问题，通过向量搜索和关键词搜索检索候选内容，按权限和元数据过滤，重排序，在 token 预算内组装上下文，生成回答时要求引用来源并在证据缺失时拒绝作答，最后进行事后的事实核查。

INGEST: sources → parse → chunk → embed → index
QUERY:  question → rewrite → hybrid search
        → ACL filter → rerank → prompt → LLM
        → grounding check → answer + citations

26. 为什么即使文档存在，RAG 系统仍会给出错误答案？

回答： 常见的原因大致如下：文档解析不佳（表格被压平成乱码）、分块把答案切分到了不同块的边界之外、查询措辞与文档词汇不匹配（缩写、产品代码）、纯向量搜索漏掉了关键词搜索本可命中的精确标识符、传入的分块太少或太多、文档的过时版本排名高于当前版本，或者模型忽略了证据。诊断方法是把检索和生成分开：在改动提示词之前，先检查正确的分块是否出现在靠前的结果中。

27. 什么是混合搜索，为什么要加一个重排序器？

回答： 混合搜索将稠密向量相似度（擅长语义和同义改写）与稀疏关键词搜索（如 BM25，擅长精确术语、ID、错误代码）相结合，并合并结果，通常采用倒数排名融合。重排序器（通常是交叉编码器）随后对每个查询-分块对进行联合打分，并对更大的候选集重新排序，使只有最相关的少数几个分块进入提示词。检索以低成本广撒网；重排序则在小集合上投入更多算力以换取精确度。前后都要用检索指标进行衡量。

微调 vs RAG

28. 什么时候应该微调而不是使用 RAG？

回答： 微调是为了改变行为，而不是添加事实。合理的理由包括：模型总是无法保持一致的输出格式或风格、有大量标注样本的领域特定分类或抽取任务、超高吞吐量下需要更短的提示词（把指令移入权重中），或者让小模型出色地完成一个狭窄任务。当需求是知识时，使用 RAG：最新的、私有的、经常变化的或需要引用来源的信息。许多生产系统两者兼用：RAG 负责事实，轻量微调的模型负责格式和语气。先尝试提示词和 RAG，因为它们改起来成本更低。可在 RAG vs 微调 中对比两者。

29. 什么是 LoRA 和参数高效微调？

回答： 参数高效微调（PEFT）只更新少量新增参数，而不是所有模型权重。LoRA（低秩适配）冻结基础模型，只训练注入到选定层中的小型低秩矩阵；QLoRA 则在量化后的基础模型上进行，以进一步减少内存占用。优点：GPU 内存占用大幅降低、训练更快、适配器文件小，并且可以在一个基础模型上同时服务多个适配器。局限：你仍然需要干净、有代表性的训练数据和评测集，而且微调后的模型可能在通用能力或安全行为上出现退化，因此每次微调后都要重新运行安全和回归测试。

30. 微调需要什么数据，可能出现什么问题？

答： 你需要与生产输入和期望输出完全一致的高质量示例、一个留出的测试集，以及明确的指标。质量胜过数量；几百条经过仔细审核的示例往往比数千条嘈杂的示例更能教会模型格式。常见失败：在含有错误的输出上训练（模型会学会这些错误）、测试数据泄漏到训练集中、对单一模板过拟合、训练示例中包含事后无法删除的个人数据、通用能力的灾难性遗忘，以及没有在基础模型被弃用时重新调优的计划。

多模态生成式 AI

31. 什么是多模态模型？它适合哪些企业任务？

答： 多模态模型能够接收、有时还能生成不止一种模态：文本、图像、音频、视频或文档。适合企业的场景包括读取发票、理赔表单和身份证件；理解 IT 工单中的截图；描述保险中的损失照片；分析报告中的图表；以及语音助手中的语音。工程问题与文本相同，另加几个：图像分辨率和 token 成本、文档页数限制、手写体和低质量扫描件，以及需要根据业务规则验证提取的字段。

32. 在文档处理中，什么时候用 OCR 加 LLM，什么时候直接用视觉模型？

答： 专用的 OCR 或文档版面分析服务能提供带坐标和置信度分数的确定性文本，适合审计、高亮和大量标准表单；然后由 LLM 对该文本进行结构化或推理。能够读图的视觉模型直接读取页面，能更好地处理混乱的版面、印章、复选框和混合内容，且所需流水线代码更少，但每页成本更高，并且可能在误读数字时不提示不确定性。务实的设计是以 OCR 加版面提取为主路径，将低置信度或复杂的页面交给视觉模型，并用规则和人工审核验证关键字段（金额、日期、证件号）。

33. 多模态输入有哪些特有的风险？

答： 图像和文档可能携带隐藏指令（图像中的文字、PDF 中白底白字的文字），从而构成间接提示注入。人脸、签名和证件号会产生个人数据合规义务。模型可能会在低分辨率扫描件中自信地误读数字。音频则带来说话人身份和同意授权的问题。控制措施包括：将所有提取的文本视为不可信数据、在可能的情况下于调用模型前遮蔽敏感区域、记录置信度、将不确定的情况转给人工处理，并在平台支持时对图像输入应用内容过滤。

幻觉与事实依据

34. 什么是幻觉？它为什么会发生？

回答： 幻觉是指输出流畅、自信，但错误或缺乏所提供来源支持的情况。其原因是模型被训练来生成看似合理的续写，而非核实事实；当知识缺失、模糊或过时的时候，一个看似合理的猜测仍然是最可能的续写。触发因素包括超出模型知识范围的问题、检索缺失或错误、迫使模型总是作答的提示词、冗长嘈杂的上下文，以及要求提供引用、数字或姓名等具体细节的请求。幻觉可以减少，但无法完全消除，因此系统设计必须能够捕获它。参见 LLM 幻觉详解。

35. 在生产系统中如何减少幻觉？

回答： 分层设防。将回答建立在检索到的或工具提供的证据之上；首先改进检索。指示模型仅根据上下文作答，否则就说明自己不知道，并在评测中奖励这种行为而不是惩罚它。要求在句子或论断级别提供引用，并核实被引用的段落确实存在且支持该论断。对驱动操作的事实使用结构化输出，并与记录系统进行校验。添加接地检查（由评判模型或平台功能执行，例如 Amazon Bedrock Guardrails 中的上下文接地检查）。缩小任务范围。最后，将低置信度或高影响的回答转交给人工处理。

36. “接地”是什么意思，如何衡量它？

回答： 接地的回答是指其中每一个事实性论断都由所提供的上下文支持。你可以通过忠实度（接地度）评分来衡量：将回答拆分为各个论断，并使用 LLM 评判器、NLI 模型或 Ragas 等工具，将每个论断与检索到的段落进行核对。同时结合回答相关性（是否回应了问题？）和上下文相关性（检索到的上下文是否有用？）。接地并不等于正确：如果检索到的文档已过时，一个忠实的回答仍然是错误的，因此来源的新鲜度和权威性也必须纳入流程中。

37. 如何处理系统不应回答的问题？

回答： 明确定义范围，并将拒答视为一项具有独立测试的功能。在生成之前，使用分类器或拒绝主题护栏检测超出范围或不安全的意图，并以有用的引导作为回应（“我可以帮助解答休假政策问题；薪资纠纷请通过此链接联系 HR”），在存在真实需求时升级给人工处理。在生产环境中跟踪拒答率：过低意味着过度作答；过高意味着用户无法获得本应得到的帮助。在评测集中同时包含应回答和应拒答的用例。

评测

38. 如何评测一个生成式 AI 应用？

回答： 用真实或贴近真实的查询构建评测集，并附上预期答案或验收标准，覆盖常见情况、边界情况、应当拒绝的情况以及对抗性输入。采用混合评分方式：确定性检查（模式是否有效、必填字段、禁止内容、是否调用了正确的工具）、存在确切答案时使用基于参考答案的指标、开放式质量使用带评分细则的 LLM-as-judge，并对抽样结果进行人工审核。分别评测各个组件（检索、工具选择、生成）以及端到端效果。在 CI 中对每次提示词、模型或检索变更运行评测，并在生产环境中监控同等信号。我们的 LLM 评测指南 深入讲解了相关指标。

39. 什么是 LLM-as-judge，它有哪些弱点？

回答： LLM-as-judge 是用一个模型依据评分细则（忠实度、有用性、政策合规性）对输出进行打分，或对两个回答进行比较。它将审核规模扩展到远超人工所能及的范围。已知弱点：成对比较中的位置偏差、偏好更长或更自信的回答、对同一模型家族输出的自我偏好、多次运行之间的不一致性，以及专业领域的盲区。缓解措施：带示例的具体评分细则、用二元或小范围分值代替模糊的十分制、成对测试中随机化顺序、尽可能使用不同的模型家族作为评判者，以及最关键的一点——用人工标注样本对评判者进行校准，并定期复查一致性。

40. 离线评测和在线评测有什么区别？

回答： 离线评测在发布前运行固定的测试集：它可重复、安全且能发现回归问题，但只能覆盖你能想到的情况。在线评测衡量真实流量：用户反馈、升级和解决率、任务完成率、对抽样生产轨迹的评判分数、延迟和成本，以及版本间的 A/B 或金丝雀对比。离线评测为发布把关；在线评测告诉你发布是否真正有效，并揭示新的失败模式。重要的闭环是：收集生产环境中失败的案例，进行标注，并将其加入离线测试集，使同一个 bug 不会再次上线。

41. 当业务方没有现成数据时，你如何构建黄金数据集？

回答： 从真实问题入手：支持工单、搜索日志、邮箱、FAQ，以及与当今回答这些问题的人员进行访谈。让领域专家撰写或审核每个问题的预期答案及其来源文档。有意识地加入边界情况和拒绝情况。合成生成（用 LLM 从文档中生成问题）有助于填补覆盖面，但必须经过审核，因为合成问题往往比真实问题更简单、更干净。从小规模且有代表性的数据集开始，对数据集进行版本管理，记录每条数据的审核人，并从生产失败中不断扩充。

42. 你会在 GenAI 质量仪表盘上放置哪些指标？

回答： 按受众分组。质量类：事实依据性、答案相关性、抽样流量的评审通过率、拒答率、用户点踩率。业务类：任务完成率或问题分流率、转人工率、由业务负责人测量的每案例节省时间。运营类：首 token 时间、端到端延迟百分位数、错误率和超时率、触发限流次数。成本类：每次请求、每用户和每成功结果的 token 数与花费。安全类：按类别统计的护栏拦截率、提示注入检测、PII 脱敏事件。每个指标都需要指定负责人和触发行动的阈值。

安全与护栏

43. 什么是护栏，它们在架构中处于什么位置？

回答： 护栏是根据策略检查输入和输出的控制机制。输入护栏在调用模型之前检测提示攻击、禁止话题、有毒内容和敏感数据。输出护栏在用户看到响应之前检查有害内容、PII 泄露、无依据的断言和格式违规。工具护栏在执行任何操作之前验证参数和权限。也有托管方案可用，例如 Amazon Bedrock Guardrails 提供内容过滤、禁止话题、词语过滤、敏感信息过滤、上下文依据性检查和自动推理检查，其 ApplyGuardrail API 可以独立于模型调用使用。护栏是对最小权限访问的补充，而非替代。参见 AI 护栏详解。

44. 什么是提示注入，如何防御它？

回答： 提示注入是试图覆盖应用程序指令的文本。直接注入来自用户（“忽略之前的指令”）。间接注入隐藏在系统检索或接收的内容中：网页、电子邮件、PDF、工单评论。没有彻底的解决方案，因此要纵深防御：将所有检索到的内容和工具内容视为不可信数据并清晰界定，运行注入分类器，只给模型提供当前用户被允许使用的工具和数据，对有重大影响的操作要求确认，绝不把机密信息放入提示中，并在输出触发任何操作之前进行验证。它已被列入 OWASP LLM 应用程序 Top 10，这是一个值得引用的参考资料。

面试提示： 最有力的回答是架构层面的：“即使注入成功，模型实际上能做什么？”限制影响范围。

45. 在 GenAI 应用中如何处理 PII 和敏感数据？

回答： 首先最小化：只向模型发送任务所需的字段。尽可能在调用模型前检测并屏蔽或对 PII 进行标记化处理，并在日志和追踪记录中将其脱敏。选择数据处理条款符合你合规义务的提供商和地区；对于印度个人数据，与合规团队一起对照 DPDP 法案梳理数据流。在检索中实施文档级访问控制，确保模型永远不会看到用户无权查看的记录。为提示词、输出和评测数据集设置保留期限，除非有明确的法律依据，否则不要将个人数据纳入微调数据集。

46. 什么是越狱（jailbreaking），它与提示词注入有何不同？

回答： 越狱针对的是模型自身的安全训练：用户试图通过角色扮演、编码技巧或多轮说服，让模型生成它通常会拒绝的内容。提示词注入针对的是应用程序：它劫持指令，使模型执行开发者不希望的操作或泄露数据。两者有重叠，但防御重点不同。越狱可通过模型选择、内容过滤和输出审核来缓解；注入则通过权限分离、工具权限和不可信数据处理来缓解。在上线前和重大变更后，对两者都进行红队测试。

47. 什么时候需要人工介入？

回答： 当操作不可逆或影响重大（支付、账户变更、面向客户的法律或医疗声明）时，当模型置信度或验证器发出不确定信号时，当法规要求由人做决策时，以及在早期推广、积累证据的阶段。要正确设计这一环节：向审核者展示证据和拟执行的操作，让批准、编辑和拒绝操作快速完成，记录编辑原因，并将拒绝结果反馈到评测中。如果审核者不看内容就一路点击通过，那么人工介入环节就只是纸面上的控制措施。

延迟与成本

48. LLM 应用中的延迟来自哪里，如何降低？

回答： 分解来看：网络和网关开销、检索与重排序、提示词处理（与输入 token 数成正比）、首 token 时间、生成时间（与输出 token 数成正比）、工具调用以及额外的模型往返。降低方法：流式返回响应让用户尽早看到文本、减少输入 token、限制输出长度、对简单步骤使用更快的模型、并行执行检索和相互独立的工具调用、缓存重复工作、对长且稳定的前缀使用提示词缓存，并避免不必要的 Agent 循环。参见 LLM 延迟优化。

49. 解释提示词缓存与语义缓存的区别。

回答： 提示词缓存是提供商的一项功能，它在多次调用之间复用相同提示词前缀（系统提示词、长文档、工具定义）的处理状态，从而降低缓存部分的成本和延迟；它鼓励把稳定内容放在前面、动态内容放在后面。语义缓存则是你自己搭建的一层，它存储之前的回答，并在新查询语义相似时返回缓存结果。语义缓存可以省掉整个模型调用，但有风险：看起来相似的问题可能需要不同的答案（“取消我的订单” vs “取消我的订阅”），而且缓存的答案可能过时，或在不同权限的用户之间泄露。只应将其用于低风险、非个性化的内容，并设置严格的相似度阈值和过期时间。

50. 你如何估算和控制 GenAI 功能的成本？

回答： 将每次请求的成本估算为输入 token 数乘以输入价格，加上输出 token 数乘以输出价格，再加上嵌入、重排序、护栏调用和重试的成本；然后乘以每用户每天的请求数和用户数。之后要用真实调用记录来验证，因为 Agent 循环和重试往往会让成本达到表格估算的两倍。控制手段包括：每请求 token 预算、模型路由、提示词缓存、更短的上下文、输出限制、用于离线任务的批处理 API、按用户或租户的速率限制，以及支出异常告警。应报告每次成功结果的成本，而不仅仅是每次调用的成本。

51. 什么是 LLM 网关，团队为什么要引入它？

回答： LLM 网关是应用与模型提供商之间的中央代理。它为认证和密钥管理、跨模型或跨区域的路由与故障转移、按团队的速率限制和配额、成本归因、缓存、日志与追踪，以及策略执行（如护栏或 PII 脱敏）提供统一入口。当多个应用调用多个提供商、却没人能回答“谁在哪个模型上花了多少钱”时，团队就会引入它。其风险在于引入了新的单点故障和额外延迟，因此它需要高可用性，并且必须保持轻量。

LLMOps 基础

52. 什么是 LLMOps，它与 MLOps 有何不同？

回答： LLMOps 是将 MLOps 的规范应用于 LLM 应用，但管理的产物不同。在经典 MLOps 中，你对数据集、训练代码和模型权重进行版本管理，并监控预测漂移。在 LLMOps 中，你主要使用一个并非自己训练的模型，因此需要版本管理的产物是提示词、检索配置、工具定义、模型标识符、护栏策略和评测数据集。测试依赖评测套件和评判模型，而不是单一的准确率数字；监控则增加了 token 成本、答案有据性、安全事件和多步骤链路的追踪。其发布流水线（CI、评测门禁、金丝雀发布、回滚）对任何 DevOps 工程师来说都很熟悉。更多信息请参阅 MLOps 和 LLMOps 面试题。

53. 在 GenAI 应用中应该记录和追踪哪些内容？

回答： 每次请求记录：追踪 ID、用户或租户（必要时使用假名）、提示词模板版本、模型 ID 和参数、检索到的文档 ID 及评分、工具调用及其参数和结果、护栏决策、token 数量、每一步的延迟、最终输出和用户反馈。使用 OpenTelemetry 风格的 span，使一次请求在检索、模型调用和工具之间的整个过程形成一条追踪链，并使用 LangSmith 或 Langfuse 等工具进行检查。按策略对敏感内容进行脱敏，并设置保留期限。

54. 你如何处理模型弃用和升级？

回答： 将模型视为具有生命周期的依赖项。跟踪提供商的弃用通知，尽可能固定版本，并将模型选择保留在配置中而非代码里。当新版本发布时，运行完整的评测套件，比较质量、延迟、成本和拒绝行为，并检查结构化输出和工具调用是否仍能正常解析。必要时重新调整提示词，对变更进行金丝雀发布，并在新模型被验证之前保留旧模型以便回滚。微调模型需要重新微调计划，因为其依赖的基础模型也会被退役。

55. GenAI 应用的 CI/CD 是什么样的？

回答： 常规流水线（lint、单元测试、容器构建、安全扫描、基础设施即代码）加上 GenAI 阶段：提示词和配置变更触发评测套件；质量门禁会阻止在忠实度、工具准确性或安全案例上低于阈值的合并；红队提示词作为回归测试运行；部署采用渐进式发布，并根据线上指标自动回滚。为了让评测足够快以适应拉取请求，可在每次变更时运行冒烟子集，并在每晚或发布前运行完整套件。GitHub Actions 和 Argo CD 非常适合这种方案。

GenAI 架构

56. 请解释从原始 LLM 到聊天机器人、RAG 应用、使用工具的应用、Agent 以及多 Agent 系统的演进过程。

回答： 每一步都会增加一项能力和一类新的风险，优秀的工程师只会根据问题的需要爬到相应的高度。

LLM        text in → text out, no memory
  ↓ + conversation state
Chatbot    multi-turn, still only model knowledge
  ↓ + retrieval
RAG app    answers from your documents, cites
  ↓ + tool calls
Tool app   reads/writes systems, code controls flow
  ↓ + model-driven loop
Agent      plans, picks tools, iterates to a goal
  ↓ + specialised agents
Multi-agent  agents coordinate via orchestrator

直接调用LLM是无状态的：输入提示词，输出补全结果。聊天机器人增加了对话历史和系统提示词，但仍然只了解其训练数据。RAG 应用增加了检索功能，使答案来自带有引用的私有、最新文档；新的风险在于检索质量和权限控制。工具调用应用允许模型调用函数，但流程由你的代码决定（“先分类，再查询订单，然后回答”）；这时你需要参数校验和授权。Agent 将循环的控制权交给模型：它进行规划、选择工具、观察结果并不断迭代，直到达成目标或达到步数上限；风险在于失控循环、成本和意外操作，因此你需要加入预算限制、审批关卡和调用追踪。多 Agent 系统将工作分配给专门的 Agent（分诊、研究、执行、审查），由编排器或图结构进行协调，这有助于权限隔离和专注分工，但会成倍增加延迟、成本和调试复杂度。

面试提示：最后给出你的判断：“我见过的大多数企业级问题在 RAG 或工具调用层面就能解决；只有当步骤确实无法预先固定时，我才会转向 Agent。”想深入了解 Agent，请参阅 agentic AI 面试题。

57. 请画出一个企业级 GenAI 助手的参考架构。

答案：我将其分为渠道层、负责编排的应用层、模型访问层、知识层以及贯穿各层的控制机制。

Users (web, Teams, WhatsApp)
  → API gateway + SSO (Entra ID / IAM)
  → Orchestrator service (FastAPI)
      ├ input guardrails
      ├ retrieval → vector + keyword index
      ├ tools → ServiceNow / CRM via MCP
      ├ LLM gateway → model providers
      └ output guardrails + citations
  → Response (streamed)
Cross-cutting: traces, eval, cost, audit

需要说明的关键决策：身份从用户传递到检索和工具；提示词和策略采用版本化配置；模型位于网关之后，以便随时替换；评测和可观测性从第一天起就存在。企业 AI 架构指南对每一层都有详细展开。

58. 在 GenAI 平台中，你如何设计多租户架构？

答案：隔离必须在每一个持有数据的层面都成立。检索：使用按租户划分的索引，或在服务端强制执行租户过滤，绝不能依赖提示词。缓存：缓存键包含租户和权限范围，或者对个性化内容禁用语义缓存。记忆和会话存储：按租户分区。工具：凭证按租户限定作用域。成本和速率限制：通过网关实施按租户的配额。日志：打上租户标签并配置访问控制。然后通过跨租户的评测用例显式测试隔离性，例如让租户 A 的助手回答关于租户 B 文档的问题。

59. 当模型提供商出现故障时，你如何设计 GenAI 系统以实现优雅降级？

回答：为瞬态错误设置超时和带指数退避与抖动的重试，但要限制重试次数，以免放大故障。通过网关配置回退到备用模型或区域，并确保提示词已在备用模型上测试过。使用熔断器避免持续冲击故障端点。定义降级模式：返回带链接的搜索结果而非生成的答案，将非紧急任务排队，或通过清晰的消息转接至人工渠道。主动监控速率限制，并在发布高峰之前而非期间申请配额提升。

60. 同步聊天与异步批量 GenAI：架构有何不同？

回答：同步聊天针对延迟优化：流式输出、小上下文、快速模型、严格的超时和优雅降级。异步批量工作（总结昨晚的工单、从数千份文档中提取字段、生成产品描述）则针对吞吐量和成本优化：队列、工作池、可用的供应商批量 API、更大或推理型模型、带检查点的幂等任务，以及在结果进入权威系统前的审核步骤。

实际场景

61. 你的 RAG 聊天机器人在演示中回答正确，但用户反馈在生产环境中答案有误。你如何排查？

回答：演示问题是由熟悉文档的人编写的；生产环境中的问题更模糊，使用不同的词汇，并且涉及没人测试过的内容。我会拉取失败的追踪记录，将每个失败归类为检索、生成或数据问题，然后优先修复占比最大的类别。

我会检查的内容：

  • 对于每个案例，检查正确的文档片段是否出现在检索结果集中。
  • 如果没有：解析质量、分块、缺失文档、缩写词、是否需要混合搜索或查询重写。
  • 如果有但答案错误：提示词指令、上下文排序、片段过多、模型选择。
  • 在修复之前，将每个失败案例加入评测集。

生产环境注意事项：将检索指标和答案有据性放入仪表盘，这样下一次回归会被监控系统发现，而不是被用户发现。

62. 假设一家银行想要一个面向客户的信用卡查询助手。你会设计什么，又会拒绝构建什么？

回答：我会构建一个范围受限的助手，基于经批准的内容并附带引用来回答产品和政策问题，并通过经过身份验证的只读工具处理账户相关问题（余额、还款日期、交易状态）。我不会让它提供个性化财务建议、在没有人工参与的情况下批准额度变更或争议结果，也不会让它凭模型记忆回答费用和利率问题。

我会检查的内容：

  • 在暴露任何账户工具之前，先完成客户身份验证和会话绑定。
  • 拒绝的话题：投资建议、竞争对手比较，以及任何超出信用卡范围的内容。
  • PII 处理：日志脱敏、提供给模型的最小字段、数据驻留条款。
  • 对每一条政策回答进行依据核查；费用必须来自现行费率表。
  • 合规与风险团队对评测集的签核，包括拒答案例。

生产环境注意事项： 完整记录助手说了什么以及由哪个来源支持，保留完整的审计轨迹。

63. 新功能上线后，每月 LLM 支出翻了三倍。你会怎么做？

回答： 在优化任何东西之前，先弄清 token 花在哪里。支出激增通常来自几个原因：Agent 循环或重试、提示词变大（更多历史记录、更多分块、更多工具定义）、切换到更贵的模型，或来自单一租户或机器人的流量。

我会检查的内容：

  • 根据网关或追踪数据，按功能、模型、租户和端点拆分支出。
  • 对比上线前后每个请求的输入和输出 token 数。
  • 查找请求扇出：每个用户操作触发多少次模型调用。
  • 检查提示词缓存命中率是否因动态内容被移到静态内容之前而下降。

生产环境注意事项： 为每个功能添加预算和异常告警，以便下次激增能在几小时内被发现；并在评测集上确认质量后，将简单请求路由到更便宜的模型。

64. 助手有时返回无效 JSON，导致下游系统出错。你如何修复？

回答： 从“礼貌请求”转向强制约束。如果可用，使用提供商的 schema 约束结构化输出，用 schema 库校验每个响应，携带校验错误重试一次，并将持续失败的请求发送到死信队列而不是下游。

我会检查的内容：

  • 哪些输入会触发失败：长文档、不常见的语言、输出被 max-token 限制截断。
  • schema 是否过深或存在含糊的可选字段。
  • 模型最近是否被更改或升级。

生产环境注意事项： 将 schema 校验失败率作为指标进行跟踪；输出上限处的截断是一个常见的隐性原因，表现为长输入上的失败率激增。

65. 用户上传了一份 PDF，助手开始执行其中隐藏的指令。发生了什么，你如何应对？

回答： 这是间接提示注入：不受信任的文档内容被当作了指令。立即响应：检查该会话中助手实际能做什么（哪些工具、哪些数据），确认是否执行了任何操作或泄露了数据，并在必要时通过禁用文档处理流程中的写入工具来进行遏制。

我会检查的内容：

  • 文档文本如何放入提示词：是否清晰分隔并标记为不受信任的数据，还是与指令混在一起？
  • 是否对提取的文档文本运行注入分类器或提示词攻击过滤器。
  • 该流程中的工具权限；按用户而非服务账户实施最小权限。
  • 对重大操作设置确认关卡。

生产环境注意事项： 将该恶意文档加入红队回归测试套件。

66. 业务方因为推理模型在演示中得分更高，就想在所有场景都使用它。你如何回应？

回答： 同意进行测试，并将决策框架设定为在客户自身工作负载上每元成本和每秒延迟所换取的质量。按任务类型在同一评测集上运行推理模型和快速模型。

我会检查的内容：

  • 按任务类型而非整体来看质量差异；推理模型往往只在少数困难案例上有帮助。
  • 对照用户体验目标的延迟百分位数。
  • 在生产规模下（包括推理 token）每个成功结果的成本。
  • 路由或级联设计能否以更低成本获得大部分质量提升。

生产环境注意事项： 将结果以表格形式呈现给业务负责人；路由式设计往往胜出，这样决策就基于证据而非演示印象。

67. 一家医院希望用 GenAI 来总结出院记录。你在设计上有哪些顾虑？

回答： 这是临床文档，因此设计必须是辅助性的，由临床医生强制审核，绝不能自主运行。摘要必须严格基于原始记录，不得遗漏关键项目（过敏史、用药变更、随访说明），并且必须标注不确定性而不是猜测。

我会检查的内容：

  • 数据处理：患者数据保留在获批的地区和服务商协议内；访问权限与临床医生的角色绑定。
  • 为关键项目设置结构化章节，每项都附带指向原文的链接。
  • 由临床医生参与评测：遗漏率和事实错误，而不仅仅是流畅度。

生产环境注意事项： 明确测量遗漏情况；在临床环境中，遗漏过敏信息比一句别扭的话严重得多。监管和医院治理审查应纳入计划之中，而不是上线之后再做。

68. 平均响应时间没问题，但用户抱怨助手很慢。你会怎么做？

回答： 平均值掩盖了长尾。查看首 token 时间和端到端延迟百分位数，并按步骤和请求类型细分。

我会检查的内容：

  • 是否实现了端到端流式输出，还是某个代理在缓冲响应？
  • 慢请求中哪一步占主导：检索、重排序、模型、工具，还是反复的 Agent 迭代？
  • 超长输入：用户粘贴大文档，或历史记录无限增长。
  • 高峰时段服务商限流或速率限制重试。

生产环境注意事项： 为每个步骤设定延迟预算，并对慢的长尾进行告警。感知速度同样重要：在工具调用期间显示进度（“正在搜索政策”）。

69. 假设一家保险公司希望自动化处理来自电子邮件的理赔申请，其中包含照片和 PDF。你会如何着手？

回答： 把它当作一个文档与决策流水线，而不是聊天机器人。对邮件进行分类，从正文、附件和照片中提取结构化的理赔字段，对照保单数据进行校验，然后生成一份草稿理赔单供理赔员确认。先自动化干净、高置信度的案例。

我会检查的内容：

  • 在标注样本上的字段级提取准确率，尤其是保单号、日期和金额。
  • 每个字段的置信度阈值，用于决定自动填充还是人工审核。
  • 通过只读工具与保单管理系统进行校验。
  • 对附件中注入的指令或被篡改图片的处理。

生产环境考量： 与理赔团队一起衡量节省的理赔员时间和每个字段的纠正率；这就是业务价值所在，它还能告诉你哪些字段需要改进。

70. 模型升级后，用户反映回答变得更长且不够精确。你会怎么做？

回答： 如果影响显著，先回滚或减少新模型的流量，然后在评测集上对比新旧模型以量化变化。新模型版本对相同提示词的响应往往不同：冗长度、拒绝行为或格式遵循都可能有所差异。

我会检查的内容：

  • 相同输入下新旧模型的长度和格式指标对比。
  • 评测标准是否涵盖简洁性；如果没有则补充。
  • 提示词调整：明确的长度限制、期望风格的示例。
  • 结构化输出和工具调用的兼容性。

71. 一个内部知识助手向员工展示了其不应看到的 HR 文档内容。哪里出了问题？

回答： 检索环节没有执行权限控制。通常是因为文档使用可以读取所有内容的服务账号进行索引，而访问控制元数据要么没有被捕获，要么在查询时没有被过滤。这是一起安全事件：限制索引访问，根据日志评估暴露范围，并按照规定流程通知相关人员。

我会检查的内容：

  • 每个数据源在摄取时是否捕获了访问控制列表。
  • 检索查询是否按请求用户所属组进行过滤，并在服务端强制执行。
  • 权限同步：源系统中权限变更多快能同步到索引。
  • 可能重放受限内容的缓存或对话记忆。

生产环境考量： 在评测套件中加入权限测试用例（相同问题、不同角色的用户、不同的预期答案），并在每次摄取变更时运行它们。

72. 假设一家零售商希望为大型商品目录生成 GenAI 产品描述。你如何确保其安全且可扩展？

回答： 将其作为异步批处理流水线运行：输入结构化产品属性，输出生成描述，且描述仅基于这些属性生成，以避免模型虚构功能、保修或宣传语。通过现有内容工作流进行验证、抽样审核和发布。

我会检查的内容：

  • 事实依据：每条声明都对应一个属性；过滤违禁词和无依据的声明。
  • 品牌语调：通过少样本示例实现，如果业务量足够大，可使用轻量微调的小模型。
  • 地区语言：由母语人士审核质量，而不仅仅依赖 LLM 评判。
  • 每个品类的人工审核样本量，对健康产品等受监管品类应更高。

生产环境考量： 按品类跟踪发布后的更正和客户投诉，并将更正后的描述作为示例反馈给模型。

73. 一位利益相关者要求你在公司所有文档上微调模型，使其“无所不知”。你如何回应？

回答： 解释微调在可靠存储事实方面表现不佳：它无法引用来源，会随文档变化而过时，无法遵守按用户的权限控制，而且事后删除文档意味着需要重新训练。建议采用带访问控制和引用功能的 RAG 方案处理这些文档，并将微调保留给后续评测中暴露出的行为差距。

我会检查的内容：

  • 用户实际需要回答的问题，以及内容变更的频率。
  • 各部门之间的权限要求。
  • 是否存在微调确实能解决的格式或风格问题。

生产环境考量： 提供一个简短的试点：在某个部门的文档上运行带评测集的 RAG，让利益相关者在做出更大决策之前看到带引用的回答和可衡量的质量。

74. 设想一个 GCC IT 团队希望有一个助手能通过聊天创建和更新 ServiceNow 工单。你会增加哪些控制措施？

回答： 这是一个具有写权限的工具使用型应用，因此控制措施的重点在于身份和影响范围。助手以发起请求员工的权限运行，而非使用超级用户账户，并且在创建或更新工单之前会显示确认摘要。

我会检查的内容：

  • OAuth 或委托身份，使 ServiceNow 强制执行用户自身的访问权限。
  • 收窄的工具范围：create_incident、add_comment、get_ticket_status，并对字段进行验证，为类别和优先级设置枚举值。
  • 幂等键，确保重试不会创建重复工单。
  • 审计记录，将每次工单变更与用户、对话和模型输出关联起来。

生产环境考量： 通过 MCP 服务器暴露这些工具，可以让其他助手在相同控制措施下复用它们；将工具调用准确率（正确的工具、正确的参数）作为一等指标进行衡量。

75. 你被要求在一个季度内将 GenAI 概念验证推向生产环境。你的计划是什么？

回答： 首先就业务成果和成功指标达成一致，然后按照风险的要求依次加固系统：评测、安全与数据访问、可靠性、可观测性、成本，最后是上线。概念验证证明的是可能性；生产环境证明的是在真实用户、数据和约束条件下的可重复性。

我会检查的内容：

  • 由业务方签署确认的负责人、成功指标和验收阈值。
  • 与领域专家一起基于真实查询构建的评测集；以及基线分数。
  • 身份认证、权限、PII 处理、防护栏以及安全审查。
  • 基础设施即代码、带评测门禁的 CI/CD、环境管理和回滚机制。
  • 追踪、仪表盘、成本预算、告警和值班手册。
  • 试点小组、反馈闭环，然后是带有“继续/停止”标准的分阶段上线。

生产环境注意事项： 大多数延误来自数据访问审批和安全审查，而不是模型工作，所以要在第一周就启动这些事项。这段从 AI 演示到企业成果的历程，正是前沿部署工程师为客户所做的工作；参见 FDE 如何将 AI 从 POC 推向生产环境。

核心要点

  • 基础知识通过调试来检验：token、上下文预算和采样解释了大多数成本、延迟和一致性问题。
  • 事实来自上下文（检索和工具），行为来自提示词，偶尔来自微调；要始终保持这一区分的清晰。
  • 结构化输出和工具调用是 GenAI 与真实系统接触的地方，因此验证、权限和幂等性比提示词措辞更重要。
  • 基于你自己的评测集和每次成功产出的成本来选择模型；在快速模型和推理模型之间进行路由，而不是在所有场景都用同一个模型。
  • 评测是核心支柱：离线门禁、在线监控、经过校准的 LLM 评审，以及失败案例收集闭环。
  • 安全是架构层面的：要假设注入攻击可能成功，并限制模型能够触及的范围。
  • 只在问题需要时，才从 LLM 向多 Agent 阶梯攀升。

面试准备清单

  • 用一个调试案例分别解释 token、上下文窗口、嵌入和温度。
  • 构建一个 RAG 应用，包含混合搜索、引用、访问过滤和一套可以展示的评测集。
  • 构建一个工具调用流程，包含模式验证、权限检查和确认步骤。
  • 运行一次 LLM 评审式评测，并在样本上与你自己的标注进行比较。
  • 为应用添加追踪，并展示每次请求的 token 成本。
  • 尝试至少两家模型提供商（例如 Amazon Bedrock 和 Azure OpenAI），并在同一任务上比较质量、延迟和成本。
  • 准备一块企业助手的白板架构图，包括身份认证、防护栏和可观测性。
  • 大声演练三个场景问题的回答：生产质量下降、成本激增和安全事件。
  • 阅读目标雇主所用云平台的最新文档；名称和功能经常变化。

常见问题

GenAI 工程师是做什么的？

GenAI 工程师设计、构建和运营使用大语言模型及其他生成式模型的应用，包括提示词、检索管道、工具集成、评测、防护栏、部署和监控。

生成式 AI 工程师面试需要哪些技能？

Python、API 和后端基础，LLM 概念（如 token、嵌入和采样），RAG、结构化输出和函数调用，评测方法，包括提示词注入在内的安全基础，以及至少一个主流云平台上的云部署。

2026 年我该如何准备 GenAI 工程师面试？

构建并部署一两个带评测和可观测性的真实项目，练习口头讲解设计权衡，演练关于质量、成本和安全的场景问题，并阅读雇主所用云平台的最新文档。

应届生的生成式 AI 面试问题有所不同吗？

是的。应届生主要被问基础概念、提示词、基础 RAG 和项目讲解，而有经验的候选人则面对架构、评测策略、成本控制和生产事故场景。

GenAI 岗位需要机器学习或深度学习知识吗？

Application-focused GenAI roles need a working understanding of how models are trained and why they behave as they do, but rarely require training models from scratch. Fine-tuning and model-serving roles need deeper ML knowledge.

Which programming language is most useful for GenAI engineering?

Python is the most common choice because most SDKs, frameworks and evaluation tools support it first. Java and TypeScript are also used in enterprise backends, so knowing how to call models from your team's main language helps.

What projects should I show in a generative AI interview?

A RAG assistant over real documents with citations and an evaluation set, a tool-calling application that safely reads and writes to a system such as a ticketing tool, and ideally one deployed project with tracing and cost tracking.

Is generative AI engineering a good career choice in 2026?

It suits engineers who enjoy combining software engineering, data and product thinking. The work is shifting from demos to production systems, so engineers who can evaluate, secure and operate GenAI applications are well placed.

How is a GenAI engineer different from a Forward Deployed Engineer?

A GenAI engineer focuses on building generative AI systems, usually inside a product or platform team. A Forward Deployed Engineer applies similar skills directly with customers, owning discovery, integration and deployment into their environment.
