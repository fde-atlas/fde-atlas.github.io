Anthropic FDE 面试：如何逐轮准备

原标题：Anthropic FDE Interview: How to Prepare Round by Round

FDE Times · 2026-10-16 · 约 7 分钟读完

摘要

文章以 Anthropic 伦敦前沿部署工程师职位为对象，主张把招聘启事当作备考大纲，将每项要求对应到最可能考察它的面试环节。据 Exponent/Aced 的面试指南，流程包括招聘人员电话、围绕 Claude 与 MCP 的技术面、逐步加需求的编程测试，以及方案设计与行为面结合的终面。文中用示例说明应把每步需求写成独立纯函数，设计环节应先提问再画架构，行为面看重真实失败经历。Anthropic 官方规定现场面试和带回家作业不得使用 Claude，除非面试官允许。

要点

  • 把招聘启事当大纲，逐条对应面试环节。
  • 技术面围绕 Claude 部署与 MCP 工具展开。
  • 编程测试逐步加需求，应写成可扩展的纯函数链。
  • 设计面先提澄清问题，再提架构方案。
  • 现场面试与作业禁用 Claude，违规会失去信任。

在进行任何编码练习之前，先把每项要求——从 MCP 服务器到 25-50% 的时间驻扎在客户现场——对应到最可能考察它的面试环节。

简要概述

  • Anthropic 的 FDE 招聘广告要求具备生产级 LLM 经验、扎实的 Python 能力，以及在情况不明朗时能自行找到方向的能力。先学习这些内容。
  • 一份面试准备指南描述了这样的流程：招聘人员电话沟通、围绕 Claude 和 MCP 的技术初筛、每一步都会增加新需求的编码测试，以及结合行为问题的设计环节。
  • 你可以使用 Claude 来准备面试，但在正式面试或带回家的作业中不得使用，除非面试官允许。

Anthropic 在伦敦的前沿部署工程师招聘广告中有一句很容易被略过的话：25-50% 的时间用于前往客户现场，与他们一起直接构建。这看起来像是差旅安排，但它表明这个岗位需要的是能在客户面前进行构建的人，而不仅仅是擅长算法谜题的人。

因此，最有效的准备方式是把招聘广告本身当作大纲，将每项要求对应到最可能考察它的面试环节。

招聘广告就是大纲

根据招聘启事，该岗位隶属于应用 AI 团队。FDE 在客户自己的系统中使用 Claude 构建生产级应用。他们交付的是具体的东西：MCP 服务器、子 Agent 和 Agent 技能。这是一份你必须能够亲手构建的东西的清单，仅仅知道这些名称是不够的。

要求同样直接。候选人需要在技术型、面向客户的岗位（例如 FDE）中拥有 4 年或以上的经验。

候选人需要具备 LLM 的生产级经验，包括高级提示词工程和 Agent 开发。他们需要扎实的 Python 能力，而且招聘启事希望找到一位高度主动、能够在庞大、多层且模糊的组织中自行找到方向的人。

每项要求都可以对应到最可能涉及它的面试环节。所以第一项任务是在打开任何编码练习网站之前，先建立这张对应表。

四个环节，每个环节考察一种能力

Exponent/Aced 的一份面试准备指南列出了该岗位的示例流程。第一轮是与招聘人员进行的 30 分钟电话沟通，内容涉及你的背景、求职动机、推荐人以及适合你的职级。

接下来是技术初筛，围绕一个真实场景展开：部署带 MCP 工具的 Claude，并让系统在超长上下文中保持稳定。

根据同一份指南，编码环节是在 CodeSignal 风格的平台上进行的分步实操练习，每一步都会增加一个新需求。

最后一轮面试由两部分组成：解决方案设计，即为客户设计 Claude 系统的架构；以及关于行为表现和公司价值观的问题。

这只是一个示例流程，而非固定时间表，因此请向你的招聘人员询问你自己的面试轮次顺序。

职位描述中的要求最可能考察该点的轮次如何准备

示例：每一步都增加一个新需求的编程测试

拿一个假设的练习题，而不是真实的面试题。第一步：获取 JSON 格式的支持工单列表，并按客户分组。第二步：删除内容重复的工单。第三步：在发送给模型之前进行裁剪，使每个客户的总长度保持在限制以内。

陷阱在于把第一步写成一个冗长的函数。到第三步时，你就不得不在计时进行的情况下把它拆开重写。更稳妥的做法是把每个需求都转化为一个纯函数，这样新需求只需在链条上添加一个环节：

from dataclasses import dataclass
from collections import defaultdict

@dataclass(frozen=True)
class Ticket:
    id: str
    customer: str
    created_at: str  # ISO 8601, e.g. "2026-03-01T09:30:00Z"
    text: str

def load(rows: list[dict]) -> list[Ticket]:
    return [Ticket(r["id"], r["customer"], r["created_at"], r["text"].strip())
            for r in rows]

def dedupe(tickets: list[Ticket]) -> list[Ticket]:          # step 2
    seen, out = set(), []
    for t in tickets:
        key = (t.customer, t.text.lower())
        if key not in seen:
            seen.add(key)
            out.append(t)
    return out

def group(tickets: list[Ticket]) -> dict[str, list[Ticket]]:  # step 1
    groups = defaultdict(list)
    for t in tickets:
        groups[t.customer].append(t)
    return dict(groups)

def budget(groups, max_chars: int):                            # step 3
    trimmed = {}
    for customer, items in groups.items():
        total, kept = 0, []
        # newest first: ISO 8601 strings in one timezone sort chronologically
        for t in sorted(items, key=lambda t: t.created_at, reverse=True):
            if total + len(t.text) > max_chars:
                break
            kept.append(t)
            total += len(t.text)
        trimmed[customer] = kept
    return trimmed

def pipeline(rows, max_chars=4000):
    return budget(group(dedupe(load(rows))), max_chars)

在第三步中，代码按工单创建时间排序，而不是按 id 排序，因为更大的 id 并不能保证是更新的工单。如果数据中没有时间戳字段，请在退而使用 id 之前清楚地说明你的假设。

很多得分来自你边写代码边说的话。明确说出权衡：你保留最新的工单，因为你假设它们更相关；如果这个假设被证明是错误的，你会与客户确认。

这个上下文长度限制问题也与技术初筛核心的长上下文稳定性问题密切相关。

设计轮：先提问，后画图

由于职位描述强调在情况不明朗时找到方向，预计设计题会省略大量细节，因此要养成在动手画任何东西之前先提问的习惯。

假设面试官给出这样的题目：“一家保险公司希望其员工向 Claude 咨询保单条款。”不要立刻画出带有向量数据库的架构图，而是先问几个问题。

你可以从这三个问题入手：“谁会使用它，呼叫中心员工还是理赔部门？保单存放在哪个系统中，它是否有访问控制？如果 Claude 回答错误，后果是客户不满还是错误的赔付？”

只有在回答完这三个问题之后，你才提出架构方案：一个遵循现有访问控制机制的 MCP 服务器、一个专门负责引用政策条款的子 Agent，以及一套基于员工真实提问构建的测试用例。

行为面试与深度探讨环节：真实的故事胜过包装精美的故事

Educative 关于 Anthropic 通用工程师招聘流程的指南指出，技术深度探讨环节更青睐真正理解自己所构建系统的人。在行为面试环节，面试官往往更看重诚实、自我认知和反思，而不是包装精美的成功故事。

实际操作中，至少准备一个关于你某次部署失败的故事。讲清楚技术原因、你当时做出的决策，以及之后你有什么不同的做法。如果你在被追问两层之后仍能解释清楚，这个故事的价值胜过十个只停留在表面描述的项目。

这也是修改简历的时机。避免使用泛泛的“有 LLM 经验”。要写明你构建了一个将模型连接到某个具体系统的 MCP 服务器、它为谁运行，以及你如何衡量其质量。

这样具体的内容并不能替代招聘启事中明确要求的 4 年以上工作经验。它们只是帮助阅读你简历的人一眼看出你这些年到底做了什么。

使用 Claude 的规则：了解它们，避免不必要的失分

Anthropic 已发布了关于候选人使用 AI 的官方指引。你可以使用 Claude 来润色申请材料，但初稿必须由你自己撰写。你可以使用 Claude 来调研公司、练习回答，并为面试官准备问题。

红线划在测评环节。现场面试“完全靠你自己”，除非面试官另有说明，否则不得使用任何 AI 辅助。家庭作业式任务同样不能使用 Claude，除非获得许可。

对于一个整天与 Claude 打交道的职位来说，这看似奇怪，但合理的解读是：他们想在没有助手陪伴的情况下看到你的底层能力。

让优秀候选人折戟的错误

第一个常见错误是复习错了材料：花几周时间刷算法题，而在示例流程中，技术环节是一道基于 MCP 的 Claude 部署场景题。第二个错误是把代码写成一个庞大的整体块，导致每出现一个新需求都要推倒重写。

还有一个错误是在设计题仍然开放、尚未明确时就直接跳到架构设计，跳过了职位描述中点名要求的那种在模糊性中导航的能力。

最后两个错误与人有关。其一是讲述过于完美的故事，让听者找不到任何你真正学到东西的痕迹。

其二是在被禁止的场合使用 Claude，例如未经许可在家庭作业式任务中使用。这会让你失去信任，而在一个以客户信任为根基的职位上，失去信任就意味着失去一切。

本周的练习：请一位同事扮演面试官，只给你一个非常模糊的设计题目，例如“一家医院想在前台使用 Claude”。

设定 30 分钟的计时器，前 10 分钟你只能提问，不能画图；练习结束后，问你的同事你的哪些问题最能澄清问题。
