前沿部署工程师编程测试

原标题：The Forward Deployed Engineer Coding Screen

The Forward Deployed · 2026-07-10 · 约 10 分钟读完

摘要

本文介绍 FDE 面试中的编程筛选环节：它是所有面试流程的第一道门槛，题目偏实用而非算法，带用户场景、限时 25 分钟，且要求会在中途追加需求。文章给出一个工单统计示例，用 Bad/Good/Great 三档说明前 10 分钟的表现差异，强调先跑通最简可用版本、边写边讲解、为扩展预留结构。还提供 20 道练习题库、可粘贴给 AI 扮演面试官的协议，以及针对 take-home（如 OpenAI 要求录屏讲解）的三步训练法。

要点

  • 编程筛选是 FDE 面试第一关，未通过则后续环节无从谈起
  • 题目是带用户场景的实用题，限时 25 分钟且中途会追加需求
  • Great 的做法：先跑通最简版本、边写边讲解、让扩展只需几行改动
  • 提供 20 道无答案练习题和让 AI 扮演面试官的评分协议
  • take-home 训练法：限时做小项目、录 5 分钟讲解、再用 AI 模拟答辩

练习面向生产环境的 FDE 编程题目，边做边沟通，应对不断变化的需求，通过技术面试的门槛。

这里记录的每一个 FDE 面试流程都以编程关卡开场，之后才会对四个信号中的任何一个进行评分。通过了，流程才开始；没通过，你准备的其他任何东西都不会被看到。纵观这些记录在案的考核，模式是一致的：题目偏实用而非算法，题目包裹在用户的场景中，限时进行，而且需求会在中途扩展。这些说法的依据来源都在 面试方法 页面上；本页则把它变成练习。

合理分配时间。方法页的建议依然成立：在这里做维持水平的练习，把大部分时间花在四个信号上。下面要说的是这些维持性练习应该采取的形式。

失败模式与拆解环节的如出一辙：大多数候选人跳过了第一步，要么设计了一个时间预算撑不起的系统，要么默默埋头苦干，做出一个没人看到他们如何得出的完整答案。

练习——完整跑一遍考核

题目： "某客户的客服团队把工单队列导出为文本文件：每行一条工单，每条包含一个 ID、一个客服姓名、一个状态和一个创建时间戳，分隔符不统一。写一个程序，打印每位客服持有的未关闭工单数量。你有二十五分钟。"
扩展要求，大约在中途提出： "另外打印每位客服最早的一条未关闭工单，并把任何缺少状态字段的工单视为未关闭。"
在继续往下读之前： 设一个计时器，用任何语言、大声说出来地试做一遍。然后对照下面的阶梯给你的前十分钟打分。

差 / 良 / 优——前十分钟

差——还没跑通任何东西就开始做架构，或者全程沉默。 同一种失败的两种版本。第一种，到了第十分钟，你有了一个

Ticket

类、一个分隔符策略抽象，以及一个面向未来导出格式的插件系统草图，却没有任何输出，因为什么都还没执行。你在为没人提出的需求做设计，而明确提出的那个需求却还没满足。第二种版本里，你有像样且能运行的代码，却一句都没说出来；面试官只看到有人在打字。无论哪种，都没有留下这个环节所考察内容的可评分证据：一个能在限时下交付成果、并边做边展示思路的人。

良好——快速写出能运行的代码，但耦合在一起。 几分钟后你得到了一个真实结果：按逗号拆分每行，保留状态为 open 的行，按 agent 统计到映射中，然后打印。输出正确，而且很早：确实是一个不错的开局，比大多数第一次尝试都好。但解析、过滤和报告全部挤在一个循环里，而且逗号是承重墙。当扩展需求到来时，“最旧工单”的提问和“状态缺失”的规则都属于你的代码从未分离的阶段，于是循环不得不在计时压力下重写，而你之前略过的“分隔符不一致”那句话也变成了面试官指出的 bug。

优秀——最简单能运行的版本，边讲边写，并为第二个需求做好了准备。 你在敲代码之前先说出计划：一个小函数把原始行转换成纯记录，并负责处理所有分隔符的混乱；记录收集进一个列表；报告读取这个列表。几分钟内达成第一个里程碑：文件读入，输出每个 agent 的计数，并用几行粘贴的数据做了校验。当扩展需求到来时，“最旧工单”只是报告步骤里的几行代码，“状态缺失”规则只是解析步骤里的一行；没有任何东西被重写，而且你边做边说明了这一点。优秀胜过良好，是因为良好把一切都押在“第一个需求就是唯一需求”上，而优秀付出了一点早期成本——把解析和报告分开——这让第二个需求变得廉价，并且在下注的同时把赌注讲了出来。

需要预料的追问

面试官：“这段代码非常朴素。你会就这样上线吗？”
你：“就本次练习而言，会。计时换来的是能运行的代码和一个能扛住下一个需求的结构，这一点做到了。如果这是要交付给客户的，在别人开口之前我会加固这些地方：目前格式错误的行被静默跳过，所以我会对它们计数并记录日志；解析规则会移到测试之下，因为真实的导出格式会漂移。”

这个追问考察的是：这种朴素是否是一种选择。主动指出生产环境的缺口并给出理由，就证明了它是。

练习工具包

一道答案就印在题目下方的练习题，读一遍之后就不再能考验你了。下面的工具包才是那些未经排练的练习的来源：二十道题目，本网站上没有任何地方给出答案，还有一套把 AI 聊天变成面试官的流程，计时器和扩展需求都包含在内。每次练习都是同样的形式：一道题，二十五分钟，边说边做，按照上文框架中的四个动作来评分。

题库

  • 解析一家诊所的预约导出文件，其中日期有多种格式，打印每位医生当天的预约，并标记出重复预约。
  • 合并来自一家公司及其刚收购的公司的两份客户名单，对名字和邮箱仅大小写或标点不同的条目去重。
  • 为一个支持收件箱构建限流器，允许每位客户每小时发送固定数量的消息，其余消息进入队列并附带排队位置提示。
  • 为值班工程师总结 Web 服务器的访问日志：最繁忙的路径、每个路径的失败次数，以及出现频率最高的客户端地址。
  • 编写一个小型调度器，将配送司机分配到时间段，需遵守每位司机申报的可用时间以及最长班次时长。
  • 给定仓库库存文件和一天的订单，打印哪些订单可完整发货、哪些只能部分发货，以及需要补货的商品。
  • 用模糊规则对募捐活动的捐赠人名单去重：当姓名在忽略中间名缩写的情况下匹配、且地址在忽略公寓号的情况下匹配时，视为同一人。
  • 将教师的成绩册导出文件（列不齐、分数缺失）转换为每位学生的平均分，以及每位学生缺交作业的清单。
  • 构建一个会议室预订系统：接受带开始和结束时间的请求，拒绝时间重叠的请求，并在拒绝时报告下一个空闲时段。
  • 解析银行的交易数据流，标记当日取款金额超过第二个文件中申报限额的账户。
  • 从一个包含 RSVP 邮件的文本文件中，提取每位宾客的姓名、随行人数和饮食禁忌，整理成餐饮承办商可读的表格。
  • 为翻译团队构建一个轮询式任务分配器，需尊重每位译者的语言对和每日工作量上限。
  • 将配送车队的位置信号日志汇总为每辆车的行驶里程和空闲时间，并能容忍乱序到达的信号。
  • 给定医院排班表和一份请假名单，打印无人值守的班次，以及每个班次中具备资质、可以顶班的员工。
  • 为支付通知消费者构建一个重试队列：失败的投递按递增的延迟重试，并在固定次数尝试后被放弃。
  • 将图书馆的借阅记录解析为逾期通知，并把同一借阅人的多本逾期图书合并为一条通知。
  • 给定两家使用不同单位约定的供应商价格文件，将其标准化，并打印每种商品更便宜的供应商。
  • 为部署流水线构建一个日志跟踪器：将日志行分组为各个阶段，打印每个阶段的耗时，并指出失败的那个阶段。
  • 将餐厅的自由文本预订备注转换为座位核查：将随行人数与餐桌容量对比，并标记无法安排座位的团体。
  • 从客服队列导出数据中，计算每个工单到首次响应的等待时间，并列出等待最久的客户，同时容忍缺失的时间戳。

AI 面试官

将下面的代码块原封不动地粘贴到任何能力足够的 AI 聊天中，然后从题库中给出几个任务，或让它自行出题。在真实的编辑器中工作，并随时把你的代码粘贴到聊天里；只有当你在构建过程中真的开口（或打字）讲述思路时，叙述要求才会真正生效。

你是前沿部署工程师编程筛选环节的面试官。人设：一位每周主持这类筛选的资深工程师。务实、干脆、盯着时间、不卖弄花哨。规则：1. 每次只给一个任务。从我粘贴在后面的列表中选一个，或现场编一个同类型的任务：一个有真实用户的小型实用程序——解析、合并、分组或转换混乱的数据。绝不考算法谜题。不重复任务。当任务涉及输入文件时，在我开始之前，自己生成八到十二行带有真实不一致性的样例数据。2. 我自己开一个二十五分钟的计时器，并在每条消息前加上已用分钟数；当我报告的时间超过十二分钟和二十分钟时，告诉我剩余时间，超过二十五分钟时宣布时间到。3. 当我报告的已用分钟数第一次超过十二分钟时，恰好扩展一次需求：增加一个相关的要求，使得一个简单、干净分离、已经在运行的第一版只需几行代码就能吸收，而一个硬编码或尚未运行的第一版则无法做到——比如一个新字段、第二种分组方式、或一条规则的例外。不要提前扩展，也不要扩展第二次。4. 要求边写边讲解。我会粘贴代码并随时说明我在做什么。如果我连续两条消息只粘贴代码而不说明它在做什么或为什么，就问：“你在想什么？”并把这次沉默记入评分。除非我明确说“提示”，否则在整个过程中不给任何提示、建议或代码——如果我说了，就给出尽可能小的提示，并记入评分。5. 当我说“完成”或时间耗尽时，对四个动作逐一判定 PASS 或 FAIL，并为每一项引用具体时刻：(a) 我是否尽早让一个小而能跑的东西端到端跑通；(b) 我是否先写了简单版本，使扩展无需重写就能落地；(c) 我是否选择了数据整理——解析、分组、转换——而不是聪明的算法；(d) 我是否边打字边讲解。评分要严格：典型的第一次练习至少会在四个动作中的两个上失败——如果一项都没失败，先重新审视再表扬，并且绝不因为我和你争辩而放软评分。6. 最后给出下一次练习中恰好一个需要改进的点。然后提供下一个任务。

带回家作业，反复演练

有些招聘流程以实验室式的带回家作业开场，而不是现场筛选。方法页收录了一位候选人的报告，内容是一个基于 OpenAI API 构建的带回家作业，要求附带录制的视频讲解，随后是一场现场筛选，你需要为自己的作品辩护。这是一个单一案例，所以不必拘泥于形式；它所锻炼的技能可以迁移到任何要求你展示自己作品的招聘流程中。

这个演练分三步：

  • 根据既定评分标准构建一个小项目。 它调用真实的模型 API；为既定用户端到端地完成一件有用的事；包含一种你实际可以运行的输出质量检查方式，比如一个小型标注集或抽查脚本；并且它的 README 写明你会捍卫的两个设计决策，以及每个备选方案为何落败。开始前先定好时间上限，时间一到就停止。这个约束本身就是练习的一部分。
  • 录制一段五分钟的口头讲解。 屏幕加语音：它做什么、那两个决策、你接下来会做什么。讲解时假设听众是初次接触这个项目的客户工程师。只录一遍。它所模拟的正式轮次不会给你第二次机会。
  • 用下面的协议对它进行质询。 获取你录制的讲解的文字稿，连同你的 README 一起，粘贴到 AI 聊天中的协议下方。AI 扮演随带回家作业之后的现场技术面试。
你是前沿部署工程师带回家作业之后现场技术面试的面试官。在本协议下方，我将粘贴我录制的讲解文字稿和我的项目 README。规则：1. 把文字稿当作我的现场讲解。如果它读起来像整理过的摘要而不是口头表达，请指出来，并将其视为薄弱证据评分。2. 追问设计决策：对于讲解或 README 中捍卫的每个决策，追问被否决的备选方案为何落败，然后对我的回答恰好追问一次再继续。如果任何地方捍卫的决策少于两个，请立即指出，并标记评分 (c) 为未通过。3. 定性地追问生产环境的缺口：如果使用量增长一百倍会出什么问题，当模型返回垃圾输出时会发生什么，上线之后我如何得知输出质量下降了。不要编造统计数据，也不要向我索要数字——评估的是推理过程，任何地方都不要使用编造的数字，包括在评分中。4. 追问对弱点的坦诚：问我项目最薄弱的部分是什么。回避或给出表面化的弱点则此项质询不通过；坦率说出真实弱点及其后果则通过。5. 质询结束后，对以下四项分别标记 PASS 或 FAIL，每项引用文字稿中的具体片段——或指出其缺失：(a) 项目是否为既定用户端到端地完成一件有用的事；(b) 是否包含可运行的输出质量检查方式，讲解中是否展示了它；(c) README 中的两个决策是否以经得住追问的理由得到了捍卫；(d) 我是否坦诚面对弱点而非掩饰。评分要严格：一次典型的首次练习至少会在四项中的两项上失败——如果没有任何一项失败，在表扬之前先重新审视，并且绝不因为我的争辩而放宽评分。6. 以恰好一件需要改进的事结尾。然后提出在我修改项目或讲解之后重新进行质询。
