Agent API 调用重试与幂等键 TypeScript 实现

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

这篇指南面向在现场部署客服 Agent 的工程师，讲解如何用约 80 行 TypeScript 正确封装 API 调用层。文章以一笔订单被重复退款的事故切入，指出问题不在模型而在 fetch 封装代码，并给出超时、有节制重试和幂等键三要素的完整实现。

要点

  • 有副作用的 API 只有支持幂等时才能安全重试。
  • 幂等键应在循环外生成一次，每次重试复用，且只用于 POST。
  • 超时应依据下游 API 的 p99.9 延迟百分位设定。
  • 跨层重试会放大负载，Amazon 曾出现 243 倍放大案例。
  • 带键请求不应重试 5xx，因为服务器会返回保存的同一结果。

超时、有节制的重试和每个操作固定的幂等键，约 80 行 TypeScript 就能实现，可直接复制到项目中。

要点速览

  • 有副作用的 API，只有支持幂等时才能安全重试。
  • 每个业务操作只生成一次幂等键，每次重试都复用它，并且只在 POST 请求上附加。
  • 重试需要预算：如果每一层都各自重试，数据库负载最多可能放大 243 倍。

设想你在客户现场的第二周。团队部署的客服 Agent 有一个名为

createRefund

的工具，负责调用客户内部的退款 API。某天下午网络不稳，第一个请求没有收到响应，Agent 于是又试了一次。第二天早上，财务团队发现有一笔订单被退了两次款。

问题不出在模型上，而出在包裹

fetch

的那十几行代码里，这部分代码通常被当成杂活。对前线部署工程师（FDE）来说，API 调用层正是 Agent 接触客户资金、库存和生产数据的地方，必须一次写对。

这一层需要三样东西：超时、有节制的重试和幂等键。本指南逐一讲解，最后把它们组合成一个完整的 TypeScript 函数，可以直接复制，再按自己的项目修改。

为什么简单粗暴的重试很危险？

Amazon Builders’ Library 说得很直白：有副作用的 API，除非支持幂等，否则重试并不安全。退款请求超时后，客户端无法判断服务器是否已经处理。数据包可能根本没送到；也可能钱已经转出，只是响应在返回途中丢了。

幂等键恰好消除了这种不确定性。Stripe 的文档写道，如果发生连接错误，可以重新发送请求，不会有创建第二个对象或把同一次更新执行两次的风险。

机制很简单。对每个键，Stripe 都会保存第一个请求的状态码和响应体，无论成功还是失败，之后每次重发都返回同样的结果。

“无论失败”这一点很关键。按 Stripe 的说法，如果第一次尝试返回 500，用同一个键重试拿到的也是同一个 500。因此，用旧键重试主要适用于失败发生在传输途中的情况，比如超时或连接中断，也就是客户端还没收到任何结果的时候。

超时该设多长？

对 Agent 来说，默认值通常宽松得多。OpenAI 的 Node SDK 默认超时是 10 分钟。这对耗时较长的模型调用合适，但查询订单的 API 不该让 Agent 等这么久。

Amazon 给出了一种有依据的选法。先确定能接受多大比例的“误超时”，即再多等一会儿本可以成功的请求；然后取下游服务对应的延迟百分位，例如 p99.9。

如果退款 API 的 p99.9 是 1.2 秒，把超时设为约 1.2 秒，就意味着你接受截断大约 0.1% 本可成功的请求。

在 Node 中不必自己用

setTimeout

实现。

AbortSignal.timeout()

返回一个到时自动中止的信号，触发时以名为

TimeoutError

的

DOMException

中止。这样代码就能区分超时和用户主动取消，两种情况需要不同的处理。

重试几次才够？

OpenAI 的 SDK 是很好的参考设计。据其 README，它默认自动重试两次，采用较短的指数退避。默认重试 408、409、429、所有 500 及以上的错误，以及连接错误。它不会重试 400 或 401，因为原样重发同一个请求，结果不会改变。

光有退避还不够，还需要抖动。Amazon 对抖动的描述是：在等待时间里加入一些随机性，让重试在时间上分散开。如果没有抖动，一千个同时失败的 Agent 会话会在同一时刻重试，再次把服务压垮。

最大的危险是跨层叠加的重试。Amazon 举过一个例子：一个五层系统，每层都独立重试，数据库负载因此放大 243 倍。

倒推一下，243 是 3 的 5 次方，也就是每层最多尝试三次的结果。Amazon 的办法是用令牌桶在本地限制重试。令牌用完后，这一层就停止重试，把错误向上传递。

完整的 TypeScript 实现

下面的

callApi

函数把三者结合在一起。注意生成键的那一行：它在循环之外。

import { randomUUID } from "node:crypto";

type Method = "GET" | "POST" | "DELETE";
interface CallOptions {
  method: Method;
  url: string;
  body?: unknown;
  timeoutMs: number;          // 取自下游 API 的 p99.9
  maxRetries?: number;        // 默认为 2
  idempotencyKey?: string;    // 如果操作已有键，就传进来
  signal?: AbortSignal;       // 来自 Agent 或用户的取消信号
}

// 令牌桶：最多 10 次重试，每秒补充 1 个令牌
class RetryBudget {
  private tokens = 10;
  constructor() {
    setInterval(() => (this.tokens = Math.min(10, this.tokens + 1)), 1000).unref();
  }
  take(): boolean {
    if (this.tokens <= 0) return false;
    this.tokens--;
    return true;
  }
}
const budget = new RetryBudget();

// 带键的请求：不重试 5xx，服务器已保存结果，只会返回同样的错误
const isRetryableStatus = (s: number, hasKey: boolean) =>
  s === 408 || s === 409 || s === 429 || (!hasKey && s >= 500);

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const backoff = (attempt: number) =>
  Math.random() * Math.min(5000, 200 * 2 ** attempt); // 抖动

export async function callApi(opts: CallOptions): Promise<Response> {
  const maxRetries = opts.maxRetries ?? 2;
  // 整个操作只生成一次；只有 POST 携带键
  const key =
    opts.method === "POST" ? opts.idempotencyKey ?? randomUUID() : undefined;

  for (let attempt = 0; ; attempt++) {
    // 每次调用都有自己的超时，并与调用方的取消信号合并
    const timeout = AbortSignal.timeout(opts.timeoutMs);
    const signal = opts.signal ? AbortSignal.any([opts.signal, timeout]) : timeout;
    try {
      const res = await fetch(opts.url, {
        method: opts.method,
        headers: {
          "Content-Type": "application/json",
          ...(key ? { "Idempotency-Key": key } : {}), // 请求头名称取决于具体 API
        },
        body: opts.body ? JSON.stringify(opts.body) : undefined,
        signal,
      });
      const canRetry =
        isRetryableStatus(res.status, key !== undefined) &&
        attempt < maxRetries &&
        budget.take();
      if (!canRetry) return res;
      await res.body?.cancel(); // 丢弃响应体，在重试前释放连接
    } catch (err) {
      // 调用方已取消：立即停止，不重试
      if (opts.signal?.aborted || attempt >= maxRetries || !budget.take()) throw err;
      // 否则是 TimeoutError 或网络错误：用同一个键重发
    }
    await sleep(backoff(attempt));
    if (opts.signal?.aborted) throw opts.signal.reason;
  }
}

回到退款的例子。第一次调用超时，catch 块收到

TimeoutError

，函数等待一段随机时间后，用同一个键重发。如果服务器其实已经处理了第一个请求，它会返回保存的结果，不会再退第二次款。

改写这个函数时，有两个小细节值得保留。调用方的取消信号通过

AbortSignal.any()

与超时合并，因此 Agent 中途被停止时，函数会立即退出，而不是继续重试。另外，为了重试而丢弃响应时，会取消其响应体，避免连接卡在连接池里。

这里的重试条件在一点上比 OpenAI SDK 更窄：携带键的请求不重试 500 及以上的错误。原因就是前面讲的机制。对于像 Stripe 这样按键保存首次结果的 API，在 500 之后用同一个键重发，只会拿到同一个 500，白白消耗预算，毫无收益。

GET 和 DELETE 不带键，所以仍然照常重试 5xx。如果客户的 API 处理键的方式不同，放宽这个条件前先问清楚。

当 409 表示与另一个并发请求冲突时，仍然值得重试。Stripe 说明，参数校验失败或请求与正在进行的请求冲突时，它不会保存结果，因此这些情况下重发是安全的。

现场常见错误

最常见的错误是在循环内生成键。这样每次重试都带着新键，服务器会把它当成新操作，幂等性就没了。

Agent 还带来一个更隐蔽的变体：模型在后面的步骤里再次调用同一个工具，而你的调用层为这次调用生成了新键。如果编排器可能重跑某个步骤，就从该步骤的 ID 派生出键，通过

idempotencyKey

传入。

第二个错误是用不同的参数复用同一个键。Stripe 会把新参数与原始请求比对，不一致就返回错误。它还可能在 24 小时后删除键，所以第二天重跑的任务不能指望旧键。

第三个错误是给每个请求都加上键。Stripe 明确指出，GET 和 DELETE 本身就是幂等的，给它们发键没有任何作用。也不要把邮箱地址或账号放进键里。Stripe 建议使用 UUID V4 或熵足够的随机字符串，最长 255 个字符，不含敏感数据。

最后一个错误最难发现：在 SDK 之上叠加重试。如果你的工具封装了一个本身就会重试两次的客户端，而 Agent 的编排器又在上面再重试一遍，放大倍数在你察觉之前就已经成倍增长了。只选一层负责重试，其他地方一律关闭重试。

把这项技能写进简历

阅读 FDE 岗位的职位描述时，留意关于对接客户系统或生产环境可靠性的要求。这类代码正适合放在这部分经历里讲。

简历上不要只写“构建了调用 API 的 Agent”。要写清楚超时依据哪个百分位设定、哪一层负责重试，以及如何用幂等防止重复操作。

面试中，“如果创建订单的请求超时，你的 Agent 会怎么做？”正是你画出上面这个循环的机会。面试官会记住那些明白超时并不等于失败、而是结果未知的候选人。
