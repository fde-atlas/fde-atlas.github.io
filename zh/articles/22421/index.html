AI 系统设计面试题 2026：50 个设计与答案

原标题：AI System Design Interview Questions 2026: 50 Designs and Answers

Cloud Soft Solutions · 2026-10-06 · 约 43 分钟读完

摘要

这篇来自 Cloud Soft Solutions 的指南面向 2026 年 AI 系统设计面试，收录 50 道题：15 题讲解设计方法，35 题给出完整设计，涵盖企业文档问答、text-to-SQL、LLM 网关、带审批的 Agent 和离线批处理流水线。文章强调 AI 系统设计不同于传统系统设计，面试官重点考察需求澄清、token 与成本估算、检索或 Agent 架构、评测方案、安全边界及模型出错时的应对。作者给出固定的答题流程，并区分初级、高级和面向客户岗位的考察重点，所有数字仅为练习估算的示例。

要点

  • 50 道题：15 题方法加 35 个完整设计，覆盖 RAG、text-to-SQL、LLM 网关等。
  • 核心答题流程：澄清需求、估算 token 与成本、画基线架构、深挖风险组件、评测与安全。
  • 高级岗位（含 FDE）需在 45 至 60 分钟内展示估算、模型路由、故障模式与成本杠杆。
  • 评测分四层：黄金数据集、组件指标、LLM 评审校准、上线后在线信号。
  • 安全边界设在信任变化处，模型本身不是边界，检索内容应视为不可信输入。

AI 系统设计面试题考察的东西与经典系统设计不同。面试官仍然期望你讨论负载均衡器、队列和数据库，但他们主要想看的是：你能否把一个模糊的 GenAI 想法转化为一个具备明确需求、token 和成本预算、检索或 Agent 架构、评测计划、安全边界，以及对“模型出错时怎么办”这一问题的可信回答的系统。 本指南涵盖 50 道高价值题目：15 道关于设计方法本身，然后是 35 道完整设计，从企业文档问答和 text-to-SQL，到 LLM 网关、带审批机制的 Agent，以及离线批量富化流水线。

如何使用本指南

  • 初级和中级面试流程（AI 工程师、GenAI 开发者）通常只选一个设计，例如 RAG 助手，并考察你能否澄清需求、勾勒组件、说出一个评测指标。
  • 高级面试流程（资深 AI 工程师、AI 架构师、前沿部署工程师）则期望你进行估算、模型路由、故障模式分析、租户与权限边界设计以及成本优化手段，并在 45 到 60 分钟内全部完成。
  • 面向客户的面试流程增加了一层需求挖掘：面试官扮演利益相关者，如果你在画架构图之前先询问业务成果，会获得加分。

先阅读 Q1 到 Q15。它们提供了后面每个设计都会复用的方法。对于每个设计，练习大声说出澄清性问题、凭记忆画出架构图，并深入论证某一个权衡取舍。本指南中的所有数字都是用于练习估算的示例占位值，并非基准测试结果或厂商报价。

设计方法：需求、估算与模型

1. 在 45–60 分钟的 AI 系统设计面试中，你应该如何组织答题结构？

回答： 使用固定的答题顺序，这样你绝不会遗漏面试官评分的要点：澄清问题和成功指标，估算流量、token、延迟和成本，画出基线架构，深入剖析风险最高的组件，然后覆盖评测、故障模式、安全和成本优化。把前五到八分钟留给提问。那些第一分钟就开始画向量数据库的候选人，通常设计出的系统是错的。

澄清（用户、任务、数据、风险、指标）| 估算（QPS、token、延迟、成本）| 基线设计（能用的最简方案）| 深入剖析（检索 / Agent / 数据路径）| 评测 -> 故障模式 -> 安全 -> 成本 | 上线计划 + 接下来我会做什么

面试技巧： 一开始就把这个顺序大声说出来。这展示了你的条理性，也让面试官如果更关注某一部分，可以尽早引导你调整方向。

2. 对于基于 LLM 的系统，哪些澄清性问题最重要？

回答： 将它们分组，以便快速覆盖全面：

  • 用户和任务： 谁在使用它，它支持什么决策或操作，是回答问题还是执行操作。
  • 数据：来源、格式、新鲜度、数据量、由谁负责，以及适用哪些权限。
  • 风险：答错的代价是什么、是否有人工审核输出、监管约束（如数据驻留要求或印度的 DPDP 法案）。
  • 规模与体验：用户数量、峰值并发、语言、渠道、延迟预期。
  • 成功标准：业务指标（处理时长、问题分流率、节省的分析师工时）以及每个请求或每月的预算。

最能揭示真相的一个问题是：“今天没有 AI 的情况下是怎么做的？”它为你提供了需要超越的基线，并且通常会暴露出真正的数据来源。

3. 你如何判断一个问题是否真的需要 LLM？

回答：当输入是非结构化语言、输出需要生成或灵活解读、且一定程度的错误可以容忍或可被审核时，使用 LLM。如果逻辑是确定性的（税务规则、资格检查），就用代码。如果你有大量标注数据和固定的标签集合，传统分类器更便宜、更可预测。如果用户只是需要找到一份文档，好的搜索可能就足够了。资深的回答往往会组合使用：用规则处理硬性约束，用分类器做路由，只在语言密集的环节使用 LLM。在面试中说出“这部分不应该用 LLM”是一个强信号，而不是弱信号。

4. 你如何在提示词、RAG、微调和 Agent 之间做选择？

回答：根据缺失的是什么来选择：知识、行为还是行动。

方法适用场景主要成本或风险
仅用提示词模型已具备足够知识；任务只是格式或风格提示词脆弱；无私有知识
RAG答案依赖私有且不断更新的文档；需要引用来源检索质量、权限、数据摄取管道
微调需要在大规模下保持一致的格式、语气或领域行为；需要更小的模型训练数据、模型变更时需重新训练、无法获取最新事实
带工具的 Agent任务需要在其他系统中执行多个步骤或操作死循环、不安全的操作、评估更困难

这些方法可以组合：许多生产系统是带一两次工具调用的 RAG 工作流，而不是自由漫游的 Agent。

5. 你如何估算每个请求的 token 数？

回答：把提示词的各部分和预期输出加总，再乘以每个用户请求的模型调用次数。一个示意性的 RAG 请求：

  • 系统提示词和指令：约 800 token
  • 检索到的上下文：5 个片段，每个约 400 token = 2,000 token
  • 对话历史（已摘要）：约 600 token
  • 用户问题：约 50 token
  • 输出：约 300 token

一次调用大约是 3,450 个输入 token 和 300 个输出 token。如果设计还包含查询改写调用和护栏检查，也要把它们计入；Agent 每个任务可能发起五到十五次调用，每次都携带不断增长的对话记录。请记住，token 数量因分词器和语言而异：印度语言的文本通常比英语每词消耗更多 token，这对多语言设计很重要。参见 tokens and context windows explained。

6. 如何估算一个 LLM 功能的月度成本？

答案： 每月请求数乘以每次请求的 token 数，输入和输出分别计价，再加上检索、托管和可观测性成本。以一个内部助手为例：

用户 20,000 名员工 用量 每天 4 个问题 x 22 天 每月请求数 20,000 x 4 x 22 = 1.76M 输入 token 1.76M x 3,450 = 约 6.1B 输出 token 1.76M x 300 = 约 0.53B 模型成本 (6.1B/1M x Pin) + (0.53B/1M x Pout)

Pin 和 Pout 是供应商当前每百万 token 的价格，应当查询而不是凭记忆引用。然后说明优化手段：更短的系统提示词、更少更小的分块、对静态前缀使用提示词缓存、把简单问题路由到更小的模型、对重复问题使用语义缓存，以及离线任务使用批量 API。面试官更看重公式和优化手段，而不是最终的卢比数字。

7. 如何为一次 GenAI 请求制定延迟预算？

答案： 把端到端延迟拆分为多个阶段并为每个阶段设定目标，然后确定用户实际感知的是什么。以一个聊天场景的预算为例：认证和策略检查约 20–50 ms，查询改写 200–400 ms，混合检索 100–300 ms，重排序 100–200 ms，然后是模型的首 token 时间和 token 生成速率。在流式输出下，用户感知的是首 token 时间，因此它成为关键目标，而总生成时间对需要完整响应的工具调用 Agent 和 API 更为重要。优化手段包括并行运行检索分支、对简单查询跳过改写步骤、中间步骤使用更小的模型、提示词缓存以及保持提示词简短。如需完整讲解，请阅读 LLM latency optimisation。

面试提示： 询问该体验是交互式聊天、语音（要求严格得多）还是后台任务（延迟几乎不重要，成本才重要）。

8. 在系统设计中如何选择模型？

回答： 按步骤选择，而不是按产品选择。分类、路由和抽取通常在小型、快速的模型上运行良好；复杂推理或长篇综合可能需要更大或具备推理能力的模型；嵌入和重排序器则是单独的选择。选择标准：在自有评测集上的质量、延迟、成本、上下文窗口、结构化输出和工具调用的可靠性、语言覆盖范围、数据驻留和合同条款，以及客户已使用的云平台上的可用性（Amazon Bedrock、Azure OpenAI、Google Cloud 上的 Gemini，或自托管的开源权重模型）。将模型置于网关或抽象层之后，以便可以更换模型，因为模型版本会被弃用。不要把硬编码的模型名称当作答案；应描述选出该模型的评测过程。参见如何为企业选择 LLM。

9. 哪些非功能性需求是 AI 系统特有的？

回答： 在可用性、延迟和安全性之外，AI 系统还增加了：

  • 质量目标： 有据可依性、答案正确性、拒答行为，在商定的评测集上进行衡量。
  • 每任务成本以及每个租户或用户的 token 预算。
  • 可复现性： 记录提示词、模型和索引版本，以便日后解释某个答案。
  • 数据驻留与保留，针对提示词、输出和日志。
  • 供应商依赖： 配额、速率限制、模型版本弃用以及备用方案。
  • 可审计性： 谁问了什么、使用了哪些来源、执行了哪些工具操作以及由谁批准。

10. 如何围绕供应商的速率限制和配额进行设计？

回答： 将模型容量视为任何稀缺依赖项。了解每个模型和区域的每分钟 token 数和每分钟请求数限制，并据此评估峰值负载。然后添加一个网关，用于强制执行每租户配额、在遇到限流错误时使用指数退避和抖动进行重试，并在达到限制时路由到次要区域或经批准的替代模型。将交互式流量与批处理流量分开，使用不同的队列和优先级，以免夜间任务饿死实时用户。对于可预测的高流量，评估供应商提供的预留或预置容量选项，并与按需定价进行比较；查阅当前文档以了解每个云平台提供的内容。

评测、故障模式与安全边界

11. 在设计面试中，评测计划是什么样的？

回答： 四个层次。第一，离线黄金数据集：由领域专家构建的真实或贴近真实的问题，附带预期来源和参考答案。第二，组件级指标：检索召回率与精确率、忠实度、答案相关性、工具调用正确性、格式有效性。第三，LLM 即评审：在样本上用人工标注进行校准，从而了解评审模型何时与人类判断不一致。第四，上线后的在线信号：用户反馈、升级或人工接管率、任务完成率以及单任务成本。用发布门禁把它们串起来：除非回归测试套件通过，否则任何提示词、模型或索引变更都不得发布。Ragas、LangSmith 和 Langfuse 等工具可以帮助运行和跟踪这些评测。想深入了解，请参阅 LLM 评测 和 LLM 评测面试题。

12. 每种 AI 设计都应应对哪些失效模式？

回答： 逐一列出它们，并为每种失效模式给出检测手段和缓解措施。

失效模式检测缓解
幻觉或无依据的回答忠实度检查、引用验证基于依据的提示、“我不知道”路径、高风险场景人工审核
检索未命中评测集上的检索召回率、低分告警混合搜索、重排序、更好的分块
通过文档或工具进行的提示注入红队测试、输出策略检查将内容视为数据、最小权限工具、审批机制
Agent 循环或成本失控步数与 token 计数步数限制、预算、超时
服务商故障或限流错误率告警备用模型或区域、降级模式
索引过期或错误每个来源的新鲜度指标增量摄取、真值来源校验
变更后的质量漂移回归测试套件、在线指标提示词版本化、金丝雀发布、回滚

13. 在 AI 架构中，你在哪里划定安全边界？

回答： 在信任发生变化的每一处。模型本身不是安全边界：其上下文中的任何内容都可能影响它的输出，因此强制执行必须发生在模型周围的代码中。

user --(SSO token)--> app / orchestrator
                         |  B1: authn, authz, tenant
            +------------+-------------+
            |                          |
   retrieval (ACL filter)     tools (scoped creds)
            |  B2: content is          |  B3: actions
            |  untrusted data          |  need policy
            +------------+-------------+
                         |
                 gateway (redact, log)
                         |  B4: data leaves org?
                   model provider

B1 将每个请求绑定到真实身份和租户。B2 将检索到的文档和工具结果视为可能包含注入指令的不可信输入。B3 依据策略和用户自身权限检查每次工具调用，并对高风险操作进行审批。B4 控制哪些数据离开组织以及服务商可以如何保留数据。控制措施目录请参阅 AI 护栏。

14. 你如何为 LLM 应用设计可观测性？

回答：对每个请求进行端到端追踪，为每次检索、重排、模型调用、护栏检查和工具调用各创建一个 span。记录提示词模板版本、模型标识符、token 数量、延迟、成本、检索到的文档 ID 以及最终结果。OpenTelemetry 提供了跨服务传播追踪的标准方式，而 Langfuse 或 LangSmith 等面向 LLM 的工具则增加了提示词和评测视图。面试中有两个设计要点：确定哪些内容不能以明文记录（PII、机密信息），并在存储前进行脱敏并制定保留规则；以及将追踪与评测关联起来，这样生产环境中的一个糟糕回答可以一键变成新的测试用例。

15. 你如何收尾一个 AI 设计回答并提出上线方案？

回答：用三句话总结：你优化的需求、架构，以及主要风险及其缓解措施。然后提出分阶段上线：先用黄金数据集进行离线评测，再与小规模用户群进行影子或内部试点，接着在有人工审核和严格预算限制下限量发布，指标保持稳定后再扩大推广。最后说明如果有更多时间你会做什么，例如为高流量步骤微调一个小模型，或构建更精细的权限模型。

知识、搜索与文档设计

下面每个设计都遵循相同的结构：澄清问题、架构草图、关键组件、权衡取舍、扩展性、评测，以及安全与成本。在面试中，你没有时间对所有部分都深入展开；请挑选真正存在风险的一两个部分。

16. 为 20,000 名员工设计一个企业文档问答助手。

回答：一个具备权限感知的 RAG 系统，覆盖 SharePoint、Confluence 和政策 PDF，可在 Teams 和网页应用中使用，回答时附带引用，当答案不在来源中时予以拒绝。

澄清问题：有哪些来源、文档数量多少？文档变更频率如何？文档权限是否因群组而异？涉及哪些语言？错误回答是带来不便还是合规问题（HR、法务、安全）？

SharePoint / Confluence / PDFs
        |  connectors + ACL sync
   parse -> chunk -> embed -> index (vectors + ACLs)
                                  |
user (SSO) -> API -> rewrite -> hybrid search
                                  |  filter: user groups
                           rerank -> top k
                                  |
                        LLM (grounded, cited)
                                  |
                   answer + citations + feedback

关键组件：同步内容和 ACL 的源连接器、保留标题和表格的解析器、混合（关键词加向量）索引（如带 pgvector 的 PostgreSQL 或托管搜索服务）、重排器、带强制引用格式的有据可依提示词，以及反馈闭环。

权衡取舍：查询时按 ACL 预过滤比后过滤更安全；较大的分块提供更多上下文但会稀释检索效果；查询改写步骤能改善追问体验但会增加延迟。

扩展性：由变更事件驱动的增量摄取，而非每晚全量重建索引；按内容哈希缓存嵌入向量；API 无状态化扩展。

评测：每个部门的黄金问题集、检索召回率、忠实度、引用正确性，以及一个“必须拒绝”的问题集——即特定角色无权查看的问题。

安全与成本： 在检索查询中强制执行 ACL 过滤，日志中进行 PII 脱敏，对静态前缀使用提示词缓存。完整构建过程见我们的 RAG 知识助手项目，检索深度相关的问题见 RAG 面试题指南。

17. 设计一个多租户 RAG SaaS 产品。

回答： 一个平台，许多客户组织上传自己的文档并获得一个助手，具备严格的数据隔离、按租户配置以及基于用量的计费。

   logs, traces, cost tags -> FinOps dashboards

关键组件：统一 API、每个应用的虚拟密钥、策略执行、提供商适配器、流式透传、重试与回退，以及按团队和用例标记的用量记录。

权衡：网关是单点故障并增加几毫秒延迟；应冗余部署并保持精简。将所有提供商功能规范化为一个 API 会丢失提供商特有的能力；必要时允许透传。

扩展：无状态、水平扩展；配额存储在快速的共享存储中。

评测：网关开销、故障转移演练、策略测试套件。

安全与成本：提供商密钥仅存于网关中。参见 LLM 网关详解 和 企业 AI 架构。

44. 为多个 AI 团队设计一个评测平台。

答案：一个共享服务，团队可以在其中注册数据集、定义指标、针对提示词、模型或流水线的任意版本运行评测，并根据结果来把关发布。

澄清问题：有多少团队和应用类型（RAG、AI Agent、信息抽取）？需要 CI 集成吗？需要人工标注吗？数据集的数据敏感度如何？

datasets (versioned)    metrics (code, judges)
          \               /
        eval run (app version X)
                 |
   runner: call app -> collect traces
                 |
   scorers: exact, schema, retrieval, LLM judge
                 |
   results store -> compare with baseline
                 |
   CI gate pass / fail | human review queue

关键组件：版本化数据集、可插拔的评分器、基于人工标注校准的裁判提示词、运行对比视图，以及能阻止回归的 CI 集成。

权衡：LLM 裁判扩展成本低但存在偏差和漂移；人工审核准确但缓慢。两者结合使用，并跟踪一致性。

扩展：具备提供商配额感知的并行运行器；缓存未变更的结果。

评测：针对平台本身的评测、裁判与人工的一致性。

安全与成本：由生产环境追踪记录构建的数据集需要进行 PII 清洗和访问控制。

45. 为用户生成内容设计一个内容审核流水线。

答案：一个分层流水线：对明显案例使用快速分类器，对边缘内容使用 LLM 进行细致的政策判断，对申诉和最困难的决策使用人工审核员。

澄清问题：内容类型（文本、图片、视频）？语言？政策类别？数量和延迟（发布前还是发布后）？下架时限的法律义务？

new content -> hash match (known bad)
                    |
   fast classifiers (per category, per lang)
       |               |               |
    clear ok      borderline       clear violation
       |               |               |
    publish     LLM + policy text    block + log
                       |
              low confidence -> human queue
                       |
     decisions + appeals -> retraining data

关键组件：哈希匹配、分类器分层、注入 LLM 提示词的政策文档、审核员控制台和申诉工作流。

权衡：发布前审核更安全但会延迟发布；阈值需要在各类别中权衡过度拦截与拦截不足。

扩展性：廉价层级承担大部分流量，因此 LLM 只处理其中一小部分。

评估：各类别的精确率和召回率、各语言的公平性、申诉推翻率。

安全与成本：审核员的心理健康和数据处理；对抗性用户会试探系统，因此要定期进行红队测试。

46. 设计一个共享护栏服务。

答案：一个供应用在模型调用前后调用的服务，用于 PII 检测与脱敏、提示注入检测、主题限制和输出策略检查，从而在各团队间保持控制的一致性。

澄清问题：是内嵌在网关中还是作为库？延迟预算？哪些策略因应用而异？支持哪些语言？

request -> input checks
           (PII redact, injection score, topic)
                 |
             model call
                 |
          output checks
   (PII, policy, schema, grounding, toxicity)
        |                  |
     pass               block / rewrite / escalate
        |
   decision log (policy version, scores)

关键组件：按应用进行策略即配置、快速检测器（正则表达式加模型）以及记录每次决策及其策略版本的日志。存在 Amazon Bedrock Guardrails 等托管方案；请查看当前功能。

权衡：更多检查会增加延迟和误报；并行运行独立检查并按风险分层。护栏能降低风险，但不能替代最小权限原则。

扩展性：无状态且水平扩展，通常与网关部署在一起。

评估：每项策略的攻击与良性测试集、误报率。参见 AI 红队测试。

安全与成本：脱敏映射本身是敏感数据；要保护好它。

47. 设计一个提示词管理与实验系统。

答案：一个注册中心，提示词像代码一样进行版本管理，与评测结果关联，通过环境部署，并通过 A/B 测试逐步上线。

澄清问题：谁编辑提示词（工程师、领域专家）？频率如何？有什么评审要求？是否必须将每个生产环境的回答追溯到某个提示词版本？

prompt edit -> registry (version, owner)
                   |
       eval suite run -> scores vs baseline
                   |
       review + approve -> staging
                   |
   canary: small share of traffic -> metrics
                   |
       promote / roll back (label "prod")

关键组件：带变量的版本化模板、环境标签、与评测运行的关联、流量切分，以及在每条追踪记录上标记提示词版本。

权衡：将提示词存储在 Git 中可获得评审和历史记录；注册中心则允许非工程师在不重新部署的情况下编辑和更改提示词。许多团队以 Git 作为唯一事实来源并进行同步。

扩展性：提示词缓存在应用中；获取失败时必须回退到最后已知的版本。

评估：未通过回归测试集不得晋升。

安全与成本：提示词变更属于生产变更；限制谁可以晋升。参见提示词工程面试题。

48. 在 Kubernetes 上设计一个自托管 LLM 推理平台。

答案：一个在内部 API 后运行开放权重模型的 GPU 服务平台，适用于数据不能离开网络、流量高且稳定，或必须服务微调模型的场景。

澄清问题： 为什么要自托管（数据驻留、成本、定制化）？模型规模多大？流量模式如何？该地区 GPU 可用性如何？团队的运维能力如何？

internal apps -> LLM gateway
                     |
   K8s (EKS / GKE / AKS) inference service
     model servers (e.g. vLLM) on GPU nodes
     continuous batching, KV cache
                     |
   autoscaler on queue depth / GPU use
                     |
   model registry -> weights (object store)
                     |
   metrics: tokens/s, TTFT, queue, GPU memory

关键组件： 支持连续批处理的推理引擎、GPU 节点池、从注册表拉取的模型权重、基于队列深度和预热容量的自动扩缩容，因为大模型的冷启动很慢。

权衡： 自托管能带来控制权，在持续高利用率下成本可能更低，但闲置 GPU 代价高昂且运维困难；量化可节省内存，但需要进行质量评估。

扩展： 按模型扩展副本数；按模型和规模进行路由。

评估： 与托管基线进行质量一致性测试、负载测试。

安全与成本： 网络隔离、模型权重的许可证审查、GPU 成本仪表盘。参见 自托管 LLM。

49. 设计一个 LLM 响应的语义缓存。

答案： 一种缓存，当新问题与之前的问题语义等价时返回已存储的答案，仅用于答案不依赖用户或快速变化数据的场景。

澄清问题： 流量的重复程度如何？答案是否个性化或依赖权限？答案需要多新鲜？

question -> normalise -> exact cache?
                             | miss
           embed -> nearest cached question
                             |
   similarity >= threshold AND same scope
   (tenant, role, source version)?
         | yes                   | no
     cached answer          full pipeline
                                 |
                       store with TTL + scope

关键组件： 精确匹配层、基于嵌入的层、按租户、权限集和索引版本划分作用域的缓存键、TTL，以及数据源变更时的失效机制。

权衡： 阈值过松会对细微差异的问题返回错误答案（“取消订单”与“取消订阅”）；阈值过严则很少命中。提供商的提示词缓存（复用静态前缀）是另一回事，是更安全的节省方式。

扩展： 向量索引加键值存储；相比主系统规模较小。

评估： 抽样审查缓存命中结果的等价性、命中率。

安全与成本： 跨权限作用域共享的缓存是数据泄露途径；必须限定作用域。关于向量索引的选择，参见 向量数据库面试题。

50. 为银行的调查团队设计一个欺诈警报叙述生成器。

答案： 当欺诈检测模型发出警报时，系统汇总交易事实和模型原因代码，然后起草一份可供调查人员使用的叙述，并在适用情况下起草一份可疑活动报告初稿，由人工最终定稿。

澄清问题： 警报量有多大？监管机构要求的报告格式是什么？模型可以看到哪些数据？叙述是影响决策还是仅用于记录？

fraud model alert + reason codes
             |
   facts builder (SQL, deterministic):
   transactions, devices, counterparties
             |
   LLM: narrative ONLY from facts JSON
        (every number referenced by ID)
             |
   validator: numbers / dates match facts
             |
   investigator edits + decides -> case system

关键组件： 确定性的事实汇总、禁止使用事实之外任何数字的提示词、对照数据源校验每个金额和日期的验证器，以及完整的案件审计。

权衡： 叙述流畅性与严格忠实性之间的取舍；应优先忠实性，固定部分使用模板。

扩展： 按警报异步处理；峰值随检测模型运行而出现。

评测： 事实一致性（自动化）、调查员修改率、合规审核员对报告的接受度。

安全与成本： LLM 从不决定是否发生欺诈；数据留在本地区域内，访问控制严格。

核心要点

  • 把最初几分钟花在澄清问题上：用户、数据、权限、答错的风险、规模和成功指标。
  • 用公式和示例数字估算 token、成本和延迟，然后指出影响它们的关键杠杆。
  • 通过评测为每个步骤选择模型，并将其隐藏在网关之后，以便随时更换。
  • 把确定性工作（算术、资格判断、权限、匹配）留在代码中；将 LLM 用于语言处理。
  • 明确划定信任边界：身份、检索内容视为不可信、工具策略以及离开组织的数据。
  • 每个设计都需要一个评测计划，包括黄金数据集、组件指标和发布门槛。
  • 高风险操作遵循提议、检查策略、批准、执行和审计的流程。

面试准备清单

  • 反复练习 Q1 的流程，直到你能在不到一小时内不看笔记完成它。
  • 准备一份可复用的估算表：每月请求数、每请求 token 数、每任务模型调用次数、成本公式。
  • 凭记忆画出五个核心设计：文档问答、支持客服 Agent、text-to-SQL、LLM 网关以及带审批的 Agent。
  • 为每个设计准备一个你能辩护五分钟的深度权衡。
  • 熟悉一款评测工具（Ragas、LangSmith 或 Langfuse）和一种追踪方法（OpenTelemetry），达到能描述真实部署方案的程度。
  • 排练故障模式的回答：供应商宕机、提示词注入、索引过期、Agent 死循环、成本激增。
  • 至少完整构建一个设计，并准备好解释哪里出了问题以及你做了哪些改动。
  • 进行一次模拟面试，让某人扮演持怀疑态度的利益相关者，询问风险和成本。

常见问题

什么是 AI 系统设计面试？

它是一种面试环节，要求你设计一个完整的 AI 驱动系统，例如 RAG 助手或 AI Agent，涵盖需求、架构、模型、评测、故障处理、安全和成本，而不仅仅是写代码或解释概念。

AI 系统设计与传统系统设计有何不同？

传统设计关注吞吐量、存储和一致性。AI 系统设计增加了非确定性输出、基于 token 的成本和延迟、检索质量、评测、提示词注入和人工审核，同时仍然需要经典的分布式系统基础知识。

哪些岗位会有 AI 系统设计环节？

高级 AI 工程师、GenAI 开发者、AI 架构师、ML 平台工程师和前沿部署工程师通常会面对这类面试。初级岗位可能会遇到较轻量的版本，聚焦于单一的 RAG 或聊天机器人设计。

我该如何准备 GenAI 系统设计面试？

学习一套可复用的方法，用示例数字练习估算，记住几个核心架构，至少端到端构建一个系统，并进行限时模拟面试，在面试中口头解释权衡取舍。

AI 系统设计需要了解特定的云服务吗？

熟悉一个云平台会有帮助，例如搭配 Amazon Bedrock 的 AWS 或搭配 Azure OpenAI 的 Azure，但面试官主要考察的是概念：网关、检索、身份认证、队列、评测和可观测性。只有在确信某项服务适用时才提及具体服务名称。

面试中我应该给出确切的 token 价格吗？

不需要。价格经常变动。展示成本公式，使用明确标注为示例的数字，并解释可调节的杠杆，例如更小的模型、缓存、更短的上下文和批处理。

AI 系统设计环节涉及多少编程？

设计环节本身通常很少或没有编程，但可能会要求你勾画一个 API、一个工具 schema 或一个提示词结构。同一流程中的其他环节通常会考察 Python 编程。

LLM 系统设计面试中最常见的错误是什么？

在弄清用户、数据、权限和成功指标之前，就直接跳到向量数据库和 Agent 框架。第二常见的错误是没有评测计划。

DevOps 或云工程师能在 AI 系统设计面试中表现出色吗？

可以。基础设施、身份认证、可靠性和成本方面的技能可以直接迁移。通过构建几个真实项目来补充 RAG、Agent、评测和防护栏的知识，你将拥有许多专注模型的候选人所不具备的优势。
