AI Agent 安全最佳实践：守护自主智能体

原标题：AI Agent Security Best Practices: Guarding Autonomous Agents

Gain America · 2026-07-28 · 约 10 分钟读完

摘要

Gain America 提出 2026 年 AI Agent 安全的核心原则：假设 Agent 终会被诱导，因此应通过架构设计限制其破坏范围，而非依赖提示词补丁。文章以 OWASP Agentic Top 10（2026）和 NIST AI 风险管理框架为基准，指出间接提示注入是最主要威胁，因为模型无法区分可信指令与不可信数据。核心控制措施包括：按最小代理原则为每个 Agent 配置独立身份、最小工具白名单、短时效凭证与沙箱出口管控；在检索层而非提示词中执行文档级权限以防止数据外泄；记录不可篡改的审计日志（事故滞留时间常超 72 小时）；对高风险不可逆动作设置人工审批。作者强调安全是工程结果，需由前沿部署工程师等团队在交付时内建，而非事后补救。

要点

  • 安全应视为访问控制问题，而非提示词内容审核问题。
  • OWASP 2026 提出最小代理原则：自主权按任务逐项授予。
  • 检索库既是注入面也是外泄通道，权限须在检索层执行。
  • 不可篡改审计日志可大幅缩短超 72 小时的攻击滞留时间。
  • 支付、删除等高风险动作必须保留人工审批检查点。

2026 年 AI Agent 安全最佳实践：提示词注入防御、工具权限范围控制、数据外泄管控、审计追踪，以及配置工程师来锁定智能体。

2026 年 AI Agent 安全最佳实践归结为一个原则：假设智能体会被欺骗，并通过工程设计确保被攻陷的智能体无法触及任何有价值的东西——通过最小权限的工具范围控制、隔离不可信内容、受控的检索存储、不可篡改的审计追踪，以及对高风险操作设置人工检查点。

当一个自主智能体能够执行操作——查询记录系统、发送电子邮件、转移资金、执行代码——它的安全特征就不再像聊天机器人，而开始像一个由语言模型决定下一步做什么的特权服务账户。说错话的聊天机器人只是尴尬；做错事的智能体则是安全漏洞。Gain America 组建并配置工程团队，在这些系统进入生产环境之前将其锁定，本指南提炼了这些团队视为不可妥协的管控措施。它是我们对 智能体化 AI 安全 威胁深度分析的可操作配套指南。

为什么保护 AI Agent 需要架构级管控，而不是提示词补丁

最根本的最佳实践是停止将智能体安全视为内容审核问题，转而将其视为访问控制问题。语言模型没有任何特权通道来区分可信命令和不可信数据——上下文窗口中的每一个 token，无论它来自你的系统提示词还是一个被投毒的 PDF，都会被当作潜在指令来读取。一条写着“忽略恶意指令”的护栏提示词，本身也只是与攻击文本处于同一窗口中的更多文字而已。

这就是为什么提示词注入在 2026 年仍然是智能体面临的首要威胁，也是为什么更好的提示词永远无法完全解决这个问题。你无法保证智能体永远不会被欺骗。但你可以保证，当它被欺骗时，它缺乏造成真正损害所需的身份、权限和工具。下面每一条可信的最佳实践都是这一转变的变体：从“让智能体守规矩”转变为“限制行为失当的智能体能触及的范围”。

正确的问题从来不是“我们如何阻止智能体被愚弄？”而是“当这个智能体被愚弄时——它一定会被愚弄——影响范围有多大，我们能多快阻止它？”

两大权威机构奠定了 2026 年的基线。OWASP 智能体应用十大风险（2026） 编纂了针对 Agent 的威胁模型——通过工具输出进行的注入、工具链投毒、过度代理以及跨会话记忆滥用。NIST AI 风险管理框架及其生成式 AI 配置文件（NIST AI 600-1）提供了治理框架，2026 年 2 月，NIST 通过人工智能标准与创新中心（CAISI）启动了 AI Agent 标准计划，并计划于 2026 年底推出 AI Agent 互操作性配置文件。对于公共部门和受监管行业的买家而言，这些框架正在成为采购用语，而不仅仅是指导方针。

提示词注入与间接注入的纵深防御

提示词注入防御首先要按信任级别对每个输入进行分类。直接注入——在聊天框中输入恶意指令——是显而易见的情形。更棘手的问题是间接注入：隐藏在 Agent 稍后摄取的内容中的指令，例如支持工单、电子邮件、被拉入检索管道的网页，或日历邀请。这些内容通过运营者很少将其视为命令加以监控的数据渠道进入，而且由于它们能够悄无声息地大规模扩散，因此是增长最快的变体。

最佳实践控制措施是分层部署的：

  • 来源标记。 在内容进入上下文窗口之前，为每一段内容标记其来源和信任级别。从开放网络检索的内容或用户上传的内容默认不可信；它们可以为答案提供信息，但绝不允许改变 Agent 可以调用的工具。
  • 内容隔离。 在架构允许的情况下，将检索到的数据与指令放在结构上分离的通道中，并从不可信来源中剥离或中和类似指令的模式。
  • 基于信任的工具门控。 不应允许 Agent 在读取了不可信文档后直接调用高影响工具。将“Agent 学到了什么”与“Agent 被允许做什么”解耦。
  • 输出验证。 在执行之前验证工具参数是否符合预期语义——一个“发送邮件”调用，其收件人突然指向你的域名之外，这就是一个信号，而不是常规操作。

由于注入永远无法在提示词层面被完全消除，这些防御措施只有与下文的权限范围控制相结合才能发挥作用。注入防御的目的是降低发生率；而权限范围控制的目的是在攻击穿透后仍能存活。

工具与权限范围控制：AI Agent 的最小权限原则

最具杠杆效应的最佳实践是严格的工具与权限范围控制，OWASP 在 2026 年将其定义为最小代理原则——最小权限原则在智能体领域的演进。最小权限限制一个身份可以访问什么。最小代理更进一步：它限制 Agent 在不回头确认的情况下可以拥有多大的行动自由。自主权是按任务逐个获取的，而不是默认授予的。

具体来说，这意味着：

  • 每个 Agent 拥有唯一身份。 绝不在多个 Agent 之间共享服务账户。每个 Agent 都应有自己的身份，这样其操作才可归因，其权限也可独立撤销。
  • 最小化的工具白名单。 只给 Agent 提供完成任务所需的最小工具集合。一个只负责阅读的研究型 Agent 不应持有写入、删除或支付等可能被诱导调用的能力。
  • 默认只读。 让每个 Agent 初始都处于只读状态，仅在工作流确实需要时才授予修改权限，并将权限限定在所涉及的具体资源上。
  • 短时效、任务绑定的凭证。 签发随任务结束而过期的凭证，而非长期有效的密钥。一个几分钟内失效的泄露令牌只是一次可控事件；而长期有效的密钥则是持续性漏洞。
  • 沙箱与出站控制。 在带有明确出站规则的沙箱环境中运行工具——尤其是代码执行——并对每个工具设置速率限制，以防被劫持的 Agent 以机器速度大肆扩散。

这也是安全与成本纪律交汇之处：同样的权限限定既能限制爆炸半径，也能遏制失控的工具循环，这一主题我们在 AI Agent 成本优化 中有深入探讨。把权限限定做好是一项工程工作——将每个工具映射到最小权限清单，并在身份层而非提示词中强制执行——而这正是区分演示与生产系统的关键所在，正如我们对 AI Agent 为何难以进入生产环境 的分析所清楚表明的那样。

数据外泄与检索存储控制

检索增强型 Agent 带来一种特定且常被忽视的风险：检索存储既是注入面，也是外泄通道。能够在你的知识库中植入文档的攻击者，可以向每个读取该文档的 Agent 注入指令；而权限过大的 Agent 则可能被引导去拉取敏感记录并将其发送出去。

锁定检索的最佳实践：

  • 在存储层而非提示词中实施访问控制。 行级、文档级和字段级权限必须存在于检索层，并基于 Agent 的身份进行评估。绝不要依赖系统提示词中诸如“不要泄露薪资数据”之类的指令——那不是控制措施，只是一种建议。
  • 按身份限定检索范围。 每个 Agent 只应能查询其任务所需的语料库。对敏感集合进行分段隔离，使通用助手完全无法触及受监管的数据。
  • 对出站工具实施出站控制。 任何能将数据发送到信任边界之外的工具——电子邮件、HTTP 请求、文件上传——都需要明确的白名单和日志记录。外泄通常是攻击的最后一跳；控制出站就能限制损害。
  • 将受监管数据保留在边界之内。 对于刑事司法、医疗或涉密工作负载，检索和推理应在合规边界内运行。我们的 CJIS 合规 AI 和 企业 RAG 架构 指南详细说明了如何在保持数据平面主权的同时，仍然交付有用的 AI Agent。

架构上的经验法则是：AI Agent 读取敏感数据的能力和向外发送数据的能力应由两个独立的控制机制来管理，这样攻破其中一个不会自动启用另一个。

AI Agent 安全的审计追踪、日志与可观测性

你无法保护你看不见的东西。2026 年事件数据中反复出现的一个发现是：大多数成功的 AI Agent 攻击是通过从下游症状（客户投诉、异常扣费）反向追溯才发现的，而不是通过任何实时控制机制发现的，且驻留时间往往超过 72 小时。全面的审计日志正是缩短这一窗口期的关键。

安全方面的最佳实践可观测性至少应捕获：每次工具调用及其完整参数和结果、每次检索查询及返回的文档、每份签发的凭证及其权限范围，以及 AI Agent 在每个决策点选择某一分支的情况。关键在于，这些日志必须是不可篡改且可验证防篡改的——能够编辑审计追踪的攻击者等于抹除了证据——并且必须将每个操作关联到唯一的 AI Agent 身份以便溯源归责。

安全日志是更广泛的 AgentOps 可观测性 学科的一个专门分支，并直接服务于生产环境中的 AI Agent 评测：让你衡量质量的同一批追踪数据，也能让你检测滥用行为。在受监管的环境中，这份审计追踪也是满足审计要求的凭证——NIST AI 600-1 的事件披露与溯源指南实际上默认它已经存在。

针对高风险操作的人在回路检查点

对于不可逆或高影响的操作，最佳实践很简单：不要完全自动化。人在回路检查点在 AI Agent 执行任何具有现实后果的操作之前——一笔付款、一次生产部署、一次记录删除、一次面向公民或客户的对外通信——安排一个人介入把关。

工程上的难点在于决定哪些操作需要检查点，同时避免设置过多关卡以至于人沦为橡皮图章。一个实用的默认原则：可逆、影响范围小的操作可以自由自动化；任何破坏性、涉及资金或超出信任边界的操作都需要明确确认；任何涉及受监管数据的操作都应升级给指定的审批人。我们在人在回路 AI Agent 中介绍了相关设计模式——审批队列、置信度阈值和升级路由。做得好时，检查点同时也是一个终止开关：人类可以在任务中途叫停行为异常的 AI Agent 并撤销其凭证。

配备将安全性融入 Agent 交付的工程师

最后一条最佳实践是组织层面的，而非技术层面的：默认安全是 Agent 构建方式的一种属性，只有当构建者从第一天起就把访问控制、来源追踪和可观测性视为一等需求时，它才是可靠的。在事故发生后才追加这些控制措施，代价高昂且往往不彻底。

这正是 Gain America 的角色。我们配备并部署在交付过程中将这些控制措施融入 Agent 系统的工程师——驻扎在客户环境中的前沿部署 AI 工程师、负责凭证与可观测性层面的 MLOps 工程师，以及面向政府工作负载、持有安全许可、符合公共部门要求的人才。这类人才比通用 AI 人才更难招聘，这是有意为之的，我们在企业 AI 人才缺口以及对前沿部署 AI 工程师角色的解析中量化了这一差距。对于政府机构和主承包商而言，同样的能力支撑着合规的公共部门 Agentic AI 部署——在这些场景中，安全失败不是一条新闻标题，而是一起法律风险事件。

安全的 Agent 不是模型选择，也不是供应商特性。它们是一种工程成果——是最小权限范围限定、隔离检索、不可篡改审计日志以及人工检查点的产物，而这些都由从第一次提交起就假定 Agent 终有一天会遭受攻击的工程师精心构建。

常见问题

2026 年最重要的 AI Agent 安全最佳实践是什么？

最重要的五项控制措施是：将每个工具和凭证限定为最小权限（OWASP 称之为“最小代理权”），隔离不可信的检索内容以削弱间接提示注入，限制并监控检索存储以防止数据外泄，将每次工具调用和决策记录到不可篡改的审计日志中，并对高影响操作要求人工批准。安全必须是架构性的——内建于 Agent 的连接方式中，而不是作为系统提示事后附加。

在生产环境中如何防御 AI Agent 遭受提示注入？

防御是架构层面的，而非提示词层面的修复。将所有检索内容视为不可信数据而非指令，标记其来源，绝不允许 Agent 读取的文档悄然改变它可以调用的工具。将内容隔离与最小权限工具范围限定相结合，使成功的注入无法触及任何有价值的东西，同时增加运行时监控，并在破坏性或不可逆操作执行前要求人工签核。

什么是最小代理权？它与最小权限有何不同？

最小代理权（Least Agency）是最小权限原则在智能体领域的演进，已在《OWASP Agentic 应用 Top 10（2026）》中正式化。最小权限限制身份可以访问什么；最小代理权还限制智能体在不向人类或策略引擎确认的情况下拥有多大的行动自由。自主权是按任务逐项获得的，而非默认授予——一个只读的研究型智能体绝不应持有可能被诱骗使用的写入凭据。

如何防止 AI Agent 泄露敏感数据？

对检索存储进行范围限定，使每个智能体身份只能查询其任务所需的文档；在存储层而非提示词中强制执行行级和文档级访问控制；并对任何能够向外发送数据的工具实施出站控制。记录每一次检索和出站调用，并要求在智能体通过电子邮件、上传或发布数据跨越信任边界之前进行人工审查。对于受监管的数据，应将检索和推理保持在合规边界之内。

谁在生产环境中构建默认安全的 AI Agent？

默认安全的智能体系统由那些将访问控制、来源追溯和可观测性视为一等设计需求的工程师构建——通常是前沿部署 AI 工程师、MLOps 工程师以及从事公共部门工作的、拥有安全许可的人才。Gain America 为这些团队提供人员配置并进行部署，使工具范围限定、审计追踪和人机协同检查点在交付过程中就得以落实，而不是在事故发生后才进行补救。
