摘要

这篇文章是 pathtofde.com 的 FDE 系统设计与集成面试题库，共 32 题，分为数据管道、API 集成、AI 系统与部署运维四组。核心观点是：FDE 面试考察的不是画出漂亮的架构图，而是在真实客户约束下（模式漂移、限流、遗留系统、不可靠数据）识别故障模式并权衡取舍的能力。每题附有“优秀答案长什么样”的提示，供练习者自评。

要点

  • 题库共 32 题，覆盖数据管道、API 集成、AI 系统与部署运维四组。
  • 核心原则：为客户现实设计，而非为白板设计。
  • 评分关键是说出故障模式、权衡取舍与度量方式。
  • 建议练习法：口头作答、三轴自评、复答并向非技术人员讲解。
  • 题目基于真实课程内容，不含技巧题或编造数据。

虚构的典型形象，源自常见模式，并非真实的人物或公司。

FDE 岗位的系统设计面试并不是架构审美竞赛。它们是对这份工作的模拟：有人交给你一个混乱的客户、一个不可靠的遗留系统和一个截止日期——然后问你会如何构建一个能在现实冲击下依然运转的东西。

一位虚构物流公司的虚构招聘经理主持白板环节。“请讲讲你会如何为我们的货运清单设计一个数据接入管道，”她说。候选人画了三个完美的方框——S3、Lambda、Postgres——然后停了下来。一片沉默。

“开局不错，”她说。“现在：承运商每季度发来的 CSV 都会多一个新列，他们的 SFTP 服务器动不动就宕机好几天，而且仓库团队不信任你的数字，因为上个季度有一个仪表盘把 40,000 个集装箱重复计算了。重新设计吧。”

第二个问题——而不是第一个——才是 FDE 面试。方框从来都不是考察点，故障模式才是。本题库中的每个问题都是同样的套路：一个看似合理的设计题目，而其背后，是前沿部署工程师必须应对的混乱现实。

FDE 系统设计的独特之处

在后端工程面试中，“设计一个 URL 短链接服务”考察的是清晰的组件划分和复杂度思维。而在 FDE 面试中，你是在为特定客户的现实做设计，而且面试官会不断变换条件：数据结构变了，第三方 API 有每分钟 10 次请求的配额限制，数据负责人不肯给你生产环境凭证，审批流程要求任何东西执行之前都必须有人工签字。

这就引出了本题库中最重要的得分杠杆：

核心原则

为客户的现实而设计，而不是为白板而设计。

一个指出了三种故障模式和两个面向客户权衡的设计，胜过一个假设输入行为良好的完美架构。要大声说出来：“这里会出什么问题，我会度量什么，如果我们选择这条路，客户要放弃什么。”这就是 FDE 思考时的声音。

如何使用本题库

题库共有四个分组、32 道题：数据管道、API 集成、AI 系统和部署与运维。每个分组开头都列出了需要先学习的已发布课程，然后是带编号的问题，并附有“优秀答案长什么样”的提示——用一两句话描述一个出色的答案应展现出什么，方便你练习和自评。

一个适用于这些题目的有效练习循环：

  • 大声回答，像在白板前讲解一样，持续 5 分钟 —— 不要只是读提示。要锻炼的是在轻度压力下进行结构化的口头推理能力。
  • 然后阅读提示，并从三个维度给自己评分：你是否指出了失败模式？你是否指出了权衡取舍？你是否说明了你会衡量什么？
  • 结合你遗漏的内容再回答一次。 学习就发生在第二轮。
  • 最后向一个非技术人员解释你的答案 —— 伴侣、朋友，甚至用平实的语言写进自己的笔记。前沿部署工程师要把设计方案“卖”给运营人员和高管，而不仅仅是工程师。

本题库不会做的事

  • 没有刁钻的陷阱题，没有冷门知识题（“说出五种 HTTP 方法”）—— 每道题都是一场带有真实世界混乱因素的设计对话。
  • 不声称某个答案就是唯一正确的设计。系统设计只有权衡取舍，没有标准答案；提示描述的是一个优秀答案应展现什么，而不是一份需要背诵的逐字稿。
  • 不编造统计数据（“87% 的 FDE 面试会问 Kafka”）。以下所有内容都基于你可以在本站学习的真实课程。

第 1 组 —— 数据管道

先学习这些课程

本组的所有内容都基于真实的 Milestone 2 数据接入管道：

Q1.1 —— 为第三方承运商每周投放的 CSV 文件设计一条接入管道

某客户每周一早上 6 点通过 SFTP 从承运商接收 CSV 清单文件。请勾勒出从文件投放到数据可查询的整条管道。然后思考：承运商的服务器偶尔会连续几天无法访问，而且他们的文件在不同周会使用不同的编码。这会带来什么改变？

优秀答案的样子：一条将文件落地与解析分开的管道（原始区 vs. 校验区），在获取步骤上具备重试和检查点机制，并在校验之前进行编码探测或归一化 —— 此外还要明确回答：当周五的文件迟到三天才到达时，周一的报告该怎么办。

Q1.2 —— 模式发生漂移

你的管道已经运行了六个月，此时承运商新增了一个列，重命名了两个现有列，并且偶尔发送带有额外字段的行。你的下游仪表盘悄无声息地坏了 —— 没有报错，只是数字不对。你如何设计管道，使模式变更能被检测到，而不是被悄悄吸收？

优秀答案的样子：在边界处进行严格校验（一个 Pydantic 风格的模式，默认拒绝未知或重命名的字段），为每个批次记录模式版本日志，在数据到达仪表盘之前对新出现或缺失的列发出告警，并为不符合规范的批次设置隔离路径，而不是尽力猜测。

Q1.3 —— 对账：证明数字是正确的

客户的仓库团队不信任你的数据管道的汇总数字，因为一个旧脚本曾经把 40,000 个集装箱重复计算了一次。请设计一个对账机制，让操作员在任何一天都能验证：进入管道的数据量与仪表盘显示的数据量是一致的。你会存储什么数据？存储在哪里？

优秀答案的样子：在管道的每个阶段捕获行数和校验和（或每批次摘要），生成一份对账报告，比较落地数、验证数与加载数，并且当数字不一致时，能清晰说明记录在哪里出现了分歧——机制本身比具体选用哪种哈希算法更重要。

Q1.4 — 死信队列：出问题的数据去哪里

为你的数据接入管道设计死信路径：验证失败的行、解析失败的文件、无法对账的批次。每条死信记录应携带哪些信息？操作员如何调查并重新处理它？以及——关键的一点——如何防止单条格式错误的行阻塞整个周一的批次？

优秀答案的样子：在行粒度（而非批次粒度）上隔离“毒”记录，每条记录携带原始载荷、验证错误和批次血缘；提供“修复并重放”的操作员工作流；并制定一条规则，规定死信记录何时应升级给数据负责人，而不是无限重试。

Q1.5 — 调度：cron、队列，还是事件驱动？

在同一个项目中，你有三种数据接入模式：(a) 每周一次的承运商 CSV 投放，(b) 必须每 15 分钟轮询一次的承运商 API，(c) 通过上传门户在不可预测的时间到达的舱单。请比较你会如何为每种模式安排调度，并为你的选择辩护。然后是转折：客户问“如果调度器本身在周末静默失效了，会发生什么？”

优秀答案的样子：针对不同模式采用不同的触发方式（每周投放用 cron，15 分钟一次的 API 用轮询循环或轻量级调度器，不可预测的到达用事件驱动），每种方式都具备幂等处理，确保重跑是安全的——此外还要有心跳监控或看门狗，当计划中的运行没有发生时通知相关人员。

Q1.6 — 迟到数据和乱序数据

你的管道为客户 KPI 仪表盘计算“每周出货量”。承运商文件经常迟到——第 12 周的舱单在第 14 周才到达。请设计管道和数据仓库表，使迟到数据能够修正历史，同时不会以任何人都无法审计的方式重写过去。你会如何向仓库经理解释这一点？

优秀答案的样子：将事件时间与处理时间分离，制定明确的重述或修正策略（追加修正记录，而不是静默更新行），并提供人类可读的解释：“你的第 12 周数字发生了变化，因为迟到的舱单到达了；这里是确切记录了哪些行发生了变化以及原因的审计轨迹。”

Q1.7 — 恰好一次、至少一次，以及介于两者之间的谎言

面试官说：“设计一个实现恰好一次处理的管道。”该管道将货运记录写入 Postgres，并向下游队列发送事件。重复数据可能在哪里产生？哪些机制能让你最接近恰好一次——或者让你确信“至少一次加幂等性”才是诚实的答案？

优秀回答的样子：指出重复数据的来源（重试的抓取、重放的批次、写入与检查点之间发生的崩溃），然后区分恰好一次投递、恰好一次处理和业务效果上的实际一次。默认情况下，Postgres 写入加上单独的队列发布并不是原子操作——事务性发件箱（transactional outbox）配合幂等消费者才是务实的答案，但要精确地陈述保证：重复数据可能会到达，但因为消费者是幂等的，所以它们是无害的。

Q1.8 — 数据回填：重建六个月的历史数据

客户已经确认了新的、更严格的模式。他们现在希望将过去六个月的原始承运商文件通过新管道重新处理。请设计回填方案：如何在不干扰每周实时管道的情况下运行回填，如何验证回填的数据，以及当回填产生的总数与客户已经向董事会报告的数字不一致时，你会怎么做？

优秀回答的样子：回填针对原始存档运行（证明原始数据区的价值），与实时路径隔离并拥有自己的输出用于对比，在新旧总数之间进行对账，并为差异制定沟通计划——FDE 的做法是把与董事会数字不一致的问题当作一次客户沟通，而不仅仅是一个数据缺陷。

第 2 组 — API 集成

先学习这些课程

本组内容基于第 3 阶段的真实经验教训——与你无法控制的系统集成时的混乱现实：

Q2.1 — 与没有 API 的遗留系统集成

客户的仓库管理系统是一个有二十年历史的本地部署应用：没有 API，每晚将 CSV 导出到共享文件夹，还有一个供应商警告你不要直接查询的“数据库”。请设计将此数据接入你的现代管道的集成方案。你计划应对的最奇怪的约束是什么？

优秀回答的样子：把 CSV 导出（或读取副本 / CDC 式捕获）作为集成接缝，而不是与供应商对抗；使用校验和与行数来检测被截断的导出；为导出格式在毫无通知的情况下发生变化做好准备；并诚实地列出你无法做到的事情（实时读取、反向写入），提前告知客户。

Q2.2 — 大规模分页

你需要从一个供应商 API 拉取 200 万条工单记录，该 API 每页分页 100 条记录，并使用基于游标的分页。面试官补充道：数据集在你分页的过程中会发生变化，而且供应商的游标在 10 分钟后过期。请设计提取方案，并解释在这里“正确性”意味着什么。

优秀答案的样子：先弄清供应商的游标语义——过期的游标可能根本无法续传，存储它毫无意义。考虑按 ID 或时间范围进行稳定分区、快照/导出 API、可续传的高水位标记，以及跨分区的对账。做好吞吐量计算（无论并发多高，20,000 页都有一个下限）。如果不存在一致的原语，就明确说出来：“用这个 API 无法实现有保证的时间点快照——这是可审计的尽力而为方案及其偏差范围。”

Q2.3 — 速率限制：每分钟 10 次请求

某承运商的追踪 API 允许每个 API 密钥每分钟 10 次请求，而你需要为 5,000 个活跃货件获取最新状态。请设计轮询策略。然后是转折：客户要求在他们的客户门户上实现“实时”追踪。你会怎么告诉他们？

优秀答案的样子：请求预算管理（按状态波动性对货件排定优先级）、带明确过期容忍度的缓存、达到限额时的退避与排队，以及与客户坦诚沟通——把每分钟 10 次请求转化为“您的门户每 N 分钟刷新一次”，并提出 webhook 或事件驱动的替代方案作为实现“实时”的真正解决办法。

Q2.4 — 不让情况变得更糟的重试

你的集成向客户的旧系统端点 POST 送达确认，该端点会间歇性超时，偶尔还会把同一请求处理两次。请设计重试策略。重试这个端点与重试幂等的 GET 有什么区别——你如何让这个 POST 可以安全重试？

优秀答案的样子：带抖动的指数退避、有上限的重试预算、由你的应用生成幂等键以便接收方去重，以及一条清晰的界线：对 GET 的重试是无害的，对 POST 的重试则需要幂等键加上验证（写后读）才能假定成功——并在重试耗尽时提供死信路径。

Q2.5 — 设计 webhook 接收器

承运商现在为货件状态变更提供 webhook。请设计你的接收器：验证、排序、重复和停机处理。然后是转折：在演示过程中，一分钟内涌入了 10,000 个 webhook，你的处理器崩溃了。哪里出了问题，如何在丢失事件的情况下修复它？

优秀答案的样子：验证 → 持久化 → 确认 → 处理 → 对账。对每个事件进行签名验证；只有在事件被持久接受（持久队列或收件箱表）之后才返回 200——在持久化之前返回 200 就等于埋下一个丢失事件的隐患。事件时间戳不能确定顺序——应使用供应商的序列号、实体版本或权威状态查询。按事件 ID 进行幂等处理，并为停机窗口提供重放/对账机制。应对突发流量的修复方案是架构层面的（队列 + 工作进程），而不是更大的服务器。

Q2.6 — 真实环境中的认证

你要集成三个客户系统：一个使用 OAuth 2.0 客户端凭证，一个使用由人工每季度轮换的长期 API 密钥，还有一个使用证书每年到期的双向 TLS。请为你的部署设计凭证管理：密钥存放在哪里、轮换如何进行、以及凌晨 2 点证书到期时会出现什么故障。然后：客户的安全团队问，你如何证明凭证从未出现在日志中。

优秀答案的样子：密钥存放在正规的密钥管理系统中（绝不放在仓库的环境变量文件里，也绝不写进日志），针对每种机制制定轮换流程并配备日历或自动化触发器，对到期情况进行监控并提前数周发出告警，同时进行日志脱敏并制定可审查的凭证处理策略——凌晨 2 点的答案是“我们在证书到期前就会收到告警，而且轮换操作手册经过测试。”

Q2.7 — 在约束条件下设计：48 小时集成

客户最大的客户要求在本周末之前在他们的门户中看到 EDI 风格的货运数据。你只有 48 小时，无法访问客户的生产网络（VPN 审批需要两周），唯一的文档是一份 2019 年的 200 页 PDF。请勾勒你的计划。你刻意排除哪些内容，又如何表达这一点？

优秀答案的样子：毫不留情地划定范围——一个最小可行集成（一种货运类型、一个方向的数据流，在无法实现自动化的地方记录手动步骤），使用本地 mock 或录制的测试数据在没有生产环境访问权限的情况下开发，尽早明确传达“不在范围内”的清单，并为第二周制定加固计划。这里考察的 FDE 技能是友善且尽早地对范围说“不”。

Q2.8 — 调试别人的 API

你的集成在测试中运行正常，但在客户的预发布环境中失败，返回一个通用的 400 错误且没有任何有用的错误信息。供应商的支持团队说“我们这边没问题”。请讲述你的调试方法：你捕获什么、对比什么，以及在没有供应商服务器访问权限的情况下如何证明故障出在哪里？

优秀答案的样子：捕获完整的请求/响应对（头部、正文、时序），对比正常环境与故障环境之间的确切字节差异，在应用代码之外用最小化请求复现问题，并构建一份证据包（时间戳、请求 ID、关联信息）让供应商能够复现——采用系统性的排除法而非猜测，且在没有证据的情况下绝不指责供应商。

第 3 组 — AI 系统

先学习这些课程

本组内容基于真实的 Stage 4 课程——构建 Ask CityOps RAG 系统并证明其有效：

Q3.1 — 为 50,000 份内部运营文档设计 RAG 系统

客户希望操作员能够对 50,000 份内部 SOP、事故报告和政策 PDF 进行自然语言提问。请勾勒架构：摄取、分块、检索、生成。然后是转折：一半的 PDF 是扫描图像，而且运营团队每周更新 SOP。什么会最先出问题？

优秀答案的样子：一个包含 OCR 处理扫描件的摄取管道、与文档结构挂钩的分块策略（而不是对所有内容都用固定大小）、使用固定版本模型的嵌入、对精确事实使用精确过滤器的检索，以及一套更新策略（对增量重新索引、文档版本化）——此外还要指出第一个失败点：过时的 SOP 被当作当前答案返回，通过文档版本化和检索中的新鲜度元数据来解决。

Q3.2 —— 先保证检索质量，再玩提示词技巧

你的 RAG 系统的答案以一种特定的方式出错：流畅、自信，并且引用的文档并不支持其论断。团队想“改进提示词”。你怀疑是检索的问题。你如何诊断问题出在检索、生成还是评测上——以及你首先会改变什么？

优秀答案的样子：对管道进行插桩以检查每个查询检索到的分块（将“存在引用”与“引用支持”区分开），用已知的问题-文档配对单独测试检索，并在动提示词之前先修复检索质量（分块、过滤器、排序）——这是课程中的原则：检索质量优先于提示词技巧。

Q3.3 —— 评测：证明 AI 变得更好了

客户问：“我们怎么知道新版助手确实比旧版更好？”设计评测方案：用什么数据集、什么评分标准、什么流程。然后是转折：产品团队在同一个版本中同时更改了系统提示词和评测集。为什么这是个问题？今后你如何修正流程？

优秀答案的样子：一个由有代表性的真实问题组成的版本化评测集、一个定义正确性的评分细则以及将其落地的评分器，还有对系统、评测集和评分逻辑分别独立进行版本管理的纪律——因为如果两者同时更改，你就无法判断是产品变了还是测试变了。

Q3.4 —— 防护栏：AI 不能失控

你的助手可以查询货运记录并起草面向客户的物流状态邮件。客户担心它可能把一个客户的数据泄露给另一个客户，或者发送一封带有编造交付日期的邮件。设计防护栏架构：在模型周围部署什么、部署在哪里，以及防护栏触发时会发生什么？

优秀答案的样子：控制措施围绕模型部署，而不是写进提示词里——在检索和工具执行之前强制执行租户授权；租户隔离的检索；对关键字段进行基于证据的校验（交付日期要与数据源核对，而不是与文字表述核对）；明确的“草稿与发送”边界（起草邮件是可逆的，发送邮件则不可逆——发送需经人工审批把关）；防范检索文档中的提示词注入；以及不会自身泄露敏感数据的审计记录。还要区分“存在引用”与“引用支持”——被引用的文档并不能证明它 supposedly 支持的论断。

Q3.5 —— 对 Agent 行为的人工审批

客户希望助手不仅能回答问题，还能执行操作：重新安排配送、发放补偿金、更新货运记录。请设计审批工作流。“授权”（“这个来电者可以操作吗？”）与“审批”（“是否有真人批准了这个具体操作？”）有什么区别——你如何同时实现两者？

优秀答案的样子：将两个概念区分开——授权检查来电者对资源的权限，审批要求真人在执行前对确切操作的不可变快照（参数冻结、原样展示）进行签核；审批记录存储在 Agent 无法改写的地方；幂等执行，确保被双重批准的操作不会重复触发；以及干跑预览，让审批者看到的是后果，而不仅仅是参数。

Q3.6 — 成本与延迟的权衡

你的 RAG 助手每次查询成本约为 $0.08，端到端耗时 6 秒。客户希望在向所有操作员进行 10 倍规模推广时，成本降到 $0.02 以下、耗时 2 秒以内。请梳理你会动用的优化手段、每种手段牺牲了什么，以及你如何做决策——不要凭空猜测你没有测量过的数字。

优秀答案的样子：说出真实的优化手段（用更小/更快的模型生成草稿、用更大的模型做验证、缓存高频查询、精简检索上下文、用流式输出降低感知延迟、更便宜的嵌入模型、在隐私允许时使用本地推理），并诚实地说明每种手段在质量或复杂度上的代价——并且在用客户自己的评测集测量质量影响之前，拒绝承诺达成目标。

Q3.7 — 真正可信的结构化输出

助手必须从事故报告中提取结构化字段（事故 ID、严重程度、受影响系统、时间线），写入客户的工单系统。自由文本提取会产生幻觉字段。请设计提取方案，使输出可被机器消费：模式（schema）、校验，以及模型无法填写必填字段时的处理方式。

优秀答案的样子：模式约束生成（模型必须符合声明的 schema）、对每个输出进行服务端校验（Pydantic 风格——schema 证明的是形状，不是真实性）、对缺失字段的显式处理（用 null 加原因，而不是编造值），以及对低置信度提取结果路由到人工审核——校验和真实性是两个独立的问题，设计要这样对待它们。

Q3.8 — 模型在你不知情的情况下变了

某个周二早晨，你的助手回答质量下降了。你的代码没有任何改动——但 API 供应商在夜间发布了新的默认模型版本。请设计本可以在客户察觉之前发现这一问题的部署标识与变更管理实践。你会固定（pin）什么、监控什么、回滚方案是什么？

优秀答案的样子：锁定确切的模型版本（而不是“latest”），记录完整的部署标识（模型工件/版本、服务配置、提示词版本、评测集版本），在实时评测切片上监控回答质量（而不仅仅是正常运行时间），对模型变更进行金丝雀或分阶段发布，以及能在几分钟内恢复到之前锁定配置的回滚机制——经验教训：“锁定确切标签”只是部署标识的开始，而不是终点。

第 4 组 — 部署与运维

先学习这些课程

本组内容基于真实的第 5 阶段课程——在企业的各种约束下将 CityOps 投入生产运行：

Q4.1 — 为整个 CityOps 技术栈使用 Docker Compose

为一个包含 FastAPI 服务、Postgres 数据库、Redis 队列、RAG worker 和运维人员控制台前端的技术栈设计本地与预发布环境部署。一个

docker compose up

就能让这一切运行起来。然后是转折：客户的安全团队规定任何容器都不得以 root 身份运行，且密钥不能存放在 compose 文件中。需要做哪些改变？

优秀答案的样子：显式声明服务依赖并通过健康检查控制启动顺序，使用命名卷，每个镜像中使用非 root 用户，以及从正规的密钥管理存储中获取密钥——把

.env

排除在版本控制之外只是起点，算不上企业级的密钥管理方案。根据运维约束选择工具：对于受控部署，Compose 可能是正确的选择；不要条件反射式地搬出 Kubernetes。要明确说出客户的可用性、安全性和扩展性需求究竟需要什么。

Q4.2 — 设计 CI/CD 流水线

为 CityOps 服务勾勒 CI/CD 流水线：每次 pull request 运行什么，合并到 main 时运行什么，以及什么来把关部署到预发布环境和生产环境。然后是转折：上个月一个有问题的迁移被发布到预发布环境，导致预发布数据库宕机了一整天。现在流水线会有什么不同？

优秀答案的样子：PR 上的快速反馈（lint、单元测试），合并时更重的检查（集成测试、镜像构建、迁移演练），生产环境部署需要人工审批的部署门禁，以及——事故之后——采用扩展-收缩式迁移（绝不一步完成破坏性变更）、部署前验证、前向恢复规划，以及内置到流水线中的迁移安全检查。注意：删除一列然后回滚应用镜像并不能恢复数据——虽然有备份，但恢复整个生产环境本身也有停机时间和数据丢失的代价。要规划前向恢复，而不仅仅是回退。

Q4.3 — 监控：在客户之前知道问题

为生产环境的 CityOps 部署设计监控：健康检查、日志、指标和告警。面试官补充一个约束：值班工程师是一位从未运维过这套系统的客户员工，而且运维手册必须控制在一页以内。你要监控什么，什么会呼叫他们，以及什么被刻意设计为不呼叫他们？

优秀答案的标准：存活检查与就绪检查分离（服务器有响应不等于模型可提供服务）、带关联 ID 的结构化日志、针对用户可见症状的少量告警（而不是对每个内部指标都告警）、其余内容用仪表盘覆盖，以及一页涵盖三种最可能故障的运行手册——告警疲劳被视为设计缺陷，而不是运维问题。

Q4.4 — 生产环境中的密钥管理、RBAC 与租户隔离

CityOps 部署服务于三个客户业务单元，它们的数据绝不能混用。请设计密钥管理、基于角色的访问控制和租户隔离：凭据存放在哪里、如何授予和撤销访问权限，以及如何向审计人员证明单元 A 的操作员无法看到单元 B 的货运数据。当员工离职时会发生什么？

优秀答案的标准：密钥存放在托管存储中并支持轮换和审计日志、按业务单元设置最小权限角色的 RBAC、在数据层强制实施租户隔离（每条查询都带租户 ID，而不仅仅是在 UI 层）、离职作为经过测试的流程（密钥撤销、会话失效），以及审计人员可以实际查验的证据——整个设计假定审计一定会发生。

Q4.5 — 选择发布策略

你需要发布 RAG 问答服务的新版本。请针对这个具体服务比较蓝绿部署、金丝雀发布和功能开关：你会选择哪一种，为什么？然后是转折：新版本的回答方式不同（不是错误，只是不同），客户的运维团队在一小时内就注意到了。你的策略如何保证这种情况是安全的？

优秀答案的标准：结合该服务的特性进行真正的比较（金丝雀发布用于逐步放量并配合质量指标、蓝绿部署用于快速回滚、功能开关用于将部署与发布解耦），给出理由做出选择而不是背诵定义——转折问题则由策略的可观测性来回答：流量切换加上对实时评测切片的回答质量监控，行为漂移时立即回滚。

Q4.6 — 备份与灾难恢复

为 CityOps 设计备份与灾难恢复方案：Postgres 数据库、向量索引、上传的文档和配置。用客户运营总监能理解的语言定义 RPO 和 RTO。然后是转折：“我们已经每晚备份一年了。”哪个问题能决定这些备份是否真的有价值？

优秀答案的标准：按组件制定备份策略（数据库转储加时间点恢复、向量索引可从源文档重建、配置纳入版本控制）、以业务影响表述 RPO/RTO（“我们最多丢失 N 小时的数据；M 小时内恢复服务”），并直接回答转折问题：“你上次从备份恢复是什么时候？”——未经测试的备份只是一种希望，要通过定期恢复演练来证明，而不是靠备份任务的绿色对勾。

Q4.7 — 在企业代理和防火墙后部署

客户的生产环境无法直接访问互联网：所有流量都经过白名单前置代理，禁止入站连接，而你的容器镜像仓库在他们的网络之外。请设计部署方案：镜像、模型权重和 Python 包如何进入环境？当某个库第一次尝试“回连”外部服务时，什么会出问题？

优秀答案的样子：搭建内部镜像仓库或自带（vendored）制品，为每一层（容器运行时、包管理器、应用程序）配置代理，构建内置全部依赖、可离线运行的镜像，并准备一份预检清单，在生产环境静默失败之前捕获“回连”行为（遥测、许可证校验、模型下载）——设计时将网络边界视为一等约束，而不是事后补救。

Q4.8 —— 凌晨 2 点的故障

现在是凌晨 2 点。客户的状态页显示运维控制台宕机，值班的客户工程师正在呼叫你，而上一次部署是六小时前。请描述你的前 30 分钟：你按什么顺序检查什么，向客户沟通什么——以及你刻意不做什么？

优秀答案的样子：冷静、有序的排查（是应用、平台还是网络的问题？在动手之前先检查健康端点和最近的变更），尽早沟通已知信息和下一步要检查的内容，克制盲目重新部署或重启一切的冲动，并为事后复盘记录时间线——FDE 的关键动作是在管理系统的同时管理客户的信心。

综合运用：完整闭环的答题模式

如果你要带一种答题结构进入每一轮系统设计面试，那就是这个四拍循环——它直接对应本文开头的原则：

环节你说什么它证明了什么
界定范围“我要构建什么、为谁构建，以及明确不在范围内的内容。”你在架构之前先澄清——这是 FDE 的探索习惯。
正常路径“直观的设计方案是这样的……”你能设计出干净的系统，而不只是批评它们。
失败模式“这些地方会出问题：schema 漂移、凭证过期、数据延迟……”你为客户的真实环境而设计，而不是为白板而设计。
权衡与度量“我们用 X 换取 Y；以下是我会度量的指标，以确认它是否有效。”你从面向客户的后果出发思考，而不仅仅是组件。

关于“正确”答案的一点说明

这 32 道题中没有哪道有唯一正确的设计。两位优秀的候选人可以选择不同的架构——一个选金丝雀发布，另一个选蓝绿部署——两人都可以通过，因为面试官评分的是推理过程：你是否揭示了约束条件、指出了失败模式、权衡了利弊，并说明了如何确认它有效？练习推理，而不是背答案。

实战示例：五分钟设计面试

问题：设计对账流水线——证明每一条货运记录都从供应商数据源进入了 Postgres，每日执行，可审计。

时间候选人展示的能力
0:00–1:00界定范围：“谁需要这个？运营负责人，每天在早上 9 点站会之前。数据量：约 20 万条记录/天。成功标准：每条源记录恰好落入一个桶——已迁移、已隔离或已拒绝——且收入精确到分。”
1:00–2:30正常路径：定时拉取 → 根据可运行的契约进行校验 → 写入 Postgres；格式错误的行进入死信队列；对账报告作为数据接入的输出，包含计数、哈希值和审计日志。
2:30–4:00故障模式：“如果供应商重命名了某个字段，校验会隔离该批次并触发告警——我们在生产环境中见过这种模式。如果拉取在批次中途崩溃，检查点会从上次提交的偏移量恢复。重复数据无害：稳定的记录键使消费者具备幂等性。”
4:00–5:00权衡与度量：“严格校验会拒绝更多数据；隔离需要人工介入。验收标准：每天 100% 的源记录都有去向，如果报告超过 26 小时未更新则告警。客户拿到的是报告，而不是承诺。”

面试官追问：“供应商现在发送更正——针对过去几天的更新记录。你的‘恰好一个桶’不变量被打破了。需要做什么改动？”优秀回答：“对记录进行版本管理：每条源记录都有一个版本号，报告跟踪每个键的最新版本，外加一个更正台账。不变量变为‘每条源记录的每个版本都有去向’。更正在物流领域是常态——设计就应该预期到它们。”

实战检验——面试前给自己打分

  • 从每组中选一道题。每道题大声作答五分钟，然后对照提示检查你的答案：你是否至少指出了两种故障模式和一项面向客户的权衡？
  • 用不到两分钟的时间，向一位不懂技术的朋友解释你的 Q3.5（审批）答案。如果他们无法复述授权与审批的区别，那你的解释还需要打磨——你的面试答案也一样。
  • 写下你 Q4.3 答案中会呼叫值班工程师的三个监控告警。为每个告警写出对应的操作手册步骤。如果任何告警没有对应的操作手册步骤，那它就是噪音，而不是监控。

如何判断你已经准备好了

当你能够应对这个题库中的任何问题时，你就准备好了：用第一分钟界定范围（“客户是谁，哪些不在范围内？”），接下来三分钟讲主流程加失败模式，最后以权衡取舍和衡量指标收尾——不看笔记、不东拉西扯、不编造你无法自圆其说的数字。白板只是一个道具；思考才是产品本身。
