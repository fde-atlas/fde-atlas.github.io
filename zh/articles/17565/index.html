调试失败的 API 请求 · FDE 面试题

原标题：Debug failing API requests · FDE interview question

FDE Interview Prep · 2026 · 约 8 分钟读完

摘要

本文是针对 Cohere 前沿部署工程师面试中“调试失败 API 请求”题型的备考指南。作者给出以“影响范围、模式、缓解、持续沟通”为框架的一小时作答模板，强调先量化错误率再排查，并附 jq 查询示例、LLM API 特有场景（限流、上下文超限、流式截断）及常见失分点。

要点

  • 答题框架：先定影响范围，再找模式，先缓解后根因。
  • 先算错误率并与他人对比，判断是单客户还是全局故障。
  • 按状态码分组排查，结合部署与配置变更时间线。
  • LLM API 特例：按 token 而非请求数看限流与上下文超限。
  • 全程主动向客户同步进展，网关超时后提醒重试风险。

如何回答

这个提示故意写得含糊。展示的顺序应是：谁受到了影响、影响有多严重，这些故障有什么共同点，以及你在排查过程中客户是否能得到你的消息。

一位候选人在 Glassdoor 上于 2026 年 8 月报告说，他们参加 Cohere 该职位的面试时，有一轮关于调试系统的问题解决环节。Source 1Cohere 前沿部署工程师面试题发布方Glassdoor（匿名面试评价）来源类型候选人的个人记述 该评价者没有说明是什么系统。这个提示是我们对这类环节的模拟，并非他们当时被问到的原题。

雇主确实会布置这类任务。Ethyca 为其前沿部署隐私工程师职位公布的带回家作业，就要求你连接其 API，复现并诊断客户的 API 错误，然后撰写给该客户的回复。Source 2Ethyca Technical Challenge -- Forward Deployed Privacy Engineer (FDPE)发布方Ethyca（GitHub）来源类型公司网站 在这里你会拿到日志。如果拿到的是架构图，就把同样的步骤当作问题来执行：追踪一个请求从客户端到数据存储的路径，说出你在每一跳会查询什么，并向面试官索要那个结果。它们就是你的日志。

  • 开始之前先说出计划。 确定范围、找出模式、进行缓解，并全程向客户同步进展。
  • 把报告转化为搜索条件。 索要失败的请求 ID、带时区的时间戳、端点、客户端看到的确切错误以及开始时间。确认收到，并给出下一次更新的时间。
  • 确认故障确实到达了你这里。 客户端看到的故障可能在你的日志中不留任何错误：在负载均衡器或 TLS 握手阶段被拒绝，或者客户端超时而你的服务器延迟返回 HTTP 200。缺失的请求 ID 本身也是证据。
  • 评估影响范围。 先看他们的错误率随时间的变化，即失败数除以请求数，再看其他所有人的情况。是一个客户还是所有客户？一个端点还是所有端点？突发还是渐进？这决定了严重程度以及还需要通知谁。
  • 找出模式。 先按状态码对失败分组；RFC 9110 中的状态码类别能告诉你该看请求侧还是自己这一侧。然后按端点、客户端版本、主机和载荷大小切分，并把开始时间与部署、配置变更和密钥轮换对齐。
  • 一次只验证一个假设。 “只有超过请求体大小上限的请求会失败”这样的假设，可以用一次查询来证实或推翻。
  • 在完全弄清之前先缓解。 回滚、摘掉坏主机，或给客户提供临时解决方案，并告诉他们哪些操作可以安全重试。
  • 在一小时结束时以书面形式收尾。 你知道了什么、还不知道什么、改变了什么，以及下一次更新的时间。

前沿部署工程师一种软件工程师，在客户的问题和环境中构建并交付生产系统，并对客户的最终结果负责。

追问

一旦你的第一个回答摆上桌面，面试官接下来可能会问什么。

  • 失败的请求 ID 在日志里完全找不到。现在怎么办？
  • 失败是 POST 请求的网关超时。关于重试，你会怎么告诉客户？
  • 只有这一个客户受影响，而我们这边什么都没改。你会从哪里查起？

回答容易出错的地方

  • 盯着第一个堆栈跟踪调试一个小时，却从不统计失败数量。
  • 只统计错误数量，却不与总请求数做对比。
  • 在查明原因之前对客户保持沉默。

两分钟内回答

写出你会大声说出来的回答。计时从你说出第一个字开始。

与标准答案对比

标准答案

“我的计划是：界定范围、找出模式、缓解问题，并全程向客户同步进展。

T+0

至

T+10

：让报告可搜索。

我会立即回复客户：我们已经在处理，一小时内给出下一次更新。我会请他们提供几个失败的请求 ID 或带时区的时间戳、出问题的端点、他们客户端收到的错误内容，以及他们最早发现问题的时刻。在他们回复的同时，我从已有的信息入手——他们的租户 ID。等他们的请求 ID 到手后，第一步是确认这些请求到底有没有到达我们这边。如果找不到，我会查看边缘节点和负载均衡器的日志。如果请求在，返回 HTTP 200 且耗时很长，那就是他们的客户端在我们响应之前就超时了，而错误计数永远不会显示这种情况。

T+10

至

T+25

：界定范围。

假设 JSON 日志中包含

ts

,

tenant

,

route

,

status

,

host

和

duration_ms

:

# Their failures by status and route
jq -r 'select(.tenant=="acme" and .status>=400) | [.status, .route] | @tsv' logs/api-*.jsonl \
  | sort | uniq -c | sort -rn | head -20

# Their requests, failures and error rate per minute
jq -r 'select(.tenant=="acme") | [.ts[0:16], (if .status>=400 then 1 else 0 end)] | @tsv' logs/api-*.jsonl \
  | awk -F'\t' '{n[$1]++; e[$1]+=$2} END {for (m in n) printf "%s %d %d %.1f%%\n", m, n[m], e[m], 100*e[m]/n[m]}' | sort

# Everyone else: requests, failures and error rate per host
jq -r 'select(.tenant!="acme") | [.host, (if .status>=400 then 1 else 0 end)] | @tsv' logs/api-*.jsonl \
  | awk -F'\t' '{n[$1]++; e[$1]+=$2} END {for (h in n) printf "%s %d %d %.1f%%\n", h, n[h], e[h], 100*e[h]/n[h]}' | sort -k4 -rn

比率很重要，因为失败数量的上升可能只是流量的上升。与其他所有客户的对比是最关键的查询。如果只有这个客户失败，原因很可能在他们发送的内容或其账户的配置上。如果所有客户都在同一台主机上失败，那就是我们的问题，属于事故，我会先呼叫值班人员再继续排查。

T+25

至

T+45

：模式与假设。

状态码会指引我的方向。某一时刻开始出现 HTTP 401 或 HTTP 403，提示密钥被轮换或吊销。HTTP 413，或某一路由上的 HTTP 400，提示载荷大小问题或他们那边的模式变更，所以我会对比失败请求与成功请求的大小。HTTP 429 表示限流器拒绝了他们（

RFC 6585

），所以我会检查是哪一层返回的，并把他们的请求速率与其限额做对比。HTTP 502 或 HTTP 504 集中出现在某台主机上，或集中在慢请求上，指向上游超时或某个异常实例。我会把开始时间与我们的部署日志和配置变更对齐。每个假设都对应一个可以证伪它的查询。

如果是 LLM API，同样的状态码含义更多。 HTTP 429 可能来自每分钟 token 数限制，而请求次数看起来正常，所以我会绘制他们的每分钟 token 数，而不仅仅是请求数。因超出上下文长度导致的 HTTP 400 错误会随着提示词变大而增多，比如当他们开始加入聊天历史或检索到的文档时，所以我会按输入 token 数而不是字节数来对失败进行分桶。被代理或负载均衡器空闲超时切断的流式响应会表现为 HTTP 200 但响应体被截断，或在边缘表现为 HTTP 504，且耗时都堆积在某个整数附近。提供商也可能在 HTTP 200 之后、流中途发送错误事件，所以只有当流的最后一个事件到达时才算成功。上游模型提供商过载表现为 HTTP 503，或提供商自己的错误码，例如 Anthropic 的 API 文档 中列出的用于过载的 HTTP 529。针对流式和上下文窗口这两种情况的查询，假设日志中包含

input_tokens

:

# Their requests by 5-second duration bucket and status: a pile at one bucket is a timeout
jq -r 'select(.tenant=="acme") | [(.duration_ms/5000 | floor) * 5, .status] | @tsv' logs/api-*.jsonl \
  | sort | uniq -c | sort -k2,2n -k3,3n

# Their error rate by input-token bucket: failures only above a size point at the context window
jq -r 'select(.tenant=="acme") | [(.input_tokens/10000 | floor) * 10000, (if .status>=400 then 1 else 0 end)] | @tsv' logs/api-*.jsonl \
  | awk -F'\t' '{n[$1]++; e[$1]+=$2} END {for (b in n) printf "%s %d %d %.1f%%\n", b, n[b], e[b], 100*e[b]/n[b]}' | sort -n

作者

T+45

：缓解。

如果有部署时间吻合，就回滚。如果某台主机有问题，就把它从轮换中摘除。如果是他们的负载问题，就立即发送限额信息和临时解决方案，产品层面的问题另行讨论。

T+60

：一份书面更新。

例如：

自 UTC 09:40 起，你们约 6% 的 POST /v1/orders 请求因 HTTP 504 失败。它们都经过我们的某一台主机，该主机已于 10:31 移除；失败在 10:32 停止。网关超时意味着我们停止了等待，并不代表订单失败，因此其中一些订单可能已经存在。附件列表显示了哪些订单已创建；请在重试前先核对，或发送 Idempotency-Key 请求头，以防止重试创建重复订单。我们正在排查该主机性能下降的原因，并将在今天 UTC 17:00 前告知原因和修复方案。

它说明了影响范围、目前所知的原因、做了什么变更，以及他们下次何时会收到消息。之所以写重试那一句，是因为网关超时并不能说明上游是否已完成（RFC 9110, section 15.6.5），而 POST 不是幂等的（RFC 9110, section 9.2.2），盲目重试可能创建第二笔订单。

如果只涉及一个客户，而我们这边没有任何变更，那就是他们那边变了：新的 SDK 版本、新的区域或网络路径、他们前面的代理，或者更大的负载。我会在起始时间前后按用户和来源 IP 切分他们的请求，并询问他们当天上午部署了什么。

我要避免的是打开第一个堆栈跟踪然后调试一个小时。在按类型统计失败之前，我不知道那个跟踪到底是问题所在，还是一直存在的背景错误。

如果面试官给我的是架构图而不是日志，我会把同样的一小时用作提问：我从客户端到数据存储逐跳追踪一个请求，说明我会在每一跳查询什么，并索要结果。”
