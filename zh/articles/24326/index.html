LLM 裁判评测：一致率与召回率怎么算

FDE Times · 2026-10-24 · 约 5 分钟读完

摘要

文章以 Arize AI 前沿部署工程师的视角，讲解如何验证 LLM 裁判评测的可靠性。核心观点是：总体一致率（如 85%）可能掩盖极低的失败召回率（如 25%），未经验证的裁判不应作为发布门禁。文章通过退款助手示例说明应先建追踪、再人工标注数据集、针对客户关心的故障类型测召回率，并对 Agent 同时评测最终答案与工具调用轨迹。

要点

  • 一致率 85% 的裁判，失败召回率可能只有 25%。
  • 可观测性记录 Agent 行为，评测判断对错，两者构成闭环。
  • 裁判须先经人工标注验证，才能用作发布门禁。
  • 对 Agent 要同时评测最终答案和工具调用轨迹。
  • 数据集要带版本管理，避免实验间不可比。

在 Arize AI，FDE 与客户共建从追踪到评测的体系，核心是在弱裁判成为发布门禁前识破它。

要点速览

  • 可观测性告诉你 Agent 做了什么，评测告诉你它做得对不对。正经的体系两者缺一不可
  • LLM 裁判用作发布门禁或接入看板之前，先用人工标注验证，并针对客户关心的失败类型单独测召回率
  • 对 Agent 还要给轨迹打分：答案正确，过程也可能是错的

客户的 AI 团队打开客服助手的演示，补了一句：“我们人工看了几十段对话，都没问题。”下周他们就想向全部用户上线。此时你要回答的问题，已经不是“好不好用”，而是“出了问题，谁会发现，怎么发现？”

在 Arize AI，这几乎就是工作的全部。公司的前线部署工程师（FDE）招聘启事这样描述这个岗位：与客户的 AI 团队合作，设计、部署并扩展生产级的 GenAI 可观测性与评测体系。FDE 还要开发定制集成和工具，让 Arize 平台贴合每个客户的需求。

即使从不在 Arize 工作，这项技能也用得上。只要你在把 LLM 接入客户系统，就要准备好用数据而不是直觉来回答这个问题。

可观测性与评测是同一个闭环的两半

可观测性回答“Agent 做了什么”。每个请求都记录为一条追踪记录（trace），包含提示词、检索到的文档、工具调用和最终答案。Arize 的开源平台 Phoenix 基于 OpenTelemetry 构建追踪功能，不绑定厂商、语言或框架。

最后这一点对 FDE 很重要。客户用什么模型、什么 Agent 框架都有可能，你只需按一个通用标准埋点，不必为每套技术栈重写。

评测回答“它做得对不对”。你把 trace 整理成数据集，Phoenix 支持按版本管理这些数据集，用于实验、评测和微调。在 Arize AX 中，一次实验会在数据集的每一行上运行任务，并用 LLM 裁判打分，每个分数都附带解释，方便你针对正确的故障类型去修。

示例：一个退款助手和一个“还不错”的裁判

假设客户是一家零售商，有一个处理退款申请的 Agent。你给 Agent 埋点，收集一周的 trace，挑出 100 段对话，保存为数据集

refund-v1

。客户的两名客服人员逐条人工标注：80 段通过，20 段失败。

接着你写一个 LLM 裁判，在同样的 100 行上运行。裁判把 80 段通过的对话全部判对，但 20 段失败的只抓到 5 段。结果如下：

人工：通过人工：失败
裁判：通过8015
裁判：失败05

总体一致率为 (80 + 5) / 100 = 85%，放在幻灯片上挺好看。但失败召回率只有 5 / 20 = 25%：每四段出错的对话，裁判放过了三段。Arize 警告的正是这种情况：一致率 85% 的裁判，如果漏掉你关心的失败，照样不能用。

计算这两个数字的代码很短，而且应当总是把它们并排打印：

def judge_report(human, judge):
    # human、judge：由 "pass" / "fail" 组成的列表
    n = len(human)
    agree = sum(h == j for h, j in zip(human, judge))
    fails = [j for h, j in zip(human, judge) if h == "fail"]
    caught = sum(j == "fail" for j in fails)
    return {
        "agreement": agree / n,
        "fail_recall": caught / len(fails) if fails else None,
    }

修复从裁判的解释入手。读完 15 个漏判案例，你可能会发现一个共同模式：裁判只检查回答是否礼貌、是否符合政策，完全不知道 Agent 在查询订单状态之前就确认了退款。

答案正确，不等于过程正确

这个例子里的问题不在措辞，而在路径。Agent 说“您的订单已退款”，却跳过了查询订单的工具调用。Arize 建议，对 Agent 必须同时评测最终答案和轨迹。

所以第二版裁判需要看到 trace 中的工具调用序列，并配上一条明确的标准：确认退款之前必须先查订单状态。在

refund-v1

上重跑实验，把失败召回率与上一版对比。数据集保持不变，任何差异就只来自裁判，而不是数据。

Arize 建议，只有在裁判经过人工标注验证之后，才用它来卡发布、驱动看板或做自动路由。这个顺序是硬性规定：在未经验证的裁判上搭门禁，会把它的盲区一并自动化。

在客户那里，应该按什么顺序做？

先做追踪，没有 trace，一切关于质量的讨论都只能凭感觉。然后和客户一起选出他们真正担心的故障类型，比如错误退款、数据泄露或超出政策范围的回答。这份清单决定了你在哪一组上测召回率。

接下来建一个带版本的数据集，请客户的人来标注，最好是领域专家而不是工程师。之后写裁判，测一致率和召回率，根据解释修正，只有当召回率达到客户能接受的水平时，才把它升级为发布门禁。

呈现结果的方式也要看对象。Arize 的岗位要求 FDE 主导技术讨论，对象从工程师一直到高管。工程师需要混淆矩阵；高管只需要一句话：“裁判目前只能抓到 20 个退款故障中的 5 个，所以还不能用来卡发布。”

让评测体系早早夭折的错误

最常见的错误是只报一个一致率数字，比如上面的 85%。第二个是在两次实验之间改动数据集，结果没人知道分数提高是因为提示词，还是因为数据变简单了。第三个是对调用工具的 Agent 只给最终答案打分。

第四个关乎工作方式。Arize 的 FDE 会同时推进多个项目，从界定范围到交接全程负责，还要参与编写团队的工作手册。如果每个客户都从零搭流程，你会跟不上，所以要把上面的步骤做成可复用的模板。

这项技能怎么写进简历？

Arize 的招聘启事要求 2-5 年软件开发经验，低于许多资深 FDE 岗位。作为交换，候选人必须在生产环境中开发、部署并持续改进过 GenAI 应用，并熟悉云和容器工具。

面对这样的岗位，“用过 LLM-as-a-judge”这种描述说明不了什么。更有力的写法是：“用 100 条人工标注验证裁判，把失败召回率从 25% 提升到足以卡发布的水平”。这能让面试官知道，你懂得测对的东西。

这周，从你手头任意一个 LLM 应用里取 50 条 trace，自己标注，再让裁判打分。如果失败召回率让你吃惊，你看到的正是客户 AI 团队没看到的东西。
