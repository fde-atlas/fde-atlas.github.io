Pre-mortem 事前验尸会议怎么开：FDE 上线前风险排查

FDE Times · 2026-11-03 · 约 6 分钟读完

摘要

这篇文章介绍如何用 Gary Klein 提出的事前验尸（pre-mortem）方法，在 FDE 项目上线前排查风险。作者以保险公司部署 LLM Agent 分拣理赔为例，给出 30 分钟会议流程：假设项目已失败、各自独立写下原因、轮流发言、投票选出三大风险与机会，并为每个风险指定负责人和截止时间。文章还列举常见错误，并说明如何把主持经验写进简历。

要点

  • 事前验尸假设项目已失败，打破双方保面子的沉默。
  • Klein 方法最短 20-30 分钟，借鉴前瞻性后见之明研究。
  • 流程含独立书写、轮流发言、圆点投票与任务分配。
  • 须请真正用户参加，并在上线前约两周开会。
  • 常见错误：说可能失败、高层先发言、风险无负责人。

先宣布项目已经失败，再问原因：Gary Klein 的方法能打破双方为保面子而守的沉默。

要点速览

  • 项目启动会往往掩盖风险，因为没人想破坏团队的气氛。
  • 事前验尸从“项目已经失败”这一假设出发，谁说出最尖锐的原因，谁就被看作看得最清楚的人。
  • 一场会最短 20-30 分钟即可，但结束时必须投票选出少数几个风险，每个风险都有负责人和截止时间。

离上线还有两周。指导委员会会议上，每个人汇报自己负责的部分：集成已经跑通，评测过了阈值，运营团队也培训完了。没人提出异议。但经验告诉你，这么顺利的会，通常漏掉了什么。

心理学家 Gary Klein 大约在 30 年前（以 2021 年计）提出了事前验尸（pre-mortem）方法，他对这种现象说得很直白。

这类会议上总有一种不言明的压力：没人愿意说出疑虑，怕破坏团队的和谐。对前线部署工程师（FDE）来说，压力更大，因为同一张桌子边坐着两家机构，谁都不想让对方丢面子。

你站在双方之间，因此也最适合打破这种沉默。事前验尸是成本最低的工具。它不需要特别的权限，只需要会主持会议。

换一个问题，讨论方式就变了

问“这个项目可能在哪里出问题？”，通常只能得到稳妥的回答。事前验尸问的是另一个问题。

按 Klein 的描述，主持人告诉大家，刚才讨论的计划已经失败了，然后让每个人独立写下原因。他 2007 年发表在《哈佛商业评论》上的文章，也建立在同一个假设上：正在规划的项目刚刚失败了。

Wikipedia 用医学做了个类比。常规的计划评审问的是病人可能会怎样；事前验尸则假设病人已经去世，再问死因。

这一方法借鉴了 Mitchell、Russo 和 Pennington 1989 年关于“前瞻性后见之明”（prospective hindsight）的研究：站在想象中的未来往回看。

最巧妙的地方在于参与者的动机。Klein 观察到，一旦把失败当成既定事实，人们就会通过所提问题的质量来展示自己的能力。指出风险不再被看作对项目缺乏信心，而是一种贡献。

与客户演练一场 30 分钟的会

设想一个场景。你正在为一家保险公司部署一个 LLM Agent，用来分拣理赔案件。在场的有客户方的项目发起人、运营负责人、负责核心系统的 IT 工程师、一名理赔专员，还有你。

Klein 认为这样的会最短 20-30 分钟就够了。下面的流程保留了 Klein 的独立书写和逐轮发言。最后两步，即投票和交接，来自 Atlassian 的模板以及英国政府数字医疗团队的实践。

第 0-3 分钟，开场。 把准备好的开场白一字不差地念出来：“现在是上线三个月后。项目失败了：Agent 已经停用，员工又回到了手工处理。请每个人写下导致这一结果的原因。”

开场白必须用过去时，而且要具体。一说“假设它可能失败”，效果立刻就没了。

第 3-8 分钟，各自书写，不讨论。 每个人独立写下原因。这一步安静进行，很关键，它能防止一线员工被发起人的观点带着走。

英国数字医疗团队在这里加了一步：把在场的人分成“灾难组”和“成功组”。五个人的会，可以请一两个人写相反的情景：三个月后，Agent 成功了。为什么？

像“理赔专员信任 Agent，因为他们能看到每次分拣决策背后的理由”这样的回答，会告诉你哪些内容必须留在范围内，工期吃紧时也不能砍掉。

第 8-20 分钟，轮流发言。 Klein 建议主持人先坦诚地开头，做个示范，并且每人每轮只说一个原因。你可以先说自己这部分的弱点：“我的评测集是用去年的理赔案件做的，而今年的分拣规则已经变了。”

接着，理赔专员可能会说，员工不信任 Agent，于是每件都重新核对，根本没省下时间。IT 工程师可能会指出，核心系统在高峰时段限制 API 调用次数。这类话在普通的指导委员会会议上很少有人说出来。

第 20-25 分钟，投票。 列出的清单通常比能处理的多。英国数字医疗团队让每个人用圆点投票，选出三个最大的风险和三个最大的机会。照着做即可：三个风险成为要修复的事项，三个机会成为上线计划里要保住的内容。

第 25-30 分钟，分配任务。 前三大风险都必须有负责人和截止时间。在保险场景里，可能是这样：你在周五前往评测集里补充 200 个按新规则处理的理赔案件。

运营负责人挑两名员工并行试用一周。IT 工程师确认 API 限额，你再加一个队列。

模板现成，但要按客户调整

对大型、多方参与的项目，Atlassian 的 Team Playbook 提供了一个更长的现成版本：3-11 人，约 60 分钟，包含静默头脑风暴、对主要风险投票，以及分配带负责人和截止时间的行动项。

用在客户那边，需要做两处调整。第一，请真正的用户参加，因为发起人很少知道 Agent 会在日常工作的哪个环节出问题。第二，会要开得早，大约在上线前两周，这样才有时间修复；上线前一天开会，只会让所有人更焦虑。

英国数字医疗团队的经验是：价值在于行动。Colin Pattinson 写道，这场会挖出了没人预料到的风险，团队及时处理了其中几个。在他看来，事前验尸逼着你在问题日后毁掉项目之前就直面它们。

让事前验尸沦为诉苦会的错误

最常见的错误是说“可能失败”，而不是“已经失败”。措辞上只是小小的变化，但听的人会退回防御姿态，你又只能听到稳妥的回答。

第二个错误是让职位最高的人先发言，而且说的是无关痛痒的原因，比如“可能是时间不太够”。

Klein 希望主持人先开口，好让大家也敢直说。第一轮就说个无关痛痒的原因，传递的是相反的信号：这里说话要客气。所以要提前和发起人约好，第一个原因必须是真正让人不舒服的事，或者你自己先说。

第三个错误是会议结束时列了 30 个风险，却没有负责人。没有负责人和截止时间的清单，只是一份大家的担忧记录。最后一个错误是只请自己的团队。那样你只会听到自己早就知道的风险。

把这场会变成简历上的证据

如果你瞄准的 FDE 岗位描述里提到与利益相关方协作或风险管理，主持过的事前验尸就是证明这项能力的好证据。前提是你能说出它带来了什么改变。

回到保险场景。一句弱的简历描述是：“上线前组织了一次事前验尸会。”

强的描述要说清谁参加、发现了什么、修复了什么：“上线前两周与 4 名客户方利益相关方主持事前验尸会；发现评测与新规则脱节、核心系统高峰时段存在 API 限额，并在发布前解决了这两个问题。”

面试中，“讲一次你预防事故的经历”正是讲细节的地方。说出你用的开场白、理赔专员提出而发起人从没听过的原因，以及随后的并行试用。

面试官想看到的是，你会主动找问题，而不只是在问题爆发后救火。

下次指导委员会会议顺利得让人起疑时，你不必和任何人争论。只要问一句：如果三个月后 Agent 被停用了，你们觉得原因会是什么？
