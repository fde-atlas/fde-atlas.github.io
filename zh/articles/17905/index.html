Streamlit 适合做什么：FDE 何时该换架构

FDE Times · 2026-11-12 · 约 5 分钟读完

摘要

文章分析 Streamlit 的适用边界：其全脚本重跑模型让 FDE 能快速搭建客户演示，但在状态持久化、授权和复杂交互上存在硬性限制。作者给出三个换架构信号，并建议在演示当天就向客户说明迁移条件。

要点

  • Streamlit 每次交互重跑整个脚本，演示快但复杂应用易撞天花板。
  • st.cache_data 可缓存耗时数据加载，Session State 刷新标签页即清空。
  • st.login 基于 OIDC 只做认证不做授权，无法满足企业角色访问控制。
  • 复杂多步工作流需手动维护大量 Session State 键，易出错。
  • 建议用假数据做公开演示，真实数据只在客户批准的环境运行。

要点速览

  • Streamlit 在界面需要更新时重跑整个脚本，所以演示做得快，也正因如此，复杂应用很快会撞上天花板
  • st.cache_data 能让耗时的数据加载函数不必每次点击都重跑；而 Session State 在用户刷新标签页后就会清空
  • st.login 通过 OIDC 提供身份认证，但不提供授权；企业客户一旦需要基于角色的访问控制，就该换架构了

据官方文档，每当界面需要更新，Streamlit 都会把整个 Python 脚本从第一行到最后一行重新运行一遍。正是这个设计，让你能在一个下午做出客户演示；这也是应用一旦要承担查看数据之外的需求，就会撞上天花板的原因之一。

对前线部署工程师（FDE）来说，这不是纸上谈兵。在客户现场，第一周最需要的往往是一个跑在真实数据上的界面，让业务方能点一点、提意见。弄清 Streamlit 擅长什么、在哪里会出问题，才能向客户做出兑现得了的承诺。

它本来是为什么而做的？

Streamlit 自称是构建和分享数据应用的更快方式。Snowflake 于 2022 年 3 月 2 日宣布有意收购 Streamlit，新闻稿中称它是一个帮助开发者和数据科学家构建、分享数据应用的开源框架。

“数据”和“分享”这两个词，恰好划定了它的适用范围。不用写前端，不用搭 API，也不用操心路由。你写一个读数据、画几个控件的 Python 脚本，这个脚本就是应用本身。

重跑模型：演示为何快，应用为何慢

Streamlit 文档说得很明确：默认情况下，用户每操作一次控件，应用就重跑一次。这让代码容易理解：没有纠缠不清的回调，也没有需要同步的界面状态；从上往下读一遍脚本，就知道界面会显示什么。

代价在于慢函数。设想给一家物流公司做演示，读取订单文件的函数约需 8 秒。如果客户在会上改了十次筛选条件，就是十次重跑，大约 80 秒盯着加载动画，足以打乱演示的节奏。

Streamlit 正是为此提供了缓存机制。文档指出，不加缓存时，耗时长的函数会一遍遍重复执行，拖慢应用。对返回数据的函数，推荐默认使用

st.cache_data

：

import streamlit as st
import pandas as pd

@st.cache_data
def load_orders(path):
    return pd.read_csv(path)  # 很慢，但只有第一次真正执行

orders = load_orders("orders_sample.csv")

if "notes" not in st.session_state:
    st.session_state["notes"] = []  # 用户在本次会话中的笔记

在物流示例里，这 8 秒现在只在第一次花掉；之后九次更改筛选条件，数据都从缓存读取。还有一点：根据文档，

st.cache_data

每次调用函数都会生成一份新的数据副本。

这意味着在脚本里修改 DataFrame 不会破坏缓存，但表非常大时，复制本身也要消耗资源。

到了客户办公室、打开笔记本后的第一件事：在写任何控件之前，先给每个数据加载函数套上

@st.cache_data

。

该换架构的三个信号

第一个信号是状态。Session State 用于在多次重跑之间保存数据，它绑定在每个用户会话上，不在用户之间共享。文档也说得很直白：关闭或刷新标签页，Session State 里的内容就全部消失。

做演示时，这可以接受。但如果客户开始要求多步骤工作流，比如分析师在第一步审批申请，团队负责人在第二步复核，按一下 F5 就可能让成果全部清空。这时你需要持久化存储，以及真正能管理状态的架构。

第二个信号是访问控制。Streamlit 内置了基于 OIDC 的

st.login

认证，但文档写得很清楚：OIDC 支持身份认证，不支持授权。知道用户是谁，和知道用户能看什么，是两回事；需要基于角色访问控制的企业客户，问的恰恰是第二个问题。

第三个信号来自重跑模型本身。回到物流示例：假设客户想在表格里选中一个订单，打开表单修改收货地址，再回到表格，且筛选条件保持不变。

由于每次点击都会重跑整个脚本，你得自己把选中的订单、筛选条件和填了一半的表单内容存进 Session State，再在每次运行开头读回来。

每多一个子界面，就多出几个必须彼此一致的 Session State 键，只要有一个键对不上，表格就会显示错误的订单。当大部分时间都花在维持界面状态一致，而不是开发客户需要的功能时，Streamlit 就不再是合适的选择。

分享很快，但要小心客户数据

Streamlit Community Cloud 可以从 GitHub 仓库免费创建、部署和管理应用。做内部演示或作品集非常方便：推送代码，就能得到一个可以发给别人的链接。

涉及客户数据时，这应当是先向客户确认的问题，而不是默认做法。公开演示用结构相同的假数据搭建，真实数据只在客户批准的环境中运行。

先学什么，求职时怎么展示

按这个顺序学：重跑模型，然后是

st.cache_data

，接着是 Session State，最后是

st.login

及其局限。掌握这四点，就足以做出演示，也能向客户解释为什么演示还不是产品。

简历上不要只写“熟悉 Streamlit”。可以这样写：用一天时间在客户样例数据上做出原型，与客户约定更换架构的条件，随后迁移到具备持久状态和授权的系统。目标是让读者看到你两件事都能做：快速交付演示，也知道何时该停。

一小时练习：赶在客户之前找到断点

拿一份假的订单 CSV 文件，做一个带筛选条件的表格，分别记录读文件函数套上

@st.cache_data

前后每次更改筛选条件的耗时。接着加入选中订单的功能和修改地址的表单，两者都存在 Session State 里。最后按下 F5，记下哪些内容消失了。

这个练习能帮你避开首次演示中常见的三个错误。一是忘记加缓存，客户每点一下都要等。二是因为部署太容易，就把客户的真实数据放到公开应用上。三是看到

st.login

就当场承诺基于角色的访问控制。

用 Streamlit 花一个下午，可以赢得客户的信任。能否保住这份信任，取决于在演示当天就提前告诉客户：它什么时候会被别的方案替代。
