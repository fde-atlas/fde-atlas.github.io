端到端追踪一次请求 · FDE 编程题

原标题：Trace a request end to end · FDE coding question

FDE Interview Prep · 2026 · 约 3 分钟读完

摘要

本文介绍 Scale AI 前沿部署工程师面试中的一道编码题：在大型代码库中追踪一个请求的完整链路。作者给出方法：从入口文件找到启动点，用框架路由表定位 handler，逐层记录跨越数据库、缓存、队列等边界的跳转，并用运行时验证（如堆栈跟踪、request id）把推测升级为确认。文章还列出常见追问和错误做法，例如只画同步调用链、把猜测当作事实。

要点

  • 题目要求从单个请求出发，快速绘制代码库全链路地图。
  • 每条边需标注证据类型：运行过、读过代码或仅是猜测。
  • 建议先查 OpenTelemetry 或 APM 等现有追踪获取真实链路。
  • 需注意装饰器、依赖注入、ORM 钩子等搜索容易遗漏的间接层。
  • 常见错误是从 README 或目录树读起，而非从具体请求入手。

如何回答

一位候选人在 Aced（原 Exponent）上报告说，其 Scale AI 现场面试（面试记录为 2025 年 8 月）包含一轮调试大型代码库的环节。Source 1Scale AI 前沿部署工程师面试经验（2026）发布者Aced（原 Exponent）来源类型候选人的个人分享 这个问题练习的正是这类环节可能考察的一项技能：仅凭一个请求，在不通读整个代码库的情况下，快速建立一张准确的地图。

  • Pin one concrete request. Method, path and an example body: 
    POST /api/v2/invoices/<id>/send
    . Say the deliverable: every hop from the network edge to each store and external call, with a file and line, each marked ran, read or guessed.
  • 从进程启动的地方开始。 Procfile、Dockerfile CMD 或 package.json 脚本指明了 Web 入口点和各个 worker，而 worker 运行的部分是 handler 无法体现的。检查是否已有链路追踪（OpenTelemetry、APM、request-id 中间件）：一条真实的 trace 就是一个已确认的骨架。
  • 用框架的方式找到路由。 请求它的路由表（flask routes、bin/rails routes），或搜索一个独特的片段而非完整 URL，因为前缀可能在别处拼接。如果该字符串哪里都找不到，路径可能在应用收到之前就被重写了：检查 ingress、网关或代理配置。
  • 向下走，记录边界。 Handler、service、数据访问层；在每一跳，记录什么跨越了边界：数据库、缓存、队列、HTTP 调用。按顺序列出中间件，而不必逐行阅读。
  • 搜寻搜索会漏掉的间接层。 装饰器、依赖注入、ORM 钩子、feature flag、队列生产者。对于队列，搜索任务名以找到消费者。
  • 用运行时来确认。 来自最深函数的堆栈跟踪、一个贯穿两侧日志的 request id，或在现有测试中加一个 print 运行一次。把边界从“读过”或“推测”升级为“运行过”。

边做边讲解。陷阱是按文件夹顺序读文件，然后把一个猜测当作地图呈现出来。

追问

当你的第一个回答摆上桌面后，面试官接下来可能会问的问题。

  • 路由字符串在代码库里哪里都找不到。你如何找到 handler？
  • 你的地图显示邮件已发送，但客户从未收到。你会先检查哪一跳，在那里你会看什么？
  • 路径进入了一个你无法打开其代码的服务。这一跳在图上该怎么标注？
  • 你的时间快用完了。哪些边你会保留“推断”标记，哪些必须确认？

常见的错误答案

  • 从 README 或目录树开始向外阅读，而不是从一个具体请求出发，结果一轮下来只得到一幅模糊的全景图。
  • 只画出同步调用链，漏掉了队列跳转、ORM 钩子或决定实际行为的请求前中间件。
  • 把根据命名规范猜测的边当作事实呈现，却没有运行任何东西来验证。
