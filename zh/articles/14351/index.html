摘要

文章梳理了 FDE 岗位面试中语音 AI Agent 实作业务的真实案例与要点。作者从候选人公开的 GitHub 仓库中收集了多份题目，包括 HappyRobot 的入站承运商销售 Agent（需自建指标面板、邮件和五分钟视频）、限时两小时的牙科预约系统提示词测试、HVAC 预约 Agent 和律所客户登记 Agent 等。核心观点是：电话场景无法隐藏缺陷，聊天机器人的习惯会失效。文章给出具体建议：为每轮对话设定延迟预算（示例约一秒）并分阶段记录 p50/p95；正确处理打断（barge-in）与“嗯哼”类附和，历史记录只存来电者实际听到的内容；为工具调用设置超时、带抖动的重试和明确的失败话术；预设转人工触发条件并做暖转接；提示词要为听觉而写，如逐字读回 MC 号、用口语说价格。

要点

  • 语音实作无法隐藏缺陷，聊天习惯会失效。
  • 公开题目包括 HappyRobot 承运商销售、牙科提示词测试等。
  • 每轮对话应设延迟预算并记录 p50/p95。
  • 需处理打断、附和词与静默超时。
  • 工具失败要有重试与明确话术，并预设转人工条件。

为什么聊天习惯在电话通话中行不通

在通话中，一个项目符号列表、一个链接和三个选项会变成一大段来电者必须记住的话。需要改掉的四个习惯：

  • 过长的回合。 每个 Agent 回合只讲一个想法，最多提一个问题。来电者无法快速浏览。
  • 格式化。 Markdown、列表和 URL 会被念出来或被跳过。为耳朵而写提示词。
  • 轻信转录文本。 语音转文本会听错 ID 和数字。把 AI Agent 将要据此行动的任何内容都复述确认一遍，例如 MC 号码、日期或地址。
  • 数字当作文本。 模型写成数字形式的费率可能被念得很奇怪。告诉模型如何说出金额、日期和 ID，并进行测试。

以下是在承运商销售电话中的区别：

Chat habit:
  "Great! Here are 3 loads that match:
   1) Dallas to Atlanta, $1,850 ...
   2) ... Which would you like?"

Voice:
  "I've got a dry van out of Dallas going
   to Atlanta, picking up tomorrow morning.
   It pays eighteen fifty. Want to hear
   more on that one?"

语音版本只推销一票货物，像经纪人那样说出价格，并以一个是非问题收尾。在仅限提示词的测试中，评审者会想象它被念出来的样子来阅读你的提示词。

实战示例：错过预约的异议

hobbes3 简报中最难对付的来电者，是那些说自己从未预约过的患者。来源 2带回家的作业：语音 AI 提示词工程（PDF）发布方hobbes3（GitHub）来源类型候选人的带回家作业仓库 以下是我们为那一刻编写的提示词部分示例，专为耳朵而写：

If the patient says they never booked:
- Do not argue or cite records.
- Say: "That's alright, it may have
  been booked for you. Would you like
  to find a time that suits you now?"
- If they are still upset, apologize
  once, offer to remove them from
  reminders, and end the call kindly.
- Never repeat the missed date twice.

争论记录能赢得道理，却会输掉改期——而改期才是这通电话的真正目标。

延迟：为每一轮设定预算

在通话中，回复慢就是冷场，而对方会用说话盖过你 Agent 的回复来填补冷场。为单轮写下预算，并据此测量。

阶段示例预算
检测语音结束300 ms
最终转写150 ms
模型首 token400 ms
首段音频输出150 ms
单轮总计1000 ms

这些是我们的示例值，并非标准。关键在于每个阶段都有一个数字，而且你的提交日志能记录每一轮的时间花在哪里。

  • 全部流式处理。 在模型回复的第一句话上就开始语音合成，而不是等整个回复完成。
  • 保持热路径提示词简短。 它在每一轮都会消耗时间。
  • 在慢速工具调用前先说话。 如果一次查询可能耗时较长，Agent 应先说“我帮您查一下”，让沉默有理由。
  • 记录每个阶段的 p50 和 p95。 好看的平均值会掩盖让来电者陷入沉默的那一轮。

在评审时直说：“我的预算是每轮一秒。模型首 token 是最慢的阶段，所以我精简了提示词，并把货物详情移到了工具调用中。”

轮次切换、打断与沉默

来电者打断。 这就是插话（barge-in）。当来电者开始盖过 Agent 说话时，一旦确认这是真正的发言而非附和，就立即停止播放。然后修复容易遗漏的部分：对话历史必须只记录来电者实际听到的内容。否则模型会以为自己说过来电者从未听到的话。

def heard_text(words, played_ms):
    # words: [(word, end_ms)], grouped
    # from the TTS timestamps
    said = [w for w, end in words
            if end <= played_ms]
    return " ".join(said + ["[cut off]"])

将

heard_text

的结果存储为 Agent 的发言，而不是模型生成的文本。许多 TTS API 会返回每个字符的时间戳，所以要先将其归组为单词。在播放时测量

played_ms

，而不是在发送时：TTS 的进度领先于来电者的耳朵。OpenAI 的

Realtime API 
conversation.item.truncate
event

正是为此而存在的：音频已发送到客户端但尚未播放。

来电者说“嗯嗯”。 简短的附和不是打断。在停止播放前，要求最少词数（Pipecat 以

MinWordsUserTurnStartStrategy

的形式提供此功能），或忽略“嗯嗯”、“好的”、“行”等简短附和词列表，否则你的 Agent 会不断打断自己。

来电者沉默了。 设置一个沉默超时，例如

silence_timeout = 6s

。第一次超时，用一个简短的问题重新提示。第二次，礼貌地结束通话，并将该通话记录为放弃，而不是失败。

一个适合放入测试集的实用小场景：Agent 正在宣读货物的详情，承运商插话问“重量是多少？”，Agent 应该回答重量，而不是重新开始推销。

当工具调用在通话中途失败

上面的每个简报都依赖某个 API。当其中一个在通话中途失败时，Agent 会陷入沉默，或者更糟——装作成功继续进行，告诉承运商他们已通过验证，而实际上并没有。

为每个工具设置超时、一次重试，以及一个提示词知道如何处理的明确失败结果：

import asyncio, random

async def verify_carrier(mc, lookup,
                         timeout=1.5):
    for attempt in range(2):
        try:
            return await asyncio.wait_for(
                lookup(mc), timeout)
        except Exception:
            if attempt == 0:
                await asyncio.sleep(
                    random.uniform(0.1, 0.4))
    return {"status": "unverified"}

我们针对四个模拟查询进行了测试：一个先挂起一次然后返回结果，一个拒绝连接，一个始终挂起，还有一个返回 HTTP 500 错误。它返回记录，然后

unverified

三次。最坏情况刚好超过三秒，所以 Agent 在调用此工具前会说“让我查一下您的 MC 号”。我们在

retrying with exponential backoff and jitter

中讨论了为什么抖动很重要。

然后在提示词中决定，当结果是

unverified

时 Agent 该说什么。例如：“我现在无法确认您的运营资质。我可以安排经纪人在一小时内给您回电。哪个号码最方便？”绝不要让模型即兴发挥验证流程。

在你的文档中也要列出这些失败模式：

  • 重复预订。 如果 HVAC 预订电话超时，预订可能实际上已经成功。如果预订 API 接受幂等键，就发送一个，这样重试就不会创建第二个预约；如果不接受，在重试前先查询来电者的预订记录，并在文档中说明。
  • 错误输入。 听错的 MC 号会返回“未找到”。在判定承运商不合格之前，Agent 应该复述号码并再次确认。

我们关于标注假设并呈现失败模式的课程展示了如何呈现这份清单。

转接给人工

在构建之前先确定转接触发条件：

  • 来电者要求与人工交谈。第一次就照办。
  • Agent 已经两次未能理解同一件事。
  • 请求超出了 Agent 的职责范围：超出谈判上限的反报价，或律所接待中的法律建议。
  • 安全问题。提到闻到燃气味的 HVAC 来电者应收到预设的安全提示并转接人工，而不是预订时段。

做成温馨转接：给人工坐席一份简短摘要，让来电者不必重复自己。例如：“承运商已验证，对达拉斯货源感兴趣，还价两次，要价超出我们的承受范围。”如果没有人可用，记录回电号码。在演示中展示一次转接：这证明你考虑到了客户的员工，而不仅仅是模型。

指标仪表盘和演示

IanDalton 的 HappyRobot 任务要求你自建一个仪表盘，以评估“产品视野”。来源 1FDE 技术挑战：入站承运商销售（PDF）发布者IanDalton（GitHub）来源类型候选人的课后作业仓库 所以要为运营台的人而建，而不是为你自己。我们关于利益相关者与成功指标的课程讲解了如何选择指标。经纪人的视图可能显示：

  • 按结果分类的通话：已预订、无匹配货源、承运商不合格、转接人工、放弃。
  • 谈判：成交价与挂牌价的对比，以及经过多少轮谈判。
  • 按结果分类的情绪分析，以便及早发现不良趋势。
  • 健康状况：p95 轮次延迟、工具错误率和转接率。

最后一组是工程师需要负责的内容。我们关于为 AI 助手定义 SLO 的问题会将其转化为你可以辩护的目标。

  • 在 Agent 说话时说“嗯哼”的来电者
  • 沉默不语的来电者
  • 需要复述确认的听错的 ID
  • 主 API 超时
  • 要求转接人工
  • Agent 必须拒绝的请求

逐一运行，保留录音，并展示结果。我们关于为支持型 Agent 设计评测框架 的问题展示了如何将这些通话转化为可重复的测试套件，而如何知道你的 AI 系统有效 则更深入地探讨评测。

对于视频，先展示一段真实通话，然后展示仪表盘，再展示一个处理得当的失败案例。说明如果再有一周你会做什么。从小处着手：一个能端到端处理一通电话的行走骨架，胜过一个从未接过电话的精明谈判引擎。
