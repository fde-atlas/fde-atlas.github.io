网站漏洞诊断的工作通常只到发现网站的漏洞为止，一般不包含修复工作。IPA（信息处理推进机构）也明确指出，即使诊断未发现漏洞，也不能说就是安全的。因此在委托诊断之前，应先确定由谁来修复报告中的问题。本文面向正在寻找诊断外包服务商的委托方，不涉及诊断工具的产品比较。

漏洞是指程序或配置中的缺陷中，可能被攻击者利用而导致信息泄露或篡改的漏洞。网站漏洞诊断是一项在指定范围内排查网站是否残留此类漏洞并汇总成报告书的服务。对于网站而言，“安全诊断”这一叫法也常被用于同一含义。例如，检查在输入框中输入恶意字符串能否窃取数据库内容（SQL注入）、能否在他人浏览器中擅自执行处理（跨站脚本）。

根据方式不同，诊断可分为以下3类。

ツール診断手動診断ペネトレーションテスト
内容专用软件自动进行检查（也称为漏洞扫描）诊断技术人员根据页面操作手动测试扮演攻击者尝试入侵，确认危害能扩散到什么程度
适用场景想先大范围确认时想检查登录后的功能或复杂页面操作时想确认处理重要信息的整个系统的防护时
弱点容易遗漏与页面流程相关的缺陷费用上升，耗时也更长费用往往最高
公开价格示例全年不限次数36.3万日元（含税）仅人工诊断每次请求5.5万日元（含税）100万日元起

“弱点”一行是各方法的普遍特性。价格的出处与税务区分汇总于第4章。

在外包之前，有3项可以自行确认的事项。提前掌握这些情况，有助于更顺利地撰写询价项目（第6章）。

・列出网站运行所用的软件清单（CMS、插件、服务器OS），检查是否存在旧版本 ・检查是否有未使用的页面或网站仍处于公开状态（若放任不管，即使发现漏洞也可能无暇处理） ・检查通信是否加密（HTTPS）、登录密码是否容易被猜到

IPA的《安全网站运营管理20条》公开了包含上述内容的20项检查清单（出处：IPA《安全网站运营管理20条》）。同一资料还建议在外部机构诊断后仍应定期持续进行。自行检查的作用是减少问题产生的入口。由于不能替代诊断，处理个人信息或支付业务的网站建议考虑外包。

IPA的《网站健康诊断规范》是一份汇总了13项基本检查模式的资料。该资料写明，即使诊断未发现漏洞，也不能据此宣布安全（出处：IPA《安全网站的构建方法》）。当免费工具或简易诊断显示“无问题”时，也应按同样的含义理解。

诊断的内容因“检查什么”而异。在获取报价之前，应先确定本公司的委托属于哪一类。

Webサイト・Webアプリ診断ネットワーク診断(プラットフォーム診断)WordPress診断
检查对象页面、输入框、登录、URL服务器及网络设备开放的入口（端口）、OS与软件版本本体、主题、插件的状态以及自行添加的定制程序
主要指摘对恶意输入的脆弱性、登录与权限的缺陷旧版本、不必要的开放入口、配置缺陷未更新的组件、存在已知漏洞的组件
费用计算方式页面数、画面数、请求数IP地址（IP）数量取决于诊断内容（仅确认组件的简易诊断也有较便宜的例子）

请求是指在页面上点击按钮等向网站发送的一次通信。各公司在费用上按“页面”还是按“请求”计算有所不同。

通过画面和输入栏检查漏洞的诊断，一般所说的“网站漏洞诊断”就是指这个。IPA 的网站健康诊断规范列出了 13 个项目，包括 SQL 注入、跨站脚本，以及认证（登录）、会话管理（登录状态的保持方式）、授权控制（登录后权限的划分方式）的缺陷等。诊断需要登录的画面时，需要准备用于诊断的账号。さくらのサイバーセキュリティ的诊断工具规定，每次诊断中需要登录的位置为 1 处。需要认证的画面较多的网站，应确认报价的前提条件。

网络诊断是检查放置网站的服务器和网络设备本身。即使网站程序没有漏洞，如果服务器操作系统老旧，也可能从这里被入侵。开源的诊断软件有 OpenVAS 等，用于自动检查服务器的老旧程度和配置缺陷。外包时的价格多以 IP 地址数量决定。公开价格方面，ABURIDA 为每个 IP 4 万日元（含税 4.4 万日元），Cyber Security Cloud 为 5 个 IP 起 35 万日元（不含税）。

WordPress 由本体、主题、插件这些他人制作的部件集合构成。因此诊断的重点是确认部件版本是否老旧、是否含有存在已知漏洞的部件。自行添加的程序以及咨询表单等输入栏，则采用与网站诊断相同的方法进行检查。委托诊断公司时，应告知是 WordPress 以及所使用插件的数量。诊断中被指出的部件更新或更换，可能会影响网站的运行，因此需要有人负责修复，这一点将在第 5 章讨论。在本次确认的公开页面中未找到 WordPress 专用诊断的价格表。费用取决于诊断内容，仅确认部件的简易诊断有便宜的例子，而如果要检查到自行添加的程序，则与网站诊断一样按页面数量等进行报价。

选择委托方的判断标准如下。

・有自家的程序或画面（登录、咨询表单、会员页面）→ 网站诊断 ・服务器的操作系统或配置由自家或委托方管理 → 也纳入网络诊断 ・使用 WordPress 且自行添加的程序较少 → 以确认部件更新状况为主。如有自行添加的程序或表单，该部分通过网站诊断检查 ・不清楚属于哪种 → 在报价委托中写明网站构成（CMS 类型、服务器管理员）进行咨询

诊断服务可分为以下 4 种类型。区别不在于诊断的方法，而在于“发现之后，由谁负责修复到完成”。

诊断仅自动（也有包含手动的产品）可选择包含手动的方式仅限软件覆盖的范围与诊断公司合作或自行进行
修复自家原则上由自家（也有公司提供修复咨询）自家也有包含在范围内的合同

适合场景日常简易确认、发布前确认需要向交易方提交报告书时、重要网站开发力量雄厚的公司诊断后公司内部没有修复人员的公司

费用倾向在第 4 章所列公开价格的范围内。FDE 型因诊断范围和修复范围不同金额会变化，因此无法以公开价格展示。诊断后希望连修复一起委托时，可在报价委托中询问诊断公司是否提供“修复支援”，或咨询 FDE 型。修复后仍需持续的维护管理并外包时，漏洞管理服务的比较与选择方法中对这 4 种类型进行了比较。

使用开源免费工具（ZAP（旧称 OWASP ZAP）、OpenVAS 等）也可以诊断网站或服务器。其优势在于不产生费用，但由于诊断成为自家的工作，配置、执行时间的调整、结果的解读、误报的甄别都留在自家。IPA 对 3 种检查网站漏洞的开源工具进行了评估，并在报告中总结了其特点和使用时的注意事项。免费工具适合自家有开发负责人、能够解读结果并进行修复的情况。由不了解结果解读方法的负责人使用时，容易变成“指出的问题太多无从下手”或“没有指出问题所以安全”这两种情况之一。

从表格中可以读出以下3个趋势。

・工具诊断约为十几万至数十万日元，包含人工的诊断约为数十万至一百数十万日元 ・影响金额的主要因素是页面（画面）数、请求数、IP数量 ・“最多多少页面”“最多多少请求”各服务商不同，只比较总价会导致误判

即使页面数相同，需要登录的画面数量、有无报告会、再诊断的条件也会使最终金额不同。 例如，同样是10页以内的“自动+人工”，Cyber Business为20万日元，CEC为75万日元起，公开价格相差3倍以上。 页面和请求的计算方式不同，因此与ABURIDA（10个请求44万日元）无法简单比较。 如果不以相同的前提向多家公司询价，就无法进行比较。

从公开价格中可以读出3个适用于自身情况的参考标准（仅为对表格价格的解读，并非报价）。

・10页左右的公司网站，先用自动方式检查 → 工具诊断12.1万至36.3万日元（含税。Sakura、ITM） ・10页左右，想加入人工检查 → 从20万日元（Cyber Business）到75万日元起（CEC），各公司差距较大 ・有登录功能的网站（会员页面、EC） → 有以诊断1次包含1个需登录处为例的情况（Sakura），登录画面数量可能产生额外费用，因此报价时应告知画面数量

公开价格是诊断和报告书的费用。 修复发现的漏洞的费用，大多数情况下不包含在内。 公布修复费用的公司，在表中8家公司的公开页面上均未找到。 再诊断有条件免费的情况。CEC规定自动诊断的再诊断在诊断后3个月内免费，ABURIDA也规定危险度为中（Medium）以上的指摘在3个月内的再诊断免费。 但再诊断只是“确认是否修复”，并非修复工作本身。 修复费用需根据第5章所述的修复承担方另行报价。

诊断结束后，会收到附有危险度评级的指摘以及修复方法建议的报告书。 此后的工作就超出了诊断服务的范围。 如果没有确定修复指摘的人，报告书就会一直留在共享文件夹中无人查看，漏洞依然存在。 IPA也建议在确认Web健康诊断的结果后，接受更详细的诊断或实施对策。

修复报告书指摘的人，将是以下4种之一。

修复方适用的场景事先确认的事项
自公司开发负责人公司内有能修改代码的人相对于指摘的数量，能否安排出修复时间
制作网站的制作公司、开发公司制作方目前仍在合同期内是否能在维护范围内承接修复诊断指摘的工作（是否另行收费）
诊断公司的修复支援诊断公司也提供修复咨询是仅到“报告书讲解”，还是到“代码修复”
FDE型（进入现场的工程师）公司内无人修复，与制作公司也已断绝联系如何划分诊断范围与修复范围来签订合同

诊断公司的“报告会”是讲解报告书内容的场合，并非修复本身。 ABURIDA的报告会为每次15万日元（含税16.5万日元）的另行收费，不包含在诊断价格中。 如果尚未确定修复承担方，在询价时询问“能否委托到修复为止”，可以减少之后重新寻找的麻烦。 FDE型的费用因诊断范围和修复范围而异，需单独报价。 DeFactory情况下的流程写在5-4中。

再诊断是在修复之后确认“漏洞是否已堵上”的诊断。 在未修复的状态下接受再诊断，只会得到相同的指摘。 顺序是“诊断 → 修复 → 再诊断确认”，应在签订合同前确定由谁承担修复阶段。

改变画面结构的大规模修复、需要与制作公司协调的修复，即使发现了漏洞也可能无法立即完成。 IPA的20条守则中，作为无法及时修复Web应用时的对策，将引入WAF（Web应用防火墙，检测并阻断非法通信的机制）等以减少修复前影响的方法列为“有效手段之一”。 ABURIDA也说明在发布前无法修复时会建议引入WAF。 WAF不是消除漏洞的手段，而是减少修复前损害的手段。 引入过渡性对策后，仍需确定修复承担方和期限。

以DeFactory为例说明委托FDE型的流程（来自其公司公开页面的内容）。 ・诊断后，结合对业务的影响，共同决定报告书指摘中哪些先修复、哪些延后 ・进入现场修改代码，并将修复方法移交给公司内部成员（通过结对编程进行技术转移） ・合同为准委托（致力于解决问题的形式），基本为3个月。费用因诊断和修复范围而异，需单独报价 ・咨询入口为免费的访谈（约1小时）。访谈后5个工作日内提出方案，达成一致后，大约2周内启动 即使问题尚未整理清楚也可以咨询。 咨询通过DeFactory的FDE支援受理。

选择时，请依次确认以下6点。

  • 诊断对象和方法是否适合本公司。 统一确定检查Web网站、网络、WordPress中的哪一个，用工具还是人工（1-1、第2章）
  • 报价的前提是否一致。 统一页面数、请求数、IP数量以及含税还是不含税后进行比较（第4章）
  • 能否看懂报告书的内容。 通过样本确认是否有危险度评级方法、复现步骤、修复方法的记载
  • 是否有报告会及答疑支持。 确认有无报告会及其费用、诊断后答疑的受理期限
  • 诊断后的修复和再诊断能委托到什么程度。 确认修复支援的范围、再诊断的免费条件和期限（第5章）
  • 诊断的影响以及事先手续是否明确。 确认是在正式网站上诊断，还是在诊断用环境中进行。IPA的Web健康诊断规范（出处）指出，诊断可能导致网站停止运行或注册了意外的数据，因此要求事先获得服务器或数据中心管理员的许可

委托报价时，应写明以下项目。这样可以减少诊断公司重新确认前提条件的麻烦，也更容易比较返回的报价金额。

・诊断对象（网站URL、网络IP地址数量、是否有WordPress及插件数量） ・页面数、需要登录的页面数、表单数 ・希望的诊断方式（仅工具、包含手动） ・进行诊断的环境（正式环境、诊断用环境）及希望的时间 ・报告书的提交对象（自用、提交给交易对象用）及是否需要报告会 ・是否希望委托到修复为止，还是仅诊断 ・再诊断的条件（次数、期间、费用） ・标注含税还是不含税

在诊断之前，还需确认是否需要通知托管公司或云服务的管理员将进行诊断。关于修复的咨询，可参考FDE企业的比较与选择方法，比较承担修复工作的外包商类型。
