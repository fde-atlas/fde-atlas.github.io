摘要

这篇来自 FDE Jobs 的日文指南面向想转任前沿部署工程师（FDE）的职场人，按出身职种给出转型路线图。文章认为完全零经验直接转岗很难，但相邻职种转型现实可行，因为 FDE 人才池小、各公司积极进行潜力型招聘。核心前提是已具备实现经验或客户对接经验之一，SIer 与售前工程师出身者最有优势。最有说服力的实绩是项目不止于试点，而是投入生产并被客户实际使用，且能用前后对比的定量数据呈现。文章还给出技能清单（Python、LLM/RAG、系统集成、需求定义、客户沟通）、约 6 至 13 个月的学习计划，以及应对职位名称混乱（FDE／SE／AI 导入／CE／DS）的求职策略。

要点

  • 转型前提：已有实现经验或客户对接经验之一。
  • SIer、售前工程师出身最易转型；纯工程师需补客户沟通。
  • 最有价值的实绩是生产环境落地并被客户使用，附定量成果。
  • 必备技能：Python、LLM/RAG、系统集成、需求定义、客户沟通。
  • 求职需横跨 FDE／SE／AI 导入／CE／DS 等多种职位名称检索。

零经验能否成为FDE：结论

直接说结论：“完全零经验（既无实现经验也无客户对接经验）”直接转型很难，但从相邻职种转型是完全现实可行的。FDE（前沿部署工程师）是出现时间较短的职种，人才池较小，各公司都在扩大潜力招聘的名额。这里的“零经验”指的是“从未担任过FDE这一头衔”，如果有软件工程师、SIer、售前工程师、咨询、客户成功等实务经验，那就是很好的基础。

FDE的本质在于“既能亲自实现，又能将客户的业务课题结构化并推动落地”。因此被要求的前提是，已经拥有“实现经验”或“客户对接经验”其中之一。两者兼备最理想，但即使只有其中一项，只要计划性地补足不足的另一项，也能达到目标。职种本身的定义详见什么是FDE，与相邻职种的区别详见FDE与软件工程师的区别、FDE与咨询顾问的区别。

所需前提：实现经验或客户对接经验二者其一

FDE是靠“技术实现能力”和“客户对接能力”两个轮子支撑的职种。零经验起步时首先要做的，是准确把握自己已经拥有哪个轮子、缺少哪个轮子。如果两者都从零同时积累，会走弯路。以优势为立足点，用最短路径补足不足，才是标准做法。所需技能的全貌已整理在FDE所需的技能中。

实现经验：能否亲自做出可运行的东西

FDE不是“写设计文档让别人去做”，而是在客户现场亲自写代码、连接API、交付可运行的产品。比起华丽的架构，更被要求的是“总之要能跑起来”的实现能力。用Python等做过简单工具的经验、搭建过业务系统的经验、个人开发中做过API对接的经验——无论形式如何，只要有“亲自从零完成可运行产品”的经历，就构成了实现经验的基础。如果完全没有实现经验，就先从这里着手。

客户对接经验：能否将课题结构化并达成共识

FDE要倾听客户模糊的需求，将真正的课题结构化，排定优先级，取得相关人员的共识并向前推进。提案、需求定义、沟通谈判、期望值管理、进度汇报——这些经验在销售、咨询、售前、客户成功、外包开发的现场都能自然积累。“懂技术但从未与公司外部的人打过交道”的纯技术工程师，这里就是最大的成长空间。

推动业务的当事人意识：能否对成果负责

FDE与其他工程师职种的决定性区别在于，评价标准不是“是否做出来了”，而是“是否被使用、是否产生了成果”。让导入在现场落地生根，对客户的业务指标或销售额产生变化负责到底的当事人意识——这不是头衔问题而是态度问题，即使是零经验，从今天起也可以培养。面试中也会重点考察这种当事人意识（参考：FDE面试常见问题）。

自我诊断：你的哪个轮子更强

请试着写下两个问题的答案：“最近自己投入最多动手的成果是什么”“与公司外部或其他部门的人达成共识的经验有多少”。前者更丰富，说明实现是优势（不足是客户对接）；后者更丰富，说明客户对接是优势（不足是实现）。这个诊断将成为下一章按出身职种划分的路线图中，你选择哪条路径的起点。

按出身职种划分的路线图

以现有职业优势为基础，补足不足要素，是最短的路径。这里针对6个代表性出身职种，分别说明其优势、不足和具体对策。请从与自己最接近的职种开始阅读。无论哪个职种，共同的达成目标是“做出不止步于PoC、投入生产环境并被客户（内部客户也可以）实际使用的成绩”。

从软件工程师转型：积累客户对接的经验

优势在于实现能力。不足是客户沟通与需求定义。最短的路径是，把公司内部其他部门当作“内部客户”，练习倾听需求、定义需求、制作工具并让他们使用，并跟进到落地扎根为止，积累这样的经验。主动争取有客户对接的项目或陪同售前也很有效。技术方面，如果能在个人开发中掌握 LLM API 的使用和 RAG 的构建，即战力会大幅提升。只要填补“会写代码但缺乏面对客户的经验”这一短板，就能成为最接近 FDE 的人才之一。关于区别的整理，请参阅FDE 与软件工程师的区别。

从 SIer・SE 转型：叠加产品思维与 AI 技能

这一群体兼具客户对接与实现两方面的基础，是最容易转型的群体。需求定义、客户沟通、系统集成、现场落地——这些 FDE 的日常工作他们已经经历过。需要补足的是两点：(1) 从外包思维（按吩咐做东西）切换到自研产品思维（用产品创造价值），(2) 叠加 AI/LLM 技能。补上这些，就能成为既懂技术又懂客户的强力候选人。关键在于能否把 SIer 文化的“瀑布式、多层转包”思维，升级为产品企业的“快速发布、快速验证”思维。

从售前工程师转型：补足实现能力

在客户面前做演示、解答技术疑问、用技术支撑提案——售前工程师的经验与 FDE 的客户对接能力几乎直接相通。不足的是“签约后自己动手做出来并跑起来”的实现能力。很多情况是能做演示，但缺乏生产环境实现的经验，因此要用 Python、API 集成、LLM 应用，做出哪怕很小的、由自己完整完成的产品。从售前（卖之前）到 FDE（卖之后做出来并交付）的角色深化转型，近年来尤其增多。职位名称的相近性也可参考解决方案工程师招聘页面。

从咨询・售前转型：在问题定义与实现之间架桥

问题结构化、假设构建、相关方协调、向管理层提案是优势。学习欠缺的实现能力（Python、API、LLM），并做出哪怕很小的、自己能跑起来的成果，就能成为“既能讲战略又能动手”的稀缺人才。咨询往往扮演“提案后离开”的角色，而 FDE 的不同之处在于“自己把提案做出来，并跟进到落地扎根为止”。理解这一区别，能否跨越实现的鸿沟就是分水岭。详情请参阅FDE 与咨询顾问的区别。

从客户成功转型：加深技术深度

与客户持续同行、扩大使用、防止流失——客户成功的经验与 FDE“让产品在导入后被持续使用”的角色非常接近。不足的是技术深度。从产品配置修改的层面再进一步，能够自己实现 API 集成、数据整合、基于 LLM 的功能扩展，就能跨越 CS 与 FDE 的边界。课题是填补“比任何人都了解客户业务，但自己无法实现”的短板。导入后扩大使用（扩展）的思路，可以直接成为 FDE 的评价标准。

从基础设施・数据岗位转型：扩展到客户沟通与应用实现

基础设施工程师、SRE、数据工程师已经具备云、数据管道、运维这些生成 AI 导入中必备的基础能力。RAG 和 LLM 应用归根结底是由数据整备与运维决定成败的，因此这一基础非常有力。不足的是两点：(1) 应用层与 LLM 应用的实现，(2) 在客户面前倾听问题并达成共识的经验。如果能从幕后角色迈出一步，走向“到客户现场交付价值”的角色，就能建立起擅长数据的 FDE 这一独特定位。

需要掌握的技能：技术与人际的双轮驱动

FDE 所需的技能是“技术技能”与“人际・商业技能”的双轮驱动。从零经验切入的话，优先补足自己欠缺的那一侧。这里讲解尤其需要掌握的 5 个领域。完整清单请参阅FDE 所需的技能。

Python・API 集成（实现的基础）

FDE 实现语言的核心是 Python。因为生成 AI 生态系统（LLM 库、数据处理、自动化）在 Python 中最为完善，首先要能用 Python 编写脚本、调用外部 API 获取并加工数据、返回结果，把这一整套流程亲手做出来。此外，如果能做到使用 REST/Webhook 与其他系统集成、掌握云（AWS/GCP/Azure）基础、Git 以及简单的部署，就具备了在客户环境中“总之先跑起来”的 FDE 基础实力。

LLM・RAG・评测（Eval）设计

在生成 AI 领域的 FDE 中，这一领域的市场价值最高。包括使用 LLM API 构建应用、实现让模型参考公司内部数据的 RAG（检索增强生成）、提示词设计，以及衡量输出质量的评测（Eval）设计。尤其是 RAG 与评测，是解决“PoC 能跑但生产环境质量不达标”的核心，能实现这一点就会迅速成为稀缺人才。理解 LLM 的实现模式与局限，最快捷的方式是通过各家公司的官方文档（OpenAI / Anthropic 等）加上自己动手验证来深入。关于 PoC 为何在生产环境失败，为什么 AI 的 PoC 在生产环境会失败中有详细总结。

系统集成・数据集成

将 AI 与客户现有系统（核心业务系统、CRM、数据库、各类 SaaS）对接的集成能力，在 FDE 的实际工作中经常被考验。数据的获取、清洗、对接，认证与权限的处理，嵌入现有工作流——这项技能就是填补“在自家封闭环境中运行的演示”与“在客户复杂生产环境中运行的系统”之间的差距。在生成 AI 导入的现场，实际情况是大部分时间都花在 AI 模型本身的周边集成与数据整备上，而非模型本身。

需求定义・问题结构化

客户往往带着“想用 AI 做点什么”这种模糊的状态前来。FDE 要从中挖掘出真正应该解决的问题，进行结构化、排定优先级，并落实到可实现的范围内。FDE 的上游不是“按吩咐做东西”，而是“定义应该做的东西”。理解客户的业务流程，判断 AI 在哪些地方有效、哪些地方无效，并就现实的范围达成共识——这种上游能力在很大程度上决定了能否在生产环境中创造价值。

客户沟通・期望值管理・英语

与相关方访谈、调整期望值、共享进度、出现问题时进行说明，以及向管理层用语言表达价值。FDE 需要具备将技术翻译成“业务语言”并传达的能力。既然生成式 AI 并非万能，坦诚地说明“能做什么、不能做什么”以建立信任的诚实态度也很重要。此外，如果目标是外资 AI 企业，英语能力会大幅拓宽可应聘的职位和薪资范围（参考：FDE 是否需要英语能力）。由于工作以与本国团队沟通和阅读文档为主，先从读写开始就足够了。

打造被认可实绩的方法：不要止步于 PoC

FDE 招聘中最受认可的不是头衔或证书，而是“不止步于 PoC（概念验证），而是投入生产环境、被客户实际使用并取得成果”的实绩。反过来说，即使是零经验，只要能做出一个这种形式的实绩，选拔就会大幅前进。重要的不是“做了”，而是“被使用了，业务或数字发生了变化”。面向内部客户（本部门或其他部门）也可以，副业或个人开发也没问题。

案例分析的条目记载内容
课题客户／现场面临的业务课题（为什么困扰）
自己的负责范围需求定义／实现／集成／落地中负责了哪些部分、到什么程度
解决方案用什么技术、设计解决的（LLM、RAG、集成等）
成果用定量方式表达（工时削减、使用率、销售额、响应时间）
生产落地是否不是昙花一现而是持续被使用、是否持续改进

参与到生产投入与落地

演示和 PoC 只能证明“能做出来”。FDE 的价值在于“在生产环境中运行、在现场落地、持续改进”。如果职场有机会，请主动承担把停留在 PoC 阶段的项目推进到生产投入的角色。如果没有机会，可以选择一项公司内部的重复性工作，用 AI 实现自动化让同事使用，接受反馈并改进——即使是这个小循环，也是“生产投入、落地”的体验。

用定量方式讲述成果

“变得方便了”说服力很弱，而“把每月耗时◯小时的工作削减了约◯%”“将咨询一线处理的◯%自动化”这样用定量方式讲述，说服力有天壤之别。从打造实绩的阶段开始，就要记录 Before/After 的数值。注意保密，对外讲述时隐去具体名称，用比例和规模感来表达（例如：在制造业将技术文档检索的工时削减约三成）。这种量化也可以直接成为年薪谈判的武器（参考：FDE 的年薪行情）。

通过内部客户、副业打造“面对客户”的经历

即使跳槽前没有外部客户的项目，也可以把其他部门当作客户，打造面对客户的实绩。访谈销售部的重复性工作、定义需求、开发工具并导入、陪伴到落地——这正是 FDE 工作的缩影。通过副业、外包完成一个小型 AI 导入项目也很有效。“访谈→需求→实现→落地→成果”的完整循环哪怕只经历过一次，也是面试中最能讲述的素材。

把失败中的学习也变成资产

FDE 的现场就是一连串的不如意。“最初的方法不适合现场而重做”“精度不达标，从评估设计重新审视”这类失败与调整方向的故事，会作为主人翁意识和解决问题能力的证明而受到高度评价。比起漂亮的成功故事，能讲述挫折及从中学到东西的人，更容易被判断为能在现场创造价值。

作品集的制作方法

做出实绩后，要把它整理成招聘负责人能理解的形式。FDE 的作品集不是展示“代码量”，而是展示“如何结构化客户课题、如何实现、取得了什么成果”的故事。要采用能同时传达技术能力和业务贡献的结构。详细的制作方法整理在 FDE 作品集的制作方法 中。

用案例分析的形式整理

把上一章的表格（课题→负责范围→解决方案→成果→落地）直接作为各项目的模板。理想状态是每个项目一页，让读者在 30 秒内抓住“解决了什么”。不要只停留在技术说明，一定要以“客户／现场变得如何更好”为主角。招聘 FDE 的企业想看的不是技术的炫目，而是“解决业务课题的实绩”。

公开“能运行的小型”代码

在 GitHub 等平台公开使用 LLM/RAG 的、虽小但完整的项目，会成为实现能力的客观证据。不需要大规模，“通过 API 集成用 RAG 检索公司内部文档”“总结会议纪要并提取要点”这类贴近实务的能运行的东西就很有效。在 README 中写上“解决什么问题、如何实现、有什么巧思”，这本身就成了一个迷你案例分析。

附上成果指标和业务背景

不要只罗列技术栈，一定要附上“为谁、解决了什么课题、改善了多少”的业务背景。涉及保密的数值用比例和规模感表达。FDE 是将技术翻译为业务价值的职位，所以作品集本身就成为这种翻译能力的示范。比起项目规模，“课题设定的敏锐度”和“成果的讲述方式”更受评价。

串联“为什么选择 FDE”的故事

在作品集开头，写上自己出身职位的优势，以及如何将其运用到 FDE 的一贯故事。像“在 SIer 磨炼了面对客户和需求定义的能力，自学补充了生成式 AI 的实现能力，做出了生产投入的实绩”这样，把点（实绩）用线（职业故事）串联起来，招聘负责人就容易想象“这个人在 FDE 岗位上会成长”。

求职方法：攻克职位名称的混乱

寻找 FDE 时最大的陷阱是职位名称的混乱。同样是“在客户现场实现 AI 并使其落地”的工作，各企业的叫法五花八门，只搜索“FDE”会错过很多好条件的职位。把下表中的所有称呼都纳入搜索范围是铁则。在本站的职位列表中，可以跨职位搜索这些客户驻场型 AI 实现职位。

职位名称的混乱：FDE／SE／AI 导入／CE／DS

主要称呼如下：①Forward Deployed Engineer（FDE）＝前沿部署工程师招聘，②解决方案工程师（SE）＝解决方案工程师招聘，③AI导入工程师＝AI导入工程师招聘，④客户工程师（CE）＝客户工程师招聘，⑤部署策略师（DS）＝部署策略师招聘，⑥专业服务＝专业服务招聘。称呼虽不同，但工作核心相近，需通过招聘启事的内容（客户现场、实现、落地）来判断。

通过招聘启事的内容来判断

不要被头衔迷惑，要仔细阅读职责内容。识别FDE类招聘的方法是看是否同时满足以下4点：(1) 深入客户／用户现场，(2) 亲自进行实现（不只是设计），(3) 负责的不仅是PoC，而是到正式上线与落地为止，(4) 对客户的事业成果负责。反之，如果“仅做设计”“以陪同销售为主”“以维护运维为中心”，则与FDE的角色不同。各职种指南请参见什么是解决方案工程师、什么是AI导入工程师、什么是客户工程师、什么是部署策略师、什么是专业服务。

了解招聘的企业类型

招聘FDE型人才的企业有5类：(1) 外资顶级AI企业（Palantir、OpenAI、Anthropic等），(2) 外资SaaS日本法人，(3) 国内AI初创公司，(4) SIer／咨询公司的AI部门，(5) 事业公司的AI自研部门。无经验的潜力招聘名额，尤其容易在初创公司和SIer／咨询公司的AI部门找到。招聘动向可通过招聘FDE的企业确认，各企业招聘可通过按招聘企业分类的职位查看。

搜索渠道与定期观察

可同时利用各公司官方招聘页面（Palantir／OpenAI／Anthropic等的Careers）、AI／工程师专用招聘平台，以及FDE专用的本站FDE招聘 综合。由于FDE职位的流动很快，定期观察非常重要。远程办公、全国招聘的职位也很多，居住在地方也能应聘的岗位正在增加。对感兴趣的企业请收藏书签，以免错过招聘的时机。

判断“欢迎无经验”与潜力招聘

由于FDE人才储备较小，各公司都积极进行潜力招聘，即录用“现在虽不完美但有成长潜力的人”。想从无经验切入的话，识别这类名额并投递，能提高成功率。但另一方面，有些职位虽然宣称“欢迎无经验”，实际却并非如此，因此保持辨别力非常重要。

潜力招聘的信号

“实现经验或客户对接经验任一必备”“欢迎条件中包含LLM/RAG”“入职后培训与入职引导完善”“欢迎从相邻职种转型”等描述，都是积极进行潜力招聘的信号。反之，如果写着“FDE经验◯年以上必备”“只要即战力”，则对无经验者难度较高。要区分欢迎条件和必备条件，从能满足大部分必备条件的职位入手，才是现实的策略。

用“桥梁”来讲述自己的优势

潜力招聘中受到评价的，是能否用出身职种的优势来衔接“虽无FDE经验，但为什么自己适合这个岗位”。例如“在SIer做了◯年需求定义和客户交涉，此外自学掌握了LLM实现并投入生产”，像这样把既有优势＋补足的要素＋实绩三点串联起来讲述，招聘方就能具体地想象你的成长空间。

避开“欢迎无经验”的陷阱

有些职位虽然“欢迎无经验”，但实际只是单纯的运维、测试或陪同销售，既无法实现也无法解决客户课题。请在面试中具体确认入职后是否有作为FDE进行实现和正式上线的机会。询问“最初半年会交给什么样的项目”“以PoC结束的项目和推进到正式上线的项目的比例”，就能看清实际情况。

第一家公司选择“能积累经验的环境”

从无经验开始的第一家公司，比起年薪，选择“能否积累FDE实绩”在长期上更为划算。如果正式上线项目多、能放手让你实现、能从前辈FDE身上学习，那么1〜2年内市场价值就会大幅提升。只要最初做出实绩，之后的年薪和职位自然会随之而来（参考：FDE的职业路径、FDE的一天工作）。

面试对策：考察什么

FDE的面试不仅考察技术能力，还考察“如何解决客户课题”的思考过程，以及对成果的主人翁意识。对于无经验者的应聘，尤其重要的是能否一贯地讲述“为什么选择FDE”“如何发挥自己的优势”。常见问题与回答的构建方式在FDE面试常见问题中有详细总结。

案例・技术课题：展示思考过程

有时会出“某客户面临这样的课题，如何解决”的案例题，或简单的实现课题。被评价的不是正确答案本身，而是将课题结构化、确认前提、落实到现实范围的思考过程。能够反问“首先应该确认什么”的态度，就是现场客户对接能力的证明。

实绩深挖：用STAR法量化讲述

当被问到“最有成果的项目是哪个”时，按情境、课题、行动、结果（STAR）的顺序，结合量化数据讲述。务必包含正式上线、落地、成果三点，并明确自己的负责范围。当被问到从失败中学到什么时，诚实地讲述调整方向的故事，能传达出主人翁意识。前面章节制作的实绩和作品集可以直接作为素材。

一贯地讲述“为什么选择FDE”

这是无经验应聘中最受考察的一点。请准备好能一条线讲清：出身职种的优势→被FDE吸引的理由→为此所做的努力→今后想如何贡献。“技术和客户都想兼顾”这一动机，正与FDE的本质一致。在理解应聘方的事业和产品的基础上，深入到“如果是自己能解决什么”，会留下强烈印象。

通过反问展示主人翁意识

面试最后的反问环节，是展示主人翁意识的绝佳机会。“入职后最初会负责什么项目”“以PoC结束的项目和正式上线项目的比例”“FDE的成果如何被评价”等深入现场和成果的问题会留下好印象。不仅关注待遇条件，而是带着“确认自己能创造什么价值”的态度，这本身就传达出了FDE的特质。

学习路线图（时间参考）

下面为零经验者以 FDE 为目标的学习计划，并附上各阶段的大致时长。以下时长仅为参考，会因出身职业和可用于学习的时间而前后浮动。SIer、SE 出身等有基础的人可以缩短，完全跨行业的人（包括实现学习在内）则需要更长的时间。共同的目标是“做出一个正式投入生产（本番）的实绩，并将其整理成案例研究和作品集”。

阶段大致时长要做的事
第 1 阶段：夯实基础1～3 个月通过动手实践掌握 Python、API 对接、云基础、Git
第 2 阶段：AI 实现2～4 个月LLM API 应用、RAG 构建、提示词设计、评测（Eval）的实现
第 3 阶段：积累实绩2～4 个月通过公司内部客户／副业，以完整周期完成一个正式投入生产的案例
第 4 阶段：求职准备1～2 个月完善作品集、考虑职位名称差异的求职搜索、面试准备

第 1 阶段：夯实基础（1～3 个月）

要做到能够自己用 Python 编写脚本，调用外部 API 获取并加工数据这一整套流程。同时要接触云（AWS/GCP/Azure）基础、Git，以及简单的部署。有实现经验的人可以缩短这一阶段，直接进入第 2 阶段。完全跨行业的人则要加厚这一阶段，务必创造“自己从零完成一个能运行的东西”的体验。

第 2 阶段：AI 实现（2～4 个月）

通过动手实践掌握使用 LLM API 构建应用、RAG 的实现、提示词设计、输出质量的评测（Eval）。以各公司官方文档（OpenAI / Anthropic 等）作为第一手信息，同时自己动手做小型应用进行验证，这是最快的方式。如果能深入到解决“PoC 能跑通但正式环境达不到质量”的评测设计，你的市场价值会在这里迅速提升。

第 3 阶段：积累实绩（2～4 个月）

用学到的技术，以完整周期（需求调研→需求→实现→落地→成果衡量）完成一个公司内部客户或副业的小型项目。这将成为 FDE 招聘中最有分量的“正式投入生产并被实际使用的实绩”。务必测量 Before/After 的数值，在注意保密的前提下将其整理成案例研究。失败与调整方向的记录也要作为资产保留下来。

第 4 阶段：求职准备（1～2 个月）

将实绩整理进作品集，考虑到职位名称的差异（FDE／SE／AI 导入／CE／DS）进行求职搜索，并推进面试准备。要准备好能够从出身职业的优势出发，连贯地阐述“为什么选择 FDE”，并准备好反向提问。求职时可通过 FDE 招聘 综合 和 招聘列表 进行定点观察，以潜力录用岗位为中心进行投递。

总结：从零经验到 FDE 的最短路径

从零经验成为 FDE 的路径是清晰的：(1) 判断自己拥有的是“实现”还是“直面客户”哪一方面的圈子；(2) 以优势为轴补足短板（按出身职业划分的路线图）；(3) 双轮并进地夯实 Python、LLM/RAG、系统集成、需求定义、商务谈判技能；(4) 不止步于 PoC，做出一个正式投入生产的实绩；(5) 整理成案例研究和作品集；(6) 攻克职位名称差异进行求职搜索，通过潜力录用岗位投递；(7) 做好能够连贯阐述“为什么选择 FDE”的面试准备——只要按计划逐步积累这 7 个步骤，从相邻职位转型是完全现实的。

FDE 是同时通晓技术与业务的稀缺职位，处于人才持续短缺的卖方市场。可以说现在正是从零经验挑战的好时机。接下来若要继续阅读，所需技能的详情请见 FDE 所需的技能，年薪行情请见 FDE 的年薪行情，转型后的职业发展请见 FDE 的职业路径，实际招聘信息请通过 FDE 招聘 综合 和 招聘列表 确认。
