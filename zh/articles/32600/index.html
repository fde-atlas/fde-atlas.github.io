Agent SDK 选型：Claude、OpenAI 与 Google ADK 对比

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

文章主张 Agent SDK 的选型应由客户约束决定，而非基准测试分数。作者提出四个前置问题：智能体运行位置与运维方、模型是否已锁定、危险操作的拦截机制、追踪与质量评估归属。文中列举关键差异：OpenAI Agents SDK 的追踪默认开启，但零数据保留政策客户无法使用；Google ADK 提供 Go、Java 等多语言版本，适合本地化部署；Claude Agent SDK 的 deny 钩子在 bypassPermissions 模式下依然生效。作者建议 FDE 在写代码前先问清这四个问题，以减少后期重写。

要点

  • 选型取决于客户约束，不是基准分数。
  • 零数据保留客户用不了 OpenAI 默认追踪。
  • ADK 支持 Go 和 Java，适合本地部署。
  • Claude 的 deny 钩子在 bypassPermissions 下仍生效。
  • OpenAI 输入输出护栏只覆盖首尾智能体。

三大 Agent SDK 怎么选，取决于客户约束而非基准分数，写代码前问清四个问题即可。

要点速览

  • 不要从基准测试出发，而要从四个问题出发：智能体在哪运行、用哪个模型、谁控制权限、谁来看追踪。
  • 在零数据保留政策下使用 OpenAI API 的客户，无法使用 OpenAI Agents SDK 默认开启的追踪。如果客户团队写 Go 或 Java，ADK 有这两种语言的官方库，而 Claude Agent SDK 只提供 Python 和 TypeScript。
  • Claude Agent SDK 的权限判定顺序有精确的文档说明，deny 钩子先于其他所有步骤运行；ADK 自带评估智能体执行轨迹的工具。

OpenAI Agents SDK 的文档写明，追踪默认开启。同一份文档也写明，在零数据保留（Zero Data Retention）政策下使用 OpenAI API 的组织无法使用追踪。一项默认功能，可能因为客户合同里的一条条款而消失。

这个细节说明了真实项目里 Agent SDK 是怎么选出来的。没有人照着排行榜挑。候选名单是被客户提出的约束一步步收窄的，通常发生在第一次工作会议上，通常也在任何人打开编辑器之前。

对前线部署工程师（FDE）来说，这是一项值钱的技能。第一周选错框架，到第六周就得重写可观测性层、权限层，有时连模型调用层也要重写。下面给出在 Claude Agent SDK、OpenAI Agents SDK 和 Google ADK 之间做选择的四个问题，以及各自的坑。

智能体在哪运行，谁来运维？

先问这个问题，因为它决定了系统出故障时谁来值班。根据 Anthropic 的文档，Claude Agent SDK 把 Claude Code 内部运行的同一套智能体循环、工具集和上下文管理打包成了 Python 和 TypeScript 库。

智能体嵌入在你的应用里，运行在你自己运维的进程中。OpenAI Agents SDK 同样是 Python 库，用 pip 安装，在你自己的进程里运行，另外还提供一个沙箱智能体，用于在隔离的工作空间里执行任务。

如果客户什么都不想运维，Anthropic 另有一款产品 Managed Agents。它是托管的运行框架，负责执行智能体循环，会话运行在 Anthropic 管理的云端沙箱，或客户自有基础设施上的自托管沙箱中。

和客户沟通时，要把这两款产品分清楚。混为一谈，最容易对数据存放位置做出错误承诺。

Google ADK 是开源的，设计上可以部署在任何地方：容器化后跑在自有基础设施上，或一条命令部署到 Google Cloud。所以三者都能运行在项目团队可控的基础设施上，区别在于语言。

假设一家银行只允许软件运行在自己的数据中心，内部团队写 Java。ADK 有 Python、TypeScript、Go、Java 和 Kotlin 版本，应当排在首位。

Claude Agent SDK 只提供 Python 和 TypeScript 库。对于其他语言，Anthropic 的文档给出的方案是把 Claude Code CLI 作为子进程运行，再读取它的 JSON 输出。这条路走得通，但客户团队得多维护一层集成。

客户已经选定模型，还是想保留切换的余地？

很多客户已经和某家模型厂商签了合同，另一些客户则想保留日后切换的可能。这两类客户需要不同的建议。

OpenAI Agents SDK 通过 Any-LLM 和 LiteLLM 支持非 OpenAI 模型，但文档把这两种集成都归为 beta，仅尽力提供支持。

如果客户用的是其他模型，在做出任何承诺之前，你得在项目的真实流程上亲自验证该厂商的表现。相比之下，ADK 自称通过对接各厂商的适配器，几乎能配合任何生成式模型使用，不限于 Gemini。

Claude Agent SDK 围绕 Claude Code 自身的智能体构建，最好把它看作面向已经选定 Claude 的客户的方案，而不是一个用来来回切换模型的中间层。这里的建议很简单：如果客户说“我们还不确定用哪个模型”，不要凭团队偏好选 SDK，然后指望适配器够用。

谁有权拦截危险操作？

能调用工具的智能体会做实事：写文件、调 API、改数据。所以客户的安全团队会问，靠什么阻止它做错事。Anthropic 的文档回答得很详细。

根据 Anthropic 的权限文档，每次工具调用都按固定顺序判定：钩子、deny 规则、ask 规则、权限模式、allow 规则，最后是 canUseTool 回调。钩子先于其他一切运行。

即使智能体处于 bypassPermissions 模式，deny 钩子依然生效。对于无界面运行的智能体，Anthropic 建议把 allowedTools 与 permissionMode “dontAsk” 结合使用，锁定允许使用的工具集合。

OpenAI Agents SDK 刻意保持精简，只有几个基本原语：智能体、让一个智能体把工作交给另一个的交接（handoff）、护栏（guardrail），以及内置追踪。坑就在护栏上：输入护栏只在链条的第一个智能体上运行，输出护栏只在最后一个上运行。

假设一个客服部署串联了三个智能体，中间那个有权退款。如果你把检查放在输入护栏里，以为它能覆盖整条链，那么中间的智能体在任何一步都不会被检查。

解决办法是把检查放在退款工具本身。SDK 为此提供了工具护栏：根据文档，凡是挂了护栏的函数工具，每次调用都会运行护栏，在工具执行前检查输入，执行后检查输出。

在发给客户的设计文档里把这一点写清楚。客户的安全团队一定会问这个问题，答案要在他们开口之前就备好。

谁来看追踪，质量怎么衡量？

第四个问题往往被拖到第二个月，等到客户问智能体为什么周二给了错误答案时才浮出水面。三款 SDK 的答案各不相同。

OpenAI Agents SDK 内置追踪且默认开启，调试起来非常方便。但正如开头所说，零数据保留政策下的客户用不上。对这类客户，可观测性层从一开始就得自己搭。

根据 Google Cloud 的文档，ADK 内置评估工具，另有合作伙伴工具，可以检查智能体的执行轨迹：既看最终答案对不对，也看智能体经过了哪些步骤得出答案。

对于必须证明智能体遵循既定流程的客户，比如申请审核，这是实实在在的优势。

Claude Agent SDK 提供钩子，可以在智能体生命周期的关键节点运行代码，还有会话、子智能体和 MCP。钩子是接入可观测性的天然位置。

使用 Claude Agent SDK 的一种做法是：用钩子把每次工具调用记录到客户的日志系统，再基于这些数据构建测试集。搭建需要花些功夫，但数据完全留在客户手里。

四个问题，三种答案

每份文档只讲自家产品。只有把它们放到同样的问题下对照，才能看出各自强在哪里、哪里还需要追问。

问客户的问题 Claude Agent SDK OpenAI Agents SDK Google ADK
智能体在哪运行，谁来运维？ Python/TypeScript 库，运行在项目团队运维的进程中；需要托管则用 Managed Agents Python 库，运行在项目团队的进程中，另有沙箱智能体 开源，有 Go 和 Java 版本；容器化部署在自有基础设施或 Google Cloud
用哪个模型，能否切换？ 围绕 Claude Code 的智能体构建 非 OpenAI 模型通过 beta、尽力支持的适配器运行 几乎适配任何生成式模型
谁拦截危险操作？ 钩子先于每一步运行；deny 钩子在 bypassPermissions 下仍然生效 输入护栏只在第一个智能体上，输出护栏只在最后一个上；工具护栏在所挂工具的每次调用时运行 概览文档未说明工具拦截机制；承诺之前先在客户自己的流程上测试

这张表不评冠军，它展示的是哪个问题会排除哪款 SDK。客户处于零数据保留政策下又需要可观测性，就有理由重新考虑 OpenAI Agents SDK。

客户需要 Go 或 Java，ADK 就有明显优势，而 Claude Agent SDK 只能绕远路，经由 CLI 接入。已经选定 Claude、安全团队要求严格的客户，正是 Anthropic 有序权限模型的目标用户。

接下来练什么

一篇教程指出，做个演示就收手，是为 FDE 工作学习智能体时收效最低的方式。

最有效的练习是在两款 SDK 上构建同一个智能体，然后故意把它弄坏：让一个危险工具绕过护栏，关掉追踪，换一个模型。

读岗位描述时，留意“on-prem”“data residency”“Zero Data Retention”“GCP”或“Java”这类字眼。正是这些约束决定了最终选哪款 SDK。

简历上不要写“熟悉 LangChain 和智能体框架”，而是写这样一句：“根据数据保留要求和工具调用权限控制需求，为申请处理智能体选定 SDK。”

这句话说明你真正和客户坐在一起干过活。

框架会随每次发布不断变化，这四个问题的变化要慢得多。写代码之前先问清这四个问题的 FDE，往往最后重写得最少。
