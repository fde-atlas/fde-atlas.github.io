本场小组讨论探讨了多家公司如何利用前沿部署工程（FDE）团队将 LLM 应用在企业客户中投入生产。来自 OpenAI、Ramp、Nominal 和 Dataland 的代表介绍了 FDE 如何直接深入客户现场，构建、部署并迭代 AI 解决方案，同时平衡定制化开发与可扩展的产品路线图。这一模式使这些公司能够通过将深厚的技术专长与对客户的深入理解相结合，解决复杂的、特定行业的问题，最终既推动客户即时成功，也促进长期的产品开发。成果包括显著的企业级采用：例如某电信公司的 AI 每天处理 70,000 通客户服务来电，以及 Dataland 每个人力贡献数百万美元的 ARR，同时持续将洞察反馈回来以改进核心模型和平台。

本页内容

本案例研究全面展示了多家科技公司如何通过前沿部署工程（FDE）团队将 LLM 投入生产。讨论汇集了来自 OpenAI、Ramp、Nominal 和 Dataland 的见解，从不同视角审视同一个根本挑战：如何在复杂的企业环境中成功部署和维护基于 LLM 的解决方案。

概述与背景

本场讨论揭示了一个共识：前沿部署工程已成为 LLM 在生产环境中落地的关键职能。虽然 FDE 角色在 Palantir 等公司早已存在，但过去一年其规模增长了约 10 倍，这主要得益于 LLM 能力的不断扩展，以及如今可以用 AI 解决的问题范围相应扩大。这种增长看似有悖直觉，因为更强的模型理论上应该需要更少的人工干预，但嘉宾们解释说，模型能力的提升实际上使人们能够应对更复杂、更异构的问题，而这些问题需要深厚的领域专业知识才能成功落地。

各公司的具体做法

OpenAI 的 FDE 模式

OpenAI 的前沿部署工程团队有两大核心使命：推动广泛采用，并将模型能力推向极限。该团队专注于发现市场中可复用的问题，与客户深度合作构建平台，然后决定是将解决方案作为独立产品发布，还是将其集成到 Codex 等现有产品中。负责这项工作的 Colin Jarvis 描述说，团队以两种截然不同的模式运作。第一，他们致力于打造可复用、可扩展的解决方案，最终使其成为自助式产品。第二，他们攻克半导体和生命科学等行业中最具挑战性的问题，与后训练团队紧密合作，以提升底层模型的性能。

OpenAI 的 FDE 团队在短短几年内从两人发展到超过 90 人，同时进行约十个大型项目。他们保持高度严格的筛选标准，仔细评估问题是否真正符合 FDE 的特点，以及是否有实现经常性收入的现实路径。团队由传统 FDE（类似于 Palantir 的 Delta 角色）、面向客户的技术专家（类似于 Echo 角色）组成，并且越来越多地引入行业领域的专家，例如芯片验证工程师和生命科学家，他们能够为高度专业化的领域正确制定任务和评测。

他们工作的一个具体例子是一个拥有 2,000 人的日本销售团队需要幻灯片生成助手。FDE 们首先必须尝试多种方法来格式化幻灯片，使模型能够生成高质量的输出，在尝试了更简单的基于方框的布局后，最终选择了 HTML 生成方案。随后他们生成了大量示例，并与后训练团队合作，这使得后续模型版本中的幻灯片生成能力得到显著提升。这体现了客户部署与模型改进之间的反馈循环。

另一个重要项目是为一家大型电信公司的客户服务部署实时语音 AI。最初的原型在读取电话号码等基本任务上表现不佳。然而，经过与后训练团队六个月的迭代，并构建了用于评测和自我改进循环的平台工具后，该系统现在每天处理约 70,000 通电话而没有出现重大问题。这既展示了生产级 LLM 部署的技术挑战，也展示了在大规模场景下实现可靠性所需的迭代方法。

OpenAI 的 FDE 团队越来越多地探讨一个问题：任何新产品是否可以直接作为 Codex 的扩展，而不是独立的产品。这反映出改进后的编程 Agent 已经把原本可能是 50 个独立产品的东西整合成了平台能力。该团队目前维护着两条尚未被 Codex 吸收的主要产品线：监管文档撰写和工作流自动化平台，两者都瞄准企业对高一致性的需求。

Ramp 的做法

Ramp 组建 FDE 团队，主要是为了赢得并服务企业客户，同时保护核心产品开发不被定制化的企业需求带偏。组建该团队的 Calvin 将 Ramp 的 FDE 职责描述为“为赢得企业客户不惜一切代价”，并在解决方案上富有创造性。他们要解决的根本问题是避免一个经典陷阱：企业交易通过无休止的定制功能需求使产品路线图脱轨。

Ramp 的 FDE 模式在几个方面与传统做法不同。首先，FDE 主要通过 Zoom 远程工作，而不是长时间驻场，大约每季度与客户会面一次。其次，他们与其他工程团队一起在核心代码库中工作，而不是维护独立的系统。第三，每位 FDE 通常同时服务五到六个客户，而不是深耕单一客户。这种“摊薄精力”的方式自然地激励 FDE 专注于能反哺整体产品路线图的高杠杆解决方案，而不是构建大量定制功能。

该团队将 ROI 简单地衡量为企业客户收入除以 FDE 薪资，并通过尽量减少维护负担来保持这一比率非常可观。他们更倾向于加速推进能让多个客户受益的路线图功能，而不是构建定制方案。当定制工作确有必要时，他们会与核心产品团队保持紧密合作，并努力将改动控制在最小范围，以避免长期技术债务。

对于 Ramp 的财务团队客户——他们通常使用 Excel 而非代码——FDE 团队开发了 Ramp Labs，其中包括一个在用户原生环境中服务用户的 Excel Agent。这体现了他们的原则：到客户所在之处去满足他们，而不是强迫他们采用全新的工作流程。

Nominal 的理念

Nominal 为从事卫星、核反应堆及其他先进硬件系统开发的硬件工程师构建数据和 AI 平台。CTO Jason 将前沿部署工程描述为自公司成立第一天起就融入其使命的核心，并嵌入在“赋能他们的使命”这一公司价值观中。该团队的职责不仅限于即时的客户成功，还包括理解最前沿的产品需求，并将洞察反馈到长期路线图的制定中。

Nominal 的方法强调在 FDE 工作与纯咨询之间划清界限。他们从 Palantir 在所谓“黑暗时代”的经历中吸取了教训——当时前沿部署团队几乎发生了“起义”，声称核心产品毫无用处，并完全另起炉灶构建独立系统。为避免这种情况，Nominal 的首批前沿部署工程师都是曾经构建过软件平台、并因客户与工程团队之间的“传话游戏”而感到沮丧的人。这建立了高度信任的关系，使领导层能够确信 FDE 们并非在简单地做咨询项目。

该团队明确利用前沿部署工程来加速销售周期，认为即使这意味着将 Nominal 的资源投入到原本可能要等 12 个月才能由大型传统公司内部处理的工作上，从战略角度也是值得的。不过，他们对何时以及如何这样做保持着纪律。一个例子是他们与一家无人机飞行测试公司的首份大合同。客户希望将数据转换脚本自动化，FDE 团队以可泛化的基于容器的架构构建了这一功能，而不是作为定制方案。这后来成为向其他客户销售的核心基础设施，同时也为初始客户带来了即时价值。

Nominal 设有相互独立但彼此关联的角色：任务运营（高度技术化、出身机械或电气工程、可能并非代码原生背景的前工程师）、任务开发（即 FDE 职能），以及不断壮大的销售团队。他们强调在前沿部署与核心产品岗位之间轮换工程师，他们最成功的时刻往往来自工程师在现场使用自家产品、发现其不足，然后带着改进的动力归来。

Dataland 的 Agent 优先模式

Dataland 为企业劳动力外包构建 AI，覆盖医疗、能源、消费电子、物流和废弃物管理等多个行业。联合创始人 Howard 将前沿部署工程描述为公司的命脉，因为他们为每个客户构建高度定制化的异构 AI Agent，而不是销售一个千篇一律的平台。他们的方法可以说是定制化部署的最极端版本，但通过对持续价值交付的精心把控，他们仍然保持着软件经济学。

Dataland 仅凭两名前沿部署工程师（即将扩展至三名），就实现了人均数百万美元的 ARR，展现出非凡的杠杆效应。他们的秘诀是“极度 AI 化”——投入大量时间构建元智能体（meta-agents），以加速自身的智能体开发流程。这解决了一个根本性挑战：没有任何智能体部署是静态的。随着客户业务的演进，其系统会变化、政策会更新、新产品线会推出，这一切都要求智能体随之调整。Dataland 大力投入于自动化智能体维护与改进的外循环，从而以最少的人工持续干预实现价值的持续交付。

他们认为 FDE 变得愈发重要的原因在于市场扩张。传统 SaaS 面向所有人，针对特定工作流提供平台，而劳动力自动化的总可寻址市场规模要大几个数量级，且本质上高度异质。如今 LLM 的能力使攻克这一系列多样化问题成为可能，但要取得成功，需要工程师深入理解具体用例，几乎达到能够亲自胜任这些工作的程度。这种领域专长必须与对前沿 AI 平台的深刻理解相结合，才能打造出有效的解决方案。

Dataland 认为编程智能体之所以格外成功，是因为每个软件工程师在该领域天然就是前沿部署工程师——他们每天写代码，对用例了如指掌。要在能源或废弃物管理等其他行业复制这一点，就需要让工程师深入嵌入并理解那些具体场景，然后才能构建有效的解决方案。

技术模式与演进

从基础设施到解决问题的转变

Colin 描述了在过去一年中 FDE 团队工作方式的重大转变。此前，使用早期版本的智能体 SDK 进行开发需要大量的底层搭建、自定义基础设施，以及针对每个问题的众多评测。团队可能要构建五个不同的智能体并配套五套不同的评测集，而仅仅达到可用原型所需的时间就限制了可解决问题的复杂度。

大约从 2026 年初开始，能够处理长周期任务的更强编码模型改变了这一格局。如今，FDE 编写的管道式代码大幅减少，相应地把更多时间用于解决客户的实际用例。这使得团队能够向更高层次、更难的问题迈进。半导体项目就说明了这一点：最初十个月专注于软件工程加速任务，例如将 Agent 部署到 CI 流水线中以及构建自动调试 Agent。只有在打下这些基础之后，团队才能开始开发执行物理芯片设计的 Agent——在更稳定的基础能力之上构建，从而可以信任 Codex 处理底层 50% 的任务，同时专注于更高层次、更高价值的活动。

评测与改进循环

各公司的一个共同主题是客户部署、评测开发与模型改进之间的紧密整合。OpenAI 的做法清晰地体现了这一点：FDE 与领域专家深度协作，理解他们的具体任务，确保模型能够解决这些任务，并生成反馈给后训练团队的评测数据。这形成了一个飞轮：真实部署中的挑战直接推动模型能力提升，进而使团队能够解决更复杂的问题。

幻灯片生成的例子具体展示了这一过程。在识别出客户需求后，FDE 尝试了多种输出格式，最终选定了一种在模型能力与质量要求之间取得平衡的方案。随后，他们基于该格式生成了大量训练样本。三个月后，一个新模型快照问世，其幻灯片生成能力显著提升。这一模式在各个领域反复出现：FDE 本质上是把领域特定问题转化为模型可以学习的格式，生成代表这些问题的合成数据，并与研究团队合作提升模型在这些特定任务上的表现。

电信语音客服部署展示了这一模式如何从单一模型改进延伸到构建完整的生产系统。团队不仅提升了模型遵循指令的能力，还为客户构建了平台能力，使客户能够创建自己的评测并建立自我改进循环，用于后续迭代。这使客户能够在没有 FDE 持续参与的情况下维护和演进其部署，这是规模化推广该方案的关键要求。

Codex 的整合

多位嘉宾指出，日益强大的编程 Agent，尤其是 Codex，已经从根本上改变了行业格局。在讨论的六个月前，OpenAI 的 FDE 团队预计要为不同用例构建大约 50 个独立产品，并可能形成一个其他人也能贡献更多产品的生态系统。然而，Codex 的能力提升如此迅猛，以至于约 80% 的计划产品可以改为以 Codex 扩展的形式实现。这种整合不仅影响 OpenAI，也影响所有使用这些工具的公司。

Dataland 的小团队能实现如此高的单人工程师生产力，很大程度上依赖于这些编程能力来构建和维护其元 Agent 基础设施。Ramp 的 FDE 之所以能同时服务多个客户，部分原因在于借助 AI 辅助开发，他们的推进速度更快。Nominal 的工程师，无论是传统的任务运营角色还是 FDE 角色，在 AI 工具的帮助下都越来越多地编写代码，以往的角色边界因此变得模糊。

这体现了 LLMOps 中一个更广泛的模式：用于构建 LLM 应用的工具本身正借助 LLM 能力快速改进，从而对开发者生产力产生复合效应。FDE 团队作为这些工具在复杂真实场景中的首批用户，既受益于这一加速进程，也为其做出贡献。

组织设计与文化

边界问题

讨论中反复涉及的一个核心挑战是：如何在 FDE 团队为单个客户构建的内容与属于核心平台的内容之间保持恰当的边界。Calvin 将其表述为保护核心团队不被企业需求淹没，同时仍能赢得订单。Jason 则警告要避免“Palantir 黑暗时代”——当时 FD 团队实际上放弃了核心产品，转而构建平行系统。Howard 强调要评估工作是否能带来可复用的价值，而非一次性咨询。

有几种机制有助于维持这些边界。第一，招聘画像很重要：要寻找曾经的创始人、早期阶段的工程师，以及关心营收和业务成果而非仅仅热衷于构建有趣技术的人。第二，结构性决策也很关键，例如 FDE 是在共享代码库中工作（Ramp 的做法）还是在独立系统中工作，这会影响定制工作偏离平台开发的难易程度。第三，围绕何为成功的指标与文化——Ramp 将 FDE 的 ROI 衡量为营收除以薪资，这形成了最大化杠杆而非增加人手的压力。

第四，在 FDE 与核心产品角色之间定期轮换，有助于保持共同语境并防止形成孤岛。构建平台功能的工程师随后与客户一起使用这些功能时，能直接获得关于哪些有效、哪些无效的反馈。而当发现了关键客户需求的 FDE 轮换到核心团队时，他们可以倡导并将这些功能实现为平台能力。

服务收入的陷阱

Colin 阐述了一个关键风险：服务收入会变成咨询公司无法戒掉的“毒品”，导致它们不断出售越来越大的定制化项目，而不是打造可扩展的产品。OpenAI 的组织结构有助于避免这一点，因为商业组织并非公司的权力中心——产品和研究团队主导战略，并推动 FDE 朝着可构建、可扩展的解决方案前进。团队衡量成功的主要标准不是服务收入，而是长期价值：这将为那些随后能够自助服务的数字原生客户解锁多少 ARR？哪些模型改进将惠及整个客户群？

Jason 的描述更加形象：客户可能会对前沿部署工程师产生依赖。如果撤回 FDE 会导致客户解雇你，这就表明你未能交付独立于人员编制之外的持久价值。解决方案需要清晰的价值工程：确保产品或平台在初始部署之后仍能持续创造价值，而不仅仅是可计费的小时数。

招聘与团队构成

所有嘉宾都强调，优秀的 FDE 需要具备一种罕见的技能组合：扎实的技术深度、快速学习新领域的能力、对模糊性的适应力、客户同理心、沟通能力以及商业敏锐度。Jason 称这或许是未来创始人最好的训练场，因为它要求从零到一构建解决方案、紧跟 AI 前沿、赢得客户信任，并在组织政治中游刃有余。

Colin 强调，“对价值的不懈追求”和以结果为导向是最关键的特质。最优秀的 FDE 不会迷恋自己创造的东西的形式；他们始终专注于功能和用户采用。如果用户不使用某个解决方案，优秀的 FDE 会果断推翻重来，尝试完全不同的方案，而不是为自己的工作辩护。

公司从多元背景中招聘人才——咨询（BCG、麦肯锡）、有 Palantir 工作经验的人、前创始人、早期创业公司工程师——但成功与否取决于特定的思维方式，而非出身背景。这一角色也随公司发展阶段而演变。在产品扩张阶段，公司可能需要能够广泛探索并识别新用例的 FDE。在以平台整合为重点的收缩阶段，他们可能优先考虑能够将解决方案标准化并向核心团队反馈洞察的 FDE。

商业模式与规模化考量

从定制到平台

从定制解决方案到平台能力的演进，是实现可持续规模化扩张的关键模式。Nominal 基于容器的数据转换系统最初是为一位客户做的定制工作，但从一开始就按照可泛化的思路进行架构设计。OpenAI 的工作流自动化和监管文档撰写产品，则是在多次客户合作中反复出现的模式基础上诞生的。Ramp 则持续评估某些企业级阻碍是否出现在多个客户身上，从而决定是否应将其转化为平台功能。

这一演进过程并不总是线性或可预测的。Jason 描述了产品扩张与收缩的循环：公司在探索新用例与将经验沉淀为平台之间来回摇摆。在这些阶段之间，FDE 的优先级甚至招聘画像都可能发生变化。关键的纪律在于识别定制工作何时具有战略意义（加速重要的销售周期、学习新领域、验证潜在的平台功能），何时只是无差异化的咨询工作。

经济模型与杠杆

尽管都采用 FDE 模式，这些公司却展现出截然不同的经济模型。Ramp 让单个 FDE 同时服务五到六个客户，尽量减少定制工作，专注于加速产品路线图。他们的 ROI 指标很简单：收入除以薪资成本。Dataland 通过大量使用元智能体（meta-agents）和自动化的智能体维护外循环，实现了每位工程师创造数百万美元 ARR。OpenAI 则较少关注即时的服务收入，更看重长期战略价值：这能带来哪些模型改进？能催生哪些自助式产品？

所有模式都强调杠杆效应，但实现机制各不相同。Ramp 通过让 FDE 在核心代码库中工作来实现杠杆，使其成果具备最大的可复用性。Dataland 通过构建能大幅加速后续智能体开发的基础设施来实现杠杆。OpenAI 则通过改进底层模型和平台来实现杠杆，使整类问题都能自助解决。

模型进步的作用

有趣的是，更强的模型并没有减少对 FDE 团队的需求，而是改变了这些团队的工作内容。FDE 不再需要花几个月搭建基础设施和评测来让基本功能跑通，而是去攻克更难、更有价值的问题。半导体的例子很能说明问题：只有在 Codex 可靠到足以处理常规编码任务之后，团队才能着手解决物理芯片设计方面的挑战。

这预示着 FDE 角色将在抽象层次上持续向上演进。随着模型能够自主处理更多基础性任务，人类专家将越来越专注于问题定义、领域专属的评测设计，以及识别下一个可攻克的前沿问题。所需技能可能从传统软件工程转向领域专业知识加 AI 系统知识的组合。

批判性评估与开放问题

尽管各位嘉宾为前沿部署工程提出了令人信服的案例，但其中存在的一些矛盾与风险值得考量。首先，这些成功案例主要来自资源充裕的公司（OpenAI、Ramp）或工程师人均生产力极高的公司（Dataland）。目前尚不清楚普通初创公司能否有效执行这一模式，还是说它需要不同寻常的条件。

其次，尽管有明确的原则，战略性定制工作与咨询之间的界限仍带有一定的主观性。不同公司划定的这条线位置各异，而且关于失败案例或本应更早放弃的项目的讨论也很有限。这些自我报告的成功指标缺乏外部验证。

第三，该模式的可扩展性存在固有限制。OpenAI 同时进行约十个项目，动用 90 多人，这表明每个大型项目都需要大量持续投入。即使工具和模型不断改进，任何团队能有效处理的复杂企业部署数量可能都存在上限。

第四，讨论高度聚焦于成功的技术部署，但对初始 FDE 交付结束后的长期维护成本、合同续签和客户留存涉及较少。电信行业每天 7 万通电话的案例令人印象深刻，但持续运营是什么样子？需要多少后续支持？

最后，对灵活性和定制解决方案的强调可能产生技术债务，而这种债务往往要到后期才会显现。尽管各方都表示有意将其降至最低，但让 90 多名工程师在多样化的客户环境中进行开发，不可避免地会带来复杂性，随着这些工程师轮换或离职，这种复杂性可能变得难以维护。

尽管如此，这些案例研究为成熟的组织如何在复杂的企业环境中将 LLM 投入生产提供了宝贵见解。多家商业模式不同的公司不约而同地采用前沿部署工程，表明这一模式确实解决了 LLM 落地中的真实挑战。对部署与模型改进之间紧密反馈循环的重视、对定制工作与平台工作之间边界的谨慎管理，以及招聘时看重特定思维方式而非单纯技术能力，都为构建 LLM 产品的组织提供了具体指导。而更强大的编程 Agent 正在减轻基础设施负担，同时使更难的问题求解成为可能，这一演进也让我们得以窥见该领域未来几年的发展方向。
