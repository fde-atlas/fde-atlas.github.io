前沿部署工程，第 9 部分：LLM 原生的性能、延迟、Token 与成本

原标题：Forward deployed engineering, Part 9: LLM-native performance, latency, tokens and cost

Abhinav Bhatia · 2026-10-20 · 约 18 分钟读完

摘要

本文是前沿部署工程系列第九篇，以 Acme 路由器为例讲解 LLM 原生的性能与成本指标：首 token 时间、每秒 token 数、上下文窗口、思考 token、缓存、流式输出与批处理，并强调优化前先测量。作者指出传统 Web 指标无法解释模型系统的慢与贵，正确答案若耗时 20 秒或成本过高仍算失败。

要点

  • 一次模型调用分为排队、prefill、思考和逐 token 解码四个阶段。
  • 成本大头通常是最贵的模型和思考 token，示例中思考占 35%。
  • 缓存只对完全相同的前缀生效，不变的文本应放在提示词最前。
  • 流式输出不缩短总耗时，但让用户从首 token 时间就开始阅读。
  • 核心习惯：先追踪真实请求的 p50 与 p95，再决定优化方向。

由模型驱动的系统，其缓慢和昂贵的方式与普通 Web 服务不同。本部分从零开始解释首 Token 时间、每秒 Token 数、上下文大小、思考、缓存、流式传输、批处理以及每次请求的成本，然后以 Acme 路由器为例，展示最重要的一个习惯：优化之前先测量。

在第 8 部分中，我们修复了一个会自我隐藏的故障：一个登录错误以“无数据”的形式出现在 Acme Consumer Brands 的供应规划员 Sam 面前。现在路由器会大声报错，并且有了让它保持诚实的测试。一周后，市场部的 Maria 发来了另一条消息：“系统能用了，回答也不错。但是太慢了，而且财务想知道为什么账单比预估的高。”

这是另一种类型的问题。没有任何东西坏了。系统只是比人们预期的更慢、更贵，而且没人能确切说出原因。语言模型有自己独特的缓慢和昂贵方式，常用的 Web 服务指标（每秒请求数、服务器时间）无法解释它们。

本部分讲解那些真正有用的指标。它解释一次模型调用内部发生了什么、提示词的长度为什么重要、思考的成本是什么，以及缓存、流式传输、批处理和模型大小各自如何改变整体情况。最后以一个比任何单项技术都更重要的习惯收尾：优化之前先测量。

这在 FDE 的职位描述中是如何体现的？

Google 的招聘信息直接点名了这项技能。截至 2026 年 10 月 20 日，以下是三个例子：

  • Google Cloud 的 前沿部署工程师，Gen AI 招聘信息将以下内容列为优先资格：“了解‘LLM 原生’指标（例如 tokens/sec、每次请求成本）以及优化状态管理和细粒度追踪的技术。”
  • 同一招聘信息要求工程师“构建高性能的评测流水线和可观测性框架，以确保 Agentic 系统在准确性、安全性和延迟方面满足严格的要求。”
  • OpenAI 的 前沿部署工程师 招聘信息（伦敦）寻找“构建或部署过由 LLM 或生成式模型驱动的系统，并理解模型行为如何影响产品体验”的人。

延迟和成本正是模型行为与产品体验交汇之处。一个需要 20 秒才能给出的正确答案，或者一个成本高于它所替代的分析师的答案，都不算成功。

我需要先了解什么？

以下是本部分使用的术语，每个都附有通俗的解释：

  • Token（词元）： 模型读取和写入的基本单位，是词的一部分。Google 的文档指出，对于 Gemini 模型，一个 token 大约相当于 4 个字符，100 个 token 大约相当于 60 到 80 个英文单词。模型的定价和限额都以 token 计，而不是以词计。
  • 输入（提示词）token： 你发送的所有内容：指令、工具描述、之前的消息、检索到的文档以及问题本身。
  • 输出 token： 模型写回的内容。
  • 思考 token： 推理模型在给出答案之前为理清问题而生成的 token。它们通常不会展示给用户，但 Google 的定价页面将输出价格列为“文本输出（响应与推理）”，因此这些 token 按输出费率计费。
  • 上下文窗口： 单次请求所能容纳的最大 token 数量，输入和输出加在一起。
  • 延迟： 用户需要等待多久。吞吐量： 系统在一段时间内完成多少工作，例如每分钟处理多少个问题。
  • 百分位数： 描述测量值分布情况的一种方式。p50（中位数）是一半请求都能达到的值。p95 是 95% 的请求都能达到的值，因此它反映了最慢用户的体验。两者都要报告，绝不能只报告平均值。

一次模型调用内部发生了什么？

每次模型调用都要经历相同的阶段。在时间线上观察这些阶段，就能解释人们所说的“慢”的大部分原因：

一次模型调用的结构：请求发出并可能排队，模型读取整个提示词（预填充），可能进行思考，然后逐个 token 生成答案；首 token 时间在第一个可见 token 到达时结束，之后的速度用每秒 token 数衡量

  • 网络与排队。 请求传输到模型端点，并可能等待可用容量。
  • 预填充。 模型必须先读取整个提示词，然后才能开始写任何内容。提示词越长，预填充时间越长。
  • 思考，如果模型被允许思考的话。在此阶段不会出现任何可见内容。
  • 解码。 模型逐个 token 地写出答案。

从这幅图中可以得出三个指标，它们共同描述了一次模型调用的体验：

  • 首 token 时间（TTFT）： 从发送请求到收到答案第一个 token 的时间。NVIDIA 的公开基准测试指南正是这样定义的，并指出它包括排队、预填充和网络时间，且提示词越长该时间越长。对于盯着屏幕的用户来说，TTFT 是系统开始让人感觉有响应的那一刻。
  • token 间延迟： 相邻两个输出 token 之间的间隔。
  • 每秒 token 数： 答案开始生成后到达的速度，即输出 token 数除以解码时间。

端到端延迟 从发出请求开始，到最后一个 token 结束。一个 Agent 的端到端延迟是依次运行的模型调用和工具调用耗时之和。

钱都花在哪里了？

一次模型调用的账单取决于四项 token 计数，各自按不同价格计费：新鲜输入、缓存输入、输出和思考。Agent 系列中关于部署、观测与成本的文章为 Acme Agent 构建了一份成本报告。其中的示例（token 计数仅为说明之用）分解如下：

一个 Acme 问题的钱花在哪里，使用 agent 系列成本报告中的示例 token 计数：Pro 上的 writer 是最昂贵的一次调用，思考 token 约占总量的三分之一，而缓存输入占比最小

有三点值得注意，而且在我见过的大多数 Agent 中都成立：

  • 最大的模型通常也是最大的成本。 writer 运行在 Gemini 3.1 Pro Preview 上，其每 token 成本高于 Flash。
  • 思考占了很大比重。 在这个例子中，它占该问题成本的 35%。
  • 缓存输入很便宜。 它占营销 Agent 提示词的大部分，却只占其成本的最小部分。

做估算时，有两条定价规则很重要。Google 的定价页面说明，如果请求的输入超过 200,000 token，则其所有 token 都按更高的长上下文费率计费。页面还说明，只对返回 200（成功）响应的请求收费；失败的请求不收费。但这并不意味着重试是免费的，因为一次成功的重试就是第二次付费调用。

应该汇报的数字来自 agent 系列成本报告：每个已解答问题的成本，即总成本除以正确回答的问题数。一个便宜但错误的答案仍然花了钱，而且用户还会再问一次。

为什么要在优化之前先测量？

当有人说“它很慢”时，人们往往想立刻改点什么：换更小的模型、缩短提示词、加缓存。根据我的经验，对时间去向的第一次猜测，错的次数往往比对的次数多。所以第一步始终是对一个真实问题进行追踪：

一个 Acme 问题的时间花在哪里，使用示例计时数据：extract 调用、两个 specialist 中较慢的那个以及 writer 几乎构成了全部等待时间；路由代码小到看不见，而且在没有流式输出的情况下，Sam 在 writer 完成之前什么都看不到

图中的数字是虚构的，但这个形态很典型。人们常常首先怀疑的路由代码几乎不耗时。extract 调用很短。两个 specialist 按设计并行运行（如 agent 系列的路由器文章所述），因此较慢的那个决定了等待时间的中段。writer 约占总时长的一半，而 writer 的时间中超过一半用于思考。

有了这份追踪数据，就可以清楚地看到：加快路由代码不会节省任何时间，而让 writer 少思考，或者对其答案进行流式输出，才会最大程度地改变 Maria 的体验。

要自己进行测量，可以在 Cloud Trace 中查看一个慢问题的 span（ADK 会把每次模型调用记录为一个

generate_content

span 及其 token 数量），然后对二十个问题重复此过程，查看 p50 和 p95。不要基于单次运行进行优化。

为什么长对话会变得更慢、更昂贵？

模型在调用之间不保留任何记忆。为了延续对话，应用程序在每一轮新对话中都会发送指令、工具描述以及到目前为止的整个对话内容。因此，每当用户提出后续问题时，输入都会增长：

为什么长对话会变得更慢、更昂贵：模型在调用之间不保留记忆，因此每一轮都要重新发送指令和工具，再加上到目前为止的整个对话内容；历史部分每轮都在增长，而新问题本身却很小

每一轮的成本都比上一轮更高，预填充耗时也更长。此外还有质量成本。研究论文《Lost in the Middle》发现，语言模型对长上下文开头和结尾信息的利用效果优于中间部分的信息。更长的提示词并不自动就是更好的提示词。

解决方法说起来很简单：

  • 只发送该步骤所需的内容。 撰写者需要的是专家的发现结果，而不是他们完整的工具输出。提取步骤需要的是最近几轮对话，而不是整个历史记录。
  • 当对话超过设定长度时，裁剪或总结旧的轮次。
  • 将大段参考文本排除在提示词之外，在需要时检索相关部分（本系列第 4 部分将介绍检索）。
  • 将状态保存在状态存储中。 Agent 必须记住的事实（例如用户所在地区）应存放在会话状态或记忆中（agents 系列的记忆篇），而不是放在不断增长的对话记录中。

缓存如何提供帮助？

上下文缓存允许模型复用它对提示词开头部分已完成的工作。如果许多请求都以相同的文本开头，则共享部分（前缀）可以以低得多的价格读取。Google Cloud 提供两种类型。隐式缓存是自动的，在每个项目中默认开启，缓存 token 可享受 90% 的折扣。显式缓存允许您自行创建缓存并控制其存续时间，但这会增加存储费用。

问题在于“前缀”这个词。缓存只能复用从第一个 token 开始就完全相同的文本。因此，提示词的顺序决定了缓存是否有效：

提示词顺序与缓存：缓存只能复用完全相同的前缀，因此把不变的内容放在前面（指令、技能文本、工具声明），把变化的内容放在最后（问题）；只要开头有一个变化的值，其后的所有内容都无法复用

把不变的内容放在前面（指令、技能文本、工具声明），把变化的内容放在最后（问题）。如果在开头有一个单独的变化值，比如今天的日期或用户的名字，那么它之后的内容都无法复用。Agent Platform 文档规定，大多数 Gemini 3 模型的缓存最低要求为 4,096 个 token，因此非常短的提示词根本不会被缓存。每次响应都会报告其输入 token 中有多少来自缓存，Acme 的 Agent 会将该数字记录为

cached_tokens

。它告诉你缓存是否在实践中真正生效。

agents 系列中的两条用量记录展示了需要关注的内容。营销 Agent 的提示词大部分来自缓存；而写作 Agent 的则完全没有：

流式输出能让速度更快吗？

流式输出是指在模型生成答案的同时，将其逐段发送给用户，而不是等待完整答案。在 Agent Platform 上，对应的 REST 方法是

streamGenerateContent

.

流式输出与等待完整答案的对比：两者在同一时刻完成，但使用流式输出时，用户在首个 token 生成时间即可开始阅读，而不是盯着加载图标直到结束

流式输出并不会让模型变得更快。总时间是相同的。改变的是用户等待的内容：使用流式输出时，Maria 在首个 token 生成时间即可开始阅读，而不是盯着加载图标直到结束。对于一个生成几段文字的写作 Agent 来说，这就是“感觉响应迅速的系统”和“感觉卡死的系统”之间的区别。

一个诚实的限制：只有当模型与屏幕之间的每一层都传递这些片段时，流式输出才有帮助。在多 Agent 系统中，如果路由器要先收集完专家的完整答案再继续，那么无论模型如何，这部分都不会流式输出。请检查每一跳。

我该如何选择模型规模，以及它应该思考多少？

更大的模型通常更擅长复杂的推理，但更慢且每个 token 的成本更高。更小的模型更快、更便宜，而且许多步骤并不需要更大的模型。我使用的规则是：每个步骤都从能通过其评测的最小模型开始，只有当评测表明有必要时才升级。

对于 Acme，提取步骤只是把一个问题改写成一行。agents 系列的部署、观测与成本一文建议尝试使用 Gemini 3.1 Flash-Lite 来完成它，价格只是 Flash 的零头，前提是路由准确率在 agents 系列的评测一文中的评测关卡里保持 100%。写作 Agent 需要将发现整合成清晰、正确的答案，因此在更小的模型通过同样的关卡之前，它继续使用 Pro。关卡本身是一份简短的最低分数清单，这里做了简化：

THRESHOLDS = {  # metric -> minimum mean score
    "route_correct": 1.0,   # routing is code: < 100 % is a bug
    "grounded": 1.0,        # no invented numbers, ever
    "golden_numbers": 0.9,
    "refusal_rubrics": 0.9, # judge: only after calibration
    "faithfulness": 4.0,    # judge, 1-5 scale
}

更便宜的提取模型只有当

route_correct

保持在 1.0 时才能通过。

如果没有人在等待答案呢？

有些模型工作没有用户在旁观：夜间评测运行、提示词变更后对旧问题的重新评分，或对一周反馈的总结。这类工作不需要最快或最可用的容量。Google Cloud 提供了几种购买模型容量的方式：

在 Gemini Enterprise Agent Platform 上购买模型容量的方式：Standard PayGo 适用于大多数交互式流量，Priority PayGo 以更高费率适用于业务关键的高峰流量，Flex PayGo（预览版）和批处理以半价适用于可以等待的工作，Provisioned Throughput 适用于稳定、可预测的用量

  • Standard PayGo（按需付费）在共享容量上按 token 计费。
  • Priority PayGo 按 token 收取更高费率；文档建议将其用于流量不可预测的业务关键工作负载，例如面向客户的助手。
  • Flex PayGo（截至 2026 年 10 月为预览版）比 Standard 便宜 50%，适用于可以容忍更高延迟的同步工作。
  • Batch 一次性接收大量请求并稍后返回结果，同样享有 50% 的折扣。
  • Provisioned Throughput 是一种固定成本、固定期限的订阅，用于预留容量。

对于 Acme，显而易见的做法是在 Flex 或批处理上运行夜间黄金集评测。在开发期间，它们是模型账单中实实在在的一部分，而且凌晨两点没有人在等待它们的结果。

试试看：哪个杠杆对成本的影响最大？

这个脚本无需任何云资源即可运行，只需要 Python 3。它以成本报告中的示例问题为基础，每次只改变一个因素。将其保存为

levers.py

:

PRICES = {  # US$ per million tokens: input, cached input, output (incl. thinking)
    "gemini-3.5-flash": (1.50, 0.15, 9.00),
    "gemini-3.1-flash-lite": (0.25, 0.025, 1.50),
    "gemini-3.1-pro-preview": (2.00, 0.20, 12.00),
}
BASE = [  # step, model, prompt tokens, of which cached, output, thinking
    ("extract", "gemini-3.5-flash", 3200, 0, 120, 300),
    ("marketing", "gemini-3.5-flash", 19500, 15000, 500, 600),
    ("writer", "gemini-3.1-pro-preview", 5000, 0, 450, 900),
]

def cost(calls):
    total = 0.0
    for _, model, prompt, cached, out, think in calls:
        p_in, p_cached, p_out = PRICES[model]
        total += ((prompt - cached) * p_in + cached * p_cached + (out + think) * p_out) / 1e6
    return total

def change(step, **kw):
    keys = ("model", "prompt", "cached", "out", "think")
    rows = []
    for row in BASE:
        if row[0] == step:
            d = dict(zip(keys, row[1:]))
            d.update(kw)
            row = (step, *[d[k] for k in keys])
        rows.append(row)
    return rows

SCENARIOS = {
    "baseline": BASE,
    "extract on Flash-Lite": change("extract", model="gemini-3.1-flash-lite"),
    "writer thinks half as much": change("writer", think=450),
    "writer prompt 84% cached": change("writer", cached=4200),
}
base = cost(BASE)
for name, calls in SCENARIOS.items():
    c = cost(calls)
    print(f"{name:30s} {c:.4f} per question  {c / 0.8:.4f} per resolved (80%)  "
          f"{100 * (c - base) / base:+.0f}%")

可能出问题的地方

  • 没有追踪数据就进行优化。 你会加速你怀疑的部分，而不是真正慢的部分。
  • 只报告平均值。 二十个请求里有一个非常慢的请求在平均值中不可见，但对等待的那个用户来说却非常明显。请报告 p50 和 p95。
  • 把思考排除在成本模型之外。 思考按输出计费，可能占总成本的三分之一。
  • 不小心破坏了缓存。 提示词顶部的时间戳或用户名会让每个请求看起来都是新的。每次修改提示词后都要关注 cached_tokens。
  • 更便宜的模型回答质量更差。 每个问题的成本下降了，但每个已解决问题（resolved question）的成本上升了。任何性能变更都要通过与其他变更相同的评测关卡。
  • 流式传输在某一跳就中断了。 如果任何一层缓冲了整个答案，用户就看不到任何好处。
  • 过早预留容量。 预置吞吐量（Provisioned Throughput）是一种承诺。应在测量使用量之后再购买，而不是之前。

我现在会怎么做

  • 挑选二十个真实问题，记录 p50 和 p95 的端到端延迟以及每个已解决问题（resolved question）的成本。这就是你的基线。
  • 打开最慢那个问题的追踪记录，写下哪一步耗时最多。
  • 重新调整每个提示词的顺序，让不变的部分放在最前面，然后检查 cached_tokens。
  • 对每一步，尝试能通过评测的最小模型和最低思考级别。
  • 把评测和其他离线模型工作转移到 Flex 或批处理上。

我们学到了什么？

  • 每次模型调用都经过相同的阶段（网络和排队、预填充、思考和解码），而首 token 时间、每秒 token 数和端到端延迟描述了它的体验。
  • 账单取决于新鲜输入、缓存输入、输出和思考 token 的数量，而应该报告的数字是每个已解决问题（resolved question）的成本。
  • 在优化之前，先用追踪记录以及大量问题的 p50 和 p95 进行测量，因为对时间去向的第一次猜测往往是错的。
  • 长对话会随着每一轮变得更慢、更贵，所以每一步只发送它需要的内容，并把事实保存在状态中。
  • 缓存只复用完全相同的前缀，所以把永远不变的内容放在最前面，并在每次修改提示词后关注 cached_tokens。
  • 流式传输让用户可以在首 token 时间就开始阅读，但并不会让模型更快；每一步都应该在能通过其评测的最小模型和最低思考级别上运行，而没有人等待的工作应该放到 Flex 或批处理上。
