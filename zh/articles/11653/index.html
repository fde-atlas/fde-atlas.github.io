ThunderAgent (2026) 面向 FDE 的解读

原标题：ThunderAgent (2026) Explained for FDEs

FDE Interviews · 2026-10-18 · 约 4 分钟读完

摘要

ThunderAgent 把 Agent 工作流当作“程序”来调度，解决推理引擎与工具编排分离导致的 KV cache 反复驱逐、节点内存失衡和沙箱堆积问题。在 GLM-4.6 与 H100 上，服务吞吐达 vLLM 的 1.48-3.58 倍，RL rollout 快 1.79-3.92 倍，磁盘占用降 4.2 倍，已开源并被 SkyRL 采用。

要点

  • 现有栈把 Agent 每轮当作独立请求，等待工具时缓存被驱逐，延迟最高升 7.14 倍。
  • 调度器为每个请求标记程序 ID，跟踪上下文长度、阶段与状态，每 5 秒检查后端。
  • 暂停规则：先暂停工具调用中与较短的程序；恢复时优先推理中与较短的程序。
  • 全局队列允许程序在任意节点恢复，消除节点间最高 51% 的内存失衡。
  • 沙箱在恢复前预创建、程序结束即删除，磁盘占用降 4.2 倍。

一分钟读懂这篇论文

编码或研究 agent 的运行方式是一个循环：在 GPU 上思考，调用工具（运行测试、查询 API、浏览网页），把结果追加到上下文，再继续思考。它的上下文只会不断增长，因此每一轮几乎都可以复用上一轮的全部 KV cache。如今的技术栈将推理引擎（vLLM、SGLang）与工具编排器（Kubernetes）搭配使用，并把每一轮当作独立的请求来处理。

作者在 GLM-4.6 agent 上实测了这种拆分带来的三个问题。KV cache 抖动： 在内存压力下，引擎会驱逐正在等待工具的 agent 的缓存，为其他 agent 腾出空间；当工具返回时，整个历史必须重新预填充，使单请求 latency 最高升至 7.14 倍。内存不均衡： 为保证缓存局部性而将 agent 的请求固定在单个节点上的路由器，会让各节点的内存占用逐渐失衡，在 90 分钟的 rollout 中差距可达 51%。工具生命周期盲区： 已结束的 agent 的沙箱和镜像会一直留在磁盘上直到磁盘占满，且沙箱的搭建时间随并发增加而增长。

ThunderAgent 增加了一个理解程序语义的调度层。每个请求都携带一个程序 ID；调度器跟踪每个程序的 context length、阶段（推理或行动）和状态（活跃、暂停、已终止）。它每 5 秒检查一次每个后端。如果活跃程序需要的 KV 超过后端所持有的量，它会暂停程序，优先暂停行动中的和较短的程序，释放它们的缓存；当空间恢复时，它会恢复等待中的程序，优先恢复推理中的和较短的程序。被暂停的程序在一个全局队列中等待，并可在任意节点上恢复，这解决了内存不均衡问题。行动中程序的内存占用会随时间衰减，因此长时间的工具调用会先于短调用释放缓存。工具环境会在程序恢复前提前准备好，并在程序结束时删除。

在 H100 上，针对 SWE-agent、OpenHands、ToolOrchestra 和一个科学 agent 的服务吞吐量达到 vLLM 的 1.48-3.58 倍；使用 SGLang 路由器时，RL rollout 比 vLLM 快 1.79-3.92 倍；磁盘占用降低了 4.2 倍。该项目已开源，并被 SkyRL 采用。

研究笔记：问题、方法与结果

OpenHands RL rollout 相对于使用 SGLang 路由器的 vLLM 的吞吐量，GLM-4.6 运行在两个 8xH100 节点上（69.1 提升至 270.8 步/分钟）

作者测得的、随 agent 并发增长而出现的单请求延迟最坏升幅（由 KV cache 抖动导致）

当工具沙箱在其程序结束后被删除时节省的磁盘空间

Agent 工作流在 GPU 上的推理与工具调用（编译器、沙箱、API）之间交替进行，并在每一轮重发不断增长的历史记录。推理引擎把每一轮视为独立请求：高负载时会驱逐等待工具的 agent 的 KV cache 并在之后重新预填充；感知 KV 的路由器将 agent 固定在节点上导致内存失衡；工具沙箱无人清理而不断堆积。

将每个工作流建模为一个程序（id、上下文长度、阶段、状态、工具环境）。每隔几秒，将每个后端的活跃程序保持在 KV 容量之内：优先暂停处于工具调用中的程序和较短的程序，优先恢复推理中的程序和较短的程序，所有后端共享一个队列。衰减长时间空闲的工具调用的内存占用，在恢复前预先准备沙箱，并在程序结束时删除它们。

在 H100 上跨编码、路由和科学类 Agent 的测试中，服务吞吐量达到 vLLM 的 1.48-3.58 倍、Continuum 的 1.17-3.31 倍（高并发下）。在两个 8xH100 节点上的 RL rollout 比 vLLM 配合 SGLang 路由器快 1.79-3.92 倍，沙箱清理使磁盘占用降低 4.2 倍。

为什么这对 FDE 很重要

Agent 工作负载与聊天不同：上下文长且不断增长、工具调用中有长时间停顿，以及在批处理作业、评测和 RL 中有大量并发会话。为聊天调优的技术栈会随着并发上升，把大部分吞吐量浪费在重计算上。

Agent 越多，吞吐量可能反而下降。 在论文的 vLLM 基线中，当并行工作流数量超过内存容量后，总吞吐量不升反降。在为客户扩展 Agent 集群之前，先找到这个拐点，或者使用能自动限制活跃程序数量的调度器。

按 Agent 每轮测量前缀缓存命中率。 Agent 应接近 100%，因为每一轮都是对上一轮的延伸。负载下命中率下降意味着缓存在工具调用期间被逐出。

工具基础设施是推理成本的一部分。 沙箱的搭建时间和泄漏的环境会像 GPU 显存一样限制持续吞吐量；将清理与工作流完成绑定是解决之道。
