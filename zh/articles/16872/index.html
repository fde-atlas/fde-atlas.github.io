展示你的证据

原标题：Present Your Evidence

pathtofde.com · 2026-10-15 · 约 21 分钟读完

摘要

本文以虚构的招聘场景说明：招聘经理不会细读作品集，只会快速浏览证据。作者提出“证据漏斗”模型，将求职流程分为搜索、个人主页、演示、面试四道关卡，并给出三项可操作的改造：用“角色—证明—关键词”公式重写 LinkedIn 标题、把 About 压缩为三句话、把 GitHub 打磨成可快速浏览的证据页（精选仓库、完整 README、可复现的运行步骤），再配一段两分钟演示视频。文章强调诚实原则：所有陈述必须经得起背景调查与技术面试，不得夸大课程项目为企业级生产经验。

要点

  • 招聘经理只浏览证据，不细读代码或作品集。
  • 证据漏斗分四关：搜索、主页、演示、面试。
  • LinkedIn 标题公式：角色—一句话证明—关键词。
  • GitHub 要可快速浏览：精选仓库加完整 README。
  • 所有陈述须真实，不得夸大项目经验。

CityOps 试点或

上线 CityOps，这篇文章可以作为之后的待办清单。无需其他工具——一个免费的 LinkedIn 账号、一个免费的 GitHub 账号，以及一部能录制视频的手机即可。

周二上午 9:42。Priya 是一家中型物流公司的招聘经理，她开着一个浏览器标签页，肩上来自副总裁的压力越来越大：FDE 职位已经空缺六周了。她在 LinkedIn 上搜索"RAG engineer LLM production"，返回了一大堆简历。

她点了第一个。头衔："Software Engineer @ SomeCorp"。自我介绍部分全是空洞的流行词。没有项目、没有链接、没有演示。返回搜索结果。

她点了第二个。头衔："Backend Engineer | Building Applied AI & RAG Systems | Targeting Forward-Deployed Engineering"。GitHub 置顶了三个仓库，每个 README 读起来都像一份现场报告。而就在个人主页的最上方——有一个链接："2 分钟演示：基于 CityOps 运维手册语料库的 RAG copilot。"

她看了视频。九十秒后，她把这个主页转发给了副总裁，并附上一句："面试这个人。"

本课中出现的所有人名、公司和主页都是基于常见招聘模式的虚构示例——不是真实人物，也不是真实结果。但其背后的机制是真实的，而这正是本课的核心。

一个没人能找到的优秀工程师得不到面试机会；而一个能被找到却无法被评估的工程师也得不到回音。本课就是要弥合这两个缺口：让你可被发现——招聘人员能找到你；同时可被展示——当他们找到你时，能在三分钟内看到你的成果。

一个需要牢记的原则

招聘经理不会细读作品集；他们只会快速浏览证据。没有人会克隆你的仓库去读 4,000 行代码。他们会花五秒看你的头衔，三十秒浏览 README，两分钟看演示视频——而决定就在这里产生。你的任务就是让这三样东西无可辩驳。

最基本的概念：证据漏斗

把招聘流程想象成一个有四道关卡的漏斗。在每一道关卡，不同的材料发挥作用，而每道关卡都会在下一关被考虑之前筛掉一部分候选人：

GitHub 和演示视频是同一关卡内两条互补的证据路径：仓库让你的工作可被查验，视频让你的工作可被理解。一个不愿克隆你仓库的招聘经理，仍然会看两分钟视频。

注意这种不对称性。面试是最后一道关卡——只有前三关都奏效，你才能走到这一步。大多数候选人把全部精力投入面试准备，却把前三关当作走过场。这恰恰搞反了：面试机会正是从漏斗中产生的。

漏斗还告诉你每一关"好"的标准是什么：

关卡谁在做决定你有多少时间什么能胜出
搜索招聘人员 / 搜索算法瞬间——你要么出现在结果里，要么不在匹配人们实际搜索方式的关键词
个人主页招聘人员快速浏览大约 10 秒一句清晰的标题 + 首屏内的证据
演示观看的招聘经理大约 2 分钟屏幕上能运行的软件，配上简洁的讲解
面试整个面试小组30–60 分钟你讲述证据背后的故事

三份作品。三道关卡。本课将重建这三者：你的 LinkedIn 个人主页（搜索关卡）、你的 GitHub 个人主页（证据关卡），以及你的 2 分钟演示视频（“哦，这是真的”关卡）。每个部分都遵循同样的路径：诚实地审视薄弱版本，学习最基本的概念，构建强大版本，并使其可复用。

1. LinkedIn：搜索关卡

LinkedIn 不是简历。简历是别人在已经认定你有趣之后才会阅读的文档。LinkedIn 是一个搜索索引——招聘人员查询它的方式就像查询 Google 一样，而能浮现出来的主页，正是那些匹配查询词汇的主页。

这正是大多数求职者搞错的地方。他们只顾着优化以打动人类，却忘了自己首先是通过搜索被找到的。

薄弱版本（先把它拆解）

下面是一个有能力的工程师最典型的 LinkedIn 主页——这是招聘人员划过屏幕的数百个主页的综合体。请以搜索引擎的视角来读它：

Headline: Software Engineer @ AcmeCorp
About: Results-driven software engineer with a passion for
building scalable solutions and leveraging cutting-edge
technologies. Proven track record of delivering high-quality
software in agile environments. Team player. Quick learner.

Featured: (empty)
Experience: Software Engineer, AcmeCorp — 2023–present
  "Responsible for developing and maintaining backend services."
Skills: Java, Python, SQL, Problem Solving, Teamwork

现在用招聘人员的查询来检验它：“RAG 工程师，生产环境 LLM，向量搜索，评测。”零匹配。这个主页在真正重要的搜索中不可见。而对于那些确实点进来看的人类，标题只说“普通工程师”，About 部分没有任何能把此人与另外一万人区分开的内容。每个陈述都是形容词；没有任何作品。

标题改写公式

你的标题是求职过程中最有价值的一段文字。它出现在搜索结果中，是招聘人员点击之前看到的内容，也是 LinkedIn 搜索算法重点加权的内容。公式如下：

标题公式

[你想要的职位] — [一行证明能力的内容]（关键词，关键词，关键词）

一句话完成三件事：职位告诉搜索引擎和招聘人员你是谁；证明给人类一个点击的理由；关键词确保你在人们实际执行的查询中浮现出来。如果你的标题离开形容词就撑不住，就重写它。

改写前后——同一位工程师，同样的技能，一个隐藏自己的标题和一个能被找到的标题。（一如既往，均为虚构综合案例。）

BeforeAfter
Headline"Software Engineer @ AcmeCorp""Backend Engineer | Building Applied AI & RAG Systems | Targeting Forward-Deployed Engineering"
搜索看到的内容“software engineer”——数百万分之一后端工程师、应用 AI、RAG 系统——匹配真实的查询
人类看到的一个头衔和一家公司他是谁、在做什么、想要什么——一个点击的理由
证明内容无“构建应用 AI 与 RAG 系统”是一个声明，GitHub 主页必须证明它

几条让标题保持诚实的经验法则：

  • 分别说明你是什么、你想要什么。 “后端工程师 | 目标是前沿部署工程”两次说出了真相：当前的身份和志向。在尚未担任该职位之前，把“前沿部署工程师”作为标题，意味着你拥有一段并不存在的任职经历。你的 CityOps 里程碑能证明你的技能，但证明不了头衔。
  • 证明胜过形容词。 “对 AI 充满热情”是形容词。“上线了带评测的 Ask CityOps RAG 试点”是证明。一条可核查的声明胜过一整段形容词。
  • 关键词能提升可发现性，但不能保证。 使用你目标职位招聘信息中的词汇：LLM API、向量搜索、结构化输出、评测、RAG、FastAPI、Docker、CI/CD。关键词能帮助招聘人员找到你——但搜索可见性还取决于招聘人员的筛选条件、人脉背景和主页完整度。把关键词当作让评估更容易的策略，而不是保证排名的杠杆。
  • 一个作品就够了。 不要罗列所有项目。最强、最相关的那一个项目就是钩子；其余的放在精选板块和 GitHub 里。

About 板块：三句话的自我推介

大多数 About 板块是优秀主页的葬身之地——五大段行业黑话，没人能读完。解决办法是一个约束：三句话。只给你十秒钟的招聘人员会读完三句话。

I'm a backend engineer focused on building reliable APIs, data systems,
and applied AI solutions, with an interest in customer-facing engineering.
Alongside my professional engineering work, I'm building CityOps, a
simulated municipal operations platform that brings together data
ingestion, REST APIs, retrieval-based AI, evaluations, and deployment
practices. The project demonstrates my approach to solving integration
problems, validating behavior, and documenting operational tradeoffs.
I'm exploring Forward-Deployed Engineer opportunities where I can combine
software engineering with customer problem-solving, technical ownership,
and production reliability.

为什么这种结构有效：

  • 第一句——声明： 用你自己的话说明你是一名什么样的工程师。不是“充满热情的问题解决者”——而是一个具体的工程师身份。
  • 第二句——证明： 一个作品，附带具体的技术细节。“约 400 份客户文档”、“结构化输出引用”、“部署在企业代理之后”——每个短语都可核查，且每个都对应 Stage 4 和 Stage 5 课程中的词汇：RAG 端到端、结构化输出、部署在企业代理之后。（只有当工作是真实的，这些细节才成立——参见下方的诚实提示。）
  • 第三句——诉求： 明确说出你想要的职位。这有双重作用：告诉招聘人员该向你推荐什么，同时过滤掉无关的邀约。

诚实检查点

你个人资料中的所有内容都必须经得起背景调查、技术面试，以及一个持怀疑态度的招聘经理点开你的代码仓库的检验。CityOps 项目为你提供了真实的成果——一个可运行的 RAG 试点、一个已部署的服务、你真正运行过的评测。准确描述你所构建的东西；不要把一个课程项目夸大成“企业级生产经验”。“带着评测交付了一个试点”（真实、有力）和“主导了企业 AI 转型”（夸大，而且会让你在面试环节而非搜索环节被筛掉）之间有着持久的区别。自信保留，绝对化的表述去掉。

“Open to Work（求职中）”的问题：权衡取舍，而非硬性规则

LinkedIn 允许你表明自己正在找工作——可以用所有人都能看到的照片边框，也可以只对招聘人员私密可见。双方都有合理的论据，诚实的答案是效果取决于你的具体情况：

选项能获得什么要付出什么
公开的“Open to Work”边框曝光度最大；一些招聘人员会专门筛选这个标记。向你的社交网络清晰传达你在求职，这往往能带来熟人引荐——这是质量最高的渠道。所有人都能看到，包括你现在的雇主和同事。在大多数科技圈这没什么污名，但在某些企业文化中，少数人会觉得这显得“很急迫”。
私密标记（仅招聘人员可见）你会出现在招聘人员的“求职中”搜索结果里，而没有公开边框。对现任雇主的屏蔽并不完美——LinkedIn 会尝试对你的公司隐藏，但这不是保证。你的社交网络看不到，所以你失去了熟人引荐渠道。曝光度低于公开边框。
不做任何标记完全私密。当你有工作且现任雇主不知道你在找工作时很有用。你放弃了两个渠道。招聘人员仍然可以通过关键词找到你——这个标记是加分项，不是前提条件。

务实的解读：如果你在职且你的经理不知道你在找工作，就使用私密标记，并用朋友的账号验证哪些内容可见。如果你在公开求职，对大多数职位来说，公开边框的曝光优势大于劣势——但这由你决定，任何告诉你它“永远”正确或“永远”是危险信号的人，都在兜售他们并不具备的确定性。

让它可复用：LinkedIn 检查清单

  • 用“角色—证据—关键词”公式重写个人简介标题
  • “关于”板块压缩成三句话：主张、证据、诉求
  • “精选”板块链接你最强的演示视频和一个代码仓库
  • 工作经历条目描述你构建了什么，而非职责——每个职位一个可查证的成果
  • 设置自定义个人主页 URL（linkedin.com/in/yourname）——免费，只需两分钟，而且它出现的每个地方都显得很有心思
  • 头像：真实的面孔、近照、可辨认——这是信任信号，不是时尚宣言

GitHub 上真正令人印象深刻的东西

证据它证明了什么
清晰的 README + 架构沟通与设计思维
可复现的环境搭建工程完整性
自动化测试验证纪律
带有实质性检查的 CI可重复的质量关卡
失败场景 + 局限性运维判断力
可追溯的实现决策责任心与推理能力

提交历史只是辅助背景，不能替代一切。在私有公司仓库中工作的候选人，公开的提交图谱可能很冷清，但仍然可能是优秀的工程师——评审者真正阅读的是 README、测试和决策。

2. GitHub：证据关卡

如果 LinkedIn 让你被发现，那么 GitHub 就是持怀疑态度的招聘经理判断这些说法是否属实的场所。这里有一个大多数候选人都会忽略的基本概念：评审者不会读你的代码。他们浏览的是你的证据。 一个需要筛选十五份资料的招聘经理，大概只会花两分钟看你的 GitHub——而且他们会把时间花在你的个人主页、置顶仓库的 README 和提交图谱上。代码本身只有在通过初筛后才会被阅读，如果会被阅读的话。

所以设计目标不是“令人印象深刻的代码”，而是“令人印象深刻的可浏览性”：一个能在不到一分钟内回答评审者真正关心的三个问题的主页：

  • 这个人能把事情做完吗？（置顶仓库配有完整的 README，而不是被弃置的半成品。）
  • 这个人像工程师一样工作吗？（提交历史有真实的提交信息、测试、CI——而不是一个巨大的“最终代码”提交。）
  • 这个人能解释自己的工作吗？（README 是为读者而写的，包含问题、方法和如何运行。）

主页剖析：评审者实际看到的内容

你的 GitHub 主页就是一个落地页。请像对待落地页一样对待它：

元素评审者检查什么“好”是什么样子
个人 README他们知道如何介绍自己吗？简短：你是谁、你构建什么、演示视频和 LinkedIn 的链接。不超过 15 行——它是一个路标，不是一篇文章。
置顶仓库（2–4 个）最好的作品是什么？你最强的项目，每个都有真正的 README。严格精选——四个优秀的仓库胜过十二个参差不齐的仓库。
提交图谱他们是否持续构建？数月内的稳定活动。有间断没关系（你有自己的生活）；模式应该体现“定期构建东西”，而不是“前一晚临时抱佛脚地提交”。
语言栏技术栈与说法是否匹配？如果你的 LinkedIn 写着 Python 和 RAG，你的仓库就不应该 90% 是 HTML 教程。

README 优先的仓库：30 秒测试

README 是任何仓库中被阅读最多的文件——也是候选人最忽视的文件。一份优秀的 README 按顺序回答四个问题，评审者应该能在滚动浏览三十秒内获取全部四个答案：

# Ask CityOps — RAG copilot for customer support

> Answers customer questions from ~400 support documents, with
> citations to the source passages. Built as the Stage 4 milestone
> of the Path to FDE curriculum.

## What it does (the demo)
[2-minute demo video link]

## How to run it
pip install -r requirements.txt
uvicorn app.main:app

## How it's built
- Ingestion: document chunking + embeddings
  (see: Feeding the Machine, Embeddings & Vector Search)
- Retrieval: hybrid search over a vector index with exact filters
  for exact facts (see: RAG End-to-End)
- Generation: structured output with per-request citations
  (see: Structured Output)
- Quality: eval set with a versioned scoring rubric
  (see: Evals & Tracing)
- Safety: input validation + guardrails + audit logging
  (see: Guardrails, Approvals & Audit)

## What I'd do next
- Add per-tenant isolation before multi-customer rollout
- Expand the eval set with adversarial queries
- Cut p95 latency with cached embeddings for repeat queries

注意这里真正起作用的是什么。顶部的引用行是 5 秒钟的推介。“如何运行”证明它确实能跑起来——一个没人能运行的仓库只是截图，不是证据。“如何构建”把每个子系统对应到真实的技术（以及真实的经验教训——如果你发布过自己的文章，可以链接到 RAG 端到端、评测与追踪、护栏、审批与审计）。而“接下来我会做什么”是大多数候选人跳过、但评审者会记住的部分——它展示了判断力，而这正是面试要考察的东西。

薄弱版本（先把它拆解）

最常见的候选人仓库：一个 README 只写着

# my-project

再无其他内容，只有一条标题为“final”的提交，没有运行说明，还有——经典的败笔——一个

.env

文件，里面把真实的 API 密钥提交到了仓库。每一个都是信号，而且它们指向同一个方向：

this person doesn't work the way a professional team works.

每一项的修复都很简单、机械，这正是评审者把它们的缺失视为重要信号的原因。

提交规范：作品集中最廉价的信号

提交历史是一份行为记录。“final”、“fix”、“asdf”这样的提交信息会告诉评审者，你把版本控制当成了保存按钮。门槛很低，回报却很实在：

  • 像有人会阅读那样写提交信息： “为 RAG 管道添加逐请求引用校验”胜过“更新一些东西”。使用祈使语气，一行，说明做了什么以及为什么。
  • 小而合逻辑的提交： 每次提交只包含一个功能或修复。评审者浏览你的历史时应该能讲述出项目的演进过程——这就是工程思维的证据。
  • 绝不提交密钥。 API 密钥、令牌、凭证——只要进了 git 历史，就算泄露了。使用列入 .gitignore 的 .env 文件，这正是 密钥与安全基础 课程所教的——但注意：.gitignore 只能防止未来的提交。已经存在于 git 历史中的密钥已经泄露了：撤销/轮换它，并清理历史。在公开的作品集仓库中泄露密钥，是让注重安全的评审者最快把你筛掉的方式。
  • 展示那些乏味的职业素养： 测试（使用 pytest 进行测试）、CI 工作流（使用 GitHub Actions 实现 CI/CD）、能正常构建的项目。提交记录上的绿色对勾是评审者快速浏览时的信号，表明项目是活跃且在维护的。

误区： “评审者会阅读我最好的代码并评判其质量。”

现实： 在筛选阶段，几乎没人会读你的代码。他们浏览 README、扫一眼提交图、确认项目能跑起来。代码质量是在面试中被评判的——当他们让你走查自己的仓库时。所以 GitHub 筛选奖励的是善于讲解和善始善终的人，而赢得它的诚实方式就是真正成为这样的人：完成项目、写好 README、代码可运行。

让它可复用：GitHub 检查清单

  • 个人主页 README 不超过 15 行，附上演示视频和 LinkedIn 的链接
  • 2–4 个置顶仓库——只放最强的作品，每个都 README 优先
  • 每个置顶的 README：一句话简介、演示链接、运行说明、架构概述、“下一步我会做什么”
  • 提交信息使用祈使语气；不要出现 "final"/"fix"/"asdf"
  • 任何仓库历史中不得包含密钥——将 .env 加入 .gitignore
  • 置顶仓库的 CI 保持绿色；测试齐全且全部通过

3. 两分钟演示视频：“哦，这是真的”这道关卡

这是大多数候选人从不制作的材料，而它恰恰是杠杆率最高的一个。LinkedIn 头衔能让人找到你，GitHub 主页能经得起快速浏览，但一段 两分钟的演示视频 能做到前两者都做不到的事：它把能运行的软件呈现在招聘经理面前的屏幕上，让他们切身感受到作品的质量。

最基本的概念：视频不是演讲，而是带解说的屏幕录制。 不要幻灯片。不要对着镜头花九十秒讲解架构。观看者应在前三十秒内看到真实软件完成真实的事情，并听你像一线工程师向客户展示成果那样进行解说。

薄弱版本（先把它拆解）

典型的候选人演示（如果有的话）：时长七分钟，开头用三分钟幻灯片讲“问题空间”和“我们的方法”，真正的演示从第四分钟才开始，现场出了故障，解说者花一分钟道歉和刷新页面。招聘经理在九十秒时就关掉了标签页。这里的每个失败模式都可以修复：限制时长，从能运行的东西开始，并且 提前录制 ——这不是现场编程面试，而是一份作品。录三遍，选出最好的一版。

脚本模板：四个节拍，两分钟

下面的结构是一个可用于任何项目的模板。四个节拍，硬性时间戳——如果某个节拍超时了，删减文字，而不是删减节拍：

THE 2-MINUTE DEMO — script template
====================================
0:00–0:15  THE PROBLEM (15 seconds)
  State the customer problem in one or two sentences. No background,
  no market sizing. The viewer must understand WHY this exists
  before they see a single pixel of UI.

0:15–1:00  THE DEMO (45 seconds)
  Show the thing working, end to end, on screen. Narrate what you're
  doing as you do it. One realistic scenario — not a tour of every
  feature. If it takes more than 45 seconds, your scenario is too big.

1:00–1:30  WHAT YOU BUILT AND HOW (30 seconds)
  Name the key technical decisions, fast. "RAG over the runbook corpus,
  hybrid retrieval, structured-output citations, evals on a labeled
  set." This is the resume in spoken form — vocabulary the hiring
  manager's checklist recognizes.

1:30–2:00  WHAT YOU'D DO NEXT (30 seconds)
  Two concrete next steps, showing judgment. "Per-tenant isolation
  before multi-customer rollout, and expanding the eval set with
  adversarial queries." Never end on "that's it" — end on trajectory.

PRODUCTION NOTES
  - Record your screen at 1080p, narration on a phone mic in a quiet room.
  - Pre-record. Do three takes; ship the best one.
  - Put the video link at the TOP of the repo README and in your
    LinkedIn Featured section. An undiscoverable demo is a private demo.
  - Captions on. Recruiters watch on mute more often than you'd think.

实例演示：Ask CityOps 演示

下面是填好的模板——一个说明性的综合示例，展示学习者的 Ask CityOps 演示（Stage 4 里程碑 的 RAG copilot）可以如何编写脚本。大声朗读一遍，时长应约为两分钟：

诚实规则，打印在脚本旁边： 描述你实际构建的毕业项目——你使用的运行手册语料库、你测量过的评测集、你测试过的防护栏。“如果视频、仓库和评测结果无法证明某个说法，就把它删掉。”400 份文档的生产场景是一个可选的高级扩展，需明确标注为可选——而不是默认的故事。

0:00–0:15  THE PROBLEM
"CityOps support agents answer the same questions every day by searching
through the runbook corpus by hand. Customers wait hours for answers that exist in
the docs. Ask CityOps is a copilot that answers from those documents —
with citations, so the agent can trust it."

0:15–1:00  THE DEMO
[Screen: the Ask CityOps chat interface. Narrator types:]
"What's our SLA for critical outages?"
[The copilot answers in seconds, with two cited passages highlighted
from the source documents.]
"Notice the citations — every claim links back to the exact passage.
Now watch what happens with a question the docs can't answer:"
[Types: "What's our refund policy for alien abductions?"]
"On this unsupported question, the copilot abstains rather than
inventing an answer. One refusal doesn't prove the guardrail — I also test
this behavior against a labeled set of unsupported questions, and the
results are linked in the repository."

1:00–1:30  WHAT I BUILT AND HOW
"Under the hood: document ingestion with chunking and embeddings,
hybrid retrieval with exact filters for exact facts, structured output
so every response carries its citations, and an eval set with a versioned
scoring rubric so I can prove the answers got better as I iterated."

1:30–2:00  WHAT I'D DO NEXT
"Before real customers: per-tenant isolation so one customer's docs never
leak into another's answers, and adversarial queries in the eval set —
the failure mode I'm most worried about is confident wrong answers on
ambiguous questions. Link to the repo and the eval results are below."

为什么这个演示有效：问题具体且贴近人；观看者在第二十秒就看到能运行的软件；“我不知道”的时刻是视频中最有力的三十秒——它展示了防护栏，而这正是招聘经理筛选时看重的判断力；结尾展示了成长轨迹，而不是草草收场。

让它可复用：演示清单

  • 总时长不超过 2:30，0:15 前说明问题，0:30 前屏幕上出现能运行的软件
  • 提前录制，三选一；不在镜头前现场调试
  • 一个真实场景——不是功能展示
  • 如果你的项目有故障处理环节，请把它包含进去（“我不知道”比完美的演示更有价值）
  • 开启字幕；1080p；安静的环境
  • 链接放在仓库 README 顶部、LinkedIn 精选板块，以及你的求职叙事中

把漏斗拼装起来

现在把三份材料都准备好，从头重新审视这个漏斗：

一位招聘人员搜索“RAG engineer LLM production evals”。你的个人简介标题与之匹配——你被搜出来了。她花十秒浏览你的主页：标题、三句话的自我介绍、带有演示视频的精选板块。她点击播放。两分钟后，她看到了可运行的软件、引用来源、拒绝产生幻觉的防护机制，以及一个在谈论下一步计划的构建者。她打开 GitHub：主页 README 指向同一个演示，置顶仓库有真正的 README，提交记录读起来像工程师的日志，CI 全绿。每一道关卡上的证据都保持一致——同一个项目，同一个故事，同一套词汇。

这就是全部的玩法。不是更大的作品集。而是一致的作品集。一个强有力的项目，以三种方式呈现，每一种都针对它所守护的关卡进行了调优。

将其产品化：证据工具包

构建一次，处处复用：

  • 一个锚点项目——在本课程中，Ask CityOps 是天然的锚点：它有真实的问题、真实的检索、真实的评测，以及来自 Milestone 5 的真实部署故事。
  • 三份材料——标题 + 自我介绍（搜索关卡）、README 优先的置顶仓库（证据关卡）、2 分钟演示视频（“真实”关卡）。
  • 一套词汇——在标题、README 和视频解说中使用相同的关键词。一致性是让你在快速浏览后仍被记住的关键。
  • 一个更新习惯——每完成一个项目（包括即将到来的端到端章节），就执行一遍上面的三份清单。证据会过时；要定期刷新。

作品集证据矩阵

本章最有力的举措不是优化任何单一材料——而是在三者之间保持一致、可审计的故事。LinkedIn 上的每一项声明都必须有 GitHub 上的证明和视频中的一个片段：

LinkedIn 声明GitHub 证明视频证明
构建了一个 RAG copilot检索代码 + 评测结果带引用来源的有据回答
实现了安全控制审批与拒绝测试演示了拒答行为
构建了生产级 API端点测试 + OpenAPI 规范可运行的 API 工作流
实践了恢复流程恢复脚本 + 演练日志简短的恢复演示

当三者一致时，你就是可信的。当它们不一致时——LinkedIn 上有声明却没有仓库，视频展示了代码做不到的事情——招聘经理会注意到，面试就会变得尴尬。

2 分钟演示挑战

脚本只是模板。这才是交付物：

  • 使用合成数据或其他已获授权的数据，录制你项目中一个真实的工作流程。
  • 展示一个成功结果和一个已处理的失败案例。
  • 解释一个有意义的技术权衡。
  • 链接对应的代码、测试或评测结果。
  • 以一个局限性和下一个工程步骤收尾。

验收标准：时长不超过 2:30，展示可运行的软件，不包含敏感信息，且每项技术论断都有仓库支撑。这样就把一个有用的模板变成了可验证的作品集成果。

实战检验

  • 你在 LinkedIn 上搜索 "forward deployed engineer RAG"，而你自己的个人主页没有出现在第一页结果中。是哪道关卡没通过？杠杆效应最大的单一改进是什么？
  • 一位招聘经理在你的 GitHub 上花了两分钟，却从未打开任何代码文件。他们看了什么？哪三个信号决定了你是否通过筛选？
  • 你的演示视频长达四分钟，开头是两分钟的幻灯片。请说出脚本模板中的两个结构性修正。
  • 你的“关于”部分目前写着：“充满热情的工程师，热爱构建可扩展的 AI 解决方案，并在敏捷团队中交付价值。”请按照“论断—证明—诉求”的结构，用一个综合示例将其改写为三句话。

查看答案

1. 搜索关卡没通过。杠杆效应最大的改进是个人简介标题：它应包含你是什么人（“后端工程师”）、你想要什么（“目标：前沿部署工程”），以及招聘人员实际搜索的关键词（“RAG”、“applied AI”、“评测”）。（这是一个综合场景——搜索排名还取决于 LinkedIn 的算法和你的人脉网络，这些你无法完全控制。关键词能提升可发现性，但不能保证排名。）

2. 他们看了个人主页、置顶仓库的 README 以及提交记录图。三个信号：他们能否完成事情（置顶仓库完整且配有真实的 README）、他们是否像工程师一样工作（提交信息、测试、CI 通过——而不是只有一次“最终”提交）、他们能否解释自己的工作（README 能回答它是做什么的、如何运行、下一步是什么）。

3. 使用四拍模板把时长压缩到两分钟以内（问题 0:00–0:15，演示 0:15–1:00，构建 1:00–1:30，下一步 1:30–2:00），并把开头的幻灯片替换为前三十秒内出现在屏幕上的可运行软件——配旁白的屏幕录制，而不是演示文稿。

4. 论断：“我是一名构建应用 AI 系统的后端工程师。”证明：“在职业工作之外，我正在构建 CityOps——一个模拟市政运营平台，包含数据接入、REST API、基于检索的 AI、评测和部署实践。”诉求：“我正在探索前沿部署工程师的机会，希望将软件工程与解决客户问题结合起来。”（综合示例——请替换为你自己的真实工作，并将模拟项目标注为模拟。）

最后一点，也是这套课程从不遗漏的 DNA 的一部分：把它讲给一个真人听。 在你动任何个人资料字段之前，先告诉一位朋友——大声地、在六十秒内——你做了什么、为什么重要、以及你想要什么职位。如果你讲得磕磕绊绊，你的标题也会磕磕绊绊。三句话的 About 部分，就是把这段陈述写下来而已。

你的证据包现在是本阶段后续所有内容的基础。下一课将把同一个核心项目转化为你在面试中讲述的故事——因为漏斗的最后一道关卡是一场对话，而到那时，证据已经替你说了一半的话。准备好了之后，请从 Get Hired 页面继续。
