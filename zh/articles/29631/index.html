Microsoft Foundry 部署类型与 Agent 标准配置

FDE Times · 2026-10-09 · 约 5 分钟读完

摘要

文章面向在客户现场交付 AI Agent 的 FDE，梳理 Azure AI Foundry 更名为 Microsoft Foundry 后的四个关键决策：部署类型决定数据在哪里处理，Global Standard 可能在任意区域处理提示词，合规场景应选 Data Zone 或 Batch；Agent 分提示词与托管两类，已有代码的客户宜选托管 Agent；标准配置要求客户自带 Cosmos DB（至少 3000 RU/s）、Storage 和 AI Search，且专用终结点需用 Bicep 或 Terraform 显式声明；Assistants API 已被 Responses API 取代，需尽早规划迁移。

要点

  • 部署类型决定数据在哪个 Azure 区域处理，合规场景应选 Data Zone。
  • Batch 类型异步批处理，价格低 50%，但无实时 SLA。
  • 已有 LangChain 等代码的客户优先选托管 Agent，运行在客户 VNet。
  • 标准配置需 Cosmos DB 至少 3000 RU/s，专用终结点要自己用代码创建。
  • Assistants API 已被 Responses API（Agents v2）取代，迁移应尽早排期。

微软默认推荐 Global Standard，但它可能在任意 Azure 区域处理提示词，欧洲合规团队不会接受。

要点速览

  • Azure AI Foundry 已更名为 Microsoft Foundry，Agent API 也从 Assistants API 迁移到 Responses API（Agents v2）。
  • 进入客户项目后，第一个要定的是部署类型，因为它决定数据在哪里处理。
  • 标准配置运行在客户自己的 Cosmos DB、Storage 和 AI Search 上。Cosmos DB 至少需要 3000 RU/s，专用终结点必须自己创建。

一则招聘“Azure Forward Deployment Engineer（架构师级）”的岗位通过 Dice 发布，也出现在 Arc.dev 上，要求候选人有使用 Azure OpenAI、Semantic Kernel 和 Azure AI Foundry 构建 AI Agent 的实战经验。

与此同时，微软文档已经把这个平台称为 Microsoft Foundry。据 Schneider IT 介绍，新名称自 2026 年 1 月 1 日起生效，现有部署已自动迁移。

Leobit 认为，这次更名远不止换个标签。对前线部署工程师（FDE）来说，名称远不如在客户现场要做的三个决定重要：模型用哪种部署类型运行，用哪类 Agent，以及如何搭建标准配置才不会预配失败。

第一个问题：数据在哪里处理？

部署模型时，部署类型决定了数据在哪里处理、如何计费以及性能如何。微软建议大多数工作负载从 Global Standard 起步：新模型最先在这里上线，价格最低，覆盖的区域也最多。

代价是，选择 Global 类型时，数据可能在任意 Azure 区域处理。

假设你在为一家欧洲保险公司做项目，对方的合规团队要求提示词绝不能离开欧盟。这时 Global Standard 就不再是默认选项。Data Zone 会把处理限定在美国、欧盟或亚太某一个数据区内，因此 Data Zone EU 能满足这一要求。

再假设这家保险公司每晚还要对积压的理赔单重新打分。这项任务不需要实时响应，适合 Batch 类型：请求以异步方式分组提交，配额单独计算，目标是 24 小时内完成，价格比 Global Standard 低 50%，但没有实时 SLA。

部署类型 适用场景
Global Standard 默认选项，适用于客户对数据处理位置没有限制的情况
Data Zone（US、EU、APAC） 合规要求处理必须留在同一数据区内
Batch 任务按批运行，可以接受最长 24 小时的等待以降低成本

这个问题要在第一次需求调研时就提出来，写第一行代码之前。演示跑起来之后再改部署类型，付出的精力远比一开始选对要多。

提示词 Agent 还是托管 Agent？

Agent Service 提供三类 Agent。一端是以声明式方式编写的提示词 Agent；另一端是控制力最强的托管 Agent：你带上自己的代码和框架，由 Foundry 在容器中运行，并负责端点、扩缩容和身份。

两端都可以放进专用网络，所以不要按“哪个更私密”来选。微软文档称，提示词 Agent 支持专用网络，托管 Agent 则支持 BYO VNet，也就是运行在客户自带的 Azure 虚拟网络中。真正的区别在于 Agent 的逻辑由谁编写、归谁所有。

假设一家银行已经有一个用 LangChain 写的 Agent。改用提示词 Agent，就得用声明式方式重写逻辑。托管 Agent 则可以把现有代码原样打包进容器；它运行在客户的 VNet 里，当 Agent 需要调用只能在内网访问的系统时，这是更合理的选择。

无论选哪种，客户的 VNet 仍由对方的网络团队负责。建议：对已有 Agent 的客户，优先考虑托管 Agent，第一周就和网络团队约好时间，并列出 Agent 需要调用的所有内部系统。

真正的工作量在标准配置

Agent 标准配置要求客户自带 Storage、AI Search 和 Cosmos DB，让所有 Agent 数据都留在客户的 Azure 租户内。合规团队会满意，但 FDE 往往要逐个创建这些资源并授予权限。

这里有几个具体的坑。Cosmos DB for NoSQL 账户的总吞吐量至少要 3000 RU/s，低于这个值，预配就会失败。在专用网络中运行的 Agent 需要一个委派给 Microsoft.App/environments 的子网，而且 Foundry 资源必须与 VNet 位于同一区域。

最容易忘的一个坑：部署 Foundry 资源时，通往 AI Search、Storage 和 Cosmos DB 的专用终结点不会自动创建。因此不要在门户里逐项点击，而要用 Bicep 或 Terraform 写出全部配置，显式声明每个专用终结点，再以代码形式交给客户的平台团队。

客户现有代码调用的是哪个 API？

据微软介绍，Foundry 把 Agent、模型和工具纳入同一管理组，内置追踪、监控和评测，并共享 RBAC、网络和策略。原先名为 Azure AI Services 的一组服务现在叫 Foundry Tools，基于 hub 的项目已成为旧版。

正在使用 Azure OpenAI 的客户可以就地把资源升级为 Foundry 资源，同时保留现有端点、API 密钥和状态。因此，调用该端点的应用不需要因为升级而修改配置。

更可能出问题的是 Agent API。Assistants API（Agents v0.5/v1）已让位于 Responses API（Agents v2），后者配有统一的项目客户端。如果客户的代码库仍在调用 Assistants，从一开始就把迁移排进计划，不要等到最后一周才发现。

Azure FDE 要匹配这类岗位，先学什么？

这则岗位把 Azure OpenAI、Semantic Kernel 和 Azure AI Foundry 并列，还要求与企业客户紧密合作，在 Azure 上完成完整 AI 解决方案的需求界定、架构设计和交付。雇主要的是既能构建 Agent、又能把它落地到企业 Azure 基础设施里的人。

学习顺序：先学部署类型和数据驻留，再学标准配置，最后学用 Terraform 或 Bicep 配置专用网络。

简历上要写具体成果，例如“用 Terraform 在专用 VNet 中部署 Agent Service 标准配置，模型运行在 Data Zone EU 上”，而不只是在技能栏里列一个“Azure AI Foundry”。新旧两个名称都写上，无论招聘方搜哪个都能找到你。

产品名称可能还会再变。但数据在哪里处理、Agent 状态归谁、哪些网络路径是开放的，这些问题始终需要有人回答，而回答的人通常就是 FDE。
