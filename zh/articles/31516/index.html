部署标记模式与微服务：FDE 多租户架构怎么选

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

文章以一家银行加六家零售连锁的七客户场景为例，指出 FDE 面对多租户时，真正的问题不是单体还是微服务，而是如何按客户拆分部署。微服务按功能拆代码，解决不了数据隔离和更新节奏等客户级要求；部署标记按客户分组部署独立副本，可满足隔离与差异化发布，但成本高、租户迁移难，需从第一天起采用基础设施即代码。文章还讨论了计算资源合并的代价、地理节点模式在数据驻留场景的局限，并建议求职者在简历和面试中讲清部署决策的权衡。

要点

  • 微服务拆代码，部署标记拆客户，两者不可混淆。
  • Amazon Prime Video 案例显示合并组件可降本 90% 以上。
  • 部署标记满足隔离与更新节奏，但基础设施成本大增。
  • 租户分组应在调研阶段决定，并需基础设施即代码。
  • 数据驻留受限时，宜每区域一个标记加全局路由。

银行要求数据隔离、每季度才更新，零售连锁却要新功能尽快上线，这时部署标记比微服务更关键。

要点速览

  • 微服务能提高应用的容错能力，但对按客户提出的要求无能为力，比如数据分开存放或放慢更新。
  • 把多个任务塞进同一个计算单元成本低，但这些任务会共用发布节奏、故障域和安全上下文。
  • 部署标记把客户分成若干组，代价是基础设施大幅增加，租户也很难在标记之间迁移，因此从第一天起就需要基础设施即代码。

七个客户，一套方案：一家银行，加上六家中型零售连锁。银行不希望自己的数据和别人的放在一起，而且只接受每季度更新一次。零售连锁则希望新功能越快上线越好。假设一个团队要交付的正是这样一组客户，那么常见的第一个问题，即单体还是微服务，其实问错了。

对前线部署工程师（FDE）来说，更重要的问题是客户怎么拆：哪些客户共用基础设施，哪些客户拥有独立副本，哪些客户在什么时候收到更新。

微服务拆的是代码，部署标记拆的是客户。把两者混为一谈，结果就是系统花了大钱，却依然满足不了要求最苛刻的那个客户。

微服务解决的是另一个问题

AWS 介绍微服务时给出了一个明确的好处：服务彼此独立，应用的容错能力因此更强。这个好处是真实的，但也有代价。早在 2014 年，Martin Fowler 就指出，分布式事务出了名地难实现。

Fowler 的建议也很务实：从单体起步，保持模块化，等单体真正开始出问题时再拆成微服务。这种做法适合 FDE。FDE 通常人手少、时间紧，在有人讨论架构是否优雅之前，得先把客户环境跑起来。

反方向的案例也有一个常被引用的数字。据 DevClass 2023 年 5 月报道，Amazon 的一份内部案例研究显示，Prime Video 负责音视频质量监控的团队把分布式组件合并成单个进程，基础设施成本降低了 90% 以上。

这个结果只适用于该团队的具体情况，但它提醒人们：拆分从来不是免费的。

回到银行。把系统拆成 12 个服务，银行的两项要求一项都满足不了。

拆成 12 个服务后，银行仍然和其他所有客户共用一个数据库和一套发布计划。

合并计算成本低，但所有东西都绑在一起

Azure 架构中心有一个模式，和单体“打包在一起省钱”的思路很接近：计算资源合并（Compute Resource Consolidation），即让多个任务共享计算资源以降低成本。这个模式关注的是任务如何在基础设施上运行，而不是代码如何组织，但它清楚地展示了合并的代价。

按照该文档的说法，更新一个任务，就要停止、重新部署并重启同一计算单元里的其他所有任务；合并在一起的任务还共用一个故障域和一个安全上下文。

同一份文档指出，处理高度敏感或隐私数据的任务不应合并，因为它们需要独立的安全上下文。放到服务多个客户的部署上，这就暴露了把所有客户放在一个整体里运行的局限：在第一个客户提出数据隔离要求之前，一切都没问题。

即使采用单体，也有一个错误最好一开始就避开。Microsoft 把所有数据放进单一数据存储列为反模式，因为这会造成资源争用、拖慢性能。建议的做法是按数据的使用方式把数据分开。

代码层面是单体，并不意味着所有数据都得放在一个数据库里。

标记：按客户拆，而不是按功能拆

部署标记从另一个方向切入。它不把应用拆成多个部分，而是部署整个应用的多个独立副本，每个副本有自己的数据存储。在多租户环境中，每个标记服务一组预先划定的租户。

Microsoft 描述过一个与 FDE 工作非常接近的场景：部分大客户可能需要专属实例，小客户则共用一个多租户部署。标记还能处理更新节奏的问题。

有些客户接受频繁更新，有些客户规避风险、希望少更新，因此每个标记可以采用不同的部署环。

套用到这七个客户上：标记 A 只服务银行，拥有独立的数据和安全上下文；标记 B 由六家零售连锁共用。

每个新版本先发布到标记 B，平稳运行几周后才进入标记 A。代码仍然是模块化单体，变的只是部署方式。

标准 合并计算（Compute Resource Consolidation） 微服务 部署标记
拆分维度 不拆分，多个任务运行在一个计算单元中 按功能拆分代码 把客户分成租户组
发布节奏 改一个任务就要重新部署整个单元 无法按客户设定节奏 每组客户有自己的部署环和节奏
隔离敏感数据 共用安全上下文，不适合 无法按客户解决 大客户可以独占一个标记
主要代价 共用故障域 分布式事务难实现 基础设施大幅增加，租户难迁移
适用场景 任务不需要独立的安全上下文 单体确实已经在制造问题 客户在隔离或更新节奏上有差异

这张表容易被读成三个互斥的选项，这是误读。标记是一种部署方式，单体或微服务是一种代码组织方式，所以模块化单体完全可以运行在多个标记上，正如上面银行和零售连锁的例子。

每个副本都要花钱

Microsoft 对代价也说得很清楚：部署多套基础设施副本会显著增加运营成本。把租户从一个标记迁到另一个标记同样困难。因此，哪个客户放在哪个标记上，应该在客户需求调研阶段就慎重决定，而不是等客户已经在生产环境里跑起来之后。

运营多个标记需要基础设施即代码和漂移控制。否则，每当有人在客户环境里手动改一次配置，各个标记之间就会多分化一点。Microsoft 还建议至少部署两个标记，因为只有一个时，很容易把只在单实例下成立的假设写死在代码里。

标记也不是默认选项。按照 Microsoft 的说法，如果方案很简单、不需要大规模扩展，或者单个实例就能扛住负载，就不应使用这个模式。只有一个客户，或者所有客户都接受共享时，一个数据分离合理的模块化单体就够了。

客户要求数据留在特定区域时

还有一个选项：地理节点（geode）。与标记只服务一组客户不同，每个地理节点实例都能服务任何用户。Microsoft 表示，地理节点的设计和构建通常复杂得多，适合对数据位置没有限制的云原生平台。

所以在考虑地理节点之前，要先在一开始问清客户是否有数据位置方面的要求。Microsoft 指出，如果存在数据驻留要求，或者应用需要为会话保存临时状态，地理节点就不太合适。

这种情况下，Microsoft 建议采用标记，并配合一个全局路由层，把每个请求发到正确的标记。

如果客户要求数据绝不离开某个区域（银行、医院和政府机构经常这样要求），答案几乎是现成的：每个区域一个标记，前面加一层路由。它不是最巧妙、也不是理论上最漂亮的方案，但它能向客户的合规团队讲清楚。

写给想成为 FDE 的开发者

阅读 FDE 或解决方案工程师岗位的职位描述时，留意 multi-tenant、single-tenant deployment、dedicated instance 和 infrastructure as code 这类词。它们说明这家公司面对的正是拆分客户的问题，需要同时理解架构两条轴的人。

写简历时，不要只写“把系统迁移到微服务”。要讲清楚部署方式是怎么定的、为什么这么定：哪个客户拥有独立实例、原因是什么，发布节奏如何划分，采取了哪些措施防止环境漂移。

讲清一个权衡过利弊的决策，远比罗列一串技术更有说服力。

面试中如果被问到“单体还是微服务？”，好的回答通常先反问：有多少客户，他们之间有什么差异？在 FDE 岗位上，客户怎么拆，往往比代码怎么拆更能决定项目成败。
