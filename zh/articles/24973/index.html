LLMOps 是什么？与 MLOps 的区别、运营周期与 FDE 实务详解

原标题：LLMOpsとは？MLOpsとの違い・運用サイクルとFDEの実務を解説

FDE総研 · 2026-10-02 · 约 12 分钟读完

摘要

这篇日文文章系统讲解LLMOps的定义、与MLOps的差异及实际运作方式。作者认为LLMOps的核心不是基础设施，而是如何定义和衡量输出质量，涵盖模型选择、提示词管理、评测、监控、护栏与成本控制。文章提出“计测→评测→改进→验证→发布”的小步循环，强调评测集应从生产日志中的失败案例持续积累。对FDE而言，LLMOps正成为核心业务：与客户共同制定评测标准、分析日志、改进系统，并让客户团队能够自主运营。企业应把LLM应用视为持续运营的业务基础而非交付物，长期竞争力取决于能否建立衡量自身业务效果的机制。

要点

  • LLMOps覆盖模型选择、提示词管理、评测、监控到护栏与成本的全生命周期。
  • 与MLOps不同，改进主要靠调整提示词和RAG，而非重新训练。
  • 运营遵循计测、评测、改进、验证、发布的小步循环，评测集持续扩充。
  • FDE负责把业务标准转化为评测、分析日志并让客户自主运营。
  • 企业应把LLM应用当作持续运营的基础设施，而非一次性交付物。

什么是 LLMOps？其含义及被需要的原因是什么？

LLMOps 是一种运营理念，旨在让集成了 LLM 的应用在生产环境中稳定运行，并持续改善质量、安全性和成本。

LLMOps 是“Large Language Model Operations”的缩写。它涵盖了让基于 GPT、Claude 等 LLM 的聊天机器人、RAG（检索增强生成）、AI Agent 不是做完就束之高阁，而是在业务中持续运转的方法、工具和体制。

LLMOps 的定义涵盖到什么范围？

LLMOps 所涉及的范围，是从模型选型到提示词管理、评估、监控、改进的整个生命周期。

一般来说，人们常把以下领域统称为 LLMOps。

  • 模型选型与切换：商用 API、开放权重模型、微调后模型的区分使用
  • 提示词与上下文管理：系统提示词、Few-shot 示例、RAG 所传递文档的版本管理
  • 评估（评测）：用测试集持续衡量输出的准确性、有用性和安全性
  • 可观测性（Observability）：记录每次请求的输入输出、延迟、Token 消耗和错误
  • 护栏（Guardrails）：防范个人信息泄露、不当输出和提示词注入

它常被理解为“运行 LLM 的基础设施问题”，但实际上其重心更多在于“如何定义和衡量输出质量”。这正是 LLMOps 的特点。

为什么现在需要 LLMOps？

LLM 即使输入相同，输出也会波动，模型更新后行为也会改变。因此仅靠传统测试无法保证质量。

LLM 应用的 PoC（概念验证）几天就能做出来，但一到生产运营就会出现另一层面的难题。整理现场经常听到的问题，如下所示。

问题具体会发生什么LLMOps 的应对
输出的非确定性即使是相同的问题，回答的表述和结论也会变化通过评估集进行回归测试
模型更新的影响提供商侧的模型更新或旧模型停用导致行为变化固定模型版本，并在迁移前进行比较评估
幻觉输出看似合理的错误信息RAG 提供依据、事实性评估、人工审核
成本波动使用量增加或提示词膨胀导致 API 费用上涨Token 计量、缓存、区分使用模型
安全性提示词注入或敏感信息混入输入输出过滤、权限设计、审计日志

作为 FDE（Forward Deployed Engineer）在客户企业部署 LLM 应用时，往往会遇到“演示时运行良好，但用现场数据精度就下降”的壁垒。把 LLMOps 理解为跨越这道壁垒所需踏实的机制建设，可能更贴近实际感受。

MLOps 与 LLMOps 的区别是什么？

MLOps 的核心是“训练模型并运营”。而 LLMOps 的核心则是“如何用好现有的基础模型”。

LLMOps 是 MLOps 延伸出来的概念。但为了改进而调动的手段以及质量的衡量方式有很大不同。

MLOps 与 LLMOps 在对比表中有何不同？

最大的区别在于改进手段。MLOps 以再训练为主，而 LLMOps 以提示词和上下文的调整为主。

视角MLOpsLLMOps
主要对象自行训练的预测、分类模型使用外部或开放基础模型（LLM）的应用
改进的主要手段特征量设计、再训练、超参数调整提示词、RAG 的检索精度、模型选择、必要时进行微调
质量评估准确率、AUC 等定量指标明确没有唯一正确答案，需结合 LLM-as-a-Judge 和人工评估
主要成本训练用计算资源推理时的 Token 计费，或推理用 GPU
版本管理的对象数据、模型、代码提示词、模型名称与版本、检索索引、评估集
主要风险数据漂移、精度劣化幻觉、提示词注入、信息泄露
相关人员数据科学家、ML 工程师应用工程师、业务领域负责人、FDE

MLOps 的经验在 LLMOps 中能用到什么程度？

确保可复现性、自动化测试、监控、分阶段发布等 MLOps 原则，在 LLMOps 中同样可以作为基础直接沿用。

“将数据、代码和模型一起进行版本管理”“监控生产行为并检测劣化”这些理念在 LLMOps 中也没有改变。MLflow、Weights & Biases 等 MLOps 起源的工具也在不断强化 LLM 的追踪记录和评估功能。

另一方面，LLMOps 有一个不同之处：需要与业务负责人一起构建评估设计。因为“这个回答在业务上是否正确”往往不是工程师单方面能判断的。这正是深入客户现场的 FDE 发挥作用的地方。

LLMOps 的构成要素是什么？

把 LLMOps 分为“提示词与数据管理”“评估与监控”“护栏与成本管理”三个角色来考虑，更容易理清思路。

从工具名称入手容易迷失整体方向，建议先按角色进行分解。

提示词和数据如何管理？

提示词、RAG 用的文档、评测数据要与代码一样进行版本管理，以便追踪变更历史。

  • 提示词的版本管理：用 Git 管理，或使用 Langfuse、LangSmith 等提示词管理功能。要能确定生产环境中运行的是哪个版本
  • RAG 的数据管道：将文档导入、分割（chunking）、嵌入生成、索引更新做成可重新执行的形式
  • 评测数据集：将代表性问题与期望回答、判定标准成套积累起来

在实际工作中，提示词直接写在应用代码里不断增多、谁在何时改的都搞不清楚的情况并不少见。尽早让团队达成“提示词也是交付成果”这一共识，之后会轻松很多。

评测和监控要测量什么？

评测从质量、安全性、延迟、成本四个维度进行测量，并将发布前的测试与生产环境的监控分开设计。

维度代表性指标测量方法示例
质量准确性、与依据的一致性、回答的有用性评测集＋LLM-as-a-Judge、人工抽样评测
安全性不当输出的比例、是否混入敏感信息基于规则的过滤器、分类模型
延迟响应时间、首 token 时间汇总追踪日志
成本每次请求的 token 数、费用API 使用日志、仪表盘

在生产环境监控中，用户的“有用／没用”反馈、回答后的再次提问率等间接指标也很有效。LLM-as-a-Judge 虽然方便，但作为判定者的 LLM 本身也有其偏差。稳妥的做法是定期与人工评测进行对照，确认判定是否出现偏差。

护栏和成本管理要做什么？

护栏是保障输入输出安全的机制，成本管理是通过模型的合理选用和缓存来控制费用的机制。

护栏的典型示例如下。

  • 输入侧：个人信息脱敏、提示词注入检测
  • 输出侧：违禁表述过滤、抑制无依据的断言、输出格式（JSON 等）校验
  • 权限侧：根据用户权限限定 RAG 可引用的文档范围

在成本管理中，常用“路由”方式：复杂任务分配高性能模型，常规的分类或摘要分配轻量模型。利用提供商提供的提示词缓存也很有效。但削减幅度因用例而异，因此先进行测量再采取措施的顺序才是现实的。

LLMOps 的运营周期如何运转？

LLMOps 的运营是通过小步重复“测量→评测→改进→验证→发布”的循环，在培育评测集的同时不断提升质量。

不要试图一次完成，而是以持续从生产日志中学习为前提来设计循环。

运营周期的基本步骤是什么？

基本流程共 6 个步骤。事先确定评测标准，是让改进不依赖直觉的关键。

  • 用例与评测标准的定义：与业务负责人就“支持谁的什么业务、达到什么水平才算合格”达成一致
  • 基线构建：用简单的提示词和模型制作初版，用评测集测量得分
  • 追踪数据的收集：在生产或试点环境中记录输入输出、检索结果、延迟、成本
  • 失败的分析与分类：将错误回答按模式分类（检索遗漏、误解指令、知识不足、格式错误等）
  • 改进与回归测试：决定修改提示词、检索还是模型，然后修改，并用评测集确认没有退化
  • 分阶段发布：经过对部分用户的限定公开或 A/B 测试后推广至全体，然后回到第 3 步

评测集如何培育？

评测集不必一开始就追求完美，而是通过持续添加生产中发现的失败案例来逐步培育。

启动阶段，比较现实的做法是请业务负责人列出“常见问题”“答错会很麻烦的问题”，从几十条左右的小型评测集开始。运营开始后，将用户给出低评价的回答、通过日志分析发现的错误回答添加到评测集中。以此建立不再重复同样失败的机制。

评测集培育起来后，也更容易做出更换模型的判断。因为新模型发布时，可以立即比较“对本公司业务能提升多少”。

小步运转循环的诀窍是什么？

与其一开始就配备厚重的工具群，不如从追踪记录和评测集这两项入手，这样能更快地运转循环。

从一线的体感来说，按以下顺序完善可以减少返工。

阶段首先要完善的可以延后的
PoC评测标准的共识、少量评测集正式的仪表盘
试点追踪记录、失败分类的习惯自动路由
生产回归测试自动化、成本监控、护栏微调（确认有必要之后再做）

微调虽然是强有力的手段，但很多问题通过改进提示词或检索就能解决。先用评测数据确认“提示词已到极限”之后再考虑，更容易说明投入产出比。

FDE 在 LLMOps 中承担的角色和所需技能是什么？

FDE 站在客户业务与 LLM 应用之间，在现场一贯承担从制定评测标准到生产环境改进的工作。

FDE 是在 Palantir 兴起的职位，是深入客户现场、让软件在业务中落地的工程师。在提供生成式 AI 导入支持的企业中采用 FDE 型体制的越来越多，LLMOps 正逐渐成为 FDE 的核心业务之一。

在 LLMOps 现场中 FDE 具体做什么？

FDE 的工作是将“业务上的正确答案”落实到评测中，通过查看日志进行改进，并留下客户能够自主运转的运营体系。

阶段FDE 的主要工作
需求定义观察业务流程，划分交给 LLM 的范围和由人判断的范围
评测设计与业务负责人一起制定评测集和合格标准
实现实现提示词、RAG、工具集成，并与客户现有系统对接
运营改进分析追踪数据，针对每种失败模式采取改进措施
落地固化交接流程和仪表盘，让客户团队能够自主运转评测与改进

与一般的 SI 或委托开发不同的是，FDE 会在客户现场直接运转评测与改进的循环本身。这与按规格书开发后交付的推进方式有很大差异，往往需要花更多时间与客户一起深挖“精度提不上去的原因”。

擅长 LLMOps 的 FDE 需要哪些技能？

需要的是 LLM 应用实现能力、评测设计能力和业务理解能力这三项，其中评测设计能力是最容易与其他职位拉开差距的领域。

  • 实现能力：使用 Python 等进行应用开发、API 集成、RAG 构建、云端部署
  • 评测设计能力：将模糊的业务质量转化为可衡量的标准并加以表述，进而实现为评测集的能力
  • 可观测性知识：设计追踪、日志和指标，从而定位失败原因的能力
  • 安全与治理：权限设计、个人信息处理、应对客户内部规章
  • 业务理解与沟通：从一线负责人那里挖掘隐性知识，并向管理层说明投资回报的能力

有 MLOps 或 SRE 经验的工程师可以直接运用监控和自动化方面的知识。Web 应用开发者则可以先积累构建评测集并进行回归测试的经验，这样更容易掌握 LLMOps 的要领。

考虑引入 FDE 的企业应如何看待 LLMOps？

企业需要将 LLM 应用视为“需要持续运营的业务基础”，而非“交付物”，并对评测与改进体系进行投资。

生成式 AI 引入失败的常见案例包括：停留在 PoC 阶段，或引入后无人再关注精度。无论是从外部引入 FDE 还是在内部培养，如果在合同或体制搭建阶段就确定以下几点，运营就不容易流于形式。

  • 由谁制定评测标准和合格线，由谁审批
  • 为改进目的分析生产日志的允许范围（个人信息、敏感信息的处理）
  • FDE 支持结束后，负责运转评测与改进的内部人员

LLM 的性能今后还会持续更新。正因如此，比起模型本身的性能，是否拥有“能够衡量自身业务好坏的机制”才是长期竞争力的关键。LLMOps 就是让这一机制在现场扎根的实务工作，对 FDE 而言也是容易发挥专业能力的领域。
