FDE 项目结项评审：三个类别

原标题：FDE project close-out review: three buckets

FDE Times · 2026-11-05 · 约 7 分钟读完

摘要

文章提出FDE项目收尾复盘不应流于形式，而要把所有遗留事项归入三个桶：经验教训、剩余债务和产品问题，每项指定具体负责人和优先级。商业类请求应先过滤，转交CSM或TAM等负责客户关系的人。文章引用PostHog和Google SRE的做法，强调无指责文化、客户须参与会议、成果存入共享仓库，并警告不要私下绕过产品缺陷写定制代码，否则会滑向为单个客户造软件。文中给出事件跟踪部署的示例表格、产品问题模板和练习题，最后建议FDE把反馈闭环能力写进简历。

要点

  • 遗留事项必须归入三桶之一，并指定负责人。
  • 商业请求先过滤，转交客户关系负责人。
  • 绕过产品缺陷的补丁会变成定制代码，须记录为债务。
  • 复盘须无指责、客户参与，并存入共享仓库。
  • 反馈闭环和可复用工具应写入FDE简历。

每一个未了事项都属于三个类别之一（经验教训、遗留债务或产品问题），并且在前沿部署工程师离开之前，每一项都需要指定负责人。

简要说明

  • FDE 是最先碰到产品粗糙边缘的人，因此总结会议正是把这些摩擦转化为有负责人工作的时机。
  • 将商业需求转交给负责客户关系的人，然后把每个剩余事项归入且只归入一个类别，并指定负责人和优先级。
  • 没有人会重读的复盘毫无价值，所以要把它存入共享知识库，并有意识地完成客户关系的交接。

部署的最后一周总是很忙碌：交接账户、撤销权限、发送文档。总结复盘通常被压缩到最后半小时，以“一切顺利”收尾。几个月后，下一个客户在同一个问题上栽跟头，却没有人记得上次是怎么处理的。

PostHog 的手册将 FDE 描述为在真实客户负载下最先遇到产品粗糙边缘的人。手册还明确指出，在现场收集的背景信息能帮助更快地为后续客户解决问题。

因此，总结会议不是走过场。这是你唯一能确定合适的人在场的时刻，可以把这些摩擦转化为有负责人的工作，然后你再转向下一个项目，而知识不会随你流失。

每个事项都归入三个类别之一

项目结束时仍未解决的所有事项，都应归入且只归入三个类别之一。经验教训是会改变你下次工作方式的事情。遗留债务是客户或你的团队仍需完成的工作，要有负责人和截止日期。产品问题是只有产品团队才能解决的问题。

在分类之前，先过滤掉一类不属于这个技术会议的事项：商业需求，比如客户想要增加范围。在 PostHog，与客户的商业关系属于该客户的 TAE、TAM 或 CSM，而不是 FDE。在会议开始时说明这一点，记录这些需求并直接转交。

对于其他所有事项，分类的问题是：如果下一个客户遇到这个问题，谁必须去修复它？如果答案是负责该功能的团队，PostHog 有一条明确的规则。当项目因只有产品团队才能解决的问题而受阻时，FDE 应把工作交给该团队，而不是绕过它。

这条规则防范的是一个具体的风险。Tandem 总结了 Marty Cagan 对 FDE 模式的批评：危险在于逐渐演变为为每个客户构建定制软件。只有当现场学到的东西回流到共享产品中，而不是沉淀为定制代码时，这种模式才能奏效。

无论某个条目归入哪个类别，整场会议都需要一个共同的前提：不指责。Google SRE 手册中关于复盘文化的章节指出，你无法“修复”人，但你可以修复系统和流程。

客户也必须在场：一份关于项目收尾的指南强调，经验总结会要与客户一起进行，而不是作为你团队的内部复盘。

设想一次分析部署

想象你刚完成了一个电商应用的事件埋点部署。会议之前，你把工单、消息和笔记整理成一个包含六个条目的原始清单。下表展示了它们如何被分类，其中包括一个在分类前就被过滤掉的条目。

条目类别负责人下一步
同步到数据仓库的任务很慢，因为它在客户的高峰时段运行遗留债务客户的数据工程师重新安排任务时间，并设定截止日期
用户长时间离线时 SDK 会丢失事件产品问题负责 SDK 的团队开一个涵盖全部四个要点的问题
为绕过上述 SDK 缺陷而写的临时代码遗留债务FDE在问题中链接它，并记录移除日期

仔细看其中三行。临时方案没有被隐藏：它被记录为债务并链接到产品问题，这样一旦 SDK 团队发布了修复，就会有人记得把它移除。

事件重命名脚本变成了一项资产。PostHog 将构建参考实现、示例以及能加快后续项目速度的内部工具视为 FDE 工作的一部分。

最后一行是最初被过滤掉的条目。当客户在评审中提出新的需求范围时，正确的做法是记录下来并转交给负责商业关系的人，而不是当场做出承诺。

对于产品问题，PostHog 要求 FDE 通知负责该领域的团队，并开一个问题，说明哪里出了问题、谁会受到影响、它阻碍了什么以及如何复现。一个可以直接套用的模板：

Title: SDK drops events when the device is offline for a long time

What is broken: events recorded while offline are not sent after the connection returns
Who hits it: e-commerce customer, mobile app, users in areas with weak signal
What it blocks: the checkout funnel report is missing data, the customer does not yet trust the numbers
How to reproduce: turn on airplane mode, navigate a few screens, wait a long time, reconnect, check the events
Current workaround: workaround code in the customer's repo (link), to be removed after the fix

逐步进行会议

会议之前，把草拟的表格发给客户，以便他们补充内容。没有人愿意在会议进行中第一次听到一长串问题。会议期间，逐条过一遍每个条目，确定其类别，然后通过指定具体的人来确定负责人，而不是“另一个团队”。

最难的一步是确定优先级。Google 的 SRE 手册对每次评审都提出一个问题：行动计划是否合理，修复措施是否被赋予了正确的优先级？如果一个阻塞了客户主要报表的产品问题被标记为“低”，那这次会议就算失败了一半。

会议结束后，把结果存入一个共享的资料库。Google 建议将复盘报告保存在一个集中的地方，让其他人能够找到并从中学习，并且直言不讳地指出，未经评审的复盘报告等于从未存在过。关于结束项目的指南也表达了同样的意思：把它存放在团队下次能找到的地方。

最后一项任务：同一份指南指出，结束一个项目不只是发送账单，即使在项目结束之后，客户关系也应该被有意识地交接出去。在总结邮件本身中，把客户介绍给今后负责他们的人。

让会议变得毫无价值的错误做法

最常见的错误是把会议变成一场审判，比如“是谁耽误了访问请求？”。这样一来客户就会沉默，而你恰恰失去了最值得学习的故事。第二个错误是只开内部会议而不邀请客户，这会导致客户方没有人来认领剩余债务清单中的事项。

第三个错误更难察觉：因为比提交 issue 更快，就悄悄绕过产品缺陷。每一个这样的补丁都是一段定制代码，正是 Cagan 所警告的那种。

PostHog 写道，把客户问题反馈回来的意义在于改进产品路线图。一个只存在于客户仓库里的补丁对路线图毫无帮助。

最后一个错误是模糊的 issue，只有一行字：“SDK 有一个离线 bug”。如果产品团队无法复现它，他们就不会安排修复。上面模板中的四个要点，正是把你在现场目睹的情况转化为其他团队可以着手处理的工作的关键。

这项技能也应该写进你的简历。PostHog 将把经验教训反馈到产品中并构建可复用的工具描述为 FDE 职责的一部分，所以值得展示出来，而不只是写一句“为客户 X 做了部署”。

说明你为产品团队提交了多少个 issue，哪些被修复了，以及你构建的哪些工具正在被后续项目复用。阅读职位描述时，留意其中是否提到与产品团队的反馈闭环：这是公司认真对待这项工作的一个信号。

练习：你会如何对这六项进行排序？

想象你刚刚结束一个客户支持 AI Agent 的部署。原始清单有六项。第一：产品 API 在摄取大文档时会超时。第二：为绕过该缺陷而将文件拆分成块的代码。第三：客户的 IT 团队尚未停用测试账号。

第四项：你为给 Agent 的回答打分而编写的评测套件。第五项：项目损失了两周时间，因为没人知道客户方由谁批准数据。第六项：客户询问扩展到更多部门的定价。先自己分类，再阅读下面的答案。

答案：第六项首先被过滤掉，转交给 CSM 或 TAM。第一项交给产品团队，附带一个涵盖全部四个要点的 issue。第二项是 FDE 的技术债，链接在该 issue 中。第三项是由客户方指定人员负责的技术债，并设有截止日期。

第四项是一条经验教训，转化为工具并添加到内部仓库。第五项也是一条经验教训：下次在项目启动会上就要询问数据审批人的姓名。如果你把第二项弄错了，请重读为什么补丁不能被隐藏。

当下一个客户不必再付出这个客户已经付出的代价时，项目才算真正结束。
