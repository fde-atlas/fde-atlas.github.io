Postman Student Expert 停发，FDE 简历怎么写

FDE Times · 2026-11-15 · 约 4 分钟读完

摘要

Postman 已于 2026 年 3 月 23 日停办学生项目，Student Expert 课程从 Postman Academy 下架，徽章不再发放。文章认为这枚徽章本就只能证明学完一门 API 入门课，无法体现 FDE 所需的客户协作能力，建议学生用调用真实 API、附数字和 README、可被招聘方核查的项目替代证书条目。

要点

  • Postman 学生项目于 2026 年 3 月 23 日停办，徽章停发。
  • 3 月 2 日前完成课程者仍可在 Parchment backpack 找到徽章。
  • 徽章只证明 API 基础，与客户协作能力无关。
  • 简历应写带数字、链接和 README 的真实 API 项目。
  • 项目若涉及真实用户，应写明与利益相关方的沟通。

课程里的 API 基础仍值得学，但简历上的证据应是自己做的、招聘方能打开核查的项目。

要点速览

  • Postman 已关闭学生项目（Student Program），从 Postman Academy 下架 Student Expert 课程，也不再支持领取徽章的步骤。
  • 即使在项目运行期间，这枚徽章也只能说明你学完了一门自定进度的 API 基础课，与客户协作能力毫无关系。
  • 在 FDE 简历上，用一个调用真实 API 的项目替换证书条目，附上数字、README 和链接。

很多技术专业的学生曾在 LinkedIn 个人资料上挂过同一张证书：Postman API Fundamentals Student Expert。2026 年 3 月 23 日，Postman 社区 Help Hub 上的一则通知用一句话为它画上句号：学生项目（Student Program）已正式停办。

当天零点，Student Expert 课程从 Postman Academy 下架。Postman 的解释是，界面改版后，最后一步（分享 collection 以领取徽章）已不再支持。3 月 2 日前完成课程的人，仍可在自己的 Parchment backpack 中找到徽章。

征兆其实来得更早。3 月初的一个社区帖子显示，截止日期前，Free 套餐账户的徽章领取就已失效，而付费套餐用户仍能领取。

如果你原本打算靠这门课在前线部署工程师（FDE）岗位申请里加一条“API 技能”，可以放弃这个计划了。更值得问的是：这条证书究竟证明过多少东西，又该用什么来替代。

同一条简历，两种写法

设想同一份简历上的两行。第一行：“Postman API Fundamentals Student Expert”。

第二行是一个示例：“针对一个公开支付 API 构建了包含 12 个请求的 collection，处理了 token 过期、分页和 429 错误；README 记录了运行方法和遇到的 3 个失败案例。”这一行有链接可以打开核查，给面试官留下了可问的问题，而且不管哪门课程关停，它都依然成立。

Aced（原 Exponent）的 FDE 简历指南定了一条规则：每个要点都应以一个数字结尾。Scaler 同样把一条弱表述“为客户报表构建了数据管道”和一条强表述并列，后者讲清了范围：一条从客户三个数据源拉取数据的 Python 管道。上面第一行两项测试都通不过。

它之所以弱，是因为它描述的是课程，而不是你。2022 年，Postman 把这枚徽章改为正式名称 API Fundamentals Student Expert Certification，因为“Student Expert”这个名字给更高级的认证留不出空间。这枚徽章通过 Badgr 颁发，学员须完成两门课程：Intro to APIs and Postman，以及认证课程本身。

Postman 将该项目描述为一套自定进度、注重动手的课程，目标是提升“API 素养”，面向任何专业的学生。Postman 自己也宣传这枚徽章适合放在 LinkedIn 或简历上。它能证明一项基础技能，适合大二学生，但对你如何与客户协作、如何为客户部署，什么也说明不了。

而这恰恰是 FDE 招聘方想知道的。客户的 API 返回的结果和文档对不上时，你怎么应对？一枚入门徽章回答不了这个问题。

没有 FDE 头衔，证据放在哪里？

Aced 指出，对从未担任过 FDE 的候选人来说，项目（Projects）部分尤其有价值。Scaler 补充说，作品集（例如一个附有像样 README 的代码仓库）应当展示两页简历装不下的内容。

所以合理的顺序是：扎实学好 API 基础，做一个调用真实 API 的项目，写一条带数字的简历条目，最后配上 README，让招聘方能自己核查。

如果项目有真实用户，比如某个社团，或熟人经营的一家小店，要写明你和他们沟通过。Aced 建议明确写出与用户或利益相关方的协作，因为那是 FDE 工作的另一半。

collection 的 README 应该怎么写？

下面是一份示例模板，对应上文例子中的公开支付 API。

# Collection：支付 API（试用版）

如何运行
- 导入 collection 和环境文件
- 在环境中设置 API_TOKEN 变量；不要把 token 写进请求

认证
- 通过请求头 Authorization: Bearer {{API_TOKEN}} 发送 token
- 遇到的情况：运行中途 token 过期返回 401；脚本停止并给出清晰提示

分页
- API 在响应中返回 cursor；下一个请求读取该 cursor
- 检查：最后一页没有 cursor，循环正确停止

429 错误（超出速率限制）
- 读取 Retry-After 请求头，等满时间后重试
- 记录每次运行的重试次数

尚未完成
- 未在超过几页的数据量下测试

最后一节和前面三节同样重要。写明自己的局限，面试官的下一个问题就有了着落，主导对话的是你。再准备一个具体案例：某次 API 返回了错误结果，你是如何追查原因的。

已关停的课程里，有三点值得保留

第一，API 基础仍是第一位的。Postman 设定的“API 素养”目标依然正确：读懂请求和响应，理解状态码、请求头和认证。如果这是你的短板，先把它补上，再去学 Agent 或检索增强生成（RAG）。

第二，在动手中学习。这门课围绕动手练习设计，这种学法正适合 FDE 工作。读文档记不住 token 在运行中途过期时系统会怎样，自己调用一次就能记住。

第三，学习和证明是两件事。用课程来学，再用自己的作品来证明。当 FDE 招聘启事里出现“与客户系统集成”这类表述时，就在技能条目旁边直接放上你的 collection 链接。

Student Expert 徽章已经没人再发了。调用 API、记下发生了什么、让别人能复现，这个习惯仍会跟着你走进每一场面试。
