客户 VPC 部署和 BYOC 是什么：FDE 部署模型指南

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

这篇文章讲解 FDE 常见的客户 VPC 与 BYOC 部署模式：两者本质相同，只是描述视角不同，且控制平面通常仍留在厂商账号中。作者以 Databricks 的控制平面与计算平面划分为例，说明如何向客户安全团队划清边界，并给出部署地图模板、五个实操步骤，以及安全评审、物理隔离网络和升级路径等常见陷阱。

要点

  • 客户 VPC 与 BYOC 是同一模式，仅视角不同。
  • 关键在于划清控制平面、计算与数据的边界。
  • Databricks 文档清晰区分控制平面与计算平面。
  • 部署地图应列出所有跨越边界的数据出站项。
  • 上线后升级、扩容与事故响应同样重要。

要点速览

  • 客户 VPC 和 BYOC 是同一模式，只是视角相反。控制平面通常仍留在厂商的账号里
  • 在答应客户之前，先划清控制平面、计算和数据之间的边界，再列出跨越边界的一切
  • 上线只是工作的前一半。升级、扩容、事故响应和安全评审构成另一半

设想你和一家银行的第三次会议。演示很顺利，业务团队也已认可。这时安全负责人问：你们的系统能否运行在银行的 VPC 里？

很多刚接触前线部署工作的工程师会脱口而出：“能。”这个回答风险很大。客户真正想问的是：软件运行在谁的基础设施上，数据存放在哪里，厂商还保留哪些控制权。

如果你还说不清这套架构，“能”就只是一句承诺，而安全团队之后会逐项核查。

回答这个问题，本身就是许多前线部署工程师（FDE）岗位职责的一部分。Sierra 招聘 Forward Deployed Infrastructure Engineer 的启事写明了范围：在客户环境中设计部署架构，包括 VPC 配置、权限配置、网络和基础设施供给。

想做这个岗位，就必须能和客户的基础设施团队对话。

三种模式，一个问题：什么放在哪里？

采用 SaaS 时，一切都运行在厂商的账号里，客户把数据发送过去。另一端是本地部署（on-prem）。Northflank 的文档将其描述为：软件运行在客户自有数据中心或私有基础设施的硬件上。它与客户 VPC 最大的区别在于，本地部署不依托云服务商。

客户 VPC 介于两者之间：软件运行在客户的云账号里。Northflank 指出，自带云（BYOC，Bring Your Own Cloud）是同一种模式，只是从客户一侧来描述。所以客户说“BYOC”，销售说“部署在客户 VPC”，双方指的是同一件事。

关键细节在于：即使软件运行在客户的云里，控制平面通常仍留在厂商的账号中。控制平面负责编排、CI/CD、配置、监控和更新下发。因此，“运行在客户的 VPC 里”几乎从来不意味着所有东西都在客户的 VPC 里。

Databricks 展示了边界在哪里

Databricks 是最容易学习的例子，因为它的文档把边界划得很清楚。控制平面由 Databricks 在自己账号中管理的后端服务组成。负责计算的部分被单独划出，称为计算平面。

采用经典计算（classic compute）时，计算资源运行在客户的 AWS 账号里。采用 serverless 时，计算运行在 Databricks 账号内的计算层。同一个产品，对“计算在哪里发生”给出了两种不同答案。客户选择 serverless，就能获得更多便利，但也必须接受计算不再位于自己的账号中。

这正是你需要向客户解释的权衡。下表按安全团队常问的问题对比三种模式。

问题SaaS客户 VPC / BYOC本地部署
基础设施归谁厂商客户的云账号客户的数据中心
控制平面厂商通常仍是厂商视设计而定；有时没有通往厂商的路由
敏感数据离开客户可以留在客户 VPC 内留在客户基础设施上
FDE 最难的部分合同和数据流网络、权限、对等连接没有云的情况下做更新和支持

本地部署这一列最值得细读。当控制平面没有通往厂商的路由时，难点就不再是首次安装，而是如何把更新送进去。下文“常见错误”一节会再谈到这一点。

示例：为银行准备的部署地图

回到银行的问题。不要直接说“能”，而是承诺发一份部署地图。E2B 的 BYOC 文档是很好的参照，因为它准确列出了哪些留下、哪些离开。

根据 E2B 的说法，沙箱模板、快照和运行时日志都存储在客户的 BYOC VPC 中。只有匿名化指标会发回 E2B 的云端，用于可观测性；VPC 对等连接提供私有网络连接。BYOC 集群通过 Terraform 配置和机器镜像来供给。

你的地图可以是这样（示意模板，并非任何产品的真实配置）：

deployment_model: customer_vpc   # 客户称之为 BYOC
control_plane:
  location: vendor_account
  responsibilities: [orchestration, ci_cd, config, monitoring, updates]
compute_plane:
  location: customer_aws_account
data_at_rest:            # 留在客户的 VPC 内
  - templates
  - snapshots
  - runtime_logs
egress_to_vendor:        # 所有跨越边界的内容
  - type: metrics
    anonymized: true
    purpose: observability
connectivity: vpc_peering
provisioning: [terraform, machine_image]
iam: least_privilege_role_for_vendor

（行内注释分别是：“客户称之为 BYOC”“留在客户的 VPC 内”和“所有跨越边界的内容”。）

这份文件最有价值的是

egress_to_vendor

部分。安全团队不需要听“数据永远不会离开系统”，它需要的是一份完整清单：哪些内容会离开，以什么形式，出于什么目的。

自己动手的五个步骤

  • 问客户哪些数据可以放在哪里。 确认哪些敏感数据必须留在客户的基础设施上。
  • 像 Databricks 那样，把产品拆成控制平面和计算平面。 如果你的产品团队从未把两者分开，你就发现了一个项目风险。
  • 选定模式并写出地图，参照上面的示例，尤其要注意出站清单。
  • 用代码完成供给。 Terraform 加机器镜像，可以为第二个、第三个客户重建同样的集群，无需手工操作。
  • 为上线后的工作做准备。 Sierra 将部署生命周期描述为首次部署、定期升级、扩容和事故支持，并以运维手册为支撑。从第一天就写好运维手册，别等到第一次事故。

让项目卡在安全评审的错误

最常见的错误是把安全评审当成走流程。Sierra 要求候选人具备通过安全评审、合规要求和变更管理流程的经验。在大型企业里，改一条防火墙规则就可能要等完整的审批周期，你的计划必须为这种延迟留出余量。

第二个错误是默认总有一条通往厂商的网络路由。在物理隔离（air-gapped）的网络中，并没有这条路由。直接后果是，厂商一侧的控制平面无法再自行推送更新：每次升级都必须提前打包，传入客户网络，再走客户的变更管理流程。

Palantir 在 IPO 招股文件中写道，其 Apollo 平台使它能够以几乎与云端相同的速度部署到物理隔离或本地网络中。这说明这项工作需要一整套专门打造的平台，而不是多加几行配置。

第三个错误是只关注部署，忘了升级。运行在客户账号里的系统，如果没有清晰的更新路径，会逐渐落后，每一个补丁都会变成一个独立项目。

如何向雇主证明你有这项技能

阅读 FDE 岗位描述时，留意 VPC、permissioning、networking、Terraform、BYOC 和 air-gapped 这类关键词。它们表明这是一个偏基础设施的岗位。如果当前工作没有机会接触这些，用两个 AWS 账号做一个个人项目就足以练手。

简历上避免写“有云经验”这类空泛描述，要具体：编写 Terraform 在客户账号中搭建系统，为厂商设计最小权限的 IAM 角色，配置 VPC 对等连接，编写升级运维手册。被问到时，要能逐项讲清细节。

下次再听到“这能跑在我们的 VPC 里吗？”，别急着回答。打开一个空白文件，开始画地图。
