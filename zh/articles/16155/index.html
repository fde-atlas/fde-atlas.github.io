作为 FDE，如何为 LLM 评测构建黄金数据集

原标题：How to build a golden set for LLM evals as an FDE

FDE Interview Prep · 2026-09-25 · 约 13 分钟读完

摘要

这篇文章面向前沿部署工程师，讲解在客户没有任何标注数据时，如何从零构建用于 LLM 评测的黄金集。作者以虚构的工单分类场景为例，给出完整流程：按业务分层抽样真实流量、先与客户共同编写标注指南、由客户专家标注并用 Cohen's kappa 检验一致性、版本化管理并保留 holdout 集、持续纳入生产失败案例，最后在跑分前与客户签署按分段的上线标准。文章还引用 OpenAI 与 Snowflake 的 FDE 职位说明，说明评测能力是该岗位的明确要求，并给出面试中的口头回答模板与常见追问。

要点

  • 黄金集是专家确认、版本化的真实输入集合，不是演示样例或合成提示。
  • 按分段分层抽样，确保法律威胁等罕见但高风险案例不被随机抽样淹没。
  • 先写标注指南再标注，用 Cohen's kappa 检验专家一致性，分歧即缺失规则。
  • 保留 holdout、禁止跨版本比较分数，并把每个生产失败加入测试集。
  • 上线标准须在跑分前与客户签署，按分段设阈值并以现有流程为基线。

试点在演示中运行良好，这时客户的副总裁问出了决定它能否上线的问题：“我们怎么知道它已经好到可以启用了？”你想找有标注的数据来证明，却发现根本没有：多年的工单，却没有记录过正确答案是什么。这篇文章将展示如何从零开始构建证据——既适用于实际工作，也适用于面试。本文隶属于the FDE interview guide，其中涵盖了每一轮面试。

简短的回答是：按细分场景对真实流量进行抽样，编写标注指南，让客户的专家对样本进行标注并检查他们之间的一致性，冻结并版本化该数据集并留出保留集，把每一次生产环境中的失败都加进去，并在任何人看到分数之前，就它商定launch criteria。这个经过版本化、专家达成一致的样本就是golden set。

什么是 golden set，什么不是

golden set 是一个固定的真实输入集合，每个输入都带有客户专家一致认可的正确答案或标签，用于以相同的方式对系统的每个版本进行评分。

它不是：

  • 你的演示示例。你挑选这些示例正是因为它们能跑通。
  • 仅靠合成提示词。生成的示例对填补空白很有用，但它们无法涵盖真实流量中的错别字、转发的邮件链和没写完的问题。
  • 训练或 few-shot 数据。任何出现在提示词或微调集中的内容都不再是测试。
  • 一个单一的数字。这个集合的存在是为了展示每个细分场景的质量，因为平均值会掩盖那个会让你陷入麻烦的细分场景。

这已经写进了岗位职责里。OpenAI 的（医疗健康）职位描述中列出了定义评测，以及针对客户特定的验收标准来衡量质量。来源 1Forward Deployed Engineer (FDE), Healthcare - SF发布方OpenAI (Ashby)来源类型公司职位发布 Snowflake 的 Senior/Staff Applied AI FDE 职位要求应聘者将模糊的客户目标转化为质量指标、评测框架和 golden dataset。来源 2Senior/Staff Forward Deployed Engineer, Applied AI @ Snowflake发布方Snowflake (Ashby job board)来源类型公司职位发布

在下文描述的 Snorkel 面试经历中，ground truth 是以 CSV 文件的形式提供的。而在真实的部署中，没有人会把它交给你，所以可以预期接下来的追问是：“这些正确答案是从哪里来的？”下面的步骤就是我们回答这个问题的方法，而不是任何雇主发布的评分标准。

一个贯穿全文的示例让内容更具体。一家虚构的薪资软件公司希望用一个 AI Agent 将支持工单分类为账单、故障和法律威胁，并对每个工单进行路由。账单类几乎占全部，而法律威胁很罕见，且一旦出错代价高昂。

按细分场景从真实流量中抽样

从客户的实际输入开始：一个月的工单、邮件、通话记录或查询，并按照其安全团队要求的方式处理。首先弄清每个数据源由谁负责以及数据有多新，因为你需要获得拉取数据的权限。

然后按分层抽样，而不是随机抽样。简单的随机样本反映整体流量分布，所以稀有分层几乎不会出现。选择与客户关心的决策相匹配的分层：意图、客户等级、语言、渠道或风险。

import random
from collections import defaultdict

def stratify(rows, seg, k, seed=7):
    """Up to k rows from every segment."""
    rng = random.Random(seed)
    groups = defaultdict(list)
    for row in rows:
        groups[seg(row)].append(row)
    sample = []
    for _, items in sorted(groups.items()):
        take = min(k, len(items))
        sample += rng.sample(items, take)
    return sample

我们在 900 条账单、90 条故障和 10 条法律威胁工单的模拟流量上运行了它，

k=40

。它返回了 40 条账单、40 条故障以及全部 10 条法律威胁。同样流量下 120 条的简单随机样本在我们的运行中只抽到 2 条法律威胁，而在重复抽样中，约 28% 的此类样本一条都没有抽到。

但分层抽样无法凭空创造样本。全部 10 条法律威胁仍然很少，而且划分后大约一半会留在留出集中。当稀有分层正是最重要的那个时，就去主动寻找更多：扩大时间窗口，在历史工单中搜索“律师”或“attorney”，并向法务团队索取他们处理过的案例。

在面试中可以讲两点：

  • 同时保留真实分布。 分层抽样过度代表稀有分层，因此由此得出的整体分数并不是用户实际会看到的。按分层分别报告，需要单一整体数字时再按真实流量分布加权。
  • 有意加入困难案例。 模糊的请求、信息缺失、系统应当拒绝的问题，以及第二语言的输入。把它们标记为独立的分层，这样它们就不会消失在平均值里。

多大规模？根据决策来定。如果系统在某个分层上的正确率约为 0.90，

n=100

给出约

±0.06

的 95% 置信区间（正态近似）。在

时区间是偏斜的，用 Wilson 方法约为 0.77 到 0.96，因此真实的下降可能藏在其中。这足以看出某个分层的崩溃，而不是微小的下滑。把权衡说出来：每个分层更多样本，还是让忙碌的专家做更仔细的标注。从小规模开始，逐步扩大。

在任何人标注之前先写好标注指南

标注者之间的大多数分歧源于缺少规则，而不是粗心的人。先与客户一起写好指南，并保持足够简短以便阅读。

一份有用的指南对每个标签应包含：

  • 用客户的话写的一行定义；
  • 两三个明确属于该标签的真实示例；
  • 不属于该标签的近似案例及其原因；
  • 当输入同时符合两个标签或都不符合时该如何处理。

以工资单为例，难点在于法律威胁。“我要就这些费用找我的律师谈谈”是法律威胁还是账单问题？指南必须明确说明，因为两位专家会在此产生分歧，模型也会如此。就每个指标由谁负责以及谁会提出异议达成一致是同一类对话：负责该风险的人来写这条规则。

自由文本回答：是一份清单，而不是一个标签

大多数 LLM 系统写的是回答，而不是标签：一条回复、一份摘要、一个 Agent 的消息。不存在唯一正确的字符串，因此指南要说明正确回答必须包含什么、绝不能说什么。

假设这家薪资公司还想让 Agent 回答账单问题。输入是“为什么我三月份被扣了两次款？”黄金记录中保存着账单负责人撰写的一条参考答案，外加两份清单。在这个虚构的产品中，重复扣款会自动退款：

  • 必须包含：重复扣款将在 5-7 个工作日内退款；账单页面的链接。
  • 绝不能：承诺退款金额；提供法律建议。

由评审员或 AI Agent 对每一项标记通过或不通过。只有所有项都通过，回答才算通过。参考答案展示的是好的回答听起来什么样；而被评分的是清单，因为两个好的回答很少措辞相同。

由客户的专家来打标签，并检验一致性

正确答案属于拥有决策权的人：支持负责人、理赔员、合规官。你可以起草标签以节省他们的时间，但每一项都要由他们确认。如果你自己打标签，那你评的是自己对业务的理解。

然后衡量专家之间是否一致。给他们中两人同一批数据，比如 100 条，且不让他们看到彼此的标签，然后计算评分者间一致性。使用，而不是原始一致率，因为原始一致率会美化偏斜的标签集。

一个带通过或不通过标签的实例：两位专家在 100 条中有 88 条一致，一位标记 20 条不通过，另一位标记 18 条。随机一致性为 0.692，因此 kappa 为

(0.88 - 0.692) / (1 - 0.692) ≈ 0.61

。这看起来比 0.88 的原始一致率差，而且这正是它的用意。

在 0.61 时，先别急着标注其余数据。阅读那 12 条不一致的地方，把缺失的规则写进指南，然后让两位专家重新标注一批新数据。这里写的 kappa 只比较两位评分者；若更多，请使用 Fleiss' kappa 或 Krippendorff's alpha。

对结果的处理方式：

  • 阅读不一致之处，而不只是看分数。每一处都是一条缺失的规则。把它加进指南，并升级指南版本。
  • 指定一名仲裁人。由一个人裁决有争议的条目，其理由写入指南。
  • 把专家一致性视为上限。如果两位专家在一批条目上意见不一致，那么任何系统都无法被证明在这些条目上超越该水平。尽早向客户说明这一点；这比事后任何免责声明都更能校准预期。

如果你打算用模型作为评分器，先对照这些专家标签检验它。LLM 作为评委的陷阱那篇文章介绍了具体做法。

为数据集做版本管理并保留留出集

分数只有结合其来源数据集的版本才有意义。把数据集作为文件存入版本控制，每行一条记录（JSONL）。下面是一条记录，为适应手机屏幕分成几行显示：

{
  "id": "g-0412",
  "input":
    "I'm talking to my lawyer about these charges",
  "segment": "legal_threat",
  "expected": "route_to_legal",
  "source": "sampled",
  "guide": "v2",
  "split": "holdout"
}

自由文本记录携带的是自己的检查清单，而不是一个标签：

{
  "id": "g-0907",
  "input": "Why was I charged twice in March?",
  "segment": "billing_answer",
  "reference": "Sorry about that...",
  "must_include": [
    "duplicate refunded in 5-7 business days",
    "link to billing page"
  ],
  "must_not": [
    "promise a refund amount",
    "legal advice"
  ],
  "source": "sampled",
  "guide": "v2",
  "split": "dev"
}

三条规则保证它诚实可靠：

  • 拆分它。 保留一个你在修改提示词时会查看的开发集，以及一个只用于评分的保留集。如果对整个集合进行调优，更好的分数可能只意味着你拟合了测试集。
  • 绝不在不同版本之间比较。 当集合发生变化时，先在新版本上对旧系统重新评分，然后再宣称有改进。
  • 记录每个条目存在的原因。 是抽样所得、手工添加的困难案例，还是生产故障。这会在日后告诉你集合在哪个细分上比较薄弱。

这个集合现在是一个回归测试套件：在每次提示词、模型或检索变更上线之前，它都会运行。

把每一个生产故障都加进来

黄金集永远不会完工。每一个被用户标记、被 Agent 纠正或被审核人员推翻的输出，都是下一版本的候选条目：按照指南打标签，标记其所属细分，然后添加进来，并附上

source: production

.

这样，这个集合就不再是发布周的一个快照。Decagon 在自己的产品中内置了类似的检查机制：2026 年 6 月，它发布了 Duet Autopilot，该功能会针对暴露问题的对话以及一个包含数百段对话的黄金测试集来测试每一项拟议的 Agent 变更，并要求在任何变更进入生产环境之前获得人工批准。来源 3Introducing Duet Autopilot: The self-improving agent for conversational AI发布方Decagon 博客来源类型公司博客

在一次访谈中，一句话概括了这一点：“每一个生产故障都会变成一个测试用例，所以同样的错误不可能在我们不知情的情况下上线两次。”

把集合变成客户签字确认的上线标准

这个集合的存在是为了回答副总裁的问题。在任何人看到分数之前，先与客户一起写下：

  • 每个细分的指标，而不是一个平均值。对于薪资 Agent：计费和故障场景下的路由准确率，以及法律威胁的召回率。
  • 每一项的阈值，例如计费场景准确率 >= 0.90，且保留集中不得遗漏任何法律威胁，并在指定的版本上测量。只有 10 个法律威胁时，你无法测量像 0.98 这样的召回率，因为一次遗漏就已经是 0.90 了。这也是要主动去找更多法律威胁案例的另一个原因。
  • 基线。 在同一个集合上对客户当前的流程评分。如果他们的团队今天会遗漏某些法律威胁，那么这个遗漏率才是应该讨论的基准，而不是完美无缺。
  • 一个不得恶化的护栏指标，例如被发送到错误队列的工单比例。
  • 谁签字确认，以及未达标时怎么办：是在风险细分上带人工审核的缩小范围上线，还是再迭代一轮。

在构建之前先写下评判标准不仅是我们的建议。ElevenLabs 2026 年 4 月关于前沿部署工程经验教训的文章推荐测试驱动的方法，即在构建语音 AI Agent 之前先定义成功标准和测试。来源 4构建持久的语音 Agent：前沿部署工程的一些经验教训发布者ElevenLabs来源类型公司博客 那篇关于在案例面试中选择成功指标的文章更深入地探讨了如何挑选数字及其护栏指标。

面试中该说什么

当面试官问“客户没有标注数据，那你会如何评估它？”时，下面是一个你可以在大约一分钟内说完的版本：

“我会从他们的真实流量中构建一个黄金集。首先按细分场景抽样，这样像法律威胁这类罕见、高代价的案例才会出现，而不只是账单问题。在任何人开始标注之前，我会与负责该风险的人一起撰写一份简短的标注指南。由他们的专家来标注，而不是我，并且让其中两人标注一段重叠的样本，以便我用 Cohen's kappa 检验一致性；每一处分歧都会成为指南中的一条规则。我会冻结一个从不用于调优的保留集，对整个集合做版本管理，并把每一个生产环境中的失败案例加入其中。在运行任何东西之前，我们会以他们当前的流程为基线，就每个细分场景商定上线标准，这样‘是否足够好’就变成一次检查，而不是一场争论。”

预期会有三个追问：它需要多大（用权衡来回答，而不是一个神奇的数字）、如果专家意见不一致怎么办（这就是上限，需要修正的是指南）、以及模型能否给它打分（只有在模型与专家一致之后才行）。解释为什么系统不可能每次都正确有助于应对之后的对话。然后在免费练习案例中，用一个会反驳你的客户来演练整套回答，该案例只需登录即可。

大声练习

阅读本文不等于在压力下作答。按顺序回答三个问题：

  • 一分钟内说出来：客户问你如何知道你的 AI 系统有效。
  • 编写评分器：对照真实值文件为模型输出打分。
  • 设计流水线：为客服 Agent 设计评测框架。

更完整的回答，包括指标、基线和监控，请阅读如何回答“你怎么知道它有效？”。现在就从第一个问题开始。

人们常问的问题

什么是 LLM 评测中的黄金集？

一组固定、有版本管理的真实输入，附带客户专家一致认可的答案或标签。每次模型、提示词或检索变更都要在它上面运行，这样在用户之前就能看到质量是升还是降。

黄金集应该多大？

要大到足以覆盖你关心的每个细分场景，并有足够样本能看出变化；又要小到专家能仔细标注。从小规模开始，按细分场景抽样，并随生产环境中的失败案例逐步扩充。面试中要讲清这个权衡，而不是报一个神奇数字。

谁来给黄金集打标签？

由客户的领域专家依据书面标注指南来标注，并抽取一部分样本由两人重复标注，以便测量一致性。工程师可以起草标签，但对决策负责的人应当认可这些答案。
