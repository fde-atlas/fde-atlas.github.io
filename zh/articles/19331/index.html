什么是MCP？MCP服务器的机制与企业导入的权限设计

原标题：MCPとは？MCPサーバーの仕組みと企業導入の権限設計

摘要

本文系统介绍MCP（Model Context Protocol）：这一由Anthropic于2024年11月发布、2025年12月移交Linux Foundation旗下Agentic AI Foundation的连接规范，用于统一AI应用与外部数据、功能的对接方式，将M×N的集成降为M+N。文章讲解主机、客户端、服务器三种角色及工具、资源、提示词三类功能，重点说明2026-07-28版规范的破坏性变更（废除initialize与会话），并指出规范无法强制执行安全要求，企业需自行完成五项权限设计：服务器许可清单、运行身份、暴露操作、执行前人工确认、日志与定期盘点。作者还提醒官方Registry不构成安全保证，并给出分阶段导入路径。

要点

  • MCP统一AI应用与外部系统的连接，集成从M×N降为M+N。
  • 现行2026-07-28版废除initialize与会话，新旧实现可能互不兼容。
  • 规范要求人工可拒绝工具执行，但协议层面无法强制。
  • 企业应先定五项权限设计：许可清单、运行身份、操作范围、确认、记录。
  • 官方MCP Registry仅为信息目录，不保证服务器安全。

让 AI Agent 读取企业内部数据、操作业务系统时，为每个产品单独构建连接方式所带来的工作量是个问题。MCP（Model Context Protocol）就是将这种连接统一为通用标准的规范。它由 Anthropic 于 2024 年 11 月发布，并于 2025 年 12 月捐赠给 Linux Foundation 旗下的 Agentic AI Foundation。

日本的行政部门也有相关动向。数字厅在 2026 年 7 月 21 日的《实现数字社会重点计划》中决定，将在令和 8 年度内确定行政系统对 MCP 等标准的应对方针，并在 My Number 门户网站上以令和 9 年度内为目标构建 MCP 等基础平台。

  • MCP 是连接 AI 应用（宿主）与提供数据和功能的MCP 服务器的规范。宿主为每个连接目标准备一个客户端，客户端与服务器以一对一方式连接。通信采用 JSON-RPC 2.0 进行。
  • 现行规范为 2026-07-28 版。连接开始时通过 initialize 进行的握手流程已被废除，改为每次请求独立完成的方式。如果按照旧版说明进行实现，可能会出现无法连接新服务器的组合。
  • 规范要求在执行工具前允许人工拒绝，且不信任工具的自我声明。但正如规范本身所写，这些要求无法通过协议强制执行。
  • 在企业中引入时，先确定以下 5 点会更容易推进：允许使用的服务器、以谁的权限运行、可公开的操作、执行前的确认、以及日志记录。

本文内容基于 2026 年 11 月 5 日确认的规范官方网站（modelcontextprotocol.io）及各公司官方文档编写。

本文的目标读者

  • 计划将 AI Agent 连接到内部系统或 SaaS，希望判断是否采用 MCP 的信息系统部门、DX 推进部门
  • 已收到一线使用 MCP 服务器的申请，但没有许可标准的安全负责人
  • 正在考虑将自家产品或数据作为 MCP 服务器提供的产品负责人

MCP 是什么（3 行要点）

  • MCP 是 AI 应用使用外部数据和功能的通用连接规范。规范官方网站将其比作 AI 应用的 USB-C 接口。
  • 分为使用方（宿主与客户端）和提供方（服务器），服务器提供“工具”“资源”“提示词”三类功能。
  • 连接变得容易的同时，AI 可操作的范围也随之扩大。企业需要决定允许使用哪些服务器、以谁的权限、使用到什么程度。

为什么需要 MCP

在 MCP 出现之前，每次要让 AI 应用使用内部系统，都需要按应用、按系统分别构建集成。如果有 M 种 AI 应用、N 种连接目标，集成数量就会达到 M×N 种。

采用 MCP 后，只要连接目标的系统准备一个 MCP 服务器，任何支持 MCP 的 AI 应用都能以相同方式使用它。AI 应用一侧也只需实现一个 MCP 客户端，即可使用众多服务器。集成数量减少为 M+N 种。

支持范围也在不断扩大。OpenAI 通过 Responses API 支持调用远程 MCP 服务器，Google 为 Google Cloud 的服务提供托管的 MCP 服务器。AWS 通过 Amazon Bedrock AgentCore Gateway 可将 MCP 服务器作为连接目标，其支持的协议版本包含 2026-07-28 版。

MCP 的机制

宿主、客户端、服务器三种角色

规范将角色分为三类。

角色职责示例
宿主用户操作的 AI 应用。启动并管理多个客户端，负责连接许可、获取同意、与 LLM 的协作Claude、ChatGPT、企业内部开发的 AI Agent
客户端宿主内部负责与单个服务器连接的组件。客户端与服务器为一对一由宿主为每个连接目标准备
服务器向 AI 提供数据和功能的程序。可以是 PC 上的进程，也可以是网络上的服务文件检索、CRM、工单管理、数据库

规范的设计原则要求：不让服务器读取完整对话内容，也不向其展示其他服务器的内部信息。对话历史保留在宿主中，只向服务器传递必要的信息，服务器之间的协作由宿主控制。这并非协议自动保障的机制，而是依靠宿主的实现来保障。从企业的角度看，决定将哪些信息传递给哪个服务器的位置就是宿主。

MCP 服务器提供的 3 类功能

功能内容企业中的应用示例
工具（Tools）AI 执行的函数。AI 根据上下文自行发现并调用案件检索、创建工单、起草邮件
资源（Resources）AI 或用户读取的数据内部规章文档、客户主数据的一部分、设计文档
提示词（Prompts）用户选择使用的固定指令或工作流周报的编写流程、咨询初次回复的模板

工具是权限设计中最需要注意的功能。规范将工具定义为“model-controlled”，即由 AI 自行判断调用。与只读的资源不同，工具可能涉及写入或发送操作。

连接方式：stdio 与 Streamable HTTP

标准的连接方式有两种。

  • stdio：主机将MCP服务器作为PC上的子进程启动，通过标准输入输出进行交互。适用于在开发者PC上运行的本地服务器。不遵循授权规范，凭证从环境变量等获取
  • Streamable HTTP：通过HTTP的POST向网络上的MCP服务器发送消息。适用于企业内部系统或SaaS提供的远程服务器。按规范，授权的实现是可选的（OPTIONAL），但如果实现，建议遵循基于OAuth 2.1的授权规范（SHOULD）

2024-11-05版中的HTTP+SSE方式，在2026-07-28版中被归类为不推荐使用（Deprecated）。新建时不要选择它。

2026-07-28版规范的变化

MCP规范以日期管理版本。历经2024-11-05版、2025-03-26版、2025-06-18版、2025-11-25版修订，2026年7月28日发布的2026-07-28版为现行版本。由于该版本包含不向后兼容的变更，如果基于2025年及之前的解说文章进行实现，会存在不一致之处。

变化点截至2025-11-25版2026-07-28版
连接的开始通过initialize商定版本和功能后再通信废除该流程。每次请求都附带版本和客户端功能发送
会话通过Mcp-Session-Id维持会话废除协议层面的会话。如需状态，将服务器发放的ID通过工具参数传递
服务器信息的获取通过initialize的响应得知可通过server/discover获取（服务器必须实现）
服务器的询问服务器向客户端发送请求服务器返回“需要额外输入”的结果，客户端附带输入重新发送原始请求
Sampling、Roots、Logging在规范中定义（Sampling、Roots是客户端侧功能，Logging是服务器侧功能）不推荐使用。新实现不采用

不推荐使用的功能，原则上会在规范中保留12个月以上（存在紧急情况下可缩短至90天的例外）。Sampling、Roots、Logging被删除，最早也是在2027年7月28日之后发布的版本。HTTP+SSE方式的删除时间另行规定。

引入的企业需要确认的是，所使用的主机和服务器支持哪个版本。根据规范兼容性表，只支持2025-11-25版及之前方式的客户端，无法连接只支持2026-07-28版方式的服务器。

MCP与API集成、Function Calling的区别

比较点各自的API集成Function CallingMCP
决定什么每个系统的调用方式在单个AI应用中，让模型选择函数的方法连接AI应用与外部功能的通用标准
由谁构建每次集成都需开发AI应用的开发者定义函数提供方构建一个服务器，支持MCP的应用共同使用
适用场景以固定的顺序运行固定的处理仅在企业内部应用中使用的少量函数让多个AI应用使用相同的企业内部系统或SaaS

MCP并非要取代API。许多MCP服务器在内部调用现有的API。MCP规定的是统一AI应用视角下调用方式的部分。

企业使用时容易出现的问题

作为易于连接的另一面，AI可触及的范围会扩大。规范的Security Best Practices列举了实现和运营中可能出现的问题。摘录与企业决策相关的内容如下。

问题会发生什么规范给出的对策
令牌转用（Token Passthrough）MCP服务器接收并非发给自己的令牌并原样传递给下游API。绕过下游的利用限制和审计日志服务器不得接受并非发给自己的令牌（MUST NOT）
混淆代理人（Confused Deputy）以单一固定ID连接外部API的中继服务器，在未取得用户同意的情况下通过授权，授权码被攻击者夺走中继服务器必须取得每个客户端的同意，在进入外部授权前进行确认
本地服务器被劫持恶意命令被植入配置中，在PC上执行任意代码提供一键配置的客户端，必须完整显示要执行的命令，并取得明确批准（MUST）
过大的作用域一开始就获取全部权限的令牌，泄露时损害变大从最小的作用域开始，仅在需要相关操作时追加取得同意
SSRF恶意服务器通过授权流程让客户端访问企业内部地址生产环境使用HTTPS，禁止连接私有IP地址段

此外，工具的说明文字以及“只读”等注记（annotation）是服务器自行申报的。规范要求（MUST）不得信任来自不可信服务器的注记。标注“不会删除”的工具是否真的不删除，仅凭申报无法确认。

员工以个人判断连接未经批准的 MCP 服务器，属于影子 AI 的一种。检测与替代方案的思路已总结在“影子 AI 对策｜仅靠禁止无法防范的原因与 4 个控制点”中。

企业导入时需确定的 5 项权限设计

规范将用户能够同意并理解所有数据访问与操作作为原则。同时，规范也明确指出，MCP 本身无法在协议层面强制执行这一原则。确保其被遵守的机制，需要由导入的企业来设计。FDX 建议首先确定以下 5 点。

1. 确定可以使用哪些服务器

首先要确定的，是公司内部允许使用的 MCP 服务器许可列表。官方 MCP Registry（registry.modelcontextprotocol.io）汇集了公开服务器的信息，截至 2026 年 11 月 5 日确认时仍处于预览阶段。Registry 有意采取不评估所载信息的方针，将代码安全性的检查交给 npm 等分发渠道，以及使用 Registry 的市场平台。

载入 Registry 并不等于安全保证。而且公司内部服务器不属于 Registry 的对象，因此许可列表需由企业自行维护。

  • 提供来源：是官方服务器，还是第三方制作的
  • 连接方式：是本地（stdio），还是远程（Streamable HTTP）
  • 处理的数据：接触哪个业务系统、哪个类别的信息
  • 对应的规范版本：能否与所用的主机连接

2. 确定以谁的权限运行

在远程 MCP 服务器上实现授权时，MCP 服务器作为 OAuth 2.1 的资源服务器，MCP 客户端作为 OAuth 的客户端。此时规范将服务器公开授权服务器信息的机制（RFC 9728）以及指定令牌目标的机制（RFC 8707）设为必需。公司内部使用的远程服务器，前提是仅限于已实现授权的服务器。

企业决策的关键在于，AI 是以“用户本人的权限”运行，还是以“共用的服务账号”运行。若以用户本人的权限运行，该人无法查看的信息 AI 也无法查看。若以共用账号供全体员工使用，除非另行建立按用户的访问控制和记录机制，否则平时无法浏览的信息可能通过 AI 被获取，日志中也不会留下是谁的操作。

规范也要求服务器验证收到的令牌是否是发给自己的，不得接受或转发其他令牌。

3. 收窄公开的操作

一个 MCP 服务器可能拥有多个工具。例如 CRM 服务器即使拥有“搜索”“更新”“删除”“批量导出”等工具，很多业务最初只需允许使用搜索即可。

规范允许

tools/list

返回的工具根据请求所附权限进行调整。对于收窄了作用域的令牌，可以设计为只展示该作用域下可用的工具。从最小作用域开始，在需要更新时再取得额外同意，这也符合规范的建议。

4. 执行前由人确认

规范建议（SHOULD）应始终保持人可以拒绝工具调用的状态，并推荐在界面上展示向 AI 公开的工具、执行时的提示以及确认界面。

作为公司内部的运营方式，将操作分为 3 类来确定会更易于判断。

类别示例执行前的确认
读取搜索、列表、用于摘要的获取可以不确认。但目标数据类别在第 1 项中限制
写入创建、更新、保存草稿展示内容并取得批准
向外部发送・删除发送邮件、向外部共享、删除、批量处理每次都取得批准。批量处理设置数量上限

OpenAI 的 Responses API 默认设置为在执行 MCP 工具时要求批准。不要仅依赖产品默认设置，应在公司内部确定在哪些类别上取消批准。即使工具申报为“只读”，也不要因该申报而省略确认。

5. 记录并盘点

规范建议客户端为审计目的记录工具的使用情况。记录谁、从哪个主机、调用了哪个服务器的哪个工具、使用了什么参数。

同时，每季度重新审视许可列表中的服务器。停用未被使用的服务器，并确认提供方的更新是否增加了工具。工具列表可能因服务器端的更新而在用户无操作的情况下发生变化。

将数据边界、权限、审计日志的设计整理为公司级 AI 治理的方法，已在“AI 治理与实现安全｜6 个控制点”中解说。

导入的推进方式

阶段要做的事判断标准
1. 确定目标业务选择一个希望让 AI 使用公司内部系统的业务。从仅靠读取就能产生价值的业务开始能否用数字说明会减少谁、多少工作时间
2. 选择服务器有官方服务器就用官方的；没有的话比较自建还是现有 API 集成是否够用能否填满许可清单的 4 个项目
3. 设计权限以使用者本人的权限运行，将范围和工具降到最小AI 是否接触不到平时看不到的信息
4. 小规模试点限定部门使用，确认审批界面和日志审批流程是否拖慢业务，能否通过日志追踪操作
5. 推广逐步增加写入类工具，扩大使用部门是否确定了盘点负责人和周期

常见问题（FAQ）

Q1. MCP 是什么？

A. MCP（Model Context Protocol）是 AI 应用使用外部数据和功能的通用连接标准。AI 应用（主机）为每个连接对象准备客户端，与提供数据和功能的 MCP 服务器一对一连接，通过 JSON-RPC 2.0 进行交互。它于 2024 年 11 月由 Anthropic 发布，并于 2025 年 12 月捐赠给 Linux Foundation 旗下的 Agentic AI Foundation。

Q2. MCP 服务器是什么？

A. 是向 AI 提供功能和数据的程序。它可以提供三类内容：AI 执行的「工具」、读取的「资源」以及固定格式的指令「提示词」。包括在 PC 上运行的本地服务器（stdio 连接），以及内部系统和 SaaS 提供的远程服务器（Streamable HTTP 连接）。

Q3. MCP 与 API 有什么区别？

A. API 是各系统各自的调用方式，而 MCP 是统一 AI 应用视角下调用方式的标准。由于大多数 MCP 服务器在内部调用现有 API，因此 MCP 并不是替代 API 的东西。当希望让多个 AI 应用使用同一内部系统时，MCP 更为合适。

Q4. MCP 在安全上有风险吗？

A. 标准本身并非危险，但由于 AI 可触及的范围扩大，设计失误时损害也会扩大。规范中规定了禁止重复使用令牌、工具执行前需人工确认等要求，但也明确说明协议层面无法强制执行。允许使用的服务器、以谁的权限运行、公开哪些操作、执行前的确认、记录这 5 点需要由引入企业自行决定。

Q5. 收录在官方 MCP Registry 中的服务器就安全吗？

A. 不一定安全。官方 MCP Registry 是收集公开服务器信息的场所，截至 2026 年 11 月 5 日确认时仍处于预览阶段。收录信息不做主动评估，代码安全性的检查交由分发方或使用方的应用市场负责。企业内部应通过自己的许可清单进行管理。

Q6. 2025 年制作的 MCP 服务器和客户端还能直接使用吗？

A. 取决于组合情况。2026-07-28 版废止了连接启动的

initialize

和会话。在规范兼容性表中，仅支持旧方式的客户端无法连接仅支持新方式的服务器。请确认所使用的主机和服务器支持的版本，必要时更新为同时支持两种方式的 SDK。

总结

  • MCP 是连接 AI 应用与内部系统、SaaS 的通用连接标准，由主机、客户端、服务器 3 种角色构成
  • MCP 服务器提供工具、资源、提示词。由 AI 判断并调用的工具是权限设计的核心
  • 现行规范为 2026-07-28 版，initialize 和会话已被废止。请确认所使用的主机和服务器支持的版本
  • 规范禁止重复使用令牌，并要求在工具执行前允许人工拒绝，但协议本身无法强制执行
  • 在企业中，应先确定五点：允许使用的服务器、以谁的身份运行、公开哪些操作、执行前的确认、记录与盘点
  • 被收录到官方 MCP Registry 并不等于安全保证。允许列表应由企业自行维护
