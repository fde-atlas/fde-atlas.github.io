OpenAI 前沿部署工程师职位揭秘

原标题：Inside OpenAI’s Forward Deployed Engineer Role

Engineering Leadership · 2026-08-15 · 约 5 分钟读完

摘要

本文基于对 OpenAI 前沿部署工程全球负责人 Colin Jarvis 的访谈，介绍该组织的运作方式。OpenAI 的 FDE 组织一年前从 2 人起步，现已发展到约 140 人，定位在市场推广与产品研究之间，负责收集客户洞察并反馈给产品与研究团队。OpenAI 还成立了独立的 Deployment Company（约 200 人），专注于帮助客户落地产品，而内部 FDE 组织刻意保持较小规模。文章还描述了 FDE 的日常工作、约 50% 的驻场时间安排，以及从软件工程师转型为 FDE 的准备建议（部分内容为付费订阅）。

要点

  • OpenAI 的 FDE 组织从 2 人增长到约 140 人。
  • 新成立的 Deployment Company 约 200 人，专注客户落地。
  • FDE 以结果为导向，目标是解决问题并让自己变得不再被需要。
  • FDE 约一半时间驻场，部分国家高达 80%。
  • 客户洞察会以具体形式反馈给研究团队改进模型。

简介

前沿部署工程师（FDE）这一角色近年来备受关注，OpenAI 就是其 FDE 团队快速扩张的一个很好的例子。

此外，他们最近还成立了一个名为 OpenAI Deployment Company 的独立实体，专注于帮助客户使用 OpenAI 的产品。

我有幸与 OpenAI 前沿部署工程全球负责人 Colin Jarvis 进行了交流。

我们聊了很多，包括他们的团队如何运作、什么样的人能成为优秀的 FDE、他们如何与客户合作，以及工程师如何为这一角色做好准备。

让我们开始吧！

OpenAI 如何构建其前沿部署工程组织

OpenAI 于去年启动了前沿部署工程组织，重点是从客户那里收集洞察、了解实际用例，并将这些洞察反馈给产品和研究团队。

他们最初只有 2 个人，如今 FDE 组织已发展到约 140 人。FDE 组织处于 GTM（市场推广）组织与产品和研究团队之间，与双方协作，充当“纽带”。

在与不同客户合作一段时间后，他们发现人们和公司所面临的问题中存在可复现的规律，这也是他们最近成立 OpenAI Deployment Company 的原因（它是一个独立实体，但仍属于 OpenAI 的一部分）。

该实体目前已发展到约 200 人，我预计未来还会大幅增长。它的目标完全是帮助解决客户问题，而这正是 FDE 的核心所在。

Colin 提到，他们有意将 OpenAI 内部的 FDE 组织保持在相对较小的规模，专注于为产品和研究团队获取洞察，同时持续扩展 OpenAI Deployment Company，以支持需要集成其产品的客户。

现在，让我们更深入地了解 FDE 这一角色。

OpenAI 的前沿部署工程师角色

当我问 Colin 如何定义 OpenAI 的 FDE 角色时，他这样说道：

前沿部署工程师关注的是结果。这意味着他们的目标应该是解决那些一旦解决就能产生远超工作本身影响的问题。

因此，在实际操作中，价值并不在于编写代码，而在于解决问题，并且理想情况下，还要让自己变得“多余”，从而不再被需要。

而且，如果它们再次被需要（针对同一个问题），通常意味着问题还没有被完全解决。

他们想要的是优秀的软件工程师，同时也是善于沟通的人，能够真正深入挖掘实际的问题是什么，并以让所有人都能产生共鸣的方式解释解决方案。

而且（理想情况下），这些工程师还应该在特定客户所在的领域拥有一些专业知识。

例如，一位曾在金融科技行业工作过的软件工程师，可能非常适合担任 FDE 去帮助一位从事金融科技行业的客户，因为他们了解这个领域。

不过，Colin 提到的一个重要事项是，他们希望将领域专家和非领域专家的 FDE 混合搭配。原因在于，一个并非特定行业的专家、但拥有其他行业经验的人，更有可能“挑战现状”，并提出解决某些问题的独特想法。

FDE 日常都做些什么？

Colin 分享了一个他们目前正在日本进行的项目案例，专门针对“代码现代化”。该客户拥有大量遗留应用程序，迁移其中一个系统可能需要花费数亿美元。

他们正在利用 AI 帮助该客户将旧技术迁移到新技术。

一位 FDE 可能会花一整天与支付团队沟通，了解哪些具体事项对他们很重要，以确保迁移成功。然后在第二天，根据支付团队分享的见解开始构建测试，以确保迁移真正成功。再过一天，他们可能会编写实际的迁移代码，或者构建用于展示迁移进度和/或迁移具体步骤的 UI。

所以这个角色实际上是工程工作与直接与领域专家合作（同时也对该领域有良好理解）的结合，在两者之间来回切换。

与产品团队和研究团队之间还有一个重要的反馈循环。在这个具体项目中，他们发现用于迁移的某个特定模型总是犯一些简单的错误。

正如 Colin 提到的，他们不会把客户的具体问题原封不动地丢回给研究团队，而是尽可能具体地描述，例如：“这个模型在这类 COBOL 转 Java 的任务上表现不佳。我们需要更多围绕这些示例的训练数据。”

他们会尽一切努力让某个特定客户取得成功，但更大的目标是确保模型对每一个客户都不断变得更好。

他们大约有 50% 的时间在客户现场度过

他们通常会告诉新加入者，预计大约 50% 的时间会在客户现场。

但正如 Colin 提到的，这也因项目而异。例如，他们在阿联酋的一些员工大约 80% 的时间都在客户现场。驻扎在欧洲或美国的员工可能每月有 2-3 周与客户在一起。在日本，员工也大约 80% 的时间在现场。

但总体而言，他们注重在现场时尽可能发挥最大的影响力，宁愿度过 2 或 3 天高影响力的时间，而不是 4-5 天影响力较低的时间。

此外，他们的许多客户分布在不同地点，所以一直驻场并不现实。不过，作为一般参考，大约 50% 的时间在现场是一个合理的估计。
