FDE 所需技能｜从招聘启事要求中提取的技术与非技术技能细分

原标题：FDEに必要なスキル｜求人票の要件から抽出した技術・非技術の内訳

株式会社ウェステリア · 2026-11-16 · 约 10 分钟读完

摘要

本文分析2026年8月公开的FDE（前沿部署工程师）招聘启事，拆解其技术与非技术要求。技术方面以Python、TypeScript/JavaScript、LLM实现（提示词设计、Agent搭建、评测）及云端部署为主，很少指定具体框架；非技术要求的篇幅反而更大，核心是问题定义、范围裁剪、与非技术者达成共识及自主性。英语方面，外资AI企业日本据点几乎都要求日英双语，成为薪酬分水岭；国内AI初创企业则多数不强制英语。作者建议优先积累一次从模糊需求定义到上线运营的完整实战经验，框架熟练度可后置。

要点

  • 技术核心是Python、TypeScript、LLM实现与云端部署，很少指定框架。
  • 非技术要求篇幅更大：问题定义、范围裁剪、共识形成与自主性。
  • 外资AI企业日本据点几乎都要求日英双语，是薪酬分水岭。
  • 最优先准备：一次从定义问题到上线运营的完整实战经验。
  • 作品集看重是否被实际业务使用，而非数量或证书。

读几份 FDE 的职位描述，你会发现要求的排列有一个共同的模式：编程语言的指定、使用 LLM 的实现经验、云技术，以及大约两倍篇幅的非技术要求。本文将拆解截至撰写时（2026-08）已公开职位描述的要求，梳理各项能力被要求的程度，以及有限的准备时间应该分配到哪里。

先说结论

  • 技术方面的核心是 Python 和 TypeScript/JavaScript、使用 LLM 的实现（提示词设计、Agent 架构、评测），以及在云上的部署与运维。比起精通某个特定框架，更被看重的是从前端到后端都能独立完成的能力
  • 从职位描述的篇幅来看，非技术要求反而写得更多。在模糊的情况下定义问题的能力、与非技术人员达成共识的能力、判断权衡并裁剪范围的能力被反复提及
  • 英语方面，各公司分为必备和加分两类，外资 AI 企业的日本据点截至撰写时（2026-08）几乎都要求日英双语。这也是薪酬区间的分水岭

职位描述的要求是如何构成的

阅读 FDE 的职位描述时，你会注意到技术要求出奇地短。例如 OpenAI 的 Forward Deployed Engineer 职位描述的要求栏中，列出的仅是：能用 Python、JavaScript 或同等技术栈在前端和后端都写出生产级质量的代码，以及有使用 LLM 或生成式模型构建系统的经验，并没有指定特定的框架或库。

取而代之占据篇幅的，是关于工作方式的要求：在不确定且快速变化的环境中规划并交付复杂系统的经验、将复杂问题简化并在压力下快速做出合理判断的能力、向工程师、产品团队和客户等各方清晰传达的能力、尽早发现风险并在不降低速度的情况下进行调整的能力。这类描述接连出现。

Palantir 在东京的 Forward Deployed Software Engineer 职位描述也呈现同样的倾向，除了要求能用 Python、Java、C++、TypeScript/JavaScript 等写出高质量代码之外，还要求能与技术人员和非技术人员混合的团队协作、能在目标不断变化的环境中舒适地工作、能在最少监督下自主判断。

也就是说，这个职位的技能要求重心在于“如何行动”，而非“能写什么”。但这并不意味着前者不需要，而是前者是获得后者评价的前提，结构是这样的。

整理职位描述中出现的技术要求，如下所示。优先级是根据在多份职位描述中共同出现的程度来判断的。

从这张表中需要注意的是，几乎没有把特定框架作为要求的情况。虽然也有国内职位点名 LangChain 或 Dify，但外资的职位描述是以语言和技术栈的粒度来写的。FDE 是根据客户环境选择技术的职位，因此比起精通特定工具，在置身新环境时能短期内快速上手更有价值。

非技术技能——这才是这个职位的本体

从职位描述的篇幅来看，FDE 评价的核心在这里。不过由于是用抽象的语言写的，需要结合实际工作场景来理解。

排在最上面的“定义问题的能力”最难复制，也最能拉开差距。客户往往以“能不能用 AI 做点什么”的形式找上门来。从中确定针对哪项业务的哪个判断、以及如何衡量成功，是 FDE 的第一项工作。跳过这一步直接开始构建，就会做出能运行却没人使用的东西。

第二项裁剪范围的能力同样重要。FDE 的项目，如果想做的话可以无限扩展。必须决定这次不做什么并让客户接受，否则无法在截止日期前交付到生产环境。OpenAI 的职位描述中“在范围、速度、质量之间判断权衡，并调整计划以确保交付”这一表述，指的就是这项工作。

  • 定义问题的能力——从客户模糊的咨询中，确定目标业务、成功的衡量标准、以及不做的范围
  • 裁剪范围的能力——为了在截止日期前交付到生产环境，判断舍弃什么并与客户达成共识
  • 与非技术人员达成共识——从一线负责人到高管，向不懂技术语言的对方说明并推动决策
  • 自主性——即使没有上司的指示，也能在客户现场自主判断并推进。职位描述中常用 high agency 来表达
  • 将现场经验回馈到产品——不让个案处理止于一次性，而是把反复出现的模式沉淀为产品或公司内部资产
  • 行业领域——金融、制造、医疗、公共等。很多职位把行业名称列为加分要求

英语需要到什么程度

在日本以 FDE 为目标时，最关键的分水岭是英语。就截至撰写时（2026-08）能确认的范围而言，外资 AI 企业的日本据点几乎都要求日英双语。OpenAI 在东京的 FDE 职位描述明确写道，精通日语和英语（口语和书面）是成功的条件，简历需以英语提交，面试将以两种语言进行。Palantir 在东京的职位描述也要求具备商务水平的日语和英语。

就水准而言，考察的不是资格证书分数，而是实际工作中的使用情况。需要与总部的工程师和产品团队进行书面沟通，必要时在会议上讨论。与客户的沟通用日语，公司内部用英语，将在这种双重结构下工作。

另一方面，国内 AI 创业公司的 FDE 招聘中有相当数量并不要求英语。如果目前英语不足，比较合理的路径是先在国内企业积累 FDE 的实际工作经验，之后再补足英语去瞄准外企。

如何分配有限的时间

不可能同时补齐所有内容，所以要排定优先级。按实际工作中的效果排序，顺序如下。

推荐第一项的理由是，这是 FDE 选拔中最受关注的部分。技术栈清单可以写在简历上，但“从模糊状态中自己定义问题并交付到生产环境”的经验，只有真正做过的人才讲得出来。规模小也没关系。只要有一次把某个人的实际业务问题从定义到运营完整走完的经历，面试的内容就会完全不同。

反过来，可以往后放的是对特定框架或工具的熟练掌握。FDE 是根据客户环境选择技术的工作，工具会随项目而变。比起深入掌握一个工具，训练自己在短时间内上手新工具的能力更有用。

  • 打造一个从模糊问题定义到交付上线的经验 — 最优先。规模不限
  • 用 Python 和 TypeScript，做到从前端到后端都能写
  • 使用 LLM 进行实现并做到评测（eval）的经验 — 不要止步于“能跑起来”，要能说清精度是如何衡量的
  • 在云上自己部署并运维的经验
  • 英语 — 瞄准外企则必备；瞄准国内企业可以往后放
  • 行业领域知识 — 虽然耗时，但是日后会发挥作用的差异化要素

如何证明技能

FDE 选拔中的难点是非技术技能的证明。即使写上“能与客户一起定义问题”也传达不出什么。起作用的是具体的过程：客户在咨询时说了什么、从中重新定义了什么问题、为什么把范围切定在那里、做出的东西在生产环境中如何被使用。只要能就一个案例讲清这四点，就足以覆盖大部分评价维度。

技术方面，请认为“生产环境中有人在用的东西”比放在仓库里的成果物更有说服力。FDE 的工作包括让它持续运行，所以如果能讲上线运营之后的情况（哪里坏了、修了什么、之后的使用状况），就能传达出实际工作的分辨率。

要确认自己的现状，一个快捷的方法是把招聘要求的条件列出来进行自我评分。由株式会社ウェステリア运营的 FDE board 汇总了日本国内的 FDE 招聘信息，可以逐条对比每个职位的必备条件和优先条件。请在 FDE board 的职位列表中并排查看多份招聘启事，找出其中共同出现而自己欠缺的条件。准备就绪后想行动的人，可以先进行候选人注册，出现符合条件的职位时我们会与您联系。

常见问题

  • FDE 需要哪些编程语言？
  • 在撰写时点（2026-08）可查到的招聘启事中，Python 几乎是共同要求，此外还要求 TypeScript/JavaScript。也有像 Palantir 那样列出 Java 或 C++ 的职位，但这源于该公司的产品技术栈。重要的不是语言数量，而是能否一个人独立写出从前端到后端的生产级代码。
  • 需要机器学习的专业知识吗？
  • 在大多数 FDE 招聘中，自己训练模型的知识并不是必备条件。被要求的是用现有 LLM 构建能在业务中运行的系统的能力。提示词设计、Agent 的架构、检索（RAG）的设计，以及如何衡量输出质量（评测的构建方法）与实际工作更直接相关。不过，如果有数据科学素养，在查看客户数据时会更有优势。
  • 据说 FDE 最欠缺的技能是什么？
  • 对照招聘要求和实际的转型来源，从开发侧过来的人往往缺少“从客户模糊需求中定义问题的经验”，从咨询、SIer 侧过来的人往往缺少“独立写完生产代码的能力”。这两者都无法通过短期学习补齐，所以在目前所在的组织中有意识地主动承担这一侧的工作是最快的路径。
  • 资格证书和作品集会被如何看待？
  • FDE 的招聘启事中几乎不会把特定资格证书列为条件。作品集方面，比起数量，更看重“是否在某人的实际业务中被使用”。能有一个可以讲述上线运营后情况（什么坏了、怎么修的、现在如何被使用）的项目，比多个只能运行的成果物更受好评。
