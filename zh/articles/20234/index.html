遗留 ERP 集成：防腐层与 CDC 读写分离实践

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

这篇指南面向 FDE，讨论如何对接客户的遗留 ERP。核心观点是：直连数据库搭建最快但拆除成本最高，应作为最后手段。文章建议读写分离——读路径优先用变更数据捕获（CDC）从事务日志取数，写路径优先用带错误处理和监控的异步通道（如 SAP IDoc），UI 机器人仅在别无选择时使用。所有数据转换应集中在防腐层（ACL）中，让遗留列名和怪异数据格式不泄漏到新代码，未知值要显式报错而非套默认值。作者还给出五步现场流程，并提醒 Strangler Fig 模式在封闭 ERP 上常不可行。

要点

  • 直连数据库搭建最便宜、拆除最贵，应作最后手段。
  • 读路径优先用 CDC 读事务日志，不碰业务表。
  • 写路径优先选客户运维熟悉的异步通道，如 IDoc。
  • 防腐层集中转换遗留数据，未知值显式报错。
  • Strangler Fig 模式在请求无法拦截的封闭 ERP 上不适用。

用防腐层隔离旧模型、读写分开走，下次 ERP 升级时产品才不会跟着瘫痪。

要点速览

  • 直连数据库搭起来最便宜，拆掉最昂贵。应把它当作最后手段，而不是默认选项。
  • 防腐层把遗留数据模型挡在新代码之外，代价是额外的延迟和多运维一个服务。
  • 读走变更数据捕获，写走带错误处理工具的异步通道。只有别无他路时才用 UI 机器人。

设想你在客户工厂的第二周。Agent 需要读取采购订单、创建收货单，但客户的 ERP 已经用了十多年。API 文档没人维护，数据库管理员倒是很乐意给你一个能直接读表的账号。

几乎每个前线部署工程师（FDE）都会遇到这种情况，而最初几天做出的决定，会在项目里留存很久。难点不在于连上，而在于连接的方式要保证：十八个月后 ERP 升级时，你的产品不会跟着一起崩掉。

最容易进的门，往往最难出

Microsoft 的架构文档对这个问题描述得很准确：遗留系统的 schema 往往错综复杂，API 也已过时。如果不加处理地直接对接，新应用就会被迫沿用遗留系统的语义。

最明显的症状，是

if STAT_CD == "02"

这样的代码散落在新代码各处。到了这一步，你的产品已经和 ERP 紧紧绑在一起。

所以，那个数据库只读账号比看上去更需要谨慎对待。Netguru 一篇关于遗留系统集成的分析说得很直白：直连数据库是搭建成本最低、拆除成本最高的集成模式。演示时它很快。

但此后每次列有变动，你都得再修一次，而且没人会提前通知你。

解决办法不是拒绝一切捷径，而是先盘点所有接入点，再为读和写分别选择。

接入点适用场景代价
直接读写数据库几天内做出原型代码与 schema 绑定，拆除成本极高
变更数据捕获（读取事务日志）遗留应用无法修改时的读路径需要理解每种数据库的日志
异步通道，如 SAP IDoc大批量写入无法立即拿到结果
同步 API（OData、RFC）查询、单条记录写入受制于遗留系统的吞吐量
UI 机器人别无他路时界面一改就失效，错误难以排查

读和写要走不同的门

读路径和写路径的风险不同，应当分开。读方面，如果遗留应用围绕数据库构建且无法修改，Microsoft 建议用数据库触发器，或用读取事务日志的变更数据捕获（CDC），把变更推送给新服务。

两者之中，变更数据捕获更可取：它读取的是事务日志，不必查询 ERP 的业务表，也不必在业务表上挂任何东西。

写路径更敏感，因为写错一笔就意味着账目出错。以 SAP 为例，aixsap 上的一篇分析认为，IDoc 内置错误重处理和监控，适合大批量异步写入，而 OData 是同步的。

同一来源还指出，RFC 仍在使用，但适用范围在收窄，而且调用方需要安装专门的连接器。

这条经验不限于 SAP：优先选择客户运维团队已经会监控的通道。凌晨 2 点某张收货单卡住时，他们需要一个熟悉的界面来重新处理。你留下的脚本帮不上他们。

转换层：唯一知道旧列名的地方

无论走哪扇门，数据都要跨越一条边界。Microsoft 称之为防腐层（ACL）：一个转换层，让一个系统保持不变，同时不损害另一个系统的设计和技术选型。Netguru 的定义更简短：ACL 把遗留系统的数据模型挡在新代码之外。

下面以采购订单为例。列名是虚构的，但数据类型做过 ERP 的人都不会陌生：数字状态码、带前导零的供应商代码、以最小单位存储的金额、以字符串存储的日期。

# acl/purchase_order.py — 唯一允许知道 ERP 列名的文件
from dataclasses import dataclass
from datetime import date, datetime
from decimal import Decimal

class UnknownLegacyValue(Exception):
    pass

@dataclass(frozen=True)
class PurchaseOrder:            # 新应用的模型
    order_id: str
    supplier_id: str
    amount: Decimal
    due_date: date
    status: str                 # "open" | "approved" | "cancelled"

STATUS_MAP = {"01": "open", "02": "approved", "09": "cancelled"}

def from_legacy(row: dict) -> PurchaseOrder:
    code = row["STAT_CD"]
    if code not in STATUS_MAP:
        # 就在这里停下，不要猜
        raise UnknownLegacyValue(f"STAT_CD={code!r} PO={row['PO_NO']}")
    return PurchaseOrder(
        order_id=row["PO_NO"].strip(),
        supplier_id=row["VEND_CD"].lstrip("0"),
        amount=Decimal(row["AMT"]) / 100,
        due_date=datetime.strptime(row["DUE_DT"], "%Y%m%d").date(),
        status=STATUS_MAP[code],
    )

代码不长，但有三点很关键。Agent 和所有下游服务只看到

PurchaseOrder

，永远看不到

STAT_CD

。未知状态码会抛出明确的错误，而不是悄悄套用默认值。ERP 被替换时，你只需重写这一个文件。

ACL 并非没有成本。Microsoft 明确指出，它会增加延迟，也多了一个需要管理和维护的服务。遗留系统较慢时，ACL 可以采用异步、事件驱动的方式运行：数据通过消息完成转换，新的业务逻辑不再受遗留系统节奏的牵制。

这适合大流量的数据流，或两个系统必须完全解耦的场景。

现场五步

第一步是盘点。像上表那样列出所有接入点，注明每个接入点归谁负责、如何报告错误。要问客户的不只是“有没有 API？”，而是“同步中断时，谁会收到通知，去哪里查看？”。

第二步，把读路径和写路径分开，各自选一扇门。读优先用变更数据捕获，写优先用带监控工具的异步通道。第三步，先写 ACL 再写功能，并为真实数据中发现的每个怪异值写一个测试。

第四步，考虑渐进式替换。Martin Fowler 提到，他和同事选择了渐进式现代化，而不是一次性重写。Strangler Fig 模式使用一个门面（facade），也就是代理，拦截发往遗留系统的请求，再路由到旧应用或新服务。

但 Microsoft 也指出，如果发往后端的请求无法拦截，这种模式就不适用，而封闭的 ERP 往往正是如此。这时合理的做法是退回到用变更数据捕获做读取，并接受写入方面进展较慢。

最后一步是记录决策：选了哪扇门、为什么、接受了什么代价。接手的人最需要的就是这份文档。

常见陷阱

第一个陷阱，是让演示用的捷径变成真正的架构。第一周写下的直接查表代码，到上线时可能还在，原因仅仅是没人有时间回头去改。

第二个陷阱，是把 UI 机器人当成“集成”。Workato 提醒，应用界面一变，这类机器人就容易失效。Activepieces 指出了一个更重要的区别：API 会返回状态码，准确告诉你流程为何失败，而机器人只能猜按钮在哪里。

如果非用机器人不可，就把它放在 ACL 后面，这样替换时不必改动其他任何东西。

第三个陷阱是乐观转换。给一个没人看得懂的状态码赋默认值，是让 Agent 在客户真实数据上“自信地出错”的最快途径。

阅读 FDE 岗位描述时，“integrate with customer ERP”或“legacy systems”这类措辞，指的正是这项工作。简历上不要只写“SAP 集成”，要写清楚选了哪个接入点、为什么，以及如何处理同步失败。

本周练习不止于读路径：为你转换过的实体写出逆向函数

to_legacy

，再写一个往返测试。取一条真实记录，转换成新模型，再转换回去，逐字段与原始记录比对。

凡是不一致的地方，比如供应商代码的前导零、货币单位或日期格式，正是写路径会在你没发现之前把客户账目弄乱的地方。
