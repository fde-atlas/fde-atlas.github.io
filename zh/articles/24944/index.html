多智能体设计是什么？FDE 在现场使用的架构模式与判断标准

原标题：マルチエージェント設計とは？FDEが現場で使う構成パターンと判断基準

FDE総研 · 2026-10-19 · 约 10 分钟读完

摘要

这篇文章面向在客户现场部署生成式 AI 的前沿部署工程师，讲解多 Agent 设计的定义、适用场景与实施步骤。核心观点是：先以单 Agent 建立基准，仅在任务可并行、子任务独立时才拆分为多 Agent。文章引用 Anthropic 的研究系统（性能超过单 Agent 90.2%，但 token 消耗约为 15 倍）与 Cognition 的反对观点，整理出编排型、流水线型、路由型、评估型、交接型五种架构模式，并强调输入输出契约、评测、追踪、权限最小化及向客户移交运营等要点。

要点

  • 多 Agent 的本质是按角色拆分上下文与工具，而非单纯提升性能。
  • Anthropic 案例显示多 Agent 优于单 Agent 90.2%，但 token 消耗约 15 倍。
  • Cognition 警告并行子 Agent 缺乏共享上下文会导致成果不一致。
  • 推荐流程：先建评测集与单 Agent 基准，再依据瓶颈决定拆分点。
  • 需用 JSON 契约固定交接、设置成本上限，并按最小权限设计以利移交。

什么是多智能体设计？与单一智能体有何区别？

多智能体设计是一种设计方法，通过让多个分工不同的 AI Agent 协作来解决一个任务。

FDE（Forward Deployed Engineer，前沿部署工程师）在客户现场将生成式 AI 融入业务时，需要在早期阶段决定“是使用一个智能体，还是拆分为多个”。Palantir 推广的 FDE 这一职业，其职责是在客户业务和生产数据旁边构建系统。因此，这一决策影响的不是演示效果，而是运营成本以及故障时的排查难易度。

定义：拆分角色、上下文与工具的设计

多智能体的本质在于，将原本由单个 LLM 承载的上下文和工具，按角色进行拆分。

单一智能体在一个上下文窗口中反复进行规划、工具调用和结果解读。而在多智能体中，例如拆分为“负责规划的指挥塔”“负责检索的调查员”“负责检查输出的评估员”等角色，并让每个角色拥有专用的提示词、工具和上下文。由于每个智能体只关注自己的职责范围，指令不容易混淆。另一方面，这也带来了设计智能体之间信息传递的需求。

用对比表整理与单一智能体的区别

将两者的区别理解为“成本、并行性、调试难易度”之间的权衡，比单纯看性能更容易做出判断。

视角单一智能体多智能体
上下文全部集中在一个窗口中按角色拆分、摘要后传递
并行执行基本为串行可以同时执行子任务
Token 消耗相对较少容易大幅增加（后述公开案例中约为 15 倍）
调试可通过单条追踪链路追踪需要追踪智能体之间的交互
失败模式长上下文中遗漏指令信息断绝、判断不一致、错误连锁
适合的用途紧耦合的串行工作大范围调研、独立的子任务

Anthropic 在 2024 年 12 月的技术文章“Building effective agents”中建议，应从简单的架构开始，只在必要时才增加复杂度。就笔者的实际感受而言，在客户的 PoC（概念验证）中一开始就搭建多智能体，往往会遇到无法区分是精度问题还是协作问题的情况。

应该使用多智能体的场景和应该避免的场景是什么？

对于可并行化的调研和独立的子任务，多智能体是有效的；但对于紧耦合的工作，单一智能体更为稳妥。

适合的场景：广度优先的调研与独立任务

多智能体容易发挥效果的场景，是能够将问题分解为独立的子问题，并且可以并行调研这些子问题的场景。

Anthropic 在 2025 年 6 月的文章“How we built our multi-agent research system”中公开了由指挥塔（Claude Opus 4）指挥多个子智能体（Claude Sonnet 4）的架构。在内部调研任务评测中，报告称其超越了单一 Claude Opus 4 智能体 90.2%。同一篇文章还指出，性能差异的大部分可以用 token 消耗量来解释，并且多智能体使用的 token 约为普通聊天的 15 倍。

替换到 FDE 的现场，以下业务可以成为候选。

  • 跨多个内部系统和文档群进行调研的竞品调查或规程调查
  • 按客户或站点并行执行相同处理的数据整理或分类
  • 需要将生成与检查分开、质量要求严格的文档撰写

应避免的场景：紧耦合、低预算、短工期

在前一个判断强烈约束后一个判断的工作中，拆分智能体会导致上下文中断，质量容易下降。

Cognition 在 2025 年 6 月的文章“Don’t Build Multi-Agents”中指出，如果并行运行的子智能体在互不知晓对方判断的情况下工作，交付成果的一致性会被破坏。在此基础上，他们提出了重视共享上下文以及行动中包含隐含判断的原则。像编码这样一系列变更相互强依赖的工作，正是这种典型情况。

判断维度适合多智能体适合单一智能体
任务依赖关系子任务相互独立后续判断依赖前面的判断
预算成果价值大于 token 单价需要严格控制处理单价
工期与体制有时间搭建评估和观测基础需要在几周内拿出 PoC
所需的可解释性可以通过日志设计来保证希望用单条路径解释判断过程

多智能体的代表性架构模式有哪些？

代表性的架构有编排者型、流水线型、路由型、评估者型、交接型这 5 种。

本文基于 Anthropic 和 OpenAI 公布的指南中的分类，整理成便于 FDE 在一线使用的形式。Anthropic 的《Building effective agents》展示了提示链、路由、并行化、编排者＝工作者、评估者＝优化者这 5 种模式。OpenAI 的《A practical guide to building agents》（2025 年）则将多 Agent 分为管理器型和分散（交接）型。

模式结构适用场景主要风险
编排者＝工作者指挥塔分解任务并分发给工作者调研、报告撰写指挥塔的分解失误会波及全局
流水线（链）按固定顺序依次处理各工序提取→整理→验证灵活性低
路由对输入分类并分派给专门的 Agent客户咨询应对、窗口业务分类精度决定上限
评估者＝优化者生成方与评估方往复交互质量标准明确的文档、代码循环成本增加
交接（分散）Agent 之间相互接手职责多阶段的客户应对责任归属容易模糊

中央集权型：编排者＝工作者

由指挥塔承担任务分解与整合的中央集权型，易于控制，是 FDE 最容易优先考虑的架构。

担任指挥塔的 Agent 制定计划，向子 Agent 传递“目标、输出格式、可使用的工具、结束条件”，并整合返回的结果。前述 Anthropic 的调研系统也是这种形式。设计中最关键的是对子 Agent 指令的粒度。如果指令含糊，子 Agent 之间可能会重复进行相同的调研，或遗漏某些范围。

分散型：交接与路由

在入口处进行分流的路由，以及相互接手职责的交接，是与业务部门分工明确的组织相性良好的架构。

例如，如果像“财务咨询”“人事咨询”这样业务边界清晰，就可以让 Agent 的边界与组织边界保持一致。这样一来，客户方的相关部门就容易成为提示词和知识的所有者。考虑到 FDE 离开后的运营移交，这一点相当重要。

质量保障型：评估者＝优化者

将生成与评估分配给不同 Agent 的架构，是在能够将评估标准语言化的业务中提升质量的手段。

评估方按照检查清单对生成方产出的结果进行判定，并退回不合格的部分。如果评估标准只是“易于阅读”这类模糊的要求，循环就难以收敛。前提是要预先设定退回次数的上限。

多 Agent 设计的步骤是什么？

先用单一 Agent 建立基准线，测量其极限之后再进行拆分，按这个顺序推进是安全的。

步骤 1〜3：确定基准线与拆分点

最初的 3 个步骤，目标是达到能用数据说明拆分理由的状态。

  • 建立评测集：从客户的真实数据中收集有代表性的输入和期望输出，并确定合格与否的判定标准。
  • 用单一 Agent 测量基准线：用同一个评测集，记录精度、处理时间和 Token 消耗。
  • 识别瓶颈并确定拆分点：只有当存在“上下文溢出”“并行处理可以提速”“需要检查员”等能通过拆分解决的课题时才进行拆分。

步骤 4〜6：设计契约、评估与观测

后半的 3 个步骤，是将 Agent 之间的传递固定为“契约”，并使其在生产环境中可追踪。

  • 定义输入输出的契约：用 JSON Schema 等固定各 Agent 的输入输出，减少自由文本的传递。
  • 同时进行 Agent 单元评估与整体评估：分别测量各个 Agent 的精度和最终交付物的精度。
  • 实现追踪与停止条件：记录 Agent 之间的消息、工具调用和 Token 消耗，并设定迭代次数和成本的上限。

根据笔者的经验，如果省略步骤 4、一开始就用自由文本传递，之后在定位故障原因上往往会耗费大量时间。

FDE 在一线引入多 Agent 时的注意事项是什么？

最大的陷阱是上下文的断绝和成本膨胀，在客户环境中还会被要求权限设计和问责机制。

技术层面：上下文共享、错误传播与成本

在技术层面，需要在设计阶段就控制住信息断绝、错误连锁和 Token 费用这三个问题。

风险会发生什么对策方向
上下文的断绝子 Agent 在不了解前提的情况下做出判断共享内存、传递判断日志
错误的连锁上游的错误在下游被放大验证中间输出、Schema 检查
成本的膨胀并行化和循环导致 Token 急剧增加预算上限、区分使用模型
非确定性相同输入也会产生不同路径保存追踪记录、用评测集做回归测试

区分使用模型也很有效。采用指挥塔使用高性能模型、常规工作者使用轻量模型的架构，更容易在成本与精度之间取得平衡。

组织层面：对客户的说明、权限与运营移交

在组织层面，与客户就“由谁、对哪个 Agent 的判断承担责任”达成一致是必不可少的。

按照“最小权限原则”为每个 Agent 分配可访问的数据和系统权限也很重要。对于涉及写入或对外发送的工具，应考虑加入人工审批环节。FDE 并不会一直驻留在客户现场。以客户方能够接手的形式保留提示词、评测集和追踪记录的查看方法，是让多 Agent 投入实际运营的条件，笔者如此认为。
