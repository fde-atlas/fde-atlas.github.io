编程智能体时代 FDE 需要什么技能

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

文章综合 GitHub、Cognition、Addy Osmani 等多个信源，讨论 Agent 能自动写代码后，FDE 的价值所在：代码生成变快使瓶颈转移到定义、约束和评判三个环节。GitHub 分析 2500 多份 Agent 配置文件，发现多数失败源于描述过于模糊；Cognition 指出企业关心的是价值而非系统忙碌程度。文章认为 FDE 应是单一岗位而非流水线，并给越南等外包背景开发者提出转型建议。

要点

  • GitHub 分析 2500 多份 Agent 配置文件，多数失败因描述模糊。
  • 代码生成变快把瓶颈推向测试、评审、部署和维护环节。
  • FDE 三项核心任务：定义用户与成功标准、维护活的规格说明、评判结果。
  • 测试通过不等于代码被理解，评审已成吞吐量瓶颈。
  • 评判信息应回流修正定义，FDE 是岗位而非流水线。

GitHub 分析了 2500 多份 Agent 配置文件，多数因过于模糊而失败，问题出在布置任务的人。

要点速览

  • GitHub 分析了 2500 多份 Agent 配置文件，发现多数失败是因为过于模糊：难点在需求规格，而不在生成代码。
  • Cognition 认为，代码生成更快只会把问题推到测试、评审、部署和维护环节；企业要的是价值，而不是一个看起来很忙的系统。
  • FDE 保留的三项任务是：明确用户和成功标准，把规格说明当作活文档来写，以及靠理解代码而不是等测试通过来评判结果。

据 Addy Osmani 介绍，GitHub 分析了 2500 多份 Agent 配置文件，发现其中大多数失败的原因很平常：写得太模糊。写这些文件的人没有说清楚自己想要什么。

这一发现与 Cognition 在 AI Engineer World’s Fair 2026 上的观点吻合。在这家公司看来，更快地生成代码并不能解决全部问题，因为测试、评审、部署和维护都还在。瓶颈没有消失，只是转移了。

对想转做前线部署工程师（FDE）的开发者来说，这是一个值得重视的信号。打代码快已经不是别人愿意付钱的技能。真正有价值的，是 Agent 目前还无法替你完成的三件事：定义问题、约束 Agent、评判结果。

外包执行，FDE 做决定

Ghanemzadeh 在一篇谈前线部署 AI 工程的文章中划了一条清晰的界线：外包人员负责执行，FDE 负责决定。按他的描述，FDE 是一个有主见的操盘者，清楚要做什么、按什么顺序做、怎么做，以及如何衡量成功。

定义环节的第一个问题听起来简单，却最常被跳过：用户是谁？Ghanemzadeh 写得很直接：如果你说不出用户是谁，那根本就不算 FDE 项目。“客户想要一个 AI Agent”这样的需求只是愿望，还算不上问题。

以一家想用 Agent 处理贷款申请的银行为例。“实现核保自动化”听上去很具体，却给不出任何方向。

换成“每天大部分时间都在核对材料的支行核保人员”，你马上就知道该衡量什么、先解决什么，以及做到什么程度才算完成。

Agent 自己做不了这一步。它不会坐在核保人员旁边，也看不到哪项工作让对方叹气。所以定义这件事仍然属于一线的人。

约束是一份活的规格说明，不是一条提示词

fde.academy 博客上的一篇文章把工程师与 Agent 协作时的新角色描述为：定义任务、设定约束，然后引导 Agent。这是从业者的看法，不是研究结论。

即便如此，它与上文 GitHub 的发现一致：Agent 配置文件因模糊而失败，也就是说，失败发生在约束环节。

Osmani 引用了 GitHub 的规格驱动开发方法：规格说明成为共享的唯一事实来源，是一份随项目演进、可执行的活文档。

“活”字很关键。规格说明不是项目启动时写一次就归档了事，而是你、客户和 Agent 之间的契约，现场一有新发现就要更新。

回到银行的例子。一条好的约束可以是：“Agent 只标记材料缺失的申请，绝不自行拒绝任何申请。”这一句话起了两个作用：限制了 Agent 的行为，也记录了一项业务决策，以后写代码的人都必须遵守。

写出这句话，需要理解客户的风险，光靠提示词语法做不到。因此约束与定义直接相连：不知道用户是谁，就不知道哪些事绝不能发生在他们身上。

为什么评判成了新瓶颈

如果说定义和约束是输入，评判就是压力最集中的地方。Osmani 直接点明了问题：AI 生成代码的速度远远超过人评估代码的速度，评审变成了吞吐量问题。

很多团队的第一反应是依赖测试。Osmani 同意测试必不可少，但他明确表示测试不够。测试只能检查编写者想到的情况；代码是否真正满足客户需要，仍得由理解代码的人来回答。

他还进一步指出，“评审过的代码就是被理解的代码”这一常见的组织假设已经不成立。当一个人每天批准几十个 Agent 写的 PR 时，批准按钮只能说明代码被看过，证明不了有人真正看懂了。

Cognition 把这一论点推到企业层面。强监管行业的大公司想知道的是系统能否创造价值，至于系统忙不忙，它们并不关心。一个 Agent 可以通宵运行、提交几百个 PR，却什么都没交付。

分辨“忙碌”和“有价值”是一种判断，而这种判断建立在一开始设定的成功定义之上。fde.academy 那篇文章的结论是，评判这一层不会因为写代码那一层变快就自动化。这是一种观点，但 Osmani 和 Cognition 给出的证据都偏向它。

三项任务，三种失败方式

把三项任务放在一起看，会发现每项都有自己的失败方式，而且任何一种都可能被一个非常卖力的 Agent 掩盖。

FDE 任务 要回答的问题 出问题的信号 如何练习
定义 用户是谁，先做什么，如何衡量成功？ 说不出用户是谁；需求只是“做一个 AI Agent” 为每个工单写一句话描述用户，再写一个成功指标
约束 Agent 可以做什么，绝不能做什么？ 配置文件或规格说明含糊；规格说明写完一次就弃之不顾 把规格说明当作活文档维护，Agent 每犯一次错就更新
评判 结果是否创造价值，你是否理解代码？ 把测试通过当作完成；把评审过当作看懂了；把“忙碌”误当成“有价值” 批准前亲自讲清每处改动；对照定义好的标准衡量结果

评判反过来影响定义

Cognition 把客户交付和产品反馈描述为一个闭环：现场学到的东西回流，影响产品决策。落到这三项任务上，闭环的形态很清晰：末端的评判把信息反馈给前端的定义和约束。

当评判显示结果没有带来价值时，有一个实用的排查方法：先别怪 Agent，检查一下用户是否找对了，规格说明里是否还有模糊之处。修正输入通常比修正输出便宜。

这也是三项任务很难拆给三个人的原因。定义用户的人应当就是评判结果的人，否则没人会发现规格说明已经偏离现实。所以 FDE 是一个岗位，而不是一条流水线。

这个岗位的需求在增长。The Pragmatic Engineer 报道称，Google、OpenAI 和 Anthropic 对 FDE 的招聘需求非常旺盛。当打造 Agent 的公司也在招人站在 Agent 和客户之间，它们缺什么技能就不难猜了。

越南开发者该练什么

很多越南开发者出身外包，需求在客户那边就定好了，团队只管执行。这正是 Ghanemzadeh 所说的外包人员模式。转做 FDE，意味着要学会提出过去由别人替你回答的问题，这一点适用于任何交付型公司出身的开发者。

从当前的工作做起。把工单交给 Agent 之前，先写一句话说明用户是谁，写一个可衡量的成功标准，再写三条 Agent 不得违反的约束。如果写不出来，这个工单就还没准备好，无论交给 Agent 还是交给人。

阅读 FDE 职位描述时，留意“直接与客户合作”“定义需求”“对结果负责”这类表述。

在简历上，不要只罗列做过的功能，要写清你如何确定用户、设定了哪些成功标准，以及如何验证系统创造了价值，而不只是在运行。

Agent 写代码只会越来越快。招聘方不会问你能生成多少行代码，他们会问你是否知道哪些代码值得留下。
