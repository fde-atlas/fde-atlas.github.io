Sierra 对前沿部署工作的诠释是 Agent Engineer：负责构建、调优和运维客户专属 Agent 的人。整个面试流程围绕一个问题展开——你是真正理解 Agent 的工作原理，还是只会导入一个现成的？候选人反馈显示，面试中包含一个 take-home 作业和一轮专门为此设计的调试环节，并且在 2026 年 4 月，Sierra 重新设计了其工程 onsite 面试，聚焦于用 AI 进行构建。

什么是 Agent Engineer

Sierra 曾公开发表过关于 Agent Engineer 职位的介绍：针对客户的真实工作流构建和调优 Agent，在生产环境中对其行为负责，并随着客户需求的变化持续迭代。first-party28

从职能上看，这是一个以 Agent 为核心职责的 builder 型 FDE：客户是真实且具名的，部署成果归客户所有，采用率是衡量标准。

目前的职位名称是 Software Engineer, Agent，并将其定位为负责 Agent 开发生命周期，“从初始试点到部署和持续迭代”，服务的客户包括 The GAP、Rocket Mortgage、SoFi、Sutter Health 和 SoftBank。first-party42

与通用 FDE 职位的不同之处在于，它要求在某个特定技术领域具备深度。你需要能够精确地推理工具 schema、升级路径、guardrails、故障处理、非确定性行为的评估，以及当 Agent 在客户的客户面前自信地给出错误答案时会发生什么。

电子表格问题，详解

一道以所报道题目风格编写的练习题，并非 Sierra 自己的题目：三个阶段，每个阶段都会打破前一个阶段的设计。

单元格存储数字或公式，例如 =A1+B1+2。大声认同这个语法足够小，这样这一小时就能花在图结构上而不是解析器上。

阶段新需求重构前先说明会破坏什么
1set(cell, raw), get(cell)没什么。每次读取时递归求值是正确的——直接交付，并说明每次读取的代价是该单元格的整棵依赖树。
2拒绝循环引用；保持表格不变递归求值器永远不会终止。当新公式的某个输入已经能够到达被编辑的单元格时，编辑恰好会创建一个环，所以在修改任何内容之前先检查这一点。
3即时读取；一次变更只重新计算受影响的部分读取时求值会重复共享的工作。缓存值，维护一个读取者的反向索引，并且只重新计算下游单元格——每个单元格只计算一次，按依赖顺序进行。
import re

REF = re.compile(r"[A-Z]+[0-9]+")

class CycleError(ValueError):
    pass

class Sheet:
    def __init__(self):
        self.raw = {}      # cell -> "7" or "=A1+B1+2"
        self.deps = {}     # cell -> cells its formula reads
        self.users = {}    # cell -> cells whose formulas read it
        self.value = {}    # cell -> cached number; get() never computes

    def _reaches(self, start, target):
        # stage 2: can we walk from start to target along deps? (iterative DFS)
        stack, seen = [start], set()
        while stack:
            c = stack.pop()
            if c == target:
                return True
            if c not in seen:
                seen.add(c)
                stack.extend(self.deps.get(c, ()))
        return False

    def set(self, cell, raw):
        new = set(REF.findall(raw)) if raw.startswith("=") else set()
        if any(self._reaches(d, cell) for d in new):  # reject before mutating anything
            raise CycleError(f"{cell} would depend on itself")
        for d in self.deps.get(cell, ()):
            self.users[d].discard(cell)
        for d in new:
            self.users.setdefault(d, set()).add(cell)
        self.raw[cell], self.deps[cell] = raw, new
        self._recompute(cell)

    def _eval(self, cell):
        raw = self.raw.get(cell, "0")
        if not raw.startswith("="):
            return int(raw)
        return sum(self.value.get(t, 0) if REF.fullmatch(t) else int(t)
                   for t in (p.strip() for p in raw[1:].split("+")))

    def _recompute(self, start):
        # stage 3: only cells downstream of the edit, each evaluated once, in dependency order
        affected, stack = {start}, [start]
        while stack:
            for u in self.users.get(stack.pop(), ()):
                if u not in affected:
                    affected.add(u)
                    stack.append(u)
        waiting = {c: sum(d in affected for d in self.deps.get(c, ())) for c in affected}
        ready = [c for c in affected if waiting[c] == 0]   # Kahn's algorithm on the affected subgraph
        while ready:
            c = ready.pop()
            self.value[c] = self._eval(c)
            for u in self.users.get(c, ()):
                if u in affected:
                    waiting[u] -= 1
                    if waiting[u] == 0:
                        ready.append(u)

    def get(self, cell):
        return self.value.get(cell, 0)

代价：

get

是 O(1)；一次写入的代价是一次深度优先搜索加上对 A 个下游单元格和它们之间 E 条边的 O(A + E)。只在受影响的子图上运行 Kahn 算法，正是让菱形结构——A1 输入到 B1 和 C1，两者又都输入到 D1——只对 D1 求值一次而非两次的关键。

一次触及半个表格的写入：将单元格标记为脏，并在读取时惰性重新计算。连续多次写入：将它们批量处理，只重新计算一次。一个无法求值的公式：将错误作为其值存储并让它传播，就像电子表格在下游显示 #VALUE! 那样。拓扑排序，逐步讲解 →

为什么不用框架的约束很重要

候选人反馈称面试官会考察这一点，而且它是所有已报道的 FDE 面试流程中最清晰的信号提取手段——值得超越这一家公司去理解它。

智能体框架恰好隐藏了那些在生产环境中会出问题的部分。亲手构建一个，你就被迫做出框架原本替你做的每一个决定：

框架隐藏的决策生产环境中会出什么问题
终止条件Agent 永远循环，或在完成前一步就停下。两者都很常见；两者都是你的 bug，而不是模型的。
工具结果格式化一份原始的 400 行 API 响应会淹没上下文，模型会丢失任务的线索。
循环内的错误处理一次失败的工具调用变成了异常，而不是 Agent 可以从中恢复的观察结果。
工具 schema 设计模糊的参数描述会产生自信却错误的参数。大多数“模型不行”的报告其实是 schema bug。
上下文管理无限增长的历史意味着随着对话变长，成本上升、延迟增加、质量下降。
升级给人工从不交接比出错更糟——而这是一个产品决策，不是技术决策。

问题不在于你的 Agent 能不能跑通——而在于你能否说清为什么做出这六个决策中的每一个，以及在不同的约束下你会如何改变。只会配置框架的候选人做不到，而且这个差距在两分钟内就能听出来。

一个手写的最小客服 Agent 循环

针对 OpenAI Responses API 的大约四十行代码，汇总指南说 take-home 作业会提供这个 key。上述六个决策中的每一个都对应一行你可以指出的代码。

import json

MODEL = "the-model-your-brief-names"
POLICY = "You are Acme's support agent. Look orders up before answering. Never promise refunds."
MAX_STEPS, MAX_RESULT_CHARS = 8, 2_000
HANDOFF = "I'm handing you to a teammate who can help with this."

def lookup_order(order_id):
    return {"order_id": order_id, "status": "shipped", "eta": "2026-10-24"}  # the client's API goes here

TOOLS = [
    {"type": "function", "name": "lookup_order", "strict": True,
     "description": "Fetch one order by id. Call this before answering anything about an order.",
     "parameters": {"type": "object", "additionalProperties": False, "required": ["order_id"],
                    "properties": {"order_id": {"type": "string", "description": "Like 'A-10293'."}}}},
    {"type": "function", "name": "escalate_to_human", "strict": True,
     "description": "Hand off to a person: refunds, anything policy forbids, or when you are unsure.",
     "parameters": {"type": "object", "additionalProperties": False, "required": ["reason"],
                    "properties": {"reason": {"type": "string"}}}},
]
HANDLERS = {"lookup_order": lookup_order}

def run_turn(client, history):
    """One customer turn. Extends history in place; returns (reply, status)."""
    for _ in range(MAX_STEPS):
        resp = client.responses.create(model=MODEL, instructions=POLICY, input=history, tools=TOOLS)
        history += resp.output                    # the model's calls (and any reasoning) stay in context
        calls = [item for item in resp.output if item.type == "function_call"]
        if not calls:
            return resp.output_text, "answered"   # exit 1: the model answered
        handoff = None
        for call in calls:
            try:
                args = json.loads(call.arguments)
                if call.name == "escalate_to_human":
                    handoff, output = args["reason"], "handed off"
                else:
                    output = json.dumps(HANDLERS[call.name](**args))[:MAX_RESULT_CHARS]
            except Exception as e:                # a failed call is an observation, not a crash
                output = json.dumps({"error": type(e).__name__, "detail": str(e)[:200]})
            history.append({"type": "function_call_output", "call_id": call.call_id, "output": output})
        if handoff:
            return HANDOFF, "escalated"           # exit 2: a person takes over
    return HANDOFF, "step_limit"                  # exit 3: the budget ran out; never loop forever

成本与权衡：表格与循环

对于三个电子表格阶段，时间和空间都是通常的含义。这里 V 是单元格数量，E 是公式引用数量，A 是某次编辑下游的单元格集合。对于 Agent 的调节参数，时间指延迟，空间指进入上下文窗口的内容。

情形时间空间原因
表格阶段 1：读取时求值set 为 O(1)；get 遍历单元格的整棵依赖树，共享单元格会被重复遍历O(V) 个公式，外加递归深度正确且易于编写。遇到循环时永远不会终止。
表格阶段 2：拒绝循环set 增加一次 DFS：最坏情况 O(V + E)seen 集合，O(V)检查在任何改动发生之前运行，因此被拒绝的编辑不会留下任何痕迹。
表格阶段 3：缓存 + 反向索引get 为 O(1)；set = DFS + O(A + EA)deps、users、value：O(V + E)为每条边的两个方向都付出内存，换来即时读取。
提高 MAX_STEPS最坏情况下每轮延迟随每次额外的模型调用而增长历史记录随每次调用及其输出而增长step_limit 退出更少，但卡住的 Agent 在放弃前会消耗更多。
降低 MAX_RESULT_CHARS调用更快、更便宜每个工具结果进入上下文的部分更少硬截断可能恰好丢掉那个关键字段。更好的做法是选择字段或分页。
度量 pass^k，而非单次运行每个场景的 API 调用次数乘以 k无若单次通过率为 80%（假设各次运行相互独立），pass^8 为 0.8⁸ ≈ 0.17。

这个环节中的常见错误

  • 用 Python 做递归式循环检测递归 DFS 在链长超过约 1,000 个单元格（Python 默认递归上限）时会因 RecursionError 而崩溃。这就是 _reaches 使用显式栈的原因。写这段代码时要把这一点说出来。
  • 重试会改变状态的工具超时并不意味着操作失败了。盲目重试退款或取消操作，客户可能会被重复扣款或重复入账。发送一个幂等键，或者在重试前先查询状态。
  • 对 JSON 字符串做切片[:MAX_RESULT_CHARS] 可能从某个值的中间切开，导致模型读到残缺的 JSON。在练习中这可以接受。在真实项目中，应在序列化之前挑选任务所需的字段，或者返回一页结果和一个游标。
  • 在提示词里修 schema 缺陷当模型在本该传订单 ID 的地方传了名称时，往 POLICY 里加更多规则只是在治标。应修复参数描述并给出示例值，例如 "Like 'A-10293'."。该页面指出，大多数“模型不行”的报告最终都被证明是 schema 缺陷。
  • 发现第一个缺陷就停下据称这轮调试环节埋了大约三个缺陷。修掉一个就宣布完成，说明你已停止排查。每修复一个缺陷后，都要重新检查预期行为图，并在其他地方寻找同类缺陷。

自我检测

A1 = 1，B1 = =A1+1，C1 = =B1+1。你调用 set("A1", "=C1+1")。会发生什么？

new

为 {C1}。

_reaches("C1", "A1")

会遍历 C1 → B1 → A1 并返回 true，因此

CycleError

被抛出

before

任何索引变更。A1 仍然是 1，所有缓存值保持不变。

A1 输入到 B1 和 C1；两者又输入到 D1。你把 A1 设为 5。会运行多少次求值，顺序由什么决定？

四次：A1、B1、C1、D1 各一次。Kahn 计数显示 D1 有两个等待输入，所以只有在 B1 和 C1 都完成后它才会就绪。B1 和 C1 的执行顺序可以任意。

模型调用了一个名为 cancel_order 的工具，但它不在 HANDLERS 中。循环会怎么做？

HANDLERS[call.name]

抛出异常

KeyError

在

try

内部，因此输出变成

{"error": "KeyError", ...}

在相同的

call_id

下。它会回到历史记录中，循环继续，模型可以恢复。这会消耗 8 步中的一步。

某个场景的通过率是 80%。你演示了一次，它通过了。你证明了什么？

几乎什么都没证明。单次通过本来就有 80% 的概率发生。如果各次运行相互独立，8 次全部通过的概率是 0.8⁸ ≈ 0.17。这个差距正是 pass^k 要揭示的，所以要把每个场景运行多次并报告通过率。

快速问答

Sierra 的 Agent Engineer 面试流程是什么？

候选人的描述包括：招聘人员电话沟通、技术初筛、一道构建客服 Agent 的家庭作业、一轮针对陌生代码库的调试、一场演示，以及一轮同时考察与 Sierra 价值观契合度的招聘经理面试。2026 年 4 月，Sierra 公布了一次流程改版：系统设计电话初筛，以及一场 AI 原生的现场面试——你需要规划一个产品，用自己顺手的 AI 工具构建两小时，然后进行答辩。请向你的招聘人员确认你会遇到哪个版本。

在 Sierra 的家庭作业中可以使用 Agent 框架吗？

Sierra 没有公布过家庭作业的规则。一份汇总的候选人指南称，面试官希望看到直接调用工具的循环，而不依赖任何框架；而 2026 年 4 月的现场面试则允许候选人使用自己选择的框架。手写循环仍然是最稳妥的准备方式，因为它会逼你面对框架所隐藏的每一个决策：终止条件、工具结果的格式化、循环内的错误处理、schema 设计、上下文管理以及升级转人工。

Sierra 的电子表格面试题是什么？

一份汇总的候选人指南提到，技术初筛中有一道关于检测电子表格单元格之间循环引用的题目，并会根据要求扩展到更高效的方案。分三个阶段准备：递归求值公式、拒绝任何新输入已经能到达被编辑单元格的编辑操作，然后缓存值并按拓扑顺序只重算下游单元格。Sierra 表示其电话初筛此后已改为系统设计，所以请确认具体形式。

如何准备一场埋有预设 bug 的调试面试？

练习一套明确的方法而非追求速度：在编辑前完整阅读代码，形成具体假设，添加最小的验证手段来证实或推翻它，修复，然后验证修复效果，并检查同类 bug 是否出现在其他地方。每一步都要大声说出来——被评分的是方法本身，而不是前十分钟找到的 bug 数量。

什么是 AI Agent 工程师？

一个专注于针对特定客户的工作流构建、调优和运营 Agent 的建设者角色，负责其在生产环境中的行为。Sierra 曾公开发表过关于该角色的文章。从职能上看，它是一个职责聚焦于 Agent 的前沿部署工程师，要求在工具 schema、升级设计、防护栏以及评估非确定性行为方面具备非同寻常的深度。
