FDE 第一周交付什么

原标题：What an FDE Ships in Week One

Reveneau · 2026-09-08 · 约 9 分钟读完

摘要

Reveneau 这篇文章主张，前沿部署工程师在第一周就应交付一个能在真实环境中运行的小成果，例如一个跑在生产数据上的转换、一个读取实时记录的界面，或一个调用真实第三方 API 并处理真实错误的集成。其价值不在成果本身，而在于诊断：尽早暴露数据质量问题、权限模型与业务不符、API 真实行为以及发布流程的真实时长。作者认为最有价值的发现是摸清某家公司一次变更到达生产环境实际需要多久，这比开发估算更能决定项目进度。文章同时警告快速交付的风险：原型中的捷径（硬编码凭证、跳过错误处理）可能被后续系统依赖，导致演示惊艳但生产遥遥无期。对策是书面说明原型伪造了什么，并保持足够小以便随时丢弃。在 AI 写代码的场景下，评测套件应先于代码从规格中产生，且不能让模型自评。客户需在第一天前提供访问权限、真实数据集和能当天答疑的联系人。

要点

  • 第一周应交付触及真实数据、真实权限和真实发布路径的小成果。
  • 线框图、架构幻灯片或基于手工导出 CSV 的脚本不算合格交付。
  • 小规模发布是范围界定工具，能在数天内发现真实项目范围。
  • 最有价值的产出是摸清变更到达生产的真实时长。
  • AI 写代码时评测套件须先于代码产生，且模型不能自评。

前沿部署工程师应该在第一周交付（发布到真实使用中）一个基于真实数据的小而可用的东西。不是原型图，也不是在一小部分精选数据上的演示：而是一个数据转换、一个读取实时记录的界面、一个返回真实响应的集成。其意义在于诊断而非宣传。当你尝试发布一个极小的东西时，什么会出问题，这比任何规划文档都能让你更了解这次项目合作，因为它迫使你同时面对数据、权限和发布路径。

发布于 2026 年 9 月 8 日。编辑内容。

核心要点

  • 第一周的产出是一个界定范围的工具。当你发布一个小东西时暴露出的问题，才是真正的范围——用几天而不是几个月就发现了。
  • 它必须触及真实数据、真实认证和真实发布路径，否则它什么都没测试到。
  • 尽早发布一个小东西，也是你了解在这家公司一个变更实际需要多久才能到达生产环境的方法。
  • 失败模式是一个原型，其走捷径的做法被系统的其余部分所依赖，最终带来一个令人印象深刻的演示和一个遥遥无期的上线日期。

这种模式的常态是第一周就有东西能跑起来。这听起来像是取悦他人的噱头，其实是成本最低的测试。

什么才算数

小、真实，并且至少在系统之间的一个连接上端到端跑通。

好的第一周交付物： 一个在生产数据上运行的数据转换、一个读取实时记录的界面、一个调用真实第三方 API 并处理其真实错误的集成、一个在真实条件下触发的告警。

不是第一周交付物： 一张线框图、一页描述架构的幻灯片、一个在某人手工导出的 CSV 上运行的脚本、一个从测试文件读取数据的演示。

区别性特征是与真实系统打交道。在导出数据上运行的东西只测试了你的代码。在实时数据上运行的东西测试了你的代码、数据模式、权限、网络路径，以及那个叫 status 的字段是否真的如某人所说的那样含义的假设。

为什么它是界定范围的工具

以下是第一周发布一个极小的东西真正能揭示的内容。

数据的错误比描述的更多。 被文档标注为必填的列里出现空值、同一类别有三种拼写、2019 年迁移来的记录结构不同。

权限模型与业务不匹配。 业务把两个角色视为不同，而系统把它们建模为一个，或者相反。这是 AI 功能无法发布的常见原因之一，这也是我们为什么单独写了权限是最难的部分。

API 在真实条件下表现不同。 速率限制、间歇性超时、包含文档中未提及字段的请求负载。

发布路径比任何人说的都要长。 你会发现一项变更需要安全审查，审查委员会每两周开一次会，而下一次会议在九天之后。

每一项都是一个范围条目。在第一周发现其中四项并重新规划，是顺利的一周。到第三个月才发现，项目就会因此延期。

了解通往生产环境的路径是最有价值的成果

在第一周产出的所有内容中，最有价值的是了解在这家特定公司，一项变更需要多长时间才能到达生产环境。

第一周先询问，然后通过实际操作来验证。一项变更到达生产环境必须满足什么条件，每个环节由谁签字，以及历史上每次签字实际花了多久。公布的指标不是你想要的答案，真实的耗时才是。

这个数字对进度的影响比构建估算更大，而且大多数项目发现它时都为时已晚。项目如何运作介绍了它在其中的位置。

风险：系统其余部分开始依赖这些捷径

快速发布的失败模式是做出一个令人印象深刻却无法投入生产的原型。

事情是这样发生的。为了让某些东西在第一周跑起来，你硬编码凭证、跳过错误处理、忽略分页、直接查询生产环境。对于第一周的测试来说，这些都是正确的决定。然后某位高层看到了演示，演示变成了计划，这些捷径就此进入了关键路径。

两个习惯可以避免这种情况。用书面形式明确说出第一周的东西伪造了什么。并且把它做得足够小，丢弃它只损失一天，因为“可以随时丢弃”这个选项正是防止它变成架构的关键。

当模型编写代码时，这会是什么样子

在我们的项目中，代码由 AI 编写，这以一种特定的方式改变了第一周的成本结构。

编写代码不再是瓶颈，所以第一周的交付物可以比过去更大。风险在于，更大的第一周交付物意味着在别人的生产环境中有更多未经验证的代码，而生成的代码默认并不安全。

因此纪律要相应调整。评测套件在代码存在之前就从规格说明中产生，第一周的交付物必须像其他任何东西一样通过它。这既保持了速度，又避免第一周产出无人能确认是否正确的东西。评测驱动开发就是这套方法，而绝不让模型给自己的工作打分是让它有意义的关键。

对客户而言：可以期待什么，需要提供什么

请期待第一周的东西并不惊艳，但信息量很大。它的价值在于随之而来的那份意外清单，而不是东西本身。

在入职第一天之前就提供访问权限、一份真实数据集（而非清理过的副本），以及一位能在当天回答问题的指定联系人。前两周包含完整的清单。

当“意外清单”送达时，务必认真阅读。这份文档是你在第一个月里能得到的最有用的东西，也是最常被读得太快的东西。

常见问题

前沿部署工程师在第一周应该交付什么？

一个基于真实数据、小而能运行的东西：一个在生产数据上运行的转换、一个读取实时记录的界面，或一个调用真实 API 并处理其真实错误的集成。而不是线框图、架构幻灯片，或只能在手工导出的 CSV 上运行的脚本。

为什么这么早就发布这么小的东西？

因为它是一个界定范围的工具。接触真实数据可以检验 schema、权限、网络路径，以及“某个字段的含义确实如某人所说”这一假设。在第一周发现四个意外并重新规划，是很好的一周；在第三个月才发现它们，就是一个延期的项目。

第一周产出的最有价值的东西是什么？

了解在这家特定公司，一个变更实际需要多久才能到达生产环境。询问哪些条件必须满足、每一步由谁签字，以及历史上每次签字花了多久，然后通过发布一个东西来验证。是真实耗时，而非公布的目标。这比构建估算更能决定进度安排。

第一周快速发布有什么风险？

风险在于系统的其余部分会开始依赖这些捷径。硬编码的凭证、跳过的错误处理和被忽略的分页，在第一周的测试中都没问题——直到某位高层看到演示，而演示变成了计划。写下这个东西伪造了什么，并保持它足够小，使丢弃它只损失一天。

AI 生成的代码会改变第一周应有的样子吗？

它消除了编写代码这一限制，因此交付物可以更大。风险在于，更大的交付物意味着在别人的生产环境中有更多未经验证的代码。关键纪律是：评测套件来自代码存在之前的规格说明，第一周要像对待其他任何东西一样通过它。

要让第一周顺利开展，客户需要提供什么？

在第一天之前就设置好并测试过的访问权限、一份真实数据集（而非清理过的副本），以及一位能在当天回答问题的指定联系人。然后阅读这一周产生的意外清单——这是第一个月里最有用的文档，也是最常被读得太快的一份。

前沿部署项目如何运行

前沿部署项目分五个阶段运行：在环境内部进行探索、基于真实数据构建原型、部署到生产环境、将可复用的部分产品化，以及逐步退出，让客户自己的团队接管运行。前三个阶段是所有人都会规划的。第四个阶段是把单个客户的工作转化为产品的关键。第五个阶段最容易被跳过，而是否跳过它正是“一次部署”与“一种依赖”之间的区别。AWS 为其合作伙伴计划描述了类似的三阶段结构，最终以合作伙伴独立工作为终点。

前沿部署项目的前两周

前两周决定了之后所有工作的节奏。到第十天，一个运转良好的项目应该已经基于真实数据发布了某个小成果，写下了“正确”的定义，并梳理了变更通往生产环境的路径。浪费这两周最常见的原因是权限问题：一名等待仓库凭证的工程师是公司中最昂贵的闲置资源。第一天之前必须具备三样东西，而这三样都必须由客户提供。

在客户环境内部进行探索

探索电话能让你了解客户能够描述的内容。身处环境内部则能让你发现没人想到要提及的东西，而部署失败往往就出在第二类信息上。Marty Cagan 支持嵌入式模式的论点是，它是一种产品探索技术而非交付技术：走访多个客户现场的工程师能看到一个市场中的共性与差异，这正是客户探索的本质。实践层面的结论是：环境本身就是信息的来源，而你无法从外部研究它。

前沿部署项目的交接与退出

前沿部署项目的结束必须在项目开始时就设计好，在签约时就把日期写进合同。结束时间留待以后再定的项目等于没有终点：它会一直延续下去，因为总还有一项改进要做，而且双方都觉得这种安排很舒服。AWS 将项目结束后的客户自主能力作为其自身计划的设计目标，其合作伙伴模式也以合作伙伴团队独立工作为终点。交接的检验标准不是文档是否交付，而是客户自己的工程师能否在供应商离开之前独立地对系统做出修改。

前沿部署项目中的常见问题

前沿部署项目的失败方式只有少数几种可识别的模式，如果你知道预警信号，大多数在第三周就能看出来。无休止的项目。永远无法投入生产的演示。变成了客户经理的工程师。没人能升级的定制分支。从一开始就不打算上生产的试点。以及只是一份幻灯片的交接。每种失败都有早期信号和具体的干预措施，而工程师更努力工作解决不了其中任何一个。
