什么是 Pull Request 测试？

Pull Request（PR）是开发者向代码库提交变更建议的方式，通常在 GitHub 或 GitLab 等平台上进行。它允许团队成员在将变更合并到主代码库之前进行审查、讨论和批准。

Pull Request 测试是验证这些变更建议的过程，以确保它们不会破坏现有功能或引入 Bug。它确保：

  • 新功能不会破坏现有功能
  • Bug 修复符合预期
  • UI 流程继续按设计正常工作
  • 测试作为 CI/CD 流水线的一部分自动运行

通常，Pull Request 测试包括单元测试、集成测试和端到端（E2E）浏览器测试。

为什么传统的 PR 测试不够用

对许多开发团队来说，PR 测试是一个瓶颈。原因如下：

1. 手动维护

Selenium、Cypress 或 Playwright 等工具需要编写和维护测试脚本。当 UI 发生变化时，这些脚本就会失效。布局偏移、元素重命名或导航流程变更都会导致失败。在 React 或 Angular 等框架中，组件树更新频繁。这给开发者或 QA 工程师带来了持续的负担。

以下是 2026 年的现实：Sonar 的代码状态开发者调查发现，38% 的开发者表示审查 AI 生成的代码比审查人工编写的代码更费力。更令人担忧的是：96% 的开发者并不完全信任 AI 代码的准确性，但只有 48% 会对其进行验证。当你还要维护脆弱的测试选择器时，这种“验证债务”会不断累积。你不仅是在测试自己的功能，还在调试别人 AI 生成的测试夹具。

2. 不稳定的测试

E2E 测试以脆弱著称。测试失败往往是由时序问题或未处理的 DOM 变化引起的，而不是真正的 bug。

3. CI 流水线臃肿

在每个 PR 上运行完整的测试套件会拖慢 CI 流水线，导致代码评审和发布延迟。开发者要等待构建通过，团队失去节奏。测试分片是标准解决方案：将测试套件拆分到多台机器上并行运行。我们的 Playwright 测试分片指南详细介绍了所有主流 CI 平台的配置方法。

Stack Overflow 2025 开发者调查发现，45% 的开发者反映调试 AI 生成的代码比调试人工编写的代码更耗时。失败的 CI 构建和 AI 验证如今占用了大量开发时间。这种低效会随着规模扩大而成倍增加。

4. 覆盖率不足

由于时间限制，大多数 PR 只运行一小部分测试，导致出现盲区、bug 溜进生产环境。移动端视口是一个特别常见的缺口：测试在桌面端通过，却在 375px 宽的屏幕上失败。关于移动端验证的完整解析，请参阅我们的指南如何在 2026 年让网站适配移动端。

2026 年 PR 测试的标准

到 2026 年，“好的”测试不再只是构建通过，而是你的流水线能否在没有 Slack 提醒的情况下自我修复。

标准如下：

  • 每个 PR 自动运行测试，无需手动触发。
  • 真实浏览器模拟，而非单元测试的 mock。
  • 端到端覆盖关键用户流程：注册、登录、结账。
  • UI 变化时自我修复。按钮移动了？测试自动适应。
  • 5 分钟内出结果，快到足以保持心流状态。
  • 零配置，无需访问代码库。

测试为什么会“不稳定”（flaky），如何防止？
