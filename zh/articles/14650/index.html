OR-License 基准测试：Claude Code 得分 0.87，专家为 1.0

原标题：OR-License Benchmark: Claude Code Scores 0.87 vs Expert 1.0

AISOLO Technologies Private Limited · 2026-10-20 · 约 7 分钟读完

摘要

OR-License 是一个基于真实付费运筹优化项目构建的 Agent 评测基准，包含 10 个行业场景、31 个实例。它用客户模拟器隐藏信息，要求 Agent 主动提问、自行建模并交付可运行的方案。评测采用 DAQ 指标，不可行交付记零分。结果显示：11 个前沿模型中，Claude Code 最佳配置严格可行率达 88.39%，DAQ 为 0.87（专家为 1.0）；部分模型在成功任务上的方案质量可超过专家，但计入失败后无一达到专家水平。主要失败类型为建模错误与实现错误。作者建议在开发各阶段持续向客户确认信息，并在求解前审查建模。

要点

  • 基准来自真实付费项目：10 个场景、31 个实例。
  • DAQ 指标将不可行交付记零分，衡量可部署性。
  • Claude Code 最佳配置：可行率 88.39%，DAQ 0.87。
  • 成功任务上部分模型质量超专家，但整体无人达标。
  • 主要失败为建模错误与实现错误两类。

针对编程 Agent 的基准测试大多给模型一个干净整洁的问题。而实际的运筹学（OR）工作并非如此：客户发来电子表格、一个模糊的需求和一个截止日期，必须有人来构建模型、提出正确的问题、编写求解器代码，并交付真正能运行的东西。OR-License 是一个新基准，正是为了测试这一点。其核心发现来自作者的摘要：在 11 个使用编程 Agent 框架的前沿 LLM 中，有几个在成功完成的任务上超越了专家的解决方案质量，但一旦计入失败的交付，没有一个能匹敌专家。

该论文（arXiv）、项目网站、代码和数据集均已公开。如果你关注 Agent 评测，它可以与 FDE-Gym 前沿部署工程师基准和针对私有代码库的 Real-SWE等工作并列，这些工作同样摆脱了干净、自包含的谜题式任务。

为什么运筹学是对 Agent 的一个很好的压力测试？

运筹学是优化真实系统的学科：路径规划、排程、库存、投资组合构建、共享单车物流。难点很少在于求解器本身，而在于建模，即从杂乱的业务描述中决定变量、约束和目标应该是什么，然后忠实地实现并验证输出。

这使它成为对大家都在谈论的长时程 Agent 行为的一个天然测试。Agent 必须获取信息、做出建模选择、编写代码、运行求解器、检查结果，并以要求的格式交付。错误会不断累积，这与我们的循环工程指南中针对一般编程 Agent 讨论的动态相同。

一张基准测试记分板，展示了干净基准与真实客户工作之间的差距

OR-License 是如何构建的？

根据论文摘要和代码仓库，该设计包含四个部分。

  • 真实项目。 这 31 个实例来自付费的运筹学（OR）工作。经过去标识化处理后，它们保留了原始需求、输入数据、交付物格式和信息边界，这正是它们与教科书习题的区别所在。
  • ORSim，一个客户模拟器。 该基准测试不会一开始就把所有信息交给 Agent，而是包含一个受控模拟器，在被询问时披露业务事实，但不提供运筹学专业知识。Agent 必须自己想清楚该问什么。根据 README，模拟器和源码审查者由一个 DeepSeek 模型驱动。
  • 隐藏式评测。 任务专属的评估器检查可行性并计算目标值，部分任务还要求对提交的优化源码进行审查。质量与基准测试构建前客户接受的原始专家方案进行对比。
  • DAQ。 部署调整质量（Deployment-Adjusted Quality）对各个实例的专家相对质量取平均值，并将不可行的交付物记为零分。

DAQ 的设计是最有意思的一点。许多基准测试只报告成功案例的质量，这会美化不可靠的系统。通过将不可行的输出记为零分，OR-License 衡量的是客户实际会体验到的情况：一个违反约束的方案并非部分可用，而是完全不可用。

结果显示了什么？

摘要中的发现，浓缩为作者的原话如下：

发现细节
测试的模型11 个使用编码 Agent 框架的前沿大语言模型
可行时的质量若干模型在条件目标质量上超越了专家参考
可部署性没有模型能达到专家的 DAQ
最佳主配置Claude Code：严格可行性 88.39%，DAQ 0.87，专家参考为 1
研究链完成率在可评测任务上，各模型的任务均衡完成率为 24% 至 45%

由此得出两点解读。第一，差距在于可靠性，而非峰值能力：模型偶尔能在优化上超越人类专家，但失败频率足够高，以至于在失败记为零分后，平均值仍低于专家。第二，作者发现信息获取不止于澄清。Agent 在方案开发和验证过程中也会寻求客户信息，且部分后期阶段显示出更高的已确认问题解决比例。简而言之，只在开始时向客户提问是不够的。

轨迹分析指出两类主要失败类型：建模错误（对错误的问题建模）和实现错误（对正确的问题建模不当）。作者表示，这些发现为长程 Agent 的持续信息缺口解决、忠实的问题建模以及有证据支撑的自我改进提供了动机。

在我们能够阅读的资料中，没有看到按模型排名的排行榜，所以我们不会对其余十个模型进行排名。具体请查阅论文表格。

这与其他 Agent 基准测试相比如何？

OR-License 属于一套日益增多的、基于真实专业工作构建的评测。我们的 AI 基准测试完全指南 和 如何解读 AI 基准测试 解释了常见的陷阱。这里的独特之处在于：

  • 专家认可的参考答案。 对比基准是客户实际签字认可的解决方案，而非人工合成的标准答案。
  • 可部署性评分。 对不可行的输出计零分，将指标与现实世界的成本挂钩。
  • 信息边界。 模拟器迫使 AI Agent 主动提问，而不是读取一份完美的规格说明。
  • 规模小且异质。 跨 10 个场景的 31 个实例，单个任务内容丰富，但统计上样本薄弱，因此模型之间的单点差异并不可靠。

关于 AI Agent 输出不可靠的更广泛成本，请参阅我们对 验证税 的报道，即 AI 工作所需的额外检查和返工。

如何运行它？

README 列出了环境配置。你需要 Python 3.12、带 Compose 插件的 Docker Engine，以及所测模型的 API 访问权限。requirements 中固定了 Harbor 0.18.0 版本。

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python scripts/download_data.py
docker build -t or-license:open harbor_integration/coding_agent/image

然后复制

.env.example

到

.env

，设置

TESTED_API_BASE

,

TESTED_API_KEY

和

DEEPSEEK_API_KEY

，编辑

llm_config.yaml

中的模型标识符，并运行预检和一个任务：

python run_eval.py --task 3_food3 --model tested --validate-only
python run_eval.py --task 3_food3 --model tested --tag example-run

实用提示：

  • 数据规模。 完整下载约 3.4 GB，其中 0.6 GB 是共享单车观测数据。任务 1 至 19 和 23 无需下载。
  • 求解器许可证。 金融任务 20 至 22 需要单独的环境和许可证：任务 20 需要 MOSEK，任务 21 和 22 需要 COPT。这些需要自行获取。
  • 运行框架。 默认使用 Claude Code；--agent codex 可切换到 Codex。
  • 成本。 README 未给出单次运行的 API 成本，跨模型运行完整测试套件也不会便宜，因此建议先从单个任务开始。

构建优化 Agent 的团队能从中借鉴什么？

你无需运行完整测试套件，也能从其设计中获得启发。以下三个习惯可直接迁移到你自己的 Agent 工作流中。

第一，为可部署性评分，而不仅仅是质量。如果你的 Agent 生成排班、路线或资源分配方案，请编写一个独立的检查器来验证每一条硬性约束，并将失败计为零分，正如 DAQ 所做的那样。一个一半时间表现出色、另一半时间输出无效的模型，在平均成功率图表上看起来不错，但在生产环境中表现糟糕。

第二，将事实调查与求解分开。为 Agent 提供询问业务事实的途径，记录它提出的问题，并标记它在未询问的情况下做出的假设。该论文观察到信息获取会持续到开发和验证阶段，这提示可以在每个阶段设置一轮提问环节，例如：

Before you finalize the model, list every business fact you assumed
rather than confirmed, and ask for each one. After the first solution,
list what in the data or constraints would invalidate it.

第三，在求解器运行之前审查建模 formulation。作者识别出的两类失败——建模错误和实现错误——是需要不同检查手段的不同 bug：让人或第二个模型对照模型阅读问题陈述，以及用已知的小规模实例运行代码进行测试。

局限与开放问题

  • 作者的评估。 我们尚未看到独立的复现结果。
  • 样本量小。 31 个实例数量偏少；只需几个任务，模型排名就可能发生变化。
  • 依赖模拟器。 ORSim 本身是一个由 LLM 支持的系统，因此结果取决于它揭示事实的忠实程度。
  • 测试框架混淆因素。 由于 Agent 是在编码 Agent 框架内运行的，结果混合了模型和框架的影响，因此模型排名在一定程度上也是框架适配度的排名。
  • 来源页面滞后。 项目页面仍将论文链接列为“即将推出”，而代码仓库和 Hugging Face 已经链接了 arXiv 论文。

为什么这很重要

如果你在决定是否将专业级的优化任务交给 Agent 处理，这里有用的数字不是最佳情况下的质量，而是按可部署性调整后的质量。OR-License 表明，前沿 Agent 在其能完成的任务上已经具备与专家竞争的实力，剩下的差距在于可靠性和信息收集的纪律性。对团队而言，这意味着具体的缓解措施：对每个输出进行独立的可行性检查，在工作过程中（而不仅仅是在开始时）进行结构化的客户或利益相关者提问环节，并在花费任何求解器时间之前由人工审查问题建模。
