律所 DMS 连接器设计：FDE 必备技能

FDE Times · 2026-10-26 · 约 5 分钟读完

摘要

文章以 Legora 的 FDE 招聘启事为切入点，说明律所场景下连接器设计比模型选择更关键。核心原则是 DMS（如 iManage、NetDocuments、SharePoint）始终是记录系统，访问权限由 DMS 和道德墙决定。作者建议采用共享接口加各 DMS 适配器的架构，每次调用携带用户身份，并用六格权限测试矩阵验证道德墙，防止数据泄露。

要点

  • Legora 的 FDE 岗位要求熟悉 iManage 等文档系统、SSO 和 webhook。
  • 原始 DMS 始终是记录系统，权限由 DMS 和道德墙决定。
  • 架构上应共享接口加适配器，客户差异不进接口。
  • 用三人两案的六格矩阵测试道德墙，权限变更后重跑。
  • 常见错误包括复制 DMS 数据和跳过身份映射。

Legora 的 FDE 招聘启事表明，iManage 等文档系统仍是记录系统，构建什么由每个案件的访问权限决定。

要点速览

  • Legora 的 FDE 招聘启事要求熟悉 iManage、SharePoint 或 NetDocuments，SSO（SAML、OIDC），REST 和 webhook，并明确要求编写可复用的连接器。
  • 第一条原则：原始 DMS 始终是记录系统。每个人能检索到哪些文档，由 DMS 权限和律所的道德墙决定。
  • 连接方式可能从 API 转向 MCP，但权限控制和共享接口必须保持不变。

一家律所希望合伙人能查询存放在 iManage 中的案件文档。在第一次技术会议上，模型几乎没人提。IT 负责人只问了一个问题：如果律师 A 与案件 X 之间设有隔离墙，你们的系统会不会给 A 看到案件 X 的哪怕一页内容？

这份工作就从这个问题开始。Legora 对其前线部署工程师（FDE）岗位的描述是：介于产品工程和客户成功之间。工程师在部署期间及部署之后与企业客户并肩工作，编写生产环境代码，把 Legora 的平台接入客户的系统。

招聘启事列明了所需知识：iManage、SharePoint 或 NetDocuments 等文档管理系统，基于 SAML 和 OIDC 的 SSO，以及 REST 风格的 API 和 webhook。

启事还规定了一项具体职责：构建并维护连接器、自动化脚本和可复用工具，让后续部署更快完成。

这项技能并非 Legora 独有。任何向敏感数据行业销售软件的公司都用得上。

文档归谁所有？

2026 年 10 月，Legora 推出集成生态时强调了一条原则：律师可以在 Legora 中浏览、搜索和处理案件文档，但底层平台始终是记录系统。这句话读起来像是写给市场团队的。实际上，它是连接器最重要的设计要求。

这条原则带来两个结果。第一，DMS 保存每份文档的正式副本及其版本、元数据和编辑历史，因此连接器不能另建一份逐渐偏离原件的副本。第二，访问权限由 DMS 决定，而不是由你决定。

据 LawNext 报道，在 iManage 集成中，每个用户能检索到什么由 iManage 权限决定。Artificial Lawyer 也报道称，律所现有的道德墙和安全限制决定了 Legora 可以访问哪些内容。

道德墙用于在存在利益冲突时阻止律师接触某个案卷。文档穿透这道墙是严重事故，远不止一个普通 bug。

一个接口，多个适配器

招聘启事为什么强调“可复用”？这家律所用 iManage，下一家用 NetDocuments，再下一家所有东西都放在 SharePoint 里。如果每次都从零开始，经验永远无法积累。

合理的拆分方式是：上层提供一个共享接口供应用调用，下层为每种 DMS 各写一个适配器。下面的示意代码用于说明这种设计，并非 Legora 的代码：

from typing import Protocol

class DMSConnector(Protocol):
    def search(self, user: UserIdentity, query: str,
               matter_id: str | None = None) -> list[DocRef]: ...
    def fetch(self, user: UserIdentity, doc: DocRef) -> DocContent: ...
    def handle_event(self, event: dict) -> None: ...  # webhook：文档移动、权限变更

class IManageAdapter:
    def search(self, user, query, matter_id=None):
        token = self.tokens.for_user(user)  # 使用用户自己的 token，绝不用服务账号
        return self.client.search(query, matter=matter_id, auth=token)

    def fetch(self, user, doc):
        token = self.tokens.for_user(user)
        # 每次读取时 DMS 都会再次检查权限
        return self.client.get_document(doc.id, auth=token)

    def handle_event(self, event):
        if event["type"] in ("permission_changed", "document_moved"):
            # 丢弃按旧权限计算出的结果
            self.cache.invalidate(matter_id=event["matter_id"])

关键细节在于，每个函数都带有

UserIdentity

。每次调用都携带提问者的身份，这个身份来自 SSO（SAML 或 OIDC），适配器再用同一身份调用 DMS。随后 DMS 在搜索和打开时都按此人的权限过滤，你完全不必重新实现访问逻辑。

连接方式发生变化时，这种设计同样有用。据 LawNext 报道，Legora 已通过 API 与 iManage 集成，并计划同时接入 iManage MCP Server。

生态发布公告还提到，iManage 和 NetDocuments 通过模型上下文协议（MCP）接入，用于知识管理和搜索。只要连接方式只存在于适配器中，就可以替换适配器，而不必改动接口或权限测试。

上线前的六格矩阵

道德墙应当像安全那样测试。设想一个场景：两个案件，三名律师。An 负责案件 1001。Binh 负责案件 1002。Chi 是律所的律师，从未参与案件 1001，但因利益冲突被道德墙挡在该案件之外。

用户在案件 1001 中搜索在案件 1002 中搜索
An返回结果空
Binh空返回结果
Chi（与 1001 隔离）空，即使输入准确的文档名空

三个人乘以两个案件，得到六个格子，每个格子都是一条自动化测试。最关键的是 Chi 在案件 1001 的那一格。如果搜索索引是用一个能读取全部内容的服务账号建立的，这一格几乎必然会返回结果，也就意味着泄露。

每次权限变更后都要重跑这个矩阵。在 DMS 中把 An 从案件 1001 移除，把 webhook 事件发给

handle_event

，然后确认 An 的下一次搜索返回空。过期缓存最容易在这里悄无声息地出问题。

在客户现场端到端负责

Legora 把整个技术范围界定工作交给 FDE，从收集需求到设计集成架构。在律所，范围界定会议应当回答四个问题：用的是哪种 DMS，云端还是本地部署？SSO 用 SAML 还是 OIDC？道德墙在哪里配置？权限变更时 DMS 会不会发出 webhook？

之后的工作顺序应当是：接口、适配器、身份映射、测试矩阵、webhook 处理，最后才是问答功能。很多团队反着来，因为问答功能在演示中效果惊艳。但只要发生一次数据泄露，就足以丢掉合同。

最后一步常被跳过：把学到的东西反馈给工程和产品团队。Legora 的招聘启事写明，FDE 要与这两个团队合作，改进集成和共享产品。

如果你发现自己连续为三个客户编写同样的权限组映射，这说明它应该纳入标准连接器。

让连接器无法复用的错误

最常见的错误是把整个 DMS 复制到另一个存储中，以加快搜索。这同时违反了两条原则：副本会偏离记录系统，权限也冻结在复制那一刻。

第二个错误是让客户特有的逻辑渗入共享接口，比如一个名为

matter_code_format_firmB

的字段。所有差异都应放在适配器或配置文件里。

第三个错误是跳过身份映射。SSO 中的邮箱和 DMS 中的用户名并不总是一致。只要映射错一个人，测试矩阵就失去意义。

在简历上展示这项技能

阅读 FDE 招聘启事时，留意“可复用连接器”、具体的 DMS 产品名、SAML/OIDC 和 webhook 等字眼。它们表明这份工作偏重集成，而不是演示。

简历上不要只写“集成了 SharePoint”。要写清楚你构建了一个连接器，在若干次部署中复用，用明确数量的测试用例测试权限，并且没有一份文档穿透道德墙。招聘方读到这一行，就会知道你真正回答过 IT 负责人的那个问题。

模型会不断变化，连接方式也会变，从 REST 到 MCP，再到下一个标准。但“谁可以看什么”这个问题不会变。用测试而不是承诺来回答它的 FDE，才能赢得客户信任。
