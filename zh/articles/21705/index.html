公用事业中的 GIS 与 SCADA：FDE 需要了解的内容

原标题：GIS vs SCADA at Utilities: What FDEs Need to Know

FDE Times · 2026-11-05 · 约 6 分钟读完

摘要

这篇文章面向在电力公司工作的前沿部署工程师，解释 GIS 与 SCADA 数据不一致往往是正常现象：GIS 记录电网的设计状态，SCADA 记录实时运行状态。作者引用 PNNL 2016 年报告指出运营系统集成是最大挑战，并介绍 CIM（IEC 61970/61968）如何划分运营与资产数据的归属。文章给出一个 40 开关馈线的对账示例：先建 ID 对照表，再区分匹配、缺链、计划操作与需现场核查四类，最后才构建对象模型和仪表盘，并提醒避免把 GIS 或 SCADA 单方面当作唯一事实来源。

要点

  • GIS 存设计状态，SCADA 存实时状态，两者不一致常属正常。
  • PNNL 报告认为运营系统集成是电力公司最大挑战。
  • CIM 的 IEC 61970/61968 划分提示数据归属哪个团队。
  • 先对账分类差异，再建对象模型，最后才做仪表盘。
  • 用电力行业术语提问能更快赢得工程师信任。

GIS 记录电网的设计运行方式，SCADA 记录电网当前的实际运行方式；了解两者的差异可以避免花数周时间去修复本来就没有问题的地方。

简要概述

  • 在电力公司，GIS 存储的是设计中的电网，SCADA 存储的是运行中的电网，因此看到两者不一致是常见现象
  • CIM（IEC 61970/61968）为电网对象提供了统一的词汇，其范围划分方式也暗示了哪些数据属于哪个团队
  • 先核对并分类不一致之处，再构建对象模型，最后才做仪表盘

在电力公司工作的第一周，你会拿到三个文件：一份 GIS 导出数据、一份 SCADA 测点列表和一份资产登记表。任务听起来很简单：把三个文件关联起来，画出一条馈线。到了下午，你会发现一个开关在一个文件里是断开状态，在另一个文件里却是闭合状态，而会议室里没有人对此感到惊讶。

没有人感到惊讶，因为这不是随机错误，而是这个行业的结构性特征。PNNL 于 2016 年发布的一份关于 ADMS 的报告得出结论：电力公司 GIS 中的数据模型往往不完整、不准确，或两者兼有，并将运营系统之间的集成确定为部署中的最大挑战。

你可能带着“只要有 schema，我就能做关联”的想法来到电力公司，然后花两周时间去修复那些本来就没有问题的地方。另一种做法是提前学习一些行业概念，这样从第一次需求调研会开始，你就能提出正确的问题。

GIS 和 SCADA 描述的并不是同一种状态

GE Vernova 对这种分工有一个清晰的描述。一边是电网设计和制图团队：他们在自己的独立环境中使用 GIS 来规划和更新电网的正常状态。另一边是控制室操作员：他们在另一个独立环境中监控实时状态。

因此，GIS 回答的是“电网设计上应如何运行”，而 SCADA 回答的是“电网现在实际如何运行”。当操作员为检修或转移负荷而隔离某一段线路时，两者不一致是正常的。其他的不一致才真正是错误：GIS 没有及时更新，或者 ID 映射表有误。

1Spatial 描述了电力行业的一个典型案例：GIS 显示某个阀门是关闭的，而 SCADA 报告它是打开的。在电力公司，把“阀门”换成“开关”，就正是那个下午遇到的情况。

在编写 schema 之前，CIM 先给你一套词汇

电力行业早就有了通用语言。CIM 在 IEC 61970-301 标准下，是一个描述电力企业主要对象的抽象信息模型。它将电力系统资源表示为带有属性的对象类，使不同厂商独立开发的应用程序仍然能够相互集成。

对于 FDE 来说，CIM 最有用的部分在于它如何划分范围。根据 CIM Users Group 的说法，IEC 61970 涵盖电力系统建模和数据交换，包括 EMS、拓扑、导线和 SCADA。IEC 61968 则处理与配电网相关的模型：DMS、资产、作业、GIS、计量以及应用程序之间的消息传递。

你的客户可能不会完全按照 CIM 来实施，但这个划分仍然值得当作一张地图来使用。它为你提供了一份在与电力工程师交流时可以使用的名词清单。

它还提示了哪些数据可能属于哪个团队：运行团队，还是资产与地图团队。当一个数据字段看起来不合常理时，弄清楚谁拥有它就等于解决了一半的问题。

示例：核对一条馈线

想象一条有 40 个开关的馈线。GIS 使用诸如

SW-0412

这样的资产 ID，并带有一个表示常态的额外字段。SCADA 使用诸如

F07_SW412_POS

这样的标签名，其中值为 1 表示合闸。两个系统都不持有对方的键，因此第一项工作就是建立一张将资产 ID 映射到标签的对照表。

接下来，把每个设备整合为一个单一对象，其中两种状态分开保存，甚至落实到字段名称上：

from dataclasses import dataclass

@dataclass
class Switch:
    asset_id: str               # key from GIS
    scada_tag: str | None       # taken from the crosswalk table
    normal_open: bool           # designed state (GIS)
    measured_open: bool | None  # measured state (SCADA)

def classify(sw: Switch, switching_orders: set[str]) -> str:
    if sw.scada_tag is None or sw.measured_open is None:
        return "missing_link"
    if sw.normal_open == sw.measured_open:
        return "match"
    if sw.asset_id in switching_orders:
        return "intentional_switching"
    return "needs_field_check"

该

switching_orders

参数是近期有倒闸操作单的设备列表，你必须向控制室申请获取。没有它，每一次正常的负荷转供都会被计为错误。

假设运行结果为：31 个设备匹配成功，4 个缺失关联，3 个因计划内倒闸操作而不匹配，2 个需要现场核查。你不必报告“GIS 有 9 处错误”，而是把三份清单分别交给三个不同的人。

四个缺失关联是你和集成团队的活儿。最后两个属于地图团队，可能还得有人亲自去电线杆现场。

对象模型先于仪表盘

Palantir 曾描述过一个欧洲公用事业公司的案例研究。该公司的地理资产系统和电网系统相互独立，因此公司无法获得完整、最新的电网状态图景。解决方案是将电网拓扑建模为 Ontology 对象，并为每个电网元素创建对应的视图。

这个经验并不依赖于特定工具。设备、线路和连接关系必须首先成为显式的对象。仪表盘或预测模型都是之后的事。如果你在一个尚未核对一致的连接之上构建图表，那不过是把现有的不匹配画得更漂亮而已。

因此，在客户现场的推进顺序相当清晰：

  • 将每个系统归入 61970 或 61968 的范围，并写下其负责人。
  • 询问每个状态字段是“常态”还是“实测值”。
  • 建立资产 ID 与 SCADA 标签之间的 ID 对照表。
  • 运行分类步骤，然后把每份不匹配清单交给对应的团队。
  • 只有在地图团队和控制室都确认之后，才锁定对象模型。

常见的陷阱

最常见的陷阱是把 GIS 当作唯一事实来源并用 SCADA 状态覆盖它，或者反过来。这两个领域描述的是不同的东西，所以两者都要保留。第二个陷阱是假设一台设备只有一个 ID，而实际上每个孤立的系统通常都按自己的方式分配编码。

第三个陷阱更难察觉：对电力工程师使用通用的软件术语。问“这条记录是否过时了？”，他们会难以回答。问“这是正常状态还是量测状态？”，他们能立刻回答。使用他们的词汇是赢得他们信任的最快方式。

在职业发展方面，阅读能源领域的 FDE 职位描述时，可以把本文中的术语（CIM、IEC 61968/61970、ADMS、GIS、SCADA）当作一份清单。在简历上，不要只写“数据集成”。

要具体说明你在哪些系统之间核对过拓扑，以及你如何对不匹配之处进行分类。PNNL 报告指出运营系统之间的集成是最大的挑战，所以这类经验值得放在简历最显眼的位置。

在电力公司，理解为什么两个文件不匹配的人，比能够把它们连接起来的人更有价值。
