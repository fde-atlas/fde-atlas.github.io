多客户部署配置与密钥管理：ConfigMap、Secret、Vault

FDE Times · 2026-11-14 · 约 5 分钟读完

摘要

这篇技能指南面向 FDE，讲解一套代码服务多客户时如何分离代码、配置与密钥。文章以 12-factor 原则为基础，指出按客户名写 if 分支是配置失控的开端，并给出 Kubernetes ConfigMap 与 Secret 的使用边界：ConfigMap 不保密，Secret 默认在 etcd 中也未加密，需额外加固。密钥管理方面强调有效期与可吊销性，介绍 Vault 租约机制——吊销即失效，可应对合同终止或疑似泄露。文末列出四个常见现场配置错误，并演练了客户流失且密钥可能泄露时的逐层响应流程。

要点

  • 代码应随时可开源而不泄露凭证或客户信息。
  • ConfigMap 不保密，Kubernetes Secret 默认在 etcd 中也未加密。
  • Vault 租约吊销后密钥立即失效，便于终止合作或应对泄露。
  • 决定数据流向的变量必须显式声明，不得设默认值。
  • 各客户应使用独立租户隔离与独立 CI 服务账号。

一套代码服务多个客户时，配置与密钥要分开存放，合同终止或泄露当天，密钥必须能吊销。

要点速览

  • 所有客户的代码完全相同，只有配置不同。出现按客户名判断的 if 分支，说明两者已经混在一起。
  • ConfigMap 不能保密；默认情况下，Kubernetes Secret 在 etcd 中也是未加密存储的。
  • 密钥要有有效期，并且可以吊销：租约一旦吊销，密钥立即失效，无论是结束客户合作还是怀疑泄露。

你的方案在第一个客户那里运行顺利。接着第二个客户签约，为了赶工期，你加了一行

if customer == "B":

来切换 CRM 地址。到第三个客户时，仓库里多了

config_a.yaml

和

config_b.yaml

两个文件，还有某人晚上 11 点提交的一个 token。

没人想故意把代码库搞乱。它是在一次次仓促交付中慢慢变坏的。对前线部署工程师（FDE）来说，这是日常，而不是极端情况：同一个产品要部署到不同的基础设施、不同的数据和不同的安全规范之下。

这里需要的能力，是分清代码、配置和密钥，再把它们各自放到该放的位置。做对了，第十个客户只需要一组新的值，而不是又一条代码分支。

代码不随客户变化，配置才会

Twelve-Factor App 的配置原则基于一个观察：不同部署之间，配置差异很大，代码却不变。对 FDE 而言，“一次部署”就是一个客户。每个客户都是一次部署，各有自己的 API 地址、模型名称、批大小和访问密钥。

要检验分离是否彻底，12-factor 给出了一个测试：这个代码库能否随时开源，而不暴露任何一个凭证？对 FDE 来说，这个测试还要加一条：仓库也不能透露客户名称、内部 URL，或客户的系统是如何组织的。

12-factor 选择用环境变量保存配置。对 FDE 来说，实际理由很简单：当你站在客户机房里，被允许改参数却不能重新构建镜像时，环境变量可以当场修改，不用动一行代码。

别让“环境”数量随客户数翻倍

很多人习惯按环境命名配置集：

dev

、

staging

、

prod

。有了三个客户，列表就变成

prod-a

、

staging-a

、

prod-b

，用不了多久，就没人记得这些文件之间有什么区别。

最后一列最重要。前三行中与客户相关的值不能放在仓库里；代码中只能保留共享且无害的默认值，比如批大小。

前三个值泄露，损失主要是客户系统的信息。第四个值泄露，就是一起涉及客户的安全事件，还可能构成违约。

示例：缺少变量就立即停止的加载器

最危险的配置错误，往往来自一个没人注意到的默认值。应用正常启动，三天后却调用了另一个客户的 CRM。下面的加载器反其道而行：缺少必需变量就立即停止，并且从不打印密钥。

# config.py：从环境变量读取配置，缺少任何一项就立即停止
import os
from dataclasses import dataclass, field

class ConfigError(RuntimeError):
    pass

def _required(name: str) -> str:
    value = os.environ.get(name)
    if not value:
        raise ConfigError(f"缺少必需的环境变量：{name}")
    return value

@dataclass(frozen=True)
class Settings:
    tenant_id: str
    crm_base_url: str
    batch_size: int
    crm_api_token: str = field(repr=False)  # 密钥：绝不出现在日志中

def load() -> Settings:
    return Settings(
        tenant_id=_required("TENANT_ID"),
        crm_base_url=_required("CRM_BASE_URL"),
        batch_size=int(os.environ.get("BATCH_SIZE", "100")),  # 共享默认值，不属于任何客户
        crm_api_token=_required("CRM_API_TOKEN"),
    )

有三点值得注意。代码里没有出现任何客户名称。代码中的默认值只允许用于

BATCH_SIZE

这类无害参数：100 是安全的共享值，不是某个客户的专属数字；需要其他值的客户自行设置变量，就像客户 B 设置为 20。

凡是决定数据流向的变量，都必须显式声明，不设默认值。而

repr=False

保证调试时随手一个

print(settings)

也不会把 token 泄露到客户的日志里。

在 Kubernetes 上：配置用 ConfigMap，密钥用 Secret

如果客户使用 Kubernetes，ConfigMap 自然是前三个变量的归宿，它本就用于存放随环境变化的非敏感设置。一个镜像，多个客户集群。

envFrom:
  - configMapRef:
      name: app-config-customer-b
  - secretRef:
      name: app-secrets-customer-b

陷阱在第二项。Kubernetes 文档明确指出，ConfigMap 不提供任何保密或加密能力，敏感数据必须放进 Secret，这样密码和 token 才不会出现在应用代码里。但即便是 Secret，默认也以未加密形式存储在 etcd 中，任何能访问 API 或 etcd 的人都能读取。

因此，Secret 只有在额外加固后才安全。在与客户基础设施团队的启动会上，直接问清楚：这个集群是否启用了 Secret 加密？目前谁对这个命名空间里的 Secret 有读取权限？

密钥需要有效期

永不过期的 token 是一颗潜伏的雷，只等泄露那天引爆。OWASP 建议定期轮换密钥，让被盗凭证只能在很短时间内使用，并把密钥的存储、分发、审计和轮换集中到一处管理。

Vault 通过租约（lease）把这一思路更进一步。租约被吊销后，密钥立即失效，也无法再续期。

这彻底改变了 FDE 面对的两种最棘手局面：与客户的合同终止时，吊销该客户的租约即可，不用逐台机器排查；怀疑泄露时，先吊销，再调查。

客户之间的边界也必须同样清晰。在多租户系统中，每个租户的密钥都需要严格隔离，例如每个租户使用独立的存储，且不在客户之间共用同一把加密密钥，这样一个客户出事，不会波及其他客户。

在 CI/CD 流水线中，这意味着每个客户使用独立的服务账号：为客户 B 部署的流水线，没有任何理由能读取客户 A 的 token。

现场让配置出错的四个错误

最常见的是让客户名称混进代码，哪怕只是一条“临时”

if

分支。其次是给决定数据流向的变量设默认值。再次是把 token 放进 ConfigMap，理由是“反正在客户集群里”。

最后一个更隐蔽：你的开发机跑 SQLite，客户跑 Postgres，配置直到到了现场才出问题。12-factor 建议让开发环境与生产环境尽可能一致，让差异只存在于配置中。在自己机器上，使用与客户同类的数据库和同类的队列。

客户 B 要走了，token 可能已泄露，怎么办？

这个问题值得在客户提出之前就演练一遍，也是 FDE 面试前很好的练习场景。OWASP 把快速响应已暴露的密钥列为重点关注事项之一。

好的回答会逐层处理：吊销 B 的租约，确认 B 的 CI 服务账号碰不到其他任何客户的密钥，为仍在运行的部分签发新密钥，把所有操作记入审计日志，并且完全不改代码。

如果你在真实项目中做过这件事，就把它写进简历，用一句具体的话：客户数量、密钥如何隔离、吊销花了多长时间。

到交付第十个客户时，你的工作只是填一份变量清单、创建一个新租约。代码库始终干净到随时可以开源。
