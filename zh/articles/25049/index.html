PrivateLink 和 VPN 区别：FDE 网络选型指南

FDE Times · 2026-10-26 · 约 6 分钟读完

摘要

这篇指南面向 FDE，讲解在客户部署中如何在 PrivateLink 与站点到站点 VPN 之间做网络选型。核心判断标准是调用方向、数据位置和 IP 段是否重叠：客户调用你的服务时优先 PrivateLink，即使双方都用 10.0.0.0/16 也不冲突；需要双向打通网络时选 VPN，但要承担客户网络团队排期、地址不重叠要求和每条隧道 1.25 Gbps 的带宽限制。文章还列举了常见错误，如误以为 PrivateLink 是双向的、忘记终端节点服务默认不开放，并给出摸底会议应问的五个问题。

要点

  • 选型取决于三个问题：谁调用谁、数据在哪、IP 段是否重叠。
  • IP 段重叠时 PrivateLink 可用，接口终端节点占用客户子网地址，无路由冲突。
  • VPN 需客户配置网关设备并发起 IKE 协商，上线日期受其网络团队排期制约。
  • 标准 VPN 隧道带宽 1.25 Gbps，5 Gbps 大带宽需 Transit Gateway 或 Cloud WAN。
  • 常见错误：把 PrivateLink 当双向管道，或忘记终端节点服务默认拒绝所有连接。

VPN 打通两张网络，要求地址段不重叠；PrivateLink 只把一个服务放进客户网络。

要点速览

  • 决定选型的是三个问题：谁要调用谁、数据在哪里、双方的 IP 段是否重叠。
  • 客户调用你的服务时适合用 PrivateLink，即使双方用的是同一个 IP 段也没问题。需要打通两张网络、且客户有网络团队负责配置设备时，适合用 VPN。
  • 最常见的错误：以为 PrivateLink 是双向的；忘了终端节点服务默认不允许任何人连接。

第二次启动会上，客户的安全负责人说得很直白：他们的系统没有公网 IP，以后也不会有。你的服务跑在自家公司的 VPC 里，数据却在客户的网络中。直到这时你才发现，双方用的都是 10.0.0.0/16。

此时选哪种连接方式，决定了后面的一切：谁要配置什么，哪个团队要腾出排期，要不要有人改动网络地址规划。选择基本落在两个方案上：PrivateLink（Azure 上叫 Private Link）和站点到站点 VPN。

两者都能让流量避开公共互联网，但解决的是不同的问题。前线部署工程师（FDE）应该在客户网络团队开口之前，就想好该提哪一个。

暴露一个服务，还是打通两张网络？

最好记的说法是：PrivateLink 把一个服务带进使用方的网络，VPN 则把两张网络连在一起。

根据 AWS 文档，PrivateLink 让 VPC 像访问自身内部服务一样访问某个服务，不需要互联网网关、NAT、公网 IP、Direct Connect 或 Site-to-Site VPN。

连接由使用方发起，提供方决定接受或拒绝。VPC 终端节点与终端节点服务之间的流量始终留在 AWS 网络内，不会进入公共互联网。

站点到站点 VPN 则完全是另一回事。它是一条 IPsec 连接，每条连接有两条加密隧道，可以并行使用以提高可用性。由于两张网络会连在一起，AWS 建议在把多个 VPC 接入同一个本地网络时，使用互不重叠的 CIDR 地址段。

实例：两个都是 10.0.0.0/16 的 VPC

设想一下：你在一家提供模型推理 API 的公司做 FDE。客户的应用跑在 AWS 上，需要调用你的 API。

两个 VPC 都是 10.0.0.0/16。无论是 AWS 的站点到站点 VPN，还是 Azure 的 VNet 对等互连，云厂商都建议或要求地址段不重叠。所以通常得有一方重新规划网络地址，这很容易膨胀成一个独立项目，远远超出你这次部署的范围。

PrivateLink 绕开了这个问题。AWS 明确表示，VPC 的 IP 段重叠时，PrivateLink 是合适的方案；AWS 网络博客也提到，可以在地址重叠的 VPC 之间暴露终端节点，而不必改动底层地址规划。

原因在于，接口终端节点位于客户自己的子网里，占用的是客户地址段中的 IP，因此不会产生路由冲突。

实际操作的顺序如下。你作为提供方，在服务前面放一个负载均衡器，再基于这个负载均衡器创建终端节点服务。

终端节点服务默认不对任何人开放，所以你必须给客户的具体 AWS 主体授权，通常就是对方的 AWS 账号。客户在自己的子网中创建接口终端节点，然后你接受连接请求。

最后一步由客户完成，也是安全团队最喜欢的一步。终端节点在客户的子网里，他们可以用自己的安全组控制访问。比如，只允许自家的应用服务器调用终端节点的 443 端口。他们既不必向外开放任何东西，也不必信任一条通往你 VPC 的宽泛网络路由。

需要反过来调用客户网络时

现在把方向反过来。你的 Agent 要读取客户本地数据中心里的一个数据库。PrivateLink 采用“使用方发起连接”的模式，不会自动给你一条反向通路。有了终端节点，并不意味着两张网络能互通。

办法还是有的。AWS 表示，提供方可以把服务运行在本地服务器上，资源终端节点也支持访问本地环境中的资源，所以客户的基础设施不在 AWS 上时，PrivateLink 仍值得考虑。

但如果真正的问题是“两张网络需要互通”，站点到站点 VPN 通常是更自然的答案。它的代价要一开始就讲清楚。

第一个代价是人。客户必须配置自己的 VPN 设备（客户网关设备），默认情况下也必须由这台设备产生流量、发起 IKE 协商来建立隧道。因此，你的上线日期取决于客户网络团队的排期。

别把这里的“发起”和 PrivateLink 的“发起连接”混为一谈。IKE 只是建立隧道的那一步。

其次是地址。前面提到的 10.0.0.0/16 重叠问题，在这里会变成真正的麻烦，因为 AWS 建议地址段不重叠。

最后是带宽。标准隧道提供 1.25 Gbps。最高 5 Gbps 的大带宽隧道只能通过 Transit Gateway 或 Cloud WAN 使用。如果你的 Agent 每晚要同步大量数据，提前把这个数算清楚。

换到 Azure，逻辑不变

如果客户用的是 Azure，名词变了，思路没变。Microsoft 表示，使用 Azure Private Link 时，虚拟网络与服务之间的流量走 Microsoft 骨干网，服务无需暴露到公共互联网。提供方可以创建 Private Link 服务提供给客户。

有一个细节值得和安全团队提一下：专用终结点映射的是某个资源的具体实例，而不是整个服务，这降低了数据外泄的风险。

本地网络仍可以通过 ExpressRoute 或 VPN 隧道接入。Microsoft 还把 Private Link 定位为 VNet 对等互连的替代方案，而后者要求地址空间不重叠。这和 AWS 上的 IP 重叠问题如出一辙。

动手试试：摸底会议上的五个问题

写第一行 Terraform 之前，先拿到五个答案。一：谁要调用谁？是客户调用你，还是你调用客户？二：数据在哪里？AWS、Azure 还是本地？三：每张网络的 CIDR 地址段是什么，是否重叠？

四：每小时的峰值数据量是多少，会不会超过每条隧道 1.25 Gbps？五：客户那边谁负责网络设备，安排配置需要多长时间？如果第一题的答案是“客户调用你”，第三题的答案是“重叠”，那你几乎肯定会提议用 PrivateLink。

让部署卡住的错误

最常见的错误是把 PrivateLink 当成双向管道。它的设计是使用方调用提供方。如果你的 Agent 需要反向发起调用，那条通路要单独设计。

几乎同样常见的，是忘了终端节点服务默认不对任何人开放。客户创建终端节点后报错，双方折腾一下午，才发现没人给对方的主体授过权。

VPN 方面，有的团队只配了一条隧道，可每条连接本来都带两条，结果那条隧道一断就措手不及。还有的团队在没确认客户网络团队能否发起 IKE 之前，就先承诺了上线日期。

这项技能在你履历中的位置

看 FDE 岗位描述时，留意“customer VPC”“private networking”“on-prem deployment”这类说法。出现了，这个岗位很可能就需要能做这类工作的人。

简历上不要写“熟悉 AWS 网络”，而是用一句话写出约束和结果，例如：使用 PrivateLink 将服务交付到 IP 段重叠的客户 VPC 中，无需重新规划网络地址。

面试时别停留在概念定义上。按顺序讲清楚你问了什么、选了什么、为什么没选另一个方案。客户很少记得你用了哪种协议，他们记得的是，自己的安全团队没有多向互联网开放一个端口。
