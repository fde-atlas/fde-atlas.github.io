OpenCodeReview 评测：阿里巴巴开源 AI 代码审查工具的亮点，以及我们实测中的发现

原标题：OpenCodeReview Review: What Alibaba's Open-Source AI Code Reviewer Gets Right, and What We Found Testing It

FDE Interviews · 2026-10-21 · 约 14 分钟读完

摘要

本文实测了阿里巴巴开源的 AI 代码评审工具 OpenCodeReview（OCR）。其核心贡献是架构设计：文件筛选、规则匹配和评论定位均由确定性代码完成，模型只负责判断代码是否有问题。在其自建基准上，OCR 每个 PR 约发 3-5 条评论，token 消耗约为 Claude Code 的九分之一，但每个同模型对比中召回率都更低。作者还发现 1.13.2 版的 Java、Kotlin、C++ 规则文件缺少安全检查。结论是：适合评审注意力稀缺的团队，不适合安全评审。

要点

  • OCR 用代码处理文件筛选、规则与定位，模型只做判断。
  • 同模型下 token 约为 Claude Code 的九分之一，评论更少。
  • 所有同模型对比中 OCR 召回率更低，发现的真实 bug 更少。
  • Java、Kotlin、C++ 规则文件无安全检查，需自补规则。
  • 基准由阿里参与共建，尚无独立复现。

OpenCodeReview 是阿里巴巴开源的 AI 代码审查工具，它真正的贡献是一套架构，而不是某个模型或某个分数。它在普通代码中决定哪些文件需要审查、每条规则适用于哪些文件、每条评论落在哪里。它只把判断题交给语言模型：这段代码是否有问题？ 在它自己的基准测试上，这使它比用同一模型把 Claude Code 当作审查工具运行要安静得多，成本约低九倍，代价是发现的真实 bug 更少。我们阅读了 Go 源码，重新核算了基准测试数据，并在一个测试仓库上运行了该工具。我们的结论是：采纳这套设计，锁定版本和模型，为 Java 自行编写安全规则，并且不要把基准测试解读为“发现更多 bug”。它发现的 bug 更少，但浪费审查者时间也少得多——对大多数团队来说，这是正确的取舍。

一分钟了解 OpenCodeReview

OCR（该命令行工具是

ocr

）在以 Apache-2.0 许可证发布之前，曾是阿里巴巴内部的 AI 审查助手。README 称它在两年内服务了数万名开发者；我们无法核实这一点，因此请将其视为该公司的说法。截至 2026 年 10 月 21 日，该仓库在 GitHub 上约有 47,800 颗星，npm 包版本为 1.13.2。

它做四件事：

  • Diff 审查（ocr review）：针对工作区变更、分支范围或单个提交，支持可恢复的会话。
  • 全文件扫描（ocr scan）：对没有 diff 的目录进行扫描，用于审计从未被审查过的代码。
  • 委托模式（ocr delegate）：OCR 负责文件选择和规则解析，而你自己使用的编码 agent（Claude Code、Codex、Cursor、Kimi Code、OpenCode）用它的模型进行审查。无需 OCR API 密钥。
  • CI 集成：支持 GitHub Actions、GitLab CI、GitFlic 和 Gerrit，带有 OpenTelemetry 钩子和用于审查会话的本地查看器。

它需要 Git 2.41 或更高版本，以及任何兼容 OpenAI 或 Anthropic 的端点。

工作原理：代码负责记账，模型负责判断

README 中对用作审查者的通用 Agent 的诊断，与我们在客户部署中观察到的情况一致。面对大型变更集时，它们会跳过文件，行号偏离目标，而且质量会随着提示词的微小改动而大幅波动。OCR 的应对方案是：把每一个不容出错的步骤都从模型手中拿走。

来源：OpenCodeReview 实现。该图将确定性代码与模型调用分离开来。

源码中有四个细节值得借鉴到你构建的任何 Agent 中。

选择是一个纯函数。

selectFiles

它应用路径和扩展名过滤规则，跳过删除操作，并强制执行单文件 token 上限。它不使用 LLM，也没有 Git 访问权限，因此

--preview

命令和真实运行会计算出相同的结果。代码中的一条注释提到，这两者曾经出现过偏差。如果你的 Agent 的试运行和真实运行可能得出不同结果，那你就没有真正的试运行。

分组以低成本方式使用模型。 README 将打包称为“确定性工程”，但

grouping.go

它让 LLM 仅使用元数据（状态、路径以及新增和删除的行数，不含 diff 内容）对文件进行分组，并返回整数索引而非路径，以节省输出 token。变更集少于四个文件时跳过该调用：如果总变更量低于 200 行，则一起审查；否则每个子 Agent 审查一个文件。任何错误都会回退为每组一个文件。这是一个合理的设计。它并非完全确定性的，当你调试为什么两个文件被分开审查时，这个区别很重要。

位置来自引用，绝不来自模型。 每条评论都附带其所指的现有代码，OCR 会在 diff 中查找该文本以计算行号。只有当文本匹配失败时，才会进行第二次模型调用以提取确切的代码片段，然后再次运行匹配。这是该代码库中最具可迁移性的一个想法：永远不要让语言模型给出行号。让它给出文字，由代码来计数。

过滤器被告知哪种错误更严重。 审查过滤器的提示词指出，保留一条错误的评论只会让审查者多花几秒钟，而删掉一条正确的评论则会毁掉一个永远无人能看到的发现。它只能删除 diff 能证明是错误的评论，而“我无法验证这一点”则意味着保留。这种用平实语言写出的不对称性，正是该过滤器能在不严重牺牲召回率的情况下提升精确率的原因。

做完除法之后，有五点值得注意。

最抢眼的数字是噪音，而不是发现的 bug 数量。 在 Claude 4.6 Opus 上，Claude Code 在 1,505 个问题中找到了 435 个，OCR 找到了 301 个。在全部五组同模型对比中，Claude Code 的召回率都更高。OCR 赢的是数量：每个 PR 大约 3 条未匹配评论，对比 28 条。一个每条 PR 要面对三十条评论的评审者，到周三就不看了。

“大约 1/9 的 token”属实。 汇总五组同模型对比，Claude Code 使用的 token 是 OCR 的 9.0 倍（按模型不同，比率在 5.4 到 14.7 之间）。

对所有人来说，绝对质量都很低。 表中最好的 F1 也只有 25.1%。即使是最安静（评论最少）的配置，也只有大约三分之一的评论对应一个已验证的问题。2026 年末的 AI 评审只是第一道筛查，不是评审者。

这个基准测试并不独立。 AACR-Bench（arXiv 2601.19494）由南京大学和阿里巴巴共同撰写。其候选问题由“一个内部评审系统”和 Claude Code 生成，再由 80 名工程师验证，1,505 个问题中有 1,114 个来自这种模型加专家的增强流程。一条评论是否算正确，取决于一个 LLM 匹配器（Qwen3-235B）是否判定它与某个行号重叠的已验证问题等价。这是一个合理的方法，也意味着精确率是一个下限：一个流程中没人发现的真 bug 会被记为误报。这也意味着风格与内部系统相似的评审者拥有主场优势。我们希望看到同样的表格出现在一个阿里巴巴没有参与构建的基准上。

更新的模型得分更差。 Claude 4.8 Opus 在 OCR 1.3.1 下的 F1 为 17.9，而 4.6 为 25.1，召回率几乎减半。这一行还混杂了不同版本：Qwen3.8-Max 运行在 OCR 1.8.7 上，而其他模型运行在 1.3.1 上。一个评审框架是针对它所构建模型的习惯调校的。请把模型升级当作对评审系统的一次变更，并先在自己的样本上重新运行。

我们运行它时的发现

我们下载了 1.13.2 Linux 版本，对照公布的 SHA-256 进行了校验，并构建了一个小型仓库，其中包含一个真实的功能提交：一个 Java 服务变更，增加了库存检查和一个字符串拼接的 SQL 查询；一条没有对应中文版本的英文消息；一个新增的

lodash

innerHTML

pull_request_target

这个 Java 问题具有普遍性。Python、PHP 和 Rust 的规则文件都告诉模型标记用字符串拼接的 SQL，MyBatis mapper XML 和默认规则也直接点名 SQL 注入。Java 文件得到的却是

java.md

，它完全没有安全部分，Kotlin 和 C++ 文件也没有（C 文件至少覆盖了缓冲区溢出）。默认规则虽然会询问 SQL 注入和 XSS，但只适用于没有自己规则文件的文件类型，因此永远不会作用于 Java 文件。模型仍可能凭自身判断标记出注入问题；但规则表所保证的是，它不会被提示去查找。仓库描述承诺的规则集包含“NPE、线程安全、XSS、SQL 注入”，这在整个规则集层面属实，但对 Java 文件并不成立。

这是 OCR 设计的代价，应当公允地指出。聚焦模型注意力的规则，同时也决定了它不去看什么。 精确度和覆盖率来自同一份预算，你应该知道你的工具把预算花在了哪里。

适用场景与不适用场景

适合的场景。 拉取请求很多而资深评审者很少的团队，瓶颈在于注意力。希望在多种语言上用统一评审策略、并支持按路径设置规则的平台团队。Agentic 编码环境中 Agent 开启大量 PR、需要人工分诊的场景；我们在 agentic software factory 指南中论证过，评审会成为约束，而一个安静的初筛评审者在这里很有帮助。对于前沿部署工程师，

ocr scan

是快速熟悉陌生客户代码库的方法：对你即将改动的模块运行它，把发现的问题当作风险分布地图来阅读。

不适合的场景。 安全评审。一旦漏掉缺陷代价高昂的受监管变更。每周只有少量 PR 的小团队，通用 Agent 额外的召回几乎不占用注意力。以及任何没人维护规则文件的场景，因为规则本身就是产品。

我们的落地方式

  • 先影子运行两周。 对每个 PR 运行 OCR，但结果写入日志而非 PR。让评审者抽样标注评论是有用、错误还是琐碎。这样你就得到了自己的精确率，这是唯一重要的数字。
  • 补写你缺失的规则。 对于 Java，在自定义规则文件中加入注入、反序列化、路径遍历和密钥检查。为生成代码、第三方引入代码和快照添加忽略规则。
  • 锁定版本和模型。 更换任一之前，先重跑你标注过的样本。已发布的表格显示，模型升级可能使召回率减半。
  • 在 CI 中保留安全扫描器和依赖扫描器。 OCR 排除 lockfile，也不是 SAST 工具。
  • 衡量被实际处理的评论。 跟踪促成代码修改的评论占比。如果降到约四分之一以下，说明人们已经不看了，这个机器人就成了成本。
  • 按计划搭配一个通用 Agent 扫描高风险目录，以提交 issue 而非评论的方式输出。

成本很容易估算。基准测试中 OCR 每次评审使用 334K 到 743K tokens。按每百万输入 token 3 美元的示意价格，400K tokens 约合每个拉取请求 1.20 美元（缓存之前），一个每月合并 500 个 PR 的团队大约花费 600 美元。而每个 PR 少读 25 条多余评论所节省的评审时间，价值比这高出一个数量级。

即使你从不安装它，也能从中得到的启示

OpenCodeReview 是我们应用于每一个面向客户的 Agent 的规则的最清晰的公开示例：把判断交给模型，把簿记交给代码。 文件覆盖、位置、规则选择和可恢复性都是簿记。它们应该是你可以测试、预览和对比差异的代码。这与 harness engineering 是同一课，也是为什么 coding agents 如何查找代码与你选择哪个模型同样重要的原因。

如果你面试应用 AI 或 FDE 职位，请准备好在系统设计题中遇到类似这样的问题：“设计一个人们不会屏蔽的 AI 代码审查工具。”优秀的答案会将确定性步骤与模型步骤区分开来，在团队自己的 PR 上衡量精确率，并将审查者的注意力视为稀缺资源。请在我们的系统设计问题和 RAG 与 Agent 问题中练习这类答案，并阅读 SWE-bench 以了解本文所依赖的基准测试阅读习惯。

常见问题

OpenCodeReview（OCR）是阿里巴巴推出的一款采用 Apache-2.0 许可证的命令行 AI 代码审查工具，在内部使用后于 2026 年开源。它读取 Git diff，在代码中决定要审查哪些文件以及适用哪些规则，为每组相关文件运行一个使用工具的 LLM Agent，并发布行级评论。它兼容 OpenAI 和 Anthropic 的端点，并拥有适用于 Claude Code、Codex、Cursor、Kimi Code 和 OpenCode 的插件。

在其发布的基准测试中，它更精确且安静得多：每个拉取请求（pull request）大约产生 3 到 5 条评论，而使用相同模型的 Claude Code 则产生 6 到 30 条评论，且 token 消耗约减少 9 倍。在每一组相同模型的对比中，Claude Code 发现了更多真实问题。当审查者注意力是瓶颈时，请使用 OCR；当遗漏缺陷的代价高于阅读噪音时，请使用通用 Agent，或两者兼用。

从绝对数值来看，并不算高。在 AACR-Bench（200 个拉取请求，1,505 个已验证问题）上，OpenCodeReview 表格中的最佳配置 F1 为 25.1%：它发现了 20% 的已知问题，其评论中约三分之一匹配到某个问题。精确率是一个下限，因为基准测试只知道有人发现的问题，但与细心的真人审查者相比，差距仍然很大。

部分支持。其针对 JavaScript 和 TypeScript、Python、Go、PHP、Rust、GitHub Actions 工作流以及 MyBatis mapper XML 的规则文件包含安全检查。在 1.13.2 版本中，Java、Kotlin 和 C++ 的规则文件没有任何安全检查，而提到 SQL 注入的默认规则仅适用于没有自己规则文件的文件类型。请为这些语言添加你自己的安全规则，并在 CI 中保留专用的安全扫描器。

该工具是免费的；你需要为模型 token 付费。其基准测试报告显示，使用 OCR 时每次审查跨模型消耗 334K 到 743K token，而 Claude Code 则消耗 200 万到 570 万 token。以每百万输入 token 3 美元的示例价格计算，约 40 万 token 在缓存前大约相当于每个拉取请求 1.20 美元。请查询你自己提供商的价格和缓存费率。

讨论 (5)

行号这一点值得成为一条普遍规则，而不仅仅是在审查机器人中。每当 Agent 编辑或引用文件时，都让它引用文本内容，并让代码来定位位置。我们将一个文档批注 Agent 改为相同的模式后，错位的编辑就消失了。

读者提问：你会同时运行 OCR 和 Claude Code，还是只选其一？

并排运行一个月，处理不同的任务。OCR 在每个 PR 上发布内联评论，因为其数量尚可容忍。通用 Agent 按计划在风险较高的目录（认证、支付、迁移）上运行，并提交 issue 而非评论。衡量哪些评论被采纳处理，并砍掉人们学会忽略的那一类。

Opus 4.8 那一行是表格中无声的警告。同样的工具，更新的模型，F1 从 25.1 降到 17.9，召回率几乎减半。评审框架是针对某个模型的习惯调校的。在 CI 中固定模型版本，升级前用自己的样本重新跑一遍。

只删除 diff 能证明有误的评论的事实核查提示词是好的设计。大多数团队把过滤器写成相反的方向，然后纳闷为什么机器人从来不说有用的东西。不对称的成本应该用直白的语言写进提示词里。
