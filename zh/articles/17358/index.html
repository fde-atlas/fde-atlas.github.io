模块 5：FDE 轮次的实战编程

原标题：Module 5: Practical coding for FDE rounds

FDE Interview Prep · 2026 · 约 3 分钟读完

摘要

本文是 FDE 面试备考课程，讲解实战编码环节的核心：调用第三方 API 时的重试、幂等与限流。以虚构水务公司向计费供应商提交用量扣费为例，说明如何先向供应商确认契约（幂等键有效期、503 语义、限流归属、异常处理人），再按 HTTP 语义分类决定是否重试：429、408 等未执行可等待后重试；超时、5xx 可能已执行，仅在可安全重复时重试；4xx 拒绝类绝不重试。文章引用 Vercel 公开的 fde-challenge-backend 规格作为参照，并强调带幂等键的 POST 才能安全重试，否则可能造成客户被重复扣费。

要点

  • 实战编码考察第三方 API 调用的重试、幂等与限流。
  • 写代码前先问供应商四个契约问题，如幂等键有效期与 503 语义。
  • 按 HTTP 语义分类：未执行可重试，可能已执行须幂等键，4xx 拒绝绝不重试。
  • Vercel 的 fde-challenge-backend 规格要求 429、503 视为瞬态，最多三次尝试且并发上限为四。
  • 示例中供应商限每秒 20 次、突发 5 次、每次扣费最多四次尝试。

全文

FDE 编程轮次考察什么 已对各轮次进行排序；本课将构建实际轮次、带回家作业和客户集成都依赖的代码：调用他人 API 时失败、变慢或被限流的场景。你将使用退避和 进行重试，确保重复调用安全，并用限流器控制节奏，避免重试压垮依赖方。在工作中，这就是“小故障”与“客户被重复扣费”之间的区别。

Vercel 的公开

fde-challenge-backend

规范（由黑盒一致性测试套件验证）描述了一个服务：将有效的库存事件转发给合作伙伴目录 API，并以事件 ID 作为 ；将 429 和 503 视为暂时性错误，总共最多尝试三次；同时在途的目录调用最多四个；该文件本身并未说明这是一场面试。来源 1

HTTP contract

发布方：Vercel（GitHub 上的 vercel-solutions）来源类型：公司网站 把“总共三次尝试”理解为一次原始调用加两次重试。这份契约就是本课的浓缩：一个键、一条重试规则、一个在途调用上限。

Integrating with systems of record

围绕它设计；而在这里你要亲手写出代码。

贯穿示例是虚构的：一家自来水公司使用 将每个水表的月度用量费用提交给其计费供应商，

POST /usage-charges

且在没有键的情况下不具备幂等性。在写任何代码之前，先弄清契约。第一件要说出口的事：

候选人：“先向供应商问四个问题。它是否接受键，键的有效期多长？503 是意味着它什么都没做，还是可能已经扣费了？限流是只针对我们，还是与自来水公司的其他任务共享？还有，未知的扣费由谁来解决？”

答案是：它接受键，并保留一天。限流只针对我们：每秒 20 个请求，突发上限 5，每次扣费最多四次尝试，而不是 Vercel 的三次：要从每份契约中读出具体数字。其正常调用最慢耗时

1.8 s

。它在执行任何操作之前会返回 HTTP 429 并附带

Retry-After

，但它的代理有时会在已扣费之后发送 HTTP 503。运营团队负责解决未知扣费。

何时重试，何时不重试

首先，是决策。问两个问题：服务器是否已执行操作？重复调用是否安全？

你看到的情况是否已执行操作？是否重试？
连接错误、408、429否是，等待后重试
读取超时、连接重置、500、502、503、504可能仅在重复安全时重试
400、401、403、404、422否，它拒绝了请求绝不重试；修复请求

简而言之：在工作开始前被拒之门外，等待后重试；可能已执行，仅在重复安全时重试；被判定为错误请求，绝不重试。

一个例外：由过期访问令牌导致的 401。刷新一次并重发；再次收到 401 则为最终结果。

HTTP 规范本身将 PUT、DELETE 以及 GET 等安全方法定义为幂等的（RFC 9110）；POST 不是，PATCH 也不是（RFC 5789）。因此，只有在携带幂等键时才重试 POST，或者先确认第一次请求确实没有生效。最容易让人踩坑的是 503：规范只说服务器当前无法处理该请求，对于是否已有任何工作被执行只字未提。规范也没有承诺 429 什么都没执行；这一条取决于供应商的契约。重试抖动问题构建了完整的分类器。

候选人：“这个 POST 会创建一笔扣款，所以读取超时意味着结果未知，而不是失败。我之所以会重试，只是因为它携带了幂等键。”

指数退避加抖动以不断增长且随机化的延迟进行重试，使从同一故障中恢复的客户端不会步调一致地同时重试。
