深度研究 Agent 需要一个审查者：Jev 审查层做对了什么，以及我们测试时发现的不足

原标题：Deep Research Agents Need a Reviewer: What a Jev Review Layer Gets Right, and the Gaps We Found Testing One

FDE Interviews · 2026-10-21 · 约 11 分钟读完

摘要

本文评测了一个开源深度研究 Agent 项目：用 Nemotron 做研究、Tavily 搜索、Jev 决策模型做审查层，验证了“写报告的模型不应自审”的 maker-checker 设计。作者实测发现三个普遍缺陷：审查失败时默认放行、重试时不带审查理由、依据搜索摘要而非原文判断引用支撑，并给出逐条修复方案。

要点

  • 写报告与审查应由不同模型分离完成。
  • 审查失败默认放行是最需修复的缺陷。
  • 无理由重试只是重掷骰子而非修订。
  • 引用校验应逐句、针对原文而非摘要。
  • 建议一次定向重试后升级给人工。

带有独立审查层的深度研究 Agent 是正确的设计：撰写报告的模型不应自行决定报告是否完成。我们阅读并测试了一个基于开源 Nemotron、Tavily 和 Jev 的构建。它在审查器故障时会放行、重试时不提供反馈，并且依据搜索摘要而非来源来判断论据支撑。以下是修复方法。

深度研究 Agent 不应给自己批改作业。在草稿和用户之间加入一个独立的审查层是正确的设计，而一个用 Nemotron 做研究、Tavily 做搜索、Jev 做审查的开源构建清晰地展示了这一模式。我们阅读了每一个文件并测试了审查路径。 这个思路站得住脚。但实现中存在大多数研究 Agent 都有的三个缺陷。审查器故障时它会放行。重试时不告诉 Agent 哪里出了问题。而且它依据搜索摘要而非来源来检查论据支撑。每个缺陷都可以在不到一百行代码内修复，而修复它们正是让审查者从装饰变成关卡的关键。下文包括：这个构建如何工作、我们的发现、我们会交付给客户的设计，以及这一模式何时值得付出成本。

这个构建，以及为什么这个设计是对的

该项目位于

deep_research_agent_with_review

GitHub 上 Sumanth P 的 Hands-On-AI-Engineering 仓库中，是在 Nebius AI Builder Program 期间构建的；README 中披露了该项目的额度信息。这是一个约 700 行 Python 代码的 Streamlit 应用，包含测试。一个

LangChain

Deep Agent 运行在

nvidia/Nemotron-3-Ultra-550b-a55b

Nebius Token Factory 上，负责规划工作并调用一个

search_web

由 Tavily 支持的工具（每次查询返回五个结果，按 URL 去重，编号为来源）。它撰写一份带编号引用的 Markdown 报告。一个小函数检查这些引用。然后，报告、问题、来源以及任何引用问题会被发送给 Jev——TypeSafe 的决策模型——并附带三个结构化问题：

  • evidence_coverage（是或否）：证据是否足以回答问题而没有重大缺口？
  • claim_grounding（是或否）：报告中的重要论断是否得到其编号来源的支持？
  • action（在 approve 或 research_again 之间选择）。

概率达到 0.70 或更高即视为通过。如果 Jev 要求更多研究，Agent 会再运行一次，Jev 再审查新报告。LangSmith 记录每一步的追踪信息。

README 用一句值得记住的话陈述了这一原则：Jev“不撰写报告”。这种分离正是关键所在。生成工作的模型是最没有资格判断工作是否完成的，因为它与产生这些缺陷的盲点如出一辙。这就是银行业以及我们的 agentic software factory guide 中的“制作者-检查者”规则，它适用于研究型 Agent 的原因与适用于代码的原因相同。使用快速决策模型作为检查者也是一个不错的选择：正如我们在 what Jev is 中所述，它能在约十分之一秒内为结构化问题返回校准后的概率，而且按照我们 2026 年 9 月记录的输入价格（每百万 token 0.042 美元，输出免费），对一份 5,000 token 状态的审查成本约为百分之二美分。

我们测试审查路径时的发现

该项目的三个单元测试全部通过。它们覆盖了响应解析和引用验证。随后，我们用生产系统最终会遇到的输入调用了相同的函数。运行完整应用需要 Nebius、Tavily 和 Jev 的密钥，因此我们直接测试了决策逻辑；以下内容均不依赖模型行为。

第五行是首先需要修复的问题。当审查响应解析结果为空（字段被重命名、网关返回 200 状态码的错误页面、schema 变更）时，解析器会将审查标记为“已完成”，找不到拒绝，并写入默认解释，即批准。失败时放行的审查者只是一个进度条。而一个什么都没读到却报告批准的审查者，比没有审查者更糟糕，因为它消除了用户自身的警惕。

我们还用常见格式测试了引用检查器：

报告文本结果
Latency fell 40% [1]. Costs rose [2].通过
延迟下降了 40% [1, 2]。成本上升了 [3, 9]。(来源 9 不存在)"没有编号引用"
三项研究一致认为 [1-3]。"没有编号引用"
概述 [1]。2026 年收入翻倍。CEO 辞职。通过
收入翻倍 [7]。(只有五个来源)标记来源 7

这个正则表达式只匹配方括号中的单个数字，因此分组引用看起来就像完全没有引用，而且第二行中虚构的来源 9 从未被标记。第四行是更大的问题：只要任何地方有一个真实引用，每条未引用的声明都能通过。作为检查的第一版还算合理，它也说明了为什么引用检查应该按句子运行，而不是按报告运行。

三个缺口，以及各自付出的代价

1. 失败时放行。 前文已述。在演示中这无害。在客户部署中，评审员的 API 密钥轮换的那一天，就是每份报告都未经评审就发布的那一天，而且没人注意到，因为 UI 仍然显示"已批准"。要明确决定失败策略：阻止，或以醒目的"未评审"标签展示，无论哪种方式都要提醒某人。

2. 重试时不带评审员的理由。 当 Jev 要求更多研究时，第二次运行从头开始：新的搜索收集器、新的 Agent、原始问题，以及一句说明证据薄弱的通用句子。它不会收到第一份报告、第一批来源，也不知道哪项检查失败了。代码只向 Jev 要两个布尔值和一个选择，因此无论如何都没有理由可以传递。不带评审员理由再次研究是重新掷骰子，而不是修订。 你会得到一份有不同问题的新报告，而第二次评审是对同一分布中一次新抽样的评分。

3. 基于片段进行事实核查。 搜索工具请求结果时

include_raw_content

关闭，因此每个来源只是一个标题、一个 URL 和一段简短片段，评审负载将片段截断为 1,200 个字符。当 Jev 回答"这些声明是否得到编号来源的支持？"时，它看到的来源只是预告。一条声明可以匹配片段，却与页面内容相矛盾。

Grounded in a snippet is not grounded in a source.

抓取层是证据的一部分：如果 Agent 从未读过页面，那么流水线中就没有人读过。

这些都不罕见。我们在资金雄厚的团队构建的研究 Agent 中都见过这三种问题，这也是为什么这个小项目是一个很好的教学案例。

我们会交付的设计

这是我们提议的设计。修复会回到证据收集和起草阶段，然后重复引用、事实核查和覆盖检查。

按价值排序的改动：

  • 按策略默认失败关闭。 任何评审员错误、密钥缺失、超时或无法解析的响应都会产生明确的未评审状态。绝不默认为批准。
  • 让确定性检查成为门禁。 解析 [1, 2]、[1-3] 和脚注样式。任何包含事实声明但没有引用的句子，在任何模型看到报告之前就被移除或标记。
  • 逐条声明对照原文进行核查。 将报告拆分为一条条声明，针对每条声明向决策模型提出一个是非问题，并对照其引用的原文段落进行判断。每次调用约需十分之一秒、成本不到一美分，Jev 便宜到足以对每份报告运行二十次。逐条声明的结果还能让重试环节确切知道该修复什么。
  • 带原因的重试。 将未通过的声明、未回答的子问题以及已收集的资料一并传入。要求进行有针对性的修复，而不是重写一份新报告。
  • 记录每一次概率。 对已批准的报告也要保留覆盖率和接地得分。一个得分总是停留在 0.95 的关卡实际上什么也没把关，而只有从分布中才能看出这一点。
  • 升级，而不是循环。 进行一次有针对性的重试，然后展示报告并列出其未解决的缺口，如果风险足够大，就转交给人工处理。

这一设计将原本合并在一次调用中的三种不同工作分离开来：代码负责代码能检查的部分，一个快速的决策模型回答狭窄的事实性问题，剩下的事情由人工处理。同样的拆分方式也适用于用 LLM 评审器 替代 Jev；对于狭窄的问题，决策模型只是更便宜、更快，而当你需要书面批评意见时，LLM 评审器则更合适。

该模式的优点、缺点及适用时机

优点现有实现的缺点
撰写者和评审者是职责分离的独立模型失败时默认放行；格式错误的评审会被当作通过
带概率和明确阈值的结构化评审问题重试是盲目的，会从头重新调研
有边界：最多一次自动修订，因此成本和延迟可预测接地判断仅依据搜索摘要
每个部分（模型、搜索、评审器、追踪）都可替换引用检查仅具建议性质，且会漏掉分组引用
代码可读，有解析测试，并使用 LangSmith 进行追踪仓库中没有许可证文件，因此复用条款不明确

当错误答案代价高昂但慢一点可以接受时，可使用带评审的研究型 Agent：竞争与市场简报、供应商尽职调查、文献综述、客户会面前的客户调研、政策与法规摘要。对于前沿部署工程师而言，关于客户行业的会前简报是一个很好的首次应用场景：风险低、节省时间多，且易于抽查。

不要在以下情况使用：答案必须精确到分钟、资料位于 Agent 无法访问的登录墙之后，或输出直接发送给客户而没有任何人工阅读。评审层只能降低错误率，它并不能让一份无人阅读的报告变得可以安全发送。

在成本方面，评审是便宜的部分。使用 5500 亿参数模型并执行十几次搜索的一次研究运行，其成本远高于二十次 Jev 调用，因此逐条声明的接地检查对账单的影响微乎其微。昂贵的错误恰恰相反：在评审上省下不到一美分，却发出一份建立在搜索摘要之上的、看似自信的报告。

常见问题

审查层是一个独立组件，用于判断研究报告是否足够好、可以展示，而不是让撰写报告的模型自行决定。它通常检查证据是否覆盖了问题、每条论断是否有引用来源支持，然后批准报告或将 Agent 退回继续研究。将撰写者与审查者分离，就是应用于 Agent 的“制作者-检查者”原则。

Jev 是一个决策模型：它能在约十分之一秒内以概率形式回答结构化问题（是或否、一个选择、一个分数），每次审查的成本不到一美分的一小部分。这非常适合一个对每份报告都运行的门控。LLM 评审者能更好地解释其推理并处理开放式批评，因此好的设计是用快速决策模型作为门控，只有当它指出报告需要改进时才调用更强的模型。

失败时放行。如果审查者超时、缺少密钥或返回意外结果，许多实现仍会展示报告，有时甚至标记为已批准。失败时不拦截的审查者只是一个进度条。请提前决定审查者不可用时该怎么办，并让该路径对用户可见。

将审查者的理由、未通过的论断以及已收集的来源提供给重试，并要求它针对性地修复这些问题。用“做得更好”这类笼统指令重新运行整个研究任务属于重新掷骰，而非修订，可能产生一份带有不同问题的新报告。限制重试次数，达到上限时升级给人工处理。

不能。仅检查被引用的来源编号是否存在只能证明引用格式正确。你还需要论断级别的溯源验证：将报告拆分为论断，并逐条对照被引用的段落进行检查，最好使用完整页面而非搜索摘要。没有引用的论断应被移除或标记，而不是因为别处存在某个引用就被容忍。

讨论 (4)

片段摘录这一点是团队在生产环境中最容易忽视的。搜索 API 每条结果只返回几百个字符，审阅者仅凭这些内容就可能批准一个声明，而完整页面在两段之后却与之相矛盾。如果事实依据很重要，就应该抓取并存储整个页面，让审阅者阅读正文段落，而不是摘要预览。

读者提问：重试一次还是多次？

做一次有针对性的重试，然后就交给人工。根据我们的经验，第二次自动重试大多只是在改写措辞，很少能找到新的证据。如果第一次重试没有弥补差距，这个问题很可能需要搜索工具无法触及的来源，应该让相关人员知道这一点。

值得补充的是：无论报告是否获批，都要记录审阅者给出的概率。一个月后，你就可以将批准率与 0.7 的阈值进行对比绘图，看看这个阈值是否真的起作用，还是说每份报告都在 0.95 左右，这道关卡从未真正拦截过任何内容。
