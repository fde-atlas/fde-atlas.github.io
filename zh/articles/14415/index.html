Agentic 系统设计面试：一份 FDE 的完整解答示例

原标题：Agentic system design interview: a worked FDE answer

FDE Interview Prep · 2026-09-25 · 约 14 分钟读完

摘要

文章讲解 FDE 面试中的 agentic 系统设计环节，指出其形式可能是画架构图、与面试官角色扮演 CTO，或追问安全防护。作者以一个虚构的退款 Agent 为例，给出完整答案框架：工具白名单与最小权限凭证、步骤/时间/成本预算防止死循环、幂等写入避免重复退款、人工审批交接，以及基于历史工单的评测与分阶段灰度上线。文中引用 Google、Okta、Cohere 等公司面试报告与职位要求，强调限制应写在代码而非提示词中，多 Agent 应按权限而非提示词拆分。

要点

  • 面试形式可能是架构图、CTO 角色扮演或安全追问。
  • 核心答案：Agent 有用且无法造成损害。
  • 工具白名单加短时凭证，限制写在代码里。
  • 用步骤、时间、成本预算和重复检测防卡死。
  • 退款写入需幂等，超限或低置信度转人工审批。

招聘官的邮件里写着“agentic system design（智能体系统设计）”，而你不确定这到底是指画框图和箭头、扮演 CTO，还是被拷问安全护栏。这三种都有可能，而一份设计方案可以同时应对所有情况：一个有用且不会造成损害的智能体。想了解这一轮在整个流程中的位置，请阅读 FDE 面试指南。

简短的回答：智能体系统设计面试要求你设计一个由模型选择工具和步骤的系统，然后证明它不会造成损害。一个完整的答案要涵盖五件事：智能体可以调用哪些工具，以及使用谁的凭证；能阻止卡死运行的预算限制；哪些操作可以安全重试；由人来批准或接管的节点；以及在智能体接触真实客户之前的评测、追踪和分阶段上线。

下面先介绍候选人的反馈，然后是一个端到端设计的虚构退款智能体，并附上每一步该说的话。

场景：为客户支持团队打造一个退款 Agent

下面是我们将要据此设计的提示词。它是虚构的。

“我是一家在线零售商的 CTO。退款请求占了我们支持队列的大部分，客户要等好几天。我想要一个 Agent，能读取工单、核对订单并支付退款。要保证安全。”

在画任何框之前，先复述你听到的内容并点出风险：“所以这个 Agent 会执行一个涉及资金的操作。设计问题与其说是‘模型能不能做到’，不如说是‘什么能阻止它大规模地、重复地做错事’。”

然后勾勒整体结构。把正常路径保持为一个小的状态机，让模型只在状态内部做决策：

  • 读取工单并进行分类：是退款请求，还是其他。
  • 收集订单、客户历史和退款政策。
  • 决定退款：是否符合条件，以及金额多少。
  • 在限额内执行，或转交给人工审批。
  • 回复客户并关闭工单，或进行移交。

说明理由：“状态机意味着我能看到每张工单所处的位置，能从 trace 重放一次失败的运行，并且能在不改动其余部分的情况下更换模型。”一个每一步都能使用所有工具、自由漫游的 Agent 更难测试，也更难向安全团队解释。

工具、允许列表和受限凭证

Agent 只能做它的工具允许它做的事，所以工具列表是你的第一道防护栏。给模型一个简短的允许列表，并对每个工具进行范围限制，使其最坏的输出结果仍然可以接受。

get_orderread该客户的订单
get_policyread退款政策文本
issue_refundwrite已核实的订单，一次，限额以内
hand_offwrite始终允许

search_all_orders

服务器暴露工具，允许列表仍然由你这边掌控：Agent 只能看到这个工作流所需的工具。

将凭证限定在单次运行，而不是绑定到 Agent。 可以这样说：“Agent 从不持有长期有效的 API 密钥。每次运行都会获得一个短时效的令牌，绑定到单个客户，并且

卡住的 Agent：步骤、时间和成本预算

Agent 会卡住。ElevenLabs 在一篇关于前沿部署工程经验教训的语音 Agent 文章中，将工具误用列为 Agent 部署中最常见的反复出现的失败模式之一。来源 7构建持久的语音 Agent：来自前沿部署工程的一些经验教训发布方ElevenLabs来源类型公司博客 下面是我们对其中一种情形的示例：Agent 调用

get_order

，不满意结果，然后用相同的参数一遍又一遍地重复调用。

为每次运行设置三个预算和一个检测器：

  • 步骤预算，例如 max_steps = 12。一次退款只需要少量工具调用；十二次意味着出了问题。
  • 墙钟时间预算，例如 max_seconds = 90，这样缓慢的上游系统就无法让一张工单一直挂着。
  • 成本预算，例如每次运行 max_cost_usd = 0.50，对运行中所有模型调用的成本求和，这样一张混乱的工单就不会烧掉整月的支出。
  • 重复检测器：相同的工具、相同的参数和相同的结果出现三次，就停止运行。网络错误后的重试是编排器的职责，采用退避机制，且不计入重复次数。

预算触发后发生什么，比数字本身更重要。可以说：“卡住的 Agent 是一种有负责人的正常状态，而不是崩溃。运行会停止，保存它已收集的信息以及停止的原因，并将工单转交给人工。它不会从头重试，因为一个混乱的运行从头重试可能会以同样的方式再次陷入混乱。” 反复大声演练，直到无需看稿。

你要记录什么

每次运行都会写入一条追踪记录：运行 ID、状态、每次模型调用及其 token 数、每次工具调用及其参数和结果，以及运行结束的原因。这条追踪记录使重放成为可能，也是交接时人工所看到的内容。

按小时绘制预算触发和人工交接的图表，并在出现跳升时告警。跳升可能意味着上游 API 发生了变化，也可能只是模型变差了，所以追踪记录是你首先要查看的地方。

幂等操作与安全重试

网络在“退款已发送”和“退款已确认”之间出现故障。编排器会重试。如果

issue_refund

不是幂等的，客户就会被重复退款。

用基于业务事实（而非模型输出）构建的幂等键，让写入工具具备幂等性：

def issue_refund(order_id, cents,
                 approver=None):
    key = f"refund:{order_id}"
    rec = ledger.get(key)
    # a finished refund comes back as-is
    if rec and rec["status"] != "pending":
        return rec
    # after a crash, reuse the first amount
    amount = rec["cents"] if rec else cents
    if amount > refundable_cents(order_id):
        return {"status": "rejected"}
    if amount > AUTO_LIMIT and not approver:
        return {"status": "needs_approval"}
    ledger[key] = {"status": "pending",
                   "cents": amount}
    ledger[key] = payments.refund(
        order_id, amount,
        idempotency_key=key)
    return ledger[key]

有三个细节需要明确说出来：

  • 键是订单，而不是工单或金额。 重复的工单，或金额不同的重试，都会返回第一次的结果，而不是产生第二笔退款；同一订单的合法第二笔退款会转给人工处理。该工具还会将金额上限设为实际支付金额，而不仅仅是自动审批限额。
  • 先写入“pending”状态，并将同一个键传给服务提供商。 崩溃后，重试会再次发送同一个键，服务提供商返回其第一次的结果，因此退款只会发生一次。
  • 在生产环境中，账本是一张对键设有唯一约束的表， 这样两个并发运行就无法同时插入。

如果面试官想了解并发细节，幂等键问题涵盖了两个相同请求同时到达的情况。

当 AI Agent 转交给人工时

人工审批是设计的一部分，而不是兜底方案。当某个操作属于以下情况时，转给人工处理：

  • 不可逆或代价高昂： 超出客户限额的退款。
  • 超出政策范围： 超过退货期限的订单，或政策标记为有风险历史的客户。
  • 置信度低： AI Agent 无法将工单匹配到订单。
  • 超出预算： 触发了任何预算限制。

让转交真正有用。人工可以看到建议的操作、证据（订单及其依据的政策条款）、追踪记录，以及一句话说明 AI Agent 为何停止。他们可以一键批准、编辑或拒绝，其决策会被记录为一个新的评测用例。

决定无人响应时怎么办。如果在客户的时间窗口内无人批准，AI Agent 会等待，工单会升级；它绝不会在超时后自行操作。直截了当地说：“没有答复就意味着没有退款，并触发更响亮的警报。”

这个模式不仅仅是面试中的想法。2026 年 6 月，Decagon 发布了 Duet Autopilot，它会针对黄金测试集测试每个建议的 AI Agent 变更，并要求人工批准后才能将任何变更投入生产。来源 8Introducing Duet Autopilot: The self-improving agent for conversational AI发布方Decagon 博客来源类型公司博客 该审批针对的是 AI Agent 的变更，而不是每个操作：这是一个值得提及的有用的第二层保障。

如果他们要求多 Agent 架构

面试官可能会说“现在把它做成多 Agent 的”。按权限进行拆分。分诊 Agent 只持有读取工具。它读取工单，收集订单和政策信息，并移交一个结构化的案例：订单 ID、政策条款和建议金额。退款 Agent 接收该案例，并独自持有

issue_refund

，在相同的 token、限额和 下。

编排器保持为确定性代码，而不是第三个模型。它在 Agent 之间传递工单，为每个 Agent 分配各自的允许清单和预算，并在两者之间写入同一条追踪记录。工单中被注入的指令只会到达那个无权执行付款的 Agent。

要说的那句话：“我按权限差异来拆分 Agent，而不是按提示词差异来拆分。”五个拥有相同工具的 Agent 就是五个需要调试的东西。

评测与分阶段上线

“你怎么知道它有效？”这个问题要在被问到之前就回答好。用从客户自身历史记录构建的测试集来回答。

拉取过去的退款工单及其真实结果。对每个状态分别打分：Agent 是否正确分类了工单、是否找到了正确的订单、是否正确应用了政策、是否选择了正确的操作？错误的最终答案告诉你有环节失败了；分步骤的评分告诉你失败在哪里。Cohere 的 Agentic Platform FDE 招聘要求具备构建评测框架的能力，以衡量 Agent 的准确性、安全性和延迟，Source 9Forward Deployed Engineer, Agentic PlatformPublisherCohere (Ashby job board)Source typecompany job posting，而 Google Cloud 的 GenAI FDE 招聘则列出了为 Agentic 系统构建评测流水线和可观测性框架的要求。Source 10Forward Deployed Engineer III, Generative AI, Google Cloud — Google CareersPublisherGoogleSource typecompany job posting 准确性、安全性和延迟构成了一个很好的评分卡。

有意加入对抗性案例：一张要求查询他人订单的工单、一条被注入的指令、一笔刚好超过限额的退款、一张重复工单。在每次提示词、模型或工具变更之前运行整个测试集。评测框架问题会逐步设计这个测试框架。

然后分阶段上线，每个阶段都设有一个在开始前 CTO 同意的门槛：

  • 影子模式： Agent 对实时工单做出决策，但由人来完成实际工作，并对两者进行比较。
  • 辅助模式： Agent 起草，由人批准每一笔退款。
  • 自动模式，小范围： Agent 在一部分流量上独立处理低价值退款，作为一次金丝雀发布。
  • 扩大范围： 只有当上一阶段的数据达标时，才提高流量比例，然后提高限额。

为每个阶段指定回滚方案：一个开关就能把一切退回辅助模式。

与 CTO 对练：先问什么

如果这一轮是角色扮演，CTO 不会给你一份规格说明。你的前五分钟应该是提问，而且每个问题都应能改变设计。可以这样说：

“在开始设计之前，我有几个问题。哪些操作 Agent 可以独立执行，哪些必须由人批准？一笔错误的退款会让您付出什么代价，包括金钱和信任？它会触及哪些系统，由谁负责？客户数据必须保留在哪里？还有，在第一个月，什么会让您认为这件事是成功的？”

然后复述确认：“所以 AI Agent 可以在你的限额内自主退款，超过限额需人工审批，数据保留在你的云环境中，成功标准是首次回复更快且错误退款率不上升。对吗？”与客户一起规划 AI 项目范围介绍了如何把这些答案转化为第一个里程碑。

三个需要避免的错误，以及各自的纠正方法：

  • 一上来就谈框架。 在还不清楚 AI Agent 能做什么之前就点名某个编排库，跳过了设计所依赖的关键部分。纠正方法：先询问操作和风险。
  • 默认使用多个 Agent。 纠正方法：从一个开始，只在权限不同的地方才拆分，如上所述。
  • 安全只写在提示词里。 纠正方法：把每条限制都放进工具或令牌中，并说明每条限制存放在哪里。

当 CTO 施压（“就不能让它把所有退款都办了吗？”）时，用他们的语言解释这种权衡：要么快速但偶尔出错，且错误成本由他们选择；要么更慢，但在高风险环节安排人工把关。我们关于向非技术领导者解释 AI 局限的课程涵盖了这段对话。

在面试轮次前进行练习

我们建议的一小时面试轮次计划：

  • 开场几分钟： 提问，然后复述确认。
  • 第一个十五分钟： 状态机和工具。
  • 中间部分： 预算、幂等性、人工交接。
  • 最后十五分钟： 评测、追踪和上线。
  • 最后几分钟： 你会最先关注的绊线，例如客服团队的实际执行方式与政策条文不一致的情况。

  • 写出你的工具允许清单以及每个凭证的权限范围。
  • 说明你的步骤、时间和成本预算，以及触发任一预算时会发生什么。
  • 解释为什么你的写入工具可以安全重试，包括崩溃之后。
  • 列出哪些情况交给人工处理，以及无人应答时会发生什么。
  • 说明每次运行记录哪些日志，以及你会如何把它拆分成两个 Agent。
  • 说出你的评测集、你的阶段划分和你的回滚方案。

如何防止 Agent 无限循环？

为每次运行设定预算：最大步数、时间上限和花费上限。当相同工具调用以相同参数三次返回相同结果时停止运行；当预算耗尽时，停止重试，将案例连同摘要转交给人工处理。

Agent 什么时候应该请求人工批准？

在任何不可逆、代价高昂或违反政策的操作之前，例如超过客户设定限额的退款。向人工展示拟议操作和证据，当批准超时后，Agent 应等待而不是擅自行动。
