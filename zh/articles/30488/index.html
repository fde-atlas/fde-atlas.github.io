AWS Glue、ADF、Dataflow 对比：FDE 如何接手 ETL

FDE Times · 2026-10-08 · 约 4 分钟读完

摘要

文章面向接手数据类客户的前沿部署工程师（FDE），讲解如何快速读懂客户已有的 ETL 管道。作者对比了 AWS Glue、Azure Data Factory 和 Google Dataflow 的架构与术语：Glue 和 ADF 数据流都基于 Spark，Dataflow 则基于 Apache Beam，用一套模型统一批处理与流处理。文章给出按平台区分的排查清单，强调在 Azure 上要先确认客户用的是 ADF 还是 Fabric 中的 Data Factory，并先查集成运行时；还提醒爬网程序推断的 schema 需核实、自动化扩缩不代表逻辑正确。学习顺序建议：先学 Spark，再学 Beam，最后掌握 CI/CD 发布流程。

要点

  • Glue 与 ADF 数据流基于 Spark，Dataflow 基于 Apache Beam。
  • 接手 Azure 客户先问清是 ADF 还是 Fabric 中的 Data Factory。
  • 排查顺序：AWS 看 Data Catalog，Azure 看集成运行时，GCP 看 Beam 代码。
  • 自动化扩缩不代表转换逻辑正确，schema 推断需与数据负责人核实。
  • 学习顺序建议先 Spark，再 Beam，最后练 CI/CD 发布管道。

FDE 很少从零开始：Agent 要读的数据早已流经 Glue、ADF 或 Dataflow，第一周内就得读懂这些管道。

要点速览

  • Glue 和 ADF 数据流都运行在由服务托管的 Spark 上。Dataflow 基于 Apache Beam，批处理和流处理共用一套模型。
  • 在 Azure 客户那里，尽早问清对方用的是 ADF 还是 Microsoft Fabric 中的 Data Factory，因为 Microsoft 正在引导新用户转向 Fabric。
  • 接手时先打开什么：AWS 上看 Data Catalog，Azure 上看集成运行时，Google Cloud 上看 Beam 代码。

“你们用的是 Azure Data Factory，还是 Microsoft Fabric 中的 Data Factory？”在跑在 Azure 上的客户那里，这应该是前线部署工程师（FDE）最先问的问题之一。

原因就写在 Microsoft 自己的概览页上。Microsoft 仍将 ADF 描述为一项托管云服务，面向复杂的 ETL、ELT 和混合数据集成项目。但同一页面又称 Fabric 中的 Data Factory 是 ADF 的“下一代”，并引导新用户转向 Fabric。

这个问题背后是一个现实：只要工作涉及数据，FDE 很少从一张白纸开始。等他们到场时，客户通常已经在用 AWS Glue、Azure Data Factory 或 Google Dataflow。Agent 或模型要读取的数据，恰恰就流经这些管道。

不必把三者都学成专家，但需要在第一周内读懂客户的管道。

三个服务，三套术语

AWS 将 Glue 描述为一项无服务器数据集成服务，用于从多个来源发现、准备、迁移和整合数据。其核心是爬网程序（crawler），它负责推断 schema 并写入 Glue Data Catalog。Glue Studio 支持通过拖放搭建转换工作流，并在基于 Apache Spark 的无服务器 ETL 引擎上运行。

偏好写代码的人则使用 Spark、Python 或 Scala。

ADF 有自己的一套概念：管道（pipeline）、活动（activity）、数据集（dataset）、链接服务（linked service）、数据流（data flow）和集成运行时（integration runtime）。映射数据流运行在按需启动、用完自动关闭的 Spark 集群上，用户无需管理集群。集成运行时是活动与链接服务之间的桥梁，换句话说，它决定了管道实际在哪里运行。

Google 将 Dataflow 定义为一项统一的批处理和流处理服务，可大规模运行。Dataflow 于 2014 年 6 月发布，2015 年 4 月进入公开测试，如今基于开源项目 Apache Beam 构建。负载变化时，服务会自动增加或关闭工作节点虚拟机。

同一个问题，三处先看的地方

假设一家零售连锁企业想让 Agent 回答库存相关的问题。每天夜里，订单文件落入数据湖，而库存表存放在办公室的一个数据库里。任务是把这两个来源汇集到一个干净的位置，供 Agent 查询。下表给出了在各平台上应该先看哪里。

步骤 AWS Glue Azure Data Factory Google Dataflow
弄清数据内容 查看爬网程序写入 Data Catalog 的 schema 阅读数据集和链接服务 阅读 Beam 代码中读取数据源的部分
连通本地数据库 打开作业，记下它到办公室数据库的连接，再向网络团队询问路由和访问权限 检查由哪个集成运行时充当桥梁 找到 Beam 代码中读取数据库的步骤，再向网络团队确认工作节点虚拟机能否访问办公室数据库
转换 Glue Studio 或 PySpark 作业 运行在 Spark 上的映射数据流 Beam 转换
何时运行 按计划、按需或由事件触发 打开管道，检查活动顺序，并询问客户由什么触发 询问客户作业如何启动，是批处理还是流处理

横向逐行看下来，这个例子中最难的问题在第二行。集成运行时是活动与链接服务之间的桥梁，因此在 Azure 上，要确认管道到底能否连上办公室数据库，首先就要查它。

在编写任何转换之前，先和客户的网络与安全团队坐下来，把这座桥梁确定下来。

局限在哪里？

三个服务都隐藏了大量基础设施，而这恰恰容易让 FDE 掉以轻心。Spark 自动启停、工作节点自动扩缩，并不能说明转换逻辑是正确的。爬网程序从数据中推断出的 schema 终究只是猜测，要和该数据源的负责人核实。

Azure 还多了一个战略问题。Microsoft 表示，现有的 ADF 工作负载可以升级到 Fabric。因此，任何在 ADF 上新建内容的方案，都应当同时直接问客户：是否计划迁移到 Fabric？跳过这一步，交接刚完成，升级可能就被提上日程。

Dataflow 的难点在编程模型，而不在基础设施。Beam 用一套模型同时处理批处理和流处理，功能强大，但习惯写顺序脚本的人需要时间适应。

先学什么

如果只有一个月，先学 Spark。在 Glue 上，ETL 作业直接用 Spark 编写。在 ADF 中，Spark 位于映射数据流底层并由服务托管，因此懂 Spark 有助于理解数据流如何运行，尽管你不需要亲自运维它。

接着，把 Beam 学到能读懂 Dataflow 管道的程度。最后，练习把管道纳入发布流程：ADF 完整支持通过 Azure DevOps 和 GitHub 实现 CI/CD，企业客户会问到这一点。

阅读 FDE 岗位描述时，留意其中提到了哪些 ETL 服务，据此决定先补哪个平台。简历上不要写“熟悉 AWS Glue”，而要写你读懂了一条现有管道，找到了 schema 发生漂移的位置，并通过 CI/CD 发布了修复。

这一行能让招聘经理看到 FDE 在客户现场真正做的工作。

客户的 ETL 工具几乎肯定在你到场前就已选定。你能掌控的，是多快读懂它。
