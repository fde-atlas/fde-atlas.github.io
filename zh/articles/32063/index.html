Snowflake Cortex Analyst 与 Cortex Search 对比：FDE 指南

原标题：Snowflake Cortex Analyst vs Cortex Search: an FDE guide

FDE Times · 2026-10-30 · 约 5 分钟读完

摘要

文章以 Snowflake 两份已关闭的 FDE 招聘启事为线索，说明前沿部署工程师的核心工作不是调优 LLM，而是构建语义模型，让客户数据在 Cortex Analyst 中被正确理解。Cortex Analyst 通过 REST API 处理结构化表格问题，依赖 YAML 或 Semantic Views 定义的语义模型；Cortex Search 则用向量加关键词的混合检索处理文本，用于 RAG 和企业搜索。指标定义（如净收入的口径）需与财务用户事先确认，否则会得到看似合理却错误的答案。文章还强调评测应从项目一开始就纳入，建议用经用户认可的问答集反复回归测试，并给出学习顺序与简历写法建议。

要点

  • FDE 的核心工作是构建语义模型，而非调优 LLM。
  • Cortex Analyst 处理表格数据，需 REST API 调用和语义模型。
  • Cortex Search 用混合检索处理文本，用于 RAG 和企业搜索。
  • 指标定义须与财务用户确认，避免看似正确实则错误的答案。
  • 评测应从建模型起就做，用认可的问答集回归测试。

Cortex Analyst 处理针对表格的提问，Cortex Search 处理文档，但 FDE 的工作是让客户数据表达正确的含义。

简要概述

  • Cortex Analyst 是一项通过 REST API 调用的托管式、由 LLM 驱动的功能。它的回答是否正确，取决于语义模型。
  • Cortex Search 对文本运行混合搜索（向量加关键词），主要用于 RAG 和企业搜索。
  • 两则 Snowflake 的 FDE 招聘广告都提到构建语义模型、制作原生 Streamlit 仪表板，并将评测视为构建工作的一部分。

Snowflake 曾发布过一个名为“前沿部署工程师 - 金融分析与 AI 专家”的职位。该招聘于 2026 年 7 月 8 日截止。广告中提到的产品包括 Cortex Analyst、Cortex Agents、Cortex Search、Cortex Code 和 Snowflake CoWork。

比产品列表更能说明问题的是对工作内容的描述：构建和改进语义模型，使用户能够通过 Cortex Analyst 用自然语言查询客户的数据表。

这一细节表明，FDE 的许多工作位于赋予数据含义的层面，而较少涉及 LLM 本身。

如果你打算应聘围绕数据平台的 FDE 职位，无论是在 Snowflake 还是其他公司，请理解下面三种工具以及它们如何协同工作，而不是死记功能列表。

每种工具针对不同类型的问题

Snowflake 的文档将 Cortex Analyst 描述为一个完全托管、由 LLM 驱动的 Cortex 功能，用于构建回答结构化数据业务问题的应用。它以 REST API 的形式提供，因此可以嵌入任何应用。要让它理解数据，你必须提供语义模型。

Cortex Search 处理另一种类型的问题。它是一项混合搜索服务，结合向量搜索和关键词搜索，对文本数据运行，并支持低延迟的模糊搜索。

根据文档，它的两个主要用途是 RAG 和企业搜索。合同、邮件和对账说明交给 Cortex Search；表格中的数字交给 Analyst。

Streamlit 是一个用于构建 Web 应用的开源 Python 库。Snowflake 中的 Streamlit 让你可以在 Snowflake 内部构建、部署和共享这些应用，因此数据无需离开平台。招聘广告指出，FDE 将把财务、运营和分析仪表板构建为在 Snowflake 中原生运行的 Streamlit 应用。这些是生产级仪表板，而不仅仅是演示。

Cortex Analyst

  • 结构化数据：表格、列、数字
  • 需要描述数据含义的语义模型
  • 通过 REST API 调用

Cortex Search

  • 文本数据
  • 结合向量与关键词的混合搜索
  • 用于 RAG 和企业搜索

语义模型才是真正的产品

根据文档，Cortex Analyst 的语义模型以一个轻量级的 YAML 文件编写。对于新部署，Snowflake 推荐使用语义视图（Semantic Views）。放在 stage 上的 YAML 文件仍然受支持。

语义视图是一个 schema 级别的对象，包含四个组成部分：逻辑表、维度、事实和指标。Snowflake 将指标定义为业务绩效的量化度量。

假设财务团队提问：“上个季度各地区的净收入是多少？”假设客户有一个 orders 表和一个 regions 表。逻辑表就是这两个表；维度是地区和季度；事实是每个订单行上的金额、退款和折扣；指标则是净收入。

难点在于指标。销售团队可能把净收入视为订单总金额，而财务部门则会扣除退款和折扣。下面的草图只是说明这个定义如何写入模型，并非精确语法；具体字段名请查阅 Snowflake 的规范。

# Illustrative sketch, not exact Snowflake syntax
logical_tables:
  - name: orders
    dimensions: [region, quarter]
    facts: [amount, refund, discount]
metrics:
  - name: net_revenue
    description: "Total order value minus refunds and discounts, per the approved accounting definition"
    expr: SUM(amount) - SUM(refund) - SUM(discount)

如果没有

expr

和

description

这两行财务部门已认可的配置，模型仍会生成 SQL，但只能猜测提问者的意图。结果就是一个看似合理却仍然错误的答案。

因此，当你到达客户现场时，第一项工作就是与财务用户坐下来，用文字写出每个指标的定义，然后再打开编辑器。

招聘启事中说，FDE 将驻场与客户团队一起工作，随时清除部署过程中出现的障碍。与用户一起确定指标定义的会议正是这类障碍的典型例子。

从一开始就进行评测

另一个职位“前沿部署工程师，应用 AI”隶属于 Cortex AI 团队；该职位也已关闭。受聘者将在 Snowpark 和 Cortex 上构建生产级 AI 系统，并至少将 25% 的时间驻场服务于 Snowflake 最具战略性的客户。

该招聘启事还强调，评测必须是构建过程的核心部分，而不是留到以后再做。

对于 Cortex Analyst，最直接的评测方式是整理一组示例问题，每个问题都附有经财务用户认可的答案 SQL。每次修改语义视图后，都重新运行整套问题并比较结果。

回到净收入的例子。如果问题集中包含这个问题，且答案扣除了退款和折扣，那么定义错误就会在第一次运行时暴露出来，而不是在与 CFO 的会议上才浮现。

局限性与优先学习内容

第一个局限是工具之间的边界：Analyst 处理结构化数据，Search 处理文本。该招聘启事还在同一产品套件中提到了 Cortex Agents；如果客户提出的问题既需要表格又需要文本，那就是接下来应该在文档中深入研读的内容。

第二个局限是，答案的质量取决于语义模型的好坏。当模型回答错误时，先检查定义，再怀疑 LLM。

关于学习顺序，先从 SQL 和数据建模开始，直到你能在真实数据集上区分维度、事实和指标。然后学习足够的 Python 来构建一个 Streamlit 应用，再学习 RAG 和混合搜索以理解 Cortex Search。

在简历上，与其写“了解 Cortex”，不如描述你构建过的一个语义模型：它有多少个指标，测试集中有多少个问题，以及每次迭代后正确回答率提升了多少。

Snowflake 把 AI 工具直接放在数据旁边。因此，这些岗位招聘的是能够解释客户数据表含义的人。
