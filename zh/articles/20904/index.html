从售前到 FDE｜与售前工程师的区别以及跳槽中受认可的经验

原标题：プリセールスからFDEへ|セールスエンジニアとの違いと転職で評価される経験

FDE Talent編集部 · 2026-10-08 · 约 29 分钟读完

摘要

文章基于OpenAI、The Pragmatic Engineer及日本多家公司2026年10月的FDE招聘信息，梳理售前工程师与前沿部署工程师的边界：售前以成单为终点，FDE则在成单后进入客户生产环境直接写代码并负责系统持续运行，还需把客户侧经验反馈给产品团队。两者评价标准也不同，FDE以生产环境实际使用效果衡量，而非成单额。文章指出售前经验（PoC设计、客户决策结构理解、企业级协调）是转岗优势，但需补足API、SQL、Python等实现能力；国内SaaS公司门槛较低，Databricks、Notion等外企则要求生产级代码。最后给出简历重写与转岗步骤建议。

要点

  • 售前止于成单，FDE负责客户生产环境的实现与持续运行。
  • OpenAI的Colin Jarvis称FDE比SA更动手、处理更模糊的问题。
  • アンドパッド、Channel Talk等明确将售前经验列为FDE必备条件。
  • Databricks要求8年以上经验，Notion要求生产级代码能力。
  • 简历应围绕PoC落地生产、影响决策与产品反馈来重写。

撰写・审校：FDE Talent编辑部/以各公司官方招聘信息、官方发布等一手信息作为出处明确标注

从售前、售前工程师、客户工程师、客户成功等“面向客户的技术岗位”转型为FDE（Forward Deployed Engineer），是2026年FDE跳槽中最常见的经历模式之一。很多人已经无数次通过演示和PoC展示过价值，但在进入正式实施之前就交接给了实施团队，因此怀有“想负责到最后”的动机，而FDE正是承担这“最后一段”的职位。不过，FDE与售前在参与终点、代码所有权、评价标准上存在明确差异，如果不理解这一点就跳槽，就会出现“和想象中的工作不一样”的情况。

本文以OpenAI的FDE部门负责人的发言（The Pragmatic Engineer）、The New Stack的解读，以及andpad、Channel Talk、RevComm、Databricks、Notion、Anthropic在东京公开的招聘信息（均为2026年10月时的记载）作为一手信息，整理售前类岗位与FDE的边界、跳槽中受认可的经验、需要补足的实施能力，以及简历的重新叙述方法。

本文要点

  • 售前（售前工程师・解决方案架构师）与FDE最大的区别在于参与终点：售前的工作是在签约之前“展示可行”，而FDE则在签约之后在客户的生产环境中编写代码，并对“持续运行”负责到底。
  • 在OpenAI领导FDE部门的Colin Jarvis在接受The Pragmatic Engineer采访时解释说，SA（解决方案架构师）是顾问角色，很少在客户的基础设施上编写代码，而FDE则直接在客户的基础设施上编写代码，并处理更加模糊的状况。
  • 在日本，截至2026年10月，andpad将“IT解决方案的售前、导入咨询或系统工程师的实务经验”，Channel Talk将“Presales / Solution Engineer / Technical Consultant / CSM 等”的企业客户应对经验，分别列为FDE招聘的必备条件，售前经验作为入口被明确认可。
  • 另一方面，Databricks的东京FDE招聘要求8年以上的经验以及使用Python、Scala等的编程能力，Notion的东京FDE招聘要求能编写生产级质量的代码，因此停留在PoC阶段的人需要有意识地积累“在生产环境中运行并运维的经验”。
  • 在简历中，不以“签约金额”而是以“自己设计的PoC如何走向生产环境”“如何推动客户的决策”“向产品反馈了什么”为主线重新叙述，会更符合FDE的选拔标准。

结论：售前与FDE的分界线在于“是商谈之前还是之后”以及“代码由谁负责”

售前（售前工程师、解决方案架构师、解决方案工程师）是与销售配合、在签约之前消除技术层面疑虑的岗位。FDE则是在签约之后进入客户现场，负责到让自家产品在客户的生产业务中实际运行为止的岗位。两者在“用技术解决客户课题”这一出发点上是相同的，但工作在哪里结束、代码由谁负责、以什么标准评价却不同。

The Pragmatic Engineer指出，“Agent engineer”“Solutions Architect”“Sales Engineer”“Technical Delivery Engineer”等岗位与FDE相当接近，其区别在于FDE在与客户合作的同时，也为自家销售的产品做出贡献。也就是说，售前经验者转向FDE时新需要承担的是“生产环境的实施”和“对产品的反哺”这两点。

商谈前（售前）与商谈后（FDE）的分界线

最容易理解的分界线是时间轴。售前的工作以签约为节点结束，之后交接给实施团队或客户成功。FDE的工作则在签约之后全面展开，并在生产运行之后仍持续进行。

The New Stack解释说，FDE在客户的环境中工作，以“让系统在生产环境中运行并持续运行”为明确目标。根据该报道，FDE参与客户的沟通渠道，与客户的产品・工程团队紧密合作，直接用客户的数据和系统进行构建。不仅参与决定应该构建什么的判断，还承担从构建、集成到上线后稳定的责任，成功与否不是以投入的时间来衡量，而是以系统被使用的程度和运行状况来衡量。

同一篇文章还阐述了与传统咨询的区别。顾问在固定期限内工作，以交付物接受评价；而FDE则以系统上线后是否持续运行、持续创造价值来接受评价，工作不会因交付而结束。售前工作在以“接单”这一交付物为节点这一点上，其结构更接近顾问，而非FDE。

也有“FDE参与商谈过程”的情况

不过，有时仅凭时间轴无法完成划分。据The Pragmatic Engineer报道，当客户犹豫能否用好产品时，销售会提议配备FDE来成功完成集成。也就是说，FDE会在商谈后半段介入，还承担着作为接单决定性因素“展示在生产环境中实际运行”的角色。对有售前经验的人来说，这是最容易发挥自身经验的场景。区别在于，在那里做出的东西是否由自己一直带到生产环境。

Anthropic在东京招聘的“Applied AI Engineer”（2026年10月时点）就是这种边界体现在职位名称中的例子。招聘启事中的职责包括“作为正在评估Claude的潜在客户的主要技术顾问开展工作”“与客户经理紧密协作以理解客户需求”“开发定制试点、原型和评测套件以推动客户采用”，此外还写道“在部署期间以及生产上线后，作为持续的技术顾问开展工作”。从向潜在客户提案到上线后的建议都由一人承担，必备条件中列有“担任技术产品经理、前沿部署工程师或平台工程师的经验”以及“精通Python”。

从“展示能运行”到“在生产环境中运行”：代码所有权与责任范围的差异

最直截了当地阐述售前与FDE区别的，是在OpenAI领导FDE部门的Colin Jarvis。他在接受The Pragmatic Engineer采访时表示，FDE比SA（解决方案架构师）更偏动手实践，并在比SA传统上所处理的更模糊的情况下工作。

“SA的角色接近于顾问，很少在客户的基础设施上编写代码，通常使用匿名化或离线的数据切片来构建MVP或PoC。相比之下，FDE要动手得多，直接在客户的基础设施上编写代码，为此会使用客户的工具。”

这段话中包含了从售前转向FDE的人所面临的三个变化。

  • 数据变成真实的：处理的不再是PoC中使用的匿名化数据或样本数据，而是客户的真实数据（包括缺失、权限、遗留格式）。“演示中能跑通”不再奏效
  • 环境变成客户的：不再是在自家的沙箱中，而是在客户的基础设施和工具链（CI/CD、认证、监控、安全策略）的约束下编写代码
  • 代码由自己持续持有：PoC会随接单一并交出，而FDE拥有生产代码，对上线后的故障、改进、交接都要负责

在日本的招聘启事中，这种对“生产环境”的要求也有明文规定。Notion东京的前沿部署工程师职位（2026年10月时点）将该角色定义为“领导最复杂客户项目的动手技术交付”，业务内容包括“编写和维护定制代码”“设计和部署生产级定制Agent与AI工作流”“构建数据管道”“解决围绕规模、权限、治理的复杂问题”。必备条件中要求“精通至少一种编程语言（如Java、JavaScript、Node.js、SQL、Python），并且不排斥在面向客户或内部的工程中编写生产级代码”。

Databricks东京的FDE职位（2026年10月时点）则更加明确，将首要职责定为“Production Solution Delivery（生产解决方案交付）”，并写道“交付生产级系统、参考架构、定制应用、数据摄取以及ML/AI模型集成”。其中还有“Own the Architecture（拥有架构）”一项，期待其成为设计决策的所有者。

还要承担将经验反哺产品的责任

FDE与售前的另一个不同点，是将在客户现场获得的知识反哺到自家产品中的责任。The Pragmatic Engineer介绍了OpenAI的FDE团队在语音自动化项目中收集性能数据，与研究部门协作，为所有客户改进Realtime API的例子。在日本的招聘启事中，andpad也明确写道“将在现场最前线获取的‘第一手信息’反馈给开发团队，推动下一代产品进化”，Channel Talk也明确列出了“向Product / Engineering团队联动客户反馈”这一业务。售前中需求也会通过销售传达，但FDE凭借自己实现的结果，处于能够影响产品规格的立场。

是否有配额（销售目标）及评价标准的差异

售前一般隶属于销售组织，其评价与所负责销售的接单、销售目标挂钩。即使公司不直接给个人设定配额，评价的核心仍是“对接单贡献了多少”，这一点不变。FDE的评价标准则不同。正如The New Stack所述，FDE以“系统被使用了多少、运行得如何”来衡量，而不是以投入的时间，也不是以接单。

不过，FDE并非与销售额脱钩。The Pragmatic Engineer介绍的Ramp的FDE职位，将“与销售、GTM团队紧密协作，促成有吸引力的项目成交，激活客户，并随时间扩大Ramp所提供的价值”列为业务内容。其结构是：FDE的介入促成接单，上线后的扩展（expansion）也随之推进。区别在于，FDE的贡献不是以“接单金额”来评价，而是以“在生产环境中实际运行所带来的持续与扩展”来评价。

作为跳槽判断依据，重要的是这一考核维度的差异会区分出“适合与不适合”。在签约瞬间感受到成就感的人更适合售前；而觉得“签约后自己就离开很不甘心”“希望在生产环境跑起来之后获得客户感谢”的人则适合 FDE。

售前、CE 经验能成为优势的场景

转型为 FDE 的售前、客户工程师（Customer Engineer）出身者，拥有纯软件工程师出身者所不具备的优势。在 FDE 招聘启事所要求的能力中，以下 4 项正是售前工作中培养出来的。

1. PoC 的设计与“用能跑的东西达成共识”的能力

Andpad 的 FDE 招聘启事（截至 2026 年 10 月）将“用『能跑的东西』达成共识、原型思维的沟通能力”列为必备要求。Channel Talk 的 FDE 招聘启事也明确将“PoC（Proof of Concept）的设计与推进”写入职责。从“验证什么才能让客户做出决策”倒推来设计 PoC 的能力，是售前的核心技能，在 FDE 工作中也可以直接沿用。

2. 理解客户的决策结构

谁掌握预算，谁拥有技术上的否决权，谁在现场使用。解读这种结构的能力，对于 FDE 确定“应该做什么”不可或缺。Notion 东京的 Forward Deployed Architect 招聘启事（截至 2026 年 10 月）将“把模糊的客户目标转化为明确的工作流、实施计划、解决方案架构和可衡量的成功标准的能力”，以及“梳理现有工作流、识别客户痛点、理解运营模式、显性化技术约束、定义切实可行的未来图景的咨询式调研（Discovery）技能”列为必备要求。这正是售前的 Discovery 工作。

3. 企业级客户应对（安全、遗留系统、众多利益相关方）

Channel Talk 的 FDE 招聘启事将“在 Enterprise Deal 中，从遗留系统到最新 SaaS，从技术和安全角度进行提案与陪跑”列入职责；Databricks 的招聘启事则要求“与企业级客户合作、管理众多利益相关方之间冲突的经验”。RevComm 的 FDE 招聘启事（截至 2026 年 10 月）也将“与多个利益相关方达成共识的能力”列为必备。在企业级售前中，在信息系统部门、安全部门、业务部门之间进行协调的经验，在 FDE 选拔中会得到明确认可。

4. 业务与技术之间的翻译

Andpad 在职责中写明“业务与工程之间的翻译：弥合『能做什么（技术）』与『该做什么（业务）』之间的差距，绘制可实现的路线图”，并将“能与工程团队平等对话、将技术约束转化为业务价值的翻译能力”列为必备要求。把技术翻译成经营课题的语言、把经营课题翻译成技术需求的工作，正是售前每天都在做的事情。

关于客户成功（CSM）出身者：Channel Talk 在必备要求的示例中包含了「CSM」。见证上线后的落地与扩展的经验，会在 FDE 于生产环境上线后继续陪跑的场景中发挥作用。不过，如果技术实现经验较少，下一节“需要补足的实现能力”的比重就会加大。

需要补足的实现能力的参考标准

售前出身者在 FDE 选拔中落选的最大原因，是实现能力的证明不足。日本的 FDE 招聘启事对所需实现能力水平的要求差距很大。瞄准哪个水平的职位，决定了需要补足的量。

Notion Forward Deployed Engineer（东京）必备：熟练掌握 Java、JavaScript、Node.js、SQL、Python 等至少一门语言，能编写生产级质量的代码。具备 API 与数据集成的动手经验。5 年以上客户对接或 FDE 经验必须能编写生产级质量的代码
Databricks FDE（东京）必备：数据工程、数据平台、软件工程领域 8 年以上经验。使用 Python、Scala、JavaScript/TypeScript 编码，深入掌握 2 个以上云平台及 Apache Spark，具备生产部署的 CI/CD 经验与资深工程师同等水平
Anthropic Applied AI Engineer（东京）必备：精通 Python。欢迎：近期使用 LLM 构建生产系统的经验Python 为必备。最好有 LLM 生产环境构建经验

从这张表中，可以看到有售前经验者的现实切入点。国内SaaS的FDE（Andpad、Channel Talk、RevComm）要求具备售前、导入咨询或客户成功（CS）的经验，实现能力只需达到“能读写代码”“有API对接和SQL的实务经验”的水平即可入门。而外资平台企业的FDE（Databricks、Notion FDE）则要求生产级质量的代码或相当于资深工程师的经验，从售前直接转型需要补充实现经验。

最低应具备的3项能力

  • 01亲手完成API对接和数据处理：Webhook、REST API的对接，用SQL进行数据提取和关联，用Python做预处理，要达到能说“是我写的”而不是“我配置的”状态。RevComm、Channel Talk、Andpad的要求在这一步就能满足
  • 02至少有一段进入生产环境的经验：在以PoC结束的项目中，哪怕只有一个，也要积累让它在生产环境中运行、并参与到故障处理和改进中的经验。可以争取在公司内部跟随实现团队一起工作，或主动提出负责PoC向生产环境的迁移
  • 03以生产级质量构建包含LLM的应用：完整做出一个包含认证、错误处理、评测（衡量运行正确程度机制）的应用。Anthropic、OpenAI等AI企业的FDE和应用 AI 工程师职位非常看重这一点

要求售前经验的FDE招聘启事（截至2026年10月）

以下从官方招聘启事中引用日本FDE招聘中明确将售前、客户对接技术岗位经验列为必备条件的职位。以下内容均为截至2026年10月的信息，应聘前请务必确认原文。

Andpad Forward Deployed Engineer（FDE）

这是伴随建筑行业专用AI项目“ANDPAD Stellarc”启动而进行的招聘。必备条件的第一条是“具有IT解决方案售前、导入咨询或系统工程师的实务经验”，其后是“‘能读/能写代码’的技术素养”“用‘能运行的东西’达成共识、具备原型思维的沟通能力”。优先条件包括“在建筑、制造、物流等‘非办公人员’领域的DX项目经验”“ERP系统更新或核心系统对接等大规模系统导入、对接项目的PM/PL经验”，整体上是售前和导入的企业级经验可直接获得评价的结构。薪资未公开（根据经验和能力决定，包含每月45小时的固定加班津贴），工作地点为东京都港区。

Channel Talk 开发-Forward Deployed Engineer（FDE）

这是随着企业级客户增加而新设的职位，负责“从技术层面主导导入、实施和应用”。必备条件的第一条是“在SaaS/IT行业具有企业级客户对接经验（Presales/Solution Engineer/Technical Consultant/CSM等）”，其后是“有整理和结构化客户课题、并从技术角度提出解决方案的经验”“对API/系统对接的基本理解”。工作内容包括“API/Webhook/外部系统对接支持”“PoC（Proof of Concept）的设计与推进”“向Product/Engineering团队反馈客户意见”。招聘启事中将FDE表述为连接客户与产品的“技术锚点”。招聘启事上未记载薪资和工作地点。

RevComm Forward Deployed Engineer（FDE）

必备条件为“在BtoB SaaS/IT解决方案领域有客户洽谈经验”“有从需求整理到设计、导入独立推进的经验”“有API对接或数据对接任一方面的经验”“有使用SQL及类似工具进行数据应用的经验”“具备与多方利益相关者达成共识的能力”。优先条件包括“在SIer/IT咨询/BPO等的现场驻场或项目推进经验”“CRM/呼叫中心领域的知识”。工作内容为“整理客户的业务需求并结构化为技术需求”“使用API对接/数据整合/Webhook等进行设计”“与PdM、开发团队对齐技术前提”，其表述更倾向于寻找能独立完成“从需求整理到导入”的人，而非单纯的售前。薪资根据经验和能力决定，招聘启事中示例年薪为1,200万日元（月薪100万日元，基本工资72万日元+加班津贴28万日元）。工作地点为东京都千代田区，并注明可完全远程办公。

Notion Forward Deployed Architect（东京）

虽然职位名称是“Architect”，但这是与售前、客户工程师经验者最接近的职位。必备条件为“在技术服务/咨询、解决方案架构、实施、客户工程或类似的客户对接岗位工作5年以上”，并明确注明“无需编写生产代码”，但要求“能够推理技术约束并进行有效的故障排查”。其中写道，在需要更深入工程能力的场景（迁移、API约束、安全架构）中将与前沿部署工程团队协作，这是将FDE与FDA配对的设计。日语的读写和会话流利度为必备条件，招聘启事中标注有“#LI-Onsite”。

如上所述，同样是冠以“Forward Deployed”之名的招聘，对实现能力的要求因公司和职位而有很大差异。从售前转型时，现实的做法是先选择凭借自身实现能力能够入门的职位，入职后积累生产环境的实现经验，再向更偏实现方向的职位或企业发展。

在简历中的重新表述

售前的简历通常以“负责的项目数量和签单金额”来撰写。在FDE的选拔中，这种写法很难获得好评。受到评价的是“做了什么，它在生产环境中表现如何”“如何推动客户的决策”“向产品反馈了什么”。即使是同样的经验，也需要改变表述方式。

プリセールスの経験のFDE向けの語り直し
售前工程师式的写法面向 FDE 的重新叙述
全年技术支持○场商谈，提升成单率设计○个 PoC，其中○个进入生产环境。具体写出生产迁移中出现的问题（数据质量、认证、性能）以及自己参与的范围
为大型制造企业进行演示并贡献成单分别识别客户信息系统部门、安全部门和业务部门的顾虑，写出是用哪些技术证明（本地部署连接验证、审计日志展示等）推动了决策
解答产品的技术问题写出客户反复提出的需求中，哪些向产品团队做了提案、如何反映到规格中（或被否决的理由）
搭建 PoC 环境明确写出使用的语言、API、数据平台，诚实区分自己编写的代码范围（集成部分、数据转换、评测脚本等）和未动手实现的部分
与客户建立关系写出如何把模糊的需求（“想用 AI 做点什么”）落地为可验证的问题（“以问询分类准确率○%为目标”），以及这一过程

尤其重要的是，对进入生产环境的项目的描述。The New Stack 引用一线 FDE 的话说：“模型通常是最干净的部分。难点在于找到那些没有人文档化的工作流、人们实际信任的数据源，以及知道该流程为何如此的人。”如果你有参与 PoC 之后这类“寻找”工作的经验，就可以作为 FDE 经验来讲述。

面试中会被问到的“为什么离开售前”

在 FDE 面试中，几乎一定会被问到从售前转型的理由。如果能结合一个实际让你感到遗憾的项目，讲述“工作止步于成单让人不够满足”“想亲手把事情推进到在生产环境跑起来”“想把客户现场的经验反哺到产品中”其中之一，会更有说服力。反之，如果把“想远离销售目标”“和销售配合太累了”作为主要理由，由于 FDE 也是与销售紧密协作的职位，评价会降低。

从售前转型 FDE 的步骤

  • 01 在现职创造一个“进入生产环境”的经验：作为实现团队的一员，参与自己设计的 PoC 的生产迁移。这将成为简历的核心
  • 02 准备实现能力的证明：准备自己编写的 API 集成、SQL、Python 数据处理成果物，并做一个嵌入 LLM 的应用程序
  • 03 确定目标岗位的水准：根据自身实现能力，在要求售前经验的国内 SaaS（Andpad、Channel Talk、RevComm 等）、要求生产级代码的外企（Notion FDE、Databricks）、以及从提案到生产后都由一人负责的 AI 公司（Anthropic Applied AI Engineer）之间选择
  • 04 重新叙述简历：不以成单金额，而以 PoC 的设计、到达生产环境、推动决策的方式、对产品的反哺来撰写
  • 05 用一个项目讲清转型理由：具体准备一个“想坚持到最后”的项目

FAQ

常见问题

Q 售前和 FDE 有什么区别？

最大的区别在于参与的终点和代码的所有权。售前是在成单前消除技术顾虑的职位，PoC 和演示通常使用匿名化数据或自有环境制作。FDE 则在成单后直接在客户的生产环境中编写代码，并对生产上线后的稳定和改进负责。OpenAI 的 FDE 部门负责人解释说，SA 是顾问角色，很少在客户基础设施上写代码，而 FDE 会在更模糊的情况下直接在客户基础设施上编写代码。

Q 售前工程师可以转型为 FDE 吗？

可以。截至 2026 年 10 月，Andpad 将“IT 解决方案的售前、实施咨询或系统工程师的实务经验”、Channel Talk 将“Presales / Solution Engineer / Technical Consultant / CSM 等”的企业客户支持经验列为 FDE 招聘的必要条件。不过，是否有 API 集成、SQL、Python 等实现经验，以及是否有把 PoC 推进到生产的经验，会大大影响通过筛选的难易度。

Q 客户工程师（CE）和 FDE 一样吗？

重叠部分很多，但并不相同。客户工程师以实施后的技术支持和现有功能的运用为主，通常不会在客户环境中编写并拥有生产代码。FDE 负责生产实现，并承担把获得的经验反哺到自家产品的责任。Notion 的 Forward Deployed Architect 招聘将“客户工程”经验列为必要条件，CE 经验作为进入 FDE 类职位的入口受到认可。

Q FDE 有配额（销售目标）吗？

FDE 的评价标准是系统是否在生产环境中被使用并持续产生成果，而不是成单金额。不过也并非与销售无关，The Pragmatic Engineer 介绍的 Ramp 的 FDE 招聘把与销售和 GTM 团队协作推动项目成交、扩大客户价值列为职责。请理解为：贡献不是以成单本身衡量，而是以在生产环境运行所带来的持续使用和规模扩大来衡量。

Q 从售前转型 FDE，需要多强的编程能力？

因目标岗位而有很大差异。国内 SaaS 的 FDE（Andpad、Channel Talk、RevComm）以代码读写、API 集成、用 SQL 活用数据的水准即可入门。Notion 的东京 FDE 招聘要求能编写生产级代码，Databricks 的东京 FDE 招聘要求 8 年以上经验和 Python、Scala 等编程能力，以及 Apache Spark 的深入经验。建议至少准备一份自己编写的 API 集成和数据处理成果物，以及一个进入生产的经验。

Q 客户成功（CS）可以成为 FDE 吗？

Channel Talk 的 FDE 招聘在必要条件的示例中包含“CSM”，关注实施后的落地和扩展的经验会受到认可。不过，CS 出身者往往实现经验较少，因此以补充 API 集成、SQL、Python 的实务经验为前提。建议先从现职开始，扩大自己亲手进行技术配置和集成的范围。

Q：可以在简历中写合同金额吗？

可以写，但仅凭这一点不会得到评价。FDE 选拔中考察的是：你设计的 PoC 中有多少进入了生产环境、在生产迁移中你参与了哪些课题、你用哪些技术验证推动了客户的决策、你将哪些需求反馈到了产品中。合同金额仅作补充，请以这些内容为主线重新组织叙述。
