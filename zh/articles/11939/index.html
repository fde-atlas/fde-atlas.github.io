SQL 窗口函数

原标题：SQL Window Functions

FDE Interviews · 2026-06-14 · 约 7 分钟读完

摘要

这篇教程讲解 SQL 窗口函数与 GROUP BY 的核心区别：窗口函数不折叠行，可在保留每行数据的同时做排名、相邻比较和累计求和。文章拆解 OVER 子句的三个部分（PARTITION BY、ORDER BY、frame），对比 ROW_NUMBER、RANK、DENSE_RANK 的差异，并用六行示例演示默认 RANGE frame 在同日订单时会高估累计值，强调显式声明 ROWS frame。还指出 WHERE 无法过滤窗口结果、需用 CTE 或子查询等常见误区，以及面试中的高频考点。

要点

  • 窗口函数不折叠行，与 GROUP BY 的本质区别在于保留每行。
  • OVER 子句由 PARTITION BY、ORDER BY 和 frame 三个部分控制。
  • ROW_NUMBER 唯一、RANK 跳号、DENSE_RANK 不跳号，按场景选择。
  • 默认 RANGE frame 会把同键行合并，累计求和应显式写 ROWS。
  • WHERE 不能过滤窗口结果，需在外层查询或 CTE 中过滤。

窗口函数在与当前行相关的一组行上计算一个值，而不会把这些行折叠起来，因此你可以在保留每一行的同时进行排名、与相邻行比较或计算累计总和。它们是分析师用纯 SQL 回答“和什么相比？”这类问题的方式，而大多数面试官正是用它们来区分“会 SQL 的人”和“只会 GROUP BY 的人”。

讲稿

找出每个客户金额最高的一笔订单。现在要求在不丢弃其他行的情况下完成。这个追问正是 GROUP BY 做不到而窗口函数能做到的场景，这也是为什么大多数面试官用窗口函数来区分“会 SQL 的人”和“只会 GROUP BY 的人”。

GROUP BY 每组只返回一个数字，并把明细行丢掉。窗口函数问的是另一个问题：对于每一行，它所在的组在它周围是什么样子？而且它会保留这一行。正是“不折叠”这一个特性，使得排名、逐行比较和累计总和成为可能，而且只需对数据做一次遍历。

你需要附加一个 OVER 子句。它有三个旋钮。PARTITION BY 把行拆分成相互独立的组，就像一个不折叠的 GROUP BY。ORDER BY 对每个分区内的行排序，这正是“前一行”和“累计总和”有意义的前提，因为如果分区内没有顺序，就不存在“之前”这个概念。frame 则限定函数能看到多少行。然后结果被附加到该行上。

三个排名函数最容易让人搞混。以 100、100、90 为例。ROW_NUMBER 给出 1、2、3，并列时以任意方式打破平局，所以结果总是唯一的。RANK 给出 1、1、3，因为并列共享同一个名次，然后跳号。DENSE_RANK 给出 1、1、2，没有跳号。所以，当你想要每个客户最新的一行时用 ROW_NUMBER，而在构建排行榜时用 RANK 或 DENSE_RANK。

这里是每个客户消费金额的累计总和：对 amount 求 SUM，按客户分区，按日期排序。然后是大家常跳过的部分：显式指定 frame，即 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。如果省略它，会得到一个不同的默认值，下表用六行实际执行的记录展示了这一点。

六笔订单。客户 A 有两笔在同一天。使用 ROWS 时，第二行读出 160，即两笔订单之后的总和。默认的 RANGE frame 给出 200。第九天的两笔订单共享排序键，所以 RANGE 把它们视为一个桶，60 那一行已经包含了 40。在每日销售报表中，这相当于提前一天报告了总额，而且不会报任何错误。

还有一个陷阱。你不能在 WHERE 中对窗口函数的结果进行过滤，因为窗口函数是在 WHERE 之后才计算的。要只保留排名第一的行，需要把查询包在 CTE 或子查询中，然后在外层进行过滤。另外，OVER 内部的 ORDER BY 只为计算而对行排序，所以你的最终输出仍然需要在顶层有自己的 ORDER BY。

在面试中，直截了当地说：GROUP BY 会折叠行，窗口函数保留每一行。而计算累计总额时，要明确写出 ROWS，因为默认设置会把排序键相同的行归为一组。六行示例见 fdeinterviews.com。

TL;DR: 窗口函数在由 OVER (PARTITION BY ... ORDER BY ...) 定义的行窗口上执行计算，同时保留输出中的每一行输入。正是这个特性——不折叠行——将它与 GROUP BY 区分开来，并使得排名、行间比较和累计总额可以在一次查询中完成。

核心概念

将第 6 步与 GROUP BY 在同一位置的做法进行对比。这唯一的差异——附加而非折叠——正是窗口函数存在的全部意义。

GROUP BY

回答的是“每组一个数字”，并丢弃明细行。窗口函数回答的是“对于每一行，它所在的组是什么样子”，并保留该行。你将一个

OVER

子句附加到聚合函数或排名函数上，SQL 就会针对结果集的一个切片而不是整张表来计算该函数。

这个

OVER

子句有三个旋钮。

PARTITION BY

将行拆分为相互独立的组（就像一个

GROUP BY

但不折叠）。

ORDER BY

对每个分区内的行排序，这正是“上一行”和“累计总额”有意义的原因。帧（

ROWS BETWEEN ...

）限定了函数相对于当前行能看到多少行。

RANK() OVER (PARTITION BY dept ORDER BY salary DESC)

三个排名函数容易让人混淆。给定值 100、100、90：

ROW_NUMBER

给出 1、2、3（任意打破平局，始终唯一）。

RANK

给出 1、1、3（并列共享排名，然后跳号）。

DENSE_RANK

给出 1、1、2（并列共享，不留空隙）。当需要“每个客户最新的一行”时选

ROW_NUMBER

，排行榜则用

RANK

/

DENSE_RANK

。

LAG

和

LEAD

从分区中向前或向后第 N 行提取值，这是无需自连接就能计算差值（今天对比昨天）的干净方法。

一个完整示例

按金额对每个客户的订单排名，并随时间累计他们的消费总额。

SELECT
  customer_id,
  order_date,
  amount,
  ROW_NUMBER() OVER (
    PARTITION BY customer_id ORDER BY amount DESC
  ) AS amount_rank,
  SUM(amount) OVER (
    PARTITION BY customer_id ORDER BY order_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS running_total,
  amount - LAG(amount) OVER (
    PARTITION BY customer_id ORDER BY order_date
  ) AS delta_vs_prev
FROM orders;

每一条原始订单行都保留下来。

amount_rank

在客户内部按金额排序；

running_total

按日期累计；

delta_vs_prev

在客户的首笔订单上为 null，因为没有前一行。注意累计总额上显式指定的帧：使用

ORDER BY

而不指定帧时，默认是

RANGE UNBOUNDED PRECEDING AND CURRENT ROW

，它会把

order_date

中的并列值视为一个桶，可能悄悄地夸大总额。明确写出

ROWS

是更安全的习惯。换成

ROWS BETWEEN 6 PRECEDING AND CURRENT ROW

后，同一个

SUM

在除以行数时就变成 trailing 7 行移动平均。

在六行数据上运行，帧的警告就不再抽象了。客户 A 在同一天有两笔订单，这正是区分

ROWS

和

RANGE

:

CREATE TABLE orders (customer_id TEXT, order_date TEXT, amount INT);
INSERT INTO orders VALUES
  ('A','2026-01-05',100), ('A','2026-01-09',60), ('A','2026-01-09',40), ('A','2026-01-20',120),
  ('B','2026-01-03',70),  ('B','2026-01-11',70);

在上面的查询中再加一列

SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS default_frame_total

，不显式指定帧，在 SQLite 上（已执行）得到如下结果：

读第二行。显式

ROWS

框架给出 160，即两笔订单后的累计值。默认

RANGE

框架给出 200，因为 2026-01-09 的两笔订单共享排序键，

RANGE

把它们视为同一个桶，所以 60 那一行已经包含了 40。在每日销售报表上，这相当于提前一天报告了总额，而且不会报任何错误。这个并列还暴露了另一个问题：

delta_vs_prev

在这两行上的结果取决于 SQL 恰好先访问哪一行，因为仅凭

ORDER BY order_date

无法决定这一点。只要

ORDER BY order_date, order_id

或累计总额必须可复现，就应加上打破并列的排序键（

LAG

）。

为什么面试官会考察这一点

这是检验真实 SQL 熟练度最快的方式。如果有人为了找出“每个客户的最大订单”而去写关联子查询或自连接，那说明他们从未在实际工作中用过窗口函数。追问通常是“现在在不丢掉其他行的前提下做到这一点”，这正是

GROUP BY

无法处理而窗口函数可以处理的场景。第二个考察点：“

RANK

和

DENSE_RANK

有什么区别，对于带并列的前三名报告该用哪个？”如果你回答

RANK

，当并列值跨越截止线时，你可能返回超过三行，所以诚实的回答要说出这个权衡。

常见误解

  • “窗口函数只是一个花哨的 GROUP BY。” 它们的计算方式不同：GROUP BY 会折叠，窗口会保留。你可以在同一个查询中同时使用两者，但窗口函数在 GROUP BY 和 WHERE 之后、在已分组的行上运行。
  • “我可以在 WHERE 中过滤窗口结果。” 不行。窗口函数在 WHERE 之后求值，所以要过滤 amount_rank = 1，你需要把查询包在 CTE 或子查询中，在外层进行过滤。
  • “OVER 中的 ORDER BY 会给我的输出排序。” 它只是在计算时对窗口内部的行排序。你的最终行顺序仍需要顶层的 ORDER BY。
  • “省略框架无伤大雅。” 当存在 ORDER BY 时，默认框架是 RANGE 而不是 ROWS，它会把并列的订单键归在一起。对于累计总额，请显式声明 ROWS。

关键要点

  • OVER (PARTITION BY ... ORDER BY ...) 在保留每一行的同时计算每个窗口的值；这正是它与 GROUP BY 的根本区别。
  • ROW_NUMBER 总是唯一，RANK 在并列后跳号，DENSE_RANK 不会；根据你需要唯一性还是真正的排名来选择。
  • LAG/LEAD 用行与行之间的差值计算取代自连接；累计总额和移动平均来自显式的 ROWS BETWEEN 框架。
  • 你不能在 WHERE 中过滤窗口结果；把它推到外层查询或 CTE 中。
