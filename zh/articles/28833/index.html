原标题：Can LLM Agents Be Forward-Deployed Engineers? Requirement Discovery and Delivery for Enterprise Text-to-SQL

摘要

这篇 arXiv 论文以一个真实完成的企业级 text-to-SQL 部署项目为基准，测试 LLM Agent 能否胜任前沿部署工程师的工作。任务分两个阶段：Agent 先通过与模拟客户对话，从模糊需求中挖掘验收标准、数据权限和硬件约束；再据此规划并执行后训练方案。在 15 个模型的测试中，最强模型能找回超过 80% 的隐藏需求，开源模型仅 40-50%；交付阶段八个编码 Agent 配置中只有 25% 的运行通过全部验收标准。论文归纳出四大瓶颈：需求发现不完整（约 40% 需求缺失或失真）、执行不可靠、算力预算利用不足且缺乏系统性对比、基准准确率不等于生产可用。作者建议对发现的需求进行人工审核、监控执行计划，并明确实验环境规范。

要点

  • 以真实企业 text-to-SQL 交付项目为基准，测试 LLM Agent 能否扮演前沿部署工程师。
  • 最强模型可发现 80% 以上隐藏需求，开源模型仅 40-50%。
  • 交付阶段仅 25% 的运行通过全部验收标准。
  • 四大瓶颈：需求发现不全、执行不稳、算力利用不足、基准分数不等于生产可用。
  • 建议人工审核需求、监控执行计划并明确实验环境规范。

摘要

LLM 编程 Agent 在模型后训练自动化方面的能力日益增强，但它们能否充当前沿部署工程师（FDE）Agent——即发现客户需求并将其转化为部署决策——仍不明确。我们在一个真实的企业级 text-to-SQL 项目上对此展开研究：一个基于真实用例需求构建的模拟客户，从一个模糊的请求开始。Agent 必须在发现阶段挖掘验收标准、数据权限和硬件约束，然后在交付阶段规划并执行后训练方案。在 15 个模型中，表现最强者能发现超过 80% 的隐藏需求，开源权重模型能发现 40–50%；在交付阶段，八种编程 Agent 配置中仅有 25% 的运行通过了全部验收标准。我们识别出该项目中的四个瓶颈：（1）需求发现不完整，40% 的隐藏需求缺失或被错误呈现；（2）执行不可靠；（3）算力预算未被充分利用，且缺乏对基础模型和后训练方法的系统性比较；（4）基准测试准确率并不能保证生产可用性。我们建议对发现的需求进行人工审核，在执行过程中监控 Agent 的计划，并制定明确的实验环境规范，涵盖硬件、预算范围和生产检查。

1 引言

将一个能力强大的语言模型转化为有用的企业系统，需要理解客户的工作流程、识别运营约束，并做出将模型行为与业务需求相连接的工程决策。前沿部署工程师（FDE）通过嵌入客户团队并承担需求发现、技术设计、实现和交付的职责来完成这项工作（Vartabedian and Chernova, 2025）。这一角色由 Palantir 开创，将动手工程能力与把最初不完整的业务问题转化为可用解决方案所需的判断力相结合。

近期的行业投资凸显了这一职能的重要性。2026 年 5 月，OpenAI 宣布成立其 Deployment Company，初始投资超过 40 亿美元，以帮助组织构建和运营 AI 系统（OpenAI, 2026d）。2026 年 10 月，Anthropic 宣布投入 1 亿美元，到 2027 年底培训 10,000 名前沿部署工程师，并强调将 AI“从一个想法变为生产系统”所需的专业能力（Anthropic, 2026a）。

这引出了三个研究问题：RQ1：LLM FDE Agent 能否自动化前沿部署工程工作，即发现客户需求并交付满足这些需求的系统？RQ2：瓶颈在哪里，人工干预何时有帮助？RQ3：哪些实践能提高交付的可靠性和效率？

发现阶段，发现 Agent 将从真实项目中模拟的客户提出的模糊请求转化为已识别的需求 (1)–(4)，通过实验确定客户无法回答的问题（SQL 方言），并获得客户确认。在

交付阶段，规划 Agent 将已识别的需求转化为实验计划，执行 Agent 运行该计划，在目标硬件上进行性能分析并基于 (1)–(4) 进行评估，返回模型产物以及准确率、性能分析和成本报告。

为研究这些问题，我们以一个已完成的项目为基础，研究企业级 text-to-SQL 前沿部署工程的生产用例：一名人类前沿部署工程师向内部利益相关方交付商业 text-to-SQL 系统，包括其需求讨论、实验日志和已交付的模型。基于这一记录，我们将客户陈述的需求和运营事实标注为标准化的客户知识。

如图 1 所示，我们的 FDE Agent 分两个阶段交付解决方案：发现和交付。在发现阶段，模拟客户从一个模糊的请求开始，FDE Agent 必须通过追问来澄清需求。模拟客户使用从真实项目中标注得出的客户知识来回答 FDE Agent 的追问。最后，FDE Agent 将收集到的信息整合为一组已发现的需求。在交付阶段，FDE Agent 可以端到端地规划和执行解决方案，也可以将规划与执行分离。它首先利用发现阶段收集的需求和可用数据，制定一份涵盖模型基线、后训练、评估、性能分析和检查点选择的详细计划。最后，它不断细化并执行该计划，直至达成目标。

我们的贡献是对 FDE Agent 在真实企业 text-to-SQL 项目中的部署案例研究：(1) 使用标注的客户需求来支撑客户模拟器，并以人类 FDE 交付的系统作为交付基线；(2) 评估来自七个模型家族的 15 个 LLM Agent 的需求发现能力，衡量需求发现、通过对话进行的需求挖掘以及提问成本；(3) 在四个模型上比较自主式（端到端）和解耦式交付工作流，识别瓶颈、失败案例以及所需的人工干预。

2 相关工作

作为前沿部署工程师的 LLM Agent。

Ding 和 Zhan (2026) 在共享真实标准下，比较了 Agent 与“人类+助手”在从工单到部署的十个以 oracle 评分的阶段中交付后训练服务的情况；FDE-Bench（Ding et al., 2026）和 DeployBench（Wang et al., 2026）也对部署进行了评估。这些研究都从书面工单中给出的已收集需求开始。而我们从工单创建之前开始：Agent 通过对话和实验来定义验收标准和运营约束，以确定客户未知的事实。我们的参照是一次已完成的企业合作，包含人类轨迹和一个已在生产环境中服务的模型，而非公开数据集上的合成场景。我们基于事实清单的发现模拟设计可以推广到其他企业用例。

Agentic 后训练与机器学习工程。

2026 年的一系列基准测试探讨 Agent 能否自主进行模型后训练，包括 PostTrainBench（Rank et al., 2026）、Agent2 RL-Bench（Chen et al., 2026）、FT-Dojo（Li et al., 2026），延续了此前的机器学习工程评估，如 MLE-bench（Chan et al., 2025）、MLAgentBench（Huang et al., 2023）和 RE-Bench（Wijk et al., 2024）。每个基准都提供完整的任务规范，并以提升某个留出指标作为奖励。我们将后训练视为交付流程中的一个阶段，其验收标准由客户确定。除此之外，我们的工作还涉及迭代式需求收集，以及在自主后训练工作之前、在实际约束条件下进行技术方案探索。

对话驱动与规范欠明确的 Agent 任务。

AmbigSWE（Vijayvargiya et al., 2026）针对不完整的规范评估澄清式提问；Dialogue-SWEBench（King and Flanigan, 2026）完全移除规范，通过与基于人设、可自我修订的用户模拟器对话来评估编程 Agent；\(\tau\)-bench（Yao et al., 2025）在领域策略下针对模拟用户评估工具使用型 Agent。我们同样采用用户模拟，但将重点从澄清代码变更转移到确立部署验收标准和运营约束上，包括那些客户无法直接解决、必须由 Agent 通过实验来确定的内容。

企业级文本转 SQL。

Spider、BIRD 和 Spider 2.0 追踪 Text-to-SQL 的进展（Yu et al., 2018；Li et al., 2023；Lei et al., 2025），近期提升主要由基于执行结果的后训练驱动（Zhai et al., 2025；Yao et al., 2026）；SOMA-SQL（Somayajula et al., 2026）通过合成日志和执行探测来处理查询和模式层面的歧义；PLSQLBench 将可执行评测扩展到 Oracle PL/SQL（Liu et al., 2026）。部署准确性还取决于方言、模式、提示格式、量化和服务路径，其中若干影响已在我们的参考项目中得到记录。我们选择这一领域是因为它具有具体的生产约束和可执行的评测。

3 方法

我们将前沿部署研究分为两个阶段：发现阶段，FDE Agent 将不完整的客户需求简报转化为需求；交付阶段，将需求转化为经过后训练并已上线服务的系统。两个阶段均以一个已完成的实际项目为基础。

参考项目。

我们的参考项目是一名人类 FDE 在四个月内将一个 Oracle 方言的 text-to-SQL 模型部署到某大型企业内部生产利益相关方的项目，记录包括已确立的需求、100+ 个 LoRA 适配器和 200 次评测，以及交付的 Ministral-3 8B 系统（带有规模化扩展的独立适配器和精心设计的提示词）。我们使用这一记录来锚定客户的知识和部署约束，并为 FDE Agent 的表现建立基线。

发现阶段。

真实客户很少带着完整的需求前来。为模拟这一点，我们从参考项目中标注了 17 项核心业务、数据和评测需求，外加六项客户明确留待决定的事项，例如延迟时序边界（附录 B）。Agent 应当引导出这 17 项需求，并将六项决策记录为待定而非擅自猜测。这份经人工验证的规格说明为模拟客户提供了依据，也是发现评测的基准真值。Agent 收到一段含糊的客户开场白，必须通过对话引导出需求；我们在低、中、高三种歧义程度下测试开场白（附录 A）。

交付。

交付 Agent 接收已发现的需求和数据，必须交付一个满足这些需求的、经过后训练的 text-to-SQL 系统。我们针对这些输入比较两种工作流。在解耦工作流中，规划 Agent 生成一份结构化计划（基础模型、数据处理、后训练、评测、性能分析），该计划经校验并冻结后，再由执行 Agent 付诸实施。在自主工作流中，单个编码 Agent 在同一会话内完成规划和执行。

数据。

训练数据包含 Spider、BIRD 和 SParC（Yu et al., 2018；Li et al., 2023；Yu et al., 2019）的 Oracle 方言变体（Oracle, 2025c；Oracle, 2025a；Oracle, 2025b），其中 SParC 被扁平化为问题–SQL 对。Spider-dev 和 BIRD-dev 仅用于评测与选择。我们还纳入了来自企业客户的 100 个生产环境问题。

需求发现指标。

我们使用恢复率、引导数量和提问轮次来评估需求发现。为计算这些指标，Gemini 2.5 Flash 首先充当 LLM 评审（Zheng et al., 2023），对照经人工验证的事实清单，将每个被隐藏的事实标注为是否在提交的需求中被一致捕获，以及是否在客户对话中被披露。恢复率是正确提交的被隐藏事实所占比例；引导数量是既在对话中被披露又被正确提交的被隐藏事实数量；提问轮次统计澄清操作的次数，每次操作可能包含多个问题。对 3 个模型需求发现结果的人工审计与 LLM 评审在 70.6% 的恢复标注和 82.4% 的披露标注上一致（附录 C），为这些标注提供了支持。

交付指标。

我们报告 Spider-dev 和 BIRD-dev 上的执行准确率（EX）、生产 SQL 的编译失败率，以及在指定的纯 CPU 环境中生产 SQL 的 p90 推理延迟。目标为 Spider-dev 执行准确率 \(\geq 60\%\)、生产 SQL 编译失败率 \(\leq 10\%\)，以及 p90 延迟 \(<15\) 秒。p90 延迟基于 5 次独立运行进行测量。BIRD-dev 准确率仅供参考。编译衡量 SQL 的有效性。

4.4 LLM FDE Agent 的局限性

LLM FDE Agent 仍然不可靠：表 2 中只有 25% 的运行通过。下面我们讨论失败模式及缓解策略：

需求发现不完整，且已发现的信息并不总是被移交。在 15 个模型、10 次运行中（表 7），Agent 找回了 7,050 条被隐藏事实中的 4,227 条（60.0%），仍有 40% 缺失或被错误表述。损失不仅发生在提问环节：在客户披露的 4,122 条事实中，有 874 条（21.2%）从未进入最终文档，而且 Grok 4.7 的极端歧义运行找回了 82% 的事实，却遗漏了延迟约束，而这对交付成功至关重要（附录 C）。

执行失败发生在工作流的多个阶段。失败包括数据库连接问题、凭据获取失败、数据预处理错误以及错误的训练实现（附录 G）。这些失败表明，可靠的自主执行极具挑战性。

GPU 预算管理在规划、执行和评估之间的协调不佳。我们观察到两类预算管理失败。第一，Agent 未充分利用可用预算：在为后训练提供 12 小时 GPU 时间的情况下，规划器安排了 10 小时的实验，但实际执行耗时不足 5 小时。剩余时间被闲置，而不是用于对比实验（附录 G.3）。第二，流水线误解了预算的适用范围：在 GLM Decoupled 实验中，GPU 运行器将 12 小时的后训练限制应用到了最终推理上，导致执行器在保存检查点后跳过了 BIRD 评估（附录 G.1）。

实验选择缺乏系统性的对比验证。基础模型在不同运行之间各不相同且没有对比，而表 2 中的所有运行都使用 LoRA SFT，尽管有可用的算力和基于执行的奖励，却从未探索 GRPO。Agent 会对比服务配置（4-bit 与 BF16 基座、8-bit 与 16-bit 适配器）以优化 CPU 延迟，却忽视了对基础模型和训练方法的类似评估，使其选择缺乏充分依据。

失败缓解。我们还建议以下人工干预措施，以进一步提高端到端通过率：（1）明确的环境配置。提供所有必需的凭据和连接信息有助于 Agent 执行规划好的工作流。附录 G.2 展示了一个由缺少凭据导致的失败。（2）在发现阶段对需求、在执行阶段对计划进行人工审查。消除已发现需求中的歧义可以减少对目标的理解偏差（附录 G.1）；审查和完善计划有助于形成合理的实验设计和切合实际的资源估算（附录 G.3）。

5 结论

我们研究了 LLM Agent 能否在真实的企业 text-to-SQL 项目中充当前沿部署工程师，并引入了一项基于经人工验证的需求和已交付系统的评估。在 15 个模型中，表现最强的模型能恢复超过 80% 的被扣留需求，开源权重模型约为 50%，但只有 25% 的交付运行满足全部三项验收标准。研究揭示了四个瓶颈：需求发现不完整、自主执行不可靠、算力利用不足且对比有限，以及从基准测试到生产环境的差距。我们建议对需求和计划进行人工审查，并对硬件、预算和生产检查作出明确规定。

局限性

这些发现基于一个有边界的企业案例研究，可能无法代表客户需求、沟通风格或组织环境的多样性。更广泛的应用应考虑所代表的是谁的需求，以及由此产生的系统是否符合受影响利益相关者的利益。

信息可得性。

交互与模型设置。

客户循环。

在每次提问动作中，Gemini 2.5 Pro 会接收当前所有可用的客户知识、客户与工程师的对话历史以及最新问题，并生成一条候选回复。问题决定相关性，而不是限制模型可以知道哪些事实。回复应自然地回答已知的被询问细节，保留未知信息，避免无关的需求罗列，并区分工程提案与客户认可。没有角色采样。客户仅有对话权限：它不能运行代码、查看仓库文件、评估模型或声称工程结果。文件通过允许的标识符提供，并通过工件动作单独发布。

Gemini 2.5 Flash 审查候选回复是否存在依据不足和信息披露违规，并标注问题目标和已披露事实的 ID。这些诊断标签不会过滤生成知识。实现中还会检查私有标注标记以及某些不可用答案/文件拦截的披露。被标记的候选回复会由 Gemini 2.5 Pro 进行一次针对性重写，并进行一次进一步审查。若仍存在阻塞性违规，则返回固定的后备回复，且不新增任何已计入的事实披露。修订后，不完整、简洁性、角色和沉浸感等标记本身不再具有阻塞性；准确但不完整的回复会连同其标记一起保留。事实审查输出格式错误会使轨迹失效，而不是表现为客户的不确定。无效的诊断标签会进行一次仅针对标签的修复；该修复失败也会使轨迹失效。只有最终交付的回复会返回给 Agent；草稿、审查标签、生成来源元数据和审查者身份仅保留在研究者日志中。

Agent 循环与访问边界。

在每一轮对话中，框架输出一个最终动作块：提问（ask）、请求（request）、检查（inspect）或提交（submit）。提示词要求恰好一个最终块；解析器选取最后一个动作块，并要求它终止响应。未被派发的提问载荷（ask payload）包含的问题不会被单独送达。上限为 28 个外层轮次和 15 个初始提问动作，而非 15 个单独的疑问句；一个提问动作可以打包多个相关问题。当前运行器在提交后即停止，不会使用配置的预留问题或送达反馈钩子进行第二轮信息挖掘。

回读与恢复。

在提交时，Gemini 2.5 Flash 将每条逻辑提交行与当前可用的客户事实进行比对。对于支持的比对且不含不支持实质内容的行，程序判定为 Confirm（确认）；当某行与已知事实矛盾时，判定为 Correct（纠正），并返回标注后的答案与接受详情；否则判定为 Can't Say（无法判断）。对已标注未知事实的明确承认可以视为一致，而编造其取值则视为不支持。提交中任何位置的矛盾都会将该事实从回读前覆盖范围中移除，即使另一行正确陈述了该事实。循环在回读后即结束，不进行代理修复。交接记录将纠正内容标记为取代相应的已提交声明，并保留未解决的决策。

设 \(W\) 为从所选开场中隐去的已知核心事实，\(S\) 为在纠正前提交的评判标准中被判定一致且未在其他地方被矛盾的事实，\(A\) 为通过提问响应首次披露的事实。恢复率为 \(|W\cap S|/|W|\)，引导并提交计数为 \(|W\cap S\cap A|\)。正确提交但未在对话中披露的事实可获得恢复分，但不能获得引导分。回读纠正单独追踪，不计入回读前恢复。覆盖范围关注核心事实 ID，而非逐条子句级的完全正确性。

模型设置。

模型通过配置的托管推理接口访问，包括适用的远程托管模型端点。标准最大新 token 基准为：代理 2,048 个 token，客户生成/修订 2,048 个，评审 8,192 个。仅在检测到截断时，标准阶梯分别以 4,096/8,192/16,384、4,096/8,192 和 16,384/32,768 重试。

验收目标与数据权限。

当前的发现标注规定 Spider-dev Oracle 执行准确率 \(\geq 60\%\) 作为开发代理门槛。BIRD-dev 准确率单独报告，不与 Spider 平均，且没有通过阈值；SParC-dev 报告为可选。生产编译错误率必须在全部 100 个生产问题上等于或低于 \(10\%\)，即最多允许十次失败。缺失或被拒绝的预测、SQL 语法/编译失败以及特定于预测的超时均计为失败。基础设施故障会使检查不完整，而不完整的评测无法确立通过。

评测协议Agent（第 2 轮）：“当语义等价的 SQL 返回的行匹配时是否应判定通过，以及行顺序、数值容差、NULL 和执行错误应如何评分？”客户（第 2 轮）：“对于开发集，我们将使用执行准确率。你们将运行生成的 SQL，并将其结果与参考 SQL 的结果进行比较。我们尚未确定匹配的具体规则，比如行顺序或数值容差。”客户（第 11 轮），在提出临时规则后：“关于结果匹配，我们尚未定义那些详细规则。”客户确定了指标，但没有确定其等价关系。Agent 提出了一个具体规则以供确认，未获得授权，并将其保持开放。最终确定的需求：定义执行结果等价性：行顺序、重复项、数值容差、NULL 和错误处理。

附录 D 发现案例研究：揭示未解决的需求缺口

恢复率评估的是 Agent 是否捕获了开场中未透露的已知客户事实。探索性对话还可以通过另一种方式提供价值：它可以识别出客户尚未有既定答案的重大决策。我们在极端模糊性的 GPT-5.6 Sol 轨迹中考察了这一行为。证据支持一个较窄的结论，即客户未曾指定这些决策，也未在对话中解决它们；它并不能证明客户此前是否考虑过这些决策。

轨迹证据。

表 9 复现了实际轨迹中在需求定稿之前的摘录，并解读每次交流确立了什么。在每种情况下，Agent 都将未解决的决策与已确立的需求区分开来，而不是默默地把提议的默认值转化为客户政策。省略号删除了相邻内容，但不改变所引用的论断。

定稿的需求包含十一个未决决策条目。除上述四组之外，它还识别出未解决的输入/输出序列化、分词器选择、Oracle 版本与资源配置、隐私与数据驻留约束、生产数据来源、第三方服务审批、最终 API 契约以及生产执行行为。有些条目包含多个相关问题，因此十一是未决决策条目的数量，而非独立潜在需求的数量。

向交付的可追溯性。

后续的交付执行说明了保留这些空白为何重要。为了推进工作，该研究采用了明确的临时规则：以 Oracle 游标解析作为编译检查、研究自定义的结果比较策略、只读准入，以及用于延迟测量的 HTTP 请求边界。延迟分析对完整的 HTTP 完成请求进行了计时，但排除了模型启动、预计算分词、预热和 Oracle 执行。它对 100 题生产工作负载进行了五次完整遍历，得到全 500 题最近秩 p90 为 16.156 秒。交付报告并未将这一操作性选择呈现为已解决的客户需求：它在操作员定义的边界下报告了测量结果，同时继续将客户计时边界标记为未解决。对于编译语义、结果等价性、序列化、分词器选择和只读策略，也保留了同样的区分。

这种来源记录为后续的客户对齐提供了有用的路径。如果客户选择了不同的编译操作、计时边界或等价性规则后验收结果发生变化，该变化可以归因于先前记录的未决决策，而不会被误认为是原因不明的模型回归。保存的轨迹展示了这种可追溯性，尽管它并不包含后续的客户决策或完成的对齐周期。

与恢复率的关系。

这一行为被有意排除在恢复率指标之外。恢复率仅统计被扣留集合 \(W\) 中在回读前提交内容里得到一致呈现的已知事实。六项明确未解决的参考决策被排除在 \(W\) 之外，新浮现的开放问题也不会获得恢复率得分。因此，该案例展示了发现质量的另一个互补维度：Agent 是否识别出实质性的欠规范问题，将未知事项与需求区分开来，并保留可复现下游交接所需的决策。

附录 E 交付工作流

起始输入与角色分离。

我们的交付 Agent 实现了解耦与自主两种设置。每种条件都从对应的极端歧义轨迹的最终发现交接内容中读取需求：提交的验收标准、客户的开放决策以及回读更正，这些内容经过规范化后作为主要需求注入规划器和执行器的提示词中。每种条件还会获得已发布的工件授权和资源约束。发现阶段的标注以及私有的模拟器/评审轨迹不作为交付输入。带版本的清单固定了源工作区的清单内容。准备工作会验证这些清单、保留已发布的证据并创建一个全新的工作区；仅准备工作本身不会启动规划、训练、数据库评估或性能剖析。所选计划保留其自身的来源记录和研究设置；不得用当前规划器的默认配置替代生成冻结计划时所用的配置。

解耦设置。

基于 OpenCode 的规划器使用受控的工具接口来检查已授权的工件并生成结构化的实验计划。其规划接口允许证据检查、草稿构建、验证和提交；不允许执行 shell、模型训练、SQL 执行或性能测量。为交付 Agent 所选的已完成计划使用了静态研究输入。规划实现也支持受控的实时文献工具用于新运行，但这并不意味着所选计划使用了这些工具。此设置使用 OpenCode 规划基线，而非早期的轻量动作循环规划器。

The accepted plan is frozen before a fresh OpenCode execution session begins. The executor implements the plan, resolves prerequisites, and records repairs, deviations, and measured outcomes. Frozen training choices remain the starting prescription; bounded implementation changes must be documented so their effect on interpretation can be assessed. Planning and execution are separate sessions, and the executor does not inherit an earlier session’s implementation or results.

Autonomous setting.

A fresh OpenCode session first writes its own execution plan from the finalized discovery requirements, resources, and grants, then implements and revises that plan in the same session. No training recipe or training hyperparameters are supplied. The agent must select and justify its methods, hyperparameters, finite experiment strategy, evaluation rules, and cumulative budget, and record revisions and outcomes under its workspace’s work/ directory. Conditions remain independent; another condition’s implementation, checkpoints, or results are not inputs. We additionally conduct ablation experiment with same settings using Codex CLI.

Post-training resources and candidate models.

Each condition has one NVIDIA A100 with 80 GB of GPU memory and a single cumulative deadline of 43,199 seconds (strictly under 12 hours) to produce a checkpoint. The budget includes allocation setup, model loading, pilots, failed attempts, all training trials and resumes, rollouts, in-training evaluation, and checkpoint writes; it does not reset between trials. Because the allocation contains one GPU, the corresponding maximum is just under 12 GPU-hours. Eligible checkpoints are the pinned revisions of meta-llama/Llama-3.1-8B-Instruct and mistralai/Ministral-3-8B-Instruct-2512-BF16, to ensure fair comparison with the human FDE delivered model. Decoupled executions follow their frozen plan’s selection; autonomous agents choose and justify their selection within the same eligibility constraints. A budget is a ceiling, not a requirement to use the full allocation.

Separate CPU profiling.

Profiling follows checkpoint export on a separate allocation with 96 CPU cores, 32 GiB RAM, zero GPUs, and exactly one profiling thread. The delivery agent execution policy permits dual AMD EPYC 9J14 or dual AMD EPYC 9J45 systems. Executors must verify actual allocation and instruction support, record the observed hardware, and use matched hardware for before/after comparisons; the two CPU models are not assumed to have identical performance. This execution-specific policy is distinct from the historical discovery hardware annotation. CPU profiling is outside the post-training GPU deadline.

Data permissions and interpretation.

Released artifact availability does not expand training permission. Development examples, reference labels, and per-example execution feedback may support authorized evaluation and model selection, but not supervised training, preference training, RL rewards, training-data synthesis, or quantization calibration. Executors retain split manifests and record the provenance of training and calibration data. Runtime Oracle connection material remains outside model prompts and logs. A frozen plan, successful input verification, or completed preparation is not evidence of measured accuracy, latency, or acceptance; such claims require the corresponding execution and evaluation artifacts.

Data and downstream evaluation.

Training resources include 8,644 Spider examples, 9,055 BIRD examples, and 8,039 optional SParC turns. SParC turns are flattened without conversation history or rewriting, so some questions remain context-dependent; this is a modified setup rather than evaluation on the original conversational task. Training inputs pair questions with schema DDL. Execution accuracy compares predicted and reference query results on the target database. The deployment compilation-error denominator retains all 100 questions, including invalid or missing model outputs. Benchmark latencies are reported separately from deployment-workload acceptance. Downstream comparisons require a common timing boundary, warm-up procedure, decoding configuration, and timeout policy, with measurements tied to the final served checkpoint.
