Cloud Foundry 导入案例对比｜国内外企业的成果与 2026 年的迁移判断

原标题：Cloud Foundry導入事例を比較｜国内外企業の成果と2026年の移行判断

FDE総研 · 2026-11-04 · 约 11 分钟读完

摘要

本文梳理了Cloud Foundry的公开导入案例：海外多为Pivotal时代（2013—2019年）Allstate、The Home Depot、Ford、Comcast等美国大企业，日本国内则主要通过SAP BTP使用，可确认的一手案例有限。文章指出成果多来自开发体制变革与明确平台适用范围，而非平台本身性能，并提醒厂商发布的数据口径不一、不宜直接比较。2026年的商用路径仅剩VMware Tanzu与SAP BTP两条，Broadcom转向订阅制促使企业重新评估。文章提出应用同质性、既有合同、平台人员、迁移难度四轴判断法，并说明FDE在评估、应用盘点与首批迁移实现中的作用。

要点

  • 公开案例多为Pivotal时代美国大企业，日本以SAP BTP为主。
  • 成功关键在开发体制变革与限定cf push适用范围，而非平台性能。
  • 2026年商用路径仅剩VMware Tanzu与SAP BTP，Broadcom改订阅制。
  • 以应用同质性、合同、人员、迁移难度四轴决定去留。
  • FDE负责评估、应用盘点与首批迁移，并交接给客户团队。

Cloud Foundry 的引入案例中有哪些企业？

据 FDE 总研调查，公开案例大多是美国金融、零售、制造、通信行业的大型企业。在国内，主要是通过 SAP BTP 使用的案例。

Cloud Foundry 是一个开源 PaaS（应用运行平台），只需用

cf push

命令发送应用代码，即可自动完成构建、部署、路由和扩缩容。其引入案例大多公开于 2013～2019 年销售商业版的 Pivotal 公司时期，以大会演讲或该公司客户案例的形式发布。

海外：Pivotal 时期公开的大型企业案例

Allstate、The Home Depot、Ford、Comcast 等公司曾通过演讲资料和官方公告公开采用或使用 Pivotal Cloud Foundry 的情况。

企业行业公开的背景本文章中的处理方式
Allstate保险在大会上介绍内部开发组织“CompoZed Labs”的采用情况与开发体制变革一同引入的案例
The Home Depot零售在 Cloud Foundry 相关大会上演讲大规模零售平台上的采用案例
Ford汽车2016 年宣布对 Pivotal 出资，在软件开发方面开展合作事业公司对平台厂商出资的案例
Comcast通信·媒体在 Cloud Foundry Summit 上演讲通信企业内部平台的采用案例

各公司展示成果的数值（发布频率、开发周期缩短率等）大多来自厂商资料或演讲。由于测量方法和前提条件不统一，本文章不转载这些数值。如需对比，请在 Cloud Foundry Foundation 官方网站或各公司的一手资料中确认数值是何时、在什么范围内测量的。

国内：SAP BTP 与厂商提供平台是主要入口

在国内接触 Cloud Foundry 的主要途径有两个：SAP Business Technology Platform（SAP BTP）的 Cloud Foundry 环境，以及商业发行版（厂商销售的 Cloud Foundry 产品）。

SAP BTP 提供了作为应用运行环境的“Cloud Foundry 环境”和基于 Kubernetes 的“Kyma 环境”。因此，使用 SAP ERP 的国内企业在开发扩展应用时，存在未意识到自己在使用 Cloud Foundry 的情况。另一方面，国内企业以公司名义讲述 Cloud Foundry 成果的资料中，FDE 总研编辑部能确认为一手资料的非常有限。因此本文章不列举国内企业名称。

阅读案例时的注意事项

阅读案例时，区分发布者是谁非常重要。厂商的发布、用户企业本人的演讲、第三方的分析，其可信度各不相同。

信息来源类型示例阅读方法
厂商的一手发布Pivotal／VMware／Broadcom 的客户案例成果容易被正面总结。需确认测量条件
用户企业本人的演讲Cloud Foundry Summit 等演讲容易谈及问题和失败。需确认演讲年份
第三方的分析·报道调查公司报告、技术媒体确认样本范围·期间，不要推广到范围之外

公开案例大多是 2015～2019 年的。如果直接用于 2026 年的迁移判断，会与许可体系以及 Kubernetes 周边工具已成熟的现状产生偏差。

成功引入 Cloud Foundry 的组织有哪些共同点？

据 FDE 总研的整理，影响成果的不是平台性能，而是开发体制的变革，以及是否明确划定了标准化的范围。

对比阅读公开案例可以发现，几乎没有“仅引入 Cloud Foundry 就取得成果”的说法。引人注目的是那些同时改变了开发方式和团队角色分工的案例。

共同点 1：将平台团队作为面向内部的“产品”来运营

在成功案例中，平台团队将内部开发者视为“客户”。他们设定服务质量目标（SLO），并明确用户可自行使用的范围来运营。

Cloud Foundry 很早就将如今被称为“平台工程”的理念付诸实践。从一线的感受来说，如果平台团队变成接受请求后逐次处理的窗口，

cf push

的便捷性就难以发挥。

共同点 2：限定了“用 cf push 运行的应用”的范围

Cloud Foundry 适合的是像 Web 应用和业务 API 那样存在大量相似配置应用的环境。取得成果的组织没有勉强搭载其他应用。

  • 优先搭载无状态的 Web·API 应用
  • 数据库和消息队列作为外部服务，通过 Service Broker（连接外部服务的机制）分离出去
  • 需要 GPU 处理或特殊网络配置的应用，保留在另外的平台上

一开始就定好这条界线，可以避免因处理例外情况而使平台变得复杂。

共同点3：与开发方法的变革一起引入

Pivotal 时代的许多案例，都是与 Pivotal Labs 式的结对编程、XP（极限编程）以及产品型组织建设一起被提及的。

需要注意的是，很难把平台的引入效果与组织变革的效果区分开来。最好避免解读为“只要引入 Cloud Foundry 就能得到同样的成果”。

截至2026年，Cloud Foundry 处于怎样的定位？

截至2026年11月，Cloud Foundry 仍作为 OSS 持续存在。商用的主要途径有两个：Broadcom 旗下的 VMware Tanzu 和 SAP BTP。

主要事件年表

所有者和产品名称多次变更，导致案例的新旧难以分辨。

年份事件
2011年VMware 将 Cloud Foundry 作为 OSS 公开
2013年Pivotal 成立。Cloud Foundry 业务移交至 Pivotal
2015年Cloud Foundry Foundation 在 Linux Foundation 旗下成立
2018年Pivotal 在 NYSE 上市
2019年VMware 收购 Pivotal 完成
2020年商用版更名为“VMware Tanzu Application Service”
2023年IBM 终止提供 IBM Cloud Foundry（同年6月）。11月 Broadcom 完成 VMware 收购
2024年商用版重组为“VMware Tanzu Platform for Cloud Foundry”

各时期的准确日期和提供条件，请通过各公司的官方公告确认。

Broadcom 收购后的许可变化

收购了 VMware 的 Broadcom 于2023年12月宣布终止永久许可的销售，转向订阅模式。对现有用户而言，这成为重新考虑迁移的契机。

由于合同续约时费用结构可能发生变化，“是否继续使用下去”的判断不能仅从技术层面决定。具体价格因合同而异，无法通过公开信息进行比较，因此本文不作讨论。

Korifi：在 Kubernetes 上重现 Cloud Foundry 的操作体验

Cloud Foundry Foundation 正在推进一个在 Kubernetes 上

cf push

重现其操作体验的项目“Korifi”。

使用 Korifi，可以在保持开发者使用体验不变的情况下，仅将执行平台转向 Kubernetes，这是一种中间路线的选择。不过，其功能未必与传统的 Cloud Foundry 完全相同。在生产环境使用之前，需要用自己公司的应用确认其运行情况。

Cloud Foundry、Kubernetes 及其他 PaaS 应该选哪个？

基本的选择方式是：重视开发者体验的标准化就选 Cloud Foundry，重视自由度和易采用性就选 Kubernetes，小规模场景则选托管型 PaaS。

三种选项的比较

视角Cloud Foundry（Tanzu／SAP BTP）Kubernetes（EKS／GKE／AKS／OpenShift 等）托管型 PaaS（Cloud Run、Azure App Service、Heroku 等）
开发者操作以 cf push 为中心保持统一可通过清单（配置文件）、Helm 等自由搭建几乎只需 deploy 操作即可
自由度较低（刻意让用户遵循标准的设计）高低（需遵循云服务商的规范）
平台运维负担中～高（需要平台的运维和更新）高（还需选择周边工具）低
人才市场有经验者有限有经验者较多有云经验者即可应对
适合的规模拥有大量相似结构应用的大型组织中～大规模、应用种类多样小～中规模、应用数量少

FDE 总研的4轴判断法

FDE 总研考虑到现有的比较文章往往偏重“功能差异”，建议从以下4个轴进行判断。

判断轴倾向于继续使用或采用 Cloud Foundry 的条件倾向于 Kubernetes 或其他 PaaS 的条件
①应用的同质性大部分是 Java/Spring 等相似结构的 Web 应用语言和结构各异，有状态的应用较多
②现有合同与资产已有 Tanzu／SAP BTP 合同，或已熟悉构建机制（buildpack）全新引入，或续约时费用大幅变化
③承担平台的人员有平台团队，但 Kubernetes 有经验者较少能够确保 Kubernetes 有经验者
④将来迁移的难易度已完成迁移目标（Korifi 等）的验证最重视将来更换的便利性

如果4个轴中有3个以上偏向同一侧，方针基本就确定了。如果2对2持平，比较现实的做法是选取几个主要应用进行试迁移，根据实际耗费的工时来判断。

企业规模和现有资产会如何影响引入判断？

是否已有 Tanzu／SAP BTP 合同，以及能配备多少平台专职人员，会大幅改变继续使用 Cloud Foundry 的合理性。

不同前提条件下的判断参考

前提判断参考理由注意点
大企业、已在用 Tanzu在合同续约前比较“继续使用／Korifi／迁移 Kubernetes”三个方案应用数量多，一次性迁移的风险大在同一时间点比较费用估算和迁移工时
以 SAP 为中心的企业根据用途区分使用 SAP BTP 的 Cloud Foundry 环境和 Kyma 环境与 SAP 的集成容易在 BTP 上完成定期确认 SAP 方面的提供方针变化
中坚企业・新导入从托管 PaaS 或 Kubernetes 开始考虑新建基础团队的负担较大选择 Cloud Foundry 时以商业支持为前提
初创企业托管 PaaS 是基本选择没有以少数人员运营基础设施的余力在规模变大后再重新评估

现有用户考虑迁移时的步骤

现有用户不要一下子全面迁移，按以下顺序分阶段推进更安全。

  • 对应用进行盘点，将语言、依赖服务、流量、负责团队整理成清单
  • 用①〜④的判断标准，对每个应用的迁移难度进行分类
  • 用2〜3个容易迁移的应用进行试迁移，记录工时和故障的倾向
  • 从合同更新日期倒推，决定是继续使用、分阶段迁移还是全面迁移

从现场的经验来看，跳过③的试迁移容易误判工时。尤其是 buildpack 隐式代为处理的配置（运行环境的版本、证书、环境变量的传递）容易被遗漏。

FDE 在 Cloud Foundry 导入项目中承担什么？

FDE（Forward Deployed Engineer：深入客户现场进行实现的工程师）将与客户一起承担迁移可行性评估、应用盘点以及最初几个应用的迁移实现。

FDE 是由 Palantir 推广的职位。其特点是不仅止于提交资料，还要负责在客户现场做出能实际运行的东西。Cloud Foundry 的迁移和继续使用的判断涉及技术、合同和组织，因此是 FDE 式的参与方式容易发挥作用的领域。

评估阶段：盘点与 12-factor 符合度确认

在评估阶段，FDE 的职责不仅是阅读资料，还要在客户的实际环境中运行应用，确认迁移的难度。

  • 确认各应用在多大程度上符合 12-factor（面向云的应用设计12原则）
  • 将通过 Service Broker 连接的外部服务的依赖关系绘制成图
  • 掌握合同更新日期、基础团队的体制、运维规则（Runbook）的完善程度

实现阶段：在不破坏现有 cf push 运维方式的前提下迁移

在实现阶段，最大的议题是在不改变开发者熟悉的操作的情况下迁移运行平台。

整备 Korifi 或 Kubernetes 上的构建与部署机制，与客户的工程师一起迁移最初几个应用。直到将该流程移交给客户方为止为一个阶段。如果 FDE 全部自己迁移，客户方就不会留下运维的诀窍。

FDE 与其他职位的区别、适合与不适合的人

职位Cloud Foundry 项目中的主要成果物与现场的参与方式
FDE试迁移的实现与判断材料进入客户环境，一起构建
IT 咨询顾问方针与迁移计划以方针制定为中心
SIer符合需求的迁移作业在合同范围内的作业
公司内部 SWE／PdM自有应用的改修与优先级排序以自有产品为对象

按经验阶段的参考标准

  • 实务经验尚浅的阶段：先在 Cloud Foundry 或 Kubernetes 中任选其一，积累部署与运维的实务经验。
  • 已充分积累基础设施实务经验的阶段：在基础设施经验之外，如果还能处理合同和组织层面的议题，就更容易作为 FDE 获得认可。
  • 英语能力：Cloud Foundry 和 Korifi 的一手信息以英语为主。具备能阅读文档和 GitHub Issue 程度的阅读能力会有优势。

不适合的人 只想专注于基础设施搭建的人，或想避免与客户协调的人，负担往往会较大。因为 FDE 的职责不在于技术选择本身，而在于让客户能够自己运营该选择。
