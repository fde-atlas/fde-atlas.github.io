什么是 Jev？TypeSafe AI 的 System One 模型详解——写给前沿部署工程师

原标题：What Is Jev? TypeSafe AI's System One Model, Explained for Forward Deployed Engineers

FDE Interviews · 2026-09-20 · 约 22 分钟读完

摘要

本文介绍 TypeSafe AI 于 2026 年 9 月 15 日发布的 Jev，一个不生成文本、只输出带校准概率的类型化判断的 System One 决策模型。文章面向前沿部署工程师，说明其三种原语（Noul/Choice/Score）、适用场景、定价与延迟、首批独立评测结果及已知失败模式，并给出在客户流水线中放置该模型的建议。

要点

  • Jev 只做类型化判断，输出概率分布，不生成文本。
  • 三种原语：Noul 判断真假、Choice 从最多 255 个选项中选、Score 沿 2-10 级评分。
  • 定价 0.042 美元/百万输入 token，输出免费，官方称延迟约 100ms，独立实测 p50 为 236-422ms。
  • 独立零样本评测显示任务类型比模型选择影响更大；有几百到几千条标注后，普通监督模型即可追平 Jev。
  • 建议模式：控制流和副作用留在代码中，Jev 只回答循环内的窄问题，用置信度阈值决定人工介入。

实战练习：System One 决策模型的概念 · LLM 与 GenAI 问题 · RAG 与 Agent 设计问题 · 必知的 FDE 问题

Jev 是 TypeSafe AI 推出的托管 AI 模型，它做出类型化决策而非撰写文本。你向它发送一个状态（一张支持工单、一条客户记录、一段文字、一个 JSON 对象）以及一个或多个类型化问题。它返回你的代码可以直接分支处理的答案：是/否问题的概率、从封闭集合中做出的选择（附带完整概率分布），或按你定义的评分标准量级给出的分数。TypeSafe 于 2026 年 9 月 15 日在隐身运营两年后正式发布它，称之为首个 System One 模型，目前处于早期访问阶段。由于没有生成步骤，因此无需解析任何内容，模型也不可能凭空捏造你未提供的选项。对前沿部署工程师来说，有趣之处在于它的定位：它嵌入在普通软件内部，作为一个快速、廉价、带置信度的判断环节，而工作流、算术运算和副作用都留在代码中。

Jev 是什么，不是什么

这个名字源自 Daniel Kahneman 的 System 1，即快速、直觉式的思维模式，TypeSafe 的文档称其重点是快速、聚焦的判断。该模型采用公司称为“校准决策强化学习”（RLCD）的方法训练，与催生聊天模型的 RLHF 以及推理模型背后的可验证奖励训练形成对比。据公司自己的发布文章，TypeSafe 创始人 Diogo Almeida 曾在 OpenAI 参与 RLHF 研究，其主张是：聊天形态的模型并不是自动化的正确接口。

Chat and reasoning LLMs Jev, per TypeSafe's launch post and docs
训练目标人们偏好的回复（RLHF），或可验证的答案（RLVR）带校准概率的决策（RLCD）
输出字符串：散文、代码、需要解析和验证的 JSON受限于你所提供选项的类型化值

置信度被问及时过度自信且不一致每个答案都有概率分布，Choice 和 Score 还附带置信度值
最擅长人在回路中的工作、可验证的问题、原型知识丰富的人在一秒内做出的判断，嵌入在软件中
不适用于廉价、高吞吐量的结构化决策任何形式的生成、算术、日期、多跳推理

在讨论设计问题之前，有两点需要澄清。TypeScript 和 Python SDK 采用 MIT 许可证并在 GitHub 上公开；模型由 TypeSafe 的 API 提供服务，我们没有发现权重的公开发布。Jev 请求是一个函数调用，而不是工作流：持久状态、重试、事务和重放属于你的应用程序或工作流引擎。

三个原语，一个请求

每个请求携带一个状态和一组问题。每个问题看到相同的状态，独立且并行地被评估，并以你选择的键返回。

原语问题形式返回内容限制（jev-1.13）
Noul这是否为真？“客户是否请求退款？”noul，一个 0 到 1 之间的概率无单独的置信度
Choice其中哪一个？“应该由哪个团队处理？”choice，每个选项的概率，置信度最多 255 个选项
Score哪个级别？“客户有多沮丧？”沿你的级别的 score，图例，概率，置信度2 到 10 个有序级别

文档明确说明了粒度：提出一个知识渊博的人在给定正确上下文的情况下一秒钟内做出的判断。“这条消息是否传达了紧迫性？”是一个好问题。“分析这个并决定该怎么做”则不是，这是将任务拆分为小问题并在代码中组合它们的信号。这种分解不需要额外的往返，因为针对相同状态的问题是并行运行的。

一张工单，两种方式

看清差异的最清晰方法是将同一张工单通过两种形式运行。工单内容为：“嘿，我这个月被扣了两次款。有人能处理一下吗？”生成式模型通过推理来路由它：它注意到重复扣款，考虑这是账单问题还是一般支持问题，回想起账单团队处理退款，然后写出“Billing”。这是几百个输出 token、一秒或更长的延迟，以及一个你的代码必须解析并信任的字符串。Choice 问题通过评分来路由它。请求携带工单作为状态和一个包含五个选项及其标准的问题，响应是这五个选项上的一个分布、一个

choice

命名首选选项的字段，以及一个

confidence

从整个分布的形状导出的值。

图中的数字仅为示意，用于展示一个自信回答的形态，而非从 API 实际记录的数据。这些阈值来自 TypeSafe 自身在其置信度路由模式中的演算示例：低于 0.6 时，案例转给人工处理；在 0.6 到 0.85 之间时，代码对低风险决策直接执行，对中等风险决策则请求确认；高于 0.85 时，代码对高风险决策也直接执行。生成式版本口头推理的所有内容，现在要么体现在你为每个选项编写的标准中，要么体现在你的代码根据置信度所走的分支中。这就是全部的权衡：你放弃了推理过程，换来的是一个概率分布、一个阈值，以及一次成本不到一美分几分之一的毫秒级调用。

适用场景：AI 嵌入代码之中，而非代码嵌入 Agent 之中

TypeSafe 描述了三种架构。传统软件是由可靠原语构成的决策树。Agent 循环自行选择下一步操作，在有人监督时可行，无人监督时则会漂移。AI 驱动的软件——也就是本文的目标——将控制流、确定性规则和副作用保留在代码中，只在系统需要对非结构化数据做出语义判断的地方插入模型。这正是 FDE 实际交付的大多数企业自动化的形态。

置信度门槛是让这种自动化安全可靠的关键。TypeSafe 自身的银行示例采用 0.6 的下限，低于该值的一切都转给人工处理；余额查询在 0.6 时即可放行，因为最坏的情况不过是读取了错误的界面；而批准转账则要求置信度高于 0.85。阈值由你决定；让阈值随错误操作的代价而提高，才是设计的核心。

符合该形态的使用场景

最有力的用例都有一个共同特征：难点在于一个有边界的语义判断，而具有重大影响的操作仍留在代码中。以下示例来自 TypeSafe 公布的用例图谱和模式页面。

最后两行值得单独用一段来解释，因为流行的说法是“让 Jev 控制你的 Agent”，而 TypeSafe 自己的指导则更为谨慎。其构建指南指出，一个自行决定下一步的 Agent“在有人监控流程时效果良好，但每一次循环都多了一次偏离轨道的机会”，并且它推荐的设计将“控制流、确定性规则和副作用保留在代码中”。因此，决策模型并不运行循环，它只是回答循环提出的问题。函数调用 cookbook 将一个请求路由到十个交易函数之一，使用一个 Choice，其选项就是这些函数，用关于含义而非参数名的问题来填充每个参数，并将调用的置信度报告为这些判断中最不确定的那个，“因为一个错误的参数就足以毁掉整个结果”。技能推荐 cookbook 用两个请求对 182 个 Agent 技能进行排序，最多只推荐一个，并设有 0.30 的下限，低于该值则保持沉默，而且它诚实地报告了这种设计的代价：错误加载从 16.8% 降至 7.3%，不必要的加载从 9.8% 降至 4.0%，但七个原本正确的请求反而变差了，因为“一个自信的错误建议比没有建议更有说服力”。而提取级联 cookbook 则是“这需要更聪明的模型吗”这一模式的具体化：一个廉价模型负责提取，每个字段一个 Noul 询问该值是否错误，任何高于 0.7 的字段都会将整个条目发送给推理模型。每次都是同样的形态：代码掌控循环，模型在循环内回答狭窄的问题，阈值决定谁来行动。

做一点算术，仅使用标价。一个分诊流水线每月为一百万张工单各发送一个 300 token 的状态，将使用 3 亿输入 token。按标价每百万 0.042 美元计算，约为 12.60 美元，输出免费。发布博文将前沿 LLM 的输入价格定为每百万 token 0.20 至 10 美元（输出另计），因此同样的用量仅输入一项就要花费约 60 美元到约 3,000 美元。这就是为什么用例地图会谈到对每个 Agent 轨迹进行分类并扫描海量语料库：在这个价格下，过去因太贵而无法运行的任务变成了例行操作——前提是这种判断属于 System One 类型。

首批基准测试结果说明了什么，以及如何解读那张流传的图表

五天时间足以让一个基准测试生态出现，而且它已经讲述了两个故事。第一个是那张正在流传的图表：Laya 是 ConvAI Innovations 在 Jev 发布四天后以 Apache 2.0 许可发布的 421M 参数开放权重模型，其总体成绩以 83.8% 对 67.8% “击败”了 Jev。在转述之前，请先看清坐标轴。Laya 的 83.8 是其作者在微调后的检查点上，对十一个任务族共 23,024 个问题自行运行评估得出的结果。Jev 的 67.8 则完全是另一个数字：那是 TypeSafe 自己的工作流评测，其中 67.8% 是 Jev 在四个业务工作流上与两个前沿 LLM 组成的集成模型的平均一致率，每个案例成本为 0.0004 美元、耗时 0.4 秒；相比之下，Opus 5 的一致率为 73.1%，成本为 0.1761 美元、耗时 37.8 秒。这两个数字除了百分号之外毫无共同之处，而一张 Hugging Face 数据集卡片在自行重新运行两个模型之前，正是指出了这一点。

第二个故事是在同一套冻结协议下会发生什么。一项独立的零样本基准测试在四个公开数据集上，给 Jev、Laya 和一个开放 NLI 分类器相同的文本、相同的指令和相同的标签名称，且协议在推理之前就已冻结。

同一冻结协议下的独立零样本准确率（elcronos，2026 年 9 月 20 日）。Jev 在两个主题数据集上领先 16 到 33 个百分点，在情绪数据集上与 Laya 完全持平。在对话情绪数据集上，所有零样本系统都低于 0.82 的多数类基线。带轮廓的柱形是在各数据集自身标签上训练的逻辑回归或 LightGBM 模型：在有标签的情况下，一个普通的监督模型在每个数据集上都击败了所有零样本系统。

该仓库的三个发现比排名更重要。任务类型胜过模型家族：同一个 Jev 提示词形态在情绪上得分为 0.587，在推文主题上为 0.793，其校准误差在四个数据集上从 0.063 到 0.281 不等，因此 API 中没有任何信息能告诉你它在你的数据上会有怎样的表现。与训练模型打平的盈亏平衡点在几百到几千个标签之间：500 条带标签的推文足以让基于句子嵌入的逻辑回归与 Jev 持平，金融主题需要 1,000 条，情绪数据集约需 5,000 条。而 Laya 宣传的胜出在零样本下并未复现：展示 83.8 的同一张卡片也指出，基础模型在其 typed-decisions 基准上得分接近随机，直到在该基准的训练集上完成微调。

第三个来源范围较窄，但对 FDE 来说最令人安心。一项针对 Jev 将 Agent 工具调用分类为只读、破坏性、特权或数据外泄的可复现基准测试，基于 60 个手工标注的案例（其中包含 12 个用良性语言包装的对抗性案例），结果显示准确率为 91.7%，12 个对抗性案例中捕获了 11 个，在刻意设置歧义的切片上准确率为 71.4%，且校准结果在多次重复运行中保持一致：每个错误答案都伴随着留有余地的置信度，模型从未在置信度为 1.000 时出错。在住宅网络连接上客户端测得的延迟为 p50 422 毫秒、p95 542 毫秒，远高于文档中“约 100 毫秒”的说法，在您自行测量之前，应以这个数字作为规划依据。

图表中唯一真正有用的面板是选择性自动化曲线，即在自动化决策上的准确率相对于自动化流量占比的关系。Laya 报告在 50% 覆盖率下为 92.2%，而全覆盖下为 83.8%。无论具体数字如何，任何决策模型都应提供这样的曲线，因为它就是以图形呈现的置信度门控：由您来选择覆盖率，厂商不能替您选择，而绘制该曲线的带标签数据集正是用于设定阈值的同一数据集。

用 TypeSafe 自己的话说，它在哪里会出问题

文档为 jev-1.13 保留了一页记录各种尖锐边角问题的页面，最后审阅于 2026 年 9 月 17 日。FDE 应该划重点的一句话是：该模型“回答的是你写出来的问题，而不是你心里想的问题”。限定范围的词语、否定词和隐含条件都会被按字面意思解读。

不变量这一行值得单独举例，因为它会让那些按教科书意义上把输出当作概率来推理的人感到意外。在 TypeSafe 的实际案例中，同一张工单上“客户是否在要求退款”返回 0.72，而“客户是否在要求退款以外的事情”返回 0.47，总和为 1.19。每个决策只用一种问法询问，并在代码中强制执行恒等关系。

前沿部署工程师应该如何思考这个问题

把它设计成一个智能的 if 语句，因为它本来就是一个 if 语句。 将判断分解为原子问题，把所有计算、日期比较、授权决策和不可逆的副作用都保留在代码中，并用客户能够读懂的显式权重或规则来组合答案。当优先级变化时，你只需修改一个权重，而不必重写提示词。

校准是总体层面的属性，所以你仍然需要一个 golden set。 校准后的 0.8 意味着在大量预测中，0.8 的结果大约有 80% 的时间会成真。它并不能保证任何单个答案是正确的。上面的独立运行结果让这一点变得具体：同一个提示词形态，在不同数据集上产生的准确率从 0.59 到 0.79 不等，校准误差从 0.06 到 0.28 不等。用客户自己的数据构建一个带标签的集合，绘制置信度与准确率的关系图，为每个操作选择阈值，并在模型版本变更时重新运行扫描。还要运行基准测试作者所做的那种对比：用同样的几百个标签训练一个线性模型，在留出的数据行上评分，因为一旦标签存在，它可能是更划算的选择。固定使用

jev-1.13.0

而不是别名，并记录响应返回的

model

字段与每个决策一起保存。

它只有五天历史，所以要像封装任何外部依赖一样封装它。 速率限制是动态的，SDK 版本为 0.6.0，而且文档没有公布 SLA。将调用放在超时和回退机制之后，在执行操作之前先把决策记录到 outbox 中，并设计重试机制以确保重复调用不会导致重复操作。该网站上关于 fallbacks and provider failover 和 idempotency 的概念说明是这两方面的参考。

将状态视为不可信输入。 模型无法自我防御那些旨在操纵它的文本，因此让 Noul 询问“这是不是一次 提示注入”只是其中一层防护，而非全部。保留已有的确定性检查，对于受监管的客户，应在合同中明确写入零数据保留条款，而不是想当然地认为已有。

寻找项目中那些已经在用 LLM token 做快速判断的环节。 分诊、路由、验证、相关性过滤、追踪分类。这些是首批候选场景，而且在这些场景中，错误答案很容易通过阈值和人工队列低成本地被发现。

五分钟内在编码 Agent 中完成设置

尝试这种模式最快的方式，是在你已经在用的编码 Agent 中进行，因为 TypeSafe 发布了一个 Agent 技能，可以将 API 的三种问题类型、其模式及其评测建议带入 Agent 的上下文。以下所有内容均来自截至 2026 年 9 月 21 日的文档和技能仓库；在依赖它们之前请先核对两者，因为早期访问的产品变化很快。

  • 获取密钥。 在 TypeSafe 控制台中创建一个密钥，并将其导出为 TYPESAFE_API_KEY。这是 SDK 和快速入门 curl 示例所读取的变量名。
  • 安装技能。 在项目中运行 npx skills add typesafe-ai/skills --skill typesafe-ai，并在被询问时选择你的 Agent；加上 -g 可为所有项目安装。文档中提到的有 Claude Code、Codex 和 Cursor。Claude Code 还有插件方式：先运行 claude plugin marketplace add typesafe-ai/skills，再运行 claude plugin install typesafe@typesafe-ai。
  • 为 Agent 编写的代码安装 SDK。 Python 使用 pip install typesafe-sdk；TypeScript 包是 @typesafe-ai/sdk。两者均采用 MIT 许可证。
  • 让 Agent 面向一个真实环节。 让它在代码库中找到一处“提示加解析”调用或脆弱规则集实际上是一个封闭集合决策的地方，并将该环节重构为带置信度门槛的类型化问题。该技能本身的经验法则是：当“一个 LLM 提示加解析环节可以变成结构化决策”时使用模型，并且“每个问题只问一个狭窄、连贯的判断”。

两点提醒。该技能是给 Agent 的指导，而不是你仓库的策略，所以如果你希望 Agent 默认优先采用类型化决策，请用自己的话写进你自己的项目指令中，而不是照搬社交媒体帖子里的模板。另外，安装了技能并不会让错误的往返调用变得更便宜：上文提到的标注数据集、阈值扫描和固定的模型版本，仍然适用于 Agent 重构的每一个环节。

这对 FDE 和应用 AI 工程师面试意味着什么

预期设计环节会在“规则还是模型”之外增加第三个选项：规则、生成式模型或决策模型。他们想要的答案包含四个部分：说出判断的形态（快速判断还是推理链）、说明哪些部分保留在代码中、将置信度阈值与错误行动的成本挂钩，并描述在版本变更前后如何基于客户数据进行评测。我们新增了一个关于 System One 决策模型的概念页，以及两道练习题：一道关于用决策模型替换 LLM 分类器，另一道关于用它构建护栏层。更广泛的准备工作与之前相同：LLM 和 GenAI 问题、RAG 和 Agent 设计问题，以及该角色的技能指南。

把它转化为录用通知。练习这些内容所对应的真实问题和概念：

常见问题

Jev 是 TypeSafe AI 于 2026 年 9 月 15 日发布的一款托管 AI 模型，它返回的是带类型的决策，而不是生成的文本。你向它发送一个状态（一张工单、一条记录、一段文本）和带类型的问题，它会返回一个是非问题的概率、从封闭集合中做出的选择（附带完整的概率分布），或者沿你定义的评分标准等级给出的分数。TypeSafe 将这类模型称为 System One 模型。

不，至少在设计层面如此。Jev 像 LLM 一样理解自然语言输入，但它不生成文本、代码或解释。它的输出被限制在你提供的选项范围内，并附带经过校准的概率。TypeSafe 使用一种称为“校准决策强化学习”的方法来训练它，而不是用于聊天模型的 RLHF。

截至 2026 年 9 月 20 日，TypeSafe 列出的 jev-1.13.0 价格为每百万输入 token 0.042 美元，输出 token 免费。请求预算为 64k token，其中状态加上最长的问题占 32k。速率限制为每秒 250,000 token 和每分钟 1,200 次请求，TypeSafe 提醒在早期访问期间他们会动态调整这些限制。

它们是 Jev 的三种问题类型。Noul 是一个以 0 到 1 的概率返回的是非判断。Choice 从最多 255 个选项的封闭集合中选出一个选项，并返回完整的概率分布以及一个置信度值。Score 根据你定义的 2 到 10 个有序评分标准等级对状态进行评级，并返回一个按概率加权的位置以及置信度。同一请求中的所有问题看到的是相同的状态，并且相互独立、并行地进行评估。

TypeScript 和 Python 的客户端 SDK 采用 MIT 许可证。模型本身由 TypeSafe 的托管 API 提供服务，我们没有发现其权重的公开发布。请把它当作一个外部推理服务，像对待任何托管模型一样提出相同的回退和数据处理问题。

从目前的证据来看，还不能。那张显示 Laya 达到 83.8% 而 Jev 为 67.8% 的图表，比较的是两个不同的基准：一个是 Laya 在微调后检查点上的自有测试套件，另一个是 TypeSafe 的工作流评测与 LLM 集成的一致性。在一个冻结的零样本协议下，在四个公开数据集上，Jev 在其中三个上领先 Laya 10 到 33 个百分点，在第四个上打平，而且 Laya 自己的模型卡也说明，其基础模型在未微调前，在其类型化决策集上的得分接近随机。Laya 是开放权重、Apache 2.0 许可，在本地 GPU 上大约快十倍，这使它成为当你有标注数据且不能把数据外发时，一个很好的微调基础。但它并不是零样本的替代品。

它可以回答这些问题，但不应该由它来运行循环。TypeSafe 自己的构建指南将控制流、规则和副作用保留在代码中，并警告说，一个自行决定下一步的 Agent 在没有人工监督的情况下会失控。它的 cookbook 展示了可行的工作形态：在封闭的工具列表上使用 Choice，每个参数对应一个问题；对每个提取出的字段使用 Noul，询问它是否错误，并在超过阈值时升级到推理模型；还有一个两阶段的技能排序器，在低于底线时保持沉默。代码拥有循环；模型只在其中回答狭窄的问题。

使用 npx skills add typesafe-ai/skills --skill typesafe-ai 安装 TypeSafe 发布的 Agent 技能（加上 -g 可用于所有项目），或者在 Claude Code 中添加 typesafe-ai/skills 市场并安装 typesafe 插件。从 TypeSafe 控制台中创建的密钥导出 TYPESAFE_API_KEY，安装 Python 或 TypeScript SDK，然后让 Agent 将一个提示加解析的步骤重建为带有置信度门控的类型化问题。该技能将三种问题类型、模式和评测建议带入 Agent 的上下文中。

在没有回退方案的情况下，它不应处于关键路径上。它在本文章发布前五天才进入早期访问，速率限制是动态的，而且 TypeSafe 自己的文档列出了 jev-1.13 的九种失败模式。它更适合作为代码控制的工作流中一个带置信度门控的判断组件，在客户自己的标注数据上进行评测，固定模型版本，并在置信度低时提供转人工或 LLM 的路径。

讨论（5）

我发现向客户的平台团队解释这一点最清晰的方式是：这是分类器的回归，但你不需要训练它。微调过的 BERT 给你一个标签和一个在训练分布之外不可信的 softmax。而在这里，你在请求中写出选项和标准，得到一个经过校准的分布，并通过编辑一个映射而不是重新训练来修改分类体系。

而让它超越分类器的关键在于扇出。一次调用中对同一个状态发起十二个独立的问题，然后由你的代码来组合它们。这是一棵叶子节点上带有模型的决策树，而这正是大多数企业自动化真正需要的形态。

读者提问：置信度值与直接读取 Choice 上的最高概率有什么区别？如果账单是 0.88，那不就是置信度吗？

接近但不相同。置信度是 TypeSafe 从整个分布的形状推导出的统计量，因此当其余概率稀薄地分散在十个选项上时，0.88 的读法与面对唯一一个 0.12 竞争对手时的 0.88 是不同的。Noul 答案完全没有置信度，只有概率。他们文档中的实用规则是：不要把在 Noul 上调好的阈值搬到 Choice 上使用，也不要期望一个问题与其否定形式的概率之和为一。

在他们的故障模式页面中，我会为任何 FDE 划重点的一句话是：状态即数据，模型默认不会将其视为敌意内容。一份为了论证自身分类而写的工单可以改变答案。因此防护层仍然必须分层部署，允许列表、授权检查和 PII 正则表达式应留在代码中，它们本来就该在那里。
