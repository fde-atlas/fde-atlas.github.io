FDE 如何借助编码 Agent 并行处理五个客户项目

原标题：How FDEs run five client engagements in parallel with coding agents

Fredrin · 2026-07-18 · 约 7 分钟读完

摘要

这篇文章讲前沿部署工程师如何借助编码 Agent 同时推进约五个客户项目。作者认为瓶颈不在写代码速度，而在恢复上下文的成本和 Agent 静默停滞；解法是结构化隔离：每个项目独立目录（git worktree）、独立运行环境、独立 Agent 会话和书面状态记录。一人实际可监督三到六条并行流，上限由评审成本决定，因此缩小 diff 比增加 Agent 数量更有效。文章还给出每日流程（先清评审队列、最后开新任务）和规模化后的三大风险：上下文流失、评审走过场、客户混淆。最后介绍其产品 Fredrin，用看板解决多 Agent 并行的可见性问题。

要点

  • 并行失败主因是恢复上下文成本与静默停滞，而非代码写得慢。
  • 每个项目需独立 worktree、环境、Agent 会话和书面状态。
  • 一人可监督三到六条流，上限取决于评审每个 diff 的耗时。
  • 每日流程：先清评审队列，回答阻塞项，最后才开新任务。
  • 规模化三大风险：上下文流失、评审走过场、客户间混淆。

你不是靠把速度提高五倍来做到这一点。你靠的是确保没有任何一个项目需要你在机器可以无人值守完成的部分亲自在场，并且让每个项目都处于隔离的工作区中，这样在它们之间切换只需一眼，而不是花二十分钟重建上下文。稀缺资源不再是你的打字速度，而是你的注意力，因此整个工作流程都会围绕如何用好注意力来重新安排。

本文先通用性地描述这一工作流程——它适用于 git、终端和任何编程 Agent——然后展示当界面专为它打造时会是什么样子。

为什么并行客户项目会难以为继？

原因并非人们通常以为的那样。失败很少是因为代码写得太慢。真正的原因是每个项目都带有恢复成本：从决定处理客户 B 到真正能为客户 B 创造价值之间的时间。

这个成本由许多小事构成。我之前在哪个分支上。我不在的时候 Agent 做了什么。周二电话里他们说了什么改变了计划。四个进行中的事项里哪个实际上在等我。单独看每件事只需三十秒。但跨五个项目、一天十几次上下文切换，它们就占去了大半天。

再加上第二种失败：静默停滞。一个二十分钟前就已完成任务的 Agent 和一个等待确认提示的 Agent，从外部看起来一模一样——也就是说，两者看起来都像毫无动静。项目每完成一小时却无人察觉，就有一小时你已付出却未收获的吞吐量。

这两个问题都无法靠更快的模型解决。它们都能靠结构解决。

一个项目需要什么才能独立可运作？

四样东西，缺了任何一样，你都会以恢复成本的形式付出代价：

  • 它自己的检出目录。 不是你切换过去的分支——而是与其他目录同时存在的一个目录。
  • 它自己的运行环境。 它自己的开发服务器、自己的端口、自己的数据库。任何共享的东西都会成为串行化的瓶颈点。
  • 它自己的 Agent 会话，范围限定在该项目的代码和约定之内。
  • 它自己的书面状态——什么在进行中、什么被阻塞、什么已决定。写下来，而不是靠记忆。

最后一点是人们最容易跳过的，而它恰恰决定了五个项目是可持续的，还是只能勉强撑一阵子。

如何低成本地隔离一个项目？

Git worktree。worktree 是由同一个仓库支撑的第二个工作目录，检出不同的分支，与其他目录同时存在。

git worktree add ../client-acme-ingest feature/ingest
git worktree add ../client-borealis-auth feature/auth

两个目录，两个分支，一个仓库，无需 stash，无需切换分支。每个目录都有自己独立的

node_modules

，自己独立的

.env

，以及在自己端口上运行的开发服务器。在一个目录中工作的 Agent 无法触碰另一个目录的文件，当你同时运行多个任务时，这一点至关重要。

对于使用不同仓库的独立客户来说，隔离是免费的——它们本来就是不同的检出。Worktree 最有价值的地方在于同一个客户内部：一个代码库中有三条工作流，而你不想让它们在单个分支后面串行执行。

两条来之不易的实用经验。把环境文件复制到每个新的 worktree 中；新建的 worktree 里没有

.env

环境文件，报错信息会让人摸不着头脑。另外，给每个 worktree 分配不同的端口，因为两个开发服务器争抢同一个端口所产生的错误信息与实际问题毫无关系。

一个人到底能同时监督多少个 Agent？

实践中，大多数人最多能同时处理三到六条工作流，而这个上限取决于审查能力，而不是任何技术因素。

这笔账很残酷。如果一个 Agent 每 25 分钟产出一个可审查的变更，而一次认真审查需要 10 分钟，那么一个人大约只能维持五条工作流，超过这个数量队列的增长速度就会超过消化速度。突破这个上限后，你并不是在推进更多工作，而是在积累未经审查的工作——这更糟：它看起来像进展，实际上是风险。

因此，真正关键的杠杆不是 Agent 数量，而是每个变更的审查成本。把你判断一个 diff 是否可接受所需的时间减半，你的实际产能就翻倍了，而且无需改动任何模型设置。这就是为什么本系列的下一篇文章将完全围绕如何让变更变得易于审查。

有两件事会把方向带偏，都值得抵制。把一个任务分散给多个 Agent 会成倍增加审查负担，却不会成倍增加产出。而让一个项目长时间无人值守地运行，会产生一个巨大的 diff——这是现存审查成本最高的产物。

日常循环是什么样的？

大致如下，而且顺序是刻意安排的：

  • 先清空审查队列。 任何已完成的工作都在阻塞一条工作流。审查它能重启该工作流；写新任务单则不能。
  • 回应被阻塞的。 一个在等待问题的 Agent 就是一台停机的机器。
  • 最后才启动新工作——在清空队列之前填满每条通道，会让你在一天结束时留下六个未经审查的分支。
  • 把决策写在工作所在之处，而不是记在脑子里或私人笔记里。这正是让明天变得轻松的关键。
  • 小改动立即发布。 已合并的变更是吞吐量；已批准但未合并的只是库存。

整套纪律就是：先完成，再开始。

当你扩大规模时，什么会最先崩溃？

三件事，按这个顺序。

上下文会蒸发。 每个客户都有自己的约定、约束和决策历史。这些知识只存在你脑子里，一个周末就会流失，一个月后就彻底消失。解决办法是把它保存在客户的代码仓库里——一份约定文件、一份决策日志——让任何 Agent 在未来的任何任务中都能直接读取，无需你重新解释。文件是持久的载体，因为它比工具更长寿，并且随代码一起迁移。

审查沦为走过场。 当待审队列很长时，批准就成了阻力最小的路径，你参与工作的质量悄悄变成了模型默认输出的质量。解决办法是结构性的：更小的 diff、明确的验收标准，以及一条清晰的底线——疲惫时绝不批准什么。

客户之间会混淆。 把客户 A 的架构约定用进客户 B 的代码库，是最令人尴尬的失败模式，而且当两个项目在时间上重叠时最容易发生。隔离不仅是技术上的便利——它也能让这些客户在你的头脑中保持分离。

工具应该放在什么位置？

上面所说的一切，只需要 git、一个终端和任意 Agent 就能实现。很多人正是这样运行的，如果你同时在做两个项目，或许也应该如此。

到了四五个项目时，出问题的不是能力，而是可见性。你可以手动创建 worktree，但你很难盯着十五个终端窗口回答“其中哪个现在需要我”——这是你每天要问五十遍的问题，而一整面墙的终端恰恰最不擅长回答它。

这正是 Fredrin 要填补的空白。一张工单自带自己的分支、自己的 worktree 和自己的 Agent 会话，一起创建、一起销毁，隔离不再需要你手动维护。看板直接回答可见性问题：什么在运行，什么在等你，什么可以交付。审查是一个列，而不是在滚动历史里做考古。

它与编辑器的区别值得明确说明，因为这是最常见的误解。编辑器优化的是一个人编辑一个仓库的场景；这与监督多个 Agent 服务多个客户是完全不同的问题，因此我们把它当作一个不同的品类，而不是一个更好的编辑器——相关论述见 Fredrin vs Cursor。它也不是那种接下工单、返回成品 PR 的自主 Agent；每一次变更仍然由人来审查和交付，Fredrin vs Devin 解释了为什么这是一个深思熟虑的选择。

常见问题

同时做五个项目是现实，还是营销数字？ 对于一名拥有良好隔离机制和小 diff 习惯的资深工程师来说，五条工作线是现实的。但五个客户都要求每天同步在场则不现实，任何工具都解决不了这个问题——这是排程问题，不是工程问题。

这需要特定的 AI 工具吗？ 不需要。这套工作流与具体的 Agent 无关，可以配合 Claude Code、Codex、Cursor、Gemini CLI 或任何取代它们的工具使用。刻意保持这种通用性是有原因的：你用来执行工作的界面应该比任何特定的模型供应商活得更久。

客户的安全要求怎么办？ 这套工作流兼容严格的环境，因为隔离是本地的——worktree 就是你机器上的目录，代码始终留在客户的仓库中。客户之间的差异在于他们的代码是否允许发送给模型提供商。这一点要在处理第一个工单之前确认，而不是之后。

Agent 辅助的工作如何计费？ 大多数 FDE 是拿薪水的，所以这主要关系到承包商。坦率的说法是，你计费的是成果和判断力，而不是敲键盘的次数。按小时付费的客户迟早会察觉；购买已交付软件的客户则不会在意。

如果我的客户在不同的仓库中，还需要 worktree 吗？ 用于区分客户的话不需要——独立的仓库已经做到了这一点。Worktree 的价值体现在单个客户内部：当你需要在同一个代码库中并行推进多条工作流时。

如果这套方法不奏效，首先应该修正什么？ Diff 的大小。几乎所有症状——评审缓慢、走过场式的批准、积压的队列——都可以追溯到改动过大、难以快速评估这一问题。
