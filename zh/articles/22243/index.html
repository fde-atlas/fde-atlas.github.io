为什么 API 银行 Column 在招聘 FDE

原标题：Why Column, an API Bank, Is Hiring an FDE

FDE Times · 2026-10-28 · 约 6 分钟读完

摘要

Column 是一家以 API 形式出售银行服务的全国性持牌银行，其 2026 年 10 月 6 日在旧金山发布的 FDE 招聘启事显示：该角色作为战略客户的技术负责人，覆盖从接入到上线的全过程，同时参与塑造 API、文档与开发者体验。文章对比了 FDE 与解决方案工程师的分工，并借 CRV、PostHog、Palantir 的定义给出甄别真假 FDE 岗位的方法与求职建议。

要点

  • Column 以 API 卖银行服务，2026 年 10 月在旧金山招聘 FDE。
  • FDE 是战略客户的技术负责人，覆盖接入到上线。
  • FDE 与解决方案工程师的区别在于职责区间与产品参与度。
  • 招聘启事中的动词能判断是否为真正的 FDE 岗位。
  • 建议求职者展示把客户问题转化为产品改进的经历。

Column 的 API 附带规范文档和沙盒环境，但其背后是一家真实的银行，而集成点本身就是产品。

简要概述

  • 一家通过 API 销售服务的银行 Column，于 2026 年 10 月 6 日在旧金山发布了一个 FDE 职位。
  • 与覆盖从售前到支持全流程客户的解决方案工程师不同，Column 的 FDE 负责战略客户从入驻到上线的整个阶段。
  • 在 FDE 招聘广告中，诸如“塑造 API 和文档”这类面向产品的动词，正是区分真正的 FDE 职位与改头换面的支持岗位的关键标志。

2026 年 10 月 6 日发布的一则招聘广告显示，一家以 API 形式销售服务的银行 Column 正在旧金山招聘前沿部署工程师。这位新员工将成为战略客户的技术负责人，负责从入驻到上线日的全过程。

乍一看，这似乎是个悖论。Column 的 API 由 OpenAPI 规范描述，并附带沙盒环境：这正是那种客户本应自行处理的产品——阅读文档、调用接口、完成任务。那么，为什么还要在客户身边安排一名工程师呢？

如果你是 FDE 或想成为 FDE，这个答案值得深思。当产品是 API 时，客户进行集成的地方就是产品本身。

站在这个位置上的人，如果被赋予相应的权限，所做的就不只是让客户跑起来。他们还会把客户遇到的绊脚之处带回产品中加以修复。这正是真正的 FDE 与换了个名字的客户支持之间的分界线。

一家面向工程师的银行，但并非从零构建

Column 自称是唯一一家旨在帮助客户构建和资助新金融产品的全国性特许银行。该公司表示，它由工程师创立，就是为了解决与现有银行合作时的种种困扰。

不过，“面向工程师的银行”并不意味着从零开始。据一家律师事务所的百科页面介绍，创始人收购了加利福尼亚州奇科市的一家单分行银行，而不是再创办一家初创公司。

这个细节对 FDE 来说比表面上更重要。在 API 层之下是一家真实的银行：Column 的解决方案工程师招聘广告中也列出了监管和风险方面的职责。因此，站在客户与 API 之间的人，既要理解代码，也要理解规范文档无法完全阐明的种种约束。

为什么好的文档仍然不够

想象一家想在应用中嵌入账户和转账功能的初创公司。其团队阅读文档，并在沙盒环境中相当迅速地构建了流程。然后，他们卡在了文档没有说明的地方：转账被退回时如何对账，如何为终端客户建模账户，上线日之前需要完成哪些准备工作。

如果每个问题都要走工单流程，客户的团队要等上好几天，银行则会看到十个互不相关的工单。但如果十个战略客户恰好在同一个地方卡住，那就不是十个支持案例，而是文档或 API 设计中的一处缺陷。只有全程跟进集成的人才能看出这种规律。

这就是为什么 Column 的招聘广告把两份工作合并在一个人身上。FDE 直接与合作伙伴的工程团队合作设计、构建并上线产品，同时也与 Column 自己的工程师紧密协作，共同打磨 API、文档和开发者体验。

FDE 与解决方案工程师有什么区别？

Column 并不缺少面向客户的工程师。其解决方案工程师岗位负责在售前、实施、入职和支持各阶段维护与客户的技术关系，而且广告本身也说明，这个岗位比该职业的通常情况更具技术性。

既然两个岗位都高度技术化，区别不太可能在于技能水平。仔细对比两份广告，区别在于覆盖范围：解决方案工程师横跨售前到售后的一切环节，而 FDE 负责的范围更窄，即从入职到上线，作为技术负责人，并参与产品本身。

把这份广告与 FDE 的独立定义放在一起，就能看清 Column 承诺了哪些部分，哪些部分需要你自己去问。风险投资公司 CRV 认为，在客户环境中编写生产代码是 FDE 的决定性特征，并认为 FDE 可以同时覆盖售前和售后，同时仍然写代码。

PostHog 将 FDE 描述为嵌入客户团队、弥合产品与真实需求之间差距的人。Palantir 的前沿部署软件工程师招聘广告则说，该工程师与客户合作（通常在现场），理解并解决他们的问题。

通常在客户现场工作Palantir广告中未提及你坐在哪里？每周花多少时间与客户相处？

最后一列最重要。招聘广告给你一个承诺；面试中的回答则告诉你这个承诺是否兑现。

像工程师一样阅读 FDE 招聘广告

PostHog 指出，一些公司将 FDE 头衔用于更接近售前工程师的工作。因此，两则带有 FDE 字样的招聘广告在任何国家都不保证是同一份工作。

线索藏在动词里。当广告说 FDE 将参与塑造 API、文档或平台时（如 Column 的广告），这个职位就有回到产品端的路径。当广告只谈支持和合作时，直接问一句：最近一次是谁把客户的反馈推动成了产品变更。

Column 广告中的另一句话值得注意：候选人需要很强的项目管理能力，能够同时推进多个项目并让每个项目持续向前。

把这个职位的两半都写进你的简历

如果你曾在看到客户反复问同一个问题后修复过文档，或者因为某个端点会让集成方猜错而提议修改它，请把这些写在简历最上方。对于像 Column 这样描述的职位，这是最能证明你能把客户混乱的问题转化为具体产品变更的证据。

怎么写也很重要。不要写“支持客户集成 API”，而是写成一条链：客户遇到了什么问题，你负责了哪部分直到上线，你同时处理了多少个客户，以及你给产品团队带回了什么。

如果你缺乏这种经验，最省钱的路径是自己成为集成方。选一个有公开沙盒的 API，搭建一个小流程，记下每一个你不得不猜测的地方，然后把这份清单转化为对文档和 API 的修改建议。这是最接近销售 API 的公司里 FDE 日常工作的事情。

一份好的 OpenAPI 规范是一个答案。FDE 招聘广告指出了第二个答案：有人站在客户的问题与规范之间，这样随着时间推移，规范能让客户越来越少地猜测。
