为什么 OpenAI 派遣工程师驻场：企业级 AI 的 FDE 实战手册

原标题：Why OpenAI Sends Engineers On-Site: The FDE Playbook for Enterprise AI

BestHub · 2026-10-05 · 约 6 分钟读完

摘要

OpenAI 前沿部署工程负责人 Colin Jarvis 与前 Palantir FDE Apoorv Agrawal 对谈，解释为何模型越强越需要 FDE：企业落地的瓶颈不是模型能力，而是信任、评测、数据与业务规则。文章通过 Morgan Stanley、欧洲半导体、亚太车企供应链和 Klarna 案例，阐述评测驱动开发、确定性约束与概率性判断的分工，以及从定制项目提炼通用产品的“吃进痛点、产出产品”方法论。

要点

  • Morgan Stanley 项目技术管线 6-8 周完成，但 4 个月用于试点与建立顾问信任，最终采用率约 98%，研报使用量约 3 倍增长。
  • 半导体验证 Agent 先只做故障调查，待工程师信任后才加入执行环境，逐步扩展权限。
  • 供应链编排器把硬业务规则编码为确定性约束，模糊语义判断才交给 LLM。
  • Klarna 项目从约 20 条策略扩展到 400+，其框架后来开源为 Swarm 并演化为 Agents SDK。
  • OpenAI FDE 团队从 2 人增至 39 人，年底目标 52 人，定位为 0→1 产品发现团队而非咨询部门。

引言

本文记录了 2025 年前 Palantir 前沿部署工程师（FDE）Apoorv Agrawal 与 OpenAI FDE 负责人 Colin Jarvis 之间的一次对话。他们探讨了为什么尽管模型能力日益增强，OpenAI 仍在不断扩大 FDE 团队，以及 FDE 模式与传统咨询有何不同。

01 为什么更强的模型需要更多 FDE

Colin Jarvis 于 2022 年 11 月加入 OpenAI，就在 ChatGPT 发布前几周。早期的企业项目（Morgan Stanley、Klarna）表明，仅仅交付 API 和文档很少能让客户走向生产环境。可靠的路径是：工程师驻场，深入理解数据、流程以及一线用户的实际工作方式。

Morgan Stanley 案例研究

2023 年，Morgan Stanley 希望 GPT-4 能为财富顾问呈现内部研究成果——这是在 RAG 尚未形成成熟工程模式之前的经典 RAG 场景。技术管线（检索调优、护栏）在 6–8 周内即可运行。随后的 4 个月则花在试点、标注、评测驱动的迭代以及建立顾问信任上。由于 GPT-4 是概率性的，团队无法像传统软件那样保证确定性的输出。他们让顾问实时使用系统、标注结果、积累评测集，并针对真实失败进行迭代，同时保留对照源文档验证答案的能力。

结果：约 98% 的顾问采用率，研究报告使用量增长约 3 倍。Apoorv 的心得是：“通过迭代建立信任，而不仅仅是技术卓越。”生产就绪需要回答：答案能否被验证？关键操作是否有护栏？模型错误能否被追溯？用户是否愿意在工作流程中信任该系统？FDE 的工作正存在于“模型能做到”与“企业敢使用”之间的鸿沟中。

02 部署 AI Agent：并非从第一天起就完全自主

半导体验证 Agent

在一家欧洲半导体公司，OpenAI 的前沿部署工程师花了数周时间梳理芯片研发价值链，并将重点放在验证环节——据估计，工程师 70–80% 的时间都花在运行测试、修复 Bug 和处理遗留兼容性问题上。最初的 Agent（使用 Codex）不修改代码，只负责调查故障——读取日志、检查代码、生成带有假设根因的工单。只有在工程师信任这些调查结果之后，团队才加入执行环境，让 Agent 能够运行测试、观察结果并迭代修复方案。该工具最终演化为一个调试调查与分诊 Agent，目标是让简单问题在次日早晨前得到解决，复杂问题则已完成预调查。

评测驱动开发

Colin 强调，真实的工程工作流涉及跨系统的 20 多个连续操作。OpenAI 首先与领域专家一起构建真实轨迹，创建带标注的评测集，然后基于这些评测集进行开发。只有当评测验证通过后，LLM 驱动的能力才被视为完成。

汽车供应链编排器

为一家亚太地区汽车制造商，OpenAI 将数据保留在现有系统中，并为 LLM 编排器构建了 API。在一个演示场景中（对中国出口韩国征收 25% 关税），系统识别出受影响的零部件，分析了成本传导，并重新优化了采购方案。关键在于，硬性业务规则（如双源采购要求、交期限制）被编码为确定性约束，而不是提示词。Colin 的原则是：“只要能用确定性方法，就用确定性方法。”模糊的语义判断交给 LLM；需要 100% 正确性的规则交给确定性代码。验证路径让用户能够检查底层数据表。优化过程使用了一个模拟器：模型调整参数、运行多个场景、比较成本与交付的权衡，并推荐一个仍能通过确定性验证的方案。

Apoorv 总结了两大支柱：使用评测驱动开发，以及有意识地权衡确定性与概率性。Agent 的成熟度不是以自主执行步数来衡量，而是以每次扩大权限时都能增加一层可验证性的机制来衡量。

03 Klarna：从定制项目到可复用产品

Apoorv 提出了对 FDE 的经典质疑：这不就是咨询吗？Colin 用 Klarna 客服项目作为回答。早期，数百条政策使得手写的提示词和工具调用难以维护。团队将指令和工具参数化，为每个意图配备评测，并将规模从约 20 条政策扩展到 400 多条。

在解决 Klarna 的问题之后，他们提炼出一个通用框架（后来以 Swarm 之名开源）。一次成功还不够；他们在更大、更复杂的项目（如 T-Mobile）上验证了这些基础组件。此后，FDE 和产品团队才将其产品化为 Agents SDK 和 AgentKit。OpenAI 将 FDE 定位为一支 0→1 团队：深入攻克最棘手的具体问题，然后移交给规模化团队或合作伙伴。

Apoorv 的“吃下痛苦 → 排出产品”框架：首次项目大约只能产出 20% 可复用的代码；做过 2–3 个类似项目后，可复用比例达到约 50%；只有到那时才推给平台团队。危险在于过早泛化——在发现真正的问题之前就构建通用解决方案。Colin 提醒创始人：要弄清楚 FDE 到底是为了服务收入，还是为了产品探索。两者混在一起会导致公司变成咨询店，因为短期服务收入是会上瘾的。

OpenAI 针对两类问题：(1) 有明确产品假设的领域（如客户服务、文档生成），需要设计合作伙伴；(2) 极其困难的领域问题（半导体、生命科学），可能反哺研究。经济价值必须在 1000 万至 10 亿美元以上区间。截至访谈时，OpenAI 的 FDE 团队已从 2 人增长到 39 人，年底目标为 52 人，且无意成为数千人规模的实施部门。

04 超越 MCP：缺失的逻辑 / 元数据翻译层

被问及下一个重大机会时，Colin 指向的不是新的模型架构，而是将企业原始数据和隐藏的业务逻辑翻译成 LLM 真正能用的东西。数据存放在数据仓库、SharePoint 和内部系统中；逻辑则藏在未成文的工作流程里。MCP 连接器能让模型调用某个系统，但不会告诉它何时该把仓库数据与 SharePoint 文档结合，也不会告诉它如何应用隐含的业务规则。FDE 们反复构建轻量级的“逻辑层”或“元数据翻译层”来弥合这一鸿沟。

Apoorv 将此与 Palantir 的 Ontology 联系起来。Colin 认同这一挑战并不新鲜——数据工程领域早就争论过集中式与虚拟访问层——但消费者变了：如今 LLM 会编写查询并组合数据，因此元数据、语义和数据组织方式直接决定了 Agent 的正确性。

未来：面向专业领域的微调

Colin 的长期/短期押注：微调。随着 Agent 编排、工具使用、评测、标注和执行环境的成熟，团队可以更容易地生成训练数据、快速标注、构建训练集，并针对特定 GenAI 用例（芯片设计、药物发现）微调模型。以前这些领域缺乏足够的真实任务数据；现在 Agent 系统可以记录过程、评估结果并整理数据集。下一阶段可能不只是更复杂的 Agent 工作流，而是通过微调把某些能力蒸馏回模型本身。

从摩根士丹利、半导体、供应链、Klarna 到 T-Mobile，模式是一致的：模型撞上的是企业约束——信任、评测、数据、业务规则、环境限制——而非原始智能。FDE 进入最具体的问题，解决它们，然后提炼出可成为产品的原语，这些产品的生产闭环最终可能反哺模型改进。正如 Apoorv 总结的：“客户项目不是终点，而是产品探索的起点。”
