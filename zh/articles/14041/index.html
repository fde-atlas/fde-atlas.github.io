Cognition 如何开展前沿部署工程

原标题：How Forward Deployed Engineering is done at Cognition

AI Engineer · 2024-03-12 · 约 11 分钟读完

摘要

本文整理 Cognition 部署工程负责人 Jia Wu 在 AI Engineer World's Fair 2026 的演讲，阐述其前沿部署工程师（FDE）方法论：定位客户软件生命周期中的真实瓶颈，将 Devin 的能力配置为可由事件触发的自动化，并把现场经验反馈到产品路线图。文中给出多项案例数据，但多为匿名或凭记忆的估算，缺乏计算方法与样本细节。

要点

  • 写代码只约占问题两成，FDE 应先找到测试、评审、部署等真正瓶颈。
  • 部署要避免“token 最大化”，把重复工作接到事件触发上，形成可复用流程。
  • 现场经验是高保真评测集，需按范围、产品潜力、路线图价值三问过滤反馈。
  • 衡量应看交付而非消耗：产能、交付周期缩短约 82%、PR 数量三个维度。
  • 案例包括 Nubank ETL 迁移约三分之一时间完成，及 Bilt 每周产出相当于十多名工程师。

前沿部署工程将 AI Agent 能力与真实的交付瓶颈连接起来，并把一线实践中发生的情况转化为更好的产品决策。

从基准测试的热潮到实际可用性

一个编码 AI Agent 即使能解决基准测试任务，工程师们仍然会疑惑自己究竟什么时候才会真正用到它。这就是 Devin 在 2024 年发布时面临的落差：对自主软件工程的热忱很快遭遇了对实际可用性的失望。Cognition 的部署工程负责人 Jia Wu 回忆，发布时 SWE-bench 成绩约为 13%。这是一个历史基准测试结果，并非对当前性能或企业生产力的衡量。他记得一周之内，人们的反应就从担心工程师会被淘汰，转变为把该 AI Agent 当作“其他办法都试完了才拿来一试”的东西。

打开完整原始片段

Cognition 最终把这种质疑融入了自己的广告，通过一场刻意自嘲的营销活动，将产品宣传为“现在就有用”。但部署层面的问题依然比“AI Agent 能否写代码”要求更高：它的能力如何才能成为客户可以信赖的东西？该产品提供了常见的入口——一个可与 Claude Code 类比的 CLI，以及一个可与 Cursor 或 Windsurf 类比的 IDE 界面。这些界面确立了工程师与系统交互的方式；但仅凭它们本身，并不能解释一个组织如何从中获得价值。

在 Cognition 收购 Windsurf 之后，Wu 从 Windsurf 一方加入。除了 CLI 和 IDE 之外，他认为 Devin Cloud 是 Cognition 最广为人知的 AI Agent 产品。更宏大的目标是让 AI Agent 成为企业软件工程职能的一部分，而不仅仅是又一个提交代码请求的地方。

Wu 介绍，在过去六个月中，Cognition 内部合并的 PR 数量增长了近一个数量级，而招聘却相对滞后。他将这些 PR 描述为稳健且质量良好，并指出企业用户在不同用例中的采用正在快速增长。这些是他个人的观察；本次演讲并未提供独立的质量衡量，也未给出采用数据的原始依据。这引出了运营层面的问题：什么样的工作让这种扩张成为可能？

在软件生命周期中找到瓶颈

想象两个圆：一个包含产品能做什么，另一个包含客户需要解决的问题。它们的交集代表 product-market fit（产品市场契合度）。Cognition 的前沿部署工程旨在扩大这个重叠区域。要做到这一点，需要理解客户的问题领域，而不仅仅是了解产品的功能。

打开完整原始片段

对于软件工程而言，问题领域包括现有代码库的整个生命周期。功能需要构建、审查、部署和维护。遗留软件使大多数企业无法把开发当作从零开始的、干净利落的提示词序列。即使是一份写得很好的用户故事，也只是指出了值得构建的东西；组织仍然要把它转化为能创造业务价值的可用软件。

在有足够上下文工程的前提下，Wu 认为生成所需的代码块已基本解决。Wu 估计编写代码通常只占问题的 20%。这是他对这项工作的个人界定，并非普遍的实测分配。更快的代码生成之后，测试、审查、部署和维护仍有待解决。 因此，FDE 在决定 Agent 应该放在哪里之前，需要先找出这条链路中真正的瓶颈。

把需求探索转化为有针对性的自动化

在没有明确目标的情况下，把 Agent 部署到复杂的开发生命周期中，可能只会产生消耗而没有有用的交付。Wu 把这称为 token 最大化：系统在运行，token 在消耗，但不一定产生任何实际成果。部署的首要任务是把 Devin 的能力映射到一个足够重要的客户问题上，以证明这项工作值得投入。

客户需求探索与实施紧密相连。Wu 描述过这样的工作日：四到五小时的客户电话会议，接着是四到五小时的键盘操作。电话会议用于识别具有最大业务价值的战略举措。实施阶段则把选定的工转化为自动化，使其能够响应警报或事件，而无需 FDE 手动启动每一次 Agent 运行。预期的推进路径是：

  • 与客户一起确定一项重要的业务举措。
  • 找出阻碍该举措的软件工作。
  • 配置 Agent 来执行相关工作。
  • 把重复性工作与应当触发它的事件连接起来。

目标是让工作流可以重复执行，而不需要部署工程师一直充当它的操作员。

这仍然留下了一个更难的问题：投资回报率，吴（Wu）认为这个问题模糊且尚未解决。嵌入客户环境能让候选人的工作变得具体：积压的功能、修复任务、从未上线的代码、没人编写的测试，或需要分诊的告警。将产品能力映射到这些需求是工作的一半。即使客户满意，也不意味着完成了全部职责。

将一线证据带回产品路线图

另一半则朝相反方向运行：将客户问题映射回产品。解决单个部署只能移动产品与问题重叠区域的一侧。从这次经验中改进产品，会让下一次部署更容易、更有价值。客户交付与产品反馈构成一个闭环。

吴将一线经验描述为一个高保真的评测集。前沿部署工程师每天面对客户实际遇到的代码仓库、组织约束和失败案例。他们的职责是将这些背景转化为产品决策，而不是原封不动地转发每一个请求。三个问题组织了这种转化：

  • 范围： 这是企业中反复出现的挑战，还是某个用户特有的需求？
  • 产品潜力： 部署过程中遇到的变通方法、临时方案或 bug，是否应该转化为一个受支持的功能？
  • 路线图价值： 解决它是否能减少关于该构建什么、以及客户为何愿意为之付费的不确定性？

其目的是通过将工程优先级与观察到的客户需求和收入机会联系起来，来降低路线图风险。

这种反馈不是交付之后的行政步骤。它正是让一次成功的部署能够为后续客户改进产品的关键。FDE 在两个方向上架起桥梁：先应用今天已有的东西，再帮助确定接下来应该有什么。

将广泛的客户技能与深刻的判断力相结合

这种双向职责解释了为什么 FDE 角色难以归类为售前工程、解决方案架构或传统软件工程。Cognition 寻找的是 T 型技能画像：在人员、业务、流程、客户和技术方面具备广度，同时拥有一个使其在现场尤为有用的深度专长。

深度专长不必对每位招聘者都完全相同：

  • 产品判断力： 来自产品管理的人可能理解功能如何相互配合，以及什么构成一个连贯的产品。在吴看来，实现成本的不断下降使得决定构建什么变得更加重要。
  • 技术专长： 创始人和软件工程师可能在某个技术领域拥有深厚的积累。Wu 愿意雇用商业技能仍在成长的人，因为在已经外派的情况下成为现场的技术专家，是更难在岗位上培养的能力。

共同的要求是具备足够的广度来与客户协作，同时拥有难以替代的深度。

优秀的外派工程师能够解决客户问题，并将其与产品路线图联系起来。Wu 通过对“这项工作为何重要”的好奇心来区分卓越者。他们会追问这个问题对企业是否重要，以及从中获得的经验能否为其他客户改进产品。这种好奇心与第二种承诺并存：与客户保持紧密联系。让客户取得成功既是外派工作的直接目标，也是建立持久企业合作的基础。

衡量交付而非消耗

Wu 描述了 AI Agent 部署的早期阶段，当时 token 用量本身就可以作为 KPI。补贴预算让实验成本很低，运行更多工作可能看起来像是进展。他将下一阶段称为智能编排，这一阶段要对可衡量的交付负责。大型受监管企业想知道系统是否产生价值，而不仅仅是它是否忙碌。

这一区别也改变了改进的单位。让一名工程师更快是有价值的，但这并不一定会加速一个包含技术人员和非技术人员的组织。Wu 将每个层级十倍的提升作为一个挑战，而不是已经实现的组织级成果。他对孤立的 CLI 和 IDE 工具的批评在于，它们本身无法协调实现那种组织变革所需的更广泛工作。因此，证明必须超越单个工具的活动。

区分产能、交付时间和产出

Cognition 将一次 Agent 运行及其相关的追踪或轨迹称为一个会话。会话指标用于估算生成的工程小时数以及其中被视为有生产力的部分。Wu 透露，一次为期三个月的客户合作产生了相当于 150 多名额外工程师的产能。这是一个推断出的产能等效值，并非声称该客户真的雇用了这么多人。

如果工程小时估算只是重新包装活动量，它仍然可能类似于 token 最大化。Wu 在转向交付时间之前明确提出了这一质疑。Wu 在一个匿名化的部署前后对比案例中报告，交付周期缩短了约 82%。他描述了在 Devin 部署并完全启用之前和之后，观察客户现有的项目、工单和冲刺指标。数字上的说法是减少 82%；伴随的数量级表述不应被视为等同的计算。

第三个维度是已交付的产出。Wu 在一个匿名化对比中报告，与工程师在 Devin 之前使用单点工具相比，PR 数量几乎翻倍。这问的是额外的活动是否转化为工程产物，而不仅仅是更多的会话。

这三个证明点回答的是不同的问题：

衡量指标它问的是什么单独来看它不能确立什么
估算的有效小时数会话产生了多少产能？项目是否更早完成
交付周期工作是否更早完成？产出质量是否提升
PR 产出是否产生了更多变更？这些变更是否创造了业务价值

Wu 将它们呈现为三个匿名化的案例研究结果，而非一个普遍效应。该演讲并未提供将这些结果转化为通用生产力估算所需的计算方法、样本量或因果控制。

将部署模型应用于遗留系统迁移

迁移工作使企业问题变得具体。Wu 引入 Nubank 作为一个涉及 ETL 迁移的公开客户案例。Wu 回忆起 Nubank 的一次迁移，由 50 名工程师负责，使用 Devin 后在大约三分之一的时间内完成。他将 Devin 的贡献描述为自主完成，但他没有拆分人工提示、监督或审查的部分。人员配置和时间线的数字仍是他大致的回忆。

下一个例子涉及另一家大型拉丁美洲银行迁移税务识别系统。Wu 报告以大约一半的工程工作量完成了该银行的税务识别迁移。他将这项工作与 COBOL 和 JCL 等遗留环境联系起来，在这些环境中专业知识可能难以找到。展示的案例研究幻灯片包含 Itaú 的标志并描述了 COBOL 迁移的成果；它与前面的 Nubank 案例是分开的。

将验收与工程产能区分开来

Bilt 提供了另一种类型的例子：持续的工程产出，而非一次有明确边界的银行迁移。Wu 在讨论 Bilt 的合并和 PR 验收时提到了数量级的提升，但没有定义其基线或分母。这一措辞并不能证明验收率有精确的提升。

Wu 报告称，Bilt 的每周产出相当于十多名工程师的工作量。这是一个独立的产能主张，而不是表达 PR 验收的另一种方式。他在进行比较时强调了 Bilt 现有工程师的实力：其预期的价值在于扩展一个有能力团队的产出。

让客户成功成为共同责任

这一运营模式依赖于超越嵌入工程师和收集反馈的承诺。Cognition 也将内部价值观应用于客户合作。一次成功的部署能让在组织内部引入 Devin 的人获得他们可以为之背书的可见成果，从而将他们转变为内部拥护者。

有时这种承诺意味着物理上的接近。Wu 描述了将某人派往巴西约两个月，住在客户附近并帮助部署取得成功。与贴近相伴的是对正确性的关注：需要改进的工程实践应当被提出并反馈到产品中，不能让自尊心阻碍团队解决这些问题。

这使得销售、售后和工程之间的界限，不如对客户结果的共同责任重要。每个人都为将产品成功推向市场做出贡献。Wu 最后强调了紧迫性：这项工作处于棘手的客户问题与大规模软件变革的交汇点，每一秒都很宝贵。这个角色的职责是让这项工作持续推进——从具体的客户需求出发，经过交付，再回馈到更好的产品中。
