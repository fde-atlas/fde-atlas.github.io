Palantir 的 AI FDE 实现前沿部署自动化，而中国仍在招募人类 FDE

原标题：Palantir's AI FDE Automates Forward Deployment While China Still Recruits Human FDEs

BestHub · 2026-09-18 · 约 8 分钟读完

摘要

文章分析 Palantir 的 AI FDE 如何自动化前沿部署工程中的执行环节：在 Foundry 内完成数据集成、Ontology 维护等任务，并通过 AIP Evolve 让 Agent 基于评测自主优化模型与提示词，演示中单次调用计算成本下降 65%。国内企业则用 AI FDE 将串行交付流程并行化，某招股书项目从约六个月压缩到两周完成七至八成初始建模。作者认为定义正确标准与错误边界仍需人类，FDE 角色正转向设计 Agent 的工作空间。

要点

  • Palantir AI FDE 于 2026 年 3 月 GA，在 Foundry 内自动化数据集成与 Ontology 维护。
  • AI FDE 遵循最小权限原则，仅开放任务所需工具与上下文，写入需人工确认。
  • AIP Evolve 让 Agent 团队自主换模型、改提示词并跑评测，成本降 65%。
  • 国内实践中 AI FDE 将串行交付并行化，招股书建模从六个月缩至两周达七至八成。
  • 定义正确标准、上下文与错误边界仍是人类 FDE 的核心职责。

Palantir 的 AI FDE：从人工执行到 Agent 自动化

Palantir 长期以来一直将前沿部署工程作为其核心产品开发机制——工程师驻场嵌入客户现场，然后将真实问题反馈给核心产品团队，这一过程被称为“人类版反向传播”。2026 年 3 月，Palantir 的 AI FDE 正式全面上线。它在 Foundry 内运行，执行数据转换、管理代码仓库、维护本体，并将自然语言任务转化为具体的 Foundry 操作。到 2026 年 9 月，Palantir 推出了 AIP Evolve：用户指定优化目标、目标、验证方法和允许的修改边界；随后一组 AI FDE 会搜索解决方案、修改现有 AI 系统、运行评测，并提交方案供人类审核。

Palantir 正在对 FDE 工作进行分解。凡是可以由上下文、工具、评测、权限和分支来定义的任务，正逐步交给 Agent 处理；而目标设定、正确性定义和生产上线决策仍由人类负责。

01 Palantir 首先自动化的是执行链，而非判断

人类 FDE 花费大量时间在具体的工程工作上：查找数据、理解模式、构建管道、修改业务对象、编写函数、维护仓库、测试和迭代。这些任务有一个共同的关键特征：它们都具备工具、状态、反馈和可验证的结果。AI FDE 首先自动化的正是这一层。

AI FDE 并非拥有完整企业访问权限的超级 Agent。Palantir 强调限制其可见范围：只提供当前任务所需的数据集、函数、分支、对象类型或文档。最佳实践明确建议只提供必要的工具和上下文。AI FDE 还会根据任务切换模式——数据集成会加载集成文档和工具；本体编辑会进入专用模式；函数编辑则会再次切换。Agent 可以在执行过程中更改模式和能力。Palantir 的理由是：一个 Python Transform Agent 不需要治理或 React 工具；多余的能力会增加干扰和错误调用工具的情况。由此得出一条实用的企业级 Agent 原则：让 Agent 可操作的世界尽可能小，而不是尽可能大。

第二个关键是闭环执行。在编写 Function 之后，AI FDE 会创建测试、运行 Eval、读取失败结果、诊断、修改并重新运行。自四月起，集成到 AI FDE 中的 AIP Evals 使完整的“编写 → 测试 → 观察失败 → 调整 → 编写”循环能够在 Agent 内部完成。这种 Action → Observe → Evaluate → Adjust → Action 的循环让自动化成为可能：模型不需要比人类更懂业务，它只需要一个稳定的“执行—反馈—纠正”循环。

尽管模型能力不断提升，Palantir 仍然保持着工程护栏。AI FDE 在当前用户的身份下运行——没有独立的超级账户。用户无法访问的数据，AI FDE 同样无法访问。写操作默认需要用户确认；高风险操作需要逐项审批；Branch 范围内的编辑可以预先授权；只读操作默认放行。所有操作都会进入 Foundry 现有的 Audit Log。

代码和 Ontology 变更不会直接进入生产环境。Palantir 建议 AI FDE 在 Branch 中工作，通过 Global Branch Proposal 或 Pull Request 提交，经人工审核后再合并。其理念是：Agent 可以出错，但错误被限制在可验证、可审计、可回滚的边界之内。

02 AIP Evolve 让 Agent 优化 Agent

以前，是人类指导 AI FDE：换这个模型、调这个 Prompt、改这个工作流。AIP Evolve 将人类输入抽象为四个要素：优化什么、目标是什么、如何验证、以及修改可以走多远。

Palantir 的官方示例：一个库存分配 AI Workflow 被认为成本过高。用户将“降低成本”设为 Goal，选择 10 个有代表性的 Test Cases，允许更改 Model 和 Prompt，并将迭代次数上限设为 5。AIP Evolve 协调多个 AI FDE：检查当前 Workflow、创建测试、尝试 Model Swap、调整 Prompt、运行 Evaluation。该过程会生成一张 Agent Graph，展示负责分析、测试创建、模型替换、评估、Prompt 工程和提案撰写的 Specialist Agents。

在演示中，系统运行了 3 轮。最终 Proposal：将 GPT-4o 替换为 GPT-5.4 Mini，并为两个 Prompt 添加 Guardrails。全部 10 个测试通过；平均 Compute Cost 从每次调用 204.6 降至 72.4 计算秒，降幅达 65%。

65% 这个数字是次要的；真正改变的是优化过程本身。以前，工程师发现成本过高时会手动分析：是不是模型太贵？Prompt 能否缩短？换更小的模型会不会影响准确性？需要哪些 Guardrails？然后再手动测试。现在，人类只需定义一个更高层次的问题：“我要降低成本，但不能出现明显的 Regression。”Agent 会在 Model-Prompt-Configuration 空间中搜索满足该约束的方案。

这与典型的 Coding Agent 回答“如何完成这项任务？”不同。AIP Evolve 回答的是“在成本、延迟、质量约束下，哪种系统配置最优？”其关键支撑是评测。AIP 评测定义测试用例、评估函数、预期输出，比较模型/版本，并观察非确定性模型的方差。只有当“好”成为机器可判定的标准时，Agent 才能知道一次改动是优化还是退化。因此，生产环境中的自我改进 Agent 首先暴露的并非模型智能的差距，而是一个更现实的问题：企业能否先定义“更好”意味着什么？

03 不止 Palantir：AI FDE 已在重塑真实交付

类似的转变也出现在中国的企业级 AI 交付中。在 2026 年 8 月 26 日的一场 DataFun 圆桌讨论上，从业者反馈，AI FDE 第一阶段的影响不只是“一个人干得更快”，而是把原本串行的 FDE 工作拆解为并行任务。

悦点科技分享道：传统上，FDE 按业务访谈 → 资料收集 → 本体发现 → 数据管线的顺序推进。引入 AI FDE 后，人类仍负责访谈，而 AI 同时提取信息；在数据调研阶段，AI 并行探查数据库 Schema、API 文档和主数据。旧的链条“访谈 → 文档 → 建模 → 数据 → 管线 → 验证”变为“访谈 / 文档 / 数据探索 / API 分析”并行推进 → 再汇入建模与验证。人类带宽不再限制能同时启动多少条工作流。

一个 IPO 招股书项目的具体数据：传统人工方式从业务理解到完成本体建模至少需要六个月。借助 AI，利用历史招股书和现有数据系统自动提取业务对象、关系和核心指标，约两周就完成了 70–80% 的初始对象、关系和指标映射。这并没有完成整个项目——指标计算逻辑仍需专家调优，动态业务逻辑仍难以一次到位；完整支撑一份招股书报告大约花了两个月，定性部分仍需专业人员处理。

这个案例说明的不只是“AI 取代 FDE”。AI FDE 首先压缩的是耗时、高度结构化、易于验证的前置工作，把人类时间推向判断密度更高的任务。圆桌参与者认为：如果 AI FDE 只是让更多人以旧的 FDE 模式去做咨询/交付，那不过是给旧模式换个名字；真正的推动力是把经典 FDE 工作 AI 化，让 AI 快速产出 0 到 1 的原型，再由人类引导其走向正确。

Palantir 与国内实践的起点不同——Palantir 自动优化模型/提示词/工作流；国内实践则首先自动化访谈提取、数据探索、业务建模和交付流程。但两者都指向一个共同模式：能够用 Context、Tool、Workflow、Feedback 和 Eval 来描述的 FDE 工作，最容易被 Agent 接管。

04 不容易被自动化的部分：定义“正确”

这就是为什么“AI FDE 取代人类 FDE”仍然为时过早。AIP Evolve 看起来高度自动化——更换模型、编辑提示词、运行测试、持续迭代。但三个关键决策仍然由人来完成：

定义 Agent 应该知道什么。模型擅长公开知识，但哪些内部业务规则、数据关系和历史经验必须进入 Context，并非显而易见。Context 太少 → Agent 会误解企业；太多 → 则是噪音。人类 FDE 的工作从“研究一切”转变为“决定什么进入 Agent 的工作区”。

定义什么算作正确。这是 AIP Evolve 的核心前提。将计算成本降低 65% 很容易衡量，但真实业务要混乱得多。客服 Agent 的准确率上升但投诉率也上升——这算优化吗？供应链 Agent 的平均成本下降但尾部风险的缺货增加——这可以接受吗？一个工作流从十步缩减到三步但遗漏了合规检查——这是效率提升还是倒退？所有这些都落在 Eval 上。Eval 不会从模型中自发产生；人类必须将业务上的“对”与“错”转化为测试用例、指标、约束和可接受的边界。

定义 Agent 可以错到什么程度。Palantir 允许 AI FDE 深度访问系统，并不是因为认为模型可靠，而是因为它保留了权限、工具审批、分支、Pull Request、人工审核和审计——将 Agent 的试错约束在可控环境之内。

这可能才是 AI FDE 对 FDE 角色的真正变革。过去，顶尖 FDE 的价值来自亲手执行：写 SQL、调试数据管道、集成 API、逐步把系统接入客户环境。往后，更多执行动作将转移给 Agent。人类 FDE 的核心问题变成：Agent 必须知道什么？什么结果算作正确？允许它在哪些地方出错？

中国当前对更多 FDE 的需求与 Palantir 的 AI FDE 并不矛盾。随着企业 AI 更深入地进入真实业务，人类必须首先把隐性的业务知识、权限、流程和判断标准转化为机器可用的 Context、Tools、Workflows 和 Evals。每一次完成的 FDE 交付都会留下一条新的可学习轨迹：这个场景需要什么 Context、调用哪些 Tools、何时升级给人类、什么结果可以进入生产环境。当这些经验被结构化之后，它们本身就成为 Agent 可以执行的对象。

Palantir 展示的并非“FDE 消失”，而是 FDE 工作变得可编程、可验证，从而可以被 AI Agent 接管。过去，FDE 优化 Agent；现在，Agent 优化 Agent。最难自动化的仍是最后一个问题：定义什么才算“更好”。
