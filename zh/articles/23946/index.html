Palantir导入案例分领域解析｜日本企业的推进方法与FDE的作用

原标题：Palantir導入事例を領域別に解説｜日本企業の進め方とFDEの役割

FDE総研 · 2026-08-21 · 约 16 分钟读完

摘要

文章按领域梳理 Palantir 的导入案例：政府与防务以 Gotham 整合分散情报，民间案例则集中在航空、制药、能源、制造等依赖现场数据的行业，几乎都使用 Foundry，产品选择更多由机密等级与采购主体决定。文中列举 Airbus 的 Skywise、Merck KGaA 合资的 Athinia、BP 合作及英国 NHS 最多 3.3 亿英镑的 FDP 合同，并指出 NHS 案例引发的患者数据争议说明共识构建成本不可忽视。日本市场以 SOMPO 合资与富士通战略合作为起点，导入通常经历业务限定、PoC、单部门上线、横向推广四阶段，难点在于决策者分散、与既有 SIer 的角色划分及数据所有部门的共识。作者强调 FDE 的价值在于深入现场定义问题、把业务语言转译为数据模型并交付持续被使用的应用，其成果以是否被持续使用衡量；多数成效来自推进方法而非产品本身，企业可先在既有技术栈上复用这些方法。

要点

  • 政府防务用 Gotham，民间案例几乎全用 Foundry，产品区分取决于机密等级与采购主体。
  • 代表案例包括 Airbus Skywise、Merck KGaA 合资 Athinia、BP 合作及 NHS 约 3.3 亿英镑的 FDP 合同。
  • 日本以 SOMPO 合资与富士通合作为起点，导入分四阶段推进，PoC 到正式上线最难。
  • FDE 深入现场定义问题，成果以业务是否被持续使用与判断是否改变来衡量。
  • 多数成效源于推进方法，企业可先在既有技术栈上复用这些方法再评估是否引入平台。

Palantir的导入案例集中在哪些领域？

Palantir的导入案例集中在政府·防卫，以及航空、制药、能源等现场数据繁重的产业。

Palantir的产品线大致分为两类：面向政府、防卫与情报机构的Palantir Gotham，以及面向民间企业业务运营的Palantir Foundry（来源：Palantir官方网站“Platforms” https://www.palantir.com/platforms/）。导入案例的分布也基本符合这一划分。一类是整合高机密性、分散信息的政府项目；另一类是涉及设备、供应链、库存等物理运营的民间项目。

Palantir的导入案例很少被描述为“BI工具的替代”。公开案例中的大多数并不止于查看分析结果，还包括现场判断以及向业务系统的回写。FDE（Forward Deployed Engineer）深入客户现场工作，也被认为是因为Palantir的导入会深入到现场业务层面。

在政府·防卫领域，Palantir是如何被使用的？

在政府·防卫领域，Palantir被用于将分散的信息整合到统一模型中，以加快决策速度。

Palantir Gotham一直被用于在统一的通用模型上处理跨多个信息源的数据。其目的是让分析人员和指挥官能够在同一画面上掌握局势（来源：Palantir官方网站“Gotham” https://www.palantir.com/platforms/gotham/）。与美国国防部、美国陆军的合同，在Palantir的财报资料中被持续提及为主要收入来源。公共部门的销售额是事业支柱之一，这一点可以从Palantir的公开信息中得到确认（来源：Palantir Investor Relations https://investors.palantir.com/）。

在英国，2023年11月，NHS England公布将Federated Data Platform（FDP）合同委托给以Palantir为核心的联合体。合同规模被广泛报道为最高3.3亿英镑的多年期合同。作为处理公共医疗数据整合的导入案例，这是经常被引用的项目。

另一方面，NHS的项目围绕患者数据的处理也引发了社会层面的讨论。在阅读Palantir的导入案例时，不仅关注成功因素，还关注接受方为达成共识所付出的成本，会对实际工作更有帮助。政府·公共领域的案例比民间耗时更长，其原因在于达成共识而非技术要求。公共项目的成败，取决于是否具备能够将共识形成的设计也纳入提案的体制。

在民间企业中，哪些行业的Palantir导入案例最为突出？

在民间，航空、制药、能源、制造等拥有设备与供应链的行业中，Palantir的导入案例最为突出。

代表性案例是Airbus与Palantir共同构建的面向航空业的平台“Skywise”。该平台于2017年发布，作为在航空公司之间共享飞机运营与维护数据的机制而广为人知。主要用途是故障的预兆检测与维护计划（来源：Skywise官方网站 https://www.skywise.com/）。在制药·材料领域，Merck KGaA与Palantir于2021年成立了合资公司Athinia，处理半导体材料的供应链数据。在能源领域，BP与Palantir的长期合作已被公布，用于上游作业的数据应用。

领域主要使用的产品典型用途公开的代表性案例
政府·防卫·情报Palantir Gotham信息整合、态势掌握、决策支持与美国国防部、美国陆军相关的合同
公共医疗Palantir Foundry医疗数据协作、供需与候诊可视化英国NHS的Federated Data Platform（2023年合同）
航空·制造Palantir Foundry预兆性维护、生产与质量数据整合Airbus的Skywise（2017年发布）

看“主要使用的产品”这一列可以发现，民间的案例全部使用Palantir Foundry。产品的区分使用与其说取决于行业，不如说取决于机密等级与采购主体，这样看更接近实际情况。首先确认自己公司作为采购方属于哪一类别，比较研究的对象就不容易偏离。

Palantir导入案例容易产生的业务课题有什么共同点？

共同点在于：分散在多个系统中的现场数据，无法用于日常判断。

上表所列的案例虽然行业各异，但课题的结构非常相似。核心系统、设备日志、Excel、外部数据各自独立，数据核对依靠人工，判断依赖经验。而且这种判断并非月度分析，而是每天、每小时都在发生。

反之，如果业务只需单一 SaaS 即可完成，或只是查看月度报告的用途，那么引入 Palantir 这样庞大的平台就缺乏理由。在现场访谈时，有时会出现“据说什么都能做，所以想全公司使用”的需求。即便在这种情况下，先确认首个目标业务是否满足以下三个条件，反而更容易推进导入。

条件需确认的事项缺失时容易发生的问题
频率判断以每天或每小时的频率发生效果难以显现，无法产生持续使用的动机
数据割裂判断所需的数据分散在两个以上的系统中现有工具已够用，引入整合平台的理由薄弱
负责人能够以实名确定对该判断负责的担当者即使做出了可运行的系统，也没有持续使用的人

如果选择缺失任一条件的业务作为第一弹，即使做出了可运行的系统，也不会被持续使用。在评估初期就将这三个条件套用于候选业务，仅剔除不符合的，就能大幅缩小目标范围。

日本企业的 Palantir 导入案例是如何推进的？

在日本，多以与 SOMPO、富士通等国内大企业的合资、合作作为起点，从自用扩展到对外的形式居多。

Palantir 在日本市场的起步方式有其特点。不仅像在美国那样直接与客户企业签订大型合同，还通过与国内大型事业公司的合资、合作来建立立足点。日本企业在引入海外供应商的平台时，需要经过信息系统部门的审查、安全要求、与现有 SIer 的关系梳理等流程。采取合资、合作的形式，很自然地可以理解为是为了让国内合作伙伴承担这些流程。

将本文所涉及的公开案例按时间顺序排列，如下所示。

日本代表性的 Palantir 导入案例有哪些？

日本的代表性案例有两个：与 SOMPO 控股成立合资公司，以及与富士通的战略合作。

SOMPO 控股于 2019 年 11 月与 Palantir 成立合资公司 Palantir Technologies Japan，并公布了在护理、保险领域推进数据应用的方针（出处：SOMPO 控股新闻稿 https://www.sompo-hd.com/）。这一举措常被描述为整合护理业务中积累的现场数据，从而改善服务质量和运营效率。

富士通于 2020 年宣布与 Palantir 开展战略合作。此后，推进了 Palantir Foundry 在日本的提供，以及富士通自身业务变革的应用（出处：富士通新闻稿 https://pr.fujitsu.com/jp/news/）。供应商先在自己公司充分使用后再推广给客户的顺序，在日本市场更容易具有说服力。

企业时间形式主要目标领域
SOMPO 控股2019年11月成立合资公司 Palantir Technologies Japan护理、保险
富士通2020年战略合作Palantir Foundry 在日本的提供、自身业务变革

这两个案例的公开信息都以方针和体制的说明为主，公开具体削减金额或效果指标的案例有限。在制作面向公司内部的资料时，比较现实的做法是将海外案例的定量信息与国内案例的体制、推进方式的信息分开处理。若将两者混在一起，容易产生“在日本国内也能取得相同数值”的错误期待。

日本企业的 Palantir 导入按什么顺序推进？

通常按限定目标业务、PoC、单一部门的生产运行、向其他部门横向推广这四个阶段推进。

日本企业的数据平台导入，不仅限于 Palantir，通常也经历以下阶段。需要注意的是，每个阶段的决策者都会变化。

阶段期限参考主要工作决策者常见的失败
1. 业务确定2〜6周缩小目标业务和判断的范围、现场观察事业部门负责人目标范围过大，焦点不明确
2. PoC数月数据连接、本体（Ontology）设计、应用原型事业部门＋信息系统部门停留在好看的原型演示，未与业务连接
3. 生产运行数月以上权限设计、运营体制、与现有系统集成信息系统部门＋现场运营负责人未确定，项目被搁置
4. 横向推广6个月起向其他部门推广、培养内部人才经营层各部门重新开发，资产无法复用

最困难的往往是第 2 阶段向第 3 阶段的过渡。这在现场相关人员之间是普遍的共识。PoC 阶段以“做出了有趣的东西”就能达成共识。但生产运行如果不明确谁每天查看该界面、谁负责异常处理，就无法运转。此时暴露出来的不是技术问题，而是体制问题。

随着阶段推进，决策者从现场转移到经营层。因此，仅靠第 1 阶段动员的人员无法跨越第 3 阶段。如果从一开始就让信息系统部门参与，就可以避免将权限设计的讨论延后。

日本企业特有的受挫点有哪些？

容易成为障碍的是决策者分散、与现有 SIer 的角色梳理、数据所有部门的共识形成这三点。

受挫点发生的情况提前应对的措施
决策者分散事业部门、信息系统部门、经营层的审批分散，无人能单独推进一开始就明确各阶段的决策者
与现有 SIer 的角色梳理在数据连接阶段耗费大量协调时间在着手前确定核心系统维护的分工
数据所有部门的抵触因其他部门能看到本部门数据而遭到抵触，项目被退回从初期就动员所有部门的负责人，通过权限设计达成共识

第三个问题无法用技术解决，只能作为权限设计与治理问题来处理。如果跳过这一点直接推进“先收集数据吧”，之后会被打回重来。从讨论初期就把数据所属部门的负责人纳入进来，结果上往往是捷径。

在 Palantir 的导入案例中，FDE 都在做什么？

FDE 深入客户现场，将业务语言翻译成数据模型，并一直做到把可运行的业务应用开发完成。

Palantir 的导入案例之所以被讲述为“业务变革”而非“工具导入”，背后在于 FDE 这一职位。FDE 是 Forward Deployed Engineer 的缩写，指被前方部署到客户现场的工程师。其角色不是接收需求规格说明书后进行开发，而是深入现场定义课题本身，进行实现，并推进到实际被使用的状态（来源：Palantir 官网“Careers” https://www.palantir.com/careers/）。

FDE 在导入初期从哪里入手？

导入初期的 FDE，会先于数据基础的设计，从把要改善的决策收敛为一个开始。

首先要做的是明确谁、在何时、决策什么。如果是工厂，就确认生产计划的负责人；如果是物流，就确认派车的负责人，每天查看哪些信息、做出什么判断。先把对象收敛为一个，再反推所需数据并逐一接入。

这个顺序与日本系统开发中常见的“先建全公司数据基础”的做法正好相反。不过，两者并非谁对谁错的关系。

推进方式能得到的东西作为交换付出的东西
业务起点（FDE 型）成果显现快整体设计变成事后补做
基础起点（全公司数据基础先行）整体设计的一致性成果显现需要时间

Palantir 导入案例中被讲述的速度感，应理解为选择业务起点后的结果。

FDE 的成果在哪里衡量？

FDE 的成果不是以交付物衡量，而是以现场是否持续使用、判断是否发生改变来衡量。

与一般的委托开发并列对比，FDE 评价标准的差异就一目了然了。

视角一般的委托开发／SIerPalantir 型 FDE
起点客户写好的需求规格说明书通过现场观察自行定义的课题
主要成果物符合规格的系统在现场被使用的业务应用以及发生变化的运营方式
成功的判定验收、交付持续使用、判断的改变、向下一个业务的推广
与客户的距离以窗口对接人为主从现场负责人到经营层直接接触
要求的姿态遵守范围（scope）包括重新定义范围的提案

按照 Palantir 型 FDE 的标准，做出来的东西如果没人使用，成果就视为零。FDE 这种工作方式一方面被描绘得很有魅力，另一方面其高负荷也常被指出。其原因大多被认为在于这套评价标准的严苛。

从 Palantir 的导入案例能看出 FDE 需要哪些技能？

从导入案例可以读出，FDE 除了技术能力之外，还需要业务理解、沟通能力以及收敛范围的判断力。

技术方面，SQL、Python、数据建模、API 集成等基础是根基。但追踪导入案例会发现，决定成败的并不是技术的高度。能否从现场负责人那里引出真实的课题。能否对经营层说出“这次做到这里，这里不做”。即使使用同样的产品，结果也会因能否做到这两点而不同。

技能在导入案例中发挥作用的场景
技术能力（SQL・Python・数据建模・API 集成）数据接入与业务应用的实现
业务理解明确谁、在何时、决策什么
沟通能力从现场负责人那里引出真实的课题
收敛范围的判断力向经营层展示做与不做的范围

工程师如果想以 FDE 为目标，与其一上来就摆弄 Palantir 产品，不如在现在的职场直接对业务负责人进行访谈，做小东西让人使用，积累这样的经验更容易转型。即使招聘启事上罗列着产品名称，面试中问到的往往也是这类经验。

要在自己公司复现 Palantir 的导入案例需要什么？

复现所需的不是产品本身，而是限定对象业务、深入现场的人才，以及包括写回在内的设计。

参考 Palantir 导入案例的企业，其问题大多最终归结为“要达到同样效果是否必须用 Palantir”。产品固有的价值确实存在：本体论（ontology）、权限管理、包含写回在内的统一基础平台。不过，案例成果的相当一部分来自推进方式。如果只是推进方式，用现有技术栈也有做到同样事情的空间。

不用 Palantir 也能复现的部分是什么？

推进方式的大部分可以复现，但作为统一基础平台的一致性和权限管理的精细程度上会与 Palantir 产生差距。

区分内容对产品的依赖
容易复现把对象业务收敛为一个、深入现场定义课题、做小东西让人使用、设计到写回为止不依赖
容易产生差距将多个数据源放到统一的业务模型上，一致地处理权限、审计、应用与 AI自行构建需要相当的工作量

容易产生差距的部分，也是选择付费平台的主要理由。判断的基准有三个：需要集成的系统数量、权限管理的复杂程度、横向推广的计划数量。

情况适合的选择
对象为 1～2 个系统，且局限于单一部门用现有基础和应用开发往往就够了
跨部门，且需要精细控制可见范围自行构建会导致后续运营负担沉重，因此考虑统一基础平台

最初的 90 天应该确定什么？

最初的 90 天，要确定四件事：对象业务、负责人、成功指标、与数据提供部门的共识。

将导入讨论初期希望确定的项目，连同时间上的大致节点一起整理如下。

  • 第 1～2 周：确定对象业务 — 选择一个每天发生、决策者明确、目前依赖 Excel 和经验的业务。
  • 第 3～4 周：确定负责人 — 用实名确定事业部门侧的决策者和日常运营的负责人。可以兼任，但不能留空。
  • 第5〜6周：就成功指标达成共识 — 将指标聚焦到1〜2个现场能够认可的指标，例如“判断所需时间”“返工件数”等。
  • 第7〜10周：与数据提供部门达成共识 — 从目标数据的所属部门取得关于提供范围和可见范围的共识。
  • 第11〜13周：将首个原型交付现场 — 相比完成度，优先让现场能够实际操作并提出意见。

把90天中的大部分时间用于达成共识而非技术验证，可能有人会感到不解。然而，回顾那些中途受挫的项目，技术上不可行的情况其实很少。更多的情况是上述某一项在空缺状态下就贸然推进——这是我的切身感受。

Palantir导入的投资判断应该看哪些指标？

相比许可费，从目标业务的判断频率和单件改善幅度倒推计算，更符合实务。

在平台导入的投资判断中，人们往往只关注初期费用和年度许可费。如果将比较对象设定为“现状的人工成本＋机会损失”，讨论就会变得具体。例如，假设每天需要30分钟的判断缩短为10分钟，且在3个据点×250个工作日发生，试算如下。

项目数值（基于假设的试算）
单次缩短时间30分钟→10分钟（缩短20分钟）
年度判断次数3个据点×250个工作日＝750次
年度削减时间20分钟×750次＝约250小时（根据上述假设计算得出的试算值）

此外，如果判断质量得到提升，缺货、库存过剩、设备停机也会减少。

不过，这一试算在导入前无法保证精度。正因如此，先聚焦第一期的目标业务，取得实测值后再判断是否横向推广，这一顺序至关重要。Palantir导入案例中所谈及的大型成果，大多也是在单一业务实绩的基础上逐步积累而来的。理解这一点，有助于调整公司内部的期望值。

另外，本文所记载的企业名称、时期、合同规模均基于各公司及公共机构的公开信息。对于未公开具体效果数值的案例，本文未记载相关数值。在贵公司自行研究时，请通过各公司的一手信息和报价进行确认。
