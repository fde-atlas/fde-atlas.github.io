内部软件访问申请：FDE 交互项目演练

FDECareer.work · 2026-10-26 · 约 5 分钟读完

摘要

FDECareer 发布一个面向 FDE 的合成演练项目：模拟员工申请软件访问权限，经历申请、审批、开通、查询与到期回收全流程。项目强调每个动作需有可核对回执，重复请求不产生新效果，响应丢失时通过查询恢复，回收失败则进入人工接管状态。网页版仅内存模拟，离线 Python 包用 SQLite 验证持久化与重启恢复，含 12 个预置场景。文章还给出改造任务与作品集撰写建议，明确所有数据为合成，不代表生产验收。

要点

  • 合成演练：申请、审批、开通、查询、回收五步全流程。
  • 核心原则：每个动作都要有可核对的回执证据。
  • 响应丢失应查询原回执，而非新建申请重试。
  • 回收失败进入 human_owned，需人工处置权限。
  • 离线包含 12 个预置场景，验证 SQLite 一致性。

本演练面向 FDE（Forward Deployed Engineer，前线部署工程师）。在这个独立设计的合成项目里，你需要让一份访问申请经历核验、批准、开通和到期回收。目标不是让模型自动决定谁能访问什么，而是把一次动作的依据、授权和业务结果连起来。

所有组织、软件、人员、申请和时间均为合成数据。网页不收集企业资料，不连接真实账号或模型；刷新会清空内存状态。Python 包额外验证 SQLite 持久化和进程重启后的恢复，不代表真实系统已通过生产验收。

项目目标与责任范围

合成组织 north 的 employee-01 申请 canvas-room 的 viewer 权限，理由是查看团队计划看板。访问有效至模拟日 10。manager-01 是具名审批人，执行服务负责资格检查、模拟开通、回执查询和回收。申请人、审批人和执行者分别承担不同责任。

本项目只模拟一个软件和一个申请对象。它不创建真实账号、发送消息、购买许可证，也不运行后台定时任务。模拟时间需要手动推进；到期只是触发回收的条件，回收失败后访问可能仍然存在。

成功条件是每个动作都有可核对结果：正常流程产生一个开通回执；重复请求不增加效果；批准后的变化会阻止新开通；响应丢失可以找到原回执；只有独立回收回执才能证明模拟回收完成。

流程与职责

固定提取输出保留申请编号、组织、员工、软件、权限、用途和到期日。资格与策略由程序判断，不让固定模型建议直接授权。审批绑定整份申请和策略版本；实际开通前重新核验。网页中选择角色只是教学切换，真实应用必须从可信服务端身份得到组织与角色。

业务对象与动作契约

对象或动作 本练习约定 应核对的证据
申请 组织 north，viewer，到期日 10 完整结构化载荷
批准 manager-01 确认精确载荷与策略版本 approval 中的 request 与 policy_version
开通 同一申请最多一个模拟效果 grants 长度与原回执
结果查询 查询已有业务效果，不重新创建 receipt_recovered 与 grants=1
回收 到期后执行，记录独立效果 revocations 长度与回收回执
接管 回收失败后停止自动开通 human_owned，回收效果仍为 0

这些约定是教学设计，不是通用访问控制标准。申请编号只是练习中的稳定键；真实服务还必须规定键的作用域、载荷冲突、保留时间和下游查询接口。

先选择场景，按“下一步”推进。每一步会显示即将模拟的角色；可以主动切换角色，观察职责检查。批准前后分别查看结构化证据，比较 payload、策略版本与回执。右侧故障注入和模拟时间用于自主实验；偏离预置步骤后，页面不再将当前运行标为预置场景通过。

“运行场景集”会在相互独立的内存状态中检查全部预置用例；它不会替代你当前逐步练习的状态。导出记录包含当前状态、事件、场景版本和已运行的场景集结果。导出在本机完成，没有上传。

异常与恢复：先确认发生了什么

正常开通后丢失响应，调用方得到 outcome_unknown，系统里已经有一个效果。下一步应查原申请的回执，恢复到 receipt_recovered，而不是生成另一个申请编号来重试。网页的“模拟重启”仅复制内存快照；离线包会实际关闭并重开 SQLite 连接。

回收失败是另一类问题。系统保留现有开通记录，状态进入 human_owned，回收效果仍为零。人工必须检查实际权限并完成处置，才能在真实系统中关闭事件。切断自动开通有助于控制后续动作，但不能替代权限回收。

批准后改为 editor、撤销审批人权限、改变策略版本，分别得到 approval_invalid、approver_inactive、policy_stale。它们都应在新效果产生前被识别。不要因为新权限也被软件支持，就让原批准覆盖新的业务动作。

下载后在本地复现

解压完整包，进入 offline-lab，使用 Python 3.10 或更高版本运行：

python3 lab.py --db access-lab.sqlite --output results.json
python3 -m unittest discover -s . -p 'test_lab.py' -v

首次命令应输出 passed: 12；重复使用同一数据库应得到相同事件与效果数量。需要从头实验时换一个数据库路径，保留旧文件作为证据。包内 README 逐项列出预期终态，scenarios.json 与网页使用同一版本。

本例在 SQLite 的一次事务里提交状态、效果和事件，只证明本地一致性。真实外部身份平台与数据库之间不共享这次事务；接入时仍需下游幂等、结果查询、对账和人工升级。固定输出也没有测试真实模型的提取质量。

改造任务与作品证据

先增加“申请在执行前已过期”的拒绝用例，再增加“批准后员工停用”的测试。对每个变化写出预期和实际结果，解释为什么开通次数应该保持为零。不要直接改预期文件来消除失败。

完成后保留需求范围、对象关系、一次失败运行、修复差异、完整测试输出和接管说明。作品集中写清“合成训练项目”，区分平台提供部分与自己新增部分；没有真实客户采用数据时，不填写上线规模、节省金额或业务提升比例。
