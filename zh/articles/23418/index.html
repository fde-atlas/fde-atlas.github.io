FDE 如何讲解系统架构：C4 模型两种讲法

FDE Times · 2026-11-18 · 约 5 分钟读完

摘要

这篇指南讨论 FDE 如何用 C4 模型向不同受众讲解同一个系统：面向运营总监用系统上下文图加权衡说明，帮助其快速做决策；面向客户首席工程师则用容器图、运维手册等交付物，支撑其离场后的独立运维。文章以保险公司理赔 AI Agent 为例，给出两种讲法的具体写法，并强调两份材料必须出自同一个模型，避免承诺与配置脱节。

要点

  • FDE 至少要把同一系统讲两遍：对总监讲决策，对首席工程师讲运维。
  • 上下文图面向非技术受众，容器图才出现技术选型，两图须同源。
  • 权衡说明应以听众能回答的问题收尾，如“等几分钟可否接受”。
  • 常见错误包括过度简化、细节过多、以及拿幻灯片充当交接文档。
  • 作品集中并排展示两版讲解，可同时证明技术深度与沟通判断力。

总监需要一段话来拍板，客户的首席工程师需要足够细节，在你离场后独立运维系统。

要点速览

  • 先选受众，再定讲法：总监关心决策，首席工程师关心运维。
  • 上下文图连非技术读者也能看懂，技术名称只出现在容器图上，两张图必须出自同一个模型。
  • 技术版是你离开项目后客户工程师会打开的东西，要把它当作交付物来做。

系统半夜 3 点出故障时被叫起来的人，很少是当初批准它的人。前线部署工程师（FDE）通常至少要把同一个系统讲两遍。第一遍在会议室里，对象是运营总监：他签批预算，向管理层负责。第二遍对象是客户的首席工程师：你离开项目很久以后，半夜处理故障的值班人是他。

这两场会需要两种说法。FullStack 写道，FDE 必须向永远不会读代码的人解释技术权衡。Palantir 更进一步，把这项工作拆成两个角色：据 Oxagile 介绍，Echo 角色负责使命、利益相关方和客户采用，Delta 角色负责技术执行。

一个人单干时，两个角色都得自己演，而且两份讲解要出自同一个模型，彼此不能矛盾。

每类受众带着不同的问题而来

Lucidchart 建议先想清楚受众是谁，再选择讲法。在 FDE 项目里，这个问题的答案相当具体。

总监想知道系统会给他的工作带来什么变化，以及他需要做什么决定。首席工程师想知道什么跑在哪里、哪里可能出问题、出了问题由谁来修。

C4 模型正好提供两个对应的层次。根据 C4 文档，系统上下文图可以拿给非技术人员看。它的受众不需要了解技术，所以稳妥的做法是只画人和软件系统。

容器图位于下一层，面向开发和运维人员。它展示高层架构、主要技术选型以及各容器之间如何通信。两张图描述的是同一个系统，所以你对总监的承诺，会和你交给工程师的配置保持一致。

图本身也有优势。Lucidchart 认为，视觉内容比只靠读或听的概念更容易学会，也记得更久，所以一张四个框的图，效果往往胜过三页文字。

一个理赔系统，讲两遍

看一个假设的案例。你为一家保险公司部署了一个智能体：它读取理赔邮件，提取字段，再放到界面上供理赔员审批。有一个决定必须做：邮件一到就立即处理每笔理赔，还是先把理赔放进队列依次处理。

给总监的版本以一张四个框的上下文图开场：提交理赔的客户、理赔员、公司现有的保单管理系统，以及 AI 模型提供商。图上没有任何一条箭头写着数据库的名字。

接着是一段权衡说明，写到让总监读完就能直接回答：

“有两个方案。方案一：邮件一到就读取每笔理赔，理赔员几乎立刻就能看到结果。代价是，如果外部 AI 服务变慢或宕机，部分理赔需要重新提交。方案二：理赔进入队列，逐一读取，几分钟后出结果。换来的是，即使 AI 服务出问题，也不会丢失任何一笔理赔。团队建议采用方案二。只需要您确认一件事：对目前的理赔审核流程来说，等几分钟可以接受吗？”

给首席工程师的版本，是同一个系统的容器图。图上有邮件接收服务、队列、调用模型 API 的 worker、存放提取结果的 Postgres 数据库，以及供理赔员使用的 Web 应用。

到这里，话题就变成：允许重试几次，失败消息存在哪里，告警设在哪里，队列积压时谁来值班。

下表把同一个决定用两种口径并列：

方面 对运营总监 对首席工程师
决定 等几分钟是否可以接受 从同步处理切换为队列加 worker
风险 理赔可能需要重新提交 调用模型 API 超时、消息丢失
缓解措施 不会丢失任何一笔理赔 有上限的重试、存放失败消息的位置
会后的任务 回答是或否 接收运维手册和值班表

别让两个版本变成两个故事

从单一模型开始：列出参与者、系统和容器，放在全团队共同编辑的一个文件里。先画上下文图。如果不提技术就画不出这个系统，说明你可能还没弄清它为谁服务。

然后写权衡说明。The Hustling Engineer 建议，开头先讲这个概念为什么对听众重要，并始终把技术工作和具体结果挂钩。所以这段话应该以一个听众能回答的问题结尾，比如“等几分钟可以接受吗”。

The Hustling Engineer 还建议用日常物品和经历来类比，让复杂概念更好理解；实在绕不开的术语，要给出定义。

试着把“延迟”换成“等几分钟”，把“重试”换成“自动重发”。队列可以比作银行的叫号机：先到先办，某个窗口暂时关闭时，也不会有人被跳过。

最后才画容器图，组件名称从同一个模型里照搬，再加上技术信息。收尾时，请总监用自己的话复述这个决定。如果他复述出的正是你提出的那个问题，这次讲解就成功了。

常见错误来自两头

面对非技术受众，最常见的错误是简化过头，变得居高临下。a16z 描述 FDE 的工作方式是深入客户组织内部，理解业务背景，而这些背景恰恰装在你面前这些听众的脑子里。

运营总监比你更懂理赔审核流程，所以要用这个流程本身的语言。

相反的错误是细节太多。如果总监看的幻灯片上出现了某个开源库的名字，你多半是在讲给自己听。

最危险的错误出在工程那一侧：把给总监看的幻灯片交给首席工程师，就算是交接了。凌晨 3 点值班的人需要的是容器图、运维手册和已做出的决策；幻灯片帮不了他找到哪条消息卡住了。

最后一个错误是让两个版本逐渐脱节，比如对总监说“几分钟”，超时配置却允许等上一个小时。

把这项能力变成简历上的证据

FullStack 把优秀 FDE 的两项要求并列：资深工程师的技术深度，以及与非技术人员一起处理没人说清楚的问题时的判断力。简历上的一行字很难体现这一点，文档却可以。

在作品集里，把同一个项目的上下文图、容器图和权衡说明并排放，每份都标明目标受众。面试官能一眼同时看到这两项要求。

看招聘启事时，留意那些要求你同时与技术和非技术利益相关方合作的条目。它们意味着面试可能会让你把一个系统讲两遍。提前拿一个你做过的系统计时练习：给总监讲两分钟，给首席工程师讲十分钟。

在你离开项目那天，总监会记得自己做过的决定；队列第一次积压时，首席工程师会打开你留下的文档。每份讲解都应该为那个时刻而写。
