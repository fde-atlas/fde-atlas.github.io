Factory 是如何开展前沿部署工程的

原标题：How Forward Deployed Engineering is done at Factory

AI Engineer · 2026-06-15 · 约 12 分钟读完

摘要

Factory 联合创始人兼 CTO Eno Reyes 在 AI Engineer World's Fair 2026 的演讲中阐述其前沿部署工程实践：部署工程师不是做定制咨询，而是把大客户环境中的真实工作流反馈回产品，推动产品能在客户环境中“自组装”。演讲提出软件工厂的三项基础（模型无关、数据与轨迹访问、企业治理），强调确定性验证（lint、类型检查、安全扫描、端到端测试）是延长 AI Agent 自主工作的前提，并主张先定义可验证的完成标准再消耗推理资源。Reyes 称 Factory 自身自主度约 15–20%，内部法律工作流已近乎完全自主维护，而终端 harness 因缺少视觉验证器仍无法闭环修复闪烁等问题。扩展策略是打造可被其他团队复制的示范代码库。

要点

  • 部署工程师是产品反馈渠道，Factory 拒绝把代码现代化当咨询服务出售。
  • 软件工厂三基础：模型无关、数据与轨迹可访问、企业级治理。
  • 确定性验证决定 Agent 自主度，验证循环越多，可承担的任务越长。
  • Missions 要求先定义可验证的完成标准，曾自主迁移超 5000 万行代码库。
  • Factory 自主度约 15–20%；内部法律工作流近乎 100% 自主维护。

一名驻扎在客户处的工程师究竟应该做什么？

当一家软件公司将工程师派驻到客户的组织内部时，这些工程师要交付的是什么：定制化的安装、一个完成的项目，还是一个更好的产品？前沿部署工程源于 Palantir 将工程师置于客户真实需求一线的做法。该专题的介绍将 OpenAI、Anthropic 和 Google DeepMind 列入正在扩充这类团队的公司之列，同时还有一个包含 Anthropic、Cursor、Factory、Ramp 和 Decagon 的专题环节。Factory 的视角来自联合创始人兼 CTO Eno Reyes，他此前曾在 Hugging Face 和 Microsoft 从事机器学习和软件工程工作。

职位名称并不能回答这个问题。派驻工程师可能更贴近产品或工程，代表客户或与客户并肩工作，把更多时间花在编写代码上，或花在协调人员与战略上。从历史上看，派驻往往是一种获取权限的要求：代码库、数据流和集成点都位于客户的组织边界之内。但这种安排如今涵盖了若干截然不同的业务。

模式工程师交付的内容
专业服务代表客户完成的工作
客户定制适配围绕单一客户改造的平台
新应用在客户环境中构建的新系统，可能基于该平台

前沿部署工程师、派驻工程师、应用 AI 工程师等头衔可能掩盖这些差异。理解交付模式比选择头衔更重要。

Factory 不想承接的现代化需求

设想一位客户已经获得了代码库现代化的咨询报价，并请 Factory 承接这次迁移。Factory 的目标不是把该项目作为服务来执行——即使其工程师会使用 Factory 自己的产品。Reyes 的理由既有经济层面的，也有技术层面的：咨询业务可以在不充分改进产品以支撑更大业务的情况下产生收入。

部署工程师是客户到产品的反馈渠道。 Reyes 称他们为“产品的矛尖”。他们从工程管理层以及 Factory 最大、最关键客户的日常一线工程师那里收集信息：开发实际是如何进行的、人们如何使用 AI，以及产品在哪些地方无法契合。这些信息会回流为快速的产品改进。期望的结果是产品能够在客户环境中有效地自我组装，而不是需要持续投入嵌入式人力。

这仍然需要大量的客户工作。必须有人理解环境、梳理其工作流，并论证改变这些工作流为何能带来回报。Factory 提供构建软件工厂的基石；部署工程师则帮助把这些基石与客户实际的开发流程和业务成果连接起来。

从输入信号到受监控的部署

每个软件组织其实都在运行一座隐性的工厂。客户对话、缺陷报告、Slack 或 Teams 讨论，以及高管指令作为信号进入。这些信号权重不同；人们会对它们排定优先级、分诊，并把其中一些转化为计划。开发者随后把计划转化为对事实源（通常是代码库或工程系统）的更改。

更改要经过验证：代码评审、QA、安全评估、静态应用安全测试（SAST）、linter 和类型检查器。检查通过后，组织进行发布和部署。对已部署软件的监控会产生更多信号，从而闭合这个循环。Reyes 指出，大多数组织对这个循环的监测都很差：各个阶段是存在的，但阶段之间的转换和反馈尚未被充分理解，无法可靠地自动化。

自主化的目标是一条从信号到部署的不间断路径。 这并不意味着把人类从工程中移除，而是改变他们介入的位置：人们构建并改进工作流经的系统，而不必打断每一次单独的更改。要达到这种状态，需要理解并改造每个阶段，包括阶段之间的交接。

软件工厂是建出来的，不是买来的

平台可以提供框架，但组织仍然必须投入建设自己的工厂。Reyes 指出了这项投入的三大基础：

  • 模型无关性： 与单一模型绑定的工厂既面临更高的成本，也受制于提供商关于什么能被构建的决策。
  • 数据与追踪的访问权限： 客户需要了解流经系统的信息，才能理解并演进它。
  • 企业治理： 必须由集中式控制来决定信息可以流向何处。

Factory 的 Droid 是旨在提供这些基础的 Agent 框架。数据访问不应与自动记录每条消息相混淆：Factory 当前的数据流文档将消息内容追踪描述为可选且由客户自行配置的功能。

Reyes 介绍说，金融、医疗和政府领域的客户在物理隔离（air-gapped）环境中运行 Droid。一位同事举的潜艇例子让这一预期边界令人印象深刻：整个软件工厂可以完全封闭运行。具体而言，当前的部署文档要求在完全物理隔离运行时使用内部模型端点和遥测收集器，并以离线方式导入制品。

让部署可重复，并明确业务价值

部署工程师必须对构建模块有足够的了解，才能帮助客户搭建其工厂，同时不断改进产品，实现一键式自组装。Reyes 提到拥有数万名员工、可能数十万名工程师以及数万个代码库的组织。在这样的规模下，手动安装和调整每个实例不可能成为运营模式。自组装是产品方向，而不是跳过对环境理解的借口。

成果故事必须从一开始就清晰明了。Reyes 给出了一个示例场景：经过 AI 代码审查、QA 和安全分析的变更，遇到 Bug 的可能性降低 87%。随后他梳理了提议的因果链：将 Bug 率降低一定幅度，提升客户满意度，并将这一提升与收入、增长或新业务联系起来。这个百分比是假设性的；真正有用的要求是将工程干预与业务目标关联起来。做到这一点既需要工程判断力，也需要业务知识。

讲解运营模式是部署工作的另一部分。许多组织缺乏自主性成熟度模型，也没有成为自主软件组织的路线图。工程师必须学会演进、优化和扩展一个构建软件的系统，而不是亲自操作每一块软件。这种抽象层次的提升即使对经验丰富的工程师来说也存在学习曲线。

开发者体验从业者已经在思考如何赋能其他开发者。愿意深入技术领域的产品经理也能胜任这项工作，习惯了高质量开发环境的工程师同样可以。工作流设计将反馈渠道扩展到整个产品：企业管控、Droid、编排工作流、可观测性、成本控制、自动模型路由以及 harness 质量都可以通过与各类客户组织的紧密合作得到改进。

验证让更长时间的自主工作成为可能

Agent readiness 始于确定性的反馈。代码检查工具、类型检查器、安全扫描或端到端测试都会产生 Agent 可以据此行动的结果：改动通过或不通过。Reyes 用代码库中存在多少这样的验证循环来描述就绪程度。反馈越多，Agent 就能在更复杂任务上工作更长时间，而无需人类告诉它们是否走在正确的轨道上。

一个简单的验证入口可以说明这一机制。在一个已经定义了这些脚本的项目中，shell 只暴露一个通过/失败的结果，同时保留各项单独的检查：

bash

#!/usr/bin/env bash
set -euo pipefail

npm run lint
npm run typecheck
npm run security:scan
npm run test:e2e

失败的命令会中止整个序列，并暴露出一个需要修复的具体问题。通过则意味着这些检查接受了改动；它并不能证明这些检查从未涉及的性质。随着 Agent 任务变长，这一区别会变得越来越重要。

Missions 通过一个长时间运行的 harness 将这一原则应用于困难但可验证的知识工作。Reyes 描述说，输出质量与验证工作的能力成正比。其实际含义是，在提升自主性的过程中，应当把投入验证能力作为其中一部分，而不是把验证视为仅在 Agent 完成后才进行的检查。

Factory 提供了扫描就绪度差距的工具。Reyes 估计，Droid 可以按需修复大约 30–40% 的低垂就绪度问题，同时描述大约 60% 可能需要改变工作流。这些是没有明确评估范围的粗略估计。一些较难的改动涉及人：更严格的自动化检查可能让人觉得过于吹毛求疵，草率地引入它们可能会打断人类的开发流程。部署工程师必须在改进反馈系统的同时，理解已经在这个系统中工作的团队。

在消耗推理之前先定义完成标准

Missions 将大部分人类参与转移到规划上。它的运行流程很直接：

  • 指定一个值得解决的、有边界的任务。
  • 用可验证的方式定义“解决方案已完成”意味着什么。
  • 让测试框架持续针对这些条件工作，直到任务完成。

决定性的特征不仅仅是任务可以被描述，而是完成与否可以被检验。Reyes 提出了一个宽泛的主张：凡是能够通过验证其所需的验证系统来表达的问题，都可以用当代 AI 解决。当前的 Missions 指南在操作上更为受限：它要求可脚本化的验证，并讨论了错误、干预和恢复。

Reyes 报告了对包含 3000 万、4000 万以及超过 5000 万行代码的代码库的全自主迁移。他没有提供客户身份、验证标准、耗时或人工协助的细节，因此这些例子只是确立了他主张的规模，而非一个可复现的迁移基准。配套的幻灯片从有界的任务出发，经过多步骤任务，扩展到所有知识工作，并在这一演进过程下方标注了自定义技能、编排文件、作为上下文的验证以及人工检查点。

他描述的其他应用超出了代码迁移的范畴：在生物医学和医疗健康问题上的高级深度学习工作，以及金融机构使用 AI Agent 进行股票研究。在后一个例子中，工作包括构建和比较股票模型，并构建能够在其基础上进行反向传播和/或交易的系统。这些是围绕可评估产出组织知识工作的另外一些例子。

这些都不是简单的下载、安装然后点击开始按钮。必要的投入从手动解决任务转向准备一个能够验证其解决方案的环境。如果没有做好 Agent 就绪准备，客户可能连一个能力极强的系统都无法从中受益。Reyes 将这一点与模型后训练中的密集奖励联系起来：频繁的验证信号有助于让工作持续朝向长期目标。运行时检查在这里提供反馈；这一解释并不意味着部署的测试框架会在线训练模型权重。

打造一个其他团队能够识别的典范

一个部署团队不可能亲自改造每一个代码库。扩展策略是先在少数几个地方树立模型，然后让客户自己的团队将其推广到整个公司。Reyes 用迪士尼的 Epcot 作类比：一座原本打算作为典范的城市变成了主题公园。按照他的说法，其城市规划和交通理念仍然影响了后来的城市，包括在此之前半个世纪里建造的城市。

有用的软件对应物是一个可运行的代码库，它让另一种软件开发方式变得可见且可实现。其他工程师能够识别这种模式，并将其引入自己所在的组织部分。但示例可能变得过于先进或过于特殊。如果同事们看到的是一个主题公园，而不是他们自身环境的一个可信版本，他们就不会去模仿。部署工程师必须展示有意义的进展，同时又不能让转型的成本和速度显得遥不可及。这正是 Reyes 关于“未来分布不均”这一观察的实际意义所在：孤立的示例只有在他人都能够采纳时才有价值。

法律工作流可以闭环；终端闪烁问题尚不能

Reyes 报告 Factory 的人工干预前自主率约为 15–20%，而自主率（autonomy ratio）处于接近 90% 的区间。他随附的解释提到了中断前的人类和 AI 行为，但并未足够清晰地定义分母，因此无法调和这两个数字。当前的 software-factory 产品页面 则将自主率定义为由 Agent 端到端完成且无需人工介入的已合并工作；这一较新的定义不应追溯应用于这些已报告的数字。Reyes 还表示，一些客户的代码库比 Factory 的更自主，因为它们的工作受到更多约束。

这种约束指向了完全自主可能最先到来的领域：受控的内部工具。Reyes 将 Legal Droid——Factory 的内部法律工作流——描述为实际上 100% 自主维护的。它与核心 Droid 框架的对比颇具启发性。基于终端的框架仍然存在视觉问题，而 Factory 缺乏足够的验证器，尤其是闪烁问题。由于没有可靠的方法来检测该缺陷，系统无法闭合修复循环。

工作流哪些因素促成或限制了自主性
受控的内部工具受限的范围使完成情况更容易验证
Legal DroidReyes 报告该法律工作流实现了自主维护
核心终端框架缺失的视觉验证器导致闪烁等问题无法解决

剩下的工作本身就是一项工程问题：构建能够验证困难属性的系统。人类视觉感知和对外部世界的认知之所以仍然有价值，正是因为它们有助于识别并形式化当前检查所遗漏的内容。

构建者、教育者与系统思考者

本说明介绍了 Factory 寻求的人才画像。前创始人可以帮助定义新兴产品领域，而不仅仅是执行既定的安装流程。Reyes 将软件开发生命周期中的各个阶段——代码审查、事件响应、QA 和测试——视为潜在的十亿美元级业务。这是他对机会的评估，而非已报告的收入。

该职位结合了多种能力：

  • 构建者： 将客户问题转化为可运行的系统和产品改进。
  • 传授者： 精通 AI，能与组织各层级的人沟通，并以高管风范将技术决策与业务关切联系起来。
  • 系统思考者： 设计反馈回路、建模数据，并理解工作应如何在复杂组织中流转。

这些技能汇聚于同一项任务：帮助客户构建一个能够日益自主维护和改进软件的系统，同时将所学反馈到产品中。
