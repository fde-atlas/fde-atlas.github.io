让 Claude Code 真正投入实际工作

原标题：Shipping Claude Code for real work

Anil Pervaiz — AI Agents & Automation Engineer · 2026-03-14 · 约 3 分钟读完

摘要

作者基于六个月在三个生产代码库中日常使用 Claude Code 的经验，总结出可扩展的提示模式与工程习惯。核心观点是把 AI Agent 当作承包商而非自动补全：给出示例、限定改动范围、先要计划。最危险的失败是看似正确实则错误的平滑 diff，因此必须逐行审阅，评审成为新的瓶颈。配套的项目文档、快速测试与类型检查等基础设施能显著提升效果。作者仍亲自处理安全敏感等高判断度代码。

要点

  • 把 Claude Code 当承包商下工单，而非自动补全。
  • 三个关键习惯：给示例、限定文件范围、先要计划。
  • 最危险的是看似正确实则错误的 diff，未读不合并。
  • Agent 写得快时，人工评审成为新瓶颈。
  • 安全敏感与高判断度代码仍需亲自编写。

这是一份在生产代码库上运行 Claude Code 的实战报告——哪些模式可以扩展，哪些看似成功的失败模式，以及我坚持的日常习惯。

在三个生产代码库上把 Claude Code 作为日常工具使用六个月后，我不再使用自动补全式的辅助编程工具了。区别不在于模型本身，而在于你如何与它协作。

以下是这份实战报告：可以扩展的提示词模式、看似成功的失败模式，以及那些能把一个聪明的助手变成真正队友的小型基础设施投入。

把它当作承包商，而不是自动补全

自动补全帮你完成一行代码，而 Agent 完成的是一个任务。思维上的转变是：不要按按键来思考，而要按工单来思考：“给这三个路由加上限流器，遵循现有的错误格式，然后给我看 diff。”你的请求越像交给一个称职承包商的工单，结果就越好。

真正可扩展的提示词模式

三个习惯起了主要作用：

  • 指向示例。“匹配这个文件中的模式”胜过任何长篇描述。
  • 限定范围。告诉它哪些文件可以改动，哪些不要碰。无边界任务会产生无边界的 diff。
  • 对任何非琐碎的任务，先要求它给出计划。花 30 秒审查计划，能在它写出 300 行代码之前发现错误的方向。

看似成功的失败模式

危险的输出不是那些明显有问题的，而是那种自信、看似合理的 diff——扫一眼能通过，却悄悄做错了事：一个什么都没断言的测试、一条被吞掉的错误路径、一个因为“不在范围内”而被跳过的安全检查。这与构建不产生幻觉的 Agent 是同一个教训：模型最危险的时刻，是它错了却表现得很流畅。解决办法简单且不容妥协——绝不合并你没有读过的代码。

审查成为新的瓶颈

当 Agent 写代码的速度超过你的阅读速度时，你的审查就成了约束。我顺势而为：更小的 diff、更清晰的提交，以及一个习惯——在合并前问自己“什么会让这段代码出错？”被 AI 编程工具坑惨的团队，正是那些让速度跑赢审查的团队。

把它变成队友的基础设施

几项廉价投入产生了复利效应：

  • 一份简明的项目文档，写明各项约定，这样我不用每次会话都重新解释技术栈。
  • 它可以自己运行的快速测试和类型检查器，让它获得反馈循环，而不是靠猜。
  • 小而可审查的提交，这样出了问题时我能准确看到错在哪里。

这些都不稀奇。这正是让人类团队保持高效的同一套规范——只不过 Agent 对它的回报更加明显。

我不使用它的场景

我仍然亲自编写最难的部分：安全敏感的代码、复杂的状态机，以及那些“95% 正确还不如不上线”的东西。Agent 在定义清晰的 80% 上很快。剩下的 20% 才是判断力所在，而客户付费聘请 AI 架构师，买的正是这种判断力。

Claude Code 并没有取代工程判断力，而是改变了我投入判断力的地方：打字更少，审查和决策更多。如果你想在自己的技术栈中实现这种速度，AI Lab 展示了我交付过的成果，你也可以预约通话来聊聊。

我为初创公司和团队交付生产级 AI——AI Agent、RAG、自动化——背后是十年的设计与 Webflow 功底。
