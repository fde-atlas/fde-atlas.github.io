面向客户环境的 IaC：在不拥有云的情况下使用 Terraform 和 Helm

原标题：IaC for Customer Environments: Terraform and Helm Where You Do Not Own the Cloud

Vibe Engines · 2026-07-31 · 约 15 分钟读完

摘要

这篇文章讨论前沿部署工程师在客户云账号中实施基础设施即代码（IaC）的实践。作者指出客户环境与自有环境的根本差异：权限受限、无出网、状态文件归属等。文章给出四个关键问题、无出网VPC的故障清单、代码组织原则、密钥处理模式和交接验证方法，并以3-AZ EKS部署为例说明端点规划。

要点

  • 客户环境部署前先问四个问题：账号归属、状态存放、谁执行、网络出口
  • 无出网VPC会破坏镜像拉取、依赖安装、日志和证书检查，且多在运行时才暴露
  • Terraform状态应存客户账号的加密桶中，密钥应通过引用而非值传递
  • 代码结构要让客户工程师一小时内读懂，新客户只需新增envs目录和tfvars
  • 交接需通过客户亲手执行、净室重建、runbook覆盖四操作、书面归属四项检验

在你自己的组织内部，基础设施即代码是一个已有良好默认方案的成熟问题。而在客户的账户里，这些默认方案几乎全都失效：你可能没有权限创建角色，VPC 没有通往互联网的路由，状态文件不能放在你的存储桶里，而且最终接手这一切的人从未用过 Terraform。技术是相同的，但围绕技术的一切都不同。

决定架构的四个问题

在写下任何一行 HCL 或 YAML 之前，先问清楚这些问题。每个答案都会排除一半的设计空间，而其中一个答错了，后期就不是修改，而是重写。

在专用账户中拥有完整管理员权限是最简单的情况，但很少见。更常见的情况是：共享账户带有权限边界，无法创建 IAM 角色，而且落地区（landing zone）的服务控制策略会默默禁止某些操作。第一天就要索取 SCP 列表和权限边界文档——否则失败模式就是在三周后的执行阶段才发现某项操作被禁止。

Terraform 状态必须存放在你离开后他们仍能访问的地方，而且它默认以明文包含机密信息。这意味着要在他们的账户里建一个存储桶，加密、开启版本控制、配置锁表，并且只允许负责运维这一小部分人访问。状态放在你的账户里，其便利性恰好只维持到项目合作结束为止。

你用笔记本电脑来执行部署只是第一阶段的临时方案，却往往会悄悄变成永久状态。目标应该是他们的流水线——他们的 CI、他们的审批关卡、他们的变更窗口。要明确规划向其迁移，因为一个只有已离场的供应商才知道如何执行的部署，最终会被他们的平台团队通过重建来解决。

这是最关键的问题。“这些子网有出站互联网访问吗？”如果答案是没有，那么容器镜像、软件包安装、模型 API、遥测和证书吊销检查全都会出问题——而且通常不是在执行部署时，而是在首次运行时，这更糟糕。极端情况请参见气隙部署。

区分你拥有的和他们拥有的

他们的 VPC、集群、IdP 和 KMS 密钥是输入，而不是你管理的资源。把它们作为变量接收，并使用 data source。在你的模块里创建 VPC 意味着一次

terraform destroy

可能会摧毁早于你存在的基础设施——这是一个真正无法挽回的错误。

在编写模块之前先写 PREREQS.md

列出他们的团队必须创建的所有事项的精确清单，包括 IAM 策略 JSON、子网要求和终端节点列表，逐字照录。这份文档就是他们的云团队要审批的东西，一个具体的请求几天内就能获批，而模糊的请求只会被安排进会议。

一切都做版本管理并固定版本

Provider 版本、模块版本、chart 版本、镜像摘要。在客户环境里，“上个月还能用”是一张要你亲自处理的工单。镜像应固定到摘要（digest）而不是标签——被移动的标签意味着一次无法复现的部署。

让模块保持平淡

不要用花哨的动态块，不要对

for_each

计算出的 map 做深度操作，不要手写抽象。读者是一位称职的工程师，但代码不是他写的，而且他之所以看它，是因为周五下午四点出了故障。为这种阅读场景优化，而不是为行数优化。

保持 Helm values 精简且有文档

每个环境一个 values 文件，每个键都注释说明它的作用以及修改后会发生什么。避免那种需要懂 Go 模板才能读懂输出的模板化；

helm template

输出应该能让不懂 Helm 的人也能检查。

你绝不能看到的密钥

你手中客户凭证的正确数量是零，而做到这一点是一个设计决策。

总会有人提出把数据库密码用邮件发给你。拒绝并给他们一个更好的方案是工作的一部分——而更好的方案几乎总是他们已经拥有的。

行之有效的模式

  • 他们的密钥存储是唯一事实来源：Vault、Secrets Manager、Key Vault，或由其中之一支撑的 Kubernetes secrets。
  • Terraform 通过 ARN 或路径引用密钥，绝不引用值本身。
  • 工作负载在运行时通过工作负载身份读取——IRSA、托管标识、联合身份。
  • 你拥有的是引用权限，而不是读取权限。
  • 轮换由他们负责，而你构建的东西在轮换发生时不会坏掉。

等着被写进报告的问题

  • 一个密钥在 terraform.tfvars 里，而它在 git 中，而 git 在你的 GitHub 组织里。
  • 一个密钥在 Helm values 文件里，经过 base64，因此算是“编码”过。
  • 一个凭证在你的密码管理器里，而项目结束已经两年。
  • Terraform state 存放在没有加密的存储桶里——state 以明文保存密钥。
  • 一个共享服务账号，三个人持有其凭证，却没有人轮换。

不要让他们的云团队去猜你需要什么——他们会为了给你解锁而过度授权，然后安全审查会在最糟糕的时机把权限削减回去。把策略写出来：精确的操作、精确的资源 ARN、适用的条件。每条语句附上一段理由说明。这是你能拿到的最快审批，而且起草过程往往会可靠地暴露出你申请了却并不需要的权限。这与企业身份中最小权限一节所讲的纪律是同一回事。

交付出去，让它活下来

一份只有你能运行的 IaC 交付物不是交付物，而是依赖。四个检查决定交接是否真实，而它们都是你可以验证而非仅仅声称的事情。

他们来执行它，你在旁观看

不是你在他们注视下进行应用。他们的工程师、他们的凭证、他们的流水线，在真实环境中做一个真实的变更。那一小时里出错的每一件事，都是你尚未还清的文档欠账，而且你会发现不少。

从仓库出发的洁净环境重建

销毁一个非生产环境，仅凭仓库将其重建，不依赖本地文件，也没有任何未记录在案的步骤。这是检验代码是否完整的唯一诚实方式——而它第一次几乎必然失败，这正是为什么你要在交接之前而不是之后运行它。

运行手册覆盖四个动词

应用、升级、回滚、销毁——每个动词都要有预期输出和一个具名的故障分支。销毁比人们想象的更重要：一个没人敢删除的环境，最终会变成一个没人敢修改的环境。

所有权被写下来

哪个团队拥有状态，谁审批变更，应用失败时该打给谁。这里的模糊不清，正是导致一次部署最终无人认领、漂移一年、然后被一个从不联系你的平台团队重建的原因。

事故期间总会有人在控制台里改动一些东西——凌晨两点这么做是合理的。真正的失败在于事后没人去对账，于是六个月后

terraform plan

提议销毁生产环境所依赖的资源，所有人都不再信任这个工具。按计划运行

plan

，对意外的差异发出告警，并把漂移当作一个有文档化响应流程的正常运维事件，而不是一种道德上的过失。

供应配置只是容易的那一半

难的那一半是权限沟通、安全审查和交接。这些内容在本课程的其他地方练习。

全景图：你交付什么，他们拥有什么，谁来应用

terraform destroy

无法触碰它。只有应用及其可观测性是你状态中的资源，而该状态存放在他们的存储桶里。虚线框是决定这一切能否运行的网络事实。

实战示例：3 可用区无出站流量 EKS 部署的端点规划

以本页的端点清单为例，集群分布在三个可用区（示意）。网关端点是路由表条目。每个接口端点会在你提供的每个子网中放入一个网络接口，带一个私有 IP。算一算你向他们网络团队要了多少东西。

1s3（网关）镜像拉取也会受影响：ECR 将层存储在 S3 中0 / 0
2ecr.api、ecr.dkr镜像仓库认证与清单：第一个 Pod 超时2 / 6

7eks、elasticloadbalancing集群与负载均衡器的 API 调用11 / 33

第 1 步是那个要花掉一天时间的步骤。团队添加了两个 ECR 端点，仍然遇到镜像拉取超时，却没有意识到层文件来自 S3。第 7 步的总数才是应该写进 PREREQS.md 的：11 个接口端点，每个端点都要有一个安全组允许来自工作负载的 443 端口流量，还要做一个私有 DNS 决策，以及 33 个私有 IP。在提问之前先检查子网。一个 /28 有 16 个地址，AWS 保留 5 个，剩下 11 个，所以每个可用区的一个 /28 会被端点完全用尽，没有给其他任何东西留出空间。

这些在生产环境和面试中的体现

  • 着陆区与 SCP在 AWS Organizations 着陆区中，服务控制策略可以拒绝某个操作，即使该主体在成员账户中拥有完整管理员权限。这就是为什么 SCP 清单是第一天就要提出的需求：一个在三周后才因你从未见过的拒绝而失败的 apply，是进度问题，而不是 bug。
  • 客户安全评审你的 PREREQS.md 和你编写的 IAM 策略就是他们安全团队要审批的内容。一个包含精确操作、资源 ARN 以及每条语句一句理由的请求，会被当作一份文档来评审。模糊的请求只会换来一场会议。
  • 定时漂移检查terraform plan -detailed-exitcode 在没有变更时返回 0，出错时返回 1，有待应用的变更时返回 2。在他们的流水线中按计划运行它，并对返回值 2 发出警报。这样“有人在凌晨 2 点在控制台里改了它”就会变成一张工单，而不是一个意外。
  • 面试版回答“把我们的产品部署到一个无互联网访问的银行 VPC 中”是常见的 FDE 设计题。先抛出四个问题（用谁的账户、状态由谁持有、由谁运行、网络通向哪里），然后是端点清单，最后是如何交接。HCL 是最无趣的部分。

自我检测

你已经添加了 ecr.api 和 ecr.dkr 端点，但 Pod 仍然处于 ImagePullBackOff 状态并超时。缺了什么？

S3 网关端点。ECR 通过自己的端点提供清单，但镜像层存储在 S3 中，因此层下载没有路由。这是一个免费的路由表条目，也是无出站流量构建中最常见的疏漏。

他们的 SCP 拒绝了 iam:CreateRole，而你的模块会创建工作负载的 IRSA 角色。你会怎么改？

不再创建它。把角色 ARN 作为输入变量，并把角色（信任策略和确切的权限 JSON）写进 PREREQS.md，由他们的团队来创建。它移到了所有权分界线的他们那一侧——受他们 SCP 管辖的东西本来就该在那里。

一次事故之后，计划中的 Terraform 计划想删除某人在控制台里添加的一条安全组规则。你要执行 apply 吗？

不要盲目执行。生产环境现在可能依赖那条规则。先弄清楚它为什么被添加。如果应该保留，就把它写进代码（或导入），让计划恢复干净。如果不该保留，就作为计划中的变更删除它。无论哪种方式，漂移都得到了有记录的响应，工具也保持可信。

从仓库进行的洁净室重建可以成功，但应用的行为与生产环境不同。你的镜像引用为 app:1.4。最可能的原因是什么？

标签被移动了。有人重新推送了

app:1.4

，因此重建在同一个名称下拉取了不同的字节。改用摘要（digest）引用镜像（

app@sha256:…

），这样同一个仓库始终部署相同的代码，重建也才能证明它声称要证明的东西。

快问快答

对于客户部署，Terraform 状态应该存放在哪里？

存放在客户的账户中——一个加密、启用版本控制的存储桶加锁表，访问权限仅限于将要运维该系统的人员。状态文件默认以明文形式包含机密信息，而且在项目结束后必须仍可由客户访问。把状态放在你自己的账户里，只在合作期间方便，之后就会变成一个孤立的依赖。

在无出站流量的 VPC 中，什么会出问题？

容器镜像拉取、构建或启动时的软件包安装、云存储 API 调用（即使是私有存储桶，其 API 端点也是公有的）、托管模型 API、日志和指标上报、OCSP 或 CRL 证书检查，以及 NTP。大多数问题在运行时而非配置时暴露。解决办法是：镜像仓库镜像、自带依赖、VPC 接口端点和网关端点、有 PrivateLink 的地方使用 PrivateLink，以及一个带导出流程的本地遥测收集器。

在部署过程中，你应该如何处理客户的机密信息？

最终你手里应该一个密钥都没有。他们的密钥存储是唯一事实来源，Terraform 通过 ARN 或路径引用密钥而不是引用值，工作负载在运行时通过 IRSA 或托管标识等工作负载身份读取密钥。你获得的是引用权限，而不是读取权限，轮换仍然归他们管。出现在 tfvars、Helm values 文件或你的密码管理器里的密钥，都是等着被写进审计报告的问题项。

你如何组织 Terraform，让客户团队能够接管它？

使用在所有客户之间完全一致的可复用版本化模块，外加一个按环境划分的目录，其中存放包含所有客户特定内容的 tfvars 文件。把他们的 VPC、集群、身份提供商和 KMS 密钥作为输入而不是由你管理，这样一次 destroy 就不会删除早于你介入的基础设施。再添加一份 PREREQS.md，逐项列出他们的团队必须创建的内容（包括 IAM 策略 JSON），以及一份覆盖 apply、升级、回滚和 destroy 的 runbook。

你如何验证一次基础设施交接是真实完成的？

四项检查：他们的工程师使用自己的凭证和流水线，在你注视下应用一次真实变更；一个非生产环境仅凭仓库（没有任何本地文件或未记录的步骤）被销毁并重建；runbook 覆盖 apply、升级、回滚和 destroy，并附有预期输出和具名的故障分支；以及所有权被白纸黑字写下来——哪个团队持有状态、谁审批变更、apply 失败时该找谁。
