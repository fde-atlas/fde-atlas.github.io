FDE 作品集仓库：Agent、评测、README 和视频

原标题：FDE Portfolio Repo: Agent, Evals, README and Video

FDE Times · 2026-10-09 · 约 8 分钟读完

摘要

这篇文章来自 FDE Academy 的指南，讲解如何搭建一个有说服力的 FDE 作品集仓库。核心观点是：单个基于真实脏数据的深度项目胜过多个精美演示；仓库应展示 Agent 在哪里失败、失败频率及应对方式。文章以发票匹配 Agent 为例，给出五个步骤：选定企业级 MVP 场景、保持核心循环简洁可读、先记录日志再写评测、从真实失败出发构建评测集、撰写案例式 README 和面向管理者的三分钟视频。文中引用 Anthropic、OpenAI 和 Hamel Husain 的评测方法，强调用 pass^k（连续 k 次全部成功的概率）报告结果：单次正确率 80% 的 Agent 连续三次正确的概率仅约 51.2%。

要点

  • 一个带案例研究的真实项目胜过八个精美演示。
  • Agent 单次正确率 80%，连续三次正确仅约 51.2%。
  • 评测用例应从真实失败中提炼，先用廉价断言。
  • README 顶部应报告 pass^k 并注明用例数与 k 值。
  • 保留的失败清单体现坦诚，是简历上的亮点。

一个 80% 时候正确的 Agent，连续三次正确的概率只有 51%，所以基于真实失败构建的评测胜过精美的演示。

简要说明

  • 一个带案例研究的深度项目胜过许多精美的演示；选择一个数据脏乱的真实企业场景。
  • 保持 Agent 循环简单易读，在工具描述上投入精力，并从一开始就记录每次运行。
  • 基于真实失败构建评测，先用廉价的断言，报告 pass^k，并阅读对话记录来检查评分器。

假设你的 Agent 在 80% 的运行中给出正确答案。这听起来不错，直到你算出它连续三次正确的概率：0.8 × 0.8 × 0.8 = 51.2%。

这就是为什么 FDE 作品集仓库不应止步于一个运行良好的演示。演示只是单次尝试。一个值得发送的仓库必须展示 Agent 在哪里失败、失败频率有多高，以及你如何处理每一次失败。这里的度量方法借鉴了 Anthropic、OpenAI 和 Hamel Husain 关于为 AI 系统构建评测的建议。

培训机构 FDE Academy 博客上的一篇指南直言不讳：一个已部署项目加上一份书面案例研究，比八个精美的演示更有分量。

这是建议，不是定律，但其中的道理很容易理解：一个在真实数据上运行的系统，比八个在干净数据上运行的原型更能展示技能。

下面是构建这样一个仓库的五个步骤。本文中的代码是一个精简的草图：调用模型的函数留空，以便你接入自己使用的任何 SDK。

步骤 1：什么样的问题才算足够“企业级”？

同一篇 FDE Academy 指南建议选择一个真实的企业场景，只构建 MVP 而不是追求完整愿景，并使用真实或接近真实的脏数据。最后一个条件正是 FDE 作品集与课程作业的区别所在。

想象一家通过电子邮件接收供应商发票的分销公司。有些是倾斜打印的扫描 PDF；有些把货币写成“VND”，有些写成“đ”；有些税号缺了几位数字。MVP 只做一件事：Agent 读取发票，与采购订单进行比对，然后返回“匹配”、“不匹配”（附原因）或“需要人工审核”。

invoice-agent/
  agent/loop.py        # core loop
  agent/tools.py       # tools + descriptions
  data/raw/            # messy invoices
  logs/                # one JSONL file per run
  evals/cases.jsonl    # case set
  evals/test_basic.py  # pytest-style assertions
  README.md

（注释依次为：核心循环；工具及描述；脏发票；每次运行一个 JSONL 文件；案例集；pytest 风格的断言。）

检查：你能用一句话说明 MVP 的范围。如果这句话中“和”出现超过两次，就删减。

步骤 2：为什么核心循环必须能在五分钟内读懂？

在《Building effective agents》中，Anthropic 建议寻找尽可能简单的解决方案，只有在真正需要时才增加复杂性。它还警告说，框架往往会增加一层层抽象，掩盖底层的提示词和响应。对于作品集来说，这是一个严重的缺陷：审阅者打开仓库却找不到提示词，就无法判断你的思考方式。

# agent/loop.py — condensed sketch
def run(invoice_text, po, call_model, tools, log):
    messages = [system_prompt(), user_msg(invoice_text, po)]
    for step in range(8):                  # cap the number of steps
        reply = call_model(messages, tools)
        log.write(step, messages, reply)   # log everything
        if reply.tool_call is None:
            return parse_verdict(reply)
        result = tools[reply.tool_call.name](**reply.tool_call.args)
        messages += [reply, tool_result(result)]
    return {"verdict": "needs_review", "reason": "ran out of steps"}

（注释中标记了步数上限并记录所有内容；fallback 原因表示“步数用尽”。）

值得投入精力的部分是工具。Anthropic 将其称为 Agent 与计算机的接口，并建议精心设计：彻底地文档化工具并进行测试。应用到这个仓库，每个工具的 docstring 都应明确说明输入格式、何时返回空值，并包含一个示例。

def lookup_po(po_number: str) -> dict:
    """Look up a purchase order by PO number.
    po_number: 'PO-' followed by 6 digits, e.g. 'PO-004512'.
    Returns {} if not found; do NOT guess a near-match number."""

（docstring 写道：按 PO 号查询采购订单；格式为“PO-”加六位数字，例如“PO-004512”；如果未找到则返回 {}，并且不要猜测近似匹配。）

检查：把仓库交给

loop.py

一个从未见过该仓库的人。阅读五分钟后，他们能解释这个 Agent 做了什么。

第 3 步：在编写评测之前先记录日志

OpenAI 的《Evaluation best practices》建议在开发过程中记录所有内容，以便日后从日志中挖掘评测用例。在《Your AI Product Needs Evals》中，Hamel Husain 更进一步，呼吁扫除查看数据的一切障碍。如果查看一次运行意味着打开三个文件并滚动到手酸，你很快就会停止查看。

最简单的方法是每次运行记录一行 JSONL，包含输入、每次工具调用和最终判定。然后写一个小脚本，以可读的形式将每次运行打印到终端。

将 Agent 运行 20-30 次，

data/raw/

并阅读每一次运行。你很可能会发现未曾预料到的失败——例如，Agent 是把“1.200.000”（越南记法，用点作千位分隔符）读作一百二十万，还是读作 1.2。

检查：你有一份自己记录的真实失败清单，每一条都附有日志文件的路径。

第 4 步：评测从失败出发，而非从理论出发

Anthropic 对评测的定义很简洁：给 AI 系统一个输入，然后对其输出应用评分逻辑，以衡量它是否成功。在它看来，从真实失败中提取的 20-50 个简单任务已经是一个很好的起点。第 3 步的失败清单就是评测套件的原始素材。

{"id": "c07", "invoice": "data/raw/inv_07.pdf", "po": "PO-004512", "expect": "mismatch", "must_mention": "quantity"}

Husain 建议第一层应该是快速、廉价的断言，也就是你已经在 pytest 中编写的那类断言。代码能检查的就让代码检查；只有代码无法检查的才让模型来评分。

# evals/test_basic.py — sketch
@pytest.mark.parametrize("case", load_cases("evals/cases.jsonl"))
def test_verdict(case):
    out = run_case(case)
    assert out["verdict"] == case["expect"]
    assert case["must_mention"] in out["reason"]
pytest evals/ -q

根据 Anthropic 的说法，Agent 评测通常结合三种评分器：基于代码的、基于模型的和人工的。对于作品集仓库来说，代码层必须扎实。再添加一个基于模型的评分器来判断 Agent 给出的理由是否合理，并在 README 中明确说明哪些部分是你人工评分的。

OpenAI 将这种方法称为评测驱动开发：尽早评测、频繁评测，并为每个阶段编写测试。

应该放在 README 顶部的数字是 pass^k。Anthropic 区分了 pass@k 和 pass^k：pass^k 是全部 k 次尝试都成功的概率。本文开头处的计算正是一个每次运行正确率为 80% 的 Agent 的 pass^3（假设各次运行相互独立）：51.2%。

想象一位每天使用该 Agent 三次的会计师。某一天三次使用全部正确的概率只有刚过一半，所以大约每隔一天这个人就会遇到一次错误。

当案例集还很小时，解读这个数字要小心。在 20 个案例的情况下，单个案例的结果翻转就会使 pass^k 变动 5 个百分点，而且 k 越小，单次运行的运气就越容易美化数据。

在实践中，每个案例至少运行三次，再把整个测试套件重新运行一遍以观察数字是否大幅波动，并且始终在结果旁边报告案例数量和 k 的取值。

评测的最后一步是最常被跳过的一步。Anthropic 强调，如果不阅读大量尝试的记录和评分，你就无法知道评分器是否在正确地打分。随机挑选十个被评为“通过”的运行并重新阅读它们。过于宽松的评分器比弱小的 Agent 更危险。

检查：

pytest

运行全部案例集，但并不需要全部通过。因为案例来自真实的失败，有些保持红色是正常的，那些红色案例就是你的待办清单。README 应说明总案例中有多少通过，并附上按失败类别划分的 pass^3 表格。

第 5 步：为不会运行代码的人准备的 README 和视频

GitHub Docs 列出了 README 应回答的问题，首先是项目是做什么的。对于 FDE 仓库来说，README 应该读起来像一篇简短的案例研究。

它应涵盖假设客户的问题、MVP 的范围以及你刻意排除的内容、带 pass^k 的评测结果、仍然存在的三个失败，以及如果再给你两周时间你会如何解决它们。

“剩余失败”这一部分值得用心打磨。它向读者表明你能够度量自己的系统，并且对其局限性坦诚相告。

3 分钟的视频应该为管理者而非工程师制作。一种划分方式是：30 秒陈述问题，90 秒在来自

data/raw/

的一张真实脏乱发票上运行 Agent，45 秒打开评测结果并读出 pass^k 数字，最后 15 秒讲一个你尚未修复的失败。不要拍摄自己敲代码的画面。

常见错误

最常见的错误是在还不清楚自己需要什么之前就选择了一个重量级框架，导致提示词最终被埋在五层类之下。第二个错误是使用干净的自生成数据，这会让评测全部变绿，却证明不了任何东西。第三个错误是只报告最好的一次运行结果，而不是 pass^k。

这项技能如何延续到客户工作中？

这五个步骤不仅适用于作品集；它们是你在客户部署中需要的习惯，而你的仓库就是你首先练习这些习惯的地方。

在你的简历上，避免使用笼统的“构建了 AI Agent”。改用带数字的一句话，例如“基于真实失败案例构建了 40 个评测用例，将 pass^3 从 X 提升到 Y”，其中 X 和 Y 来自你自己的仓库。如果职位描述中提到“评估”或“可靠性”，请在申请时附上这个仓库的链接。

让仓库提前回答每个客户最终都会问的问题：AI Agent 在哪里失败，失败频率是多少？
