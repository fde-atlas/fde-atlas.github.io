每一次部署都是一家由两位创始人共同创办的初创公司

原标题：Every deployment is a startup with two founders

Anjor Kanekar · 2026-10-13 · 约 3 分钟读完

摘要

作者以 Palantir 前员工视角提出：每个部署应视为一家由两位联合创始人组成的小公司，部署策略师像 CEO，FDE 像 CTO。两者职责边界模糊、共同对业务结果负责，而非简单的客户经理加工程师分工。文中举例策略师写 PySpark、工程师买硬盘寄给客户等高度自主的行为，并批评多对多人员配置导致责任推诿，建议按用例分组并配固定搭档。

要点

  • Palantir 中策略师称 Echo，FDE 称 Delta，策略师入职技术门槛较低但需数据分析能力。
  • 作者主张部署像双人创业公司：策略师是 CEO，FDE 是 CTO，职责互相渗透。
  • 实际工作中角色是分布而非固定描述，作者本人几乎不做客户-facing 工作。
  • 作者曾未经审批用公司卡买硬盘寄给客户，体现联合创始人式的自主权。
  • 多对多配置导致甩锅，建议按用例分组、每组配专属搭档。

全文

当人们听说 Palantir 如何为部署配置人员时，通常会想象一个项目经理和一个工程师的组合：部署策略师负责管理客户，前沿部署工程师负责构建产品。对，也不全对。

Palantir 确实为这两个角色分别招聘。Palantir 给一切都起了有趣的名字，所以策略师被称为 Echo，FDE 被称为 Delta。策略师在招聘时的技术门槛较低。他们不需要是工程师，但必须具备分析能力。他们要能够用数据来回答一个开放式问题。他们中的许多人还拥有领域专业知识，或者擅长管理客户关系。

但我一直回归的心智模型是不同的。把每一次部署想象成一家自成一体的初创公司，拥有两位创始人。策略师是 CEO，FDE 是 CTO。如果你和联合创始人一起经营一家初创公司，头衔其实并不重要。你的头衔可能是 CEO，但有时你也要写代码。你的头衔可能是 CTO，但你也要参加销售电话会议并处理运营事务。头衔只是划分了大致的责任范围，并没有在两者之间划出一条明确的界线。

在我的一个部署项目中，我们一共有四个人。我是技术负责人，还有两名策略师和另一名工程师。其中一位策略师是我的好朋友，拥有机械工程博士学位。她编写了大量用于集成客户数据的 PySpark 代码。她也是部署项目面对客户的门面。另一位策略师则完全不懂技术，连 Python 都几乎不会写。我们的流水线中有一部分出于性能原因必须用 Java 编写。当他需要修改那部分代码而我没有空帮忙时，他就会自己直接开一个 pull request。他的态度是：行吧，我就按我的方式改，把一切搞砸，然后你就不得不来帮我了。这招很有效。最后我总会说：“好吧，行，我来修。”

有趣的是，我自己并没有做太多面向客户的工作。与我共事的策略师在这方面做得远比我多，我主要和客户方的技术对接人沟通。我认识的其他 FDE 则做了多得多的这类工作。这两个角色实际上都是一种分布，职位描述大致只是其中的中位数。

创始人式的定位也带来了很大的自主权，实际运作也正是如此。我做过一些疯狂的事情。有一个客户的本地部署磁盘空间快用完了，而他们的采购流程需要九个月。于是我用公司信用卡买了硬盘，寄给客户，账单的事以后再说。我没有向任何人请示。这就是一个 CTO 会做的事。

人们最容易忽略的一点是：这一对搭档是一个整体。他们共同对业务结果负责，所以如果其中一个人掉了链子，就等于两个人都掉了链子。他们的激励是彼此一致的。正因如此，他们才能应对那些不一致的激励，比如产品团队想要一回事，而领导层想要另一回事。我在 If LEGO had forward deployed engineers 中写过，为什么其中一些不一致是刻意为之的。

我最近目睹了这种情况出问题。我 advise 的一家公司将其部署负责人和工程师按多对多的方式配对，以保持人员安排的灵活性。当我试图把它画出来时，结果发现一位负责人连着三名工程师，而其中一名工程师又连着其他几位负责人。我根本理不清。他们的一位领导告诉我，他开始看到这样的 Slack 消息：“我和他讨论过了，他说他会把这件事搞定。”工作被甩手扔给了对方。我的建议是按用例或用户类型对客户分组，并为每组配备一对专职搭档。一个人同时参与几对搭档是可以的，但多对多不行。人不是可以随意互换的。

并非每个部署都需要这样运作。如果没有太多产品探索，而你真正需要的只是有人来填补执行上的空缺，那么另一种形态可能更合理。所以第一个问题是：你把人派到一线想要达成什么。第二个问题是：你是否拥有合适形态的人才。

如果是探索，那就招两位创始人。
