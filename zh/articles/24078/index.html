DevOps 文化与基础

1. 什么是 DevOps，它为什么重要？

答案： DevOps 是一种工作方式：构建软件的人和运行软件的人共同承担交付责任，并以自动化和快速反馈作为支撑。其目标是缩短从代码变更到生产环境产生价值的路径，同时保证这条路径的安全。它之所以重要，是因为大型、低频的发布既缓慢又难以调试；DevOps 用小批量、自动化的构建-测试-部署、共享监控和无指责的学习方式取代了这种模式。

面试提示： 避免回答“DevOps 就是 CI/CD 加 Docker 加 Kubernetes”。先讲文化和流动，再提到支撑它们的实践和工具。

2. DevOps 与传统 IT 运维和开发模式有何不同？

答案： 在传统模式中，开发团队编写代码后“甩手交给”独立的运维团队去部署和运行，通常要通过变更工单和固定的发布窗口。两者的激励相互冲突：一方要功能，一方要稳定。DevOps 将二者对齐。团队对服务端到端负责（其强形式是“谁构建，谁运行”），环境通过代码而非手工创建，发布小而频繁，稳定性来自自动化测试、渐进式发布和快速回滚，而不是靠少发布。

实际案例： 设想海得拉巴一家银行的 GCC 团队，从依赖冗长手工操作手册的月末周末发布，转变为通过流水线进行每日部署。

3. 在 DevOps 中，CALMS 是什么意思？

答案： CALMS 是评估 DevOps 落地的常用框架：文化（共同担责、无指责的学习）、自动化（构建、测试、基础设施、部署）、精益（小批量、限制在制品、消除浪费和等待）、度量（交付和可靠性指标，而非虚荣指标）以及共享（跨团队共享知识、工具和复盘）。自动化只是五项之一。

4. 什么是 DORA 指标？每项指标衡量什么？

答案： DORA（DevOps Research and Assessment，现隶属于 Google Cloud 的研究项目）最初提出“四大关键指标”，目前以两组共五项指标来描述软件交付绩效。

组别指标衡量内容
吞吐量变更前置时间从变更提交到版本控制到其在生产环境运行所需的时间
吞吐量部署频率部署到生产环境的频率，或两次部署之间的间隔时间
吞吐量失败部署恢复时间从一次失败且需要立即干预的部署中恢复所需的时间（早期版本称之为服务恢复时间，常缩写为 MTTR）
稳定性变更失败率需要立即干预（如回滚或热修复）的部署所占比例
稳定性部署返工率因生产事故而进行的计划外部署所占比例

前四项是最初的四大关键指标；返工率是较新增加的。DORA 的核心发现：速度与稳定性并非此消彼长的权衡关系。

5. 在真实组织中，你会如何度量 DORA 指标而不被“刷指标”？

答案： 从系统中采集数据：用提交和部署事件计算前置时间和频率，用与事故、回滚或热修复相关联的部署计算失败率和恢复时间。然后制定让刷指标毫无意义的规则：按服务和团队度量以推动改进，绝不用于给个人排名；事先就定义达成一致（配置变更算不算一次部署？）；看趋势而非单一数值；并将吞吐量与稳定性指标放在一起解读。

生产环境注意事项： 最难的一环是部署与事故的关联。在复盘时为每起事故标注引发它的部署或变更 ID，否则你的变更失败率将是虚构的。

6. 持续集成、持续交付和持续部署有什么区别？

回答： 持续集成是指每个开发人员频繁地将小改动合并到主分支（至少每天一次），每次合并都会触发自动构建和测试运行，使集成问题在几分钟内暴露出来。持续交付是指通过流水线的每个变更都处于可发布状态，可以随时通过点击按钮或审批部署到生产环境；是否发布是一个业务决策。持续部署更进一步：每个通过所有自动检查的变更都会自动进入生产环境，无需人工把关。受监管的组织通常止步于带审批环节的持续交付。

8. 你用过哪种 Git 分支策略，为什么：基于主干开发还是 GitFlow？

回答： 基于主干开发只保留一个主分支；开发人员在短生命周期分支上工作（几小时到一两天）或直接提交，未完成的工作通过功能开关隐藏。它适合持续集成，因为几乎没有需要合并的分歧。GitFlow 使用长期存在的 develop 和 release 分支，外加 feature 和 hotfix 分支；它适合维护多个发布版本的产品，但长期存在的分支会延迟集成。对于持续部署的 Web 服务，我会选择基于主干开发，配合每个 PR 的代码评审和 CI。

9. git merge 和 git rebase 有什么区别？分别什么时候使用？

回答：

git merge

通过一个合并提交将两条历史连接起来，并完整保留实际发生的历史。

git rebase

会将你的提交在另一个分支之上重放，并重写它们的哈希值以产生线性历史。在打开或更新 PR 之前，请在你自己的本地或功能分支上使用 rebase，使其与 main 保持同步。切勿 rebase 其他人已经从共享分支拉取的提交，因为重写共享历史会迫使所有人进行协调。更深入的 Git 问题（reflog、cherry-pick、bisect、使用 Git LFS 处理大型二进制文件）在

Git interview questions

指南中。

10. “左移”是什么意思，它的局限是什么？

答案： 左移是指将测试、安全和质量检查提前到交付流程中更早的阶段，更接近代码编写之时，因为在 IDE 或 PR 中发现的缺陷比在生产环境中发现的缺陷修复成本低得多。示例：每次提交都运行 lint 和单元测试，在 pre-commit 钩子中进行密钥扫描，在 PR 中进行依赖扫描，以及在

terraform apply

之前进行 IaC 策略检查。其局限在于，有些问题只有在真实流量和数据下的生产环境中才会出现，因此左移必须与“右移”相结合：金丝雀分析、可观测性、混沌测试和快速回滚。

11. 自动化在 DevOps 中的角色是什么，哪些事情不应该自动化？

答案： 自动化让可重复的工作变得快速、一致且可审计：构建、测试、环境创建、部署、证书续期、备份和常规修复。不应该自动化（或暂时不应自动化）的事情：没人理解的过程（自动化混乱只会产生更快的混乱）、人工检查比构建安全自动化更便宜的低频高风险操作（例如删除生产数据库），以及需要判断力的事项，例如事故严重程度或客户沟通。

CI/CD 流水线设计与构建产物

13. CI/CD 流水线有哪些关键阶段？

答案： 针对容器化服务，一个可靠的流水线通常包含以下阶段，快速检查放在最前面，以便尽早暴露失败：

commit / PR
  |
  v
lint + unit tests + secret scan      (minutes)
  |
  v
build artifact once, tag with SHA
  |
  v
SAST, dependency + image scan, SBOM
  |
  v
push to registry, sign artifact
  |
  v
deploy to staging -> integration tests
  |
  v
approval (if required)
  |
  v
progressive prod rollout -> verify
  |
  v
auto rollback on failed health checks

Pull request 运行早期阶段；合并到 main 则运行完整链条。

14. “一次构建，多次部署”是什么意思，你如何管理构建产物？

回答： 你只构建一次工件（容器镜像、JAR、软件包），给它一个不可变的标识符，然后将同一个工件依次推广到测试、预发布和生产环境，每个环境只更改配置。为每个环境重新构建意味着生产环境运行的是从未测试过的东西。实践中：用提交 SHA 为镜像打标签（可选再加上语义化版本号），推送到 ECR、ACR、Artifactory 或 Nexus 等镜像仓库，通过 digest 部署以实现完全不可变，并在仓库中将标签设为不可变，防止任何人覆盖

v1.4.2

.

面试提示： 提到

latest

不是可部署的标签及其原因，是快速展示专业度的信号。

15. 请解释 Jenkins 架构，以及你会如何为多个团队进行扩展。

回答： Jenkins 有一个控制器（以前称为主节点/master），负责提供 UI、将配置和任务历史存储在

JENKINS_HOME

中、调度构建；还有

agents

（以前称为从节点/slaves），在执行器上运行构建。扩展方法：绝不在控制器上运行构建；使用临时代理，例如通过 Kubernetes 插件为每次构建创建的 Pod 或云端虚拟机，使容量随需求变化且每次构建都在干净环境中启动；用 JCasC 管理配置，用 Jenkinsfile 管理任务；并固定和测试插件——这是 Jenkins 最主要的运维风险。开源版控制器是单点故障，因此高可用通常意味着从备份和配置即代码进行快速且经过测试的恢复。

面试提示： 对于以 Jenkins 为主的职位，Jenkins CI/CD 课程会动手实践这些模式。

16. 声明式和脚本式 Jenkins 流水线有什么区别？共享库的用途是什么？

回答： 两者都存放在提交到仓库的

Jenkinsfile

中。

Declarative

流水线使用结构化的

pipeline { agent ... stages { ... } post { ... } }

语法，更易读、易验证、易标准化。

Scripted

流水线是完整的 Groovy，为复杂逻辑提供了灵活性，但牺牲了可读性，也更容易出错。优先使用声明式，并将复杂逻辑放入

shared libraries

中：这是存放在独立仓库中的版本化 Groovy 代码，团队通过

@Library

导入，暴露出诸如

buildAndPushImage()

之类的步骤。它们消除了 Jenkinsfile 之间的复制粘贴。

17. 你会如何在 GitHub Actions、GitLab CI、Jenkins 和 Azure Pipelines 之间做选择？

回答： 从代码所在的位置以及组织已有的运维体系出发。如果代码在 GitHub 上，GitHub Actions 是阻力最小的选择，拥有庞大的 action 市场以及通过 OIDC 联合身份连接云端的简便方式。GitLab CI 是 GitLab 上的自然选择。Azure Pipelines 适合使用 Azure DevOps 看板和仓库的以微软为中心的环境。当你需要最大灵活性、必须完全自托管，或已在共享库上投入大量资源时，Jenkins 是合理选择；代价是你需要自己运维和打补丁。此外还应比较运行器、身份集成、模板、审计以及每构建分钟的成本。

18. 你使用哪些策略来优化构建时间？

回答： 先测量：找出哪个阶段耗时最长。然后应用常规手段。基于锁文件缓存依赖（Maven、npm、pip 缓存）。调整 Dockerfile 指令顺序，使依赖层被缓存，并使用 BuildKit 缓存挂载或远程层缓存。并行运行独立阶段和测试分片。在 monorepo 中使用路径过滤或带依赖图的构建工具，只运行受变更影响的部分。把缓慢的端到端测试套件移到合并后或按计划运行，保持 PR 门禁快速。

19. 你如何在流水线中设计质量门禁和测试策略？

回答： 遵循测试金字塔：大量快速的单元测试，较少的集成或契约测试，以及少量针对关键流程的端到端测试。把快速、确定性的测试放入 PR 门禁并设为阻塞项。加入静态分析、针对变更代码的覆盖率（而非绝对数字），以及带严重性阈值的安全扫描。每个门禁都必须可信：随机失败的门禁比没有门禁更糟，因为人们会学会反复重跑直到变绿。

20. 你如何在 CI/CD 流水线中处理机密和敏感数据？

回答： 原则是：代码、流水线文件或日志中不存放长期机密，流水线只获得所需的最小权限和最短时间。具体做法：使用 OIDC 联合认证，让 CI 任务用其签名的身份令牌换取短期云凭证（例如 GitHub Actions 担任 AWS IAM 角色，信任策略限定到特定仓库和分支或环境），而不是存储访问密钥。将应用机密存储在机密管理器中（AWS Secrets Manager、Azure Key Vault、HashiCorp Vault），在部署或运行时获取。将不可避免的 CI 机密限定在受保护分支，绝不暴露给 fork PR。在 pre-commit 钩子和 CI 中加入机密扫描，并准备好轮换操作手册。

21. 你如何在 CI/CD 流水线中处理数据库模式迁移？

回答： 使用 Flyway、Liquibase、Alembic 或框架自带的迁移系统等工具，在仓库中对迁移进行版本管理，并将其作为受控的流水线步骤或部署前任务运行，而不是手动执行。关键模式是扩展与收缩：先部署向后兼容的变更（添加可空列或新表），再部署同时写入新旧结构的应用代码，回填数据，切换读取，最后在后续版本中才删除旧列。这样新旧应用版本可以同时正常工作，这对滚动、蓝绿和金丝雀部署至关重要，也使应用回滚安全。

22. monorepo 与多仓库的流水线有何不同？

答： 在 monorepo 中，一次更改可能涉及多个服务，因此流水线必须检测哪些内容发生了变化，并借助路径过滤器或具备依赖感知能力的构建系统，只构建和测试受影响的组件；否则每次提交都会触发全部构建，CI 会变得缓慢且成本高昂。在 polyrepo 模式下，每个服务都有自己简单的流水线，但你需要可复用的模板来避免配置漂移，还需要带版本管理的共享库和契约测试来发现服务之间的集成问题。

23. 编写可维护的流水线即代码有哪些好的实践？

答： 将流水线定义放在与代码相同的仓库中，并像审查代码一样对其进行审查。通过带版本的模板、可复用的工作流或共享库来实现复用，而不是复制粘贴，并固定模板和第三方操作的版本（将 action 固定到 commit SHA，而不是会变动的标签）。将业务逻辑放在可以在本地运行的脚本中（

make test

），这样流水线只是一个轻量的编排器，开发者可以在自己的机器上复现故障。对流水线的更改采用与应用代码相同的分支保护策略，因为拥有生产环境凭证的流水线本身就是一个生产系统。

24. 你如何管理环境和晋升流程，包括预览环境？

答： 定义少量长期存在的环境（例如 dev、staging、production），每个环境都由相同的 IaC 配合不同的变量创建，并将同一个制品依次晋升到这些环境。配置差异应放在环境特定的值文件或配置服务中，绝不要放在镜像里。临时预览环境会随每个 pull request 启动，通常作为一个 Kubernetes 命名空间，让评审者和测试人员可以在隔离环境中试用更改；当 PR 关闭时必须自动销毁这些环境，使用合成数据或脱敏数据，并设置成本上限。staging 环境在网络、身份认证和数据量方面应尽量与生产环境保持一致。

部署策略与回滚

25. 你会如何实现蓝绿部署策略？

答： 运行两个完全相同的生产环境。蓝色环境承载线上流量；你将新版本部署到绿色环境，直接对绿色环境运行冒烟测试，然后通过更改负载均衡器的目标组、Kubernetes Service 的选择器或 DNS 权重来切换流量。如果出现问题，可以切回仍在运行旧版本的蓝色环境，因此回滚只需几秒钟。难点不在于切换本身，而在于状态：数据库变更必须向后兼容（参见 Q21），会话应保存在实例之外，进行中的连接必须能够排空。

26. 什么是金丝雀部署？你如何自动化“继续或终止”的决策？

答： 金丝雀发布将一小部分真实流量发送到新版本，其余流量仍留在稳定版本上，如果金丝雀运行健康，则逐步增加流量比例。自动化分析会比较金丝雀版本与基线版本的错误率、延迟、饱和度和业务指标。Kubernetes 上的 Argo Rollouts 或 Flagger 等工具，或云负载均衡器和服务网格的流量切换功能，会执行这些步骤，并在分析失败时自动中止。相关技术包括暗发布（代码已部署但通过开关隐藏）和影子流量（将真实请求复制到新版本并丢弃其响应），它们可以在不影响客户的情况下测试真实负载下的行为，前提是支付或邮件等副作用被抑制。

27. 滚动、重建、蓝绿和金丝雀部署有什么区别？

策略工作方式适用场景注意事项
重建停止所有旧实例，启动新实例停机可接受或版本无法共存切换期间的服务中断
滚动分批替换实例Kubernetes 上无状态服务的默认选择两个版本同时在线；回滚缓慢
蓝绿完整的并行环境，切换流量最看重快速回滚时双倍容量，共享数据库状态
金丝雀先发送小部分流量，再逐步增加高流量服务、风险敏感的变更需要良好的指标和流量切分

答： 根据所需的回滚速度、额外容量的成本、两个版本能否同时运行以及可观测性的质量来选择。Kubernetes 原生支持滚动和重建；蓝绿和金丝雀需要额外的工具。

28. 什么是功能开关（feature flags），它们如何改变部署和发布？

答： 功能开关是一个运行时开关，无需重新部署即可开启或关闭代码路径。功能开关将部署（代码已进入生产环境）与发布（用户可以看到它）分离开来，这使得基于主干开发不完整的功能、按用户群逐步发布、紧急关闭开关和实验成为可能。风险包括：开关债务（遗留的旧开关在代码中造成未经测试的组合）、绕过变更控制的开关配置更改，以及开关服务本身导致的故障。良好实践是为每个发布开关指定负责人和过期时间，在完全发布后将其移除，像审计部署一样审计开关变更，并在开关服务不可用时设置安全的默认值。OpenFeature 是一个供应商中立的 CNCF 开关 SDK 规范。

29. 回滚还是向前修复：如何决策，什么使回滚安全？

答： 当由部署引发事故时，如果回滚快速且安全，回滚是默认选择，因为恢复服务比找到 bug 更重要。当修复很小且已被理解，或者不可逆的数据变更导致无法回滚时，则选择前滚。回滚只有在事先做好准备时才是安全的：上一个制品仍然可用且不可变，数据库变更向后兼容，配置与代码一起版本化，功能开关可以关闭新路径，并且回滚流程是自动化且经过演练的，而不是一个没人执行过的 wiki 页面。

30. 真正的零停机部署需要什么？

答： 需要多方面配合。就绪探针或负载均衡器健康检查，确保新实例只有在就绪后才接收流量。优雅停机：收到 SIGTERM 时，应用停止接受新请求，完成进行中的请求并关闭连接，且终止宽限期足够长；在 Kubernetes 上，一个短暂的

preStop

延迟有助于在进程退出前更新端点。负载均衡器上的连接排空。发布期间有足够的备用容量（

maxUnavailable: 0

带有激增）。向后兼容的 API 和模式，使新旧版本可以共存。

基础设施即代码与配置管理

31. 什么是基础设施即代码，它有哪些好处？

答： 基础设施即代码是指在版本控制的文件中定义服务器、网络、数据库、权限和其他基础设施，由工具来应用这些定义，而不是通过在控制台中点击来创建。好处：环境可复现，每次变更都在拉取请求中审查并留下审计记录，可以检测配置漂移，灾难恢复变成“重新应用代码”，同一个模块可以创建多个一致的环境。IaC 通常是声明式的（描述最终状态：Terraform、CloudFormation、Bicep），而不是命令式的（脚本化步骤），因为声明式工具会处理顺序和幂等性。

32. Terraform 和 CloudFormation 如何比较？

答： CloudFormation 是 AWS 的原生服务：无需管理状态文件，与 AWS 深度集成，失败时支持堆栈级回滚，并且通过 AWS 本身支持新的 AWS 功能。它只能管理 AWS（加上注册表扩展）。Terraform 是多云和多提供商的，使用一种语言（HCL），拥有庞大的模块生态和清晰的

plan

之前

apply

；代价是你需要管理状态及其安全性。自 HashiCorp 于 2023 年更改 Terraform 的许可证以来，开源分支 OpenTofu 作为一个大体兼容的替代方案而存在。关于状态、模块和工作流的完整问题集见

Terraform interview questions

指南中。

33. 你使用哪些策略来管理 Terraform 状态文件？

答案： 永远不要把状态保存在笔记本电脑或 Git 中。使用支持锁定和加密的远程后端：带版本控制和加密的 S3 存储桶（较新的 Terraform 版本支持 S3 原生锁文件；较旧的配置使用 DynamoDB 表进行锁定）、带 blob 租约的 Azure Storage、Google Cloud Storage，或 HCP Terraform 等托管服务。限制访问权限，因为状态可能包含明文形式的机密信息。按环境和按组件（网络、数据、应用）拆分状态，这样即使出错影响范围也较小，且计划执行保持快速。使用

terraform state mv

或

moved

块进行重构，使用

import

块纳管现有资源，并对生产数据库等关键资源使用

lifecycle { prevent_destroy = true }

。

34. 在 Terraform 这样的 IaC 框架中，你会如何处理机密信息？

答案： 将机密值排除在代码和提交到 Git 的变量文件之外。优先使用平台托管的机密（例如保存在 Secrets Manager 或 Key Vault 中的数据库密码），并通过名称引用。当 Terraform 必须读取机密时，使用来自机密管理器或 Vault 提供程序的数据源，将变量和输出标记为

sensitive

，以便在 CLI 输出中被遮蔽，同时要记住敏感值仍可能落入状态文件中，因此状态必须加密并控制访问。较新的 Terraform 版本增加了临时值和只写参数，旨在让部分机密不进入状态文件；请查阅当前文档了解哪些资源支持这些特性。

35. Ansible 和其他配置管理工具如何融入 DevOps 流水线，为什么用它们而不是 shell 脚本？

答案： Terraform 负责基础设施的供给；Ansible、Chef 或 Puppet 等配置管理工具负责配置其上运行的内容：软件包、用户、文件、服务、操作系统加固以及向虚拟机部署应用。Ansible 是无代理的（使用 SSH 或 WinRM），使用 YAML playbook 和角色，其模块是幂等的：运行两次 playbook 会使系统保持相同状态。Shell 脚本也能完成同样的工作，但你需要手动实现幂等性、错误处理、主机清单、并行执行和报告。在流水线中，Ansible 通常在 Terraform 之后运行以配置虚拟机，或在镜像构建期间（例如配合 Packer）用于创建黄金镜像。深入了解 Ansible 面试问题 指南。

36. 你如何检测和处理生产环境中的配置漂移？

答案： 漂移是指真实基础设施不再与代码一致，通常是因为有人在事故处理期间手动更改了配置。通过定期运行来检测

terraform plan

任务（在未变更的代码上出现非空计划即意味着漂移），可借助 AWS Config 或 Azure Policy，以及持续将集群状态与 Git 进行对比的 GitOps 控制器。预防漂移的方法包括：移除生产环境中宽泛的控制台写权限，使用有日志记录和告警的应急（break-glass）角色，并优先采用不可变基础设施（用替换而非修补）。发现漂移后要有意识地做出决策：如果手动变更是正确的，就通过 PR 将其代码化；如果不正确，则重新应用代码以回滚。

容器与编排

37. Docker 容器的主要优势是什么？容器与虚拟机有何区别？

答案： 容器将应用程序及其依赖打包成一个镜像，使其在任何地方都以相同方式运行，从而消除了笔记本、CI 和生产环境之间的环境漂移。容器可以在几秒内启动，在主机上高密度部署，并使不可变的、带版本控制的部署变得自然而然。虚拟机虚拟化硬件并运行自己完整的客户内核和操作系统；容器共享主机内核，通过 Linux 命名空间（进程、网络、挂载等）实现隔离，并用 cgroups 进行资源限制。容器更轻量；虚拟机隔离性更强。Dockerfile 实践、镜像层、BuildKit 和容器安全在 Docker 面试题 指南中有深入讲解。

38. Kubernetes 中 Deployment 与 StatefulSet 有什么区别？持久化存储是如何处理的？

答案： Deployment 管理可互换的、无状态的 Pod：任何 Pod 都可以被另一个随机名称的 Pod 替换，滚动更新可以按任意顺序进行。StatefulSet 为每个 Pod 提供稳定的身份标识（

db-0

,

db-1

）、通过 headless Service 获得的稳定 DNS 名称、有序的创建、扩缩容和更新，以及来自

volumeClaimTemplates

的专属 PersistentVolumeClaim，当 Pod 被重新调度时，该 PVC 仍绑定在该身份上。PVC 请求 StorageClass，StorageClass 通过 CSI 驱动程序供应卷。数据库、Kafka 或 Elasticsearch 类的集群系统应使用 StatefulSet，不过许多团队更倾向于使用托管云数据库，而将 Kubernetes 保留给无状态工作负载。更多集群相关的问题见

Kubernetes interview questions

指南中。

39. 什么是 Helm chart？它是如何使用的？

答案： Helm 是 Kubernetes 的包管理器。chart 是一个带版本控制的打包集合，包含模板化的清单（

templates/

）、默认配置（

values.yaml

）和元数据（

Chart.yaml

）。你可以将 chart 作为 release 安装，并使用特定于环境的值，对其进行升级，或回滚到之前的版本。常见的替代或补充方案包括 Kustomize（无需模板即可对普通 YAML 打补丁）以及从 Git 渲染 Helm chart 的 GitOps 工具。常见陷阱：过于复杂而无人能读懂的模板、将机密信息写入 values 文件，以及各环境之间 chart 版本不一致。

40. 在面试层面，Kubernetes 中 Pod 与 Service 之间的网络是如何工作的？

答： 每个 Pod 都拥有自己的 IP 地址，CNI 插件（例如 AWS VPC CNI、Azure CNI、Calico 或 Cilium）确保 Pod 可以跨节点互相访问而无需 NAT。由于 Pod IP 会变化，Service 提供一个稳定的虚拟 IP 和 DNS 名称（

orders.payments.svc.cluster.local

），并根据标签选择健康的 Pod 进行负载均衡；由 kube-proxy 或 eBPF 数据平面来实现。ClusterIP 是内部使用的，NodePort 和 LoadBalancer 将服务暴露到外部，Ingress 或较新的 Gateway API 则按主机和路径路由 HTTP 流量。NetworkPolicy 限制哪些 Pod 可以与哪些 Pod 通信，这对安全至关重要，因为默认策略是允许所有流量。

41. 什么是 GitOps？它与基于推送的 CD 有何不同？

42. 在 GitOps 环境中如何处理密钥和多环境？

答： 明文的 Kubernetes Secret 绝不能提交到 Git，因为它们只是 base64 编码。常见模式有：External Secrets Operator 从 AWS Secrets Manager、Azure Key Vault 或 Vault 同步密钥到集群，Git 中只存储引用；Sealed Secrets 使用只有集群内控制器才能解密的密钥对密钥进行加密；SOPS 使用 KMS 密钥加密文件中的值。对于多环境，在配置仓库中为每个环境使用一个目录或 Kustomize overlay（或每个环境的 Helm values），通过 PR 将镜像标签更新到下一个环境的文件夹来实现晋级，并使用 Argo CD ApplicationSets 或 Flux Kustomizations 管理多个集群。避免每个环境一个分支的做法。

43. 什么是平台工程？什么是内部开发者平台？

回答： 平台工程是构建和运营一个内部开发者平台（IDP）：这是在基础设施、CI/CD、可观测性和安全之上的一层精心设计的自助服务层，让产品团队无需每个人都成为 Kubernetes、Terraform 和云 IAM 专家就能交付软件。典型内容包括：黄金路径（带有明确约定的模板，可创建一个新服务，并自动配置好代码仓库、流水线、Dockerfile、Helm chart、仪表盘和告警）、服务目录和门户（Backstage 是广泛使用的开源方案），以及以策略而非工单形式内置的防护栏。平台团队将平台视为一个面向内部客户的产品。

44. 你如何衡量一个内部平台是否成功？

回答： 衡量开发者的成果，而不是平台团队交付的功能数量。有用的信号包括：平台上团队的 DORA 指标与之前对比；新服务上线到生产环境所需的时间；配置一个环境所需的时间；黄金路径的采用率（自愿采用才是诚实的检验，强制采用会掩盖糟糕的体验）；平台团队收到的常规任务工单数量（应该下降）；以及开发者满意度调查。如果团队绕过平台、使用自己的脚本，那就是用户研究在告诉你平台缺少什么。

可观测性、值班与事故处理

45. 监控和可观测性有什么区别？OpenTelemetry 扮演什么角色？

回答： 监控关注已知的故障模式；可观测性让你能够提出新的问题，调试你没有预料到的故障。它依赖于相互关联的遥测数据：指标（用于告警和趋势的低成本聚合数据）、日志（详细事件，最好是结构化 JSON）和追踪（一个请求跨服务的路径，包含每一跳的耗时）。OpenTelemetry 是 CNCF 的标准，用于代码插桩并以厂商中立格式收集这些遥测数据；OpenTelemetry Collector 接收、处理并将数据导出到 Prometheus、Grafana Tempo 或 Loki、Jaeger 等后端，或商业工具。Prometheus、PromQL 和 Grafana 的具体内容见 Prometheus 和 Grafana 面试题 指南。

46. 什么是 SLI、SLO 和错误预算？它们如何指导发布决策？

回答： SLI（服务等级指标）是衡量良好事件占总事件比例的指标，反映用户体验，例如在 300 毫秒内成功处理的结账请求比例。SLO（服务等级目标）是该 SLI 在某个时间窗口内的目标，例如 28 天内达到 99.9%。错误预算是允许的不可靠程度，即剩余的 0.1%。只要预算还有剩余，团队就可以自由发布；如果预算消耗过快，他们就会放缓发布节奏，优先处理可靠性工作。应基于消耗速率（预算被消耗的速度）而非原始阈值来告警。SRE 相关的深入内容见 面向 DevOps 工程师的 SRE 面试题。

47. 什么样的告警才是好的告警？如何避免告警疲劳？

回答： 一次好的紧急呼叫应当紧急、可执行，并且关乎用户影响。应基于症状告警（错误率、延迟、SLO 消耗速率，以及延迟、流量、错误和饱和度这四个黄金信号），而非原因（某个 Pod 重启了、CPU 占用偏高），后者应放在仪表盘或低优先级工单中。每个触发紧急呼叫的告警都应附带运行手册和仪表盘链接，并指定负责人。减少疲劳的方法包括：删除或降级无人处理的告警、合并相关告警、设置合理的“for”持续时间以避免抖动，以及按服务归属进行路由。如果一个告警触发后正确的应对是“忽略它”，那这个告警就是一个缺陷。

48. 事故是如何处置的？涉及哪些角色？

回答： 尽早宣布事故，使用事先根据客户影响定义好的严重级别。然后分配角色：一名事故指挥官负责协调和决策，但不参与调试；一名或多名响应人员或运维负责人负责调查和缓解；一名沟通负责人按固定节奏向利益相关方和状态页更新进展；以及一名记录员负责维护时间线。优先进行缓解（回滚、故障转移、关闭功能开关、扩容），而非查找根因。对于涉及 AI 功能的事故，还有一些额外的故障模式，详见 AI 事故响应手册。

49. 什么是无指责复盘？它应包含哪些内容？

回答： 无指责复盘是在重大事故之后进行的书面回顾，重点在于系统和流程为何允许故障发生，而不是谁犯了错。其假设是：在当时的认知下，人们的行为是合理的；如果一名工程师能用一条命令搞垮生产环境，那么问题在于系统本身。内容应包括：摘要与影响（持续时间、受影响的用户）、包含发现、响应和恢复时间的时间线、促成因素（通常是多个，而非单一的“根因”）、做得好的地方，以及带负责人和截止日期的行动项，并按优先级排序，确保少数重要修复真正落地。要跟踪行动项直至完成。

50. 如何让值班可持续？

回答： 轮值规模要足够大，避免人们过于频繁地值班，并设置主值班和副值班、清晰的交接流程以及升级路径。让工作合理化：只对可操作、影响用户的问题进行告警，保持运维手册（runbook）及时更新，并赋予值班工程师无需请示即可回滚的权限。将每班次的告警次数和非工作时间的打扰作为健康指标进行跟踪，并在每个轮值周期中投入部分时间修复最嘈杂告警的根源。对于全球 GCC 团队，如果交接纪律良好，印度与其他地区之间的“日不落”交接可以完全避免夜间告警。

流水线安全与成本意识

51. CI/CD 流水线中应包含哪些安全控制措施？

回答： 按阶段分层部署，并让速度快的安全检查成为阻断项。Pre-commit 和 PR 阶段：密钥扫描、代码规范检查（linting）、SAST（代码静态分析）、针对存在漏洞或许可证不佳的依赖的软件成分分析，以及针对配置错误（如公开的存储桶或开放的安全组）的 IaC 扫描。构建阶段：基础镜像策略、容器镜像扫描、SBOM 生成、制品签名。部署阶段：准入时的策略即代码（Kyverno 或 OPA Gatekeeper 拒绝特权 Pod 或未签名镜像）、环境审批、最小权限的部署身份。运行时阶段：DAST 以及对已部署镜像的重新扫描。设置严重性阈值和带过期机制的例外流程，否则团队要么不断被阻断，要么干脆忽略所有告警。各工具的详细对比见 DevSecOps 面试题 指南。

52. 什么是软件供应链安全？什么是 SBOM、签名和 SLSA？

回答： 供应链安全保护进入你制品的一切内容以及构建它的过程。SBOM（软件物料清单，采用 SPDX 或 CycloneDX 格式）列出了制品中的组件，因此当新漏洞公布时，你可以在几分钟内找到受影响的服务。签名（例如使用 Sigstore 的 cosign）可以证明镜像来自你的流水线且未被篡改；准入策略可以拒绝未签名的镜像。SLSA（Supply-chain Levels for Software Artifacts，软件制品供应链等级）是一个构建完整性逐级提升的框架，核心是生成可验证的来源证明（provenance），记录制品是如何构建的以及来自什么源代码。

53. 如何保护 CI 运行器（runner）和流水线自身的权限？

回答： 将 CI 系统视为拥有强大凭证的生产系统来对待。为每条流水线分配独立的身份，并遵循最小权限原则，按环境限定作用范围，使部署到开发环境的任务无法触及生产环境。优先使用每次任务结束后即销毁的临时运行器，这样即使某次构建被攻破也无法持久驻留。切勿将自托管运行器连接到公开仓库。限制谁可以编辑流水线定义和受保护分支，要求对工作流变更进行审查，将默认令牌权限设为只读，并将第三方 action 或插件固定到经过验证的版本。在 Jenkins 中，应用基于角色的访问控制（例如使用 Role-based Authorization Strategy 插件），限制脚本审批，并对控制器与代理之间的通信进行加密。

54. DevOps 工程师如何为云成本意识做出贡献？

回答： DevOps 工程师掌控着许多产生成本的决策，因此成本是工作的一部分。实际贡献包括：在 IaC 中强制执行标签规范（团队、服务、环境），以便分配支出；根据实际使用情况调整实例和 Kubernetes 资源请求的规格；对非生产环境进行自动扩缩并定时在非工作时段关机；自动删除预览环境和旧快照；设置镜像仓库和日志的保留策略；为 CI 运行器和容错任务使用竞价型或可抢占容量；并使用 Infracost 等工具在 Terraform 拉取请求中展示成本估算。更深入的 FinOps 实践请参阅 FinOps 面试题 指南。

DevOps 中的 AI 与面向 AI 的 DevOps

55. 当应用使用 LLM 时，DevOps 会发生哪些变化（LLMOps）？

回答： 流水线的基本原则不变，但会出现新的产物和新的关卡。提示词、模型标识符、检索配置和工具定义成为需要版本化的产物，它们对行为的破坏能力不亚于代码。检查精确输出的测试不再适用，因此评测套件（针对正确性、依据性和安全性进行评分的黄金数据集）成为部署前的质量关卡，回归问题会阻止发布。可观测性方面新增了令牌用量、每请求成本、每次模型调用的延迟，以及检索和工具调用的追踪，通常通过 OpenTelemetry 实现。模型弃用类似于依赖升级，而自托管模型则带来 GPU 相关的考量。延伸阅读：AI DevOps 与 LLMOps、面向 AI 应用的 CI/CD，以及 MLOps 与 LLMOps 面试题。

56. 什么是 AIOps，它的现实局限是什么？

答： AIOps 将机器学习以及越来越多的 LLM 应用于运维数据：用异常检测替代固定阈值来监控指标，将数千条告警关联为少数几个事件，通过将事件与最近的部署关联来提示可能的原因，以及使用 LLM Agent 来总结日志或运行只读诊断。其局限性也是真实存在的：模型需要干净、标注良好的遥测数据和服务归属映射，否则它们只会关联噪声；在促销活动等合法变更期间，异常检测器会产生误报；LLM 的总结可能自信地出错；而没有审批的自动修复可能把一个事故变成两个。写入操作必须由人来审批。场景式练习见 AI DevOps 和 AIOps 面试指南。

57. 在 DevOps 工作流中应如何使用 AI 编程助手和 AI 代码审查？

答： 它们可用于起草流水线 YAML、Terraform 模块、Dockerfile、测试和脚本，解释不熟悉的代码，以及对拉取请求给出初步审查意见。应将其输出视为不可信的贡献：它需要经过与人工代码相同的 PR 审查、测试、安全扫描和策略检查。注意具体风险：虚构的包或参数、过时的 API、过于宽泛的 IAM 权限以及粘贴到提示词中的密钥。DORA 关于 AI 辅助开发的研究将 AI 描述为放大器：拥有强大测试、小批量交付和良好平台的团队会受益，而基础薄弱的团队会看到更多不稳定。因此，在衡量生产力提升的同时，也要衡量变更失败率和返工率。参见 企业中的 AI 编程助手。

职业路径与新人准备

58. DevOps 工程师、SRE、平台工程师和前沿部署工程师这些角色有何区别？

答： 它们在技能上有重叠，但关注点和服务的对象不同。

角色主要关注点服务对象
DevOps 工程师CI/CD、自动化、IaC、环境、发布流程产品和开发团队
站点可靠性工程师（SRE）通过 SLO、错误预算、事件响应、减少琐事、容量规划保障可靠性通过服务服务最终用户
平台工程师内部开发者平台、黄金路径、自助服务以内部开发者为客户
前沿部署工程师在客户环境中进行工程工作，集成、部署并运行软件（通常是 AI 系统），直到其交付业务成果外部企业客户

DevOps 工程师通常会转向 SRE 或平台角色；喜欢面向客户的 AI 系统工作的人可以关注 FDE 角色。参见 DevOps 与 SRE 和 从 DevOps 工程师到 FDE 的转型指南。

59. 作为没有生产经验的新人，你应该构建并讲述什么样的项目？

回答： 与其做很多教程，不如完整地构建一个你完全理解的项目。一个很好的例子：一个带数据库的小型 Web 服务，用多阶段 Dockerfile 容器化；一个 GitHub Actions 流水线，运行测试、扫描、构建并推送以提交 SHA 为标签的镜像；用 Terraform 创建网络、Kubernetes 集群或虚拟机以及托管数据库；通过 Helm 或 Argo CD 部署；Prometheus 和 Grafana 仪表盘并配置一条有意义的告警；以及一份包含架构图、如何回滚和运行成本的 README。然后故意把它弄坏：杀掉一个 Pod、推送一个失败的测试、撤销一个权限，并记录你是如何诊断每一个问题的。对“出了什么问题？”的真实回答胜过任何证书。

DevOps 场景类问题

60. 昨天还是绿色的 CI 流水线今天失败了，而没有人改动代码。你会怎么做？

回答： “没有人改动代码”通常意味着仓库之外的东西发生了变化：依赖、基础镜像、运行器、凭据或外部服务。

我会检查的内容：

  • 具体错误和出错的步骤：依赖解析、构建、测试、推送还是部署。
  • 未固定的依赖或浮动的基础镜像标签，一夜之间拉取了新版本。
  • 运行器镜像或工具版本变化（托管运行器镜像更新、新的 Node 或 JDK 默认版本）。
  • 过期的凭据、令牌或证书，以及公共镜像拉取的仓库速率限制。
  • 重新运行最后一个绿色的提交：如果它也失败，说明原因是环境问题。

生产环境考量： 然后消除这类问题：用锁文件固定依赖，用摘要（digest）固定基础镜像并通过自动更新的 PR 更新，将公共镜像镜像到私有仓库，并在凭据过期前发出告警。

61. 一个 Kubernetes 部署卡在半路：新 Pod 处于 CrashLoopBackOff 状态，发布没有进展。你会怎么做？

回答： 首先保护用户：因为配置合理的滚动更新会让旧 Pod 继续提供服务，先检查是否有用户影响。如果有，或者修复方法不明显，就运行

kubectl rollout undo

（对于 GitOps 则在 Git 中回滚），然后再排查。

我会检查的内容：

  • 用 kubectl describe pod 查看事件：镜像拉取错误、OOMKilled、探针失败、调度失败。
  • 用 kubectl logs --previous 查看容器退出的原因。
  • 缺失或变更的配置：一个在此环境中不存在的新环境变量、Secret 或 ConfigMap。
  • 就绪或存活探针对启动较慢的应用来说过于激进。
  • 新版本的资源限制过低，或某个依赖（数据库、下游 API）不可达。

生产环境考量： 设置

progressDeadlineSeconds

并让流水线在发布未完成时自动失败并回滚，这样卡住的发布就永远不会依赖于有人注意到它。

62. 构建耗时 40 分钟，开发者们都在抱怨。你会如何缩短它？

回答： 在做任何改动之前先进行测量，然后优先针对耗时最长的阶段。

我会检查的内容：

  • 查看近期各次运行中每个阶段的耗时，找出最慢的阶段以及等待执行器的排队时间。
  • 依赖下载时间：是否有基于锁文件作为键的缓存，缓存是否命中？
  • Docker 层缓存：是否因为源代码被过早复制，导致依赖层每次都被重新构建？
  • 测试：能否并行分片执行？PR 门禁中是否包含可以合并后再运行的缓慢端到端测试？
  • 单体仓库：是否每次变更都构建所有内容，而不是只构建受影响的组件？
  • 执行器规格以及重复的工作。

生产环境考量： 为 PR 反馈循环设定目标（例如十分钟以内），在仪表板上跟踪它，并将回归视为 bug。

63. 一位开发者不小心将 AWS 访问密钥推送到了公开的 GitHub 仓库。你会怎么做？

回答： 从密钥被推送的那一刻起就假定它已泄露，因为自动化扫描器很快就能发现公开的密钥。先撤销；清理历史记录并不能让密钥变得安全。

我会检查的内容：

  • 立即停用并删除该密钥，如果仍需要，则通过正规的密钥存储创建替代密钥。
  • 通过 CloudTrail 审查自推送以来使用该密钥执行的每一个操作：新建的 IAM 用户或密钥、启动的实例、数据访问。
  • 找出所有使用该密钥的地方，将其更新为新凭证，或者更好的做法是改用基于角色的访问。
  • 从历史记录中移除该密钥（使用 git filter-repo 或 BFG），并强制推送，同时要意识到 fork 和克隆中可能仍保留着它。

生产环境考量： 防止下一次发生：在所有仓库上启用推送保护和密钥扫描、pre-commit 钩子、不为人或 CI 使用长期访问密钥（改用 SSO 和 OIDC），并准备经过演练的轮换操作手册。

64. 你正在值班，凌晨 2 点面向客户的主要 API 开始返回错误。请描述你的应对过程。

回答： 确认告警，评估影响，按合适的严重级别宣布事故，并优先进行缓解，而不是先找根因。

我会检查的内容：

  • 影响范围：涉及哪些端点、区域和客户；服务仪表板上的错误率和延迟。
  • 最近有什么变更：部署、配置或功能开关变更、基础设施变更、证书过期。最近的变更是头号嫌疑对象，回滚它是最快的缓解手段。
  • 依赖项：数据库连接和延迟、下游 API、DNS、云服务商状态。
  • 资源饱和度：CPU、内存、连接池、线程池、队列深度；流量是否异常偏高？
  • 通过追踪和日志定位一个失败请求，找出发生故障的环节。
  • 尽早升级上报，并按固定节奏向相关方通报进展。

生产环境注意事项： 缓解后，用指标确认恢复情况，干净地交接，并安排一次无指责的事后复盘。

65. 不稳定的测试随机导致 PR 门禁失败，开发人员已经开始反复重跑直到变绿。你如何解决这个问题？

回答： 一个可以通过重跑来绕过的门禁就不再是门禁了。目标是快速恢复信任，而不是掩盖真正的失败。

我会检查的内容：

  • 收集数据：哪些测试间歇性失败，频率如何，在哪些运行器上。
  • 常见原因：测试之间的共享状态、测试顺序依赖、时序假设和固定 sleep、真实的网络调用、时区和日期、共享运行器上的资源竞争。
  • 将确认不稳定的测试隔离到一个非阻塞的作业中，并指定负责人和截止日期，而不是删除它们或给门禁加上一刀切的重试。
  • 修复根本原因：为每个测试隔离数据、模拟外部服务、用显式等待替代 sleep、在本地以随机顺序运行测试以暴露依赖。

生产环境注意事项： 有限次数的自动重试作为临时措施是可以接受的，前提是每次重试都被记录并报告；静默重试会掩盖真正的竞态条件，而这些条件同样会影响生产环境。

66. 一个金丝雀发布看起来健康并被晋升了，但现在某个移动应用版本的客户报告出现故障。发生了什么，你该怎么做？

回答： 金丝雀分析很可能只测量了聚合指标，而影响小部分用户的故障——例如依赖新 API 所更改的某个响应字段的旧应用版本——被稀释到阈值以下。通过回滚或用功能开关关闭该变更来缓解，然后再调查。

我会检查的内容：

  • 按客户端版本、地区和端点细分的错误率，而不仅仅是整体错误率。
  • API 差异：是否有被移除或重命名的字段、类型变更或更严格的校验。
  • 契约测试是否覆盖了仍在使用的旧客户端版本。

生产环境注意事项： 为金丝雀分析添加针对重要维度的分段级指标，通过版本管理和弃用窗口保持 API 向后兼容，并为受支持的客户端版本添加消费者契约测试。

67. 一次生产部署运行的数据库迁移中途失败。应用程序正在报错。你该怎么做？

回答： 停止流水线，确保没有其他操作继续进行，精确评估数据库状态，并选择最安全的路径恢复到一致状态。

我会检查的内容：

  • 迁移工具的历史表：哪些步骤已应用，失败的步骤是否在事务中运行（某些数据库无法以事务方式回滚 DDL）。
  • 锁：是否有长时间运行的迁移持有表锁，从而导致应用程序报错？
  • 之前的应用程序版本是否与当前 schema 兼容；如果是，先回滚应用。
  • 备份和时间点恢复作为最后手段，需考虑在此之后写入的数据。

生产环境注意事项： 使用扩展与收缩式迁移，针对生产规模的副本测试迁移，设置锁超时，并将高风险迁移与应用发布分开。

68. 流水线中的 terraform plan 显示它将销毁并重建生产数据库。你会怎么做？

回答： 不要执行 apply。对有状态资源的 replace 是需要立即停线的事件。先查明是哪个属性强制替换。

我会检查的内容：

  • plan 输出中标记为强制替换的行：通常是不可变属性，例如引擎版本系列、子网组、标识符或加密设置。
  • 代码是否被重构（资源被重命名或移入模块）但没有使用 moved 块，这会让 Terraform 认为它是一个新资源。
  • Provider 版本升级改变了默认值。

生产环境注意事项： 对于重构，使用

moved

块或 state 移动来修复，或调整变更使其变为原地更新。用

prevent_destroy

保护关键资源，在数据库上启用删除保护，并设置流水线策略：任何销毁已标记有状态资源的 plan，未经高级人员明确批准一律阻止。

69. 在一次事故中，有人在控制台手动修改了安全组和实例规格。一周后，一次 apply 将其还原并导致又一次故障。如何防止这种情况？

回答： 根本问题是紧急变更没有回写到代码中，导致代码与实际状态出现偏差，下一次 apply 把生产环境“修复”回了故障状态。

我会检查的内容：

  • 审计日志中该时间段内的手动变更及操作者，不追究责任。
  • 定期的漂移检测是否在运行，以及其输出由谁接收。

生产环境注意事项： 让紧急访问（break-glass）被记录并触发告警，要求任何手动变更在事故关闭前必须有对应的后续 PR，运行每日漂移检测 plan 并自动创建工单，并在 apply 前仔细审查 plan 中是否有意外变更。

70. Jenkins 控制器崩溃且无法启动，而今天有一个版本要发布。你会怎么做？

回答： 将 CI 恢复本身作为一起事故处理，同时评估发布是否可以走有文档记录的备用路径。

我会检查的内容：

  • 控制器日志：JENKINS_HOME 磁盘已满、内存不足、配置损坏，或某个插件更新导致无法启动（这是非常常见的原因）。
  • 如果磁盘已满，清理旧的构建日志和产物，并添加保留策略。
  • 如果实例无法恢复，则基于配置即代码（Configuration as Code）和 JENKINS_HOME 的最新备份重建。
  • 对于发布：只有在存在经过审计的紧急部署流程时才使用它；否则推迟发布。

生产环境注意事项： 之后，在预发布控制器中测试插件更新，监控磁盘和堆内存，定期备份，并演练重建流程。

71. 每月云账单大幅上涨，财务部门在追问原因。你会如何调查？

回答： 在成本分析工具中按服务、账户、区域和标签拆分增长，找出推动增长的少数几个条目，并将每一项与某次变更关联起来。

我会检查的内容：

  • 哪些服务增长了：计算、存储、数据传输、NAT 网关处理、日志和监控数据摄取、托管 AI 或 GPU 使用。
  • 未打标签或孤立资源：被遗忘的测试集群、预览环境、未挂载的卷、旧快照。
  • 自动扩容后从未缩容的实例，或 Kubernetes 的资源请求远高于实际使用量。
  • 增长是否属于合理的业务增长，如果是，那么讨论的重点就变成每个客户或每笔交易的单位成本。

生产环境注意事项： 为每个账户和团队添加预算和异常告警，在 IaC 中强制打标签，自动过期非生产资源，并在基础设施变更的拉取请求中展示成本。

72. 你需要为五十个团队统一 CI/CD 标准，而每个团队都有自己的流水线风格。你会如何推进？

回答： 把它当作一个平台产品来做，而不是强制命令。只有当黄金路径比团队自己的脚本更省事时，他们才会采用。

我会检查的内容：

  • 访谈一部分团队，找出共同需求和现有流水线的痛点。
  • 将不可妥协的管控项（安全扫描、签名、审批、审计）与可灵活定制的部分分开定义。
  • 构建带版本管理的可复用模板或共享库，覆盖常见技术栈，提供合理的默认值并文档化扩展点。
  • 先迁移几个愿意参与的试点团队，衡量他们的 DORA 指标并收集反馈，在推广前持续改进。

生产环境注意事项： 为模板做版本管理并逐步推出变更，因为一个损坏的共享模板会同时破坏五十条流水线。通过策略强制执行必要的管控项，确保即使团队自行定制也能生效。

73. 值班团队每周收到大量告警，其中大多数无需采取任何行动。你会如何解决？

回答： 告警疲劳是一种可靠性风险，因为真正的告警会淹没在噪音中被遗漏。解决办法是系统性审查，而不是把所有告警都静音。

我会检查的内容：

  • 导出几周的告警记录：哪些告警触发最频繁，以及每次触发了什么操作。
  • 删除从未引发任何行动的告警；将基于原因的告警降级为工单或仪表盘。
  • 用基于用户可见症状的 SLO 燃烧率告警替代阈值告警。
  • 修复最频繁的合理告警背后的根本原因，例如每周都会写满的磁盘。

生产环境注意事项： 将每班次的页面量作为一项跟踪指标，在每次值班交接时进行审查，并要求每个新的告警都必须有运行手册和负责人。

74. 一个被广泛使用的库公布了严重漏洞，而你有两百个服务。你如何应对？

回答： 速度取决于准备：你需要快速找到受影响的服务，按暴露程度排定优先级，并通过正常的流水线进行修补。

我会检查的内容：

  • 查询 SBOM 或依赖扫描清单，列出包含受影响版本（包括传递依赖）的每一个服务和镜像。
  • 优先处理面向互联网和处理敏感数据的服务。
  • 在可行时应用临时缓解措施：WAF 规则、禁用受漏洞影响功能的配置开关、网络限制。
  • 跨仓库发起自动化的依赖更新 PR，让流水线进行测试和部署，并在仪表板上跟踪进度。
  • 重新扫描运行中的镜像，并检查日志中是否有利用漏洞的尝试。

生产环境注意事项： 这正是对 SBOM、自动化依赖更新以及快速可信流水线的投入获得回报的地方。经常部署小规模变更的团队修补速度要快得多。

75. 采用 AI 编程助手后，PR 数量上升了，但变更失败率也上升了。你该怎么办？

回答： 这就是 DORA 所描述的放大效应：代码到达生产的速度快于审查和测试系统所能承受的速度。应当强化系统，而不是简单地禁用工具。

我会检查的内容：

  • 哪些类型的失败增加了：缺少测试、基础设施配置错误、依赖问题，还是审查者草草浏览的大型 PR。
  • 变更代码的测试覆盖率，以及测试是否在没有真实断言的情况下被生成。
  • AI 辅助变更中的策略与安全扫描发现的问题，例如过于宽泛的 IAM 权限。

生产环境注意事项： 强制使用小型 PR，要求为新代码编写有意义的测试，为 IaC 添加策略即代码，对高风险变更使用渐进式交付，并在跟踪吞吐量的同时跟踪变更失败率和返工率，以便用稳定性来检验生产力主张。

核心要点

  • DevOps 是共同所有权加上快速、安全的流动；工具应放在文化和度量之后。
  • Know the current DORA metrics: change lead time, deployment frequency, failed deployment recovery time, change fail rate and deployment rework rate, and that speed and stability rise together.
  • Build once, promote the same immutable artifact, and make rollback a tested, automated path that includes database compatibility.
  • Choose blue-green, canary, rolling or feature flags based on rollback speed, cost and observability, and be able to explain the trade-off.
  • IaC, GitOps and platform engineering exist to make the right way the easy, self-service way, with guardrails as policy.
  • In scenarios, lead with impact and mitigation, then investigate what changed, then prevent the class of problem.
  • AI helps with code, review and operations, but it amplifies existing practices; keep humans approving write actions and measure stability.

Interview preparation checklist

  • Draw your project's pipeline from commit to production on a whiteboard, naming every stage and why it exists.
  • Explain CI vs continuous delivery vs continuous deployment, and the five DORA metrics, in under two minutes each.
  • Build and deploy one service end to end with GitHub Actions or Jenkins, Docker, Terraform and Kubernetes, then break it and fix it.
  • Practise a canary or blue-green rollout and a rollback, including a backward-compatible schema change.
  • Set up OIDC from CI to a cloud account so you can explain keyless authentication from experience.
  • Write a Terraform configuration with remote state and locking, and explain what forces resource replacement.
  • Create a Grafana dashboard and one SLO-based alert with a runbook.
  • Prepare three stories: a failure you diagnosed, an automation that saved time, and a disagreement you resolved.
  • Rehearse scenario answers in the order: impact, recent change, mitigate, communicate, root cause, prevention.

FAQ

What skills are required for a DevOps engineer role in 2026?

Linux, networking basics, Git, scripting in Bash or Python, one CI/CD tool, Docker, Kubernetes fundamentals, Terraform, one cloud platform in depth, and monitoring. Troubleshooting and communication matter as much.

How should a fresher prepare for a DevOps interview?

Learn Linux, Git and one cloud well, then build one end-to-end project with a pipeline, containers, Terraform and monitoring. Practise explaining it, break it deliberately, and prepare answers on how you diagnosed each failure.

Can a fresher get a DevOps engineer job?

Yes, though many freshers start in related roles such as cloud support, build and release, or junior operations and move into DevOps.

Which CI/CD tool should I learn first?

GitHub Actions is a practical first choice because it is easy to start and widely used. Learn Jenkins concepts as well, since many enterprises and GCCs still run Jenkins, and the pipeline principles transfer between tools.

How are experienced DevOps engineers interviewed differently from freshers?

Experienced candidates get fewer definitions and more design and scenario questions: pipeline architecture, deployment strategies, Terraform state, incident handling, security controls and how they measured improvement with DORA metrics.

Do I need to know Kubernetes for a DevOps interview?

For most roles, yes, at least pods, Deployments, Services, ConfigMaps, Secrets, probes and basic troubleshooting.

Is DevOps a good career with AI changing software development?

AI changes the work rather than removing it. Someone still has to design pipelines, secure supply chains, run AI workloads reliably and govern AI-generated changes, and those skills are in demand across product companies and GCCs.

What is the difference between DevOps and SRE?

DevOps focuses on delivery flow and automation across the lifecycle, while SRE focuses on reliability using SLOs, error budgets, incident response and toil reduction. The skills overlap heavily.

Are certifications necessary for DevOps jobs?

They are not mandatory but can help with shortlisting, especially cloud and Kubernetes certifications. Pair any certification with a project you can explain.
