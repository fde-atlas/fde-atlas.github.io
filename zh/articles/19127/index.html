FDE 求职如何证明能力：项目部署复盘怎么写

FDE Times · 2026-10-09 · 约 6 分钟读完

摘要

文章讨论 FDE 求职者如何用项目部署复盘证明能力。Robert Half 2026 年 3 月调查显示，67% 的美国 HR 负责人认为 AI 生成的简历拖慢招聘，精致简历因此贬值。作者认为公开写作很少能让招聘方主动找上门，其价值体现在学习阶段和面试官核查你的时候。文章建议做一个含真实云端部署（API、身份认证、日志）的完整项目，并撰写包含用户故事、架构决策、失误和已知局限的复盘文章，与内推结合使用效果最好。

要点

  • Robert Half 调查：67% 的美国 HR 负责人称 AI 简历拖慢招聘。
  • 公开写作很少吸引招聘方，价值在核查时显现。
  • 有分量的项目需真实部署：API、身份认证、日志。
  • 复盘应写清架构、失误和已知局限，经得起追问。
  • 部署复盘与内推结合是最有效的求职策略。

67% 的美国 HR 负责人称 AI 简历拖慢招聘，项目复盘的价值在有人核查你时才显现。

要点速览

  • Robert Half 的一项调查显示，67% 的美国 HR 负责人表示，审阅 AI 生成的简历拖慢了招聘，可核查的证据因此更有价值。
  • 一个公开项目要有分量，需要有包含 API、身份认证和日志的真实部署，以及一份写清架构和已知局限的 README。
  • Hacker News 上的个人经历表明，简历很少被细读，内推也并非十拿九稳。项目复盘真正起作用，是在有人已经开始了解你的时候。

2026 年 3 月，招聘公司 Robert Half 公布了一个值得求职者琢磨的数字：67% 的美国 HR 负责人表示，审阅 AI 生成的简历拖慢了招聘。雇主收到的申请更多了，选人却花得更久。

Hacker News 上有个帖子讨论：AI 都能写简历了，现在哪些招聘信号还重要？一位评论者半开玩笑地说，太过完美的简历多半出自 AI 之手。照这个逻辑，一个小错误反倒成了真人的标志。

一份精致的简历几乎不费力气就能得到，精致本身也就不值钱了。Robert Half 的结论是：雇主越来越需要可信的人来核实候选人的技能。

如果你瞄准的是前线部署工程师（FDE）岗位，这就是你要面对的问题。The Pragmatic Engineer 注意到，大约从 2025 年初开始出现一波 FDE 招聘潮；截至 2026 年 5 月，它仍称需求旺盛且在增长，Google、OpenAI 和 Anthropic 都在大举招人。

那么，公开写自己的项目，能不能让你从海量申请中脱颖而出？能，但很少是靠让招聘方找上门。一篇讲项目如何上线生产环境的文章，在两个时刻最有价值：一是你还在学习的时候，二是有人已经想核查你的工作的时候。

FDE 招聘方想核实什么？

The Pragmatic Engineer 的作者 Gergely Orosz 指出，几乎所有招 FDE 的雇主都看重扎实的软件工程基础。这是底线，一个整洁的 GitHub 仓库就能证明。

有些公司要求更高。Orosz 提到的 Commure 和 Matta 两家公司，看重端到端构建并交付项目的实战经验。“交付”这一环，光靠代码讲不完整。

FDE 职业指南 FDE Academy 建议候选人介绍一个已经开发完成并部署上线的项目，而不只是展示代码。Blockchain Council 说得更进一步：与其做许多小 demo，不如以生产环境的标准，做一个完整的公开产品。

按这一来源的说法，这样的项目应该有真实的云端部署，包含 API 接口、基本的身份认证和运行日志。配套的 README 应包括用户故事、架构图、运行说明和已知局限。

最后一项值得留意。demo 从不展示已知局限，而把局限列出来，就是在告诉读者：你清楚自己的系统会在哪里出问题。

两个候选人，同一个项目

设想两位候选人，各自做了一个智能体，读取客户支持工单并把结果写入 CRM。候选人 A 有一个整洁的仓库、一份附安装说明的 README 和一个 demo。候选人 B 有同样的仓库，外加一篇长文。

B 在文中解释了：CRM 的 API 限流时为什么需要一个队列；用户多年手工录入的杂乱字段是怎么映射的；智能体写错内容时，B 又是如何向支持人员解释的。

A 证明了扎实的软件工程基础。B 还证明了自己把一个项目从构建一路做到交付，这正是 Commure 和 Matta 这类公司在找的。

差别在面试现场最明显。B 的面试官手上已有可以深挖的素材：“如果客户不让你搭队列，你会怎么办？”每一个扎实的回答，都是 AI 难以替你写出来的证据。

A 的面试官只能从零开始，而此时他们恰恰最有理由怀疑一份看起来过于完美的简历。

没人读你的博客，除非关键时刻

别对简历上的那个链接抱太大期望。在同一个 Hacker News 帖子里，有人说招聘方很少读简历；另一个人认为真正管用的是内推，随即有人回复说，在他们公司连内推都不再优先了。

这些是个人经历，不是数据，但足以说明没有捷径。所以，别把写文章当成让招聘方找到你的手段。

Shawn Wang（swyx）展示了另一面。他说，自己全部的公开写作“被翻了出来”，用他的话说，差不多就是靠这些拿到了 AWS 的工作。注意这个动词：写作是“被翻出来”的，也就是有人在找的时候发现了它，而不是它主动上门敲门。

swyx 还指出了一个在被录用之前就能拿到的好处。对他来说，公开写作是一种有章法的学习方式，读者会指出你哪里错了。让陌生人在博客上挑出你队列设计的毛病，远比在面试中被挑出来舒服得多。

下表比较了 FDE 候选人通常拥有的四类信号。各列内容是编辑部根据上述建议和个人经历作出的评估，并非实测数据。

信号 是否难以用 AI 伪造？（评估） 能证明什么 何时被阅读
简历要点 极易伪造 不经核实几乎证明不了什么；太过精致反而招人怀疑 筛选阶段，如果有人读的话
只有代码的 GitHub 仓库 中等 软件工程基础 招聘方愿意点开的时候
附真实部署的部署复盘文章 难，因为要经得起追问 端到端项目：用户故事、架构、局限、运维 面试官了解你时，或内推人转交时
内推 难 不能直接证明什么，只是他人的背书 筛选之前，如果内推仍被优先的话

没有哪种信号单独就够。内推来得最早，却证明不了能力，而且按一些人的经历，它也不再十拿九稳。

部署复盘文章证明力最强，但通常最后才被读到。内推人帮你敲开门，文章给面试官提供可以核查的内容。两者结合是最明智的策略。

怎么写出经得起“那又怎样？”的文章

别同时铺开五个项目，挑一个就好。Blockchain Council 建议做一个完整的产品，是有道理的：围绕一个真实系统写深写透，比五个 demo 更能给面试官留下深挖的空间。

文章结构可以沿用这一来源为 README 列出的几个部分。从用户故事讲起。以上面的工单智能体为例，可以是：支持人员要花时间把结果手工复制进 CRM，历史数据一团糟。

中间、也是篇幅最长的部分，讲架构和集成决策。画一张简单的图：工单进来，经过智能体，进入队列，再写进 CRM。然后坦诚写一件你做错的事，比如第一次直接调用 API，结果被限流挡住了。

最后一部分讲已知局限：哪类工单智能体会处理错，出错时你如何告知支持人员。附上真实部署的链接，包括 API、身份认证和日志，让读者可以亲自核查，而不必只听你说。

发布前做个测试：重读每一段，问一句“那又怎样？”。答不上来的段落，或者只是罗列所用技术的段落，都应该围绕一个具体决策及其理由重写。

如果你的简历上还没有一行写到为真实客户做部署，这篇文章就是你证明自己能独立把系统从想法做到稳定运行的地方。

简历上的每个项目都应该有一句用部署语言写成的描述，例如“针对限流的 CRM 上线了一个智能体，处理手工录入的数据”，并附上文章链接。

阅读岗位描述时，留意“端到端”“面向客户”“集成”这类说法。这些地方正是你的文章可以充当证据的地方。然后请一位业内熟人先读一读、给些反馈，再开口请他内推。

当人人都能拥有一份精致的简历，最难伪造的，是一个系统真实运行过的痕迹，以及一个经得起“那又怎样？”追问的故事。
