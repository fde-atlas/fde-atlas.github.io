面向 FDE 的 Python 与 SQL：如何验证客户数据

原标题：Python and SQL for FDEs: How to Validate Customer Data

FDE Times · 2026-10-08 · 约 7 分钟读完

摘要

文章以一个真实场景开篇：FDE 给客户写的 SQL 查询无报错，却因 JOIN 导致订单重复计数，收入虚高。作者认为 Python 和 SQL 是 FDE 的基本门槛，SQL 首先应作为数据校验工具而非报表工具。文章引用 Palantir、Databricks、Capicua 等公司的职位要求佐证，并给出具体做法：先检查键是否唯一、比较 JOIN 前后行数、用 LEFT JOIN 找出未匹配记录，再用 ROW_NUMBER() 去重修复，最后把校验逻辑固化为带 validate 和 assert 的 Python 脚本。文中还列出常见错误，如习惯性用 INNER JOIN、擅自决定去重规则、用 SELECT DISTINCT 掩盖问题等。

要点

  • SQL 首要是校验客户数据，其次才是产出报表。
  • 坏 JOIN 不报错，会重复或丢失数据，最危险。
  • 校验三步：查键唯一性、比 JOIN 前后行数、找未匹配记录。
  • 用 Python 的 validate 和 assert 把检查变成可重复的脚本。
  • 去重规则是业务决策，应与客户确认而非自行猜测。

一个悄悄重复计算订单的 JOIN，正是 FDE 招聘启事把 Python 和 SQL 视为底线、把先检查键视为习惯的原因。

简要概述

  • 客户数据通常很混乱，所以 SQL 首先是检查数据的工具，其次才是生成报表的工具。
  • 最危险的错误是错误的 JOIN：它不会报错，但会重复行或丢失数据。
  • Python 把这些检查变成带有断言的可重复代码，在任何东西成为产品之前就完成验证。

周一，你获得了客户 Postgres 数据库的只读权限。到中午，他们的销售负责人想要按地区划分的收入。你在

orders

表和

customers

表之间写了一个 JOIN，三秒钟就运行完毕，然后你把结果发了过去。

当天下午他们打来电话。你表格中的总收入比财务部门的数字要高。查询没有语法错误，也没有抛出任何异常。它只是把一些订单计算了两次，而且没有告诉任何人。

这种情况正是 Python 和 SQL 被视为 FDE 工作底线的原因。你不需要了解一长串框架。你需要的是在信任数据之前先检查数据的习惯，以及足够的技能把这些检查变成可以重复运行的代码。

招聘启事对这个底线是怎么说的？

Capicua 将 FDE 工作描述为编写直接在客户基础设施和数据上运行的生产代码。招聘启事也指向同样的方向；它们的主要区别在于是否明确提到 SQL。

Databricks 在其新加坡高级 FDE 职位的任职要求中明确列出了 Python 和 SQL，还希望 FDE 能够将 OpenAI、Anthropic 和 Gemini 等 AI API 集成到应用程序中。Palantir 要求精通 Python、Java 或 C++ 等语言，并提到用 Python 进行数据处理和分析，但没有提到 SQL。

即便如此，Palantir 的另一份招聘启事提到了 Postgres、Cassandra、Hadoop 和 Spark。Paraform 将其概括为一种后端语言加上快速提取和整理数据的能力。

阅读招聘启事时，注意诸如“提取和整理数据”或“数据处理”之类的措辞，或者诸如 Postgres 和 Spark 之类的具体系统名称。这些信号表明你将直接处理真实数据。即使是 AI API 集成也建立在数据之上，如果数据是错的，产品也是错的。

关键词是“客户的”：这些数据是别人设计的，而你完全不知道有多少代系统修改过它。

为什么说 SQL 首先是检查工具？

HCL GUVI 称 SQL 是 FDE 最实用的技能之一。其理由是客户环境中充满了数据库、运营记录和不一致的数据。它还警告说，错误的 JOIN 可能产生重复记录或悄悄抹掉重要信息。

它的建议是调查客户数据，而不是默认信任它。

所以 FDE 的 SQL 有两个任务。第一个是质询数据：键真的唯一吗？JOIN 会不会使行数膨胀？有没有行被丢掉？只有在这之后，它才回答业务问题。

示例：拆解一个被夸大的收入数字

回到周一下午。假设

customers

表有

customer_id

,

region

表和

updated_at

这几列。第一个问题是

customer_id

是否真的是唯一键。（下面的列别名是越南语：

row_count

是行数，

customer_count

是客户数，

record_count

是记录数。）

-- 1. Is the key unique?
SELECT COUNT(*) AS row_count,
       COUNT(DISTINCT customer_id) AS customer_count
FROM customers;

-- If row_count > customer_count, see who is duplicated
SELECT customer_id, COUNT(*) AS record_count
FROM customers
GROUP BY customer_id
HAVING COUNT(*) > 1
ORDER BY record_count DESC
LIMIT 10;

想象结果显示有些客户有两条或三条记录：每次他们更改地址时，系统都会新增一行，而不是更新旧记录。这些客户的每一笔订单在 JOIN 中都会被重复计算。多出来的收入就来自这里。

下一步是直接度量 JOIN 的影响，而不是凭猜测：

-- 2. Does the JOIN change the row count?
SELECT
  (SELECT COUNT(*) FROM orders) AS before_join,
  (SELECT COUNT(*) FROM orders o
     JOIN customers c ON c.customer_id = o.customer_id) AS after_join;

-- 3. Are there orders with no matching customer (an INNER JOIN would drop them)?
SELECT COUNT(*) AS unmatched_orders
FROM orders o
LEFT JOIN customers c ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL;
before_join

（JOIN 之前）和

after_join

（JOIN 之后）必须相等。如果

after_join

更大，说明你在重复计算行。如果

unmatched_orders

（未匹配的订单）大于 0，说明原来的 INNER JOIN 正在悄悄丢弃这些订单。

修复方法：只保留每个客户的最新记录，并使用 LEFT JOIN，这样就不会丢失任何订单。

WITH cust AS (
  SELECT customer_id, region,
         ROW_NUMBER() OVER (PARTITION BY customer_id
                            ORDER BY updated_at DESC) AS rn
  FROM customers
)
SELECT COALESCE(cust.region, '(unknown)') AS region,
       SUM(o.amount) AS revenue
FROM orders o
LEFT JOIN cust ON cust.customer_id = o.customer_id AND cust.rn = 1
GROUP BY 1
ORDER BY revenue DESC;

那个

(unknown)

（“未知”）行不是需要隐藏的错误，而是需要带回给客户的发现：有多少订单无法关联到任何客户，以及为什么。

Python 让检查变得可重复

上面的 SQL 只能回答今天的问题。下周新数据到来时，你需要这些检查能够自动运行并在失败时报错。Python 可以做到这一点，这也是 Palantir 招聘启事中“数据处理与分析”变成具体工作的地方。

import os
import pandas as pd
from sqlalchemy import create_engine

engine = create_engine(os.environ["CUSTOMER_DB_URL"])

orders = pd.read_sql("SELECT order_id, customer_id, amount FROM orders", engine)
customers = pd.read_sql(
    "SELECT customer_id, region, updated_at FROM customers", engine
)

# Keep the most recent record for each customer
customers = (customers.sort_values("updated_at")
                      .drop_duplicates("customer_id", keep="last"))

# validate raises an error if the customers side still has duplicate keys
merged = orders.merge(customers, on="customer_id",
                      how="left", validate="many_to_one")
assert len(merged) == len(orders), "JOIN changed the row count"

unmatched_rate = merged["region"].isna().mean()
print(f"Share of orders with no matching customer: {unmatched_rate:.1%}")

report = (merged.fillna({"region": "(unknown)"})
                .groupby("region")["amount"].sum()
                .sort_values(ascending=False))

这里最有价值的三行代码是

validate="many_to_one"

，它在客户侧仍有重复键时抛出错误；是

assert

，它在 JOIN 改变了行数时失败；还有那行打印无匹配客户订单占比的代码。它们共同把周一下午的教训变成了硬性要求。下次数据出问题时，流水线会在错误数字到达客户之前停下来。

应该按什么顺序工作？

每次遇到新的客户表，都遵循同样的流程。首先，统计行数和去重后的键数，看看键是否真的唯一。然后度量每次 JOIN 前后的行数，并用 LEFT JOIN 加上

IS NULL

.

一旦发现问题，就在查询层面用 ROW_NUMBER() 或与客户确认过的记录选择规则来修复。最后，把所有检查移入 Python 作为断言，并且始终在报告总数的同时报告未匹配数据的占比，而不只是总数。

常见错误

最常见的错误是习惯性地使用 INNER JOIN。它看起来整洁，却恰好丢弃了你最需要看到的记录。另一个错误是自己决定去重规则：“取最新记录”是一个业务决策，应该询问客户，而不是自己猜测。

另一个错误是用

SELECT DISTINCT

来在查询末尾打补丁。它掩盖了症状却不告诉你原因，还可能把真正不同的行合并在一起。

最后一个错误是在笔记本里手动检查，却不把工作保存为脚本。下周数据变了，旧的 bug 又出现了，而且没人记得当时检查过什么。

如何在简历上展示这项技能

对于转型做 FDE 工作的开发者来说，简历上写“精通 Python 和 SQL”几乎说明不了什么。更有说服力的一句话应该讲一个故事：发现某张客户表存在重复键导致报告的营收虚高，用 pandas 编写了自动化检查，并向运营团队报告了未匹配订单的比例。

本周练习

找一个你有读取权限的真实数据库，可以是工作中的数据库，也可以是至少包含两张关联表的公开数据集。选一个你或同事曾经写过的报表查询，运行上述三项检查，然后把它重写为一个带有

validate

表和

assert

.

如果三项检查全部通过，你现在就有了证明这个数字正确的证据。如果没有通过，你就在客户之前发现了 bug，而这正是 FDE 的职责。
