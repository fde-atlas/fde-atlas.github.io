FDE 系统设计面试：客户部署、RAG 与集成

原标题：FDE System Design Interview: Customer Deployments, RAG, Integrations

Crack ML Interview · 2026-11-11 · 约 12 分钟读完

摘要

这篇指南讲解 FDE 岗位的系统设计面试：与“设计 Twitter”不同，系统必须运行在客户环境中，受其单点登录、网络规则、数据驻留和不可更改的记录系统约束。文章提出六步框架（上下文、契约、数据流、信任边界、故障处理、上线运维），并以律所文档助手为例演示权限感知的 RAG 设计，包括查询前权限过滤、约 330GB 向量存储的容量估算、约两周的回填调度、评测与分阶段上线，还列出常见追问、评分维度和 14 道练习题。

要点

  • FDE 系统设计面试考察在客户约束下的设计，而非通用互联网架构。
  • 提出六步框架：上下文、契约、数据流、信任、故障、上线。
  • 律所案例强调查询时权限预过滤，权限失败时应拒绝回答。
  • 用真实数字做容量与回填估算，如 8000 万文档约两周嵌入。
  • 评分关注集成、审计、幂等写入、故障恢复与交接运维。

简要总结

FDE 系统设计不是“设计 Twitter”。系统运行在客户的环境中：他们的单点登录、他们的网络规则、他们的数据驻留要求、他们无法更改的记录系统。优秀的回答从这些约束出发，定义与现有系统的契约，画出带幂等写入的数据流，把权限和审计放在核心位置，规划部分失败和数据回填，并以客户能够运维的上线方案收尾。用真实的算术来估算规模，而不是一句“它能扩展”。

这个环节考察什么

  • 在你无法控制的约束下进行设计：系统可以运行在哪里（客户的云账户、本地部署、你的 SaaS）、使用哪个身份提供商、哪些数据可以离开哪个区域。
  • 通过真实接口与记录系统集成：有速率限制的 API、夜间文件、变更数据流、会重复到达或乱序到达的 webhook。
  • 把安全作为设计输入：通过客户的单点登录进行认证、镜像源系统权限的授权、密钥管理、审计日志和个人数据处理。
  • 失败与恢复：重试、死信队列、重放、回填以及修复 bug 后的重新处理，且不产生重复效果。
  • 运维它：分阶段上线、可观测性、成本，以及你离开后客户自己的团队要如何运行它。
  • 对于 AI 系统：带评测、溯源和防护栏的检索与 AI Agent 设计，而不只是一次模型调用。

如何应对：上下文、契约、数据流、信任、失败、上线

我们的指导（编辑观点），而非候选人报告

  • 上下文与约束 询问系统运行在哪里、谁在使用、有多少用户和多少数据、延迟预期、合规要求以及截止日期。把数字记下来；你将用它们来做规模估算。
  • 与现有系统的契约 列出你读取或写入的每个系统、它的接口（API、文件投递、数据库副本、事件流）、它的限制以及负责人。决定哪些必须对用户是同步的，哪些可以是异步的。
  • 数据流 摄取、转换、存储、服务。为每条流选择批处理或流式处理，让每次写入都是幂等的（自然键或幂等键），并说明如何检测上游的 schema 变更。
  • 信任边界 通过客户的身份提供商（SAML 或 OIDC）进行单点登录、从源系统派生的授权、最小权限服务账户、托管存储中的密钥、对每次敏感数据读取的审计日志，以及哪些个人数据被存储、存在哪里、存多久。
  • 失败模式 针对每个外部依赖：当它变慢、宕机、对你限速或发送坏数据时会发生什么。带退避的有界重试、可重放的死信队列、对账任务，以及修复 bug 后重新处理历史数据的能力。
  • 上线与运维 影子模式、试点小组、功能开关、仪表盘上的三四个指标、附带运维手册的告警、每月成本，以及向客户团队的交接。

实例解析：为一家律师事务所构建具备权限感知的文档助手

提示词

一家拥有 5,000 名员工的律师事务所想要一个内部助手，用于回答有关其文档管理系统（DMS）的问题：该系统约有 800 万份文档，按客户案件组织。部分案件处于伦理隔离墙之后：只有该案件的律师可以查看。所有内容必须保留在律所自己的云账户中。请设计该系统。

  • 背景与数字 假设每日 2,000 名用户，峰值每秒 20 个问题，目标是第 95 百分位的首个答案 token 在 3 秒内返回，且每个答案都必须引用其使用的文档。假设每份文档平均 10 个分块、每块约 250 个 token：共 8,000 万个分块。
  • 契约 DMS 是文档和权限的记录系统。通过其 API 使用只读服务账户读取文档和访问列表，并订阅其变更事件（新版本、删除、权限变更）。用户使用律所的身份提供商登录；组成员关系来自该提供商。
  • 摄取 回填任务和增量任务汇入同一条流水线：获取文档、提取文本（扫描件使用 OCR）、按标题切分为分块、生成嵌入，并将分块文本、向量和元数据（文档 id、版本、案件 id、允许的主体）写入索引。键为文档 id 加版本，因此重放会覆盖而不是重复。容量估算：8,000 万个 1,024 维 float32 向量约 330 GB；int8 量化后约 82 GB 加上图结构开销，可容纳在几个内存优化的节点上。回填的瓶颈是嵌入吞吐量而非成本：200 亿个 token 按每分钟 100 万个计算约需两周，因此第一天就启动，并优先处理活跃案件。
  • 查询时的权限控制 这是设计的核心。每个分块存储其文档允许读取的主体。查询时，解析用户的主体（用户 id 加组），并将其作为过滤器传入向量搜索内部，使受限分块永远不会成为候选。检索后再过滤是双重错误：受限文本已被获取，且前 10 条结果可能为空。当 DMS 变更文档的访问列表时，更新分块元数据（无需重新嵌入）；一个夜间任务比较 DMS 与索引之间的访问列表并修复漂移。如果权限查询失败，则不回答任何内容：默认拒绝（fail closed）。
  • 回答 采用混合检索（关键词加向量），因为律师会搜索定义术语、案件名称和条款编号；对前 50 条重排为 8 条；生成时指示模型仅根据段落作答并为每个论断引用来源。引用以链接形式指向 DMS，打开时会再次校验权限。
  • 信任、审计与故障记录每一次提问、检索到的文档 ID 和答案，并按律所的政策保留，因为律所必须能够证明谁查看了什么。模型端点在律所的云账户内运行。如果 DMS 对摄取进行限流，变更事件队列会吸收压力；反复失败的事件会进入死信队列，并配有重放工具。
  • 评估与上线在上线前，用两个业务组构建测试集：200 个真实问题及其对应的答案文档。跟踪前 10 的检索召回率、引用支持每个论断的答案占比，以及以受限访问账户运行的权限测试套件，通过标准是零泄露。先以影子模式（答案仅项目团队可见）推广到一个业务组，然后到该业务组，最后全所推广。

为什么这个回答得分高：候选人把权限放在核心位置，并为选择预过滤给出了明确理由；完成了存储和回填的算术计算，并由此得出调度上的结论；保持 DMS 作为唯一事实来源；定义了包含安全门槛的评估。注意其中没有出现的内容：没有花时间在向量数据库品牌之间做选择。

常见追问及其考察点

  • “一名律师在 10:00 被移出某个案件。他们什么时候会停止看到该案件的文档？”
  • 考察权限的时效性。事件驱动的更新需要几秒到几分钟；说明这个时间窗口，如果律所需要零延迟，可为处于信息隔离墙后的案件增加针对 DMS 的逐查询校验。
  • “客户不允许任何数据离开他们的网络，包括发送到模型 API。”
  • 考察部署选项。在其网络内自托管开放权重模型，并接受随之而来的容量与质量权衡；或者如果符合规则，使用托管在客户云账户内的供应商模型。
  • “上线之后你怎么知道答案质量是好的？”
  • 考察生产环境中的评估。抽样人工审核、带理由的点赞或点踩、监控无引用的答案，以及每次更改提示词、分块或模型时重新运行离线测试集。
  • “源 API 每秒允许 10 个请求，而你需要读取 800 万份文档。”
  • 考察算术能力。800 万个请求按每秒 10 个计算需要超过九天。应要求批量导出或更高的限额，优先处理活跃数据，并把管道设计为可断点续传。
  • “单租户还是多租户？”
  • 考察隔离性的权衡。受监管的客户通常要求专用部署；这会带来更高的运行和升级成本。如果采用多租户，则在每个键、查询和日志中都加入租户 ID，并用测试证明隔离性。

常见错误

  • 当客户只有 2,000 个用户时却按互联网规模设计，并且遗漏了真正的难点——集成和权限。
  • 在检索之后才过滤权限，或者忽略数据摄取后的权限变更。
  • “我们要用一个向量数据库”，却没有分块、检索、评测或更新策略。
  • 没有针对回填、出现 bug 后重新处理或上游 schema 变更的方案。
  • 写操作不具备幂等性，导致每次重试都可能在客户系统中产生重复记录。
  • 没有上线、监控或成本估算方案。

常见问题

  • FDE 系统设计与标准系统设计面试有何不同？
  • 标准轮次通常允许你假设拥有一个从零开始的系统。FDE 轮次则将系统置于客户的环境中，因此身份、权限、与无法更改的系统的集成、数据驻留和上线部署的权重远高于原始规模。
  • 这一轮需要了解 RAG 和 AI Agent 吗？
  • 对于专注于 AI 的公司，通常需要：许多反馈的设计问题都是围绕模型的助手或流水线。你需要充分掌握检索、分块、混合搜索、重排序、评测和权限感知过滤，以便做出并捍卫你的选择。
  • 我应该点名具体产品吗？
  • 说出类别和所需的属性（“一个支持搜索时过滤的向量索引”），仅在举例时提及某个产品。面试官关心的是属性，而客户可能已经有既定标准。
  • 应该在安全上花多少时间？
  • 足以让安全成为设计的一部分而非事后补充：对于企业部署，通常占讨论的四分之一。展示身份验证发生在哪里、授权如何推导，以及记录哪些内容。

其他 FDE 轮次

问题分解

将模糊的业务需求转化为范围明确、可构建的计划：目标成果、你真正拥有的数据、第一个切片，以及你如何知道它成功了。

实用编码

针对混乱输入编写可运行的代码：数据整理、调用分页且限流的 API，以及调试并非你编写的代码。

AI / LLM 应用

在模型 API 上构建有用的东西：结构化输出、检索、工具和 AI Agent，并配有证明其有效的评测，以及失效时的防护措施。

行为与客户

关于担当和判断力的故事，加上现场角色扮演：一次失败的演示、一位不满的赞助人、一个你必须拒绝的请求。
