FDE 岗位解读：Column 招聘前线部署工程师

FDE Times · 2026-10-28 · 约 5 分钟读完

摘要

文章分析以 API 形式提供银行服务的 Column 于 2026 年 10 月 6 日发布的 FDE 招聘启事。作者指出，即使产品有完善的 OpenAPI 规范和沙箱，客户集成之处才是产品本身，FDE 的价值在于把客户卡住的地方带回产品。文章对比了 FDE 与 Solutions Engineer 的分工：前者专注战略客户从接入到上线，后者覆盖售前到售后全过程，并给出面试提问与简历写法建议。

要点

  • Column 于 2026 年 10 月 6 日在旧金山招聘 FDE。
  • FDE 负责战略客户从接入到上线，并可塑造 API 与文档。
  • Solutions Engineer 覆盖售前到售后，FDE 范围更窄但通向产品。
  • 作者建议用面试提问验证招聘启事中的承诺。
  • 简历应写成从客户问题到产品改动的完整链条。

Column 的 API 有规范文档和沙箱，但底下是一家真正的银行，客户集成之处才是产品本身。

要点速览

  • 以 API 形式提供服务的银行 Column 于 2026 年 10 月 6 日发布了一个位于旧金山的 FDE 岗位。
  • Solutions Engineer 覆盖客户从售前到支持的全过程，Column 的 FDE 则针对战略客户，负责从接入到上线的完整阶段。
  • 在 FDE 招聘启事里，“塑造 API 和文档”这类面向产品的动词，是区分真正 FDE 岗位与改名客服岗位的标志。

2026 年 10 月 6 日发布的一则招聘启事显示，以 API 形式提供服务的银行 Column 正在旧金山招聘一名前线部署工程师（FDE）。这名工程师将担任战略客户的技术负责人，从接入一直负责到上线当天。

乍看之下，这有些矛盾。Column 的 API 由 OpenAPI 规范描述，并配有沙箱，正是那种本该让客户自助完成的产品：读文档、调接口、把事做完。那为什么还要在客户身边安排一名工程师？

如果你是 FDE，或者想成为 FDE，这个问题值得想清楚。产品是 API 时，客户集成的地方就是产品本身。

站在那里的人，如果被赋予足够的权限，就不只是让客户跑起来。他们会把客户卡住的地方带回产品，推动修复。这正是真正的 FDE 与换了名字的客户支持之间的分界线。

为工程师打造的银行，但并非从零起步

Column 称自己是唯一一家专为帮助客户构建新金融产品并为其提供资金而设计的全国性特许银行。公司表示，它由工程师创立，就是为了解决与现有银行合作时的种种不便。

不过，“为工程师打造的银行”并不意味着从零建起。据一家律所的 wiki 介绍，创始人没有再做一家创业公司，而是收购了加州 Chico 一家只有一个网点的银行。

这个细节对 FDE 的意义比看上去更大。API 层之下是一家真正的银行：Column 的 Solutions Engineer 招聘启事里也列出了监管和风控方面的职责。因此，站在客户和 API 之间的人，既要懂代码，也要懂那些规范文档无法完全写清的约束。

文档写得好，为什么还不够

设想一家创业公司想在自己的 App 里嵌入账户和转账功能。团队读完文档，很快就在沙箱里搭好了流程。接着，他们卡在了文档没写的地方：转账被退回时怎么对账，怎样为终端客户建模账户，上线当天之前必须完成哪些事。

如果每个问题都走工单，客户团队要等上好几天，银行看到的则是十张互不相关的工单。但如果十个战略客户恰好卡在同一个地方，那就不是十个支持案例，而是文档或 API 设计中的一个缺陷。只有从头到尾跟完一次集成的人，才能看出这种规律。

这就是 Column 的招聘启事把两份工作交给同一个人的原因。FDE 直接与合作方的工程团队一起设计、构建和上线产品，同时与 Column 自己的工程师紧密合作，塑造 API、文档和开发者体验。

FDE 和 Solutions Engineer 有什么不同？

Column 并不缺面向客户的工程师。它的 Solutions Engineer 岗位负责售前、实施、接入和支持各阶段与客户的技术对接，启事本身还写明，这个岗位比行业里常见的同类岗位技术性更强。

既然两个岗位都高度偏技术，区别就不太可能在技能水平上。细读两份启事，区别在于覆盖的阶段：Solutions Engineer 覆盖从售前到售后的全过程，FDE 则以技术负责人的身份负责更窄的一段，从接入到上线，并且能参与产品本身。

把这份启事放在 FDE 的独立定义旁边对照，就能看清哪些是 Column 明确承诺的，哪些需要自己去问。风投机构 CRV 认为，在客户环境中编写生产代码是 FDE 的标志性特征，并认为 FDE 可以在写代码的同时覆盖售前和售后。

PostHog 将 FDE 描述为嵌入客户团队、弥合产品与真实需求之间差距的人。Palantir 的 Forward Deployed Software Engineer 招聘启事则写道，这类工程师与客户合作，常常在现场，去理解并解决客户的问题。

FDE 标准 来源 Column 的 FDE 招聘启事 面试时可以问的问题
在客户环境中编写生产代码 CRV 与合作方工程团队一起设计、构建和上线 你写的代码放在客户的仓库里，还是 Column 的仓库里？
覆盖售前和售后 CRV 从接入到上线；售前归 Solutions Engineer 谁把客户交给你，你从哪个阶段开始介入？
弥合产品与需求的差距 PostHog 与工程团队一起塑造 API、文档和开发者体验 上一次客户反馈改变 API 是什么时候？
常在客户现场工作 Palantir 启事未提及 你在哪里办公，每周和客户相处多少时间？

最后一列最重要。招聘启事给的是承诺，面试中的回答才能告诉你这个承诺是否兑现。

像工程师一样读 FDE 招聘启事

PostHog 指出，有些公司把 FDE 的头衔用在更接近售前工程师的工作上。所以，无论在哪个国家，两份都写着 FDE 的招聘启事，并不保证是同一份工作。

线索在动词里。如果启事像 Column 这样写明 FDE 将塑造 API、文档或平台，这个岗位就有一条通回产品的路径。如果启事只谈支持和合作，就直接问：最近一次把客户需求推进到产品里的变更，是谁推动的？

Column 的启事里还有一句值得留意：候选人需要很强的项目管理能力，能同时推进多个客户项目，并让每一个都持续向前。

在简历里写清岗位的两部分

如果你曾在看到客户反复问同一个问题后改过文档，或者因为某个接口让集成方猜错而提议修改它，就把这些经历放在简历最前面。对于 Column 这样描述的岗位，这是最直接的证据，说明你能把客户杂乱的问题转化为对产品的具体改动。

写法同样重要。不要写“支持客户集成 API”，而要写成一条链：客户遇到了什么问题，你负责哪一部分直到上线，同时跟进了多少个客户，又把什么带回给了产品团队。

如果你还没有这样的经历，成本最低的办法是自己当一回集成方。挑一个有公开沙箱的 API，搭一个小流程，记下每一个不得不靠猜的地方，再把这份清单整理成对文档和 API 的修改建议。这是最接近卖 API 的公司里 FDE 日常工作的练习。

一份好的 OpenAPI 规范是一个答案。这份 FDE 招聘启事指向了第二个答案：在客户的问题和这份规范之间站一个人，让规范随着时间推移，迫使客户去猜的地方越来越少。
