为什么在部署 Agent 小队之前你需要 Agentic 上下文工程

原标题：Why You Need Agentic Context Engineering Before Deploying Agent Squads

Monterail · 2026-07-15 · 约 9 分钟读完

摘要

Monterail 这篇文章认为，AI Agent 团队失败的原因通常不是模型能力，而是代码库、文档和内部规范只为人类阅读而设计。文章提出 Agentic Context Engineering（ACE）：把 API 契约、服务边界、所有权等结构化信息做成机器可读、持续维护的上下文层，并区分它与语义检索（RAG）的不同，给出代码库就绪度自查清单、维护成本与实施约束，强调 FDE 在前期梳理隐性知识中的关键作用。

要点

  • Agent 失败多因代码库未按机器可读结构设计，而非模型问题。
  • 结构化上下文与语义检索解决不同问题，不能互相替代。
  • 过期的上下文层比没有更危险，会误导 Agent 产出错误代码。
  • 上下文层是需持续维护的工程交付物，不是一次性配置。
  • FDE 负责梳理隐性知识、划定服务边界，难以完全自动化。

新的默认标准。您构建智能、快速且可持续的 AI 软件的中心

Agentic 上下文工程是指将代码库、其文档和策略重构为机器可读的层，让 AI Agent 能够自主处理，而无需人工在中间翻译。这是我们在之前一篇文章中所提观点背后缺失的一环：agentic delivery 的吞吐量承诺在 Agent 遇到未记录的 API 边界或含糊的数据模型时就会崩塌。如今 AI Agent 可以在没有人工参与的情况下发现 bug、编写规格说明、运行测试套件并创建 pull request。但如果底层的代码库从未为机器阅读而构建，这一切都无从谈起。

执行摘要 当 Agent 团队失败时，底层模型很少是问题所在。真正的问题通常是代码库、文档和内部策略是为人类入职培训而非自主执行而构建的。Agentic 上下文工程（ACE）将这一差距视为需要自身维护计划的基础设施：它用结构化的、动态的上下文取代静态提示词，使 Agent 能够保留有效的做法、摒弃无效的做法，并依据明确的契约行事而非凭空猜测。跳过这一步，Agent 就会基于无人核实的假设编写看似合理的代码。投资于此，Agent 就可以在夜间无人监督地运行，无需有人随时待命来拦截糟糕的合并。本文将介绍其机制、使其落地的 workflow 模式，以及决定它能否在生产环境中站得住脚的约束条件。

为什么 AI 编程 Agent 在为人类构建的代码库上会失败

大多数生产代码库依赖部落知识运转：Slack 讨论串、入职培训电话，以及在文档枯竭时询问资历最深的同事。这对新员工来说没问题，他们可以追问。但对 Agent 来说就行不通了，它无法区分过时的注释和关键的约束。这种模式是可以预见的：一个未记录的 API 边界导致 Agent 误读意图，Agent 要么停滞要么猜测，而猜测出的实现会在一夜之间发布一个破坏下游服务的变更，且无人清醒地发现它。

对 AI 生成代码的研究发现，当模型在缺乏对周围系统的结构性理解时工作，缺陷率会更高。在 How Defective Commented-out Code Augment Defects in AI-Assisted Code Generation 中，分析 GitHub Copilot 的研究人员发现，更稀疏的上下文（例如被空行包围的代码）与更高的缺陷率相关。

关于长上下文模型的另一项独立研究指出了一个相关但不同的问题：上下文腐化（context rot），即当越来越多、且相关性越来越低的材料被塞进本已十分宽裕的上下文窗口时，准确率会随之下降。这一区分很重要。更大的上下文窗口无法修复一个从未为机器阅读而设计的代码库，它只是让 Agent 在到达真正重要的部分之前，有更多无关文本需要费力翻阅。

为什么标准提示词对 Agent 失效

在非结构化代码库上运行的 Agent 团队往往以以下几种相同的方式失败：

  • 上下文坍缩。反复将长指令压缩成短指令，会剥离掉 Agent 下次遇到相同边缘情况时所需的领域特定细节和故障排查信息。
  • 无状态性。 缺乏持久化层时，一个上周解决了棘手迁移问题的 Agent，本周对它毫无记忆，只会重复同样失败的方案。
  • 上下文污染。 向 Agent 输入原始检索转储或无限制的内存日志会使其不堪重负，增加它调用错误工具或幻觉出不存在的函数的概率。

机制：Agentic 上下文工程如何运作

这是结构性工作，关乎形式而非措辞。机器可读的模式（schema）、OpenAPI 规范、JSON Schema 定义和架构决策记录（Architecture Decision Records）需要成为工具能够实际操作的真正产物，而不是被归档为可有可无的文档。模块化同样重要：一个 10,000 行的单体代码库会让 Agent 晕头转向，就像它会让新员工晕头转向一样，而模块化的代码库则能让工具只传入相关的代码片段。确定性的配置、锁文件（lockfile）和稳定的 JSON 序列化意味着系统可以缓存结果，而不必让 Agent 在每次调用时重新推导状态。严格的类型系统，无论是 TypeScript、Python 类型提示还是 Rust，都起到同样的作用：Agent 可以直接解析它，而不必猜测意图。

收益体现在三个方面：相比非结构化基线有更好的性能表现，Agent 能够在无需频繁确认的情况下承担更多多步骤任务，以及更低的 token 成本和延迟，因为 Agent 不必在每次调用时重新阅读臃肿的上下文。

这一切若没有良好的工具支撑都无法实现。Agent 调用的函数需要清晰的 docstring 和带类型的参数，就像任何内部 API 一样。错误信息需要可操作，而不是一个光秃秃的堆栈跟踪：“错误：未找到用户 ID。您是想找 active_users 吗？”这样的信息能让 Agent 有所行动，而原始堆栈跟踪永远做不到。这与Agentic DevOps 在 CI/CD 层遇到的信号可读性问题是同一回事：只有当信号本身结构化到足以解析时，Agent 才能对失败的测试或日志事件采取行动。安全与合规规则应作为 Agent 实际上无法绕过的约束置于运行时中，而不是躺在没人打开的 wiki 页面上。一份持续更新的 SPEC.md 或 PRD，配合一个只读的“计划模式”（Agent 在实施变更前先在其中规划方案），能让意图与执行保持关联。

结构化上下文与语义检索

这两者经常被混淆，因此有必要精确说明它究竟取代了什么。检索增强生成和向量搜索检索的是与查询读起来相似的文本。Agentic 上下文工程检索的是结构化关系：哪些服务调用哪些函数、谁负责哪个边界、哪份契约是权威的。这种差异恰恰在最关键的地方显现：在涉及某个函数调用方的变更中。

为什么标准向量搜索还不够

语义相似度搜索检索的是读起来相似的文本，而不是结构上相关的代码。一个函数和它的五个调用方之间可能几乎没有共同的词汇，因此向量索引没有理由把它们归为一组。举一个具体的失败案例：一个 Agent 修改了某个函数的签名；向量搜索层从未暴露出另一个模块中的三个调用点；本地测试通过；而故障只在生产环境中显现。这就是为什么上下文工程是一门不同于“更好的 RAG”的独立学科：它解决的是一个语义搜索从未被设计去解决的结构性问题。

Agent 就绪度审计清单

在给 Agent 团队分配实际工作之前，技术领导者需要一个具体的方法来评估他们的代码库是否已经就绪。Agent 就绪度与更广泛的组织 AI 就绪度问题并列，后者包括数据、治理和人才，但下面的清单聚焦于在代码库层面最重要的信号。以下清单提供了一份快速、诚实的自评，涵盖最关键的那些信号。

如何保持上下文同步：陈旧性问题

每位读到这份清单的技术领导者最终都会问同一个后续问题：建成之后由谁来维护？一个与实际代码脱节的上下文层比没有上下文层更糟，因为 Agent 会信任它。一份过时的 ADR 或陈旧的 OpenAPI 规范不仅仅是帮不上忙。它会主动误导 Agent，使其产出与错误契约在内部保持一致的代码。这就是为什么上下文工程从第一天起就会产生持续的维护成本，而不是一次性搭建费用。

Agentic 上下文工程的实施约束有哪些？

遗留单体系统需要先进行一次初始分解，才有可能进行智能体上下文工程。你无法在一个尚不存在服务边界的代码库上叠加机器可读的契约。受 GDPR、HIPAA 或 PSD2 约束的重合规环境，需要把过去写在审查清单里的策略重写为可执行的模式级约束，由智能体自动执行，而不是由人在事后检查。可扩展性往往与服务数量而非代码库的原始规模相关：一个五服务系统所需的技术投入可能远少于一个五十微服务系统，因为每增加一个服务边界，就多了一个需要建模并保持更新的契约。

前沿部署工程师：开路先锋

前沿部署工程师（通常简称 FDE）负责在智能体团队对接真实代码库之前完成那些不起眼的基础工作：阅读没有文档的端点，访谈那些独占部落知识的工程师，弄清服务边界实际所在的位置与人们假设的位置之间的差异。这个角色决定了智能体上下文工程是停留在幻灯片上的概念，还是生产环境中可运行的系统。在实践中，这意味着梳理未文档化的 API 参数，通过直接访谈挖掘部落知识，并在任何智能体接触代码库之前起草第一版安全护栏。其中部分工作无法完全自动化，因为必须有人来判断“足够模块化”对于一个拥有自身历史和约束的特定系统究竟意味着什么。

实施 ACE 的最佳实践是什么

在做得好的团队中，有几项实践反复出现。增量压缩让智能体定期压缩自己的历史草稿区，在不丢失重要经验的前提下释放 token 空间。子智能体架构（有时称为集群）将复杂问题拆分为范围严格限定的角色，比如由一个审查智能体监督一个写作智能体，从而保持每个上下文边界的整洁。持续上下文验证将上下文层本身视为代码：编写测试和护栏，在检索或操作中的幻觉进入合并之前将其捕获。

核心要点

  • 智能体团队失败的最常见原因是代码库从未为机器解析而进行结构化设计，而不是底层模型能力不足。
  • 上下文腐化不同于上下文缺失；即使技术上没有任何内容缺失，用无关文件塞满大窗口也会降低准确性。
  • 结构性上下文（所有权边界、API 契约、服务依赖）解决的是与语义检索不同的问题，不应被视为语义检索的替代品。
  • 过时的上下文层比没有上下文层更危险，因为智能体会信任它，并产出内部一致但错误的代码。
  • 前沿部署工程师仍然不可或缺，因为关于服务边界和系统特定的“足够模块化”阈值的判断难以完全自动化。

上下文工程是一次性设置还是持续进行的过程？

智能体交付的效果取决于其底层的上下文层，而这一层是一个拥有自身生命周期的工程交付物，而不是在智能体到来之前临时附加的一次性任务。真正从智能体团队中获得价值的组织，会像对待生产基础设施一样对待上下文工程：明确归属、经过测试，并按计划维护。编写高质量代码依然重要，而设计 AI 能够直接使用的代码库正成为同等重要的技能。如果您想评估自己的代码库现状，Monterail 的 AI 开发团队可以帮助您规划智能体就绪系统实际所需的拆分与治理工作。
