MVP（Minimum Viable Product）直译为日语是“实用最小限度的产品”。这里的关键在于“Minimum（最小限度）”与“Viable（具备实用价值）”两者的兼顾。

它并非单纯的“未完成品”或“无法运行的试制品”，而是指具备能够解决特定用户课题的最小功能、且实际可在市场上进行测试状态的产品。

MVP开发是指有意图、有计划地构建这一MVP，并快速循环“市场投放→收集反馈→改进”的开发方法。

术语正式名称含义
MVPMinimum Viable Product实用最小限度的产品
MVP开发—运用MVP进行假设验证的开发方法
精益创业—以MVP为核心概念的业务开发方法论

MVP开发这一概念起源于2011年埃里克·莱斯在其著作《精益创业》中提出的方法论。精益创业是将丰田“精益生产方式”的思想应用于软件开发和业务开发，其核心概念是高速循环“构建（Build）→衡量（Measure）→学习（Learn）”的BML（Build-Measure-Learn）循环。关于高速运转BML循环的具体设计方法，我们在【实战指南】精益开发与MVP｜最快运转假设验证的设计与方法中进行了讲解。

在这一BML循环中，最初的“构建”阶段所打造的就是MVP。它并非完整的产品，而是聚焦于能够验证最重要假设的最小功能，从而无需投入多余的开发工时，就能快速发现“市场真正需要的东西”。

在精益创业出现之前的瀑布式开发中，通常的做法是花费数月至数年打造“完成品”后再发布，此时才首次确认市场反应。采用这种方法，即使发现与用户需求的偏差，修正也需要巨大的成本和时间。MVP开发作为从根本上解决这一问题的方法，迅速得到普及。

MVP开发如今之所以备受关注，背后有以下3个结构性变化。

① 市场变化速度加快

随着数字化的发展，竞争对手已能在短时间内发布类似产品。在花费长时间打造完美产品的过程中，被竞争对手抢占先发利益的风险日益增大。率先进入市场并不断学习，已成为竞争优势的源泉。

② 云与SaaS的普及降低了原型的门槛

AWS、GCP等云基础设施，Stripe、Twilio等API，以及NoCode工具的出现，使得过去工程师团队需要数周构建的功能，如今在数天内即可实现。

③ 生成AI的出现使MVP开发的成本与速度发生剧变

将ChatGPT、Gemini、Claude等生成AI融入MVP开发，据报告有的案例可将开发工时较以往削减30%至50%。此外，将AI本身作为MVP核心功能的“AI原生MVP”这一类别正在迅速扩大，这也使MVP开发再次成为关注焦点。

实施MVP开发的目的，大致可归纳为以下3点。

① 假设验证（探索 Product-Market Fit）

商业上最大的风险是“做出了没人想要的东西”。在MVP开发中，“这类用户应该存在这一课题”“这个功能应该能解决它”等假设，将通过真实用户的行为数据进行验证。若假设不成立，可以转向（Pivot）；若找到正确假设，则可以进行规模化扩张。

② 开发成本的最小化

与先开发完整功能再发布的传统开发方式相比，MVP开发通过省去不必要的功能开发来将成本降至最低。有创业公司调查显示，产品开发成本的60～80%花费在“用户实际不会使用的功能”上，而MVP开发能从根本上削减这种浪费。

③ 确保先发优势

比竞争对手更早进入市场，率先获得品牌认知、用户数据和经验积累，也是重要目的。尤其是在利基市场中，早期进入带来的口碑传播和社区建设，会成为后来者难以追赶的进入壁垒。

优点内容具体效果
降低开发风险以少量投资验证商业假设将失败成本降至最低
加快市场进入速度通过精简功能缩短发布周期以数周至数月为单位投入市场
早期把握用户需求从真实的用户行为数据中学习基于事实而非假设进行决策
对投资人和利益相关方更具说服力用可运行的产品证明价值降低追加融资和内部审批的门槛

MVP开发并非万能。在充分理解的基础上加以运用非常重要。

缺点① 对品牌形象的影响风险

由于以最少的功能和质量发布，早期用户可能会获得负面体验。尤其是面向BtoC的消费者服务，第一印象容易以口碑和评价的形式留存下来，可能妨碍后续的改进。

→ 对策：从封闭β测试或基于访谈的验证开始，在确保一定质量后再进行公开发布。

缺点② “最小限度”的定义容易变得模糊

如果团队内部对“Minimum”的理解各不相同，结果就会不断添加不必要的功能，导致MVP不再是MVP的“功能蔓延（Feature Creep）”。

→ 对策：将需要验证的假设收敛到1～2个，并事先创建“功能范围定义书”，仅列出与之直接相关的功能。

缺点③ 技术债务的累积

如果为了“尽快推出”而用粗糙的代码实现，在后续的功能扩展和规模化时，技术债务可能会显现为问题。

→ 对策：从MVP阶段起就进行着眼于未来扩展的架构设计，并对核心领域设定一定的代码质量标准。

这3个术语容易被混淆，但它们的目的、对象和完成度各不相同。准确理解它们，才能在项目的各个阶段选择合适的方法。

PoC（Proof of Concept：概念验证）是为了确认“技术上是否可行”而进行的验证。它不以交付给用户为前提，而是工程师或研究人员为内部确认而制作的。PoC的优缺点及成功要点，在什么是PoC？优缺点及3个成功要点详解中有详细讲解。

例如，针对“能否用AI对我们公司生产线的数据进行异常检测？”这一问题实施PoC时，会实际构建机器学习模型并测量精度，但无需将其做成外部用户可用的UI。它始终只是确认“技术是否成立”的阶段。

与MVP的最大区别在于，PoC的目的是技术验证，不以向用户提供价值为前提。而MVP的目的是验证商业假设，必须是真实用户能感受到价值的最小限度产品。

原型（Prototype）是“用于确认产品的形态、动作和UX的试制品”。主要用于设计和UI的验证，不需要实际运行数据，主要目的是再现外观和操作感。

用Figma制作的UI原型，或用于确认硬件外观的3D打印模型等，都是典型例子。

与MVP的最大区别在于，原型的目的是“确认动作印象”，并不设想真实用户会在生产环境中使用。而MVP则由真实用户实际使用，并根据其行为数据验证商业假设。

敏捷开发是通过重复短周期迭代（Sprint）来推进开发的“流程方法论”。它与MVP开发的目的不同，但两者契合度非常高，多数情况下会搭配使用。

敏捷开发 = 开发的流程与推进方式（短期迭代） MVP开发 = 做什么、从哪里起步的战略（最小假设验证）

MVP开发发布后，一边接收反馈一边用敏捷方式反复改进，是最常见的组合模式。

这是最常见的MVP方法，发布仅实现核心功能的可运行试制品。UI可以粗糙，但需实现用户实际可用的功能。

特点

  • 可验证实际的操作感与UX
  • 可同时确认技术上的可行性
  • 容易获得来自用户的具体反馈

代表性成功案例：Dropbox Dropbox 在开发初期 MVP 时，在实际构建文件同步系统之前，先发布了一段 3 分钟的演示视频，展示“文件自动同步的过程”（与后述的演示视频型 MVP 相结合）。随后发布了搭载实际同步功能的原型 MVP，首日就获得了数千名 Beta 用户。这一阶段仅支持 Mac 系统，共享功能也很有限，但对于验证“解决文件同步问题”这一核心假设来说已经足够。

这是一种完全不使用数字系统或自动化，由人工手动提供服务来验证“需求是否存在”的方法。对用户来说看起来像正常的服务，而后台则由人工来处理。

  • 开发成本几乎为零
  • 能够直接听取用户真正想要的东西
  • 在自动化之前能够深入理解业务流程

代表性成功案例：Food on the Table 这是一项为用户提供每周菜谱和所需食材清单的服务。创始人最初不使用任何技术手段，每周为 1 位用户手动构思菜谱，查看超市传单后制作清单，以礼宾式方式提供服务。通过这种手动验证深入理解了用户需求，之后才推进系统化。

这是一种在实际产品开发之前，仅创建落地页并投放广告，来衡量用户反应（点击率、注册率）的方法。能够以最快、最便宜的方式验证“需求是否存在”这一最基本的假设。

  • 几乎不需要开发工时（仅需制作落地页）
  • 能够以数值定量地衡量需求
  • 能够对目标受众、宣传语、价格区间等多种模式进行 A/B 测试

验证流程

  • 创建包含临时服务名称、宣传语和价值的落地页
  • 通过 Google 广告或社交媒体广告触达目标用户
  • 衡量“预注册”“加入等待名单”等 CTA 的点击率和注册率
  • 确认存在一定需求后进入开发阶段（或修改宣传语后重新测试）

这是一种表面上看起来系统在自动运行，实际上背后由人工手动操作和判断的方法。名称来源于电影《绿野仙踪》，取自幕后藏着真正操作者的那一幕。

  • 在实现 AI 或复杂算法之前就能验证需求
  • 在完整还原用户体验的同时，将开发成本降到最低
  • 通过探索“人工介入的空间”，明确自动化的优先级

代表性成功案例：Zappos 如今作为全球最大规模的在线鞋类电商而闻名的 Zappos，在创业初期并没有实际库存。用户下单后，创始人会到附近的鞋店实际购买并发货，完全依靠手动运营。通过这种绿野仙踪式 MVP，验证了“在网上买鞋”这一行为确实会发生，之后才构建了正式的电商系统。

这是一种不从零开始自行开发系统，而是组合现有的 SaaS 工具和 API 来构建服务的方法。通过利用 Airtable、Notion、Zapier、Slack 等工具，几乎无需开发成本就能验证服务的“机制”。

  • 开发工时最少（很多情况下可以用无代码、低代码实现）
  • 能够利用现有工具的可靠性和稳定性
  • 能够专注于产品核心价值的验证

应用示例

  • 预约管理：用 Calendly 接受预约，用 Notion 管理数据
  • 电商：Shopify 与 Stripe 组合的支付
  • 内部工具：用 Airtable 搭建数据库，用 Zapier 实现自动化，用 Slack 发送通知

这是一种在实际产品尚不存在时，制作展示“产品运行状态”的演示视频来验证需求的方法。视觉吸引力强，能在短时间内收集到目标用户的反应。

代表性成功案例：Dropbox（重述） 如前所述，Dropbox 发布了一段 3 分钟的简单屏幕录制视频。视频演示了“计划实现的功能”，并引导用户前往预注册表单，发布后不久等待名单注册人数就达到了 75,000 人。这成为了实际开发投资决策的依据。

选择合适 MVP 方法的判断标准如下。

想要验证的假设推荐方法
想确认“是否存在需求”烟雾测试 / 演示视频型
想确认“UX 是否有效”原型型
想确认“用户是否真的会使用（行为）”礼宾型 / 绿野仙踪型

想确认“AI 能否替代判断”绿野仙踪型 → 原型型

2023 年以来生成式 AI（LLM）的迅速普及，正在从根本上改变 MVP 开发的方式。特别是以下 3 个要点，被开发者们视为开发一线的真实体会。

① 开发速度大幅提升

通过使用 GitHub Copilot、Cursor 等 AI 编程助手，可以大幅减少编写常规代码的时间。尤其在 CRUD API 实现、测试代码自动生成、文档生成等方面效果显著。一名工程师将以前需要 2 周的初始实现缩短到 1 周以内完成的案例也并不罕见。

② “人工验证”阶段可以用 AI 替代

传统的礼宾型、绿野仙踪型 MVP 以“人工手动运营”为前提。但通过利用生成式 AI，需要自然语言处理的业务（文档摘要、推荐、问答应答等）可以由 AI 承担，几乎在自动化的状态下提供服务。由此，可以在远超人工验证的成本和极限的规模上进行假设验证。

③ AI 本身成为核心功能（AI 原生 MVP）

越来越多的产品不再是“用生成式 AI 来优化现有系统”，而是“AI 的推理能力本身就是服务价值的核心”。这就是所谓的“AI 原生 MVP”领域，典型例子包括：利用 ChatGPT API 或 Anthropic API 的自然语言界面、使用 RAG（检索增强生成）的文档检索，以及基于图像生成 AI 的创意辅助工具等。

模式① 活用 ChatGPT API：自然语言界面 MVP

用户以文本形式输入问题或指令，AI 进行相应的回答或处理。在 MVP 阶段，仅通过提示词工程与 API 的组合即可实现，因此几乎无需编写复杂的后端逻辑，就能做出“可运行的产品”。

具体示例：

  • 法律文书 AI 摘要工具（面向律师事务所的 SaaS）
  • 客户支持一线应答聊天机器人
  • 招聘材料筛选自动化工具

模式② 使用 RAG（检索增强生成）的文档检索 MVP

将企业内部文档（手册、会议纪要、规章制度等）存入向量数据库，AI 在回答用户问题时检索并参考相关文档。使用 LangChain 或 LlamaIndex 等框架，MVP 阶段的实现大约只需几天到一周时间。

  • 公司内部规章与 FAQ 的 AI 检索系统
  • 产品手册 AI 支持台
  • 从历史提案书、合同中提取信息的工具

模式③ 活用图像生成 AI：创意辅助 MVP

集成 Stable Diffusion 或 DALL-E 等 API，提供根据用户输入文本生成图像的功能。其优势在于即使没有设计师也能生成视觉内容，在广告、电商、出版领域的需求正不断增长。

  • 面向电商网站的商品图像自动生成工具
  • 社交媒体发帖用横幅自动生成服务
  • 建筑、室内设计的透视图自动生成工具

模式④ 活用多模态 AI：图像、语音输入 MVP

不仅处理文本，还能以图像或语音作为输入由 AI 处理的产品。通过活用 GPT-4 Vision 或 Gemini Pro 等多模态模型，可以实现“只需拍照即可诊断、分析”的 UX。

  • 制造业：只需拍摄设备照片即可检测故障的 AI 巡检工具
  • 餐饮业：根据食材照片推荐菜谱的厨师助手
  • 医疗：根据皮肤照片提示皮肤科就诊优先级的筛查工具（在医生监督下）

案例① Notion AI（Notion）

Notion 于 2023 年初以 MVP 形式 limited 公开了 AI 写作助手功能。他们采用面向现有用户的候补名单（waitlist）方式逐步推广，在收集反馈的同时扩充功能。以 AI 文章生成、摘要、翻译功能为核心的 MVP 获得好评，并由此推动了后续的正式发布。

案例② Cursor（AI 代码编辑器）

基于 VS Code 的编辑器，由 AI 提供代码自动补全、重构、Bug 修复建议。最初的 MVP 只有简单的代码补全功能，在确认了工程师的强烈需求后才扩充功能。如今它已作为一款可以与 AI 进行“结对编程”式开发的工具而快速增长。

案例③ 国内 SaaS 案例：AI 合同审查服务

在国内 LegalTech 领域，出现了多款利用 ChatGPT API 的合同审查 SaaS。初期 MVP 的构成非常简单：“上传 PDF → GPT 解析条款 → 高亮风险点”，但直击法务人员的痛点，在 β 版阶段就获得了大量企业客户的付费合同。

利用生成式 AI 进行 MVP 开发，有一些特有的注意事项。

风险内容对策
幻觉AI 生成错误信息实现输出验证逻辑、设置人工审核流程
API 成本膨胀随着用户增加，API 成本急剧上升尽早设计 Token 数优化与缓存策略
提示词注入恶意用户操纵提示词实施输入清洗、保护系统提示词
依赖风险依赖特定 API 提供商考虑多模型支持设计以及向替代 API 切换的设计
数据隐私将用户数据发送至 API 需获得同意妥善完善服务条款与隐私政策

MVP 开发的第一步，是将“想要验证什么”聚焦到 1～2 个问题上。如果这一阶段敷衍了事，将成为后续所有环节偏离方向的原因。

建议将假设以如下形式写成文字。

“[目标用户] 由于存在 [课题或情境]，通过提供 [解决方案]，应当能够实现 [行为或成果]。”

例如：“中小企业的法务负责人因合同审查耗时过长而困扰，通过提供 AI 合同审查工具，应当能够将审查时间缩短 50%。”

针对该假设，重要的是定量地定义“哪些指标发生变化才能说假设得到了证明”。

假设确定后，为验证该假设，将功能划分为“绝对必需的功能”和“没有也能完成验证的功能”。

功能分类标准（MoSCoW 法）

分类含义MVP 阶段的处理
Must Have假设验证必不可少的功能必须实现
Should Have有则更好但并非必需排除在范围之外
Could Have有余力时希望实现排除在范围之外
Won’t Have本版本不需要明确排除

基于所选方法（上一章的6种方法）构建MVP。这一阶段的重要原则是“不追求完美”。

构建MVP时的检查清单

  • 核心功能是否实际可用
  • 用户能否独立完成操作
  • 是否没有严重的Bug和安全风险
  • 是否内置了数据收集与统计的机制（Google Analytics、Mixpanel等）
  • 是否设计了收集反馈的路径

MVP发布之后，“衡量”和“学习”是最重要的阶段。不是凭感觉判断，而是基于数据决定下一步行动。

MVP阶段应衡量的主要指标

指标内容衡量工具示例
激活率用户首次使用核心功能的比例Mixpanel、Amplitude
留存率一定时间后回访用户的比例Mixpanel、Amplitude
NPS（净推荐值）用0～10分评价“是否愿意推荐给朋友”Typeform、Delighted
转化率免费→付费等的转化率Stripe、自有数据库
流失率停止使用服务的用户比例Chartmogul

在收集定量数据的同时，通过用户访谈收集定性数据也很重要。因为数字中看不到的“为什么会这样行动”的原因，往往成为下一次改进的核心。

根据收集到的数据，判断是“继续改进（迭代）”、“改变方向（转型）”，还是“转入正式的开发与营销（规模化）”。

进入规模化阶段的判断标准参考

  • 留存率超过一定水平（B2C的话，周留存率超过20%是一个参考标准）
  • 核心功能的NPS达到40以上
  • 已从多个用户那里获得“即使付费也想使用”的反馈
  • 单位经济模型（LTV/CAC）有望成立

失败模式①：轻视“M”而过分重视“V”

本应彻底贯彻“Minimum（最小化）”，却不断添加功能，最终变成“全功能版产品”的模式。锁定开发范围，并定期重新审视“这个功能真的对假设验证有必要吗？”非常重要。

失败模式②：不验证假设而反复改进

不断回应用户“希望更多地○○”的要求，导致“回应客户的话”取代假设验证成为目的的模式。重要的是用数据为所有改进需求排定优先级，优先处理与核心假设直接相关的需求。

失败模式③：把衡量机制放到最后

优先“尽快发布”而把分析工具的配置放到最后，结果发布后无法获取数据，只能凭“感觉”做决策的模式。应在发布前将Google Analytics和Mixpanel的实现作为必备要求。

理解MVP开发并实际拥有新业务或产品上线经验的工程师和PM，在当前自由职业市场中评价明显较高。其原因主要有3点。

① 兼具“构建能力”和“思考能力”的人才仍然很少

通常的系统开发项目要求“按需求实现”的技能，而MVP开发则需要“从假设出发思考应该做什么，并以最快速度推向市场”这种伴随商业决策的能力。这种“能够连接BizDev与Engineering的人才”长期短缺，因此单价容易偏高。

② 来自初创企业和新业务部门的需求旺盛

大企业的新业务部门、推进DX的中型企业、获得VC支持的初创企业等，MVP开发的需求正从多方面增长。这些客户强烈寻求“有0→1阶段上线经验的人”，对有经验者的单价优待十分明确。

③ 与生成式AI应用技能相结合，稀缺性更高

除了MVP开发经验之外，拥有ChatGPT API、LangChain等生成式AI应用技能的工程师，能够在“AI原生MVP开发”这一新领域建立先发优势。该领域的项目持续增加，2025至2026年间对有经验者的邀约急剧增多。

自由职业工程师的月平均单价，截至2025年12月为78.3万日元（En Japan“Freelance Start”调查）。如果具备MVP开发、AI开发的专业能力，存在大量远超这一平均水平的项目。

全栈工程师（有MVP经验）从需求定义到实现、部署全程负责80～120万日元
AI/LLM工程师（RAG、API集成）生成式AI功能的设计与实现90～130万日元

要在MVP开发和AI开发项目中以自由职业者身份实现高单价，技能组合与成果展示方式非常重要。请参考以下策略。

① 在作品集中明确展示MVP的“假设验证过程”

不是简单地说“开发了○○”，而是能够说明“基于什么假设、选择了什么最小功能、构建了怎样的反馈循环”这一过程的作品集，会大幅提升客户的评价。因为这不仅能体现作为工程师的实现能力，还能传达从业务视角出发的思考能力。

② 积累生成式 AI 应用的实际落地经验

请通过个人项目或参与 OSS 贡献，积累使用 ChatGPT API 和 Anthropic Claude API 进行产品实现的经验。如果具备 RAG 架构的实现经验、LangChain/LlamaIndex 的应用能力以及提示词工程方面的知识，可选的项目范围将大大拓宽。

③ 与初创公司和新事业部建立联系

MVP 和 AI 项目大多由初创公司或大企业的新事业部发包。参加初创公司聚集的社区（技术学习会、Slack 社区、VC 主办的活动等）并建立联系，是获取项目的捷径。此外，如果利用自由职业中介机构，选择承接较多 MVP 开发和 AI 开发项目的中介机构非常重要。

④ 以“能独立从零上线 MVP”作为武器

在初创公司和新事业启动的第一线，对“能够独立完成从需求定义到基础设施搭建、前端实现直至部署的工程师”的需求非常高。将全栈实现能力与 AI 应用知识相结合，可以确立“一人 MVP 开发者”这一稀缺定位。

本文从 MVP 开发的基本定义，到与 PoC、原型的区别、6 种开发方法、运用生成式 AI 的最新案例，以及实际的推进步骤，进行了系统性讲解。

在此再次梳理要点。

  • MVP（Minimum Viable Product） 即“实用最小可行产品”，是以最快速度、最小成本验证商业假设的战略性方法。
  • 理解 PoC 用于技术验证、原型用于 UX 确认、MVP 用于市场验证 的角色差异，并根据阶段选择合适的方法非常重要。
  • 6 种 MVP 方法（原型型、人工代劳型、冒烟测试、绿野仙踪型、拼凑型、演示视频型）需根据想要验证的假设分别选用。
  • 生成式 AI 的出现使 MVP 的开发速度和成本效率得到极大提升，以 AI 本身作为核心功能的“AI 原生 MVP”这一全新领域正在迅速扩大。
  • 能够从事 MVP 开发和 AI 开发的工程师与 PM，在自由职业市场中处于更容易获得高单价项目的有利位置。

MVP 开发的技能不仅仅是掌握一种开发方法，更是构成“从零打造事业的能力”的核心。这种将技术实力与商业思维相结合的技能组合，无论对正式员工还是自由职业者而言，都可以说是未来工程师与 PM 所需市场价值的核心。
