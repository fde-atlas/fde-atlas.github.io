Oliva · 产品与售后支持助手

原标题：Oliva · Product and after-sales support assistant

AIelsen Agent Field Notes · 约 12 分钟读完

摘要

本文介绍 Oliva 为跨境电商售后团队构建的 AI 客服知识工作站：Agent 从手册、政策表中检索证据并起草回复，客服人员在既有工作区审核后决定是否发送，确认的修改经去重和限流后沉淀为知识库更新。文章记录了表格检索补全、回复策略调整、内部校验信息外泄修复等决策过程，并给出试点评估指标与从小范围高频问题起步的建议。

要点

  • Oliva 构建客服知识工作站，Agent 检索证据并起草回复，人工审核后发送
  • 修复表格检索盲区，解决规格答案不准确与版本冲突问题
  • 按事实完整度区分直接回答、条件说明和待确认项，避免编造服务承诺
  • 知识更新加入去重、限流和预览检查，防止重复内容拖慢系统
  • 建议从单一产品的高频问题试点，用起草耗时和错误率评估效果

支持产品、发货和售后咨询建议回复附带证据；由员工审核后发送经审核的修改意见持续用于知识维护

让工作站处理重复的检索和起草工作，使客服人员能够专注于客户的具体情况、事实和服务承诺。类似的咨询可以采用一致的指引，经审核的修改意见也能为下一次回复提供参考。

01 / 任务背景

陷入停滞。

产品知识分散在手册、文档和表格中。支持人员在回答有关规格、配送和售后服务的常见问题时，必须查找信息并核对不同的答案。当案件转交他人时，客户还可能被再次询问他们已经提供过的细节。

同一规格可能同时出现在手册表格、产品文档和早先的回复中。找到不同版本的支持人员可能给出不同的答案。更多的培训仍然无法消除每次查找和核对信息的需求。

质量审查发现了错误的规格、虚构的服务承诺，以及向客户索要他们已经提供过的订单详情。支持人员需要一份能推动咨询进展的草稿，并清楚标明哪些事实尚未确认。

一个相关支持知识项目的事故复盘发现，已结束活动的措辞仍然出现在购买咨询中。如果不将活动期与履约期区分开，旧材料可能造成已不再适用的购买或服务预期。

有用的修正值得保留，但直接导入每一条反馈会造成重复和冲突。知识的增长拖慢了服务速度。因此更新需要审核、去重和容量控制。

  • 决策

  • 增加了对表格及相关材料的检索覆盖，解决了内容冲突并调整了检索组件，然后用类似的规格问题对答案和来源进行了核查。
  • 输出
  • 一个能够检索关键表格的知识库，以及规格核查结果。
  • 交接
  • 有了可核实的事实，工作人员便可以判断如何措辞回答，以及哪些条件仍需确认。

回复草稿和待确认事项，供工作人员审核。

  • 输入
  • 检索到的材料、原始客户问题以及来自多批次回复的质量反馈。
  • 决策
  • 有依据的信息可以直接解释。确切的数字、服务政策和处理时长不能凭猜测，客户已提供的信息也不应再次询问。
  • 行动
  • 区分了已确认的事实、需要说明的条件和缺失的信息；增加了场景和角色规则；并核查了规格、服务承诺和现有订单信息的使用。
  • 输出
  • 回复草稿和待确认事项，供工作人员审核。
  • 交接
  • 使用真实的客户措辞来检验草稿是否回答了问题，同时避免过度谨慎导致常规咨询无法推进。

一个从问题到草稿再到人工确认的协作流程。

  • 输入
  • 团队基于表格的工作流程，以及他们在阅读、编辑和发送回复方面的实际习惯。
  • 决策
  • 工作人员需要在他们处理咨询的地方看到草稿和支持信息，并保留他们的审核决策记录。
  • 行动
  • 集成了现有工作区，展示建议回复和核查信息，并记录批准、修改或拒绝。确认内容后，工作人员决定是否通过其惯常流程发送。
  • 输出
  • 一个从问题到草稿再到人工确认的协作流程。
  • 交接
  • 批准或修改后的内容成为知识更新的候选。被拒绝的内容保留为问题记录，而不是直接成为标准答案。

一个受控的 FAQ 更新流程和清理工具。

  • 输入
  • 工作人员确认的修正内容，以及反馈导入带来的重复内容和运营压力。
  • 决策
  • 审核经验值得保留，但反复导入会使知识更难检索，并可能干扰持续使用。
  • 行动
  • 清理了冗余内容，增加了去重、导入频率限制和预览检查，并保留了可审查的更新记录。
  • 输出
  • 一个受控的 FAQ 更新流程和清理工具。
  • 交接
  • 相似咨询可以复用有用的修正。新知识仍需检查版本、冲突和使用范围。

一台可分发的工位机、集成说明和操作材料。

  • 输入
  • 持续使用过程中遇到的连接、启动、工作区集成和多知识库需求。
  • 决策
  • 在工作日内接收草稿，与在演示中回答一个问题，交付标准截然不同。
  • 行动
  • 修复了连接和启动问题，增加了预热和缓存刷新流程，并记录了安装、桥接、多知识库配置和维护方法。
  • 输出
  • 一台可分发的工位机、集成说明和操作材料。
  • 交接
  • 持续用真实咨询核查事实、回复行为和运行状态，并将新发现的错误反馈到文档和规则中。

03 / 决策

与输出同等重要。

当草稿、来源或实际行为与预期不符时，Agent 如何定位问题并选择下一步？

  • 信号
  • 相似的产品规格问题反复得到不准确的回答。
  • 选择
  • 追溯答案对应的表格，补全索引并解决冲突的材料，然后用相同的问题再次核查。
  • 带来的改变
  • 修复解决了可验证的来源和检索问题，使员工能够回到正确的参考资料。
  • 信号
  • 严格的禁止推断规则导致许多常规咨询被搁置。放宽后又暴露出虚构的服务和重复索取信息的情况。
  • 选择
  • 根据事实的完整程度区分直接解释、条件解释和待确认事项，并将质量检查扩展到服务、操作、时间和政策。
  • 带来的改变
  • 员工收到了可以直接使用的草稿，并能专注于真正需要判断的条件。
  • 信号
  • 内部验证备注出现在了客户回复中。
  • 选择
  • 禁用了有问题的验证配置，并核查对外措辞及其与事实的一致性。
  • 带来的改变
  • 将客户回复中必要的信息与内部检查流程分开，减少了额外解释的需要和失去信任的风险。
  • 信号
  • 自动导入成倍增加了重复知识，影响了工位机持续服务支持人员的能力。
  • 选择
  • 保留了反馈流程，同时增加了去重、频率限制和导入前检查。
  • 带来的改变
  • 一次员工修正可以为后续的问询提供参考，并对知识维护和运营能力设置明确的控制。

需要修复的：意图、有效性和来源粒度

将实际措辞与检索到的来源进行核对。区分活动阶段知识与履约阶段知识，把已过期条目和缺失条件排除在当前承诺之外。

  • 01用户措辞口语化措辞未能命中相关意图，导致预期的检索策略没有运行。
  • 02候选材料一条 FAQ 混入了不同业务阶段的条目；文件级标签过于粗糙。
  • 03修复与复测扩展真实问题措辞的覆盖范围，检查旧条目的检索与排序，然后用同样的问题复测。
  • 04持续治理为单条知识条目附加有效期、适用阶段和来源类型，而不是把项目事实硬编码在共享代码中。

同样的问题、不同的策略、选中的来源以及答案的变化。

保留哪个基线、观察什么、推迟什么。

意图覆盖、条目有效性、索引结构与可追溯性。

根据相关知识工程工作中的策略评估和事故复盘整理而成。姓名、日期、原始问答及项目参数均已省略。这些摘录用于说明相关的工程判断，并未将整个项目的成果归功于某一位参与者。

07 / 可复用的工作

转化为可复用的方法。

跨境电商客服与客户运营团队，拥有大量产品信息、敏感的服务承诺，以及频繁的重复性或售后咨询。

  • 输入
  • 客户问题、已提供的信息以及当前源材料
  • 方法
  • 识别问题、查找证据，并整理已知内容和需要确认的内容
  • 输出
  • 一份客服人员可以核查的建议回复
  • 检查
  • 原始问题已得到回应，已提供的信息已被使用，承诺均有证据支持。
  • 输入
  • 原始问题、源材料及错误草稿
  • 方法
  • 按顺序检查源材料覆盖情况、适用条件、检索结果和事实性表述
  • 输出
  • 一份可审查的错误发生环节记录
  • 检查
  • 说明是哪一层出了问题，并用类似问题验证修正结果。
  • 输入
  • 经员工确认的修订内容
  • 方法
  • 检查重复与冲突，预览变更并控制导入
  • 输出
  • 一份可维护的客服 FAQ
  • 检查
  • 有用的修正会被复用；被拒绝的内容和重复条目不会直接进入标准答案。

一个务实的起点

从某一款产品的高频问题开始。在增加更多问题类型之前，先让员工在现有工作空间中检查草稿、证据以及所需的编辑量。
