前沿部署工程，第 7 部分：数天内完成原型，数周内投入生产

原标题：Forward deployed engineering, Part 7: Prototype in days, production in weeks

Abhinav Bhatia · 2026-10-20 · 约 16 分钟读完

摘要

本文是前沿部署工程系列第七篇，以虚构客户 Acme Consumer Brands 为例，讲解 FDE 如何在几天内刻意构建一个用后即弃的原型，再用数周时间将其加固为生产系统并交接给客户团队。作者主张原型与生产系统应分开：原型只为回答一个明确问题（如能否答对 Maria 的 20 个真实业务问题），需签订一页式原型契约，写明时间盒、成功标准和刻意跳过的部分；AI 辅助编码可加速原型开发，但合并的代码仍须由工程师逐行审查。加固清单涵盖身份、数据访问、护栏、评测、可观测性、成本、部署与灰度发布，其中身份与数据访问优先。交接需交付运行手册、明确到人名的所有权，并通过渐进式培训让客户独立运维。

要点

  • 原型应刻意用后即弃，与生产系统分开构建。
  • 原型契约须写明问题、时间盒、成功标准与跳过项。
  • AI 辅助编码加速开发，但敏感代码须人工逐行审查。
  • 加固清单按序覆盖身份、护栏、评测、成本与部署。
  • 交接靠运行手册、具名所有权和渐进式培训完成。

在第 6 部分中，我们为 Acme Consumer Brands 选择了一个框架：ADK，并在由不同团队负责的 Agent 之间设置了 A2A 边界。现在客户想看到一些能实际运行的东西。在我与合作伙伴的合作中，这往往是项目成败的关键时刻，而且通常发生在第一周。

有两种出错的方式。一种是花六周时间精心构建一个系统，却没有任何人验证过它是否回答了正确的问题。另一种是快速构建一个让所有人眼前一亮的演示，然后眼睁睁看着这个演示被推入生产环境——带着个人密钥、没有测试、也没有负责人。

本部分讲的就是这两种错误之间的路径。作为驻扎在 Acme 的 FDE，你会刻意在几天内构建一个原型，并计划将其丢弃。你使用 AI 辅助编码来快速推进，同时不降低标准。然后，你用几周时间加固真正的系统，使用 Production-ready agents 系列详细构建的清单，并进行交接，让 Acme 自己的团队能够运行它。

什么是原型？为什么要构建一个注定要丢弃的原型？

原型是系统的一个小型、粗糙的版本，目的是快速回答一个问题。把它当作一个实验：它的存在是为了回答一个问题，它的价值就在于这个答案。

原型有两种，你构建的是哪一种很重要：

  • 一次性原型是为了学习某些东西而构建，之后会被删除。速度比结构更重要。
  • 演进式原型则会逐步成长为产品，因此从一开始就需要良好的结构。

生产环境则是另一个极端：真实用户依赖的系统，由一个对其负责的团队来运营。为一次性原型做规划的想法由来已久。在《人月神话》（1975 年）中，Fred Brooks 指出，构建新型系统的团队无论是否有意，都会先构建一个一次性版本，因此应该主动为此做好规划。

我的观点：对于 AI Agent，几乎每次都应该构建一次性原型。原型需要学习的东西，比如模型能否基于这些数据回答这些问题，与生产环境所需的东西截然不同：身份认证、防护栏、测试和运维。试图同时兼顾两者，会让原型变得缓慢，也会让生产系统变得混乱。

一次性原型与生产系统的对比：原型用一个共享账号、没有防护栏，只为少数人回答一个问题，然后被删除；生产环境则以每个用户的真实身份为其服务，配备防护栏、评测关卡、流水线和明确的负责人，并运行多年

Acme 的原型应该证明什么？

没有明确问题的原型会变成一个永无止境的演示。所以在编写任何代码之前，你要与客户一起撰写一份一页纸的原型契约。这是 Acme 的那份：

PROTOTYPE CONTRACT: Acme campaign questions                 (throwaway)

Question it must answer:  Can an agent answer Maria's 20 real campaign
                          questions from the marketing tables, with the
                          right numbers?
Built with:               ADK, run in the agents-cli playground
Data:                     a read-only copy of three marketing tables,
                          eight weeks, no personal data
Skipped on purpose:       user sign-in, Databricks, the router,
                          guardrails, deployment, cost tracking
Time box:                 three days
Success:                  16 of the 20 answers correct, judged by Maria
Decision at the end:      harden it / change the use case / stop
What survives:            the 20 questions and checked answers, the tool
                          descriptions, the lessons learned
What is thrown away:      everything else

“三张营销表”指的是 Acme 的营销活动表。下面是其中第一张，让你了解原型读取的数据是什么样的：

三张营销表之一：campaign_performance，每个营销活动、地区和周对应一行，由市场部门拥有，通过 BigQuery 读取；这是 Acme Pure Refill Launch 在西欧的前四周

业务术语与 AI Agent 背后的数据 解释了每张表和每个列。

其中有三行起到了关键作用：

  • “有意跳过”被明确写下并达成一致。没有人能在事后声称这个演示已达到生产就绪水平，因为每个人都签署了一份列出其缺失之处的清单。
  • “成功”是一个由业务用户判断的数字，而 Maria 的 20 个问题来自探索阶段（第 2 部分）。这些数字只是示例，但关键在于其形式。
  • “留存下来的东西” 少而精。这 20 个经过核对答案的问题成为用于评测的黄金集的首批案例（证明它有效：把关发布的评测）。工具描述会延续到真实的 Agent 中（你的第一个 Agent：单一职责，狭窄的工具）。

原型阶段以一次决策会议收尾。三种结果都是好结果。三天后就因为数据无法回答问题而停止，远比三个月后才发现要便宜得多。

一个示例性的项目时间线：几天内完成一次性原型，然后做出加固、更换用例或停止的决策，接着是数周的加固，再进行有真实用户参与的试点，最后交接给客户团队

AI 辅助编程如何改变最初几天的工作？

AI 辅助编程是指使用模型来帮助编写、解释和修改代码。它有两个层次：

  • 编程助手在你输入时建议代码，并回答关于代码库的问题。
  • 编程 Agent 接受任务、进行规划、编辑多个文件、运行命令和测试，并汇报结果以供审查。

Google 自家的工具覆盖了这两个层次。Gemini Code Assist 提供 Standard 和 Enterprise 版本，通过 Google Cloud 管理。Gemini CLI 是一个在终端中运行的开源 Agent。Google Antigravity 是一个以 Agent 为先的开发平台，包含应用、IDE、CLI 和 SDK。专门针对 Agent，agents-cli 将自己描述为“用于在 Google Cloud 上构建 Agent 的 CLI 和技能”，可与你的编程 Agent 配合使用：你先安装它：

uvx google-agents-cli setup

然后让你的编程 Agent 来搭建并构建该 Agent。

对于 Acme 原型来说，这把三天的打字工作变成了三天的检查工作。编程 Agent 搭建项目骨架，编写每个工具及其测试的首个版本，并解释 Acme 现有数据代码中你从未见过的部分。你的工作从编写每一行代码，转变为明确任务并审查产出的结果。

项目中的 AI 辅助编程：你明确任务，编程 Agent 进行规划和编辑，运行测试和检查，你审查每一行代码并合并；敏感代码始终由人工审查；Google 工具覆盖助手和 Agent 两个层次

三条规则可以确保 AI 辅助编程在他人的环境中安全进行：

  • 只使用客户已批准的工具。 在第一周就问清楚（第 3 部分）。绝不要将客户数据、模式或凭据粘贴到未经批准的工具中。
  • 每一行代码都由你负责。 你合并的生成代码就是你的代码。要像审查同事的改动一样审查它。
  • 手工审查敏感部分。 身份验证、数据访问、路由规则以及任何写入数据的部分，每次都要逐行审查。

我的看法：AI 辅助编码让原型的成本大大降低，这也让“用完即弃”的原则变得更加重要。当一个演示只需一个下午就能完成时，直接上线的诱惑就会增大。

原型与生产系统之间的差距是什么？

下面是 Maria 的一个问题在 Acme 原型和生产系统中的流转路径：

同一个问题走两条路径：在原型中，一个进程使用共享密钥读取数据副本并打印答案；在生产系统中，Gemini Enterprise 为 Maria 登录，路由器应用防护栏并在代码中进行路由，一个专用 Agent 以 Maria 的身份读取实时数据，每一步都有追踪和成本记录

原型调用一个使用共享服务账号的 Agent 并打印答案。生产系统会检查用户身份，在代码中路由问题，以该用户的身份读取数据（对于供应数据，这意味着以 Maria 的身份访问 Databricks），通过每一道防护栏，记录追踪并核算成本。答案在 Maria 看来是一样的，但围绕它的一切都不同。

在开始加固之前，先扫描原型中那些绝不能保留的捷径。文末的试一试部分有一个小脚本可以完成这项工作。

加固清单上有哪些内容？

加固是指把一个能运行的原型变成一个安全、经过测试、可观测且运行成本可控的系统。把这份清单作为文件保存在代码仓库中，让客户的审查人员可以看到进度：

HARDENING CHECKLIST: Acme router                     owner     status

Identity       each agent has its own identity, least privilege
               supply reads Databricks as the signed-in user
Data access    read-only checks, row and cost limits on queries
Guardrails     kill switch, rate limit, Model Armor, audit log
               human approval before anything that writes data
Evals          golden set and held-out set; a gate in the pipeline
Observability  one trace per question; redacted structured logs
Cost           cost per resolved question, measured and budgeted
Deployment     deployed by a pipeline, secrets in Secret Manager
Rollout        shadow mode, then a pilot group, then everyone
Handover       runbook, named owners, the customer has deployed

清单中的每一项在 Agent 系列文章中都有一篇详细讲解如何实现的文章：

按顺序排列的加固清单：首先是身份和数据访问，然后是防护栏、评测、可观测性、成本、部署和上线；每张卡片都标明它回答的问题以及 Agent 系列中实现它的文章

  • 身份：提问者是谁，以及每个 Agent 如何证明自己的身份（Agent 的身份）。
  • 数据访问：在不安全查询到达数据库之前将其拒绝的回调（让 Agent 安全地访问数据）。
  • 防护栏：模型无法绕过的插件（无法被绕过的防护栏）。
  • 评测：能够阻止发布的 Agent 行为测试（证明它有效：为发布把关的评测）。
  • 可观测性、成本和部署：Agent Runtime、追踪、日志以及一个问题的成本（部署、观测并为之付费）。
  • 上线：发布到 Gemini Enterprise 并进行分阶段上线（交付给用户）。

这份清单是有顺序的。身份和数据访问排在最前面，因为如果 Agent 能读取用户无权查看的数据，其他所有测试都毫无意义。评测排在上线之前，因为没有基线就无法评判一个试点。

为什么代码只需几天，加固却要几周？

大多数加固工作并不是写代码。需要有人批准安全设计、创建身份、授予数据访问权限、配置身份提供商、与业务用户一起为评测用例打标签并商定预算。这些步骤中的每一步都要等待客户方有其他工作要做的某个人。以下是一个针对 Acme 的示例计划：

针对 Acme 的一个示例性六周加固计划：安全审查和访问申请在原型周启动，身份和数据检查优先进行，评测和可观测性并行推进，然后是流水线、试点和交接

有两个习惯可以避免进度拖延：

  • 第一天就启动耗时的审批流程。 安全审查和数据访问申请应在原型周内提交，而不是在原型周结束后。
  • 并行推进工作。 评测和可观测性互不依赖，因此两个人可以同时构建它们。

我该如何交接，才能让系统在我离开后继续运行？

FDE 的工作终会结束，但系统不能随之结束。交接是将系统以及运行系统所需的知识有计划地移交给客户团队。它包含三个部分。

一份运维手册。 运维手册（Google 的 SRE 书中称之为 playbook）是一份关于如何运行系统的书面指南：如何部署、如何回滚、告警意味着什么，以及针对每种已知故障该怎么做。SRE 书中指出，提前在 playbook 中记录最佳实践，与临场发挥相比，能将 MTTR（平均修复时间）大约缩短三分之二。以下是我使用的提纲：

# Runbook: Acme router
## What it does, and what it must never do
## Who owns what (names, not teams)
## How to deploy, and how to roll back
## Dashboards and alerts, and what each alert means
## Known failures and what to do
### Answers say "I could not verify every figure" more often than usual
### The supply agent returns 401 errors
### Cost per question jumps
## How to change a prompt or a model safely (run the eval gate)
## How to report a product bug (Part 8)

明确的责任归属。 系统的每个部分都需要在客户方指定一名负责人：代码、提示词、评测集、云项目、预算和值班轮换表。其中有些属于不同的团队，这没有问题，只要每一项旁边都有一个名字。

交接时的责任归属图：系统的每个部分在 Acme 都有指定的负责人，从路由代码和流水线到供应 Agent、评测集、预算、安全和值班轮换表；名字均为虚构

在实践中培训。 幻灯片教不会任何人运行一个系统。我与合作伙伴使用的模式是渐进式放手：首先你在客户的工程师观看时构建，然后你们一起构建，接着他们构建而你进行审查，最后由他们全权负责。检验交接是否成功的标准很简单：在你离开之前，Acme 的某个人已经部署过一次变更、回滚过一次，并使用运维手册处理过一次演练事故，全程没有你参与。

交接期间的渐进式放手：首先 FDE 在客户的工程师观看时构建，然后他们一起构建，接着客户构建而 FDE 进行审查，最后由客户全权负责；比例为示意

Google 的 SRE 手册描述了生产就绪评审，即在运维团队接手服务之前，对服务可靠性进行的一次结构化检查。将这一理念简化后的版本很适合作为最终的交接会议：一起过一遍检查清单、运维手册和负责人，并将所有未完成的事项记录下来，注明负责人和日期。

试试看：找出原型中的捷径

这个脚本用于查找那些在一次性原型中尚可接受、但绝不能进入生产环境的捷径。它只需要 Python 3，无需任何额外的软件包。将其保存为

prototype_leftovers.py

:

"""Find prototype shortcuts that must not reach production. Python 3 only, no packages."""
import re
import sys
from pathlib import Path

CHECKS = [
    ("hard-coded secret", re.compile(r"(api[_-]?key|secret|token|password)\s*=\s*['\"][^'\"]{8,}['\"]", re.I)),
    ("key file in the repo", re.compile(r"service[_-]?account.*\.json|credentials\.json", re.I)),
    ("personal or shared login", re.compile(r"@(gmail|example)\.com", re.I)),
    ("print instead of logging", re.compile(r"^\s*print\(")),
    ("unbounded query", re.compile(r"select\s+\*\s+from(?![^\n]*\blimit\b)", re.I)),
    ("note to self", re.compile(r"#\s*(TODO|FIXME|HACK)\b")),
]


def scan(root: Path):
    found = []
    for path in sorted(root.rglob("*.py")):
        if ".venv" in path.parts or path.name == Path(__file__).name:
            continue
        for n, line in enumerate(path.read_text(errors="ignore").splitlines(), start=1):
            for label, pattern in CHECKS:
                if pattern.search(line):
                    found.append((label, f"{path.relative_to(root)}:{n}"))
    if not any(root.rglob("test_*.py")):
        found.append(("no tests found", str(root)))
    return found


if __name__ == "__main__":
    root = Path(sys.argv[1] if len(sys.argv) > 1 else ".")
    results = scan(root)
    for label, where in results:
        print(f"{label:26} {where}")
    print(f"\n{len(results)} item(s) to fix or justify before hardening.")

然后试试这些：

  • 找出它漏掉的那个。 该查询使用 f-string 构建 SQL，因此像 x' OR '1'='1 这样的品牌名称会改变查询。添加一项针对包含 SELECT 的 f-string 的检查，然后用参数化查询修复该工具，就像 你的第一个 Agent：单一任务，狭窄工具 中所做的那样。
  • 在你自己的原型上运行它。 它打印出的每一行，要么是检查清单上的一项加固任务，要么是你应该记录下来的一项决策。

这个脚本只能发现明显的捷径。请同时使用客户批准的密钥扫描和代码审查工具。

可能出问题的地方

  • 演示变成了生产。 一个能运行的原型被展示给某位总监，对方下周就想要它。签署过的原型合同及其“有意跳过”清单就是你的保护。
  • 没有问题，就没有终点。 没有成功衡量标准的原型会不断膨胀。在开始之前，先就 20 个问题和目标达成一致。
  • 加固开始得太晚。 安全审查和访问申请需要数周时间。在原型周期间就启动它们。
  • 信任生成的代码。 编码 Agent 可能会写出没有行数限制的查询，或者记录令牌。请人工审查敏感代码。
  • 客户数据进入了错误的工具。 将 schema 或样本粘贴到未经批准的助手中，可能违反客户的数据政策。先确认哪些工具是获得批准的。
  • 用幻灯片交接。 如果在你离开之前，客户的团队从未部署过或回滚过系统，那么交接就没有真正发生。
  • 以团队名称作为负责人。 “数据团队负责评测集”意味着没有人负责。写下一个具体的人名。

我现在会怎么做

  • 在编写任何代码之前，先为你的下一个项目写一份原型合同，并让业务用户就成功衡量标准达成一致。
  • 第一天就启动安全审查和数据访问申请。
  • 将加固清单保存在代码仓库中，每一行都注明负责人和状态。
  • 在加固开始之前，运行这个遗留捷径脚本，或你自己的版本。
  • 在你离开前两周，预约交接演练（部署、回滚、事故演练）。

我们学到了什么？

  • 一次性原型的存在是为了快速回答一个问题，而计划将其删除则能防止它滑向生产环境。
  • 一页纸的原型合同，加上由业务用户判定的成功标准，以及一份明确列出有意跳过事项的清单，能同时保护双方。
  • AI 辅助编程把数天的敲代码变成了数天的检查工作，前提是你只使用经过批准的工具，对每一行代码负责，并人工审查敏感代码。
  • 加固工作按照清单顺序进行，首先从身份和数据访问开始，因为如果 Agent 能读取用户可能无权查看的数据，其他所有测试都毫无意义。
  • 加固需要数周时间，因为大部分工作都在等人，所以要在第一天就启动耗时的审批流程，并并行推进独立的工作。
  • 只有当客户团队在没有你的情况下，使用运维手册完成了一次变更部署、一次回滚，并处理了一次演练事故，交接才算完成。

接下来是什么？

即使是加固完善的系统，也会以无人预料到的方式出现故障。在第 8 部分：现场调试中，我们将阅读陌生代码、复现故障、利用日志和追踪来区分客户环境问题与产品缺陷，并撰写一份产品与工程团队能够据此行动的缺陷报告。本部分中的运维手册和指定的负责人正是调查的起点。
