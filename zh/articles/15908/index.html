我在 AI 异世界重生为 FDE，来自北美AI Agent 公司的一线实录

Superlinear Academy · 2017 · 约 8 分钟读完

摘要

作者现任 Cresta 的 Head of FDE，以第一人称讲述自己从创业公司联合创始人转岗为前沿部署工程师的经历。文章解释 FDE 的职责：在客户现场把 AI Agent 产品真正落地，涵盖集成、调试、评测与上线运维。作者认为 AI 时代产品难以开箱即用，FDE 通过真实交付倒逼产品进化，区别于售前工程师和解决方案架构师，需直接写生产代码并对业务结果负责。文中还给出 FDE 的时间分配（约三分之一写代码、三分之一写 prompt、三分之一做评测）和适合人群画像。

要点

  • FDE 是在客户现场把 AI 产品真正跑起来的工程师。
  • AI 产品难开箱即用，需 FDE 对接客户系统与流程。
  • FDE 贯穿售前售后，直接写生产代码并对结果负责。
  • 作者时间约三分之一写代码、写 prompt、做评测。
  • OpenAI、Anthropic、Databricks 等大厂都在抢招 FDE。

大家好，应号称“不布置话题”的 Mts Shu 的“邀请”，我在刚经历两周高强度出差回家后，来和大家分享 FDE （Forward Deployed Enginner) 这个在 AI 异世界里正流行的职业。坦白说我最不爱看“AI 味儿”很重的文章，所以先声明：此文不一定客观，也完全不权威。想看四平八稳、面面俱到的总结，欢迎自行搜索。这篇如果还有点价值，大概就是提供一些 data points，讲讲为什么我在创业四年后，换了一家公司“重生”为 FDE。这究竟是新一波浪潮，还是新瓶装旧酒、昙花一现的黑话？

我之前在 LinkedIn 写过两篇英文博客（1， 2），分享加入新公司、尝试新工种的感受。以下内容也部分来自那两篇，算是“废物利用”🤣 但清晨一杯咖啡下肚，我突然觉得：既然面向中文读者，就不必那么四平八稳，写点有意思的。我这是又换赛道又换职业，不就是活脱脱的“异世界重生＋转职”嘛？

所以各位看客，准备好点赞关注加小铃铛了吗？接下来我以个人视角，聊聊为什么 2B 的 AI 公司都在疯狂招 FDE。

FDE 是什么？为什么 AI 公司需要它？

我在 Cresta 这家 AI 公司做 Head of FDE。先回答一个问题：什么是 FDE？

FDE, Forward Deployed Engineer。当然这等于没说..

一句话：FDE 是把 AI 产品在客户现场真正“跑起来”的工程师。

众所周知，AI Demo 很酷炫，短时间就能做出 wow 效果（我就不配图了）。但真要落地，很多企业自己的数据和流程要么很“草根”，要么彼此割裂。客气点说：业务流程、旧系统和数据栈都不尽相同。你买 HubSpot 或 Stripe，几天培训熟悉界面就能上手；而 AI 产品往往只是一个输入框、一个电话号码：简单可问答，复杂能退款、改行程、招人裁人，去做 web app、mobile app、API/SDK 能做的一切事。有点像以前有人吹的“框计算”，但确实 AI 就是重新定义的用户体验。

FDE 的职责，就是站在客户一线，把通用平台与具体场景对齐：理解业务、拼接能力、打磨体验、上线运行、稳定扩展。FDE 不光把产品送到“最后一公里”，更像把宜家家具做成你家最需要的那把摇椅，把雅马哈钢琴调到最适合你书房的音色，是给 John Wick 手工定制西装的那位裁缝。

FDE 最早是 Palantir 做国防大单时提出来了，好像已经十几年历史，当时还真的是把工程师部署在前线（可能现在还是）

“好吧，那就是做实施、onsite engineer、solution architect、professional service，卖人头、卖时间？”呃😅，你非要这么想也行。但为什么这个词现在这么热，甚至号称是 AI 时代最热的工种？

很简单，我们还在 AI 时代的蛮荒期🍖。原先 SaaS/标品的做法在 AI 面前并不总奏效。企业级 AI 产品不能指望开箱即用，不能指望客户自己知道怎么“调教”AI，往往做不到 PLG，也很难自助化（self‑service）；如果你用旧世界的办法在这片 AI 异世界，就很难真正落地。

在 AI Agent 这个仍快速演化的赛道里，需求的多样性和不确定性尤为明显。你会遇到各种“看似不可复制”的定制化工作：语料治理、对话流程细化、与客户 API 与数据网关的集成、合规与安全要求的适配、上线后的监控与回滚策略……这些事情看似零散，但最后会沉淀成产品路线图与最佳实践库。这就是 FDE 的价值：用一次次真实交付，倒逼产品进化——不用等产品面面俱到，就能抢占山头、锁定大客户。

以 Cresta 为例（好吧，迟早要进广告的）。本质上我们是一家 AI Agent 公司，主要服务联络中心（文字、语音、邮件）。公司 2017 年成立；如果按 1B 的“独角兽”口径，我们去年就达到了。很多大银行和航空公司很多年前就用 Cresta 做人工客服的辅助（有点像CheatingDaddy这样的AI面试小助手：实时提示怎么说、评估沟通效率、 快速复盘）。现在则更多用于降本增效：只要不是太“离谱”的 case，很多问题都可以让 AI Agent 来回答或执行——比如完成预订、改签、退款等复杂流程，搞不定再转给人工座席（human agent），或者由一个人工座席同时处理多个 case，在 AI Agent 背后提供特批与支持。

要把这样一套系统真正跑进生产，需要接入客户的 VPN、CRM、工单系统、知识库与电话系统，对接鉴权、速率限制、数据权限；同时要把对话策略和业务 KPI 对齐（如首次响应率、转化率、平均处理时长等）。这些工作如果没有 FDE 在前线顺藤摸瓜、穿针引线并负责到底，很难稳定落地。

传统的 Sales Engineer 在签单之前做 Demo；传统的 PS 则在签单之后做调优、二次开发。而 FDE 贯穿始终：把 AI 通过工程与经验真正跑起来，一边倒逼产品部门做出调整改进，一边持续支持客户。

不能指望产品团队推出一个完美的产品让客户自己用。AI 时代，确定性被重新定义了。写 Prompt 是个技术和艺术的结合，而且需要结合大量历史会话数据做模拟回测。即使有大量码农的客户往往也搞不定如此复杂精致的 AI 项目。客户掏钱买的不再是一个产品，是一个 AI 方案，是一个全新用户体验。脏活累活脑力活，无所谓。能收钱就行，不是吗？

在你还在怀疑 FDE 存在必要性时，OpenAI, Anthropic, Databricks, Snowflake等 AI 大厂都在疯狂搜刮和培养 FDE。模型的差别已经非常细微，应用的价值很多时候就看实施的怎么样。客户用的开心才愿意多买 token。

它和 Solution Engineer / Solution Architect 有什么不同？

很多人会把 FDE 和售前工程师（SE）、解决方案架构师（SA）放在一起比较。确实我们都面向客户，但 FDE 的工作方式更“工程化”。

第一，FDE 直接写生产代码。 SE 更偏向售前场景的技术表达与原型演示，SA 更偏向架构设计与技术选型；而 FDE 既要设计也要实现，要把方案接到客户真实系统里，并对上线质量负责。

第二，FDE 对结果负责到“最后一公里”。 我们不仅给出方案，还要把它跑通、跑稳、跑出可衡量的业务价值。上线是否达标、是否能在 SLO 下稳定扩展、问题发生如何定位和回滚，都是 FDE 的日常。

第三，FDE 是“复合型选手”。 既能和客户高层讨论业务闭环，也能和对方工程师对着日志抓 Bug；既要做需求澄清与范围控制，也要在关键路径亲自下场编码。这种切换，是 FDE 的常态。

我为什么重生为 FDE

在 LinkedIn 文章里，我用乔布斯的“connect the dots”这套西方人的老生常谈，讲自己如何走到 FDE 这一步。

按这篇的设定，我就是“重生＋转职”。

我最初是个 full‑stack 工程师，干过 JavaScript、Flash、EJB 等各种语言和平台；后来做管理，带过加拿大、美国、印度和国内的团队。2021 年到上个月，我作为 cofounder 做了一家 streaming database 创业公司。PM、UX、Doc、DevRel、SDR、SA、PS、CloudOps……都做过一些。我也是上个月才第一次听到 FDE 这个词，然后觉得：哇，这对我们这种什么都碰一点、还创过业的人太友好了。比较官方地说：这些“点”被一条线串了起来——工程实现能力、产品抽象能力、以及面向客户的协作与交付能力，在 FDE 这个岗位上被同时要求，并形成合力。

这也是我特别喜欢 FDE 的原因：每天都能把抽象而复杂的技术，与具体业务问题对上号；既保留了工程师对质量与效率的执着，也保留了 PM 对产品体验的执拗，更保留了对业务结果的责任感；还能到处出差。

FDE 可能有 1/3 的时间和客户对齐远景目标与具体流程，1/3 把 AI 方案做出来，1/3 与内部团队协调反馈。具体到实现，大约 1/3 写代码（主要是 Python，也会有 JS/Go/Java），1/3 写 prompt（既有最佳实践，也有不少不可言说的 art 与 taste），1/3 写测试并做 evals。

所以，什么样的人适合做 FDE？

用“AI八股”文风可以列很长。说人话，我觉得 FDE 就是要“快、准、狠”（当然这很片面，主要为了好记——据说押韵更容易被记住）。

  • 快：是多层面的快: 很快 get 客户的痛点、需求与约束，很快交付，很快学新东西。FDE 首先要是过硬的 software engineer。full‑stack 最好。与一般资深工程师不同，FDE 不一定追求最精巧优雅或极致性能的方案；2 天做出一个可行的 Python 方案，往往比 20 天打磨一个 Rust 方案更实际。Cresta 后台很多代码是 Go 或基于 AWS 的服务，它们足够快；而 FDE 常写的是与客户各类系统的对接（多为 REST 或 GraphQL，少量是私有 SDK），或 Salesforce/HubSpot 等 SaaS 的集成，Python 通常够用。使用 coding assistant 或 Vibe Coding 完全 OK。我近一年主要用 Claude Code，入职后第一个 PR 基本都是 Copilot/Codex 辅助写的。可以把 FDE 理解为 vibe coding 的一种最佳“变现方式”：雇主和客户花钱请你 vibe coding😁
  • 准：要犀利，抓大放小，动态调整优先级。快速获得客户信任，准确定位项目关键，并在公司内部找到合适的资源支援。
  • 狠：FDE 不是轻松活。很多大佬把 FDE 与创业联系在一起，是因为创过业的人都知道，早九晚五很难成事。需求变化、人员变动是常态；该出差出差，该加班加班；不懂就问，不会就学。

不用很久我们Cresta年营收就要过亿了，我们打算在温哥华加大招聘，各类职位都会开放。关于 FDE，理想的画像👤大致是：

  • 在咨询公司或创业公司做过，技术过硬、吃苦耐劳，并有丰富的客户协作经验，能说会道，能屈能伸 （对酒量没要求，也不需要会高尔夫，毕竟有大销售搞定🤝客户关系）
  • 技术全面、学习能力强，熟练掌握各类 Vibe Coding（这就像当年“熟练掌握 Word 等办公软件”，但如今更应景）；出活快，懂变通
  • OK甚至 Enjoy travel，因为大约 1/3 的时间会在路上🤷 （我上班第一天老板说有个项目可以观摩一下 FDE 如何干活，我第二天就开车去西雅图。第二周则是来到硅谷 HQ 和产品团队熟络一下。 不要太远的话， 项目前期和客户 onsite 聊还是效率更高，关系也更融洽，后续大量 zoom/teams 线上会议，往往也有客户 staging env 的 VPN。毕竟不是驻场工程师）
