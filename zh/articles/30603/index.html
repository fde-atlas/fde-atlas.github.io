面向 FDE 的 AML/KYC：AI Agent 的合规签核

原标题：AML/KYC for FDEs: compliance sign-off for AI agents

FDE Times · 2026-11-06 · 约 6 分钟读完

摘要

文章面向在银行部署 AML 告警审查 Agent 的前沿部署工程师，核心论点是合规部门而非工程团队决定上线时间，合规所需的三类证据（验证、风险权衡、可解释性）必须从第一周就开始准备。作者引用 Wolfsberg Group 的三大支柱框架、Co-Investigator AI 研究以及 FinCEN 与美国监管机构的最新指引，给出试点设计方法：在已结案告警上运行，逐个分析漏报案例而非只报总体准确率。文章强调 Agent 只能给出建议、由调查员签署决定，并提醒日志范围、SAR 叙述模板和适用的模型政策应由客户机构决定，工程师不应擅自定夺。

要点

  • 合规部门决定上线，证据须从第一周开始收集。
  • Wolfsberg 三支柱：验证、风险权衡、可解释性。
  • 试点用已结案告警，逐个解释漏报案例。
  • Agent 只建议，调查员决定并签署。
  • 日志范围与模板由客户合规政策决定。

如果到第六周才第一次接触合规，你可能要重建大部分架构，所以他们需要的证据要从第一周就开始准备。

简要说明

  • AML 警报审查 Agent 只提供建议。调查员仍然负责决策并签字。
  • 合规需要三样东西：验证证据、漏报案例风险的量化数字，以及每条建议的解释。
  • 记录什么内容、使用哪种叙述模板、哪份模型政策覆盖该 Agent，这些都是机构内部的决定。写代码之前先问清楚。

你刚被要求把一个 Agent 接入某家银行的 AML 警报队列。这个 Agent 读取交易历史、汇总 KYC 文件、建议关闭还是升级每条警报，并为可疑活动报告（SAR）起草叙述文本。演示运行顺利，客户的工程团队非常喜欢它。

但工程团队并不能决定上线日期。决定上线日期的是合规部门。如果你到第六周才第一次接触合规，很可能要重建大部分架构。

这类项目正变得越来越常见。制定金融犯罪标准的大型银行协会 Wolfsberg Group 在 2025 年 8 月的一份声明中指出，金融机构正逐步将自动化、AI 和 ML 纳入其可疑活动监测策略。

因此，对 FDE 来说，稀缺的能力不是调用 LLM，而是让 Agent 通过合规审查。

合规部门到底需要看到什么？

Wolfsberg 的负责任创新框架有三大支柱：迁移到新工具时的验证、在模型风险与金融犯罪风险之间取得平衡，以及可解释性——即外部人员能够清楚地看到系统的覆盖范围和运行效果。

以工程师的视角来看，每个支柱都是你必须交付的成果，而不是一句口号。

第二个支柱是最常被误解的。模型风险是指 Agent 出错的可能性。金融犯罪风险是指洗钱漏网的可能性——可能是因为 Agent 判断错误，也可能是因为旧流程太慢跟不上。

合规部门并不要求一个完美的 Agent。他们想看到的是两种风险以具体数字并排呈现。

试点，用数字说话

假设你提议让该 Agent 处理调查人员上季度关闭的 200 条警报。这些结果已经知晓，因此这是你能拿到的最佳评测集。假设该 Agent 建议关闭 150 条、上报 50 条。

工程团队会查看那 150 条：四分之三的队列可以得到更快处理。合规团队则会立刻提出另一个问题：在 Agent 想要关闭的 150 条中，有多少是调查人员实际上报了的？

如果答案是 6 条，那么这 6 个案例就是会议的核心。你需要逐一打开它们，解释 Agent 为什么漏掉了，并提出修复方案。

这就是在数据基础上权衡风险。你不要说“该 Agent 准确率为 97%”，而是说：该 Agent 缩短了这一组的处理时间，代价是漏掉了 6 个案例，在当前阈值下尚不可接受，以下是补救措施。合规团队可以基于这样的陈述做出决策。

同样的故事也说明了为什么不能让 Agent 自行关闭警报。Co-Investigator AI（一项 2025 年关于起草 AML 叙述的 Agent 的研究）的作者强调，人类调查人员必须牢牢保持在流程之中。在你的设计中，让 Agent 写“建议”，让人类按下“决策”按钮。

由谁决定记录什么内容以及如何书写？

有三个问题工程师往往自行拍板，但实际上属于客户组织。第一个是叙述模板。Co-Investigator AI 研究指出，SAR 叙述的质量在不同金融机构之间差异很大。Agent 可以帮助标准化它们，但在你编写提示词之前，必须由合规团队确定采用哪个模板。

第二个是日志记录。同一研究指向一种为每个 Agent 保留完整审计日志的设计。不过，记录多少取决于规则的规定。

FinCEN 和美国银行业监管机构于 2025 年 10 月 9 日发布了一套 SAR 常见问题解答，以减少金融机构不必要的合规工作。根据律师事务所 Orrick 的分析，这些解答明确指出，没有法律要求记录不提交 SAR 的决定，也没有要求在 SAR 提交后重新审查。

因此，Agent 记录什么内容是客户的政策选择，而不是你的。让合规团队确定必填字段清单，然后让 Agent 针对每条建议准确记录该清单，而不是默认“全部记录”或“跳过”。

第三个是该 Agent 适用哪项政策。2026 年 4 月 17 日，美联储、FDIC 和 OCC 发布了关于模型风险管理的 SR 26-2，取代了沿用多年的 SR 11-7。

根据 Baker Tilly 的说法，新指引并未涉及生成式 AI，AI 将通过单独的指引或规则来处理。因此，直接询问客户的模型治理团队：这个 LLM Agent 将依据哪项内部政策获得批准？

按什么顺序？

第一周，申请与合规部门和模型治理团队召开一次联合会议，并带上上面的三支柱表格。目标是达成三项书面共识：AI Agent 的范围（它只提供建议，不做决定）、可接受的漏报阈值，以及适用于该 Agent 的模型政策。

接下来，申请获批的叙述模板和必须记录的数据字段清单。只有拿到这两样之后，才应该编写提示词和日志模式。然后在已关闭的警报上运行试点，并把每个漏报案例带到第二次会议上，而不是只带一个汇总数字。

四个最常见的错误都源于同一个习惯：工程师决定了本属于合规部门的事情。

  • 先动手构建，事后再申请批准。
  • 让 AI Agent 自行关闭警报，“为了节省时间”。
  • 不查阅政策就选择日志记录级别。
  • 想当然地认为现有的模型验证流程会自动适用于 LLM。

在职业发展方面，如果你的目标是金融领域的 FDE 职位，请牢牢掌握本文中的概念：AML、KYC、SAR 和模型风险管理。

如果你曾带领一个系统通过控制职能的审批流程，请以成果的形式写进简历：你设计了试点，控制职能设定了某个阈值，系统在给定条件下获得批准。

谈论这段经历时，先从你发现的漏报案例以及你如何处理它们讲起，因为这才能表明你理解风险，而不只是会写提示词。
