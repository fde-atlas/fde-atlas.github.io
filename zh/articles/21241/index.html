Cursor FDE 岗位要求与面试准备

FDE Times · 2026-10-24 · 约 5 分钟读完

摘要

文章解读 Cursor（Anysphere）为伦敦发布的 FDE EMEA 招聘启事，强调该岗位对生产系统负责而非做演示，要求端到端交付、Python 与 TypeScript、与客户工程师做需求调研，并负责评测、追踪和成本。作者建议以一次带真实数据的迁移项目作为面试准备，并整理成可复用的操作手册。

要点

  • Cursor 的 FDE 岗位要求对生产系统负责，明确不做演示。
  • 岗位覆盖需求调研、工作流搭建、评测、追踪与成本的完整周期。
  • 经验要求五年以上，其中至少两年直接面向客户。
  • 团队以 Strategist 加一到两名 FDE 组成小组，正在建设完整 FDE 组织。
  • 最佳准备是用真实仓库做迁移，产出合并率、成本数据和操作手册。

伦敦岗位覆盖从需求调研到评测、追踪和成本的完整项目，最好的准备是自己做一次迁移。

要点速览

  • Cursor 在伦敦发布的 FDE EMEA 岗位强调对生产系统负责，而不是做演示
  • Cursor 要求的能力：端到端交付，Python 和 TypeScript，与客户工程师一起做需求调研，并负责评测、追踪和成本
  • 最好的准备是搭建一个有真实数据的迁移工作流，再整理成一份操作手册

打开 Cursor（所属公司为 Anysphere）于 2026 年 6 月 4 日为伦敦岗位发布的 Forward Deployed Engineer, EMEA 招聘启事，里面有一句话说得相当直白：这不是一个做演示的岗位，你要对必须在真实世界中运行的系统负责。

读后面的内容时，请记住这句话。很多工程师把招聘启事当作关键词清单，用来往简历里塞词。对这个岗位，正确的读法是把每一行当作你入职第一周在客户现场要做的任务，然后问自己：做过没有？有什么证据？

招聘启事描述的其实是一个完整项目

把所有要求读完，会发现 Cursor 这份启事描述的是一个相当完整的工作周期。你要和客户的工程师一起做需求调研，为重构、迁移、PR 评审循环或从故障到修复等工作搭建 Cursor 工作流。

之后，你要亲自负责评测、追踪（tracing）和成本之间的权衡，并把做出来的东西打包成可复用的模式。

在技能方面，Cursor 要求有搭建生产级 AI 工作流的经验，能在前端、后端、基础设施和提示词迭代之间端到端地工作，具备运维可靠性意识，并且精通 Python 和 TypeScript/JavaScript。

Exponent 的岗位汇总页面列出的经验要求是五年或以上，其中至少两年直接与客户打交道。

Cursor 如何在组织中定位这个岗位，也值得细读。公司把 FDE 描述为与企业工程组织坐在一起工作的人（也可能远程），Exponent 的页面还提到，Cursor 正在建设一个完整的 FDE 组织，而不是一个支持部门。

这直接影响你在面试中如何讲自己的经历：你是让产品真正跑起来的人，而不是处理工单的人。

Cursor 的 FDE 团队是怎样组织的？

Cursor 于 2026 年 7 月 24 日发布的 Forward Deployed Strategist 招聘启事展示了团队的组织方式。每个小组（pod）由一名 Strategist 和一到两名 FDE 组成；FDE 与客户团队坐在一起，搭建更深入的生产系统。这份启事还重申了公司的使命：让编程自动化。

在管理层面，Cursor 正在招聘一名 Regional Director of Forward Deployed Engineering，岗位发布于 2026 年 7 月 22 日，负责带领并扩充一支 6–8 人的 FDE 团队，承担战略项目。

这个人需要有八年或以上带领工程团队交付生产系统的经验，能作为客户的高层技术负责人，并要建设可复用的操作手册，让整个 FDE 组织不断进步。

由此可以得出一条准备建议：既然 FDE 组织的领导层负责建设共享的操作手册，那么能把为一个客户做的工作转化为适用于下一个客户的成果的 FDE，很可能会受到高度重视。

两个层面的证据都要准备：一个运行良好的客户，一个别人能复用的模式。

示例：一个有真实数据的迁移项目

设想一个假设的客户，想把几百个服务从旧的日志库迁移到新的日志库。这正是招聘启事提到的那类工作。与客户技术负责人的一次好的需求调研可能是这样的：

FDE： 迁移 PR 需要满足什么条件，你们团队才能不经手动修改就直接合并？ 技术负责人： CI 通过，告警系统读取的日志格式不变，每个 PR 只涉及一个服务。 FDE： 谁来评审？他们每周能为这件事拿出多少小时？ 技术负责人： 两个人，每人几小时。

前三条回答定义了你的评测：CI 通过、日志格式不变、只涉及一个服务。最后一个回答定义了真正的约束：人工评审能力，而不是代码生成速度。

再看一个假设计算。工作流生成 200 个 PR，150 个通过 CI，评审者合并了 120 个。合并率是 60%，而不是 CI 数字暗示的 75%。如果整批的模型总成本是 C，那么每个合并 PR 的真实成本是 C 除以 120，而不是 C 除以 200。

追踪的价值就体现在这里。为每个 PR 保存一份追踪记录，你就能看出那 30 个通过 CI 的 PR 为什么被拒：也许是日志格式被改了，也许是同时改动了两个服务。

每一种原因都可以变成一项自动检查，在 PR 到达评审者之前运行。这样两位评审者只需阅读真正有机会被合并的 PR。

把项目变成求职材料

下表把招聘启事中的每项要求，对应到你可以通过上述项目自己准备的证据。

启事中的要求 应准备的证据
与客户工程师一起做需求调研 一页记录：提了哪些问题，由此得出了哪些合并标准
搭建 Cursor 工作流（迁移、PR 评审） 一个包含真实 PR 系列的仓库，每个 PR 只有一个范围
评测、追踪、成本 一张表：合并率、被拒原因、每个合并 PR 的成本
端到端，Python 和 TypeScript 一个 Python 编排脚本，一个 TypeScript 小型仪表盘
可复用的模式 一页别人照着就能做的操作手册

简历里要用结果说话：用一行写清工作流、合并率，以及读完追踪后加了哪项检查。如果你与客户打交道的经验不足两年，就写那些和其他团队坐在一起排查生产问题的经历，这是最接近这份工作的素材。

准备中的常见错误

最常见的错误，是在一个明确表示不看演示的岗位面试中带一个演示。一段 Agent 修代码的精美视频回答不了这些问题：它在真实仓库上跑了多少次？失败了多少次？失败时你做了什么？

另一个错误是忽视成本。招聘启事写得很清楚，FDE 负责成本权衡，如果你说不出一个 PR 花了多少钱，就等于把直接分配给你的那部分工作留了白。也不要只谈代码：面试官想听你在写第一行代码之前问了客户什么。

最后一个错误是成功跑通一次就停下来。在一个领导层负责建设操作手册的组织里，下一个问题几乎必然是：没有你，别人能重复这件事吗？

这周，挑一个开源仓库，用 Cursor 迁移 20 个文件。20 个 PR 加一张诚实的数据表，比任何演示都更有说服力。
