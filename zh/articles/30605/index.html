IBM 前沿部署部门：FDE 角色是什么样的

原标题：IBM Forward Deployed Unit: what the FDE role looks like

FDE Times · 2026-11-22 · 约 7 分钟读完

摘要

文章分析 IBM 于 2026 年 5 月推出的 Forward Deployed Unit（FDU）模式。IBM 宣称六人小组可完成三十人团队的工作，但未提供数据；九月另一篇文章又描述为三到四人小组，两者是不同描述而非团队缩减趋势。与 OpenAI 式由一名 FDE 独自负责的模式不同，FDU 中前沿部署工程师与架构师、业务负责人、领域专家协作，核心技能是划分决策边界、审查 AI Agent 输出、把 Agent 当作受控账户管理权限，并从第一天准备可移交的评测集与运行手册，确保客户最终能独立运营。

要点

  • IBM 的 FDU 是常设小组，FDE 与架构师、业务负责人、领域专家协作。
  • 六人组与三到四人组是 IBM 两次不同描述，不能视为团队缩减趋势。
  • FDE 核心技能是划分决策边界并审查各 Agent 的输出。
  • Agent 应像员工账户一样管理身份、权限与日志，第一周即与安全团队沟通。
  • 需从第一天积累可运行的移交资产，让客户最终独立运营。

在 IBM 的前沿部署部门（Forward Deployed Unit）中，FDE 指挥 AI Agent，与队友分担职责，并留下客户可以在没有他们的情况下运行的系统。

简要概述

  • IBM 将 FDU 描述为一个规模小但常设的部门，其中 FDE 与架构师共享一个席位，此外还有成果负责人和领域专家。
  • IBM 赋予 FDE 的任务是将 AI 资产和 AI Agent 编排成业务解决方案，因此核心技能是分工和审查产出。
  • 发布时的六人团队和九月份的三或四人团队是 IBM 的两种不同描述，并非实测趋势。

当 IBM 于 2026 年 5 月 14 日推出其前沿部署部门（FDU）时，它声称一个六人小组可以完成 30 人团队的工作。这是 IBM 自己对这一模式能力的说法，且发布时没有任何数据支持。

到了九月，IBM 的另一篇文章描述了一个典型的仅由三或四人组成的部门，其中 FDE 与技术架构师共享一个席位。这两个数字是 IBM 对该模式的两种独立描述。两者并不一致，也不应被解读为团队正在持续缩减的证据。

如果你习惯于 OpenAI 风格的 FDE——即一名从头到尾负责客户问题直至投入生产的工程师——那么 FDU 会把你置于一个截然不同的位置。你是三或四人中的一员，身边有一整支 AI Agent 队伍，你的工作是把所有这些整合成能运行的东西。

是一名能力全面的工程师，还是一整套系统？

OpenAI 写道，FDE 的职责是足够稳健地解决客户的问题，使客户愿意在系统投入生产后接手运营。其 FDE 不需要在第一天就了解该行业，但他们有责任去学习它。一切都依赖于一个能力广泛的人。

IBM 则将这些能力分散到多个人身上。发布公告将 FDU 描述为由负责重新设计流程的领域专家、负责将战略与执行连接起来的架构师以及工程师组成。报道此次发布的 Verdict 同样描述了一个由技术、业务流程和架构专家组成的小组。

在六月的一份分析中，IBM 将 FDE 称为第四种角色，与负责客户成果的人、领域专家和架构师并列。该公司赋予 FDE 的任务是将 AI 资产和 AI Agent 编排成业务解决方案。

IBM 还表示，该部门是常设的，不会在每个项目结束后解散。IBM 将此定位为咨询行业的一次转变：更少的建议方案演示文稿，更多由工程师自己构建的系统。

作为 FDU 中的 FDE，你自己动手做的事情更少了，但你必须让自己的工作与其他人以及 AI Agent 的工作相契合。

三个人，十五个 AI Agent：第一周

举一个假设的例子。某制造商的采购部门希望将供应商发票与采购订单的匹配流程自动化。该小组由一名业务成果负责人、你（FDE 兼架构师）、一名采购专家以及大约十五个 Agent 组成。

单打独斗的 FDE 的本能是第一天就开始写代码。而在 FDU 中，首要任务是划定边界：哪些决策归谁、哪个 Agent 从谁那里接活、谁来审核该 Agent 的产出。下表展示了一种划分方式。

角色负责决策的事项委派给 Agent 的工作审核产出
成果负责人成功指标、优先级汇编进度报告、每周衡量指标对照目标的业务指标
FDE / 架构师集成架构、访问权限、部署方案生成连接器、提取发票、编写测试、运行夜间评测代码和评测结果
领域专家什么才算正确匹配、哪些例外需要人工处理起草用户访谈问题、初步标注评测集中“正确”的定义、已标注样本

最后一列往往最容易被留空。十五个 Agent 并行运行所产生的产出，远超三个人所能阅读的量。因此，每条 Agent 工作流都需要且仅需要一名审核人，并配有明确的标准，例如审核随机抽样，或只有在评测达到约定阈值后才放行工作。

还要注意，“正确匹配”的定义属于领域专家，而不是你。单打独斗的 FDE 必须自己学习领域知识，并通过客户探索访谈来推断。而在 FDU 中，你需要的能力是把队友的回答转化为可运行的测试用例。

Agent 是持有门禁卡的同事

当 Agent 在客户系统内部工作时，担任架构师角色的人要承担一项很少有人预先规划的工作。稳妥的做法是把每个 Agent 当作一名新员工账户来管理。

每个 Agent 应拥有自己的身份，只获得其所需的权限，走与真人相同的访问申请流程，并且所有操作都要记录在客户安全团队可读取的地方。发票提取 Agent 需要发票文件夹的读取权限，但不需要 ERP 的写入权限。

在第一周就向安全团队提交 Agent 清单及各自的权限。让他们在项目中途自行发现，是最容易把一次例行沟通变成一场调查的做法。

辅助轮只有在被拆掉时才有用

Forrester 将 FDE 比作自行车上的辅助轮：确实有用，立竿见影，但前提是最终有人把它们拆掉。相比之下，FDU 是 IBM 的常设单位。正因为该单位不会自行解散，客户之后要骑什么车的问题必须尽早提出。

实际的答案是准备一套交接资产。以发票匹配为例，这套资产应包括版本化的提示词、一个评测集（其中“正确”的定义需由领域专家签字确认）、一份数据映射、Agent 及其权限清单，以及一份操作手册，以便客户的团队在模型变更时能自行重新运行评测。

从第一天起就为这些资产创建文件夹，并在整个项目期间让每个角色填写自己负责的部分。如果留到最后一周，你只能交付描述系统的文档，而客户需要的是能够实际运行的资产。

转向单元模型时人们容易踩的坑

最常见的错误是单打独斗思维的 FDE 把所有决策都攥在自己手里。你代替领域专家定义什么算正确，或者不询问业务结果负责人就更改成功指标。结果就是三个人手里握着同一个真相的三个版本。

第二个错误是把 Agent 当作个人工具。一个运行在你的令牌和权限下的 Agent 游离于客户的访问管理流程之外，并且在你离开项目的那一刻就从系统中消失。

第三个错误是用运行中的 Agent 数量来衡量生产力。IBM 将一个小型单元与庞大的 Agent 队伍相配合，并以此对比一个需要约 300 人、耗时 12 到 15 个月的传统项目。

这种对比只有在每个 Agent 的输出都有审核者和配套评测时才有意义；十五个无人检查的流程就是十五个错误来源。

这对你的简历意味着什么

阅读职位描述时，先弄清楚你将是客户现场唯一的工程师，还是多技能团队中的一个角色。这两种工作需要不同的技能组合，所以这个问题值得在第一轮面试中提出。

OpenAI 式的模式需要一个在广泛领域都有资源整合能力、能自主学习业务知识的人。单元模式需要一个能够划定边界、治理 Agent 并完成交接的人。

在简历上，不要只列出你构建了什么。要描述你如何与领域专家协作、如何为自动化组件授予权限，以及你离开后客户能够独立运行什么。

如果你申请的是一个采用单元模式的团队，请为上述每一点准备一个具体的案例。

IBM 写道，一个单元的产能现在受限于最难环节上的资深判断力，而初级员工产出的任务量不再是衡量标准。对 FDE 而言，这种判断力在辅助轮摘掉的那一天接受检验：客户能否靠自己继续前行。
