Palantir 分解面试示例，完整解析

原标题：Palantir decomposition interview example, worked through

FDE Interview Prep · 2026-09-25 · 约 15 分钟读完

摘要

本文以一名候选人在 Blind 上报告的 Palantir 校招分解面试题为例，完整演示一套六步解题方法：题目给出约 8000 条伦敦出租车行程数据（8 列），要求在一周内提出改进司机生活的想法、画出系统组件、设计 API 并写代码。作者强调先澄清关键问题（如 id 是行程还是司机、服务对象是路边扬招还是预约司机），再选定指标（每班次有载分钟数）并设护栏指标，指出数据看不到空驶时间和未满足需求等盲点，最后给出一个每晚批处理生成的“下一站去哪”页面作为 v0，并讨论羊群效应等风险。需注意该候选人最终被拒，文中方法并非 Palantir 官方答案。

要点

  • 题目源自候选人在 Blind 的报告，作者并非官方答案。
  • 先澄清关键问题：id 含义、司机类型、第八列是什么。
  • 指标定为每班次有载分钟数，护栏是其他区域乘客接单量。
  • 8000 条数据粒度太细时每格不足 1 条，v0 须粗分组。
  • v0 是每晚重建的去向推荐页，首要风险是羊群效应。

你已经读到，面试官希望你澄清问题、界定范围并交付一个小型的第一版。下面是一位候选人报告的 Palantir 面试提示的实际样子：一份伦敦出租车行程样本，以及一个改善司机生活的建议请求。来源 1Palantir 学习与拆解面试（Blind）发布平台Blind来源类型Blind 上的候选人报告 下面我们用六步方法端到端地完成这道题，并给出每一步应该大声说出的措辞。关于整个环节，请阅读我们的拆解面试指南。

一分钟版答案：

  • 澄清： id 是行程还是司机，以及是哪些司机（路边扬招还是预约）？
  • 指标： 每班次每小时的有载分钟数，以其他地方的乘客接单量作为护栏指标。
  • v0： 一个“接下来去哪儿”页面，每晚根据各区域和时段的接客数据构建。
  • 风险： 羊群效应，因此要展示多个区域的分布，而不是单一最优区域。
  • 周一： 向数据负责人索要司机 ID，以便测量空驶时间。

澄清：是哪些司机，以及在什么方面做得更好

“改善司机的生活”可能意味着每小时赚更多钱、更少的空驶里程、更短的班次或更安全的夜晚，而每一种都会导向不同的产品。Palantir 告诉现场面试的候选人，要讲清楚他们打算如何处理分析和技术问题，并在必要时提出问题。来源 3Palantir Careers | Getting Hired发布方Palantir来源类型公司招聘页面 在我们的方法中，你只提出那些答案会改变你所构建内容的问题，然后果断做出决定。

在这里能通过这一检验的问题：

  • 第八列是什么？ 海报上只列了七列。如果它是司机 ID 或车辆 ID，你就能衡量空驶时间，整个设计都会随之改变。
  • 是哪些司机？ 路边扬招出租车司机可以选择在哪里巡游和等候。而接预订订单的司机大多只能去订单指定的地点。“在哪里等候”工具对前者有帮助，对后者几乎没用。
  • id 是行程还是司机？ 司机 ID 能让你看到同一司机各次行程之间的间隔，也就是他们的空驶时间。行程 ID 则做不到这一点。
  • 这是谁的数据？ 是车队运营商、司机应用，还是城市数据集？数据的所有者决定了你一周内能把产品交付给谁，以及可以向他们展示什么。
  • 位置是什么，覆盖什么时间段？ 是坐标还是命名区域，是一周还是一年：每一种情况都会改变你的分组方式。

可以这样表述：

“在选定方案之前，我有几个会改变我构建内容的问题。你说有八列，但我只看到七个名称。第八列是什么？这些是路边扬招出租车还是预订行程？id 是行程还是司机？还有，你说改善司机的生活，是指每小时收入，还是像更短的班次之类的？”

如果面试官回答“你觉得呢？”，不要再追问。大声说出你的决定，并标注假设：

“我假设这是路边扬招出租车，id 是行程 ID，第八列是类似车辆类型的字段，而不是司机 ID，位置是命名区域，数据涵盖几周的时间。我将把‘更好’定义为班次内每小时有更多的有偿工作时间。这些假设都写在白板上了；如有不对请指正。”

一位带有 Palantir 标签、自称曾在那里工作过的 Blind 用户在 2025 年 3 月写道，糟糕的分解表现意味着不提问、不做澄清就做出重大假设、在动手之前误解问题、给出不切实际的方案，以及不对最初的 v0 进行扩展。来源 2Update: interview experience - Palantir new grad FDSE interview (Blind)发布方Blind来源类型Blind 上的候选人报告来源 4Palantir FDSE Interview (Blind)发布方Blind (Teamblind)来源类型Blind 上的候选人报告 标注假设可以解决其中的第二项：你仍然会做出假设，但会让面试官看到并纠正它们。我们的免费课程开放式环节与一页纸方法用一个简短的案例展示了完整的流程。

利益相关者：司机、乘客以及数据的所有者

一个司机工具影响的不只是司机。请逐行列出每个人群：

  • 司机。 即用户。一个让他们空驶很长一段路去“热门”区域的工具，只会让他们的日子更糟。
  • 乘客。 如果所有出租车都涌向同样的区域，其他地方的等待时间就会变长；而且他们的上车和下车地点可能暴露他们住在哪里，所以司机只能看到汇总数据。
  • 数据所有者。 提供这些数据的人决定是否允许访问，以及司机可以看到什么。

然后选定一个数字，并为它设置护栏指标：

“成功指标是使用该工具的司机与未使用的司机相比，每班次每小时的有薪分钟数。护栏指标是我们引导司机离开的区域中的乘客接单量，这样司机就不会通过让其他区域无车可打而获益。”

现在注意这个问题：如果

id

是行程 ID，这些数据行根本无法衡量该指标。大声说出来；这将成为你的下一步。

数据：这些列能告诉你什么、不能告诉你什么

在设计任何东西之前，先把各列读一遍。一位参加过 Palantir 面试的人在 2022 年 7 月在 Blind 上写道，“澄清问题和数据模式/数据来源非常重要。” 来源 2更新：面试经历 - Palantir 应届生 FDSE 面试（Blind）发布者Blind来源类型Blind 上的候选人报告来源 4Palantir FDSE 面试（Blind）发布者Blind (Teamblind)来源类型Blind 上的候选人报告 以下是在这份数据上的具体体现。

列能告诉你不能告诉你
fare每次行程的收入小费、附加费、运营成本
起点位置和时间接单发生的地点和时间人们在何处等待却没有等到车
终点位置和时间司机空车后最终到达的地方他们接下来去了哪里

这种逐列阅读的练习是我们数据集优先的提示词课程的核心。

三个盲区最为关键：

  • 空驶时间。 司机最辛苦的时间是两单之间的时间。而这些数据只记录有收入的时间。
  • 未被满足的需求。 一次接单只显示出租车与乘客相遇的地方，而不是乘客在雨中等待的地方。这份数据只是司机已经去过的地方的地图。
  • 供给。 一个挤满等待出租车的繁忙区域，可能比一个没有车的安静区域更糟，而数据行两者都体现不出来。

然后在最初几分钟内检查数据行中的陷阱：

  • 零距离或零分钟的行程，可能是测试或取消的订单；
  • 跨越午夜的行程，因此要按开始时间分桶；
  • 机场订单，其金额大到足以拉偏任何平均值，所以要用总和或中位数，并说明用的是哪种；
  • 时钟：时间是否为当地时间，以及夏令时切换时会发生什么。

接下来，一个决定设计的数字。一位候选人报告了 8,000 条记录。来源 1Palantir Learning & Decomposition Interview (Blind)发布者Blind来源类型Blind 上的候选人报告 摊薄开来，几乎什么都没有：

50 zones x 168 hours = 8,400
8,000 / 8,400 = under 1
10 areas x 5 bands = 50
8,000 / 50 = about 160

所以 v0 粗粒度分组：少数几个区域和时间段，而不是每条街每小时。把它说成一个决策：“在细粒度下每个单元格不到一单行程，所以我会按少数几个区域和时间段分组，并展示每个数字背后有多少单行程支撑。”

如果被要求写代码，核心步骤很清晰：分箱和聚合。以下是在一个带有报告列的小型虚构样本上运行的结果：

import pandas as pd

t = pd.read_csv("trips.csv",
    parse_dates=["start_time", "end_time"])
secs = (t.end_time - t.start_time)
t["mins"] = secs.dt.total_seconds() / 60
ok = (t.mins > 0) & (t.distance > 0)
t = t[ok & (t.fare > 0)].copy()
t["band"] = pd.cut(
    t.start_time.dt.hour,
    [0, 7, 10, 17, 21, 24], right=False,
    labels=["night", "am", "day",
            "pm", "late"])
g = t.groupby(["start_location", "band"],
              observed=True)
cells = g.agg(trips=("id", "count"),
              fare=("fare", "sum"),
              mins=("mins", "sum"))
cells["per_min"] = (
    cells.fare / cells.mins).round(2)
top = cells.sort_values("per_min",
                         ascending=False)
print(top[["trips", "per_min"]])

在我们的样本上输出如下：

Heathrow       am        2     1.10
Soho           late      3     0.62
Kings X        am        2     0.59

过滤器删掉了一行零时长、零车费的记录；要提到这一点。然后说出能赢得这一轮的关键：希思罗机场早间的每付费分钟收益看起来最好，却是页面上最具误导性的一行。数据看不到司机在机场接单前排队的等待时间，所以付费率美化了它。关于附带数据集的拆解面试的文章会更深入地讲解如何读出每列数据背后的陷阱。

一个小到足以交付的第一版

Palantir 关于开放式问题的页面说要阐明备选方案和权衡，得出一个具体的方法，并“先交付一个可运行的想法，之后再扩展”。来源 5Palantir Careers | Navigating Open-Ended Questions发布者Palantir Technologies来源类型公司招聘页面 把一周的时间限制当作展示这条建议的机会。一口气说出你考虑过哪些想法以及为什么放弃它们：

想法所需数据适配这些列吗？
下一步去哪等按地点和时间的上车记录是
班次规划器司机 ID 和班次日志否
路线建议GPS 轨迹否
调整车费对车费的控制权不是司机能掌控的
“我考虑过班次规划器和路线建议。两者都需要我们没有的数据。下一步去哪恰好用到这些列，所以这就是 v0。”

现在描述行走骨架：能端到端运行的最精简版本，服务一个真实用户做出一个真实决策。

  • 用户：一位刚送完乘客的街头扬召司机。
  • 决策：去哪里接下一单。
  • 真实的：按区域和时间段统计的上车数、付费分钟数和车费，来自行程数据。
  • 模拟的：任何实时内容。它是一张每晚重建的表，区域边界是手工绘制的。
  • 它能验证的：遵循它的司机是否比不遵循的司机等待时间更短。

组件图，画得小到能放进手机屏幕或白板一角：

“v0 是司机在完成一单后打开的一个页面：从这里、在这个时间出发，一份按每小时接单数排序的附近区域简短列表，附带付费费率以及每个数字背后的行程数。一个夜间任务构建这张表，一个接口提供数据。它能在一周内完成，因为没有任何实时功能。”

Pro 课程《The walking skeleton》讲解了第一版中哪些内容可以模拟，哪些内容绝不能模拟。

需要当面指出的风险与失败模式

指出不同类型的风险，每种都要给出前几周能观察到的信号以及应对措施：

  • 羊群效应。 每位司机都收到相同的首选区域，该区域车辆涌入，推荐就不再准确。信号：推荐区域的每位司机接单数下降。应对：展示一个分布区间，而不是单一赢家。
  • 历史偏差。 数据行反映的是出租车已经去过的地方，所以 v0 可能只是重复今天的习惯。信号：首选区域恰好就是数据行中最繁忙的区域。应对：如实说明，并让试点来检验。
  • 样本稀薄的单元格。 信号：某个单元格的行程数低于 trips_behind 下限。应对：将其隐藏，并在其他每个单元格上显示计数。
  • 隐私。 深夜在住宅附近的接单。信号：任何接单记录可追溯到少数几个地址的单元格。应对：扩大区域范围或删除该单元格；绝不展示单次行程。
  • 过时的模式。 节庆活动、罢工和天气都会让夜间构建的表格失效。信号：建议与实际结果出现偏差。应对：在已知有活动的日子回退显示“未知”。
  • 安全。 一个促使司机延长工作时间或加快节奏的工具是伤害，而不是功能。信号：用户的班次变长。应对：绝不按工作时长排序。
“我最先关注的风险是羊群效应：如果每位司机都收到相同的首选区域，推荐就不再准确。信号是我们推荐区域的每位司机接单数下降，解决办法是展示一个分布区间。”

下一步，以及如何收尾

Palantir 的指南解释了对开放式问题的关注，指出紧迫的现实问题需要在有时间打磨完美之前就拿出可行的解决方案。来源 5Palantir Careers | Navigating Open-Ended Questions发布方Palantir Technologies来源类型公司招聘页面 “能用先行”就是 v0。然后再扩展：一位自称曾在 Palantir 工作过的 Blind 用户表示，没有在 v0 基础上继续扩展是表现不佳的原因之一。来源 2Update: interview experience - Palantir new grad FDSE interview (Blind)发布方Blind来源类型 Blind 上的候选人报告来源 4Palantir FDSE Interview (Blind)发布方Blind (Teamblind)来源类型 Blind 上的候选人报告

  • v1，数据。 向负责人索要司机 ID 以及班次开始和结束时间。这样你就能测量空驶时间，也就是你真正选定的指标。
  • v1，测试。 把页面提供给一部分司机而不提供给另一部分，并比较每小时的付费分钟数。
  • v2，实时。 一旦试点证明这个想法有效，就用近期接单数据替换夜间构建的表格。

当时间快用完时，分四部分收尾：问题、第一版、最大的风险和周一。

“收尾总结：司机在空驶时段赚不到钱，而这些数据行只记录有偿时段。第一版是一个‘下一步去哪里’的页面，每晚按区域和时间段从上车数据构建。最大的风险是羊群效应，所以我们展示一个分散度指标，并观察每位司机的上车次数。周一我会问数据负责人 id 字段能否变成司机 ID，因为这才是让我们能测量空驶时间的关键。”

结合上面的图示、端点和代码片段，这覆盖了题目要求中的每一项：一个想法、组成部件、一个 API 和代码，而且都小到一周内可以交付。

适用于任何提示词的要点

可在任何拆解类提示词上复用的动作

  • 复述题目要求，包括提示词点名的每一个交付物。
  • 找到决定你能测量什么的那个字段，并首先围绕它提问。
  • 在选定想法之前，先列出数据看不到的东西。
  • 做一次规模估算，确定你设计的粒度。
  • 选择契合数据的想法，并说出你放弃的那些。
  • 指出对非用户人群的一种潜在伤害。
  • 以你周一会问的问题收尾。

两个常见错误，以及各自的纠正方法：

  • 在一周内承诺任何“最优”的东西。 承诺的是一份带证据数量的排序清单。
  • 把这篇演练当作标准答案。 要练习的是动作，而不是这个答案。

同样的动作也适用于没有数据的提示词。在 First Round Review 于 2026 年 2 月发布的一次访谈中，Palantir 的前招聘负责人举了一个示例场景：向候选人解释内幕交易，并要求他们设计一个解决方案，包括需要什么数据以及会向客户问什么问题。来源 6So You Want to Hire a Forward Deployed Engineer发布方First Round Review来源类型新闻报道 我们关于内幕交易面试题的文章详细解析了这道题。

在一道你没见过的题上练习

拿一道同类型的免费题目，用计时器跑完每一步：用健身应用事件数据构建一个功能 附带可供阅读的数据行，提升城市公交可靠性 是出租车题最接近的同类题，而不增加人手缩短结账队伍 则完全没有数据集。每道题都有参考答案供你对照。

然后大声跑一遍同样的六个动作，对象是一个会回应你的人。/try 上的建筑许可案例是免费的：登录后，与一位只会回答你所问内容的模拟客户一起界定一个模糊问题，然后查看你的评分卡。数一数你在没有提示的情况下完成了多少个清单上的动作。

拆解环节一种开放式面试，你需要从一个有多种可能解法的模糊问题出发，边思考边表达，最终得出一个具体方案和第一个可运行版本。
