构建持久耐用的语音 AI Agent：来自 FDE 的经验教训

原标题：Building voice agents that last: Lessons from FDEs

ElevenCreative · 2026-04-02 · 约 13 分钟读完

摘要

ElevenCreative 以前沿部署工程师的实战经验为基础，讲解如何构建可持续运行的语音 AI Agent。文章指出传统软件与核心编排器的差异，强调以评测驱动开发、分阶段发布和持续迭代，并以 Revolut 部署为例说明成效。

要点

  • 传统软件可预测，核心编排器需评测与监控。
  • 选择用例应看业务价值而非技术趣味。
  • 先定义成功评测标准与 Agent 测试再开发。
  • 常见失败多为提示词问题而非模型问题。
  • 扩量是信心决策，须分阶段发布验证改动。

收听收听本文

对大多数组织而言，支持职能的点状解决方案长期以来一直以“偏转率”来衡量，即减少来电量并尽量减少人工客服的介入。但偏转并不等于解决，两者之间的差距正是客户体验崩坏之处。要弥合这一差距，AI Agent 不仅需要访问数据，还需要访问执行操作所需的系统。这样，AI Agent 就能处理退款、引导客户完成结账流程，并在情况需要时带着完整上下文转接给人工客服。这使企业能够大规模处理客户交互，在显著减轻人工支持团队负担的同时，改善通话双方的体验。在与全球服务 7000 万客户的金融科技公司 Revolut 的近期部署中，这意味着问题解决时间缩短了 8 倍，通话成功率达到 99.7%。

组织必须以迭代的方式应对这种规模的变革，紧密围绕公司的核心使命，并得到高层的强力支持。在技术层面，对非结构化环境进行推理存在固有风险，必须谨慎管理。赋予 AI Agent 在客户关系管理（CRM）系统中操作、在销售点系统中修改订单或升级案例的能力，意味着治理模型与模型本身同等重要。因此，重点不再是 AI Agent 能否胜任实际工作，而是需要哪些机制才能安全、可重复地部署它们。

在本文中，我们基于自身经验，分享从首次部署到扩展至组织整个客户运营体系的成功 AI Agent 的关键要素。

交付 AI Agent 与交付软件的区别

在深入探讨 AI Agent 构建之前，值得将语音 Agent 的部署与企业数十年来一直在做的传统软件进行对比。从这个视角来看，AI Agent 可以分为两个不同的组成部分：传统软件和核心编排器。

软件

核心编排器

传统软件组件的主要目标是提升 Agent 的交付与性能。对于 ElevenAgents 而言，这包括版本管理、A/B 测试、电话功能和首条消息配置等功能。这些组件在部署后几乎不会发生漂移，因此其行为具有高度可预测性。通过稳健的工程实践，组织可以快速基于这些功能进行构建，并通过一套严格的指标、追踪和日志体系，深入掌握其生产环境中的表现。这一层的延迟优化遵循成熟且明确的模式：缓存、连接池、基础设施扩容和协议优化都是结果可确定、效果可靠的手段。

核心编排器组件本质上更难预测，但它们决定了 Agent 的运行时表现，既包括回答质量，也包括感知延迟。与传统软件不同，这些组件处理的是自然语言和音频，其输入空间实际上是无限的，措辞、上下文、背景噪音或用户行为的细微变化，都可能随时间产生显著不同的输出。这使得仅靠传统测试方法是不够的：一个 Agent 可能在数百个测试用例中表现完美，却仍会在生产环境中以难以预料的方式失败。

这一层的延迟也更不确定，受模型推理时间、音频伪影的注入、工具调用链以及生成式系统固有的变异性影响。管理好这些组件需要一种不同的方法论：围绕评测框架和生产监控来构建，并愿意基于真实对话数据（而非仅仅依赖部署前的假设）持续迭代。

这一区别决定了组织应如何推进采用：从组织相关但风险较低的用例入手，随着对系统信心的增长，再稳步扩大规模。

发布周期

选择探路者

对于刚开始采用语音 Agent 的团队来说，选择合适的探路者是最重要的早期决策之一。而且，这件事与技术的关系远比大多数人预期的要小。那些能够快速取得早期成功、避免陷入无休止 POC 泥潭的团队，往往有一个共同点：他们能够清晰地回答以下几个问题。

  • 这个用例如何带来可衡量的业务价值？起步的正确用例不是技术上最有趣的那一个，而是最有可能在业务已经关心的结果上产生实际影响的那一个。这通过收入影响、成本降低、客户满意度以及管理层已经在跟踪并对其负责的其他指标来衡量。如果没有这种与业务价值的直接关联，就很难证明让 AI Agent 达到理想效果所需的迭代周期是合理的，势头很可能在技术有机会证明自己之前就停滞下来。
  • 用户是否能立即清楚了解 AI Agent 的范围和用途？范围模糊是从开发到生产过程中最常见的偏差来源之一。不了解 AI Agent 能做什么、不能做什么的用户，会以评测套件从未预料到的方式试探其边界。一个范围界定清晰的 AI Agent 会从第一条消息开始就设定预期，并妥善处理超出范围的请求。
  • 良好和糟糕的交互是什么样的，能否将它们编成一套具体的评测标准？良好的交互不仅仅是 AI Agent 完成了任务，还包括用户感到被倾听、升级发生在正确的时机，以及结果与业务意图一致。评测标准分为两类：由平台捕获的量化指标（如任务完成率和升级率），以及需要分析对话本身的基于对话记录的标准。尽早定义基于对话记录的标准，可以为团队提供一个具体的建设目标。它们还设定了一个自然的上线门槛。当你的 AI Agent 能够持续通过其评测标准，且平台指标已经稳定时，你就有信心进入生产环境。如果没有定义好的标准，上线就只能靠主观判断。
  • 性能与控制之间的权衡是什么，在这个阶段哪个更重要？赋予 AI Agent 的自主权越多，交互就越自然灵活，但超出已验证边界的风险也越大。通过受限提示和更严格的升级逻辑来加强控制可以降低这种风险，但可能让 AI Agent 显得僵化。两个极端都不可取。过早锁死的组织最终只会得到一个美化版的 IVR。而在建立信任之前就推进太快的组织，则会造成得不偿失的支持负担。理解这个调节旋钮在成熟的每个阶段应处于什么位置，将决定模型配置、升级逻辑，以及 AI Agent 的知识有多少放在提示中、多少放在检索或结构化数据源中。

回答了这些问题之后，组织就可以从战略转向执行，开始规划构建工作。

为初始构建打好基础

进入执行阶段时，团队可以借鉴几乎与软件本身一样古老的方法论。测试驱动开发（TDD）为在整个构建过程中保持 Agent 与核心指标一致提供了框架。

具体而言，开发团队和业务利益相关者应共同定义并构建两个基础性产物：成功评估标准，用于确立在单次通话和整体层面什么才算“好”；以及 Agent 测试，用于反复验证 Agent 应表现出的特定行为。前者最好通过审查真实的人工通话来形成。后者则逐步构建，从一组初始预期行为开始，随着新行为的引入和边界情况的发现而不断扩展。

有了初始测试集之后，Agent 开发从系统提示词开始。这里定义了 Agent 的规则、语气和方法：它应该做什么、不应该做什么，以及在角色边界处应如何表现。一个精心设计的系统提示词既关乎结构，也关乎内容。将指令划分为清晰标注的章节、把相关指引放在一起、避免条件式措辞，这些都会对 Agent 行为的一致性产生实质性影响。在这个阶段，我们常常会回到提示词指南。

与系统提示词一起配置的还有 Agent 的核心组件：LLM、文本转语音（TTS）模型和语音。LLM 的选择主要是延迟与性能之间的权衡——为速度优化的模型通常会牺牲一定的推理能力，反之亦然。对于 TTS，正确的选择取决于用例最看重什么，是富有表现力的演绎、低延迟，还是多语言支持。而语音的选择既是技术决策，也是品牌决策。它塑造了组织给每位来电者的印象，使其成为少数几个与构建 Agent 的工程师同样属于品牌和营销团队的配置决策之一。这意味着语音选择可以与开发过程的其他部分并行进行，而不必成为开始或结束时的瓶颈。ElevenAgents 提供超过 10,000 个语音可供选择，如果没有合适的，团队还可以克隆或创建自己的语音。

在此基础上，Agent 还可以可选地扩展知识库、工具和渠道配置。每一项新增都会解锁新能力，但也会引入新的需要测试的范围。无论是电话集成、访问外部数据库，还是代表客户采取行动的能力，在扩大范围之前，这些决策都值得对照评估标准进行压力测试。添加工具时，系统提示词和工具描述会明确说明何时以及如何调用每个工具，从而使 Agent 在正确的上下文中一致地使用它们。

在这些基础就绪之后，这个 AI Agent 就可以接受检验了。

迈向生产就绪

当在落地阶段定义的测试和评测标准开始针对已构建的 AI Agent 运行时，开发就变成了一个紧密的循环：增加更多测试、识别失败、更新系统提示词或配置，然后再次运行。在这个阶段，大多数失败并非模型失败，而是提示词失败。一条在孤立状态下看似清晰的指令，当 AI Agent 在对话中途遇到它时，往往会显得含糊不清。初始测试套件未曾预料的边缘情况也会浮现出来。每一个这样的案例都可以直接从对话本身创建为一个新的 Next Turn 测试。何时停止迭代这个问题有一个具体的答案：当 AI Agent 在多次运行中都能稳定通过其评测标准，并且任务完成率和转人工率等平台指标已稳定在可接受范围内时。这正是为什么在构建之前定义这些标准如此重要。没有它们，就绪与否就变成了主观判断，而终点线也会不断移动。

在实践中，大多数团队发现，一小部分反复出现的失败模式占了问题的绝大多数。最常见的是提示词歧义，即 AI Agent 收到相互冲突或描述不足的指令，从而默认表现出不可预测的行为；工具误用，即 AI Agent 在错误的上下文中调用工具，或在该调用时未能调用；以及转人工漂移，即 AI Agent 要么过于激进地转人工，要么紧紧抓住本应移交的对话不放。每一种都有提示词层面的修复方法。收紧相关指令、添加明确的示例，或调整转人工阈值，通常就足够了。风险在于没有在上线之前发现这些问题。

团队在这方面最常见的错误，是把通过测试套件当作保证，而不是一个信号。一个只覆盖正常路径的测试套件很容易通过，但意义甚微。覆盖拒绝场景、对话中途转向、模糊输入以及重度工具交互，才能让结果具有分量。同样，跳过仿真测试、只依赖轮次级测试的团队，会错过一类只在完整对话中才会出现的失败，例如上下文漂移，即 AI Agent 忘记了较早的轮次；或者错误累积，即通话早期的一个小失误逐渐累积成糟糕的结果。一旦反复出现的失败模式得到解决，并且 AI Agent 能够优雅地（而非完美地）处理长尾边缘情况，在预发布环境中继续迭代的边际价值就会递减。到那时，更有价值的信号来自真实对话。

上线并不意味着迭代结束，而是意味着学习的重心从合成测试转移到生产对话记录。定义上线标准的评估指标成为衡量线上表现的基线，迭代循环由此继续进行。

反馈循环、评估，以及何时停止迭代

一旦测试定义完成并开始运行，流水线中的缺口很快就会显现。通过对话分析，团队可以精确定位交互出错的具体时刻，并利用这一信号创建新测试，明确需要修改的地方。最常见的干预手段是提示词层面的：收紧工具调用描述、为边缘情况添加更明确的指令，或澄清在实践中被证明含糊不清的升级条件。在某些情况下，问题出在更深层，如果延迟或推理质量达不到用例的要求，则需要重新审视底层模型配置。

这个阶段最重要的原则是验证变更，而不是想当然。一个修复某个故障的改动可能会悄悄引入另一个故障。ElevenAgents 支持版本管理，允许团队在向更大范围的用户推广之前，先在一小部分用户上测试新迭代。这样可以确认改进确实带来了更好的结果，而不是把故障模式转移到了别处。

可能出现的问题

这个阶段最严重的错误是跳过分阶段推广，直接把变更推送给全部用户。没有分阶段推广，你就失去了隔离任何单一变更影响的能力；而在大规模场景下，这会让你几乎无法理解究竟是什么在驱动平台指标的改善或退化。把全部用户当作测试环境不仅有风险，还会让你失去做出后续可靠决策所需的可观测性。

除了推广策略之外，还有两种失败模式值得警惕。第一种是过度关注近期故障。当一次高关注度的对话出现问题时，人们自然会想立即、大范围地打补丁，但未经完整测试套件验证就做出的被动提示词修改，往往会导致原本稳定的行为出现退化。每一次变更，无论多么微小，都应被视为一次新迭代并进行相应测试。第二种是评估漂移。随着时间推移，团队可能会在不知不觉中降低通过测试的标准，尤其是在交付压力之下。在范围界定阶段定义的评估标准应当始终作为锚点。如果这些标准开始显得过于严格，正确的做法是重新审视并有意识地更新它们，而不是让标准在无形中被侵蚀。

自信地扩展规模

增加流量是一个基于信心的决策，而不是基于时间的决策。扩展的信号是：Agent 在多次测试运行中持续通过评测标准、平台指标已经稳定，并且分支灰度发布相对对照组没有出现明显的性能回退。

在这个阶段，一个常见的问题是：多少流量才足以得出结论。每个分支少于 100 次调用的批次会产生过大的方差，无法可靠地评估结果。25 次调用中 60% 的通过率和 100 次调用中 60% 的通过率，代表的置信水平截然不同。除了达到一定的数量之外，批次还应足够大，以覆盖真实输入的完整范围，包括可能的边缘情况、不常见的意图，以及只有在高流量下才会出现、在小样本中很少显现的失败模式。

更多的流量会同时放大有效和无效的部分。在核心失败模式得到解决之前进行扩展，会造成难以挽回的支持负担。

循环往复

知道何时停止与知道要修复什么同样重要。迭代存在边际收益递减，暂停的正确信号是 Agent 能够持续达到在范围界定阶段设定的评测标准。到那时，进一步的改动带来的风险大于收益。

“持续达到标准”的具体表现因场景而异。数据访问受限或集成不完整的团队，在这些问题解决之前，可能会发现 50% 左右的转人工率就是现实的上限。在数据访问能力强的场景中，表现最好的部署通常以任务完成率高于 80%、转人工率低于 20% 为目标。比任何单一数字更重要的是稳定性：在生产流量中连续数周保持一致的表现，且多次测试运行之间没有明显回退，才是真正的信号。当下一次迭代的边际收益小于回退风险时，就该停止了。

这并不意味着工作已经结束。当出现新的需求时，流程会从头开始。第一次构建时的范围界定问题，对第二次构建同样适用。不同的是，进入第二个周期的团队已经拥有测试套件、评测基线和运营经验，而第一个周期必须从零开始建立这些。这种复利式的优势，正是那些从语音 Agent 中获得持久价值的组织与那些始终停留在概念验证阶段的组织之间的分水岭。

结论

我们看到那些成功弥合“拦截”与“解决”之间差距的团队，都是在开始构建之前就定义好“好”的标准、在整个迭代周期中保持纪律，并把每次部署都当作下一次部署的基础的团队。对话式 Agent 不是一次性的部署——真实的对话会暴露出任何测试套件都无法完全预见的边缘情况，而改进的工作在上线之后也不会停止。

ElevenAgents 正是围绕这一现实而构建的。Agent 测试、对话分析和分支发布是将概念验证转变为真正能大规模解决客户问题（而不仅仅是 deflect）的系统的基础。这正是值得弥补的差距。
