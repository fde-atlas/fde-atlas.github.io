AGI 与 AI Agent：FDE 如何界定“AI 员工”

原标题：AGI vs AI agents: how FDEs scope the "AI employee"

FDE Times · 2026-10-08 · 约 7 分钟读完

摘要

文章讨论前沿部署工程师如何应对客户提出的“AI 员工”需求。作者指出，客户想象中无所不能的 AI 员工实际上接近 AGI 的定义，而 AGI 至今仍是理论概念；FDE 真正能交付的是由 LLM、工具、记忆组装而成的 Agent。文章引用 Anthropic 的工具使用文档说明：模型只提出调用请求，实际执行由应用完成，且能力取决于接入了哪些工具。作者给出一张对照表，把客户的常见期望转化为可落地的范围问题，并以退款 Agent 为例：缺失参数时模型可能编造合理值，需设计成必须询问用户；每步 95% 正确率的十步流程整体正确率仅约 60%，说明自主性越高错误越易累积。结论是先做固定工作流，再按数据逐步放权。

要点

  • “什么都能做的 AI 员工”即 AGI，仍是理论，无法购买或部署。
  • 模型只提出工具调用，执行由应用完成，能力取决于接入的工具与权限。
  • 缺失参数时模型可能编造合理值，系统应设计为必须向用户询问。
  • 每步 95% 正确率的十步流程整体仅约 60% 正确，自主性带来累积错误。
  • 先从固定工作流入手，按沙盒数据逐步授予更多自主权。

高管们想象中的东西接近 AGI 的定义，而 AGI 仍停留在理论层面；FDE 的职责是把这种期望转化为一个设计方案，同时不扼杀它。

简而言之

  • 客户所描述的“无所不能的 AI 员工”就是 AGI。按照通常的定义，AGI 仍属理论概念，并不是任何人都能买到的产品。
  • 一个 Agent 能做什么，取决于工程团队接入的工具以及这些工具的描述方式。模型只负责提出调用请求；由应用程序来执行它们。
  • 从最简单的方案开始，通常是固定的工作流，之后再逐步增加自主性，因为自主性会带来更高的成本和不断累积的错误。

1965 年，Herbert Simon 预言，在二十年内，机器将能够完成人类能做的任何工作。六十多年过去了，这一承诺以一个新名字延续至今：“AI 员工”。

每一位 FDE 迟早都会遇到这样的时刻。客户方的高管看了几场演示，读了几条新闻标题，然后就会问：他们什么时候能拥有一个能独立处理一切事务的 AI 员工。这是一个合理的问题。

问题在于，这个问题把两种截然不同的东西混为一谈，除非在第一次会议上就把它们区分开，否则项目将按照一个当今任何系统都无法达到的标准来评判。

客户想象的是 AGI。FDE 能交付的是 Agent。两者之间的差距不会因为等待更智能的模型而缩小，只能通过设计来弥合，而这份设计正是 FDE 与客户共同制定的。

“无所不能”早已有一个名字，而且它仍然只是假设

Wikipedia 将 AGI 定义为一种假设形态的人工智能，它能在几乎每一项认知任务上达到或超越人类。关键词是“假设”。一个能处理一切事务的 AI 员工几乎逐字符合这一定义，这意味着它还不是任何人都能购买或部署的东西。

如今在企业中运行的是窄 AI，或称弱 AI：它能解决特定问题，但不具备通用认知能力。这就是 FDE 将要部署的系统与高管脑海中想象之间的距离。

争论 AGI 何时到来是一个陷阱。Simon 的预言错了。Geoffrey Hinton 曾表示 AGI “还要 30 到 50 年，甚至更久”，随后又自己大幅修正了这一数字。当该领域的领军人物之间存在如此大的分歧时，争论时间表只会让会议偏离正轨。

应该改用这样一句话：那东西还不存在，而这是我们这个季度能构建的东西。

真正交付的是 Agent，由各个部件组装而成

DAIR.AI 的 Prompt Engineering Guide 将 Agent 定义为一种使用 LLM 的系统，旨在自主行动并解决复杂任务。Agent 的存在有其实际原因：当任务需要多个步骤、规划和推理时，单独的 LLM 会力不从心。

因此，需要为它赋予规划与自我审查能力、工具访问权限以及记忆。

所谓“AI 员工”，其实是工程师拼装出来的一套组合体，背后并没有一个通用的智能，而且这套组合体的每个部分都有各自的局限。

Anthropic 的工具使用文档清楚地展示了这些局限有多具体。Claude 自己不会执行任何操作。它返回一个结构化的调用请求，然后要么由开发者的应用程序来执行（客户端工具），要么由 Anthropic 来执行（服务器端工具）。

模型只有在请求匹配工具所描述的能力、且答案不在上下文中时，才会调用工具。

这句话为整个对话奠定了基调。它把问题从“AI 够不够聪明？”转移到“我们要把它连接到哪些系统、赋予什么权限？”，而客户方的管理者可以对第二个问题做出决策。

从客户所说的话，到 FDE 应该反问的问题

下表将常见的期望与系统的实际行为一一对应。最后一列是把期望转化为工作范围的反问。

客户所说系统实际做什么FDE 应该反问什么
“它知道该做什么”只有当请求匹配已描述的能力时才调用工具“你最希望它做的头三件具体事情是什么？”
“它能自己接入我们的系统”模型只提出调用请求；由我们的应用程序来执行“涉及哪些系统？读权限还是写权限？由谁负责？”
“如果信息缺失，它会自己想办法”当必需参数缺失时，模型可能会推断出一个听起来合理的值“哪些字段必须始终向用户询问？”
“就让它自己决定吧”自主性越高，成本越高，错误也更容易累积放大“哪些步骤必须经过人工审批？”
“现在就做完整版”从最简单的方案开始，只在必要时才增加复杂度“流程中哪些部分已经固定、可以直接写成代码？”

第三列正是 FDE 的价值所在：阅读技术文档，并将其转化为帮助客户决策的问题。这就是这份工作的核心技能。

一个具体案例：退款 Agent

以一家虚构的零售连锁企业为例，它想要一个“AI 客服员工”来同时处理退款。这个 Agent 拥有三个工具：查询订单、查看退货政策、执行退款。一位客户写道：“我想退回我上周买的鞋”，却没有提供订单号。

Anthropic 的文档警告说，当必需参数缺失时，模型可能会推断出一个听起来合理的值。在这里，“合理”可能意味着另一位客户最近的一笔鞋类订单。人类员工会主动询问。而使用 Agent 时，不要听天由命：要在系统设计上让它必须询问。

然后是误差累积问题，Anthropic 直接将其点名为自主性的代价。这是一个说明性的算术，而非实测数据：如果 Agent 的每一步有 95% 的正确率，那么 10 个顺序步骤组成的链条完全正确的概率只有约 60%（0.95 的 10 次方 ≈ 0.599）。

这个数字足以让高管明白，为什么“直接让它自己决定”是一个有风险的决策。

出路在于 Anthropic 对两类系统的区分。工作流通过预定义的代码路径来编排 LLM 和工具。Agent 则让 LLM 自主引导自己的流程。对于退款场景，订单查询和政策检查已经是固定步骤，所以把它们写成工作流是合理的。

只有理解客户的消息和起草回复才需要模型的灵活性。

根据 Anthropic 的说法，Agentic 系统往往以延迟和成本换取更好的任务表现。有些场景值得做这种交换；有些则不值得。在这个例子中，退款本身应当需要人工审批，直到沙盒试点数据证明可以放宽为止。

这与 Anthropic 自己的建议一致：在沙盒环境中进行充分测试，并设置好防护栏。

在不泼冷水的情况下说“还不行”

最常见的错误是生硬的反驳：“你想要的是 AGI，没人能造出来。”这话没错，但它扼杀了让 FDE 走进会议室的那份热情。更好的做法是先承认那个目标，然后用三个步骤规划通往那里的路线：

  • 说出客户想象中的东西，并诚实地说明它目前仍停留在理论层面。
  • 一起列出具体的任务，并挑选一个流程清晰的任务，先以工作流的形式构建。
  • 商定里程碑，届时由数据决定是否授予更多自主权。

Anthropic 的建议是找到尽可能简单的方案，只在确有必要时才增加复杂度。把这句话带进会议。它相当于一份有序的计划，是决策者可以批准、跟踪和衡量的东西，而且没有人会把它听成拒绝。

值得练习的技能是把期望转化为范围

许多开发者，无论在越南还是其他地方，都擅长写代码，却很少练习把模糊的期望转化为具体的范围，而这正是 FDE 每天都在使用的技能。练习用销售总监一听就懂的语言来解释 AGI、狭义 AI 和 Agent。

阅读职位描述时，留意诸如“将业务需求转化为技术方案”、“与利益相关者界定范围”或“面向客户”之类的措辞。在简历上，不要只写“用 LLM 构建了 Agent”；要说明你在哪里选择了工作流而非 Agent，在哪里设置了审批步骤，以及为什么。

一个小型个人项目就足够了：一个带几个工具的 Agent，外加一页文档，记录参数缺失的案例以及你如何强制模型进行追问。这一页展示了你如何看待系统的局限，而一个“什么都能做”的演示永远无法揭示这一点。

Simon 的承诺之所以落空，是因为它指望机器自己琢磨出人们想要什么。FDE 的工作正是避免这种赌注：与客户坐在一起，记录下他们需要完成的每一项任务，并为 AI Agent 提供完成每项任务所需的精确工具。
