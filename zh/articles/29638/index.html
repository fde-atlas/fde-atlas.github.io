Amazon Bedrock AgentCore 是什么：安全评审要点

FDE Times · 2026-11-04 · 约 4 分钟读完

摘要

文章面向 FDE，梳理 Amazon Bedrock AgentCore 在客户安全评审中的价值：Runtime、Identity、Observability 三项服务分别回答 Agent 在哪里运行、谁可调用、日志在哪三个问题。文中给出 microVM 与 Instances 两种计算类型的选择建议（会话上限分别为 8 小时和 14 天），并提醒 CloudTrail 目前只覆盖 Gateway 和 Agent Registry，审计存在缺口，应在上线前主动向客户说明。

要点

  • AgentCore 于 2025 年 7 月发布预览版，10 月 13 日正式 GA。
  • Runtime、Identity、Observability 对应安全团队的三个核心问题。
  • microVM 会话上限 8 小时，Instances 最长 14 天且跑在客户账号的 EC2 上。
  • Identity 可对接 Okta、Microsoft Entra ID 等现有 IdP，无需迁移用户。
  • CloudTrail 目前只记录 Gateway 和 Agent Registry，审计缺口需提前告知客户。

Runtime、Identity、Observability 管运行位置、调用权限和日志，缺口决定 FDE 能承诺多少。

要点速览

  • AgentCore 包含多项服务，直接回答安全团队问题的是三项：负责执行的 Runtime、负责认证的 Identity 和负责监控的 Observability。
  • microVM 为每个会话单独隔离，会话最长保持 8 小时；Instances 运行在客户账号内的 EC2 上，会话最长保持 14 天。
  • 遥测数据以 OpenTelemetry 标准导出并存储在 CloudWatch，但 CloudTrail 目前只记录部分能力。

AWS 于 2025 年 7 月 16 日发布 Amazon Bedrock AgentCore 预览版，2025 年 10 月 13 日正式发布（GA）。产品页用一句简短的口号概括它：任意框架、任意模型、规模化安全。

对前线部署工程师（FDE）来说，口号不如第三次客户会议上听到的问题重要。到那时，提示词已经稳定，演示也能跑通。坐在对面的换成了安全团队，他们会问三件事：Agent 在哪里运行？谁可以调用它？出了问题去哪里看日志？

AgentCore 用三个组件回答这三个问题：Runtime、Identity 和 Observability。弄清楚每个组件能做什么、暂时还做不到什么，在客户的 AWS 上从试点走向生产环境就会快得多。

它能做什么，不承诺什么

AWS 文档把 AgentCore 描述为一个模块化平台，用于构建、部署和运行 Agent。它支持任意框架和任意基础模型，无需自行管理基础设施。

销售 AgentCore 实施服务的合作伙伴 Mission Cloud 称，该平台由七项托管服务组成。这家合作伙伴这样说有商业利益，因此“七项”应视为它自己的统计口径。

本文没有覆盖整个产品，只挑出与安全团队三个问题对应的三项服务。另外两项能力 Gateway 和 Agent Registry，只在下文审计部分出现。

Runtime 不要求丢掉已有代码。Agent 可以用任意框架编写，并通过模型上下文协议（MCP）或 Agent 间协议（A2A）与工具或其他 Agent 通信。所以，如果客户已经有 Agent，第一步是迁移它的运行位置，而不是重写。

一个例子：选对计算类型

假设你在为一家物流公司工作，需要把两个 Agent 推向生产环境。第一个是仓库员工的助手，每次问答会话只持续几分钟。第二个在夜间对账，每次运行约 10 小时。

Runtime 提供两种计算类型。使用 microVM 时，每个用户会话运行在独立的 microVM 中，CPU、内存和文件系统彼此隔离。会话结束后，microVM 随即销毁并清理。两名仓库员工因此永远不会共用同一个环境，这种类型很适合第一个 Agent。

第二个 Agent 则不同。microVM 会话最长 8 小时，10 小时的任务会在第 8 小时被中断。Instances 允许会话最长 14 天，运行在客户自己账号内、由 AWS 托管的 EC2 基础设施上。这通常正是合规团队想听到的。

所以，选择计算类型前要实测会话时长，不要靠猜。需求调研阶段一个数字出错，就可能导致整个架构推倒重来。

Identity：客户无需更换 IdP

Runtime 内置的认证由 AgentCore Identity 负责。每个 Agent 都有自己的身份，系统可以对接企业已在使用的身份提供商（IdP），例如 Okta、Microsoft Entra ID 或 Amazon Cognito。据 AWS 介绍，客户无需把用户迁移到新系统，也无需重建登录流程。

向客户介绍时，应该先讲这一点。在物流的例子中，仓库员工用日常使用的 Okta 账号登录，而对账 Agent 拥有独立身份，与人的身份分开。

可观测性开箱即用，审计仍有欠缺

AgentCore 以兼容 OpenTelemetry 的格式导出遥测数据，因此数据可以接入客户现有的任何监控体系。指标、span 和日志存储在客户账号下的 Amazon CloudWatch 中。现成的仪表盘展示会话数、延迟、token 用量和错误。

审计是需要小心的地方。AWS 文档明确写道，CloudTrail 目前只覆盖部分能力，具体是 Gateway 和 Agent Registry。银行或医院可能要求每一次 API 调用都留下记录。遇到这种情况，要在会上当场提出这个缺口，不要让客户在上线后才发现。

安全评审之前，先做一张表：一列写客户的审计要求，另一列写 CloudTrail 目前记录的内容。把这张表带进会议室，远比承诺“AWS 全都管好了”更能赢得信任。

迁移 Agent 到 AgentCore 的三个常见错误

第一个错误是凭感觉估计会话时长。一个你以为跑 6 小时、实际拖到 9 小时的任务会超过 microVM 的 8 小时上限，而这类故障通常要等客户的真实数据开始流入才会暴露。

第二个错误是因为接入了 CloudWatch 就承诺完整审计。遥测帮助你调试；合规团队关心的是 CloudTrail，而它目前还没有覆盖所有能力。

第三个错误是为了“适配”平台而重写客户的 Agent。Runtime 接受任意框架和模型，精力应该放在 Agent 的运行位置、身份和日志上，而不是客户已经验证过的 Agent 逻辑。

先学什么，简历上怎么写

如果刚起步，先学 Runtime：两种计算类型、会话上限，以及如何部署一个用你熟悉的框架编写的 Agent。然后用真实的 IdP 学 Identity，再学在 CloudWatch 中查看 trace。同时学习 MCP 和 A2A，这两个协议并不绑定 AWS。

简历上写一句“用过 AgentCore”几乎说明不了什么。要写清三个决策：你根据实测的会话时长选择了计算类型；你把 Agent 接入了客户的 IdP，并把 Agent 的身份与用户身份分开。

还有，你在上线前指出了审计缺口。如果还没有真实客户，就在测试账号里复现上面的双 Agent 例子，并写一份 README 解释每个选择。

工具会变，但这三个问题始终有价值：Agent 在哪里运行，谁可以调用，一切是否都有记录。能把这三个问题答得清清楚楚的 FDE，才会被请回来做下一个项目。
