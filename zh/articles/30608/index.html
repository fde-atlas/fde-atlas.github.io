FDE 系统设计面试：集成遗留系统

原标题：FDE System Design Interview: Integrating Legacy Systems

FDE Times · 2026-10-30 · 约 6 分钟读完

摘要

这篇文章讨论 FDE 系统设计面试中的遗留系统集成题。作者认为，直接提出干净的重写方案是错误答案，因为 Praxent 等 FDE 职位明确要求在客户已有约束下工作。文章以保险理赔分诊系统为例，给出一条安全路径：先确认可改动的集成点，用仅出站连接的 agent 穿透防火墙，通过 CDC 从数据库捕获事件，用防腐层（ACL）隔离旧模式，再以 Strangler Fig 门面逐个迁移功能。文章引用 Martin Fowler 对整体重写高失败率的警告，并提醒主动说明 ACL 延迟和最终一致性等代价。

要点

  • FDE 面试考察在既有约束下设计，而非推倒重写。
  • 推荐顺序：找集成点、出站连接、CDC 捕获事件、ACL 转换、门面迁移。
  • Martin Fowler 认为整体重写大多以失败告终。
  • Palantir Foundry 曾用仅出站的 agent 架构。
  • 须主动说明 ACL 延迟与最终一致性代价。

提议彻底重建会忽略招聘启事所要求的内容；绞杀者无花果（Strangler Fig）门面模式表明你能在他人已做出的决策框架内开展工作。

简要概述

  • 像 Praxent 这样的 FDE 招聘启事明确要求与你实际面对的系统集成，包括遗留核心系统，因此要把客户的约束当作问题本身来对待。
  • 一个稳妥的顺序：找到集成点，连接出站调用，通过 CDC 捕获事件，通过 ACL 进行转换，然后使用门面模式逐个迁移功能。
  • 不要提议全面重写——Martin Fowler 说这种计划大多以失败告终——也不要让旧的数据库模式泄漏到新服务中。

想象一下这道题：客户是一家保险公司，其保单管理系统已在本地运行多年，运维团队不允许任何人改动它。他们想要一个能够对保险理赔进行分类分派的服务。你有 45 分钟和一块白板。

许多工程师会直接提出一个干净的架构：API 网关、微服务、新数据库，以及一个“逐步迁移所有功能”的方案。在标准的软件工程师面试中，这样的回答也许足够了。但对于 FDE 职位，这恰恰跳过了招聘启事所描述的工作。

Praxent 的 FDE 招聘启事明确要求与你实际面对的系统进行干净的集成，包括遗留核心系统，并直言你需要在他人已做出的决策框架内工作。

因此，合理的准备方式是假设面试官想看到的是你如何围绕约束进行设计，而不是你多么擅长假装约束不存在。

为什么“干净地重写”是错误的答案？

Martin Fowler 警告不要一次性全面重写：这听起来简单，但据他观察，大多数此类计划都以失败告终。他推崇的方法是渐进式现代化，而且它有一个名字：绞杀者无花果（Strangler Fig）。

根据 Microsoft 的 Azure 架构文档，绞杀者无花果模式会用新的应用和服务逐步替换旧系统的部分功能。与此同时，旧系统继续运行尚未迁移的功能。其核心机制是门面——一个位于遗留后端之前的代理层，决定每个请求是发往旧应用还是新服务。

但每种模式都有前提条件。Microsoft 指出，如果你无法访问遗留系统的源代码，也没有其他被允许改动的集成点（例如数据库），那么绞杀者无花果模式可能并不适用。这就是面试中应该提出的第一个问题。

从提问开始，而不是画图

对于上面那道保险公司的题目，把前五分钟用来提问。保单系统的代码能否修改？如果不能，你能否读取它的数据库？内部网络允许哪个方向的连接？谁负责审批访问权限，通常需要多长时间？

最后一个问题不是凑数的。Appsierra 这家提供 FDE 的公司指出，访问权限配置、安全审查和客户审批所花的时间，往往比找到工程师还要长。

这只是供应商的观点，而非独立数据，但如果你把审查时间纳入计划，就能表明你真正了解实际项目会在哪里卡住。

假设面试官回答：不能改代码、允许读取数据库、没有入站防火墙规则。这三个答案决定了大部分架构。

实战示例：逐层构建数据通路

从网络开始。当防火墙不会开放入站连接时，你需要在客户网络内部署一个 Agent，并让它只发起出站连接。Palantir Foundry 正是这样做的：客户网络内的 Agent 通过单向出站 HTTPS 连接持续轮询 Foundry 来获取任务。

其文档现在已将这种 Agent Worker 架构标记为遗留方案，但在勾勒设计时，不开放任何入站端口的原则仍然值得遵循。

接下来是捕获事件。由于不能修改代码，你无法在应用程序中插入“新理赔到达时发送事件”的调用。对于无法修改的组件，Microsoft 建议直接从数据库本身捕获事件，例如用变更数据捕获读取事务日志，这样应用程序代码完全不会被触碰。

事件现在能到达你这里了，但它们仍带着旧系统的形态。Microsoft 警告说，遗留系统往往有混乱的 Schema 和过时的 API。如果没有隔离层，新设计会逐渐吸收旧系统的语义。这个隔离层被称为防腐层（ACL）。

想象一下旧的理赔表使用缩写列名、数字状态码，金额以乘以 100 的整数存储。ACL 是唯一了解这些约定的地方：

# ACL: translate a legacy record into the new service's model
STATUS_MAP = {"01": "submitted", "02": "in_review", "09": "closed"}

def to_claim(row: dict) -> Claim:
    return Claim(
        claim_id=row["CLM_NO"].strip(),
        policy_id=row["POL_REF"].strip(),
        status=STATUS_MAP.get(row["ST_CD"], "unknown"),
        amount=Decimal(row["AMT_X100"]) / 100,
    )

分诊服务只使用

Claim

，从不读取

ST_CD

。这也是现实中的重头戏：Appsierra 将 FDE 的集成工作描述为把客户真实的 Schema、命名约定和数据缺口与产品所需的内容进行调和。

最后是外观层（Façade）。第一天，只有一条路径迁移到新服务；其余一切仍走旧系统：

MIGRATED = {"/claims/triage"}

def route(path: str) -> str:
    return NEW_SERVICE if path in MIGRATED else LEGACY

迁移另一个功能只需在

MIGRATED

中添加一行，回滚也同样简单。

每一层都有代价：主动说出来

在被问到之前先说出代价。Microsoft 指出，ACL 会给两个系统之间的调用增加延迟。如果分诊必须立即向正在与客户通话的坐席返回结果，这个延迟就必须纳入你的预算。

如果旧系统以批处理方式运行或速度较慢，你还有另一个选择：通过 Service Bus、Event Grid 或 Event Hubs 等队列构建事件驱动的 ACL。

据微软所述，这种做法将新系统与旧系统的吞吐量限制解耦。代价是数据到达得更晚，且只有在延迟之后才保持一致（最终一致性），你应当明确说明这一点。

从零开始的答案

  • 不问任何问题就先画出全新架构
  • 提议重写整个系统
  • 假设入站防火墙规则可以开放
  • 在新服务中直接读取旧数据库模式

FDE 的答案

  • 先询问哪些集成点可以改动
  • 使用门面（façade）逐个迁移功能
  • 部署一个只进行出站连接的 Agent
  • 通过 ACL 转换所有内容，并明确指出其增加的延迟

需要避免的陷阱

第一个陷阱是在未检查前提条件的情况下应用绞杀者无花果模式（Strangler Fig）。如果客户既不允许你改动代码，也不允许你改动数据库，那么门面就无从着手，你应当坦率地说明这一点，而不是强行套用该模式。

另一个陷阱是 ACL 仅仅作为架构图上的一个方框存在。如果 ACL 之外的任何服务仍在读取旧的状态码，那么遗留语义就已经泄漏到了新系统中。也不要忘记人这一因素：如果没有人批准访问权限，再优雅的架构也只能停留在纸面上。

对你的职业发展而言：在阅读招聘广告时，“遗留核心系统”、“本地部署（on-prem）”或“现有系统”等措辞是很好的提示，能让你预判系统设计环节会考察什么。在简历上，不要只罗列技术，而要写出类似“通过 CDC 将数据从系统 X 中迁出，且客户侧无需任何代码改动”这样的表述，因为这正是 FDE 招聘广告所描述的那类集成工作。

本周的练习很简单：拿上面的保险场景题，把其中一个答案改成“不允许读取数据库”，然后重新解答。如果你仍然能够解释为什么架构必须改变，那你正是在练习 FDE 招聘广告所看重的技能。
