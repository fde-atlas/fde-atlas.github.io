事先阅读“什么是部署策略师（DS）？”“什么是前沿部署工程师（FDE）？”会加深理解。

结论：DS负责“做什么”，FDE负责“怎么做”

  • DS与FDE是互补关系，并非对立结构。DS承担“为什么做”“以什么为成果”这一投资判断与成功定义，FDE则将其实现为可运行的系统。
  • 将两者分开，是因为战略决策与技术实现所需的技能组合差异很大。若由一人包揽，经营层对话与实现两者之一必然被削弱。
  • 招聘顺序原则上为 DS → FDE。没有DS而只投入FDE，会大量产出“无法贴合业务的实现”，并在无法做出退出判断的情况下耗尽预算。

以下按顺序解说各维度。

维度1：主要目的

DS的主要目的是 达成AI投资的ROI与决策驱动。为经营层提供可判断“做 / 不做”“扩大 / 退出”的依据，并在决策会议上推动表决。

FDE的主要目的是 让贴合业务的软件运行起来。仅按规格书运行是不够的，成果在于打造现场在日常业务中实际使用的状态。

维度2：成果定义

DS的成果是可转化为ROI故事的KPI改善，以上线判定或内部接管完成为里程碑。

FDE的成果是可运行的系统与生产环境运营、自主化交付。仅仅写了代码并不算成果。

维度3：KPI

DS的评估指标是 业务KPI的改善幅度 与 退出判定的准确性。改善幅度因目标业务而异，例如客户服务是平均响应时间缩短X%，制造业是不良率降低Y%等。退出判定的准确性，以该退出的项目是否退出 / 该扩大的项目是否扩大来衡量。

FDE的评估指标是 使用率 / 业务应用率 / 修改交付周期。部署的系统是否在现场被使用、最终用户是否每天在使用、从修改需求到生产环境上线的时间有多短。

维度4：技能要求

DS涵盖 业务理解 × KPI设计 × 经营对话 三大领域。业务理解是领域经验（金融 / 制造 / 医疗等），KPI设计是战略咨询类的议题设计能力，经营对话是与经营层进行逻辑对话的经验。不需要写代码，但要能读懂代码。

FDE涵盖 业务理解 × 技术实现 × 运营设计 三大领域。业务理解可以比DS稍浅，但技术实现必须达到能在实际工作中熟练编写Python / TypeScript / SQL的水平。运营设计需要能设计到监控、告警、SLI / SLO层面（参考：将FDE融入组织｜技能地图与评估标准）。

维度5：合同形式

DS多采用 成果联动型（达成KPI）+ 月度固定 的混合合同。成功报酬随KPI达成程度而变动。这是因为DS是对“拿出成果”负有责任的职位，按小时计费并不合理。

FDE多采用 月度固定 + 成果激励。以上线达成或自主化完成等里程碑为单位追加激励。虽然是按时间计费，但不是SES那种“人月单价”。

维度6：参与期间

两者都是6〜18个月，但投入的峰值不同。DS在 前期（Define / Decompose）与后期（Decentralize）投入较多。FDE在 中期（Build / Run）投入较多。参见下图。

维度7：汇报对象

DS直接向 客户的经营层 / 事业负责人 汇报。月度经营报告由DS主持。

FDE向 客户的现场负责人 / 内部团队负责人 汇报。周度指导由FDE与现场负责人共同推进。

一旦两者的边界变得模糊，就会出现现场的声音传不到经营层 / 经营的判断传不到现场的双重断层。

维度8：退出条件

DS 的撤退条件是 KPI 达成 + 内部决策者培养完成。如果客户方没有培养出“下一个 DS”，就无法撤退。

FDE 的撤退条件是 由内部工程师完成维护与扩展。客户工程师能够独立进行扩展改修的状态即为达成标准。

Palantir / OpenAI / Anthropic 各公司的角色分工

Palantir：DS 与 FDE 的发源地

在 Palantir，DS / FDE 会以成对形式配置到同一项目中。自创业期起，公司一直以“与客户深度绑定的 Forward Deployed Team”为旗帜。对于 Foundry / Gotham 这类通用软件包＋需要定制化的产品，如果缺少 DS 的“翻译能力”与 FDE 的“实现能力”这两大支柱，产品就卖不出去。

两家公司都有物理驻扎在客户办公室的文化，部分项目中 DS 的现场驻留时间比 FDE 更长。

OpenAI：Deployment / GTM Engineering

OpenAI 以 Deployment Engineering / GTM Engineering 的名义设有类似角色，为 enterprise 客户提供 ChatGPT Enterprise / API 的业务集成支持。相当于 DS 的岗位有时也会以 Customer Engineer 或 Solutions Architect 的头衔运作。

Anthropic：Deployment Strategist 招聘

Anthropic 明确以“Deployment Strategist”这一职位名称发布招聘。该角色负责在客户方主导 Claude 的业务集成，与 Forward Deployed Engineer / Customer Engineer 并行协作。

Scale AI：Forward Deployed Solutions Engineer

Scale AI 采用名为 Forward Deployed Solutions Engineer 的整合型角色，以一人之力体现 DS + FDE 的复合型人才。这是因为 Scale AI 的产品特性（数据标注平台）相对同质化，各项目的定制化程度比其他公司浅，分离职种的收益较小。

详细的海外案例请参见“从 Palantir / OpenAI / Scale AI 看 FDE 模式的实态”。

日本企业容易混淆的 3 种模式

混淆 1：误认为“DS = 表现优秀的 PM”

PM 是按既定计划如期推进的职位。DS 则是 构建计划的前提，并在必要时拥有变更计划权限 的职位。决策主体不同。

要将 PM 出身者转型为 DS，需要强化议题设计能力与与经营层对话的经验。反之，把战略咨询出身者放在 PM 岗位上，往往会因过度提出议题而阻碍项目推进。

混淆 2：误认为“FDE = 派遣 SE”

SES 或派遣 SE 按规格实现。FDE 则是 在与业务的对话中构建规格本身 的职位。由于在需求确定之前就深入现场，与业务负责人的对话量、对业务领域理解的深度，都是 SES 无法比拟的。

FDE 的技能组合是“资深工程师 + 产品经理 + 领域专家”的融合，年薪范围通常是 SES 的 2～3 倍（参考：FDE vs SES vs SI vs 战略咨询｜4 种模式彻底比较）。

混淆 3：误认为“DS 和 FDE 可以由同一个人承担”

Palantir / Anthropic / OpenAI 原则上都将 DS 与 FDE 分离。原因在于时间上的争夺。若把时间用于与经营层对话，就无法专注于实现；若埋头于实现，月度经营汇报就会敷衍了事。越想兼顾两者，两者都会变得不彻底。

例外是像 Scale AI 这样销售同质化产品的企业，但在 enterprise AI 实现中，分离几乎总是正确答案。

先招哪一个｜按阶段的优先顺序

阶段状况优先招聘理由
Phase 0AI 投资决策前DS制作投资决策材料是 DS 的工作
Phase 1PoC 设计DS → FDEDS 进行 KPI 设计 → FDE 进行 PoC 实现
Phase 2PoC → 投产增员 FDE投产后实现比重上升
Phase 3投产运营 + 横向推广两者持续DS 负责横向推广决策，FDE 负责新项目实现
Phase 4自主化 / 撤退DS 最后撤退判定与内部移交是 DS 的工作

从 Phase 0 就做出“只招 FDE”的判断是失败模式。在没有投资决策的情况下养着工程师，做什么都定不下来，PoC 乱立，最终全部半途而废。

两者结合的合同形态示例

模式 A：DS + FDE 成对配置（Palantir 型）

  • 以 DS 1 名 + FDE 2～3 名为一组提供
  • 合同期 6～12 个月
  • 月度固定费用 + KPI 达成激励
  • 撤退条件在签约时明文化

成本最高，但成功率也最高。是 enterprise 领域的主流。

模式 B：DS 单独配置 + FDE 按需

  • DS 1 名配置 12～18 个月
  • FDE 仅在实现阶段按需从多家公司采购
  • 由 DS 负责 FDE 的遴选与统筹

适用于中等规模项目。DS 负荷较高，以有能力的 DS 为前提。

模式 C：DS 按需 + 内部 FDE

  • 外部 DS 集中投入 3～6 个月
  • FDE由内部工程师承担
  • DS在指导内部FDE候选人的同时主导KPI设计

适合内制化倾向较强的企业。可以加速内部工程师向DS / FDE转型，但起步较慢。

FAQ

Q1. 一人能否同时兼任DS和FDE？

例外情况下可以，但不推荐。先行企业几乎都将两个职位分离，其原因如前章“日本企业容易混淆的3种模式”中的混淆3所述，归根结底在于经营层对话与实现工作的时间分配无法兼顾。

仅在小规模创业公司预算约束严格的情况下，有让资深人才兼任的案例。即便如此也撑不过3个月。

Q2. DS的上级是谁？

在客户方是业务负责人（CXO / 事业本部长）。在实施方（如FDX这样的实现合作伙伴一方）由相当于Engagement Lead或Practice Director的资深DS统筹管理。FDE的现场负责人不会成为DS的上级。

Q3. 是否存在FDE晋升为DS的职业路径？

存在但数量较少。FDE向DS的转换需要补强经营对话能力和议题设计能力，需要12〜24个月的有意识训练。反之，DS转为FDE的情况几乎没有（技能组合不匹配）。

Palantir设有FDE → Engagement Lead → DS的晋升路径。日本企业也可以采用类似的设计。

Q4. 应该先招聘DS还是FDE？

应该先招聘DS。如果没有DS而只招FDE，“做什么”无法确定，PoC会泛滥。先招DS则KPI设计和投产判定能够发挥作用，对FDE的招聘判断也会更加准确。

不过，如果仅限于已经明确要做什么的特定领域（例如：定型业务的RPA化），FDE先行也能成立。

Q5. 两者的薪酬差距有多大？

在外资AI企业中，DS的薪酬略高于FDE（基本工资 + 绩效联动）。在日本企业内制的情况下，DS：FDE ≈ 1.3〜1.5 : 1。这反映了两者技能组合稀缺性的差异。

不过FDE的资深层（Principal FDE）有时也能获得与DS同等甚至更高的薪酬。

Q6. 内制与外包相结合时应如何设计？

典型案例如下。

  • 外部DS（全职）+ 外部FDE（全职）→ 模式A
  • 外部DS（全职）+ 内制FDE（兼职）→ 启动期
  • 内制DS（全职）+ 外部FDE（按项目）→ 内制成熟期

完全内制通常在AX推进开始24个月以上后才实现。从一开始就追求完全内制会导致起步过慢。

Q7. 应如何设计DS / FDE的评审机制？

DS采用每季度ROI评审（业务KPI改善 / 撤退判定的准确性 / 内制化进度）。FDE采用每月运营评审（运行率 / 业务应用率 / 事件应对）。如果用同一评价标准衡量两者，必然有一方显得偏低。

FDX的DS+FDE混合式服务

FDX株式会社以DS + FDE的成对配置（模式A）作为标准服务提供。

  • DS 1名 + FDE 2〜3名的团队编制
  • 月度经营报告（DS主持）+ 每周指导会议（FDE主持）
  • 与KPI达成联动的绩效报酬
  • 6〜12个月内完成内制移交 → 合同终止
  • 撤退条件在合同中明确记载（自主运行完成 / KPI未达成时的重新评估）

如果将“仅DS”“仅FDE”分别签订合同委托，两者的协作会变弱，难以取得成果。通过成对配置纳入同一个合同包，责任归属才能明确。
