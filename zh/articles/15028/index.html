OAuth

原标题：OAuth

FDE Interview Prep · 2026 · 约 2 分钟读完

摘要

本文面向 FDE 面试，讲解 OAuth 2.0（RFC 6749）授权框架：授权服务器向客户端发放限定范围和有效期的访问令牌，避免持有用户密码。重点介绍授权码加 PKCE、客户端凭证两种授权方式，以及 RFC 8693 令牌交换在 AI Agent 场景中的用法。文章以 Okta 的 FDE 职位要求为例，说明面试中如何设计多用户代理的令牌方案：按用户委派最小权限令牌、机器对机器调用使用独立客户端身份、检索时按用户权限过滤索引、令牌交换时加入 act 声明以便审计，并强调刷新失败时应重新征得用户同意而非回退到共享服务账号。

要点

  • OAuth 2.0 是授权框架，令牌限定范围与有效期，避免共享密码。
  • 常见授权方式：授权码加 PKCE 用于用户，客户端凭证用于服务。
  • RFC 8693 令牌交换可换出更窄令牌，配合 act 声明实现代理审计。
  • 共享索引会泄露数据，检索时须按请求用户权限过滤。
  • Okta FDE 职位要求掌握 OAuth、令牌交换、act 声明与 DPoP。

全文

OAuth（版本为 2.0，定义见 RFC 6749，当前安全指南见 RFC 9700）是一个授权框架：授权服务器向客户端颁发一个访问令牌，通常在范围和有效期上受限，使客户端能够代表用户或以自身身份调用 API，而无需持有用户的密码。最常见的两种授权方式是：面向用户的带 PKCE 的授权码授权（RFC 7636），以及面向服务的客户端凭证授权（RFC 6749, section 4.4）。设计题还会加入第三种：令牌交换（RFC 8693），即一个服务用它收到的令牌换取一个范围更窄的令牌，以便代表用户调用下一个服务。OAuth 本身并不涉及用户是谁；这正是 OpenID Connect 所补充的内容。

如果 Agent 搜索的是用管理员账户构建的索引，仅有委派令牌是不够的：泄露点在于共享索引，因此要么在查询时按请求用户的权限过滤检索结果，要么按用户分别建索引。当 Agent 调用下游服务时，将用户的令牌交换为一个范围更窄的令牌，并附带一个

act

声明来指明该 Agent，这样审计日志就会显示是该 Agent 代表该用户行事，而不仅仅是用户本人。当刷新失败时，应要求用户重新授权；绝不要退回到服务账户。
