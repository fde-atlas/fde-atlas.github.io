为什么多智能体系统会失败（2025）——写给 FDE 的解读

原标题：Why Multi-Agent Systems Fail (2025) Explained for FDEs

FDE Interviews · 2026-10-17 · 约 4 分钟读完

摘要

这篇 Berkeley 团队（含 Matei Zaharia、Ion Stoica 等）的论文研究多 Agent 系统为何失败。团队用扎根理论分析了五个框架的 150 多条执行轨迹，提出 MAST 分类法：14 种失败模式，分为系统设计、Agent 间失调、任务验证三类。六个开源系统失败率在 41% 到 86.7% 之间。核心结论是失败多源于组织设计而非模型能力，换更好的模型解决不了问题。对 FDE 的启示：先读轨迹、命名失败模式，多数修复是设计工作，且能单 Agent 解决就不要加多 Agent 协调。

要点

  • 六个开源系统失败率达 41%–86.7%
  • MAST 分类法含 14 种失败模式、三大类
  • 基于 150 多条轨迹、专家一致性 κ=0.88
  • 失败主因是系统设计而非模型能力
  • FDE 应先分析轨迹再做设计修复

一分钟读懂这篇论文

Multi-agent 系统将一项任务拆分给多个具有不同角色的 LLM Agent：规划者和编码者、CEO 和评审者、监督者和一组工具 Agent。这类系统很流行，但常常令人失望。作者测量了六个开源系统的失败率，介于 41% 到 86.7% 之间，每个系统都在各自的基准上测试。

论文提出的问题是为什么。这个团队是伯克利的团队，包括 Matei Zaharia、Joseph Gonzalez 和 Ion Stoica，他们从五个框架中获取了超过 150 条执行轨迹（每条轨迹平均超过 15,000 行），并让六位专家使用扎根理论（Grounded Theory）来阅读这些轨迹——这是一种定性方法，类别从数据中涌现，而不是作为假设预先设定。他们持续阅读，直到新的轨迹不再产生新的失败类型。随后，三位标注者独立标注轨迹，并经过三轮讨论解决分歧，直到一致性达到 Cohen's κ = 0.88。

研究成果是 MAST，即多 Agent 系统失败分类法：三个类别共 14 种失败模式。系统设计问题包括忽视任务约束、重复步骤以及不知道何时停止。Agent 间失调涵盖偏离任务的 Agent、隐瞒其他 Agent 所需信息的 Agent，或言行不一的 Agent。任务验证失败则包括过早停止，或检查不当或根本不检查。

为了扩大规模，他们针对人工标注校准了一个 LLM judge（OpenAI 的 o1，配合 few-shot 示例），达到 94% 的准确率和 κ = 0.77，并用它标注了来自七个框架的 1,642 条轨迹。他们的核心主张是：这些失败大多源于组织设计而非模型能力不足，因此仅靠更好的模型无法解决这些问题。

研究笔记：问题、方法与结果

MAST 分类法中的失败模式，分为三个类别

六个系统中最差系统在其自身基准上的失败率（AppWorld）

专家标注者在最终分类法上的一致性

多 Agent 系统往往仅勉强胜过单个 Agent 或 best-of-N 采样，而且没有人有一套共享的词汇来解释它们为何失败，因此每个团队都要从零开始调试。

阅读真实的执行轨迹，直到失败模式不再变化；将每种模式定义得足够精确，使专家们达成一致；然后用校准过的 LLM judge 来扩展标注规模。

MAST：三个类别共 14 种失败模式——系统设计、Agent 间失调和任务验证，人工一致性 κ = 0.88，并公开了包含 1,642 条已标注轨迹的数据集。

为什么这对 FDE 很重要

当客户的 multi-agent 试点停滞不前时，讨论通常会转向更换模型。这篇论文为你提供了一个更好的第一步：阅读轨迹，并指出失败所在。

共享的术语能加快调试速度。“Agent 搞混了”是无法采取行动的。而“审查者通过了能编译但从未运行过的代码”（无验证或验证不完整），或“工具 Agent 知道用户名必须是电话号码却从未说明”（信息隐瞒）则直接指向修复方法。

大多数修复属于设计工作，也就是 FDE 的工作。清晰的角色定义、明确的停止条件、谁有权结束对话，以及验证实际目标而非代码能否编译的验证器——这些都是无需重新训练任何东西就能掌控的选择。

这也是减少 Agent 数量的一个论据。如果一条固定步骤的流水线或一个带工具的单个 Agent 就能完成工作，那么 14 种失败模式就是 14 个不加多余协调的理由。其中若干模式，如对话重置、信息隐瞒和忽略其他 Agent 的输入，根本不会发生在单个 Agent 身上。

使用误差范围。论文中的干预措施在一个系统上仅将 32 个任务提升了 5 个。在告诉客户某个改动修复了他们的系统之前，先确保你自己的评测规模足够大，能够证明这一点。
