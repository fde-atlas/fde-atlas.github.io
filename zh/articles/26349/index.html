数据库隔离级别与丢失更新：多 Agent 并发写入

FDE Times · 2026-11-04 · 约 6 分钟读完

摘要

文章通过一个积分凭空减少的案例，讲解多 Agent 并发写入导致的丢失更新问题。丢失更新不抛异常，是否发生取决于客户数据库的隔离级别：PostgreSQL 默认 Read Committed，MySQL InnoDB 默认 REPEATABLE READ，CockroachDB 默认 SERIALIZABLE，同名级别行为并不一致。作者给出三种修复方案：原子更新、SELECT ... FOR UPDATE 悲观锁、提高隔离级别并配合重试循环。重试需同时捕获序列化失败与死锁，且每次重新读取数据并加入随机退避。文章还提醒快照隔离下的写偏斜风险，建议统一加锁顺序，并在事务外调用 LLM。

要点

  • 丢失更新不报错，取决于数据库隔离级别配置。
  • 三大数据库默认隔离级别不同，同名含义各异。
  • 三种修复：原子更新、FOR UPDATE 悲观锁、隔离级别加重试。
  • 重试须捕获死锁、重新读数据并加随机退避。
  • 警惕写偏斜，统一加锁顺序，事务外调用 LLM。

丢失更新不会抛出异常；它是否发生，取决于客户数据库的隔离级别，而很少有工程师查过这项设置。

要点速览

  • 两个 Agent 同时运行时，先读值、在代码里计算、再写回，是丢失更新最快的途径
  • PostgreSQL 默认 Read Committed，MySQL InnoDB 默认 REPEATABLE READ，CockroachDB 默认 SERIALIZABLE，同一段代码可能得出三种结果
  • 隔离级别越严格，客户端越要做好重试准备，重试循环除了序列化失败，还必须捕获死锁

周一早上，客户反馈一个账户扣错了积分。日志显示，客服 Agent 加了 50 积分作为补偿，计费 Agent 扣了 30 积分手续费，两边都报告成功。余额本应是 120，数据库里却是 70。

按通常的标准，这段代码没有 bug。每个 Agent 都正确执行了自己的逻辑，只是恰好同时运行。Agent 一旦进入客户的系统，多个进程写同一条记录就成了家常便饭。数据库最后留下哪个数字，取决于事务的用法，以及数据库运行在哪个隔离级别。

多数工程师都知道 ACID 这个缩写，但很少有人清楚客户数据库里的 I 是怎么配置的。前线部署工程师（FDE）必须清楚，因为这类 bug 不抛任何异常，只会悄悄损坏数据，等客户自己发现。

50 积分去哪了？

把两个会话按时间顺序并排摆开，答案一目了然。两个 Agent 用的是同一套代码：读取余额，在 Python 里算出新余额，再写回去。

-- Agent A（客服）                -- Agent B（计费）
SELECT balance FROM accounts      SELECT balance FROM accounts
 WHERE id = 42;   -- 100           WHERE id = 42;   -- 100
-- 计算 100 + 50 = 150            -- 计算 100 - 30 = 70
UPDATE accounts SET balance = 150
 WHERE id = 42; COMMIT;
                                  UPDATE accounts SET balance = 70
                                   WHERE id = 42; COMMIT;

这就是丢失更新（lost update）：后写入的一方覆盖了先写入的结果，却完全不知道对方存在。70 是 Python 根据过期的读取值算出来的，数据库收到的只是一个常量，照存不误。

上面的场景运行在 Read Committed 下，这是 PostgreSQL 的默认级别。除非有人专门改过配置，否则这种“读取、计算、写回”的代码在两个 Agent 交错执行时毫无保护。

三种修复，各管一类问题

最简单的办法是让数据库来做算术。写成

UPDATE accounts SET balance = balance + 50 WHERE id = 42

，加法在语句内部完成，也就不存在上例那种由过期读取算出的常量。

只是加减一个数的修改，首先就该试这个办法。即便如此，也要在客户的真实数据库上开两个 psql 窗口亲自验证。

不过，Agent 往往要先读再做决定：比如余额够才扣手续费，或者让 LLM 根据客户当前状态选择操作。这时需要悲观锁。

SELECT ... FOR UPDATE

会把刚读到的行当作即将更新的行锁住，阻止另一个 Agent 覆盖写入。

BEGIN;
SELECT balance FROM accounts WHERE id = 42 FOR UPDATE;
-- 在第 42 行被锁住期间，由代码做出决定
UPDATE accounts SET balance = 70 WHERE id = 42;
COMMIT;

第三种办法针对 PostgreSQL：让事务运行在 Repeatable Read 或 Serializable 级别，并接受数据库可能以序列化错误中止事务。PostgreSQL 文档要求运行在 Repeatable Read 的应用做好重试准备。一旦出现这种错误，必须放弃整个事务并从头重跑，而不只是重跑失败的那条语句。

注意，这里说的是 PostgreSQL 的行为。MySQL InnoDB 也有一个叫 REPEATABLE READ 的级别，但名字相同不代表行为相同，不要默认它能提供同样的保护。

重试循环还得多捕获一类错误。在 psycopg 中，

SerializationFailure

（错误码 40001）和

DeadlockDetected

（错误码 40P01）是两个独立的异常类。只捕获前者，循环就会漏掉死锁。

import random
import time

from psycopg import errors

RETRYABLE = (errors.SerializationFailure, errors.DeadlockDetected)

def run_with_retry(conn, work, attempts=5):
    for i in range(attempts):
        try:
            with conn.transaction():
                conn.execute("SET TRANSACTION ISOLATION LEVEL REPEATABLE READ")
                return work(conn)  # 每次尝试都从头重新读取
        except RETRYABLE:
            if i == attempts - 1:
                raise
            # 带随机抖动的退避，避免两个 Agent 立刻再次冲突
            time.sleep(0.05 * 2 ** i + random.uniform(0, 0.05))

这段代码最关键的一点是：

work

每次尝试都必须重新读取数据。如果 Agent 沿用旧的读取结果，或沿用基于旧状态算出的 LLM 回答，重试只会把错误的值再写一遍。

time.sleep

这一行是带少量随机性的指数退避。没有它，两个刚刚冲突的 Agent 可能同时重试，再次撞在一起。

方案机制适用场景
原子更新算术写在语句里，不存在过期值加、减、计数
SELECT ... FOR UPDATE
 锁住刚读到的行，另一个 Agent 无法覆盖先读再决定，高争用
Repeatable Read/Serializable + 重试（PostgreSQL）PostgreSQL 以序列化错误中止事务，客户端重跑整个事务低争用，逻辑复杂

快照仍会放过一类 bug

提高隔离级别后，还剩一个陷阱。Jepsen 指出，快照隔离允许写偏斜（write skew）：多个事务读取同一份共享状态，各自修改不同的对象集合，然后都提交成功。PostgreSQL 文档同样写明，Repeatable Read 能防止其表格中除序列化异常之外的所有现象，而写偏斜正属于序列化异常。

假设客户有一条规则：每个账户至少保留一个紧急联系人，账户 42 目前有两个。Agent A 删除第一个，Agent B 删除第二个。

两边都数到两个联系人，判断删除是安全的。各自删掉不同的行，没有哪一行被写了两次，也就没有冲突可报。最后，这个账户一个可联系的人都没有了。

所以 PostgreSQL 文档警告：在 Repeatable Read 下执行业务规则，如果不谨慎地使用显式锁，很难做对。写偏斜的前提是双方从不碰同一行，合理的做法就是强迫双方经过同一行：计数之前，先对账户 42 本身那一行执行

SELECT ... FOR UPDATE

。

另一条路是 Serializable。PostgreSQL wiki 把写偏斜称为 SSI 能防止的最简单的异常：先提交者胜出，另一个事务被回滚并必须重跑，这又要用到上面的重试循环。

隔离级别同名，各家数据库含义不同

FDE 从一个客户换到下一个客户时，最常在这里栽跟头。MySQL InnoDB 默认是 REPEATABLE READ，而不是 PostgreSQL 那样的 Read Committed。CockroachDB 默认是 SERIALIZABLE，并要求客户端自行实现重试逻辑，错误码为 40001。

Martin Kleppmann 在测试 ACID 中 I 的项目 Hermitage 里指出，repeatable read 这样的名字在不同数据库里含义不同。

后果很明确。上个项目在 CockroachDB 上运行良好的 Agent 代码，如果依赖数据库拦截冲突，放到默认配置的 PostgreSQL 上就可能损坏数据。反过来，为 PostgreSQL 写的、没有重试的代码，到了 CockroachDB 上会遇到 40001 错误却无人处理。要检查真实配置，别凭记忆。

锁越多，多一个风险：死锁

用上

FOR UPDATE

之后，死锁随之而来：Agent A 锁住账户、等待发票，Agent B 锁住发票、等待账户。PostgreSQL 会检测到这种情况，中止其中一个事务，让其他事务继续。

死锁和序列化失败是不同的错误，所以即使在 Read Committed 下也需要重试循环，而且要像上面的代码那样捕获

DeadlockDetected

。MySQL 文档给出了类似建议：对因死锁失败的事务，始终做好重新执行的准备。

根据 PostgreSQL 文档，最好的防御是让所有应用都按一致的顺序获取多个对象上的锁。为整个 Agent 系统定一条约定，比如总是先锁账户再锁发票，或按 id 升序加锁，并写进交接文档，免得客户团队日后打破它。

客户现场的常见陷阱

最常见的陷阱，是放任 Agent 生成“读取、在代码中计算、写回”的 SQL，却没人检查争用。同样常见的还有：重试时不重新读取数据，重试连续触发而没有退避，以及重试只捕获序列化失败而漏掉死锁。

Agent 系统特有的陷阱，是在等待 LLM 响应时一直开着事务。MySQL 文档建议让事务保持小而短，以减少冲突。所以应当先读数据，在事务之外调用模型，再开一个短事务重新校验并写入。

下次在让第二个 Agent 写同一张表之前，先问一句：如果两个 Agent 在同一毫秒运行，最后留下的是哪个数字？在 FDE 面试中，讲清一次亲手追查并修复丢失更新的经历，远比技能清单上的一个“PostgreSQL”有分量。
