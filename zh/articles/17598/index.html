VCR.py 教程：录制 API 响应让 CI 离线运行

FDE Times · 2026-10-21 · 约 6 分钟读完

摘要

这篇教程介绍如何用 VCR.py 和 pytest-recording 把客户 API 的请求响应录制到 cassette 文件中，让集成测试在 CI 里完全离线运行，避免客户沙箱不稳定导致构建失败。文章给出完整示例：编写独立客户端模块、录制并过滤 Authorization 头和查询参数中的密钥、用 before_record_response 钩子清除响应里的个人数据、在 CI 中用 none 模式加 --block-network 双重保险。还讲解了各录制模式的适用场景、常见错误（请求体不参与匹配、事后加过滤器无法清除已提交的密钥），以及 cassette 在客户沟通和交接中的文档价值。

要点

  • 录制一次 API 响应后测试可离线回放，无需令牌。
  • 提交前必须过滤请求头、查询参数和响应体中的敏感数据。
  • CI 用 none 模式加 --block-network，意外请求会直接报错。
  • 客户改数据结构时用 rewrite 模式重录，并在单独 PR 提交。
  • 已提交的密钥无法靠过滤器删除，需通知客户吊销令牌。

VCR.py 和 pytest-recording 可离线回放录好的响应，但提交前须清掉令牌和客户数据。

要点速览

  • 把真实请求录进 cassette 一次，之后测试回放响应，不需要网络，也不需要令牌。
  • 提交前先过滤请求头、查询字符串和响应体，因为 cassette 是谁都能读的纯文本文件。
  • CI 中保持 pytest-recording 默认的 none 模式，再加上 --block-network，任何意外请求都会让测试失败。

设想这样一个场景：你在客户现场的第二周，对方的沙箱 API 每天下午都开始返回 503 错误。每到这时 CI 就变红，而你的代码一行都没改过。

最干净的解法是只调用一次真实 API，把每个请求和响应都录下来，之后每次运行都用这份录制。VCR.py 做的正是这件事。根据该库的文档，测试首次运行时会把 HTTP 请求录制到一个 YAML 格式的 cassette 文件中，此后测试就从这个文件读取。

本指南搭建一个完整示例：为一个假想的客户订单 API 编写客户端，pytest 测试只录制一次，提交前屏蔽敏感数据，CI 完全离线运行。任何集成项目的第一周，你都会用到这套做法。

开始前需要准备什么？

需要 Python、pytest、

requests

库，以及两个包：

vcrpy

和

pytest-recording

。后者是基于 VCR.py 的 pytest 插件，可以用

pytest.mark.vcr

标记测试，不必自己逐段包装代码。

pip install pytest requests vcrpy pytest-recording

下文的

api.example-customer.com

端点只是占位符。在真实项目中，请换成客户的沙箱地址和对方发给你的令牌。

第 1 步：写一个轻量客户端，与测试分开

把所有 HTTP 调用放进独立模块。测试调用这个函数的方式与生产代码完全一致。

# orders_client.py
import requests

BASE_URL = "https://api.example-customer.com"

def list_orders(token, status="open"):
    resp = requests.get(
        f"{BASE_URL}/v1/orders",
        params={"status": status},
        headers={"Authorization": f"Bearer {token}"},
        timeout=10,
    )
    resp.raise_for_status()
    return resp.json()["orders"]

检查：在终端用真实令牌运行一次这个函数，确认 API 返回订单列表。如果这一步失败，就什么都别录，因为 cassette 会把错误也原样存下来。

第 2 步：用原生 VCR.py 录制第一个 cassette

在使用插件之前，先看看 VCR.py 在最底层如何工作。

# test_raw.py
import os
import vcr
from orders_client import list_orders

def test_list_orders_raw():
    with vcr.use_cassette("fixtures/vcr_cassettes/orders.yaml"):
        orders = list_orders(token=os.environ["CUSTOMER_TOKEN"])
    assert isinstance(orders, list)

VCR.py 的默认录制模式是

once

：cassette 文件不存在时录制新的交互；文件已存在时只回放。把测试运行两次，第二次会明显更快，因为它不再走网络。

现在打开

orders.yaml

。你会看到带令牌的

Authorization

请求头原封不动地躺在文件里，还有客户订单的全部内容。记下这里出现的几个真实邮箱地址和邮箱域名，后面检查时要用。不要提交这个文件。删掉它，进入第 3 步。

第 3 步：改用 pytest-recording 并过滤密钥

使用 pytest-recording 时，录制配置放在

vcr_config

fixture 中。这里也是声明哪些内容绝不能进入 cassette 的地方。

# conftest.py
import pytest
from scrub import scrub_response

@pytest.fixture(scope="module")
def vcr_config():
    return {
        "filter_headers": ["authorization"],
        "filter_query_parameters": ["api_key"],
        "before_record_response": scrub_response,
    }
filter_headers

接收一个列表，列出录制时要去掉的请求头；

filter_query_parameters

对查询字符串做同样的事。后者在客户把密钥放进 URL 时很关键，比如

?api_key=...

，这种写法在老系统里仍然常见。

# test_orders.py
import os
import pytest
from orders_client import list_orders

@pytest.mark.vcr
def test_list_open_orders():
    token = os.environ.get("CUSTOMER_TOKEN", "dummy")
    orders = list_orders(token=token)
    assert all(o["status"] == "open" for o in orders)

注意

"dummy"

这个值：回放时测试不需要真实令牌。CI 里完全不存放任何密钥，这正是你想要的。

第 4 步：屏蔽响应中的客户数据

过滤请求头只解决了一半问题。响应体里仍然有终端用户的邮箱、姓名和地址。

before_record_response

钩子可以在录制前修改响应，也可以返回

None

，把这一对请求和响应整个从 cassette 中丢弃。

# scrub.py
import json

def scrub_response(response):
    body = response["body"]["string"]
    try:
        data = json.loads(body)
    except ValueError:
        return response
    for order in data.get("orders", []):
        order["customer_email"] = "[email protected]"
    response["body"]["string"] = json.dumps(data).encode()
    return response

这是简化版本：它假定响应体是未压缩的 JSON，且需要屏蔽的字段叫

customer_email

。对接真实 API 时，请向客户确认哪些字段包含个人数据，不要靠猜。

现在重新录制。pytest-recording 默认运行在

none

模式，不会意外访问网络，因此你必须主动开启录制。由于插件的录制配置都在

vcr_config

中，最容易管理的做法是：在本机临时把该 fixture 设为

once

模式，用真实令牌运行一次测试，提交前再删掉这一行。

CUSTOMER_TOKEN=xxx pytest test_orders.py

检查：打开新生成的 cassette，搜索

Bearer

和令牌，再搜索客户的真实邮箱域名以及第 2 步记下的邮箱地址。不要搜索

@

字符，因为替换值

里也有它。什么都搜不到时才提交。

[email protected]

第 5 步：把 CI 锁定在离线模式

CI 中不需要额外配置录制模式，因为

none

本来就是默认值。该模式遇到任何新请求都会报错，所以如果有人新增了 API 调用却忘了录制 cassette，测试会立即失败，而不是悄悄向外发请求。

pytest --block-network
--block-network

参数会在测试运行期间阻断所有网络访问，没有

vcr

标记的测试也不例外。这是第二道防线，专门拦截完全绕过 VCR 的网络调用。

客户 API 变更时，怎么重新录制？

很多人的 cassette 就是在这一步弄坏的。每种录制模式对应不同场景，选错了可能让 CI 意外访问真实网络。

模式行为适用场景
once
 仅在 cassette 不存在时录制在本机首次录制
new_episodes
 回放已有交互，录制新的交互为现有测试新增端点
none
 遇到任何新请求都报错CI 和所有日常运行
all
 从不回放，始终录制很少用；CI 中几乎不用
rewrite
 从头重新录制 cassette（pytest-recording）客户改了数据结构，需要一份干净的录制

客户宣布数据结构变更时，在自己机器上运行

rewrite

，按第 4 步打开文件检查密钥，然后在单独的拉取请求（PR）中提交。这样 cassette 的 diff 就能准确显示 API 改了什么。

常见错误

第一个与请求匹配有关。VCR.py 默认按方法、协议、主机、端口、路径和查询参数匹配，也就是说它会忽略请求体。两次请求体不同的

POST /v1/orders

调用可能被视为同一个请求，测试就会拿到错误的响应。

需要测试同一 URL 的多个 POST 时，稳妥的做法是像第 2 步那样，用

vcr.use_cassette

给每次调用单独一个 cassette 文件。

第二个是在 cassette 已经提交之后才加过滤器。过滤器只对下一次录制生效，无法删除已进入 git 历史的令牌。遇到这种情况，要通知客户吊销该令牌，而不只是改文件。

第三个是调试结束后忘了从

vcr_config

中删掉录制模式，最糟的是留在

all

。之后每次运行都会调用真实 API，CI 开始需要令牌，你又回到了原点。

这项技能在客户现场怎么用？

在真实项目中，cassette 还能兼作文档。客户问你的系统向他们的 API 发了什么，你打开 YAML 文件，给他们看已屏蔽数据的请求。这个回答比任何架构图都更有说服力。

它对交接也有帮助。客户方的工程师克隆仓库，运行

pytest --block-network

，无需申请沙箱权限就能看到测试全绿。你离开现场，测试套件留下来继续运行。

职业方面：阅读前线部署工程师（FDE）的岗位描述时，留意“integrate with customer systems”或“own integrations end to end”这类表述。简历上不要只写“写了测试”，而要写成果，例如“为客户 API 搭建离线集成测试套件，使用 VCR.py 录制，过滤凭据和个人数据，CI 无需网络”。

面试时，如果你能讲清楚 CI 为什么应该运行在

none

模式，面试官就会看出你理解其中的风险，而不只是会用一个库。

下次客户沙箱再返回 503，你的 CI 不受影响。只有在客户宣布数据结构变更的那天，才需要再调用一次真实 API。
