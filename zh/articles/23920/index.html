FDSE 是什么？与 FDE 的区别、工作内容、所需技能及成为方法详解

原标题：FDSEとは？FDEとの違い・仕事内容・必要スキルと目指し方を解説

FDE総研 · 2026-09-03 · 约 13 分钟读完

摘要

这篇来自FDE总研的文章解释了FDSE（前沿部署软件工程师）这一Palantir正式职位名称：FDSE驻扎在客户现场，从需求确认到实现本番质量的软件都由自己完成。文章梳理了FDSE与FDE、Deployment Strategist、普通SWE、SIer上游SE及咨询顾问的区别，指出其本质在于既拥有定义需求的权限、又无法逃避写代码。文章还介绍了单个项目从现场观察、数据接入、最小可用版本到移交运营的典型流程，所需的数据、前端与业务沟通三层技能，适合与不适合的人群，以及在职准备和转职面试的要点，并提醒注意避免过度依赖特定平台经验。

要点

  • FDSE是Palantir的正式职位，需在客户现场交付本番质量软件。
  • FDE是行业通称，Palantir内部由FDSE负责实现、DS负责业务定义。
  • FDSE特征是需求确定权与代码实现责任集于一身。
  • 项目流程为现场观察、接入数据、尽早交付可用版本、再逐步完善。
  • 技能上要求从数据到UI的广度，加上业务语言化与临场判断力。

FDSE是什么的缩写？是一个怎样的职位？

FDSE是Palantir的正式职位名称，指深入客户现场、负责实现生产级软件的工程师。

FDSE是Forward Deployed Software Engineer的缩写。“明明是工程师却在客户现场听取需求并当场编写代码”这种工作方式，在日本IT行业长期以来常被与SIer的上游工程或咨询顾问的工作相提并论。FDSE是在这种工作方式上增加了“亲自把生产级软件写完的责任”的职位。Palantir Technologies（2003年创立，现总部位于美国科罗拉多州丹佛）将其作为主要职位之一刊登在招聘页面上，FDSE这个名称也因此广为人知。

FDSE的正式名称是什么？Palantir对其角色的定义是什么？

FDSE直译为“前线配置型软件工程师”，在Palantir产品之上实现客户专用的解决方案。

正如其名称Forward（前线）Deployed（被配置的）Software Engineer所示，FDSE被配置在客户现场。根据Palantir的招聘信息，FDSE的职责是直接面对客户的业务课题，在Palantir的平台上设计并实现解决方案。FDSE所使用的Palantir产品有以下4个。

产品定位
Gotham以政府和防卫领域为主的平台
Foundry面向商业企业的平台
Apollo部署基础设施
AIP（Artificial Intelligence Platform）2023年推出的AI平台

FDSE在这些产品之上，为该客户搭建专用的数据管道、本体（业务概念模型）以及业务应用。

需要注意的是，FDSE并不是“陪同销售的工程师”。Palantir所定义的FDSE不是做演示的人，而是真正交付可运行的成果、并使其达到在现场被实际使用状态的人。

FDSE为什么会出现？

FDSE是为填补通用产品无法覆盖的业务固有差异、由人在现场加以弥补而设计的职位。

制造线的良品率、医院的病床运营、供应链的零部件供应。在这些领域，数据的形态和决策的顺序都因企业而异。仅靠标准功能来解决，最后总会残留业务固有的差异。即使由咨询顾问用文档来填补这些残留，也无法变成软件。若放入产品团队的路线图，则要等上好几个季度。

FDSE正是对这一结构性鸿沟的回答。大部分由平台承担，剩余部分在现场编写。这种分工要成立，平台侧必须采用“可在现场即时扩展”的设计。Palantir的Foundry和AIP正是基于这一前提构建的。

近年来，以OpenAI和Sierra为代表的AI企业也在以“Forward Deployed Engineer（FDE）”的名称招聘同类职位。Palantir所开创的这一职位的理念，正在成为行业的通用语言。

FDSE与FDE以及一般软件工程师有什么不同？

FDE是职位的统称，FDSE是Palantir的正式职位名称。与其他职位最大的区别在于实现工作所占比例之高。

由于叫法混杂，先做个梳理。日语招聘信息和文章中写“FDE”的，大多是源自Palantir职位名称的一般性用法。另一方面，Palantir公司内部的职位体系是双轨制：负责实现的是FDSE，负责定义业务课题和维护客户关系的是Deployment Strategist（DS）。

FDE与FDSE是什么关系？

FDE是行业通用的概念名称，FDSE则相当于Palantir将其定义为实现担当的具体职位名称。

术语定位主要使用场景
FDE（Forward Deployed Engineer）职位的统称、概念跨行业使用。AI企业和SaaS企业的招聘中也常使用
FDSE（Forward Deployed Software Engineer）Palantir的正式职位名称明确实现责任。以平台上的开发为中心
DS（Deployment Strategist）Palantir的正式职位名称以定义业务课题、建立关系、定义成果为中心

从从业者的角度来看，不必太在意FDE与FDSE的区别。在跳槽市场上，搜索“FDE”就能同时找到两者。日本国内的FDE类职位，很多情况下并不像Palantir那样职责划分明确。比起这一点，更有用的是通过职位描述确认该职位对实现工作的要求程度。

SWE、SIer、咨询顾问与FDSE有什么不同？

在交付物是代码这一点上与SWE相同，但由谁确定需求、在哪里工作这两点有着决定性的不同。

视角FDSE自有产品的SWESIer的上游SE战略与业务咨询
需求的来源自己在现场确定PdM、路线图客户的需求规格书自己定义（实现由其他团队负责）
主要工作场所客户现场（现场与远程并用）本公司本公司＋客户现场客户现场
最终交付物可运行的应用、流水线产品功能设计文档＋外包开发方的交付物建议与报告资料
评价标准是否在现场被实际使用指标改善、发布交付期、质量、成本对决策的影响
写代码的比例高（核心工作）高低～中几乎为零

FDSE独有的特征，可以归结为“需求的来源”和“写代码的比例”两者都很高。既拥有决定需求的权限，又无法从实现中脱身。这种张力正是FDSE这一职业的本质。

Deployment Strategist（DS）与FDSE如何分工？

基本模式是DS提出问题，FDSE实现解决方案。不过实际的边界会随项目规模而变化。

在小规模项目中，FDSE兼任DS的角色并不罕见。相反，在大型导入项目中，多个FDSE分担不同模块，DS则专注于与客户的决策者对齐成果指标。

一线实务者中常有人反映，日本企业在新设FDE类职位时，有让一个人背负这两个角色而使其疲惫不堪的例子。在起步阶段兼任有时难以避免。但是否将其作为长期持续的体制保留下来，则需要慎重考虑。

FDSE的工作内容和单个项目的推进方式是怎样的？

FDSE独自承担从需求定义到实现、再到落地支持的全过程。单个项目通常以数周到数个月为周期运转。

FDSE按哪些阶段推进单个项目？

从现场观察开始，尽早展示可运行的东西，边观察实际使用情况边打磨完善。这就是FDSE的基本模式。

  • 进入现场（第1天～第1周）：实际观察业务，掌握谁在操作哪个系统、操作多少次。不能仅靠访谈了事。
  • 连接数据（第1～3周）：将核心系统、Excel、传感器日志等分散的数据源接入，整合为统一的模型。在Palantir的语境中，这相当于将业务概念定义为本体（ontology）的工序。
  • 产出最小可运行版本（第2～6周）：比起完成度，优先让现场负责人能在自己的业务中实际使用。此时获得的反馈，是关于需求的最大信息来源。
  • 打磨完善与移交运营（第3阶段之后，往往持续数个月）：细化异常处理、权限、审计日志以及与现有业务流程的对接。这是最不起眼、也是坑最多的工序。
  • 落地与撤收：将运营移交给客户方的负责人。此后还要在一定时期内跟踪是否持续被使用，必要时扩展到下一个课题。

需要注意的是，这个流程并非一条直线。在第3阶段展示的瞬间，发现“其实要解决的课题根本不对”的情况确实存在。正因为要尽早发现这一点，才要尽早展示——这就是这种推进方式的思路。

FDSE实际写什么样的代码，接触哪些技术？

FDSE一个人在数据处理和前端两端之间来回穿梭。比起专业的深度，更起作用的是覆盖面的广度。

领域典型工作常用技术
数据接入核心系统、CSV、API对接SQL、Python、各类连接器
转换与建模向业务概念的规范化、质量保障PySpark、SQL、本体定义
应用实现现场负责人使用的界面TypeScript、React、低代码UI
运营与权限访问控制、监控、CI/CD各类部署平台
分析与LLM对接决策支持、摘要与抽取分析工具、LLM API

“是不是需要Palantir平台特有的知识？”这种担忧很常见。但选拔中考察的是通用的编程能力和问题解决能力，Palantir产品特有的使用方法默认是入职后再学习的。其他公司的FDE职位情况也一样。

FDSE的实际工作状态如何？出差和驻场程度如何？

FDSE的主要负担有两个：前往客户现场的移动，以及每次项目切换时都要从零重新积累上下文。

疫情之后，与远程办公并用的情况有所推进，但在初期阶段，驻场的比重至今仍然很高。此外，每次项目更换都需要从零重新积累行业知识。从制造业转到医疗行业这类转换，智识上的刺激很大，但知识难以积累。

多位实务者异口同声地表示，能否享受这种切换成本，最能决定一个人是否适合FDSE。

FDSE需要哪些技能和经验？

FDSE需要三层技能：数据处理和应用实现这两项，再加上将业务转化为语言表达的能力。

FDSE需要哪些技术技能？

FDSE中被看重的不是单点的深度，而是能凭一己之力从数据打通到UI的覆盖广度。

技能要求水平判断标准
编程（Python等）必需、高能独立完成业务逻辑的实现
SQL、数据建模必需、高能把脏数据整理成可用的形态
Web／UI实现必需、中～高能自己做出现场使用的界面
云与基础设施中理解部署和权限设计
分布式处理（Spark等）有则更强能托付大规模数据的处理
LLM／AI应用近年重要性上升能设计如何嵌入业务

这并不意味着“浅而广”。前提是在任何领域都能写出经得起生产环境运行的代码，在此基础上还要求范围广泛——这是其要求水准。

FDSE需要哪些非技术技能？

将客户的语言翻译成规格，并在决策者不在场时也能推动前进的判断力，在很大程度上决定FDSE的成果。

具体来说是以下三点。

  • 挖掘约束的能力：找出现场负责人说“很麻烦”的作业背后的约束条件。
  • 达成共识的能力：当出现相互矛盾的要求时，提出优先级建议并达成共识。
  • 临时判断的能力：在信息尚不齐全时做出临时判断，并保持事后可以修正的形态。

当这三者齐备时，即使技术水平相同，成果也会有很大差异。如果目标是 Palantir 本部或外资 AI 企业，英语需要达到实际业务水平。而在国内企业的 FDE 类职位中，也有不少招聘并不将其作为必要条件。

什么样的人适合 FDSE？什么样的人会感到痛苦？

能从客户现场感受到价值的人适合 FDSE。最想优先深耕技术的人则会有较大摩擦。

适合的人容易感到痛苦的人
想直接看到自己写的东西被谁、如何使用想长期培育一个架构
能把掌握业务知识本身当作乐趣想在代码评审文化中磨炼技术
不畏惧在不确定的情况下做决策想扎根于一个系统持续投入

符合右栏的人，可能会觉得 FDSE 这种按项目开发然后交接的循环不够过瘾。这不是优劣问题，而是想从工作中获得何种回报的差异。

想成为 FDSE，应该从哪里开始？

最短的路径是：先在现职中争取直接与客户沟通的工作，并把实现能力与业务理解整合成一项实绩。

要在现职中创造 FDE 式的工作，该怎么做？

即使在跳槽之前，也有三个 FDSE 要素可以在现在的职场中复现。最好把它们整理成能在选拔中讲述的实绩形式。

  • 参与需求访谈，亲自落实到规格：不要等待经由销售或 PdM 传达下来的需求，而是建立直接接触一手信息的渠道。
  • 自己发现并自己解决一个公司内部的业务问题：把部门的手工作业工具化，并跟进到被实际使用为止。规模小也没关系。
  • 完整走一遍数据平台的上游到下游：如果不分工而是独立完成数据接入、转换、可视化的全过程，这样的经验会很有说服力。

FDSE 的选拔考察什么？如何准备？

除了编码能力之外，能否讲述自己如何重新定义客户的问题，是选拔的关键分水岭。

选拔要素考察的内容准备方向
编码测试通用的实现能力、将思考转化为语言的能力反复练习算法与设计基础
技术面试从数据到 UI 的覆盖范围准备一个端到端完成的案例
案例／业务面试将模糊问题结构化的能力将改变问题定义的经验用语言表达出来
文化面试现场导向、对不确定性的承受力坦诚地讲述对出差和变化的态度

薪资水平因企业和地区而有很大差异。在美国企业的招聘中，有时会依据法律公开薪资范围。数值请务必在应聘方的最新招聘要求中确认。FDE 总研不会在此列举推测性的数字。

有 FDSE 经验的人之后会走向怎样的职业道路？

同时拥有现场经验与产品实现经验的 FDSE，无论转向 PdM、架构师还是创业都比较容易。

积累数年 FDSE 经验后，你会成为既能讲“业务语言”又能讲“实现语言”的人才。这种组合十分稀缺，容易通向产品管理、解决方案架构师、公司内部新业务启动，或者自己创业。实际上，在美国，Palantir 出身者带着 FDE 式思维方式创办初创企业的例子不断涌现。

另一方面，如果积累的经验过度依赖特定平台，市场价值可能会有偏差。FDE 总研建议有意识地保留在通用技术栈上的实现经验。即使无法选择项目中使用的工具，作为个人，你仍然可以选择重新学习什么。
