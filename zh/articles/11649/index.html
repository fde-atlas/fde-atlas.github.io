原标题：U-Fold (2026) Explained for FDEs

FDE Interviews · 2026-10-17 · 约 4 分钟读完

摘要

这篇来自 FDE Interviews 的解读分析了 U-Fold 论文（2026）。作者来自浙江大学、阿里通义实验室和西湖大学。文章指出，传统上下文折叠方法为单目标任务设计，在多轮客服对话中会丢失营业时间、数量等细粒度约束，也无法跟踪用户改变的想法。U-Fold 不丢弃历史，而是保留完整对话和工具日志，每收到新消息就用两次模型调用重建工作上下文：一个摘要模块生成带待办清单的时间线摘要，一个抽取模块按行号选取相关工具输出并逐字引用关键事实。在 τ-bench、τ²-bench 和 VitaBench 上，用五个骨干模型测试，U-Fold 在 45 个格子中的 37 个胜过 ReAct，平均提升 1.1 到 3.4 分，在噪声工具输出场景下优势更大（27.0 对 11.0）。文章还提醒 FDE 注意成本：每条消息触发两次额外调用，且抽取器每次读取全部工具历史。

要点

  • 传统折叠方法为单目标任务设计，多轮对话中会丢失细粒度约束

一分钟读完这篇论文

大多数上下文折叠方法都是为单一长任务、单一目标设计的：研究一个问题、修复一个 bug。它们会总结旧步骤并丢弃原始内容。浙江大学、阿里巴巴通义实验室和西湖大学的 Jin Su、Runnan Fang、Fajie Yuan 及其同事们研究了一个不同的场景：一个 agent 与用户进行多轮对话、调用工具，而用户不断提出新需求并改变主意。在这种场景下，他们发现了两个失败点：摘要会丢失之后会用到的细粒度约束，而且无法跟踪用户当前的真实意图。

他们的开篇示例：一位用户选择了一家香薰店，工具记录显示其营业时间为 12:00，然后要求预订“周六上午 11 点，如果不行就下午 2 点”。一个普通的折叠摘要保留了店名和套餐信息，却丢失了营业时间，于是 agent 预订了上午 11 点。

U-Fold 从不丢弃任何内容。它保存完整的对话以及每一次工具调用和结果。每当收到新的用户消息时，它会通过两次额外的模型调用来重建 agent 的工作上下文。Conversation Summarization（对话摘要）模块重写一份按时间顺序排列的摘要，跟踪目标、约束和用户改变主意的记录，并以一份尚未完成事项的待办清单结尾。Dynamic Data Extraction（动态数据提取）模块读取该摘要以及完整的工具历史，按行范围选出重要的观察行，并逐字保留事实和约束，同时为 agent 提供提示。随后主 agent 基于摘要、提取的数据和新消息运行其常规的 ReAct loop。

在使用五个骨干模型的 τ-bench、τ²-bench 和 VitaBench 上，U-Fold 在大多数测试项中比 ReAct 高出几个百分点，并大幅超越“摘要后丢弃”的基线方法，尤其是在工具输出冗长且充满噪声的情况下。

上下文折叠方法通过总结并丢弃历史来适应预算限制。它们是为单目标任务构建的。在多轮客户对话中，摘要会丢失细粒度约束（营业时间、数量、ID），并落后于改变主意的用户，导致 agent 基于过时或不完整的事实采取行动。

永不丢弃。保存完整的对话和工具日志，并在每条新用户消息到来时通过两次 LLM 调用重建 agent 的工作上下文：一个摘要器撰写按时间顺序的摘要和待办清单，一个提取器按行范围选出相关的工具输出行，并逐字陈述事实和约束。

在 τ-bench、τ²-bench 和 VitaBench 上使用五个骨干模型，U-Fold 在 45 个单元格中的 37 个击败了 ReAct，每个骨干模型平均领先 1.1 到 3.4 分，并领先 ReSum 和 IterResearch 3.1 到 27.0 分。在 VitaBench 上加入噪声工具输出后，它得分为 27.0 对 11.0（In-store）和 12.0 对 4.0（Cross-Scenarios）。

为什么这对 FDE 很重要

面向客户的 Agent 天然是多轮的：预订、下单、支持、账户变更。在这些部署中，丢失一个约束条件就会变成一个错误的订单和一笔退款。

不要让摘要成为唯一的副本。 U-Fold 的核心做法是保留原始历史记录，并将每个摘要视为可丢弃的视图。任何部署都可以采用这一点。存储完整日志，并重建工作上下文，而不是替换它。

显式跟踪意图。 一个每轮重写的待处理用户请求的运行待办清单，是一种低成本的机制，能让“用户改变了主意”对 agent 可见。

引用工具输出，不要转述。 提取器通过行范围引用工具输出并逐字复制事实，因此 ID、营业时间和价格永远不会被改写。

自己计算成本。 每条用户消息会触发两次额外的模型调用，且提取器每次都会读取整个工具历史。论文报告的是主 Agent 的 context length，而不是总 token 数或 latency。使用 prompt caching 时，这一差异可能会逆转成本格局。
