FDE 分解面试：一页纸方法论

原标题：The FDE decomposition interview: the method on one page

FDE Interview Prep · 2026 · 约 11 分钟读完

摘要

这篇文章以医院翻译服务案例为例，拆解 Palantir 等公司 FDE 面试中的开放式问题（decomposition）环节的答题方法。作者提出六步框架：先澄清问题定义，再梳理利益相关者与指标、数据来源、按风险排序的工作流、最小可行版本（v0）和失败模式，最后用四部分收尾。文章引用 Palantir 官方建议（先给出可落地方案再扩展）、多位候选人在 Blind 和 Aced 上的面经，以及 OpenAI 前沿部署工程负责人 Colin Jarvis 的观点，说明该环节兼具案例面试与系统设计的特点。文中还给出示例 SQL、白板记录方式和评分标准，并指出常见失败模式：只做应用、只谈利益相关者或过度设计架构。

要点

  • 以医院翻译应用案例演示 FDE 分解面试的完整答法。
  • 方法分六步：澄清、利益相关者、数据输入、按风险排序、v0、失败模式。
  • Palantir 官方建议：先交付可运行的想法，再逐步扩展。
  • 候选人面经显示该环节可能带数据集，需写查询或设计 API。
  • 常见失误：直接做应用、只谈干系人、为小数据量设计复杂架构。

这个题目是一道分解轮：一个有多个合理答案的客户问题，加上时间限制。这里的方法和评分标准是我们自己的；没有雇主会公开这些。

方法详解，逐步展开

进入每个步骤时说出其开场白，离开时做一次交接，最后以四部分收尾。一位曾在 Palantir 工作的 Blind 用户在 2025 年 3 月提出过类似的流程，他表示很难给出一个放之四海皆准的答案：先提问，拆解问题，构建一个实用的解决方案，然后扩展这个 v0，即第一个可运行的版本。来源 12Palantir FDSE 面试 (Blind)发布方Blind (Teamblind)来源类型Blind 上的候选人报告来源 13Palantir 伦敦面试求助 !!! (Blind)发布方Blind (Teamblind)来源类型Blind 上的候选人报告

  • 澄清。“在我设计任何东西之前：您说的等待时间过长，是从什么时候到什么时候？”院长指的是投诉，翻译服务指的是从提出请求到翻译到位，患者指的是从办理入院到翻译进入房间。在这里，等待集中在较少使用的语言和下午的门诊，而且知情同意需要合格译员。
  • 利益相关者与指标。“谁做决定，谁使用它，谁付钱，谁可能阻拦它？”院长做决定；排班员和护士长使用它；翻译服务付钱；合规和 IT 安全可能阻拦它。指标：每周没有翻译就开始的预约数量；护栏指标：翻译成本。今天没人知道当前数值，所以先测量。
  • 输入。“对每个数据源：谁负责，数据多新，有什么问题，谁批准访问？”请求日志是事后录入的，没有预约 ID，因此在每次请求前两天内按病历号（MRN）匹配：一个匹配是干净的，两个是模糊的，没有则未匹配。
  • 按风险划分工作流。“风险最大的未知数放在最前面，这是我否定的顺序。”这里的关键是等待是否集中：如果是，提前预约就能解决；如果不是，那就是人员配置问题。先测量等待发生在哪里；第一天就申请排班数据的访问权限。以应用为先的顺序行不通：应用无法显示缺口在哪里。
  • 。“这是真实用户很快就能用上的最精简版本。”每天晚上，翻译服务和护士长会收到第二天需要翻译的预约，并附上已指派的译员或“暂无”。两周内就能看出提前预约是否能填补大部分缺口。接下来，AI 应该用在错误会被发现的地方：它用患者的语言起草提醒模板，由一名合格译员逐一审核或纠正一次，这些纠正就成为测试集。绝不用于知情同意谈话。
  • 失败模式。“这可能会怎样失败，我们如何尽早发现？”数据：语言字段为空或错误，因此未知项保留在列表中，第一周通过办理入院时的未知项数量来评估规模。危害：为患者预约了错误语言的译员，可通过译员报告的不匹配情况发现。组织层面：以每分钟成本为考核指标的翻译服务部门可能不愿预约付费的视频译员；信号是门诊开始时缺口仍然存在。

一次交接只推进一个决定：

候选人：“这些信息足够让我下判断了。第一版是一个晚间清单，我假设语言字段大部分是填好的。下一步：谁会参与其中。”

被推向应用时，把它保持为一个假设：

面试官：“主任有这个应用的预算。为什么不直接把它做出来？”候选人：“这个选项仍在考虑中。首先：上个月没有口译员的预约中，有多少是应用支持的语言？如果占多数，就先做应用。”面试官：“没人有这个数字。”候选人：“那么找到这个数字就是第一个工作流，而晚间清单用的是同一份数据。应用等答案出来再说。”

当时间快用完时，分四部分收尾：问题、第一版、最大的风险，以及周一的行动。

候选人：“总结一下：等待的根源是少数几种语言在下午门诊的预约太晚，而不是翻译本身。第一版是每晚生成明天的清单；下一版加入由口译员确认的 AI 提醒。最大的风险是语言字段空白或填错，所以未知情况也列入清单。周一我会申请排班系统的只读权限。”

具体性贯穿每一步：带主键的实体、一个界面，以及一个决定取舍的量级估算。把实体说出来：

patient(mrn, preferred_language)
  language set once, at registration
appointment(appointment_id, mrn,
            clinic, starts_at)
request_log(request_id, mrn,
            language, typed_at)
  no appointment_id
Volume: ~1,500 appointments a day,
a few hundred on the list

如果被问到，写出核心查询：明天的预约按 MRN 关联患者，筛出非英语者，未知情况保留。

SELECT a.starts_at, a.clinic, a.mrn,
       COALESCE(NULLIF(TRIM(p.preferred_language), ''), 'unknown')
         AS language
FROM appointment AS a
JOIN patient AS p ON p.mrn = a.mrn
WHERE a.starts_at >= :tomorrow AND a.starts_at < :day_after
  AND COALESCE(NULLIF(TRIM(p.preferred_language), ''), 'unknown')
      <> 'English'
ORDER BY language, a.starts_at;

排班员在口译员一栏手动输入：这正是第一版所模拟的。每晚几百行意味着只需在报表副本上跑一个查询，无需数据管道。

第二个查询统计每个请求的候选预约数量。其中没有候选或有两个及以上候选的占比，就是你的第一个数据质量指标。

WITH matched AS (
  SELECT r.request_id, COUNT(a.appointment_id) AS candidates
  FROM request_log AS r
  LEFT JOIN appointment AS a
    ON a.mrn = r.mrn
   AND a.starts_at <= r.typed_at
   AND a.starts_at >= r.typed_at - INTERVAL '2 days'
  GROUP BY r.request_id
)
SELECT LEAST(candidates, 2) AS candidates, COUNT(*) AS requests
FROM matched
GROUP BY 1
ORDER BY 1;

优先改进什么

取你低于 3 级的最低门槛项，否则取你的最低分项，并在下次运行前演练其改进方法。

在我们的评分标准中，先澄清再解题、可运行骨架和技术具体性是门槛项。通过：加权分数达到 3 级或以上，每个门槛项达到 3 级或以上，没有任何项低于 2 级。倾向通过：加权分数达到 2.3 级或以上，每个门槛项达到 2 级或以上，没有任何项为 0 级。其他情况均为“尚未达标”。10 分钟运行会对每个维度打分，但不给出判定。没有 Pro 时，记分卡上的下一步会链接回这里。判定是我们评分标准的训练信号，不代表对任何公司决策的预测。

每个维度都有一个用于纠正它的练习和一个用于教授它的课程：

维度需要演练的改进
先澄清再解题（门槛项）说出每个答案会翻转哪个取舍；在标注假设的前提下做出承诺
利益相关者与成功指标谁来决策、使用、付费和阻碍；一个带当前值的指标
输入、负责人与新鲜度每个数据源的负责人、新鲜度、访问方式和关联键
分解与排序风险最高的优先，以及你否决的顺序
行走骨架（关卡）一个真实用户、真实数据、一个决策，以及你伪造的部分
失败模式不同类型的风险，其中一个是组织层面的，每个都配一个第一周的信号
沟通边想边说，说出每一步，随时记录事实，用四个部分收尾
技术具体性（关卡）带键的实体、一个接口、一个能决定方案取舍的数据量

针对每个关卡，给出一个弱回答和一个强回答：

  • 澄清。 弱：“预算和时间线是什么？”无论答案如何都不改变你要构建的东西。强：“你说的太长，是指从请求到到达的时间，还是指开始时没有翻译在场的预约？第二种会改变我要构建的东西。”
  • 行走骨架。 弱：“我们会构建一个排班平台。”没人会很快用上它。强：“明天的预约清单，每晚通过邮件发给翻译服务部门，每个预约一行，指派的翻译由人工填写。”
  • 技术具体性。 弱：“我们会把数据拉进数据仓库。”没有表，没有规模。强：“预约表通过病历号（MRN）与患者表关联。每晚几百行，所以一条查询即可，无需流水线。”
