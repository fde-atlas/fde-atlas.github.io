Snowflake FDE 岗位：Cortex Analyst 与语义模型

FDE Times · 2026-10-30 · 约 4 分钟读完

摘要

文章通过 Snowflake 两则已关闭的 FDE 招聘启事，分析数据平台方向前沿部署工程师的实际工作重心：不在 LLM 本身，而在语义模型。Cortex Analyst 处理结构化数据、依赖 YAML 或语义视图描述指标定义；Cortex Search 以混合检索处理文本，用于 RAG 和企业搜索；FDE 还需用 Streamlit 构建生产级看板，并把评测纳入构建流程。作者建议先学 SQL 与数据建模，再学 Python、Streamlit 和检索技术。

要点

  • FDE 的核心工作是构建语义模型，而非调优 LLM。
  • Cortex Analyst 面向结构化数据，需提供语义模型才能准确作答。
  • Cortex Search 用向量加关键词的混合检索处理文本，服务 RAG 与企业搜索。
  • 指标定义分歧是常见阻碍，需与客户当面敲定并写入模型。
  • 评测应从第一天开始，用带标准答案 SQL 的问题集验证每次修改。

Cortex Analyst 管表格，Cortex Search 管文档，FDE 要做的是让客户数据的含义准确无误。

要点速览

  • Cortex Analyst 是一项托管的、基于 LLM 的功能，通过 REST API 调用。答案是否正确取决于语义模型。
  • Cortex Search 对文本执行混合检索（向量加关键词），主要用于 RAG 和企业搜索。
  • Snowflake 的两则 FDE 招聘启事都提到：构建语义模型、开发原生 Streamlit 看板，并把评测作为构建过程的一部分。

Snowflake 曾发布一个岗位，名为“Forward Deployed Engineer - Finance Analytics & AI Specialist”，该招聘已于 2026 年 7 月 8 日关闭。启事中提到的产品包括 Cortex Analyst、Cortex Agents、Cortex Search、Cortex Code 和 Snowflake CoWork。

比产品清单更能说明问题的，是对工作内容的描述：构建并持续改进语义模型，让用户能通过 Cortex Analyst 用自然语言查询客户的数据表。

这个细节说明，前线部署工程师（FDE）的大部分工作落在赋予数据含义的那一层，而不是 LLM 本身。

如果打算申请数据平台方向的 FDE 岗位，无论是否在 Snowflake，与其背功能清单，不如弄懂下面三个工具，以及它们如何配合。

不同的问题用不同的工具

Snowflake 文档将 Cortex Analyst 描述为一项全托管、基于 LLM 的 Cortex 功能，用于构建能回答结构化数据业务问题的应用。它以 REST API 形式提供，可以嵌入任何应用。要让它理解数据，必须提供语义模型。

Cortex Search 处理的是另一类问题。它是一项混合检索服务，结合向量检索与关键词检索，作用于文本数据，支持低延迟的模糊搜索。

按文档的说法，它的两大用途是 RAG 和企业搜索。合同、邮件、对账备注交给 Cortex Search；存放在表里的数字交给 Analyst。

Streamlit 是一个用于构建 Web 应用的开源 Python 库。Streamlit in Snowflake 让开发者在 Snowflake 内部构建、部署和共享这类应用，数据无需离开 Snowflake。招聘启事写明，FDE 要以原生运行在 Snowflake 中的 Streamlit 应用形式，构建财务、运营和分析看板。这些是生产环境中的看板，不只是演示。

Cortex Analyst

  • 结构化数据：表、列、数值
  • 需要一个描述数据含义的语义模型
  • 通过 REST API 调用

Cortex Search

  • 文本数据
  • 结合向量与关键词的混合检索
  • 用于 RAG 和企业搜索

语义模型才是真正的产品

根据文档，Cortex Analyst 的语义模型写在一个轻量的 YAML 文件中。对于新部署，Snowflake 推荐使用语义视图（Semantic Views），放在 stage 上的 YAML 文件仍然受支持。

语义视图是 schema 级别的对象，包含四个组成部分：逻辑表、维度、事实和指标。Snowflake 将指标定义为衡量业务表现的量化度量。

假设财务团队问：“上季度各区域的净收入是多少？”客户有一张订单表和一张区域表。逻辑表就是这两张表；维度是区域和季度；事实是每条订单明细的金额、退款和折扣；指标是净收入。

难点在指标。销售部门可能把净收入当作订单总额，会计部门则会扣除退款和折扣。下面的示意只用来说明这个定义如何写进模型，并非准确语法，具体字段名请查阅 Snowflake 的规范。

# 示意草图，并非准确的 Snowflake 语法
logical_tables:
  - name: orders
    dimensions: [region, quarter]
    facts: [amount, refund, discount]
metrics:
  - name: net_revenue
    description: "订单总额减去退款和折扣，以会计部门批准的定义为准"
    expr: SUM(amount) - SUM(refund) - SUM(discount)

如果没有会计部门认可的

expr

和

description

这两行，模型照样能生成 SQL，但只能猜测提问者的意思。结果就是答案看上去合理，实际却是错的。

所以到了客户现场，第一件事是和财务用户坐下来，用文字写清每个指标的定义，然后才打开编辑器。

招聘启事提到，FDE 要在客户现场与对方团队一起工作，随时清除部署中的阻碍。和用户一起敲定指标定义，正是这类阻碍的典型例子。

从一开始就做评测

另一个岗位“Forward Deployed Engineer, Applied AI”隶属 Cortex AI 团队，该招聘同样已关闭。入职者将基于 Snowpark 和 Cortex 构建生产级 AI 系统，至少 25% 的时间要在 Snowflake 最具战略意义的客户现场工作。

启事还强调，评测必须是构建过程的核心环节，而不是留到以后再做。

对 Cortex Analyst 而言，最直接的评测方式是整理一组样例问题，每个问题都配有财务用户认可的答案 SQL。每次修改语义视图，就把整组问题重跑一遍，对比结果。

回到净收入的例子。如果测试集里有这个问题，且标准答案扣除了退款和折扣，那么定义错误在第一次运行时就会暴露，而不是在和 CFO 开会时才冒出来。

局限与学习顺序

第一个局限是工具之间的边界：Analyst 处理结构化数据，Search 处理文本。招聘启事在同一产品套件中还列出了 Cortex Agents；如果客户的问题同时需要表格和文本，这就是下一步该去文档里研读的内容。

第二个局限是，答案的质量上限取决于语义模型。模型答错时，先检查定义，再怀疑 LLM。

至于学习顺序，先学 SQL 和数据建模，做到能在真实数据集上分清维度、事实和指标。然后学够用的 Python 来构建 Streamlit 应用，再学 RAG 和混合检索，以理解 Cortex Search。

简历上不要写“熟悉 Cortex”，而要描述自己构建过的一个语义模型：有多少个指标，测试集里有多少个问题，每次修订后正确率提升了多少。

Snowflake 把 AI 工具放在紧挨数据的位置。因此，这些岗位要的是能讲清客户数据表含义的人。
