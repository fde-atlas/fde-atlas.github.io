反洗钱 AML Agent 如何通过合规审批

FDE Times · 2026-11-06 · 约 5 分钟读完

摘要

这篇文章面向金融领域的 FDE，讲解 AML 预警审核 Agent 如何通过银行合规审批。核心观点是上线决定权在合规而非工程团队，合规证据必须从第一周开始准备。文章引用 Wolfsberg Group 2025 年 8 月声明、Co-Investigator AI 研究、FinCEN 2025 年 10 月 SAR FAQ 及 2026 年 4 月 SR 26-2 指引，给出三大支柱对应的交付物、试点漏报案例的数字化分析方法，以及需要由客户机构决定的三件事：叙述模板、日志范围和适用的模型政策。

要点

  • Agent 只提建议，关闭或升级的决定和签字必须由人类调查员完成。
  • 合规要三样东西：验证证据、漏报风险的具体数字、每条建议的解释。
  • 用已结案预警做试点，逐个分析漏报案例，而非只报准确率。
  • 叙述模板、日志字段和适用政策应由客户机构决定，写代码前先问清。
  • 第一周与合规和模型治理开联席会，拿到书面确认的三项结论。

第六周才第一次见合规，大部分架构可能要重做，所以合规要的证据得从第一周开始准备。

要点速览

  • AML 预警审核 Agent 只提建议，决定和签字仍由调查员完成。
  • 合规需要三样东西：验证证据、漏报风险的具体数字，以及每条建议的解释。
  • 记录什么日志、采用哪种叙述模板、Agent 归哪项模型政策管，都由机构决定。写代码前先问清楚。

你刚接到任务，要把一个 Agent 接入某家银行的反洗钱（AML）预警队列。这个 Agent 读取交易历史，汇总了解你的客户（KYC）档案，对每条预警给出关闭或升级的建议，并起草可疑活动报告（SAR）的叙述部分。演示很顺利，客户的工程团队非常满意。

但上线时间不由工程团队决定，而由合规决定。如果到第六周才第一次见到合规，很可能要重做大部分架构。

这类项目越来越常见。Wolfsberg Group 是由多家大型银行组成、负责制定金融犯罪领域标准的协会。它在 2025 年 8 月的一份声明中指出，金融机构正逐步把自动化、AI 和 ML 纳入可疑活动监测策略。

因此，对前线部署工程师（FDE）来说，稀缺的能力不是调用 LLM，而是让 Agent 通过合规审批。

合规到底需要看到什么？

Wolfsberg 的负责任创新框架有三大支柱：切换到新工具时的验证；在模型风险与金融犯罪风险之间取得平衡；可解释性，即外部人员能清楚看到系统覆盖了多少范围、效果如何。

从工程师的角度看，每一条支柱都是一项要交付的成果，而不是口号。

第二条支柱最容易被误解。模型风险是 Agent 出错的可能性。金融犯罪风险是洗钱行为漏网的可能性，原因可能是 Agent 判断错误，也可能是旧流程太慢、跟不上。

合规并不要求 Agent 完美无缺。他们要看到两种风险放在一起比较，而且用具体数字说话。

用数字走一遍试点

假设你提议让 Agent 处理上季度调查员已经结案的 200 条预警。这些预警的结果都已知，因此是你手里最好的评测集。假设 Agent 建议关闭 150 条、升级 50 条。

工程团队会盯着那 150 条：队列里四分之三的预警可以处理得更快。合规会马上问另一个问题：Agent 想关闭的 150 条里，有多少条当初被调查员升级了？

如果答案是 6 条，这 6 个案例就是会议的焦点。你需要逐一打开，解释 Agent 为什么漏掉，并提出修正方案。

这就是用数据平衡风险。不要说“Agent 准确率 97%”，而要说：Agent 缩短了这类预警的处理时间，代价是 6 个漏报案例，在当前阈值下尚不可接受，补救办法是这样的。面对这样的表述，合规才能做出决定。

同一个例子也说明了为什么 Agent 不能自行关闭预警。Co-Investigator AI 是 2025 年一项关于起草 AML 叙述的 Agent 的研究，作者强调，人类调查员始终要牢牢留在流程中。在你的设计里，让 Agent 写“建议”，让人来按“决定”按钮。

记录什么、怎么写，由谁决定？

有三个问题，工程师往往自己就定了，其实应该由客户机构来决定。第一是叙述模板。Co-Investigator AI 研究指出，不同金融机构的 SAR 叙述质量差异很大。Agent 可以帮助统一标准，但统一成哪种模板，必须在你写提示词之前由合规确定。

第二是日志。同一项研究倾向于为每个 Agent 设计完整的审计日志。但具体记录多少，取决于规则怎么要求。

2025 年 10 月 9 日，FinCEN 与美国银行业监管机构发布了一组 SAR 常见问题解答（FAQ），以减少金融机构不必要的合规工作。据律师事务所 Orrick 的分析，这组 FAQ 明确：法律并不要求记录不提交 SAR 的决定，也不要求在 SAR 提交后重新复核。

所以 Agent 记录什么，是客户的政策选择，不是你的选择。先让合规确定必填字段清单，再让 Agent 针对每条建议严格记录这份清单，而不是默认“全部记录”或“干脆不记”。

第三是 Agent 适用哪项政策。2026 年 4 月 17 日，Fed、FDIC 和 OCC 发布了关于模型风险管理的 SR 26-2，取代沿用多年的 SR 11-7。

据 Baker Tilly 称，新指引没有涉及生成式 AI，AI 将通过单独的指引或规则来处理。所以要直接问客户的模型治理团队：这个 LLM Agent 将依据哪项内部政策审批？

按什么顺序做？

第一周，申请与合规和模型治理团队开一次联席会议，带上前面那张三大支柱表格。目标是会后拿到书面确认的三件事：Agent 的职责范围（只建议，不决定）、可接受的漏报阈值，以及 Agent 适用的模型政策。

接下来，索取已批准的叙述模板和必须记录的数据字段清单。两样都拿到后，再写提示词和日志 schema。然后在已结案预警上运行试点，第二次开会时带上每一个漏报案例，而不是只给一个汇总数字。

最常见的四个错误都源于同一个习惯：工程师替合规做了本该由合规做的决定。

  • 先做出来，再去申请审批。
  • 为了“节省时间”，让 Agent 自行关闭预警。
  • 不核对政策就自行决定日志级别。
  • 以为现有的模型验证流程自动适用于 LLM。

职业方面，如果你瞄准的是金融领域的 FDE 岗位，要牢牢掌握本文涉及的概念：AML、KYC、SAR 和模型风险管理。

如果你曾带着一个系统走完控制职能部门的审批流程，就在简历上用结果来写：你设计了试点，控制职能部门设定了某个阈值，系统在某些条件下获得批准。

谈到这段经历时，先讲你打开了哪些漏报案例、如何处理，因为这才能说明你懂风险，而不只是会写提示词。
