公开写作能帮你获得 FDE 职位吗？真的有效吗？

原标题：Write in public to get hired as an FDE: does it work?

FDE Times · 2026-10-09 · 约 7 分钟读完

摘要

文章讨论公开写作项目复盘能否帮助求职者获得FDE（前沿部署工程师）职位。Robert Half调查显示67%的美国HR负责人认为AI生成的简历拖慢了招聘，使简历上的修饰失去说服力。作者认为，项目复盘的价值不在于吸引招聘者注意，而在于面试官核查你时提供可验证的证据：真实部署、API、认证、日志以及坦诚列出已知局限。文章建议只写一个完整项目，围绕用户故事、架构决策和失误展开，并配合内推使用效果最佳。

要点

  • 67%的美国HR负责人认为AI简历拖慢招聘。
  • 项目复盘的价值在于被核查时提供可验证证据。
  • 真实部署加坦诚的已知局限最难被AI伪造。
  • 建议只写一个完整项目，按用户故事与架构展开。
  • 内推开门，复盘供面试官验证，两者结合最有效。

简要概述

  • Robert Half 的一项调查发现，67% 的美国 HR 负责人表示审阅 AI 生成的简历拖慢了招聘速度，这使得可核实的证据更有价值。
  • 一个公开项目要有分量，需要具备真实的部署（包括 API、身份验证和日志），以及一份清楚说明架构和已知局限的 README。
  • Hacker News 上的说法表明，简历很少被仔细阅读，内推也并非稳操胜券。当有人已经在调查你时，一份项目报告才会带来回报。

2026 年 3 月，招聘公司 Robert Half 发布了一个求职者应当思考的数字：67% 的美国 HR 负责人表示，审阅 AI 生成的简历拖慢了招聘速度。雇主收到的申请更多了，但选定人选却需要更长时间。

在 Hacker News 上一个询问“既然 AI 能写简历，如今哪些新的招聘信号更重要”的讨论帖中，一位评论者半开玩笑地表示，一份过于精致的简历很可能是 AI 的作品。按照这个逻辑，一个小小的失误反而成了真人的标志。

当精致的简历几乎不需要花费任何精力时，精致便失去了价值。Robert Half 得出结论：雇主越来越需要能够核实候选人技能的可信之人。

如果你的目标是 FDE 职位，这就是你要面对的问题。The Pragmatic Engineer 指出，大约从 2025 年初开始出现了一波 FDE 招聘热潮，截至 2026 年 5 月，需求仍被描述为居高不下且持续增长，Google、OpenAI 和 Anthropic 都在大规模招聘。

那么，公开撰写关于你项目的文章能否帮助你在众多申请中脱颖而出？能，但很少是通过让招聘者主动找到你。一篇关于将项目推向生产的报告最有价值的两个时刻是：你还在学习的时候，以及有人已经想要核实你的工作的时候。

FDE 招聘者想核实什么？

The Pragmatic Engineer 的作者 Gergely Orosz 指出，几乎每一位 FDE 雇主都在寻找具备扎实软件工程基础的人。这是基本门槛，而一个整洁的 GitHub 仓库可以证明这一点。

有些公司要求更多。Orosz 提到的 Commure 和 Matta 两家公司，看重端到端构建和交付项目的动手经验。而“交付”这一部分，仅凭代码无法讲述完整的故事。

FDE Academy 是一份关于 FDE 职业的指南，它建议候选人描述一个已经开发和部署的项目，而不仅仅是展示代码。Blockchain Council 走得更远：与其做许多小演示，不如以生产思维构建一个完整的公开产品。

根据该资料，这样的项目应该有真实的云端部署，包含 API 端点、基本身份验证和运行日志。随附的 README 应包含用户故事、架构图、运行说明和已知局限。

最后一项值得注意。演示永远不会展示其已知局限，但把它们列出来，能让读者知道你清楚自己的系统可能在哪些地方出问题。

两位候选人，一个项目

设想两位候选人，各自构建了一个读取客户支持工单并将结果写入 CRM 的 AI Agent。候选人 A 有一个整洁的代码仓库、一份包含安装说明的 README 和一个演示。候选人 B 有同样的代码仓库，外加一篇长文。

B 的文章解释了当 CRM 的 API 对请求限流时为什么需要队列，如何处理用户多年来手工输入的杂乱字段，以及每当 Agent 写错内容时如何向支持人员解释。

A 证明了扎实的软件工程基础。B 还证明了他们把一个项目从构建一路做到了上线，而这正是 Commure 和 Matta 这类公司所看重的。

这种差异在面试房间里最为明显。B 的面试官手头有现成的材料可以深挖：“如果客户不让你搭建队列，你会怎么办？”每一个扎实的回答都是 AI 难以替你写出来的证据。

A 的面试官则必须从零开始，而恰恰在这个时刻，他们完全有理由对一份看起来过于精美的简历心存怀疑。

没人读你的博客，除非它真正起作用的时候

不要对简历上的链接抱太大期望。在同一则 Hacker News 讨论串中，有人说招聘人员很少读简历，另一个人认为内推才是真正起作用的，却随即被告知在回复者所在的公司，连内推也不再享有优先权。

这些只是个人经历，并非数据，但足以说明没有捷径可走。所以不要把写文章当作让招聘人员发现你的途径。

Shawn Wang (swyx) 展示了另一面。他说自己的全部公开写作被提及，用他的话说，差不多帮他拿到了 AWS 的工作。注意这个动词：写作“被提及”，意思是它是在有人寻找时被发现的，而不是它主动去敲门。

Swyx 还指出了一个在任何人雇用你之前就会到来的好处。对他来说，公开写作是一种结构化的学习方式，读者会指出你错在哪里。让一个陌生人在博客上发现你队列设计中的缺陷，远比在面试中被发现要轻松得多。

每种信号分别能证明什么？

下表比较了 FDE 候选人通常拥有的四种信号。各列内容是基于上述建议和经历做出的编辑评估，而非实测数据。

信号用 AI 伪造的难度？（评估）能证明什么何时会被阅读
简历要点极易造假不经核实几乎毫无价值；过度包装反而会引起怀疑筛选阶段，如果有人看的话
仅含代码的 GitHub 仓库中等软件工程基础招聘人员愿意点开看的时候
附带真实部署的部署文章困难，因为它必须经得起追问一个端到端项目：用户故事、架构、局限性、运维面试官深入了解你或推荐人转述的时候
内推困难本身不证明任何能力，只是他人的背书筛选之前，如果内推仍然有优先权

没有任何单一信号是足够的。内推来得最早，但证明不了能力，而且据一些说法，它也不再是稳操胜券的了。

部署文章最有说服力，但通常最后才被读到。推荐人帮你打开门；文章则给面试官提供了可以核实的东西。把两者结合起来是最明智的策略。

如何写出一篇经得起“那又怎样？”拷问的文章

不要同时折腾五个项目；选一个。Blockchain Council 建议打造一个完整的产品是有道理的：一篇关于一个真实系统的深度文章，比五个演示更能给面试官提供深入挖掘的素材。

按照资料中 README 的相同章节结构来组织文章。以用户故事开头。对于上面提到的工单 Agent，可能是：支持人员浪费时间手动把结果复制进 CRM，而且遗留数据一团糟。

中间最长的部分讲架构和集成决策。画一张简单的图：工单进来，经过 Agent，进入队列，然后到达 CRM。然后诚实地描述一件你做错的事，比如第一次直接调用 API 结果被速率限制挡住了。

最后一部分讲已知局限：Agent 会把哪些类型的工单处理错，以及发生这种情况时你如何告知支持人员。附上真实部署的链接，包括其 API、身份验证和日志，让读者可以自行核实，而不是听你一面之词。

发布前的测试：重读每一段并问“那又怎样？”。任何无法回答这个问题、或者只是罗列所用技术的段落，都应该围绕一个具体决策及其背后的原因重写。

如果你的简历还没有为真实客户部署系统的经历，这篇文章就是证明你独立把一个系统从想法带到稳定运行的地方。

简历上的每个项目都应该有一行用部署语言写的描述，比如“交付了一个对接有速率限制的 CRM 的 Agent，能处理手工录入的数据”，并附上文章链接。

阅读职位描述时，留意“端到端”、“面向客户”或“集成”之类的措辞。这些正是你的文章可以作为证据的地方。然后在你请业内熟人内推之前，先请他们读一读这篇文章并给出反馈。

当人人都能拥有一份精美的简历时，最难伪造的，是一个真正运行过的系统留下的痕迹，以及一个经得起“那又怎样？”这一追问的故事。
