角色与基础知识

1. 用一段话说明 AI 工程师是做什么的？

答案： AI 工程师在 AI 模型之上构建软件产品和内部系统，这些模型大多是通过 API 访问或自行托管预训练的基础模型。这项工作包括设计模型所看到的上下文（提示词、检索到的文档、工具结果），将模型连接到数据和企业系统，构建评测以便了解其是否有效，并在生产环境中以安全、监控和成本控制的方式运行它。模型只是其中一个组件。AI 工程师负责的是围绕模型的整个系统。

面试提示： 最后用一句话谈谈你交付过的东西，例如“在我上一个项目中，这意味着一个检索管道、一个包含 150 道题的评测集和一个成本仪表盘。”这会让面试官知道你真正做过这项工作，而不只是读过相关内容。

2. AI 工程师与机器学习工程师、数据科学家有何不同？

答案： 每个角色的出发点不同，衡量标准也不同。

角色核心问题典型产出物
数据科学家数据告诉我们什么，哪个模型或分析能回答业务问题？分析、实验、notebook、训练好的模型、报告
机器学习工程师我们如何训练、服务模型，并让模型在大规模下保持可靠？特征管道、训练任务、模型注册表、服务基础设施
AI 工程师我们如何将基础模型转化为可用、安全的产品功能？RAG 管道、AI Agent、工具集成、评测套件、API、防护栏

在实践中，这些角色有所重叠。AI 工程师很少从零开始训练模型，但必须对机器学习有足够的了解，以便判断何时微调、小型分类器或传统模型比 LLM 更合适。

3. AI 工程师与前沿部署工程师相比有何不同？

回答： 两者都构建生产级 AI。区别在于他们所处的位置以及所负责的内容。AI 工程师通常在产品或平台团队工作，端到端地负责一个功能。前沿部署工程师则嵌入到特定客户中，在该客户的环境内负责最终成果，包括需求挖掘、复杂的集成、安全审查和利益相关者沟通。FDE 这一角色由 Palantir 推广开来。如今 AI 实验室和企业软件公司也在招聘 FDE。我们在 FDE 与 AI 工程师对比 中详细比较了这两个角色。

4. 什么时候不应该使用 LLM？

回答： 当确定性规则、SQL 查询、搜索索引或小型训练分类器能以更低成本、更可预测或更可解释的方式解决问题时，就不要用 LLM。例如：验证 PAN 格式、计算 EMI、按固定产品代码路由工单，或监管机构要求模型可解释的欺诈评分场景。LLM 的价值体现在非结构化语言上：总结、从杂乱文档中提取信息、基于文本回答问题，以及在工具之间进行选择。

面试提示： 面试官问这个问题是为了考察判断力。一个想用 LLM 解决所有问题的候选人是一个危险信号。

5. AI、生成式 AI 和智能体 AI 之间有什么区别？

回答： AI 是一个宽泛的领域，指执行需要智能的任务的系统。生成式 AI 是其中的子集，它生成新内容（文本、代码、图像、音频），通常使用基础模型。智能体 AI 则以循环方式使用生成式模型：模型进行规划、调用工具、观察结果，并以一定的自主性朝目标行动。每上升一步都会增加能力，同时也增加风险，因为系统从生成文本转变为执行操作。

6. LLM 应用的主要构建模块有哪些？

回答： 一个典型的生产级 LLM 应用包含以下层次：

  • 客户端或渠道：网页、Teams、WhatsApp 或 API。
  • 应用后端，负责处理身份验证、会话和业务规则。
  • 上下文组装：系统提示词、对话历史、检索到的文档和工具定义。
  • 模型访问层，通常位于网关之后。
  • 工具与集成。
  • 输入和输出上的防护栏。
  • 可观测性：追踪、日志、成本。
  • 评测：离线测试集和在线反馈。

弱候选人只会列出模型和向量数据库。强候选人无需被问及就会提到评测和可观测性。

7. “从 AI 演示到企业成果”对你来说意味着什么？

回答： 演示只能证明模型在友好的输入上一次性完成某个任务。而企业成果意味着该任务能在真实约束下——权限、审计、延迟目标、预算和变更管理——为真实用户、在真实数据上可靠地完成。这两者之间的差距正是大多数 AI 工程投入所在，也是大多数项目失败的地方。请具体指出这些差距：数据质量、访问控制、评测、边缘情况、集成、监控和用户采纳。我们关于 为什么 AI 演示在企业生产中失败 的文章列出了这些失败模式。

面向 AI 的 Python 与软件工程

8. 对 AI 工程师来说，哪些 Python 技能最重要？

回答： 以下技能最重要：

  • async I/O，因为模型调用和工具调用都受网络限制；
  • 类型提示和 Pydantic 模型，用于结构化输入和输出；
  • 一个 Web 框架，例如 FastAPI；
  • 带超时和重试的 HTTP 客户端；
  • 流式响应；
  • 打包和依赖版本锁定；
  • 使用 pytest 进行测试，包括对模型调用的 mock；
  • 使用 pandas 或 polars 进行基本数据处理。

Notebook 适合探索，但生产代码需要模块、测试以及独立于代码之外的配置。我们的 面向 AI 工程师的 Python 指南涵盖了这套工具。

9. 为什么调用 LLM 时 async 很重要，有哪些陷阱？

回答： 一次模型调用可能需要数秒。使用同步代码时，单个 worker 在此期间会闲置。Async 让一个进程能够处理许多并发请求，并让你可以并行地展开独立的调用，例如多个检索或工具调用。陷阱包括：

  • 在 async 路由中使用阻塞式库，例如同步数据库驱动，会卡住整个事件循环。
  • 无界的并发可能触发提供商的速率限制。请使用信号量。
  • 没有超时设置的请求可能永远挂起。
  • 聚合任务中的异常如果无人处理就会丢失。

面试提示： 提到

asyncio.gather

并发限制和每次调用的超时。这能表明你确实在生产环境中运行过这些。

10. 如何从 LLM 获得可靠的结构化输出？

回答： 使用提供商原生的结构化输出或函数调用模式并配合 JSON schema，而不是在自由文本中要求 JSON。将 schema 定义为 Pydantic 模型并验证每个响应。如果验证失败，附带错误信息重试一次，之后回退到安全的默认值或人工处理。保持 schema 小而扁平，对分类字段使用枚举，只有当模型确实可能不知道该值时才将字段设为可选。符合 schema 的输出仍可能是错误的，因此你仍需要业务验证，例如检查所声称的金额是否超过政策限额。更多内容见 函数调用与结构化输出。

11. 如何为调用 LLM 的代码编写单元测试？

答案： 将代码拆分为确定性部分和非确定性部分。对确定性部分进行常规单元测试：提示词组装、解析、校验、工具路由和错误处理，将模型客户端 mock 为返回固定响应（包括格式错误的响应）。模型行为则用评测套件单独测试，针对真实模型运行并对输出打分。在 CI 中，每次提交都运行单元测试，并在提示词或模型变更时运行较小的评测子集。对真实模型输出断言精确的字符串相等非常脆弱，所以不要这样做。

12. 如何处理模型 API 的重试、超时和速率限制？

答案： 为每次调用设置明确的超时。只重试第二次尝试可能成功的错误（限流、5xx、连接重置），使用带抖动的指数退避并设置重试上限。遵守 retry-after 响应头。绝不要盲目重试有副作用的调用，例如创建工单的工具，这类场景应使用幂等键。在提供商前面加一个熔断器，这样提供商故障时可以优雅降级——切换到备用模型或返回“稍后再试”的消息，而不是让成千上万个请求卡在队列里。在大规模场景下，网关可以集中管理速率限制和故障转移。参见 LLM 网关详解。

13. 你会如何组织一个 LLM 服务的代码库？

答案： 将以下关注点分离：

  • API 层：路由、鉴权、请求校验。
  • 编排：工作流或 Agent 图。
  • 提示词：以文件形式保存的版本化模板，而不是埋在代码里的字符串。
  • 检索：索引和搜索。
  • 工具：每个集成一个模块，使用类型化接口。
  • 模型客户端：一个适配器，便于更换提供商。
  • 配置：模型 ID、温度、限制。
  • 评测：数据集、评分器、运行器。

将模型 ID 和提示词放在配置中，这样修改它们就是一次经过审查、可测试的变更，而不是临时热改。

14. 在 AI 应用中，好的日志是什么样的？

答案： 使用结构化日志，每一行都带有请求或追踪 ID。对于每次模型调用，记录模型 ID、提示词版本、token 数量、延迟、成本估算、所有工具调用及其参数和结果、护栏决策以及最终状态。只有在策略允许的情况下才存储完整的提示词和响应，并在记录日志前对 PII 进行脱敏。对于多步骤 Agent，OpenTelemetry span 这类追踪比扁平日志更有用，因为它们能显示哪个步骤慢或失败了。

LLM 基础

15. 请具体解释 LLM 是如何生成文本的，不要含糊其辞。

回答： LLM 是一种 Transformer 模型，通过训练来根据前面的 token 预测下一个 token。在推理时，它对输入 token 进行编码，计算下一个 token 在词表上的概率分布，采样或选择一个 token，将其追加到序列中，然后重复这一过程，直到满足停止条件或达到 token 上限。模型并不会查询事实数据库。它“知道”的一切都编码在训练得到的权重中，再加上你放入上下文的内容。这就是为什么接地（grounding）和评估如此重要。我们单独的 LLM 面试题 对模型内部机制有更深入的讲解。

16. 什么是 token 和上下文窗口？它们为什么对工程师很重要？

回答： Token 是模型读取和写入的子词单位。定价、延迟和限制都以 token 计算。上下文窗口是模型在单次调用中可以关注的最大 token 数（输入加输出）。工程上的影响包括：

  • 长提示词成本更高，并且会拖慢首 token 的生成时间。
  • 非常长的上下文可能把相关事实“埋”在中间。
  • 非英语文本（包括印度语言）每个词往往消耗更多 token。
  • 你必须为输出预留空间。

17. temperature 和 top-p 控制什么？该如何设置？

回答： 两者都控制采样中的随机性。Temperature 会缩放概率分布：值越低，模型越确定；值越高，输出越多样。Top-p（核采样）将选择范围限制在累计概率达到 p 的最小 token 集合内。对于信息抽取、分类和工具调用，应使用较低的 temperature。对于头脑风暴或创意文案，可以使用较高的值。只调两者之一，不要同时调整。一些专注于推理的模型会限制或忽略这些参数，因此请查阅每个模型的提供商文档。

18. LLM 为什么会产生幻觉？如何减少幻觉？

回答： 模型生成的是看似合理的续写，而不是经过验证的事实。当上下文中缺少答案，或问题引导出自信的语气时，模型就会用流畅的猜测来填补空白。减少幻觉的方法：

  • 将回答建立在检索到的来源之上，并要求提供引用。
  • 指示模型说“我不知道”，并实际测试它是否真的会这样做。
  • 降低 temperature。
  • 用 schema 约束输出。
  • 通过工具或数据库验证其陈述。
  • 在评测中衡量忠实度。

你可以减少幻觉，但无法完全消除它，因此要在 UX 和审批流程设计中考虑到这一点。

19. 什么是嵌入（embeddings）？它们与 LLM 本身有何不同？

回答： 嵌入模型将文本（或图像）映射为固定长度的向量，语义相似的输入会落在相近的位置。它通常是一个独立于生成器的、更小的模型。嵌入支撑语义搜索、聚类、去重和分类。你选择的嵌入模型决定了检索质量的上限：如果相关文本块从未被检索到，任何生成器都无法挽救答案。如果更换嵌入模型，你必须对整个语料库重新生成嵌入。

20. 什么是推理模型？什么时候值得使用它们？

回答： 推理模型在回答之前会花费额外的推理时算力进行中间思考。这能提升多步问题的表现，例如数学、规划、复杂代码和棘手的政策解读。它们成本更高、响应更慢。请将它们用于困难、低频的决策，或作为规划器。对于分类、抽取和格式化等高频、简单的步骤，请使用更快的通用模型。许多优秀的系统会同时结合两者。

21. 如何在大型托管模型、小型模型和自托管开放权重模型之间做选择？

回答： 从需求出发：任务难度、延迟、调用量、数据驻留、成本以及你能承担多少运维工作。大型托管模型在困难任务上最强，且无需基础设施。小型模型对于窄任务更便宜、更快，尤其是在微调之后。自托管开放权重模型让你掌控数据和版本，但你需要自己负责 GPU、扩缩容、补丁和安全。在候选模型上运行同一套评测集，用数据来做决策。

提示词与上下文工程

22. 提示词工程和上下文工程有什么区别？

回答： 提示词工程是编写指令：角色、任务、约束、示例、输出格式。上下文工程是更宽泛的工作，即决定每次调用时进入模型上下文窗口的所有内容：系统指令、选定的历史记录、检索到的文档、工具定义、工具结果、记忆和用户元数据。它还包括决定哪些内容不该放入。在生产系统中，大多数质量问题最终都是上下文问题（错误的文档、过时的历史记录、过多的工具），而不是措辞问题。参见上下文工程指南。

23. 生产级助手的优秀系统提示词应包含哪些内容？

回答： 一个好的系统提示词应涵盖：

  • 清晰的角色和范围：助手做什么、不做什么。
  • 依据规则：仅根据提供的来源回答，引用来源，当答案不在来源中时要明确说明。
  • 语气和受众。
  • 输出格式。
  • 升级处理行为。
  • 对测试中发现的常见边界情况的明确处理方式。

像代码一样对它进行版本管理和评审。不要在其中放入机密或授权逻辑。系统提示词不是安全边界，用户往往能让模型把它透露出来。

24. 少样本示例什么时候有帮助，什么时候有害？

答案： 当输出格式或风格难以用文字描述时，少样本示例会有帮助，例如特定的提取布局或边界模糊的分类任务。当模型照搬示例的表面细节、示例挤占了更有用的上下文，或使模型偏向示例中的标签时，它们会有害。应选择覆盖边界情况而非简单情况的示例；对于标签集较大的场景，可考虑按查询动态检索示例。要在评测集上对比有无示例的效果，而不是想当然地认为它们有帮助。

25. 在长对话中如何管理对话历史？

答案： 不要永远重发完整的历史记录。常见策略有：

  • 对近期对话轮次使用滑动窗口。
  • 对较早的轮次维护一份滚动摘要。
  • 将持久性事实（用户的账户类型、未关闭的工单 ID）提取到结构化状态中。
  • 当过去的轮次变得相关时，对其进行检索。

保持工具结果的紧凑：存储完整结果，但只把模型需要的字段传给它。要显式测试长对话行为，因为质量往往在多轮之后悄然下降。

26. 如何对提示词进行版本管理和测试？

答案： 将提示词作为模板存储在代码仓库中（或提示词注册表中），每个都带有版本 ID。把每次变更当作一次拉取请求来处理，运行评测套件并与上一版本的分数进行比较。在每次生产调用中记录提示词版本，以便将质量回退关联到具体的变更。对于有风险的变更，先在一小部分流量上灰度发布。LangSmith 或 Langfuse 等工具可以同时管理提示词版本和评测运行。

27. 什么是提示词链，什么时候它比一个大提示词更好？

答案： 提示词链将任务拆分为顺序调用，例如先分类，再检索，再起草，再检查。每一步职责单一，可以单独测试。当各步骤需要不同的模型或温度、需要验证中间结果，或单个提示词总是把任务的某部分做错时，链式方式优于一个大提示词。代价是更高的延迟、更多的调用和更多的故障点。如果单个结构良好的提示词能通过评测，就保持简单。

RAG

28. 解释 RAG 以及企业为什么使用它。

答案： 检索增强生成在查询时从你自己的数据中检索相关段落，并将其放入模型的上下文中，使答案基于最新、私有的来源。企业使用它是因为：

  • 知识更新的速度超过了重新训练模型的速度；
  • 答案需要引用以保证可信度和可审计性；
  • 可以在检索时实施访问控制；
  • 对于知识类需求，它通常比微调更便宜、更可控。

从什么是 RAG开始，并使用我们专门的 RAG 面试题来深入了解检索层面。

29. 请讲解 RAG 系统的索引和查询流水线。

答案：

INDEXING
sources -> parse -> clean -> chunk -> embed
        -> store (vectors + text + metadata + ACLs)

QUERY
question -> rewrite -> hybrid search (filter by ACL)
         -> rerank -> top-k chunks -> prompt
         -> LLM -> answer + citations -> checks

每个阶段都可能引入错误：解析丢失表格，分块拆散了从句，嵌入漏掉了缩写词，过滤器丢掉了正确的文档，重排序又把它排到后面。调试时，先找出失败的阶段，再去修改提示词。

30. 如何选择分块策略？

答案： 让文档结构和问题类型来决定。对于政策、合同和手册，基于结构的分块（按标题、章节或条款）通常优于固定大小切分。对于均匀的正文，带重叠的固定大小分块是合理的基线。保持表格完整，或将其连同表头转换为文本。为每个分块附加章节标题和文档元数据。然后用评测问题测试多种分块大小，并根据检索指标来选择。

31. 什么是混合搜索，为什么要加重排序器？

答案： 混合搜索将关键词搜索（BM25）与向量搜索相结合，前者能捕捉产品代码、错误 ID 和人名等精确词，后者能捕捉改写表述。两个结果列表会被融合，通常采用倒数排名融合。然后重排序器（通常是交叉编码器）针对查询对顶部候选结果重新打分，其精度远高于嵌入相似度，因此发送给模型的少数分块才是正确的。当出现“答案就在索引里，但 RAG 找不到”的情况时，这种组合是常见的解决方案。

32. 如何在 RAG 中实施文档权限控制？

答案： 在检索时实施权限控制，而不是在提示词中。在索引时为每个分块存储访问元数据（群组、角色、部门、敏感度标签），并从源系统同步。在查询时，从身份提供方（例如 Microsoft Entra ID）解析用户的身份和群组，并将其作为搜索查询中的强制过滤器。告诉模型“不要透露 HR 文档”并不是访问控制。还要处理权限变更：被删除的文档和被撤销的访问权限必须尽快反映到索引中，并且你应该测试这一点。

33. RAG 还是微调：如何决定？

答案： RAG 用于知识：会变化的事实、需要引用或需要权限控制的内容。微调用于行为：一致的格式、领域风格、狭窄的分类任务，或让较小的模型在特定任务上匹配较大模型的表现。当模型既需要领域行为又需要最新事实时，两者结合使用。先尝试提示词和 RAG，因为它们改动成本更低。参见 RAG vs 微调。

34. 什么是 Agentic RAG 和 GraphRAG，什么时候值得使用它们？

回答： 在 Agentic RAG 中，Agent 会决定是否检索、搜索哪个数据源、如何重新表述查询，以及结果是否足够好还是应该再次搜索。它有助于处理多跳问题和多数据源场景，代价是延迟增加和不可预测性。GraphRAG 则从语料库中构建实体和关系的知识图谱，并将其用于依赖关联关系的问题（“哪些供应商与跨地区的延迟发货有关联”）。两者只有在经过良好调优的普通 RAG 基线在某一可衡量的类别问题上失败时，才值得采用。

Agent 与工具

35. 究竟什么是 AI Agent？

回答： Agent 是一种系统，其中模型在循环中决定采取哪些行动来达成目标。它读取目标和上下文，选择工具，观察结果，并持续进行直到完成或达到限制。其定义性特征是模型控制流程。在固定工作流中，由代码控制流程，模型只是填充步骤。许多生产环境中的“Agent”实际上是带有一两个模型驱动决策的工作流，而这往往是正确的设计。想深入了解，请参阅我们的 agentic AI 面试题。

36. 工具（函数）调用在底层是如何工作的？

回答： 你向模型发送一份工具定义列表：名称、描述以及参数的 JSON schema。当模型判断需要某个工具时，它会返回一个结构化的工具调用请求，而不是文本。由你的代码（而非模型）验证参数、检查权限、执行工具，并将结果作为新消息发回。然后模型继续运行。模型本身从不执行任何操作。这就是为什么执行层是你实施授权、验证、速率限制和审计的地方。

37. 工作流还是自主 Agent：如何抉择？

回答： 当步骤已知且顺序很重要时，使用确定性工作流，例如审批、合规流程和数据管道。当路径取决于系统在过程中发现的内容时，使用 Agent，例如跨数据源的故障排查或研究。一个常见的折中方案是带有有界 agentic 步骤的工作流：一种图结构，其中某些节点允许模型在少数几个工具之间进行选择，并设有明确的出口和人工检查点。LangGraph 等框架对此有显式建模。

39. 如何防止 Agent 陷入循环或失控？

回答：在模型之外设置硬性限制：最大步数、每个工具的最大调用次数、每次运行的最大 token 数和成本上限，以及实际时间超时。检测重复行为，例如用相同参数调用同一工具。给模型一个明确的“完成”或“上报”动作。让工具错误信息足够详尽，使模型能够恢复，而不是盲目重试。记录每一步，以便看清循环从哪里开始。对于长时间运行的 Agent，应保存状态检查点，使失败后能干净地恢复，而不是重新开始。

40. Agent 可以拥有哪些类型的记忆？

回答：工作记忆是当前运行中的上下文和状态。短期记忆或会话记忆是本次会话的对话和中间结果。长期记忆是存储在模型之外（数据库或向量存储中）的事实、偏好或过往结果，并在相关时被检索。情景记忆记录过去的运行，供 Agent 从中学习。长期记忆会带来隐私和正确性问题：存储什么内容、谁能查看、如何更正或删除。

41. 多 Agent 系统什么时候是好主意，什么时候又是过度设计？

回答：当子任务需要不同的工具、权限或提示词时，多 Agent 设计很有帮助，例如一个 IT 运维系统中有独立的诊断、变更和沟通 Agent，或者当工作可以并行运行时。如果一个配备良好工具的单个 Agent 就能完成任务，那多 Agent 就是过度设计。每增加一个 Agent 都会带来协调开销、延迟、成本，以及新的失败模式，例如 Agent 之间互相误解。从一个 Agent 开始，只在评测或安全边界需要时才拆分，并保留一个监督者或显式图结构，使控制流保持清晰可理解。

评测

42. 为什么评测是 AI 工程师的核心技能？

回答： 如果没有评测，对提示词、模型、分块设置或工具的每一次改动都只是猜测，你无法区分改进和退化。有了像样的评测套件，你就可以安全地升级模型、比较供应商、在 CI 中捕获退化，并为利益相关者提供证据而非印象。在企业项目中，“我们如何知道它有效？”往往是决定试点能否获批进入生产环境的关键问题。完整方法参见 LLM 评测。

43. 如何从零开始构建评测数据集？

回答： 从真实或贴近真实的输入开始。从支持工单、搜索日志或领域专家那里收集问题。编写预期答案或验收标准，并为 RAG 提供来源引用。覆盖常见情况、边缘情况、必须拒绝或升级的问题、对抗性输入，以及数据中找不到答案的问题。从小规模开始，大约一百个精心挑选的条目，然后根据生产环境的失败案例扩充数据集。对数据集进行版本管理，并保留一部分留出集，以免提示词过拟合到测试集上。

真实案例： 以保险公司的理赔助手为例。最有价值的评测条目通常来自理赔员列出的那些“自信但错误的回答会导致错误赔付”的问题。这些条目值得用最严格的评分标准。

44. 你会用哪些指标来评测 RAG 系统？

回答： 分别测量检索和生成。

  • 检索： 上下文召回率（是否检索到了所需的段落？）、上下文精确率（检索到的内容中有多少是相关的？），以及针对标注来源文档的命中率或 MRR。
  • 生成： 忠实度（答案是否得到上下文支持？）、答案相关性、与参考答案相比的正确性，以及引用准确性。
  • 运营层面： 答案缺失时的拒绝行为、延迟和单次回答成本。

Ragas 等库实现了其中若干指标。比工具更重要的是，根据你自己数据上的人工判断来校准这些指标。

45. 什么是 LLM-as-a-judge（以 LLM 为评判者），它有哪些弱点？

回答： LLM-as-a-judge 使用模型根据评分标准对输出进行打分，例如“每个论断是否都有来源支持？是/否并说明理由。”它将评测扩展到人工无法审阅的规模。它的弱点包括：

  • 位置偏差和冗长偏差：评判者往往偏爱更长的答案或第一个选项。
  • 对同一模型家族输出的自我偏好。
  • 多次运行之间结果不一致。
  • 在领域正确性方面存在盲区。

缓解方法：使用狭窄的二元或小规模评分标准，先要求给出理由再打分，在成对比较中随机化顺序，并在信任评判者之前测量它与专家标注的一致程度。

46. 如何评测一个 Agent 而不是单次回复？

回答： 既要评估轨迹，也要评估最终答案。Agent 是否完成了任务？是否选择了正确的工具并使用了有效参数？是否避免了禁止的操作、在需要时请求批准，并在步骤和成本预算内完成？使用模拟或沙箱工具构建场景测试，并检查最终状态，例如“工单已创建且优先级正确，未发送邮件”。跟踪任务成功率、工具调用准确率、每任务步骤数和升级率。

47. 离线评测和在线监控如何配合？

回答： 离线评测在发布前基于固定数据集运行，作为提示词、模型和代码变更的把关环节。在线监控则在真实流量上运行：用户反馈、升级率和重试率、对真实对话进行抽样的 LLM 评分、护栏触发率、延迟和成本。在线信号会揭示新的失败类型。你将这些转化为新的离线测试用例，使评测集随产品一起改进。两者缺一发布，质量就会在无声中悄然退化。

如果你想在评估、RAG 和生产部署方面进行动手实践，并将其与云和安全结合学习，Cloudsoft 的 APEX AI、ML、云与网络安全课程 将这些作为相互关联的技能而非孤立的主题来讲解。

数据管道

48. AI 的生产级摄取管道是什么样的？

回答： 生产级摄取管道执行以下操作：

  • 从源连接器（SharePoint、Confluence、S3、数据库、工单工具）拉取数据，尽可能采用增量方式。
  • 将文档解析为文本和结构。
  • 清洗并去重。
  • 提取元数据和权限。
  • 分块、嵌入并 upsert 到索引中。
  • 记录数据血缘（哪个源版本生成了哪个分块）。

它需要调度、重试、失败文档的死信处理，以及关于已处理、失败和跳过文档数量的指标。应将其视为有负责人和告警机制的真正数据管道，而不是一次性脚本。

49. 如何处理 PDF、扫描文档和表格？

回答： 根据文档类型选择解析器。文本型 PDF 可以直接提取，但要检查阅读顺序和多栏布局。扫描件需要 OCR 或文档智能服务。表格需要具备布局感知能力的解析，将表头与单元格保持关联，通常转换为 Markdown 或逐行句子。图像和图表可能需要多模态模型来描述它们。在索引任何内容之前，先人工抽样检查解析结果，因为解析错误在下游是不可见的，只会表现为“模型出错了”。

50. 如何保持索引与源数据同步更新且一致？

回答： 使用变更检测（webhook、变更流或修改时间戳）进行增量更新。使用稳定的文档 ID，使更新替换旧的分块而不是产生重复。传播删除操作。定期运行完整对账以发现偏差。在每个分块上存储源版本和索引时间，使回答能够展示数据的新鲜度，并在距上次成功同步的时间超过业务可接受范围时发出警报。过期的权限与过期的内容同样危险。

51. 在 AI 数据管道中如何处理 PII（个人身份信息）？

回答： 在数据摄入时进行分类。针对每个字段决定是排除、脱敏、令牌化，还是在更严格的访问控制下保留。使用模式规则加上命名实体检测器来检测 PII（Aadhaar、PAN、电话号码、账号），当用例不需要时在索引或记录日志前进行遮蔽。将处理保持在所需区域内。记录用途和保留期限，以满足印度 DPDP 法案等合规义务。

55. 你如何为一个项目选择云 AI 平台？

答： 通常是由客户现有的云环境、身份体系和数据所在位置决定，而不是模型基准测试。如果数据和 Entra ID 都在 Azure 上，把 AI 也放在那里可以让网络、身份和合规保持简单。除此之外，还应比较所需区域可用的模型、数据驻留、私有网络、配额、托管的 RAG 和 Agent 功能、可观测性，以及在你预期用量下的定价。为了保留选择余地，可以在你的代码与提供商 SDK 之间加一层轻量抽象或网关。

56. 访问云端 LLM 的“私有”访问涉及什么？

答： 私有访问涉及：

  • 通过私有网络调用模型端点（VPC 端点或 Private Link、私有端点），使流量不经过公共互联网。
  • 使用工作负载身份（IAM 角色、托管标识）而非静态 API 密钥。
  • 在策略要求时使用客户管理的密钥加密数据。
  • 选择满足驻留规则的区域。
  • 确认提供商的数据使用条款，例如提示词不会被用于训练。

安全团队会逐项询问这些内容，因此至少要能针对一家云解释清楚。

部署、MLOps 与 LLMOps

57. 什么是 LLMOps，它与经典 MLOps 有何不同？

答： 经典 MLOps 的核心是训练流水线、特征存储、模型注册表以及输入数据的漂移。LLMOps 保留了部署与监控的规范，但改变了你进行版本管理和监控的对象。除了代码之外，你还要对提示词、检索配置、工具定义和模型 ID 进行版本管理。你使用测试集和评判模型进行评测，而不是单一的准确率数字。你监控 token、成本、延迟、护栏触发情况和回答质量。你还需要管理你无法控制的上游模型变更。深入阅读：MLOps 与 LLMOps 面试题。

58. 你会如何为 LLM 应用设计 CI/CD？

答案：

PR：代码 / 提示词 / 配置变更 -> lint + 单元测试（使用 mock 模型）-> 构建容器镜像 + 扫描 -> 用评测子集对比基线（质量门禁）-> 部署到预发布环境 -> 完整评测 + 负载测试 -> 生产环境金丝雀发布 -> 监控质量 + 成本 -> 转正发布，或回滚

AI 特有的环节是评测门禁。一次降低忠实度的提示词修改，应当像单元测试失败一样让流水线失败。使用 GitHub Actions 或类似工具做 CI，使用 GitOps（Argo CD）做 Kubernetes 部署。

59. 如何安全地升级到新的模型版本？

答案： 明确固定模型版本，而不是使用浮动别名。在新版本上运行完整的评测套件，并按类别比较，而不仅仅看平均值，因为一个模型可能在整体上提升，却在最重要的数据切片上出现退化。同时检查格式合规性、拒答行为、延迟和成本。通过功能开关或金丝雀流量切片逐步发布，观察线上指标，并保留旧版本以便回滚。跟踪供应商的弃用日期，以免被迫进行未经测试的升级。

60. 你会如何在 Kubernetes 上部署 AI 服务？

答案： 将 API 和工作进程打包为容器。设置资源请求与限制、就绪与存活探针，以及基于请求速率或队列深度（而非仅 CPU）的水平自动扩缩容，因为 LLM 调用是 I/O 密集型的。使用工作负载身份访问云资源，并从密钥库获取机密。将长时间运行的 Agent 任务放入队列由工作进程处理，而不是保持 HTTP 连接打开。如果你自托管模型，GPU 节点池和推理引擎会带来各自的扩缩容问题。用 Terraform 和 Helm 或 Kustomize 以代码方式管理这一切。

61. 你会在 LLMOps 仪表盘上放哪些内容？

答案：

  • 流量与可靠性： 请求量、按类型分类的错误率、首 token 时间和总延迟百分位数。
  • 用量与成本： 输入和输出 token 数、每个请求以及每个租户或功能的成本。
  • 质量： 用户反馈率、抽样评审评分、升级人工处理率。
  • 安全： 护栏和拒答触发率。
  • 检索： 空结果率、索引新鲜度。
  • Agent： 每个任务的步骤数和工具错误率。

对突变进行告警，因为拒答激增或检索命中数下降通常意味着上游某个环节出了问题。

安全

62. 什么是提示词注入，你如何防御它？

答案： 提示词注入是指不可信文本（用户输入，或检索到的文档、电子邮件和网页中的内容）中包含模型随后会遵循的指令，从而覆盖你的意图。在企业系统中，通过检索内容进行的间接注入是更危险的形式。没有任何单一防御手段是足够的，所以要分层防御：

  • 将所有检索到的内容和工具内容视为数据，并在提示词中清晰地将其分隔开。
  • 给模型最小权限的工具。
  • 对高影响操作要求人工批准。
  • 在服务端验证工具参数。
  • 过滤输出，例如阻止意外的 URL 或数据外泄模式。
  • 定期进行红队测试。

深入阅读：AI 安全面试题。

63. 你如何保护 Agent 可以调用的工具？

回答： 为 Agent 赋予独立的身份和范围受限的凭证，绝不使用共享的管理员密钥。在可能的情况下，代表用户执行操作，使 Agent 永远不会做超出用户权限范围的事。暴露窄化的工具（如 "create_incident"），而非通用工具（如 "run_sql"）。用 schema 和业务规则校验每个参数。对工具进行限流，记录每次调用的对象、内容和时间以供审计，并将破坏性或涉及资金的操作置于显式审批之后。

64. 什么是护栏（guardrails），它们位于何处？

回答： 护栏是围绕模型的检查机制：

  • 输入检查：越狱和注入检测、主题范围限制、PII 检测。
  • 输出检查：毒性内容、PII 泄露、有据性、格式与政策合规性。
  • 操作检查：工具权限与审批。

它们可以是规则、分类器、托管服务（例如 Bedrock Guardrails 或 Azure AI Content Safety），也可以是基于 LLM 的检查。要用真实流量来调优它们，因为过度拦截会让用户感到沮丧，正如拦截不足会带来风险一样。

65. 如何防止敏感数据通过 LLM 应用泄露？

回答： 控制进入的内容，并检查输出的内容。强制执行检索权限，尽量减少并脱敏上下文中的 PII，确保密钥不进入提示词。选择数据使用条款符合你政策的提供商和区域，限制包含提示词的日志，并扫描输出中的敏感模式。在多租户系统中，按租户隔离数据和缓存，确保一个租户的上下文永远不会出现在另一个租户的回答中。

66. 什么是 AI 红队测试，你会首先测试什么？

回答： AI 红队测试是指主动攻击你的 AI 系统，以便在攻击者或用户之前发现故障。首先测试对你的特定系统伤害最大的攻击：

  • 通过系统将要检索的文档进行间接注入。
  • 试图让 Agent 调用超出其权限范围的工具。
  • 提取其他用户的数据。
  • 在你的领域内违反政策的输出，例如它不应给出的金融或医疗建议。
  • 系统提示词泄露。

将每个发现转化为自动化回归测试。

成本与延迟

67. 在构建之前如何估算 LLM 功能的成本？

回答： 按模型的每 token 价格，将预期请求数乘以平均输入 token 数（系统提示词 + 历史 + 检索到的上下文 + 工具定义）和输出 token 数。然后加上嵌入、向量存储、重排序、护栏调用和 Agent 步骤的成本。Agent 会使账单成倍增加，因为每一步都是一次额外的调用。建立一个带有清晰标注假设的小型电子表格，例如一个说明性案例：每天几千次请求，每次几千个 token。然后在试点中用真实测量数据来验证它。

68. 降低 LLM 成本的主要手段有哪些？

回答： 主要手段：

  • 将每个任务路由到能通过评测的最小模型。
  • 精简上下文：更少但更优质的分块、压缩工具结果、摘要化历史记录。
  • 对稳定的前缀使用提供商的提示词缓存。
  • 对答案不依赖用户的重复查询缓存响应。
  • 批量处理离线任务。
  • 限制输出长度。
  • 限制 Agent 步骤数。

衡量每个成功任务的成本，而不是每次调用的成本。一个更便宜的模型如果需要重试或更多人工升级，总体成本可能更高。

69. RAG 或 Agent 请求的延迟来自哪里，如何降低？

答案： 延迟会在查询改写、检索、重排序、首 token 时间、生成长度、护栏调用，以及 Agent 的每一轮顺序工具往返中不断累积。降低延迟的方法：

  • 向用户流式输出 token。
  • 并行执行相互独立的检索和工具调用。
  • 中间步骤使用更小的模型。
  • 缩短提示词。
  • 使用缓存。
  • 将服务部署在同一区域。

对每一步进行追踪，从而优化真正慢的那一步。参见 LLM 延迟优化。

70. 什么是语义缓存，它有哪些风险？

答案： 语义缓存是指当新查询的嵌入与之前某个查询足够接近时，直接返回已存储的答案，从而省去一次模型调用。其风险包括：

  • 两个问题看似相似实则不同时返回错误答案（“取消我的卡” vs “取消我的补卡申请”）。
  • 将某个用户的个性化或有权限限制的答案返回给另一个用户。
  • 源数据更新后返回过时的答案。

仅对非个性化内容使用语义缓存，按租户和权限集划分缓存范围，设置严格的相似度阈值和较短的 TTL，并在源数据更新时使缓存失效。

71. 模型路由是如何工作的？

答案： 路由器根据请求的难度、类型或风险将其发送到不同的模型。简单的常见问题交给小而快的模型，复杂或高风险的请求交给更强的模型。路由器可以是规则、小型分类器，或升级检查机制（先尝试小模型，如果其置信度或验证不通过则升级）。要对路由器本身进行评测，因为把难题错误地路由给弱模型是一个质量缺陷。网关是实现路由的天然位置。

答案： 先明确需求：数据源（SharePoint、Confluence、政策 PDF）、权限、渠道（网页和 Teams）、语言、延迟目标和审计需求。

    |
Assistant API (FastAPI)
  |-- query rewrite (small model)

  |-- rerank -> top chunks
  |-- generate w/ citations (LLM via gateway)
  |-- output checks (PII, groundedness)

Ingestion: connectors -> parse -> chunk

75. 设计一个文本转 SQL 的分析助手。

答案： 为问题检索相关的模式、表描述和示例查询。用模型生成 SQL，然后在执行前进行检查：解析它，只允许 SELECT，仅允许已批准的表和列，添加行数限制，并在只读副本上以用户的数据权限运行。返回结果时同时展示 SQL，以便分析师验证。在一组“问题-预期结果”对上进行评测，比较结果而不是 SQL 字符串。难点在于业务定义（如“活跃客户”），语义层或精心维护的术语表比提示词更能解决这个问题。

行为与协作

78. 讲讲你上线过的一个 AI 功能。出了什么问题，你做了什么改变？

答案： 使用 STAR 结构，但把大部分时间花在技术决策和失败上。一个有力的回答会指出一个具体问题，例如“检索漏掉了扫描附件中的答案”。它解释你如何发现问题（评测结果、追踪、用户反馈）、你做了什么改变（OCR 解析、混合搜索），以及你如何衡量改进。最后以你会如何以不同方式来做收尾。面试官关注的是担当、证据以及对权衡的坦诚，而不是一个完美无缺的故事。

面试技巧： 准备两个这样的故事，一个关于质量，一个关于安全或成本。使用你能详细讨论的项目，如果你职业生涯尚早，也可以使用自己的作品集项目。

79. 如何向期望完美结果的非技术利益相关者解释 LLM 的局限性？

回答： 把局限性转化为业务决策。展示在对方实际问题上的实测准确率，说明哪些错误可以容忍、哪些不能，并提出控制措施：引用来源、对高风险输出进行人工审核、限定范围，以及升级路径。在上线前就成功标准达成一致，例如在评测集上可接受的准确率水平和审核流程，这样“是否足够好？”就有了约定的答案，而不是见仁见智的问题。

80. 在 AI 项目中，你如何与数据、安全和领域团队合作？

回答： 尽早让他们参与，而不是等到上线时。向数据负责人询问数据来源、质量和权限。向安全团队询问威胁模型、数据分类以及工具访问权限的审批。请领域专家定义评测集并评判答案。在最初几周内分享一份简短的架构与风险文档，定期用真实数据进行演示，并保留决策日志。许多 AI 项目在安全审查中搁浅，就是因为安全团队太晚才看到设计方案。

真实场景

81. 你的 RAG 助手给一位高管提供了一个自信但错误的答案。你会怎么做？

回答： 控制问题影响，通过追踪记录诊断，修复根本原因，并添加回归测试。迅速承认错误，然后在改动任何东西之前，先弄清楚是检索还是生成环节出了问题。

我会检查的内容：

  • 追踪记录：检索到了哪些文本块，正确的文档是否在其中？
  • 来源本身是否过时或自相矛盾。
  • 答案是否忠实于检索到的上下文，还是模型自行添加了事实。
  • 类似的问题是否也会失败（快速跑一批测试）。

生产环境注意事项： 将该问题加入评测集。如果来源过时，修复数据新鲜度流水线。如果是模型编造了事实，收紧接地规则，并添加一个忠实度检查，在无法确认时回退为“我在来源中找不到这个信息”。

82. 在没有代码变更的情况下，延迟一夜之间翻倍。你会如何排查？

回答： 没有代码变更不代表什么都没变。利用追踪记录找出哪个环节变慢了，然后排查上游的变更。

我会检查的内容：

  • 各步骤的 span 耗时：模型、检索、重排序器、工具。
  • 服务商状态页面以及限流或重试次数。
  • 模型别名是否切换到了新版本，或输出长度是否增长。
  • 索引规模增长、导致上下文膨胀的数据变更，或流量激增。

生产环境注意事项： 固定模型版本，针对每个步骤的延迟百分位数设置告警，并预先配置备用模型或备用区域，以便在排查问题时可以切换流量。

83. 每月 LLM 支出远超预算。你会怎么做？

回答： 在削减任何成本之前，先按功能、租户、模型和 token 类型拆解成本。超支通常来自几个原因：上下文臃肿、Agent 循环、重试，或某个重度用户或集成。

我会检查的内容：

  • 每次请求的成本分布：是否由长尾请求推高了总成本？
  • 平均输入 token 随时间的变化（历史记录增长、分块过多）。
  • 每个任务的 Agent 步骤数和重试率。
  • 是否有批处理作业或测试环境在调用生产模型。

生产环境注意事项： 在网关层添加按租户的预算和告警，将简单流量路由到更小的模型，启用提示词缓存，并将每次成功任务的成本作为常设 KPI 进行跟踪。

84. 一位用户让助手泄露了机密 HR 文档的内容。请应对。

回答： 将其视为安全事件：进行遏制、评估影响范围、修复访问控制，并通过事件流程上报。这是授权失败，而不是提示词问题。

我会检查的内容：

  • 该文档的 ACL 元数据是否被正确索引。
  • 针对该用户和该代码路径，检索过滤器是否被应用。
  • 可能向其他用户返回过答案的缓存（语义缓存或响应缓存）。
  • 审计日志中其他受影响的查询和用户。

生产环境注意事项： 将权限过滤器设为检索层的强制要求（任何代码路径都不能跳过），在 CI 中添加自动化权限测试，并按权限集划分缓存范围。

85. 试点运行良好，但业务方要求四周内上线生产。你如何规划？

回答： 先就狭窄的生产范围和不可妥协事项清单达成一致，然后倒排计划。试点与生产之间常见的差距包括：安全审查、真实权限、评测、监控以及支持责任归属。

我会检查的内容：

  • 评测集是否反映真实用户，还是只包含演示问题。
  • 安全和数据保护审查的所需时间。
  • 集成和 SSO 的就绪情况，以及负载预期。
  • 上线后由谁提供支持，以及回滚计划。

生产环境注意事项： 先面向有限的用户群体上线，并配备监控和反馈机制，在指标保持稳定的情况下逐步扩大范围。按时分阶段上线，胜过公开失败的全量上线。

86. 你的 Agent 在 ServiceNow 中创建了重复工单。请诊断并修复。

回答： 重复通常来自没有幂等性的重试，或者 Agent 没有识别出它的第一次调用已经成功。

我会检查的内容：

  • 追踪记录：工具是否超时并被重试，尽管第一次调用其实已经成功？
  • 工具结果是否向模型明确报告了成功以及工单号。
  • 同一次运行中参数完全相同的重复调用。
  • 并发问题：两个 worker 处理同一事件。

生产环境注意事项： 添加幂等键（例如对话与意图的哈希值），在创建工单前先检查是否已存在未关闭的工单，并限制每次运行中创建类工具调用的次数。

87. 在供应商模型升级后，JSON 输出开始无法通过校验。现在该怎么办？

回答： 如果可以，先回滚到固定的上一个版本，然后测量回归问题并以可控的方式修复。

我会检查的内容：

  • 是否使用了浮动别名而不是固定版本。
  • 哪些字段失败，以及失败方式如何（多余的散文、缺失字段、类型错误）。
  • 是否启用了原生结构化输出模式。
  • 你的评测套件在新版本上的格式合规结果。

生产环境注意事项： 使用模式强制的输出模式，携带错误信息校验并重试一次，并将格式合规作为模型升级测试中的门槛。

88. 用户说回答“太笼统”。你如何改进？

回答： 笼统的回答通常意味着上下文薄弱或缺失，而不是模型能力弱。检查模型实际看到了什么。

我会检查的内容：

  • 检索到的内容块是具体的，还是宽泛的概览页面。
  • 是否传入了用户上下文（角色、地点、产品）。
  • 提示词是否要求具体性：步骤、来自来源的数字、引用。
  • 一份按问题类型分类的“笼统”投诉样本。

生产环境注意事项： 改进内容块元数据和重排序，在安全的前提下将用户属性加入上下文，并在评测评分标准中增加具体性要求。

89. 业务方希望助手也支持印地语和泰卢固语。需要做哪些改动？

回答： 在承诺之前，针对每种语言分别检查模型质量、跨语言检索、token 成本和评测。

我会检查的内容：

  • 每种语言在领域问题上的模型质量，由母语者评判。
  • 嵌入模型是否支持跨语言检索（用泰卢固语提问检索英文文档）。
  • 每种语言的 token 数量，这会影响成本和延迟。
  • 印地英混合语等混合输入，以及音译文本。

生产环境注意事项： 为每种语言构建评测集，决定是翻译查询还是进行跨语言检索，并保持回答语言与用户语言一致。

90. 某银行的安全团队拒绝将客户数据发送到公共 LLM API。你会提出哪些方案？

回答： 提供满足其管控要求的架构，而不是与之争辩。

我会检查的内容：

  • 究竟哪些数据类别受到限制，以及原因（法规、合同、政策）。
  • 他们批准的云环境中的云模型，或通过区域内私有网络接入的云模型，是否满足要求。
  • PII 能否在模型看到数据之前进行脱敏或标记化处理。
  • 是否需要针对某些数据类别使用自托管的开源权重模型。

生产环境考量： 将数据流、保留策略、加密方式和供应商条款整理成一页文档，供安全团队审批。最终结果往往是混合方案：脱敏后的数据交给云模型，最敏感的任务则使用自托管模型。

91. 你用新的嵌入模型重新建立索引后，检索质量下降了。为什么？

回答： 常见原因包括重新索引不完整（新旧向量混杂）、查询时使用的模型与索引时的模型不一致、维度或距离度量发生变化，或者新模型在你的领域词汇上表现更差。

我会检查的内容：

  • 索引中的每个向量是否都来自同一个模型版本。
  • 查询嵌入是否使用相同的模型以及任何必需的前缀或指令。
  • 距离度量和归一化设置。
  • 在评测集上对比新旧索引的检索指标。

生产环境考量： 重新索引到一个新索引，只有在检索评测通过后，才通过蓝绿切换进行切换。

92. 一个 Agent 一直调用错误的工具。你如何修复？

回答： 工具选择主要取决于工具名称、描述以及 Agent 需要在多少个工具中进行选择。

我会检查的内容：

  • 工具描述是否存在重叠或含糊不清。
  • 上下文中的工具是否过多。能否对它们进行分组，或动态选择工具？
  • 系统提示词是否通过示例说明了何时使用每个工具。
  • 评测套件中每种意图的工具选择准确率。

生产环境考量： 重写工具描述，明确说明何时使用以及何时不使用每个工具，按意图路由到较小的工具集，并将工具选择测试加入 CI。

93. 一家医院想要一个为医生总结病历的助手。你有哪些顾虑？

回答： 临床安全、隐私和责任归属是首要问题。该助手是辅助临床医生的，绝不能取代他们的判断。

我会检查的内容：

  • 健康记录的数据驻留、同意和访问规则。
  • 遗漏风险：摘要中遗漏一条过敏信息就是严重的失败。
  • 每条摘要陈述是否都能追溯到源记录。
  • 由临床医生对代表性记录（包括边缘案例）进行评估。

生产环境考量： 内联显示来源，关键字段（过敏、用药）从结构化数据中标记而非依赖生成文本，记录使用情况以供审计，并保持临床医生作为最终决策者。

94. 产品团队想要一个完全自主的 Agent 来审批供应商付款。你如何回应？

回答： 建议采用分级自主：由 AI Agent 准备付款，再由人工审批。只有当可衡量的准确率和控制措施足以支撑时，自主性才逐步提升。

我会检查的内容：

  • 现有的审批控制措施和职责分离规则。
  • 欺诈风险，例如被篡改的发票以及文档中被注入的指令。
  • 错误审批的代价与节省的时间之间的权衡。
  • 审计要求。

生产环境注意事项： 先从仅推荐模式开始。只有对低金额、符合政策、已知供应商的情况才考虑自动审批，并在代码中强制执行限额，同时记录每一次决策。

95. 你的评测分数看起来很好，但用户却不满意。这是怎么回事？

回答： 评测集已不再反映真实使用情况，或者这些指标没有衡量用户真正关心的内容。

我会检查的内容：

  • 将评测问题与日志中的真实查询分布进行对比。
  • 阅读一部分低评分对话，并对失败类型进行标注。
  • 检查评判模型是否与人工评分一致。
  • 检查是否存在用户体验问题：延迟、格式、缺少后续跟进。

Production consideration: Refresh the eval set from production traffic regularly and add user-centred criteria such as actionability and completeness.

96. A document in the knowledge base contains hidden text telling the AI to email data externally. What do you do?

Answer: This is indirect prompt injection. Remove the document, check whether any action was taken, and harden the system so injected text cannot trigger exfiltration.

我会检查的内容：

  • Logs: did any tool call follow retrieval of that document?
  • Whether the agent has any outbound tool (email, HTTP) it does not need.
  • How the document entered the corpus, and who can add content.
  • Other documents with similar patterns.

Production consideration: Remove unneeded tools, restrict outbound destinations, require approval for external sends, scan ingested content for injection patterns, and add the case to red-team tests.

97. Leadership asks whether the AI assistant is "worth it". How do you answer?

Answer: Answer with a measured comparison against the baseline process, not anecdotes.

我会检查的内容：

  • The baseline metrics recorded before launch (handling time, resolution rate, backlog).
  • Adoption: active users and repeat usage.
  • Quality and risk: error rate, escalations, incidents.
  • Full cost: models, infrastructure, support and review time.

Production consideration: Define value metrics before building. If you didn't, measure a comparison group now.

98. Your team wants to fine-tune a model because "RAG isn't accurate enough". How do you evaluate the proposal?

Answer: First find out what kind of inaccuracy it is. Fine-tuning rarely fixes retrieval or knowledge-freshness problems.

我会检查的内容：

  • Whether the failures are retrieval misses, unfaithful generation, or format and style issues.
  • Whether better chunking, hybrid search or reranking closes the gap.
  • Whether there is enough clean, labelled training data.
  • The ongoing cost of retraining as the base model or data changes.

Production consideration: Fine-tune only for a measured behavioural gap, compare against the improved RAG baseline on the same eval set, and plan how the fine-tuned model will be versioned and retrained.

99. A GCC team in Hyderabad must support the same assistant for business units in three countries. What changes?

Answer: Data residency, regulation, language and local policy differences turn one assistant into a configurable platform.

我会检查的内容：

  • Residency and AI regulations per country, for example the EU AI Act for European units.
  • Whether each region needs its own model endpoint and index.
  • Country-specific policies and documents, and how they are scoped.
  • Support hours, ownership and escalation per region.

Production consideration: Deploy per region from the same code with region-specific configuration, scope retrieval by country, and keep separate eval sets per business unit.

100. On day one at a new client, you inherit an AI system with no tests, no monitoring and unhappy users. What are your first two weeks?

Answer: Make the system observable first, then measurable, then improve it. Don't rewrite anything before you understand it.

我会检查的内容：

  • Architecture, data sources, permissions and the riskiest capabilities (tools that write).
  • Tracing and cost logging on every request, added in the first days.
  • A first eval set of real failing and common questions, built with users.
  • Quick security risks: over-privileged keys, missing permission filters.

Production consideration: Fix critical security gaps immediately. Then make one measured improvement at a time and share before-and-after results with stakeholders weekly. This is the everyday work of Forward Deployed Engineers. Our FDE interview questions cover that role in depth.

Key takeaways

  • AI engineer interviews in 2026 test production judgement: evaluation, security, cost and failure handling, not only model knowledge.
  • Treat the LLM as an unreliable dependency. Validate outputs, enforce limits in code, and keep authorisation out of prompts.
  • Most RAG and agent quality problems are context problems. Diagnose the failing stage from traces before changing prompts.
  • Evaluation is the skill that separates good candidates: offline gates in CI, plus online monitoring that feeds new test cases.
  • Know one cloud deeply and the others at the map level, using current names: Bedrock AgentCore, Microsoft Foundry, Gemini Enterprise Agent Platform.
  • For scenario questions, use the same pattern: contain, check the trace, fix the root cause, add a regression test.

Interview preparation checklist

  • Build one RAG project with permission-aware retrieval, citations and an eval set you can show.
  • Build one agent with at least two real tools (for example a ticketing API), step limits and an approval step.
  • Be able to draw three architectures from memory: knowledge assistant, action-taking agent, document extraction.
  • Prepare a cost estimate for one of your projects, with stated assumptions.
  • Practise explaining prompt injection defences and RAG access control without notes.
  • Review one cloud's AI services in its current official documentation.
  • Prepare two STAR stories: one quality failure you fixed, one security or cost issue.
  • Practise five scenario questions aloud with the contain, diagnose, fix, prevent structure.
  • Read the specialist guide for your target role: GenAI, agentic, RAG, cloud or MLOps.

FAQ

What skills are required to become an AI engineer in 2026?

Strong Python and API engineering, LLM fundamentals, RAG, tool calling and agents, evaluation, one major cloud, containers and CI/CD, and the basics of AI security. Communication with business and security teams matters as much as code.

Do I need a machine learning degree to become an AI engineer?

No. Most AI engineering builds on pre-trained models, so software engineering skills plus a working understanding of how models behave are usually enough to start. A portfolio of working projects carries more weight than a degree title.

How should I prepare for an AI engineer interview?

Build two or three end-to-end projects, practise explaining their architecture and failures, rehearse system design and scenario questions aloud, and review current cloud AI service names in official documentation.

Is AI engineering a good career for software developers?

For developers who enjoy building products, yes. Organisations need engineers who can integrate AI with real systems, data and security controls, and existing backend skills transfer directly.

What is the difference between an AI engineer and a GenAI developer?

The titles overlap heavily. GenAI developer usually stresses building with generative models. AI engineer is often broader and can include evaluation, deployment and sometimes traditional ML.

Which cloud should I learn for AI engineering?

Learn the one most used by the employers you are targeting, and learn it in depth, then understand the equivalent services on the other two at a high level. The core concepts carry across clouds.

Are coding rounds still part of AI engineer interviews?

Usually yes. Expect practical Python tasks such as calling an API, parsing structured output, writing an async pipeline or adding tests, often alongside a system design round.

How important are projects for freshers applying to AI engineer roles?

Very important. A deployed project with an eval set, a README explaining trade-offs and a short demo shows interviewers far more than certificates alone.

What do interviewers look for in AI system design rounds?

Clear requirements gathering, sensible component choices, permission and security handling, an evaluation plan, cost and latency awareness, and honest discussion of failure modes and trade-offs.
