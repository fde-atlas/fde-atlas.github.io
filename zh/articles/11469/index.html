AI 项目范围界定问题：需求挖掘演练

原标题：AI Project Scoping Questions: Discovery Drill

Vibe Engines · 2026-09-03 · 约 9 分钟读完

摘要

Vibe Engines 推出一个浏览器内交互式练习，训练 AI 项目需求澄清能力。练习给出两个模糊的客户需求（如发票自动化），各提供 12 个候选问题，但只允许问 6 个。每个问题按答案是否影响构建方案打 0–3 分，并按 Outcome、Data、Users、Constraints、Success、Risk 六个维度统计覆盖面。总分与满分 18 对比：信号值达 80% 且覆盖 4 个维度为可立项，55% 且覆盖 3 个为部分可立项。文章用 Kestrel Freight 案例演示三种问法得分差异，指出常见错误（如让客户选技术方案、把猜测当需求），并提醒该评分是作者主观设定，不能替代真实访谈。

要点

  • 每次练习限问 6 个问题，从 12 个候选中挑选
  • 问题按 0–3 分计分，标准是答案是否改变构建方案
  • 覆盖 Outcome、Data、Users、Constraints、Success、Risk 六个维度
  • 80% 信号值加 4 维覆盖为可立项，55% 加 3 维为部分可立项
  • 常见错误包括让客户选模型、把猜测当需求、只接受单一准确率目标

全文

一个针对每次需求调研电话真正考察的技能的练习。两个描述不足的客户需求，每个十二个候选问题，预算只有六个——花掉它们，看看客户真正的回答，并让每个问题根据“答案是否会改变你要构建的东西”来评分。最后生成一份可复制的需求界定文档、覆盖六个维度的覆盖图，以及那个你要么发现、要么错过的真正问题所在。

“我们想让 AI 处理我们的发票。”

本次会话 6 个问题。剩余 6 个

这个限制正是关键所在。一次真实的需求调研电话大约只有六个真正重要的问题的空间，而被衡量的技能就是选出哪六个。

/18

在左侧选择问题。每个问题会占用一个名额，并返回客户真正的回答——这是判断问题是否值得问的唯一依据。

评分规则：如果答案会改变你要构建的东西，得 3 分；如果会改变计划，得 2 分；如果只是了解更好，得 1 分；如果问得太早或没有错误答案，得 0 分。

“我们想让 AI 处理我们的发票”是需求的开始，而不是需求本身，接下来的六个问题将决定这个项目是被构建还是被争论。 这个练习让你置身于两次需求调研电话中，从十二个候选问题中只有六个的预算，展示客户真正的回答，并评估你捕获了多少可用信号。

它计算什么

每份简报有十二个候选问题。每个问题都属于六个维度之一（成果、数据、用户、约束、成功、风险），并带有评分规则给出的信号值：3 表示答案会改变你要构建的东西，2 表示会改变计划，1 表示只是了解更好，0 表示问得太早或没有错误答案。

budget     = 6 questions per session
score      = sum of the values of the questions asked
max score  = sum of the six highest values in the brief
signal %   = score / max score × 100
coverage   = distinct axes asked about, 0 to 6

Scopeable          signal % ≥ 80 and coverage ≥ 4
Partial            signal % ≥ 55 and coverage ≥ 3
Not scopeable yet  anything else

面板将分数显示为

score/max

并点亮每个已覆盖的维度。当第六个名额用完时，它会添加评级、需求背后真正的故事，以及一份纯文本需求界定文档：每个问题附上客户在维度标签下的回答，每个未触及的维度列为待定风险并附其引导性问题，以及三个后续步骤。

一个完整示例

默认简报是 Kestrel Freight。它的十二个问题中有七个值 3 分，所以最好的六个问题可得

6 × 3 = 18

。三个会话展示了这些规则如何区分它们：

会话问题及分值分数维度评级
常见开场模型选择 0，ERP API 1，对 AI 的看法 0，预算 1，发票量 3，当前流程 38/18，44%5尚不可界定
混合当前流程 3，发票量 3，可运行位置 2，ERP API 1，预算 1，模型选择 010/18，56%4部分
强当前流程 3，发票量 3，谁处理异常 3，可运行位置 2，成功指标数字 3，错误审批的成本 317/18，94%6可界定

开场环节触及五个轴却仍然失败，因为 18 分中只得 8 分，低于 55% 的门槛：没有信号支撑的广度不算数。强势环节在约束问题上让出 1 分（该问题值 2 分），但覆盖了全部六个轴，因此其文档没有未覆盖的风险部分。六个 3 分问题全部局限于 Outcome、Data、Users 和 Success，拿到满分 18 分，同时也评上了 Scopeable，但文档中 Constraints 和 Risk 仍列为未覆盖，四周的 ERP 审批以及 £500 和 £5,000 的多付款阈值也始终未被发掘。

假设与局限

  • 分值是作者的主观判断。 每个 0 到 3 的分值都是演练作者针对本简报的判断，而非测量结果；在这里值 1 分的问题，在另一个项目中可能是决定性的。
  • 顺序无关紧要。 分数是总和，所以最后问出的最佳问题与最先问出的得分相同。而在真实通话中，前面的回答会改变下一个问题该问什么。
  • 固定回答。 客户每次都说同样的话，从不主动补充更多信息。而真实的利益相关者会跑题、互相矛盾，并且需要追问。
  • 覆盖只是计数。 只要有一个问题触及某个轴，该轴就算被覆盖，无论多么浅。
  • 两份简报。 第二份简报 Halcyon Health 没有 3 分的 Outcome 问题，因此在那里覆盖全部六个轴的环节最高只能得 17 分。

如何使用结果

  • 在提出每个问题之前，先问自己：无论答案是哪个，是否会改变你要构建的东西。 如果不会，它就是 0 分或 1 分的问题，不配占用六个名额之一。
  • 把未覆盖风险清单当作你的下一份议程。 每个未触及的轴都是一个待安排的问题，而且通常是 Data 或 Risk。
  • 把每个回答转化为范围。 可衡量的回答变成验收标准，例如 60 个例外中有 40 个无需人工介入即可解决；依赖关系变成带日期的假设。
  • 问对人。 有几个低分其实是合理的问题问错了利益相关者，例如把 ERP API 的问题问给了财务副总裁。

何时使用，何时不使用

在真实的需求挖掘通话前用它来热身，养成“答案是否会改变构建”的提问习惯，作为前沿部署工程师拆解环节的练习，或者与团队一起使用：所有人玩同一份简报，然后比较各自选了哪六个问题以及为什么。

不要把它当作真实通话的脚本。真实通话会分叉，最佳的下一个问题取决于上一个回答。也不要用这个分数去评判同事的真实需求挖掘，因为它的分值只为这两份简报而设。

权衡与局限

演练规则真实项目中的情况
每个问题占用一个名额有些只需几秒钟；“能否给我看 50 个真实例外”可能要花掉某人一周的时间
0 分问题仍计入覆盖一个没有回答的问题对其轴毫无揭示
最佳六问就是分值最高的六个，无论其轴是什么最佳议程要在信号与盲区之间取得平衡
一位拍板人回答所有问题多个利益相关者给出不同、有时甚至相互矛盾的答案

第二行有明显的效果：一个薄弱的问题反而可能提高评级。下面的测验展示了一个得分更低却评级更高的会话。

常见错误

  • 让客户来选择实现方案。 模型选择以及向量搜索还是关键词搜索是你的决定；把问题抛给对方等于把决定交给一个缺乏背景的人，也表明你在还没理解之前就开始构建了。
  • 把猜测写成需求。 来自不了解情况的人的一句“每天几百条？”并不是业务量目标。把它标记为未知，去问真正了解的人。
  • 接受单一的准确率数字。 当低于 500 英镑的错误无人察觉，而超过 5000 英镑的错误却传到审计那里时，系统需要按金额划分阈值，而不是单一目标。
  • 跳过真实数据。 “有些数据有点过时”是一个警告。在做出任何承诺之前，先在第一周索要实际的数据存储或 50 个真实案例。
  • 被动接受日期而不是主动塑造它。 在诸如每两周一次的平台评审会等审批流程进入计划之前，“季度末”只是一个愿望。

Kestrel：你问了关于 Outcome、Data 和 Users 的五个 3 分问题（当前流程、某人将停止做什么、业务量、50 个例外情况、由谁处理）。第六个问题应该花在 ERP API 问题上还是模型选择问题上？

按评级来看，选模型选择。如果问 ERP API 问题（Data，1 分），得分是

16/18 = 88.9%

但只有三个轴，所以

Partial

。如果问模型选择（Constraints，0 分），得分是

15/18 = 83.3%

超过四个轴，所以

Scopeable

。覆盖度会把被无价值问题触及的轴也计入；真正的解法是那个 3 分的成功或风险问题，它能在四个轴上拿到 18 分。

Halcyon：你问了 b1、b2、b3、b4、b5 和 b12 全部六个问题，每个都值 3 分。文档怎么说？你漏掉了什么？

得分 18/18，100%，覆盖 Data、Risk、Users 和 Success：Scopeable。文档将 Outcome 和 Constraints 列为未解决的风险，因此那个 3 分的患者数据问题从未被问到，随之错过的答案是：人们会粘贴可识别身份的数据，而这会改变日志记录、保留策略和模型路由。

工作原理

  • 两个真实的欠明确需求，各配十二个候选问题。
  • 六个问题的预算：限制本身就是练习的意义。
  • 每个问题根据其答案是否会改变构建方案打 0–3 分。
  • 与最优的六个问题对比评级，并考察六个轴上的覆盖度。
  • 导出一份范围界定文档，记录你学到的内容和尚未解决的风险。

常见问题

在需求挖掘电话中，什么样才算一个好的澄清问题？

好问题的答案会改变你要构建的东西。询问客户目前一步步是怎么做的，往往会发现所谓的问题其实早已解决，真正的工作在别处。没有错误答案的问题，比如问客户对 AI 的感受如何，只会浪费一个提问名额，却换不回任何可以据此设计的信息。提问前的检验很简单：如果答案无论怎样，我构建的东西都会不同吗？如果不会，这个问题可以留待以后再问。

一次范围界定会议需要覆盖哪些维度？

六个：成果（如果这件事成功，业务会发生什么变化）、数据（有哪些数据、归谁所有、你能否真正拿到）、用户（现在谁在做这项工作、他们目前用什么替代方式）、约束（可以运行在哪里、能触碰什么、需要谁批准）、成功（哪个数字会变化、如何衡量、由谁认可）以及风险（出错的代价、以及这种出错频率多高可以接受）。你从未问过的维度就是意外的来源，而且通常是数据或风险。

为什么把问题数量限制在六个？

因为一场真正的需求挖掘电话大约只有六个重要问题的空间，而无论在岗位上还是在前沿部署工程师的分解面试环节中，被考察的技能正是选出这六个问题。取消名额限制就等于取消了这项练习：在问题不限的情况下，每个人最终都会覆盖所有内容，也就无法考察优先级排序能力。名额限制还能让礼貌性的无效回答的代价变得可见，因为花在一个无效回答上的名额，就是没有花在数据或风险上的名额。

范围界定演练中的分数是如何计算的？

每个候选问题都有一个 0 到 3 的分值：如果答案会改变你要构建的东西，得 3 分；如果会改变计划，得 2 分；如果只是了解一下也不错，得 1 分；如果问得太早，得 0 分。你的分数是你所问六个问题的总和，与最优的六个问题对比，两份简报中的满分都是 18 分。得分达到或超过 80% 且覆盖至少四个维度，评为 Scopeable（可界定范围）；55% 且覆盖三个维度，评为 Partial（部分可界定）；低于此则为 Not scopeable yet（尚不可界定范围）。

拿到答案之后该做什么？

把每个答案转化为一条验收标准，或一个带日期的假设。六十个例外中有四十个无需人工处理即可解决，这是一条可测试的验收标准；客户在第一周内授予 ERP 访问权限是一个假设，而且只有当工作说明书（SOW）中也写明延误将逐日顺延里程碑时，它才能真正保护你。范围界定结束时仍未明确的事项，就是已经排定在第四个月发生的范围争议。

在构建 AI 项目之前，我应该问哪些问题？

从当前的流程开始，逐步梳理，因为这往往能表明所述问题其实已经解决，真正的工作在别处。然后索要数据的真实示例、如今由谁执行这项工作以及他们如何决策、系统可能部署在哪里以及谁批准访问权限、定义成功的那个数字以及谁认可它，还有答错一次的代价。模型选择、搜索技术和预算留到以后或交给其他人：这些答案很少会改变项目范围。
