什么是本体（Ontology）？含义、与知识图谱的区别、以及用 AI 构建的方法

什么是本体（要点3行）

  • 本体是一张“语义地图”。它以机器可解释的形式，将某一领域中存在的概念（事物）及其关系与约束体系化。可以把它理解为：不是用表名或列名，而是用现场使用的业务语言重新定义数据的工作。
  • 它的作用是数据整合与现场运营之间的粘合剂。“有数据却用不了”的实质，是数据的含义（上下文）没有被任何人共享。本体正是填补这一缺失层次的东西。
  • 概念本身是1990年代以来的老技术，但它在2026年重新受到关注，是因为AI Agent开始深入到执行层面，同时LLM大幅降低了构建成本。

接下来，本文将依次梳理它与相近术语的区别、Palantir式的结构、对LLM精度的实证数据以及失败模式。

为什么是“现在”谈本体｜3股力量

本体（ontology）原本源于哲学的“存在论”，在信息科学领域自1990年代起就在语义网（Semantic Web）的背景下被研究。RDF、OWL等标准规范也在20多年前就已建立。也就是说，这并不是一个全新的概念。

尽管如此，从2025年到2026年它作为实务术语迅速升温，是因为以下3股力量叠加在了一起。

力量1：AI从“读取”转向“驱动”

当生成式AI的用途还停留在聊天和摘要时，数据的含义即使有些模糊，实际危害也不大。因为最后由人工目视修正即可。

但当AI Agent开始承担下单、授信、库存预留、创建工单等业务执行时，情况就不同了。如果“客户”在销售管理系统和会计系统中指向不同的粒度，Agent就会若无其事地对错误的对象执行处理。对于执行任务的AI而言，严格的语义定义已不可或缺。这是本体被重新评估的最大驱动力。

力量2：LLM瓦解了构建成本

过去本体构建未能普及的最大原因是投入产出比不划算。即使专家花数月用OWL手写概念体系，能使用它的应用也十分有限。

LLM从两方面打破了这一前提。第一，从现有Schema和文档中抽取概念候选、关系候选的起草工作，现在能以人工成本的几十分之一完成。第二，构建好的本体可以用作自然语言提问与数据之间的翻译器，投资回报的出口一下子扩大了。构建变便宜了，用途也增多了。普及的条件已经齐备。

力量3：数据基座厂商集体收敛到语义层

2026年初，企业级数据基座纷纷提出了同一个承诺：大规模地为AI Agent提供业务上下文。

  • Microsoft Fabric IQ：在Fabric上定义业务术语、属性与关系，并将其与实际数据关联的语义层
  • Databricks Unity Catalog Business Semantics：2026年初正式GA（一般提供），以目录为起点定义业务语义
  • Snowflake Cortex：同样以语义模型为核心向AI传递上下文

曾经被视为Palantir独有概念的东西，正在成为主要平台的标准功能。可以认为，本体正在从“少数先进企业的奢侈品”转变为“数据基座的标准组成要素”。

梳理4个容易混淆的术语

讨论无法对上频的大部分原因，在于术语的混淆。首先要把这里统一好。

术语指的是什么打个比方
本体概念、属性、关系、约束的“定义（类型）”本身设计图、模板
知识图谱将实际数据灌入本体后的实体按设计图建成的建筑
语义层将指标定义在全公司统一为一份的“读取”层共同的度量尺
数据目录记录什么数据在哪里存在的清单索引、藏书列表

最重要的区别是本体（Ontology）与知识图谱。本体相当于“模板”，知识图谱相当于“把实际数据灌入该模板后的成品”。“客户拥有一个或多个订单”这一定义是本体，而“山田商事拥有订单A、B、C”这一实体则是知识图谱。

与语义层的区别也需要掌握。语义层往往是统一指标定义的只读层，如销售额、库存周转率等。后文将提到的Palantir式本体，其决定性的不同之处在于，它还拥有用于“驱动行动”的层。

Palantir式本体｜用“物”与“事”映射世界

将本体提升到实务水准的代表性例子，就是Palantir的Foundry / AIP。该公司将本体表述为组织的数字孪生。它是位于数据集和模型之上、将它们与现实世界的对应物（从工厂、设备、产品等物理资产，到接单、交易等概念）连接起来的层。

其结构大致分为两大要素群。

语义要素｜对组织进行“describe（描述）”

  • 对象类型：现实世界实体或事件的模式定义。例如有“机场”这一对象类型，JFK和LHR就是其各自的对象
  • 属性：对象所具有的属性
  • 链接类型：对象类型之间关系的定义。如“此订单关联到此客户”这类关系

动态要素｜对组织进行“change（变更）”

  • 动作类型：接收现场操作人员的输入，连接现有系统以驱动决策流程。是在遵循管控与治理的同时引发变更的机制
  • 函数：用于描述并逐步完善任意复杂度业务逻辑的机制
  • 动态安全：控制谁可以查看哪些对象、执行哪些动作

这才是本质所在。一般的语义层停留在“读取”的层，而Palantir式本体则是同时处理读写的应用程序基础。

简而言之，本体就是将业务翻译为物（名词）与事（动词）的结果。“接单”“库存”“配送班次”是物，“批准订单”“改签班次”是事。只要建立了这种对应关系，人类和AI Agent就能在同一世界观之上进行判断和执行。

而这也意味着技术人员所需能力的变化。除了编写代码的能力之外，理解现场业务流程并将其翻译为数字世界中的物与事的设计能力开始受到考验。FDX之所以重视Forward Deployed Engineer（FDE）这一职位，原因也在于此（什么是FDE）。

本体能在多大程度上提升LLM的准确率

不能止步于“定义语义似乎有好处”，还要看定量的实证。近几年，多个独立的基准测试都得出了相同方向的结论。

使用知识图谱后LLM的准确率提升至约3倍

data.world于2023年发布、并在2024年GRADES-NDA研讨会上发表的企业级基准测试，已成为该领域的基准点。在针对真实企业SQL数据库的问答中，出现了如下差距。

  • 直接查询SQL数据库时的准确率：16.7%
  • 将相同数据转换为知识图谱表示后查询时：54.2%

相同的数据、相同的LLM（GPT-4），唯一的区别是有没有语义层，准确率就提升到了约3倍。尤其在“复杂问题 × 复杂模式”的领域，直接使用SQL时准确率几乎降至零，而通过知识图谱则保持了显著的精度。

加上基于本体的检查后，准确率提升至72%

后续研究（Sequeda et al., 2024）提出了一种将本体用作检查生成查询的机制的方法。

  • OBQC（Ontology-Based Query Check）：确定性地检查LLM生成的SPARQL查询是否符合本体的语义
  • LLM Repair：将检查产生的错误说明返回给LLM，让其修复查询

对于“模型变聪明后语义层是否就不需要了”这一疑问，dbt Labs于2026年发布的基准测试给出了答案。下表是对同一份已建模数据的比较，差异仅在于接口。

即使在2026年的模型中，语义层依然有效

对于“模型变聪明后，语义层是否就不再需要了”这一疑问，dbt Labs 于 2026 年发布的基准测试给出了答案。下表是对同一份已建模数据的比较，唯一的差异在于接口。

路径GPT-5.3 CodexClaude Sonnet 4.6
通过语义层100%98.2%
让AI编写SQL（text-to-SQL）84.1%90.0%

即使是最新一代的模型，通过语义层的精度也明显更高。此外，在提供带上下文的元数据时，相比仅使用模式的提示，SQL生成精度提升了3倍；在另一个522题规模的基准测试中，也报告了38%的相对提升。

模型的进化并未使语义层失去必要性。恰恰相反，当 AI Agent 承担到执行环节时，剩余的十几%错误会作为业务事故显现出来，因此语义层的价值反而上升。

本体（Ontology）导入的5种失败模式

另一方面，构建本体也是一个难度很高的项目。最好先了解实施失败的典型情况。

1. 建模的对象不是业务，而是源系统

这是最常见的失败。如果将现有表原样照搬到对象类型中，就会出现一堆源自表名的名称，最终得到一个除数据部门外无人能看懂的模型。本体的价值在于“用现场的语言重新定义”，这样一来投资就全部白费了。正确的做法恰恰相反：设计应从业务流程开始，之后再连接现有模式（Schema）。

2. 膨胀与腐化

在被放任不管的本体中，可选字段不断增殖，几乎重复的对象类型并排存在，“第3个月某个团队作为变通方案需要”的 Action 会一直残留。定义越多，就越搞不清哪个才是正确的。

3. 定义缺少负责人

健康的运营需要为每个对象类型指定一位拥有裁定定义争议权限的具名负责人。如果“客户是谁”这个问题在销售和财务之间无法达成一致就继续推进，本体就会变成未被采纳的定义的坟场。

4. 试图一次性对全公司建模

构建并维护一个能准确表达整个组织的数据、流程和模型的本体极其复杂，还需要持续更新。“先制作全公司的完整地图”这种推进方式几乎注定会半途而废。

5. 供应商锁定

如果将业务逻辑、语义模型和运营工作流嵌入特定产品，迁移成本会变得极高。此外，Foundry 的本体不具备 OWL 式的逻辑推理引擎，也不是以多供应商的 Agent 互操作性为前提设计的。将本公司的语义定义在多大程度上保留在自己手中，是选型时应当有意识决定的议题。

这些与AI PoC 失败的5个结构性原因具有相同的结构。也就是说，问题不在于技术，而在于共识形成与运营设计。

日本企业特有的议题

1. “销售额”的定义因部门而异的问题

日本企业着手本体时，多数情况下会卡在这一步之前。因为销售额、稼动、客户、案件等基本术语，各部门在使用时含义各不相同。乍看之下这似乎是本体之前的问题，但其实统一这些术语本身就是导入本体的最大价值。以引入 AI 为契机，首次实现全公司术语定义的统一，这种附带效果不可小觑。

2. 协调文化与“事”的语言化

“物”（名词）的定义相对容易推进。难的是“事”（动词）。在日本企业的业务中，审批流程和例外处理往往没有明文化，而是靠现场的协调来运转。将这些隐性知识定义为 Action Type 是一项费力的工作，但竞争对手无法模仿的差异化恰恰埋藏在这里（关于企业内部知识的结构化，另请参见什么是 Company Brain）。

3. 权限体系的继承

谁可以查看哪些对象、可以执行哪些 Action。在日本企业中，能在多大程度上忠实继承 Active Directory 等现有权限体系，决定了实施的成败。这一点事后难以补做，是设计初期就应确定的项目。

4. 跨部门共识需要管理层的支持

统一定义必然伴随部门间的利益协调。仅靠现场主导的自下而上无法达成结论。能否建立让管理层能够裁定“就按这个定义执行”的体制，是项目的分水岭。

本体构建的推进方法｜5个步骤

作为失败模式的反面，现实的推进方法如下。

  • 从用例倒推：不是“全公司的地图”，而是选择一个想要改善的决策。从“配送延误时，将哪些班次改道”这样具体的问题开始
  • 将“物”限定在10〜30个：只定义该决策所需的名词。比起全面性，优先追求让现场觉得“用这个词就能明白”的精准度
  • 定义“事”，并确定执行权限：对每个 Action 都要写明“谁”在“什么条件下”可以执行。写到这个程度，才能委托给 AI Agent
  • 连接实际数据，消除模糊性：一旦接入实际数据，必然会出现“客户有3种”之类的矛盾。这种摩擦才是真正的考验，纸面设计是发现不了的
  • 连接 AI，运行评估循环：建立汇集业务实际问题的评测集，测量正确率和“不知道”率。使每次修改定义时数字都会变化

而且，成功的运营有共同的做法：每个对象类型都有拥有裁定权的负责人、Action Type 在发布前要通过评审，以及废弃不再使用的属性的流程已被文档化。本体不是做完就结束的东西，而是需要培育和修剪的对象。

FDX 所思考的“本体的构建方法”

本体不是买了产品就能得到的东西。它是一个将本公司的业务重新翻译成人类与 AI 可以共享的语言的实施项目。正因如此，如果兼具业务理解和技术实施能力的人才不进入现场，项目就无法推进。

FDX株式会社通过 Forward Deployed Engineer（FDE）与 Deployment Strategist（DS）的配对方式全程陪伴。

  • DS 与经营层共同把握“从哪个决策入手、以什么粒度定义”，并建立能够裁定部门间定义之争的体制（什么是DS）
  • FDE 深入现场，将物与事连接到实际数据、现有系统和权限体系（什么是FDE）
  • 先建立评测集，在测量精度和“无法回答”率的同时逐步完善定义
  • 与 AI Agent 的连接，从读取用途逐步扩展到执行用途（AI Agent 完全指南）
  • 最终将定义的所有权移交给内部团队，FDX 退出

“明明建好了数据平台，AI 却无法用于业务”“术语各部门各不相同，全公司的 AI 应用推进不了”。这类障碍往往不是工具选型的问题，而是语义定义的问题。FDX 从这里开始与您共同设计。

FAQ

Q1. 本体（Ontology）与知识图谱有什么区别？

本体是概念、关系、约束的“定义（模型）”本身，而知识图谱是将实际数据注入该定义后的实体。可以理解为“模板”与“按模板建成的建筑”的关系。“客户拥有一个以上的订单”是本体，“山田商事拥有订单 A、B、C”则对应知识图谱。实务中两者常被一起提及，因此容易混淆，但设计对象是本体这一侧。

Q2. 本体与语义层是同一个东西吗？

有重叠但不相同。语义层通常指将销售额、库存周转率等指标定义在全公司范围内统一的“读取”层。而以 Palantir 的 Ontology 为代表的企业级本体，在此基础上还拥有动作类型（Action Type）、函数（Function）等“执行”层，是同时处理读取和写入的应用程序的基础。如果想让 AI Agent 执行业务，就需要后者的覆盖范围。

Q3. 构建本体真的能提升 LLM 的精度吗？

多个独立基准测试都表明可以提升。在 data.world 的企业级基准测试中，直接查询 SQL 数据库的准确率为 16.7%，而将相同数据表示为知识图谱后达到 54.2%，约为 3 倍。再加上基于本体的查询检查（OBQC）和 LLM 修复，可达到 72.55%。dbt Labs 于 2026 年发布的基准测试也显示，针对相同的已建模数据，通过语义层的准确率为 98～100%，而让 AI 编写 SQL 的方式为 84～90%，差距依然存在。

Q4. 模型变聪明之后，本体就不需要了吗？

目前的实证结果恰恰相反。即使是 2026 年的最新模型，通过语义层的精度也明显更高。更重要的是，当 AI Agent 开始承担执行任务时，剩余的十几百分比错误会直接变成业务事故。仅用于读取时人类可以修正，但在自动执行下单、授信的阶段是不可接受的。合理的判断是：Agent 化越深入，语义层的重要性越高。

Q5. 不引入 Palantir 就无法构建本体吗？

可以构建。截至 2026 年初，Microsoft Fabric IQ、Databricks Unity Catalog Business Semantics（GA）、Snowflake Cortex 等主要数据平台都提供同等的语义层。也有使用 RDF/OWL 等开放标准构建的选项。比起产品选型，将自身业务翻译为物与事的设计工作更为重要。不过，如果将业务逻辑深度嵌入特定产品，迁移成本会很高，因此建议事先决定定义在多大程度上保留在自己公司。

Q6. 应该从多大规模开始？

试图一次性对全公司建模的做法几乎必然失败。现实的做法是：先选择一个想要改善的决策，将其中所需的名词限定在 10～30 个。一旦连接实际数据，“客户有 3 种定义”之类的矛盾必然浮现，尽早迎接这种摩擦反而更快见效。从取得成果的领域逐步扩展到相邻业务，才是正道。

Q7. 构建本体需要什么样的人才？

仅有数据建模的技术能力是不够的。还需要理解现场的业务流程，并将其翻译为数字世界中的物与事的设计能力。此外，由于必须建立能够裁定部门间分裂定义的体制，因此需要能够同时连接经营层与现场的角色。FDX 采用由 FDE（实现）与 DS（战略与共识形成）配对承担这一工作的设计（参考：DS 与 FDE 的角色差异）。

总结

  • 本体是用人类和 AI 双方都能理解的词汇与关系重新定义数据的“语义地图”，是连接数据集成与现场运营的粘合剂
  • 重新受到关注的理由有三个：AI 不仅读取还开始承担执行、LLM 打破了构建成本、主要数据平台向语义层收敛
  • 本体是“模板”，知识图谱是注入实际数据后的“实体”。语义层停留在读取层，而 Palantir 型则拥有到执行层的完整体系
  • 效果已得到实证。知识图谱化使正确率从 16.7% 提升到 54.2%，加上本体检查后达到 72.55%。即使是 2026 年的最新模型，通过语义层的精度也更高
  • 失败不是源于技术，而是源于共识形成。对源系统建模、定义负责人缺位、全公司一揽子推进是典型的失败模式
  • 在日本企业中，往往从“各部门对销售额的定义不一致”这一阶段开始，而统一这些定义本身就成为最大的价值所在
