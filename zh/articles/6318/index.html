GPU 需求不是矩形的

典型的容量合同会给客户在固定期限内提供固定数量的 GPU。把容量随时间画出来，就是一个矩形。但真实工作负载的表现不同：它们会在一天中增长、飙升和回落。按峰值购买，就要为闲置硬件付费；买少了，又有错失需求的风险。

Erik 将 Modal 的押注描述为一种期限转换：将数千家客户的需求汇集起来，在底层锁定容量，并让每个客户在需要时使用所需的量。总需求越平滑，这个资源池就越有用。这是对 我们与 SF Compute 的 Evan Conrad 对谈 的有益补充：Evan 专注于让容量可交易；Erik 则专注于让容量以更小、更弹性的切片被使用。

另一边也存在财务风险。如果供应商以当前价格锁定容量，而 GPU 价格随后下跌，就可能持有昂贵的供应。Erik 表示他不认为近期会出现崩盘，但认为在构建业务时这种可能性值得考虑。跳转到 GPU 价格讨论 →

差点没能活下来的沙箱

Modal 推出沙箱，是因为 Erik 和联合创始人 Akshat Bubna 注意到语言模型可以生成代码——而总得有个地方来运行这些代码。早期采用情况平淡，团队甚至讨论过关停这个产品。随后，编码 Agent、后台 Agent 和强化学习带来了新的需求。Erik 说，沙箱如今已增长到约占 Modal 收入的三分之一，这是他在发布时未曾预料到的结果。

这种增长也改变了基础设施需要承担的任务。一个 AI Agent 可能会创建环境、运行代码、检查结果，然后反复尝试多次。启动和恢复这些环境的延迟成为了体验的一部分。在我们最近对 Akshat 的采访中，我们探讨了这种从开发者体验到 Agent 体验的转变；在这里，Erik 补充了产品和业务层面的故事。跳转到沙箱讨论 →

快速启动是一项基础设施特性

弹性只有在容量能够足够快地到位时才有意义。Modal 的无服务器 GPU 文章描述了其中的机制：可用 GPU 缓冲池、自定义文件系统、进程检查点以及 GPU 内存快照。这些组件减少了让另一个模型副本上线所需的工作。这是基础设施决策如何体现在应用响应速度和成本上的一个具体例子。
