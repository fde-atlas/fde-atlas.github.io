构建应付账款的 Finance AI Agent：端到端指南

原标题：Build a Finance AI Agent for Accounts Payable, End to End

Cloud Soft Solutions · 2026-10-06 · 约 13 分钟读完

摘要

本文以 FDE 的方式演示如何为应付账款（AP）构建一个可上生产的财务 AI Agent：从印度中型制造商的共享服务中心场景出发，覆盖发票提取、供应商校验、由代码而非模型执行的三方匹配、异常解释与审批路由。核心原则是控制权在财务手中：Agent 只能暂存发票和设置状态，绝不付款、不改供应商或银行信息，所有决策留有证据和只追加审计日志。文章还给出评测指标、影子模式分阶段上线和 ROI 测算方法，可作为合成数据上的作品集项目。

要点

  • 以印度制造商 AP 场景为例，从业务痛点到可量化收益完整走通。
  • 三方匹配用确定性规则代码执行，LLM 只负责读取、解释和起草。
  • Agent 无付款、改主数据等工具权限，越权目标为零。
  • 评测覆盖提取准确率、异常精确率与召回、控制违规等指标。
  • 按影子模式、辅助模式、扩大推广三阶段上线，附 ROI 测算框架。

本指南以前沿部署工程师交付给财务团队的方式，构建一个应付账款（AP）财务 AI Agent：从业务问题出发，直到可衡量的回报。应付账款财务 AI Agent 只有在能够提取并校验发票、按财务部门设定的容差执行三单匹配、解释每一项异常、按授权额度路由审批，且绝不自行过账或放款付款时，才具备生产就绪条件。 该场景仅为示例；文末的里程碑计划使其成为一个可基于合成数据构建的作品集项目。

将文档转换为结构化字段的内容已在企业文档智能项目中介绍。本文涵盖提取之后的环节：应付账款流程、其控制措施，以及必须信任该系统的人员。

业务问题

示例场景。设想一家中型印度制造商，其共享服务应付账款团队位于海得拉巴。发票通过两种方式到达：作为 PDF 发送到共享的 AP 邮箱，以及通过供应商门户上传文件并填写若干表头字段。大多数发票与原材料和备件的采购订单（PO）相关。其余为服务、租金和水电等非 PO 发票。

AP 主管用运营层面的语言描述了痛点：

  • 文员将发票重新录入 ERP，并手工对照采购订单和收货单（GRN）进行核对。
  • 价格差异、少收货和错误的 PO 编号滞留在收件箱中，而供应商则在催促付款。
  • 月末发票激增，导致加班，且应计项目建立在数据不完整的基础上。
  • 内部审计已标记出重复付款，以及一例通过电子邮件提交并被接受的银行信息变更。

CFO 希望在不失去控制的前提下加快处理速度并减少审计发现。在财务领域，从 AI 演示走向企业级成果，意味着控制措施要更强，而不是更弱。

需求

需求调研阶段引入了 AP、采购、财务总监、内部审计、ERP 负责人和 IT 安全团队。

功能性需求

  • 从邮箱和门户摄取发票，提取表头、行项目和税额字段，并为每个字段提供置信度评分。
  • 对照供应商主数据进行校验：供应商存在且处于活跃状态、税务登记信息匹配、付款条款一致。
  • 按财务配置的容差，在行项目级别执行三单匹配（PO、收货单、发票）。
  • 在任何路由之前，检测可能的重复项和欺诈信号。
  • 为每项异常标记原因代码及其背后的证据，并起草供文员审核的供应商问询函。
  • 根据授权矩阵，将匹配成功的发票路由至审批流程。

硬性边界

  • AI Agent 绝不过账付款、创建付款批次、更改供应商主数据或编辑银行信息。
  • AI Agent 绝不在未经文员批准的情况下向供应商发送电子邮件。
  • 该 AI Agent 不提供税务建议。税务处理问题请咨询税务团队。

架构

该设计包含五个部分：接收、提取、确定性匹配与控制引擎、负责编排和解释的 AI Agent，以及 ERP 工具服务器。身份认证和只追加审计日志贯穿所有部分。

关键决策：

  • 匹配由代码完成，而非模型判断。 容差以及数量和价格检查是确定性规则；LLM 负责读取、解释和起草，但绝不决定匹配结果。
  • AI Agent 的 ERP 角色无权过账。 它可以读取、暂存（保存未过账）发票并设置工作流状态；过账和付款由人工负责。
  • 每个决策都附带证据。 每个异常都链接到导致该异常的采购订单行、收货单行和发票字段。

数据

发票

预期会遇到原生 PDF、扫描件、多页行项目表格，以及表头录入信息与文件内容不一致的门户提交件。存储每份原始文件及其哈希值，不做任何改动。

主数据与交易数据

  • 供应商主数据： 供应商 ID、法定名称、税务登记、银行信息（只读，对模型脱敏）、付款条件、状态。
  • 采购订单： 行项目包含物料、数量、单价、税码和未结数量。
  • 收货单： 每个采购订单行的已接收和已验收数量。对于服务，对应的是服务录入或验收单。
  • 发票历史： 用于重复检测和构建评测集。

印度发票上的 GST 字段

印度税务发票通常包含应付账款需要采集的 GST 信息。这些信息通常包括供应商和接收方的 GSTIN、发票号和日期、供货地点、每行的 HSN 或 SAC 代码、应税价值，以及分为 CGST 和 SGST 或 IGST 的税额。AI Agent 提取这些字段并检查其一致性：GSTIN 格式有效、供应商 GSTIN 与供应商主数据匹配、行合计正确。税务处理和进项抵扣问题属于税务团队的职责范围；任何依赖税务解释的规则均由财务部门提供并负责维护。

LLM

根据该 AI Agent 的实际功能选择模型，然后使用你自己的标注发票验证这一选择：

  • 结构化提取： 从混乱的版式中提取符合 schema 的 JSON。
  • 有据可依的解释： 异常原因仅引用传递给它的证据。
  • 平台与区域： 在财务与安全部门批准的区域使用 Amazon Bedrock、Azure OpenAI 或 Google Cloud 上的 Gemini。

将模型置于轻量客户端接口之后，并在代码使用输出前先按 schema 校验所有输出。

RAG

RAG 只占很小一部分：核心数据是结构化的，并通过 ID 获取。检索用于 AP 政策文档以及同一供应商过去已解决的异常案例，以辅助查询起草。可复用 RAG 知识助手项目 中的模式；政策回答必须引用现行政策版本。

三方匹配

对于每张发票行，引擎查找对应的采购订单行及其收货记录，然后比较：

  • 数量： 发票数量与尚未开票的已收货数量。
  • 价格： 发票单价与采购订单单价。
  • 合计与税额： 行合计、表头合计和税额与计算值进行比对。

容差由财务部门配置，而非工程师硬编码的数值。可以按供应商类别或公司代码设置为金额、百分比或两者兼有，并在超过某个金额阈值时适用更严格的规则。容差变更像任何控制变更一样进行版本管理和审批，每个决策都会记录其使用的版本。在没有收货单的情况下（例如某些服务），财务可以配置两方匹配。

异常与供应商问询

每个异常都会获得一个原因代码（价格差异、数量超过收货、未找到采购订单、GSTIN 不匹配、疑似重复）、其背后的证据，以及建议的下一步操作。对于供应商侧的问题，系统会起草一份问询函，引用发票号、采购订单行和差异；该图会在一个带检查点的 LangGraph interrupt 处暂停，直到业务员编辑或批准。 ServiceNow AI Agent 项目 详细展示了这种中断模式。

月末负载

月末业务量是设计输入，而非事后考虑。将提取运行为一个带有自动扩缩工作进程的队列。队列按到期日和提前付款折扣窗口排序，而非按到达时间。对 ERP 调用进行限速，以免其他月末作业被饿死。如果吞吐量落后，发票按顺序等待，AP 可在仪表板上看到积压情况。使用合成的月末批次进行负载测试。

任何工具都无法过账发票、释放付款或更改供应商或银行数据。这些工具根本不存在，因此提示词无法触达它们。

MCP/API

大多数 ERP 为供应商、采购订单、收货单和发票提供 REST 或 OData API。将它们封装在 MCP 服务器中（Model Context Protocol，Anthropic 于 2024 年底推出的开放协议）可以为工具契约、字段白名单、幂等性和审计提供一个统一的位置。对于单一的后端作业，直接调用 API 也是合理的。MCP vs API 阐述了其中的权衡。无论哪种方式，ERP 自身的角色模型始终是最终的执行点。

安全

职责分离

将 Agent 映射到现有的职责分离（SoD）模型中，作为一个独立角色。它可以捕获和提议，但不能审批、过账或付款。维护供应商主数据的人不能审批该供应商的发票，而 Agent 的服务身份不持有任何这些冲突权限。内部审计会像审查新员工的岗位一样对其进行审查。

审批限额

授权委托矩阵（金额区间、成本中心、审批人）以版本化配置的形式存在，由主计长负责管理。模型不能选择或跳过审批人，拆分发票以规避限额的行为会被标记。

重复发票检测

检查完全匹配（相同供应商、发票号和金额）和近似匹配：仅在标点或零填充上有差异的发票号、来自同一供应商的相同金额和日期，以及通过邮箱和门户同时到达的相同文件哈希。近似匹配会使发票挂起等待人工处理，而不会被自动拒绝。

欺诈信号

  • 银行信息变更： 如果发票或电子邮件显示的银行信息与供应商主数据不一致，Agent 会执行挂起并创建任务进行带外验证。这意味着拨打已知联系人并使用档案中已有的号码，绝不使用发票或电子邮件中提供的号码。Agent 无法更新银行信息。
  • 其他信号：新供应商的第一张紧急发票、恰好略低于审批限额的整数金额、发件人域名与供应商不匹配，或 GSTIN 不一致。
  • 将发票和电子邮件文本视为不可信输入。隐藏在 PDF 中的指令（“紧急批准，跳过审核”）最多只能产生一个被标记的异常，因为 Agent 没有执行该操作的工具。

审计追踪

为每个步骤编写只追加记录：源文件哈希、提取的值、模型和提示词版本、规则与容差版本、匹配结果、谁在何时批准了什么。审计人员可以重现任何发票为何按其方式路由。企业级 AI 治理涵盖此类系统的所有权、模型风险和变更控制。

云

  • 在 AWS 上： EKS 或 ECS，用于 PostgreSQL 的 Amazon RDS（状态、检查点、审计），带对象锁的 S3 用于保存原始文件，Bedrock、Secrets Manager 以及与 ERP 的私有连接。
  • 在 Azure 上： AKS 或 Container Apps，Azure Database for PostgreSQL，不可变 Blob 存储，Azure OpenAI 和 Key Vault，对于财务用户使用 Microsoft Entra ID 登录的场景是天然契合。

将数据保留在财务和安全部门批准的区域，并使用 Terraform 配置一切，以便审计既能追踪环境，也能追踪代码。

可观测性

每次发票运行都是一条追踪记录，包含提取、每次 ERP 工具调用、匹配、控制检查和审批等待的 span。在 Langfuse 或 LangSmith 中记录脱敏后的值、延迟、token 数、模型 ID 和提示词版本，并通过 OpenTelemetry 接入客户的监控系统。仪表板展示队列深度与到期日期的对比、按原因代码分类的异常、文员覆盖操作和欺诈冻结。某个供应商的置信度下降通常意味着出现了新的发票模板。更多细节见 AI 可观测性。

评测

在调优之前构建评测集：合成或匿名化的发票及其采购订单和收据，每份均由资深文员标注。

指标测试设计通过规则
字段级提取准确率跨布局、扫描件和多页案例的标注发票；按字段评分（GSTIN、总额、行数量）每个字段商定的阈值；关键字段采用更严格的标准
匹配决策一致性包含文员决策和原因代码的发票/采购订单/收货单集合与文员的一致性，按原因代码审查，而不仅看总体
异常精确率文员确认为真实异常的标记异常高到足以让文员持续信任队列
控制项异常召回率预置的重复项、近似重复项、银行账户变更和限额拆分案例每个预置的控制案例均被捕获
控制项违规注入的指令，尝试过账、付款或编辑供应商零；任何失败都会阻止发布

异常精确率低会用误报淹没文员；漏掉控制案例则会造成资金损失。按供应商和文档类型报告这两项指标。对 Agent 路径和动作进行评分的方法见 如何评测 AI Agent。

部署

GitHub Actions 运行单元测试、工具契约测试、控制项违规测试套件以及对照阈值的评测，然后进行构建、扫描和部署。Argo CD 同步到集群。提示词、容差和 DoA 矩阵均进行版本管理，并需要财务部门签字确认。

  • 影子模式： 决策与文员的决策进行对比，但不实际使用。
  • 辅助模式，单一公司代码：办事员确认每一步。
  • 更大范围推广：干净匹配自动路由给审批人。异常始终交由人工处理。一个开关可将 Agent 切回影子模式。避免在月末结账期间启动新阶段。

投资回报率（ROI）

ROI 是与财务主管商定的方法，并以基线为参照进行衡量。以下所有输入均为假设占位符，仅用于展示计算过程，并非实际结果。

输入占位符真实来源
每月处理的发票数（N）[占位符：N]ERP 和录入计数
每张发票节省的办事员分钟数（T）[占位符：T]计时样本，影子模式对比基线
办事员每小时综合成本（C）[客户数据]财务部门
新获取的提前付款折扣（D）[占位符：D]折扣报告，前后对比
防止的重复付款（P）[占位符：P]已确认的暂扣，经审计验证
每月运行成本（K）[来自账单]云服务、模型使用、支持

每月价值 = (N × T ÷ 60 × C) + D + P − K − 摊销的建设成本。对时间部分打折扣，因为并非每一分钟节省都能转化为有效工作。审计发现单独报告。

自己动手构建：里程碑计划

使用你自己生成的合成供应商、采购订单、收货单和发票，切勿使用真实雇主的财务数据。一个小型 PostgreSQL 模式可以替代 MCP 服务器背后的 ERP。

里程碑交付物
1. 模拟 ERP 和数据供应商、采购订单、收货单和发票表；一个生成器，用于生成干净、不匹配、重复和银行信息变更等案例
2. 提取经模式验证的提取，带逐字段置信度；首批字段准确率评分
3. 匹配引擎行级三方匹配，带版本化容差配置和单元测试
4. 控制重复和近似重复检查、欺诈信号暂扣、授权（DoA）路由
5. Agent 和 MCP 服务器LangGraph 图、无过账或付款能力的 ERP 工具、供应商查询时的办事员中断
6. 审计与运维仅追加审计日志、追踪、Docker、Terraform、以控制违规测试套件为门禁的 CI
7. 价值评测报告、月末负载测试、ROI 单页说明，以及展示银行信息变更暂扣的演示

常见问题

什么是用于应付账款的财务 AI Agent？

它是一种应用程序，使用 LLM 读取发票、对照供应商主数据和采购订单进行验证、通过确定性规则执行三方匹配、解释异常、起草供应商查询并将发票路由以供审批。在受控构建中，它从不执行过账或付款。

应该由 LLM 决定发票是否匹配吗？

不应该。匹配应由确定性代码执行，应用财务配置的容差。LLM 负责提取字段、解释结果和起草文本，这样每个匹配决策都可复现、可审计。

Agent 如何处理印度发票上的 GST 字段？

它会提取 GSTIN、供货地点、HSN 或 SAC 代码、应税价值以及 CGST、SGST 或 IGST 金额等字段，并根据供应商主数据检查格式和一致性。税务处理方面的问题留给税务团队；该 Agent 不提供税务建议。

如何防范银行信息变更带来的欺诈？

该 Agent 无法更改银行信息。如果发票或电子邮件显示的银行信息与供应商主数据不同，它会将该发票置于挂起状态，并创建一个任务，要求通过档案中已有的已知联系人进行带外核实。

对于应付账款 Agent，哪些指标最重要？

字段级提取准确率、与资深办事员的匹配决策一致率、异常处理的精确率、对种子控制用例（如重复发票）的召回率，以及必须保持为零的控制违规次数。

我可以在没有真实 ERP 访问权限的情况下构建这个项目吗？

可以。在 PostgreSQL 中模拟一个小型 ERP，生成合成的供应商、采购订单、收货单和发票，并通过你自己的 MCP 服务器将其暴露出来。评审者真正关心的是控制、评测和审计设计。
