面向 FDE 的 TabPFN：运行一次诚实的表格模型试点

原标题：TabPFN for FDEs: running an honest tabular model pilot

FDE Times · 2026-10-27 · 约 7 分钟读完

摘要

文章面向前沿部署工程师，讲解如何在客户真实数据上诚实验证 TabPFN 这类表格基础模型。TabPFN 由 Prior Labs 开发，用一亿个合成数据集训练，在最多一万样本的数据集上大幅超越以往方法，SAP 于 2026 年 5 月收购该公司，理由是 LLM 难以处理结构化业务数据。但基准成绩不等于客户表格上的效果，作者给出试点方法：与基线模型用同一时间切分对比、按数据量画学习曲线、用 ROC AUC 等抗类别不平衡的指标，并提醒防范数据泄露、勿超出论文验证范围、提前向厂商确认数据安全问题。

要点

  • TabPFN 从一亿个合成数据集学习，无需客户真实数据即可预测。
  • SAP 收购 Prior Labs，认为 LLM 难以预测结构化业务表格。
  • 试点须用同一时间切分、强基线和按数据量的学习曲线对比。
  • 类别不平衡时准确率会误导，应改用 ROC AUC 等指标。
  • 常见错误包括数据泄露、拿基准成绩代替实测和忽视一万行上限。

简要概述

  • TabPFN 从合成表格数据中学习，而非客户数据，并在最多 10,000 个样本的数据集上明显优于早期方法
  • 基准测试结果并不能证明其在客户真实表格上的表现，因此 FDE 的任务是在那张表格上再次证明这一点
  • 一个好的试点需要三样东西：在同一数据划分上的强基线、按数据量绘制的学习曲线，以及一个不会被类别不平衡迷惑的指标

一位客户发来他们 ERP 系统的导出数据：几千行订单、几十列字段，以及一个非常日常的问题：“提前告诉我们哪些订单会延迟交付。”总有人会补充一句：“为什么不交给聊天机器人，看看它能不能猜出来？”

这正是许多工程师容易卡住的地方。当 SAP 于 2026 年 5 月 4 日宣布收购 Prior Labs 时，它明确表示 LLM 难以对结构化业务数据做出预测，因为它们对表格、数字和统计只有肤浅的理解。客户的订单表恰好落在这个薄弱点上。

Prior Labs 开发的是 TabPFN，一个专为表格数据构建的基础模型。这类产品给 FDE 带来了一项非常具体的工作：在客户自己的表格上，诚实地证明这个基础模型比旧方法更有价值。

一个从虚构数据中学会如何学习的模型

对于表格数据，常见的做法是为每个问题单独训练一个模型，通常是梯度提升，然后调整其参数。TabPFN 走了一条不同的路线。根据 2025 年 1 月发表在 Nature 上的论文，它是一种学习算法，而这个算法本身是从数百万个合成数据集中学习得到的。

弗莱堡大学的新闻稿给出了一个具体数字：该模型在一亿个合成数据集上进行了训练。值得注意的细节是，它完全没有从任何客户的真实数据中学习。它学到的是如何面对一张陌生的表格并立即做出预测。

已发表的结果非常出色。在最多 10,000 个样本的数据集上，论文报告称 TabPFN 以较大优势超越了此前所有方法。弗莱堡大学还补充说，它只需 50% 的数据就能达到此前最佳模型相同的准确率。

如果这个基础模型如此出色，为什么还需要有人陪在客户身边？

因为基准测试不等于客户的表格。真实的表格中有事后被覆盖的列、中途改变格式的客户 ID，以及每个仓库定义都不相同的“延迟”标签。基础模型无法独自解决这些问题。

Prior Labs 也不把模型当作密封的黑盒来出售。早在 2025 年初的融资轮中，该公司就表示 TabPFN 支持在企业的专有数据上进行微调。到 2025 年 12 月向企业销售时，在客户自有数据上微调仍是其卖点的一部分。

而在客户数据上微调，就意味着必须有人到现场：理解数据、搭建数据管道、衡量结果，然后向决策者解释这些结果。

SiliconANGLE 将 Prior Labs 的目标描述为帮助企业理解并使用对其运营最重要的复杂信息。这类信息很少以干净的表格形式现成存在。把它变成可用的表格，正是坐在客户身边的人的工作。

一个诚实的试点是什么样子

想象一家拥有 1,800 个客户的分销商。每个客户是一行在特定日期记录的数据，包含 40 列，外加一列“下一季度是否流失”的标签。假设只有 90 个客户流失，即 5%。

一个预测“没有人流失”的懒惰模型可以达到 95% 的准确率，却一个流失客户都抓不到。因为它给每个客户的分数都相同，其 ROC AUC 正好是 0.5，和抛硬币没什么区别。所以准确率从一开始就被排除，取而代之的是 ROC AUC 以及最高风险组中的精确率。

但你需要回答的问题不是“TabPFN 好不好？”正确的问题是：在这张表上，它比基线好多少，需要多少数据？

下面的代码正是遵循这一思路：相同的时间切分、多个数据规模、多个模型。

from sklearn.metrics import roc_auc_score

# Fixed time-based split: train on the past, test on the later period
df = df.sort_values("snapshot_date")
cut = int(len(df) * 0.7)
train, test = df.iloc[:cut], df.iloc[cut:]
X_train, y_train = train[features], train["churn"]
X_test, y_test = test[features], test["churn"]

def learning_curve(make_model, fractions=(0.25, 0.5, 1.0)):
    scores = {}
    for frac in fractions:
        n = int(len(X_train) * frac)
        model = make_model()
        # Take the n rows closest to the test period
        model.fit(X_train.iloc[-n:], y_train.iloc[-n:])
        proba = model.predict_proba(X_test)[:, 1]
        scores[frac] = roc_auc_score(y_test, proba)
    return scores

# make_baseline: tuned gradient boosting
# make_foundation: tabular foundation model
results = {name: learning_curve(fn) for name, fn in
           {"baseline": make_baseline, "foundation": make_foundation}.items()}

学习曲线是最有价值的部分。如果基础模型只用 50% 的数据就能匹敌使用 100% 数据的基线，你就用真实数据亲自验证了弗莱堡方面的说法。对客户来说，这个结果非常实用：他们可以从一个地区的数据开始，而不必等到收集全国的数据。

如果两条曲线重叠，那也是一个结果。如实报告，然后提出下一步：也许是微调，也许是先清理标签。

自己动手：按什么顺序？

先和懂业务的人一起定义标签，并对每一列提出问题：这个值在预测时是否已知？这个问题能在你写下一行代码之前就挡住大部分数据泄漏。

接下来，锁定切分方式，构建一个经过良好调优的强基线。弱基线会让所有差距失去意义，客户那边敏锐的人会立刻发现。只有在这之后，才在相同的切分上运行基础模型和学习曲线。

最后，给出有条件的建议。如果基础模型明显且稳定地胜出，就在真实工作流中试用它。如果只是险胜，考虑在客户自有数据上进行微调——这一选项已包含在 Prior Labs 的企业产品中。如果它没有胜出，就保留基线，并记录原因。

让试点失去公信力的错误

最常见的错误是数据泄露：诸如“实际交付日期”这样的列混入了输入特征，让每个模型看起来都表现出色。第二个错误是把基准测试结果放在幻灯片上，代替在客户真实数据上测得的结果。Nature 那张图是尝试的理由，而不是这个项目的证据。

第三个错误是忘记适用范围。如果客户的表格远超 10,000 行，你就已经超出了 2025 年论文验证的范围，必须重新测量，而不是外推。

最后一个错误是向安全团队承诺你没有核实过的东西。模型在预训练时使用了合成数据，并不能说明客户的数据之后会流向哪里。

在安全会议之前，直接向供应商询问：模型在预测时需要哪些客户数据，微调期间数据存储在哪里，模型运行在谁的基础设施上？

这项技能如何体现在简历上

TabPFN 的下载量超过 300 万次，是一个广泛使用的开源工具，所以你可以立即练习，无需等待项目机会。上面那个 1,800 家客户的试点，你可以用公开数据自己搭建。

在阅读基础模型公司前沿部署 ML 工程师的职位描述时，留意诸如“在客户数据上微调”“模型评估”以及“直接与客户合作”之类的措辞。

然后撰写简历来证明这些能力。不要写“熟悉表格机器学习”；要写：什么问题、哪个基线、哪个指标、差距多大、数据规模多大。

招聘 FDE 的人想看到的是，你在懂得赞美之前先懂得测量。一个从 1 亿张假表格中学习过的模型，仍然需要有人对真实表格提出最难的问题：在预测时，我们真的已经知道这一列了吗？
