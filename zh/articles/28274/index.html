前沿部署工程，第 8 部分：现场调试

原标题：Forward deployed engineering, Part 8: Debugging in the field

Abhinav Bhatia · 2026-10-20 · 约 17 分钟读完

摘要

本文是前沿部署工程系列第八篇，讲解 FDE 如何在客户现场调试不属于自己的系统：从用户症状出发，按固定顺序阅读陌生代码，用“复现阶梯”逐步剥离变量让故障按需发生，再通过日志与追踪定位根因。文中以 Acme 案例为例：专家 Agent 返回 401 登录失败，却被 writer 包装成“没有数据”，根因是客户端未按文档要求使用 mTLS 证书绑定令牌。作者强调判断问题归属（客户环境、自己的代码还是产品缺陷）、临时方案须有负责人和截止日期且绝不削弱安全性，并给出可执行的产品团队报告模板。

要点

  • 现场调试遵循循环：症状、复现、观察、定位归属、修复或临时方案、报告。
  • 读陌生代码应先跑一次、找入口、跟随一个请求，而非从头读仓库。
  • 复现阶梯逐层剥离变量，最终用秒级单元测试验证修复。
  • Acme 案例中 401 登录失败被 writer 掩盖为“无数据”，根因是未用 mTLS。
  • 临时方案须记录负责人与截止日期，且绝不能以削弱安全为代价。

一个你并没有编写的系统出了问题，发生在一个你无法掌控的环境里，而且是在客户面前。本部分将介绍前沿部署工程师如何阅读陌生的代码、复现故障、查看日志和追踪信息、判断这是谁的问题、在临时解决方案和彻底修复之间做出选择，以及撰写一份产品团队可以据此行动的缺陷报告。

在第 7 部分中，我们把 Acme Consumer Brands 的原型推向了生产环境，并连同运维手册一起交给了客户的团队。这正是真实用户到来的时刻，而真实用户会发现测试没有发现的问题。第一条消息通常长这样，来自 Acme 的供应规划师 Sam：“助手说供应团队没有上周缺货的数据。我们肯定有这些数据。”

接下来发生的事情，是前沿部署工程师工作中最显眼的部分之一。代码可能是你的、客户的，或者是某个产品团队的。故障发生在一个你不拥有的环境里。而且人们正在观察你能否快速、冷静地弄清楚到底发生了什么。

本部分将介绍如何阅读你没有编写的代码、复现故障、查看日志和追踪信息、判断这是谁的问题、在临时解决方案和彻底修复之间做出选择，以及撰写一份产品团队可以据此行动的报告。

这在 FDE 的职位描述中是如何体现的？

调试几乎出现在每一份公开的 FDE 招聘信息中，通常与向产品团队反馈的闭环放在一起。以下是截至 2026 年 10 月 20 日的三个例子：

  • Google Cloud 的 Forward Deployed Engineer, Gen AI 招聘信息描述了这样一个人：他将“直接在客户环境中编写代码、调试并共同交付定制的 Agent 解决方案”，并且将“识别 Google AI 技术栈中可复用的现场模式和摩擦点，将其转化为可复用的模块或提交给工程团队的正式产品功能请求”。
  • Microsoft 的 Principal Forward Deployed Engineer 招聘信息写道：“编写原型，阅读追踪信息，在客户的代码库中工作。”它还要求工程师带给产品团队的是模式而非个例，“包括复现步骤、测量数据、架构分析和量化的业务影响”。
  • OpenAI 的 Forward Deployed Engineer 招聘信息（伦敦）要求应聘者能够“分享现场反馈，帮助研究和产品团队了解模型在哪些方面表现出色，在哪些方面可以改进”。

所以这份工作同时包含两件事：让客户的系统今天就能运转起来，并把你的所学转化为能改进产品、惠及所有人的证据。

我首先需要了解什么？

以下是本部分使用的术语，每个都附有通俗解释：

  • 症状（Symptom）： 用户看到的现象，用他们自己的话描述。它不是原因。Sam 的症状是“没有数据”。
  • 复现（Reproduction）（常简称为 repro）：一组能让故障按需发生的步骤。最小复现（minimal reproduction） 是仍然能触发故障的最少步骤和代码。
  • 日志（Log）： 代码运行时记录的单个事件的记录，例如“工具被调用”或“请求被拒绝”。结构化日志（structured log） 以数据形式（通常是 JSON）写入，因此可以按字段过滤。
  • 追踪与跨度（Trace and span）： 追踪（trace） 是一个请求从头到尾的完整记录，由多个跨度（span） 组成。每个跨度是一个计时步骤，例如一次模型调用或对另一个 Agent 的调用。
  • 根因（Root cause）： 最早的那个环节，如果它有所不同，故障就不会发生。它之后的一切都是后果。
  • 临时解决方案（Workaround）： 在原因仍然存在的情况下规避问题的改动。
  • 回归测试（Regression test）： 如果这个确切的问题再次出现就会失败的测试。

综合起来，它们构成了每次现场排查都会遵循的一个循环：

现场调试循环：从用户描述的症状出发，让故障按需复现，通过日志、追踪和代码观察它，隔离是谁的问题，修复它或应用一个注明日期的临时解决方案，带着证据上报，然后闭环

人们很容易从症状直接跳到修复，因为客户正在等待。在我与合作伙伴的合作中，大多数没有奏效的修复都源于跳过了中间步骤。

如何阅读不是我写的代码？

前沿部署工程师经常调试别人写的代码：客户的团队、合作伙伴，或者已经离职的同事。常见的错误是从仓库顶部开始逐个读文件。一个大型代码库包含的代码远超你的需要，而且在你看到一次请求完整走一遍之前，你不会知道哪些部分是重要的。

我每次都使用同样的阅读顺序：

阅读非自己写的代码的顺序：先运行一次，找到入口点，跟随一个请求从头走到尾，读测试以了解意图，然后搜索确切的错误文本并查看该文件的修改历史

入口点（entry point） 是请求进入代码的地方。在 ADK 项目中，它是

root_agent

in

agent.py

；对于 Acme 路由器，它是构建于

the router post of the agents series

中的图工作流。从这里开始，只读这一个请求所经过的代码。测试告诉你作者希望代码做什么，而对抛出错误的文件执行

meant

和

git log

可以告诉你谁最后修改了它以及为什么。AI 编程助手在这里能节省大量时间，例如解释一个模块或找出一个函数的所有调用者。但在依赖它们给出的信息之前，请对照代码进行核实。

git blame

在引发错误的文件上，能告诉你最后是谁修改了它以及为什么。AI 编程助手在这里能节省大量时间，例如解释某个模块或找出某个函数的所有调用者。在依赖它们给出的信息之前，请先对照代码进行核实。

对于 Acme 路由器，入口点很短，一分钟就能读完。它是一个边的列表：

root_agent = Workflow(
    name="acb_demo_router",
    edges=[
        (START, front),
        (front, {"continue": extract, "reply": reply}),
        (extract, route),
        (route, {
            "marketing": marketing_remote,
            "supply": supply_remote,
            "both": both,
            "decline": decline,
        }),
        (marketing_remote, writer),
        (supply_remote, writer),
        (both, writer),
    ],
)

这几行告诉你一个问题可能涉及哪些节点，从而应该先打开哪些文件：对于“无数据”的回答，会调用远程专家和撰写器。Agent 系列的路由文章解释了每条边。

如何按需制造一次故障？

看不到故障就无法修复。任何排查的首要真实目标都是复现。从用户遇到问题的地方开始，然后每次移除一个活动部件，直到故障在一个小而快的场景中发生：

复现阶梯：从用户遇到问题的地方开始，每一步移除一个活动部件，从 Gemini Enterprise 中的 Sam，到 staging 路由器，再到发起一次 A2A 调用的脚本，最后到一秒内运行完的单元测试

沿阶梯每往下一步，就排除一个可能的罪魁祸首。当故障仍然发生在一个只对 supply agent 发起单次调用、完全不涉及模型的脚本中时，你已经排除了提示词、模型和用户界面。当它发生在单元测试中时，你可以在几秒钟内尝试修复，而不必重新部署。

在客户环境中，有两点实际注意事项。第一，使用测试身份，而不是用户的身份。你绝不应该向 Sam 索要他的密码或令牌，以便“以他的身份尝试”。第二，边做边记录每一步，并加上时间戳。写报告时你会需要它们，客户的安全团队也可能询问你做了什么。

如果故障不是每次都发生，它就是间歇性的：记录发生频率（“20 次尝试中 3 次”）以及失败的那些尝试有什么不同。如果以前是正常的，

git bisect

通过测试最后一个正常版本和第一个异常版本之间的各个版本来找出导致故障的变更。

日志和追踪能告诉我什么？

一旦能够复现故障，你就可以仔细查看它。对于 agent 来说，最有用的视图通常是追踪，因为它在时间线上显示一次请求的每一步。Acme 的 agent 将追踪发送到 Cloud Trace，将结构化日志发送到 Cloud Logging，具体设置见 agent 系列的部署、观测与成本文章。

这是 Sam 那个问题的追踪的简化版本：

Sam 的问题的追踪：两次对专家的调用都以 401 快速结束，而撰写器仍然写出了一个回答，于是登录失败以“专家没有数据”的形式到达 Sam

两次对专家 agent 的调用几乎立即结束，都返回 HTTP 401（服务器表示“我不接受你的凭据”的方式）。这些 span 的日志包含完整消息：“未满足 Context-Aware Access 要求。”然后撰写器仍然运行，没有收到任何结果，于是写出一个礼貌的回答，说专家没有数据。

最后一步正是这个问题令人困惑的原因。故障把自己隐藏了起来。 登录失败以空结果的形式呈现给用户。阅读调用链路时，要注意三点：结束得远比平时快的步骤、以错误码结束的步骤，以及在前面某一步失败后却若无其事继续执行的步骤。

是客户的运行环境、我们的代码，还是产品本身的问题？

这是现场调试中最重要的问题，因为它决定了谁必须采取行动。运行环境是客户运行的一切：他们的网络、安全策略、身份提供商。故障可能来自那里，来自你和客户编写的代码，也可能来自产品本身。我会依次问两个问题：

隔离原因：如果只在客户的运行环境内失败，就查看他们的网络、策略和身份提供商；如果在你自己的项目中失败，而产品的行为与其文档一致，那就是你的代码或配置问题；如果产品行为与文档不符，那就是产品缺陷

在客户的运行环境之外也会失败吗？ 用你自己的测试项目运行同样的代码。如果只在客户那里失败，就查看他们的环境：检查加密流量的代理（位于他们网络与互联网之间的服务器）、防火墙规则、VPC Service Controls 边界（Google Cloud 中围绕一组项目的边界）、组织策略或身份提供商设置。本系列第 3 部分讲过如何在第一周询问这些内容。

产品的行为与其文档一致吗？ 阅读官方页面，而不是论坛回答或模型的总结。如果产品行为与文档一致，问题就在你的代码或配置中。如果不一致，你可能发现了一个产品缺陷。

对 Acme 来说，答案很快出来了。故障在我们自己的测试项目中也发生了，所以不是 Acme 的运行环境问题。而且 Agent Runtime 文档说明 Agent Identity 令牌默认是证书绑定的：令牌只在出示匹配客户端证书的连接上才被接受，使用的是 mTLS（双向 TLS，客户端和服务器都要证明各自的身份）。我们的第一个路由器使用了标准 HTTP 客户端，只发送令牌而不带证书。产品的行为与文档完全一致。缺陷在我们的传输层，修复方法是加载运行时的证书并调用 mTLS 端点。修复的核心是一个小型传输层，这里做了简化：

class AgentIdentityMtlsTransport(httpx.AsyncBaseTransport):
    async def handle_async_request(self, request):
        ctx = mtls.get_default_ssl_context()  # None: no cert
        if ctx:
            host = _to_mtls_host(request.url.host)
            request.url = request.url.copy_with(host=host)
        inner = httpx.AsyncHTTPTransport(verify=ctx)
        return await inner.handle_async_request(request)

在运行时上，它出示 Agent 的证书，并将 Google API 调用发送到

*.mtls.googleapis.com

主机。在没有证书的笔记本电脑上，它的行为就像普通传输层。

逐行解释了这个修复。

说句实在话：“我们的代码”并不意味着产品团队没有需要学习的地方。我们浪费了时间，因为错误以数据缺失的形式呈现给用户，这是有用的反馈。我在下文会再谈到这一点。

我应该修复它，还是绕过它？

有时修复需要数天时间，而客户等不了那么久。一个临时方案能让客户继续运转，但前提是必须以严格的纪律来处理：

临时方案与修复的区别：临时方案是在原因仍然存在的情况下绕过问题，因此需要指定负责人、截止日期和书面记录；修复则消除原因并附带测试；临时方案绝不能削弱安全性

一个临时方案需要写下三件事：由谁负责、何时结束以及记录在哪里。缺少这些，它就会变成永久方案，下一个团队接手的将是一个谜团。对于 Acme，在传输层修复进行测试期间，一个合理的临时方案是暂停供应类问题并显示一条明确的提示信息，而不是让路由器回答“无数据”。

有一种临时方案我绝不接受：削弱安全性的方案。文档允许你关闭令牌绑定。这会让 401 错误在几分钟内消失，但也会让任何泄露的令牌在任何地方都能使用。前沿部署工程师是客户环境中的客人，为了演示能跑通而降低他们的安全性，会破坏整个合作所依赖的信任。

我如何撰写一份产品与工程团队能够据此行动的报告？

当原因确实出在产品上，或者产品让人容易犯错时，你的报告就是产品团队将会看到的东西。他们不认识客户，看不到客户环境，而且会收到大量报告。一份好的报告能让工程师在不需要问你任何问题的情况下复现问题。

Google Cloud 关于支持工单的公开指南要求提供任何产品团队都需要的核心信息：ISO 8601 格式的精确时间、产品和功能、位置、具体标识符（如项目 ID）、有用的工件，以及问题是间歇性的还是持续性的。我还会加上预期行为、影响和最小复现步骤。以下是我使用的模板：

TITLE: <component>: <what happens> when <condition>
       e.g. "Agent Runtime A2A call: 401 'Context-Aware Access requirements
       are not met' when the client sends a bound token over plain TLS"

SUMMARY      One or two sentences. What fails, for whom, since when.
ENVIRONMENT  Product and version, region, project ID (never a token or a
             customer name), SDK and library versions.
TIME         First seen 2026-10-14T09:12:00Z; still happening / ended at ...
STEPS        Numbered, from a clean start. Link the minimal reproduction.
EXPECTED     What the documentation says should happen (link the page).
ACTUAL       What happened. Exact error text, request ID, trace ID.
FREQUENCY    Every time / 3 of 20 attempts / only after ...
IMPACT       Who is blocked and what it costs, in plain words.
WORKAROUND   What we do meanwhile, and why it is not good enough.
ASK          Bug fix, documentation change, or feature request.

两条规则让这个模板发挥作用。第一，每个问题一份报告。Google 的支持指南也是这么说的：每个问题一个工单，重复的会被关闭。第二，删除所有机密信息。在复现中使用你自己的测试项目和测试身份，绝不使用客户的令牌、数据或名称。

如果产品的行为与文档一致，报告就变成功能请求或文档请求。对于 Acme，报告大概会是：“当证书绑定的令牌在没有 mTLS 的情况下使用时，返回一个明确说明这一点的错误，并让 A2A 示例默认使用 mTLS 传输。”这正是 Microsoft 那篇帖子所要求的模式，也是 Google 那篇中的“正式产品功能请求”。来自一个客户的一份报告只是个例。在三个合作项目中看到同样的摩擦，并附上三个复现步骤，才是产品团队能够据此行动的模式。

我如何形成闭环？

提交报告并不是终点。只有当客户在没有临时方案的情况下也安全无虞，并且没有人会再遇到同样的问题时，这个闭环才算真正完成：

闭环：现场发现变成报告，产品团队对其进行分类处理，随后返回一个变更或明确的答复，临时方案在预定日期被移除，回归测试和操作手册条目确保没有人再遇到同样的问题

  • 告诉客户你发现了什么、改了什么、还有什么未解决，用他们的团队可以复述给管理层的语言来表达。第 10 部分讲解如何向高管汇报。
  • 跟踪报告，直到问题被修复、得到答复，或被关闭为“按预期工作”。当状态发生变化时，及时更新客户。
  • 在你写下的日期移除临时方案，或者调整日期并说明原因。
  • 添加回归测试。 对于 Acme，这次事件产生了两个测试：传输层必须在运行时使用 mTLS 主机，并且每个 401 或 403 必须以错误形式出现，绝不能表现为空结果。Agent 系列的评测文章展示了这类测试如何为发布把关。
  • 把它写进操作手册，让下一次项目中的下一位工程师能在几分钟而非几小时内识别出同样的症状。

Google 的 SRE 手册将这种书面版本称为无指责事后复盘：一种回顾原因和修复方案、但不追究个人责任的复盘。同样的基调也适用于客户沟通。

试试看：把模糊的症状变成报告

做这个练习不需要云项目。请看下面这条消息，这是前沿部署工程师每周都会收到的那种消息：

“助手又出问题了。今天早上它给 Maria 一个奇怪的答案，现在没人信任它了。”
  • 用用户的语言写下症状，然后列出在动任何代码之前你会问 Maria 的五个问题。（我的问题从这些开始：你问了什么、在什么时间、你期望看到什么？）
  • 为它画出复现阶梯，就像上面的图示那样。能够仍然展现问题的最小单元是什么？
  • 决定你会在追踪中寻找什么。 你期望看到哪些步骤？如果哪些步骤缺失、耗时极短或以错误结束，会让你担忧？
  • 填写报告模板，在尚不清楚答案的地方使用占位符。空白字段会告诉你接下来需要查明什么。

如果你有一个已部署的 Agent，请在 Cloud Trace 中挑选一个失败的请求，并用一段话逐步解释它。

可能出现的问题

  • 只修复症状。 修改 writer 的提示词让它不再说“无数据”，反而会把 401 隐藏得更好。始终要找到最早出错的步骤。
  • 先在生产环境中调试。 每次尝试都很慢，每个错误都清晰可见。
  • 索要用户的凭证。 应使用测试身份。如果这个 bug 只发生在某一个用户身上，请将该用户的权限与你的测试用户的权限进行对比。
  • 过早归咎于产品。 一份最终发现是配置错误的报告，既浪费产品团队的时间，也损害你的信誉。先查阅文档。
  • 没有截止日期的临时方案。 它们会变成永久性的，而且没有文档记录。
  • 报告里满是客户细节。 工单中的姓名、令牌和数据都是泄露。在你自己的项目中复现问题。
  • 保持沉默。 三天没有任何消息的客户会以为什么都没发生，即使你每天都在处理。

我现在会怎么做

  • 在任何事情出问题之前，先为你今天正在构建的 Agent 编写复现阶梯。
  • 确保每个身份验证错误都作为错误记录并导致测试失败，绝不能作为空结果处理。
  • 将报告模板复制到你们团队的跟踪系统中，作为新问题的默认模板。
  • 建立一个操作手册页面，每个现场问题记录一条：症状、原因、修复方法和测试。
  • 在第一周就与客户约定好：他们将如何向你报告问题，以及你将如何向他们更新进展。

我们学到了什么？

  • 现场调查遵循一个循环：症状、复现、日志和追踪、根因、修复或临时方案、报告，以及回归测试。
  • 从入口点阅读不熟悉的代码，跟踪一个请求的完整流程，并借助测试和历史记录来理解作者的意图。
  • 使用测试身份和仍然能触发失败的最小步骤集来复现故障，并记录每一步及时间戳。
  • 在追踪中，注意结束得太快的步骤、以错误结束的步骤，以及在先前步骤失败后仍继续执行的步骤，因为失败可能把自己伪装成空结果。
  • 通过以下问题判断是谁的问题：它在客户环境之外是否也会失败？产品的行为是否符合其文档所述？
  • 临时方案需要有负责人、截止日期和记录，并且绝不能削弱安全性；一份好的报告能让产品工程师无需向你提问就能复现问题。
