洞察 04

在现场完成 AI 落地的新型工程师形象

FDE（Forward Deployed Engineer，前沿部署工程师）是一种不局限于开发据点、主动深入客户企业业务现场，将 AI 的设计、实现与运营一气呵成地承担起来的工程师角色。该概念由 Palantir 提出，并作为以 OpenAI 为代表的 AI 企业的核心职位迅速普及。本文将从定义、由来、工作内容以及与其他职位的区别等方面，系统性地梳理“什么是 FDE”。

FDE（Forward Deployed Engineer）直译为 “部署在前线的工程师” 。该名称源自军事术语 "forward deployed"（前方部署），指常驻并贴近远离开发据点的客户现场、从发现问题到实现与运营全程负责的工程师。

传统的软件开发中，需求定义由客户方负责，实现由开发供应商负责，角色与物理距离划分得非常明确。FDE 则有意打破这一界限，让工程师自身深入客户的业务之中，实现“在现场发现问题、当场构建、当场改进”的 短周期改进循环 。

最早将 FDE 这一职位体系化的，据说是美国的数据分析公司 Palantir Technologies 。Palantir 面对政府机构和大型制造业等处理复杂且高机密性数据的客户，需要提供的不是千篇一律的 SaaS，而是 “为每个客户量身优化的软件” 。

为此而诞生的，就是把工程师派驻到客户现场、从理解数据结构到重新设计业务流程、再到实现仪表盘一气呵成承担下来的 FDE 工作方式。FDE 也常被形容为“能写代码的战略家”“理解业务的实现者”。

随着生成式 AI 的普及，FDE 的价值被重新审视。 OpenAI 将 Forward Deployed Engineer 列为主要招聘职位之一，将其定位为推动企业版 ChatGPT 和 API 落地成功的角色。Google、Salesforce、LayerX 等认真投入企业级 AI 的公司，也开始招聘承担 FDE 类角色的人才。

其背后的现实是： “AI 即使能够导入，要让它真正融入业务却极其困难” 。即便模型和 API 日益通用化，最终成果仍深度依赖于 业务数据、业务流程和用户的使用方式 。能够在现场即时调整这些要素的人才，才真正决定 AI 的 ROI。

FDE 在现场承担的工作，大致可以归纳为以下 4 项。

  • ① 业务理解与访谈：结构性地把握现场的隐性知识、判断标准、现有业务流程和评估指标。
  • ② 设计与原型制作：基于所获得的理解，设计包含 AI、数据基础和 UI 在内的解决方案，并在数天至数周内做出可运行的原型。
  • ③ 实现与集成：与现有系统、数据源、认证和运营流程集成，打磨到现场实际可用的状态。
  • ④ 落地与改进：在现场收集反馈的同时，持续改进功能、提示词、UI 和运营设计。

关键在于， 这些工作不是由不同的负责人分工推进，而是由一个人或小型团队横向承担 。由于减少了会议流程和交接环节，改进周期会变得极短。

FDE 与哪些职位相近？下面梳理一下常被拿来比较的几个角色。

  • IT 咨询顾问：以战略制定和需求定义为中心，通常不会写代码并完成实现。FDE 则是“能写代码的战略家”。
  • SE、委托开发：按照规格说明书进行开发，很少与客户一起共同制定规格。FDE 则是“在规格确定之前就进入现场”。
  • 产品经理：决定产品的方向和优先级。FDE 的不同之处在于“为眼前的客户动手做事”。
  • SRE、基础设施工程师：以系统的稳定运营为主要目标。FDE 则以业务成果（ROI）为主要目标。

详细的比较在 FDE 与 IT 咨询的区别是什么？AI 落地中产出结果的责任人的角色 中有系统梳理。

要作为 FDE 取得成果，需要同时具备 硬技能（实现能力）、领域知识（业务理解）和软技能（适应能力） 这三项。技术对应 SE，业务理解对应咨询顾问，适应能力对应 PM——FDE 的本质难度与价值，正在于 由一个人横向跨越 这些原本分属不同职位的强项。

关于这三项技能组合为何重要，在 FDE 必备的 3 项技能｜以实现能力、业务理解和适应能力驱动现场 AI 中有详细讲解。

许多 AI 导入项目止步于 PoC（概念验证），未能进入正式运营便草草收场。原因不在技术，而在于 “没有人能够一边吸收现场的隐性知识、一边推进到实现落地” 。咨询顾问整理需求，供应商按规格说明书开发，现场却说“这根本没法用”然后结束——这种结构性失败在 AI 项目止步于 PoC、AI 无人使用的原因与规避方法 中有详细梳理。
