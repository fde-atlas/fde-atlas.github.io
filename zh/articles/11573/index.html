FDE 实战演练手册：界定范围、构建方案、答辩展示（附练习题）

原标题：The FDE Take-Home Playbook: Scope, Build, Defend (with a Practice Spec)

Vibe Engines · 2026-07-31 · 约 12 分钟读完

摘要

这篇文章讲解 FDE 招聘流程中带回家作业（take-home）的应对方法。作者指出 OpenAI、Sierra、Distyl 等公司的考核重点不是产出量，而是范围判断、验证和可辩护性。文章给出五阶段方法（先写范围备忘录、搭骨架、做通一条窄路径、证明可用、写文档并演练），并附一道五小时物流邮件分类练习题、30 分自评量表和时间分配的收益分析。核心结论：明确写出不做什么、测量标注不一致带来的准确率上限、超时排队而非丢弃、记录权衡取舍，比多加功能得分高得多。

要点

  • 评分权重最高的是范围判断，明确写出不做什么最有价值
  • 五阶段法：范围备忘录、骨架、窄路径、验证、文档演练
  • 测量标注不一致率，据此设定可达的准确率目标
  • API 超时应排队重试且保证幂等，不能丢邮件
  • 超时砍功能不砍验证，验证是每分钟得分最高的阶段

带回家作业是现代 FDE 面试流程的重心——在 OpenAI 是数小时的构建任务，在 Sierra 是从零实现一个 agent，在 Distyl 是借助 AI 完成的构建。这三者的评分标准完全相同：不看你产出了多少，而看你是否合理界定了范围，以及能否为每一个决策辩护。下面是方法，外加一份练习题规格和评分标准。

评分者真正在考察什么

FDE 面试中的带回家作业是一次客户交付项目的缩影。评分者在问：面对一个模糊的任务说明和固定的时间预算，这个人选择构建什么，拒绝构建什么，如何知道它有效，以及能否向客户解释清楚？

产出量不在考察之列。一个范围窄但完整、带测试和清晰文档的构建，永远胜过一个面面俱到却松散的作品。

信号权重如何解读
范围判断最高你是否砍掉了该砍的东西并明确说明？一份明确的“不构建 X 是因为 Y”清单是你能提交的最有力材料。
验证高测试、评测或可复现的检查。在部署类岗位上，“它能用”却拿不出证据是最无力的说法。
失败处理高超时、速率限制、格式错误的输入、部分失败。这正是这个岗位存在所要应对的企业现实。
可辩护性高每个不显而易见的决策都有一句话理由。这是走查环节评分的内容。
可运维性中别人能跑起来吗？一份两段式的运行手册很少见，且显得资深。
代码质量中可读且风格一致。没人会给“聪明”加分。
功能数量最低常常是负分。只有广度没有深度会被解读为判断力差。

方法

五个阶段，各有固定的时间预算。预算比技巧更重要——大多数失败都是时间分配的失败。

界定范围，在写任何代码之前

先写一份简短的备忘录：这个方案解决什么问题、用户是谁、成功意味着什么、你会构建什么、明确不构建什么，以及你做了哪些假设。半页即可。它会成为你 README 的开头和答辩的主线。

如果任务说明是模糊的，那是有意为之。请用书面形式解决歧义，而不是默默猜测。

搭建整条路径的骨架

端到端，用占位实现：输入、处理、输出、错误路径。第一小时内就让某些东西跑起来，哪怕每一步都是假的。这能保证当时间不够时——时间总是不够——你交付的是一个完整的东西。

构建那一条真实路径

让这条窄路径真正跑通。边做边处理那些难看的边界情况，而不是留到最后：超时、限流、格式错误的行、部分失败、不能造成重复的重试。抵制一切做第二个功能的冲动。

证明它

为必须成立的性质编写测试，如果输出是模糊的就用评测。然后刻意破坏它：断网、喂垃圾数据、把同一个请求发两遍。修复坏掉的地方，或将其记录为已知问题。

这是人们在时间紧张时最先砍掉的阶段，却是每分钟得分最高的阶段。

撰写文档并演练

README：范围备忘录、如何运行、三个附带被否决方案的权衡、已知局限，以及如果再多两天你会做什么。然后演练一段两分钟的口头概述——问题、范围、方法、证据——因为答辩就是这样开场的。

“如果再多两天我会做什么”是整个提交中最便宜的高价值段落。它把每一个缺口从疏忽变成明确的权衡，也给面试官一个容易切入、富有成效的开场问题。

一份练习题——五小时，贴近真实

刻意保持模糊，形似真实的任务简报。给自己设定时间上限，然后用下面的评分标准给自己打分。

一家中型物流公司每天收到约 400 封支持邮件。如今一位运营协调员会逐封阅读，判断它属于六个类别中的哪一个，如有运单号则提取出来，并分配优先级。他们想把这一流程自动化。他们给了你一份包含 300 封历史邮件的文件，附带团队标注的标签，以及一个内部运单 API 的访问权限，该 API 可以查询运单号并返回运单状态。

交付物： 一件他们明天就能运行的东西，外加你的推理过程。五小时。

让这道题成为真正的 FDE 考验的，正是那些模糊之处：

陷阱

  • 那 300 个标签不一致——同一类邮件出现在两个类别下。你会去核查吗？
  • “优先级”没有定义。你是自行发明一个定义，还是询问并声明一个假设？
  • 运单 API 有时会超时。你的流水线会丢掉那封邮件吗？
  • 有些邮件没有运单号。这是错误还是正常情况？
  • 没有人说清楚准确率达到多少才算够好。你能提出一个阈值并说明理由吗？

一份优秀提交是什么样子

  • 一份范围备忘录，指出标签不一致问题并对其进行量化。
  • 一条完整路径：邮件进，类别和运单号出，错误得到处理。
  • 一个留出的评测集，附明确的指标和明确的目标。
  • 当 API 不可用时实现优雅降级——进入队列，而不是丢弃。
  • 一份明确列出未构建内容的清单：没有界面，没有再训练循环，没有优先级模型。
  • 一段运维手册和一节“再多两天”的内容。

在动手构建任何东西之前，先测量标签不一致度。两位协调员对同一封邮件的标注不同；这个上限决定了实际可达到的准确率，并把“准确率有多高？”变成一个由你掌控的对话。这就是协商式评测技能，也是前沿实验室 FDE 职位描述中被引用最多的硬技能。10方法 →

自评分量表

满分三十分。请诚实打分；低于 20 分在竞争激烈的流程中无法晋级。

评分标准0 分2 分4–5 分
范围备忘录没有描述了构建了什么还说明了没有构建什么，以及原因
单条路径的完整性没有任何东西能端到端运行只有正常路径错误、重试和降级都已处理
验证没有少量测试测试加上一个有明确指标和目标的评测
歧义处理默默猜测列出了假设列出了假设，并在可测量的地方进行了测量
可运维性没有说明如何运行运维手册：最先会坏什么、要监控什么
可辩护性无法解释选择能解释大部分写下三个权衡及被否决的替代方案

成本与权衡：一分钟在哪里最值钱

每一行都是你在五小时内做出的一个决策。时间是从 300 分钟预算中花费的成本，分值是量表上涉及的分数（满分 30 分），原因是评分者会在你的答辩中寻找的理由。

案例时间分值原因
先写范围备忘录30 分钟范围备忘录行：0 或 2 → 4–5。它还为歧义和可辩护性行打下基础它会成为 README 的开头和答辩的前两分钟。写一次，用三次。
在构建任何部分之前先搭好整条路径的骨架45 分钟，全部为桩代码保护单条路径行免于 0 分（“没有任何东西能端到端运行”）如果第五小时进展不顺利，你仍能交出能端到端运行的东西。没有骨架，一个晚期的 bug 可能让你什么都没法运行。
测量标签不一致度属于 30 分钟的范围界定阶段歧义行：“列出了假设”（2 分）→“已测量”（4–5 分）协调员之间的分歧限制了你能达到的准确率。测量它，你就能自己设定目标，而不是被拿 100% 来评判。
API 超时时排队，不要丢弃构建阶段内的几分钟单条路径行：正常路径（2 分）→ 已处理降级（4–5 分）一封因超时丢失的邮件就是一张丢失的客户工单。“排队，不要丢弃”之所以出现在优秀提交清单里，是有原因的。
构建时把权衡写下来每个决策耗时秒级可辩护性行：“能解释大部分”（2）→ 三个书面权衡（4–5）到答辩时你不会记得当初为什么选 SQLite 而不是队列服务。在决策当下写一行备注，是评分标准中最便宜的得分点。
第二个功能（优先级模型、UI）从 135 或 60 分钟里挤出来没有评分行。功能数量权重最低，且常常是负分它会占用某个计分阶段所需的时间。把它列到“再要两天”清单里。
时间紧张时砍掉证明阶段最多省 60 分钟验证行：最多 5 → 0–2这是人们常砍的部分，也是最昂贵的砍法。如果构建超时 45 分钟，证明就只剩 15 分钟。应该砍范围。
两段式的运行手册约占 30 分钟文档撰写中的 10 分钟可运维性行：“如何运行”（2）→ 4–5很少有人写，但读起来显得资深：什么会先出问题、要监控什么。
大幅超出五小时多花 1 小时或更多毫无收益，还可能损失判断分超时会被解读为范围失控，而这正是主要考察点。

看懂“空间”这一列，计划就自然成形。评分标准上几乎每一分都取决于写下来的判断，而不是代码量。一个范围收窄的构建，配上备忘录、实测上限、队列、评测和运行手册，可以拿到远超 20 分。同样五个小时花在三个功能上而以上都没有，可能拿不到 10 分。把超时情形演练一次去感受它：构建花 180 分钟而不是 135 分钟，证明就只剩 15 分钟而不是 60。这刚好够把主路径跑一遍，而不够去故意破坏任何东西。

自我检验

上面的练习规格，加上一些复杂情况。在打开每一题之前先作答。

五小时中的第四小时。唯一那条路径端到端可用，没有测试，优先级模型做了一半。最后 60 分钟你怎么用？

停下优先级模型。把时间用来证明那条路径：用留出集评测，写明指标和目标，然后故意破坏它（杀掉 API、发送垃圾数据、重复发送同一封邮件）。把优先级模型移到“再要两天”清单，并用一句话说明为什么它被延后。验证最多值 5 分。做了一半的功能一文不值。

你在 300 个标注中发现 40 对几乎相同的邮件。其中 10 对的两个标注不一致。这对你的准确率目标意味着什么？

协调员在这 40 对本应获得相同标注的邮件中，有 30 对达成一致，即 75%。以这些标注打分的模型不可能达到 95%，因为标注本身有四分之一的时间互相矛盾。把这个数字写进范围备忘录，并提出一个相对它的目标。或者合并他们混淆的两个类别，并说明这一点。无论哪种方式，你都把准确率问题变成了一个可以回答的问题。

假设发货 API 每 20 次调用就有 1 次超时。每天 400 封邮件，每封都要查询，一个遇错即中断的流水线会损失什么？它应该怎么做？

400 ÷ 20 = 每天 20 封邮件，在无人察觉的情况下丢失。正确做法是：无论如何先对邮件分类，把查询放入重试队列，并将工单标记为“待补引用”。重试必须是幂等的，以消息 ID 为键，这样重试绝不会创建第二个工单。这就是优雅降级，它能把单一路径那一行移到最高档。

在答辩中面试官会问：“你为什么不做一个界面？”最有力的回答是什么？

指出范围备忘录中的“不构建清单”：团队要的是自动化，协调人本来就在邮件中工作，而界面本可以来自验证阶段之后。然后说明如果再多两天你会构建什么。你选择了不构建并写了下来，这算作判断力，而不是遗漏。这就是可辩护性那一行。糟糕的回答是“我没时间了”，这等于说砍掉功能是意外。这可能是事实，但它把与评分标准完全相反的信号交给了评分者。

快问快答

如何通过 FDE 带回家作业？

编码前用书面形式界定范围，尽早搭好整条路径的骨架以便始终有完整可运行的东西，构建一条真正可用且处理了失败情况的窄路径，用五分之一的时间证明它能运行，并写下三个权衡及你否决的备选方案。评分者对范围判断、验证和可辩护性的重视远高于功能数量。

面试带回家作业应该花多长时间？

遵守规定的时间预算——前沿实验室 FDE 职位通常在五小时左右。严重超时不会得到奖励，反而往往表明范围判断不佳。如果时间不够，砍功能而不是砍验证：一个带测试的完整窄构建，得分高于一个没有测试的宽泛构建。

带回家作业的 README 应该包含什么？

范围备忘录（问题、用户、成功定义、你构建了什么、你刻意没有构建什么、假设）、如何运行、三个权衡及被否决的备选方案、已知局限、一份简短的运维手册（说明什么最先出问题、要监控什么），以及一个“再多两天我会做什么”的部分，把缺口转化为明确的权衡。

如何准备带回家作业的答辩或讲解？

在构建过程中就把权衡写下来，因为事后你不会记得。在通话前故意弄坏自己的代码，这样你才知道它会怎么失败。准备一个两分钟的概述，涵盖问题、范围、方法和证据，并准备一个诚实的弱点及你会采取的修复方案。绝不要用“AI 工具做的”来解释某个决策——这个成果是你的。
