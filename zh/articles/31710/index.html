AI Agent 的前沿部署工程

原标题：Forward Deployed Engineering for AI Agents

Reveneau · 2026-09-08 · 约 11 分钟读完

摘要

这篇指南讨论为何企业 AI Agent 项目需要前沿部署工程师：Agent 一旦执行动作，权限、工具范围和升级路径都取决于客户组织，无法从外部设计。文章基于 1,000 份招聘数据分析技能需求，并给出权限继承、工具评估、升级路径设计和属性化评测等具体方法。

要点

  • 1,000 份招聘中 35% 提到 AI Agent，超过 LLM 经验的 31%。
  • 权限是最难部分，应让 Agent 继承所代表用户的权限，而非宽泛服务账号。
  • 每个工具需评估最坏后果，写入类操作通常需人工审核环节。
  • 升级路径的四个设计问题决定 Agent 上线后是否被关停。
  • 评测应检查属性而非固定输出，评测套件是交接的关键产物。

在前沿部署工程师的职位招聘中，AI Agent 出现的比例为 35%，高于通用 LLM 经验的 31% 和检索的 12%。Agent 之所以需要这个角色而非普通的集成工作，是因为 Agent 需要权限、工具访问权和升级路径，而这三者都是客户组织的属性，而非你产品的属性。AWS 将其自身的方法论命名为 Agentic Process Transformation，引导客户从业务流程入手，为 AI Agent 重新设计流程，部署到生产环境，并展示可衡量的成果。

发布于 2026 年 9 月 8 日。编辑报道。

核心要点

  • Agent 在 35% 的招聘信息中被提及，LLM 经验为 31%，RAG 为 12%，因此 Agent 工作是目前最常见的合作内容。
  • 权限是最难的部分，而它是客户组织的属性，因此无法从外部进行设计。
  • 升级路径是设计工作的主体：当 Agent 不确定时会发生什么、由谁审核、以及审核人员看到什么。
  • AWS 的 Agentic Process Transformation 从业务流程而非能力出发，这是正确的顺序。

如今大多数嵌入式合作都涉及 Agent。本页讨论的正是这类合作的具体要求。

为什么 Agent 需要这个角色

回答问题的 Agent 是一次集成。采取行动的 Agent 则是一次组织变革，区别在于工作落在哪里。

一个执行操作的 Agent 需要知道它被允许做什么、代表谁、使用什么数据，以及当它不确定时会发生什么。这四点中的每一点都是客户公司的属性，而非你产品的属性。你无法通过一次需求调研电话来设计它们，因为这些答案尚不存在，也没有人以任何形式记录下来。

招聘数据反映了这一点。在 1,000 条招聘信息中，AI Agent 被提及的比例为 35%，LLM 经验为 31%，检索为 12%。Agent 工作如今已成为最常见的合作内容，而不再是新兴事物。

权限是最难的部分

这是一个令团队感到意外的发现，由于它出现得太过频繁，我们已单独撰文讨论：权限是 AI 功能中最难的部分。

问题在于，业务上对角色的区分方式是软件模型无法体现的。理赔专员和高级理赔专员在实际工作中的权限不同，这种差异体现在习惯中而非权限设置中。代表前者的 Agent 绝不能执行只有后者才能执行的操作，而从来没有人需要把这种区别写下来，因为人们凭直觉就知道。

嵌入式工程师在第一周就能通过尝试用真实数据发布一个小东西发现这一点。而从外部看，它会在第四个月以一场没人预料到的安全审查异议的形式出现。

一个说明这种区别的实际例子。 一家保险公司希望用一个 Agent 起草理赔调整函。初级理赔员可以起草一封信供审核，高级理赔员可以不经审核直接发送，而软件从来不需要知道这种区别，因为总有人知道自己当时扮演的是哪种角色。如果为初级理赔员构建 Agent，那么无论它多么自信，它都必须始终只产出草稿，绝不能直接发送信件。如果为高级理赔员构建，直接发送或许没问题。如果给整个团队授予一个统一的扁平权限级别，这个 Agent 要么拖慢高级理赔员的正常工作速度，要么让初级理赔员发出本不该由他们单独发出的信件。

应当坚持的模式。 Agent 应继承它所服务对象的权限，而不是运行在一个宽泛的服务账号上。Palantir 的 AI FDE 文档 正是针对其自家的 Agent 描述了这一点：所有操作都遵循现有用户权限，上下文从最小化开始，并随用户的选择逐步扩展。宽泛的服务账号是最省事的默认做法，也正是它让一个乐于助人的 Agent 变成一次数据泄露。安全与访问 对此有详细说明。

工具访问权限是一个范围界定决策，而不是一项配置

你赋予 Agent 的每一个工具都是一种能力，也是一种责任。决定给它哪些工具看似技术决策，实则是业务决策，需要客户参与其中。

每个工具问两个问题。如果 Agent 判断错误，这个工具可能造成的最坏后果是什么？以及，在没有人工介入的情况下，这种后果是否可以接受？

对于只读工具，答案通常是肯定的。对于任何会写入数据、转移资金、联系客户或更改他人依赖的记录的操作，答案通常是加一道审核环节。我们关于判断某项功能是否需要人工介入的文章讨论了这种判断。

升级路径就是设计的大部分

对于生产环境中的 Agent，有趣的设计工作不在于正常使用场景，而在于当 Agent 不确定或出错时会发生什么。

什么触发升级。 置信度阈值是最粗糙的版本，而且很少够用。更好的触发条件通常是结构化的：这类操作一律升级，超过这个数值阈值一律升级，这个客户群体一律升级。

由谁接收。 一个有明确指派、且有处理能力的角色。没有人负责的升级队列只会不断积压。

他们看到什么。 足够的上下文以便快速决策，这通常意味着 Agent 的推理过程和底层记录，而不仅仅是它的结论。

最终用户看到什么。 他们是否知道有 Agent 参与，以及他们能对此做什么。

这四点做错是 AI Agent 上线后被停用的最常见原因，而如果没有将要运营它的人参与，这四点中的任何一点都无法回答。

一个构建良好的升级路径的实例。 某支持类 AI Agent 被允许在规定金额以内直接发放退款而无需审核，因为公司判定，在该价值阈值以下，错误退款的成本还不及让人工核查所花费的时间。超过该阈值时，案例会路由到一个指定队列，由特定团队在工作时间内监控，审核人员能看到完整对话以及 AI Agent 给出的推理过程，而不仅仅是它的最终答案。客户会被明确告知，现在有一位真人正在审核他们的请求。上述每一个决策都是关于可接受风险的业务选择，而非技术设置，而且每一项都是由在 AI Agent 上线之前就理解业务的人做出的。

AWS 的框架，这才是正确的顺序

AWS 的合作伙伴计划提出了一套方法论，即 Agentic Process Transformation，它引导客户从业务流程入手，为 AI Agent 重新设计流程，将其部署到生产环境，并展示可衡量的成果。

从业务流程而非从能力出发，才是正确的顺序，而这与大多数 AI Agent 项目的做法恰恰相反。常见的失败方式是先看模型能做什么，再寻找可以应用它的地方，结果做出一个能力很强却挂在一个没人需要改造的流程上的系统。

Anthropic 为该职位发布的招聘信息中明确提到，需要交付可用于生产环境的技术产物，例如 MCP 服务器和 AI Agent，这告诉你这项工作如今产出的具体交付物是什么。

验证，AI Agent 让它变得更难

AI Agent 能产生的输出范围比普通功能更广，因此检查方式必须有所不同。

用一组固定的预期输出来测试 AI Agent 很快就会失败，因为可接受的答案有很多。有效的方法是评估属性：它是否始终在权限范围内行事，是否在应该升级时进行了升级，是否避免了绝不能执行的操作，结果是否在容差范围内。

这些检查来自规格说明，在 AI Agent 存在之前就已确定，并且由被测模型以外的某种东西来评分。评测驱动开发 就是这套方法，生产环境中的 AI Agent 涵盖了针对 AI Agent 的具体版本，而绝不让模型给自己的工作打分 则是让评分有意义的原则。

一个属性检查的实际示例。属性检查不是问“Agent 给出的退款金额是否与我们的测试用例相同”，而是问“Agent 是否曾在超过阈值的情况下发放退款而没有转交人工审核”，并且要在测试套件能生成的每一个场景上运行，包括没人想到要手动编写的场景。第一种检查在 Agent 的措辞因合理原因发生变化时就会失效。第二种检查无论措辞如何变化都能持续有效，因为它检查的是真正重要的属性，而不是某个碰巧正确过一次的具体输出。

这同时也是交接产物。接手一个 Agent 的客户团队更需要评测套件，而不是代码，因为代码会变，而评测套件才能告诉他们这次变更是否安全。

在启动 Agent 项目之前应该问什么

Agent 代表谁行事，你们的权限模型今天是否体现了这一区别？它可能执行的最坏动作是什么，不经审核是否可以接受？升级上报由谁接收，他们是否有处理能力？我们正在改变的是哪个业务流程，而不是我们在部署什么能力？

四个问题。如果答案尚不存在，那这就是工作的第一阶段，而不是推迟工作的理由。

回答这些问题恰恰是那种必须在客户内部、与日常运营 Agent 的人一起完成的工作，这正是为什么面向企业 AI 的前沿部署工程将 Agent 项目视为同一底层问题的一个特定案例，而不是一个独立问题。

最适合

  • 在企业内部规划 Agent 部署的范围
  • 决定应给 Agent 哪些工具，哪些需要审核步骤
  • 在 Agent 上线生产环境之前设计升级上报路径

不适合的情况

  • Agent 是只读且内部使用的，这种情况下其中大部分都是额外负担

决策前请确认

  • 确认 Agent 继承的是具名用户的权限，而不是服务账号
  • 对每个工具，说明最坏结果是什么，以及不经人工处理是否可以接受
  • 指定升级上报的接收人，并确认他们有处理能力
  • 从正在改变的业务流程出发，而不是从正在部署的能力出发

常见问题

为什么 AI Agent 需要嵌入式工程师，而不是普通的集成工作？

因为一个会执行动作的 Agent 需要知道它可以做什么、代表谁、使用什么数据，以及当它不确定时会发生什么。这四点都是客户组织的属性，而不是你们产品的属性，而且在有人去建立它们之前，这些都不存在书面形式。

在企业中部署 Agent 最难的部分是什么？

权限。业务上对不同角色的区别对待，软件并未建模，这种区别体现在习惯中而非权限设置里。代表初级角色行事的 AI Agent 绝不能做只有高级角色才能做的事，而此前从没有人需要把这一点写下来，因为人们凭直觉就知道。

应该如何配置 AI Agent 的权限？

它应该继承其所代表人员的权限，而不是运行在一个权限宽泛的服务账号上。Palantir 自己的 Agent 文档描述了这种模式：操作遵循现有用户权限，上下文从最小范围开始，随用户的选择逐步扩展。宽泛的服务账号是最省事的默认做法，也是主要的泄露风险。

如何决定给 AI Agent 哪些工具？

每个工具问两个问题。如果 Agent 判断错误，最坏会造成什么后果？在没有人工介入的情况下，这种后果是否可以接受？只读工具通常可以通过。任何会写入数据、转移资金、联系客户或更改关键记录的工具，通常都需要一个审核环节。

是什么导致 AI Agent 在上线后被停用？

通常是升级路径出了问题。有四件事必须做对：什么触发升级、谁接收升级、他们看到什么、最终用户看到什么。基于操作类型或金额阈值等结构性触发条件，比置信度分数更可靠，而无人负责的升级队列只会不断积压。

如何测试 AI Agent？

不能对照固定的预期输出，因为很多答案都是可以接受的。应该评估属性：它是否始终在权限范围内行事，该升级时是否升级了，是否避免了禁止的操作，结果是否在容差范围内。这些检查标准在 Agent 存在之前就来自规格说明，并且独立于模型进行评分。

面向企业级 AI 的前沿部署工程

企业 AI 试点失败有三个原因：数据从未经过审计、成功指标在工作开始前无人定义、用户被塞给了一个他们从未参与设计的工作流程。这三个问题都无法在楼外解决，这正是嵌入式工程在此场景下的全部意义所在。MIT NANDA 在 2025 年 7 月报告称，95% 的生成式 AI 试点没有产生可衡量的损益影响，该报告基于 52 次高管访谈、153 份领导者问卷调查和 300 个公开部署案例。它所描述的失败是组织性的，而非技术性的。

金融服务领域的前沿部署工程

金融服务是该角色最大的客户群体：在指明目标行业的职位招聘中占 24%。决定每个项目如何开展的约束条件是审计追踪。在大多数软件中，审计日志是可以后期添加的功能；而在这里，它是系统从第一个数据模型决策起就必须具备的属性，因为监管者提出的问题不是答案是否正确，而是你能否展示答案是如何得出的。这一要求改变了驻场工程师在第一周要构建的东西。

政府与国防领域的前沿部署工程

政府与国防是这一模式的发源地，在指明目标行业的职位招聘中仍占 18%。三个约束条件决定每个项目如何开展，而且都不是技术性的：人员安全审查，它决定了谁有资格参与；与互联网隔离的环境，它去掉了大多数团队默认拥有的工具；以及漫长的采购周期，长到合同尚未结束技术就已更新换代。针对这三点的工程应对方式是相同的，即为约束而设计，而不是绕开它。

医疗健康领域的前沿部署工程

在指明目标行业的前沿部署工程师职位招聘中，医疗健康占 17%。两个约束条件决定每个项目。数据通常不能离开机构，这意味着工作必须在他们的基础设施内、按他们的条件进行。而且临床工作流程不能中断，这意味着每次部署都是对一个持续运行、后果真实的流程的改动。这两点共同排除了软件团队通常依赖的两样东西：把数据带回去处理，以及维护窗口。
