Ramp 如何开展前沿部署工程

原标题：How Forward Deployed Engineering is done at Ramp

AI Engineer · 2026-07-28 · 约 8 分钟读完

摘要

Ramp 工程总监 Leo Mehr 在 AI Engineer World's Fair 2026 分享其前沿部署工程实践：FDE 隶属工程团队，核心职责是把企业客户的阻塞需求转化为正确的产品决策，再用 AI Agent 加速需求澄清与规格编写。

要点

  • FDE 隶属工程部门，约 30 人团队含 API 与 AI 服务，目标是赢得大企业客户。
  • “持续界定范围”原则：先追问需求动机、真实用户、替代方案，再决定是否构建。
  • 案例：团队为客户新学 iOS 和 Android 开发并实现功能，事后才发现客户只用 iOS。
  • FDE Intake Agent 将请求澄清的响应时间从数小时缩短到秒级，估算节省约 20% 界定范围时间。
  • 未来 FDE 工作将转向 Agent 运维、输出评测与上下文交付，但界定范围与扩容须并重。

Ramp 如何实践前沿部署工程

Ramp 的前沿部署工程师将企业客户的阻碍转化为产品工作，然后利用 AI Agent 加速那些让这些工作值得构建的追问与探索。

前沿部署工程师应该构建什么？

当前沿部署工程的职责是帮助企业客户取得成功时，它究竟负责什么？在这场演讲时，Leo Mehr 自称是 Ramp 的工程总监。他加入时，FDE 团队只有两名工程师；此后他的组织已发展到约 30 名工程师，涵盖 FDE、开发者 API 和 AI 服务。这个更大的组织很重要：这些人数并非仅属于 FDE 团队。

Ramp 的答案始于 FDE 的定位。它隶属于工程部门，使命是通过让核心产品和新推出的 agentic 功能在最大的企业客户那里良好运行，帮助 Ramp 赢得更高端的市场。Mehr 反对那种认为 FDE 只是一系列技术市场推广岗位中最终晋升一站的看法。这份工作要对产品本身承担责任。

在打开 SAP API 文档之前

对每个请求都说“是”并不等于帮助客户。Mehr 用一匹腿上绑了火箭的马来说明这种区别：不断累积的改进需求可能最终产出一个与精心设计的载具截然不同的东西。前沿部署工程师应该在交付优质软件的同时寻找帮助客户的方法。客户成功要求判断什么是正确的事情，而不是仅仅同意去构建它。

打开完整源帧

设想 Ramp 的一个常见场景：周五晚上，一位企业销售代表说，只有团队构建一个 SAP S/4HANA 集成，一笔战略交易才能成交。工程师的本能反应是去找 SAP API 文档，开始研究如何实现。而训练有素的 FDE 会先停下来，质疑这个前提。

范围界定的对话会依次探讨几个问题：

  • 紧迫感的来源是什么？ 季度末的销售指标可能带来并非源自客户的压力。
  • 谁将使用这个集成？ 找出实际的用户以及他们需要完成的工作。
  • 已经存在哪些替代方案？ 检查现有的变通办法，以及临时的手动流程能否解决当前的问题。
  • 客户能否自行建立连接？ 拥有技术资源的客户也许可以直接使用 Ramp Developer API，而无需 Ramp 来构建集成。
  • 还有谁会受益？ 在决定可复用能力的范围之前，先考察现有客户和潜在客户管道。

这些问题把对某个特定实现的需求转化为产品决策的背景信息。结果可能仍然是一个集成，但团队现在能够解释为什么这个集成是值得的投资。

客户无法使用的 Android 功能

一个早期的移动端报销项目让“缺乏上下文”的代价变得具体。一家大型企业客户需要在移动端使用报销功能，但 Ramp 的移动团队已经超负荷。两位 FDE 工程师挺身而出，学习了 iOS 和 Android 开发，并花了大约两周时间在两个平台上构建了该功能。团队为突破了实现瓶颈而感到兴奋。

随后他们向客户征求 Android 测试用户。客户解释说，公司规定所有员工必须使用 iOS 设备。直到两个版本都完成之后，团队才发现 Android 的工作对提出需求的客户来说毫无必要。

这个错误并非执行上的失败，而是在执行之前未能验证一个基本假设。即便是像移动端支持这样看似简单直接的需求，也需要询问客户实际使用的是哪些设备。工程热情和学习新平台的能力，无法挽回已经花在解决错误问题上的时间。

将工作扩展到实现之外

仅仅做好范围界定并不能应对模型能力的不断变化。Mehr 认为，FDE 必须持续重新审视自己的哪些知识工作可以由模型和 AI Agent 完成。用 token 实现规模化意味着把这个问题应用到整个工作流程中，而不是把 AI 辅助视为从开始写代码时才介入的东西。

生命周期提供了一个有用的分解方式：

  • 收集上下文。
  • 界定需求范围。
  • 编写规格说明。
  • 实现功能。

每个阶段都是 AI Agent 工作的候选对象。替换整个生命周期是一个目标，而非这个演示中已完成的系统；将其拆分为多个阶段，使得逐个改进每个部分成为可能。

会提出下一个问题的 AI Agent

Ramp 的内部

FDE Requests

Slack 频道会收到来自客户经理、解决方案人员和销售代表的许多客户及潜在客户遇到的阻碍问题。屏幕上的示例是来自客户成功经理 Greg 的一份提交。它通过 Notion 工作流提交；在 Notion 中打开该请求即可查看其详情。

这些详情差异很大。有些提交会详细描述客户的情况；有些则只有一行字，要求进行 SAP 集成。以前，FDE 会阅读请求，了解产品已支持的功能，然后与客户反复沟通以确定实际需求。耗时的工作恰恰是提问环节——正是这些提问避免了演讲前半部分提到的那些错误。

Ramp 的第一个版本使用 Notion agents 来接收请求并提出几个问题。它不需要自动化整个生命周期就能发挥作用。几周后，Mehr 报告说，这个收集工作流中的回复延迟已从数小时或数天降至数秒。代表们可以立即开始与 AI Agent 互动，而不必等待工程师的初步回复。

后来的迭代版本增加了一个友好的企鹅形象，并与提交者进行多轮问答，直到 AI Agent 认为该请求已准备好生成规格说明。截图显示了

FDE Intake Agent

询问客户期望的结果、当前工作流以及可用数据。重要的进展是从少量初始问题发展为一种交流，能够在工程师接手之前完善请求。

从澄清后的请求到可构建的规格说明

收集助手推进了生命周期的第一阶段。在另一端，Mehr 表示，前沿模型可以根据格式良好的规格说明一次性生成中等规模的功能，使实现变得更容易。这是他的能力评估；演讲并未定义功能基准或给出成功率。

困难的中段依然存在：如何将收集到的上下文和初始需求转化为一份足以驱动实现工作的规格说明。Mehr 将这项工作描述为尚未成形且充满挑战，并将其确定为未来进一步投入的重点。Ramp 提出的 Agent 工厂将把各阶段的 Agent 连接起来，但现有的需求录入助手并不能证明从需求到产品的整条路径已经实现自动化。

上下文与评测成为工程工作

从这次演讲展望未来六到十二个月，Mehr 预计更多 FDE 的工作将转向这条流水线中的应用 AI 问题。有三项职责尤为突出：

  • Agent 运维： 保持驱动各阶段的运行框架平稳运转。
  • 输出评测： 使用评测、评分标准和人工反馈来判断每个阶段输出的质量。
  • 上下文交付： 确保每次 LLM 调用都能获得其决策所需的信息。

这是对随着团队构建该系统，这一角色可能如何发展的预测。

上下文交付尤其困难，因为产品知识并不局限于文档之中。历史决策以及产品经理头脑中积累的理解，可能会改变一份优秀规格说明应有的样子。Notion 文档、知识库和帮助文章只能捕捉其中的一部分理解。Skills、记忆和工具或许能有所帮助，但 Mehr 并没有为它们规定具体的实现方式。

FDE 对最终输出的品味和判断仍负有责任。 将工作交给 Agent 改变的是工程师产出结果的方式；它并没有免除他们判断结果是否合格的义务。

更大的产能仍需要方向

Agent 工厂继承的是其需求界定工作的质量。如果系统始终没有弄清客户需要什么，更快的执行只会产出更多方向错误的成果——也就是 Mehr 所说的“token 狂灌垃圾炮”。火箭动力马的问题在自动化之后依然存在；只是制造起来更容易了。

相反的失败同样值得重视。在 Mehr 看来，一个需求界定出色却不投资 Agent 的团队，有被竞争对手超越的风险。因此，需求界定与 token 驱动的产能必须共同发展：前者确保工作始终指向有用的结果，后者则扩大团队交付成果的能力。FDE 的未来两者缺一不可。
