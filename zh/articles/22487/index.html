Ramp 的 FDE：先定框架，再把接待工作交给 AI Agent

原标题：FDE chez Ramp : cadrer, puis confier l'accueil aux agents

SFEIR AI · 2026-11-10 · 约 4 分钟读完

摘要

本文评述 Ramp 工程总监 Leo Mehr 在 AI Engineer World's Fair 2026 的 14 分钟演讲，总结其两年半 FDE 实践的两条原则：先做好需求框定，再用 AI Agent 扩大规模。Ramp 的 FDE 团队从两人发展到约三十人，隶属工程部门，服务大客户。文中举例说明框定不足导致浪费（为客户开发了 Android 报销功能，结果客户全员用 iPhone），并介绍用 Notion Agent 搭建的接待 Agent，将首次响应从数小时缩短到数秒，估计节省约 20% 的框定时间。作者认为最难的是把澄清后的需求转化为可执行的规格，并指出该接待 Agent 可直接移植到售前场景。

要点

  • Ramp 的 FDE 团队从两人增至约三十人，隶属工程部门。
  • 原则一：先框定需求，避免为紧急但不必要的需求浪费工时。
  • 原则二：把需求生命周期各环节交给 AI Agent 处理。
  • 接待 Agent 使首次响应从数小时缩至数秒，节省约 20% 框定时间。
  • 作者认为需求转规格是当前 Agent 最薄弱、咨询价值最高的环节。

一个周五晚上，Ramp 的一位销售人员要求做 SAP S/4HANA 集成：没有它，一个战略客户就不会签约（约 3:03 处）。Leo Mehr 讲述说，这样的场景以这样或那样的形式反复上演，它概括了他在 Ramp 两年半 前沿部署工程 经历中总结出的两个原则中的第一个。他宣布了两个原则，不多不少，并在十四分钟内兑现承诺。他刚加入时，FDE 团队只有两名工程师；演讲时，他领导着约三十名工程师，分布在 FDE、开发者 API 以及新的 AI 服务业务中。在 Ramp，FDE 隶属于工程部门，通过为客户运行产品及其新的 agentic 功能，帮助公司赢得大客户。Leo Mehr 顺便驳斥了把 FDE 视为技术售前岗位终极形态的梗。

始终界定范围

用他的比喻来说，对每一个需求都说“是”，就像给马的四条腿绑上火箭，而不是像在旧金山街头行驶的 Waymo（约 2:02 处）。面对那位周五晚上的销售人员，他建议停下来先问几个问题。是谁在催促：是客户，还是一个在追赶季度指标的销售？谁会使用这个集成？有没有变通办法，比如临时的手动方案？客户是否有能调用 Ramp API 的开发者？最重要的是，还有哪些潜在客户或客户能从中受益？

他还讲了一个失败案例（约 5:04 处）。一个大客户想要移动端报销功能；移动团队忙不过来，于是两名 FDE 学了 iOS 和 Android，几周内就交付了。当要 Android 测试用户名单时，团队才得知该客户给所有员工配的都是 iPhone。一个界定范围的问题本可以省去一半的工作。

用 token 实现规模化

第二个原则是将 FDE 需求的生命周期拆分（收集上下文、框定范围、撰写规格说明、实现），并把每个阶段交给 AI Agent（约 7:05）。Ramp 从需求受理开始。客户经理、客户成功团队和销售人员通过一个 Notion 表单，把他们的阻塞问题发布到一个专门的 Slack 频道，质量参差不齐：有些人写得很详细，有些人只写一行。第一版用 Notion 的 Agent 构建，只会问两三个问题。首次响应时间从数小时或数天缩短到几秒钟，销售人员开始与 Agent 对话。当前版本以一只小企鹅的形象呈现，会进行多轮提问，直到能够撰写出一份规格说明。Leo Mehr 估计节省了大约 20% 的框定时间——这个数字他自己说出来时也有些犹豫。

他把难点定位在链条的中段（约 10:10）。受理 Agent 负责澄清需求，前沿模型能够根据一份好的规格说明一次性实现一个中等规模的功能；而在两者之间，从一份已澄清的需求到一份可执行的规格说明，工具仍然很匮乏。他预计，六到十二个月后，Ramp 的 FDE 将把时间花在应用 AI 问题上：一个运转顺畅的 harness、带评分表和人工反馈的评测，尤其是为 Agent 提供恰当的上下文——包括产品经理脑子里有、但任何 Notion 页面里都没有的内容。对结果的品味和判断仍然是 FDE 的事。

两个原则合在一起

结论把两者联系起来（约 12:11）。一个没有框定范围的 Agent 工厂会变成一台“token maxing slop cannon”：一门烧着 token 喷射劣质内容的大炮。一支擅长框定范围却不投资 Agent 的专家团队，将被那些与 Agent 一同成长起来的竞争对手超越。

对一家 IT 服务公司而言

Ramp 的受理 Agent 可以原封不动地移植到售前环节：一个在需求到达架构师案头之前提出框定性问题的 Agent。关于链条中段的诊断指出了顾问的价值所在：把一份已澄清的需求转化为可执行的规格说明——这正是当今 Agent 表现最差的环节。

评价

原创性：3/5。 先框定再构建并不新鲜。其价值在于两个原则的结合，以及“slop 大炮”这个形象，它点出了许多团队已经在经历的风险。

信息质量：4/5。 十四分钟没有废话，有坦诚的例子（那个无用的 Android 应用），有可复制的实践（受理 Agent）。但这个演讲对第一步之后的工具着墨不多，20% 也只是一个估计。再多花十分钟讲受理 Agent 也不为过。

值得前台接待人员观看的内容：7:05 到 10:10，如果你需要处理客户请求流。这是整个系列中性价比最高的一段。
