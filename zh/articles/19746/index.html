API 契约优先设计：FDE 选 REST 还是 GraphQL

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

这篇指南面向 FDE，主张在客户现场采用契约优先的 API 设计：先写 OpenAPI 或 GraphQL schema，再写实现代码。文章以货运风险评分项目为例，说明 API 是客户团队赖以构建的契约，并给出资源命名、幂等写入、版本策略等具体做法，最后附求职展示建议。

要点

  • 先定访问级别（公开、合作伙伴或私有），再选 REST 或 GraphQL。
  • REST 适合固定操作的 ERP 集成，GraphQL 适合多前端按需取数。
  • URI 用业务名词，写操作尽量用幂等的 PUT，避免重试产生重复记录。
  • 新增字段一般安全，破坏性变更需选定版本策略并写入交接文档。
  • 求职简历应具体描述契约编写与幂等端点设计，而非泛泛的“构建 REST API”。

客户 ERP 团队会在你定义的每个字段上写代码，所以先定谁能调用，再按调用方选 REST 或 GraphQL。

要点速览

  • 对客户的系统来说，API 就是契约。先写好契约（OpenAPI 或 GraphQL schema），再写代码。
  • 不要让 API 照搬数据库结构。用业务名词命名资源，凡是可能被重试的写操作都要做成幂等。
  • 新增字段很少会影响客户端。破坏性变更无法避免时，选定一种版本策略，并写进交接文档。

设想你在客户现场的第三周。货运风险评分模型已经跑起来，演示也很顺利。这时，客户的 ERP 负责人问了三个问题：他们的系统调用哪里，返回什么数据，你这边有变动时怎么通知他们？

这三个问题决定了你离开后这套方案的命运。模型可以换成别的，但 ERP 团队已经写好代码去调用的那些端点，很难再改。

你的任务是把这层 API 设计好，让客户团队能自己集成、运维和升级，不必再回头找你。

API 是契约，不是实现细节

IBM 把 API 定义为一种契约：让一个软件访问另一个软件提供的数据或调用其功能。对前线部署工程师（FDE）来说，“契约”二字要按字面理解。响应里的每个字段都是一项承诺，对面的团队会在它上面构建业务逻辑。

所以第一个问题不是用 REST 还是 GraphQL，而是谁有权调用这个 API。IBM 按访问级别给 API 分类：公开 API 完全向互联网开放，合作伙伴 API 和私有 API 则限制使用者。

一个只服务内部 ERP 和几家货运合作伙伴的风险评分方案，几乎肯定不需要公开。一开始就把这件事定下来，后面能省掉和安全团队开的很多会。

REST 还是 GraphQL：按调用方来选

据 IBM 介绍，REST 是当今最流行的 Web API 架构；SOAP 则是基于 XML 的消息协议，对消息结构和传输有严格标准。如果客户的 ERP 只支持 SOAP，那就只能用 SOAP；但对新设计来说，实际的选择通常是 REST 或 GraphQL。

GraphQL 官方文档的描述是：在强类型系统之上构建灵活、无需版本号的 API。schema 定义数据的形状，客户端只请求自己需要的字段。

有个细节容易忽略：GraphQL 规范刻意不涉及网络、授权和分页，这三样都得由你的团队自己设计。

REST

  • 最流行的 Web API 架构，ERP 团队几乎肯定熟悉
  • 资源用名词命名，行为由 HTTP 方法决定
  • 破坏性变更靠版本处理：URI、查询字符串、请求头或媒体类型

GraphQL

  • 客户端按需获取字段，适合多个数据需求各异的界面
  • schema 随时间演进，而不是打版本号
  • 授权、分页和网络需自行设计，规范并未定义

如果 ERP 集成团队只需要几个固定操作，交接时选 REST 通常风险更低。如果主要使用方是多个前端、各自需要不同的数据切片，GraphQL 更合适。

完整示例：货运风险 API

回到这个假设的物流客户。团队的初稿通常是这样的：一个端点

POST /getRiskScore

，返回

{"shp_id": 8812, "rsk_v2": 0.83, "flg_manual": 1}

。它能用，但有三个错误，会在交接后惹麻烦。

第一，URI 里用了动词。Microsoft 的指南建议用名词（资源）命名 URI，而不是动词（对资源的操作）。

第二，

rsk_v2

和

flg_manual

这些名字直接取自表的列名。Microsoft 建议不要让 API 照搬数据库的内部结构。道理很简单：哪天你改了列名，所有客户端都会跟着出错。

第三个最难发现。ERP 发送货运数据，遇到超时后自动重试。如果写入端点用的是 POST，每次重试都可能多创建一条记录。

Microsoft 指出，PUT 必须是幂等的：同一请求发送多次，只修改一个资源，且值相同。POST 和 PATCH 没有这个保证。

修订版在写代码之前先写成契约。Microsoft 称之为契约优先（contract-first）：先设计契约，也就是接口，再写实现它的代码。契约的第一部分声明写操作：

openapi: 3.0.3
info:
  title: Shipment Risk API
  version: 1.0.0
paths:
  /v1/shipments/{shipmentId}:
    put:
      summary: 创建或更新货运记录（幂等，可安全重试）

下一部分同样位于

paths

下，描述读操作以及 ERP 将收到的响应结构：

  /v1/shipments/{shipmentId}/risk-assessment:
    get:
      summary: 获取最新的风险评估
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                required: [shipmentId, riskLevel, score]
                properties:
                  shipmentId: { type: string }
                  riskLevel: { type: string, enum: [low, medium, high] }
                  score: { type: number, minimum: 0, maximum: 1 }
                  reasons: { type: array, items: { type: string } }

注意变化在哪里。资源现在是

shipments

和

risk-assessment

，ERP 那边任何人一看就懂。写操作使用 PUT，以 ERP 提供的

shipmentId

为键，所以无论请求重试多少次，都只有一条货运记录。

在内部，映射层把

rsk_v2

转换成

score

，这样你可以改数据库 schema，契约保持不变。

什么时候需要版本？

六个月后，客户想加一个

estimatedDelayHours

字段。新增字段通常不会影响客户端，因为旧代码会直接忽略不认识的字段。相反，把

riskLevel

从字符串改成数字，或者删掉

reasons

，就属于破坏性变更。

针对破坏性变更，Microsoft 列出了四种策略：把版本放在 URI、查询字符串、请求头或媒体类型中。Microsoft 认为

/v1/

这样的 URI 版本是简单的做法，但也提醒：API 经过多轮变更、服务端要同时维护多个版本时，这种方式会变得难以管理。

GraphQL 走的是另一条路：类型系统随时间演进，不打版本号。实际做法是新增字段、保留旧字段，确认没有客户端再使用某个旧字段后才把它删掉。

无论选 REST 还是 GraphQL，这条规则都要写进交接文档，让客户团队知道字段何时会被删除，以及会如何提前通知他们。

下一个项目可以照做的流程

先列出客户在交流中使用的业务名词，比如货运、订单、评估，这些就是候选资源。然后针对每个写操作，问集成团队：超时后客户端会不会重试？

如果会，就把这个操作设计成基于客户端提供 ID 的 PUT。必须保留 POST 的地方，常见做法是要求客户端在请求头里带上幂等键，服务端据此识别重复请求，返回先前的结果，而不是新建记录。

接着编写 OpenAPI 契约或 GraphQL schema，和真正调用 API 的人一起评审。如果选了 GraphQL，要把授权和分页也拿到评审里讨论，因为规范不会替你处理。双方达成一致后，再写映射层和处理代码。

最常见的错误都源于图省事：在响应里直接返回 ORM 实体；所有写操作都用 POST；改了字段类型却不升版本；合作伙伴级访问就够用，却把 API 设成公开；以为 GraphQL 自带授权而选了它。

这些做法在写代码时各省一个下午，交接后却要让客户付出几周的代价。

求职时如何展示这项能力

阅读 FDE 职位描述时，留意“integration”“API design”“customer-facing technical delivery”这类说法。它们说明这个岗位用得上的正是这项能力。

简历上与其写“构建了 REST API”，不如写得具体些：编写契约优先的 OpenAPI 规范，并与合作伙伴的集成团队共同评审；设计幂等的写入端点，让客户端可以安全重试。

面试前，准备好一个场景题的回答：客户需要修改一个被多个系统调用的字段，你怎么办？有说服力的回答，起点是一份从第一天就写下来的契约。
