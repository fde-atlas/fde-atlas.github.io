超越 FDE 热潮：Palantir 的本体作为 AI Agent 的操作层

原标题：Beyond FDE Hype: Palantir's Ontology as the AI Agent Operating Layer

BestHub · 2026-10-22 · 约 8 分钟读完

摘要

文章剖析前沿部署工程师热潮，指出多数公司只模仿了派驻现场的形式，却缺少Palantir的核心方法论：将现场经验沉淀为Ontology。Ontology是组织运营的数字孪生，由语义层（定义对象与关系）、动作层（定义可执行操作）、治理层（定义权限与审计）构成，通过提交即事务、写回源系统、审计日志让业务决策成为可复用的数据资产。AIP的AI Agent直接构建在Ontology之上，Ontology MCP将对象与动作暴露为外部Agent可调用的工具。文章给出银行案例的18-36个月四阶段落地路径，并对比dbt语义层与Neo4j等替代方案的不足，强调有治理的写入能力目前是Ontology独有。

本文分析了日益兴起的 FDE(前沿部署工程师)趋势,并指出 Palantir 的本体(Ontology)——一个由语义层、行动层和治理层组成的组织运营三层级数字孪生——是实现可靠 AI Agent 部署的关键基础设施,并将其与传统数据平台进行对比,勾勒出一条多年的采用路径。

AI 逐步解析

01 熟悉的 FDE 模式:驻场历史、平台闭环与三个问题

FDE(前沿部署工程师)这一概念在 AI 圈迅速升温,据报道,OpenAI、AWS 和微软等公司 2026 年相关岗位的需求同比增长了 729%。FDE 起源于 Palantir(内部称为 Delta),前沿部署工程师会深入客户组织内部,在真实环境中编写生产代码,在合同签订后接手部署工作,并一直留驻到系统在生产环境中稳定运行。与在签约时即告结束的售前工作不同,FDE 负责整个部署生命周期。Palantir 将 Delta 置于业务团队之下:产品工程师负责“为众多客户打造一种能力”,而 Delta 则“为一个客户交付多种能力”。

作者指出,这种模式与二十年前的企业软件交付方式如出一辙:驻场技术支持、售前售后一体化,以及驻扎在客户现场以捕捉定制需求的开发人员。这一模式并不新鲜,但 Palantir 的理论框架赋予了它独特的价值。FDE 不是高端外包,而是产品研发的前向延伸。在现场反复验证的能力会被泛化并吸收进平台,成为可复用的产品功能——Foundry 正是这一反馈闭环的产物。竞争对手往往只模仿了“派工程师驻场”这一部分,却遗漏了“现场洞察反哺平台”这一关键机制。

从历史上看,驻场团队从未系统性地回答过三个问题:沉淀什么、产出什么、遵循什么标准。Palantir 将这些答案固化成了一个名为本体(Ontology)的体系。

02 什么是本体:组织的数字孪生

本体（Ontology）是 Palantir 知识体系的核心，通常译作“本体”。Foundry 文档将其定义为一个“操作层”，位于集成数据集、虚拟表和模型之上，结合了语义元素（对象、属性、链接）和动作元素（操作、函数、动态安全）。关键区别在于：Ontology 既不是数据目录，也不是数据库模式。以订单为例，数据库存储的是一张包含字段的表（模式）；而 Ontology 将订单表示为一个对象，具有属性（金额、状态、收货地址）、与其他对象的链接（客户、生产线）、操作（重新分配、取消、加急）以及权限约束（谁能看到成本价、谁能更改状态）。数据库回答的是“数据长什么样”；Ontology 回答的是“业务如何运转”——它是组织运营模式的数字孪生。

03 三层结构：从“存在什么”到“能做什么”再到“谁能做”

数字孪生由三层构成：语义层回答“存在什么”，动作层回答“能做什么”，治理层回答“谁能做”。

语义层定义业务世界中的对象。订单、设备、患者是对象类型；金额、状态、序列号是属性；订单属于客户、设备安装在生产线上是链接。一个被低估的机制是接口（Interfaces）：当多个对象类型共享相同的结构和行为时，接口描述它们的共同形态，使下游使用者可以依赖接口而非具体类型。语义层最大的价值在于与数据源解耦：ERP 的

asset_number

和 IoT 平台的

device_ref

都映射到同一个

Asset

对象，因此应用开发者无需关心数据来自哪个系统。

动作层定义可以对对象做什么。传统数据平台只建模名词，忽略动词；重新分配订单或审批请求这类行为散落在应用代码中，没有统一的名称或约束。Ontology 同样对“决策”进行建模：每个动作类型都是明确定义的操作。动作层的存在，正是“数据模型”与“业务系统”的分界线。

治理层回答谁能做什么。权限直接作用于对象类型和属性，独立于底层数据源的权限：同一个对象可能对某些用户显示成本价，而对另一些用户只显示售价。其他功能还包括分类标记（适用于国防等受监管行业）、Git 风格的分支与版本管理，以及完整的血缘追踪。三者结合，语义层让业务显性化，动作层让业务可操作，治理层让操作可控。

04 五大构件与回写闭环：Ontology 如何活起来

在组件层面，Ontology 的基本材料有五种：对象类型、属性（包括跨类型可复用的共享属性）、链接类型、动作类型和函数。要让这张“只读地图”动起来，需要动作类型的执行机制，其核心有三点：

提交即事务。一次动作类型提交即完成对对象、属性和链接的全部修改；校验规则和业务约束在提交时强制执行。无论请求来自哪个应用，都必须经过同一条校验路径——不存在绕行通道；这不是前端里的表单逻辑。

副作用与回写。提交成功后可触发通知、审计和下游系统调用，并通过 Writeback 将结果安全地回写到 ERP、CRM、MES 等源系统。业务用户直接在系统中做决策，同时源数据保持干净。

审计留痕。每次提交自动记录日志；决策本身成为数据资产：一个人的判断成为下一个人的输入，实现经验的复利积累。

工程实现将模型拆分为三个解耦的服务：OMS 管理 schema（对象、链接、动作类型的定义与版本）；OSS 负责读取（高吞吐查询层）；Funnel 负责写入（所有写入都先经过治理策略和 schema 校验再持久化）。一个供应链场景可以说明完整闭环：某配送中心发生火灾，通过 IoT 数据更新

Facility

对象；影响沿链接传播到采购订单和库存；物流经理在 UI 中执行一个

Initiate_Reorder

动作；决策通过校验并回写到底层 ERP——从感知到行动，全部发生在同一张图上。

05 Ontology 与 AI：Agent 的操作层

动作层是 AI Agent 推理与行动的基础。AIP（Palantir 的 AI 平台）直接构建在 Ontology 之上。要让一个 Agent 承担工作，必须先有人定义它可以讨论哪些对象、可以读取哪些数据、可以执行哪些动作、必须遵守哪些权限、必须留下哪些证据——这正是 FDE 在现场工作的沉淀。

一个值得注意的接口是 Ontology MCP：将选定的对象类型、动作类型和查询函数暴露为 MCP 工具，允许外部 Agent 直接调用。由此，Ontology 同时扮演三种角色：企业状态的语义模型、Agent 的工具与动作目录、治理与审计接口——在同一层中定义并记录 Agent 能做什么、做过什么。

06 落地路径与成本：哪些该借鉴，哪些不该照搬

Ontology 不是一次性的建模项目，而是一个长周期的迭代过程。某银行的案例展示了四个阶段：第 3–6 个月——数据接入和首批核心对象（客户、账户、交易）；第 6–12 个月——丰富关联、定义首批动作和函数、引入动态权限；第 9–18 个月——构建对象感知的应用和首批 Agent，实现对核心系统的双向回写；第 18–36 个月——在全行推广，并迈向生态系统集成。这一节奏与三层结构相呼应：先语义，再动作，最后 Agent。

该系统捆绑在 Foundry 平台内，要求全面采用——这是最大的门槛。与其他方案相比：dbt 风格的语义层只覆盖指标且只读；图数据库（如 Neo4j）可以建模实体关系，但通常需要把数据迁移到图存储中，同样缺乏受治理的写入通道。将校验、副作用、审计和属性级权限统一在一个系统中——即“受治理的写入”——目前是 Ontology 独有的能力；其他方案无法提供完整的功能集。

07 对我们的启示：沉淀比模式更难复制

回顾 FDE 浪潮，作者总结出三点启示：

现场经验必须回流为平台能力。交付后即消失的项目式补丁是驻场模式几十年来的一大顽疾；没有扎根的反馈机制，FDE 就只是一条更昂贵的劳动力成本项。

先建模语义，再建模动作。先与业务方厘清“对象是什么、它们如何关联”，然后再谈自动化和 Agent 化。顺序颠倒，AI 只会更快地执行混乱。

组织建模是 Agent 部署的前提。除了模型能力之外，企业 AI 的成功往往取决于是否有一个清晰的 Ontology 层：对象、权限、动作、证据。没有它，部署 Agent 就像让人在没有地图的情况下开车。

FDE 这个标签还会火一阵子，但头衔终会褪色。其核心方法论——让了解一线的人参与定义组织如何被软件描述——本应在二十年前就做；现在做也不算太晚。
