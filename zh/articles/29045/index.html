Factory：通过前沿部署工程为企业构建自主软件工程 Agent

原标题：Factory: Building Autonomous Software Engineering Agents for Enterprise with Forward Deployed Engineering

摘要

本文介绍 Factory 如何用前沿部署工程师推动其自主软件工程 Agent 平台 Droid 在企业落地。其前沿部署工程师不做传统专业服务，而是作为客户与产品团队之间的信息通道，帮助客户把代码库改造为“Agent 就绪”状态，即建立大量确定性验证回路。验证能力越强，Agent 自主运行时间越长。其 Missions 产品已能自主迁移数千万行代码库。Factory 自身代码库约 15-20% 的变更完全自主，自主比率处于 80% 高位区间。文章同时指出验证系统建设、组织变革和平台锁定等挑战。

  • 约 30-40% 的验证改进可由 Droid 自动完成，其余需人工流程调整。

摘要

Factory 是一家为企业团队构建自主软件工程 Agent 的公司，其雇佣前沿部署工程师，将 AI 驱动的软件开发能力嵌入客户组织内部。Factory 的部署工程师并不从事传统的专业服务工作，而是充当产品开发的“先锋尖兵”，从企业客户那里收集深入洞察，以持续打磨其 Droid Agent 运行平台。该解决方案专注于打造“软件工厂”——即端到端的自动化流水线，能在极少人工干预的情况下将业务信号转化为已部署的代码。成功的关键在于通过大量的验证循环和校验系统，使客户的代码库达到“Agent 就绪”状态，部分客户已实现较高水平的自主性，包括 15-20% 的完全自主代码变更，以及接近 80% 上限区间的自主率。

Factory 正在通过名为 Droid 的平台为企业团队构建自主软件工程 Agent。该公司采用了一种独特的前沿部署工程模式，与 Palantir 等公司开创的传统模式有显著不同。Factory 的部署工程师并非被派驻到客户处执行专业服务工作或代表客户进行定制开发，而是充当大型企业客户与产品团队之间的关键反馈机制。

整体架构与产品愿景

Factory 产品理念的核心是“软件工厂”的概念——一条经过埋点监测、由 AI 增强的流水线，能在极少人工干预的情况下将业务信号转化为已部署的软件。该公司将软件开发视为存在于每个组织中的隐性反馈循环：来自外部世界的信号（客户沟通、缺陷报告、内部交流、高管指令）流入系统，人类围绕这些信号进行优先级排序和规划，开发者将计划转化为代码变更，这些变更经过各个验证阶段（代码评审、QA、安全分析、使用 SAST 工具的自动化测试、linter、类型检查器），最终软件被部署并监控，产生新的信号，重新启动这一循环。

Factory 的核心论点是：大多数组织对这一反馈循环的监测都很薄弱，而 AI 可以改造这条流水线的每个阶段。最终目标是实现从信号到部署的全流程无人工中断，但这并不意味着将人类从工程工作中移除——而是让人类从直接操作软件，转变为维护和管理构建软件的系统。

Droid 平台与模型无关性

Droid harness 是 Factory 的标准、模型无关的 Agent 平台，为构建这类软件工厂提供了基础。模型无关性被视为一项关键的架构原则，原因有以下几点。首先，对单一模型供应商的锁定会带来财务风险并限制灵活性。其次，人们担心模型供应商可能会左右客户能用其软件工厂构建什么、不能构建什么。第三，掌握流经系统的所有追踪记录和数据，对于软件工厂随时间不断演进至关重要。

该平台在企业层提供集中式的治理与控制，让组织能够决定信息的流向。对于金融、医疗和政府等高度安全环境中的客户，Droid 可以进行物理隔离部署。Factory 的工程师提到，Droid 理论上甚至可以在潜艇中运行，这凸显了该平台在完全隔离环境中运行的能力。

该产品包含多个组件，包括企业级控制、Droid harness 本身、在其上运行的工作流、可观测性工具、成本控制、自动化模型路由，以及 harness 的整体质量。每一项都是前沿部署工程师在与各类客户组织紧密合作时发现的潜在改进领域。

前沿部署工程模式

Factory 的前沿部署工程师在几个关键方面不同于传统模式。他们明确不做专业服务类工作——如果客户提出一项通常由咨询公司报价的代码库现代化需求，Factory 的目标并不是替客户执行那次迁移，即使使用 Factory 自己的产品也是如此。原因在于，这类工作无法切实改进产品，也无法作为商业模式进行规模化。

相反，前沿部署工程师充当从大型关键客户回传信息至产品团队的信息通道。他们与工程领导层以及一线战术工程师深度协作，了解围绕软件开发和 AI 落地的思考过程，然后迅速将这些信息反馈回来，以调整产品使其更好地适配客户环境。最终目标是让 Factory 的平台在客户环境中以最少的人工干预实现自我组装——当面对拥有 45,000 名员工、数万名工程师以及可能数万个代码库的组织时，这是必不可少的。

该职位涵盖几项关键职责：向客户讲解自主性成熟度模型以及构建自主软件组织的意义，通过引入验证循环使代码库达到 Agent 就绪状态，设计契合现有开发实践的工作流，以及构建清晰的 ROI 故事，将软件工厂的产出与核心业务目标联系起来。例如，证明 AI 辅助的代码审查、QA 和安全分析能将缺陷率降低特定百分比，进而提升客户满意度并推动收入增长。

Agent 就绪性与验证循环

Factory 提出的一个关键概念是“Agent 就绪性”——衡量代码库中存在多少确定性验证循环。大多数组织在构建确定性验证方面都有一定程度的一致性：lint 工具、类型检查器、安全扫描、要么通过要么失败的端到端测试。Agent 就绪性对这些反馈循环的数量和质量进行量化。

基本原则是：当代码库拥有大量此类反馈循环时，Agent 可以在更少人工干预的情况下，在更复杂的任务上运行更长时间。长时间运行的 Agent 框架的输出质量与其工作可被验证的程度成正比。如果能大规模引入验证，自主性就会相应提升。

Factory 已开发出扫描代码库并识别提升 Agent 就绪性机会的工具。大约 30-40% 的容易解决的问题只需指示 Droid 自动处理即可修复。然而，剩下的 60% 涉及工作流变更和人员适应。人们并不总是习惯自动化系统的“吹毛求疵”，因此部署工程师必须谨慎引入验证策略，既不打乱现有开发工作流，又能化解人员的顾虑。

这种方法与现代语言模型的实际训练方式相契合。模型在后训练阶段会在复杂任务上接收密集的奖励信号。同样，验证信号构成了奖励的基础，使 Agent 能够在长期、目标导向的问题上保持正轨。

Missions：长时间运行的自主框架

Factory 开发了一款名为 Missions 的产品，他们认为这是在实现完全软件工厂自动化之前的“Agent 时代的终极形态”。Missions 是一个精心构建的框架，围绕处理极其困难且可验证的知识型工作问题这一概念而设计。它作为一个长时间运行的框架运作，除规划阶段外几乎不需要人工干预。

Missions 的工作流程非常直接：定义一个边界清晰的任务，用可验证的方式明确“解决这个任务”意味着什么，然后不断推动推理的杠杆，直到任务完成。该系统在解决可验证完成的问题时被描述为“能力惊人”。关键洞察在于：如果任何问题都能被框定为一组需要对其进行验证的验证系统，那么这个问题今天就可以用 AI 来解决。

Factory 已经看到 Missions 被应用于极其复杂的问题，包括完全自主地迁移 3000 万至 5000 万行的代码库、围绕生物医学和医疗健康问题开展先进的深度学习策略，以及为金融机构构建模型，通过分析、比较并可能进行股票交易的系统来优化股票研究。然而，Missions 的成功绝对需要 Agent 就绪度——如果没有经过妥善准备的代码库，即使是最强大的 AI 系统也会失败。

自主性指标与现状

Factory 跟踪两项关于自主性的关键指标。“自主性百分比”表示完全自主完成的变更所占的比例。“自主性比率”衡量在被中断之前，人类与 AI 系统所执行操作的比例。Factory 自己的代码库已达到约 15-20% 的自主性，自主性比率处于 80% 以上的高位，这意味着大多数操作序列由 AI 主导，人类干预极少。

有趣的是，一些客户的代码库实际上比 Factory 自己的更加自主，因为它们运行在约束更强的领域中。Factory 发现，哪些类型的软件会率先达到 100% 自主性并不明显——预测是高度封闭的内部工具可能会最先实现。例如，Factory 有一个用于法律任务的内部“法律机器人”工作流，实际上已经 100% 自主维护。

然而，Factory 的核心框架尚未完全自主，因为他们在基于终端的框架中缺少能够验证某些困难视觉问题的验证器。诸如视觉闪烁之类的问题很难以可验证的方式捕捉，因此这些挑战的闭环还无法完成。这说明了关于未来工作的一个重要观点：构建验证系统来验证困难问题本身就是一项工程任务，而人类在视觉处理和上下文理解方面的优势，为构建这些系统提供了大量工作机会。

扩展策略与变革管理

Factory 的扩展策略强调创建可运行的成功范例，而不是为每个客户构建完整的解决方案。这里使用的类比是华特·迪士尼对 Epcot 的最初构想——打造一个示范性的模范城市，激励其他城市采用类似的创新。虽然 Epcot 最终变成了主题公园，但当时确实有一些城市在建设基础设施时参考了迪士尼关于集中式城市交通的理念。

Factory 的目标是打造一个“未来城市、未来代码库的可行范例”，展示什么是可能的，同时又不过于超前，以免看起来像一座遥不可及的主题公园。这种平衡至关重要：要构建的东西必须证明未来是可以实现的，但又不能吓跑那些担心转型成本的组织。其理念是，人类聪明而机智——只要看到一个有说服力的范例，他们就会想出如何将这些理念应用到自己的代码库中。

这一理念承认了技术进步分布的不均衡。有一些特定的代码库（甚至不是整个公司，而是公司内部的个别代码库）确实非常出色，并开始进入自动驾驶状态。未来存在于一个个局部之中，而部署工程师的角色就是审慎地扩大这些局部。

批判性评估与权衡

虽然 Factory 的愿景很有吸引力，但也出现了几个重要的考量与潜在担忧。“如果你能把任何问题框定为一组需要对其进行验证的验证系统，那么你今天就能用 AI 解决这个问题”这一论断很大胆，但带有重大限制条件。这只适用于能够进行全面验证的问题，而许多创造性的、开放式的或全新的问题领域——其成功标准是涌现的或主观的——则被排除在外。

对 Agent 就绪性的要求意味着一笔可观的前期投入，可能并非小事。那 60% 需要改变工作流程和人类适应的改进，可能会面临巨大的组织阻力。这份演示承认人类必须适应自动化系统的“吹毛求疵”，但这种文化变革可能比描述的更具挑战性，尤其是在拥有成熟工程文化的组织中。

模型无关性的主张很有价值，但该平台仍然意味着被锁定在 Factory 自己的 harness 和架构上。虽然客户拥有自己的数据和追踪记录，但在深度集成之后从 Droid 平台迁移出去可能会相当复杂。气隙部署能力对于注重安全的行业来说确实令人印象深刻，但可能会限制其从集中式模型改进和共享经验中获益的能力。

从工程师直接编写代码转变为维护编写代码的系统，代表着工程工作性质的根本性变化。虽然这被呈现为“抽象层级的升级”，但它可能并不适合所有工程师或所有问题领域。演示中也承认“大多数人，即使是非常有见地的软件工程师，都会有一个学习曲线”，这表明这一转变可能比乐观的表述所暗示的更具颠覆性。

经济模式很有意思——明确拒绝专业服务收入、转而追求产品改进和可扩展性，从产品角度来看值得钦佩，但可能会限制近期的收入机会。这一模式的成功取决于平台能否真正实现自我组装，而对于复杂的企业环境来说，这仍然是一个愿景目标。

最后，所分享的指标（15-20% 的自主性、80% 以上的自主率上限）表明，尽管进展显著，我们仍处于早期阶段。Factory 自身终端工具中的可视化验证问题表明，即使是构建自主系统的公司，在实现完全自主方面也面临根本性挑战。这种坦诚的承认令人耳目一新，但也说明对于大多数组织和用例而言，从信号到部署、无需人工干预的“软件工厂”愿景在很大程度上仍属未来。
