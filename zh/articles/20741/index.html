摘要

文章列出十个面向 FDE 求职的 AI 项目，强调项目应像客户交付物：已部署、有安全设计、有评测和文档。每个项目给出业务场景、技术栈、证明的能力和进阶目标，并建议组合两三个完整项目胜过一堆 notebook。

要点

  • 面试官像审阅客户交付物一样看 GitHub，看重部署、安全、评测、文档四要素。
  • 十个项目涵盖权限感知 RAG、幂等集成服务、MCP 工单 Agent、多 Agent 事故摘要等场景。
  • 安全类项目强调 PII 脱敏、审计日志和威胁建模；Agent 项目强调最小权限与人工审批。
  • 评测与可观测性项目把 AI 质量变成 CI 门禁，并追踪成本与延迟。
  • 建议组合：核心系统加评测、成本看板，再配一个 ROI 一页纸演示。

能让 FDE 招聘经理信服的 AI 工程师项目，并不是那些提示词写得最巧妙的，而是那些看起来像客户交付物的项目：已部署、已加固安全、已评测并有文档，让别人也能直接运行。 下面是十个 AI FDE 项目，每个都以业务问题为框架，附带构建计划、技术栈、它能证明什么以及进阶目标。你不需要全部做完。认真做好两三个，比一整个文件夹的 notebook 更能在面试环节中加分。

如果你还在了解这个职位本身，可以先从什么是前沿部署工程师开始。想了解每个项目旨在证明的技能，请参阅雇主看重的 FDE 工程师技能。本页是构建清单。

想要更多灵感？ 参阅适合简历和 GitHub 的 25 个 Agentic AI 项目，从入门到专家级。

什么样的项目能让 FDE 招聘经理信服

FDE 面试官阅读你的 GitHub，就像客户阅读供应商的交接文档一样。他们只问一个问题：如果下个月把这个人派到一家银行或医院面前，他们能否交付一个能在生产环境中稳定运行的东西？以下四个特质可以回答这个问题。

  • 已部署。 它运行在你笔记本之外的地方：托管云服务上的容器，通过基础设施即代码进行配置，并置于真实的 API 之后。一个可访问的 URL 或运行系统的录屏演示都算数。
  • 安全加固。 身份验证、授权、密钥不放在代码仓库中，并附有关于提示词注入和数据处理的书面说明。企业客户在询问准确性之前，会先问这些。
  • 经过评测。 有固定的测试集、明确的指标和结果表格，包括失败的用例。“运行良好”不是证据；忠实度得分和三个记录在案的失败模式才是。
  • 像交付物一样编写文档。 一份客户工程师能够照着操作的 README、一张架构图和一页纸的业务摘要。

每个项目覆盖 FDE 链条的一部分；汇总表格展示了如何将它们组合起来。

客户问题 -> 需求调研 -> 数据 -> RAG / Agent -> 工具 / MCP -> API -> 安全 -> 云 -> 部署 -> 可观测性 -> 评测 -> 业务成果

1. 具备权限感知 RAG 的企业知识助手

业务问题。 设想一家保险公司，其核保、理赔和人力资源团队各自持有自己的保单文档。员工希望有一个统一的助手，但人力资源文档绝不能出现在核保员的回答中。安全审查人员会首先检查这一点。

你要构建什么。 一个数据摄取管道，将文档分块并连同元数据（部门、密级、来源、生效日期）一起存储嵌入向量。一个检索层，在相似度搜索之前（而不是生成之后）根据调用者的组权限进行过滤。回答附带指向确切来源分块的引用，当检索没有返回相关内容时，助手会说“我不知道”。

技术栈。 Python/FastAPI、带 pgvector 的 PostgreSQL、用于嵌入和生成的 Amazon Bedrock 或 Azure OpenAI、用于检索链的 LangChain、用于登录和组声明的 Microsoft Entra ID、用于评测的 Ragas、Docker。

它证明了什么。 你理解检索不仅是相关性问题，同样也是访问控制问题，并且你能够衡量答案质量。如果你对 RAG 基础还不熟悉，请先阅读 什么是 RAG。

进阶目标。 添加文档版本控制，使被取代的政策在新版本被摄取的那一刻起就不再出现在答案中，并添加一个评测用例来证明这一点。

2. 客户集成服务（API、重试、幂等性）

业务问题。 一家零售商希望将 AI 生成的产品信息增强推送到其订单和目录系统中。这些系统响应缓慢、有速率限制且偶尔宕机。一个天真的集成方案会在重试时重复写入记录，或者悄悄丢弃它们。

你要构建什么。 一个 FastAPI 服务，用于接收任务、调用 LLM 增强记录，并将结果写入下游 API。包含幂等键以确保重试的请求绝不会创建重复记录、带抖动的指数退避、用于持续失败任务的死信表，以及客户可以轮询的状态端点。针对一个注入超时和服务器错误的模拟服务编写契约测试。

技术栈。 Python/FastAPI、用于任务状态和幂等记录的 PostgreSQL、Docker、用于测试的 GitHub Actions、用于在 AWS 上进行配置的 Terraform。

它证明了什么。 扎实的集成工程能力，而这正是 FDE 每周工作中相当大的一部分。不可靠的集成是试点项目停滞的常见原因。

进阶目标。 使用结构化输出契约对 LLM 输出添加模式校验，并将未通过校验的记录路由到人工审核队列，而不是直接发送到下游系统。

3. 通过 MCP 实现带人工审批的 ServiceNow 或 Jira 工单 Agent

业务问题。 设想海得拉巴的一个 GCC IT 团队被大量重复的服务台工单淹没。他们想要一个 Agent，能够读取新工单、查找类似的已解决工单、起草分类和回复，并更新工单，但没有人会让 Agent 在无人监督的情况下写入记录系统。

你要构建什么。 一个 MCP 服务器，暴露一小组带类型的工具（搜索工单、获取工单、添加工作备注、更新分类）。一个以 LangGraph 状态机形式构建的 Agent 规划操作，并在任何写入操作之前在审批节点暂停。只读工具可以自由运行；每次写入都会连同其审批人一起被记录。

技术栈。 Python、MCP（Model Context Protocol）、LangGraph、ServiceNow 开发者实例或 Jira 云免费版、Azure OpenAI 或 Gemini、用于审计日志的 PostgreSQL。

它证明了什么。 你能够以最小权限范围和人在回路的方式将 Agent 连接到真实的企业工具。有关协议基础，请参阅 什么是 MCP。

进阶目标。 通过编写第二个 MCP 服务器，将工单后端从 ServiceNow 切换到 Jira，且不改动 Agent。

4. IT 运维多 Agent 事件摘要器

业务问题。 在故障期间，银行的值班工程师需要在日志、指标、近期部署和事件频道之间来回切换。管理层希望每隔几分钟获得一份持续更新的摘要，并在事后获得一份事后复盘草稿。

你要构建什么。 一个监督 Agent，负责分派给各专家 Agent：查询近期错误日志的日志分析 Agent、从 GitHub 列出近期部署的变更分析 Agent，以及整理时间线并为高管撰写摘要的写作 Agent。各 Agent 通过类型化图共享状态，且每个 Agent 都有步骤预算，以防止混乱的 Agent 无限循环。

技术栈。 LangGraph、Python/FastAPI、用于追踪的 OpenTelemetry、GitHub API、Kubernetes（EKS）上的 Docker，以及用于检查 Agent 运行情况的 Langfuse 或 LangSmith。

它能证明什么。 你能判断何时需要多个 Agent、何时一个就够，并且能对它们进行约束和观测。什么是 Agentic AI 涵盖了这些底层模式。

进阶目标。 重放一次已录制的事件，并将生成的时间线与人工撰写的时间线进行对比评分，使摘要器具备回归测试。

想在部署过此类系统的工程师的反馈下构建这样的系统吗？Cloudsoft 的 FDE PRO 项目 将通过五个企业级项目，带你从客户问题走向已部署、已评测的系统。

5. 带 PII 脱敏与审计的安全银行或金融助手

业务问题。 银行的运营人员希望有一个助手来解答账户服务流程相关的问题并总结客户投诉。投诉文本中包含账号、电话号码和姓名，这些信息绝不能以明文形式传给模型提供商或写入日志。

你要构建什么。 一个脱敏层，在任何模型调用之前检测并遮蔽 PII，仅在授权用户需要查看原文时使用可逆令牌。输入和输出护栏会拒绝提示注入尝试和偏离主题的请求。一个只追加的审计日志记录谁问了什么、检索了哪些文档以及返回了什么。撰写一份威胁模型，涵盖主要风险及每项风险的应对控制措施。

技术栈。 Python/FastAPI、带护栏的 Amazon Bedrock、用于审计追踪的 PostgreSQL、Microsoft Entra ID、在 AWS 上使用私有网络的 Terraform、Docker。

它能证明什么。 你将安全与合规视为设计输入，而不是最后勾选的检查项。

进阶目标。 构建一套由注入和数据外泄提示组成的红队评测集，并报告拦截率以及回答质量。

6. 文档智能流水线（提取、校验、路由）

业务问题。 某医院的账务团队以扫描版 PDF 的形式接收保险预授权表单。员工需要将字段手动录入账务系统，并通过邮件追讨缺失的信息。

你要构建的东西。 一条流水线：将字段提取到严格的模式（schema）中，用业务规则进行校验（日期在有效范围内、必填字段齐全、保单号格式正确），为每个字段赋予置信度，并对文档进行分流：自动批准并录入系统、转交人工审核，或退回发件方并附上缺失项清单。一个小型审核界面或 API 允许人工修正字段，修正结果将存储为未来的评测数据。

技术栈。 Python，Gemini、Bedrock 或 Azure OpenAI 上的多模态模型，Pydantic 模式，PostgreSQL，Docker 中基于队列的 worker，GitHub Actions。

它能证明什么。 并非每个企业 AI 项目都是聊天机器人，而信息提取会迫使你度量字段级别的准确率。

进阶目标。 在一个标注数据集上报告每个字段的精确率和召回率，然后展示调整置信度阈值如何在人工工作量与错误率之间进行权衡。

7. 面向 LLM 应用的评测框架与 CI 回归门禁

业务问题。 团队为了修复一个投诉而修改了提示词，却悄悄破坏了另外五个回答。直到用户发现之前，没有任何人察觉。

你要构建的东西。 以项目 1 或 5 为基础，添加一个版本化的测试集，涵盖常见问题、边界情况、语料库中无答案的问题以及对抗性提示词。运行确定性检查（格式、引用存在、预期时的拒答）和模型评分指标（忠实度、答案相关性、上下文精确率）。将其接入 GitHub Actions，使任何导致某项指标跌破阈值的拉取请求无法通过构建，并将变更回答的差异以报告形式发布。

技术栈。 Ragas、LangSmith 或 Langfuse 数据集，pytest，GitHub Actions，以及用于长期存储结果的 PostgreSQL。

它能证明什么。 你可以让 AI 质量成为发布标准，而非主观意见。LLM 评测指南解释了这些指标以及 LLM-as-judge 的局限性。

进阶目标。 通过人工标注一个样本来校准你的评分模型，并报告自动评分与你一致的比例。

8. AI 服务的可观测性与成本仪表盘

业务问题。 一个 AI 助手已经上线，云账单不断攀升，客户的平台团队提出三个问题：哪个功能成本最高，为什么有些请求耗时远超其他请求，以及质量是否在漂移。

你要构建的东西。 用 OpenTelemetry span 为你之前的某个服务添加插桩，覆盖检索、每次模型调用和每次工具调用。捕获每个请求的 token 数量、延迟和模型名称，并按租户和功能标记支出。构建一个仪表盘，展示每请求成本、延迟分位数、错误率和抽样质量评分。为成本激增和“我不知道”类回答增多添加告警。

技术栈。 OpenTelemetry、Langfuse 或 LangSmith、Kubernetes（EKS）、Terraform，以及 AWS、Azure 或 Google Cloud 上的托管仪表盘。

它证明了什么。 生产环境的所有权意识。

进阶目标。 为简单查询添加一条更便宜的模型路由，然后将仪表盘和评测框架结合使用，展示节省的成本及其对质量的影响。

9. 带防护栏的 GitHub PR 审查 AI Agent

业务问题。 一家产品公司的平台团队希望对拉取请求进行初审并给出评论，覆盖缺失的测试、有风险的基础设施变更和泄露的密钥，但这个 AI Agent 不能合并、推送或批准任何内容。

你构建什么。 一个 GitHub App 或 Actions 工作流，读取 diff，先应用确定性检查（密钥模式、Terraform plan 风险规则），然后让模型给出审查评论，评论被约束到一个包含文件、行号、严重程度和建议的 schema。防护栏包括：只读的仓库权限、每个 PR 的评论数硬上限、不对 diff 之外的文件发表评论，以及将 PR 本身的内容视为不可信输入，这样代码注释中注入的指令就无法劫持 AI Agent。

技术栈。 GitHub Actions、GitHub API、Python、Bedrock、Azure OpenAI 或 Gemini，以及一小套带标注的历史 PR 用于评估。

它证明了什么。 你能够严格限定 AI Agent 的权限，并在开发者每天使用的工作流中防御间接提示注入。它还展示了 CI/CD 熟练度（参见 GitOps 和 GitHub Actions 培训）。

进阶目标。 在你带标注的 PR 上衡量 AI Agent 评论的精确率，并调整提示词和规则，直到开发者不会将其静音。

10. 高管演示与 ROI 单页文档（客户工程交付物）

业务问题。 工程本身没问题，但赞助人只有十分钟时间和 CFO 决定是否为试点拨款。这个项目不是新代码，而是把上面某个项目转化为决策的交付物。

你构建什么。 选出你最强的项目，产出三样东西。一段约五分钟的录制演示，以业务问题开场，展示一条真实的用户旅程，然后展示一次被优雅处理的失败。一页 ROI 摘要，说明基线流程、来自试点数据的实测改进、任何预测背后的假设、来自仪表盘的运行成本以及风险。还有一份简短的“下一步我们会做什么”计划，包含阶段关卡。

技术栈。 你之前的项目、其评测报告和成本数据，一个录屏工具和一份文档。

它证明了什么。 客户工程：你能够把系统行为转化为业务语言而不夸大其词。这是 FDE 与纯构建者之间最清晰的区别，正如 将 AI 从 POC 推向生产 逐阶段所解释的那样。

进阶目标。 请一位财务或运营人员冷启动观看演示，记下他们提出的每一个问题，然后修改单页文档来回答这些问题。

摘要：项目、技能与难度

项目展示的技能难度
1. 权限感知型知识助手RAG、访问控制、引用、评测中级
2. 客户集成服务API、重试、幂等性、契约测试中级
3. 基于 MCP 的工单 AgentAgent、MCP、工具权限范围、人工审批中级到高级
4. IT 运维多 Agent 摘要器多 Agent 设计、追踪、有界自主性高级
5. 安全银行助手PII 脱敏、防护栏、审计、威胁建模高级
6. 文档智能流水线结构化提取、校验、人工路由中级
7. 评测框架与 CI 门禁测试集、RAG 指标、CI/CD中级
8. 可观测性与成本仪表盘OpenTelemetry、成本归因、告警中级到高级
9. 带防护栏的 PR 审查 Agent最小权限、间接注入防御、GitHub Actions中级
10. 高管演示与 ROI 一页纸需求挖掘、沟通表达、业务框架代码门槛低，但做好很难

一个实用的组合：以项目 1 或 5 作为核心系统，在其上叠加项目 7 和 8，用项目 3 作为 Agent 部分，再用项目 10 作为包装。应届生可以从项目 2 和 6 入手，它们对 Agent 经验的要求较低；FDE 工程师路线图展示了每个项目在学习路径中的位置。

如何展示你的项目

构建只是工作的一半。你如何包装它决定了面试官会在你的代码仓库上花两分钟还是二十分钟。更全面的作品集清单见如何成为 AI FDE；上面每个项目都应附带以下四份材料。

一份客户能看懂的 README

开头用两句话说明业务问题以及用户是谁。然后是前提条件、在干净机器上可用的分步安装与配置说明、各环境变量及其作用、如何运行评测，以及一个“已知局限”部分。

一张架构图

一张图展示组件、数据流、信任边界以及每次模型调用发生的位置。标出在哪里强制执行身份验证，以及在哪里对 PII 进行脱敏。

一份评测报告

你的测试集规模与构成、所选指标及其理由、结果表格、三到五个带注释的失败案例以及你因此做出的改进。为其中一项改进附上前后的对比数据。

一段演示视频

三到五分钟，先讲问题。展示正常流程、一次处理得当的失败，以及追踪记录或仪表盘的一瞥。把链接放在 README 顶部，让忙碌的审阅者最先看到它。

其中几个项目与 FDE PRO 课程直接对应：它的五个企业级项目分别是客户集成服务、企业知识助手、通过 MCP 实现的 ServiceNow AI Agent、IT 运维多智能体平台和安全银行 AI 助手，而“GlobalBank”毕业项目则是一次模拟的客户合作，用于锻炼项目 10 中的需求挖掘、演示和业务汇报技能。

常见问题

FDE 作品集需要多少个项目？

通常两到三个有深度的项目就足够了，前提是每个项目都完成了部署、安全加固、评测和文档编写。深度胜过数量。

应届生应该先做哪个项目？

从客户集成服务或文档智能流水线开始。这两个项目都能教你 API、校验、测试和部署，而不需要高级的智能体设计，而且都为你日后添加 RAG 或智能体打下基础。

构建这些项目需要像 ServiceNow 这样的付费企业工具吗？

不需要。ServiceNow 提供个人开发者实例，Jira 有免费套餐，这对工单智能体来说已经足够。身份认证方面，可以注册一个 Microsoft Entra ID 租户用于学习，其余部分用云免费套餐或小额预算即可覆盖，只要你在不用时关闭资源。

这些项目应该用 AWS、Azure 还是 Google Cloud？

选定一个云平台，并用 Terraform 把所有东西规范地部署上去。AWS 是常见的第一选择，模型可用 Amazon Bedrock；Azure 搭配 Azure OpenAI 则适合面向以微软为主的企业客户。在 README 中展示你能把设计迁移到第二个云平台是一个有用的加分项。

RAG 聊天机器人项目还值得做吗？

基础的“上传 PDF 然后提问”的聊天机器人价值不大。但一个具备权限感知检索、引用标注、文档版本管理和评测报告的 RAG 系统，仍然是最强的作品集项目之一，因为这些正是企业实际面临的问题。

面试中如何展示这些项目？

先讲业务问题，然后讲解架构图，接着展示评测结果和你修复过的一个故障。准备好可分享的演示视频。面试官会追问权衡取舍，所以要准备好说明面对真实客户时你会做哪些改变。
