Databricks FDE 面试：Spark、Unity Catalog 与 Genie

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

文章分析 Databricks 首尔 FDE 岗位的面试准备路径。招聘要求聚焦 Spark（7 年以上经验、运行时内部机制），而 Genie 与 Unity Catalog 虽不在任职要求中，却是实际部署的关键。作者梳理了 shuffle、AQE、broadcast join 等 Spark 调优要点，讲解 Unity Catalog 的权限、血缘与审计，并以行过滤示例说明 Genie 的回答质量取决于底层治理配置。

要点

  • 首尔 FDE 岗要求 7 年以上经验，重点考 Spark 运行时内部机制。
  • Spark 准备核心：shuffle 分区、AQE、broadcast join 与用 Spark UI 定位数据倾斜。
  • Unity Catalog 通过权限、行过滤、血缘和审计回答“谁能看到什么”。
  • Genie 建在 Unity Catalog 之上，权限配置错误会直接导致错误答案。
  • 建议学习顺序：先 Spark，再 Unity Catalog 治理 SQL，最后 Genie Agent 配置。

要点速览

  • Databricks 首尔 FDE 岗位要求 7 年以上经验，以及深厚的 Spark 知识，包括运行时内部机制。
  • Unity Catalog 负责访问权限、数据血缘和审计；Genie 正是依据这些权限作答。
  • 合理的学习顺序：先学 Spark 和 Spark UI，再学 Unity Catalog 治理 SQL，最后学 Genie Agent 配置。

Databricks 在首尔招聘前线部署工程师（FDE）的启事写得很明白：候选人需要有基于 Apache Spark 的分布式计算深厚经验，并理解 Spark 的运行时内部机制。相比之下，Genie 和 Unity Catalog 只出现在公司介绍里，不在任职要求中。

要通过招聘流程，准备的重点是 Spark。但从官方文档看，部署 Unity Catalog 和 Genie，考验的是访问权限、元数据和业务规则。

Spark：学到能讲清楚一个作业为什么慢

首尔岗位要求 7 年以上数据工程、数据平台与分析或软件工程经验；能用 Python、Scala 或 JavaScript/TypeScript 编程；约 20% 的时间要去客户现场出差。面向国家安全业务的 Senior FDE 岗位保留了同样的 Spark 要求，把门槛降到 6 年以上，并增加了 MLOps、ML/AI 模型和 AI API 的实践经验要求。

“运行时内部机制”听起来很虚，其实可以归结为三件具体的事。第一是 shuffle：join 和聚合会让数据在节点之间移动，

spark.sql.shuffle.partitions

默认把这部分工作拆成 200 个分区。

第二是自适应查询执行（AQE），从 Spark 3.2.0 起默认开启。AQE 利用运行时统计信息，合并 shuffle 之后过小的分区，并拆分 sort-merge join 中倾斜的分区。第三是 broadcast join：小于

spark.sql.autoBroadcastJoinThreshold

（默认 10 MB）的表会直接发送到每个 worker，不再做 shuffle。

练习方法是故意让作业变慢，再去读 Spark UI。把一张大表和一张小表做 join，打开 SQL 标签页，点击 Details，看物理计划用的是 BroadcastHashJoin 还是 SortMergeJoin。把阈值设为 -1 关闭广播，重新运行，对比耗时。

然后打开最慢的 stage 的详情页。Summary Metrics 表展示了任务运行时间的分布：如果最慢的任务比中位数慢很多倍，数据很可能有倾斜。Shuffle Read Size 和 Shuffle spill (disk) 两列显示移动了多少数据，以及是否溢写到磁盘。

练习用 UI 里的真实数字描述你看到的情况。面试时，这是证明你懂 Spark 底层原理最具体的方式。

Unity Catalog 回答“谁能看到什么”

Databricks 将 Unity Catalog 定义为内置于平台的数据与 AI 统一治理层。所有对象都位于

catalog.schema.object

三级命名空间中。表和卷可以是托管的（Unity Catalog 同时负责治理和底层存储文件的生命周期），也可以是外部的。

据 Microsoft Learn 介绍，2023 年 11 月 9 日之后创建的 Azure Databricks 工作区都会自动启用 Unity Catalog，Unity Catalog 也有开源版本。因此，在使用较新工作区的客户那里，你很可能从第一天起就要和它打交道。

文档把 Unity Catalog 的能力分成几个方面，其中最值得先学的有三个：权限、血缘和审计。权限通过特权、基于属性的访问控制（ABAC）策略、行过滤、列过滤和工作区绑定来实现。

血缘无需手动配置，就能记录从源数据到模型、服务和仪表盘的路径；所有数据访问和系统活动都会写入专门存放审计日志的系统表，合规团队需要的正是这些。

示例：每个分区只看到自己的数据

假设一家零售连锁企业有一张

sales.core.orders

表，其中有

region

列。需求是：越南的分析师组只能看到越南的订单，管理员组能看到全部。第一步是授予读取权限：

GRANT USE CATALOG ON CATALOG sales TO `analysts_vn`;
GRANT USE SCHEMA ON SCHEMA sales.core TO `analysts_vn`;
GRANT SELECT ON TABLE sales.core.orders TO `analysts_vn`;

只有 GRANT SELECT 时，这个组仍然能读到所有行。要按地区限制，需要写一个对每行返回 true 或 false 的函数，再把它挂到表上：

CREATE FUNCTION sales.gov.region_filter(region STRING)
RETURN IF(is_account_group_member('admins'), true, region = 'VN');

ALTER TABLE sales.core.orders
SET ROW FILTER sales.gov.region_filter ON (region);

此后，同样一句

SELECT * FROM sales.core.orders

，不同的人运行会得到两种结果。访问逻辑落在表上，而不是分散在各个仪表盘里。在客户那里，先和数据负责人一起敲定“谁能看哪些行”的对照表，再动手写函数。

文档里有两个细节值得记住。函数参数类型必须与列类型一致：如果不一致且 ANSI 模式关闭，无法转换的值会变成 NULL，过滤器可能不报错就返回整张表。

另外，如果多张表需要同一条规则，Databricks 建议使用挂在 catalog 或 schema 级别的 ABAC 策略，而不是逐表挂行过滤器。

Genie 建在 Unity Catalog 之上，权限错了，答案就错

根据 2026 年 9 月的文档，Genie 现在是一个产品系列，包括 Genie One、Genie Agents 和 Genie Code。Genie Agents 是按业务领域组织的环境，数据团队在其中配置可信数据、指标和业务规则，Genie One 依靠这些内容回答问题。

命名也变了：当前的概览页已不再使用“Genie space”一词。参考旧教程时，先看它的更新日期。

Databricks 表示，Genie 的每个回答都基于组织自己的数据，并经过 Unity Catalog 的治理层。

实际影响是：上面示例中的行过滤器，同样决定了越南的 Genie 用户能看到什么。如果权限做得马虎，Genie 会把这个错误直接交给业务用户，而且是以一个非常有说服力的回答呈现。

搭建 Genie Agent 是一项配置工作：选择数据集、编写示例查询、编写指令。之后再通过指标、业务规则和已验证答案来调优质量。例如，如果客户对“净收入”的定义是扣除退货，就必须把它写成业务规则；本周被问得最多的问题，应当有一个已验证答案。

根据文档，在 2027 年 1 月 31 日之前，用户可以免费使用 Genie One 和 Genie Agents，服务主体（service principal）不在此列。现在正是上手练习的好时机。

先学什么，简历上写什么

合理的顺序是先学 Spark 和 Spark UI，因为那是入门的敲门砖。接着是 Unity Catalog 治理 SQL：GRANT、行过滤、列过滤、读懂血缘和审计日志。Genie Agents 放在最后，因为它依赖前两层。

简历上不要写“熟悉 Databricks”，而要写具体的工作：“用 Spark UI 定位 join 中的数据倾斜，把作业耗时从 X 降到 Y”，或者“为订单表设计按地区的行过滤，并通过审计日志验证”。

读职位描述时，别跳过只出现在公司介绍里的产品。它们往往就是你要部署的东西；而对 Genie 来说，回答质量取决于下面的权限层。
