Andrew Ng 的 AI 工程技能图谱（2026 年 8 月）

原标题：Andrew Ng's AI Engineering Skills Map (Aug 2026)

AISOLO Technologies Private Limited · 2026-08-15 · 约 14 分钟读完

摘要

Andrew Ng 于 2026 年 8 月基于 10,000 多条招聘信息、专家访谈和调查数据，提出 AI 工程的四项核心技能：构建与部署 AI 应用、软件工程基础、使用编码 Agent、塑造构建方向。他认为提示词工程并非重点，评测与错误分析、软件基础、产品判断才是关键。后续系列文章进一步细化了各技能的子项，并反驳了让 Agent 长时间自主运行的“设好就不管”用法。

要点

  • 技能地图来自 10,000 多条招聘信息与专家访谈，而非流行观点。
  • 四项技能：构建部署 AI 应用、软件工程基础、使用编码 Agent、塑造构建。
  • 评测与错误分析是把不可预测的 AI 系统变得可控的核心机制。
  • 软件基础是指导编码 Agent 的语言，不懂权衡就难以正确指挥。
  • Ng 认为长时程自主 Agent 运行的实用性被夸大，人工干预效果更好。

为什么是技能图谱，为什么是现在

吴恩达以 explainx.ai 自身受众经常遇到的问题开篇：“在充满噪音、炒作和信息泛滥的 AI 环境中，哪些技能最值得学习？”每周都会出现新的框架、新的 Agent 工具、新的“必备技能”帖子——而其中大部分只是观点，而非数据。

这个框架的不同之处在于数据来源。吴恩达的团队没有调查自己通讯的订阅者，也没有从少数案例研究中进行推断。他们分析了超过 10,000 条招聘职位，与 AI 专家、招聘经理和猎头进行了数十次结构化访谈，并叠加了调查数据——然后寻找在所有三个来源中都聚集出现的技能。吴恩达自己的表述是：“你可以非正式地把我们的过程理解为，对海量的职位和专家访谈数据集进行聚类，以识别最重要的技能——不仅是今天，也包括不久的将来。”

最后这个限定条件很重要。这不是当前职位头衔的快照——而是试图找到足够持久的技能，使其在底层工具不断变化的情况下依然重要。

四项技能，以及每项技能的实际要求

1. 构建和部署 AI 应用

吴恩达指出，AI 软件的定义性特征是不可预测性：“当你向 LLM 发送提示词时，你不知道会得到什么。”传统软件的行为是确定性的；AI 系统则不然。这项技能不是知道 LLM、RAG、上下文工程和 Agentic 工作流的存在——而是知道如何运用统计技术来测量、引导和治理那些默认行为不可预测的系统。

吴恩达特别指出一项具体能力是这项技能的核心：执行严谨的评测和错误分析循环。这不是构建模块之上的锦上添花——而是将不可预测的系统转变为可治理系统的机制。如果你无法测量你的 RAG 管道或 AI Agent 在哪里失败，你就无法系统性地修复它；你只能不断调整提示词，直到它在眼前的那一个示例上看起来正确为止。

此后，吴恩达在后续系列的第一部分中将这项技能细化为六个明确的子技能——LLM 基础、用数据为模型提供依据、构建 Agentic 系统、评测驱动开发、生产环境运维，以及机器学习基础。

2. 软件工程基础

这是最容易被对 AI 工具感到兴奋的人忽略的技能，也是吴恩达花最多篇幅为之辩护的一项。软件工程意味着在成本、可扩展性、可靠性和速度之间进行权衡——而理解这些权衡，正是让开发者能够识别出眼前的问题究竟涉及哪种权衡的关键。

吴恩达在此做了鲜明的对比：一个缺乏经验的开发者如果在不了解其编码 Agent 所做权衡的情况下凭感觉编码，通常会得到糟糕的权衡结果，因为他们不知道该向 Agent 提供什么上下文来正确引导它。软件基础并不是与 Agent 编码相竞争的技能——它是你用来指挥 Agent 编码的语言。一个知道“最终一致性”或“N+1 查询”是什么意思的开发者，可以明确告诉 Agent 应遵守什么约束；而不知道的开发者只能指望 Agent 碰巧猜对。

3. 使用编码 Agent

吴恩达将其视为一项独立的、可学习的技能——而不是你用几周 Cursor 或 Claude Code 就能被动掌握的东西。它需要一个关于 Agent 实际如何运作的有效心智模型：它们的局限性、如何绕过这些局限，以及——至关重要的是——知道何时该介入、何时该放手让 Agent 自行工作。

吴恩达列举的具体要点，读起来就像一份给当今所有构建 Agent 工作流的人的清单：

  • 有意识地管理 Agent 的上下文窗口，而不是任其被噪音填满
  • 在规划与执行之间权衡——何时先写详细规格说明，何时让 Agent 自行探索
  • 为 Agent 提供验证器或评测，使其能够自主闭环，而不需要在每一步都由人来检查
  • 知道什么时候值得写一份清晰的规格说明——什么时候不值得
  • 编排多个 Agent 协同完成同一任务
  • 避免具体的失败模式，例如让拥有不受限制访问权限的 Agent搞砸生产数据库

吴恩达还补充了一个容易被低估的元层面观点：由于 Agent 编码工具变化很快，“熟练使用编码 Agent 不仅意味着了解前沿实践，还意味着要养成不断尝试新工具、持续演进工作流的习惯。”这项技能不是一套固定的技术——而是一种随着底层工具变化而不断重新评估自己工作流的习惯，这正是 explainx.ai 在其循环工程指南中阐述的纪律。

吴恩达后来还针对这项技能发布了一篇完整的深度解析——关于五个子技能、“规划 → 执行 → 部署”工作流，以及他反对“设置完就不管”的长时程运行的主张，请参见下文的专门章节。

4. 塑造构建过程

这是对职业生涯影响最深远的技能，也是技术教程最少涉及的一项。吴恩达的论点是：编程 Agent 在按照明确规格交付方面进步迅速，因此真正的工程工作正在向上游转移——转向决定规格中应该包含什么。“工程师不应再期望拿到一份像素级精确的设计稿，然后只负责实现它。”

这种转变需要产品直觉，以及对业务背景和客户目标的理解——这些技能传统上属于产品管理的范畴，如今正融入工程师自身的工作。吴恩达将其视为机遇而非负担：AI 赋予个人开发者比以往更多的主导权和自主性，让他们能够发现问题与机会，并直接付诸执行。这一机遇背后的实用技能是对节奏的判断——知道何时应该把粗糙的 MVP 交付给真实用户测试，何时应该放慢脚步、更谨慎地构建。这与吴恩达自己的三循环框架在机制上描述的是同一种张力：内层的编码循环以分钟为单位运行，外层则包裹着更缓慢的人类反馈循环和市场反馈循环，由后者决定内层循环究竟应该构建什么。

吴恩达的深度剖析：使用编程 Agent 的五项子技能

2026 年 9 月 4 日，吴恩达在 X 上发布了一篇专门的后续文章，以第一部分和第二部分对待其他分支的同等严谨程度，深入展开了技能之三——“使用编程 Agent”。文章配有一张更新后的图表，将“使用编程 Agent”列为四大顶层分支之一（与构建/部署 AI 应用、软件工程基础以及塑造构建过程并列），每个分支又进一步细分为具名的子分支。

吴恩达解释了为什么这一分支值得单独深入剖析：它的演进速度快于其他三项顶层技能。他写道：“专有 Agent（如 Claude Code、Codex 和 Cursor）与开放 Agent（如 OpenCode 和 Pi）通过框架和模型的双重改进大步前进。”——因此，保持与时俱进需要“一个持续实验、构建和学习的过 程”，而不是一门学一次就够的技术。

这项技能背后的工作流：规划、执行、部署

在列出五项子技能之前，吴恩达先勾勒了它们共同服务的高层工作流——这一总结来自他对数十位顶尖 AI 工程师的访谈，以及对自己团队的观察：

  • 规划——先进行头脑风暴（调研、实验、理解现有代码库），然后撰写一份涵盖需求、技术设计和架构的规格说明，接着生成执行计划。吴恩达建议明确审查该计划：审视关键假设、检查安全漏洞，并警惕过度工程化。
  • 执行——构建、测试和验证，并在“Agent 自主性与人类监督之间取得恰当的平衡”。这分为两部分：(i) 让 Agent 以经过校准的自主程度进行构建，以及 (ii) 通过自动化检查和/或人工检查来验证其输出。
  • 部署与监控——进行部署，“或许通过 CI/CD 流水线或额外的人工关卡加以控制”，然后使用 Agent 来监控日志、发现问题，并提出并执行改进。

吴恩达明确指出，这看起来像是 Agent 出现之前的软件开发生命周期，这是有原因的——它本来就是同一个生命周期。变化的是精力的投入方向：“我们把精力更多地放在决定构建什么、设计架构、编写规格说明以及验证输出上，而不是代码本身。”每个步骤的时长因项目而异，步骤可能被跳过，而且——这也是他在最后反复强调的一点——“这个工作流是高度迭代的，有经验的开发者知道何时应该根据后续步骤的反馈返回到更早的步骤。”

五项子技能

1. 引导工作流。这是驾驭上述三个步骤的元技能：决定每个步骤中人工与 Agent 各投入多少精力、何时迭代回更早的步骤，以及理解每种选择在速度、成本、风险和人工投入上的权衡。这是将其他四项子技能串联起来的关键——它是一种关于何时运用其他技能的判断力，而非某种具体技术。

2. 赋予 Agent 自主性。为每个任务选择合适的自主级别——交互式来回协作、委派一大块工作，或循环执行直至成功——此外还要在各构建阶段谨慎管理上下文，决定何时通过编排并行运行多个 Agent（explainx.ai 在其 Claude Code 子 Agent 与多 Agent 工作流指南中涵盖了同样的内容），在并发会话中管理人的注意力，并通过权限和关卡安全地运行 Agent，以限制泄露、数据丢失或损害的风险。

3. 审查工作成果。设计与任务相匹配的测试和验证——包括行为和功能两方面——让 Agent 提供截图作为证据，使用评测集和 LLM 作为裁判进行定性检查，决定将多少审查工作自动化，使用 Agent 化的代码审查以及 AI 安全/架构审计，审慎地插入人工审查，并验证部署情况，同时借助 Agent 将监控和事件管理落地为日常运营。

4. 定制 Agent 及其环境。集成 Agent 技能、插件和 MCP 服务器，并在过时后予以精简；使用钩子（hooks）自动化可重复的步骤（代码审查触发器、CI/CD）；维护常驻上下文——吴恩达特别点名了 AGENTS.md 和 CLAUDE.md——其中包含代码库信息、架构、风格和数据访问模式（参见 explainx.ai 关于 AGENTS.md 和 CLAUDE.md 等 Agent Markdown 文件的指南）；在会话之间和并行 Agent 之间保存状态；通过运行后复盘积累经验；设定约定使代码库便于 Agent 导航；并在团队的各个 Agent 之间协调上下文。

5. 编码 Agent 基础。 理解 Agent 实际上如何进行代码库搜索与检索、如何管理上下文窗口、添加工具或 MCP 服务器等操作如何影响上下文、Agent 与子 Agent 如何交互，以及如何通过在 LLM 外包裹一个框架来构建 Agent。吴恩达在这里的观点是实用性的，而非学术性的：这些基础知识“揭开了 Agent 的神秘面纱”，帮助你识别失败模式——过度工程化、因缺乏显式验证而失去严谨性、半途而废、危险的破坏性操作——并帮助你引导 Agent，及时发现它何时偏离了轨道。

吴恩达对“设置好就不管”的驳斥

结尾的论述是这篇文章最值得引用的部分，它直指 explainx.ai 曾从另一个角度报道过的一种叙事：吴恩达说，社交媒体“常常把编码 Agent 的使用过度简化”。让 Agent 自主运行数小时、消耗数百万 token，有时确实有用——但“超长周期任务的实际效用——尤其是相对于成本而言——被过度炒作了”。他的结论是：“最有效的编码 Agent 使用方式是一个复杂、高度迭代的过程，高水平的人类判断与干预比‘设置好就不管’能带来好得多的结果。”

吴恩达所描述的这种权衡，在 explainx.ai 自己的报道中已经有一个直接的、量化的例子。当一个未发布的 Claude 研究模型将黎曼猜想下界从 41.6% 推进到 67.2%时，它在两次会话中动用了大约 60 个子 Agent 和 3100 万输出 token——而且过程中探索的 650 个思路都以失败告终。这并不是对那次运行的批评（结果确实很有价值，仅输出计费就约 310 美元），但这正是吴恩达提醒开发者需要预算考虑的比例：长周期、高 token 消耗的 Agent 工作回报并不均衡，大部分花费都投入到了行不通的路径上。吴恩达的论点是，这只是例外情况，而不是在典型工程任务中值得追求的默认模式——在这种任务中，由人类指导的更短、经过审查的迭代，胜过让 Agent 无人监督地循环运行数小时。

吴恩达在结尾将这项技能定位为让工程师能够掌控整体构建——“更多内容将在未来的文章中呈现。”

人们在问什么

这是否只与头衔是“AI 工程师”的人相关？ 不是——吴恩达明确区分了这一点。他刻意谈论的是“AI 工程技能”，而不是“AI 工程师”这一角色，并直接与云技能作类比：如今每个开发者都需要使用云，但只有少数人拥有“云工程师”的头衔。他的主张是，无论名片上写的是什么，全栈工程师、数据工程师、DevOps 工程师和机器学习工程师都需要掌握这四项技能。

提示词工程在这其中处于什么位置？ 它并没有单独成为一个类别——它是技能 #1（构建 AI 应用）的一个子组成部分，而且还是相对较小的一部分。吴恩达的框架更看重软件工程基础和产品判断力，而不是提示词技巧，这对于任何把“学会更好地写提示词”当作 AI 技能提升全部内容的人来说，都是一种有益的纠正。

这与单纯的“用 AI 学编程”有何不同？ 四项技能中的三项——软件基础、Agent 编排和塑造构建过程——明确关乎判断力和引导能力，而不是让 Agent 产出代码的具体机制。吴恩达贯穿全文的观点是：工作中代码生成这部分正在最快地商品化；仍然稀缺的部分，恰恰是那些需要对权衡取舍、优先级和节奏做出人类判断的部分。

我实际应该怎么做？ 把它当作一次自我审视，而不是一份阅读清单。针对这四项技能，诚实地问问自己哪一项最薄弱——来自传统软件背景的开发者大多在 #2 上很强，而在 #1 和 #4 上较弱；来自纯提示词背景的开发者则正好相反。explainx.ai 的 训练营课程 正是围绕这一差距构建的：将构建模块知识（LLM、RAG、评测）与软件工程素养和 Agent 编排实践相结合，而吴恩达的研究表明，雇主实际筛选的正是这些能力。

后续还会有更多内容吗？ 会——吴恩达表示这篇文章只是一个初步的综合，关于四项技能中每一项的更多细节即将推出。目前已经发布了三篇后续文章：第一部分：构建和部署 AI 应用（8 月 21 日）、第二部分：软件工程基础（8 月 29 日），以及上文提到的 9 月 4 日关于使用编码 Agent 的深度解析，吴恩达还表示会有更多内容。explainx.ai 将持续跟踪并报道每一次扩展。

核心要点

吴恩达这一框架最有价值的地方不在于清单上的任何单项技能——而在于其排序。四项技能中的三项（基础、Agent 编排、塑造构建过程）关乎在一个你无法完全掌控的系统下做出判断，而不是更快地产出更多代码。这与 前沿部署工程 岗位一整年来所奖励的能力完全吻合：不是原始产出，而是知道该构建什么、引导 Agent 正确地构建它，并识别出 Agent 所做的权衡何时是错误的。如果你正在决定接下来在 AI 领域学什么，吴恩达基于数据的答案很明确：少花时间寻找完美的提示词，多花时间打好基础、培养判断力——正是这些让 Agent 的输出从一开始就值得信赖。
