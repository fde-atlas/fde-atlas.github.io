接手烂尾项目怎么办：FDE 第一周接管清单

FDE Times · 2026-11-15 · 约 6 分钟读完

摘要

这篇指南面向接手前任外包方留下的烂尾项目的 FDE，主张第一周不要急于改代码，而是交付三样东西：资产归属清单、生产基线和书面评估。文章引用 Thoughtworks、Wavect、Redwerk 等来源，说明如何盘点域名、云账号、API 密钥等资产的归属与找回路径，如何用带时间戳的指标区分新旧故障，以及为何应以数据库而非文档为准。重建决策应基于证据：多数代码只需重构，只有架构性缺陷才值得重建。最后强调评估须由掌握预算的客户签字，并给出常见错误清单与简历建议。

要点

  • 第一周目标是业务照常运转，不做任何改进。
  • 先盘点资产归属，每个“未知”都是具体风险。
  • 改动前先记录基线，才能分清新旧故障。
  • 文档与系统不一致时，以数据库为准。
  • 重写是基于证据的结论，多数代码只需重构。

该重建什么，应由资产归属清单、生产基线和书面评估决定，而不是凭直觉。

要点速览

  • 第一目标是让业务照常运转，暂时不追求任何改进。
  • 先看真实系统，再看文档：两者不一致时，以数据库为准。
  • 全面重写是基于证据得出的结论；大多数继承下来的代码只需要重构。

周一，你来到客户办公室。前任外包方已经离场，留下一个代码仓库、几个似乎没人知道密码的云账号、一条只能跑一半的流水线，还有一群追问“什么时候能做完”的管理层。所有人最想先知道的是：要不要全部推倒重来？

从这里入手就错了。AI Codex 一篇讨论范围界定的文章指出，大多数走偏的前线部署工程师（FDE）项目，在第一周结束时就已经偏了。接管项目时，第一周的分量更重：你接手的不只是系统，还有客户在一段半途而废的合作之后残留的疑虑。

下文逐一拆解前五天：先盘点现有家底，再敲定一份重建清单，并且能用数字向客户说明理由。

第一件事不是修

Thoughtworks 在介绍一次大型遗留系统接管时，特意把近期目标定得很低：至少保证业务照常运转。不做改进，不做优化，只求不弄坏已经在跑的东西。

道理听起来显而易见，但现场的压力往往反其道而行。客户想看到进展，而“展示进展”最快的办法就是提交代码。问题在于，在理解系统之前做的每一次改动都是赌博；一旦出事，账会记在你名下，而不是前任外包方名下。

所以第一周要交付三样东西：资产归属清单、生产基线和书面评估。重建清单从这三样里产生。

钥匙到底在谁手里？

Wavect 的 30 天接管计划要求，在第 1 到第 5 天，为每项资产记录：账号的法定归属方、付费方、管理员、找回联系人以及移交路径。

这里的资产指一切：域名、云账号、代码仓库、第三方 API 密钥、邮件发送账号，甚至任务跟踪工具的工作区。

假设有一家物流客户，前任外包方给它留下一套做了一半的订单分拣系统。第二天结束时，清单可能是这样的：

资产 法定归属方 付费方 管理员 找回方式 移交路径
主域名 客户 客户 前任外包方 外包方邮箱 通过注册商更换管理员
云账号 前任外包方 前任外包方，再转账给客户 前任外包方 未知 转移账号或重建
代码仓库 客户的组织 客户 外包方两名开发者 客户 移除旧权限，加入新团队
LLM 服务 API 密钥 未知 外包方的信用卡 未知 未知 需要核实

每个“未知”格子，都是一个现在能叫出名字的具体风险。这个例子里中间两行比任何烂代码都危险：一旦外包方停止支付云账号费用，系统就会停摆，而客户那边没有任何人有权限把它重新打开。

开始轮换密码和访问密钥时，Wavect 提醒了一个容易忽略的点：回滚权限必须掌握在客户手里。不要变成下一个“前任外包方”，成为唯一握着钥匙的人。

先测量，再改动

第二项交付物是基线。Wavect 列出了任何改动之前需要记录的指标：流量、错误率、延迟、队列深度、备份状态、未关闭的故障、工单量，以及已知版本的发布状态。

目的是日后能分清哪些故障是你造成的，哪些是继承来的。假设这套订单分拣系统有 4% 的请求失败。

如果没有测量，你周四上线第一个补丁，客户下周看到 4% 的错误率，就会问你为什么把系统弄坏了。有了带时间戳的基线，你可以指着数字说：系统本来就是这个水平，这是把它降下来的计划。

基线也是此后所有价值讨论的基础。没有起点，谁也证明不了改进了多少。

相信数据库，而不是文档

前任外包方通常会留下文档，而文档通常比现实好看。AI Codex 建议先申请真实系统的只读权限，再要文档：文档描述的是意图，数据库描述的是现实，两者不一致时，以数据库为准。

在物流的例子里，文档可能写着每个订单都会自动分拣。而一条按状态统计订单数的查询可能显示，有很大一部分订单卡在等待人工审核的状态。这个落差恰恰是客户花钱要解决的问题，却没有出现在文档的任何一页上。

dev.to 上一篇关于从外包公司手里接管代码库的指南建议，头 48 小时只读不动。这段时间里，先读代码、日志、提交历史和数据库 schema，再碰任何东西。

为了把握全局，Thoughtworks 用 C1/C2 图画出继承下来的架构，并在一张地图上跟踪接管进度：已完成的服务标绿色，待处理的标灰色。

这样一张图，也是每周五下午向客户汇报的最佳工具。

用标准而不是感觉敲定重建清单

到第四天，你手上的数据已经足以给每个组件分类。Wavect 写道，“全部重写”是结论，而不是起步的方法。

Redwerk 给出了更明确的规则：架构合理、只是细节混乱时就重构。关于继承代码的大多数决策最终都是重构，因为代码写得乱远比真正坏掉常见得多。

套用到例子上：如果从订单系统到分拣器的数据流向正确，只是代码重复、缺少测试，那就重构。

如果分拣器不经队列直接写入生产数据库，每次出错都会丢订单，那就是架构问题，有理由重建这一部分。

两个组件，两种结论，而不是对整个系统一句“推倒重来”。

Thoughtworks 用一份标准模板作为接管每个服务的验收标准。你也可以照做：一个服务只有在满足以下条件后才能变“绿”——每项资产的归属方已明确，有基线，新团队中有人能部署和回滚，并且已被归入保留、重构、重建三类之一。

书面评估，以及由谁签字

dev.to 的指南说得很坚决：改动任何东西之前，先写一份文档。第五天的评估包括资产清单、基线、服务地图，以及附带每项理由的分类清单。

但文档如果到了错的人手里，也不够用。AI Codex 建议坚持推动，直到拿到一个可衡量的成功定义，并且由掌握预算的人认可。

在物流的例子里，这个定义可能是“需要人工审核的订单比例在 Y 周内降到 X”，X 和 Y 由客户根据你刚测出的基线来定。

预算负责人一旦签字，重建清单就不再是你的个人意见，而是双方的共同承诺。

常见错误

最常见的错误，是第一天就动手修东西来“刷存在感”，事后却无法证明系统原来有多糟。其次是轻信交接文档，不打开数据库看一眼。

另一个常见错误，是轮换了所有凭证，却把管理员权限留在自己手里，恰好重蹈了你受雇来解决的那个问题。最后一个，是和最好说话的用户敲定范围，而不是和掌握预算的人。

接管能力值得写进简历

浏览 FDE 招聘启事时，留意那些提到在客户现有系统上工作的描述：接管能力正是在这类场景中派上用场，也值得在简历里放一个具体案例。

本周练习：挑一个你在维护但不是你搭建的系统，假设它的外包方明天早上就消失，用一个下午写出一页评估。你数出的“未知”格子数量，就是客户在不知情的情况下承担的风险。
