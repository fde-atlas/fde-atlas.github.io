计算机网络自顶向下方法怎么读：FDE 用 Wireshark 排查网络

FDE Times · 2026-11-15 · 约 5 分钟读完

摘要

文章面向 FDE，介绍如何有选择地阅读 Kurose 与 Ross 的《计算机网络：自顶向下方法》第 9 版，并配合免费的 Wireshark 实验排查客户网络问题。作者建议优先读第 2、3、8 章，其余章节按需再读，并给出用 DNS、TCP 重传、TLS 握手三个过滤条件逐层定位“API 慢”问题的实操流程，还提醒了常见错误和简历写法。

要点

  • 第 9 版由 Pearson 于 2025 年夏季出版，新增 HTTP/3、QUIC 与 TLS 1.3。
  • FDE 优先读第 2、3、8 章，第 5、7 章等用到再读。
  • 用 dns、tcp.analysis.retransmission、tls.handship 三个过滤条件逐层排查。
  • 应在客户真实网络路径上抓包，并避免凭单次抓包下结论。
  • 作者免费提供的 Wireshark 实验把书本知识转化为动手技能。

要点速览

  • Pearson 于 2025 年夏季出版第 9 版，新增 HTTP/3、QUIC 和 TLS 1.3
  • 对 FDE 来说，第 2、3、8 章优先；第 5、7 章可以等用到时再读
  • Wireshark 实验对所有人免费开放，正是它把知识变成技能

客户说每次 API 调用都要好几秒。你的服务器日志却显示，请求几十毫秒就处理完了。时间耗在了链路上的某个地方，而大家等着你说出究竟在哪里。

对前线部署工程师（FDE）来说，这样的时刻并不陌生。你在别人的网络里工作，面对的是别人的代理、证书和 Wi-Fi，也没有基础设施团队替你接手问题。许多习惯在应用层工作的工程师，可能也是头一回需要仔细查看一个个数据包。

James F. Kurose（UMass Amherst）和 Keith Ross（NYU Abu Dhabi）合著的《计算机网络：自顶向下方法》（Computer Networking: A Top-Down Approach）并不是为 FDE 写的。但只要挑对章节，再配上作者免费向教师、学生和读者提供的 Wireshark 实验，它恰好能提供那个下午所需要的一切。

自顶向下，正好对应客户抱怨的顺序

第 9 版于 2025 年夏季面世，Pearson 标注的发布日期是 2025 年 6 月 20 日，可在线阅读、租借或购买纸质版。全书八章，从“计算机网络和因特网”一直到“计算机网络中的安全”。Pearson 对这种写法的描述是：自顶向下地呈现这门复杂的学科。

这种自顶向下的顺序，正是这本书适合 FDE 的原因。客户从不按网络分层报告故障，他们只报告自己看到的现象：页面打不开、请求卡住、浏览器弹出红色的证书警告。从应用层开始逐层向下，正是优秀的调试者提出问题的方式。

大多数事故从第 2、3 章开始

第 2 章（应用层）在这一版中更新了 HTTP/3 和 QUIC 的内容，排查客户的 Web 或 API 流量之前应先读这一章。第 3 章（传输层）更新了拥塞控制一节，并补完了第 2 章开头的 QUIC 内容，所以这两章最好连着读。

这两章几乎涵盖了“API 慢”问题中那几秒钟可能消失的所有地方：域名解析、连接建立，以及传输途中的丢包。最有效的用法，是直接把它们带进一次抓包分析。

用 Wireshark 追查“API 慢”问题

在客户许可的前提下，在出问题的机器上抓包，同时复现一次 API 调用。然后忍住，不要一下子看整个抓包文件。按书中讲解的顺序，逐层过滤。下文的数字只是举例说明糟糕的结果可能是什么样，并非标准阈值。

第一步，输入过滤条件

dns

，对比每个查询的发出时间和响应时间。

假设一次正常查询约 20 毫秒就能得到响应，但客户的抓包显示查询被重发了两次，响应在 1.5 秒后才到达。大部分延迟在 HTTP 开始之前就已经发生，这属于第 2 章的范畴。

第二步，按

tcp.analysis.retransmission

过滤，让 Wireshark 只显示重传的报文段。假设一次调用由 400 个报文段组成，其中 40 个被重传，即 10%。说明途中有数据包在丢失，而第 3 章给了你解释连接为何随之被限速的语言。

如果只看到零星一两行，问题很可能出在别处。如果按

tcp

过滤几乎什么都没有，试试

quic

，因为连接可能走的是 HTTP/3。

第三步，按

tls.handshake

过滤，看握手进行到了哪一步。如果客户端发出最初的 hello 后等了好几秒都没有回应，或者握手以错误告警结束，你就找到了断点。只有这三步都没有问题，才需要去测量从发出请求到收到响应首字节的时间。

到这一步，你对客户说的话就不一样了。与其说“我查一下”，你可以说“请求到达服务器之前，你们的连接在反复重传数据包”。前一句是在争取时间，后一句指向了解决办法。

这里有三个容易犯的错误：

  • 在自己的笔记本上抓包，而不是在客户真实的网络路径上抓，结果抓包看起来一切正常，客户那边却依然很慢。
  • 只凭一次抓包下结论，而问题可能只在网络高峰负载时出现。
  • 还没检查 DNS 就归咎于“网络”，尽管 DNS 是排除成本最低的一项。

故障出在握手时，读第 8 章

第 9 版的第 8 章（安全）新增了 TLS 1.3 和 WPA3，客户环境中证书或握手出错时，用得上的就是这部分内容。先读懂一次正确的握手如何进行，再去找它在哪里断掉。

剩下两章值得了解，但可以往后放。第 5 章（网络层：控制平面）新增了 SDN 的内容，并以 Google 的 Orion 网络控制系统作为案例研究，在你需要处理客户的路由或云网络时会有帮助。

第 7 章（无线网络和移动网络）是这一版改写幅度最大的一章，涵盖 Wi-Fi 6 和 5G。当问题出在客户自己办公室的 Wi-Fi 或移动网络时，再翻开它。

Wireshark 实验把阅读变成实践

作者的实验页面写道，观察协议实体之间交换报文的基本工具是分组嗅探器。这些实验教的正是这项技能，覆盖 HTTP、DNS、TCP、UDP、IP、NAT、DHCP、ICMP、以太网和 ARP、802.11 Wi-Fi、5G 以及 TLS。

它们不只是应试练习。Wireshark 官方文档说，网络管理员用它来排查网络问题。你在家练的技能，用的就是你将来在客户机器上打开的同一个工具。

对 FDE 来说，合理的顺序是：读完第 2 章做 HTTP 和 DNS 实验，读完第 3 章做 TCP 实验，然后跳到第 8 章，做 TLS 实验。第 1 章略读，了解整体框架即可，其余章节等项目需要时再读。

值得记住的三点，以及怎样写进简历

合上书之后，有三点值得带到现场。一是自顶向下排查，从客户能看到的现象入手。二是书中在应用层和传输层两章都讲了 QUIC，所以排查 QUIC 故障时不要只盯着一处。三是先用分组嗅探器观察，再做推测。

职业方面，简历上写一句“懂网络”说服不了任何人。从个人项目中抓取一次真实的 API 调用，用上面三个过滤条件逐一分析，写一页说明，讲清每一步花了多长时间，然后放进作品集。

浏览 FDE 招聘启事时，留意那些提到客户网络环境、VPC 或企业代理的岗位描述：这样的分析在那里最能让你脱颖而出。

下次客户再说“API 很慢”，打开抓包文件，让他们看清时间都花在了哪里。
