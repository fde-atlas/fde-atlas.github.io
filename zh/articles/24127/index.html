Palantir Pipeline Builder 是什么？功能与在 FDE 中的使用方法

原标题：Palantir Pipeline Builderとは？機能とFDEでの使い方

FDE総研 · 2026-10-29 · 约 9 分钟读完

摘要

这篇文章介绍 Palantir Foundry 的数据集成工具 Pipeline Builder：它让用户在 GUI 上完成从数据清洗、转换到写入 Ontology 的流程，且支持分支、变更提案、数据质量检查等生产级运维能力。文章对比了它与基于 Python/SQL 的 Code Repositories 的差异，并从 FDE 视角说明其在导入初期快速验证需求、以及最终向客户交接中的作用。

要点

  • Pipeline Builder 在 GUI 上完成数据转换并直接输出到 Ontology。
  • 支持分支、提案、质量检查与增量、流式处理，可用于生产环境。
  • 与 Code Repositories 互补：前者易读易共享，后者表达力强。
  • FDE 用它与客户同屏验证数据，快速交付可运行成果。
  • 选型时应考虑客户后续能否自行维护，便于交接。

什么是 Palantir Pipeline Builder？在 Foundry 中的角色是什么？

Pipeline Builder 是 Palantir Foundry 中的一款数据集成工具，可在 GUI 上完成从数据导入、转换到输出至 Ontology 的全流程搭建。

在 Foundry 中，原始数据（ERP、传感器、文件等）经过转换后流入 Ontology（业务对象模型），供应用程序和 AIP 使用。Pipeline Builder 负责这一流程中的“转换”环节。Palantir 官方文档（Foundry › Pipeline Builder）将其介绍为一款让技术人员与非技术人员在同一屏幕上协作的数据集成应用程序。

Pipeline Builder 处于怎样的定位？

其特点是无需编写代码即可搭建转换处理，同时可作为生产级别的管道进行运维。

所谓的无代码工具往往被视为仅适用于原型开发。但用 Pipeline Builder 构建的管道会在 Foundry 的构建平台上定期运行，并纳入数据血缘（数据来源追踪）和分支管理的范畴。由于数据的“来源”和“去向”都显示在同一张图上，业务部门的负责人也能确认处理内容。在 FDE（Forward Deployed Engineer）的实际工作中，这种“可以展示并达成共识”的特性，往往是选择该工具的重要原因。

它承担 Foundry 数据流中的哪个环节？

Pipeline Builder 承担“原始数据 → 整理后的数据集 → Ontology”的中间层，也可以直接写入 Ontology。

层级主要作用相关的主要 Foundry 应用
导入从外部系统同步数据Data Connection
转换清洗、合并、汇总Pipeline Builder / Code Repositories
语义化定义业务对象与关联关系Ontology Manager
应用业务应用、分析、AIPWorkshop / Quiver / AIP Logic 等

从 FDE 的角度来看，Pipeline Builder 是将客户数据转化为“业务可用形态”的第一道关口。在项目初期的几周内能准备好多少可信数据，往往会影响后续应用开发的速度。

Pipeline Builder 的主要功能有哪些？

主要功能包括可视化转换、类型检查、预览、分支与评审、数据质量检查、Ontology 输出这六项。

Pipeline Builder 有许多细致的功能，聚焦到 FDE 实务中常用的部分，可以整理如下。

转换与预览类功能有哪些？

可将合并、过滤、汇总等转换作为节点连接起来，边实时预览各步骤的结果边进行搭建。

功能内容实务中的应用场景
转换节点在 GUI 中放置 Join、Union、Filter、Aggregate、Pivot、类型转换等主数据合并及匹配的前置处理
表达式（Expression）组合函数对列进行计算日期标准化、代码值转换
预览用样本即时确认各节点的输出与客户一起边看屏幕边验证
类型检查在构建前发现 schema 不一致尽早察觉上游列的变更
LLM 转换将 AIP 的 LLM 作为转换步骤嵌入自由文本的分类与抽取
UDF用代码补充标准函数无法实现的处理部分实现自定义逻辑

尤其是类型检查在实务中非常有效。错误会在编辑阶段就显示出来，而不是在运行构建之后才发现失败，从而减少返工。

运维与治理类功能有哪些？

它具备分支、变更提案（Proposal）、数据质量检查、定时执行等功能，是为生产运维而设计的。

  • 分支：在不影响生产环境的情况下尝试变更，验证后再合并
  • Proposal：以差异形式展示变更内容，经评审和批准后生效
  • 数据质量检查（Expectations）：在构建时检查主键唯一性、NULL 比率等
  • 调度：以上游数据更新或时间点为触发条件执行构建
  • 输出目标选择：可选择数据集、Ontology 的对象类型或关联类型等

处理方式不仅支持批处理，还支持增量（差量处理）和流式处理。由于可用的转换范围因处理方式而异，最新的支持情况请以官方文档为准。

与 Code Repositories 有何区别？如何区分使用？

Pipeline Builder 的优势在于速度和易于共享，Code Repositories 的优势在于表达能力和精细控制，多数情况下两者会结合使用。

Code Repositories 是 Foundry 的开发环境，可以用 Python（PySpark）、SQL、Java 等语言将转换以代码形式编写，并基于 Git 进行管理。虽然同样承担“转换”工作，但两者的擅长领域不同。

在功能方面有什么区别？

最大的区别在于“谁能看懂、能写到什么程度”：可读性方面 Pipeline Builder 更优，自由度方面 Code Repositories 更胜一筹。

视角Pipeline BuilderCode Repositories
构建方式在 GUI 中放置节点代码（Python/SQL/Java 等）
主要使用者分析师、FDE、业务人员数据工程师、FDE
上手速度快需要搭建环境和编写代码
表达能力标准转换＋UDF 的范围包括各类库在内几乎没有限制
测试以质量检查和预览为主可以编写单元测试
审查Proposal（GUI 上的差异对比）Git 的 Pull Request
与业务方的共享可以直接展示图表需要对代码进行讲解

应该依据什么标准来选择使用？

大致标准是：标准转换能处理的用 Pipeline Builder，需要复杂算法或外部库的处理用 Code Repositories。

在实际工作中，可以考虑以下判断维度。

  • 适合 Pipeline Builder 的场景：主表关联、数据清洗、汇总、导出到 Ontology。计划移交给客户侧的处理
  • 适合 Code Repositories 的场景：优化计算、自定义实体匹配算法、机器学习预处理、需要严格单元测试的处理
  • 结合使用的场景：用 Code Repositories 实现重量级计算，其输出通过 Pipeline Builder 整理后流入 Ontology

对 FDE 来说，容易忽视的是“易于移交”这一点。FDE 迟早会离开现场，因此客户能否自行维护是工具选择的重要标准。即使对工程师来说代码更便于编写，刻意选择 Pipeline Builder 的判断也有其合理性。

如何用 Pipeline Builder 构建管道？

基本流程是通过添加输入、放置转换、预览验证、设置质量检查、定义输出、部署这 6 个步骤来构建。

由于具体的界面操作会因版本而异，这里只聚焦于整体流程和关键要点进行说明。

基本的构建步骤是什么？

最小配置的流程是：选择输入数据集，连接转换节点，定义输出并进行部署。

  • 创建管道：在 Foundry 项目中新建，并选择批处理还是流式处理
  • 添加输入：选择通过 Data Connection 导入的数据集或媒体集
  • 组装转换：按类型转换 → 清洗 → 关联 → 汇总的顺序连接节点
  • 通过预览进行验证：在各节点的输出中确认行数和值的分布
  • 定义输出：将数据集或 Ontology 的对象类型设置为输出目标
  • 部署（构建）：设置调度，纳入定期执行

构建时容易踩坑的地方有哪些？

类型不匹配、关联键重复、对模式变更的跟进是三个容易踩坑的点，尽早加入质量检查可以保持稳定。

常见问题会发生什么应对方向
类型不匹配日期和数值以字符串形式流入在输入后立即放置类型转换节点
关联键重复Join 后行数膨胀在关联前去重，并设置主键唯一性检查
上游模式变更列名变更导致构建失败确认类型检查的错误，在分支中修复
逻辑膨胀图表变得难以阅读用中间数据集划分阶段

根据经验，如果省略 Join 后的行数检查，很容易导致后续仪表板出现“数字对不上”的问询。质量检查不应“以后再加”，从第一次部署起就加入才是稳妥做法。

FDE 在实际工作中如何运用 Pipeline Builder？

FDE 使用 Pipeline Builder，在与客户相同的界面上核对数据的同时快速展示价值，最终将其作为移交给客户的工具。

Palantir 的 FDE 是深入客户现场、以短周期完成从发现问题到实现落地的职位。Pipeline Builder 是与这种工作方式非常契合的工具。

在导入初期是如何使用的？

导入初期主要用于：在短时间内将客户的原始数据连接到 Ontology，展示“能运行的东西”以固化需求。

实际工作流程可以设想为如下形式。

  • 数据探索：使用预览功能，与客户一起确认数据的缺失和表述不一致问题
  • 需求对齐：一边展示转换图表，一边当场就“是否可以按这个条件筛选”达成一致
  • 首次演示：输出到 Ontology，用 Workshop 的简单界面重现业务流程

这里重要的不是完成度，而是验证的速度。能在会议中修改逻辑并立即展示结果，这是基于代码的开发所不具备的优势。

Pipeline Builder 的技能对 FDE 的职业发展有什么作用？

Pipeline Builder 的技能能够同时展示数据建模能力和业务理解能力，因此容易被视为 FDE 的基础技能而受到认可。

掌握的技能内容在 FDE 之外的转用方向
数据建模用实体和关系来把握业务数据工程师、分析工程师
数据质量设计从业务需求出发设计检查规则数据治理
达成共识用可视化的逻辑与相关方达成共识PM、解决方案架构师
交接设计构建客户能够自行维护的配置实施咨询

另一方面，仅靠 GUI 工具往往难以体现技术深度。对于以 FDE 为目标的工程师来说，比较现实的策略是同时掌握 Pipeline Builder 和 Code Repositories（PySpark/SQL），并将“能够判断该选择哪一种”作为自己的优势。

对于考虑引入 FDE 的企业决策者而言，FDE 用 Pipeline Builder 搭建的资产能否在企业内部得到维护，直接关系到合同结束后的自主运营能力。如果从引入阶段就建立起让内部数据负责人参与提案评审的机制，交接往往会更加顺畅。
