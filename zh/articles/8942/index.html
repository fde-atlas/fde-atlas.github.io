面向前沿部署工程师的 LLM 应用构建模块

原标题：LLM Application Building Blocks for Forward Deployed Engineers

The Forward Deployed · 2026-07-05 · 约 3 分钟读完

摘要

本文面向尚未接触 LLM 的工程师，重新定义 LLM 应用的本质：模型只是一个非确定性的中间组件，真正的工程在于围绕它搭建的确定性脚手架。文章指出模型两大限制——只知上下文内容、输出具有概率性——并逐一介绍六类核心构件：提示与结构化输出、检索与上下文组装、工具调用、编排（Agent）、MCP 标准接口，以及评测与运维。作者用“坏/好/优秀”三档回答示范如何在面试中描述 LLM 应用，强调应从生命周期而非模型本身切入设计。

要点

  • 模型是非确定性函数，工程重点在周边脚手架
  • 两大限制：无自身记忆、输出具概率性
  • 六大构件：提示、检索、工具、编排、MCP、评测运维
  • 面试应先讲生命周期，而非先讲模型

学习生产级 LLM 应用的核心组件，以及提示词、检索、工具、编排、评测和运维如何协同工作。

如果你是一名还没有用 LLM 构建过东西的优秀工程师，这一页会为你重新框定整个领域。你已经知道如何构建系统。新的变化在于中间的那个组件——模型——是一个非确定性函数，而几乎所有的实际工程工作都是围绕它搭建的确定性脚手架。LLM 应用不是“调用模型”。它是一个小型系统，本节将讲解它的各个组成部分。

为什么这种重新框定很重要

经典工程师的直觉是把模型当作一次库调用：输入字符串，输出字符串，完事。这种直觉能做出演示，却会在生产环境中失败，因为它忽略了中间组件的两个残酷事实：模型只知道你在本次调用中提供给它的上下文（它没有自己的记忆），而且它是概率性的（同样的输入可能产生不同的输出）。本节中的每个构建模块都是为了应对其中一个事实而存在的：把正确的信息放进上下文，并让不确定的输出变得安全且有用。

在继续阅读之前：一位用户问你的助手：“我们昨天的会上决定了什么？”模型从未见过你的会议。请说出它要回答这个问题必须发生的两件事。两者都不是“一个更聪明的模型”。

两件事：会议记录必须被检索出来并放入上下文（模型无法回忆它从未见过的内容），并且请求必须连同正确的指令一起组装。这就是检索和上下文组装，即下文模块中的两个，再高的模型质量也无法替代它们。

各个模块及其讲解位置

每个模块对应本节中的一页。它们共同构成了你在面试中设计或在客户项目中上线的每一个 LLM 应用的解剖结构。

  • 提示词与结构化输出。你问什么、如何给出指令，以及如何让输出呈现你的代码可以解析并据此行动的形状。 → 提示词与结构化输出
  • 上下文组装与检索。模型只能看到你放进窗口的内容，因此核心技能是把正确的信息放进去，最常见的方式是对客户自己的数据进行检索。 → 检索（RAG）与向量搜索
  • 工具使用。模型无法自行行动；你为它提供工具（函数、API），它可以请求你去运行，从而把一个文本生成器变成能够查询信息和执行操作的东西。 → 工具使用与函数调用
  • 编排。把这些串联成一个多步骤循环（模型规划、调用工具、读取结果、决定下一步）正是“Agent”的由来，而知道什么时候不该这么做也是技能的一半。 → Agent 与编排
  • 标准管道。 通过通用接口将模型连接到工具和数据，而不是每次都做定制集成。→ Model Context Protocol (MCP)

差 / 好 / 优秀——“LLM 应用是如何工作的？”

差——“你把用户的消息发给模型，然后返回回复。” 这是库调用的思维模型。它无法解释记忆、私有数据、操作或可靠性，而且会让面试官觉得你只是用过聊天机器人，而不是构建过。

好——“你构建一个带有上下文的提示词，调用模型，可能还会做检索。” 各个部分都在，但比较松散。差距在于：没有清晰的生命周期，没有提到工具和输出侧，也没有意识到脚手架本身就是工程所在。

优秀——“它是一个生命周期：组装上下文（系统提示词、用户输入、检索到的数据、历史记录），调用模型，处理它请求的任何工具调用——执行这些调用并把结果反馈回去——然后在返回之前应用输出检查。模型只是其中一个非确定性步骤；围绕它的检索、工具和评测才是应用本身。” 你描述了一个系统，指出了记忆和操作的来源，并把工程放在了它真正所在的地方。

面试中要带上的要点

当设计题以“构建一个 AI 助手，它……”开头时，不要一上来就谈模型。先从生命周期讲起：你要组装什么上下文、从哪里来，需要哪些工具，返回前要检查什么，以及你如何确认结果是对的。说出这些模块，并把模型当作你工程化的系统中的一个组件——这是构建过 LLM 应用的人和只是调用过 API 的人之间的区别。
