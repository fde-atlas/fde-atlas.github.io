前沿部署工程的肮脏秘密

原标题：The Dirty Secret of Forward Deployed Engineering

AI Engineer · 2024-07-11 · 约 9 分钟读完

摘要

Natalie Meurer 在 AI Engineer World's Fair 2026 的演讲中提出，FDE 这一头衔并不对应一个边界清晰的学科。她以自己在 Palantir（2016 至 2021 年）和 Sierra 的经历，梳理了该角色职责的累积过程：从保障平台稳定、数据集成、构建定制方案，到培训客户自行使用软件。不同时期入职的 FDE 实际做的工作差异很大，招聘时只看头衔意义有限。贯穿始终的共同点是对客户结果负责。随着编码 Agent 降低写代码的成本，产品工程与客户工作正在融合，Sierra 等公司推动按结果定价，其可行性取决于产品的自主性与结果可归因程度。她的结论是：狭义的 FDE 正在消失，但对客户结果负责的工程文化正在扩散到整个工程组织。

要点

  • FDE 头衔涵盖多种工作，并非单一学科。
  • Palantir 时期职责逐步累积：稳定、集成、方案、赋能。
  • 共同主线是对客户结果负责，而非特定技术栈。
  • 编码 Agent 使产品工程与客户工作互相靠近。
  • 按结果定价依赖自主性与可归因性两个维度。

前沿部署工程的肮脏秘密

前沿部署工程从维持客户部署系统的运转，发展到交付客户成果。如今，编码 Agent 正在把这份责任带回产品工程本身。

你雇用前沿部署工程师是为了做什么？

你是一名前沿部署工程师，还是正在雇用一名？Natalie Meurer 以这两个问题开场。它们指出了同一个问题的两面：工程师和雇主正在使用一个头衔，但其职责在不同团队之间可能差异巨大。

Meurer 以 Sierra Agent 工程负责人的身份探讨这个问题，她在公司工作了大约两年。她的职业道路始于乔治城大学外交学院的科技政策，随后学习编程并加入 Palantir。2016 年至 2021 年，她从事隐私、基础设施和前沿部署工作，主要面向执法和国防客户。在斯坦福大学完成商科学习后，她于 2024 年加入 Sierra——当时所在的团队名为部署团队。

这个名字让她困扰，因为它没有描述团队实际在构建的东西。2024 年 7 月，也就是加入约六个月后，她发表了 Meet the AI agent engineer。她最初的区分是有用的：Agent 工程是 AI 工程的一个子学科，与前沿部署工程一样对客户负责，但拥有自己的技术领域。随着 Agent 工程的流行，harness 工程开始作为其中一个可能的专业方向而兴起。相关词汇不断扩张。

这种泛滥引出了演讲的核心论点：前沿部署工程“并不存在”。这项工作当然存在；问题在于这个标签涵盖的工作种类太多，以至于不再指代一个连贯的学科。它在 AI 领域的流行使这种模糊性变得更加严重。要理解前沿部署工程师究竟做什么，就要追踪这个头衔下积累起来的各种职责——从平台运营到客户成果。

首先，让客户的部署系统保持运行

2016 年吸引 Meurer 的 Palantir 招聘启事把工作地点放在首位。当代的工程类招聘广告可能会强调编程语言和技术技能，而这些启事强调的是前沿部署部分：与客户坐在一起，驻扎在现场。Palantir 的生态系统很大一部分是本地化部署，因此物理上的接近是交付软件的一部分。

漫画中的刻板印象是：一名应届毕业生从直升机上空降下来，同时还在修复运行时错误。这份工作的早期形态更接近于人们熟知的 DevOps：平台稳定性占据了大部分工作内容。Meurer 自己的入职任务就是在 EC2 实例上部署 Palantir 的软件。在工程师能让产品发挥作用之前，安装必须先跑起来。

她引用的一封典型客户邮件体现了当时的运维现实：有人又把实例的电源拔了，工程师得凌晨两点赶到现场。最初，对客户负责就意味着恢复可用性。产品眼前的瓶颈不是再增加一个功能，而是一套能正常运行的系统。

稳定的平台仍然需要数据

回顾 Meurer 时间线中 2012 年前后，平台稳定性的提升暴露了下一个问题。Palantir 卖的是数据集成软件，但没有集成数据的软件就像一家什么电影都不放映的电影院。在这个类比中，2008 年时这家影院还没建起来；到 2012 年，影院建好了，却没有电影可看。

客户面对一个能正常运转的平台，反应是数据仍然分散在 20 个不同的地方。前沿部署工程师必须把这些数据源连接起来。大部分集成工作使用的是 Java 的各种变体；Meurer 还记得 Palantir 的客户端是用 Java Swing 编写的。此时的工作内容变成了 DevOps 加数据集成，而不是用一个新的专业取代运维。

集成还需要理解这些记录在客户环境中的含义。Meurer 在这里把 Palantir 的 本体（ontology） 描述为数据的分类体系。例如，一个数据源把客户键称为

customer_id

而另一个数据源则称之为

account_id

。要把两者映射到同一个客户对象上，就需要理解它们是否真的指向同一个业务实体。贴近客户对于这一判断以及部署本身都很重要。

把集成好的数据变成人们能用的东西

到 2016 年，定制化解决方案又增加了一项职责。工程师为已知的客户问题构建应用程序，通常是以 Slate 仪表盘的形式。Meurer 把 Slate 描述为一个拖拽式构建工具，类似于 Retool，它把页面上的组件映射到数据源。一旦数据可用，下一个问题就是如何让它发挥作用。而理解这些数据的工程师正处在回答这个问题的最佳位置。

在她的叙述中，Slate 时代让位于 Foundry，重心也扩展到从数据到决策的转化。这一演进暴露了仪表盘的一个局限：展示信息并不一定能完成客户的工作流程。Meurer 的经验教训是，没有写回数据源功能的仪表盘会逐渐失去价值。一个有用的运营应用必须支持对数据采取行动，而不仅仅是查看数据。

通过培训客户来扩大工作规模

大约在 2020 年，随着 Palantir 临近 IPO，把工程师派往芬兰、堪培拉或其他每个客户所在地已不足以支撑规模化。客户需要自己完成更多工作。赋能由此成为该角色的另一部分，与平台稳定性、集成和定制解决方案并列。

Meurer 提到 Airbus 的 Skywise 项目，该项目使数千名 Airbus 工程师能够在 Foundry 上执行前沿部署工程工作。这是她对赋能工作的描述，而非经过测量的培训成果。她还指出在她离职后推出的 AI FDE，即利用大语言模型完成类似工作。AIP 训练营则代表了同一演进中的教学一面：前沿部署工程师或部署策略师帮助客户学习软件。她举了 Alex Karp 主持训练营的例子。

这些是相互重叠的职责，而非界限分明的时代更替。工作内容总量不断增加，造就了 Meurer 所认为的通才式训练，正是这种训练帮助 Palantir 的前员工成为创始人。对于招聘而言，这提示了一个比“某人是否拥有过该头衔”更有信息量的问题：他们是哪一年代的 FDE？

Meurer 叙述中的年代强调的职责
2008平台稳定性
2012数据集成
2016定制解决方案
2020客户赋能

她的葡萄酒类比给最早年代贴上了“一丝恐慌”的标签。这些年份和界限可以商榷；其实际价值在于区分候选人实际做过的工作。仅凭头衔无法判断一个人最强的经验是运营部署、数据建模、构建应用，还是培训客户。

共同的主线是对客户负责

到 2026 年，这一头衔已遍布 AI 行业。Meurer 提到 GCP 招聘客户工程师或 FDE、OpenAI 的企业部署推进——以 OpenAI Deployment Company 公告为代表——以及 Aaron Levie 关于这项工作重要性的帖子。但需求的普遍存在并不意味着这份工作已成为单一学科。

她那则讽刺性的拼贴式招聘启事要求应聘者拥有八年资深工程师经验、六年直销经验、四年解决方案架构师经验，最好还有教学经验。它揭示了招聘过程如何把累积的职责变成一个不切实际的候选人要求。在亲自招聘部署类岗位大约两年到两年半之后，Meurer 也理解了让一个人承担所有这些职责的压力。

无论职位描述如何变化，对客户负责始终是不变的内核。 无论是恢复可用性、集成数据、构建定制解决方案，还是帮助客户上手，工程师的职责都是让软件真正为某人所用。这种共同的责任比任何特定的语言、框架或部署位置都更能解释这个角色的本质。

更廉价的代码让产品工作与客户工作走到一起

当工程师可以通过提示一个后台编码 Agent 并快速获得有用的代码时，这种分工会发生什么变化？前沿部署工程师早已在把客户信号转化为产品需求：更高的稳定性、更好的集成，或某个缺失的工作流。编码 Agent 延展了他们针对这些信号采取行动的能力。他们可以超越对话和原型，构建端到端的解决方案。

Meurer 报告了 Sierra 的一种互补性变化：产品工程正变得更加面向客户。这两种角色从相反的方向接近同一种关系。前沿部署工程师把对客户的理解带入产品；产品工程师则越来越多地把产品专业知识直接带给客户。无论身处哪种角色，优秀的工程师都需要把两者结合起来思考。

这种融合增加的是职责，而不是让运营性工作消失。产品工程师——以及基础设施工程师——仍然需要理解软件是如何部署的。与此同时，更廉价的代码改变了商业问题：客户应该为什么付费？Meurer 借鉴了 Emergence Capital 以及 Sierra 的市场推广运营负责人 Elliot Greenwald 的工作，后者的 Outcomemaxxing 阐述了这一定价论点。

结果定价既需要自主性，也需要归因

Sierra 明确的定价原则是：客户应该为软件平台所交付的价值付费。应用这一原则取决于产品能否被归功于结果本身。当归因较弱时，按结果收费就很困难；按席位定价长期以来提供了一种出售访问权限的方式，而无需对最终结果承担责任。

该框架引入了第二个维度：实现结果的代理能力或自主性。归因关注的是结果能否与产品关联起来；自主性关注的是产品能完成多少工作。AI Agent 可以让软件在这两个维度上向上、向右移动——即真正完成工作，并对结果负责。

定价依据客户为什么付费演讲中的示例
席位软件的使用权传统软件订阅
用量服务的消耗量基础模型提供商
结果交付的成果完成一笔销售或解决一个客户咨询

向 OpenAI 或 Anthropic 支付的费用体现了用量定价：即使下游结果难以归因于模型服务，消耗量也是可衡量的。在客户体验领域，完成一笔销售或解决一个咨询可以提供更直接的结果。Meurer 预测，这个市场的大多数定价将转向按结果收费；这一预测取决于产品实现并证实这些结果的能力。

谁负责交付结果？

将能够直接为产品做出贡献的工程师与按结果收费的业务结合起来，那个悬而未决的问题就变得具体了：谁来保证结果？ Meurer 将这一职责归于前沿部署工程。这个角色将产品的能力与客户的实际结果连接起来。

这改变了她最初的分类。在 2024 年，Agent 工程看起来像是一个独特的、以结果为导向的专业方向——前沿部署工程的一种变体。现在她看到产品工程、Agent 工程、AI 工程、解决方案工程和客户工程正在向同一职责汇聚。她有所保留的说法是：一切都是前沿部署工程，或者至少正在朝这个方向发展。

这项工作仍然包括赋能、DevOps、构建解决方案、数据集成、构建 AI Agent 并将其部署到生产环境。每项活动都为向客户交付成果做出贡献，Meurer 认为定价应反映相应的结果。这个头衔可能缺乏清晰的技术边界，但它所表达的职责依然有价值。

这正是她结尾悖论的力量所在：“前沿部署工程已死”与“前沿部署工程万岁”。一个边界狭窄的学科正在让位于一种更广泛的期望：工程师要对客户的结果负责。她补充说，Sierra 正在招聘各类前沿部署工程职位。
