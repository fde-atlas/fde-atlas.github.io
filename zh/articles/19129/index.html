Sierra FDE 面试：AI 原生现场面试准备指南

FDE Times · 2026-10-27 · 约 6 分钟读完

摘要

本文介绍 Sierra 的 AI 原生现场面试流程，并提供一套 90 分钟自主演练方案。Sierra 面试分规划、构建、评审三阶段，构建阶段面试官离场，候选人须在 2 小时内借助编程 Agent 独立完成产品。文章强调 Agent 只加速实现，范围取舍、截止线和转向决策仍须由候选人负责并记录，这些能力同样适用于 FDE 驻场工作。

要点

  • Sierra 面试分规划、构建、评审三阶段，构建阶段为 2 小时。
  • 构建阶段面试官离场，候选人独自用编程 Agent 完成产品。
  • 演练将三阶段压缩至 90 分钟，制造比实战更大的时间压力。
  • 建议用 PLAN.md 和 DECISIONS.md 记录范围削减与转向决策。
  • 各轮面试对 AI 的使用规则不同，以面试邀请为准。

一场比真实两小时构建更紧的 90 分钟演练，专练 Sierra 三个阶段都考察的范围取舍判断。

要点速览

  • Sierra 的真实面试分规划、构建、评审三部分，仅构建阶段就有 2 小时。本文的 90 分钟演练有意压缩时间，让你习惯更大的时间压力。
  • Agent 能帮你更快写出代码，但范围、截止线和转向时机仍由你决定。
  • 每轮面试对 AI 的使用规则各不相同，以你收到的面试邀请为准。

在 Sierra 的 AI 原生现场面试中，到了某个时间点，面试官会起身离开房间。此后你有 2 小时，把刚才一起定义的想法做成一个能用的产品，期间可以随时转向或缩小范围。

Sierra 表示，这种形式更容易看出候选人是否有主动性，比如卡住时会不会换个方向。对前线部署工程师（FDE）来说，这也是驻场客户第一周就要用到的能力：需求模糊，时间紧张，每一次删减都要向别人解释清楚。

本文介绍如何在自己的笔记本上安排一场 90 分钟的演练。真实面试没有这么短：在规划和评审之外，Sierra 仅构建阶段就有 2 小时。把三个阶段压进 90 分钟是有意为之，让你在比实战更大的时间压力下习惯削减范围。

真实面试怎么进行？

Sierra 把这一轮分成三部分。在规划（Plan）阶段，你和面试官一起定义要做的产品。在构建（Build）阶段，面试官离场，你在 2 小时内独自把产品做出来。

在评审（Review）阶段，你们会围绕主要产品流程和你做出的选择展开讨论。随后面试官阅读你的代码，评估你的工程判断力。

做规划时，记住 Sierra 已经明确说过的一点：你可以边做边削减范围，也可以跳过 CRUD、认证这类样板代码，把精力放在产品的独特之处。只有几个小时，这项许可很有价值。

不要以为每一轮都是这样。Aced（前身为 Exponent）的一份指南显示，Agent 工程师的招聘流程中有一轮 60 分钟的现场调试，使用 TypeScript 和 React。

Aced 还提到，Sierra 已宣布调整部分轮次。PracHub 上的另一份指南指出，每一轮对 AI 的使用规则可能各不相同，以你收到的面试邀请为准。

开始计时前要准备什么

你需要一台装有日常所用编程 Agent 的笔记本、一个空仓库、一个计时器，以及一位扮演面试官的人。如果独自练习，提前写好五个追问问题，结束时自己作答。根据 Aced 的说法，整个招聘流程通常需要 2-5 周。

下表是 90 分钟的建议分配，并非 Sierra 的日程安排：

阶段练习时长必须产出
规划10 分钟写明主流程和截止线的 PLAN.md
构建65 分钟主流程跑通，带检查和错误处理
评审15 分钟演示和决策日志

第 1 步：10 分钟完成规划，把截止线写下来

假设扮演面试官的人出了这样一道题：客服团队需要一个界面，显示哪些对话应当转给人工处理，以及原因。这样的需求很模糊。在这 10 分钟里，你要问够问题把它收窄，然后写下来：

# PLAN.md
用户：客服值班主管，在班次开始时查看
主流程：加载示例对话列表 -> 标记“需人工”并给出原因 -> 按标记筛选
数据：示例 JSON 文件，20 段对话（跳过 CRUD：静态数据足以验证流程）
跳过：登录（跳过认证：单用户，仅本地运行）
截止线：主流程跑通后 -> 停止加功能，转向检查、错误处理、演示
备选方案：如果标记功能卡住超过 15 分钟 -> 改用简单的关键词规则

两条“跳过”都附带了理由，这是有意的。PracHub 的指南建议，只有能把原因讲清楚时才跳过样板代码，并提前设定截止线：主流程一跑通，就转向检查、错误处理和演示。

一个快速检验：如果扮演面试官的人读完 PLAN.md 还看不出你会在哪里停下，这份计划就不合格。

第 2 步：告诉 Agent 它看不到的东西

Claude Code 的最佳实践文档把与 Agent 协作归纳为三点：告诉 Agent 它看不到的信息，给它一个能自己运行的检查，执行没有例外的规则。

这条原则适用于任何编程 Agent。写第一行代码之前，先把它整理成一份简短的说明文件：

# AGENT.md（简版）
背景：供客服值班主管使用的内部工具，仅本地运行。
不要做：登录、数据库、管理页面。
每次改动后必须检查：运行测试套件；3 段结果已知的示例对话
  必须得到正确的标记。
硬性规则：未经询问不得引入新库；每次只改一个部分。

最关键的是那三段已知答案的对话。Agent 拿它们做检查，你在评审时拿它们当证据。这是简化版本：真实面试中，请用你最熟悉的测试框架来写检查。

第 3 步：做到截止线，然后停止打磨

让循环保持短小：给 Agent 一个小任务，运行检查，读 diff，然后才交代下一个任务。

PracHub 的指南把角色划分得很清楚：Agent 是加快实现的工具，你才是产品负责人。

一旦接受了自己讲不清的 diff，你就把产品的主导权交给了 Agent。

每次改变方向，都在决策日志里写一行。这花不了一分钟，却会在评审时帮上大忙：

# DECISIONS.md
[第 32 分钟] 基于模型的标记在 3 个测试样例上结果不稳定
  -> 改用关键词规则 + 长度阈值。原因：先要有一个可靠的流程。
[第 51 分钟] 主流程跑通。到达截止线 -> 停止添加日期筛选。
[第 55 分钟] 增加对损坏 JSON 文件的处理：显示提示信息，而不是白屏。

第 32 分钟那一行正是 Sierra 想看到的：卡住时换方向，而不是越陷越深。Sierra 允许边做边转向、缩小范围。由于 15 分钟阈值事先写进了 PLAN.md，你做这个决定时头脑清醒，而不是手忙脚乱。

第 4 步：把评审当成真正的辩论来排练

Sierra 的评审有两层：围绕产品流程的讨论，以及评估工程判断力的代码阅读。扮演面试官的人应当真正提出质疑：为什么值班主管要先按标记筛选？为什么砍掉日期筛选？处理损坏文件的代码在哪里？

对每个问题，你都应该能打开两样东西：DECISIONS.md 里的一行记录，以及一段你能讲清每个分支的代码。如果某部分是 Agent 写的，直接说明，再解释你为什么保留它。

PracHub 的指南提醒：绝不要借助 AI 助手绕过明确规定的规则，也绝不要隐瞒代码出自谁手。

让演练白费的几种错误

最常见的错误是让 Agent 替你做决定。你问 Agent“下一步该做什么”，然后照做，结果到了评审时你没有自己的故事可讲。第二种是前 20 分钟都花在登录和数据库上，尽管 Sierra 允许跳过它们。

第三种是到了截止线却不停下。第 70 分钟加上的额外功能，几乎永远比不上错误处理和一个流畅运行的演示。

最后一种是每一轮都用同一种方式练。Aced 描述的 60 分钟 TypeScript 和 React 调试轮需要不同的准备，AI 规则也可能不同。

这项能力在客户现场体现在哪里？

把面试官换成客户的运营负责人，把 2 小时换成演示前的一个短冲刺，步骤完全一样：和他们一起定义主流程，写下跳过了什么以及原因，到截止线就停，然后向那些没坐在你身边看你写代码的人逐一解释每个选择。

对求职而言，每次演练都会留下三样值得放进作品集的东西：PLAN.md、DECISIONS.md 和一个能运行的仓库。在简历上，“借助编程 Agent 在 2 小时内完成原型，并记录范围削减和转向决策”这样的一句话，比罗列工具更有说服力。

阅读 FDE 岗位描述时，留意 scoping、prototyping、working with ambiguity 这类措辞。它们往往说明这个岗位看重的正是你刚练过的能力，也是讲述 DECISIONS.md 里那些故事的好切入点。

在这类面试中，编程 Agent 和你同处一室。雇主想看到的，是只有你才能做出的决策。
