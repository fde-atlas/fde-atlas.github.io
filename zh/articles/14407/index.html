FDE-Gym 基准测试：最佳 Agent 仅解决 95 个任务中的 14 个

原标题：FDE-Gym Benchmark: Best Agent Solves Only 14 of 95 Tasks

AISOLO Technologies Private Limited · 2026-10-16 · 约 8 分钟读完

摘要

FDE-Gym 是一个模拟前沿部署工程师工作的基准：客户请求可能指向错误的问题，关键约束未被明说，交付成果要在真实系统中验证。基准包含 95 个任务、20 个客户场景和 18 个行业，Agent 需与 130 多个有耐心限制的脚本化干系人互动，提问还要计费。在 13 个模型配置中，最好的 Claude Opus 5.5 平均得分仅 0.56，只解决 14 个任务；瓶颈在于发现未明说的约束，而非执行代码。项目以 Apache-2.0 开源，附 arXiv 论文与 Hugging Face 数据集。

要点

  • 最佳模型 Claude Opus 5.5 仅解决 95 个任务中的 14 个。
  • 主要瓶颈是发现未明说的约束，L0 到 L1 得分骤降。
  • 基准含 95 个任务、20 个场景、130 多个脚本化干系人。
  • 提问有成本，违规操作会将得分清零。
  • 项目以 Apache-2.0 开源，含论文与数据集。

大多数 Agent 基准测试会给模型一个明确的任务，然后检查任务是否完成。但真实的工作很少以这种方式出现。FDE-Gym 测试的是更混乱的版本：客户提出的需求可能本身就是错的，关键规则从未被明说，而且交付的答案必须能在真实运行的系统中生效。结果令人清醒。在来自七家提供商的 13 个模型配置中，表现最好的 Claude Opus 5.5 平均得分为 0.56，仅解决了 95 个任务中的 14 个。

这篇 arXiv 论文 附带一个采用 Apache-2.0 许可的 GitHub 仓库 以及一个 Hugging Face 数据集。作者称之为对“AI 交付最后一公里”的测试。对于任何销售或采购 Agent 构建软件的人来说，这是近期出现的最有用的现实检验之一。

什么是前沿部署工程师，为什么要为此进行测试？

前沿部署工程师（FDE）与客户一起工作，将模糊的业务需求转化为能在客户自身系统中运行的软件。这份工作的重点不在于编写代码，而在于提出正确的问题：发起人的请求是否针对真正的问题？哪些规则已经过时？谁掌握着关键信息？哪些东西绝对不能动？

这正是 Agent 正在被销售进企业的场景，也是典型基准测试几乎无法反映的场景。作者指出，定义明确的编码任务如今已被高比例解决，因此他们构建了一个难点在于情境而非语法的测试。

这个基准测试是如何构建的？

场景与变体。 行业专家从真实项目中改编了 20 个场景。每个场景包含一个原始任务，外加两到七个改变关键事实（例如哪条规则已过时或谁掌握关键信息）的变体，共计 95 个任务。

环境。 Agent 在客户系统的一个副本中工作，其中包含文档、数据和员工名录。它可以与 130 多个脚本化的利益相关者互动，这些角色耐心有限、有披露信息的条件，并受联系限制。交付的系统会被原样部署，并在留出的数据上进行测试。

四个指令级别。 同一环境和评分器在四个级别下运行：

  • L0： 问题、规则和评分标准都已明说。
  • L1： 问题已明说。
  • L2： 一个模糊但正确的请求。
  • L3：发起人的原始请求，可能存在误导。这是主要设定。

评分。业务提升以客户自己的指标来衡量，并做归一化处理，使“什么都不做”的基线为 0，专家参考为 1。发生事故（如未经授权的操作）会将正提升清零。利益相关者接触成本对消息、试运行和等待时间计费。最终得分为调整后的提升减去接触成本，任务在达到 0.8 或以上且无事故时视为已解决。

防作弊护栏。只有当参考得分至少为 0.95、“什么都不做”基线得分为 0、字面解决方案得分不超过 0.2、捷径策略得分不超过 0.8 时，任务才会被收录。作者表示，他们针对 270 多种捷径和绕过策略对评分器进行了测试。

结果显示了什么？

  • 最佳模型解决的任务很少。Claude Opus 5.5 在 L3 上得分为 0.56（95% 置信区间为 0.50 至 0.62），解决了 95 个任务中的 14 个。有五种配置一个任务都没解决。
  • 集成并不能解决问题。为每个任务挑选最佳配置也只能达到 0.70 和 30 个已解决任务。
  • 约束条件是瓶颈。三个领先模型在 L0 上得分为 0.73 至 0.82，但在 L1 上仅为 0.39 至 0.62，因此损失来自必须自行发现规则，而不是来自后来转向被误导的请求。
  • 了解事实并不够。领先模型能恢复 72% 至 85% 的关键事实，但只能达到参考提升的 0.60 至 0.70，而接触成本又扣除了另外 0.14 至 0.22。
  • 弱模型可能造成损害。在计入接触成本后，Claude Haiku 4.5 在 95 个任务中的 79 个上得分低于“什么都不做”基线。
  • 场景影响很大。在 20 个场景中的 5 个里，没有任何模型的平均得分达到 0.5 或以上。
  • 花费与得分并不相关。成本和轮次数量几乎无法解释排名。
  • 其他基准测试高估了 Agent。在 Terminal-Bench 2.1、Vibe Code Bench 和 Finance Agent 上解决 61% 至 90% 任务的模型，在这里得分仅为 0.19 至 0.56，不过作者提醒这些指标不能直接比较。

关于顶级模型在其他方面的表现，请参阅我们关于 Claude Opus 5.5 发布基准测试 和 FrontierCode 维护者合并基准测试 的文章。

被误导的请求是什么样的？

L3 设定才是真正重要的，而且这个理念很容易被忽视。假设客户的运营负责人要求一个标记延迟发货的仪表板。而收入流失的真正原因原来是定价系统中一条过时的规则，没有人提到过它，唯一知道这件事的同事只有在你问对问题时才会回答。完全按要求构建仪表板的 Agent 产生的是字面解决方案，根据基准测试的收录检查，得分最多为 0.2。而一个询问正确的利益相关者、找到规则并修复定价逻辑的 Agent 则可以达到参考得分。

那个场景只是我们的示例，并非该基准测试中的任务之一，但它捕捉到了作者所描述的模式：变体会改变某个关键事实，例如哪条规则已过时，或谁掌握着关键信息，因此死记一个场景并不能迁移。模型必须在每种情况下主动提问、倾听并核实。

评分机制则针对两种坏习惯。从不提问的 Agent 会遗漏约束条件，交付错误的东西。什么都问的 Agent 则会烧掉沟通成本，因为消息、试运行和等待都要计费。最佳行为是有针对性地、尽早提问，这正是人类前沿部署工程师被看重的原因。

它与其他 Agent 基准测试相比如何？

Terminal-Bench、Vibe Code Bench 和 Finance Agent 衡量的是 Agent 能否在受控环境中执行定义明确的工作，根据论文，强大的模型现在能解决其中 61% 到 90% 的任务。FDE-Gym 在三个方面有所不同：请求本身可能是错的，成功与否是在部署后按客户自己的业务指标来衡量，而且提问是有代价的。论文将其置于关于歧义（如 Ambig-SWE 和 LHAW）、探索（TheAgentCompany）和 Agent 构建（tau-bench）的研究附近，并指出其独特之处在于：被误导的请求、以业务指标为结果，以及提问的成本。

由于作者警告这些数字在不同基准测试之间不可直接比较，最稳妥的结论是方向性的：当加入歧义和隐藏规则后，同样的模型会失去大部分表面上的亮眼成绩。这与我们对 Pine 的 SaaS-Bench 声明的解读相呼应——高得惊人的数字依赖于特定的测试设置。

这对部署 Agent 的人意味着什么？

预期演示与交付之间的差距。 一个能在清晰工单上写出正确代码的 Agent，面对需求部分未言明的客户仍可能失败。如果你转售 Agent 构建的成果，请把负责需求探索的人力成本计入定价。

为提问做预算。 该基准测试对沟通收费，因为现实中的利益相关者耐心有限。什么都不问的 Agent 会遗漏约束条件；问得太多的 Agent 则会推高成本。两者都要评估。

关注事故，而不仅仅是产出。 未经授权的操作会将得分清零。这与我们在 Agent 安全报道中提出的担忧一致，例如 APEX-Harm 研究表明正确的交付物可能掩盖不安全的操作。

在你自己的技术栈上使用它。 由于测试框架是开源的，你可以接入自己的 Agent 框架进行比较，而不必依赖厂商给出的数字。

它有哪些局限性？

作者直截了当地列出了这些局限：

  • 利益相关者是脚本化的，因此无法捕捉真实人类的不可预测性。
  • 目前只测试了模型；尚无人类基线，不过一个供人类尝试相同任务的在线平台正在被用来收集这一基线。
  • 所有模型均在同一个极简 Agent 框架中运行，这可能会低估或高估某些厂商的表现。
  • L0 至 L2 的样本量较小，每个层级仅有 20 个任务。
  • 联系成本为专家估算值，并非实测数据。
  • 无法排除训练数据污染的可能性。

另外请注意公开情况：20 个原始任务和评分器可应要求提供，其中包含三个公开示例，而 75 个变体和参考解决方案则被保留不公开。这保护了基准测试，但也限制了独立复现。

如何试用

README 给出了以下步骤，需要 Docker、Python 3.9 或更高版本，以及一个存放在仓库之外的 OpenRouter 密钥：

git clone https://github.com/deeplethe/fde-gym.git
cd fde-gym
mkdir -p ~/.fdegym
python3 scripts/fetch_cases.py
docker compose up --build

将你的 OpenRouter 密钥存储在

~/.fdegym/openrouter_key

中，然后再启动。站点运行在

http://127.0.0.1:8787

上，包含一个运行器、PostgreSQL 和一个兼容 S3 的对象存储。首个注册的账户将成为管理员。由于该站点会执行提交的代码，README 建议在向他人开放之前先阅读其自托管指南。一个廉价模型扮演客户方人员，而选择编码 Agent 的模型则被列为路线图事项。评分范围从 0（什么都没改）到 100（参考解决方案），80 分及以上视为解决。README 要求用户不要在这些案例上进行训练。

我们仍不了解的问题

  • 人类在同一任务上的得分如何。
  • 使用更强的 Agent 框架或针对发现调优的工具后，结果会如何变化。
  • 鉴于该基准测试的结果仅针对论文发表时测试的模型，更新的模型能否缩小约束发现方面的差距。
  • 脚本化的利益相关者能在多大程度上预测真实客户的行为。
