降低工厂停机时间 · FDE 分解问题

原标题：Reduce factory downtime · FDE decomposition question

FDE Interview Prep · 2026 · 约 7 分钟读完

摘要

本文拆解一道 Databricks 前沿部署工程师面试题：如何降低工厂停机时间。作者主张先算钱再谈数据：找出损失毛利最多的产线，把停机分钟拆成停机次数与修复时长，因为传感器主要缩短诊断而非等待配件。随后明确干系人与指标（每计划生产小时的意外停机分钟，对照上季度基线），核查 historian 标签与资产映射、补齐故障标注，先交付一条可读的规则报告，模型留到有足够标注数据之后。

要点

  • 先定位损失毛利最多的产线与故障模式，再谈传感器。
  • 把停机分钟拆成停机次数与修复时长，传感器只对前者帮助大。
  • 明确工厂经理、维护计划员与控制工程师的角色，只读 historian，不碰 PLC。
  • 先补齐标签到资产的映射和故障标注，再选一条产线一种故障模式。
  • 先上线可读的阈值规则报告，模型要等有足够标注故障后再做。

如何作答

将损失的分钟数拆分为停机发生的频率和每次停机持续的时长，因为传感器对前者帮助最大。传感器可以缩短诊断时间，但无法缩短等待技术人员或备件的时间。题目把传感器数据作为答案摆在你面前；把它当作需要验证的输入之一，并从钱的角度入手。

一位报告了 Databricks 初级岗位面试流程的候选人，在 2026 年 8 月发布的报告中称这是最重要的一题，并表示这意味着几乎要把面试官当作客户来对待，在触及架构之前先澄清利益相关方、范围和 KPI。来源 1Databricks 前沿部署工程师面试经验发布方Aced（前身为 Exponent）来源类型候选人的个人记录 下面的步骤保持这一顺序：先谈钱和人，再谈数据，最后才是模型。

  • 先问停机在哪里造成的成本最高，以及为什么。 哪些产线、哪些故障模式、上个季度损失了多少分钟。然后把这些分钟数拆分为停机次数和修复时间。如果封盖机很少停机，但每次停机都要等技术人员或备件几个小时，那么备件和响应时间比任何传感器都更有效。瓶颈产线上的停机会损失产量；而下游有缓冲的产线停机可能损失很小。要问工厂是否卖出了它生产的所有产品；如果没有，损失一小时意味着加班费和废料，而不是失去销售。
  • 明确相关人员和指标。 厂长负责毛利率目标。维护计划员和技术人员要对任何警报采取行动，操作员负责记录产线停机的原因。控制工程师负责 PLC、历史数据库和不能干扰的工厂网络：从历史数据库读取数据，最好是从控制网络之外的副本读取，绝不要直接轮询 PLC。成功的标准是该产线每个计划生产小时内的非计划停机分钟数减少，以上季度为基线，同时列出计划维护时长和被忽略的警报数。使用工厂自己的术语：停机次数对应 MTBF，修复时间对应 MTTR，两者共同构成 OEE 中的可用率项。
  • 在信任数据之前先核查输入。 历史数据库标签、来自 MES 的停机事件、来自维护系统的工单。对每一项，询问负责人、采样率、历史数据长度，以及标签是否映射到物理资产。“没人用它”往往意味着没有标签到资产的映射，也没有故障标注。
  • 选定一条产线和一种故障模式： 选择成本最高且在发生前有迹可循的那一种。突发性堵塞则不行。
  • 为过去的故障打标签。 和技术人员一起坐下来，把一年的工单转化为带标签的事件。
  • 先交付规则，再谈模型。 为维护计划员提供一份日报，其中包含一个他们可以争论的阈值，阈值通过对比故障发生前的读数与正常运行时的读数来设定。

全厂范围的预测性维护是一个应当避免的承诺。没有标注过的故障，你就无法区分一个模型是好是坏。

追问

当你的第一个回答摆上桌面后，面试官接下来可能会问的问题。

  • 画出将传感器读数关联到停机事件的表结构。
  • 历史数据库每分钟采样一次，但故障在几秒内就会显现。现在怎么办？
  • 维护日志是自由文本。你会如何为第一条产线标注故障？

回答容易出错的地方

  • 承诺覆盖全厂的预测性维护，而不是聚焦一条有标注故障的产线。
  • 一上来就在传感器数据上建模型，却没有先问哪条产线在损失钱，或者是否曾经标注过任何故障。

两分钟内回答

写出你会大声说出的回答。计时从你说出第一个字开始。

与标准答案对比

标准答案

第一分半钟。“在看传感器之前，我会先找出哪条产线损失的毛利最多，并把它的损失分钟数拆解为停机频率和每次维修的时长，因为传感器数据主要对前者有帮助。工厂经理负责目标，维护计划员对任何预警采取行动，控制工程师决定我可以读取什么，所以我只从历史数据库读取，绝不触碰 PLC。缺失的部分通常是从历史数据库标签到机器的映射，加上没人标注过的故障，所以我会和一名技术员一起，为一条产线把这两样都建起来。然后我向计划员交付一条可读的规则，作为晨报，并以每计划生产小时的非计划停机分钟数对比上一季度来衡量效果。等我们积累了足够多的标注故障，再上模型。”

如果他们想要细节：

成本与范围。“在谈传感器之前：哪条产线因计划外停机损失的毛利最多？我会索取上一季度各产线按停机原因代码分类的停机分钟数，以及财务部门给出的每小时产出的毛利。假设数据显示灌装线是瓶颈，首要原因是封盖机。我把封盖机的停机分钟拆分为停机次数和修复时间，修复时间再细分为等待技师、诊断、等待备件和实际修理；这些时间戳来自工单。传感器主要帮助统计次数，对诊断略有帮助。该产线上一季度每计划生产小时的计划外停机分钟数就是基线。”

“然后公开算钱。假设封盖机上一季度停机 38 次，每次 55 分钟，财务给出的瓶颈线毛利为

$4,000

每小时。那就是每季度约

$139,000

，这决定了试点的价值，也让我判断备一个封盖机机头放在货架上是否比任何传感器方案更划算。”

人员。“工厂厂长负责毛利目标并批准试点。维修计划员是我的用户，因为预警只有转化为计划内的维修任务才有用。控制工程师是关键阻碍方：没有他们，任何东西都不能接触 PLC 或工厂网络，所以我从历史数据库读取数据，最好是从控制网络之外的一份副本读取。”

数据关联。“所有人都缺的那张表，是历史数据库标签到物理资产的映射表。有了它，我就能拉取每次停机前的读数：”

CREATE TABLE downtime_event (
  event_id      bigint PRIMARY KEY,
  line_id       text        NOT NULL,
  asset_id      text,                 -- null when the operator logged only the line
  started_at    timestamptz NOT NULL,
  ended_at      timestamptz,
  reason_code   text,                 -- operator's pick list, often 'other'
  work_order_id text                  -- link to the maintenance system, often missing
);

CREATE TABLE tag_asset (
  tag           text PRIMARY KEY,     -- historian tag name
  asset_id      text NOT NULL,
  unit          text,
  sample_period interval
);

SELECT d.event_id, r.tag, r.ts, r.value
FROM downtime_event d
JOIN tag_asset ta     ON ta.asset_id = d.asset_id   -- stops with no asset drop out here
JOIN sensor_reading r ON r.tag = ta.tag
                     AND r.ts >= d.started_at - interval '7 days'
                     AND r.ts <  d.started_at
WHERE d.line_id = 'filling_2';

“我还会在随机时间拉取同样的时间窗口，且窗口之后没有停机，针对相同的资产。一个在正常运行前和故障前触发频率一样的阈值就是噪音。我会剔除包含另一次停机或维修任务的窗口，并且正常运行窗口只从计划生产时间中抽取，这样维修期间或计划停机期间采集的读数绝不会算作正常运行。我还会报告有多少次停机没有对应资产，因为关联操作会把它们丢掉。我还会要求提供原始记录值，而不是插值后的值。历史数据库通常存储压缩数据，插值可能把我正在寻找的尖峰平滑掉。”

分钟级采样，秒级故障。“分钟级数据仍能显示缓慢漂移：电机电流逐日攀升、温度持续上升。但它无法显示亚分钟级的事件。所以针对这一条产线，我会问控制工程师两个问题：封盖机的标签能否更快地采集，以及边缘端能否计算每分钟的最大值和均方根值，以免尖峰被平均掉？我不会承诺用分钟级平均值做轴承诊断；那需要采样频率远高的振动传感器。”

标签。“我拉取该产线一年的工单。我和一位技师商定一个简短的分类体系——部件和故障模式——并一起标注一个样本。其余的用关键词规则或语言模型标注，在任何人信任这些标签之前，我会报告它们与我们人工标注的一致率。然后我按资产和时间重叠，把每张已标注的工单关联到一次停机事件。”

第一个切片。“一行代码，一种故障模式，给计划员的一份晨报：当前状态或温度趋势越过阈值的封盖机资产，加上它们近期的工单。一条他们能看懂的规则。等我们积累了足够多的带标签故障数据后再上模型。”

故障模式与指标。“操作工忙的时候会选‘其他’，所以我每周检查原因代码的质量。误报太多计划员就不看了，因此被忽略的告警是一条护栏。指标是灌装线每计划生产小时的非计划停机分钟数，而不是原始分钟数，这样更忙的季度不会被误判为失败；我把它与上个季度对比，并结合计划维护小时数一起看。用工厂的话说，停机次数对应 MTBF，维修时间对应 MTTR，两者共同构成 OEE 中的可用率项。”
