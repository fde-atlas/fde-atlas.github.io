Anthropic 前沿部署工程师在客户系统中交付的关键产物

原标题：Key Artifacts Anthropic FDEs Deliver in Customer Systems

Educative · 2026-10-16 · 约 6 分钟读完

摘要

本文以一家大型零售商的客服场景为例，介绍 Anthropic 前沿部署工程师（FDE）交付的四类产物：生产应用、MCP 服务器、子 Agent 和 Agent 技能，并说明在信息不全时如何做可撤销的早期决策、坚持安全标准，以及把经验提炼成可复用模式。

要点

  • FDE 交付四类产物：生产应用、MCP 服务器、子 Agent、Agent 技能。
  • 零售商案例中，回复助手、订单查询、退款审核子 Agent 各司其职。
  • 早期需明确范围、成功标准、集成面和安全姿态四项决策。
  • 安全标准包括最小访问、人工审批重大操作、可预测失败。
  • 经验被提炼为工具合同模板、上线清单、评测标准等复用模式。

了解 Anthropic 前沿部署工程师的核心交付物。学习他们如何将宽泛的客户目标转化为具体的生产级应用、MCP 服务器、子 Agent 和 Agent 技能。探索在模糊性下做决策以及优先考虑安全性，如何塑造出能顺畅集成到客户环境中的持久、可靠的解决方案。

一家大型零售商的平台团队请 Anthropic 帮助将 Claude 用于客户支持。这个请求以一个宽泛的目标形式到来。团队希望为其支持人员提供更快的答案，并且他们已经拥有一个工单系统、一个订单数据库，以及由支持人员手动应用的内部退款政策。

宽泛的目标能给出合作方向，但没有具体形态。在构建开始之前，FDE 会把这个目标转化为一份清单，列出合作结束时将存在的具体事物。清单上的每一项都是客户可以运行、检查和维护的东西。

Anthropic 的 FDE 交付一组可识别的此类交付物，并在明确的工作预期下构建它们。了解这两点，能让我们用面试官所关注的术语来描述我们自己的工作。

FDE 交付的四类交付物

FDE 交付物是在合作结束后运行在客户生产工作流中的技术产物。Anthropic 列出了其 FDE 交付的四种类型。

  • 生产级应用： 在客户自身环境中使用 Claude 模型构建、并由真实人员在日常工作中使用的系统。
  • MCP 服务器： 通过模型上下文协议（MCP）将客户的工具和数据暴露给 Claude 的服务，MCP 是一个用于将 AI 应用连接到外部系统的开放标准。一个服务器可以为任何支持该协议的应用提供服务。
  • 子 Agent： 由主 Agent 将有边界的子任务交给其处理的专注型 Agent。每个子 Agent 使用自己的指令、工具和上下文进行工作，然后将结果返回给主 Agent。
  • Agent 技能： 打包可重复流程的指令、脚本和参考文件的文件夹。Claude 只在任务需要时才加载某个技能，因此技能库能在不使每个请求变得臃肿的情况下增加能力。

这四类交付物相互配合。生产级应用是用户看到的部分。MCP 服务器、子 Agent 和 Agent 技能将它连接到客户的系统、将其工作拆分为专注的部分，并编码客户的流程。

对于这家零售商，清单变得具体了。生产级应用是工单系统内的一个回复助手。一个 MCP 服务器让 Claude 可以读取订单状态和发货历史。一个子 Agent 在支持人员看到之前，根据政策检查每份退款草稿。一个 Agent 技能打包了退款政策本身，包括其阈值和例外情况，使该流程保存在一个统一维护的地方。

命名交付物是第一步。决定先构建什么，通常发生在客户尚未回答完所有问题之前。

在模糊性下做决策

项目合作的第一周很少能带来完整的信息。零售商可能还不知道哪些客服人员将试点使用该助手、订单数据库是否允许新服务进行读取访问，或者超过一定金额的退款由谁审批。模糊性下的自主性是指在信息有限的情况下做出明确、可逆的决策，然后在答案到来时加以确认。Anthropic 期望其 FDE 以这种方式工作，并在路径不清晰时展现出高度的主动性。

四个早期决策决定了项目的整体形态。

  • 范围边界： 针对一个指定群体的一个工作流，例如面向退货团队的退款工单。
  • 成功标准： 客户认可的衡量指标，例如客服人员在稍作修改后即发送的退款草稿占比。
  • 集成界面： 第一版所连接的具体系统，例如工单系统和订单数据库。
  • 安全姿态： 在试点期间对系统可读取、修改或执行的操作的限制，例如只读访问订单，以及未经人工客服批准不得发放退款。

这些决策可以写在一页纸上。它们设定了任何技术设计都必须满足的条件，并且每一项都可以在客户确认或纠正后进行调整。

注意：写下未确认的约束条件 一个假设一旦被写下来、指定负责人并安排确认，就会变得有用。只存在于某个人脑海中的假设，往往会在构建后期以意外情况的形式浮现。

在这四项决策中，安全姿态的影响最为深远，因为它体现了 Anthropic 对每一次部署都坚持的标准。

将安全与可靠作为交付标准

Anthropic 期望其 FDE 在构建新解决方案的同时，坚持其对安全性和可靠性的高标准。在交付工作中，这些标准会转化为每个交付物中的具体选择。

  • 最小访问权限： 每个 MCP 服务器只暴露工作流所需的工具和字段。零售商的服务器只读取订单状态，而将支付详情排除在访问范围之外。
  • 重大操作需人工审批： 具有实际成本的操作（例如发放退款）需等待人工批准。
  • 上线前经过测试： 在更多用户依赖系统之前，团队会用真实案例（包括棘手的案例）对系统进行检验。
  • 可预测的失败： 当查询失败或请求不明确时，系统会明确说明，并将该案例转交给人工处理。

可靠性还取决于人。前沿部署工程师（FDE）同时与客户团队和 Anthropic 内部团队协作，因此与客户安全团队达成的限制约定必须传达给每一位基于该限制进行开发的工程师。正因如此，Anthropic 寻找具备强烈协作意识的人，而 FDE 在每一次这样的沟通中都代表着 Anthropic。

每一项选择都需要付出努力才能第一次就做对。把这些选择记录下来，让下一次项目合作能以此为基础，就是这项工作的最后一部分。

将项目合作转化为可复用的模式

一次项目合作解决的是一个客户的问题，而其中许多经验教训同样适用于下一个客户。模式提炼是指把在多次项目合作中反复出现的经验教训，转化为可复用的成果，供其他交付团队作为起点使用。

假设零售商项目合作表明，每一个工具连接都需要同样的约定。该约定列出了允许的操作、所需的输入以及指定的客户负责人。保存在会议记录中，这份约定只对一个客户有帮助；写成工具契约模板，它就能为下一个团队提供一个经过验证的起点。

项目合作中常常产出的其他模式包括以下几种。

  • 上线检查清单： 将试点推广到更多用户时的就绪检查、负责人和回滚决策。
  • 评估评分标准： 用于判断输出是否满足客户任务需求和安全需求的评分指南。
  • 通用化 Agent 技能： 最初为某个客户的流程编写的技能，经过重塑后，使拥有类似流程的其他客户也能加以适配使用。

一个好的模式会保留重复出现的结构，而舍弃客户特有的细节。工具契约模板保留了约定的形式，而零售商的退款阈值则仍归属于该零售商。

交付超越项目合作本身的工作成果

在 FDE 转向下一个项目合作之后，客户的团队还要长期运行 FDE 构建的系统。这些成果承载着项目合作的价值，而其背后的决策——关于范围、访问权限和审批的决策——应当得到与代码同等的重视。当我们描述自己过去的工作时，说清楚我们交付了什么、在事实尚未完整时做出了哪些决策、坚守了哪些限制，能让面试官清晰地了解我们在客户系统内部会如何开展工作。而这正是 FDE 面试流程所要考察的内容。
