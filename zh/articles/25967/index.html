FDE 代码库契约：FDE 可以在你的代码仓库中修改什么

原标题：FDE Codebase Contract: What FDEs May Change in Your Repo

Falkster.AI · 2026-09-27 · 约 11 分钟读完

摘要

文章基于 UC Berkeley 的 HarnessTax 研究与 Tomasz Tunguz 的成本分析，指出编码 harness（工具集、循环、上下文组装）对成功率影响很小，但成本差异可达 1.1 至 5.1 倍。作者提出 FDE 与工程团队之间的代码库契约：客户层（提示词、规则、阈值、评测行）由 FDE 当天修改无需评审；harness 层须通过带评测数据和单例成本的 PR 修改；核心代码永不 fork。工程团队则须提供可 diff 的配置、可信沙箱、每次 harness 变更的评测和按客户的单例成本看板。

要点

  • HarnessTax 研究：同一模型在不同 harness 下成功率相近，成本差最高 5.1 倍。
  • 三层契约：客户层 FDE 即改，harness 层走 PR 并附成本，核心永不 fork。
  • FDE 现场添加的工具和技能实质是 harness 变更，即成本决策。
  • 工程团队须回报：可 diff 配置、可信沙箱、全客户评测、单例成本看板。
  • Palantir 的 FDE 与产品工程师分工因产物分离而有效，Agent 产物合一故须成文契约。

六位 UC Berkeley 的研究人员于 9 月 16 日发表了一项名为 HarnessTax 的研究。Melissa Z. Pan、Shuo Yang、Negar Arabzadeh、Wei-Lin Chiang、Ion Stoica 和 Matei Zaharia 让七个模型分别通过三个编码 harness——Claude Code、Codex CLI 和 Pi——在 SWE-bench Lite 和 Terminal-Bench 2.0 的各 30 个任务上运行。Claude Fable 5 在 Claude Code 中解决了 97.8% 的尝试，在 Codex 中为 96.7%，在 Pi 中为 96.7%。Claude Code 每次尝试的成本约为 Pi 的两倍，$1.33 对 $0.67。他们的一句话结论是：“同一个模型可以在成本相差高达 5 倍的情况下取得相近的成功率。”

Tomasz Tunguz 第二天读到了这篇文章，并做了毛利率计算。GPT-5.6 Sol 在 Pi 上的成本比在 Claude Code 上低 71%，而结果相同。42 组 harness 对比中，没有任何一组显示出统计上显著的质量差异。成本差异（取决于 harness）从 1.1 倍到 5.1 倍不等。他的演算示例——是说明而非案例：两家初创公司竞标同一个 25 万美元的合同，一家毛利率 38%，一家 75%，胜负仅由 harness 决定。

这篇文章在 Hacker News 上获得了 231 个赞和 97 条评论，几乎全是关于编码 Agent 的。没有人说出那个不言自明的关键点。harness 正是前沿部署工程师所改变的东西。工具、技能、上下文、循环。这一层决定了每个答案的成本，却几乎不影响质量。所以，那位在某个周二为客户词汇表添加三个工具和一份 2000 字技能的 FDE，实际上刚刚为该客户账户做出了一个毛利率决策。没有 pull request，没有评审，没有定价。那只是“配置而已”。

这是 The FDE Transition 的第 4 部分。第 3 部分讲的是 FDE 对产品负有的责任。本部分讲的是与工程团队的契约：FDE 可以在现场更改什么，什么属于 harness 而非代码，以及工程团队反过来欠什么。

简要版本

  • 三层，三条规则。
  • 客户层——提示词、规则、阈值、连接器设置以及客户的评测行——归 FDE 所有，当天即可更改，无需评审，但有两个条件：必须版本化，并且能用一条命令与出厂默认值做 diff。
  • harness——工具集、循环、上下文组装、防护栏以及模型选择——归工程团队所有，FDE 只能通过 pull request 更改，且必须附上客户的评测行和每案例成本，因为 harness 的更改意味着其上每个客户的成本变化。核心归工程团队所有，绝不 fork。
  • 工程团队反过来欠四样东西：一个可 diff 的配置、一个成本数字有意义的沙箱、每次 harness 更改时在每个客户的评测行上运行评测，以及在仪表盘上显示每个客户每个已解决案例的成本。
  • Nabeel Qureshi 的 Palantir 对这条界线有一个清晰的表述：FDE 过拟合，产品工程师泛化。它之所以成立，是因为两个团队产出不同的工件。而在 Agent 产品中，这条界线贯穿同一个文件，这正是必须把它写下来的原因。

为什么这条界线移动了

Palantir 的分工之所以有效，是因为产物不同。根据 Reflections on Palantir，FDE 在空客构建了“用于制造飞机的 Asana”，而产品开发工程师将其产品化。Qureshi 对代码的描述是诚实的：FDE 代码“能快速把事情办成，这通常意味着，委婉地说，技术债务和临时性的变通方案”，而 PD 代码“能干净地扩展，适用于多种用例，并且不会崩溃”。两种产物，以及它们之间的从部署到产品的循环。

在 Agent 产品中只有一种产物。一个提示词。一个技能文件。一个工具描述。一位 Hacker News 评论者测量了 Claude Code 发给模型的初始指令，达 80 KB，其中大部分是工具描述。那就是 harness。FDE 为客户的工单系统添加的工具，以及解释其审批层级的技能，也是 harness，在客户每次调用时都会生效。Tunguz 的那句话值得划线强调：“Harness 将常见工作流凝聚成可重复的模式：确定性代码或技能。”代码或技能。这个“或”就是全部的契约。FDE 在现场编写的技能就是一次 harness 变更，而没有人说过哪些变更是 FDE 有权做的，哪些需要第二双眼睛和一个价格。

我曾在部署团队之上管理过产品，失败总是同样的形态。现场的人做出了能解除客户阻塞的变更，而上游没有人知道它的存在，直到它以账单的形式出现。解决办法从来不是“不许他们改东西”。而是一条成文的界线。

三个层级

层级一：FDE 完全拥有的部分

客户层。提示词和词汇、业务规则、阈值、路由、连接器设置，以及客户的评测行。FDE 当天就修改它，无需审查，因为这正是设置 FDE 的理由。第二部分已经指出：如果改一个提示词要走工单和发布列车，那你拥有的就是一个带着差旅预算的队列。

两个条件。它有版本控制。并且它能用一条命令与出厂默认值做差异对比，因为这个差异就是交接包中的 delta，而一个需要 FDE 靠记忆而不是靠生成的 delta 是不会被发送出去的。

Decagon 的 Jesse Zhang 认为，根本需要 FDE 本身就是产品薄弱的标志，并声称一个他与 Sierra 共同服务的客户，用 Sierra 的嵌入式工程师一年构建了三个工作流，而切换后一个月就构建了七个。我无法核实那个客户。这个说法针对的是层级一：产品有多少部分存在于这一层，以及客户自己的人能否驱动它。Decagon 的赌注是，这一层可以被推出去，直到不再需要 FDE。Perspective AI 的调查显示，64% 的 FDE 将他们的主要工作描述为进行大量定制的部署，这说明目前还没有谁的层级一足够大。

层级二：harness，通过 pull request，并附带价格

工具集、Agent 循环、上下文组装、防护栏、模型选择。这些归工程团队所有。FDE 可以修改它们，而且往往也应该修改，因为 FDE 知道客户的工单 API 在高负载下会超时。但修改必须以 pull request 的形式提交，而这个 PR 通常要附带两样东西：促成这次修改的客户评测数据行，以及在沙箱中测得的修改前后每案例成本。

HarnessTax 有一个细节，应该让每个想添加新工具的 FDE 感到警醒。Pi 仅用四个工具——read、write、edit 和 bash——就在两个基准测试上都达到了帕累托前沿。每个工具描述在每次调用时都消耗 token，而 FDE 面对客户时的本能就是做加法。PR 正是这种本能与数字相遇的地方：这个改动新增了一个工具，它在这位客户的评测数据行上把解决率提升了这么多，每案例成本增加了这么多。工程团队在与产品交接相同的两周窗口内做出决定：将其泛化给所有客户、保留为单客户技能，还是拒绝。如果窗口关闭时仍无答复，FDE 无论如何都会把它作为第一层技能发布，于是这就成了一次无人定价的 harness 变更。

Leo Mehr 在十八个月内将 Ramp 的 FDE 团队从两名工程师扩展到十六名，团队隶属于工程部门，从事核心产品的工作。他的 Ramp 帖子 中有一条我会放在 PR 模板最顶部的规则：始终明确范围。谁在推动紧迫性，谁真正在使用它，其他潜在客户会不会需要它？在 他的 AI Engineer 演讲 中，他说团队正朝着把大部分时间花在运营 harness 和维护评测上的方向发展，并警告了一个未界定范围的请求一旦被自动化会产生什么——一台“token 最大化垃圾炮”。如果 FDE 正在成为 harness 操作员——我认为这个判断是对的——那么“带价格的 PR”规则就不是对这份工作的约束，它就是这份工作本身。

第三层：核心，以及“fork”这个词

FDE 绝不 fork 核心。不为演示，不为赶工期，也不因为客户的 CTO 在场。fork 是一种承认——承认第一层太小了，而正确的修复是提交一个第一层或第二层的 PR，为所有人移动边界。关于产品中必须改变什么的手册章节 给出了检验标准，我只复述其中一句：如果 FDE 最近构建的三件事中有任何一件需要核心 PR，那边界就放错了地方。

一个例外：FDE 嵌入某个产品小组一周，专门移动那条边界。那是戴着访客徽章的产品工程，不是部署。

工程团队欠什么

四样东西，和一个时钟。

一份可 diff 的配置。按客户区分、有版本控制，一条命令即可生成与已发布默认配置之间的 delta。Substrate-first engineering，应用到这个席位上。

一个足够贴近客户的沙盒，在那里测得的每案件成本才有意义。Zeta 的首席数据官 Neej Gore 在 VentureBeat 上划出了界线：一边是沙盒，工程师在其中安装缺失的组件并反馈回去，使其随产品再次发布；另一边是泥潭，同一个组件在每个客户那里都要手工搭建。这是一篇厂商供稿，代表供应商视角，但这个区分无论如何都成立。

每次测试框架变更时，在每个客户的行数据上运行评测。框架变更会影响每个客户的成本，而且根据 HarnessTax，有时还会影响质量：在十二次模型对比中，有一个替代框架在九次中拥有最高的成功率。行数据来自回交包。如果第 3 部分没有发生，工程团队就是在盲改框架。评测即规格 讲的是一般情况。

在仪表盘上，与解决率并列显示每个客户的每已解决案件成本。Gore 还希望在上面加上产品化滞后时间，即从一线发现到下一个客户可用的已测试能力所需的时间。经济学章节 解释了为什么毛利率取决于它。

还有时间表。FDE 拉取请求的评审窗口，最多两周，由一名指定的工程师负责，就像回交由一名指定的产品人员负责一样。放任 FDE PR 闲置的工程团队，等于在第一层获得了从未定价过的技能。

这对一线人员和高层意味着什么

如果你是 FDE：你一直都知道客户真正需要哪个工具。现在你可以为它定价了。一份附带行数据和成本差异的 PR 是整个公司里最有说服力的文件，它能让你进入那个把框架通用化的房间。

如果你管理工程团队：框架是一个按客户核算损益的产品，而 FDE 是它最活跃的贡献者。Tunguz 的结束语就是简报：“有效的框架不是奇异成分的鸡尾酒：深刻的客户理解、一组相关评测，以及一个自动化爬山法的工厂。”FDE 就是客户理解和评测。为他们建好工厂，并写明他们可以改动什么。

本周可以尝试的一件事：选一个活跃客户，把他们的配置与发布的默认配置做对比。对于每一行涉及工具、循环或模型所见上下文的配置，问问工程团队是否知道它的存在，以及它每案件成本是多少。数一数没人定价过的行数。这就是缺失契约的大小。

这是 AI 产品管理 上持续论证的一部分：一旦构建变得廉价，稀缺的工作就是决定为所有人构建什么，而代码库契约就是工程团队与一线就由谁做决定达成一致的地方。

常见问题

前沿部署工程师可以在代码库中改动什么？+

三层，三条规则。客户层（提示词、业务规则、阈值、路由、连接器设置以及客户的评测行）归 FDE 所有：当天修改、无需评审，但有两个条件——必须纳入版本管理，且能用一条命令与出厂默认配置做差异对比。测试框架（工具集、Agent 循环、上下文组装、防护栏、模型选择）归工程团队所有：FDE 只能通过拉取请求来修改它，且该 PR 必须附带客户的评测行以及在沙箱中测得的单案例成本。核心层只归工程团队所有，FDE 绝不分叉它。

为什么 HarnessTax 研究对 FDE 很重要？+

因为测试框架正是 FDE 在现场所接触的那一层。HarnessTax 由 Melissa Z. Pan、Shuo Yang、Negar Arabzadeh、Wei-Lin Chiang、Ion Stoica 和 Matei Zaharia 于 2026 年 9 月 16 日发布，该研究在 SWE-bench Lite 和 Terminal-Bench 2.0 上通过 Claude Code、Codex CLI 和 Pi 运行了七个模型。Claude Fable 5 在 Claude Code 中的尝试解决率为 97.8%，在 Codex 和 Pi 中均为 96.7%，而 Claude Code 每次尝试的成本约为 Pi 的两倍（1.33 美元对 0.67 美元）。Tomasz Tunguz 的解读：GPT-5.6 Sol 在 Pi 上比在 Claude Code 上便宜 71%，在 42 组对比中质量差异没有统计学显著性，成本差距在 1.1 倍到 5.1 倍之间。FDE 添加的每一个工具和技能都是对测试框架的改动，因此对该客户而言就是成本的变化，而合同必须写明由谁来批准。

工程团队应该为前沿部署工程师提供什么？+

四件事。一份按客户划分的配置，纳入版本管理，并能用一条命令与出厂默认配置做差异对比，这样交接包中的差异是自动生成的，而不是靠记忆。一个足够贴近客户环境的沙箱，使在其中测得的单案例成本有意义。每次测试框架改动都要在每个客户的评测行上运行评测，因为测试框架的改动会影响每个客户的成本，有时还会影响质量。以及在仪表盘上、紧挨着解决率的位置，展示每个客户的单已解决案例成本。再加上一个评审窗口：一份搁置数周的 FDE 拉取请求，最终会变成第一层里一个没人定价过的技能。

FDE 应该为某个客户分叉核心产品吗？+

不应该。不为演示，也不为赶工期。分叉是一种自白，承认客户层太小了，正确的做法是提交一个第一层或第二层的拉取请求，为所有人移动这条边界。唯一的例外是 FDE 被嵌入某个产品小组一周来移动这条边界，那是戴着访客证的产品工程，不是部署。手册中的检验标准依然成立：拿出 FDE 最近为客户构建的三样东西，如果其中任何一样需要核心层的拉取请求，那这条边界就放错了位置。

Palantir 在 FDE 与产品工程师之间的分工是怎样的？+

根据 Nabeel Qureshi 的《Reflections on Palantir》，前沿部署工程师每周有三四天驻场工作，直接解决客户的问题，而不必担心过拟合；产品开发工程师则把 FDE 们构建的成果加以泛化，以便在其他地方销售。FDE 的代码追求快速完成任务——他礼貌地称之为技术债务和临时变通方案——而 PD 的代码则能干净地扩展。当两个团队编写不同的产物时，这条界线很容易维持。但在 Agent 产品中，这条界线贯穿于同一个提示词、同一个技能、同一个工具描述，这正是必须把它明确写下来的原因。

什么是《FDE 转型》系列？+

这是一个在 falkster.com 上每周发布两次的系列，面向前沿部署工程师以及围绕他们构建团队的领导者。第一部分提出核心论点：FDE 是从服务部门走来的产品构建者。第二部分论证 FDE 短缺本质上是一个产品问题。第三部分讲的是向产品团队的交接。第四部分是与工程团队之间的代码库契约。后续部分涵盖：谁与销售共同拥有对客户的承诺、与客户成功团队共度的第二个月、FDE 记分卡、职业发展、薪酬、从 FDE 型公司采购，以及什么时候根本不该雇用 FDE。
