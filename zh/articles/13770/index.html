Delta、Echo、Dev：头衔从何而来

原标题：Delta, Echo, Dev: where the title came from

LMVersity · 2026-09-02 · 约 6 分钟读完

摘要

本文追溯 Palantir 前沿部署工程师职位的起源：其业务拓展团队以北约音标字母命名，工程团队即 Delta。文章区分了三种角色——写生产代码的 Delta、平台开发工程师 Dev、非工程师的 Echo（部署策略师），并说明该角色因客户数据无法外传而必须驻场，Foundry 产品正是从现场手工“脏活”中提炼而来。作者指出 ElevenLabs、Glean、Decagon、Sierra、HappyRobot 等公司在新名义下复制了这一分工，并建议求职者判断公司实际招聘的是哪一类角色。

要点

  • Palantir 以北约音标字母命名业务拓展团队，工程师团队称 Delta。
  • Delta 与 Dev 通过同样的技术面试，但 Delta 隶属业务拓展，服务单一客户。
  • Echo 即部署策略师，通常非工程师，负责关系、推广与变革管理。
  • 因客户数据不能外传，工程师必须驻场；Foundry 由现场工作提炼而成。
  • ElevenLabs、Glean、Decagon、Sierra、HappyRobot 等以新名称重建了 Delta/Echo 分工。

Palantir 发明了这个职位，以北约音标字母为其命名，并将其拆分为工程师和非工程师两种角色。弄清一家公司实际招聘的是这两者中的哪一种，比职位名称本身更能说明问题。

  • 解释 Dev、Delta 和 Echo 的分工，以及这三者中谁编写生产代码。
  • 描述 Foundry 如何从一线工作中诞生，以及这说明产品源自何处。
  • 找出在 ElevenLabs、Glean、Decagon、Sierra 和 HappyRobot 中以新名称重现的 Delta/Echo 分工。

这个头衔听起来像军事用语，因为它确实是借来的。Palantir 的商务拓展团队以北约音标字母命名，而商务拓展内部的工程团队就是 Delta 团队。Palantir 自己 2019 年的博客文章正是这样说的：这个名字是“对 Palantir 早期岁月的回溯，当时商务拓展的每个团队都以北约音标字母中的一个字母命名”。

这个细节比看起来更重要。这些工程师并不在产品开发部门。他们是刻意被放在商务拓展部门的。

两个并排的容器。产品开发部门包含一个方框：Dev。商务拓展部门包含两个方框：Delta 和 Echo。一条线从 Delta 指向 Dev，标注为：一线工作转化为产品。

三个名称

Palantir 的文章用一句话划清了界限，这句话值得记住，因为面试官会用到它。

  • Dev 是产品开发部门的软件工程师。Dev 负责“开发和构建 Palantir 的软件平台”，端到端地负责平台组件。他们的定位是一项能力，服务众多客户。
  • Delta 是商务拓展部门的前沿部署软件工程师。Delta 负责“向客户部署软件平台”，针对单一客户的关键业务问题进行定制。他们的定位是一个客户，运用多种能力。
  • Echo 是部署策略师。通常不是工程师。负责客户关系、产品采用、变革管理和组织内部的政治协调。Barry McCardel 曾在 Palantir 担任 Echo 近五年，他对这个角色的公开描述最为清晰。

Delta 通过了与 Dev 相同的技术面试。这是关键事实。这个头衔虽然属于商务拓展部门，但门槛是工程门槛，而此后每一家复制这一模式的公司，要么保留了这条规则，要么悄悄打破了它——读一读他们的招聘启事，你就能分辨出是哪种情况。

为什么这个职位必须存在

两个机制，均有据可查。

第一个是访问权限。PostHog 的说明文章给出了实际的触发因素：Palantir 发现，即使是面向情报客户的简单演示，“也可能需要数周的保密协议和安全审查”。如果你无法把客户的数据拿出来交给你的工程师，那就把工程师派到数据所在之处。其他一切都源于这一约束。差旅、驻场节奏、安全问卷、本路径第 05 阶段中的气隙部署：它们都是“数据不能离开”的下游结果。

第二个是发现。Qureshi 对他在那里八年经历的描述是：FDE 深入制造、医疗、航空航天和网络安全现场，详细学习业务流程，并亲手做“杂活”。产品开发工程师观察现场不断重复的手工操作，然后构建工具将其自动化。他对旗舰产品如何诞生的总结是：FDE 去客户现场，做大量手工杂活，PD 工程师则构建工具来自动化这些杂活。用于数据摄取的 Magritte、用于可视化的 Contour、用于构建 Web 应用的 Workshop。

Palantir 如今出售的平台 Foundry，正是这一循环的产物。它不是先设计再部署，而是被提炼出来的。

McCardel 从策略师的角度描述了同样的事情：现场团队充当研发实验室，Foundry 在部署中“因需要而生”，之后才迁移到核心平台中。他也坦率地谈到了代价。“我们在免费做项目，”他写道，某些部署的利润率“实际上是负无穷”。

这就是整个模式所依赖的交易。你在早期接受服务形态的经济模型，以换取用其他方式无法获得的知识，然后把这些知识转化为产品。Qureshi 用利润率来描述回报：Palantir 在 2023 年达到了他所引用的 80% 毛利率，而 Accenture 是 32%。

规模有多大

Gergely Orosz 报告说，直到大约 2016 年，Palantir 雇用的 FDE 比传统软件工程师还多。Foundry 发布之后，更多 FDE 转向了核心产品工作。

仔细体会这个顺序。一家公司以现场工程师为主，现场工程师孕育了产品，而产品一旦存在，平衡就发生了转变。如果面试中有人问你，为什么一家 FDE 占比很高的公司不会自动变成咨询公司，诚实的答案是：这完全取决于这个比例是一个阶段还是一种永久状态。

角色的扩散

Ramp 的工程博客给出了时间线。这个角色“在 10 多年里一直很冷门”，Scale AI 和 C3.ai 在 2010 年代后期开始采用它，如今它在 OpenAI、Anthropic、Databricks、Ramp 以及早期 AI 创业公司中已经很常见。

将这一理念转化为招聘浪潮的文章是 Joe Schmidt 于 2025 年 6 月发表在 a16z 上的《Trading Margin for Moat》。其论点是：AI 创业公司应当接受早期较低的毛利率，以换取掌控客户的工作流程，其先例是 Salesforce、ServiceNow 和 Workday。文中被引用最多的一句话是：购买 AI 的企业“就像你奶奶拿到一部 iPhone：她们想用，但需要你来帮她设置”。值得注意的是，这篇 a16z 文章完全没有讨论 Palantir 的 Delta 和 Echo 历史。起源故事和当前的浪潮是两件独立的事情，只是后来被焊接在了一起。

Semafor 在 2025 年 7 月记录了这种效仿行为，点名了 OpenAI、Anthropic 和 H Company。H Company 的前 Palantir 出身 CEO 把这一论点说得很直白：拥有最好的技术固然好，但“要打造一家成功的公司，这肯定不够”。维基百科的词条现在将 AWS、OpenAI 和 Anthropic 列为该职位的雇主，并指出 AWS 向一个专注于将工程师嵌入客户团队的部门投资了十亿美元。

Bob McGrew 是 Palantir 的早期高管，后来成为 OpenAI 的首席研究官，他在 2025 年面向 Y Combinator 做了一场关于这套打法的演讲。相关总结将该模式描述为把“做不可规模化的事情”制度化。根据这些总结，他给那些想效仿这一模式的创始人的建议基本上是：别这么做，因为它极其容易变成一家低毛利率的咨询公司，这很危险。

这种分工，正在各地被复制

了解 Delta/Echo 区分的最大用处在于，你现在可以在新的名目下看到它。它已在以下公司被重建：

  • ElevenLabs，设有“Forward Deployed Engineer - Software Engineer”和“Forward Deployed Engineer - Strategist”职位。Strategist 职位只要求“基础 Python 能力”，并接受学生项目作为面向客户的经验证明。
  • Glean，设有前沿部署工程师，与前沿部署产品经理一起在小组中工作。
  • Decagon，设有 Agent Builder FDE，与 Agent 产品经理和 Agent 策略经理并肩工作。
  • Sierra，设有 Agent 工程师和 Agent 产品经理，另设一个 Forward Deployed Infrastructure Engineer 负责部署方面的工作。
  • HappyRobot，设有负责商业策略和变革管理的部署策略师，以及负责构建的 FDE。

这不是冷知识。它决定了你该申请哪个职位。如果一家公司两种职位都有，策略师路线看起来更容易进入，但不会把你纳入工程师职级体系。如果一家公司只有一个职位，而且除了名字之外处处都是策略师性质，那么职位描述会大谈工作坊、赋能和利益相关者对齐，却对你具体要构建什么含糊其辞。

还有第三种变体需要识别：基础设施型 FDE。Sierra 的职位描述是最清晰的公开范例，Palantir 的工程师在论坛上也描述过大量 AWS 管理、网络管理和容器相关的工作。这是一个真实存在的岗位和真实的职业阶梯，它与为律师事务所构建 AI Agent 并不是同一份工作。

从中应该得到什么

两点。

第一，起源解释了形态。之所以需要出差，是因为数据无法移动。之所以存在产品反馈闭环，是因为知识只存在于现场。这两者都不是装饰。

第二，你现在有了一个可以向任何使用这个头衔的公司提出的问题：你们招聘的是三者中的哪一种？一家无法清楚回答的公司，通常是在招 Echo，却把它称作 Delta，因为 Delta 更能吸引优秀的工程师。

在你的日志中写下一行：你的目标是哪一类，以及为什么。这条路径培养的是 Delta。如果在读完第 06 阶段后，你决定自己更想成为 Echo，那也是一个合理的答案，而且你应该尽早知道这一点，因为两者的准备方式不同。

在你的日志中简短注明：你的目标是 Delta/Echo 分界线的哪一侧，以及为什么。
