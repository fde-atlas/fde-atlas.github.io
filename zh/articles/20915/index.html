企业级 AI 架构：分层参考设计

原标题：Enterprise AI Architecture: The Layered Reference Design

Cloud Soft Solutions · 2026-10-06 · 约 13 分钟读完

摘要

文章提出一套企业级 AI 分层参考架构，覆盖从渠道、网关、编排到知识、模型、工具集成等十一个层次，以及安全、可观测性和治理三条横向控制带。作者强调架构应在层间边界处设置控制，并讨论身份传递、多租户隔离、数据驻留、成本控制和缓存等横切关注点。文中还给出逐层的自建与采购建议、单云托管、混合开源权重模型和纯本地部署三种模式，并以一家印度银行的示例架构说明各层如何落地。

要点

  • 提出十一个层次的企业 AI 分层参考架构。
  • 安全、可观测性、治理作为横向带包裹每次跨层调用。
  • 检索时按 ACL 过滤权限，混合向量与关键词搜索。
  • 用模型网关统一托管与开源模型的路由和预算。
  • 给出单云、混合、本地化三种部署模式及银行示例。

企业级 AI 系统远不止是 API 背后的一个模型。健全的企业级 AI 架构将系统划分为多个层次，使每一层只承担一项职责、与相邻层之间有清晰的契约，并且可以在不重写其余部分的情况下被替换。 本文正是这样一份参考设计：介绍每一层的职责、决策和典型技术，以及这些内容在云端、混合和本地部署中如何变化。

这是一份架构参考，而非流程指南。关于系统如何分阶段构建并设置签核关卡，请阅读前沿部署工程师如何将 AI 从 POC 推向生产环境。关于缺少某些层时会出什么问题，请参阅为什么 AI 演示在企业生产环境中失败。本文只聚焦组件与边界。

安全、可观测性和治理被绘制为横向条带，因为它们不是流程中的步骤。它们包裹着每一个跨越层边界的调用。LLM 应用架构总是在边界处失效，所以控制措施就应该放在那里。

逐层详解

1. 渠道层

职责： 在用户已经在工作的地方与他们相遇。在大多数企业中，这意味着 Microsoft Teams 或 Slack、现有的内网或门户、移动应用，以及供其他系统调用的 API。

设计决策： 保持渠道层精简。Teams 机器人应该只负责将消息转换为请求并渲染响应，仅此而已。业务逻辑一旦写进渠道适配器，第二个渠道出现时就会被重复实现。要尽早决定引用和审批在每个渠道中如何呈现。

示例： 基于 Bot Framework 的 Teams 机器人、React Web 客户端、用于系统间调用的 FastAPI 端点。

2. 网关层

职责： 验证调用者身份、确认终端用户是谁、按租户或团队实施速率限制和配额，并路由到正确的用例或版本。

设计决策： 网关是身份进入系统的地方，因此它必须生成一个令牌或上下文对象，将用户身份向下游传递（下文将详述身份传播）。它也是对新提示词或模型版本进行金丝雀路由的天然位置。

示例： Amazon API Gateway、Azure API Management、Kubernetes 上的 ingress controller、用于 OAuth/OIDC 的 Microsoft Entra ID。

3. 编排层

职责： 决定一个请求如何处理：单次检索并回答、确定性工作流，或者一个会规划、调用工具并循环的 AI Agent。它还负责维护会话状态、短期记忆和人机协作检查点。

设计决策：在任务已知的情况下，优先使用显式工作流（具有定义节点和边的图），而非开放式 Agent 循环。仅在路径真正多变时才使用 Agent。限制迭代次数，持久化状态以便长时间运行的任务可以恢复，并在任何更改记录系统的操作之前设置审批步骤。

示例：LangGraph 用于有状态图和多 Agent 模式，LangChain 用于组件，Amazon Bedrock Agents 作为托管选项，用 Python/FastAPI 服务承载编排代码。

4. 知识

职责：摄取文档和记录，对其进行分块和嵌入，保持内容更新，并在查询时检索正确的段落，同时根据用户可见权限进行过滤。这是企业中 RAG 架构的核心。

设计决策：

  • 混合搜索。向量搜索能找到同义改写；关键词搜索（BM25）能找到产品代码、条款编号和名称。将两者结合并添加重排序器。
  • 检索时的权限控制。将源系统的访问控制列表与每个分块一起存储，并在查询时据此过滤。绝不要先检索再在提示词中过滤。
  • 增量摄取。管道必须能处理源系统的更新和删除，而不仅仅是新增，并记录每个分块来自哪个文档版本。

示例：PostgreSQL 配合 pgvector（向量、元数据和全文检索在同一数据库中），更大规模语料库可用 Amazon OpenSearch 或 Azure AI Search，Bedrock Knowledge Bases 作为托管管道。关于该概念本身，请参阅什么是 RAG。

5. 模型层

职责：通过统一的内部接口提供对语言模型、嵌入模型和重排序模型的访问。

设计决策：在应用与提供商之间放置一个模型网关（或路由器）。它负责保管凭证、执行各团队预算、记录 token 用量、故障转移，并将简单请求路由到更小、更便宜的模型。没有它，每个团队都会硬编码某个提供商。明确哪些类别的数据可以发送到哪些模型，并写成文档。

示例：Amazon Bedrock、Azure OpenAI 和 Vertex AI 上的 Google Gemini 提供托管模型；必须留在您网络内的工作负载可使用在 GPU 节点上运行的开源权重模型；在所有这些之上构建或采用一个网关服务。

6. 工具与集成

职责：让 Agent 能够读取企业系统并对其执行操作：工单系统、CRM、ERP、代码仓库、核心银行系统。

设计决策： 将每个系统只封装一次，置于描述清晰的接口之后，而不是让每个 Agent 直接调用原始 API。模型上下文协议（MCP）是 Anthropic 于 2024 年底推出的开放协议，它标准化了 AI 应用发现和调用工具、读取资源的方式，因此一个 ServiceNow MCP 服务器可以服务多个 Agent。在底层，MCP 服务器仍然调用系统的常规 API，使用用户的委托身份，并将读取与写入工具分开。相关权衡见 MCP vs API。

示例： 用于 ServiceNow、Jira 和 GitHub 的 MCP 服务器；用于遗留系统的 REST 或 SOAP 客户端；用于异步操作的消息队列。

7. 安全

职责： 在每个边界检查输入和输出：提示词注入检测、PII 检测与脱敏、主题和内容过滤、输出模式校验，以及工具调用前的策略检查。

设计决策： 将检索到的文档和工具输出视为不可信输入，而不仅仅是用户消息。护栏是一层防御，不能替代工具上的最小权限控制。完整的威胁模型见 AI security for enterprises。

示例： Amazon Bedrock Guardrails、Azure AI Content Safety、编排代码中的自定义校验器。

8. 数据

职责： 保存应用自身的状态（对话、反馈、审批），以及 Agent 用作上下文的事件和特征，例如客户最近的交易或工单的历史记录。

设计决策： 将运营数据与日志和追踪分开，按数据类别设置保留期限，并决定对话历史存储在哪里以及谁可以读取。

示例： 用于应用状态的 PostgreSQL；Kafka 或 Amazon EventBridge 等事件流；在已有 ML 特征时使用的特征存储。

9. 平台

职责： 可靠、可重复且安全地运行一切。

设计决策： 大多数企业 AI 平台架构将 Kubernetes（控制、GPU 调度）与无服务器架构（突发性、无状态的部分）相结合。一切都以代码形式定义，通过流水线部署，并在各环境间逐级推进，提示词、模型配置和索引版本被视为可部署的制品。

示例： Docker、Kubernetes（EKS、AKS、GKE）、AWS Lambda、Terraform、GitHub Actions、用于 GitOps 的 Argo CD。这些如何映射到 AWS 服务，请参见 AWS for AI engineers。

10. 可观测性与评测

职责： 跨层追踪每个请求（检索到的分块、提示词、模型调用、工具调用、延迟、token、成本），收集用户反馈，并在每次变更时运行评测集。

设计决策： 使用 OpenTelemetry 进行埋点，使追踪数据流入企业现有的监控系统，并在其上使用支持 LLM 的工具。评测是 CI 流水线的一部分，而不是偶尔进行的工作。详情见 AI observability。

示例： OpenTelemetry、LangSmith、Langfuse、用于 RAG 指标的 Ragas、CloudWatch 或 Azure Monitor。

11. 治理

职责： 了解哪些模型、提示词、数据源和 Agent 正在生产环境中运行，由谁负责，通过了哪些风险审查，并对系统做了什么以及为什么这样做保留审计记录。

设计决策： 维护一个用例及其所用模型和数据的登记表；在新用例或新数据类别上线前要求进行审查；确保审计日志不可篡改。

示例： 模型和提示词登记表、流水线中的策略即代码、集中式审计日志，以及用于对平台本身进行基于角色的访问控制的 Microsoft Entra ID 组。

横切关注点

身份传播。 最终用户的身份必须从渠道经过网关、编排层，并传递到每一次检索和工具调用中。如果 Agent 使用共享服务账户调用 ServiceNow，它就能看到并执行该账户所能做的一切，而不管是谁发起的请求。使用令牌交换或代表用户（on-behalf-of）流程，让下游系统执行它们自己的权限控制，并在每条追踪记录中记录用户身份。

多租户。 无论租户是业务部门、国家还是外部客户，都要在索引（独立索引或强制租户过滤器）、会话存储、缓存和配额中对它们进行隔离。一个忽略租户的共享缓存就是一个随时可能爆发的数据泄露隐患。

数据驻留。 了解每个模型端点在哪个区域处理数据、嵌入向量和日志存储在哪里，以及是否启用了任何跨区域推理。对于受监管的印度工作负载，这通常意味着固定使用印度的云区域，并确保路径上的每个托管服务都遵守这一要求。

成本控制。 在模型网关处按用例和按团队归因令牌用量，并设置预算和告警。可用的手段：更小的模型、精简的上下文、限制 Agent 循环次数。

缓存。 三种不同的缓存：用于长且稳定的系统提示词的提供商提示词缓存；用于重复问题的响应缓存（以租户、用户权限和索引版本作为键，绝不能仅以问题文本作为键）；以及摄取过程中的嵌入缓存。重新索引时使其失效。

在真实客户的环境中设计这些关注点，正是前沿部署工程的核心。如果你想通过一次完整的模拟项目来实践它，而不是仅仅阅读相关内容，Cloudsoft 的 AI 前沿部署工程师课程 将通过五个企业项目和 GlobalBank 毕业项目带你完成这一过程。

逐层分析：自建还是采购

没有企业会自建或采购每一层。下表给出了一个典型的起始选择。

层级通常采购 / 使用托管服务通常自建或配置
渠道Teams、Slack、现有门户轻量级机器人或 UI 适配器
网关API Gateway / APIM、Entra ID路由规则、配额、金丝雀发布配置
编排框架（LangGraph）、简单场景使用托管 Agent工作流、Agent 图、审批步骤
知识向量数据库或搜索服务、简单语料库使用托管摄取连接器、分块、ACL 同步、数据新鲜度
模型层通过云提供商使用托管模型模型网关策略、路由逻辑
工具可信场景使用供应商提供的 MCP 服务器面向内部系统和遗留系统的 MCP 服务器
安全托管护栏和内容服务领域策略、输出验证器
数据托管 PostgreSQL、事件流模式、保留规则
平台托管 Kubernetes、无服务器Terraform 模块、流水线、GitOps
可观测性 / 评测LangSmith 或 Langfuse、云监控评测集、仪表板、告警
治理审计日志、策略工具注册表、评审流程、所有权

一个实用的判断标准：当某一层承载了业务特有的内容时就自建，无差异化的基础管道则直接采购。

三种部署模式

模式 A：单云托管

一切都在一个云上运行，使用其托管 AI 服务：AWS 上的 Amazon Bedrock、Azure 上的 Azure OpenAI，或 Google Cloud 上 Vertex AI 的 Gemini。模型、护栏、知识库和 Agent 与企业其他资产处于相同的网络、身份和日志边界内，这使它成为已标准化于单一云的企业最快的路径。风险在于耦合：保持模型网关和编排代码与提供商无关，这样后续迁移只需修改配置，而非重写代码。针对 AWS，Cloudsoft 的 AWS 培训 和 AWS 解决方案架构师课程 涵盖了该模式所依赖的网络、IAM 和服务设计。

模式 B：混合部署与开放权重模型

托管模型处理通用推理，而开放权重模型则运行在企业自己的 Kubernetes GPU 节点上，用于敏感数据、分类或提取等大批量窄任务，或需要微调模型的场景。模型网关是让这一切可行的关键：应用调用统一接口，路由策略根据数据类别和任务决定由哪个模型服务请求。代价在于运维：GPU 容量规划、模型服务、补丁更新以及对你托管的每个模型进行评测。Kubernetes 培训 是运行该服务层的基础。

模式 C：本地部署或物理隔离

某些受监管或与国防相关的工作负载无法向任何公共云端点发送数据。此时每一层都在数据中心内运行：本地 GPU 上的开放权重模型、自托管的向量存储、自托管的可观测性，以及内部软件包和模型镜像。需要为有限的 GPU 容量、较慢的模型升级、自托管护栏以及更长的变更审批周期做好规划。分层设计依然适用，只是每层内部的技术有所不同。

一个示例银行架构

设想一家中型银行，其技术团队由海得拉巴的 GCC 管理，希望在一个平台上实现三件事：面向网点员工的政策助手、起草客户投诉回复的 Agent，以及负责事件分流的 IT 运维 Agent。对应到各层，架构大致如下：

  • 渠道： 员工使用 Teams；IT 运维使用内部服务台门户。
  • 网关： Azure API Management 搭配 Microsoft Entra ID；按业务部门设置配额。
  • 编排： EKS 上的 LangGraph 服务；投诉流程是固定工作流，在内容送达客户之前设有强制的人工审批节点。
  • 知识： 使用带 pgvector 的 PostgreSQL 存储政策通函和产品条款，网点和角色 ACL 每晚从文档管理系统同步，并带有生效日期过滤器，确保被取代的通函永远不会被引用。
  • 模型层： 模型网关路由到印度 AWS 区域的 Amazon Bedrock 模型；包含账户详情的投诉文本在离开银行 VPC 之前会被脱敏。
  • 工具： 用于 ServiceNow（事件）和投诉系统的 MCP 服务器，读取工具与写入工具分离，写入工具需要审批令牌。
  • 安全： Bedrock Guardrails 加上一个银行专用的校验器，阻止任何包含账号的回复。
  • 数据： PostgreSQL 中的对话和审批记录，保留期限与银行的记录政策保持一致。
  • 平台： Terraform、GitHub Actions、Argo CD，独立的开发、UAT 和生产账户。
  • 可观测性： OpenTelemetry 追踪接入 Langfuse 和 CloudWatch；在 CI 中使用 Ragas 针对版本化的测试集进行评测。
  • 治理： 由风险团队评审的用例登记册，对每次工具操作及其所服务的用户保留不可篡改的审计日志。

关键在于复用：第二和第三个用例可以直接接入已经存在的各层。

架构反模式

  • 单体聊天机器人。 渠道、提示词、检索和工具调用都放在一个服务里。每次改动都有风险，且没有任何东西可复用。
  • 到处使用提供商 SDK。 每个团队直接调用模型提供商，因此没有统一的成本视图，没有故障转移，也难以更换模型。
  • 服务账户 Agent。 Agent 使用强大的共享身份而非用户的委托身份来执行操作。
  • 在提示词中过滤权限。 检索受限文档，然后要求模型不要展示它们。
  • 万事皆 Agent。 对三步工作流就能更廉价、更可预测地完成的任务，使用开放式 Agent 循环。
  • 仅用向量检索。 缺少针对标识符和代码的精确匹配搜索。
  • 可观测性事后补。 没有追踪记录，因此无法解释错误的回答。

常见问题

什么是企业 AI 架构？

企业级 AI 架构是一系列层次、组件和边界，使组织能够安全、可靠地大规模运行 AI 助手和 AI Agent。它涵盖渠道、网关、编排、知识检索、模型、工具集成、安全、数据、平台、可观测性和治理，还包括身份、数据驻留和成本等横切关注点。

什么是模型网关？我需要它吗？

模型网关是位于你的应用程序与模型提供商之间的内部服务。它负责凭证、路由、故障转移、Token 日志记录和预算管理。一旦涉及多个团队或多个模型，你就需要一个网关来控制成本，并在不修改代码的情况下更换模型。

我应该使用 AI Agent 还是工作流？

只要步骤是预先已知的，就应使用确定性工作流；只有在路径真正取决于模型发现的内容时，才使用 AI Agent。许多生产系统是包含一两个 AI Agent 步骤的工作流。

在 RAG 架构中，文档权限应该在哪里强制执行？

在检索时，直接在搜索查询本身中执行。每个分块都携带来自其源系统的访问控制信息，查询会根据当前用户的身份和所属组进行过滤。受限内容绝不应进入模型的上下文窗口。

MCP 在企业级 AI 架构中处于什么位置？

MCP 位于工具与集成层。MCP 服务器封装企业系统（如 ServiceNow 或 Jira），并将其能力暴露为任何兼容 MCP 的 AI Agent 都能发现和调用的工具。它并不取代系统的 API，而是标准化 AI 应用使用该 API 的方式。

AI 应用应该用 Kubernetes 还是 Serverless？

大多数企业两者都用。Kubernetes 适合长时间运行的编排服务、GPU 上的自托管模型以及需要精细控制的工作负载。Serverless 适合事件驱动的数据摄取以及突发性的无状态函数。应按组件逐一选择。

混合 AI 架构与单一云架构有何不同？

混合架构将云提供商的托管模型与你自行运行的开源权重模型相结合，通常是为了将敏感数据保留在自己的网络中，或降低高吞吐量任务的成本。模型网关会根据数据类别和任务来路由每个请求。

工程师设计这种架构需要哪些技能？

云架构与网络、身份与访问管理、Python 服务开发、RAG 与 AI Agent 设计、Kubernetes 与基础设施即代码、CI/CD、可观测性与评测，以及与安全和风险团队协作的能力。
