AI 工程师面试题：LLM API、RAG 与评测

原标题：AI Engineer Interview Questions: LLM APIs, RAG and Evals

Prepare.sh · 2026-09-20 · 约 13 分钟读完

摘要

文章基于真实招聘启事、公司公开的面试流程和候选人第一手记录，整理了 AI 工程师（含前沿部署工程师等职位）的高频面试题及答案。作者指出职位名称混乱，多数岗位不叫 AI Engineer；考察重点是提示词、Agent 与评测三件套，RAG 出现频率低于预期；后端基本功仍是底线，框架名几乎不被要求。文章还详解了 429 限流与费用上限的区别、结构化输出仍需校验、检索与生成错误的区分、pgvector 索引取舍、评测集设计，以及缓存与批处理对成本和吞吐的影响。

要点

  • 职位名称不统一，只搜 AI Engineer 会错过大部分岗位。
  • 核心要求是提示词、Agent、评测三件套，框架名几乎不出现。
  • 429 可能是限流也可能是费用上限，盲目重试会造成自伤。
  • 检索失败与生成失败要先分开测量，再决定修复方向。
  • 缓存不仅省钱，还能提升吞吐，批处理可享五折。

下面的每一个问题都能追溯到你自己可以阅读的内容：一份真实的招聘启事、一家公司自己对面试流程的描述，或者一篇署有姓名和日期的第一人称叙述。这里没有任何一条是我编造的“常见问题”。答案都基于厂商文档，因为面试官自己的思维模型也正是来源于此。

在看问题之前先提醒一句。这类工作的职位名称尚未统一。在我浏览过的招聘启事中，只有一份，来自 Stripe，叫作“AI Engineer”。其余的都叫“Forward Deployed Engineer（前沿部署工程师）”、“Applied AI Engineer（应用 AI 工程师）”、“Member of Technical Staff”或“Product Engineer, AI”。如果你只用“AI Engineer”这几个词去筛选职位板，你会错过大部分市场。

招聘启事真正要求的是什么

Anthropic 的应用 AI 工程师招聘启事要求“具备 LLM 的生产经验，包括高级提示词工程、Agent 开发与框架、评测框架、对话记录分析、MCP 以及大规模部署”。Glean 的创始前沿部署工程师招聘启事几乎以相同的顺序说了同样的话：“你已经在真实世界中交付过 AI 驱动的解决方案，提示词工程、Agent 开发、评测框架、大规模部署。而不只是原型。”

这个三件套，提示词、Agent、评测，是反复出现的核心。RAG 出现的频率比它名声所暗示的要低一些。Notion 要求有“MCP、API、LLM 应用、提示词工程、检索/RAG 系统或工作流编排”方面的经验，Pinecone 的现场工程招聘启事则要求“熟悉嵌入、相似性搜索、推荐系统和 RAG 的概念”。Stripe 要求“有构建和部署 AI Agent、LLM 驱动的工具或工作流自动化的经验，超越基础提示词工程”，外加“扎实的后端工程基础”。

有两点值得注意，因为它们会改变你的准备方式：

后端基础仍然是底线。 Cursor 的招聘启事会问你是否有“处理过生产可靠性问题（指标、告警、安全发布、事故响应）”。Intercom 说得更直白，把潜台词挑明了：“不需要机器学习经验。我们相信，凭借出色的软件工程技能，你可以立即高效地开展工作，并在团队工作中学习机器学习。”

框架名称大多缺席。 LinkedIn 的 2026 年职位上升榜（2026 年 1 月 7 日发布）将人工智能工程师列为美国增长最快的第一大职位，并列出的热门技能为 LangChain、RAG 和 PyTorch。然而，在我读过的所有招聘启事中，没有一份把 LangChain 列为要求，连 LlamaIndex 自己的也不例外。学习概念本身，而不是某个框架的 API 表面。

关于薪酬，要把你看到的每一个数字都当作在衡量不同的东西。Stack Overflow 2025 年开发者调查显示，AI/ML 工程师岗位在美国的总薪酬中位数为 189,500 美元，数据来自 23,928 份自报的薪资回复。这个数字与招聘指南中的基本工资区间不可比，也与大型科技公司以股权为主的总额不可比。

你会遇到的面试形式

Janvi Kalra 在加入 OpenAI 之前面试过 46 家 AI 公司，她于 2025 年 5 月向 Gergely Orosz 描述了现状：“AI 工程面试五花八门。似乎并不存在一种‘AI 工程师面试’的固定格式。”可以预期会有算法编程、系统设计、带回家的构建任务以及对 LLM 细节的深入探讨的某种组合。

值得专门准备的新形式是现场构建。Sierra 于 2026 年 4 月公布了自己的面试流程：规划阶段，“候选人主导构思，面试官通过提问来完善它”；构建阶段，“面试官离开，候选人在 2 小时内使用自己选择的 AI 工具和框架将想法变为现实”；以及评审阶段，双方“就关键产品流程和所做的选择进行辩论”并阅读代码。

Applied Intuition 在 2026 年 7 月描述了类似的结构：先是“45 分钟不使用 AI 的编程任务”，然后是 45 分钟开放式的系统设计问题，最后是“两小时时间，使用任何他们想用的 AI 模型和任何框架，构建他们刚设计的系统的可运行原型”。

注意两者的共同模式：AI 工具在一轮中被禁止，在另一轮中则是必需的。Anthropic 公布的候选人指南在谈到现场面试时说：“这完全靠你自己——除非我们另有说明，否则不得使用 AI 辅助”，而 Datadog 的指南则说：“对于某些岗位，我们会进行 AI 辅助编程面试……如果你将参加 AI 编程面试，我们会提前明确告知。”问清楚你参加的是哪一种。没人会介意这个问题，而猜错的代价很高。

“我们的生产环境开始收到 429 错误了。请带我梳理一遍排查过程。”

这个问题能区分真正上线过产品的人和只做过原型的人，而且它直接对应招聘启事中“大规模部署”的表述。

答案。首先，读取响应内容，因为 429 并不只有一种含义。速率限制的情况会告诉你需要等待多久。OpenAI 的速率限制文档明确指出：“如果存在

Retry-After

字段，请遵循它，降低请求速率，然后逐步提高”，并且“如果

Retry-After

字段缺失，则增加重试之间的延迟，并加入一个小的随机延迟。”响应头会告诉你超出了哪个配额：

x-ratelimit-remaining-requests

和

x-ratelimit-remaining-tokens

，以及对应的

-limit-

和

-reset-

变体。Anthropic 在

anthropic-ratelimit-requests-remaining

,

anthropic-ratelimit-input-tokens-remaining

和

anthropic-ratelimit-output-tokens-remaining

下暴露了同样的机制，另外还有一个

retry-after

字段，文档说明为“等待到可以重试请求为止的秒数。更早的重试将会失败。”

然后是大多数候选人都会漏掉的情况。429 也可能意味着你的额度用完了，对这种情况无限重试等于自己给自己制造故障。Anthropic 的消费上限响应返回相同的

rate_limit_error

类型，但没有

retry-after

头部，且

error.details.error_code

为

enforced_spend_limit_reached

。OpenAI 说得很直白：“不要重试配额、账单或其他需要你采取行动的错误。”

一个出色的回答会补充： 在供应商前面加一个队列，让背压由你自己掌控；加入抖动，避免重试同步形成惊群效应；在剩余 token 头部归零之前就基于它们告警，而不是等错误出现后再告警；并为面向用户的请求准备一个备用模型或降级路径。

可能的追问： 在你的监控指标中，如何区分速率限制和消费上限？一个流式请求中途失败时你会怎么处理？你会重试一个非幂等的工具调用吗？

“如何获得真正可解析的输出？”

答案。 别再解析自然语言了。OpenAI 的结构化输出功能“确保模型始终生成符合你提供的 JSON Schema 的响应”，而且文档对旧方法说得很直接：结构化输出“是 JSON 模式的演进”，并且“只有结构化输出才能保证符合 Schema”。工具侧也是同样的思路，

strict: true

意味着函数调用“可靠地符合函数 Schema，而不是尽力而为”。Anthropic 的工具文档也印证了这一点：“在你的自定义工具定义中添加

strict: true

，以确保 Claude 的工具调用始终完全符合你的 Schema。”

然后是能让你拿到 offer 的关键部分：说明你仍然会做校验。文档列出了真实的失败路径：拒绝信息出现在单独的

refusal

字段中、响应被 token 上限截断，以及不支持的 Schema 特性。符合 Schema 不等于正确或完整，你的代码必须能处理模型拒绝作答的情况。

追问： 当响应被截断时，你的解析器会怎样？一个已经上线的 Schema 你如何做版本管理？校验失败时重试放在哪里，又如何防止这个循环烧光预算？

“我们的支持机器人回答得很有信心，但完全是错的。”

答案。 在动提示词之前，先把检索失败和生成失败区分开，因为两者的修复方法毫无关联。OpenAI 的准确性指南指出了两种检索失败模式：你可能提供了“错误的上下文，导致模型根本无法回答”，或者“太多无关的上下文，淹没了真正的信息并引发幻觉”。先做度量。Ragas 把这个问题划分得很清晰：上下文召回率衡量“有多少相关文档（或信息片段）被成功检索”，而忠实度“衡量

response

与

retrieved context

的事实一致性”。低召回率是检索问题。高召回率但低忠实度是生成问题。

在生成方面，Anthropic 的幻觉指南给出了具体做法而非空泛理念：“允许 Claude 说‘我不知道’”，要求模型在回答长文档问题前先逐字提取引文，并让论断可审计——“如果找不到引文，就必须撤回该论断。”他们的 Citations API 把同样的理念做成了产品功能，返回“支持每个论断的确切段落”。文档对上限很坦诚，你在面试中也应如此：这些技术“并不能完全消除幻觉”。

在检索方面，要知道分块策略对数字的影响比提示词措辞更大。Anthropic 的 Contextual Retrieval 文章报告了随着每种技术的加入，top-20 检索失败率的下降情况：

这些是 Anthropic 在自己的评测集上发布的数字，并非自然规律，但结果的形态（混合搜索优于纯向量搜索，重排序再次带来提升）与大多数团队的发现一致。

追问： 你会如何在用户之前发现这类失败？你的评测集是什么样的，标准答案是谁写的？什么时候正确的解决方案是“展示来源，让人类来判断”，而不是任何技术手段？

“选一个向量索引并为之辩护。”

答案。 在 pgvector 中，这种权衡各有整整一段文档说明。HNSW“具有比 IVFFlat 更好的查询性能（就速度-召回权衡而言），但构建时间更慢，且占用更多内存”。IVFFlat“比 HNSW 构建更快、占用内存更少，但查询性能较低”。

能体现你真正用过它们的操作细节是：IVFFlat 需要从数据中学习其列表，所以 pgvector 建议你“在表中已有一些数据之后再创建索引”，而 HNSW“由于没有训练步骤，可以在表中没有任何数据时创建索引”。这一个差异就决定了哪种索引适合每晚重建索引的流水线，哪种适合持续摄取的流水线。

HNSW IVFFlat
相同召回率下的查询速度更好更差
构建时间更慢更快
内存更多更少
构建前是否需要数据否是

如果想脱颖而出，要主动提到过滤。Qdrant 的文档警告说“当使用过于严格的过滤器时，HNSW 图开始失效”，而这正是每个多租户产品中都会出现的情况：只搜索该用户的文档。你可以在 Qdrant 工作区中实验这一点，而不是空泛地争论。

追问： 你如何选择

m

和

ef_construct

？你的召回率目标是多少，是如何测量的？如果集合增长 100 倍会有什么变化？

“你怎么知道新版本是否更好？”

评测设计在职位要求中频繁出现（Anthropic、Glean 和 LlamaIndex 都明确提到），尽管它很少拥有独立的面试环节。请把它当作其他所有问题的追问来准备。

答案。 首先要拒绝目标含糊不清的版本。Anthropic 的文档对比了一个糟糕的成功标准——“模型应该能很好地进行情感分类”——和一个好的标准：“情感分析模型应在一个由 10,000 条多样化 Twitter 帖子组成的留出测试集上……达到至少 0.85 的 F1 分数……这比当前基线提升了 5%。”

然后是三条说起来容易、却难以反驳的规则。镜像真实任务的分布，包括边缘情况。将评分自动化，以便每次变更都能运行评测，并且“数量优先于质量：信号略低但数量更多的自动化评分问题，胜过数量更少但需要人工精细评分的高质量评测。”如果使用模型作为裁判，“通常的最佳实践是使用与生成被评测输出不同的模型来进行评估”。

OpenAI 的指南也指向同一方向，倡导评测驱动的开发，并点名了两种值得原样引用给提问者的反模式：“过于笼统的指标：仅依赖困惑度或 BLEU 分数等学术指标”，以及“凭感觉的评测：把‘看起来效果不错’当作评估策略”。

一个能让你显得读过发布说明的当前事实：不要把答案锚定在某个特定的评测平台上。OpenAI 于 2026 年 6 月 3 日宣布弃用其 Evals 平台，现有评测将于 2026 年 10 月 31 日变为只读，仪表盘和 API 计划于 2026 年 11 月 30 日关闭，并公布了迁移到 Promptfoo 的路径。工具会不断更迭。你拥有的带标注示例数据集才是资产。

追问： 在第一天、还没有流量时，评测集从哪里来？如何防止它腐化？你的离线与在线指标相关性如何，当两者不一致时你会怎么做？

“把这个功能的成本和延迟减半。”

答案。 在追逐模型之前，先攻克 token 和往返次数。OpenAI 的延迟指南列出的优化杠杆值得牢记：“生成更少的 token”、“使用更少的输入 token”、“发起更少的请求”、“并行化”、“让用户等待更少的时间”，以及人们最容易忘记的一条：“不要默认使用 LLM。”

然后是缓存——对于任何拥有长系统提示词或大文档的场景，这才是真正省钱的地方。Anthropic 的定价结构：在 5 分钟 TTL 下，缓存写入成本为基础输入价格的 1.25 倍，1 小时 TTL 下为 2 倍，而在大多数模型上，“缓存读取 token 的价格为基础输入 token 价格的 0.1 倍”（Claude Opus 5.5 和 Sonnet 5.5 为 0.05 倍，Claude Fable 5.1 和 Mythos 5.1 为 0.025 倍），且缓存“每次被使用时都会免费刷新”。OpenAI 一侧也是同一数量级，缓存输入按未缓存费率的一部分计费。

这个问题的关键细节在于：缓存买到的是吞吐量，而不仅仅是省钱。Anthropic 的速率限制文档写道：“对于大多数 Claude 模型，只有未缓存的输入 token 才计入你的 ITPM 速率限制”，并给出了他们自己的计算示例：“在 2,000,000 ITPM 限制和 80% 缓存命中率的情况下，你实际上每分钟可以处理 10,000,000 个总输入 token。”如果你的瓶颈是速率限制而不是成本限制，那么缓存命中率就是你的容量规划。

对于任何不需要立即得到答案的任务，两家提供商都对批量处理打五折。离线数据增强、数据回填和评测运行都应该归入这一类。

追问： 什么会使你的缓存失效，实际中这种情况多久发生一次？你如何把首 token 时间与总时间分开测量？这个系统的哪些部分无法缓存，为什么？

“为我们设计一个 RAG 系统”

这个提示词的一个真实版本，来自 Mai Chi Bao 对他 2025 年 5 月 LLM 面试的记述：“为一个客服聊天机器人设计一个可用于生产环境的系统，该机器人使用微调后的 LLM 基于公司文档来回答查询。”明确的约束条件包括：出于数据隐私考虑使用开源模型、支持 100+ 并发用户、响应时间低于 2 秒，以及答案必须基于文档。交付物包括架构图、模型选型论证、检索细节、部署与扩展方案、监控与评测计划，以及成本估算。

如何回答。 围绕约束条件展开，而不是围绕架构图。在 100 个并发用户下实现低于 2 秒的响应，首先是一个服务问题（批处理、KV 缓存、尽早流式输出首 token），然后才是模型问题。数据隐私排除了托管 API，这会把你的成本模型从按 token 计费变成按 GPU 小时计费。“基于公司文档”意味着要有引用和一个“我不知道”的兜底路径，而不是一个更好的提示词。

说出你不会构建什么。OpenAI 自己的指南指出“提示词工程通常是最好的起点”，并且当“模型因为训练集中没有相关内容而缺乏上下文知识”时应优化上下文，而当输出“不一致……格式”或语气不对时才优化模型本身。用微调来弥补知识缺口是典型的错误答案，面试官会专门留意这一点。

“你会在这里使用 Agent 吗？”

答案。 先定义术语，因为这个领域一半的分歧都源于词汇。Anthropic 的工程博文划出了这条界线：“工作流是通过预定义代码路径来编排 LLM 和工具的系统。而 Agent 则是 LLM 动态主导自身流程和工具使用的系统。”

然后给出那个“无聊”的建议，也就是文档中的建议：“从简单的提示词开始，通过全面的评测进行优化，只有在更简单的方案不够用时才引入多步 Agent 系统。”说出你会优先尝试的模式：提示词链、路由、并行化，并说明使用 Agent 的代价：不确定性、工具调用带来的更大影响范围，以及难度大得多的调试。如果任务有一组已知的步骤，就把步骤写出来。

追问： 你如何限制 Agent 的花费和步数？工具故障会对循环造成什么影响？你如何测试一个每次运行路径都不同的东西？

如何练习这一点

阅读你目标公司的具体招聘启事，借用他们的词汇。当 Anthropic 提到 MCP、Glean 提到评测框架时，这些就是他们的面试官在复盘时使用的词。

然后开始刷题。我们为 AI 实验室维护了按公司分类的题库，包括 Anthropic 和 OpenAI，而这些面试流程仍然会考察的后端基础知识都在后端工程面试课程中。如果你觉得检索和存储方面比较薄弱，我们那篇关于将 Redis 用作 LLM 和 RAG 应用记忆层的文章涵盖了你会被要求在白板上画出的各个组成部分，而云服务中的提示词工程一文则涵盖了招聘启事放在首位的那部分工作内容。

最后一条建议，来自面试形式如今的演变：做一个小东西并把它上线。一个能说出“我在生产环境运行过这个，这是我的评测集，这是 429 风暴教给我的东西”的候选人，无需被问就能回答本页的每一个问题。
