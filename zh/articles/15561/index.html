RAG 系统设计面试：一份 FDE 的完整解答示例

原标题：RAG system design interview: a worked FDE answer

FDE Interview Prep · 2026-09-25 · 约 13 分钟读完

摘要

这篇文章针对 AI 方向的 FDE 面试，完整演示了如何回答“设计一个 RAG 系统”这类系统设计题。作者指出，好的答案应从客户的文档、用户和权限出发，而非直接画向量数据库架构图。文章引用 Cohere、Ramp、Databricks、Scale AI 等公司的 FDE 招聘要求，说明 RAG 能力是常见考察点，并给出一个保险公司的具体案例，按范围界定、文档解析与分块、混合检索与重排序、检索时权限过滤、带引用的回答、评测与成本延迟预算的顺序展开，最后以第一版上线范围和常见追问收尾。

要点

  • 强答案从客户文档、用户与权限出发，而非向量数据库。
  • 混合检索负责召回，重排序负责顶部精度，两者分开评测。
  • 权限必须在检索层过滤，不能靠系统提示词约束模型。
  • 引用须由代码校验：ID 存在、引文属实、段落支持论断。
  • 收尾应界定第一版范围，并说明暂缓扫描件、Agent 与微调的原因。

一个出色的 RAG 设计答案必须涵盖的内容

这道题的题干故意写得很短。“为我们的内部文档设计一个 RAG 系统”没有说明用户是谁、他们可以查看哪些文档、答错的代价是什么。把填补这些空白当作任务本身：任何人都能画出“先检索、后生成”的 RAG 循环；让答案出彩的是围绕它的一切。

完整答案的编号流程

在我们的方法中，你要先说出这个计划，以便面试官进行引导：

  • 界定范围。 文档、用户、权限，以及答错的代价。
  • 摄取。 按结构解析，在每个分块上保留元数据和访问列表，并增量更新。
  • 分块。 按文档自身的单元切分：章节、条款、一张工单及其修复方案。
  • 检索。 关键词与向量搜索结合，合并结果，并按用户权限过滤。
  • 重排。 用交叉编码器对较大的候选集重新排序，只保留少数几个。
  • 回答。 仅基于这些段落生成答案，每个论断附引用，否则就说明文档无法回答该问题。
  • 评估。 在带标注的数据集上分别对检索和答案打分，上线前和每次变更后都要做。
  • 预算。 各阶段的延迟和每次查询的成本，用你会去核对的数字来说明。

从文档、用户和权限入手

举一个具体的题目：一家保险公司希望其理赔员和核保员能够查询保单条款、核保指南和内部备忘录。在你画框图之前，先问这些问题，并说明每个答案会带来什么改变：

  • “有哪些文档，什么格式，多久更新一次？” 扫描版 PDF 意味着需要 OCR 和解析质量检查。带版本的条款意味着每个分块都要标注生效日期，否则你会用去年的保单来回答。
  • “谁来提问，他们拿答案做什么？” 依据答案赔付理赔款的理赔员需要引用来源和拒答机制。
  • “每个人都能看到所有文档吗？” 在保险公司里，不能：定价备忘录和核保指南只留在核保部门。这决定了权限检查放在哪里。
  • “答错的代价是什么？” 如果会赔钱或引发投诉，系统在无法引用来源时必须拒答。
  • “必须部署在哪里？” 如果文档不能离开客户的云环境，那么模型、索引和日志都要移到他们的信任边界之内。

时间紧迫时，可以直接陈述假设：“我假设用户是内部员工，文档系统带有访问列表，存在部分受限内容，且答错有代价。如果有任何假设不对，请打断我。”

数据摄取与分块

说四件事。

先解析再分块。 恢复标题、章节编号和表格。再好的分块大小也弥补不了糟糕的解析。

按文档自身的单元切分。 保险条款按其编号章节切分，每个分块都携带其标题路径，例如

Exclusions > 4.2 Flood

，这样某条除外责任就不会脱离其所属章节而孤立存在。简短的备忘录可以保持完整。

Chunking contracts compared with support tickets

通过两个语料库并结合代码进行讲解。

为每个分块保留元数据。 文档 ID、版本、生效日期、章节、来源链接，以及在摄取时从源系统复制的访问权限列表。这个列表使权限过滤成为可能。

增量更新。 以文档 ID 和内容哈希作为流水线的键，这样重跑时会跳过未更改的文件，而更改过的文件会替换其旧分块。先写入新版本的分块，再切换文档的当前版本，这样任何查询都不会看到两个版本各一半的内容。访问权限列表尚未同步的文档会被索引为对任何人都不可见，而绝不会是公开可见。

使用同一个嵌入模型对分块和查询进行嵌入。更换该模型意味着要对整个索引重新嵌入，所以要尽早说明这一成本。

常见的错误：把“我会用 512 个 token 加一些重叠来分块”当作你整个数据摄取方案的回答。那只是一个默认值，不是设计。

检索：混合搜索，然后重排序

向量搜索匹配语义，但对精确字符串的匹配很差。保险文档中充满了精确字符串：保单号、表单代码、条款引用。因此要在向量搜索之外同时运行关键词搜索（BM25），这种组合称为混合搜索，并合并两个排序结果列表。

倒数排名融合是一种简单的合并方法。它只使用排名，因此忽略了两个系统的分数，因为这两个分数不可比（Cormack, Clarke and Buettcher）：

def rrf(lists, k=60):
    s = {}
    for ranked in lists:
        for r, d in enumerate(ranked, 1):
            s[d] = s.get(d, 0) + 1/(k + r)
    return sorted(s, key=s.get,
                  reverse=True)

kw = ["w4.2", "g9", "m17"]
vec = ["m17", "w4.2", "faq3"]
print(rrf([kw, vec]))
# ['w4.2', 'm17', 'g9', 'faq3']

这里

w4.2

是保单条款的 4.2 节，

g9

是一份指引，

m17

是一份备忘录。两个列表都排名靠前的段落会升至顶部。常数

k=60

取自论文中的数值。

然后添加一个重排序器。先低成本地检索一个较宽的候选集，用一个交叉编码器把查询和段落放在一起阅读来为每一对打分，并保留最好的几条。它对整个语料库来说太慢，所以只处理候选集。

在被问到之前主动说明其局限：重排序器只能对检索找到的内容重新排序。如果正确的段落根本没进入候选集，解决办法是提高召回率。问题检索找到了正确的文档，但排名太低是需要演练的后续问题，附有评测代码。

要用的原话：“用混合检索保证召回，用重排序器保证顶部结果的精确度，我会分别对两者进行测量。”

在检索时按权限过滤，而不是在提示词里过滤

在我们的方法中，这一部分必须做到完全正确。错误的设计会从所有内容中检索，然后告诉模型“不要向理赔人员展示核保内容”。此时模型已经读到了受限文本，一个措辞巧妙的问题，或植入在另一份检索文档中的指令，都可能把这些内容套出来。

正确的设计是在搜索内部、排序之前进行过滤：

  • 从经过验证的登录令牌中获取用户身份及其所属组，绝不要从请求体中获取。
  • 将它们作为过滤器传入搜索，使其只返回访问列表包含该用户或其所属组之一、且没有针对他们的拒绝条目的文本块：allowed & ({user.id} | user.groups) 非空。镜像源系统自身的规则，包括针对单个用户的共享和拒绝设置。
  • 只对通过过滤的内容进行排序和重排序。模型永远不会看到用户无权打开的文本。
  • 当引用被打开时，用用户自己在源系统中的会话再次校验。

排序后过滤有两个缺陷：排名靠前的结果可能全部受限，导致无结果可返回；而且这个空档会暴露受限文档的存在。

然后说明延迟：访问列表按计划同步，因此被撤销的访问会一直保留到下一次同步，你需要与客户的安全团队就这一延迟达成一致。如果你缓存答案，要把权限集放入缓存键中，否则一个人的答案会到达另一个人手里。

各厂商针对自己的 AI 功能也阐述了同样的原则：Rippling 在 2026 年 3 月的公告中表示，Rippling AI 会继承用户现有的角色和访问权限，因此经理只能看到自己团队的内容，而 HR 管理员能看到更多。来源 7Rippling AI: Built to Do the Work, Not Just Talk About It发布方Rippling来源类型公司博客

永远不要说的话

“系统提示词告诉模型用户可以看到哪些文档。”指令可以被诱导放弃其职责，而检索查询中的过滤器则不能。

带有用户可自行核验的引用的答案

客户真正的问题是“我能信任它吗？”，而引用让用户可以自行核验。Microsoft 的 Frontier Company 页面上的一条客户评价，将 LSEG 的 Workspace AI Search 的联合工程开发归功于 Microsoft FDE，该产品结合了 RAG 和前沿大语言模型，“以提供有据可依、带引用的答案”。来源 8Microsoft Frontier Company发布方Microsoft来源类型公司网站

让引用成为你的代码可以校验的数据，而不是模型写出的散文：

  • 将每段检索到的文本以一个由你的代码掌控的短 ID 放入提示词，并把映射关系保留在代码中。
  • 要求结构化输出：每条陈述、支持它的文本块 ID，以及一段简短引用。
  • 在显示前检查每一条回复。本次请求已检索到该 ID，引文出现在该段落中，且该段落支持该陈述——这需要一个蕴含模型或一个经过人工标注校准的 LLM 评判器。
  • 标题和链接一律从你的源数据存储中渲染，绝不要从模型的文本中渲染。
  • 当没有检索到相关内容时，如实说明，并展示最接近的段落。

主动提出这个棘手案例：段落说保单涵盖水管爆裂造成的水渍，而答案说它涵盖洪水。ID 和引文检查都能通过；只有支持性检查能发现这个问题。让助手引用来源并核实其真实性中有一个可以详细讲解的校验器。

评测、成本与延迟预算

“你怎么知道它有效？”这个问题一定会被问到，所以要在设计中就给出答案。分别对检索和答案打分：好段落配坏答案，与错误段落上的好推理，是两种不同的 bug。

  • 数据集。 一套与理赔处理人员和核保人员共同编写的真实问题黄金集，每个问题都标注了能回答它的章节，而不是 chunk ID，这样即使分块方式改变它依然有效。加入文档无法回答的问题，以及无权访问答案的用户提出的问题。
  • 检索。 正确的章节是否出现在前几条结果中？在每次改动前后报告 top-k 命中率。
  • 答案。 答案是否正确，每条陈述是否都有其引用的段落支持，以及它是否拒绝了无法回答的问题？
  • 权限。 是否有任何受限段落到达了无权访问的用户？把这项作为每次改动的测试来运行，而不是作为指标：任何一次泄露都阻止发布。
  • 上线之后。 记录问题、检索到的 ID 和引文，让用户标记错误答案，并每周审查一个样本。

如何回答“你怎么知道它有效？”对这一半有更深入的讲解。向理赔总监解释仍然存在的错误本身就是一门技能，在向非技术领导者解释 AI 的局限中有介绍。

延迟。 为每个阶段设定延迟预算。这些是你提出然后再去测量的数字，而不是事实，两行“已显示”是累计值：

阶段p95 预算
嵌入查询50 ms
过滤式混合搜索150 ms
重排候选结果250 ms
已显示段落450 ms
模型生成完整答案3 s
引文检查500 ms
已显示经检查的答案4 s

在聊天助手中，重排器花这点时间是值得的；但在边输入边搜索的场景中则不然。在显示前检查引文意味着答案会一次性完整出现而不是流式输出，因此在答案及其检查运行期间，可以先在大约半秒时展示检索到的段落。如果客户想要流式输出，就流式输出，并在每条陈述通过检查后将其标记为已核实。

成本。 写出公式，而不是猜测。每次查询的成本是以下各项之和：

  • 查询本身；
  • 对候选结果的重排；
  • 输入 token 数乘以输入价格；
  • 输出 token 数乘以输出价格；
  • 引用检查：对每条陈述用一个蕴含模型，或者用一次评审调用，把陈述及其对应段落一起送入。

输入 token 包括指令、段落和问题，所以最大的杠杆是发送多少段落。其他手段：在服务商支持的地方缓存提示词的固定部分，把简单问题发给更小的模型，并按密钥中设置的权限缓存重复的答案。用一个小型蕴含模型可以让检查保持低成本；把 LLM 评审留给小模型不确定的陈述。

你会发布的第一个版本，以及可以预期的后续问题

最后以界定范围收尾。对这家保险公司：仅限理赔处理指南，理赔与核保的访问权限分离，带重排序器的混合检索，无法引用来源时拒绝作答的带引用答案，以及与单个理赔团队进行的试点。

然后说明它不包含什么，以及原因：

  • 扫描存档， 直到在样本上测过解析质量为止。
  • 能执行操作的 Agent， 直到答案获得信任为止。
  • 微调， 因为新文档意味着检索需要重新索引，而微调模型需要重新训练，且微调模型无法引用其来源。如果面试官追问，面试中的微调与 RAG 对比 会单独回答这个问题。

可以预期的后续问题，以及第一句回应：

  • “一夜之间涌入数千份新文档。” “摄取是一个以文档和哈希为键的队列，嵌入有独立的并发上限，新分块在活动版本切换时上线。”
  • “有用户看到了不该看的文档。” “首先我关闭那条路径。然后按顺序对照审计日志检查访问列表同步、过滤器和缓存键。”
  • “它必须在我们自己的云内运行。” “那么索引、两个模型和日志都放在边界之内，我会逐一列出所有跨越边界的东西。”法院检索问题 就是这个版本的完整版，企业系统设计详解 讲了它的边界和回滚。
  • “为什么不用长上下文模型、不做检索？” “语料放不下，即使放得下，每次查询都要为全部内容付费。我仍然需要构建按用户划分的上下文来遵守权限，那就是多了几步的检索，而且我仍然需要展示答案来自哪个段落。”

常见问题

RAG 系统设计答案应涵盖哪些内容？

数据摄取与分块、检索（混合关键词与向量搜索加重排序器是可靠的默认方案）、权限过滤、带引用的答案生成、评测，以及成本和延迟。从客户的文档和用户出发，并说明第一版会省略哪些内容。

文档权限应该在提示词中强制执行吗？

不应该。在检索时按用户权限进行过滤，这样用户看不到的文本就永远不会到达模型。提示词中的指令可能被忽略或被其他文本覆盖；而检索查询中的过滤器则不会。

如何评测 RAG 系统？

分别对检索和答案打分。对于检索，检查在一组标注好的真实问题上，正确的段落是否出现在靠前的结果中。对于答案，检查正确性以及每个论断是否得到其引用段落的支持，并在上线后持续跟踪这两项。
