摘要

本文实测了 Comet 开源的 LLM 评测与追踪平台 Opik。全平台采用 Apache-2.0 许可证，可完全自托管，适合数据不能出网的客户。但作者发现两个关键问题：SDK 默认向 Comet 上报错误与产品分析，自托管服务器默认发送每日用量统计，需修改四个配置项；字符串相似度指标不可靠，测试中错误答案得 0.96 分而正确改写仅得 0.45 分。幻觉评测混入通用知识判断，对企业 RAG 会误判。建议先追踪、后评测，用真实失败案例建数据集，并对评测指标做人工校准。

Opik 是 Comet 推出的 Apache-2.0 许可平台，用于 LLM 追踪、评估与监控，且支持完全自托管。我们实际安装了它并阅读了源代码。其字符串指标给一个错误答案打了 0.96 分，给一个正确答案只打了 0.45 分，而且 SDK 默认会向 Comet 上报错误和使用数据。本文介绍它的适用场景以及如何进行配置。

Opik 是 Comet 的开源平台，用于对 LLM 应用和 Agent 进行追踪、评估与监控，它最有力的卖点在于许可证：整个平台（包括服务器和 UI）都采用 Apache-2.0 许可，无需商业协议即可自托管。当客户的数据不能离开其网络时，它就是一个天然的默认选择。 我们安装了 SDK，阅读了服务器和 SDK 代码，并离线运行了它的指标。有两个发现会影响我们的部署方式：SDK 默认向 Comet 发送错误报告和产品分析数据，自托管服务器也会发送每日使用量统计，因此一个严格封闭的部署需要修改四项设置。此外，在任何人信任仪表盘之前，评估指标都需要先校准：两个字符串相似度指标给一个事实错误的答案打了 0.96 分，给一个正确的答案只打了 0.45 分。Opik 是一个不错的平台，但它（以及任何其他工具）都无法替你决定“好”对你的应用意味着什么。

Opik 能做什么

Opik 覆盖了从开发到生产的完整闭环：

  • 追踪。 用 @track 装饰一个函数，或使用其集成之一（README 列出了数十种，包括 Google ADK、LangChain、CrewAI、DSPy、Anthropic、Gemini、Bedrock，以及面向其他语言的 OpenTelemetry 路径），每次调用都会变成一条带有嵌套 span 的追踪记录：模型调用、工具调用、检索步骤。
  • 评估。 数据集、在数据集上运行你的应用的实验，以及各类指标：字符串启发式指标（精确匹配、包含、正则、Levenshtein、BLEU、ROUGE、BERTScore 等）和 LLM 评审指标（幻觉、答案相关性、上下文精确率与召回率、事实性、内容审核、有用性、G-Eval、轨迹准确率、LLM 评审团）。
  • 生产监控。 用于分数、追踪数量和 token 用量的仪表盘，以及在线评估规则，可用评审指标对抽样的生产追踪进行打分。
  • 提示词管理、一个 playground、护栏、用于 CI 的 pytest 集成，以及一个 Agent Optimizer SDK，包含进化式、少样本贝叶斯、GEPA、元提示和参数优化器。
  • 一个 MCP server，让 Claude Code、Cursor、Codex 及类似 Agent 可以在聊天中读取追踪记录并运行评估。

截至2026年10月21日，该仓库在GitHub上约有22,800颗星，平台版本为2.2.114，我们安装的Python SDK版本为2.2.113。README声称该系统每天处理超过4000万条trace；这是Comet给出的数字。

自托管：免费许可，真实的运维负担

Docker Compose部署会启动MySQL、Redis、ClickHouse、ZooKeeper和MinIO，然后是Opik的Java后端、一个Python后端、前端，以及可选的guardrails后端、Jaeger和OpenTelemetry收集器。一个脚本（

./opik.sh

）即可在本地将其启动；Helm chart则覆盖Kubernetes。

对于分析类产品来说，这是一套常见的技术栈，但它意味着真实的运维承诺。ClickHouse存储trace，其增长取决于span大小，而不仅仅是trace数量。在首次部署之前，请先确定数据保留策略、备份方案，以及当数据摄入落后时由谁来响应。“可免费自托管”仅指免许可费用。账单转移到了运行ClickHouse的人身上。

对于许多客户项目来说，这仍然是正确的取舍。无法将提示词和输出发送到供应商云端的受监管客户，在流行工具中有三个现实的选择：一个可以自行运行的Apache-2.0平台（Opik）、一个MIT核心加付费企业模块的平台（Langfuse），或者一个提供企业自托管方案的闭源产品。Opik自己的对比表就是这样呈现的，我们认同其中的许可事实。表格的其余部分则是供应商的表述方式。

.env

中。

指标：我们测量了什么

Opik 提供了许多字符串相似度指标，它们对于其设计所针对的任务是有用的。我们在离线环境下，针对一行参考答案运行了其中两个指标，以观察它们在语义至关重要的客服机器人回答上的表现。

指标定义：Opik LevenshteinRatio 和 ROUGE 实现。上述分数来自本文所述的离线实验，而非上游基准测试。

告知客户无法获得退款的否定性回答，Levenshtein 比值得分为 0.96，ROUGE-L 得分为 0.94。数字错误的回答得分为 0.98 和 0.88。正确的意译回答得分为 0.45 和 0.20。一个

Contains("30")

检查捕获了错误的数字，却漏掉了否定表述。这些都不是 Opik 实现上的缺陷；这正是字符串相似度所度量的内容。

A metric that rewards looking like the reference will rank a confident wrong answer above a correct one in different words.

请将这些指标用于格式、精确标识符、提取字段以及模板化输出的回归检测，而不是用于自由文本的正确性判断。

LLM 评判指标才是检查语义的地方，其代码中有两个细节值得注意。

幻觉评判器还会对照通用知识进行评分。 在提供了上下文的情况下，评判器的指令要求输出不得添加超出上下文的信息或与上下文矛盾，同时还要求它“不应与公认的事实或通用知识相矛盾”。对于公共领域的问题，这是合理的。但对于以客户自身文档（银行的费用表、保险公司的保单条款、公司的休假规定）为事实来源的企业助手而言，客户的事实可能与评判模型所认为的标准不同，忠实的回答会被标记为幻觉。对于基于企业内部文档的 RAG，请使用仅基于上下文的忠实度提示。

G-Eval 分数取决于提供商。 当评判模型返回 token 对数概率时，Opik 会将分数计算为分数 token 上的概率加权平均值，这是 G-Eval 论文中的方法，能给出更平滑、更稳定的分数。当提供商不返回对数概率时，它会回退到模型所写的整数值。因此，同一指标在两个提供商上可能产生形状不同的分数分布。在任何比较中请保持评判模型固定不变。

还有两个需要了解的默认设置：SDK 的默认评判模型是

openai/gpt-5-nano

（由

default_llm

设置），这是一个小而便宜的模型；评判提示将输入包裹在标签中，并附带将其视为数据的指令，这是针对试图指示评判器的回答的一种合理防御措施。

我们对任何平台上的任何评判器的规则都遵循我们的 LLM-as-a-judge 概念：手工标注 100 到 200 个示例，衡量评判器与这些标注的一致性，然后才把它的分数放到仪表盘上。固定评判模型，并为每个分数存储提示词版本。没有评判器版本的评测分数，是一个六个月后没人能解释的数字。

用途

Agent 调试。 包含工具调用和检索片段的嵌套追踪，是查看 Agent 为何走了十五步而不是四步的最快方式。这是每个团队在第一周就能获得价值的地方。关于应记录什么内容，请参见 agent observability and telemetry。

CI 中的回归门禁。 数据集加实验加 pytest 集成，为你提供一个 eval regression suite：一组固定的用例，当提示词、模型或检索发生变化时，这些用例的表现不能变差。从 50 个代表真实失败的用例开始，而不是 2,000 个合成用例。

生产环境采样。 在线规则可以使用评判指标对一部分线上追踪进行评分。对百分之几的流量进行评分，针对趋势设置告警，并将低分路由到人工审核，而不是对单条追踪进行告警。

升级前对比模型。 用当前模型和候选模型运行同一数据集，并逐用例对比，而不仅仅是看总体；回归往往隐藏在平均值中。

我们不会用它来： 在没有人工 calibration 的情况下作为判断答案是否正确的唯一依据，或作为安全边界。护栏有帮助，但它们应该部署在你应用中模型的前面，并配有自己的测试。

我们会如何为客户进行部署

  • 在编写代码之前先决定追踪数据存放在哪里。 如果数据不能离开网络，就自托管，并在基础镜像中设置上述四个配置项。
  • 先追踪，后评测。 为 Agent 的每一次模型调用、工具调用和检索都加上片段埋点，并在选择指标之前花一周时间阅读追踪数据。
  • 用真实失败构建数据集。 每一份缺陷报告和每一条糟糕的追踪都成为一个用例。
  • 按领域选择指标。 对结构化字段使用精确匹配或正则检查；对自由文本的忠实度使用经过校准、仅依赖上下文的评判模型；其余部分进行人工审核。
  • 对产生分数的一切内容进行版本管理。 包括评判模型、提示词、指标版本、数据集版本。
  • 设定保留与脱敏策略。 追踪记录包含客户数据。需决定在采集时屏蔽哪些内容、跨度数据保留多久以及谁有权读取。

对于前沿部署工程师来说，这是项目初期最常见的情况之一：客户有一个原型，没有追踪记录，对质量的印象只是“大体还行”。搭建追踪系统和一套 50 个用例的回归集，就能把这些变成你可以有理有据地展示的数字。这也是面试中的常见话题。请练习讲解离线评估与在线评估、评判模型为何需要校准，以及如何为模型升级设置门禁，可参考我们的 MLOps 问题和智能体软件工厂指南，后者将模型升级视为部署来讲解。

常见问题

Opik 是 Comet 推出的开源平台，用于追踪、评估和监控 LLM 应用与 Agent。它记录应用的追踪和跨度数据，在数据集上运行基于代码或 LLM 评判指标的评估，通过在线规则为生产流量打分，管理提示词，并包含 Agent 优化器和护栏。整个平台（包括服务器）采用 Apache-2.0 许可证，可自行托管。

可以。服务器、Web 应用和评估功能均采用 Apache-2.0 许可证，可在 Docker Compose 或 Kubernetes 上运行，无需商业许可。运行它意味着需要同时运维 MySQL、Redis、ClickHouse、ZooKeeper 和 MinIO 以及 Opik 自身的服务，因此成本是工程时间而非许可费用。

这四者都能追踪多步骤 Agent 并运行 LLM 评判评估。主要区别在于许可和托管方式：Opik 的完整平台采用 Apache-2.0，Langfuse 的核心采用 MIT 并有商业企业模块，Phoenix 在 Elastic License 2.0 下为源码可用，LangSmith 则闭源且仅在 企业版计划中支持自托管。根据数据必须存放的位置和团队已有的技术栈来选择。

Python SDK 默认指向 Comet 的云服务，并且默认启用了 Sentry 错误上报和产品分析。自托管服务器默认每天向 Comet 的统计端点发送使用量计数（用户数、追踪数、实验数、数据集数）；我们在该报告中未发现追踪内容。如果你的数据合规规则要求不得有外呼请求，可在客户端设置 OPIK_URL_OVERRIDE、OPIK_SENTRY_ENABLE=false 和 OPIK_ANALYTICS_ENABLE=false，并在服务器上设置 OPIK_USAGE_REPORT_ENABLED=false。

它们是工具，不是裁决。在我们的离线测试中，Levenshtein 和 ROUGE 给一个否定的错误答案打出了 0.96 和 0.94 分，而给一个正确的改写答案只打了 0.45 和 0.20 分。LLM 评审类指标更擅长理解语义，但需要在你自己的数据上对照人工标注进行校准。字符串指标用于格式和精确匹配检查，而评审类指标只有在验证了与人工判断的一致性之后才能使用。

讨论 (4)

幻觉提示词中关于通用知识的条款在一家银行的部署中坑了我们。银行自身的产品条款与评审模型认为的“标准”不同，导致忠实的回答被误判。我们把提示词分叉为仅依据上下文进行评判，误报就消失了。

读者提问：自托管技术栈对小团队来说负担重吗？

比单个容器重，但比看起来轻。在追踪量或可用性需求迫使你迁移到 Kubernetes 之前，先用 Docker Compose；把 ClickHouse 放在有备份的磁盘上；并且从第一天起就确定数据保留策略。让人意外的是存储大型 span 的成本，而不是计算成本。

这篇文章里一个值得借鉴的习惯：像对待代码一样对评审模型进行版本管理。在指标中固定模型名称，把提示词哈希与每个评分一起存储，这样六个月后你就能区分是质量变了还是评审模型变了。
