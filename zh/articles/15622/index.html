TypeScript 中的 Agent API 调用：重试与幂等性

原标题：Agent API Calls in TypeScript: Retries, Idempotency

FDE Times · 2026-10-08 · 约 8 分钟读完

摘要

这篇文章面向前沿部署工程师，讲解如何用约 80 行 TypeScript 为 AI Agent 的 API 调用层实现超时、克制的重试与幂等键，避免超时后重试导致重复退款等事故。文章引用 Amazon 与 Stripe 的实践，给出完整可复用的 callApi 函数，并总结常见错误，如循环内生成幂等键、多层重试叠加等。

要点

  • 有副作用的 API 只有支持幂等才能安全重试。
  • 幂等键每次业务操作只生成一次，仅用于 POST 请求。
  • 超时应基于下游接口的 p99.9 延迟设定，可用 AbortSignal.timeout()。
  • 重试需加抖动和令牌桶预算，五层各自重试可使数据库负载放大 243 倍。
  • 带幂等键的请求重试 5xx 无意义，服务器会返回缓存的同一错误。

超时、有纪律的重试以及每个操作固定的幂等键，只需大约 80 行 TypeScript 代码，可直接复制到项目中使用。

简要说明

  • 一个有副作用的 API 只有在支持幂等性的情况下才能安全重试。
  • 每个业务操作只生成一次幂等键，在每次重试时复用它，并且只附加到 POST 请求上。
  • 重试需要有预算：如果每一层都自行重试，数据库的负载可能增长多达 243 倍。

想象一下你在客户现场工作的第二周。你们团队部署的客户支持 Agent 有一个名为

createRefund

的工具，它会调用客户的内部退款 API。某天下午网络不稳定。第一个请求没有得到响应，于是 Agent 再次尝试。第二天早上，财务团队发现有一笔订单被退款了两次。

这不是模型造成的。问题出在包装

fetch

的那十几行代码上——所有人都把它当作杂活。对于前沿部署工程师来说，API 调用层正是 Agent 触及客户资金、库存和生产数据的地方。你需要第一次就把它做对。

这一层需要三样东西：超时、有纪律的重试和幂等键。本指南将逐一介绍，然后把它们整合到一个完整的 TypeScript 函数中，你可以复制并根据自己的项目进行调整。

为什么朴素的重试很危险？

Amazon Builders' Library 对此直言不讳：有副作用的 API 在不支持幂等性的情况下重试是不安全的。当退款请求超时时，客户端无法判断服务器是否已处理该请求。数据包可能根本没有到达。也可能钱已经转出去了，只是响应在返回途中丢失了。

幂等键正好消除了这种不确定性。Stripe 的文档指出，如果发生连接错误，你可以重新发送请求，而不会有创建第二个对象或重复应用同一更新的风险。

其机制很简单。对于每个键，无论第一次请求成功还是失败，Stripe 都会存储其状态码和响应体，并在每次重发时返回相同的结果。

“或失败”这几个字很重要。正如 Stripe 所描述的，如果第一次尝试返回了 500，使用相同键的重试也会得到同样的 500。因此，使用旧键重试主要适用于故障发生在传输过程中的情况，例如超时或连接中断，即客户端尚未收到任何结果的时候。

超时应该设置多长？

对于 Agent 来说，默认值通常过于宽松。OpenAI 的 Node SDK 默认超时时间为 10 分钟。这适合长时间的模型调用，但订单查询 API 不应该让 Agent 等待那么久。

Amazon 提供了一种有原则的选择方法。首先确定你能接受多大比例的“虚假”超时，即如果你再多等一会儿本可以成功的请求。然后取下游服务对应的延迟百分位数，例如 p99.9。

如果退款 API 的 p99.9 是 1.2 秒，那么约 1.2 秒的超时意味着你接受切断大约 0.1% 本可以成功的请求。

在 Node 中，你不需要用

setTimeout

.

AbortSignal.timeout()

会返回一个在给定时间后自行中止的信号，当它触发时，会以一个名为

DOMException

中止。这样你的代码就能区分超时和用户主动取消，这两种情况需要不同的处理方式。

TimeoutError

的

多少次重试才够？

OpenAI 的 SDK 是一个很好的参考设计。根据其 README，它会自动重试两次，并采用较短的指数退避。默认情况下，它会重试 408、409、429、所有 500 及以上的错误，以及连接错误。它不会重试 400 或 401，因为原样重发相同的请求并不会改变结果。

只有退避是不够的，你还需要抖动（jitter）。Amazon 将抖动描述为在等待时间中加入一些随机性，使重试在时间上分散开来。没有它，一千个同时失败的 Agent 会话会在同一时刻全部重试，再次把服务压垮。

最大的危险是重试在多层之间叠加。Amazon 给出了一个五层系统的例子，每层独立重试，导致数据库负载放大 243 倍。

反推可知，243 是 3 的 5 次方，也就是每层最多尝试三次时的结果。Amazon 的解决方案是用令牌桶在本地限制重试。当令牌用尽时，该层停止重试并将错误向上传递。

完整的 TypeScript 版本

下面是一个

callApi

函数，它将这三者结合在一起。注意生成键的那一行：它位于循环之外。

import { randomUUID } from "node:crypto";

type Method = "GET" | "POST" | "DELETE";
interface CallOptions {
  method: Method;
  url: string;
  body?: unknown;
  timeoutMs: number;          // taken from the downstream API's p99.9
  maxRetries?: number;        // defaults to 2
  idempotencyKey?: string;    // pass one in if the operation already has a key
  signal?: AbortSignal;       // cancellation signal from the agent or the user
}

// Token bucket: at most 10 retries, refilling 1 token per second
class RetryBudget {
  private tokens = 10;
  constructor() {
    setInterval(() => (this.tokens = Math.min(10, this.tokens + 1)), 1000).unref();
  }
  take(): boolean {
    if (this.tokens <= 0) return false;
    this.tokens--;
    return true;
  }
}
const budget = new RetryBudget();

// Requests with a key: don't retry 5xx, the server has stored it and will return the same error
const isRetryableStatus = (s: number, hasKey: boolean) =>
  s === 408 || s === 409 || s === 429 || (!hasKey && s >= 500);

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const backoff = (attempt: number) =>
  Math.random() * Math.min(5000, 200 * 2 ** attempt); // jitter

export async function callApi(opts: CallOptions): Promise<Response> {
  const maxRetries = opts.maxRetries ?? 2;
  // Generated ONCE for the whole operation; only POST carries a key
  const key =
    opts.method === "POST" ? opts.idempotencyKey ?? randomUUID() : undefined;

  for (let attempt = 0; ; attempt++) {
    // Each call gets its own timeout, combined with the caller's cancellation signal
    const timeout = AbortSignal.timeout(opts.timeoutMs);
    const signal = opts.signal ? AbortSignal.any([opts.signal, timeout]) : timeout;
    try {
      const res = await fetch(opts.url, {
        method: opts.method,
        headers: {
          "Content-Type": "application/json",
          ...(key ? { "Idempotency-Key": key } : {}), // header name depends on the API
        },
        body: opts.body ? JSON.stringify(opts.body) : undefined,
        signal,
      });
      const canRetry =
        isRetryableStatus(res.status, key !== undefined) &&
        attempt < maxRetries &&
        budget.take();
      if (!canRetry) return res;
      await res.body?.cancel(); // discard the body to free the connection before retrying
    } catch (err) {
      // If the caller cancelled, stop immediately, no retry
      if (opts.signal?.aborted || attempt >= maxRetries || !budget.take()) throw err;
      // Otherwise it's a TimeoutError or network error: resend with the SAME key
    }
    await sleep(backoff(attempt));
    if (opts.signal?.aborted) throw opts.signal.reason;
  }
}

回到退款的例子。第一次调用超时，catch 块收到一个

TimeoutError

，函数等待一个随机间隔后使用相同的键重新发送请求。如果服务器已经处理了第一个请求，它会返回存储的结果，不会产生第二笔退款。

在改造这个函数时，有两个小细节值得保留。调用方的取消信号通过

AbortSignal.any()

与超时结合在一起，因此如果 Agent 中途被停止，函数会立即退出，而不是继续重试。另外，当为了重试而丢弃一个响应时，其响应体会被取消，以免连接滞留在连接池中。

这里的重试条件在一个方面比 OpenAI SDK 的更严格：携带键的请求不会重试 500 及以上的错误。原因在于前面描述的机制。对于像 Stripe 这样按键存储首个结果的 API，在收到 500 后用同一个键重发只会返回同样的 500。这只会消耗预算，毫无收益。

GET 和 DELETE 不携带键，所以它们仍会照常重试 5xx。如果客户的 API 对键的处理方式不同，请在放宽此条件之前先询问他们。

当 409 表示与另一个并发运行的请求发生冲突时，仍然值得重试。Stripe 明确说明，当参数未通过验证或请求与已在进行中的请求冲突时，它不会存储结果，因此在这些情况下重发是安全的。

实践中的常见错误

最常见的错误是在循环内部生成键。这样每次重试都会携带一个新键，服务器会将其视为新操作，幂等性就失效了。

AI Agent 会带来一个更隐蔽的版本。模型在稍后的步骤中再次调用同一个工具，而你的层为该调用生成了新键。如果你的编排器可以重新运行某个步骤，请从该步骤的 ID 派生键，并通过

idempotencyKey

.

第二个错误是用不同的参数复用同一个键。Stripe 会将新参数与原始请求进行比较，如果不同则返回错误。它还可能在 24 小时后删除键，因此第二天重新运行的任务不能依赖旧键。

第三个错误是给每个请求都附加键。Stripe 明确表示 GET 和 DELETE 本身已经是幂等的，因此为它们发送键没有任何作用。也不要把电子邮件地址或账号放进键里。Stripe 建议使用 UUID V4 或具有足够熵的随机字符串，最长 255 个字符，且不包含敏感数据。

最后一个错误最难发现：在 SDK 之上叠加重试。如果你的工具封装了一个已经重试两次的客户端，而 Agent 的编排器又在上面再次重试，放大倍数在你察觉之前就已经成倍增加。只选择一层来执行重试，并在其他所有地方关闭重试。
