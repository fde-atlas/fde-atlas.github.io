前沿部署工程，第 2 部分：探索——从业务问题到可构建的东西

原标题：Forward deployed engineering, Part 2: Discovery, from a business problem to something you can build

Abhinav Bhatia · 2026-10-20 · 约 16 分钟读完

摘要

作者Abhinav Bhatia以虚构公司Acme Consumer Brands为例，讲解前沿部署工程师如何在动手开发前完成发现阶段：把模糊需求转化为问题陈述、设定带基线的业务与技术指标、评估可行性、选定首个用例，最终形成赞助人签字的一页式项目简报。文章强调多数AI项目失败源于未充分界定问题，并列举了应当拒绝项目的情形。

要点

  • 发现阶段通常限时一到三周，产出五项书面共识。
  • 问题陈述须指明谁有问题、现状成本与改进目标。
  • 指标分业务、采纳与技术三层，每项需基线。
  • 首个用例应优先只读、数据源有明确责任人。
  • 无归属、无决策变化或无法度量的项目应拒绝。

大多数陷入停滞的 AI 项目，从一开始就没有被正确界定范围。本部分从零开始讲解探索：如何把一个需求转化为问题陈述，如何选择业务和技术成功指标并确定基线，如何评估可行性，如何挑选第一个用例，如何说不，以及如何撰写一页纸的项目简报。

在第一部分中，我介绍了前沿部署工程师（FDE）的工作内容以及项目的运作方式：驻场、探索、构建、加固和交接。本部分讲的是其中的第二步，探索，因为它决定了其余三步是否值得去做。

在我与合作伙伴的合作中，那些进展艰难的项目很少是因为模型本身。它们之所以艰难，是因为团队在还没有人就“要解决什么问题、为谁解决、以及如何判断是否成功”达成一致之前，就开始动手构建了。做错方向的好原型依然是错的，而且通常要过几周才会有人察觉。

我先从基础讲起：什么是探索，以及你需要掌握的几个术语。然后，我会以虚构公司 Acme Consumer Brands 为例，跟踪一个真实的请求，从一个模糊的需求出发，最终形成一份在任何代码编写之前由发起人签署的一页纸简报。

这在 FDE 的职位描述中是如何体现的？

公开的 FDE 招聘信息用略有不同的措辞直接要求探索能力：

  • Google Cloud 的 Forward Deployed Engineer, GenAI 招聘信息将“具备主持技术探索会议的经验”列为最低任职资格。
  • Google Cloud 的 AI Outcome Customer Engineer, Forward Deployed Engineering 招聘信息要求你“评估项目可行性，塑造面向长期采用的方案，并验证 FDE 项目请求”。
  • OpenAI 的 Forward Deployed Software Engineer 招聘信息要求你“与战略客户深度驻场合作，详细了解他们的业务挑战和技术需求”，并“为概念验证原型和完整的生产部署准备详细的工作范围和项目计划”。

综合来看，这些描述指向同一种能力：把一场关于业务的对话转化为工程师可以构建、发起人可以衡量的项目范围。这种能力就是探索。

什么是探索？

探索是你在构建之前所做的工作，目的是找出哪个问题值得解决，以及你是否有能力解决它。

一个更精确的版本，也是我使用的版本：发现是一个限时阶段（有固定的结束日期，通常为一到三周），它产出五项客户书面同意的成果。每一项都是你在本系列中会再次遇到的术语：

  • 问题陈述：一段话，说明谁遇到了问题、目前的情况如何、造成了什么损失，以及更好的状态是什么样的。
  • 成功指标：用来判断工作是否有效的数字。业务指标衡量企业关心的结果，例如销售损失。技术指标衡量系统本身，例如其数据的准确频率。每个指标都需要一个基线（在你做任何改动之前测得的当前值）。
  • 可行性评估：数据、访问权限、技术和组织条件是否使问题在可用时间内可解。
  • 用例：系统将为某一组用户完成的一项具体工作。发现阶段要选出第一个用例。
  • 范围：哪些内容包含在内，同样重要的是，哪些内容被明确排除在外。

这五项都写入项目简报，这是一页纸的文档，由发起人（拥有成果和预算的高层人员）在构建开始前签署。

一个有用的类比是看医生。病人来了说“我需要抗生素”。这就是诉求。医生询问症状和病史（发现），诊断病情（问题陈述），选择治疗方案（用例），并预约复诊以检查疗效（对照基线的成功指标）。好医生有时会说“你不需要抗生素”，好的 FDE 有时也会说“你不需要 AI Agent”。

发现阶段将模糊的诉求收窄为一页简报：诉求变成问题陈述，问题获得成功指标、可行性检查和第一个用例，最终形成一份在任何构建开始前由发起人签署的简报

Acme 到底想要什么？

Acme Consumer Brands 是 Production-ready agents 系列中虚构的消费品公司。它正在西欧开展一项名为 Acme Pure Refill Launch 的活动。营销数据存储在 Google Cloud 的 BigQuery 中，而供应数据存储在 Databricks 中，因此每个团队只能看到一半的情况。营销团队看到 EUR 283,590 的支出和良好的点击率。供应团队看到西欧的准时足量交付率（OTIF）（订单按时且完整送达的比例）为 87.4%，以及西欧 EUR 36,026 的零售商罚款（西欧和南欧合计为 EUR 51,331）。所有这些数字都是虚构的。

送达 FDE 的请求只有一句话：“我们想要一个打通营销和供应的 AI Agent。”在 agents 系列中，这个诉求变成了一个路由器和两个专门的 Agent。而本文讲述的是在这些代码存在之前发生的对话。

如何将一个诉求转化为问题陈述？

一个需求几乎总是指向某个解决方案（一个 AI Agent）。而问题陈述则指向某个人、某项成本和一个目标。要从前者走到后者，你需要询问的是工作本身，而不是工具。

需求指向的是解决方案；问题陈述则指明谁遇到了问题、目前的情况如何、代价是什么、更好的状态是什么样——这才是你可以用来设计和衡量的依据

以下是我认为在初次会面中最有用的问题：

  • “告诉我上一次你需要这个东西是什么时候。” 一个具体的近期事件能让你了解真实的步骤、真实的系统和真实的延误。而泛泛的描述只会给你官方流程。
  • “演示给我看。” 坐在用户旁边，看他们完成任务。在 Acme，品牌管理部的 Maria 会向分析师提出请求，分析师从 BigQuery 导出活动报告，向供应链团队索要来自 Databricks 的 OTIF 数据，然后在电子表格中将两者合并。
  • “拿到答案后，你会做出什么不同的决定？” 如果没有人能说出哪个决定会因此改变，这个问题就不值得立项。
  • “多久发生一次，每次要多久？” 计数能把抱怨变成成本。

这是第 2 步中分析师的电子表格，涵盖活动的前四周：

分析师今天手工制作的电子表格：从 BigQuery 导出的活动支出与来自 Databricks 的 OTIF 数据并排，Acme Pure Refill Launch 西欧活动每周一行，并附有七周总计

业务术语与 Agent 背后的数据 解释了每一列的含义以及两张表如何关联。

整理成文后，Acme 的问题陈述如下：

西欧的品牌经理和供应计划员无法同时查看活动支出和供应表现。如今他们需要求助分析师，等待约两天才能得到一份整合的答案，导致促销活动在库存耗尽时仍在进行。更好的状态是当天就能得到答案，用他们自己的话表述，且数字为两个团队共同信任。

两天的等待时间在这里只是示例。在实际项目中，这应该是一个你实际测量出来的数字，这就引出了指标的话题。

你需要和谁沟通？

利益相关者是任何能够帮助、使用、批准或阻碍这项工作的人。在需求探索阶段，你需要接触五类人，每一类要问的问题各不相同。

需求探索阶段要会面的五类人以及各自要问的一个问题：向发起人问决策，向用户问当前工作，向数据所有者问谁可以查看什么，向安全团队问什么绝不能外泄，向平台团队问可以部署在哪里

  • 高管发起人对结果负责。要问哪个决策会因此变得更好。
  • 用户是今天实际做这项工作的人。在 Acme，他们是品牌管理部的 Maria 和供应计划员 Sam。观察他们的工作方式。
  • 数据所有者决定谁可以读取哪些表。在 Acme，供应数据团队拥有 Databricks 中的表，包括零售商罚款数据，只有供应团队可以计算。
  • 安全与风险团队决定什么绝不能外泄，以及什么必须被记录。
  • 平台和 IT 决定系统可以在哪里运行、使用哪个身份提供商以及如何访问数据。第 3 部分讲的就是这个群体。

我看到最常被遗漏的群体是数据所有者，他们很少参加启动会议，但在第二周却掌握着你需要的访问权限。

你如何知道它成功了？

成功指标是一个数字，如果工作有效，它就会变动。你需要在多个层级上设置指标，因为每个层级回答的是不同人的问题。

Google Cloud 的指南 KPIs for gen AI 将指标分为模型质量、系统质量、采用度和业务价值。它还警告说，团队常常把运营效率的提升与最终目标混为一谈。Google 的 Rules of Machine Learning 把这一点提得更早，作为规则 #2：“首先，设计并实现指标。”

我把指标画成一棵树，让每个技术数字都关联到一个业务数字：

Acme 的指标树：正确数字和延迟等技术指标，支撑每周用户数和决策时间等采用与行为指标，进而支撑减少销售流失这一业务成果；每个问题的成本则进入商业论证

  • 业务成果（一个滞后指标，变动缓慢且滞后）：促销活动期间因缺货导致的销售流失减少。这个指标由业务方衡量，而不是 FDE。
  • 采用与行为（领先指标，变动较早并预示结果）：每周活跃用户数、无需分析师即可解答的问题数，以及从提问到决策的时间。
  • 技术指标，由构建方控制：在一组黄金问题上的正确数字、路由到正确的专家、p95 延迟（95% 的回答都能超过的响应时间）以及每个问题的成本。Agent 系列中的 Proving it works, evals that gate releases 展示了如何自动测量前两项。

每个指标都需要一个基线，即在构建之前测量。在 Acme，分析师团队的请求队列已经记录了每个请求的到达时间和解答时间，因此两天这个数字可以来自真实的时间戳。没有基线，你可以证明 Agent 很快，但无法证明任何东西得到了改善。

它可行吗？

可行性意味着检查问题能否用实际存在的数据、访问权限、技术和人员，在你拥有的时间内解决。我会做四项检查。

在你承诺之前进行四项可行性检查：数据是否存在且质量足够好，Agent 能否获得访问权限，模型能否完成语言部分而由代码完成其余工作，以及组织是否会采用并拥有它

  • 数据。 要求查看每个数据源的二十条真实记录。检查是否存在缺口、延迟加载以及有两个相互竞争定义的指标。在 Acme，两张表都存在，且供应部门已公布了 OTIF 公式。
  • 访问权限。 弄清楚谁负责审批访问权限，以及新授权需要多长时间。在 Acme，供应 Agent 必须以登录用户的身份读取 Databricks，这需要一个 Acme 身份团队必须批准的 OAuth 应用。这是唯一一项黄色预警检查项，会写入简报的风险部分。Agent 系列中的 Agent 的身份认证解释了原因。
  • 技术。 询问是否真的需要模型，以及用于哪个部分。Google《机器学习规则》的第一条就是“不要害怕在没有机器学习的情况下发布产品。”《People + AI 指南》也提出了类似观点：找到用户需求与 AI 优势的重叠之处。在本系列中，规则是模型负责读写语言，代码负责做决策。在 Acme，需要模型来理解问题并撰写答案，但哪个团队可以查看罚款数据则是一条代码中的规则。
  • 组织。 确认在你离开后会有人接管这个系统，用户有时间进行测试，并且发起人会在某个日期做出决策。

如何选择第一个用例？

大多数需求调研会产出的想法往往超出一次合作所能交付的范围。将每个候选用例放在两个维度上评估：业务价值和可行性。第一个用例应该在两个维度上都表现突出。

选择第一个用例：Acme 的五个候选用例按业务价值和可行性排列；缺货的活动成本在两个维度上都很高，因此排在首位，而自动重新规划和新的预测模型虽有价值但目前尚不可行

对 Acme 来说，候选用例包括：

  • A. 缺货的活动成本。 它回答了发起人的问题，是只读的，需要两个都有明确负责人的数据源，并且可以用黄金问题进行测试。这个排在首位。
  • B. 自动供应重新规划。 它很有价值，但会修改数据，并且需要人工审批环节。它会在稍后回归，届时会加入 Agent 系列中无法通过对话绕过的护栏所述的审批环节。
  • C. 品牌指南问答。 它很容易实现，但没有人迫切需要它，也没有人能说出它会改善哪个指标。
  • D. 新的需求预测模型。 它很有价值，但这是一个以月为单位衡量的数据科学项目，且尚未确定负责人。
  • E. 总结每周销售邮件。 它很容易实现，每周能节省几分钟时间。

我选择第一个用例的经验法则是：先做只读，再做读写；每个数据源有一个明确的负责人；有一个本月就能建立基线的指标；以及一个发起人能看到的结果。

你应该询问哪些数据和访问权限问题？

在我参与过的每一次合作中都会遇到这些问题。在第一周，我会针对第一个用例中的每个数据源提出这些问题：

For each data source in the first use case:
  1. Where does it live? (system, project, region)
  2. Who owns it, and who approves access?
  3. Is there one agreed definition for each figure we will quote?
  4. How fresh is it, and who notices when a load is late?
  5. Does it contain personal or confidential data?
  6. Will the agent read it as itself, or as the signed-in user?
  7. How long does a new access grant usually take here?
  8. Can we see twenty real rows this week?

问题 1、5 和 6 既是设计问题，也是调研问题，第 3 部分会进一步讨论它们。

什么时候应该说不？

拒绝也是工作的一部分。前沿部署工程师的价值在于，他们能够及早、友善地告诉发起人某个方案行不通。以下是我会说“不”或“还不是时候”的情况：

  • 交接后没有负责人。 无人负责的系统几个月内就会停止运转。
  • 数据不存在，或者没人有权读取。 那是一个数据项目，应该按数据项目来界定范围。
  • 没有人能说出会改变哪个决策。 那这个 AI Agent 只是一个演示，而不是工具。
  • 成功指标无法衡量。 你最终将无法证明任何成果。
  • 让模型去做基于规则的决策。 权限、审批和计算应该放在代码里。模型仍然可以解释结果。

表达方式很重要。我采用“不行，但我会这样做”的方式：更小的范围、非 AI 的解决方案，或者必须先完成的数据任务。在 Acme，发起人最初要求一个能在“出现缺货时自动重新规划供应”的 Agent。第一阶段并不做这件事：先以只读方式启动，证明数据准确，然后在有人工审批环节的前提下加入重新规划功能。

一页纸的项目简报里应该写什么？

项目简报把探索阶段达成的所有共识记录在一页纸上。篇幅短是有意为之：如果一页纸装不下，说明范围太大了。这是 Acme 的简报，包含示例目标：

Acme 的一页纸项目简报，包含示例目标：用用户的话描述问题、一个首批用例、范围之外的内容、三个层次的成功标准、一个基线，以及一个有明确日期的继续或终止决策

有几个字段值得说明：

  • 范围之外是文档中最有用的一行。当有人在第五周提出预测需求时，你只需指向它。
  • 成功包含业务、采纳和技术三行，与指标树相对应。这里的目标只是示例；在真实的简报中，它们来自基线和发起人。
  • 决策有明确日期。在第二周结束时，发起人根据原型和初步技术测量结果决定继续推进还是停止。
  • 交接后负责人指定一个团队，这样即使发生组织重组也能延续。

def feasibility(data, access, effort):
    """The weakest check sets the pace, so use the minimum, not the average."""
    return min(data, access, effort)


def blockers(owner, measurable):
    reasons = []
    if not owner:
        reasons.append("no owner after handover")
    if not measurable:
        reasons.append("no measurable success metric")
    return reasons


rows = []
for name, value, data, access, effort, owner, measurable in CANDIDATES:
    stop = blockers(owner, measurable)
    score = 0 if stop else value * feasibility(data, access, effort)
    rows.append((score, name, stop))

for score, name, stop in sorted(rows, key=lambda r: r[0], reverse=True):
    note = "blocked: " + ", ".join(stop) if stop else ""
    print(f"{score:>3}  {name:<30} {note}")

运行

python3 score_use_cases.py

。我运行时，输出如下：

 15  Campaign cost of stockouts
  5  Automatic supply replanning
  5  Summarise weekly sales email
  0  Chat over brand guidelines     blocked: no measurable success metric
  0  New demand forecast model      blocked: no owner after handover

这些分数是我对虚构的 Acme 的判断。然后尝试以下改动：

  • 给你自己组织中的三个想法打分。如果每个想法的数据项都得 5 分，说明你还没有真正查看过数据。
  • 把可行性中的最小值改为平均值。自动重新规划会跃升到列表前列，尽管其中一项检查只有 1 分。这就是我使用最弱检查项的原因：一个被阻塞的审批会让整个项目停摆。
  • 然后为得分最高的想法写一份一页纸简报，使用上图中的字段。

可能出什么问题

  • 没有截止日期的探索阶段。 没有时间限制，探索就会变成一连串的研讨会。从第一天起就定下决策日期。
  • 只访谈发起人。 发起人描述的是流程“应该”如何运作，而用户才能告诉你它“实际”如何运作。
  • 没有基线的指标。 你能证明 Agent 很快，却无法证明任何东西有所改善。
  • 挑选最令人印象深刻的用例。 它通常审批最多、数据处理最重、风险最大。应该挑选你能完成并衡量的那一个。
  • 没人签署的简报。 如果发起人没有以书面形式同意范围，范围就会不断膨胀。
  • 忽视琥珀色检查项。 访问权限审批耗时最长。在第一周就启动，甚至在决定是否推进之前就开始。

我现在会怎么做

  • 把你最近三个需求改写成问题陈述：谁、现状、成本、更好的样子。
  • 从现有数据中找出一个本周就能衡量的基线。
  • 为五类干系人群体逐一写上真实姓名。任何空白都是风险。
  • 用八个数据与访问问题逐一检验一个数据源。
  • 填写一页纸简报，并在编写任何代码之前让发起人阅读。

我们学到了什么？

  • 探索是一个有时间限制的阶段，其产出是问题陈述、成功指标、可行性检查、首个用例和范围，全部以书面形式达成一致。
  • “需求”指向的是解决方案，而问题陈述则指明谁有问题、现状如何、代价是什么以及更好的样子是什么。
  • 成功指标最好组织成一棵树：技术指标支撑采用指标，采用指标支撑业务成果，且每一项都需要在构建之前测得基线。
  • 四项可行性检查——数据、访问、技术和组织——必须在任何承诺之前完成，而最薄弱的一项决定了整体节奏。
  • 首个用例应在价值和可行性两方面都很高，而说“不，我建议改为这样做”也是工作的一部分。
  • 由发起人签署的一页纸合作简报，记录了探索阶段在编写任何代码之前所达成的一切共识。

接下来是什么？

简报已签署，首个用例已选定。现在系统必须融入一个 FDE 并不拥有的环境：Acme 的身份提供商、网络、数据位置和安全审查。第 3 部分，在别人的环境中做设计，将介绍前期技术设计以及第一周应该提出的问题。
