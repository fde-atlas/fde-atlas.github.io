什么是前沿部署工程师？

原标题：What is a forward deployed engineer?

FDE Interview Prep · 2026-09-25 · 约 45 分钟读完

原文过长，译文只包含前一部分。

摘要

这篇指南面向求职者，解释前沿部署工程师（FDE）是什么：一名软件工程师，围绕单个客户的问题驻场工作，交付生产级软件而非咨询建议。文章引用 Palantir、OpenAI、Anthropic、Google Cloud 等公司的职位描述与博客，梳理岗位职责、差旅强度和招聘标准，并区分两类 FDE 岗位：AI 公司的 Agent 与评测开发，以及企业软件公司的平台部署与数据集成。文中还追溯了该职位起源于 Palantir 的 Delta 与 Echo 内部称谓，并记录 2025 至 2026 年间 OpenAI、AWS、Microsoft 等公司投入数十亿美元组建 FDE 组织的扩张。

要点

  • FDE 的职责范围由客户成果决定，而非某个产品组件。
  • Palantir 内部称 FDE 为 Delta，与 Dev 的区别是“一个客户、多种能力”。
  • 两类岗位：AI 公司做 Agent 与评测，企业软件公司做平台部署与数据集成。
  • 差旅要求差异大，从每 4-8 周一次到 70-90% 时间驻场。
  • OpenAI、AWS、Microsoft 等在 2026 年投入数十亿美元扩建 FDE 组织。

用雇主的话来说的定义

每家雇主对这份工作的措辞都略有不同，当你针对某一家公司定制回答时，确切的表述非常重要。以下是雇主在其招聘启事和博客中发布的定义：

  • Palantir 表示，Delta 负责将其软件平台部署到客户处，隶属于业务发展部门，并有为客户实现技术成果的使命。来源 2Dev versus Delta: Demystifying engineering roles at Palantir发布方Palantir 博客来源类型公司博客 在 Palantir 2020 年博客的一篇问答中，一位名叫 Brian 的 FDSE 将该角色描述为一种软件工程师，直接嵌入客户现场，配置 Palantir 的现有平台以解决他们最棘手的问题。来源 3A Day in the Life of a Palantir Forward Deployed Software Engineer发布方Palantir 博客来源类型公司博客
  • OpenAI 位于旧金山的 FDE 招聘启事称，该团队与客户合作，将研究突破转化为生产系统，并且 FDE 负责需求发现、技术范围界定、系统设计、构建和生产上线。来源 11Forward Deployed Engineer (FDE) - SF发布方OpenAI Careers来源类型公司招聘启事
  • Anthropic 的 FDE 招聘启事将该角色置于其应用 AI 团队中，嵌入其最具战略意义的客户处，使用 Claude 构建生产应用，包括服务器、子 Agent 和技能。来源 4Forward Deployed Engineer (New York City, NY; San Francisco, CA; Seattle, WA)发布方Anthropic（Greenhouse 招聘平台）来源类型公司招聘启事
  • Google Cloud 的 GenAI FDE 招聘启事将该角色描述为一名嵌入式构建者，在客户环境中编写代码、调试并共同交付 AI Agent 解决方案，而不是传统的顾问角色。来源 12Forward Deployed Engineer IV, GenAI, Google Cloud — Google Careers发布方Google来源类型公司招聘启事

并排阅读这些定义，它们的形态是一致的：一名工程师，专注于某一个客户的问题，构建能够进入生产环境的软件。没有一个是止步于建议：每一个都以工程师构建或部署的软件为终点。

用一段你可以脱口而出的回答来解释 FDE 的含义

招聘人员可能会以“你认为这个角色是什么？”开场。一个含糊的回答会表明你还没有弄清楚这份工作到底是构建还是提建议。以下是一个基于上述定义构建的版本。把中间那句话换成你面前这份招聘启事中的一句话：

“FDE 是一种软件工程师，其工作范围是某一个客户的问题，而不是产品的某一个部分。你们的职位描述说 FDE 负责从需求发现到生产上线的全部工作，所以我的理解是：我来界定范围，我在客户的环境中构建，而且当上线出问题时，客户打电话找的人就是我。评判标准是客户的业务是否真的发生了改变，而我在一线学到的东西会反馈给产品团队。”

这份工作不是什么

  • 不是顾问。 Palantir 称，人们普遍误以为 Delta 是顾问；一位 Delta 在其博客中引用时表示，顾问通常只产出一次性的分析，而 Delta 则与客户一起构建长期解决方案。来源 2Dev 与 Delta：揭秘 Palantir 的工程角色发布方Palantir Blog来源类型公司博客
  • 不是咨询型架构师。 The Pragmatic Engineer 在 2025 年 8 月报道，参考 OpenAI 的 Colin Jarvis 提供的信息，OpenAI 的 FDE 使用客户的工具直接在客户基础设施上编写代码，而其解决方案架构师则更偏咨询性质。来源 13什么是前沿部署工程师，为什么他们如此抢手？（Gergely Orosz）发布方The Pragmatic Engineer来源类型新闻报道
  • 不是单一固定的工作。 在 2026 年 AI Engineer World’s Fair 上，Sierra 的 Agent 工程负责人 Natalie Meurer 表示，每一位前沿部署工程师都要对客户负责，无论工作是 DevOps、赋能、定制解决方案还是数据集成。来源 14前沿部署工程的肮脏秘密（Natalie Meurer，Sierra Agent 工程负责人；AI Engineer World's Fair 2026）发布方AI Engineer来源类型演讲录像或访谈

这个角色的由来

一周的工作是什么样的

没有雇主公布过经过测量的典型 FDE 一周。现有的是个人叙述，而它们在一点上是一致的：工作内容随项目阶段而变化。

一个示例性的一周，AI 版本

这是我们虚构的合成案例，用来展示工作节奏，并非真实测量的一周。想象一位 FDE 被派驻到一家地区性保险公司，该公司想要一个助手来对 incoming 理赔件进行分流：

  • 周一，现场办公。 理赔负责人说所有理赔件都通过电子邮件到达。你和理赔员坐在一起，了解到紧急理赔件其实是通过一个没人提过的经纪人门户进来的。
  • 周二。 你申请该门户数据库的只读权限。IT 部门说需要安全审查。你当天下午写了一份一页纸的申请，明确列出需要哪些表以及原因。
  • 周三。 在等待期间，你把电子邮件这条路径端到端地交付给几位理赔员使用：数据接入、一个分流模型，以及一个写着“队列错误”的按钮。虽然简陋，但它跑在他们的真实数据上。
  • 周四。 “队列错误”的点击显示，分流器把水管爆裂的理赔件送进了洪水队列，把雨水管道堵塞的理赔件送进了水渍险队列，因为两者都包含“水”这个词。你把这些理赔件加入评测集，修改提示词，并重放上周的真实理赔件，确认错误分流减少且没有破坏其他功能。
  • 周五，远程办公。 你为客户的项目负责人撰写每周进展报告，并单独给产品团队写了一份说明：平台没有对接这个经纪人门户的连接器，而下一家保险公司也会需要。

探索、构建、评测、干系人沟通和产品反馈都在一周内完成，而不是按顺序进行。问题你的第一个月会是什么样子？会让你把这个循环大声规划出来：它的框架是免费的，参考答案在 Pro 版中。在 Pro 版中，关于行走骨架的课程会把简陋的第一版变成一套方法论。

同样的一周，企业版

另一个合成案例，针对另一类 FDE 岗位。想象一位 FDE 被派驻到一家制造商，其维护计划员希望每个工厂都能在一块屏幕上看到逾期的工单：

  • 周一，现场办公。 计划员说 ERP 里什么都有。你请他们每个人演示今天是如何查找逾期工单的，结果发现 Derby 工厂的计划员自己维护着一个电子表格。
  • 周二。 你把工单和资产登记表拉进平台并进行关联，结果 Derby 工厂的工单在关联结果中全部消失了。

下面是能发现这个问题的检查方法。在信任一次关联之前，按数据源统计未匹配的数量：

-- How many work orders per plant found no asset?
SELECT w.plant,
       COUNT(*) AS work_orders,
       SUM(CASE WHEN a.asset_id IS NULL THEN 1 ELSE 0 END) AS unmatched
FROM work_orders w
LEFT JOIN assets a ON CAST(a.asset_id AS TEXT) = w.asset_ref
GROUP BY w.plant;
plant  work_orders  unmatched
Derby  3            3
Leeds  2            0

Derby 的每一行都未匹配，而 Leeds 的每一行都匹配，所以问题在于 Derby 写入键的方式，而不是资产缺失。Leeds 把资产引用写成 42；Derby 写成

P02-00042

。去掉前缀后比较数字：

-- SQLite. In Postgres 14 or later: CAST(split_part(w.asset_ref, '-', -1) AS INTEGER)
LEFT JOIN assets a
  ON a.asset_id = CAST(SUBSTR(w.asset_ref, INSTR(w.asset_ref, '-') + 1) AS INTEGER)

重新运行计数，Derby 的未匹配数降为零。

  • 周三。 你问 Derby 的规划师为什么引用看起来不一样，得知前缀是 Derby 的工厂代码，因为 Derby 的系统是独立搭建的才加上的，而前缀后面的数字与 Leeds 使用的全公司统一资产编号相同。你把它记作流水线强制执行的一条规则，而不是一次性的临时修复。
  • 周四。 屏幕交付给 Leeds 和 Derby 的规划师，你观察他们按哪些列排序。
  • 周五，远程。 给你的产品团队留一条备注：连接器应该规范化带工厂前缀的键，因为下一家制造商也会有同样的情况。

这就是上表中企业那一行，也就是包含 Palantir、Databricks 和 MongoDB 的那一行：一个客户的数据，集成在雇主平台上，上面再叠加一个应用。当面试官问你怎么知道一条流水线是对的，你可以这样说：“在向任何人展示数字之前，我会先统计未能连接的部分，并按数据源拆分，因为一次静默的连接失败看起来和安静的一周一模一样。”要练习这方面的技能，可以修复一个扇出导致收入虚增的连接，并设计一个统一零售商数据源的平台。两者均免费，附有参考答案。

第一点是能够用代码展示的。以下是将保险公司那一周的周四作为回放检查：上周的理赔，每条都带有理赔员确认的标签和路由器选择的标签，以及哪些标签被混淆成哪些标签的计数。

from collections import Counter

# Last week's claims: (text, label the adjuster confirmed, label the router chose)
replay = [
    ("Burst pipe under the kitchen sink", "escape_of_water", "flood"),
    ("River came over the bank into the ground floor", "flood", "flood"),
    ("Storm drain backed up into the garage", "flood", "escape_of_water"),
    ("Washing machine hose split overnight", "escape_of_water", "escape_of_water"),
    ("Hail cracked roof tiles", "storm", "storm"),
    ("Radiator valve leaking through the ceiling", "escape_of_water", "flood"),
]

right = sum(want == got for _, want, got in replay)
print(f"routed correctly: {right}/{len(replay)}")
confusions = Counter((want, got) for _, want, got in replay if want != got)
for (want, got), n in confusions.most_common():
    print(f"  {want} sent to {got}: {n}")
routed correctly: 3/6
  escape_of_water sent to flood: 2
  flood sent to escape_of_water: 1

混淆计数能告诉你路由器错在哪个方向，而仅凭准确率数字会掩盖这一点。保留回放集，在每次提示词或模型变更后重新运行它，并把每次新的“错误队列”点击加入其中。可以对客户赞助人、或对面试官说的话：“在我上线提示词变更之前，我会用上周的真实理赔数据重新运行一遍，这样我就能向你证明这个修复没有破坏洪水险的路由。”

对于 AI FDE 职位，你应该准备好展示什么

  • 你构建的、有真实用户使用过的 AI Agent 或检索系统，以及最先出问题的地方
  • 你如何衡量质量：一个评测集、一个基准，或一个经过人工校验的 LLM 评判器
  • 你向非技术人员解释模型局限的一次经历
  • 你如何处理生产环境中的延迟、成本或风险
