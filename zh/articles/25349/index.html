Batch API 批处理怎么用：大模型成本减半

FDE Times · 2026-10-26 · 约 5 分钟读完

摘要

这篇指南讲解如何用 Anthropic、OpenAI 和 Google Gemini 的 Batch API 处理大规模离线任务：三家厂商批处理均打五折，但需接受最长 24 小时的等待。作者以 30 万份合同打标签为例，说明批次拆分要兼顾请求数与大小上限、custom_id 应使用客户主键、结果须在 29 天内存入客户自有存储，并提醒不要把 24 小时当成对客户的 SLA，应预留重跑窗口。

要点

  • 三家厂商批处理均五折，代价是最长 24 小时等待。
  • 24 小时是上限而非承诺，截止时间应预留重跑窗口。
  • 拆批需同时考虑请求数和 256 MB 大小上限。
  • custom_id 应用客户主键，结果须在 29 天内存入客户存储。
  • 提示词缓存加批处理可将 token 成本降低近 95%。

三家大模型厂商的批处理都打五折，难点在于拆好批次，并在 29 天内存好结果。

要点速览

  • Anthropic、OpenAI 和 Google Gemini 的批处理都打五折。在 Anthropic 和 OpenAI，代价是接受最长 24 小时的等待，不过 Anthropic 的大多数批次不到一小时就能完成。
  • 24 小时是上限，不是承诺：到时仍未完成的批次会过期。因此客户的截止时间必须留出第二轮运行的余量。
  • Anthropic 的批处理结果只能在 29 天内下载，数据管道必须第一时间把结果存进客户自己的存储。

周一，客户发来一个存储桶链接，里面有 30 万份旧合同。他们希望在周五董事会之前，每份合同都按条款类型和风险打好标签。上周的演示很顺利，因为每次调用只给模型发一份文档。

照这个方式调用 30 万次，会撞上速率限制，会和客户用户每天依赖的聊天功能抢配额，花费也是必要成本的两倍。厂商推出 Batch API，正是为了这类工作。一名合格的前线部署工程师（FDE）需要知道什么时候该用它，同样重要的是，什么时候不该用。

用时间换一半的价格

Anthropic 的 Message Batches API 专为异步批量处理设计。批次中的每个 token，无论输入还是输出，都按标准 API 价格的 50% 计费。根据该公司的文档，大多数批次不到一小时就能完成。

这个折扣并非 Anthropic 独有。Simon Willison 指出，OpenAI 和 Google Gemini 的批处理同样打五折。OpenAI 的 Batch API 在 24 小时内完成，而且 24 小时是它唯一接受的完成窗口。换取半价的代价，是放弃立即拿到结果的权利。

所以决定性的问题不是技术问题，而是产品问题：有没有人在等结果？Anthropic 列出的适合批处理的工作包括运行评测、内容审核、数据分析和批量内容生成。它们的共同点是，没有用户盯着聊天框。

用批处理

  • 给积压的文档打标签
  • 每次改提示词后重跑评测集
  • 审核用户已发布的内容
  • 汇总报告，第二天早上前完成即可

必须实时运行

  • 回答用户的聊天机器人和助手
  • 需要在实时工作流中做决策的 Agent
  • 必须即时拦截的交易检查
  • 任何有人点了按钮在等的界面

Quora 的一位产品经理曾这样总结使用体验：把一批任务发出去，24 小时内下载结果，非常方便。但“方便”成立的前提是，客户的流程本来就以天而不是以秒为单位运转。

24 小时是上限，别把它变成对客户的承诺

很多工程师在这里出错。2024 年 10 月 8 日发布时，Anthropic 称每个批次会在 24 小时内处理完。现在的文档说得更明确：24 小时内未处理完的批次会过期，需求高峰时过期的批次可能更多。

如果向客户承诺“24 小时内出结果”，就是在承诺厂商并没有向你承诺的事。应遵循的规则是：客户的截止时间至少要容纳两个窗口，一个用于主运行，一个用于重跑过期或失败的部分。

周一数据就绪、周五截止，时间很宽裕。如果数据到周四晚上才到，紧急的部分就要实时运行。

实例：拆分 30 万份合同

Anthropic 的上限是每批 100,000 个请求或 256 MB，先到者为准。粗看之下，30 万份文档只需 3 个批次。但合同往往很长，大小上限会先于请求数上限卡住你。

假设每个请求（合同正文加提示词）平均 3 KB，那么 100,000 个请求约为 300 MB，超过了 256 MB 的上限。256 MB 除以 3 KB，约为 85,000 个请求。

为异常长的合同留出安全余量，每批设为 80,000 个请求，最终是 4 个批次。如果客户用的是 OpenAI，上限是 50,000 个请求和 200 MB 的输入文件，数字必须从头重新算。

第二个需要设计的是

custom_id

。它是把结果对应回正确文档的唯一线索，所以要用客户系统中的主键，而不是循环计数器。下面的代码用 Anthropic 的 Python SDK 勾勒了整个流程：

import anthropic

client = anthropic.Anthropic()

# 所有合同共用的系统提示词，因此缓存 1 小时
SYSTEM = [{
    "type": "text",
    "text": LABELING_GUIDE,  # 较长的共享标签分类体系
    "cache_control": {"type": "ephemeral", "ttl": "1h"},
}]

def to_request(doc):
    return {
        "custom_id": doc.contract_id,  # 客户系统的主键
        "params": {
            "model": MODEL,
            "max_tokens": 1024,
            "system": SYSTEM,
            "messages": [{"role": "user", "content": doc.text}],
        },
    }

batch = client.messages.batches.create(
    requests=[to_request(d) for d in chunk]  # 每块最多 80,000 份文档
)

# 当 processing_status == "ended" 时：
for entry in client.messages.batches.results(batch.id):
    if entry.result.type == "succeeded":
        save_to_customer_store(entry.custom_id, entry.result.message)
    else:  # "errored" 或 "expired"
        queue_for_retry(entry.custom_id, entry.result.type)
cache_control

这一行不是摆设。一个批次的运行时间可能超过 5 分钟，因此 Anthropic 建议使用 1 小时的缓存时长，让共享上下文（例如很长的标签指南）获得更多缓存命中。

2024 年 10 月 15 日，Willison 算过，提示词缓存与批处理结合，可以把 Claude 3.5 Sonnet 的 token 成本降低近 95%。实际节省多少取决于每个请求中共享提示词的占比，但方向是明确的。

结果不会一直留在那里

Anthropic 的批处理结果只能在创建后 29 天内下载。过了这个期限，批次仍然可见，但结果已无法取回。如果客户可能三个月后回来问“这份合同当时是怎么打标签的？”，这就是一个缺口。

因此，

save_to_customer_store

这一步必须在批次结束后立即执行，写入客户自己拥有的存储，并同时记录所用的提示词版本和模型。

如果客户同时还有实时功能在运行，OpenAI 还有一个值得一提的优势：批处理的速率限制与各模型的速率限制相互独立，大任务不会挤占实时流量的配额。

上线流程与常见错误

面对大规模语料，应遵循的顺序是：确认没人需要实时结果；测出平均请求大小；先用约 1,000 份文档跑一个小规模试验批次；按两项上限拆分其余部分；在提交大批次之前，先搭好失败和过期请求的重试循环。

试验批次能给出耗时和错误率的真实数据，向客户汇报时就有数字可依，而不是凭猜测。

最常见的错误是把 24 小时当成 SLA。其次是只按请求数拆分批次，提交时才发现超出了大小上限。第三种更难察觉：所用的

custom_id

无法对应回客户系统，30 万条结果回来后，根本分不清哪一行属于哪份合同。

剩下两种属于运维问题。一是把结果留在厂商平台上，忘了在第 29 天前下载。二是没有处理

errored

和

expired

两种情况，客户的报告悄无声息地漏掉了几个百分点的数据，却没人发现。

如何写进简历

阅读 FDE 岗位描述时，留意其中是否提到处理大量文档、定期运行评测或控制模型成本。如果有，批处理经验就值得带到面试中。

简历上写一句“将 N 份文档的打标签数据管道从实时改为批处理，成本减半，配有重试机制，结果存入客户自有存储”，能让招聘方看到你理解成本、可靠性和数据归属。

客户很少直接问你 Batch API 的事。他们会问这个月的账单为什么这么高，或者为什么偏偏在大任务运行那天聊天机器人变慢了。能早早发现一半工作量根本不需要即时响应的 FDE，往往也是能同时回答这两个问题的人。
