前沿部署工程师的 SQL 技能：

原标题：SQL Skills for Forward Deployed Engineers

摘要

这篇文章面向前沿部署工程师，说明为什么 SQL 是仅次于 Python 的重要技能：65% 的 FDE 招聘要求中出现 SQL。文章梳理了 FDE 实际需要的 SQL 模式（多表连接、窗口函数、CTE、聚合、日期函数、CASE 表达式），以及高级技能如 EXPLAIN 查询计划分析、索引设计、递归 CTE 和 JSON 操作。还比较了 Postgres、MySQL、SQL Server、Snowflake、BigQuery、Databricks 等方言差异，并给出在陌生客户数据库中探索 schema 的五步方法，以及生产环境安全操作和 dbt 相关建议。

为什么 SQL 是 Python 之后的第二项关键技能

SQL 出现在 65% 的前沿部署工程师职位招聘中，仅次于占比 78% 的 Python。这一频率低估了它的实际重要性。大多数 FDE 项目都涉及大量的客户数据工作：理解现有的数据模式、提取用于评测的测试数据集、跨客户系统联接数据、对客户团队在项目结束后将接管的查询进行性能调优，以及在生产环境中验证数据质量。这些工作大部分都是用 SQL 完成的。

FDE 所需的 SQL 熟练度不同于数据工程 SQL 或分析师 SQL。FDE 通常要在文档有限的陌生客户数据模式中工作，面对他们没有设计过的数据库，而且处于查询可能影响客户运营的生产环境中。因此，真正重要的技能与学术环境或纯分析岗位所强调的 SQL 技能有所不同。

本指南涵盖 FDE 在客户项目中真正需要的内容：实用的查询模式、性能考量、客户数据库导航技能，以及值得深入掌握的特定 SQL 方言。这里的视角是“什么能在真实的客户工作中带来好结果”，而不是“什么会出现在面试题中”。

每个 FDE 都应烂熟于心的核心 SQL 模式

多表联接及恰当的联接类型选择。 客户的数据模式通常包含 5-15 张通过外键关联的表，而大多数查询需要联接其中 3-7 张。关键技能在于判断何时使用 INNER JOIN（仅保留两表中都有匹配的行）、LEFT JOIN（保留左表全部行，右表无匹配处为 NULL）或 FULL OUTER JOIN（保留两表全部行）。错误的联接类型会悄无声息地产生错误答案，这是最糟糕的一类 bug。

用于时间序列和排名模式的窗口函数。 ROW_NUMBER()、RANK()、DENSE_RANK()、LAG()、LEAD() 以及窗口上的聚合函数（SUM、AVG、COUNT）是客户项目通常所需的分析查询中必不可少的。用例示例：去重记录并保留最新一条（ROW_NUMBER OVER PARTITION BY）、计算累计总额（SUM OVER ORDER BY）、找出每组的前 N 名（RANK OVER PARTITION BY）。窗口函数是区分 FDE 级 SQL 与基础 SQL 的标志。

使用公用表表达式（CTE）编写可读性强的复杂查询。 CTE 让你可以把复杂查询构建为一系列命名的子查询，而不是嵌套子查询。一个 200 行的查询用 8 个命名 CTE 表达，明显比用 5 层嵌套 SELECT 语句表达的同一查询更易于维护。项目结束后，客户工程团队会接手你的 SQL；CTE 结构的查询会被采纳和扩展，而嵌套子查询则会被重写或替换。

使用 GROUP BY 和 HAVING 进行聚合。 基本聚合几乎出现在每一条 FDE 查询中：按类别统计记录数、按组求和、按时间段计算指标平均值。HAVING 用于过滤聚合后的结果（而 WHERE 是在聚合之前进行过滤）。混淆 WHERE 和 HAVING 是最常见的 SQL 错误之一；理解何时使用哪个是基础。

跨方言的日期和时间函数。 不同的数据库有不同的日期函数（Postgres 和 Snowflake 中的 DATE_TRUNC，BigQuery 中的 TIMESTAMP_TRUNC，SQL Server 中的 DATEADD）。FDE 需要使用客户所用的任何方言，因此跨方言的灵活性比精通某一种方言更重要。常见操作：截断到月份、增加天数、计算日期差、将字符串解析为日期、将日期格式化为字符串。

用于条件逻辑的 CASE 表达式。 CASE WHEN ... THEN ... ELSE ... END 是 SQL 中的 if-then-else。它几乎出现在每一条客户相关查询中，用于分类、条件聚合和数据清理。掌握嵌套的 CASE 表达式以及带多个条件的 CASE；这是你在 SQL 中表达业务逻辑的方式。

区分资深 FDE 的 SQL 模式

使用 EXPLAIN 进行查询性能分析。 EXPLAIN（或 EXPLAIN ANALYZE）会显示数据库将使用的查询计划。资深 FDE 会阅读查询计划来识别性能问题：本应使用索引扫描的大表却进行了顺序扫描、本应使用嵌套循环连接却使用了哈希连接（或反之）、本可避免的高开销排序。阅读查询计划起初并不直观，但这正是运行 100 毫秒的 SQL 和运行 10 分钟的 SQL 之间的差别。

索引设计与选择。 了解表上存在哪些索引、哪些列被一起索引（复合索引），以及哪些查询可以使用哪些索引，能让你编写高效利用现有索引的 SQL，或向客户 DBA 推荐新索引。客户的数据模式中常常存在未记录的索引；了解如何通过数据库目录检查它们是 FDE 的基本技能。

集合操作：UNION、INTERSECT、EXCEPT。 它们不如连接常用，但对特定模式至关重要：合并相似查询的结果（UNION）、查找同时出现在两个查询中的记录（INTERSECT）、查找出现在一个查询但不在另一个查询中的记录（EXCEPT）。用例：比较两个时间点的客户数据快照、查找存在于一个系统但不存在于另一个系统的记录、从多个来源构建查找表。

用于层级数据的递归 CTE。 WITH RECURSIVE 用于处理树形结构数据：组织架构层级、评论线程、类别树、依赖图。带有父子关系的客户数据模式几乎总会在某个时刻需要递归查询。这个模式比基本 CTE 更难，但值得掌握，因为 SQL 中没有其他方法能干净地处理树的遍历。

现代方言中的 JSON 操作。 Postgres、BigQuery、Snowflake 以及大多数现代数据库都支持 JSON，让你可以查询行内的嵌套数据结构。客户的 schema 中越来越多地包含用于半结构化数据的 JSON 列。常见模式：从 JSON 中提取值、展平数组、按 JSON 属性过滤、对 JSON 内容进行聚合。具体语法因方言而异，但概念上的操作是相似的。

存储过程和用户自定义函数。 大多数 FDE 工作并不需要编写存储过程，但在浏览不熟悉的代码库时，能够读懂客户现有的存储过程非常重要。客户系统常常将业务逻辑封装在存储过程中，FDE 在设计变更之前需要先理解这些逻辑。

让 FDE 踩坑的数据库方言差异

Postgres： 许多现代应用的默认选择，并且日益成为分析类工作负载的默认选择。强大的 JSON 支持、成熟的窗口函数、中等规模分析的良好性能。使用 Postgres 客户环境的 FDE 比较轻松：文档丰富、行为可预测、性能特征易于把控。

MySQL： 常见于较旧的客户应用中。分析功能比 Postgres 弱，对 SQL 标准的遵循一致性较差，但由于应用广泛，FDE 会经常遇到它。需要注意：与 Postgres 不同的大小写敏感性、略有差异的日期函数语法、旧版本中较弱的 CTE 支持、事务隔离的怪癖。

SQL Server： 常见于企业客户环境中。强大的分析功能，包括窗口函数和 CTE。某些操作有独特的语法（用 TOP 而非 LIMIT、用 GETDATE() 而非 CURRENT_TIMESTAMP、用于过程式代码的 T-SQL 扩展）。服务企业客户的 FDE 应具备基本的 SQL Server 熟练度。

Snowflake： 客户分析工作负载中占主导地位的云数据仓库。性能出色、窗口函数强大、原生 JSON 支持，以及时间旅行查询和零拷贝克隆等独特功能。与数据成熟度高的客户合作时，FDE 的工作几乎总会涉及 Snowflake。值得了解的具体模式：用于半结构化数据的 VARIANT 列、用于展开数组的 FLATTEN、用于历史查询的时间旅行语法。

BigQuery： 以 Google 为中心的客户技术栈中占主导地位的云数据仓库。独特的语法（STRUCT 和 ARRAY 类型、project.dataset.table 命名、用于提取日期部分的 EXTRACT）。性能特征与行式数据库截然不同：对分区数据进行全表扫描是常态，索引不受用户控制，成本按每次查询扫描的字节数计算。

Databricks SQL： 在以 AI 为重点的客户环境中越来越常见。基于 Spark SQL 并带有扩展。概念上与 Snowflake 和 BigQuery 类似，但具有处理 Delta Lake 表和增量处理的特定模式。从事 AI 客户部署工作的前沿部署工程师经常会在传统数据仓库之外或代替传统数据仓库遇到 Databricks。

如何在不熟悉的客户 Schema 中开展工作

第一步：找到 schema 文档。 客户数据库有时会有文档；但通常不完整或已过时。首先向客户团队索取任何现有的 schema 文档、ER 图或数据字典。将其视为起点，而非事实依据。

第二步：检查数据库目录。 大多数数据库都有描述自身 schema 的系统表（标准 SQL 中的 INFORMATION_SCHEMA、Postgres 中的 pg_catalog、SQL Server 中的 sys 表）。查询这些表以列出表、列、数据类型、主键、外键和索引。这能让你获得实际存在的 schema，而它往往与文档不一致。

第三步：抽样查看数据。 对每张表运行 SELECT * FROM each_table LIMIT 100 来查看真实数据。寻找列命名模式、值分布、明显的外键（table_id 列）以及数据质量问题。抽样能揭示文档通常不会说明的内容：哪些列实际有数据、哪些列包含垃圾数据、哪些列以不同名称表示同一概念。

第四步：通过示例 join 梳理表关系。 如果你怀疑两张表相关联，但这种关系没有通过外键明确表达，可以编写一个测试查询将它们 join 起来，并检查结果数量是否合理。基数检查（一对一、一对多、多对多）即使在没有文档的情况下也能揭示数据结构。

第五步：与客户团队验证假设。 一旦你对 schema 有了初步理解，把它写下来并请客户工程团队验证。提出具体问题：“我假设这张表中的 customer_id 对应 customers 表中的 id，对吗？”客户通常很欣赏这种结构化的问题，因为它们能揭示客户自身文档中的缺口。

常见问题

对于 FDE 工作来说，学习 SQL 最有效的方法是什么？

构建真实的东西。在本地搭建一个 Postgres 数据库，加载一个公开数据集（data.gov、Kaggle、通过 GitHub API 获取的 GitHub 数据），并针对它编写 20-30 个分析查询。在真实数据上进行真实练习，能建立教科书无法给予的肌肉记忆和模式识别能力。然后在不同的方言中练习（在 BigQuery 和 Snowflake 的免费层级中尝试同一数据集），以培养方言灵活性。

FDE 需要掌握多少 SQL 性能调优？

达到能识别查询存在性能问题并自行修复常见问题的程度即可。你不需要达到 DBA 级别的查询优化专家水平。标准是：能读懂 EXPLAIN 输出，识别明显糟糕的查询计划，知道何时该添加索引、何时该重构查询，理解顺序扫描与索引扫描的区别。深度调优由客户的 DBA 负责；FDE 处理的是日常合作流程中出现的表层优化工作。

在客户环境中，我应该学 SQL 还是 NoSQL？

两者都学，以 SQL 为优先。大多数客户数据存放在关系型数据库中，SQL 是通用的访问语言。NoSQL 技能（MongoDB、DynamoDB、键值存储）会在特定的客户环境中用到，值得掌握，但在 FDE 工作中所占的比重小于 SQL。如果时间只够学一个，先学 SQL。

FDE 如何在生产环境的客户环境中安全地处理 SQL？

有几个实践方法。第一，在对生产环境执行之前，始终先在开发或预发布环境上测试查询。第二，尽可能使用只读连接，防止意外写入。第三，为可能返回海量结果集的测试查询添加 LIMIT 子句。第四，修改数据时，使用事务包裹操作，并在提交前核对行数。第五，任何影响生产环境的工作都要遵循客户的变更管理流程。跳过这些做法正是 FDE 意外搞坏客户系统的原因。

那 dbt 对 FDE 来说呢？

dbt（data build tool）是现代数据栈中占主导地位的转换层。与数据成熟度较高的客户合作的 FDE 会经常遇到 dbt 项目。值得掌握的技能：阅读 dbt 模型定义和血缘关系，理解 dbt 宏及其编写方法，读懂并使用 dbt 项目结构，针对客户数据运行 dbt 测试。你不需要成为 dbt 专家才能成为高效的 FDE，但 dbt 的熟练度出现得足够频繁，对于服务现代数据客户的工程师来说，这项投入是值得的。
