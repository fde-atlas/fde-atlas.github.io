FDE 业务术语表：在写代码之前先定义术语

原标题：Business Glossary for FDEs: Define Terms Before Code

FDE Times · 2026-11-08 · 约 7 分钟读完

摘要

文章面向前沿部署工程师，论述为何要在写代码之前先厘清业务术语。同一个词（如“已完成订单”）在不同部门有不同含义，SQL 的 WHERE 子句会默默选定一种解释，一旦数字与客户账目不符，损失的是信任。作者给出五步法：收集高频名词、用边界案例单独访谈领域专家、用 Event Storming 对齐各部门、为每个含义命名并指定归属部门和可执行规则、把术语表落实到列名、指标名和语义层（如 dbt、Palantir Ontology）。文中用零售公司例子说明：1,000 笔付款成功、920 笔发货、850 笔过退货期的订单，仪表盘显示 1,000 而会计记 850，差距源于定义而非数据错误。文章还列出常见错误：只采纳声音最大的部门的定义、术语表只躺在 wiki 上、把术语表一次性冻结不再更新。

要点

  • 同一个业务词在不同部门含义不同，边界由部门文化决定。
  • WHERE 子句会默默选定一种含义，错误定义直接损害客户信任。
  • 五步法：收集名词、边界案例访谈、Event Storming 对齐、命名并指定归属、落地到代码。
  • 术语表必须进入列名、指标名和语义层，而非只放在 wiki。
  • 常见错误：采纳强势部门的定义、术语不进代码、冻结术语表不随业务演进。

一个 WHERE 子句会悄悄选定其中一种含义，而驻扎在客户现场的前沿部署工程师，会为错误的那种含义付出信任的代价。

简要说明

  • 像“客户”或“产品”这类多义词是软件项目中反复出现的困惑来源，而含义之间的边界通常由部门文化来划定。
  • 不要强迫全公司统一到一种含义上：为每种含义起一个专属名称，指定一个负责部门，并给出一条可衡量的规则。
  • 术语表只有活在列名、指标名称和语义层中才有价值，放在没人阅读的 wiki 页面上毫无意义。

想象你在一家零售公司的第二周。你演示一个名为“本月已完成订单”的仪表盘。销售主管点头；首席会计师皱眉，因为这个数字比她账上的高。数据管道没有任何 bug。他们两人只是在同一个名称下统计不同的东西。

Martin Fowler 将此描述为一个项目接一个项目反复出现的问题：像“客户”或“产品”这样的多义词会造成无休止的困惑。对于构建内部产品的工程师来说，代价不过是几次会议。

而对于坐在客户现场的前沿部署工程师来说，代价是信任：一旦人们见过一个错误的数字，之后看到每一个数字都会带着怀疑。

在写代码之前处理这个问题的原因很简单。Fowler 写道，软件难以很好地应对歧义。人们可以说“已完成订单”，并在上下文中仍然彼此理解。而一条

WHERE status = 'completed'

子句必须精确选定一种含义，而且它是悄悄选定的，不会告诉任何人。

为什么一个词会有三种含义？

Event Storming 的创始人 Alberto Brandolini 直言不讳地说，术语本质上是模糊的：每个人都会以自己的方式解读同一个词，因为每个部门有不同的视角和不同的需求。

Codurance 博客上的一篇文章给出了一个来自同一家公司内部的例子：销售专家和会计专家可以把两个不同的概念附加到同一个词上。

Fowler 提出了一个更值得记住的观点。业务上下文之间的边界通常不是由技术决定的，而主要由人的文化决定：哪些团队一起工作，哪个部门负责什么。每个上下文对同一概念可能拥有完全不同的模型。

所以你的目标不是赢得一场关于“正确”含义的争论。Three Dots Labs 说得很清楚：同一个词在不同上下文中表示不同的东西是正常的，只要上下文之间的边界被清晰地划定。

前沿部署工程师的职责是让每种含义显现出来，为它命名，并记录它适用的范围。

一个词，“已完成”，三个数字

回到那家假想的零售公司。销售部门认为，客户支付成功，订单即告完成。仓库部门认为，货物已扫描出库并交付给承运商，订单才算完成。会计部门则认为，只有当客户收到货物、退货期已过且没有发生退款时，订单才算完成。

用数字让它更具体：假设本月有 1,000 笔支付成功的订单，920 笔已从仓库发货，850 笔已过退货期且无退款。你的仪表盘按支付状态列统计，所以显示 1,000。会计记录的是 850。这 150 笔订单的差距不是数据错误，而是定义错误。

现在再引入一个回答“我的订单完成了吗？”的客服 AI Agent。如果这个 Agent 按销售口径理解“完成”一词，它会对仍停留在仓库中的订单回答“是”。同样的定义错误，但这次直接暴露给了终端客户。

这个示例的定稿术语表可能如下：

规范名称归属部门可度量的规则数据字段已定稿的边界情况
已支付订单销售支付交易成功payment_status = 'captured'货到付款订单何时计入？
已发货订单仓库存在出库扫描记录shipped_at IS NOT NULL部分交付的订单
收入结算订单会计已交付、已过退货期、无退款settled_at IS NOT NULL换购其他商品的订单

请注意，这张表刻意不再包含“完成”这个词。从现在起，“完成”一词本身不得再出现在代码、指标名称或 Agent 的提示词中。

五步定稿术语表

第一步是收集词汇。阅读工单、表名、列名、客户发来的 Excel 文件和会议记录，然后标记出现频率最高的名词。最熟悉的词，比如“客户”“订单”和“产品”，往往是最危险的，正如 Fowler 所警告的那样。

第二步：分别访谈每位领域专家，正如 Codurance 所建议的。不要问“完成是什么意思？”，因为每个人都会给出笼统的回答。要用边界情况来提问：“半退款的订单算吗？”“如果客户换了尺码，原订单算什么？”。这些情况才能真正暴露人们实际使用的定义。

第三步：让各部门参加同一场讨论。Three Dots Labs 认为 Event Storming 是发现并对齐开发者与利益相关者之间词汇的最佳方式之一。

当“客户付款”“货物离开仓库”“退货期到期”等事件按时间顺序贴在墙上时，每个人都能看到自己的“完成”在这条时间线上处于什么位置。

第四步：为每个含义命名并指定负责人。每个含义都有自己的名称、一个在定义需要变更时负责的部门，以及一条机器可以执行的规则。“订单没问题”不是定义。“已

settled_at

且无退款记录”才是。

第五步：把术语表放进系统。Eric Evans 将这个目的地称为通用语言：一种开发人员与业务用户之间共享的、严谨的语言，在会议和代码中以完全相同的方式使用。变量名、列名、指标名以及 AI Agent 的工具描述都必须使用规范名称。

工具在这一步能提供帮助。dbt 的语义层让你可以在建模层一次性定义一个指标，这样每个业务部门无论使用什么工具，都共享同一个定义。

当定义发生变化时，变更会传播到所有调用它的地方。在 Palantir，Ontology 用对象、属性和链接来描述客户组织。但工具只是存储定义；选择哪个定义仍然是人与人之间的事。

会让术语表早早夭折的错误

最常见的错误是采纳嗓门最大的人或为项目付费的部门的含义。另一个部门不会在会议上争辩；它会悄悄保留自己的 Excel 文件，而你的系统就成了第二个没人信任的系统。

第二个错误是术语表只存在于 wiki 上，从未进入代码。如果列仍然叫

is_completed

，六个月后新来的工程师会按自己猜测的任意含义来使用它。

第三个错误是把术语表冻结起来。Fowler 强调，语言必须随着团队对领域理解的深入而演进，所以要记录每个术语确定的日期和批准人，并在客户的流程发生变化时重新开启讨论。

把这项技能变成职业优势

阅读 FDE 职位描述时，留意诸如“领域建模”、“ontology”、“语义层”或“与业务利益相关者合作”之类的措辞。它们表明这家公司正需要这种技能。

在简历上，不要写“与客户沟通良好”。写一行有具体成果的内容，例如与三个部门敲定了一套指标定义，消除了仪表盘与账本之间的差距。

在面试中，准备一个关于某个术语导致两个部门互相误解的故事：你是如何发现的，你询问了哪些边界情况，以及最终定义存放在系统的哪个位置。这样的故事表明你既能与数据打交道，也能与人打交道，而这正是这个职位所要求的。

练习：一个状态列，一个下午

打开你正在处理的订单表或客户表，对状态列运行

SELECT DISTINCT

，并列出它包含的每一个值。对每个值，写一个边界情况问题，例如“部分退款的订单应该取哪个值？”。

把这份清单拿给两个不同部门的人，然后把结果填进一个类似上面示例的五列表格。两个答案不一致的地方，就是你术语表的第一行。

错误的代码一个下午就能修好。而一个已经被误解、并且扩散到每张表、每份报告和每个 AI Agent 回答中的词，还得从客户头脑中纠正过来，所以在敲下第一个

WHERE

.
