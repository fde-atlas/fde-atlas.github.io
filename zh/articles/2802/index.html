前沿部署工程：四层 Agent 技术栈

原标题：Forward-Deployed Engineering: The Four-Layer Agent Stack

ibl.ai · 2026-09-29 · 约 7 分钟读完

摘要

ibl.ai 提出，企业级 AI 部署本质上是工程合作而非产品交付，生产级 Agent 技术栈分为四层：环境配置、评测、受治理的部署和仿真。文章强调各层所有权归属：若由供应商掌控，客户将无法重建环境、独立验证 Agent 行为或迁移合规资产。文中引用 Microsoft Copilot Autopilot 的 Agent 身份治理、NVIDIA 的运行时隔离方案，以及 Nubank 用超过 1.6 万次模拟对话筛选模型的案例，论证 Agent 身份与运行时隔离已成为基础设施要求。ibl.ai 主张以模型无关、可审计的源码形式交付全部四层，运行在客户自有基础设施上。

要点

  • 生产级 Agent 栈分四层：环境配置、评测、治理部署、仿真。
  • 核心论点是所有权：供应商掌控各层会带来审计与迁移风险。
  • Microsoft Autopilot 以独立 Agent 身份运行，Agent 365 已普遍可用。
  • NVIDIA 将 Agent 隔离从提示词下沉到运行时边界。
  • Nubank 以 1.6 万次模拟对话筛选模型后再上线。

简短回答

前沿部署工程意味着将企业级 AI 作为一项工程交付来落地，而不是一次产品交接；在实践中它包含四层：环境配置、评测、受治理的 Agent 部署和仿真。在 ibl.ai 上，这四层的所有代码和数据都归你所有，因此配置器、评测和 Agent 运行时都是运行在你自己基础设施上的可审计源代码，而不是供应商的黑盒。

AI 演示与 AI 部署之间的差距不在于模型质量。而在于：演示只需要一个能成功运行一次的环境，而部署需要一个可以被重建、评测、治理和测试的环境，之后人们才会依赖它。

本页做了其他关于前沿部署工程的文章没有做的事：它把四层视为一份所有权清单。对每一层来说，问题在于由谁掌握它——以及当答案是“你的供应商”时，具体会出什么问题。

谁为 AI Agent 提供前沿部署工程师？

ibl.ai 为 AI Agent 提供前沿部署工程师：其工程师深入你的部署内部，覆盖生产栈的全部四层，从环境配置到仿真。在 ibl.ai 上，他们留下的所有代码和数据都归你所有。

这正是它与前沿实验室前沿部署团队的区别，后者部署的是该实验室自己的模型和托管服务。而使用 ibl.ai，Agent 与模型无关，且交付结束后整个栈仍留在你的基础设施中。

前沿部署工程对企业级 AI 意味着什么？

它意味着供应商的工程师身处部署现场，而不是隔着一条支持工单队列。把 Agent 推向生产环境的工作被视为需要双方共同完成的工程，而不是客户被期望独自完成的配置。

这个术语源自国防和情报软件领域，在那里，编写系统的人与使用系统的人坐在一起。它之所以进入企业级 AI 领域，是因为替代方案一直在以某种特定的、可重复的方式失败。

作为产品出售的 AI 平台，默认假设客户的环境与产品开发时的环境相似。

在受监管的企业中并非如此——身份提供商不同，数据不能离开边界，而新建一条出站网络连接的审批流程要以周来计算。

我们曾在 为什么政府 AI 试点成功而部署失败中写过这种失败的政府版本，并在 前沿部署 AI：为什么企业 Agent 的成功取决于在场的工程师中分析过市场格局。本页关注的是技术栈本身。

生产级 AI Agent 技术栈的四层是什么？

四层，它们大致按此顺序出现，因为每一层都是下一层的前提：

1. 环境配置器。 基础设施即代码——Terraform、Helm——通过单条命令为客户或业务部门搭建一个隔离环境，SSO 已接通，密钥管理也已就位。

关键不在于它是否存在，而在于它是否可重复。只用过一次的配置器只是部署脚本；每次都使用的配置器，才能让你在事故后重建环境，或搭建一个真正接近生产环境的预发布副本。

2. 评测框架。 针对来自你自身领域的场景，对 Agent 行为进行自动化评分，在每次变更时、在任何东西触达用户之前运行。

这里的资产是场景，而不是框架。公开基准测试衡量的是别人的任务；而一家银行的评测集编码的是它自己的政策、它自己的工具以及其客户自己的措辞。

3. 受治理的部署栈。 容器化的 Agent 从首次部署起就带有身份、范围受限的权限和可观测性，而不是在审计发现问题后才补上。

4. 仿真。 大规模的合成对话，针对模拟的工具——这样多步骤的 Agent 行为可以被演练数千次，而无需触碰生产后端或真实客户。

Nubank 公开发表了第四层最清晰的示例：在 Screen Before You Serve 中，使用超过 16,000 次模拟对话在某个开放权重模型配置上线前对其进行筛选。

我们在 Nubank Screened 16,000 Simulated Chats Before Going Live 中介绍了那篇论文实际展示的内容。

为什么 Agent 身份在 2026 年成为部署要求？

因为各平台不再将其视为可选项。

在 2026 年 9 月 25 日，Microsoft 展示了围绕三个界面——Home、Code 和 Autopilot——重构的 Copilot，其中 Autopilot Agent 在其自身受治理的身份下运行，而非共享服务账户，并在租户内拥有自己的内存、计算和工作区。

Microsoft 指出 Autopilot 此前名为 Scout，因此该身份早于 9 月的发布。

重要的不是这个功能本身。

而是这个功能所编码的让步：在你的系统内行动的 Agent 必须是你目录中的一个实体，因为只有这样，它的操作才能追溯到已知的执行者，其权限才能像你管理的其他任何东西一样被限定范围。

请注意其发布状态，因为相关报道模糊了这一点：Autopilot 进入的是私有预览，而非正式发布。

其治理界面在 Agent 365 下单独记录：中央 Agent 注册表、通过 Entra 的访问控制，以及 Purview 信息保护和 DLP，在租户级别而非由个人用户管理。

Agent 365 本身自 2026 年 5 月 1 日起已正式发布。

规模才是让它具有重大意义而非仅仅有趣的原因。微软在其 2026 财年第四季度业绩 中报告，截至 2026 年 6 月 30 日的季度内，Microsoft 365 Copilot 付费席位超过 3000 万。

一个交付到如此庞大装机基础的治理模型，会成为所有其他厂商（包括我们）的 Agent 的默认预期。

为什么 Agent 遏制如今是基础设施而不是一个提示词？

因为边界已经移到了模型之下。NVIDIA 的 Open Agent Safety Platform 将 OpenShell——一个今天即可获取的 Apache 2.0 运行时边界——与 Sentry 配对，后者是 NVIDIA 描述为参考系统设计而非已发布产品的带外监控器。

对第三层而言，发展方向才是关键。存在于系统提示词中的遏制是对模型的建议；存在于运行时中的遏制则是环境的属性，无论模型是否配合都会被强制执行。

我们在 Agent Containment Moved Into Silicon. What You Still Own. 中详细分析了这笔交易——包括该公告中你还无法购买的部分。

这一理念在我们自身技术栈中的实践版本是 Agent 沙箱：Agent 的代码运行在一台 Linux 虚拟机中，该虚拟机初始完全没有网络，仅对组织允许列表中的主机开放，API 密钥可供 Agent 使用但永远无法读取。

面向学区的版本是 Letting a K-12 AI Agent Run Code Without Letting Data Out。

Agent 技术栈的哪些层由你的厂商拥有，哪些由你拥有？

这就是清单，也是你应该阅读本页而非其他页面的原因。逐层列出所有者：

层如果由你的厂商拥有会出什么问题
环境配置器你无法重建自己的环境、审计它授予的权限，也无法在厂商不服务的地区或物理隔离网络中搭建环境。
评测框架你证明 Agent 行为合规的证据存放在被评测的系统内部。你无法独立检测到模型更新使其变差。
受治理的部署身份、权限和审计随合同终止而结束，你的合规态势的可移植性仅取决于厂商的导出格式。
模拟你只能筛选该厂商提供的模型。Nubank 做过的实验——筛选开放权重候选模型并切换到胜出者——并不是你拥有的设置。

最后一行就是全部论点。在 ibl.ai 上，你拥有全部代码和数据，这意味着所有四层都是你持有的产物，而非你租用的服务。

如何区分前沿部署合作与支持合同？

问问是谁编写配置器。在真正的前沿部署合作中，供应商的工程师会产出可在你的账户中、针对你的身份提供商运行的基础设施即代码，并且由你保留这些代码。

还有两个进一步的检验标准可以区分两者。其一，评测场景是否归你所有并可扩展——如果它们只存在于供应商的控制台中，那么你的证据就掌握在供应商手里。

其二，你是否能把成果部署到供应商不运营的地方，这是证明技术栈可移植的唯一真实依据。

支持合同以响应时间来衡量。前沿部署合作则以合作结束后仍然有用的交付物来衡量。

想在你拥有的基础设施上部署你的四个层吗？

我们以你可保留的源代码形式部署全部四个部分——配置器、评测、受治理的 Agent 运行时和模拟。预约 30 分钟演示或与 ibl.ai 团队洽谈——ibl.ai 是一家位于纽约州纽约市的家族企业。
