前沿部署工程师 vs 解决方案架构师

原标题：Forward deployed engineer vs solutions architect

FDE Interview Prep · 2026-09-25 · 约 35 分钟读完

摘要

文章通过分析 Anthropic、OpenAI、Google Cloud、Baseten 等公司的招聘启事，区分前沿部署工程师（FDE）与解决方案架构师（SA）两种岗位。核心判断标准是：系统上线后出问题，谁动手改代码。FDE 在客户系统内编写并维护生产代码，深度服务一两家客户；SA 负责方案设计、原型验证和咨询，覆盖更多客户，通常隶属销售或市场推广部门。文章还比较了两者在代码类型、上线后职责、所属部门、薪酬结构和面试形式上的差异，指出 FDE 并非 SA 的晋升，而是深度与广度两种不同杠杆的选择。

要点

  • 判断标准：系统上线后出故障，谁负责改代码。
  • FDE 写生产代码并承担上线后维护，SA 只做原型验证和咨询。
  • FDE 深耕一两家客户，SA 面向更宽的客户组合。
  • 职位名称最不可靠，应看职责描述和所属部门。
  • FDE 不是 SA 的晋升，而是深度与广度两种杠杆的选择。

直接给你答案。前沿部署工程师（FDE）编写与某一客户的系统一起运行或运行于其内部的生产代码，并在上线后对其负责。解决方案架构师（SA）负责设计解决方案，用原型和概念验证来证明其可行性，并指导他人构建和运行该方案，通常隶属于销售、市场推广或现场团队。本指南的其余部分将教你如何从职位描述本身、用雇主自己的话来区分这两种职位，然后介绍两者面试的差异，以及如何从 SA 转型为 FDE。如果你想先看精简版，免费课程FDE 与相邻职位的区别对另一组职位描述语句进行了同样的测试。

需求挖掘、设计和客户信任属于两种职位共同的工作。区别在于最终由谁来编写实际运行的代码。

区分一个职位的那道关键问题

问一句：系统上线后出了故障，由谁来写修复代码？如果这个岗位会改动生产代码（集成、可靠性、值班响应），那它就是 FDE 工作，无论头衔是什么。如果这个岗位只做分诊、协调或提建议，而由别人改代码，那它就是 SA 工作。

头衔是页面上最不可靠的证据。有些 FDE 职位带有售前职责，有些架构师职位也会交付真正的代码。下面的章节会告诉你哪些内容才是决定性的。

下面这段代码展示了这种差异。以下两个版本都从分页 API 中拉取支持工单。

SA：证明 API 能回答。 这是概念验证，是在售前一周里应该写的东西。

import requests

URL = "https://api.example.com/v1/tickets"
params = {"limit": 100}
tickets = []
while True:
    page = requests.get(URL, params=params).json()
    tickets += page["data"]
    if not page["next_cursor"]:
        break
    params["cursor"] = page["next_cursor"]
print(len(tickets), "tickets")

它在一个安静的下午能正常工作。遇到第一个 429 或 503 就会挂掉，重跑得从第一页重新开始，而且任何地方都不会保存数据。

FDE：证明它能持续回答。 首先，给单个请求加上重试：遇到 429 时退避，

5xx

，并遵守

Retry-After

（当 API 以秒为单位返回该值时），再加上 ，遇到任何其他错误则大声报错。

import json, random, sqlite3, time, requests

URL = "https://api.example.com/v1/tickets"

def get(params, tries=6):
    for n in range(tries):
        r = requests.get(URL, params=params, timeout=10)
        if r.status_code != 429 and r.status_code < 500:
            r.raise_for_status()  # other 4xx: fail loudly
            return r.json()
        wait = r.headers.get("Retry-After", "")
        wait = int(wait) if wait.isdigit() else min(2 ** n, 30)
        time.sleep(wait + random.random())  # jitter
    raise RuntimeError(f"gave up after {tries} tries: {params}")

然后是同步本身。每一页的行数据及其后的游标在同一个事务中提交，插入操作是以工单 ID 为键的 upsert，因此崩溃的运行可以从最后保存的页面恢复，重放也不会改变任何数据。每一页都会写入一条结构化日志。

db = sqlite3.connect("sync.db")
db.execute("CREATE TABLE IF NOT EXISTS tickets"
           " (id TEXT PRIMARY KEY, body TEXT)")
db.execute("CREATE TABLE IF NOT EXISTS checkpoint"
           " (k TEXT PRIMARY KEY, cursor TEXT)")
row = db.execute("SELECT cursor FROM checkpoint").fetchone()
cursor = row[0] if row else None
while True:
    page = get({"limit": 100} | ({"cursor": cursor} if cursor else {}))
    cursor = page["next_cursor"]
    with db:  # rows and cursor commit together, or not at all
        db.executemany(
            "INSERT INTO tickets VALUES (?, ?) ON CONFLICT(id)"
            " DO UPDATE SET body = excluded.body",
            [(t["id"], json.dumps(t)) for t in page["data"]])
        db.execute("INSERT OR REPLACE INTO checkpoint"
                   " VALUES ('tickets', ?)", (cursor,))
    print(json.dumps({"event": "page_synced",
                      "rows": len(page["data"]), "cursor": cursor}))
    if not cursor:
        break  # done: the next run starts a fresh pass

我们用一个每隔几次调用就返回 429 或 503 的假 API 对两者进行了测试。概念验证在第三次请求时就挂了。生产版本则顺利跑完；中途被杀掉后，它从保存的游标处恢复，第二次完整运行后行数保持不变。在面试中值得大声说出的那句话是：“我的概念验证证明了它可行；而生产版本才是让我半夜被叫起来的那个。” 不稳定的 API 集成问题 正是要求你在面试条件下构建这样的东西。

服务多少客户

FDE 头衔下的目标达成收入（OTE）并不能证明这是销售岗位。Okta 将其首席 FDE 的薪酬表述为 OTE，“包含基本工资和激励性薪酬”，且同一招聘启事中说“你仍然要写代码”。来源 24首席前沿部署工程师 - Okta for AI Agents发布方Okta (Greenhouse)来源类型公司招聘启事 而 Baseten 在一份 FDE 经理招聘启事中表示“Baseten 的 FDE 不是销售职能”。来源 8工程经理，前沿部署工程（LLM）@ Baseten发布方Baseten (Ashby)来源类型公司招聘启事

最公平的薪酬比较是同一家雇主同时发布这两个职位。Baseten 和 Modal 都是这样做的，并附有薪酬信息，但它们给出了不同的答案。截至 2026 年 9 月，Baseten 的前沿部署工程师招聘启事显示“$165K – $330K • Offers Equity”，记录为工资。来源 25前沿部署工程师招聘启事发布方Baseten (Ashby job board)来源类型公司招聘启事 其解决方案架构师职位隶属于市场推广部门，显示相同的区间和相同的股权说明；我们的记录没有说明该区间是基本工资还是总薪酬。来源 5解决方案架构师 @ Baseten发布方Baseten (Ashby)来源类型公司招聘启事 FDE 招聘启事所属的部门被 Baseten 称为“EPD”。来源 25前沿部署工程师招聘启事发布方Baseten (Ashby job board)来源类型公司招聘启事 因此在 Baseten，公布的薪酬并不区分这两个职位；区分它们的是部门和代码。Modal 的薪酬区间则不同：截至 2026 年 9 月，其解决方案架构师招聘启事显示 $200K–$280K 加股权，未说明是基本工资还是总薪酬，并要求有 5 年以上解决方案工程或售前工程经验，而其前沿部署工程师 - ML 招聘启事列出的工资为 $180K–$250K 加股权。来源 26解决方案架构师 @ Modal发布方Modal (Ashby)来源类型公司招聘启事来源 27前沿部署工程师 - ML @ Modal发布方Modal (Ashby)来源类型公司招聘启事 SA 的薪酬区间在纸面上更高，但其中可能包含浮动薪酬，而且这两个职位的级别可能并不相同。两家雇主，两种答案：公布的薪酬并不能告诉你总体上哪个职位薪酬更高。

出差

出差要求按各职位发布信息说明，且各区间有所重叠。截至 2026 年 9 月，在 FDE 方面，OpenAI 的旧金山职位要求出差比例最高可达 50%，Anthropic 的职位预计为 25%。来源 1Job Application for Forward Deployed Engineer at Anthropic发布方Anthropic (Greenhouse)来源类型公司职位发布来源 3Forward Deployed Engineer (FDE) - SF发布方OpenAI (Ashby)来源类型公司职位发布在 SA 方面，AWS 的解决方案架构师职位预期出差比例为 15–20%，而 Modal 的解决方案架构师职位要求愿意出差最高可达 30%。来源 17Solutions Architect, Enterprise Greenfield发布方Amazon (amazon.jobs)来源类型公司职位发布来源 26Solutions Architect @ Modal发布方Modal (Ashby)来源类型公司职位发布一个架构师职位可能比 FDE 职位要求更多出差，因此在这些职位发布中，出差并不能区分这两种角色。阅读这一行内容，出差一课会告诉你在与招聘人员通话前应该问什么。

在五条真实职位描述上试一试

以下是来自真实职位发布的五条描述。在阅读答案之前，请先判断每一条属于：FDE、SA，还是都不是？如果你在听音频，请在此暂停。

  • “这不是一个演示型岗位。你要为在真实世界中运行的系统负责。”
  • “这个岗位不是做演示支持的。”
  • “与传统咨询类岗位不同”，你将“编写代码、调试，并共同交付”“直接在客户环境中运行”的解决方案。
  • “你仍然要编写代码”，出现在一个以目标达成薪酬（on-target earnings）形式公布薪资的职位发布上。
  • “一个以产品为导向、背负销售指标的技术销售岗位。”

答案，以及决定答案的关键词：

  • FDE。 Cursor 的 FDE 职位发布。来源 7Forward Deployed Engineer发布方Cursor (Ashby job board)来源类型公司职位发布板决定性的是第二句话，而不是“不是演示”：“为在真实世界中运行的系统负责”指的是该岗位需要对其负责的持续运行的系统。
  • SA，而且这是个陷阱。 Modal 的解决方案架构师职位发布先说了这句话，然后又称自己为“一个战略性、咨询式的岗位”。来源 26Solutions Architect @ Modal发布方Modal (Ashby)来源类型公司职位发布如果第一条描述让你以为“不是演示”就意味着 FDE，那么第二条说明了为什么并非如此：一个关键词可以排除某个角色，但很少能单独确认某个角色。请读下一句。
  • FDE。 Google Cloud 的 GenAI FDE 职位发布。来源 4Forward Deployed Engineer IV, GenAI, Google Cloud — Google Careers发布方Google来源类型公司职位发布这条描述点出了它不是什么（“咨询类”），也点出了它是什么的动词：编写代码、调试、交付，而且是在客户的环境内。
  • FDE。 Okta 的首席 FDE。来源 24Principal Forward Deployed Engineer - Okta for AI Agents发布方Okta (Greenhouse)来源类型公司职位发布。薪酬栏看起来像销售，但“你仍然要写代码”是职责，而职责比薪酬栏更重要。
  • 都不是：比起两者更接近销售。 Ramp 的 AI Solutions Engineer 是一个背负销售配额的技术销售岗位，而不是前沿部署工程岗位。来源 28Ramp Ashby job board (AI Solutions Engineer)发布方Ramp (Ashby job board)来源类型公司职位发布。“背负配额”是决定性的词，而像这样擦边而过的职位名称正是你要读透职位名称背后内容的原因。

如果你全部答对了五道题，你就掌握了方法：找到起决定作用的职责，读任何口号之后的下一句话，并让职责的分量高于职位名称和薪酬栏。Telling FDE apart from its neighbors 还有另一组案例可供练习，其中还藏着一个陷阱。

售后神话

你会读到这样的说法：FDE 只在合同签署之后工作，而解决方案架构师只在合同签署之前工作。例如，招聘平台 Paraform 将 FDE 描述为接手解决方案工程师留下的工作，但没有为这种交接提供任何来源。Source 42Forward-Deployed Engineer vs. Solutions Engineer vs. Customer Engineer发布方Paraform来源类型招聘平台 雇主自己发布的职位信息并不支持这种清晰的划分。

在售前工作的 FDE。 OpenAI 的金融服务 FDE 职位要求 FDE “从售前到生产上线后全程负责需求探索与范围界定”。来源 9Forward Deployed Engineer (FDE), Financial Services- NYC发布方OpenAI (Ashby)来源类型公司招聘信息 截至 2026 年 9 月，Anthropic 正在招聘其首个前沿部署工程售前项目负责人，负责带领 FDE 团队“从商机推进到签署合同”，与之对应的是一位售后负责人，负责从签约开始之后的交付工作。来源 43Pre-Sales Program Lead, Forward Deployed Engineering发布方Anthropic (Greenhouse)来源类型公司招聘信息 Ramp 的工程博客称其 FDE 团队与客户合作，“从他们还是销售漏斗中的潜在客户，到实施与上线，再到长期支持”。来源 44Forward Deployed Engineering发布方Ramp Builders（工程博客）来源类型公司博客 LangChain 的部署工程团队覆盖“从售前评测到部署后的咨询工作”。来源 45Deployed Engineer (UK) @ LangChain发布方LangChain (Ashby job board)来源类型公司招聘信息 The Pragmatic Engineer 报道称，许多雇佣 FDE 的初创公司利用他们来帮助赢得客户。来源 6What are Forward Deployed Engineers, and why are they so in demand? 在售后工作的架构师。 OpenAI 自己的 FDE 负责人 Colin Jarvis 在 2026 年 5 月称解决方案架构是售后的“规模化动作”，并将 FDE 团队与之区分开来。来源 16The Future of Forward Deployed Engineering | OpenAI, Ramp, Nominal, Dataland发布方South Park Commons (YouTube)来源类型演讲或访谈录音 Anthropic 的应用 AI 架构师明确属于售前岗位。来源 2Job Application for Applied AI Architect, Commercial at Anthropic发布方Anthropic (Greenhouse)来源类型公司招聘信息 但 Vercel 的解决方案架构师覆盖“售前与售后两个技术环节”，而 Databricks 的交付解决方案架构师则是售后技术负责人。来源 10Delivery Solutions Architect发布方Databricks (Greenhouse)来源类型公司招聘信息来源 18Solutions Architect发布方Vercel (Greenhouse)来源类型公司招聘信息

因此，“售前还是售后？”并不能区分这两种角色。不妨问一个更好的问题：签约之后，这个角色负责的是什么——收入、方案，还是运行中的系统？ 收入属于销售。方案属于架构。运行中的系统属于 FDE 的工作。

可用的措辞：一个示例回答

这个故事是为了展示结构而虚构的，包括第 1 步中的副业项目。请讲述你自己的经历。

“作为一家数据集成厂商的解决方案架构师，我为一家物流客户规划了工单同步方案并构建了概念验证。他们的团队将其推向生产环境，一个月后他们的仪表盘出现了工单重复计数：当厂商的 API 在运行中途失败时，任务从第一页重新开始，把所有数据又插入了一遍。我能看出原因，但修复不归我发布。于是我自己构建了生产版本：一个从分页 API 到 Postgres 的同步程序，每抓取一页就保存游标，按工单 id 进行 upsert 以确保重放不会产生任何变化，并在遇到速率限制时退避。从春天开始我每晚运行它。它只呼叫过我一次，当时厂商把一个字段从字符串改成了列表，于是我加了一个检查，把坏行隔离出来而不是让整个运行失败。这就是我作为 FDE 想负责的部分：不是架构图，而是那个会在深夜呼叫你的系统。”

如果他们问“你会做出什么不同的做法？”：“我会先构建对账机制，每晚对源端行数和目标端行数进行核对。客户的重复计数在他们的数据里存在了好几天才被发现，而行数检查在第一晚就能发现它。现在这是我写的第一样东西。”
