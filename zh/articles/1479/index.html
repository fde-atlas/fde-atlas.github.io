摘要

你的 AI Agent 是否还停留在永远无法上线的演示阶段？

为你的 AI 开发原型是容易的部分。但把它真正投入企业使用，才是让大多数项目栽跟头的地方。

问题出在哪里？

将 AI Agent 从模拟环境迁移到真实环境，需要处理遗留数据、安全限制和低效的流程。

根据 Gartner 的报告，到 2027 年，超过 40% 的 AI Agent 项目甚至在上線之前就会被放弃。

这通常是由于实施问题。不过，一份清晰的前沿部署工程计划可以规避这些问题——下面介绍 FDE 如何部署 AI Agent……

前沿部署工程是一种模式，由顶尖软件工程师驻场在客户的系统内部，解决棘手的技术问题。Palantir 在二十年前建立了这种方法，用于处理国防和情报机构的机密本地数据工作。

如今，OpenAI、Anthropic 和 Databricks 等公司使用同样的模式，将 AI Agent 部署到实际业务系统中。

FDE 不在供应商的办公室里工作。这些开发者在你的业务现场工作，了解你的软件技术栈，并编写与你的数据交互的代码。

前沿部署工程师身兼数职，既是程序员、架构师，又是业务顾问。FDE 不是安装现成的软件，而是重新设计流程、构建安全的数据管道，并编写让 AI 模型与真实世界集成的代码。‍

FDE 负责整个上线周期，他们的日常工作包括：

  • 流程梳理： FDE 会梳理你的公司内部实际的工作方式，而不是流程文档上写的那种“应该”的工作方式。
  • 动手工程： 这些开发者构建将 Agent 从演示推向实际使用所需的数据链路、安全层和测试框架。
  • 直接反馈传递： FDE 将来自一线的失败信号直接反馈给核心产品团队，以便快速修复。
  • 团队协调： FDE 弥合技术团队、法务部门和业务领导之间的鸿沟，确保上线按计划推进。

AI Agent 功能强大。但可用的演示与实际系统之间的差距，正是大多数企业损失时间、金钱和信任的地方。

演示只能证明模型可以完成某项任务。它能在安全的测试环境中读取文件并给出不错的答案。但真实的业务需要更多。它需要一个能在实际系统中读取、思考、规划并做出真实改变的 AI。

当你让一个 AI Agent 更新 Salesforce 记录、查询受严格管控的数据库，或总结一次私人客户通话时，项目就脱离了 AI 世界，直接撞上企业 IT 的硬性规则。

虽然 79% 的企业在测试 AI Agent，但只有 11% 能将其投入全面实际使用。问题不在于智能，而在于系统如何连接。OWASP 针对AI Agent 的十大风险清单清楚地说明了这一点：一个没有限制的 Agent 容易遭受目标劫持、提示词攻击和不受控的自由访问。

FDE 部署 AI Agent 并消除这一差距的方式，是在工程与业务的交汇处工作。他们带来了普通实施团队无法比拟的明显优势：

  • 直接嵌入： FDE 从第一天起就在你的现场工作。他们在第一周内就能将可运行的演示交付到你的真实系统中，省去数月的规划。
  • 全栈编码深度： FDE 不是只会调整现成工具的实施人员。他们是真正的程序员，能编写 Python、SQL 以及在压力下依然可靠的复杂 AI 工作流逻辑。
  • 处理混乱数据的能力： FDE 不会等待干净整洁的数据。他们深入老旧数据库，构建数据管道，并绘制 Agent 正常思考所需的数据映射。
  • 直接的产品反馈： 当 FDE 在现场遇到 bug 时，他们会将信号直接反馈给核心团队。这就是 FDE 部署 AI Agent 更快、修复更及时的原因，而不是依赖模糊的远期计划。

企业往往基于炒作而非真实需求启动 AI 项目。这导致“Agent 洗白”——把基础脚本包装成 AI Agent 出售。前沿部署工程师避免这种情况的关键步骤包括：

  • 审计工作的实际完成方式： 梳理任务实际发生的、隐藏的真实路径。使用流程挖掘工具找出真实的工作流，而不是旧手册里写的那种。
  • 检查数据健康状况： 确保 Agent 所需的数据易于访问、干净且新鲜。建立在陈旧或损坏数据之上的 Agent，上线那一刻就会失败。
  • 标记法律风险： 尽早识别适用的法规和法律。医疗或金融领域的工作流，其限制比物流或零售领域严格得多。
  • 按影响力选择： 选择高频、重复性强且跨越多个系统的工作流。这些正是 AI 能带来最明显价值的任务。
  • 设定基线指标： 在构建之前，先衡量人类目前如何完成这项任务。为节省的时间、减少的错误和单任务成本设定明确目标。

将原始语言模型直接接入企业数据库，结果并不可靠。你的前沿部署工程师必须为模型设置控制框架，限制其行为范围，并明确何时需要人工介入。关键步骤包括：

  • 选择 Agent 设计模式： 采用 Andrew Ng 等 AI 领袖提出的模式，包括反思（Reflection）、工具使用（Tool Use）、规划（Planning）和多 Agent 协作（Multi-Agent Teamwork）。
  • 设置安全闸门： 明确划定机器停止、人工接管的界限。高风险操作必须始终需要人工批准。
  • 选择工作流引擎： 使用 LangGraph、CrewAI 或 AutoGen 等工具来管理 Agent 的选择。一个好的状态机能让 Agent 保持正轨，避免陷入失控循环。
  • 不要过度构建： 简单规则就能处理的任务，不要用复杂的 AI 推理。过度思考会增加成本并产生不必要的错误。
  • 衡量效率： 跟踪 Agent 消耗的 token 数量与其成功率。一个好的 Agent 能完成任务，而不会在多余步骤上浪费算力。

AI 模型基于其训练数据被冻结在某个时间点。要理解你的业务，它需要访问实时的、组织良好的数据。

在这一步，你的 FDE 或前沿部署工程师会构建模型与你的真实数据源之间的连接。

  • 构建知识图谱： 超越基础的向量搜索。构建一张数据地图，追踪业务中各事物之间的关联。Agent 必须从一个真实、实时的唯一事实来源获取信息。
  • 保持数据新鲜： 建立让 Agent 数据保持最新的流水线。过时的数据会导致 Agent 以十足的信心执行错误的操作。确保每个数据点都能追溯到其来源。
  • 超越基础 RAG： 标准的检索增强生成（RAG）在实际使用中常常失效。简单的向量搜索无法理解复杂的业务关联。在没有正确附加信息的情况下拉取一份通用政策文档，会导致错误的操作。
  • 使用 GraphRAG： 基于图谱的检索知道数据对象之间如何相互关联。这能减少错误答案，并提升复杂多步推理任务的准确性。

让 Agent 成为 Agent 的是它的行动能力。但对于前沿部署工程师来说，为每个模型与每个旧系统之间构建定制的 API 连接，会造成无法扩展的混乱。

  • 安全地开放内部系统： 建立让 Agent 能够与你的 ERP、CRM 和 ITSM 工具通信的连接。每个连接都必须校验输入并妥善处理错误。
  • 为错误编写代码： 如果 Agent 无法读取 API 响应，它必须安全地失败。一个在超时后伪造成功的 Agent 会造成无声的数据损坏。
  • 设置模型上下文协议（MCP）： Anthropic 的 MCP 是一个开源的 JSON-RPC 框架，用于将 AI Agent 连接到业务工具。它为 AI Agent 提供了一种统一的方式来发现工具、读取数据和执行操作，而无需为每个供应商编写定制代码。‍
  • 解决 N×M 问题： 没有共享标准时，将每个 AI 模型连接到每个系统会形成一张由定制代码构成的乱网。MCP 通过为 AI Agent 提供一种安全的方式即时连接任何系统来解决这一问题。

赋予软件自主行动的能力会带来真实的安全风险。一个容易受到提示词攻击的 Agent 可能被骗去窃取数据、篡改记录或滥用其访问权限。FDE 会基于 OWASP AI Agent 十大风险构建分层防御方案。

  • 控制 Agent 可访问的范围： 将每个 Agent 的访问权限锁定到最低限度。映射行级安全，使 Agent 获得与调用它的用户完全相同的权限。明确划分读取与写入的界限。使用每次会话后即过期的短期访问令牌。
  • 添加防护机制与人工审批： 为高风险操作建立必需的人工检查点。资金转移、数据变更和对外发送的消息在执行前都需要人工批准。添加针对提示词攻击的防御措施，并对每次工具调用进行严格检查。
  • 满足安全与合规要求： 建立持久的审计日志，追踪 Agent 做出的每一个决策。与 Azure Active Directory 和 CyberArk 等身份管理工具集成。确保系统遵循您所在地区和行业的数据法规。

常规软件测试是固定的。相同的输入总是产生相同的输出。AI Agent 则不是这样。

Agent 可能通过错误的工具得到正确答案。FDE 必须测试 Agent 的行为方式，而不仅仅是它的输出。关键步骤包括：

  • 测试输出： 检查每个最终答案是否正确并符合要求的格式。运行脚本，将结果与已知正确答案进行比对。
  • 测试路径： 检查 Agent 是否以正确的顺序选择了正确的工具。通过被封锁的 API 得到的正确答案是安全失败，而不是成功。
  • 测试业务结果： 确认完整的业务成果端到端地实现。一个出现得太晚、错过截止期限的完美数字毫无价值。
  • 衡量重复成功率： 让 Agent 多次执行同一任务。Pass^k 指标可以显示多次尝试中的成功概率，并捕捉隐蔽的随机失败。

将 AI Agent 从程序员的笔记本电脑迁移到实际业务系统，需要处理 IT 规则、安全审查和网络配置。前沿部署工程师在此环节的关键步骤包括：

  • 打包 Agent： 使用 Docker 封装 Agent 并在 Kubernetes 上运行。这确保它在开发、测试和生产环境中以相同方式运行。
  • 保护密钥： 通过密钥管理器提供 API 密钥。切勿将私密信息硬编码到 Agent 的代码或配置文件中。
  • 搭建 CI/CD 流水线： 自动化构建、测试和部署流程。确保经过测试的更新快速、安全地到达生产系统。
  • 锁定模型版本： 在生产系统中固定确切的模型版本。当 LLM 提供商推送更新时，确保它不会破坏您的提示词或工具配置。

在实际使用中，AI Agent 会遇到测试从未覆盖的数据模式和边缘情况。

如果没有合适的追踪手段，工作流深处的故障会表现为一个模糊的超时错误，根本原因始终被掩盖。

  • 捕获追踪信息： 使用 OpenTelemetry 记录每一步操作、模型调用、数据拉取和工具动作。这为您提供 Agent 做了什么以及为什么这样做的完整记录。
  • 警惕漂移： 跟踪 AI Agent 的回答是否随着数据变化而随时间改变。尽早发现漂移，可以在用户察觉之前阻止质量下滑。
  • 将失败反馈给团队： 把线上错误转化为更好的提示词和更严格的工具规则。AI Agent 在实际使用中遇到的每一次失败，都是改进的机会。
  • 让人类标记问题： 建立让员工实时标记错误输出的机制。收集这些修正，并反馈到测试流程中，防止同样的错误再次出现。

每个新的 AI Agent 都从零开始构建，会造成技术债务和知识孤岛。规模化需要共享组件和复用。关键步骤包括：

  • 提取可复用组件： 从首次部署中找出数据配置、安全规则和工具连接，将其打包为现成的模板，供未来的 AI Agent 使用。
  • 建立共享工具目录： 创建一个集中管理 MCP 服务器和 API 连接的清单。新的 AI Agent 可以复用现有资源，而不是从零开始构建。
  • 跟踪部署速度： 衡量每个新 AI Agent 上线所需的时间。目标是每次都有明显提升。第二个 AI Agent 的上线时间应该只是第一个的一小部分。
  • 交接给内部团队： FDE 编写操作手册，并将可运行的系统交给贵方自己的工程团队。目标是让贵方组织能够独立运营，而不是永远依赖外部帮助。

FDE 部署 AI Agent 和上线推广的真实情况，体现在那些区分成功项目与代价高昂的失败项目的数据之中。

FDE 使用这些基准来设定目标、推动提升并向领导层证明价值：

  • 实际使用成功率： 虽然 79% 的企业在测试 AI Agent，但只有 11% 实现了全面实际使用。FDE 专注于跨越这一鸿沟。
  • 财务回报率： 89% 的金融公司表示，已部署的 AI 提升了收入或降低了成本。摩根士丹利的 AI Agent 在 16,000 名顾问中的使用率达到 98%，每次客户会议可节省约 30 分钟。
  • 运营影响： Klarna 的 AI Agent 完成了相当于 700 名人工客服的工作，目标是实现 4000 万美元的利润增长。坦帕总医院使用 Palantir AIP 将 ICU 住院时间缩短了 7.5%，每年节省 2700 万美元。
  • 高难度任务准确率： 在 Terminal-Bench 2.0 上，顶级模型在简单任务上得分 65%，但在复杂的多步骤工作上降至 16%。这正是 FDE 构建的测试体系对实际使用如此重要的原因。
  • 行动工具增长： 能够执行操作而不仅仅是读取数据的 AI 工具占比，在 16 个月内从 24% 上升到 65%。这一转变使得强大的安全设计比以往任何时候都更加关键。

FDE 这一角色要求非常高。它需要业内所说的“工程师加外交官”——一个既能上午调优 RAG 流水线，又能在午餐后向医院 CIO 捍卫安全方案的人。

  • 动手编码能力： 精通 Python、SQL，以及构建能够经受变更和迁移考验的端到端 ML 和数据流水线。
  • Agent 设计与 LLMOps： 深入了解 LangChain、LangGraph 和 DSPy 等工作流引擎。具备构建规划、反思和多 Agent 协作模式的能力。
  • 模型上下文协议（MCP）： 能够构建和运行 MCP 服务器，将旧有 API 和数据库转化为可供 AI 使用的 JSON-RPC 资源。
  • 系统集成与安全： 熟悉行级安全、PII 脱敏、短时效访问令牌，以及在受限网络中管理访问权限。
  • 追踪与 DevOps： 配置 OpenTelemetry 追踪、通过 Docker 和 Kubernetes 打包系统，以及运行 CI/CD 流水线。
  • 流程拆解： 运用 MECE 或金字塔原理等结构化方法，将模糊的高管目标拆解为具体、可执行的工程任务。
  • 干系人管理： 应对复杂的办公室政治，主持作战室会议，并让法务、IT 和业务团队达成共识。
  • 变革管理： 负责转型中“人”的一面。通过设计体验，让员工理解 AI 的局限性、信任其输出，并充满信心地采用新工作流程。

对于将 AI Agent 规模化落地到实际使用的前沿部署工程团队，这份由 FDE 驱动的清单可帮助您避免最常见的从演示到上线阶段的失败：

  • 选定的业务工作流具有清晰、可衡量的基线和目标成果。
  • 业务数据易于访问、映射清晰，且法律风险已经过审查。
  • Agent 可自主执行的确切范围已形成书面文档。人类保留最终决定权。
  • 业务上下文通过知识图谱、GraphRAG 或统一数据地图进行关联。
  • 工具通过 MCP 等标准路径接入。读写权限边界清晰。
  • 已实施严格的最低访问权限规则。Agent 获得的权限与人类用户相同。
  • 提示词攻击防御和工具输入校验可拦截恶意请求。
  • 高风险操作在执行前需要人工批准。
  • 使用 pass^k 指标对 Agent 在输出质量、工具调用路径和恢复率方面进行测试。
  • 审计日志不可篡改。系统遵循您所在地区的数据法规。
  • CI/CD 流水线已上线，并配置了速率限制、密钥处理和模型备份方案。
  • 每个步骤均启用追踪，记录 Token 消耗、响应速度和工具错误。
  • 人工修正和边缘案例失败会反馈到提示词调优和工具更新中。
  • 成功以节省的时间、减少的错误或明确的 ROI 来衡量——而不仅仅是模型分数。
