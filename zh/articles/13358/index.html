我在交接前如何评估 Agent 质量

原标题：How I evaluate agent quality before handoff

Anil Pervaiz — AI Agents & Automation Engineer · 2026-08-26 · 约 7 分钟读完

摘要

作者提出一套 FDE 在交接 AI Agent 前的评测方法：用冒烟测试验证环境与权限，用 15–40 个真实客户任务构成黄金集，按行为评分而非精确匹配；再分别检验检索引用、工具调用与 schema、护栏（越权、PII、注入、超支）等，并安排对抗测试与影子运行。上线以记分卡为门槛，任何 P0 红项即不交接，同时需交付黄金集、运行手册与负责人。

要点

  • 黄金集应取自真实工单与运营痛点，含升级路径。
  • 检索、工具调用、护栏需分层独立探测。
  • 对抗测试须由非构建者执行并记录所有失败。
  • 记分卡任一 P0 红项即禁止交接上线。
  • 交接需附黄金集、运行手册、kill switch 与负责人。

一份在交接前评估 AI Agent 的实用 FDE 手册——冒烟测试、黄金集、检索检查、工具调用验证、护栏，以及一份不是靠演示日“感觉良好”的上线评分卡。

*如果你不能故意让 Agent 失败，你就还没准备好把它交给运营人员。*

上线一个 AI Agent 很容易造假：一个顺利路径的演示、创始人点头、周五部署。交接意味着更严格的标准。运营人员能够运行它，故障清晰可见，并且质量是在*他们的*数据上衡量的——而不是你笔记本上的测试数据。这就是前沿部署工程中“加固并交接”的那一半。这篇文章就是我在宣布一个 Agent 完工之前真正使用的评测手册。

关于日常工作循环，请参阅 FDE 实际做什么。关于为什么演示会撒谎，请参阅 没人演示的那 80%。

简要版本

在交接之前，我会运行分层评估：验证技术栈能启动、工具能通过认证的冒烟测试；一组包含真实客户任务和预期行为的小型黄金集；涉及 RAG 时的检索与引用检查；Agent 操作系统时的工具调用与模式验证；针对政策、PII、支出和升级的护栏测试；以及一个带日志记录的短暂影子或分阶段上线窗口。上线靠的是评分卡，而不是感觉。如果关键项是红色的，我们就不交接。

生产环境中质量意味着什么

维度运营人员关心的问题
任务成功率它是否完成了企业付费要做的任务？
忠实度它是否严格依据检索到的或允许的来源？
安全与政策该拒绝或升级时它是否照做了？
工具正确性它是否用有效参数调用了正确的工具？
故障下的用户体验检索为空、超时、部分工具不可用——用户会看到什么？
可运维性没有我，别人能否通过日志调试一个错误答案？
成本与延迟在预期流量下，它是否稳定地控制在预算之内？

基准测试是可选的。客户任务不是。

评测阶梯

不要一上来就搭建 500 个用例的测试框架。逐级攀登：

1. Smoke          →  does it run?
2. Golden set     →  does it do the jobs we sold?
3. Slice probes   →  retrieval, tools, guardrails in isolation
4. Adversarial    →  can we break it on purpose?
5. Shadow / stage →  real traffic, limited blast radius
6. Handoff gate   →  scorecard + owners + runbook

当关卡变绿时就停止攀登，而不是当演示感觉良好时。

1. 冒烟测试

通过标准：应用能在预发布环境启动，模型密钥和工具凭据对非管理员测试用户有效，一条读取路径和一条写入路径能返回结构化的成功或错误，且日志中能端到端地看到请求 ID。

失败标准：只有用创始人的管理员令牌才能运行——身份是第一个 80%。

2. 黄金集

从客户的真实世界中构建 15 到 40 个真实任务。不是人造的琐碎问题。每个用例包含输入、关于哪些文档或系统应该起作用的上下文说明、预期的行为（而非精确字符串），以及严重级别：P0 阻塞、P1 应修复、P2 可选。

对于语言输出，行为评分标准胜过精确匹配：

标签含义
pass达成目标，未违反政策
soft_fail可用但缺少引用、语气不当或步骤不完整
hard_fail操作错误、关键事实出现幻觉、违反政策、工具调用错误
escalate正确拒绝或转交给人工处理

案例来源应包括真实工单、销售常见问题、运营人员的“我们总是搞错”清单、帮助中心热门文章以及已知的边缘账户。

这就是支持类 Agent 赢得信任的方式。SupportPilot 不是“聊天能用”就行——而是在文档允许时自动解决，不允许时升级，并为人工做好摘要。黄金案例必须同时涵盖这两条路径。

3. 检索与引用探测

如果 Agent 需要基于文档回答，就要把检索能力与表达能力分开评估。用有唯一明确来源页面的已知答案问题进行探测。提出语料库中不存在的问题——它绝不能凭空编造。输入相互冲突的文档，检查它是否会在不知不觉中将它们混为一谈。把一份过时文档排在靠前的位置，看看它能否被发现。

通过信号：正确来源在 top-k 中出现的频率足以满足使用场景，关键论断都有来源支撑，并且在检索为空时 Agent 会说“我不知道”或进行升级。

DotChat 优化的是论断引用到具体页面。你的评测应该像用户一样惩罚那些没有依据却流畅的回答。

无需研究团队即可计算的指标：黄金集上 top-k 的检索命中率、事实性回答的引用覆盖率，以及对二十条回答进行人工忠实度抽查。

4. 工具调用与模式校验

需要写入 CMS、CRM 或支付系统的 Agent 需要工具评测，而不仅仅是聊天评测。探测有效参数是否成功执行、无效参数是否在类型、必填字段和枚举上被明确拒绝、危险操作是否被阻止或需要审批，以及部分失败是否绝不会留下静默的半写入状态。

这正是 webflow-agent-kit 背后的理念：在边界处使用 Zod，让模型无法在结构化系统上自由发挥。

如果错误的工具载荷在到达 API 之前就被拦截，而正确的载荷足够确定、可以从日志中重放，即为通过。

5. 护栏测试

编写必须默认失败的案例：

护栏失败条件示例
授权用户访问了另一个租户的文档
PII 与敏感数据Agent 应拒绝或脱敏，但没有这样做
领域越界即兴提供临床或法律建议，而不是升级处理
支出超限购买未被阻止并记录
提示词注入检索到的文档中的“忽略你的指令”被服从

Mindoor 和 AgentPayOps 是护栏类产品：策略与审计是核心功能，而非脚注。你的评测集应将“应当拒绝”作为一等案例——许多团队只测试“应当回答”。

6. 对抗性一小时

与非构建者的人预留六十到九十分钟。错别字、混合语言、空输入。文档中的提示注入。超出策略的请求。工具滥用和重复写入。超长上下文。

记录一切。每一个严重失败都要变成一个修复、一条护栏，或一条写进交接文档的已接受限制。

7. 影子或分阶段上线

在完全交接之前，用真实语料副本进行预发布环境测试，或通过功能开关让有限用户使用生产环境，或采用影子模式记录 Agent *将会*执行的操作。

关注错误率、升级率、单任务成本、主要失败集群和操作员投诉。如果你说不出第一周由谁负责监控这些指标，那你就不是在交接——而是在甩手不管。

上线记分卡

关卡P0 标准
冒烟测试非管理员用户路径可用；密钥不出现在客户端
黄金集P0 用例达到约定的通过率
事实依据必须有依据的 P0 事实零 hard_fail
升级所有应升级的用例均升级
工具无效工具调用被拒绝；P0 流程无静默部分写入
护栏所有 P0 策略用例均失败即关闭
可观测性日志中包含请求 ID、工具追踪、模型和检索摘要
运行手册一页纸：常见故障、负责人、终止开关
安全形态有数据流和保留期限的答案
成本上限黄金集上的实测成本和延迟在预算内

规则： 任何 P0 红灯都意味着不能交接。协商缩减范围或修复问题。“在生产环境里监控”不能替代关卡。

多少评测才算足够

参与类型最低要求
一周试点冒烟测试、15 个黄金用例、5 个对抗用例、在真实数据上分阶段演示
生产支持 Agent30 个以上含升级路径的黄金用例、检索探针、一周影子运行
会写入或花钱的 Agent以上全部，外加工具模式测试、一套策略测试套件和审计日志审查

完美的评测并不存在。有据可查、可复现的关卡才存在。

我交出钥匙时附带什么

带用例和标签的黄金集文件。最新的记分卡快照。明确说明的已知限制。一份运行手册和终止开关。日志访问说明。以及语料更新和提示词修改的负责人是谁。

如果这六项缺一，那 Agent 就还在我的笔记本电脑上，即使它已经部署了。

反模式

把“CEO 喜欢这个演示”当作验收标准。只做精确字符串匹配，既脆弱又容易被钻空子。只测试英文的正常路径。没有应拒绝的用例。只在生产环境从未用过的固定 PDF 上评测。一次改动巨大的提示词却不重跑黄金集。交接时没有运营负责人。

交接一个 Agent 需要完整的评测平台吗？

不需要。一个电子表格黄金集、一个运行用例的脚本、日志和一份记分卡就足以起步。平台以后再上；关卡现在就要有。

Agent 交接评测的合理通过率是多少？

按每次合作单独约定。对于较小的 P0 任务集，常见做法是：关键的真实任务设高门槛，政策类和需升级类任务要求 100% 通过。软性失败可以排期修复；P0 上的硬性失败会阻止交接。

AI Agent 交接评估与模型基准测试有何不同？

基准测试是在抽象层面比较模型。交接评测衡量的则是你的 AI Agent、你的工具、你的数据和你的政策，在业务关心的任务上的表现。

评估在前沿部署工程师的工作循环中处于什么位置？

在薄切片之后、加固阶段进行，交接之前。先确定范围、梳理技术栈、切片、用评测进行加固、交接，然后把模式反馈到产品或开源工具中。参见 FDE 中心。
