你的 FDE 百天成长路线图

原标题：your 100-day roadmap to becoming an FDE

Somewhat Artificial · 2026-10-13 · 约 12 分钟读完

摘要

作者以 OpenAI 认证 FDE 的身份，给出一份 100 天学习路线图，通过完整构建一个带引用来源、需人工审核的支持助手项目，学习从需求界定、软件开发、模型集成、上下文工程、评测到部署试点的全流程。文章强调评测应从第一天开始，并提醒该计划不保证就业。

要点

  • 以一个支持助手项目贯穿 100 天学习。
  • 六个阶段：界定、编码、AI 基础、上下文、评测、部署。
  • 评测从第一天开始，而非项目后期。
  • 检索与模型使用需分开测试，引用须可溯源。
  • 作者声明该计划非官方课程，不保证就业。

前沿部署工程师到底是干什么的？

你和客户坐在一起，弄清楚真正的问题，围绕他们团队现有的工作方式构建软件，并在测试和上线过程中持续参与。

本指南讲的是如何为 AI 应用做这项工作。我是一名 OpenAI 认证的 FDE，这是我建议你执行的 100 天计划。

一个项目，从头做到尾。

项目内容： 构建一个支持助手，它能提取已批准的政策、起草带来源的回复，并交给人工审核。

先说实话：这个进度假设你已经掌握基础编程，并且能持续投入。如果你是编程新手，请先打好基础，再拉长时间线。这是我的建议计划，不是官方认证课程，也不保证 100 天内找到工作。

100 天计划一览

时间重点完成内容
第 1–10 天需求界定一份问题简报和一个基线
第 11–30 天编程一个带 API 和数据库的应用
第 31–45 天AI 基础一个经过测试的模型集成
第 46–60 天上下文工程带引用来源的政策检索
第 61–80 天评测一套可重复的评测套件
第 81–100 天部署一个试点和一份作品集案例

评测从第一天开始。 在界定项目的当下，就写下真实任务以及良好表现的标准。第 61–80 天是用来扩展和自动化这些测试的，而不是第一次给应用做测试。

第 1–10 天 · 界定问题

学习： 客户调研、工作流梳理、需求、边界和成功指标。练好提问：现在是怎么做的、谁负责这项任务、哪里会出问题、有用的结果是什么样的。

实践：

  • 如果可以，和三位潜在用户聊聊
  • 完整观察一项任务从头到尾的执行过程
  • 为支持助手选定一个狭窄的类别，比如政策类问题
  • 收集允许使用的示例，并测量当前的处理时间或错误率

然后写一份一页纸的简报：

  • 用户及其问题
  • 当前的步骤
  • 你拥有的数据
  • 你的第一个功能
  • 你刻意排除的内容
  • 人工审核环节在哪里
  • 你将如何衡量成功

并决定谁有权批准试点。

检查点： 用户能读懂你的简报，并就你要构建什么、他们将如何评判达成一致。在你选定模型之前，就已经有了第一批测试用例。

学习资源，按此顺序

  • NN/g：Discovery · 文章，面向初学者，聚焦问题界定、用户需求、约束条件、利益相关者对齐和期望成果。应用它： 写一份简报，写明用户、他们的问题、当前流程和一个可衡量的成果。列出你还需要学习的内容。
  • NN/g：撰写有效的访谈指南 · 文章，初级，重点是如何组织访谈、选择问题并挖掘真实经历。应用方法： 准备一些关于最近一次支持请求的问题。请用户带你走一遍事情的经过、他们使用了哪些工具，以及在哪里卡住了。
  • NN/g：旅程图 101 · 文章，初级，重点是参与者、场景、阶段、行动、痛点和机会。应用方法： 把一个请求从到达一直画到解决。标出交接环节、延迟和缺失的信息，然后选出你的第一个版本要解决的那部分。

最终产出： 一页纸简报、当前工作流程图、访谈笔记、一个基线，以及一份初始评测用例清单。你的用户应该能在这些文档中认出他们实际遇到的问题。

第 11–30 天 · 构建软件

学习： Python 函数、数据结构、异常和测试。SQL 表、连接和更新。HTTP、JSON 和 API。Git 提交和分支。学会阅读堆栈跟踪并复现 bug。

构建： 一个应用，接收支持请求、保存到数据库，并允许审核人员更改其状态。界面保持简单。添加输入验证，并为数据库操作和 API 错误编写测试。

正确使用 AI 编程工具： 请求小改动、阅读 diff、运行测试，并向自己解释代码。不要把 API 密钥放进你的仓库。当生成的代码出问题时，你需要能够调试这个应用。

检查点： 别人能按照你的 README 操作，运行应用、提交一个请求并看到它被正确存储。你能在代码中追踪一次失败的全过程。

学习资源

  • 哈佛 CS50：Python · 课程 + 练习，初级，重点是函数、数据结构、异常、库、文件 I/O 和单元测试。应用方法： 构建一个脚本，加载支持请求、验证字段并处理格式错误的输入。在接入模型之前先写好测试。
  • 哈佛 CS50：SQL · 课程 + 练习，初级，重点是查询、关系、表设计、约束和写入数据。应用方法： 创建 requests 和 reviewers 表。保存新请求、更新其状态，并连接两张表以显示每个请求由谁审核。
  • FastAPI 教程 · 官方教程，需要基础 Python，重点是请求体、验证、响应模型、错误处理、安全和测试。应用方法： 提供提交和审核请求的端点。对缺失字段返回有用的错误信息，并在不调用模型的情况下测试 API。
  • Pro Git · 在线书籍，全程使用，重点是入门、Git 基础和 Git 分支。应用方法： 提交一个可用的基线，在分支上做一次修改，查看 diff，并练习撤销一次错误的修改。

有选择地学习。如果你是初学者，放慢速度并完成练习。如果你已经会编程，就在构建过程中遇到缺口时再补。你不需要在 20 天内学完两门完整课程。

第 31–45 天 · 加入 AI

学习：模型 API 调用、指令、token、上下文窗口、输出限制、结构化输出和工具调用。真正要弄懂两件事：合法的 JSON 不等于正确的答案，以及提议的工具调用在执行前需要经过验证。

构建：将每个请求分类到一组固定的类别中，并返回结构化结果。添加一个只读的政策查询函数。在应用程序代码中验证工具参数并执行权限控制。起草回复供人工审核，并确保实际发送环节不受模型控制。

对比：在相同的示例上测试两种提示词或模型配置。记录错误、响应时间和成本。从单次模型调用或简单的工作流开始，只有当实测到的失败证明有必要时才增加步骤。

检查点：应用能够处理无效输出、失败的 API 调用和未知类别。你能解释为什么选择该配置。

学习资源

  • Full Stack LLM Bootcamp · 录播课程，需要基础编程能力，重点是 LLM 应用生命周期、提示词、增强模型和部署概念。注意，这是 2023 年的课程，模型、API 和定价请参考当前提供商的文档。学以致用：画出你的请求到响应的工作流，并标出哪些步骤真正需要模型。先构建最小可用版本。
  • OpenAI: Structured model outputs · 官方指南，需要基础 API 知识，重点是 schema、受约束的响应格式，以及处理输出失败或拒绝的情况。学以致用：以结构化数据返回请求类别和草稿。验证字段并测试内容是否正确，而不仅仅是能否解析。
  • OpenAI: Function calling · 官方指南，需要基础 API 知识，重点是工具定义、参数 schema、工具调用循环和返回工具结果。学以致用：添加只读政策查询功能。在运行前于你的应用中验证参数并执行访问权限控制。
  • Anthropic: Building effective agents · 工程文章，中级水平，作为你的架构检查。重点是工作流与 AI Agent 的对比、路由，以及何时额外的自主性才真正有用。学以致用：将你的工作流与 Agent 方案进行对比。写下能证明有必要增加步骤或更多自主性的具体失败场景。

第 46–60 天 · 为它提供有用的上下文

学习：如何为每个任务选择指令、对话历史、检索到的文档和工具结果。关于检索增强生成（RAG）：分块、嵌入、关键词搜索、排序和来源元数据。

构建：为一个小型已批准政策集合建立索引。检索相关章节及其来源 ID，并起草引用这些来源的回复。将检索范围限制在当前用户有权查看的文档。决定当政策相互冲突、已过时或根本无法回答问题时该如何处理。

单独测试检索： 对每个问题，标注应该返回哪份政策文档，并在评判最终答案之前检查它是否出现在结果中。将文档内的任何指令视为不可信内容。

检查点： 你可以确切看到模型收到了什么上下文，将任何论断追溯到其来源，并在文档不够用时获得有用的交接。

学习资源

  • Anthropic：有效的上下文工程 · 工程文章，部分聚焦 LLM 应用的经验，重点在于选择有用的上下文、工具输出、记忆以及长时任务的策略。应用方法： 记录为请求发送的确切指令、检索到的文本和历史记录。删掉无关内容，并在相同的评测用例上比较行为。
  • Anthropic：上下文检索 · 技术文章，需先理解基础 RAG，在此建立你的基线。重点关注分块上下文、嵌入、关键词检索和重排序。将其发布的结果视为其环境下的发现，而非对你能获得的承诺收益。应用方法： 编写已知来源文档的政策问题。将简单的检索基线与一个改动过的设置进行比较，并衡量正确的证据是否被检索回来。
  • Anthropic：为 Agent 编写有效的工具 · 工程文章，中级水平，重点在于工具命名、描述、有用的响应字段以及以评测驱动的迭代。应用方法： 为政策查询工具提供清晰的描述和带来源 ID 的紧凑结果。测试模糊查询和空搜索结果。

将两项检查分开： 检索是否找到了正确的证据，以及模型是否正确使用了它？再好的提示词也无法找回检索器从未找到的政策。

最终交付： 一个检索测试集、每个请求的上下文日志、回复中的来源引用，以及针对过时、缺失或冲突政策的成文行为规范。

第 61–80 天 · 让质量变得可测试

评测是一个可重复的任务加上一条评判结果的规则。把普通软件测试留给确定性代码。将评测用于模型回答、检索到的证据、工具选择以及完整工作流。

构建评测集： 从可管理的规模开始，比如 30–50 个多样化的示例，然后根据你的失败案例逐步扩充。使用合成数据或经授权的、去标识化的数据。保留一个从不用于调优提示词的留出集。那个起始数量只是项目练习，并不能证明你已达到生产就绪水平。

测试用例预期行为
正常的政策问题从正确的政策中回答并引用它
缺少订单细节询问缺失的细节，不要凭空编造
没有相关政策解释缺口并交接给人工处理
政策版本冲突使用已批准的当前版本或上报
其他客户的数据应用访问控制阻止检索
藏在文档中的指令将其视为数据，不要执行
查询超时报告或安全重试，绝不谎报成功

评估行为表现，而不是它听起来有多自信

跟踪任务成功率、无依据的断言、引用是否正确、交接是否正确、工具参数、权限失败、延迟和成本。用代码检查来验证模式和精确规则，用人工评审来评估回答质量。如果加入 AI 评分器，先将其判断结果与人工标注进行对比。

运行并对比： 使用 Promptfoo 或一个小型测试运行器。每次结果都保存模型、提示词和数据集版本。检查失败轨迹，每次只改一处，然后重跑。将关键安全失败与平均分分开记录。

交付物： 一份包含测试用例数量、各类别通过率、失败情况、延迟和成本的报告。与你的用户商定发布阈值，并在模型、提示词、检索或工具发生任何变更后重跑。

学习资源

  • OpenAI：评测最佳实践 · 官方指南，初级到中级。聚焦任务特定目标、有代表性的数据、评分标准和持续评测。重点关注评测设计，并在采用某个托管功能前查阅最新文档。应用方法： 将你的需求简报转化为评分细则。在对比不同配置之前，先定义什么是好答案、什么是正确交接、什么是关键失败。
  • Promptfoo：入门指南 · 动手实践文档，基础开发环境搭建。聚焦测试用例、断言、提供方和配置对比。应用方法： 用两个提示词版本运行相同的客服案例。保存每个用例的结果，检查性能回退，并在模型或检索变更后重跑。
  • Anthropic：揭开 AI Agent 评测的神秘面纱 · 工程文章，中级。在这里深入学习。聚焦任务、试验、评分器、对话记录和结果，以及为什么执行多个动作的 Agent 更难测试。应用方法： 端到端检查一次失败的运行。弄清失败究竟来自检索、工具选择、参数、环境还是最终答案。

实践循环： 收集一个失败案例 → 写出预期行为 → 添加一个用例 → 只改一处 → 重跑 → 复盘。保留一个留出测试集，并用人工判断来校验自动评分器。

最终交付： 带版本的测试数据、评分细则、分类别结果、延迟和成本数据、失败轨迹，以及简短的发布决策。即使平均分上升，也要让严重的权限或操作失败保持可见。

第 81–90 天 · 部署并运行试点

学习： 托管、环境变量、密钥、身份验证、授权、容器、日志和回滚。理解超时、重试和幂等性，确保重复请求不会触发重复操作。

部署： 打包应用，使用服务端凭证并添加基于角色的访问控制。记录足够的日志以便排查失败，同时不保留不需要的隐私数据。对模型使用设置限额。任何需要审批的操作都保留人工评审。

试点： 观察一小群愿意参与的用户完成原始任务。记录处理时间、纠正、失败和反馈。将其与需求简报中的基线进行比较，并询问应用在哪些地方增加了额外的工作。

检查点： 用户可以安全地访问试点，你可以调查失败的请求，并且在 AI 或其工具宕机时有备用方案。

学习资源

  • Docker：入门 · 官方教程，需要基础编程知识，重点关注镜像、容器、Dockerfile 以及可复现地运行应用。实践应用： 打包你的应用，并记录其他人如何运行它。确保凭据不进入镜像和代码仓库。
  • FastAPI：部署 · 官方指南，需要 Python 后端经验，重点关注 HTTPS、启动、重启、worker、内存和部署概念。实践应用： 部署一个带身份验证接口的小型试点。检查进程重启或上游 API 失败时会发生什么。
  • OWASP：LLM 应用 Top 10 · 安全参考，中级水平，用于你的安全审查。重点关注提示词注入、敏感信息泄露和过度代理，并阅读当前项目资料以了解详细风险。实践应用： 为策略中的恶意文本、跨用户数据访问和未授权操作添加测试用例。在应用代码中强制执行权限控制。
  • Google SRE 工作手册：监控 · 书籍章节，中级水平，重点关注有助于诊断行为和服务健康状况的指标和结构化日志。实践应用： 跟踪请求成功率、错误、延迟和成本。保留请求 ID，以便在不记录不必要隐私数据的情况下追踪报告的故障。

第 91–100 天 · 展示你的学习成果

构建你的作品集案例研究。展示问题、用户和原始工作流程。解释你的范围、架构、检索选择和审批节点。包含一个简短的演示、可分享的代码、安装说明、评测数据集（或安全样本）以及结果报告。

如实报告： 说明你的样本量和测试条件。将离线评测结果与真实试点结果分开。如果你还没有真实用户，请称之为原型，并描述下一步的验证步骤。

准备好谈论： 你为什么使用 AI、哪些地方普通代码就足够了、你最严重的失败、你如何调试它，以及如果有更多时间你会做出什么改变。练习向工程师和非技术客户讲解同一个项目。

使用这个案例研究结构

  • 问题： 谁需要帮助以及任务是如何运作的
  • 范围： 你构建了什么以及你刻意排除了什么
  • 设计： 主要组件以及你选择它们的原因
  • 证据： 评测用例、结果、测试条件和用户反馈
  • 局限性： 失败、未解决的风险和你的下一个实验

学习资源

  • GitHub：关于仓库 README 文件 · 官方指南，面向初学者，重点讲解项目是做什么的、为什么有用以及别人如何使用它。实践： 编写安装步骤、简短的演示路径、示例输入、环境要求和已知限制。请别人仅凭 README 运行项目。
  • Google：技术写作课程 · 自学课程，从初学者到中级，重点讲解受众、清晰的句子、一致的术语以及组织技术说明。从 Technical Writing One 开始。实践： 写一份客户能看懂的一页案例研究，把问题和观察到的结果放在实现细节之前。

第 100 天的终点线

一个你能讲清楚的可运行项目、一套评测、真实反馈的证据，以及一份清晰的案例研究。一个可运行的仓库、一个简短的演示、一份评测报告。如果你只跑了离线测试，请如实说明。

利用这些内容，对照实际的 FDE 职位描述找出自己的差距，并据此调整你的求职申请。

保持计划的灵活性。当你能展示出检查点成果时再进入下一阶段，而不是看完一节课就继续。
