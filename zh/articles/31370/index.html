Figma 的首个 FDE 团队：面向 Agent 的设计系统

原标题：Figma's first FDE team: agent-ready design systems

FDE Times · 2026-11-03 · 约 6 分钟读完

摘要

Figma 正在组建公司首个前沿部署工程师团队，职位设于产品与工程部门，明确不属于销售或服务。其核心任务是把企业设计系统改造为 Agent 可用的形态：借助 MCP server、Code Connect 和 Skills 等工具，为每位客户建立专属上下文，使 AI 生成的代码真正符合客户的设计系统。文章指出产品本身只是容器，组件映射与未成文的设计规范必须由资深工程师在客户现场完成，因此要求五年以上经验并常驻客户。作者建议求职者用开源设计系统练习构建 Agent 上下文，并用可量化的指标（组件复用、token 使用、variant 正确性）证明成果。

要点

  • Figma 首个 FDE 团队隶属产品与工程，明确区别于销售与服务。
  • 核心使命是让企业设计系统对 AI Agent 可用，使生成代码符合客户体系。
  • MCP server、Code Connect 与 Skills 只是容器，客户专属上下文无法随产品交付。
  • 职位要求资深工程师，因为错误的映射或 Agent 写权限可能破坏客户文件。
  • 求职练习建议：构建上下文并用组件、token、variant 三项指标量化效果。

招聘启事称，这一职位既不属于销售也不属于服务：MCP 服务器和 Code Connect 已经存在，但每个组织的上下文仍需构建。

简要概述

  • Figma 正在组建其首个 FDE 团队，招聘高级/资深级别人才，隶属于产品与工程部门，并与销售和服务部门完全分开。
  • 核心工作是让企业设计系统为 Agent 做好准备，使 AI 工具生成的代码符合客户自己的系统。
  • 要瞄准这类职位，请练习在真实代码库上构建 Agent 上下文，并用数字衡量结果。

在 Greenhouse 上发布的 FDE 职位中，Figma 直言不讳：这是产品与工程部门的一个高级/资深工程职位，既不是销售也不是服务。Figma 还表示，这是公司的首个 FDE 团队，一个创始团队。

一家设计工具公司组建一个与客户并肩工作的工程师团队，听起来可能有些奇怪。原因在于招聘启事中阐明的使命：让企业设计系统为 Agent 做好准备，使 AI 工具生成的代码符合该系统并忠实于设计。

这句话值得细细品读。它揭示了 AI 领域 FDE 工作的发展方向：客户需要的不再仅仅是 API 集成，而是专门为其组织构建的一层上下文。只有既懂代码又理解客户方人员的人才能构建这一层。

产品已经存在，那还缺什么？

看看 Figma 目前的工具集，基础设施已相当完备。根据其开发者文档，Figma MCP 服务器将 Figma 引入 AI 工作流。该服务器不只是读取设计数据：通过 MCP 客户端，Agent 还可以直接在 Figma 中创建和编辑内容。

接下来是 Code Connect，它是代码库与 Dev Mode 之间的桥梁。据 Figma 称，它通过复用客户的真实组件，使生成的代码与客户的代码库保持一致。文档还提到，Agent 在 Figma 中构建和编辑内容时，可以将设计系统作为唯一事实来源。

六月举办的 Config 2026 让公司向代码方向又迈进了一步。Code Layers 将代码呈现在画布上，按照 Figma 的描述，设计师现在可以直接在 Figma 中创建交互式代码。根据 Classmethod 的总结，Skills 功能让团队能够将自己的设计工作流和规范打包为可复用的 Agent 指令。

但所有这些工具都有一个共同的弱点：它们只是容器。Code Connect 自身并不知道客户代码库中的哪个

Button

组件对应画布上的哪个组件。

Skills 自身也不知道某家银行的设计团队何时使用 warning 变体而非 danger 变体。这些上下文存在于每个组织成员的头脑中，没有任何产品能将其打包交付。

“Agent 就绪”在实践中是什么样子？

想象一家公司拥有内部 React 组件库，以及一个包含“Button/Primary”组件的 Figma 文件。如果没有映射，Agent 通过 MCP 读取设计后，会生成一个裸的

<button>

标签，带有硬编码的十六进制颜色和以像素为单位的内边距。看起来没问题，但它完全没有用到设计系统。

而有了 Code Connect 映射，Agent 就知道要从客户的组件库中导入

<Button variant="primary">

。再加上一个记录了诸如“表单中的主按钮始终放在右侧，绝不能两个主按钮并排”这类约定的 Skill，生成的代码就不仅是正确的组件，还遵循了该组织实际使用它的方式。

从第一种状态过渡到第二种状态，正是 FDE 的工作。你需要阅读客户的代码仓库，与设计团队坐下来梳理出他们从未写下来的约定，编写映射和指令，然后在真实页面上测试结果。

下表将产品文档与招聘启事中的使命并列对照。右栏是对每一层工具在客户侧提出的要求的推断，并非 Figma 官方发布的清单。

产品层产品提供什么FDE 在客户处必须做什么
MCP 服务器从 MCP 客户端读取设计数据并写回画布将其接入客户使用的 AI 工具，并决定 Agent 可以写什么、写到哪里
Code Connect代码库与 Dev Mode 之间的桥梁将画布上的每个组件映射到客户代码仓库中的真实组件
Skills可复用 Agent 指令的容器梳理设计团队未成文的约定，并将其转化为指令

每个客户拿到的中间栏都一样；右栏则各不相同。正是这个不可复制的部分，使得产品公司必须聘请会到现场工作的工程师。

为什么必须是资深工程师？

招聘启事中的任职要求是：拥有五年以上端到端构建生产级软件的经验，并且有相当长一段时间与客户或合作团队嵌入式协作的经历。该职位还需要定期出差，与战略客户面对面合作。

从这个人需要做的决策类型来看，原因显而易见。如果错误地映射了一个共享组件，Agent 生成的每一个页面都会随之出错。

如果不给 Agent 对大公司画布的写权限设置边界，它可能毁掉整个团队的文件。这类选择需要的是亲自构建并运维过真实系统的人。

还有一个原因，藏在“产品与工程”这几个字里。第一个团队往往是产品学到最多的地方：每当 FDE 不得不一遍又一遍地编写同类映射或指令时，这就在向产品团队发出信号，指明下一步该自动化什么。

服务工程师只是把活干完；产品工程师则会把经验带回产品。

如果你的目标是这个职位，应该练习什么？

核心技能是为 Agent 构建关于现有系统的上下文，而不是编写巧妙的提示词。

最好的练习方式就是做一个小型的同类工作：选一个带 React 库的开源设计系统，映射几个组件，编写约定说明，然后让 Agent 构建同一个界面两次，一次带上下文，一次不带。

然后进行测量。在每次运行中，统计有多少界面元素使用了库中的组件，有多少是硬编码值的裸 HTML。

不要止步于统计组件数量，因为一个界面可能用了正确的组件却仍然破坏系统。还要检查颜色和间距是来自库的 token，还是仍然是十六进制色值和手动输入的像素值。

然后检查变体：Agent 构建的删除账户按钮使用了

variant="primary"

而不是 danger 变体，这种错误是组件统计无法发现的。

假设第一次运行只有 20 个元素中的 3 个满足全部三项标准，第二次有 20 个中的 17 个：简历或作品集上这样的数字，比任何关于“有 AI Agent 经验”的描述都更有说服力。

在阅读任何公司的 FDE 职位描述时，你可以把 Figma 的招聘启事作为参照标准。这个职位属于组织的哪个部门、什么级别、是否是创始团队、是否需要长期驻扎在客户现场？这些内容能告诉你，你将成为一线的产品工程师，还是变相的售后实施团队的一员。

第一个团队今天手工编写的映射和说明，未来很可能会被内置到产品中。现在加入的人将是决定什么值得自动化的人，这是一个值得争取的位置。
