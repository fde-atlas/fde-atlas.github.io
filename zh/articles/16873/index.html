摘要

这篇文章是 pathtofde.com“Get Hired”阶段的实战项目简报：虚构客户 Acme Corp（中型零售商）需要在六周内上线 Nimbus 平台。作者通过对比两位候选人的作品集，说明教程式项目无法证明 FDE 能力，而端到端的模拟交付可以。文章给出六周里程碑计划、交付物清单和评分标准，核心原则是“简报即工作，评分标准即合同”，按结果而非完成度打分。

要点

  • 对比两类作品集：五个教程项目败给一个端到端模拟交付项目。
  • 虚构客户 Acme Corp 提供十年混乱订单数据、老旧库存 API 和多方干系人。
  • 六周计划含发现笔记、数据契约、迁移管道、API 连接器、仪表盘与 SOP 助手。
  • 核心原则：按结果评分，先观察后决策，收入定义须书面确认。
  • 交付物包括对账报告、评测集、运行手册等可面试展示的工件。

Maya 担任前沿部署团队的招聘经理已有六年。她的办公桌上放着两份作品集。

候选人 A 列出了五个完成的教程项目：一个待办事项应用、一个天气仪表盘、一个基于示例数据集构建的聊天机器人演示、一个 Kaggle 笔记本，以及一个热门网站的克隆。每个仓库的 README 都写着“为了学习 X 而构建”。没有任何一个项目是以业务所需的方式完成的：没有数据契约，没有错误处理，没有运维手册，也没有任何人实际使用过它的证据。

候选人 B 只有一个项目：一份针对一家虚构零售商的为期六周的交付简报，并端到端地执行完毕。其中有一份需求探索备忘录。一份附带隔离策略的数据契约。一条迁移流水线，其对账报告证明数字完全对得上。一个针对棘手遗留 API 的连接器，包含身份验证、分页、重试和 Webhook 处理。一个实时仪表盘。一个基于客户 SOP 文档的 AI 助手——带有评测集和实测结果，而不是凭感觉。一份值班工程师凌晨两点也能照着执行的运维手册。

Maya 面试了候选人 B。这篇文章就是教你如何成为候选人 B。

项目简报是你在没有客户的情况下，能构建的最接近真实 FDE 交付的东西。这一份给了你完整的体验——混乱的数据、老旧的 API、各利益相关方、截止期限——外加它将被评分所依据的评分标准。简报就是工作；评分标准就是契约。

核心原则

“简报就是工作；评分标准就是契约。”在真实的交付中，客户对“完成”的定义是唯一重要的定义。在这里，评分标准扮演着这个角色：它评判的是成果——对账一致的数据、健壮的连接器、经过实测的 Copilot 质量——而不是努力程度，也不是“完成表演”。在写下一行代码之前先读评分标准，就像签合同之前先读合同一样。

为什么要有这份简报

第 6 阶段是“求职”阶段，它的通货是证据。前沿部署岗位的招聘经理买的不是证书；他们买的是一种预测——当客户的数据一团糟、他们的 API 处处作对、他们的高管要求周五看到演示时，你会如何表现。教程无法提供这种证据。而一份从零构建的交付简报可以——因为它迫使你做出与在职 FDE 相同的权衡：什么需要澄清，什么需要度量，什么需要加固，什么需要记录，以及什么需要拒绝。

本简报刻意采用全新构建的形式，而非引导式演练。你接触这个项目的方式与真实项目一样：信息不完整、利益相关者诉求冲突、硬性约束以及截止日期。你产出的将是一份读起来像一线实战成果的作品集——调研笔记、数据契约、对账报告、连接器、仪表盘、带评测的 Copilot，以及运维手册。每份成果都回答了招聘经理真正会问的一个问题：这个人能否在不破坏业务的前提下，把一个陷入困境的客户变成一个上线运行的系统？

以下所有内容都遵循两条规则。第一，评分看结果，而非完成度——这是课程里程碑评分卡的规则。一条能运行但会静默丢失 3% 订单的数据管道，还不如一份诚实的报告，后者会说“我们今天能迁移 97%，并且明确说明剩下 3% 需要什么”。第二，把你观察到的东西与你决定的东西分开：先对数据进行画像再清洗，先对 API 进行测量再信任，先对 Copilot 进行评测再演示。

如果你需要在开始前温习一下，可以参考这些有用的背景资料：调研：把“我们快撑不住了”变成问题陈述、范围界定与成功指标：你拒绝构建什么，以及在约束条件下设计系统。

1. 项目：Acme Corp

本节中的所有内容都是虚构且仅作说明之用——这是一个由常见模式拼合而成的复合项目，因此你无需真实客户即可执行。在工作时请把它当作真实项目：做出决策、记录下来，并准备好为它们辩护。

你是谁

你是一家软件公司的前沿部署工程师，该公司销售 Nimbus——一个虚构的业务运营平台：包含仪表盘、数据管道、集成和 AI 助手，且每个客户的数据均相互隔离。一位新客户已经签约。你就是被派去让他们上线运行的工程师。

客户是谁

Acme Corp（虚构）是一家中型零售商：拥有几十家门店和一个网上商店，经营了大约十年。他们的成功恰恰制造了混乱——增长速度超过了系统的承载能力。用销售代表的一句话来说，他们的需求是：“我们需要一个统一的业务视图，以及一个能根据我们的 SOP 文档回答问题的 AI 助手。”你在第一周的工作，就是把这句话转化为一个可以据此构建的问题陈述。

他们交给你什么

三份资产，每一份都是典型的 FDE 头疼问题：

  • 十年来的订单数据被困在 Excel 和 CSV 导出文件里。 不是数据库——而是导出文件，由不同的人手工生成，跨越十年。请做好应对现实中各种数据损坏的准备：日期格式不一致（03/04/2019、2019-04-03 和 Apr 3 19 混在一起）、重复的客户（"Acme Retail Ltd" vs "ACME RETAIL LTD." vs "acme-retail"）、相当比例的行缺少 SKU，还有不断变化的列名——同一个字段在不同年份、不同导出人手里被叫作 OrderID、order_id、Order No 和 id。有些文件是 UTF-8，有些不是。有些有 12 列，有些有 31 列。
  • 一个老旧库存系统，藏在摇摇欲坠的 REST API 后面。 它是库存水平的权威记录系统，短期内不会下线——Acme 的仓库全靠它运转。这个 API 有身份验证（一套老旧的 token 方案）、分页（页大小不一致，偶尔出现重复页）、未文档化的速率限制、间歇性的 500 错误，以及触发不可靠的 webhook 支持。文档只有一部分，你应该像对待陌生人的指路一样对待它：一切都要验证。背景阅读：遗留系统、SDK 设计与调试别人的 API、分页、速率限制与重试、实战中的身份验证、Webhooks。
  • 利益相关者需要两样东西上线：一个仪表盘和一个基于他们 SOP 文档的 AI 助手。 仪表盘必须基于你自己迁移和整合的数据，真实地反映业务——订单、收入、库存。助手必须根据他们的标准操作流程回答员工的问题：退货、退款、发货截止时间、折扣规则。它必须引用来源，并且绝不能编造政策。

目标与截止期限

在六周内让 Acme 在 Nimbus 上线，且不破坏他们的业务。 “上线”意味着：他们的订单历史已迁移并对账完成，库存数据从遗留 API 流入，一个 CFO 信任的仪表盘，一个员工能用的 SOP 助手，以及一份交接包，让他们的团队（或你离开后的你的团队）能够运维。“不破坏他们的业务”意味着遗留库存系统全程不受干扰地继续运行——你以只读方式集成，分阶段切换，并且可以回滚。

利益相关者笔记（示例性质）

以下笔记是虚构的示例——由利益相关者实际会说的话综合而成。请像阅读调研访谈笔记那样阅读它们：每一行背后都隐藏着一个需求、一个风险或一个陷阱。

Priya，运营负责人（虚构）：“在向客户承诺任何事之前，我只需要知道仓库里实际有什么。现在我要查三张电子表格，还要打电话给 Marcus。如果你的仪表盘哪怕错一次，我的团队就会回到电子表格，再也不回来了。”

Marcus，仓库经理（虚构）：“库存系统很旧，但能用。节日旺季期间谁都不许碰它——如果你的集成拖慢了它或锁住了表，责任在你。另外，webhook 有时会触发两次，有时根本不触发。”

Dana，CFO（虚构）：“董事会汇报材料每月第一个周一发出。你仪表盘上的收入数字必须和我们会计导出的数字分毫不差，否则我没法用。而且我需要知道哪些订单你没能迁移，以及原因。”

收入定义是一个需求发现决策

在收入被定义清楚之前，“分毫不差”毫无意义。在第 2 周结束前，把裁定记录下来——书面形式，并署上利益相关者的名字：

  • 包含哪些内容： 总销售额？折扣？退款？税费？运费？已取消的订单？
  • 金额机制： 货币、舍入方法（银行家舍入？四舍五入？）、截止时区、会计期间截止点。
  • 退款处理： 负向调整、退货窗口、拒付。

两个定义不同的正确实现会报告不同的总额——而且两者都能“对账”。定义就是契约。对于初始数据集，会计参考导出文件是检验你的理解是否正确的独立证据。

Sam，门店店员（虚构）：“顾客问我退货政策，我根据心情会给出三种不同的答案。如果助手能直接告诉我真实的政策并附上文档链接，那就救了我的命。但如果它编造政策，你还没调试完我就先被开除了。”

像 FDE 一样阅读这些备注

  • Priya 的备注是一个信任要求：一个错误的数字就会毁掉采纳。你的对账报告就是对她的回答。
  • Marcus 的备注是一个约束：只读集成、高峰期不给遗留系统增加负载、幂等的 webhook 处理（触发两次 = 只处理一次）。
  • Dana 的备注是一个成功指标：收入对账分毫不差；未迁移的订单要逐条列出，而不是隐藏起来。
  • Sam 的备注是一个安全要求：引用检索到的证据集，并测量幻觉率——而不是“模型看起来还行”。

关于如何把这类备注转化为可构建的问题陈述的需求发现技巧，参见 Discovery。关于决定六周内不构建什么，参见 Scoping & Success Metrics。

第 0 天就绪状态

在六周开始之前，确认你有一条起跑线。本练习不会告诉你如何构建解决方案——它确认你已掌握足够的信息可以开始：

  • 合成源文件可用： 订单、客户、会计参考、SOP。
  • 遗留 API 模拟器可运行： 包含已文档化和故意未文档化的行为。
  • 成功指标已定义： 财务规则、API 限制、AI 质量、恢复标准。
  • 利益相关者决策有明确负责人： 一种有据可查的歧义解决方式——你自己的决策日志，或由同事扮演利益相关者。虚构的签名不是真实的客户验收。
  • 评测证据可复现： 测试夹具、测试命令、评分标准。
  • 项目标注为模拟项目： README、演示、简历和面试叙述中都要如此说明。

起步包（包含已知缺陷的合成导出数据、会计参考资料、带认证/分页/限流/间歇性故障的遗留 API 模拟器、webhook 夹具、版本化 SOP 文档、隐藏评估夹具以及 Docker Compose 配置）提供的是客户的环境——而不是解决方案。

2. 六周计划

这是里程碑的主线。每个里程碑都有退出标准——必须是已经达成的事实，而不是你尝试过的事情。你可以压缩或调整各周的顺序，但不能跳过任何退出标准。如果某项标准未达成，该里程碑就没有完成，并且你要在状态说明中如实说明：对红色（受阻）里程碑的诚实本身就是评分项（见评分标准）。

周里程碑退出标准（必须为真）
1调研笔记存在书面的问题陈述，且每位利益相关者的核心需求都用他们自己的话复述并确认。明确的范围外清单（你在六周内拒绝构建的内容）。指明负责人和风险（例如，“遗留 API 未记录的速率限制——负责人：你，缓解措施：实测退避”）。一页纸的项目参与计划，包含下述里程碑。
1–2数据剖析针对实际导出数据的剖析报告：发现的每种不同日期格式、按年份映射的列名变体、实测的重复客户率、缺失 SKU 行的占比、编码/行长度异常。尚未做任何清洗——这个里程碑只做观察，其产出是数据契约赖以建立的证据。
2–3数据契约一份书面契约：订单、客户、产品的规范模式；规范化规则（日期 → ISO、客户去重键、SKU 处理）；经客户批准的脏数据隔离策略（你提出方案，他们做决定——绝不能反过来）；带严重级别的校验规则（拒绝 vs. 隔离 vs. 警告）。以版本化文档形式存储，而不是只存在于口口相传的经验中。
3–4迁移管道一条可重复运行的管道（是代码，而不是你只跑过一次的 notebook），它读取导出数据、应用契约，并输出两份报告：校验报告（按规则统计被拒绝/隔离/警告的行数）和对账报告（源行数 vs. 迁移行数，收入总额 vs. 会计导出数据——精确到分，按 Dana 的要求）。在同一输入上重新运行管道会产生完全相同的输出（幂等、确定性）。
4–5遗留 API 集成一个连接器：完成身份验证、分页遍历库存（不假设页面大小）、针对实测的故障模式采用退避重试、通过幂等键对不可靠的 webhook 去重，并且绝不向遗留系统写入数据。记录你实测到的限流行为，而不是文档声称的行为。提供一次负载测试或有理有据的论证，证明它不会在高峰期干扰仓库。
5仪表盘 + SOP 副驾驶仪表盘：利益相关者可以交叉核对的数字（收入、订单、库存）与对账报告一致；每个数字都可追溯到来源。副驾驶：基于 SOP 文档并附带引用的回答；一套由真实员工问题组成、并带有实测通过率的评测集；防护栏（不编造政策、PII 处理、审计追踪）。两者都在 Nimbus 上实现租户隔离。
6部署、加固、演示、交接部署在项目的安全态势之下（密钥管理、RBAC、租户隔离），配备健康检查、日志和监控——在 Priya 察觉之前就会向你告警。针对商定的成功指标进行利益相关者演示。一份运维手册：如何运维、如何回滚、每种已知故障模式触发时该怎么做，以及你离开后谁负责什么。获得（虚构的）利益相关者的书面签核。

背景阅读，按里程碑对应

  • 数据剖析与清洗：Files & the Messy Real World、Data Wrangling with pandas、SQL for Field Work、Dates, Timezones & Money。
  • 契约与校验：Trust No Input: Data Validation with Pydantic。
  • API 集成：SDK Design & Debugging Someone Else's API、Pagination, Rate Limits & Retries、Auth in the Wild、Webhooks。
  • 副驾驶：Feeding the Machine: Document Ingestion for RAG、RAG End-to-End、Evals & Tracing: Proving the AI Got Better、Guardrails, Approvals & Audit。
  • 仪表盘：The Operator Console。
  • 部署与加固：Docker & Compose in One Sitting、CI/CD with GitHub Actions、Health Checks, Logs & Monitoring、Secrets, RBAC & Tenant Isolation、Passing the Enterprise Security Review、Release Strategies、Backups & Disaster Recovery。

3. 交付物清单

六周结束时，桌上摆着的就是这份成果包。每一项都是真实项目会留下的产物——而且每一项都可以在面试中展示，不会泄露任何人的机密，因为客户是虚构的。

#交付物它证明了什么
1调研备忘录——问题陈述、以利益相关者原话表述的需求、范围外清单、附带责任人的风险你在构建之前先澄清。
2数据剖析报告——实测到的混乱：日期格式、列名变体、重复客户率、缺失 SKU 占比、编码异常你在决策之前先观察。
3数据契约（版本化） — 规范模式、标准化规则、客户批准的隔离策略、验证严重级别你把数据协议变得明确且持久。
4迁移流水线（代码） — 可重复、确定性、幂等你构建的是可以重复运行的东西，而不是只跑过一次的 notebook。
5验证报告 — 按规则统计的拒绝/隔离/警告数量你衡量流水线对数据做了什么。
6对账报告 — 源数据与迁移后的数量和收入总额对比，精确到分你能证明数字对得上。（Dana 的董事会汇报。）
7遗留 API 连接器 — 认证、分页、带退避的重试、幂等的 webhook 处理、只读你在不破坏系统的情况下集成你不控制的系统。
8连接器测试笔记 — 实测的速率限制、发现的故障模式、峰值负载推理你验证陌生人的指引。（Marcus 的仓库。）
9Nimbus 上的实时仪表盘 — 数字可追溯到数据源你交付一个利益相关者信任的界面。（Priya 的团队。）
10SOP copilot — 基于 SOP 文档的带引用回答、防护栏、审计追踪你负责任地把 AI 交给员工使用。（Sam 的工作。）
11Copilot 评测集 + 结果 — 真实员工问题、通过率、失败分析你衡量 AI 质量，而不是口头断言。
12安全态势说明 — 密钥处理、RBAC、租户隔离、安全审查问了什么你把信任当作系统属性来对待。
13监控与告警 — 健康检查、日志、在客户察觉之前就触发的告警你运维你交付的东西。
14演示脚本 + 利益相关者签字确认 — 演示与既定成功指标对应你沟通的是成果，而不是活动。
15运维手册 — 运维操作、回滚计划、已知故障模式及应对措施、交接后的负责人你让客户（或下一位工程师）能在凌晨两点把它跑起来。

什么不是“完成”

在你笔记本上能跑的演示不算完成。只跑过一次的流水线不算完成。“看起来不错”的 copilot 不算完成。完成意味着：已对账、已衡量、已记录、可由他人部署，并对照成功指标获得签字确认。 下面的评分标准就是检验这一点的工具——在你规划每周工作之前，现在就读它。

三个交付物的剖析（实例摘录）

抽象的清单教不会人；交付物才行。下面是三个权重最高的交付物实际样子的精简摘录。它们是虚构的 Acme 场景中的示例——你的细节会有所不同，但严谨程度应当一致。

摘录 1 — 数据契约（版本化的 YAML）。 注意它不做什么：它从不猜测。含糊的日期会带着规则名称进入隔离区，而不是被静默地使用默认值。

# data-contract v0.3 — Acme Corp orders (fictional example)
# Approved by: Dana (CFO), Acme — 2026-10-20 (illustrative)
entities:
  order:
    fields:
      order_id:      {type: string, required: true}
      order_date:    {type: date, required: true, format: ISO-8601}
      customer_key:  {type: string, required: true}   # candidate match key ONLY:
                                                 # normalized name + postcode is a heuristic,
                                                 # not an identity. Uncertain matches keep
                                                 # their original identity and go to review —
                                                 # never silently merge.
      sku:           {type: string, required: false}  # missing -> quarantine, not drop
      line_total:    {type: money, required: true, currency: USD}
normalization:
  - dates: all observed formats mapped -> ISO-8601; unparseable -> quarantine(rule=date_unparseable)
  - customers: lowercase, strip punctuation/suffixes -> match key; collisions -> quarantine(rule=customer_collision)
  - columns: per-year alias map (OrderID/order_id/Order No/id -> order_id)
validation:
  reject:    [order_id missing, order_date in future,
              line_total < 0]   # zero-value promo lines are legitimate;
              # negative adjustments route to refund handling, not rejection
  quarantine_rules:
    date_ambiguous: [03/04/2019-style MM/DD vs DD/MM — quarantine with
                     per-file locale evidence; never guess]
  quarantine: [date_unparseable, customer_collision, sku missing]
  warn:      [line_total rounding > $0.01 vs source]
quarantine_policy:
  owner: Acme ops (Priya) reviews weekly; unreviewed rows stay quarantined,
         never auto-promoted. Reject-rate tolerance set by Acme, not by us.

红色： SOP copilot 评测：总体 88%，但弃答测试失败（20 个中的 12 个）——当 SOP 未作规定时，模型会凭通用知识作答。我们不会按计划在下周演示 copilot。取而代之的是：将范围缩小到退货/退款/发货（有文档记录的部分），添加严格的弃答路径，并重新运行评测。演示移至第 6 周；仪表板演示仍按计划进行。

4. 约束条件：不要破坏业务

约束条件是区分正式项目与业余副业的关键。这些是不可协商的；无论仪表板多么炫目，违反其中任何一条都会导致任务失败。

约束 1：旧系统不可触碰

库存 API 是仓库实际运作的记录系统。你的集成是只读的：不写入、不改 schema、不对对方系统做“快速修复”。你不能在高峰期增加可能危及仓库运行的负载——Marcus 关于假日旺季的警告是一条硬性边界。据此设计连接器：积极缓存、按业务方批准的时间表同步、一旦 API 出现压力迹象立即退避，并准备一个有文档记录的紧急停止开关。如果 API 宕机，Acme 的仓库要能继续运转，你的仪表板显示的是标注为过期的数据，而不是静默出错的数据。

约束 2：数据在被证明清白之前都是有罪的

十年的人工导出数据会包含没人记得制造过的矛盾。你的工作不是以孤胆英雄的方式“清洗数据”，而是让混乱可见，并让客户做出决策。隔离策略属于 Acme：你提出阈值和后果，由他们批准。你拒绝或隔离的每一行都要在验证报告中逐条列出并附上原因。静默丢弃是对信任的破坏——Priya 的团队会找出那一个错误的数字，而那正是他们记住的数字。

一个需要提前规划的具体陷阱：

03/04/2019

可能是 3 月 4 日，也可能是 4 月 3 日，取决于是谁输入的。你不能靠猜测来解决这个问题。数据契约必须说明如何处理有歧义的日期（隔离？客户裁定？依据每个文件的地区证据？），并且对账报告必须显示该决策被一致地应用。日期处理背景：

约束 3：Copilot 不得凭空编造政策

Sam 的担忧是正确的担忧。一个用自信、貌似合理却错误的答案来回答“退货政策是什么？”的助手，比没有助手更糟。因此：每个回答都要引用检索到的证据集，要有明确的“我在 SOP 中没有找到”的行为，评测要衡量有据性（而不仅仅是流畅度），并围绕 PII 和审计设置防护栏。如果评测数字不好，你要如实报告并缩小范围——而不是上线然后祈祷。背景：防护栏、审批与审计 和 评测与追踪。

约束 4：六周意味着学会说不

你不可能在六周内重建他们的仓库系统、完美统一十年的主数据，并交付一个通用 AI 平台——假装可以做到正是项目失败的原因。发现备忘录中的范围外清单是一份交付物，而不是道歉。一份好的范围外清单会列出你拒绝了的诱人选项（实时同步？跨全部历史记录的完整客户主数据去重？多语言 SOP？），并说明客户将得到什么替代方案。

验收标准

评分标准衡量工作成果；这些阈值定义了“完成”。在发现阶段与利益相关者达成一致（或记录你的假设）——而不是在数字出来之后。

要求所需证据
数据对账精确的行数、精确到分的账务总额、逐条列出的异常
API 弹性针对分页漂移、429/500 处理、重复 webhook 的测试
遗留系统安全请求速率上限、并发限制、紧急停止开关演练
Copilot 可信度带标注的测试集、通过率、对无依据问题的拒答率
租户隔离跨租户访问拒绝测试
恢复能力带计时结果的回滚或恢复演练实测
监控注入故障并产生预期告警

硬性红线：加权平均不能让一份出色的仪表盘弥补租户数据泄露或捏造退款政策的问题。无论总分多高，租户隔离失败、编造政策答案、收入无法对账都自动判定为不合格。

5. 评分标准：按结果评分，而非完成度

这就是契约。请用可验证的结果给自己打分——或让同行给你打分——而不是看你投入了多少努力。权重总和为 100。对每项标准而言，“优秀”意味着结果有证据支撑；“合格”意味着能用但证据薄弱；“需改进”意味着招聘经理在面试中一眼就能看出差距。

标准（权重）优秀合格需改进
数据完整性与对账（25%）对账报告将源数据 → 迁移后的数量和收入与会计导出数据精确对账到分。每一条被拒绝/隔离的行都附有规则和原因，逐条列明。管道具有确定性：重复运行产生完全相同的输出。模糊情况（日期、重复客户）通过有记录且经客户批准的规则解决。数量能对上，但收入有微小偏差且解释含糊其辞，或者隔离原因归类过于粗糙（如“坏行”），让人无从下手。重复运行大体上能复现结果。数字对不上，报告也没有说明。静默丢弃数据。日期/客户的模糊情况靠猜测“解决”，且无记录。重新运行管道会得到不同结果。
API 集成健壮性（20%）连接器能处理认证、分页（不假设页大小）、根据实测故障模式调优的指数退避重试，以及幂等的 webhook 处理（重复投递只处理一次）。从设计上就是只读的。有书面证据表明不会在高峰期干扰遗留系统，并配有紧急停止开关。速率限制行为是实测的，而非引用文档。在正常路径下能工作；有重试机制但使用未经测量的默认值；webhook 去重“大概”没问题。没有关于峰值负载影响的证据。本应验证的地方却轻信了文档。页大小变化就崩溃、重复 webhook 导致库存重复计数，或者——最坏情况——向遗留系统写入数据。没有重试策略；一个 500 错误就中断同步。假设文档是准确的。
Copilot 质量，含评测（20%）回答附带对所检索 SOP 证据的引用。有一套标注好的评测集，包含真实的员工问题，并附有实测通过率和失败分析（什么失败了、为什么、做了什么改进）。有明确的拒答行为（“SOP 中没有”）。防护措施：不编造政策、处理 PII、有审计记录。如果数据不佳，诚实地缩小了范围。有引用，但评测集规模小或临时拼凑；报告了通过率但没有失败分析。有拒答机制但未经测试。提到了防护措施，但未演示。没有评测——“演示里看起来不错”。回答没有引用。演示中出现编造的政策。声称的质量代码并未实际衡量。
部署与加固（15%）密钥妥善管理（绝不放在代码里），RBAC 和租户隔离到位，健康检查 + 日志 + 监控能在客户察觉之前发出警报。有回滚计划且合理；对迁移数据考虑了备份/灾难恢复。包含安全审查式的自我批评。已部署且可访问，但密钥处理草率，监控是“我会去看日志”，回滚是“重新部署旧版本（未测试）”。在笔记本电脑上运行。凭据放在代码仓库里。没有监控，没有回滚方案，没有租户隔离。“我们以后再加固。”
干系人沟通（10%）调研备忘录准确复述了干系人的需求；状态说明诚实地报告红色里程碑并附有计划；演示对应约定的成功指标；Dana 的营收问题和 Priya 的信任问题用实际产出物回答，而不是形容词。状态是绿-黄-红但含糊不清；演示展示的是功能而非成功指标；干系人需求被粗略转述。没有书面沟通产出物。演示是功能巡览。坏消息被隐瞒直到被问起。承诺了任务简报中没有的内容。
运维手册与交接（10%）一位从未见过该系统的值班工程师也能操作它：启动/关闭、日常操作、每种已知故障模式的症状 → 诊断 → 修复、回滚步骤、升级联系人，以及你离开后的责任归属。通过让其他人照着执行来验证。有运维手册但读起来像架构笔记；列出了故障模式但没有应对措施；回滚步骤未经测试。没有运维手册，或者 README 只写着“有问题请联系我”。你一离开，知识就随之流失。

如何使用这份评分标准

  • 开始之前： 把它当作一份合同来读。每一个“优秀”单元格都是你承诺要达到的要求。
  • 进行中： 当某一周进展不顺时，评分标准告诉你该优先保住什么。一个诚实报告并附有恢复计划的红色里程碑，胜过一个虚构的绿色里程碑——“干系人沟通”考察的正是这种诚实。
  • 结束后： 严格给自己打分，写下分数并附上证据链接（报告文件、评测输出、运维手册章节），并把总体结果放进你的作品集 README。一个有证据支撑的自评 78/100，比一个声称的 100 分更有说服力。
  • 面试时： 讲解评分标准中的一行及其对应证据。“这是我的对账报告——收入精确到分都核对无误，还有这 2,140 条被隔离的行及其原因”比任何证书都更能让面试圆满结束。

项目通常如何在每一项上失败

请把评分标准当作这个项目在实践中死掉的六种方式的清单。下面的每个失败案例都是真实工程师实际犯过的错误的综合——请对照检查你的计划：

  • 数据完整性： “看起来没问题”的迁移——抽查了十行数据，从未核对总额，那 2% 被丢弃的行最终是由 CFO 发现的，而不是你。解决方法始终如一：在任何人开口要求之前，先跑出一份对账报告。
  • API 集成： 只走理想路径的连接器——只按文档构建，从未针对 API 的实际行为测试，于是第一个重复的 webhook 分页就在生产环境中把库存重复计算了。解决方法：先探测，不做假设，一切去重。
  • Copilot 质量： 演示驱动的 copilot——只针对演示脚本里的五个问题做调优，从未在员工实际提问的问题上做评测，第一次拒答失败就发生在用户面前。解决方法：在演示之前，先根据真实问题分布构建一套评测集。
  • 部署： 笔记本电脑上的部署——一切正常，直到工程师去休假，因为密钥、监控和回滚都只存在于他的脑子里。解决方法：运行手册测试——把它交给一个陌生人。
  • 沟通： “一切正常”的假象——连续数周汇报“进展顺利”，然后在第 6 周突然爆出意外，这让客户明白你的状态报告不过是营销话术。解决方法：里程碑一变红就当周上报，并附上恢复计划。
  • 交接： “有事打我电话”式交接——没有运行手册，没有责任移交，六个月后没人知道为什么同步任务里有一条没人看得懂的 cron 条目。解决方法：写运行手册时，要当作你从此永远联系不上来写。

误区：“完成度才是评分依据。” 一个建立在未对账数据之上的成品仪表盘，得分会低于一个诚实的、未完成的迁移——只要后者对缺失内容及原因有精确的说明。评分标准里没有“很努力”这一行。它评的是业务可以依赖的成果。这正是以成果而非完成度评分的全部意义所在。

6. 提示（卡住时展开）

卡住本身就是任务的一部分——真实的项目也不会附带一本答案手册。但长期卡死对谁都没好处，所以这里提供一些提示。打开提示之前，请至少先尝试一个小时。

提示：第 1 周我到底该从哪里开始？

从利益相关者的笔记开始，而不是从数据开始。先写问题陈述：每位利益相关者一段，用他们自己的话，然后再写一段说明“六周内上线”具体意味着什么。接着写范围外清单——这会迫使范围界定对话尽早展开。只有在这之后才打开第一个 CSV。技巧回顾：需求发现。

提示：如何在不被淹没的情况下对十年的混乱导出数据进行画像分析？

不要全部读完——抽样并测量。写一个小型画像工具，对每个文件报告：列名、行数、每个日期类列检测到的日期格式、每列的空值占比，以及重复键率。第 2 周的产出就是这份报告，而不是清洗后的数据。在画像分析阶段忍住不要清洗；先观察，后决策。参见 Files & the Messy Real World 和 Data Wrangling with pandas。

提示：数据契约实际上长什么样？

一份简短的版本化文档：(1) 每个实体的规范模式（字段名、类型、必填/可选），(2) 规范化规则（“所有日期 → ISO 8601；客户匹配键 = 规范化名称 + 邮编”），(3) 带严重级别的验证规则——拒绝（绝不加载）、隔离（加载到审查表）、警告（加载并标记），以及 (4) 由客户签署确认的隔离策略：阈值、谁审查隔离表、未审查的行如何处理。用代码（例如 Pydantic 模型——参见 Trust No Input）而非仅仅是文字来编码这些规则。

提示：验证与对账——它们不是一回事吗？

不是，评分标准对两者都有要求。验证是在数据流转时逐行对照契约进行检查（“这一行是否满足规则？”）。对账是在事后将整个迁移与源数据进行核对（“每一条源数据行是否都落在了某个地方——已迁移、已隔离或已拒绝——总数是否一致？”）。只有验证没有对账可能会悄悄丢失数据行；只有对账没有验证则无法告诉你数据行失败的原因。Dana 的董事会汇报需要这份对账报告。

提示：遗留 API 只有部分文档。我该如何安全地集成？

把文档当作假设。探测：翻页并检查是否存在重复/重叠的页以及变化的页大小；在你可控的负载下测量 429/500 错误实际何时出现；用一个记录所有内容的接收端测试 webhook 投递，然后通过重放投递来验证幂等性。将这一切封装在一个具备认证、分页、带退避的重试和幂等键的连接器中——并保持只读。背景：SDK Design & Debugging Someone Else's API、Pagination, Rate Limits & Retries、Webhooks。调试方法：Debugging Like a Detective。

提示：这个 copilot 需要多少道评测题？

足以覆盖真实的问题分布即可，没有神奇的数字。先从 Sam 的视角编写 30–50 个问题（退货、退款、发货截止时间、折扣规则），包括答案不在 SOP 中的陷阱问题（用于测试拒答能力）以及同一问题的不同表述（用于测试鲁棒性）。用来源章节标注预期答案。报告每个类别的通过率，并附上失败分析——“拒答测试 4/12 失败，因为模型用通用知识作答”这类句子才有说服力。方法：评测与追踪；数据接入：喂饱机器。

提示：具体来说，运行手册里应该写什么？

把它写给一个凌晨两点面对系统的陌生人看：如何启动/停止每个组件，“健康”是什么样子（仪表盘、日志行），五种最可能出现的故障及其症状 → 诊断 → 修复（库存同步过期、webhook 积压、流水线验证激增、copilot 评测回归、API 令牌过期），逐步的回滚流程，已迁移数据的备份/恢复，以及交接后谁负责什么。然后把手册交给某个人，观察他们照着操作——他们卡住的每一处都是运行手册的 bug。运维背景：健康检查、日志与监控、备份与灾难恢复。

7. 参考解答在你尝试之后解锁

Project Acme 的完整参考解答稍后会作为一个即将推出的端到端章节出现——同样的任务简报，配上所有交付物完整执行，让你可以把自己的决策与另一种思路进行对比。它之所以在你尝试之后才解锁，是有原因的：先读解答会把这次实战变成一篇教程，而教程恰恰是这份简报要对抗的东西。

诚实的操作顺序是：

  • 自己动手完成简报——完整六周（或你事先声明的一个压缩版本），并按上面的评分标准打分。
  • 在查看任何其他内容之前，先写下你的分数和依据。
  • 然后再读参考章节，把你的决策与它做对比：你在哪些地方的范围界定不同？参考方案衡量了哪些你没衡量的东西？你的哪些判断经受住了第二意见的检验？

第 3 步中的对比才是学习发生的地方——而且这是一个绝佳的面试故事：“这是我做的东西，这是我如何给它打分的，这是我在看到另一种做法后想要改变的地方。”

实战检验

  • 为什么评分标准把对账（25%）与验证分开打分，而不是把两者合并成“流水线能跑通”？
  • 说出两个在生产环境中可见的具体信号，表明你的数据契约正在被新数据违反。
  • Marcus 的仓库运行在遗留系统上。你的同步任务在高峰日的下午 2 点开始报 500 错误。你会做什么——以及不会做什么？
  • 你的 copilot 评测显示总体通过率为 90%，但在大多数拒答测试上失败（它会回答 SOP 未覆盖的问题）。你会上线它吗？你会做哪些改变？
  • 同事说“如果数据变了，我就重新跑一遍 notebook。”这违反了评分标准的哪一项？什么交付物可以解决这个问题？

核对答案

1. 因为它们捕获的故障不同：验证是在数据流经时逐行检查规则；对账则是在事后将整个迁移结果与源数据核对（记录数、精确到分的收入）。一条流水线可以对它处理的每一行都通过验证，却悄无声息地漏处理某些行。Dana 的董事会汇报需要的是对账，而不仅仅是验证。

2. 以下任意两项：验证报告中隔离/拒绝率激增；对账总额与源数据总额出现偏差；接入日志中出现新的列名或日期格式；仪表盘数字与财务导出数据不一致；流水线监控中触发模式验证失败告警。

3. 应该做的：立即退避（不要猛击一个本已吃力的遗留系统），提供带标注的过期库存数据，按运维手册发出告警，并在低峰期排查。不应该做的：激进重试、在对方系统上“修复”任何东西，或悄悄提供看似新鲜但错误的数据。约束条件是只读且不造成损害——无论发生什么，数据仓库都必须持续运行。

4. 不要原样上线：90% 的亮眼指标加上弃答失败，意味着它会编造政策——这正是 Sam 被解雇的场景。缩小范围（减少问题类型、收紧检索阈值），增加显式的弃答路径，重新评测，并如实报告数字。一个更小但值得信赖的 copilot，胜过一个宽泛却过度自信的。

5. 数据完整性与对账（25%）：重新运行 notebook 既不具备确定性，也无法审查——没有版本化的契约强制执行，没有输出验证/对账报告，也没有相同输出的保证。解决方案是以代码形式交付的迁移流水线（交付物 #4），输出验证和对账报告（#5、#6）。

Project Acme 是“获得录用”阶段的第二个作品集简报：一次全新的构建，由你亲手执行，以结果评分。它留下的交付物——调研备忘录、数据契约、对账报告、连接器、评测、运维手册——正是招聘经理真正购买的证据。像业务依赖它们那样去构建，因为在这个简报的故事里，业务确实依赖它们。

当你准备好以面试官会追问的方式来谈论这项工作时，获得录用页面 就是这个阶段的大本营。
