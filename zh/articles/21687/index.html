FDE 在部署 AI Agent 之前如何梳理销售流程

原标题：How FDEs map a sales process before deploying an AI agent

FDE Times · 2026-10-26 · 约 6 分钟读完

摘要

本文以 Outreach 招聘前沿部署工程师的职位描述为线索，说明部署销售类 AI Agent 前必须先梳理客户的销售流程。作者指出，Agent 失败的原因往往不在提示词，而在其读取的数据与出现时机脱离实际流程。文章给出四阶段流程映射方法、培训与变革管理计划，以及向产品团队反馈的结构化格式，并列举四种常见错误。

要点

  • Outreach 的 FDE 职位要求销售流程理解与变革管理，而非仅代码能力。
  • 流程映射的价值在于发现文档与实际操作不一致之处。
  • 培训、文档与现场支持属于部署工作的一部分。
  • 向 Product 的反馈应包含观察、频率、影响与建议四要素。
  • 常见错误包括只访谈销售主管、照搬客户文档流程图等。

销售团队可能在两周内就弃用一个邮件起草 AI Agent，而 Outreach 的一份招聘广告列出了两项有助于避免这种情况的任务，且都不涉及代码。

简要概述

  • Outreach 面向 AI Revenue Agents 的 FDE 职位要求具备 LLM 经验和销售流程知识，此外还需负责客户培训和变革管理
  • 流程图最有价值的地方在于它显示销售团队的实际做法与文档不一致之处，因为那正是 AI Agent 必须读取正确数据的地方
  • 培训和向产品团队反馈是部署的一部分，而不是上线后的收尾工作

上线两周后，日志显示该 AI Agent 的大部分草稿都在未被阅读的情况下被删除了。设想一个团队刚刚交付了一个为 B2B 软件公司销售人员起草外联邮件的 AI Agent。演示进行得很顺利，邮件写得不错，高管们也频频点头。这个案例是假设的，但这种模式很常见。

问题很少出在提示词上。它出在 AI Agent 所处的流程之中——而构建者从未亲身见过这个流程。Outreach 的一份招聘广告相当精确地描述了有助于避免这种情况的工作。

Outreach 为其 AI Revenue Agents 团队发布的“前沿部署工程师”职位要求具备 AI/ML 系统、LLM 或提示词工程方面的经验。然而，同一份招聘广告列出了两项不涉及代码的任务。第一项是与销售、营销和 RevOps 合作，深入了解客户的业务流程。

第二项是通过培训、文档和实操支持，帮助客户团队采用新工具并改变他们的工作方式。任何想成为 AI 产品 FDE 的人都可以从本周开始练习这两项技能。

为什么流程必须先于提示词？

PostHog 将 FDE 描述为弥合产品能力与客户实际需求之间差距的人。Pragmatic Engineer 认为，LLM 集成和 AI 产品尤其适合这一角色。

对于销售 AI Agent 来说，这种差距存在于三个地方：提示词、AI Agent 读取的数据，以及它出现在销售人员工作日中的时机。

提示词在你的掌控之下。数据和时机则由客户的流程决定。这就是为什么 Outreach 明确要求“对销售流程有实际理解”，涵盖潜在客户开发、需求挖掘、销售管道管理和交易评审。这四个阶段也是绘制流程图的良好框架。

示例：绘制四个阶段

回到开篇的那家公司。安排三次单独的访谈：一次与几位直接销售的客户代表，一次与营销部门，一次与 RevOps。

不要问“你们的流程是什么？”，因为这个问题只会让人背诵幻灯片上的内容。要问具体的场景：“上次你准备需求挖掘电话时，打开了哪些标签页，顺序是怎样的？”

在市场部门，问题是哪些标准使线索有资格转交给销售，以及谁有权修改这些标准。在销售运营部门，请要求查看 CRM 配置，并直接询问：哪些字段实际被填写，哪些几乎总是空的？三次会谈之后，你就能整理出这样一张表。

阶段谁来做输入数据AI Agent 可以在哪里提供帮助
潜客开发销售代表、市场部门线索列表、线索资格标准根据线索背景起草第一封邮件
需求探索销售代表通话记录、互动历史会前摘要、建议提问
管道管理销售代表、销售运营CRM 阶段字段标记近期无活动的交易
交易评审销售经理管道报告为每笔交易准备风险摘要

这张表只是草稿。它真正的价值在于不同团队的回答不一致之处。比如销售运营报告说阶段字段持续更新，而销售代表说他们只在每周交易评审前才编辑它。那么一个在周中读取阶段字段的 Agent，实际上是在处理几天前的旧数据。

这样的发现会改变设计。你可能需要把交易提醒移到评审刚结束之后，或者让 Agent 同时读取邮件历史，而不是只依赖阶段字段。仅靠编写提示词永远无法发现这类细节。

培训也是部署的一部分

Outreach 将培训、文档和实操支持归入变更管理之下，这是正确的定位。在上面那家公司，如果新工具在第一周拖慢了销售代表的速度，他们很可能就会弃用它，即使从长远来看它对他们有帮助。

一个简单的计划可以先让一小群销售代表试用。地图上的每个阶段都配一页简短文档，回答三个问题：Agent 做什么、销售代表做什么、什么时候可以忽略 Agent 的建议。第三个问题最重要，因为只有当用户被允许不同意时，他们才会信任一个工具。

实操支持意味着在销售代表真正使用工具时在场，而不仅仅是在发布网络研讨会上。这符合 Palantir 对其 FDSE 的定位精神：与客户并肩工作，快速理解他们最棘手的问题。对于销售 Agent 来说，“并肩”意味着在一个上午的潜客开发中坐在销售代表旁边。

那个上午学到的东西会比任何仪表盘都多。跟踪销售代表编辑后发送的草稿占比，因为这个数字能说明 Agent 是否真正融入了他们的工作流程。

把经验带回产品团队

Pragmatic Engineer 将 FDE 定义为在客户团队和核心产品工程团队之间轮岗的工程师。Outreach 的职位描述把这种轮岗变成了一项具体职责：基于从客户那里学到的东西，向产品团队和工程团队提供结构化反馈。

这里的“结构化”不只是指在 Slack 上留一条抱怨。每条反馈都应包含四个部分：观察到的现象、发生频率、对客户的影响，以及改进建议。

以过时的阶段字段为例，反馈项可能会指出 AI Agent 需要阶段之外的活动信号来源，因为在许多客户那里，该字段只在会议周期中才会更新。

让流程图失去作用的四个常见错误

最常见的是只访谈销售负责人。管理者描述的是流程“应该”如何运行，而一线销售才会告诉你流程“实际”如何运行。其次是直接照搬客户入职文档中的图表，并将其当作事实。

另一个常见错误是把培训压缩为上线前的单次培训，而习惯的养成需要数周的持续支持。最后一个错误是把反馈当作零散轶事发给产品团队。没有频率和影响数据，产品团队就无法据此排定优先级。

把这项技能写进简历

阅读 FDE 职位描述时，留意 RevOps、变革管理、赋能（enablement）或“业务流程”等字眼。这些词表明公司希望找到能站在软件与客户实际工作方式之间的人，而不是只会集成 API 的人。如果你从未做过销售，请研究上述四个阶段，直到你能讲清楚一次交易评审是如何进行的。

最好的证明是一份具体的成果物：基于真实访谈绘制的流程图、一页纸的培训计划，以及一条提交给产品团队的反馈。招聘人员读完这三页内容，对你的理解会远胜于一句“沟通能力强”的自我评价。

好的提示词决定 AI Agent 能写出什么，而流程图和培训计划决定是否有人会使用它写出的内容。
