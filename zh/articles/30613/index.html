面向 FDE 的参考 AI Agent 与 W&B Weave 工作坊

原标题：Reference agents and W&B Weave workshops for FDEs

FDE Times · 2026-11-08 · 约 6 分钟读完

摘要

文章以 CoreWeave 的 FDE（AI Agents）岗位为例，说明前沿部署工程师应把构建与教学结合：交付一个故意带有缺陷的参考 Agent，配合 W&B Weave 的追踪与评测功能，在研讨会上让客户团队亲手定位故障、修复并对比版本，从而真正掌握方法。

要点

  • CoreWeave 的 FDE 岗位把构建 Agent 与举办培训研讨会并列为职责。
  • 参考 Agent 应故意保留典型故障，让追踪和评测有内容可讲。
  • 示例中 12 个任务配合 LLM 评审与手写评分器，定位到错误的工具调用。
  • 客户团队修复后重跑评测，发现修复一处可能导致另一任务回退。
  • 常见错误：用自己的技术栈、只靠 LLM 评审、把研讨会当成单向灌输。

CoreWeave 的 FDE 职位将构建 Agent 与主持工作坊相结合，而一个在 W&B Weave 中追踪到的有缺陷的 Agent，能让客户的团队清楚地看到问题究竟出在哪里。

简要概述

  • CoreWeave 对 FDE（AI Agent）职位的描述涵盖两项工作：与客户的 AI 团队并肩合作，在 W&B Weave 上构建 Agent；以及主持工作坊，加速产品落地。
  • 参考 Agent 是一种教学工具。它的价值在于随附的任务、评分器和追踪记录。
  • 一次成功的工作坊，应以客户的团队修复 Agent、重新运行评测，并能判断 v2 相比 v1 是改进还是退步作为结束标志。

CoreWeave 发布的前沿部署工程师（AI Agent）职位描述，将教学与构建置于同等重要的地位。该职位的人员需要与客户的 AI 工程团队并肩合作，使用 W&B Weave 设计、原型化并将 Agent 推向生产环境。工作坊、深度探讨和赋能培训也被写入职位描述，其明确目标是帮助客户更快地采用产品。

客户的处境很常见：他们的 AI 团队有一个在 notebook 中运行良好的 Agent，但一旦真实用户使用，就会给出错误答案，而且没有人能说清是哪一步出了问题。再演示一个精美的 demo 也帮不了他们。他们需要的是一种深入 Agent 内部并对其进行度量的方法。

构建与教学实际上是同一种能力。你构建的参考 Agent 就是工作坊的教学材料，而工作坊正是检验这个 Agent 的地方。本指南将介绍如何兼顾两者，以便在你离开后客户的团队能够继续推进。

为什么参考 Agent 不应该完美无缺？

Weave 是在 CoreWeave 完成对 Weights & Biases 的收购后进入 CoreWeave 的。CoreWeave 的文档将 Weave 描述为一个可观测性与评测平台，用于追踪、评测和改进 Agent 与 LLM 应用。追踪和评测是这里最重要的两项工作。参考 Agent 必须同时满足这两点，而仅仅运行顺畅是不够的。

在 Weave 的追踪模型中，每次 Agent 运行都是一次对话。对话由多轮组成，每一轮包含一次模型调用及其工具调用。对于教学者来说，这种结构非常有用：它让你能够精确指出 Agent 出错的那一轮和那次工具调用，而不是含糊地说“模型产生了幻觉”。

因此，一个好的参考 Agent 应该刻意包含一两个客户的团队在真实世界中会遇到的典型故障。如果 Agent 从一开始就能把每个任务都做对，追踪记录就无物可看，评测也无从改进，工作坊就变成了一场表演。

一个端到端的示例

以一个假想的客户——一家物流公司为例。其 AI 团队想要一个能够阅读投诉邮件、查询订单并起草回复的 Agent。你的参考 Agent 只需要两个工具：

lookup_order(order_id)

来查找订单，并

draft_reply(order, issue)

来撰写回复。当邮件包含多个数字时，你刻意让提示词在如何挑选订单号这一点上保持模糊。

接下来是任务集。Weave 的 agent 评测教程使用一个裁判模型，根据每个任务的成功标准来为 agent 完成任务的程度打分。你从客户已匿名化的真实邮件中编写了 12 个任务。每个任务都有一条一句话标准，例如：“回复中写明了正确的订单号和预计送达日期，且没有承诺退款。”

仅靠一个 LLM 裁判是不够的。Weave 使用 LLM 裁判结合自定义评分器进行打分，W&B 的 agents 页面说明评分器可以是内置的、第三方的，或由你自己编写。

你添加了一个非常简单的手写评分器：将工具调用中的

order_id

与正确答案进行比对。裁判负责评估回复的质量，而评分器则在不涉及任何主观判断的情况下核对事实。

假设 v1 运行完毕，而

order_id

评分器在 12 个任务中只答对了 7 个。在工作坊中，你打开一个失败任务的追踪记录，逐步逐轮地讲解。

模型读取邮件，调用

lookup_order

时传入的是电话号码而不是订单号，收到错误返回，却仍然起草了一封听起来完全自信的回复。整个房间的人都能看到，问题出在第一次工具调用，而不是撰写步骤。

现在你把键盘交给客户的团队。他们修改提示词并添加一个订单号格式的检查，产出 v2。Weave 让他们针对新版本重新运行同一任务集，并查看 v2 在记录的分数上相比 v1 是进步还是退步。假设评分器提升到 12 个任务中答对 11 个，但裁判将其中一个任务评为比之前更低。

这个退步的任务是本次课程最有价值的一课。客户的团队亲眼看到，修复一个问题可能会破坏另一个问题。他们也理解了为什么每次修改后都必须重新运行整个任务集，而不是只重试导致失败的那封邮件。

工作坊应该如何组织？

一个三小时的课程可以按下表进行划分。总体原则是：客户的团队在键盘前操作的时间应随每个环节逐步增加。

环节时长客户的团队做什么他们收获什么
阅读追踪记录40 分钟跟随失败任务的对话、轮次和工具调用一份按步骤分类的失败清单
编写任务和评分器60 分钟从他们自己的数据中编写更多任务和一个自定义评分器他们自己的评测套件
修复并比较版本60 分钟创建 v2，重新运行，解读进步与退步一份 v1 与 v2 的对比
商定后续步骤20 分钟选定第一个应用此方法的真实 agent一份接下来一周的计划

最后一个板块最容易在会议超时时被砍掉。千万别砍。如果没有一个真实的 AI Agent 名称和一位负责人，前三个板块中学到的一切最终只会躺在没人再打开的笔记本里。

常见错误

最常见的错误是基于自己的数据和自己的技术栈，而不是客户的数据和技术栈来构建参考 Agent。CoreWeave 已承诺保持 W&B 平台的互操作性，对 FDE 而言，这一承诺意味着将 Weave 接入客户已经在使用的任何框架和模型。不要让客户切换到你最熟悉的工具。

第二个错误是让 LLM 评判器决定一切。评判器适合为文本打分，但代码能验证的事实，例如订单号、金额或日期，应该使用手写的评分器。否则，客户的团队会争论评判器的分数，而不是去修复失败之处。

第三个错误是把工作坊当作单向输出。这份职位描述要求 FDE 从一线收集反馈并传回，以影响 Weave 的路线图。每当客户的团队在某个界面上卡住，或者不得不一遍又一遍地编写同一个评分器时，当天就记录下来，因为这是给产品团队的数据。

在求职时把这项技能变成优势

inferencejobs.com 上的职位要求掌握 Python、现代 ML/AI 框架，以及至少五年软件工程或实际编程经验。这些只是入门门槛。但由于工作坊和能力赋能已写入职位描述，你能教会他人构建和评测 Agent 的证据才是你应该放在最显眼位置的内容。

所以，在你的作品集中放一个参考 Agent 仓库，包含三样东西：一套带评判标准的任务集、至少一个自定义评分器，以及一份包含回归任务的 v1 与 v2 对比。

附上一份你实际讲授过的工作坊议程，哪怕只是讲给同事听。在简历上，用成果来描述，例如“团队 X 在赋能培训后开始自行开展评测”，而不是“有 LLM 经验”。

准备面试时，不要只演练你的 Agent 架构故事。还要准备一个赋能培训的故事，而最有力的一个就是：另一个团队在没有你提示的情况下，自己发现了那个回归任务。
