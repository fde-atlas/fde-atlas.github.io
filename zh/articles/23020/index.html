【LLMOps】支持FDE开发的追踪平台建设

原标题：【LLMOps】FDEの開発を支えるトレーシング基盤の開発

Zenn · 2026-11-02 · 约 9 分钟读完

摘要

AI Shift 的 AI 团队为支持 FDE 开发多种 AI Agent，构建了一套追踪基础设施。由于 FDE 专注于解决客户课题，代码插桩常被降低优先级，导致执行记录收集不完整。团队采用 Agent Router（原 Envoy AI Gateway）作为 LLM Gateway，在基础设施层自动采集输入输出、模型名、token 数等遥测数据，经 OpenTelemetry Collector 汇总后仅将 LLM 相关数据发送至 Langfuse。对于 Gateway 无法覆盖的业务语义数据（如用途标记、用户与 session 元数据），则通过自研 Tracing SDK（支持 Python 与 TypeScript）手动插桩，并制作 AI Agent 用的 Skill 让编码 AI 代为完成插桩，降低 FDE 负担。

要点

  • FDE 专注客户课题，插桩常被搁置，导致执行记录收集遗漏。
  • LLM Gateway 在基础设施层自动采集 LLM 调用遥测数据。
  • 遥测经 OpenTelemetry Collector 汇总后发送至 Langfuse。
  • 业务语义数据由自研 Tracing SDK 手动插桩补充。
  • 配套 Skill 让编码 AI 代为插桩，降低 FDE 负担。

前言

大家好，我是 AI Shift AI 团队的林崎（@u_hyszk）。

在引入 AI Agent 之后，当进入“该做评测并据此改进了”的阶段时，是否曾遇到过缺少用于收集评测所需执行记录的平台……这样的经历？即使想收集执行记录，却不知道该怎么做，导致优先级被降低……是否也有过这样的经历？

本文将介绍为引入 AI Worker 的客户开发各种 AI Agent 和应用的FDE (Forward Deployed Engineer)，为了留存并利用执行记录而搭建的机制。

背景与课题

关于本次开发的缘由，将结合我们公司的产品“AI Worker Platform”以及 FDE 的工作方式的前提和课题感进行说明。

AI Worker Platform 与 FDE

AI Shift 提供名为“AI Worker Platform”的产品，作为将整个业务流程 AI 化的统一平台。

https://www.aiworker.jp/ai-solution

与现有产品“AI Worker VoiceAgent”相比，

  • 所涉及的业务领域（后台业务、销售支持、数据分析等）极为广泛，需要深入理解
  • 各自所需的系统集成（内部系统、外部 API、数据库等）较为复杂

存在诸如此类的课题。仅靠提供单纯的 SaaS 产品，很难解决这些课题。

そこで弊社では、FDE職 を新設[1]し、お客様の業務に徹底的に向き合ったソリューションの提供を目指してきました。AI ShiftのFDEは、お客様の業務に深く入り込み、技術でAI x DXを成功に導くことをミッションに以下のような業務を担っています。

  • 客户业务分析与课题识别
  • AI 引入计划与技术设计
  • AI Worker Platform 及外部系统的集成实现
  • 引入后的运维支持与效果评估
  • 向产品提供反馈

最近，为了最大化向客户提供的价值，FDE 不仅使用 AI Worker Platform，单独进行实现的机会也在增加。AI Shift 的 FDE 充分利用生成式 AI，将开发流程中几乎所有工作自动化，从而专注于解决客户的课题。

收集用于评测与改进的执行记录

AI 团队的使命之一，是在 FDE 开发各种 AI Agent 和应用的过程中，如何保障 AI Agent 的输出质量，并向客户展示投入产出比。本文将聚焦其中作为评测与改进前提的“收集执行记录”这一部分。

要在引入 AI Agent 后进行评测与改进，就需要关于 AI Agent 如何运行的执行记录。Langfuse、Arize Phoenix 等众多 LLM 工程平台，都使用名为 OpenTelemetry 的可观测性框架来收集称为遥测数据的数据。主要术语如下。

  • 遥测数据（Telemetry）：从系统及其运行中产生的数据。除后述的追踪外，还包括作为可用性和性能测量值的指标，以及带时间戳的文本记录日志。
  • 追踪（Trace）：以树形结构记录单个请求整体处理过程的数据。
  • 跨度（Span）：追踪中单个工作或操作的单位。

要收集遥测数据，需要对目标应用进行“插桩”，即嵌入用于输出遥测数据的代码。

为了轻松且可靠地收集执行记录

要对 AI Agent 进行评测与改进，收集执行记录是必不可少的。如果尽早收集执行记录，也有望顺利推进评测所需的需求整理。

另一方面，对于应专注于解决客户课题的 FDE 来说，插桩的优先级往往较低。这是因为即使没有插桩，所创建的应用也能正常运行，紧急度较低；此外，如何进行插桩每次都需要判断，负担较大。

基于这样的背景，我们判断有必要将执行记录的收集方式机制化，以便

  • 消除所构建应用中执行记录的收集遗漏
  • 将收集方法标准化
  • 提升 FDE 的开发体验，使其能够专注于解决客户课题

。

支撑 FDE 开发的追踪平台

本次构建的系统的整体架构如下。

追踪平台（重发）

调用 LLM 时使用 LLM Gateway，采用在基础设施层面收集遥测数据的方式。此外，对于 LLM Gateway 无法收集的、包含业务含义的数据，则通过 SDK 和 Skill 进行手动插桩。收集到的遥测数据汇总到 OpenTelemetry Collector，之后仅将与 LLM 调用相关的遥测数据发送到 LLM 工程平台 Langfuse。

通过 LLM Gateway 自动发送遥测数据

我们规定在调用 LLM 时必须使用 LLM Gateway。该 LLM Gateway 会记录输入输出、模型名称、Token 数量等信息，并将遥测数据自动发送到 OpenTelemetry Collector。之后，仅将与 LLM 调用相关的遥测数据发送到 Langfuse。

通过这种方式，在 LLM Gateway 层面进行基础设施级的数据收集，无需由 FDE 来判断是否进行插桩，即可自动收集遥测数据。

本次我们使用 Agent Router（原 Envoy AI Gateway）作为 LLM Gateway。Agent Router 支持基于 OpenTelemetry 的追踪，只需指定环境变量即可启用。Docker Compose 的配置示例如下。

services:
  aigw:
    image: docker.io/envoyproxy/ai-gateway-cli:v1.1.0
    command: run
    ports:
      - 127.0.0.1:1985:1975
    environment:
      OPENAI_API_KEY: ${OPENAI_API_KEY:-}
      OTEL_SERVICE_NAME: aigw
      OTEL_TRACES_EXPORTER: otlp
      OTEL_METRICS_EXPORTER: none
      OTEL_LOGS_EXPORTER: none
      OTEL_EXPORTER_OTLP_ENDPOINT: http://otel-collector:4318
      OTEL_EXPORTER_OTLP_PROTOCOL: http/protobuf
      AI_GATEWAY_TRACING_SEMCONV: openinference
    depends_on:
      - otel-collector

LLM Gateway 插桩的课题

通过 LLM Gateway 收集遥测数据虽然方便，但也存在无法收集需要在应用层面赋予业务含义的数据这一课题。具体来说，无法收集以下数据。

  • 表示应用内部处理关联关系的 Header（traceparent）
  • 表示 LLM 用途（如检索、工具调用、排序等）的数据
  • 表示用户、会话的元数据和标签

关于第一点，由于应用侧不进行上下文传播，LLM Gateway 每次都会重新生成新的追踪，因此存在每次 LLM 调用都会生成一个深度为 1 的独立追踪的问题。在复杂的使用场景下，数据分析和评估会变得困难。

对于需要业务含义的数据，由于原理上难以通过 LLM Gateway 收集，因此我们决定同时采用基于 SDK 和 Skill 的手动插桩。

基于 Tracing SDK 和 Skill 的手动插桩

为了对 LLM Gateway 生成的追踪赋予业务含义，我们开发了专用的 Tracing SDK。该 SDK 的范围如下。

  • 与 LLM Gateway 的集成
  • 考虑业务含义的追踪结构化与标准化
  • 表示 LLM 用途的数据的附加与传播
  • 用户、会话标识符等元数据和标签的附加与传播

由于 LLM 调用本身的插桩由 LLM Gateway 承担，因此不在 SDK 的范围内。通过该 SDK 进行插桩，可以收集到便于分析和评估的高质量数据。

Python 和 TypeScript 中 SDK 的使用示例如下。

此外，为了降低 FDE 的开发负担，我们创建了用于通过 Tracing SDK 进行插桩的面向 AI Agent 的 Skill。使用该 Skill，可以将插桩工作交给编码 AI，大幅降低实现负担。

通过这样的机制化，可以实现：

  • 通过 LLM Gateway 消除收集遗漏
  • 通过 SDK 和 Skill 实现插桩标准化
  • 通过 SDK 和 Skill 提升 FDE 的开发体验

从而达成一系列目标。
