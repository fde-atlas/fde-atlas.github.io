数据科学家转 FDE：面试考什么、差距在哪

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

文章面向想转型 FDE 的数据科学家，指出 ML 经验和调试思维是可迁移的优势，但面试真正考察的是问题拆解、生产级编码、客户同理心和端到端主人翁意识。文中引用 Sundeep Teki 的面试指南、FDE Academy 与 Cloud Authority 的分析，并给出包含算法练习、端到端项目和简历改写的补齐计划。

要点

  • ML 与调试经验是优势，许多 FDE 岗位明确要求相关背景。
  • 差距在模型之外：问题拆解、生产代码与端到端负责。
  • 面试一轮约 60 分钟考察模糊问题拆解，模型应放在最后考虑。
  • 需补齐云、API、鉴权、数据库、监控及 VPC、SSO、HIPAA 等客户约束知识。
  • 建议刷中等难度算法题、做含 RAG 的端到端项目，并重写简历。

ML 直觉和调试能力可以带走，面试真正考的是拆解模糊问题、生产代码和端到端负责。

要点速览

  • ML 经验和调试思维是实打实的优势，不少 FDE 岗位明确要求 ML 或 Agent 开发经验。
  • 差距不在模型本身，而在问题拆解、生产代码和端到端负责。
  • 比起你待过哪些公司，雇主更看重端到端交付的能力。

设想这样一个场景：你训练完一个用户流失预测模型，AUC 不错，notebook 也很整洁，于是交给了平台团队。三周后，模型还躺在那里，因为没有人把它接入客户的登录系统。

做 FDE，负责接入的人就是你。好消息是，这条路确实走得通：FDE Academy 的职业指南把 ML 工程师列为进入 AI 公司前线部署工程（Forward Deployed Engineering）的可行路径之一。

Cloud Authority 在 2026 年对招聘信息做的一项分析也发现，许多 FDE 岗位直接提到了机器学习或 Agent 开发经验。

不那么轻松的消息是：根据 Sundeep Teki 的 2026 年 FDE 面试指南，FDE 的面试流程会同时考察通常分开评估的四项能力：问题拆解、编码、客户同理心和主人翁意识。建模能力只是入场券。真正的问题是：哪些该保留，哪些要补。

你带来的东西比你想的更值钱

ML 基础是直接的优势，尤其是在 AI 公司需要懂模型、数据管道和 LLM 应用如何部署与集成的人时。你知道模型为什么会退化，数据泄漏长什么样，怎么看数据分布。这些是你已有的直觉，不必从头学起。

第二样值得保留的是调试思维。FDE Academy 关于从数据工程师转 FDE 的指南明确指出，调试能力可以迁移。当你追查某个特征为什么突然全变成 null 时，你做的正是 FDE 对接一个出故障的客户系统时要做的事：提出假设、缩小范围、验证。

但同一份指南也点出了核心区别：做数据的人通常在内部工作，而 FDE 直接面对客户。调试思维不变，但你需要理解的系统数量成倍增加。

差距在模型周围，不在模型里

Cloud Authority 援引 The Pragmatic Engineer，对两种角色做了一个清晰的区分：开发者为许多客户构建一种能力；FDE 则深入一个客户，覆盖多种能力。当你站在单个客户这一边时，训练模型只是你亲手做的许多工作之一。

Palantir 在华沙的 Forward Deployed Software Engineer 招聘信息中写道，这份工作以小团队形式开展，监督很少，要对高风险项目端到端负责。同一份招聘信息要求候选人是一名强力的程序员，熟练掌握 Python、Java、C++ 等语言。统计能力替代不了这项要求。

保留

  • 对模型、数据管道和 LLM 应用的理解
  • 数据调试直觉：缩小范围、检验假设
  • 日常使用的 Python 和 SQL

补齐

  • 先拆解模糊问题，再考虑模型
  • 生产代码和 LeetCode 中等难度算法
  • 云、API、鉴权、数据库、监控
  • 客户约束：VPC、SSO、HIPAA/SOC2
  • 部署出故障时自己扛起来

一个模糊问题，逐层拆解

Teki 把问题拆解列为 FDE 面试中最重要的能力。技术深挖环节约 60 分钟，不写代码，围绕一个表述非常宽泛的真实问题展开。ML 背景的人恰恰容易在这里栽跟头，因为他们的第一反应往往是选模型。

举一个假设的题目：“一家连锁诊所想用 AI 让患者少等一会儿。”数据科学家会想直接用梯度提升预测等待时间。FDE 则按另一种顺序拆解问题：

1. 用户：谁在承受等待？患者、前台还是医生？
2. 决策：谁有了更好的信息会采取不同行动？（前台重新排期？诊所加班次？）
3. 数据：预约、签到时间和就诊时长存在哪里？谁有权限访问？
4. 约束：医疗数据 -> HIPAA，运行在客户的 VPC 内，
   通过现有 SSO 登录
5. 第一周：按时段展示等待时间的看板，暂时不需要模型
6. 然后才是 ML：按小时预测负载，为排班提供建议

注意，模型出现在最后一步。第四层也不是偶然：Teki 指出，FDE 的系统设计面试与每个客户的具体情况挂钩，涉及 VPC、SSO、HIPAA/SOC2 等话题。

如果你能在面试中说出“这些数据不能离开客户的基础设施”，你回答的正是这一轮系统设计要考的问题，而不只是画了一张模型架构图。

凌晨两点部署出了故障

Teki 用一个非常具体的场景说明主人翁意识：凌晨两点部署出了故障，你不去提工单。对习惯把模型交给其他团队的人来说，这是最大的思维转变。

沿用诊所的例子，假设预测接口突然返回 401 错误。旧的反应是通知平台团队。FDE 的反应是自己追查：SSO token 是不是刚轮换过？服务账号对预约表还有读权限吗？修好之后，写下根因，并加一条告警，下次更早发现。

调试思维仍然是你的，只是现在它的范围是整个系统。

练习计划：算法、一个真实项目、一份新简历

第一，算法。Teki 描述的编码面试是 LeetCode 中等难度，但包装成客户场景；有候选人反映在 Palantir 遇到过 BFS 和图论题。notebook 练不出这种反应，你需要定期刷题，并练习边想边说。

第二，一个端到端项目。FDE Academy 建议做一个包含云、API、身份验证、数据库和监控的项目。对 ML 背景的人来说，最快的路径是拿自己以前的一个模型，封装成带登录的服务，把预测结果记录到数据库，再做一个跟踪延迟和数据漂移的看板。

再加一层小规模的检索增强生成（RAG）也很值得，因为 Teki 列出的技能包括 Python、LLM/RAG、云、SQL/数据管道和全栈。

第三，简历。Teki 认为，端到端交付的能力比公司名气更重要。对没在大厂工作过的开发者（包括许多越南开发者）来说，这是好消息：每一条经历都应写清楚你为谁解决了什么问题、交付了什么系统、在生产环境中表现如何。

阅读岗位描述时，留意“end-to-end”“customer-facing”“minimal supervision”这类措辞，借此判断一个岗位是否正需要你刚补齐的这些能力。

ML 背景的人常踩的坑

最常见的坑是一开口就报模型名。面试官想听你追问用户和决策，而不是比较 XGBoost 和 Transformer。

第二个坑是作品集全是 notebook。notebook 证明你擅长分析，却证明不了你会部署、做用户鉴权或监控系统。第三个坑是因为自己“做 AI”而轻视算法面试。编码面试依然是 LeetCode 中等难度，Palantir 的招聘信息也依然要求强力的程序员。

最后一个坑是谈准确率，而不谈客户结果。诊所买的不是 AUC，而是患者少等一会儿的早晨。

本周练习：挑一个你做过的模型，像诊所的例子那样，为一个假想客户写出六层拆解，然后问问自己：哪一层你从没亲手处理过？那一层就是你接下来要学的。
