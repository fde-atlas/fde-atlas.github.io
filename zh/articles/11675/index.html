Search-R1 (2025) 详解：写给 FDE 的解读

原标题：Search-R1 (2025) Explained for FDEs

FDE Interviews · 2026-10-26 · 约 3 分钟读完

摘要

Search-R1 是一种训练方法：让语言模型在强化学习过程中与搜索引擎交互，模型自行生成查询、阅读检索结果并可再次搜索，最终以答案正确性作为奖励。关键实现细节是 token 来源区分——检索返回的内容只作上下文，不参与策略优化。论文在通用与多跳问答任务上验证了效果，但作者提醒这并不等于所有企业应用都应改用 RL 训练的搜索 Agent。对 FDE 而言，可先从 ReAct 循环和检索基线入手，只有当失败模式明确时才考虑专项训练。

要点

  • 模型在 RL rollout 中生成查询并多次搜索，以最终答案为奖励。
  • 检索返回的 token 被掩蔽，不计入策略优化目标。
  • 评测基于共享语料和检索器，隔离了学习到的搜索行为贡献。
  • FDE 应先测检索基线，失败模式明确时再考虑训练。
  • 每次额外搜索都增加延迟与上下文成本，需满足客户权限要求。

一分钟读懂这篇论文

Search-R1 在语言模型与搜索引擎交互的过程中对其进行训练。模型生成一个查询，接收返回的段落，继续推理，并可以在给出最终答案之前再次搜索。强化学习只奖励最终结果，因此策略可以学习哪些搜索决策有助于完成任务。

关键的实现细节是 token 来源。一次 rollout 中既包含模型生成的词，也包含检索返回的词。检索到的词提供了上下文，但策略并未选择它们。Search-R1 将这些词从策略优化目标中屏蔽掉，而不是把它们当作生成的动作。

论文在通用问答和多跳问答上评估了该方法，使用共享的 Wikipedia 语料库和检索器。这些控制条件有助于分离出学习到的搜索行为所带来的贡献。但它们并不能证明每个企业助手都应该用经过 RL 训练的 agent 来取代简单的检索流水线。

这是一种带有具体执行循环的训练方法。应用程序可以借鉴其中受限的搜索接口和来源记录机制，而不必运行完整的训练流程，但这样做并不等于复现了论文报告的模型收益。原始代码和检查点可在作者的 Search-R1 repository 中找到。

被提示去搜索的模型可能做出糟糕的检索决策，因为其训练过程从未优化过这些交互。

把搜索放进 RL rollout 中，奖励最终答案的正确性，并将外部提供的 token 从策略目标中排除。

在共享语料库和检索器下，所评估的 QA 系统均有所提升。实际部署仍需要证据质量、访问控制、受限搜索和合适的奖励机制。

为什么这对 FDE 很重要

一个多步骤的客户问题可能需要先找到某个实体，再查询关于该实体的关键事实。基于原始问题的一次固定搜索可能会遗漏这种依赖关系。搜索循环可以在看到第一个结果之后再构造第二个查询，前提是它有可靠的停止方式，并且有足够的时间完成。

Search-R1 为你提供了一种讨论如何训练这种行为的方式，而不必完全依赖提示词。它也让成本变得可见：每增加一次搜索都会产生检索工作，并为后续生成增加上下文。其收益必须经受住客户的 latency 和权限要求的考验。

从 ReAct 循环 和一个经过测量的检索基线开始。如果轨迹反复显示查询选择不佳或停止决策不当，考虑是否有必要进行任务特定的训练。如果所需的证据缺失或无法获取，任何搜索策略优化都无法弥补。
