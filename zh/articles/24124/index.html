Palantir AIP Logic 是什么？原理、使用方法与 FDE 实务中的应用

原标题：Palantir AIP Logicとは？仕組み・使い方とFDE実務での活用法

FDE総研 · 2026-10-21 · 约 9 分钟读完

摘要

本文介绍 Palantir Foundry 的 AIP Logic：一个无代码环境，可将 LLM 推理作为函数嵌入业务流程，并与 Ontology 及权限模型联动。文章说明其输入、块、工具、输出的构成，讲解从定义输入到发布五步构建流程，比较其与代码函数的分工，并从 FDE 实务角度阐述如何在客户现场快速原型化业务判断、所需技能及生产运用的风险管理要点。

要点

  • AIP Logic 让 LLM 在 Ontology 与权限模型内运行，可发布为可调用的函数。
  • 函数由输入、块、工具、输出四要素构成，LLM 通过工具访问对象与动作。
  • 判断类处理用 AIP Logic，确定性计算用代码函数，二者常组合使用。
  • FDE 用它快速复现现场判断逻辑，需具备 Ontology 设计与业务理解能力。
  • 生产运用应限制工具、引入人工审批，并用 AIP Evals 做回归测试。

Palantir AIP Logic 是什么？

Palantir AIP Logic 是一个开发环境，用于以无代码方式创建嵌入 LLM 的函数，并与 Ontology 联动。它是 Palantir Foundry 上 AIP（Artificial Intelligence Platform）的功能之一，用于将 LLM 的推理安全地嵌入业务逻辑中。

AIP Logic 能做什么？

使用 AIP Logic，可以创建以 Ontology 对象为输入、由 LLM 进行判断并返回结果或写入结果的函数。与在笔记本或聊天界面中尝试不同，创建的处理会作为“函数”发布，可从其他应用程序调用。

典型用途如下。

用途输入（示例）AIP Logic 的输出（示例）
分类、打标签询价、故障报告的对象类别、优先级
摘要、提取长篇报告、会议纪要要点、结构化条目
决策支持库存、需求、约束的对象推荐行动方案
写入自动化判定结果向 Ontology 应用 Action

与 ChatGPT 等通用聊天有何不同？

AIP Logic 最大的不同在于，LLM 是在自家的 Ontology 和权限模型中运行的。使用通用聊天时，数据的导入和结果的反映需要人工手动完成。而在 AIP Logic 中，LLM 可引用的对象和可执行的 Action 会作为工具显式传入，因此设计者可以控制“能接触什么”。

从一线的感觉来说，AIP Logic 与其说是“尝试 LLM 的场所”，不如说是“把 LLM 变成业务流程组件的场所”。我们认为，它承担着将容易止步于 PoC 的生成式 AI 应用连接到实际生产业务的职责，这种理解更接近实际情况。

AIP Logic 的工作原理是怎样的？

AIP Logic 是由输入、块的串联和输出构成的函数，并将 Ontology 操作作为工具传给 LLM。其内部接近声明式工作流，各块按顺序执行，并将结果传递给下一个块。

AIP Logic 由哪些要素构成？

AIP Logic 的函数由输入、块、工具、输出四个要素组成。按照 Palantir 官方文档（AIP Logic overview）的说明整理如下。

要素作用具体示例
输入（Inputs）传给函数的参数对象、对象集、字符串、数值
块（Blocks）处理的单元使用 LLM、执行函数、应用 Action、条件分支、循环、创建变量
工具（Tools）LLM 块可使用的功能对象搜索、函数调用、应用 Action、计算器
输出（Output）函数的返回值字符串、对象、结构化的值

核心是 LLM 使用块。在这里定义提示词、使用的模型、工具和输出的类型。只要指定输出的类型，就能以结构化形式接收结果，而不是自由文本，便于后续处理。

与 Ontology 的联动是如何实现的？

AIP Logic 直接引用 Ontology 的对象、链接和 Action，并原样继承 Foundry 的权限设置。即使 LLM 提议或执行 Action，也要经过 Ontology 中已定义的 Action（包括验证和权限检查）。因此，在结构上很难发生直接改写数据库之类的事故。

此外，各步骤的输入输出和 LLM 的推理过程可以通过调试器确认。由于可以追踪调用了哪个工具、使用了什么参数，在质量改进时更容易定位原因。

AIP Logic 的创建步骤是什么？

AIP Logic 的创建分为五个阶段：定义输入、组装块、调试、评测、发布。与其一开始就搭建复杂的流程，不如从单个 LLM 块小规模起步，再逐步扩展，这样更不容易失败。

基本的创建步骤是什么？

AIP Logic 的基本步骤是：在 Foundry 上创建新的 Logic 文件，然后依次定义从输入到输出的流程。

  • 定义输入：确定目标对象类型和参数（例如：一条“询价”对象）。
  • 组装块：在 LLM 使用块中设置提示词和输出类型，并根据需要添加条件分支或应用 Action 的块。
  • 传入工具：只以最小限度选择允许 LLM 使用的对象搜索和 Action。
  • 用调试器试运行：输入实际数据，确认各块的输入输出和 LLM 的推理。
  • 评测并发布：用测试用例确认精度后再发布，并从 Workshop、Action 或自动化中调用。

提高质量有什么技巧？

我的印象是，AIP Logic 的质量往往不是取决于提示词的技巧，而是取决于“传递的信息和工具的精简程度”。只传递必要的属性，并严格限定输出类型，结果的波动就会明显减少。

改进要点要做的事预期效果
输入的精简只传递判断所需的属性减少噪声，还能降低成本
输出类型的指定使用枚举类型或结构化输出后续处理更容易
工具的最小化限定允许的操作降低误操作的风险
评测的体系化用 AIP Evals 管理测试用例能发现变更导致的性能退化

AIP Logic 和用代码编写的函数该如何区分使用？

需要判断或自然语言理解的处理适合用 AIP Logic，确定性的计算或复杂处理适合用代码编写的函数。实务中通常不是偏向其中一方，而是采用从 AIP Logic 调用代码函数的组合方式。

各自的擅长领域是什么？

AIP Logic 适合处理含糊输入的处理，而用 TypeScript 或 Python 编写的函数适合需要严格性的处理。在 Foundry 中，可以把在 Code Repositories 中编写的函数作为 AIP Logic 的函数执行块或工具来调用。

视角AIP Logic用代码编写的函数（TypeScript/Python）
擅长的处理分类、摘要、抽取、判断辅助汇总、计算、严格的业务规则
开发的难易度无代码即可快速尝试需要工程知识
结果的可复现性由于是 LLM，存在波动相同输入则结果相同
测试用 AIP Evals 进行评测用单元测试来保障
承担者业务人员也容易参与主要是工程师

犹豫不决时的判断标准是什么？

用“相同输入是否必须返回相同答案”来判断，通常就不会犹豫。像费用计算或库存预留这类正确答案唯一确定的处理用代码编写，AIP Logic 只需将其作为工具调用。不让 LLM 进行计算是稳定运行的基本原则。

在 FDE 实务中 AIP Logic 是如何被应用的？

对 FDE 来说，AIP Logic 是把客户的业务课题变成当场可运行的原型并达成共识的工具。FDE（Forward Deployed Engineer）是深入客户现场解决问题的职位，构建速度本身就是价值。

在客户现场是如何使用的？

FDE 用 AIP Logic 在短时间内复现通过访谈了解到的业务判断，并与现场负责人一起打磨完善。典型的流程如下。

  • 观察现场负责人日常进行的判断（例如：咨询的分类、异常的初步判定）
  • 把判断所用的信息整理为 Ontology 的对象
  • 用 AIP Logic 搭建判断逻辑，用真实数据展示给现场负责人
  • 把“这种情况不对”的反馈加入评测用例并加以改进
  • 集成到 Workshop 应用或自动化中，纳入业务流程

在 Palantir 与客户短期集中开展的“AIP Bootcamp”中，也介绍了用 AIP 功能在几天内把实际用例做成形的方法。我觉得这里重要的不是 AIP Logic 的操作技能本身，而是识别业务中哪些环节适合嵌入 LLM 判断的能力。

FDE 需要具备哪些技能？

熟练运用 AIP Logic 的 FDE 需要具备三项能力：Ontology 的设计能力、业务理解能力，以及判断 LLM 局限的判断力。

技能内容与 AIP Logic 的关系
Ontology 设计对象、链接、动作的建模决定输入和工具的质量
业务理解把现场的判断标准用语言表达出来成为提示词和评测用例的基础
LLM 的判断判断哪些范围交给 LLM决定与代码的职责分工
编程用 TypeScript/Python 开发函数补充严格的处理

这并不意味着因为是无代码就不需要工程师了。相反，能够用代码弥补无代码无法表达的部分、并能进行整体设计的 FDE，其价值正在不断提升。

将 AIP Logic 投入生产运行时需要注意什么？

在 AIP Logic 的生产运行中，需要把握三点：输出的波动、写入操作的管控、评测与版本管理。即使原型运行良好，也最好避免直接进行全面自动化。

如何管理质量和风险？

AIP Logic 的质量管理通过持续运行评测用例的机制与人工确认相结合来进行。主要注意事项如下。

风险可能发生的情况对策
输出的波动相同输入判定结果不同限制输出类型，扩充评测用例
错误的写入执行不恰当的动作加入人工审批，将工具减到最少
模型变更的影响更新模型后精度发生变化发布前用 AIP Evals 进行回归测试
成本的增加大量执行导致费用增加精简输入，限定执行对象

尤其是涉及动作的处理，建议一开始采用“LLM 提议、人工审批”的形式。在确认精度稳定后再扩大自动化范围，就不会损害现场的信任。

运营体制上需要注意什么？

要长期运营 AIP Logic，必须明确函数的负责人和评测用例的更新规则。业务规则一旦变化，提示词和评测用例都会过时。事先决定由谁审批变更、通过哪些测试才能发布，就能防止依赖个人。

从向客户交付 AIP Logic 的 FDE 立场来看，比起把东西做完，更重要的是留下客户能够自己持续修改的状态。只有当文档、评测用例和变更流程成套交付时，项目才算真正成功吧。
