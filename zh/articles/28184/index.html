前沿部署工程，第三部分：在他人的领地内进行设计

原标题：Forward deployed engineering, Part 3: Designing inside someone else's estate

Abhinav Bhatia · 2026-10-20 · 约 17 分钟读完

摘要

作者以虚构客户 Acme 的案例，讲解前沿部署工程师如何在客户已有的技术环境中做前期设计：数据归属、身份认证、私有网络路径、合规边界与安全评审。核心观点是 FDE 只拥有 Agent 代码本身，其余组件都归客户团队所有，任何改动都是需要排期的请求，设计必须从第一周起围绕客户现有环境展开。

要点

  • FDE 只拥有 Agent 代码，其余组件归客户团队所有
  • 先做数据地图：数据位置、所有者、敏感度和读取身份
  • 身份设计需注意换 IdP 会丢失聊天记录等风险
  • 网络路径用 Private Service Connect 和 VPC Service Controls 私有连通
  • 安全评审应主动提交设计包，并把附加条件当作任务落实

FDE 需要在自己不拥有的系统中做设计。本部分从零开始讲解前期技术设计：数据存放在哪里、由谁负责，哪个身份提供商为用户登录签名，流量如何通过 Private Service Connect 和 VPC Service Controls 私密传输，适用哪些合规边界，安全审查如何进行，第一周该问什么问题，以及一份设计评审清单。

在第二部分中，我们把 Acme Consumer Brands 的一个模糊需求变成了一份已签署的一页纸简报：一个首个用例——“这次活动因缺货损失了多少？”、只读访问、附带成功指标和基线。现在需要有人来设计这个系统。

这正是前沿部署工作与构建自己产品差异最大的地方。做自己的产品时，你可以选择云项目、网络、身份提供商和安全规则。而在客户的环境中，这些都已经存在，由其他团队负责，你所需要的每一项变更都是一个有各自交付周期的请求。一个忽视这一点的设计在白板上看起来很漂亮，然后却要等上几周的审批。

本文按照我的工作顺序讲解前期设计：数据存放在哪里、由谁负责，谁登录以及如何登录，流量如何传输，适用哪些合规规则，以及安全审查如何进行。文末附上我第一周会问的问题和一份设计评审清单。

这在 FDE 职位描述中是如何体现的？

公开的 FDE 招聘信息直接描述了这项工作：

  • Google Cloud 的 Forward Deployed Engineer, GenAI 招聘信息要求你“设计并编写连接 Google AI 产品与客户现有基础设施的中间层，包括 API、遗留数据孤岛和安全边界。”同一则招聘信息还描述了要解决“发布阻碍，包括解决集成难题、数据就绪问题和状态管理问题。”
  • Google Cloud 的 AI Outcome Customer Engineer, Forward Deployed Engineering 招聘信息写道，你将“设计这些技术资产如何真正集成到客户的 IT 生态系统中（连接器、身份、数据驻留、法律约束）。”
  • OpenAI 的 Forward Deployed Software Engineer 招聘信息描述了“在客户的基础设施上并肩编码，推动项目完成。”

共同点在于客户的基础设施。设计必须适配客户已经在运行的东西。

什么是领地？为什么它是别人的？

一个组织的资产环境是指它已经在运行的一切：其云组织和项目、网络、身份系统、数据平台、安全工具以及管理这些的各类策略。当你作为 FDE 加入时，你是在这个资产环境之内进行设计。

本文中还会出现几个术语：

  • 落地区（Google Cloud 也称之为云基础）是平台团队预先构建的项目、网络、身份和策略的配置，让新工作负载能够安全落地。如果客户已有落地区，你的设计就要从它出发。
  • 数据所有者是对某个数据集负责、并决定谁可以使用它的人或团队。
  • 身份提供商（IdP）是负责让用户登录并告知其他系统其身份的系统。
  • 网络边界是控制哪些流量可以到达或离开一组资源的界限。
  • 合规边界是来自法律、合同或策略的规则，限制数据可以流向何处以及如何处理。
  • 安全评审是客户在接触真实数据之前，对你的设计是否符合其策略进行的正式检查。

装修一套租来的公寓是个恰当的类比。租户（FDE）可以改造厨房（Agent 代码），但需要房东的许可（安全评审），不能动承重墙（身份提供商和网络设计），必须使用大楼的管道和线路（网络路径），并且要遵守建筑法规（合规要求）。以下是 Acme 的资产环境：

AI Agent 必须栖身其中的 Acme 资产环境：企业身份提供商、包含 Gemini Enterprise、Agent Runtime 和 BigQuery 的 Google Cloud 组织，以及一个独立的 Databricks 工作区；每个方框都有归属，而 FDE 只拥有 Agent 代码

只有一个方框是 FDE 要构建的：Agent Runtime 上的 Agent，它们运行在平台团队为我们设置好的一个项目中。其他每个方框都属于 Acme 的某个团队，而第一周你能做的最有价值的事，就是弄清楚是谁。

数据存放在哪里，由谁负责？

从数据开始，因为几乎所有其他决策都取决于它。对于第一个用例中的每个数据源，我都会填写一份数据地图：数据是什么、存放在哪里、谁负责、敏感程度如何，以及由哪个身份来读取。

第一个用例的数据地图：对每个数据源，标明其存放位置、负责人、敏感程度以及由哪个身份读取；营销活动支出由 Agent 读取，供应数据仅以用户身份读取，罚款数据仅由供应方读取，而聊天记录则需要做出位置和保留期限的决策

“存放在哪里”有两层含义，客户对两者都很在意：

  • 静态存储指数据存储的位置。
  • 处理中指数据在使用过程中被处理的位置，包括模型读取它的位置。

Gemini Enterprise 对两者都有说明。其位置页面列出了

在 Acme，数据地图一目了然地显示了三件事：

  • 营销活动支出位于欧盟的 BigQuery 中，营销 Agent 以自身身份、只读方式访问它。
  • 订单、OTIF 和罚款位于 Databricks 中，由供应链数据团队负责。供应链 Agent 以登录用户身份读取这些数据，且只有供应链一方可以计算罚款。Acme 使用联合查询，因此两个团队都无需复制对方的数据，正如 Agent 系列中的 Agent 究竟是什么 所解释的那样。
  • 聊天记录也是数据。它可能包含个人数据，因此与其他数据源一样，需要确定其位置和保留策略。Gemini Enterprise 的安全概览指出，用户请求的数据会在 60 天内删除。Agent 系列中的记忆：Agent 应该记住什么介绍了 Agent 应该记住和不应该记住的内容。

谁在登录，Agent 又如何得知？

每个请求都需要回答“是谁在提问？”，而客户的身份提供方会给出答案。有两个标准承担了大部分工作：

  • SAML 2.0（安全断言标记语言）是一种基于 XML 的标准，身份提供方会向应用程序发送一个经过签名的断言，即说明用户身份的声明。
  • OpenID Connect（OIDC）是构建在 OAuth 2.0 之上的身份层。身份提供方会签发一个 ID 令牌，即描述用户信息的已签名 JSON 文档。

Gemini Enterprise 随后需要知道哪些用户对应哪些身份，以便执行每个数据源的访问规则。其身份提供方指南提供了两种选择：

  • Google Identity，Google 推荐新环境使用。如果第三方身份提供方支持 OIDC 或 SAML 2.0，它也可以与之配合使用。
  • Workforce Identity Federation，它将来自外部身份提供方的用户联合起来，因此他们的账户不会存储在 Google Cloud 中，也不会同步到 Google Cloud。该指南指出，通过数据摄取连接的 Microsoft 365 数据源需要 Microsoft Entra ID 与 Workforce Identity Federation。

文档中有两条警告应当纳入每一份设计。第一，如果日后更换身份提供商，用户将丢失现有的聊天记录，因为记录绑定在他们旧的 ID 上。第二，安全概览警告说，能够编辑劳动力池属性映射的管理员可能有意或无意地启用用户冒充功能。文档建议尽量少授予这些角色，并使用 Privileged Access Manager 对其进行审计。

让用户登录只是身份设计的一半。Agent 也需要自己的身份，而且 Sam 的身份必须传递到 Databricks，同时模型绝不能看到他的令牌：

一个问题的身份流转过程：Sam 通过企业身份提供商登录，Gemini Enterprise 知道 Sam 是谁，路由器以自身身份调用供应链 Agent 并将 Sam 的身份作为元数据附带，Databricks 根据 Unity Catalog 授权校验 Sam 自己的令牌

Agent 系列中的Agent 身份一文用代码构建了这一流程。在设计阶段，任务是把每个决策达成一致并记录下来。我使用一份简短的架构决策记录（ADR）：一页纸记录一个决策、可选方案、理由和后果。

一份关于整体决策的架构决策记录——用户如何登录：以事实形式呈现的背景、可选方案、决策及其理由、需要长期承担的后果，以及何时重新审视

ADR 的价值在几个月后才最明显，比如有人问为什么身份项目之后聊天记录消失了，或者提议接入 Microsoft 365 数据时。答案，以及重新审视该决策的条件，早已白纸黑字写好。

流量如何从 A 到达 B？

接下来，梳理每一条网络路径。先介绍几个基础概念：

  • Virtual Private Cloud（VPC）网络是 Google Cloud 内部的私有网络。其中的资源通过内部 IP 地址相互通信。
  • Cloud VPN 和 Cloud Interconnect 通过加密隧道或专用链路，将公司的办公室或数据中心连接到其 VPC。
  • Private Service Connect（PSC）让你可以通过自己 VPC 中的内部 IP 地址访问 Google API 或其他网络中的服务，因此流量无需经过公共互联网。
  • VPC Service Controls 围绕项目和 Google 服务绘制一个服务边界，以降低数据外泄（数据被有意或无意地复制出去）的风险。

这是 Acme 的设计：

Acme 设计中的网络路径：用户通过 Private Service Connect 端点经企业网络访问 Gemini Enterprise，一个 VPC Service Controls 边界环绕着 Google Cloud 项目，Agent 通过接入 Acme VPC 的 Private Service Connect 接口私有地访问 Databricks

需要达成一致的有三条路径：

  • Gemini Enterprise 的用户。 默认情况下，用户通过公共互联网访问 Gemini Enterprise，并且需要进行身份验证。Gemini Enterprise 文档介绍了私有 UI 访问：用户通过 Cloud VPN 或 Cloud Interconnect 连接到 PSC 端点，内部 DNS 将 Gemini Enterprise 域名解析为该端点的 IP 地址。
  • 边界。 要使用 VPC Service Controls 保护 Gemini Enterprise 应用，你需要将其项目添加到边界中，并限制 Discovery Engine API（discoveryengine.googleapis.com）。此后，该 API 无法从公共互联网访问，除入站规则允许的情况外，用户界面将被阻止，并且在管理员更新相关组织政策约束之前，无法创建新的数据存储。文档建议先使用试运行模式，它会记录边界本会阻止的内容，但并不实际阻止。
  • 访问私有数据的 Agent。 运行在 Agent Runtime 上的 Agent 位于 Google 托管的网络中，无法访问你的 VPC。Private Service Connect 接口将其连接到你项目中的网络附件，使其流量可以访问私有服务。文档列出了容易让人踩坑的细节：网络附件需要至少 /28 的子网，并且在 VPC Service Controls 边界内，Agent 完全无法访问互联网，除非你构建出站路径，例如在你的 VPC 中配置带 Cloud NAT 的代理。另一方面，Google Cloud 上的 Databricks 也支持 Private Service Connect，其文档指出，启用私有连接本身并不会阻止对工作区的公共访问。

这张图中的每一个箭头都属于网络团队或 Databricks 管理员。我的看法：在第一周就画出这张图，在你编写任何 Agent 代码之前，并把它作为问题（而不是请求）带给网络团队。

适用哪些合规边界？

合规规则层层嵌套。我把它们画成一个个环，从你最无法更改的到你能完全掌控的：

合规边界层层嵌套：法律和合同包含 Acme 自己的政策，政策包含你配置的平台控制，平台控制包含 Agent 读取、存储和展示的内容；每个环都有不同的负责人签字确认

  • 法律和合同。 在英国，UK GDPR 要求对可能给个人带来高风险的处理进行数据保护影响评估（DPIA）。这个 Agent 是否需要评估由隐私团队决定，所以要在第一周就询问他们。行业规则和客户合同也属于同一个环。
  • Acme 的政策。 数据分类、保留期限和批准的区域。由数据所有者来执行这些政策。
  • 平台控制。 将策略付诸实施的设置：你选择的位置、客户管理的加密密钥（CMEK）、边界、审计日志和 Access Transparency（Google 员工对你的内容所执行操作的日志）。其文档列出了限制条件，包括数据存储和应用必须采用多区域而非全球配置才能被完全覆盖，这与上文的位置权衡相关联。CMEK 文档中有一个细节值得写进计划：CMEK 仅在密钥注册后才生效，在此之前创建的应用或连接器仍不受保护。请先设置好密钥。
  • Agent。 它读取、存储和展示什么，以及向谁展示。这是 FDE 负责的环节，通过工具、防护栏和评测来实现。

安全审查是如何进行的？

安全审查是客户在任何真实数据流动之前，检查设计是否符合其政策的环节。审查者通常需要相同的材料：架构图、数据映射、身份设计、网络路径和威胁模型（列出系统可能被攻击或滥用的各种方式，并为每种方式配备相应的控制措施）。对于 Agent，OWASP LLM 应用十大风险是一个很好的起点清单，因为它涵盖了提示注入等标准 Web 审查可能遗漏的风险。

将安全审查视为跨越三周的流程：FDE 发送设计包，安全团队提出威胁模型问题，数据所有者批准授权，平台团队以试运行方式执行边界，安全团队在试点前附带条件地签字批准

根据我的经验，有三件事能让审查更快：

  • 在任何人开口之前就发送设计包，如果客户有自己的模板，就用他们的模板。
  • 用可以指出的控制措施来回答威胁模型问题，例如只读身份、阻止写入的回调，以及 agents 系列中无法被绕过的防护栏里的人工审批步骤。
  • 把附带条件当作任务来对待。“批准，前提是日志接入我们的安全监控系统”就是一个“是”。把它加入计划并完成它。

第二点中阻止写入的回调足够简短，可以直接放进设计包。这是 agents 系列中的只读防护，它在每次 SQL 工具调用之前运行：

def sql_guard(tool, args: dict, tool_context) -> dict | None:
    """before_tool_callback: block anything that is not read-only."""
    if not tool.name.endswith("_sql"):
        return None
    refusal = guard_sql(args.get("sql") or "")
    if refusal:
        _log("sql_blocked", agent=tool_context.agent_name, tool=tool.name)
        return {"status": "blocked", "error": refusal}
    return None

root_agent = Agent(
    ...,
    before_tool_callback=[sql_guard, person_gate],
)

第一周你应该问什么？

这些是我在第一周会提出的问题，按负责人分组。每一个未得到回答的问题都是计划中的一个风险。

Data (data owners)
  - Where is each source stored, and in which region?
  - Where may it be processed by a model? Global, EU, UK only?
  - Which fields are personal or confidential?
Identity (IT identity team)
  - Which identity provider, and does it support OIDC or SAML 2.0?
  - Will any Microsoft 365 data be connected later?
  - Who approves a new OAuth app, and how long does it take?
Network (network and platform teams)
  - Is there a landing zone and a Shared VPC we must use?
  - Must users reach the app privately, over VPN or Interconnect?
  - Is there a VPC Service Controls perimeter, and who changes it?
  - How do services in the perimeter reach the internet, if at all?
Compliance (privacy, legal, security)
  - Does this need a DPIA? Who decides?
  - Are customer-managed keys required? Who holds them?
  - How long may conversations be kept?
Operations (platform team)
  - Who owns the system after handover, and who is on call?
  - How do changes reach production here?

设计评审清单上应该有什么？

在正式安全审查之前，我会按照这份清单自行进行设计评审。它足够简短，可以在一次会议中读完：

[ ] Every data source has an owner, a location and a sensitivity
[ ] Processing location agreed, not only storage location
[ ] Identity provider chosen and written up as a decision record
[ ] Each data source states its identity: agent or signed-in user
[ ] No credential ever reaches the model's context
[ ] Every network path drawn, with its owner
[ ] Perimeter tested in dry run; egress path agreed if needed
[ ] Encryption keys set up before apps and connectors are created
[ ] DPIA decision recorded by the privacy team
[ ] Retention set for chat history and memory
[ ] Audit logs routed to the customer's monitoring
[ ] Owner after handover named, with on-call and change process

试试看：检查设计中的缺口

这个脚本会根据所需的决策检查设计描述，并列出任何缺失或仍未解决的问题。它只需要 Python 3。将其保存为

check_design.py

:

REQUIRED = {
    "data": ["location_at_rest", "processing_location", "owner", "sensitivity", "read_as"],
    "identity": ["idp", "protocol", "user_identity_to_data", "agent_identity"],
    "network": ["user_path", "agent_egress", "perimeter", "dry_run_done"],
    "compliance": ["dpia_needed", "encryption", "retention", "audit_logs"],
    "operations": ["owner_after_handover", "on_call", "change_process"],
}

design = {
    "data": {"location_at_rest": "EU", "processing_location": "unknown",
             "owner": "supply data team", "sensitivity": "confidential",
             "read_as": "signed-in user"},
    "identity": {"idp": "corporate IdP", "protocol": "OIDC",
                 "user_identity_to_data": "OAuth, per user", "agent_identity": "Agent Identity"},
    "network": {"user_path": "PSC endpoint", "agent_egress": "PSC interface",
                "perimeter": "VPC Service Controls", "dry_run_done": False},
    "compliance": {"dpia_needed": "ask privacy team", "encryption": "CMEK"},
    "operations": {"owner_after_handover": "data platform team"},
}

UNSURE = {"unknown", "ask privacy team", "tbc", ""}
gaps = 0
for area, keys in REQUIRED.items():
    for key in keys:
        value = design.get(area, {}).get(key)
        if value is None:
            print(f"MISSING  {area}.{key}")
        elif value is False or str(value).lower() in UNSURE:
            print(f"OPEN     {area}.{key} = {value!r}")
        else:
            continue
        gaps += 1
print(f"{gaps} items to close before the design review")

然后尝试以下修改：

  • 为你熟悉的系统填写设计字典。未完成的项目就是你第一周要问的问题。
  • 为每个领域添加负责人，并在每个缺口旁打印下一步该问谁。这份清单就变成了一份计划。
  • 将 processing_location 设置为 "global"，并自问客户的政策是否允许。脚本无法回答这个问题；数据所有者可以。

可能出什么问题

  • 按你预期的环境来设计。 你假设是公共端点，结果发现是边界；假设是 Google 账号，结果发现是第三方身份提供商。画图之前先问清楚。
  • 太晚才提出变更请求。 新的 OAuth 应用、防火墙规则或边界变更，每一项都可能需要数周时间。在第一周就提出，甚至在设计定稿之前。
  • 只有存储位置而没有处理位置。 数据留在欧盟，但模型调用却发往别处。两者都要达成一致。
  • 不进行试运行就强制执行边界。 用户失去界面，数据存储创建停止，Agent 失去对外通路。先试运行并阅读日志。
  • 上线后更换身份提供商。 用户会丢失聊天记录。一次性做出决定，并记录下来。
  • 把安全评审当作最后的一道关卡。 作为从第一周就开始的对话，效果要好得多。

我现在会做什么

  • 为一个客户或内部系统绘制环境地图，并在每个框里写上负责人。
  • 为一个用例填写数据地图，包括处理位置和聊天记录。
  • 为身份提供商撰写一份决策记录，至少列出两个真实可选方案。
  • 追踪每条网络路径，并标记哪些路径会跨越边界。
  • 在设计会议之前，而不是会议期间，把第一周的问题发给各负责人。

我们学到了什么？

  • 环境是客户已经在运行的一切，其中每个框都有一个负责人，而获得其批准本身也有各自的交付周期。
  • 数据地图为每个数据源记录：存储和处理的位置、所有者是谁、敏感程度如何，以及哪个身份会读取它。
  • 身份有两个部分：用户如何通过身份提供商登录，以及 Agent 如何在不让模型看到令牌的情况下，将用户身份传递给数据。
  • 每条网络路径都需要一个负责人，VPC Service Controls 边界在强制执行之前应先以试运行模式运行。
  • 合规边界从法律和合同层层嵌套到 Agent 本身，每一层都有不同的签署人。
  • 安全评审作为从第一周就开始的对话会进行得更快，并在别人开口索要之前就把设计包发出去。

接下来是什么？

设计已达成一致，安全评审也有了设计包。在第 4 部分，数据准备与从零开始的 RAG中，我们将转向数据本身：文档如何通过解析、分块、嵌入和向量搜索变成答案，以及答案为什么会出错。
