FDE 探索：如何找到客户的真实问题

原标题：FDE discovery: how to find the client's real problem

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

文章以“自动化 PR 审查”的例子说明：客户提出的需求往往只是假设，真正的瓶颈可能是只有两名工程师有权审批。作者结合 Perspective AI 的五阶段需求探索方法（Scope、Interview、Synthesize、Validate、Spec）与 Learn Cursor、Palantir 面试资料，强调 FDE 应先画出一页纸的人员与系统地图、用基于事件的问题追问真实流程，并通过“交接测试”检验规格说明是否完整。

要点

  • 客户陈述的需求只是待验证的假设，而非真实问题。
  • PR 审查案例中，瓶颈是两名审批人过载，不是缺少自动化。
  • 需求探索分五阶段，每阶段有明确的完成标志。
  • 应追问最近一次实际交付流程中等待最久的环节。
  • Palantir 分解面试轮考察的正是这种提问与拆解能力。

把客户提出的每一个需求都当作待验证的假设；几个恰到好处的探索性问题，可以省下三周用来构建错误方案的时间。

简要概述

  • 客户提出的需求只是一个假设：要求自动化 PR 审查的请求，可能掩盖了只有两个人有审批权限的事实。
  • 探索分为五个阶段；当人员和系统能够画在一页地图上时，范围界定就完成了；当团队成员无需再开会就能动手构建时，规格定义就完成了。
  • 分解面试环节考察的正是这项能力：优秀的候选人会把前十分钟花在提问上。

设想客户给你发来一句话：“团队需要一个能自动审查 pull request 的工具。”你脑子里立刻浮现出解决方案：一个读取 diff、留下评论并给出风险评分的 Agent。三周后你演示成果，客户说看起来很棒，而从打开 PR 到合并的时间却和之前一模一样。

Learn Cursor 的 FDE 面试流程正是以这个场景开场的。客户的工程师交给你一个问题陈述，而按照该流程的说法，这几乎从来都不是真正的问题。

在那个例子里，瓶颈并不在于缺乏自动化。审查之所以要花四天，是因为只有两名资深工程师有审批权限，而他们俩都被工作压得喘不过气。

对于想转入 FDE 工作的开发者来说，这项能力正是区分 FDE 与单纯接单干活者的关键。你已经会写代码了。你需要学习的是如何把一个模糊的需求转化为客户和团队成员都相信方向正确的计划。

需求只是一个假设

Perspective AI 于 2026 年 7 月发布的 FDE 探索手册，从一个听起来有点直白的假设出发：客户说自己需要的，并不是他们真正需要的。这不是因为客户在撒谎。而是他们用自己熟悉的工具的语言，描述他们能想象出的解决方案，而不是描述工作究竟卡在哪里。

因此，“我们需要自动化 PR 审查”应该被理解为“客户相信自动化审查能让一切变快”。这是一个假设，你的首要任务就是验证它。如果假设成立，你就能更有信心地构建；如果假设不成立，你刚刚省下了三周时间。

哪个问题能扭转对问题的理解？

常见的错误是问客户“你想要哪些功能？”。这只会让他们复述最初的需求。Learn Cursor 提出的问题则反其道而行：请客户带你走一遍他们最近上线的变更，并指出它在哪个环节等待的时间最长。

这个问题之所以有效，是因为它把对话拉回到真实发生过的事情上，有日期、有真实的人。下面是一段假设性的对话，展示它是如何展开的：

FDE： 能带我走一遍你们团队上一次发布的改动吗？从打开 PR 到进入生产环境，它在哪个环节等待的时间最长？

客户： 大概是在评审环节。PR 打开后大约要等四天才会有人批准。

FDE： 这四天里是谁在负责批准？他们在等什么？

客户： 只有两位资深工程师能批准。他们还要负责值班和系统设计，所以手头总是积压着十几个 PR。

到这一步，问题已经变了。一个自动评论的 Agent 仍然会让 PR 停在那同两个人的队列里。更合理的方案也许是帮这两个人更快地评审，或者明确哪些类型的改动需要他们、哪些不需要，但你只有在与客户验证之后才能做出选择。

五个阶段，每个阶段都有一个完成的标志

一个好问题还不算方法。Perspective AI 的行动指南将需求探索分为五个连续阶段：界定范围（Scope）、访谈（Interview）、综合归纳（Synthesize）、验证（Validate）和规格说明（Spec）。每个阶段都有一个条件，告诉你何时可以进入下一阶段。

界定范围完成的标志是，你能在一张纸上画出涉及的人员和系统。在 PR 的例子里，这张纸上包括写代码的人、两位审批人、CI 系统和代码仓库。这个阶段以确定决策点收尾：系统将帮助谁采取什么行动。如果你说不出这句话，就还不具备访谈的条件。

访谈是指你使用上面那种基于事件的提问方式，与每天实际做这项工作的人交流，而不仅仅是提出请求的那个人。综合归纳是指把你听到的内容归类为机会并排序。很多人提到的瓶颈通常比一个人提出的抱怨更值得关注。

验证是指你回到客户的领域专家那里，确认排在清单最前面的机会确实是最值得构建的东西。手里有了排序结果，你会很想跳过这一步，而这恰恰是它应该保留的原因。最后，规格说明以“交接测试”来评判：拿到规格说明的队友必须能够在不再召开任何会议的情况下完成构建。

导致需求探索失败的错误

第一个也是最常见的问题是直接跳到解决方案。techinterview.org 对 FDE 面试的分析恰好描述了这一点：候选人听到问题后就直接冲向解决方案。在实际工作中，这个错误会变成一个没人使用的精美演示。

第二个是只与提出请求的人交流。提交工单的工程师看到的是症状；而那两位审批人才知道队列为什么这么长。如果你的一页地图上只有一个名字，那你几乎肯定遗漏了相关人员。

第三种情况是写了一份规格说明，还需要附带一场解释会议。当同事需要通过会议才能理解规格说明时，说明决策还留在你的脑子里。回头检查一下，你是否写下了决策点，以及你为什么选择这个方案。

面试考察的正是这项技能

这不仅是入职后才需要的技能。根据 techinterview.org 的介绍，Palantir 的拆解环节考察的是将模糊的现实世界难题拆分成更小的部分，然后提出解决方案的能力。优秀的候选人会先花十分钟提问。

所以在面试练习时，要训练自己克制住立刻勾勒架构的冲动。先问谁在使用它、工作在哪里卡住、哪个决策悬而未决，然后在提出任何方案之前，把人员和系统的关系图大声说出来。

在简历上，与其写“构建了工具 X”，不如用一行字描述一次你发现原始需求是错的，以及你如何调整方向的经历。这样一行字恰好展示了拆解环节所考察的技能。

下次收到一行字的需求时，先别打开编辑器；先拿出一张白纸。如果你还不能在上面画出谁在等待谁，说明你仍然不知道自己需要构建什么。
