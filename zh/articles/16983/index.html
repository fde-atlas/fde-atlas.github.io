FDE 如何根据现场笔记构建本体 | AI 可遍历的名词与动词词典

原标题：How an FDE Builds an Ontology from Field Notes | A Dictionary of Nouns and Verbs an AI Can Traverse

TIMEWELL · 2026-09-15 · 约 10 分钟读完

摘要

TIMEWELL 的 FDE 系列第六篇，讲如何把现场访谈与观察得到的“名词动词词典”整理成本体（ontology），供 AI Agent 遍历和行动。文章给出从访谈记录中提取名词、动词、关系、状态、例外五类要素的方法，用图结构承载，并与合同开发中的数据建模对比：本体把动词和例外与名词写在一起、每周更新、模式沉淀进产品标准 schema、例外作为客户配置，且所有权交给客户现场。作者以自家产品 ZEROCK 为例，认为 FDE 离场后客户能自行维护词典才是完成条件。

要点

  • 本体是让 AI Agent 可行动的名词动词词典，源自 Gruber 1993 年定义与 Palantir 实践。
  • 从访谈与观察记录提取名词、动词、关系、状态、例外五类要素，例外最易丢失也最关键。
  • 词典以图结构组织：名词为节点、关系为边，Agent 通过遍历图来回答和执行。
  • 与合同开发数据建模不同：动词例外与名词同录、每周更新、模式进产品 schema、分支作客户配置。
  • 词典所有权须交给客户现场，FDE 不再被需要才算完成。

您好，我是 TIMEWELL 的滨本隆太。

这是我们的 FDE 实践系列的第六篇文章。前五篇介绍了从现场收集信息的技能。访谈记下名词和动词，观察验证它们，民族志加深其含义，KJ 法将它们结构化，视频为其添加数字。而“名词和动词词典”出现在上述每一篇文章中。这次我想解释一下这本词典如何被转化为 AI 可以遍历的形式。

在早前一篇关于 FDE 与 AI 陪伴的区别的文章中，我写道，Agent 在学会名词和动词之前无法运行。要让一个 Agent“分配订单”，它必须以机器可读的形式掌握：在这家公司里订单是什么、分配意味着什么、分配之前和之后发生什么。这种形式就是本体论。这个词听起来令人生畏，但它所做的就是用公司自己的语言划分世界，并把它交给机器。如果您想先检查自己的业务词汇在多大程度上已经达到了可以交给 AI 的形式，请进行 AI 素养检查。

什么是本体论：用公司自己的语言划分世界

这个词源自哲学，但在信息科学领域，Tom Gruber 于 1993 年将其定义为“对概念化的显式规范”：对某个领域中存在什么以及这些事物之间如何关联的可共享、显式的书面描述。1 简而言之，就是对一个领域的名词、动词和关系的无歧义词典。

Palantir 将这一理念置于其企业产品的核心。在其文档中，本体论是位于集成数据之上的一层，将数据与其现实世界的对应物连接起来，由对象类型、属性、链接、操作类型和函数构成。2 对象是名词，链接是关系，操作是动词。一位在 Palantir 担任了八年 FDE 的人士将“本体论”列为公司的老内部术语之一，3其结构清晰可见：当 FDE 将在现场学到的业务含义带回产品时，本体论就是它的落脚点。

为什么在 AI Agent 时代需要它？因为 Agent 会行动。一个只做文本摘要的 AI 可以基于公司词汇的模糊定义运行。但一个“分配待审批订单并发出发货指令”的 Agent，如果不知道“待审批”是什么意思、什么是分配、发货指令需要谁的授权，就无法行动。如果它强行行动，就会错误地分配。名词和动词的定义是 Agent 行动的基础。

从访谈记录到词典：提取名词、动词、关系、状态和异常

以下是操作流程。素材就是前五篇文章中收集的一切：访谈记录、五栏观察记录、三层民族志笔记、KJ 分组名称以及视频计数。从中提取五样东西。

提取什么它是什么访谈记录中的例子如何写入词典
名词这家公司使用的物品名称“订单一来，我们先查库存”订单、库存
动词人们对名词做的事“我们把库存分配出去，标记为已预留”分配（把库存分给订单）、预留（口头预留销售）
关系名词之间如何连接“每个订单都附带一个出货”一个订单有一个或多个出货
状态名词可能处于的阶段“待审批的东西我们一律不碰”订单状态：已接收、待审批、已审批、已出货
例外与常规不同的路径及其条件“紧急的时候由副主任盖章”审批人是科长，但紧急类除外，此时由副主任审批

名词要用公司自己的说法，不要翻译成系统术语。如果“分配”和“预留”含义不同，它们就是两个动词。这正是 KJ 分组名称发挥作用的地方。分组名称“实际上审批分两步：副主任判断，科长盖章”就成了动词“审批”的定义。词典条目写作：“审批是指副主任判断、科长盖章。”把两个步骤写进词典后，AI Agent 就不会在第一步之后停下来。

关系和状态要通过观察和视频来确认。访谈记录说每个订单都附带出货，但屏幕录像可能显示有些订单被标记为完成却没有出货。这时关系就要修正为“订单附带出货，样品出货除外”。所说与所见之间的差距能提升词典的精确度。

例外最重要，也最容易丢失。“紧急的时候由副主任盖章”不会出现在功能清单上，但会出现在词典里。AI Agent 是把紧急订单搁置等待科长，还是转给副主任，就取决于这一句话。

在提取环节我们使用 AI。它阅读访谈记录和观察记录，并列出全部五个类别的候选词。机器在提出候选方面更快：几分钟内就能从几百个片段中提出几十个名词和动词。但需要人来修正它们，因为同一个词在不同部门含义不同。销售部门的“预留”和仓库的“预留”是不同的动作，机器提取会把它们合并。词典则分别写入“预留（销售）”和“预留（仓库）”，并附上根据上下文判断所指的规则。只有通过民族志加深了对词义理解的人才能做出这种区分。

让词典可被遍历：图与 Agent

词典建立之后，会被转换成机器可以遍历的形式：一张图，名词作为节点，关系作为边。状态是节点的属性，动词是对节点允许执行的操作，例外则是这些操作上的条件。

采用这种形式的原因在于，AI Agent 不只是回答问题；它们要遍历并执行操作。要回答“这个订单能否发货？”，Agent 必须从订单节点出发，经过它的状态（是否已批准？）、它的关系（库存是否已分配？）以及它的例外（紧急类别是否只需要主管助理审批？）。在一堆文档中搜索无法完成这样的遍历。将大语言模型与知识图谱相结合来回答跨越整个语料库的问题，在 2024 年被系统化为 GraphRAG。4 我们的 ZEROCK 是一款以这种形式保存企业知识、供 Agent 遍历的产品，而在现场构建的词典则直接进入产品的结构中。

这与 a16z 在 2026 年 1 月关于可复用原语的文章相呼应。那篇文章将真正的 FDE 模式描述为建立在可复用原语、数据模型和工作流组件之上，而不是为每个客户开发全新功能。5 本体是这些原语中最基础的部分。“订单有状态”“审批可以有多个阶段”“例外按类别分支”：这些结构在不同公司之间不会改变。改变的是状态的名称、阶段的数量和类别的划分。因此结构存在于产品的标准模式（schema）中，而名称、阶段和类别则是每个客户的配置。在三家客户那里看到的“审批是两阶段的”会成为产品模式；“在这家公司，紧急类别要交给主管助理”则成为配置。KJ 文章中“模式或分支”的归类方式，正是落在这里，落在产品的结构中。

关于 Agent 运行方式的细节，请参见关于上下文工程的文章。在传递给 Agent 的所有上下文中，词典是变化最少、但一旦出错危害最大的部分。

它与合同开发中的数据建模有何不同

合同开发中也有数据建模环节：识别实体、定义关系、设计数据库。把名词和关系写出来看起来是一样的。区别在这里。

维度数据建模（合同开发）FDE 本体
目的设计系统的数据库为 AI Agent 提供行动依据
来源需求文档车间现场的话语、观察、视频
动词与例外单独写成功能规格说明与名词一起写，并附带条件
更新在设计阶段冻结每周更新，依据对工作产物的反馈
归属客户的数据库产品标准 schema 中的模式，分支作为客户扩展
所有者开发方客户方，以便 FDE 离开后仍可更新

最大的区别在于对动词和例外的处理。数据建模只处理名词和关系；动词被写进单独的功能规格说明，例外则最终归入备注中的“其他”。本体则把动词和例外与名词写在同一处，并附带条件。对 Agent 来说，动词“审批”和例外“紧急件交给副经理”与名词“订单”同样重要。

另一个区别是所有者。合同数据模型的所有者是开发方，变更属于维护合同。FDE 本体则把所有者放在客户一方。当现场人员因为紧急类别的审批人变更而编辑词典时，Agent 的行为随之改变。一旦达到这种状态，FDE 就可以离开。AWS 于 2026 年 6 月推出的 FDE 组织，把客户在项目结束时能够自主运营作为设计的核心；6 对我们而言，能够自主运营的条件是词典的所有者在现场。

现场：每周更新词典并反映到工作产物中

流程每周执行一次。周一至周四在现场收集。周五用 KJ 法构建分组，从组名中提取五个要点，并更新词典。下周一让 Agent 读取更新后的词典并产出工作产物。问现场人员“有什么不同？”，然后修正词典。这个循环为一周。

词典是带版本管理的。“审批”的定义从第一周的“科长盖章”，到第二周的“副经理判断、科长盖章”，再到第三周的“紧急类别：仅副经理”，这种演变是正常的。保留各版本可以在事后追溯 Agent 行为为何改变。当对方说“它的行为和上周不一样”时，展示词典的 diff 就能结束解释。

然后确定词典的所有者。我们的工程师在现场时会持续更新它，但在结束之前，我们会把它交给现场的人。交接的内容是提取五类要素的流程、按部门区分含义的方法，以及版本管理的方式。当对方能够自行编辑“紧急类别的审批人从副经理改为主管”这样的条目时，就不再需要 FDE 了。不再被需要，就是这一步的完成条件。

我们做什么，以及止步于何处

坦白说，词典是活的东西，永远不会完成。公司的用语会变，组织会变，例外会不断增多。我们带回家的词典在半年后过时，正是因为没有把所有者留在现场。所以交接才是完成条件。

这是有局限的。AI 提取只能做到提出候选。“同一个词，不同含义”和“不同的词，同一个含义”是机器看不见的。当“预留”在访谈记录中出现四十次时，有多少次指销售、有多少次指仓库，要由在场的人来区分。而且词典的质量不会超过所收集片段的质量。如果访谈只发生在会议室里，词典就是“应有流程”的词典，而 AI Agent 会在“实际流程”上卡住。这也是前五篇文章的技能必须先行的一个原因。

最后，坦率地说明与我们产品的关系。我们的 ZEROCK 将这本词典作为结构来承载。所以我们的前沿部署工程师在构建词典的同时也在培育产品。这不是利益冲突，这正是 FDE 模式本身。如果所学不能回馈到产品中，那就只是外包工作。但词典的所有者是客户，其内容也属于客户。回馈到产品中的是结构，而不是这家公司自己的名词和动词。

总结

在现场收集的名词和动词词典，本身并不能被 AI Agent 当作词典使用。要从访谈记录和观察记录中提取名词、动词、关系、状态和例外，把它们组织成图的形式，让 AI Agent 在其中遍历。这就是本体论：用公司自己的语言切分世界，并把它交给机器。

它与合同制数据建模的不同之处在于：把动词和例外连同条件一起写入、每周更新、在保留分支作为客户扩展的同时把模式回馈到产品的标准 schema 中，并把所有者放在客户一侧。不再需要 FDE，就是完成条件。

如果您希望把企业的业务词汇变成 AI Agent 可以遍历的形式，或者正在寻找能把车间词典转化为产品结构的合作伙伴，请了解 WARP 计划 或与我们联系。下一篇文章将把所有这些技能浓缩进一周：一个 FDE 的一周，从第一天到周五。
