Palantir Foundry导入案例分行业解析｜成果与FDE的作用

原标题：Palantir Foundry導入事例を業界別に解説｜成果とFDEの役割

FDE総研 · 2026-10-20 · 约 10 分钟读完

摘要

本文基于公开资料，按行业梳理 Palantir Foundry 的导入案例，包括 Airbus、BP、NHS England 与日本的 SOMPO 集团，并说明 FDE 在其中的角色。文章指出各案例的共同点：不止于数据整合，而是通过 Ontology 将业务对象建模，并构建现场实际使用的运营应用，把决策结果写回业务流程。作者还介绍了 Palantir 内部 Delta（前沿部署软件工程师）与 Echo（部署策略师）的分工、导入各阶段的工作内容，以及日本企业导入时需注意的内制比率、数据存放、成本与现场参与等论点。

要点

  • Airbus、BP、NHS England、SOMPO 为公开可查的代表性案例。
  • 共同模式：用 Ontology 建模业务对象，并构建现场运营应用。
  • Palantir 内部由 Delta 负责技术实现，Echo 负责业务设计。
  • FDE 工作随阶段变化：从课题探索到应用构建再到运营移交。
  • 建议从小型用例起步，优先选择决策者明确、成果可量化的业务。

Palantir Foundry 的导入案例遍布航空、能源、医疗与公共、制造与供应链、保险与护理等众多行业。它们的共同点是：用“Ontology（业务对象模型）”把分散的数据连接起来，并落实到现场决策。本文仅基于公开的发布和报道所能确认的范围，梳理各行业的使用方式以及 FDE（Forward Deployed Engineer）的角色。

Palantir Foundry 的导入案例中有哪些企业？

Foundry 被航空领域的 Airbus、能源领域的 BP、英国的 NHS England 等大型组织所使用。下面以公开信息可确认的案例为中心进行介绍。

公开信息可确认的代表性导入企业有哪些？

代表案例包括 Airbus、BP、NHS England，以及日本的 SOMPO 集团。这些企业或公共机构都官方发布过与 Palantir 合作的消息。

企业/组织行业公开的主要举措时间（以公布为准）
Airbus航空基于 Palantir 技术构建航空数据平台“Skywise”，并向航空公司提供2017 年巴黎航展上发布
BP能源长期用作整合运营数据的平台，并延长了包含 AIP（Palantir AI Platform）在内的战略合作合同2024 年公布多年期合同
NHS England医疗与公共由 Palantir 牵头的联合体中标，作为 Federated Data Platform（FDP）的基础2023 年 11 月公布合同签订
SOMPO 控股保险与护理成立合资公司 Palantir Technologies Japan，推进护理等领域的数据应用2019 年成立合资公司

数字和合同范围均为发布时点的内容。最新情况请通过各公司的新闻稿和 Palantir 的 IR 资料（Form 10-K、财报说明）确认。

导入案例有哪些共同模式？

共同点是“不止步于数据整合，而是深入构建现场的业务应用”。这与引入 BI 工具的项目不同。

  • 整合分散的数据：通过管道汇集 ERP、传感器、业务系统、Excel 等
  • 用 Ontology 建模：重新定义为“机体”“设备”“患者”“订单”等业务对象
  • 构建运营应用：通过 Workshop 等工具为现场负责人打造日常使用的界面和操作
  • 将决策写回系统：把判断结果反映到原系统和业务流程中

阅读公开案例可以发现，被作为成果提及的并不是“做出了仪表盘”，而是“计划、维护和分配的判断变快了”。Foundry 与其说是 BI 产品，不如说是作为构建业务应用的平台而被选用。

按行业来看，Foundry 解决了什么问题？

各行业的课题各不相同，但 Foundry 解决的是“跨部门、跨系统决策迟缓”的问题。下面按行业梳理。

制造、航空、能源领域用它来做什么？

在重资产行业中，主要用途是将设备和机体的运行数据与维护、计划业务相结合。预测性维护和供应链可视化是其代表。

行业典型课题用 Foundry 的解决方式（常见模式）
航空（Airbus 等）各机体的运营、维护数据分散在航空公司、制造商和零部件供应商之间像 Skywise 那样跨行业共享数据，用于维护计划和零部件调配
能源（BP 等）油田、工厂的传感器数据与运营决策相互割裂将设备建模为数字孪生，用于运营优化和安全管理
制造与汽车发现零部件缺货或需求波动的时机滞后用 Ontology 连接采购、库存和生产计划，快速确定影响范围

从现场实务人员的角度看，在这个领域真正起作用的，与其说是高级算法，不如说是“所有部门用同一个 ID 查看相同的零部件、相同的设备”这种状态。主数据治理耗费了超出预期的工时——这类说法在数据整合项目中很常见，并不限于 Foundry。

医疗、公共、金融领域如何使用？

在医疗和公共领域，常见用途是在遵守严格访问控制的前提下，对病床、人员和物资的分配进行决策。在金融和保险领域，则以风险分析和欺诈检测为主。

  • 医疗（NHS England 等）：NHS 的 FDP 是一个连接各医院数据、支撑手术等待名单和病床管理的构想。关于采用 Palantir，围绕患者数据的处理在英国国内也曾引发争议。
  • 公共与行政：Palantir 最初以面向政府的 Gotham 闻名。Foundry 也被用于行政数据整合，其权限管理和审计日志的精细程度广受好评。
  • 金融与保险：通过连接客户、交易和保险理赔数据，用于欺诈检测和承保风险分析。

行业监管越严格，对数据血缘（Lineage）和权限设计的要求就越高。在这个环节，稳妥的做法是在技术选型阶段尽早让法务和信息安全部门参与进来。

日本企业导入 Palantir Foundry 的案例有哪些？

日本的代表性案例是SOMPO控股公司。该公司于2019年与Palantir成立合资公司，在护理和保险领域推进应用。

SOMPO与Palantir Technologies Japan的举措是什么？

SOMPO通过合资公司深度参与Palantir在日本国内的业务拓展，并在集团旗下的护理事业中推进数据应用。这是日本最引人注目的案例。

项目公开的内容
合资公司成立2019年，SOMPO控股与Palantir成立Palantir Technologies Japan
出资SOMPO于2020年宣布对Palantir出资
主要应用领域护理现场的数据应用（“真实数据平台”构想）、保险业务
定位集团内部应用，以及面向国内企业和自治体拓展的窗口

护理是一个记录容易分散在纸质文件和各个独立系统中的领域。汇集数据、使护理质量和工作负担可视化这一举措，也与日本的社会课题相契合。具体的成果数据，建议通过SOMPO的整合报告和新闻发布稿进行确认。

日本企业引入时的议题是什么？

在日本企业中，完全依赖供应商的体制和数据存放地的限制常常成为讨论焦点。Foundry的效果在很大程度上取决于公司内部是否有能够运营的人才。

  • 自研比例：如果全部外包给SIer，Ontology的设计意图就不会留在公司内部
  • 数据存放地：首先确认是否需要存放在国内区域、是否包含个人信息
  • 成本预估：从PoC阶段开始就估算许可证和计算资源的费用结构
  • 现场参与：建立业务部门能够自行修改界面的体制，更容易落地扎根

日本公开的案例还不多。如果考虑引入，比较现实的做法是通过Palantir Technologies Japan或实施合作伙伴，咨询能否展示未公开的参考案例。

在Foundry导入中，FDE承担什么角色？

FDE是一种深入客户现场、从业务课题的识别到数据整合、应用构建直至落地扎根全程负责的职位。它实质上决定了Foundry导入案例能否取得成果。

Palantir中“Delta”和“Echo”的分工是什么？

在Palantir，相当于FDE的职位在公司内部被称为“Delta”，主要负责技术实现。与客户的沟通和业务设计则由“Echo”（部署策略师）承担。这两个角色组队进入现场。

角色Palantir内部称呼主要职责所需技能
Forward Deployed Software EngineerDelta构建数据管道、Ontology设计、应用实现Python／SQL／TypeScript、数据建模
Deployment StrategistEcho课题定义、利益相关者协调、成果定义业务理解、引导协调、假设构建
产品工程师（总部侧）开发产品功能、反映现场反馈软件设计、平台开发

FDE的特点在于，在产品团队和客户之间来回穿梭，以“现场能否实际使用”为标准进行判断。由于这类职位名称和团队构成因企业而异，在Palantir以外的FDE招聘中，需要逐一确认职责范围。

在导入的各个阶段，FDE做什么？

FDE的工作随导入阶段发生很大变化。初期以课题探索和数据连接为主，后期以运营移交和横向推广为中心。

  • 探索（数天至数周）：在现场进行访谈，将能产生价值的业务聚焦到一个
  • 连接：与源系统对接，构建最小限度的数据管道和Ontology
  • 构建：制作现场人员使用的应用，观察使用情况并以短周期进行修改
  • 移交：将运营和改进的技能传授给客户方的工程师和业务负责人
  • 扩展：将用例推广到相邻的业务和部门

从从业者的角度来看，FDE除了技术能力之外，还需要具备能够清晰表述“由谁、在多快的时间内做出哪个决策”的能力。在职业发展方面，可以说这是一个同时具备数据工程和咨询经验更容易受到好评的职位。

成功导入Foundry的推进方法是什么？

容易成功的推进方法是“从小处着手，先证明现场的判断发生了变化，然后再推广”。据称，先构建全公司数据基础的做法容易失败。

如何选择最初的用例？

选择最初的用例，常规做法是选择决策者明确、成果可以用数字衡量的业务。比起数据是否齐全，更应优先考虑业务上的痛点是否足够大。

选择标准好的例子应避免的例子
决策者工厂厂长、物流负责人等，可以确定做出判断的负责人需要多个部门合议
成果的衡量方式缺货件数、计划所需时间、开工率“数据应用程度”等抽象指标
频率每天至每周进行的判断每年一次的计划工作
数据主要数据已存在于现有系统中以新装传感器为前提

Palantir通过AIP的导入，推出了通过为期数天的“AIP Bootcamp”用客户数据在短时间内构建用例的方法。缩短初期验证周期的思路，同样适用于整个Foundry导入过程。

避免失败的检查要点是什么？

失败大多不是技术问题，而是源于缺乏负责人和运营移交的延误。在导入前确定体制和退出方案非常重要。

  • 任命业务负责人：不是IT部门，而是在业务侧设置负责人
  • 确保内部FDE人才：培养在Palantir或合作伙伴撤出后仍能进行改进的人才
  • 治理设计：从初期开始就将权限、审计、数据血缘纳入设计
  • 投入产出比评审：每季度重新审视哪些用例在产生价值
  • 锁定效应评估：确认 Ontology 和业务逻辑能在多大程度上迁移到外部

对于对 FDE 感兴趣的工程师来说，这些检查要点本身就是一份“现场所需工作”的清单。对于考虑引入的企业而言，这也是描绘应在公司内部培养的人才形象的线索。
