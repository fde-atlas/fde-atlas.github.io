能力 1：案例研究精通（占面试的 30%）

它是什么： 面对一个模糊的真实企业问题，在 45-60 分钟内将其拆解为可执行的步骤。没有唯一正确答案。

示例题目（Palantir）：

“某医院系统希望利用 AI 降低再入院率。他们拥有 5 家医院、10,000 张床位，再入院率为 18%。你会构建什么？”

面试官考察的内容：

  • Clarifying questions (first 5-10 minutes)
    • 你是否会询问数据可用性？
    • 你是否理解成功指标？
    • 你是否会探询约束条件（预算、时间线、合规性）？
  • Problem decomposition (next 15-20 minutes)
    • 你能否将问题拆解为子问题？
    • 你是否会进行优先级排序（MVP 与长期方案）？
    • 你是否能识别依赖关系？
  • Solution design (next 15-20 minutes)
    • 你的方案在技术上是否可行？
    • 你是否考虑边界情况？
    • 你是否思考可扩展性？
  • Communication (throughout)
    • 你的表达是否有条理（而非漫无边际）？
    • 当面试官质疑你的假设时，你能否灵活调整？
    • 你是否边思考边说出想法？

必须掌握的框架：CIRCLES

C - 理解情境（提出澄清性问题）I - 识别客户（谁受益？）R - 复述问题（用自己的话重述）C - 通过优先级筛选（MVP 与锦上添花）L - 列出解决方案（3-5 种方案，各自优缺点）E - 评估权衡（技术、商业、时间线）S - 总结建议（选定一个并说明理由）

备考策略：

  • 研读 10 个以上真实案例研究（见下方案例研究库）
  • 录下自己解题的过程（注意口头禅、结构是否清晰）
  • 计时练习（严格 45 分钟）
  • 向通过 FDE 面试的人寻求反馈

能力 2：Python 编程（占面试的 25%）

它是什么： Leetcode 中等/困难题，但侧重生产级代码质量（错误处理、可读性、测试）。

与 SWE 面试相比的难度： 算法复杂度相近，但面试官更关注：

  • 你写的代码能否让面向客户的工程师维护？
  • 你是否优雅地处理错误（客户会遇到边界情况）？
  • 你的代码是否易读（你要培训的是客户，而不仅仅是工程师）？

示例题目（Google FDE）：

“编写一个函数，接收视频文件路径，返回检测到的所有人脸列表及其时间戳。假设你可以调用一个人脸检测 API。处理错误情况（文件不存在、视频损坏、API 失败）。”

不只是： “编写一个检测人脸的函数。”

这道题的 FDE 特色在于：

  • 错误处理（文件不存在怎么办？API 超时怎么办？）
  • 生产环境思维（日志、重试逻辑、优雅降级）
  • 客户影响（如果失败，客户的部署就会中断）

备考策略：

  • Grind Leetcode (100-150 problems)
    • 重点：中等题（70%），困难题（30%）
    • 类别：数组、哈希表、树、图、动态规划
    • 目标：中等题 25 分钟内解决，困难题 45 分钟内解决
  • Practice production code quality
    • 给每道 LeetCode 题的解法加上错误处理
    • 编写文档字符串和注释
    • 自问：“面向客户的工程师能看懂这段代码吗？”
  • Live coding practice
    • 使用 Pramp 或 Interviewing.io（10 次以上模拟面试）
    • 练习边想边说（沉默写代码在 FDE 面试中行不通）
    • 适应被打断（面试官会在你写代码中途提问）

学习资源：

  • LeetCode（显而易见）
  • Grokking the Coding Interview（基于模式的方法）
  • Cracking the Coding Interview（用于夯实基础）

能力 3：系统设计（占面试的 20%）

是什么： 设计一个可扩展的系统（API、数据管道、AI 服务）来解决客户问题。

FDE 特色： 与 SWE 系统设计（侧重规模）不同，FDE 系统设计侧重于：

  • 客户集成： 该系统如何融入现有工作流程？
  • 部署灵活性： 云端、私有云、本地部署选项
  • 故障模式： 系统出问题时会怎样？（客户比内部用户更难宽容）
  • AI 组件： RAG 管道、Agent 系统、实时推理

示例题目（Anthropic）：

“设计一个系统，让客户能够使用自然语言查询搜索 1000 万个视频文件。查询应在 2 秒内返回结果。支持云端和本地部署。”

需要涵盖的内容：

  • Requirements clarification (5 minutes)
    • 数据规模（1000 万个视频，平均每个 10 分钟 ≈ 100TB）
    • 查询量（1000 QPS？10 QPS？）
    • 延迟要求（严格小于 2 秒）
    • 部署约束（云端 vs 本地部署 = 不同的架构）
  • High-level architecture (10 minutes)
    • 摄取管道（视频 → 嵌入向量）
    • 向量数据库（Pinecone、Weaviate 或自托管）
    • 查询服务（API 层）
    • 检索 + 重排序（RAG 模式）
  • Deep dives (20 minutes)
    • 如何生成视频嵌入向量（CLIP、ImageBind）？
    • 如何处理 100TB 存储（云 vs 本地部署的权衡）？
    • 如何实现小于 2 秒的查询（索引、缓存、近似方法）？
    • 如何进行本地部署（Docker、Kubernetes、隔离网络）？
  • Trade-offs & failure modes (5 minutes)
    • 向量数据库宕机怎么办？（回退到关键词搜索）
    • 嵌入生成太慢怎么办？（异步处理、队列）
    • 查询有歧义怎么办？（澄清界面、查询扩展）

备考策略：

  • Study AI system design patterns
    • RAG（检索增强生成）
    • Agentic 工作流（LangGraph、CrewAI）
    • 实时推理（模型服务、批处理）
    • 评测流水线（离线评测、在线监控）
  • Practice 15-20 designs
    • 5 个 RAG 系统（搜索、问答、文档对话）
    • 5 个 Agentic 系统（客户支持、数据分析、代码生成）
    • 5 个数据流水线（视频处理、实时分析、批处理 ETL）
    • 5 个 API 设计（REST、GraphQL、webhooks）
  • Focus on deployment options
    • 云（AWS、GCP、Azure）
    • 私有云（客户 VPC、数据驻留）
    • 本地部署（隔离网络、合规、Kubernetes）

学习资源：

  • System Design Interview（Alex Xu）— 第 1 卷和第 2 卷
  • Designing Data-Intensive Applications（Martin Kleppmann）
  • System Design Primer（GitHub）

能力 4：AI/ML 深度（占面试的 15%）

它是什么： 对生产级 AI 系统的深入理解——RAG、Agent、评测、可观测性——而非研究或模型训练。

FDE 特有的重点： 面向客户部署的应用 AI，而非研究：

  • 你能否构建一个能在生产环境中运行的 RAG 流水线？
  • 你知道如何评估 AI 输出质量吗？
  • 你能调试 Agent 失败的原因吗？
  • 你了解 AI 可观测性（LangSmith、W&B）吗？

需要掌握的主题：

1. RAG（检索增强生成）

核心知识：

  • 向量数据库（Pinecone、Weaviate、ChromaDB）
  • 嵌入模型（OpenAI、Cohere、开源）
  • 检索策略（语义、混合、重排序）
  • 分块策略（固定、语义、递归）
  • RAG 评测（检索准确率、回答质量）

你会遇到的面试问题：

  • “你会如何将 RAG 准确率从 60% 提升到 80%？”
  • “客户的 RAG 返回了不相关的结果。你如何调试？”
  • “为一个包含 1000 万文档的系统设计 RAG，且查询时间小于 2 秒。”

2. Agentic 系统

核心知识：

  • Agent 框架（LangGraph、CrewAI、Autogen）
  • 工具调用 / 函数调用
  • 多 Agent 编排
  • Agent 评测（任务成功率、成本）

面试问题：

  • “设计一个分析客户支持工单并路由到正确团队的 Agent。”
  • “你会如何评估一个 Agent 的表现？”
  • “客户的 Agent 发起了太多 API 调用。你如何优化？”

3. 评测与可观测性

核心知识：

  • 离线评测（测试集、指标、基准）
  • 在线评测（A/B 测试、人工反馈）
  • AI 可观测性工具（LangSmith、Weights & Biases、Arize）
  • 调试 AI 故障（提示词日志、追踪分析）

面试问题：

  • “客户说 AI 给出了错误的答案。你会如何调查？”
  • “为一个客户支持 AI 设计一套评测框架。”
  • “你会如何对两种不同的 RAG 检索策略进行 A/B 测试？”

备考策略：

  • Build 3-5 projects
    • RAG 系统（文档问答）
    • Agent 工作流（研究助手、数据分析师）
    • 评测流水线（衡量准确率、成本、延迟）
  • Deep dive on production challenges
    • 学习 LangChain 生产环境指南
    • 阅读 OpenAI Evals 框架
    • 理解 AI 可观测性模式
  • Practice debugging scenarios
    • “RAG 返回不相关的结果”（检查嵌入质量、检索策略）
    • “Agent 陷入循环”（添加熔断机制、状态管理）
    • “评测显示准确率只有 40%”（改进提示词、增加示例、使用更好的模型）

能力 5：SQL（占面试的 5%）

是什么： 用于数据分析的复杂 SQL 查询（CTE、窗口函数、连接）。

FDE 特有的考察重点： 客户数据分析——“按营收展示我们的前 10 大客户”或“找出这份使用数据中的异常”。

需要掌握的主题：

  • CTE（公用表表达式）
  • 窗口函数（ROW_NUMBER、RANK、LAG、LEAD）
  • 复杂连接（INNER、LEFT、FULL OUTER、CROSS）
  • 聚合（GROUP BY、HAVING、ROLLUP）
  • 查询优化（索引、EXPLAIN、查询计划）

示例问题（Palantir）：

“给定 users（id、email、signup_date）和 events（id、user_id、event_type、timestamp）两张表，编写一个查询，返回最近 30 天内注册但尚未触发 event_type='activation' 的用户。”

预期解法：

WITH recent_signups AS (
  SELECT id, email, signup_date
  FROM users
  WHERE signup_date >= CURRENT_DATE - INTERVAL '30 days'
),
activated_users AS (
  SELECT DISTINCT user_id
  FROM events
  WHERE event_type = 'activation'
)
SELECT rs.id, rs.email, rs.signup_date
FROM recent_signups rs
LEFT JOIN activated_users au ON rs.id = au.user_id
WHERE au.user_id IS NULL
ORDER BY rs.signup_date DESC;

备考策略：

  • Practice 50-75 SQL problems
    • LeetCode SQL（50 道题）
    • HackerRank SQL（高级级别）
    • SQLZoo（全部教程）
  • Master window functions
    • 这些出现在 80% 的 FDE SQL 面试中
    • 练习：每组前 N 名、累计总和、移动平均
  • Practice on real-world data
    • 下载示例数据集（Kaggle）
    • 分析：客户群组、流失、漏斗分析

能力 6：沟通（占面试的 3%）

是什么： 向非技术客户解释技术概念。

如何考察：

  • 案例研究之后：“向一位非技术高管解释你的解决方案。”
  • 编码过程中：“向客户解释这个算法。”
  • 行为面试：“讲一次你必须解释某个技术问题的经历。”

框架：解释金字塔

第 1 层：执行摘要（15 秒）

  • 它解决什么问题？
  • 业务影响是什么？

第 2 层：它是如何工作的（30 秒）

  • 高层次的机制（不用行话）
  • 类比或比喻

第 3 层：技术细节（仅在被问到时）

  • 算法、数据结构、架构
  • 权衡与备选方案

示例：

糟糕的解释：

“我们将使用带三元组损失的孪生神经网络将视频编码到 768 维的嵌入空间，然后使用带 HNSW 索引的近似最近邻搜索来查询向量数据库。”

好的解释：

[L1] “我们正在为您的视频打造一个搜索引擎——就像 Google，但针对的是视频内容。它能让您的团队在几秒钟内找到相关素材，而不是几个小时。” [L2] “工作原理是这样的：我们把每个视频看一遍，为其中的内容生成一个‘指纹’，然后把这些指纹存入一个可搜索的数据库。当有人搜索时，我们会把查询内容与最接近的视频指纹进行匹配。” [L3 - 仅在被问到时] “从技术上讲，我们使用嵌入模型将视频转换为向量表示，存入向量数据库，并使用近似最近邻搜索实现快速检索。我们可以为 1000 万个视频建立索引，并在 2 秒内返回结果。”

备考策略：

  • Practice 10 technical explanations
    • Record yourself explaining:
      • 向非技术人员解释 RAG 的工作原理
      • 向 CEO 解释数据库如何扩展
      • 向合规官解释加密如何保护数据
    • 回看录像：你是否用了行话？表达是否清晰？细节是否过多？
  • Use analogies
    • 向量数据库 = 图书馆卡片目录
    • 负载均衡器 = 餐厅领位员安排顾客入座
    • API = 餐厅菜单（你点菜，厨房做菜）
  • Practice the "5-year-old test"
    • 你能向一个 5 岁的孩子解释清楚吗？
    • 如果不能，说明你理解得还不够透彻

能力项 7：行为面试（占面试的 2%）

是什么： 用 STAR 故事展示客户同理心、责任担当和冲突解决能力。

FDE 特有的考察点： 不只是“讲讲你遇到冲突的一次经历”——面试官想看到：

  • 面向客户的经验（或其替代经历）
  • 出问题时勇于担责（客户不在乎是谁的错）
  • 在技术完美主义与客户时间表之间取得平衡

准备 5 个 STAR 故事：

  • Cross-functional collaboration
    • 情境：与非技术团队（销售、产品、客户成功）合作过
    • 任务：需要交付他们能理解/能推销的技术方案
    • 行动：你如何在技术与业务之间架起桥梁
    • 结果：客户成果或业务影响
  • Handling ambiguity
    • 情境：接到模糊的需求或未定义的问题
    • 任务：在没有明确规格的情况下进行范围界定并交付
    • 行动：你如何拆解问题、提出澄清性问题
    • 结果：尽管存在模糊性仍成功交付
  • Failed project
    • 情境：项目失败或未达预期
    • 任务：你在失败中应承担的责任
    • 行动：你学到了什么，会如何换一种做法
    • 结果：你如何应用这些教训（救赎之路）
  • Technical disagreement
    • 情境：在技术方案上与团队/经理意见不合
    • 任务：需要为自己的方案争取支持或做出妥协
    • 行动：你如何专业地处理分歧
    • 结果：最终结果以及你在影响力方面学到的东西
  • Driving impact without authority
    • 情境：需要影响你无权管理的人
    • 任务：让他们优先处理你的项目/请求
    • 行动：你如何建立共识（数据、说服、人际关系）
    • 结果：通过影响力带来的成效

需要准备的面试问题：

  • “讲一次你向非技术背景的听众解释技术概念的经历。”
  • “描述一次客户对你的工作不满的情况。你是如何处理的？”
  • “讲一个失败的项目。你学到了什么？”
  • “描述一次你出于业务原因不得不做出技术权衡的经历。”
  • “讲一次你在如何解决问题上与团队意见不一致的经历。”

备考策略：

  • Write out 5 STAR stories
    • 不要背稿子（听起来很机械）
    • 内化：情境、任务、行动、结果
    • 练习自然地讲述（给自己录音）
  • Focus on customer impact in results
    • 差的结果：“我们上线了这个功能。”
    • 好的结果：“我们上线了这个功能，帮助 10 个客户将每周的手工工作从 8 小时减少到 30 分钟，为整个客户群每年节省 5 万美元。”
  • Prepare for "tell me more" follow-ups
    • 面试官会深入追问：“你具体做了什么？”
    • 不要夸大：你在夸大自己的作用时他们能看出来
    • 诚实地承认自己的贡献

第三部分：案例研究深度剖析 + 练习题

案例研究框架：CIRCLES（详细版）

C - 理解情境（5 分钟）

提出澄清性问题以了解：

  • 客户： 谁会受益？（最终用户、管理员、高管？）
  • 问题范围： 问题有多大？（收入影响、用户数量、发生频率？）
  • 数据可用性： 有哪些数据？（历史数据、实时数据流、数据质量？）
  • 约束条件： 预算？时间表？合规要求？
  • 成功指标： 如何衡量成功？（准确率、延迟、采用率、投资回报率？）

示例：

面试官：“一家医院想用 AI 减少再入院率。”你：“很好，我有几个澄清性问题：目前的再入院率和目标分别是多少？我们有历史患者数据吗？（电子病历、就诊记录、用药记录？）部署的时间表是什么？有合规方面的限制吗？（HIPAA、数据访问限制？）我们如何定义成功？（再入院率降低的百分比？投资回报率？）”

I - 确定客户（2 分钟）

明确你在为谁构建产品：

  • 主要用户： 谁每天与系统交互？（医生、护士、患者？）
  • 次要利益相关者： 谁关心结果？（医院 CFO、保险公司？）
  • 使用场景： 他们会如何使用它？（出院时、出院后监测？）

R - 复述问题（2 分钟）

用自己的话复述问题：

“所以我们要构建一个 AI 系统，预测哪些患者在出院后 30 天内属于再入院高风险。系统会在出院规划期间提醒护理团队，以便他们采取预防措施——比如安排复诊预约或安排居家医疗服务。成功意味着在保持护理质量的同时，将再入院率降低 X%。”

面试官应确认： “对，没错”，或纠正你的理解。

C - 优先级取舍（5 分钟）

区分 MVP 和锦上添花的功能：

MVP（必须随首发推出）：

  • 风险预测模型（核心功能）
  • 与电子病历（EMR）集成（以访问患者数据）
  • 面向护理团队的警报系统（他们的使用方式）

V2（可以后续添加）：

  • 面向患者的应用（自我监测）
  • 预测分析仪表板（长期趋势）
  • 与居家医疗服务集成（自动转诊）

使用 RICE 框架：

  • Reach（覆盖面）： 影响多少患者/员工？
  • Impact（影响）： 能在多大程度上改善结果？
  • Confidence（信心）： 我们对它有效的把握有多大？
  • Effort（工作量）： 构建需要多长时间？

L - 列出解决方案（15 分钟）

头脑风暴 3-5 种方案，列出各自的优缺点：

方案 1：基于规则的系统

  • 优点：简单、可解释、构建速度快
  • 缺点：准确率较低，无法从数据中学习

方案 2：机器学习模型（逻辑回归）

  • 优点：准确率更高，能从数据中学习
  • 缺点：需要标注数据和一定的机器学习专业知识

方法三：深度学习（神经网络）

  • 优点：准确率潜力最佳，能处理复杂模式
  • 缺点：需要大量数据，“黑箱”，成本高

方法四：混合方案（规则 + 机器学习）

  • 优点：兼顾可解释性与准确性
  • 缺点：维护更复杂

E - 评估权衡（10 分钟）

深入探讨推荐方案：

推荐：方法四（混合方案）

理由：

  • 可解释性至关重要（医生需要信任它）
  • 随着数据积累，机器学习可以不断改进
  • 规则可处理边缘情况（监管要求、临床指南）

技术设计：

  • 特征工程：年龄、诊断代码、用药情况、既往就诊记录、社会决定因素
  • 模型：梯度提升（XGBoost），兼顾准确性与可解释性
  • 集成：在出院流程中调用的实时 API
  • 提醒系统：EMR 通知 + 向护理协调员发送短信

部署：

  • 第一阶段：影子模式（模型运行但不发出提醒，与实际再入院情况对比）
  • 第二阶段：试点（一个病区，对所有提醒进行人工审核）
  • 第三阶段：全面推广（所有病区，自动提醒）

评估：

  • 精确率/召回率（尽量减少误报——避免提醒疲劳）
  • AUC-ROC（模型整体质量）
  • 临床结果（实际再入院率的降低）

S - 总结建议（5 分钟）

简明总结：

“总之，我推荐采用机器学习（梯度提升）与临床规则相结合的混合方案。我们将从 MVP 开始，在出院时预测高风险患者，并通过 EMR 集成向护理团队发出提醒。我们会先以影子模式部署以验证准确性，然后在全面推广前在一个病区进行试点。成功指标是精确率/召回率（模型质量）和再入院率的降低（临床影响）。这一方案在准确性、可解释性和上市速度之间取得了平衡。”

谈判框架

第一阶段：尽早设定预期

在招聘人员初筛时：

招聘人员：“你的薪资期望是多少？”

你的回应：

“我的目标是在 [company] 担任前沿部署工程师的市场水平。根据 Levels.fyi 上 [location] 地区 FDE 的数据，总薪酬大约在 $[X]-$[Y] 之间。这与该职位的预算相符吗？”

为什么这样有效：

  • 将讨论锚定在市场数据上（而不是你目前的薪资）
  • 表明你做过调研
  • 避免自我压价
  • 不承诺具体数字（为后续留有余地）

第二阶段：收集竞争性 Offer

最佳筹码：多个 Offer。

策略：

  • 申请 10-15 家公司（不要只申请 1 家梦想公司）
  • 安排面试时间，让各 Offer 在相近的时间段内到来
  • 用 Offer 作为筹码：“我手上有一个 [Company X] 的 Offer，薪酬是 $Y。你们能否匹配或超过？”

示例：

“我对 Anthropic 的这个职位非常感兴趣。我手上还有一个 OpenAI 的 Offer，总薪酬为 $450K。Anthropic 是我的首选，因为 [使命、团队等]。你们是否有灵活空间来匹配或超过 OpenAI 的 Offer？”

第三阶段：分别谈判各个组成部分

不要只要求“更多钱”——逐项谈判每个组成部分：

基本工资：

  • 更容易提高（不涉及股权稀释）
  • 影响 401k 匹配和奖金
  • 优先谈判

股权：

  • 更难提高（存在稀释顾虑）
  • 但如果公司发展良好，杠杆价值很高
  • 在基本工资谈到上限后再谈判

签约奖金：

  • 最容易提高（一次性成本）
  • 弥补你在原公司尚未归属的股权
  • 最后谈判

谈判示例：

“感谢你们提供 $200K 基本工资 + 每年 $80K 股票的 Offer。我很期待加入。有两个请求：能否将基本工资提高到 $220K？这与资深 FDE 的市场数据相符。能否增加 $50K 的签约奖金？我在现公司还有 $60K 未归属的股权。如果可以做到，我今天就能签字。”

第四阶段：利用竞争性 Offer

如果你手上有多个 Offer：

发给公司 A（你的首选）的邮件：

主题：Offer 跟进——延期请求你好 [Recruiter]，感谢你发来的 Offer。[Company A] 是我的首选，因为 [具体原因]。我手上还有 [Company B] 的 $X 和 [Company C] 的 $Y 两个 Offer。[Company B] 的截止日期是 [date]。问题：总薪酬方面是否有灵活空间来匹配或超过 [Company B] 的 Offer？能否将我的截止日期延长至 [date]，以便我做出充分知情的决定？我很期待加入，并希望促成此事。此致，[Your name]

为什么这样有效：

  • 表明你有其他选择（筹码）
  • 传达出真诚的兴趣（而不只是追逐金钱）
  • 制造紧迫感（竞争性的截止日期）
  • 提出具体问题（招聘人员更容易采取行动）

常见的谈判错误

错误 1：透露你目前的薪资

招聘人员：“你目前的薪资是多少？”

糟糕的回答：“12 万美元”（让讨论的锚点偏低）

好的回答：“我的目标是 FDE 的市场水平，根据级别不同在 20 万至 30 万美元之间。这与这个职位的定位一致吗？”

错误 2：立即接受第一个 offer

招聘人员：“我们提供的总薪酬是 25 万美元。可以吗？”

糟糕的回答：“可以！我接受！”（白白放弃了钱）

好的回答：“谢谢！我很兴奋。能给我 3-5 天时间审阅细节后再答复你吗？”

原因：即使 offer 很好，也一定要谈判。公司对此有预期。立即答应会表明你本来愿意接受更低的待遇。

错误 3：没有筹码就谈判

你：“能把 offer 提高到 35 万美元吗？”

招聘人员：“为什么？”

你：“因为我想要更多的钱。”（太弱了）

更好的做法：

  • 利用竞争性 offer：“我手上有一个来自 X 公司的 offer，薪酬是 Y。”
  • 利用市场数据：“Levels.fyi 显示 [公司] 的 FDE 平均薪酬是 Z。”
  • 利用你的价值：“我具备 [具体技能/经验]，这在 FDE 中很罕见。”

错误 4：谈判错误的薪酬组成部分

场景：你想要更多现金。公司提出把股权从每年 8 万美元提高到每年 10 万美元。

为什么这可能不好：股权有风险（归属期、公司估值）。基本工资是有保障的。

更好的做法：先谈基本工资。如果已经到顶，再谈股权或签约奖金。

错误 5：态度对抗

糟糕的语气：“你们的 offer 是一种侮辱。我要 40 万美元，否则我就走人。”

好的语气：“我对这个职位非常感兴趣。根据市场数据和我的竞争性 offer，我的目标是 35 万美元。这方面有灵活空间吗？”

原因：招聘是建立关系的过程。你以后会和这些人共事。保持合作态度。
