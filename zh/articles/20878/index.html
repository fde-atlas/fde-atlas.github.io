标准开场

交接任务简报

这一部分的目的

目的

如何运行。一名面试官在整个一小时内扮演一位客户，直到结束语之前都不出戏。第二名面试官在这里是默认配置，而不是可选项：主面试官无法同时扮演角色、掌控五个环节的计时并勾选四十多项信号。第二个人不说话。他们记录三个时间戳——首次提到访问权限的分钟数、首次要求真实数据的分钟数，以及在第 22 分钟截止前是否出现了任何具体承诺——并由他们保管信号表。唯一规则：下面的台账内容一律不主动提供。只有当候选人以客户的口吻问起时才透露，绝不能提前。遇到你确实不知道的情况，就说“我不知道”，并且要当真；这一小时内你至少应该使用这句话两次。术语表，让你在回答领域问题时不必犹豫。Quote（报价单）——承保人给出的定价要约。Binder（暂保单）——保单签发前的临时承保确认。Endorsement（批单）——对现有保单的期内变更。Loss run（理赔记录）——理赔历史报告，通常来自承保人。Renewal season（续保季）——大多数保单集中续保的时间窗口。保留台账，仅在被问及时提供。如果他们问 -> 你回答。// 现在谁在做这件事，有多少人 -> 六个人。我的两名下属，就坐在这里。还有四名通过马尼拉一家机构签约的离岸外包人员，采用滚动合同。// 每个人的考核指标是什么 -> 我的主管按发现的错误数量考核。我的 CFO 看的是外包机构的发票。没有人按速度考核。// 处理一份文件需要多长时间 -> 批单、报价单或暂保单需要三四分钟。理赔记录需要二十分钟或更久，因为得有人翻四十页去找八个数字。// 文件（不包括电子邮件）-> 每天大约五百份。四百封电子邮件，承保人会在一夜之间把五六封合并成一批。// 构成比例 -> 大约一半是批单，三分之一是报价单和暂保单，每十二份文件中约有一份是理赔记录。// 如果他们当场算术——四百六十份快速文件按三四分钟计算，加上四十份理赔记录按二十分钟计算，总计在三十六到四十四个人时之间，而我这六个人共有四十二个人时 -> 用这些话确认：“差不多刚好满负荷到略微超负荷，取决于你取三到四分钟的哪一端。这正是我们的实际感受。大多数日子我们待到六点以后，没有任何事情拖到明天。”// 如果他们接着问哪些文件最耗时 -> 理赔记录。十二份文件里占一份，却占了大约三分之一的分钟数。// CFO 期望节省多少 -> 他说六个人里省四个。他指的是外包机构合同。// 需要录入哪些字段 -> 十一个：被保险人名称、保单号、承保人、生效日期、到期日期、保费、限额、免赔额、登记经纪人、文件类型、接收日期。// 其中一个出错时下游会发生什么 -> 保费录错会影响下一次开票的金额。保单号录错几个月内都不会有任何可见影响。登记经纪人录错会把佣金付给错误的人，我的会计团队是在承保人对账单无法核对时才发现的。// 已经尝试过什么 -> 2024 年用过一家 OCR 供应商。它只能读取机器可读的承保人 PDF，其他都不行。// 如果他们追问为什么终止了 -> 它能运行，但没有帮我们省下一个人。这就是为什么我的 CFO 对简单文件不感兴趣。// 哪些文件已经是机器可读的 -> 一家承保人的，约占收到的百分之三十。他们的 PDF 带有文本层，而且版式多年来一直没变。// 如果他们问那百分之三十占多少分钟比例 -> 那些都是快速文件。大约占五分之一的时间，对应十分之三的文件。// 理赔记录长什么样 -> 扫描的传真件，最多四十页，多年理赔历史。// 手写内容 -> 大约百分之十五的理赔记录带有手写批注。// 如果他们问手写内容是否在被录入的字段上 -> 几乎从不。通常是理赔员写在页边空白处的备注。// 保单管理系统 -> 一款 2009 年的本地部署供应商产品。没有公开 API。// 数据如何进入系统 -> 通过供应商支持的每夜 CSV 导入。凌晨两点运行，按保单号执行 upsert，日期格式错误时整行拒绝，并把拒绝记录写入一个没人看的日志。// 环境 -> 没有测试副本。只有一个共享管理员凭据，四个人知道。// IT -> 一个人，每周两天。// 变更审批 -> 周四会议。// 数据可以存放在哪里 -> 我的三家最大承保人之一有一条条款，要求我们的数据保留在我们自己的租户内。// 如果他们问数据处理协议，或我们被允许外发什么 -> 我们与那家 OCR 供应商在 2024 年签过一份。由我们的合规人员起草，花了三周。我不知道里面写了什么。// 邮箱 -> Microsoft 365 上的一个共享 Outlook 邮箱。// 目前的质量控制 -> 我的主管抽查百分之十的录入记录，并把她发现的问题记在电子表格里，追溯两年。// 表里有多少行 -> 大约四百行。她相信自己发现了大部分出错的地方。她并不确定。// 目前的错误率 -> 她抽查的内容中约百分之二发现问题。// 去年的保费在系统里吗 -> 在。有六年的续保历史。// 如果他们追问那段历史是否可靠 -> 保费是可靠的。限额和免赔额从 2022 年才开始一致录入。// “本季度”是什么意思 -> 续保季。十一周后开始。// 如果被问百分之十的阈值去年会标记出什么 -> 我不知道，这是个合理的问题。可能比我想要的要多。// 我们 IT 资产清单上的 RPA 许可证 -> 两年前为另一个流程买的。它不在这个工作流上，我不希望你们对此过度解读。

我是 [COMPANY_NAME] 的 [YOUR_NAME]，在接下来的一个小时里，我不会扮演面试官。我会扮演一位客户——我经营着一家刚与我们签署试点的公司的运营部门，而你就是我们要派来的工程师。我对自己的业务非常了解，但我不会主动告诉你，因为我不知道哪些部分对你重要。你可以问我任何问题。如果我不知道，我会直说，而且这是真的。大约二十分钟后，我会打断你，问你一周后我的环境里会运行什么，所以要给自己留出时间。这里没有白板要求——尽管聊，并把你之后想发给我的东西记下来。

这段话的用途

目的

告诉候选人这一轮是现场的需求界定对话，而不是设计练习，并提醒他们会有一个承诺要求，因此优秀的候选人会主动管理时间，而不是被突然袭击。提到的分钟数是关键信息，需要与下方的时长核对：第一和第二部分分别为八分钟和十四分钟，所以打断点落在第二十二分钟。如果你重新调整这一轮的时间，也要同步调整这句话。

那么，我们的情况是这样的。我经营着一家中型商业保险经纪公司的运营部门。我们每天大约收到四百封来自保险公司和客户的带附件的邮件——报价单、承保协议、批单、损失记录。我的团队里有人会逐一打开每封邮件，弄清楚它是什么，把上面的数字提取出来，然后输入到我们的保单管理系统中。我希望你的 AI 来做这件事。我的 CFO 已经批准了一个试点，我希望在这个季度看到能运行的东西。

这段话的用途

目的

用客户自己的话交代背景，其中用户、数据、成功指标和截止日期都刻意保持模糊。本轮后续的每个问题都依赖于这种模糊性。注意“四百封邮件”不是“四百份文档”，客户不会主动纠正这一点。

所以——这就是我想要的：你的 AI 读取文档并把数字输入进去。你想从哪里开始？

这个问题的用途，以及要听什么

目的

按候选人探索的顺序来区分他们，而不是看他们是否探索。每个有准备的候选人都会提出澄清问题；真正的信号在于最初的问题是关于人和时间，还是关于文件格式。

需评分的信号

  • 在询问任何关于文档的问题之前，先问今天实际是谁在做这项工作，以及有多少人
  • 以每份文档的分钟数或每天的小时数建立人工基线，并用数字复述出来
  • 当场交叉验证该基线——六个人处理五百份文档意味着满负荷且毫无余量，那么 CFO 以为自己在购买的那部分人手在哪里——并追问哪个数字是错的
  • 将日常业务会发生变化的人与批准预算的人区分开来，并询问各自的考核指标是什么
  • 询问数据录入之后会发生什么，以及一条数据出错时下游会出什么问题
  • 询问各类文档类型的占比，不接受把每日总量当作单一数字
  • 询问是什么促成了这次试点，并揭示“本季度”背后隐藏的续约季日期
  • 询问这里已经尝试过哪些方案，包括供应商、脚本以及团队自己开发的任何东西
  • 点出他们刻意暂不询问的事项，并说明为什么可以等一等
  • 在最初五分钟内不提出任何架构、模型或供应商方案

追问问题

  • 我团队里谁会在你们构建这个系统时坐在你旁边？
  • 如果这件事完美成功，我的损益表上会有什么变化，谁会最先注意到？
  • 假如我告诉你那四百是个猜测，你想要什么来替代？
  • 你最想亲眼看到的第一样东西是什么，而不是听我说？
  • 到目前为止我说的话里，有没有你认为不对的地方？

代码究竟是如何进入系统的

这一部分的目的

目的

这两个问题能区分前沿部署工程师和解决方案架构师。在客户环境中交付过系统的人会先询问凭证和审批，再询问架构，并且会要求查看真实记录，而不是轻信口头描述的 schema。没有这种经历的人则两者都不会提及。

假设我们对问题达成了一致。请带我走一遍，在你的任何一行代码运行到我们的系统之前，你需要我和我唯一的 IT 人员提供什么——并告诉我你会在什么时候提出这些需求。

这个问题的用途，以及要听什么

目的

测试部署的现实情况是计划的一部分还是事后补想。只在自家公司系统内构建过的候选人会从架构角度回答这个问题；而部署过到别人系统里的候选人会从访问权限、审批和日历天数的角度回答。

需评分的信号

  • 在这个问题的前两分钟内询问凭证、网络访问权限，以及能授予这些权限的具体负责人
  • 询问是否存在非生产环境，并在得知不存在时调整方案
  • 询问谁有权批准生产变更，以及这种审批的频率
  • 对系统进行拆分：只有写回 2009 年系统才需要周四的会议，因此它上游的所有部分都可以每日发布
  • 在提出任何托管服务之前，先询问数据允许存放在哪里——客户的租户、我们的云，还是第三方
  • 询问该客户在合同上允许第三方处理哪些数据，并将这一答案与推理运行的位置挂钩
  • 将每夜的 CSV 导入视为真正的集成接口，而不是为缺失的 API 提供的安慰奖
  • 说明仅凭只读权限，他们在第一天就能完成什么
  • 指出共享管理员凭据是一种风险，并要求提供服务账号，但不会因此拒绝开始工作
  • 将访问和审批延迟换算成日历天数，并把这一数字纳入计划

追问问题

  • 我的 IT 只是一个人，每周工作两天。这对你来说有影响吗？
  • 我们没有保单系统的测试副本。你会怎么做？
  • 我们的数据是否需要放在你的笔记本电脑上？
  • 我的一家承保商有关于我们数据可在何处处理的条款。这会导致合作无法进行吗？
  • 如果今晚我只给你一份只读导出文件，到周五你手上会有什么？

你一直在说“那些文档”。在做出任何承诺之前，你想看哪些内容、看多少，以及你在寻找什么？

这个问题的用途，以及要听什么

目的

区分那些会亲自验证数据的候选人与那些只相信数据描述的候选人。需求简报描述的是一条干净的 PDF 流；而其背后的实际情况更脏、更单薄。如果到第四周才发现这一点，而不是在这一小时内发现，就会毁掉整个合作项目。

需评分的信号

  • 要求查看实际文档，而不是对文档的描述，并说出一个具体数字
  • 明确说明样本应如何选取，并且不让客户挑选示例
  • 明确要求查看最糟糕的案例——被拒件、需要升级处理的件，或耗时最长的件
  • 询问近几个月数据构成比例的变化，而不是把数据量视为一成不变
  • 询问或发现扫描件和手写材料，而不是假定全部都是数字 PDF
  • 询问是否有任何子集已经是机器可读的，并将其单独划为一个独立问题
  • 要求查看团队输入了什么，而不仅仅是他们从哪里读取
  • 一旦样本比简报所暗示的更混乱，就明显地当场重新界定范围或重新报价
  • 询问谁能交付样本，以及需要多少天

追问问题

  • 多少份才够？十份？一千份？
  • 如果我把最干净的十份发给你，那能告诉你什么？
  • 其中一些是以传真形式到达的。这有问题吗？
  • 在那个样本中，你需要看到什么才会放弃这个试点？
  • 你想要的是文档本身，还是我的团队从文档中输入的内容？

第一周切分

这一部分的目的

目的

这是整场面试中信噪比最高的一个问题，必须在固定的时间点提出——第 22 分钟——无论候选人进行到哪里，或者只对推进较快的候选人进行评分。提问前先做发布检查：夜间 CSV 导入和主管抽查这两个事实是否已经出现？如果任一尚未出现，现在就用客户的口吻释放出来——“我应该提一下，保单系统有一个隔夜导入，而且我的主管已经会手工抽查其中一部分”——并记下你不得不这样做。下面的信号中有三个以及大部分错误处理部分，没有这两个事实就无法评分，否则第二部分表现较弱的候选人会让剩下的半小时完全无法产生可比的信号。

让我在这里打断你。我在整点有一个硬性截止，在你离开之前，我需要你提供一些东西。

这段话的用途

目的

强制按时间而非对话的自然节奏进行切割，并且刻意做到突然，因为在不完整的信息下做出承诺的能力正是要考察的东西。

距今一周后。我的环境里运行着什么，谁动过它，你有意识地决定不构建什么？

这个问题的用途，以及要听什么

目的

在一小时内重现这个角色的标志性失败：漂亮的设计无人部署。按架构层次排序的候选人在第三周之前做不出任何可演示的东西，而这个问题能在九十秒内暴露这一点。

需评分的信号

  • 说出一个端到端的东西，客户中某个具名的人可以看到它在运行，而不是一个组件
  • 第一周的交付物触及那个丑陋的集成——向 2009 年系统的夜间导入——并且不推迟它
  • 有意收窄到一种文档类型或一个承运商，并说明是哪一个以及为什么
  • 明确推迟提取质量工作，并说明第一版会在哪些方面明显不佳
  • 说明第一周人类仍在做什么，而不是描述一个无人值守的流水线
  • 承诺一个客户周五可以核对的数字：处理的文档数、节省的分钟数、匹配的字段数
  • 用客户的语言列出至少两件他们有意识不构建的东西
  • 围绕周四的变更窗口排序，而不是围绕工程上的便利
  • 说明客户在第一周必须做什么，以及截止时间

追问问题

  • 假设你第一周构建的一切最终都是错的。我还能得到什么？
  • 哪种文档类型，为什么是那一种？
  • 下周五我的团队会有什么不同？
  • 如果下周五我只能看一个屏幕，上面有什么？
  • 这里面哪一部分你会在第三周毫不犹豫地扔掉？

范围变更

这一部分的目的

目的

客户在后期增加范围并更改日期，这是客户的常态。这不是在测试候选人是否会说不，而是测试他们能否进行交换、用客户的单位为交换定价，并在继续之前获得明确的答复。它必须能区分“交换”与“直接拒绝”以及“妥协”，因为这三种情况都很常见，而只有一种才算通过。客户决定（写下来，确保每位候选人都一样）：如果他们让你在标记和日期之间做选择，选日期。要说：“日期不是我能改的，现在是续约季，而且我的团队需要在忙起来之前有四周时间使用它。我宁愿标记晚一点，也不愿数据提取晚一点。”不要为喜欢的候选人即兴给出不同的答案。

在你离开之前还有两件事。我的 CFO 昨天看了这个，问它是否也能标记比去年高出百分之十以上的续约报价——这才是真正让我们流失客户的问题。而且他不希望它在续约季开始时才上线。他希望提前四周上线，这样我的团队就有时间在忙起来之前学会使用它。那是七周，不是十一周。

这段话的用途

目的

在候选人已经确定计划的时点，引入一个真实的业务请求和一个真实的日期变更，使接受请求的代价真实存在，且对双方都清晰可见。这个日期是刻意设置的新信息：在第一部分提取出“十一周”的候选人，在这里会得知目标是在其中提前四周，这是真正的压缩，而不是对他们已有信息的重复。

那么——你能做到吗？续约标记，并且在七周而不是十一周上线。

这个问题的用途，以及要听什么

目的

在范围压力下的行为，决定了项目合作能否存续。妥协和直接拒绝在当场都显得果断，但都会失败；通过的表现是附带明确答复的、经过定价的交换。

需评分的信号

  • 在回答是或否之前，先询问续约标记的用途以及谁会根据它采取行动
  • 用天数和人数为新增需求定价，而不是用工作量、复杂度或点数
  • 明确指出如果新需求加入，会有什么具体内容被移出范围
  • 等待并从客户那里获得对这次交换的明确是或否
  • 将两个请求分开——新功能和更早的日期——并给出不同的回答
  • 注意到续约对比需要去年的数据，并询问这些数据是否已经在系统中
  • 在同意构建之前，质疑百分之十的阈值，并询问它本会标记出去年续约的多大比例
  • 提出一个更省成本的版本，使其符合已经商定的计划
  • 在继续之前，用一句话复述修订后的协议
  • 不会在不至少把其中一项明确报价的情况下，同时接受新增范围和压缩后的日期

追问问题

  • 这是肯定的答复吗？
  • 这要花我多少钱？
  • 我的 CFO 会问为什么不。我该怎么跟他说？
  • 如果七周不可商量，那什么会被砍掉？
  • 这两者中你更想要哪个——是那个标记，还是那个日期？

犯错之时，以及你留下什么

这一部分的目的

目的

定义这个角色的三个特质，也是已发布的面试内容会问到却几乎从不评分的：当一个自动化系统在别人的业务里出错时会发生什么，在你受雇去取代其工作的那些人中间度过十一周是什么体验，以及工程师轮换离开后客户环境里还留下什么。各类指南会把“你会如何交接”列为一个问题，然后就止步于此；下面要讲的是一个好答案应包含的内容。这些特质也能清晰地把前沿部署工程师与外包承包商区分开来，而后者正是最可能出现在候选人管道里的人群。第二个客户决策，写下来：如果他们要你商定一个可接受的错误率，说你不知道。然后接受任何把保费、生效日期和记录承保人置于人工审核之下、并允许低风险字段自动过账的逐字段方案。不要在接受任何单一混合数字之前不先问它涵盖哪些字段。轮次结束后评分，依据是邮件发出的总结而非现场表现：是否在一天内无需二次催促就收到了书面总结，以及其中是否包含问题本身、第一周的范围、范围外清单、对客户的要求，以及双方都会关注的那个数字？

你的系统迟早会把某个数字弄错。带我走一遍它第一次出错时会发生什么——以及你怎么能在我之前就知道。

这个问题的用途，以及要听什么

目的

几乎每一份 AI 工程指南都在教“搭建评测框架”，所以泛泛的答案千篇一律、毫无价值。真正有区分度的做法是把客户现有的手工质量流程借来作为第一套评测集，只有真正向真实业务交付过的人才想得到这一步。

需评分的信号

  • 在提出任何自己的评测方案之前，先问客户今天是如何发现录错的数字的
  • 索取主管现有的抽查记录，并提议将其作为第一套评测集
  • 指出该记录的局限——它只包含人工在抽样的十分之一中发现的错误——并要求在此基础上再补充一个随机样本
  • 区分人工在内部就能发现的问题与已经传到承保人或客户那里的问题
  • 让客户说出哪些字段允许出错、哪些不允许
  • 提出置信度阈值或审核队列，以替代“要么自动化、要么不做”的二选一
  • 用客户自己的话说明系统在不确定时会怎么做
  • 明确指出系统出错时会通知谁，以及通过什么机制通知
  • 给出可接受错误的具体数字，并让客户认可这个数字，且不暗示零错误
  • 把衡量指标挂到客户已经在运行的流程上，而不是挂到一个没人会打开的新仪表盘上

追问问题

  • 如果它悄悄错了一个月，你怎么会知道？
  • 我们有些项目已经在人工检查了。这对你有帮助吗？
  • 这里可接受的错误率是多少？给我一个数字。
  • 系统出问题时，应该给谁打电话？
  • 哪种错误会让我在承运商面前丢脸？

还有一件事。你想坐在一起的那六个人，正是我的 CFO 谈及编制时数着的六个人。没有人告诉过他们这件事。你要怎么和他们一起度过十一周？

这个问题的用途，以及要听什么

目的

这个角色的核心风险所在，也是决定样本能否真正到位的关键环节。台账里已经包含了这个问题所需的一切：CFO 购买的是编制成本，六人中有四个是外包承包商，而候选人刚刚索要其表格的那位主管正是被自动化对象之一。真正嵌入过的人会立刻、具体地回答这个问题。没有嵌入过的人则会空谈变革管理。

需评分的信号

  • 把披露这件事当作客户要解决的问题，并询问团队已经被告知了什么
  • 在同意与任何人坐下来之前，先问是谁告诉他们的、什么时候、用了什么措辞
  • 拒绝从尚未被告知真相的人那里开始收集样本
  • 具体而非抽象地指出主管的工作将变成什么
  • 区分两名正式员工与四名外包承包商，不假装两者的答案是一样的
  • 请客户亲自向团队说出这个计划，而不主动提出代为传话
  • 说明当有人直接问“这是不是要取代我的工作”时，他们会怎么回应
  • 预判团队配合的速度会慢于日程假设，并把这一点写进日程表

追问问题

  • 你觉得我的团队已经猜到了什么？
  • 其中一个人直接问你。你会怎么说？
  • 你想让我告诉他们，还是你想自己说？
  • 你想要其表格的那位主管正是六人之一。这会改变你的请求吗？
  • 如果我告诉你他们都会被重新安排岗位，而你并不相信我呢？

最后一件事。假设这件事成功了，试点结束后你就轮换离开。这里会留下什么，由谁负责？还有，在你走之前，告诉我你认为我们刚刚达成了什么共识——我想把它发给我的 CFO。

这个问题的用途，以及要听什么

目的

测试定义这个角色的核心特质——留下的是成果物而不是建议，同时检验六十分钟的优质对话是否产出了任何可分享的东西。那些谈得头头是道却什么都没交出来的候选人，恰恰展示了会丢掉项目的典型行为。口头复述当场评分；书面总结稍后评分，依据本节开头说明中的轮次后评分标准。

需评分的信号

  • 指出客户方将由谁负责拥有该系统，以及交接前这个人必须做过什么
  • 描述客户在项目结束前自己运行一次部署，候选人在旁观察
  • 指出存放在客户仓库和环境中的成果物，而不是候选人自己的
  • 包含一个在系统故障时会大声报错并通知到指定人员的检查
  • 交接评测集，并说明之后由谁来补充它
  • 说明供应商升级保单系统或承保方更改表单时会发生什么
  • 准确复述之前达成的取舍，包括被舍弃的那一项
  • 主动进行口头复述，并且对范围外清单的覆盖与计划一样细致
  • 明确说明需要客户提供什么，具体到内容和日期

追问问题

  • 周一早上七点你联系不上的时候，这里谁能解决这个问题？
  • 供应商升级我们的保单系统时会怎样？
  • 如果你培训的那个人离职了，我实际还剩下什么？
  • 把那份总结发给我——里面有什么内容？
  • 在你开始之前，你希望我书面提供什么？

收尾

我的时间到了，现在我要退出客户角色。请今天或明天把书面总结发给我——我会像那位客户一样去读它，也就是说我会像看计划一样仔细看范围外清单。无论如何，我们会在三个工作日内给你答复。

这段话的用途

目的

明确结束模拟，让候选人知道角色扮演已经结束，并将书面总结转化为一个真实的交付物，可以在面试结束后依据本节开头说明中的轮次后评分标准进行评分。

前沿部署工程师面试——常见问题

  • 这份前沿部署工程师面试计划是给谁用的？
  • 它是为面试官而非候选人编写的：即负责前沿部署工程师岗位“客户需求界定模拟”环节的招聘经理、工程师或面试小组成员。它为你提供一份 60 分钟的对话脚本——8 个问题，每个问题说明其目的和需要评分的信号——让你不必在前一晚从零开始设计整个环节。
  • “客户需求界定模拟”环节考察什么？
  • 本轮聚焦于：在客户自身环境中为一个未充分定义的 AI 部署项目划定范围，采用实时角色扮演形式，包含访问限制、后期范围变更和交接环节。流程涵盖交接需求简报、代码实际如何进入、第一周的切入点、范围变更与承认错误，以及你留下什么，依据 75 个可观察信号进行评分，全部 8 个问题均设有追问提示，以便在回答不够深入时进一步挖掘。
  • 60 分钟是如何分配的？
  • 60 分钟用于 8 个问题。问题包括交接需求简报（8 分钟）、代码实际如何进入（14 分钟）、第一周的切入点（10 分钟）、范围变更与承认错误（9 分钟），以及你留下什么（19 分钟）。设定时间是为了让整轮面试按计划进行，并确保每位候选人接受相同结构的面试——这也是让两位候选人 afterwards 具有可比性的关键。
