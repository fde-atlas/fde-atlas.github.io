解决方案工程师转 FDE：把 PoC 写成生产代码

FDE Times · 2026-10-08 · 约 7 分钟读完

摘要

文章以一个六行的工单分类 PoC 为例，讲解解决方案工程师如何补齐与 FDE 的差距：核心区别在于写生产代码并对部署结果负责。作者演示了如何加入错误处理、标签校验、重试与人工复核队列，再补充测试、架构文档，并用 FastAPI 和 Docker 部署到真实环境。文章还分析了 FDE 面试考察点、职位描述中的售前陷阱，以及转岗者常犯的四个错误。

要点

  • FDE 与解决方案工程师的区别：写生产代码并对部署结果负责。
  • PoC 改造四步：错误处理、测试、架构文档、真实部署。
  • 兜底逻辑是业务决策，如 needs_review 队列需与客户商定。
  • 面试考运维取舍，编码难度约 LeetCode 中等题。
  • 简历应展示运行中的系统，而非打磨过的演示。

把一个简短 PoC 改写到生产标准，就能看清差距具体在哪，可逐项补齐，也值得写进简历。

要点速览

  • 从解决方案工程师转为 FDE，意味着从演示代码转向生产代码，并对部署结果负责。
  • 最有效的练习：拿一个现成的 PoC，补上错误处理、测试和架构文档，再部署到真实环境。
  • FDE 面试中，你必须讲清为什么选择某种部署方式，而不只是证明代码能跑。

你刚演示完一个基于 LLM 的支持工单分类工具，客户非常满意。下周一，它上线进入生产环境。凌晨三点，一个 CSV 文件传进来，里面有一行空白，模型回了一句问候而不是 JSON，整条数据管道随之停摆。

如果你是解决方案工程师，工作通常在合同签下那一刻就结束了。如果你是前线部署工程师（FDE），凌晨 3 点爬起来修的人就是你。

fde.academy 的转岗指南把两者的区别归结为两个转变：你写的是生产代码而不是演示代码；你要对部署结果负责，而不是成交后就交出去。

好消息是，这个差距轮廓清晰，每一块都可以单独练习。下文拿一个极短的概念验证（PoC），一步步改到生产标准，再讲如何在简历和面试中展示这项能力。

对设计负责，不等于对系统负责

Aced 在比较这两种岗位时写道，FDE 一周的大部分时间都在写生产代码。解决方案架构师则只对设计负责，不对运行中的系统负责。系统一旦出故障或没能带来价值，修复它就是 FDE 的直接责任。

Sundeep Teki 在他 2026 年的 FDE 面试指南里说得更直白：你不提工单，也不怪别的团队，而是自己动手修。对咨询出身的人来说，这是最大的变化，比学新语法、新框架都大。

fde.academy 有一句话值得记住：PoC 只需证明一个观点，生产代码却要经得起现实的考验。这里的“现实”指脏数据、不稳定的网络、返回意料之外内容的 API，以及六个月后读你代码的另一个人。

一个六行的 PoC 会在哪里出问题？

设想上面那场客户会议用的演示代码：

import csv, json
from llm import client

for row in csv.DictReader(open("tickets.csv")):
    out = client.complete(f"对这个工单分类：{row['text']}")
    print(row["id"], json.loads(out)["label"])

（提示词字符串的意思是“对这个工单分类：”。）在十个精心挑选的样例工单上，它运行得很顺。可一放进真实环境，至少有五处会出问题。空工单照样发给模型，长达数页的工单可能超出上下文长度上限，一次 API 超时就能让整个循环崩掉。

如果模型返回纯文本，

json.loads

会抛异常。如果模型编出一个并不存在的标签，这个标签会悄无声息地流进下游系统。

改写后的代码不需要更聪明，只需要把每一种可能的失败都当成一定会发生。首先，显式声明合法标签，并配一个专用 logger：

import json, logging, time
from llm import client

LABELS = {"billing", "bug", "account", "other"}
log = logging.getLogger("triage")

接着，把单次模型调用拆成独立函数，截断输入、设置超时并校验返回的标签：

def call_model(text: str) -> str | None:
    out = client.complete(f"对这个工单分类：{text[:4000]}", timeout=20)
    label = json.loads(out).get("label")
    if label in LABELS:
        return label
    log.warning("未知标签：%r", label)
    return None

警告内容是“未知标签”。最后，

classify

函数处理空输入，按退避策略重试，并在所有尝试都失败时给出一条出路：

def classify(text: str, retries: int = 3) -> str:
    if not text or not text.strip():
        return "other"
    for attempt in range(retries):
        try:
            label = call_model(text)
            if label:
                return label
        except (TimeoutError, json.JSONDecodeError) as e:
            log.warning("第 %d 次尝试失败：%s", attempt + 1, e)
            time.sleep(2 ** attempt)
    return "needs_review"

注意最后一行。系统不会崩溃，而是把工单送进

needs_review

队列，交给人工检查。

这是一个业务决策，必须和客户商定：他们每天能接受多少工单落进这个队列？生产代码里到处是这类问题，演示代码则统统跳过。

然后，针对刚才列出的情况写测试：

def test_empty_ticket_goes_to_other():
    assert classify("   ") == "other"

def test_non_json_reply_goes_to_review(monkeypatch):
    monkeypatch.setattr(client, "complete", lambda *a, **k: "你好呀")
    assert classify("我被重复扣费了", retries=1) == "needs_review"

这里模拟的模型回复“你好”，测试工单内容是“我被重复扣费了”。这两个测试写起来不到十分钟，却能把一次凌晨 3 点的事故变成你早上 9 点在日志里读到的一行警告。

PoC 走向生产的四个步骤

fde.academy 最实用的建议是：拿一个现成的 PoC，按生产标准重建。他们把工作分成四步：加错误处理、写测试、写架构文档、部署到真实环境。上面的例子只完成了前两步。

第三步常被低估。架构文档不必长，只需回答：数据从哪里进来，流向哪里，调用了哪些外部服务，出故障时去日志的哪里找。对这个工单分类器来说，下面这样一页就足以起步：

# triage-service
输入：来自客户系统的工单（id, text）
输出：{billing, bug, account, other, needs_review} 中的一个标签
外部调用：LLM API，超时 20 秒，最多重试 3 次
出故障时：查看 "triage" logger，统计每天的 needs_review 工单数
运维负责人：你的名字，以及出问题时如何联系你

这几项分别是：输入（来自客户系统的工单，含 id 和 text）；输出（集合中的一个标签）；外部调用（LLM API，超时 20 秒，最多重试 3 次）；出故障时（查看 “triage” logger，统计每天的 needs_review 工单数）；运维负责人（你的名字，以及事故期间如何联系你）。读这一页的很可能是客户那边要和你一起运维系统的工程师。最后一行最重要，因为它写明了系统归谁负责。

第四步才真正检验能力。Coursera 介绍 AI 工程师的文章把“将模型做成其他应用可集成的 API”和“管理生产基础设施”列为核心职责。对上面的例子，在名为

api.py

的文件里把

classify

包装成一个接口，只需几行：

from fastapi import FastAPI
from pydantic import BaseModel
from triage import classify

app = FastAPI()

class Ticket(BaseModel):
    id: str
    text: str

@app.post("/classify")
def classify_ticket(t: Ticket) -> dict:
    return {"id": t.id, "label": classify(t.text)}

@app.get("/health")
def health() -> dict:
    return {"ok": True}
/health

接口用来接入监控，确认服务还活着。但留在笔记本上的代码不算部署。下一步是把服务打包，让它在任何地方都以同样方式运行，比如用一个简短的 Dockerfile：

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]

然后构建、运行，并以外部用户的身份亲自测一遍：

docker build -t triage-service .
docker run -d -p 8000:8000 -e LLM_API_KEY="$LLM_API_KEY" triage-service
curl http://localhost:8000/health
curl -X POST http://localhost:8000/classify \
  -H "Content-Type: application/json" \
  -d '{"id": "t-1", "text": "   "}'

注意

-e

参数：API 密钥通过环境变量传入，从不写进代码或镜像。最后一条

curl

发送的是空工单，正是当初让演示管道崩掉的那种情况，这次你应该拿到

other

标签。

镜像在本机跑通后，把它放到别人能通过网络访问的服务器或容器服务上，并把

/health

接入监控。在客户那里，这通常是对方已经在用的基础设施，所以第一个要问的问题是：服务部署在哪里，谁有权限看日志。

面试考的正是这个差距

根据 Sundeep Teki 的指南，FDE 的编码面试难度大致相当于 LeetCode 中等题，但放在客户场景中。在 Palantir，题目会围绕你为终端用户构建的东西来设定。

技术深挖环节时长 60 分钟，不写代码，评分看澄清问题的能力、根因分析，以及你如何权衡取舍。

Coursera 对 AI 工程师面试也有同样的观察：你得解释为什么选择某种方式来开发、部署和扩展方案。深挖环节不要求你敲代码，但仍然考验运维经验。

如果你从没亲手部署过任何东西，取舍这一环会立刻暴露出来：你能说“应该加重试”，却说不出重试几次、为什么。

读职位描述时还有一个陷阱。Teki 的指南指出，Anthropic 不用 FDE 这个头衔，而是为 Applied AI 团队招聘 Solutions Architect。这是一个售前岗位，职责是成为客户信赖的技术顾问。头衔并不能告诉你谁对生产环境负责。

读职位描述（JD）时，留意 “own deployment”“on-call”“ship to production” 这类表述。如果通篇都是 “workshop” 和 “demo”，那仍然是咨询岗位。

转岗者常犯的错误

最常见的是在简历上放一个打磨精美的演示，而不是一个正在运行的系统。“为 5 家客户搭建聊天机器人演示”所传达的信息，不如“部署了一个带测试、重试和人工复核队列的工单分类 API，目前在运行中”。

FDE 招聘方想看到的是你对一个运行中的系统负过责，而不只是做过设计。

第二个错误是用

try/except

吞掉所有错误，让代码蒙混过关。这是在掩盖错误，而不是处理错误。每个兜底分支都应该写日志，并且通向一个有人能看到的状态，比如例子里的

needs_review

。

第三个错误是以为转岗必须有学位。Coursera 谈的是 AI 工程整体而非 FDE，它认为学位并非必需，转岗者可以靠项目和认证入行。

如果目标是 FDE，就选一个像上面例子那样的项目：一个你亲手部署的服务，配上测试和文档。

最后一个错误更隐蔽：出了事故，你的第一反应是去找负责的团队。作为 FDE，那个团队就是你自己。

咨询顾问和 FDE 的差距，在于演示结束后你问自己的那个问题。一个问客户喜不喜欢；另一个问今晚什么会把这个系统弄垮。
