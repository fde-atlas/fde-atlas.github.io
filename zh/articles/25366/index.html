FDE 现场调试：如何复现现场 bug

FDE Times · 2026-10-25 · 约 6 分钟读完

摘要

本文以 Saronic 自主水面船只的 FDE 工作为背景，讲解现场 bug 调试方法：核心是先复现再修复。文章用一艘无人船进港偏航的假想案例，说明如何用环形缓冲区在本地记录完整数据、经低带宽卫星链路只传摘要，再通过回放判断问题出在软件、硬件还是网络层，并强调把触发 bug 的快照固化为回归测试、在受控试验中主动注入故障。

要点

  • 复现优先于修复：无法复现的 bug 不可靠。
  • 回放可复现则问题在软件，否则怀疑输入或不确定性。
  • 本地全量记录，慢速链路只传摘要，环形缓冲区保留故障前数据。
  • 多次回放、固定随机种子，先解决软件栈确定性问题。
  • 在受控试验中主动注入 GPS 丢失等故障，并预设客观通过标准。

一个以 Saronic 的 FDE 岗位为背景的假想案例说明：先记录足够数据复现故障，再动手修复。

要点速览

  • 在现场，复现 bug 往往比修复更难。先记录数据，再修。
  • 回放能复现，bug 就在软件里；不能复现，就要怀疑输入（硬件、网络）或软件栈存在不确定性。
  • 在受控试验中主动制造故障，例如 GPS 丢失或发动机故障，不要等真实环境替你触发。

设想一艘无人船，整个上午都在近海稳稳保持航向。到了下午进港时，它开始偏离航向，自行纠正，随后又偏了出去。回到办公室回放日志，一切看起来都正常。

处理这类故障，就写在从事自主系统的前线部署工程师（FDE）的岗位描述里。Saronic 制造自主水面船只，它对自家 FDE 的描述是：在真实环境中集成、部署并改进自主系统的人。

按照岗位描述，FDE 在部署期间要同时排查软件、硬件和网络问题，还有 50% 或更多的时间在国内外出差。

你也许永远不会登上一艘船。但几乎每个 FDE 都遇到过只在客户现场出现的 bug：没有调试器可挂，网络很慢，也没人能替你重现那个确切的时刻。海上是这个问题最严酷的版本，也因此最适合拿来学习。

在现场，难的是复现 bug

海上的某个时刻只发生一次。海浪、风、周围船只和卫星信号，不会再以同样的方式凑到一起。如果什么都没记录就当场打补丁，你既无法证明修复有效，也认不出 bug 何时卷土重来。

在 Saronic，负责规划海上试验的岗位通过结构化流程跟踪缺陷，为每个缺陷记录复现步骤、严重程度和纠正措施。值得记住的原则是：在能复现 bug 之前，你手里没有任何可靠的东西可修。

复现需要数据。据 Saronic 介绍，其 Corsair 船的耐久试验由多路摄像头产生了约 500 小时视频，总计约 17 TB。

该公司表示，会把这批数据用于模型开发、回放和回归测试。这次试验设计为连续运行，用来评估可靠性和耐久性，换句话说，就是把短时测试漏掉的故障暴露出来。

慢速链路逼你决定传回什么

一项关于自主船舶的研究指出，在海上，船只受制于低带宽的卫星链路。没人会通过这样的连接传 17 TB 数据。所以要把两件事分开：在船上的机器里记录全部数据，只向岸上发送足以让人知道“出事了”的信息。

下面是这个思路的简单草图。阈值、冷却期和字段名都只是示例：

import collections, json, time

def send_over_satlink(msg):
    """桩函数：替换为真实的卫星客户端，并加上队列和大小限制。"""
    payload = json.dumps(msg).encode()
    assert len(payload) < 512, "摘要必须足够小"
    print("SATLINK", payload)

class FieldRecorder:
    """在本地机器上记录全部数据，经慢速链路只发送摘要。"""
    def __init__(self, window_s=120, rate_hz=50, cooldown_s=60):
        self.buf = collections.deque(maxlen=window_s * rate_hz)
        self.cooldown_s = cooldown_s
        self.last_snap = {}  # 原因 -> 最近一次快照的时间

    def record(self, s):  # s：包含 t、heading_err_deg、gps_fix、link_ok、sw_version 的 dict
        self.buf.append(s)
        if abs(s["heading_err_deg"]) > 5:
            self.maybe_snapshot("heading_error")

    def maybe_snapshot(self, reason):
        now = time.monotonic()
        if now - self.last_snap.get(reason, float("-inf")) < self.cooldown_s:
            return  # 仍是同一次航向偏离，不再额外保存快照
        self.last_snap[reason] = now
        path = f"/data/snap_{int(time.time())}_{reason}.jsonl"
        with open(path, "w") as f:
            for s in self.buf:
                f.write(json.dumps(s) + "\n")
        # 经卫星只传几百字节，完整文件留在船上
        send_over_satlink({"reason": reason, "file": path, "n": len(self.buf)})

关键在环形缓冲区：检测到异常时，你手里已经有之前两分钟的数据，也就是导致故障的那一段。冷却期同样重要。没有它，一次持续几分钟的航向偏离会生成成千上万份快照，写满磁盘，也堵死卫星链路。

还要把三层的状态写进同一条记录：软件版本、GPS 状态和链路状态。这样到了隔离故障时，你手里才有证据。

示例：港内偏航

回到开头那艘船。这是一个用来练习方法的假设场景，并非 Saronic 公布过的事故。纸面上有三类假设：导航逻辑没处理好只在近岸出现的情况；传感器在港口环境下读数不同；连接中断导致系统切换模式。

就定位层而言，这个假设有依据。关于自主船舶的研究警告，GPS 失去信号、遭到干扰或欺骗时，船上无人的船只可能陷入危险境地。这正是记录中

gps_fix

字段如此重要的原因。

决定性的测试是回放。把记录下的那份快照原样输入办公室机器上的导航软件栈。如果虚拟船和海上一样偏航，bug 就在逻辑里，你也有了可以对着修的测试用例。

如果回放结果完美，有两种可能。第一种是你输入的数据与系统在海上实际收到的不同，这时要怀疑时序、硬件或网络。

第二种是软件栈本身不确定：线程顺序、处理延迟或某个随机步骤，都可能让同样的输入产生不同结果。

所以要多次运行回放，固定随机种子，使用模拟时钟。如果各次结果不一致，先解决软件栈的确定性问题，再对硬件下结论。

排查结果按下面的方式写进 bug 工单：

字段偏航 bug 的填写方式
症状接近港口时，航向误差反复超过阈值
条件时间、位置、GPS 状态、链路状态、软件版本
复现步骤回放某一份具体快照；记录运行次数，以及其中多少次出现 bug
严重程度是否影响运行安全
可疑层软件、硬件还是网络，附回放得到的证据
纠正措施修复方案，外加一个基于这份快照的回归测试

很多人会跳过最后一行。触发 bug 的快照应当成为永久测试，这样下次试验就不必再到海上重新寻找老 bug。

抢在真实环境之前触发故障

避免海上意外的最好办法，是在受控试验中自己制造故障。2013 年的一次海上试验中，GPS 被有意干扰，一套原型系统自动切换到了 eLoran。

那次测试针对的是定位系统，而非自主船舶，但方法可以原样照搬。

最近的一次自主化演示中，包含一项针对模拟机械故障的应急响应演练，同时由岸上远程监控船只。

这类测试只有在事先定好标准时才有价值。Saronic 围绕测试矩阵组织测试，每项需求都对应一个客观的通过或失败标准。

“降级方案运行良好”只是一种印象。“GPS 丢失时切换到备用系统，偏差不超过允许值”才是可以检验的标准。

还有安全问题。在 Saronic，现场测试负责人实时指挥试验，并对试验安全负责。要有意注入故障，必须事先与此人商定；谁都不能擅自切断正在运行的系统。

常见错误

最常见的错误，是只在自己熟悉的那一层调试。软件工程师一头扎进代码，证据却指向天线或链路。这就是 FDE 岗位描述把软件、硬件和网络写在同一行的原因。

第二个错误，是想通过慢速链路把所有数据都传回去，结果在最需要链路的时刻把它堵死。第三个错误，是当场修复却不保存快照，修复永远无法证明。第四个错误，是测试没有通过或失败标准，事后再争论结果到底好不好。

缩短现场与代码之间的回路

Saronic 的测试规划人员每天与软件团队、船只运营和供应商协作，力求快速而彻底地解决每个问题。好的 bug 工单能让这个回路持续运转：办公室里的人拿到快照和复现步骤，不必亲赴现场也能弄清发生了什么。

在职业层面，阅读 FDE 招聘信息时，留意“software, hardware, and networking”或“real-world environments”这类措辞：它们意味着这份工作要求现场调试。简历上不要只写“处理过生产事故”。

讲一个具体 bug 的故事：你如何采集数据、如何复现、把问题隔离到哪一层、又把它变成了什么回归测试。面试时，这样的故事远比一串工具清单更有说服力。

大海不给你第二次机会。好的工程师，是能把那个唯一的故障时刻带回办公室、想回放多少次就回放多少次的人。
