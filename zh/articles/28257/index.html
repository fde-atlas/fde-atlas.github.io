前沿部署工程，第 6 部分：Agent 框架对比

摘要

本文是前沿部署工程系列第六篇，以虚构客户 Acme 为例，比较 ADK、LangGraph、CrewAI 与 AutoGen（及其后继 Microsoft Agent Framework）四个 Agent 框架。作者指出所有框架都建立在 ReAct、反思、监督者、图四种模式之上，模式比语法更重要；同一任务在 ADK 与 LangGraph 中实现后仅数据传递方式不同。文中给出选型的六个问题，并强调框架的重要性低于发现与数据准备阶段。

要点

  • 四个框架底层都是 ReAct、反思、监督者、图四种模式。
  • 同一路由任务在 ADK 与 LangGraph 中写法不同但逻辑相同。
  • 选型首问：客户团队离开后由谁维护代码。
  • AutoGen 已归档，新项目应改用 Microsoft Agent Framework。
  • 不同框架的 Agent 可通过 A2A 与 MCP 协作。

Agent 框架到底做什么？

AI Agent 到底是什么在 Agent 系列中，将 Agent 定义为模型加指令、工具和一个循环。你可以在一个简短的 Python 文件里自己写出这个循环。而框架可以让你不必在每个项目中重复编写它。

简单的定义：Agent 框架是一个替你运行 Agent 循环的库，这样你只需编写与你的问题相关的部分。

更准确地说，框架为你提供六样东西：

  • 模型连接器。 一种调用模型的方式，无论是 Gemini 还是其他提供商。
  • 工具定义。 它把一个 Python 函数变成一个工具（模型可以请求你的代码运行的函数），带有名称、描述和带类型的参数。
  • 编排（决定接下来运行什么）。单个 Agent 的循环，以及组合 Agent 的方式：依次执行、并行执行、循环执行或以图的形式执行。
  • 状态与记忆。 状态是一次运行在步骤之间记住的内容；记忆是 Agent 在对话之间记住的内容。
  • 回调或中间件（在模型或工具调用之前或之后运行的你的代码）。这是防护栏所在之处。
  • 可观测性与部署钩子。 追踪、日志，以及将 Agent 作为服务运行的方式。

最接近的类比是 Django 这样的 Web 框架：它运行请求循环，而你编写视图。同样地，Agent 框架运行 Agent 循环，它的编排相当于 URL 路由，它的回调相当于 Web 中间件。

Agent 框架的作用：你编写指令、工具、规则和检查；框架为你提供模型连接器、循环、编排、状态、回调和追踪；平台负责运行它；无论你选择哪个框架，模型、数据、工具代码和评测集都保持不变

注意更换框架时哪些东西不会改变：模型、客户的数据、工具内部的代码以及你的评测集。我的看法是：这正是为什么框架的重要性低于大多数人的预期，也远低于探索（第 2 部分）和数据就绪度（第 4 部分）。

每个框架底层都包含哪些模式？

职位描述中列出了 ReAct、自我反思和层级委派。这些是模式：每个框架都用自己的一套语法来实现的思想。一旦掌握了这些模式，你就能读懂任何框架的代码。

ReAct：思考、行动、观察、重复

ReAct（推理与行动）来自 Yao 及其同事 2022 年的一篇论文。模型先写一个简短的推理步骤，选择要调用的工具（行动），读取结果（观察），然后重复这一过程，直到能够给出答案。如今大多数工具调用型 Agent 都运行 ReAct 循环。

在 Acme，市场部的 Maria 询问“Acme Pure Refill Launch 在西欧的表现如何？”市场 Agent 推理出需要支出和销售数据，于是调用支出工具，读取结果，再调用销售工具，然后给出答案。

当一个拥有少量工具的 Agent 就足够、且你无法预知步骤时，选择 ReAct。在 ADK 中，这是一个

Agent

带工具的 Agent；在 LangChain 中则是

create_agent

，它运行在 LangGraph 上。

ReAct 循环：模型推理它需要什么，通过调用工具来行动，观察结果并重复，直到能够回答；在这里，营销 Agent 先获取支出数据，再获取销售数据，然后回答 Maria

反思：起草、批评、修改

反思（职位描述中称之为自我反思）增加了一个检查步骤。第一步产出草稿，第二步对草稿进行批评，然后修改草稿。两篇著名论文描述了这一思想：Reflexion（Shinn 等人，2023）和 Self-Refine（Madaan 等人，2023）。批评者可以是模型，也可以是普通代码。

在 Acme，撰写者起草答案，代码将每个数字与专家的结论进行核对（路由器，让代码选择路径），因为核对数字不需要判断力。

该检查是撰写者 after-model 回调中的普通代码。简化后，关键的代码行如下：

def writer_after_model(callback_context, llm_response):
    st = callback_context.state
    text = "".join(p.text for p in llm_response.content.parts
                   if p.text and not p.thought)
    evidence = [str(st[k]) for k in FINDINGS_KEYS if st.get(k)]
    missing = ungrounded_numbers(text, evidence, st.get("question", ""))
    if missing:
        text = fallback_answer(evidence)  # what the specialists reported
    llm_response.content.parts = [types.Part(text=text)]
    return llm_response

agents 系列中的路由器，让代码选择路径解释了每一行代码，包括为什么要替换整个答案而不是打补丁。

主管：一个 Agent 把工作交给其他 Agent

主管（也称为协调者或管理者）是一个读取请求并将其中的部分工作交给工作者 Agent 的 Agent。当工作者还可以拥有自己的工作者时，职位描述称之为层级委派。通常由模型来做选择。

在 Acme，协调者的模型会读取 Maria 的问题，并选择营销或供应团队。

当专家很多、请求变化很大、且选错的代价很容易挽回时，选择主管模式。在 ADK 中，你给协调者

Agent

另外两种模式：在反思模式中，撰写者起草，检查者批准或将草稿退回，并限制轮次；在主管模式中，模型读取请求并将其交给多个工作者 Agent 之一

CrewAI。 一个具有两层结构的开源框架。Crews 是由角色扮演 Agent 组成的团队，每个 Agent 都有角色、目标和背景故事，通过顺序或层级流程完成任务。Flows 是具有状态、条件和循环的事件驱动工作流；文档称 Flows 是应用程序的骨干。最新版本是 2026 年 10 月 14 日发布的 1.15.28。当问题自然地映射为角色和任务时选择它，并在需要控制时把 crews 放进一个 Flow 中。

AutoGen 与 Microsoft Agent Framework。 AutoGen 是微软的智能体相互通信的研究框架。截至 2026 年 10 月，其仓库已归档，README 表明微软不再提供错误修复、安全修复、新功能或支持，并建议新用户从 Microsoft Agent Framework 开始：它是直接后继者，由同一批团队构建，将 AutoGen 的智能体理念与 Semantic Kernel 的企业级功能相结合。它支持 Python 和 .NET，其 1.0 Python 包已于 2026 年 4 月 2 日发布。当客户基于微软技术栈构建时，选择它。当职位描述提到 AutoGen 时，应将其理解为多智能体对话模式，并且不要在 AutoGen 本身上启动新的生产工作。

截至 2026 年 10 月，四个框架并排对比：ADK、LangGraph、CrewAI，以及 AutoGen 及其后继者 Microsoft Agent Framework，从构建块、代码中的路由、语言、最新版本、A2A 和 MCP 支持以及最佳适用场景等方面进行比较

一个坦诚的缺口：这些版本号每周都在变化。在你做决定的当天查看每个项目的发布说明，并把日期写进设计文档。

同一个任务在两个框架中是什么样子的？

以下是 Acme 路由器的核心决策：一个问题进来，代码决定应由营销还是供应来回答，然后被选中的专家进行回答。这些专家是存根，因此代码无需模型或 API 密钥即可运行。我用 ADK Python 2.12.0 和 LangGraph 1.2.16 运行了两个版本。

首先，ADK：

ADK 中的 Acme 路由决策：route 是一个普通函数节点，返回一个带有 route 值的 Event，一条 dict 边将问题发送给匹配的专家

  • route 是一个函数节点。 它返回一个 Event，其 route 值指明下一步。不调用任何模型，因此零成本，且每次都给出相同的答案。
  • dict 边将每个 route 值映射到一个节点。ADK 只运行匹配的那一个。
  • 一个节点的输出成为下一个节点的 node_input。 数据沿着边流动。

现在在 LangGraph 中实现同样的功能：

LangGraph 中的同一决策：所有节点共享一个带类型的 state，一个返回下一个节点名称的路由函数，以及通过 compile 得到可运行的图

  • State 是一个带类型的字典，由所有节点共享。节点只返回它们修改的键。
  • add_conditional_edges 调用路由函数，并使用返回的键来选择下一个节点。
  • compile() 将构建器转换为一个可以用 invoke 运行的图。

两者都是图，都在纯 Python 中路由，同一个单元测试可以验证两者。它们的区别在于数据如何流动：ADK 将每个节点的输出传递给下一个节点，而 LangGraph 维护一个共享的 state。我的看法：一旦你理解了这个模式，另一种语法只需一天就能学会，因此将要负责维护这段代码的团队的技能远比这更重要。

我如何为客户选择框架？

按以下顺序提出六个问题：

选择框架的六个问题，按顺序为：谁来负责维护、它将在哪里运行、规则是否必须每次都成立、团队使用哪些语言、项目是否有人维护，以及它是否支持 A2A 和 MCP

  • 谁来负责维护？ 客户的团队会在你离开后继续维护代码（第 7 部分），所以他们熟悉的框架胜过他们不了解的、略胜一筹的框架。
  • 它将在哪里运行？ 如果在 Google Cloud 上运行，配合 Agent Runtime 和 Gemini Enterprise，ADK 可以端到端衔接。
  • 规则是否必须每次都成立？ 如果是，你就需要图工作流。
  • 使用哪些语言？ Microsoft Agent Framework 在图中列出的语言基础上增加了 .NET。
  • 项目是否有人维护？ 已归档的项目不会再获得安全修复。
  • 它是否支持 A2A 和 MCP？ 目前这四个选项都以某种形式支持。

对 Acme 来说，这些答案指向 ADK。Acme 运行在 Google Cloud 上，Agent 将运行在 Agent Runtime 上，用户将通过 Gemini Enterprise 访问它们，而且路由规则必须每次都成立。你不必丢弃数据科学团队的 LangGraph 笔记本。它可以作为第 7 部分原型的依据：保留其中的测试问题和提示词。而且由于路由器通过 A2A 调用各专家 Agent，供应团队以后即使用 LangGraph 重建他们的 Agent，路由器也无需任何改动。

用不同框架构建的 Agent 之间如何通信？

两个开放协议使混合系统成为可能：

  • A2A（Agent2Agent）让一个 Agent 发现另一个 Agent、把工作交给它并取回结果。截至 2026 年 10 月，最新发布的规范版本是 1.0.0，它是 Linux 基金会的项目。
  • MCP（Model Context Protocol）让一个 Agent 发现并调用另一台服务器上的工具。最新规范版本的日期是 2026 年 7 月 28 日。

每个框架都以自己的方式支持它们：

  • ADK：RemoteA2aAgent 调用远程 Agent，McpToolset 连接 MCP 服务器。
  • LangGraph：LangSmith 的 Agent Server 在 /a2a/{assistant_id} 提供 A2A 端点，支持 A2A 1.0；LangChain 的 MCP 支持自 1.4 版起仍标记为 beta。
  • CrewAI：A2AClientConfig 和 A2AServerConfig（安装 crewai[a2a]），以及作为工具的 MCP 服务器。
  • Microsoft Agent Framework：用于工具的 MCP 客户端和 A2A 托管示例。

安全地混用框架：Maria 在 Gemini Enterprise 中提问，ADK 路由器通过 A2A 调用营销 Agent 和一个用 LangGraph 重建的供应 Agent，每个专家 Agent 通过 MCP 调用其工具；路由器永远不需要知道另一端使用的是哪个框架

Agent 系列中 Agents talking to agents 一文中的规则仍然适用：当另一端是拥有自己模型、规则和权限的 Agent 时使用 A2A，当它是工具时使用 MCP。那篇文章详细讲解了 Agent 卡片、任务和消息。

动手试试：在两个框架中运行同一个路由器

你需要 Python 3.11 或更高版本。在一个全新的虚拟环境中安装这两个框架：

python3 -m venv .venv && source .venv/bin/activate
pip install google-adk langgraph

将上面的 ADK 代码保存为

try_adk.py

并在底部加上这个运行器：

import asyncio
from google.adk.runners import Runner
from google.adk.sessions import InMemorySessionService
from google.genai import types


async def main():
    runner = Runner(app_name="acme", agent=root_agent,
                    session_service=InMemorySessionService(), auto_create_session=True)
    for q in ["What did the spring campaign cost?", "What did the stockouts cost us?"]:
        msg = types.Content(role="user", parts=[types.Part(text=q)])
        async for ev in runner.run_async(user_id="maria", session_id=q, new_message=msg):
            if ev.output and "answers" in str(ev.output):
                print(ev.output)

asyncio.run(main())

将 LangGraph 代码保存为

try_langgraph.py

并以以下内容结尾：

for q in ["What did the spring campaign cost?", "What did the stockouts cost us?"]:
    print(graph.invoke({"question": q})["answer"])

当我运行每个脚本时，两者打印出相同的内容：

marketing answers: What did the spring campaign cost?
supply answers: What did the stockouts cost us?

然后尝试以下改动：

  • 把规则移出去。 将关键词检查放到一个单独的文件 rules.py 中，不导入任何框架，并从两个路由函数中调用它。为它编写一个 pytest 测试。这是让业务规则在框架之间保持可移植性的好习惯。
  • 添加一个“both”路由。 在 LangGraph 中，让路由函数返回一个节点名称列表，两个节点就会并行运行。在 ADK 中，使用节点元组和 JoinNode，如路由器：让代码选择路径所示。比较每个框架需要多少代码。

可能出问题的地方

  • 凭演示做选择。 一个精彩的十分钟演示无法说明客户的运行时环境、身份提供方或团队技能。先问那六个问题。
  • 业务规则写在框架类里。 更换框架就意味着重写它们。请把规则保留在纯 Python 中。
  • 必须始终成立的规则却用监督者。 由模型选择路由通常是对的，但“通常”对合规性来说还不够好。
  • 没有上限的反思。 一个永不满足的批评者会烧掉成本。请限制轮数。
  • 一个进程里放两个框架。 两个运行时和两套追踪配置很难调试。改为在 A2A 边界处混合框架。
  • 版本未固定，或协议版本未经测试。 固定版本，并尽早测试真实的 A2A 调用，因为一方可能说 1.0，而另一方只支持 0.3。

我现在会怎么做

  • 阅读每个框架文档中的一个示例，找出其中的四种模式。
  • 运行上面的两个脚本，然后在每个脚本中添加“both”路由。
  • 把那六个问题、客户的回答和日期写进你的设计文档。
  • 把每条业务规则都放在一个不依赖框架的模块中并配上自己的测试，并在不同团队拥有的 Agent 之间设置 A2A 边界。

我们学到了什么？

  • Agent 框架替你运行 Agent 循环，而模型、数据、工具代码和评测集无论你选择哪个框架都保持不变。
  • 每个框架的底层都是四种模式（ReAct、反思、监督者和图），一旦掌握了它们，你就能读懂任何框架的代码。
  • 当一条规则必须在每次请求上都成立时，把它放进图中并用纯代码来决定，而不是让模型去选择。
  • ADK、LangGraph、CrewAI 和 Microsoft Agent Framework 的差异主要在于语法以及数据在步骤之间的流动方式，因此将由谁来负责代码的团队技能比微小的功能差异更重要。
  • 按顺序回答六个问题来做出选择，首先从谁将负责该系统以及它将运行在哪里开始，并把答案和日期写入设计文档。
  • 用不同框架构建的 Agent 通过 A2A 协同工作，并通过 MCP 访问工具，因此应在 A2A 边界处混合使用框架，绝不要在同一个进程内部混用。

接下来是什么？

框架已经选定。在第 7 部分：数天完成原型，数周投入生产中，我们将构建一个计划丢弃的原型，借助 AI 辅助编程加快速度，然后逐步完成加固清单以及向 Acme 自有团队的交接。它建立在本文所做的选择之上：路由器采用 ADK，并由不同团队负责的 Agent 之间以 A2A 作为边界。
