带基线的 AI Agent 评测：Intercom Fin 示例

原标题：AI agent evals with a baseline: Intercom Fin example

FDE Times · 2026-10-24 · 约 6 分钟读完

摘要

文章以 Intercom 的招聘广告为切入点：其都柏林前沿部署软件工程师职位承诺为 AI Agent Fin 带来可衡量的业务成果，却没有给出任何目标数字。作者认为，这意味着定义衡量方式是 FDE 自己的责任。Fin 的公开数据（Anthropic 案例中的 51% 开箱解决率、AWS 案例中首 30 天平均 56%）只是平均值，不能当作对具体客户的承诺。文章建议用客户真实对话构建评测集，在首次运行前确定主指标和基线，并像 Intercom 内部那样，每次改动都与基线对比、检查回归。文中给出一个 30 条“订单查询”对话的示例：首轮解决率 60%，按失败原因分组后修复订单号格式问题，第二轮升至 83% 且无回归。文章还列出常见错误，并说明如何在简历和面试中呈现这类经历。

要点

  • Intercom 招聘广告承诺可衡量成果，却未给出目标数字。
  • Fin 公开的 51% 与 56% 是平均值，不代表具体客户。
  • 应在首次运行前用客户真实对话确定评测集与主指标。
  • 示例中解决率从 60% 升至 83%，且无回归。
  • 常见错误：事后选指标、只看解决率、只用自造的简单用例。

Intercom 会将 Fin 的每一次变更与基准进行对比测试，而优秀的前沿部署工程师也会在与每位客户合作时保持同样的习惯。

简要概述

  • Intercom 的 FDE 招聘广告承诺可衡量的业务成果，却没有给出任何目标，因此定义衡量标准的工作落到了 FDE 身上。
  • Fin 的公开数据是开箱即用 51%，前 30 天平均 56%，但这两个数字都不是你正在服务的客户的数据。
  • 诚实的答案是：基于客户自己的对话构建评测集，并在首次运行之前确定基准和主要指标。

Intercom 在都柏林的前沿部署软件工程师招聘广告做出了一个重大承诺：确保公司的客服 AI Agent Fin 带来真实、可衡量的业务成果。但读到页面末尾，你找不到任何一个具体目标。

这个空白可以被视为这份工作的第一道考验。当没有人说“你必须达到这个数字”时，FDE 就必须决定衡量什么、如何衡量，以及与什么进行比较。

这种情况很早就会出现。

广告描述了与 Fin 的战略客户紧密合作，了解他们的业务问题和技术需求。在客户现场，你几乎肯定会听到的问题是：“对我们来说，Fin 能解决多大比例的问题？”本指南将展示如何用评测集而非承诺来回答这个问题。

公开数字不是客户的数据

有两个公开数据值得记住。Anthropic 的案例研究称，Fin 在未经任何定制的情况下，开箱即用即可达到 51% 的解决率。AWS 的案例研究称，客户在前 30 天内平均达到 56%。

这两个数字之所以不同，是因为它们是在不同时间点、由不同来源测量的。两者都是平均值，因此都无法告诉你坐在对面的零售商或保险公司会是什么情况。

所以，如果你把“56%”当作保证，那么当客户的真实数字低于此值时，他们对这句话的记忆会比任何演示都深刻。专业的回答是：“我们会在你们自己的对话上进行测量，然后报告数字。”

Intercom 如何衡量自己？

这个方法已经存在，而且来自 Intercom 本身。根据 Anthropic 的案例研究，Fin 的每一次变更，从小幅调整到重大更新，都会与生产环境中运行的基准进行严格测试。测试会同时考察多项指标：回答准确性、解决率、客户满意度和回复质量。

Intercom 将此称为评测驱动的交付，并表示这正是其 AI 研究团队在构建和打磨产品时所使用的同一套纪律。其 Evals 产品使用基于客户自身对话构建的模拟场景来测试 Fin 的行为。

Intercom 的定义很简洁：评测（Eval）是一组有名称的模拟（Simulation），也就是多轮测试对话。致力于 Fin 的机器学习科学家 Pedro Tabacof 写道：如果你认真对待 AI，就必须认真对待评测。

示例：针对“我的订单在哪里？”的 30 个用例评测

想象客户是一家零售商，AI Agent 需要通过内部 API 回答订单问题。在改动提示词或代码之前，你要按照 Tabacof 对 A/B 测试的建议：在开始之前先确定一个主要指标。

这里的主要指标是无需转接人工客服即可解决的对话占比。回答准确率是次要指标，不能下降：如果解决率上升但回答变得更不准确，该变更将被拒绝。

你取 30 段订单对话，为每段标注预期结果，然后编写一个简单的运行器：

import json

# Each line: one multi-turn test conversation + the expected outcome
# {"id": "o-07", "turns": ["Where is my order #A-1029?"], "expect": "resolved"}
CASES = [json.loads(line) for line in open("evals/orders.jsonl")]

def run(agent, cases):
    results = {}
    for c in cases:
        out = agent.converse(c["turns"])
        results[c["id"]] = {"ok": out.outcome == c["expect"],
                            "reason": out.failure_reason}
    return results

def rate(results):
    return sum(r["ok"] for r in results.values()) / len(results)

baseline = json.load(open("evals/baseline.json"))  # the previous run
current = run(agent, CASES)
regressions = [k for k, r in current.items()
               if baseline[k]["ok"] and not r["ok"]]
print(f"{rate(baseline):.0%} -> {rate(current):.0%}, regressions: {regressions}")

最重要的一行是

regressions

。整体解决率更高，仍可能掩盖一些以前通过、现在失败的用例，而这些正是客户最先注意到的。

在修复任何东西之前，先阅读失败案例

假设第一次运行解决了 30 个用例中的 18 个，即 60%。这个结果成为基线。现在最有价值的事情不是修改提示词，而是阅读那 12 个失败案例，并按原因分组。

在这个例子中，七个失败是因为用户输入的订单号形如“#A-1029”，而 API 只接受“A1029”。两个失败是因为 API 超时，还有三个询问的是订单范围之外的问题。

最大的分组指明了应优先修复什么，而修复只需一行代码，在查询函数顶部对订单号进行规范化：

order_id = re.sub(r"[^A-Za-z0-9]", "", raw_order_id)  # "#A-1029" -> "A1029"

下一次运行达到 30 个中的 25 个，即 83%，且回归列表为空。剩下的五个属于另外两个分组，已经归入下一轮的工作。

在真实客户处再做一遍

面对真实客户时，流程保持不变。以他们的真实对话作为素材，就像 Intercom 的 Evals 从客户对话构建场景一样，并与客户方了解业务的人一起标注，因为你无法独自判断关于他们退款政策的哪个答案是正确的。

然后在第一次运行之前，把主要指标和次要指标写进一份客户也会阅读的文档。每一次变更，哪怕只是提示词中的一行，都要对照基线重新运行，就像 Intercom 对 Fin 本身所做的那样。

这个顺序也解决了由谁设定目标的问题。当客户从一开始就认可主要指标时，最终数字就是双方都认可的结果，而不是 FDE 给自己打的分数。

需要避免的错误

第一个错误是在看到结果之后才选择指标。先运行，然后挑一个最好看的数字来汇报，这是失去信任最快的方式，而这正是“事先确定指标”这条建议所要防止的。

第二个误区是只看解决率。Intercom 还会衡量准确率、满意度和回复质量，因为一个用错误答案“解决”对话的 Agent，比把它转交给人类的 Agent 更糟糕。

第三个误区是评测集只包含你自己编造的简单案例。像“#A-1029”这样的案例只会出现在真实对话中，而且它们往往是失败案例中最大的一类。

这项能力在简历和面试中如何体现？

阅读 FDE 招聘广告时，留意那些附带“可衡量的成果”却没有具体数字的措辞。看到这类表述时，准备好一个具体的故事，讲述你曾亲自设定衡量标准的一次经历：你选择了哪个指标、为什么选择，以及结果如何。

在 Staff 级别，Intercom 期望候选人能够设定方向、对结果负责，并直接与客户以及市场推广团队合作。一个带有基线的评测集让你能用数字向销售团队汇报结果，而不是在演示之后凭印象汇报。

在简历上，一条好的经历描述包含三个部分：你连接的系统、你如何衡量它，以及前后的数字。参照上面的例子：“为一个订单查询 Agent 构建了包含 30 段对话的评测集；自助解决率从 60% 提升到 83%（18→25/30），且没有出现回归问题。”

本周练习

选择一个包含用户级数据的公开 API，例如订单、工单或预约，并编写一个调用它的简单 Agent。编写 30 段测试对话，确定一个主要指标，先运行一次作为基线，并记录每次失败的原因。

你带到面试中的不是代码仓库，而是这句话：“12 个失败中有 7 个来自用户输入订单号的方式”，而只有亲自做过衡量的人才能说出这句话。
