“全栈工程师”这个词被广泛使用，但其定义却一直模糊不清、各自解读。有人自称“会前端和后端就是全栈”，也有人认为必须涵盖基础设施和DevOps才能称为全栈。

首先，让我们来梳理一下这个词的准确含义和职责范围。

仅限拥有5年以上实战经验的工程师

高单价・直接承包项目信息

全栈工程师是指能够独立承担从前端到后端，甚至包括基础设施领域在内的系统开发多个环节的工程师。“全栈（full stack）”意味着在多个技术领域具备一定以上的技能，并掌握开发的整体面貌。

需要注意的是，全栈工程师并不是一个特定的职位名称。即使招聘启事上写着“招聘全栈工程师”，各企业要求的技能范围也各不相同。有的企业可能认为会React和Node.js就足够了，而有的企业则可能要求具备AWS的搭建经验。

因此，与其说全栈工程师是一种职位，不如将其理解为“能够覆盖广泛技术领域的技能组合”的称谓更为准确。

全栈工程师的职责范围，大致可分为以下3个领域。

领域主要职责代表性技术
前端实现用户直接接触的界面HTML/CSS、JavaScript、React、Vue.js、Next.js
后端服务器端处理、API设计与实现、业务逻辑构建Java、Python、Ruby、PHP、Go、Node.js
基础设施应用程序基础的搭建与运维AWS、GCP、Azure、Docker、Kubernetes、Terraform

在小型项目或初创公司中，由一名工程师负责所有这些工作的情形并不少见。而在大型项目中，全栈工程师则常常作为前后端之间的桥梁，承担团队间的协调工作。

有人认为“全栈工程师＝什么都会的超人”，但现实稍有不同。并非在所有领域都达到专家级别，通常是在具备广泛基础知识的同时，在特定领域发挥深厚的专业性。

例如，以后端开发为主轴，同时也能胜任前端和基础设施工作的工程师；或者以前端见长，同时能够进行API设计和数据库操作的工程师。这种“擅长领域＋广泛覆盖范围”的组合，才是现实中全栈工程师的真实面貌。

这也与后文所述的“T型人才”理念相关联，是否具备这种“核心专业性”将极大影响市场价值。

全栈工程师所需的技能多种多样。本文将针对前端、后端、数据库、基础设施这4个领域，讲解具体的技术栈和所需技能。

前端开发负责实现用户直接看到的界面部分。基础是使用HTML/CSS进行标记，以及用JavaScript实现动态处理。在当前的Web开发中，使用React、Vue.js、Next.js等框架进行开发已成为主流。

所需技能包括：组件设计的理解、状态管理（Redux、Vuex、Zustand等）、API对接、响应式设计的实现等。此外，能够准确还原UI/UX设计师所设计稿的编码能力也不可或缺。

不仅仅是按照设计稿实现，能否在实现时考虑性能和可访问性，将影响作为工程师的评价。

后端开发负责实现服务器端运行的业务逻辑和数据处理。主要的服务器端语言包括Java、Python、Ruby、PHP、Go、Node.js（TypeScript）等。每种语言都有相应的框架，如Spring Boot、Django、Ruby on Rails、Laravel、Gin、Express/NestJS等。

全栈工程师所需的能力，并不仅限于能用框架实现功能的水平。更重要的是能够做出着眼于系统整体的设计决策，例如 API 设计、认证与授权的实现、错误处理、日志设计等。

正因为同时理解前端和后端，才能提出合适的 API 设计和高效的数据结构。这是全栈工程师的优势所在，也是其能够充当前后端之间桥梁的价值源泉。

数据库是存储和管理应用程序所处理数据的重要基础。全栈工程师需要具备的能力是：合理选用 MySQL、PostgreSQL、MongoDB 等数据库，并具备表设计和查询优化的技能。

在掌握基本的 CRUD 操作和 SQL 编写的前提下，还需要具备性能方面的知识，例如索引设计、规范化与非规范化的取舍、N+1 问题的解决等。在大型服务中，数据量增长带来的性能劣化往往是常见问题。因此，最好也掌握一些在运维阶段能派上用场的技能，例如慢查询的定位与优化、引入合适的缓存策略等。

基础设施领域负责应用程序运行基础的搭建与运维。在当前的开发中，使用 AWS、GCP、Azure 等云服务已成为主流。这要求理解 EC2、Lambda、S3、RDS、CloudFront 等各项服务的特性，并具备合理组合运用的知识。

此外，使用 Docker 和 Kubernetes 进行容器化运维、使用 Terraform 实现 Infrastructure as Code（IaC）、使用 GitHub Actions 或 CircleCI 搭建 CI/CD 流水线等 DevOps 技能的重要性也在不断提升。Linux 的基本操作、网络基础知识以及安全意识，也是覆盖基础设施领域不可或缺的能力。

📌Pro Tip 懂“基础设施”能让单价飙升 很多工程师喜欢写代码，却往往对基础设施的搭建和维护敬而远之。正因如此，能够包揽这部分工作的全栈工程师在现场备受重视，单价谈判也更容易通过。“既能写代码，又懂基础设施”的人才具有很高的稀缺价值。

即使同样名为全栈工程师，其市场价值也会因技能深度而有很大差异。下表按领域整理了年薪 600 万日元级别与年薪超过 1,000 万日元级别的区别。

领域年薪 600 万日元级别年薪超 1,000 万日元级别
前端HTML/CSS 修改、使用现有组件React/Next.js 的设计与性能优化
后端使用框架进行实现架构选型、API 设计、技术选型
数据库基本的 CRUD 操作、SQL 编写大规模数据的调优与设计决策
基础设施按操作手册进行操作、修改配置IaC（Terraform）/ CI/CD 搭建与运维设计

从这张表可以看出，年薪超过 1,000 万日元的工程师不仅“能实现”，还达到了“能做出设计决策”的水平。关键不在于“广而浅”，而在于要有意识地思考“能做到多深”，这是能否获得高单价的关键分水岭。

相信很多人都听过“别当全栈工程师”“全栈工程师没用”这样的声音。事实上，确实有一部分现场存在这样的评价。但“全栈工程师不需要”是一种误解，市场需求反而在逐年增长。

下面将解说这些负面评价产生的原因，以及如何克服它们。

对全栈工程师的负面评价，主要有三个原因。

①专业性容易不够深入

由于学习的技术范围很广，人们会担心每一项技术的深度不足。在需要高度专业性的场合，可能会给人“半吊子”的印象。

②难以持续跟进所有领域的最新技术

IT 技术进化迅速，前端和后端都不断有新技术涌现。要持续跟进所有技术，现实中非常困难，存在知识过时的风险。

③优势不鲜明

说“什么都会”的人，反而容易让人产生疑问：“这个人最大的优势到底是什么？”与拥有明确专业领域的人相比，有时难以获得好评。

这些批评有一定的合理性。尤其是当“所有领域都只是平均分”时，被压价的风险会更高。

那么，作为全栈工程师该如何提升市场价值呢？答案就是进化为“T 型人才”。

所谓 T 型人才，是指在一个专业领域拥有深厚见识（纵轴），同时又能广泛覆盖其他领域（横轴）的人才。例如，在后端开发中具备能进行架构选型和设计决策水平的专业性，同时前端和基础设施也都能顺利应对的工程师。

“后端 120 分，其他 80 分”的人才，与“全部 80 分”的人才有着明确的差异化。反过来说，如果所有领域都只停留在“能实现”的水平，就会被看作可替代的人才。

拥有一个作为立足点的专业领域，并在该领域达到“能做出设计决策”的水平。这就是摆脱“样样通、样样松”的具体战略。

📌Pro Tip “T 型”的纵轴是什么都可以，但深度才是关键 无论是前端、后端还是基础设施，只要在其中一个领域达到“能做出设计决策的水平”，它就可以成为纵轴。重要的不是“选择什么”，而是“能做到多深”。

虽然有“全栈工程师不需要”的声音，但企业方面的需求确实存在。企业对全栈工程师的期待主要有以下四点好处。

①提升开发速度

由于一个人就能完成开发流程的大部分环节，比多人分工协作的开发推进得更迅速。减少了各负责人之间的交接和协调时间，有助于缩短整个项目的交付周期。

②削减人力成本与资源

如果不用分别雇用前端工程师和后端工程师，而是交给一名全栈工程师负责，就有可能降低总成本。

③灵活应对多种角色

随着 DevOps 和敏捷开发的普及，一名工程师从开发到运维全程参与的场景越来越多。全栈技能组合正好契合这种一线需求。

④能以整体最优的视角行动

由于能够俯瞰系统整体，可以在理解各环节和技术之间联系的基础上提出并实现最优方案。例如根据后端的约束调整前端实现，能够避免陷入局部最优的判断，这是一大优势。

需求尤为突出的是初创企业以及希望推进信息化的中小企业。在以少数人进行服务开发的初创企业中，很多情况下没有预算配备多名专业工程师。因此，能够一人承担广泛职责的全栈工程师备受青睐。

即使在难以配备专业人才的中小企业，能够统筹整个开发并发挥领导作用的人才也十分宝贵。从自由职业者的接单趋势来看，面向全栈工程师的项目也非常丰富。其特点是 Web 服务和 DX 推进项目的招聘尤为醒目，允许远程办公的项目也很多。

根据经济产业省的估算，到 2030 年 IT 人才缺口最大约为 79 万人。在人才需求不断攀升的背景下，能够广泛应对各类工作的全栈工程师今后将越来越受到关注。

对于自由职业工程师来说，最关心的莫过于实际能赚多少钱。本文将结合具体数据，讲解与正式员工的年收入比较、高单价项目的条件，以及不同商流下实际到手收入的差异。

全栈工程师的年收入因雇用形态而有很大差异。

正式员工的情况

正式员工全栈工程师的平均年收入约为 600 万至 700 万日元。作为参考，系统工程师（委托开发）的平均年收入约为 557 万日元。全栈工程师有偏高的倾向，但差距并不大。

自由职业者的情况

另一方面，自由职业全栈工程师的年收入据说在 960 万至 1,500 万日元左右。月单价 80 万至 100 万日元的项目很多，与其他工程师职位相比也处于较高水平。

为什么会产生如此大的差距呢？原因之一是，自由职业者的技能和经验会直接反映在单价上。企业希望以项目为单位确保即战力，因此倾向于提供高额报酬作为对价。

另一个原因是，正式员工薪资中不包含企业看不到的成本（公司负担的社会保险费、福利待遇、培训成本等）。自由职业者自行承担这些成本，相应地，这部分会加算到报酬中。

自由职业全栈工程师要获得月单价 80 万至 100 万日元的高单价项目，需要满足以下几个条件。

实务经验的年限

许多高单价项目要求“3 年以上实务经验”。前提是在前端和后端方面都具备一定的实务经验。

设计与技术选型的经验

如前述技能掌握程度表所示，要求达到的不仅是“能够实现”，而是“能够做出设计判断”的水平。如果具备架构选型、API 设计、基础设施架构设计等经验，评价会更高。

复合型技能组合

如果能够全面应对从前端到后端乃至云基础设施，项目的选择范围就会更广。尤其是能够覆盖基础设施领域的工程师稀缺价值高，在单价谈判中也更有利。

沟通能力

不仅是技术能力，与客户和团队成员的顺畅沟通也很重要。要求能够顺利完成需求访谈、进度汇报、问题共享等工作。

作为自由职业者获得高收入时，容易被忽视的是“商流”问题。所谓商流，是指项目从终端客户传递到工程师手中的中介链条。商流越浅（中介商越少），工程师的到手收入就越多。

下表展示了相同技能水平的工程师因商流不同，到手收入会有多大变化。

商流终端企业支付金额中间抽成工程师到手收入

“做全栈却工作繁重、月入 60 万”与“相同技能月入 100 万”。这一差距并非源于技能，而是由商流造成的。

终端直签、总包直签的项目中间抽成较少，返还给工程师的比例更高。与客户直接沟通的机会也更多，还有从需求阶段就能深入参与的优势。

DeFactory 主要承接终端直签、总包直签等商流较浅的项目。抽成比例也公开透明，实现了高透明度的交易。“为提升技能投入时间”固然正确，但仅通过改变商流，到手收入翻 1.5 倍的情况也时有发生。请先确认当前项目的商流，检查自己的技能是否得到了合理的定价。

📌Pro Tip 意识到商流是“应当坚持的条件”的工程师才能胜出 在寻找项目时，很多工程师会关注技术栈和工作方式，却不确认商流。然而，要最大化长期留存的收入，在选择代理机构时注重商流至关重要。
