SGLang (2023) 面向 FDE 的详解

原标题：SGLang (2023) Explained for FDEs

FDE Interviews · 2026-10-17 · 约 4 分钟读完

摘要

本文解读斯坦福与伯克利团队的 SGLang 论文。针对 Agent、少样本分类、JSON 抽取等反复发送重叠提示词的“语言模型程序”，SGLang 提出 RadixAttention：用基数树保留已完成请求的 KV 缓存并复用最长前缀，配合缓存感知调度；再用压缩有限状态机让受限解码中固定文本一次前向完成。对比 vLLM、Guidance、LMQL，吞吐最高提升 6.4 倍；在 Chatbot Arena 上线一个月，Vicuna-33B 有 74.1% 的提示词 token 命中缓存，首 token 延迟降低 1.7 倍。文章还给出 FDE 实践建议：稳定内容放提示词前部以提升缓存命中、Agent 获益最大、结构化输出可更快、应监控命中率，并提醒这些特性现已进入 vLLM 等引擎，选型应按客户实际负载实测。

要点

  • SGLang 用基数树复用 KV 缓存前缀，LRU 淘汰并按缓存感知调度请求
  • 压缩有限状态机让受限解码的固定片段一次前向完成
  • 吞吐最高达 vLLM 等基线的 6.4 倍，Arena 上 74.1% token 命中缓存
  • FDE 应把稳定内容放提示词前部，并监控生产缓存命中率
  • 前缀缓存现已普及，选型需按客户负载实测而非论文数字

一分钟读懂这篇论文

许多真实应用并非发送一个提示就得到一个答案。Agent 会循环进行推理和工具调用，每次都重新发送不断增长的历史记录。少样本分类器在每次提问时都发送相同的示例。自洽性针对同一个提示采样多个答案。思维树程序会进行分支。JSON 提取器强制模型生成固定结构，其中只有少数可变字段。作者将这些称为“语言模型程序”，它们具有两个共同特征：多次调用且提示相互重叠，以及结构化输出。

SGLang 由斯坦福和伯克利团队（Lianmin Zheng、Ying Sheng、Ion Stoica、Joseph Gonzalez 等）开发，是一个服务运行时，外加一个用于编写此类程序的嵌入式小型 Python 语言。其核心运行时思想是 RadixAttention。SGLang 不在请求结束时丢弃其 KV 缓存，而是将其保存在以 token 序列为键的基数树中。新请求会遍历这棵树，复用最长的已缓存前缀，只计算剩余部分。当内存填满时，最久未使用的叶子节点会被逐出。缓存感知调度器会对等待中的请求进行排序，以最大化前缀共享，从而避免缓存抖动。

第二个思想是用于受限解码的压缩有限状态机。当输出必须匹配正则表达式（例如 JSON schema）时，标准引擎会屏蔽不允许的 token，并逐个 token 解码，即使在只有一种可能续写的区段也是如此，比如

{"summary": "

。SGLang 将这些强制区段合并，使它们在单次前向传播中处理完成。对于仅通过 API 提供的模型，“API 投机执行”技巧让一次调用越过停止条件继续生成，从而同时满足后续调用，节省输入 token 成本。

在 Agent、思维树、少样本基准测试、JSON 解码、检索流水线和多轮对话等场景中，SGLang 的吞吐量最高达到 vLLM、Guidance 和 LMQL 的 6.4 倍。在 Chatbot Arena 上为开放模型服务一个月期间，Vicuna-33B 的提示 token 有 74.1% 来自缓存，首 token 延迟降低了 1.7 倍。

研究笔记：问题、方法与结果

在语言模型程序工作负载上，吞吐量高于现有系统

在 Chatbot Arena 上为 Vicuna-33B 服务一个月期间，提示 token 由缓存提供的比例

在完全没有复用的工作负载上，维护基数树的开销

Agent、少样本提示、多轮对话和 JSON 提取会以相互重叠的提示和固定的输出格式多次调用模型，但服务引擎在每次请求后都会丢弃 KV 缓存，即使对于固定文本也逐个 token 解码。

将已完成请求的 KV 缓存保存在基数树中，实现自动前缀复用，支持 LRU 淘汰和缓存感知调度；压缩受限解码状态机，使固定片段一步解码完成；并为这些程序添加一门小型 Python 语言。

在 agent、推理、few-shot、JSON、RAG 和聊天等负载上，吞吐量最高达到 vLLM、Guidance 和 LMQL 的 6.4 倍；在 Chatbot Arena 上，Vicuna-33B 有 74.1% 的提示词 token 从缓存中提供服务，首 token 延迟降低 1.7 倍。

为什么这对 FDE 很重要

企业部署大多是语言模型程序：agent、带有固定指令的检索流水线、按 schema 提取、few-shot 分类器。这篇论文展示了在重复计算相同前缀上隐藏了多少成本，以及如何避免为此买单。

提示词顺序决定缓存复用。 复用只在完全相同的前缀上有效。把稳定的内容放在前面，例如系统指令、工具定义和 few-shot 示例，把可变内容（用户的问题、检索到的文档）放在后面。提示词开头的一个时间戳或用户名可能会悄悄破坏其下方所有内容的缓存。

Agent 获益最大。 每个 agent 步骤都会重发完整历史；有了前缀缓存，每一步只需为新 token 付费。这同时改变了 agent 负载的延迟和所需 GPU 数量。

结构化输出可以更快，而不仅仅是更安全。受限解码常被视为一种成本；有了压缩状态机，schema 的固定部分几乎免费。如果客户需要 JSON，应使用引擎的结构化输出支持，而不是解析自由文本再重试。

命中率是需要跟踪的指标。 在生产环境中，缓存命中率直接影响吞吐量和首 token 延迟。要监控它，并在提示词变更后排查命中率下降的原因。

这些想法如今已无处不在。 自动前缀缓存和快速受限解码也存在于 vLLM 和其他引擎中；论文的基线是一个没有这些功能的旧版 vLLM。应根据客户负载上的实测结果来选择引擎，而不是仅凭这篇论文的数字。
