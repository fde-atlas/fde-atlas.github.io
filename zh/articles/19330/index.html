AI 驱动开发是什么？编码 Agent 的企业导入与运营设计

原标题：AI駆動開発とは？コーディングエージェントの企業導入と運用設計

FDX株式会社 · 2026-11-13 · 约 20 分钟读完

摘要

这篇来自FDX株式会社的长文系统介绍了日本所称的“AI驱动开发”：让Claude Code、Codex、GitHub Copilot等编码Agent承担调查、编辑、执行命令与测试，人负责规格、评审与合并。文章指出该词尚无官方定义，并区分了规格驱动开发与vibe coding；整理了各工具的沙箱、审批、管理员设置等管控功能；引用METR、DORA、Stack Overflow等研究说明生产性证据存在分歧，体感与实测可能相反；最后提出企业导入需先决定授权范围、权限与执行环境、仓库指示书、验证关卡、度量与培养五项设计，并给出分阶段推进方案。

要点

  • AI驱动开发指Agent负责实现与测试，人掌握规格、评审与合并，尚无官方定义。
  • METR 2025年实验显示AI使资深开发者耗时增加19%，但本人自认快了20%。
  • 主要工具具备沙箱、审批层级与用户无法覆盖的管理员设置等管控功能。
  • 风险包括提示注入、幻觉包名、密钥泄露与评审积压，OWASP已列出Agent十大风险。
  • 企业导入应先定五项设计：授权范围、权限环境、指示书、验证关卡、度量培养。

让 AI 协助开发的方式，正在从建议代码后续内容的“补全”，扩展到整体承接任务的“Agent”。编码 Agent 接到指示后会阅读代码、编辑文件、执行命令和测试，并汇总返回变更。这种将实现和测试交给 Agent、由人掌握规格与判断的开发方式，在日本被称为“AI 驱动开发”。

不过，使用 AI 并不一定能加快开发。2025 年一项针对有经验开发者的对比实验显示，使用 AI 的作业反而多花了 19% 的时间。而参与者却感觉自己快了 20%。导入的成败，与其说取决于工具性能，不如说取决于“委托什么、如何验证”的设计。

  • AI 驱动开发是一种开发方式：将实现、测试、修正交给编码 Agent，由人掌握规格、审查与合并的判断。目前尚无官方定义
  • 与之相似的术语有规格驱动开发和氛围编程（vibe coding）。前者是先写好规格书再让 AI 实现的方法；后者是不阅读生成代码就直接接受的游戏式开发，不适合业务场景
  • 主要工具都具备沙箱、审批分级、用户无法覆盖的管理员设置等管控功能。是否使用由导入的企业决定
  • 在企业导入时，先确定委托范围、权限与执行环境、仓库指示书、验证关卡、度量与培养这 5 点，推进起来会更顺利

本文内容基于 2026 年 11 月 5 日确认的各公司官方文档和研究机构的一手资料撰写。

本文的目标读者

主要读者是希望判断是否在开发团队中引入 Claude Code、Codex、GitHub Copilot 等编码 Agent 的 CTO 和开发部门负责人。本文也面向一线工程师开始个人使用 Agent 后，需要制定公司内部规则的信息系统部门和安全负责人。希望将 AI 驱动开发纳入工程师培养计划的人事与培训负责人，建议从 5 个设计要点中的“度量并培养”开始阅读。

什么是 AI 驱动开发（3 行要点）

  • 一种开发方式：将代码的调查、编辑、命令执行、测试整体委托给编码 Agent
  • 人通过规格和验收条件传达“要做什么”，并审查产生的变更、决定是否合并
  • 正因为可以整体委托任务，如果不事先确定验证方式，质量与安全就会崩坏

AI 开发辅助的 3 个阶段

辅助开发的 AI，按委托单位的大小可分为 3 个阶段。

阶段委托给 AI 的单位人验证的单位典型用法
补全数行到函数每条建议让 AI 建议未写完代码的后续内容
对话回答提问、按文件修改每次回答询问错误原因、让 AI 重写函数
Agent任务（调查、编辑、命令执行、测试）拉取请求（变更的集合）委托修复缺陷，接收测试通过的变更

AWS 的规范指南将编码 Agent 描述为：能够针对编程课题进行推理、生成和修改代码、并与开发环境交互的工具。与补全类工具不同，其差异在于能解读目的、从环境中收集上下文、提出行动建议并执行。

Agent 有两种形态：在开发者 PC 上运行的类型，以及在云端运行并返回拉取请求的类型。前者如 Claude Code 和 Codex CLI，在终端或编辑器中运行，开发者可以边确认边推进。后者如 GitHub Copilot cloud agent，分配 Issue 后会在隔离环境中作业，并以拉取请求的形式返回结果。

与规格驱动开发、氛围编程的区别

AI 驱动开发周边有几个相似的术语。“AI 驱动开发”没有标准化团体或政府的官方定义，范围因使用者而异。为统一比较基准，本文按如下方式区分。

术语内容出处在业务中的定位
AI 驱动开发将实现委托给 Agent、由人掌握规格与判断的开发方式的总称在日本广泛使用的称呼。定义并不统一本文的对象
规格驱动开发（SDD）将“做什么、为什么做”写入规格书，再由此落到计划、任务、代码的方法GitHub 的 Spec Kit、AWS 的 Kiro 等采用AI 驱动开发中的一种推进方式。因保留规格，适合业务场景
AI-DLC由 AI 承担计划与执行、重要判断由人做出的开发生命周期AWS 于 2025 年 7 月公开的方法论可作为厂商方法论参考
氛围编程（vibe coding）不阅读生成的代码直接接受、出错就直接贴给 AI 的开发方式Andrej Karpathy 于 2025 年 2 月的帖子本人限定用于周末的一次性项目。不适合业务开发

GitHub 的 Spec Kit 将规格驱动开发描述为：确定“做什么、为什么做”，并将规格转化为计划、任务和可运行代码的方法。AWS 的 Kiro 则是先创建需求（requirements.md）、设计（design.md）、任务（tasks.md）三个文件，再进入实现。

“氛围编程”一词有时也被用来泛指用 AI 进行开发这件事本身。其原始帖子写的是不阅读差异就直接接受的游戏式做法，与业务的质量标准是两回事。

主要编码 Agent 与管控功能

企业使用时需要关注的，不是生成性能，而是管理员能限制什么。本文整理主要工具的管控功能。由于产品名称和功能变化频繁，建议在引入时通过官方文档确认。

工具运行位置主要管控功能
Claude Code（Anthropic）终端、编辑器，也有云端运行权限模式、拒绝・确认・允许规则、管理员设置（managed settings）、可在操作前后插入处理的 hooks、沙箱
Codex（OpenAI）终端、编辑器、云端沙箱三档（仅读取・写入工作文件夹・无限制）、审批策略、默认不联网、管理员设置
GitHub Copilot cloud agentGitHub 上的隔离环境只有拥有写入权限的用户才能启动、只能写入单个分支、不能自行审批和合并、默认工作流运行需要人工审批、防火墙
Kiro（AWS）编辑器、终端规格驱动开发功能、组织级 MCP 允许列表（面向通过 IAM Identity Center 或 API 密钥认证的用户）

在 Claude Code 中，规则按拒绝、确认、允许的顺序评估，由最先匹配的规则决定结果。无需确认即运行的模式和自动模式可通过管理员设置禁止，且用户设置无法覆盖。官方文档明确指出，写在 CLAUDE.md 等文件中的指令只能引导 Claude 的行为，不会改变允许范围。

Codex 建议在 Git 管理的文件夹中采用写入工作文件夹与按需审批相结合的设置，且默认不连接网络。GitHub Copilot cloud agent 无法自行审批或合并其创建的拉取请求，委托任务的本人也无法审批该拉取请求。

产品重组也在持续。GitHub 将 agent 的名称从 coding agent 改为 cloud agent。AWS 于 2026 年 4 月 30 日宣布，将于 2027 年 4 月 30 日终止 Amazon Q Developer 的 IDE 插件及付费计划的支持，并引导用户迁移至 Kiro。

此外，各工具使用的指令文件写法正趋向于 AGENTS.md 这一通用格式。AGENTS.md 由 OpenAI 创建，并于 2025 年 12 月捐赠给 Linux Foundation 旗下的 Agentic AI Foundation。据官方网站介绍，已有超过 6 万个开源项目使用，Codex、GitHub Copilot、Gemini CLI、Cursor 等均已支持。

关于生产力的研究结果存在分歧

AI 驱动开发的效果因测量方法不同而结果各异。在引入决策时，需要区分体感数字与实测数字来解读。

调查对象主要结果
METR（2025 年 7 月）16 名有经验的开源开发者、246 个课题使用 AI 使工作时间延长了 19%。事前预期为缩短 24%，结束后的体感也是缩短 20%
METR（2026 年 2 月的重复实验）57 人、800 个以上任务得出了缩短工作时间的估计（原参与者 18%，新参与者 4%）。但由于放弃参与的开发者大幅增加，METR 自身表示这不是能反映当前效果的可信结果
DORA（Google，2025 年 9 月）约 5,000 名技术人员90% 在工作中使用 AI，超过 80% 认为生产力有所提升。30% 对 AI 生成的代码几乎或完全不信任
Stack Overflow 开发者调查（2025 年）开发者84% 正在使用或计划使用 AI。46% 的人不信任其准确性，超过信任者的 33%。66% 对“大致正确但不完全正确”的输出感到不满

METR 2025 年的实验所使用的工具是当时的版本，METR 自身也在页面上注明结果已过时。尽管如此，本人体感与实测结果方向相反这一点，在思考引入评估方法时至今仍有参考价值。

DORA 的 2025 年报告得出结论：AI 不是修复团队，而是放大团队已有的长处与短处。同时，报告列出了发挥 AI 效果的 7 项能力：明确传达的 AI 方针、健全的数据基础、AI 可使用的内部数据、强大的版本管理、小单位作业、以用户为中心的态度、高质量的内部平台。向测试和评审机制薄弱的团队引入 agent，弱点也会被放大。

企业使用时容易出现的问题

编码 agent 可以读取文件、执行命令、与外部通信。正因为省去了人工逐项确认，问题发生时的影响更容易扩大。

问题会发生什么一手资料中的报告
指令劫持（提示注入）agent 会遵循写在 Issue、README、依赖包中的指令Invariant Labs 于 2025 年 5 月报告，通过让 agent 读取公开仓库中的恶意 Issue，可诱导 agent 将非公开仓库的信息写入公开的拉取请求
幻觉包名AI 写出实际不存在的包名，攻击者以相同名称发布恶意包2025 年 USENIX Security 的论文让 16 个模型生成了 57.6 万条代码，报告称代码所引用的包中不存在的比例平均为：商用模型 5.2% 以上，开源模型 21.7% 以上
秘密信息泄露Agent 读取 .env 或密钥文件，并输出到日志或对外通信中Claude Code 官方文档给出了拒绝读取 .env 等文件的规则示例

OWASP 于 2025 年 12 月发布了将 Agent 型 AI 特有风险归纳为 10 项的「Top 10 for Agentic Applications」。其中列举了目标劫持、工具误用、权限滥用、意外代码执行等，同样直接适用于编码 Agent。在日本国内，AI 安全研究所（AISI）在 2026 年 7 月的《AI 安全评估要点指南》第 1.20 版中，结合 AI Agent 的普及更新了评估要点。

企业导入时需确定的 5 项设计

下面以编辑部的示例设计的形式，介绍在企业中使用编码 Agent 时需要事先确定的 5 项设计。

1. 确定委托范围

首先要确定将哪个仓库的哪些工作委托给 Agent。如果一次性向全公司开放，一旦出现问题就难以锁定原因。

分类工作示例处理方式
易于委托添加测试、修复小缺陷、更新文档、解决类型和 lint 错误作为试点对象
有条件委托添加功能、重构、更新库写明规格和验收条件后再委托
暂不委托认证、支付、处理个人信息的功能、生产环境配置由人编写，Agent 仅用于调查和说明

2. 确定权限和执行环境

其次，要确定 Agent 运行的环境，以及无需确认即可执行的操作范围。对于在开发者 PC 上运行的类型，要使用沙箱和网络限制，

.env

拒绝读取 .env 和密钥文件。Claude Code 和 Codex 都有由管理员分发、用户无法覆盖的设置，禁止无需确认即执行的模式也在此处进行。

对于在云端运行的类型，要确认 Agent 可使用的凭证和通信目标。GitHub Copilot cloud agent 通过防火墙限制对互联网的连接，并将可写入的分支限定为 1 个。如果要在公司内部环境中实现同样的效果，只需给 Agent 专用账号授予最小权限。

3. 在仓库中放置指令文件

Agent 会读取仓库中放置的指令文件进行工作。在 AGENTS.md 或 CLAUDE.md 中写明构建和测试命令、代码规范、不可触碰的目录，产出的变更就会保持一致。Codex 会按顺序读取从仓库根目录到工作文件夹的 AGENTS.md，并优先采用较深层级的文件。

但指令文件不具备强制力。Claude Code 官方文档要求，必须确保阻止的操作应通过权限规则或在操作前插入处理的 hooks 来阻止。「不连接生产数据库」不仅要写在指令文件中，还要通过设置使其无法连接。

4. 设置验证关卡

对 Agent 的变更，要以与人工变更相同或更严格的标准进行验证。测试、类型检查、lint、安全检查必须在 CI 中全部通过；对于添加依赖包的变更，要确认该包确实存在且可信。

评审和合并由人来把关。GitHub Copilot cloud agent 的机制是 Agent 无法自行合并，委托人本人也无法批准。在公司内部规则中，如果采用由委托人以外的人评审并合并的方式，可以减少未经阅读就通过的变更。

5. 度量并持续改进

效果不能靠体感，而要用开发指标来衡量。正如 METR 的实验所示，本人的感觉有时会与实测结果相反。要在导入前后对比变更的交付周期、评审所需时间、合并后的返工和故障数量。

使用方法的差异也很大。如果规格的写法、委托单位的划分、评审的关注点不统一，即使是相同的工具，不同人的成果也会大不相同。要通过培训统一基本用法，并在团队内共享效果好的指令文件和设置。

导入的推进方式

下面给出基于这 5 项设计的推进方式示例。期间以拥有数个开发团队的企业为假设，仅供参考。

阶段期间参考工作内容

常见问题（FAQ）

Q1. 什么是 AI 驱动开发？

A. 一种开发方式：将代码的调查、编辑、命令执行、测试整体交给编码 Agent，而人掌握规格、审查和合并的判断。目前没有标准化组织或政府的官方定义，这是在日本广泛使用的叫法。AWS 以 AI-DLC、GitHub 和 AWS 以规格驱动开发（Spec-Driven Development）的名称提出了相近的做法。

Q2. 与规格驱动开发的区别是什么？

A. 规格驱动开发是 AI 驱动开发中的一种做法。先在规格说明书中写明做什么、为什么做，再由此落到计划、任务和代码。由于规格会以文件形式留存，便于审查和交接，适合业务开发。

Q3. Vibe Coding 能用于业务吗？

A. 不适合业务开发。Vibe Coding 是 Andrej Karpathy 于 2025 年 2 月提出的说法，指不阅读生成的代码就直接接受的做法。他本人也将其限定为周末的一次性项目。在业务中，应先写规格，审查变更后再合并。

Q4. AI 驱动开发能让开发变快吗？

A. 取决于条件。METR 在 2025 年的实验中，有经验的开发者在使用 AI 后实际工作时长增加了 19%，但本人却感觉快了 20%。DORA 的 2025 年报告结论是：AI 会同时放大团队的长处和短处。应完善测试和审查机制，用交付周期和返工率等指标而非体感来衡量效果。

Q5. 编码 Agent 在安全方面有哪些注意事项？

A. Agent 可以读取文件、执行命令、与外部通信，因此要注意指令劫持、机密信息读取、引入不存在的包等风险。使用沙箱和网络限制，

.env

拒绝读取等敏感内容，依赖包的添加由人工确认。使用公司的商业套餐签约，不要让个人账号处理公司内部代码。

Q6. 什么是 AGENTS.md？

A. 一种用于向编码 Agent 告知构建和测试命令、代码规范的通用指令书格式。由 OpenAI 创建，并于 2025 年 12 月捐赠给 Linux Foundation 旗下的 Agentic AI Foundation。Codex、GitHub Copilot、Gemini CLI、Cursor 等均已支持。由于指令书不具有强制力，需要确保禁止的操作应通过各工具的权限设置来阻止。

总结

  • AI 驱动开发是一种开发方式：将实现、测试、修正交给编码 Agent，而人掌握规格、审查和合并的判断
  • 规格驱动开发是其中的一种做法，由于规格会留存，适合业务开发。Vibe Coding 不适合业务开发
  • 主要工具都具备沙箱、审批分级、使用者无法覆盖的管理员设置。是否使用由导入的企业决定
  • 生产力的研究结果存在分歧。由于体感与实测存在偏差，应以交付周期和返工率来衡量效果
  • 在企业中，应先确定 5 点：委派范围、权限与执行环境、仓库指令书、验证关卡、度量与培养
  • 指令书不具有强制力。要禁止的操作通过设置来阻止，审查和合并应由与请求者不同的人负责
