摘要

OpenAI 未公布 FDE（前沿部署工程师）take-home 的固定格式，官方指南只说明考核形式因团队而异，且 2026 年 8 月起新增了 AI 工具使用规则。文章梳理了四份候选报告：一份为期一周的语义搜索构建（进入 onsite）、一份约五小时加视频讲解的报告（属姊妹岗位）、一份设计文档类报告（公司不明）及一份可信度最低的博客。作者据此提出通用四步法：界定范围、搭建最小可用版本、建立评测、答辩。文中给出五小时与一周两种时间分配方案，并强调评测集、失败分析和主动披露 AI 使用的重要性。

要点

  • OpenAI 官方未公布 FDE take-home 格式，仅称因团队而异。
  • 候选报告显示格式多样：一周构建、五小时加视频、设计文档。

你能安全得出的结论很少：少数几个人在不同时间描述了不同形态的流程，而且这些岗位并不总是相同的。这些都不能告诉你招聘人员会给你发什么，也没有说明每种形式的使用频率。证据图谱一课展示了如何这样梳理任何公司的事实：雇主发布了什么、候选人报告了什么（谁、何时、哪个岗位），以及没人知道什么。

这些报告的共同点比它们的差异更有用。每种形式都要求你面对一个宽泛的问题，决定构建或提出什么，证明它可行，然后向会追问细节的人解释你的选择。这就是套路。

适用于任何形式的套路：界定范围、构建、评测、答辩

这是我们的方法，不是 OpenAI 公布的评分标准。它基于指南中的原话（解决方案、质量、性能、测试、沟通）以及招聘启事对评测的强调。

步骤代码设计文档
界定范围README 中的简报问题 + 非目标
构建精简的端到端构建最简架构
评测带标注的数据集 + 打分评测方案 + 上线标准
答辩视频，然后现场问答权衡取舍，然后现场问答

在每种形式中，这些步骤的顺序保持不变；变化的只是每一步所占的时间。如果有一周时间，构建步骤会扩大，但一周也足以让你过度构建，所以界定范围更重要，而不是更不重要。

如何分配时间

这是我们建议的分配方式，不是 OpenAI 公布的任何内容。

五个小时：

  • 三十分钟：界定范围，并提交你的问题
  • 两小时：精简的端到端骨架
  • 一小时：构建评测集并打分
  • 四十五分钟：修复最严重的失误
  • 四十五分钟：README 和视频

一周：

  • 第一天：界定范围、提问和搭建骨架
  • 第二至四天：根据评测结果改进
  • 第五天：阅读失误之处并撰写总结
  • 第六天：README 和视频
  • 第七天：缓冲时间，以及一次干净克隆测试

界定范围：在构建之前先把简报写回去

在写任何代码之前，用自己的话把问题复述一遍。把它放在 README 或文档的顶部。

以一位候选人描述的 2026 年 5 月某次面试的题目为例：为聊天助手构建产品目录上的语义搜索。来源 5OpenAI 前沿部署工程师面试经历发布者Aced（前身为 Exponent）来源类型候选人的个人记述 以下是为它填写好的简报：

  • 目标：购物者输入一句自然语言请求，即可获得最多五个真实商品，包含标题、价格和链接。
  • 用户：使用聊天助手的购物者，通常带有约束条件（价格、尺寸）。
  • 范围内：目录的一个样本、一个模型、前五名检索、一个包含二十条查询的标注集。
  • 范围外：个性化、按毛利率重排序、网页 UI（用 CLI 展示同样的内容）。
  • 假设：目录是静态的；如果需要每日更新，我只会对变更的商品重新生成嵌入。
  • 成功标准：标注集上的 top-5 命中率和 MRR，外加每个未命中案例的一行说明。

一份糟糕的任务说明只会写“构建语义搜索”。而这份说明能让评审者知道你构建了什么、跳过了什么，以及该如何评判。

假设部分最能体现你的判断力。评审者可以不同意某个假设，但仍然会因为你在明面上写出了它而认可你。

尽早提出你的问题。如果准备材料中有未明确之处，请在收到题目当天就写信给你的招聘人员：

“感谢这份带回家的测试题。为了正确界定范围，我有两个简短的问题：本次评估是否允许使用 AI 编程助手？提交时是否需要附带视频演示？如果没有特别要求，我会在 README 中披露任何 AI 的使用情况。”

这条消息遵循了 OpenAI 自己的建议——不确定时就要问。来源 1Interview Guide | OpenAI发布方OpenAISource typecompany hiring pageSource 2OpenAI interview guide (Wayback Machine capture)发布方OpenAI (archived by Internet Archive)Source typearchived company page 关于其他雇主如何表述 AI 规则，以及如何披露你的使用情况，请参阅关于在带回家测试中使用 AI 的文章。

构建：先做一个精简可用的版本

在把任何部分做精之前，先端到端地跑通整条路径。对于搜索示例，这意味着：加载目录的一个切片、生成嵌入、回答一条查询，并通过题目要求的任何接口返回结果。丑没关系，能跑才是关键。

行走骨架一课深入讲解了这种模式。在带回家测试中，它能保护你避免一个常见的失败：做出了一条漂亮的数据摄取流水线，却在时间耗尽时无法运行任何查询。

骨架跑通之后，把剩余的构建时间花在评测显示最薄弱的环节上。如果你想在做正式题目之前热身，可以不借助任何库构建 TF-IDF 检索：这是同样的“检索加排序”循环，只是规模小到可以一次坐下来完成。

需要避免的错误：

  • 在第二小时更换向量存储。使用内存中的嵌入数组即可；几千个商品完全可以放进内存。
  • 一开始就嵌入整个目录。先从样本开始，让一条查询端到端跑通，然后再扩展规模。
  • 做一个 React 前端。一个打印前五名结果及分数的 CLI 就能展示评审者需要的一切。
  • 掩盖粗糙之处。在 README 中列出已知的缺陷。自己发现它们体现的是判断力；被评审者发现则显得是失误。

对于设计文档类题目，构建步骤就是架构：一张图、从输入到答案的数据流，以及你会最先构建的少数几个组件。不要把你所知道的每个服务都列出来。

评测：展示你如何知道它有效

这是时间紧张时最容易省略的一步，也是职位描述的语言所指向的一步。来源 4Forward Deployed Engineer (FDE) - SF | OpenAI发布方OpenAI来源类型公司招聘启事 一个可运行的演示说明它在所选查询上能跑通。而评测则说明它在未经调优的查询上的表现。

形式上保持小而真实：一个简短的现实查询列表、每个查询对应哪些人工会判定为正确的产品，以及一个分数。以下是搜索示例的完整评测框架：

def hit_rate(runs, gold, k):
    pairs = zip(runs, gold)
    s = [bool(set(r[:k]) & g)
         for r, g in pairs]
    return sum(s) / len(s)

def rr(r, g):
    for n, doc in enumerate(r):
        if doc in g:
            return 1 / (n + 1)
    return 0.0

def mrr(runs, gold):
    pairs = zip(runs, gold)
    s = [rr(r, g)
         for r, g in pairs]
    return sum(s) / len(s)

# Top 3 for three queries, and
# the products marked relevant.
runs = [["p7", "p2", "p9"],
        ["p4", "p1", "p3"],
        ["p8", "p6", "p5"]]
gold = [{"p2"}, {"p4"}, {"p0"}]
hr = hit_rate(runs, gold, 3)
print(round(hr, 2))
print(round(mrr(runs, gold), 2))
# 0.67, then 0.5

命中率衡量正确产品出现在靠前位置的频率。平均倒数排名（MRR）则奖励把正确产品排在第一位。两者都要报告，然后做比任何数字都更重要的事：阅读失败案例。上面的第三个查询没有找到任何相关结果。为什么？是拼写错误、相似度搜索无法执行的价格上限，还是索引中缺失的产品？每个失败案例写一行说明。

这张简短的失败表正是把演示变成工程提交物的关键：

查询类型出了什么问题下一步修复
价格限制（“在某预算以内”）相似度无法执行价格上限解析限制条件，先做过滤
品牌拼写错误没有接近的匹配为品牌添加模糊匹配

对于设计文档类题目，改为撰写评测计划：你会构建的测试集、指标、达到什么阈值才上线，以及上线后要监控什么。How do you know your AI system works? 就是同一个问题被明确提出来，并附带了回答框架。

答辩：提交物的现场讨论

一位候选人报告称，2026 年 5 月有一次关于提交物的现场团队讨论；一位 Blind 评论者在 2026 年 3 月提到过视频演示，所以两种情况都要准备。来源 5OpenAI Forward Deployed Engineer Interview Experience发布方Aced（前身为 Exponent）来源类型候选人的个人记录来源 6Anthropic/OpenAI FDE Interview loop -- same as SWE?发布方Blind（teamblind.com）来源类型候选人在 Blind 上的报告

对于视频，先讲结果，而不是代码：它做什么、一次现场查询、评测分数、最大的差距所在。The take-home walkthrough video 帖子里有一份脚本。

对于现场讨论，预计会遇到类似下面的问题，并为每个问题准备好一句话回答：

  • “为什么选这个方案而不是显而易见的替代方案？” 说明你选择了什么、付出了什么代价，以及何时会切换方案：“我只用了 embeddings，因为商品目录小且静态。代价是价格约束会失效，评测结果也显示了这一点。如果有更多时间，我会在排序前加一个结构化过滤器。” 可以通过 defend your take-home design 来练习。
  • “如果再多一天，你会改什么？” 说出一个改进点，并与你测量到的某个失败相关联；再说出一个你有意省略的内容。在 take-home 中你会改什么？ 有参考答案。
  • “这在真实客户面前能撑得住吗？” 谈谈最先出问题的地方：更大目录下的延迟、数据过期、其他语言的查询，以及你会如何发现这些问题。
  • “你是如何使用 AI 工具的？” 如果允许使用，请明确说明用在哪里：“我用助手生成了样板代码和测试脚手架。检索设计、评测集和失败分析都是我自己做的。”

提交清单

无论采用哪种形式，请在提交前一晚执行以下检查。

提交前

  • 简要回顾放在最前面：目标、用户、范围、范围外内容、假设、成功标准
  • 项目能在干净的克隆环境中用 README 中的命令运行，而且你已经试过这些命令
  • 密钥和 API key 已移出仓库，README 说明了需要设置哪些变量
  • 有测试集、评分，以及一份简短的失误清单，每条失误都附有原因
  • 测试覆盖了核心路径（指南明确提到了工程面试的测试覆盖率）
  • 已知缺口和下一步修复方案在评审者发现之前就已写下来
  • AI 的使用已按你的准备材料或招聘人员要求的方式进行了披露
  • 如果要求提供视频，视频应以结果开头，并符合给你的时长限制
  • 你能解释每一个文件，包括助手写的任何代码
  • 你能说出为什么选择你的方案而不是显而易见的替代方案

对于设计文档，把前四项换成：问题和非目标放在最前面、一张架构图、包含上线阈值的评估计划，以及一个说明你拒绝了哪些方案的权衡章节。关于 FDE take-home 的更全面文章介绍了其他公司的题目要求，如果你的流程涉及不止一家公司的话。

在真正考核之前练习答辩环节

构建是你能独自完成的部分。答辩环节则是压力下容易出错的部分，因为有人会提出你没有预料到的追问。免费练习案例让你面对一个带着模糊问题的 AI 客户，限时 10 分钟：你需要界定范围、提出第一版方案并说明如何验证它有效，然后一张评分卡会显示你问了什么、漏了什么。注册登录后即可免费使用。在题目到来之前先做一次练习，这样你写的第一份简要回顾就不会是真正考核的那份。
