FDE 每周到底在做什么

原标题：What FDEs Actually Do All Week

Big Tech Careers · 2026-04-16 · 约 10 分钟读完

摘要

Lleverage 的 FDE Milos Mandic 以一周工作日志的形式，描述初创公司前沿部署工程师的真实日常：同时服务约十个客户、每周约五十小时，时间大致一半开会、一半构建。文章指出工作重心并非写代码，而是理解客户业务、管理期望与跨工具沟通，并强调编码 Agent 压缩了打字时间，使瓶颈转向从客户提取业务上下文。

要点

  • 作者同时并行服务约十个客户，与 Palantir 式深度驻场模式不同。
  • 时间分配约一半会议、一半构建，深度工作常被打断。
  • 构建难点在 80% 之后：脏数据、无标准答案、下游系统约束。
  • 主要沟通对象是业务方而非工程师，核心工作是翻译与期望管理。
  • 编码 Agent 压缩编码时间，瓶颈变为提取客户业务上下文。

Ashish Prajapati 将于 5 月 16 日举办为期一天的 NVIDIA Associate — AI Infrastructure and Operations（NCA-AIIO）认证直播训练营。Ashish 拥有 5 项 NVIDIA 认证，他在 Udemy 上的自学 NVIDIA 课程评分极高。本周他为 Big Tech Careers 的读者提供 5 折优惠。

自从我开始撰写 FDE Hub 通讯以来，已有数十人联系我，说他们喜欢我分享的关于 FDE 角色的内容。最常见的请求是什么？多讲讲日常工作。真实的体验。一周到底是什么样的？

合理的要求。这是一周最近的记录。十个客户，五十个小时，还有多到让人头晕的上下文切换。

先简单说明一下：在 Palantir 或 OpenAI 这样的大公司，FDE 通常会同时深入服务一两个客户。而在 Lleverage 这样的初创公司，我要同时为许多客户并行推进部署。这是这个角色的另一种形态——深度较浅，但更注重跨场景的模式识别。两者都是合理的。这就是初创公司 FDE 的体验。

周一：为混乱做规划

一周从规划会议开始。我、其他 FDE 以及我们的客户交付负责人会坐下来花一个小时，逐一审查每个活跃客户，并确定本周的优先事项。

这听起来很公司化。其实不然。这是生存之道。

当你同时服务十个客户时，你需要知道哪些火苗正在闷烧，以免它们变成大火。哪个 PoC 即将到期。哪个客户已经沉默太久——这通常意味着他们卡住了，只是还没告诉我们。哪个潜在客户需要在失去动力之前进行一次需求界定电话会议。

我们用 Linear 来跟踪一切。每个客户都有自己的项目、自己的任务集、自己的状态。没有这些，我一天之内就会迷失方向。

规划之后，周一剩下的时间就是一连串的电话。与现有客户的状态更新。与一个潜在客户的售前电话，试图弄清楚他们想要的东西到底是否可行。等我抬起头来，已经是下午 6 点，而我一行代码都没写。

这种情况比我希望的更常见。

两个进行中的构建项目

我通常在任何时候都有两个客户处于活跃构建阶段，其余客户则处于更早或更晚的阶段。

第一个例子可能是文档处理流水线。纸面上听起来很简单：文档进来，结构化数据出去。实际上，单个客户会有六种文档类型从十几个不同来源涌入，每一种都需要分类、路由、根据业务规则校验，然后推入一个对“什么才算有效数据”有着自己想法的下游系统。

你很快就能做到 80%，感觉终点近在眼前。其实不然。核心流程能跑通了。我可以拿一个干净的示例，提取所需内容，按要求的格式交付，演示效果也不错。但之后的一切，才是没人看见的部分。

文档到达时的格式与规范不完全一致。理论上必填的字段在实践中其实是可选的，而 AI Agent 必须知道两者的区别。同一个客户的两位操作员对同一份文档的正确答案意见不一，这意味着根本不存在所谓的标准答案，只有一场协商。手写批注会干扰 OCR。客户发来的扫描 PDF 分辨率低到让整个流程都不可靠。下游系统因为一个在需求沟通会上没人提过的字段约束而拒绝上传。

我大量的构建时间都花在追查这些问题上。收紧提示词，补充模型区分不同文档类型所需的上下文，扩充测试集以捕捉尚未见过的失败情况，为那些 AI Agent 应该上报人工而不是瞎猜的场景添加兜底逻辑。这些都不光鲜，但正是“让人眼前一亮的演示”与“无需专人看管就能在生产环境运行的系统”之间的差别。

第二个构建通常处于更早期阶段。我们已经在少量输入输出对上验证了概念，现在需要扩展到一百个甚至更多，而这正是为原型设计的架构开始不堪重负的地方。PoC 是魔术，生产是管道工程。在两者之间迁移，往往意味着要重新审视那些当初只是为了证明“这事可行”而做出的决定。

这也是编码 Agent 改变了我每周工作形态的地方。我在后台用 Claude Code 处理大量繁琐工作：搭建测试用例脚手架、重构凌乱的原型代码、针对一个我还在摸索的 API 起草集成胶水代码。它并没有减少思考。如果说有什么变化，那就是它让我更清楚地意识到，这份工作本来就有多少是在思考。它真正压缩的是打字的时间，这意味着瓶颈进一步上移了。瓶颈不再是我构建的速度有多快，而是我能多快从客户那里提取出足够的运营上下文，以确定下一步该构建什么。

沟通的蔓延

我登录着几十个 Slack 工作区和 Microsoft Teams 实例。每个客户都使用自己的工具，而我们总是迁就他们，所以有些客户用 Slack，有些用 Teams，每个都有各自的频道、各自的通知提示音，以及各自对什么算紧急事项的约定。大多数客户还有我的手机号码，这意味着一次真正的紧急升级可能在周日晚上 9 点以 WhatsApp 消息的形式出现。这种情况不常发生，但发生得足够多，以至于我总是把手机放在触手可及的地方。

除此之外还有我们的内部工具。用 Linear 做项目跟踪，用 Notion 做文档，用 Google Docs 做共享规格说明和提案，用 Excel 做数据分析（而且它经常还是数据来源），用 Postman 调试 API，而 Claude 和 Claude Code 则贯穿其中大部分环节，用于写作、调试和边思考边出声。

上下文切换其实并不只是在不同项目之间移动。它是要记住哪个客户用哪个工具、哪个频道用于紧急问题而哪个用于一般更新，以及三天前我上次深入他们的世界时，某段对话进行到了哪里。

当系统出故障时

每隔几周，上游就会出问题。可能是模型提供商发生事故，某个云区域出现波动，或者某个认证服务出了故障。这种时候，我们的客户就会遇到问题，而客户一有问题，就会给我们发消息。

半天时间就这样消失在救火中。查看状态页面，给惊慌失措的客户发送更新，试图弄清楚我们是否能绕过这次故障。通常绕不过去，但你还是得查。你可能已经把完美的一周规划好了，然后一个上游提供商就直接把你拖入被动应对模式。你原本留出的深度工作只能再等一天。

我们有监控机制来尽早发现这些问题，这很有帮助，但并不能完全消除干扰。

五五开的时间分配

如果诚实地说说时间分配，大概是 50% 开会、50% 构建。会议包括客户例行沟通、内部规划、售前通话、需求界定会议、状态更新，以及偶尔的救火电话。构建则是真正的编码、提示词工程、测试、调试，以及把我们需要哪些基础能力的洞察反馈给产品团队。

我尽量把周二和周四保护起来用于深度工作——四个小时的整块时间，让我能真正在复杂问题上取得进展。但这并不总能守住。一次客户紧急升级或一个紧急的潜在客户电话可以毁掉任何一天。不过当我真的拿到那些整块时间时，那才是真正的工作发生的时候。

会议之间的短暂间隙，这里 30 分钟、那里 60 分钟，则用来做小修复和维护。你没法在 45 分钟内设计一个系统架构，但你可以微调一个提示词、启动一个 AI Agent 做小型重构、回复客户的问题，或者审查一次通宵运行的测试结果。

关于人的部分

我的大部分对话对象是业务利益相关者，而不是技术人员。这一点起初让我很意外。我原以为会花更多时间和工程师打交道，但实际上，我主要在需要系统访问权限或集成支持时才联系技术人员。日常工作面对的是运营经理、部门主管和高管们，他们正在试图弄清楚 AI 到底能为他们的业务做些什么。

这份工作中很大一部分是“翻译”。解释什么是可行的，管理对 AI Agent 能力边界的预期，把“我们想要一个能自动搞定一切的 AI”这类需求引导为“让我们先从这些具体的输入和输出开始”。我们发现同样的解释重复得太频繁，于是编写了一份操作手册。这是一份分享给每个客户的文档，涵盖我们需要客户提供哪些数据、我们如何沟通、他们应如何测试和反馈，以及如何记录 Agent 完成工作所需的 SOP 和业务规则。

最后一部分是最关键的。Agent 需要你把业务规则先写下来，才能围绕它们实现自动化，而大多数客户从未把这些规则写下来。操作手册在我们编写任何一行代码之前就设定了这一预期。

周五：内部聚焦

到了周五，客户电话逐渐减少，内部工作开始增多。这时我们会进行团队同步、复盘和产品反馈会议。这些事情对长期发展很重要，但在客户工作繁忙时往往被挤掉。

产品反馈循环是我认为这份工作中最有价值的部分之一。当你在多个客户之间实施相同的模式时，你会开始看清哪些内容应该被抽象到平台中。我会花时间和产品团队讨论哪些基础组件我们一直在从零构建，因为这通常意味着它们应该作为可配置的功能存在，而不是每次都要编写的代码。这场对话中有趣的另一半是反向思考：哪些模式看似可复用，但实际上不应该被产品化，因为客户之间的边缘情况比共享的核心部分更大。分辨这两者的能力，只有同时参与多个实施项目才能学到。

这个角色真正需要什么

回顾一个典型的工作周，有几点特别突出。

首先，你必须能适应混乱。十个客户、不同的工具、不同的阶段、不同的问题、不断的上下文切换。如果你需要长时间不受干扰的专注才能高效工作，这个角色会让你崩溃。

其次，技术工作是真实存在的，但很碎片化。你不会每天花八个小时写代码。你在这里花两个小时，在那里花四个小时，其余时间都在对话中，而这些对话决定了代码需要实现什么。编程 Agent 已经稍微改变了这个比例，但并没有从根本上改变它。

第三，业务侧是绕不开的。如果你只想埋头做东西、不想和人打交道，这个职位不适合你。我一周的大部分时间都在沟通：翻译需求、管理预期、协调各方利益相关者的关系。

第四，你掌握完整的上下文。每个客户对应一名 FDE，没有交接给交付团队的环节。你界定的范围就是你要构建的东西。这很累，但也让人清醒。你不能过度承诺，因为负责交付的人就是你自己。

坦诚的版本

如果非要说出定义这个职位的关键，那就是：这份工作与其说是构建 AI 系统，不如说是深入理解业务，从而知道该构建什么。

技术能力很重要。你需要会写代码，理解 LLM 的工作原理，能在压力下调试系统。但真正的差异化优势，是在混乱的人类组织中识别模式的能力：看清真正阻碍客户的问题是什么——而这往往不是他们口中所说的障碍；知道什么时候该反驳，什么时候该按他们的要求直接做。

每一周都不一样，每一个客户都不一样。唯一不变的是，我精心规划的周二深度工作时段，多半会被某件事打断。

这就是这份工作。
