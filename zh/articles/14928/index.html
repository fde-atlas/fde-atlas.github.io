逆向工作法与 Amazon PR/FAQ：FDE 指南

原标题：Working Backwards and Amazon PR/FAQ: a guide for FDEs

FDE Times · 2026-11-11 · 约 6 分钟读完

摘要

文章介绍 Amazon 的 PR/FAQ 方法如何帮助前沿部署工程师在写代码前与客户对齐问题。作者 Colin Bryar 与 Bill Carr 在《Working Backwards》中说明：先写一页新闻稿和 FAQ，再动手开发。新闻稿迫使你明确承诺并从具体用户视角描述收益；FAQ 分外部与内部两部分，回答不了的问题即风险。文章还指出三种常见错误，并建议先读免费的在线说明再读书。

要点

  • PR/FAQ 要求在写代码前先完成一页新闻稿与 FAQ。
  • 新闻稿须从具体用户视角描述收益，而非罗列功能。
  • FAQ 分外部与内部问题，答不出的问题应列入计划。
  • 常见错误：功能清单、问题堆砌、缺少客户方反馈。
  • 建议先读免费说明，再读书本，跳过重复轶事。

Amazon 的 PR/FAQ 方法由两位前高管在《Working Backwards》中提出，为 FDE 提供了一个一页纸的检验方法，判断客户的问题是否真正清晰。

Working Backwards: Insights, Stories, and Secrets from Inside Amazon· Colin Bryar ·

封面：Open Library

简要介绍

  • Colin Bryar 和 Bill Carr，两位前 Amazon 高管，描述了公司如何在构建产品之前先撰写新闻稿和 FAQ。
  • 对 FDE 而言，PR/FAQ 是一种在改动成本仍然很低时，与客户在纸面上就问题达成一致的方式。
  • 先阅读免费的 PR/FAQ 说明文章，再读这本书，并略读其中的轶事。

据 AWS Executive Insights 介绍，Amazon 在构建产品之前，会为它预期发布的产品撰写一篇新闻稿。换句话说，它在任何代码存在之前就写好了故事的结局。在《Working Backwards》中，Colin Bryar 和 Bill Carr 把这一习惯转化为 Amazon 以外的人也能学习和遵循的流程。

对前沿部署工程师来说，这不仅仅是企业文化。在客户现场，最昂贵的错误通常不是 bug，而是构建出技术上正确但客户并不需要的东西。问题模糊不清，双方各有各的理解，而差距往往几周后才显现出来。

PR/FAQ 让双方阅读并认可同一页内容，而此时修改问题的成本只需敲几下键盘。

《Working Backwards: Insights, Stories, and Secrets from Inside Amazon》（St. Martin’s 出版）是两位前 Amazon 高管撰写的内部视角记述，介绍了公司独特的原则和流程。Publishers Weekly 评价说，无论大小型组织都能从中获得借鉴，尽管个人轶事重复得相当频繁。

作者将 Working Backwards 定义为一种审查创意和创造新产品的系统化方法。对 FDE 而言，最有用的部分是 PR/FAQ 流程，其中包含三个可以在下一次项目中运用的理念。

第一个理念：新闻稿迫使你明确说出你承诺的是什么

作者将撰写新闻稿称为一种“强制机制”，一种让产品构建者始终关注客户的机制。关键在于顺序：新闻稿和 FAQ 在任何东西被构建之前就已完成。

AWS 表示，这一方法基于这样一种观点：客户的声音是开发任何产品时最重要的输入。

想象一下，你被派往一家保险公司，对方希望“使用 AI Agent 处理理赔”。这是一个愿望，还不是问题陈述。当你坐下来撰写新闻稿的开头一句时，那些棘手的问题就会浮现：谁在使用它？它为他们减轻了什么工作？成功是什么样子？

如果新闻稿需要一个数字，比如理赔处理速度提升了多少，而你和客户都不知道现在处理需要多长时间，那你就找到了第一个探索性问题。这就是在动手改提示词之前应该先测量的东西。

第二个要点：一页纸，从用户的角度来写

据 AWS 介绍，新闻稿必须恰好一页，这个限制迫使作者简化内容、聚焦核心想法。作者还要求对客户进行精确描述，并且收益段落要从客户的角度来写。

回到保险公司的例子。“保险公司”这个客户范围太宽泛了。改写成“车险理赔员”，你就必须问这个人的一天工作是什么样的、他们在哪里卡住。一页纸装不下三个用户群体和五个功能，所以你必须做出选择。

一个示例开头可以完整地这样写：“从今天起，每一份到达理赔员手中的新车险理赔案件，都会附带一份现成的损失摘要和一份缺失文件清单。

他们不再需要逐个打开附件来检查客户是否提交了所有材料。省下来的时间可以用于疑难案件，在这些案件上，他们的经验才真正决定结果。”

注意，这段话没有提到任何模型、向量数据库或流水线。它只说明了一个具体的人不再需要做哪些工作，以及他们把省下的时间用来做什么。你可以把这个模板复用到自己的项目中：谁、过去在哪里遇到困难、现在得到了什么。

尽早选择也对你有帮助：范围越窄，越快进入生产环境，结果也更容易衡量。

第三个要点：FAQ 是检验问题的地方

FAQ 分为两部分。首先是外部 FAQ，即客户会问的问题。然后是内部 FAQ，即团队必须回答的问题。AWS 明确表示，它不会收录所有能想到的问题，而是从最重要的那个开始。

在保险的例子中，最重要的外部问题可能是“当 AI Agent 出错时，谁来负责？”。一个示例回答：AI Agent 只提供建议，理赔员仍然决定批准还是拒绝，并且每条建议都会被记录下来以供日后审查。

最重要的内部问题可能是“理赔数据存放在哪个系统里，我们有访问权限吗？”。一个示例回答：理赔数据存放在现有的理赔管理系统中，客户的 IT 团队必须在项目开始前授予测试环境的只读访问权限。

任何你还无法回答的问题都是风险。把它写进计划里，而不是让它在演示时才暴露出来。

作者强调，最好的 PR/FAQ 来自多次迭代，并听取跨职能团队的反馈。在客户现场，这个团队包括运营人员、IT、合规部门和你自己的团队。纸面上的每一次修改，都比代码里的修改便宜得多。

把 PR/FAQ 写错的三种方式

最常见的错误是把新闻稿写成功能清单：“支持 OCR、API 集成、实时仪表盘”。这种清单忽略了从客户角度写作的要求，因为它描述的是你的团队在做什么，而不是用户因此省去了什么工作。

第二种是把所有能想到的问题都塞进 FAQ。三十个问题权重相同，客户方的读者无法判断哪一个可能让项目夭折。学学 AWS 的做法：最重要的问题放前面，其余的放后面。

第三种更难察觉：草稿只有你自己的团队读过。如果几轮下来客户方没有任何人提出意见，那这份 PR/FAQ 只不过是你的猜测换了个更好的格式，你也就失去了在纸面上解决问题这一核心价值。

应该按什么顺序阅读？

先从 workingbackwards.com 上关于 PR/FAQ 流程的讲解和 AWS Executive Insights 上关于产品管理的文章开始。两者都是免费的，足以让你写出第一版草稿。然后再读这本书，理解这个流程为何如此设计，重复的轶事略读即可。

这本书适合刚转入 FDE 角色的工程师，也适合技术背景深厚、但仍然习惯于领一张工单就直接开始写代码的人。

如果你正在转行，可以把一份去掉客户细节的 PR/FAQ 放进作品集。当面试聊到客户调研或需求界定时，你可以拿出一份真实的文档，而不是泛泛而谈。

下次客户说“我们想要 AI”时，不要打开编辑器。打开一张空白页，写下客户在项目完成那天想要读到的那份新闻稿。
