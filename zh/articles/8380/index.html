面向 FDE 面试与生产系统的 AI 评测

原标题：AI Evaluations for FDE Interviews and Production Systems

The Forward Deployed · 2026-07-05 · 约 8 分钟读完

摘要

本文面向前沿部署工程师，讲解如何用评测（evals）证明 AI 系统在生产环境可靠。核心观点：演示表现好不等于客户数据上可用，无法度量就无法弥合差距。文章分层介绍离线评测、在线评测和 LLM-as-judge 三种方法，强调评测集需可重复、需按日运行回归、需用人类专家校准裁判模型，并给出样本量与噪声带的计算方法。

要点

  • 评测是区分能交付演示与赢得生产信任的工程师的关键技能。
  • 评测分三层：离线回归、在线真实流量监测、LLM-as-judge 打分。
  • 裁判模型需用人类专家评分校准，GPT-4 级裁判与人类一致率可超 80%。
  • Morgan Stanley 案例显示每日回归测试与顾问高采用率并存。
  • 小评测集分数差异可能只是噪声，需计算标准误并优先做配对比较。

学习构建黄金数据集、选择有用的指标、评估模型行为、运行回归测试，并通过评测在生产级 AI 中赢得信任。

如果在生产部分你只学一件事，那就学这一件。评测（evals）是你判断一个概率性系统是否可靠的方法，而“先建评测”的习惯是区分“只会交付演示的工程师”和“能在生产环境中赢得客户信任的工程师”的最清晰分界线。它是这个角色技术能力的核心信号。

为什么这就是工作本身，而不是杂务

每个 FDE 项目都会遇到这样的模式。模型在演示中表现良好。你把它跑在客户的真实数据上——几十年的不一致记录、无人记录过的边缘案例、监管机构必须能够签字确认的问题——它就崩溃了。弥合这个差距就是部署工作，而你无法弥合一个你无法衡量的差距。

在继续阅读之前：一位客户问：“我怎么知道这个助手是准确的？”你可以说“我们测试过，看起来不错”。为什么这个回答会让你失去资格，一位资深的 FDE 又会怎么回答？

“看起来不错”之所以不合格，是因为它经不起下一个问题：在什么上准确、如何衡量、如果明天变差了你怎么知道？资深的回答会给出一个针对数据集的数字：“我们在一组固定的代表性问题上给它打分，由领域专家和自动化评审员共同评分；它目前处于某个已知的准确率水平，而且我们每天重新运行整套测试，这样回归问题一天之内就会暴露。”这一句话包含了数据集、评分者、数字，以及让它保持可信的执行节奏。

三个层次，按顺序构建

评测不是单一的东西。你要分层构建，每一层回答上一层无法回答的问题。

离线评测——它到底能不能用？

从一个固定的输入数据集开始，每个输入都配有正确答案的概念，并在任何东西上线之前先运行它。这是你的回归测试套件。对于一个检索助手来说，就是一组真实问题，以及它们应该检索到的段落或答案。离线评测的核心在于可重复性：同一套测试，在每次变更时都运行，这样你才能判断新的提示词或模型是变好了还是变差了。没有它，每一次“改进”都只是猜测。

在线评测——它在真实环境中能用吗？

离线数据永远无法覆盖真实用户行为的完整分布。在线评测衡量的是线上系统：采样真实流量、记录输出、追踪点赞/点踩、升级转人工和任务完成情况。你的离线分数与在线分数之间的差距本身就是一个信号。差距过大意味着你的测试集不像真实情况，需要修复的是你的测试集。

LLM 作为评审员——如何大规模地为“好”打分？

大多数 FDE 的产出并非对错之分，而是更好或更差——一段摘要、一个答案、一封邮件草稿。你不可能对每一个都进行人工评分。标准做法是用一个强大的模型作为裁判：给它输入、输出和评分标准，让它打分。这既便宜又可扩展，但有两种失效模式需要注意：裁判有偏见（偏好更长的答案、偏好自己的风格），而且会漂移。因此，你要用人工评分对裁判进行校准抽样，并在高风险环节保持人工参与。裁判是放大人类判断，而不是取代它。

Calibration is a procedure, and it is short enough to recite: sample real outputs from the system, have humans — ideally the customer's domain experts — grade them against the same rubric the judge uses, and measure how often the judge agrees with the humans. When they diverge, the disagreements are the diagnostic: an ambiguous rubric gets rewritten, a biased judge gets a different prompt or model, and if the humans disagree with each other, the rubric was underspecified for people too. The benchmark to know: Zheng et al., studying this systematically, found that strong LLM judges like GPT-4 can "achiev[e] over 80% agreement, the same level of agreement between humans" — which makes human-to-human agreement the natural bar, since a judge near it scores about as consistently as your experts do. The same paper documents the judge biases you are calibrating against: position bias, verbosity bias, and self-enhancement bias.

赢得信任的纪律：每天运行

一次性的上线前评测，在语料库或模型发生变化的那一刻就会过时。在受监管的环境中，“上线时是准确的”不是辩护理由。真正能赢得采纳的做法，是建立一个常驻回归测试套件，在每次变更时和按计划定期运行，让漂移在一天之内暴露出来，而不是在客户会议上才被发现。Morgan Stanley 项目就是现成的案例：团队针对固定的问题集每天运行回归测试，顾问采纳率接近全员水平。资料来源将这两个事实并列呈现；把前者解读为赢得后者的原因，是本课程基于项目页面的论证。信任不是一次上线事件，而是客户能看到的、始终在运行的流程。

差 / 良 / 优——“你如何评估这个系统？”

差——“我试了一堆提示词，输出看起来是对的。” 这是轶事，不是测量。它无法检测回归，无法向监管机构辩护，还会告诉面试官你从没运行过真实的东西。

良——“我构建了一个代表性案例的测试集，并在上线前评估了准确率。” 这是真正的离线评测，属于扎实的中级水平工作。与“优”的差距在于：它只是一个快照，没有考虑线上分布，也没有说明你会如何发现系统变差。

很好——每次变更都跑离线回归套件，在线指标监测真实流量，用一个以专家评分校准的 LLM 评审来覆盖主观部分，再加上每日运行以便快速暴露漂移。客户的合规标准被编码进评审的评分细则中。 分层、持续，并与客户对“好”的实际定义挂钩——这是一个真实的受监管部署所采用的结构。

这个变更是真实的吗？

一个常设的评测套件会产生一连串分数，而一连串分数会引出一个上面各层无法回答的问题。昨天套件读数是百分之八十二；你改了提示词；今天是百分之八十四。是改进还是噪声？在有限案例集上的评测分数只是对系统在完整分布上表现的估计，而任何估计都带有抽样噪声。案例集越小，噪声区间越宽——小于该区间的 Delta 不过是披着百分比外衣的抛硬币。

区间的宽度来自比例的标准误，计算只需几行：

Standard error of a proportion:   SE = sqrt(p × (1 − p) / n)

At a score of p = 0.8 on n = 200 cases:
    0.8 × 0.2 = 0.16
    0.16 / 200 = 0.0008
    sqrt(0.0008) ≈ 0.028          → one SE ≈ 2.8 points

So an 82% → 84% move is a two-point delta, well inside one SE.

Growing the set shrinks the band:
    0.16 / 1000 = 0.00016
    sqrt(0.00016) ≈ 0.013         → at n = 1,000, one SE ≈ 1.3 points

从这个算术可以得出三条操作规则。第一，按你需要检测的 Delta 来确定评测集的规模：小 Delta 需要大集合，如果你负担得起的集合很小，那么只有较大的变化才可读——在构建套件时就要决定哪些 Delta 是重要的。第二，优先在同一批案例上做配对比较：让新旧版本跑完全相同的套件，剔除两者一致的案例，从两者不一致的案例中读取结果。如果新版本赢得了大多数不一致的案例，说明变更确实起了作用；如果不一致案例大致对半分，那你看到的只是噪声。共享案例在比较中相互抵消，这使得它能分辨出比两个独立抽样分数更小的差异。第三，当发布门禁取决于这个数字时，在分数旁边注明噪声区间——“八十四，正负三”能让签字的人准确知道这个数字能承载多大的分量。

上面的评审校准流程遵循同样的逻辑：评审与专家之间的一致率同样是在有限样本上测得的比例，因此带有同样的区间，而只用少数案例校准的评审只是名义上的校准。

一个最小化的评测框架

你不需要框架就能起步。下面的骨架就是全部思想：一个数据集、一个打分器、一个聚合。(示例代码。)

# eval_harness.py — the smallest thing that is a real eval
import json

def load_cases(path):
    # each case: {"input": ..., "expected": ...(optional), "rubric": ...}
    return [json.loads(line) for line in open(path)]

def score(case, output, judge):
    """Return a 0..1 score. Swap in exact-match, retrieval-hit, or LLM-judge."""
    if "expected" in case:
        return float(case["expected"].lower() in output.lower())  # cheap offline check
    return judge(case["input"], output, case["rubric"])           # subjective -> judge

def run(cases, system, judge):
    results = [(c, system(c["input"])) for c in cases]
    scores = [score(c, out, judge) for c, out in results]
    return {
        "n": len(scores),
        "mean": sum(scores) / len(scores),
        "fails": [c["input"] for (c, _), s in zip(results, scores) if s < 0.5],
    }

# Run it on every change. Check `mean` against last run; investigate `fails`.

三个特性使它成为真正的评测而非演示：它是可重复的（每次运行相同的案例）、它能聚合（一个可以随时间追踪的数字）、它能暴露失败（一份供你去修复的清单）。其余一切——更好的数据集、校准过的评审、在线抽样——都是在这条主轴上的精化。

面试中要带走什么

在 AI 系统设计环节中，当提示词涉及任何准确性、安全性或合规性标准时，不要一上来就谈模型或向量存储。应当首先阐述你将如何持续地、基于一个贴近客户真实场景的数据集来衡量正确性，以及人类在流程中处于什么位置。画架构图说明不了什么；评测策略才是决定答案成败的关键。
