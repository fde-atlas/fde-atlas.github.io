FDE 部署手册、操作手册与模板仓库

原标题：FDE deployment playbook, runbooks and template repo

FDE Times · 2026-10-09 · 约 6 分钟读完

摘要

文章提出，前沿部署工程师若不把交付成果沉淀成文档和模板，项目就沦为难以规模化的一次性定制。作者给出约三小时可完成的最低配置：记录架构决策的 ADR、纯操作步骤的 runbook、按阶段组织的 playbook，以及用 GitHub 模板仓库（而非 fork，避免泄露旧客户历史）打包的代码。文中以虚构的物流公司发票 Agent 为例演示各文档写法，并强调与客户运维人员共同演练 runbook、在 ADR 中标注“何时重新评估”。最后建议求职者在简历中具体展示打包复用能力。

要点

  • 交付项目不沉淀文档，就会变成难以规模化的纯定制。
  • 最低工具包：ADR、runbook、分阶段 playbook 和模板仓库。
  • ADR 最关键的是“何时重新评估”，说明决策依赖旧客户条件。
  • 用模板仓库而非 fork，避免旧客户提交历史泄露。
  • 简历应写明打包复用成果，而非只写“为客户部署了系统”。

五份文档和一个模板仓库，大约三个小时就能完成，让团队在 FDE 离开时学到的经验不再随之流失。

简要说明

  • 每个交付的项目都是产品的原材料。如果不把它写下来，这些工作就只能停留在一次性的定制上，而定制是很难规模化的。
  • 最基本的工具包包括：用于记录决策的 ADR、用于运维的 runbook、一份分阶段的 playbook，以及一个模板仓库。
  • 从模板创建的仓库只有一个提交记录，因此老客户的历史记录不会带过去。而 fork 则会携带完整的历史。

部署的最后一周往往匆匆而过：演示、验收签字、交接，然后奔向下一位客户。三个月后，第二位客户带来了同样的问题，团队又得从一张白纸开始。

fde.academy 上的 FDE playbook 将部署分为六个阶段。最后一个阶段是反馈闭环，即为每位客户构建的定制工作逐渐标准化为可复用的功能。同一网站上关于 Palantir 模式的文章说得更直接：FDE 构建的每一个解决方案都会为后续的产品开发提供养分。

同一篇文章也指出了其中的隐患。如果这个闭环没有得到管理，工作就会滑向纯粹的定制，变得极难规模化。因此，将已完成项目打包的能力，实际上就是“为产品做出贡献”与“逐个客户做一次性定制”之间的分界线。

一个晚上能做出什么？

完成之后，你将拥有一个文档文件夹和一个 GitHub 上的模板仓库。作为贯穿全文的示例，假设你刚为一家物流公司交付了一个读取 PDF 发票并将数据推入其 ERP 的 agent。这个例子是假设性的，但下面的结构适用于任何类型的项目。

你需要四样东西：一个 GitHub 账号、老项目的仓库、部署期间的会议记录或聊天记录，以及大约三个不受打扰的小时。目标结构如下（已简化）：

fde-invoice-agent-template/
├── README.md            # what problem this repo solves, how to run it
├── docs/
│   ├── adr/             # architecture decisions, one file per decision
│   ├── runbooks/        # how-to: incident handling, operations
│   ├── explanation/     # why the system works the way it does
│   └── playbook.md      # deployment phases for a new customer
├── config/
│   └── customer.example.yaml
└── src/

需要撰写的五份文档是 README、ADR、runbook、说明文档和 playbook。下面的步骤将逐一介绍，最后把所有内容打包进模板仓库。

第 1 步：趁记忆还新鲜，记录下决策

adr.github.io 上的定义很简短：架构决策记录（ADR）记录一项架构决策及其背后的理由。打开会议记录，寻找团队曾经争论过的要点，例如选用哪种 OCR、批处理还是实时处理，或者 agent 应该自行修正数据还是等待人工批准。

# ADR-003: The agent does not write directly to the ERP; it waits for human approval

## Context
Invoice formats are inconsistent; the customer's ERP does not support rollback.

## Decision
The agent writes to a staging table; accounting approves before data is pushed to the ERP.

## Consequences
+ No incorrect data reaches the books.
- Adds a manual step; approval time needs to be measured.

## When to revisit
When a new customer's ERP has an undo API.

“何时重新审视”这一节是最有价值的部分。它告诉接手的人：该决策依赖于旧客户的特定条件，因此新客户可能需要不同的做法。检查：把 ADR 交给一位未参与该项目的同事。如果他们读完之后仍然问“为什么不直接写入 ERP？”，说明文档缺少背景信息。

第 2 步：将操作手册与解释性内容分开

Diátaxis 将操作指南定义为引导读者解决问题或达成结果的指引。操作手册应本着这种精神编写：每一步都是一个动作，中间不要夹杂解释性段落。把“为什么”留给

docs/explanation/

.

# Runbook: Invoice queue is stuck

Goal: the queue runs again and no invoices are lost.

1. Open the queue dashboard; note the number of invoices waiting.
2. Check the worker logs for the last 15 minutes, looking for OCR timeout errors.
3. If there are timeouts: switch the worker to file-by-file processing mode.
4. Confirm the number of waiting invoices is going down.
5. If it has not gone down after 30 minutes: alert the customer's on-call contact (see directory).

Understanding the cause: docs/explanation/ocr-timeouts.md

示例中的数字仅作说明之用；请替换为你系统的真实阈值。检查：快速浏览操作手册。如果任何一步以“请注意，系统……”开头，就把那句话移到解释部分。

第 3 步：与将要使用操作手册的人一起编写

Google 的 SRE 手册在事故管理一章中建议提前做好准备：尽早与将要参与处理事故的人员共同制定并记录事故处理流程。在发票 Agent 的例子中，如果客户在交接后自行运营系统，那么这些人就是客户的 IT 团队，而不是你的团队。

所以不要独自编写操作手册然后通过邮件发送文件。安排一次 45 分钟的会议，让操作人员逐步执行每个步骤，而你坐在一旁默默观察。任何他们需要询问的步骤都需要重写。

第 4 步：按阶段组装 playbook

playbook.md

并不是 ADR 的副本。它是一张地图：针对每个部署阶段，写下要向客户询问什么、需要阅读哪些 ADR 以及需要提前准备哪些操作手册。你可以使用 fde.academy playbook 的六个阶段作为框架，只要最后一个阶段始终是反馈到产品的闭环即可。

## Phase: Data integration
- Ask the customer: does the ERP support undo? (→ ADR-003)
- Prepare: runbooks/queue-stuck.md
- Customised for the previous customer: parser for a custom invoice template
  → candidate for the product (core team notified)

最后一行正是 Palantir 式闭环真正发生的地方：来自一线的解决方案由核心团队评审，并转化为产品能力。每当你写下“产品候选功能”，你就把项目从纯定制的陷阱中拉了出来。

第 5 步：构建模板仓库，而不是 fork

GitHub 的文档说明，任何有权访问模板仓库的人都可以基于它创建新仓库。以这种方式创建的仓库只包含一个提交。而 fork 则不同：它会携带完整的历史记录。

对 FDE 来说，这个区别很重要。旧项目的提交历史中可能包含客户名称、内部端点，或者有人误提交后又删除的示例 CSV 文件。

最干净的流程是创建一个新仓库，只复制清理后的代码，将所有客户特定的值替换为

customer.example.yaml

，然后在仓库设置中开启模板模式。

检查： 用模板创建一个测试仓库，打开提交历史，确认只有一个提交。然后在整个代码库中搜索旧客户的名称、他们的域名以及诸如 “prod” 之类的词。结果应该为空。

三个让文档变得毫无用处的错误

第一个是把操作手册当作教科书来写。《SRE》一书中关于值班工程师培训的章节指出，仅通过流程、清单和手册来进行培训是一种反模式。

操作手册帮助人们执行正确的步骤；而

explanation/

文件夹帮助他们理解背后的原因。当事故看起来与任何书面步骤都不符时，只有这种理解才能救他们。

第二个错误是为了省时间而直接复刻（fork）旧客户的仓库，把它的全部提交历史都带了过来。第三个错误是只记录“是什么”而跳过“为什么”。没有 ADR，下一个客户就会继承那些只在旧客户情境下才说得通的决策。

这项技能在招聘中如何体现？

在阅读 FDE 职位描述时，你可能会以各种名称遇到上述反馈循环。留意那些关于把一线经验带回产品团队，或构建可跨客户复用资产的段落：这表明该公司恰恰需要这项技能。

在简历上，不要只写“为客户 Y 部署了系统 X”。要更具体一些，例如：“将项目打包成模板仓库、ADR 和操作手册；下一个客户无需从零重写即可复用”。如果可以，附上一个清理过的公开模板仓库的链接。在面试中，选一个 ADR，讲讲它背后的争论过程。

在新客户那里的第一天，首先要打开的是上一个项目的

playbook.md

，而不是 IDE。一个交付的项目只有当下一个人能够复用时，才会成为团队的资产。
