DataHub 与 Atlan 对比：FDE 如何盘点客户数据

FDE Times · 2026-10-08 · 约 5 分钟读完

摘要

文章以 FDE 入驻客户第一周的场景，对比数据目录工具 DataHub 与 Atlan：前者开源（Apache 2.0，可自托管），后者为专有 SaaS 且未公开定价，两者均支持 80 多个连接器。作者认为选型取决于客户现状而非工具优劣，并强调接入数据源只是起点，真正价值在于指定资产负责人、标记 PII 和划分敏感级别。文中用零售商 Agent 案例说明：40 个订单相关资产中 70% 无人负责，并指出两大常见错误——未确认范围就接入全部数据源、标记 PII 却不指定负责人。结论是治理先行，否则构建 Agent 后必然返工。

要点

  • DataHub 开源可自托管，Atlan 是未公开定价的专有 SaaS。
  • 两者连接器均超 80 个，选型取决于客户现有环境。
  • 案例中 40 个订单资产仅 12 个有负责人，占七成缺口。
  • 常见错误：未书面确认范围就接入数据源、标 PII 不定负责人。
  • FDE 应先完成归属与分级，再让 Agent 读取数据。

DataHub 和 Atlan 能标出每张表归谁负责、哪些列含个人数据，前提是按对的顺序用。

要点速览

  • DataHub 的开源核心采用 Apache 2.0 许可，可通过 UI 或 CLI 接入元数据；Atlan 是专有 SaaS，未公开定价。
  • 两者都提供 80 多个连接器，选哪个通常取决于客户想自己运维，还是直接买现成的。
  • 接入数据源是容易的部分，真正的价值在于指定负责人、标记 PII 和划分敏感级别。

Atlan 的文档承诺，只需“几分钟”就能完成平台配置、接入首批数据源并掌握基本概念。这是厂商的说法，就技术连接这一步而言，也许确实如此。

但凡刚到新客户现场的前线部署工程师（FDE）都知道，这几分钟回答不了第一周真正的问题：哪些表可信，谁对它们负责，哪些列含有个人信息。

这正是数据目录值得学的原因。当你要基于客户数据构建 Agent 或数据管道时，代价最高的错误很少出在模型上，而是用错了表，或者把敏感数据发到了不该去的地方。

DataHub 和 Atlan 代表两种不同路线：一个有开源核心，一个是专有 SaaS。弄清它们能做什么，尤其是使用的先后顺序，就能在第一周内摸清客户的数据全貌。

两种工具，两条路通向同一张地图

DataHub 将自己定位为面向 AI 和数据的上下文管理平台，把发现、治理和可观测性整合到整个数据栈中。Atlan 则称自己是 AI 的“上下文层”，把数据与业务定义和访问策略关联起来。

连接器方面，Atlan 文档宣称支持 80 多个数据源；独立对比网站 Modern DataTools 认为两者不相上下，各有 80 多个。真正的区别在部署模式。

DataHub

  • 开源核心，Apache 2.0 许可
  • DataHub Core 免费；DataHub Cloud 面向企业
  • 自托管或托管服务
  • 通过 UI 或 CLI 接入元数据

Atlan

  • 专有 SaaS
  • 未公开定价
  • 核心能力：目录、治理、血缘、质量、术语表

所以到了客户现场，第一个问题不是哪个工具更好，而是客户现在处于什么状态。如果客户有基础设施团队，希望一切留在自己的网络内，自托管 DataHub 是自然的选择。如果客户已经买了 Atlan，你的任务是把现有的工具用熟，而不是劝他们换掉。

用数据目录的第一周是什么样？

假设有一家零售商，需要一个能回答订单问题的 Agent。它有一个数据仓库、几个看板，还有一个没人记得是谁建的原始文件夹。第一天的首要任务是把这些数据源接入目录，一行提示词都还没写。

用 DataHub 时，可以通过界面快速加载元数据，也可以用 CLI，让配置得以保存、评审和重复运行。在客户现场，后一种更有价值，因为它给接手的人留下了记录。

元数据接入后，最有用的工具是搜索框。DataHub 能在整个生态中搜索，包括看板、数据集、ML 模型和原始文件。输入“order”，你第一次看到“订单”这个概念出现的所有位置，而不只是带你的人碰巧提到的那张表。

一笔小账，看清真正的工作量

假设搜索返回 40 个与订单相关的资产。你四处打听，只能确认其中 12 个的负责人。剩下的 28 个，也就是 70%，是没人负责的数据，这就是你要带到周末会议上的数字。

DataHub 支持在目录内定义归属并追踪 PII。因此下一步是为已知的 12 个资产指定负责人，再标记含个人信息的列，比如姓名、电话号码和收货地址。

接下来是分级。Palo Alto Networks 将数据分类定义为按敏感程度、重要性和预设标准组织数据。常见级别为公开、内部使用、受限和机密。

套用到这个例子：商品目录表可能属于内部使用，而存有电话号码的客户表显然属于受限或机密。

让第一周跑偏的两个错误

最常见的错误是还没和客户商定范围，就接入所有数据源。80 多个连接器让这件事非常容易，但塞满与订单问题无关的元数据，只会让搜索结果更嘈杂，你还可能碰到客户并未授权你查看的系统。

首次接入之前，先以书面形式确认数据源清单。

另一个错误是标记了 PII，却没有指定具体负责人。如果某列标注为电话号码，却没人对它负责，那么当 Agent 需要读取权限时，没有人有权批准或拒绝。所以在上面的例子里，指定负责人排在标记 PII 之前。

难的部分，数据目录替你做不了

第一个局限是速度的承诺。Atlan 所说的“几分钟”，是厂商针对连接这一步的说法。指定负责人需要有人回答问题，没有哪个工具能自己知道一个匿名原始文件该由谁负责。

第二个局限在于如何看待 AI 的上下文。DataHub 在 2026 年 4 月的一篇博客中提出，语义层必要但不充分；Agent 还需要血缘、归属、数据新鲜度和访问权限。文章还认为，治理不是事后再补上的功能。

这是一家卖数据目录的公司的观点，自有其动机，但它建议的工作顺序与真实部署中的情况相符。

对 FDE 来说，结论很直接：先建 Agent、后问权限，你就得返工客户最在意的那部分。

先学什么，怎么展示

从 DataHub Core 入手，因为它开源，在自己的机器上就能跑，不需要签合同。按真实工作的顺序学：先通过 UI 接入，再用 CLI，然后是搜索、指定归属、标记 PII。没有使用 Atlan 的客户，很难接触到它，所以起步阶段读读文档、熟悉术语表和血缘的概念就够了。

面试 FDE 岗位时，可以问一个问题：“在你们最近的客户那里，谁决定 Agent 能读哪些表？这个决定记录在哪里？”答案能告诉你，这家公司把治理当作 FDE 的工作，还是别人的事。

简历上不要写“有数据目录使用经验”，而要用数字写出成果：接入了多少数据源，有负责人的资产占比前后各是多少，标记了多少个 PII 列。

建模型的人，客户几乎随便就能招到。真正赢得信任的，是你在第一周结束时能交出一份清单，写清楚哪些数据可以安全地交给 Agent 读取。
