与系统集成商合作：FDE 负责什么

原标题：Working with systems integrators: what the FDE owns

FDE Times · 2026-11-06 · 约 7 分钟读完

摘要

文章讨论厂商FDE与系统集成商（如Accenture、Deloitte）协作时的职责划分。核心矛盾在于双方对“完成”的定义不同：SI按合同范围交付，FDE以业务结果为准。作者以保险理赔Agent为例，指出UAT全过但评测仅85%达标的情况，并提出责任矩阵、评测集作为共同验收标准、每周平台简报和交接演练等做法，以及FDE应避免的三个陷阱。

要点

  • OpenAI、Deloitte等已让FDE与咨询伙伴同场协作。
  • SI按SOW交付，FDE以生产环境的业务结果定义完成。
  • 示例中UAT 20/20通过，但200条真实理赔评测仅85%。
  • 建议用责任矩阵明确每行唯一主责人。
  • FDE应把评测集变成共同验收标准并做好交接。

系统集成商按 SOW 交付；而 FDE 负责一个以业务成果衡量的“完成”标准，此外还要掌握产品知识并完成向运营团队的交接。

简要概述

  • 厂商 FDE 与系统集成商团队的合作日益增多：OpenAI 引入埃森哲和凯捷与其 FDE 团队协同工作，德勤也已将 FDE 编入其交付团队。
  • 最脆弱的环节是“完成”的定义：系统集成商按项目范围接受评判，而 FDE 只有在业务成果于生产环境中真正跑起来时才算完成。
  • FDE 靠三件事来主导工作：以评测衡量的验收标准、定期的平台简报，以及与系统集成商工程师共同演练过的交接流程。

当你参加与企业客户的第一次启动会时，发现房间里并非只有你一个技术人员。桌子对面坐着埃森哲或德勤的团队，手里有已签署的 SOW、时间表和自己的项目经理。你脑海中冒出的第一个问题是：那我到底是来干什么的？

这种情况越来越常见。2026 年 2 月 23 日 OpenAI 发布其 Frontier 平台时，埃森哲和凯捷等咨询公司作为合作伙伴加入，与 OpenAI 的 FDE 团队并肩工作。更早之前，2025 年 12 月，埃森哲与 Palantir 成立了联合业务部门，依托超过 2,000 名具备 Palantir 技能的埃森哲员工。

因此，与系统集成商（SI）协作已成为 FDE 工作的一部分，而不再只是销售侧的事务。做得好，它能让你主导技术工作而不必事必躬亲。

做得不好，就会出现两种结果之一：你变成系统集成商的答疑客服，或者变成客户办公室里他们的竞争对手。

两个团队，两种“完成”的含义

初看之下，分工似乎很清晰：系统集成商负责构建和集成，而你是最懂平台的人。但双方的考核标准并不相同。

据 Webfuse 所述，咨询项目的范围和方法由 SOW 事先固定，咨询顾问按是否完成该范围接受评判，咨询公司则追踪人员利用率。

相比之下，FDE 的评判标准是真实的生产使用情况和对工作流程的可衡量影响。Entrans 是一家销售 FDE 服务的公司，其观点应视为带有自身立场的看法，它表示只有当系统真正交付预期的业务成果时，工作才算完成。成功也不是以正常运行时间或 API 延迟等传统 SLA 来衡量的。

而这两个里程碑之间的空间，往往无人签字确认。

Forgepoint Capital 解释了为什么这一缺口难以通过合同来弥合：AI 项目的质量很难写进条款。它提出，如果双方连“什么是好”都无法达成一致，又如何能就 SOW 中的交付物达成一致呢？

这是一种观点，而不是测量结果。但它解释了为什么最难定义的部分——包括评测、Agent 行为以及模型错误的处理——往往会落到你头上，即使合同里对此只字未提。Salesforce 的 Nick Johnston 说得很直白：Agent 时代将由业务成果决定，而不是由试点决定。

这些都不能说明 SI 是行动更慢的一方。2026 年 8 月，Deloitte 宣布将在一个 Salesforce 项目中把 FDE 直接编入其解决方案交付团队。SD Times 也认为，FDE 是对传统顾问的补充而非替代，填补了他们较弱的环节。头衔并不重要，重要的是谁对什么负责。

一个实际案例：保险理赔 Agent

假设客户是一家保险公司，希望有一个 Agent 阅读理赔文件，并建议批准或转交人工审核员。

SI 的 SOW 将“完成”定义为：Agent 与理赔管理系统集成，并通过包含 20 个场景的 UAT。客户希望将简单理赔自动化，前提是 Agent 的准确率至少达到 95%。

现在来算一笔账。Agent 通过了全部 20/20 个 UAT 场景，因为这些全是正常路径的用例。但当你在包含 200 条真实匿名理赔的评测集上运行时，它只答对了 170 条，即 85%。按合同，项目已经完成；但客户需要的业务成果并未达成。

这里没有人做错什么。SI 交付的完全符合签署的内容；只是合同衡量了错误的指标。你的职责是在第一周就发现这个差距，而不是在上线当天才发现。

第一个工具是责任矩阵，在任何人开始写代码之前完成：

领域SI供应商 FDE客户
与理赔系统的集成、身份验证、内部数据主要负责人就 API 限制提供建议授予访问权限
评测套件及 95% 的阈值在 CI 中运行设计并对其质量负责标注数据，批准阈值
Agent 设计、模型错误处理实现主要负责人确认业务规则
平台限制及即将发生的变更被告知主要负责人被告知
上线后的运维手册主要负责人共同编写、共同演练批准

每一行都有且只有一个主要负责人。第二行是你发挥主导作用的地方：评测套件成为共享的验收文档，SI 团队在每次变更时都运行它。这样，合同意义上的“完成”和业务成果意义上的“完成”最终就是同一回事。

在不越界的前提下指出差距

你如何呈现 85% 这个数字，与数字本身同样重要。在每周例会上，你可以这样说。

你：“UAT 已全部通过，贵团队的集成工作也非常扎实。我们刚刚又运行了 200 条真实理赔，准确率为 85%，而业务目标是 95%。差距主要出在 Agent 的行为上，这是我们这一方的责任。”

SI 负责人：“那这会影响我们的时间表吗？”

你：“不会影响集成。我只是建议把这 200 条索赔加入你们的 CI，让每次构建都输出一个分数。我们修复 AI Agent，你们就能立刻看到结果。”

这段对话恰好做了三件事，且顺序明确：肯定 SI 做得好的部分，主动承担差距的责任，并提出一个共享机制——在 CI 中运行评测——而不是指责任何人。

第一周就要做的几步

首先，请求阅读 SI 的 SOW，或至少是范围和验收条款。用一句话写下其中“完成”的定义，再与客户真正需要的结果进行对比。这两句话之间的差距就是你的工作计划。

接着，起草责任矩阵，并请客户的技术负责人确认。一旦客户同意，SI 就不会觉得是你擅自给自己安排了角色。

然后，用真实数据构建评测套件，并将其提议为共享的验收标准。发布在 dev.to 上的一份 FDE 指南建议，在编写生产代码之前，先用一个可衡量的数字来定义“可用”。如果质量真的像 Forgepoint 所说的那样难以写进合同，那么一套可运行的评测套件就是最接近质量条款的东西。

之后，与 SI 工程师建立一个简短的每周平台交流：平台的限制、故障时的行为以及即将到来的变更。这是只有你掌握的知识，尽早分享往往能为双方节省数天的调试时间。

最后，从一开始就准备好交接。同一份指南描述了 FDE 留下的东西：一个正在运行的系统，以及组织独立运营它的能力。

当 SI 将接管运营时，与他们一起编写运维手册，并演练一次事故：由 SI 工程师处理，而你只在旁观察。

让 FDE 丢掉角色的三个陷阱

最常见的陷阱是把 SI 当作对手。在客户的办公室里，两个团队要么一起赢，要么一起输，应该带进会议室的观点是：FDE 是咨询顾问的补充。

另一个陷阱是为了赶进度而悄悄替 SI 完成他们的工作。当进展缓慢时，很容易失去耐心。但你替他们写的代码，在你离开项目的那一天，没有人知道如何运行。

最难察觉的陷阱是把平台知识据为己有，让自己显得不可或缺。你拿薪水是为了让客户和 SI 能够自己运营系统，而不是让他们永远离不开你。

如果你在一家技术供应商面试 FDE 职位，直接询问你与集成商或咨询合作伙伴合作的频率。答案会告诉你，你每天将使用哪些技能。

在简历上，要具体：你把哪套评测套件变成了共享的验收标准，以及 SI 团队从什么时候开始独立运营系统。

下次系统集成商在项目启动会上坐在你旁边时，不要问你是来干什么的。要问合同里如何定义“完成”。
