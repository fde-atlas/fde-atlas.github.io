企业系统设计不是“设计一个社交网络”

原标题：Enterprise system design is not ‘design a social network’

FDE Interview Prep · 2026 · 约 11 分钟读完

摘要

这篇文章针对 FDE 面试中的系统设计环节，主张设计应从客户环境而非流量规模出发。作者以医院短信通知和虚构泵制造商为例，给出七个必须先问的约束问题（合规、数据量、延迟、身份、部署边界、运维、上线标准），并演示每个答案如何改变架构，如 Entra 分组过滤、ERP 内网集成、GDPR 数据驻留等。文章还列出开局五忌、一小时答题结构，并引用 Blind、Reddit 候选人报告及 OpenAI、Okta、Cohere 招聘要求佐证。

要点

  • 设计题应从客户环境切入，而非流量规模。
  • 七个约束问题：合规、数据、延迟、身份、边界、运维、上线。
  • 每个答案都要说明会改变设计的哪一部分。
  • 主动找出相互冲突的约束并当面解决。
  • 引用候选人报告与 OpenAI、Okta 等职位要求佐证。

让一位优秀的后端工程师设计一个通知服务，你会得到扇出、分区和送达率。但如果客户是一家医院网络，并且系统要部署在客户自己的云账户中，第一个问题就变成了：一条短信里能否包含患者的姓名。在以客户为框架的设计面试中，决定架构的是客户的环境，而不是流量。下面介绍如何开场：要问哪些问题、每个答案会推动什么，以及当两者冲突时该说什么。

从客户出发，而不是从规模出发

开场白：“在我评估任何东西之前，我想先了解您的环境；它对方案的影响比流量更大。”

以医院为例，任何流量估算都无法回答这些问题，而在我们的解读中，每一个答案都会改变一个设计要素：

  • 短信可以携带患者数据吗？ 在合规部门明确之前，默认不可以：“您的护理团队有一条新消息；请登录查看。”于是登录页面就进入了设计。
  • 用哪家短信服务商？ 从合规部门批准的名单中选一家；如果患者数据可能到达该服务商，预计需要签署业务伙伴协议。
  • 每次发布由谁审批？ 由他们的变更委员会审批，因此上线计划中要写明这一点。

应当首先询问的约束条件

针对下面的每个约束各问一个问题，然后问第七个关于上线的问题，并在动手画图之前说明每个答案会改变什么。简而言之：合规决定数据存放的位置，身份决定权限来自哪里，运维决定你能负担得起运行什么。

约束答案会改变什么
合规制度数据存放位置、记录哪些日志、允许哪些供应商
数据量与新鲜度批量还是增量摄取
延迟与并发流式处理、缓存、模型规模
身份提供商SAML 还是 OIDC；用户和组如何配置；权限来自哪里
部署边界通过私有连接访问你的云，还是部署在他们的账户中；出站规则
预算与运维托管还是自建部分；发布节奏

大声说出来：

“在我画任何东西之前，先问几个问题，因为每一个都会改变设计。适用哪些规则和审计？数据量多大，多新鲜？人们能等多久，同时有多少人请求？谁登录，通过什么方式登录？这必须运行在哪里，可以调用什么？我们离开之后谁来运维，在这里变更如何进入生产环境？最后一个问题分两部分：上线之前，你们的安全团队需要看到什么？什么能让你们的服务负责人相信这些答案是正确的？”

第七个问题决定了评测集和验收标准。截至 2026 年 9 月，OpenAI 的医疗领域 FDE 招聘启事要求其应聘者定义衡量质量的上线标准，“对照客户特定的验收阈值”。来源 8Forward Deployed Engineer (FDE), Healthcare - SF发布方OpenAI (Ashby)来源类型公司招聘启事

把这些问题一次性批量问出；如果面试官不愿回答，就大声说出你的假设然后继续：“我会假设是 Entra，并会标注这一点。”澄清问题可能耗尽整场时间：一位候选人在 Aced 上于 2026 年 8 月报告，在 Google 一个中级 FDE 职位的面试中，等他问完关于一个非常抽象的系统的问题时，时间几乎用完了。来源 9Google Forward Deployed Engineer Interview Experience发布方Aced（前身为 Exponent）来源类型候选人的个人分享。在拆解类案例中，两个能改变计划的问题就足够了；而在设计轮中，约束条件本身就是问题所在，所以要快速问完全部七个。

每个回答改变了什么：

  • Entra 组： 在搜索查询中、排序之前，根据已验证令牌所属的组过滤段落，绝不要放在提示词里。超过令牌的组数上限时，Entra 会发送一个 Microsoft Graph 指针而不是列表：询问一名技术人员的组数有多少，并使用应用角色或分配给应用程序的组。
  • 本地部署 ERP： 风险最高的集成，通过他们的工厂链路（Direct Connect 或站点到站点 VPN）访问，所以放入第一版。询问其 API 每秒能承受多少次读取；如果早间查询可能超过该上限，就在会话中保留每台机器的历史记录。
  • 每月几百次变更： 增量摄取手册；维修记录留在 ERP 中，实时查询。
  • 延迟与并发： 流式输出答案，然后对模型而非应用进行容量估算：峰值：400 人同时提问，回答：约 10 秒，从开始到结束 => 模型端约 40 请求/秒，输入：每次约 4,000 个 token（问题 + 段落），输出：每次约 400 个 token => 约 960 万输入 token/分钟 => 约 100 万输出 token/分钟。要说：“应用会自动扩缩容；我会第一周就去核查你们账户在该区域的模型配额，因为提升配额需要时间。这个峰值是同时提问的人数，还是登录人数？”
  • 欧盟员工与现场联系人： 问题中可能会提到现场联系人，因此要把欧盟个人数据保留在欧盟区域，并从欧盟的模型端点作答，这是应对 GDPR 第五章最简单的方案。欧盟的跨区域推理配置只留在欧盟区域内；全局配置则不然。在做出更多承诺之前，先询问他们的数据保护官。
  • 供应商审计报告： 答案路径上的每一项服务，包括模型端点，都要先通过他们的供应商评审。
  • 工厂 IT 与变更委员会： 优先使用托管服务，并将模型或提示词的变更作为计划内变更交付，附上评测报告。

然后找出两个不能同时成立的回答，并当场解决矛盾。在这里，任何内容都不能公开，但技术人员却要通过蜂窝网络工作：

“这两点按现在的说法不能同时成立。有两条路：一是从你们管理的平板电脑到现有网络的每应用 VPN，二是在应用前面加一个访问服务。该服务有一个互联网地址，但会拒绝任何没有有效 Entra 登录的请求，并将每次访问记录到具名用户。所以，对你们的安全团队来说：‘不公开’是指不允许未经身份验证的端点，还是完全不允许新的互联网地址？如果是前者，我倾向于访问服务：不必在每台平板上装 VPN 客户端。如果是后者，就用 VPN：应用本身不新增任何地址。这个决定由你们的网络团队来做。”

先问这项约束保护的是什么，推荐一种方案并说明理由，然后把决策权交还给它的所有者。访问服务可以是 AWS Verified Access，它本身是面向互联网的。然后一口气复述这些约束：“也就是说：用你们的 AWS 账户，不对外公开，通过 Entra 登录，欧盟数据存放在欧盟区域，发布需经每周变更委员会，上线前还要通过安全审查。还有没有我遗漏的、会阻碍这项方案落地的事项？”

我们的设计评分标准中，第一个维度考察的是是否询问了上述每一项约束，以及客户的安全和运维团队的要求；与客户一起解决冲突的得分更高。

浪费最初几分钟的五种方式

  • 在问出第一个约束问题之前就开始画架构图。
  • 只问规模。
  • 问那些答案不会改变任何决策的问题。
  • 问得太久，以至于设计根本没开始。
  • 说“我们会让它合规”。合规是客户的整套体系：请描述你提供的控制措施，并预期需要签署 HIPAA 要求处理患者数据的供应商签署的商业伙伴协议。

一小时的结构

按此顺序进行这一小时，并说出每个步骤的名称；每一步都是我们设计标准的一个维度。

  • 需求与约束。 七个问题，目标用数字表示，解决一个冲突。
  • 。 最精简的可部署版本，验证风险最高的集成，包括其进入生产的阶段以及跳过的内容。对于泵制造商：“版本一通过 Entra 登录，基于其手册回答美国技术人员关于一条产品线的问题，并通过工厂链路从 ERP 获取维修历史。在工厂 IT 批准写入路径之前，它跳过向工单写入的操作。”
  • 组件与数据流。 从源到用户的一条路径，每个组件都有理由，并移除一个：“手册存入 S3；一个工作进程对变更的文件重新索引，按区域和产品线为段落打标签；API 位于访问服务之后；模型在技术人员所在区域运行；历史记录是对 ERP 的实时调用，仅在会话期间保留。移除：维修记录的副本；由 ERP 保存它们。”
  • 信任边界与身份。 谁以何种方式认证，权限在哪里强制执行（数据层，绝不在提示词中），什么可以离开系统，以及被盗凭证能触及什么：“ERP 调用使用只读服务身份；被盗的平板电脑令牌在会话结束前只能触及一名技术人员的手册和历史记录。”用 SSO 设计问题 练习。
  • 故障模式与回滚。 每个依赖项会怎样失败，用户会看到什么，以及代码、提示词、配置和数据如何通过各自的变更流程撤销：“如果工厂链路中断，就基于手册回答，并说明历史记录不可用。”用 上线一个有风险的变更 练习。
  • 可观测性与评测。 追踪、答案质量的度量，以及商定的上线标准：“技术人员的问题集，在每次模型或提示词变更时进行评分。”用 How do you know it works? 练习。
  • 权衡、成本与沟通。 以对 CTO 的两句话收尾：“我们选择 [X] 而非 [Y]，原因是 [reason]，并且版本一优先验证 [the risk]。成本的主要驱动因素是 [A]；如果 [C] 发生变化，我会重新审视 [B]。”

我们的评分标准以行走骨架以及可观测性与评测作为门槛：任何一项不达标的运行都无法通过，无论其余部分多么出色。
