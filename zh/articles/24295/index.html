FDE 如何将客户的 IT 团队变成盟友

原标题：How FDEs Turn a Client's IT Team Into Allies

FDE Times · 2026-10-30 · 约 7 分钟读完

摘要

文章讨论前沿部署工程师如何化解客户 IT 团队的敌意。IT 团队担心被取代或接手看不懂的系统，因此 FDE 应在首次会议就明确目标：让客户团队最终能独立运行和扩展系统。具体做法包括第一周就引入安全团队审查数据流、与客户工程师结对编程并记录共同决策、逐步移交所有权。文章还列出五个常见错误，如绕过 IT 团队找高管施压、申请过大的权限、把安全审查留到最后等。

要点

  • IT 团队抵触 FDE，根源是怕被取代和怕接手不理解的系统。
  • 首次会议就承诺：项目结束时客户团队可独立维护系统。
  • 第一周引入安全团队，早期改动成本低，末期改动可能阻断上线。
  • 结对编程与决策日志让移交贯穿全程，最终交接成本极小。
  • 五大错误：越级施压、权限过大、独占演示、无文档、安全后置。

合同里承诺的内容很少与真实数据相符，而客户的 IT 团队最清楚问题出在哪里，所以要从第一天起就让他们成为共同负责人。

简要概述

  • IT 团队对 FDE 保持警惕，是因为他们担心被取代，或者担心接手一个自己不理解的系统，而不是因为你能力太强。
  • 从一开始就明确说明：目标是让他们在没有你的情况下运行并扩展这个系统。
  • 在第一周就邀请安全团队参与，与客户的工程师结对编程，并在整个项目过程中逐步交接。

申请订单数据库只读权限的工单已经三天没有回复。在技术会议上，客户的 IT 负责人双臂交叉，对每个问题都给出同样的回答：“我们需要核实一下。”

这不是无礼。从 IT 负责人的角度看，一个被高层引入的陌生人正在做本该属于 IT 团队的工作。

Palantir 将前沿部署软件工程师的工作比作初创公司的 CTO：小团队、端到端的责任，通常在客户现场工作。职责范围如此之广，FDE 最终做的恰恰是本该落到 IT 团队头上的工作。

即使客户喜欢你，你仍然是外人。First Round Review 报道称，一家财富 100 强公司的总法律顾问亲切地称呼 Ironclad 派来的工程师为“背包客”。这个绰号听起来友好，但要点在于：背着背包来的人，最终也会背着背包离开。

为什么没有他们你就干不了这活？

你可以绕过 IT 团队，让高管支持者向他们施压。但这很快会适得其反。一位前 Palantir FDE 招聘人员告诉 First Round Review，你在现场发现的情况会与合同中承诺的截然不同。

OpenAI 的前沿部署工程负责人向 The Pragmatic Engineer 表达了同样的观点：客户在需求界定阶段描述的情况，往往与他们的真实数据和系统不符。

而知道这个差距在哪里的人——比如哪张表满是垃圾数据，或者哪个任务在凌晨 2 点运行并锁表——几乎总是在 IT 团队里。

把他们排除在外，你就失去了最需要的信息来源。

所以问题不是如何绕过 IT 团队，而是他们在害怕什么，以及你如何回应这种恐惧。

改变叙事：你的使命是离开

IT 团队通常害怕两件事。他们害怕被取代，也害怕接手一个自己不理解的系统，以至于当系统在午夜崩溃时，扛责任的是他们。这两种恐惧的答案是一样的。

Simpliaxis 上的一篇 FDE 项目交接指南设定了一个明确的目标：客户的团队必须能够在不需要联系你的情况下运行并持续开发这个系统。

这份指南还颠覆了通常的看法：让自己变得不再被需要并不会降低你的价值，反而是你价值的证明。CIO.com 上一篇关于智能体 AI 时代 FDE 的文章同样建议从一开始就为所有权移交做好设计，让客户的团队能够运营和扩展系统。

在第一次会议上就这样说，并照此行事，你就不再是那个来取代他们的人。你会成为帮助他们接管新系统的人。

示例：一个库存 Agent 和一个四人 IT 团队

以一个假设的部署为例：为一个零售商部署一个回答库存问题的 Agent。该 Agent 需要从一个由四人 IT 团队管理的 ERP 系统中读取数据。有三件事需要按顺序完成。

第一步：在写下一行代码之前，先开一个 30 分钟的会议。 不要一上来就请求访问权限。先了解真实的系统：“库存表是批量更新还是实时更新？上次数据出错是什么原因引起的？系统上有没有你们不希望任何人碰的东西？”最后一个问题最重要，因为它赋予了他们划定边界的权利。

以一个承诺来结束会议：“到项目结束时，你们的团队应该能够在不联系供应商的情况下修复和扩展这个 Agent。项目日程将围绕这个目标来制定。”

第二步：在第一周就让安全团队参与进来。 CIO.com 的文章强调，智能体 AI 的治理不能是最后阶段才拿出来的合规清单。ElevenLabs 写道，对于其 FDE 团队而言，安全、数据控制和监管合规从一开始就是强制要求。

因此，请带上一页纸的数据流说明：Agent 可以读取哪三张表（只读）、日志存放在哪里，以及提示词中是否包含客户数据。

让安全团队随意划掉任何他们不满意的内容。第一周提出的修改只需几个小时；同样的修改放到最后一周，可能会直接导致上线日期被搁置。

第三步：一起设计，一起写代码。 Simpliaxis 的指南列出了三个具体做法：让客户的工程师参与设计决策，在构建过程中与他们结对编程，并在工作中解释你的思路。ElevenLabs 描述其 FDE 与客户的技术团队并肩工作，直接在客户自己的基础设施内开展工作。

在库存示例中，这意味着在共享代码库中保存一份决策日志，外加每周两次结对编程会议，每次与四人团队中的不同成员配对。一条日志记录可以像这样简短：

D-03: Cache inventory query results for 15 minutes
Reason: avoid calling the ERP directly every time the agent answers
Rejected option: read the inventory table directly in real time
Decided with: [client engineer's name]
To change it, edit: the cache config file; the IT team can do this themselves

“与谁共同决定”这一行是最有价值的细节。它把你的决定变成了共同的决定，并告诉未来的读者，在你离开之后应该去问谁。

Simpliaxis 的指南解释了这为什么有效：与客户团队并肩构建的工程师在整个项目过程中持续交接，因此最终的移交工作量非常小。到了最后一周，已经不需要再进行为期三天的“交接培训”了。

什么样的措辞能让 IT 团队放心？

大多数戒备心理源于你的开场方式。你仍然可以提出你确切需要的东西；只是措辞要改变：

不要这样说应该这样说
“给我 ERP 的管理员权限，这样我能更快推进。”“我只需要这三张表的只读权限。有没有哪张你们希望排除在外？”
“这部分我来处理，你们不用操心。”“我们一起结对做这个吧，因为将来维护它的是你们的团队。”
“周五给领导层做演示。”“周四先和 IT 团队做一次试运行，周五由你们的团队共同演示。”
“安全问题可以留到后面的阶段。”“这是数据流图。能不能在我们开始构建之前让安全团队审阅一下？”

五个会把盟友变成阻碍者的错误

最常见的错误是，每当 IT 团队响应迟缓时，就越过他们直接去找高管支持者。你赢了一张工单，却失去了整个团队。第二个错误是索要超出实际需要的权限，这恰恰印证了安全团队的担忧。

第三个错误是向领导层演示却不邀请 IT 团队，结果他们只能从别人那里听说有一个系统正运行在他们自己的基础设施上。

第四个错误是写出只有你自己看得懂的代码：没有决策日志，没有运维手册，一切都装在你脑子里。第五个错误是把安全问题拖到最后，而这正是 CIO.com 和 ElevenLabs 都警告过要避免的。

这项技能在简历上如何体现？

阅读 FDE 职位描述时，留意诸如“与技术团队并肩工作”、“交接”或“赋能”之类的措辞。这些词出现的地方，说明该公司重视向客户交接，而不仅仅是构建。

面试时，准备一个你曾让一个心存戒备的团队参与工作的故事。要具体说明你在第一次会议上提出了什么请求、何时让安全团队介入，以及你和谁结对合作。

在简历上，写交接的成果：客户团队有多少名工程师、你离开后他们独立运行系统了多久，以及他们自己添加了哪些功能。

这些数字必须是你的真实数据。它们直接对应 FDE 交接指南所设定的目标：客户团队在没有你的情况下运行并扩展系统。

最终的检验很简单。在你背起行囊离开之后，系统仍在运行，而维护它的人正是第一次会议上抱着双臂坐在那里的 IT 负责人。
