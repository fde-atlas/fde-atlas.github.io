消灭“纸割”渠道，构建 FDE 到产品的闭环

原标题：Kill the Paper-Cut Channel as the FDE to Product Loop

Falkster.AI · 2026-11-04 · 约 9 分钟读完

摘要

作者批评 Salesforce Agentforce 负责人 Jayesh Govindarajan 提出的六步 AI 原生产品组织方法中的第五步：让 FDE 把现场反馈发到一个 Slack 频道。作者认为频道只是收件箱，缺少数量、期限和书面决定，无法衡量闭环。文章提出以“交接包”替代，包含配置差异、评测数据、被弃用功能和同类客户数量，在三个时间点交付，产品团队须在两周内由具名负责人给出书面决定，并用泛化率作为衡量指标。

要点

  • Govindarajan 领导约 700 人的 Agentforce 团队，提出六步法构建 AI 原生产品组织。
  • 第五步用 Slack 频道收集 FDE 反馈，作者认为这只是收件箱而非闭环。
  • Slack 数据显示 50% 消息来自应用和 Agent，每周 MCP 调用达 1.27 亿次。
  • 替代方案是交接包：配置差异、评测行、弃用项和客户数量，三个时间点交付。
  • 衡量指标为泛化率：两周内书面决定的比例与三客户模式落地的比例。

Aakash Gupta 对 Jayesh Govindarajan 的访谈，是目前对 Salesforce 这种规模公司的 AI 原生产品组织最详尽的公开描述，而其中六个步骤之一就是一个伪装成闭环的收件箱。这是针对“纸割渠道”作为 FDE 到产品闭环的一篇 Kill List 条目。

简要版本

  • Govindarajan 领导着 Agentforce 背后约 700 人的组织，他向 Gupta 给出的六个步骤是：让团队自选工具、把 Slack 变成操作系统、在必须确定性的地方让 Agent 保持确定性、以评测为先、把反馈接入路线图，以及在全面推广之前先落地一个成功案例。
  • 第五步是关键：前沿部署工程师把一线反馈发布到一个 Slack 频道，并打上 paper cut（纸割问题）或 feature request（功能请求）标签，产品经理则将帖子与路线图匹配，并询问针对特定客户的修复是否应该成为通用功能。
  • 同一天，Salesforce 公布了 Slack 的数据：目前 50% 的 Slack 消息来自应用和 Agent，每周有 1.27 亿次 MCP 工具调用，且每季度翻倍。一个频道就是一个收件箱。它没有计数、没有日期、也没有回传的决策，因此无法产出那个能说明闭环是否有效的数字。
  • 替代方案是我在九月写下的回传包：Delta、评测行、反转情况以及计数，在第两周、上线时和第 60 天交付，产品方须在两周内由具名负责人给出书面决策，并附上通用版本必须通过的评测。
  • 这个指标是泛化率：两周内得到决策的回传包数量，以及已交付的三客户模式数量。把频道作为闭环杀掉。把它留作收件箱。

Govindarajan 所描述的内容

Gupta 的这篇文章在 Dreamforce 现场录制，从生命周期开篇。Govindarajan 的论点是：计划、构建、测试、发布、评审这套流程已不再适用于 AI 功能。新模型每隔几个月就发布一次，他的团队不断返工已构建的 Agent，往往还会简化它们，因为模型能做更多事情；而且 Agent 会漂移：一个以政策文档为依据的退款 Agent，在文档被改写得含糊不清而代码未变之后，开始发放过大的退款。取代旧流程的 ADLC 是一个闭环——观察、构建、测试、评估、部署——而从中得出的那句话正是我会挂在墙上的：在为构建做预算之前，先为评测和可观测性做预算。

然后是六个步骤。给团队选择工具的自由，因为高管不应替团队选定赢家；团队在没有强制命令的情况下从 Cursor 迁移到了 Claude Code。把 Slack 变成操作系统，配备公司机器人和用于客户反馈的 Slack Connect。在需要的地方让 Agent 保持确定性，因为不同 Agent 之间的管道数据不能有差异，由 Agent Script 指定哪些部分必须如此。以评测为先，使用领域专属的评测，并在信任 Agent 之前先做出评级决策。把反馈接入路线图。先落地一个成功案例，再全面推广。

第五步，用 Gupta 的话说：前沿部署工程师将现场反馈发布到一个 Slack 频道，并标记为“小痛点”或“功能请求”。产品经理将这些帖子与路线图进行匹配，并判断针对特定客户的修复是否应该成为通用功能。

同一天，Salesforce 的新闻室发布了《Slack 数据一览》。每周 1.27 亿次 MCP 工具调用，环比翻倍。每周有 190 万用户在 Slack 中与第三方 Agent 交互。Salesforce 内部有 69.4 万个活跃频道。而头条是：现在 50% 的 Slack 消息来自应用和 Agent。

频道就是收件箱

把这两件事放在一起看。企业软件领域最大的 Agent 厂商的反馈闭环是一个 Slack 频道，而到达 Slack 的内容中有一半现在是由非人类的东西写成的。“小痛点”频道将不仅由 FDE 填充，也会由 Agent 填充，而 Govindarajan 自己的主动式 Agent 也将是发帖者之一。

这对收件箱来说没问题。但它不是一个闭环，区别在于频道不承载的三样东西。

一个计数。关于某个客户小痛点的帖子并不会说明有多少其他客户也有同样的问题。从部署到产品的闭环：FDE 工作如何成为路线图基于一条规则：一次是轶事，两次是巧合，三次是规律。将帖子与路线图匹配的产品经理是在脑子里、跨越整个频道做这个计数，这意味着它实际上没有被做。

一个日期。被标记的帖子中没有任何内容说明产品何时欠一个答复。发帖的 FDE 回到客户那里只会说“我已经提了”。

一个回传的决策。将帖子与路线图匹配并不是决策。那是没有编辑产物的编辑工作。泛化为通用功能、保留为配置，还是砍掉——由一个具名的人做出——才是决策。帖子附近某个地方的路线图条目不是。

这个数据包

吸收痛点，产出产品：FDE 的回传是我在九月写下的，当时 Palantir 将 Fujitsu 任命为全球 FDE 合作伙伴，回传不再是一件可以在走廊里随口完成的事。它有四个部分。

Delta。客户实际运行的内容，与已交付产品相对照，用配置术语写就。不是“我们定制了接入流程”，而是那些不同的设置、提示词和规则。

评测行。客户那些在交付时失败、现在能通过的用例，以产品团队可以直接运行的行的形式呈现。这是 FDE 离开后仍然留存的部分，也是 Govindarajan 的评测优先步骤所需要、而他的频道并不承载的部分。

反转项。客户关闭、覆盖或悄悄停用的东西，以及 FDE 对原因的最佳猜测。

计数。据 FDE 所知，有多少其他客户存在同样的问题。正是这一行让“三客户规则”变得可执行。

它在三个固定时间点交付，而不是等有人想起来才做：两周后、上线时、第 60 天。同时它也带来一个反向的义务。产品团队须在两周内给出书面决定：泛化、保留为配置，或砍掉。决定须来自具名的人，并附上泛化版本必须通过的评测。

最后这一条正是 Govindarajan 那句最精彩的话该放的地方。在构建之前就为评测做预算，意味着评测随泛化决定一起流转，而不是在功能上线之后。数据包带着客户的原始数据进来，而决定则带着通用评测出去。

渠道无法产出的那个数字

FDE 计分卡：统计留下来的，而不是派出去的为这个职能给出了四个数字，其中衡量闭环的是泛化率：在两周内获得书面决定的移交数据包的比例，以及已上线的三客户模式的比例。它记在产品的计分卡上，而不是工程师的。

试着从渠道计算这个数字。没有可统计的数据包，没有会错过的两周时限，没有可查到的决定。渠道只能告诉你有多少帖子带了每个标签。它无法告诉你闭环是否完成，而这正是检验标准：如果这个载体无法产出该指标，它就是一个收件箱。

Kill List 条目就是把渠道当作闭环。收件箱保留在 Slack 里，带着它的两个标签，AI Agent 也可以在那里发帖。闭环是数据包、三个日期，以及写有具名负责人的决定。

在 产品领导力 一文中，核心论点是：如今的领导工作，是判断哪些协调角色已不再必要，并公开说出来。把渠道帖子对应到路线图上的 PM 是一个协调角色。而在带有统计数字的数据包上写决定的 PM 则是编辑，这才是会留下来的角色。

本周，如果你的 FDE 在渠道发帖：取最近的二十条帖子，为每一条写下有相同问题的客户数量、产品团队须答复的日期，以及决定。那些空白之处，就是你尚未拥有的闭环。

常见问题

Jayesh Govindarajan 提出的打造 AI 原生产品团队的六个步骤是什么？+

根据 Aakash Gupta 对 Dreamforce 访谈的报道：给团队选择工具的自由，而不是指定唯一工具；把 Slack 作为操作系统，包括用 Slack Connect 收集客户反馈；在必须确定性的地方让 Agent 保持确定性，用 Agent Script 标注哪些部分，因为不同 Agent 之间的管道数据不能有差异；以评测为先，在信任一个 Agent 之前先决定如何给它打分；把反馈接入路线图，由前沿部署工程师把一线反馈发布到一个 Slack 频道，并打上小问题或功能请求的标签，由产品经理将帖子与路线图对应起来；在全面推广之前先落地一个成功案例。其底层是 ADLC，一个持续的观察、构建、测试、评估、部署循环，取代线性的 SDLC。

这个反馈频道有什么问题？+

作为收件箱，它没问题。但作为循环，缺了三样东西。计数：频道里的一条帖子无法说明还有多少其他客户遇到同样的问题，因此“一个是轶事，三个是规律”的规则无法适用。日期：打了标签的帖子里没有任何信息说明产品何时必须给出答复。决策回传：把帖子与路线图对应起来并不是来自具名人士的书面决策，发帖的 FDE 无法告诉客户接下来会发生什么。Salesforce 同一天公布的 Slack 数据显示，现在 50% 的 Slack 消息来自应用和 Agent，所以这个频道会从两头不断涌入信息。

用什么来取代它？+

来自 Absorb Pain, Excrete Product 的交接回传包。包含四项内容：已交付产品与客户实际运行版本之间的差异，用配置术语表述；客户的评测行，即上线时失败、现在通过的用例；反转项，客户关闭或覆盖了什么以及原因；以及遇到相同问题的其他客户的数量。在三个时间点交付：两周后、上线时、第 60 天。产品必须在两周内给出书面决策——泛化、保留为配置，或砍掉——由具名人士做出，并附上泛化版本必须通过的评测。

如何衡量这个循环？+

泛化率，来自 The FDE Scorecard：在两周内获得书面决策的交接回传包的比例，以及已交付的“三客户规律”的比例。这两项指标都应记在职能部门的记分卡和产品部门的记分卡上，而不是个人工程师的记分卡上。一个只有两个标签的频道无法产出这两个数字中的任何一个，这正是判断某事物是循环还是收件箱的检验标准。

在构建之前为评测预留的预算应该放在哪里？+

放在决策里。Govindarajan 的观点是，AI 功能的维护成本很高，所以在为构建做预算之前，先为评测和可观测性做预算。交接回传包把客户的评测行带进来，泛化决策则把泛化版本必须通过的评测带出去。评测随决策一起流转，而不是在功能上线后才补写。
