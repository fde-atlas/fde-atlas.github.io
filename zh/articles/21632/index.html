摘要

日本公司DeFactory推出“安全FDE”服务，不卖扫描工具，而是派前沿部署工程师进入客户团队，把诊断报告和扫描结果中堆积的安全问题推进到实际修复。服务覆盖漏洞分诊、依赖更新、供应链防护（SBOM、锁文件固定）、生成AI治理等三领域，流程示例为从3,000条扫描检出筛至50条、提交30个带测试的修复PR。AI起草修复但必须经人工审核，最终批准权在客户。入口试用约2至4周，也接受单次委托。

要点

  • 不卖工具，基于客户现有扫描与诊断结果开展修复。
  • 示例流程：3,000条检出筛至50条，产出30个带测试的修复PR。
  • 覆盖漏洞、供应链、生成AI三领域，含SBOM与AI资产台账。
  • AI起草修复，人工审核，客户保留最终批准权。
  • 入口试用2至4周，可单次委托，按范围报价。

VALUE

我们融入贵公司的团队，承接那些往往在“发现之后”就停滞的工作。提供的价值有以下 6 项。

判断 | | | | |

诊断公司的报告书、多个扫描器的结果、AI 诊断的问题点被汇总为统一的优先级，“本月修复的项目”与“不修复的理由”一应俱全。

  • 将不同来源的问题点整合为一份清单
  • 按利用实绩、是否外部公开、资产重要度、相关代码是否实际被使用（可达性）进行筛选
  • 无法立即修复的项目，附带理由与期限进行记录

修复 | | | | |

修复工作在附带测试与影响确认的情况下推进。“一修就坏”的顾虑减少，停滞的响应重新运转起来。

  • AI 生成的草稿由人工确认后实现
  • 补充回归测试
  • 整理影响范围并准备回滚步骤

上线

从评审请求、变更申请到发布窗口的调整，全程并行推进。上线的判断与审批由贵公司进行。

  • 整理为便于评审的形式
  • 准备变更申请
  • 协调发布计划

持续验证 | | | | |

通过修复后的复验与在入口处拦截同类问题的机制，保持修复后的状态。

  • 重新扫描与回归确认
  • 集成到 CI/CD
  • 通过向公共组件集中，实现同类问题的一并处理

说明

响应记录与 SBOM 一应俱全，面对交易伙伴的检查表和审计的问询，能够以事实作答。

  • 整理响应记录
  • SBOM 的制作与提交应对
  • 构建检查表回答的依据

生成式 AI | | | | |

从诊断到后续实现，完善安全使用生成式 AI 的基础架构与规则。

  • 内部 RAG 的权限控制与封闭网络的内部 AI 基础架构
  • 使用日志的审计与 AI 资产台账
  • 使用策略与审批流程

WHY DEFACTORY

不止步于检测，而是负责到修复与运维的 实现支持服务。

HOW WE WORK

漏洞・攻击面管理与应用/供应链按以下流程推进。

STEP 1

发现 | | | | |

接收现有的扫描结果和诊断报告书，统一格式并汇总为清单。

STEP 2

筛选

根据被利用的实绩、是否对外公开、资产的重要程度，选出优先修复的项目。

STEP 3

修复 | | | | |

通过 Pull Request 提交修复方案和测试。审查与批准由贵公司的团队进行。

STEP 4

循环

即使出现新的问题点，也能留下以同样流程应对的机制和运营方式。

SAFETY

源代码和诊断结果属于机密信息。在开始工作之前，会通过合同明确信息的处理范围。

运营方针

访问权限仅限于工作所需的最小范围。

保留工作记录（日志），并以贵公司可确认的形式保存。

使用 LLM 处理代码或诊断结果时，会事先征得贵公司的同意。使用不用于训练的服务，必要时在封闭网络环境中进行。

AI 生成的修复内容，必定由人工进行审查。

在签订合同之前，就保密、责任范围和验收条件达成一致。

关于服务范围

修复时会在交付成果中附上复检结果。但不保证能防范所有攻击。
