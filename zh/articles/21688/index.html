OpenAI FDE 面试：家庭作业、评审、AI 编程

原标题：OpenAI FDE Interview: Take-Home, Review, AI Coding

FDE Times · 2026-10-21 · 约 7 分钟读完

摘要

本文梳理 OpenAI 前沿部署工程师招聘中的家庭作业环节：候选人需为 Amazon 商品数据构建语义搜索系统。各来源对时长说法不一（约五小时或一周），建议像对待客户需求一样与招聘方确认范围。评分侧重能否解释设计决策并关联客户需求，而非技术炫技。编程环节允许使用 AI 工具，关键是边写边讲出思路。作者建议维护决策日志、自建评测集，并把项目当作交付给客户的产品来完成。

要点

  • 家庭作业时长来源说法不一：约五小时或一周，应与招聘方确认。
  • 评分看重解释设计决策并关联客户需求，无法讲清作品者不通过。
  • 应从用户查询出发设计，价格等硬约束用元数据过滤而非向量。
  • 编程环节允许用 AI，需共享屏幕并边写边讲思路。
  • 决策日志和评测集既是面试准备，也是可写进简历的作品集。

简要概述

  • 关于带回家作业的时长，各方说法不一：一位候选人和 Aced 的指南说大约一周，而 Aced 的概览、Gaijineer 和 The Forward Deployed 则说大约五小时。
  • Aced 描述了一个 60 分钟的环节：你先解释自己的设计选择，然后回答关于 RAG、微调与提示词对比、防护栏和评测的问题。
  • 编程环节允许使用 AI。Aced 的指南建议你共享屏幕，并在操作过程中边做边讲解你的思路。

你打开招聘人员的邮件，读到任务简报：基于 Amazon 商品数据构建一个供 ChatGPT 使用的语义搜索系统。一位 OpenAI FDE 候选人在 Aced 上讲述，他收到的正是这个任务，并有一周时间构建一个真正能运行的系统。

这只是一个人的经历，并非标准任务简报，而且描述这一流程的各方说法也不完全一致。但 Aced 的指南（Aced 前身为 Exponent）强调了一个值得记住的要点：把带回家作业当作交付给真实客户的产品来对待。

任务简报是一份小合同，而不是一场考试

首先要弄清楚的是时间限制，因为各方说法不一。Aced 的指南说你有一周时间提交可运行的代码、一个正在运行的应用和一个视频演示。Gaijineer 和 The Forward Deployed 则描述了一个大约五小时的带回家作业，要求基于 OpenAI 的 API 构建真实的东西，并附上视频。

甚至 Aced 自己也给出了两个数字：其 FDE 面试概览（即下文所述 60 分钟评审环节的来源）说带回家作业大约五小时，而其 OpenAI 专属指南则说大约一周。流程可能已经改变，或者不同团队的执行方式不同，所以不要把任何一个数字当作定论。

因此，务实的建议是：像与客户商定范围一样，向招聘人员问清楚截止日期和需要提交的内容。Final Round AI 描述说，视频演示就像你在向客户介绍这个应用一样。

评分标准比任何技术技巧都重要。收到 Amazon 任务的那位候选人表示，评分更看重解释决策过程，并将其与客户需求联系起来。

Final Round AI 说得更直白：无法清楚解释自己做了什么的工程师无法进入下一轮。一个令人印象深刻的检索技巧，救不了一份评审者无法运行或看不懂的提交作品。

从用户输入的内容出发，而不是从架构图出发

Perspective AI 建议从客户的待完成任务出发，而不是从参考架构出发。假设你收到了 Amazon 的题目。不要立刻打开 notebook，而是先写下 ChatGPT 用户可能输入的三条查询：“100 美元以下适合经常坐飞机的人的降噪耳机”、“送给喜欢恐龙的 5 岁孩子的礼物”、“不会变黄的 iPhone 15 手机壳”。

这三条查询立刻揭示了两种信号。语义部分（“经常坐飞机的人”、“喜欢恐龙”）适合用 embeddings。硬性约束（“100 美元以下”、“iPhone 15”）则应该通过元数据过滤来处理，因为 embeddings 不擅长比较数字，而这正是你之后需要解释的那类决策。

接下来是如何表示一个商品。一条记录通常包含标题、品牌、类目、几行功能要点，可能还有评论。最简单且仍然站得住脚的方案是每个商品对应一段短文本，同时把价格和类目保留为过滤字段：

def product_to_text(p):
    # One document per product; price stays structured for filtering
    lines = [p["title"], f"Brand: {p['brand']}", f"Category: {p['category']}"]
    lines += p.get("bullets", [])[:5]
    return "\n".join(lines)

def search(query, max_price=None, k=5):
    q_vec = embed(query)
    candidates = [p for p in products if max_price is None or p["price"] <= max_price]
    return top_k_by_cosine(q_vec, candidates, k)

这就是分块策略发挥作用的地方。如果你把长描述拆成多个 chunk，就必须把结果合并回商品层级。不做合并的话，同一个商品可能占据前五名中的三个位置。

加入评论会带来日常语言，比如“整个航班戴着耳朵也不疼”，但也会带来噪音。两种选择都可以，只要你能说出理由。

最后，进行度量。假设你自己写了 30 条查询，并提前标注了每条查询中哪些商品算正确。如果 21 条查询的前五名中至少有一个正确商品，那么 hit@5 就是 70%，这可以成为评审时很好的开场白：“第一版达到了 70%。加入价格过滤后提升到了多少，以及为什么。”

决策日志就是你带到评审会上的东西

Aced 描述了一场 60 分钟的面试，结合了展示你的工作和深入的技术追问。你要解释自己的设计选择，然后回答关于 RAG、微调与提示之间的权衡，以及防护栏和评测的后续问题。

Aced 的指南还补充说，面试官会检查你的设计是否从客户真正的需求出发。

据 Aced 所说，这一环节的常见问题是：你为什么选择这个方案，又在哪里决定不走另一条路？最好的准备是一份决策日志，记录每个技术选择源自哪项用户需求。模板大致如下：

决策被否决的方案以用户需求表述的理由何时更改
每个商品一份文档把描述拆成多个 chunk用户需要的是不同商品的列表，而不是文本片段当长描述稀释了 embedding 时
价格作为硬性过滤把价格放进被嵌入的文本中“100 美元以下”是约束条件，不是提示几乎从不
暂无评价将评价追加到文档中第一版保持简单；先衡量再添加当评测显示对日常语言查询有遗漏时

最后一列最有价值。当被问及“如果客户有一千万个产品怎么办？”时，你不必临场发挥，因为你已经写下了会改变你想法的条件。为 Aced 列出的主题添加几行，例如为什么你目前还不需要微调，以及哪个护栏会拦截价格错误的结果。

AI 辅助编程环节：考察的是你如何使用工具

收到 Amazon 题目的那位候选人只是简单提到连编程初筛都启用了 AI，并未详细描述规则。Aced 的指南则更加明确：允许使用 AI 工具，因此请共享屏幕，并在操作过程中讲述你的推理过程。

当每位候选人都拥有相同的工具时，面试官唯一能观察到的就是你如何思考。边做边说出想法可能是这样的：

“在让 AI 写任何东西之前，先确定一件事：输入可以是空数组吗？现在我会让它给出第一个版本……这一行用了 sort，所以是 n log n，对这道题来说可以接受。我会添加一个针对重复元素的测试，因为这是容易遗漏的情况。”

这里的建议是让面试官看到你仔细阅读 AI 生成的代码、编写自己的测试，并在运行之前发现 bug。粘贴输出然后沉默等待，浪费了展示你思考方式的机会。

会让原本不错的提交翻车的错误

一个常见的错误是优化错了方向：花三天时间做一个精巧的重排序器，却没有 README、没有一行运行命令、没有评测集。如果你按照 Aced 的建议，把它当作交付给客户的产品来对待，那么这个提交还不如一个带测试和衡量的简单系统。

另一个错误是视频演示一开场就放架构图。应该以用户的查询开场，展示结果，然后再解释底层实现。永远不要用“因为教程是这么做的”来回答“为什么”的问题；决策日志的存在就是为了让你永远不必说出这句话。

即使你从不在 OpenAI 面试，这些准备也不会白费。一个带评测、决策日志和五分钟视频的搜索项目，是适合任何 FDE 职位的作品集作品。

在简历上，把它写成一行，包含一个数字和一个假设客户，例如“对 200 个产品进行语义搜索，通过价格过滤器将 hit@5 从 70% 提升到 X%”，而不是仅仅罗列“RAG、嵌入”。

本周的练习：用大约五个小时重做 Amazon 题目，即 Gaijineer、The Forward Deployed 和 Aced 的概述中所描述的基准，而不是那位候选人被给的一周时间。然后请一位朋友扮演客户，向你提问整整 60 分钟，把你无法直接回答的任何问题直接写进“何时改变”那一列。
