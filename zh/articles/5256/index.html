Cursor 的前沿部署工程

原标题：Forward Deployed Engineering at Cursor

AI Engineer · 2026-02-12 · 约 11 分钟读完

摘要

Cursor 全球前沿部署工程负责人 Pauline Brunet 在 AI Engineer World's Fair 2026 分享如何搭建 FDE 职能。她用客户数字化成熟度与产品定制化两个维度决定是否需要 FDE，避免把 FDE 变成人员外包。项目须有高管支持、客户自有团队参与，并以可衡量的业务结果为目标，如把流程从三小时压缩到二十分钟。交付后客户应能持续使用成果，FDE 还要把客户反馈带回产品路线图。团队先招五年以上经验的全能型工程师，再逐步按行业与产品专长细分，并借助合作伙伴扩大交付规模。

要点

  • 用客户成熟度和产品定制化两个维度判断是否需要 FDE。
  • 项目需高管支持、客户团队参与，拒绝纯补人头的需求。
  • 以可衡量的结果为准，如流程从三小时缩到二十分钟。
  • 交付标准是客户在团队离开后仍继续使用成果。
  • 先招资深通才，再按行业和产品专长逐步细分团队。

客户什么时候需要 FDE？

客户应该获得文档、一支常规部署团队，还是一名嵌入其组织内部的工程师？这一决策正是 前沿部署工程（FDE） 职能设计背后的核心问题。Pauline Brunet 在 Cursor 全球范围内领导这一职能，她在咨询行业和三家科技公司积累了十年的企业 AI 部署经验。Cursor 的产品方向——从自主编程，到异步与同步 AI Agent，再到 AI 软件工厂——为她正在打造的团队提供了背景。

先从客户的转型历程入手，再审视你要求他们采用的产品。Brunet 使用两个维度：客户数字化成熟度 和 产品定制化程度。客户是否拥有工程师以及实施变更的技术能力？产品是在收到登录凭证后几乎立即可用，就像她举例的 Teams 那样，还是需要大量的配置和开发？这些问题比把 FDE 当作专业服务或人员外包的另一种说法更有价值。

客户成熟度产品定制化程度合作模式
高低自助服务与文档
低低传统 SaaS 部署
高高顾问与加速
低高嵌入式转型

技术成熟的客户使用简单的产品时，基本可以凭借优质的文档实现自助服务。成熟度较低的客户采用同类产品时，可能需要一次常规的、按部就班的推广。这两种情况都不必然需要稀缺的 FDE 资源。面对高度可定制的产品，成熟的客户可以自己完成大量工作，但会从建议和加速中受益。处于转型早期阶段的客户可能需要一支嵌入式团队，因为他们尚无法招聘或配备所需的专业人才。

Brunet 矩阵中的蓝色 FDE 区域强调了更深入的工程参与能够发挥作用的场景。即使是使用相对简单产品的成熟客户，也可能从功能扩展中受益，而这类工作还能为产品工程团队建立一条有价值的反馈回路。但在这种情况下，FDE 产生影响力的机会，要小于那些需要大量转型的合作项目。

对于拥有可定制产品的成熟客户，要记住他们自己已经能做多少事情。Brunet 不希望 FDE 的工作退化为解决方案架构、记录 bug 或更新文档。同样，一次传统的部署可能只需要一个配置扩展，而不需要 FDE 团队为整个公司开展产品入门和进阶培训。在招聘之前先界定有实质意义的工作。 招募并高薪聘请顶尖工程师，却只分配例行工作，会导致倦怠和流失；实际交付的角色不再与当初推销的角色相符。

跨组织层级的工程工作

Brunet 所招募的 FDE 创始成员画像，兼具深厚的技术能力和高情商。同一位工程师可能先与 CIO、CTO 或 COO 合作，然后与开发者、工程经理以及负责转型或 AI 的领导者共事。他们必须迅速发现一个有价值的问题，理解现有流程，并找出技术可以如何改进它。这种发现还包括组织文化：谁能推动变革落地，人们又将如何接受它？

安装先进的技术并不能保证有人会使用它。FDE 必须陪伴人们度过变革过程，同时保持技术上的可信度。由于新版本每周都在发布，好奇心和持续学习是这份工作的一部分：客户期望面前的工程师了解现在有哪些新的可能。

让工程师嵌入客户现场，也让供应商得以异常直接地了解客户需求。反复出现的请求成为产品和工程团队下一步应该构建什么的依据。FDE 必须在客户和内部团队之间谨慎地传递这些反馈，把反复出现的摩擦转化为产品方向，而不只是收集零散的请求。

构建客户会持续运行的东西

Cursor 的客户包括拥有深度技术型买家和用户的成熟组织，这同时塑造了它的招聘方式和项目模式。Brunet 会寻找一位经济决策人或高层支持者，能够将拟议的工作与公司的战略目标联系起来。项目需要具备实质性的业务价值、客户指派的人员、可以访问将要进行开发的系统和代码库，以及自上而下对改变工作方式的支持。高层支持之所以重要，是因为它为交付创造了条件，而不仅仅是让项目获得曝光。

Brunet 介绍了基于 Cursor SDK 构建的云 Agent、长时间运行的 Agent、自动化和应用的实际部署案例。退出标准很务实：成果必须创造足够的价值，让客户在 FDE 团队离开后仍继续使用。如果在合作结束时部署就被关停，那就没有实现团队所追求的持久变革。

团队还在测试 Cursor 能否在软件开发生命周期之外发挥作用。Brunet 描述了与人力资源、财务、供应链和电商团队的合作，包括探索资产管理业务的零售商和银行。这些合作让 FDE 得以与客户一起探索平台的边界，并发现其能力能否改善公司其他领域的工作。

询问谁将与你们并肩协作

共同开发需要客户团队。 Cursor 的 FDE 在客户的代码库中工作，但这并不意味着他们是替代人员。在 Brunet 看来，主要因人手不足而提出的请求是一个警示信号。客户应当认为该项目足够重要，值得投入自己的人员。

她的筛选问题很直接：“谁将是工作团队？”假设提议的用例是自动化呼叫中心工单系统的长时间运行 Agent。在同意构建之前，先确定将参与协作的人员。这个问题把关于自动化的热烈讨论转化为对客户承诺的具体检验。这种关系也是双向的：FDE 会影响产品路线图，然后随着原本无法实现的用例变得可行，把新能力带回给客户。

明确的使命让这些边界更容易维持。Cursor 的使命是与客户合作，共同设计和构建他们的 AI 软件工厂，变革他们在整个生命周期中设计、开发和维护软件的方式。它告诉客户这次合作要达成什么目标，也让工程师能够评估任务。当某个项目听起来像人员外包时，团队可以追问它是否推进了这一使命。

从经验丰富的通才入手，再走向专业化

在演讲时，Cursor 创始 FDE 招聘要求五年以上软件工程经验，并具备面向客户的经验。Brunet 初期招聘的是能够兼顾该角色两方面的人才，而不是毕业生或初级工程师。她预计随着团队壮大，这一情况会改变。最终的分工可能包括客户工作能力更强但仍具备技术素养的人，以及技术深厚且有潜力学习客户工作的工程师。这些是团队演进的规划，而非对现有分工的描述。

Cursor 采用矩阵式组织，初期按地域划分。Brunet 预计行业专业化会变得更加重要：与银行对话的工程师需要理解支付系统和资产管理风险。行业语言是建立可信度的一部分，因为它表明对客户实际工作的理解。

产品专长提供了另一个维度。团队中有长期运行的云端 AI Agent 和 Cursor SDK 方面的专家，同事可以将他们引入项目。Brunet 提到她的团队成员来自 Spotify、Rippling 和 Palantir 等组织，同时强调他们与客户合作的热情和能力。团队结构保持刻意灵活：随着产品变化和客户转型的推进，团队的角色和招聘画像也应随之改变。

让客户学习改变产品供给

Brunet 的建议是尝试一个真实的客户项目，快速学习，并随时调整——即使项目失败。冗长的规划无法替代发现客户真正需要什么。她举了自己产品供给中的一个例子：客户反复询问在采用强大的 AI 工具后如何重组组织。他们希望在招聘画像、职位描述、团队结构、协作和流程方面获得帮助，以便充分获取这些工具的价值。她原本无意提供这类工作，但正在考虑，并会招聘合适的团队来支持它。

合作伙伴可以扩展交付能力，而无需 FDE 团队事事亲力亲为：

  • 客户知识： 系统集成商和咨询顾问通常拥有长期合作关系，并且已经了解该组织。
  • 互补能力： Brunet 认为变革管理是她更希望由合作伙伴协助交付的工作。
  • 可复制的推广： 一旦成熟产品被反复部署，合作伙伴就可以扩大其覆盖范围。她提到了在电信、医疗保健和生命科学领域的推广经验。

这种分工在使大规模部署成为可能的同时，也为 FDE 工作保留了空间。

同样的纪律也适用于拒绝工作。当 Cursor 不是合适的工具时，Brunet 建议直接说出来。诚实的边界能建立可信度，并可能促使客户日后带来更契合的使用场景。接受不合适的工作，一旦进展不佳，团队也要承担责任。服务内容、招聘画像、薪酬和任务分配应当相互匹配，这样招募来交付服务的人才才能保持积极性。

固定结果，让实现范围保持方向性

一次合作始于确认所陈述的问题就是真正的问题。一个请求可能描述的是症状，或者来自并不负责该流程的人。要问清谁负责，并与那个人沟通。Brunet 希望在决定解决什么之前，先接触到工作流、流程或部门的负责人。

接下来，就成功标准达成一致。Brunet 举例的目标是将一个端到端流程从三小时的基线缩短到二十分钟，前提是客户同意这算作成功。这是一个提议的结果，而非已报告的部署成果。她将基于问题的承诺与开放式地分配两名 FDE 六个月进行对比：在她看来，只提供人员而不定义他们应完成什么，是失败的配方。

将预期结果转化为方向性的实现范围：

  • 指明要自动化的流程。 定义应当从头到尾运行的工作。
  • 描述 Agent 的输入和决策。 明确它将获取哪些数据、做出哪些决策。
  • 确定人的参与。 明确谁应属于反馈回路。
  • 将工作流与一个 KPI 关联。 例如平均解决时间，或答复客户保险理赔所需的时间。

这为项目赋予了技术形态，而不必假装已经完全理解客户系统的每个细节。

Brunet 用一个为期六周的合作来说明方向性范围：涵盖初始阶段、选定的自动化和 Agent 搭建，同时让可完成的工作量保持灵活。原因在于对客户流程、数据和系统的不确定性。实施过程中的学习可能揭示出比预期更多的工作，或一个更好的方向。客户在看到可能性后也可能想要转向，因此范围应能容纳这种学习，同时仍与预期结果挂钩。

客户参与必须贯穿范围界定、方案设计、构建、实施、人在回路的验证、与基线的对比以及 ROI 识别的全过程。成果由客户拥有；FDE 始终保持亲力亲为。 工程师仍然要配置系统并在客户的代码库中开发，但不应该独自完成。Brunet 警示的画面是：一名 FDE 被孤立在客户办公室的小隔间里。最后，回到约定的流程时长目标，并询问实际工作是否接近该目标。

衡量价值，而不只是 Agent 的账单

如果交付未达到目标，要调查原因并决定可以改变什么。然后清晰地传达投资回报。Brunet 讲述了一个例子：一个据称每天成本为 2,000 美元的 Agent，其工作帮助派遣了合适的人去维修设备。她的回应是询问设备派遣成本的降低是否足以证明这笔支出的合理性。与她交谈的人同意可以，但从未以这种方式衡量过收益；这个轶事没有提供量化的节省金额或净 ROI。

Brunet 将业务价值分为三类：

  • 增加收入： 帮助企业赚取更多。
  • 降低成本： 减少交付成果的开支。
  • 降低风险： 减少暴露于不利结果的可能性。

一个项目应至少支持其中之一，也可能同时支持多项。Agent 的运营成本只有相对于它所改变的业务成果才有意义。

留下成果物和做好工作的空间

项目还需要交接：留下文档成果物，帮助客户在团队离开后继续推进。在组织层面，构建适合公司的 FDE 职能，然后学习、调整并扩展它。这需要一种人们愿意参与、持续学习并有机会做出最佳工作的文化。

Brunet 以招聘格言“A 级人才雇用 A 级人才，B 级人才雇用 C 级人才”作结。她的重点在于团队成长过程中保持质量和匹配度：为组织及其客户招聘，并用值得做的工作让这些人保持动力。
