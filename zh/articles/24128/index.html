Palantir Workshop 是什么？详解其功能与 FDE 实务中的应用

原标题：Palantir Workshopとは？機能とFDE実務での使い方を解説

FDE総研 · 2026-10-27 · 约 12 分钟读完

摘要

这篇文章介绍 Palantir Foundry 中的 Workshop：一个基于本体（Ontology）、以低代码方式搭建业务应用的工具，面向一线人员的日常判断与操作，而非单纯的数据看板。文章拆解了其五大构成要素（组件、变量、事件、Actions、Functions），说明写入与业务规则由本体侧的 Action 型统一管控，并对比了 Workshop、Slate、Quiver 三种界面工具的适用场景。对 FDE 而言，Workshop 适合在数日内把业务访谈成果变成可运行界面，与现场反复迭代；文章还提醒变量命名、模块拆分、权限与性能等易积累的技术债，并强调真正被评价的是把业务分解为对象与操作的设计能力，而非工具操作速度。

要点

  • Workshop 基于本体对象搭建低代码业务应用，可读可写，区别于 BI 看板。
  • 界面由组件、变量、事件组成，写入靠 Actions，复杂计算靠 Functions。
  • 业务规则（权限、校验）应在本体与 Action 型层面集中控制，而非应用侧。
  • 与 Slate（自由定制）、Quiver（分析）相比，业务操作类界面首选 Workshop。
  • FDE 应先做最小本体与只读界面，快速试用迭代，最后再引入写入功能。

什么是 Palantir Workshop？

Palantir Workshop 是一款以 Palantir Foundry 的本体（Ontology）为基础、用低代码方式搭建业务应用的工具。它并非用于数据分析仪表盘，而是用于构建现场人员日常进行判断和操作的“业务界面”。

Palantir 的官方文档也将 Workshop 介绍为构建面向运营的应用时的核心工具。可以认为，当 FDE（前沿部署工程师）进入客户现场、需要在短时间内展示可运行的成果时，Workshop 往往是首选。

以本体为起点的应用构建工具

Workshop 的特点在于处理的是本体上的“对象”，而非数据表。界面以这些对象为单位进行设计。

Foundry 的本体是将数据集转换为“工厂”“设备”“订单”“客户”等业务概念（对象类型）及其之间的链接。Workshop 的组件直接读写这些对象。因此，应用开发者无需每次都编写 SQL 或 API 连接。

反过来说，如果本体设计粗糙，Workshop 应用的易用性也无法提升。决定 Workshop 质量的因素中，一半以上在于本体侧的设计。

谁在什么场景下使用？

用 Workshop 构建的，是供现场人员“查看、判断、操作”的业务应用。构建者包括 FDE、客户方的数据负责人以及业务部门的高级用户。

典型用途如下：

用途示例界面上进行的操作主要使用者
告警与异常处理将存在异常的对象列成清单，分配负责人并更新处理状态运营人员
计划与分配比较库存、人员、设备的分配方案，确定计划计划人员、管理层
案件与案例管理在每条案件的详情界面确认经过并变更状态审核、调查人员
面向经营层的状况把握通过指标卡片、地图和图表查看整体情况，并深入到具体案件决策者

所有用途的共同点是：不仅“查看”，还包括“写入（记录决策）”的操作都能在一个界面内完成。这正是与 BI 工具最大的区别。

Workshop 的主要功能与机制是什么？

Workshop 采用这样的职责分工：用组件、变量和事件搭建界面，用 Actions 进行写入，用 Functions 进行计算。

只要把握这 5 个要素之间的关系，就基本能读懂 Workshop 的应用。

构成要素职责实务中的理解
组件表格、图表、地图、筛选器、按钮等界面部件“目标设备清单”“地图”“按状态统计的数量”
变量保存对象集合、选中值、字符串和数值等状态“清单中选中的设备”“筛选后的订单集合”
事件以点击等为触发更新变量，打开界面跳转或覆盖层“选中某行后打开详情面板”
Actions创建、编辑、删除本体中的对象“分配负责人”“将状态改为已完成”
Functions用 TypeScript 或 Python 编写汇总、派生值和复杂逻辑“计算优先级评分并排序”

组件、变量、事件三要素

Workshop 界面的运行方式是：组件读写变量，事件切换变量与界面状态。

例如，将筛选组件过滤后的结果放入对象集变量，再将该变量同时传递给表格和地图，两个组件就会联动。在表格中选中一行时，“当前选中对象”变量会更新，右侧详情面板随之切换内容。能否设计好这种“变量的流动”，是 Workshop 开发的基本技能。

布局通过组合区块、标签页、页面以及抽屉、模态框等覆盖层来构建。由于大部分逻辑无需编写代码、可在配置界面中搭建，因此可以与业务人员一起查看界面并当场进行修改。

用 Actions 和 Functions 承担写入与计算

能否成为合格的业务应用，取决于 Actions 的写入能力和 Functions 的逻辑嵌入。

Actions 以本体的 Action 类型来定义。Workshop 的按钮和表单调用这些 Action 来更新对象。Action 类型可以设置执行条件（提交条件）和参数校验。因此，“只有有权限的负责人才能审批”“必填项为空则无法提交”等业务规则，可以在本体侧统一保障，而非依赖界面。

Functions 用于创建仅靠标准组件配置难以实现的汇总和派生指标。根据现场经验，一开始就过度依赖 Functions 会导致维护人员受限。更稳妥的做法是先用标准功能搭建到能搭的程度，只在确实必要的地方使用代码。

与 AIP 的联动

近年的 Workshop 也被用作将 Palantir AIP 的功能嵌入业务界面的场所。

通过 Functions 或 Actions 调用用 AIP Logic 构建的基于 LLM 的逻辑，或在界面上放置 Agent 式的助手，这类架构在官方文档和演示中都有介绍。这里重要的是，不要直接确定生成式 AI 的输出，而是设计成由人通过 Action 进行审批的流程。“AI 提议，人来决策”的业务设计是 FDE 所必需的。另外，AIP 相关功能更新频率较高，可用范围请以引入时点的官方文档为准。

Workshop 与 Slate、Quiver 有什么区别？

Workshop 是基于本体的业务应用，Slate 是自由度很高的定制应用，Quiver 则适合分析与仪表盘。

由于它们都是能在 Foundry 中创建“界面”的工具，初次接触的人容易混淆。下面用表格总结设计理念上的差异。

三种工具的对比表

差异可以从“谁、为了什么目的使用界面”和“做到多深的定制程度”这两点来整理。

视角WorkshopSlateQuiver
主要目的面向运营的业务应用精细定制的定制应用对象和时序数据的分析与仪表盘
数据处理以本体的对象为中心灵活组合查询和 API 调用从分析视角处理对象和时序数据
开发方式低代码（以配置为主＋按需使用 Functions）偏代码，包含 HTML/CSS/JavaScript偏无代码，组合分析卡片
写入（Writeback）通过 Actions 标准支持可以支持，但设计自由度高，相应也更费工夫以分析为主要目的，写入不是主要用途
外观定制在标准组件范围内保持统一感可按像素级调整面向分析的标准展示
易维护性容易移交给客户方容易依赖开发者的技能分析负责人自己就能轻松更新

选用的判断标准

一般来说，拿不准时应优先考虑 Workshop，只有在明确 Workshop 无法满足需求时才选择 Slate。

实际工作中的判断顺序如下。

  • 是否是现场负责人日常操作、记录判断的界面 → 如果是，选 Workshop
  • 是否以时序数据的深入分析或探索指标间关系的分析为主要目的 → 如果是，选 Quiver（也可考虑嵌入 Workshop）
  • 是否像对外门户一样，必须要定制设计或特殊操作 → 考虑 Slate
  • 选择 Slate 时，需确认接手方是否有能维护前端的人员

从 FDE 的视角来看，尤其要重视第四点。FDE 迟早会离开现场。客户能否持续自行改进，在工具选型阶段就基本决定了。

FDE 在实际工作中如何使用 Workshop？

FDE 将 Workshop 作为一种工具，把业务访谈的结果在几天内变成可运行的界面，并与现场一起反复重构。

Palantir 式 FDE 的价值不在于堆砌需求规格说明书，而在于在客户现场使用“可运行的东西”来收窄问题。Workshop 的低代码特性与这种推进方式非常契合。

从访谈到正式运营的流程

典型的推进方式是：先构建本体的最小配置，再创建界面并在现场试用，最后通过 Actions 将业务嵌入，按此顺序进行。

步骤FDE 所做的工作交付物
1. 业务观察观察负责人目前在哪个界面、报表上做什么判断判断要点清单
2. 本体的最小设计只定义判断所需的对象类型和链接最小限度的对象模型
3. 只读界面用列表、详情、筛选创建“能看到当前状况”的界面第一个 Workshop 模块
4. 现场试用让负责人在实际业务中使用，删掉没人用的界面改进点清单
5. 嵌入写入功能将分配、审批、状态更新做成 Actions业务可闭环的应用
6. 移交将变量的配置和命名规则文档化，交由客户方负责人负责后续改进运营文档

重要的是以较短的周期反复进行步骤 3 和 4。如果一开始就把写入功能都做进去，当业务流程发生变化时，需要重做的范围会很大。

在现场需要注意的要点

Workshop 虽然能快速构建，但也容易积累设计上的技术债。变量的命名、模块的拆分、权限的设计，最好在最初就确定下来，这样更安全。

从现场实务人员的经验来看，以下几点容易在日后成为问题。

  • 变量过多：每增加一个界面就创建变量，会让人无法追踪哪个变量与什么联动。应在一开始就确定易于理解用途的命名规则。
  • 单个模块塞入过多内容：按使用者角色拆分模块，公共部分用嵌入方式复用，会更易于维护。
  • 试图在应用侧控制权限：可以展示的数据、可以执行的操作，原则上应通过本体和 Action 类型的权限来控制。
  • 把性能问题往后拖：把大量对象直接灌入表格会导致显示变慢。筛选的初始值和汇总方式应在试用阶段就确认。

这些都不是 Workshop 特有的高深话题。但它们是 FDE 在客户面前展示了“能快速构建”之后容易栽跟头的地方。

Workshop 的技能对职业发展有何帮助？

Workshop 技能被认可的不是操作速度。将业务分解为对象和操作的设计能力，才是作为 FDE 获得认可的关键。

被认可的是设计能力，而非工具操作

Workshop 的操作只需几周就能掌握。真正拉开差距的，是“把哪些判断放到界面上、把哪些操作做成 Action”的设计。

FDE 的招聘和考核所看重的，是例如以下这些能力。

技能领域通过 Workshop 锻炼的内容在其他环境中同样适用的原因
业务分解将判断要点落实到对象和 Action 上这是任何业务系统设计都共通的
数据建模设计本体的对象类型和链接这本身就是领域建模
产品思维删掉无人使用的界面，减少操作数量直接适用于内部工具开发和 SaaS 开发
与客户的对话边展示可运行的界面边敲定需求在咨询和售前工作中同样重要

即使转到不使用 Palantir 产品的环境，“定义业务对象，并为其设计操作和权限”这一思路依然可以直接沿用。Workshop 作为能在短时间内掌握这种思维方式的教材，也很有价值。

学习方法与经验的展示方式

捷径是先用官方培训教材掌握基础，然后能够说明“我把什么样的业务判断搬到了界面上”。

学习步骤的示例如下。

  • 通过 Palantir 官方学习网站（Palantir Learn）和官方文档，依次学习本体、Workshop、Actions 的基础
  • 如果可以使用面向个人或开发者的环境，则以身边的业务（例如：咨询管理）为题材，尝试制作列表、详情、状态更新三个界面
  • 将所开发的应用“支持了哪些判断、减少了哪些操作”整理成文字
  • 如果要参加官方认证考试，请在官方网站确认当时的适用范围和考试要求

面向开发者的环境和认证考试的内容可能会有变化，因此请务必确认着手时的官方信息。

在简历和面试中，只写“会使用 Workshop”是传达不出什么的。如果能结合业务变化来说明，例如“将现场负责人的例外处理，从列表到任务分配都在一个界面内完成”，就能传达出作为 FDE 的实务经验。对于考虑引入 FDE 的企业决策者来说，比起对工具的熟练程度，这种“将业务翻译成界面的能力”才是识别人材的关键。
