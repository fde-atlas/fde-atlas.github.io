Decagon 是如何开展前沿部署工程的

原标题：How Forward Deployed Engineering is done at Decagon

AI Engineer · 2025-09-23 · 约 24 分钟读完

摘要

Decagon 前沿部署工程负责人 Sunny Rekhi 在 AI Engineer World's Fair 2026 演讲中介绍其部署方法：公司一年内从约 50 人增至 500 人，前沿部署工程与产品工程共用同一团队和标准。部署先做客服支持，再借助已有后端集成扩展到创收场景（如 Hertz 租约续期外呼）。团队将定制需求沉淀为可复用产品能力，并随规模增长把通才角色拆分为 Agent builder 与 Agent software engineer。

要点

  • Decagon 一年内从约 50 人扩张到 500 人。
  • Hertz 案例显示入站支持可扩展为创收外呼。
  • 前沿部署工程与产品工程是同一团队、同一标准。
  • 通才角色拆分为 Agent builder 与 Agent software engineer。
  • 定制工作应转化为未来客户可用的产品能力。

Decagon 如何开展前沿部署工程

Decagon 的部署模式将 Agent 配置、客户建议和可复用的产品能力连接起来，使每一次企业部署都能改进下一次部署。

从支持交互说起

打电话给某个品牌寻求帮助，第一件事可能是 navigating 语音菜单：按 1 处理账单，按 2 处理会员事务。就紧急问题发送邮件，回复可能需要两三个工作日。Decagon 用一个 AI 客服 Agent 取代这些交互，它能立即接听电话并回复邮件，以类人的对话方式跨语言、跨渠道全天候服务。

初期部署针对的是原本需要人工处理的复杂支持工作流。一旦 Agent 了解了客户并与他们建立了关系，同样的部署就可以支持创造收入的沟通。这一转变取决于 Agent 已经掌握了哪些信息，以及它能访问哪些业务系统。

Sunny Rekhi 举的例子是 Hertz。Hertz 最初引入 Decagon 是为了处理复杂的呼入支持。Rekhi 描述了现有的后端集成随后如何启用了另一个工作流：在客户需要续租或延长汽车租约时主动联系客户，并且客户可以在 Decagon 内完成整个流程。呼入支持建立了连接；这些连接使外呼行动成为可能。

配置 Agent 并改进产品

部署方式因企业规模和行业而异。金融机构和技术品牌有不同的需求；大型企业和中端市场客户需要不同的部署动作。在这些差异之中，Decagon 将工作分为两类活动。

  • 配置 Agent。 确定它如何响应用户请求、使用什么样的品牌语气、采取哪些行动，以及对企业而言什么才算成功。决定哪些用户意图应转交给人工处理。大部分配置工作在 UI 中完成。
  • 构建可复用的产品能力。 将客户请求视为产品功能缺失的证据。如果企业 A 今天需要某个功能，而企业 B 很快也可能需要，那就以一种同时服务于 C、D 和 E 的方式来解决这个问题。

第一类活动让 Agent 为特定客户工作。第二类活动将团队从该客户那里学到的东西回馈到共享产品中。

在 Decagon，前沿部署工程就是产品工程。 Rekhi 描述的是同样的工程标准、同样的汇报结构，往往还是同一个团队。一家财富 20 强客户的痛点可以变成一个需要排期的产品功能。因此，发现需求的人和构建产品的人未必是两个不同的角色；这种重叠也体现在组织架构中。

随组织成长拆分通才角色

Rekhi 介绍，Decagon 在一年内从大约 50 人增长到 500 人。在增长早期，Agent 软件工程师负责整个部署。他们坐在客户旁边配置 Agent，包括它的实际语音和说话风格。他们还负责集成后端系统：即使是密码重置流程，也需要访问客户的身份认证系统，Agent 才能执行操作。同样的工程师还会把客户的功能需求带入平台。

在更大规模下，Decagon 将这类通才工作拆分为两条专业路线：

角色主要工作产品反馈
Agent 构建师主要通过 UI 配置 Agent标记 UI 尚无法满足的需求
Agent 软件工程师构建企业所要求的能力将这些能力融入产品

Agent 构建师对驱动平台的模型以及如何让模型适配企业的用例培养出直觉。当配置需要超出 UI 的范围时，这一边界就成为产品开发的信号。Agent 软件工程师则始终站在企业产品需求的第一线。

当定制代码变得容易时，要保持克制

一位重要客户希望立即获得某个功能。借助 Codex 或 Claude Code，工程师可以快速产出一个一次性的实现。Rekhi 指出，在这种情况下，克制才是稀缺的技能：在动手构建之前，先考虑该方案如何能推广到未来的客户。代码生成越快，这一架构决策就越关键。

客户所有权赋予这种克制一个具体的目标。Decagon 希望客户拥有自己的 Agent。一个由提示词和补丁组成的黑盒，对客户和供应商来说都很脆弱，而且会削弱这种所有权。工程任务是通过未来客户也能使用的能力来满足当前需求，而不是积累只有最初实现者才看得懂的例外情况。

在实施之前先就成功标准达成一致

需求收集从最初的交易范围界定对话中就开始了。团队需要明确对客户而言成功意味着什么，并且最好将这一共识落实到书面。问题非常具体：

  • 指标： 部署必须改善哪些衡量指标，哪些目标最重要？
  • 渠道： 初始范围是电话、电子邮件、短信、WhatsApp，还是某种组合？
  • 结果： 要解决的是什么痛点，期望的结果是什么样的？

一旦这些决策达成一致，实施就可以快速推进。

大客户可能会带来立即开始构建的压力。但当 AI 编程降低了实现请求所需的投入时，更多的工程工作就转向了确认这是否是正确的请求。关于必须构建什么的共识，需要先于匆忙动手构建。

让行业知识不断积累

Decagon 会安排在某个垂直领域有经验的人员参与该垂直领域的后续部署。如果一个核心团队曾服务过金融服务客户 A、B 和 C，那么这些经验应该延续到金融服务客户 D。

好处首先体现在能说客户的“语言”，从而建立信任。其次体现在更快的上手速度，因为之前构建 Agent 的方法和成功定义可以沿用。运营目标是让每次部署都借助积累的知识比上一次更快，而不是每次都要重新进行一遍探索过程。

11:17 ↗

让工程工作可以通过自助服务获得

可复用性还有另一个维度：谁能够执行这项工作？一个解决方案可能服务于多个客户，但每次部署仍然需要一名工程师。前沿部署团队还必须思考如何让业务的其他部门也能解决同样的问题。

Decagon 的既定目标是让客户完全通过自然语言来配置 Agent。当某项任务仍然需要工程师时，这种依赖关系就指出了应该纳入产品中的东西。工程团队最先接触到这个需求，然后将其转化为其他团队乃至最终客户都能使用的能力。

CRM 集成提供了一个具体例子。早期，Decagon 反复编写定制集成。Rekhi 回忆道，大约在第 25 个定制集成时，团队决定构建一条自助服务路径。原本需要工程师编写定制代码才能完成的工作，此后可以由客户或构建 Agent 的团队自行完成。这一产品改进同时改变了实现方式和能够交付它的人员范围。

12:41 ↗

围绕早期价值安排部署顺序

一家财富 500 强客户可能会带着覆盖整个客服运营的需求而来。由于渠道众多、用户意图复杂，Decagon 的部署可能变得任意复杂。因此，范围需要回答一个实际问题：什么能够最先展示价值？

顺序是先建立有用的运营，再进行扩展。Decagon 尽量避免客户在看到价值之前等待数月。Rekhi 将其与客户的关系描述为多年期合作伙伴关系，这为从初始部署扩展到更广泛的客服流程和创收工作流留出了空间。长期目标并不要求首次部署就包含一切。

利用客服历史记录来选择要自动化的内容

选择首个范围既是顾问工作，也是执行工作。客户通常带着具体需求而来，但一个在众多企业中部署过 AI 的团队，掌握着客户可能不具备的信息。对类似问题的反复接触，为前沿部署团队质疑客户提出的优先级提供了依据。

Decagon 会摄取客户的历史客服数据，并据此推荐优先自动化哪些工作流以获得最高的预期回报。该建议可能与客户最初的要求不同。团队仍然需要执行，但其领域知识也能帮助客户决定在哪里执行最有价值。

打造一家从每次部署中学习的公司

“定制变为自助”将单次的部署工作转化为一个反复出现的产品问题。每当有人执行一项手动的一次性任务时，公司里的其他人可能也在做同样的事情。把这类工作收回到产品中，消除的是一个反复出现的障碍，而不仅仅是又完成了一次实例。

Rekhi 将 Decagon 的进展归功于对客户需求的快速响应、勤奋的团队，以及以顾问身份行事所赢得的信任。这种信任建立在参考其他部署情况和客户自身数据而提出的建议之上。将定制工作产品化则将这些优势联系起来：快速响应可以改进共享系统，而不是停留在一次孤立的交付上。

随着公司的发展，非正式的知识传递已不再足够。Decagon 在跨部署共享知识、确保一线人员将信息反馈给平台方面变得更加严格。改进客户 A 的 Agent 应该能让客户 B 获得更好的效果。

因此，前沿部署的责任不仅限于让某一个客户的 Agent 正常运行。它还包括将改进回馈到产品中，并让能力在整个组织内流动，使更多人能够使用它们。一次部署也是下一次部署的输入：客户得到一个配置好的 Agent，而公司则获得一个更强的产品以及一种更可复用的交付方式。
