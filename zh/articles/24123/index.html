Palantir AIP Agent Studio 是什么？功能与构建步骤

原标题：Palantir AIP Agent Studioとは？機能と構築手順

FDE総研 · 2026-10-26 · 约 12 分钟读完

摘要

这篇文章介绍 Palantir AIP Agent Studio，一个基于 Ontology 以低代码方式构建和发布 LLM 业务对话代理的开发环境。文章说明其五大构成要素（模型、系统提示词、检索上下文、工具、应用状态），给出从目标定义到测试发布的六步构建流程，并区分它与 AIP Threads、AIP Logic 的分工。作者建议先做只读代理、用10到20个预期问题验证，再逐步加入写入类工具；代理沿用 Foundry 现有权限控制。对 FDE 而言，其价值在于快速试作，且 Ontology 数据建模质量比提示词技巧更能决定代理成败。

要点

  • AIP Agent Studio 通过 Ontology 连接数据与业务逻辑，低代码构建对话式 AI Agent。
  • 代理由模型、系统提示词、检索上下文、工具、应用状态五要素构成。
  • 构建流程分六步：目标定义、模型与提示词、上下文、工具、测试、发布。
  • 代理沿用 Foundry 权限控制，写入类工具需用户确认等防护设计。
  • FDE 应先做只读试作，Ontology 建模质量比提示词更影响成败。

Palantir AIP Agent Studio 是什么？

Palantir AIP Agent Studio 是 AIP 的开发环境，能够以低代码为主的方式创建并发布连接 Ontology 数据与业务逻辑的 LLM Agent。

Palantir AIP（Artificial Intelligence Platform）是在 Foundry 之上将生成式 AI 融入业务的产品群。AIP Agent Studio 在其中作为“创建对话式 Agent 的场所”使用。在 Palantir 官方文档中，用 AIP Agent Studio 创建的 Agent 被称为“AIP Agent”。其设想的使用场景是：与用户对话的同时，检索 Ontology 的对象、执行 Action、或参考文档进行回答。

AIP Agent Studio 诞生的背景是什么？

因为要在业务中使用 LLM，不仅需要聊天功能，还需要一套能够处理企业数据并符合权限管理的“操作”机制。

通用的聊天 AI 并不了解企业内部的库存、设备、项目等业务数据。即使了解，也无法管理“谁可以查看哪些数据”的权限。针对这一课题，Palantir 采取的方法是：将数据、逻辑和动作整合到一个模型中的“Ontology”，作为 LLM 的上下文（context）和工具（tool）提供给 LLM。AIP Agent Studio 可以理解为将这一理念具体化为“组装 Agent 的界面”。

在 FDE（Forward Deployed Engineer）的实际工作中，经常需要将客户“想用生成式 AI 做点什么”的需求，落实到具体的业务流程和数据连接设计中。如果将 AIP Agent Studio 定位为用于快速原型化这一落地过程的工具，就更容易把握其整体面貌。

面向哪些业务和用户？

主要设想的是“业务专用助手”：现场人员用自然语言查询业务数据、做出判断，必要时通过 Action 完成记录。

典型用途如下。

  • 调查与查询：针对“本周哪些出货存在较高延迟风险”这类问题，检索 Ontology 的对象并作答
  • 文档参考：检索手册、规程等文档，在给出依据的同时进行回答
  • 创建与更新：基于对话结果，通过 Action 创建维护工单或更新状态（通常采用在执行前加入用户确认的设计）
  • 应用集成：将 Agent 嵌入 Workshop 应用的界面，基于界面上选中的对象进行回答

设想用户分为 Agent 的“创建方”和“使用方”。创建方是 FDE 以及企业内部的数据／应用开发者，使用方是业务人员。

AIP Agent Studio 的主要功能和构成要素是什么？

Agent 由“模型”“指令（提示词）”“检索上下文”“工具”“应用状态”五个要素构成。

AIP Agent Studio 的设置界面大致由以下要素构成。由于名称可能随 Palantir 的 UI 更新而变化，最新表述请以官方文档为准。

构成要素作用设计时的主要考量
模型（LLM）选择承担推理的 LLM精度、速度以及可用模型的组织策略
系统提示词（指令）规定角色、语气、禁止事项和回答格式明确业务规则、如何展示依据
检索上下文（Retrieval context）从 Ontology 的对象或文档中获取相关信息展示哪些数据、以什么粒度展示
工具（Tools）对象检索、Action 执行、Function 调用等写入类工具的审批流程
应用状态（变量）与 Workshop 等外部应用之间传递值界面选择状态与 Agent 的联动

检索上下文与工具的区别是什么？

将检索上下文理解为“回答前自动提供的信息”，将工具理解为“LLM 按需调用的操作”，这样设计会更容易。

检索上下文是一种机制，将与用户提问相关的对象或文档片段自动插入到提示词中。如果使用语义检索，需要事先为目标数据准备嵌入（embedding）。

另一方面，工具是 LLM 在对话流程中判断“现在需要”时才调用的功能。包括对象的筛选检索、汇总、Function 的执行、通过 Action 更新数据等。

实际工作中容易纠结的是“全部做成工具，还是偏向上下文”这一判断。依笔者之见，几乎每次都会参考的少量信息放入上下文，而根据条件区别使用的查询和更新则归入工具，这样行为更容易稳定。不过，最优的分配会因数据量和模型而异，因此边评测边调整才是现实的做法。

权限与治理如何保障？

Agent 会以执行用户所拥有的权限范围访问 Ontology，因此 Foundry 现有的访问控制会直接生效。

Palantir 平台的设计是，标记（Marking）和项目权限等访问控制不仅适用于数据，也适用于 AIP 的功能。即使 Agent 检索 Ontology，也不会返回用户没有查看权限的对象。这在从 PoC 阶段迈向生产运营的过程中是一个很大的优势。

不过，Action 这类写入型工具需要谨慎处理。建议在设计阶段就确定好诸如“执行前必须经过用户确认”“只公开限定对象的 Action”等防护措施（guardrail）。

在 AIP Agent Studio 中创建 Agent 的步骤是什么？

基本流程是按照“目的定义→模型与指令设置→上下文连接→添加工具→测试→发布”这 6 个阶段推进。

以下是根据 Palantir 官方文档的结构和一般开发流程整理的步骤。具体的菜单名称可能因环境和版本而异。

#步骤主要工作完成的标志
1目的与用例的定义列举目标用户、预期问题、禁止事项已形成预期问题清单（评测集的基础）
2创建 Agent、选择模型在 AIP Agent Studio 中新建并选择 LLM空的 Agent 可以进行对话
3系统提示词设计描述角色、回答格式、依据的呈现方式、禁止事项语气和回答格式符合预期
4检索上下文连接连接 Ontology 的对象类型或文档能够带着依据回答预期问题
5添加工具注册检索、汇总、Function、Action查询和更新在测试中均成功
6测试、发布用评测集验证，并集成到 Workshop 等后发布用户可以在业务界面中使用

最初的原型应该把握哪些要点？

最初应聚焦于只读的 Agent，用 10～20 个左右的预期问题确认其行为之后，再添加写入型工具，这样比较安全。

“10～20 个问题”是笔者作为参考使用的规模，并非官方标准。这里重要的是，不要一开始就把 Action 纳入进来。在查询精度尚不稳定的情况下添加更新型工具，会提高错误更新对象的风险。

在原型阶段，记录以下几点有助于后续的顺利改进。

  • 回答的准确性（是否与 Ontology 的值一致）
  • 依据的呈现（能否看出引用了哪些对象、文档）
  • 工具选择的合理性（是否调用了应调用的工具，有没有多余的调用）
  • 是否能够拒绝应当拒绝的请求

发布与集成是如何进行的？

已发布的 Agent，通常通过 Workshop 的 AIP Agent 小部件嵌入到业务应用中使用。

集成到 Workshop 后，可以将界面上所选的对象作为应用变量传递给 Agent。例如，只需请求“总结这台设备最近的异常情况”，就能让 Agent 以当前选中的设备为对象进行回答。

除此之外，Palantir 还提供将 Agent 作为 Function 发布、从其他逻辑或 API 调用的方法。可用的发布途径会随时间不断扩充，请在引入时确认当时的发布说明。

与 AIP Logic 和 Threads 有什么区别？

分工是：Threads 用于通用的对话与分析，AIP Logic 用于将固定流程处理函数化，AIP Agent Studio 用于构建业务专用的对话 Agent。

AIP 中有多个处理生成式 AI 的功能，这是初学者最容易混淆的地方。下面用表格总结它们的区别。

视角AIP ThreadsAIP LogicAIP Agent Studio
主要目的针对文档或数据当场进行对话、分析将使用 LLM 的处理以无代码方式函数化构建并发布业务专用的对话型 Agent
对话性高（以聊天为中心）低（输入→输出的处理）高（聊天＋工具执行）
可复用性以个人、临时用途为主可作为 Function 从各处调用可将配置好的 Agent 分发给多名用户
典型输出回答、摘要结构化的值或 Ontology 编辑回答＋通过 Action 进行更新
适用场景探索性调查批处理、与 Automate 结合的自动化面向现场人员的业务助手

如何与 AIP Logic 区分使用？

输入和输出固定的固定流程处理适合 AIP Logic，而需要与用户交互、需求会变化的处理适合 AIP Agent Studio。

例如“对咨询邮件进行分类并添加类别”这类处理，由于输入和输出明确，用 AIP Logic 函数化并通过 Automate 定期执行的架构比较自然。而“负责人一边询问情况一边决定应对措施”这类业务，由于对话过程中所需信息会变化，更适合使用 Agent。

两者也可以组合使用。将 AIP Logic 创建的函数作为 AIP Agent Studio 的工具调用，就可以实现“判定逻辑由 Logic 严格处理，对话由 Agent 灵活应对”的分工。笔者经常推荐这种组合，作为易于保证质量的架构。

什么时候应该从 Threads 迁移？

当同类问题反复出现，且多名负责人开始以相同流程使用时，就是考虑在 Agent Studio 中将其 Agent 化的时机。

Threads 虽然使用方便，但指示和数据连接的设置往往因使用者而异。如果要将其固化为业务流程，最好将其做成固定了提示词和工具的 Agent，让所有人都能以相同的品质使用。按照“用 Threads 探索→用 Agent Studio 标准化→用 Logic/Automate 自动化”这样的渐进式成熟模型来考虑，也更容易与客户达成共识。

FDE 在实际工作中如何使用 AIP Agent Studio？

FDE 将 AIP Agent Studio 作为一种工具，把客户的业务课题转化为几天到几周内即可运行的试作品，并为是否投入生产提供判断依据。

Palantir 式 FDE 的价值在于深入客户现场，从课题发现到实现、落地全程贯通负责。AIP Agent Studio 在其中“尽早展示可运行的东西”这一环节尤其能发挥威力。

在实施现场应按什么顺序推进？

按照业务观察→Ontology 整备→Agent 试作→现场评估→投入生产的顺序，先于 Agent 固化 Ontology 是标准做法。

Agent 的质量高度依赖于所连接的 Ontology 的质量。如果对象类型的属性名含糊不清，或者链接不完整，LLM 就无法找到正确的数据。从现场经验来看，与其不断调整提示词，不如重新审视 Ontology 的属性说明和对象设计，这样改善往往更快。

推进方式的示例如下。

  • 观察现场负责人的业务，梳理出“谁、为了做什么判断、看哪些数据”
  • 在 Ontology 中整备所需的对象类型和 Action
  • 用 AIP Agent Studio 试作只读的 Agent
  • 让现场负责人实际使用，从提问日志中收集失败模式
  • 加入写入类工具、Workshop 集成、权限设计后投入生产

FDE 需要哪些技能和注意事项？

比起提示词技术，业务理解、数据建模、评测设计这三点决定成果，应避免过度自主化。

AIP Agent Studio 可以无代码操作，因此容易被认为“只要会写提示词就能做出来”。但在实际工作中拉开差距的是以下技能。

技能领域具体内容在 AIP Agent Studio 中的运用方式
业务理解掌握现场的判断流程和异常处理反映到系统提示词和禁止事项中
数据建模Ontology 的对象、链接、Action 设计提升检索上下文和工具的精度
评测设计预期问题集、合格标准、日志分析定量地运转改善循环
治理权限、审批流程、审计日志的设计保障写入类工具的安全性
利益相关者协调调整现场、IT 部门、管理层的期望值从试作到投入生产获得共识

作为注意事项，建议逐步扩大交给 Agent 的范围。如果从一开始就设计成“自主判断并执行更新”，一旦发生错误，说明责任就会变得模糊。至少在初期阶段，稳妥的做法是保持“Agent 提出建议，由人来批准并执行 Action”的形式。

对于立志成为 FDE 的工程师来说，AIP Agent Studio 是一个可以动手体验 Palantir 理念“以 Ontology 为中心的 AI 应用”的入口。然而，即使几天就能学会工具本身的操作，能否做出能在业务中落地的 Agent，取决于对现场课题理解的深度。在熟练掌握工具的同时积累数据建模和业务分析的经验，才是提升 FDE 市场价值的捷径。
