从问答到可运行：本体论与 FDE 共建企业级 AI 的语义运行时

原标题：From Q&A to Runnable: Ontology & FDE Co-Build Enterprise AI's Semantic Runtime

BestHub · 2026-09-24 · 约 15 分钟读完

摘要

本文以财务损益报告（PL BKD）场景为例，论证企业 AI 要从问答走向可执行，需要本体（Ontology）作为语义运行层，并由前沿部署工程师在现场完成语义工程。文章指出 RAG、图检索、SQL Agent 单独使用均不足以支撑核心财务场景，并展示了从 96 张 Excel 表格中提取 3000 多个候选对象、收敛为本体对象、规则与数仓映射，最终实现指标查询端到端可计算、可解释、可审计的运行闭环。

要点

  • 企业 AI 缺的不是更强模型，而是连接语义、数据、规则与执行的运行层机制。
  • RAG 只提供证据，图检索只展示关系，SQL Agent 缺口径保证，需本体统一组织。
  • FDE 通过采集、暴露、收敛、起草治理四步，把现场隐性知识转为可运行语义资产。
  • Excel 公式被释放为带版本、责任人、验证方式的规则，并连接数仓映射。
  • 查询结果与历史样本比对，超阈值即转人工复核，形成失败治理机制。

本文探讨本体论与前沿部署工程师（FDE）如何协作，为企业级 AI 构建语义运行时层，并通过一个复杂的财务 PL BKD 场景，展示如何从问答迈向可执行、可审计、可治理的 AI 系统。

亚信科技：新技术探索

引言：为什么企业拥有大语言模型和数据，却仍无法进入核心财务场景

企业通过数字化积累了海量的系统、数据仓库、指标平台和报表资产。大语言模型（LLM）提供了自然语言入口：用户可以询问政策、报表、指标定义，并获得分析辅助。表面上，企业智能化似乎只是把大语言模型与现有数据和文档连接起来的问题。

然而，一旦进入财务、运营、风控、供应链等核心场景，问题便迅速浮现。大语言模型可以解释一个指标名称，却未必知道它在当前企业口径下如何计算。RAG 能检索相关政策，却无法执行确定性规则。SQL Agent 能生成查询，却缺乏对字段背后业务语义的理解。知识图谱能展示对象之间的关系，却无法判断合规性、是否需要复核，或触发业务动作。

缺失的一环不是更强的模型，而是一种将业务语义、数据事实、规则逻辑和动作执行连接起来的运行时机制。没有它，大语言模型只能“回答”；有了它，AI 才能“判断、解释、审计并执行”。

本文认为需要两个并行的答案：本体论回答“系统运行在什么之上”——它是承载业务对象、口径规则、数据映射和审计边界的语义运行时层。FDE（前沿部署工程师）回答“这种能力如何在现场构建和治理”——其价值在于将现场复杂性转化为可运行、可验证、可治理的语义工程。AI 不会取代 FDE，而是把 FDE 从低效的信息整理中解放出来，专注于边界判断、规则确认和受控验证。

本案例研究使用 PL BKD（Profit and Loss Booked，损益入账）财务报表——一套多主体、多版本、多口径、公式复杂的报表集。难点不在于展示，而在于指标如何定义、计算、对账、解释和复用。

澄清问题：财务报表是一个语义运行时问题，而非展示问题

传统项目把 PL BKD 当作报表自动化：导入 Excel 数据、搭建页面、加上查询/筛选/导出功能，再点缀一些 LLM 解释。但在现场，那些 Excel 文件是被压缩的业务知识载体：行列结构承载管理维度，科目层级承载财务分类，单元格公式承载指标依赖，版本/期间承载管理口径，手工调整承载专家判断，报表样式承载长期形成的使用习惯。

在实践中，交付物是一个包含 96 个工作表的工作簿。每个工作表可能承载不同的实体、指标口径、维度组合和公式逻辑。人工逐页阅读效率低下，且容易遗漏隐藏公式、跨表引用、指标别名和口径差异。

业务用户会问“这个指标为什么变了？"、“这个结果从哪里来？"、“这个口径能不能调整？"；而系统看到的只有单元格、字段、代码和数值。这里存在语义鸿沟：业务说的是实体、科目、指标、收入、成本、利润、预测、实际、差异；系统存储的是表、字段、主键、版本、期间、组织层级和金额字段。

因此，PL BKD 的本质不是“如何把 Excel 搬进系统”，而是“如何把 Excel 背后的财务语义转化为系统可运行的能力”。把它当作报表问题，得到的是一个新展示页面；把它当作语义运行时问题，得到的是可复用的财务本体、指标规则、数据映射、校验机制和行动闭环。

这就是这个领域需要的不是传话筒式的分析师，而是能够做出语义判断的 FDE：哪些概念成为本体对象，哪些公式成为规则，哪些映射需要业务确认，哪些结果只是候选，哪些行动必须进入人工审核。

为什么仅靠 RAG、图谱检索和 SQL Agent 是不够的

PL BKD 很容易被误判为常规的“LLM + 数据”问题。逐一审视各条技术路线，会发现它们单独使用时都有清晰的边界：

RAG 适合文档检索和文本问答。它从政策、手册、指标手册中找到相关段落，再由 LLM 生成解释。但 PL BKD 的关键不是找到一段文字，而是从实体、期间、版本、科目、公式和数仓字段出发计算出可信的结果。RAG 提供的是证据，而不是规则执行。

图谱检索适合对象关系查询。它能告诉你某个指标关联哪些科目、某个实体属于哪个组织、某个公式依赖哪些子指标。但缺少规则、约束和行动，它只能回答“存在某种关系”，而无法回答“如何计算”、“结果是否正确”、“出现异常该怎么办”。图谱让知识可见，而本体让知识可运行。

SQL Agent 适合自然语言取数场景。它将用户问题转换为 SQL，但缺乏业务口径保障。相似的字段名 ≠ 语义一致；可查询的数据 ≠ 可用于当前指标；正确的 SQL 结果 ≠ 正确的业务结果。在财务领域，一个缺失的过滤条件、版本口径或科目汇总规则，都可能使结果偏离业务事实。

本体并不取代这些能力，而是将它们组织起来。RAG 提供文档证据，图检索提供关系路径，SQL Agent 提供数据查询，LLM 提供解析与交互，Agent 提供动作编排，而本体提供统一的业务对象、关系、规则、约束、版本和权限边界。没有本体，这些只是点状工具；有了本体，它们围绕统一的企业语义协同工作。

竞争格局的关键正在于此：仅有 RAG 停留在问答层面；仅有 SQL Agent 卡在口径上；仅有图谱停留在关系展示；仅有报表自动化则陷入重复开发。真正的护城河，是将语义、规则、数据和动作组织成一个可持续演进的运行时层。

FDE 理念：将现场复杂性转化为可运行的语义工程

如果说本体回答的是“系统靠什么运行”，那么 FDE 回答的是“这种能力如何从现场构建而来”。按照行业定义，FDE 是驻扎在现场、在真实业务约束下交付可运行解决方案的工程师——不是传话的分析师，不是只做页面交付的实施顾问，也不是纯粹的后端建模工程师。在本场景中，FDE 的核心工作是语义工程：识别对象、收敛边界、确认规则、验证映射、并主导治理。其价值不在于把需求翻译成页面，而在于把现场复杂性转化为可运行、可验证、可治理的语义能力。

在财务领域，许多规则并非以结构化文档的形式存在，而是散落在口头解释、会议讨论、Excel 公式、历史处理习惯和专家经验之中。FDE 的工作，就是将这些隐性知识转化为系统可执行的语义资产。

AI 改变的不是 FDE 的判断权，而是 FDE 的工作重心。过去，FDE 需要花数小时回放会议、整理纪要、人工阅读表格、手工搭建模型。如今 AI 辅助完成初步结构化，FDE 则专注于判断、确认与治理。整个方法链条被压缩为四个步骤：

收集。AI 访谈和 AI 会议纪要围绕实体、科目、指标、公式、版本、期间、口径、数据来源和验收样本持续追问，将业务表达转化为候选语义素材。例如，业务方反复提到“按实体”“科目汇总为指标”“公式计算”“口径后续可能调整”。这些表达很快形成结构，FDE 随后进行判断：实体和指标成为核心对象，科目汇总意味着关系和规则，公式需要提取为逻辑规则，口径调整意味着规则版本化和治理机制。

曝光。面对 96 张表，人工阅读难以完整识别实体、科目、指标、公式以及跨表依赖。表格解析从这些表中提取出 3000 多个候选对象和指标公式。目标不是“越多越好”，而是把隐藏在 Excel 中的业务知识转化为可分析、可筛选、可审查的语义素材。

收敛。3000 多个候选 ≠ 完成的本体。高质量本体不在于更大，而在于边界清晰、对象稳定、关系可用、规则可验证。FDE 围绕业务目标和验收问题进行筛选：哪些对象直接支持主报表？哪些指标参与核心计算？哪些公式影响关键结果？哪些字段只是属性？哪些内容留在场景边界之外？AI 帮助“发现得多”，FDE 决定“选择什么”。

起草与治理。在 FDE 确认的边界内，AI 辅助本体构建自动生成对象定义、关系候选、逻辑规则和数据映射草稿。FDE 从“手工构建模型”转变为“审查、修正、治理模型”。对于对象：重点审查边界；对于关系：确认其对业务问题的支持；对于规则：确认适用范围、版本、负责人和异常处理；对于映射：验证字段语义、筛选条件和样本结果。

三道判断关卡贯穿始终：

哪些进入本体，哪些留在场景之外。

哪些可以由 AI 起草，哪些需要业务负责人确认。

哪些可以自动运行，哪些必须进入人工审查。

这四个步骤共同构成 FDE 方法：不是用 AI 取代现场判断，而是用 AI 放大现场判断的效率和覆盖面，让语义工程从手工作坊转变为可复制的交付。

关键突破：从 Excel 公式到与数据仓库映射相连的可管理规则

PL BKD 的突破在于将 Excel 公式从单元格中释放出来，转化为可管理、可复用、可审计的逻辑规则，并将这些规则与底层数据连接起来。

传统上，财务指标的计算逻辑隐藏在 Excel 公式里。业务用户能用它们，但系统无法管理它们；公式能算出结果，却难以解释影响范围；报表可以复制，规则却难以复用；一旦指标口径变更，就需要手工修改表和公式并重新对账。

结构化之后，公式变成指标对象之间的依赖关系。一个指标由哪些子指标构成、是求和/相减/比率、是否依赖版本/期间/主体/组织范围——全部被记录下来。规则进一步获得名称、输入、输出、适用范围、生效版本、责任人和证据来源、验证方式。

示例：一条简化的毛利率规则：

Rule: PL_BKD_GrossMargin_Calculation v1.2
Input: Revenue, Cost
Output: GrossMargin
Logic: GrossMargin = Revenue - Cost
Scope: Entity, Period, Version=Actual
Owner: Finance Dept
Evidence: PL BKD Excel sample 2026‑07
Validation: Compare with historical Excel sample; threshold ±0.5%

验证不能是“毛利率 + 成本 = 收入”这种同义反复——那只是把计算重新排列一遍，无法发现真实偏差。有效的验证必须对照外部基准：历史 Excel 样本、业务给定的阈值，或跨口径的结果。FDE 负责确认规则范围、版本、责任人和异常处理——而不是重写每一条公式。

规则必须连接数据仓库才能真正运行。没有数据的本体只是知识模型；没有本体的数据只是一堆字段。语义映射要建立的不是“字段对字段”，而是一条完整的链路：“本体对象 — 业务属性 — 仓库字段 — 过滤条件 — 转换逻辑 — 验证样本”。

示例：简化的收入指标映射：

Mapping: Revenue_PL_BKD v1.3
Source System: Financial Detail Fact Table
Amount Field: amt
Period Filter: period = '2026-07'
Version Filter: version = 'Actual'
Entity Join: org_id → Entity-A
Currency Conversion: CNY → 10k CNY
Exclusion: Non‑operating adjustment accounts (list)
Validation Sample: 2026‑07 PL BKD Excel revenue = 1,280.50 10k CNY

一个指标要能自动取数，至少需要明确：取自哪个系统/表？取哪个金额字段？如何过滤期间/版本？如何关联组织/主体？币种/单位如何换算？排除哪些科目？样本能否与历史 Excel 对齐？AI 可以推荐映射路径，但 FDE 必须完成三项验证：字段语义一致性、过滤条件完整性、样本对齐。只有通过这些验证，映射才能进入可运行的规则。

规则解决“怎么算”；映射解决“从哪取”。二者结合，把对象和关系从骨架变成可计算的链路。后续新增指标、口径调整或类似报表迁移，都可以复用已有的实体、科目、期间、组织和指标映射——这就是从“项目交付”到“能力沉淀”的分界线。

运行时闭环：单条指标查询如何端到端执行

如果止步于对象/规则/映射的定义，本体仍然只是设计时资产，而非运行时层。“语义运行时层”的真正考验在于：一个业务问题能否走通完整的统一语义链路。

示例问题：“Entity-A 2026 年 7 月的毛利率是多少？”

第一步：问题解析。系统将自然语言锚定到本体对象：指标 = GrossMargin，主体 = Entity-A，期间 = 2026-07，版本 = Actual，场景 = PL BKD。如果解析结果不确定，应返回澄清项，而不是猜测。

步骤 2：规则匹配。系统找到 "PL_BKD_GrossMargin_Calculation" 当前生效版本 v1.2，确认输入为收入、成本，约束为实体/期间/版本。

步骤 3：映射数据获取。系统使用收入映射 v1.3 和成本映射 v1.1，从财务明细事实表中提取明细：按实体 A、2026 年 7 月、实际数过滤；按科目类型汇总；金额统一为万元人民币；应用已确认的非经营性调整科目排除清单。

步骤 4：规则计算。执行 "毛利率 = 收入 - 成本"。结果：收入 1,280.50，成本 792.30，毛利率 488.20（万元人民币）。保留中间结果，形成可追溯的计算链。

步骤 5：校验与解释。系统将计算结果与 2026 年 7 月 PL BKD Excel 样例进行核对。样例毛利率 = 488.60，绝对差异 0.40，差异率约 0.08% < 业务阈值 0.50% → 校验通过。系统返回毛利率金额，并附公式链、数据来源、过滤条件、规则版本和校验状态。

步骤 6：异常处理。若差异率超过阈值，不给出"确定性结论"，而是转入人工复核队列。FDE 或业务负责人沿对象、规则、映射、数据链路逐层排查，定位原因。系统继续提供解释，但不得自动触发下游生产动作。

一次成功的响应必须至少提供以下解释信息（实体、金额已脱敏）：

这一闭环表明：LLM 负责理解与交互；本体约束业务语义；规则保证计算的确定性；映射连接事实数据；Agent 负责编排调用；人与治理机制兜底风险。"可运行"意味着一个业务问题能够被解析、计算、解释、校验，并在失败时可以定位——而不仅仅是把 Excel 搬进系统。

失败治理：差异如何被定位并转化为治理资产

高质量的实践不仅要展示成功路径，还要展示失败如何被定位。对于财务语义运行时层而言，真正的危险不是出现差异，而是差异无法解释、无法归因、无法沉淀。

在 PL BKD 校验中，系统曾计算出某实体/期间的收入与原始 Excel 样例不一致。第一反应往往是归咎于公式错误或数仓数据不准。但沿语义链逐层排查后发现，两者都不是：毛利率/收入的计算表达式成立，底层金额字段也返回了数值。差异出在口径边界——有一类科目在数仓中仍被打上"收入"标签，因此被自动汇总进收入；但在 PL BKD 的管理口径中，这些科目属于需人工排除的非经营性调整，不应计入当期经营收入。Excel 依靠人的记忆来排除；而系统没有显式约束，"业务默认"就泄漏了。

如果没有本体和映射链，这类问题往往被笼统地标注为“数据不准确”或“系统算错”，最终以资深员工的口头解释收场。而在语义运行层中，定位会收敛到一个具体节点：

指标结果触发样本校验失败。

回溯到收入指标，但不急于修改公式。

检查收入映射的科目集和过滤条件。

发现差异集中在少数几个特殊科目上。

与财务负责人确认：这些科目在 PL BKD 口径下应予剔除。

将剔除条件写入映射，升级映射版本。

复测通过；将确认人、适用场景、生效版本一并归档。

这次修复的关键不在于纠正某个数字，而在于把一个隐性的业务默认约定转化为可版本化的治理资产。此后，类似指标不再依赖某个人的临时记忆，而是执行已确认的口径约束。对 FDE 而言，专业性不体现在“保证一次算对”，而体现在把错误定位到具体某一层——对象、规则、映射、数据或权限——并将修复沉淀为可复用的能力。

这也解释了为什么失败案例应当纳入方法论，而不是藏在项目复盘中：成功路径证明系统“能算”，失败闭环证明系统“能治理”。缺少后者，语义运行层就仍只是一套看似完整的定义集合，而非生产可用的能力。

验证框架：覆盖度、准确性、可解释性与可复用性

技术视角不能止步于愿景，还必须明确验证方式。结合 PL BKD 的实践，至少应从四个维度提供证据。下表展示了脱敏后的阶段性结果，用以说明验证口径和可观测的收益；出于客户敏感性考虑，实体名称、金额及部分过程细节已做脱敏处理。

1. 语义覆盖度。关键不在于候选对象有多少，而在于收敛后的核心对象、规则和映射是否足以支撑主要报表的运行。“~3,200 → 186”的漏斗表明，AI 负责全面暴露，FDE 负责将可运行范围收敛到可验证的边界。

2. 计算准确性。以历史 Excel 样本为基线，对比系统动态计算结果。关键不在于“能算”，而在于出现不一致时，能否定位问题来自公式解析、数据映射、版本口径、期间范围、手工调整还是数据质量，并在修复后复测通过。前文所述的收入口径剔除科目治理闭环，对应表中一个关键偏差案例：第一轮校验失败，补充剔除条件、升级映射版本后，复测通过。

3. 可解释性与可追溯性。系统必须输出指标结果的公式链、数据来源、过滤条件、规则版本、校验状态。在财务领域，没有解释链的自动计算很难让业务方接受；有了解释链，业务负责人才能信任并接手确认。MVP 阶段核心指标解释链的完整性，是业务方接受自动计算的前提。

4. 可复用性与效率。业务理解是否能更快形成可评审的材料，建模是否从手工搭建转变为评审/修正，新指标、规则调整、同类报表迁移是否能复用已有对象、关系、映射。表格显示的收益主要来自“减少重复梳理、增加边界确认”——而不是消除人的判断。

注：以上数字为验证方法的脱敏示意，正式发布时应替换为项目实测口径。但验证逻辑是清晰的：没有覆盖率、准确率、可解释性和可复用性的证据，只能证明“路径是对的”，而不能证明“已经做成了”。

边界与外推：哪些能进入生产，哪些能复制到其他场景

只谈自动取数、动态计算、AI 推理而不谈风险边界，企业生产环境很难准入，在财务领域尤其如此。

权限边界。用户能问什么、看什么、算什么，必须受主体、组织、期间、指标权限约束。不能通过 LLM 问答或 Agent 调用绕过数据权限。

审计边界。指标结果必须可追溯到数据来源、公式版本、规则配置、映射关系、人工确认记录。建议审计链包括：操作人、操作时间、输入参数、数据版本、规则版本、映射版本、输出结果、校验状态、人工确认记录、动作执行记录。

误判与回滚边界。AI 解析公式、推荐映射、生成解释都可能出错。关键指标、关键规则、高风险动作必须进入人工评审，尤其是在首次上线、口径调整、数仓结构变更时。出现以下情况应触发回滚或暂停自动动作：核心校验失败；关键指标与样本偏差超出业务阈值；权限校验失败；数据源结构变更未经确认；规则版本变更未经业务负责人确认；Agent 动作产生意外的下游影响。

更稳妥的上线方式是分阶段推进：第一阶段只读验证，仅输出计算结果和解释，不执行生产动作；第二阶段半自动，异常结果进入人工评审队列；第三阶段仅对稳定规则开放 Agent 动作，同时保留审计和回滚机制。这些边界不会削弱智能化，反而能让智能化进入核心业务系统。

就外推而言，PL BKD 提供的不是一个孤立的财务应用，而是一个可复制的范式：以真实业务问题为入口，以 FDE 为现场翻译角色，以 AI 辅助采集/解析加速理解，以本体为语义基座，以规则逻辑为确定性判断，以数据平台为事实来源，以 Agent 为行动编排。它可以扩展到预算预测、经营分析、风险预警、项目管理、供应链、绩效管理——前提是场景具备复杂指标、跨系统数据、隐性规则、动态计算和可解释性要求。

反之，如果场景只需要文档问答、缺乏稳定口径、缺乏可对账样本，或业务方无法确认规则归属，就不要强行套用本体方案。语义运行层和 FDE 方法都有适用边界。

数据与案例边界说明：本文中的客户实体、金额明细、科目编码及部分流程信息均已脱敏；验证结果用于说明方法的有效性与量级，不作为原始业务数据对外披露。

结论：企业 AI 竞争比拼的是语义组织与现场语义工程能力

PL BKD 表明，企业智能的深水区不只是“让 AI 回答”，而是“让系统理解、计算、解释、审计、行动”。大模型解决交互与生成；数据平台解决事实供给；Agent 解决行动编排；本体解决业务语义与规则运行；FDE 解决这套能力如何在现场被构建、确认并守住。

因此，本体的价值不在于把业务描述得更复杂，而在于把复杂业务转化为可运行的系统能力。FDE 的价值不在于取代业务专家或建模工具，而在于把现场复杂性翻译成可运行、可验证、可治理的语义工程。

未来的企业 AI 竞争，不只是谁的模型更强，而是谁能更快、更稳定地把业务语义、数据事实、规则逻辑和行动执行组织成一个可持续演进的智能底座。
