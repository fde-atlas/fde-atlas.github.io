本文是 FDE 面试题库的技术部分，提供 37 道技术面试题，分为 API、Python、SQL 与数据、调试场景四组。作者强调技术答案必须补充客户影响：说明机制服务谁、出错时客户损失什么。文章给出练习方法：大声演练、限时两到三分钟、先自答再看提示。题目附有优秀答案的要点描述，如批量接口的取舍、游标分页、幂等重试、时区处理、连接 fan-out、指标定义澄清等。

招聘难题。招聘人员只有四十分钟和你相处，并且要做出一个决定：这个人能否被直接投入客户混乱的系统中，被托付系统权限，并被放手独处足够长的时间，最终交付出客户真正会使用的东西？

她没有一块写满刁钻谜题的白板。她有一份她见过工程师搞砸的真实失败案例清单——一个悄悄丢失记录的 API，一条在凌晨 3 点阻塞数据接入管道的校验规则，一个看起来正确实则错误的仪表盘。她会带你走一遍这些失败案例的变体，并倾听你的思考方式。注意：本题库场景中的人物和公司是基于常见模式的示例性合成——情境才是重点，而非名字。

这是 FDE 面试题库的 A 部分：共三十七道技术题，分为四组，每一题都是 FDE 面试流程真正在考察的模式。请大声练习。

核心原则

一个忽略客户的技术答案只是半个答案。下面的每一道题都可以用一个正确的机制来回答。优秀的候选人还会说出这个机制服务于谁、出错时客户会受到什么影响，以及他们在生产环境中会首先检查什么。先回答机制，再说明它为什么对另一端的人很重要。

如何使用本题库

这些是练习题，而非答案集——这是刻意为之。FDE 面试不是知识竞赛；面试官会改变每道题的细节，一段背好的答案在追问面前会瞬间崩塌。所以：

  • 大声演练。把你的答案说给一个人听，或说给你的手机录音听，就像你在面试现场说出来那样。如果你无法用平实的语言解释它，说明你还没有真正掌握它。
  • 限时作答。每道题给自己两到三分钟，这是一段真实口头回答的长度。冗长的漫谈会显得不确定。
  • FDE 的关键一招：在你的技术答案之后，加一句关于客户影响的话——谁会感受到这次故障、它让他们付出什么代价，或者当它正常运行时他们的境况有何改变。这一句话往往就是“通过”与“强烈推荐通过”之间的差别。
  • 后看提示。每道题下方以斜体标注的是“好的答案长什么样”：一两句话描述一个强答案的形态。先自己起草答案，再进行对比。

第 1 组——API：设计、版本控制、身份验证、分页、重试、Webhook，以及调试别人的 API

这是最重的一组，这并非偶然。FDE 生活在别人的系统之中，而大部分接触都通过 API 发生——包括你自己的和对方的。这些循环考察的模式是：你能否设计出一个让别人可以信赖的契约，以及你能否诊断出一个已经在对你撒谎的契约？

先学习这些课程

  • 你正在设计一个 REST 端点，让市政机构提交 311 服务请求——路面坑洼、垃圾漏收、路灯损坏。对于每天提交数千条报告的机构，你会如何在 POST /requests 和 POST /requests/batch 端点之间做选择？ 优秀回答的样子：讨论逐条请求的成本（延迟、速率限制、客户端复杂度）与批量语义的对比——部分成功、原子性、逐项错误报告——并给出一个阈值，说明批量端点在什么情况下值得引入其复杂性。
  • 某合作团队的 API 在 JSON 响应体中返回 200 OK 并附带错误信息，有时却返回 500 且响应体完全可用。你如何编写一个能在这种情况下正常工作的客户端？ 优秀回答的样子：不要与 API 争论——定义你自己的明确成功契约（对照供应商文档化的行为进行验证，并配有测试），并且在没有该契约的情况下，绝不把看似可用的 500 响应体当作成功。日志要有诊断性而非原始记录：带脱敏的结构化日志、请求 ID、经过清理的响应样本，以及受限的访问权限——原始载荷会泄露 API 密钥、令牌和个人身份信息（PII）。
  • 你的 API 已在生产环境运行六个月，此时机构要求添加一个字段，但添加它会破坏现有客户端。请阐述你的版本管理策略——以及你在什么情况下会完全拒绝做版本管理？ 优秀回答的样子：解释增量变更与破坏性变更的区别，说明为什么增量变更通常更优，并指出破坏性的情形——改变字段语义、认证或错误契约——在这些情况下拒绝做版本管理就等于接受静默的数据损坏。
  • 对于一个与市政供应商的服务器对服务器集成，请比较 API 密钥、OAuth 2.0 客户端凭证和双向 TLS。什么因素会促使你选择其中每一种？ 优秀回答的样子：权衡安全保证与运维成本——密钥简单但共享密钥会泄露，OAuth 提供可轮换的短生命周期作用域令牌，mTLS 提供强身份验证但运维负担重——并将选择与线上传输数据的敏感度挂钩。
  • 你使用 ?page=3 对大型结果集进行分页。有客户端报告说，在他们的抓取过程中有新行插入时，出现了记录缺失和重复。这是怎么回事，你如何修复？ 优秀回答的样子：解释偏移分页会随着行的插入或删除而偏移，然后描述基于游标的分页作为解决方案——并指出促使这一改进的客户可见症状，而不仅仅是机制本身。
  • 第三方 API 将你限速为每分钟 100 次请求，并在超限时返回 429 和 Retry-After 头。你的夜间同步任务需要迁移 50,000 条记录。你会如何设计客户端？ 优秀回答的要点：先澄清再计算——每次请求处理多少条记录（页大小）？是否有单独的吞吐量限制？然后再做算术：最少分钟数 = 所需 API 请求数 ÷ 100。接着加上并发预算、带抖动的指数退避，以及对 Retry-After 的尊重——对已经不堪重负的服务器狂轰滥炸式的重试对谁都没有好处。
  • 什么时候你会重试一个失败的请求，什么时候你绝不重试？ 优秀回答的要点：重试只适用于幂等的、可安全重复的操作，并且要有超时和有界的重试次数；绝不盲目重试非幂等的写操作，比如支付或记录创建——应该改用幂等键来设计，并说明为什么客户的资金安全是原因所在。
  • 该机构希望在请求状态变化时获得实时更新，他们要求使用 webhook。在你信任一个 webhook 接收器之前，它需要具备什么？ 优秀回答的要点：验证 → 持久化记录 → 确认 → 幂等处理 → 对账。首先进行签名验证；只有在事件被持久化接受（持久队列或收件箱表）之后才返回 200 确认——返回 200 后崩溃就意味着事件丢失。事件 ID 提供的是幂等去重，而不是顺序保证——状态更新仍可能乱序到达，所以要为此做好设计。一个未经验证的 webhook 就是通向你系统的一扇敞开的大门。
  • 你接手了一个与遗留供应商 API 的集成，它没有文档、返回未记录的错误码，并且会在不通知的情况下改变行为。你的调试手册是什么？ 优秀回答的要点：首先捕获并记录原始请求和响应，构建一套固定当前行为的特征化测试套件，通过对比不同时间点的行为来检测静默变更，并编写你自己的契约层，让供应商的混乱远离你的领域代码。
  • 面试官问：“为公开的 311 受理 API 设计限流。”你会把限流器放在哪里、以什么为键，以及触发限流的合法用户会遇到什么？ 优秀回答的要点：说明部署位置的权衡（边缘/网关与应用层）、尽可能以有意义的键（如 API key 或租户）而非原始 IP 来限流、返回带 Retry-After 的 429，并保护面向市民的路径——受影响的客户是一位无法报告街道被淹的居民。

第 2 组 — Python：数据处理、校验、测试、打包、日期时间

Python 是 FDE 的实战语言：管道、胶水代码、ETL、命令行工具、副驾驶的工具。这里的循环测试的不是语法谜题——而是测试你的代码能否在混乱的真实世界中存活，在那里输入会说谎，时区会与你作对。

先学习这些课程

  • 你从供应商那里拿到一份包含 311 报告的 CSV。有些日期是 03/04/2026，有些是 2026-03-04，还有些写着“上周二”。请讲讲你的数据清洗方法。 优秀回答的样子：在解析任何内容之前先分析格式，按优先级顺序尝试严格解析器，将无法解析的行隔离并记录原因——绝不默默猜测日和月哪个在前，因为猜错会破坏客户的时间线。
  • 你什么时候会用 pandas，什么时候它不适合这项工作？ 优秀回答的样子：pandas 在交互式探索和中等规模的表格转换中物有所值。对于大文件，先考虑分块处理和节省内存的 dtype——只有当信号表明 pandas 确实做不到时（真正的流式摄取、分布式规模，或跨管线的显式 schema 强制），才切换工具（DuckDB、Polars、Spark）。
  • 供应商把某个字段从数字改成了带货币符号的字符串，你的管线在凌晨 2 点崩溃了。你会做什么改动，让这类故障再也不会在凌晨 2 点呼叫你？ 优秀回答的样子：在数据进入业务逻辑之前，用 Pydantic 这样的 schema 在边界处进行校验，以明确原因拒绝或隔离数据，并说明凌晨 2 点的告警正是信任一个从未度量过的输入所付出的代价。
  • 面试官让你为一个重试不稳定 HTTP 调用的函数编写测试。你实际测试什么？ 优秀回答的样子：不是网络——mock 传输层，测试尝试次数、退避时间的增长、停止重试的行为，以及在较晚的成功时最终成功；重点是测试你自己的逻辑，而不是供应商的可用性。
  • 你同事的管线在他的笔记本上能通过，在你的机器上却失败。然后在 CI 中也失败了。你的调试操作顺序是什么？ 优秀回答的样子：先查环境再查代码——依赖版本、lock 文件、环境变量、Python 版本——因为“在我机器上能跑”几乎总是披着代码外衣的环境问题。
  • Python 包的 lock 文件里应该包含什么，没有它就交付会给客户带来什么后果？ 优秀回答的样子：固定每个传递依赖的精确版本；没有它们，几个月后的部署可能解析出不同的包并表现不同——而客户会为一次没有任何人故意做出的变更承担事故后果。
  • 同一事件收到两个时间戳：2026-03-08T02:30:00 没有时区，以及 2026-03-08T07:30:00Z。其中一个处于夏令时切换期间。你如何在不破坏记录的前提下处理？ 优秀回答的样子：拒绝猜测。2026 年 3 月 8 日是春季时钟前拨的切换日——02:30 是一个不存在的本地时间，而不是有歧义的时间。要讲清两种情况：春季前拨会产生不存在的时间；秋季回拨会产生出现两次的时间。而且，不带时区的时间戳在不知道其来源时区的情况下无法可靠地解释——应在数据接入时要求使用带时区信息的时间。
  • 你被要求构建一个小型 CLI 工具，供机构的外勤团队在 Windows 笔记本电脑上运行。从第一天起你会内置什么？ 优秀回答的样子：清晰的帮助文本、带日志级别的结构化日志、合理的默认值、明确告知下一步该做什么的错误信息，以及可复现的打包方式——因为你的用户是一位疲惫的团队负责人，而不是开发者，工具必须以有帮助的方式失败。
  • 收到一个包含 40 列的数据文件，但只有 6 列重要。你会让全部 40 列都通过整个流水线吗？ 优秀回答的样子：尽早倾向于最小化数据——在接入时丢弃不需要的内容，记录原因，并将其与真实成本挂钩：存储、模式漂移的暴露面，以及你现在有责任承担的隐私风险。

第 3 组 — SQL 与数据：连接、聚合、对账查询、面向混乱数据的模式设计

SQL 是检验候选人诚实性的地方。错误的连接不会抛出错误——它会悄悄返回一个错误的数字，而有人会据此做出预算决策。这些问题考察的是你能否写出值得信赖的查询。

先学习这些课程

  • 一个查询将 requests 连接到 work_orders，行数暴增——仪表盘显示的未完成请求数是昨天的十倍。哪里出了问题，你如何证明？ 优秀回答的样子：识别出一对多连接导致的行数扇出，然后通过在连接前后分别计数、并在正确的粒度上进行聚合来证明——强有力的回答会先检查数据粒度，而不是责怪数据。
  • 你何时使用 LEFT JOIN 与 INNER JOIN，每种选择对数据做出了什么隐含声明？ 优秀回答的样子：内连接声明每一行都有匹配项，并悄悄丢弃其余行；左连接保留未匹配的行，并引入你必须在上游下游处理的 NULL——要指出每种选择隐藏了哪些行，因为被隐藏的行通常正是客户需要看到的。
  • 运营仪表盘显示上个月完成了 1,240 个请求。财务导出显示 1,198。两个查询“看起来都对”。你如何对账？ 优秀回答的样子：不要武断地选一个赢家——编写查询来隔离差异集合，检查定义（什么算“已完成”？使用哪个时区的截止时间？），并解释两个数字不一致首先是定义问题，其次才是数据问题。
  • 写出方法思路——而不是完整查询——针对：“按请求类型统计平均关闭天数，排除重新打开超过一次的请求。陷阱是什么？” 优秀回答的样子：陷阱是在错误的行上求平均——重新打开的请求会抬高平均值，且 NULL 关闭日期必须显式排除；勾勒出先过滤后聚合的顺序，并指出如果忘记这些，哪些行会扭曲数字。
  • 你需要为服务请求写一个去重查询，同一个坑洞被三位不同居民上报。你如何判定什么算“同一份”报告？ 优秀回答的样子：承认这是一个业务决策，而不是 SQL 决策——提出基于位置邻近度、类型和时间窗口进行匹配，展示如何将近似重复项呈现给人工审核，并指出过度激进的去重会悄悄把市民的声音从记录中删除。
  • 一张表将请求状态存为自由文本："open"、"Open"、"OPEN"、"in progress"、"In-Progress"、"done"、"closed"。该机构想要可靠的状态报告。你的计划是什么？ 优秀回答的样子：先分析不同的取值，与数据所有者——而不是独自——定义规范的状态枚举，用可审计的映射表进行迁移，并对该列加约束，使混乱无法再次滋生。
  • 解释“快的查询”和“正确的查询”之间的区别，并给出一个追求速度破坏正确性的案例。 优秀回答的样子：快的查询返回迅速，正确的查询在正确的粒度上返回正确的行。说出一个真实的失败模式：没有 ORDER BY 的 LIMIT、连接一对多表导致总数翻倍、在聚合之前还是之后过滤、内连接悄悄排除未匹配的行，或者与源数据产生偏差的汇总表。（合规的优化器可以改变连接顺序或使用索引而不改变语义——不要把应用层的错误归咎于执行计划。）先验证正确性，再优化。
  • 你会如何设计一个用于摄取你无法控制的混乱供应商数据的模式——格式变化、列出现又消失、有些行半空？ 优秀回答的样子：一个原始落地区，精确存储到达的内容；一个带类型化模式、经过验证的干净层；被拒绝的行连同原因进入隔离区；以及一条审计轨迹——因为你无法修复无法重放的东西。
  • 该机构要求一个单一的“按时解决的请求”指标向市长办公室汇报。在写下第一行 SQL 之前，你会澄清什么？ 优秀回答的样子：确定定义——“解决”意味着什么、“按时”是对照哪个 SLA 时钟、暂停状态如何处理、重新打开的案件、截止时间的时区——并把它写成书面文件，因为一个你无法定义的指标，在数字受到质疑时也是你无法辩护的指标。

第 4 组——调试场景：“管道一夜之间坏了”

这就是决定大多数 FDE 面试结果的群体。没人指望你了解系统——他们指望的是一套方法。每个场景都是围绕 CityOps 主线综合而成的：311 数据管道、API、Ask CityOps 副驾驶、部署。像侦探办案一样向面试官展示你的调查过程，而不是像背题库的选手那样应付闪卡。

  • 你半夜被告警叫醒：夜间 311 数据接入管道处理了零条记录。任务日志里没有任何错误——它在四秒内“成功”完成。请讲述你的调查过程。 优秀回答的样子：从那个并非真正的成功入手——检查上游文件（是否到达？是否被重命名？是否为空？）、源端数量与落地数量是否一致、任务自身的记录数断言；最有力的回答会指出本应由哪些监控在人工发现之前就捕捉到这个问题。
  • 管道运行正常，但今天早上该机构的运营仪表盘显示昨天的数字少了一半。数据团队说“管道没问题”。你如何找出真正的原因？ 优秀回答的样子：把“没问题”当作一个待验证的说法——在每个阶段边界对比行数、检查仪表盘的查询和过滤条件、排查时区或日期边界偏移，并用原始数据源独立核对仪表盘上的数字。
  • 市民反映公开的 311 API 能正常返回他们提交的请求，但他们昨天提交的请求却从状态页上消失了。数据明明在数据库里。你会从哪里查起？ 优秀回答的样子：缩小“在数据库里”与“不在页面上”之间的差距——缓存、只读副本延迟、状态查询应用的过滤条件、分页截断——并解释为什么你从栈的两端同时二分排查，而不是在中间瞎猜。
  • Ask CityOps 副驾驶开始对垃圾清运时间表给出自信却错误的回答。RAG 检索没有任何改动。到底是什么变了，你又如何证明？ 优秀回答的样子：检索没变不代表依据没变——检查源文档是否被静默修改、对提示词和模型做版本管理、将引用与检索到的证据逐一核对，并运行评测集来定位回归出现的时间点。
  • 周五部署之后，API 在线、健康检查全部通过，但每次写入都返回 200 OK，而实际上什么都没保存。请讲述排查过程。 优秀回答的样子：区分存活与就绪——健康检查 GET 只能证明服务器有响应——端到端检查写入路径、部署 diff、功能开关，以及部署是否迁移了写入目标；并指出本应在客户发现之前就捕捉到这个问题的缺失就绪检查。
  • 供应商的旧系统每周开始返回一次垃圾数据——而且只在周一早上。你的代码没有任何改动。你如何处理这种无法按需复现的间歇性上游故障？ 优秀回答的样子：记录并打上时间戳保存每个原始载荷，将故障与供应商的排程关联起来（周一早上的批处理窗口是经典案例），用捕获的样本构建特征化测试，并加上校验和隔离机制，让他们糟糕的周一早晨不再变成你的事故。
  • 你的日志显示每个工作日早上 9 点 LLM API 的 429 响应激增，在机构最繁忙的一小时里 copilot 慢得像爬一样。修复方法是什么——陷阱又是什么？ 优秀回答的样子：规划并发预算，优雅地排队和卸载负载，缓存可重复的调用——而陷阱在于，在高峰时段对限流 API 进行重试会让峰值更糟；应该退避，而不是猛敲。
  • 一位同事说“数据库很慢”，因为他们的查询要花两分钟。你如何判断问题出在数据库、查询，还是预期本身？ 优秀回答的样子：先测量——检查查询计划、行数，以及昨天是否跑得更快——因为“慢”是一种比较，答案会随着变化的内容而完全不同：是数据量变了、计划变了，还是它周围的流量变了。
  • 这是你在客户现场的第一周。一条没人完全理解的生产流水线已经间歇性故障了一个月，值班工程师已经精疲力竭。没人能给你一份操作手册。你从哪里入手？ 优秀回答的样子：先谦逊，后英雄——在动任何东西之前先读日志，梳理流水线的各个阶段和负责人，先和那位精疲力竭的值班工程师聊聊，因为他们掌握着上下文，并在改动任何一行代码之前，先把你发现的内容写成一份书面梳理。

不要死记硬背

  • 不要把这些提示当作背好的答案——面试官会变换细节，一段与追问对不上号的排练过的回答，比一个粗糙但诚实的回答更糟糕。
  • 不要只答机制。每个分组都青睐能补上客户影响那句话的候选人：谁受到了影响，他们付出了什么代价，问题解决后会有什么改变。
  • 不要假装确定。“我不知道，但我会这样去弄清楚”是一个完整而有力的回答——尤其是在第 4 组。

实战示例：好与卓越的分界线

API——429 问题，附评分

好（6/10）：“我会加上指数退避的重试，并遵守 Retry-After。”卓越（10/10）：“首先我会确定页面大小和每次请求的记录数——没有这些，算术毫无意义。然后：最少分钟数 = 所需请求数 ÷ 100，设置并发预算以免重试加剧负载，带抖动的退避，如果计算表明同步无法在窗口内完成，就与客户进行一次坦诚的沟通。猛敲一台苦苦挣扎的服务器的重试对谁都没有好处。”

追问：“供应商在客户尚未签署的企业合同上提供了更高级别。你会基于它来构建吗？”

Python — DST 问题，评分版

良好（6/10）：“我会让所有时间都带时区信息。” 优秀（10/10）：“2026 年 3 月 8 日是春季时钟快进——02:30 在 America/New_York 时区不存在，它不是模糊的，而是无效的。秋季时钟回拨才是模糊的情况。一个不带时区的时间戳无法在没有其来源时区的情况下被解释，所以我会隔离该记录，要求在数据摄入时使用带时区的日期时间，并记录所适用的转换规则。”

追问：“源系统无法发送时区信息。业务明天就需要这份报告。你怎么办？”

SQL — 快速 vs. 正确，评分版

良好（6/10）：“我会检查查询计划并添加索引。” 优秀（10/10）：“正确性优先：我会验证数据粒度——这是没有 ORDER BY 的 LIMIT 吗？是 join 导致总数翻倍吗？是在聚合之前进行过滤吗？是汇总表与源数据发生了偏差吗？然后我会编写一个对账查询来证明结果正确，之后才去优化性能。优化器不会悄悄丢掉行；应用逻辑才会。”

追问：“正确的查询需要 40 分钟，而仪表盘需要每小时更新。现在怎么办？”

调试 — 静默失败的管道，评分版

良好（6/10）：“我会检查日志并重新运行。” 优秀（10/10）：“一条在零记录的情况下报告成功的管道是监控失败，而不是数据失败。我会检查‘成功’到底断言了什么——行数？schema 检查？——然后补上缺失的不变量，回填缺口，并在客户开口之前主动告诉他们缺失了什么、缺失了多久。对客户说的那句话和修复本身同样重要。”

追问：“你发现管道已经静默空转了三周。客户已经展示了这些数字。你的第一通电话打给谁？”

实战检验

任选三道题——一道来自第 1 组，一道来自第 3 组，一道来自第 4 组。录下自己大声回答这三道题，总时长不超过八分钟。然后回放，并按照以下标准给自己打分：

  • 你是否在任何观点之前先清楚地陈述了机制？
  • 你是否加上了那句关于客户影响的话？
  • 你是否说出了在生产环境中你会首先检查什么？
  • 你是否避免了编造数字或声称自己并不具备的确定性？

一次合格的演练是什么感觉

你听起来像一个曾经被线上告警呼叫过的人——对未知保持冷静，对下一步行动具体明确，并且总能说出这到底是谁的问题。如果你的回答太长，删掉开场白；机制和客户影响那句话就是全部答案。
