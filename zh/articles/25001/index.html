LLM 成本削减实践指南｜FDE 在现场使用的手法与优先级

原标题：LLMコスト削減の実践ガイド｜FDEが現場で使う手法と優先順位

FDE総研 · 2026-10-23 · 约 10 分钟读完

摘要

这篇来自 FDE総研 的日文指南系统讲解 LLM 成本削减：成本由模型单价、输入输出 token 量和调用次数决定，作者提出模型分流、提示词压缩、缓存、批处理、上下文优化五种手法，并强调应按“先计量、再低风险措施、最后换模型”的顺序推进，同时用评测集守住质量。文章还论述了 FDE 在客户现场将技术指标翻译成业务成本、与客户就质量与成本平衡达成共识中的独特作用。

要点

  • LLM 成本由单价×token 量×调用次数决定，长输入与冗余输出最易膨胀。
  • 五种主要手法：模型分流、提示词压缩、提示缓存、批处理、上下文优化。
  • Anthropic 缓存读取约为常规输入价 1 折，两家批处理 API 均为半价。
  • 推荐顺序：先计量、再低风险措施、最后才换模型，并配评测集防质量下滑。
  • FDE 的价值在于把成本换算成每件业务费用，与客户就质量线达成共识。

LLM 的成本由什么决定？

LLM 的成本基本由“token 单价 × token 数量 × 调用次数”决定。首先应该关注的是较长的输入和输出的数量。

LLM 的 API 使用费，在大多数商用模型中都是按“输入 token”和“输出 token”各自的单价乘以使用量来计算的。与按月固定收费的 SaaS 不同，使用量增加，账单金额也会随之增加。这就是为什么 PoC 阶段不在意的金额，到了生产环境会膨胀数十倍。

成本因素内容在一线容易膨胀的场景
模型单价各模型每 100 万 token 的价格所有处理都用最高端模型运行
输入 token 数量系统 prompt、RAG 检索结果、对话历史每次都传入完整的长篇手册全文
输出 token 数量模型生成的文本或 JSON一句“请详细说明”就返回冗长的输出
调用次数每项业务的 API 调用次数Agent 反复多次调用工具
重试与失败因超时或解析失败而重试因 JSON 格式错误而重新执行同一处理

token 单价因模型选择会有多大变化？

token 单价因模型性能档次而有很大差异。即使是同一家提供商，高端模型与轻量模型的价格也可能相差一个数量级。

Anthropic、OpenAI、Google 等主要提供商都提供多个性能与价格不同的模型。高端模型擅长复杂推理，但单价较高。而分类、抽取等固定模式处理，往往用轻量模型就足够了。由于单价会频繁调整，在估算之前务必在各家官方定价页面确认最新数值。

输入、输出、调用次数，哪个影响最大？

影响最大的是每次都会附带的较长输入，以及在多数模型中单价高于输入的输出。

在输入方面，系统 prompt、对话历史、RAG 检索到的文档会随每次调用不断累积。在输出方面，虽然单次数量不多，但在输出单价往往被设定为输入数倍的模型中，冗长的输出会直接推高成本。此外，在 AI Agent 型架构中，一个任务会多次调用模型，调用次数会以乘法方式放大成本。

LLM 成本削减的主要方法有哪些？

主要方法有五种：模型分工使用、prompt 压缩、缓存、批处理、上下文设计。

每种方法都对应“降低单价”“减少数量”“减少次数”之一。下表整理了各方法的特点。效果大小因用例而异，请作为相对参考来看待。

方法作用的因素实现成本质量风险适合的处理
模型分工使用（路由）单价中中～高难度参差不齐的查询
Prompt 压缩与输出控制数量低低～中所有处理
Prompt 缓存单价（输入）低几乎没有共用的长系统 prompt 或文档
Batch API 与异步化单价低～中几乎没有不需要即时响应的批量处理
RAG 与上下文设计的优化数量中～高中内部文档检索、知识问答
结果缓存与去重次数中低相同问题反复出现的业务

如何设计模型分工使用？

基本做法是按处理难度分配模型。仅仅把轻量处理迁移到轻量模型，就能降低单价。

常见的分工方式是：“分类、抽取、格式化”用轻量模型，“复杂推理与最终回答生成”用高端模型。还有一种“路由”方式，先用轻量模型或规则判断输入难度后再分流。但一旦判断错误，质量就会下降，因此前提是使用后文提到的评测集来验证分流的准确性。

Prompt 缓存与批处理的效果有多大？

Prompt 缓存与批处理可以在不改变质量的前提下降低单价，是性价比很高的措施。

Prompt 缓存是一种复用每次相同的开头部分（如系统 prompt、参考文档等），从而降低该部分输入单价的机制。例如 Anthropic 的官方定价中，从缓存读取的输入按普通输入单价的 1 折计费（写入缓存有加价）。批处理是一种以折扣价格处理、但不要求即时响应的机制。Anthropic 的 Message Batches API 和 OpenAI 的 Batch API 官方均标明为标准费率的 5 折。由于条件和折扣率可能变化，采用前请确认最新文档。

如何削减 prompt 与上下文？

首先，重新审视每次传入的信息是否真的必要。在此基础上，通过指令限定输出的格式与长度。

在一线常见的情况是，“以防万一”而传入全文的手册，以及无限累积的对话历史。重新审视 RAG 检索的条数与 chunk 大小、将历史摘要后再传入、用 JSON schema 或字数上限限定输出。这些措施虽然朴素，但能在控制质量影响的同时减少数量。

应该按什么顺序推进 LLM 成本削减？

按计量、低风险措施、模型更换的顺序推进比较安全。请避免一上来就更换模型。

现场常见的模式是：一开始就决定“太贵了，换成便宜的模型”，结果质量下降，遭到现场投诉。从不影响质量的部分入手削减，更容易获得相关人员的同意。

  • 进行计量：按功能、提示词、用户分别记录 token 用量和调用次数
  • 找出主要支出来源：聚焦于占支出大部分的少数处理
  • 引入不影响质量的措施：提示词缓存、批处理、抑制重试、消除重复调用
  • 减少用量：压缩提示词、约束输出格式、精简上下文
  • 准备评测基础：构建代表性输入与期望输出的集合
  • 尝试区分使用模型：一边用评测集进行比较，一边逐步迁移到轻量模型

为什么首先需要计量？

因为如果不清楚在什么上用了多少，就无法选择效果大的措施。计量是一切的起点。

仅凭账单总额，无法知道是哪个功能推高了成本。首先要为每个请求在日志中记录输入 token 数、输出 token 数、模型名称、功能名称，并按日汇总。使用面向 LLM 的监控工具或网关，可以较快完成这种可视化。

从低风险措施入手有什么好处？

从低风险措施开始，即使不讨论质量问题也能产生削减效果。这对赢得公司内部的信任也很有效。

缓存和批处理不会改变输出内容，因此可以简化质量保证流程。如果能把最初的成果以“质量不变、只有成本下降”的形式展示出来，那么对于接下来有风险的措施（如更换模型），也更容易取得共识。

FDE 在 LLM 成本削减中承担什么角色？

FDE 深入客户现场，从技术层面设计业务需求与成本的平衡，并以可运营的形式将其落地。

FDE（Forward Deployed Engineer）是在 Palantir 普及起来的职位，其特点是深入客户现场，直到解决问题都亲自实现。LLM 的成本削减不会仅靠技术上的巧思就结束，它本身就是与客户逐一敲定“哪项业务需要什么质量”的工作。正因如此，我认为这是 FDE 的价值容易体现的领域。

视角一般开发团队FDE
起点规格书、工单客户现场的业务流程
成本的判断标准API 单价或技术效率每笔业务的价值与成本的平衡
质量的定义测试的合格标准现场负责人能够接受的水平
交付物功能实现除实现外，还包括运营规则与监控机制

在客户现场首先应该可视化什么？

以业务为单位可视化“每笔业务花费多少”。这样就能把技术指标转换为经营的语言。

即使告诉客户“每月数百万 token”，也很难打动客户的决策者。如果转换为业务单位，如“处理一条咨询花费多少日元”“处理一张报表花费多少日元”，就可以与人工处理进行比较，或作为投资判断的依据。这种转换工作，只有理解现场业务的 FDE 才能做到。

如何就业务需求与成本的平衡达成共识？

与客户约定每项处理所需的质量，明确使用高端模型的范围，在此基础上取得共识。

并非所有处理都需要最高质量。面向内部的草稿生成与发送给客户的最终回答，可容忍的错误水平是不同的。FDE 通过对现场负责人的访谈明确这条界线，并与客户的决策者一起确定“这项业务用轻量模型就足够”“只有这个判断使用高端模型”之类的方针。

如何在削减 LLM 成本的同时不降低质量？

守住质量的关键在于：在削减措施之前准备评测集，分阶段切换，并持续监控。

成本削减的失败大多源于“感觉上应该没问题”就进行切换，结果发现质量下降为时已晚。必须建立削减与评测始终成对运行的机制。

质量保护机制目的实施时机
评测集（黄金数据）在相同条件下比较变更前后的质量引入措施之前
A/B 测试、分阶段发布用部分流量确认影响切换时
质量指标监控检测正确率、错误率、用户评价的变化运营期间持续进行
回滚流程出现问题时立即恢复到原有配置事先准备好

评测集应该怎么构建？

准备数十到数百条生产环境中具有代表性的输入与期望输出，做到每次变更都能自动评分。

评测集中不仅要有常见的输入，还应包含过去曾出现误答问题的案例和边界案例，这样效果更好。评分时，将可用完全匹配或规则判定的项目与使用 LLM 作为评判者的项目结合起来。评测标准最好与客户的现场负责人一起确定。

哪些领域不能削减？

错误影响重大的判断以及直接交付给客户的输出，是应优先质量而非成本的领域。

涉及金额或合同的判断、医疗或安全相关的信息、发送给外部的最终回答，即使成本略高，也建议保留高端模型和人工检查。成本削减的目的是把节省下来的预算投入到价值更高的处理上。如果以牺牲质量来追求削减率，从长远来看，可能会失去对 LLM 应用本身的信任。
