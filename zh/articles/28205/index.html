前沿部署工程，第 4 部分：数据就绪与从零构建 RAG

原标题：Forward deployed engineering, Part 4: Data readiness and RAG from zero

Abhinav Bhatia · 2026-10-20 · 约 15 分钟读完

摘要

作者以虚构客户 Acme Consumer Brands 的缺货成本问题为例，讲解前沿部署工程师如何从零准备文档数据并搭建 RAG。缺货罚款条款散落在 SharePoint 的 PDF 合同中，表格数据无法覆盖，因此需要让 Agent 能检索并引用这些文档。文章定义了数据就绪的五项检查（可找到、可读取、最新、有归属、有权限），解释分块、嵌入、混合检索、重排序与引用溯源，并介绍 Google Cloud 的四种托管方案，最后给出用 Recall@k 和 MRR 评测检索、按决策树排查错误答案的方法。

要点

  • 数据就绪五检查：可找到、可读取、最新、有归属、有权限。
  • RAG 分为离线索引与在线检索两段，分块策略应按文档类型选择。
  • 混合检索加重排序解决向量搜索对精确条款号的短板。
  • Google Cloud 提供从数据存储到自建管线的四级方案，建议从简入手。
  • 用 Recall@k 与 MRR 单独评测检索，再按决策树定位错误答案。

大多数 AI Agent 的回答质量取决于其背后的文档。本部分从零开始：什么才算数据就绪、RAG 如何将文档转化为带引用的回答、为什么混合搜索和重排序很重要、Google Cloud 提供哪些托管选项，以及如何判断一个回答出错的原因。

在第 3 部分中，我们在 Acme Consumer Brands 的环境中进行设计：数据存放在哪里、由哪个身份提供商进行登录认证、允许哪些网络路径。设计敲定后，工作就转向数据本身。

Acme 的问题仍然是 AI Agent 系列中的那个问题：“这些缺货让我们损失了多少钱？”销量和订单明细存放在 Databricks 表中，AI Agent 系列展示了 Agent 如何安全地查询这些数据。但在项目进行的第二周，供应团队告诉我了一件任何表中都没有记录的事情。延迟或短缺交付的罚金是按零售商在供应协议中规定的。这些协议是 SharePoint 中的 PDF 文件，有些还是扫描件。两家零售商有多个版本同时生效。因此缺货的成本取决于一份文档，而无法读取该文档的 Agent 只能给出半个答案。

这些内容在 FDE 的职位描述中如何体现？

检索是公开的 FDE 招聘信息中最常见的要求之一。Google Cloud 的 GenAI 前沿部署工程师职位要求：

  • “有使用向量数据库和类 RAG 架构为结构化和非结构化数据构建管道的经验，以支撑企业级 AI 解决方案。”
  • 能够“解决发布阻碍因素，包括攻克集成难题、数据就绪问题和状态管理问题”。

Google Cloud 的一个企业上下文层 FDE 职位增加了“通过提供合适的话术、工具以及特定品牌所需的特定知识库来调优 AI Agent”，并将知识图谱和本体的经验列为加分项。

这份工作的重点不在于调用模型，而在于为模型提供正确的事实。

“数据就绪”到底是什么意思？

这是我与客户使用的一个简单定义：当 Agent 能够找到数据、读取数据、确信数据是最新的、知道数据出错时该问谁，并且遵守谁有权查看数据时，数据才算就绪。 其中每一项都是你可以在第一周内完成的检查。

数据就绪的五个检查项：可查找、可读取、最新、有负责人且有权限，每一项都以 Acme 的供应文档为例说明其含义

  • 可查找。 你知道文档存放的每一个位置。在 Acme，供应协议分散在三个 SharePoint 站点上，每个区域一个。
  • 可读取。 程序能够提取文本。扫描版 PDF 只是页面的图片，因此需要先进行 OCR（光学字符识别，一种将文本图像转换为文本的软件），其他步骤才能进行。
  • 最新。 只有一个版本是有效的。两份 Northmart 协议，v3 和 v4，都存放在文档库中。引用 v3 的 Agent 会自信地给出错误答案。
  • 有负责人。 有人对内容负责。商务团队负责合同条款，因此由他们而不是 FDE 来决定哪个版本是权威版本。
  • 有权限。 你知道谁可以查看它。定价条款仅限商务团队查看，Agent 必须保持这一点。

在我与合作伙伴的工作中，大多数“AI 出错了”的升级问题最终都归结为这五项检查之一。

用通俗的话说，什么是 RAG？

大语言模型只知道其训练数据中的内容。它从未见过 Acme 的合同。RAG 在提问时解决了这个问题：在模型回答之前，你的代码会从自己的文档中查找最相关的段落，并将它们与问题一起放入提示词中。然后模型根据这些段落撰写答案。

正式的定义来自 2020 年命名该技术的论文：RAG 将模型的参数化记忆（它在训练中学到的内容，存储在其权重中）与非参数化记忆（一个在提问时被检索的外部文档索引）结合起来。拆解开来，这为你提供了每天都会用到的词汇：

  • 语料库。 你希望从中获取答案的全部文档集合。
  • 分块。 文档的一小部分，例如一个章节或几段文字。你检索的是分块，而不是整个文档。
  • 嵌入。 表示分块含义的一串数字。
  • 索引或向量存储。 存放分块及其嵌入的数据库，其构建方式使其能够快速找到相似的内容。
  • 检索。 查找与问题最相关的分块。
  • 接地（Grounding）。 让答案依赖于检索到的文本块，而不是模型的记忆。
  • 引用（Citation）。 从答案中的某句话链接回支持它的文本块。

一个日常类比很有帮助。RAG 把闭卷考试变成了开卷考试。语料库是教科书，索引是它的目录，检索是找到正确的页码，生成则是翻开这些页面写出答案。大部分工程工作都花在“找到正确的页码”上。

RAG 有两个在不同时间运行的部分。先看一份文档经过前半部分，再看一个问题经过后半部分：

文档如何变成文本块？

解析是把文件转换成保留其结构的干净文本。从 PDF 中直接提取纯文本会丢失标题，并把表格压平成一串数字。布局感知解析器会保留结构：哪一行是标题，哪些单元格属于哪一行。在 Google Cloud 上，Document AI 的布局解析器可以做到这一点，RAG Engine 可以在摄取过程中使用它。

分块是把解析后的文本切分成足够小、能够精确检索的片段。有三种常见策略：

  • 固定大小。 每 N 个 token 切一块，通常带有一定的重叠（前一块的结尾在下一块的开头重复出现）。简单且可预测。RAG Engine 的默认设置是每个文本块 1,024 个 token，重叠 256 个 token。
  • 结构感知。 按标题切分，并保持表格完整。更适合合同、政策与手册，因为章节是自然的语义单元。
  • 语义。 在话题发生变化处切分，使用嵌入来检测变化。适用于转录稿等长篇非结构化文本。

这就是固定大小分块对 Northmart 罚则表格造成的效果，以及结构感知分块的样子：

用两种方式对一页合同进行分块：固定大小分块把罚则表格切成了两半，而结构感知分块则保持整个章节完整，并携带来源、版本和可见权限等元数据

Acme 从中得到了两个教训。第一，按文档类型选择分块策略，而不是对整个语料库只用一种。第二，在摄取时附加元数据（关于文本块的信息，如来源、页码、版本和允许访问的组）。元数据让你能够过滤掉 v3、执行权限控制，并在之后引用页码。事后补加要困难得多。

什么是嵌入？向量搜索如何使用它？

嵌入模型将文本转换成向量（一个固定长度的数字列表），使含义相近的文本获得相近的向量。在 Google Cloud 上，

gemini-embedding-001

默认返回 3,072 个数字，而

output_dimensionality

参数允许你请求更少的数量以节省存储空间。该 API 还支持

task type

：你使用

RETRIEVAL_DOCUMENT

嵌入文本块，使用

RETRIEVAL_QUERY

嵌入问题，使每一方都针对其角色进行了优化。

嵌入会将含义相似的文本放在相近的位置：关于延迟交付罚款的问题会落在罚则条款旁边，向量搜索通过余弦相似度返回其最近邻

向量搜索将问题嵌入并向量最接近的文本块，通常以余弦相似度（两个向量指向同一方向的接近程度）来衡量。将问题与每个文本块进行比较称为精确搜索或 k 近邻（kNN）搜索。这种方法准确，但随着语料库的增长速度会变慢。近似最近邻（ANN）搜索使用更智能的索引，只检查一小部分向量，用少量精度换取大幅速度提升。Google 的 Vector Search 构建在 ScaNN 之上，这是 Google Research 开发的一种 ANN 算法。

为什么仅靠向量搜索还不够？

嵌入擅长理解语义，但不擅长精确字符串。当你查询“第 14.2 条”或产品代码“PL-500”时，向量搜索可能返回主题相关但引用了错误条款的文本块。关键词搜索（也称为稀疏搜索或基于分词的搜索，通常使用 BM25 等算法评分）则相反：对精确词语非常精准，但无法识别同义词。

混合搜索同时运行两者并合并两个排序列表。Google Cloud 上的 Vector Search 直接支持这一点，并使用倒数排名融合（RRF）合并结果，该方法会奖励在任一列表中排名靠前的文本块。然后，重排序器将问题和每个入围的文本块一起读取，并评估该文本块回答问题的程度。Google Cloud 上的排名 API 可以完成这项工作，RAG Engine 文档描述其延迟非常低，低于 100 毫秒。

检索漏斗：关键词搜索和向量搜索各自返回约五十个候选结果，倒数排名融合将它们合并，排名模型对它们重新排序，只有最好的五个会送达模型

廉价而宽泛的搜索负责寻找候选结果；精确的步骤只在入围名单上运行。在 Acme，关键词搜索解决了引用条款编号的问题，重排序将正确的 Northmart 章节排到了第一位。

溯源和引用如何保证答案的可靠性？

检索为模型提供了好的素材，但并不能强制模型使用它。溯源是一种规范，用于检查答案中的每个论断是否都有检索到的文本块支持，而引用则让这种支持对读者可见。

Google Cloud 正是为此提供了溯源检查 API。你发送一个候选答案及其应依据的事实，它会返回一个 0 到 1 之间的支持度评分，以及每个论断的引用。你可以设定一个阈值，低于该阈值的答案将不按原样展示。

为答案提供依据：草稿答案中的每条声明都链接到支持它的文本块；其中一条声明没有支持，因此支持得分低于阈值，该声明会在用户看到之前被移除

Agent 系列将同样的规则应用于数字，由代码检查作者引用的每一个数字（由路由器决定，让代码选择路径）。模型负责撰写，而由模型之外的东西决定答案能否展示。

Google Cloud 提供哪些托管选项？

你很少需要自己构建所有这些。截至 2026 年 10 月，有四个层级可供选择，并且需要注意一次更名：以前称为 Vertex AI Search 的产品正在更名为 Agent Search，而原来的 Vertex AI 平台现在更名为 Gemini Enterprise Agent Platform。较旧的博客文章和代码示例仍在使用旧名称，API 端点（

discoveryengine.googleapis.com

）没有变化。

在 Google Cloud 上构建检索的四种方式，从构建最少到控制最多：Gemini Enterprise 数据存储、Agent Search、RAG Engine，以及由嵌入、Vector Search、排序 API 和检查依据 API 组成的自有管道

  • Gemini Enterprise 数据存储。 连接器可将 SharePoint、Google Drive、Box 和其他来源接入 Gemini Enterprise，并保留源系统的权限。当用户是在 Gemini Enterprise 应用中工作的员工时，选择它。第 5 部分深入介绍连接器。
  • Agent Search。 通过 API 提供托管式摄取、解析、分块、搜索、排序和答案生成。当你自己的应用或 Agent 需要搜索或依据支持（例如为供应 Agent 提供的合同搜索工具），并且希望由 Google 运行管道时，选择它。
  • RAG Engine。 围绕语料库构建的托管式 RAG 服务，你可以选择分块大小、解析器和向量数据库（默认为其自有的托管数据库，也可以是 Vector Search、Pinecone，或预览版中的 Weaviate）。当你想控制文档的准备方式时，选择它。
  • 自有管道。 单独使用的构建模块：嵌入 API、Vector Search、排序 API 和 检查依据 API。当你的数据或规模不寻常，或者检索质量本身就是你的产品时，选择它。

一个需要坦承的缺口：截至 2026 年 10 月，RAG Engine 文档说明新项目必须加入允许列表才能在 us-central1、us-east1、us-east4 和 europe-west1 中使用，且其他几个区域仍处于预览阶段。在承诺设计方案之前，请先查看区域表。

我的看法：从最左边开始，只有当评测显示检索问题无法由更简单的选项解决时，才向右移动。每向右一步，都意味着你离开后客户需要维护更多代码。

我如何知道检索是否正常工作？

将检索与答案分开评估。如果你只对最终答案打分，就无法判断错误答案究竟来自糟糕的检索还是糟糕的生成，结果会调错地方。

方法很简单。与数据负责人一起，写下 30 到 50 个真实问题，并为每个问题标注应当回答它的文本块。运行你的检索器并记录其返回结果。然后计算两个数字：

  • Recall@k（召回率@k）。 正确文本块出现在前 k 个结果中的问题比例。如果它没有被检索到，模型就无法使用它。
  • 平均倒数排名（MRR）。 正确文本块位置的倒数（第一名记 1，第二名记 0.5，未出现记 0）的平均值。它告诉你正确文本块排得有多靠前。

只有在检索质量达标后，才对答案本身进行评分，评估其正确性和有据性，这正是 agents 系列中 Proving it works, evals that gate releases 一文所构建的发布门禁。

为什么 RAG 的答案会出错？

当客户向我展示一个错误答案时，我会和他们一起走一遍这棵决策树。它能把“AI 出错了”转化为一个具体、可修复的原因：

诊断错误的 RAG 答案：首先询问正确的文本块是否被检索到；如果没有，检查它是否在索引中，然后再检查排序；如果被检索到了，则检查答案是否遵循了它

  • 幻觉。 正确的文本块被检索到了，或者没有检索到任何相关内容，但模型还是写出了看似合理的内容。通过有据性检查以及一条指令来修复它：当支持依据薄弱时，回答“我找不到相关内容”。
  • 数据过时。 索引比数据源更旧。每个连接器和摄取任务都有同步计划；今天早上签署的合同在下一次同步之前是不可见的。在每条引用中显示文档日期，让用户能够看到。
  • 权限。 这是企业环境中最关键的问题。如果你使用单一服务账号摄取文档，索引就不再知道谁有权读取每个文件，而 Agent 的每个用户现在都能看到该账号可见的一切内容。例如，RAG Engine 的 Google Drive 导入是通过与服务账号共享文件夹来实现的。相比之下，Gemini Enterprise 连接器会根据源系统的访问控制列表来校验登录用户。在摄取任何内容之前，先确定你需要哪种行为。
  • 解析或分块不佳。 表格被压平或被切成两半，就像 Northmart 的例子那样。直接查看文本块本身，而不仅仅是看分数。

    {"q": "Who books carrier slots?", "expected": "sop_p2",
     "got": ["sop_p4", "sop_p2", "spec_pl500_p1"]},
    {"q": "Shelf life of Acme Pure 500ml?", "expected": "spec_pl500_p1",
     "got": ["spec_pl500_p2", "spec_pl250_p1", "sop_p2"]},
    {"q": "Notice period to end the Northmart deal?", "expected": "northmart_v4_p19_s22",
     "got": ["northmart_v3_p18_s22", "northmart_v4_p19_s22", "northmart_v4_p7_s14.2"]},
]

def recall_at_k(rows, k):
    hits = sum(1 for r in rows if r["expected"] in r["got"][:k])
    return hits / len(rows)

def mrr(rows):
    total = 0.0
    for r in rows:
        if r["expected"] in r["got"]:
            total += 1 / (r["got"].index(r["expected"]) + 1)
    return total / len(rows)

print(f"recall@1 = {recall_at_k(results, 1):.2f}")
print(f"recall@3 = {recall_at_k(results, 3):.2f}")
print(f"MRR      = {mrr(results):.2f}")
for r in results:
    if r["expected"] not in r["got"]:
        print("MISSED:", r["q"])

你应该会看到

recall@1 = 0.25

,

recall@3 = 0.75

和

MRR = 0.50

，其中保质期问题未被命中。然后尝试两件事：

  • 看最后一个案例。旧的 v3 合同排在 v4 之上。把 northmart_v3_p18_s22 从列表中移除——这正是对版本做元数据过滤的效果——然后观察 MRR 上升。
  • 就你熟悉的文档写五个问题，并为每个问题附上应该能回答它的文本块。这就是一个真实检索测试集的起点。

项目中可能出什么问题

  • 在测量之前就承诺准确率。 先就测试集和目标达成一致。
  • 把所有东西都导入。 文档越多，意味着近似重复和过期版本越多。先从第一个用例所需的内容开始。
  • 把 FDE 当作数据所有者。 你能发现一份过期合同；只有商务团队才能将其停用。在第 2 部分的项目简报中，为每个数据源指定一位负责人。
  • 用调整提示词来修复检索问题。 如果召回率低，任何提示词都帮不上忙。

我现在会做什么

  • 对第一个用例的文档运行五项就绪检查，并记录每一项失败。
  • 解析十份有代表性的文档，并在索引其余文档之前亲自阅读这些文本块。
  • 在导入时附加来源、页码、版本、负责人和权限元数据。
  • 与数据负责人一起构建一个包含 30 个问题的检索测试集，并跟踪 recall@5 和 MRR。
  • 从最符合需求且管理程度最高的方案开始，只有当数据表明需要时，才添加混合搜索、重排序或接地检查。

我们学到了什么？

  • 当 AI Agent 能够找到数据、读取数据、确信数据是最新的、知道谁负责它，并遵守谁可以查看它时，数据才算就绪。
  • RAG 在提问时从你自己的文档中查找相关段落，并将它们连同问题一起提供给模型，因此答案可以引用其出处。
  • 分块策略应按文档类型选择，而来源、版本和许可群组等元数据必须在导入时附加。
  • 向量搜索擅长语义、不擅长精确字符串，因此混合搜索加上重排序通常比单独使用任何一种搜索效果更好。
  • Google Cloud 提供四个层级，从 Gemini Enterprise 数据存储到自建流水线，从最符合需求且管理程度最高的方案入手是值得的。
  • 在对答案评分之前，应先用 recall@k 和 MRR 来衡量检索效果，而错误答案应通过诊断树追溯到具体原因。

接下来是什么？

检索只是集成的一种。第 5 部分：企业集成、API、连接器和身份中，我们将把 Agent 连接到 Acme 的其余资产：REST API 及其身份验证方式、Gemini Enterprise 中的 SharePoint、Box 和 Google Drive 连接器、保持权限完整性的身份标准（SAML、OIDC 和 SCIM），以及 MCP 服务器为何正在成为集成层。
