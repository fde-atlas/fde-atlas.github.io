使用 Vite 的 React TypeScript 演示：面向客户的六个步骤

原标题：React TypeScript demo with Vite: six steps for clients

FDE Times · 2026-10-08 · 约 7 分钟读完

摘要

这篇实操指南面向前沿部署工程师，讲解如何在客户一台没有 Node 的裸机上，用 Vite 和 React TypeScript 在几小时内搭建一个可交付的文档问答演示。文章分六步展开：确认 Node 版本（20.19+ 或 22.12+）、用 react-ts 模板脚手架、先写类型契约、集中管理 API 调用、接入界面状态、构建前用 tsc --noEmit 做类型检查。核心提醒包括：Vite 只转译不检查类型；VITE_ 变量会被打进浏览器代码，绝不能放 API 密钥；useState 应从带类型的初始值推断类型。作者还建议在简历上用具体成果而非技术清单来展示这类能力。

要点

  • Vite 要求 Node.js 20.19+ 或 22.12+，先查版本再动手。
  • Vite 只转译 TypeScript，构建前必须运行 tsc --noEmit 并故意埋错验证。
  • VITE_ 变量会打包进浏览器代码，API 密钥必须放在后端。
  • 先写 types.ts 作为前后端契约，API 调用集中在 api.ts 便于修改。
  • 简历上应写具体成果（如几小时内从裸机到可部署构建），而非罗列技术。

六个步骤可以让客户演示从一台没有 Node 的笔记本电脑，变成一个通过类型检查、构建干净且没有 API 密钥泄露到打包文件中的项目。

简要说明

  • Vite 需要 Node.js 20.19+ 或 22.12+。在做任何其他事情之前，先检查 node -v。
  • Vite 只转译 TypeScript，并不做类型检查。在构建到 dist 之前先运行 tsc --noEmit，并故意埋一个错误，以确认该命令能捕获它。
  • 每个 VITE_ 变量都会被打包进客户端代码，因此 API 密钥应放在后端。

周二，客户问：“我的团队周五能试用吗？”基于他们内部文档回答问题的后端已经可以运行了，但客户不读 JSON。他们需要一个文本框、一个按钮，以及屏幕上显示的答案。他们分配给你的工作机是台裸机，甚至连 Node 都没有。

前沿部署工程师经常遇到这种情况，而它所需要的技能并不是高级 React 技巧，而是在几个小时内从零开始得到一个干净的构建，并且方式要让同事下周能够接手。下面的六个步骤以这样一个例子为例，从第一条命令一直讲到

dist

文件夹。

为什么选择 Vite 而不是框架？

React 官方文档建议使用框架来启动新应用。它也坦率地指出了自行搭建的成本：灵活性更高，但你需要自己选择路由、数据获取和其他常见模式的工具。

对于一个单屏演示来说，这种成本几乎为零，因为你暂时既不需要路由，也不需要复杂的数据获取策略。Vite 提供了一个能快速启动的轻量脚手架。如果演示发展成多页面的产品，那时再重新考虑框架的问题。

第 1 步：在输入任何其他内容之前，先安装合适的 Node

Vite 要求 Node.js 20.19+ 或 22.12+。在裸机上，安装 22.12 或更高版本，可以使用官方安装程序，如果客户的机器允许，也可以使用 nvm 之类的版本管理器。然后检查：

node -v
npm -v

如果

node -v

打印出的版本低于要求，请停下来立即修复。Node 版本错误如果在后面的步骤中才暴露出来，往往看起来像 Vite 错误，你可能会浪费一个下午去追查错误的问题。

第 2 步：一条命令搭建脚手架，一条命令运行

Vite 使用

npm create vite@latest

来搭建项目。带 TypeScript 的 React 模板是

react-ts

（还有

react-compiler-ts

):

npm create vite@latest client-demo -- --template react-ts
cd client-demo
npm install
npm run dev

默认的

dev

脚本只是

vite

，它会在

localhost:5173

启动一个开发服务器。示例页面出现后，基础设施就完成了。如果客户已经有一个用 JavaScript 编写的 React 项目，添加类型定义即可，不必从头开始：

npm install --save-dev @types/react @types/react-dom

.

第 3 步：在编写 UI 之前先写数据类型

在动屏幕之前，先创建

src/types.ts

。这个文件是后端与界面之间的契约：

export type Status = "idle" | "loading" | "done" | "error";

export type Answer = {
  text: string;
  sources: string[];
};

React 文档指出，声明的 prop 类型既能用于检查正确性，也能作为直接显示在编辑器中的文档。对 FDE 来说，第二个好处同样重要：接手的人打开文件就能看到 API 返回什么，而无需实际调用它。

第 4 步：把所有 API 调用集中在一处

创建

src/api.ts

。所有与网络相关的代码都放在这里，这样当客户在周四更改后端地址时，你只需修改一行代码：

import type { Answer } from "./types";

// Just the backend address, not a secret
const API_URL = import.meta.env.VITE_API_URL;

export async function readAnswer(question: string) {
  const res = await fetch(`${API_URL}/answer`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question }),
  });
  if (!res.ok) throw new Error(`API returned ${res.status}`);
  return (await res.json()) as Answer;
}

（注释内容为：“只有后端地址，不是密钥。”错误信息为“API returned”加上状态码。）

以及项目根目录下的

.env

文件：

VITE_API_URL=http://localhost:8000

有一个细节至关重要：

VITE_

变量会直接打包进在浏览器中运行的代码里，Vite 文档明确说明它们不得包含 API 密钥等敏感信息。模型或客户系统的密钥应放在后端。UI 只需要知道地址。

第 5 步：把 API 接入界面

现在才轮到

src/App.tsx

，模板已经创建好了它。包含 JSX 的文件必须使用

.tsx

扩展名，所以不要把它重命名为

.ts

。将其内容替换为以下代码：

import { useState } from "react";
import type { FormEvent } from "react";
import { readAnswer } from "./api";
import type { Answer, Status } from "./types";

type UiState = { status: Status; answer: Answer | null };
const initial: UiState = { status: "idle", answer: null };

export default function App() {
  const [ui, setUi] = useState(initial);

  async function handleSubmit(e: FormEvent) {
    e.preventDefault();
    const form = new FormData(e.currentTarget as HTMLFormElement);
    const question = String(form.get("question") ?? "");
    setUi({ status: "loading", answer: null });
    try {
      const answer = await readAnswer(question);
      setUi({ status: "done", answer });
    } catch {
      setUi({ status: "error", answer: null });
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <textarea name="question" rows={4} />
      <button disabled={ui.status === "loading"}>Ask</button>
      {ui.status === "error" && <p>Could not reach the API, please try again.</p>}
      {ui.answer && <p>{ui.answer.text}</p>}
    </form>
  );
}

（按钮文字是“提问”；错误行是“无法连接 API，请重试。”）

注意这一行

useState(initial)

。这个 hook 会从初始值推断类型。如果写一个不带类型的

useState("idle")

，TypeScript 会推断为

string

，因此像

"loadng"

这样的拼写错误就会漏过去。写成

useState(null)

的话，类型就是

null

，你就无法把答案赋给它。

最优雅的解决方法是给这个 hook 一个已经带有类型的初始值。

initial

被声明为

UiState

，因此

status

只接受联合类型中的四个值，而

answer

可以接受

null

或一个

Answer

。如果你更倾向于使用多个独立的状态，标准做法是把

Status

直接作为类型参数传给

useState

.

把两个状态放在同一个对象里还有另一个好处：绝不会出现状态是“error”而旧答案还显示在屏幕上的情况。保存文件，回到

localhost:5173

，输入一个问题并点击。如果后端在运行，答案就会出现。关掉后端，错误行就会出现。客户会两种情况都试，所以你也必须都测到。

第 6 步：开发服务器能运行不代表代码正确

这是最大的陷阱。Vite 只转译 TypeScript 文件，并不检查类型。开发服务器会毫无怨言地提供一个满是类型错误的文件，你只有在客户恰好点到出错的分支时才会发现问题。这就是为什么 Vite 文档建议在构建生产版本时运行

tsc --noEmit

：

npx tsc --noEmit
npm run build

不要仅仅因为类型检查命令没有报告任何问题就相信它。验证一下：在给 status 赋值的地方输入

"loadng"

，然后再次运行。如果命令依然沉默，那它很可能没有检查到 UI 代码。在有多个

tsconfig

文件的项目中，直接把它指向覆盖

src

代码的那个文件，并使用

-p

标志，直到故意设置的错误出现。

然后打开

package.json

并检查

build

脚本是否在

vite build

之前运行类型检查。如果没有，就把它加上，这样团队里任何人都不会忘记。构建输出默认进入

dist

文件夹：一组静态文件，放到 Web 服务器上供客户在浏览器中打开。

那些会毁掉周五演示的错误

最常见的错误是把开发服务器当作证明。在 localhost 上运行的页面只能说明浏览器能运行这些代码，并不能说明类型是正确的。紧随其后的是信任一个报告通过却从未见过它真正捕获过任何错误的类型检查命令。

最危险的错误是把密钥放进

VITE_

变量里，“只是为了快一点，反正只是个演示”。演示包会通过邮件和群聊转发，密钥也随之传播。做一次就足以失去客户安全团队的信任。

两个较小的错误会耗费数小时：在

.ts

文件里写 JSX，以及让

useState

从裸字符串推断类型，或在有多种可能取值的状态时使用

null

。只要你给它机会，TypeScript 能捕获这两个问题。

这项技能在简历上处于什么位置？

阅读 FDE 职位描述时，留意诸如“构建原型”“面向客户的演示”或“快速迭代”之类的措辞。如果出现了这些词，这六个步骤正是你应该能够展示的内容，而展示结果比罗列技术更有说服力。

在简历上，与其写“精通 React、TypeScript”，不如写一行带成果的内容：在一次会话中从裸机搭建出文档问答演示并完成生产构建，API 层独立分离，后端可以更换而无需改动 UI，密钥保存在服务器端。一个恰好包含

types.ts

,

api.ts

,

App.tsx

结构的公开仓库，比任何形容词都更能说明问题。

下次客户问“周五能试用吗？”，正确的答案不是“可以”。而是在周四下午发出一个指向

dist

文件夹的链接。
