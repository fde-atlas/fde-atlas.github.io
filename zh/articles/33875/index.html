企业 AI 中的数据访问谈判

原标题：The data-access negotiation in enterprise AI

Mayur Patil · 2026-10-16 · 约 5 分钟读完

摘要

作者基于前沿部署工程经验指出，企业 AI 项目初期最大的延误往往不是技术，而是数据访问审批。他把审批视为与数据所有者、安全、平台、合规四方的谈判，主张为每个用例撰写两到四页的访问请求文档，并给出只读起步、脱敏数据、审批内置到工具、提前预约安全评审等加速策略。文中引用 SAP Agent Gateway 与 Claude Code 的 MCP Tasks、Elicitations 说明代理权限仍是人为决定，并以 Palantir FDE 案例说明表面阻塞背后的真实需求。

要点

  • 企业 AI 项目前三周常耗在等待数据访问审批上。
  • 审批实为四场谈判：数据所有者、安全、平台、合规各有顾虑。
  • 建议按用例写两到四页文档，分节回应四方关切。
  • 加速策略：只读起步、脱敏数据、审批写入工具而非提示词。
  • 若两周内无法达成审批，可建议暂停项目。

问一位工程师是什么拖慢了企业 AI 项目，你会听到模型、框架或集成。问一位做过前沿部署工作的人，答案却不同。头三周都耗在等待上：等服务账号、等数据共享审批、等一场没人安排的安全评审——因为没人知道需要它。

如今我把这种等待视为每个项目的第一个工程问题。它是一场谈判，有固定的形态，你可以谈得好，也可以谈得糟。

为什么这件事越来越难

AI Agent 改变了安全团队提出的问题。检索聊天机器人只是读取，而 Agent 会执行操作：更新记录、发送消息、触发工作流。

让这一切变得容易的协议正在快速到来。十月下旬，Claude Code 的 CLI 增加了 MCP Tasks（公开测试版），允许工具运行长时间任务；还增加了 Elicitations，允许工具在任务中途暂停，向人请求确认（Upstash）。SAP 通过一个具备发现、允许列表和审计功能的 Agent Gateway，将入站 Agent2Agent 调用正式全面开放，并且明确指出：“发现本身并不授予调用某个 Agent 的权限。”（SAP Architecture Center）。

这句话就是整场谈判的缩影。技术让触达变得容易，但权限仍然是人的决定，而且必须有人把它请求好。

你实际在与之谈判的四个人

“获取数据访问权限”背后隐藏着四场独立的对话。每个人都有不同的担忧。

  • 数据所有者通常来自业务部门而非 IT，他们担心滥用，也担心被追责。他们需要确切知道是哪些字段、用于什么目的、使用多久。
  • 安全评审员担心的是影响范围。系统能触达什么，如果它被攻破或仅仅出错，会发生什么。
  • 平台或基础设施团队担心的是运维负担。多一个服务账号、多一条网络路径、多一个要在周六打补丁的东西。
  • 法务、隐私或合规团队担心数据流向何处，尤其是流向托管在辖区之外的模型。

大多数延误都源于在一封邮件里向这四个人同时要“访问权限”。而他们每个人需要的是不同的文档。

放大

关闭

获取数据访问权限是四场谈判。数据所有者担心滥用和追责，需要确切的字段、用途和有效期。安全团队担心影响范围，需要明确的负责人和受限的写入权限。平台团队担心运维负担，需要每个系统一个身份。合规团队担心数据流向，需要明确模型托管位置和数据保留策略。一份请求，每人一个章节，并列出你不需要的字段。

我写的访问请求

在提出任何请求之前，我会为每个用例写一份简短的文档。它发给所有四个人，但每个章节都是为其中一位而写的。

  • 目的与工作流程。 用一段话说明业务任务、目前由谁执行，以及将发生哪些变化。
  • 数据清单。 列出具体的表、字段或文档集，标注读取或写入，并说明每项的理由。明确列出我们不需要的字段。删减列是加快审批通过的最快方式。
  • 操作边界。 列出系统可执行的每一项操作，标注为无人值守、需人工确认或不允许。对记录系统的写入操作一律从“需确认”开始。
  • 身份。 每个系统和环境使用一个服务身份，绝不使用共享技术账户，并授予最小角色权限。
  • 模型托管。 使用哪个模型、托管在哪里、依据什么条款，以及是否保留任何数据。在数据驻留有要求的地方，说明哪些部分运行在区域内或本地托管的模型上。
  • 日志与审计。 记录什么内容、谁可以查看、保留多久。业务负责人能看懂的日志，在评审中比只有工程师才能解析的日志更有价值。
  • 到期与复审。 访问权限设定到期日期，并在交接时进行复审。

它只有两到四页，却能节省数周时间。

加快审批通过的模式

从只读切片开始。 先在只读权限上验证工作流程，由人工执行最终操作。待评测表明该步骤可靠后，再申请写入权限。

构建阶段使用脱敏或合成数据，评测阶段使用真实数据。 许多安全团队会快速批准脱敏的开发数据，并单独批准真实数据用于一次有评分、有日志记录的评测运行。

把审批放进工具里，而不是提示词里。 系统提示词中的“更改记录前务必询问”只是对模型的一个请求。而一个没有记录在案的确认就不会继续执行的工具，才是评审人员真正可以测试的控制措施。在客户端支持的情况下，引导式确认（Elicitations）是一种实现方式；简单的审批队列是另一种。

提前预约安全评审。 在第一周就弄清评审流程是什么、队列有多长。届时就基于设计草案预约评审，即使之后还会修改。

把评测结果带到评审会上。 当评审人员能看到系统出错的频率以及出错时的后果时，他们的态度就会放宽。

卡点通常是什么

我反复看到的一个模式：表面上的阻碍并非真正的阻碍。LinkedIn 上广为流传的一篇总结 Palantir FDE 实践经验的文章讲述了一位数据质量工程师将一次数据迁移阻拦了约一年的故事。她真正的需求是一种肉眼查看数据行的方式。一旦有人为她构建了一个查看器，她在几天内就批准了迁移（Glenn Santos, LinkedIn）。

在我自己的项目中，隐藏需求通常是以下三种之一。数据所有者希望在数据被使用之前先看到输出结果。安全团队需要一个具名的人来对服务账户负责。或者合规部门需要一句话说明模型在哪里运行。问问每个人怎样才会愿意点头答应，并把这些记录下来。

为此做规划，为此定价

获取访问权限的时间不是计划中的富余量，它就是第一道关卡的计划本身。在我的项目中，只有当数据所有者的批准落实为书面形式、安全审查已预约或已完成、且行动边界已达成一致时，准备阶段才算通过。如果这些在大约两周内无法达成，正确的建议可能是暂停。关于这如何与商业条款相关联，我在为 FDE 项目定价中有详细说明。

把它当作一项技能来学习

这就是为什么我在 AIXL Academy 前沿部署 AI 工程培训班中，把访问权限谈判作为一项正式技能与代码一起教授。这是大多数工程师从未被要求做过的工作，也是决定他们的代码能否真正运行起来的关键。日期和费用信息见 AIXL Academy 页面。这背后的方法论在前沿部署工程中有阐述。

常见问题

为什么企业 AI 项目要等这么久才能获得数据访问权限？

因为“访问权限”实际上是四项审批，分别来自数据所有者、安全、平台和合规部门，每一方关注的重点都不同。一个笼统模糊的请求无法满足其中任何一方。

AI 数据访问请求应该包含哪些内容？

用途、字段级数据清单、行动边界、每个系统一个服务身份、模型托管与数据保留、日志与审计，以及有效期。

如何让 AI Agent 更快通过安全审查？

从只读权限开始，构建阶段使用脱敏数据，把人工审批放进工具而不是提示词中，在第一周就预约审查，并带上评测结果。

AI Agent 是否应该获得对记录系统的写权限？

一开始不应该。先从由人工确认每次写入开始，只有当评测表明某些步骤可靠时，才允许无人值守的写入。
