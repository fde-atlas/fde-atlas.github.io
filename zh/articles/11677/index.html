Sarathi-Serve（分块预填充）（2024）FDE 解读

原标题：Sarathi-Serve (chunked prefill) (2024) Explained for FDEs

FDE Interviews · 2026-10-18 · 约 4 分钟读完

摘要

Sarathi-Serve 论文解析：LLM 推理服务中，长 prompt 的 prefill 会阻塞所有正在生成的响应，造成卡顿。该方案用分块 prefill 加无阻塞批处理，把 prefill 拆成小块与 decode 混合调度，兼顾吞吐与延迟。在严格 P99 延迟目标下，Mistral-7B 承载能力达 vLLM 的 2.6 倍，Yi-34B 达 3.7 倍，并让 Falcon-180B 在普通以太网上做流水线并行成为可能。对 FDE 的启示：客户反馈“回答中途卡住”往往源于调度器优先处理他人长 prompt；应检查服务引擎是否开启分块 prefill 及 token 预算设置，批大小上限对此几乎无影响，RAG 等长 prompt 场景受影响最大。

要点

  • Prefill 是计算瓶颈，decode 是内存瓶颈，二者调度冲突导致生成卡顿。
  • 分块 prefill 把长 prompt 拆成小块，与 decode 混合进每轮迭代。
  • 严格 P99 延迟下，承载能力比 vLLM 高 2.6 至 3.7 倍。
  • Token 预预算决定延迟取舍：512 严格，2048 宽松。
  • 批大小上限对卡顿几乎无影响，问题根源是 prefill 长度。

一分钟读懂这篇论文

每个请求都有两个阶段。Prefill（预填充）一次性处理整个提示词；它是计算受限的，即使只有一个请求也会让 GPU 饱和。Decode（解码）每次迭代为每个请求生成一个 token；它是内存受限的，因为每次迭代都要读取全部权重却只做很少的算术运算，所以把多个解码请求批量处理几乎不增加成本。

像 vLLM 和 Orca 这样的服务器在迭代级别进行批处理，并积极接纳新请求，优先运行它们的预填充，因为这样能扩大下一次解码批次。代价是生成停顿：当处理一个数千 token 的提示词时，所有正在进行的响应都会暂停，有时长达数秒。尾部请求的 token 间隔时间（TBT）随负载上升。较早的请求级批处理可以避免停顿，但会让 GPU 利用不足。因此运营者不得不在吞吐量与延迟之间权衡。

Sarathi-Serve 用两个机制消除了这种权衡。分块预填充把长提示词拆成几百个 token 的块，在多次迭代中计算。无停顿批处理按固定顺序构建每次迭代：先放所有正在运行的解码，再放任何部分完成的预填充，然后是新请求，直到达到token 预算。由于解码迭代有空闲的算力，加入几百个预填充 token 几乎不会延长迭代时间，任何正在进行的响应都不必等待整个提示词。迭代时间也变得均匀，这消除了模型分布在多台机器上时的流水线气泡。

token 预算决定了权衡：严格延迟目标下用 512 个 token，宽松目标下用 2,048 个。Sarathi-Serve 基于 vLLM 构建，在严格的 P99 TBT 目标下，对 Mistral-7B 的承载负载是 vLLM 的 2.6 倍，对 Yi-34B 是 3.7 倍，并让基于普通以太网的流水线并行对 Falcon-180B 变得可行。

研究笔记：问题、方法与结果

在严格的 P99 token 间隔时间目标下，两块 A100 上运行 Yi-34B 时每秒处理的查询数超过 vLLM

当一个完整提示词未经分块加入解码批次时，迭代时间比纯解码批次延长多少

每块 512 个 token 的分块带来的额外预填充时间；在 2,048 时接近于零

LLM 服务器为了吞吐量在每次迭代时对请求进行批处理，并积极接纳新提示词。新提示词的预填充可能耗时数秒；在此期间，所有正在进行的响应都停止生成 token。较小的批次可以避免这些生成停顿，但会浪费 GPU。在使用流水线并行时，不均匀的迭代还会让各阶段空闲。

解码迭代是内存受限的，算力处于空闲状态。把每个提示词拆成块，每次迭代由所有正在运行的解码加上预填充块组成，直到达到固定的 token 预算（无停顿批处理），这样新请求加入时不会让任何人暂停，且各迭代耗时大致相同。根据延迟目标选择预算。

在严格的尾延迟目标下，与 vLLM 相比，单张 A100 上 Mistral-7B 的服务容量提升了 2.6 倍，两张 A100 上 Yi-34B 提升了 3.7 倍。在两个节点间采用流水线并行时，在严格目标下 Falcon-180B 的服务容量比 vLLM 的混合并行方案高出 3.6 倍。

这对 FDE 为什么重要

用户能感知到两种延迟：首 token 时间，以及后续流式输出的流畅程度。当客户说“忙的时候答案会在句子中间卡住”时，原因往往是调度器为了运行别人的长 prompt 而暂停了解码。

询问服务引擎如何接纳 prefill。 分块 prefill 现已是主流引擎的标准选项；它是否开启、token 预算是多少，对高负载下的尾延迟的影响比大多数其他设置都大。

批大小上限解决不了问题。 论文发现，在严格的延迟目标下，vLLM 的容量在最大批大小为 32、64 和 128 时几乎没有变化，因为卡顿来自 prefill 长度，而不是批大小。

长 prompt 会让情况更糟。 prompt 达数千 token 的 RAG、文档和 agent 工作负载正是 prefill 干扰最严重的地方；论文中 arXiv 摘要工作负载（prompt 中位数为 7,059 个 token）的容量最低。
