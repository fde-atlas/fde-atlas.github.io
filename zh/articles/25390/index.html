MCP导入的推进方法｜FDE在现场实践的5个步骤与设计要点

原标题：MCP導入の進め方｜FDEが現場で実践する5ステップと設計の勘所

FDE総研 · 2026-10-01 · 约 10 分钟读完

摘要

这篇来自 FDE総研 的日文文章由前沿部署工程师视角讲解 MCP（Model Context Protocol）的落地方法。MCP 是 Anthropic 于 2024 年 11 月发布的开放标准，获 OpenAI、Google、Microsoft 支持，可将 AI 与工具的集成从 N×M 问题简化为每个工具一个服务器。文章指出把 API 端点一对一转成工具通常行不通，应按业务单位重新设计，并提出“业务选定→数据盘点→工具设计→评测→生产部署”五步法，建议从只读、低风险场景起步。安全方面强调提示注入、工具污染、权限过大和令牌处理四大风险，主张最小权限、人工审批，并在 PoC 阶段就引入安全团队。

要点

  • MCP 是 Anthropic 发布的开放标准，OpenAI、Google、Microsoft 均已支持。
  • 采用五步导入法：业务选定、数据盘点、工具设计、评测、生产部署。
  • 首个用例应选只读、低风险业务，写入类操作放到后续阶段。
  • 工具设计要点是数量少、说明清晰、权限窄，按业务单位而非 API 端点划分。
  • 主要风险为提示注入、工具污染、权限过大与令牌误用，需最小权限加人工审批。

MCP是什么，为什么在企业中的导入不断推进？

MCP是连接AI Agent与内外部工具和数据的开放标准。由于能降低单独集成的开发成本，企业在采用上不断扩大。

MCP（Model Context Protocol）是Anthropic于2024年11月发布的协议。它将LLM应用访问文件、数据库、SaaS、内部API等外部上下文的方式进行了统一。发布后，OpenAI、Google、Microsoft等主要AI厂商也宣布支持。因此，MCP已不再被视为特定厂商的专有规范，而是作为行业的通用接口来对待。

MCP的基本结构是怎样的？

MCP由“主机、客户端、服务器”三层构成。通信使用JSON-RPC 2.0。

构成要素角色具体示例
主机用户操作的AI应用本体Claude Desktop、IDE、自研的Agent平台
客户端主机内与服务器一对一连接的组件主机生成的连接单元
服务器公开工具和数据的程序GitHub、Slack、内部DB的MCP服务器

服务器公开的功能主要有以下3种。

  • Tools：模型可调用的函数（创建工单、执行SQL等）
  • Resources：模型可引用的数据（文件、文档、记录）
  • Prompts：可复用的固定指令模板

通信方式（传输层）有两种。本地运行时使用stdio，远程运行时基本使用Streamable HTTP。

企业关注MCP的原因是什么？

企业最关注的原因在于，MCP能让AI与工具的集成从“N×M问题”中解放出来。一次构建的集成可以在多个AI应用中复用。

如果没有MCP，当AI应用有N个、工具有M个时，最多需要N×M种单独集成。只要遵循MCP，工具方只需准备一个MCP服务器，就能被多个支持的主机使用。作为FDE进入现场时，我印象中“希望Copilot和自研Agent都能使用相同的内部数据”这类需求很多。MCP在满足这类需求方面很有优势，我认为它是一种容易说明导入动机的技术。

MCP与传统的API集成有何不同？

MCP并非要取代API。它是在API之前增加一层“AI能够自行理解并调用的层”。

REST API和GraphQL是以人类开发者阅读文档并实现为前提的。而在MCP中，服务器会向客户端告知其工具的名称、说明和输入Schema。模型阅读这些说明后，判断何时使用哪个工具。

功能层面的差异在哪里？

最大的差异在于功能可以被动态发现，以及它是为模型调用而设计的。认证和执行机制本身仍继续使用API。

视角传统API集成MCP
调用主体开发者编写的代码LLM（经由主机）
功能发现阅读文档后静态实现通过tools/list等动态获取
接口单位端点Tools / Resources / Prompts
复用性每个集成对象单独实现在遵循规范的主机间通用
授权每个API各自的方式远程访问定义了基于OAuth 2.1的规范
主要关注点准确的请求与响应避免模型误用的说明与粒度

是否可以直接把API转化为MCP？

将API端点一对一转换为MCP工具的做法，在多数情况下并不奏效。需要以业务为单位重新设计工具。

现场常见的失败做法是，把数十个端点原样公开为工具。工具过多时，模型容易选错。说明文字会挤占上下文，往往导致精度和成本双双恶化。例如，像“搜索客户”“汇总返回客户的合同状态”这样，以用户实际想做的事情为单位来整合工具，通常会更稳定。

如何稳妥地推进MCP导入？

要稳妥推进，关键是把用例限定为一个。在此基础上，从只读开始逐步扩展的5个步骤是有效的。

MCP在技术上容易上手，但不少情况会停留在“先搭了个服务器”就止步不前。从FDE的角度，我建议按照能带来业务成果的顺序推进。

MCP导入的5个步骤是什么？

5个步骤是“业务选择→数据盘点→工具设计→验证→生产部署”。在每个步骤结束时设定完成条件非常重要。

步骤内容完成条件的标准
1. 选择用例挑选一个频率高、判断可由AI辅助的业务已确定目标业务、使用者和成功指标
2. 数据与系统盘点梳理所需的数据源、权限和现有API每个连接对象的认证方式和负责人明确
3. 工具设计与实现按业务单元设计 Tools/Resources，并实现服务器读取类工具能在本地运行
4. 评估与验证用代表性的问题集检验准确性、误用及失败时的行为评估集达到合格线
5. 生产部署与运营设计完善授权、日志、监控，并推广给目标用户与运营负责人确定了事故应对流程

应该如何选择第一个用例？

初期选择“以读取为中心”、“即使出错损失也较小”的业务比较安全。写入类操作留到第二阶段以后再做吧。

容易成为候选的是：内部知识检索、咨询记录摘要、数据分析的前期调研等。相反，像下单、汇款、向客户发送这类对外部产生影响操作，最好一开始就排除在外。就我个人的感觉而言，最初几周最重要的评估指标是“现场是否每天都在使用”。比起准确率的数字，是否被持续使用往往更能真实反映导入的成败。

工具设计需要把握的关键点是什么？

设计的关键在于“数量少、说明清晰、权限窄”这三点。让模型不产生困惑的设计，会直接体现在准确率上。

  • 控制工具数量：一个服务器公开的工具，仅限于必要的那些
  • 说明文字要按规格说明书来写：明确写出何时使用、何时不使用
  • 严格定义输入 schema：指定枚举类型和必填项，减少自由输入
  • 输出要摘要后返回：不要原样返回大量原始数据，而是整理成模型能处理的量
  • 用错误信息提示下一步行动：像“权限不足，请向管理员确认”这样，返回恢复的线索

在 MCP 导入中，FDE 承担什么样的角色？

FDE 承担着连接业务需求与 MCP 技术设计之间的桥梁角色。是不让项目止步于 PoC、陪伴到在现场落地生根的负责人。

Palantir 推广的 FDE（Forward Deployed Engineer，前沿部署工程师），是一种深入客户现场、负责从发现问题到实现与落地的职业。MCP 导入正是 FDE 的优势能够充分发挥的主题。因为即使协议本身很简单，“将哪些业务、用哪些数据、以什么权限交给 AI”，如果不理解现场是无法决定的。

FDE 承担的具体业务是什么？

FDE 的业务大致分为四类：需求梳理、工具设计、评估、内部推广。每一项都以与现场的对话为出发点。

领域FDE 的具体业务相关对象
需求梳理观察业务流程，决定交给 AI 的范围现场负责人、业务部门主管
工具设计将现有 API 和 DB 重组为按业务单元划分的 MCP 工具内部工程师、系统管理员
评估从现场的实际问题创建评估集，反复改进现场负责人、质量管理
推广与落地编写使用指南、举办学习会、收集反馈信息系统部门、管理层

对工程师个人有什么技能要求？

除了实现能力之外，还需要“将业务语言化的能力”和“设计安全机制的能力”。仅有协议知识是不够的。

技术方面，能够用 TypeScript 或 Python 的官方 SDK 实现 MCP 服务器、理解包括 OAuth 在内的授权机制是基础。不过，我认为作为 FDE 产生差距的关键，在于能否将现场的隐性知识落实到工具的说明文字和评估集中。MCP 相关经验，对于以 FDE 为目标的工程师来说，是一个容易成为“将 AI 实现到业务中”这一具体证明的作品集领域。

MCP 导入中需要注意的安全与运营课题是什么？

最大的风险是提示注入与过度权限的组合。必须采用最小权限和人工审批来控制损失的设计。

使用 MCP 后，模型可以读取外部数据、操作外部系统。在变得便利的同时，被攻击的面也扩大了。MCP 的规范本身也开始纳入安全相关的最佳实践。即便如此，留给运营侧设计的部分仍然很大。

典型的安全风险有哪些？

典型的风险有四个：注入、工具污染、权限过度授予、令牌处理不当。各自需要不同的对策。

风险内容主要对策
提示注入模型服从了读取的文档或邮件中嵌入的指令在写入类操作中加入人工审批、区分不可信输入
工具污染（Tool Poisoning）恶意服务器在工具的说明文字中植入非法指令用允许列表管理所使用的服务器，确认来源
过度权限服务器以管理员权限运行，能执行预期之外的操作最小权限的服务账户、按用户的授权
令牌处理不当将收到的令牌原样转用于下游 API按规范避免令牌传递（透传），使用针对目标资源的专用令牌

特别需要注意的是，“能读取内部数据”“能向外部发送”“会读取不可信输入”这三者集中在同一个 Agent 上的配置。这种组合容易导致数据泄露，建议在设计阶段就将其分开。

运营中容易忽视的课题是什么？

容易忽视的是：服务器泛滥、审计日志不足、对规范修订的跟进。运营比导入持续得更久。

  • 野服务器的泛滥：各部门各自搭建 MCP 服务器，就无法掌握谁在访问哪些数据。可以考虑用内部服务器登记簿或网关进行统一管理
  • 审计日志：如果不记录“谁的请求、哪个工具、用什么参数被调用”，事故发生时就无法追溯原因
  • 规范的修订：MCP 规范以带日期的版本持续修订。需要将 SDK 和服务器的更新计划纳入运营
  • 成本与延迟：工具的说明文字和大的响应会增加 token 消耗。定期盘点会有效果

从现场的实际感受来说，如果在 PoC 阶段就让安全负责人参与进来，正式部署时的返工会大大减少。正因为 MCP 是一种“连上就能用”的技术，决定连接到什么程度的判断，正是引入方大显身手之处。FDE 所处的位置，使其能够用技术和业务两种语言来解释这一判断。
