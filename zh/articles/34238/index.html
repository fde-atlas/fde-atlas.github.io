现场发现如何在数小时内进入产品路线图

原标题：How Field Findings Reach the Product Roadmap in Hours

Falkster.AI · 2026-11-25 · 约 10 分钟读完

摘要

Workday 在 2026 年 11 月 24 日的财报电话会上宣布，将前沿部署工程师纳入产品与技术团队，由产品负责人 Gerrit Kazmaier 直接管理。作者认为现场团队正变成产品的传感器网络：工程师带回客户真实需求，Deployment Agent 已响应超过 200 万次部署查询，日志本身就是产品难点的地图。最佳实践是把发现写成测试和 pull request，当天由产品负责人决定是否全量发布，同时客户数据与商业机密绝不外传。作者主张现场团队应向 CPO 汇报，并预测到 2028 年现场发现到修复的中位时间将缩短至 48 小时以内。

要点

  • Workday 将前沿部署工程师划入产品团队，而非销售或服务部门。
  • Deployment Agent 上线以来已响应超过 200 万次部署查询。
  • 现场发现应写成测试加 pull request，当天由产品负责人裁决。
  • 客户数据、规则与定价绝不随修复模式外传。
  • 作者预测 2028 年现场发现到修复中位时间低于 48 小时。

昨天，Workday 向投资者说明了其现场工程师的部署方向。Workday 是许多大型企业赖以运转的人力资源和财务软件的提供商。其产品与技术总裁 Gerrit Kazmaier 在财报电话会议上表示：“我们正在加大对产品与技术团队内部前沿部署工程师的投入。”

前沿部署工程师（FDE）是指驻场与客户合作、让软件在客户环境中顺利运行的工程师。大多数公司将其归入销售或服务部门，而 Workday 将他们置于产品部门之内。

随后他解释了原因。“我们为某一个客户解决问题所获得的经验，会直接回馈到面向所有客户的 AI Agent 中。”

我认为这句话描述了未来几年这一领域工作的定位。现场工作正在转变为产品的传感网络。它是一套仪器，告诉产品团队在客户那里真实发生了什么。而从传感器到修复之间的线路，已经缩短到可以用小时来衡量。

本文是《FDE 转型》的第 18 部分，属于《产品操作系统》系列。第 17 部分讨论了当 AI Agent 完成构建工作时，工程师仍然掌握什么。本部分讨论的是工程师要回馈什么。

简要版本

  • Workday 现在将现场工程师置于产品团队内部。其产品负责人表示，他们在一个客户那里学到的东西会直接进入面向所有客户的产品中。我认为每一家软件公司都在朝这个方向前进。
  • 现场工作变成一个传感网络，它有两类传感器。人员负责察觉客户真正的需求。
  • 负责配置产品的软件 Agent 会记录每一个问题和每一个卡住的步骤。两者都应在当天送达产品团队。
  • 发现问题的最佳形式是附带测试的小型修改建议。这里有一条硬性规则：模式可以传递给其他客户，但客户自身的数据和机密绝不能外传。
  • 当现场工作和路线图都向同一位领导者——首席产品官（CPO）——汇报时，这一切的效果最佳。

Workday 将现场工作移入产品部门

在电话会议的后续环节，一位 JPMorgan 的分析师问到了这些工程师。以下是 Kazmaier 在问答环节的自动转录文本中的回答：“他们是核心工程与技术组织的一部分。”他们与最大的客户合作处理最棘手的案例。接下来是我要划重点的部分。他们的职责还包括“改进我们的 AI 系统和 AI 部署技术，以便将此推广到我们的全部客户群。”

因此，工程师有两个产出。一个是让某个客户成功上线。另一个是让产品对其他所有人都变得更好。

Workday 没有公布该团队的人数或成本，我也不会去猜测。它公布的是汇报关系，而这才是真正的新闻。第 15 部分曾论证现场工作应归属于产品负责人。现在有一家大型公司正在这样做，并且向投资者公开说明了这一点。

首席执行官 Aneel Bhusri 点明了回报。他说，在这种模式下，AI Agent 可以在“几周内，而不是几年内”上线。

两类传感器

第一个传感器是人。Boaz Francis 在 Wonderful 负责前沿部署工程，该公司向大型企业销售 AI 平台。Milos Mandic 于 11 月 17 日为 FDE Hub 采访了他。Francis 说，他的工程师在公司已有认知的基础上进行构建，然后“他们可以通过 PR 或反馈的形式把这些知识回馈给公司”。

PR 是 pull request（拉取请求），是对产品代码提出的一项修改建议，由他人审查后再合并。记住这个词，我后面还会讲到它。

他还解释了为什么这一切在加速。“有了 AI，这个循环变得快得多、快得多，因为构建的部分被缩短了。”

第二个传感器根本不是人。Workday 产品高级副总裁 Max Wessel 在同一场电话会议上给出了一个数字：“Deployment Agent 自上线以来已响应了超过 200 万次部署查询。”Deployment Agent 是 Workday 为搭建产品的团队提供的软件助手。

想想这 200 万个问题里包含着什么。每一个问题都是一个搭建产品的人不知道下一步该做什么的时刻。这是我的解读，Workday 并没有说明它如何使用这些问题。但这样一堆数据就是一张标明产品哪里难用的地图。不需要任何工程师写报告，因为日志本身就已经是一份报告。

第 17 部分把人类剩下的工作称为“缺口工时”。Agent 的日志则是这幅图景的另一半。缺口工时显示 Agent 在哪里做得不够好，而这些问题显示产品在哪里做得不够好。

周一的产品经理部分从产品的角度提出了同样的观点：如今发现（discovery）是一种每日信号。而一线现场是这种信号最丰富的来源。它来自那些已经购买并正在努力让产品运转起来的客户。

管道变短了

传感器是容易的部分，导线更难。

大多数一线发现仍然以故事的形式传播。有人在会议上讲一个，它落进某个聊天频道，几周后由产品经理来整理。第 3 部分为此设计了一套书面材料包，在三个固定时点交接。内容依然是对的，但节奏现在太慢了。

以下是我会搭建的管道。

发现首先被写成一条测试。那是来自客户的一个真实案例，以及一个优秀产品应该给出的答案。第 12 部分解释了为什么由工程师来写它。

然后它变成一个 pull request，也就是 Francis 提到的那种形式。工程师，或者由工程师指挥的 Agent，直接向产品本身提出修复方案。当由 Agent 来做构建时，这可能只需要一个下午。

一位指定的产品负责人在当天做出决定：面向所有人发布、把它保留为仅针对这一位客户的设置，还是拒绝并说明原因。

而且这条测试会保留下来。它在之后的每次发布中都会运行，这样修复就不会悄悄失效。

数两件事。第一是从发现到修复所需的小时数，每个客户都有。第二是层级数，即该发现在上报过程中跨越的汇报层级数量。影响闭环一章已经为这个职位提供了这一衡量标准。

Airrived 的首席执行官 Anurag Gurtu 在十月为 Crunchbase News 撰写了一篇犀利的客座专栏。文章讲的是依赖现场工程师的公司，他的检验标准是两个问题：“完全摊销后，下一个客户的入驻成本到底是多少？”以及：“随着公司扩张，这个数字会下降吗，还是只是让组织架构图不断膨胀？”

短管道正是让这个数字下降的方法。没有它，他就是对的，而你经营的是一家人力派遣公司。

永远不外传的东西

这里有一条界线，买家们已经开始追问了。

Lindsay Clark 于 10 月 22 日在 The Register 上报道了在工程师到来之前客户应该核查什么。她引用了研究机构 Gartner 高级总监 Mukul Saha 的话。他直白地描述了这类交易：工程师在工作中学习，“他们会带回某些让产品变得更好的知识。”然后他说：“但这里面有一条微妙的界线。”

假设带回去的是某个客户的独特优势，而它最终帮助了该客户的竞争对手。Saha 对此的说法是：“那就是对知识产权的彻底侵犯，对吧？”IP 即知识产权，指公司拥有的专有知识。

他是对的，而传感器网络会让这个问题更加尖锐。所以要在第一次部署之前就把规则写下来。

可以带回去的是产品中的缺口、修复方案，以及测试的形态。必须留下的是客户的数据、它的规则、它的价格，以及任何让它优于竞争对手的东西。要带回去的测试行，必须先用虚构数据重写。

第 10 部分讲过买方的合同。我会把这一点作为条款加进去，用直白的语言。而且我会每个月向客户展示带回去内容的清单。能看到清单的客户才有理由信任你。

为什么这是 CPO 的组织

以下是这个 OS 论证中属于这个职位的部分。

传感器只有连接到能采取行动的东西上才有用。在销售部门下，现场发现只是客户账户上的一条备注。在服务部门下，它是工时。而在产品部门内部，它是一个有评审人的拉取请求，而评审人掌握着路线图。

Kazmaier 的说法是“直接传回”。直接意味着中间没有任何汇报层级。

其他职位也从同一条线上读取信息。设计团队获得真实的工作流程。产品营销获得可以使用的证据，这是本系列的下一部分。Product Builder 从真实客户那里获得测试行。这是一个只有一个负责人的闭环。CPO 转型提供了那个职位上的视角。而Agent 名册正是为部署 Agent 指定负责人的地方。

我的预期

这些是我的预测，不是事实。

到 2027 年底，在部署了 Agent 的公司里，来自 Agent 日志的现场发现将多于来自人工撰写的报告。

到 2028 年，最优秀的团队将实现：中位数情况下，从现场发现到为每位客户完成修复不超过 48 小时。这些公司将取消每周现场评审会议，代之以每日评审队列。

到 2027 年底，在包含厂商工程师的大型合同中，关于哪些信息需要回传的条款将成为标准。Gartner 已经在建议买方询问这一点。

本周可以尝试的一件事

找出你们最近五个已落地的现场发现。为每一个写下它是如何到达的：一个故事、一张工单，还是一个拉取请求。然后为每位客户写下从首次听闻到上线所经过的小时数。

现在挑一个还躺在频道里的发现。本周把它写成测试和拉取请求，并指名发给某位产品负责人。

如果现场没有人能对产品提交拉取请求，先解决这个问题。这是那条线路，它属于 CPO。

常见问题

把现场称为产品的传感器网络是什么意思？+

在客户处工作的人员和 Agent 是告诉产品团队现场真实情况的仪器。传感器有两种。前沿部署工程师能察觉客户真正的需求。部署 Agent 则记录每一个问题和每一个卡住的步骤。这两类读数都应在当天送达产品团队，产品也应因此做出改变。

Workday 在 2026 年 11 月 24 日关于前沿部署工程师说了什么？+

在 2027 财年第三季度财报电话会议上，Workday 产品与技术总裁 Gerrit Kazmaier 表示，公司将加大对产品与技术团队内部前沿部署工程师的投入。他说，他们在为某一位客户解决问题时所获得的经验，会直接回流到 Workday 面向所有客户的 AI Agent 中。Workday 未公布该团队的人数或成本。

200 万这个数字是什么？+

Workday 产品高级副总裁 Max Wessel 在同一场电话会议上表示，Deployment Agent 自上线以来已响应超过 200 万次部署查询。Falk 的解读（Workday 并未如此表述）是，每一次查询都标记了一个产品难以配置的地方，因此这份日志就像一份无需任何人撰写的现场报告。

现场发现应如何传递到产品团队？+

分四步。把发现写成一条测试，即一个真实案例，附上优秀产品应给出的答案。把它变成一个 pull request，即对产品的一项拟议变更。由一位具名的产品负责人在当天决定是将其发布给所有客户、保留为单个客户的设置，还是附理由拒绝。该测试会保留下来，并在之后的每次发布中运行。统计从发现到所有客户都获得修复所需的小时数，以及它跨越了多少条汇报线。

什么绝不能从一个客户传递到另一个客户？+

客户的数据、规则、价格，以及任何使其优于竞争对手的东西。Gartner 的 Mukul Saha 告诉 The Register，工程师能带回什么存在一条微妙的界限，把某个客户的优势传递给其他客户将侵犯其知识产权。可以传递的是产品的缺口、修复方案，以及使用虚构数据编写的测试形态。把这一点写进合同，并每月向客户展示清单。

为什么这能支持现场团队向 CPO 汇报？+

传感器只有连接到能采取行动的环节才有用。在销售体系下，现场发现只是客户账户上的一条备注；在服务部门，它只是工时。而在产品体系内，它是一个有评审人的 pull request，而评审人掌握着路线图。Workday 把其前沿部署工程师放在产品与技术团队内部，其产品负责人描述了一种直接回流的学习机制，中间没有任何汇报环节。

对于作为传感器网络的现场团队，Falk 有哪些预测？+

这些是预测，而非事实。到 2027 年底，在部署了部署 Agent 的公司中，来自 Agent 日志的现场发现将多于来自人工撰写的报告。到 2028 年，最优秀的团队能让现场发现转化为所有客户可用的修复，中位时间不超过 48 小时，并且每日评审队列将取代每周现场评审会议。到 2027 年底，关于哪些内容可以回传的条款将成为包含厂商工程师的大型合同中的标准条款。
