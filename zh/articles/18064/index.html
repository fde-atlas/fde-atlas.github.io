AI Agent 分级自主权与交接：FDE 实践指南

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

这篇指南讨论 FDE 如何用证据逐步提升 AI Agent 的自主权，并在离场前完成治理交接。文章引用 Anthropic 数据说明信任随使用经验增长，介绍红绿灯权限模型和 MIT 的 A1-A5 分级，强调按动作而非按 Agent 授权，并给出退款工单 Agent 的策略配置示例、五步实施顺序和交接清单。

要点

  • Anthropic 数据：750 次会话的老用户超 40% 开启自动批准，新手约 20%。
  • 红绿灯模型按风险给每个动作分级授权，Agent 需逐级挣得自主权。
  • MIT A1-A5 分级：A3 须会上报，A4 转向治理，A5 仍无独立决策权。
  • 升级应依据监控数据而非时间表，策略放在可审查的配置文件中。
  • 交接从第一天开始，每个红色动作须有客户方具名负责人。

750 次会话的老用户开启自动批准的比例超 40%，是新手两倍；红绿灯权限表把信任变成规则。

要点速览

  • Anthropic 的数据显示，信任随经验增长：新用户约在 20% 的会话中开启全自动批准，用满 750 次会话的用户这一比例超过 40%。
  • 按风险给每个动作分类，红色动作一开始只提建议；只有监控数据证明上一级已经稳定，才升一级。
  • 交接是把治理职责（制定策略、审计）移交给客户方一位具名负责人。它从第一天就开始，并要请外部人员检验。

设想一个项目进行到第三周。你搭建的客服工单 Agent 在沙箱里运行顺畅。客户的运营负责人问：“它什么时候能独立工作，不用再有人点批准？”接着又问了一个更难的问题：“你离开项目后，我这边谁来照看它？”

这两个问题其实是同一项技能。前者是凭证据而不是凭感觉提高 Agent 的自主程度；后者是把 Agent 的监督职责交给客户团队，让它在你走后还能继续运转。

两件事只要做错一件，Agent 就会落入两种结局之一：要么永远困在人工审批模式里，要么过早放手，出了第一次事故就被收回权限。

信任会积累，而且可以度量

Anthropic 公开过人们实际使用 Agent 的数据，规律很简单：会话数不足 50 次的新用户，约在 20% 的会话中开启全自动批准；会话数超过 750 次的用户，这一比例超过 40%。

从 Agent 一侧看，Anthropic 的内部数据显示，随着 Agent 表现提升，每次会话的平均人工干预次数从 5.4 降到 3.3。模型能承担的自主程度与实际被赋予的自主程度之间存在差距，Anthropic 称之为“部署积压”（deployment overhang），并认为这个差距相当大。

对前线部署工程师（FDE）来说，这就是一份岗位说明。模型很可能已经足够好，缺的是一条证据链，让客户愿意放更多权。Anthropic 还强调，没有部署后的监控，就无从了解 Agent 的真实使用情况。没有日志和指标，你就拿不出任何说服别人的东西。

红绿灯：按动作授权，而不是按 Agent 授权

Data Science Dojo 介绍的红绿灯模型不把权限整体授予某个 Agent，而是按风险给每个动作分类，再分配相应的权限级别。高风险动作只能提建议，由人来批准。

与之配套的原则是：Agent 必须凭实际表现出的能力，一级一级“挣得”自主权。

MIT Media Lab 的 A1 到 A5 分级还补充了两点值得记住。到 A3，Agent 必须知道何时停下来、上报给人。到 A4，人不再逐个监督动作，而是转向治理系统：制定策略、确认 Agent 可以运作的业务范围，以及审计。

在最高一级，MIT Media Lab 还划了一条 FDE 应当熟记的界线：A5 意味着 Agent 能自行执行，不代表它拥有自己的决策权。它仍受所代表组织的权限约束。

示例：一个处理退款工单的 Agent

回到开头的工单 Agent。第一步是列出它能调用的所有工具，给每个工具标上颜色。下表只是示意，升级阈值是你和客户商定的数字，没有通用标准。

动作颜色起始级别升级标准（示例）
读取订单历史、查询配送状态绿自动执行，记录日志不需要
给工单打标签并分派黄自动执行，人工每日抽查连续数周标签修正率都很低
给客户发送邮件回复黄只写草稿，由人点击发送需要修改内容的草稿占比持续下降
办理退款红只提建议，由人批准只对小额退款升级，并由客户方的策略负责人签字

最后一行让执行与决策权的区别变得具体。Agent 也许准确到可以自己办理退款，但谁能退多少钱是客户的政策，这个阈值必须由客户方的人来定，而不是你。

策略应放在配置里，便于阅读和审查，而不是散落在各个提示词中：

actions:
  lookup_order:   { tier: green,  mode: auto }
  tag_ticket:     { tier: yellow, mode: auto, sample_review: daily }
  send_reply:     { tier: yellow, mode: draft_only }
  issue_refund:   { tier: red,    mode: propose_only, owner: "客服负责人" }
escalate_when:
  - confidence_below_threshold
  - customer_mentions_legal_action
promotion_review: weekly   # 复盘人工干预、修正和事故
owner

字段是很多人会忽略的细节。每个红色动作都需要一位具名负责人，对是否升级负责，这正是交接的起点。

动手：按顺序走五步

按 Anthropic 的建议，先在带护栏的沙箱里起步，并设计好检查点，让 Agent 在这些地方停下来征求反馈。然后像上表那样给每个动作标颜色，拿不准的一律先标红。

接着，在上生产环境之前搭好监控：统计每次会话的人工干预次数、输出被修正的频率，以及 Agent 上报的频率。这些数字取代“我看着挺好”。

每周和客户坐下来复盘这些数字，只有当前级别稳定后，才把一组动作升一级。最后，当大多数动作都已是绿色或黄色，就把这场复盘会的主持权交给客户方的某个人。到这一步，他们承担的正是 A4 的治理角色。

交接从第一天开始

Tandem 的建议听起来反直觉，却是对的：在你意识到需要交接之前就开始交接。最后一周才写的静态文档很快就会过时。所以要把读者引向系统的实时状态，比如策略配置文件、人工干预看板和升级历史，而不是把它们复制进一份 Word 文档。

PostHog 给“完成”定了一条清晰的标准：只有客户团队里的一个外人无需任何人先讲解就能接手，交付物才算完成。后续步骤必须具体、有先后顺序，并落到具名的人头上。“运营团队会监控”不算后续步骤。

运维手册应按症状组织，而不是按架构组织。半夜值班的人是从“Agent 发出的邮件语气不对”或“上报率突然飙升”开始排查的，而不是从服务架构图开始。AI Codex 建议做一个测试：把运维手册交给一位没参与搭建系统的人，请他大声读出自己会如何处理某个症状。

常见错误

第一个错误是按时间表升级（“一个月后就让它自己跑”），而不是看数据。第二个是把能力和决策权混为一谈：Agent 准确率达到 99%，并不意味着它有权决定退款政策。

第三个是没有部署后监控，于是升级评审会变成一场凭印象的争论。最后一个是把交接拖到最后一周，那时唯一清楚动作 X 为什么还是红色的人，正准备离开。

如果你在申请 FDE 岗位，请用数字而不是形容词把这项技能写进简历。例如：为一个 Agent 设计自主权路线图，把每次会话的干预次数从 X 降到 Y，并把复盘流程移交给客户的运营团队。

本周练习

挑一个你在运行的自动化流程：一个 Agent、一个 cron 任务或一个内部机器人。仿照上面的 YAML 示例写一份策略文件，给每个红色动作指定一位负责人，再针对恰好一个症状写一条运维手册条目。把它交给一位从未接触过这套系统的同事，安静地听他读出来。

他卡住的地方，就是你的系统仍然依赖你的地方。好的 FDE 会在离开项目之前消除这些地方。
