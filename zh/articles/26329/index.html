电力行业 FDE：GIS 与 SCADA 数据对账

FDE Times · 2026-11-05 · 约 5 分钟读完

摘要

这篇文章面向在电力公司工作的前沿部署工程师，解释 GIS 与 SCADA 数据为何经常对不上：GIS 记录设计状态，SCADA 记录实时量测状态，两者本就可能不同。作者建议用 CIM（IEC 61970/61968）划分数据归属，先建 ID 对照表并对不一致项分类（缺失关联、有意倒闸、需现场核查），再建对象模型，最后才做仪表盘。文中以一条 40 开关馈线为例演示分类流程，并提醒不要把任一系统当作唯一可信来源。

要点

  • GIS 存设计状态，SCADA 存实时量测状态，两者不一致很常见。
  • CIM 的 IEC 61970/61968 范围划分可提示数据归运行还是资产团队。
  • 先建资产 ID 与 SCADA 标签对照表，再对不一致项分类。
  • 引用 PNNL 报告：运行系统集成是 ADMS 部署最大挑战。
  • 顺序应为：对账、建对象模型、最后才做仪表盘。

GIS 记录电网按设计如何运行，SCADA 记录电网此刻如何运行，分清两者能少白忙几周。

要点速览

  • 在电力公司，GIS 存的是设计中的电网，SCADA 存的是运行中的电网，两者对不上很常见
  • CIM（IEC 61970/61968）为电网对象提供了一套通用词汇，它的范围划分也提示了哪些数据归哪个团队
  • 先对账并给不一致项分类，再建对象模型，最后才做仪表盘

在电力公司上班的第一周，你会拿到三份文件：一份 GIS 导出数据、一份 SCADA 测点清单和一份资产台账。任务听上去很简单：把三份文件关联起来，画出一条馈线。到了下午，你发现有个开关在一份文件里是分闸，在另一份里却是合闸，而会议室里没有一个人觉得意外。

没人意外，是因为这不是偶然的错误，而是这个行业的结构性特点。PNNL 在 2016 年发布的一份关于先进配电管理系统（ADMS）的报告得出结论：电力公司地理信息系统（GIS）中的数据模型往往不完整、不准确，或者两者兼有；报告还指出，运行系统之间的集成是部署中最大的挑战。

如果你带着“有 schema 就能 join”的想法进入电力公司，很可能花两周去修根本没坏的东西。另一种做法是提前学几个行业概念，从第一次需求调研起就问对问题。

GIS 和 SCADA 描述的不是同一个状态

GE Vernova 对这种割裂的描述很到位。一边是电网设计和制图团队：他们用 GIS 规划和更新电网的正常状态，自成一个孤岛。另一边是调度控制室的运行人员：他们在另一个孤岛里监视电网的实时状态。

所以，GIS 回答的是“电网按设计应该怎样运行”，SCADA 回答的是“电网此刻正在怎样运行”。运行人员为检修或转移负荷而隔离某一段线路时，两者本来就应该不同。另一些不一致则确实是错误：GIS 没有及时更新，或者 ID 映射表有误。

1Spatial 描述过公用事业行业的一个典型案例：GIS 显示某个阀门处于关闭状态，SCADA 却报告它是打开的。换到电力公司，把“阀门”换成“开关”，就是那天下午的情形。

写 schema 之前，CIM 先给了你一套词汇

电力行业早就有一套通用语言。公共信息模型（CIM）由 IEC 61970-301 标准定义，是一个抽象信息模型，描述电力企业中的主要对象。它把电力系统资源表示为带属性的对象类，让不同厂商独立开发的应用也能相互集成。

对前线部署工程师（FDE）来说，CIM 最有用的地方是它划分范围的方式。据 CIM Users Group 介绍，IEC 61970 覆盖电力系统建模和数据交换，包括能量管理系统（EMS）、拓扑、导体和 SCADA。IEC 61968 负责与配电网相关的模型：配电管理系统（DMS）、资产、作业、GIS、计量以及应用间的消息传递。

客户未必严格按 CIM 实现，但这种划分仍然值得当作地图来用。它给了你一份名词清单，跟电力工程师沟通时可以直接用。

它还提示了哪些数据大概率归哪个团队：运行，还是资产与制图。某个数据字段看起来很离谱时，知道它归谁管，问题就解决了一半。

示例：对账一条馈线

设想一条有 40 个开关的馈线。GIS 用

SW-0412

这样的资产 ID，另有一个字段记录正常状态。SCADA 用

F07_SW412_POS

这样的标签名，值为 1 表示合闸。两个系统都不保存对方的键，所以第一步是建一张对照表，把资产 ID 映射到标签。

接着，把每台设备整合成一个对象，两种状态分开保存，连字段名都要区分开：

from dataclasses import dataclass

@dataclass
class Switch:
    asset_id: str               # 来自 GIS 的键
    scada_tag: str | None       # 从对照表中获取
    normal_open: bool           # 设计状态（GIS）
    measured_open: bool | None  # 量测状态（SCADA）

def classify(sw: Switch, switching_orders: set[str]) -> str:
    if sw.scada_tag is None or sw.measured_open is None:
        return "missing_link"
    if sw.normal_open == sw.measured_open:
        return "match"
    if sw.asset_id in switching_orders:
        return "intentional_switching"
    return "needs_field_check"

参数

switching_orders

是近期有倒闸操作票的设备清单，需要向调度控制室索取。没有这份清单，每一次正常的负荷转移都会被算成错误。

假设运行结果是：31 台设备一致，4 台缺少关联，3 台因有意倒闸而不一致，2 台需要现场核查。与其报告“GIS 有 9 处错误”，不如带着三份清单去找三个不同的人。

4 个缺失关联是你和集成团队的活。最后 2 个归制图团队，可能还得有人亲自去电线杆那儿看一眼。

先建对象模型，再做仪表盘

Palantir 介绍过与一家欧洲电力公司合作的案例。这家公司的地理资产系统和电网系统彼此独立，因此缺少一幅完整、及时的电网状态全景。解决办法是把电网拓扑建模为 Ontology 对象和视图，用来表示每个网络元件。

这个经验与工具无关。设备、线路和连接关系必须先成为显式的对象，仪表盘或预测模型都排在后面。如果在没有对账的 join 上做图表，你只是把现有的不一致画得更好看而已。

因此，在客户现场的工作顺序相当清楚：

  • 把每个系统放进 61970 或 61968 的范围中，记下它的负责人。
  • 问清楚每个状态字段是“正常”还是“量测”。
  • 建立资产 ID 与 SCADA 标签之间的 ID 对照表。
  • 运行分类步骤，再把每份不一致清单交给对应团队。
  • 等制图团队和调度控制室都确认之后，再锁定对象模型。

常见的坑

最常见的坑，是把 GIS 当作唯一可信来源，用 SCADA 的状态去覆盖它，或者反过来。两个字段描述的是不同的东西，所以两者都要保留。第二个坑是以为一台设备只有一个 ID，而实际上每个孤岛通常都按自己的方式编码。

第三个坑更难察觉：跟电力工程师说通用的软件术语。问“这条记录是不是过期了？”，他们很难回答；问“这是正常状态还是量测状态？”，他们马上就能回答。用他们的词汇，是赢得信任最快的办法。

职业发展方面，阅读能源行业的 FDE 岗位描述时，可以把本文出现的术语（CIM、IEC 61968/61970、ADMS、GIS、SCADA）当作核对清单。简历上不要只写“数据集成”。

要具体写明你在哪些系统之间对账过拓扑，以及如何给不一致项分类。PNNL 的报告把运行系统之间的集成列为最大挑战，所以这类经验值得放在最前面。

在电力公司，明白两份文件为什么对不上的人，比会把它们 join 起来的人更有价值。
