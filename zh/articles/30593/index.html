Bedrock Agents 课程下线后如何迁移 AgentCore

FDE Times · 2026-11-23 · 约 4 分钟读完

摘要

DeepLearning.AI 的 Bedrock 智能体课程已下线，AWS 的 Bedrock Agents 也停止接受新用户并更名为 Agents Classic，但存量智能体仍在生产环境运行。文章建议把这门课程当作遗留系统的地图来读：搭建方式已过时，新项目应改用 AgentCore 与 Strands Agents SDK，并补学 Observability、Identity、Policy 和 Evaluations。但课程中三个思路依然成立：工具是智能体与客户系统的契约（迁移时需锁定 schema 并做回归测试）、算术应交给可核查的代码而非模型、负责任 AI 是有真实配置的工程层。文章还给出按客户情况区分的学习顺序与求职建议。

要点

  • 课程已下线，Bedrock Agents 更名 Agents Classic，存量客户可继续使用。
  • 新项目应基于 AgentCore 与 Strands Agents SDK，并补学 Policy、Observability 等。
  • 迁移时先锁定工具 schema，再用真实问题做回归测试后才关闭旧路径。
  • 三个仍成立的思路：工具即契约、算术交给代码、负责任 AI 需配置与评测。
  • 求职时可询问客户用 Agents Classic 还是 AgentCore，判断工作性质。

把它当作遗留系统的地图来读：换到 AgentCore 之后，课程里有三个思路依然成立。

要点速览

  • DeepLearning.AI 已下线这门课程，AWS 也已停止接受 Bedrock Agents 的新用户注册，该服务现更名为 Agents Classic
  • 已在使用 Agents Classic 的客户可以继续运行，因此前线部署工程师（FDE）仍需理解课程讲授的架构
  • 新项目应基于 AgentCore 和 Strands Agents SDK 构建，并在此基础上补学 Observability、Identity、Policy 和 Evaluations

DeepLearning.AI 上 Serverless Agentic Workflows with Amazon Bedrock 的课程页面于 2026 年 6 月 4 日更新，开头只剩一句话：本课程已下线。AWS 文档同样写明，这门课程的核心服务 Amazon Bedrock Agents 已不再接受新用户注册，并更名为 Agents Classic。

乍看之下，事情到此为止。但 AWS 也明确表示，现有的 Bedrock Agents 用户可以继续使用。

对前线部署工程师（FDE）来说，关键正是这一点。基于 Bedrock Agents 构建的系统很可能仍在生产环境中运行。当你被派驻到一家早前就部署了智能体的 AWS 客户那里，遇到的很可能正是这门课程讲的那套概念。

因此，这门课程最适合当作一张遗留系统的地图来重读，再配上一张通往当前平台的对照表。下文分清哪些该保留，哪些该舍弃。

一门由 AWS 讲授的短课程

授课人是 AWS 的 Mike Chambers。课程定位为中级，时长约 1 小时 34 分钟，包含 8 个视频和 5 个代码示例。唯一的先修要求是基础 Python，面向想为工作或个人项目构建智能体应用的人。

课程目标说得很直接：用无服务器技术把一个“负责任”的智能体应用推向生产环境。它要解决的底层问题，是用智能体工作流处理那些难以事先预测的任务，因为这些任务取决于用户输入，比如调用 API。

Classmethod 在 2024 年 12 月 8 日发布的一篇实操记录梳理了具体路径；据该文介绍，这门课程免费。学员先在 Bedrock Agents 上搭建一个智能体，接入 AWS Lambda 函数，用 Knowledge Base 回答常见问题（也就是 AWS 托管的 RAG），挂上 Guardrails，再用 Code Interpreter 加入计算逻辑。

哪些已经过时？

课程构建智能体的方式建立在全托管的 Bedrock Agents 模式之上：每个智能体至少需要一个 action group，外加 knowledge base 和 trace。

对于新用户，AWS 指向的是 Amazon Bedrock AgentCore，在那里智能体用 Strands Agents SDK 以代码方式定义。根据 AWS 文档，AgentCore 可搭配任意框架和任意模型，由多个模块化服务组成，每个服务都能单独使用。

如果客户刚刚起步，不要照着课程一步步搭建智能体。你会直接撞上一扇对新用户关闭的注册大门。

课程还漏掉了真实生产工作需要的几块内容。AgentCore 自带 Observability、Identity、Policy 和 Evaluations。AWS 特别把 Policy 描述为一个确定性的控制层，能让智能体守住业务边界和规则，又不拖慢运行速度。这部分需要自己补学。

仍值得保留的三个思路

第一，工具是智能体与客户系统之间的契约。在课程里，这份契约是一个指向 Lambda 函数的 action group。在 AgentCore 上，Gateway 把 API、Lambda 函数和现有服务转换成兼容 MCP 的工具，所以课程中关于把智能体接入 CRM 的内容，讲的思路依然正确。

假设有一家零售客户，在 Agents Classic 上运行客服智能体，其中一个 action group 通过 Lambda 查询订单。迁移到 AgentCore 时，Gateway 可以把这个 Lambda 函数封装成 MCP 工具。真正费力的是关闭旧路径之前的两步。

第一步是锁定 schema。例如，

look_up_order

工具接收一个必填的字符串

order_id

和一个用于核验订单归属的

email

，只返回三个字段：

status

、

estimated_delivery_date

和

total_amount

。旧智能体隐式接受的任何字段，比如电话号码，要么写进文档，要么有意删除。

第二步是回归测试。拿旧智能体收到过的真实问题，同时跑一遍旧 action group 和新工具，检查调用的工具、传入的参数和返回的结果是否完全一致。一致之后，才关闭旧的 action group。

第二个思路：别让模型做算术。课程把计算交给 Code Interpreter。智能体报价、计算退款或汇总库存时，数字应当经过真正执行、可以核查的代码，因为客户一定会问这个数字从哪来。

第三个思路：“负责任”是一个有真实配置的工程层。课程把 Guardrails 直接放在通往生产环境的路上；在 AgentCore 上，Policy 和 Evaluations 承担的是同样的作用：让智能体守住边界。

这只是思路上的对应，并不意味着 Policy 取代了 Guardrails。当客户问智能体会不会给出违规回答时，你需要拿出的是一份配置和一套评测，而不是一句承诺。

谁该学，按什么顺序学？

如果你即将接手一家已在运行 Bedrock Agents 的客户，在打开对方的 AWS 账号之前，先吃透 action group、knowledge base、trace 和 guardrail。然后阅读 AgentCore 文档：先看 Gateway，因为它直接衔接你已经熟悉的 Lambda 部分，再看 Policy、Observability、Identity 和 Evaluations。Strands Agents SDK 留到最后，等你准备用代码编写智能体时再学。

如果客户完全是 AWS 新用户，直接上 AgentCore 和 Strands。这种情况下，这门课程只能作为背景，帮你理解旧系统为什么长成现在这样。

在职业层面，如果招聘岗位提到 Amazon Bedrock，面试时可以问一句：他们的客户用的是 Agents Classic 还是 AgentCore。答案会告诉你，这份工作是维护、迁移还是从零搭建。

写简历时，“通过 AgentCore Gateway 将 Bedrock Agents 的 action group 迁移为 MCP 工具，并配套回归测试”这样一行，远比一张已下线课程的证书更有说服力。

课程已经关闭，而基于 Bedrock Agents 构建的智能体仍被允许继续运行。等它们需要“搬家”时，接到电话的会是那个两代平台都懂的人。
