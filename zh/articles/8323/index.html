TencentDB Agent Memory 评测：面向 AI Agent 的分层记忆、基准测试的真实表现，以及何时使用它

原标题：TencentDB Agent Memory Review: Layered Memory for AI Agents, What the Benchmarks Really Show, and When to Use It

FDE Interviews · 2026-10-21 · 约 10 分钟读完

摘要

本文评测腾讯云开源的 TencentDB Agent Memory。该系统以代理方式部署在 Agent 与模型之间，将对话逐层提炼为事实、场景与画像，并提供技能、Wiki 和代码图谱等共享资产，所有摘要可回溯到原始证据。作者重算了其基准数据：宣传的 51.52% 提升只是 WideSearch 从 33% 到 50%，SWE-bench 仅加 5.8 分，且两个 token 节省数字与表格不符，缺少运行次数、方差和模型信息。文章还提醒代理会读取全部提示词、可能破坏提示词缓存，并给出试点建议：适合多人反复解释同一项目背景的团队，不适合单人或快速变化的事实。

要点

  • 系统作为代理注入分层记忆，摘要可回溯原始证据
  • 51.52% 头条数字实为 WideSearch 从 33% 升至 50%
  • 两个 token 节省数字无法从 README 表格复算

TencentDB Agent Memory 通过一个代理为编程和工作类 Agent 提供共享的分层记忆：聊天记忆、技能、Wiki 和代码图谱。我们阅读了代码并重新计算了其基准测试。51.52% 这个亮眼数字只是单一基准测试上提升了 17 个百分点，而且两个 token 数据与其自身表格不符。

作者：ADAM REYES · FDEINTERVIEWS 编辑部 · 更新于 2026 年 10 月 21 日 · 阅读时长 8 分钟

实践一下：Agent 记忆的概念 · 上下文工程取代了提示词工程 · RAG 与 Agent 设计问题 · 必知的 FDE 问题

TencentDB Agent Memory 是一个开源记忆层，让编程和工作类 Agent 能够跨会话、跨 Agent、跨团队地记住项目上下文、决策和流程。它主要通过作为代理位于 Agent 与其模型之间来工作，将相关记忆注入每个请求，并把每一轮对话写回分层存储。 该设计是合理的，某些地方甚至颇为巧妙，尤其是它坚持让每条摘要都保留一条回溯到原始证据的路径。其基准测试部分则不如 29,700 个 GitHub 星标所暗示的那么可靠。"+51.52%" 这个亮眼数字只是单一基准测试从 33% 提升到 50%，没有给出运行次数或模型信息，而且两个 token 节省数据无法从 README 自身的表格中重新计算得出。我们的观点：这一架构值得学习，对于经常向 Agent 重复同样内容的团队来说也值得试点，前提是你要以它的本来面目来审视它——一个会读取工程师发送的每一条提示词的服务。

一个名字下的两个产品

该仓库有两个分支，描述的是两个不同的产品，这也解释了为什么它的截图彼此不一致。

The

main

分支

描述的是一个基于“符号化短期记忆加分层长期记忆”构建的 OpenClaw 和 Hermes 插件。在长任务中，它将庞大的工具输出（搜索结果、代码、错误堆栈）转储到文件中，并在上下文中只保留一张紧凑的任务状态 Mermaid 图谱，节点 ID 可供

agent

用来获取完整文本。这就是带有广为流传的基准测试表的 README。

默认分支

feat/server_team

（v2）描述的是一个团队记忆中心。一个代理位于 Agent 的模型调用之前，四类记忆资产在网页面板中管理：聊天记忆（偏好、事实和决策）、技能（带触发条件和验证规则的版本化流程）、由文档构建的 Wiki，以及由代码仓库构建的 CodeGraph。资产具有所有者、版本和可见性级别（

private

,

team

,

restricted

以及

agent

），且新记忆默认为私有。其 README 只保留了一行基准测试数据。变更日志和路线图显示当前版本约为 v2.0.x。

两者共享同一个长期记忆理念，因此我们只介绍一次该架构。

工作原理

架构来源：team-branch README，其中描述了代理和共享内存服务。

分层。 原始对话（L0）保持不变。异步管道将其提炼为原子事实、偏好和约束（L1）、围绕项目的场景块（L2）以及稳定模式的画像（L3）。上层以人类可读的 Markdown 存储，下层存入数据库以支持全文搜索。召回默认提供紧凑的上层内容，当需要具体事实时，通过 BM25 加向量搜索进行下钻，并使用倒数排名融合进行合并。结果受条目数、每条记忆的字符数、总字符数和超时时间限制（召回代码中默认为 5 秒）。

可追溯性。 每个上层条目都保留一条通向其来源证据的路径。这是我们会复制到任何记忆系统中的部分。无法追溯回来源的摘要就是谣言。 当画像中的某条事实被证明是错误的，你需要找到产生它的对话；当客户要求删除某些内容时，你需要从由其派生的每一层中移除它。

资产，而不仅仅是聊天。 技能从成功的对话和工具调用中提炼而来，带有版本和触发边界。Wiki 页面和 CodeGraph 索引作为工具暴露（

/v3/tools/list

,

/v3/tools/call

），而不是粘贴进上下文，因此文档只有在 Agent 主动请求时才会进入提示词。致谢部分说明 CodeGraph 模块使用了 colbymchenry 的 codegraph 项目中的代码，Skill 模块则基于 Hermes Agent 构建。

符号化短期记忆（

main

分支）。与其在

the context window

中保留五十个工具输出，Agent 维护一个小型图，记录它做了什么以及每个原始结果保存在哪里。

Keep the pointer, not the payload.

Mermaid 是编码该图的一种方式；重要的设计选择是每个节点都有一个 ID，可按需检索完整文本，因此压缩永远不会破坏信息。这与长期运行的编码 Agent 中基于文件的草稿板是同一原则，而且是个好原则。

四点观察。

标题是相对数字，且来自单一基准测试。“将通过率提升 51.52%”是指 WideSearch 从 33% 提升到 50%。同一插件在 SWE-bench 上增加 5.8 分，在 AA-LCR 上增加 3.5 分。低基数上的相对提升是营销数字；分数才是工程数字。两者都是真的，但只有一个能告诉你用户的体验会有什么变化。

两个 token 数字与其表格不符。WideSearch 的降幅重新计算应为 61.30%，而非标题中的 61.38%；SWE-bench 的应为 31.63%，而非 33.09%。这些是小错误，但很重要，因为它们暗示表格和正文可能来自不同的运行结果，或是分别编辑的。当标题数字无法从旁边的表格重新计算得出时，请相信表格，并追问标题出自哪次运行。

没有样本量、方差或模型信息。README 没有说明运行了多少任务、运行了多少次、使用哪个模型，以及结果的离散程度。AA-LCR 上 3.5 分的提升可能只是噪声。默认分支现在只保留 PersonaMem 一行，同样没有说明配置。

SWE-bench 的设置偏向插件。README 称 SWE-bench“每个会话连续运行 50 个任务，以模拟真实世界长程 Agent 的上下文累积压力”。这是对记忆系统的有效压力测试。但它也是一个在单个会话中携带五十个任务历史的基线，很少有生产环境会在不压缩的情况下这样做。31.63% 的 token 节省中，有一部分只是插件做了基本上下文重置策略同样会做的事。公平的比较应针对带常规压缩的基线。

这些并不意味着该系统不能工作。它意味着已发布的证据无法告诉你它能给你带来多大帮助，你需要自己进行测量。

记忆代理会对你的数据和账单造成什么影响

将每次模型调用都经由记忆代理路由，其后果是 README 的“零代码集成”所低估的。

它会读取一切。代理能看到每个提示和响应，包括源代码、堆栈跟踪以及工程师粘贴的任何机密。默认情况下，代理配置启用了注入（将技能、知识工具和记忆块添加到系统提示中）和提取（将每轮的用户查询和助手回复写入 L0）。记忆代理是你自己选择的中间人。请像审查中间人一样审查它。

它会把对话发送给第二个模型。部署模板中有两套模型设置：一套用于代理的上游，另一套用于记忆服务自身的摘要和嵌入。它们可以是不同的提供商。你的数据处理审查必须覆盖两者。

它改变了 prompt caching。 召回的记忆会被注入到系统提示词中，而系统提示词通常是 prompt caching 所依赖的稳定前缀。如果注入的内容每次请求都不同，缓存就会失效，每次调用都要为整个前缀支付全价。该项目自身的配置就警告过，配置不当的多节点部署会导致上游 Anthropic 缓存每次都未命中。把稳定的指令放在前面，记忆块放在其后，并在前后分别测量你的缓存命中率。

它默认拉取

latest

镜像。

快速入门模板使用

:latest

来自

Docker

Hub 的标签，且脚本会复用本地的

latest

而不检查更新。除了在笔记本上试用之外，任何场景都应固定版本。

什么时候值得用

适合的场景。 多个人和 Agent 反复解释相同架构、约定和决策的团队。代理机构和前沿部署团队在同一个客户的代码库中工作数月，每次新会话重新讲解的成本真实存在。需要在跨对话中掌握客户稳定事实的支持和运维 Agent。

不适合的场景。 只有一个 Agent 的单人开发者，一个维护良好的

AGENTS.md

或项目笔记文件就能免费完成大部分工作。快速变化的事实，一条被自信注入的过时记忆比没有记忆更糟。受监管的数据，除非已审查过代理、记忆模型的提供商和数据保留策略。

我们的试点方式。 在一个团队上运行两周，仅使用私有记忆。测量三件事：每个已完成任务的 token 数、有多少比例的会话中有人重新讲解了本应由记忆提供的上下文，以及注入的记忆出错或过时的频率。只有在有人审核之后才将记忆提升为团队范围，添加一条能触及每一层的删除路径，并与最便宜的替代方案——一份精心维护的项目笔记文件加上 Agent 内置的压缩功能——进行比较。如果代理没有以明显优势胜出，那么笔记文件就是赢家。

对于 FDE 来说，记忆设计如今已成为常见的面试话题：存什么、以什么粒度存、如何检索、如何避免过时以及如何删除。这里的分层模型是一个很好的参考答案。请阅读我们的 Agent 记忆 概念、关于 上下文工程取代提示词工程 的文章，并用我们的 RAG 和 Agent 问题 进行练习。

把它转化为要约。研究它所对应的真实问题和概念：

常见问题

TencentDB Agent Memory 是腾讯云推出的一个采用 MIT 许可证的开源记忆系统，面向 Claude Code、Codex、OpenClaw 和 Hermes 等 AI Agent。其当前版本以代理形式运行在 Agent 与其模型之间：它在每次请求中注入相关的记忆、技能和知识工具，并将每一轮对话写回分层记忆存储。它还会构建文档 wiki 和代码图谱，并支持团队共享和访问控制。

原始对话首先被存储（L0），然后在后台被提炼为原子事实和偏好（L1）、场景级摘要（L2）以及长期人设（L3）。在请求时，Agent 默认获得紧凑的上层内容，当需要某个具体事实时，再回退到详细的下层内容，通过 BM25 和向量搜索并经倒数排名融合进行检索。结果按条数、字符数和超时时间进行限制。

这些数据看似合理但较为单薄。该项目报告了在四个基准上使用和不使用其插件的成功率，但没有说明任务数量、运行次数、方差或所用模型。标题中 51.52% 的提升是 WideSearch 从 33% 提升到 50%；在 SWE-bench 上提升为 5.8 个百分点。README 中两处 token 减少的数字与同一表格中的 token 数量对不上。

经过审查后可以使用。该代理会看到每一个提示词和响应，向系统提示词添加内容，默认将每一轮对话写入记忆，并将对话发送给一个单独的模型进行摘要。请像对待任何处理源代码和凭据的服务一样对待它：自行托管、固定镜像版本、慎重选择记忆模型的提供商，并在上线前设置保留和访问规则。

当多个 Agent 或人员反复重新解释相同的项目背景、约定和决策，且这些背景变化缓慢时，它很有用。对于一次性任务、只有一个 Agent 的单用户，或者快速变化的事实（过时的记忆比没有记忆更糟），它帮助不大。建议从一小组经过审查的共享记忆开始，而不是捕获所有内容。

讨论 (4)

缓存问题是那个悄悄烧钱的地方。我们曾有一个记忆层，会把召回的事实前置到系统提示词中，结果我们的提示词缓存命中率从大多数请求命中降到几乎为零。把记忆块移到稳定指令之后，一个下午就修复了这个问题。

读者提问：先做共享团队记忆，还是先做每用户记忆？

默认采用按用户隔离和隐私优先，正如本项目的设计。个人记忆经本人审核后，再提升为团队记忆。无人整理的团队记忆，不出一个月就会变成共享的杂物抽屉，而每个 Agent 都会继承这些杂物。

值得加入治理清单的还有：删除路径。当客户要求你遗忘某些内容时，你需要将其从 L0 以及由其提炼出的每一层中移除。在真正需要之前，先问清楚系统如何将某个角色事实追溯到其来源对话。
