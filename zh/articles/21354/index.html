构建企业级 RAG 知识助手，端到端实现

原标题：Build an Enterprise RAG Knowledge Assistant, End to End

Cloud Soft Solutions · 2026-10-06 · 约 13 分钟读完

摘要

文章以一家中型保险公司的运营团队为场景，按前沿部署工程师的交付方式，完整讲解企业级 RAG 知识助手的构建：从业务问题、需求与成功指标，到架构、数据、检索、安全、评测、部署与 ROI 计算。核心观点是助手只有在正确引用来源、遵守权限、可评测、可监控时才算完成。

要点

  • 以保险运营场景驱动，目标是减少差错、加快入职、减少 SME 打扰，而非做聊天机器人。
  • 架构采用 PostgreSQL 加 pgvector，混合检索加重排序，权限过滤在数据库查询内完成。
  • 按文档结构分块并保留版本元数据，排除已废止文档，引用需代码校验。
  • Agent 保持轻量：未找到答案时经用户确认后通过 MCP 向文档负责人建工单。
  • 先定固定测试集与指标，CI/CD 中权限泄漏零容忍，ROI 与客户共同测算。

这是一个完整的 RAG 项目，按照前沿部署工程师向客户交付的方式来讲解：从业务问题到可衡量的投资回报。企业知识助手只有在满足以下条件时才算“完成”：从正确的文档中回答问题、遵守文档的访问权限、引用来源、能在固定测试集上进行评测，并运行在受监控的云基础设施上。 该场景仅为示例；文末的构建方案会将其转化为一个你可以在面试中有理有据地展示的 RAG 作品集项目。

关于基础知识（嵌入、分块、向量存储），请阅读 什么是 RAG 及其工作原理；本文重点讨论工程决策。

业务问题

示例场景。设想一家中型保险公司，其运营团队（理赔处理、保单服务和客户支持后台）需要依赖一个庞大且不断增长的文档库，包括保单条款、标准操作程序（SOP）、核保指南、通函和流程说明。这些文档存放在 SharePoint 站点和 PDF 文件夹中。有些文档已被取代但从未删除；有些存在两个地区版本。

对于海得拉巴或班加罗尔的 GCC 或服务交付团队的任何人来说，这些症状都不陌生：

  • 新员工需要数周时间才能上手，因为找到“正确的 SOP”靠的是口口相传的经验。
  • 有人按照已被取代的流程操作时就会出错。
  • 领域专家（SME）反复回答同样的问题。

客户想要的是减少流程错误、加快新人上手、减少对 SME 的打扰，而不是“一个聊天机器人”。这种从 AI 演示到企业成果的视角转变，驱动着下文的每一个决策。

需求

与运营负责人、团队主管、一位 SME 和信息安全人员的需求梳理，产出了三组需求。

功能性需求

  • 仅基于已批准的文档回答有关流程和资格规则的问题。
  • 每个回答都引用文档、章节和生效日期，并附有链接。
  • 当文档中不包含答案时，明确说明，并主动提出可以向文档所有者提交查询。
  • 绝不基于已被取代的文档回答，除非用户询问的是历史信息。

非功能性需求

  • 用户只能看到其 SSO 用户组在 SharePoint 中已有权限访问的内容。
  • 数据保留在客户的云账户和已批准的区域中；任何提示词或文档都不会用于训练供应商的模型。
  • 商定的 p95 延迟目标，并在生产环境中进行测量。
  • 完整的审计追踪：谁问了什么、检索了哪些分块、回答了什么。

成功指标

指标测量方式负责方
回答正确性由 SME 和 LLM 评审员评分的固定测试集工程 + SME
忠实度 / 引用准确性每次发布时的自动化评测工程
正确拒答率测试集中的不可回答问题工程
权限泄露在访问控制测试套件上必须为零安全
采用率与问题分流周活跃用户数、SME 查询前后对比运营

在编写代码之前就这些指标达成一致的目标，是你能做的最有价值的一件事。

架构

一条离线索引流水线、一个在线查询服务，以及贯穿两者的身份、评测与可观测性。

关键决策及其原因：

  • 使用 pgvector 的 PostgreSQL 作为存储。分块、元数据、ACL 和向量存放在同一个数据库中，因此权限过滤和关键词搜索可以自然地与向量搜索结合。
  • 无状态 API，独立的工作进程，这样大规模重建索引不会拖慢用户流量。
  • 模型访问隐藏在接口之后。 应用调用一个轻量的 llm_client，因此在 Amazon Bedrock 和 Azure OpenAI 之间切换只需改配置，而无需重写代码。

数据

大多数 RAG 质量问题其实是数据问题。

从 SharePoint 和 PDF 摄取数据

  • 使用 Microsoft Graph API，并在 Microsoft Entra ID 中注册应用，只读权限限定在约定的站点。拉取文件、元数据和权限信息。
  • 先做一次全量抓取，然后使用 delta 查询和文件哈希进行增量同步，这样只有发生变化的文档才会被重新分块和重新嵌入。
  • 使用能识别版面的解析器处理 PDF，保留标题、列表和表格。对扫描版 PDF 做标记：OCR 错误会悄悄损害检索质量。

分块

SOP 和保单条款是结构化文档，因此应按结构分块，而不是按固定的 token 数量。按标题和编号步骤切分，尽量把一个流程的步骤保持在同一块中，并把每个表格与其标题放在一起。为每个分块前置一个简短的上下文头部，例如

Claims SOP > 4. Document verification > 4.2 Missing documents

，这样像“第二次提醒后升级处理”这样的段落单独出现时仍然有意义。采用父子分块方式：检索小的分块，把父级章节发送给模型。

元数据

字段用途
doc_id、title、section_path引用和深链接
version、effective_date、status优先使用现行版本；排除已废止版本
department、product_line、region过滤和查询路由
owner（个人或团队）路由“未找到”类工单
allowed_groups权限感知检索
source_hash、ingested_at增量同步和审计

要预料到会发现重复文档和冲突版本。不要在代码中静默解决它们：为文档所有者生成一份报告。这往往是客户看到的第一项价值。

LLM

不要从排行榜上挑选模型。根据对这个客户真正重要的标准来选择，然后在自己的测试集上验证：

  • 有据回答： 它是否始终基于所提供的上下文作答，并在上下文没有相关信息时拒绝回答？
  • 指令遵循： 它能否稳定地生成你的代码可以解析的引用格式？
  • 数据驻留与条款： 通过客户所选平台（Amazon Bedrock、Azure OpenAI 或 Google Cloud 上的 Gemini）在已批准的区域提供。
  • 在真实上下文规模下的延迟与单次回答成本。

一个实用的模式是两层架构：用能力较强的模型生成答案，用更小、更便宜的模型进行查询改写和分类。嵌入模型也按同样的方式选择，即以客户自身问题样本上的检索质量为准。请记住，更换嵌入模型意味着需要重新嵌入整个语料库，所以要尽早决定。

RAG

查询路径有五个阶段，每个阶段都有一个具体的决策。

  • 查询理解。 利用聊天历史将追问改写为独立查询（“那摩托车呢？”变成“摩托车理赔的文件缺失升级流程是什么？”）。当用户明确说明时，提取诸如产品线之类的过滤条件。
  • 混合检索。 并行运行向量相似度搜索和 PostgreSQL 全文搜索，两者都受用户所属权限组和 status = 'current' 的限制。使用倒数排名融合进行合并。关键词搜索在这里很重要，因为保险运营中充满精确术语：表单代码、条款编号、产品名称。
  • 重排序。 将排名靠前的候选结果交给交叉编码器重排序器（托管或自托管），只保留少量最佳结果。这通常是性价比最高的大幅质量提升手段。
  • 提示词组装。 系统指令要求：仅根据编号来源回答，每条论断都标注其来源 ID，当来源无法回答问题时回复“我在已批准的文档中找不到此信息”。包含每个来源的标题和生效日期。
  • 引用验证。 在代码中检查每个被引用的 ID 是否都在检索到的集合中，对不在其中的进行丢弃或标记。将引用渲染为指向确切 SharePoint 文档和章节的链接。

增加相关性阈值：如果最佳重排序得分低于调校好的截止值，则跳过生成，直接走“未找到”路径。这可以避免许多自信却错误的回答。

Agent

保持 Agent 轻量。每一个自主步骤都会增加风险和评测工作量。值得添加的唯一 Agent 行为是：当未找到答案时，主动提出向文档负责人提交工单。

question -> retrieve -> score ok? --yes--> answer+cites
                           |
                           no
                           v
              "Not found. Raise a query?"
                           |
                     user confirms
                           v
           create_ticket(owner, question, ctx)
                           v
                 ticket ID shown to user

这是一个小型状态机，用 LangGraph 或纯 Python 都能轻松实现。模型提议工单并起草摘要；用户确认；由确定性代码调用工具。模型永远不会自行决定创建工单。“未找到”工单的聚类也能让 SME 准确看到哪些文档缺失。

工具

狭义地定义工具，使用带类型的输入和服务器端验证：

工具输入防护措施
search_documentsquery, filters用户 ACL 在服务器端应用，绝不由模型传递
get_document_sectiondoc_id, section_path获取时重新校验权限
create_ticketowner_team, question, summary, source_ids需要用户确认；按用户限流
get_ticket_statusticket_id仅限用户自己提交的工单

用户身份始终来自经过身份验证的会话，绝不来自模型输出，并且每次调用都会记录日志。

MCP/API

工单集成（ServiceNow 或 Jira，取决于客户使用哪个）通过 MCP 服务器暴露。MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年底推出的开放协议，用于将 AI 应用连接到工具和数据。作为 MCP 服务器，这些工单工具以后可以被其他助手复用。

  • MCP 服务器只暴露 create_ticket 和 get_ticket_status，不暴露更广泛的功能。
  • 它使用最小权限的服务账户，并在每张工单中记录最终用户的身份。
  • 调用是幂等的：客户端生成的请求 ID 可防止重试时产生重复工单。

助手本身通过一个简单的 REST API 提供（

POST /ask

,

POST /feedback

,

GET /health

），因此 Web UI 或 Teams 机器人可以置于其前端。

Cloudsoft 的 AI 前沿部署工程师课程 涵盖了端到端构建这套系统，包括通过 MCP 实现的工单 Agent：企业知识助手是 FDE PRO 的五个企业项目之一，通过 MCP 实现的 ServiceNow AI Agent 则是另一个。

安全

评审人员首先测试权限。该设计采用基于 SSO 组的权限感知检索：

  • 用户使用 Microsoft Entra ID (OIDC) 登录。API 验证令牌并读取用户的组成员身份。
  • 在数据摄取时，每个分块都会存储允许读取其源文档的组，这些组从 SharePoint 权限镜像而来。
  • 每次检索查询都会在数据库查询内部、排序之前，按用户所属组与分块允许组的交集进行过滤。在生成之后再过滤就太晚了。
  • SharePoint 中的权限变更会在下次同步时传播；需与安全团队就可能存在的滞后程度达成一致，并为权限撤销运行更快的同步。

除访问控制之外：

  • 提示词注入：将文档文本视为数据。用户确认和服务器端 ACL 限制了注入指令可能造成的危害。
  • PII：在日志和追踪中脱敏个人数据；仅在审计策略要求时保留原始问题。
  • 密钥与网络：使用托管密钥存储，以及到模型端点的私有连接。

更广泛的威胁模型在 企业 AI 安全 中有介绍。

云

合适的服务取决于客户现有的云环境。

  • 在 AWS 上：API 和 worker 以容器形式运行在 ECS 或 EKS 上，使用带 pgvector 的 Amazon RDS for PostgreSQL，使用 Amazon Bedrock 进行生成和嵌入，使用 S3 存储原始文档副本，使用 Secrets Manager，并通过 VPC 端点确保到 Bedrock 的流量保持私有。
  • 在 Azure 上： AKS 或 Container Apps 上的容器、带 pgvector 的 Azure Database for PostgreSQL、Azure OpenAI 提供模型、Blob Storage、Key Vault 和专用终结点。已经在使用 Microsoft 365 的保险公司通常更倾向于这条路线。

用 Terraform 配置所有资源，确保各环境完全一致。我们的 面向 AI 工程师的 AWS 指南深入介绍了这些服务。

可观测性

每个请求都会生成一条追踪，包含查询重写、每条检索路径、重排、LLM 调用和工具调用的 span。记录 chunk ID 和分数、token 数、延迟、模型 ID 和提示词版本。Langfuse 或 LangSmith 提供 LLM 专属视图；OpenTelemetry 将相同的 span 接入客户现有的监控系统。

仪表盘：每日提问数、按主题统计的“未找到”率、点踩率、p95 延迟和每次回答的成本。对错误、延迟以及“未找到”率的突然飙升设置告警，后者往往意味着同步出了问题。更多内容见 AI 可观测性。

评测

在调优任何东西之前，先构建一个固定测试集。从 SME 那里收集真实问题，每个问题附带预期答案和支持的源文档章节。包括：

  • 需要精确术语的问题（表单代码、条款编号）。
  • 答案在不同文档版本之间发生变化的问题。
  • 无法回答的问题，正确行为是拒绝回答。
  • 访问控制用例：不同组的用户提出相同的问题。

检索指标：预期来源是否出现在前几条结果中（recall at k、MRR）？生成指标：对检索上下文的忠实度、答案与参考答案的正确性、引用准确性以及正确的拒绝。Ragas 等工具可以自动化其中多项；在信任任何 LLM 评判者之前，先用 SME 在样本上的打分对其进行校准。方法论以及 LLM 作为评判者的局限性，见我们的 LLM 评测指南。

对测试集进行版本管理，并把每个生产环境中的失败案例加入其中。

部署

AI 应用的 CI/CD 测试的是行为，而不仅仅是代码。GitHub Actions 流水线在每个 pull request 上运行：

  • Lint、单元测试和类型检查。
  • 访问控制测试套件（任何泄露都会导致构建失败）。
  • 在固定测试集上运行评测；如果关键指标相比主分支低于约定阈值，构建即失败。
  • 构建并扫描容器镜像；推送到镜像仓库。
  • 使用 Terraform 管理的基础设施部署到 staging；如果运行在 EKS 上，由 Argo CD 同步 Kubernetes 清单。

提示词、分块设置和模型 ID 都是版本化的配置，因此提示词的变更与代码变更走同样的门禁。分阶段上线：先面向内部 SME 小组，然后一个团队，最后推广到整个运营团队，并使用 feature flag 以便回退到仅搜索模式。AI 应用的 CI/CD 详细介绍了流水线设计。

ROI

ROI 是与客户商定的方法，而不是你单方面宣布的数字。商定输入项、测量基线、上线后进行对比。以下所有数字均为假设的占位符，仅用于展示计算方法，并非实际结果。

输入项占位符如何获取真实数值
用户数（U）例如 100 名员工试点名单
每用户每日查询次数（L）例如 5 次时间动作抽样或调查
每次查询节省的分钟数（M）例如 4 分钟任务计时，前后对比
每年工作日数（D）例如 220 天HR 日历
每小时综合人力成本（C）客户提供的数字财务部门
每年运行成本（R）来自账单云与模型用量、支持工作量

年度时间价值 = U × L × M × D ÷ 60 × C。净价值 = 时间价值 − R − 分摊的建设成本。使用占位符输入，U × L × M × D ÷ 60 每年约为 7,300 小时，再乘以 C。要打折扣：并非每一分钟节省的时间都能转化为有效工作。较软性的收益单独报告：减少因 SOP 过时导致的错误、加快入职速度，以及通过“未找到”工单发现并弥补文档缺口。

自己动手构建：里程碑计划

使用公开或自撰的文档，切勿使用真实的机密文件。

里程碑交付物
1. 语料库与测试集数十份带版本信息的文档和两个权限组；一套带预期来源的测试问题集
2. 数据摄取解析器、结构感知分块器、元数据、pgvector 索引、基于哈希的增量同步
3. 基线 RAGFastAPI /ask，支持向量搜索、引用，并记录首批评测分数
4. 质量混合搜索、重排序器、相关性阈值、引用校验；评测分数与基线对比
5. 安全OIDC 登录、按组过滤的检索、访问控制测试
6. Agent 与 MCP带“未找到”流程和用户确认；用于 Jira 或模拟工单 API 的 MCP 服务器
7. 运维追踪、仪表盘、Terraform、带评测门禁的 GitHub Actions、部署到 AWS 或 Azure
8. 价值包含占位符方法的 ROI 单页文档、演示视频、README

常见问题

RAG 项目仍然是好的作品集项目吗？

是的，前提是它超越了一个基础的聊天机器人。一个展示权限感知检索、引用、固定评测集、追踪和部署流水线的 RAG 项目，能够体现企业所需的工程能力，而 notebook 演示则做不到这一点。

企业知识助手应该使用哪种向量数据库？

PostgreSQL 配合 pgvector 是一个很好的默认选择，因为分块、元数据、权限、向量和全文检索都存放在同一个数据库中，权限过滤会非常简单。只有在规模或特定功能有需求时，才迁移到专用的向量数据库。

如何防止用户看到他们无权查看的文档？

在数据摄取时，将每个源文档的允许访问组存储在每个分块上，从用户的 SSO 令牌中读取其所属组，并在排序之前在数据库查询内部按这些组过滤检索结果。用一套访问控制测试来验证，任何泄露都会导致构建失败。

面向公司文档的 RAG 聊天机器人需要使用 Agent 吗？

不一定。先从纯 RAG 开始。只有在能消除真实摩擦的地方才加入轻量的 Agent 步骤，例如在找不到答案时提议向文档所有者提交工单，并在任何工具运行前由用户确认。

如何对 RAG 项目进行端到端评估？

构建一个固定的测试集，包含真实问题、预期答案和来源章节，其中包括无法回答的问题和访问控制场景。衡量检索召回率、忠实度、答案正确性、引用准确性以及正确的拒答，并在 CI 中对每次变更运行评测。

我可以在 AWS 或 Azure 上构建这个项目吗？

两者都可以。在 AWS 上，Amazon Bedrock 配合 RDS for PostgreSQL 以及 ECS 或 EKS 上的容器是常见的组合。在 Azure 上，Azure OpenAI 配合 Azure Database for PostgreSQL 以及 AKS 或 Container Apps，适合已经在使用 Microsoft 365 的组织。
