LLM 的评测方法是什么？详解 FDE 在现场使用的指标、流程与工具

原标题：LLMの評価方法とは？FDEが現場で使う指標・手順・ツールを解説

FDE総研 · 2026-10-05 · 约 10 分钟读完

摘要

这篇日文文章面向在客户现场工作的前沿部署工程师，系统讲解LLM评测方法。文章将评测分为自动评测、LLM-as-a-Judge和人手评测三类，强调FDE的核心任务是评测整个应用系统而非模型本身，并给出指标选择、数据集构建、改进流程和工具选型的实操建议。

要点

  • 评测分自动、LLM-as-a-Judge、人手三类，需按目的组合使用。
  • FDE重点是系统评测，公开基准好不代表客户业务数据上表现好。
  • 指标应从用例的失败定义反推，并连同延迟、成本、安全一起测量。
  • 评测流程为：定义失败、建数据集、测基线、迭代改进、上线监控。
  • 工具选型优先考虑数据存放限制和客户团队能否接手运维。

LLM 的评测方法有哪些类型？

LLM 的评测方法大致分为“自动评测”“LLM-as-a-Judge”“人工评测”三种。不是只选其中一种，而是根据目的组合使用。

LLM 的评测可以分为衡量模型本身性能的“模型评测”，以及衡量包含提示词、检索、后处理在内的整个应用质量的“系统评测”，这样思考更容易理清。FDE（Forward Deployed Engineer）在客户现场主要处理的是后者的系统评测。即使 MMLU 等公开基准的排名很好，也不一定能在客户的业务数据上按预期运行。

自动评测与 LLM-as-a-Judge 有什么区别？

自动评测是用规则或统计来衡量与正确答案一致程度的方法，而 LLM-as-a-Judge 是让另一个 LLM 进行打分的方法。

自动评测通过完全匹配（Exact Match）、基于正则表达式的格式检查、BLEU 或 ROUGE 等字符串重叠度、BERTScore 等嵌入相似度等方式机械地给出分数。它成本低、可重复，但容易给“意思相同但措辞不同”的回答打出低分。

LLM-as-a-Judge 是把评分标准（评分细则）写入提示词，让用于评测的 LLM 判定“准确性”“对依据的忠实度”等的方法。它也能评估自由撰写的回答。另一方面，Zheng 等（2023, “Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena”, arXiv:2306.05685）报告了因提示顺序而改变判定的位置偏差、偏好较长回答的冗长性偏差、对自己输出的高评价即自我偏好偏差等问题。

评测方法适合的对象强项弱项
自动评测（规则、统计）分类、抽取、固定格式输出成本低、可重复性高对改写和自由撰写较弱
LLM-as-a-Judge摘要、问答、对话能大量为自由撰写的回答打分打分不稳定、存在偏差
人工评测最终质量、业务适配性能反映现场的感觉成本高、耗时

什么时候需要人工评测？

人工评测在制定评分标准时，以及验证自动评测可靠性时不可或缺。

LLM-as-a-Judge 的打分与人的判断一致程度如何，只有与实际由人打分的样本对比才能知道。在现场，很多时候人们会感到，与业务负责人一起对最初的几十件到一百件左右的样本进行打分、并把“什么才算好的回答”用语言表述出来的过程，决定了之后整个评测的质量。与其一直全部用人工打分，不如把人力集中在标准制定和定期抽查上，这才是现实的做法。

如何选择 LLM 评测的指标？

指标要从“该用例中什么算失败”倒推来选择。除质量指标外，还必须同时测量成本和延迟。

如果先决定指标，往往会变成只测量容易测量的东西。FDE 首先要与客户一起梳理“出现这种回答就会给业务带来麻烦”的失败案例，然后选择能检测出这些失败的指标。

各用例的代表性指标有哪些？

RAG 以忠实度和检索精度为中心，分类与抽取以准确率或 F1 为中心，摘要与对话则以全面性和有用性为中心。

用例主要质量指标补充说明
分类、打标签准确率、精确率与召回率、F1标签存在偏差时重视 F1
信息抽取（JSON 输出等）字段级完全匹配、Schema 符合率格式错误可通过规则检测
RAG（内部文档问答）Faithfulness（忠实度）、Answer Relevancy、Context Precision / RecallRagas 等定义的指标
摘要全面性、事实错误的有无、ROUGE仅凭 ROUGE 难以判断质量
对话、助手有用性、语气、拒绝的恰当性以评分细则＋LLM-as-a-Judge 为中心

RAG 的指标广泛参照 Ragas 文档中的定义。将“回答是否被检索到的文档所支持（忠实度）”与“是否检索到了必要的文档（Context Recall）”分开测量，就能区分问题出在检索侧还是生成侧。

除质量外还应测量哪些指标？

在生产运营中，除质量外，还需要测量延迟、每请求成本和安全性。

即使精度很高，如果响应要花几十秒，或者每件的 API 费用不符合业务的成本效益，导入也难以推进。Stanford CRFM 的 HELM（Liang 等，2022）也提出了不仅包括准确性，还包括健壮性、公平性、偏差、有害性、效率等多方面的评测。在现场，至少把以下 4 个维度放在一起观察，讨论会更容易进行。

  • 质量：准确性、忠实度、格式符合
  • 速度：p50 / p95 延迟
  • 成本：输入输出 token 量与每件费用
  • 安全性：个人信息泄露、不当输出、对提示词注入的抵抗力

LLM 评测按什么流程推进？

LLM 评测按“定义失败→创建评测数据→测量基线→改进与再评测→生产监控”的顺序推进。

这个顺序是有原因的。如果先开始改进提示词而不先准备评测数据，就没有人能判断是否真的改进了。

评测数据集怎么建？

评测数据集由接近客户真实数据的输入与期望输出的配对组成，混合典型示例和困难示例来构建。

评测数据（黄金数据集）的制作方法如下。

  • 从实际咨询和日志中收集输入：使用前先对个人信息进行脱敏处理
  • 区分典型示例和边界示例：混合常见问题、文档中没有答案的问题、模糊的问题以及蓄意的攻击性输入
  • 标注期望输出或评分标准：对于正确答案不唯一的任务，用“应包含的要素”“不应包含的要素”来描述
  • 通过业务负责人的审核：不要仅由 FDE 决定正确答案
  • 进行版本管理：保留数据的变更历史，使分数可以比较

并不是数量越多越好。即使数量少，只要覆盖了失败模式，往往能获得更多改进的线索。也可以用 LLM 合成评测数据，但只用合成数据容易遗漏真实输入的特点，所以与真实数据结合使用比较稳妥。

改进循环怎么运转？

每次只引入一个变更，用相同的评测数据重新评测，比较前后的分数和失败案例。

如果同时改变提示词、模型、分块方式和检索条数，就无法知道哪个变更起了作用。不仅要看分数的平均值，还必须亲自查看“改进前正确、改进后失败的案例（退化）”。将发布前的评测集成到 CI 中，分数低于标准就阻止合并，这样也能把质量标准传承给后来加入的成员。

LLM 评测有哪些可用工具？

LLM 评测工具分为评测指标库、测试执行工具、追踪与监控平台三大类来选择。

与其用一个工具包办所有事情，不如在开发时的测试和生产环境的监控中分工，这样往往更易于运维。

有代表性的 LLM 评测工具有哪些？

Ragas、DeepEval、promptfoo、LangSmith、Langfuse、Arize Phoenix 等比较常用。

工具类别主要用途提供形式
Ragas评测指标库面向 RAG 的指标（忠实度、Context Recall 等）OSS（Python）
DeepEval评测指标与测试pytest 风格的 LLM 测试、LLM-as-a-Judge 指标OSS（Python）
promptfoo测试执行提示词与模型的比较、红队测试OSS（CLI / Node.js）
OpenAI Evals评测框架评测任务的定义与执行OSS＋OpenAI 平台功能
LangSmith追踪与评测平台追踪、数据集管理、评测执行SaaS（LangChain 公司）
Langfuse追踪与评测平台追踪、分数记录、提示词管理OSS（可自托管）＋云服务
Arize Phoenix追踪与评测平台追踪可视化、评测OSS
MLflow实验管理LLM 评测结果的记录与比较OSS

各工具的功能和定价体系更新很快，引入前请通过官方文档确认最新规格。

工具该怎么选？

优先考虑客户的数据能放在哪里，以及能否融入现有的开发和运维体系。

比功能对比更应优先确认的是数据的处理方式。金融、医疗、公共领域的客户，有时无法将提示词或日志发送到外部 SaaS，可自托管的 OSS（如 Langfuse、Arize Phoenix）会成为候选。其次是客户工程师能否接手。FDE 离开后无人能运维的评测平台，最终会被弃用。以 Python 为主的组织可选 Ragas 或 DeepEval，想以 CI 为中心运转则可选 promptfoo，总之要贴合客户团队的技术栈来选择才稳妥。

FDE 在客户现场进行 LLM 评测时需要注意什么？

FDE 需要与客户一起制定评测标准，并特别注意数据的处理方式和评测结果的说明责任。

由 Palantir 推广的 FDE 这一职位，其职责是深入客户现场，使产品在实际业务中可用。LLM 评测也一样，不仅要技术上正确，还必须能用于客户的决策，否则毫无意义。

如何与客户就评测标准达成一致？

在评测之前，用书面形式就“达到百分之多少才能上线”的合格线以及绝对不可容忍的失败达成一致。

由于 LLM 的输出是概率性的，无法保证 100% 的准确率。在现场提前确定以下事项，可以大大减轻之后的争论。

  • 合格线：主要指标的目标值及其依据（例如与人工处理时的错误率进行比较）
  • 致命失败：如给出错误金额、输出个人信息等，哪怕出现一例也必须停止的失败
  • 需要人工确认的范围：划分自动化范围与由人做最终判断的范围
  • 重新评测的条件：模型更新、文档追加、业务规则变更的时机

数值目标会因客户的业务风险而有很大差异，所以最好不要指望存在通用的“正确数字”。

数据和安全方面需要注意什么？

评测数据包含实际业务的信息，因此首先要确认脱敏、保存位置以及能否发送到外部 API。

使用 LLM-as-a-Judge 时，需要把被评测的输入和输出发送给评测用 LLM。即使生产系统运行在封闭网络环境中，却只有评测流水线把数据发送到外部 API，这是容易出现的疏漏。要连同评测数据集、日志以及裁判模型的调用目标一起，与客户的信息安全部门进行确认。

还有一点需要注意的是评测结果的传达方式。如果只报告平均分数，决策者只能了解到“大致能跑”。将具有代表性的成功案例和失败案例并列展示，并用业务语言说明“在哪类问题上、以何种方式出错”，才能成为追加投资和运营设计的判断依据。评测不仅是衡量质量的手段，更是让客户与 FDE 看到同一现实的共同语言——这是我作为一线实务工作者的切身感受。
