Postman 联合创始人从 AI 优先时代学到了什么

原标题：What Postman's Co-Founder Learned About the AI-first era

Rocketlane · 2026-06-15 · 约 7 分钟读完

摘要

Postman 联合创始人 Ankit Sobti 在 Propel 26 分享公司从产品驱动增长转向企业级服务的过程：PLG 让 Postman 进入 98% 的财富 500 强，但要落地企业 AI 价值，仍需建立专业服务团队与 FDE 职能。他提出 AI 落地需要智能层、数据层与 API 执行层三者协同，并警告好坏模式都会复利式放大，组织需从第一天起建立可观测性。

要点

  • PLG 让 Postman 进入 98% 的财富 500 强，但企业级价值需靠专业服务与 FDE 实现。
  • API 是 AI Agent 的执行层，没有 API，智能只能停留在推荐。
  • AI 落地需三层协同：智能层、数据层与 API 执行层，只做模型层易止步于演示。
  • 好坏模式都会复利，快速实验的同时必须建立可观测性与成功度量。
  • FDE 应作为产品反馈引擎，沉淀可复用模式并反哺产品。

从 PLG 天花板到企业级深度：为什么 API、AI Agent 和复利模式决定了你的 AI 投资是创造势能，还是放大问题。

产品驱动增长让 Postman 进入了 98% 的财富 500 强企业。但据联合创始人 Ankit Sobti 所言，仅靠产品本身并不足以释放企业级价值。

随着 AI 应用的加速，Postman 面临着一个新的挑战：帮助客户将实验转化为成果。这意味着要组建专业服务团队，建立前沿部署工程（FDE）职能，并重新思考企业要真正做好 AI 准备究竟需要什么。

在 Propel 26 大会上，Sobti 回顾了这段历程——从扩展全球应用最广泛的开发者平台之一，到帮助客户在企业级规模上落地运营 AI。

对话涵盖了 API、AI Agent、交付准备度，以及每一位专业服务负责人都应铭记的警示：好的模式会复利增长，坏的模式同样如此。

请继续阅读，了解本次会议的核心要点。

Sobti 给出了整个 Propel 26 大会上关于 AI 技术栈最清晰的解释之一：

“API 是将 AI Agent 或 AI 的概率性思考转化为行动的手和脚。”

AI Agent 可以推理、规划和推荐。但如果没有能够执行这些决策的系统，它们实际上什么也做不了。

更新客户记录。触发工作流。发送通知。修改项目状态。从企业系统中提取数据。

所有这些操作最终都要通过 API 来完成。

正因如此，Sobti 将今天的 AI 浪潮视为 Postman 最初使命的延伸，而非背离。在 AI 出现之前，API 帮助企业开放能力并创造新的商业价值。如今，这些同样的 API 已成为智能 Agent 的执行层。

这对专业服务团队的影响是深远的。

AI 实施不再只是软件部署，而是运营部署。服务团队越来越多地承担起帮助客户将智能与行动相连接的责任——而这需要安全、可发现且治理良好的 API。

随着组织部署越来越多的 Agent，实施复杂性也在增长。每一个新的工作流都会引入依赖关系、集成、治理要求和运营风险。

问题不在于客户是否会采用 AI，而在于他们的底层系统是否已准备好支持 AI。

本次会议中最实用的框架之一，是 Sobti 对为什么许多 AI 项目尽管早期成果喜人却依然停滞的解释。

大多数组织几乎只关注 Agent 层。

他们选择一个模型。选定一个平台。构建一个概念验证。然后就开始疑惑为什么应用推广停滞不前。

据 Sobti 所说，成功的 AI 部署需要三个层级协同运作：

这正是大多数组织投入精力的地方。

  • 我们应该使用哪个模型？
  • 使用哪个编排框架？
  • 使用哪个 Agent 平台？

这些都是重要的问题——但它们只占问题的一部分。

Agent 需要上下文。

在许多组织中，机构知识散落在文档、会议、Slack 对话以及资深员工的头脑中。

如果这些知识没有经过结构化、无法被发现和访问，Agent 就无法可靠地基于它们进行运作。

这往往就是实施开始出问题的地方。

即使具备了智能和上下文，Agent 仍然需要执行的方式。

如果 API 没有文档、难以发现、缺乏治理，AI 系统就会变成推荐引擎，而非执行引擎。

正如 Sobti 所解释的：

“我需要这三者协同运作。我需要 Agent 拥有智能系统，需要数据层作为记录系统，还需要通过 API 构建行动系统。”

对于专业服务负责人来说，这为实施提供了一个有用的视角。

在规划 AI 项目之前，先评估这三个层级。只专注于模型的组织，往往最终只能做出令人印象深刻却永远无法投入生产的演示。而在数据、流程和执行基础方面投入同等精力的组织，则更有可能取得持久的成果。

Sobti 最强烈的警告并非针对技术。

而是针对组织行为。

“好事会复利，坏事同样会复利。”

他描述了一个许多领导者都会感到熟悉的场景。

一位工程师试用某个 AI 工具，解决了一个真实的客户问题。结果在内部传开，其他团队纷纷效仿这一做法。领导层首先认可这一成功，薪酬方案开始奖励这种行为。

几个月后，组织发现其背后的假设是有缺陷的。

到那时，这种模式已经渗透到各个角落。

  • 流程依赖它。
  • 围绕它组建团队。
  • 客户期待它。

最初只是局部优化的东西，已经成为运营模式的一部分。

挑战不在于 AI 本身，而在于 AI 加速好决策和坏决策的速度。

Sobti 的建议并不是放慢实验的脚步。

恰恰相反。要快速行动，积极学习，但从第一天起就在系统中构建可观测性。

组织行动得越快，就越需要了解表面之下实际发生的事情。

对于专业服务负责人来说，这一经验直接适用于交付运营。在将新的工作流、流程或 AI 能力推广到整个组织之前，先明确成功的标准，并建立持续衡量的机制。

否则，你最终会发现问题和成果一起增长。

Sobti 的三层框架揭示了许多服务组织今天面临的挑战：AI 就绪度不仅仅是一个技术问题。

它是一个运营可见性问题。

专业服务团队往往要在彼此割裂的系统中管理项目、客户沟通、资源规划、实施流程和业务成果。这种碎片化使人难以判断新的 AI 驱动流程是否真正创造了价值——还是在悄然引入风险。

这正是记录系统变得至关重要的地方。

Rocketlane 为交付组织提供项目执行、客户协作、资源分配和交付成果的统一视图。当团队开始将 AI 引入实施和上线流程时，这种互联的基础让衡量结果、识别新出现的模式以及在问题蔓延到整个项目组合之前发现它们变得更加容易。

Sobti 所描述的同一原则在这里同样适用：良好的交付习惯会复利累积，坏习惯也是如此。可见性决定了哪一种能够存续。

Sobti 从产品驱动增长到企业级交付的历程揭示了许多远远超出 Postman 范畴的经验。

先建 PS，再建 FDE。 Postman 在大力投入前沿部署工程之前，先建立了专业服务机制。服务创造了客户信任，浮现出高价值问题，并产生了证明更深投入合理性的洞察。

把 FDE 用作产品反馈引擎。 目标不是永远为某一个客户解决问题，而是识别可复制的模式、验证需求，并把成功的解决方案反馈到产品中。

赢得解决更大问题的资格。 每一次成功的合作都会创造信任。这种信任会随着时间推移成为解决更具战略性的客户挑战的基础。

谨慎扩展，快速学习。 从可见的客户成果开始。让结果驱动采用，而不是靠组织指令。

Ankit Sobti 的分享其实并不是关于 API 的。

它是关于杠杆的。

API 是让 AI Agent 得以行动的机制。但对专业服务领导者而言，更广泛的启示是：每一个决策都会复利累积。交付流程会累积。客户信任会累积。AI 采用模式也会累积。

脱颖而出的组织未必是部署最多 AI 的那些，而是那些先打好正确基础的组织：可信的数据、可观察的交付系统，以及客户、服务团队和产品组织之间清晰的反馈闭环。

Sobti 主张，要快速行动。

只是要确保你能看清自己正在加速的是什么。

这正是 AI 试验与 AI 优势之间的根本区别。

“

“加快了 CSV 导入速度，让我不必再要求客户使用模板文件或创建映射好的数据导出。集成快捷，在常规流程之外也很灵活。我们发现定义工作簿和模板令人困惑；在之前的工作中，它是通过代码配置的，我更喜欢那种方式。”

企业实施失败的原因是客户不遵循流程或未能按时提供干净的数据。大多数延误纯粹是“客户侧”问题。

实施失败是因为复杂环境需要实时技术问题解决能力。FDE 能打通传统上线团队无法自行解决的工作流、集成和未知限制。
