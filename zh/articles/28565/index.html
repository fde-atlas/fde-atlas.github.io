接手一个被放弃的项目：第一周

原标题：Taking over an abandoned project: the first week

FDE Times · 2026-11-15 · 约 7 分钟读完

摘要

这篇文章面向接手他人遗留项目的 FDE，提出第一周的目标不是修复而是摸清现状。作者综合 Thoughtworks、Wavect、Redwerk 等来源，给出五天计划：盘点资产归属、建立生产环境基线、以数据库而非文档为准了解系统，最后用书面评估和预算负责人确认重建清单。核心观点是“全部重写”是结论而非起点，多数遗留代码只需重构，判断应基于证据而非直觉。

要点

  • 第一周目标是维持业务正常运转，而非改进。
  • 先做资产归属清单，每个“未知”都是具体风险。
  • 建立带时间戳的基线，区分新旧故障并证明改进。
  • 文档描述意图，数据库反映现实，以数据库为准。
  • 重建清单需预算负责人签字，成为共同承诺。

简要说明

  • 第一个目标是让业务照常运转，而不是先做任何改进。
  • 先读真实的系统，再读文档：当两者不一致时，以数据库为准。

周一，你来到客户的办公室。前任承包商已经离开，留下一个代码仓库、几个似乎没人知道密码的云账户、一条半能用的流水线，以及一个不断追问“什么时候能做完？”的领导团队。所有人都想先得到解答的问题是：要不要推倒重来。

这个起点就是错的。一篇关于 AI Codex 项目范围界定的文章指出，大多数偏离正轨的前沿部署项目，在第一周结束时就已经注定了结局。在接手项目中，这第一周的分量更重：你继承的不仅是系统，还有客户在一段半途而废的合作之后残留的种种疑虑。

接下来的内容将带你走完头五天：先盘点现有的一切，然后以能用数字向客户有理有据地说明的方式，确定需要重建的事项清单。

第一项工作不是修复

Thoughtworks 在描述一次大型遗留系统的接手时，设定了一个刻意低调的近期目标：至少，让业务照常运转。不做改进，不做优化。只要不破坏已经在运行的东西。

这听起来显而易见，但现场的压力却把人往相反的方向推。客户想看到进展，而“展示进展”最快的方式就是提交代码。问题在于，在你理解系统之前所做的每一处改动都是一场赌博，一旦出错，责任会记在你的名下，而不是前任承包商的。

因此，第一周有三项交付物：一份所有权清单、一条生产环境基线和一份书面评估。重建清单正是从这三者中产生的。

谁才真正掌握着钥匙？

Wavect 的 30 天接手计划要求，在第 1 至 5 天，你要为每一项资产记录：账户的法定所有者、付款方、管理员、恢复联系人以及交接路径。

这里的资产指一切：域名、云账户、代码仓库、第三方 API 密钥、邮件发送账户，甚至任务跟踪工具的工作区。

设想一个物流客户，其订单分拣系统被前任承包商留了个半成品。到第二天结束时，清单可能是这样的：

资产法定所有者付款方管理员恢复交接
主域名客户客户前任承包商承包商的邮箱通过注册商更换管理员
云账户前任承包商前任承包商，已转付前任承包商未知转移账户或重建
代码仓库客户的组织客户两名承包商开发者客户移除访问权限，添加新团队
LLM 服务 API 密钥未知承包商的信用卡未知未知需要核实

每一个“未知”单元格都是你现在可以明确指出的具体风险。这个例子中的中间两行比任何糟糕的代码都更危险：如果承包商停止支付云账户费用，系统就会关停，而客户方没有任何人有权限将其重新开启。

当你开始轮换密码和访问密钥时，Wavect 指出了一个容易被忽略的要点：回滚权限必须掌握在客户手中。不要成为下一个前任承包商，成为唯一持有密钥的人。

先测量，再改动

第二项交付物是基线。Wavect 列出了在任何改动之前需要记录的内容：流量、错误率、延迟、队列深度、备份状态、未解决的事故、支持工单数量以及已知发布的状态。

这样做的目的是，日后能够区分哪些故障是你造成的，哪些是你接手时就存在的。假设订单分拣系统有 4% 的请求失败。

如果没有测量，你在周四部署了第一个补丁，客户在下周看到 4% 的错误率，就会质问你为什么把它弄坏了。有了带时间戳的基线，你就可以指着数据说：系统本来就在这个水平，这是降低它的计划。

基线也是日后每一次关于价值的谈话的基础。没有起点，就没有人能证明事情改善了多少。

相信数据库，而不是文档

前任承包商通常会留下文档，而文档通常比现实更漂亮。AI Codex 建议在索取文档之前先申请真实系统的只读访问权限，因为文档描述的是意图，而数据库描述的是现实，当两者不一致时，数据库是对的。

在物流的例子中，文档可能写着每个订单都会自动分拣。一个按状态统计订单数量的查询可能显示，很大一部分订单停留在“等待人工审核”的状态。这个差距正是客户花钱要解决的问题，而文档的任何一页都没有提到它。

dev.to 上的一篇关于从代理商手中接管代码库的指南建议，把最初的 48 小时完全用来阅读。在这段时间里，先阅读代码、日志、提交历史和数据库结构，然后再动手改动任何东西。

为了把握全局，Thoughtworks 将接手的架构绘制成 C1/C2 图，并在一张地图上跟踪接管进度，用绿色标记表示已完成的服务，灰色表示仍在等待的服务。

这样一张地图也是你每周五下午可以交给客户的最佳汇报工具。

用标准而非感觉来敲定重建清单

到第四天，你已经拥有足够的数据来对每个组件进行分类。Wavect 写道，“全部重写”是一个结论，而不是一种起步方法。

Redwerk 给出了更明确的规则：当架构健全而混乱只存在于细节中时就进行重构，而且关于遗留代码的大多数决策最终都以重构收场，因为混乱的代码远比真正损坏的代码常见。

应用到这个例子：如果从订单系统到分拣机的数据流向是正确的，但代码重复且缺乏测试，那就是重构。

如果分拣机直接写入生产数据库而没有队列，导致每次故障都会丢失订单，那就是架构问题，重建该部分是有理由的。

两个组件得出两种不同的结论，而不是对整个系统一律“推倒重来”。

Thoughtworks 使用一份标准模板作为接管每个服务的验收标准。你也可以这样做：只有当每项资产的所有者都已明确、它有了基线、新团队中有人能够部署并回滚它，并且它已被归入三个组之一——保留、重构或重建——时，该服务才算“变绿”。

书面评估及其签署人

dev.to 指南强调：在改动任何东西之前，先写一份文档。第五天的评估包含资产清单、基线、服务地图以及分类列表及每项的理由。

但如果文档送错了读者，光有文档是不够的。AI Codex 建议持续推动，直到获得一个可衡量的成功定义，并得到掌控预算的人的认可。

在物流的例子中，这可能是“需要人工审核的订单比例在 Y 周内降至 X”，其中 X 和 Y 由客户根据你刚刚测得的基线来设定。

一旦预算负责人签字确认，重建清单就不再是你个人的意见，而是一份共同的承诺。

常见错误

最常见的错误是在第一天就动手修东西以“挣表现分”，之后却无法展示系统之前有多糟糕。其次是未打开数据库就轻信交接文档。

另一个常见错误是轮换了所有凭据却把管理员权限留给自己，这恰恰重复了你被雇来要解决的问题。最后，是与最友好的用户而不是掌握预算的人来确定范围。

接管技能应写进你的简历

阅读 FDE 职位描述时，留意提到要处理客户现有系统的字句：那正是接管技能将被用到的地方，也是你的简历中值得放一个具体例子的地方。

本周的练习：挑选一个你负责维护但并非由你构建的系统，假设它的承包商明天早上突然消失，然后在一个下午写出一页纸的评估。你数出的“未知”单元格数量，就是客户在不知情的情况下承担的风险。
