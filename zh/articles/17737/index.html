FDE 需求发现方法：如何找到客户的真问题

FDE Times · 2026-10-08 · 约 4 分钟读完

摘要

文章综合 Learn Cursor 的 FDE 面试课程与 Perspective AI 的需求发现手册，主张把客户提出的需求当作待验证的假设。以 PR 评审自动化为例：表面需求是自动化，真实瓶颈是只有两位 staff 工程师有权批准且不堪重负。文章给出五阶段方法（界定范围、访谈、综合、验证、写规格），每个阶段有明确完成标志，并指出跳到方案、只访谈提需求者、规格需再开会解释这三个常见错误。这项能力也是 Palantir 等公司 FDE 面试问题拆解环节的考察重点。

要点

  • 客户需求只是假设，验证假设可省下三周做错东西的时间。
  • 用回顾最近一次上线变更的提问法，找到真实等待环节。
  • 五阶段各有完成标志：一页纸画清人和系统、规格免开会即可构建。
  • 三大错误：急于给方案、只访谈提需求者、规格含糊需再解释。
  • Palantir 面试的问题拆解环节考察的正是这种提问与拆解能力。

把每个需求都当作待验证的假设，问对几个问题，就能少花三周做错的东西。

要点速览

  • 客户提出的需求只是一个假设：“自动化 PR 评审”的背后，可能是只有两个人有权批准。
  • 需求发现分五个阶段；人和系统能画在一页纸上，界定范围才算完成；队友不用再开会就能动手构建，规格才算完成。
  • FDE 面试的问题拆解环节考的正是这项能力：优秀候选人会把前十分钟用来提问。

设想客户发来一句话：“团队需要一个能自动评审 pull request 的工具。”方案立刻在你脑子里成形：一个 Agent，读 diff、写评论、给出风险评分。三周后你做完演示，客户说效果很好，可从提交 PR 到合并的时间和以前一模一样。

Learn Cursor 的前线部署工程师（FDE）面试课程，开篇就是这个场景。客户的工程师递给你一份问题描述，而按照课程的说法，这几乎从来不是真正的问题。

在这个例子里，瓶颈并不是缺少自动化。评审要花四天，是因为只有两位 staff 工程师有权批准，而这两人都被工作压得喘不过气。

对想转做 FDE 的开发者来说，正是这项能力把 FDE 和只会接工单的人区分开。写代码你已经会了，要学的是把模糊的需求变成一份客户和队友都认可方向正确的计划。

需求只是一个假设

Perspective AI 在 2026 年 7 月发布的 FDE 需求发现手册，从一个听上去有点直白的前提出发：客户说他们需要的，并不是他们真正需要的。这不是因为客户撒谎。他们描述的是自己能想到的方案，用的是自己熟悉的工具的语言，而不是在描述工作卡在了哪里。

所以，“我们需要自动化 PR 评审”应该读作“客户认为自动化评审能让一切变快”。这是一个假设，你的第一项工作就是检验它。假设成立，你构建时更有底气；假设不成立，你刚刚省下了三周。

什么问题能让问题翻转？

常见的错误是问客户“你想要哪些功能？”。这只会让对方把原来的需求再说一遍。Learn Cursor 建议的问法正好相反：请客户带你回顾最近一次上线的变更，指出它在哪里等得最久。

这个问题之所以管用，是因为它把对话拉回到真实发生过的事情上，有日期，有具体的人。下面用一段假设的对话说明它如何展开：

FDE： 能带我回顾一下你们团队最近上线的一次变更吗？从提交 PR 到进入生产环境，它在哪里等得最久？

客户： 应该是评审。PR 提交后，大概要四天才有人批准。

FDE： 这四天里由谁来批准？他们在等什么？

客户： 只有两位 staff 工程师能批准。他们还要负责 on-call 和系统设计，手上总是堆着十几个 PR。

到这里，问题已经变了。一个自动写评论的 Agent，并不能让 PR 离开这两个人的队列。更合理的方案也许是帮这两人评审得更快，或者明确哪些变更需要他们、哪些不需要，但具体选哪个，要先和客户验证过再定。

五个阶段，各有完成标志

一个好问题还算不上方法。Perspective AI 的手册把需求发现分成五个连续阶段：界定范围（Scope）、访谈（Interview）、综合（Synthesize）、验证（Validate）和写规格（Spec）。每个阶段都有一个条件，告诉你何时可以进入下一阶段。

界定范围的完成标志，是你能在一张纸上画出涉及的人和系统。在 PR 的例子里，这张纸上有写代码的人、两位批准人、CI 系统和代码仓库。这一阶段以明确决策点收尾：系统要帮谁采取什么行动。如果这句话你说不出来，就还没准备好去访谈。

访谈阶段，要用上面那种基于事件的问题，去问每天真正干活的人，而不只是提需求的那个人。综合是把听到的内容归纳成若干机会，并排出优先级。很多人都提到的瓶颈，通常比某一个人的抱怨更值得关注。

验证阶段，要回到客户的领域专家那里，确认排在首位的机会确实最值得构建。手里有了排序，你会很想跳过这一步，而这正是它必须保留的原因。最后，写规格以“交接测试”来判断：队友拿着规格说明，不用再开任何会就能动手构建。

让需求发现失败的几个错误

第一个、也是最常见的错误，是直接跳到方案。techinterview.org 对 FDE 面试的分析描述的正是这种情况：候选人一听完问题，就急着给出方案。在实际工作中，这个错误的结果是一个精美却没人用的演示。

第二个错误是只和提需求的人交流。提工单的工程师看到的是症状，两位批准人才知道队列为什么这么长。如果你那张一页纸的图上只有一个名字，几乎可以肯定漏掉了人。

第三个错误是写出一份需要另开会解释的规格。队友要靠开会才能看懂规格，说明决策还留在你脑子里。回头检查一下：决策点写下来了吗？为什么选这个机会写清楚了吗？

面试考的正是这项能力

这不只是入职以后才用得上的能力。据 techinterview.org 介绍，Palantir 的问题拆解环节考察的是把一个模糊的现实挑战拆成小块、再提出方案的能力。优秀候选人会把前十分钟用来提问。

所以准备面试时，要训练自己克制住马上画架构图的冲动。先问谁在用、工作卡在哪里、哪个决策在等着，然后把人和系统的关系图口头讲出来，再提出任何方案。

简历上，与其写“构建了工具 X”，不如写一句：某次你发现原始需求是错的，以及你如何调整了方向。这样一句话，展示的恰恰是问题拆解环节要考的能力。

下次收到一句话的需求，先别打开编辑器，先拿出一张白纸。如果还画不出谁在等谁，你就还不知道该做什么。
