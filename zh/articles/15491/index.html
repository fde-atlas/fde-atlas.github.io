Palantir FDSE 面试：重构与学习

原标题：Palantir FDSE interview: re-engineering, learning

FDE Times · 2026-10-09 · 约 7 分钟读完

摘要

本文介绍 Palantir 前沿部署软件工程师现场面试中的重工程与学习两轮，强调评分看系统性排查过程而非速度，并给出可自建的练习方法：向代码植入逻辑 bug、从错误输出反推原因、先预测再运行陌生 API，以及如何提问与避免常见失误。

要点

  • 重工程轮给 200–1000 行陌生代码，60 分钟修复逻辑 bug。
  • 正确方法是从错误输出反推输入，逐次只改一处。
  • 学习轮考察陌生 API，应先细读文档再动手。
  • 提问要讲清当前理解，问高层问题而非细节。
  • 这套排查流程同样适用于客户现场的遗留系统。

简要说明

  • 重构轮通常是一个 200–1,000 行的代码库，产生错误结果。Bug 出在逻辑上，而不是语法上，面试官观察的是你是否系统性地调试。
  • 强的候选人从错误的输出出发，回溯到输入。在某个位置猜测、打补丁然后重新运行，这种做法往往会导致被拒。
  • 在学习轮中，仔细阅读文档，大声说出你的理解，并提出高层次的问题。长时间的沉默很容易被解读为卡住了。

你会拿到一个 200 到 1,000 行、从未见过的代码库。它产生错误的结果，你在 CodePair 中有 60 分钟来修复它。Bug 可能只是一个从减号变成了加号的符号。

这就是 Palantir 前沿部署软件工程师现场面试中的重构练习。现场面试从五种类型中抽取最多四轮：分解、重构、编码、学习和系统设计。本指南涵盖其中两轮：重构和学习。

这两轮都值得认真练习，因为它们贴近真实工作。重构意味着与现有系统打交道：理解它、评判它，然后扩展或修复它。这是对 FDE 处理客户遗留系统工作的相当忠实的模拟。

学习轮给你一个陌生的工具或 API，并期望你立即使用它。当你必须使用客户已有的任何工具时，这也是一种熟悉的情境。

评分的是过程，而不是速度

Aced/Exponent 指南明确指出，面试官关注的是你的调试过程是否系统化，而不是你多快发现第一个 bug。根据 TechPrep，这一轮还衡量你花多长时间才能理清一个混乱的代码库并开始产出有用的成果。

因此，刷大量题目是不够的。你需要把一个流程练习到成为条件反射。下面的步骤展示如何在你的笔记本电脑上构建一个小型练习集来做到这一点。

你需要：Python 3、一个编辑器、一个计时器以及一种录制自己的方式。一位愿意扮演面试官的朋友就更好了。

第 1 步：向一段代码中植入 bug

Palantir 题目中的 bug 是逻辑 bug：符号翻转、对排序顺序的错误假设，或者一个变量在循环迭代之间没有被重置。下面的代码是为练习而写的，不是真实的面试题。它故意包含那三类 bug 中的两类。

# ledger.py — a self-built exercise with planted bugs
def net_by_customer(txns):
    result = {}
    total = 0
    current = None
    for cust, kind, amount in sorted(txns):
        if cust != current:
            if current is not None:
                result[current] = total
            current = cust
        if kind == "refund":
            total += amount
        else:
            total += amount
    result[current] = total
    return result

txns = [("A", "sale", 100), ("A", "refund", 30), ("B", "sale", 50)]
print(net_by_customer(txns))

运行

python3 ledger.py

。正确结果是 A 为 70，B 为 50。而它实际打印的是

{'A': 130, 'B': 180}

。检查：如果你看到的正是这两个数字，练习就准备就绪了。

第 2 步：从错误的输出反向推导到输入

优秀的候选人会顺着数据从输出回溯到输入；瞎猜乱试只会导致被拒。从最明显错误的数字入手。

B 的结果是 180，但客户 B 只有一笔 50 的交易。多出的 130 必然来自别处，而 130 正是 A 的数值。向上追溯，你会发现

total

把 A 的全部余额都带给了 B，因为当客户切换时它从未被重置为 0。

接下来看 A。它显示 130 而不是 70，差了 60，正好是 30 退款的两倍。恰好是某个数值两倍的偏差是符号翻转的经典迹象：代码在应该减去 30 的地方加上了 30。现在你有了两个假设，都是从数字本身推导出来的，而不是凭直觉。

检查：每修复一个 bug 后重新运行，看看哪个数字变对了。每次只改一处，这样你才能确定哪个改动产生了哪个结果。

第 3 步：在修复任何东西之前先通读整个代码块

Aced/Exponent 建议在确定修复方案之前，先从头到尾通读整个代码块，因为最显眼的问题未必是真正的问题。在

ledger.py

中，很多人看到

sorted(txns)

就立刻怀疑是排序的问题。实际上，按客户排序恰恰是循环正确分组所需要的。

要单独练习排序顺序的 bug，可以写一个额外的函数，把

txns[0]

当作客户的首次交易，然后输入一份不按时间顺序排列的数据。接着问自己：这段代码假设输入是什么样的，谁来保证这个假设成立？

第 4 步：把每个假设大声说出来

在解题过程中，按照这个模式说话：“输出哪里错了。我为什么怀疑它。我将如何验证。”录下完整的 60 分钟。回放时，数一数你在没有先陈述假设的情况下改了多少次代码。每一次都是你在瞎猜。

学习环节：比你想的更仔细地阅读文档

学习环节会给你一个陌生的概念或小型 API，并要求你用它构建一些东西。据 Leonstaff 所说，最常见的失败原因是浏览一遍文档，然后猜测 API 的行为。

如何练习：在你的语言的标准库中选一个你从未接触过的模块。先花 20 分钟只读文档，然后写一个目的明确的小脚本。每次调用函数之前，大声说出你期望它返回什么，然后运行它来验证。

先预测，后运行：用 groupby 练一次

下面是一段使用 Python 的

itertools.groupby

的示例练习，假设你从未用过它。自设任务：统计每位客户的交易次数。

from itertools import groupby
custs = ["A", "B", "A"]
print([(k, len(list(g))) for k, g in groupby(custs)])

只浏览文档的人只看到“group by”这个名字，然后按 SQL 的方式预测：

[('A', 2), ('B', 1)]

。运行后你得到

[('A', 1), ('B', 1), ('A', 1)]

。预测错了，而这正是你的心智模型需要修正的时刻。

回到文档，你会发现

groupby

只对具有相同键的连续元素进行分组，因此输入必须先排序。改成

groupby(sorted(custs))

就能得到

[('A', 2), ('B', 1)]

。这也是为什么

sorted(txns)

在

ledger.py

中不算 bug。

会话结束后检查：你至少写下了一处预测与文档不符的地方，并且能解释原因。在面试室里，一句“我原以为它会对所有元素分组；结果它只对相邻元素分组”这样的话，就能向面试官展示你是如何学习的。

少提问，但要在正确的层面提问

先解释你目前对问题的理解，让面试官在你确定方案之前纠正你的心智模型。但问太多细节问题会让你显得需要别人手把手指导。

对比两个问题。“这个函数返回的是列表还是字典？”是你自己可以查到的。“我的理解是这个 API 按批次工作；如果我理解错了，我会修改设计”则向面试官展示了你思考的层面。

长时间的沉默很容易被解读为卡住了，即使你实际上在思考。如果你需要安静地阅读，请先说明：“给我两分钟时间读一下认证部分。”

常见错误

第一种是修好第一个看起来不对的地方，然后重新运行看看会发生什么。第二种是一次性改动多处，导致即使结果正确，你也无法解释原因。

第三种，在学习环节中，是凭对某个外观相似的库的记忆来填补文档中的空白，这正是

groupby

.

这项技能在客户现场的应用

想象你刚到一位客户那里，他们报告说一张汇总表的数据对不上。这条流水线是别人多年前写的，目前也没有人可以请教。方法与

ledger.py

相同：选取一条具体的错误记录，测量差异，逐步回溯每个转换步骤，并在修复任何东西之前向客户清楚地陈述你的假设。

在简历上，不要只写“调试过遗留系统”。而是这样组织：错误的输出是什么样的，你如何隔离问题，以及你修复了什么。阅读职位描述时，“现有系统”或“不熟悉的工具”这类措辞表明该职位恰恰需要本指南所训练的这两项技能。

Palantir 的面试官不会因为你多快发现第一个 bug 而加分，而是看你如何去寻找它。这种系统性的找 bug 方法，也是你面对客户的系统时需要带上的能力。
