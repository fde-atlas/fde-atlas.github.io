为什么 Agentic AI 正在催生对前沿部署工程师的需求

原标题：Why Agentic AI Is Creating Demand for Forward Deployed Engineers

Cloud Soft Solutions · 2026-10-06 · 约 13 分钟读完

摘要

文章认为，AI 从“回答问题”变为“执行操作”后，企业部署的工程难度大幅上升。聊天机器人答错只是小问题，而 Agent 错误操作真实系统则构成事故。作者区分聊天机器人、RAG 助手与 Agent 三类系统的风险差异，并详细说明 Agent 部署所需的工具设计、最小权限身份、人工审批、幂等性、审计、回滚与成本控制。文中以海德拉巴一家 GCC 的 ServiceNow 服务台 Agent 为例，展示前沿部署工程师需与客户共同确定的权限范围、审批规则、评测集与灰度发布等决策。文章指出 MCP 只是标准接口，客户特定的集成、治理与评测工作无法产品化，这正是 FDE 需求增长的结构性原因，并列举常见错误与所需技能。

要点

  • Agent 会真实操作系统，出错即事故，风险远高于聊天机器人。
  • 部署需工具设计、最小权限、人工审批、幂等、审计与回滚。
  • MCP 只是标准接口，客户特定集成仍需人工工程。
  • 以 GCC 服务台为例说明权限、审批、评测等本地化决策。
  • 各客户系统、政策与身份体系不同，FDE 需求因此增长。

一个给出错误答案的聊天机器人只是带来不便。而一个采取错误行动的 Agent——比如关闭了错误的工单、给错误的客户发了邮件或修改了错误的记录——则是一起事故。Agentic AI 正在创造对前沿部署工程师的需求，因为一旦 AI 能够在企业系统内部执行操作，每一次部署都需要有人来设计工具、界定权限、定义审批规则，并根据该客户自身的系统和策略评估行为，而这些工作无法完全打包成产品。 模型在所有客户那里都是一样的。但集成、身份和风险决策每次都不同。

如果你想了解关于为什么集成已成为企业 AI 瓶颈的更全面的职业论述，请阅读 为什么 AI 工程的未来是前沿部署工程。本文聚焦于一个更具体的问题：Agent 究竟在哪些方面提高了门槛，以及一个 agentic AI 工程师实际需要构建什么、决策什么。

聊天机器人 vs RAG 助手 vs Agent

这三者常被笼统地归为“GenAI 应用”，但它们带来的工程负担截然不同。区别不在于模型有多聪明，而在于系统被允许触碰什么。

影响范围一个用户收到一个错误答案错误或泄露的答案，可能来自用户本不该看到的文档错误的记录被修改、错误的人被通知，且操作以机器速度重复执行

失败成本低；由人工阅读后丢弃中等；错误建议可能被人采纳执行高；系统自身已执行操作，往往在有人查看之前就已完成

RAG 助手可能出错。而 Agent 不仅可能出错，还可能让错误的事情发生。正是从读取到执行操作这一转变，把一个 AI 功能变成了一 piece 需要像支付集成一样严谨对待的运营软件。

当 AI 能够执行操作时，什么发生了变化

当 Agent 被赋予工具时，一整套对聊天机器人来说从未重要的工程问题突然变成了必选项。这些都不是什么高深的东西：它们是标准的分布式系统和安全实践，只是应用到了一个会自主决策的组件上。

工具设计

模型只能看到工具的名称、描述和输入 schema。一个模糊的工具，比如

update_ticket(fields)

会诱导模型修改任何东西。而一个狭窄的工具，比如

add_work_note(incident_id, note)

或

set_priority(incident_id, priority, reason)

限制可能出错的范围，并使意图可审计。好的 Agent 工具应当是小型的、有类型的、在服务端进行校验的，并以业务动作而非底层 API 来命名。

每个用户的最小权限身份

一个诱人的捷径是使用一个权限宽泛的服务账号，让 Agent 为所有用户使用它。这意味着任何用户都可以通过 Agent 做该服务账号能做的任何事情。更安全的模式是代表用户（on-behalf-of）访问：Agent 使用从登录用户身份派生的令牌来执行操作，因此它只能查看和更改该用户有权访问的内容。在 Microsoft 环境中，这通常意味着使用具有委派权限和窄范围定义的 Entra ID；在其他系统中，则意味着 OAuth 范围或谨慎映射到工具上的每用户角色。

人在环审批

并非每个操作都应该是自主的。合理的设计会按风险对工具分类：读取操作自由运行，低风险写入（添加备注）在记录日志的情况下运行，高风险写入（关闭事件、重新指派 P1、触碰生产环境）则暂停等待人工批准。审批规则是一项业务决策，并且因客户而异。

幂等性与重试

模型调用会超时，网络会故障，Agent 有时会重复某个步骤。如果“创建工单”被盲目重试，就会产生重复工单。写入工具需要幂等键或先检查再创建的步骤，而重试需要区分“调用失败”和“调用成功但响应丢失”。

审计追踪

对于每个操作，系统都应记录 Agent 是代表谁执行操作的、调用了哪个工具、使用了什么参数、模型给出的理由是什么、返回了什么结果，以及是否有人工批准。

回滚

有些操作可以撤销（重新打开工单、还原字段），有些则不能（已发送的电子邮件）。工具层应当知道哪些可以撤销，为可逆更改保留先前状态，并将不可逆操作引导至审批流程。

速率限制与每任务成本

处于循环中的 Agent 可能猛烈调用 API 或消耗大量模型令牌。企业系统有自己的速率限制，客户也会询问每个已完成任务的成本。步骤限制、每用户配额、重复查询的缓存以及每任务成本跟踪是设计的一部分，而非事后补充。

MCP：一个标准插头，而非成品集成

模型上下文协议（MCP）是 Anthropic 于 2024 年底推出的一项开放协议，用于标准化 AI 应用连接工具和数据的方式。MCP 服务器以一致的格式公开一组工具、资源和提示；任何兼容 MCP 的客户端（例如 Agent 框架或 AI 助手）都可以发现并调用它们，而无需为每种配对编写自定义胶水代码。

MCP 不能决定任何与特定客户相关的事情。对于每个系统，仍然需要有人：

  • 选择将哪些操作公开为工具，哪些完全不公开。
  • 编写服务器，将这些工具映射到客户的 API、自定义字段和工作流上。
  • 配置身份验证，使服务器以相应用户的权限执行操作，而不是使用共享的超级用户。
  • 验证输入，执行业务规则，并返回模型能够理解的错误信息。
  • 像对待其他生产服务一样，对服务器进行托管、监控、版本管理和补丁更新。

面向工单工具的通用连接器只是一个起点。而一个能够理解该客户的“分配组”字段决定路由、P1 事件需要经理批准才能关闭、某一类别由外包供应商处理的服务器，则是针对客户特定需求的工程。这正是 FDE 类型工作的所在。

编排：状态、检查点与中断

简单的 Agent 运行一个循环：模型选择一个工具，结果返回，如此重复。企业级 Agent 通常需要更多的结构，像 LangGraph 这样的框架将 Agent 建模为步骤组成的图。有三个概念最为重要，而且很容易直白地解释：

  • 状态是任务到目前为止的共享记录：用户的请求、已检索的内容、调用了哪些工具以及它们返回了什么。每个步骤都会读取并更新它，因此行为是显式的，而不是埋藏在冗长的提示词中。
  • 检查点在每一步之后将该状态保存到诸如 PostgreSQL 的存储中。如果进程崩溃或某一步失败，运行会从上一个检查点恢复，而不是从头开始并重复副作用。
  • 中断在定义的节点暂停图的执行，通常是在高风险工具调用之前，并等待人工介入。审批者可以看到拟议的操作，予以批准、编辑或拒绝，然后图从检查点恢复运行。

你不一定非要用 LangGraph，但确实需要这些概念。

一个示例场景：一家 GCC 的 IT 服务台 Agent

设想一家位于海得拉巴的全球能力中心，为其母公司遍布全球的办事处提供 IT 支持。该服务台在 ServiceNow 中处理大量重复性事件：密码和访问问题、VPN 故障、笔记本电脑申请、应用程序错误。管理层希望有一个 Agent 能够对新事件进行分类，找到相关文章，添加建议的解决方案，并在安全的情况下更新或解决工单。

生产版本大致如下：

Engineer / service-desk analyst
        |
        v
  Chat UI / ServiceNow panel
        |  (user signs in via Entra ID)
        v
  Agent service (FastAPI + LangGraph)
   |  state + checkpoints -> PostgreSQL
   |  traces -> Langfuse / OpenTelemetry
   |
   |-- LLM (Bedrock / Azure OpenAI)
   |

   |     read_incident, search_incidents

   |

架构并不是难点，决策才是。以下是该项目的前沿部署工程师需要与客户共同确定的事项：

  • 权限范围。 Agent 使用分析师的委托身份可以读写哪些 ServiceNow 表和字段。安全事件和 HR 相关工单被完全排除，因此工具永远不会返回它们。
  • 审批规则。 添加工作备注和建议类别会自动运行。更改优先级需要说明理由。解决任何事件，以及对高优先级或 VIP 用户工单的任何操作，都会暂停以等待分析师批准。
  • 评测集。 一组经过匿名化的历史事件，由资深分析师标注出正确的知识库文章、正确的下一步操作以及会出错的操作。这成为了每次提示词、工具或模型变更时都要运行的回归测试套件。
  • 防护机制。 对每个写入工具进行服务端验证、限制每个任务的步骤数、拒绝处理用户分配组之外的工单、更新时使用幂等键，以及在数据到达模型或追踪记录之前过滤个人数据。
  • 监控。 记录每次运行的追踪信息、任务完成率的仪表盘、批准与拒绝率、工具错误、延迟以及每个已解决工单的成本，并在拒绝率上升时发出警报——这往往是出现回归的第一个信号。
  • 上线。 先以影子模式运行（仅提供建议，不执行写入），然后扩展到一个分配组，再逐步扩大范围，每个阶段都由服务台负责人签字确认。

这些决策都无法原封不动地照搬到另一个 GCC，后者可能使用 Jira 而非 ServiceNow，采用不同的身份认证配置，或者设有员工委员会，要求每次自动化变更对受影响的员工可见。这正是这项工作需要工程师在场参与的核心原因。关于此类项目如何从试点走向上线的分阶段视图，请参阅 FDE 如何将 AI 从概念验证推向生产环境。

如何评估智能体

评估聊天机器人主要是评判最终答案。评估智能体则要评判它所走的路径以及沿途做出的更改。以下是一些有用的衡量指标，应随时间追踪趋势，而非简化为单一分数：

  • 任务成功率。 智能体是否为该案例达成了预期结果？对于服务台而言：找到正确的文章、添加正确的备注、工单处于正确的状态。
  • 工具调用准确率。 它是否选择了正确的工具、参数正确、顺序合理，并避免了不必要的调用？
  • 不安全操作率。 它多久会尝试一次超出策略的操作，例如触碰被排除的工单类型，或试图在未经批准的情况下解决问题？理想情况下防护机制会阻止这些操作，但尝试行为本身就是一种信号。
  • 轨迹审查。 由人工阅读一部分运行样本的完整追踪记录，尤其是失败和被拒绝批准的案例，以发现指标遗漏的模式：循环、误读指令、过于激进的操作。
  • 批准结果。 人工批准、修改或拒绝建议操作的频率。修改率上升能告诉你智能体的判断正在哪些方面发生偏移。

团队使用 LangSmith 或 Langfuse 等工具来捕获追踪记录并运行评测数据集，使用 Ragas 处理流水线中的检索部分。工具本身不如纪律重要：与客户专家共同构建带标注的评测集，并在每次变更前运行。许多 AI 演示在生产环境中失败的原因都可以追溯到跳过了这一步，相关内容在为什么 AI 演示在企业生产中失败中有介绍。

为什么 AI Agent 催生了对 FDE 类工程师的需求

前沿部署工程师是直接在客户环境中工作、让技术在该环境中产生实际成果的工程师；FDE 角色完全指南对该定义有深入阐述。出于以下几个结构性原因，AI Agent 增加了对这类人才的需求：

  • 每个客户的系统都不相同。 同样的工单产品，但自定义字段、工作流、集成和数据质量各不相同。
  • 每个客户的政策都不相同。 哪些可以自动化、哪些需要审批、哪些必须记录以及由谁签字确认，这些都是治理决策，而非产品设置。
  • 身份是客户特定的。 将 Agent 的工具映射到客户的身份提供商、角色和权限范围，需要访问并理解该环境。
  • 评测需要客户的专家参与。 只有他们的分析师才知道针对他们的事件，正确的处理动作是什么。
  • 风险审批是本地化的。 安全、合规和运营团队希望有一位工程师能够准确解释 Agent 能做什么、不能做什么。

平台会持续吸收通用部分：托管模型、标准 MCP 连接器、编排框架、追踪。其上的客户特定层并不会消失；随着 Agent 被赋予更多任务，这一层还会不断增长。这就是为什么现在越来越多的职位描述将 Agent 框架、企业集成和安全整合在一个角色中，无论其头衔是 FDE、Agentic AI 工程师还是 AI 解决方案工程师。

Agentic AI 项目中的常见错误

  • 一个无所不能的服务账户。 它让演示变得简单，却让安全审查变得不可能。
  • 把原始 API 直接暴露为工具。 给模型一个通用的“调用任意端点”工具，等于把系统的全部攻击面都交给了它。
  • 把审批当作界面上的点缀。 如果审批没有在编排层和工具服务器中强制执行，一次提示词的改动就可能绕过它。
  • 没有幂等性。 重试会导致重复的工单、重复的邮件和困惑的用户。
  • 只评估最终答案。 Agent 可能通过不安全的路径得出正确答案；需要对轨迹进行审查。
  • 信任检索到的内容。 工单或文档中的文本可能包含指令；应将其视为数据，绝不能当作命令。
  • 忽视每个任务的成本。 Agent 循环会成倍增加模型调用次数；如果不加跟踪，账单会让所有人吃惊。

常见问题

Agentic AI 只是炒作吗？

围绕它的营销往往是炒作，但其背后的转变是真实的：模型现在能够可靠地调用工具，因此 AI 系统可以在业务软件中执行操作，而不仅仅是生成文本。实际价值取决于对工具、权限、审批和评测的精心设计，这也是为什么许多 Agent 试点在跳过这些工作时陷入停滞。

什么是 Agentic AI 工程师？

Agentic AI 工程师负责设计、构建和运营使用工具在真实系统中完成多步骤任务的 AI 系统。除了提示词和框架之外，该角色还涵盖工具设计、身份与最小权限访问、人工审批流程、错误处理、可观测性以及 Agent 行为的评测。

构建 AI Agent 需要 LangGraph 吗？

不需要特定的框架，但你需要掌握 LangGraph 所明确体现的概念：共享状态、用于恢复的检查点以及用于人工审批的中断机制。LangGraph 是企业 Agent 的常见选择，因为它直接对这些概念建模，所以值得深入学习。

什么是 MCP？

MCP（Model Context Protocol，模型上下文协议）是 Anthropic 于 2024 年底推出的开放协议，用于标准化 AI 应用连接工具和数据的方式。MCP 服务器暴露工具和资源，任何兼容的客户端都可以发现并调用它们。但仍然需要有人为每个客户系统构建、加固和运维该服务器。

AI Agent 在企业中安全吗？

如果经过专门设计，它们可以是安全的。安全性来自窄范围工具、按用户最小权限访问、高风险操作需人工批准、服务端校验、审计日志、尽可能支持回滚以及持续评测。一个拥有广泛权限且无需审批的 Agent，无论模型多好都不安全。

FDE 如何测试 AI Agent？

他们会根据客户专家标注的真实、匿名化案例构建评测集，然后衡量任务成功率、工具调用准确性和不安全操作的尝试次数，并完整复盘失败轨迹。每次变更都会运行这套评测，并在允许 Agent 写入生产系统之前先以影子模式上线。
