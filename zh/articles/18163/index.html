真正能体现 FDE 准备度的 5 个作品集项目

原标题：The 5 portfolio projects that actually signal FDE readiness

AI Codex · 2026-05-14 · 约 11 分钟读完

摘要

文章针对 FDE（前沿部署工程师）求职，指出常规教程式作品集无法证明真实企业环境下的交付能力，并提出五个更能体现准备度的项目：连接多个真实数据源的 MCP server、针对具体场景的评测框架、带真实约束的企业集成、书面架构决策记录（ADR），以及生产事故复盘。作者强调展示错误处理、权衡取舍、面向非技术受众的沟通与真实失败经历，并建议先在周末完成 ADR，因为它无需新代码且最能区分候选人。

要点

  • 教程式项目只能证明会照做，不能证明 FDE 能力。
  • MCP server 需接三个以上真实数据源并含权限与降级处理。
  • 评测框架应展示真实失败率与修复过程，而非满分。
  • ADR 要写明被否方案、代价与改进之处，体现诚实权衡。
  • 生产事故复盘证明你真正上线过并从故障中学习。

简要概述

一个满是副项目的 GitHub 只能告诉 FDE 招聘经理你会写代码。他们真正想看到的是你能在现实世界中构建的证据——面对遗留系统、模糊的需求和非技术背景的利益相关者。这五个项目恰好展示了这一点。

目录

大多数开发者作品集建议都千篇一律：做三个项目，放到 GitHub 上，写个 README。这些建议适用于标准的软件工程岗位，但 FDE 的招聘不同。

FDE 招聘经理评估的是一些具体的能力：你能否在真实的企业环境中构建生产级 AI 系统，面对没有文档的 API、不完整的需求和非技术背景的利益相关者？一个照着教程做完的干净项目回答不了这个问题。它回答的是另一个问题：你能否照着说明做？

这五个项目的设计目的就是回答正确的问题。

FDE 面试官真正看重什么

在介绍项目之前，值得先了解评估标准。当 FDE 面试官审阅你的作品集时，他们在寻找：

生产级思维 —— 错误处理、可观测性、访问控制、优雅降级。项目能否应对故障场景，还是只在一切顺利时才能运行？

架构决策能力 —— 不只是“这是我做的东西”。你为什么这样构建？考虑过哪些方案？放弃了哪些？一个没有架构推理的项目只能告诉他们你把它做出来了，而不能证明你懂得如何设计系统。

面向非技术受众的沟通能力 —— 非工程师能否理解你构建了什么以及为什么？FDE 会花大量时间与不写代码的利益相关者打交道。你的 README 和文档就是这项能力的代理指标。

应对现实约束的证据 —— 你是否处理过棘手的问题？认证问题、未文档化的 API 行为、数据不一致、速率限制？毫无摩擦的项目说明你只在干净的环境中工作过。

项目 1：连接 3 个以上真实数据源的 MCP 服务器

为什么这个项目有效：

Anthropic 的 FDE 职位列表明确将 MCP 服务器开发列为交付成果之一。这不是一个泛泛的“证明你懂 API”的项目。MCP 服务器是 FDE 将 Claude 连接到企业数据的方式——内部 CRM、数据仓库、工单系统。构建一个连接多个数据源的 MCP 服务器，能证明你理解数据访问模式、认证和路由，而这几乎是所有企业 AI 部署的核心技术架构。

要构建什么：

一个至少连接 3 个真实数据源的 MCP 服务器。不要用玩具示例。不错的组合有：

  • GitHub（通过 API）+ Notion（通过 API）+ 一个 CRM API（HubSpot 有免费套餐）
  • Slack（通过 webhook）+ Linear 或 Jira + 一个你自己掌控的数据库
  • 任何涉及结构化数据源、非结构化知识源和具备执行能力数据源的组合

代码仓库应有一份清晰的 README，说明：

  • 服务器做什么
  • 你为什么选择这三个数据源（服务于什么用例？）
  • 每个数据源的认证方式是如何工作的
  • 当某个数据源不可用时会怎样

应包含的内容：

一个访问控制层。哪怕很简单——不是每个工具都应该对每个查询开放。展示你思考过谁能访问什么，这体现了大多数初级开发者会忽略的生产级思维。

针对每个数据源单独的错误处理。如果 GitHub API 被限流，服务器应优雅降级，而不是崩溃。记录每种失败情形下会发生什么。

不要做的事：

不要封装三个返回静态数据的玩具 API。重点在于真实的 API、真实的认证、真实的限流、真实的不一致行为。这种摩擦正是意义所在。

项目 2：针对真实用例的评测框架

为什么这个项目有效：

生产环境中的 AI Agent 会以在没有正式评测套件时确实难以察觉的方式失败。大多数初级开发者完全跳过评测，依赖“我测试时它能用”。FDE 招聘经理深知，生产系统就是这样积累隐性故障的。一个评测框架表明你关注可靠性和回归预防——这正是“做出来了”与“上线了并维护着”之间的区别。

要构建什么：

选择一个具体的 Agent 工作流——不是“模型好不好？”，而是类似：“一个从文档语料库中回答公司人力资源政策问题的 Agent”或“一个把客户支持工单路由到正确团队的 Agent”。然后为这个具体工作流构建一套评测套件。

这套套件应包括：

  • 至少 20 个测试用例
  • 覆盖边界情况和失败模式的用例，而不只是简单示例
  • 一种运行套件并汇总查看结果的方式（通过率、失败模式）
  • 你在开发过程中发现的、有文档记录的失败模式

应包含的内容：

展示你发现的失败模式。一个第一版就显示 100% 通过率的评测套件，看起来像是你写了简单的测试。一个显示 73% 通过率、随后是你所做的修复、再之后是 94% 通过率的评测套件，才表明你确实发现了真实的问题。

记录你的评分方法。你是如何决定对这个任务什么算“正确”的？这是一个有实际影响的设计决策。

不要做的事：

不要构建一个通用的“LLM 质量评估器”。那是一个产品，不是作品集项目。为某一个具体任务构建评测，把它做好，并解释为什么你选择的用例是正确的用例。

项目 3：有真实约束的企业级集成

为什么这个项目有效：

FDE 在遗留的企业环境中工作。这不是可有可无的背景——它就是这份工作的核心。一个能证明你处理过无文档 API、身份验证难题、数据不一致或合规相关需求的项目，表明你接触过真实的工程，而不仅仅是教程式的工程。

要构建什么：

与真实企业工具的集成。以下选项效果不错：

  • Salesforce（有免费的开发者版）——他们的 API 文档完善，但数据模型很复杂
  • 一个遗留数据库——搭建一个带有真实混乱模式的 PostgreSQL 或 MySQL 实例，并在其上构建一个 AI 层
  • 一个 ERP 模拟器——有一些开源 ERP 工具正是为此目的而存在的
  • 你工作或实习过的公司的任何内部工具——即使是一个小型集成也算数

要记录什么：

这个项目的价值在于文档，而不仅仅是代码。你需要写下：

  • 你开始时什么出了问题或不清楚
  • 你是如何弄清楚那些无文档行为的
  • 你会有什么不同的做法
  • 非技术利益相关者需要了解哪些内容才能理解这个集成是如何工作的

如果你是在真实公司（实习、工作、自由职业）构建过这个项目，请记录真实的约束和挑战。如有需要可对公司匿名——重要的是细节，而不是名字。

是什么让这个项目真正有价值：

它是适应能力的证明。任何人都可以针对返回一致 JSON 的文档完善的 REST API 进行开发。但不是每个人都处理过有时返回 XML、有时返回 JSON 的 API，或者“customer_id”字段在不同表中含义不同的数据库。这些正是 FDE 每天面对的工作环境。

项目 4：一份书面的架构决策记录（ADR）

为什么这个项目有效：

这不是代码，而是一份文档。但它可能是这份清单上最能让你脱颖而出的项目。

FDE 需要不断向非技术高管和利益相关者解释架构决策。撰写一份清晰、坦诚的 ADR——说明你选择了什么、拒绝了什么、权衡是什么、以及你会重新审视什么——是一种直接的沟通能力信号，而大多数技术作品集完全没有展示这一点。

要写什么：

从你的其他作品集项目中选取一个架构决策。写一份 1–2 页的文档，涵盖：

  • 背景情况——你在构建什么，你需要做什么决策
  • 你考虑过的选项——至少 3 个，并附上坦诚的权衡分析
  • 决策——你选择了什么以及为什么
  • 你会重新审视什么——如果有更多时间、更多信息或不同的约束条件，你会有什么不同的做法？

优秀作品的样子：

一份好的 ADR 不会假装这个决定是显而易见的。它表明你真正评估过各种备选方案，并做出了经得起推敲的选择。“我会重新审视什么”这一部分尤其有价值——它体现了智识上的诚实，以及超越已做决定进行思考的能力。

不要做的事：

不要在事后才写一份只用正面措辞来为决定辩护的 ADR。读者应该感觉自己在看你思考的过程，而不是在读你为一个早已得出的结论所做的辩护。

放在哪里：

作为一份链接文档放在项目 README 中。当面试官问“这个项目中最难的架构决定是什么？”时，你的回答应该以“我其实为此写过一份 ADR”开头，然后把链接发给他们。

项目 5：针对生产环境中出现过的故障撰写的事后复盘

为什么这个项目有效：

FDE 面试几乎总会包含这样一个问题的变体：“讲讲你上线过的东西出故障的经历。当时发生了什么？”一份书面的事后复盘能同时展示三件事：你确实把东西部署到了生产环境（而不只是业余项目），你以系统的方式思考（而不只是“我的代码有 bug”），以及你对失败坦诚相待——这种坦诚本身就是可信度的信号。

要写什么：

500–1,000 字，涵盖：

  • 出了什么故障 —— 具体描述故障，不要含糊其辞
  • 为什么出故障 —— 根本原因，而不只是表象
  • 你是如何诊断的 —— 你弄清楚问题所在的过程是什么
  • 你做了什么改变 —— 修复方案，以及为防止问题再次发生所做的流程或架构上的改变
  • 你会怎么做 differently —— 坦诚的反思

如果生产环境从未出过故障怎么办？

那说明你部署到生产环境的东西还不够多。这是一个信号。去构建真实的东西，把它部署到某个地方，并接受它会以你未曾预料的方式出故障。如果你只在 localhost 上构建过，那你还拿不出事后复盘——而这是一个值得在面试前弥补的差距。

如果你在工作中经历过可以描述的真实生产故障（适当匿名化处理），那些也算数。哪怕是实习期间搞挂了预发布环境而写的事后复盘，也是事后复盘。

放在哪里：

作为链接文档放在相关项目的 README 中。或者发布在你的个人网站或 GitHub 上的公开文章。载体形式不如内容的存在和质量重要。

如何展示作品集

仓库结构：

每个项目都应该有：

  • 一份 README，开头说明这个项目做什么、为什么存在（而不是它用了哪些技术）
  • 一节介绍架构决定（如果写过 ADR，附上链接）
  • 一节介绍已知局限以及你会如何改进
  • 真正可用的安装/运行说明

面试中：

当被要求介绍一个项目时，不要从技术栈讲起。应该先说：“我要解决的问题……”然后是约束条件，接着是决策过程。技术只是背景，不是故事本身。

如果你的项目写过 ADR（架构决策记录）和事后复盘，在讲解时引用它们。大多数候选人没有这些材料，拥有它们本身就是一种信号。

需要避免的危险信号

教程复刻项目 —— 如果项目明显来自某个教程（数据集是 MNIST，API 是天气 API，结构和你照着做的指南一模一样），这表明你还没有超越被动式学习。FDE 招聘要求具备独立判断能力。

没有错误处理 —— 检查每一个项目。它是否会静默失败？是否会抛出未捕获的异常？是否有任何日志？错误处理是判断你是否考虑过生产环境的最清晰信号。

没有测试、没有评测 —— 至少，你应该能解释你会测试什么以及如何测试。更好的做法是：真的有测试。

没有记录你会如何改进 —— 每个项目都应该有“局限性”或“我会改进什么”的部分。如果一切看起来都很完美，这表明你要么知识不足以发现问题，要么你没有说实话。两者都不会让 FDE 面试官放心。

无法运行的项目 —— 如果面试官尝试运行你的项目却失败了，这是一个重大的负面信号。面试前，在一台干净的机器上测试你自己的安装说明。

上面的五个项目不是一份机械完成的清单。每一个都是为了回答 FDE 面试官会问的一个具体问题。MCP 服务器回答的是：你能否构建企业数据连接层？评测框架回答的是：你是否考虑可靠性，而不仅仅是能力？企业集成回答的是：你是否应对过现实世界的约束？ADR 回答的是：你能否向非技术受众传达架构决策？事后复盘回答的是：你是否有过生产环境上线经历，并从故障中学到了东西？

如果你能回答这五个问题，你就已经为 FDE 面试做好了准备。

技能模块：这个周末写出 ADR

场景。 你已经决定追求 FDE 职位。看着上面的五个项目，你估算需要三个月的晚间时间，然后悄悄失去了动力。与此同时，你已经有现成的工作成果——你在工作中构建的系统、你设计的服务、你主导的迁移——只是团队之外从来没有人见过。

你的任务。 这个周末完成项目 4——架构决策记录，内容关于你已经构建过的东西。两到三页。一个真实的决策，来自真实的工作。

先做这一个，有三个原因。它是五个项目中唯一不需要写新代码的。它是大多数候选人都会跳过的，所以能立刻形成区分度。而且它考验的正是 FDE 真正被录用的原因——向非技术人员解释一个技术决策，并让他们认同。

按以下结构来写：决策、背景与约束、你否决的选项及原因、你最终的选择、付出的代价，以及你会如何改进。

优秀范例——一份真实文档的开头：

决策： 我们把订单同步服务放在消息队列后面，而不是直接调用 ERP 的 API。背景： ERP 对全公司限制每分钟 40 个请求，仅仓库扫码一项在高峰期就达到 300。供应商报价十一周来提升限额，且不肯承诺具体数字。否决——客户端限流： 最简单的方案，但意味着扫码员在高峰期最多要等九分钟。运营主管当场否决，大约用了四秒钟。这个决定是对的，而我当时没有充分权衡。否决——缓存读取： 对读取有帮助，但对写入毫无作用，而写入才是问题所在。选择——带批量写入的队列： 每 10 秒窗口批量写入 25 条，高峰期也远低于限额。付出的代价： 最终一致性。库存数据最多可能滞后 10 秒。我们与运营方明确达成了共识，并把滞后窗口显示在 UI 中。我会如何改进： 我在与运营主管沟通之前，先花了一周做缓存方案。如果第一天就和她谈十分钟，这个方案当场就会被否掉。现在我处理这类问题时，会先问谁在承受这个约束。

常见错误。 把 ADR 写得好像这个决策事后看来显而易见。面试官从一段干净利落的叙述中学不到任何东西——他们想看的是你能否在两个可行方案之间保持张力，说出你放弃了什么，并且不带表演地承认一次失误。“付出的代价”和“我会如何改进”这两部分才是整份文档的核心。如果这两部分单薄，那 ADR 就只是营销材料，而不是证据。

为什么这是关键练习。 每一次 FDE 项目最终都会归结为这样一场对话——面对客户的架构师、他们的 CFO，或一个持怀疑态度的内部团队。写一份 ADR 是你在真正进入会议室之前最接近实战的练习。而且与其他四个项目不同，你可以在一个周末完成它，并在周一就有东西可以发送。
