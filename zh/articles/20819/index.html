使用 LLM 构建企业文档智能处理管道

原标题：Build an Enterprise Document Intelligence Pipeline with LLMs

Cloud Soft Solutions · 2026-10-06 · 约 13 分钟读完

摘要

本文以保险理赔场景为例，按前沿部署工程师的交付方式讲解如何用 LLM 构建企业文档智能管道：把理赔材料转化为结构化数据并自动路由。核心观点是管道“完成”的标准是每个字段带证据与置信度、低置信度文档进入人工复核、直通率基于标注测试集诚实度量。文章覆盖架构、模式设计、手写件与低质量扫描处理、验证规则、置信度评分、轻量 Agent、安全合规、扩展与评测，并给出可写成作品集项目的实施计划。

要点

  • 管道完成标准：字段带证据与置信度，低置信度进人工复核。
  • OCR 与 LLM 抽取分层，验证与路由由确定性代码负责。
  • 置信度综合 OCR 置信、验证结果、双次抽取一致性等信号。
  • 直通率须连同错误逃逸率一起按渠道与文档类型度量。
  • 先影子模式运行，再按文档类型逐步开放直通。

这是一个文档智能项目，按照前沿部署工程师的交付方式来讲解：文档输入，输出结构化数据和决策。企业级文档智能流水线只有在每个提取字段都带有证据和置信度、低置信度的工作进入人工审核队列而非下游系统、并且直通率是对照标注测试集诚实衡量时，才算“完成”。 该场景仅为示例；文末的构建计划会把它变成一个你可以在面试中有理有据展示的作品集项目。

我们的 RAG 知识助手项目 是基于文档回答问题。而这个项目是把文档转化为结构化数据和路由决策，因此难点在于模式（schema）、扫描质量、校验和置信度，而不是检索。

业务问题

示例场景。设想一家健康险和车险保险公司，其理赔运营团队部分由位于海得拉巴的 GCC 运营，通过电子邮件、客户门户、合作医院渠道和扫描邮件接收理赔材料包。一个材料包可能混合理赔申请表、医院账单、药房收据、身份证明文件、修理厂估价单和附函，从干净的 PDF 到倾斜的手机照片和手写表格都有。

如今，数据录入人员打开每个材料包，判断每一页是什么，然后把保单号、索赔人信息、日期、明细项目和金额录入理赔系统。症状如下：

  • 理赔件在队列中积压数天，甚至无人查看。
  • 录入错误（日期颠倒、漏掉明细项目）导致后续返工和纠纷。
  • 洪灾或节日出行高峰后业务量激增，团队无法一夜之间扩容。

客户想要的是更快、更少错误的理赔登记，而不是“能读 PDF 的 AI”。从 AI 演示到企业成果：提取一张清晰的发票很容易；安全地处理一张模糊的手写表格才是真正的工作。

需求

与理赔、数据录入、反欺诈、合规和安全团队的调研产出了以下需求。

功能性需求

  • 按文档类型对理赔材料包的每一页进行分类，并拆分多文档 PDF。
  • 按文档类型将约定的一组字段提取到带版本控制的 JSON 模式中。
  • 每个字段都链接到其来源页面和边界框。
  • 应用业务校验规则。
  • 对每份文档进行路由：直通到理赔系统，或连同原因进入人工审核队列。
  • 绝不批准或拒绝理赔；由理赔评估员决定。

非功能性需求

  • 个人和健康数据保留在客户的账户和获批区域内。
  • 在约定的窗口内、模型速率限制之内，清除激增的积压任务。
  • 完整的审计追踪：原始文件、模型和提示词版本、提取的值、审核员的更正。
  • 跟踪每份文档的成本，并控制在约定预算之内。

关键决策：

  • OCR 和版面解析与 LLM 抽取相互分离。 托管服务（如 Azure AI Document Intelligence 或 Amazon Textract，对于干净的数字 PDF 也可用开源解析器）返回文本、表格、键值对、单词置信度和坐标；LLM 将其映射到 schema 中。坐标作为证据，且任一层都可以替换。
  • 确定性代码负责校验和路由。 模型提出值；规则和阈值决定这些值的处理方式。
  • 状态存储在 PostgreSQL 中（文档、带证据的抽取结果、审核记录）；原始文件存放在对象存储中。

数据

Schema 设计

Schema 是与下游系统的契约，因此要与理赔系统负责人共同设计。经得起考验的规则：

  • 每种文档类型一个 schema（理赔申请表、医院账单、身份证件、修理厂估价单、信函），像 API 一样进行版本管理。
  • 每个字段都可空。 必须能够表达“文档上不存在”；否则模型会编造一个值来填充该字段。
  • 规范化类型： 日期采用 ISO 格式，金额用小数加币种表示，有列表可依的代码用枚举表示。
  • 每个字段附带证据： 原样文本、页码、边界框。
  • 明细项用数组表示，并单独抽取打印总额以便校验时交叉核对。
{
  "doc_type": "hospital_bill",
  "schema_version": "1.3",
  "admission_date": {"value": "2026-03-14",
    "raw": "14/03/26", "page": 1, "bbox": [...]},
  "line_items": [...],
  "printed_total": {...}
}

手写体和低质量扫描件

这是演示容易翻车的地方。要明确做好规划：

  • 预处理： 在 OCR 之前对图像进行去偏斜、旋转、裁剪和降噪。检测空白页和接近空白的页面。
  • 质量门控： 为每页打分（分辨率、模糊度、平均 OCR 置信度）。低于阈值时，路由到人工审核或请求重新扫描，而不是自信地抽取垃圾数据。
  • 手写体： 托管 OCR 能在一定程度上处理，但准确率参差不齐。要单独测量，并对手写字段应用更严格的阈值。
  • 多模态模型可直接读取页面图像，有助于处理印章和勾选框。将其用作疑难页面的第二意见，而非替代 OCR 坐标。

尽早对真实案卷的去标识化样本进行标注。能告诉你可实现的直通率的是它的质量构成，而不是供应商的演示。

LLM

模型的任务很窄：给定已分类文档的版面输出，填充 schema。实用模式：

  • 结构化输出： 使用平台的 JSON schema 或工具调用模式，用 Pydantic 校验，遇到无效 JSON 时重试。
  • 按文档类型分别设计提示词，字段定义由理赔领域专家撰写（“入院日期是患者入院的日期，而不是账单日期”），并附上几个已完成的示例。
  • 对空值的指令： “如果文档中没有某个字段，返回 null；绝不推断。”
  • 两级模型： 用较便宜的模型做分类；用能力更强的模型处理复杂文档，例如逐项列明的账单。

校验规则

确定性检查能捕捉模型无法知道的问题：保单存在且在事故日期处于有效状态、明细项加总等于打印的总金额、出院日期不早于入院日期、索赔人与列出的成员匹配（模糊匹配）。每次失败都附带原因代码。

置信度评分

不要问模型“你有多大把握？”然后相信那个数字。按字段综合多个信号：

  • 证据片段的 OCR 词置信度。
  • 提取的值是否在 OCR 文本中原样出现（或规范化后出现）。
  • 涉及该字段的规则的校验结果。
  • 两次提取过程在高价值字段上的一致性。
  • 页面质量评分，以及该字段是否为手写。

将这些信号综合成一个分数，并在标注集上按字段校准阈值：选择使自动接受值的精确率达到与业务方商定目标的阈值。保单号和索赔金额应该比医院地址使用更严格的阈值。

RAG

这条流水线几乎不需要 RAG。只有两个窄用途值得保留：获取保单记录以校验字段（实际上是数据库查询），以及检索之前人工修正过的文档，作为异常版式的少样本示例。检索机制在上文链接的知识助手指南中有说明。

Agent

Agent 刻意保持轻量：它是一个异常处理器，只在文档未通过校验或置信度检查时运行。它解决简单的异常，其余的则解释给人工处理。

用一个小型 LangGraph 状态机或带步骤上限的纯 Python 来构建它。它的工具是只读的，或只能重新运行某个阶段；它不能写入理赔系统，且已解决的异常仍需通过同样的校验和阈值。

人机协同 UI

审核队列是价值成败的关键。一个好的审核界面应显示：

  • 一侧是页面图像，另一侧是提取的字段；点击某个字段会高亮其边界框。
  • 只高亮被标记的字段，并显示原因代码和 Agent 的备注，让审核员进行确认而不是重新录入。
  • 键盘优先的修正操作，以及一键“已请求重新扫描”或“文档类型错误”。
  • 按紧急程度和时长排定优先级；按技能分配任务。

每次修正都与原始值一起存储。这些修正就是你下一批标注数据，也是阈值调优的输入。

安全

理赔材料包含大量个人和健康数据，因此 PII 处理从第一天起就纳入设计：

  • 数据最小化： 只提取流程所需的字段，并遮蔽无需完整展示的标识符；合规团队制定规则，包括印度《数字个人数据保护法》规定的义务。
  • 加密与访问： 静态数据使用客户自管密钥；审核员通过 SSO 组（例如 Microsoft Entra ID）只能看到自己业务条线的队列。
  • 日志与追踪： 只存储文档 ID 和字段名，不存储值。
  • 模型访问： 通过已批准区域的私有端点访问模型服务，并确认条款规定输入不会用于训练。
  • 提示词注入： 随附信函可能包含指令。将文档文本视为数据；Agent 的工具无法改变理赔结果。
  • 保留策略： 按约定的时间表删除页面图像和 OCR 输出。

更全面的威胁模型见 AI security for enterprises。

云

  • AWS 上： S3 存储原件，Amazon Textract 负责 OCR 和版面分析，Amazon Bedrock 负责提取，各阶段之间用 SQS，工作进程运行在 ECS 或 EKS 上，RDS 运行 PostgreSQL，外加 KMS 和 VPC 端点。详情见 AWS for AI FDE engineers。
  • Azure 上： Blob Storage、Azure AI Document Intelligence、Azure OpenAI、Service Bus 队列，工作进程运行在 AKS 或 Container Apps 上，Azure Database for PostgreSQL，外加 Key Vault 和私有端点。参见 Azure for FDE engineers。

批量工作负载的扩展

理赔请求会集中爆发式到达。要为积压而设计：

  • 根据队列深度自动扩缩容的 Worker，每个阶段一个队列。
  • 在 OCR 和模型调用前设置速率限制器；遇到限流时退避重试。
  • 优先级通道：紧急医疗理赔优先于常规积压任务。
  • 在有折扣批量推理服务的地方，将其用于积压通道。
  • 以文档哈希为键的幂等阶段，确保重试不会重复处理理赔。

可观测性

使用 OpenTelemetry span 追踪每个文档在各个阶段的流转，并使用 Langfuse 或 LangSmith 记录 LLM 调用（提示词版本、模型 ID、token 数、延迟）。这里重要的仪表盘包括：

  • 每个阶段的文档数量和队列时长，以便尽早发现积压。
  • 按文档类型和渠道统计的 STR；突然下降通常意味着出现了新的表单版式或扫描仪问题。
  • 最常见的校验失败代码和最常被人工修正的字段。
  • 按类型统计的每份文档成本，细分为 OCR、模型和人工审核时间。

更多模式请参见 AI 可观测性。

评测

构建一个由去标识化材料包组成的标注测试集，以反映真实的组合：渠道、文档类型、清晰和模糊的扫描件、手写内容，以及多页账单和缺失字段等边缘情况。领域专家为每个字段标注正确值（或空值）。

字段级精确率和召回率

  • 精确率：在系统提取的值中，有多少是正确的？
  • 召回率：在文档上实际存在的值中，有多少被正确提取？
  • 按字段和文档类型分别报告，而不是一个混合数字。为每个字段定义“正确”的标准：保单号要求精确匹配，日期和金额要求归一化匹配，姓名和地址要求模糊匹配。
  • 为不存在的字段编造值属于精确率错误，也是危害最大的错误。

直通率，诚实地测量

STR 很容易被夸大。请诚实地测量：

  • 只有在任何阶段都没有人工介入（包括重新扫描和重新分类）的文档才算作直通。
  • 将 STR 与错误逃逸率一起报告：每周审计一份随机抽取的直通文档样本。高 STR 但存在逃逸错误，比较低的 STR 更糟糕。
  • 按渠道和文档类型分别报告 STR。
  • 在真实业务组合上测量，绝不要从分母中剔除“困难”文档。

在 CI 中对每次提示词、模型或 schema 变更运行测试集评测。通用方法见我们的 LLM 评测指南。

部署

  • GitHub Actions 运行单元测试、schema 测试和提取评测；如果任何关键字段的精确率低于其阈值，构建即失败。
  • 构建并扫描容器镜像后推送；Terraform 管理基础设施；Argo CD 在 EKS 或 AKS 上同步 Kubernetes 清单。
  • 先采用影子模式：流水线与人工录入并行处理实时材料包，并将其输出与员工录入的内容进行对比。此时还没有任何内容被自动路由。
  • 然后为一种文档类型和渠道启用直通处理，采用保守阈值，并在经审计的错误逃逸率保持在目标范围内时逐步放宽。

提示词、Schema 和阈值都是版本化的配置，与代码走同样的门禁流程。

投资回报率（ROI）

从单份文档成本入手，再与当前人工成本进行比较。以下所有输入均为假设的占位值，用于展示方法，而非实际结果。

每次复核耗时（Mr）对比人工录入（Mm）例如 2 对 8 分钟计时样本
每小时综合人力成本（C）客户提供的数据财务部门

单份文档成本 = OCR + 模型 + 计算 + (1 − STR) × Mr ÷ 60 × C。人工单份文档成本 = Mm ÷ 60 × C。每月节省 = N ×（人工 − 自动化）− 平台运行与支持成本。避免的返工和更快的登记速度应单独报告。降低单份文档成本（更便宜的分类器、对干净的结构化表单跳过 LLM、批处理通道）在 AI 的云成本优化中有介绍。

自己动手构建：里程碑计划

仅使用合成文档：生成表单和账单，手工填写一部分并拍出模糊的照片。切勿使用真实的个人数据。

里程碑交付物
1. 数据集覆盖四种文档类型的小型合成文档包集合，逐字段标注
2. 接入与分类上传 API、存储、页面拆分器和分类器，并报告准确率
3. OCR 与信息抽取托管 OCR 或开源解析器，输出经 Schema 校验且带证据的 JSON
4. 校验与置信度规则引擎、逐字段评分、经校准的阈值
5. 复核界面与异常处理 Agent并排对比的复核界面；有边界约束的异常处理器
6. 评测字段级精确率/召回率、STR 和错误逃逸率，纳入报告和 CI
7. 扩展与运维队列工作进程、限流、追踪、Terraform，部署到 AWS 或 Azure
8. 价值单份文档成本分解与 ROI 方法、README、演示视频

在 README 中，展示一份因明确原因被路由到人工复核的低质量扫描件，并如实展示 STR 及其对应的经审计错误率。更多作品集创意，请参阅 每个 AI FDE 都应该构建的 10 个项目。

常见问题

什么是文档智能？

文档智能是指将表单、账单、证件和信函等文档中的信息自动分类并抽取为结构化数据，并对不确定的情况进行校验和人工复核。

基于 LLM 的智能文档处理与传统 OCR 有何不同？

OCR 将图像转换为文本和版面。LLM 能把各种版面映射到固定的模式（schema）并规范化取值，这是模板难以做到的。OCR 在坐标和单词置信度方面仍然不可或缺。

文档 AI 流水线与 RAG 项目有什么不同？

有不同。RAG 通过检索文段来回答问题，而文档 AI 流水线要把每一份传入的文档转换为结构化字段和路由决策，因此其核心问题是模式（schema）、扫描质量、校验、置信度和人工审核。

如何处理手写内容和低质量扫描件？

对图像进行预处理，为页面质量打分，并将低质量页面路由到人工审核或重新扫描请求。单独衡量手写识别准确率，并对手写字段应用更严格的阈值。

应该如何衡量直通率？

只有在任何阶段都没有人工介入的情况下，文档才算直通处理；应按文档类型和渠道分别报告直通率，并始终结合通过定期随机抽检直通文档得出的错误逃逸率一起呈现。

在 AI 文档提取中如何保护 PII（个人身份信息）？

只提取所需字段，对标识符进行脱敏，加密数据，按 SSO 用户组限制审核人员权限，从日志和追踪记录中隐去取值，在获批区域内使用私有模型端点，并执行数据保留策略。
