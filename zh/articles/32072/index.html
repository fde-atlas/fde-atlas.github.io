# 面向遗留 API 的 Kong API Gateway：FDE 需要了解的内容

原标题：Kong API Gateway for legacy APIs: what FDEs need

FDE Times · 2026-11-23 · 约 4 分钟读完

摘要

文章借 Kong 重新发布的 FDE 招聘启事，说明前沿部署工程师如何用 API 网关处理客户的遗留系统。Kong Gateway 是 Apache 2.0 开源反向代理，配合插件和 decK 声明式配置，可在不改动遗留后端的情况下集中管理路由。作者给出把遗留订单服务接到网关的最小示例，并指出网关无法修复后端本身的问题、配置文件需像代码一样严格评审。该职位要求 8 年以上经验，需自建迁移工具，把客户从旧 API 管理平台迁到 Kong。

要点

  • Kong 于 2026 年 11 月 20 日重新发布 FDE 职位，要求 8 年以上经验。
  • 职责是从遗留 API 管理平台迁移客户到 Kong，并自建迁移工具。
  • Kong 是开源反向代理，用插件扩展、用 decK 声明式配置。
  • 把网关放在遗留系统前，可在中间层改动而不碰后端代码。
  • 网关不能修复后端缺陷，配置错误可能切断整组客户端。

该招聘广告还列出了工程师在将 API 网关部署到客户传统系统之前所需的技能。

简要概述

  • Kong Gateway 是一个基于 Apache 2.0 许可证的开源反向代理，可通过插件进行扩展，并使用 decK 进行声明式配置。
  • 一旦客户通过网关调用，你就拥有了一个统一的修改入口，而无需触碰客户的后端传统系统。
  • Kong 本身正在招聘 FDE，以帮助客户从传统 API 管理平台迁移，并要求 8 年以上的工作经验。

Kong 于 2026 年 11 月 20 日重新发布了其前沿部署工程师职位，其中一项职责写得非常明确：负责将客户从传统 API 管理平台迁移到 Kong 的项目。被录用者还必须自行构建迁移所需的工具。

该广告称这是一个专业服务部门内面向客户的战略性工程职位。Kong 的前沿部署工程师与企业客户合作，设计、构建和部署基于 Kong 的解决方案，涵盖云端、混合和本地环境。Built In 上的职位信息还补充说，该职位既涉及 AI 基础设施，也涉及 API 基础设施。

即使你不打算申请 Kong 的职位，这则广告中的经验教训依然适用。如果你的客户有一个没人愿意触碰的后端，那么在其前面部署一个 API 网关是值得考虑的。Kong 是一个很好的学习对象，因为它的代码是开放的，文档也是公开的。

API 网关就是一个反向代理

官方文档将 Kong Gateway 描述为一个轻量、快速且灵活的云原生 API 网关。同一文档将 API 网关定义为一种反向代理，让你能够管理、配置和路由发往 API 的请求。

据 Kong 的首席技术官兼联合创始人 Marco Palladino 所说，Mashape 于 2015 年将该开源项目发布。该 GitHub 仓库采用 Apache 2.0 许可证。

有两个特性使 Kong 非常适合在客户现场工作。第一个是插件：GitHub README 指出，插件为网关添加高级功能，插件中心（Plugin Hub）列出了来自社区和 Kong Inc. 的插件。第二个是 decK，这是一个通过声明式状态文件管理配置的工具。

Kong 的文档从未提及“传统系统”。这一用法源于反向代理本身的角色。客户调用网关，网关将请求转发到后端，因此每一处修改都可以在这个中间层完成，而无需编辑其背后的代码。

一个最简示例：将传统订单服务置于网关之后

假设有一个客户，其订单服务运行在

orders-legacy.internal:8080

。它的作者早已离开，没人愿意触碰它。

你的工作是通过 Kong 为客户端路由，以便日后有地方添加功能。decK 状态文件可能如下所示，不过你应当对照你所运行版本的 decK 文档检查语法：

_format_version: "3.0"
services:
  - name: orders-legacy
    url: http://orders-legacy.internal:8080
    routes:
      - name: orders-route
        paths:
          - /orders

该文件声明了两样东西。服务（service）指向遗留后端。路由（route）规定路径为

/orders

的请求发往该服务。你用 decK 将文件同步到网关，把客户端切换到网关的地址，遗留后端便照旧运行，一切如前。

更大的收益来自后续步骤。该文件存放在 git 中，因此每次路由变更都要经过 pull request，并可由 CI/CD 应用。

这正是 Kong 招聘启事所要求的自动化工作。当客户端需要新功能时，你在网关上挂载一个插件。当订单服务终于可以重写时，你只需修改

url

，客户端无需任何改动。

网关无法修复其背后的东西

这是一开始就要向客户讲清的限制。如果遗留后端缓慢或容易出错，在前面加一个网关并不能让它变得更健康。请求多了一跳，客户端也多了一个需要运维和监控的生产组件。

配置文件本身也成为需要精心维护的资产。decK 中一条声明错误的路由可能切断一整组客户端，因此对文件的审查和测试应当与代码一样严格。

从遗留 API 管理平台迁移则更加困难，因为该平台上运行的每一条策略都必须映射到新配置中。Kong 在招聘启事中写明其 FDE 必须构建迁移工具，这表明这种映射在企业规模下很难手工完成。

因此在客户现场，第一项任务应当是盘点。列出每个端点、谁在调用它、谁负责它。只有拿到这份清单，你才知道该先迁移哪些路由、风险在哪里。

Kong 在寻找什么，以及应该先学什么

Kong 的招聘启事要求 8 年以上经验以及广泛的技能：Kubernetes；AWS、Azure 或 GCP；自动化和 CI/CD；外加 Python、Go、Java、JavaScript 或 Lua。

这是一个资深岗位画像。如果你只工作了两年三年，请把它当作一份待补差距的地图，而不是一道将你拒之门槛之外的门槛。

合理的学习顺序是由核心向外扩展。先从反向代理和路由开始。然后在本地运行 Kong，并用 git 中的 decK 管理其配置。

最后，把它部署到 Kubernetes 上。阅读其他公司的 FDE 招聘启事时，留意类似的术语以预判实际工作，然后在面试中就此提问。

在简历上，不要只写“有 API 网关经验”。要描述具体的工作：你把哪个系统放到了网关后面、迁移了多少客户端、以及你如何确保没有人受到影响。这些细节能向雇主证明，你曾在不中断系统的情况下改造过一个真实的系统。
