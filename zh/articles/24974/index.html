使用 AI Agent 推进业务自动化的实务步骤与 FDE 的作用

原标题：AIエージェントで業務自動化を進める実務手順とFDEの役割

FDE総研 · 2026-09-11 · 约 9 分钟读完

摘要

这篇日文文章比较了RPA与AI Agent在业务自动化中的差异，指出AI Agent以目标驱动、可能“静默失败”，因此评测、权限与监控设计比模型精度更关键。作者给出五阶段实施步骤与首个30天的具体做法，说明多数项目卡在PoC阶段是因业务定义模糊和责任划分缺失，并阐述FDE在现场挖掘例外、设计评测与权限、移交运维中的核心作用，最后建议以人工介入率和处理时间为主指标，在2至3个月后评估效果。

要点

  • RPA按固定步骤运行，AI Agent接收目标自行组织步骤，故障方式完全不同。
  • AI Agent会不停机却给出错误结果，必须以评测数据和人工介入率做监控。
  • 适合首批导入的是例外多、可挽回、有人工最终确认的业务。
  • 实施分五阶段：盘点、限定范围、评测准备、分阶段授权、运维移交。
  • FDE核心能力是业务结构化、评测与权限设计、以及运维交接。

  • 业务切分：将目标业务按工序分解，区分包含判断的工序与单纯作业的工序，确定自动化范围。
  • 数据与工具连接：定义要引用的内部数据和要执行的工具（搜索、核心系统、文件操作），并将读取与写入分离。
  • 评测集构建：从实际业务中收集带正确答案的样本，准备可在发布前判定合格与否的评测集。
  • 权限与审计审查：将赋予 Agent 的权限限定到最小，并与安全部门一起确认执行日志和退回路径。
  • 有限运行与扩展：先在部分团队以带人工介入的方式运行，指标稳定后再扩大目标业务和自动执行的范围。

AI Agent 的业务自动化与 RPA 有何不同？

最大的区别在于：RPA 是重现既定步骤，而 AI Agent 是接收目标后自行组织步骤本身。

这一区别直接改变了实施的难度。RPA 是一种以“人把‘怎么操作’全部写完”为前提的工具，只要写完就能稳定运行。AI Agent 则是交付“希望达成什么”，并将过程中的判断委托给它的工具。委托的范围扩大到什么程度是设计的核心，无法明确决定这一点的组织，无论模型性能如何，项目都会停滞。

FDE（Forward Deployed Engineer）这一职位之所以受到关注，是因为这种“在现场决定委托范围”的工作，既不同于传统的委托开发，也不同于企业内部 SE。Palantir 使这一称谓广泛流行，如今日本的 SaaS 企业和 AI 初创公司也开始设立同类角色。

RPA 与 AI Agent 的故障方式有何不同？

RPA 是界面操作的记录，AI Agent 是判断的委托，两者的故障方式和运维成本根本不同。

RPA 的故障清晰且可重现。界面按钮位置一变就会停止，停止后立刻能发现。而 AI Agent 的故障方式是不停止却返回错误的答案。处理已完成，日志显示正常，几周后才有人察觉。能否以这种“静默失败”为前提来设计监控，是运维的分水岭。

视角RPAAI Agent
指令的给出方式明示全部步骤给出目标与约束
对异常的处理出现异常即停止推理异常并继续（错误也会继续）
主要故障模式明确的错误停止静默的错误回答、错误操作
所需监控检测运行／停止持续测量输出质量与人工介入率
对变更的稳健性对界面变更脆弱对措辞、格式的波动稳健
责任的归属编写步骤的人设计权限与审批的人
初期构建的重点步骤的精细打磨评测数据与权限设计

从现场观察来看，RPA 经验越长的团队越容易残留“跑起来了＝完成”的感觉，往往忘记把评测和日志的工作量纳入初期估算。这一点最好在启动前明确约定，后续会轻松很多。

哪些业务适合 AI Agent？

异常多、需要判断，但即使失败也能挽回的业务，是引入 AI Agent 的首选候选。

适合的领域包括：咨询的初步分类、从内部文档中按条件提取、报价与申请的草稿撰写、数据缺陷的检测等。共同点是“保留了人工最终确认的余地”。反之，如果选择金额确定、对外自动发送、库存或预订的确认操作等撤销成本高的处理作为首个题材，往往会因担心事故而收紧权限，最终变成全部由人来确认的形式。

用 AI Agent 推进业务自动化的步骤是什么？

实务上按业务盘点、范围限定、评测数据整备、分阶段授权、运维移交的顺序推进。

阶段期限参考主要交付物进入下一阶段的条件
1. 盘点2～4 周业务流程图、异常清单能够列举异常模式
2. 范围限定1～2 周目标业务定义书明确写出了不做的事项
3. 评测整备2～4 周评测数据集、合格标准正确答案可由人工判定
4. 分阶段展开4～8 周仅提案→带审批的执行人工介入率低于目标
5. 运维移交2～4 周运维手册、监控配置现场能够自行发现异常

期限只是一般性参考，很大程度上取决于目标业务的复杂程度和相关部门的数量。跨部门的业务，与其说是技术问题，不如说达成共识更耗时，这样预估更稳妥。

最初的 30 天要做什么？

最初 30 天的捷径不是自动化，而是把时间用在目标业务的语言化描述和评测数据的收集上。

具体按以下顺序推进。

  • 与目标业务的负责人同行，观察 5～10 件实际处理，逐个手头操作进行观察
  • 梳理“手册上没写但实际在做的事项”
  • 从历史处理记录中抽取代表案例与异常案例共数十件
  • 请负责人本人逐件判定“什么是正确答案”
  • 将判定存在分歧的项目，作为判断标准写成文字

第 5 步是本质所在。负责人之间判定不一致的项目，AI Agent 也必然不一致。把人尚未达成共识的判断委托给系统，往往只会导致关于精度的讨论无休无止。

正式上线前要确定什么？

上线前的前提是：确定失败时的回退方式、日志、审批的落点，并将责任归属保留在人身上。

最低限度需要准备的是：(1) Agent 全部操作的审计日志，(2) 抵消误操作的步骤，(3) 超过一定条件即要求人工审批的阈值，(4) 停止开关，共 4 项。尤其是 (3)，如果用金额、件数、目标客户等业务语言来定义，现场就能自行调整。只有技术人员才能修改的阈值，在运维移交后必然被搁置。

AI Agent 的业务自动化会在哪里失败？

大多数情况并非因为精度不足，而是因为业务定义的模糊和运营体制的缺失而停滞，无法从 PoC 走向下一步。

为什么会卡在 PoC 阶段？

PoC 的成功条件宽松，而生产环境则要考验异常处理和责任划分，因此同样的成果，评价却会反转。

在 PoC 阶段，“大致正确”就能赢得掌声。而在生产环境中，第一个问题则是“出错时谁来负责”。如果 PoC 的设计无法回答这个问题，即使精度足够也无法进入生产环境。反过来说，如果从 PoC 阶段就把审批流程和审计日志纳入验证范围，决策速度会快得惊人。我认为 FDE 从早期就深入业务侧的价值，正在于能够从一开始就把这些“生产环境的问题”融入设计之中。

如果权限和数据的设计出错会怎样？

权限给得太宽，事故的影响范围就无法预估；给得太窄，人工返工增多，效果就会消失。

常见的情况是，直接把现有系统的管理员账号交给 Agent 使用。虽然能运行，但没人能说清可能发生什么，结果在安全评审中被退回。推荐的做法是，为 Agent 发放专用账号，仅列举并授予必要的操作。所授予操作的清单可以直接作为风险说明材料，审计应对也更容易推进。

在数据方面，容易遗漏的是确认参照范围内是否混入了个人信息或人事信息。如果让 Agent 整体参照“业务所需的文档”，意料之外的信息就会混入回答中。

AI Agent 业务自动化对 FDE 要求哪些技能？

业务结构化能力、数据与权限的设计能力、以及运营交接能力，这三项是 FDE 的核心技能。

业务侧需要什么能力？

最有效的是扎根现场挖掘异常情况，并将判断标准落实到文档和评测数据中的能力。

需求规格说明书中的业务与实际业务必然存在偏差。FDE 的工作，就是在现场而非案头捕捉这些偏差。负责人无意识中进行的确认、只在繁忙期变化的运营、仅适用于特定客户的例外。这些信息不会出现在问卷中，而是在旁边观察作业时以闲聊的形式浮现出来。能否把在这里获得的信息直接转化为一条评测数据，正是能力高低的分水岭。

技术侧需要什么能力？

FDE 需要具备评测设计、日志设计、权限设计，以及出现故障时能够回滚的实现能力。

技能领域具体能做到的事缺失时会发生的事
评测设计将业务的正确答案定义为可判定的形式精度讨论沦为主观争论
日志与可观测性使判断依据和输入输出可追踪无法说明错误的原因
权限与安全基于最小权限的连接设计在评审中被退回
集成实现与现有系统的对接和回滚无法做出生产部署的判断
运营移交交接操作手册和监控FDE 一离开运营就停滞

我理解 Palantir 式的 FDE 之所以受到重视，是因为他们能独自横跨这五个领域，并在现场闭环完成。如果采用分工推进，各负责人之间遗漏的问题必然会出现，而那里正是最耗时的环节。

如何衡量 AI Agent 业务自动化的成果？

以处理时间和人工介入率为主要指标，同时将质量和事故数量作为护栏指标并行跟踪。

应该设置哪些指标？

相比自动化率，观察“人工触碰的次数”更能准确反映业务是否真正变轻松了。

指标定义类别
单件处理时间从受理到完成所需的时间主指标
人工介入率人工修正、审批的件数 ÷ 总件数主指标
输出质量评分针对评测数据的合格率护栏指标
重大事故件数需要撤销的处理件数护栏指标
目标业务覆盖率纳入自动化目标的业务比例辅助指标

只追求自动化率，就会倾向于只自动化容易处理的案件来凑数字。将人工介入率和处理时间并列观察，就能可视化“虽然自动化了，但确认耗时很长”的状态。

什么时候衡量效果？

衡量效果不应在导入后立即进行，而是在异常情况经历一轮的 2～3 个月后测量，数字更接近实际情况。

按月、季度、年度发生的业务，在上线后的几周内一次也不会出现。只有经过包含决算期和繁忙期的期间，才能真正看到人工介入率。如果直接把导入初期的好看数字用于内部报告，之后往往要疲于解释数字下滑。我认为在初期报告中明确标注测量期间和未验证的异常情况，在实际操作上更为稳妥。

从作为 FDE 的切身感受来说，成果能够稳固下来的项目，不是数字好看的项目，而是现场负责人开始自己调整阈值的项目。我认为运营交到现场手中的那一刻，才是业务自动化项目实质性的完成节点。
