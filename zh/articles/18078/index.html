LLM 调用前 PII 脱敏与越南个人数据保护法

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

文章以越南第 356 号法令（2026 年 1 月 1 日生效）为背景，讲解在调用境外 LLM API 前处理个人敏感信息的合规要点。核心区分是：加密或用占位符加映射表打码的数据仍属个人数据，只有不留回溯路径的去标识化数据才不再受《2025 年个人数据保护法》约束。作者给出分层过滤器的代码骨架（正则加 NER），强调过滤器必须失败即阻断，并用真实越南语数据测量漏报率，最终由客户法务团队判断系统属于哪一类。

要点

  • 加密后的数据在法律上仍属个人数据，不是去标识化。
  • 保留占位符与真实姓名的映射表，很难称为去标识化。
  • 过滤器出错时应阻断请求，不能失败放行。
  • 漏报率须用客户真实越南语数据按实体类型测量。
  • 最终定性由客户法务团队判断，工程师需如实说明回溯线索。

第 356 号法令收紧敏感数据跨境规则，为图方便留下的映射表可能让系统算不上去标识化。

要点速览

  • 按《2025 年个人数据保护法》，去标识化后的数据不再属于个人数据，而仅仅加密的数据仍是个人数据。
  • 把姓名换成 PERSON_001 标签、同时保留可还原的映射表，只能降低泄露风险。只要还存在回到真实姓名的路径，就很难称为去标识化，最终由客户的法务团队判断。
  • 检测器出错时，过滤器必须阻断请求；漏报率必须用真实的越南语数据来测。

入职一家金融服务客户的第一周，你接到任务：做一个用 LLM 总结客服工单的功能。效果最好的模型通过一个部署在境外的 API 提供。评审会上，法务负责人问：“客户在电话里报给客服的姓名、手机号和密码，会不会传出越南？”

这个问题源自第 356 号法令。该法令于 2026 年 1 月 1 日生效，取代了第 13/2023 号法令，并改变了相关规则。

如果未经彻底去标识化的敏感数据仍要经过境外 API，该法令要求履行更严格的跨境传输手续，并采取加密、匿名化或同等的安全措施。

很多工程师会回答：团队已经全部打码了。只有当你确切知道打码做到了哪一步，这个回答才站得住。法律在“为降低暴露而打码”和“去标识化”之间划了一条相当清晰的界线，两者之间的差距决定了客户身上还背着多少义务。

打码到什么程度，数据才不再是个人数据？

先看定义。《2025 年个人数据保护法》将个人数据定义为能识别特定个人或有助于识别该个人的信息。后半句“有助于识别”最关键：删掉姓名，却留下“教师，会安分部，1990 年出生”，读者依然能追溯到唯一一个人。

法律也给出了明确的出口：经过去标识化的数据不再视为个人数据。这里的去标识化，是指修改或删除信息，生成一个不再指向任何人的新数据集。

第 356 号法令本身就要求数据在数据交易所交易前先做去标识化，可见这是法律正式认可的措施。

工程师通常在两处栽跟头。第一，按照法律，加密后的数据仍是个人数据，因此加密不是出口。

第二，第 14 条第 6 款禁止对去标识化的数据重新识别，也就是说，真正的去标识化必须是单向的。任何需要把真实姓名重新贴回 LLM 回答的数据管道，从一开始就很难归入去标识化。

做法示例法律上的定性
加密发送手机号的密文仍是个人数据
标签加映射表
PERSON_001
↔ “Nguyen Thi Lan”		 降低了风险，但仍有回到真实姓名的路径，很难称为去标识化
真正的去标识化删除姓名及一切有助于推断身份的细节，不留回溯路径不再是个人数据

Wavect 对 GDPR 的一篇分析就中间这一行得出了类似结论：把某人改名为

PERSON_001

能降低暴露风险，但处理流程仍在 GDPR 的管辖范围内。

这只是提醒你要谨慎的信号，不是针对越南的法律结论。客户的系统属于哪一行，由他们的律师决定；你的工作是帮他们看清系统落在哪一行。

一张工单如何通过过滤器

来看一张假设的工单：

Nguyen Thi Lan 女士，手机 0912345678，会安的教师，反映无法登录电子身份认证账户，旧密码是 Lan@1990。

这张工单里有四类信息需要处理。姓名和手机号最显眼。电子身份认证账户的密码被第 356 号法令列为敏感数据，因此捕获它是第一优先级。“会安的教师”这几个字不能直接识别任何人，却有助于识别她。

要总结这张工单，LLM 只需知道事件类型。因此期望的输出只是这样：

[用户]，手机 [电话]，[地点] 的 [职业]，反映无法登录电子身份认证账户，旧密码是 [密钥]。

（这些标签分别代表用户、电话、职业、地点和密钥。）

没有序号，也没有映射表。内部系统仍通过工单 ID 把结果送回对应的人，但 LLM 永远看不到这个 ID。

不过说得直白些，工单 ID 本身也是回溯到用户的一条线索。这种做法大幅减少了流出系统的信息量，却不能让整个系统变成真正的去标识化。向客户描述时，就应该这样如实说明。

下面是骨架代码示意。正则表达式仅作示例，需要根据客户实际的数据格式调整：

import re

RULES = [
    ("SECRET", r"(password|passcode|pwd)\s*(old|new)?\s*(is|:)\s*\S+"),
    ("PHONE", r"\b0\d{9}\b"),
    ("EMAIL", r"[\w.+-]+@[\w-]+\.[\w.]+"),
]

class PIIFilterError(Exception):
    pass

def redact(text: str, ner) -> str:
    for label, pattern in RULES:
        text = re.sub(pattern, f"[{label}]", text, flags=re.IGNORECASE)
    # 人名、地点、职业：需要 NER 模型（例如 Presidio 加越南语模型）
    for span in sorted(ner(text), key=lambda s: -s.start):
        text = text[:span.start] + f"[{span.label}]" + text[span.end:]
    return text

def build_prompt(ticket: str, ner) -> str:
    try:
        clean = redact(ticket, ner)
    except Exception as e:
        # 失败即阻断：过滤器出错时，不向外发送任何内容
        raise PIIFilterError("PII 过滤器不可用") from e
    return f"请总结以下事件：\n{clean}"

（注释说明：人名、地点和职业需要 NER 模型，例如 Presidio 加越南语模型；过滤器出错时，不向外发送任何内容。提示词要求“总结以下事件”。）

最关键的是

except

这一段。Wavect 建议，过滤器绝不能因为检测器变慢或宕机就悄悄“失败放行”（fail open）。实践中，问题往往始于这样一行代码：“超时了就直接发原文，别影响用户。”

检测器再好，也要自己测

检测层可以选用开源库 Microsoft Presidio，它能识别并匿名化文本和图像中的隐私实体，是合理的选择。

即便如此，Presidio 自己的介绍页也写明，不保证能找出所有敏感信息。越南语姓名可能不带声调符号、使用缩写或拼错，漏报率事先无法预估。

所以上线生产环境前，Wavect 建议用客户自己的数据测量：漏报率、任务质量、延迟，以及过滤器如何处理越南语和英语混杂的文本。

举一个假设的数字说明。你人工标注 200 张工单，数出 412 个需要打码的实体，过滤器抓到 375 个。召回率为 375/412，约 91%，也就是说仍有 37 条个人数据流出。

91% 听起来很高，但每天有数千张工单，每天泄露的数据条数会相当可观。结果要按实体类型拆开看，因为漏掉一个密码比漏掉一个区名严重得多。每次新增规则或更换模型，都要像跑回归测试一样重跑这套测试集。

在客户现场的五个步骤

第一步：和客户一起给数据分类。你需要弄清哪些字段属于第 356 号法令规定的敏感类别，以及 LLM 任务实际需要什么。大多数总结或分类任务根本不需要知道任何人的姓名。

第二步：搭建分层过滤器。正则处理结构化内容，NER 处理姓名、地点和职业。第三步：给 LLM 调用套上失败即阻断（fail closed）机制，并记录每一次被阻断的请求。

第四步：在标注数据上测召回率，按实体类型拆分。第五步：写一页数据流说明，标明系统处于上表的哪一行、还有哪些回溯到个人的线索，然后交给法务团队决定。

数据打码并不意味着义务就此结束。法律把加密、解密和去标识化都列为个人数据处理活动，因此在客户基础设施上运行的打码步骤，和其他处理步骤一样必须合规。

常见错误

最常见的错误是只遮住直接标识符，却忽略有助于确定身份的细节。其次是把加密或可逆令牌当成去标识化。

第三个错误与第二个相伴而生：保留占位符 ↔ 真实姓名的映射表，然后告诉客户数据已经去标识化。

把“有助于识别”的定义、加密数据仍属个人数据的规定以及禁止重新识别的条款放在一起读，保留了回到真实姓名路径的方案就很难归为去标识化。

最终判断由客户的律师作出，但他们需要知道映射表的存在。

还有两个错误：一是只用文档里的英文示例句测试过滤器，二是默认过滤器永远会正常运行。

如何把这项技能写进简历

不要只写“用过 Presidio”。要写你在越南语数据上测量了 PII 打码的召回率，并设计了失败即阻断机制，有数字就写上数字。

阅读前线部署工程师（FDE）岗位的职位描述时，“data residency”“PII”或“compliance review”这类字眼，说明对方需要的正是这项技能。
