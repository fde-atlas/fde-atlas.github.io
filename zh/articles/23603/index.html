摘要

根据 Gartner 的数据，60% 的企业 AI 试点从未进入生产环境。更糟糕的是，50% 的 PoC 项目在创造任何实际价值之前就被放弃！

但问题很少出在技术上，而是出在部署上。

这正是前沿部署工程服务公司的用武之地。他们深入你的系统内部，找出真正的问题，并通过交付代码来解决它。

本指南将为你全面讲解：你是否需要 FDE、哪种模式适合你、去哪里寻找、如何甄选，以及费用是多少。

招聘 FDE 不像招聘普通工程师，因为这一职位非常稀缺——这意味着甄选方式有所不同，工作安排和任务也不一样。此外，招聘 FDE 或 FDE 团队要求你清楚地了解他们的任务、你需要采用的合作模式，以及对 FDE 费用的现实预期。

Palantir 最早建立了这一模式。但 OpenAI、Anthropic、Databricks 和 Scale AI 出于同样的原因都在运营 FDE 项目。他们利用 FDE 来弥合模型能力与客户在生产环境中实际需求之间的差距。

Google Cloud 或 AWS 的解决方案工程师完成销售后就转向下一个项目。Microsoft 的客户工程师负责试运行，然后交接。Salesforce 的实施工程师则按照既定手册操作。

然而，他们都不像 FDE 那样对结果负责——FDE 会一直留到系统真正跑通为止。如果跑不通，责任在他们。

FDE 模式并不适用于所有情况。它是为某一类问题而设计的：让技术在一个需求尚不明确、失败代价高昂的复杂系统中真正落地。

所以在开始寻找之前，请诚实地评估你所面对的情况。

  • 问题需要先进行探索。 在有人深入系统内部之前，没人能定义要构建什么。也就是说，这项工作完成之前，构建无法开始。
  • 环境复杂。 陈旧的系统、被锁死的数据或严格的规则阻碍了标准的交付方式。
  • 必须进入生产环境。 概念验证不是目标，业务每天使用的系统才是。
  • 需求尚未完全明确。 业务问题是已知的，但正确的解决方法还不清楚。
  • 工程师必须与真实用户协作。 构建者与使用者之间的反馈循环才是成功的关键。
  • 必须有人对整体结果负责。 不仅是代码，还包括系统的实际采用。
  • 问题已经完全定义清楚。 如果规格说明已经完成，你需要的只是构建者。普通员工或承包商更合适。
  • 你只是缺人手。 这种情况下人员扩充更合适。
  • 你有明确的积压任务。 一份固定的任务清单更适合交给交付团队，而不是 FDE。
  • 事后没人负责系统。 FDE 会把系统交接给别人。如果没有人接手，工作成果就无法延续。
  • 你无法提供真实系统的访问权限。 看不到生产环境的 FDE 无法解决生产环境的问题。
  • 问题还需要界定范围。 先从探索阶段开始。等有了明确要构建的东西，再引入 FDE。

如果你希望长期在组织内部拥有 FDE 技能，直接招聘是合理的。但代价是时间和成本。根据 Anthropic 的招聘网站， 这一职位的薪酬在 $184,000 到 $320,000 之间，这还不包括股权。

由于这类人才极为稀缺，招聘周期会很长。请以月为单位做预算，而不是以周为单位。但这些知识将永久留在你的企业内部。

承包商可以在固定的冲刺周期内为你提供 FDE 技能，且没有长期绑定。这适用于范围明确、且你的团队能够主导工作的情况。但在开工之前，必须先解决一件事：代码归谁所有。

根据美国法律，除非书面协议另有约定，代码归承包商所有。不要把这件事拖到最后。

人员扩充是按时间和材料计费，从供应商处引入工程师。方向由你的团队来定。

供应商提供人手。当你清楚要构建什么时，这种方式效果最好。但如果你还需要摸索要做什么，那它就不合适了。

按成果签约意味着你与合作伙伴签订合同，交付一个明确的结果。例如，Accenture 运营着一支完整的 Palantir FDE 团队，就是以这种方式运作的。

合作伙伴对成果负责，而不仅仅是工时。交接已写入合同：运维手册、培训和知识转移全部包含在内。这种模式最适合复杂度高、且你的团队缺乏 AI 交付经验的情况。

FDE 并非来自普通产品工程师的人才池。兼具生产深度和客户判断力的人才非常稀缺。因此，大多数招聘负责人找错了地方，最终招到的是无法在混乱的客户一线环境中工作的优秀工程师。

  • FDE 专属职位。 曾在 Palantir、OpenAI、Anthropic、Scale AI 或 Databricks 担任 FDE 职位的工程师是最强的信号。这些公司对这类人才的筛选非常严格。
  • LinkedIn 和人脉网络。 搜索 Forward Deployed Engineer、Frontier Agent Engineer 或 Applied AI Engineer。在工作经历中寻找生产系统负责相关的表述，而不仅仅是头衔。
  • 内部推荐。 在复杂企业环境中工作的工程师往往认识同类人才。推荐网络能发掘那些尚未投递过任何申请的人。
  • 相邻岗位。 Google Cloud 的客户工程师、AWS 的解决方案架构师，以及 Salesforce 或 ServiceNow 的技术架构师都可能是合适人选，但前提是他们的履历显示出真正的生产环境负责经验。
  • 前沿部署工程师或类似岗位。 直接匹配。但要确认他们真正负责过生产环境，而不仅仅是提供咨询建议。
  • 有构建实绩的解决方案工程师。 如果他们编写并交付过真实代码，而不仅仅是设计方案，就是合适人选。
  • 平台公司的客户工程师。 如果他们对结果负责，而不仅仅是完成销售，就是强有力的候选人。
  • 有面向客户经历的全栈工程师。 如果他们之前曾在真实运行的外部系统中交付过代码，就能快速成长为该角色。

简历审查和编程测试无法告诉你某人能否胜任这份工作。你同时招聘的是两种能力：深厚的技术功底，以及在客户的世界中无需每一步都被指导就能做出判断的能力。因此，你必须同时测试这两方面。

Anthropic 在其招聘文档中说得直白：“我们关心的是你能做什么，而不是你在哪里学的。我们约一半的技术人员此前没有机器学习经验。”Accenture 也持相同观点。他们更看重一个人如何拆解难题，而不是掌握哪些语法。所以按真正重要的程度排序：

  • 生产经验。 他们是否在真实运行的客户系统中交付过代码，而不是在沙盒环境中？
  • 客户洞察。 他们能否分辨客户提出的需求与客户真正需要的东西之间的差距？
  • 范围控制。 他们会削减范围以交付可用的东西，还是试图构建全部功能却一无所成？
  • 模糊性管理。 在没有路线图的情况下，他们会主动建立结构，还是等待别人告诉他们该做什么？
  • 生产负责。 他们会坚持到客户真正采用为止，还是代码合入后就离开？
  • 冗长的技术清单。 五页的技能列表并不是良好判断力的标志。大多数 FDE 技术栈都是在工作中学会的。
  • 仅有知名雇主背景。 他们在哪里工作远不如他们在那里负责并交付了什么重要。
  • 特定框架专长。 客户的技术栈不会与候选人之前使用的相同。适应能力才是关键。
  • 模型训练背景。 大多数企业级 FDE 工作是使用和连接模型，而不是训练模型。

优秀的 FDE 面试问题应是行为性的且具体的。它们测试的是某人实际做过什么，而不是他们认为应该说什么。

下面每个问题都对应 Palantir、OpenAI、Anthropic 和 Scale AI 共同看重的一项核心能力。要留意真实的细节、体现负责态度的措辞，以及在真实压力下展现判断力的迹象。

软弱的回答有明显的模式。候选人谈论他们构建了什么，却不提他们遇到的限制。他们复述客户的要求，却不追问那是否是正确的需求。他们在代码合入时就宣称工作完成，而不是在客户能够自行运行时。

然而，出色的回答截然不同。候选人会提到真实的人、真实的阻碍，以及他们做出的真实决策。

入围的这些 FDE 开发者会谈论哪里出了问题，以及他们是如何解决的。最重要的是，他们会明确表示结果由自己负责，而不是留给别人收拾。

大多数 FDE 招聘广告在优秀候选人读到之前就已经失败了。它们罗列工具，而不是描述问题。

它们使用的语言可以套用于任何高级工程师职位。因此，合适的人直接划走，不会多看一眼。

  • 真实的业务问题。 用平实的语言描述它。优秀的 FDE 读到后立刻就能判断自己是否合适。
  • 涉及的系统。 写明他们将接触的数据源、API 和平台。隐瞒这些只会浪费双方的时间。
  • 生产环境成果。 描述工作结束时必须存在并上线运行的东西。
  • 如何衡量成功。 是采用率、可靠性，还是工作流影响。而不是交付了多少代码。
  • 客户互动细节。 写明他们将与谁合作以及合作频率。隐瞒出差或客户需求会导致人员很快流失。
  • 交接预期。 明确说明工作结束时需要交付运维手册，并让团队有能力独立运行系统。
  • 冗长的工具和框架清单。 这说明你不理解这个职位真正需要什么。
  • 空洞的套话。 像“热爱技术”这类短语对优秀候选人毫无吸引力。他们会直接跳过。
  • 与成果无关的要求。 如果它无助于系统的交付和运行，就删掉。

问题： 用一两句平实的话说明。具体指出哪里出了问题或缺少什么。‍

你将做什么： 负责成果的调研、设计、构建和上线。与真实用户合作。从采用到交接全程负责到底。‍

环境： 写明所用语言、云架构、数据源以及任何合规限制。‍

完成的定义： 系统已上线、被采用且文档齐全。而不仅仅是代码合并。‍

我们的要求： 4 至 5 年以上工程经验。有在复杂客户系统中交付成果的业绩记录。精通 Python 或 TypeScript。具备相关领域经验。

大多数企业级 AI 项目失败，并不是因为技术不对，而是因为没有人在工作开始前做好铺垫。Gartner 将相当大比例的 GenAI 失败归因于目标不清晰和规划不善。 这两者都是准备阶段的问题。所以，在写任何代码之前，先定义好这些事项。

  • 成果。 项目结束时必须有什么在上线运行？在工作开始之前就写下来，而不是事后。
  • 环境访问权限。 数据源、API 和系统的访问权限必须在第一天之前确认到位。访问延迟是项目时间表失控的最常见原因。
  • 代码所有权。 根据美国法律，雇佣作品条款必须以书面形式约定，代码才能归客户所有。在项目启动前把这件事办好。
  • 内部负责人。 指定贵组织内部在 FDE 离开后将负责运行该系统的人。如果一开始没有指定人选，最后也不会有人接手。
  • 交接格式。 在启动阶段而非收尾阶段就商定交接的形式。包括运行手册、培训，以及团队可以独立运行系统的签署确认。
  • 退出条款。 如果合作提前结束会怎样？半成品系统归谁所有？在它演变成纠纷之前就做出决定。

成本取决于模型、人员的资历、其技术方向以及所在地点。

在美国一线市场，顶级 AI 实验室 FDE 的基本薪资在每年 184,000 至 320,000 美元之间。但这些只是基本数字。股权是真实存在的，且不包含在这些数字中。

因此，包括税收、福利和股权在内的完整雇佣成本将远高于基本薪资。招聘周期也很长。请预留三到六个月的积极寻访时间，尤其是在主要科技市场之外。

FDE 承包商或人员增补没有公开的费率。费率因资历、方向和地点而异。美国劳工统计局给出的软件开发人员平均年薪为 138,110 美元。

然而，考虑到该职位所承担的生产系统所有权和面向客户的要求，FDE 承包商的费率远高于这一水平。

合作伙伴交易按复杂程度、范围和时长定价。没有公开的基准。也就是说，除非附带明确的方法和真实的来源，否则请谨慎对待任何笼统的平均数字。

两种路径并非总有优劣之分。但正确的选择取决于你需要 FDE 技能的时间长短、你需要推进的速度，以及一旦这类工程师到位后，你的团队是否有能力领导他们。

当你在构建需要留在组织内部的核心 AI 系统时，选择直接招聘。问题必须足够清晰，才能证明长期招聘的合理性。你还需要具备领导精英工程师的管理能力。

当复杂度高、你的团队缺乏 AI 交付经验且速度至关重要时，选择合作伙伴。埃森哲（Accenture）运营着专门的 Palantir 业务部门，能带来 FDE 方法和认证人才。IBM、德勤（Deloitte）和 Google Cloud 的专业服务团队也在大规模运营类似的模式。

  • 每个 Entrans 项目都以成果会议启动。验收标准在任何代码编写之前就已写明并达成一致。

前沿部署工程师是一种资深工程师，他们深入客户的系统内部，负责解决方案的完整生命周期，从需求发现到上线和交接。这一模式由 Palantir 开创，如今被 OpenAI、Anthropic、Scale AI 和 Databricks 广泛采用。他们编写生产代码，对结果负责，而不是交付后便离开的顾问。

首先选择适合您的模式：直接招聘、承包商、人员扩充，或以成果为范围的合作伙伴。然后可以关注 Palantir、OpenAI、Anthropic、Scale AI 和 Databricks 的 FDE 职位，或 Google Cloud、AWS、Salesforce 和 ServiceNow 的相关岗位。不过，务必考察候选人是否真正具备生产环境负责和客户需求发现的实际经验，而不仅仅是技术能力。

核心技能包括生产工程、技术需求发现、范围控制、客户沟通以及端到端的责任担当。大多数 FDE 使用 Python 和 TypeScript，并具备 AWS、Azure 或 GCP 的云经验。但相比框架知识，更重要的是在真实、复杂、混乱的企业系统中交付成果的能力。

使用行为面试问题，要求候选人举出过去在客户系统中进行生产工作的真实案例。考察其需求发现直觉、范围判断能力和责任担当意识。优秀的候选人会谈论出了什么问题以及他们如何解决；而较弱的候选人只会描述自己做了什么，却说不清遇到的限制。仅靠编程测试无法考察这个角色所需的判断力。

直接招聘周期较长。这类人才稀缺，竞争激烈。在一线城市市场，预计需要三到六个月的积极搜寻。不过，承包商和合作伙伴渠道的推进速度要快得多。成熟的服务商拥有预先审核好的人才库，启动时间可以从数月缩短到数周。
