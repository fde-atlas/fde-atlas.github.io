FDE 招聘要求怎么读：以 Together AI 为例

FDE Times · 2026-11-08 · 约 6 分钟读完

摘要

文章以 Together AI 的三份 FDE 招聘启事为例，讲解如何读懂 FDE 岗位要求：同一头衔实际对应 GPU 集群验证、推理优化和后训练三类工作，其中两岗 OTE 同为 $270,000–300,000。作者建议从启事中的动词入手理解日常工作，并针对每条要求准备带测量数据的证据，而非按通用模板刷题。文章还用高流量客服聊天机器人的例子演示如何从负载特征推导优化顺序：先开前缀缓存和分块 prefill，再考虑投机解码。

要点

  • Together AI 的 FDE 头衔对应三份不同工作：集群验证、推理优化、后训练。
  • Inference 与 Post-Training 两岗薪资相同，均为 $270,000–300,000 OTE。
  • 读启事先看动词：选择、配置、优化、测试即日常工作内容。
  • 每条要求应准备带基准数据的证据，如 repo 中的测试脚本与对比结果。
  • 常见误区：按通用模板准备、只谈架构、照搬启事技术清单。

要点速览

  • 在 Together AI，FDE 这个头衔对应三份不同的工作：GPU 集群验证、推理优化和后训练。
  • 招聘启事里的动词，比如选择、配置、优化、测试，描述的就是每天要做的事。
  • 针对每一条要求，准备好有测量数据的证据，回答客户一定会问的问题。

在 Together AI 2026 年的招聘启事中，同一个 Forward Deployed Engineer 头衔对应着三份工作。第一位工程师负责在 GPU 集群交付客户之前完成验证；第二位负责选择和调优推理引擎；第三位帮助客户选定后训练方法，并制定数据策略。

如果只是扫一眼启事，然后按“通用 FDE”来准备，很可能花一个月刷系统设计和算法题，而启事真正关心的却是这样的问题：某个引擎为什么在某类硬件上跑得慢。

读懂招聘启事本身就是一项技能。它和前线部署工程师（FDE）在客户现场做的事很接近：拿到一份用业务语言写的需求，把它转化为可测量的技术工作。

Together AI 的三份启事写得都很具体，是练习这项技能的好材料。同样的读法也适用于任何 AI 基础设施公司的 FDE 招聘启事。

三份启事，三份不同的工作

Strategic Inference 岗位要求 FDE 为每个客户选择、配置并优化推理引擎，并要求具备 vLLM、TensorRT-LLM 或 SGLang 等引擎的专家级实战经验。

GPU Clusters 岗位以基础设施为核心：在集群交付客户之前运行测试套件，并排查 InfiniBand 网络和 NVLink 拓扑中的底层瓶颈。这份启事已于 2026 年 6 月 8 日下线，但对理解偏基础设施方向的 FDE 仍有参考价值。

根据 Together AI 的产品页面，其集群规模从可即时启动的自助式集群，一直到数千张 GPU 的部署。在这种规模下，一个漏过验证的故障节点就不再是内部问题，而会变成客户系统里的一次事故。

Post-Training 岗位要求 FDE 针对每个用例推荐合适的后训练方法，并帮助客户制定配套的数据策略。

Inference 和 Post-Training 两份启事列出的美国基本薪资范围相同：$270,000–300,000 OTE。薪资一样，工作内容和准备方向却完全不同。

启事里的动词，就是你的日常工作

读启事时，先看动词，再看名词。Inference 启事写道，FDE 要根据硬件、模型架构和负载特征来选择、配置和优化推理引擎。

一句话，三个动词，三个变量。所以准备时要练习回答：如果这三个变量里只变了一个，你会先调什么，为什么？

GPU Clusters 启事对交付前测试套件用的动词是“设计并执行”，并点名了 NCCL、DCGM 和 GPU Burn。“交付前”这个说法表明，这套测试是集群到达客户手中之前的最后一道关卡。

NCCL 测试通过 all-reduce 等操作检查 GPU 之间的通信带宽；DCGM 对每张 GPU 做健康诊断；GPU Burn 让 GPU 持续高负载运行，使故障在客户碰到之前暴露出来。

实例：把 Inference 启事变成练习项目

假设你的客户运营着一个高流量的客服聊天机器人。每条 prompt 都很长，因为带着对话历史，而回答很短。这是一个具体的负载画像：prefill 重，decode 轻。面对这样的负载，你会先调什么？

Inference 启事点名了三个抓手：调优 KV cache、使用投机解码（speculative decoding）、选择最优的张量并行度。KV cache 保存已处理 token 的 key 和 value，省去重复计算，代价是占用 GPU 显存。

投机解码让一个小模型先猜出后面几个 token，大模型只需验证。张量并行则把每一层的矩阵切分到多张 GPU 上。

有个细节值得注意：最适合这个聊天机器人的两项技术，启事里并没有提到。

vLLM 文档说明，自动前缀缓存（automatic prefix caching）只缩短 prefill 阶段；在多轮对话中，它可以复用已经算好的结果，不必每次都重新处理整段聊天历史。

这个负载里最重的就是 prefill，所以第一步是开启前缀缓存。

第二步是分块 prefill（chunked prefill）。根据 vLLM 文档，这项技术把大的 prefill 与正在 decode 的请求一起批处理，并优先处理 decode，从而改善 token 间延迟。prompt 很长时，它能避免每来一个重 prompt，其他用户的回答就在中途卡住。

投机解码放在后面。vLLM 文档指出，它主要在中低 QPS、且负载受显存带宽限制时帮助降低 token 间延迟。高流量、短回答的聊天机器人不在这个区间，先开它费力而收效甚微。

所以，一个好的回答是这样的：先测当前的首 token 时间和 token 间延迟；开启前缀缓存，再测一次；加上分块 prefill，再测一次；只有数据表明 decode 才是真正瓶颈时，才去尝试投机解码。顺着这个思路，可以把启事里的每条要求整理成一张准备表：

启事中的要求 客户会问的问题 需要准备的证据
根据硬件和负载选择引擎 “我们该用 vLLM、SGLang 还是 TensorRT-LLM？” 两个引擎在同一模型、同一组 prompt 上的基准测试
KV cache 调优 “并发用户一多，为什么显存就不够了？” 随缓存预留显存上限变化的吞吐量曲线
投机解码 “怎样让回答更快出来？” 开关草稿模型时的延迟对比，并写清楚什么情况下它没有帮助
张量并行 “模型一张 GPU 放不下怎么办？” 模型切分到不同数量 GPU 时的延迟与吞吐量对比
按负载画像优化 “我的聊天机器人应该先开什么？” 按上述顺序每一步之后测得的 TTFT 和 ITL

第三列最重要。“用过 vLLM”证明不了专家级实战经验；一个包含基准测试脚本、测量数据，以及一段解释结果成因的说明的 repo，才能证明。

用同样的方法读另外两份启事

对 GPU Clusters 启事来说，客户的问题几乎总是：“这个集群准备好了吗？”好的证据是一份你亲手写的交付检查清单，写明哪些测试按什么顺序运行、什么阈值算通过、失败后如何处理。

如果没有大集群可以做实验，租几张 GPU 用几个小时，就足以跑 NCCL 测试和 DCGM 诊断，再逐项解释结果。all-reduce 带宽低于预期，正好可以作为练习启事要求的 InfiniBand 和 NVLink 排查的起点。

Post-Training 启事中有两个说法值得留意：“针对每个用例的合适后训练方法”和“数据策略”。这说明难点更多在于选对方法、选对数据，而不在模型本身。

需要准备的证据是对一个小模型做一次微调：训练前先建好评测集，给出前后对比表，再用一小段话解释为什么为这个用例选择这种方法。

三份启事的简历建议是一样的：把“熟悉 vLLM、KV cache”换成一句话，写清背景、你改了什么、改动前后的测量数据。这样的一行字让读者看到因果，而不是一串关键词。

常见的准备误区

最常见的误区是按通用模板准备。应聘 Inference 岗位却只谈 RAG 和 prompt，就是跑题；应聘 GPU Clusters 这类岗位却从没读过 NCCL 测试的输出，也一样。

第二个误区是停留在架构层面。如果你的面试回答只有系统架构图，从来没落到引擎配置上，那多半还没触及启事描述的工作：选择、配置、优化。

第三个误区是背下启事里的技术清单，套用到所有负载上。上面的聊天机器人例子说明，被点名的技术不一定是第一步；面试官想听的是你如何从负载推导出选择，并用测量数据支撑。

下次打开一份 FDE 招聘启事，别问自己够不够格，而要针对每一条要求问：我在 GitHub 上已经有什么证据可以拿出来？
