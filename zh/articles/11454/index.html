前沿部署工程师的 AI 应用模式

原标题：AI App Patterns for Forward Deployed Engineers

Vibe Engines · 2026-07-24 · 约 14 分钟读完

摘要

这篇 Vibe Engines 的手册总结了现代前沿部署工程师的核心 AI 工具箱：几乎所有部署都由 RAG、Agent 和评测三种模式组合而成。文章逐一说明各模式的适用场景与代价，强调克制原则——优先选最简单的方案，并给出成本对比表。重点篇幅放在评测上：用冻结的黄金测试集、固定的评分模型和 CI 门槛把“看起来能用”变成可验证的数字。文中用发票路由的例子说明，平均分从 0.79 升到 0.83 也可能掩盖高成本案例的回归，PR 应被拒绝。最后提醒常见错误，如先上 Agent、RAG 缺权限控制、只报平均分等，并主张诚实交付：明确系统能做什么，对关键操作保留人工审核。

要点

  • FDE 部署核心是 RAG、Agent、评测三种模式的组合。
  • 选型要克制：提示词优先于 RAG，固定工作流优先于 Agent。
  • 评测是验收标准：冻结测试集加 CI 门槛防止回归。
  • 示例显示平均分提升可能掩盖高成本案例的回归。
  • 诚实交付：关键操作保留人工审核，不夸大系统能力。

如今大多数 FDE 部署都呈现出相同的形态：拿一个 LLM，让它处理客户杂乱而具体的数据。对其文档进行检索，用一个 agent 驱动他们的某项工作流，再用评测来判断它是否好到可以上线。这是每位现代 FDE 都会使用的应用 AI 工具箱——以及如何在其中做出选择。

现代 FDE 靠 AI 运转

十年前，FDE 做的是软件与软件的集成。今天，很大一部分部署的核心都是一样的：拿一个能力强大的 LLM，让它处理客户具体而杂乱的数据。 客户有搜索引擎无法导航的文档，有吞噬分析师整个下午的工作流，有需要阅读非结构化文本才能做出的决策。FDE 的职责就是把现代 AI 精准地对准这些问题——而相应的工具箱已经沉淀为三种可靠的模式。

本手册就是这份工具箱的地图，写给需要选择并应用这些模式、而非发明它们的 FDE。每种模式在本站都有各自的深度手册；这里我们介绍每种模式的用途、何时使用它，以及它们如何组合成一个你可以问心无愧上线的解决方案。

三种模式

检索、Agent 和评测。几乎所有 AI 形态的 FDE 部署都是这三者的某种组合。

模式作用FDE 用它来……
RAG检索客户文档中相关的片段，并让模型的回答基于这些片段无需重新训练即可基于客户知识回答问题，并随文档变化保持最新
Agent让模型通过调用工具来驱动多步骤工作流，自行决定下一步做什么自动化不止一次调用就能完成的工作流——在风险较高的步骤上保留人工把关
评测用有代表性的测试集为系统输出打分判断系统是否好到可以上线，并在提示词或模型变更时捕捉性能回退

它们可以组合：典型的部署是一个 RAG 系统，有时外面再包一层同时调用客户工具的 agent，并由评测把关，证明它达到了成功标准。理解每一种模式——以及关键在于，何时不去使用更花哨的那种——正是现代这一角色的应用 AI 部分。

基于客户文档的 RAG

检索增强生成是主力工具。客户拥有一批知识——政策、手册、工单、合同——并希望模型准确、带引用地基于这些知识回答问题。RAG 无需重新训练即可做到这一点：将文档分块、向量化，检索出与问题最相关的片段，然后把它们作为 grounding 提供给模型，使答案来自客户的事实，而非模型的猜测。

有两点直接落在你身上。分块 + 检索质量 —— 检索不好意味着模型会自信地给出错误答案，所以大部分调优都花在这里。还有访问控制 —— 用户只能检索到他们有权查看的文档，这在多团队部署中是真正的安全需求，而不是事后才考虑的问题。

RAG 通常是首先尝试的方案，因为它搭建起来很快，能让模型基于可验证的来源，并且文档一更新就能同步。它与其他方案相比的取舍是 RAG 与微调手册 的主题。

用于工作流的 Agent

当任务不只是“回答一个问题” —— 当它涉及客户系统中的多个步骤、决策和操作时 —— 你就需要用到 Agent：一种能够调用工具、观察结果并决定下一步做什么的模型。一个 Agent 可以读取工单、查询记录、起草回复并归档 —— 这类多步骤工作流过去在每个环节都需要人工参与。

Agent 功能强大，但也容易用力过猛。FDE 的准则是使用能解决问题的最小自主权：当步骤已知时，一个只调用一次模型的固定工作流胜过自由漫游的 Agent，因为它更可预测、更容易调试。而对于任何有重大影响的操作 —— 发送邮件、转移资金、修改记录 —— 都要保留人工审核环节。有两本现场手册对此有深入探讨：Agent 模式 讲怎么做，Agent 与工作流 讲关键的何时不该用。

评测作为验收测试

这是工程师最容易跳过、事后又后悔的模式。评测是让“看起来能用”变成一个你可以为之背书的数字的方法。

一个没有评测的 AI 系统是你无法诚实地交付的系统，因为“演示中看起来不错”经不起真实输入的考验。评测是一组有代表性的示例加上一种给输出打分的方法 —— 一个针对模糊而非精确行为的测试套件。对 FDE 来说，它是回到需求发现的桥梁：大家一致同意的成功指标就变成你用来衡量的评测标准。

评测能给你什么

  • 对“它够不够好？”的客观回答 —— 与商定的指标挂钩。
  • 当你更改提示词、模型或检索时的回归防护。
  • 客户利益相关方可以信任的证据。

如何开始

  • 从客户那里收集带有已知正确答案的真实示例。
  • 选择一种打分方法（精确匹配、LLM 评审、任务指标）。
  • 每次更改都运行评测；让数字可见。

评测让 AI 从一种感觉变成一门工程。这个主题足够深入，值得专门研究 —— Agent 评测 和 CI 中的评测 —— 也值得在交互式挑战中培养一种条件反射。

选对模式 —— 并诚实地交付

这项元技能是克制：选择能达标的最简单模式。当知识能放进上下文时，精心设计的提示词胜过 RAG；当需求是知识而非行为时，RAG 胜过微调；当步骤已知时，固定工作流胜过 AI Agent。复杂性是你在可靠性和可调试性上付出的代价，所以只有在更简单的模式明显不够用时才增加它。

如果需求是…就选择…
让模型以不同方式表现/输出格式更好的提示词，然后是微调
基于客户文档给出有依据的回答RAG
带操作的多步骤工作流一个 AI Agent（能用的最小自主性）
知道这一切是否足够好评测——永远都要

并且诚实地交付。大多数 AI 解决方案并不完美，但如果工作流的设计能让错误被发现而不是被盲目执行，这就没问题。在需求发现阶段就定义好“足够好”的标准，在关键决策上保留人工环节，坦率地说明失败模式，并且——因为模型会读取不受信任的客户内容——把每个输入都当作潜在的对抗性输入（安全手册涵盖了提示词注入）。一个诚实地交付 85% 并能安全处理其余 15% 的 FDE 能创造真正的价值；一个夸大一个脆弱的 95% 的 FDE，在系统第一次出问题时就会失去客户。这种诚实——关于系统能做什么、不能做什么——是整个 FDE 手艺的最后一块拼图。

能抓住平均值所掩盖问题的关卡

评测是工程师最容易跳过然后后悔的模式。这是最小版本，但它是一个真正的控制手段，而不是一份文档。

上面的一切都产出一个数字。仪表盘上的数字改变不了任何东西——提示词照样会在周五被修改，模型照样会被升级，回归照样会被发布。从“我们有评测”到“评测是控制手段”的转变只发生在一个时刻：当某人的拉取请求被拒绝时。

总体分数

以人类基线为准——即他们的两位专家彼此一致的频率——而不是以销售会议上拍出的整数为准。

# 回归和评审模型的怪癖。

有两项纪律能让这道关卡长期保持诚实。黄金集是冻结的——修改一个用例是一项需要审核并记录原因的决策，标准与 schema 迁移相同，因为评测流水线最常见的死法，就是一个失败的用例被以“反正它本来就是错的”这种听起来合理的理由悄悄改掉。而评审模型是固定的，因为升级它会重新校准所有历史分数的基线。

产品中一个一键纠错控件能把六周的真实使用转化为带标注的数据。这是成本最低的标注流水线，也是唯一能提供你没想到的用例的来源，而几乎没有人会在需要之前就把它做出来。完整论述见 面向客户工作的评测；该方法可在 评测构建实验室 中实际操作。

实例演示：一次提示词修改通过关卡

假设你已部署了一个发票路由助手。冻结的黄金集有 200 个用例，其中 40 个属于高成本类别（会被自动批准的发票）。一位同事提交了一个重写提示词的 PR。上面深度剖析中的关卡对两个版本都运行。计数和分数仅为示意。

总分≥ 0.72158 / 200 = 0.79 ✓166 / 200 = 0.83 ✓
高成本错误率≤ 0.020 / 40 = 0 ✓2 / 40 = 0.05 ✗
回归无基线3 个原本通过的用例现在失败 ✗

新提示词修复了 11 个用例，破坏了 3 个，所以分数上升了 8（158 + 11 − 3 = 166）。仪表盘会显示系统变好了。被破坏的 3 个用例中有 2 个是高成本发票，而这正是客户为之付费的失败。只有回归列表和错误预算能看到它。还要注意预算的分辨率：40 个高成本用例下，单个错误就是 2.5%，已经超过 2%。该类别至少需要 50 个用例，一个错误才能落在预算之内。

常见错误

  • 一开始就使用 Agent演示用的 Agent 看起来很炫，但失败的方式无人能复现。如果你能在白板上写出步骤，就把它们编码为工作流，只在需要判断的地方使用模型。
  • 没有访问控制的 RAG如果检索不考虑提问者是谁，初级用户的问题可能会检索出董事会资料。在检索时按用户权限过滤，而不是在答案生成之后。
  • 用演示数据构建黄金集你自己编写的案例只能测试你已经想到的东西。黄金集应基于真实的客户输入构建，答案需经客户专家认可，并按稀有且代价高的案例分层，确保它们包含在内。
  • 修改失败的黄金案例失败的案例是集合中最有价值的一行。只有在经过评审并记录原因的情况下才能修改它，就像对待 schema 迁移一样。
  • 只报告一个平均值平均值会把少数代价高昂的失败隐藏在大量廉价的胜利之中，正如示例所示。应同时报告高成本类别和回归列表。

这在生产环境和面试中的体现

  • 从需求发现到验收在需求发现阶段商定的成功指标，例如“85% 正确，其余标记出来”，会成为门禁的阈值。一个没人同意过的阈值，是日后你会争论不休的数字。
  • 安全审查客户的安全团队会问谁能检索什么，以及模型可以自主执行哪些操作。按用户的检索过滤器和重大操作的人工审批可以同时回答这两个问题。
  • 交接当你离开时，客户的团队会接手这个系统。一个冻结的黄金集、一个固定的评判器和 CI 中的一个门禁，让他们在没有你的情况下也能修改提示词。
  • 面试版本面对一个混乱的客户问题，说出你会从哪种模式入手，以及更简单的模式为何不够用。然后说明你会如何衡量它。在被问到之前主动说出“评测”，是你能给出的最强信号。

自我检测

一位客户的政策手册有 30 页，每年更新两次。他们想要一个问答助手。RAG、微调还是提示词？

先从包含手册内容的提示词开始，前提是它能放进模型的上下文。这是能达标的最简单模式，更新只需编辑提示词。当语料库超出上下文窗口，或用户需要不同的子集时，再转向 RAG。

总分从 0.79 提升到了 0.83。这个 PR 应该合并吗？

不能只看这个数字。先检查回归列表和高成本错误率。在之前的实例中，同样的涨幅掩盖了两个损坏的高成本案例，门禁拒绝了它。

你的高成本类别有 40 个案例，预算是 2%。单个错误会怎样？

它会阻止 PR 合并：1 / 40 = 2.5% > 2%。当案例少于 50 个时，预算实际上意味着零错误。要么把类别扩充到至少 50 个案例，要么把预算改用数量来表述。

任务是：读取工单、查询账户、起草回复、发送。该用 AI Agent 还是工作流？

用固定工作流：步骤是已知的。用模型来起草，并在发送前加入人工审批，因为发送是有重大后果的操作。

快速问答

前沿部署工程师最常用哪些 AI 模式？

三种占主导。RAG（检索增强生成）通过检索相关片段，让 LLM 基于客户自己的文档工作并据此作答。AI Agent 让模型通过调用工具驱动多步骤工作流，对有重大后果的操作由人工把关。而评测——一套测试集加评分方法——充当验收测试，决定解决方案是否足够好、可以交付。

什么时候该用 RAG，什么时候该用微调？

当需求是知识时，选 RAG——模型必须使用客户特定的、不断变化的文档来回答；检索无需重新训练即可提供依据，并随文档更新。当需求是行为或格式时，选微调——即基础模型做不好的统一风格、结构或任务。大多数 FDE 部署从提示词加 RAG 开始，只有在仍存在明显行为差距时才进行微调。

什么是评测？它对 FDE 为什么重要？

评测是一组有代表性的示例，加上对模型输出进行评分的方法——实际上就是 AI 系统的测试套件。对 FDE 来说，评测就是验收测试：它把“看起来能用”变成一个与发现阶段商定的成功指标挂钩的可量化数字。当你更改提示词或模型时，它还能捕捉回归，并向客户提供解决方案足够好的客观证据。

当 AI 解决方案达不到 100% 准确时，如何诚实地交付它？

在发现阶段定义“足够好”的标准（例如“85% 正确、其余标记给人工处理，每天节省四小时”），设计工作流使模型的错误被捕获而不是被盲目执行，并对有重大后果的决策保留人工把关。坦率地说明失败模式，并用评测来度量它们。一个诚实达到 85% 准确率并安全处理其余 15% 的 AI 系统，胜过一个假装完美的系统。
