前沿部署工程的 AI 工具

原标题：AI tools for Forward Deployed Engineering

AI Engineer · 2026-07-28 · 约 29 分钟读完

摘要

Varick Agents 的 Vasuman Moza 与工程负责人 JD 在 AI Engineer World's Fair 2026 上介绍面向前沿部署工程师的内部 AI 工具。核心观点是：Agent 执行能力已接近成熟，稀缺的是理解客户业务的注意力。FDE 需先深入客户部门、梳理未成文的例外流程，再围绕 AI 重构流程，并在 NetSuite、SAP 等现有系统之上部署。Varick 用依赖图表示企业流程，通过后训练与强化学习训练模型撰写精炼分析并检索正确上下文，其 FDE Agent 分为参与、工作流、自主维护三个阶段，目标是让一名工程师维护多个客户。

要点

  • Agent 执行能力已强，瓶颈在于理解客户业务的注意力
  • FDE 三步职责：梳理流程、围绕 AI 重构、在现有系统上部署
  • 例外交接流程（如 AP 到 AR 的四天延误）是文档常遗漏的关键信息
  • Varick 用依赖图加后训练与强化学习训练 FDE Agent，分三阶段开发
  • 部门级重构报告 25%–75% ROI，高于单点方案的 5%–10%

你能深入到客户什么程度？

一个工程团队如何在不以相同速度增加人手的情况下，深入理解每个客户并变革其运营？这就是 Varick Agents 背后的规模化问题，Vasuman Moza 在其中描述了高度定制化的企业部署，要求工程师深入客户的业务内部工作。稀缺的资源并不仅仅是构建另一个 Agent 的能力，而是理解该 Agent 应该做什么所需的注意力。

Moza 的出发点是，推理模型和执行框架已经改变了约束条件。浏览器操作工具、API 以及 Model Context Protocol 集成为 Agent 提供了跨软件系统执行工作的途径。他将这种执行能力描述为接近完美——这是对技术的一个强判断，而非本文中给出的实测结果。

业务上下文仍然顽固地保持本地化。一个医疗保健销售部门和一个 SaaS 销售部门可能名字相同，但运作方式却大不相同。它们的员工了解那些让工作得以推进的例外情况、依赖关系和非正式决策，但提取这些知识非常困难。把它们打包进一个简单的 API 或模型调用，并不能自动产生对业务的持久理解。部署问题越来越多地在于明确界定工作内容，而不仅仅是执行工作。

2:32 ↗

在重新设计流程之前先梳理例外情况

从以人为中心的运营转向以 AI 为中心的运营，需要的不仅仅是分发 Cursor、Claude Code、Codex 或 Factory。运营流程本身必须改变。一名前沿部署工程师（FDE）首先要了解公司如何运转，然后再思考借助 AI 它可以如何以不同的方式运转。

在 Varick，多名 FDE 会驻扎在客户处，但他们把拥有数千名员工的企业缩小到一个部门。在财务领域，这意味着访谈应付账款（AP）、应收账款（AR）、卡对账、银行业务、开票以及财务规划与分析（FP&A）的流程负责人。关键问题不仅仅是流程通常如何运作，而是当流程失败时会发生什么。

在 Moza 的例子中，AP（应付账款）部门的 Sarah 把一个采购订单/发票对账问题交给 Chris，增加了四天的处理周期。一份描述黄金路径和几个边缘情况的文档可能永远无法捕捉到这种交接。然而，这种交接是 Agent 必须处理的实际流程的一部分。这些公司特有的异常路径解释了为什么企业自动化仍然需要大量的人工指导：缺失的信息往往是当文档化的流程失效时，人们如何进行补救。

4:49 ↗

足够多地重新设计以创造价值，但保留可采纳性

在梳理完工作之后，第二项职责是对其进行重新设计。在一个有缺陷的流程中加入 AI，可能会保留原有的瓶颈，同时引入新的失败模式。Moza 引用了 95% 的试点失败率，以及另一个未指明来源的 87% 的数字，来描述令人失望的企业应用结果。这些数字不应被视为可互换的生产采纳率或投资回报率指标：可能与 MIT 相关的来源，《The GenAI Divide: State of AI in Business 2025》，区分了报告的回报与生产采纳率，而第二个统计数据的来源尚未确定。

这种困难即使在编程领域也很明显。让一个 Agent 重构整个代码库仍然需要人工输入；把类似的工具交给财务、销售、市场、采购或物流中的非技术操作人员，并不能让他们具备工程师驾驭系统的能力。FDE 必须围绕 Agent 的能力和操作人员的使用能力来重新设计流程。

一次改动太多可能会破坏采纳。习惯了十一步工作流程的操作人员，当流程变成一步时可能会难以适应。但保留每一步也会让价值无法实现。在另一个八步的例子中，Moza 这样分配职责：

职责步骤数角色
自主 Agent4无需干预完成工作
有人工参与的 Agent3让人保持在流程中
仅人工1保留风险较高或 Agent 价值较低的工作

设计决策是在单个步骤的层面上做出的。自动化是职责的分配，而不是把人从整个流程中移除的要求。

7:02 ↗

部署在企业已经在使用的系统上

FDE 的第三项职责是在现有系统上进行部署。企业已在 NetSuite、Dynamics、SAP 和 Salesforce 上投入巨资。一个要求企业放弃这些系统的独立 AI 产品，忽视了它们已经付出的成本和组织投入。Moza 报告称，有一位客户花费了 500 万美元和五年时间迁移到 NetSuite。要求该客户再次迁移，不太可能是一个可行的切入点。

Varick 的做法是将 Agent 置于这些记录系统之上。其 Varick OS 平台提供 Agent 的创建、监控和治理，同时保留客户现有的企业软件。因此，这三项职责构成一个序列：梳理人们实际的工作方式，围绕 AI 重新设计流程，并在业务已经运行的地方部署由此产生的 Agent。

8:28 ↗

围绕稀缺的 FDE 扩展上下文工作

这种职责组合使得 FDE 难以招聘。Moza 将 2026 年及以后描述为对兼具卓越技术能力、沟通技巧和对客户敏感度的人才需求不断增长的时期。他关于顶尖百分位和数量级差异的比喻，表达的是这种雄心的规模，而非实际测量的招聘标准。在实践中，公司往往要么培训顾问学习工程，要么培训工程师学习客户沟通；要找到两者兼备的人才则更为困难。

FDE Agent 旨在扩展这些人的能力。一名工程师或前沿部署策略师应能在保留客户所需人工支持的同时，维护多个客户关系。工作负载包括持续的邮件往来、数百页的文档，以及优先级相互冲突的流程负责人。应付账款依赖于应收账款、对账和 FP&A，但每位负责人对什么最重要都有不同的看法。管理好这一共享上下文，正是让一个小团队能够提供高强度支持、而不必沦为只能靠增加人手来扩张的咨询公司的关键。

Moza 将大约 2024 年的执行约束与他当前“知识工作几乎已完全解决”的观点进行对比。从这一视角出发，剩下的挑战在于设计工作如何完成：理解客户、选择自动化什么，以及以足够稳健的方式实施工作流，从而改变部门绩效。关于知识工作已被解决的宏大论断，是他投资 FDE 工具的前提。

Moza 估计，孤立的客户挖掘或 AP 解决方案的投资回报率为 5–10%，而 Varick 的全部门转型则可带来 25%、50% 或 75% 的投资回报率。他没有提供客户层面的具体结果、衡量周期，也没有给出这些数字的投资回报率定义。其战略区别在于范围：重新设计整个部门可以解决单一功能产品无法触及的依赖关系。他将预期收益归纳为收入提升、成本节约和风险缓解，然后把技术讲解交给工程主管 JD。

从文档分析到工作流辅助

内部工具项目始于办公室内的一种反差。JD 的平台团队使用编程助手得心应手，而 FDE 们却被客户沟通搞得筋疲力尽。当他询问他们的工作流程时，得到的答案是一个重复的文档分析循环。JD 描述说，FDE 们将大约 150 页的内容上传到 Claude，等待大约两分钟，然后收到他们认为冗长且不正确的分析。这一描述只是运营轶事，并非受控的延迟或准确性测试。提出的补救方案是一个专为 FDE 打造的助手，分三个阶段开发。

第一阶段是项目对接 Agent，帮助 FDE 准备和理解工作。它会提取 Granola 笔记、综合整理文档并阅读 PowerPoint 幻灯片。它提出的问题非常实际：这个流程由谁负责，或者邮件中的 Sarah 和 Slack 中拼写不同的名字是否指同一个人。反复回答这些问题是构建工作流的一部分，而每次都要等待通用助手会拖慢工程师的速度。

第二阶段是工作流 Agent，它将项目对接上下文嵌入 Varick 的平台中。当 FDE 构建工作流时，该 Agent 可以标记被遗忘的异常情况，或建议在选择邮件收件人之前先确认流程负责人。它与 Claude 或 Codex 协同工作，检查正在构建的工作流是否反映了预期的业务流程。上下文助手现在出现在其答案会影响实施的关键节点上。

第三阶段是自主维护，JD 明确表示团队尚未达到这一阶段。他举的例子是客户通过邮件要求更改 QC 报告的目标位置。预期的流程是：

  • 接收客户的变更请求。
  • 查询已存储的对该公司的理解。
  • 在 Varick 的平台上更改工作流，无需 FDE 参与。

幻灯片将第三大支柱标注为开发 Agent。所提出的自主能力将处理小型维护请求，同时为 FDE 保留时间用于访谈和更深入的流程理解；这并非已演示的实际变更。

将公司表示为依赖关系

所有三个阶段都需要一个关于公司如何运作的共享表示。JD 将存储引擎视为次要的：图数据库或 Postgres 都可以保存这些信息。Varick 使用依赖图，因为流程负责人关心前置条件。在 A 和 B 批准之前，C 不应该需要处理某个任务。

一个简单的 SQL 示例使这一前置条件规则变得具体。这里 A 已批准，B 仍在等待，因此 C 无法继续。该查询测试的是是否存在未满足的前置条件，而不是将单个批准视为充分条件：

sql

WITH dependencies(task, prerequisite) AS (
  VALUES ('C', 'A'), ('C', 'B')
), approvals(person, approved) AS (
  VALUES ('A', true), ('B', false)
)
SELECT NOT EXISTS (
  SELECT 1
  FROM dependencies AS d
  LEFT JOIN approvals AS a
    ON a.person = d.prerequisite
  WHERE d.task = 'C'
    AND a.approved IS DISTINCT FROM true
) AS c_can_proceed;

表名和审批状态说明了 JD 的“A 和 B 先于 C”规则；它们并非 Varick 公开的模式（schema）。JD 还描述说，真实的企业工作流大体上是线性的，但包含许多循环，因此这个局部前置条件检查并不能定义整个公司图的语义。

针对客户实际需要的细节进行训练

有了表示之后，第一个模型训练问题是输出质量：给定正确的提取上下文，模型能否写出有用的分析？JD 报告说，Claude 的长篇分析对于这项工作来说过于冗长。缺失的技能是他在顾问身上看到的判断力——识别客户关心哪些细节，哪些可以压缩或省略。

因此，Varick 在开源基础模型上对模型进行后训练，以在细节与清晰度之间取得平衡。JD 提到了一个与 Kimi K2.6 一致的 Kimi 模型，同时表示其他模型也可以使用。目标是从提取的上下文中生成规范化的流程图。训练目标不仅仅是更短的答案：而是保留具有操作意义的细节、又不将其埋没在不必要分析中的答案。

训练模型找到正确的上下文

从给定上下文中写出好内容只解决了问题的一半。公司的知识图谱可能很大，可靠地找到相关上下文本身就是一件困难的事。在对模型进行后训练之后，Varick 将其置于一个强化学习环境中，并配有用于遍历该图谱的自定义工具。模型必须学会获取其分析所需的信息。

JD 给出了两个工具支持任务的示例：

  • 解析人员。 判断两个引用是否指向同一个人。一家公司可能有许多名叫 Mike 的员工；仅凭姓名匹配可能会选错人，并附加错误的所有权上下文。
  • 检查依赖关系。 识别冗余循环或违反有向无环图（DAG）约束的情况。这既检查图结构，也涉及记录检索。

前面的描述允许操作层面的循环，而这一部分讨论的是 DAG 违规。演讲并未说明哪些关系必须无环，也没有说明合法的工作流循环如何表示。要正确实现校验器，必须明确这一区别。

该架构区分了两种失败模式：检索到错误的上下文，以及基于正确上下文产出糟糕的分析。后训练解决规范化流程的实用性问题；RL 环境解决工具使用和遍历问题。架构幻灯片还提到了检索评测，以及针对遍历失败的强化学习，但 JD 未提供奖励规范或评测结果。对小型工作流变更的自主管理仍是开发中的下一阶段。

合作依然始于业务内部

工具并不能省去了解客户的初始工作。回到合作模式，Moza 描述了一个刻意的顺序：先派 FDE 和策略师进入公司进行审计，然后在 Varick 的平台上实施 Agent。仅凭产品能力无法揭示一家企业实际如何运转；审计提供了这些能力所需的理解。

技术基础设施依然重要，但推动 FDE Agent 的约束是部署过程中的人力投入。Moza 最后邀请工程师加入团队，并邀请企业探讨内部转型。预期的结果是：在自动化进入生产之前，企业的流程已被充分理解并重新设计，而 FDE 的协助使这种深度的合作能够覆盖更多客户。
