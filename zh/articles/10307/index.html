为什么 RAG 是 FDE 最重要的单项 AI 技能

检索增强生成（RAG）是一种架构模式，它将通用的 LLM 能力转化为面向客户的 AI 应用。没有 RAG，LLM 只知道它在训练期间学到的内容。有了 RAG，LLM 可以检索客户特定的上下文（文档、数据库记录、代码、对话历史），并基于该上下文生成回答。对于在客户环境中构建 AI 应用的 FDE 来说，RAG 是玩具演示与可投入生产系统之间的分水岭。

FDE Pulse 对 200 多条 AI 公司 FDE 职位发布的分析显示，78% 的职位明确提到 RAG、向量数据库或检索作为必备技能。其余 22% 提到 LLM 应用但未使用具体的 RAG 术语，但无论职位描述如何表述，生产级 AI 工作几乎总是采用 RAG 模式。掌握 RAG 架构是 FDE 在 2026 年能做出的回报最高的 AI 技能投资。

本指南从三个层面介绍 FDE 需要了解的 RAG 架构知识：每个 FDE 都应理解的概念模型、生产级项目所需的实现模式，以及资深 FDE 岗位所期望的运维深度。目标是让你在客户项目中有足够的深度做出架构决策，而不是把你培养成 RAG 研究人员。

概念模型：从文档到响应的六个步骤

步骤 1：文档摄取。 你从客户特定的源文档开始：PDF、HTML 页面、Confluence wiki 条目、代码仓库、支持工单、合同文件。摄取管道将这些文档解析为规范化的文本表示，并保留元数据（来源 URL、文档标题、作者、日期、访问权限），这些信息在后续步骤中会用到。

步骤 2：分块。 文档被切分成更小的片段（通常每块 200-1,000 个 token），称为块（chunk）。分块策略多种多样：固定大小分块（简单，但常产生生硬的切分）、语义分块（按段落或章节边界切分，更自然）、递归分块（适应文档结构的层级式切分）。分块策略的重要性远超大多数团队的认知；无论管道其余部分多么出色，糟糕的分块都会毁掉检索质量。

步骤 3：嵌入。 每个块通过嵌入模型（OpenAI 的 text-embedding-3-large、Cohere 的 embed-multilingual-v3、Voyage AI 的模型，或开源替代方案）转换为高维向量表示。该向量以某种方式捕捉块的语义含义，使你能够通过向量相似度搜索找到相似的块。

第 4 步：向量存储。 嵌入向量会存储在针对相似性搜索优化的向量数据库中。常见的选择包括：Pinecone（托管服务）、Weaviate（开源并提供托管云）、Qdrant（开源，可云端或自托管）、pgvector（Postgres 扩展）、Chroma（轻量级，常用于原型开发）。具体选择取决于规模需求、运维偏好，以及客户是否已有可扩展的 Postgres 基础设施。

第 5 步：检索。 当用户查询进来时，会使用与分块时相同的模型进行嵌入，然后通过相似性搜索从向量数据库中检索出最相似的前 K 个分块。K 通常在 3 到 20 之间，具体取决于用例。现代检索通常将向量相似性与其他信号（BM25 关键词搜索、元数据过滤、时效性加权）结合，采用混合检索方式，其效果优于纯向量搜索。

第 6 步：生成。 检索到的分块会作为上下文插入到 LLM 的提示词中，与用户查询和指令放在一起。LLM 基于检索到的上下文生成回答。提示词的结构（分块如何格式化、用什么指令引导 LLM、上下文不足时如何处理）对生产级输出质量至关重要。

生产级 RAG：超越基础模式

混合检索。 纯向量相似性搜索会漏掉那些精确关键词匹配很重要的查询（产品代码、特定名称、技术 ID）。将向量搜索与 BM25 关键词搜索结合，并对合并后的结果进行重排序，其效果优于单独使用任何一种方法。实现方式：如果向量数据库支持混合搜索（Weaviate、Qdrant），则直接使用；否则分别运行向量搜索和 BM25 搜索，再用倒数排名融合（reciprocal rank fusion）合并结果。

重排序。 初始检索基于粗粒度相似性返回最相似的前 K 个分块。重排序器（通常是交叉编码器模型，如 Cohere Rerank 或 BAAI 的 bge-reranker）会用更昂贵但更准确的评分函数对前 K 个候选结果重新打分。在真实的客户用例中，重排序通常能将检索质量提升 10-30%，代价是额外的延迟和计算开销。

查询转换。 用户查询往往不精确、有歧义，或与相关分块的表述方式不同。查询转换会在检索前重写用户查询。常见模式：HyDE（假设性文档嵌入）先生成一个假设性答案，再将其嵌入用于检索；多查询将查询重写为 3-5 个变体并分别检索；查询分解将复杂查询拆分为多个子查询并分别检索。

元数据过滤。 生产级 RAG 系统很少搜索整个文档语料库。在向量搜索之前按元数据（文档来源、日期范围、访问权限、文档类型）进行过滤，能显著提升相关性和安全性。对于面向特定客户的部署，基于元数据的访问控制往往是最重要的生产考量；你不希望某个客户的 RAG 系统返回另一个客户的文档。

评测流水线。 玩具级 RAG 演示与生产部署的 RAG 系统之间最大的区别在于评测基础设施。生产系统包括：由代表性查询和预期响应组成的黄金测试集、对检索质量（召回率、精确率、命中率）和生成质量（忠实度、答案相关性）进行打分的自动化评测运行、对生产查询质量的持续监控，以及将用户点赞/点踩信号纳入模型改进的反馈闭环。没有评测流水线，你就无法知道 RAG 系统何时出现退化、何时可以投入生产。

FDE 项目中的向量数据库选型

Pinecone： 2026 年使用最广泛的托管向量数据库。性能强劲，开发者体验良好，运维模型简单。定价按 pod 或按 serverless 用量计费，对于负载波动较大的场景，serverless 通常更经济。最适合：希望拥有托管基础设施且无需承担运维负担的团队、偏好云原生的客户、可以接受额外供应商关系的部署。

Weaviate： 开源，同时提供强大的托管云选项。以一流混合搜索支持以及能很好处理复杂元数据的灵活 schema 模型著称。最适合：希望保留开源退路同时可选托管便利的团队、需要混合搜索的部署、拥有复杂文档元数据结构的客户。

Qdrant： 开源向量数据库，性能强劲，托管云服务正在兴起。比 Weaviate 更轻量，在纯向量工作负载上往往更快。最适合：偏好自托管的基础设施团队、以向量搜索性能为首要标准的部署、能够自行运维 Qdrant 集群的客户。

pgvector： 为现有 Postgres 部署添加向量搜索能力的 Postgres 扩展。在大规模场景下比专用向量数据库慢，但当客户已拥有 Postgres 基础设施和运维经验时，往往是正确的选择。最适合：1000 万向量以下的部署、拥有强大 Postgres 运维能力的客户、以及避免引入新基础设施依赖比性能更重要的场景。

Chroma: 轻量级向量数据库，常用于原型设计和小规模部署。其单进程设计使其不适合大规模生产环境，但简单性使其非常适合 FDE 项目的前 1-2 周——在投入生产基础设施之前先验证概念。

选择启发式方法： 需要扩展的原型可从 Pinecone serverless 开始。如果开源很重要或混合搜索至关重要，则切换到 Weaviate 或 Qdrant。当客户现有的 Postgres 基础设施使这一权衡值得时，使用 pgvector。在获得生产使用数据之前，不要让这个决定显得不可更改；如果早期选择不合适，向量数据库迁移是可行的。

常见的 RAG 失败模式及调试方法

失败：检索返回不相关的分块。 最常见的原因：分块策略不佳。过长的分块会稀释嵌入信号；过短的分块会丢失语义上下文。诊断方法：针对代表性查询检查检索到的前 K 个分块。如果分块偏离主题，请重新审视分块策略。如果分块切题但生成结果错误，问题出在提示词或模型选择上，而不是检索。

失败：尽管使用了 RAG，LLM 仍产生幻觉。 最常见的原因：分块实际上并不包含答案（检索未命中）、指令没有告诉 LLM 将回答基于上下文，或者 LLM 在训练中获得的竞争性知识覆盖了上下文。诊断方法：添加明确的指令，例如“如果答案不在提供的上下文中，请如实说明”。运行仅检索测试，验证是否检索到了正确的分块。如果较小的模型无法可靠地遵循基于上下文的指令，请使用能力更强的模型。

失败：延迟超出客户要求。 最常见的原因：同步重排序增加 1-3 秒、多查询方法成倍增加嵌入延迟、大上下文规模下 LLM 生成缓慢。诊断方法：按组件分析端到端延迟。优先优化最慢的组件。为重复查询缓存嵌入。即使文档摄取使用较慢的模型，查询阶段也可考虑使用更快的嵌入模型。

失败：质量随时间下降。 最常见的原因：源文档已更改，但向量存储尚未更新。生产环境的 RAG 系统需要重新索引管道，能够检测文档变更并更新嵌入，无需人工干预。实现方法：跟踪文档哈希或最后修改时间戳，对已更改的文档重新嵌入，对于数据陈旧会导致严重质量退化的系统，定期运行全量重新索引。

失败：成本意外膨胀。 最常见的原因：对昂贵的嵌入模型和大型向量索引的高查询量。诊断方法：记录每次查询的嵌入 API 成本，按索引大小和查询量监控向量数据库成本，尽可能使用缓存。当质量差异不足以证明成本合理时，考虑使用更小的嵌入模型（text-embedding-3-small 与 text-embedding-3-large 相比）。在生产规模下，经济性至关重要；一个客户每天对高级模型运行 1 万次查询，每月可能产生巨额账单。

常见问题

FDE 需要从零构建 RAG，还是使用框架？

生产环境的 FDE 工作通常将核心流程的直接 SDK 使用与针对特定模式选择性使用 LangChain 或 LlamaIndex 等框架相结合。纯粹使用框架往往会产生脆弱的生产代码，错误模式难以理解。纯粹从零实现往往会重复造轮子，重新实现框架已经调试好的模式。务实的做法是：在框架能干净利落地解决问题时使用框架（文档加载、常见的分块策略），在需要控制力时使用直接 SDK 访问（检索、提示词构建、生成），并在面向客户的交接材料中记录这一架构决策。

RAG 有意义的最低语料库规模是多少？

不固定，但大致的经验法则：少于 50 份文档（几百个分块）时，传统搜索甚至把所有内容放进提示词上下文的效果可能优于 RAG。50 到 5,000 份文档是典型 FDE RAG 部署的最佳区间。超过 5,000 份文档时，RAG 几乎总是正确的模式。超过 100,000 份文档时，你需要仔细考虑检索质量、基础设施成本和重建索引的流水线，但基本模式仍然适用。

我应该使用 OpenAI 的嵌入模型，还是 Cohere 或 Voyage AI？

在 2026 年，这三家都能生产出生产级质量的嵌入。特定用例适合特定选择：多语言内容适合 Cohere 的多语言模型，代码检索适合 Voyage AI 的代码专用嵌入，通用英语内容三者皆可，其中 OpenAI 是最安全的默认选择。成本各不相同；embedding-3-small 对于高查询量的工作最为经济。对于大多数 FDE 项目，默认使用 OpenAI 的 text-embedding-3-large，只有在有特定理由时才切换。

在没有真实标注数据的情况下，我该如何评估 RAG 的质量？

即使没有精心整理的测试集，也有几种方法可行。第一，生成合成测试集：使用 LLM 从你的文档语料库中生成问答对，然后据此评估 RAG 系统。第二，使用 LLM 作为评判者的模式：让另一个 LLM 评估 RAG 的回答是否基于检索到的上下文。第三，在生产环境中收集用户反馈：对真实回答的点赞/点踩信号可以提供持续的评测数据。合成评测与生产反馈相结合，无需前期投入即可获得精心整理测试集的大部分价值。

RAG 会被长上下文模型取代吗？

在 2026 年不会。长上下文模型（100 万以上 token 的上下文窗口）对某些用例有帮助，但对大多数生产场景并不能取代 RAG。长上下文带来的成本和延迟对许多应用来说仍然过高。检索质量往往胜过把所有内容都放进上下文，因为聚焦的上下文比稀释的上下文能产生更好的 LLM 回答。大多数生产系统采用的都是混合模式：用 RAG 进行筛选和聚焦，同时提供足够的上下文让 LLM 获得所需信息。“长上下文取代 RAG”的论调不断被提出，但在生产实践中一再被证明是错误的。
