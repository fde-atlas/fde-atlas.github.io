Glean 创始 FDE：该职位考察什么，如何申请

原标题：Glean Founding FDE: what the role tests, how to apply

FDE Times · 2026-10-25 · 约 6 分钟读完

摘要

文章分析 Glean 的 Founding FDE（前沿部署工程师）招聘要求，指出该岗位核心是从零到一的产品创造，而非部署现有产品。引用 Thomas Otter 的判断标准：若 FDE 向客户计费，则服务于项目而非产品；Glean 采取相反模式，工程师为战略客户构建的成果会进入 Glean 产品本身。岗位要求 4 年以上技术经验、在需求模糊环境中从零构建生产级软件，并需掌握 AI Agent 开发、评测与规模化部署。工作需与 Forward Deployed PM 组队、对接客户高管，出差占比 25%–50%。文章还给出简历写法建议：按业务问题、模糊性、自建成果、复用情况四步呈现从零到一经历。

要点

  • Glean 明确该岗位核心是从零到一产品创造，成果会进入产品。
  • Otter 的检验标准：向客户计费的 FDE 服务于项目而非产品。
  • 硬性要求：4 年以上经验，在模糊需求下从零构建生产软件。
  • AI 能力重点在 Agent 开发、评测框架与规模化部署，而非仅会调用 API。
  • 岗位需与 Forward Deployed PM 协作、对接客户高管，出差占 25%–50%。

他们为战略客户构建的东西会随 Glean 的产品一起发布，因此仅有出色的实施经验不足以达到招聘门槛。

简要概述

  • Glean 的招聘启事明确指出，创始 FDE 的核心工作是 0 到 1 的产品创造，而且工程师所构建的内容将由 Glean 随其产品一起发布。
  • Thomas Otter 认为，向客户收费的 FDE 服务的是项目而非产品。Glean 选择了相反的模式。
  • 要申请该职位，你需要拿出证据，证明你曾在需求尚不明确的情况下亲自构建过生产级软件；仅仅擅长部署是不够的。

“你的首要任务将是 0 到 1 的产品创造。”这句话来自 Glean 的创始前沿部署工程师招聘启事，它把重点放在创造产品上，而不是部署已有的产品。

启事中后面的一句话更加直白：你构建的东西将由 Glean 随其产品一起发布。这使得担任这一职位的人不仅仅是产品团队的延伸，而是处于路线图的源头。

这一点很重要，因为 FDE 这个头衔目前被使用得非常随意。Thomas Otter 在撰写关于这一职业的文章时警告说，许多 FDE 岗位实际上只是贴上新标签的实施或售前工作。

Glean 的启事展示了一个“真正的” FDE 岗位考察什么，以及为什么安装现有产品的经验——无论做得多好——都无法让你通过筛选。

为什么出色的部署工作还不够

在部署岗位上，产品已经存在。问题是如何让它在客户的环境中运行。而 Glean 的启事分配的是另一项任务：在其最具战略意义的客户那里找出最大的未解决业务问题。在那一刻，根本没有产品可以安装。

因此启事中的核心要求是：你曾在模糊的环境中从零开始构建过生产级软件。其中关键的一个词是“模糊”。

实施人员依据的是已经存在的规格说明。而做 0 到 1 工作的人必须亲自撰写这份规格说明，往往是在几次对话之后——此时客户甚至还没弄清楚自己需要什么。

Otter 描述的正是这类工作。在他看来，FDE 适合那些范围不确定、你在构建前所未有之物的工作。

Otter 的检验标准：项目还是产品？

Otter 还提供了一个快速检验方法：如果 FDE 是向客户收费的，那么他们是为项目工作，而不是为产品工作。这个推理很容易理解：当客户为工程师的时间付费时，双方都有动力交付合同规定的内容，没有人有理由把解决方案变成可复用的东西。

Glean 选择了相反的路径。“你构建的东西将由 Glean 集成到其产品中发布”这句话，既是一份招聘宣传，更是对其运营模式的承诺。Underdog 的 2026 年职业指南也表达了同样的观点：FDE 将客户端的混乱转化为公司可以复用的产品洞察。

把 Glean 的帖子与 Otter 的警告放在一起，你就得到了一张用于检验任何 FDE 职位的对照表：

维度被标为 FDE 的部署岗位Glean 式的创始 FDE
起点一个需要安装和运行的现有产品一个无人解决过的业务问题
产出为单个客户完成的项目随后进入共享产品的软件
谁为时间买单通常是客户，按项目付费公司，因为成果会反哺产品路线图
需要证明的经验配置、集成、支持在需求模糊的情况下从零构建生产级软件
与谁共事支持和销售团队前沿部署 PM、C 级高管

左栏的工作并非低人一等。它是一份不同的工作，需要不同的简历，也通向不同的职业路径。

在客户处的一周

假设战略客户是一家保险公司，其法务团队每周要花数小时在合同中搜寻条款。部署工程师会问要接入哪些存储系统、如何设置权限。这些问题没错，但它们是从产品出发的。

而创始 FDE 会先问业务：哪个决策被卡住了，延误给公司造成多大损失，谁来签字批准。真正的问题可能是将新合同与标准模板进行比对，而搜索只是次要需求。

这位工程师随后构建一个小型 AI Agent，用法务团队的真实案例编写一套评测集，只有当评测分数足够可靠时才将其推向生产环境。

最后一步才是区分这两种角色的关键：重写解决方案，让第二家、第三家客户也能使用。在 Glean 的模式中，这正是为单个客户构建的东西变成整个产品功能的那一刻。

一个小分队、一个坐在 C 级高管旁边的座位，以及无数次航班

Glean 发布在 General Catalyst 招聘板上的帖子称，该职位隶属于一个由前沿部署 PM 组成的小分队，并担任客户 C 级高管的技术伙伴。

这种结构说明了很多。有 PM 在身边意味着工程师不必独自承担所有塑造产品的责任，但他们仍必须以平等的身份争论应该构建什么。

帖子还要求你以创始人的自主性和主人翁意识开展工作。在实践中，没有人会给你派发任务单。你自己选择问题，如果选错了，后果也由你自己承担。

还有切实的个人代价：该职位需要 25%–50% 的时间出差。如果你的家庭情况无法接受这一点，最好在进入面试流程之前就了解清楚，而不是拿到 offer 后才权衡。

对 AI 的要求并非装饰

帖子中的基本门槛是 4 年以上技术岗位经验，并有将软件交付到生产环境的记录。但它还指出了另一个经验领域：Agent 开发、评测框架和大规模部署。

这三者放在一起是有原因的。任何人都能在一周内为客户搭建一个 Agent 演示。真正区分从 0 到 1 的构建者与演示构建者的，是评测：你是否知道一个 Agent 何时足够好、可以上生产环境，并且能否向客户的领导层证明这一点？

所以如果你是从后端或数据工程转过来的，学会调用模型的 API 只是起点。还要学会从真实数据编写评测集，并在流量增长时监控 Agent。这类招聘帖子考察的正是这些。

如何在纸面上证明从 0 到 1

大多数工程师的简历读起来像一份技术栈和系统的清单。对于 Glean 的创始 FDE 这样的职位，这种格式恰恰掩盖了招聘者需要看到的东西。

他们不是在问你是否懂 Kubernetes。他们是在问你，是否曾经从一个未解决的问题出发，最终做出真正有人使用的软件。

用四个节拍来写每个重要项目：业务问题、最初的不确定性、你自己构建了什么，以及它之后在哪里被复用。大多数人会跳过最后一拍，但它恰恰回答了 Otter 的问题：你是在为项目工作，还是在为产品工作？

阅读招聘帖子时，反过来做这个测试。如果一个帖子只谈配置、入职和演示支持，那它就是一个部署岗位，无论头衔怎么写。

如果它谈的是从零构建、谈路线图、谈与客户领导层合作，那你看到的是一个产品岗位，你需要准备好自己的从 0 到 1 的故事。

头衔中的“创始”一词听起来像一种荣誉。仔细阅读 Glean 的帖子，你会发现它其实是一道面试题：你是否曾在没人能告诉你它应该是什么样子的情况下，创造出原本不存在的东西？
