LLM 评测面试：“你怎么知道它有效？”

原标题：LLM evaluation interview: ‘how do you know it works?’

FDE Interview Prep · 2026-09-25 · 约 13 分钟读完

摘要

这篇 FDE 面试备赛文章讲如何回答“你怎么知道系统有效”。作者提出五要素框架：与客户目标匹配的指标、真实测试数据、基线对比、具体结果（含失败案例）、上线后监控，并用支持邮件路由和临床摘要两个例子对比了弱回答与强回答。文章还涵盖无标注数据时构建评测集、LLM 评审的可信度、模型版本固定、按代价拆分错误等追问，并引用 OpenAI、Snowflake、Scale AI 等职位说明说明评测确为 FDE 岗位要求。

要点

  • 完整回答需五要素：指标、数据、基线、结果、监控。
  • 结果要给出计数与错误分类，而非单一准确率。
  • 文本输出应转为逐项通过/不通过的检查规则。
  • 无标注时从真实输入采样，由客户专家标注并冻结测试集。
  • OpenAI、Snowflake、Scale AI 等职位明确要求评测能力。

你做出了演示。它能干净利落地回答示例问题，面试官点点头，然后问道：“你怎么知道它是有效的？”最省事的回答是把演示再描述一遍。这篇文章教你如何用证据来回答。这只是众多环节中的一环；FDE 面试指南涵盖了其余内容。

简而言之：一个完整的回答要说出五件事。与客户关心的内容相匹配的指标、你用来测量的数据、你用来对比的基线、结果，以及上线后你要监控什么。然后，不用等对方问，你就主动说出系统仍然会在哪些地方失败。“我试了一堆例子，看起来都不错”不是回答，只是对演示的描述。

完整回答的五个部分

这份清单是我们自己总结的，不是任何雇主公布的评分标准。它之所以有效，是因为每个部分都回应了细心听者心中的一个疑虑。

部分它回应的疑虑
指标“你衡量的是客户真正在乎的东西吗？”
数据“测试集是真实的吗？你是否在它上面调过参？”
基线“比什么更好？”
结果“好到什么程度？在哪些地方会失败？”
监控“下个月系统出问题时，你怎么会知道？”

指标。 从系统所支持的决策以及代价最大的错误出发。对于一个客服路由系统，一封分错队列的工单可能会搁置一天。对于一份医疗摘要，漏掉一条过敏信息比一个笨拙的句子代价大得多。选择能统计出昂贵错误的指标，并说明是谁认可了这个指标。关于利益相关者与成功指标的课程讲解了如何找到赞助方已经信任的那个数字。

数据。 说明测试样例来自哪里、有多少个、正确答案是谁写的，以及你没有在它们上面调过提示词。真实的输入胜过编造的输入。

基线。 单独一个数字毫无意义。把它与客户目前的做法（一个人、一条关键词规则、旧系统）或你自己系统的最简版本进行对比。

结果。 给出具体数量而不只是比率，并按类别细分。“38 封取消邮件中漏了 3 封”比一个百分比更有说服力，因为听者能看出这个类别有多小。

监控。 说明你在生产环境中关注什么、什么情况会触发警报，以及警报触发后会发生什么。

一个糟糕的回答和一个出色的回答，逐字对比

场景设定：在一次实战构建中，你做了一个 LLM 路由器，读取一家订阅制公司的客服邮件，并把每封邮件分派到一个队列：退款、取消、账单或其他。面试官问你怎么知道它是有效的。

糟糕的回答。

“我在一堆邮件上测试过，几乎全答对了。我还用 GPT 给回复打分，提示词相当稳健。在生产环境中我会加上日志和监控。”

它的问题在于：

  • “一堆”和“几乎全”都不是数字。听者无法分辨到底是五封邮件还是五百封。
  • 没有基线，所以“几乎全部正确”可能还不如客户现有的关键词规则。
  • 提到了模型评分器，但没有验证。谁来验证评分器？
  • “日志和监控”只是列了一个工具，而不是一个信号或一个动作。
  • 完全没说哪里会失败。这读起来要么是没去看，要么是在隐瞒。

这是强回答。（数字是为示例虚构的。）

“决策是每封邮件去往哪个队列，而代价高昂的错误是一封取消请求被分到账单队列，因为客户会被再次扣费。所以我按队列分别测量准确率，并单独测量取消队列的召回率：有多少真实的取消邮件最终被分到了那里。“数据是：上个月收件箱里的 200 封真实邮件，我在写提示词时一封都没看过。支持团队负责人给它们打了标签，在评分之前，我和她先就边界情况的处理规则达成了一致。“基线是他们现有的关键词规则。在同样的 200 封邮件上，规则正确分对了 131 封，而 LLM 路由器分对了 172 封。在取消请求上，规则漏掉了 38 封中的 14 封；路由器漏掉了 3 封。“失败在哪里：在分错的 28 封中，有 11 封同时提出了两个请求，比如既要求退款又要求取消。目前我把这类邮件转给人工处理。“上线之后，我会记录每一次路由决策及邮件 ID，让支持团队把分错的邮件重新入队，并把每次重新入队当作新的带标签样本。如果取消邮件的重新入队率超过我们约定的阈值，路由器就回退到关键词规则，同时我去查明原因。”

注意这个顺序：决策、指标、数据、基线、结果、失败、监控。它很简短、很具体，每句话都消除一个疑虑。如果面试官想听术语，全都在里面：取消那个数字是单一类别的召回率，而“它被分到了哪个错误队列”的配对就是混淆矩阵的非对角线单元格。对着这个确切提示词的问题页面练习说出你自己的版本，那里演示了一位客户提出这个问题的完整过程。

当输出是文本而不是标签时

路由器每封邮件只有一个正确答案。而摘要器、助手或回复起草器没有，所以“准确率”无从统计。解决办法是把“好”转化为逐项通过或不通过的检查。

  • 把评分标准写成通过/不通过的检查项。 以临床笔记摘要为例：“提到笔记中的每一种过敏史”、“引用的段落确实存在”、“不给出政策范围之外的建议”。每一项检查都是“是”或“否”，而不是十分制的打分。
  • 先让人对一小部分样本打分。 由领域专家对照每项检查给几十个输出打分。这就是这些检查项的真实标准（ground truth）。
  • 为每项检查添加一个 LLM 评审，且只在它与专家一致之后。 每次评审调用只问一个狭窄的问题。如果它在某项检查上与专家分歧过于频繁，该项检查就继续由人工打分。
  • 按检查项报告失败情况。 “120 份摘要中有 4 份漏掉了过敏史”能让客户知道该担心什么。一个平均分做不到这一点。

一个适合总结者的口语化版本：

“我和护士长一起把‘一份好的摘要’变成了四项通过/不通过的检查，第一条是‘病历中出现的每一种过敏都必须出现在摘要里’。她给 60 份摘要打了分，在放手让它评其余摘要之前，每项检查的 LLM 评审与她的判断几乎完全一致。在 400 份摘要中，过敏检查失败了 6 次，全部是因为过敏信息在扫描附件里，所以这类病历现在会转给人工处理。”

当客户没有标注数据时如何构建评测集

对一个出色回答的常见追问往往是“客户没有标注数据，那你的正确答案是从哪里来的？”下面是一套你可以在一分钟内讲完的流程。

从零构建评测集

  • 从日志、工单或文档中提取真实输入。凭空编造的示例会漏掉那些混乱棘手的情况。
  • 按真实分布抽样，然后有意加入困难案例：模糊的请求、缺失的数据、系统应当拒绝回答的问题。
  • 让客户方的领域专家来撰写正确答案，而不是你自己写。
  • 让两个人对一部分重叠样本进行标注。在意见不一致的地方，由一位指定的人做出裁决，裁决理由则成为评分指南。
  • 冻结一个你从不据此调优的测试集。另留一个单独的切片用于尝试提示词改动。
  • 从生产环境中持续扩充数据集：每一个被标记或被纠正的输出都加入其中。

标注不一致这一步比看起来更重要。如果两位专家只在部分答案上达成一致，就把他们的一致率视为大致的上限。远高于这个上限的分数通常意味着系统学到了某位标注者的习惯，而不是它更常答对。要把这一点明确说出来；这表明你清楚这个数字能说明什么、不能说明什么。关于为 LLM 评测构建黄金数据集的文章对抽样和标注有更深入的讲解。

一个你能解释清楚的简短评分脚本

你可能会被要求亲自编写评分代码。一位候选人在 2026 年 4 月报告称，Snorkel AI 的招聘人员描述了一场 FDE 技术筛选，基于一份客户简报、一个标准答案 CSV 和模型输出，候选人需要编写评测代码并找出错误模式；该候选人后来表示面试被取消了。来源 8Got a Snorkel AI Forward Deployed Engineer interview next week, anyone been through this? Format is unusual (post by u/itskabeer)发布者Reddit r/csMajors来源类型Reddit 上的候选人报告来源 9Got a Snorkel AI Forward Deployed Engineer interview next week, anyone been through this? Format is unusual (comment by u/itskabeer)发布者Reddit r/csMajors来源类型Reddit 上的候选人报告

你不需要为此使用任何框架。下面是完整的思路，基线与系统并列展示：

from collections import Counter

rows = [  # (gold, baseline, system)
    ("refund", "refund", "refund"),
    ("cancel", "refund", "cancel"),
    ("billing", "billing", "billing"),
    ("cancel", "other", "cancel"),
    ("other", "refund", "billing"),
    # None: output failed to parse
    ("refund", "refund", None),
]

def score(col):
    right = sum(r[0] == r[col] for r in rows)
    errors = Counter(
        (r[0], r[col])
        for r in rows
        if r[0] != r[col]
    )
    return right / len(rows), errors

for name, col in [("baseline", 1), ("system", 2)]:
    acc, errors = score(col)
    print(f"{name}: {acc:.2f}")
    for (gold, got), n in errors.items():
        print(f"  {gold} -> {got}: {n}")

运行后它会打印：

baseline: 0.50
  cancel -> refund: 1
  cancel -> other: 1
  other -> refund: 1
system: 0.67
  other -> billing: 1
  refund -> None: 1

编写代码时你可以这样说：

  • 分母是每一行。 最后一行解析失败，但它仍然计入，算作一个错误答案。如果把它剔除，系统得分会从 0.67 升到 0.80——这正是那种在困难输入上放弃的模型反而显得更好的原因。
  • 错误对才是有用的部分。 它们是混淆矩阵中非对角线的单元格。cancel -> refund 告诉你该修什么。单一的准确率数字做不到这一点。
  • 六行数据证明不了什么。 要主动说出来。在真实数据集上，你还应报告每个队列有多少示例，因为少量行上的比率会随单个示例而大幅波动。

要练习包含错误分类和标准答案文件的完整版本，可以试试评分脚本题。

上线后你要监控什么

离线分数描述的是你测量当天的状态。生产环境会漂移：用户提出新问题，文档发生变化，模型供应商发布新版本。要说出信号和应对动作，而不是工具。

  • 输入构成。 各类别或主题的占比。突然出现新主题意味着你的测试集已不再匹配现实。
  • 结果信号。 重新排队、对草拟回复的编辑、用户标记、转人工。这些都是免费的标注。
  • 抽样审查。 每周固定数量的输出，由客户方的人阅读，并使用与测试集相同的评分指南打分。
  • 回归运行。 冻结的测试集在每次提示词、模型或检索变更之前运行，分数下降则阻止该变更。
  • 成本与延迟。 即使质量保持不变，更慢或更昂贵的回答也可能破坏商业可行性。

每个信号都需要一个负责人和一个动作：“如果取消业务的错误路由超过约定水平，就回退到规则系统并通知我。”关于为支持型 Agent 设计评测框架的问题是这份清单在设计轮的版本。

追问：LLM 评审、漂移以及错误答案的代价

一个出色的首轮回答会引来更难的追问。为每个追问准备好一句话的回答。

“你用 LLM 来打分。你怎么信任它？” 手动对一份留出样本打分，然后将评审的判定与人工标注进行比较。如果评审与人类不一致的频率高于系统犯下你所关心的错误的频率，它就无法测量那个错误，该类别应改由人工打分。注意那些偏好更长答案或第一个选项的评审（Zheng 等人的 MT-Bench 评审论文第 3.3 节同时指出了这两点）。关于 LLM-as-a-judge 失效模式的文章列出了其余问题。

“供应商更新模型时怎么办？” 固定一个具体的模型版本，绝不使用会变动的别名（Anthropic 关于模型 ID 的页面说明了哪些 ID 是固定快照、哪些是别名）。切换前重跑冻结测试集，除了总体数字外还要比较错误对，并跟踪供应商的退役日期，以免被迫切换时未经测试。

“如果错误答案代价很高怎么办？” 那么准确率就不是正确的单一指标。按代价拆分错误，为高代价错误设定更严格的标准，并设计系统在不确定时转人工。向非技术买家解释这种权衡本身就是一项技能；关于向非技术领导者解释 AI 局限的课程涵盖了相关措辞，关于为什么助手不可能每次都正确的问题也是如此。

“这是一个 RAG 系统。你测量什么？” 分别测量检索和生成：正确的段落是否被召回，答案是否忠实于它？否则你无法判断该修复哪一半。参见RAG 系统设计面试演练以及关于检查引用是否真实的问题。

大声练习

阅读这五个部分很容易。但在追问下按顺序、带数字地说出来就不容易了。选一个你做过的项目，把五个部分写在一张卡片上，并在两分钟内说出答案。当你想要一个会反驳你的客户时，运行免费 AI 练习题，看看你在压力下能否拿出证据。

从针对这个问题的提问页面开始：写下你的答案，计时两分钟，然后与参考答案对比。下面其余的 AI 轮次问题也是以同样的方式构建的。

人们常问的问题

当被问到我如何知道我的 AI 系统有效时，我该说什么？

说出五件事：与客户目标匹配的指标、你测量它所用的数据、你对比的基线、结果，以及上线后你监控什么。然后说明系统还有哪些不足，以及你会如何处理。

FDE 职位涉及评测工作吗？

有几个职位描述提到了这一点。Snowflake 的应用 AI FDE 职位要求应聘者将客户目标转化为质量指标、评测框架和黄金数据集，而 Scale AI 的 Frontier Agents FDE 职位列出了包含黄金数据集、回归测试套件和 LLM 作为评判者的评测框架。来源 2Senior/Staff Forward Deployed Engineer, Applied AI @ Snowflake发布方Snowflake (Ashby job board)来源类型公司职位发布来源 3Frontier Agents Engineer (Forward Deployed Engineering)发布方Scale AI (Greenhouse)来源类型公司职位发布
