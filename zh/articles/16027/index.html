Sierra：AI 时代前沿部署工程与 Agent 工程的演进

原标题：Sierra: Evolution of Forward Deployed Engineering and Agent Engineering in the AI Era

ZenML LLMOps Database · 2026 · 约 9 分钟读完

摘要

本文整理 Sierra 的 Agent Engineering 负责人 Natalie Mier 的分享，梳理前沿部署工程师自 2008 年 Palantir 起的演变：从 DevOps、数据集成、定制方案到平台赋能。作者认为随着 LLM 与编码 Agent 让代码生产变得廉价，产品工程与客户-facing 角色的界限正在模糊，工程角色趋于融合。Sierra 据此提出 Agent Engineering，让工程师负责 AI Agent 的生产部署与结果交付，并主张 AI Agent 使按结果计费（如完成销售、解决客户问题）成为可能，认为 AI 市场定价将普遍转向结果导向。文章同时指出部分论断偏乐观，结果归因模糊的场景可能限制该模式适用性。

要点

  • Palantir 时代前沿部署工程师经历 DevOps、数据集成、定制方案、平台赋能四个阶段。
  • 编码 Agent 降低代码成本，瓶颈从实现速度转向理解客户需求与保障结果。
  • Sierra 的 Agent Engineering 要求工程师负责 Agent 全生命周期与可衡量业务结果。
  • AI Agent 兼具高归因与高自主性，使按结果计费成为可行模式。
  • 作者认为所有工程角色正变得面向客户，角色界限趋于融合。

摘要

Sierra 的 Agent 工程负责人追溯了前沿部署工程从 2008 年 Palantir 以 DevOps 为核心的起源到现代 AI 时代的演变，探讨了这一角色如何扩展到涵盖数据集成、定制化解决方案和赋能。该演讲认为，随着通过大语言模型和编程 Agent 使代码生产变得廉价，前沿部署工程师现在可以构建端到端的解决方案，而产品工程与面向客户角色之间的界限也日益模糊。Sierra 将这些洞察应用于以基于结果的定价模式为核心的 Agent 工程，其中 AI Agent 自主解决客户咨询，前沿部署工程师负责将 Agent 部署到生产环境，并确保可衡量的结果，例如完成销售或解决客户问题。

概述

这份由 Sierra 的 Agent 工程负责人 Natalie Mier 呈现的案例研究，全面探讨了前沿部署工程这一角色在 AI 时代的演变，尤其关注大语言模型和编程 Agent 如何改变产品工程、解决方案工程与面向客户技术角色之间的传统边界。演讲追溯了前沿部署工程从其在 Palantir 的起源到 Sierra 当前 Agent 工程方法的历史发展，演讲者将后者定位为 AI 工程的一个子学科，专注于客户责任与结果交付。

演讲者提出了一个颇具争议性的论点：“前沿部署工程并不存在”作为一个连贯的单一学科，它实际上代表着一组不断扩展的能力，随着通过大语言模型使代码生产变得廉价，这些能力正变得对所有工程角色都至关重要。Sierra 的 Agent 工程方法源于认识到传统的前沿部署工程模式需要为 AI Agent 时代而演进——在这个时代，结果可以直接被衡量和定价。

历史背景与演变

该演讲通过追溯 Palantir 不同时期的前沿部署工程，提供了宝贵的历史背景，每个时期都在保留原有职责的基础上增加新的职责。2008 年，该角色主要专注于平台稳定性和 DevOps，工程师会被实际派驻到客户现场维护本地化部署。这通常涉及排查运行时问题，并全天候响应基础设施故障。演讲者自己在 Palantir 的入职项目就是在一个 EC2 实例上部署软件，这体现了早期前沿部署工作以 DevOps 为主的特性。

到 2012 年，随着 Palantir 平台趋于稳定，前沿部署工程师开始承担数据集成职责。演讲者用“没有电影的电影院”这一类比来解释为什么数据集成软件在没有集成数据的情况下毫无用处。前沿部署工程师开始负责整合来自不同来源的数据，并创建本体（ontology）来对数据进行合理分类。这要求他们对客户环境和数据格局有深入的理解。

2016 年前后引入了定制解决方案构建，通常以 Slate 仪表板的形式呈现。Slate 是 Palantir 的拖拽式构建工具，类似于 Retool，可以将组件映射到数据源。前沿部署工程师成为最能将数据变得有用的人，因为他们既懂技术数据结构，又了解客户背景。然而，一个关键的经验教训是：没有对数据源回写能力的仪表板往往会随时间推移而衰减，只能提供有限的价值。

到 2020 年，临近 IPO，Palantir 转向平台赋能，希望让客户能够自己完成更多工作，而不是需要将工程师派往全球各地。这体现在与空客（Airbus）合作的 Skywise 项目中，数千名空客工程师得以使用 Foundry 平台完成此前由前沿部署工程师完成的工作。最近，Palantir 推出了 AIP，利用大语言模型进行类似的赋能工作，不过这发生在演讲者离职之后。

LLMOps 的转型

对 LLMOps 从业者而言，关键洞察在于：当通过编码 Agent 和 LLM 驱动的开发工具使代码变得易于生产时，前沿部署工程师的角色会发生根本性转变。前沿部署工程师不再受实现速度的制约，现在可以借助编码 Agent 快速进行原型设计并构建端到端解决方案。这将瓶颈从实现转移到了理解客户需求和确保成果上。

Sierra 的 Agent 工程方法正是源于这一认识。2024 年 7 月，演讲者发表了一篇文章，提出 Agent 工程是 AI 工程的一个子学科，它既保留了前沿部署工程所特有的对客户负责的特质，又专注于 Agent 领域。其愿景是让 Agent 工程师负责在生产环境中构建、部署 AI Agent 并确保其成果。

不过，演讲者指出，在随后的两年里，他们的思考已经有所演变。他们不再认为 Agent 工程是一门独立的学科，而是看到一种融合正在发生：所有工程角色都变得更加面向客户和注重结果。产品工程师越来越多地直接面对客户，而前沿部署工程师则更深入地参与产品开发。编码 Agent 的普及加速了这种融合，使任何角色的工程师都能快速构建解决方案。

基于结果的定价与 LLMOps

Sierra 的 LLMOps 方法的一个关键方面，是转向由 AI Agent 实现的基于结果的定价模式。演讲者提出了一个包含两个维度的框架：结果能在多大程度上归因于产品，以及实现这些结果的自主性/能动性。传统的按席位定价存在于归因度低的场景中。按使用量定价，比如企业向 OpenAI 或 Anthropic 支付的基础模型访问费用，能更好地追踪使用情况，但仍然无法直接衡量结果。

在客户体验场景中，AI Agent 使真正的基于结果的定价成为可能，因为归因度和自主性都很高。以 Sierra 的用例为例，结果可能包括完成的销售或成功解决的客户咨询。Agent 拥有采取行动以实现这些结果的自主权，而结果也可以直接归因于 Agent 的表现。演讲者认为，AI 市场中的大多数定价都将转向基于结果的模式。

这种定价模式对 LLMOps 有着深远的影响。当客户基于结果而非席位或 API 调用来付费时，工程团队必须确保在生产环境中可靠地交付这些结果。这就需要前沿部署工程师或 Agent 工程师，他们能够将 Agent 部署到生产环境中，根据结果指标监控其表现，并在结果未达成时快速迭代。问责的对象不再仅仅是正常运行时间或功能交付，而是可衡量的业务结果。

Agent 工程的实践

虽然这次演讲对 Sierra 的 Agent 工程实践的具体技术实现细节着墨不多，但仍有几个关键原则浮现出来。Sierra 的 Agent 工程师负责生产环境中 Agent 的完整生命周期：构建、部署，并确保它们交付可衡量的结果。这需要将传统前沿部署工程的能力（如 DevOps 和对客户的理解）与围绕 Agent 设计和 LLM 编排的新型 AI 专项技能相结合。

演讲者提到 Sierra 从 2024 年到 2026 年一直在使用这种模式，这表明他们在 Agent 工程这一学科上积累了大约两年的生产实践经验。在此期间，他们观察到出现了更加专业化的角色，例如“harness engineering（工具链工程）”，他们将其定位为 Agent 工程的一个子集，这表明尽管工程角色总体上趋于融合，但 Agent 领域内部的专业化程度却在不断提高。

这一角色需要多样化的技能组合，演讲者幽默地形容为需要“八年资深工程师经验、六年直接销售经验和四年解决方案架构师经验”，外加教学经验。虽然这种说法有夸张成分，但它反映了 Agent 工程真正的多学科性质：深厚的技术能力、面向客户的能力、解决方案架构能力以及赋能能力。

批判性评估

这场演讲就 LLM 驱动的工具如何变革工程角色提供了宝贵的见解，但有几个方面值得平衡地看待。“前沿部署工程并不存在”这一说法是刻意挑衅性的，而且在某种程度上与 Sierra 积极招聘这些岗位的做法相矛盾。更准确地说，这场演讲表明前沿部署工程已经变得如此多面化，以至于难以精确定义，这与它不存在是两回事。

由 AI Agent 实现的基于结果的定价这一愿景很有吸引力，但可能更适用于某些用例而非其他用例。解决支持咨询或完成销售交易的客户体验 Agent 是结果衡量的天然契合场景。然而，许多企业级 AI 应用的结果可能更难衡量或难以直接归因，这可能会限制该模式的适用性。演讲并未深入探讨如何处理结果归因模糊的场景。

关于编码 Agent 使代码生产变得廉价、并使前沿部署工程师能够快速构建端到端解决方案的说法是乐观的，并且与厂商围绕 AI 辅助开发的叙事相一致。虽然编码 Agent 确实能加速开发，但生产级代码仍然需要大量的工程判断、测试、安全考量和架构思维，而这些是编码 Agent 无法完全自动化的。演讲如果能更细致地讨论编码 Agent 在生产环境中的能力与局限，将会更有价值。

对 Palantir 前沿部署工程演进的历史分析很有价值，且基于公开信息来看也基本准确。然而，Palantir 的模式需要在全球范围内向客户现场派遣工程师，这意味着大量的人力资本投入，对大多数公司而言在经济上未必可行。Sierra 的做法似乎利用远程办公和 Agent 自动化使这一模式更具可扩展性，但文中并未深入探讨其经济性。

“所有工程工作都在变成前沿部署工程”这一趋同论点发人深省，但或许有些言过其实。虽然产品工程师确实能从理解客户中受益，部署工程师也能从产品思维中受益，但不同的专业分工和关注领域很可能仍有其价值。并非每位工程师都需要在 DevOps、数据集成、解决方案构建、赋能和 Agent 开发等各方面同样出色。

LLMOps 的启示

对于 LLMOps 从业者而言，Sierra 的经验带来了几点关键启示。首先，随着 LLM 和编码 Agent 加快开发速度，瓶颈从实现转向了理解客户需求并确保生产环境中的实际成果。这表明 LLMOps 实践应强调成果度量、生产监控和快速迭代周期，而不仅仅是部署自动化。

其次，基于成果的定价模式为投资于 AI 系统的生产可靠性和成果度量创造了强有力的激励。LLMOps 团队需要能够追踪业务成果的监测手段，而不仅仅是延迟和正常运行时间等技术指标，还包括任务完成率、客户满意度或转化率等业务成果。这需要工程、产品和业务团队之间的紧密协作。

第三，前沿部署工程师或 Agent 工程师的角色在 LLMOps 生命周期中变得至关重要。这些人在通用平台能力与特定客户成果之间架起桥梁，定制 Agent 行为、集成客户数据，并根据生产表现进行迭代。采用 AI Agent 的组织很可能需要设立专门角色，专注于这一部署与成果交付职能。

第四，赋能与平台化的方式有助于规模化部署专长。正如 Palantir 让 Airbus 的工程师能够自己完成前沿部署工作一样，组织可以构建平台和工具，使更广泛的团队能够在生产环境中部署和管理 Agent。这表明 LLMOps 平台应在技术先进性之外，优先考虑易用的界面和自助服务能力。

最后，产品工程与面向客户角色之间界限的模糊表明，LLMOps 技能可能需要更广泛地分布于整个工程组织，而不是集中在专门的团队中。从事 LLM 产品开发的工程师可能需要掌握部署、监控、客户理解和效果衡量等技能，而这些技能传统上分属于不同的角色。

结论

Sierra 对 Agent 工程以及前沿部署工程演进的视角，为我们理解 LLM 如何不仅改变工程团队构建的东西，还改变团队的组织方式和价值交付方式，提供了宝贵的参考。自主 AI Agent 带来的从按席位收费到按效果收费的转变，创造了新的问责模式，并波及组织结构和 LLMOps 实践。虽然演示中的某些说法可能略显乐观或带有宣传色彩，但围绕效果导向、角色融合以及部署专业知识重要性的核心洞见，对于构建生产级 LLM 系统的组织而言很有价值。此外，Palantir 演进历程的历史背景也提供了有益的视角，展示了面向客户的技术角色如何随平台日益复杂而不断调整，为我们预见类似角色在 AI 时代的演进提供了参考。
