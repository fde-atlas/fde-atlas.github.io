FDE 分解面试：给定一个数据集，读取其中的列

原标题：FDE decomposition interview with a dataset: read the columns

FDE Interview Prep · 2026-09-25 · 约 13 分钟读完

摘要

这篇文章针对 FDE 面试中的数据集分解题，提出一套以列为先的方法：先弄清表的粒度、键和时间戳，再确定用户及其决策，提出一个功能和一个指标，最后写出验证想法的第一条查询。作者引用 Blind 上 Palantir 校招候选人的报告（如 8000 条伦敦出租车数据题），并用虚构的健身应用事件表完整演示，标注了重复事件、跨平台事件名不一致、时区缺失、未关闭窗口、样本过薄等常见陷阱。

要点

  • 分解面试可能附带数据集，Palantir 候选人在 Blind 上有相关报告。
  • 先读表：粒度、键、时间戳，再提想法。
  • 确定一个用户和其重复出现的决策，再定功能与指标。
  • 第一条查询是验证想法的最低成本测试，需边写边叙述。
  • 常见陷阱：重复行、平台事件名差异、时区混乱、窗口未关闭。

面试官共享屏幕，上面有一张表格，说“这里有一些数据，用它做点有用的东西”，然后就沉默了。你面对一块空白白板、一份从未见过的列清单，还有想在一分钟内就推销一个 AI 教练的冲动。这篇文章是我们的拆解面试指南的窄化版本：当模糊的问题以行和列的形式出现时，该怎么做。

简短的回答：从列出发，而不是从一个想法出发。大声读出表格的粒度、键和时间戳。然后说出一个用户以及数据能帮助他们做出的决策，提出一个功能和一个指标，并写出第一个能证明这个想法值得构建的查询。本文其余部分将在一个健身应用的事件表上实践这个方法，运行查询并标出陷阱。

下面的方法是我们自己的，它在 AI 产品公司同样适用。

如果表格是模型调用日志

粒度： 每次请求一行，还是每次重试一行？键：

request_id

针对

conversation_id

，并且

prompt_version

是否可靠？

Clocks:

延迟是在客户端还是服务端测量的？

The open window:

点赞可能在响应之后几分钟甚至几天才到达，所以最近的请求看起来像是未评分的。在评分窗口关闭之前，先把它们搁置。

先读表格：粒度、键和时间戳

在形成观点之前，先花两三分钟阅读。按顺序回答三个问题。

粒度：一行代表什么？ 用一句话说出来：“每条事件一行、每场会话一行、每个用户一行。”粒度决定了你要做的每一次计数。如果你以为一行是一次锻炼，实际上却是一条事件，那么你给出的每个数字都会被夸大。

键：什么与什么关联？ 说出标识一行的列，以及指向其他对象的列：用户、会话、设备、订单。要问哪些键是可靠的。一个本不该重复却重复出现的键，就是你发现的第一个数据质量问题。

时间戳：什么时候，用的是谁的时钟？ 对每个时间列要问两件事。它处于哪个时区？它记录的是事情发生的时间，还是服务器接收的时间？一部在飞行后同步的手机，会在今天发送昨天的锻炼数据。

你可以使用的话术：

“在挑选功能之前，我想先读一下这张表。我认为粒度是每条事件一行。event_id 是唯一的吗，还是客户端可能重复发送同一条事件？另外，这些时间戳来自设备时钟还是服务器？”

找到用户和决策

表里没有现成的用户，你需要自己去找。看看这些列，然后问：如果有人能以良好的汇总方式看到这些数据，谁会因此改变自己的做法？

至少说出两个候选用户，每人一句话，然后选定一个。所选的应该是一个有反复出现的决策的人，而不是一个模糊的目标。“下个季度决定要重做哪项锻炼的内容负责人”胜过“提升参与度”，因为一个决策会给你一个指标和一个停止点。

在一个关于 Palantir 数据方向开放性环节的 Blind 帖子中，一位未透露自己职位的评论者在 2025 年 1 月写道，该环节从一个随机功能开始，然后依次讨论 P0 功能、技术决策、数据模型和数据库、要分析什么、要跟踪哪些 KPI 以及要向高管展示什么。来源 5Palantir FDSE 面试发布者Blind（teamblind.com）来源类型Blind 上的候选人报告来源 6Palantir FDSE 拆解/系统设计面试发布者Blind（teamblind.com）来源类型Blind 上的候选人报告 尽早选定用户和决策，正是让整条链路始终指向同一目标的关键。

提出一个功能和一个指标

现在用一句话说出这个功能，并说明它不是什么。然后把指标定义得足够精确，让两个人能算出同一个数字：

  • 起作用的事件。 哪个 event_type 代表成功？
  • 分母。 以什么为分母？是启动的会话数、活跃会员数，还是下单数？
  • 时间窗口。 是在会话内、48 小时内，还是自然周内？
  • 你要排除什么。 测试账号、窗口尚未结束的会话、你无法信任的数据行。

Palantir 关于开放式问题的页面指出，要阐明各种备选方案及其权衡，得出一个具体的方法，先交付一个可运行的方案，再进行扩展。来源 3Palantir 招聘 | 应对开放式问题发布方Palantir Technologies来源类型公司招聘页面一个功能加一个指标就是可运行的方案。关于如何选择指标及其护栏指标，请阅读我们关于案例面试中成功指标的帖子。

把第一条查询大声说出来

第一条查询不是功能本身。它是检验这个功能是否值得构建的最廉价方式。如果指标在你想要采取行动的对象上几乎没有变化，那就没有决策可做，你应该直说，并选择另一个功能。

动手之前先问：“您希望我用 SQL 来写，还是先用伪代码勾勒一下？”然后边写边讲解：每个 CTE 构建了什么、其中一行代表什么、你排除了什么以及为什么。如果涉及窗口函数，我们关于 FDE 面试中 SQL 窗口函数的帖子涵盖了常见模式及如何讲解它们。

说出每张中间表的粒度

每次写 CTE 时，都要说出其中一行代表什么：“每个会话一行”。这能在数据发散（fan-out）错误发生之前就发现它们，也向面试官展示你在自查自己的工作。

实战示例：健身应用事件数据

下面是一个健身应用的虚构表格。题目是：“这是我们一周的事件数据。构建一些有用的东西。”

列内容
event_id应用为每个事件分配的 ID
session_id一次锻炼；app_open 时为空
user_id会员
event_typeapp_open、workout_started 等
workout_type跑步、力量训练、骑行、瑜伽
platformios、android 或 watch
occurred_at设备时钟时间
received_at服务器时间，UTC
duration_s秒数，记录在结束事件上

完整的虚构样本有 39 行；这里是其中六行：

event  event_type         platform
e02    workout_started    ios
e03    workout_completed  ios
e03    workout_completed  ios
e06    workout_started    android
e13    workout_started    watch
e14    workout_saved      watch

第 1 步：粒度和键。 “每个事件一行。但是

e03

出现了两次：相同的

occurred_at

(

07:34:02

)，带有

received_at
07:34:03

和

07:36:40

。所以客户端很可能重试了发送。我会询问它是如何重试的，并检查重试的频率：”

SELECT
  COUNT(*) AS n_rows,
  COUNT(DISTINCT event_id)
    AS n_events
FROM events;

在样本上它返回 39 行、38 个不同事件。所以“每个事件一行”不成立，任何按行计数的东西都必须先去重。

session_id

是将开始事件与其结束事件关联起来的键，这正是这张表能够支持完成率指标的原因。

第 2 步：按平台划分的事件词汇表。 “在信任

event_type

之前，我想看看它在每个平台上取到的所有值。”

SELECT platform, event_type,
  COUNT(*) AS n
FROM events
GROUP BY platform, event_type
ORDER BY platform, event_type;

手表从不发送

workout_completed

。它发送的是

workout_saved

。把它说出来并提问：“手表上的

workout_saved

是否与

workout_completed

在电话上吗？”假设面试官回答是。

第 3 步：时间戳。 “

received_at

是 UTC。是否每一行

occurred_at

都带有时区信息，要么是

Z

，要么是像

+01:00

?”

SELECT platform,
  COUNT(*) AS no_zone
FROM events
WHERE occurred_at NOT LIKE '%Z'
GROUP BY platform;

有两行 Android 数据没有时区，而且它们的

occurred_at

比

received_at

快一个小时：设备本地时间。在真实的数据表里我也会允许偏移量；这个样例中没有。任何按一天中的小时或按日期的统计都必须先做转换，否则这些行会落进错误的分组。

第 4 步：用户和决策。 “我看到这张表有三类用户。一位会员在决定今天要不要锻炼，这指向一个提醒功能。一位支持工程师在问哪个平台会丢失事件。还有内容负责人在决定先重做哪种锻炼类型。我选择内容负责人：这个决策每个季度都会出现，而且

session_id

让我能直接衡量它。”会员提醒是我们在

fitness-app feature question

中做过的功能，所以下一步可以练习那个。

第 5 步：一个功能，一个指标。 “这个功能是一张按锻炼类型统计的每周完成率表，并支持按平台下钻，供内容负责人在规划前查看。它不是推荐引擎。指标是完成率：在有

workout_started

的会话中，有

workout_completed

或

workout_saved

.”

第 6 步：第一个查询。

WITH s AS (
  SELECT session_id,
    MAX(workout_type)
      AS workout_type,
    MAX(user_id) AS user_id,
    MAX(CASE WHEN event_type =
      'workout_started'
      THEN 1 ELSE 0 END)
      AS started,
    MAX(CASE WHEN event_type IN (
      'workout_completed',
      'workout_saved')
      THEN 1 ELSE 0 END)
      AS finished
  FROM events
  WHERE session_id IS NOT NULL
  GROUP BY session_id
)
SELECT workout_type,
  COUNT(*) AS sessions,
  COUNT(DISTINCT user_id)
    AS members,
  SUM(finished) AS finished,
  ROUND(1.0 * SUM(finished)
    / COUNT(*), 2) AS rate
FROM s
WHERE started = 1
GROUP BY workout_type
ORDER BY rate;

边写边讲：“这个 CTE 是每个会话一行，所以重复的

e03

只计一次。我只保留有开始时间的会话，因为指标的分母是已开始的会话。

s21

有完成但没有开始：这是我会标记的丢失事件，而不是我会计入的锻炼。没有这个过滤，骑行会显示为 0.8。”在这个样例上，

strength

的完成率是 0.5，

cycling

是 0.75，

run

是 0.83，

yoga

是 1.0。

“在我信任这些数字之前，最后再检查一下：

s16

在最后一个晚上

17:30

开始，也就是文件结束前一秒。它的时间窗口还没关闭，所以我会剔除在截止时间前

2h

内开始的会话。骑行变为 1.0。力量训练仍然最低。”

然后看会员列：“力量训练有来自三位会员的六个会话。三次未完成，涉及两位会员，其中两位其实是同一位 Android 会员。样本太薄，不足以据此重做一种锻炼类型，所以页面上每个完成率旁边都会显示会员数。”

第 7 步：第一个版本。 “第一周：这个查询，加上截止时间过滤，作为每晚任务写入一张

finish_rate_weekly

表，再加一个内容负责人周一打开的页面。第二周：平台下钻和时区修复。”这就是一个：精简、真实、端到端。

列里隐藏的陷阱

这些是会让数据集环节翻车的问题，以及各自的解法。

陷阱：把行当成事物来计数

你统计的是事件，却把它们叫作锻炼。解法：先说明粒度，再统计去重后的键。在这个样例上，直接数行会把重试的

e03

数两次。

陷阱：跨平台信任事件名称

如果没有

workout_saved

检查一下，力量训练的完成率是 0.17 而不是 0.5，瑜伽也下降了。你会在日志缺口之后就把内容主管派出去。修复方法：在查看任何指标之前，先按平台或应用版本列出每个事件值。

陷阱：混用设备时间和服务器时间

不带时区的本地时间戳会把晚间锻炼记到错误的日期。延迟同步会把周二的锻炼放进周四的数据里。修复方法：确定每个指标使用哪个时钟，转换为 UTC，并且当你想表达“事情发生的时间”时，用

occurred_at

来过滤，而不是

received_at

。

陷阱：统计尚未结束的会话

在数据拉取前五分钟才开始的会话看起来像是被放弃了。在样本中，保留

s16

让骑行看起来像是第二差的锻炼。修复方法：剔除窗口尚未关闭的会话，并明确说出截止时间。

陷阱：让一个成员代表全部信号

在样本中，两个未完成的力量训练会话属于同一个成员。修复方法：在每个比率旁边显示去重成员数，并说明该比率基于多少数据。

拿到数据集后的前五分钟

  • 用一句话说出数据的粒度，然后用去重计数验证
  • 说出键名，并问哪些键会重复或缺失
  • 问每个时间戳用的是谁的时钟，是否有缺失时区的
  • 按来源列出事件或状态列的每一个值
  • 说出两三个用户，并挑一个有反复出现的决策的
  • 说出一个功能、它不是什么，以及一个指标及其时间窗口
  • 问他们想要 SQL 还是伪代码，然后写出第一个查询

常见问题

有。两位 Palantir 应届生候选人在 Blind 上报告说，他们的分解环节附带了数据；其中一位描述了伦敦出租车记录，并被要求给出面向司机的初步解决方案。没有雇主公布数据集出现的频率。来源 1Palantir Learning & Decomposition Interview (Blind)发布方Blind来源类型Blind 上的候选人报告来源 2Update: interview experience - Palantir new grad FDSE interview (Blind)发布方Blind来源类型Blind 上的候选人报告

当他们递给我一张表时，我应该先看什么？

粒度（一行代表什么）、将它与其他数据关联的主键，以及时间戳：属于哪个时区，时间指的是事件发生的时间还是数据到达的时间。这些决定了这张表能支持哪些特征和指标。

有候选人报告过带数据且要求写代码的分解环节吗？
