Palantir Foundry 是什么？功能、本体（Ontology）与 FDE 实务中的使用方法

原标题：Palantir Foundryとは？機能・オントロジーとFDE実務での使い方

FDE総研 · 2026-08-10 · 约 14 分钟读完

摘要

本文系统介绍Palantir Foundry：它并非高功能BI工具，而是覆盖数据整合到业务执行的操作平台，核心是本体（Ontology）模型。文章说明Foundry、Gotham与AIP的分工，梳理八大组件与Actions、Functions、OSDK的写回机制，并从FDE实务角度讲解导入流程、常见陷阱与学习路径。

要点

  • Foundry定位为从数据整合到业务执行的操作平台，而非BI工具。
  • 本体由对象型、链接型、动作型三要素构成，是全平台共享的业务模型。
  • Actions提供带权限与审计的写回，Functions承载业务逻辑，OSDK支持外部应用。
  • FDE成果以现场实际处理件数衡量，需兼具技术与业务共识能力。
  • 常见陷阱是业务词汇偏差、范围扩大与新旧BI并行导致的数字之争。

Palantir Foundry 是什么？

Palantir Foundry 是 Palantir 面向民营企业的平台，在一个环境中涵盖从数据集成到业务决策执行的全过程。

提供 Palantir Foundry 的 Palantir Technologies 是一家成立于 2003 年的美国企业。其面向民营企业的主力产品是 Palantir Foundry，面向政府与国防领域的产品是 Palantir Gotham（来源：Palantir Technologies 官网「Foundry」 https://www.palantir.com/platforms/foundry/ ／获取日期：2026年8月10日）。FDE（Forward Deployed Engineer）这一职位名称之所以广为人知，是因为需要有人将 Palantir Foundry 落地到客户的现场。可以说，产品的理念与 FDE 这一职位的轮廓是同时形成的，这样理解比较容易。

关于 Palantir Foundry 最常见的误解，是把它当作“功能强大的 BI 工具”。其设计思想的重心并不在可视化本身，而在可视化之后的操作环节。这种差异与其看功能对比表，不如从实际运营中体现出来。部署之后，只要观察现场有哪些人、打开该界面多少次、在那里处理了多少业务，就能一目了然。

Palantir Foundry 想解决什么课题？

Palantir Foundry 的主要目的，是弥合按部门割裂的数据与现场决策之间的断层。

在许多企业中，核心系统、CRM、传感器日志、Excel 各自分散在不同地方。数据被导入分析平台后，很容易陷入“数字是出来了，但没有人行动”的状态。Palantir Foundry 的设计不让数据止步于分析对象。首先，将数据重新关联到库存、订单、设备等业务实体（对象）上。进而，让针对这些对象的操作（审批、下单、分配）也在同一平台上完成。

从现场观察来看，Palantir Foundry 受到好评的原因，往往不是“分析精度高”，而是“从分析结果到下一步行动的距离很短”。看完仪表盘再到另一个系统下单，这种来回消失的价值，往往先于 KPI 体现为现场运营负担的减轻。反之，如果这种来回依然存在，部署结果往往会被评价为“只是多了一个看数据的地方”。

Palantir Foundry 与 Gotham、AIP 有何不同？

Palantir Foundry 是面向民营企业的运营平台，Gotham 面向政府与国防领域，AIP 则是叠加在两者之上的 AI 应用层。

Palantir AIP（Artificial Intelligence Platform）并不是一个独立的平台。它是在 Palantir Foundry 和 Palantir Gotham 所拥有的数据与本体之上，安全运行 LLM 的一个层（来源：Palantir Technologies 官网「AIP」 https://www.palantir.com/platforms/aip/ ／获取日期：2026年8月10日）。FDE 的招聘启事中同时出现「Foundry」和「AIP」的情况越来越多，也是因为这种双层结构是前提。

产品主要对象定位
Palantir Foundry民营企业涵盖从数据集成到业务执行的运营平台
Palantir Gotham政府・国防领域面向政府与国防的平台
Palantir AIPFoundry・Gotham 的用户在数据与本体之上运行 LLM 的 AI 应用层

评估 Palantir AIP 时，与其看 LLM 单体的性能，不如看其下层本体的建设状况。如果业务模型仍然模糊，只叠加 AI 层，最终还是会回到“无法追溯输出依据”这一相同的问题。当招聘启事或提案书中只有 AIP 的名字很显眼时，确认下层的业务模型由谁、定义到了什么程度，更容易把握实际情况。

一般的数据平台与 Palantir Foundry 有何不同？

与一般的 DWH＋BI 架构不同，Palantir Foundry 的覆盖范围包括业务运营的执行环节。

视角一般的 DWH＋BI 架构Palantir Foundry
主要目的数据的积累与可视化从数据集成到业务执行
数据的表现形式表、列本体（对象与链接）
回写基本上通过其他系统实施通过 Actions 在平台内部执行
权限设计以表／行级别为中心可细化到对象、属性级别
用户画像数据工程师、分析师包括现场负责人在内的业务用户
部署形态由企业自行组合工具作为集成套件提供

这份比较梳理的是功能设计方向，是否真正符合需求则因项目而异。Palantir Foundry 是一套集成套件，因此提案往往会部分替换现有的现代数据栈。这种协调正是 FDE 工作的核心。保留哪些、替换哪些，仅靠技术比较是决定不了的，需要把现有投资和运维体制的情况一并纳入考虑并达成共识。

Palantir Foundry 的主要功能和本体的作用是什么？

Palantir Foundry 的核心是本体，它作为将原始数据翻译成业务上的对象和操作的通用模型发挥作用。

Palantir Foundry 有哪些主要组件？

Palantir Foundry 是一套集成套件，在从数据连接到 AI 应用的 8 个领域中，每个领域都配备了专用组件。

领域主要组件作用
数据连接Data Connection从外部系统和数据库导入数据
管道Pipeline Builder / Code Repositories通过 GUI 或代码（Python、SQL 等）进行转换处理
数据模型Ontology Manager定义对象类型、属性和链接
分析Contour / Quiver / Object Explorer交互式分析、时序分析、对象探索
应用构建Workshop / Slate创建面向业务用户的界面
执行与自动化Actions / Functions / Automate回写处理、逻辑实现、自动执行
AI 应用AIP Logic / AIP Agent Studio引用本体的 LLM 逻辑与 AI Agent
外部集成Ontology SDK（OSDK）从外部应用以类型化方式操作本体

组件名称和功能范围会随版本更新而变化，准确的规格需要通过 Palantir 官方文档确认（来源：Palantir Docs https://www.palantir.com/docs/foundry/ ／获取日期：2026年8月10日）。这张表在实务上的要点在于，Palantir Foundry 除了“导入、整理、查看”之外，还在同一套件内拥有“执行”这一层。

记住组件名称的优先级并不高。更重要的是，能否把这张表按“属于哪一层、承担什么角色”的纵向结构来重新理解，这直接关系到项目中的架构讨论。名称可能会变，但连接、转换、模型、分析、应用、执行这样的角色分工却很少改变。

为什么本体是 Palantir Foundry 的核心？

因为本体将行数据转换为订单、设备、配送批次等业务词汇，成为所有功能共享的通用模型。

本体定义的主要是以下 3 个要素（来源：Palantir Docs“Ontology” https://www.palantir.com/docs/foundry/ontology/overview ／获取日期：2026年8月10日）。

要素表示的内容示例
对象类型（Object Type）业务上的实体订单、设备、配送批次
链接类型（Link Type）实体之间的关系订单与客户的关系
动作类型（Action Type）允许对对象执行的变更操作批准、下单、分配

正因为有这三件套，分析界面、业务界面和 AI Agent 才能共享“订单”这一概念。反过来说，如果本体设计有误，构建在其上的所有界面和自动化都会失真。因此在 FDE 的一线，往往比管道实现更愿意把时间花在本体设计的评审上，因为这样可以减少后续工序的返工。评审不能仅由技术人员完成。业务方能否用这些名称进行日常沟通，实际上就是通过与否的标准。

拿不准时，可以问一句“这个名称能否在现场的晨会上直接使用”。如果不能，那它就只是表名，而不是对象名。

Actions 和 Functions 能实现什么？

Actions 负责带权限和审计的回写，Functions 负责业务逻辑的实现，两者使在平台上进行业务处理成为可能。

Actions 是一种把“谁、在什么条件下、能以什么方式修改哪些属性”定义为类型的机制，并附带权限和审计日志。Functions 主要用 TypeScript 或 Python 编写，可在 Actions 的前后插入验证或计算。将这两者结合，就能从“通过 BI 发现问题”的阶段迈向“在平台上处理问题”的阶段。如果想从外部应用以类型化方式操作同一个本体，Ontology SDK（OSDK）就是入口。

机制承担的角色实务中的使用场景
Actions向本体回写（带权限和审计日志）让批准、下单、分配在平台内闭环完成
Functions业务逻辑的实现（TypeScript、Python 等）在 Actions 的前后插入验证或计算
Ontology SDK（OSDK）从外部应用进行类型化操作从现有应用操作同一个本体

从初步感受来看，Palantir Foundry 项目的成败，很大程度上取决于回写设计能在多大程度上与业务方的审批流程保持一致。技术上能够回写，与组织上允许回写，是两个不同的问题。后者的共识形成也包含在 FDE 的工作之中。如果做到让任何人都能追溯审批人、执行人和记录这三项，包括上线后的审计应对在内，负担都会降低。

Palantir Foundry 在 FDE 的实务中是如何被使用的？

FDE 深入客户现场，用 Palantir Foundry 从数据连接到业务应用实现、再到现场落地，全流程一气呵成地负责到底。

FDE 在 Palantir Foundry 上做哪些工作？

FDE 的工作从需求调研开始，到数据连接、本体设计、应用实现、现场落地支持，环环相扣、连续不断。

Palantir 将 Forward Deployed Software Engineer 作为公司职位公开，并说明该职责是直面客户课题、直接构建软件（来源：Palantir Technologies 招聘页面 https://www.palantir.com/careers/ ／获取日期：2026年8月10日）。在日本国内，以“客户驻场型解决方案工程师”或“实施工程师”名义招聘接近 FDE 职务的例子也在增加。

视角一般的数据工程师Palantir Foundry 的 FDE
主要交付物管道和数据表一线负责人每天早上打开的界面
成果的衡量方式数据的质量与新鲜度通过该界面实际处理的件数
所需能力的比重偏技术技术＋业务理解与共识达成

与一般的数据工程师最大的区别在于交付物的定义。正因为有这一区别，所需技能也从单纯的技术扩展到偏重业务理解。可以简单理解为：无人使用的界面，无论实现质量多高，都不计入成果的评价标准。

Palantir Foundry 的实施项目按怎样的流程推进？

一般的流程是：将业务课题聚焦为一个，启动小型用例，之后逐步横向扩展。

  • 课题识别：通过现场观察和访谈，选出一个判断停滞的环节。不从全公司最优化的角度入手。
  • 数据连接：通过 Data Connection 连接最小必要的源，确认新鲜度和缺失的实际情况。
  • 管道建设：通过 Pipeline Builder 或 Code Repositories，将数据整理为能承载业务词汇的数据。
  • 本体（Ontology）设计：定义对象类型、链接类型和操作类型，使其与业务侧的称呼一致。
  • 应用实现：用 Workshop 搭建面向一线的界面，通过 Actions 打通回写路径。
  • 落地与横向扩展：观察实际使用日志进行改进，并扩展到相邻部门的类似业务。

从业者中普遍认为，在工序1和工序4投入足够时间的项目，后半程的返工越小。不过各工序所需时长很大程度上取决于目标业务和数据质量，无法给出有依据的标准天数。当被要求估算时，与其用天数，不如用“哪项业务、在平台上完成到什么程度”这样的范围（scope）表述来达成共识更为现实。

在 Palantir Foundry 项目中，FDE 容易陷入哪些陷阱？

Palantir Foundry 项目停滞的原因，往往不是技术难度，而是业务词汇未确定和范围扩大。

典型的陷阱有三个。第一个是本体命名仅由信息系统部门决定，与一线的叫法不一致的模式。第二个是初期范围包含多个部门，在共识达成上耗费时间的模式。第三个是与现有 BI 工具的职责划分不明确就并行运行，引发“哪个数字才正确”问题的模式。

陷阱表面化的症状提前预防的对策
业务词汇的偏差界面的项目名称一线看不懂与一线负责人一起评审本体命名
范围扩大在共识达成上耗费时间，启动延迟将初期范围限定为单一部门、单一业务
与现有 BI 并行出现“哪个数字才正确”的问题提前确定作为正确依据的数字所在位置和职责划分

这些问题技术难度都不高，但一旦发生，恢复需要很长时间。之所以说 FDE 需要的能力是“实现能力＋现场的共识达成能力”，正是因为存在这一结构。另外，这里列举的倾向是编辑部（FDE总研／运营：VACAN）整理的普遍可信的范围，并不代表特定项目的实绩。

没有经验的人应该按什么顺序学习 Palantir Foundry？

先理解本体的概念，之后再接触实现工具，这样的顺序能提高学习效率。

  • 概念理解：通过 Palantir Blog 和官方 Docs，掌握本体（对象类型、链接类型、操作类型）的思路。
  • 数据转换基础：用 SQL 和 Python 进行数据转换，即使在 Palantir Foundry 以外的环境也可以，通过动手实践来掌握。
  • 官方教程：通过 Palantir Learn 的课程，把从 Pipeline Builder 到 Workshop 的流程完整走一遍。
  • 应用实现练习：选定一个小型业务场景，从对象定义到通过 Actions 回写，全部自己动手完成。
  • AI 集成：确认 AIP Logic 等引用本体的 LLM 逻辑的配置方式。

有人反映，如果跳过阶段 2 直接从阶段 3 开始，虽然能跑完教程，但难以灵活应用。Palantir Foundry 的工具操作本身属于容易上手的类型。然而，支撑其运行的数据转换设计能力，则需要作为通用技能另行掌握。

在无法直接接触 Palantir Foundry 的环境中，该如何替代？

即使接触不到产品，本体式设计的思维方式与业务访谈的练习，完全可以在其他环境中替代进行。

有效的方法是，用手头的数据尝试编写“业务对象设计”而非“表设计”。将实体、关系、允许的操作、操作的执行者与审批者汇总到一张表中。这与 Palantir Foundry 的本体设计思路几乎相同，即使没有产品许可证也可以练习。

要写出的项目对应的本体要素示例
实体对象类型订单、设备
关系链接类型订单与客户
允许的操作操作类型审批、分配
执行者与审批者Actions 的权限设计谁执行、谁审批

此外，作为 FDE 核心能力的“用现场的语言定义问题的能力”，仅通过向所在组织的相邻部门进行访谈也能得到锻炼。Palantir Foundry 的产品知识可以在入职后掌握，但业务理解与达成共识的经验，很大一部分是可以提前积累的。在选拔中，比起产品操作的熟练程度，发现业务瓶颈并推动解决的经验才是更有力的材料。
