Vannevar Labs FDE 岗位要求与 TS/SCI 安全许可

FDE Times · 2026-11-03 · 约 5 分钟读完

摘要

文章分析 Vannevar Labs 的 FDE 招聘启事，指出有效的 TS/SCI 安全许可是硬性门槛，因为工程师必须亲手把 Kubernetes 微服务部署到 IL6、JWICS 等涉密云。合规工作占很大比重：需满足国防部 RMF 标准，编写系统安全计划、运行手册和 CONOPS，并集成 IdAM、SIEM、CDS 等客户系统。启事将无许可者、纯 SaaS 背景者和无法出差者挡在门外，但作者认为向受控环境部署并留下可执行文档，是银行、医院等强监管行业 FDE 同样需要的核心能力。

要点

  • TS/SCI 安全许可是硬性前提，许可跟着涉密服务器走而非职位。
  • 部署目标是 IL6、JWICS 等涉密云，工程师需亲手操作。
  • RMF 合规与安全文档（系统安全计划、运行手册、CONOPS）是交付物。
  • 需集成客户的 IdAM、SIEM、CDS，集成和文档耗时远超写代码。
  • 同类技能适用于银行、医院等强监管行业的受控环境部署。

许可跟着服务器走而非职位：工程师要亲手把代码部署到涉密云上，银行和医院的受控环境只是温和版本。

要点速览

  • Vannevar Labs 的 FDE 招聘启事把有效的 TS/SCI 安全许可列为硬性要求，因为软件要部署到 IL6、JWICS 这样的涉密云上。
  • 工作中很大一部分是合规：落实安全控制，编写系统安全计划、运行手册和 CONOPS，以满足美国国防部的 RMF 标准。
  • 这份启事把没有安全许可的工程师、只部署过商业 SaaS 的工程师挡在门外。不过，向受控环境部署是所有强监管行业都需要的技能。

在 Vannevar Labs 的前线部署工程师（FDE）招聘启事里，最难满足的要求与 Python 或 Kubernetes 无关。候选人必须持有有效的美国绝密（Top Secret）安全许可，并具备 SCI 资格。这是能否被考虑的前提，而不是加分项。

乍看之下，这像是国防行业惯常的行政门槛。但把这份 FDE 启事和该公司另外三份工程岗位启事放在一起读，情况就清楚多了：之所以需要安全许可，是因为软件运行在涉密云上，而工程师必须亲自把代码部署上去。

你也许永远不会投递美国国防公司，但 Vannevar 展示了一种情形：当客户环境受控到极致时，FDE 的工作是什么样子。

许多其他行业也运行着受控环境，只是没那么严格：银行、医院、各国的政府机构。想在这些地方做 FDE 的人，都应该了解这类工作。

安全许可跟着服务器走，而不是跟着岗位名称走

Vannevar 自称是一家为美国战争部（即国防部的新名称）构建 AI 系统的公司。截至 2023 年初，其主要产品 Decrypt 已在 15 个以上的军事基地运行。简单说，它的客户就是军方。

Full Stack Engineer（FDE/ATO）岗位的启事把任务描述为：将一套运行在 Kubernetes 上的复杂微服务架构迁移到涉密云环境中。

在涉密网络上部署软件时，工程师还要提供直接的“hands on keyboard”（亲手操作）支持。从措辞看，负责部署的人通常直接在涉密一侧工作，而不只是远程操作。

Senior Software Engineer（ATO）的启事点名了两个环境：IL6 和 JWICS。可见，安全许可绑定的是软件运行的位置，而不是员工工牌上的头衔。

这个岗位也不止于部署。位于瓦胡岛（Oahu）的 FDE 启事写明，录用者将成为一项任务及其相关客户合作的技术负责人。

他们负责设计、构建软件，并为直接运行在客户环境中的软件承担责任。公司还表示，其工程师、产品团队和 CTO 会直接奔赴问题发生的地方，包括前往乌克兰的部队。

文档也是交付物

与 SaaS 公司的 FDE 相比，最大的不同是合规工作量。瓦胡岛的启事要求具备在风险管理框架（RMF）下开发和部署软件的经验。RMF 是软件在美国国防部系统上获准运行前必须通过的流程。

FDE/ATO 的启事要求落实关键安全控制，以满足国防部的认证标准。

Senior Software Engineer（ATO）的启事把文书工作列得很具体：部署运行手册、系统安全计划（System Security Plan）和作战概念文档（CONOPS）。在这里，文档和代码一样，都是要交付的东西。没有文档，软件就得不到授权；没有授权，软件就无法运行。

设想一个听起来很简单的需求：加一个功能，从政府数据平台拉取数据并展示给分析人员。

在 SaaS 公司，这也许只需几天：调用 API、做界面、合并、部署。瓦胡岛的启事则恰好列出了你需要打交道的系统：数据平台、身份与访问管理（IdAM）服务、安全信息与事件管理（SIEM）系统，以及跨域解决方案（CDS）。

在这个假设场景中，用户必须通过政府的身份系统登录，而不是你的。每一次访问都要把日志发送到客户监控的 SIEM。

如果数据要在两个密级不同的网络之间流动，就必须经过 CDS，系统安全计划和运行手册也要随之更新。代码本身可能仍然只需几天；集成和文档很可能会占去大部分时间。

这份招聘启事把谁挡在门外

安全许可要求中的“active”（有效）一词是最关键的细节。没有现行许可的人，技术再强也不符合条件。安全许可不是入职后能补办的东西，因此这个岗位对纯商业背景的工程师几乎是关闭的。

第二类被排除的人更不容易察觉：只在商业云上部署过 SaaS 的工程师。在那种环境里，一切都是自动化的，文档往往事后才补。他们也许能通过 Kubernetes 面试，但一个要求 RMF 经验、熟悉 IdAM、SIEM 和 CDS 并能编写系统安全计划的岗位，很可能很快暴露出短板。

第三类是无法出差的人。这个 FDE 岗位标注为完全远程，但要求出差，时间可能占 20-30%，去和负责任务的人见面。这里的“远程”并不等于待在家里。

下表汇总了四份启事中的要求、它们在日常工作中的含义，以及在国防以外的强监管行业中的对应项。

启事中的要求 在工作中意味着什么 国防以外的对应项
有效的 TS/SCI 安全许可 获准在涉密一侧工作以完成部署 获得客户生产环境的访问权限，并接受背景调查
部署到涉密云（IL6、JWICS） 把 Kubernetes 微服务带进隔离网络 在银行和医院做本地部署或物理隔离（air-gapped）安装
RMF 合规，落实安全控制 软件必须先获授权才能运行 上线前的安全审计和风险评估
运行手册、系统安全计划、CONOPS 文档是交付物 为客户 IT 团队编写运维和安全架构文档
集成 IdAM、SIEM、CDS 使用客户的基础设施，而不是自己的 集成企业 SSO，把审计日志发送到监控系统

可以带走的技能

大多数读者不符合这个具体岗位的条件，也没必要符合。值得学习的是这些启事隐含要求的能力：把软件送进一个不属于你的环境，遵守别人的规则，再用书面材料证明一切安全。

为银行或卫生机构工作的 FDE 需要的正是同样的能力，只是管控通常更宽松。

对习惯 SaaS 的人来说，最难的是在没有互联网、没有自有基础设施的条件下部署。练习这一点，远比任何 Helm 教程更接近真实工作。

写简历时，不要把合规经验埋在“熟悉安全”这样的一行字里。写清楚你集成过哪些身份系统、把审计日志发到了哪里、为哪次审计写过哪些文档；面试前，再为上表最后一列的每一行各准备一个例子。

美国 TS/SCI 安全许可只适用于这类岗位。而在别人的系统上写出一份陌生人也能照着执行的运行手册，是每个强监管客户都需要的技能。
