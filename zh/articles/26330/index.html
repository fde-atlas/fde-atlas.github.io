FDE 系统设计面试题：遗留系统集成怎么答

FDE Times · 2026-10-30 · 约 5 分钟读完

摘要

这篇文章讲解 FDE 系统设计面试中如何应对遗留系统集成题。作者以保险公司本地保单系统为例，指出提议推倒重写是错误答案，正确思路是把客户约束当作问题本身：先询问可改动的集成点，再逐层搭建数据路径——用只发起出站连接的 Agent 穿透防火墙限制，用 CDC 从数据库捕获事件，经防腐层（ACL）转换遗留 schema，最后通过绞杀者模式的外观层逐个迁移功能。文章引用 Martin Fowler 对一次性重写失败的警告和 Microsoft Azure 架构文档，并强调要主动说出每层设计的代价，如 ACL 延迟与最终一致性。

要点

  • 推倒重写不符合 FDE 岗位要求，客户约束才是考题本身。
  • 稳妥顺序：找集成点、出站 Agent、CDC 捕获事件、ACL 转换、外观层迁移。
  • Martin Fowler 认为一次性重写大多失败，应采用绞杀者模式渐进迁移。
  • 要主动说出代价：ACL 增加延迟，事件驱动方案只能最终一致。
  • 常见陷阱：不查前提条件硬套模式，或让旧 schema 渗入新服务。

提议推倒重写不符合岗位要求，用绞杀者模式的外观层才能证明你能在别人定下的约束里做事。

要点速览

  • Praxent 等公司的 FDE 招聘启事要求与给定系统集成，包括遗留核心系统，因此要把客户的约束当作问题本身。
  • 稳妥的顺序是：找出集成点，建立出站连接，通过 CDC 捕获事件，经 ACL 转换，再用外观层逐个迁移功能。
  • 不要提议全面重写，Martin Fowler 认为这类计划大多以失败告终；也不要让旧 schema 渗入新服务。

设想这样一道题：客户是一家保险公司，保单管理系统在本地部署环境中运行多年，运维团队不允许任何人改动它。客户想要一个保险理赔分诊服务。你有 45 分钟和一块白板。

很多工程师会直接画出一套干净的架构：API 网关、微服务、新数据库，再提议“逐步把所有东西迁过去”。在普通的软件工程师面试中，这样回答也许够了。但对前线部署工程师（FDE）岗位来说，这恰恰跳过了招聘启事描述的那部分工作。

Praxent 的 FDE 招聘启事明确要求与实际给定的系统干净地集成，包括遗留核心系统，并直接说明你要在别人已经做出的决策之内工作。

所以合理的准备方式是：假定面试官想看你如何围绕约束做设计，而不是你多会把约束想象掉。

为什么“干净地重写”是错误答案？

Martin Fowler 对一次性重写提出过警告：听起来简单，但据他观察，这类计划大多以失败告终。他推崇的是渐进式现代化，这种做法有个名字：绞杀者模式（Strangler Fig）。

根据 Microsoft Azure 架构文档，绞杀者模式用新的应用和服务逐步替换旧系统的部分功能，同时旧系统继续运行尚未迁移的功能。其核心机制是外观层（façade）：一个位于遗留后端前面的代理层，决定每个请求交给旧应用还是新服务。

但每种模式都有前提条件。Microsoft 指出，如果无法访问遗留系统的源代码，也没有其他允许改动的集成点（例如数据库），绞杀者模式可能并不适用。这正是面试中要问的第一个问题。

先提问，再画图

对上面的保险题目，前五分钟用来提问。保单系统的代码能改吗？如果不能，能读它的数据库吗？内部网络允许哪个方向的连接？谁审批访问权限，通常需要多久？

最后一个问题不是凑数。为企业提供 FDE 的公司 Appsierra 认为，开通访问权限、安全审查和客户审批往往比找到工程师花的时间更长。

这是供应商的看法，并非独立数据。但如果你在计划中预留审查时间，就说明你清楚真实项目通常卡在哪里。

假设面试官回答：不能改代码，可以读数据库，不能开放入站防火墙规则。这三个回答决定了大部分架构。

实例：逐层搭建数据路径

先看网络。防火墙不开放入站时，就在客户网络内部署一个 Agent，只让它发起出站连接。Palantir Foundry 正是这样做的：客户网络内的 Agent 通过单向出站 HTTPS 连接持续轮询 Foundry，领取任务。

其文档现已把这种 Agent worker 架构标为遗留方案，但不开放任何入站端口这一原则，在勾画设计时仍然值得遵循。

接下来是捕获事件。既然不能改代码，就无法在应用里插入“新理赔进来时发送事件”的调用。对于无法修改的组件，Microsoft 建议直接从数据库捕获事件，例如用变更数据捕获（CDC）读取事务日志，这样完全不用碰应用代码。

事件现在到了你手里，但仍带着旧系统的形态。Microsoft 提醒，遗留系统的 schema 往往混乱，API 也已过时。没有隔离层，新设计会逐渐吸收旧系统的语义。这个隔离层叫作防腐层（ACL）。

假设旧理赔表的列名用了缩写，状态是数字代码，金额以乘以 100 后的整数存储。只有 ACL 知道这些约定：

# ACL：把遗留记录转换为新服务的模型
STATUS_MAP = {"01": "submitted", "02": "in_review", "09": "closed"}

def to_claim(row: dict) -> Claim:
    return Claim(
        claim_id=row["CLM_NO"].strip(),
        policy_id=row["POL_REF"].strip(),
        status=STATUS_MAP.get(row["ST_CD"], "unknown"),
        amount=Decimal(row["AMT_X100"]) / 100,
    )

分诊服务只处理

Claim

，从不读取

ST_CD

。这也是现实中最费力的部分：Appsierra 把 FDE 的集成工作描述为，让客户真实的 schema、命名约定和数据缺口与产品需求对上。

最后是外观层。第一天只有一条路径迁到新服务，其余一切仍走旧系统：

MIGRATED = {"/claims/triage"}

def route(path: str) -> str:
    return NEW_SERVICE if path in MIGRATED else LEGACY

再迁移一个功能，只需在

MIGRATED

里加一行；回滚也同样简单。

每一层都有代价：主动说出来

不等面试官问，先把代价讲清楚。Microsoft 指出，ACL 会给两个系统之间的调用增加延迟。如果分诊必须立即把结果返回给正在和客户通电话的坐席，这部分延迟就得放进你的预算。

如果旧系统按批处理运行或速度较慢，还有另一个选择：通过 Service Bus、Event Grid 或 Event Hubs 等队列实现事件驱动的 ACL。

据 Microsoft 介绍，这样能让新系统摆脱旧系统的吞吐量限制。代价是数据到得更晚，只能在一段延迟后达到一致（最终一致性），这一点要明确说出来。

从零开始的答案

  • 什么都没问就画新架构
  • 提议重写整个系统
  • 假定可以开放入站防火墙规则
  • 在新服务中直接读取旧 schema

FDE 的答案

  • 先问清哪些集成点允许改动
  • 用外观层逐个迁移功能
  • 部署只发起出站连接的 Agent
  • 所有数据经 ACL 转换，并说明它增加的延迟

要避开的陷阱

第一个陷阱是不检查前提条件就套用绞杀者模式。如果客户既不让你碰代码，也不让你碰数据库，外观层就无处着力，这时应该直说，而不是硬套模式。

另一个陷阱是 ACL 只存在于架构图的一个方框里。只要 ACL 以外还有服务在读取旧状态码，遗留语义就已经渗入新系统。还有别忘了人：如果没人审批访问权限，再优雅的架构也只能停留在纸上。

职业建议：读招聘启事时，“legacy cores”“on-prem”“existing systems”这类措辞，很好地提示了系统设计面试会考什么。简历上不要只罗列技术，要写出“在客户侧零代码改动的前提下，通过 CDC 从系统 X 导出数据”这样的句子，因为这正是 FDE 招聘启事描述的集成工作。

本周的练习很简单：拿上面的保险题目，把其中一个回答改成“不允许读取数据库”，再解一遍。如果你仍能说清架构为什么必须改变，你练的正是 FDE 招聘启事所寻找的能力。
