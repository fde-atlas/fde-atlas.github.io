探索研讨会：作为 FDE 如何开展一场

原标题：Discovery workshop: how to run one as an FDE

FDE Times · 2026-10-22 · 约 7 分钟读完

摘要

这篇文章面向前沿部署工程师，讲解如何主持客户发现工作坊。作者认为大多数部署项目的成败在发现阶段就已决定，工作坊的目标是产出双方认可的问题陈述和成功定义，而非愿望清单。文章以一家虚构物流公司的发票投诉流程为例，完整演示了会前准备、流程映射、任务打分和会后验证的全过程。

要点

  • 会前先写下工作坊必须回答的唯一问题，并固定流程的起点和终点。
  • 参会者控制在十人以内，必须包含实际执行工作的一线人员。
  • 用价值和努力两个维度给任务打分，只选出一个先做的任务。
  • 会前必须问清数据能否离开内网，避免承诺被安全团队推翻。
  • 工作坊产出的一切仍是假设，会后应按影响和不确定性排序并验证。

简要概述

  • 探索阶段决定了大多数部署的成败；它应该产出双方都认可的问题陈述和成功定义。
  • 从流程的起点和终点向内绘制流程，然后按价值和投入为每项任务打分，从中精确选出一项。
  • 研讨会结束后你只有假设：按影响和不确定性排序，然后用客户的真实工作来验证它们。

早上九点，在客户的办公室。房间里坐着十二个人。运营负责人开场说：“我们想为整个投诉部门引入 AI。”IT 负责人坐在桌子尽头，双臂交叉。而那三位每天处理投诉的员工，还没有被问过一个问题。你有九十分钟。

这样的场景对前沿部署工程师来说是家常便饭，而这场会议的运作方式决定了接下来大部分事情的走向。Scaler 的 FDE 手册说得很直白：探索阶段决定了大多数部署的成败。

目标是产出双方都认可的问题陈述和成功定义，而不是一份愿望清单。

接下来是一个从头到尾的完整示例，围绕一家虚构的物流公司及其处理发票投诉的流程展开。

会议之前：一个问题、两块白板笔、不超过十个人

Koji 关于如何开展探索研讨会的指南建议，在做任何其他事情之前，先写下这场会议必须回答的那个核心问题。对于这家物流公司，这个问题不应该是“AI 如何帮助客户服务？”更好的问法是：“在发票投诉流程中，哪一步应该首先实现自动化，我们将如何衡量成功？”

专注于流程绘制的公司 Triaster 建议在会议前确定范围，然后从该范围的起点和终点开始讨论。在本例中，流程从一封投诉邮件进入共享收件箱开始，到开出贷项通知单，或投诉被附上理由驳回时结束。

参会名单同样重要。Triaster 将主题专家，即真正执行工作的人，视为必须参加。它要求团队人数不超过十人，希望有一位了解该流程如何与其他部门衔接的人，并且需要流程负责人的支持。

Scaler 也提出了同样的观点：不要只和领导层交谈；要与真正会使用系统的人坐在一起。所以面对这十二个人，第一项工作就是精简名单。

保留流程负责人、三位投诉处理员、会计部负责开具贷项通知单的人、IT 负责人和仓库经理。运营负责人可能只需要在最后十五分钟确定优先级时参加。

从两端向中间绘制

两个标记都画到白板上后，请一位经办人讲述他们上周处理的一个真实投诉。

每个步骤写在一张便利贴上：接收邮件、分类、在 ERP 中查询发票、与送货证明核对、请求审批、开具贷项通知单。

在每张便利贴下方记录四件事：谁来做、用哪个系统、需要什么数据、案件通常在哪里搁置等待。

有些问题在场的任何人都答不上来，比如送货证明存放在哪个系统。不要停下来深挖。PostHog 的 FDE 手册建议利用客户的真实工作来暴露真实问题，而不是试图事先把一切都建模出来。

在便利贴上标一个“？”，指派某人去核实，然后继续。

十个合理的任务，选一个

到绘制结束时，白板上通常会有十几个听起来都挺合理的想法。PostHog 认为 FDE 的核心判断力正在于此：知道十个合理的任务中该先做哪一个，哪些干脆不做。

OpenAI Academy 的优先级矩阵对每个工作流提出两个问题：如果做成，能带来多少价值？实现它需要多少投入和复杂度？

评估价值时，它指向三个有力信号：频率、重复性和覆盖面。以下是对物流示例的示意性打分，采用 1-5 分制：

候选工作流频率重复性覆盖面投入决策
投诉邮件分类5432先做
发票与送货证明匹配4534后做，等数据理清之后
给 CFO 的月度投诉报告1412不做
预测哪些客户会投诉2225不做

这张表不是公式。它的价值在于迫使在场的人大声说出为什么选这个任务而不是那个。CFO 报告很容易做，但它每月只运行一次，而且只有一个读者。投诉预测听起来最令人兴奋，但投入最大，价值也不明确。

就在这时有人会问：“既然都做到这儿了，能不能把预测那块也做了？”PostHog 的建议是对每一个“我们要不要顺便……”都顶回去。把这个想法写到白板上的“以后”一栏，让提出的人看到它没有被扔掉。但绝不能让它溜进今天的范围。

不能跳过的问题

第一个问题问的是 IT 负责人——那位至今仍双臂抱胸的人。Scaler 强调，如果客户的数据不允许离开内部网络，你必须在设计任何东西之前就弄清楚。直接问：投诉邮件和 ERP 数据能否发送给外部模型，由谁来审批？

第二个问题来自 PostHog 的范围界定清单：所描述的问题是否指向更深层的模式？假设在梳理案例的过程中，处理人员提到大多数投诉都来自同一个仓库。

根本原因可能是该仓库的签收扫描出了故障，而读取邮件的 Agent 只是在收拾后果。由于仓库经理就在现场，你可以当场询问这个假设是否值得核查。

第三个问题回到 Scaler 设定的目标：成功是什么样子？离开会议室前，一定要让双方都点头认可一句话，比如“从收到邮件到投诉进入正确队列的时间从 X 降到 Y”，其中 X 在接下来一周内用真实数据测量得出。

会议之后：白板上的所有内容仍然只是假设

Koji 明确表示，工作坊并不能产出证据。便利贴、打分，甚至“大多数投诉来自同一个仓库”这句话，全都是假设。

Koji 还建议按影响和不确定性对假设进行排序。在物流的例子里，“投诉邮件足够清晰，可以自动分类”影响很大，因为第一项任务完全依赖它，而且没人测量过。“大多数投诉来自同一个仓库”同样影响大且不确定。

所以会议后的第一件事就是验证这两个假设：抽取真实投诉样本，比如一周的邮件，在其上运行分类步骤，并按仓库统计投诉数量。这正是 PostHog 推荐的精神——用真实工作来暴露问题。

一天之内发送一份总结，涵盖核心问题、流程图、打分表、“以后再说”一栏、关于数据的回答以及成功的定义。

这样的文档在去掉客户名称后，也可以带去面试。在简历上，“主持了一次探索性工作坊，把范围从十个想法缩小到一个，并按约定的指标衡量结果”比“沟通能力强”更有说服力。

让工作坊沦为无效会议的错误

一个错误是没有确定起点和终点就绘制整个公司的流程，结果九十分钟过去，连一个值得自动化的步骤都没找到。

另一个错误是在询问数据约束之前就在现场做出承诺。这样的承诺可能因为安全团队的一封邮件就化为泡影。最后一个错误是把现场达成的共识当作已验证的事实，并直接在此基础上展开建设。

好的工作坊不会在掌声中结束。它的结束，是你手上有一项周一早上就能开始的任务、一个要衡量的数字，以及一份你已经委婉告知“暂不处理”的事项清单。
