Agent 框架怎么选：LangChain、LlamaIndex、Haystack 对比

FDE Times · 2026-10-08 · 约 6 分钟读完

摘要

文章以 FDE 视角讨论 Agent 框架选型：Anthropic 建议先直接调用 LLM API，因为许多模式只需几行代码，而框架的抽象层会遮蔽 prompt、增加客户团队的调试负担。LangChain、LlamaIndex、Haystack、RAGFlow 各自解决不同层的问题，选型应取决于客户的具体卡点。由于 FDE 离开后框架会留在客户代码库中，作者提出交接测试：能否打印最终 prompt、能否追溯错误来源。

要点

  • Anthropic 建议先直接调用 LLM API，框架可能遮蔽底层 prompt。
  • 四个工具各管一层：LangChain 快速上手，LlamaIndex 管数据，Haystack 显式管道，RAGFlow 处理复杂文档。
  • FDE 离开后框架留在客户代码库，引入前须确认它承担真正的工作。
  • 文中物流公司案例显示问题出在文档切分，而非 Agent 编排。
  • 交接测试：能否打印最终 prompt 并追溯错误到具体 chunk。

Anthropic 建议先直接调用 API；选 LangChain、LlamaIndex 还是 Haystack，实质是决定把哪一层交给别人的库。

要点速览

  • Anthropic 建议从直接调用 LLM API 开始，因为许多模式只需几行代码，并提醒框架可能遮蔽底层 prompt。
  • 四个工具服务于四个不同的层：LangChain 用于快速上手，LlamaIndex 面向数据层，Haystack 提供显式管道，RAGFlow 处理复杂文档。
  • 对 FDE 来说，离开后框架仍留在客户的代码库里，所以只有当它承担真正的工作、且你足够了解它时，才值得引入。

Anthropic 在 2024 年 12 月 19 日发布的 Agent 构建指南中，给出了一条与许多开发者的本能做法相反的建议：先直接调用 LLM API。理由很务实：许多模式只需要几行代码。

与此同时，每个框架都有自己的承诺。Haystack 称自己是用于构建可上生产环境的 Agent 的开源框架。LangChain 承诺能用任意模型提供商快速跑起 Agent。LlamaIndex 则邀请你基于组织自己的数据构建 Agent。

对前线部署工程师（FDE）来说，选框架不只是个人偏好。你写的代码在你离开后会留在客户的代码库里，凌晨两点排查问题的是客户的团队。

所以，正确的问题不是“哪个框架最好”，而是“客户卡在哪里，这一部分该不该交给别人的库？”

每个工具解决的是工作的不同部分

仔细读每个项目的自我介绍，就会发现它们在不同的场地上比赛。LangChain 强调快速上手和兼容任意模型提供商。如果需要具备一定确定性的生产级 Agent，它会把你引向另一个产品 LangGraph，后者提供底层控制。

LangChain 还有 LangSmith，一个用于观测、评测和部署 Agent 的平台。这一点对 FDE 很重要：这个生态中有一部分是客户可能需要购买的产品，而不只是开源库。推荐 LangChain 时，要讲清楚客户用了哪些组件，哪些日后可能带来费用。

LlamaIndex 从数据出发：它是一个 Python 工具包，用于构建运行在客户自有数据上的 LLM Agent。它的 workflow 是事件驱动的多步骤流程，把 Agent、数据连接器和工具组合在一起。在这幅图景里，检索增强生成（RAG）只是众多工具之一。

Haystack 不把逻辑藏在自动化的层后面。根据 deepset 的文档，管道是一张由你亲手连接的图，因此每次运行方式都一样。该项目强调对检索、路由、记忆和生成的显式控制，并承诺可以更换模型或基础设施而无需重写系统。

RAGFlow 与其他几个不同：它是一个开箱即用、部署后即可运行的 RAG 引擎，而其他几个都是需要在代码里组装的库。它的强项是深度理解格式复杂的非结构化文档。它还能让用户直观地看到文档如何被切分成 chunk，便于人工介入。

下表把每个工具放进客户现场常见的场景中：

工具擅长适合客户需要引入前要问的问题
LangChain + LangGraph快速上手，兼容多家提供商；LangGraph 用于需要确定性的生产环境先用快速演示说服决策者，再转向可控流程客户会用 LangSmith 吗，谁来付费？
LlamaIndex基于私有数据的 Agent、事件驱动的 workflow、大量数据连接器数据分散在多个来源哪些连接器真正需要，哪些暂时不需要？
Haystack开发者亲手连接的管道、运行结果一致、可替换模型和基础设施审计、结果可复现、担心被锁定客户团队有没有人手维护这张图？
RAGFlow预构建引擎，理解复杂文档，chunk 可查看、可修正杂乱的 PDF 档案，由业务人员检查检索质量他们能否接受运行一个独立系统而不是一个库？
直接调用 API中间层最少，每个 prompt 一览无余需要快速调试的简单流程你在重写的哪些部分，框架其实已经解决得很好？

客户卡在哪里？

假设一个场景：一家物流公司想要一个内部 Agent，回答有关运输合同的问题。数据是几千份带表格的扫描 PDF，多年来用不同模板起草。你有两周时间。

第一周，你直接调用 API，把文档按固定长度切分成 chunk，并在每次请求前打印完整的 prompt。有用户询问海防–河内线路的仓储费，模型答错了。打印出的 prompt（数字仅作示意）如下：

上下文：
[Chunk 15] 海防 - 河内 | 4,200,000 | 350,000
[Chunk 31] 仓储费按月收取，于期末支付……
问题：海防 - 河内线路的仓储费是多少？

问题一眼就能看出来。表头行“路线 | 运费 | 仓储费”落在了 chunk 14 中，而它从未被检索到，于是模型看到两个没有列名的数字，选了第一个。问题出在文档的读取和切分方式上，与 Agent 编排毫无关系。

这时就该引入专门做文档理解的工具，比如 RAGFlow。它的 chunk 检查界面能让运营侧的人看到费用表与表头被切开了，并加以调整，让整张表落在同一个 chunk 里。再次打印 prompt，上下文中已包含所有列名，模型选出了正确的数字 350,000。

客户现场第一天的教训：讨论框架之前，先打印 prompt，问一问检索到的 chunk 是否足以让人类读者答对。

其他场景会指向其他工具。如果文档干净，但分散在 SharePoint、数据库和电子邮件中，LlamaIndex 的数据层就是帮你省力的部分。

再假设客户是一家需要接受审计的企业，要求每个答案都可复现。那么 Haystack 这种亲手连接、每次运行方式一致的图，在合规团队面前会更容易站得住脚。

如果客户老板只需要三天内看到演示以便批预算，用 LangChain 快速起步是合理的，前提是你事先说明生产环境需要 LangGraph 或其他方案。

你离开了，抽象留给客户来扛

Anthropic 点出了最大的风险：框架往往会增加抽象层，遮蔽底层 prompt，让调试更难。对开发内部产品的开发者来说，这只是小麻烦。对 FDE 来说，这是留给客户团队的一笔债。

Anthropic 的第二条建议更直接：如果使用框架，就要理解底层代码。它指出，对框架内部运行机制的错误假设是客户出错的常见原因。实际情况中，错误通常始于有人以为框架在做一件事，而它实际上在做另一件事。

这就给每个框架定下了一道交接前必须通过的测试。你能否像上面运输合同的例子那样，打印出发送给模型的确切最终 prompt？客户团队能否把一个错误答案追溯到导致它的那个 chunk 和那一步路由？

如果答案是否定的，那么框架为你节省的时间，是让客户日后买单换来的。

自己写不等于全部重写

把 Anthropic 的建议理解成“永远别用框架”是误读。它说的是许多模式只需几行代码，而“许多”给其余情况留了余地。一个工具调用循环、一个摘要步骤或一个简单的路由器，各自几十行代码就能写完，客户团队里任何人都能读懂。

自己为满是表格的 PDF 写解析器，或者为十个数据源自己写连接器，就是在重做 RAGFlow 或 LlamaIndex 已经大量投入的工作。Haystack“换模型不用重写”的承诺，也只有在客户确实可能更换模型时才有价值。

如果不会更换，自己写一层薄薄的适配层就足以降低被锁定的风险。

因此，客户现场的合理做法通常是混合式的。编排自己写，并保持极薄，薄到能打印每一个 prompt。只在恰好一个繁重的层引入框架，让它承担真正的工作。交接时附上一页说明，解释为什么这一层用库，其他层不用。

开发者应该练什么

这里真正有价值的技能，是能在客户的工程师面前解释清楚为什么这个工具适合这部分工作；背熟四个工具的 API 用处不大。练习方法是用两种方式解决同一个问题：直接调用 API 和使用框架，然后记下框架在哪里帮了忙、在哪里遮住了 prompt。

岗位描述里的框架名称也是线索：提到 LangGraph 和可观测性的岗位，很可能需要有人把 Agent 可控地推向生产环境。描述自己的经验时，要让招聘方看到你如何权衡用或不用一个工具；单纯罗列库名说明不了什么。

框架会改名、合并产品、调整定位。先直接调用 API、找准客户的卡点、然后再选工具，这个习惯会比它们中的任何一个都更长久。
