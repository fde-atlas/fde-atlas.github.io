代码评审怎么带新人：FDE 代码评审指南

FDE Times · 2026-11-15 · 约 6 分钟读完

摘要

这篇文章面向 FDE 团队的代码评审者，主张评审不仅是客户环境上线前的最后防线，更是带新人的日常培训渠道。核心做法是给每条评论打上 blocking、non-blocking 或 nit 标签，写清问题与理由，把修法交给作者，并在阻塞问题解决后尽早批准。衡量标准不是抓到多少 bug，而是新人随时间推移对评审者的依赖是否下降。文章还建议按新人资历调整评论详细程度，并列举了评审者的四种常见错误。

要点

  • 评审的次要目标是让新人逐渐不再依赖评审者。
  • 评论分 blocking、non-blocking、nit 三类，标明是否阻塞合并。
  • 每条评论针对代码、附理由，修法一般交给作者决定。
  • 代码整体变好即批准，nit 推迟到清理 PR。
  • 按新人资历调整评论详细程度，并跟踪阻塞评论数下降趋势。

每条评论标明是否阻塞、写清理由、把修法交给作者：客户有保障，新人也成长得更快。

要点速览

  • 评审有一个次要但重要的目标：让作者随时间推移需要的评审越来越少。
  • blocking、non-blocking 和 nit 三种标签，能让新 FDE 一眼看出代码接触客户数据之前哪些必须修。
  • 说清问题和理由，修法交给作者决定，代码明显变好时就批准。

设想这样一个场景：一位入职三周的 FDE 提交了第一个触及客户真实数据的拉取请求（PR），是一个把订单从客户 API 同步到数据仓库的脚本。打开一看，你想评论的地方有 14 处。而客户周一上午就要试运行。

常见的捷径有两种。一种是为了省时间自己重写，结果下一次新人还得等你。另一种是留下 14 条看起来同样分量的评论，新人花两天时间从变量名一路改到一个可能弄乱客户数据的 bug，却不知道哪些才真正要紧。

对前线部署工程师（FDE）来说，评审既是代码在客户环境中运行前的最后一道防线，也是每天都在运转的培训渠道。因此，评论怎么写，直接影响新人多快能独立工作，也是外界看得见的、你带人能力的信号。

正确的衡量标准：他们还有多需要你

Google 的代码评审指南明确写出了一个次要目标：提升作者的技能，让他们随着时间推移需要的评审越来越少。换句话说，好的评审不只看抓到多少 bug，还要看同一个人的下一个 PR 里，必须拦下的问题是否变少了。

这个目标与 FDE 团队带新人的方式相吻合。根据 FDE Academy 对入职前 90 天的描述，早期工作会刻意限定范围，让新人在风险仍可控的层面犯错，而不是在旗舰客户身上犯错。

经理会密切跟进，但不会紧到让人窒息。里程碑是新人能够接手一个真实项目、不再需要严密监督的那一刻。

评审正是这种“密切但不窒息”的跟进发生的地方。矛盾在于：客户需要安心，新人需要自己做决定的空间。解法是把两者分开：哪些因为让客户面临风险而必须阻止合并，哪些只是经验之谈。

一个 PR，三类评论

回到那个订单同步脚本。假设它的核心是这样的：

def sync_orders(since):
    orders = client.get("/orders", params={"since": since}).json()
    for o in orders:
        log.info(f"正在同步 {o}")
        db.execute(
            "INSERT INTO orders VALUES (%s, %s, %s)",
            (o["id"], o["email"], o["total"]),
        )

这段代码在演示中能跑。但它有两个会伤害客户的 bug、一个待确认的问题，以及几处纯属外观的小毛病。一组好的评论会把每一类都标得清清楚楚：

issue (blocking)：如果任务在网络故障后重跑，这条 INSERT
会写入重复订单，客户看板上的收入会被算两次。我们需要一种
无论运行多少次结果都一样的写入方式。具体用哪种方案由你决定。

issue (blocking)：这行日志打印了整个订单，包括终端客户的邮箱。
日志通常比数据库有更多人和更多系统在读。只记录订单 id 即可。

question (non-blocking)：客户的 API 有分页吗？如果有，
这个函数可能只拉到第一页。

nit：把 `o` 改名为 `order` 更易读。非必须。

“blocking”和“non-blocking”标签来自 Conventional Comments。这套约定把阻塞性评论定义为：在解决之前会阻止 PR 被接受的评论。

约定的作者认为，打标签能为评审者和作者省下数小时的误解。“Nit”前缀则来自 Google，指技术上应该处理、但无关大局的小问题。

再留意评论写法上的三个细节。每条评论都针对代码（“这条 INSERT 会写入重复数据”），而不是针对人（“你忘了处理重跑”），这符合 Google 的原则：只评论代码，绝不评论作者。

每条评论都附有一句理由，因为理由能帮作者理解你为什么提出这一点，并把背后的原则带到下一个 PR。

第三个细节更微妙。对重复写入的 bug，你指出问题，让作者自己选择修法；按照 Google 的说法，这样往往能让作者学到更多。

对日志里的邮箱，你则直接说明该怎么做，因为正确答案只有一个，而客户数据不是做实验的地方。什么时候让新人自己想清楚、什么时候直接指路，是带教中最难的部分。

什么时候点批准？

现在重新清点最初那 14 条评论。假设分类之后，2 条是阻塞性的，3 条是问题或建议，9 条是 nit。新人一个下午就修好了 2 个阻塞问题，回答了 3 个问题，PR 在周末前合并；9 条 nit 放进之后的清理 PR。

这正是 Google 推荐的批准标准：只要变更确实改善了代码库的整体健康度，就倾向于批准，即使它并不完美。

评审者追求的是持续改进，而不是完美。对 FDE 来说，这个标准还多了一层含义：客户恰好在有风险的地方得到保护，新人也不会在没有风险的地方被卡住。

同一个 bug，对不同的人用不同的剂量

Crafting Tech Teams 上的文章《Benevolent Code Reviews As a Busy Manager》建议，针对提交 PR 的每个人或每对搭档，调整措辞和详细程度。

对入职第一周的新人，关于重复写入的评论可能要写三句话，再附上一个任务重跑的例子。到了第六周，同一个问题只需要一句提问：“如果它运行两次会怎样？”

这句简短的提问是进步的标志，不是偷懒。你在把判断力从自己的脑子里转移到新人的脑子里。

同一篇文章强调，评审应当起到教育、支持和疏通的作用，而人在感到被评判时是学不进东西的。在客户截止日期前甩出一连串严厉的评论，是让新人不再提问的最快方式。

下一个 PR 的五个步骤

第 1 步：识别风险。 读第一行代码之前，先问这个 PR 在客户侧触及了什么：真实数据、个人信息，还是只是一个内部工具。答案决定阻塞门槛设在哪里。

第 2 步：先通读再动笔。 评论之前把整个 PR 完整看一遍，这样才能按严重程度分类，而不是按代码行的顺序评论。

第 3 步：每条评论都按模板写。 每条评论都有标签、针对代码、附一句理由；只有在对客户风险很高时才直接给出修法。

第 4 步：尽早批准。 阻塞问题一解决就批准，nit 推到清理 PR 里。

第 5 步：跟踪趋势。 记录你带的人每个 PR 上的阻塞评论数；如果这个数字逐周下降，说明你做对了。

评审者的常见错误

最常见的错误是替他们改。今天快了，却拖慢了整个季度，因为新人始终没有自己走一遍推理过程。第二个错误是所有评论都不打标签，于是作者把一个变量名和一个会丢数据的 bug 同等对待。

第三个错误出现在客户压力之下：出于焦虑把 nit 升级成阻塞问题，或者反过来，为了赶演示把安全 bug 降级为非阻塞。最后一个错误是对所有人用同一种详细程度：对已经很扎实的人啰嗦，对新人却过于简短。

FDE Academy 描述的 90 天里程碑，即新人能接手真实项目、不再需要严密监督，也是一项值得写进简历的成果，如果你的目标是高级 FDE 或 FDE 负责人岗位。写得具体些：你带过谁走到这个里程碑，你给团队引入了哪些评审约定来帮助他们做到。

面试时，拿出一条你真实写过、带标签和理由的评论，通常比泛泛地声称自己有领导力更有说服力。

好的导师用一个有些反直觉的标准衡量自己的成功：某天新人的 PR 到了你手里，你已经找不到需要阻塞的地方。
