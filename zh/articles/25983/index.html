FDE 交接：为什么一份文档还不够

原标题：FDE Handovers: Why a Document Isn't Enough

Falkster.AI · 2026-11-19 · 约 6 分钟读完

摘要

文章讨论 FDE 交接问题：交接文档只能记录结论，无法承载工程师面对新情况时的条件式判断。作者引用 Marco Di Santo 离开 LivePerson 前的做法——用自己推理真实决策的视频转录训练一个决策 Agent，该 Agent 掌握五类“视情况而定”的问题维度（客户规模、合同结构、风险容忍度、监管环境、续约临近度），可组合出 32 种情境。作者认为这是 FDE 离场前应构建的“离场产物”，并给出五个可自问的问题作为实践起点。

要点

  • 交接文档记录结论，不记录决策过程。
  • Marco Di Santo 用视频转录训练决策 Agent。
  • 五类问题维度可组合出 32 种情境。
  • 决策 Agent 是 FDE 的“离场产物”。
  • 作者列出五个离场前应自答的问题。

Marco Di Santo 本周发布的内容让我一直念念不忘。他在离开 LivePerson 职位之前，构建了一个决策 AI Agent，用他自己推理真实决策过程的视频转录进行训练。标题是我希望自己能写出的一句话：“文档保存的是你当时知道的东西，而 Agent 保存的是你会如何决策。”

简要版本

  • 前沿部署工程（FDE）工作中的交接文档记录的是事实，而不是如何决策。
  • 面对某类客户、在某种合同、某种风险等级下该说什么：这种技能会随着工程师一起离开。
  • Marco Di Santo 在离开 LivePerson 之前构建了一个决策 AI Agent。
  • 它保存了他在任何通话之前都会问的五个“视情况而定”的问题。
  • 如果即将离开的工程师在离职前构建了正确的系统，新站点接手的工程师就不需要靠猜。

文档问题并不是文档问题

在我做前沿部署工程工作时接触过的客户站点，即将离职的工程师总会留下一些东西。一个 Confluence 页面、一份 Notion 文档、一条很长的交接 Slack 消息。这些文档并不差。它们记录了当时真实的情况。边界情况。集成的怪癖。干系人的名字。

但它们没有记录的是：工程师会如何决策下一次尚未发生的通话。

这种推理是无法写下来的。不是因为工程师不擅长写作，而是因为这种推理不是一个句子，而是一个条件判断。它取决于这个客户是企业级还是中型市场。它取决于合同是基于用量的还是固定月度席位费。它取决于他们距离续约有多近，以及这里的失败是否会变成一个流失的故事。

一份文档只能保存一个答案。而上面这五个维度会产生 32 种组合。没有任何交接文档能覆盖 32 种组合。文档给出的只是它撰写时那个特定情境下的答案，然后指望你自己去举一反三。

而这种举一反三，就是那一周的“考古”工作。

Marco 构建了什么

Marco 构建了一个用他自己训练的决策 AI Agent。他录制了自己在 LivePerson 推理真实决策过程的视频。比如客户询问是否要在数据层尚未就绪时扩大用量。比如平台表现不佳时的续约。比如为了赶上上线截止日期而请求跳过某个配置步骤。

这个 AI Agent 基于五种问题类型运行：

  • 按客户规模和战略重要性
  • 按合同结构（用量、席位、基于结果）
  • 按客户声明的风险容忍度
  • 按监管环境（医疗、金融服务）
  • 按距离续约的远近

5 个问题

这些并不是别人告诉这个 AI Agent 要使用的类别。它们是 Marco 在做决策时自然会想到的维度。转录内容揭示了他早已在隐性使用的结构。

其结果不是一个回答一般产品问题的聊天机器人，而是一个狭窄的系统，它以 Marco 的方式推理，被约束在 Marco 实际做出的决策范围内，并且局限于他实际工作的领域。

为什么这对 FDE 尤其重要

FDE 工作有一个大多数产品工作不具备的特性：项目合作会结束。工程师会离开现场、离开客户账户、离开客户关系。数月现场工作积累起来的一切都会随工程师一同离开。信任、机构知识，以及关于这位客户实际会用什么而非他们说想要什么的判断。

这不是一个能通过文档解决的问题，因为问题并不在于缺少文档。本站的 FDE Transition 系列涵盖了项目开始时你需要的东西：理解代码库契约，了解已部署的 Agent 是什么样子。这些是抵达时的产物。而决策 Agent 是离开时的产物，它不在任何清单上。

代理机构的知识传递缺口：在客户现场最后一天关门离开的人，带走的远不止笔记本电脑。他们带走了让自己卓有成效的条件式推理。文档是结论的记录，而决策 Agent 是过程的记录。

离开之前应该构建什么

用于 FDE 交接的决策 Agent，其实际形态比听起来简单。Marco 使用了视频转录。这之所以有效，是因为它能挖掘出你不会想到要写下来的推理过程。你也可以通过一次对自己的结构化访谈来完成：

五个值得录下自己回答的问题：

  • 在哪三种情况下，你会建议放慢节奏而不是与客户继续推进？
  • 哪一种集成捷径是安全的，哪一种看起来安全但实际上不安全？
  • 这位客户说他们想要什么，而那其实并不是他们真正需要的？
  • 客户方谁应该参与每一个重大决策讨论，谁不应该参与？
  • 需要满足什么条件，你才会建议完全暂停这个项目合作？

这些问题的答案不在任何文档里。如果你不把它们记录下来，它们就是下一个项目第一周要让别人付出的代价。

承诺

我还没有为自己的交接构建过决策 Agent。这篇文章在一定程度上就是下次要这么做的承诺。这个产物的形态来自 Marco 的文章，而非我自己的实践。

如果你正在结束一个现场项目，最后一周你能构建的最好的东西不是一份更好的状态文档，而是一个承载着你本会如何决策的系统。

常见问题

在 FDE 交接的语境中，什么是决策 Agent？+

决策 Agent 是一个小型 AI 系统，它学习的不是某个人得出了什么结论，而是这个人如何推理做出决策。在 FDE 交接中，它捕捉的是文档无法承载的“视情况而定”的逻辑：哪种建议适用于哪种客户规模、哪种合同类型、哪种风险偏好。Marco Di Santo 在离开 LivePerson 的职位之前，用自己推理过程的视频转录构建了一个这样的 Agent。

为什么交接文档对 FDE 工作不起作用？+

交接文档记录的是结论。它告诉下一位工程师今天哪些事情是成立的。但它没有告诉他们，当情况发生变化时，明天该如何决定该做什么。产生这些结论的推理过程随着工程师一起离开了。在新客户现场的第一个星期就变成了考古：翻阅工单和讨论串，试图还原的不是发生了什么，而是前任是如何思考的。

Marco Di Santo 使用的五种“视情况而定”的问题类型是什么？+

按客户规模、按合同结构、按风险偏好、按监管环境，以及按距离续约的远近。每一个都是正确建议会随之变化的维度。文档只记录某一种组合下的答案；而 Agent 可以承载完整的决策树。

这与写出更好的文档有什么不同？+

更好的文档记录的仍然是输出。差距不在于数量或格式，而在于推理链条根本没有被捕捉下来。决策 Agent 的训练素材是这个人出声推理的过程，而不是他们写下的结论。Marco 描述的视频转录方法，就是在这种推理随人离开之前将其捕捉下来的一种方式。

这对 falkster.com 上的 FDE Transition 系列意味着什么？+

FDE Transition 系列涵盖的是 FDE 工程师在客户项目开始时需要的东西：理解代码库契约，以及部署在客户现场的 Agent 是什么样子。而交接问题则是项目周期的另一端。离开之前构建的决策 Agent，与到达之前写好的代码库契约互为补充。
