设计支持当日停用（deprovisioning）的 SSO

原标题：Design SSO with same-day deprovisioning

FDE Interview Prep · 2026 · 约 7 分钟读完

摘要

这是一篇 FDE 面试练习题解析，主题是如何设计带当日撤销能力的 SSO。文章指出常见误区：只画登录流程，忽略已存在的会话——新登录无法终止旧会话，离职者可继续使用。作者建议把问题拆为认证与账号供给两部分，并给出模型答案：澄清客户 IdP 与 SCIM 能力、按域名路由登录、用 SCIM 停用事件统一撤销会话与 API 令牌、无 SCIM 时以 8 小时上限兜底、每小时对账弥补漏发事件，并列举每条访问路径的失效时限。

要点

  • 核心论点：SSO 设计必须覆盖会话撤销，而非只画登录流程。
  • 建议把问题拆成认证与账号供给两部分作答。
  • 模型答案用 SCIM 停用事件统一撤销会话、令牌并移交资产。
  • 无 SCIM 时以 8 小时会话与令牌上限约束风险。
  • 每小时对账任务兜底漏发的 SCIM 事件。

如何回答

新登录对已存在的会话没有任何影响，所以一个早上离开的人仍能在昨天的浏览器标签页里继续工作，直到你撤销该会话。这正是干净的 SSO 架构图所遗漏的那一半，而题目明确要求回答的也正是这一半。职位描述本身就体现了身份认证的重要性：截至 2026 年 9 月，Okta 的招聘职位列出了身份协议，其中包括 、 和 。来源 1Senior Forward Deployed Engineer - Okta for AI Agents发布方Okta (Greenhouse)来源类型公司招聘信息来源 2Principal Forward Deployed Engineer - Okta for AI Agents发布方Okta (Greenhouse)来源类型公司招聘信息来源 3Principal Forward Deployed Engineer (Singapore)发布方Okta (Greenhouse)来源类型公司招聘信息

所以在画任何东西之前，先把问题一分为二，并且把这个划分说出来。认证回答的是“这个人现在是谁”，而配置管理回答的是“这个人是否应该在这里拥有账户，以及是什么角色”。SSO 解决的是前者。移除访问权限属于后者。

  • 明确客户情况。 用哪家身份提供商、SAML 还是 OIDC、他们的目录能否推送 SCIM，以及“有人离职的那一天”对他们的安全团队意味着什么：是 HR 记录离职的那一刻，还是当天结束之时。
  • 登录。 服务提供商发起的登录，通过已验证的邮箱域名路由，每个客户一个 IdP 连接。说出你从不跳过的断言校验项。
  • 配置管理。 用 SCIM 处理创建、更新和停用；即时创建仅作为兜底方案。
  • 端到端的取消配置。 停用事件会禁用用户、撤销会话和 API 令牌，并将其拥有的对象移交给某人。说明在没有 SCIM 时缺口有多大，以及你如何将其限定在可控范围内。
  • 角色。 一张按客户划分的表，将目录组映射到你的角色，默认采用最小权限原则。
  • 故障场景。 IdP 宕机、遗漏的 SCIM 事件、紧急管理员账户。

最后用一个具体例子收尾：一个客户、OIDC 登录，以及一个结束活跃会话的 SCIM 停用操作，并通过测试演示。

陷阱在于只画出一张干净的 SAML 时序图，之后便什么都没有。每一个进入你产品的途径，都需要对离职者保留访问权的时间设定上限，而且你应该能逐一说明。

追问

当你的第一个回答说完后，面试官接下来可能会问的问题。

  • 有人离职当天，其活跃会话会怎样处理？
  • 客户的身份提供方宕机了，登录会怎样？
  • 他们目录中的用户组与你的角色不匹配，如何映射？

常见的错误回答

  • 只设计了 SSO，却忘了取消开通（de-provisioning）。

两分钟内回答

写出你会大声说出的答案。计时从你说出第一个字开始。

与标准答案对比

标准答案

澄清。我会问四件事：用的是哪家 IdP（比如 Okta 或 Microsoft Entra ID）、他们能否运行、“离职当天”是指 HR 记录的那一刻吗，以及我们的产品是否有人可以创建的 API 令牌或集成。我会假设、SCIM，以及一个我们掌控的目标：在我们收到他们的 SCIM 停用通知后，访问在

5 minutes

内终止。在此之前有两个缺口属于他们，我会分别记下：HR 的记录多快到达他们的 IdP，这是他们的流程；他们的 IdP 多久向我们推送一次变更，这是他们产品的调度，不是我们的。

登录。一张

tenant_idp

表保存每个客户的 issuer、client ID、已验证域名和用户组映射。登录页要求输入邮箱，通过已验证域名找到租户，然后针对该 issuer 发起带 PKCE 的授权码流程。在回调中，我按

OpenID Connect Core, section 3.1.3.7

验证 ID 令牌：用 issuer 的 JWKS 验证签名，

iss

,

aud

,

exp

和

nonce

.

许多大型客户运行，所以两者我都支持。对于 SAML，我使用维护良好的库，并检查签名、audience、

NotOnOrAfter

,

InResponseTo

以及重放缓存。IdP 发起的登录（来自他们门户中的磁贴）没有

InResponseTo

，所以我会把它们重定向到 SP 发起的流程中。我会读取他们的元数据 URL，并在其签名证书到期前

30 days

发出告警，因为证书过期会导致整个租户被锁死。

登录时通过

(tenant_id, iss, sub)

查找用户，或通过 SCIM 的

externalId

，绝不能通过电子邮件，因为地址会被重命名和重新分配；新员工获得离职同事的地址时，绝不能继承该账户。被禁用的用户在登录时保持禁用状态；即使租户选择启用即时创建功能，也绝不会重新激活该用户。一旦租户启用 ，我会关闭其已验证域名的所有其他登录方式：密码登录、密码重置、魔法链接和社交登录。在 SSO 之前设置的密码会被作废，而不是处于休眠状态。唯一的例外是下文的紧急管理员通道。

配置管理。 我们按照 RFC 7644 提供 SCIM 端点，使用 RFC 7643 中的 User 架构。他们的目录系统创建用户、更新属性和组成员关系，并在用户离职时发送

PATCH /Users/{id}

以及

active: false

，或发送

DELETE

，之后该用户将返回 404。该端点使用我们可以轮换的每租户 bearer token。停用操作是幂等的，因为他们的目录系统会重试，而随后的

PATCH

以及

active: true

可以重新启用重新入职的员工，但不会恢复其旧的会话或令牌。两个离职调用都进入同一个处理程序：

def deactivate(tenant_id: str, user_id: str, source: str) -> None:
    with db.transaction():
        if users.status_for_update(tenant_id, user_id) == "disabled":
            return  # their directory retried; nothing left to do
        users.set_status(tenant_id, user_id, "disabled")
        users.bump_session_epoch(tenant_id, user_id)  # for JWTs
        sessions.revoke_all(tenant_id, user_id)
        tokens.revoke_all(tenant_id, user_id)  # API tokens, OAuth
        jobs.pause_owned_by(tenant_id, user_id)  # schedules, syncs
        outbox.add("handoff", tenant_id, user_id)  # runs after commit
        audit.log("user.deactivated", tenant_id, user_id,
                  source=source)

权限撤销与交接请求一起提交。对其所拥有资源的缓慢重新分配随后从 outbox 运行，遵循客户关于谁继承资源的策略，因此它绝不会回滚撤销操作，崩溃也不会丢失该操作。

会话存储在服务器端，每个请求都会检查会话，这正是使第一切片测试成立的关键。如果 API 必须使用 JWT，每个请求还会检查每个用户的

session_epoch

，该值由

deactivate

递增。一个存活

10 minutes

且没有此类检查的令牌，会让离职者在

10 minutes

内仍可访问，我会说出这个数字而不是隐瞒它。在客户的 IdP 支持的情况下，我还接受

OIDC Back-Channel Logout

，当他们的 IdP 结束会话时，我们的会话也随之结束；它不能替代 SCIM 停用。

没有 SCIM 的情况。 浏览器的缺口是会话生命周期，所以我设置上限（

max_session=8h

，然后在他们的 IdP 重新认证）。任何不会返回 IdP 的访问完全没有边界，因为它永远不会自行结束：个人 API 令牌、授权、移动端刷新令牌。因此，对于没有 SCIM 的租户，个人令牌和 OAuth 授权在

max_token_age=8h

后过期，或被租户拥有的服务账户取代，而移动端刷新令牌仅在对他们的 IdP 的刷新仍然成功时才被接受。我会以书面形式向安全团队提供这两个数字。

每一条访问途径及其关闭时间。 每条进入路径都有一个我可以明确说明的边界。

访问途径关闭时间
浏览器会话SCIM 停用后的下一个请求；没有 SCIM 时，为 8 小时会话上限
使用 JWT 的 API下一个请求，通过 session_epoch；否则为令牌生命周期
个人令牌和 OAuth 授权停用时；没有 SCIM 时，为 8 小时
移动端刷新令牌停用时；没有 SCIM 时，为在他们的 IdP 的下一次刷新
错过的 SCIM 事件下一次每小时对账

角色。 一个

group_role_map(tenant_id, idp_group, role)

由客户管理员编辑的表。未映射的组不获得任何访问权限，而不是默认的查看者角色，并且每次映射变更都会被审计。

故障处理。 如果 IdP 宕机，现有会话在过期前仍可正常使用，新登录则会失败。我不会让所有人回退到密码登录；每个租户有一名“应急管理员”持有本地凭据，配备硬件 MFA，且每次使用都会触发告警。

SCIM 事件可能被遗漏，因此一个每小时运行的任务会从客户目录的 API 读取用户列表，并停用所有在我方仍处于活跃状态但在其目录中已不活跃或不存在的用户；在其目录中被硬删除的用户视为不活跃。这样，一次遗漏事件的代价最多是一小时，我会把这个目标写在旁边。该任务需要一个只读目录凭据，我会在第一次会议上就向客户的身份团队提出申请，因为审批比写代码更耗时。我按租户衡量停用延迟，即从我方收到 SCIM 请求到该用户最后一次向我方发起请求之间的时长，一旦超出目标就触发告警。

第一片。 一个试点租户、OIDC 登录，以及一个带集成测试的 SCIM 停用功能，测试断言活跃会话在下一次请求时会收到 401。
