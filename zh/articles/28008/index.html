摘要

作者Abhinav Bhatia系统解释前沿部署工程师这一角色：定义、Palantir起源、与解决方案架构师等四种角色的区别、客户现场交付的五个阶段，以及所需技能组合。文章对比Google Cloud、Microsoft、OpenAI和Anthropic的公开招聘描述，指出该角色因AI产品难以从演示走向企业级生产而兴起。

要点

  • FDE受雇于厂商，驻扎单一客户现场，负责把系统交付到生产并反馈产品团队。
  • 术语源自Palantir：Dev面向多客户做单一能力，Delta面向单客户交付多种能力。
  • 公开职位描述反复出现六项职责：发现、构建、集成、评测、证明结果、反馈产品。
  • 与顾问和架构师的关键区别在于FDE拥有客户生产代码并为结果负责。
  • 交付分五阶段：驻场、发现、构建、加固、交接，其中加固通常耗时最长。

前沿部署工程师是 AI 领域招聘广告中最常见的职位之一，却也是解释得最少的职位之一。本部分从基础讲起：这个术语的由来、公开的职位描述提出了哪些要求、这个角色与解决方案架构师、客户工程师、顾问或软件工程师有何区别、一个项目从入驻到交接是如何运作的，以及这份工作所需的技能组合。

前沿部署工程师（FDE）这一职位如今出现在 Google Cloud、Microsoft、OpenAI 和 Anthropic 的公开招聘网站上。在我与合作伙伴的工作中，接下来听到的问题总是同一个：FDE 每天到底在做什么，它与我们已有的技术角色有何不同？

本部分从基础出发回答这个问题。我先从公开职位描述的内容讲起，然后用通俗的语言定义这个角色，追溯这个术语的来源，并将 FDE 与人们经常混淆的四个角色进行比较。接着，我使用与 生产级 Agent 系列相同的虚构公司，讲解一个项目是如何运作的，最后介绍这份工作所需的技能组合。

本系列讲的是这份工作包含什么以及如何做好它，而不是一份教你如何被任何公司录用的指南。

这些内容在 FDE 职位描述中如何体现？

以下是四段直接引用自公开招聘信息的文字：

“……一位嵌入式构建者，弥合前沿 AI 产品与客户内部生产级现实之间的鸿沟。”（Google Cloud，Forward Deployed Engineer IV，GenAI）
“……超越高层架构设计，直接在客户环境中编写代码、调试并共同交付定制的 Agent 解决方案。”（同一则 Google Cloud 招聘信息）
“与战略客户深度合作，详细了解他们的业务挑战和技术需求。”（OpenAI，Forward Deployed Software Engineer）
“验证：用客户认可的度量方式证明成果，而不是靠演示。”（Microsoft，Principal Forward Deployed Engineer）

三个词承载了大部分含义：嵌入式、交付和成果。本文其余部分将逐一展开。

什么是前沿部署工程师？

先给出简单的定义。前沿部署工程师是一种软件工程师，他们在某一家客户的组织内部工作，编写并交付让产品在该客户真实系统上运行起来的代码，并把学到的经验带回构建产品的团队。

现在是更正式的版本，基于上面的帖子整理而成。FDE 是受雇于技术供应商的工程师，被派驻到某个战略客户处执行一段明确的合作项目，负责在客户环境中交付生产系统的技术工作，并充当从一线反馈回供应商产品与工程团队的信息通道。

这个定义有五个部分，每一部分都是你在本系列中会反复遇到的概念：

  • 供应商。 其产品被部署的公司：Google Cloud、OpenAI、Anthropic 等等。FDE 受雇于供应商，或受雇于代表供应商工作的合作伙伴。
  • 合作项目。 一项有起点、有既定目标、有终点的工作。通常以周或月来衡量，并以交接作为结束。
  • 环境。 客户已经在运行的一切：他们的数据平台、身份提供商、网络、安全规则、代码仓库，以及同样重要的——他们的人员和流程。
  • 生产。 真实用户依赖的系统，具备安全保障、监控和支持，并且在 FDE 离开之后仍能持续运行。只在笔记本电脑上成功运行一次的演示不算生产。
  • 反馈闭环。 把一线发现的问题转化为缺陷报告、功能请求和可复用代码的习惯，让产品团队能够据此采取行动。

核心要点：产品团队面向众多客户进行构建，前沿部署工程师被嵌入某一个客户的环境中，把可用的系统推向生产，而一线的洞察则回流到产品团队

一个日常类比会有所帮助。建筑公司派一名工地工程师到客户的场地上，与该场地的地质条件和该客户的施工队协作，直到建筑落成。对应到我们的术语：公司是供应商，场地是客户的环境，建成的建筑是生产系统，而工地工程师发回总部的记录就是反馈闭环。

这个术语从何而来？

这个术语与数据和软件公司 Palantir 关系最为密切。在 2019 年其工程博客的一篇文章《Dev versus Delta》中，Palantir 解释了它最重要的两类工程角色。软件工程师，内部称为“Dev”，隶属于产品开发部门，负责构建平台。前沿部署软件工程师，称为“Delta”，隶属于业务发展部门，负责将这些平台部署给客户。“Delta”这个名字源于公司早期，当时每个业务发展团队都以北约音标字母表中的一个字母命名。

这篇文章用一句话概括了两者的区别：Dev 的关注点是“一项能力，众多客户”，而 Delta 的关注点是“一个客户，多种能力”。

Palantir 的两类工程角色：Dev 构建众多客户使用的一项能力；而 Delta，即前沿部署软件工程师，则把多种能力带给一个客户

这篇文章还探讨了最常见的误解，即 Delta 是顾问。正如文中一位工程师所说，顾问“通常针对特定问题提供一次性的分析、建议或解决方案”，而 Delta 则与客户一起在现有软件产品上构建长期解决方案，并经常将代码回馈到核心产品中。

最近变化的是主题。AI 供应商现在部署的是模型、Agent 平台和 MCP 服务器（Model Context Protocol 服务器，以标准方式向 AI Agent 暴露工具和数据）。Google 的招聘启事直接点明了问题所在：FDE 要解决“阻碍生产落地的各种障碍，包括解决集成复杂性、数据就绪性问题以及阻碍 AI 达到企业级成熟度的状态管理问题”。我的看法是：在别人的系统上，从可运行的演示到生产系统之间的鸿沟，正是嵌入式工程师体现价值的地方，这也是 AI 供应商采用这一职位名称的原因。

公开的职位描述到底要求什么？

我并排阅读了 Google Cloud（面向客户和面向合作伙伴的两个职位）、Microsoft、OpenAI 和 Anthropic 的公开 FDE 招聘启事。措辞各不相同，但有六项职责反复出现。

Google Cloud、Microsoft、OpenAI 和 Anthropic 公开的前沿部署工程师招聘启事中反复出现的六项职责，以及明确提及各项职责的招聘启事

  • 发现与界定范围。 Google 要求“有主持客户技术发现会议的经验”；Microsoft 要求 FDE“确立问题陈述、基线、商定的成功衡量标准以及计划”。第 2 部分涵盖这一内容。
  • 构建生产系统。 Google 提到“多 Agent 系统、MCP 服务器”；Anthropic 提到“MCP 服务器、子 Agent 和 Agent 技能”。第 4、6 和 7 部分涵盖构建过程。
  • 与现有系统环境集成。 Google 将此称为“Google AI 产品与客户现有基础设施之间的连接组织，包括 API、遗留数据孤岛和安全边界”。第 3 和第 5 部分涵盖这一内容，我关于将 Gemini Enterprise 接入 Databricks Genie的文章就是一个实际案例。
  • 评估与观测。 Google 要求具备“评估流水线和可观测性框架”以及 LLM 原生指标（针对大语言模型的特定度量指标，如每秒 token 数和每次请求成本）方面的知识。第 9 部分涵盖性能方面的内容。
  • 证明成果。 Google 将工作与“可衡量的投资回报率（ROI）”挂钩，Microsoft 则要求采用客户认可的衡量方式。第 10 部分涵盖这一内容。
  • 向产品反馈。 每份招聘启事都有类似的要求。Google 要求 FDE 将“可复用的现场模式和摩擦点”转化为“正式的产品功能请求”。第 8 部分介绍具体做法。

还有两个实际细节反复出现。Anthropic 和 OpenAI 都提到需要频繁出差到客户现场（分别为 25% 到 50%，以及最高 50%）。而 Google 的合作伙伴 FDE 职位描述的则是与“战略 AI 合作伙伴及其自己的 FDE 团队”合作完成的同样工作，说明该角色在合作伙伴一方也存在。

FDE 与我已知的那些角色有什么不同？

FDE 与四个常见角色有所重叠。我用同样的方式逐一介绍，并配以贯穿本系列的 Acme 项目中的简短例子。

  • 解决方案架构师。 设计产品应如何契合客户的系统，通常同时负责多个客户，且主要通过架构图、评审和指导开展工作。在 Acme，解决方案架构师会建议采用 BigQuery 与 Databricks 的联邦查询，而不是复制数据。当客户自己的团队将负责构建时，选择这个角色。
  • 客户工程师。 这是 Google Cloud 对技术售前工程师的称呼，在交易成形阶段负责运行评测、演示和概念验证。在 Acme，客户工程师可能会演示一个回答营销问题的 AI Agent。在尚未做出承诺之前，选择这个角色。Google 还招聘一个 AI Outcome Customer Engineer 职位，该职位“弥合售前协议成形与售后执行之间的差距”，并“隶属于我们的前沿部署工程（FDE）组织”，这表明这两个角色已经非常接近。
  • 顾问。 分析问题并推荐解决方案，通常有时间限制，且往往独立于任何一家供应商的产品。在 Acme，顾问可能会出具一份报告，说明营销部门和供应链部门为何在活动上意见不一。当客户主要需要做出决策、之后再进行构建时，选择这个角色。
  • 软件工程师（产品团队）。构建所有客户都会使用的功能。在 Acme，这就是修复 FDE 所报告 bug 的供应商工程师。当修复应属于面向所有人的产品时，选择这个角色。

在我看来，各角色的定位是：顾问和 FDE 服务于单一客户，产品软件工程师和客户工程师服务于众多客户；顾问和架构师主要提供建议，FDE 和软件工程师交付生产代码

我的看法：最清晰的判断标准是这个问题——“谁拥有在这个客户生产环境中运行的代码，谁对结果负责？”如果答案是 FDE，同时客户自己的团队参与其中，那么你面对的就是前沿部署工作。如果答案是“客户按照我们的建议来做”，那就是架构或咨询工作。

一个项目是如何运作的？

每个职位描述都勾勒出同样的轨迹，即使他们对步骤的命名各不相同。Microsoft 的职位描述使用 Discover、Build 和 Validate。我将其分为五个阶段，因为这条轨迹的中段——把原型变成可用于生产环境的东西——正是大多数项目停滞的地方。

一个项目如何运行：嵌入、发现、构建、加固和交接，全部在客户的环境内进行；每个完成的使用案例都可以引出下一个，并且一线洞察会持续流向产品团队

  • 嵌入。 获得对系统、数据和人员的访问权限。了解谁负责什么。第一天，FDE 往往只有一台笔记本电脑、没有任何权限，所以这个阶段主要是提请求、做介绍和阅读文档。
  • 发现。 把业务问题转化为可构建的东西：清晰的问题陈述、一个成功指标（双方都认可的一个数字，用来判断是否成功）、第一个使用案例，以及一份刻意暂不去做的事项清单。
  • 构建。 在几天内用真实数据做出原型，与客户自己的工程师一起构建，他们日后将负责维护它。原型的目的是快速学习，往往会被有意丢弃。
  • 加固。 补齐生产环境所需的一切：身份认证、防护栏、评测、追踪、成本控制和部署流水线。这通常是最长的阶段。
  • 交接。 编写运维手册（告诉客户团队如何运行和修复系统的文档），指定负责人，培训团队，并根据发现阶段确定的基线审查结果。

图中的周数仅作示意，针对的是第一个使用案例。实际项目差异很大，而一次良好的交接往往会直接引出下一个使用案例。

在 Acme，这一切是什么样的？

下面是贯穿全文的示例。Acme Consumer Brands（虚构公司）开展了一次广告活动。市场部门说它是成功的，供应部门说它是失败的，而双方都没错。广告数据存放在 BigQuery（Google Cloud 的数据仓库）中，而交付数据存放在 Databricks（一个独立的数据平台）中。没有人把两者放在一起对比过。

想象你是嵌入 Acme 的 FDE。生产就绪的 Agent 系列就是那次构建：三个 Agent 无需复制数据即可跨两个数据源回答问题。

生产就绪 Agent 系列的构建全景图：用户在 Gemini Enterprise 中提问，路由 Agent 拆分问题，市场 Agent 以用户身份读取 BigQuery，供应 Agent 以用户身份读取 Databricks，最终返回一个经过校验的答案

Agent 系列中的路由器：让代码选择路径构建了路由器，系列介绍则完整讲解了整个系统。

本系列涵盖这次构建周边的一切，每个阶段都会产出具体的成果：

Acme 项目中每个阶段的产出，以及本系列和生产就绪 Agent 系列分别在哪里讲解这些内容

请注意，这项工作中有多少部分并不是 Agent 代码。在第一个 Agent出现之前，你需要访问两个由不同团队拥有的数据平台、一个达成共识的问题，以及一个能衡量答案是否有效的指标。Agent 完成工作之后，工程工作仍在继续：Databricks 的按用户访问控制（Agent 的身份管理）、发布门禁（作为发布门禁的评测）以及向真实用户的分阶段发布（交付给用户）。

反馈循环在 Acme 也有体现。举例来说，当供应经理提出一个冗长的多部分问题时，路由器超时了。这个症状有两种可能的原因，而 FDE 的职责就是查明是哪一种。

实践中的反馈循环：Acme 处的一个症状被复现并隔离；如果问题出在 Acme 自己的环境中，就在那里修复；而如果是产品缺陷或功能缺口，则会形成一份报告，由产品团队修复并发布给所有客户

如果原因出在 Acme 的环境中，比如防火墙规则或规格不足的数据仓库，你就在那里修复它。如果是产品缺陷或缺失的功能，同样的最小复现就会成为一份产品团队可以据此行动的报告。第 8 部分会详细讲解这个循环，包括一份缺陷报告模板。

这份工作需要哪些技能？

招聘启事要求的能力范围很广。Google 的最低任职资格包括：使用 Python 进行软件开发、利用向量数据库为结构化和非结构化数据构建管道、检索增强生成（RAG：获取相关文档并将其连同问题一起提供给模型）、将 AI 解决方案推向生产环境、在云平台上设计 AI 系统架构，以及主持需求探索会议。其优先任职资格还增加了多 Agent 框架（点名了 LangGraph、CrewAI 和 ADK）以及诸如 ReAct（模型推理、调用工具并读取结果的循环）之类的模式。AI Outcome Customer Engineer 的招聘启事还增加了代码调试、企业系统集成，以及“将深层技术集成问题转化为业务影响”的能力。

我把这些归纳为五大类：

公开招聘启事所要求的技能组合，分为五组，以及本系列和 Agent 系列中覆盖每一组的相关部分

我的看法：很少有人一开始就在这五个方面都很强。在与合作伙伴的合作中，我看到人们从两个方向进入这项工作。有些是正在学习主持需求探索会议并与高管沟通的资深工程师；另一些是正在学习交付生产级代码的资深面向客户的架构师。两条路径都可行，本系列的写作方式也让你可以从任意一条路径入手。如果你从未构建过 Agent，请在阅读本篇的同时阅读Agent 到底是什么。

动手试试：把一份真实的职位描述映射到项目交付流程

理解这个角色的最佳方式是仔细阅读真实的招聘启事。下面这个简短的脚本使用简单的关键词，将职位描述的各行归类到五个交付阶段中。它只需要 Python 3，无需任何额外的软件包。将其保存为

import sys

STAGES = {
    "embed": ["embed", "on-site", "travel", "relationship"],
    "discover": ["discovery", "scope", "problem statement", "success measure", "feasibility"],
    "build": ["prototype", "build", "code", "ship", "integrat", "mcp"],
    "harden": ["production", "evaluation", "observability", "security", "latency", "tracing"],
    "hand over": ["best practice", "adoption", "long-term", "runbook", "train"],
}
FEEDBACK = ["feedback", "feature request", "roadmap", "product and engineering"]

text = sys.stdin.read().lower()
for line in [l.strip() for l in text.splitlines() if l.strip()]:
    hits = [s for s, words in STAGES.items() if any(w in line for w in words)]
    if any(w in line for w in FEEDBACK):
        hits.append("feedback loop")
    print(f"{', '.join(hits) or '(none)':<32} {line[:60]}")

将任意公开的 FDE 职位描述中的职责部分复制到一个名为

posting.txt

的文件中，每行一条职责，然后运行

python3 map_posting.py < posting.txt

。使用下方链接的 Google Cloud FDE IV 职位中的五条职责，我得到的结果是：

build, harden                    serve as a developer for complex ai applications, transition
build, harden                    architect and code the connective tissue between google’s ai
build, harden                    build high-performance evaluation pipelines and observabilit
feedback loop                    identify repeatable field patterns and friction points in go
build, hand over                 co-build with customer engineering teams to instill google-g

看第三行。脚本把它标记为“build”，仅仅因为句子以“build”一词开头，尽管这条职责实际上是关于加固的。关键词匹配很粗糙，而这正是这个练习的意义所在：有用的部分是你亲自阅读每条职责，并判断它属于项目合作的哪个阶段。还要注意，这份职位描述中没有任何一行对应“embed”或“discover”；它把发现阶段放在了任职要求里。接下来试试这些：

  • 用两家不同公司的职位描述运行它，比较各自侧重哪些阶段。
  • 增加一个“prove”阶段，关键词包括“roi”、“baseline”和“measur”。

可能出什么问题

  • 滑向咨询工作。 如果几周过去了，只有幻灯片，客户系统上却没有可运行的代码，那么这次合作已经变成了咨询性质的工作。尽早让原型跑在真实数据上。
  • 在自己的环境里构建。 一个只能在供应商的测试项目中运行、却无法在客户的网络和身份规则下运行的系统，算不上已部署。一旦获得访问权限，就尽快在实际运行的地方进行构建。
  • 自己变成系统。 如果只有 FDE 能操作或修复所构建的东西，那么交接就失败了。从第一周起就与客户的工程师结对工作，并随手编写运维手册。
  • 反馈沦为轶事。 “某位客户不满意”不会改变产品路线图，你悄悄构建了两次的临时解决方案同样不会。Microsoft 的职位描述要求 FDE 带回的是模式而非轶事，并要有复现和度量作为支撑。
  • 没有商定的衡量标准。 如果在发现阶段没有人写下基线和成功指标，那么无论系统多么出色，你都无法在最后证明成果。

我们学到了什么？

  • 前沿部署工程师是由供应商或合作伙伴雇用的软件工程师，在某一客户的系统内部工作，在那里交付生产系统，并把所学反馈给产品团队。
  • 这个术语与 Palantir 关系最为密切，在那里，前沿部署工程师的关注点是“一个客户，多种能力”，而产品工程师的关注点是“一种能力，多个客户”。
  • Google Cloud、Microsoft、OpenAI 和 Anthropic 的公开职位描述共有六项职责：发现与界定范围、构建、集成、评估与观测、证明成果，以及向产品团队反馈。
  • 区分 FDE 与架构师或顾问的最明确标准是：谁拥有客户生产环境中运行的代码，谁为成果负责。
  • 一次合作会经历 embed、discover、build、harden 和 hand over 几个阶段，而加固通常是最长的阶段。
  • 很少有人能在全部五类技能上都表现出色，而且人们进入这一领域时，要么来自工程背景，要么来自面向客户的岗位。

接下来会怎样？

一次项目合作的成败取决于最初两周。在第二部分，探索：从业务问题到可构建的东西中，我们会与 Acme 的市场和供应链团队坐下来，撰写问题陈述和成功指标，选择第一个用例，决定拒绝哪些内容，并产出一份一页纸的项目简报。
