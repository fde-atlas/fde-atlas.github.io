FDE 评测怎么做：Intercom 岗位解读与评测集实战

FDE Times · 2026-10-24 · 约 5 分钟读完

摘要

文章以 Intercom 在都柏林招聘前沿部署软件工程师的启事为切入点：岗位承诺为客户 AI 客服智能体 Fin 带来可衡量的业务成果，却未给出任何具体指标，定义衡量方式的责任落在 FDE 身上。作者指出 Fin 的公开数字（开箱即用解决率 51%、前 30 天平均 56%）只是平均值，不能代表具体客户，靠谱做法是用客户真实对话构建评测集，在首次运行前确定主指标与基线。文中给出一个订单查询智能体的示例：30 段测试对话，主指标为无需转人工的解决率，回答准确率作为不可下降的次要指标；通过分析失败用例（如订单号格式问题）修复后，解决率从 60% 提升到 83% 且无回归。文章还提醒三个常见错误：事后选指标、只看解决率、评测集缺乏真实用例，并说明如何把这套方法写进简历与面试故事。

要点

  • Intercom 的 FDE 招聘承诺可衡量成果，却未给出任何具体指标。
  • Fin 公开的 51% 与 56% 是平均值，不代表具体客户的数字。
  • 应基于客户真实对话建立评测集，运行前先定基线与主指标。
  • 示例中修复订单号格式问题后，解决率从 60% 升至 83% 且无回归。
  • 三大错误：事后选指标、只看解决率、评测集缺少真实用例。

Intercom 拿基线检验 Fin 的每次改动，优秀的 FDE 也会把这个习惯带到每个客户身上。

要点速览

  • Intercom 的 FDE 招聘启事承诺可衡量的业务成果，却没有给出任何目标，定义衡量方式的责任落在 FDE 身上。
  • Fin 公开的数字是开箱即用 51%、前 30 天平均 56%，但这两个数字都不是你所服务客户的数字。
  • 靠谱的回答是用客户自己的对话建立评测集，在第一次运行前就定好基线和主指标。

Intercom 在都柏林招聘前线部署软件工程师（Forward Deployed Software Engineer），招聘启事许下了一个大承诺：确保公司的客服 AI 智能体 Fin 带来真实、可衡量的业务成果。可是把页面读到底，找不到任何一个具体目标。

这个空白可以看作这份工作的第一道考题。没有人说“你必须达到这个数字”时，前线部署工程师（FDE）就得自己决定衡量什么、怎么衡量、和什么做对比。

这种局面来得很早。

启事提到要与 Fin 的战略客户紧密合作，理解他们的业务问题和技术需求。到了客户现场，你几乎一定会听到这样一个问题：“对我们来说，Fin 能解决百分之多少？”本文介绍如何用评测集而不是承诺来回答它。

公开数字不是客户的数字

有两个公开数字值得记住。Anthropic 的案例研究称，Fin 在任何定制之前，开箱即用的解决率为 51%。AWS 的案例研究称，客户在前 30 天内平均达到 56%。

两个数字不同，是因为它们由不同来源在不同时间点测得。两者都是平均值，对坐在你对面的零售商或保险公司来说，都说明不了什么。

如果把“56%”当成保证，一旦客户的真实数字更低，他们记住这句话的时间会比记住任何演示都长。专业的回答是：“我们会用你们自己的对话来测，然后报告数字。”

Intercom 自己怎么衡量？

方法现成就有，而且来自 Intercom 自己。据 Anthropic 的案例研究，Fin 的每一次改动，从小调整到大更新，都要与生产环境中运行的基线做严格对比测试。测试同时看多项指标：回答准确率、解决率、客户满意度和回复质量。

Intercom 把这种做法称为评测驱动交付（eval-driven delivery），并表示这与其 AI 研究团队打造和打磨产品时遵循的是同一套方法。它的 Evals 产品用基于客户自己对话构建的模拟场景来测试 Fin 的行为。

Intercom 的定义很简洁：一个 Eval 就是一组有名称的 Simulation，即多轮测试对话。在 Fin 团队工作的机器学习科学家 Pedro Tabacof 写道，如果你认真对待 AI，就必须认真对待评测。

示例：针对“我的订单在哪”的 30 个用例评测

假设客户是一家零售商，智能体需要通过内部 API 回答订单问题。在动提示词或代码之前，先照 Tabacof 对 A/B 测试的建议做：开始前确定主指标。

这里的主指标是无需转人工客服就解决的对话占比。回答准确率是不能下降的次要指标：如果解决率上升而回答准确率下降，这次改动就被否决。

取 30 段订单相关对话，逐一标注预期结果，然后写一个小型运行器：

import json

# 每行：一段多轮测试对话 + 预期结果
# {"id": "o-07", "turns": ["我的订单 #A-1029 到哪了？"], "expect": "resolved"}
CASES = [json.loads(line) for line in open("evals/orders.jsonl")]

def run(agent, cases):
    results = {}
    for c in cases:
        out = agent.converse(c["turns"])
        results[c["id"]] = {"ok": out.outcome == c["expect"],
                            "reason": out.failure_reason}
    return results

def rate(results):
    return sum(r["ok"] for r in results.values()) / len(results)

baseline = json.load(open("evals/baseline.json"))  # 上一次运行的结果
current = run(agent, CASES)
regressions = [k for k, r in current.items()
               if baseline[k]["ok"] and not r["ok"]]
print(f"{rate(baseline):.0%} -> {rate(current):.0%}，回归：{regressions}")

最关键的是

regressions

这一行。总体比例上升，仍可能掩盖几个原本通过、现在失败的用例，而客户最先注意到的正是这些。

修之前先读失败用例

假设第一次运行解决了 30 个用例中的 18 个，即 60%。这个结果就是基线。此时最有价值的事不是改提示词，而是读完 12 个失败用例，按原因归类。

在这个例子里，有 7 个失败是因为用户把订单号输成“#A-1029”，而 API 只接受“A1029”。2 个失败是因为 API 超时，还有 3 个问的是订单范围以外的事。

最大的一组说明了该先修什么。修复只需一行，在查询函数开头把订单号规范化：

order_id = re.sub(r"[^A-Za-z0-9]", "", raw_order_id)  # "#A-1029" -> "A1029"

下一次运行达到 30 个中的 25 个，即 83%，回归列表为空。剩下 5 个属于另外两组，已经整理成下一轮的工作。

在真实客户那里再做一遍

面对真实客户，步骤不变。以客户的真实对话为来源，正如 Intercom 的 Evals 用客户对话构建场景；再请客户那边懂业务的人一起标注，因为关于他们的退款政策，哪种回答才算正确，你自己无从判断。

然后在第一次运行前，把主指标和次要指标写进一份客户也会读的文档。每次改动，哪怕只改一行提示词，都要对照基线重跑，就像 Intercom 对 Fin 本身所做的那样。

这个顺序也回答了谁来定目标的问题。如果客户一开始就认可了主指标，最终数字就是双方都承认的结果，而不是 FDE 给自己打的分。

需要避免的错误

第一个错误是看到结果后再选指标。先跑，再挑最好看的数字来报告，是失去信任最快的方式，而事先确定指标的建议正是为了防止这一点。

第二个错误是只看解决率。Intercom 同时衡量准确率、满意度和回复质量，因为一个用错误答案“解决”对话的智能体，比把对话转给人工的智能体更糟。

第三个错误是评测集里全是自己编的简单用例。像“#A-1029”这样的情况只会出现在真实对话里，而且往往是最大的一组失败。

这项技能在简历和面试中怎么体现？

读 FDE 招聘启事时，留意那些只说“可衡量成果”却不附任何数字的表述。看到这类说法，准备好一个具体的故事，讲你自己定下衡量方式的经历：选了哪个指标、为什么选、结果如何。

在 Staff 级别，Intercom 期望的人能够把握方向、对结果负责，并直接与客户和 Go-To-Market 团队合作。有了带基线的评测集，你就能用数字而不是演示后的印象向销售团队汇报结果。

在简历上，一条好的要点包含三部分：你接入的系统、你的衡量方式、前后对比的数字。按上面的例子可以写：“为订单查询智能体构建 30 段对话的评测集；自助解决率从 60% 提升到 83%（18→25/30），无回归。”

本周练习

挑一个带有用户级数据的公开 API，比如订单、工单或预约，写一个调用它的简单智能体。写 30 段测试对话，确定主指标，运行一次作为基线，并记下每个失败的原因。

你带进面试的不是代码仓库，而是“12 个失败中有 7 个来自用户输入订单号的方式”这句话，只有亲手做过衡量的人才说得出来。
