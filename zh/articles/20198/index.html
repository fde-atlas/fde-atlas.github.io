面向 FDE 的情境调查：观察用户的实际工作方式

原标题：Contextual Inquiry for FDEs: Watch How Users Work

FDE Times · 2026-10-09 · 约 6 分钟读完

摘要

这篇文章面向前沿部署工程师，讲解情境式调研方法：客户在需求梳理时描述的流程往往比真实工作更简洁，原因、动机和心智模型会在口头总结中丢失，而用户自己也意识不到的习惯只能通过现场观察发现。文章建议以“学徒”姿态静默观察用户一整天，用四栏记录法记下例外操作和非正式变通，把提问留到用户休息时；同时警告不要打断用户、不要充当技术支持、不要只观察团队负责人。文中用一个物流客服团队的假设案例说明，这些观察结果如何暴露出 Agent 设计中的隐患，并建议将观察日志与需求文档对照，把差异转化为设计修改。

要点

  • 口头描述的流程会丢失原因与心智模型，与实际工作存在差距。
  • 以学徒姿态静默观察，用四栏日志记录例外与变通。
  • 不要打断用户、不要帮忙解决技术问题，否则会掩盖真实困难。
  • 应观察一线最终用户，而非只看团队负责人。
  • 将观察结果与需求梳理文档对照，修正 Agent 设计。

人们描述的是他们自认为遵循的流程；而坐在他们身边，你会发现他们自己都不知道的习惯——而这恰恰是 AI Agent 出问题的地方。

简要概述

  • 当用户描述一个流程时，背后的推理、动机和心智模型都会丢失，所以你必须观察他们的实际操作才能看到这些东西
  • 以学徒的身份行动：安静观察，记录例外情况和捷径，把问题留到他们停下来的时候再问
  • 不要成为用户的技术支持，因为这样做会掩盖你专程前来发现的那些困难

你刚刚与一家物流公司的运营负责人完成了一次需求界定会议。流程已经被清晰地勾勒出来：一封投诉邮件到达，一名员工阅读它，在系统中选择事件类型，然后将其转给负责的团队。四个步骤，你的任务就是构建一个自动化这些步骤的 AI Agent。

这张图几乎肯定是不完整的。没有人对你撒谎。人们只是在描述他们自认为遵循的流程。OpenAI 的前沿部署工程负责人在 Pragmatic Engineer 上撰文指出，客户在需求界定时描述的内容，往往与实际数据和系统的真实情况不符。

对 FDE 来说，这个差距不仅仅是用户体验问题。如果你的 AI Agent 是围绕那张四步图设计的，它恰恰会在图中被遗漏的地方出问题。本指南介绍弥合这一差距的技能：花一天时间待在用户身边，用正确的方式观察。

为什么描述总是比实际工作更“整洁”？

其机制很简单。Nielsen Norman Group（NN/g）指出，当人们回忆并总结自己的流程时，底层的推理、动机和心智模型会从总结中流失。

留下的只有步骤；原因则丢失了。这就是为什么 UserTesting 指出，用户报告的行为并不总是与你观察到的行为一致。

这个差距也无法通过更细致的提问来弥补。根据 NN/g 的说法，真实的工作场景还会暴露出用户自己都没有察觉的行为，而你无法询问一个人他们自己都不知道的习惯。

这就是为什么 Paraform 在描述 FDE 角色时说，有些约束只有在你观察一个人实际使用软件时才会显现。

实际结果是，FDE 必须出现在工作发生的地方。一位 Palantir 的 FDE 告诉 Pragmatic Engineer，在大多数周里，他们会有好几天在客户现场工作。

以学徒而非采访者的身份到场

NN/g 将情境调查定义为一种结合深度观察与访谈的民族志实地研究形式。它用师徒关系来形容这种关系：师傅通过实际操作传授技艺，学徒通过观察来学习。

以学徒的角色参与，会改变你在现场的位置。面试官提问并等待回答；而学徒观察师傅的手部动作，注意他们在哪里犹豫、打开了哪些额外的窗口，然后才问：“您为什么这么做？”用户无需展示任何东西，只需像平常一样工作即可。

示例：在投诉团队的一天

回到那家物流公司。想象你从早上 9 点起坐在投诉处理专员 Lan 身后。你什么都不问，只在四列的表格里做笔记。以下是该记录的一个假设摘录：

时间你看到的内容记下的问题设计启示
9:12在选择事件类型之前，她在第二块显示器上打开一个 Excel 文件来查询客户姓名这个文件是什么？由谁更新？系统之外存在一份优先客户名单。Agent 需要能够读取它
9:40她把运单号复制到承运商网站上，而不是查询内部系统为什么不在系统里查状态？内部数据可能有延迟；在 Agent 依赖它之前，先确认其更新速度是否足够快
10:05面对一封含义模糊的邮件，她把它粘贴到团队聊天里询问同事这类案件通常由谁决定？必须有转交人工的路径；不要强迫 Agent 自己对每封邮件进行分类
10:30她对一封同时描述两个事件的邮件选择了“其他”包含多个事件的邮件如何处理？当前数据模型假设每封邮件只有一个标签

这些行都不会出现在四步图里。然而其中任何一条都可能让 Agent 在上线生产的第一周就出问题。值得注意的是，Lan 并没有隐瞒这些。对她来说，这只是“工作本来就是这么做的”，没什么值得一提的。

在她休息时，你拿出问题那一列。直到此刻访谈才真正开始，而且它锚定在刚刚发生的事情上，而非泛泛的回忆。

自己动手的步骤

准备。 请求观察一个普通的工作日，而不是演示。明确说明你是来学习他们如何工作的，而不是来评估他们。带上上面的四列记录模板。

同时观察常规工作和例外情况。 AI Engineer 关于 FDE 的知识库建议，在观察常规工作的同时，也要观察会产生实际后果的例外情况以及非正式的变通办法。常规工作让你看到理想路径；例外和捷径让你看到真实系统缺少什么。

当故事听起来太顺畅时，请对方举一个例子。 同一资料来源建议，当一个流程被描述得过于顺畅时，你应该请对方举一个近期的例子。实际操作中可以问：“你上次遇到这样的案件是什么时候？能打开给我看看吗？”一个具体的例子能把人们从理想化的流程拉回到实际发生的事情上。

与需求界定相互印证。当天晚上，把你的记录与需求界定文档对照。每一处不一致，要么是需要带给决策者的问题，要么是对设计的修改。

让观察失去价值的错误

最常见的错误是打断。AI Engineer 指出，在用户工作时提问会改变他们的行为。如果问“你为什么打开那个文件？”，Lan 可能会为了迎合你而开始“照章办事”。所以记下时间，把问题留到之后。

第二个错误对工程师来说更难避免：看到用户遇到困难就想立刻帮忙。同一资料来源警告说，当你成为用户的技术支持时，你恰恰会掩盖你此行要发现的那些困难。

Lan 在运营商网站上挣扎的那三分钟是宝贵的数据。给她展示一个捷径，这些数据就消失了。

第三个错误是只观察团队负责人。负责需求界定的人通常不是每天实际干活的人。请求与最终用户坐在一起，尽可能贴近一线。

这项技能在简历上如何体现？

阅读 FDE 职位描述时，留意诸如“与客户在现场合作”或“直接与最终用户合作”之类的措辞。Paraform 将 FDE 与最终用户之间的反馈循环描述为“面对面”。观察正是这些招聘启事隐含要求的技能。

在简历上或面试中，不要写“出色的客户沟通能力”。讲一个具体的序列：你观察了谁、观察了多久、发现了哪种非正式的变通方法，以及设计因此发生了怎样的改变。

这样的故事能向招聘人员表明，你能够挖掘真实需求，而不只是执行别人交给你的需求。

需求界定中的四步图仍然有用：它是你的第一个假设。在 Lan 身边待上一天，就是在你的代码不得不在生产环境中检验这个假设之前，先对它进行检验。
