SWE-RL (2025) 解读：面向 FDE

原标题：SWE-RL (2025) Explained for FDEs

FDE Interviews · 2026-10-18 · 约 4 分钟读完

摘要

SWE-RL 用 GitHub 上 27.3 万条已合并的 PR 作为训练种子，跳过执行环境，以预测补丁与真实补丁的序列相似度作为奖励，通过 GRPO 训练 Llama3-SWE-RL-70B。该模型在 SWE-bench Verified 上达到 41.0%（基于 500 次采样加生成测试重排），监督基线为 36.2%。文章指出相似度奖励只是代理指标、重采样成本高、单次训练需约 16384 H100 GPU 小时，并讨论了如何将客户 PR 历史转化为训练数据。

要点

  • 用 27.3 万条已合并 PR 作种子，训练时无需执行环境
  • 奖励为补丁相似度，格式错误记 -1，用 GRPO 训练
  • SWE-bench Verified 达 41.0%，监督基线为 36.2%
  • 相似度奖励偏袒模仿原开发者的写法，是代理指标
  • 单次训练约 16384 H100 GPU 小时，成本不低

一分钟读懂这篇论文

DeepSeek-R1 表明，使用简单的基于规则的奖励进行强化学习（RL），可以提升模型在数学和竞赛编程上的推理能力——这些场景中答案很容易验证。SWE-RL 则探讨同样的方法是否适用于日常软件工程：在这类场景中，验证一个修复通常意味着要在可运行的环境中运行项目的测试。

作者在训练过程中避免了执行代码。他们从 GitHub 上收集满足以下条件的拉取请求：关联了某个 issue、描述了 bug 修复、并修改了代码文件，最终保留了 273,000 个作为 种子。每个种子向模型提供一个 issue、被修改文件的完整内容以及一些相关的未修改文件，并将实际合并的补丁保留为 oracle。模型先写出推理过程，然后给出搜索替换式的编辑。如果输出格式错误，奖励为 -1；否则奖励为预测补丁与 oracle 补丁之间的 序列相似度，由 Python 的

difflib.SequenceMatcher

计算，取值范围为 0 到 1。训练使用

GRPO

，该方法会比较同一问题的 16 次尝试的奖励。

最终得到的模型 Llama3-SWE-RL-70B 在 Agentless Mini 中解决了 SWE-bench Verified 的 41.0%。Agentless Mini 是一个简化的流水线：定位相关文件、采样多个修复方案、编写复现测试并进行重排序。只有修复步骤经过了训练；该模型还能处理文件定位和测试编写，尽管它从未为此接受过训练。基于相同种子构建的监督基线得分为 36.2%。

作者还报告了在软件问题之外的收益（代码推理、数学），并认为 RL 能泛化，而监督 微调 则会使能力变窄。

研究笔记：问题、方法与结果

SWE-bench Verified 搭配 Agentless Mini，使用 30 个生成的测试从每个 issue 的 500 个采样补丁中选出一个

在给定正确文件的情况下的修复准确率，监督基线对比 RL，两者均为贪心解码

一次训练运行的 H100 GPU 小时数：512 块 GPU 运行约 32 小时

基于规则的奖励的强化学习让模型在数学和竞赛编程上表现更好——在这些场景中，答案可以被精确验证，或者运行程序的成本很低。而真实的软件修复很难验证：运行一个仓库的测试需要为每个项目搭建可运行的环境，大规模构建这样的环境成本高昂。

在训练中跳过代码执行。选取关联了 issue 的已合并拉取请求，向模型提供 issue 和完整文件，并根据其补丁与已合并补丁的相似程度（difflib 的序列相似度比率）给予奖励，格式错误的输出记为 -1。使用 GRPO 在 273,000 个这样的种子上进行训练。

在给定正确文件的情况下，修复准确率从 5.4%（基础模型）和 29.6%（监督基线）提升到 34.8%。端到端来看，采样 500 个补丁并用生成的测试进行重排序后，它解决了 SWE-bench Verified 的 41.0%。多个域外基准测试也有所提升，其中一些提升更多来自格式改善而非推理能力。

为什么这对 FDE 很重要

许多客户会问：他们自己的工程历史（多年的工单、拉取请求和已合并的修复）能否让编码模型在他们的代码库上表现更好。SWE-RL 是把这类历史转化为训练数据的最清晰的可行方案，而且无需为每个仓库构建可执行环境。它同时也展示了这种捷径的代价。

数据很便宜；奖励只是一个代理。 与已合并补丁的相似度作为奖励，会鼓励模型写出与原开发者相同的内容。一个风格不同但正确的修复，得分会低于一个照搬“标准答案”形状但错误的修复。作者自己也列出了这一局限。

头条数字依赖大量采样。 41.0% 之所以是 pass@1，只是因为最终提交了一个补丁；它是从 500 个样本中选出的，每个问题生成了 30 个测试。同样模型在 20 个样本时得分只有 33.6%。如果你照搬这套设置，请为这种推理开销做好预算。

训练规模不小。 一次运行在 70B 模型上使用了 512 块 H100 约 32 小时，即 16,384 GPU 小时。

格式化占了一半的功劳。 基础模型只有 12.2% 的时间能产出格式正确的编辑。RL 带来的部分增益，以及大部分域外数学增益，其实是模型学会了遵循输出格式。

如果客户想要这个，实际可行的版本要小得多：一个规模适中的模型，以他们自己的拉取请求作为种子，在存在测试的地方用执行来校验，相似度仅作为兜底。
