如何使用本指南

如今几乎每一轮 AI 工程面试都会涉及评测，无论职位名称是 GenAI 工程师、AI 工程师、MLOps 还是前沿部署工程师。如果你想先了解概念背景，请阅读我们的 LLM 评测指南。各层级面试官通常会考察的内容：

  • 应届生和初级工程师： 为什么不能用简单断言来测试 LLM 输出、exact match、F1 和 ROUGE 各衡量什么，以及什么是黄金集。
  • 中级工程师： 忠实度、上下文精确率与召回率、评审评分标准、合成数据，以及如何将评测接入流水线。
  • 高级和架构师岗位： 用人类标准校准评审模型、Agent 轨迹评测、线上实验、数据污染、公平性切片、评测成本，以及诊断一个没人预见的回归问题。

在阅读参考答案之前，先大声回答每道题。如果可以，附上一个你亲手构建过的例子；面试官对一个具体的评测故事的记忆，远比一串指标名称深刻得多。

为什么 LLM 的评测与众不同

1. 为什么不能像测试普通软件那样测试 LLM 应用？

答案： 传统软件是确定性的：相同输入产生相同输出，因此你可以断言相等。而 LLM 应用是概率性且开放式的。同一个提示词每次运行可能产生不同的措辞，许多不同的答案都可能是正确的，而一个流畅的答案也可能是错的。质量还是多维度的：一个答案可能准确但无用、有用但不安全，或正确但格式不对。因此，与其对精确字符串做通过/失败的单元测试，不如在一个有代表性的数据集上评估行为分布，综合使用确定性检查、基于参考的指标、基于模型的评审和人工审核。

面试提示： 提到在合适的地方你仍然会保留确定性测试：JSON schema 校验、必填字段、工具调用名称、禁用短语。并非所有东西都需要评审模型。

2. 你究竟在评测什么：模型还是系统？

回答： 通常是系统。一个生产级 LLM 应用是一条流水线：提示词模板、检索、重排序、工具调用、防护栏、后处理以及模型本身。模型评测（公开基准、能力测试）告诉你一个模型是否是合理的候选者。系统或任务评测则告诉你，你的应用在结合你的数据、提示词和工具的情况下，能否完成用户需要的任务。在其余一切固定的情况下更换模型是一个实验；在模型固定的情况下更改分块策略是另一个实验。好的评测能让你把质量变化归因于你所更改的那个组件。

3. LLM 输出质量的主要维度有哪些？

回答： 一套实用的维度是：正确性（对任务而言事实是否正确）、有据性或忠实性（是否由所提供的上下文支持）、相关性（是否回应了问题）、完整性、格式合规（模式、长度、语言、语气）、安全性（毒性、有害内容、数据泄露）、拒答行为（该拒绝的拒绝，该回答的回答），以及运行层面的质量（延迟、token 成本）。并非每个应用都需要全部维度。工单分类器主要需要准确性和格式合规；面向客户的助手还需要有据性、安全性和语气。

面试提示： 把这些维度与业务风险联系起来。“对银行来说，一个没有依据的关于收费的回答会引发投诉，甚至可能是合规问题，因此忠实性要设硬性阈值。”

4. 离线评测和在线评测有什么区别？

回答： 离线评测是在发布前针对固定数据集运行你的系统：它可重复、便于跨版本比较且安全，但效果取决于数据集的质量。在线评测是在发布后衡量真实流量下的行为：用户反馈、隐式信号、抽样评审打分和 A/B 测试。它反映现实，但有噪声、更慢且带有风险。两者都需要。离线评测是阻止明显退化的关卡；在线评测能发现数据集遗漏的问题，而这些发现又会回流到离线数据集中。

  production traffic --> sample + label --> golden set
        ^                                     |
        |                                     v
  online signals <-- release <-- CI gate <-- offline eval

5. 为什么“演示中看起来不错”不算评测？

回答： 演示只是少数手工挑选的输入，通常是正常路径，而且由构建系统的人来判断。它没有对边界情况的覆盖，没有对多次运行之间差异的度量，没有可比较的基线，也没有可供他人复现的记录。评测意味着一个代表真实使用情况的版本化数据集、定义了指标和阈值、按版本存储结果，以及在任何更改之后重新运行全部内容的方法。这一差距是 AI 演示在企业生产环境中失败 的主要原因之一。

构建评测集

6. 什么是黄金集（golden set），如何构建它？

回答：黄金集（golden set）是经过精心整理、带有版本管理的输入集合，包含预期输出或评分标准，并由熟悉该领域的人员审核。构建方法：收集真实问题（支持工单、搜索日志、用户访谈），覆盖主要意图和高风险的边缘情况，与领域专家一起撰写参考答案或验收标准，记录元数据（意图、难度、语言、来源文档），并将其存入版本控制或评测平台。宁可小而精，也不要大而杂；几百条经过仔细审核的条目通常比数千条未经检查的条目更有价值。

实际案例：假设一家保险公司正在构建理赔政策助手。黄金集包括常见问题（“理疗是否在承保范围内？”）、答案因保单版本而异的问题、助手必须拒绝回答的问题（法律建议），以及文档中没有答案的问题，每条都按产品线打标签，以便对结果进行切分分析。

7. 合成评测数据在什么时候有用，有哪些风险？

回答：合成数据是由 LLM 根据你的文档或种子示例生成的，当你几乎没有真实流量、需要覆盖罕见情况、想要对抗性或多语言变体，或必须避免使用敏感的生产数据时，它很有用。风险在于：生成的问题往往比真实问题更容易、更“教科书化”，它们继承了生成器的风格和盲点，可能泄露源文本块中的答案措辞（使检索效果看起来比实际更好），而且如果同一个模型家族既生成又评判，分数可能会被夸大。缓解措施包括：让人类审核样本、将合成问题与真实问题混合、给合成条目打标签以便单独报告，以及刻意生成更难的变体。我们关于 AI 测试用合成数据的指南更深入地介绍了生成技术。

8. 如何利用生产数据来改进评测集？

回答：定期对生产轨迹进行抽样，并采用分层抽样，确保你能看到每种意图，而不仅仅是最常见的那些。优先关注带有负面信号的轨迹：点踩、升级到人工、重试、长会话、低评判分数。让审核人员为它们打标签、写出预期行为，并加入黄金集。在存储任何数据之前，应用你的数据保护规则：屏蔽或删除个人数据，并遵循同意和保留政策（在印度，DPDP 法案适用于你处理的个人数据）。随着时间推移，黄金集会逐渐贴近真实困难案例的分布，这正是你想要的。

面试提示：可以说“每一次生产事故都会变成一个回归测试”。这表明你形成了闭环。

9. 评测集应该有多大？

回答： 规模要大到你所关心的差异超过噪声。如果你想检测通过率的微小变化，需要的题目数量就比只捕捉大幅退化时更多；当只有几十道题时，两次运行之间相差几道题可能纯属随机。实用做法是：核心题集从几百道题起步，如果输出不确定，则对每个配置运行多次，报告置信区间或至少报告运行间的方差，并为特定风险（安全、提示注入、拒答、格式）保留单独的较小题集。意图和边界情况的覆盖比单纯的数量更重要。

10. 如何防止评测集过时或泄漏到训练数据中？

回答： 对评测集进行版本管理，记录哪个系统版本在哪个数据集版本上评分，并定期从生产环境中刷新。当来源文档发生变化时，淘汰相应题目，否则你会惩罚正确的新答案。保留一部分提示工程师在调优时看不到的保留集，因为针对同一批可见示例反复迭代提示，会像训练一样过拟合。如果你进行微调，务必确保评测题目绝不进入训练数据，并检查近似重复项，而不仅仅是完全相同的副本。

指标

11. 什么时候适合使用精确匹配和 F1？

回答： 精确匹配（在规范化大小写、空白和标点之后）适用于存在唯一标准答案的情况：分类标签、提取的发票号码、是/否决策、SQL 结果集。词元级 F1（词元精确率和召回率相对于参考答案的调和平均数）适用于措辞略有变化的简短抽取式答案，可给予部分得分。对于长篇自由格式的回答，两者都会失效，因为正确的改写会得分很低。请将它们用于结构化任务和抽取任务，以及较大输出中的结构化部分（例如 JSON 响应中的

category

字段）。

12. BLEU 和 ROUGE 在 LLM 评估中有哪些局限？

回答： BLEU 衡量相对于参考答案的 n 元词组精确率，源自机器翻译；ROUGE 衡量 n 元词组召回率，源自文本摘要。两者都奖励表面词汇的重叠，而非语义。一个措辞不同的正确答案得分很低，而一个复制关键短语的错误答案（“该索赔不在承保范围内”与“该索赔在承保范围内”）得分很高，而且它们完全无法反映忠实度、安全性或有用性。它们还需要参考文本，而这对开放式任务来说成本很高。对于模板化摘要等约束严格的任务，它们仍可作为廉价的趋势信号，但你不应仅凭它们来决定是否发布。

面试提示： 给出否定句的例子。这表明你理解为什么重叠类指标对语义视而不见。

13. 语义相似度评分是如何工作的，它在哪里会失效？

回答： 你使用嵌入模型对生成的答案和参考答案进行向量化并计算余弦相似度，或者使用交叉编码器直接对这一对文本打分。它对改写的容忍度远高于 BLEU 或 ROUGE。它有三种失效方式：嵌入捕捉的是主题而非真实性，因此“费用是 500 卢比”和“费用是 5,000 卢比”看起来非常相似；阈值是任意的且因模型而异；以及包含一个错误句子的长答案仍然会得到高分。应将语义相似度作为其中一个信号，并结合针对事实、数字和否定句的声明级检查。

14. 什么是忠实度（groundedness，有据性），它是如何衡量的？

回答： 忠实度衡量的是答案中的每一条声明是否都得到系统所获上下文的支持，而不论该声明在现实中是否为真。常见方法是：由 LLM 将答案拆分为原子声明，然后逐条对照检索到的上下文进行检查，得分即为受支持声明的比例。自然语言推理模型可以代替 LLM 来执行蕴含检查。忠实度是捕捉 RAG 幻觉的主要指标。请注意，如果检索到的文档已过时，一个忠实的答案仍可能是错误的，因此你还需要对照参考答案衡量正确性。我们关于 LLM 幻觉的讲解文章涵盖了其成因。

15. 答案相关性、上下文精确率和上下文召回率分别衡量什么？

回答： 答案（回复）相关性衡量答案是否回应了所提出的问题，并对回避性、不完整或冗长填充的回答进行惩罚；一种做法是从答案生成问题，再将其与原始问题进行比较。上下文精确率衡量检索到的文本块是否相关，以及相关的文本块是否排在靠前位置。上下文召回率衡量检索到的上下文是否包含生成参考答案所需的全部信息，因此通常需要参考答案。三者结合可以将检索问题（上下文召回率低）与生成问题（上下文良好但忠实度低）区分开来。

指标回答的问题是否需要参考答案？
忠实度答案是否得到上下文支持？否
答案相关性是否回应了问题？否
上下文精确率检索到的上下文是否相关且排序良好？取决于变体
上下文召回率检索是否找齐了所需的一切信息？通常需要
答案正确性是否与预期答案相符？是

16. 如何评估毒性与安全性？

答： 使用专门的安全测试集：有害请求、越狱尝试、文档中的提示注入、索取个人数据的请求，以及边缘但合法的请求。用安全分类器或供应商的内容安全服务对输出打分，再加上一个带有明确政策评分标准的评审模型，并抽样送人工审核。双向衡量：不安全输出的比例，以及安全请求被错误拦截的比例。安全评测是持续性的，不是一次性的，因为攻击手段不断演变；它与 AI 红队测试 有重叠——红队测试寻找新的失败模式，而评测则在每次发布时检查已知问题。

17. 为什么拒绝率很重要，如何衡量过度拒绝？

答： 拒绝太少的系统不安全；拒绝太多的系统没有用处，用户会绕开它。构建两个带标签的集合：必须拒绝或升级处理的请求，以及看起来敏感但实际合法的请求（“我该如何举报一笔欺诈交易？”）。分别测量两者的拒绝率。用评审模型或分类器将每个输出标记为已回答、已拒绝或部分回答。在每次发布中跟踪这两个数字，因为收紧防护或更换模型往往会改善一个指标，同时悄悄恶化另一个。拒绝还应当得体：解释原因，并提供下一步操作或转接人工服务。

18. 每个 LLM 评测套件都应包含哪些确定性检查？

答： 在任何评审模型之前对每个条目运行的廉价、无歧义的检查：输出能解析为有效 JSON 或符合 schema、必需字段存在、枚举值有效、长度在限制范围内、响应使用所要求的语言、没有泄露系统提示词或内部标识符、在不应出现的地方没有个人数据模式（电话号码、Aadhaar、PAN 格式）、引用格式正确，以及工具调用的名称和参数类型有效。这些检查快速、免费、可复现，能发现相当比例的回归问题，尤其是在模型升级之后。关于如何在生成时强制执行 schema，请参见 函数调用与结构化输出。

LLM 即评审

19. 什么是 LLM 即评审，什么时候应该使用它？

答： LLM 即评审是指使用一个带有评分提示词和评分标准的语言模型，对难以计算的输出质量进行打分或比较：有用性、忠实度、语气、政策合规性、推理质量。当输出是开放式的、评判标准可以清晰写下来、且全量人工审核太慢或成本太高时，可以使用它。在确定性检查可行的地方不要使用它，并且在没有测量它与人工标签在你自己数据上的一致性之前，不要信任它。评审模型是一种测量工具，而工具需要校准。

20. 如何设计一个好的评审评分标准？

回答： 让每条标准都具体且可观察，每次评判调用只打一个维度，而不是“整体质量”；用具体描述定义每个分数等级，附上每个等级的简短示例；要求在打分前先给出简要理由，使推理过程可审查；并给评判模型恰好所需的输入（问题、上下文、参考答案、回答）。二元或三级量表通常比十分制更稳定。返回结构化输出，以便分数能被可靠解析。

Criterion: Faithfulness
Inputs: question, retrieved_context, answer
PASS: every factual claim is supported by context
PARTIAL: minor unsupported detail, core answer OK
FAIL: any claim contradicts or is absent from context
Output JSON: {"reasoning": "...", "label": "PASS"}

面试提示： 要说明你像管理代码一样对评分标准进行版本管理。修改评分标准就等于修改了指标，因此修改前后的分数不可比较。

21. LLM 评判模型有哪些偏差？

回答： 有充分记录的偏差包括位置偏差（在两两比较中偏好第一个或第二个答案）、冗长偏差（偏好更长的答案）、自我偏好（偏好来自同一模型系列的输出）、重形式轻实质（奖励自信、格式良好的文本）、对提示词措辞敏感，以及在医学或税务等专业领域知识薄弱。缓解措施：交换位置并只统计一致的判定；通过指令和测试确保对长度中立；使用与被测系统不同模型系列的评判模型；尽可能使用参考答案；并与领域专家进行校准。

22. 如何将 LLM 评判模型与人工标注进行校准？

回答： 让领域专家独立标注一个有代表性的样本，最好每条由两名标注者标注，这样你还能了解人与人之间的一致性。让评判模型对相同条目打分。用准确率加上机会校正统计量（如 Cohen's kappa）来衡量一致性，并查看混淆矩阵，因为漏判失败的评判模型（假通过）比稍微严苛的更危险。阅读不一致之处，完善评分标准或示例，并在新条目上重复验证，以避免评分标准过拟合于校准集。每当更换评判模型、评分标准或领域时都要重新校准。人与人之间的一致性是实际上限；不要指望评判模型超越它。

23. 两两比较还是逐点评判：何时使用哪种？

回答： 逐点评判是依据评分标准对单个输出打分（通过/失败或量表）。它适合绝对阈值、发布门禁和监控，因为每个输出都有自己的分数。两两比较评判是对同一输入展示两个输出并询问哪个更好。它对比较两个提示词或模型更敏感，因为相对判断比绝对判断更容易，但它无法告诉你任一输出是否可接受，并且需要交换位置来控制偏差。常见模式：开发阶段用两两比较挑选更强的变体，CI 和生产环境用逐点评判来强制最低质量。

24. 如何让评判模型的分数可靠到足以作为发布门禁？

回答： 固定评判模型版本并设置低温度或零温度，为评分标准做版本管理，使用结构化输出，并通过多次对同一项目打分来衡量评判模型的自一致性。只使用已被证明与人类判断一致的指标作为门禁，且阈值的余量应超过运行间的噪声。将评判模型指标与确定性检查相结合，使门禁不依赖于单一模型的意见。每次发布保留一小部分经人工审核的审计样本，以便及时发现评判模型本身的漂移。

RAG 评测

25. 如何对 RAG 系统进行端到端评测？

回答： 分别评测检索和生成，然后再整体评测。检索：为每个问题标注哪些文档或分块是相关的，然后测量 recall@k、精确率或上下文精确率，以及 MRR 或 nDCG 等排序指标。生成：在给定检索到的上下文的情况下，对照参考答案测量忠实度、答案相关性和正确性。端到端：答案正确性、引用准确性（被引用的来源是否确实支持该句子），以及面对无法回答问题时的行为。按文档类型、意图和语言对结果进行切分分析。我们的 RAG 评测指标 文章逐项讲解各指标，RAG 面试题 指南则涵盖架构方面的内容。

 question -> retriever -> chunks -> generator -> answer
               |                       |          |
      recall@k, ranking     faithfulness   correctness,
      context precision     relevance      citations

26. 如何评测系统对知识库中没有答案的问题的行为？

回答： 在黄金集中故意加入无法回答的问题：语料库之外的主题、关于不存在产品的问题，以及在文档更新中答案已被删除的问题。期望的行为是诚实地回答“我在可用文档中找不到这个”并给出下一步建议，而不是一个看似合理的编造。测量正确拒答率和在可回答问题上的错误拒答率。这能捕捉到最具破坏性的 RAG 失败：基于松散相关分块构建的自信回答。

27. 如何判断 RAG 的性能回退来自检索还是生成？

回答： 查看失败项目上的分阶段指标。如果上下文召回率下降了，说明所需信息从未到达模型：检查分块、嵌入、过滤器、索引新鲜度和重排序器的变更。如果上下文召回率正常但忠实度或正确性下降，说明模型拥有信息但使用不当：检查提示词变更、上下文排序、上下文长度和模型版本。一个有用的诊断方法是用黄金上下文注入重新运行生成器；如果答案恢复正常，问题就在检索环节。

实际案例： 设想海得拉巴一家 GCC 的 IT 团队，其服务台助手开始给出错误的 VPN 操作说明。上下文召回率只在关于某个工具的问题上下降，原因是某个重新索引任务静默跳过了扫描版 PDF。生成环节没有问题。

Agent 评测

28. 评测一个 Agent 与评测单次 LLM 调用有何不同？

回答：Agent 会执行多个步骤：它进行规划、调用工具、读取结果并决定下一步做什么，通常跨越多轮对话。因此你需要在多个层面进行评测：最终结果（任务是否正确完成）、轨迹（步骤是否合理、高效且安全），以及单个步骤（每个工具是否被正确选择和调用）。Agent 还会产生副作用，所以评测必须在沙箱或模拟（mock）工具上运行，并且你需要成本和步骤数等指标，因为一个经过多次冗余工具调用才成功的 Agent 仍然是个问题。AI Agent 评测指南对此有深入讲解。

29. 轨迹评测与结果评测：有什么区别？

回答：结果评测检查最终状态：退款金额是否正确、工单是否进入了正确的队列、数据库中是否包含预期的行。它最接近业务价值，并且能容忍不同的有效路径。轨迹评测检查动作序列：Agent 在修改账户前是否验证了身份、是否避免了在读取之前调用写入工具、是否陷入循环或重复调用。它能捕捉那些碰巧结局良好但危险或浪费的行为。轨迹可以与参考序列进行比较（精确匹配、按顺序匹配或任意顺序匹配），也可以由评判模型根据规则打分。结果评测用于衡量成功率，轨迹评测用于衡量安全性和效率。

30. 如何衡量工具调用的正确性？

回答：将其分解为工具选择（为该步骤选择正确的工具，或正确地不使用工具）、参数正确性（符合 schema、从对话中正确提取值、没有虚构的 ID）、调用顺序和依赖关系，以及对工具错误的处理（重试、询问用户，或升级上报而不是编造结果）。确定性检查用于验证名称和 schema；参考轨迹用于检查预期参数；评判模型评估在给定上下文下该选择是否合理。对于写入操作，还要检查在策略要求的地方是否请求了批准。

面试提示：提到你会使用返回真实成功、空和错误响应的模拟工具进行评测，因为一个只见过正常工具结果的 Agent 并没有真正被测试过。

31. 如何评测多轮对话或会话？

回答： 在会话层面评估目标完成度，在轮次层面评估正确性、相关性和指令遵循能力。要进行规模化测试，可以使用模拟用户——即给定人设和目标的 LLM——与 Agent 对话，直到目标达成或达到轮次上限，然后对对话记录进行评判。检查 Agent 是否能在多轮之间保持上下文、不重复询问已回答的问题，并能处理对话中途的变化（“其实，换成另一个账户”）。托管服务现已支持这种模式；例如，Amazon Bedrock AgentCore Evaluations 提供会话层面（如目标成功率）、追踪层面（如正确性、忠实度和有用性）和工具层面（工具选择和参数准确性）的内置评估器，评分基于基于 OpenTelemetry 的追踪数据。请查阅当前文档以获取评估器列表。Bedrock AgentCore 面试题指南涵盖了该服务本身。

在线评估

32. 如何为 LLM 功能运行 A/B 测试？

回答： 在开始之前定义主要指标（任务完成率、无需升级即解决率、转化率），以及护栏指标（安全事件、延迟、成本、投诉率）。在用户或会话层面进行随机化，而不是按请求随机化，以免用户在同一次对话中在不同变体之间来回切换。提前确定样本量和持续时间，避免在数据看起来不错时就停止。注意新鲜感效应，因为用户与新事物的交互方式会有所不同。将实验与对两个分支的抽样评判得分相结合，这样你就能理解为什么某个变体会胜出。

33. 哪些显式和隐式用户信号是有用的，它们有哪些陷阱？

回答： 显式信号：点赞/点踩、评分、书面反馈、“报告问题”。隐式信号：复制答案、对同一问题换一种说法重新提问、放弃会话、升级到人工、在发送前大幅编辑生成的草稿、接受或拒绝建议。陷阱：显式反馈稀少且偏向强烈意见，隐式信号含义模糊（会话时长短可能意味着成功也可能意味着挫败），而且两者都会受 UI 设计的影响。应将它们视为值得审查的追踪记录的线索，而不是真实标准。

34. 如何在生产环境中持续监控质量？

回答： 使用 OpenTelemetry 或追踪平台，对每个请求记录输入、检索到的上下文、工具调用、输出、延迟和成本。在全部流量上运行低成本的确定性检查，并在抽样流量上运行评判评估器，按意图分层并加权偏向高风险流程。将得分放入仪表盘并设置下降告警，将低分追踪记录路由到审查队列，以充实黄金数据集。同时跟踪输入主题的漂移：新产品发布可能会改变用户的提问内容。更全面的设置在我们的 AI 可观测性指南中有介绍。

CI 中的回归门禁

35. 如何在 CI/CD 流水线中构建评测门禁？

回答： 将提示词、检索配置、模型 ID 和评分标准视为版本化的产物。在每个涉及它们的拉取请求上，运行一套快速测试：确定性检查加上一个小而有代表性的、由评判模型打分的子集。在合并或发布前，运行完整测试套件。与当前生产基线进行比较，而不仅仅是绝对数值，如果任何阻断性指标下降超过设定的容差，或任何关键测试（安全、政策）失败，则使构建失败。发布包含各分片得分和具体失败示例的报告，以便评审人员采取行动。我们关于 AI 应用的 CI/CD 的文章展示了流水线结构。

 PR opened
   |
   v
 lint + schema tests --> fast eval subset --> report
   |                                          |
 merge --> full eval vs baseline --> pass? --> deploy
                                       |
                                       no --> block

36. 如何处理 CI 中的非确定性和不稳定的评测结果？

回答： 尽可能降低方差：固定温度、锁定模型和评判模型版本、为未变化的输出缓存评判结果。通过多次运行基线来测量剩余方差，并将容差设置得比该噪声更宽。将硬性门禁（模式、安全、关键政策项，必须每次通过）与软性指标（评判平均值，下降不得超过容差）分开。对于处于临界线的结果，应重新运行受影响的分片或升级到人工评审，而不是让工程师反复重试直到变绿。

面试提示： 面试官喜欢听到你说，你宁愿拥有一个更小、稳定且人们信任的门禁，也不愿要一个庞大、不稳定且人人学会无视的门禁。

基准测试、数据污染、公平性与成本

37. 公开基准测试与任务评测有什么区别？什么是数据污染？

回答： 公开基准测试在标准数据集上衡量通用能力（推理、编程、知识），有助于筛选模型。任务评测则在你的数据上衡量你的应用，决定某项功能能否发布。基准测试分数往往无法预测任务表现，因为你的领域、语言组合、文档和格式规则各不相同。数据污染是指基准测试题目或其近似改写出现在了模型的训练数据中，因此高分可能反映的是记忆而非能力。迹象包括在较旧基准上出现可疑的高分，而在新编写的等价题目上得分骤降。对于自己的评测，防御方法是：保留从未公开的、私有的、留出的、定期更新的数据集。LLM 面试题指南从模型侧介绍了基准测试设计。

38. 如何评估 LLM 应用的公平性？

回答： 根据用例和法律要求（在印度部署场景中相关的性别、地区、语言、年龄、残障、种姓或宗教）确定哪些群体和属性是重要的。构建仅改变属性的反事实测试对，例如同一贷款查询使用不同的姓名或城市，然后比较输出、评分、语气和拒绝率。按语言和用户群体对所有主要指标进行切分，因为区域语言或混合语码的 Hinglish 的质量往往会下降。使用评判模型来检测刻板印象和语气问题，并以多元化的人工审核员进行校准。记录发现的问题和修复措施。我们关于 AI 偏见与公平性测试 的指南详细介绍了这些方法。

真实案例： 假设一家零售商的产品助手在英文问答中表现出色，但对泰卢固语和印地语查询的回答更简短、更不准确。聚合评分会掩盖这一点；而按语言切分则会立即暴露问题。

39. 你如何控制评测的成本？

回答： 评测成本来自运行被测系统、运行评判模型以及人工审核时间。控制手段：先运行确定性检查，只对通过的项目进行评判；在验证较小评判模型与人工判断的一致性后，将其用于简单标准；为未变更的项目缓存输出和评判分数；对测试套件分层（每次 PR 运行小型套件，夜间或发布前运行完整套件）；对生产流量进行抽样而非全部评分；并在提供商支持时使用批量推理。将人工审核时间用于校准和分歧案例，而不是重复检查容易通过的项。像跟踪其他云成本一样跟踪每次发布的评测支出。

评测工具

40. 有哪些类型的评测工具，你会如何在它们之间做选择？

回答： 这些工具分为几类，许多团队会组合使用不止一种：

  • 指标库： Ragas（RAG 和 Agent 指标，如忠实度、回答相关性、上下文精确率和上下文召回率）和 DeepEval（pytest 风格的 LLM 测试用例，内置和自定义指标，包括 G-Eval 风格的量规评判）。
  • 追踪与评测平台： LangSmith（数据集、实验、在线评估器、LangChain 及其他代码的追踪）和 Langfuse（开源追踪、数据集、LLM 即评判的评估器和人工标注，可自托管）。
  • 配置驱动的测试运行器： promptfoo（开源 CLI，在配置中声明提示词、提供商和断言，并具有红队测试功能；现由 OpenAI 拥有，仍作为开源维护）。
  • 提供商评测服务： Amazon Bedrock Evaluations 用于模型和知识库，Amazon Bedrock AgentCore Evaluations 用于 AI Agent（支持在线、按需和批量评测，内置和自定义评估器），Microsoft Foundry 中的评估器（例如事实准确性和相关性），以及 Google Cloud Vertex AI 上的 Gen AI 评测服务（Google 一直在对 Vertex AI 的部分功能进行品牌重塑，请查看当前命名）。

选择时应基于：你的追踪数据已存放在哪里、数据是否必须留在你的环境中（自托管、区域）、你需要哪些指标、CI 集成以及团队的熟悉程度。指标的定义比工具本身更重要：在信任某个库给出的数字之前，务必先阅读它是如何计算该指标的，因为相同的指标名称在不同工具中可能含义不同。

面试提示： 面试中不要表现出对某个工具的偏爱。要说明每个类别的功能，以及你会如何在自有数据上验证任何工具的指标。

如果你想端到端地练习这些内容——从构建黄金数据集和评估器，到将评测接入云端基础设施的 CI——APEX AI、ML、云与网络安全课程 涵盖了评测，以及模型开发、云端部署和 AI 安全。

真实场景问题

41. 你的 LLM 评估器在大量条目上与人工审核员的意见不一致。你会怎么做？

回答： 在理解一致性问题之前，先停止使用评估器做门禁，然后将其视为一个测量问题：查明是评估器、评分标准还是人工标注出了问题。

我会检查的内容：

  • 人工审核员之间在相同条目上的一致性。如果审核员彼此之间都不一致，说明评分标准含糊不清，任何评估器都无法解决。
  • 混淆矩阵：评估器是过于宽松（误通过）还是过于严格，具体出现在哪些数据切片上？
  • 逐条并排阅读不一致样本，寻找规律，例如长度偏差、领域知识缺失，或人工审核员应用了评分标准中从未写明的某个标准。
  • 评估器是否与人工审核员接收相同的输入（上下文、参考答案、政策文档）。
  • 评估器模型或评分标准最近是否在未重新校准的情况下发生了变更。

生产环境考量： 根据不一致样本重写评分标准，加入明确的等级描述和示例；考虑使用更强的或不同系列的评估器模型；将复合标准拆分为多个独立评估器；并在新数据上重新测量。对于评估器仍然不可靠的切片，保留人工审核环节。

42. 发布后离线评测分数上升了，但用户投诉却增加了。为什么？

回答： 评测集或指标不再代表用户真正看重的东西，或者这次发布改变了评测未覆盖的某些方面。

我会检查的内容：

  • 黄金数据集是否与当前流量匹配：将生产环境的意图分布与评测集进行对比。
  • 未测量的维度：延迟、回答长度、语气、拒绝率、移动端格式、语言。
  • 评判偏差：一个新提示词如果生成更长、更自信的回答，可能会提高评判分数，却让用户感到厌烦。
  • 过拟合：针对可见评测集反复调优提示词。
  • 投诉记录本身，需详细阅读并按故障类型分组。

生产环境注意事项： 将投诉案例加入黄金集，补充缺失的指标，运行留出集测试，并对影响用户体验的变更使用线上 A/B 测试。指标只是代理；当代理与现实出现分歧时，以现实为准。

43. 新模型版本破坏了你的输出格式，下游解析失败。你如何处理？

回答： 立即回滚或固定到之前的模型版本，然后查明为什么格式检查在发布前没有发现这个问题。

我会检查的内容：

  • 模型是否固定在特定版本上，还是使用了会自动变动的别名。
  • 出现了哪些格式失败：JSON 周围有多余文字、markdown 代码围栏、字段重命名、日期格式不同、工具调用结构变化。
  • 是否有结构化输出或模式约束解码可用但未被使用。
  • 评测套件是否在足够多的真实输入上进行了模式验证测试，包括长文本和多语言输入。
  • 解析器在失败时的行为：是重试、修复还是明确报错？

生产环境注意事项： 固定模型版本，将每次模型变更视为必须通过完整评测门槛的发布，在支持的地方使用原生结构化输出，在运行时对每个响应进行模式验证并设置安全回退，并保留一份模型迁移清单。在一个模型上有效的提示词往往需要针对下一个模型进行调整。

44. 忠实度分数很高，但领域专家说许多回答是错误的。这是怎么回事？

回答： 回答忠实于检索到的上下文，但上下文本身是错误的、过时的或不完整的，或者忠实度评判过于宽松。

我会检查的内容：

  • 错误回答背后的源文档：已被取代的政策版本、内容相互冲突的重复文档。
  • 对照参考答案检查上下文召回和正确性，而不仅仅是忠实度。
  • 评判是检查每一条声明，还是只看大意。
  • 用于生效日期和文档状态的元数据过滤器。

生产环境注意事项： 忠实度衡量的是与上下文的一致性，而不是真实性。应将其与专家审核集上的回答正确性配对使用，并修复内容治理，让已停用的文档离开索引。

45. 你的 Agent 的任务成功率在测试中表现良好，但在生产环境中成本太高且速度太慢。你如何评估修复方案？

回答： 将效率纳入评估，然后在质量和成本两方面共同优化。

我会检查的内容：

  • 从轨迹中统计每个任务的步骤数和工具调用次数，寻找循环、重复读取和不必要的规划步骤。
  • 每一步的 Token 用量，以及每一轮重新发送了多少上下文。
  • 较小的模型能否在不降低结果评分的前提下处理路由或简单步骤。
  • 生产任务构成与测试集的对比；真实任务可能更长。

生产环境考量： 对每个变体并排报告成功率、平均和尾部延迟，以及每个成功任务的成本。只有当成功率保持在容差范围内且成本或延迟有所改善时，变更才会发布。我们的 LLM 延迟优化 指南列出了常用的优化手段。

46. 一位利益相关者问：“这个助手可以上线了吗？”你如何用证据来回答？

回答： 将评测结果转化为基于风险的就绪标准，这些标准在测试开始前已与业务方达成一致。

我会检查的内容：

  • 各维度结果是否达到约定阈值：正确性、忠实度、安全性、拒答率、延迟、成本。
  • 按切片划分的结果，尤其是高风险意图和较少使用的语言。
  • 已知的失败模式及其缓解措施（人工接管、防护栏、范围限制）。
  • 上线当天的监控和回滚就绪情况。

生产环境考量： 建议采用分阶段发布，例如先面向内部用户，再面向有限的客户群体，同时运行在线评测，并设定明确的扩大范围标准。就绪与否是一个有据可查的决策，而不是一种感觉。

47. 考虑一家医院部署出院小结助手。你会如何设计它的评测？

回答： 临床文本属于高风险场景，因此评测以临床医生审核和严格的重大错误定义为核心，自动化指标仅作为辅助。

我会检查的内容：

  • 由临床医生审核的去标识化病历黄金集，覆盖常见和复杂病例。
  • 针对原始病历的声明级忠实度，对虚构的药物、剂量或诊断零容忍。
  • 对关键项目的遗漏检查，例如过敏史和随访说明。
  • 评测裁判与临床医生的校准，并由临床医生持续对样本进行签核。
  • 对评测数据和日志的隐私控制。

生产环境考量： 助手负责起草，临床医生负责批准。上线后评测仍会继续，通过追踪临床医生对每份草稿的修改量来衡量——这是一个强有力的隐式质量信号。

48. 两个提示词版本的平均分几乎相同。你如何做出决策？

回答： 平均值会掩盖差异，因此在宣布平局之前，要先查看分布、切片和成本。

我会检查的内容：

  • 差异是否在多次运行的噪声范围内；如果是，则在质量上属于平局。
  • 按切片划分的结果：某个版本可能在高风险意图上表现更强。
  • 失败的严重程度，而不仅仅是数量：一次重大失败比几次轻微失败更严重。
  • 采用位置交换的成对评审对比，再加上对输出不一致之处的人工复核。
  • 每个提示词的 Token 成本、延迟和可维护性。

生产环境注意事项： 如果质量确实相同，就选择更便宜、更简单的提示词；如果用户体验可能有差异，则进行在线测试。

49. 你的 RAG 助手在印地语和泰卢固语问题上表现较差。你如何调查并修复？

答案： 把每种语言当作独立的评测切片，逐个阶段测试流水线。

我会检查的内容：

  • 黄金集中每种语言是否有足够多的真实母语书写问题，包括语码混合和音译文本。
  • 每种语言的检索召回率：嵌入模型对这些语言的处理是否良好，文档语言是否与查询语言一致？
  • 每种语言的生成质量与流畅度，由母语使用者评审。
  • 评审模型本身在该语言上是否可靠。

生产环境注意事项： 修复手段可能包括多语言嵌入模型、检索前的查询翻译、语言感知的重排序，或翻译后的文档。然后把每种语言的阈值纳入 CI 门禁，使单一语言的退化无法隐藏在平均值中。

50. 你加入一个对线上助手完全没有评测的团队。头几周你会搭建什么？

答案： 先搭建能产生可信信号的最小闭环，再逐步扩展。

我会检查的内容：

  • 如果缺失，为所有请求加上追踪，以便查看输入、上下文、输出和成本。
  • 从真实追踪记录和利益相关者访谈中构建首个黄金集，并与领域专家共同评审。
  • 确定性检查，以及两三个与主要业务风险挂钩的评审指标，并在标注样本上进行校准。
  • 为当前生产版本建立基线分数。
  • 在提示词和模型变更上设置 CI 门禁，并每周评审低分的生产追踪记录。

生产环境注意事项： 从业务方理解并信任的指标入手。一个小而可信、能拦住一次糟糕发布的评测系统，会为你赢得扩展它所需的支持。这正是前沿部署工程师在客户组织内部所做的工作：把 AI 系统从演示推向可衡量的企业成果。FDE 工程师面试题指南涵盖了这一角色。

核心要点

  • LLM 评测衡量模型在代表性数据集上的行为，结合确定性检查、参考指标、经过校准的评审模型和人工复核。
  • 基于真实使用和专家评审构建的带版本管理的黄金集是基础；合成数据可以补充覆盖面，但必须单独评审和报告。
  • BLEU 和 ROUGE 等重叠度指标对开放式回答作用有限；忠实度、相关性以及上下文精确率和召回率可以逐阶段诊断 RAG。
  • LLM 评判器是一种测量工具：要编写具体的评分标准、控制偏差，并在将其作为门禁之前先与人类判断的一致性进行校准。
  • Agent 需要在结果、轨迹和工具层面进行评估，针对沙箱化的工具运行，并在衡量成功的同时测量成本和步骤数。
  • CI 中的离线门禁能阻止已知回归；在线信号和 A/B 测试能发现数据集遗漏的问题，而这些案例又会回流到数据集中。
  • 每个指标都要按意图、语言和用户群体进行切分；平均值会掩盖真正重要的失败。

面试准备清单

  • 为一个 RAG 应用构建一个小型黄金集（五十到一百条），并用确定性检查加两个评判器指标对其进行评分。
  • 自己标注一个样本，测量评判器与你标注的一致性，并准备好讨论其中的分歧。
  • 运行一个评测库，例如 Ragas 或 DeepEval，并准确解释其中某个指标是如何计算的。
  • 将一次评测运行接入 GitHub Actions 工作流，使其在与存储的基线对比出现回归时失败。
  • 评估一个 agent 任务，使用返回成功、空值和错误响应的模拟工具。
  • 准备一个关于某个指标误导了你、以及你做了什么改变的故事。
  • 能够在白板上画出从离线到在线的反馈闭环。
  • 回顾你的评测运行成本，以及你会如何降低它。
  • 大声练习情景问题，使用“先检查、后修复”的结构。

常见问题

LLM 评估岗位需要哪些技能？

你需要 Python、统计学基础（如抽样、方差和一致性度量）、对 RAG 和 agent 架构的理解、编写评判标准的经验，以及熟悉追踪和 CI 流水线。领域直觉也很重要，因为好的评估标准来自对用户和业务实际需求的理解。

LLM 评估是一个独立的岗位，还是 AI 工程的一部分？

两种情况都存在。有些团队设有专门的评估或 AI 质量工程师，但在大多数团队中，评估是 AI 工程师、GenAI 工程师、MLOps 工程师和前沿部署工程师的核心职责。面试官越来越把评估能力视为生产经验的标志。

应届生应该如何准备 LLM 评估面试题？

学习本指南中的指标定义，然后构建一个小型 RAG 项目，包含黄金集、几个评判器指标和一个 CI 检查。能够展示你的评测结果、解释你发现的某个失败以及你如何修复它，比死记指标名称更有说服力。

AI 评估面试需要懂统计学吗？

你需要的是实用统计学而非理论：样本量和噪声、置信区间、两个变体的比较，以及 Cohen's kappa 等一致性度量。高级岗位可能还会问到 A/B 测试的实验设计以及如何避免提前停止。

我应该学习哪些 LLM 评估工具？

学习一个指标库，例如 Ragas 或 DeepEval，一个追踪与评测平台，例如 LangSmith 或 Langfuse，并了解配置驱动的运行器（例如 promptfoo）是如何工作的。了解云服务商的评测服务对平台相关的岗位会有帮助。这些概念在不同工具之间是相通的，因此精通其中一个比浅尝辄止地了解所有工具更有价值。

RAG 评测面试题与一般 LLM 评测题有什么不同？

两者有重叠，但 RAG 题目侧重于使用上下文召回率、上下文精确率和忠实度等指标来区分检索质量与生成质量，此外还涉及对无法回答问题的行为表现以及引用准确性。一般 LLM 评测还会涵盖裁判模型、安全性、Agent 和在线测试。

Agent 评测面试题通常如何设置？

面试官通常会问你怎么衡量任务成功、如何评估工具调用序列、在工具具有副作用时如何安全地进行测试，以及如何处理多轮会话。至少会有一个场景题，关于一个 Agent 虽然成功了，但速度太慢、成本太高或采取了不安全的捷径。

对于印度工程师来说，AI 评测是一个好的职业方向吗？

在海得拉巴、班加罗尔等地的 GCC、产品公司和服务企业中，AI 相关岗位越来越要求具备评测技能，因为企业在向客户交付 AI 之前需要拿出证据。这些技能与测试、SDET、数据和 MLOps 背景也能很好地结合。
