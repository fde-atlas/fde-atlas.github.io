NVIDIA SkillSpector 评测：这个 Agent 技能扫描器能发现什么、会漏掉什么，以及 SAFE 意味着什么

原标题：NVIDIA SkillSpector Review: What the Agent Skill Scanner Catches, What It Misses, and What SAFE Means

FDE Interviews · 2026-11-12 · 约 11 分钟读完

摘要

作者在隔离容器中用 NVIDIA 开源的 SkillSpector 2.13.4 扫描七个自制的 AI Agent 技能。静态分析可靠地拦下了向服务器发送令牌的脚本和含已知 CVE 的旧依赖，但对纯指令型攻击偏弱：一条隐藏注释指示 Agent 偷偷复制对话的技能仅得 7 分、判为 SAFE。原因是判定取决于 0 到 100 的总分而非最严重发现，默认 CI 退出码只在 50 分以上失败。文章建议以发现项而非 SAFE 标签作为门禁，开启 LLM 阶段审查指令文本，并配合哈希锁定、人工审读和运行时限制。

要点

  • 静态分析准确拦截令牌外传脚本与含 CVE 的旧依赖。
  • 隐藏“别告诉用户”指令的技能仅得 7 分被判 SAFE。
  • 判定基于总分而非最严重发现，CI 默认 50 分以上才失败。
  • 建议以发现项为门禁，LLM 阶段审查指令文本。
  • 还需哈希锁定技能、人工审读脚本并限制运行时权限。

实践一下：设计编码 Agent 插件钩子的控制机制 · AI 安全与治理问题 · Agent 沙箱的概念 · 必知的 FDE 面试问题

NVIDIA 的 SkillSpector 是一款免费的开源扫描器，在你安装 AI Agent 技能之前读取它，并评估其风险程度。我们在七个自编测试技能上运行了 2.13.4 版本。它明确标记了两个明显的威胁：一个向服务器发送令牌的脚本和一对过时且有漏洞的依赖项，两者均被评为 DO NOT INSTALL。然而，在关闭可选的 LLM 阶段后，三个任何认真审阅者都会拒绝的技能却被评为 SAFE，其中一个技能的隐藏注释指示 Agent 将对话复制到 gist 且绝口不提。 我们的结论：把它作为门禁之一，对指令文本启用 LLM 阶段，并基于发现的问题而非仅凭 SAFE 标签来决定是否让构建失败。

SkillSpector 是什么

Agent 技能就是一个文件夹：一个

SKILL.md

指令文件，通常附带 Agent 可以运行的脚本。Claude Code、Codex CLI、Gemini CLI 等其他 Agent 会以用户的权限加载技能，而社区市场现在成千上万地分发这些技能。这使得技能在某种意义上成为与 npm 包一样的供应链制品，但有一个特别之处：载荷的一部分是模型会遵从的自然语言文本。

SkillSpector 由 NVIDIA 以 Apache 2.0 许可发布，可以从目录、单个文件、Git 仓库、URL 或 zip 扫描技能。它有两个阶段：

  • 静态分析。 正则表达式模式、针对 subprocess 和 eval 等调用的 Python AST 检查、从机密到网络调用的污点追踪、YARA 签名，以及针对 OSV.dev 的依赖项查询。2.13.4 版本列出了 17 个类别共 71 种模式，涵盖从 提示注入 和数据外泄到 MCP 工具投毒。本周流传的截图显示的是 64 和 16，那是旧版 README。
  • LLM 语义审查（可选）。 配置的模型会结合上下文和意图审查静态发现。其 README 在这一点上很谨慎：已确认的发现可以提升置信度，有争议的发现会被标记为 llm-unconfirmed，而每个确定性发现都会保留在报告中。该阶段不会删除发现，README 也声明它不保证 精确率。

输出是一个 0 到 100 的评分及建议，形式可以是终端、JSON、Markdown 或 SARIF。SkillSpector 也是 NVIDIA Verified Skills 流水线的一部分，该流水线在技能进入 NVIDIA 自家目录之前对其进行扫描和签名。

正确解读推介背后的数字

README 及分享它的帖子引用了一项研究："Agent Skills in the Wild"（Liu 等，arXiv 2601.10338，2026 年 1 月）。有三个细节会改变这些数字被引用的方式：

被引用的说法论文实际内容
“在 42,447 个技能中，26.1% 存在漏洞”收集了 42,447 个；分析了 31,132 个。被分析集合中 26.1% 至少存在一种漏洞模式（约 8,126 个技能）。
“5.2% 是恶意的”5.2% 表现出“强烈暗示恶意意图”的高危模式，这是一种基于模式的估计。
“LLM 分析将精确率提升到约 87%”86.7% 的精确率和 82.5% 的召回率属于论文自有的 SkillScan 方法，而非 SkillSpector 的 LLM 阶段。

同一第一作者的后续研究（arXiv 2602.06547，2026 年 2 月）收集了 98,380 个技能并动态验证了行为。它确认了 157 个恶意技能，约 0.16%，并发现其中一半以上来自同一个使用模板化品牌仿冒的行为者。数据集不同，方法不同，因此这两个比率不能相减。有意义的解读是：粗心且有风险的技能很常见，而确认恶意的技能更少见且是有意为之。其标题"Do Not Mention This to the User"恰好描述了我们最难的测试用例。

我们测试了什么

我们在其 Git 标签上于一个一次性 Docker 容器内构建了 SkillSpector 2.13.4，并以只读方式挂载扫描了我们编写的七个技能。我们只运行了静态分析（

--no-llm

），因为 LLM 阶段会把文件发送给模型提供商，且其结果取决于你选择哪个模型。我们扫描的内容没有任何被执行，无论是由我们还是由工具。这些技能是：

测试技能审阅者意见得分与判定发现
纯格式化指令，无脚本没问题0，SAFE无
运行 git status 的脚本没问题16，SAFE使用子进程，未声明权限（均为 MEDIUM）
将环境中的令牌发送到服务器的脚本拒绝65，DO NOT INSTALL凭据流向网络汇点（CRITICAL）
固定 requests 2.19.0 和 pyyaml 5.3拒绝或升级62，DO NOT INSTALL通过 OSV.dev 发现的已知 CVE（CRITICAL 和 HIGH）
从字符串片段构建模块和函数名，然后运行 shell 命令的脚本拒绝13，SAFE动态导入（MEDIUM），动态属性（LOW）
隐藏的 HTML 注释，指示 Agent 读取 ~/.aws/credentials 且不作声拒绝22，CAUTION凭据文件访问（HIGH）
隐藏的 HTML 注释，指示 Agent 将对话复制到新的 gist 且永不告知用户拒绝7，SAFE隐蔽指令（MEDIUM）

前四行是工具按宣传方式工作的表现。良性脚本得到两条警示性发现，得分仍为 SAFE，这对审阅队列来说是正确的结果。令牌发送者和过时依赖被高置信度地捕获。

扫描器发现了问题，并正确地将其标记为提示注入，但计算结果仍然给出了 SAFE。一个读取

issues

而不是

recommendation

的门禁本可以拦住它。

最后三行才是教训。拆分字符串脚本是绕过模式匹配器、隐藏

os.system

的一种众所周知的手法。SkillSpector 注意到了动态导入并明确指出，但分数仍停留在 13。隐藏注释类技能是指令攻击：其中没有任何代码。提到凭据文件的那个因为路径触发了 HIGH 发现，但分数仍落在 22 的 CAUTION。要求 Agent 外传对话并加以隐藏的那个既没有提到文件也没有提到命令，得分仅为 7。

分数如何转化为判定

阅读源码就能解释这些结果。各发现累加得到 0 到 100 的分数；决定判定的是分数本身，而不是最严重的发现：0 到 20 为 SAFE，21 到 50 为 CAUTION，51 及以上为 DO NOT INSTALL。CLI 只有在分数超过 50 时才以非零值退出。对于任何想把它接入 CI 的人来说，这意味着三个后果：

  • HIGH 发现可能出现在 CAUTION 判定之内，而 MEDIUM 级别的提示注入发现可能出现在 SAFE 之内。
  • 默认的退出码门禁会放行所有 50 分及以下的内容。 在我们的样本中，这包括审查者会拒绝的全部三个技能。
  • 指令级攻击是静态分析最薄弱的地方，而这恰恰是后续研究在野外发现的那一类：嵌入在文档中的对抗性指令。

这些都不是工具诚信方面的缺陷。README 明确将第一阶段定位为“高召回率”和“中等精确率”，并列出了运行时行为和非英文文本作为局限。风险在于团队如何解读仪表盘上的那一个词。

数据外传与信任模型

在对内部技能运行它之前，有两条网络路径需要注意：

  • LLM 分析会将文件内容发送到你配置的提供商。 SkillSpector 支持 OpenAI、Anthropic、Bedrock、Google Cloud 上的 Gemini、NVIDIA Build、Azure OpenAI、本地 Ollama 或 vLLM 等。对于提到主机名或运维手册的内部技能，请选择经批准的端点或本地模型。
  • 依赖检查会将包名和版本发送到 OSV.dev，即使使用 --no-llm 也是如此。它发送的是坐标而非文件内容，并且在离线时会回退到一个内置的小型列表。

SkillSpector 从不运行技能，它也不是一个沙箱。它告诉你技能在安装前是什么样子；对于你无论如何都要安装的技能，它无法起到任何遏制作用。那种遏制是单独的控制措施，在 agent 沙箱化 中有介绍。

我们会如何推广落地

对于允许工程师安装技能的团队，我们会采用以下顺序：

  • 对每个新技能和每次更新运行静态分析，以 SARIF 格式输出到安全团队已经在关注的代码扫描视图中。
  • 以发现的问题而非判定结果作为门禁失败标准。 任何 HIGH 或 CRITICAL 级别的发现，以及任何提示注入、数据外泄或动态执行类的发现，无论评分如何都必须交由人工处理。使用基线文件来接受已知的、经过审查的发现，这样重新扫描时只会显示新问题。
  • 对指令文本运行 LLM 阶段，通过经批准的提供商进行，并固定使用一个模型，以确保各次扫描之间的结果具有可比性。
  • 任何包含脚本的技能都必须经过人工阅读。 该研究发现这类技能包含漏洞的可能性高出 2.12 倍。
  • 在内部注册表中按哈希值固定已安装的技能，并在每次版本变更时重新扫描。上个月干净的技能明天可能就带上了新脚本；插件生命周期钩子也有同样的问题，正如coding-agent 插件钩子问题所探讨的那样。
  • 限制已安装技能能触及的范围：Agent 环境中不放置环境级云凭证、设置出站流量白名单，并尽可能使用只读挂载。

扫描之后：这个技能到底有没有用？

一次干净的扫描只能说明这个技能不太可能伤害你，却不能说明它是否让 Agent 变得更好。一个没有帮助的技能仍然会在每次会话中消耗上下文，并与其他技能争夺 Agent 的注意力。NVIDIA 的配套工具 SkillEvaluator 会让 Agent 在相同任务下分别在有技能和无技能的情况下运行，并报告两者的差异。我们在SkillEvaluator 评测中解读了其发布的 400 多个技能的结果。

在面试中如何谈论这一点

技能与插件供应链如今已成为 AI 安全与治理 面试中的标准话题，因为前沿部署工程师正是在客户环境中安装 Agent 的人。有力的回答是分层的：安装前用扫描器和人工阅读进行审查，固定所安装的内容，隔离所运行的内容，并监控其行为。无力的回答只是说出一个扫描器的名字就结束了。如果你能解释为什么对一条隐藏的“不要告诉用户”指令评 7 分是流程问题而非工具缺陷，你就展现出了这一轮面试所考察的判断力。更宏观的模式——模型会遵循其读取的不可信内容——就是换了新包装的 提示注入。

于 2026 年 11 月 12 日针对 SkillSpector v2.13.4（2026 年 11 月 4 日发布）进行了测试。星标数和模式总数变化很快；在依赖这些数据之前，请先查看仓库。

把它转化为录用通知。掌握这些内容对应的真实问题和概念：

常见问题

SkillSpector 是一款 Apache-2.0 协议的 AI Agent 技能安全扫描器，针对 Claude Code、Codex、Gemini CLI 及类似 Agent 加载的指令和脚本文件夹。它在不运行技能的情况下读取技能，对 17 个类别中的 71 种模式（版本 2.13.4）应用静态检查，可选择让 LLM 审查发现的问题，并返回 0 到 100 的风险评分以及 SAFE、CAUTION 或 DO NOT INSTALL 建议。

它表示总分不超过 20。这并不意味着没有发现问题。在我们的测试中，即使存在提示注入和动态代码执行的 MEDIUM 级发现，在关闭 LLM 阶段时技能仍被评为 SAFE，其中包括一个隐藏注释指示 Agent 将对话复制到某处且不告诉用户的技能。请以发现的问题为准，而不仅仅是最终结论。

开启 LLM 分析时（配置了提供商时的默认行为），它会把被扫描文件的内容发送给该提供商。使用 --no-llm 时内容保留在本地，但依赖检查仍会将包名和版本发送到 OSV.dev。SkillSpector 从不执行它所扫描的技能。

SkillSpector 引用的研究收集了 42,447 个技能并分析了其中 31,132 个。其中，26.1% 至少存在一种漏洞模式，5.2% 显示出暗示恶意意图的高危模式。另一项对 98,380 个技能进行动态行为验证的研究确认了 157 个恶意技能，约占 0.16%。这两项研究在不同的数据集上衡量的是不同的东西。

不是，其 README 也明确说明：它是纵深防御，而非沙箱。请将其作为流水线中的一道关卡，该流水线还应通过哈希固定技能、审查技能携带的每个脚本、对指令文本运行 LLM 阶段或人工阅读，并限制已安装技能可访问的范围。

讨论 (4)

拆分字符串的结果是我会展示给安全团队的那种。静态分析本质上是对文本的模式匹配，任何故意编写恶意 skill 的人都会绕过这些模式。这并不是在贬低这个工具，而是第二阶段存在的理由，也是为什么仅凭第一阶段的 SAFE 结果绝不应成为对携带脚本的 skill 的最终结论。

读者提问：既然 LLM 阶段才是真正读取意图的部分，为什么不总是运行它？

成本和数据。每次扫描都会把 skill 的文件发送给模型提供商，这对公开市场的 skill 来说没问题，但对包含运行手册或主机名的内部 skill 来说就是一个需要认真考虑的问题。我们的默认策略是：每次变更都运行静态分析，任何新增或变更的内容都通过经批准的提供商运行 LLM 阶段，而任何携带脚本的 skill 都需要人工审查。

在与客户沟通时，论文本身的数据值得理清。26.1% 是“至少存在一种漏洞模式”，其中包含大量粗心编写的代码。而在后续研究中，经行为确认的恶意比例要低得多。两者都是需要审查的理由，但它们与 CISO 展开的对话是不同的。
