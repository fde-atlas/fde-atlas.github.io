A2UI 1.0 详解：Google 面向 Agent 的生成式 UI 协议、有哪些变化以及何时使用

原标题：A2UI 1.0 Explained: Google's Generative UI Protocol for Agents, What Changed, and When to Use It

FDE Interviews · 2026-11-12 · 约 10 分钟读完

摘要

文章解析 Google 于 2026 年 11 月 11 日发布的 A2UI 1.0，首个稳定版生成式 UI 开放协议。AI Agent 不再输出纯文本，而是以结构化数据描述界面，由应用从注册组件目录中校验并用原生组件渲染。1.0 新增双向函数调用、多目录混用、无障碍属性，并从协议中移除主题。官方基准显示 Express 格式可减少约 2.7 至 3.1 倍 UI 代码 token，输入 token 减少约 45%。文章还对比 AG-UI、MCP Apps、A2A 的分工，并给出适用与不适用场景，强调其适合跨信任边界的 Agent 交互。

要点

  • A2UI 1.0 是 Google 首个稳定版生成式 UI 协议，Agent 以数据描述界面。
  • 应用通过组件目录校验并原生渲染，模型不生成可执行代码。
  • 1.0 新增双向函数调用、多目录混用与无障碍属性。
  • 基准显示 UI 代码 token 减少约 3 倍，输入 token 减少约 45%。
  • 适合需要用户决策、跨端渲染及跨信任边界的 Agent 场景。

A2UI 是一个开放协议，让 AI Agent 用交互式界面回答，例如待确认的表单、图表或审批卡片，而不是一大段文字。Agent 将界面描述为数据，只使用你的应用已注册的组件，而你的应用用自己的原生组件来渲染它。由 Google 于 2026 年 11 月 11 日发布的 1.0 版本是首个稳定版本。它新增了双向函数调用以及混合使用多个组件目录的能力，并提供了 Python、TypeScript 和 Dart 的 Agent SDK。 当 Agent 需要在网页和移动端收集决策或展示结构化数据时可以使用它，尤其是当 Agent 处于你的信任边界之外时。

它解决的问题

Agent 用文本回答，因为文本是模型生成的东西。这对提问有效，对执行任务却不行。比较三个产品、审批一个包含十个步骤的计划，或在四个日程中找出共同可用的时间，都会变成一轮又一轮的“选哪个？”。显而易见的解决办法是让模型直接编写 HTML 或 React，但这会带来更糟的问题：模型任意生成的代码运行在你的产品中，样式随模型喜好而定，行为也由它随意发明。

A2UI 走的是中间路线。应用发布一个目录：即 Agent 可以使用的组件、它们的属性以及它可以调用的函数。Agent 从该目录中以结构化数据的方式组合出一个界面。应用对其进行校验并原生渲染。Agent 控制布局与连接方式；应用控制存在什么以及它做什么。

工作原理

A2UI 有三层：

  • 推理层。 模型以推理格式编写 UI 描述。新项目的默认选择是 A2UI Express，一种紧凑的构造函数调用表示法，例如 root = Text("Hello")。直接使用 JSON 仍然可行。决策模型也可以从列表中挑选组件，而不是编写文本。
  • 传输层。 Agent SDK 解析模型的输出，根据目录进行校验，展开宏，并发出传输消息：createSurface、updateComponents、updateDataModel 和 deleteSurface，以 application/a2ui+json 格式通过你使用的任何通道发送，包括 A2A、AG-UI 或 MCP。
  • 渲染层。 在应用中，核心库将消息转换为框架无关的 UI 树，框架适配器将其映射为原生控件，而目录则限制了可以出现的内容。

以下是模型实际生成的内容。这个 Express 代码块及其编译出的 JSON 来自项目自身的一致性测试：

root = Column([greeting, farewell])
greeting = Text("Hello")
farewell = Text("Goodbye")
{
  "version": "1.0",
  "createSurface": {
    "surfaceId": "default_surface",
    "catalogId": "conformance/simplified",
    "components": [
      { "id": "root", "component": "Column", "children": ["greeting", "farewell"] },
      { "id": "greeting", "component": "Text", "text": "Hello" },
      { "id": "farewell", "component": "Text", "text": "Goodbye" }
    ]
  }
}

变量名会成为组件 ID，而信封由 SDK 而非模型来编写。如果模型命名了一个目录中未声明的组件，编译会在任何内容到达屏幕之前因验证错误而失败。

值通过数据模型到达屏幕。组件绑定到一个路径，例如

/booking/time

，代理服务器会从你的系统中填充该路径。模型可以在从未看到余额的情况下布局余额字段。用户操作和被允许的函数调用会作为事件回流到代理。

1.0 中的变化

从 0.9 到 1.0 的演进指南很长。对大多数团队而言重要的变化：

变化为什么重要
双向函数调用：callRendererFunction 和 callAgentFunction，各自带有响应消息日期选择器可以当场向代理询问可用性。目录为每个函数声明 allowedCallers，渲染器会拒绝某个角色无权发起的调用
函数上的 requiresUserActivation诸如打开 URL 之类的函数可以要求真实的用户手势，因此代理无法自行触发它们
同一界面上的混合目录一个视图可以组合来自你的应用和合作伙伴的组件，每个组件带有明确的 @catalogId，且没有静默回退
保留的 @ 键（@path、@call、@catalogId、@checks）自定义组件现在可以声明自己的元数据或检查，而不会与协议冲突。指南警告迁移时不要盲目地进行全局查找替换
无障碍属性，包括 ARIA live regions流式 UI 可以向屏幕阅读器播报变化
从协议中移除 theme品牌样式保留在应用中；代理无法重新设计你的产品的样式
整个 UI 在一条 createSurface 消息中；角色重命名（client 变为 renderer，server 变为 agent）更少的往返；更清晰的词汇，因为渲染有时发生在服务器上

渲染器已支持 Web 上的 React、Angular 和 Lit，以及 Flutter 和 SwiftUI。Jetpack Compose 渲染器目前为 0.9.1 版本，1.0 支持已宣布即将推出，而 Gemini 目前渲染的是 0.9.1，因此预计一段时间内实际环境中会存在混合版本。

两点解读。开启思考模式时，大部分输出是推理内容，而 Express 不会压缩这部分，因此总输出的节省约为四分之一而非三分之二。而 45% 的输入节省是更不起眼的收益：紧凑的组件签名取代了系统提示词中的完整 JSON Schema，而这份提示词每一轮都要付费。作为一个粗略的独立验证，该项目 Express 一致性测试套件中的四个多组件案例编译后的压缩 JSON 字节数大约大 3.1 倍（范围 2.4 到 3.8）。字节不等于 token，四个小案例也算不上基准测试，但方向是一致的。

谁在使用它

Google 的发布文章点名了四家外部采用者。Atlassian 正在将 A2UI 引入 Jira，处理工单的 Agent 可以通过工作项中的交互式卡片向团队询问缺失的决策。Alation 用它渲染指标卡片和图表，同一信息流既出现在其产品内部，也通过 MCP Apps 出现在 Claude 中。字节跳动于 2026 年 6 月为其 Lynx 框架发布了 A2UI 渲染器。彭博也在基于它进行开发。在 Google 内部，Gemini Notebook 通过 A2UI 卡片提出幻灯片格式的问题，Gemini Enterprise 的 Agent 也已经能够用 A2UI 做出响应。

有一个细节与我们之前介绍过的工作相关：字节跳动的 Lynx 演练场使用决策模型 Jev 来选择组件和取值，而不是让 LLM 生成文本，而对决策模型的官方 SDK 支持已列入 A2UI 路线图。从固定目录中做选择是一个分类问题，这正是 System One 决策模型既快速又校准良好的领域。

A2UI、AG-UI、MCP Apps 和 A2A

这些名字一起出现，但它们回答的是不同的问题：

协议回答的问题方向
MCPAgent 如何调用工具和读取数据？从 Agent 到工具
A2AAgent 如何将任务委托给其他 Agent？Agent 与 Agent 之间
AG-UI前端如何跟随 Agent 的运行过程：消息、工具调用、状态？从 Agent 到应用，以事件形式
A2UI屏幕应该显示什么，由应用允许的组件构建而成？从 Agent 到应用，以 UI 描述形式
MCP AppsMCP 服务器如何将交互式视图交付到 AI 助手中？从服务器到宿主助手

它们可以组合使用。A2UI 消息可以搭载在 AG-UI 事件或 A2A 消息中，A2UI 界面也可以在 MCP App 内渲染，Alation 的信息流出现在 Claude 中正是通过这种方式。

何时使用，何时不使用

适用场景：

  • Agent 需要获取决策或结构化输入：审批、表单、选择器、对比。
  • 同一个 Agent 同时服务 Web 和移动端，而你希望用一份描述在每个平台上原生渲染。
  • Agent 是远程的、第三方的或跨越信任边界的，你需要限制它能在屏幕上呈现的内容。
  • 敏感值应留在模型上下文之外。

不适用场景：

  • 答案只是纯文本，或者只是一个可以从工具结果渲染出来的静态图表。
  • 你同时控制 Agent 和前端，且 UI 需求只是少量固定卡片；直接使用带类型的工具结果可能更简单。
  • 你需要在组件内部实现任意自定义逻辑。沙箱化逻辑是路线图上的事项，并非 1.0 版本的功能。

前沿部署工程师的视角

在 Agent 设计的讨论中，生成式 UI 正在兴起，其理念是“Agent 不应只是回答，还应让用户批准某些操作”。有力的回答会区分三个决策：模型可以决定什么（从组件目录中选择布局和连接方式）、应用强制执行什么（校验、允许的调用、对任何有副作用的操作要求用户激活），以及数据来自哪里（由你的系统填充的绑定路径，而非模型输入的值）。这种分离与工具调用上的护栏背后的思路相同，只是应用到了屏幕上。请在 RAG 和 Agent 设计问题上练习这一点，并准备好说明为什么你不会让模型向客户的产品中输出 HTML。

常见问题

A2UI（Agent-to-User Interface）是一个开放协议，由 Google 发起，采用 Apache 2.0 许可证，它允许 Agent 用交互式屏幕而非文本来回答。Agent 将 UI 描述为引用应用已注册组件的数据，应用则使用自己的原生组件在 React、Angular、Lit、Flutter、SwiftUI 或 Jetpack Compose 中进行渲染。1.0 版本是首个稳定版本，于 2026 年 11 月 11 日发布。

双向函数调用（Agent 可以调用渲染器的函数，渲染器也可以调用 Agent 的函数，允许的调用方在目录中声明）、在同一界面上混合使用来自多个目录的组件、为协议键保留的 @ 前缀、包括实时区域在内的无障碍属性、扩展元数据、从协议中移除主题，以及除 Python 之外新增的 TypeScript 和 Dart Agent SDK。

对于生成的 UI 代码，根据项目的基准测试，答案是肯定的：在 gemini-3.8-flash 上的 54 个样本中，关闭思考模式时代码 token 减少 2.7 倍，开启思考模式时减少 3.1 倍，且通过率相同。当模型同时进行思考时，总输出减少的幅度要小得多（23%），因为思考 token 不会缩减。输入 token 减少 45%，因为紧凑的组件签名取代了提示词中的完整 JSON Schema。

AG-UI 是一个事件协议，用于将 Agent 的运行过程（消息、工具调用、状态）流式传输到前端。A2UI 描述屏幕包含的内容，即来自已批准目录的组件。MCP Apps 允许 MCP 服务器向 AI 助手交付交互式 UI。它们可以结合使用：A2UI 屏幕可以在 AG-UI 事件中传输，或在 MCP App 中渲染。

它就是为这种场景设计的。Agent 只能放置组件并调用应用已注册的函数，UI 是数据而非可执行代码，并且值可以绑定到 agent 服务器上的数据模型，因此敏感字段无需经过模型。校验、操作处理和授权仍然由应用侧负责。

讨论（4）

正是这种信任边界的框架，使它与前沿部署工作相关。在银行或医院，问题从来不是“Agent 能否画出漂亮的图表”，而是“第三方 Agent 能否在我们的屏幕上放置未经批准的内容”。目录允许清单是安全审查人员真正能够签字认可的答案。

读者提问：如果模型永远看不到敏感值，它怎么知道该显示什么？

它看到的是结构和路径，而不是值。模型放置一个绑定到 /account/balance 的 TextField，agent 服务器从你的系统填充该路径的数据模型。模型决定布局和接线；你的代码决定数值。这和参数化查询让数据远离 SQL 文本是同一个思路。

破坏性变更的说明对已经在用 0.9 的人很重要。Gemini 目前渲染 0.9.1，而 Compose 渲染器仍在 0.9.1，因此混合部署会在一段时间内同时运行两个协议版本。按界面分别固定版本，不要一刀切地把 'path' 替换为 '@path'；迁移指南正是针对这一点发出了警告。
