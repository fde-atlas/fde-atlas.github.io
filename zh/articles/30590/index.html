Docker 离线部署：FDE 的 Dockerfile 实践

FDE Times · 2026-10-08 · 约 4 分钟读完

摘要

文章面向 FDE，把 Docker 定位为客户交付工具而非开发环境。作者指出客户环境常缺外网、root 权限或相同芯片架构，并给出对应做法：docker save/load 离线传输、USER 与 rootless 模式降权、buildx --platform 跨架构构建。文中以 NVIDIA DGX OS 指南和 Overleaf 离线部署文档为例，并提供一个多阶段 Dockerfile 最小示例，建议按 digest 固定基础镜像、用 .dockerignore 精简镜像，最后给出转岗学习路径与简历建议。

要点

  • 镜像越小越可复现，越容易通过客户安全审查。
  • 断网环境用 docker save/load 经 U 盘交付镜像。
  • 无 root 需求时用 USER 指令或 rootless 模式运行。
  • 芯片架构不同需用 buildx --platform 提前构建。
  • 建议先在两台机器间完整演练 build、save、load 流程。

断网、禁用 root、芯片架构不同，Docker 成了交付工具，Dockerfile 决定客户是否放行。

要点速览

  • 对 FDE 来说，Docker 镜像是交给客户的交付包，而不是开发环境。镜像越小、越可复现、所需权限越少，就越容易获批。
  • 客户的基础设施可能缺少三样你习以为常的东西：外网（用 save/load）、root（用 USER 和 rootless 模式）、相同的 CPU 架构（用 --platform）。
  • 第一次去客户现场之前，先在两台不同的机器之间把 build → save → load 完整走一遍。

NVIDIA 的 DGX OS 8 指南用很直白的话描述了把容器镜像送上隔离网络服务器的步骤：把镜像复制到便携存储设备（例如 U 盘），再带到目标系统上。没有镜像仓库，也没有

docker pull

。DGX 服务器获取软件的方式，和二十年前靠安装光盘装机差不多。

如果你是前线部署工程师（FDE），很可能会遇到完全一样的情况，而且不只在 NVIDIA：Overleaf 专门为离线部署的客户写了一份完整指南。开发者写的代码跑在笔记本和 CI 上；FDE 则要让它跑在客户掌控的基础设施上，那里可能不通外网、禁止 root，芯片也和你的不一样。

所以到了 FDE 手里，Docker 不再只是方便开发的工具，而是交付工具。Dockerfile 怎么写，决定了客户的基础设施团队到底让不让你的软件运行。

镜像是交付包，不是开发环境

Docker 官方把 Docker Engine 描述为一种用于构建和打包应用的开源容器化技术。这个说法没错，但对 FDE 来说还不够。你真正交给客户的是镜像，镜像里的每样东西都会经过对方安全团队的检查。

正因如此，多阶段构建在这里远比本地运行时重要。一个 Dockerfile 里写多条

FROM

指令，每条开启一个新阶段；第一阶段包含构建所需的完整编译器和库，最后一个阶段只复制构建产物。Docker 文档用一句话概括了结果：一个精简的生产镜像，里面只有二进制文件。

镜像里的东西越少，要回答的问题就越少，要拷进 U 盘的数据越少，潜在漏洞也越少。同样的道理，

.dockerignore

文件可以把无关文件挡在构建之外，而不必调整仓库结构。

构建之前要问客户的三个问题

第一：服务器能不能上外网？如果不能，交付就靠两条命令。

docker image save

把镜像写成 tar 文件，包含所有父层和标签；

docker image load

再从 tar 文件加载回来，即使用 gzip、bzip2、xz 或 zstd 压缩过也没问题，标签也会一并恢复。

Overleaf 的本地部署指南描述的正是这个流程：把 .tar 文件搬到离线服务器，然后逐个执行

docker load

。

第二：服务需不需要 root？Docker 建议，如果服务无需特权就能运行，就用

USER

切换到非 root 用户。更进一步，rootless 模式可以让 Docker 守护进程和容器都以普通用户身份运行，适合禁止以 root 运行守护进程的客户。

第三：服务器用的是什么芯片？NVIDIA 的指南要求在一台联网、且与隔离系统 CPU 架构相同的机器上拉取镜像。在 ARM 笔记本上构建，再拿到 x86 服务器上，镜像是跑不起来的。借助 buildx 的

--platform

参数做多平台构建，可以指定

linux/amd64

或

linux/arm64

等目标。

一个最小化流程

假设要给一家客户交付一个小服务，客户有一台离线的 x86 服务器。Dockerfile 大致如下，

@sha256:

后面的部分要填入基础镜像的真实 digest：

FROM golang:1.22@sha256:... AS build
WORKDIR /src
COPY . .
RUN go build -o /out/server ./cmd/server

FROM alpine@sha256:...
COPY --from=build /out/server /server
USER 10001
ENTRYPOINT ["/server"]

两行

FROM

，两个阶段，最终镜像里只有二进制文件，并以非 root 用户运行。基础镜像按 digest 固定，因为标签可能变化；Docker 把这当作保护供应链的手段，对 FDE 来说，它的意义很简单：今天测试的镜像，和客户下个月加载的镜像完全一致。

在联网机器上，按正确的架构构建并打包：

docker buildx build --platform linux/amd64 -t acme/agent:1.4.0 .
docker image save acme/agent:1.4.0 | gzip > agent-1.4.0.tar.gz

文件通过便携存储送到客户服务器后：

docker image load -i agent-1.4.0.tar.gz
acme/agent:1.4.0

标签会原样恢复，之后照常运行容器即可。

Docker 不会替你检查基础设施

Docker 会严格按你的要求执行；这个要求是否符合客户的服务器，是你的责任。NVIDIA 要求在与隔离系统 CPU 架构相同的机器上拉取镜像，自有道理：架构应该在敲下构建命令之前就和客户确认，而不是站在服务器旁边才发现。

不固定的标签也一样：构建照样能成功，但下一次构建可能产出不同的镜像。

rootless 模式同样属于守护进程这一侧，也就是说，它要在客户的机器上配置，而不是写在你的镜像里。你可以建议开启，但开启它的是对方的基础设施团队。

非 root 的

USER

也只适用于服务确实无需特权就能运行的情况。如果代码要写入需要 root 权限的路径，先改代码，而不是改 Dockerfile。

先学什么

如果你正打算转做 FDE，不要从容器编排学起。先掌握多阶段 Dockerfile，弄清 digest 和标签的区别，再在两台不同的机器之间完整走一遍 build、save、load，其中一台断开网络。这个流程一个晚上就能做完，学到的却比读一周文档还多。

求职小建议：如果岗位描述提到 on-prem、air-gapped，或者部署到客户自有基础设施，面试前准备好一段离线交付的经历。

简历上别写“熟悉 Docker”，而是写明你打包并交付过一个在非 root 环境中离线运行的服务，再附上优化前后的镜像大小。

NVIDIA 指南里的 U 盘并不代表落后。它提醒你：在客户那一侧，软件只有在你掌控不了的地方跑起来，才算真正交付。
