OpenAI 发布了一篇由 Colin Jarvis 撰写的长文，介绍其前沿部署工程（FDE）团队的工作内容。Colin Jarvis 于 2025 年初创立该团队并负责领导。简而言之：前沿部署工程师深入客户现场解决难题，将解决方案投入生产，然后把行之有效的做法转化为 Codex 技能、插件和产品，并把无效的部分反馈给研究部门。OpenAI 对这一目标的表述是部署鸿沟，即“模型表面上的能力与人们能够可靠用于实际工作之间的距离”。

这篇文章《What FDE means at OpenAI》的不同寻常之处在于，它附带了来自具体部署项目的确切数据。本文对这些数据进行了总结，区分了 OpenAI 的说法与外界可以验证的内容，并解释了这对使用 AI 构建产品或招聘 AI 人才的人意味着什么。关于这一职位本身，请参阅我们此前的解读文章：前沿部署工程师是最热门的技术职位以及什么是前沿部署工程师。

什么是部署鸿沟？

一座跨越鸿沟的桥梁，用以说明 OpenAI 前沿部署工程中模型与实际工作之间的部署鸿沟

Jarvis 认为，模型能力的进步速度超过了使用模型所需的系统和流程。有时缺失的是一款产品。有时模型在基准测试中得分很高，却无法应对真实工作流中的变量和约束。第二种情况尤为重要：这正是厂商基准测试图表与生产环境现实存在差距的原因，我们在 FDE-Gym 基准测试报道中追踪了这一主题——前沿模型只能解决一小部分真实的前沿部署任务。

OpenAI 的 FDE 应对方案有两条分支。在模型已经能够胜任的地方，FDE 与产品团队和客户合作，使解决方案可复用。在模型力有不逮的地方，FDE 与客户精确界定差距，并将其交给研究部门。其既定目标是让每一次合作都为下一个客户留下更好的起点。

原则一：从结果出发

Jarvis 在每次团队会议开始时都会在幻灯片上写下一句话：“从结果出发，做一切必要之事以取得成功，然后再追求规模化。”他提醒说，一个令人印象深刻的演示可以在有人追问它是否在真实世界中有效之前走得很远。这项工作的目标是达到“我们敢在生产环境中为之担保”的标准。

半导体的例子

2025 年年中，约 15 名 FDE 与一家大型半导体客户合作，围绕十余个用例展开工作，目标是让芯片验证实现 AI 原生化。据该文章所述，在该行业中，验证大约占项目工作量的 70%。这些用例包括定向测试生成、根因分析与调试，以及一个架构助手。

有几名 FDE 在几天前才加入，从未接触过半导体行业。他们嵌入验证团队，利用业余时间自学芯片设计，并与客户的工程师一起构建评测，以测试 AI 能否生成有用的测试并诊断芯片故障。每个用例都构建了定制的测试框架。在三到六个月内，所有用例都达到了生产阶段并实现了早期采用。

OpenAI 报告称，基于 AI 的定向测试生成节省了约 48% 的时间，内核优化带来了 22% 的中位数性能提升，数周的调试工作被压缩到数小时。Jarvis 说，客户的首席硬件官询问这些 FDE 是否曾做过芯片设计师。他的观点是：工程师不必在第一天就了解该行业，但学习它是他们的责任，而且随着编码助手让软件开发变得更快，理解客户的业务变得更加重要。

团队中的领域专家

团队将通才与领域专家混合搭配。在生命科学领域，具有科学背景的 FDE 从事临床前药物发现任务，例如靶点验证与优先级排序、基因表达分析以及化学合成路线重构。文章将此定位为做出正确判断和质疑现状假设所需的知识。

原则二：用 Codex 让成功可复制

一个企业部署从单一团队扩展到多个团队，展示 FDE 工作如何迁移到共享的 Codex 技能上

对建设者而言最有用的部分是接下来发生的事情。每个半导体工作流程都成功了，但每个都需要太多定制集成，难以推广到其他团队。到那时，Codex 的能力已经增强，一名 FDE 围绕它重建了他们的应用。团队将用例迁移到一个以 Codex 为核心的共享框架上。

  • 定制应用变成了基于通用 Codex 原语构建的插件和技能。
  • Codex 成为了统一界面，因此为每个用例单独编写的终端 UI 和 CLI 被淘汰了。
  • 每个项目大约移除了 90% 的定制代码。
  • 对 Codex 的集中式改进减少了胶水代码，打包的技能可以由 AI 卓越中心共享和集中管控。

扩展到新团队只需更换连接器或 MCP 服务器、构建新的评测（团队也有相应的技能）并开始运行。OpenAI 给出了一个 2026 年 8 月的例子：首次部署花了两个月，第二个团队只用了一天，后续团队的接入速度更快。

如果你从事 Agent Harness 相关工作，这就是值得借鉴的模式：把领域逻辑放在可移植的技能和连接器中，把评测作为一等公民产物，其余交给平台承载。我们关于 Codex 作为开放 Agent 平台的报道和 Agent 技能指南深入讲解了具体机制，MCP 入门则解释了连接器部分。

从客户部署成长为产品的案例

Jarvis 表示，OpenAI Presence——其面向企业的语音和聊天 Agent 产品——正是从真实部署中成长起来的。这项工作始于 Swarm，经过 Agents API 的演进，如今文章称，有一位客户超过一半的来电都由 AI 处理。产品本身可参见我们的 OpenAI Presence 发布报道。

Thrive Holdings 的例子是关于会计领域的。前沿部署工程师和研究人员与工程师及会计师合作，为 Crete 的会计师事务所构建了 Tax AI。在试点中，它处理了 7,000 份纳税申报表，吞吐量提升约 50%。出租物业申报是最难的案例：经过六周的工程和实践者审查，才达到 90% 的精确率和召回率。这些模式可复用于其他税表，团队现在正将其应用于记账、审计和 IT 支持。

第三个例子 John Deere 的数字较少。OpenAI 表示，Deere 使用其 API 为农民提供 See & Spray 除草技术的个性化设置指导和推荐，文章称该技术最多可减少 70% 的化学品使用。文中未给出 AI 层面的采用指标。

原则三：弥合智能差距

有时更好的产品能让团队简化工作，有时则是模型本身无法胜任。Jarvis 表示，许多重要的合作项目刻意从这些极限处起步，由客户、前沿部署工程师和研究团队共同致力于攻克这些难题。

案例研究是一家大型电信客户，希望将客服平台扩展到语音领域。语音约占其客服量的 90%，且比聊天更难控制成本。在需求界定阶段，OpenAI 的模型在关键生产评测中的得分约为 60%，客服场景中的函数调用和指令遵循是薄弱环节。前沿部署工程师负责构建平台并定义模型需要完成的任务，研究团队则致力于弥补能力差距，用客户的需求持续测试 successive 模型快照。六个月内，评测得分从约 60% 升至 80%，随后超过 90%，达到了生产环境所需的水平。

由此产生的语音模型现在支持该客户、其他定制客服部署，以及通过 Presence 提供的托管部署。用 Jarvis 的话说，这是“让自己变得多余”的第二个版本：把当今模型无法解决的问题转化为未来模型能够具备的能力。这也与 OpenAI 的语音工作相关，例如面向语音 Agent 的 GPT-Live-1。

为什么这对用 AI 构建产品的人很重要

首先，它展示了一家前沿实验室认为企业价值在哪里产生：不在于模型本身，而在于围绕模型的评测、工具框架和领域知识。其次，这表明各实验室正在嵌入式工程上展开竞争，这一模式也体现在 Databricks 在 3,500 名工程师中部署 GPT-6 Astra 以及 Anthropic 的 Claude Frontier Academy 中。第三，Codex 整合的故事表明，今天编写的定制 Agent 代码明天可能被平台功能删除，因此应投资于能在更换中存续的评测和连接器。

如果你想得到这份工作该怎么做

Jarvis 的招聘信号是一致的：选择困难的问题，学习客户的业务，偏好简单的解决方案（“奥卡姆剃刀适用”），并构建人们可以依赖的东西——而他称这个行业“被夸大其词所污染”。我们的 FDE 准备指南、面试题和关于该职位如何重塑工作的分析介绍了如何准备。首先练习构建评测；这是帖子中重复最多的技能。

局限与未决问题

  • 这篇帖子既是描述，也是一篇招聘和定位文章，结尾还发出了与团队合作或加入团队的邀请。
  • 没有提供成本数据：半导体部署需要多少 FDE 时间，价格是多少？
  • 90% 的定制代码减少衡量的是删除的代码行数，而非总体节省的工作量。
  • 帖子未说明有多少客户获得了 FDE 支持而非自助服务，也未说明团队如何扩展。

帖子的结尾一句正是其主旨：当 Codex 能够处理你花了几个月构建的工作时，“去找更难的问题吧。”
