FDE 每周到底在做什么

原标题：What FDEs Actually Do All Week

FDE Hub · 2025-12-09 · 约 7 分钟读完

摘要

作者以 Lleverage 创业公司 FDE 的一周为例，讲述前沿部署工程师的真实日常：同时服务十个客户、约五十小时工作，一半时间开会、一半时间构建。文章指出创业公司 FDE 与 Palantir、OpenAI 的深度驻场模式不同，更强调跨客户的模式识别，核心能力在于理解业务而非单纯写代码。

要点

  • 创业公司 FDE 同时并行服务约十个客户，与 Palantir 式深度驻场模式不同
  • 时间大致五五开：一半开会沟通，一半写代码、调 prompt 和测试
  • 从 PoC 到生产是最大挑战，原型架构往往需要推翻重来
  • 客户多用业务方沟通，需反复管理对 AI Agent 能力的预期，并沉淀成 playbook
  • 核心能力是跨混乱组织的模式识别，而非纯技术

自从我开始撰写这份通讯以来，已有数十人联系我，说他们喜欢我分享的关于 FDE 角色的内容。最常见的请求是什么？多讲讲日常工作。真实的体验。一周实际上是什么样的？

有道理。这是上周的情况。十个客户，五十个小时，还有多到让人头晕的上下文切换。

简单说明一下：在 Palantir 或 OpenAI 这样的大公司，FDE 通常一次只深入服务一两个客户。而在 Lleverage 这样的初创公司，我同时在多个客户之间并行开展部署。这是这个角色的另一种版本：深度更少，但更多跨场景的模式识别。两者都是合理的。这就是初创公司 FDE 的体验

周一：规划混乱

一周从一场规划会议开始。我、其他 FDE 以及我们的客户交付负责人坐下来一个小时，逐一审查每个活跃客户，并确定本周的优先事项。

这听起来很公司化。其实不是。这是生存需要。

当你同时服务十个客户时，你需要知道哪些火苗正在闷烧，以免它们变成大火。哪个 PoC 即将到期。哪个客户已经沉默太久，这通常意味着他们卡住了，只是还没告诉我们。哪个潜在客户需要在失去兴趣之前进行一次需求界定电话会议。

我们用 Linear 来跟踪一切。每个客户都有自己的项目、自己的任务集、自己的状态。没有这个，我一天之内就会迷失方向。

规划之后，周一剩下的时间就是一连串的电话。与现有客户的状态更新。与一个潜在客户的售前电话，试图弄清楚他们想要的东西是否可行。等我抬起头来，已经是下午 6 点，而我一行代码都没写。

这种情况比我希望的更常见。

两个进行中的构建

目前我有两个客户处于活跃构建阶段。

第一个是为一家保险公司做的文档处理流水线。我们大约完成了 80%，听起来接近完成，但其实不是。核心工作流程已经能跑通。我可以接收他们的文档，提取他们需要的数据，并以他们要求的格式输出。

但那 80% 只覆盖了理想路径。接下来才是难的部分。

边缘情况。不符合预期格式的文档。有时存在有时不存在的字段。OCR 难以处理的手写批注。还有一位客户发送的扫描 PDF 分辨率低到让提取结果不可靠。

这周我花了几个小时做提示词调优。添加额外的上下文来帮助模型理解它看到的内容。扩大测试样本量，以捕捉我们尚未见过的失败。这不是什么光鲜的工作，但它是让人眼前一亮的演示与真正在生产环境中运行的系统之间的差别。

第二个项目还处于早期阶段。我们已经在少数几组输入输出对上验证了概念可行。现在需要扩展到 100 组以上，这意味着原型阶段行之有效的架构可能撑不住了。

这是没有人会替你准备的转变。PoC 是一场魔术，生产环境则是管道工程。从前者过渡到后者，往往需要重新审视那些当初只是为了证明“这事儿能做成”而做出的决策。

沟通的蔓延

有一件事没人提醒过我：我登录着几十个 Slack 工作区和 Microsoft Teams 实例。

每个客户都用他们自己的工具，我们则迁就他们。所以有些客户用 Slack，有些用 Teams。每个都有自己的频道、自己的通知提示音、自己的话题线程规范。

再加上我们内部使用的工具：用 Linear 做项目跟踪，用 Notion 做文档，用 Google Docs 共享规格说明和提案，用 Excel 做数据分析（也常常作为数据来源），用 Postman 做 API 测试，用 Claude 做所有事情——从写代码、起草客户沟通内容，到梳理问题思路。

上下文切换不只是在不同项目之间来回移动。它意味着要记住哪个客户用哪个工具、哪个频道是处理紧急问题的而哪个是发一般性更新的，以及三天前我最后一次处理他们的问题时，对话进行到了哪里。

当系统出故障时

上周，Cloudflare 宕机了。

我们的系统依赖 Cloudflare，这意味着 Cloudflare 出问题，我们的客户就会出问题。而客户一出问题，就会给我们发消息。

我半天的时间都耗在了救火上：查看状态页面，给惊慌失措的客户发送更新，试图弄清楚我们是否有办法绕过这次故障绕路而行。没有办法，但你还是得去查。

这是工作中不会出现在规划文档里的部分。你可以把完美的一周安排得明明白白，然后某个上游供应商出了事故，你突然就进入了被动应对模式。深度专注的工作被推迟，你本来要写的代码又得再等一天。

我们有监控机制来尽早发现这类问题，这有帮助，但并不能消除干扰。

五五开的时间分配

老实说，我的时间分配大概是 50% 开会、50% 构建。

开会包括：客户例会、内部规划、售前通话、范围界定会议、状态更新，以及系统出故障时偶尔的救火电话。

构建包括：实际编码、提示词工程、测试、调试，以及把关于我们需要哪些基础能力的洞察反馈给产品团队。

我尽量把周二和周四保护起来用于深度工作。四个小时的时间块，让我能真正在复杂问题上取得进展。这并不总是能实现。客户升级投诉或潜在客户的紧急电话随时可能打乱任何一天。但当我真的能拿到这些时间块时，那才是真正的工作发生的时候。

会议之间的短暂间隙，那些零散的 30-60 分钟，是用来做小修复和维护的。你不可能在 45 分钟内设计出一个系统架构。但你可以调整一个提示词、回复一个客户问题，或者查看测试结果。

人的部分

我的大部分对话对象是业务利益相关者，而不是技术人员。

这一开始让我很意外。我原以为会花更多时间和工程师打交道。但实际上，我主要在需要系统访问权限或集成方面的帮助时才和技术人员交流。日常工作面对的是运营经理、部门主管和高管，他们都在试图弄清楚 AI 到底能为他们的业务做什么。

这意味着大量的“翻译”工作。解释什么是可行的。管理对 AI Agent 能力边界的预期。把“我们想要一个能自动搞定一切的 AI”这类需求，引导到“让我们先从这些具体的输入和输出开始”。

我们发现自己反复解释同样的内容，次数多到干脆做了一份操作手册。这是一份分享给每个客户的文档，涵盖：我们需要他们提供什么数据、我们如何沟通、他们应该如何测试和反馈，以及如何提供 SOP 和业务规则。

最后一部分至关重要。AI Agent 不是魔法。它们需要上下文。它们需要示例。它们需要先理解你业务的规则，才能实现任何自动化。这份手册在我们写下第一行代码之前就设定好了这种预期。

周五：内部事务

到了周五，客户电话逐渐减少，内部工作开始增多。

这时候我们会进行团队同步、复盘和产品反馈会议。这些对长期发展很重要的事情，在客户工作繁忙时往往被挤掉。

产品反馈循环是我认为这份工作中最有价值的部分之一。当你在多个客户那里实施相同的模式时，你会开始看出哪些内容应该被抽象到平台中。我会花时间和产品团队讨论哪些基础组件我们一直在从零构建，这意味着它们或许应该作为可配置的功能存在，而不是每次都要重新编写的代码。

这个角色真正需要什么

回顾上周，有几点很突出。

第一：你必须能适应混乱。十个客户、不同的工具、不同的阶段、不同的问题、不断的上下文切换。如果你需要长时间不受干扰的专注才能高效工作，这个角色会把你击垮。

第二：技术工作是真实存在的，但很碎片化。你并不是每天花八个小时写代码。而是这里写两个小时，那里写四个小时，剩下的时间都花在那些决定代码应该做什么的沟通上。

第三：业务这一面是无法回避的。如果你只想埋头做东西、不想和人打交道，这个岗位不适合你。我每周大部分时间都在沟通：翻译需求、管理预期、协调各方利益相关者的关系。

第四：你要承担完整的上下文。每个客户一名 FDE，没有交接给交付团队的环节。你规划的范围就是你要构建的东西。这很累，但也让人清醒。你不能过度承诺，因为负责交付的人就是你自己。

诚实的版本

如果要用一句话概括这个角色的本质，那就是：这份工作与其说是构建 AI 系统，不如说是深入理解业务，从而知道该构建什么。

技术能力很重要。你需要会写代码，理解 LLM 的工作原理，能在压力下调试系统。但真正的差异化能力，是在混乱的人类组织中识别规律的能力。看清真正阻碍客户的问题是什么——而这往往不是他们口中所说的那个。知道什么时候该据理力争，什么时候该按他们要求的去做。

每一周都不一样，每一个客户都不一样。唯一不变的是，我精心规划的周二深度工作时段，多半会被某件事打断。

这就是这份工作。
