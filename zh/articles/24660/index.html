Python 性能分析：cProfile 与 py-spy 用法

FDE Times · 2026-10-22 · 约 5 分钟读完

摘要

cProfile 适合可重跑的脚本，py-spy 可在不改代码、不重启的情况下剖析运行中的进程。本文讲清两者用法及容器中的 SYS_PTRACE 权限。

能重跑脚本就用 cProfile；进程已在客户机器上运行，就用 py-spy 从外部采样，不改代码。

要点速览

  • cProfile 测量每一次函数调用，结果精确，但会拖慢程序。py-spy 从进程外部采样，开销极低，可用于生产环境。
  • cumulative 列指向算法选择不当，time 列指向热点循环。先修算法。
  • 在容器内，py-spy 需要 SYS_PTRACE 权限。在客户集群上，修改安全上下文之前先问管理员。

客户的一个夜间任务原本跑 20 分钟，如今已经跑了三个小时还没结束。会议室里每个人都有自己的猜测：数据库、网络、刚升级的那个库。优秀的前线部署工程师（FDE）不会再多提一个猜测。他们会运行性能剖析工具，十分钟后就能指出到底是哪个函数吃掉了时间。

这项技能听起来很基础，但在客户现场，它决定你能否保住对方的信任。你通常不能随意改代码，也不能重启正在运行的服务，同时还得向一行相关代码都没写过的人解释结果。

本指南针对这两种情况介绍两个工具：能重跑脚本时用 cProfile，进程已在客户机器上运行时用 py-spy。

要做什么，需要准备什么？

你将对一个故意写慢的模拟数据管道做性能剖析，读懂结果，修复后再测一次。你需要 Python 3、一个终端，以及按 GitHub 上 benfred/py-spy 仓库说明安装好的 py-spy。Docker 一节要求本机装有 Docker。

下面是示例脚本。它模拟一个非常常见的 enrich 步骤：把每一行交易数据与客户信息关联起来。

# slow.py — 模拟数据管道，故意写慢
def load_rows(n):
    return [{"id": i, "customer": i % 1000} for i in range(n)]

def enrich(rows, customers):
    out = []
    for r in rows:
        # 对每一行都在列表中做线性查找
        match = [c for c in customers if c["id"] == r["customer"]]
        out.append({**r, "name": match[0]["name"]})
    return out

def main():
    customers = [{"id": i, "name": f"cust{i}"} for i in range(1000)]
    rows = load_rows(50_000)
    enrich(rows, customers)

if __name__ == "__main__":
    main()

第 1 步：运行 cProfile，按 cumulative 排序

cProfile 是确定性剖析器：它跟踪每一次函数调用、返回和异常事件，并精确测量其间的时间间隔。在较新的 Python 版本中，文档把这个剖析器称为

profiling.tracing

，并保留

cProfile

作为向后兼容的别名，所以熟悉的命令依然可用。

python -m cProfile -s cumulative slow.py

检查： 表格顶部，

main

和

enrich

的累计时间接近总运行时间。Python 文档推荐的正是用这一列来发现高层的算法错误。这里问题一眼可见：

enrich

几乎占了全部时间，而它做的只是查找。

第 2 步：改用 time 找出热点循环

python -m cProfile -s time slow.py

time 列是内部时间：函数自身耗费的时间，不含它调用的其他函数。根据 Python 文档，这个数字用来找出值得精细优化的“热点循环”。读一下示例脚本就知道原因：5 万行中的每一行都要扫描全部 1,000 个客户。

视 Python 版本而定，

enrich

内部的列表推导式可能会、也可能不会在表格中单独占一行。无论哪种情况，扫描列表的开销都集中在

enrich

附近，看那里就行。

阅读顺序很重要。先看 cumulative，回答“是不是方法用错了？”；再看 time，弄清“哪个循环需要抠出每一毫秒？”。在错误的算法里优化循环，是浪费时间最快的方式。

简单的修复是只构建一次 dict，然后在其中查找：

def enrich(rows, customers):
    by_id = {c["id"]: c["name"] for c in customers}
    return [{**r, "name": by_id[r["customer"]]} for r in rows]

重新执行第 1 步，比较修复前后

enrich

的累计时间。看绝对数值，不要看排名：

enrich

可能仍排在表格前列、紧挨着

main

，因为在这样的小脚本里它依然是最重的一步。

第 3 步：把结果存入文件以便比较

需要把结果发给同事，或比较修复前后时，用

-o

写入文件，再用标准库的

pstats

模块读取。

python -m cProfile -o before.prof slow.py

常见错误： 在使用

-o

的命令里加上

-s cumulative

，然后奇怪为什么不出表格。文档写明，排序键只在不使用

-o

时生效。有效的键包括

cumulative

、

time

、

calls

和

name

。

另一个错误： 把在 cProfile 下测得的秒数当作真实运行时间报给客户。由于要记录每一个事件，这个剖析器会拖慢程序。用它比较函数之间的比例，真实时间要在关闭剖析器后另行测量。

第 4 步：不能重启时，用 py-spy

在客户环境中，数据管道往往已经在某个 worker 里运行，你不能停下它再用 cProfile 包一层。这时就轮到 py-spy：一个在进程外部运行的采样剖析器。它开销极低，可以在不改代码、不重启任何东西的前提下用于生产代码。

Python 文档也讲清了代价：采样剖析器只能以相对的方式告诉你时间花在了哪里。

先在自己的笔记本上用示例脚本（未修复版本）练习：

py-spy record -o profile.svg -- python slow.py
--

用来隔开 py-spy 要启动的命令。在浏览器中打开

profile.svg

：最宽的块就是耗时最多的地方，它应当与第 1 步的结论一致。

如果想交互式探索、放大查看各个分支，可以导出为 speedscope 格式：

py-spy record --format speedscope -o profile.json -- python slow.py

针对运行中的进程，py-spy 还有两个命令，都通过 PID 挂载。

py-spy top

实时显示哪些函数在消耗 CPU。

py-spy dump

打印每个 Python 线程当前的调用栈。具体参数请查看所装版本的

py-spy dump --help

。

分清“慢”和“卡住”，能更快选对命令。Dagster 的故障排查文档建议在任务卡住时使用

dump

，因为按线程输出的调用栈往往能立刻显示卡在哪里。代码只是慢的时候，用

record

生成火焰图。

第 5 步：容器与客户集群

几乎所有人第一次都会卡在这里。在 Linux 上，默认配置下要挂载到非子进程需要 root 权限。在 Docker 中，默认的 seccomp 配置恰好拦截了 py-spy 读取其他进程内存所用的系统调用，因此容器必须带上这项能力运行：

docker run --cap-add SYS_PTRACE <image>

Kubernetes 默认去掉

SYS_PTRACE

，所以你需要把它加到 pod 的安全上下文中。Dagster 建议先与集群管理员确认这一临时改动是否可以接受。在客户现场，这是必须的，而不只是礼貌。

实用建议：尽早提出这项申请，在第一周就把它列入你的访问权限清单。凌晨 2 点出事故时，没人想去开安全工单。

这项技能在客户现场怎么用？

设想客户反映他们的 enrich 任务每个季度都变得更慢。你在 worker 上运行

py-spy top

，看到一个查找函数占了大部分采样。

接着你在笔记本上用 cProfile 和样例数据复现问题，看到累计时间同样堆在这个函数上。你带回给客户的，是修复前后的火焰图，而不是猜测。

对职业发展而言，这是值得写进简历并附上数字的经历：哪个任务、慢到什么程度、用了哪些工具，以及在关闭剖析器的情况下测得快了多少。

当岗位描述里出现“debug production issues”或“performance tuning”之类的字眼时，准备好这样一个故事，包括申请 SYS_PTRACE 的细节。这个细节能让面试官看出你确实在别人的基础设施上干过活。

下次会议上再有人说“多半是数据库的问题”，你手里已经有了用数据回答的命令。
