专业服务行业的 AI 自建与采购对比（2026）

原标题：Build vs Buy AI for Professional Services (2026)

Rocketlane · 2026-08-14 · 约 11 分钟读完

摘要

Rocketlane 这篇文章讨论专业服务公司应自建还是购买 AI Agent。作者认为传统“自建或购买”的权衡框架已失效：模型智能本身已可租用，真正昂贵的是连接数据源、权限与维护等外围工程。文章借用 Geoffrey Moore 的核心与情境框架，主张交付类 Agent 属于情境，应购买；公司真正该拥有的是专有数据、方法论与判断力。文中引用 Gartner 预测 2027 年底前超 40% 的 Agentic AI 项目将被取消，自建 Agent 年维护成本约为初始投入的 15–20%，并给出三项判断测试与 OneSource Virtual 的混合实践案例。

要点

  • 自建周末原型有价值，但“建了就要一直养”是误区。
  • 模型智能可租用，难的是打通五处数据源并保证可靠性。
  • 自建 Agent 年维护成本约为初始投入的 15–20%。
  • Gartner 预测 2027 年底前超 40% Agentic AI 项目被取消。
  • 结论：租智能、买情境工具，拥有数据、方法与判断力。

专业服务领域中最昂贵的 AI 错误，有些看起来根本不像错误。它们看起来像胜利。

想象一下，你的团队花了一个周末构建一个 AI Agent——那种不只是起草答案，而是真正完成工作的 Agent。到周日晚上它已经运行起来，你把一次销售电话的笔记喂给它。几分钟后，它就生成了一份相当不错的 SOW 初稿，而这通常需要花掉整个下午。

到了周一，结论似乎显而易见：既然可以自己构建，为什么要花钱买工具？

这很容易理解。当这么有用的东西在两天内就拼凑出来时，购买软件就开始像是一种“不自己构建”的税。这个原型感觉就像你做出了正确决定的证明。

但仔细一看，事情并没有那么简单。这只是一张更大账单上的第一行，而大多数公司根本没有预料到这张账单。

那个周末项目只是专业服务会议上一个更大决定的小型版本：我们应该自己构建 Agent，还是购买？

大多数团队把这当作一个关于成本、速度和控制权的问题。但这分散了对真正重要问题的注意力：你公司的优势究竟在哪里，以及你正在权衡的 AI 与此是否有关。

多年来，“构建还是购买”的争论一直是在成本与控制权、速度与定制化之间权衡，然后选边站。人们至今仍在会议中使用这份清单，但它并不真正适合当今的 AI 格局。

如果你自己构建，你就获得了控制权。你的数据留在内部，没有供应商来设定你的路线图或提高你的价格，而且工具完全契合你的工作方式。对于任何涉及敏感客户数据或真正专有方法的东西，这种控制权价值巨大。

如果你改为购买，你获得的是速度和他人的专业经验。你可以在几周内（而不是几个季度）上线运行，维护工作由一家以保持其可靠性为全部业务的公司来处理。

两种情况都站得住脚，而这正是问题所在。只要问题还是“构建还是购买”，双方都是对的，谁也不会改变立场。

这场争论遗漏的是：那个周末原型并不是浪费，即使你从未在生产环境中运行它。构建某样东西会迫使你了解你的工作流程究竟是什么、它在哪里出问题、哪些数据重要，以及人在哪里必须介入。这是真正有价值的知识。

错误不在于为了学习而构建。而在于因为是你构建的，就假设你现在必须永远维护它。

为学习而构建，为扩展而购买。你创建的第一个 Agent 可能正是你乐于放手的那个，因为它的真正目的是让你明白自己真正需要购买什么。

Gartner 预测，到 2027 年底，超过 40% 的Agentic AI 项目将因成本上升、业务价值不明确以及风险控制不佳而被取消。这正是你的周末原型所无法揭示的。

“自建 AI”和“外购 AI”这两个选项过于宽泛，算不上真正的选择。实际上存在两个层面：负责推理的 AI 引擎，以及你围绕它构建的一切，使其在你的业务中有用且可靠。旧有的清单试图同时覆盖这两个层面。

更好的问题是：你应该拥有哪一层，租用哪一层。如果搞清楚了这一点，整个决策就会变得清晰得多。

大多数团队认为，构建 AI Agent 最难的部分是确保它足够聪明，能够处理实际工作，比如理清复杂的客户情况或起草有用的文档。虽然推理质量仍然重要，但从零开始构建核心智能已不再是主要挑战。

模型越来越成为可以租用的东西。让这种智能在你的业务中可靠运行，才是真正的难点。

在专业服务领域，最棘手的部分是为 Agent 提供正确的信息。要发现某个实施项目正在脱轨，它需要项目计划、对应的已记录工时、下周的人员分配、客户在周二电话会议上的发言，以及上季度类似项目的进展情况。

在大多数公司里，这五类信息分散在五个地方。通话录音在 Gong 里。客户历史在 Salesforce 里。交付状态在 PSA 里。资源计划在电子表格里。财务数据则完全在另一个地方。

自研的 Agent 或许可以通过 API 访问其中一两个数据源。但它通常无法实时连接全部五个数据源，并使用正确的权限和标识符，来识别 PSA 中的这个项目对应 Salesforce 中的那个客户账户。

而且一个只掌握一半信息的 Agent 给出的不是半个答案，而是一个自信却错误的答案——这在面向客户的交付工作中要糟糕得多。

我们在Rocketlane构建了一套交付 Agent，而耗费最多心血的行为不是智能，而是克制。当 Agent 在夜间发现迁移差异时，它不会直接套用标准修复方案，而是呈现它发现的问题，并询问是应该解决它，还是等待你的审核。

教会 Agent 何时不应采取行动，需要对客户账户、风险大小以及由谁做决定有真正的了解。这正是周末搭建的方案很少能触及的部分，因为这种判断力并不在模型里，而在模型周围的脚手架中——而这一层始终需要持续的关注。

行业估计显示，每年仅维持一个自研 Agent 运行的成本就相当于原始构建成本的 15–20%。无法持续维护的控制权不是资产，而是一项长期开支。

真正获得价值的企业，并不是那些拥有最先进 AI Agent 的企业，而是那些交付数据早已实现互联互通、干净且得到充分治理的企业——这样 Agent 才有坚实的基础可以立足。

如果智能是可以租用的部分，那么真正重要的问题就是：什么才真正值得拥有。

战略作家 Geoffrey Moore 将企业所做的一切分为两类。核心（Core）是让客户选择你的工作，是你的差异化所在。背景（Context）则是你为了维持经营而必须胜任的其他一切工作，但没有客户会因为这些而选择你。他的法则是：拥有你的核心，租用你的背景。

这就是“什么值得拥有”的答案。

起草 SOW、更新项目记录或标记进度延误的 Agent 属于背景。每家企业都需要它，但没有客户会因为你自己构建了一个版本而选择你，而竞争对手同样可以轻松获得相同的能力。

你的核心是你的判断力、你的客户关系，以及你多年来积累的方法——这些方法让你能够反复地将已签署的合同转化为实际成果，并且比任何人都做得更好。

你的核心从来不是支撑工作的底层软件，而是软件所执行的知识。一个 Agent 可以掌握关于项目的每一个数据点，却仍然会出错，因为了解项目的全部信息并不等同于知道一个优秀的项目应该是什么样子。这才是值得拥有的知识。

这引出了一个令人不安的结论：你最想构建的 AI，通常恰恰是你应该购买的 AI。

那些构建起来最令人兴奋的工具，比如交付 Agent 和你自己工作流内部的自动化，实际上都属于你的背景。它们之所以感觉像核心，是因为它们离你的实际工作太近了。

邻近不等于差异化，而构建背景正是企业悄悄把最优质的资源耗散在无法形成差异化优势的工作上的方式。

有判断力去构建一个真正优秀的交付 Agent 的人，通常是你的一位资深专家——正是客户愿意花最高价钱请到会议室里的那个人。

他们每个月花在完善内部 Agent 上的时间，就是一个月更专注于管道工程而非解决客户问题的时间。SPI 发现，2025 年可计费利用率降至 66.4%，而基准水平超过 70%。把资深人员抽调到内部构建项目上，既是一个技术决策，也同样是一个利用率决策。

所以，真正的问题从来不是“我们能构建这个吗？”你最好的人手大概率可以。

问题是他们是否应该这么做。

核心与背景的区分只有在你能够实际应用时才有用。但这里有一个陷阱：近距离看，一切都像是核心，所以“这是否具有差异化？”恰恰是你最可能答错的问题。你需要更敏锐的检验标准；以下是三个行之有效的方法：

客户是否为此付费，或者在其表现出色时有所察觉？如果不是，那它很可能就是背景，无论它多么精巧。

竞争对手能否仅凭公开信息重建它？如果能，那么拥有它也保护不了什么。

你自己的专有数据能否让它有实质性的提升？如果它之所以有效，仅仅是因为你独特的历史经验或判断力，那才是一个真正的核心信号。这才是值得拥有的那一层。

用这三个问题去检验任何 AI 能力，大多数能力都会自然归入以下三条路径之一。

从实时项目数据中提取的状态报告、能自动运行并验证的迁移、根据日历建议待审批的工时表——如果街对面的竞争对手也需要同样的能力，并且会以几乎相同的方式使用它，那它就是通用能力，你应该直接购买。

你已经明白原因了：智能是可以租用的，而昂贵的部分是围绕它的脚手架——连接、护栏，以及技术底层不断变化时的维护工作。这些都不是你的差异化所在，所以把你最优秀的人才放在这里是错误的。

这就是给那些已经在一个周末做出点东西、或者接入了几个 Claude Agent、又不想把这些成果扔掉的团队的答案。

你不必扔掉。

租用基础部分（引擎、数据模型、维护），并在其上构建一个薄层，用来承载贵公司独特的交付方式。你的 Agent 不会被废弃，而是接入一个能够真正洞察你全部项目数据的系统，你也不用再让一个自研工具去承担它承受不住的重量。

OneSource Virtual 正是这样做的。他们没有从零开始构建平台，而是购买了一个平台，并在其上构建了一个定制的风险评分应用，按照他们对“健康项目”的定义进行调优，从实时薪资数据中提取上线确认信息，而不是依赖静态电子表格。

他们的专家时间没有一分花在重建人人都有的基础部分上，而是全部投入到了真正属于他们、可防御的部分。这不是自建与购买之间的妥协，而是两全其美。

如果 AI 本身就是客户付费的对象，或者你的数据真正独一无二，或者没有供应商能满足真实的合规需求，那就自建。那是你的核心。错误不在于自建，而在于把第一类的东西当成这一类来自我安慰——因为这项工作看起来离你太近了。

我们销售平台，所以坦白我们的立场才是公平的。

这是这个框架中让我们付出代价的部分。如果你诚实地应用它，它有时会告诉你去自建一个我们更希望卖给你的东西，或者什么都不买。这正是测试在起作用——它在寻找你的真正优势所在。

那些今天看起来令人印象深刻的交付 Agent——能起草 SOW、运行迁移、标记风险——正在迅速商品化。很快，每个严肃的平台都会拥有它们，就像每款工具最终都加上了搜索功能一样。

现在自建 AI Agent 是一场与时间的赛跑。你正在投入最优秀的人才去拥有一样每季度都变得更便宜、可以租用的东西。

然而，不会商品化的是 AI 之上的那一层：知道哪个客户即将沉默、第二周（而不是第八周）该谈哪些范围话题，以及哪个项目实施需要你最好的架构师。

AI Agent 会越来越擅长呈现这些需要判断力的决策，但它们不会替你做决策。所以重要的问题不是你的公司是否应该拥有 AI Agent，而是在智能成为商品的世界里，你的公司应该拥有什么。

脱颖而出的公司不会是拥有最多 AI 的公司，而是那些拥有让 AI 变得无可替代的东西的公司：他们的数据、他们的方法论、他们来之不易的判断力，以及让这三者在每个项目中不断改进的反馈闭环。

这些都不是来自模型，而是来自你的公司多年来积累的交付经验，以及承载这些知识的人。
