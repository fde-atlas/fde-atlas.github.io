Forward Deployed Engineers in the Age of AI Agents

How FDEs deploy LLMs and AI agents in enterprises: evals, RAG, integrations, and getting from demo to production.

On AI agent projects, a forward deployed engineer (FDE) connects the model to a customer's real data and systems, defines what "working" means through evals, wraps the agent in deterministic guardrails, and stays until the people who use it trust it. The model is rarely the bottleneck; the work is in permissions, messy data, tool integrations and the months between a convincing demo and a system people rely on.

OpenAI, Anthropic and AWS all run forward deployed teams, and Decagon says nearly every modern AI company now has one. In mid-2026 AWS put $1 billion behind a new forward deployed engineering organization aimed specifically at enterprise agentic AI. The job differs in important ways from the version Palantir made famous.

What changes when the product is an agent

Classic Palantir deployments brought a deterministic data platform to a customer and built integrations and workflow apps around it. Agent deployments keep that integration work and add uncertainty: outputs are probabilistic, the system takes actions, and the model underneath keeps changing. Bob McGrew, who helped build Palantir's model and later led research at OpenAI, argues in an interview on the FDE model that for AI agents there is no ready-made product yet, so the product discovery has to happen inside the customer.

In practice:

  • Measurement replaces specification. Correct behavior cannot be asserted in code, so evals become the acceptance test.
  • Guardrails become architecture. Hard business rules move out of the prompt into deterministic checks.
  • Permissions matter more. An agent that reads documents or opens pull requests needs access controls as strict as an employee's.
  • Prototypes take days, so the bottleneck shifts to scoping, data access and trust.

Data access, retrieval and tools

Customers want an agent that answers from their own policies, tickets and documents, so retrieval-augmented generation is the workhorse. FDE Interviews' skills guide names the two RAG failures that bite in production: surfacing a document the user is not allowed to see, and confidently citing a chunk that does not support the claim.

According to ZenML's write-up of an interview with Colin Jarvis, who leads OpenAI's FDE team, the team often avoids moving data at all. It builds a data or metadata layer with APIs that the model can query in place, and treats MCP connectors as a starting point that still needs logic between raw systems and the model. Agents also get the tools an expert would use, such as a simulator or a sandbox to test their own code.

Evals and guardrails

OpenAI's FDE team calls its method eval-driven development: no LLM-based code counts as done until verification exists. On a semiconductor engagement, the team worked with the customer's engineers to record expert trajectories, the sequence of steps a person follows to triage a bug, and turned them into labeled eval sets before building. On an automotive supply-chain project, rules such as keeping at least two suppliers for critical parts were checked by deterministic code every time, with the LLM handling analysis and running a simulator. FDE Interviews adds that a useful test set covers easy, ambiguous and adversarial cases, and that reading the failures matters more than the aggregate pass rate.

From demo to production

The technical pipeline is often the short part. In ZenML's account, OpenAI's 2023 deployment for Morgan Stanley's wealth advisors had retrieval, guardrails and basic evals working in six to eight weeks, then needed four more months of pilots and labeling with advisors before they trusted it; adoption reached 98%. The semiconductor bug-triage agent first wrote tickets explaining probable causes and only later, as trust grew, proposed fixes as pull requests.

So autonomy expands in steps: users see the agent's reasoning before it acts, and someone at the customer is trained to own the system. Decagon warns about agent builds that decay into "a black box of prompts and patches" and argues that forward deployed teams should design agents the customer can still understand and maintain a year later.

Turning deployments into product

The best-documented loop runs from Klarna to OpenAI's agent tooling. Per ZenML, Jarvis helped Klarna replace hand-written prompts for more than 400 policies with parameterized instructions and tools, each wrapped in evals. OpenAI turned the pattern into Swarm, open-sourced it, validated it on a more complex T-Mobile deployment, and its product team then built the Agents SDK and later AgentKit. The mistake Jarvis warns against is generalizing too early. See building an FDE team for staffing, the Palantir model for origins, and cases for deployment write-ups.

FAQ

What does a forward deployed engineer do on an AI agent project?

They scope the use case with the customer, connect the agent to the systems and data it needs, build retrieval and tool integrations, write the evals that define success, add guardrails and monitoring, and run the pilot with real users until the system is trusted and someone on the customer side owns it. Along the way they report patterns that repeat across customers back to the product team.

What skills does an AI forward deployed engineer need?

Solid production engineering comes first: usually Python or TypeScript, API integration, cloud and data pipelines. On top of that sit four LLM skills: retrieval-augmented generation, eval design, agent and tool-use design, and managing cost and latency. Just as important are scoping vague problems, explaining trade-offs to non-technical stakeholders, and knowing when a deterministic rule beats a model call. Open roles are listed on the jobs board.

How long does it take to get an enterprise AI agent into production?

A working prototype on real data can take days to a few weeks; earning trust takes longer. In OpenAI's Morgan Stanley deployment the technical pipeline took six to eight weeks and piloting took four more months. AWS says its forward deployed teams aim to ship something into a live workflow within 45 days. Regulated, high-stakes use cases sit at the long end of that range.

Why do FDEs write evals before building the agent?

Because an agent's behavior cannot be fully specified in code, the eval set becomes the definition of done. Building it first with the customer's experts forces agreement on what correct looks like, exposes the hard cases early, gives a fair way to compare prompts and models as they change, and produces the evidence a risk or compliance team needs before approving production use.

Will AI agents replace forward deployed engineers?

Agents already write much of the glue code, and AWS describes its field teams working alongside agents to build faster. That shrinks the build phase but leaves the parts that depend on judgment and trust: choosing the right problem, negotiating data access, deciding where guardrails go, and bringing users along. The role is more likely to shift toward that work than to disappear.
