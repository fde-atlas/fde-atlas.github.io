Summary

This monthly-updated guide from FDX (November 16, 2026 edition) catalogs 21 open-weight LLMs with parameter counts, context lengths, and licenses, plus GPU sizing tables and 3-year TCO comparisons. Its core conclusion: 27B–33B models running on a single GPU via FP8 or 4-bit quantization are the most practical choice, mostly under Apache 2.0 or MIT. Flagships whose weights exceed one node (H200×8), like Kimi K3.1 Pro at ~1.56TB, should be consumed via API instead of self-hosted. The article stresses checking licenses per model, since terms differ even within one vendor, and routing custom licenses through legal review. November updates add Mistral Large 4 and replace Kimi K3 with Kimi K3.1 Pro.

Key points

  • 27B–33B models fit one GPU with FP8/4-bit quantization; most practical for enterprise use.
  • Flagships exceeding one H200×8 node should be used via API, not self-hosted.
  • Apache 2.0 and MIT allow free commercial use; custom licenses need legal review.
  • November adds Mistral Large 4 (~1T params); Kimi K3 replaced by K3.1 Pro.
  • Local LLMs pay off only for data-residency, high-volume, or sub-second latency needs.

What is an open-weight model

*Note: The model comparisons and selection guidance in this and the following sections (including parameter counts, context length, licenses, GPU prices, and criteria such as Japanese performance and scale) are based on information as of November 16, 2026. However, GPU prices are reference values and were not re-verified in the November 16 review.

An open-weight model is a model whose trained weights (parameters) are publicly released and can be downloaded and run for inference on your own infrastructure. Unlike cloud APIs, input data can be processed without sending it externally, and the version of the model used can be fixed in-house. Even if the weights are public, the training data and training code are not necessarily released. For this reason, they are distinguished from open source, which publishes source code. The difference from open source and how to read each license type is organized in The difference between open weights and open source.

The range of scales is wide. The 1T-class flagships are Kimi K3.1 Pro, Qwen3.8-2.4T-A95B, DeepSeek-V4-Pro-0813, MiMo-V2.6-Pro, and Mistral Large 4. Below them, the 500B–800B range (Muse Spark Open, Hy4 preview, GLM-5.3, Ling-3.1-flash-1019, DeepSeek-V4.1-Flash) requires a single node with 4–8 H200s. The 120B–320B band now includes Qwen3.8-Flash-Next, MiMo-V2.6-Flash, and GLM-5.3-Flash. The 27B–33B class that runs on a single GPU with FP8 or 4-bit quantization consists of Qwen3.8-27B, Gemma 4 31B, Muse Glimmer 30B, llm-jp-4.1-33b, and Nemotron 3.5 Lightning 30B-A3B. The PLaMo 3 series is also 31B, but its license is proprietary.

What can realistically be run on your own infrastructure is the 30B–120B class; flagships that do not fit on a single node become candidates for API use. The listing order is by scale, not by ranking.

Whether commercial use is permitted depends on the license. Apache 2.0 and MIT (DeepSeek series, GLM-5.3-Flash, MiMo-V2.6 series, Ling-3.1-flash-1019) only require attribution and permit commercial use, modification, and redistribution. The proprietary licenses are Kimi K3.1-Pro License, Qwen3.8-Max License, Qwen Community License 1.0, GLM-5.3 License, Muse Model License, Mistral Ecosystem Open-Weight License, and PLaMo community license, and require legal review. Even from the same provider, conditions differ by model, so do not infer from the vendor name alone. For example, Meta's 30B-class Muse Glimmer is Apache 2.0, but the 816B Muse Spark Open released in October is under a proprietary license. The differences in conditions are organized in the "Model selection points" section below and in FAQ Q2.

Three cases where a local LLM is needed

Local LLMs are heavier to build and operate than cloud APIs. Blindly moving on-premises is inefficient; consider it only when one of the following three cases applies.

Case 1: Data cannot be taken out

  • Financial institutions' customer transaction data
  • Medical institutions' patient records
  • Sensitive information in defense / police / public infrastructure
  • Confidential legal / IP-related documents

More and more cases can be covered even with cloud APIs through Enterprise contracts (exclusion from data training / log retention controls), but if regulations require that "data physically never leaves the country / is not processed in environments outside your control," local deployment is essential.

Case 2: Long-term operations exceeding tens of millions of tokens per month

Cloud APIs are pay-as-you-go, but for workloads that continuously consume tens of millions to hundreds of millions of tokens per month (internal knowledge search / large-scale document summarization / 24-hour chatbots), a local LLM can pay off over a 3-5 year TCO.

A rough break-even guideline: for workloads consuming 100 million tokens per month × 12 months = 1.2 billion tokens per year with cloud spending exceeding $200K, an in-house GPU cluster (4-8 H100s) starts to become an option.

Case 3: Sub-second latency requirements

  • Call center voice responses (responses within 200ms)
  • Real-time translation / interpretation assistance (within 300ms)
  • Search engine completion / autocomplete (within 100ms)

Cloud APIs take 1-3 seconds due to network latency + queue waiting + generation time. Local LLMs are essential for workloads with sub-second requirements.

November 2026 updates (changes from the October 20 version)

1. Mistral AI released the 1T-class Mistral Large 4. Released on October 29, 2026 with weights published on a Hugging Face repository, it is a MoE with approximately 1T total parameters and 49B active (52B including the embedding and output layers). The model card only states the total parameters as "approximately 1T" and does not give an exact figure. Context is 1M, input supports text and images, and the supported languages include Japanese.

The license is Mistral's own modified-MIT Mistral Ecosystem Open-Weight License. If the user or an affiliated company operates Model as a Service (a business that provides the model's capabilities to third parties via API, etc.), a separate commercial license must be obtained from Mistral AI before commercial use, regardless of revenue scale. Internal use that does not provide the model to third parties is exempt from this condition. Even within Mistral AI, the 119B Mistral-Small-4 remains Apache 2.0, with different conditions.

The official FP8 weight files total about 1,061GB, which fits on 8× H200 (1,128GB), but leaves less than 70GB of headroom for the KV cache. For Blackwell-generation GPUs, an NVFP4 version (about 610GB) is published in a separate repository.

2. inclusionAI released an improved version of Ling-3.1-flash. Ling-3.1-flash-1019, published on October 27, 2026, is described in the model card as an improved version of the previous release. The architecture (560B total, 25B active) and license (MIT) are the same as before, and the table has been updated accordingly. The model card states a context of 1M, but the default in the config file is 262,144, and the model card does not describe how to extend it to 1M. If you plan to rely on long context, verify it in your own environment before adopting it.

3. A usage restrictions section was added to the MiMo-V2.6 model cards. On October 28, 2026, a "Use Restrictions" section was added prohibiting uses such as military purposes and malicious cyber activity. The same section states that this addition does not change the model's license, which remains MIT. The license text file still has not been published.

4. After November 4, Kimi K3 was replaced by its successor, Kimi K3.1 Pro. The Hugging Face repository for Moonshot AI's Kimi K3.1 Pro was created on November 2, 2026. It is a model post-trained from Kimi K3 with large-scale reinforcement learning, and is described as the first model in the K3.1 series. The configuration—2.8T total, 104B active, context of 1,048,576, MXFP4 distribution with weight files of about 1.56TB—is the same as Kimi K3. The license is the Kimi K3.1-Pro License; I compared the text against the Kimi K3 License and confirmed that the only difference is the model name. My check of the November 4 edition relied only on the update history of the existing repository, so I missed this model, which appeared in a separate repository.

5. The PLaMo community license was revised on November 9, 2026. Unchanged from before the revision: commercial use requires prior registration with PFN; if annual revenue including affiliated companies exceeds 1 billion yen, a separate commercial license is required; and when providing the model to third parties, a "Built with PLaMo" attribution is required. Compared with the pre-revision text (the November 6 record preserved in the Web Archive), three points changed mainly. Outputs of "transformation models" that only perform conversion or analysis of inputs, such as translation or classification, can now be published without explicitly stating that they are PLaMo outputs (if used as a major part of long published works such as books or papers, it must be stated in the colophon or similar). For Muse Spark Open, which requires an application to access, I confirmed via the file listing that the license text file's last update remains October 15 (the November 10 update was to the chat template only). Model Selection Points

Don't start from scale. Kimi K3.1 Pro is an MXFP4-distribution model built with quantization-aware training (QAT), and the official weight files alone total about 1.56TB. That requires 12 GPUs in H200 (141GB) terms, and it won't fit in an 8-GPU node (1,128GB). This is no longer an on-premise discussion—it becomes a data center business discussion. The pragmatic approach is to accept that flagship-class models are "things to use via API," not "things to build in-house."

The boundary for single-GPU operation is roughly the 120B class. Mistral-Small-4-119B (6.5B active) and gpt-oss-120b (5.1B active) exceed 100B total parameters, but as MoE models their active parameters are small, so inference cost is effectively light. However, MoE requires loading the weights of all experts into VRAM, so estimate required VRAM based on total parameters, not active parameters. Getting this wrong leads to mistaken procurement.

That said, if the distribution format is low precision, requirements drop. gpt-oss-120b's MoE weights are post-trained in MXFP4, and the official model card explicitly states it runs on a single 80GB GPU (H100 or MI300X). DeepSeek-V4-Pro-0813 also has about 1.6T total parameters, but the official weight files are about 0.89TB, which by calculation fits within the 1,128GB of 8× H200. Mechanical calculation from total parameters and the actual distribution format are different things, so always check the model card and file size.

The most realistic class for business use is 27–33B. Qwen3.8-27B / Gemma 4 31B / Muse Glimmer 30B / llm-jp-4.1-33b are Apache 2.0, and Nemotron 3.5 Lightning 30B-A3B is OpenMDW-1.1; none impose revenue or user-count conditions on commercial use. With FP8 or 4-bit quantization, they fit on a single 48GB-class GPU. Most internal use cases (summarization, classification, extraction, first-line responses) are covered by this band.

MIT and Apache 2.0 can be treated as practically equivalent. The DeepSeek family, GLM-5.3-Flash, the MiMo-V2.6 family, and Ling-3.1-flash-1019 are MIT, and the 30B-class models above are Apache 2.0 or OpenMDW-1.1; all permit commercial use, modification, and redistribution. Conditions are limited to things like copyright notices and inclusion of the license text upon distribution. Only the proprietary licenses (Kimi K3.1-Pro License, Qwen3.8-Max License, Qwen Community License 1.0, GLM-5.3 License, Muse Model License, Mistral Ecosystem Open-Weight License, PLaMo community license) require legal review.

Don't decide Japanese-language performance based on published benchmarks. Model turnover happens on a quarterly basis, and there is no established consensus on "the best model for Japanese." Build an evaluation set based on your own business (500–1,000 samples), measure three candidates in practice, and decide. Once built, this evaluation set can be reused for the next model update, turning model selection into an ongoing process.

Inference Infrastructure Options

vLLM (the standard for production operation)

  • Optimized for batch inference on NVIDIA GPUs (PagedAttention)
  • High throughput / low latency
  • Can be wrapped with an OpenAI-compatible API (vLLM provides /v1/chat/completions)

Use cases: enterprise production operation / traffic of 100 req/s or more / hosting multiple models in parallel

llama.cpp (lightweight / on-premise / CPU-capable)

  • C++ implementation with quantization (GGUF) support
  • Runs on CPU too (not fast, but sufficient for PoC)
  • Can run on Mac / Windows laptops as well

Use cases: small-scale on-premise / edge / developer desktops

TGI (Text Generation Inference / official HuggingFace)

  • Deep integration with the HuggingFace ecosystem
  • Stable as an inference server
  • Slightly lower performance than vLLM but easier to operate

Use cases: existing HuggingFace users / validation environments with frequent model switching

Ollama (local development / prototyping)

  • Model download → inference in one command
  • Supports macOS / Linux / Windows
  • Abundant pre-quantized models

Use cases: PoC / individual developer environments / demos

SGLang (performance-oriented)

  • Positioned as an improved version of vLLM
  • Strong at structured output / JSON mode
  • Somewhat higher learning cost

Use cases: structured-output-heavy workloads / cases where vLLM falls short on performance

Flagships whose weights do not fit on a single node (H200×8) can be ruled out for on-premises deployment. The power, cooling, and inter-node connectivity requirements fall into the realm of data center design. Even 1T-class models like DeepSeek-V4-Pro-0813, MiMo-V2.6-Pro, and Mistral Large 4 would mathematically fit on one node thanks to their low-precision distribution formats, but the initial investment would be on the order of $240K. The realistic approach is to use flagship-class models via API or managed inference and run 30B–120B-class models in-house.

On-premises vs cloud GPUs (reference estimates)

For a 4× H100 setup, the numbers are as follows.

  • On-premises: initial $120K (GPUs) + $30K (server / cooling / power) = $150K plus $1–2K/month in electricity
  • Cloud (AWS p5.48xlarge / GCP a3-megagpu): $30–50/hour × 730h = $22K–36K/month
  • Dedicated cloud GPUs (Together / Fireworks / Lambda): $10–20/hour × 730h = $7K–15K/month

Three-year TCO is as follows.

  • On-premises: $150K + $36K (electricity) + staffing costs = roughly $250–350K
  • Cloud: $800K–$1.3M
  • Dedicated cloud: $250–540K

Rule of thumb: for 24/7 full utilization, on-premises is cheaper. For daytime-only operation, the cloud is cheaper.

Domestic data center provider options

  • SAKURA Internet (GPU cloud "Kouryoku" / High-Power)
  • NTT Data (private cloud GPU)
  • Fujitsu (FUJITSU Hybrid IT Service)
  • Domestic H100 / H200 resources are in tight supply, and lead times of 6–12 months are not uncommon

If domestic data center requirements apply (especially finance / healthcare), contracts need to be arranged early.

Hybrid design with cloud APIs

Rather than aiming for full localization, hybrid is the standard approach.

Design principles

RequirementRouting destination
Contains sensitive information / data cannot leave the premisesLocal LLM
High-difficulty reasoning / latest models neededCloud API (top-tier Claude / GPT / Gemini models)
High-frequency, lightweight tasksLocal LLM
After-hours batch processingCloud API batch (50% discount)
Sub-second response requirementsLocal LLMs (especially CPU + quantization)

Routing implementation

There are three patterns.

  • Rule-based: route using data classification tags (easy / low flexibility)
  • Small classification model: use FastText / DistilBERT etc. to judge sensitivity → route to local / cloud
  • Gateway products: leverage routing products such as LiteLLM / OpenRouter / Portkey

Start with rule-based, then evolve to a classification model / gateway product once operational logs accumulate.

Data governance perspective

Audit logs

Local LLMs hold input / output logs in-house. This is a major advantage over cloud APIs (especially default APIs without an Enterprise contract).

  • Monthly sampling review of inputs and outputs
  • Retention of evidence for regulatory compliance (7 years, etc., depending on industry requirements)
  • Presentation in internal audits / external audits

Model update policy

Open-weight models receive major updates on a scale of months.

  • Security patches: define an SLA for applying them, e.g. within 30 days
  • Performance improvements: decide on updates via quarterly evaluations (staged rollout after A/B testing)
  • Switching validation: maintain in-house benchmarks to check for quality degradation in existing workflows

Security patches

  • CVE handling for inference infrastructure (vLLM / TGI etc.): monthly patching
  • OS / containers: same as the normal operational infrastructure
  • Vulnerabilities in the model itself (prompt injection etc.): in-house Red Team / audits

FAQ

Q1. Which open-weight model has the best Japanese performance?

There is no established answer that can be declared as "the one." Model turnover happens on a quarterly basis, and benchmark rankings should be viewed on the assumption that they will change with the next update.

As options developed primarily for Japanese, there are NII's llm-jp-4.1-33b-thinking (Apache 2.0, 33B, context of 65,536; noted as for research and development on the model card) and Preferred Networks' PLaMo 3 series (31B; however, commercial use requires prior registration, and companies with annual revenue over 1 billion yen require a separate commercial license). On the general-purpose side, Qwen3.8-27B / Gemma 4 31B are stable across multiple languages, and NVIDIA's Nemotron 3.5 Lightning 30B-A3B also lists Japanese among its supported languages.

The way to decide does not change. Build an evaluation set for your own business (500–1,000 samples) and measure three candidates. Once built, the evaluation set can be reused for the next model update. Rather than chasing benchmark rankings, owning your own evaluation set becomes a long-term asset.

Q2. Which models require caution for commercial use due to licensing?

Seven models with proprietary licenses should always go through legal review.

  • PLaMo 3 series (Preferred Networks): PLaMo community license. Commercial use requires prior registration with PFN, and if the user or an affiliated company has annual revenue exceeding 1 billion yen, a separate commercial license must be obtained from PFN. Enterprises will almost certainly fall under this condition
  • Qwen3.8-Flash-Next (Alibaba): Qwen Community License 1.0. If the user or an affiliated company operates a Model as a Service or AI Work Assistant business, a separate license is required before commercial use regardless of revenue scale (internal use not provided to third parties is excluded)
  • Qwen3.8-2.4T-A95B (Alibaba): Qwen3.8-Max License. A separate license is required if the same businesses as above are operated and revenue including affiliated companies exceeds 50 million USD in the last 12 months
  • Kimi K3.1 Pro (Moonshot AI): Kimi K3.1-Pro License (the terms are identical to the previous Kimi K3 License except for the model name). A separate agreement is required if the user or an affiliated company operates a Model as a Service business and revenue including affiliated companies exceeds 20 million USD in the last 12 months
  • GLM-5.3 (Z.ai): GLM-5.3 License. If the user or an affiliated company operates a Model as a Service business and revenue including affiliated companies exceeds 10 billion USD in the last 12 months, Z.ai's security review is required before commercial use
  • Muse Spark Open (Meta): Muse Model License. Products and services using this model or derivatives must display "Built with Muse Spark Open" regardless of scale. If the user or an affiliated company operates a Model as a Service business and revenue including affiliated companies exceeds 20 million USD in the last 12 months, notification to Meta and a separate agreement are required (internal use not provided to third parties is excluded)
  • Mistral Large 4 (Mistral AI): Mistral Ecosystem Open-Weight License. If the user or an affiliated company operates a Model as a Service business, a separate commercial license from Mistral AI is required before commercial use regardless of revenue scale (internal use not provided to third parties is excluded). Inclusion of the copyright notice is also required

Qwen3.8-Flash-Next, Qwen3.8-2.4T-A95B, and Kimi K3.1 Pro also carry an obligation to display the model name on screen when used in products with more than 100 million monthly users or more than 20 million USD in monthly revenue.

Models that can be used commercially, modified, and redistributed under attribution-only obligations are Qwen3.8-27B / Gemma 4 31B / Muse Glimmer 30B / llm-jp-4.1-33b / Mistral-Small-4-119B / gpt-oss-120b / Hy4 preview (all Apache 2.0), Nemotron 3.5 Lightning (OpenMDW-1.1), and DeepSeek-V4 series / GLM-5.3-Flash / MiMo-V2.6 series / Ling-3.1-flash-1019 (MIT).

Do not infer licenses from vendor names. Even from the same provider and the same generation, conditions differ per model. Note that the license descriptions in this article reflect what could be confirmed as of November 16, 2026, and do not constitute legal advice. For MiMo-V2.6 and Ling-3.1-flash-1019, no license text file has been published, so the judgment was based on the MIT notation in the model cards. The license text for Muse Spark Open was confirmed on October 20. For adoption decisions, check the latest version of the original text and have it reviewed by your own legal team.

Q3. Is vLLM the only choice for an inference platform?

vLLM is the de facto standard for enterprise production at present, but the right choice depends on the use case.

  • Production / high throughput: vLLM
  • On-prem / lightweight / CPU: llama.cpp
  • HuggingFace ecosystem: TGI
  • PoC / development: Ollama
  • Heavy structured output / latest optimizations: SGLang

Using several in combination is also common. A typical setup is Ollama for validation, vLLM for production, and llama.cpp for edge.

Q4. How many GPUs are needed?

Work backward from business requirements.

  • Small PoC / personal / 20B-class quantized: 1x RTX 4090 ($1.6K)
  • Mid-size production / 27-33B class: 1x RTX 6000 Ada ($7K+) or H100 x1 ($25K+). If serving in BF16, the RTX PRO 6000 Blackwell (96GB) is also a candidate
  • Large-scale production / 120B-class MoE: H100 x1 to H200 x1 ($25K+). MoE requires loading weights for the total parameter count, so do not size by active parameters, but requirements drop if the distribution format is lower precision (gpt-oss-120b fits on a single 80GB card)
  • MoE with weight files of 180-330GB: H200 x2-4 ($60K-$120K). Qwen3.8-Flash-Next / MiMo-V2.6-Flash / GLM-5.3-Flash
  • Weight files of roughly 500-1,100GB: H200 x4-8 ($120K-$240K). GLM-5.3 / Hy4 preview / Ling-3.1-flash-1019 / DeepSeek-V4-Pro-0813, etc. Mistral Large 4 (about 1,061GB in FP8) requires H200 x8, leaving little room for the KV cache
  • Flagships that don't fit on one node: Kimi K3.1 Pro / Qwen3.8-2.4T. Use an API or managed inference

Including cooling, power, and networking equipment, budget roughly 1.5x the above for initial costs.

If you want to map these requirements to your own business, consult FDX.

Q6. How should security patches be operated?

Operate at the following three tiers.

  • OS / containers: same as your normal operations platform (monthly patches / emergency patches)
  • Inference platform (vLLM / TGI): track releases via GitHub Watch / monthly patches
  • Model itself: evaluate updates quarterly / hotfix for critical bugs

In domestic data center environments, applying patches requires an approval process. Clarify the SLA in advance.

Q6. Is it really cheaper than cloud APIs?

Evaluate over a 3-5 year TCO. Unless your workload consumes over 100 million tokens per month, 24/7/365, self-hosted on-prem is rarely cheaper.

Below that, dedicated cloud GPUs (Together / Fireworks / Lambda Labs) or hosted models via a Marketplace win on cost-performance.

If you want to map these requirements to your own business, consult FDX.

Q7. In a hybrid design, how do you choose the cloud side?

Evaluate on the following three factors.

  • Latest model performance: top-tier models from Claude / GPT / Gemini
  • Enterprise contracts: exclusion from training data / log retention controls / SLA
  • Domestic data center availability: AWS Tokyo / GCP Tokyo / Azure Japan East, etc.

The standard approach is to keep sensitive data local and route high-difficulty reasoning to the cloud. You don't need to match models on both sides; use each for its strengths.

Summary

  • Consider local LLMs for three cases: data cannot leave the premises, long-term operation exceeding tens of millions of tokens per month, or sub-second latency requirements.
  • The easiest to build in-house are 27B–33B-class models that run on a single GPU with FP8 or 4-bit quantization. Options have returned in the 120B–320B class, but flagships that don't fit on a single node are used via API
  • Read licenses per model rather than guessing from the vendor name. Even the same provider and same generation can have different terms. Custom licenses (PLaMo community license / Qwen3.8-Max / Qwen Community 1.0 / Kimi K3.1-Pro / GLM-5.3 / Muse Model License / Mistral Ecosystem Open-Weight License) require legal review; in particular, PLaMo 3 requires a separate commercial contract for companies with annual revenue over 1 billion yen
  • There is no established consensus on Japanese-language performance. Build your own eval set (500–1,000 samples) and measure actual performance. The eval set becomes an asset that can be reused for future model updates
  • For inference infrastructure, use vLLM for production, llama.cpp for lightweight/on-premise, and Ollama for validation, depending on the use case
  • Evaluate costs on a 3–5 year TCO basis. Unless running at full capacity 24/7/365, dedicated cloud GPUs are often advantageous
  • Rather than going fully local, the standard approach is a hybrid design: sensitive data stays local, while high-difficulty inference uses cloud APIs
  • Decide on adoption together with operational design covering audit logs, model update policies, and security patches
