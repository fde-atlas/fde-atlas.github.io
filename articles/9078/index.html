Week 5: Building a Deterministic Vertical Slice from a Problem Contract

Original title: 第 5 周：从问题合同做出确定性垂直薄片

FDE 成长手册 · 2026-08-25 · 8 min read

Summary

Week 5 of an FDE handbook argues the first engineering deliverable should be a narrow but complete deterministic vertical slice—not an AI architecture. Using a synthetic policy-confirmation example, it walks through trusted server-side identity, structured inputs, relational policy queries with versioning, and explicit review/denial states for edge cases. It provides a five-day plan, a test matrix, acceptance criteria, common failure modes with recovery steps, and an independent migration exercise on supply-chain order status.

Key points

  • Ship a deterministic vertical slice before considering models.
  • Identity must come from server-side sessions, never request bodies.
  • Missing, conflicting, or restricted tasks must enter explicit review states.
  • Default to a modular monolith rather than microservices.
  • Tests must verify responses, database state, and traceable sources.

Direct answer: The first engineering deliverable should not be "set up the AI architecture," but a narrow yet complete deterministic slice: an authorized role submits a structured task, the server validates input and identity, and the currently applicable and traceable policy is retrieved from relational data; missing fields, conflicts, or special tasks enter an explicit review state. First prove that ordinary software can correctly express the task and its failures, then decide whether a model is needed later.

This week adds only one difficulty: build the first code loop

Title "This week adds only one difficulty: build the first code loop"

Week 4 already decided "why this is worth exploring"; Week 5 only verifies "whether the target task can be run end-to-end with the simplest, explainable software."

Discovery Brief v1  → 一个角色和触发  → 结构化输入  → 服务端身份与业务校验  → 关系数据查询  → 成功或明确异常  → 来源、版本、状态与测试证据

A vertical slice does not mean only writing the database, only drawing the interface, or only building an API. It runs from user trigger all the way to a visible result, passing through the minimum layers needed for the implementation. Deterministic means that the same version, same identity, and same input produce predictable results; it does not mean "never fails."

Success input and expected result

Title "Success input and expected result"

Below is a behavioral example similar to an HTTP interface. If you use a function, CLI, or other interface, just keep the field semantics and visible results consistent.

{  "request_id": "req-w05-001",  "task_type": "plan_change",  "region": "east",  "purchased_at": "2026-08-10"}

The identity comes from a fixed server-side test session and does not appear in the request body. Expected response:

{  "request_id": "req-w05-001",  "status": "eligible",  "candidate": {    "policy_id": "POL-PLAN-01",    "version": 3,    "effective_from": "2026-08-01",    "effective_to": "2026-12-31",    "source_id": "KB-BILLING-2026-08"  },  "next_action": "review_source"}

Expected persisted state:

request_ididentity_fixturetask_typeresult_statuspolicy_idpolicy_versionsource_id
req-w05-001support_agent_fixtureplan_changeeligiblePOL-PLAN-013KB-BILLING-2026-08

Returning a policy candidate does not mean the support agent has correctly completed the task, let alone that the customer received the correct reply. This week only proves that the system can produce a traceable candidate.

Exception input and expected result

Title "Exception input and expected result"

Missing region:

{  "request_id": "req-w05-002",  "task_type": "plan_change",  "purchased_at": "2026-08-10"}

Expected result:

{  "request_id": "req-w05-002",  "status": "needs_review",  "reason_code": "MISSING_REGION",  "candidate": null,  "next_action": "collect_required_field"}

The database must not silently save a default region, nor return a seemingly correct policy.

When an ordinary support agent queries a special refund:

{  "request_id": "req-w05-003",  "task_type": "special_refund",  "region": "east",  "purchased_at": "2026-08-10"}

Only a safe status is expected to be returned:

{  "request_id": "req-w05-003",  "status": "needs_review",  "reason_code": "SPECIAL_TASK_REQUIRES_REVIEW",  "candidate": null,  "next_action": "escalate"}

The response must not leak the supervisor policy content, nor does it need to tell the ordinary support agent "there is a restricted policy named POL-REFUND-09."

Minimal decision process

Title "Minimal decision process"

从可信测试会话取得身份  → 未知身份：denied  → 校验必需字段      → 缺失：needs_review / MISSING_FIELD  → 查询当前适用且允许的政策      → 恰好一条：eligible + 来源与版本      → 零条：needs_review / NO_APPLICABLE_POLICY      → 多条冲突：needs_review / CONFLICTING_POLICIES  → 保存 request_id、输入摘要、终态和来源

This is a behavioral rule, not code in any particular language. Do not put the full policy text into ordinary logs.

Minimal mental model: slice the task thin first, then choose components

Title "Minimal mental model: slice the task thin first, then choose components"

Before writing code, use six questions to limit the scope:

  • Role: Who triggers it, and where is the identity trustworthily obtained from?
  • Input: Which fields are minimally required to make the decision?
  • Rules: Which judgments must be deterministic?
  • Result: What can the user see and verify?
  • Exceptions: Under what circumstances must it be rejected or escalated?
  • Non-goals: What is explicitly not being done this week?

If you need more than ten services to describe a single request, first check whether you have crammed a future phase into this week.

Why a modular monolith by default

Title "Why a modular monolith by default"

This week's risk is misrepresenting the task and its state, not service scale. Within a single process or deployment unit you can still separate interface, business rules, data access, and audit modules; this is easier to run, test, and modify than splitting into microservices first.

Example of a completed ADR:

# ADR-001：使用模块化单体建立确定性基线
- 状态：接受（课程模拟）- Brief：northstar-discovery-brief-v1- 决定：用一个部署单元实现身份校验、政策查询和任务记录- 原因：范围只有一个只读任务；需要快速验证业务状态和错误，而不是独立扩缩容- 未选：微服务——当前没有独立团队、独立发布或扩缩容证据- 未选：RAG/模型——输入和规则是结构化的，且尚未建立正式评测- 代价：模块边界需要靠代码和测试维持- 重新评审条件：出现独立发布、隔离、负载或组织所有权证据

Day 2: Define interfaces, relationships, and state

Title "Day 2: Define interfaces, relationships, and state"

Interface versions must at least be able to distinguish future incompatible changes. The relationship model should store:

  • Policy stable ID and version;
  • Task type, region, effective and expiration times;
  • Source ID and minimum access level;
  • Request ID, trusted test identity, input digest, and terminal state;
  • Creation time and the Brief/data version currently in use.

Write the migration first, then insert fixed synthetic fixtures. Constraints should make missing key identifiers or illegal date relationships fail early; do not rely only on interface validation.

Day 3: Implement a minimal modular monolith

Title "Day 3: Implement a minimal modular monolith"

Use a tech stack you are already familiar with, and implement in order:

  • Obtain the controlled test identity from a fixed server-side session;
  • Validate structured input;
  • Execute queries by applicability period, task type, region, and access level;
  • Map zero, one, and multiple candidates to explicit states;
  • Return source and version;
  • Save a safe task record.

Write the actual steps needed to run the application into your own README. Since this page does not provide a code repository, do not treat the example JSON as an already existing interface.

Day 4: Write one success test and one failure test first

Title "Day 4: Write one success test and one failure test first"

Automated tests must verify both:

  • The user-visible response;
  • The database task terminal state;
  • The candidate policies and versions;
  • No false success for missing-field or restricted scenarios;
  • No policy text, keys, or personal information in ordinary logs.

Merely asserting HTTP 200 or that a function did not throw does not count as a task test.

Day 5: Change one condition and record an ADR

Title "Day 5: Change one condition and record an ADR"

First demonstrate the

req-w05-001

full path, then independently complete one change of your choice:

  • Move the purchase date to a version boundary;
  • Remove the region;
  • Create two simultaneously applicable versions;
  • Use an unknown identity.

When demonstrating, follow the order "input → identity → query → terminal state → database → tests," not just the interface.

Acceptance and failure recovery

Title "Acceptance and failure recovery"

Passing this week requires all of the following:

  • Your own README states how to actually run it, and example inputs produce deterministic results;
  • The interface, data model, and tests all reference the same version of the Brief;
  • Missing, conflicting, and unknown identities do not return false success;
  • The single controlled test identity is obtained server-side, and unknown identities are denied by default;
  • Output includes source, version, and processing path;
  • Automated tests verify visible results and database terminal state, not just status codes;
  • No models, vector retrieval, AI agents, MCP, or microservice splitting;
  • No conflating local runs with production, adoption, or business impact.
Common failureDiagnostic signalRecovery action
Writing lots of code before finding the taskMany modules, but cannot explain a single requestDelete side branches and return to the slice contract
Splitting microservices from the startDebugging mostly spent on networking and deploymentMerge into a modular monolith, keep re-evaluation conditions
Only a success demoMissing fields still return a policyAdd explicit rejection or review terminal states
Request body self-reports identityChanging the role field grants privilege escalationObtain identity from a server-side test session, deny by default
Output looks correct but has no sourceOnly policy text or "refundable"Return source ID, version, validity period, and processing status
Filling default fields for simplicityMissing region treated as eastEnter needs_review, return to the task and data evidence

Independent migration: supply chain order status verification

Title "Independent migration: supply chain order status verification"

Do not copy the policy fields. Redo it for "a planner verifies an order's current status":

  • Specify the role, trigger, order ID, carrier, and event time;
  • Define the states "confirmed," "data conflict," "source stale," and "needs manual verification";
  • Provide one success input, one input with an ERP vs. carrier status conflict, and expected results;
  • Explain why the side with the later update time cannot be automatically chosen on conflict;
  • Write one piece of new evidence that would send you back to the supply chain Brief.

If you merely change

policy_id

into

order_id

without changing timeliness, source ownership, and error cost, the migration has not passed.

Explain the same slice to three audiences

Title "Explain the same slice to three audiences"

  • Boss version: Which delivery risk does this slice validate, why not use AI first, and what does the next investment depend on.
  • Frontline version: Which step of the task the system changes, when it will reject or escalate, and how users can view the basis.
  • Engineering version: How the Brief version enters the interface, relationship states, server-side identity, queries, and tests; which capabilities are explicitly deferred.
