How to Choose an Agent Framework: Comparing LangChain, LlamaIndex, and Haystack

Original title: Agent 框架怎么选：LangChain、LlamaIndex、Haystack 对比

FDE Times · 2026-10-08 · 6 min read

Summary

This article examines Agent framework selection from an FDE perspective. Anthropic's December 2024 guidance recommends starting with direct LLM API calls, since many patterns need only a few lines of code, and warns that framework abstractions can hide prompts and complicate debugging. LangChain, LlamaIndex, Haystack, and RAGFlow each address different layers, so the right choice depends on where the customer is actually stuck. Because FDE code stays in the customer's codebase after departure, the author proposes a handover test: can you print the exact final prompt and trace a wrong answer back to its chunk and routing step?

Key points

  • Anthropic advises starting with direct API calls; frameworks can obscure prompts and hinder debugging.
  • Each tool serves a different layer: LangChain for quick starts, LlamaIndex for data, Haystack for explicit pipelines, RAGFlow for complex documents.
  • FDE code outlives the engagement, so frameworks should only be adopted when they do real, understood work.
  • A logistics case study shows the failure was in document chunking, not Agent orchestration.
  • The handover test: print the final prompt and trace errors to specific chunks and routing steps.

Key takeaways

  • The four tools serve four different layers: LangChain for quick starts, LlamaIndex for the data layer, Haystack for explicit pipelines, and RAGFlow for complex documents.
  • For an FDE, the framework stays in the customer's codebase after you leave, so it's only worth adopting if it does real work and you know it well.

In its agent-building guide published on December 19, 2024, Anthropic gave advice that runs counter to many developers' instincts: start by calling the LLM API directly. The reasoning is pragmatic: many patterns require only a few lines of code.

At the same time, every framework makes its own promises. Haystack calls itself an open-source framework for building production-ready agents. LangChain promises to get agents running quickly with any model provider. LlamaIndex invites you to build agents on top of your organization's own data.

For a Forward Deployed Engineer (FDE), choosing a framework isn't just a matter of personal preference. The code you write stays in the customer's codebase after you leave, and it's the customer's team that debugs issues at 2 a.m.

So the right question isn't "which framework is best," but "where is the customer stuck, and should this part be handed over to someone else's library?"

Each tool solves a different part of the work

Reading each project's self-description carefully reveals that they compete on different playing fields. LangChain emphasizes quick starts and compatibility with any model provider. If you need production-grade agents with a degree of determinism, it will point you to another product, LangGraph, which offers low-level control.

LangChain also has LangSmith, a platform for observing, evaluating, and deploying agents. This matters for FDEs: part of this ecosystem is a product the customer may need to purchase, not just an open-source library. When recommending LangChain, be clear about which components the customer is using and which may incur costs later.

LlamaIndex starts from data: it's a Python toolkit for building LLM agents that run on the customer's own data. Its workflows are event-driven, multi-step processes that combine agents, data connectors, and tools. In this picture, retrieval-augmented generation (RAG) is just one of many tools.

Haystack doesn't hide logic behind automated layers. According to deepset's documentation, a pipeline is a graph you connect by hand, so it runs the same way every time. The project emphasizes explicit control over retrieval, routing, memory, and generation, and promises you can swap models or infrastructure without rewriting the system.

RAGFlow differs from the others: it's an out-of-the-box RAG engine that runs once deployed, while the others are libraries that need to be assembled in code. Its strength is deeply understanding unstructured documents with complex formats. It also lets users visually see how documents are split into chunks, making manual intervention easy.

Where is the customer stuck?

Imagine a scenario: a logistics company wants an internal agent to answer questions about shipping contracts. The data is thousands of scanned PDFs with tables, drafted over the years using different templates. You have two weeks.

In the first week, you call the API directly, split documents into fixed-length chunks, and print the full prompt before each request. A user asks about warehousing fees for the Haiphong–Hanoi route, and the model answers incorrectly. The printed prompt (numbers are illustrative only) looks like this:

上下文：
[Chunk 15] 海防 - 河内 | 4,200,000 | 350,000
[Chunk 31] 仓储费按月收取，于期末支付……
问题：海防 - 河内线路的仓储费是多少？

The problem is obvious at a glance. The header row "Route | Freight | Warehousing fee" landed in chunk 14, which was never retrieved, so the model saw two numbers without column names and picked the first one. The problem lies in how the document was read and split, with nothing to do with agent orchestration.

This is when you should bring in a tool specialized in document understanding, such as RAGFlow. Its chunk inspection interface lets operations staff see that the fee table was split from its header, and adjust it so the whole table lands in the same chunk. Print the prompt again, and the context now includes all column names; the model picks the correct number, 350,000.

A lesson from day one at the customer site: before discussing frameworks, print the prompt and ask whether the retrieved chunks would be enough for a human reader to answer correctly.

Other scenarios point to other tools. If the documents are clean but scattered across SharePoint, databases, and email, LlamaIndex's data layer is the part that saves you effort.

Now suppose the customer is an enterprise that must undergo audits and requires every answer to be reproducible. Then Haystack's hand-connected graph, which runs the same way every time, will be easier to defend in front of the compliance team.

If the customer's boss just needs to see a demo within three days to approve a budget, starting quickly with LangChain is reasonable, provided you explain upfront that production will require LangGraph or another solution.

You leave, and the customer carries the abstraction

Anthropic points out the biggest risk: frameworks often add layers of abstraction that obscure the underlying prompts, making debugging harder. For developers building internal products, this is a minor annoyance. For an FDE, it's a debt left to the customer's team.

Anthropic's second recommendation is more direct: if you use a framework, understand the underlying code. It notes that incorrect assumptions about how a framework works internally are a common cause of customer errors. In practice, mistakes usually start with someone assuming the framework does one thing when it actually does another.

This sets a test every framework must pass before handover. Can you print the exact final prompt sent to the model, as in the shipping contract example above? Can the customer's team trace a wrong answer back to the chunk and the routing step that caused it?

If the answer is no, then the time the framework saves you is paid for later by the customer's commitment.

Writing it yourself doesn't mean rewriting everything

Interpreting Anthropic's advice as "never use frameworks" is a misreading. What it says is that many patterns require only a few lines of code, and "many" leaves room for the rest. A tool-calling loop, a summarization step, or a simple router can each be written in a few dozen lines of code that anyone on the customer's team can read.

Writing your own parser for a table-heavy PDF, or your own connectors for ten data sources, means redoing work that RAGFlow or LlamaIndex has already invested heavily in. Haystack's promise of "swap models without rewriting" is only valuable if the customer is actually likely to switch models.

If they won't, writing a thin adaptation layer yourself is enough to reduce the risk of lock-in.

Therefore, the sensible approach on the customer's site is usually a hybrid one. Write the orchestration yourself and keep it extremely thin—thin enough that you can print every prompt. Introduce a framework only in exactly one heavy layer, and let it do the real work. At handover, include a one-page note explaining why that layer uses a library and the others don't.

What developers should practice

The skill that's truly valuable here is being able to explain clearly, in front of the customer's engineers, why this tool fits this part of the job; memorizing the APIs of four tools isn't very useful. A good way to practice is to solve the same problem two ways: calling the API directly and using a framework, then noting where the framework helped and where it obscured the prompt.

Framework names in job descriptions are also clues: a role that mentions LangGraph and observability likely needs someone to push AI agents controllably into production. When describing your experience, show recruiters how you weigh whether to use a tool or not; simply listing library names proves nothing.

Frameworks will rename themselves, merge products, and shift their positioning. The habit of calling the API directly first, pinpointing the customer's pain point, and only then choosing a tool will outlast any of them.
