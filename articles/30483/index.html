How FDEs Can Safely Use Claude Code in Customer Codebases

Original title: FDE 如何在客户代码库安全使用 Claude Code

FDE Times · 2026-10-09 · 5 min read

Summary

This article advises forward deployed engineers on safely running AI coding tools inside customer codebases. It compares Claude Code, Codex, and Cursor defaults: Claude Code stores session transcripts in plaintext locally for 30 days, and zero data retention (ZDR) must be enabled per organization even on Enterprise plans. Cursor's ZDR promise disappears when you plug in your own API key. The author stresses that CLAUDE.md files are instructions, not enforcement—sandboxes and permission modes are what actually constrain agents—and recommends reviewing every command, adding transcript cleanup to offboarding checklists, and learning permission models before prompt techniques.

Key points

  • Claude Code keeps plaintext session transcripts locally for 30 days by default.
  • ZDR requires per-organization enablement, even for Enterprise accounts.
  • Cursor's ZDR promise no longer applies when using your own API key.
  • CLAUDE.md is only instructions; sandboxes and permission modes are the real guardrails.
  • Add transcript cleanup to project offboarding checklists for client work.

Claude Code, Codex, and Cursor all let you add restrictions, but their defaults differ, and the exceptions that violate customer policies are buried in privacy documentation.

Key Points at a Glance

  • By default, Claude Code saves session transcripts in plaintext on your local machine for 30 days, including when working with customer code.
  • No-training promises and ZDR depend on account type and each tool's configuration, such as whether you use your own API key in Cursor.
  • CLAUDE.md is just instructions. What actually constrains the agent is the sandbox and permission modes.

Every Claude Code session you open on your laptop leaves a trace. Anthropic's documentation states that session transcripts are stored in plaintext at

~/.claude/projects/

and retained for 30 days by default. If that session ran on a customer's codebase, the large amount of content the agent read and anything you pasted in may still be sitting on your hard drive.

For engineers building internal products, this rarely matters. For Forward Deployed Engineers (FDEs), it does. The repositories you work in don't belong to you, and every command the agent runs must comply with the customer's data policies.

Claude Code, Codex, and Cursor all provide ways to restrict agent behavior. But their defaults differ, and the most critical exceptions are written in privacy documentation that few people read carefully.

What can an agent do in your repository?

Anthropic positions Claude Code as an agentic coding tool. It can read codebases, modify files, run commands, and connect to development tools, and it works in the terminal, IDE, desktop app, and browser. At the start of each session, it reads the

CLAUDE.md

file in the repository, making that file a good place to record coding conventions and customer constraints.

OpenAI's Codex, when running locally, is sandboxed by the operating system itself and can only access what is permitted. Codex runs offline by default. A separate set of approval policies determines when it must ask for your consent before acting.

As for Cursor, the thing most worth reading carefully is its data commitments, which is also where FDEs most often stumble.

Before writing a prompt, first clarify the account

A wrong command at least shows up on screen, and you can still stop it. Where code goes after it leaves your machine is far harder to detect. So it's worth asking the right questions before typing your first prompt.

Anthropic states that if you're on commercial terms (Team, Enterprise, API), code and prompts sent to Claude Code are not used to train models; individual plans are different, so the first question to ask is the account type.

Even an Enterprise plan doesn't automatically come with zero data retention (ZDR). Anthropic's documentation notes that ZDR must be enabled separately per organization, and only after the customer team confirms the organization qualifies.

Cursor's trap is subtler. For teams, Privacy Mode is enabled by default for all members, with a commitment that code won't be used for training by Cursor or model providers; admins can also enforce it organization-wide, and members can't turn it off.

But when you use your own API key, ZDR no longer applies. Imagine you're on-site at a customer and run out of quota; to finish a demo on time, you plug your personal API key into Cursor. The interface looks exactly the same, but the ZDR commitment is gone. So changes like this need approval in advance, not reporting after the fact.

A sample session

Suppose a customer asks you to fix a failing test in the payment service. Before typing your first prompt, create a short

CLAUDE.md

：

# 客户约束
- 不要读取 secrets/ 目录或任何 .env 文件
- 不要调用外部网络服务
- 只能用以下命令运行测试：make test-payments
- 不要提交 commit；只提出 diff，供客户工程师审查

Then open the session in Manual mode. Claude Code starts with read-only permissions only, so the first task should be having it read the code and explain why the test fails.

When it proposes modifying files or running

make test-payments

, read each command in full before approving. If permission prompts become too frequent, switch to sandboxed bash with an isolated filesystem and network, rather than approving everything blindly.

Remember,

CLAUDE.md

is only what the agent reads at the start of a session. It's instructions, not a fence. The line "do not call external network services" is only truly guaranteed when the sandbox blocks the network.

Doing the same work with Codex

In Codex, the network fence is already in place, because it's offline by default. Suppose the payment test needs to download a dependency not on your machine: the command will fail, and the agent will stop or ask you, depending on the approval policy.

This is the moment when mistakes are easiest to make, because opening up the network takes only a second. Stop first and ask the customer's engineers: is this service allowed to make outbound calls, and to where. Only after getting consent should you loosen permissions, and record that decision in the handover documentation.

The tools won't take responsibility for you

Anthropic's security documentation is blunt: reviewing proposed code and commands before approving them is your responsibility. On a customer site, this has real consequences. A command that deletes a directory, even if proposed by the agent, is your command once you approve it.

The second limitation is the laptop itself. Plaintext session transcripts retained for 30 days means that at the end of a project, the handover isn't complete until these directories are cleaned up as the customer requires. Add this step to the offboarding checklist for every project.

What to learn first, and what to put on your resume

Don't start with prompt tricks. Learn three things in order: the permission modes and sandbox of the tools you use; what "commercial terms" and ZDR mean; and then how to write constraint files for a repository. The first should become reflexive, because it's the part the tools actually enforce.

When reading job descriptions, watch for whether the role involves working directly on customer infrastructure or codebases; if so, this skill is worth raising proactively in interviews. A resume line like "built workflows for using coding agents in an offline sandbox on a financial services customer's codebase" tells a hiring manager far more than "proficient in Claude Code."

Customers will most likely never ask which tools you used. But if they ask where the project's session transcripts are, you should be able to answer immediately.
