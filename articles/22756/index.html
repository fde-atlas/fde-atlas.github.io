TL;DR

FDE coding rounds look less like puzzles and more like a day on site: read a sample of real-looking data, call an API that paginates and rate-limits, aggregate the result correctly, and fix someone else's bug. Interviewers want code that runs early, handles the boring edge cases (duplicates, time zones, money, retries) and is tested as you go. Clever algorithms matter less than correctness and a clean structure you can extend when the follow-up arrives.

What this round tests

The two coding questions in our bank that were reported from FDE interviews are practical: call a REST API and use the result, and validate a form and append the rows to a table. The other reported questions on this page's list are similar work from engineering loops at FDE-hiring companies: query an endpoint and combine the results, parse logs or CSVs into a report, crawl linked resources, or find the bug in a small service. Two of them drop you into an existing multi-file codebase rather than a blank editor.

  • Getting to running code fast, then improving it, rather than designing in your head for 20 minutes.
  • Reading a data or API contract carefully: field types, nullability, pagination, error codes, units and time zones.
  • Handling the edge cases real data has: duplicates, out-of-order records, malformed rows, partial failures, money and dates.
  • Structure: small functions for fetch, parse, transform and output, so a follow-up ("now add caching", "now make it resumable") is a small change.
  • Debugging code you did not write: reproduce, isolate, fix, and protect the fix with a test.

How to approach it: read, probe, skeleton, happy path, harden, verify

Our guidance (editorial), not a candidate report

  • 1. Read the contract Write down the input shape and the expected output in a comment before coding: field names, types, which fields can be missing, and what the API does at the end of the data. Ask about anything the sample does not settle (are amounts strings or numbers? which time zone are dates in?).
  • 2. Probe the data Print three records, the count, and the distinct values of any status field. Look for nulls, duplicates and mixed formats. Two minutes here saves twenty later.
  • 3. Skeleton Write function signatures for fetch, parse, transform and report, with a main that wires them. Interviewers can follow the plan even before the bodies exist.
  • 4. Happy path end to end Make the smallest input produce the right output, and run it. Running code at minute 15 is worth more than perfect code at minute 40.
  • 5. Harden Add pagination termination, retries with backoff for 429 and 5xx (honouring Retry-After), timeouts, deduplication by key, exact decimal money, time-zone aware dates, and a place for bad rows (count and keep them with a reason instead of crashing or silently dropping).
  • 6. Verify and talk scale Assert on a case you computed by hand, add one test per edge case you handled, then say what changes at 100 times the data: streaming instead of loading everything, checkpointing the cursor, concurrency limits.

Worked example: revenue per customer from a paginated orders API

The prompt

An orders API returns JSON pages of up to 200 orders with a next_cursor field (null on the last page). It returns HTTP 429 with a Retry-After header when you go too fast and occasionally 503. Each order has id, customer_id, status (paid, partially_refunded, refunded, cancelled), amount and refunded_amount as decimal strings, currency, created_at and updated_at (ISO 8601, UTC). Compute net revenue in USD per customer for orders created in the last 30 days, given a table of exchange rates. Orders can change while you page through, so the same order may appear twice.

The candidate first states the decisions the prompt leaves open: net revenue is amount minus refunded_amount; cancelled and fully refunded orders count as zero; when an order appears twice the copy with the later updated_at wins; an unknown currency is an error to report, not something to skip silently. Filtering by updated_since = the cutoff is safe because an order created inside the window cannot have been updated before it.

import random
import time
from collections import defaultdict
from datetime import datetime, timedelta, timezone
from decimal import Decimal

import requests

ORDERS_URL = "https://api.example.com/v1/orders"
RETRYABLE = {429, 500, 502, 503, 504}


def get_with_retries(session, url, params, max_retries=5):
    """GET with backoff. Retries timeouts, 429 and 5xx; any other 4xx is a bug in our request."""
    for attempt in range(max_retries + 1):
        try:
            resp = session.get(url, params=params, timeout=10)
        except (requests.ConnectionError, requests.Timeout):
            resp = None
        if resp is not None and resp.status_code not in RETRYABLE:
            resp.raise_for_status()
            return resp
        if attempt == max_retries:
            break
        if resp is not None and resp.status_code == 429 and resp.headers.get("Retry-After", "").isdigit():
            wait = int(resp.headers["Retry-After"])
        else:
            wait = min(30, 2 ** attempt) * random.uniform(0.5, 1.0)  # exponential backoff with jitter
        time.sleep(wait)
    status = resp.status_code if resp is not None else "network error"
    raise RuntimeError(f"giving up on {url} after {max_retries} retries ({status})")


def fetch_orders(session, updated_since):
    """Yield every order updated since the given time, following the cursor to the end."""
    params = {"updated_since": updated_since.isoformat(), "limit": 200}
    while True:
        body = get_with_retries(session, ORDERS_URL, params).json()
        yield from body["data"]
        cursor = body.get("next_cursor")
        if not cursor:
            return
        params = {"cursor": cursor, "limit": 200}
def parse_ts(s):
    # fromisoformat only accepts a trailing "Z" from Python 3.11 on.
    return datetime.fromisoformat(s.replace("Z", "+00:00"))


def net_revenue_by_customer(orders, fx_to_usd, now, days=30):
    cutoff = now - timedelta(days=days)

    latest = {}  # order id -> newest copy seen
    for o in orders:
        prev = latest.get(o["id"])
        if prev is None or parse_ts(o["updated_at"]) > parse_ts(prev["updated_at"]):
            latest[o["id"]] = o

    totals = defaultdict(Decimal)
    for o in latest.values():
        created = parse_ts(o["created_at"])
        if not (cutoff <= created < now) or o["status"] in ("cancelled", "refunded"):
            continue
        if o["currency"] not in fx_to_usd:
            raise ValueError(f"no exchange rate for {o['currency']} (order {o['id']})")
        net = Decimal(o["amount"]) - Decimal(o.get("refunded_amount") or "0")
        totals[o["customer_id"]] += net * fx_to_usd[o["currency"]]

    return {c: v.quantize(Decimal("0.01")) for c, v in totals.items()}


def main(session, fx_to_usd):
    now = datetime.now(timezone.utc)
    orders = fetch_orders(session, updated_since=now - timedelta(days=30))
    return net_revenue_by_customer(orders, fx_to_usd, now)
class FakeResp:
    def __init__(self, status, body=None, headers=None):
        self.status_code, self._body, self.headers = status, body, headers or {}

    def json(self):
        return self._body

    def raise_for_status(self):
        if self.status_code >= 400:
            raise requests.HTTPError(self.status_code)


class FakeSession:
    def __init__(self, responses):
        self.responses = list(responses)

    def get(self, url, params, timeout):
        return self.responses.pop(0)


def order(id, cust, amount, updated, status="paid", refunded="0.00", cur="USD"):
    return {"id": id, "customer_id": cust, "status": status, "amount": amount,
            "refunded_amount": refunded, "currency": cur,
            "created_at": "2026-11-01T10:00:00Z", "updated_at": updated}


def test_dedupes_refunds_and_retries(monkeypatch):
    monkeypatch.setattr(time, "sleep", lambda s: None)
    page1 = {"data": [order("o1", "c1", "100.00", "2026-11-01T10:00:00Z"),
                      order("o2", "c2", "50.00", "2026-11-01T10:00:00Z")],
             "next_cursor": "abc"}
    # o1 changed while we paged: it reappears with a partial refund.
    page2 = {"data": [order("o1", "c1", "100.00", "2026-11-02T09:00:00Z",
                            status="partially_refunded", refunded="30.00"),
                      order("o3", "c2", "20.00", "2026-11-01T11:00:00Z", status="refunded", refunded="20.00")],
             "next_cursor": None}
    session = FakeSession([FakeResp(429, headers={"Retry-After": "1"}),
                           FakeResp(200, page1), FakeResp(200, page2)])
    now = datetime(2026, 11, 10, tzinfo=timezone.utc)
    orders = fetch_orders(session, now - timedelta(days=30))
    assert net_revenue_by_customer(orders, {"USD": Decimal("1")}, now) == {
        "c1": Decimal("70.00"), "c2": Decimal("50.00")}

What the interviewer sees: the fetch is a generator, so memory stays flat however many pages there are; retries only cover failures that are safe to retry; money never touches a float; the duplicate-order case is handled by a rule stated up front and proved by a test. When asked about scale, the candidate adds: persist the last cursor after each page so a crash resumes instead of restarting, and if several workers share one API key, put a shared token bucket in front of the calls instead of letting each worker back off on its own.

Common follow-ups and what they probe

  • "The job dies on page 400 of 900. What happens on rerun?"
  • Probes resumability. Checkpoint the cursor (and the partial aggregate, or recompute it from stored raw pages) after each page, and make reprocessing idempotent so a repeated page cannot double count.
  • "Would you retry a POST that creates a payment?"
  • Probes idempotency. Only with an idempotency key the server honours; otherwise a timeout followed by a retry can charge twice. Reads are safe to retry, writes need a key or a check-then-write.
  • "Ten workers share one API key with a limit of 50 requests per second."
  • Probes coordination. Independent backoff makes workers collide. Use a shared rate limiter (a token bucket in Redis, or a single fetcher feeding a queue) sized below the limit.
  • "How do you test this without hitting the real API?"
  • Probes design for testability. Inject the HTTP session (as above), record a few real responses as fixtures, and add contract tests that run against a sandbox on a schedule rather than on every commit.
  • "Ten percent of rows fail to parse. What do you do?"
  • Probes data-quality judgement. Do not drop them silently: count them, keep each with its reason, report the rate, and agree with the customer on a threshold that stops the run.

How it is scored

Our guidance (editorial), not a candidate report

Our synthesis of what interviewers in this round look for. Exact rubrics vary by company and are not published.

Dimension Weak signal Strong signal
Correctness Works on the sample only Handles duplicates, empty pages, nulls, time zones and money correctly
Progress Nothing runs until the end Runs a happy path early, then hardens it
Structure One long function Small, testable functions with clear inputs and outputs
Robustness Retries everything forever, or nothing Bounded retries for retryable errors only, with backoff and timeouts
Testing Eyeballs printed output Asserts on hand-computed cases, one per edge case
Communication Silent coding States assumptions and trade-offs as decisions are made

Common mistakes

  • Using floats for money, then rounding at the end and getting a different total from the customer's finance team.
  • Comparing naive and time-zone aware datetimes, or treating a UTC timestamp as a local business date.
  • A pagination loop with no clear end condition, or one that skips the last page.
  • Catching every exception and continuing, which turns a bug into silently wrong numbers.
  • Retrying requests that are not safe to repeat.
  • Loading every page into a list before processing when a generator would do.
  • Building a class hierarchy before a single record has been parsed.

FAQ

  • Is FDE coding easier than a standard software engineering coding interview?
  • It is different rather than easier. Algorithmic depth matters less, but the bar on correctness with messy data, API behaviour and code quality is high, and the problems are longer and more open-ended.
  • Which language should I use?
  • Python is the most common choice because data handling and HTTP are short to write. Use the language you are fastest and most correct in, unless the company asks for a specific one.
  • Can I look things up during the interview?
  • It varies by company and round, and is not something our reports pin down. Ask at the start what is allowed. Even when documentation or an assistant is allowed, explain what you are checking and why.
  • Do I need to memorise LeetCode patterns?
  • Know the basics well (hash maps, sorting, heaps, BFS and DFS, intervals, sliding windows), because they show up inside practical problems. Grinding hundreds of puzzles is a poor use of time for this role.
