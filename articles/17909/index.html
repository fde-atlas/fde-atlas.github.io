Data Pipeline Idempotency: MERGE Deduplication and Historical Backfill

Original title: 数据管道幂等性：MERGE 去重与历史回填

FDE Times · 2026-10-08 · 6 min read

Summary

This guide shows forward deployed engineers how to make daily data pipeline loads idempotent so reruns never duplicate data. It recommends MERGE on a business key, or replacing an entire partition with DELETE plus INSERT inside one transaction, and avoiding nondeterministic values like NOW(). Watermarks should only filter data, not guarantee correctness. Once each partition is idempotent, backfilling years of history becomes a simple loop rerunning the same nightly code per day, with common pitfalls like wrong business keys highlighted.

Key points

  • Idempotency is a property of each operation; every pipeline step must be designed for it.
  • Use MERGE keyed on business keys, or partition overwrite within a single transaction.
  • Write event time or scheduler-passed batch dates instead of NOW() to keep reruns deterministic.
  • Watermarks are fragile at boundaries and with late data; idempotent writes make re-selection harmless.
  • Backfill is just rerunning partitions in order; failures resume from the failed day without cleanup.

Key Takeaways

  • Watermarks only filter data; preventing duplicates depends on the write step.
  • MERGE on the business key, or DELETE and then INSERT an entire partition within the same transaction, and reruns leave results unchanged.
  • Once every partition is idempotent, backfilling is just rerunning each day in order.

Imagine your first week on-site at a retail client. Last night's order load job failed halfway through, ops clicked rerun, and this morning the dashboard shows revenue doubled. Nobody wrote a single wrong line of SQL; the problem is that the job was never designed to be run twice.

If you're a Forward Deployed Engineer (FDE), you'll run into this sooner or later.

Sooner or later the client will also ask: "Can you load all our data going back to the start of last year?" As long as your pipeline doesn't produce duplicates on rerun, you can say yes with confidence—without pulling an all-nighter.

This article builds a daily orders pipeline with three properties: incremental loading, safe reruns, and backfilling that uses the exact same code that runs every night. The SQL below is simplified; the exact syntax varies by the client's data warehouse.

What do you need before getting started?

IBM describes a data pipeline as three stages: ingesting raw data from multiple sources, transforming the data, and storing it in a data warehouse. The pipeline in this article runs in batch mode, loading data in chunks at fixed intervals. Each batch is triggered by a job scheduler—software that runs tasks in the background on a schedule, with no one needing to be present.

You'll need a database that supports transactions and MERGE, plus two tables:

staging_orders

one for the raw data just pulled in,

orders

and one as the target table. Each order uses

order_id

as the business key and

order_date

as the event date. Beyond that, you only need a small Python script that invokes the job day by day.

Before you start, keep this definition in mind: an operation is idempotent if executing it multiple times leaves the result unchanged. That's exactly why it can be retried without side effects or data corruption.

One point that's often overlooked: idempotency is a property of a single operation, and it doesn't automatically hold across an entire system. Every step in the pipeline must be designed for idempotency individually.

Step 1: Use daily partitions as the unit of work

Each run processes a single logical day, called

batch_date

. This date is passed in as a parameter by the scheduler; the job itself never decides on its own what "today" is.

-- 任务中的每条语句都按这个参数过滤
SELECT order_id, customer_id, amount, updated_at, order_date
FROM staging_orders
WHERE order_date = :batch_date;

Check: For

2026-03-01

run the query above twice; the row counts must be identical. If they differ, the data source is still changing while you read it, and you must clarify this before proceeding.

Step 2: Use MERGE so reruns produce no new data

The usual culprit behind a doubled revenue dashboard is a plain INSERT. Suppose there are 1,000 orders on 2026-03-01; if the INSERT runs twice, the target table ends up with 2,000 rows. MERGE (upsert) is different: new keys are inserted, existing keys are updated.

MERGE INTO orders AS t
USING (
  SELECT order_id, customer_id, amount, updated_at, order_date
  FROM staging_orders
  WHERE order_date = :batch_date
) AS s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET
  customer_id = s.customer_id,
  amount      = s.amount,
  updated_at  = s.updated_at
WHEN NOT MATCHED THEN INSERT
  (order_id, customer_id, amount, updated_at, order_date)
  VALUES (s.order_id, s.customer_id, s.amount, s.updated_at, s.order_date);

When the same batch is rerun, every row is updated to the value it already had, so the second run changes nothing. In the example above, no matter how many times the job runs, the target table always has 1,000 rows.

Check: Run the MERGE twice, then search for duplicates; the result must be empty.

SELECT order_id, COUNT(*)
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;

Step 3: If there's no business key, replace the entire partition

Some tables have no stable business key, such as a daily revenue summary table. In that case, treat the entire partition as the unit of work and replace it wholesale. Rerunning a day means replacing that day's data, not doubling it.

BEGIN;
DELETE FROM daily_revenue WHERE order_date = :batch_date;
INSERT INTO daily_revenue (order_date, total_amount, order_count)
SELECT order_date, SUM(amount), COUNT(*)
FROM orders
WHERE order_date = :batch_date
GROUP BY order_date;
COMMIT;

The most critical parts of this code are

BEGIN

and

COMMIT

. DELETE followed by INSERT is only safe inside the same transaction. If the job crashes between the two statements, the partition is left empty, and the next morning the client sees zero revenue for that day.

Check: In a test environment, make the job stop right after the DELETE (for example, by deliberately injecting an error), then confirm the old data for that day is intact.

Step 4: Remove NOW() from your writes

Many jobs write

loaded_at = NOW()

to every row. A pipeline that does this produces different data on every rerun, and is therefore no longer idempotent. Use event time or the batch's logical date instead. Below is still the write from Step 3, with only the INSERT in the

BEGIN ... COMMIT

block changed:

-- 修改前：... SELECT order_date, SUM(amount), COUNT(*), NOW()
-- 修改后：写入调度器传入的逻辑日期
INSERT INTO daily_revenue (order_date, total_amount, order_count, batch_date)
SELECT order_date, SUM(amount), COUNT(*), :batch_date
FROM orders
WHERE order_date = :batch_date
GROUP BY order_date;

Check: Run the same day twice, export the results to files, and diff them. If even a single column differs, there's still a source of nondeterminism in the job.

Why watermarks won't save you?

The common approach to incremental loading is to keep a watermark—for example, the maximum

updated_at

already loaded—and pull only newer rows next time. An analysis by Algoscale points out that watermark logic looks simple but is surprisingly fragile in practice.

It breaks on timestamps that fall exactly on the boundary, late-arriving rows, and timezone inconsistencies; one case on Fabric even produced duplicate data.

So don't let the watermark be responsible for data correctness. Once writes are idempotent, each business key maps to exactly one row, and selecting the same row twice produces no duplicates. In Algoscale's words, duplicate selection no longer corrupts data; at worst you read a bit more data.

In practice, once writes are switched to MERGE, you can deliberately move the watermark back a little to catch late-arriving rows. The cost is reading some extra data; the benefit is no longer worrying about losing data.

Step 5: Backfill is just a loop

At this point, backfilling the client's historical data becomes simple: rerun partition by partition. Data Vidhya writes that for teams with idempotent pipelines, backfilling is something you knock out on an ordinary Tuesday afternoon. The script below is simplified;

run_partition

is a function that invokes Steps 1 through 4 for a given date.

from datetime import date, timedelta

def run_partition(batch_date):
    # 先 MERGE 写入 orders，再覆盖 batch_date 当天的 daily_revenue
    ...

d = date(2025, 1, 1)
end = date(2025, 12, 31)
while d <= end:
    run_partition(d)
    d += timedelta(days=1)

Check: Run the loop twice over a short range (say, three days); the row counts and totals from both runs must match exactly. If the loop fails on day 200, just resume from that day—no cleanup needed.

Common Pitfalls

The most common mistake is choosing the wrong business key. If the client's source system reuses

order_id

across different stores, MERGE will overwrite the wrong orders; the correct key should be a combination of store and order number. Ask about this during the client requirements discovery phase—don't guess.

Equally common: DELETE and INSERT split across two jobs, or running in autocommit mode, which throws away the safety net that transactions provide in Step 3. Many teams also only test the happy path. A pipeline that has never been run twice for the same day should be considered untested.

On the Client Site

At a new client, your first task isn't to write a new pipeline—it's to ask: "What happens if we rerun last night's job?" The answer will tell you whether their system can withstand retries and backfills.

Before agreeing to load three years of historical data, first check whether each target table is written with INSERT, MERGE, or partition replacement.

If you're applying for an FDE role, look for job descriptions that mention "data ingestion," "backfill," or "pipeline reliability." Writing "built ETL pipelines" on your resume says almost nothing. Instead, be specific: you changed a job from INSERT to MERGE on the business key, and therefore backfilled a year of data with zero duplicates.

Every pipeline will eventually fail. What's truly worth showcasing is a pipeline where a failure just means rerunning—no one has to clean up data afterward.
