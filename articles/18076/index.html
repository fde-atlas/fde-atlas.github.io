asyncio Concurrency Control: Rate Limiting and 429 Retry for Batch LLM Requests

Original title: asyncio 并发控制：LLM 批量请求限流与 429 重试

FDE Times · 2026-10-09 · 7 min read

Summary

This guide teaches FDEs how to batch 20,000 LLM requests (e.g., classifying support tickets) with asyncio without hitting 429 storms, PoolTimeout, or scripts stuck at 97%. It introduces four brakes: a Semaphore to cap in-flight requests, a rate limiter that actually determines total runtime, layered timeouts (httpx, retry budget, outer asyncio.timeout), and bounded retries. It explains that Anthropic's spend-limit 429s lack retry-after and should stop the job, why TaskGroup beats gather for cancellation, and lists common on-site mistakes like mismatched Semaphore and connection pool sizes.

Key points

  • A rate limiter, not concurrency, determines total batch runtime.
  • Timeouts need three layers: httpx, retry budget, and asyncio.timeout.
  • A bare 429 without retry-after means stop, not retry.
  • TaskGroup cancels remaining tasks on failure; gather does not.
  • Keep Semaphore size equal to httpx max_connections.

Four limits—concurrency, pacing, timeouts, and retries—to say goodbye to 429 storms, PoolTimeout, and getting stuck at 97%.

Key takeaways

  • A Semaphore only limits the number of requests running at the same time. The API may still enforce per-second rate limits, so you also need a rate limiter, and the total task duration is determined by the rate limiter.
  • Every layer of waiting needs its own cap: httpx timeouts, a time budget for retries, and an outer asyncio.timeout.
  • Catch errors for individual records inside the worker; let errors like hitting a spend limit propagate so the TaskGroup cancels the whole job.

A client sends you 20,000 support tickets and asks you to classify them with an LLM by Monday morning. The sequential

for

loop would take about a full day, so you switch to

asyncio.gather

and fire everything off at once. First the screen fills with 429 errors, then

PoolTimeout

appears, and at 97% the script freezes.

Almost every Forward Deployed Engineer (FDE) has run into this, whether the target is OpenAI's API, Anthropic's API, or the client's aging internal system. The problem isn't slowness: slow jobs eventually finish.

What actually breaks is a script without brakes. This guide covers the four brakes you need to install, a complete pipeline, and how to read a 429 correctly—deciding when to wait and when to stop.

Why does sending everything at once make things slower?

Every API has limits. OpenAI's documentation is explicit: requests that exceed the limit will temporarily receive

429

errors. When 20,000 coroutines queue up together, most of them just get 429s, then retry at the same moment and get blocked together again.

The client can also choke. httpx maintains a connection pool of limited size. If a request waits longer than the

pool

timeout for a connection, it throws

PoolTimeout

, meaning you've created more concurrent requests than the pool can supply connections for.

Getting stuck at 97% usually means some request hung with no mechanism to cut it off, or a retry loop with no exit. These errors don't surface. The script just sits there, and you can't tell where it's stuck.

A Semaphore alone isn't enough—you also need pacing

The first brake is

asyncio.Semaphore

. The Python documentation describes it as a counter that never goes below zero. When the counter hits zero, tasks calling

acquire()

wait until another task calls

release()

. With

Semaphore(20)

, no more than 20 requests ever run at the same time.

Here's the next point, often overlooked. Anthropic explains that its API uses a token bucket algorithm: capacity refills continuously rather than resetting at the start of each minute. So a 60 RPM limit may actually be enforced at 1 request per second, and a short burst can exceed it.

Imagine 20 requests in parallel, each taking only 300 ms. Within one second you've sent about 60 requests, exhausting the entire minute's quota, even though concurrency never exceeded 20.

So the second brake is a rate limiter, which enforces a minimum interval between sends. Anthropic also recommends ramping up traffic gradually and keeping usage steady to avoid triggering acceleration limits. In practice, start with a larger interval and shrink it over the first few minutes.

The two brakes serve different purposes, so do the math before you start. The rate limiter determines the throughput ceiling: at 1 request per second, 20,000 tickets take 20,000 seconds, about 5.5 hours, no matter how many requests are allowed in parallel.

The Semaphore limits the number of in-flight requests. That number roughly equals the send rate times the duration of a single request: if each LLM call takes 10 seconds, you'll have about 10 in-flight requests, so

Semaphore(20)

mainly serves as a safety net when the API becomes abnormally slow.

If 5.5 hours still beats Monday's deadline, let the job run overnight. If it doesn't, raising the Semaphore won't make it faster—what you should do is ask the client to request a higher quota.

A pipeline for classifying 20,000 tickets

Below is skeleton code that calls a classification API with httpx. The remaining two brakes are timeouts and capped retries. Look closely at the numbers: each one lives at a different layer.

import asyncio, random, time
import httpx

MAX_CONCURRENT = 20
MIN_INTERVAL = 1.0      # 60 RPM -> 每秒 1 个请求 -> 20,000 张工单约 5.5 小时
RETRY_BUDGET_S = 120    # 重试允许的总时长
PER_ITEM_S = 150        # 每张工单的硬性上限

# 与服务商相关的开关：
# Anthropic：消费上限的 429 不带 retry-after，重试无用 -> True
# OpenAI：缺少该响应头时，使用指数退避 + 抖动 -> False
STOP_ON_BARE_429 = True

class SpendLimitError(Exception):
    """Anthropic 式的消费上限 429，不带 retry-after：重试无用。"""

class Pacer:
    def __init__(self, interval: float):
        self.interval = interval
        self._lock = asyncio.Lock()
        self._next = 0.0

    async def wait(self):
        async with self._lock:
            now = time.monotonic()
            if self._next > now:
                await asyncio.sleep(self._next - now)
            self._next = max(now, self._next) + self.interval

def retry_after_seconds(resp):
    try:
        return float(resp.headers["retry-after"])
    except (KeyError, ValueError):
        return None

async def call_with_retry(client, pacer, payload, max_attempts=5):
    start = time.monotonic()
    for attempt in range(max_attempts):
        await pacer.wait()
        resp = await client.post("/classify", json=payload)
        if resp.status_code not in (429, 503):
            resp.raise_for_status()
            return resp.json()
        if (resp.status_code == 429 and STOP_ON_BARE_429
                and "retry-after" not in resp.headers):
            raise SpendLimitError("429 且没有 retry-after")  # 停止，不要重试
        wait = retry_after_seconds(resp)
        if wait is None:                      # 响应头缺失或无效（开关关闭），或 503
            wait = min(2 ** attempt, 30)      # 指数退避
        wait += random.uniform(0, 1)          # 抖动
        if time.monotonic() - start + wait > RETRY_BUDGET_S:
            break
        await asyncio.sleep(wait)
    raise RuntimeError(f"重试次数已用尽，最后状态码 {resp.status_code}")

async def worker(client, sem, pacer, ticket):
    async with sem:
        try:
            async with asyncio.timeout(PER_ITEM_S):
                result = await call_with_retry(client, pacer, ticket)
            return {"id": ticket["id"], "ok": True, "result": result}
        except SpendLimitError:
            raise                             # 让 TaskGroup 取消整个任务
        except Exception as e:
            return {"id": ticket["id"], "ok": False, "error": repr(e)}

async def main(tickets):
    sem = asyncio.Semaphore(MAX_CONCURRENT)
    pacer = Pacer(MIN_INTERVAL)
    limits = httpx.Limits(max_connections=MAX_CONCURRENT)
    timeout = httpx.Timeout(60.0, pool=30.0)
    try:
        async with httpx.AsyncClient(base_url="https://api.khach.example",
                                     limits=limits, timeout=timeout) as client:
            async with asyncio.TaskGroup() as tg:
                tasks = [tg.create_task(worker(client, sem, pacer, t))
                         for t in tickets]
    except* SpendLimitError:
        print("已触达消费上限：停止任务，通知客户的账号负责人")
        raise
    return [t.result() for t in tasks]

The retry logic follows OpenAI's recommendation.

Retry-After

is only a

最短

wait time: wait at least that long, plus a small random amount.

If that response header is missing or invalid, fall back to exponential backoff with jitter, so all clients don't retry simultaneously. Cap retries by both attempt count and total duration—here, 5 attempts and 120 seconds.

When you hit a 429 without that header, stop immediately; this branch is controlled by the

STOP_ON_BARE_429

switch and must be configured per provider. For Anthropic, the documentation states that spend-limit 429s come without

retry-after

, so retries are useless—turning the switch on makes sense.

For OpenAI, the official recommendation is to back off when the header is missing, so turn the switch off. If you're calling a client's API, first ask how they signal "do not retry," then adjust this one condition accordingly.

Timeouts work at three layers. httpx by default throws

TimeoutException

after 5 seconds without network activity. That's too short for LLM calls that generate long replies, so here it's raised to 60 seconds. The middle layer is the 120-second retry budget, and the outermost

asyncio.timeout(150)

wraps everything, converting any stuck situation into

TimeoutError

, guaranteeing no ticket hangs forever.

Which errors to catch, and which to let through

An easily missed detail:

try/except

sits inside the worker

内部

. With

TaskGroup

, as soon as any task fails for the first time with an exception other than

CancelledError

, the rest of the group is cancelled. One bad ticket must not drag down the other 19,999, so the worker catches ordinary errors itself and returns a record marked

ok: False

.

But for

SpendLimitError

, that cancellation behavior is exactly what you want. The worker re-raises it, the TaskGroup cancels all remaining tasks, and

main

is caught via

except*

. The job stops immediately, instead of letting thousands of tickets slam into the same wall one after another.

Why not use

gather

? By default,

gather

propagates the first exception, but the other awaitables

不会被取消

and keep running.

Your

main

function has already returned, yet requests are still in flight—some extremely hard-to-trace bugs come from exactly this. With a TaskGroup, once an error is raised, the remaining tasks are all cancelled, leaving no runaway requests still running.

Not every 429 should be retried

If you're calling through an official SDK, don't hand-write the retry loop above. OpenAI's documentation states that every official SDK automatically retries eligible

429

and

503

responses according to its retry configuration.

Do the math: if the SDK retries a few times per call and your loop tries 5 more times, the actual number of requests sent is the product of the two, not the sum. Keep the Semaphore, the rate limiter, and the timeouts; adjust retries in the SDK's configuration instead.

There's another kind of 429. According to Anthropic's documentation, when an organization hits its spend limit, the 429 response comes without the

retry-after

header, and all retries (including the SDK's automatic retries) will fail until access is restored. That's why, when integrating with Anthropic, the code above turns the switch on and raises

SpendLimitError

instead of continuing to back off.

If you're using Anthropic's SDK, check for this response header in the logs or in the exceptions returned by the SDK. Once you encounter it, stop the task and notify the customer's account owner.

Common mistakes at customer sites

First, a Semaphore larger than httpx's

max_connections

. The extra requests wait in the connection pool and receive

PoolTimeout

, which looks like a network error but is actually a configuration error. Keep these two numbers consistent.

Second, retries with no time budget. Five attempts, each waiting the full 60-second

Retry-After

, and a single ticket takes five minutes. Third, logs that only record the total error count. If the results include

id

and

error

for each ticket, you only need to rerun the 312 failed ones, not all 20,000.

The last one is running at full capacity from the first minute on the customer's system. Their internal API won't necessarily return a 429 as politely as OpenAI does; it might just crash. Ask about the real limits first, then ramp up gradually.

How this skill shows up on a resume

When reading FDE job descriptions, look for items about integrating with customer APIs or handling large batches of data: that's exactly where this skill comes into play.

On your resume, rather than writing "proficient in asyncio," write outcomes: processed N records through a rate-limited API, using pacing and capped retries, with per-record error reporting, and no tasks left hanging.

In interviews, clearly explaining

TaskGroup

versus

gather

, or why for Anthropic a 429 without

retry-after

means stop rather than retry, is far more convincing than listing library names.

A good batch script doesn't need to be the fastest. It needs to finish, and be able to tell you exactly which tickets didn't complete and why, before the customer even asks.
