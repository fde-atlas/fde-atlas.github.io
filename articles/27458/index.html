Today's Judgment

Today's two platform signals point to the same thing: the unit of competition in enterprise AI is upgrading from "can you build an agent" to "can you organize a group of agents into business operations systems and continuously improve them using production traces."

Baidu proposed an "industry agent operating system" that orchestrates general, specialized, and custom agents in a unified way—upward, it takes on business tasks; in the middle, it connects enterprise knowledge and processes; downward, it schedules compute and security resources. AWS, meanwhile, has turned agent optimization into an engineering closed loop of "production traces → suggestions → offline evals → online A/B → promotion"—changing prompts has gone from a craft to a controlled release.

Single-agent development will become increasingly platformized. The high-value work of the Forward Deployed Engineer will concentrate on task decomposition, system integration, permissions and accountability, cross-agent coordination, outcome metrics, and operational governance—the platform sells the "operating system," while the FDE translates the customer's business problems into a runnable, sign-off-ready task system.

Key Signals

Baidu proposes an "industry agent operating system": multiple agents, enterprise systems, and cloud resources form a business operations closed loop

  • Source: Baidu Intelligent Economy Forum | Press release; People's Daily coverage
  • On September 16, Baidu proposed an "industry agent operating system": general, specialized, and custom agents are orchestrated in a unified way—upward, it takes on tasks; in the middle, it connects enterprise knowledge, data, and processes; downward, it schedules compute and security resources. The ecosystem platform also opens up connectors, skills, suites, and hardware onboarding. Per Baidu, Taikang Insurance Group has already deployed more than 3,500 agents, consuming 20 billion tokens per day. People's Daily framed the forum as a key shift in the industry's direction: "from being able to answer to being able to deliver."
  • Why it matters: The word "operating system" is well chosen—when the number of agents in an enterprise grows from single digits to thousands, the question shifts from "how to build one" to "how to manage a group": who takes on which task, who accesses which data, how conflicts are adjudicated, how costs are allocated. The FDE's solution template should upgrade from a "feature checklist" to a three-layer task system: a business task layer (what to do, who signs off) → a knowledge/data/process connection layer (what makes it correct) → a model/compute/security resource layer (what to build with, how much it costs)—with owners, failure escalation paths, and acceptance metrics specified at each layer. Note: the 3,500 agents and 20 billion tokens figures come from Baidu's press release and were not confirmed by People's Daily; token consumption is not business value.

AWS AgentCore: turning agent improvement into a "traces—suggestions—evals—A/B—promotion" closed loop

  • Source: AWS official | Original link
  • On September 16, AWS released its AgentCore system prompt optimization method: it reads production traces and reward signals, compares successful/failed paths, and proposes configuration changes; candidate changes must pass offline batch evals and online A/B testing before promotion. The control mechanisms are finely designed: candidate prompts whose length grows by more than 20% are rejected; they must pass safety checks; and directly reusing original sentences from traces is prohibited (to prevent overfitting). AWS recommends starting with 10-50 diverse traces.
  • Why it matters: This echoes last week's openJiuwen RSI across borders—production agents should not rely on engineers "tweaking prompts by feel." Configuration changes should be treated with the same rigor as code releases: explainable, comparable, and reversible. The full trace-driven optimization pipeline has seven gates: production traces → success/failure labeling → change suggestions → safety/length/overfitting checks → offline regression → online gradual A/B rollout → promotion or rollback. The direct takeaway for FDEs: failure logs, task scores, user complaints, configuration versions, regression sets, rollout percentages, and rollback criteria should all become formal deliverable assets—pull 20 success/failure traces from any existing project and you can run the first minimal closed loop. Note: AWS's benchmark scores are vendor evals and cannot be extrapolated to enterprise ROI.

Platform capabilities keep ramping up: Tencent Cloud adds long-term memory stores and knowledge freshness management

  • Source: Tencent Cloud product updates | Original link
  • Tencent Cloud's agent development platform September product updates added long-term memory stores, knowledge base metadata, and scheduled updates—addressing three production pain points respectively: user-level memory governance, retrieval precision, and knowledge freshness. In the same period, the 2026 ITValue Summit took "systematic AI adoption" as its theme, with topics shifting from model parameters to data, knowledge, infrastructure, and organizational capability.
  • Why it matters: The direction of platform vendors' feature evolution confirms the real ranking of pain points on the enterprise side—how to govern memory (how to correct erroneous memories, how to delete and audit them), how to make retrieval more accurate, how to keep knowledge fresh. In long-term operations, these three issues are more fatal than "how well it answers." The shift in topics at the CIO conference is the same signal: industry discussion is moving from models to systems. Note: platform capability updates do not equal customer production results; deletion, audit, and correction mechanisms for long-term memory still await testing with named customers.

Implications for FDE Practitioners

  • Upgrade the solution template to a three-layer task system: a business task layer, a business connection layer, and a technical resource layer—specifying inputs, permissions, responsibilities, failure escalation, and sign-off at each layer. What customers buy is not the number of agents, but the reliability of the task system.
  • Build a "change release gate" for every project: production traces go into a failure library, and any configuration change goes through offline regression, gradual rollout, human review, and release and rollback records. Starting with 20 traces is enough—the key is that the process exists, not the scale.
  • Maintain professional habits toward platform numbers: for 3,500 agents, first ask how "active" is defined; for 20 billion tokens, first ask about task success rates—helping customers translate vendor narratives into verifiable metrics is itself part of the FDE's everyday value.
  • Two kinds of compounding—pick the right one: one is delivering the same course a thousand times over; the other is depositing another layer of methods, standards, and training tasks with every real project you do. The former is a scale business; the latter is the FDE's long-term moat—true compounding is not repetition, but writing back.
