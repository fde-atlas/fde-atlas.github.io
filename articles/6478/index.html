Run the engagement as a learning loop with explicit release gates

FDE Interviews · 2026-08-09 · 16 min read

Summary

Lesson three of a Foundations of Forward Deployed Engineering course frames a pilot engagement as an eight-activity learning loop: discover, scope, evaluate, ship, integrate, observe, learn, and productize. The loop is a set of dependencies, not a linear release plan—identity, integration, and security checks start during discovery and must pass before affected production use. A synthetic freight pilot shows how evidence, such as contract reads failing to preserve caller permissions, forces a return to design and release decisions. The lesson also calculates when a reusable connector pays off: bespoke work costs 20 hours per deployment versus 36 upfront plus 8 per deployment for shared; without maintenance, three deployments tie, and adding 12 maintenance hours pushes the tie to four. Repetition alone does not justify generalizing; reuse proposals need demand, cost, migration, and a named maintenance owner.

Key points

  • The eight-activity loop is a dependency structure, not a chronological release plan.
  • Evaluation complements deterministic requirements; human review alone is not release approval.
  • A caller-scope permission defect in the freight pilot must be fixed before any affected release.
  • Reuse arithmetic: three deployments tie without maintenance, four with 12 maintenance hours added.
  • A third similar implementation is not an automatic rule for productizing shared components.

Feed useful patterns into shared capabilities, when the demand, maintenance and cost case support doing so.

You've mapped the last-mile work, and the roles that collaborate on it. This lesson gives the rest of Foundations a working structure, and a small planning exercise you can run before learning the implementation details.

Use the loop as a set of questions. The diagram keeps eight activities visible. It isn't a mandatory chronological deployment plan.

Discover the real problem, scope one thin slice, evaluate by defining what works, ship an approved release, integrate with their systems, observe what it does, learn and change the build, and productize, making it reusable. Productize feeds back into discover, carrying learning into the next engagement.

In particular, identity, integration and security can't wait until after a production release, simply because "integrate" appears later in the drawing. Those checks begin during discovery. And they must meet their release conditions before affected use.

Each activity asks a question, and leaves something behind. Discover asks what task and constraint we're actually addressing, and leaves a workflow trace with its open assumptions, while scope asks what bounded outcome this phase can assess, and fixes the eligible population, the exclusions and the decision. Evaluate asks what would count as useful and acceptable. Its answer is a baseline, quality rules, failure cases and an analysis plan. The ship step asks whether this revision is permitted, and ready for its intended use. Proof? An approved release scope, and a checked artifact.

Integrate asks whether the source, identity, network and downstream contracts hold, and leaves tested boundaries with named owners, while observe asks what happens during use, including failed and unfinished work, and collects quality, completion, cost and operating signals. Learn asks which assumption or implementation needs revision. The answer is a change backed by evidence. Or a stop. And productize asks which recurring capability is worth maintaining for reuse. It leaves a reuse proposal, tests, costs and a long-term owner.

Evaluation is part of the specification, especially for probabilistic behavior. It doesn't replace deterministic requirements, such as permission enforcement, valid state transitions and recovery. A human review step can reduce some risks, but it needs a defined scope, information and capacity. Its mere presence isn't release approval.

Samples and prototypes can produce useful evidence about limited questions. State which questions they answer, and which require the target environment or a representative evaluation. And production data isn't the default testing material, when a safer approved fixture can answer the question.

Now follow one change around the loop. In this synthetic freight pilot, the initial request is "summarize every exception."

Observation shows operators first need to identify the shipment, and find the applicable contract. So the proposal becomes a domestic, read-only decision aid for a defined set of records, with uncertain matches routed to manual review. The team agrees its eligible cases and quality checks before implementation.

Integration testing then shows that some contract reads don't preserve the caller's scope, which means the request ran with the service's own broader credential, instead of the permissions of the person asking. That finding sends the team back to the design and release decision. It isn't something to watch casually after rollout.

After the access path is corrected and verified under the responsible process, a bounded release may proceed, if the other required checks pass. Then something new shows up. Later observation reveals that operators spend more time verifying summaries for multi-leg shipments.

So. Were those shipments excluded? Then record whether any entered the workflow unexpectedly. If they were included, investigate the failed segment and revisit the scope. Either way, don't drop inconvenient cases from the success report without saying so.

A release can be paused, reduced or reversed, where the evidence and authority require it. Iteration isn't a promise that every problem will yield to one more prompt change. Agree the time, cost and evidence that would justify continuing, before the experiment becomes indefinite.

Next, tell repetition apart from a reuse case. A recurring need is a reason to investigate a shared component, but it doesn't prove that the third similar implementation is the correct moment to generalize.

Three customers may use similarly named fields with different semantics, permission models or lifecycle rules. So compare the stable core and the variation.

An adapter might share parsing, validation and checkpoint machinery, while leaving customer-specific mapping and credentials in configuration. Shared behavior needs tests across the supported contracts, migration planning for existing users and an owner who can maintain it.

Reusable work can serve the current customer too. A supported connector may reduce their maintenance burden. Turn it around, and a one-off integration may be appropriate when demand is narrow, and a general framework would cost more than it saves. The decision isn't a moral ranking of software and services.

Now calculate a small reuse decision. This synthetic estimate compares engineering hours across future deployments.

Bespoke work takes 20 hours per deployment. A shared connector needs 36 hours up front, and eight hours per deployment for configuration and verification. Ignore maintenance at first, to expose the basic arithmetic. Then add it explicitly.

Plot both. Bespoke is 20 hours times the deployment count. Shared is 36 plus 8 times the count. Twenty d equals 36 plus eight d, so d is 3. Three deployments tie, at 60 hours each. The fourth saves 12 hours, 80 against 68. Every deployment past the tie saves the difference in the per-deployment rates, 20 minus 8. That's why the saving is 12 hours each time.

Now add 12 maintenance hours over the same planning horizon. That moves the up-front figure to 48, and the crossing to d equals 4. So four deployments tie at 80 hours, and the fifth saves 12, at 100 against 88.

The estimates don't establish that five customers will arrive, or that shared behavior will fit them. These compare engineering hours. Not profit. A real decision may also include support, opportunity cost, migration, reliability, licensing and strategic value.

Add comparable costs to both options, and avoid counting already-spent effort as a future saving, because a component that saves setup time but centralizes a risky failure mode needs a reliability review as well.

Last, decide who carries the learning forward. A reuse proposal should name the repeated need, source evidence, stable interface and supported variations, along with expected demand, estimated costs, migration and a maintenance owner.

Coordinate with the product team, rather than assuming the field engineer can add every useful abstraction to the shared platform. Sometimes the right output is better documentation, a deployment template, a test fixture, or a clearly documented unsupported case. Product learning is broader than a new feature. It should help future decisions without leaking customer data, or preserving an accidental workaround as the product contract.

After a pilot, record what changed in the workflow, and what remains uncertain. A clean handover can coexist with future iteration under a new owner, and the original engineer need not stay indefinitely to keep the loop alive.

A small reuse decision, calculated

This synthetic estimate compares engineering hours across future deployments. Bespoke work takes 20 hours per deployment, while a shared connector needs 36 hours up front and eight hours per deployment for configuration and verification. Leave maintenance out at first so the basic arithmetic is visible, then add it explicitly.

def costs(deployments, shared_maintenance=0):
    if type(deployments) is not int or deployments < 0:
        raise ValueError('Deployment count must be a nonnegative integer')
    if shared_maintenance < 0:
        raise ValueError('Maintenance hours cannot be negative')
    bespoke = 20 * deployments
    shared = 36 + 8 * deployments + shared_maintenance
    return bespoke, shared

for count in range(1, 6):
    print(count, costs(count), costs(count, shared_maintenance=12))
assert costs(3) == (60, 60)
assert costs(4) == (80, 68)
assert costs(4, 12) == (80, 80)
assert costs(5, 12) == (100, 88)
# 1 (20, 44) (20, 56)
# 2 (40, 52) (40, 64)
# 3 (60, 60) (60, 72)
# 4 (80, 68) (80, 80)
# 5 (100, 76) (100, 88)

Without the added maintenance estimate, three deployments tie and the fourth saves 12 hours. With 12 extra maintenance hours over the same planning horizon, four tie and the fifth saves 12. The tie is where the two lines cross: 20 hours per deployment against 36 up front plus 8 per deployment, so 20d = 36 + 8d and d = 3. Every deployment past the tie saves the difference in the per-deployment rates, 20 minus 8, which is why the saving is 12 hours each time. Adding 12 maintenance hours moves the up-front figure to 48 and the crossing to d = 4, and raising setup to 60 in the exercise moves it to 6. When the current commitment calls for a one-off

Apply the same synthetic cost estimates to an actual scheduling choice. One deployment is funded and due next week, and four other organizations have expressed interest without any of them committing. The engineer has 28 working hours available next week; eight are already committed to unrelated customer work. The estimates above cover implementation, configuration and verification for the proposed connector scope. For this exercise, both approaches are technically acceptable if the required checks pass, and the one-off has an accepted support owner. Those conditions would need evidence in a real engagement.

Write a recommendation that separates next week's capacity from the longer planning horizon. There are 20 hours available for this deployment: 28 minus eight. Bespoke work uses exactly those 20 hours. The shared option needs 44 hours before its first deployment, 36 of setup plus eight of configuration and verification, which is 24 hours more than the project has. Neither prospective demand nor a future saving supplies those hours next week.

Decision horizon Comparison Defensible conclusion
Current funded deployment 20 bespoke hours versus 44 shared hours; 20 available The one-off fits the estimate; the shared option needs an explicit capacity or date change
Five deployments, if they happen 100 bespoke hours versus 88 shared hours, including the extra 12 shared-maintenance hours Reuse could save 12 hours under these assumptions; interested organizations are not confirmed deployments
Ongoing ownership One-off support accepted; shared maintenance owner still unassigned A favorable estimate does not assign responsibility for a shared component

The eight hours of unrelated work are already deducted from capacity; do not add them again to the connector's cost. The 12 shared-maintenance hours belong to the longer comparison, not the first-week implementation estimate. They represent additional shared-component maintenance in this fixture. If either option has other support costs, include them on a comparable basis before using the totals for a real decision.

A worked recommendation chooses the bounded one-off for the funded delivery, records the interface and tests that might be reusable, and schedules a separate reuse review when demand and ownership are clearer. That serves an important current customer without committing to a general platform. State that the 20-hour estimate leaves no spare project capacity; an overrun needs a scope, staffing or date decision, not invisible overtime. Do not quietly consume the other customer's eight hours.

Changed input: all five deployments become funded, a shared maintainer accepts the stated scope, and the first deadline moves to allow 52 total working hours before it. Eight hours stay reserved for unrelated work, which leaves 44 for the shared first deployment, so it now fits the estimate exactly, and the full-horizon comparison favors shared work by 12 hours. Revise your recommendation if the contracts really share the assumed behavior. What changed the choice was demand and time, not repetition. The revised plan still has no spare capacity at its first milestone.
