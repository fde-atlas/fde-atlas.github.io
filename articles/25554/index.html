your 100-day roadmap to becoming an FDE

Somewhat Artificial · 2026-10-13 · 12 min read

Summary

An OpenAI-certified FDE lays out a 100-day plan to learn forward deployed engineering by building one complete project: a support assistant that retrieves approved policies, drafts cited replies, and routes them for human review. The roadmap moves through scoping, software fundamentals, AI integration, context engineering and RAG, evals, and deployment with a pilot. Notably, evals begin on day one, retrieval quality is tested separately from model behavior, and the author cautions the plan assumes basic coding skills and guarantees neither certification nor a job.

Key points

  • One project, a support assistant, spans all 100 days.
  • Six phases: scoping, coding, AI basics, context, evals, deployment.
  • Evals are written from day one, not added late.
  • Retrieval and model usage are tested as separate checks.
  • Author disclaims official certification or job guarantees.

wtf does a forward deployed engineer actually do?

you sit with a customer, figure out the real problem, build software around how their team already works, and stay involved through testing and rollout.

this guide is about doing that work for AI applications. i'm an OpenAI-certified FDE, and this is the 100-day plan i'd put you on.

one project, start to finish.

the project: build a support assistant that pulls approved policies, drafts a reply with sources, and hands it to a person for review.

quick honesty check: this pace assumes you already know basic programming and can show up consistently. if you're new to coding, do the foundations first and stretch the timeline. this is my suggested plan. it's not an official certification course, and it's not a promise of a job in 100 days.

the 100 days at a glance

when focus what you finish
days 1–10 scoping a problem brief and a baseline
days 11–30 coding an app with an API and a database
days 31–45 AI fundamentals a tested model integration
days 46–60 context engineering policy retrieval with citations
days 61–80 evals a repeatable evaluation suite
days 81–100 deployment a pilot and a portfolio case study

evals start on day one. write down real tasks and what good behavior looks like the moment you scope the project. days 61–80 are for expanding and automating those tests, not for testing the app for the first time.

days 1–10 · scope the problem

learn: customer discovery, workflow mapping, requirements, boundaries and success metrics. get good at asking what happens today, who owns the task, where it breaks, and what a useful result would look like.

do:

  • talk to three potential users if you can
  • watch one task happen from start to finish
  • pick one narrow category for the support assistant, like policy questions
  • collect examples you're allowed to use, and measure the current handling time or error rate

then write a one-page brief:

  • the user and their problem
  • the current steps
  • the data you have
  • your first feature
  • what you're deliberately leaving out
  • where a human approves
  • how you'll measure success

and decide who gets to approve the pilot.

checkpoint: a user can read your brief and agree on what you're building and how they'll judge it. you already have your first test cases before you've picked a model.

resources, in this order

  • NN/g: Discovery · article, beginner focus on problem framing, user needs, constraints, stakeholder alignment and desired outcomes. apply it: write a brief that names the user, their problem, the current process and one measurable outcome. list what you still need to learn.
  • NN/g: Writing an effective interview guide · article, beginner focus on how to structure an interview, choose questions and dig into real experiences. apply it: prep questions about a recent support request. ask the user to walk you through what happened, which tools they used and where they got stuck.
  • NN/g: Journey Mapping 101 · article, beginner focus on actors, scenarios, stages, actions, pain points and opportunities. apply it: map one request from arrival to resolution. mark the handoffs, delays and missing info, then pick the part your first version will fix.

finish with: a one-page brief, a map of the current workflow, interview notes, a baseline and a list of initial eval cases. your user should recognize their actual problem in these docs.

days 11–30 · build the software

learn: Python functions, data structures, exceptions and tests. SQL tables, joins and updates. HTTP, JSON and APIs. Git commits and branches. learn to read stack traces and reproduce bugs.

build: an app that takes a support request, saves it to a database and lets a reviewer change its status. keep the interface simple. add input validation, plus tests for database operations and API errors.

use AI coding tools, properly: ask for small changes, read the diff, run the tests and explain the code back to yourself. keep API keys out of your repo. you need to be able to debug the app when the generated code breaks.

checkpoint: someone else can follow your README, run the app, submit a request and see it stored correctly. you can trace a failure through the code.

resources

  • Harvard CS50: Python · course + exercises, beginner focus on functions, data structures, exceptions, libraries, file I/O and unit tests. apply it: build a script that loads support requests, validates fields and handles malformed input. write tests before you connect it to a model.
  • Harvard CS50: SQL · course + exercises, beginner focus on querying, relationships, table design, constraints and writing data. apply it: create requests and reviewers tables. save new requests, update their status and join the tables to show who reviewed each one.
  • FastAPI tutorial · official tutorial, basic Python required focus on request bodies, validation, response models, error handling, security and testing. apply it: expose endpoints to submit and review a request. return useful errors for missing fields and test the API without calling a model.
  • Pro Git · online book, use it throughout focus on Getting Started, Git Basics and Git Branching. apply it: commit a working baseline, make a change on a branch, inspect the diff and practise reverting a bad change.

study selectively. if you're a beginner, slow down and do the exercises. if you already code, fill the gaps as you hit them while building. you don't need to finish both full courses in 20 days.

days 31–45 · add AI

learn: model API calls, instructions, tokens, context windows, output limits, structured outputs and tool calling. two things to really get: valid JSON doesn't mean a correct answer, and a proposed tool call needs validation before it runs.

build: classify each request into a fixed set of categories and return a structured result. add a read-only policy lookup function. validate tool arguments and enforce permissions in your application code. draft a reply for human review, and keep the actual sending outside the model's control.

compare: test two prompt or model configurations on the same examples. record errors, response time and cost. start with one model call or a simple workflow, and only add steps when a measured failure justifies them.

checkpoint: the app handles invalid output, failed API calls and unknown categories. you can explain why you chose that configuration.

resources

  • Full Stack LLM Bootcamp · recorded lectures, basic programming required focus on the LLM app lifecycle, prompting, augmented models and deployment concepts. heads up, it's a 2023 course, so use current provider docs for models, APIs and pricing. apply it: sketch your request-to-response workflow and mark which steps actually need a model. build the smallest useful version first.
  • OpenAI: Structured model outputs · official guide, basic API knowledge focus on schemas, constrained response formats and handling output failures or refusals. apply it: return a request category and a draft as structured data. validate the fields and test whether the content is right, not just whether it parses.
  • OpenAI: Function calling · official guide, basic API knowledge focus on tool definitions, argument schemas, the tool-call loop and returning tool results. apply it: add the read-only policy lookup. validate arguments and enforce access permissions in your app before running it.
  • Anthropic: Building effective agents · engineering article, intermediate your architecture check. focus on workflows vs agents, routing, and when extra autonomy is actually useful. apply it: compare your workflow with an agent approach. write down the specific failure that would justify adding another step or more autonomy.

days 46–60 · give it useful context

learn: how to pick the instructions, conversation history, retrieved documents and tool results for each task. for retrieval-augmented generation (RAG): chunking, embeddings, keyword search, ranking and source metadata.

build: index a small collection of approved policies. retrieve the relevant sections with their source IDs, and draft a reply that cites them. limit retrieval to docs the current user is allowed to see. decide what happens when policies conflict, are outdated, or just don't answer the question.

test retrieval on its own: for each question, label which policy should come back, and check that it shows up in the results before you judge the final answer. treat any instructions inside documents as untrusted content.

checkpoint: you can see exactly what context the model received, trace any claim back to its source, and get a useful handoff when the docs aren't enough.

resources

  • Anthropic: Effective context engineering · engineering article, some LLM app experience focus on selecting useful context, tool outputs, memory and strategies for long-running tasks. apply it: log the exact instructions, retrieved text and history sent for a request. cut what's irrelevant and compare behavior on the same eval cases.
  • Anthropic: Contextual Retrieval · technical article, understand basic RAG first build your baseline here. focus on chunk context, embeddings, keyword retrieval and reranking. treat their published results as findings for their setup, not promised gains for yours. apply it: write policy questions with known source docs. compare a simple retrieval baseline against one changed setting, and measure whether the right evidence comes back.
  • Anthropic: Writing effective tools for agents · engineering article, intermediate focus on tool naming, descriptions, useful response fields and eval-led iteration. apply it: give the policy lookup tool a clear description and compact results with source IDs. test ambiguous queries and empty search results.

keep two checks separate: did retrieval find the right evidence, and did the model use it correctly? a better prompt can't recover a policy the retriever never found.

finish with: a retrieval test set, a context log for each request, source citations in replies, and documented behavior for outdated, missing or conflicting policies.

days 61–80 · make quality something you can test

an eval is a repeatable task plus a rule for judging the result. keep ordinary software tests for deterministic code. use evals for model answers, retrieved evidence, tool choices and the full workflow.

build the suite: start with something manageable, like 30–50 varied examples, then grow it from your failures. use synthetic or authorized, de-identified data. keep a held-out set you never use to tune prompts. that starting count is a project exercise, not proof you're production-ready.

test case expected behavior
normal policy question answer from the correct policy and cite it
missing order detail ask for the missing detail, don't invent it
no relevant policy explain the gap and hand off to a person
conflicting policy versions use the approved current version or escalate
another customer's data application access controls block retrieval
instructions hidden in a document treat them as data, don't follow them
lookup times out report or retry safely, never claim success

score behavior, not how confident it sounds

track task success, unsupported claims, correct citations, correct handoffs, tool arguments, permission failures, latency and cost. use code checks for schemas and exact rules, and human review for answer quality. if you add an AI grader, compare its judgments with human labels first.

run and compare: use Promptfoo or a small test runner. save the model, prompt and dataset versions with every result. inspect failure traces, change one thing, rerun. keep critical safety failures separate from the average score.

deliverable: a report with test-case counts, pass rates by category, failures, latency and cost. agree on release thresholds with your user, and rerun after any change to models, prompts, retrieval or tools.

resources

  • OpenAI: Evaluation best practices · official guide, beginner to intermediate focus on task-specific objectives, representative data, scoring criteria and continuous evaluation. focus on the evaluation design, and check current docs before adopting a specific hosted feature. apply it: turn your brief into a rubric. define a good answer, a correct handoff and a critical failure before comparing configurations.
  • Promptfoo: Getting started · hands-on docs, basic dev setup focus on test cases, assertions, providers and comparing configurations. apply it: run the same support cases against two prompt versions. save per-case results, inspect regressions, and rerun after a model or retrieval change.
  • Anthropic: Demystifying evals for AI agents · engineering article, intermediate go deeper here. focus on tasks, trials, graders, transcripts and outcomes, and why agents that take multiple actions are harder to test. apply it: inspect one failed run end to end. figure out whether the failure came from retrieval, tool selection, arguments, the environment or the final answer.

the practice loop: collect a failure → write its expected behavior → add a case → change one thing → rerun → review. keep a held-out set, and check automated graders against human judgment.

finish with: versioned test data, a scoring rubric, per-category results, latency and cost numbers, failure traces and a short release decision. keep serious permission or action failures visible even when the average score goes up.

days 81–90 · deploy and run a pilot

learn: hosting, environment variables, secrets, authentication, authorization, containers, logs and rollback. understand timeouts, retries and idempotency so a repeated request doesn't trigger duplicate actions.

deploy: package the app, use server-side credentials and add role-based access. log enough to investigate failures without keeping private data you don't need. put limits on model usage. keep human review on any action that needs approval.

pilot: watch a small group of willing users do the original task. record handling time, corrections, failures and feedback. compare it with the baseline from your brief, and ask where the app added extra work.

checkpoint: users can access the pilot safely, you can investigate a failed request, and you have a fallback for when the AI or its tools are down.

resources

  • Docker: Get started · official tutorial, basic coding required focus on images, containers, Dockerfiles and running an app reproducibly. apply it: package your app and document how someone else can run it. keep credentials out of the image and the repo.
  • FastAPI: Deployment · official guide, Python backend experience focus on HTTPS, startup, restarts, workers, memory and deployment concepts. apply it: deploy a small pilot with an authenticated interface. check what happens when the process restarts or an upstream API fails.
  • OWASP: Top 10 for LLM applications · security reference, intermediate your security review. focus on prompt injection, sensitive information disclosure and excessive agency, and read the current project materials for the detailed risks. apply it: add cases for malicious text inside a policy, cross-user data access and unauthorized actions. enforce permissions in application code.
  • Google SRE Workbook: Monitoring · book chapter, intermediate focus on metrics and structured logs that help you diagnose behavior and service health. apply it: track request success, errors, latency and cost. keep a request ID so you can trace a reported failure without logging unnecessary private data.

days 91–100 · show what you learned

build your portfolio case study. show the problem, the user and the original workflow. explain your scope, architecture, retrieval choices and approval points. include a short demo, code you can share, setup instructions, the eval dataset (or a safe sample) and a results report.

report honestly: name your sample size and test conditions. keep offline eval results separate from real pilot outcomes. if you don't have real users yet, call it a prototype and describe the next validation step.

be ready to talk about: why you used AI, where plain code was enough, your worst failure, how you debugged it, and what you'd change with more time. practise explaining the same project to an engineer and to a non-technical customer.

use this case-study structure

  • problem: who needed help and how the task worked
  • scope: what you built and what you deliberately left out
  • design: the major components and why you chose them
  • evidence: eval cases, results, test conditions and user feedback
  • limitations: failures, unresolved risks and your next experiment

resources

  • GitHub: About repository README files · official guide, beginner focus on explaining what a project does, why it's useful and how someone can use it. apply it: write setup steps, a short demo path, example inputs, environment requirements and known limitations. ask someone to run the project from the README.
  • Google: Technical writing courses · self-study lessons, beginner to intermediate focus on audience, clear sentences, consistent terms and organizing technical explanations. start with Technical Writing One. apply it: write a one-page case study a customer can understand. put the problem and the observed outcome before the implementation details.

the day 100 finish line

one working project you can explain, an eval suite, evidence of real feedback, and a clear case study. a runnable repo, a short demo, an eval report. if you only ran offline tests, say so.

use all of that to find your gaps against actual FDE job descriptions and tailor your applications.

and keep the plan flexible. move on when you can demonstrate the checkpoint, not when you finish watching a lesson.
