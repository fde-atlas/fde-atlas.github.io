Agent Skills with Anthropic course review for FDEs

FDE Times · 2026-11-15 · 4 min read

Summary

This review evaluates the 2-hour-19-minute Agent Skills with Anthropic course from DeepLearning.AI, taught by Elie Schoppik of Anthropic. Its central argument: the SKILL.md format is an open standard that travels across platforms—OpenAI Codex builds on the same standard—but deployment does not. Custom skills do not sync automatically, and upload, sharing scope and runtime environments differ per platform; for example, the Claude API blocks network access while Claude Code allows it. The course is worth taking if paired with each platform's documentation, and the author recommends actually deploying one skill on two platforms and documenting the differences.

Key points

  • Course runs 2h19m, with lessons on Claude API, Claude Code and the Agent SDK.
  • SKILL.md is an open standard; OpenAI Codex adopts the same format.
  • Custom skills do not sync automatically; deployment must be redone per platform.
  • Claude API has no network access; Claude Code does, causing runtime breakage.
  • Recommended: read Anthropic's engineering post first, then deploy a skill on two platforms.

The two-hour DeepLearning.AI and Anthropic course is worth taking, as long as you also read each platform's own documentation.

In brief

  • A Beginner-level course, 2 hours 19 minutes long, taught by Elie Schoppik of Anthropic, with three lessons dedicated to the Claude API, Claude Code and the Claude Agent SDK
  • The SKILL.md format also carries over to OpenAI Codex, because Codex is built on the same open standard
  • Each platform needs its own deployment: custom skills do not sync automatically, and network access and sharing scope differ

The landing page for the course Agent Skills with Anthropic makes a promise: skills follow an open standard format, so you write one once and deploy it on any agent that supports skills. The Claude API documentation carries a drier line: custom skills do not sync across surfaces, and uploading one in one place does not make it available anywhere else.

The two statements do not contradict each other. What travels is the format. Deployment, meaning upload, sharing scope and runtime environment, has to be redone on each platform, and for an FDE that is where customer projects tend to break.

The course is therefore still worth more than two hours of your time, provided you take it as an engineer about to be accountable for a system in production, not as someone watching a demo.

A short course, taught by Anthropic

DeepLearning.AI built the course with Anthropic and announced it on its community forum on 28 January 2026. The instructor is Elie Schoppik, Head of Technical Education at Anthropic. The course is rated Beginner, runs 2 hours 19 minutes, and the course page lists its most recent update as 17 July 2026.

The page says “10 Lessons” but the outline lists 12 items, so do not be surprised if your own count differs. The three most notable lessons are each dedicated to a platform: the Claude API (17 minutes), Claude Code (24 minutes) and the Claude Agent SDK (20 minutes). The page describes these lessons only briefly, so you cannot tell in advance how deeply they go into deployment.

DeepLearning.AI’s announcement describes skills as folders of instructions that extend an agent’s capabilities with specialised knowledge. For an FDE, that specialised knowledge is usually the customer’s business processes, gathered through customer discovery and something you want the agent to reuse every time.

First idea: a skill is just a folder

Anthropic’s engineering post of 16 October 2025 defines a skill as a folder containing a SKILL.md file. That simple definition has immediate practical consequences. In Claude Code, personal skills live in

~/.claude/skills/

, while project skills live in

.claude/skills/

.

Because they sit inside the repo, project skills get committed, reviewed in pull requests and handed over with the source code. Knowledge about the customer no longer lives in one person’s head.

Second idea: the format travels to other vendors too

“Write once” is the course’s marketing line, but there is independent evidence for it. Anthropic says skills run across four of its products and has published the format as an open standard, and the agentskills.io site confirms that origin. More convincing still, OpenAI Codex builds its skills on the same standard, with SKILL.md requiring

name

and

description

.

If a customer uses both Claude and Codex, you do not have to rewrite the instructions. Because Codex requires the

name

and

description

fields, write them carefully from the start if you want the skill to move to Codex without edits.

Third idea: deployment must be redone on each platform

Picture a customer whose backend calls the Claude API, whose engineering team uses Claude Code, and where another group uses Codex. You have one skill folder, but three deployment paths.

On the API, you upload the skill and it is shared across the whole workspace. With Claude Code, you commit it to

.claude/skills/

. In Codex, you choose whether to place the skill at the repo, user, admin or system level, or distribute it through a plugin if you want it used beyond a single repo.

The Claude API documentation spells out how the two environments FDEs meet most often differ.

Claude API Claude Code
Network and external APIs None Yes, like any other program on the machine
Installing packages at runtime Not allowed Documentation states no such limit
Sharing scope Whole workspace Personal folder or per project
Sync with other surfaces No automatic sync, upload separately No automatic sync

Try putting a concrete skill into that table. Suppose the skill calls an internal API to fetch the customer’s product catalogue. It works in Claude Code because there is network access, but once uploaded to the API it breaks, because there the skill cannot make outbound calls. The format is unchanged; only the environment differs.

The Claude documentation also advises treating skills like software installed on a system, and links to a separate page on governance, vetting and deployment at organisational scale. The very existence of that page shows deployment is a distinct discipline, outside the promise about the format.

What order to study in, and what to put on your CV

Read Anthropic’s engineering post “Equipping agents for the real world with Agent Skills” first, then watch the course. After the three platform lessons, open the Agent Skills overview page in the Claude API documentation straight away to fill in what the course page does not cover. If the customer uses Codex, also read OpenAI’s Build skills page.

The most worthwhile exercise is to deploy one skill on two platforms and record everything you had to change. On your CV, do not just list the course name. Write one specific line, such as “deployed the same skill to Claude Code and the Claude API, working around the no-network limit”.

A certificate shows you watched the whole course. A README that states clearly where the skill does not run shows you have actually deployed it.

Troubleshooting with journalctl When a systemd service fails to start after a reboot, you can troubleshoot it step by step using `journalctl` and related tools. ## 1. Check the service status ```bash systemctl status your-service.service ``` Focus on: - **Active**: whether it shows `active (running)`, `inactive`, or `failed` - The last few log lines, which usually contain the direct reason for the failure ## 2. View logs with journalctl View logs for the specified service: ```bash journalctl -u your-service.service ``` Only show logs from the most recent boot: ```bash journalctl -u your-service.service -b ``` Show only errors: ```bash journalctl -u your-service.service -p err -b ``` View logs from the previous boot (useful if the service failed during startup): ```bash journalctl -u your-service.service -b -1 ``` Follow logs in real time: ```bash journalctl -u your-service.service -f ``` Show the most recent 50 lines: ```bash journalctl -u your-service.service -n 50 --no-pager ``` ## 3. Common causes and solutions ### 1. The service is not enabled for auto-start on boot ```bash systemctl is-enabled your-service.service ``` If it shows `disabled`, enable it: ```bash sudo systemctl enable your-service.service ``` ### 2. Startup order dependency issues If the service starts before the network or a dependency is ready, it may fail. Check the unit file: ```bash systemctl cat your-service.service ``` Add or adjust: ```ini [Unit] After=network-online.target Wants=network-online.target ``` Then reload the configuration: ```bash sudo systemctl daemon-reload ``` ### 3. Restart behavior configuration If the process crashes and is not restarted, check the unit file: ```ini [Service] Restart=on-failure RestartSec=5 ``` ### 4. Permission or path issues - Check whether the user/group specified by `User=` and `Group=` exists and has sufficient permissions - Check whether the paths in `ExecStart=` are correct and the files are executable - If the service depends on a mounted disk, confirm that the mount is complete at boot time (add `RequiresMountsFor=`) ### 5. Environment variable issues Services started by systemd do not inherit the environment variables from your shell. If the service runs fine manually but fails at boot, it is often an environment variable problem. You can add: ```ini [Service] Environment="VAR=value" EnvironmentFile=/etc/your-service/env ``` ## 4. Other troubleshooting tips - **Check all failed units**: ```bash systemctl --failed ``` - **Check the full boot logs**: ```bash journalctl -b ``` - **Check for logs being lost**: if `journalctl` shows no historical logs, confirm that persistent logging is enabled: ```bash sudo mkdir -p /var/log/journal sudo systemctl restart systemd-journald ``` - **Manually run the ExecStart command**: switch to the corresponding user and run the command from `ExecStart=` directly to see the actual error output. ## 5. Typical troubleshooting workflow 1. `systemctl status` to confirm the failure status and initial error 2. `journalctl -u <service> -b` to view detailed logs 3. Check the unit file with `systemctl cat` to confirm dependencies, restart policy, and user permissions 4. Fix the configuration, then run `daemon-reload` and restart the service to verify 5.
