How to Run FDE Evals: Intercom Role Breakdown and an Evals Set in Practice

Original title: FDE 评测怎么做：Intercom 岗位解读与评测集实战

FDE Times · 2026-10-24 · 5 min read

Summary

This piece uses Intercom's Forward Deployed Software Engineer job posting in Dublin as a starting point: the role promises measurable business outcomes for the Fin support agent, yet lists no specific targets, leaving it to the FDE to define what and how to measure. The author argues that Fin's public figures (51% out-of-the-box resolution, 56% average in the first 30 days) are averages that say nothing about a specific customer. The reliable approach is building an eval set from the customer's own conversations and fixing a baseline and primary metric before the first run. A worked example with an order-tracking agent shows 30 test conversations, resolution rate as the primary metric and answer accuracy as a non-regressing secondary metric; fixing an order-ID formatting issue lifted resolution from 60% to 83% with no regressions. The article closes with three common mistakes and advice on presenting this skill in resumes and interviews.

Key points

  • Intercom's FDE posting promises measurable outcomes but sets no numeric targets.
  • Fin's public 51% and 56% figures are averages, not customer-specific numbers.
  • Build eval sets from real customer conversations; set baseline and metrics before the first run.
  • In the example, fixing order-ID normalization raised resolution from 60% to 83% with no regressions.
  • Avoid choosing metrics after seeing results, tracking only resolution, and using only self-made easy cases.

Key Takeaways

  • Intercom's FDE job posting promises measurable business outcomes but gives no targets, leaving the responsibility for defining how to measure them to the FDE.
  • Fin's public numbers are 51% out of the box and an average of 56% in the first 30 days, but neither number is the number for the customers you serve.
  • The reliable answer is to build an eval set from the customer's own conversations and set the baseline and primary metric before the first run.

Intercom is hiring a Forward Deployed Software Engineer in Dublin, and the job posting makes a big promise: ensure the company's customer service AI agent Fin delivers real, measurable business outcomes. Yet read the page to the end and you won't find a single concrete target.

That gap can be seen as the first test of the job. When no one says "you must hit this number," the Forward Deployed Engineer (FDE) has to decide what to measure, how to measure it, and what to compare against.

This situation arrives early.

The posting mentions working closely with Fin's strategic customers to understand their business problems and technical requirements. On-site with a customer, you will almost certainly hear this question: "What percentage of our issues can Fin resolve?" This article explains how to answer it with an eval set rather than a promise.

Public numbers are not customer numbers

There are two public numbers worth remembering. Anthropic's case study says Fin resolves 51% out of the box, before any customization. AWS's case study says customers reach an average of 56% within the first 30 days.

The two numbers differ because they were measured by different sources at different points in time. Both are averages, and neither tells you anything about the retailer or insurance company sitting across from you.

If you treat "56%" as a guarantee and the customer's real number turns out lower, they will remember that statement longer than any demo. The professional answer is: "We'll measure it using your own conversations, then report the numbers."

How does Intercom measure itself?

The method already exists, and it comes from Intercom itself. According to Anthropic's case study, every change to Fin, from small tweaks to major updates, is rigorously compared against a baseline running in production. The testing looks at multiple metrics at once: answer accuracy, resolution rate, customer satisfaction, and response quality.

Intercom calls this practice eval-driven delivery and says it follows the same methodology its AI research team uses to build and refine products. Its Evals product tests Fin's behavior using simulated scenarios built from the customer's own conversations.

Intercom's definition is concise: an Eval is a named set of Simulations, i.e., multi-turn test conversations. Pedro Tabacof, a machine learning scientist on the Fin team, wrote that if you take AI seriously, you must take evals seriously.

Example: a 30-case eval for "Where is my order?"

Suppose the customer is a retailer and the agent needs to answer order questions through an internal API. Before touching the prompt or code, follow Tabacof's advice on A/B testing: decide the primary metric before you start.

Here the primary metric is the share of conversations resolved without escalating to a human agent. Answer accuracy is the secondary metric that must not drop: if the resolution rate rises while answer accuracy falls, the change is rejected.

Take 30 order-related conversations, label the expected outcome for each, then write a small runner:

import json

# 每行：一段多轮测试对话 + 预期结果
# {"id": "o-07", "turns": ["我的订单 #A-1029 到哪了？"], "expect": "resolved"}
CASES = [json.loads(line) for line in open("evals/orders.jsonl")]

def run(agent, cases):
    results = {}
    for c in cases:
        out = agent.converse(c["turns"])
        results[c["id"]] = {"ok": out.outcome == c["expect"],
                            "reason": out.failure_reason}
    return results

def rate(results):
    return sum(r["ok"] for r in results.values()) / len(results)

baseline = json.load(open("evals/baseline.json"))  # 上一次运行的结果
current = run(agent, CASES)
regressions = [k for k, r in current.items()
               if baseline[k]["ok"] and not r["ok"]]
print(f"{rate(baseline):.0%} -> {rate(current):.0%}，回归：{regressions}")

The most critical part is

regressions

this line. An overall percentage can still rise while masking a few cases that used to pass and now fail, and these are exactly what the customer notices first.

Read the failures before fixing anything

Suppose the first run resolves 18 of the 30 cases, i.e., 60%. That result is the baseline. The most valuable thing to do now is not to tweak the prompt but to read all 12 failed cases and categorize them by cause.

In this example, 7 failures happen because users enter the order number as "#A-1029" while the API only accepts "A1029". 2 failures are due to API timeouts, and 3 ask about things outside the scope of orders.

The largest group tells you what to fix first. The fix takes one line: normalize the order number at the start of the query function:

order_id = re.sub(r"[^A-Za-z0-9]", "", raw_order_id)  # "#A-1029" -> "A1029"

The next run reaches 25 of 30, i.e., 83%, and the regression list is empty. The remaining 5 fall into the other two groups and have been organized into the next round of work.

Do it again with a real customer

With a real customer, the steps stay the same. Use the customer's real conversations as the source, just as Intercom's Evals build scenarios from customer conversations; then have someone on the customer's side who knows the business help with labeling, because you have no way to judge which answer is correct when it comes to their refund policy.

Then, before the first run, write the primary and secondary metrics into a document the customer will also read. Re-run against the baseline for every change, even a one-line prompt edit, just as Intercom does for Fin itself.

This sequence also answers the question of who sets the target. If the customer signs off on the primary metric at the start, the final number is a result both sides acknowledge, not a grade the FDE gives themselves.

Mistakes to avoid

The first mistake is choosing metrics after seeing the results. Running first and then picking the most flattering number to report is the fastest way to lose trust, and the advice to set metrics in advance exists precisely to prevent this.

The second mistake is looking only at the resolution rate. Intercom measures accuracy, satisfaction, and response quality at the same time, because an agent that "resolves" a conversation with a wrong answer is worse than one that hands the conversation to a human.

The third mistake is filling the eval set with simple cases you made up yourself. Situations like "#A-1029" only show up in real conversations, and they are often the largest group of failures.

How do you show this skill on a resume and in interviews?

When reading FDE job postings, watch for phrases that say "measurable outcomes" without attaching any numbers. When you see such wording, prepare a concrete story about a time you defined the measurement yourself: which metric you chose, why, and what the results were.

At the Staff level, Intercom expects people who can set direction, own outcomes, and work directly with customers and the go-to-market team. With an eval set that includes a baseline, you can report results to the sales team with numbers instead of post-demo impressions.

On a resume, a good bullet point has three parts: the system you integrated, how you measured it, and the before-and-after numbers. Following the example above, you could write: "Built a 30-conversation eval set for an order-lookup agent; self-service resolution rate improved from 60% to 83% (18→25/30), with no regressions."

This week's exercise

Pick a public API with user-level data, such as orders, tickets, or appointments, and write a simple agent that calls it. Write 30 test conversations, decide the primary metric, run once as the baseline, and note the cause of every failure.

What you bring into the interview is not a code repository but the sentence "7 of the 12 failures came from how users entered the order number," something only someone who has done the measuring firsthand can say.
