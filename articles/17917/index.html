# What to Do When a systemd Service Doesn't Start After a Restart? Troubleshooting with journalctl When a systemd service fails to start after a reboot, you can troubleshoot it step by step using `journalctl` and related tools. ## 1. Check the service status ```bash systemctl status your-service.service ``` Focus on: - **Active**: whether it shows `active (running)`, `inactive`, or `failed` - The last few log lines, which usually contain the direct reason for the failure ## 2. View logs with journalctl View logs for the specified service: ```bash journalctl -u your-service.service ``` Only show logs from the most recent boot: ```bash journalctl -u your-service.service -b ``` Show only errors: ```bash journalctl -u your-service.service -p err -b ``` View logs from the previous boot (useful if the service failed during startup): ```bash journalctl -u your-service.service -b -1 ``` Follow logs in real time: ```bash journalctl -u your-service.service -f ``` Show the most recent 50 lines: ```bash journalctl -u your-service.service -n 50 --no-pager ``` ## 3. Common causes and solutions ### 1. The service is not enabled for auto-start on boot ```bash systemctl is-enabled your-service.service ``` If it shows `disabled`, enable it: ```bash sudo systemctl enable your-service.service ``` ### 2. Startup order dependency issues If the service starts before the network or a dependency is ready, it may fail. Check the unit file: ```bash systemctl cat your-service.service ``` Add or adjust: ```ini [Unit] After=network-online.target Wants=network-online.target ``` Then reload the configuration: ```bash sudo systemctl daemon-reload ``` ### 3. Restart behavior configuration If the process crashes and is not restarted, check the unit file: ```ini [Service] Restart=on-failure RestartSec=5 ``` ### 4. Permission or path issues - Check whether the user/group specified by `User=` and `Group=` exists and has sufficient permissions - Check whether the paths in `ExecStart=` are correct and the files are executable - If the service depends on a mounted disk, confirm that the mount is complete at boot time (add `RequiresMountsFor=`) ### 5. Environment variable issues Services started by systemd do not inherit the environment variables from your shell. If the service runs fine manually but fails at boot, it is often an environment variable problem. You can add: ```ini [Service] Environment="VAR=value" EnvironmentFile=/etc/your-service/env ``` ## 4. Other troubleshooting tips - **Check all failed units**: ```bash systemctl --failed ``` - **Check the full boot logs**: ```bash journalctl -b ``` - **Check for logs being lost**: if `journalctl` shows no historical logs, confirm that persistent logging is enabled: ```bash sudo mkdir -p /var/log/journal sudo systemctl restart systemd-journald ``` - **Manually run the ExecStart command**: switch to the corresponding user and run the command from `ExecStart=` directly to see the actual error output. ## 5. Typical troubleshooting workflow 1. `systemctl status` to confirm the failure status and initial error 2. `journalctl -u <service> -b` to view detailed logs 3. Check the unit file with `systemctl cat` to confirm dependencies, restart policy, and user permissions 4. Fix the configuration, then run `daemon-reload` and restart the service to verify 5. If necessary, reboot to verify that auto-start on boot works properly

Summary

This guide explains why a service that runs fine after installation can fail to come back after a reboot, targeting FDEs working on customer servers. It covers three systemd configuration pitfalls and one evidence problem: start does not enable a unit for boot; Restart=on-failure ignores processes that exit with code 0; repeated crashes hit start-rate limits and lock the unit into failed state; and with Storage=auto, journals are lost on reboot unless /var/log/journal exists. The author provides a recommended unit template, useful journalctl flags (-u, -b, -f), a pre-handover checklist, and advice to include a runbook when handing machines to customers.

Key points

  • Use systemctl enable --now so the service both starts now and survives reboots.
  • Restart=on-failure won't restart processes exiting with code 0; fix exit codes in code.
  • Start-rate limits (e.g., 2 failures in 30s) put crash-looping units into failed state.
  • Without /var/log/journal, journald keeps logs only in memory, lost on reboot.
  • Reboot a staging machine and test recovery before leaving, and hand over a runbook.

The problem usually lies in three lines of systemd configuration, and the evidence may vanish along with the reboot.

Key Takeaways

  • start only makes the service run now; enable is what makes it come back after every reboot
  • Restart=on-failure cannot save a process that exits with code 0 after an error, and repeated crashes will also trigger the start rate limit
  • Under Storage=auto, a machine without a /var/log/journal directory loses all its logs on every reboot

You finish installing the service on the customer's server, type

systemctl start

, see

active (running)

, send the "done" email, and leave. Over the weekend, the customer's ops team patches the OS and reboots the machine. Monday morning, the service isn't running, and

journalctl

contains not a single line explaining what happened.

For a Forward Deployed Engineer (FDE), incidents like this are especially painful. The server isn't yours to manage, no one is on call overnight, and what the customer remembers isn't the model's accuracy but "the vendor's system keeps going down."

There are three easily overlooked causes, all in the systemd configuration. A fourth cause makes the first three hard to diagnose: the logs were never persisted at all.

start and enable are two different things

systemctl

The documentation is explicit: enable and start are independent of each other. A unit can be enabled but not running, or running but never enabled.

systemctl start

only makes the service run now; after the next reboot, systemd has no idea it should bring it back up.

Conversely,

systemctl enable

doesn't run the service either. It only creates symlinks based on the unit's

[Install]

section, and the documentation also states that it does not start the unit at the same time.

WantedBy=multi-user.target

This line makes the target have a

Wants=

-type dependency on your service. The direct consequence: a unit without an

[Install]

section cannot be enabled.

So the command you should type during installation is

systemctl enable --now app.service

: it creates the links for the next boot and immediately runs the service. Then verify with

systemctl is-enabled app

instead of just looking at

status

。

Restart= may not work the way you think

The second cause is the service dying mid-run with nothing to bring it back up. Restart= is off by default,

systemd.service

and the documentation recommends

on-failure

。

Red Hat's guide on service self-healing also treats

on-failure

as the strategy covering the most crash scenarios, including abnormal signals and non-zero exit codes.

But there's a trap here.

on-failure

only restarts when the exit code is non-zero, or when the process exits due to a signal or timeout. Imagine a Python worker that catches all exceptions, logs a "database connection lost" message, and then calls

sys.exit(0)

. From systemd's perspective, this is a clean exit, so the service just stays down.

Restart=always

restarts regardless of whether the exit was clean. The better approach is still to change the code so errors return a non-zero exit code, because under

on-failure

, exit code 0 means the work is done, not that it failed. Only use

always

。

When systemd gives up

The third cause is more subtle. Every restart is subject to the unit's start rate limit, and

RestartSec

has a default delay of only 100ms. A service that crashes on startup (say, due to a bad config file) will quickly exhaust its allowed number of starts.

systemd.unit

The documentation states that once a unit exceeds the burst number of starts within a time interval, it is no longer allowed to start. Red Hat's example configures the service so that two failed restarts within 30 seconds put it into a failed state. At that point

Restart=

no longer has any effect: systemd has stopped trying.

This mechanism can also be used deliberately. For a service deployed at a customer site, a reasonable unit looks like this:

[Unit]
Description=客户推理 worker
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=30
StartLimitBurst=2

[Service]
ExecStart=/opt/app/bin/worker
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
RestartSec=5

This gives transient errors (like a slow-starting database) time to recover on their own. The burst limit makes permanent errors surface as a clear failed state instead of falling into an endless crash loop.

The evidence disappears with the reboot

Back to Monday morning. You type

journalctl -u app -b -1

hoping to see the logs from the service's previous boot, and find nothing. According to the

journald.conf

documentation, under

Storage=auto

, the journal is only written to disk if the

/var/log/journal

directory exists; otherwise the logs are kept in memory only.

Red Hat warns of exactly this consequence: after a reboot the records are deleted, leaving no historical data to analyze. The fix is to create the storage directory and enable persistent mode:

sudo mkdir -p /var/log/journal
# 在 /etc/systemd/journald.conf 的 [Journal] 段中设置
# Storage=persistent
sudo systemctl restart systemd-journald

Once logs are persistent, three parameters are commonly used for troubleshooting:

-u

filters by a single unit,

-b

limits output to a specific boot, and

-f

follows the output in real time as you restart the service.

Checks to do before you leave

Don't wait for an incident. Each row of the table below is a question you should be able to answer before sending the "done" email.

SymptomLikely causeCheck command
Not running after rebootNot enabled, or missing [Install]systemctl is-enabled app
Dies mid-run and doesn't recoverMissing Restart=, or exits with code 0systemctl status app to see the exit code
Enters failed state after a few attemptsStart rate limit triggeredjournalctl -u app -b
No logs from the previous bootJournal kept in memory onlyls /var/log/journal

The most reliable test is still to personally reboot the customer's staging machine while you're on site, then manually kill the process and see whether it recovers. Those five minutes are far cheaper than a phone call on Monday morning.

Common mistakes

One common mistake is setting

Restart=always

on a process with a broken configuration, then being surprised to find it locked in a failed state seconds later. Another is testing only with

start

and never actually rebooting.

The last mistake is more about people: handing the machine over to the customer without a runbook. The handover should include the unit name, the

journalctl

commands to run, and what the failed state means, so the customer's on-call engineer doesn't have to call you.

Turning this skill into an advantage

In an FDE interview, explaining clearly how a service died after a reboot, how you diagnosed it with

journalctl -u ... -b -1

, and how you fixed the unit is far more convincing than a vague line in a skills list.

When writing it on your resume, frame it as an achievement: standardized unit files and persistent journals for customer-site deployments, with a handover runbook included.

This week's exercise: spin up a VM, install a worker that deliberately exits with code 0 on error, install the unit using the template above, and reboot. If you can explain why it didn't recover and point to the log line that proves it, the next time you're on site with a customer, you'll know what to check before you leave.
