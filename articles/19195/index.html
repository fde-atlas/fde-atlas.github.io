How to Write a System Cutover Process and Rollback Plan

Original title: 系统割接（Cutover）流程与回滚方案怎么写

FDE Times · 2026-10-09 · 6 min read

Summary

This guide explains how to write a cutover plan and rollback strategy for system migrations, drawing on Microsoft Dynamics 365 guidance, AWS Prescriptive Guidance, Stripe's online migration writeup, and DualEntry's runbook advice. Its core argument: cutover is a fixed sequence—freeze writes, take a final backup, sync, switch routing, test—not a single button. The final backup doubles as the rollback source and must be restore-tested beforehand. Rollback is simple only before the new system takes real transactions; after that, teams must pick among fail-forward, dual writes, or backup restore. Every plan needs a designated go/no-go decision maker, a fixed time window, and repeated rehearsals. It includes a sample runbook and five common mistakes.

Key points

  • Cutover is a fixed sequence: freeze, backup, sync, switch, test.
  • The final backup is also the rollback source; test restores beforehand.
  • Once real transactions arrive, rollback requires a pre-chosen data strategy.
  • Plans need a named decision maker, time window, and rehearsals.
  • Never declare go-live until every reconciliation check passes.

Key Takeaways

  • Cutover is a fixed sequence, not a button; the final backup is also the data source for rollback.
  • Rollback is only simple when the new system has not yet received real data. Once new transactions come in, you need a way to write that data back to the old system.
  • Every plan needs a clearly designated rollback decision-maker, a fixed time window, and multiple rehearsals.

Picture this scenario: it's Friday at 10 p.m., the customer's old order system is still running, and the data pipeline you spent three months building is ready. The most important question that night has nothing to do with code: if something goes wrong at 1 a.m., who decides to roll back, and with which data?

That night is called the cutover. Microsoft's Dynamics 365 implementation guide defines it as the process of migrating from the old system to the new one, the final step before go-live; an ERP glossary calls it a series of tightly orchestrated activities.

For a Forward Deployed Engineer (FDE), demos show the customer what the system can do; cutover lets the customer judge whether they can trust you to run it.

What cutover actually means: a sequence, not a button

Microsoft notes that during cutover, neither the old nor the new system is available, and the window usually does not exceed 48 hours, which is why it is often called a "cutover weekend." With such a short window, the order of work must be clear.

AWS Prescriptive Guidance lays out the sequence: freeze writes to the old system, take the final backup, perform the final data sync, switch routing, then test. The freeze must come first, ensuring the old system stops receiving new transactions during replication; otherwise the final sync will silently miss a few orders.

The final backup is not just an archive. AWS explicitly states that this backup can also be used for emergency rollback. The practical lesson: record the backup time precisely, and run a restore test before cutover night to make sure it actually works when you need it.

Next, you must choose between a one-time switchover and a phased (canary) switchover. AWS notes that the phased approach is more complex and takes longer, but usually has shorter downtime and faster rollback, so critical production systems often prefer it.

If the customer has thousands of users, you can first migrate one branch office or 5% of traffic, then expand gradually.

Parallel run: let machines compare first, then decide to trust

To validate a new system before trusting it, one approach is to have it process real traffic alongside the old system. GitHub's Scientist library does this at the code level: on each call, both branches run in random order and their results are compared, while the caller still receives the old branch's result.

On the data side, Stripe has described a four-step online migration process, whose first step is dual-writing to both the old and new tables to keep them in sync.

If you are replacing a set of order classification rules with a new model, this pattern applies directly: run the model in shadow mode, log every result that disagrees with the old rules, and review each one before switchover day.

Parallel runs have limits, though. DualEntry's runbook guidance for accounting systems argues that manually running two systems in parallel for a full month is usually the wrong decision: duplicate entry doubles the workload, and the second copy is the most prone to drift.

A rule worth remembering: letting machines run in parallel with automatic comparison is fine; asking the customer's staff to enter all data twice "just to be safe" is not. Once you have enough confidence, switch decisively.

Rollback is only simple before new data comes in

This is where many plans have a hole. AWS points out that once the new system receives real transactions after cutover, rollback becomes far more complex, and lists three options: fail-forward, dual-write (the application must be able to write to both the old and new databases), or backup restore. The longer the new system runs on real data, the harder the rollback.

AWS believes a rollback plan needs trigger checkpoints, a data handling strategy, and a designated contact who decides between fail-forward and rollback. Microsoft likewise requires deciding in advance who makes the final go/no-go call.

An article on the AWS blog adds a timebox rule: if, within the agreed window, the team cannot clearly articulate what the problem is and how to fix it, roll back.

AWS requires the rollback process to be written directly into the cutover plan, alongside the runbook and rehearsals. Microsoft recommends running multiple simulated cutovers, as close to real conditions as possible, until you are confident everything works smoothly.

Sample go-live night runbook

Imagine a distributor migrating order intake to the new system you are deploying. Based on AWS's sequence, a streamlined runbook would look roughly like this:

TimeTaskOwnerDecision point
22:00Freeze writes to the old systemCustomer DBAConfirm no new orders are coming in
22:15Final backup, record timestampCustomer DBABackup restore test succeeded
22:45Final data syncFDERecord counts match on both sides
23:30Switch routing to the new systemDevOpsFrom this moment the new system receives real orders
23:45Testing and reconciliationFDE + business teamTime limit 60 minutes; roll back when time is up
00:45go/no-go decisionCustomer project leadFail-forward or roll back

The last column matters most. Suppose the old system recorded 12,480 orders that day, but the new system counted only 12,477. Those three missing orders are a trigger checkpoint: either find the cause within the agreed window, or roll back.

But roll back with what? From the routing switch at 23:30 onward, the new system may have already received real orders, which are not in the 22:15 backup.

Restoring only the backup would lose all orders that came in after 23:30, so the plan must choose one of the three data strategies above in advance — for example, dual-writing back to the old system throughout the testing window.

One rule worth writing into every runbook: do not declare go-live until every item on the reconciliation checklist has passed. In the example above, the checklist could include matching order counts, matching total order amounts, and 50 randomly sampled records being identical in both systems.

Five mistakes that drag go-live night until dawn

The first is very common: five engineers staring at the same mismatched number, each wanting ten more minutes to try another fix, and the time limit becomes meaningless.

The second is a rollback plan that was written but never rehearsed, only to reveal when actually needed that the restore takes three hours instead of thirty minutes. Another is forgetting that once routing is switched, the new system is already receiving real data, while the rollback plan still assumes nothing has happened.

The last two are people problems: having the customer's staff enter data in parallel; and declaring go-live before reconciliation is complete simply because everyone is tired.

If you are preparing to move into an FDE role, watch for phrases like "migration," "go-live support," and "deployment ownership" in job descriptions. A single line on your resume — "wrote and coordinated the cutover runbook, rehearsed rollback in staging, went live with zero data loss" — impresses hiring managers more than listing any framework.

Frequently asked questions about cutover

How long does a cutover take? According to Microsoft, the cutover window usually does not exceed 48 hours, which is why it is often called a "cutover weekend." During this period, neither the old nor the new system is available, and the customer's users need to be notified in advance.

What's the difference between cutover and go-live? Cutover is the final step before go-live: the handover from the old system to the new one. Go-live is the moment, after the go/no-go decision, when the new system officially starts serving users.

Big-bang switch or phased switch? AWS notes that a phased approach is more complex but usually means shorter downtime and faster rollback. For critical production systems, it is generally the safer choice.

Who makes the go/no-go decision? Microsoft recommends deciding in advance who will make the final go/no-go call, while AWS requires a designated contact to decide between forward fix and rollback. In the runbook example above, both roles are held by the customer project lead.

Customers may forget which model you used, but they will remember whether, on go-live night, anyone could answer "what if something goes wrong?"
