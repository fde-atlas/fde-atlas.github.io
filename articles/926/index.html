In May 2026, a Douyin video made the term "FDE (Forward Deployed Engineer)" go completely viral. No coding, a million-yuan annual salary, no algorithm expertise required—these labels got countless programmers excited. But what exactly is an FDE? A real opportunity or old wine in a new bottle? After intensively studying 30+ job descriptions and interviewing for 5 types of large model roles, this article's author gives you an unvarnished answer.

On May 18, 2026, Sina Finance published a report: "This Role Is Being Made Hot by AI! Headcount Up 7x in One Year, Salaries Breaking One Million".

The data is real:

  • At leading overseas AI companies like OpenAI and Anthropic, FDE roles pay $170,000-200,000 per year (about 1.15-1.36 million RMB)
  • At domestic giants like Alibaba Cloud and Tencent Cloud, FDE roles pay 35-55K · 13 months' salary (Hangzhou, 5-10 years of experience)
  • In one year, the number of positions surged 7x

But the claim on Douyin that it's "no coding, million-yuan salary" deserves a question mark.

The truth is: FDEs do write code—they just don't "develop code from scratch." Your code volume decreases, but system debugging, script writing, and environment configuration are all still there. Those "no coding" job descriptions mostly mean you don't need to do model training and inference like an algorithm engineer.

FDE (Forward Deployed Engineer) = the person who "installs" large models into customer environments and makes them actually work.

A cooking analogy (this analogy comes from the interview summary by CSDN blogger libaiup, and I think it explains things very clearly):

RoleCooking analogyCore output
Algorithm EngineerDeveloping recipesBetter models
Application EngineerCooking the dish following the recipeWorking AI applications
Solutions ArchitectCustomizing the menu based on diners' tastesSolution documents + Demo
Forward Deployed EngineerCarrying the dish to the private room and seasoning it on the spot based on customer feedbackA customer environment that actually works

The FDE is the technical role closest to the customer. They don't just design solutions—they also work on-site at the customer's location, getting things running with their own hands:

  • Model deployment breaks in the customer environment → they troubleshoot it
  • Customer says the results aren't good → they tune it
  • Customer says requirements changed → they revise the solution

5. Forward Deployed Engineer (far right)

  • Day-to-day: on-site deployment, tuning, troubleshooting, customer training
  • Core: making models actually run in customer environments
  • Interviews: they ask about tech, about scenarios, and about customer communication

# test_deployment.py - 部署验证脚本（增强版）
import requests
import time
import concurrent.futures
import sys

API_BASE = "http://localhost:8000/v1"
MODEL_NAME = "Qwen/Qwen3-32B"

# 配置
TIMEOUT = 30  # 单次请求超时（秒）
CONCURRENCY = 10  # 并发数
TEST_PROMPTS = [
    "你好，介绍一下自己",
    "用Python写一个快速排序",
    "解释一下什么是大模型",
    "写一首关于春天的诗",
    "1+1等于几？"
]

def test_chat(prompt, request_id=0):
    """单次请求测试，带超时和错误处理"""
    try:
        start = time.time()
        response = requests.post(
            f"{API_BASE}/chat/completions",
            json={
                "model": MODEL_NAME,
                "messages": [{"role": "user", "content": prompt}],
                "max_tokens": 200,
                "temperature": 0.7
            },
            timeout=TIMEOUT
        )
        elapsed = time.time() - start
        
        if response.status_code != 200:
            return {"id": request_id, "success": False, "error": f"HTTP {response.status_code}: {response.text[:200]}"}
        
        result = response.json()
        completion_tokens = result.get('usage', {}).get('completion_tokens', 0)
        
        return {
            "id": request_id,
            "success": True,
            "elapsed": elapsed,
            "tokens": completion_tokens,
            "tps": completion_tokens / elapsed if elapsed > 0 else 0,
            "content": result['choices'][0]['message']['content'][:100]  # 只打印前100字符
        }
    except requests.exceptions.Timeout:
        return {"id": request_id, "success": False, "error": f"Timeout after {TIMEOUT}s"}
    except Exception as e:
        return {"id": request_id, "success": False, "error": str(e)}

def test_concurrent():
    """并发压力测试"""
    print(f"\n=== 并发测试（{CONCURRENCY} 并发）===")
    
    with concurrent.futures.ThreadPoolExecutor(max_workers=CONCURRENCY) as executor:
        futures = [
            executor.submit(test_chat, TEST_PROMPTS[i % len(TEST_PROMPTS)], i)
            for i in range(CONCURRENCY)
        ]
        
        results = [f.result() for f in concurrent.futures.as_completed(futures)]
    
    # 统计结果
    success = [r for r in results if r['success']]
    failed = [r for r in results if not r['success']]
    
    print(f"成功: {len(success)}/{CONCURRENCY}")
    if failed:
        print(f"失败: {len(failed)}")
        for f in failed[:3]:  # 只打印前3个失败原因
            print(f"  - {f['error']}")
    
    if success:
        avg_tps = sum(r['tps'] for r in success) / len(success)
        total_tokens = sum(r['tokens'] for r in success)
        print(f"平均TPS: {avg_tps:.1f} token/s")
        print(f"总生成Token: {total_tokens}")

def test_health():
    """健康检查"""
    try:
        r = requests.get(f"{API_BASE}/models", timeout=5)
        if r.status_code == 200:
            print("✅ 服务健康")
            return True
        else:
            print(f"❌ 健康检查失败: HTTP {r.status_code}")
            return False
    except Exception as e:
        print(f"❌ 无法连接到服务: {e}")
        return False

if __name__ == "__main__":
    print("=== vLLM 部署验证脚本 ===")
    
    # 1. 健康检查
    if not test_health():
        sys.exit(1)
    
    # 2. 单次请求测试
    print("\n=== 单次请求测试 ===")
    result = test_chat(TEST_PROMPTS[0])
    if result['success']:
        print(f"✅ 请求成功")
        print(f"耗时: {result['elapsed']:.2f}s")
        print(f"TPS: {result['tps']:.1f} token/s")
        print(f"回复预览: {result['content']}...")
    else:
        print(f"❌ 请求失败: {result['error']}")
        sys.exit(1)
    
    # 3. 并发测试
    test_concurrent()
    
    print("\n=== 测试完成 ===")

Real-world pitfall experiences (feedback from multiple FDEs):

Case 1: GPU driver version incompatibility (a banking customer)

  • Customer environment: Tesla T4, driver version 470.x (CUDA 11.4)
  • Problem: vLLM 0.4.0+ requires CUDA 12.1+, driver at least 520.x
  • Error: CUDA error: no kernel image is available for execution
  • Solution: Upgrade the driver to 535.x, but the customer's security approval took 2 weeks
  • Lesson: Before going on-site, you must first use nvidia-smi to confirm the driver version, and write it into the plan

Case 2: Unable to download models in an intranet environment (a government cloud)

  • Customer environment: Fully isolated intranet, no access to HuggingFace or ModelScope
  • Problem: The 32B model file is about 60GB, and USB copying is prohibited by security policy
  • Solution: Download in advance with huggingface-cli download to a portable drive, then transfer on the customer side with scp
  • Lesson: Model files must be prepared offline in advance; don't use git clone (too slow)

Case 3: Containers unable to access the GPU (an insurance customer)

  • Customer environment: K8s cluster, Docker installed but nvidia-container-runtime not configured
  • Error: docker run --gpus all fails with Unknown runtime specified nvidia
  • Solution: Configure /etc/docker/daemon.json, adding "default-runtime": "nvidia"
  • Verification command: docker run --rm nvidia/cuda:12.1.0-base-ubuntu22.04 nvidia-smi
  • Lesson: The first thing to do on-site — run nvidia-smi and docker info | grep -i runtime

The following is compiled from the interview notes of CSDN blogger libaiup (March 2026):

Technical questions (with key points for reference answers):

Q1: What is the principle behind vLLM's PagedAttention? How does it differ from traditional KVCache management?

  • Traditional approach: Each request's KVCache is pre-allocated as a fixed-size contiguous memory block, causing memory fragmentation and waste (similar to early OS memory management)
  • PagedAttention: Splits the KVCache into fixed-size "pages" (default 16 tokens), allocated on demand, similar to the OS's virtual memory paging mechanism
  • Effect: Memory utilization improves from ~60% to ~90%, and concurrency increases 2-4x with the same GPU memory
  • Bonus answer for interviews: Mention vLLM's Continuous Batching — pages are released immediately when a request completes and reused by new requests, without waiting for all requests in the batch to finish

Q2: After quantizing a model to INT8, accuracy drops noticeably. How do you troubleshoot?

  • Step 1: Run standard benchmarks (MMLU, C-Eval) with lm-evaluation-harness, comparing FP16 and INT8 scores
  • Step 2: Check which layers degrade the most — use per-layer sensitivity analysis with awq or gptq
  • Step 3: If it's critical layers (usually the first few layers plus attention layers), switch to mixed precision (keep FP16 for the problematic layers)
  • Practical experience: W8A8 (quantizing both weights and activations) has higher accuracy than W4A16 (quantizing weights only), but inference is 20% slower

Q3: Deploying a 70B model on 4 A100s — how do you maximize throughput?

  • Parallelism strategy: Tensor Parallel = 4 (each GPU holds 1/4 of the model parameters)
  • Batching: Enable Continuous Batching (--enable-chunked-prefill), set max-num-seqs to 256
  • Quantization: Use AWQ INT4 quantization; 70B drops from 140GB to 35GB, allowing one more replica
  • KV Cache: Set --k-cache-dtype fp8 (store KV in FP8, saving 50% of GPU memory)
  • Expected throughput: 4×A100 40GB + AWQ INT4, about 2500 tokens/s (32 concurrent users)

Scenario-based questions (unique to FDEs, with answer strategies):

Q4: The model is deployed in the customer's private environment, but the GPU driver and CUDA version are incompatible with your inference framework. The customer is pressing hard — what do you do?

  • 答题思路（STAR法则）：
    • Situation: The customer environment is restricted; drivers cannot be upgraded freely (requires security approval)
    • Action: ① First confirm the exact versions with nvidia-smi and nvcc --version; ② Check vLLM's official CUDA version compatibility table; ③ If truly incompatible, downgrade vLLM to an older version that supports that CUDA version; ④ Simultaneously go through the customer's security approval process to request a driver upgrade (parallel tracks)
    • Result: First downgrade the framework to get the service running, then upgrade the framework after the driver upgrade (2-4 weeks)
  • Bonus answer: Clearly document the environment requirements in the plan in advance, and have the customer prepare before you go on-site

Q5: After two weeks on-site, you find the customer's actual scenario is completely different from your assumptions when designing the solution. Your boss is pushing for delivery, and the customer is pushing for results. What do you do?

  • Answer strategy: First pause your current work, reconfirm requirements with the customer (leaving an email trail), then report the actual situation to your boss and request a change to the plan. Don't stubbornly proceed with the original plan — if the customer is dissatisfied after delivery, the FDE takes the blame.
  • Real-world experience: There's no standard answer to this question; it tests your communication skills and risk management awareness under pressure

Q6: The customer says your model performs worse than competitors', but you believe the model itself is fine and the issue may be the customer's poor prompt engineering. How do you communicate with the customer?

  • 答题思路（关键：不要直接说"是你的问题"）：
    • First acknowledge the issue: "Let's look at the results together and optimize until you're satisfied"
    • Let the data speak: Run a comparison test, executing the same prompts in both our demo environment and the customer's environment
    • If it really is a prompt issue: Give the customer a "Prompt Engineering Best Practices" document and help them improve their prompts
    • If it's a model issue: Be honest, and request a model change or fine-tuning
  • Core FDE capability: Technical skills + customer success mindset — not blame-shifting

Note the third question — it tests communication skills, not technical skills. FDEs do a lot of customer communication work; people with strong technical skills but poor expression struggle in this role.

If you're aiming for FDE, I recommend learning in this order. Note: this path is summarized from the real growth trajectories of multiple FDEs, not book theory.

1. Learn to deploy open-source models with vLLM

  • Deploy Qwen3 and DeepSeek-V3 locally (using the vllm serve command)
  • Understand inference optimization: Continuous Batching, PagedAttention, Tensor Parallel
  • Practical tip: Don't just test with curl; write a Python script for concurrency testing (see the enhanced test_deployment.py in Section 5 of this article)
  • Common mistake: Many people ignore the --max-model-len parameter, which causes long-text generation to fail

2. Learn to containerize model services with Docker

  • Write a Dockerfile to package the model service into an image
  • Learn to orchestrate multiple services with docker-compose (model service + Redis cache + frontend)
  • Practical tip: Simulate a "customer environment" locally—network outage, rate limiting, GPU occupied—to practice troubleshooting skills

1. Kubernetes basics

  • Deploy a model service to a K8s cluster (practice locally with minikube)
  • Configure GPU resource scheduling (nvidia.com/gpu resource)
  • Learn health checks and autoscaling (HPA)
  • Key point: K8s resources.requests must equal limits (GPU resources don't support overcommitment), otherwise scheduling will fail

2. Model quantization and optimization

  • GPTQ, AWQ, INT8 quantization (using the auto-gptq and auto-awq libraries)
  • Deploy quantized models with llama.cpp (suitable for edge devices)
  • Practical tip: After quantization, always run benchmarks—don't just look at "reduced GPU memory usage"; watch whether perplexity rises noticeably

1. Build a complete demo system

  • Frontend: a simple chat interface (with Streamlit or Gradio, done in 30 minutes)
  • Backend: FastAPI + vLLM
  • Deployment: one-click startup with Docker Compose
  • Key point: The demo must be "presentable"—not just curl commands; customers can't read terminal output

2. Simulate customer scenarios (this is the core FDE competency)

  • Scenario 1: Intranet environment with no public internet access → Learn offline model downloads (huggingface-cli download --local-dir)
  • Scenario 2: Limited GPU resources requiring multi-tenant sharing → Learn to tune vLLM's --gpu-memory-utilization parameter
  • Scenario 3: Customer has data security compliance requirements → Learn to configure access control for model services (API keys, IP whitelists)

3. Improve communication skills (a required course for FDEs)

  • FDE = 50% technical + 50% communication. No matter how strong your technical skills, you can't be a good FDE without communicating well with customers.
  • 练习方法： 把自己的技术决策"翻译"成业务语言。比如：
    • ❌ "I used Tensor Parallelism" → ✅ "I spread the model across 4 GPUs, tripling inference speed"
    • ❌ "PagedAttention optimized the KV Cache" → ✅ "With the same GPU memory, I can serve more users simultaneously, saving you hardware costs"

A Sina Finance report mentioned a key figure: the number of FDE positions surged 7x in one year.

There are two structural reasons behind this:

Reason 1: Large models have gone from "usable" to "good to use," but no one is handling the last mile

  • Algorithm engineers have made the models better
  • Application engineers have built the demos
  • But actually deploying models into enterprise intranets, adapting them to customer businesses, and tuning them to customer satisfaction—nobody is doing this, or doing it well

Reason 2: Government and enterprise customers have strong demand for private deployment

  • Data cannot leave the intranet (finance, government, healthcare)
  • Private deployment is mandatory; public cloud APIs cannot be used
  • But private deployment has a high technical barrier and requires professionals

So the essence of FDE is: the "technical implementation expert" for the last mile of large model deployment.

The demand is real, not hype. But note: the skill barrier for FDEs isn't as high as for algorithm engineers; in 5 years, if AI tools replace them (as automated deployment tools mature), competition will intensify.

  • Extroverted personality, enjoys interacting with people
  • Can accept business travel and on-site work (may need to stay at customer sites for weeks)
  • Technical breadth matters more than depth (need to know a bit of everything)
  • Strong problem-solving ability (problems in customer environments are endlessly varied)
  • Purely introverted; only likes writing code, not communicating
  • Pursues extreme technical depth (FDE doesn't require you to derive Transformer formulas)
  • Cannot accept business travel

Worth pursuing, but with conditions:

  • If you already have 2-3 years of AI application development experience → Pursuing FDE is a great career upgrade with significant salary growth
  • If you're a complete beginner → Build a solid foundation in model deployment first; don't be misled by labels like "no coding needed, million-yuan salary"
  • If you prefer pure R&D → FDE may not suit you; customer communication will drain a lot of your energy

One last honest word: The FDE role has indeed been made popular by AI, and the demand is real. But it's not a "lie back and earn" job—the technical breadth, communication skills, and on-site problem-solving abilities it requires are no less demanding than pure R&D roles.
