Summary

This Japanese article from FDE総研 explains how forward deployed engineers (FDEs) implement MCP (Model Context Protocol) in practice. MCP, released by Anthropic in November 2024 and since supported by OpenAI, Google, and Microsoft, is an open standard connecting AI agents to tools and data, reducing the N×M integration problem. The author warns against converting API endpoints one-to-one into tools, advocating business-unit-level tool design and a five-step rollout: use-case selection, data inventory, tool design, evaluation, and production deployment, starting with read-only, low-risk use cases. It covers four security risks—prompt injection, tool poisoning, excessive permissions, and token mishandling—and recommends least privilege, human approval, and involving security teams early.

Key points

  • MCP is an Anthropic open standard (Nov 2024) now backed by OpenAI, Google, and Microsoft.
  • A five-step rollout: use-case selection, data inventory, tool design, evaluation, production deployment.
  • Start with read-only, low-risk use cases; defer write operations to later phases.
  • Design few tools with clear descriptions and narrow permissions, grouped by business task, not API endpoint.
  • Key risks: prompt injection, tool poisoning, excessive permissions, token mishandling; use least privilege and human approval.

What is MCP, and why are enterprises adopting it?

MCP is an open standard that connects AI agents with tools and data inside and outside the company. Because it reduces the development cost of individual integrations, enterprise adoption is spreading.

MCP (Model Context Protocol) is a protocol released by Anthropic in November 2024. It standardizes how LLM applications access external context such as files, databases, SaaS, and internal APIs. After its release, major AI vendors including OpenAI, Google, and Microsoft announced support. As a result, MCP is now treated as an industry-wide common interface rather than a vendor-specific proprietary specification.

What is the basic structure of MCP?

MCP consists of three layers: host, client, and server. Communication uses JSON-RPC 2.0.

ComponentRoleExamples
HostThe AI application the user operatesClaude Desktop, IDEs, in-house agent platforms
ClientA component inside the host that connects one-to-one with a serverConnection units generated by the host
ServerA program that exposes tools and dataMCP servers for GitHub, Slack, internal databases

The server exposes three main types of functionality.

  • Tools: Functions the model can call (e.g., creating tickets, running SQL)
  • Resources: Data the model can reference (files, documents, records)
  • Prompts: Reusable, standardized instruction templates

There are two transport methods. The basics are stdio for local operation and Streamable HTTP for remote operation.

Why are enterprises paying attention to MCP?

The biggest reason enterprises are interested is that MCP frees AI-tool integration from the "N×M problem." An integration built once can be reused across multiple AI applications.

Without MCP, if there are N AI apps and M tools, up to N×M individual integrations are required. With MCP compliance, the tool side only needs to provide one MCP server, and it can be used by multiple supporting hosts. From my experience in the field as an FDE, there are many requests like "we want to use the same internal data in both Copilot and our own agent." MCP makes it easier to meet such needs, which makes it easy to explain the motivation for adopting it.

How does MCP differ from traditional API integration?

MCP does not replace APIs. It adds a layer in front of APIs that AI can understand and call on its own.

REST APIs and GraphQL assume that human developers read documentation and implement integrations. With MCP, the server tells the client the names, descriptions, and input schemas of its tools. The model reads those descriptions and decides which tool to use and when.

Where are the functional differences?

The biggest differences are that functionality can be discovered dynamically and that it is designed with the model calling it in mind. Authentication and execution mechanisms themselves continue to use APIs.

AspectTraditional API integrationMCP
Who makes the callCode written by developersLLM (via the host)
Discovering functionalityStatically implemented after reading documentationDynamically retrieved via tools/list, etc.
Unit of interfaceEndpointsTools / Resources / Prompts
ReusabilityIndividually implemented per integration targetShared across compliant hosts
AuthorizationMethod varies per APIRemote servers follow an OAuth 2.1-based specification
Main concernAccurate requests and responsesDescriptions and granularity that prevent model misuse

Should APIs simply be converted into MCP?

Converting API endpoints one-to-one into MCP tools usually does not work well. Tools need to be redesigned at the level of business tasks.

A common failure seen in the field is exposing dozens of endpoints as tools as-is. When there are too many tools, the model is more likely to choose the wrong one. Long descriptions consume context, degrading both accuracy and cost. For example, grouping tools at the level of what users actually want to do, such as "search for customers" or "return a summary of a customer's contract status," tends to be more stable.

How can MCP adoption be rolled out reliably?

To proceed reliably, narrow down to a single use case. From there, a five-step approach that gradually expands from read-only access is effective.

Technically, MCP is easy to start with, but many initiatives stall at "we stood up a server for now." From an FDE's perspective, I recommend proceeding in an order that leads to business outcomes.

What are the five steps for adopting MCP?

The five steps are: task selection → data inventory → tool design → validation → production rollout. It is important to define completion criteria at the end of each step.

StepContentCompletion criteria guideline
1. Use case selectionPick one task that is frequent and where AI can support decision-makingTarget task, users, and success metrics are defined
2. Data and system inventoryIdentify required data sources, permissions, and existing APIsAuthentication method and owner are known for each connection target
3. Tool Design and ImplementationDesign Tools/Resources per business process and implement the serverRead-oriented tools work locally
4. Evaluation and ValidationVerify accuracy, misuse, and failure behavior with a representative question setThe evaluation set meets the acceptance threshold
5. Production Rollout and Operations DesignSet up authorization, logging, and monitoring, then expand to target usersProcedures for operations staff and incident response are defined

How should you choose the first use case?

It is safest to start with "read-centric" processes where mistakes cause little harm. Save write-oriented processes for the second stage and beyond.

Likely candidates include internal knowledge search, summarizing inquiry histories, and preliminary research for data analysis. Conversely, operations that affect the outside world, such as ordering, money transfers, or sending messages to customers, are better kept out of the initial scope. In my experience, the best evaluation metric for the first few weeks is whether the field teams use it daily. Rather than accuracy numbers, whether it continues to be used is often the most honest indicator of whether the rollout succeeds.

What are the key points to keep in mind when designing tools?

The key design points are three: "few tools, clear descriptions, narrow permissions." A design that keeps the model from hesitating directly improves accuracy.

  • Limit the number of tools: Expose only the necessary tools on a single server
  • Write descriptions as specifications: Clearly state when to use the tool and when not to
  • Make input schemas strict: Use enums and required fields to reduce free-form input
  • Summarize outputs: Don't return large amounts of raw data; shape it to a volume the model can handle
  • Use error messages to indicate the next action: Return clues for recovery, such as "insufficient permissions, contact an administrator"

What role does an FDE play in MCP adoption?

An FDE bridges business requirements and MCP's technical design. They are the person who stays engaged until the solution takes root in the field, rather than ending at the PoC stage.

The FDE (Forward Deployed Engineer), a role popularized by Palantir, works on-site with customers and handles everything from problem discovery through implementation and adoption. MCP adoption is exactly the kind of theme where FDE strengths shine. Even though the protocol itself is simple, deciding "which processes, with which data, and with which permissions" to delegate to AI cannot be done without understanding the field.

What specific tasks does an FDE handle?

FDE work falls broadly into four areas: requirements gathering, tool design, evaluation, and internal rollout. All of them start with dialogue with the field.

AreaFDE's specific tasksPeople involved
Requirements gatheringObserve business workflows and decide the scope to delegate to AIField staff, business department heads
Tool designRestructure existing APIs and databases into business-unit MCP toolsInternal engineers, system administrators
EvaluationBuild evaluation sets from real field questions and iterate on improvementsField staff, quality control
Rollout and adoptionCreate usage guides, hold workshops, collect feedbackIT department, management

What skills are required of individual engineers?

Beyond implementation skills, what's required is "the ability to articulate business processes" and "the ability to design for security." Protocol knowledge alone is not enough.

On the technical side, the foundation is being able to implement MCP servers with the official TypeScript or Python SDKs and understanding authorization mechanisms including OAuth. However, I believe what differentiates an FDE is whether they can translate tacit field knowledge into tool descriptions and evaluation sets. Experience with MCP is an area where engineers aiming for FDE roles can easily build a portfolio that concretely demonstrates "I implemented AI in a business context."

What security and operational issues should you watch out for when adopting MCP?

The biggest risk is the combination of prompt injection and excessive permissions. A design that limits damage through least privilege and human approval is essential.

Using MCP lets the model read external data and operate external systems. While convenient, this also expands the attack surface. The MCP specification itself has come to include security best practices. Even so, much is still left to the design of the operational side.

What are the typical security risks?

The typical risks are four: injection, tool poisoning, excessive permissions, and improper token handling. Each requires different countermeasures.

RiskDescriptionMain countermeasures
Prompt injectionThe model follows instructions embedded in loaded documents or emailsInsert human approval for write operations, distinguish untrusted input
Tool poisoningA malicious server embeds malicious instructions in tool descriptionsManage allowed servers with an allowlist and verify their origin
Excessive permissionsThe server runs with administrator privileges and can perform unintended operationsLeast-privilege service accounts, per-user authorization
Improper token handlingPassing received tokens directly to downstream APIsFollow the specification and avoid token passthrough, use tokens dedicated to the target resource

The configuration to watch out for most is when a single agent combines all three of: "can read internal data," "can send externally," and "reads untrusted input." This combination easily leads to data leaks, so I recommend separating them at the design stage.

What operational issues tend to be overlooked?

Easy to overlook are server sprawl, insufficient audit logs, and keeping up with specification revisions. Operations last longer than the initial rollout.

  • Proliferation of rogue servers: If each department sets up its own MCP servers, you lose track of who is accessing which data. Consider centralizing management with an internal server registry or gateway
  • Audit logs: Without recording "whose request, which tool, with which arguments," you cannot trace the cause when an incident occurs
  • Specification revisions: The MCP specification continues to be revised with dated versions. You need to build SDK and server update plans into your operations
  • Cost and latency: Tool descriptions and large responses increase token consumption. Regular inventory reviews are effective

From hands-on experience, involving security staff at the PoC stage greatly reduces rework when moving to production. Precisely because MCP is a "plug it in and it works" technology, deciding how far to connect it is where the adopting side can show its skill. FDEs are in a position to explain that decision in both technical and business terms.
