Law Firm DMS Connector Design: Essential Skills for FDEs

Original title: 律所 DMS 连接器设计：FDE 必备技能

FDE Times · 2026-10-26 · 5 min read

Summary

Using Legora's FDE job posting as a starting point, this article argues that in law firms, connector design matters more than model choice. The core principle is that the DMS (iManage, NetDocuments, SharePoint) remains the system of record, and access is governed by DMS permissions and ethical walls. The author recommends a shared interface with per-DMS adapters, passing user identity on every call, and a six-cell permission test matrix to verify ethical walls and prevent leaks. It also lists common mistakes, like copying DMS data or skipping identity mapping.

Key points

  • Legora's FDE role requires iManage/SharePoint/NetDocuments, SSO, and reusable connectors.
  • The DMS is always the system of record; permissions and ethical walls govern access.
  • Use a shared interface with adapters so client-specific logic never leaks upward.
  • Test ethical walls with a six-cell matrix and rerun after permission changes.
  • Common failures: copying the DMS, leaking client logic into the interface, skipping identity mapping.

Key Takeaways

  • Legora's FDE job posting requires familiarity with iManage, SharePoint, or NetDocuments, SSO (SAML, OIDC), REST and webhooks, and explicitly requires writing reusable connectors.
  • First principle: the raw DMS is always the system of record. Which documents each person can retrieve is determined by DMS permissions and the firm's ethical walls.
  • The connection method may shift from APIs to MCP, but permission enforcement and the shared interface must remain unchanged.

A law firm wanted partners to be able to query matter documents stored in iManage. At the first technical meeting, hardly anyone mentioned the model. The head of IT asked only one question: if there is a wall between Attorney A and Matter X, will your system show A even a single page of Matter X?

The job starts from that question. Legora describes its Forward Deployed Engineer (FDE) role as sitting between product engineering and customer success. Engineers work alongside enterprise customers during and after deployment, writing production code to integrate Legora's platform with the customer's systems.

The job posting lists the required knowledge: document management systems such as iManage, SharePoint, or NetDocuments, SSO based on SAML and OIDC, and REST APIs and webhooks.

The posting also specifies one concrete responsibility: build and maintain connectors, automation scripts, and reusable tools so that future deployments go faster.

This skill is not unique to Legora. Any company selling software into industries with sensitive data can use it.

Who owns the documents?

In October 2026, when Legora launched its integration ecosystem, it emphasized one principle: lawyers can browse, search, and work on matter documents in Legora, but the underlying platform remains the system of record. This reads like a line written for the marketing team. In fact, it is the most important design requirement for connectors.

This principle has two consequences. First, the DMS holds the official copy of every document along with its versions, metadata, and edit history, so the connector must not create a second copy that gradually drifts from the original. Second, access permissions are decided by the DMS, not by you.

According to LawNext, in the iManage integration, what each user can retrieve is determined by iManage permissions. Artificial Lawyer also reported that a firm's existing ethical walls and security restrictions determine what Legora can access.

An ethical wall prevents lawyers from touching a matter when there is a conflict of interest. A document leaking through that wall is a serious incident, far more than an ordinary bug.

One interface, multiple adapters

Why does the job posting emphasize "reusable"? This firm uses iManage, the next one uses NetDocuments, and the one after that keeps everything in SharePoint. If you start from scratch every time, experience never accumulates.

The sensible split is: an upper layer providing a shared interface for applications to call, and a lower layer with one adapter per DMS. The illustrative code below demonstrates this design and is not Legora's code:

from typing import Protocol

class DMSConnector(Protocol):
    def search(self, user: UserIdentity, query: str,
               matter_id: str | None = None) -> list[DocRef]: ...
    def fetch(self, user: UserIdentity, doc: DocRef) -> DocContent: ...
    def handle_event(self, event: dict) -> None: ...  # webhook：文档移动、权限变更

class IManageAdapter:
    def search(self, user, query, matter_id=None):
        token = self.tokens.for_user(user)  # 使用用户自己的 token，绝不用服务账号
        return self.client.search(query, matter=matter_id, auth=token)

    def fetch(self, user, doc):
        token = self.tokens.for_user(user)
        # 每次读取时 DMS 都会再次检查权限
        return self.client.get_document(doc.id, auth=token)

    def handle_event(self, event):
        if event["type"] in ("permission_changed", "document_moved"):
            # 丢弃按旧权限计算出的结果
            self.cache.invalidate(matter_id=event["matter_id"])

The key detail is that every function takes

UserIdentity

. Every call carries the identity of the person asking, an identity that comes from SSO (SAML or OIDC), and the adapter uses that same identity to call the DMS. The DMS then filters searches and opens by that person's permissions, so you never have to reimplement access logic.

This design also pays off when the connection method changes. According to LawNext, Legora has integrated with iManage via API and plans to also connect to the iManage MCP Server.

The ecosystem announcement also mentions that iManage and NetDocuments connect via the Model Context Protocol (MCP) for knowledge management and search. As long as the connection method lives only in the adapter, you can swap the adapter without touching the interface or the permission tests.

The six-cell matrix before go-live

Ethical walls should be tested the way security is tested. Picture a scenario: two matters, three lawyers. An works on Matter 1001. Binh works on Matter 1002. Chi is a lawyer at the firm who never worked on Matter 1001 and is blocked from it by an ethical wall due to a conflict of interest.

UserSearch in Matter 1001Search in Matter 1002
AnResults returnedEmpty
BinhEmptyResults returned
Chi (walled off from 1001)Empty, even with the exact document nameEmpty

Three people times two matters gives six cells, and each cell is an automated test. The most critical cell is Chi's on Matter 1001. If the search index was built with a service account that can read everything, that cell will almost certainly return results, which means a leak.

Rerun this matrix after every permission change. Remove An from Matter 1001 in the DMS, send the webhook event to

handle_event

, then confirm that An's next search returns empty. Stale caches are most likely to fail silently here.

Owning it end to end at the customer site

Legora hands the entire technical scoping work to the FDE, from gathering requirements to designing the integration architecture. At law firms, the scoping meeting should answer four questions: which DMS is used, cloud or on-premises? Is SSO SAML or OIDC? Where are ethical walls configured? Does the DMS emit webhooks when permissions change?

The order of work after that should be: interface, adapters, identity mapping, test matrix, webhook handling, and only then the Q&A feature. Many teams do it in reverse, because the Q&A feature dazzles in demos. But a single data leak is enough to lose the contract.

The final step is often skipped: feeding what you learned back to the engineering and product teams. Legora's job posting states that the FDE works with both teams to improve integrations and the shared product.

If you find yourself writing the same permission group mapping for three customers in a row, that is a sign it belongs in the standard connector.

Mistakes that make connectors non-reusable

The most common mistake is copying the entire DMS into another store to speed up search. This violates both principles at once: the copy drifts from the system of record, and permissions are frozen at the moment of copying.

The second mistake is letting customer-specific logic seep into the shared interface, such as a field named

matter_code_format_firmB

. All differences should live in adapters or configuration files.

The third mistake is skipping identity mapping. The email in SSO and the username in the DMS do not always match. Get the mapping wrong for one person, and the test matrix becomes meaningless.

Showcasing this skill on your resume

When reading an FDE job posting, watch for phrases like "reusable connectors", specific DMS product names, SAML/OIDC, and webhooks. They signal that the job leans toward integration, not demos.

Do not just write "integrated SharePoint" on your resume. Write clearly that you built a connector, reused it across several deployments, tested permissions with a specific number of test cases, and that not a single document crossed an ethical wall. When a recruiter reads that line, they will know you have actually answered the head of IT's question.

Models will keep changing, and so will the ways we connect to them—from REST to MCP to whatever standard comes next. But the question of "who can see what" never changes. The FDE who answers it with tests rather than promises is the one who earns customer trust.
