LLM-as-a-Judge Evals: How to Calculate Agreement Rate and Recall Rate

Original title: LLM 裁判评测：一致率与召回率怎么算

FDE Times · 2026-10-24 · 5 min read

Summary

Drawing on Arize AI's forward deployed engineer practice, this guide explains how to validate LLM-as-a-judge systems before trusting them. Its central point: an 85% overall agreement rate can hide a 25% failure recall, meaning the judge misses most real faults. Using a refund-assistant example, it shows the proper sequence: build traces first, create versioned datasets, have domain experts label them, measure both agreement and failure recall for the failure types customers care about, and only then promote the judge to a release gate. For agents, both final answers and tool-call trajectories must be evaluated.

Key points

  • A judge with 85% agreement may catch only 25% of real failures.
  • Observability shows what an agent did; evals show whether it was right.
  • Validate judges against human labels before using them as release gates.
  • Score agent trajectories, not just final answers.
  • Use versioned datasets so score changes are attributable to the judge.

At Arize AI, FDEs work with customers to build systems spanning tracing to evals; the core skill is spotting a weak judge before it becomes a release gate.

Key Takeaways

  • Observability tells you what the agent did; evals tell you whether it did it right. A serious system needs both
  • Before using an LLM judge as a release gate or wiring it into dashboards, validate it with human labels, and separately measure recall on the failure types your customer cares about
  • For agents, also score the trajectory: the answer can be right while the process is wrong

The customer's AI team opens a demo of their support assistant and adds: "We manually reviewed dozens of conversations, and they all look fine." Next week they want to roll it out to all users. The question you now have to answer is no longer "does it work well," but "if something goes wrong, who will notice, and how?"

At Arize AI, this is essentially the whole job. The company's job posting for a Forward Deployed Engineer (FDE) describes the role this way: partner with customers' AI teams to design, deploy, and scale production-grade GenAI observability and evals systems. FDEs also build custom integrations and tooling to tailor the Arize platform to each customer's needs.

Even if you never work at Arize, this skill is useful. As long as you're putting LLMs into customer systems, be ready to answer that question with data, not intuition.

Observability and evals are two halves of the same loop

Observability answers "what did the agent do?" Every request is recorded as a trace, containing the prompt, retrieved documents, tool calls, and the final answer. Arize's open-source platform Phoenix builds its tracing on OpenTelemetry, with no vendor, language, or framework lock-in.

That last point matters for FDEs. Customers may use any model or agent framework; you just instrument against one universal standard instead of rewriting for every tech stack.

Evals answer "did it do it right?" You organize traces into datasets; Phoenix supports versioning these datasets for experiments, evals, and fine-tuning. In Arize AX, an experiment runs the task on every row of a dataset and scores it with an LLM judge, with each score accompanied by an explanation so you can fix the right failure type.

Example: a refund assistant and a "decent" judge

Suppose the customer is a retailer with an agent that handles refund requests. You instrument the agent, collect a week of traces, pick out 100 conversations, and save them as a dataset

refund-v1

. Two of the customer's support staff label each one by hand: 80 pass, 20 fail.

Next you write an LLM judge and run it on the same 100 rows. The judge correctly approves all 80 passing conversations, but catches only 5 of the 20 failures. The results:

人工：通过人工：失败
Judge: pass8015
Judge: fail05

Overall agreement is (80 + 5) / 100 = 85%, which looks great on a slide. But failure recall is only 5 / 20 = 25%: for every four conversations that went wrong, the judge let three through. This is exactly what Arize warns about: a judge with 85% agreement is still unusable if it misses the failures you care about.

The code to compute these two numbers is short, and you should always print them side by side:

def judge_report(human, judge):
    # human、judge：由 "pass" / "fail" 组成的列表
    n = len(human)
    agree = sum(h == j for h, j in zip(human, judge))
    fails = [j for h, j in zip(human, judge) if h == "fail"]
    caught = sum(j == "fail" for j in fails)
    return {
        "agreement": agree / n,
        "fail_recall": caught / len(fails) if fails else None,
    }

Fixing starts with the judge's explanations. After reading the 15 missed cases, you might find a common pattern: the judge only checks whether the answer is polite and policy-compliant, with no idea that the agent confirmed the refund before ever querying the order status.

A correct answer doesn't mean a correct process

The problem in this example isn't wording, it's the path. The agent said "your order has been refunded" but skipped the tool call to query the order. Arize recommends that for agents, you must evaluate both the final answer and the trajectory.

So the second version of the judge needs to see the tool call sequence in the trace, plus an explicit criterion: order status must be checked before confirming a refund. Re-run the experiment on

refund-v1

and compare failure recall against the previous version. The dataset stays unchanged, so any difference comes from the judge, not the data.

Arize recommends only using a judge to gate releases, drive dashboards, or do automatic routing after it has been validated against human labels. This order is a hard rule: building gates on an unvalidated judge automates its blind spots too.

What order should you follow at the customer's site?

Start with tracing; without traces, every discussion of quality is guesswork. Then work with the customer to pick the failure types they genuinely worry about, such as incorrect refunds, data leaks, or out-of-policy answers. That list determines which subset you measure recall on.

Next, build a versioned dataset and have the customer's people label it, ideally domain experts rather than engineers. Then write the judge, measure agreement and recall, refine it based on explanations, and only promote it to a release gate once recall reaches a level the customer can accept.

How you present results also depends on the audience. Arize's job posting requires FDEs to lead technical discussions with audiences ranging from engineers to executives. Engineers need the confusion matrix; executives need one sentence: "The judge currently catches only 5 of 20 refund failures, so it can't gate releases yet."

Mistakes that kill eval systems early

The most common mistake is reporting only an agreement number, like the 85% above. The second is changing the dataset between experiments, so nobody knows whether the score improved because of the prompt or because the data got easier. The third is scoring only the final answer for agents that call tools.

The fourth concerns how you work. Arize's FDEs run multiple projects in parallel, own everything from scoping to handoff, and help write the team's playbook. If you rebuild the process from scratch for every customer, you won't keep up, so turn the steps above into reusable templates.

How do you put this skill on your resume?

Arize's job posting asks for 2-5 years of software development experience, lower than many senior FDE roles. In exchange, candidates must have developed, deployed, and continuously improved GenAI applications in production, and be familiar with cloud and container tooling.

For a role like this, "used LLM-as-a-judge" says nothing. A stronger phrasing: "Validated a judge with 100 human labels and raised failure recall from 25% to a level sufficient to gate releases." That tells the interviewer you know how to measure the right things.

This week, take 50 traces from any LLM application you're working on, label them yourself, then have the judge score them. If the failure recall surprises you, you're seeing exactly what the customer's AI team doesn't see.
