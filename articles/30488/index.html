AWS Glue, ADF, and Dataflow Compared: How an FDE Takes Over ETL

Original title: AWS Glue、ADF、Dataflow 对比：FDE 如何接手 ETL

FDE Times · 2026-10-08 · 4 min read

Summary

This article advises forward deployed engineers (FDEs) on how to quickly understand a client's existing ETL pipelines when taking over data-related projects. It compares AWS Glue, Azure Data Factory, and Google Dataflow: Glue and ADF mapping data flows run on Spark, while Dataflow is built on Apache Beam, which unifies batch and stream processing. The author provides a platform-specific checklist for the first week—checking the Glue Data Catalog on AWS, integration runtimes on Azure, and Beam code on Google Cloud—and stresses asking Azure clients early whether they use ADF or Data Factory in Fabric, since Microsoft is steering new users toward Fabric. It also warns that crawler-inferred schemas need verification and auto-scaling does not guarantee correct logic. Recommended learning order: Spark first, then Beam, then CI/CD practices.

Key points

  • Glue and ADF data flows run on Spark; Dataflow runs on Apache Beam.
  • Ask Azure clients early whether they use ADF or Data Factory in Fabric.
  • First checks: Glue Data Catalog on AWS, integration runtime on Azure, Beam code on GCP.
  • Auto-scaling hides logic errors; crawler-inferred schemas must be verified with data owners.
  • Learn Spark first, then Beam, then practice publishing pipelines via CI/CD.

FDEs rarely start from scratch: the data an agent needs to read has long been flowing through Glue, ADF, or Dataflow, and you have to understand those pipelines within your first week.

Key takeaways

  • Both Glue and ADF data flows run on Spark managed by the service. Dataflow is based on Apache Beam, with a single model shared by batch and stream processing.
  • With Azure customers, ask early whether they use ADF or Data Factory in Microsoft Fabric, because Microsoft is steering new users toward Fabric.
  • What to open first when taking over: on AWS, the Data Catalog; on Azure, the integration runtime; on Google Cloud, the Beam code.

"Are you using Azure Data Factory, or Data Factory in Microsoft Fabric?" With customers running on Azure, this should be one of the first questions a Forward Deployed Engineer (FDE) asks.

The reason is written on Microsoft's own overview page. Microsoft still describes ADF as a managed cloud service for complex ETL, ELT, and hybrid data integration projects. But the same page calls Data Factory in Fabric the "next generation" of ADF and steers new users toward Fabric.

Behind this question lies a reality: whenever the work involves data, FDEs rarely start with a blank slate. By the time they arrive, the customer is usually already using AWS Glue, Azure Data Factory, or Google Dataflow. The data the agent or model needs to read flows precisely through those pipelines.

You don't need to become an expert in all three, but you do need to be able to read the customer's pipelines within your first week.

Three services, three sets of terminology

AWS describes Glue as a serverless data integration service for discovering, preparing, migrating, and combining data from multiple sources. At its core is the crawler, which infers schemas and writes them into the Glue Data Catalog. Glue Studio supports building transformation workflows via drag and drop, running on a serverless Apache Spark-based ETL engine.

Those who prefer writing code use Spark, Python, or Scala.

ADF has its own set of concepts: pipelines, activities, datasets, linked services, data flows, and integration runtimes. Mapping data flows run on Spark clusters that are started on demand and shut down automatically after use, so users never manage the clusters. The integration runtime is the bridge between activities and linked services; in other words, it determines where the pipeline actually runs.

Google defines Dataflow as a unified batch and stream processing service that runs at scale. Dataflow was released in June 2014, entered public beta in April 2015, and is now built on the open source project Apache Beam. As load changes, the service automatically adds or shuts down worker VMs.

One question, three places to look first

Suppose a retail chain wants an agent to answer inventory-related questions. Every night, order files land in a data lake, while the inventory table lives in a database in the office. The task is to bring these two sources together into a clean location the agent can query. The table below shows where to look first on each platform.

TransformationGlue Studio or PySpark jobsMapping data flows running on SparkBeam transforms
When it runsOn schedule, on demand, or event-triggeredOpen the pipeline, check the activity order, and ask the customer what triggers itAsk the customer how the job is started, batch or streaming

Reading across the rows, the hardest question in this example is in the second row. The integration runtime is the bridge between activities and linked services, so on Azure, checking it is the first step to confirming whether the pipeline can actually reach the office database.

Before writing any transformation, sit down with the customer's network and security teams and nail down this bridge.

Where are the limitations?

All three services hide a great deal of infrastructure, which is exactly what can make FDEs complacent. Spark starting and stopping automatically and workers auto-scaling say nothing about whether the transformation logic is correct. The schema a crawler infers from the data is ultimately just a guess; verify it with the owner of that data source.

Azure adds a strategic issue. Microsoft says existing ADF workloads can be upgraded to Fabric. So any plan to build something new on ADF should also directly ask the customer: do you plan to migrate to Fabric? Skip this step, and an upgrade may be on the table as soon as the handoff is complete.

Dataflow's difficulty lies in the programming model, not the infrastructure. Beam handles batch and stream processing with a single model, which is powerful, but people used to writing sequential scripts need time to adapt.

What to learn first

If you only have one month, learn Spark first. On Glue, ETL jobs are written directly in Spark. In ADF, Spark underlies mapping data flows and is managed by the service, so knowing Spark helps you understand how data flows run, even though you won't operate it yourself.

Next, learn enough Beam to read Dataflow pipelines. Finally, practice bringing pipelines into the release process: ADF fully supports CI/CD through Azure DevOps and GitHub, and enterprise customers will ask about it.

When reading FDE job descriptions, note which ETL services are mentioned, and use that to decide which platform to learn first. Don't write "familiar with AWS Glue" on your resume; instead, write that you read an existing pipeline, located where the schema had drifted, and shipped a fix through CI/CD.

That line shows the hiring manager the work an FDE actually does at the customer's site.

The customer's ETL tool was almost certainly chosen before you arrived. What you can control is how quickly you learn to read it.
