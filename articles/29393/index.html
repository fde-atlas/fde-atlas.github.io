What Is the Google FDE Vibe Coding Round? (How It Works and How to Prepare)

Design Gurus · 2026-11-20 · 4 min read

Summary

This article explains Google's FDE "vibe coding" round: a roughly 60-minute collaborative build from a deliberately vague spec, where the interviewer acts as a customer and changes requirements midway. It walks through a sample data-reconciliation task, an hour-by-hour strategy, and preparation advice. It stresses asking clarifying questions, building a minimal working version first, and structuring code so changes don't force rewrites. Whether AI tools are allowed is unconfirmed; candidates should ask recruiters in writing and be ready to code unaided. Common mistakes include coding before asking questions, designing for scale too early, and working in silence.

Key points

  • The round tests questioning, adaptation, and debugging, not algorithm puzzles.
  • Sample task: reconcile messy shipment records, then handle 50,000 records per minute.
  • Build the smallest working version first, with small modular functions.
  • AI tool permission is unconfirmed; assume you write every line yourself.
  • Interviewers can only record what you say out loud, so narrate your work.

The Google FDE vibe coding round is a roughly 60-minute collaborative build in which you write working code from a deliberately loose specification. The interviewer acts like a customer or teammate, leaves parts of the task undefined, and often changes a requirement partway through. It is not an algorithm puzzle. It tests how you ask questions, choose a first version, structure code that can change, and debug in front of another person. The name comes from "vibe coding," the practice of building software by describing it to an AI assistant, but public reports do not confirm that AI tools are allowed in this round.

Quick Overview

Part of the hour What happens What is evaluated
First 5 to 10 minutes You ask questions about the loose spec Clarifying the goal and the data
Next 20 minutes You build the smallest working version Practical judgment, clean structure
Middle The interviewer adds or changes a requirement Adapting code without starting over
Last 10 minutes You test, fix, and explain the next steps Debugging, communication

What the Task Looks Like

Public examples describe customer-style data problems rather than textbook problems. One representative task is to parse a messy data export, reconcile it against a second source, and then handle a sudden burst of records. Other reported variations include building a small tool from a short description, or extending existing code you did not write.

Take the reconciliation task as an example. The export might contain 2,000 shipment records with dates in three formats, duplicate ids, and missing weights. The second source is a billing table, and the customer wants a list of shipments that were billed twice or not billed at all. Halfway through, the interviewer says the export now arrives in batches of 50,000 records every minute.

How to Use the Hour

Ask before you build. Ask what the user will do with the output, what "matched" means, and what to do with a bad row. In the example, you would ask whether a shipment with a missing weight should be skipped, reported, or estimated. Write the answers as comments at the top of your file so the interviewer can see your assumptions.

Build the smallest version that works. Parse, normalize the dates, match on the shipment id, and print two lists. Keep each step in its own small function, because the change that comes later will usually affect only one step.

Expect the change and plan for it. When the interviewer adds the burst of 50,000 records a minute, explain what breaks first. Loading everything into memory and comparing every pair no longer works. Switch to a dictionary keyed by shipment id, process records in batches, and say what you would do in production, such as a queue in front of the parser.

Test out loud. Run a few small cases you wrote yourself: a duplicate id, a bad date, an empty batch. If something fails, read the error, form one guess, and check it. Interviewers watch how you debug as closely as how you write.

Are AI Tools Allowed?

Ask your recruiter directly, and ask for the answer in writing. Google has piloted a coding round for some junior and mid-level software engineer roles in which candidates use Gemini to read, debug, and improve existing code. In that pilot, interviewers reportedly score the quality of instructions given to the AI, checking of AI output, and debugging skill. Public FDE reports do not confirm that this round uses the same rules, and one FDE candidate reported that no AI tools were allowed in coding. Prepare to write every line yourself, and treat an AI assistant as a possible extra.

If AI tools are allowed, say what you are asking the assistant for and why. Read every line it produces before you run it, because an interviewer will mark you down for code you cannot explain.

Common Mistakes

  • Coding before asking questions. You may build the wrong thing for twenty minutes.
  • Designing for scale before anything works. A working small version comes first.
  • Writing one long function. A requirement change then forces a rewrite.
  • Working in silence. The interviewer writes notes for a hiring committee and can only record what you say.
