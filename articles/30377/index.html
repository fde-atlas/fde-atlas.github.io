Must-Read for FDEs: Book Review of Machine Learning Applications from Idea to Product

Original title: FDE 必读书：机器学习应用从想法到产品书评

FDE Times · 2026-11-11 · 4 min read

Summary

This review covers Emmanuel Ameisen's Building Machine Learning Powered Applications (O'Reilly, 2020), a book about the roughly 95% of ML work that happens outside model training: scoping problems, building datasets, debugging, and deployment. The author argues this unglamorous work is exactly what forward deployed engineers do daily. Three takeaways stand out: distinguish the data you found from the data you need, manually inspect raw samples before trusting metrics, and swap the model for a trivial rule to debug the surrounding pipeline. The review also notes the book predates large language models and lacks deployment detail, recommending readers add monitoring and rollback practices.

Key points

  • 95% of ML work lies outside model training, matching the FDE job description.
  • Key lesson: found datasets often lack the input-label pairs the problem needs.
  • Manually reading dozens of real samples reveals issues dashboards miss.
  • Replace the model with a simple rule to isolate pipeline bugs.
  • Book predates LLMs and is thin on deployment; add monitoring and rollback.

What Emmanuel Ameisen wrote about is the 95% beyond model training—and that's precisely where a Forward Deployed Engineer's week goes.

Key Takeaways

  • Emmanuel Ameisen's book (O'Reilly, 2020) is about the work beyond model training
  • Three ideas worth remembering: contrast the data you found with the data you need, look at samples yourself, and debug with a minimal model
  • The book needs updating for the large model era and is light on deployment details, but its approach still holds

On the page introducing the book, Emmanuel Ameisen gives a number that unsettles many machine learning newcomers: according to him, data scientists spend 95% of their time narrowing product use cases, working with data, and deploying. Training the model—what most courses almost exclusively cover—takes up only a small fraction of the remainder.

Building Machine Learning Powered Applications: Going from Idea to Product (O'Reilly, 2020) was written for that 95%. Ameisen claims the book offers practical techniques for the less-discussed parts of machine learning: building and labeling datasets, debugging models, and deploying models.

For a Forward Deployed Engineer (FDE), this list is practically a job description. Clients rarely lack algorithms; what they lack is a clearly defined problem, a usable dataset, and a system that keeps running after launch when it faces real users.

The model is just one piece

According to one reader's notes on GitHub, the book's consistent thesis is that training a model alone is not enough to get a machine learning product into users' hands.

The companion repository hundredblocks/ml-powered-applications has three parts: Jupyter notebooks demonstrating the book's concepts, an ml_editor library holding the core functions from the case study, and a Flask app. This maps exactly to three familiar stages of FDE work: running experiments, packaging them into a library, and building an app for users.

The data you found isn't necessarily the data you need

The first idea worth remembering is a brief reminder in the book: people often treat the dataset they found as the dataset they need. On a client site, this mistake surfaces in the first week—someone hands you a database export and says, "here's the data."

Imagine a customer support company that wants to "use AI to help staff reply to tickets better." Taken literally, you would generate complete replies—a problem that is broad, hard to measure, and hard to debug.

A narrower definition: predict whether a draft needs revision. The input is the draft, the output is a label, and the metric is the proportion of drafts rewritten by the team lead.

Here's the trap. The client's ticket archive may only store final replies, not the drafts before revision. Plenty of data, yet precisely missing the input-label pairs the problem requires.

So the first thing to do is ask: does the system record revision history? Ask this question before promising the client any numbers.

Before trusting metrics, look at the data yourself

A review on Substack points out that obtaining labeled data can be extremely difficult. The review also mentions a habit in the book borrowed from Monica Rogati: quickly skim a large number of samples and watch for anything unusual. The advice is so simple it's easy to overlook, but it's cheaper than any dashboard.

Applied to the ticket example: before opening a notebook, read a few dozen real drafts. You may find things no column of numbers would ever reveal, such as duplicate tickets, template replies pasted verbatim, or tickets written in multiple languages. Each finding becomes a concrete question at the next client meeting.

When the system misbehaves, simplify the model

According to the same reader's notes, the third idea is: replace the model with something simple, then debug the entire pipeline. It sounds backwards, but it's the fastest way to determine whether the problem lies in the model or around it.

For the ticket problem, a temporary "model" can be a single rule: mark any draft shorter than a certain threshold as needing revision.

If this rule produces absurd results in the interface, the bug is in data loading, field joins, or display—not in the algorithm.

Only after the entire pipeline runs end to end is it worth swapping the rule for a real model.

Where the book is outdated

The book was published in 2020, before the large model wave. The Substack review says that in the era of large models, the book needs updating but remains useful. That's a fair assessment: the three ideas above are model-agnostic and still hold even when the model is just an API call.

The second shortcoming an FDE should know about: a review on DEV Community criticizes the book for being light on deployment details. If you can only fill one gap, fill monitoring and rollback first, because these two determine whether a deployment survives its first week on a client site.

In the ticket example, monitoring means continuously tracking the proportion of drafts the team lead revises after launch, catching model degradation before the client complains. Rollback means being able to revert to the simple rule or the previous model version by changing a single configuration. Both must be in place before the first demo.

Who should read it, and how

This book suits software engineers who know Python and machine learning basics but have never delivered a model to real users. Keep the repository open as you read, running the notebooks alongside each chapter.

Afterward, spend most of your time on the ml_editor library and the Flask app. This is where the model becomes something others can use, and it's the part closest to what you'll do for clients in the future.

If you want this book to become a line on your resume, don't stop at re-running the author's repository. Apply the same three-stage structure to a different public data source.

Document where the data you found differs from the data you needed, and which bugs the simple baseline helped you catch. In an FDE interview, these decisions are more persuasive than any accuracy number.

Algorithms will change many more times. The unglamorous work nobody brags about—defining the right problem, looking at the data yourself—is always the reason clients hire an FDE.
