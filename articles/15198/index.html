A2UI 1.0 Explained: Google's Generative UI Protocol for Agents, What Changed, and When to Use It

FDE Interviews · 2026-11-12 · 10 min read

Summary

The article explains A2UI 1.0, Google's first stable release (11 November 2026) of an open generative UI protocol that lets AI agents respond with interactive screens—forms, charts, approval cards—described as structured data rather than text. The host app validates the description against a registered component catalog and renders it with native components, so the model never emits executable code. Version 1.0 adds bidirectional function calls, mixed catalogs, accessibility attributes, and removes theming from the protocol. Benchmarks show the Express notation cuts UI code tokens roughly 2.7–3.1x and input tokens about 45%. The piece contrasts A2UI with AG-UI, MCP Apps and A2A, and outlines when the protocol fits—especially for agents across trust boundaries—and when simpler approaches suffice.

Key points

  • A2UI 1.0 lets agents describe screens as data; apps render natively from a catalog.
  • New in 1.0: bidirectional function calls, mixed catalogs, ARIA accessibility, user-activation requirements.
  • Express notation cuts UI code tokens ~2.7–3.1x and input tokens ~45% on the project's benchmark.
  • A2UI composes with AG-UI, A2A and MCP Apps, which solve different layers of agent interaction.
  • Best suited for decisions, cross-platform rendering, and third-party agents outside your trust boundary.

A2UI 1.0 lets AI agents answer with native forms, charts and approval cards instead of text. What changed from 0.9, what the 3x token claim measures, how it differs from AG-UI and MCP Apps, and where it fits in an agent stack.

BY MEI LIN · FDEINTERVIEWS EDITORIAL · UPDATED NOVEMBER 12, 2026 · 7 MIN READ

PRACTICE THIS:AG-UI and agent-user interaction, the concept ·System One decision models, the concept ·RAG and agent design questions ·The must-know FDE questions

A2UI is an open protocol that lets an AI agent answer with an interactive screen, such as a form to confirm, a chart or an approval card, instead of a wall of text. The agent describes the screen as data, using only components your app has registered, and your app draws it with its own native components. Version 1.0, released by Google on 11 November 2026, is the first stable release. It adds two-way function calls and mixing components from several catalogs, and ships agent SDKs for Python, TypeScript and Dart. Use it when an agent needs to collect a decision or show structured data across web and mobile, especially when the agent sits outside your trust boundary.

The problem it solves

Agents answer in text because text is what models produce. That works for a question and fails for a task. Comparing three products, approving a plan with ten steps or picking a time that works for four calendars turns into round after round of "which one?". The obvious fix, letting the model write HTML or React, creates a worse problem: arbitrary model-generated code running in your product, styled however the model likes, with whatever behavior it invents.

A2UI takes the middle path. The app publishes a catalog: the components the agent may use, their properties and the functions it may call. The agent composes a screen from that catalog as structured data. The app validates it and renders it natively. The agent controls layout and wiring; the app controls what exists and what it does.

How it works

A2UI has three layers:

  • Inference. A model writes a description of the UI in an inference format. The default for new work is A2UI Express, a compact constructor-call notation such as 
    root = Text("Hello")
    . Direct JSON still works. A decision model can also pick components from a list instead of writing text.
  • Transport. An agent SDK parses the model's output, validates it against the catalog, expands macros and emits wire messages: 
    createSurface
    , 
    updateComponents
    , 
    updateDataModel
    and 
    deleteSurface
    , sent as 
    application/a2ui+json
    over whatever channel you use, including A2A, AG-UI or MCP.
  • Rendering. In the app, a core library turns messages into a framework-neutral UI tree, a framework adapter maps it to native widgets, and the catalog limits what can appear.

Here is what the model actually writes. This Express block and the JSON it compiles to come from the project's own conformance tests:

root = Column([greeting, farewell])
greeting = Text("Hello")
farewell = Text("Goodbye")
{
  "version": "1.0",
  "createSurface": {
    "surfaceId": "default_surface",
    "catalogId": "conformance/simplified",
    "components": [
      { "id": "root", "component": "Column", "children": ["greeting", "farewell"] },
      { "id": "greeting", "component": "Text", "text": "Hello" },
      { "id": "farewell", "component": "Text", "text": "Goodbye" }
    ]
  }
}

Variable names become component IDs, and the SDK, not the model, writes the envelope. If the model names a component the catalog does not declare, compilation fails with a validation error before anything reaches the screen.

Values reach the screen through a data model. A component binds to a path such as

/booking/time

, and the agent server fills that path from your systems. The model can lay out a balance field without ever seeing the balance. User actions and permitted function calls flow back to the agent as events.

The token claim, read properly

The launch posts say Express describes the same UI in about three times fewer output tokens than JSON. The project's benchmark (54 samples,

gemini-3.8-flash

,

temperature

0) supports that for the UI code itself and adds detail the headline leaves out:

Format Input tokens UI code tokens Total output Pass rate
Direct JSON, thinking off 10,980 807 811 53 of 54
Express, thinking off 6,000 297 (2.7x fewer) 299 53 of 54
Direct JSON, thinking unbounded 10,980 794 2,320 53 of 54
Express, thinking unbounded 6,000 260 (3.1x fewer) 1,789 (23% fewer) 53 of 54

Two readings. With thinking on, most output is reasoning, which Express does not shrink, so the saving on total output is about a quarter rather than two thirds. And the 45% input saving is the quieter win: compact component signatures replace full JSON Schemas in the system prompt, and that prompt is paid on every turn. As a rough independent check, the four multi-component cases in the project's Express conformance suite compile to minified JSON about 3.1 times larger in bytes (range 2.4 to 3.8). Bytes are not tokens, and four small cases are not a benchmark, but the direction agrees.

Who is using it

Google's launch post names four outside adopters. Atlassian is bringing A2UI to Jira, where an agent working a ticket asks the team for a missing decision through an interactive card in the work item. Alation renders metric cards and charts with it, the same feed inside its product and inside Claude through MCP Apps. ByteDance shipped an A2UI renderer for its Lynx framework in June 2026. Bloomberg is building with it. Inside Google, Gemini Notebook asks deck-format questions through A2UI cards, and Gemini Enterprise agents can already respond with A2UI.

One detail connects to work we have covered: ByteDance's Lynx playground uses a decision model, Jev, to pick components and values instead of having an LLM write text, and official SDK support for decision models is on the A2UI roadmap. Picking from a fixed catalog is a classification problem, which is where System One decision models are fast and calibrated.

A2UI, AG-UI, MCP Apps and A2A

These names arrive together, and they answer different questions:

Protocol Answers Direction
MCP How does an agent call tools and read data? Agent down to tools
A2A How do agents delegate to other agents? Agent across to agents
AG-UI How does a front end follow an agent's run: messages, tool calls, state? Agent up to the app, as events
A2UI What should the screen show, built from components the app allows? Agent up to the app, as a UI description
MCP Apps How does an MCP server ship an interactive view into an AI assistant? Server into the host assistant

They compose. A2UI messages can ride inside AG-UI events or A2A messages, and A2UI screens can render inside an MCP App, which is how Alation's feeds appear in Claude.

When to use it, and when not

Use it when:

  • The agent needs a decision or structured input: approvals, forms, pickers, comparisons.
  • The same agent serves web and mobile, and you want one description rendered natively on each.
  • The agent is remote, third-party or across a trust boundary, and you need to limit what it can put on screen.
  • Sensitive values should stay out of the model's context.

Skip it when:

  • The answer is plain text, or a single static chart you could render from a tool result.
  • You control both agent and front end, and your UI needs are a handful of fixed cards; plain typed tool results may be simpler.
  • You need arbitrary custom logic inside components. Sandboxed logic is a roadmap item, not 1.0.

The forward deployed angle

Generative UI is turning up in agent design rounds as "the agent should not just answer, it should get the user to approve something". The strong answer separates three decisions: what the model may decide (layout and wiring, from a catalog), what the app enforces (validation, allowed calls, user activation for anything with side effects), and where data comes from (bound paths filled by your systems, not values the model typed). That separation is the same instinct behind guardrails on tool calls, applied to the screen. Practice it on RAG and agent design questions, and be ready to say why you would not let a model emit HTML into a customer's product.

FAQ

A2UI (Agent-to-User Interface) is an open protocol, started at Google and licensed Apache 2.0, that lets an agent answer with an interactive screen instead of text. The agent describes the UI as data that references components the app has registered, and the app renders it with its own native components in React, Angular, Lit, Flutter, SwiftUI or Jetpack Compose. Version 1.0, the first stable release, shipped on 11 November 2026.

Bidirectional function calls (the agent can call renderer functions and the renderer can call agent functions, with allowed callers declared in the catalog), mixing components from several catalogs on one surface, a reserved @ prefix for protocol keys, accessibility attributes including live regions, extension metadata, removal of theme from the protocol, and new agent SDKs for TypeScript and Dart alongside Python.

For the generated UI code, yes on the project's benchmark: 2.7 times fewer code tokens with thinking off and 3.1 times fewer with thinking on, across 54 samples on gemini-3.8-flash, with equal pass rates. Total output falls far less when the model also thinks (23%), because thinking tokens do not shrink. Input tokens fall 45% because compact component signatures replace full JSON Schemas in the prompt.

AG-UI is an event protocol for streaming an agent's run (messages, tool calls, state) to a front end. A2UI describes what a screen contains, as components from an approved catalog. MCP Apps let an MCP server ship an interactive UI into an AI assistant. They combine: A2UI screens can travel inside AG-UI events or render inside an MCP App.

It is designed for that case. The agent can only place components and call functions the app has registered, the UI is data rather than executable code, and values can be bound to the data model on the agent server so sensitive fields need not pass through the model. You still own validation, action handling and authorization on the app side.

Discussion (4)

The trust-boundary framing is what makes this relevant to forward deployed work. At a bank or a hospital, the question is never 'can the agent draw a nice chart'. It is 'can a third-party agent put something on our screen that we did not approve'. A catalog allowlist is an answer a security reviewer can actually sign off on.

Reader question: if the model never sees sensitive values, how does it know what to show?

It sees structure and paths, not values. The model places a TextField bound to /account/balance, and the agent server fills the data model at that path from your systems. The model decides layout and wiring; your code decides the numbers. Same idea as a parameterized query keeping data out of SQL text.

The breaking-change note matters for anyone on 0.9 already. Gemini renders 0.9.1 today and the Compose renderer is still on 0.9.1, so a mixed fleet will run two protocol versions for a while. Pin per surface, and do not blanket-replace 'path' with '@path'; the migration guide warns about exactly that.
