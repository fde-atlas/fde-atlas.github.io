FDE Joint Load Testing: Resolving Customer Architecture Disagreements with k6

Original title: FDE 联合压测：用 k6 化解客户架构分歧

FDE Times · 2026-10-30 · 6 min read

Summary

This guide argues that FDEs should resolve performance disagreements with client architects by jointly designing a load test rather than debating whether a system will fail. Using Grafana k6, thresholds are agreed and committed before the test runs, so the skeptic becomes a co-author of the methodology. A worked example uses a three-phase scenario: a 50-user baseline with p95 and error-rate thresholds, a stress phase ramping to 200 users to locate the breaking point (deliberately without thresholds), and a recovery phase. Citing Google SRE, AWS Well-Architected, and Ed Glas, it recommends production-like environments with realistic data volumes, real sanitized client queries, component-level testing before full-system tests, and recording outcomes in an ADR. It also lists four mistakes that undermine joint testing.

Key points

  • Turn architecture disputes into experiments with pre-agreed pass criteria.
  • Encode agreed thresholds in k6 test files under version control.
  • Use baseline, stress, and recovery phases; stress finds the breaking point.
  • Test in production-like environments with real sanitized queries.
  • Test components first, then the system, and record decisions in an ADR.

Key Takeaways

  • Don't argue about whether the system will crash; instead, work with the customer to write down exactly how to find out where it crashes.
  • Agree on thresholds first, use an environment with sufficient data that closely resembles production, and test individual components before the whole system.
  • Push the load beyond expected levels while also measuring recovery, and finally record the decision in an ADR.

The architecture review has been going for 40 minutes. You've just finished presenting the design for a document search service to be deployed on the customer's side, and their chief architect crosses his arms: "Every request goes synchronously through the same database. It will definitely crash at peak."

You think the design is fine; he thinks it will definitely crash. You're arguing about something that hasn't happened yet, and neither of you can win with words alone—while every extra minute of arguing erodes the customer's trust in you.

Arguing better won't help either. The better move is to invite him to co-design the very test that might prove him right. This is the skill that separates an excellent Forward Deployed Engineer (FDE) from someone who only writes code: turning a disagreement into an experiment, with judging criteria agreed on by both sides in advance.

Why do tests cool down arguments?

Because they change the question itself. "Will it crash?" is a battle of beliefs; "At what load does it crash, and which component fails first?" is an engineering question, and every engineer wants to know the answer.

At Google, running a system safely requires understanding its limits first. Google's SRE book states explicitly that engineers use stress testing to find the limits of web services, and that load testing reveals the breaking point—this is foundational knowledge for capacity planning.

Seen this way, the architect's warning isn't a nuisance; it's a test requirement that nobody has written down yet.

When you say "You're right—we really don't know where the breaking point is. Let's find it together," he goes from critic to co-author. Whatever the outcome, the test methodology has his buy-in from the start.

Thresholds must be signed off before the test runs

The most damaging mistake is running the test first and discussing what the results mean afterward. By then, both sides will interpret the charts in whichever way favors them. AWS Well-Architected lists exactly this as an anti-pattern: failing to define clear, measurable performance requirements such as response time, throughput, and scalability targets.

Grafana k6 has a built-in mechanism for this: thresholds, which are pass/fail criteria declared for each metric. The thresholds live in the test file itself, so what both sides agreed on is preserved in version control, not just in a line of meeting minutes.

The second thing to agree on is where to run it. AWS cautions that a scaled-down test environment can misrepresent how the system behaves in production. If you run it on a small staging machine and the system holds up, the architect has every reason to reject the result. So, let him choose the environment.

A complete example

Continuing the scenario above, let's assume some numbers. After 20 minutes of discussion, both sides agree: normal load is 50 concurrent users, and the peak the architect is worried about is four times that. The pass thresholds under normal load are p95 below 800 ms and error rate below 1%.

The architect then raises an issue you hadn't thought of: if the system crashes at peak, how far does the load need to drop before it recovers on its own? Google's SRE book poses the same question: when some servers crash under high load, how low must the load fall before the system stabilizes again? So the scenario is split into three phases.

import http from 'k6/http';
import { check } from 'k6';
import { SharedArray } from 'k6/data';

// 客户提供的真实（已脱敏）查询，不是编造的
const queries = new SharedArray('queries', () => JSON.parse(open('./queries.json')));

export const options = {
  scenarios: {
    baseline: { executor: 'constant-vus', vus: 50, duration: '15m' },
    stress: {
      executor: 'ramping-vus', startTime: '15m', startVUs: 50,
      stages: [{ duration: '10m', target: 200 }, { duration: '5m', target: 200 }],
    },
    recovery: { executor: 'constant-vus', startTime: '30m', vus: 25, duration: '10m' },
  },
  thresholds: {
    // 双方签字认可的阈值：只适用于正常负载和恢复阶段
    'http_req_duration{scenario:baseline}': ['p(95)<800'],
    'http_req_failed{scenario:baseline}': ['rate<0.01'],
    'http_req_duration{scenario:recovery}': ['p(95)<800'],
  },
};

export default function () {
  const q = queries[Math.floor(Math.random() * queries.length)];
  const res = http.post(`${__ENV.BASE_URL}/search`, JSON.stringify({ q }),
    { headers: { 'Content-Type': 'application/json' } });
  check(res, { '状态码 200': (r) => r.status === 200 });
}

Note that

stress

phase has no thresholds. It isn't meant to be passed; it's meant to find the breaking point. k6 classifies tests by purpose: stress testing is used to observe how the system behaves at its limits—that is, what happens when load exceeds the expected average.

AWS likewise lists "not pushing the load beyond the expected upper limit" as an anti-pattern.

Suppose the results are as follows: the baseline phase passes; in the stress phase, p95 spikes sharply once users exceed roughly 140; the recovery phase passes. You were both partly right. The design can handle the current load, but it has an upper limit—and now both sides can see where that limit is.

The recovery phase here only tests one level, 25 users, so it only shows whether the system can recover at that level. To fully answer the architect's question, replace it with a

ramping-vus

that steps the load down in multiple stages—say, 150, 100, 50, and finally 25—and record the stage at which p95 first drops back below 800 ms.

Steps to do it yourself on-site at the customer

Start early. Ed Glas pointed out in a Microsoft blog post that many performance problems are architectural and can't be fixed hastily right before launch. If the architect has concerns, test this week—not the week of launch.

Seed enough data before measuring. As Ed Glas says, many performance issues only appear when the data volume is large. A database with only 10,000 records can't test the concern that "this database will eventually hold tens of millions of records."

Test individual components first, then the whole system. Google SRE notes that every component has its own breaking point and needs its own load test; Ed Glas recommends starting with a single transaction, then a mix of transactions, and only then the entire system.

In the example above, keep the scenario unchanged and just point the

BASE_URL

at an endpoint that only executes database queries. If it crashes earlier than the whole system, you've found the culprit.

Finally, write down the results. An Architecture Decision Record (ADR) documents an architectural decision along with its rationale, trade-offs, and consequences. An ADR like "keep the synchronous design; measured limit is roughly 140 users; introduce a queue when actual load reaches 100" turns the test results into a conditional commitment, so three months later nobody has to argue from scratch again.

Mistakes that make joint testing backfire

The most common mistake is writing the scenarios yourself and then inviting the customer to look at the results. A customer who didn't participate in designing the test won't trust the results. Let the architect choose the peak load and the test environment, even if you think his numbers are a bit pessimistic.

The second mistake is using fabricated queries. A list of just five queries looping over and over will hit the cache every time, and the p95 will look suspiciously good. Ask the customer for a real, anonymized sample of queries.

The third mistake is treating the stress phase as an exam that must be passed. If you avoid pushing the system to its breaking point, the architect will think you're afraid of the answer. Finding the breaking point is a shared win, not your failure.

The last mistake is forgetting the recovery phase. A system that slows down at peak and then recovers on its own is fundamentally different from one that crashes and stays down. Ask the architect directly which scenario worries him more, and let his answer determine how detailed the recovery phase should be.

Put it on your resume

Instead of just writing "performed load testing" on your resume, write something like: co-designed joint load tests with the customer's architecture team, agreed on p95 thresholds before running, located the database breaking point, and recorded the decision in an ADR.

When interviewing for an FDE role, be ready to tell a story like this, because it shows you can resolve technical disagreements with customers using numbers instead of volume.

This week's exercise: recall the last time you and someone else disagreed about a performance issue. Write down three numbers both sides should have agreed on in advance, then write a three-phase scenario to test them. The next time someone crosses their arms and says "it will crash," you'll have a ready answer: "Great, let's see together where it crashes."
