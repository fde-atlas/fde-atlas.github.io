How an FDE Can Safely Query Customer Databases: Read Replicas and Timeouts

Original title: FDE 如何安全查询客户数据库：只读副本与超时

FDE Times · 2026-10-08 · 5 min read

Summary

This guide teaches FDEs how to query customer databases without harming production systems. The core advice: connect to read-only replicas first—PostgreSQL hot standby or MongoDB secondary nodes via read preference. When only the primary is available, start each session with read-only mode plus three timeouts (statement, lock, idle-in-transaction) so a stray COUNT(*) or forgotten JOIN can't consume CPU, I/O, or block real transactions. Using a delivery company example, it shows exploring PostgreSQL schemas via information_schema and sampling MongoDB documents with $sample to discover field inconsistencies (e.g., renamed fields causing mismatched reports). It also covers replica trade-offs: long queries can be cancelled by standby replay, and secondary reads may be stale, so always disclose data sources when reporting numbers.

Key points

  • Prefer hot standby replicas or MongoDB secondaries for all queries.
  • On primaries, set read-only mode plus statement, lock, and idle timeouts.
  • Sample NoSQL documents to learn real schemas—never trust a few find() results.
  • Split long replica queries into smaller chunks instead of raising DBA limits.
  • Verify with pg_is_in_recovery() and disclose replica staleness when reporting figures.

Hot standby databases reject writes outright; when you can only connect to the primary, use a read-only session with timeouts, so a single COUNT(*) doesn't slow down live orders.

Key takeaways

  • Request access to a PostgreSQL hot standby or MongoDB secondary first, and only consider the primary as a last resort.
  • Enable read-only at the start of every session and set three timeouts: read-only blocks data modifications, while timeouts limit how long a single query can occupy CPU, I/O, and locks.
  • NoSQL schemas aren't documented anywhere, so you must sample documents to understand the real structure.

Monday morning, the customer's office. The IT team hands you a connection string and says: "Here's the database, feel free to look around." You open DBeaver and find 200+ undocumented tables. Your first instinct is to run a query against the biggest table:

SELECT COUNT(*)

。

Stop right there. If the connection string points to the primary, this seemingly harmless statement will compete with the customer's real orders for resources. "Feel free to look around" is just the IT team being polite; their systems won't handle the extra load just because they said so.

At a new customer, you need to understand their data quickly without breaking anything. This guide gives you a workflow you can use tomorrow: pick the right place to run queries, lock down your session, read PostgreSQL and NoSQL schemas, and avoid the mistakes newcomers commonly make.

The first question: where to query

PostgreSQL has a mode called hot standby. In this mode, you can connect to a replica server and run read-only queries while the replica continuously receives data from the primary. This is where a Forward Deployed Engineer (FDE) should work. Ask the IT team on day one: "Is there a standby database I can connect to?"

Hot standby databases also come with built-in protection. According to the PostgreSQL documentation, all connections on a standby are strictly read-only—you can't even write to temporary tables. Even if you accidentally run

UPDATE

, the statement will be rejected and the data remains untouched.

MongoDB is different. By default, applications send all read requests to the primary of the replica set, so you need to switch the read preference to secondary yourself to avoid adding load to production. It takes just one line of code, shown in the examples below.

Lock down your session before running your first query

Some customers don't have a standby, or only give you a user on the primary. In that case, you need to build your own guardrails. At the start of every session, paste these four lines:

SET default_transaction_read_only = on;
SET statement_timeout = '30s';
SET lock_timeout = '2s';
SET idle_in_transaction_session_timeout = '60s';

Each line guards against a different accident.

default_transaction_read_only

Is off by default, meaning every transaction can write. Turn it on so new transactions are read-only by default.

statement_timeout

Cancels statements that run longer than the set limit, so a JOIN with a missing join condition won't run all afternoon.

The other two lines handle locks.

lock_timeout

Cancels a statement when it waits too long for a lock on a table, index, or row, so your query won't sit in the queue blocking real transactions.

idle_in_transaction_session_timeout

Terminates sessions that opened a transaction but then went idle—for example, when you open a GUI tool, run a query, and go to lunch.

The PostgreSQL documentation also explicitly notes that READ ONLY is a high-level read-only concept and doesn't prevent all disk writes. But the main reason for these four lines lies elsewhere: read-only doesn't limit how much CPU a query uses, how much I/O it generates, or how long it waits for locks—those limits come from the three timeouts.

Example: reading the schema at a delivery company

Suppose the customer is a delivery company. Orders are stored in PostgreSQL, and driver event logs are in MongoDB. Your task is to figure out why the two departments' late-delivery rate reports don't match.

For PostgreSQL, start with information_schema. It's a set of views defined by the SQL standard, so anyone who has used any relational database management system (RDBMS) will find this query familiar:

SELECT table_name, column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
ORDER BY table_name, ordinal_position;

Export the results to a file and go through them column by column. In this example, the pair

orders.driver_id

and

drivers.id

already hints at a relationship between the two tables, even without a foreign key. One limitation: information_schema doesn't cover PostgreSQL-specific features. To see those, you need to check the system catalogs in

pg_catalog

.

MongoDB has no tables to list. NoSQL schemas are flexible—every document can have different data types—so only sampling reveals the real structure:

db.getMongo().setReadPref("secondaryPreferred")
db.driver_events.aggregate([
  { $sample: { size: 1000 } },
  { $project: { kv: { $objectToArray: "$$ROOT" } } },
  { $unwind: "$kv" },
  { $group: { _id: "$kv.k", n: { $sum: 1 } } },
  { $sort: { n: -1 } }
])

Suppose the results show that all 1,000 documents have

delivered_at

, but only 300 have

delivered_ts

. The most likely explanation is that the application renamed the field in some version, and the two departments are reading different fields. That's your first hypothesis to bring into the meeting, backed by concrete numbers anyone can verify.

The cost of reading from replicas

Replicas are safer than the primary, but they have their own limitations. On a hot standby, long queries can conflict with changes the standby is replaying from the primary (such as DROP TABLE). When the wait exceeds

max_standby_streaming_delay

or

max_standby_archive_delay

, PostgreSQL cancels your query.

When you hit this error, don't ask the DBA to raise the parameters—instead, break your query into smaller pieces, e.g., run it week by week instead of a whole year at once. Short queries are less likely to be canceled, and even if they are, you lose less work.

In MongoDB, all read preferences other than primary may return stale data, because secondaries replicate from the primary asynchronously. You can set

maxStalenessSeconds

to cap the acceptable delay.

More broadly, most NoSQL systems only guarantee eventual consistency. When reporting numbers to the customer, state where the data was read from and when.

Mistakes that cost an FDE trust

The most common mistake is trusting the connection string without verifying it. Running

SELECT pg_is_in_recovery();

tells you whether you're connected to a standby or the primary, and it takes two seconds.

The second is drawing conclusions about a NoSQL schema after opening a few documents with

find()

. Every document can have a different structure, so use

$sample

, or sort by

_id

and look at both old and new documents before drawing conclusions.

Another is using data read from a secondary in a meeting that requires real-time numbers without saying so upfront. Once the customer notices the numbers are off, they may start doubting the rest of your analysis too. As for transactions left hanging in a GUI tool, setting

idle_in_transaction_session_timeout

takes care of that for you.

Turn this skill into an interview advantage

When reading FDE job descriptions, watch for phrases like "working directly with customer data" or "integrating with existing systems." They mean your first week will likely look like the scenario at the start of this article.

Don't just write "proficient in SQL" on your resume. Spell out that you built a read-only access workflow covering sessions with timeouts, querying replicas, and sampling NoSQL schemas. That one sentence concretely shows what you've done with real data; "proficient in SQL" doesn't.

Customers may not remember how many clever queries you wrote. But if you slow down their order system even once, they'll remember it for a long time.
