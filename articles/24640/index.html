How to estimate Spark cluster size: start by testing with the customer's data

Original title: Spark 集群规模怎么估算：先测客户数据

FDE Times · 2026-10-08 · 6 min read

Summary

This FDE Times guide argues against estimating Spark cluster size before measuring the customer's actual data, since numbers stated in meetings tend to go straight into budgets. The author proposes a fast measurement routine: pull one day of data, count files and sizes via S3, inspect Parquet row groups with DuckDB, and run a local PySpark notebook to check read partitions, key skew, and cached memory. Results are compared against Spark's defaults: 128 MB per partition, 200 shuffle partitions, 10 MB broadcast join threshold, and 2–3 tasks per core. In a worked example of a 40 GB nightly job, small files suggest compaction first, a 6 MB dimension table gets broadcast, and a key holding 35% of rows signals skew. A DuckDB single-machine baseline compared against the batch window decides whether a cluster is needed; only runtime nearing the window, two large tables joining, or heavy disk spillover changes that conclusion. The article closes with common mistakes and an interview framework.

Key points

  • Never answer the cluster-size question without measuring a day of real customer data first.
  • Benchmark against Spark defaults: 128 MB partitions, 200 shuffle partitions, 10 MB broadcast, 2–3 tasks per core.
  • In the 40 GB example: compact small files, note the 6 MB broadcast table, and flag the 35% skewed key.
  • Run a DuckDB single-machine baseline; a cluster is justified only by three specific signals.
  • Avoid copying old configs, measuring clean samples, ignoring file layout, and forgetting dimension table growth.

Key Takeaways

  • Spark's default thresholds (128 MB, 200, 10 MB, 2–3 tasks per core) only mean something when compared against measurements on the customer's data.
  • For small and medium-sized data, Spark's overhead is substantial. DuckDB runs on a single machine and can still spill to disk, making it the first alternative worth benchmarking.
  • To conclude that "a cluster is needed," you must point to a specific number crossing a threshold, such as runtime approaching the batch window.

At a second technical meeting with a customer, someone often asks: "How many nodes should our Spark cluster have?" At that point you haven't even opened one of their data files. Answering by intuition is risky, because numbers spoken in a meeting room tend to go straight into the budget.

A safer answer is: ask for one day of real data and a few hours to run measurements. This is not dodging the question. Spark's important configurations are thresholds expressed in bytes, partition counts, or core counts; without measurement, any number you give is a guess.

As a Forward Deployed Engineer (FDE), you may have to answer this question on an unfamiliar system, under time pressure, in front of people who don't care what a partition is. So you need a measurement workflow fast enough that you can bring numbers to the next meeting.

Spark already has thresholds; your job is to test your data against them

Spark SQL ships with several default thresholds you can compare your measurements against. When reading Parquet, JSON, or ORC, each partition is at most 128 MB (

spark.sql.files.maxPartitionBytes

), so the input data volume determines the number of read tasks. For joins and aggregations, Spark by default splits data into 200 shuffle partitions (

spark.sql.shuffle.partitions

）。

The third threshold is broadcast joins: tables smaller than 10 MB are sent in full to every worker, so large tables don't need to be shuffled. The fourth comes from the tuning guide: Spark recommends allocating 2–3 tasks per CPU core, meaning the partition count should be calculated from the cluster's total core count.

Since Spark 3.2.0, Adaptive Query Execution (AQE) is enabled by default. AQE re-optimizes execution plans using runtime statistics, coalescing small shuffle partitions toward a default target size of 64 MB, and can split skewed partitions in sort-merge joins.

According to the Spark documentation, with AQE you no longer need to pick the right shuffle partition count for your dataset. Even so, AQE only corrects the execution plan at runtime. Actual data volume, file layout, and key skew still need to be measured by you.

Measuring a Nightly Job

Take a hypothetical example. A retail chain runs a nightly job: joining a

orders

table with a

stores

table, then aggregating revenue by store. You request one day of data and run three measurement commands, with no setup required.

The first command counts data volume and file count:

aws s3 ls --summarize --recursive s3://customer/orders/date=2026-10-01/

. The second uses DuckDB to inspect the Parquet file layout:

SELECT file_name,
       count(DISTINCT row_group_id) AS num_row_groups,
       max(row_group_num_rows)      AS max_rows_per_group
FROM parquet_metadata('orders/*.parquet')
GROUP BY file_name
ORDER BY max_rows_per_group DESC
LIMIT 10;

The third is a PySpark notebook running locally:

from pyspark.sql import functions as F

orders = spark.read.parquet("orders/")
stores = spark.read.parquet("stores/")

print("读取分区数:", orders.rdd.getNumPartitions())

total = orders.count()
(orders.groupBy("store_id").count()
   .withColumn("share", F.col("count") / total)
   .orderBy(F.desc("count")).show(10))

orders.cache().count()   # 然后打开 web UI 中的 Storage 页

(The comment on the last line means: "then open the Storage tab in the web UI.")

Suppose the results are as follows:

orders

40 GB total, spread across 12,000 files, averaging about 3.4 MB per file.

stores

The table is 6 MB. One

store_id

, namely the online sales channel, accounts for 35% of the rows. Each result maps to a different decision.

The customer's files are far smaller than the 100 MB–10 GB range recommended in DuckDB's Parquet layout guide.

So the first recommendation should be compacting small files, not adding nodes. If a metadata query shows a file contains only one giant row group, you also know that file can only be processed by a single thread. A reasonable row group size is 100,000 to 1,000,000 rows.

stores

The table is only 6 MB, below the 10 MB threshold, so Spark will broadcast it,

orders

meaning no shuffle is needed during the join. Write this number down: once the customer opens more stores and this table exceeds 10 MB, the execution plan will change without anyone notifying you.

The key accounting for 35% is the number to watch most closely. The Spark documentation explicitly states that data skew can severely slow down joins, but AQE's automatic splitting of skewed partitions only applies to sort-merge joins.

Open the aggregation stage in the web UI and look at the event timeline. If one task runs far longer than the others, or its shuffle read volume is several times larger, that is a warning sign to flag to the customer early.

Finally, memory. The Spark documentation says the best way to estimate memory is to cache the dataset and check the Storage tab in the web UI. Cache one day of data and you get a real number; multiply by how long the data needs to be retained. This figure is more reliable than any rule-of-thumb multiplier.

Does 40 GB Need a Cluster?

Before considering a cluster, run a comparison. A MotherDuck article points out that for small and medium-sized data, Spark ends up running at its minimum configuration while carrying substantial overhead.

The article uses AWS Glue as an example: the service requires a minimum of 2 DPUs, so even if the sample dataset is only about 1 GB, you pay for 32 GB of memory and 8 vCPUs.

DuckDB runs on a single machine and can still spill to disk when data exceeds memory. So run the nightly job's joins and aggregations as-is on DuckDB, time it, and compare against the customer's batch window. At the next meeting, you bring measured numbers, not opinions.

For example, if the batch window is 3 hours and DuckDB processes 40 GB in 25 minutes, the job doesn't need a cluster yet.

Only three signals could change that conclusion: single-machine runtime approaching the 3-hour window given the customer's data growth rate; the dimension table growing to the point where two large tables need to join each other; or disk spilling taking up most of the runtime.

When any of these signals appears, you can use the "2–3 tasks per core" recommendation to size a configuration. Suppose the planned cluster has 16 cores in total; the recommendation translates to roughly 32–48 partitions.

Only 16 tasks run at any given moment, with each core processing two to three tasks in sequence; cores that finish early pick up the next task instead of sitting idle. Leave shuffle partitions to AQE to coalesce toward the 64 MB target, and don't manually tune that 200.

Common Field Mistakes

The most common mistake is copying the configuration from a previous project, along with the manually tuned

shuffle.partitions

value for a completely different dataset. The second mistake is measuring on cleaned sample data. A clean sample has no key accounting for 35%, and everything looks smooth during measurement.

The third mistake is looking only at total volume and ignoring file layout. 40 GB split into 12,000 small files is a different problem from 40 GB split into 40 files of 1 GB each. The fourth mistake is forgetting that dimension tables grow. Set an alert when the table approaches 10 MB, because once it crosses that threshold, the execution plan changes.

Answering Interview Questions with Measurements

One question worth rehearsing before an FDE interview: "A customer adds 40 GB of data every night. Should they build a Spark cluster? How would you decide?" A weak answer lists tools; a strong answer presents a measurement plan.

You can answer in four steps. First, get one day of real data and measure the data volume, file count, row groups, dimension table sizes, and key skew. Next, cache a sample to measure actual memory usage.

Then, run a single-machine baseline on DuckDB and compare it against the batch processing window. Finally, state clearly which number would change your conclusion. This step deserves extra time: it shows the interviewer that you know under what conditions your conclusion would no longer hold.

When writing it into your resume, frame it as a concrete result, for example: "Profiled 40 GB of nightly data and recommended merging small files and using single-machine processing instead of building a cluster." If the job description mentions infrastructure cost optimization or capacity planning, tell this story there, with the numbers.

The next time a customer asks "How many nodes do we need?", first ask for a day of data, and promise to come back the next day with numbers.
