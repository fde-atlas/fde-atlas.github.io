How to Look Up FDE Salaries: Build Your Own Salary Table with the Greenhouse API

Original title: FDE 薪资怎么查：用 Greenhouse API 自建薪资表

FDE Times · 2026-10-29 · 6 min read

Summary

This tutorial shows how to build your own FDE salary table with roughly 40 lines of Python by calling Greenhouse's public Job Board API, which requires no API key. Key pitfalls: salary ranges only appear when you pass pay_transparency=true, amounts are stored in cents (5000000 means $50,000, not $5 million), and jobs without posted ranges must be kept and counted. Since US pay transparency laws in Colorado, California, and New York City drive disclosure, the data reflects the US market only. The article benchmarks results against Anthropic ($280k–$320k), OpenAI ($185k–$300k), and Palantir ($125k–$200k) base salaries, and frames the workflow—inspect structure, verify units, report missing data—as core FDE fieldwork.

Key points

  • Greenhouse's public GET API needs no key, but salary data only returns with pay_transparency=true.
  • Amounts are in cents: min_cents of 5000000 equals $50,000.00, a common unit-conversion error.
  • Only 21 of Palantir's 52 US roles list salary ranges, so missing data must be tracked, not dropped.
  • Pay disclosure stems from Colorado, California, and NYC laws, so the data is US-specific.
  • Benchmark base salaries: Anthropic $280k–$320k, OpenAI $185k–$300k, Palantir $125k–$200k, excluding equity.

About 40 lines of Python to scrape salary ranges that pay transparency laws require to be published, and write them to a CSV.

Key points at a glance

  • The Greenhouse Job Board GET endpoint doesn't require an API key, but salary ranges are only returned when you pass pay_transparency=true
  • Amounts are stored in min_cents and max_cents, where 5000000 means $50,000.00
  • Jobs without salary ranges are common: only 21 of Palantir's 52 US jobs list a salary

There's a number in the Greenhouse docs that can throw off your entire salary table:

"min_cents":5000000

. Forget that its unit is cents, and you'll think the job pays $5 million a year when it actually pays $50,000.00.

This article teaches you how to avoid traps like this. You'll write a short Python script: call Greenhouse's public jobs API, filter for Forward Deployed Engineer (FDE) roles, convert salary ranges into readable units, and write the results to a CSV file.

In the end you'll have an FDE salary table you built yourself, with the data source and scrape date noted, rather than numbers passed around by word of mouth.

If you're preparing to negotiate an offer, this table will be useful. But the bigger payoff is the skill itself: calling an unfamiliar API, reading the data structure, normalizing units, and handling missing data — exactly what an FDE does day to day on-site with customers.

Why do salary ranges appear in the API?

Mainly because the law requires it. According to the law firm Foley & Lardner, Colorado requires salary information on every job posting as long as the employer has at least one employee in the state, including remote roles. California requires covered employers to list salary ranges in job postings, and this also applies to postings published by third parties.

New York City also requires that job postings for roles working at least partly in the city state the minimum and maximum annual salary or hourly rate. So FDE roles in San Francisco and New York usually come with salary ranges, and Greenhouse provides this data through its API.

Keep in mind the consequence of this: the data you collect mainly reflects the US market, where laws mandate salary disclosure. Don't use it to infer salaries in other markets.

What do you need before writing code?

You need Python 3 and the

requests

library (

pip install requests

). No API key needed: the Greenhouse docs state that Job Board data is public and the GET endpoint requires no authentication.

What you need to find yourself is the board token, the company identifier in the API path. The fastest way is to open the company's careers page: if the page is hosted on Greenhouse, the company identifier is usually right in the URL. This is just a practical shortcut; once you find it, confirm it with step 1 below.

Step 1: Call the endpoint and inspect the structure before trusting it

The jobs list endpoint has the form

GET https://boards-api.greenhouse.io/v1/boards/{board_token}/jobs

. Adding

content=true

gives each job its full description, departments, and office locations; adding

pay_transparency=true

is what makes the API return the

pay_input_ranges

array. A Greenhouse support article also confirms that salary data is only returned when this parameter is enabled.

import requests

BOARD = "company_board_token"
URL = f"https://boards-api.greenhouse.io/v1/boards/{BOARD}/jobs"

resp = requests.get(
    URL,
    params={"content": "true", "pay_transparency": "true"},
    timeout=30,
)
resp.raise_for_status()
data = resp.json()
print(data.keys())

Check: the call doesn't throw an HTTP error, and you print the top-level keys. The code below assumes the jobs are under the

jobs

key and that each job has a

title

field. This is a simplification — verify it against the output you just printed.

Step 2: Filter for FDE roles

Job titles vary from company to company. The simple approach is to filter by strings in the title, then review each result yourself.

jobs = data.get("jobs", [])
fde_jobs = [
    j for j in jobs
    if "forward deployed" in (j.get("title") or "").lower()
]
print(len(jobs), len(fde_jobs))
for j in fde_jobs:
    print(j.get("title"))

Check: print each filtered title. If you see irrelevant titles, or you know the company uses a different name for the role, adjust the filter now — don't wait until after the table has computed its numbers.

Step 3: Convert cents to currency units, and keep jobs without salary ranges

This step determines whether the table is correct. The example JSON in the Greenhouse docs shows that every salary range has

min_cents

、

max_cents

and

currency_type

, so you must divide by 100. The code uses

.get()

so the script doesn't crash midway when a range is missing a field — consistent with the principle of never blindly trusting the data structure.

def cents(value):
    return value / 100 if value is not None else None

def to_rows(job):
    ranges = job.get("pay_input_ranges") or []
    if not ranges:
        return [{"title": job.get("title"), "min": None,
                 "max": None, "currency": None}]
    return [{
        "title": job.get("title"),
        "min": cents(r.get("min_cents")),
        "max": cents(r.get("max_cents")),
        "currency": r.get("currency_type"),
    } for r in ranges]

rows = [row for j in fde_jobs for row in to_rows(j)]

Test with the number from the docs: 5000000 divided by 100 gives 50,000.00, and 7500000 divided by 100 gives $75,000.00. If seven-figure salaries for engineering roles show up in your table, you almost certainly forgot the division.

Why keep jobs without listed salaries? Because there are more of them than you'd think. According to data compiled by Valletta Software on September 8, 2026, Palantir's Forward Deployed Software Engineer salary ranges appear on only 21 of 52 US jobs. Drop the other 31, and you won't know what share of the market your table represents.

Step 4: Write the CSV and count jobs with listed salaries

A job can have multiple salary ranges, so the number of CSV rows doesn't equal the number of jobs. Coverage must be counted per job, so your numbers can be compared with figures like "21 out of 52 jobs."

import csv
from datetime import date

with open(f"fde_pay_{BOARD}_{date.today()}.csv", "w", newline="") as f:
    w = csv.DictWriter(f, fieldnames=["title", "min", "max", "currency"])
    w.writeheader()
    w.writerows(rows)

covered = sum(1 for j in fde_jobs if j.get("pay_input_ranges"))
print(f"{covered}/{len(fde_jobs)} 个岗位标明了薪资范围")

Check: open the file and read a few rows, then compare the job count printed here with the result from step 2. The filename includes the scrape date, because salary ranges change and your table is only accurate at the moment it runs.

How do you know the table is right?

Compare it with publicly known salary ranges. Again according to Valletta Software's September 8, 2026 data, here are three benchmarks:

CompanyBase salary rangeNotes when comparing
Anthropic$280,000 to $320,000Roles located in New York, San Francisco, Seattle
OpenAI$185,000 to $300,000Equity exists beyond the range
Palantir$125,000 to $200,000Equity and bonus not included in the range

If your table differs wildly from these benchmarks, suspect your filter or the division before suspecting the market. The last column also reminds us of something often overlooked: these are base salaries, not total compensation. Comparing Palantir's median ($162,500) with OpenAI's median ($242,500) without mentioning equity is a flawed comparison.

The most common mistakes

The most common mistake is forgetting

pay_transparency=true

and then concluding that the company doesn't disclose salaries. Next come forgetting to divide by 100, averaging different currencies in the same column, and treating jobs without salary ranges as having a salary of zero.

A subtler mistake is calling the API repeatedly in a loop with no termination condition. An API that doesn't require a key doesn't mean you can call it freely; for a salary table, running it once a day is enough.

How do you use this skill on-site with customers?

Imagine your first week at a logistics customer: you need to pull order data from a system you've never seen. The steps are almost identical: make one request, print the structure, confirm the units (cents or dollars, seconds or milliseconds), and then, before building any dashboard, count how many records are missing key fields.

So once you've finished the table, don't just keep it to yourself. Put it on GitHub, and in the README note the data date, the percentage of postings that list salary, and the table's limitations.

Writing a line on your resume like "built a data pipeline to collect public salary ranges, normalized units, and reported the percentage of postings missing salary data" shows FDE recruiters exactly what they want to see: you can handle real, messy data and clearly state how trustworthy it is.

A salary table goes stale within weeks. The habit of printing the structure first and then counting the gaps will come in handy with every client.
