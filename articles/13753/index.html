Forward deployed engineer vs solutions architect

FDE Interview Prep · 2026-09-25 · 35 min read

Summary

This guide distinguishes the forward deployed engineer (FDE) from the solutions architect (SA) using real job postings from Anthropic, OpenAI, Google Cloud, Baseten, Databricks, AWS, Palantir and others. The decisive question: once a system is live and breaks, who writes the fix? FDEs write and maintain production code inside customer systems, going deep on one or a few customers; SAs build prototypes and proofs of concept and advise across a portfolio, usually from sales or go-to-market organizations. The article compares code type, post-launch ownership, customer depth, department, pay structure and interviews, and concludes FDE is not a promotion from SA but a choice between depth and breadth.

Key points

  • The sorting question: after launch, who writes the fix?
  • FDEs own production code and on-call; SAs ship prototypes and advise.
  • FDEs go deep on one or few customers; SAs cover a portfolio.
  • Titles are weak evidence; duties and department matter more.
  • FDE is a different bet than SA, not a higher rung.

If you are holding two postings like these, or wondering whether FDE is a real step up from , this guide is for you.

Here is the plain answer. A forward deployed engineer (FDE) writes production code that runs with or inside one customer’s systems, and answers for it after launch. A solutions architect (SA) shapes the solution, proves it with prototypes and proofs of concept, and guides others to build and run it, usually from a sales, go-to-market or field organization. The rest of this guide shows you how to tell the two apart from the posting itself, using employers’ own words, then how the interviews differ and how to move from SA to FDE. If you want the drill version first, the free lesson telling FDE apart from its neighbors runs the same tests on a different set of posting lines.

Discovery, design and customer trust belong to both roles. What differs is who writes the code that ends up running.

The one question that sorts a posting

Ask: once the system is live and something breaks, who writes the fix? If this role changes the production code (integrations, reliability, on-call), it is FDE work, whatever the title. If this role triages, coordinates or advises while someone else changes the code, it is SA work.

The title is the weakest evidence on the page. Some FDE postings carry pre-sales duties, and some architect postings ship real code. The sections below give you the lines that decide it.

Here is what that difference looks like in code. Both versions below pull support tickets from a paginated API.

SA: proves the API can answer. This is the proof of concept, and it is the right thing to write in a pre-sales week.

import requests

URL = "https://api.example.com/v1/tickets"
params = {"limit": 100}
tickets = []
while True:
    page = requests.get(URL, params=params).json()
    tickets += page["data"]
    if not page["next_cursor"]:
        break
    params["cursor"] = page["next_cursor"]
print(len(tickets), "tickets")

It works on a quiet afternoon. On the first 429 or 503 it dies, a rerun starts again from page one, and nothing is saved anywhere.

FDE: proves it keeps answering. First, one request with retries: back off on 429 and

5xx

, honor

Retry-After

when the API sends it in seconds, add , and fail loudly on any other error.

import json, random, sqlite3, time, requests

URL = "https://api.example.com/v1/tickets"

def get(params, tries=6):
    for n in range(tries):
        r = requests.get(URL, params=params, timeout=10)
        if r.status_code != 429 and r.status_code < 500:
            r.raise_for_status()  # other 4xx: fail loudly
            return r.json()
        wait = r.headers.get("Retry-After", "")
        wait = int(wait) if wait.isdigit() else min(2 ** n, 30)
        time.sleep(wait + random.random())  # jitter
    raise RuntimeError(f"gave up after {tries} tries: {params}")

Then the sync itself. Each page’s rows and the cursor after them commit in one transaction, and the insert is an upsert keyed on the ticket id, so a crashed run resumes from the last saved page and a replay changes nothing. Every page writes one structured log line.

db = sqlite3.connect("sync.db")
db.execute("CREATE TABLE IF NOT EXISTS tickets"
           " (id TEXT PRIMARY KEY, body TEXT)")
db.execute("CREATE TABLE IF NOT EXISTS checkpoint"
           " (k TEXT PRIMARY KEY, cursor TEXT)")
row = db.execute("SELECT cursor FROM checkpoint").fetchone()
cursor = row[0] if row else None
while True:
    page = get({"limit": 100} | ({"cursor": cursor} if cursor else {}))
    cursor = page["next_cursor"]
    with db:  # rows and cursor commit together, or not at all
        db.executemany(
            "INSERT INTO tickets VALUES (?, ?) ON CONFLICT(id)"
            " DO UPDATE SET body = excluded.body",
            [(t["id"], json.dumps(t)) for t in page["data"]])
        db.execute("INSERT OR REPLACE INTO checkpoint"
                   " VALUES ('tickets', ?)", (cursor,))
    print(json.dumps({"event": "page_synced",
                      "rows": len(page["data"]), "cursor": cursor}))
    if not cursor:
        break  # done: the next run starts a fresh pass

We ran both against a fake API that returns a 429 or a 503 every few calls. The proof of concept died on its third request. The production version finished; killed halfway, it resumed from its saved cursor, and a second full run left the row count unchanged. The sentence to say aloud in an interview is: “My proof of concept showed it could work; the production version is the one I was paged for.” The flaky API integration question asks you to build exactly this under interview conditions.

How many customers

The second thing that separates the roles is depth against breadth. An FDE goes deep on one customer, or a few; an architect covers many. The AWS Sr FDE “embeds directly inside a strategic enterprise customer”. Source 12Sr Forward Deployed Engineer, AWS Forward Deployed Engineering - Job ID: 10517491PublisherAmazon.jobsSource typecompany job posting Palantir describes its FDEs’ focus as “one customer, many capabilities”. Source 13Dev versus Delta: Demystifying engineering roles at PalantirPublisherPalantir BlogSource typecompany blogSource 14A Day in the Life of a Palantir Forward Deployed Software EngineerPublisherPalantir BlogSource typecompany blog OpenAI’s Applied AI Architect, by contrast, is the technical owner for a named portfolio of customers. Source 15Applied AI ArchitectPublisherOpenAI (Ashby)Source typecompany job posting

Colin Jarvis, who leads forward deployed engineering at OpenAI, said on a South Park Commons panel in May 2026 that OpenAI’s FDE unit works only about 10 engagements at a time and has to say no more often than yes, and he described solutions architecture as the post-sales “scale motion” for the wider market. Source 16The Future of Forward Deployed Engineering | OpenAI, Ramp, Nominal, DatalandPublisherSouth Park Commons (YouTube)Source typerecorded talk or interview

That is the honest answer to “is FDE a step up?”: it is a different bet, not a higher rung. The SA’s leverage is breadth: many accounts moving at once. The FDE’s leverage is depth: one system that has to work. Choose the kind of leverage you want.

Try it on five real lines

Here are five lines from real postings. Before you read the answers, say for each one: FDE, SA, or neither? If you are listening, pause here.

  • “This is not a demo role. You are responsible for systems that work in the real world.”
  • “This role is not demo support.”
  • “Unlike traditional advisory roles,” you will “code, debug, and jointly ship” solutions “directly within the customer’s environment”.
  • “You still write code”, on a posting that states its pay as on-target earnings.
  • “A product-focused, quota-carrying technical sales role.”

The answers, and the words that decide them:

  • FDE. Cursor’s FDE postings. Source 7Forward Deployed EngineerPublisherCursor (Ashby job board)Source typecompany job board The second sentence decides it, not “not a demo”: “responsible for systems that work in the real world” is a running system the role answers for.
  • SA, and this is the trap. Modal’s Solutions Architect posting says it, then calls itself “a strategic, consultative position”. Source 26Solutions Architect @ ModalPublisherModal (Ashby)Source typecompany job posting If the first line taught you that “not a demo” means FDE, the second shows why it doesn’t: a keyword can rule a role out, but it rarely rules one in. Read the next sentence.
  • FDE. Google Cloud’s GenAI FDE postings. Source 4Forward Deployed Engineer IV, GenAI, Google Cloud — Google CareersPublisherGoogleSource typecompany job posting The line names the role it is not (“advisory”) and the verbs it is: code, debug, ship, inside the customer’s environment.
  • FDE. Okta’s Principal FDE. Source 24Principal Forward Deployed Engineer - Okta for AI AgentsPublisherOkta (Greenhouse)Source typecompany job posting The pay line looks like sales, but “you still write code” is the duty, and duties beat the pay line.
  • Neither: closer to sales than to either. Ramp’s AI Solutions Engineer is a quota-carrying technical sales role, not a forward deployed engineering one. Source 28Ramp Ashby job board (AI Solutions Engineer)PublisherRamp (Ashby job board)Source typecompany job posting “Quota-carrying” is the deciding word, and near-miss titles like this one are why you read past the title.

If you got all five, you have the method: find the duty that decides it, read the sentence after any slogan, and let the duty outrank the title and the pay line. Telling FDE apart from its neighbors has another set to practice on, with a trap of its own.

Moving from SA to FDE

As a solutions architect, you already have half of the FDE job. You run discovery, handle stakeholders and design under constraints. Here is our plan for closing the gap. It is our method, not something interviewers publish.

  • Build one thing end to end, and run it. Pick the version your target employers would recognize, deploy it, write tests, and keep it running for a few weeks. This becomes your production story.
    • Aiming at AI labs and AI product companies: an LLM triage service over an exported support-ticket queue, with an eval set of 50 labeled tickets, retries, request tracing and a cost-per-ticket log. The number to quote is how many eval tickets it labels correctly, before and after your last change.
    • Aiming at enterprise software and data companies: an incremental sync from a paginated API into a warehouse, with a cursor checkpoint, an idempotent 
      MERGE
      , a row-count reconciliation against the source and a one-page runbook. The number to quote is rows reconciled per day, and how long it has run without a mismatch.
  • Practice timed coding weekly. Architects rarely code against a clock. Rehearse practical builds and debugging, not just puzzles, and say your reasoning out loud as you go.
  • Rewrite your stories from “recommended” to “shipped”. The verbs carry the evidence. “I designed the reference architecture and the customer’s team built it” is SA evidence. “I wrote the ingestion service, rolled it out behind a flag and was paged when the upstream API changed” is FDE evidence. Use the second kind wherever it is true.
  • Prepare the “why leave SA?” answer. Keep it about the work, not the title, as in the callout below: what you handed off, and what you want to own.
  • Consider a bridge role. Some applied AI engineer and post-sale architect roles carry more code than a pre-sales SA seat. OpenAI’s Applied AI Engineer, for one, works hands-on in code to build prototypes, evaluation harnesses, integrations and production accelerators. Source 29Applied AI EngineerPublisherOpenAI (Ashby)Source typecompany job posting Time in a role like that gives you production stories to bring to an FDE loop.

Words you can use: an illustrative answer

The story is invented to show the shape, including the side project from step 1. Tell yours from your own work.

“As an SA at a data-integration vendor, I scoped a ticket sync for a logistics customer and built the proof of concept. Their team took it to production, and a month later their dashboards were double-counting tickets: when the vendor’s API failed mid-run, the job restarted from page one and inserted everything again. I could see the cause, but the fix wasn’t mine to ship. So I built the production version myself: a sync from a paginated API into Postgres that saves its cursor with each page, upserts on the ticket id so a replay changes nothing, and backs off on rate limits. I’ve run it nightly since the spring. It paged me once, when the vendor changed a field from a string to a list, and I added a check that sets bad rows aside instead of failing the run. That’s the part I want to own as an FDE: not the diagram, the system that pages you.”

If they ask “What would you do differently?”: “I’d build the reconciliation first, a nightly count of source rows against target rows. The customer’s double-count sat in their numbers for days before anyone noticed, and a count check would have caught it on the first night. Now it’s the first thing I write.”

Two answers to avoid: “SA was too salesy” and “I want to be more technical”. The first sounds like you are avoiding customers, and this page has shown that some FDE roles carry pre-sales work too. The second names no work; say what you want to own instead.

Then back it with one story from your own work. A project you owned end to end and working inside a customer’s environment are the two questions an SA’s history is most likely to be probed on, and both are free to practice. The bridge story lesson shows how to connect your past work to the FDE job in two minutes.

Which role should you apply for?

Answer these about yourself before you pick a posting.

FDE or SA: a self-check

  • Do you want to be the person paged when the system you built breaks at a customer site?
  • Would you rather write the integration yourself than review someone else’s?
  • Can you pass a timed coding round today, or within a few weeks of practice?
  • Do you enjoy one customer’s messy environment more than many customers’ clean demos?
  • Are you comfortable with duties that may include some pre-sales work, even on an FDE title?

Mostly yes: aim at FDE postings, and use the tests above to confirm each one is really FDE work. Mostly no: an SA or applied AI architect role may suit you better, and it is a respectable job in its own right, not a lesser one. Mixed: look at the hybrid titles, and ask each recruiter who writes the fix after launch.

The three questions to ask on any recruiter call, whichever title you apply for:

  • “After launch, who is on call for what I build?”
  • “Who does this role report to, and what number is that person measured on?”
  • “If part of the pay is variable, what is it measured on: bookings, renewals, delivery milestones or company results?”
