Testability and Dependency Injection

FDE Interviews · 2026-06-14 · 1 min read

Summary

This lesson from FDE Interviews explains why code that directly reaches the clock, network, filesystem, or random generators can't be tested deterministically: its output depends on the outside world. The recommended fix is separating pure logic from side effects and injecting the world-touching dependencies so tests can substitute fakes. For inherited untestable code, it advises writing characterization tests to pin current behavior first, then refactoring under that safety net. The page also links related course lessons and practice exercises.

Key points

  • Non-deterministic dependencies (clock, network, I/O, randomness) make code hard to test.
  • Separate pure logic from side effects and inject external dependencies.
  • Tests pass fakes for injected dependencies to stay deterministic.
  • Refactor legacy code under characterization tests that pin existing behavior.
  • Includes related course lessons and coding practice exercises.

Code that reaches out to the clock, the network, the filesystem, or a random generator cannot be tested deterministically, because its output depends on the world. The fix is to separate pure logic from side effects and inject the things that touch the world (the clock, I/O, randomness) so a test can pass fakes. When you inherit untestable code, pin its current behavior with a characterization test first, then refactor under that net.
