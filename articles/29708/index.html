DataHub vs. Atlan: How FDEs Inventory Customer Data

Original title: DataHub 与 Atlan 对比：FDE 如何盘点客户数据

FDE Times · 2026-10-08 · 5 min read

Summary

This article compares DataHub and Atlan through the lens of a forward deployed engineer's first week at a customer site. DataHub has an Apache 2.0 open-source core that can be self-hosted, while Atlan is proprietary SaaS with unpublished pricing; both offer 80+ connectors, so the choice depends on the customer's existing setup. The author argues that ingesting sources is the easy part—real value comes from assigning ownership, tagging PII, and classifying sensitivity. In a retailer example, only 12 of 40 order-related assets had known owners. Two common mistakes: ingesting all sources before agreeing on scope, and tagging PII without owners. The conclusion: governance must come before building agents, or rework follows.

Key points

  • DataHub is open-source and self-hostable; Atlan is proprietary SaaS with no public pricing.

  • FDEs should establish ownership and classification before letting agents read data.

Key takeaways

  • DataHub's open-source core is Apache 2.0 licensed and can ingest metadata via UI or CLI; Atlan is proprietary SaaS with unpublished pricing.
  • Both offer 80+ connectors; choosing between them usually comes down to whether the customer wants to self-operate or buy something ready-made.
  • Connecting data sources is the easy part; the real value lies in assigning owners, tagging PII, and classifying sensitivity levels.

Atlan's documentation promises that platform setup, connecting your first data sources, and learning the basic concepts take just "a few minutes." That's the vendor's claim, and for the technical connection step, it may well be true.

But any Forward Deployed Engineer (FDE) who has just arrived at a new customer site knows those few minutes don't answer the real first-week questions: which tables are trustworthy, who owns them, and which columns contain personal information.

That's exactly why data catalogs are worth learning. When you're building agents or data pipelines on customer data, the costliest mistakes are rarely in the model—they're using the wrong table, or sending sensitive data somewhere it shouldn't go.

DataHub and Atlan represent two different paths: one has an open-source core, the other is proprietary SaaS. Understanding what they can do—especially the order in which to use them—lets you map out the customer's entire data landscape within the first week.

Two tools, two paths to the same map

DataHub positions itself as a context management platform for AI and data, integrating discovery, governance, and observability across the entire data stack. Atlan calls itself the "context layer" for AI, linking data to business definitions and access policies.

On connectors, Atlan's documentation claims support for 80+ data sources; the independent comparison site Modern DataTools rates them as evenly matched, each with 80+. The real difference is in deployment model.

DataHub

  • Open-source core, Apache 2.0 license
  • DataHub Core is free; DataHub Cloud targets enterprises
  • Self-hosted or managed service
  • Ingest metadata via UI or CLI

Atlan

  • Proprietary SaaS
  • Unpublished pricing
  • Core capabilities: cataloging, governance, lineage, quality, glossary

So when you arrive on site, the first question isn't which tool is better—it's what state the customer is in. If the customer has an infrastructure team and wants everything to stay within their own network, self-hosted DataHub is the natural choice. If the customer already bought Atlan, your job is to master the existing tool, not to talk them into switching.

What does the first week with a data catalog look like?

Suppose a retailer needs an agent that can answer questions about orders. It has a data warehouse, a few dashboards, and a raw folder nobody remembers who built. The top priority on day one is connecting these data sources to the catalog—before writing a single line of prompt.

With DataHub, you can quickly load metadata through the UI, or use the CLI so the configuration can be saved, reviewed, and re-run. On site, the latter is more valuable because it leaves a record for whoever takes over.

Once metadata is ingested, the most useful tool is the search box. DataHub searches across the entire ecosystem, including dashboards, datasets, ML models, and raw files. Type "order" and you see, for the first time, everywhere the concept of "orders" appears—not just the one table the person onboarding you happened to mention.

A small calculation that reveals the real workload

Suppose the search returns 40 order-related assets. You ask around and can only confirm owners for 12 of them. The remaining 28—70%—are data with no owner. That's the number you bring to the end-of-week meeting.

DataHub supports defining ownership within the catalog and tracking PII. So the next step is assigning owners to the 12 known assets, then tagging columns containing personal information, such as names, phone numbers, and shipping addresses.

Next comes classification. Palo Alto Networks defines data classification as organizing data by sensitivity, importance, and predefined criteria. Common levels are public, internal use, restricted, and confidential.

Applied to this example: the product catalog table might be internal use, while the customer table holding phone numbers is clearly restricted or confidential.

Two mistakes that derail the first week

The most common mistake is ingesting all data sources before agreeing on scope with the customer. With 80+ connectors, this is very easy to do, but stuffing the catalog with metadata unrelated to the order questions only makes search results noisier—and you might touch systems the customer never authorized you to see.

Before the first ingestion, confirm the data source list in writing.

Another mistake is tagging PII without assigning a specific owner. If a column is marked as a phone number but nobody owns it, then when the agent needs read access, no one has the authority to approve or deny it. So in the example above, assigning owners comes before tagging PII.

The hard part is something no data catalog can do for you

The first limitation is the promise of speed. Atlan's "a few minutes" is the vendor's claim about the connection step. Assigning owners requires someone to answer questions—no tool can know on its own who should own an anonymous raw file.

The second limitation is how to think about AI context. In an April 2026 blog post, DataHub argued that the semantic layer is necessary but not sufficient; agents also need lineage, ownership, data freshness, and access permissions. The post also argued that governance is not a feature to bolt on afterward.

That's the view of a company selling a data catalog, so it has its own motives, but the working order it recommends matches what happens in real deployments.

For an FDE, the conclusion is straightforward: build the agent first and ask about permissions later, and you'll be reworking the part the customer cares about most.

What to learn first, and how to present it

Start with DataHub Core, because it's open source, runs on your own machine, and requires no contract. Learn it in the order real work happens: ingest via UI first, then CLI, then search, ownership assignment, and PII tagging. Without a customer using Atlan, it's hard to get hands-on access, so at the starting stage, reading the docs and getting familiar with the concepts of glossary and lineage is enough.

When interviewing for an FDE role, you can ask one question: "At your most recent customer, who decided which tables the agent could read? Where was that decision documented?" The answer tells you whether the company treats governance as the FDE's job or someone else's.

Don't write "experience with data catalogs" on your resume—write results with numbers: how many data sources you ingested, the before-and-after percentage of assets with owners, and how many PII columns you tagged.

People who can build models are easy for customers to hire. What truly earns trust is handing over, at the end of week one, a list that clearly states which data can be safely given to the agent to read.
