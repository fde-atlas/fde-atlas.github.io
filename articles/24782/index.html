Unit testing is a test that verifies that the smallest units (units) that make up software operate according to specifications.

The definition of "smallest unit" varies depending on the programming paradigm.

Programming ParadigmExamples of Test Units
Procedural programmingFunctions, subroutines
Object-oriented programmingClasses, methods
Component-oriented (e.g., frontend)Individual components

For example, taking an EC site as an example, each function such as "calcTaxIncluded(price), which adds consumption tax to a product price and returns it" corresponds to a unit. In unit testing, you individually verify behaviors such as "whether this function correctly adds 10% to a normal price," "what happens when the price is 0," and "whether it returns an error when a negative value is input."

Note that unit testing is also called "unit testing (UT)," "component testing," or "module testing," but this article consistently uses "unit testing."

The main purposes of conducting unit testing are the following four points.

  • Early bug detection and reduced correction costs: It is known that correction costs increase exponentially the later a bug is discovered in development. By eliminating defects in the smallest units early through unit testing, you can minimize the impact on downstream processes.
  • Documenting code behavior specifications: Test code functions as documentation showing "how this unit should behave." This is useful for team handovers and code reviews.
  • Safety net for refactoring: When modifying code, confirming that existing tests pass prevents unintended changes (regressions).
  • Stabilizing integration testing and beyond: When the quality of each module is ensured through unit testing, it becomes easier to narrow down the causes of problems during integration testing.

The development process includes multiple test levels, each with different purposes and scopes.

Comparison ItemUnit TestingIntegration TestingSystem Testing
Alternative NamesUnit test / UT testIntegration test / IT testComprehensive test / ST test

In waterfall development, the "V-model" described above is a representative organizational method, but even in agile development, the approach of proceeding with tests in the order of unit testing → integration testing → system testing remains unchanged.

White-box testing is a method of designing test cases with an understanding of the module's internal structure (source code). It is called "white-box" because testing is done with the "inside" of the code visible.

In unit testing, white-box testing is the primary approach. The main testing techniques are as follows.

Testing TechniqueDescriptionUse Case
Statement Coverage (C0)Execute all statements (lines) at least onceBasic coverage verification
Branch Coverage (C1)Pass through all if/else branches at least onceProcesses with many conditional branches
Condition Coverage (C2)Cover all combinations of conditionsVerification of complex conditional logic
Path CoverageCover all execution pathsProcesses requiring high reliability

Concrete Example: When testing a function that returns a discount rate based on a user's age, branch coverage (C1) involves confirming that each of the branches "age under 18," "age 18 or over and under 65," and "age 65 or over" returns the correct value.

Black-box testing is a technique that tests a module without regard to its internal structure, focusing on inputs and outputs (behavior as seen from the outside). Test cases are designed based on specifications.

Testing TechniqueDescriptionExample
Equivalence PartitioningDivide inputs into groups that return the same result and test with representative valuesFor age input: "10-17 representative: 15", "18-64 representative: 30"
Boundary Value AnalysisFocus testing around boundaries (edge values)If the condition is under 18, check "17", "18", "19"
Decision TableOrganize combinations of multiple conditions in table formAll patterns of membership type × purchase amount × coupon application
State Transition TestingVerify state changes (such as screen transitions)Confirm transitions: login → add to cart → purchase → completion

While unit testing primarily uses white-box testing, it is common to combine it with black-box testing when verifying API inputs/outputs or supplementing specification-based tests.

In unit testing, the module under test must be isolated from other modules and tested independently. However, in real-world development, the module under test often depends on other unfinished modules, making it impossible to run tests as-is. That is where drivers and stubs come in.

Driver

  • A substitute for the upper-level module that "calls" the module under test
  • Used to pseudo-execute the functions or methods under test
  • Example: A driver program that simulates "the confirm order button was pressed" when testing a payment processing module

Stub

  • A substitute for the lower-level module that the module under test "calls"
  • Instead of a dependency module whose implementation is not yet complete, a simple program that returns fixed values is prepared
  • Example: If the inventory check module is not yet complete, use a stub that always returns "in stock: true" to proceed with testing

Modern test frameworks offer rich libraries (Mockito, unittest.mock, etc.) that can automatically generate mock objects that serve the role of stubs, greatly reducing the cost of implementing stubs manually.

The quality of unit testing is largely determined at the test case design stage. Before executing tests, organize the test basis (the documents that serve as the basis for testing).

The main documents to reference as the test basis for unit testing are as follows.

  • Detailed design document (module specification)
  • Class diagrams and sequence diagrams
  • Database definition document (to check constraints on input/output data)
  • Screen specification (for testing UI components)

When reading the test basis, the key point is to actively identify specification boundaries, exceptions, and error cases. Testing that only verifies normal cases is dangerous; test cases for semi-normal and abnormal cases are the key to quality.

A test case includes the following elements.

ItemExample Content
Test case IDTC-001
Test targetcalcTaxIncluded() function
Test categoryNormal case
Input valuesprice = 1000
Expected result1100 (10% tax included)
Actual result(filled in after test execution)
VerdictPass / Fail
NotesConfirm rounding down of decimal fractions

Practical tips for creating test cases are as follows.

  • Design normal, semi-normal, and abnormal cases without omission: Include not only normal cases (valid inputs) but also boundary values, zero values, null, empty strings, values exceeding the maximum, etc.
  • One test case = one verification point: Trying to verify multiple things at once makes it difficult to identify the cause when debugging
  • Fix test data: When depending on external environments (DB, date/time, etc.), use mocks to maintain test reproducibility

The unit testing workflow is as follows.

  • Build the test environment: Set up the test framework and test DB, prepare drivers and stubs
  • Execute tests: Run according to the test cases; if automated, run in bulk
  • Record results: Record Pass/Fail; for Fail, record reproduction steps, expected values, and actual values in detail
  • Register bugs: Register bugs in an ITS such as Jira or Redmine, noting the assignee, priority, and reproduction conditions
  • Fix and retest: After fixing the bug, rerun the relevant test cases and also check for side effects of the fix (regressions)

The key points in bug management are "clarifying reproduction steps" and "recording the scope of impact". Even for bugs found in unit testing, check whether they affect other modules and add related test cases as needed.

Code coverage (test coverage) is commonly used as the completion criterion for unit testing.

Coverage TypeWhat Is MeasuredTypical Target Guideline
C0 (statement coverage)Percentage of executed statement lines80-90% or more
C1 (branch coverage)Percentage of executed branches70-80% or more
C2 (condition coverage)Coverage rate of condition combinationsSet as needed for high-reliability systems

However, aiming for 100% coverage is not necessarily the right answer. Trying to cover even areas with low cost-effectiveness for testing, such as simple getter methods or constant definition files, leads to enormous testing effort. In practice, it is important to also adopt the concept of "risk-based testing," which prioritizes covering high-risk business logic.

① Cost Reduction Through Early Bug Detection

The later in the development process a bug is found, the higher the cost of fixing it. According to IBM research, a fix cost estimated as 1 at the requirements definition stage becomes 15x at the testing stage and over 100x after release. Since unit testing is performed alongside or immediately after coding, bugs can be eliminated at the stage where fix costs are lowest.

② Easy identification of problem areas

Because testing is done at the module level, when a test fails you can pinpoint exactly "which process in which module" has the problem. Bugs discovered during integration testing often take time to diagnose, but if bugs are eliminated beforehand through unit testing, integration testing proceeds smoothly.

③ A safety net for refactoring and maintenance

When modifying code, unit tests function as a "certificate of operation." By confirming that all tests pass after refactoring, you can prevent unintended side effects from changes. In particular, for maintenance of long-running systems, the presence of tests directly affects maintenance efficiency.

④ Test code serves as documentation

Well-written test code is living documentation showing "how a module should behave." It also helps with onboarding new team members and reduces communication costs for confirming specifications.

① Burden on development effort

Creating and maintaining unit tests requires considerable effort. Test cases must be updated every time the code changes, so the larger the project, the more maintenance costs accumulate. If effort is not estimated properly, it can become a cause of project delays.

② Unit testing alone cannot guarantee quality

Unit testing merely confirms that "each module works correctly on its own." Aspects such as inter-module coordination, data passing, performance, and security must be verified through integration and system testing. You should be aware that bugs can still occur in production even when unit tests pass.

③ Management costs for drivers and stubs

The larger the project, the greater the cost of creating and managing drivers and stubs. In long-running projects in particular, drivers and stubs must be updated to keep up with code changes, making management more complex. It is important to make use of mock libraries and establish automation mechanisms.

There are limits to performing unit tests manually. Manually running dozens or hundreds of test cases every time the code changes is unrealistic, and agile and sprint development in particular require "running tests multiple times a day."

By incorporating unit test automation into a CI/CD (Continuous Integration/Continuous Delivery) pipeline, you gain the following benefits.

  • Tests run automatically every time code is pushed to the repository
  • Test failures are detected immediately, reducing the risk of problematic code reaching production
  • Test results are automatically notified via Slack or email and can be shared with the whole team

[Basic CI/CD Pipeline Flow]

Push code (GitHub, etc.)

CI/CD tool is triggered (GitHub Actions / Jenkins / CircleCI, etc.)

Test framework runs automatically (JUnit / pytest / Jest, etc.)

Test results are output as reports and notified via Slack

Pass: proceed to the next step (build, deploy)

Fail: error notification, merge stopped

A simple pytest example (Python)

# Target code

def calc_tax_included(price: int) -> int:

return int(price * 1.1)

# Test code (pytest)

def test_normal():

assert calc_tax_included(1000) == 1100

def test_zero():

assert calc_tax_included(0) == 0

def test_boundary():

assert calc_tax_included(1) == 1 # Verify that decimals are truncated

When introducing unit test automation from scratch, we recommend proceeding step by step using the following steps.

  • Select the highest-risk modules in the existing project: Don't try to automate everything; start with the core parts of the business logic
  • Choose one test framework and set up the environment: Pick a framework suited to the team's primary language and get one sample test running
  • Integrate with CI/CD tools: Use GitHub Actions or similar to set up a mechanism that runs tests automatically on push
  • Establish code review rules: Instill in the team the rule that "new code must always come with test code"
  • Measure coverage and set goals: Visualize coverage with measurement tools (JaCoCo, pytest-cov, etc.) and raise it gradually

A pitfall to watch out for is that in the early stages of introducing test automation, "test code maintenance can fall behind"—a situation that often occurs in the field. Tests are not something you write once and finish; the whole team must share the awareness that they need to be continuously updated and maintained in line with code changes.

As of 2026, AI-generated test code using generative AI is rapidly permeating development sites. According to forecasts by the US research firm IDC, tools using generative AI are expected to handle about 70% of all software testing by 2028.

The main scenarios where generative AI is used in test development are as follows.

Use caseDescription
Initial generation of test codeAutomatically generates test case templates using existing production code as input
Improving test case coverageSuggests boundary values and edge cases that humans tend to overlook
Automatic generation of test dataGenerates diverse test data simply by instructing in natural language, e.g., "Generate 10 valid input patterns"
Refactoring existing testsSuggests improvements for test code with poor readability
Analyzing causes of test failuresFeeds error messages and code to identify failure causes and propose fixes

One of the most widely used AI test code generation tools today is GitHub Copilot.

Basic workflow for generating test code with GitHub Copilot

  • Open the code file to be tested in your IDE
  • Enter the /tests command in the Copilot chat, or send a prompt
  • Copilot automatically generates a test code template (including describe blocks, mock initialization, and expect syntax)
  • Review and modify the generated code, then run the tests

Example prompt (for Python × pytest):

"Please create a comprehensive unit test suite for the calcTaxIncluded function using pytest.

Include normal cases, edge cases (0 yen, negative values), and exception handling."

Key points when using ChatGPT or Claude:

To get generative AI to produce better test code, prompt quality is crucial. Accuracy improves by explicitly specifying the following elements.

  • Paste the code of the function or class to be tested
  • Specify the name of the test framework to be used (JUnit 5, pytest, etc.)
  • Specify the scenarios to be tested concretely (normal cases, error cases, boundary values)
  • Communicate any dependencies that need to be mocked

According to field reports, generative AI "suggests edge case test cases that would normally not be written," and there is a growing voice that this leads to improved test coverage. On the other hand, for conditions closely tied to complex business logic or business specifications, using AI suggestions as-is can cause discrepancies with the specifications, so review by the engineers themselves is essential.

Generative AI is a powerful tool for streamlining unit testing, but it is not all-powerful. The points engineers must always review and supplement are as follows.

  • Verifying consistency with business specifications: AI does not directly reference specification documents, so it may incorrectly design error cases based on business rules (e.g., "0 yen is a normal value in this industry")
  • A test passing is not the same as the test being correct: Even if AI-generated tests run and succeed, the testing perspective itself may be wrong (e.g., "a test that just always returns true")
  • Consideration for security and privacy: Inputting production data or highly sensitive code directly into AI tools can pose a security risk
  • Complex state management and asynchronous processing: Testing distributed systems and complex asynchronous processing tends to reduce AI generation accuracy

The optimal approach in 2026 is a division of roles where generative AI is used as "a subordinate who writes test code," while humans are responsible for test design policy and final quality decisions.

Engineers with unit test design and automation skills are in extremely high demand in the freelance market. This is driven by the following market trends.

  • Shortage of QA and test engineers: As software grows larger and more complex, quality assurance specialists are chronically in short supply
  • Spread of agile development and DevOps: Engineers who can integrate testing into CI/CD pipelines are highly valued for skills that directly serve modern development organizations
  • Rising value of "test design ability" in the age of generative AI: Now that AI can generate test code, the value of humans who can "properly evaluate and design" it has instead increased

According to multiple surveys, the average monthly rate for freelance test engineers and QA engineers is around 530,000 to 780,000 yen. However, positions that "only execute tests" tend to have lower rates, and the key to commanding high rates is upstream capability: being able to handle everything from test planning through automation promotion to quality improvement proposals.

To win high-rate freelance projects with testing and quality assurance skills as your weapon, the following strategies are effective.

1. Shift your skills from "executor" to "proposal-driven QA"

People who can do more than simply execute tests—those who can "formulate test design policies," "drive the introduction of test automation," and "establish and improve quality metrics"—are treated by clients as "QA consultants," dramatically increasing their rate negotiation power.

2. Build a portfolio showcasing generative AI usage

By presenting a portfolio of "achievements in generating, reviewing, and improving test code using generative AI such as GitHub Copilot and Claude," you can position yourself as a rare talent that matches current market needs in 2026.

3. Accumulate CI/CD integration experience

Experience connecting unit tests with CI/CD tools such as GitHub Actions, Jenkins, and CircleCI is an important skill that earns recognition as a "DevOps-capable engineer." You can build this track record even through side projects and personal development projects.

4. Deepen quality knowledge in a specific domain

Domains where mistakes are unacceptable, such as finance, healthcare, and automotive (in-vehicle systems), tend to command higher rates because they require test plans based on specialized knowledge. Specializing in an area that leverages your own background is a shortcut to high rates.

5. Make use of freelance agents

Specialized projects in test automation and QA tend to be introduced more often through freelance agents than through general job sites. It is important to register with multiple agents and clearly communicate your skill set and desired rate.

Engineers with the "three-layer skill stack" of unit testing, test automation, and generative AI usage are extremely rare and valuable in the 2026 freelance market. People who can handle everything from quality assurance in the development phase to CI/CD operations and efficiency improvements using generative AI can realistically target projects paying over 1 million yen per month.

Engineers and PMs currently working in quality assurance or test automation as full-time employees may be able to significantly increase their income by going freelance. Start by assessing your own market value.
