Week 10: Freeze the evals contract before tuning RAG

Original title: 第 10 周：在调优 RAG 前冻结评测合同

FDE 成长手册 · 2026-08-25 · 9 min read

Summary

This is week 10 of an FDE training handbook, arguing that an eval contract must be frozen before tuning any RAG candidate. Evals are decision contracts, not question banks: before seeing results, you must specify what decision the eval supports, which user tasks to cover, what counts as a correct answer or refusal, which failures are hard gates, the baseline, and the action taken on failure. Using a fictional company (北辰协作) as teaching material, it shows a complete 60-case eval set split 36/12/12 across development, calibration, and holdout, covering answerable, no-answer, conflicting, outdated, and permission-restricted slices. Permission leaks must be hard gates that averages cannot offset. It ends with a five-day implementation path and common failure recovery patterns.

Key points

  • Freeze decisions, hard gates, and failure actions before running candidates.
  • 60 cases split 36/12/12 into dev, calibration, and holdout sets.
  • Cases must cover refusals, conflicts, outdated sources, and permissions.
  • Permission failures are hard gates, not offsettable averages.
  • Holdout sets run once; modifying the system invalidates them.

Direct answer: Formal evals must be written down before looking at candidate results: what decision these results will support, which user tasks must be covered, what counts as a correct answer or correct refusal, which failures stop everything immediately, what the baseline is, and what action to take when results fall short. Week 10 is not about writing three questions for the model; it is about freezing a versioned eval contract and at least 60 representative cases, so that later RAG (Retrieval-Augmented Generation) candidates cannot win by cherry-picking questions or lowering the bar after the fact.

Why an FDE writes the "failure contract" first

Heading "Why an FDE writes the "failure contract" first"

Business leaders care about whether to keep investing; frontline staff care about when the system is trustworthy and when it must stop; engineering teams care about where failures occur. A single overall "accuracy" number cannot answer all of these questions at once.

业务决定与风险  → 一线任务、角色和异常  → 可检查的案例与标准答案  → 指标、切片、门槛和失败动作  → 第 11 周检索比较  → 第 12 周回答、引用、拒答和阶段决定

Week 10 may only use the corpus and ACL frozen in Week 9. If writing the evals reveals that a gold source is missing or conflicting, a new corpus version must be created; you cannot silently change documents behind the dataset.

The decision Beichen Collaboration must support this week

Heading "The decision Beichen Collaboration must support this week"

All companies, cases, numbers, thresholds, and results below are instructional simulation material.

This week Beichen is not deciding on a production launch, but pre-registering:

Within the frozen corpus and role scope, is the RAG candidate worth entering a controlled, read-only internal comparison; or should we keep the Week 8 deterministic baseline, narrow the scope, gather more evidence, or stop?

Unacceptable failures include:

  • A regular customer service candidate or answer surfacing supervisor-restricted facts;
  • Giving a seemingly confident answer when sources are missing, conflicting, or outdated;
  • Citations that exist but do not support the key conclusion;
  • Model output bypassing frontline confirmation and changing business state;
  • Deleting hard cases or lowering the bar after the fact to let a candidate pass.

Minimal mental model: evals are not a question bank, but a decision contract

Heading "Minimal mental model: evals are not a question bank, but a decision contract"

要作的决定  → 代表性案例  → 可核对的期望结果  → 分层指标  → 看结果前确认的门槛  → 失败后动作
ConceptNaive meaning in this lessonCommon misconception
Development setCases you may inspect and use to diagnose the implementation"The data used to train the model"
Calibration setCases used to check labels, scoring, or a one-time stage comparisonA second development set for endless parameter tuning
Holdout setExpected answers not viewed before the system is frozen; supports the final decisionLooking at results first, then picking the best run
Gold sourceThe authoritative source that confirms what is requiredThe document the model most likes to cite
Hard gateBlocks the current scope if any failure occursA deduction item offset by overall averages
SliceA subset reported separately by role, task, or riskA label shown only in an appendix

Decision rule: If a metric has no corresponding action when it fails, it is just a number; if a hard gate can be modified after seeing results, it is not a hard gate.

Complete example: from decision to failure action

Heading "Complete example: from decision to failure action"

1. First write what decision the eval supports

Heading "1. First write what decision the eval supports"

Beichen completed example:

- 决定：是否允许一个只读 RAG 候选进入后续受控比较- 比较对象：第 8 周确定性政策候选工作台- 用户与任务：普通客服核对指定计费政策，最终仍由人确认或升级- 不包含：自动回复、退款批准、模型上下文协议（MCP）、真实生产流量- 决策人：课程模拟业务负责人- 数据边界：northstar-corpus-teaching-v1，仅合成材料

2. Construct cases from task variations, not 60 random questions

Heading "2. Construct cases from task variations, not 60 random questions"

First list the task dimensions from upstream evidence:

DimensionBeichen controllable variations
User roleRegular customer service, supervisor, unknown role
Source statusCurrent, missing, conflicting, outdated, restricted
Task conditionsRegion, effective date, regular/special task
PhrasingFormal terminology, common customer service phrasing, missing required conditions
Expected actionAnswer, refuse, request more information, escalate

Generate candidate rows from these dimensions according to the count matrix above, then verify each one against sources and permission rules. The holdout set must not be stuffed with near-paraphrases; cases with the same source, task, and answer differing by only a few words should be treated as near duplicates.

This page does not provide a downloadable 60-case file. You need to write your own synthetic or approved cases in JSONL, CSV, a database table, or another versionable format. The format may vary, but no evidence field may be omitted.

3. Pre-register layered metrics

Heading "3. Pre-register layered metrics"

Week 10 only defines them; the RAG candidate is not run:

LayerMetric questionDenominatorAction on failure
CorpusDo required formal sources exist, are they current and accessibleNumber of applicable casesReturn to Week 9; do not tune retrieval
RetrievalDoes the gold source enter the allowed top-k candidatesNumber of answerable casesCheck ACL, recall, and ranking
AnswerAre required facts supported, and are forbidden facts absentAnswered cases / atomic factsBlock, fix generation or citations
RefusalDoes it stop safely when there is no answer, conflict, outdated info, or no permissionNumber of cases that should refuse or escalateNarrow scope or stop
End-to-end taskAre output state, sources, permissions, and frontline next steps all correct at onceAll applicable casesKeep the baseline or restrict experiments
ConstraintsAre latency and cost per successful task within the Brief budgetFixed eval runNarrow, switch approach, or stop

For the course's fixed cases, hard gate examples can be pre-registered as follows:

  • In the 10 permission-restricted cases, the restricted candidate or forbidden facts have 0 observations; this only describes this sample's threshold and does not prove leakage will never occur.
  • No-answer, conflict, and outdated cases must not yield seemingly definitive internal policy conclusions.
  • Citations must actually support the key facts; it is not enough to merely "have a link."
  • The number of unauthorized business effects produced by model output is 0.
  • Latency and cost use the course's simulated budget from the Brief; do not fill in numbers after the fact.

4. Run the deterministic baseline first

Heading "4. Run the deterministic baseline first"

Have the Week 8 system produce standardized results on the same applicable cases:

{  "case_id": "NS-ACL-03",  "baseline_release": "northstar-teaching-w08-r0",  "actual_state": "escalate",  "visible_document_ids": [],  "business_effects": 0,  "correlation_id": "teaching-baseline-run-003"}

The deterministic baseline may not generate natural language answers, but it is still the comparison target: candidates must not break permissions, status, or frontline verification points just to make the copy more fluent.

5. Freeze the holdout set rules

Heading "5. Freeze the holdout set rules"

If you are learning alone and cannot truly keep the answers hidden from yourself, you can:

  • First save only the holdout set inputs and checksums;
  • Put the expected answers in a separate location that is not opened for now;
  • Freeze the system manifest before unsealing;
  • Run it only once and disclose that "self-sealing does not equal an independent blind test."

Once you modify the system based on holdout set results, the original holdout set is invalidated. Keep the results and create a new data version; you cannot delete the hard cases and continue claiming a blind test.

Acceptance gates

Heading "Acceptance gates"

  • The decision, comparison baseline, user task, non-goals, and final decision-making role are explicit;
  • Metrics, thresholds, exclusion rules, and failure actions are frozen before running the RAG candidate;
  • The dataset has 36 development, 12 calibration, and 12 holdout cases, 60 in total;
  • The overall set includes 24 answerable, 10 no-answer, 8 conflict, 8 outdated, and 10 permission-restricted cases;
  • Both the calibration and holdout sets include permissions, plus conflict or outdated slices;
  • Each case records the role, corpus version, gold source, required facts, forbidden facts, expected status, risks, and sources;
  • No near-duplicate leakage across splits; cases already seen cannot continue to be labeled as holdout;
  • Conflicts or insufficient evidence can be marked as unknown; do not force an answer just to feel complete;
  • Permissions and key facts prioritize deterministic or manual rules; the model scorer is not the sole arbiter;
  • Deterministic baseline results save per-case outputs and the exact release;
  • All numbers have denominators, slices, time windows, or version sources;
  • The course quantities and thresholds are not written as industry standards, customer commitments, or production gates.

Independent transfer: supply chain ETA evals contract

Heading "Independent transfer: supply chain ETA evals contract"

Do not run the model. Based on the SOP from the Week 9 transfer, add six complete cases:

  • Two answerable, one of which uses common on-site phrasing;
  • One with no reliable source;
  • One where two current sources conflict;
  • One with only outdated sources remaining;
  • One where the outsourced role has no permission.

For each, write the gold source, required/forbidden facts, expected status, and failure action. Then answer: which one must become a hard gate? Why can't it be offset by overall averages?

View the answer checkpoints

  • The no-permission case should at least block restricted candidates and forbidden facts; passing the sample does not mean leakage never occurs.
  • The correct status for a conflict case is usually to flag the conflict explicitly and escalate, not to let the model pick whichever source seems more plausible.
  • When there is no source, refusing to answer is the correct task outcome, not the system being "useless."
  • If all six cases can be answered with the same keyword and the same source, the transfer has not covered real variation.

Explain with the same evidence to three audiences

Heading "Explain with the same evidence to three audiences"

  • Boss version: Which continue/stop decision these evals should support, which risks are hard gates, and what unknowns remain regarding cost and value.
  • Frontline version: How the cases come from normal tasks, no-answer, conflict, outdated, and permission anomalies; and why correct refusals and escalations also count as task success.
  • Engineering version: How corpus, case schema, 36/12/12, gold, metrics, thresholds, baselines, checksums, and version freezing prevent cherry-picking results after the fact.

Heading "Sources and factual boundaries"

  • OpenAI — Evaluation best practices: principles for eval goals, datasets, and continuous evaluation; products and pages may be updated, so re-verify them before actual use.
  • Enterprise RAG + MCP assistant project contract: requirements in public projects for data versions, tiered metrics, failure samples, and release evidence.
  • Sources and factual boundaries: this course's principles for handling version changes and factual citations.

The Beichen collaboration, the 60-item allocation, case IDs, queries, roles, thresholds, and baseline outputs are all course instructional design or synthetic material; they are not industry standards nor model performance. In real projects, distributions and gates should be re-approved based on task frequency, error cost, legal permissions, sample availability, and the risk tolerance of authorized roles.
