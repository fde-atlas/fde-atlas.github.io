The article analyzes the rising Forward Deployed Engineer (FDE) trend and argues that Palantir's Ontology — a three-layer digital twin of organizational operations comprising semantic, action, and governance layers — is the critical infrastructure enabling reliable AI agent deployment, contrasting it with traditional data platforms and outlining a multi-year adoption path.

AI Step-by-Step

01 The Familiar FDE Pattern: On-site History, Platform Loops, and Three Questions

The FDE (Forward Deployed Engineer) concept has surged in AI circles, with a reported 729% year-over-year demand increase for 2026 roles at companies like OpenAI, AWS, and Microsoft. Originating at Palantir (internally called Delta), FDEs embed inside customer organizations to write production code in real environments, taking over after contract signing and staying until systems run in production. Unlike pre-sales, which ends at signing, FDEs own the deployment lifecycle. Palantir positions Delta under the business team: product engineers build "one capability for many customers," while Deltas deliver "many capabilities for one customer."

The author notes this model mirrors enterprise software delivery from twenty years ago: on-site technical support, blended pre-/post-sales, and developers stationed at client sites to capture custom requirements. The pattern is familiar, but Palantir's theoretical framework adds unique value. FDE is not premium outsourcing; it is a forward extension of product R&D. Capabilities proven repeatedly on-site are generalized and absorbed into the platform, becoming reusable product features — Foundry is the result of this feedback loop. Competitors often copy only the "send engineers on-site" part, missing the crucial "on-site insights feed back into the platform" mechanism.

Historically, on-site teams never systematically answered three questions: what to precipitate, what to produce, and what standards to follow. Palantir codified the answers into a system called Ontology.

02 What Is Ontology: The Organization's Digital Twin

Ontology is the core of Palantir's knowledge system, often translated as "ontology." Foundry documentation defines it as an "operational layer" sitting atop integrated datasets, virtual tables, and models, combining semantic elements (objects, properties, links) and action elements (actions, functions, dynamic security). The key distinction: Ontology is neither a data catalog nor a database schema. For an order, the database stores a table with fields (schema); Ontology represents the order as an object with properties (amount, status, shipping address), links to other objects (customer, production line), actions (reassign, cancel, expedite), and permission constraints (who sees cost price, who can change status). Databases answer "what the data looks like"; Ontology answers "how the business operates" — it is a digital twin of the organization's operating model.

03 Three-Layer Structure: From "What Exists" to "What Can Be Done" to "Who Can Do It"

The digital twin comprises three layers: Semantic layer answers "what exists," action layer answers "what can be done," governance layer answers "who can do it."

Semantic layer defines business-world objects. Order, equipment, patient are object types; amount, status, serial number are properties; order-belongs-to-customer, equipment-mounted-on-production-line are links. An underestimated mechanism is Interfaces : when multiple object types share structure and behavior, an interface describes their common shape, allowing downstream consumers to depend on the interface rather than concrete types. The semantic layer's greatest value is decoupling from data sources: ERP's

asset_number

and IoT platform's

device_ref

both map to the same

Asset

object, so application developers no longer care which system the data originates from.

Action layer defines what can be done to objects. Traditional data platforms model only nouns, ignoring verbs; behaviors like reassigning orders or approving requests scatter across application code without unified names or constraints. Ontology models "decisions" as well: each action type is an explicitly defined operation. The presence of an action layer is the dividing line between a "data model" and a "business system."

Governance layer answers who can do what. Permissions apply directly to object types and properties, independent of underlying data-source permissions: the same object may show cost price to some users and only sale price to others. Additional features include classification labeling (for regulated industries like defense), Git-style branching and versioning, and full lineage tracking. Together, the semantic layer makes the business explicit, the action layer makes it operable, and the governance layer makes operations controllable.

04 Five Building Blocks and a Write-Back Loop: How Ontology Comes Alive

At the component level, Ontology's basic materials are five: object types, properties (including reusable shared properties across types), link types, action types, and functions. To animate this "read-only map," action-type execution mechanisms are required, centered on three points:

Submit-is-transaction. A single action-type submission completes all modifications to objects, properties, and links; validation rules and business constraints are enforced at submit time. Regardless of which application originates the request, it passes through the same validation path — no bypass channels exist; this is not form logic inside a frontend.

Side effects and write-back. Successful submission can trigger notifications, audits, and downstream system calls, with results safely written back to source systems like ERP, CRM, MES via Writeback. Business users make decisions directly in the system while source data stays clean.

Audit trail. Every submission automatically logs; the decision itself becomes a data asset: one person's judgment becomes the next person's input, enabling experience compounding.

Engineering implementation splits the model into three decoupled services: OMS manages schema (definitions and versions of objects, links, action types); OSS handles reads (high-throughput query layer); Funnel handles writes (all writes pass governance policies and schema validation before persisting). A supply-chain scenario illustrates the full loop: a distribution center fire updates the

Facility

object via IoT data; impact propagates along links to purchase orders and inventory; the logistics manager executes an

Initiate_Reorder

action in the UI; the decision passes validation and writes back to the underlying ERP — from sensing to action, all on the same graph.

05 Ontology and AI: The Agent's Operational Layer

The action layer is the foundation for AI agent reasoning and action. AIP (Palantir's AI platform) is built directly on Ontology. For an agent to take on work, someone must first define which objects it can discuss, which data it can read, which actions it can execute, which permissions it must obey, and what evidence it must leave — this is precisely the precipitation of what FDEs do on-site.

A notable interface is Ontology MCP : selected object types, action types, and query functions are exposed as MCP tools, allowing external agents to call them directly. Ontology thus simultaneously serves three roles: semantic model of enterprise state, agent tool and action catalog, and governance/audit interface — defining and logging what agents can do and have done in a single layer.

06 Adoption Path and Cost: What to Borrow, What Not to Copy

Ontology is not a one-time modeling project but a long-cycle iteration. A bank case study outlines four phases: Months 3–6 — data ingestion and first core objects (customer, account, transaction); Months 6–12 — enrich links, define first actions and functions, introduce dynamic permissions; Months 9–18 — build object-aware applications and first agents, enable bidirectional write-back to core systems; Months 18–36 — expand bank-wide and move toward ecosystem integration. This cadence mirrors the three-layer sequence: semantics first, then actions, then agents.

The system is bundled within the Foundry platform, requiring full adoption — the biggest barrier. Compared to alternatives: dbt-style semantic layers cover only metrics and remain read-only; graph databases (e.g., Neo4j) model entity relationships but typically require moving data into the graph store and likewise lack a governed write channel. The combination of validation, side effects, audit, and property-level permissions unified in one system — "governed write" — is currently unique to Ontology; other approaches do not provide the full set.

07 Lessons for Us: Precipitation Is Harder to Copy Than the Pattern

Reflecting on the FDE wave, the author draws three takeaways:

On-site experience must flow back into platform capabilities. Project-based patches that disappear after delivery are a decades-old flaw of the on-site model; without a rooted feedback mechanism, FDEs become just a more expensive labor line item.

Model semantics first, actions later. First clarify with the business "what objects are and how they relate," then discuss automation and agentification. Reverse the order, and AI will merely execute chaos faster.

Organizational modeling is a prerequisite for agent deployment. Beyond model capability, enterprise AI success often hinges on having a clear Ontology layer: objects, permissions, actions, evidence. Without it, deploying agents is like letting someone drive without a map.

The FDE label will stay hot for a while, but titles eventually fade. The core methodology — letting those who know the frontline participate in defining how the organization is described by software — should have been done twenty years ago; doing it now is not too late.
