07 FDE Scenario Cards and PoC Scope Lockdown

Original title: 07 FDE 场景卡与 PoC 范围锁定

FDE中国社区 · 2026 · 3 min read

Summary

This article presents the FDE scenario card, a template that turns vague requests like an "intelligent assistant" into concrete scenarios specifying users, inputs, outputs, permission boundaries, and acceptance metrics. It defines three maturity tiers—prototype (1–2 weeks), enterprise PoC (3–6 weeks), and production—and stresses that PoC scope must state exclusions, such as not touching core systems or automating high-risk actions. A 30–45 minute review meeting with business owners, IT, and the FDE decides whether the scenario is worth doing, feasible, and verifiable within 2–6 weeks.

Key points

  • Scenario cards compress abstract needs into reviewable deliverables.
  • Prototype, enterprise PoC, and production are distinct tiers to clarify for clients.
  • PoC scope must explicitly list what it will not do.
  • High-priority scenarios are frequent, low-risk, and have available data samples.
  • A short review meeting answers four questions before any code is written.

Chapter Objectives

Use FDE scenario cards to clearly document business requirements, data conditions, technical boundaries, permission risks, and acceptance metrics, creating a shared language for subsequent engineering and commercial communication.

Opening Case: Why "Intelligent Assistant" Is Not a Scenario

"Build an enterprise knowledge base intelligent assistant" sounds complete, but it is not a valid scenario. It has no users, tasks, inputs, outputs, risks, or acceptance metrics. Rewritten in scenario card language, it should read: "When a customer service agent handles an after-sales policy ticket, the system generates a reply draft based on the FAQ, SOP, and order status, and flags whether escalation to a human is needed."

This sentence immediately raises follow-up questions: Who uses it? What data? Who sees the output? Which cases cannot be auto-replied? What counts as success? That is the value of a scenario card: it compresses an abstract requirement into a deliverable unit that engineering, business, and compliance can jointly review.

Scenario Card Fields

FieldHow to Fill It In
Scenario nameDescribe the business task in one sentence
UsersFrontline users, management users, review users
Current processHow the task is done manually today
Pain pointsTime cost, errors, omissions, communication, rework, or risk
Input materialsDocuments, spreadsheets, systems, images, logs, or external information
Output resultsReports, lists, recommendations, tickets, messages, or approval summaries
Permission boundariesWho can view, who can query, who can execute, which actions require approval
Acceptance metricsAccuracy, time cost, adoption rate, citation rate, tool success rate, labor savings

Scenario Tiers

The scenario card should indicate the current validation tier, to prevent customers from mistaking a classroom demo for a production commitment:

TierDefinitionTypical Duration
PrototypeSample data, single role, read-only or suggestion-only output1–2 weeks
Enterprise PoCMultiple roles, real permission subset, evaluation samples3–6 weeks
ProductionGateway, audit, regression gates, operations handoverBy milestone

The FDE should clearly tell the customer: prototype, enterprise PoC, MVP, and production launch are not the same thing.

Scenario Card Example (Simplified)

FieldExample
Scenario nameCustomer service after-sales policy ticket reply draft
UsersFrontline agents, QA supervisors, after-sales experts
Current processAgent reads ticket → checks FAQ → checks order → writes reply → QA spot-checks
Pain pointsSlow information lookup, messy policy versions, error-prone compensation boundaries
Input materialsHistorical tickets, FAQ, SOP, order status API
Output resultsClassification, knowledge citations, reply draft, escalation-to-human recommendation
Permission boundariesRefunds, compensation, and complaint escalations must be handled by humans
Acceptance metricsClassification accuracy, first response time, agent adoption rate, high-risk escalation accuracy
What it does not doNo automatic compensation, no promises about final customer outcomes

The example does not need to be perfect from the start, but everyone must know where the boundaries of this PoC lie.

PoC Scope Locking

A PoC should clearly state what it will do, and also what it will not do.

What It Does

  • Which sample data it uses.
  • Which user roles it supports.
  • Which process steps it covers.
  • Which results it outputs.
  • Which tools it uses.

What It Does Not Do

  • Does not directly modify core systems.
  • Does not automatically execute high-risk actions.
  • Does not cover all historical data.
  • Does not promise to replace expert judgment.
  • Does not promise accuracy without samples.

Scenario Prioritization

High-priority scenarios typically have:

  • High frequency.
  • High time cost.
  • High reusability.
  • High room for improvement.
  • Low-risk boundaries.
  • Available data samples.
  • A business owner willing to try it.

Scenario Card Review Meeting

After the scenario card is written, hold a 30–45 minute review meeting with the business owner, AIBP, a frontline representative, the IT/data lead, and the FDE. The meeting answers only four questions:

  • Is this scenario worth doing?
  • Do the data and permissions support a small-scale validation?
  • Can the acceptance metrics be observed within 2–6 weeks?
  • Which requirements must go into the change pool rather than this round's PoC?

If these four questions cannot be settled, writing code afterward will only cost more.

Hands-On Task

Complete a scenario card and answer in one sentence:

  • Why is it worth doing now?
  • Why is this scope small enough?
  • Why is this scenario verifiable?
  • If it fails, where is it most likely to fail?

Deliverables

  • FDE scenario card.
  • PoC scope statement.
  • Preliminary acceptance metrics.
  • Risk and assumption list.

Common Pitfalls

  • Naming the scenario "intelligent assistant".
  • Not writing "what it does not do" in the scope.
  • Not specifying who is responsible for acceptance.
  • Writing only "good results" as the acceptance metric.

Checklist

  • Is the scenario specific enough?
  • Are there real sample data?
  • Are inputs, outputs, and permissions clearly defined?
  • Can the value be validated on a small scale?
