What Is Amazon Bedrock AgentCore: Key Points for Security Review

Original title: Amazon Bedrock AgentCore 是什么：安全评审要点

FDE Times · 2026-11-04 · 4 min read

Summary

This article explains how Amazon Bedrock AgentCore, previewed July 16, 2025 and GA on October 13, 2025, helps FDEs answer the three questions security teams ask: where agents run, who can invoke them, and where logs live. Runtime, Identity, and Observability map to these questions. The author highlights session limits (8 hours for microVM, 14 days for Instances on customer-account EC2), IdP integration without user migration, and a key gap: CloudTrail currently covers only Gateway and Agent Registry, so audit requirements must be checked before launch.

Key points

  • AgentCore reached GA on October 13, 2025 after a July preview.
  • Runtime, Identity, and Observability answer the three core security questions.
  • microVM sessions cap at 8 hours; Instances allow up to 14 days on customer EC2.
  • Identity integrates existing IdPs like Okta and Microsoft Entra ID.
  • CloudTrail only logs Gateway and Agent Registry, leaving an audit gap to flag early.

Runtime, Identity, and Observability manage where things run, who can call them, and what gets logged. The gaps determine how much a Forward Deployed Engineer can promise.

Key takeaways

  • AgentCore consists of multiple services, and three of them directly answer security teams' questions: Runtime for execution, Identity for authentication, and Observability for monitoring.
  • microVMs isolate each session individually, with sessions lasting up to 8 hours; Instances run on EC2 within the customer's account, with sessions lasting up to 14 days.
  • Telemetry data is exported in the OpenTelemetry standard and stored in CloudWatch, but CloudTrail currently only records a subset of capabilities.

AWS released Amazon Bedrock AgentCore in preview on July 16, 2025, and made it generally available (GA) on October 13, 2025. The product page summarizes it with a short tagline: any framework, any model, secure at scale.

For a Forward Deployed Engineer (FDE), the tagline matters less than the questions heard in the third customer meeting. By then, the prompts have stabilized and the demo runs. The people across the table are now the security team, and they ask three things: Where does the agent run? Who can invoke it? Where do you look at logs when something goes wrong?

AgentCore answers these three questions with three components: Runtime, Identity, and Observability. Understanding what each component can do, and what it can't do yet, makes moving from pilot to production on the customer's AWS much faster.

What it can do, and what it doesn't promise

AWS documentation describes AgentCore as a modular platform for building, deploying, and running agents. It supports any framework and any foundation model, without requiring you to manage infrastructure yourself.

Mission Cloud, a partner that sells AgentCore implementation services, says the platform consists of seven managed services. This partner has a commercial interest in saying so, so "seven" should be treated as its own count.

This article doesn't cover the entire product; it picks out only the three services that correspond to the security team's three questions. Two other capabilities, Gateway and Agent Registry, appear only in the audit section below.

Runtime doesn't require throwing away existing code. Agents can be written in any framework and communicate with tools or other agents via the Model Context Protocol (MCP) or the Agent-to-Agent protocol (A2A). So if the customer already has an agent, the first step is migrating where it runs, not rewriting it.

An example: choosing the right compute type

Suppose you're working for a logistics company and need to push two agents to production. The first is an assistant for warehouse staff, where each Q&A session lasts only a few minutes. The second runs nightly reconciliation, with each run taking about 10 hours.

Runtime offers two compute types. With microVMs, each user session runs in its own microVM, with CPU, memory, and file system isolated from each other. When a session ends, the microVM is destroyed and cleaned up. Two warehouse staff therefore never share the same environment, making this type a good fit for the first agent.

The second agent is different. microVM sessions last at most 8 hours, so a 10-hour task would be interrupted at hour 8. Instances allow sessions of up to 14 days, running on EC2 infrastructure hosted by AWS within the customer's own account. That's usually exactly what a compliance team wants to hear.

So, before choosing a compute type, measure session duration in practice; don't guess. One wrong number during requirements gathering can force the entire architecture to be rebuilt.

Identity: customers don't need to switch IdPs

Authentication built into Runtime is handled by AgentCore Identity. Each agent has its own identity, and the system can connect to the identity provider (IdP) the enterprise already uses, such as Okta, Microsoft Entra ID, or Amazon Cognito. According to AWS, customers don't need to migrate users to a new system or rebuild their login flows.

When presenting to customers, lead with this point. In the logistics example, warehouse staff log in with the Okta accounts they use every day, while the reconciliation agent has its own separate identity, distinct from human identities.

Observability works out of the box, but auditing still has gaps

AgentCore exports telemetry in an OpenTelemetry-compatible format, so the data can feed into any monitoring system the customer already has. Metrics, spans, and logs are stored in Amazon CloudWatch under the customer's account. Ready-made dashboards show session counts, latency, token usage, and errors.

Auditing is where you need to be careful. AWS documentation explicitly states that CloudTrail currently covers only a subset of capabilities, specifically Gateway and Agent Registry. A bank or hospital may require a record of every API call. If that comes up, raise this gap in the meeting on the spot; don't let the customer discover it after go-live.

Before the security review, make a table: one column for the customer's audit requirements, another for what CloudTrail currently records. Bringing this table into the meeting room builds far more trust than promising "AWS has it all covered."

Three common mistakes when migrating agents to AgentCore

The first mistake is estimating session duration by feel. A task you think takes 6 hours but actually drags to 9 will exceed the microVM's 8-hour limit, and this kind of failure usually only surfaces once the customer's real data starts flowing in.

The second mistake is promising full auditing just because CloudWatch is connected. Telemetry helps you debug; what compliance teams care about is CloudTrail, and it doesn't yet cover all capabilities.

The third mistake is rewriting the customer's agent to "fit" the platform. Runtime accepts any framework and model, so your effort should go into where the agent runs, its identity, and its logs, not into agent logic the customer has already validated.

What to learn first, and how to write it on your resume

If you're just starting out, learn Runtime first: the two compute types, session limits, and how to deploy an agent written in a framework you know. Then learn Identity with a real IdP, followed by viewing traces in CloudWatch. Also learn MCP and A2A; these two protocols aren't tied to AWS.

Writing "used AgentCore" on a resume says almost nothing. Spell out three decisions: you chose the compute type based on measured session duration; you connected the agent to the customer's IdP and separated the agent's identity from user identities.

And also: you flagged the audit gap before go-live. If you don't have a real customer yet, reproduce the two-agent example above in a test account and write a README explaining each choice.

Tools will change, but these three questions always matter: where the agent runs, who can invoke it, and whether everything is recorded. The FDE who can answer these three questions clearly is the one who gets invited back for the next project.
