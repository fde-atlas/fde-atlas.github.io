FDE Practical Project

Original title: FDE 实战项目

FDE 成长手册 · 2026-09-12 · 8 min read

Summary

This tutorial defines three hands-on FDE projects of increasing difficulty: a support-ticket escalation workbench, a supply-chain exception workflow, and an enterprise RAG + MCP assistant as the capstone. It stresses that projects must be full evidence packages—discovery briefs, data dictionaries, architecture decisions, evals, permissions, runbooks and handoff—not feature demos. The capstone requires 100+ versioned test samples and sets release thresholds for retrieval, refusal, permissions, tool safety, latency and cost, with cross-tenant leakage and unauthorized writes as hard blockers. Reviewers should reproduce success and failure paths, test privilege escalation and replay write requests rather than watch demo videos.

Key points

  • Three projects progress from ticket triage to a 6–8 week RAG+MCP capstone
  • Every repo needs discovery briefs, data dictionaries, ADRs, tests and runbooks
  • Capstone evals need 100+ versioned samples covering refusal, ACLs and prompt injection
  • Release gates include Recall@5 ≥ 0.85, task success ≥ 0.80, refusal ≥ 0.90
  • Cross-tenant leakage and unauthorized writes are hard blockers; review by replay, not demos

The FDE discussed on this page refers to Forward Deployed Engineer, not Full Disk Encryption. An FDE project is not a collection of feature screenshots; a qualified project as defined by this tutorial should answer: why the customer needs it, where the data comes from, what success means, what happens when it fails, who can perform which actions, and who operates it after launch.

It is recommended to complete at least one of the first two projects in order, then complete the Capstone. See the FDE learning roadmap for the full schedule.

All three projects use synthetic data or data you are authorized to make public. Do not put real sensitive information from employers, customers, or individuals into public repositories.

The Evidence Package Shared by All Projects

Heading "The Evidence Package Shared by All Projects"

Whichever project you choose, the repository should include:

  • Discovery Brief: users, current process, pain point evidence, constraints, success metrics, and non-goals;
  • Data dictionary and data source documentation, including owners, update frequency, quality rules, and retention policies;
  • Architecture diagrams, trust boundaries, key ADRs, and rejected alternatives;
  • Repeatable deployment and rollback steps;
  • Automated tests, acceptance data, and failure samples;
  • Threat model, permission matrix, and audit samples;
  • SLOs, dashboards, alerts, runbooks, and incident drill records;
  • A 5–10 minute demo, launch recommendations, retrospective, and handover checklist.

Project One: Customer Support Ticket Escalation and Root Cause Workbench

Heading "Project One: Customer Support Ticket Escalation and Root Cause Workbench"

Scenario

Heading "Scenario"

A B2B software team's tickets are scattered across the support system, product defect tracker, and customer success records. Escalation rules rely on personal experience, and managers don't discover high-risk customers until the weekly meeting. Your task is to deliver a unified workbench that lets support supervisors identify tickets needing escalation, review evidence, and assign owners.

Must Complete

Heading "Must Complete"

  • Interview support representatives, supervisors, and product staff, and document the current escalation process and responsibility boundaries;
  • Map at least three synthetic data sources into a unified ticket model, preserving source and update time;
  • Build the risk score with transparent rules first; an optional model classifier must not override manual rules;
  • Provide queues, filters, evidence details, owner assignment, and status history;
  • Implement role-based permissions on the server side, and log every status change;
  • Compare the new process with the original using replayed data; do not treat UI completeness as business success.

Acceptance Criteria

Heading "Acceptance Criteria"

  • Repeated ingestion of the same batch of inputs must not generate duplicate tickets; the explainable discrepancy between total source counts and the unified model must not exceed the course-set 0.5%;
  • Recall on pre-labeled high-risk tickets must reach the target agreed in your Discovery Brief, with false positives reported alongside;
  • Regular support agents must not modify restricted tickets owned by others; supervisor actions must record user, time, old value, and new value;
  • All five core user tasks have end-to-end tests and one real user walkthrough;
  • You can demonstrate prompts, retries, and manual handling paths when data sources are delayed or missing.
0.5%

This is the project target the course uses to force you to do reconciliation, not a general industry benchmark. If business risk is higher, set stricter thresholds with stakeholders.

Project Two: Supply Chain Anomaly Handling Workflow

Heading "Project Two: Supply Chain Anomaly Handling Workflow"

Scenario

Heading "Scenario"

A procurement team handles delays, inventory shortages, and price anomalies every day. Multiple systems send duplicate events, and supplier APIs may time out. Your task is not to build a prettier dashboard, but to turn "detect anomaly—collect evidence—recommend action—human approval—execute—reconcile" into a recoverable workflow.

Must Complete

Heading "Must Complete"

  • Define data contracts for anomaly events, handling cases, approvals, external actions, and audit records;
  • Use a rules engine to produce deterministic recommendations; models may only interpret or supplement unstructured information;
  • Provide a preview for every external action, executing only after approval;
  • Handle duplicate or ambiguous-outcome calls with idempotency keys, retry limits, and reconciliation jobs;
  • Design states for cancellation, timeout, partial success, and manual takeover;
  • Deliver an operations queue, SLOs, alerts, and a runbook for supplier dependency failures.

Acceptance Criteria

Heading "Acceptance Criteria"

  • Replaying the same event 10 times generates exactly one valid case and at most one external business effect;
  • Approvals are bound to a specific user, case, action, parameter summary, and validity period; old approvals become invalid when parameters change;
  • Timeouts, rate limits, deterministic failures, and ambiguous outcomes each receive distinct handling, with no infinite retries;
  • Interrupted workflows can be recovered from persisted state, with proof that external effects are not duplicated;
  • A manager can reconstruct the request, decision, approval, execution, and reconciliation of an action using a correlation ID.

Project Three: Enterprise RAG + MCP Assistant (Capstone)

Heading "Project Three: Enterprise RAG + MCP Assistant (Capstone)"

Scenario and Boundaries

Heading "Scenario and Boundaries"

Internal employees need cited answers from policies, product manuals, and operating procedures, and need to create service requests when necessary. The system must filter documents by tenant and role; refuse to answer when knowledge is insufficient; and require preview followed by per-action user approval for any write operation.

The goal here is not to build the "most autonomous" agent. The default topology is one agent plus deterministic retrieval, policy, and tools. Only add complexity when evals prove that parallel or multi-agent setups clearly improve quality, isolation, or latency.

See the Enterprise RAG + MCP Project README for the full project contract.

When following the 24-week standard roadmap, start from Week 19 Capstone M0 and continue through Week 24 Controlled Pilot and Handover. Use the same problem contract, corpus version, and risk boundaries for all six weeks; do not switch projects at each milestone.

If your team is evaluating a similar RAG or MCP deployment but cannot yet pin down the scenario, scope, or acceptance criteria, you can book a project diagnosis with your existing process. First determine whether the problem is worth solving, then decide whether to move into prototyping and production delivery.

Required Vertical Slice

Heading "Required Vertical Slice"

  • Discovery and scope: three user roles, five high-value tasks, baseline time costs, guardrail metrics, and the go-live decision maker;
  • Data and access: document owners, versions, validity dates, tenants, and ACL metadata carried through ingestion, indexing, retrieval, and caching;
  • RAG: a reproducible keyword or hybrid retrieval baseline, citations, conflict handling, and refusal to answer;
  • MCP tools: at least one read-only tool, one preview tool, and one approved write tool;
  • Policy and approval: the model only proposes actions, an external policy component authorizes them, and the executor produces effects;
  • Evals and validation: versioned datasets, deterministic checks, calibrated human scoring, and release gates;
  • Production operations: tracing, logs, metrics, cost, SLOs, alerting, degradation, rollback, and handover.

Capstone acceptance dataset

Title "Capstone acceptance dataset"

Build at least 100 de-identified or synthetic samples and pin their version:

TypeMinimum countQuestions to validate
Answerable questions50Retrieval, facts, citations, freshness, and multi-document synthesis
Unanswerable questions20Whether the system explicitly refuses rather than fabricating an answer
Permission and cross-tenant questions15Whether filtering is enforced at the data layer and whether caches are isolated
Prompt injection and tool abuse15Whether malicious content can change policy or trigger unauthorized effects

Each sample must record at least:

case_id

, user/tenant, question, expected sources, allowed outcomes, expected tool behavior, risk labels, and review rationale. Split training, debugging, and final acceptance samples, and avoid hand-tuning against the test questions.

Capstone release gates

Title "Capstone release gates"

The table below shows the first-version course gates, not an industry-wide benchmark. On delivery you must also report sample counts, confidence intervals or margins of error, failure distributions, model/prompt/index/tool/policy versions, and per-task cost.

DimensionFirst-version gateEvidence
RetrievalRecall@5 ≥ 0.85 on the answerable setFixed corpus and retrieval result snapshots
AnswersEnd-to-end task success rate ≥ 0.80Deterministic rules plus calibrated human scoring
CitationsKey facts cited, citation support rate ≥ 0.90Claim–source mapping table
RefusalCorrect refusal rate ≥ 0.90 on the unanswerable setAt least 20 independent samples
Permissions0 cross-tenant or privilege-escalation leaksAt least 15 negative cases; any failure blocks release
Tool safety0 unapproved writes, 0 reusing approvals after parameter changes, 0 duplicate external effectsAdversarial and replay tests; any failure blocks release
LatencyQ&A p95 ≤ 8 seconds with 10 concurrent usersRecord load, hardware, model, and network conditions
Observability100% of acceptance runs can link model, retrieval, policy, and tool steps via run_idTrace sampling and field checks
RecoveryA single-point failure of the model, index, or MCP triggers a defined degradation pathDrill records for the three failure types
CostEach accepted task stays within the budget in the Discovery BriefIncluding model, retrieval, tools, retries, and human review

Meeting the average scores does not mean you can go live. Cross-tenant leaks, unauthorized writes, secret exposure, or inability to roll back are hard blockers.

How to review the project, not the demo

Title "How to review the project, not the demo"

Reviewers should randomly select eval samples from the repository, reproduce one success path and one failure path; switch user roles to attempt privilege escalation; replay a write request; take down one dependency; then deploy from a fresh environment following the documentation. Watching only the author's prepared "golden path" video cannot prove the project is complete.

The numbers in the project description are only initial course gates. For real customer projects, you must first measure the current state, then have the business owner, security lead, and technical lead jointly set the release thresholds.

After the project passes acceptance, continue with the FDE portfolio, organizing the Discovery Brief, architecture decisions, eval reports, security gates, and operations evidence into a case that recruiters can verify.
