Window function

FDE Interview Prep · 2026 · 1 min read

Summary

This article explains SQL window functions as an FDE interview topic, citing a Rippling Manager, Forward Deployed Engineering posting (September 2026) requiring SQL and data modeling, and a Blind report of a Palantir online assessment with SQL questions. Window functions use an OVER clause with optional PARTITION BY, ORDER BY and frame, keeping every input row unlike GROUP BY. The key detail is the frame: the default RANGE frame gives tied rows the same running total, while ROWS with ties depends on engine ordering unless a tiebreaker is added. Window functions cannot appear in WHERE, so filter ranks via outer queries or CTEs; QUALIFY is only supported by some engines.

Key points

  • Window functions compute per-row values via OVER with partition, order and frame, keeping all rows.
  • Default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, so ties share running totals.
  • Use ROWS with a tiebreaker like ORDER BY order_date, order_id for deterministic per-row sums.
  • No ORDER BY means the frame is the whole partition, giving group totals on every row.
  • QUALIFY works in Snowflake, Databricks, BigQuery and DuckDB, but not SQLite or PostgreSQL.

Full text

A window function computes a value for each row from a set of related rows, defined by an

OVER

clause with an optional

PARTITION BY

,

ORDER BY

and frame. Unlike

GROUP BY

, it keeps every input row, which is what running totals, rankings (

ROW_NUMBER

,

RANK

,

DENSE_RANK

) and row-to-row comparisons (

LAG

,

LEAD

) need.

Source 2Palantir FDSE Interview (Blind thread)PublisherBlindSource typecandidate report on Blind In a SQL exercise, window functions sit behind running totals and top-N-per-group questions, and the detail to get right is the frame.

With an

ORDER BY

and no frame, the default is

RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

, so rows that tie on the ordering column are peers and get the same running total (

SQLite, window functions

); say so. For a per-row sum, write

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

and add a tiebreaker so the order is unique (

ORDER BY order_date, order_id

); with

ROWS

and ties, the running total depends on the order the engine happens to pick. With no

ORDER BY

at all, the frame is the whole partition, so

SUM(x) OVER (PARTITION BY k)

is the group total on every row.

Say which ranking function you chose and what it does with ties, and filter on a rank in an outer query or CTE, because a window function cannot appear in

WHERE

. Snowflake, Databricks, BigQuery and DuckDB also accept

QUALIFY ROW_NUMBER() OVER (...) = 1

; SQLite and PostgreSQL do not, so write the CTE there.

The running total question practices the frame on a running total per customer by day.
