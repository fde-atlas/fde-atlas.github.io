Robot Fault Diagnosis: How an FDE Uses MCAP Logs to Find Root Causes

Original title: 机器人故障诊断：FDE 如何用 MCAP 日志找根因

FDE Times · 2026-11-07 · 6 min read

Summary

Using a warehouse robot dropping boxes at Physical Intelligence as its example, this guide walks through how a forward deployed robotics engineer diagnoses root causes. It covers prioritizing tickets by fleet-wide impact rather than arrival order, reproducing failures on-site to get exact timestamps, and using Python scripts to extract short time windows around each drop from MCAP files, the default ROS 2 log format. Comparing gripper commands against feedback distinguishes hardware wear, system latency, or model issues. The author stresses closing a ticket only after checking whether other stations share the fault and reporting patterns to the design team, and lists common mistakes plus advice for demonstrating this skill in job applications.

Key points

  • Prioritize tickets by fleet impact, not arrival order.
  • Reproduce the failure on-site before diagnosing.
  • Read MCAP logs in short windows around each drop.
  • Compare commands and feedback to separate hardware, latency, and model causes.
  • Report recurring patterns to the design team before closing tickets.

Key Takeaways

  • At Physical Intelligence, the Forward Deployed Robotics Engineer is the first line of technical defense for the robot fleet, responsible for analyzing tickets, reproducing failures, and collecting diagnostic data.
  • Reproduce the failure at the robot station first, then diagnose; what you'll typically open and read is an MCAP file, the default log format for ROS 2.
  • A failure is only truly fixed once you've confirmed whether other robots exhibit the same issue and reported the pattern to the design team.

At shift handoff, a new ticket lands in the queue: "The robot at station 7 dropped a box." No photo, no timestamp, just an impatient warehouse operator waiting. You could immediately guess: worn gripper pads, a dirty camera, or a model gone wrong. All three sound plausible. But guessing like that is also the fastest way to waste two days.

Physical Intelligence positions the Forward Deployed Robotics Engineer as the first line of technical defense for a constantly growing robot fleet. These robots operate in warehouses and external data collection environments.

The job description is blunt: analyze field tickets, reproduce failures, collect diagnostic data, and follow every issue through to resolution.

This skill isn't limited to robotics. Reading multiple data streams on the same timeline, narrowing down causes step by step, and turning a one-off incident into a lesson for the whole system—this is what any Forward Deployed Engineer (FDE) troubleshooting production issues with real data has to do.

What makes robots different is that the consequences of a wrong guess are immediately visible: the box is lying on the warehouse floor.

First ticket in isn't necessarily first fixed

The job description requires prioritizing the ticket queue by impact on the entire fleet and operational goals, not by arrival order. So the first question about the station 7 ticket isn't "why" but "where else."

Suppose you filter the past week's queue for "drop" and "gripper" and find three other stations reporting similar issues, all running the same firmware version. Then the station 7 ticket is no longer a problem with one robot.

It's a symptom of a fleet-level issue and should move to the top of the queue. Conversely, if only station 7 is affected, look for causes specific to that station: hardware, layout, lighting, or box type.

Bash is enough for this step. First run

grep -il "fell\|drop" tickets/*.txt | xargs grep -h "station"

, then

sort | uniq -c

, and you'll have a preliminary conclusion in thirty seconds, no dashboard needed.

No reproduction, no diagnosis

The next step is one many software engineers want to skip: go to the station in person. Physical Intelligence explicitly lists performing physical inspections and functional tests at the robot station and confirming whether the failure can be reproduced as part of the job. A failure that can't be reproduced might just be a box that happened to be misplaced, or an operator reporting the wrong robot.

At station 7, you have the robot repeatedly grasp the same type of box. Suppose 6 out of 40 grasps result in a drop. That number is what you obtained under controlled conditions; more importantly, you know the exact time each of those 6 drops occurred. Those timestamps are the key to opening the log files.

In the logs, all data streams sit side by side

On a robot running ROS 2, what you open is usually an MCAP file. MCAP is an open-source container format for multimodal log data and the default log format for ROS 2.

It can record and replay binary messages in any format. A single file can simultaneously contain camera images, joint states, gripper commands, and force sensor data streams.

The common mistake is dumping the whole file into a visualization tool and aimlessly dragging along the timeline. The right approach is exactly the opposite: extract a window of a few seconds around each drop and read only the relevant topics. The script below demonstrates this idea. The topic names and file names are just examples; replace them with the names in your actual system.

from mcap.reader import make_reader
from mcap_ros2.decoder import DecoderFactory

TOPICS = ["/gripper/command", "/gripper/state"]
DROPS = [1730955612.4, 1730955987.1]  # 复现过程中箱子掉落的时间戳
WINDOW = 3.0  # 每次掉落前后各取的秒数

with open("station7_repro.mcap", "rb") as f:
    reader = make_reader(f, decoder_factories=[DecoderFactory()])
    for _, channel, message, msg in reader.iter_decoded_messages(topics=TOPICS):
        t = message.log_time / 1e9
        if any(abs(t - d) <= WINDOW for d in DROPS):
            print(f"{t:.3f}  {channel.topic:18}  {msg}")

The output is a short timeline with commands and feedback right next to each other. Read it like a conversation: the robot says "close the gripper"—how does the gripper respond, and how long does it take?

Three scenarios the timeline can reveal

Consider three outcomes. First, the close command was sent, but the gripper state reports a gripping force clearly lower than in successful grasps. This points to hardware: worn gripper pads, or a weak motor.

Second, the close command arrives late relative to the moment the gripper contacts the box. This points to system latency. Compare the latency between drops and successful grasps.

The third is the hardest: hardware responds normally, latency is normal, but the gripper picked a grasp point far from the box's edge. Now you have to question the model.

Physical Intelligence writes that π0.5 aims to generalize to new environments, and its experiments were conducted in home environments that never appeared in the training data.

When open-sourcing π0, the company also explicitly stated that the release was experimental, because π0 was developed for its own robots.

For someone diagnosing failures, these statements set the right expectations: the field environment may be far removed from anything the model saw in training. New box types, reflective tape, or unfamiliar lighting can all change the model's behavior without any component failing. Save the camera images from every drop.

Physical Intelligence says that 1 to 20 hours of data is enough to fine-tune π0 for a variety of tasks, so carefully documented failure scenarios are useful not only for the ticket on your desk but also for the training team.

Closing the ticket is only half the job

The job description includes a responsibility that's easy to forget: identify recurring failures across the fleet and flag durability weak points for the design team to improve.

If the gripper pads at station 7 wear out after a certain number of cycles, the next question is how many cycles the other stations have already run. Replacing a pad fixes one robot; telling the design team the pad needs to be more durable fixes the entire fleet.

A good root cause report fits on one page: symptoms, reproduction method and failure rate, log excerpts as evidence, cause, on-site fix, and the pattern reported to the design team. Write it with the same template every time, and over a few months you'll accumulate a dataset showing which failures keep recurring.

Mistakes that slow down diagnosis

The most common is diagnosing before reproducing: fixing based on a hypothesis and closing the ticket after seeing the failure disappear for five minutes. But with a failure rate of 6 out of 40, five minutes proves nothing.

The second mistake is concluding "it's the model" or "it's the hardware" just because that's the area you know best. The third is reading the entire log instead of extracting the right time window. The last is closing the ticket without ever asking whether other stations have the same problem.

How to prove this skill when job hunting

Physical Intelligence's requirements include at least 2 years of debugging and root cause analysis experience, plus experience analyzing logs and writing diagnostic scripts in Python or Bash. Faced with a job description like this, a single line on your resume saying "has debugging experience" won't convince anyone.

Be specific. For example: "Wrote Python scripts to extract log segments around incident timestamps, reducing the time to locate the cause of intermittent failures," and attach a root cause report with sensitive information removed.

In interviews, walk through a failure in the order of this article: how you prioritized, how you reproduced it, what the logs showed, and what you fed back to the design team.

The robot at station 7 still drops boxes, and so does the one at station 12. The engineer you can trust on-site is the one who can find the exact moment a box was dropped in the logs.
