How Consultants Can Transition to FDE: Python and Production Code Requirements

Original title: 咨询顾问如何转 FDE：Python 与生产代码要求

FDE Times · 2026-10-12 · 5 min read

Summary

This article examines what consultants must add to transition into forward deployed engineer roles. While customer-facing experience is valued, job postings from Palantir and Anthropic list hard requirements: solid Python (plus Java or C++ at Palantir) and experience shipping production applications. The author argues the dividing line is the deliverable—running systems like MCP servers and agent skills rather than recommendations—and warns that non-reusable, per-client code turns FDE roles into a services business. Practical advice includes building a deployed project with real users and using verbs like "built" and "shipped" on resumes.

Key points

  • Palantir requires solid Python, Java, or C++; Anthropic requires Python plus production deployment experience.
  • FDEs deliver production applications, MCP servers, and agent skills, not slide decks or reports.
  • FDEs own projects end-to-end; the person gathering requirements writes the code, avoiding handoff losses.
  • Code must be reusable; otherwise the role is consulting under an engineer's title.
  • Consultants should build and deploy a sanitized past project in Python as evidence for hiring managers.

Key Takeaways

  • Palantir explicitly requires solid programming skills in Python, Java, or C++; Anthropic requires solid Python skills and experience shipping production applications.
  • The difference between an FDE and a consultant lies in what gets handed to the customer: production applications, MCP servers, and subagents, not a set of recommendations.
  • Being able to write code is not enough. If the code cannot be reused, the FDE role effectively becomes a services business.

Palantir posted a Forward Deployed Software Engineer job listing for healthcare and civil programs serving the US government. The posting says the role's responsibilities "look like a startup CTO." A few lines down is a hard requirement: strong programming skills, with demonstrated proficiency in Python, Java, or C++.

These two lines explain why consulting experience alone is not enough. Sitting with customers, clarifying problems, and working with stakeholders is only the first half of the job. The other half is building the solution with your own hands, and both Palantir and Anthropic have written that half into their job postings as concrete programming requirements.

If you work in consulting, implementation, or solutions engineering and want to move into a Forward Deployed Engineer (FDE) role, your advantage on the customer side is real. But for that advantage to count, it must be paired with production code. So what should you practice first? The answer is in the job postings.

The dividing line is what you deliver

The fastest way to see the difference between the two roles is to look at what remains when a project ends. Anthropic describes its FDEs as going deep into customers' systems and building production applications with Claude models. It also names specific deliverables: MCP servers, subagents, and Agent Skills.

None of these are slide decks or reports. Even so, Anthropic does not shut the door on people with consulting backgrounds; it simply places that experience alongside two other requirements: solid Python programming skills and a track record of shipping production applications.

Compensation data company Pave describes the FDE as a hybrid of engineer and consultant: working on-site with customers, writing custom code for each one. Look closely, and "consultant" is only half of that label. The other half is engineer, and no amount of customer experience can substitute for it.

Why do companies want people who write code themselves?

SD Times explains the difference between the two roles in terms of speed. It argues that implementation consultants tend to be slower and prefer proven solutions, while FDEs sit down and build whatever is needed themselves. A good FDE with a small team can start creating value within weeks.

Imagine a public health agency that needs to consolidate case data from three legacy systems. The consulting approach: the project team first runs requirements workshops, writes an architecture proposal, then hands it to another team to implement. Every handoff costs time, and context leaks away along the way.

The FDE approach: the first week is also spent on requirements discovery. But within that same week, the engineer has already written a data pipeline in Python connecting the first two data sources, shows the results to real users, gathers feedback, and makes changes on the spot. There are no handoffs in between, because the person hearing the requirements is the person writing the code.

This is also why Palantir emphasizes end-to-end ownership of critical programs: teams are small, and everyone has to wear multiple hats.

"Ownership" here means owning the system until it actually runs, not stopping at recommendations. A consultant who cannot write code, no matter how well they understand the customer, cannot own a project in this sense.

Writing code is still not enough: the code must be reusable

People coming from consulting face a subtler trap. A practitioner in the field wrote on Substack to warn: if an FDE role cannot produce reusable technical assets, the company is effectively running a services business, just with employees whose titles say engineer.

Consulting habits are built around tailoring everything to each customer. Carry that habit into an FDE role and you will write one-off scripts, one version per customer, repeating the consulting model under a new title. There is code, but the value does not compound.

Return to the health agency example. An FDE with a product mindset would build the legacy system connectors as shared components that can be extracted, clearly documenting which parts are specific to that customer. The MCP servers and Agent Skills Anthropic lists are all modules that can be packaged and reused.

Where consultants have an edge, and what to practice first

This is not to downplay what you already have. Palantir's job posting describes the FDSE role this way: engage directly with customers, quickly understand their thorniest problems, then build solutions. The first half of that sentence is something many pure software engineers still have to learn from scratch, while you have been practicing it for years.

What you need to do is fill in the second half with evidence hiring managers can see. The table below maps requirements raised across multiple sources to the evidence you can prepare. The last column contains practice suggestions, not quotes from job postings.

RequirementSourceEvidence to prepare
Quickly understand customers' thorniest problems, then build solutionsPalantirA past case study (anonymized) walking from requirements discovery to what was ultimately built
Solid programming skills in Python, Java, or C++PalantirA code repository you wrote yourself, with tests and good readability
Solid Python skills and experience shipping production applicationsAnthropicA deployed application with real users
End-to-end ownership within a small teamPalantirA project where you personally went from input data to operations
Reusable technical assetsSubstack articleA shared component, such as an MCP server wrapping a real API

If you come from consulting, start with the two requirements of "solid programming" and "shipping production applications," because these are the parts customer experience cannot replace. Pick a problem from a past project, anonymize it, and build it end to end yourself in Python: ingest the data, process it, deploy it, and find real users.

On a resume, the verbs determine which category the reader puts you in. "Advised," "recommended," and "coordinated" tell a consultant's story; "built," "shipped," and "operated," plus what is running and who is using it, tell the FDE story. Customer experience should sit alongside these items to add weight to them, not replace them.

When reading job postings, watch for three words: production, end-to-end, and own. If a posting only talks about workshops, configuration, and customer relationships, it may just be implementation consulting under a new name.

In interviews, ask directly: does the code written during deployments flow back into the product? The answer will tell you whether you are joining an engineering team or a services business.

People who successfully transition from consulting to FDE are probably not those who abandon their old trade entirely, but those who keep their ability to understand customers and, for the first time, personally put what customers need into production.
