Introduction to Loop Engineering: A Systematic Approach to Harness Design for Keeping Autonomous Agents Running

Original title: ループエンジニアリング入門｜自律エージェントを動かし続けるハーネス設計の体系

FDX株式会社 · 2026-06-29 · 10 min read

Summary

This FDX article introduces "loop engineering," a design discipline for keeping AI agents running safely through repeated observation, decision, and action cycles. It attributes the 2026 surge in production agent deployments to long-task models like Claude Opus 4.7, Anthropic's published harness design guidance, and Karpathy's autoresearch approach. The framework covers a three-layer loop structure, four stop conditions (success, budget overrun, repeated verification failures, external interruption), and a tiered verification harness ordered Hook (ms), pre-commit (s), CI (min), human review (hours), with feedback pushed to the fastest tier. Practical tips include accepting partial success, quarterly harness reviews, and expressing rules via tests and types rather than prose. Anti-patterns include insurance-style prompt wording, infinite retries, and unverified delegation. It compares LangGraph, Claude Agent SDK, and Claude Code, and closes by describing FDX's FDE-led implementation and operations support.

Key points

  • Loop engineering designs harnesses so observation-decision-action cycles run safely in production.
  • Four stop conditions: success criteria, budget limits, consecutive verification failures, external interruption.
  • Verification is tiered Hook → pre-commit → CI → human, with feedback pushed to the fastest layer.
  • Tips: accept 80% partial success, review harness quarterly, encode rules in tests and types.
  • Anti-patterns: insurance prompt wording, infinite retries, trusting sub-agent output without verification.

What is loop engineering? (3-line summary)

  • Loop engineering = the discipline of designing a harness that keeps the observe → decide → act cycle running safely. Stop conditions / verification / budget management are built outside the agent itself (model + prompt).

Why autonomous agent operations spread in 2026

As a result of three converging factors, 2026 saw a rapid increase in companies running autonomous agents in production.

Factor 1: The arrival of models capable of long-running tasks

Models with built-in self-verification, such as Claude Opus 4.7, OpenAI o-series, and Gemini 3 Pro, entered full production phases. Even with minimal retries on failure, the probability of completing a task within a few loops has improved dramatically.

Factor 2: Anthropic's harness design article

The publication of Anthropic Engineering Blog's "Harness design for long-running application development" officially codified the design principle of "enforcing with tests, not documents." This made it easier for enterprises to adopt it as an internal quality assurance standard.

Factor 3: The spread of Karpathy-style "autoresearch" thinking

It was shown that the autonomous research loop proposed by Andrej Karpathy—"Modify → Verify → Keep / Discard → Repeat"—can be applied beyond coding to other domains (marketing / customer support / legal research). This broadened the methods for designing business loops.

The three-layer structure of the loop

An agent loop consists of three layers: observation, decision, and action. Each cycle passes through these three layers in order, with the results of the action layer feeding back into the next observation layer. If any layer is weak, the reliability of the entire loop collapses, so you need to understand what to design for each layer.

Observation Layer

  • state: current task state / completed steps / remaining tasks
  • memory: past conversations / knowledge base / RAG results
  • tool result: return values of the previous tool call / errors / side-effect logs

Designing the observation layer is equivalent to managing the context window. Stuffing in all history makes the decision layer unstable, so summarization, selection, and compression are required (see: 5 patterns for saving LLM tokens).

Decision Layer

  • The model looks at the observation layer and decides the next action
  • The prompt consists of decision policy (system prompt) and current observations (user message)
  • Whether to insert "reasoning" / "extended thinking" here depends on task complexity

The quality of the decision layer is determined by the signal-to-noise ratio of the observation layer. Enriching the signals in the observation layer is more effective than adding more prompts.

Action Layer

  • tool calls (external APIs / file operations / command execution)
  • side effects (DB updates / email sending / payments)
  • self-updates (writing to memory / saving training data)

The action layer includes all operations with side effects. For irreversible operations such as DB / email / payments, the standard practice is to build "guards" into the action layer.

Four patterns of stop conditions

Without designing "when to stop," loops lead to runaway behavior, cost overruns, and infinite loops. Stopping points fall broadly into four types, and in real operations they are usually deployed in combination rather than individually. Prepare everything from the desirable way to stop (success), to the undesirable ones (budget overrun, consecutive failures), to external interruption paths.

Pattern 1: Success condition met

  • Business requirements have been satisfied (KPI achieved / task completed)
  • Examples: ticket creation completed / code written and tests passing / report generated

The most desirable stop reason. Make success conditions mechanically checkable with numbers / booleans.

Pattern 2: Budget exceeded (token / time / cost)

  • Reached the configured limit on tokens / execution time / cost
  • Examples: stop when a task exceeds 50,000 tokens / 10 minutes / $5

Essential for enterprise operations. Budget-less loops cause exponential cost explosions in edge cases.

Pattern 3: Consecutive verification failures

  • An error that doesn't fix itself with retries occurs N times in a row
  • Example: retry limit of 2 (Stripe insight) / the same test fails 3 times in a row

"Infinite retries degrade LLM quality" is an empirical rule at many companies. After 2-3 failures, escalate to a human.

Pattern 4: External interruption

  • The user explicitly interrupts
  • A stop signal from another process
  • A kill switch for emergencies

Always leave a path for human operators to intervene. Full autonomy makes failure recovery difficult.

Layered design of the verification harness

Loop quality is determined by the response speed of the verification harness. The principle is "push feedback to the fastest layer."

Tier 1: Hooks (ms)

  • Immediate lint / format after file edits
  • Argument validation before tool calls
  • Side-effect guards (blocking writes to specific paths)

Verifications that can be judged in milliseconds should be completed in Hooks. This alone cuts 80% of "obviously violating" mistakes.

Tier 2: pre-commit / pre-action (seconds)

  • Type checking / static analysis
  • Lightweight unit tests
  • Business rule violation checks

Verifications that complete on the order of seconds. Run them before the agent commits / executes an action.

Tier 3: CI (minutes)

  • Integration tests / E2E tests
  • Security scans
  • Build verification

Completes on the order of minutes. Run at pull-request-equivalent timing. The agent waits for CI results before making the next decision.

Tier 4: Human review (hours / days)

  • Architecture decisions
  • Validity of business logic
  • Ethics / compliance checks

Concentrate on issues only humans can judge. Increasing this raises operational load, so automate everything that Tiers 1-3 can absorb.

Principle: In the order Hook(ms) > pre-commit(s) > CI(min) > human(h), push verification to faster layers. This minimizes human load while improving quality.

Operational tips and anti-patterns

Tip 1: Harness inventory (quarterly)

For each rule / Hook / constraint, ask quarterly "has model improvement made this unnecessary?" Remove unnecessary guardrails.

Excessive constraints lower performance. Hooks for mistakes the model can now avoid on its own should be removed.

Tip 2: Accept partial success

Aiming for "100% complete" wastes tokens over three fix loops and ends with zero results. Handing over at 80% complete is more rational than burning tokens chasing 100% (Stripe / Anthropic empirical rule).

Designing to allow partial success dramatically increases agent utilization.

Tip 3: Express information with tests / type definitions rather than explanatory documents

Explanatory documents like CLAUDE.md / AGENTS.md may be skipped by the model. Tests / type definitions catch violations in CI even if the model doesn't read them.

Prevent agent-caused mistakes from recurring with tests or lint rules. The compounding effect is large.

Anti-pattern 1: Adding insurance wording to prompts

Insurance-style wording like "double-check" or "re-verify" duplicates the model's internal verification and induces excessive loops. Don't include it in new rules / prompts.

Anti-pattern 2: Not addressing root causes with infinite retries

As mentioned in stop-condition Pattern 3, the standard practice is to cap retries of the same error after a few attempts and escalate to a human. Retrying endlessly degrades LLM output quality and hides the root cause that should actually be fixed behind the retry count.

Anti-pattern 3: Delegation without verification

Adopting sub-agent results without verifying them. Trusting a sub-agent's "I think I did it" leads to rollback work downstream.

After delegating, always verify behavior with actual results (tests / logs / screen).

FAQ

Q1. How does this differ from multi-agent?

Loop engineering is a design philosophy dealing with "safe operation of a single agent / single loop." Multi-agent deals with "coordination / division of labor among multiple agents."

The two are complementary, and each sub-agent in a multi-agent setup is also a target of loop engineering. For details, see the "Multi-Agent Implementation Guide".

Q2. Should you implement with LangGraph or Claude Agent SDK?

It depends on your business requirements.

  • Complex state transitions (human intervention / many branches / high audit requirements): LangGraph. It can be made explicit with a State Machine.
  • Simple implementation / fast startup: Claude Agent SDK. Anthropic's official SDK.
  • Autonomous coding work: Claude Code. Strong editor integration and affinity with existing dev tools.

Q3. Who decides the stopping conditions?

Business requirements + management judgment. Do not decide on the technical side alone.

  • Success criteria → Business owner
  • Budget cap → CFO / business owner
  • Retry count → SRE / platform engineer
  • Human escalation criteria → Follow the business SOP

Q4. Where should human intervention be inserted?

There are three types.

  • Approval Gate: Require approval before high-impact operations (DB deletion / large payments / customer notifications)
  • Fallback Gate: Defer judgment to a human on errors or low confidence
  • Audit Gate: Humans review samples after completion

Properly inserted human intervention yields higher operational quality than full autonomy.

Q5. How should rollback be designed for failures?

Design it in three tiers.

  • State Snapshot: Save state before each node/step executes, allowing rollback on failure.
  • Side Effect Compensation: If side effects occur, implement compensating transactions (email recall notifications / DB rollback).
  • Manual Recovery: When fully automatic rollback is difficult, present the human operator with "what happened" and "where to resume from."
