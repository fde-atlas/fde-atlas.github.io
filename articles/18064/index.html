Tiered Autonomy and Handoffs for AI Agents: A Practical Guide for FDEs

Original title: AI Agent 分级自主权与交接：FDE 实践指南

FDE Times · 2026-10-08 · 6 min read

Summary

This guide explains how FDEs should expand AI agent autonomy based on evidence rather than schedules, and how to hand over governance before leaving. Citing Anthropic data showing trust grows with experience, it presents a traffic-light model that authorizes individual actions by risk level, MIT Media Lab's A1-A5 autonomy tiers, and a worked example with YAML policy config for a refund-ticket agent. It also covers five implementation steps, monitoring metrics, and handoff practices from Tandem and PostHog.

Key points

  • Anthropic: users with 750+ sessions enable auto-approval in over 40% of sessions, versus ~20% for novices.
  • The traffic-light model grants permissions per action by risk, not per agent.
  • MIT's A1-A5 levels: A3 requires escalation to humans; A4 shifts to governance; A5 still lacks independent decision authority.
  • Promotions should rely on monitoring data like intervention counts, not calendars.
  • Handoff starts day one; every red action needs a named owner on the customer side.

Key Takeaways

  • Anthropic's data shows trust grows with experience: new users enable fully automatic approval in about 20% of sessions, while users with 750+ sessions exceed 40%.
  • Classify every action by risk; red actions start as suggestions only. Promote a level only when monitoring data proves the previous level is stable.
  • Handover means transferring governance responsibilities (setting policy, auditing) to a named owner on the customer's side. It starts on day one and should be validated by someone external.

Imagine a project in its third week. The customer support ticket agent you built runs smoothly in a sandbox. The customer's operations lead asks: "When can it work on its own without someone clicking approve?" Then comes a harder question: "After you leave the project, who on my side will look after it?"

These two questions are really the same skill. The first is raising an agent's autonomy based on evidence, not feelings; the second is transferring oversight of the agent to the customer's team so it keeps running after you're gone.

Get either one wrong and the agent ends up in one of two fates: either permanently stuck in manual-approval mode, or let loose too early and stripped of permissions after the first incident.

Trust accumulates—and it can be measured

Anthropic has published data on how people actually use agents, and the pattern is simple: new users with fewer than 50 sessions enable fully automatic approval in about 20% of sessions; users with more than 750 sessions exceed 40%.

On the agent side, Anthropic's internal data shows that as agent performance improves, the average number of human interventions per session drops from 5.4 to 3.3. There is a gap between the autonomy models could handle and the autonomy they are actually given—Anthropic calls this the "deployment overhang" and believes the gap is substantial.

For a Forward Deployed Engineer (FDE), this is a job description. The model is probably already good enough; what's missing is a chain of evidence that makes the customer willing to grant more autonomy. Anthropic also stresses that without post-deployment monitoring, you cannot know how the agent is actually being used. Without logs and metrics, you have nothing to convince anyone with.

Traffic lights: authorize by action, not by agent

The traffic-light model described by Data Science Dojo doesn't grant permissions to an agent as a whole; instead, it classifies each action by risk and assigns the corresponding permission level. High-risk actions can only be suggestions, approved by a human.

The accompanying principle: an agent must "earn" autonomy level by level, based on demonstrated performance.

MIT Media Lab's A1-to-A5 scale adds two points worth remembering. At A3, the agent must know when to stop and escalate to a human. At A4, humans stop supervising individual actions and shift to governing the system: setting policy, defining the business scope in which the agent may operate, and auditing.

At the highest level, MIT Media Lab draws a line every FDE should memorize: A5 means the agent can execute on its own—it does not mean it has its own decision-making authority. It remains bound by the permissions of the organization it represents.

Example: an agent that handles refund tickets

Back to the ticket agent from the opening. The first step is to list every tool it can call and assign each one a color. The table below is illustrative only; promotion thresholds are numbers you agree on with the customer—there is no universal standard.

ActionColorStarting levelPromotion criteria (example)
Read order history, check delivery statusGreenAutomatic, loggedNot needed
Tag and route ticketsYellowAutomatic, daily human spot checksConsistently low tag correction rate over several weeks
Send email replies to customersYellowDrafts only, human clicks sendSustained decline in the share of drafts needing edits
Issue refundsRedSuggestion only, human approvesEscalate only for small refunds, signed off by the customer's policy owner

The last row makes the distinction between execution and decision authority concrete. The agent may be accurate enough to issue refunds itself, but who may refund how much is the customer's policy—that threshold must be set by someone on the customer's side, not by you.

Policy should live in configuration, easy to read and review, not scattered across prompts:

actions:
  lookup_order:   { tier: green,  mode: auto }
  tag_ticket:     { tier: yellow, mode: auto, sample_review: daily }
  send_reply:     { tier: yellow, mode: draft_only }
  issue_refund:   { tier: red,    mode: propose_only, owner: "客服负责人" }
escalate_when:
  - confidence_below_threshold
  - customer_mentions_legal_action
promotion_review: weekly   # 复盘人工干预、修正和事故
owner

The owner field is a detail many people miss. Every red action needs a named owner responsible for whether it gets promoted—that's exactly where handover begins.

Hands-on: five steps in order

Following Anthropic's advice, start in a sandboxed environment with guardrails, and design checkpoints where the agent stops and asks for feedback. Then assign a color to every action as in the table above; when in doubt, mark it red.

Next, set up monitoring before going to production: count human interventions per session, how often outputs get corrected, and how often the agent escalates. These numbers replace "it looked fine to me."

Sit down with the customer weekly to review these numbers, and promote a set of actions one level only after the current level is stable. Finally, once most actions are green or yellow, hand the chairing of that review meeting to someone on the customer's side. At that point, they are taking on exactly the A4 governance role.

Handover starts on day one

Tandem's advice sounds counterintuitive but is right: start the handover before you realize you need one. A static document written in the final week goes stale quickly. So point readers to the system's live state—policy config files, human-intervention dashboards, escalation history—rather than copying them into a Word document.

PostHog sets a clear bar for "done": a deliverable is complete only when someone outside the team that built it can take over without anyone explaining it first. Next steps must be concrete, ordered, and assigned to named people. "The ops team will monitor it" is not a next step.

Runbooks should be organized by symptom, not by architecture. Someone on call at midnight starts from "the emails the agent sends sound off" or "escalation rate suddenly spiked," not from a service architecture diagram. AI Codex suggests a test: hand the runbook to someone who didn't build the system and ask them to read aloud how they would handle a given symptom.

Common mistakes

The first mistake is promoting on a schedule ("let it run on its own after a month") instead of on data. The second is conflating capability with decision authority: an agent hitting 99% accuracy doesn't mean it gets to decide refund policy.

The third is skipping post-deployment monitoring, which turns promotion reviews into debates based on impressions. The last is putting off handover to the final week, when the only person who knows why action X is still red is about to leave.

If you're applying for an FDE role, put this skill on your resume with numbers, not adjectives. For example: designed an autonomy roadmap for an agent, cut interventions per session from X to Y, and handed the review process over to the customer's operations team.

This week's exercise

Pick one automation you run: an agent, a cron job, or an internal bot. Write a policy file modeled on the YAML example above, assign an owner to every red action, and write one runbook entry for exactly one symptom. Hand it to a colleague who has never touched the system and quietly listen as they read it out.

Where he gets stuck is where your system still depends on you. A good FDE eliminates those spots before leaving the project.
