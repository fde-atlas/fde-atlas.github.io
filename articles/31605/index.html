FDE Project Handoff: Why Getting It Running On-Site Isn't Enough

Original title: FDE 项目交接：为什么现场跑通还不够

FDE Times · 2026-11-15 · 7 min read

Summary

Drawing on Google's Site Reliability Engineering book, the article argues that a successful run at a customer site is just a single test nobody wrote down and nobody can rerun, so it proves little about reliability. FDE custom code often ships without tests, yet the customer team inherits it, making every future change a gamble. The author proposes six types of handoff evidence: numeric acceptance criteria, single-behavior automated tests, regression tests for field bugs, scheduled production checks, and upstream PRs with reproduction cases. Tests should be written from week one to capture intent, and every field bug should become a test case, with generalizable fixes pushed upstream into the product.

Key points

  • A successful on-site run is an unrepeatable test, weak evidence of reliability.
  • Untested FDE code makes every customer-team change a gamble.
  • Handoff needs six evidence types, from acceptance criteria to upstream PRs.
  • Tests written in the last week only freeze current behavior, not intent.
  • Turn every field bug into a regression test; push fixes upstream.

Key Takeaways

  • Google's SRE book points out that a passing test cannot prove a system is reliable, but a failing test can prove it is unreliable. So "it runs on the customer's side" is very weak evidence.
  • An FDE's custom code is written for a single customer and often has no tests. Yet the people who will modify that code later are the customer's team.
  • A handoff should include: a numerically defined "working" standard, a test for each behavior, a regression test for each defect, and upstream PRs with reproduction cases attached.

In Google's book *Site Reliability Engineering*, the chapter on reliability testing opens with a brief epigraph: untested things should be treated as broken. A few paragraphs later, the book goes further: a passing test does not necessarily prove a system is reliable, but a failing test usually proves it is unreliable.

Before messaging the customer to say "done, it's running on-site," think about those two sentences. Looked at closely, one smooth run in the customer's production system is nothing more than passing a single test. Nobody wrote that test down, and nobody can run it again.

This matters because every Forward Deployed Engineer (FDE) project ends with a handoff. Educative's course on FDEs for AI systems says that a customer team cannot operate what it does not understand, nor maintain something designed only for the FDE. From the day of the handoff, the question changes from "does it work?" to "is it safe to change?"

What does one smooth run actually prove?

Consider a typical scenario. You write a script for the customer: it reads order export files from the old system, normalizes date and currency formats, and loads the data into the new data warehouse. The script runs smoothly on the last three days of data, the customer looks at the dashboard, and nods.

That run proves three things: the file formats for those three days match your assumptions, the access permissions are configured correctly, and every step of the data pipeline completed without failure.

As for what happens when some branch's export switches date formats, when a row is missing a customer ID, or when the customer's engineer renames a column next month, that run tells you nothing. None of those things have happened yet, so a smooth run naturally provides no information about them.

To be fair, running on real data is essential. PostHog's article on the FDE role says that an FDE keeps pushing forward with the customer until the customer sees real results on real data. But that is a condition of acceptance, not evidence that the system can withstand change.

The SRE book makes the distinction precise: every test that passes both before and after a change reduces the uncertainty an analyst has to consider. The key words are "before and after." That one smooth run on-site has no "after," because nobody reruns it when the code changes.

Why does FDE code often have no tests?

The main reason lies in how the work is organized. When code is written for a single customer and results are due before a demo, tests are the first thing to get cut.

The rationale sounds reasonable: the code is used in only one place, and you are right there to fix anything that breaks. But that rationale only holds until you leave.

In a Substack post on the Field-to-Product model, Second File warns about two things: custom code that exists only in one customer's account, and the "hero" engineer who becomes a single point of failure. Untested code turns you into exactly that hero, because you are the only one who knows what it should and should not do.

The people who inherit the code pay the price

*Software Engineering at Google* writes that there is another equally important reason to test software: preserving the ability to change it. For a project about to be handed off, the consequence is direct. Untested code can still be changed, but for the customer's team, every change is a gamble.

And the cost grows over time. The same book says that the later a defect is found in the development lifecycle, the more expensive it is to fix, often exponentially so. For FDE code, the latest possible moment is when the author has already moved on to another project and the defect surfaces in the customer's production environment.

Tests also accomplish something written documentation rarely does. A short test that checks a single behavior can tell the customer's team how you intended the script to handle rows without a customer ID. It is more reliable than any wiki page, because it runs.

What does handoff evidence look like?

If one smooth run is not enough, what is? The table below puts the smooth run in the first row as a baseline, then lists five other categories of evidence. Each category answers a different question, and none can substitute for the others.

EvidenceWhat it provesWhat it does not proveWho needs it most
One smooth run at the customer siteThe code did not fail on that day's data and configurationThe code can handle new data, new configurations, or new changesThe customer during the demo
Numerically defined "working" criteria agreed on at the project's startBoth parties agree on what success meansWhether the code is easy to maintainThe customer's project lead
Automated tests, each verifying a single behaviorExpected behavior still holds after every changeThe code meets the customer's business goalsThe customer's engineers when modifying the code
Regression tests written from on-site defectsKnown defects will not reappearDefects no one has encountered yetWhoever modifies the code where each defect occurred
Scheduled production environment testsThe production system stays healthy over timeWhether a specific change broke a specific behaviorThe operations team
Upstream PRs with reproduction cases attachedThe fix has found a home in the core productWhether the customer's remaining custom code is reliableThe product team

An FDE playbook published by Truong Phung on dev.to captures this distinction in one contrast: a consultant leaves behind documentation, while an FDE leaves behind a running system and the organization's ability to operate it. The five categories of evidence below the first row of the table are that ability, in a form the customer's team can verify on its own.

The playbook also recommends defining the deliverables you will leave behind from the very start, including evals, runbooks, and training for the customer's owner, rather than leaving them to the end. The author warns that without them, the system will decay within 90 days of your departure.

Turn every on-site defect into a test

Building a complete test suite for legacy code is not required. The simplest starting point is to record every defect found on-site as a test case. For an FDE, this adds almost no cost, because when fixing a defect, the input that triggered it is right at hand.

Back to the order script. Suppose that in the second week, a branch sends a file where dates are written as day-month-year, but the script reads them as month-day-year.

You fix it, then spend ten more minutes writing a test using those three rows of data to check that the dates are parsed correctly. From then on, whenever a customer engineer modifies the date parsing function and breaks this scenario again, the test fails immediately.

The next step is moving what is worth keeping into the product. The Field-to-Product article summarizes this generalization step in one sentence: push abstractions and tests upstream, and retire local patches.

The date parsing defect above is a good candidate. If the product itself has an import feature, that test belongs in the product repository, not just in some customer's custom directory.

Timing decides success or failure. Most of this work must begin in the first week of the project, not the last, because of what tests written late actually do.

What do tests written in the last week actually check?

The most common mistake is assuming that production checks are enough. Production testing is essential, but it only tells you the system is still healthy; it can't tell you which behavior your last change broke.

A subtler mistake is cramming all the tests into the final week. Tests written at that point often just document the code's current behavior. A freeCodeCamp tutorial puts it clearly: such tests don't prove the existing behavior is correct; the author writes that they are merely recording behavior, not claiming it is right.

This technique is useful when refactoring legacy code. But if the test suite you hand over consists entirely of such tests, you are freezing your own mistakes and handing them to the client team as expected behavior. Tests written while you were still asking the client "how should lines without an ID be handled?" capture intent, not the status quo.

Another trap is writing one giant test that checks everything from the input file all the way to the dashboard. When it goes red, the client's engineers have no way to tell which behavior broke. The final trap is fixing a defect on-site without leaving a test behind, and keeping the fix on a custom branch forever. The defect may come back, and the core product will never know it existed.

What do hiring managers want to see?

On a resume, "deployed a data pipeline for client X" carries no more weight than a smooth run. "Attached a regression test for every defect found on-site at handoff; subsequent fixes were shipped independently by the client team" says far more.

In interviews, be ready to walk through a specific defect: how you reproduced it, what the test looked like, and which repository that test lives in now.

A smooth on-site run gets you the acceptance signature. How well the handoff went only becomes clear when the client team makes their first code change without having to call you.
