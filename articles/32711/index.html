How to Do Data Reconciliation: A Guide to AI Project Delivery Acceptance

Original title: 数据对账怎么做：AI 项目交付验收指南

FDE Times · 2026-10-09 · 6 min read

Summary

This guide adapts accounting reconciliation discipline to AI project acceptance, aimed at forward deployed engineers whose dashboards look green but whose numbers don't match the client's ledger. It prescribes a concrete workflow: agree on written tolerance thresholds with the client (defaulting to zero), run aggregate checks (row counts plus SUM, MIN, MAX, AVG per numeric column), break down discrepancies by day to expose timezone mismatches, then row-level compare only records exceeding thresholds. A hypothetical example shows a UTC/local-time mismatch inflating totals by 18,640.25. The article stresses starting reconciliation in week one, building evidence packages, and having an independent reviewer sign off before go/no-go decisions.

Key points

  • Matching row counts proves nothing; aggregate every numeric column.
  • Date discrepancies usually stem from timezone mismatches; split by day first.
  • Thresholds must be written down with the client, defaulting to zero.
  • Run automated reconciliation checks from week one, not at acceptance.
  • An independent reviewer must sign off; builders can't certify their own output.

Borrow the reconciliation discipline from accounting: agree on tolerances in advance so that any discrepancy can be explained on the spot, without ever saying "I'll look into it later."

Key Takeaways

  • Matching row counts proves nothing. For every numeric column, compute SUM, MIN, MAX, and AVG to catch truncation, rounding, and precision loss.
  • Timezone mismatches are the most common error in date data. Break down discrepancies by day first before looking elsewhere for causes.
  • Thresholds must be written down in black and white, defaulting to 0. Reconciliation materials must pass independent review before a go/no-go decision.

Acceptance meetings often fail in a familiar way. You project the dashboard onto the screen: the agent has finished reading all of October's invoices, the data pipeline reported no errors, and total revenue is displayed. The client's controller opens the ledger, pauses for a moment, and asks: why doesn't this number match?

From that moment on, the project is no longer about how good the model is. The only question is: can you explain the discrepancy? If you can answer on the spot, the client will trust you; if you say "let me check and get back to you," the entire system comes into question.

The skill of reconciliation helps you avoid this situation. The accounting profession has been doing this for a long time: account reconciliation means checking internal records one by one against external statements or source documents. This guide explains how to bring that discipline into AI projects, so that "the system works" becomes a provable conclusion.

What is reconciliation, in plain language?

The documentation of the data quality tool Soda defines a reconciliation check as: verifying whether a target dataset is consistent with one or more source datasets. It operates at two levels. At the aggregate level, it compares metrics such as row counts and totals; at the row level, it compares records one by one.

For a Forward Deployed Engineer (FDE), the "target" is what your system produces: the invoice table extracted by the agent, an inventory forecast, or data migrated to a new warehouse. The "source" is the truth the client recognizes, usually the general ledger, an ERP system, or an Excel file the finance team has already closed.

One small concept determines everything: thresholds. Soda requires that acceptable discrepancies be defined as thresholds, with a default of 0. This default fits the accounting spirit well: if a threshold hasn't been written down, no discrepancy counts as "acceptable."

In what order should you reconcile?

Comparing row by row across the full dataset is expensive and slow. Soda recommends a more cost-effective order: run aggregate checks first (row counts, totals, averages), then selectively compare rows for the most important datasets.

Counting rows alone is not enough. A migration testing guide from Xylity recommends computing SUM, MIN, MAX, and AVG for every numeric column. Two tables might both have 4,812 rows, but one of them may have been truncated or rounded. Row counts won't reveal such errors, but totals and extremes expose them immediately.

The same guide points out that timezone mismatches are the most common error in date data. So after aggregate comparison, the next step should be breaking down discrepancies by day. If discrepancies cluster on the first or last day of a period, timezone is usually the prime suspect.

A Complete Example

The following example is hypothetical, and so are the numbers. A distributor in UTC+7 asks you to build an agent that reads invoices and writes to a

ai_invoices

table. The agent stores invoice timestamps in UTC in a

invoice_ts

column, while the finance team closes the books in a

ledger_invoices

table whose

invoice_date

column uses local time.

Before comparing, you and the controller agree in writing: the row count discrepancy must be 0; due to rounding rules, each invoice's amount may differ by at most 0.01.

In the first round, run an aggregate query, filtering October data by the column each side actually stores:

SELECT 'ai' AS src, COUNT(*) AS n, SUM(amount) AS total,
       MIN(amount) AS mn, MAX(amount) AS mx, AVG(amount) AS avg_amt
FROM ai_invoices WHERE invoice_ts >= '2026-10-01' AND invoice_ts < '2026-11-01'
UNION ALL
SELECT 'ledger', COUNT(*), SUM(amount), MIN(amount), MAX(amount), AVG(amount)
FROM ledger_invoices WHERE invoice_date >= '2026-10-01' AND invoice_date < '2026-11-01';

Suppose both sides have 4,812 rows, but the agent's total is 18,640.25 higher than the ledger. Matching row counts often lead to premature reassurance, but here it only means the errors are canceling each other out. So you break it down by day, casting

invoice_ts

to DATE to get the dates on the agent's side:

SELECT d, SUM(ai_amt) - SUM(ledger_amt) AS diff FROM (
  SELECT CAST(invoice_ts AS DATE) AS d, amount AS ai_amt, 0 AS ledger_amt FROM ai_invoices
  UNION ALL
  SELECT invoice_date, 0, amount FROM ledger_invoices
) t GROUP BY d HAVING SUM(ai_amt) - SUM(ledger_amt) <> 0 ORDER BY d;

This query deliberately does not filter by period. If you keep the October condition, you won't see the invoices pushed into adjacent months.

The discrepancies cluster on September 30, October 1, October 31, and November 1, which is the signature of a timezone problem. Since

invoice_ts

is UTC, an invoice issued at 6 a.m. local time on November 1 becomes 11 p.m. on October 31, and gets counted in October.

The fix is: first convert

invoice_ts

to the timezone the client uses for closing, then take the date, filter by period, and rerun. In this example, the total discrepancy drops from 18,640.25 to 0.37.

The remaining 0.37 is what deserves row-by-row comparison, and only over a very small range: invoices whose discrepancy exceeds the 0.01 threshold.

You find a few invoices where the agent rounds tax per line item, while accounting rounds on the total. This rounding error only surfaces after the timezone fix, because before that it was drowned out by the larger discrepancy.

Hands-On Practice: From Thresholds to Sign-Off

Before writing any SQL, ask the client: what is the source of truth, which timezone does the closing period use, and what is the discrepancy threshold for each metric. Write these on one page and send it to the client for confirmation. If no threshold has been agreed, treat it as 0.

Next, build layered automated checks. Xylity's model has five layers: the first three run automatically and are rerun after each iteration; the last two are confirmed manually before cutover to the new system.

For AI projects, the three automated layers can be: row counts, aggregate values for each numeric column, and daily discrepancies. Run them every time you modify a prompt, switch models, or adjust the data pipeline.

Then comes the evidence package. Solvexia's account reconciliation guide requires that, for every account reviewed, you record an explanation, the calculations, and the evidence. In the example above, the evidence package includes: each query, the results before and after the timezone fix, and a list of invoices with rounding discrepancies along with how each was handled.

The final step is sign-off. Again according to Solvexia, reconciliation results must be reviewed by an independent third party before being finalized. That reviewer cannot be you, because you built the system. Like Xylity's model, set an explicit go/no-go gate: only proceed with cutover when every layer has passed.

Mistakes That Cost You Trust

The first mistake is putting off reconciliation until the end of the project. An article on the Databricks engineering blog points out that teams that treat validation as an afterthought end up spending more time on reconciliation than on the migration itself. If the three automated layers run from the first week, every error is caught as soon as it appears.

The second mistake is stopping once row counts match. As the example shows, row counts can match while two different errors happen to cancel each other out. The third mistake is setting thresholds yourself, for example privately deciding that a discrepancy below 0.1% is "acceptable." That number should be decided by the client, not you.

The fourth mistake is endorsing your own system. If you wrote the data pipeline and you sign off on the results, you've skipped the very principle your client's finance team follows every month.

How should you showcase this skill when job hunting?

When reading job descriptions, watch for phrases like "data migration," "financial data," and "production validation." These teams need people who can reconcile. On your resume, don't write "ensured data quality"; instead, be specific: which data source you reconciled results against, what the thresholds were, and who signed off.

In interviews, be ready to answer questions like: "Tell me about a time when your system's numbers didn't match the source data. How did you find the cause?" A good story has four key points: how big the discrepancy was and who discovered it; the order in which you investigated; what the real cause turned out to be; and who signed off on the final result.

Stories like this are usually more persuasive than any model accuracy figure. The reason is that customers won't judge your system by accuracy—they'll judge it by whether your numbers reconcile with their ledgers.
