The Difference Between AGI and Agents: How FDEs Manage Customer Expectations

Original title: AGI 和 Agent 的区别：FDE 如何管理客户预期

FDE Times · 2026-10-08 · 6 min read

Summary

This article explains how forward deployed engineers (FDEs) should handle executives who expect an all-purpose “AI employee.” Such a vision matches the definition of AGI, which remains hypothetical, while what FDEs can actually deliver is an Agent assembled from tool calls, workflows, and human approvals. Citing Anthropic's tool use documentation, the author notes that models only propose calls that applications execute, and may fabricate plausible values when required parameters are missing. Autonomy raises costs and compounds errors: at 95% per-step accuracy, ten consecutive steps succeed only about 60% of the time. The recommended approach is to start with fixed workflows, test in sandboxes, and expand autonomy based on data, turning vague expectations into a scoped, approvable plan.

Key points

  • The “AI employee” executives imagine is AGI, which remains theoretical and unpurchasable.
  • Agents depend on which tools are integrated and how they are described; models only propose calls.
  • Missing required parameters can lead models to invent plausible values, so systems must force clarification.
  • Autonomy compounds errors: 95% per-step accuracy yields only ~60% success over ten steps.
  • Start with workflows, add autonomy gradually, guided by sandbox testing and milestone data.

Key takeaways

  • The "AI employee that can do everything" customers describe is AGI. By the commonly accepted definition, AGI remains theoretical—it is not a product anyone can buy.
  • What an agent can do depends on which tools the engineering team connects and how well those tools are described. The model only proposes calls; the application does the executing.
  • Start with the simplest solution, usually a fixed workflow, then add autonomy later, because autonomy brings higher costs and accumulating errors.

In 1965, Herbert Simon predicted that within twenty years, machines would be able to do any work a human can do. More than sixty years later, that promise lives on under a new name: the "AI employee."

Every Forward Deployed Engineer (FDE) will sooner or later face this moment: an executive on the customer's side watches a few demos, reads a few news articles, and then asks when they can get an AI employee that can independently handle everything. The question is entirely reasonable.

The trouble is that it conflates two very different things. If you don't separate them in the first meeting, the project will be measured against a standard that no system today can meet.

What the customer envisions is AGI; what the FDE can deliver is an agent. The gap between the two cannot be closed by waiting for smarter models—it must be bridged by design, and that design is drawn up by the FDE together with the customer.

"Can do everything" has had a name for a long time, and it remains hypothetical

Wikipedia defines AGI as a hypothetical form of artificial intelligence that matches or exceeds human performance on nearly all cognitive tasks. The key word is "hypothetical." An AI employee that handles everything fits this definition almost verbatim—which means it is not something anyone can buy or deploy yet.

What runs in enterprises today is narrow AI, also called weak AI: it can solve specific problems but lacks general cognitive ability. The distance between the systems an FDE deploys and the picture in an executive's head is exactly this gap.

Arguing about when AGI will arrive is a trap. Simon's prediction failed. Geoffrey Hinton once said AGI was "30 to 50 years away, or even longer," and later he himself substantially revised that number. When the most authoritative figures in the field disagree this much, debating timelines only derails the meeting.

A better framing is: that thing doesn't exist yet, and here is what we can build this quarter.

What you deliver is an agent, assembled from components

DAIR.AI's Prompt Engineering Guide defines an agent as a system that uses an LLM and is designed to act autonomously and solve complex tasks. Agents exist for a very practical reason: once a task requires multiple steps, planning, and reasoning, an LLM alone falls short.

So you add planning and self-checking, tool-calling capability, and memory.

In other words, the "AI employee" is a system assembled by engineers; there is no universal mind behind it, and every component in the assembly has its own limitations.

Anthropic's tool use documentation shows how concrete these limitations are. Claude does not execute anything itself. It returns a structured call, which is then executed by the developer's application (client-side tools) or by Anthropic (server-side tools).

Moreover, the model only calls a tool when the request matches the tool's described capability and the answer is not already in the context.

This sentence is the anchor for the entire conversation. It shifts the question from "Is the AI smart enough?" to "Which systems do we connect it to, and with what permissions?"—and the latter is a question the customer's management can decide.

From what the customer says to what the FDE should ask back

The table below maps common expectations to actual system behavior. The last column contains the questions to ask back, turning expectations into scope of work.

The third column is exactly where the FDE's value lies: reading technical documentation and translating it into questions that help the customer make decisions. This is a core skill of the job.

A complete example: a refund agent

Suppose a retail chain (fictional) wants an "AI customer service employee" that also handles refunds. The agent gets three tools: look up orders, check the return policy, and initiate a refund. A customer writes: "I want to return the shoes I bought last week," but provides no order number.

Anthropic's documentation warns that when required parameters are missing, the model may infer a plausible-sounding value. Here, "plausible" could mean another customer's recent shoe order. A human employee would ask. With an agent, you cannot leave it to chance: the system must be designed to ask.

There is also the problem of error accumulation, which Anthropic explicitly lists as the cost of autonomy. The following is illustrative arithmetic, not measured data: if the agent's accuracy at each step is 95%, the probability of all 10 consecutive steps being correct is only about 60% (0.95 to the 10th power ≈ 0.599).

This number alone helps an executive understand why "letting it decide on its own" is a risky decision.

The way out lies in Anthropic's distinction between two types of systems. Workflows orchestrate LLMs and tools through predefined code paths; agents let the LLM direct the process itself. For refunds, looking up orders and checking the policy are inherently fixed steps, so writing them as a workflow makes sense.

Only understanding the customer's message and drafting the reply requires the model's flexibility.

According to Anthropic, agentic systems often trade latency and cost for better task performance. Some scenarios are worth that trade; not all are. In this example, the refund itself should require human approval, unless data from a sandbox trial run shows it can be relaxed.

This aligns with Anthropic's own advice: test thoroughly in a sandbox environment and set up guardrails.

Saying "not yet" without deflating the room

The most common mistake is to dismiss it outright: "What you want is AGI; nobody can build that." That's true, but it kills the enthusiasm that brought the FDE into the meeting room in the first place. A better approach is to first acknowledge the goal, then sketch a path toward it in three steps:

  • Point out what the customer is envisioning and be candid that it remains theoretical.
  • Together, list specific tasks and pick one with a clear process to build first as a workflow.
  • Agree on a few milestones, at which point data will decide whether to grant more autonomy.

Anthropic's advice is: find the simplest possible solution and add complexity only when needed. Bring this sentence into the meeting. It is essentially a prioritized plan that decision-makers can approve, track, and measure—and no one will hear it as a rejection.

A skill worth practicing: turning expectations into scope

Many developers, in Vietnam and elsewhere, write strong code but rarely practice turning vague expectations into concrete scope, which is a skill FDEs use every day. Try explaining AGI, narrow AI, and AI agents in words a sales director would understand on first hearing.

When reading job descriptions, watch for phrases like "translate business requirements," "scope with stakeholders," or "customer-facing." On your resume, don't just write "built an AI agent with LLMs"—spell out where you chose a workflow over an agent, where you added approval steps, and why.

A small personal project is enough: an AI agent with a few tools, plus a one-page document recording cases with missing parameters and how you forced the model to ask. That page shows how you think about a system's boundaries, which a "can do everything" demo will never reveal.

Simon's promise fell through because it bet that machines could figure out on their own what people want. The FDE's job is to avoid that bet: sit down with the customer, write down every task they need to accomplish, then equip the AI agent with exactly the tools needed to complete each task.
