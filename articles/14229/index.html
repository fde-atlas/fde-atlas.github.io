The FDE Handbook

Fieldwork · 2026-11-15 · 2 min read

Summary

Fieldwork offers a free, open 17-chapter FDE Handbook (~3.5 hours of reading) covering the full arc of forward deployed engineering: uncovering the real problem behind a customer's request, designing the lightest system that solves it, proving it works with evals and unit economics, and landing it in production. Each chapter uses original customer scenarios, one redrawable diagram per idea, and exercises with worked answers, crediting public frameworks to their authors. Later chapters cover FDE interviews and building demonstrable proof of work.

Key points

  • Free 17-chapter handbook, ~3.5 hours, readable in order or by chapter.
  • Core arc: find the real problem, build the lightest system, prove it, land it.
  • Advocates workflows before agents, climbing the tool ladder only as needed.
  • Covers evals, cost sizing, security, and autonomy granted per action.
  • Includes interview guidance and how to spot a genuine FDE role.

Designing the system

Choosing the lightest tool, then building workflows, tools, retrieval and state that hold up.

  • 06The lightest tool that worksRules, classifiers, models, workflows, agents: climb the ladder only as far as the problem needs, and price every rung. 11 min
  • 07Workflows before agentsMost requests for an agent are better served by a workflow you design. Five patterns, three lanes, and exits to a person built first. 15 min
  • 08Giving models hands: tools and integrationsLetting a model act on real systems safely: tool loops, honest results, protected writes, identity and MCP. 14 min

  • 10State, memory and agent boundariesWhere conversation state lives once there are two servers, and where to draw the lines when one agent becomes several. 12 min

Troubleshooting with journalctl When a systemd service fails to start after a reboot, you can troubleshoot it step by step using `journalctl` and related tools. ## 1. Check the service status ```bash systemctl status your-service.service ``` Focus on: - **Active**: whether it shows `active (running)`, `inactive`, or `failed` - The last few log lines, which usually contain the direct reason for the failure ## 2. View logs with journalctl View logs for the specified service: ```bash journalctl -u your-service.service ``` Only show logs from the most recent boot: ```bash journalctl -u your-service.service -b ``` Show only errors: ```bash journalctl -u your-service.service -p err -b ``` View logs from the previous boot (useful if the service failed during startup): ```bash journalctl -u your-service.service -b -1 ``` Follow logs in real time: ```bash journalctl -u your-service.service -f ``` Show the most recent 50 lines: ```bash journalctl -u your-service.service -n 50 --no-pager ``` ## 3. Common causes and solutions ### 1. The service is not enabled for auto-start on boot ```bash systemctl is-enabled your-service.service ``` If it shows `disabled`, enable it: ```bash sudo systemctl enable your-service.service ``` ### 2. Startup order dependency issues If the service starts before the network or a dependency is ready, it may fail. Check the unit file: ```bash systemctl cat your-service.service ``` Add or adjust: ```ini [Unit] After=network-online.target Wants=network-online.target ``` Then reload the configuration: ```bash sudo systemctl daemon-reload ``` ### 3. Restart behavior configuration If the process crashes and is not restarted, check the unit file: ```ini [Service] Restart=on-failure RestartSec=5 ``` ### 4. Permission or path issues - Check whether the user/group specified by `User=` and `Group=` exists and has sufficient permissions - Check whether the paths in `ExecStart=` are correct and the files are executable - If the service depends on a mounted disk, confirm that the mount is complete at boot time (add `RequiresMountsFor=`) ### 5. Environment variable issues Services started by systemd do not inherit the environment variables from your shell. If the service runs fine manually but fails at boot, it is often an environment variable problem. You can add: ```ini [Service] Environment="VAR=value" EnvironmentFile=/etc/your-service/env ``` ## 4. Other troubleshooting tips - **Check all failed units**: ```bash systemctl --failed ``` - **Check the full boot logs**: ```bash journalctl -b ``` - **Check for logs being lost**: if `journalctl` shows no historical logs, confirm that persistent logging is enabled: ```bash sudo mkdir -p /var/log/journal sudo systemctl restart systemd-journald ``` - **Manually run the ExecStart command**: switch to the corresponding user and run the command from `ExecStart=` directly to see the actual error output. ## 5. Typical troubleshooting workflow 1. `systemctl status` to confirm the failure status and initial error 2. `journalctl -u <service> -b` to view detailed logs 3. Check the unit file with `systemctl cat` to confirm dependencies, restart policy, and user permissions 4. Fix the configuration, then run `daemon-reload` and restart the service to verify 5. If necessary, reboot to verify that auto-start on boot works properly
