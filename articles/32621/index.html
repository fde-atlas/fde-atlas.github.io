What Skills Does an FDE Need in the Age of Coding Agents?

Original title: 编程智能体时代 FDE 需要什么技能

FDE Times · 2026-10-08 · 6 min read

Summary

Drawing on GitHub, Cognition, and Addy Osmani, this article argues that as coding agents accelerate code generation, the bottleneck shifts to three tasks agents cannot do: defining the user and success criteria, constraining agents through living specifications, and judging whether results create value. GitHub's analysis of over 2,500 agent configuration files found most fail because they are too vague. Cognition stresses enterprises want value, not busy systems, and evaluation cannot be automated away. The piece concludes FDE is a single role, not an assembly line, and offers advice for developers from outsourcing backgrounds on transitioning.

Key points

  • GitHub analyzed 2,500+ agent config files; most failed from vagueness.
  • Faster code generation pushes bottlenecks to testing, review, deployment, maintenance.
  • FDE's three tasks: define users and success criteria, maintain living specs, judge results.
  • Passing tests doesn't mean code is understood; review is now a throughput problem.
  • Judgment feeds back into definition; FDE is one role, not a pipeline.

Key Takeaways

  • GitHub analyzed over 2,500 agent configuration files and found that most failed for being too vague: the hard part is requirements specification, not generating code.
  • Cognition believes that faster code generation only pushes problems downstream to testing, review, deployment, and maintenance; enterprises want value, not a system that just looks busy.
  • The three tasks FDEs retain are: clarifying who the users are and what success looks like, writing specifications as living documents, and judging results by understanding the code rather than waiting for tests to pass.

According to Addy Osmani, GitHub analyzed over 2,500 agent configuration files and found that most of them failed for a mundane reason: they were written too vaguely. The people writing these files never made clear what they actually wanted.

This finding aligns with what Cognition presented at AI Engineer World's Fair 2026. In the company's view, generating code faster doesn't solve everything, because testing, review, deployment, and maintenance are all still there. The bottleneck hasn't disappeared; it has just moved.

For developers looking to transition into a Forward Deployed Engineer (FDE) role, this is a signal worth taking seriously. Typing code fast is no longer a skill anyone is willing to pay for. What's truly valuable are the three things an agent still can't do for you: define the problem, constrain the agent, and judge the results.

Outsource the execution, FDEs make the decisions

In an article on forward deployed AI engineering, Ghanemzadeh draws a clear line: outsourced personnel handle execution, while FDEs make decisions. As he describes it, an FDE is an opinionated operator who knows what to do, in what order, how to do it, and how to measure success.

The first question in the definition phase sounds simple, yet it's the one most often skipped: who is the user? Ghanemzadeh puts it bluntly: if you can't say who the user is, it isn't an FDE project at all. A requirement like "the client wants an AI agent" is just a wish, not a problem.

Take a bank that wants to use an agent to process loan applications. "Automate underwriting" sounds specific, but it gives no direction at all.

Change it to "the branch underwriters who spend most of their day verifying documents," and you immediately know what to measure, what to solve first, and what "done" looks like.

The agent can't do this step on its own. It won't sit next to the underwriters, and it can't see which tasks make them sigh. So definition remains the job of the people on the front line.

Constraints are a living specification, not a prompt

An article on the fde.academy blog describes the engineer's new role when working with agents as: define the task, set constraints, then guide the agent. This is a practitioner's perspective, not a research conclusion.

Even so, it matches GitHub's finding above: agent configuration files fail for being vague, meaning the failure happens at the constraint stage.

Osmani cites GitHub's spec-driven development approach: the specification becomes the shared single source of truth, an executable living document that evolves with the project.

The word "living" is key. A specification isn't something you write once at project kickoff and then archive; it's a contract between you, the client, and the agent, updated whenever new discoveries emerge on the ground.

Back to the bank example. A good constraint might be: "The agent only flags applications with missing documents; it never rejects any application on its own." This one sentence does two things: it limits the agent's behavior, and it records a business decision that everyone writing code later must follow.

Writing that sentence requires understanding the client's risks—prompt syntax alone won't get you there. So constraints connect directly to definition: if you don't know who the users are, you don't know what must never happen to them.

Why judgment has become the new bottleneck

If definition and constraints are the inputs, judgment is where the pressure concentrates. Osmani states the problem directly: AI generates code far faster than humans can evaluate it, and review has become a throughput problem.

Many teams' first instinct is to rely on tests. Osmani agrees that tests are essential, but he's clear that they aren't enough. Tests can only check the cases the author thought of; whether the code actually meets the client's needs still has to be answered by someone who understands the code.

He goes further, pointing out that the common organizational assumption that "reviewed code is understood code" no longer holds. When one person approves dozens of agent-written PRs a day, the approve button only shows the code was looked at—it proves no one truly understood it.

Cognition pushes this argument to the enterprise level. Large companies in heavily regulated industries want to know whether a system creates value; they don't care how busy it is. An agent can run all night and submit hundreds of PRs while delivering nothing.

Distinguishing "busy" from "valuable" is a judgment, and that judgment rests on the definition of success set at the very beginning. The conclusion of that fde.academy article is that the judgment layer won't be automated just because the code-writing layer got faster. That's an opinion, but the evidence from both Osmani and Cognition leans toward it.

Three tasks, three ways to fail

Looking at the three tasks together, each has its own failure mode, and any one of them can be masked by a very hardworking agent.

FDE taskQuestion to answerWarning signsHow to practice
DefinitionWho is the user, what comes first, how is success measured?Can't say who the user is; the requirement is just "build an AI agent"Write a one-sentence description of the user for every ticket, plus one success metric
ConstraintsWhat can the agent do, and what must it never do?Configuration files or specifications are vague; the spec is written once and then abandonedMaintain the specification as a living document, updating it every time the agent makes a mistake
JudgmentDoes the result create value, and do you understand the code?Treating passing tests as done; treating reviewed as understood; mistaking "busy" for "valuable"Explain every change yourself before approving; measure results against the defined criteria

Judgment feeds back into definition

Cognition describes client delivery and product feedback as a closed loop: what's learned in the field flows back and informs product decisions. Mapped onto these three tasks, the loop takes a clear shape: judgment at the end feeds information back to definition and constraints at the front.

When judgment shows the results aren't creating value, there's a practical debugging approach: before blaming the agent, check whether the right user was identified and whether any vagueness remains in the specification. Fixing the inputs is usually cheaper than fixing the outputs.

This is also why the three tasks are hard to split among three people. The person who defines the user should be the one who judges the results; otherwise, no one will notice when the specification has drifted from reality. So the FDE is a role, not an assembly line.

Demand for this role is growing. The Pragmatic Engineer reports that Google, OpenAI, and Anthropic are hiring FDEs aggressively. When the companies building agents are also hiring people to stand between agents and clients, it's not hard to guess what skills they're missing.

What Vietnamese developers should practice

Many Vietnamese developers come from an outsourcing background, where requirements are defined on the client's side and the team just executes. This is exactly the outsourced personnel model Ghanemzadeh describes. Moving into an FDE role means learning to ask the questions that someone else used to answer for you, and this applies to developers coming from any delivery-focused company.

Start with your current work. Before handing a ticket to an AI agent, write one sentence describing who the user is, one measurable success criterion, and three constraints the agent must not violate. If you can't write these, the ticket isn't ready yet, whether it goes to an agent or a human.

When reading FDE job descriptions, watch for phrases like "working directly with customers," "defining requirements," and "owning outcomes."

On your resume, don't just list the features you built; clearly state how you identified the users, what success criteria you set, and how you verified the system created value, rather than just running.

AI agents will only get faster at writing code. Recruiters won't ask how many lines of code you can generate; they'll ask whether you know which code is worth keeping.
