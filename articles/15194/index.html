NVIDIA SkillSpector Review: What the Agent Skill Scanner Catches, What It Misses, and What SAFE Means

FDE Interviews · 2026-11-12 · 11 min read

Summary

The author tested NVIDIA's open-source SkillSpector 2.13.4 on seven self-written agent skills inside a disposable Docker container, static analysis only. It reliably caught a token-exfiltration script and outdated dependencies with known CVEs, but instruction-only attacks slipped through: a skill whose hidden comment told the agent to copy the conversation and stay silent scored 7, SAFE. The verdict follows the summed 0–100 score rather than the worst finding, and the default CI exit code only fails above 50. The recommendation: gate on findings, not the SAFE label; run the LLM stage on instruction text via an approved provider; and pair scanning with hash pinning, human review of scripts, and runtime restrictions.

Key points

  • Static analysis caught token exfiltration and vulnerable dependencies with high confidence.
  • A hidden 'never tell the user' instruction scored 7 and was labeled SAFE.
  • Verdicts use the summed score, so HIGH findings can sit inside CAUTION or SAFE.
  • Default CI exit code fails only above 50, passing all three reject-worthy skills.
  • Recommended rollout: gate on findings, LLM review of instructions, hash pinning, sandboxing.

We ran NVIDIA's open-source SkillSpector 2.13.4 on seven test skills. It caught a token sender and outdated dependencies, but with LLM analysis off a hidden 'tell no one' instruction scored SAFE. How to read its score and gate on it.

BY JAMES BENNETT · FDEINTERVIEWS EDITORIAL · UPDATED NOVEMBER 12, 2026 · 9 MIN READ

PRACTICE THIS:Design the controls for coding-agent plugin hooks ·AI security and governance questions ·Agent sandboxing, the concept ·The must-know FDE questions

NVIDIA SkillSpector is a free, open-source scanner that reads an AI agent skill before you install it and scores how risky it looks. We ran version 2.13.4 on seven skills we wrote for the test. It flagged the two obvious threats firmly: a script that posts a token to a server and a pair of outdated, vulnerable dependencies both scored DO NOT INSTALL. With the optional LLM stage turned off, though, three skills that a careful reviewer would reject came back SAFE, including one whose hidden comment told the agent to copy the conversation to a gist and never mention it. Our verdict: adopt it as one gate, run the LLM stage on instruction text, and fail builds on findings rather than on the SAFE label alone.

What SkillSpector is

An agent skill is a folder: a

SKILL.md

file of instructions, often with scripts the agent can run. Claude Code, Codex CLI, Gemini CLI and other agents load skills with the user's permissions, and community marketplaces now distribute them by the thousand. That makes a skill a supply-chain artifact in the same sense an npm package is, with one twist: part of the payload is prose the model obeys.

SkillSpector, released by NVIDIA under Apache 2.0, scans a skill from a directory, a single file, a Git repository, a URL or a zip. It has two stages:

  • Static analysis. Regex patterns, Python AST checks for calls such as 
    subprocess
    and 
    eval
    , taint tracking from secrets to network calls, YARA signatures, and a dependency lookup against OSV.dev. Version 2.13.4 lists 71 patterns across 17 categories, from prompt injection and data exfiltration to MCP tool poisoning. The screenshots circulating this week say 64 and 16, which is an older README.
  • LLM semantic review (optional). A configured model reviews the static findings for context and intent. Its README is careful here: a confirmed finding can gain confidence, a disputed one is tagged 
    llm-unconfirmed
    , and every deterministic finding stays in the report. The stage does not delete findings, and the README says it does not guarantee a precision rate.

The output is a 0 to 100 score with a recommendation, in terminal, JSON, Markdown or SARIF form. SkillSpector is also part of NVIDIA's Verified Skills pipeline, which scans and signs skills before they appear in NVIDIA's own catalog.

The numbers behind the pitch, read properly

The README and the posts sharing it cite one study, "Agent Skills in the Wild" (Liu et al., arXiv 2601.10338, January 2026). Three details change how its figures should be repeated:

Claim as shared What the paper says
"Across 42,447 skills, 26.1% were vulnerable" 42,447 were collected; 31,132 were analyzed. 26.1% of the analyzed set had at least one vulnerability pattern (about 8,126 skills).
"5.2% are malicious" 5.2% showed high-severity patterns "strongly suggesting malicious intent", a pattern-based estimate.
"LLM analysis pushes precision to around 87%" 86.7% precision and 82.5% recall belong to the paper's own SkillScan method, not to SkillSpector's LLM stage.

A follow-up by the same lead author (arXiv 2602.06547, February 2026) collected 98,380 skills and verified behavior dynamically. It confirmed 157 malicious skills, about 0.16%, and found over half came from one actor using templated brand impersonation. Different dataset, different method, so the two rates do not subtract. The useful reading is that careless and risky skills are common, while confirmed malicious ones are rarer and deliberate. Its title, "Do Not Mention This to the User", turned out to describe our hardest test case.

What we tested

We built SkillSpector 2.13.4 from its Git tag inside a throwaway Docker container and scanned seven skills we wrote, mounted read-only. We ran static analysis only (

--no-llm

), because the LLM stage would have sent the files to a model provider and its result depends on which model you pick. Nothing we scanned was executed, by us or by the tool. The skills:

The first four rows are the tool working as advertised. The benign script got two cautionary findings and still scored SAFE, which is the right outcome for a reviewer's queue. The token sender and the stale dependencies were caught with high confidence.

The scanner saw something, labeled it correctly as prompt injection, and the arithmetic still produced SAFE. A gate that reads

issues

instead of

recommendation

would have stopped it.

The last three rows are the lesson. The split-string script is a well-known way to hide

os.system

from a pattern matcher. SkillSpector noticed the dynamic import and said so, but the score stayed at 13. The hidden-comment skills are instruction attacks: nothing in them is code. The one that named a credential file tripped a HIGH finding because of the path, and still landed in CAUTION at 22. The one that asked the agent to exfiltrate the conversation and conceal it named no file and no command, and scored 7.

How the score turns into a verdict

Reading the source explains the results. Findings add up to a 0 to 100 score; the score, not the worst finding, picks the verdict: 0 to 20 is SAFE, 21 to 50 CAUTION, 51 and above DO NOT INSTALL. The CLI exits nonzero only when the score is above 50. Three consequences for anyone wiring it into CI:

  • A HIGH finding can sit inside a CAUTION verdict, and a MEDIUM prompt-injection finding inside SAFE.
  • A default exit-code gate passes everything at 50 or below. In our set, that includes all three skills a reviewer would reject.
  • Instruction-level attacks are where static analysis is weakest, which is exactly the class the follow-up study found in the wild: adversarial instructions embedded in documentation.

None of this is a defect in the tool's honesty. The README states the stage-one profile plainly as "high recall" with "moderate precision", and lists runtime behavior and non-English text as limits. The risk is in how a team reads one word on a dashboard.

Data egress and the trust model

Two network paths matter before you run it on internal skills:

  • LLM analysis sends file contents to the provider you configure. SkillSpector supports OpenAI, Anthropic, Bedrock, Gemini on Google Cloud, NVIDIA Build, Azure OpenAI, local Ollama or vLLM, and others. For an internal skill that mentions hostnames or runbooks, pick an approved endpoint or a local model.
  • The dependency check sends package names and versions to OSV.dev, even with 
    --no-llm
    . It sends coordinates, not file contents, and falls back to a small bundled list when offline.

SkillSpector never runs the skill, and it is not a sandbox. It tells you what a skill looks like before install; it does nothing to contain a skill you install anyway. That containment is a separate control, covered in agent sandboxing.

How we would roll it out

For a team that lets engineers install skills, the order we would use:

  • Run static analysis on every new skill and every update, with SARIF output into the code-scanning view your security team already watches.
  • Fail the gate on findings, not the verdict. Any HIGH or CRITICAL finding, and any prompt-injection, exfiltration or dynamic-execution finding, goes to a person regardless of score. Use the baseline file to accept known, reviewed findings so re-scans show only new ones.
  • Run the LLM stage on instruction text through an approved provider, pinned to one model so results are comparable between scans.
  • Require a human read for any skill that carries scripts. The study found those 2.12 times more likely to contain vulnerabilities.
  • Pin installed skills by hash in an internal registry, and re-scan on every version change. A skill that was clean last month can ship a new script tomorrow; plugin lifecycle hooks have the same problem, as the coding-agent plugin hooks question works through.
  • Limit what an installed skill can reach: no ambient cloud credentials in the agent's environment, egress allowlists, and read-only mounts where possible.

After the scan: does the skill help at all?

A clean scan says a skill is unlikely to hurt you. It says nothing about whether the skill makes the agent better, and a skill that does not help still costs context on every session and competes with other skills for the agent's attention. NVIDIA's companion tool, SkillEvaluator, runs the agent on the same tasks with and without the skill and reports the difference. We read its published results for more than 400 skills in our SkillEvaluator review.

What to say about this in an interview

Skill and plugin supply chain is now a standard topic in AI security and governance rounds, because forward deployed engineers are the people installing agents inside customer environments. The strong answer is layered: vet before install with a scanner and a reader, pin what you install, contain what runs, and watch what it does. The weak answer names a scanner and stops. If you can explain why a 7 on a hidden "do not tell the user" instruction is a process problem rather than a tool bug, you are showing the judgment the round is testing. The broader pattern, reading untrusted content that a model will follow, is prompt injection in a new package.

It reads a skill without running it, applies static checks for 71 patterns in 17 categories (version 2.13.4), optionally asks an LLM to review the findings, and returns a 0 to 100 risk score with a SAFE, CAUTION or DO NOT INSTALL recommendation.

It means the total score was 20 or lower. It does not mean no problem was found. Discussion (4)

The split-string result is the one I would show a security team. Static analysis is pattern matching over text, and anyone writing a malicious skill on purpose will write around the patterns. That is not a knock on the tool. It is the reason the second stage exists, and the reason a SAFE from stage one alone should never be the last word on a skill that carries scripts.

Reader question: if the LLM stage is the part that reads intent, why not just always run it?

Cost and data. Every scan sends the skill's files to a model provider, which is fine for a public marketplace skill and a real question for an internal one that embeds runbooks or hostnames. Our default would be static on every change, the LLM stage through an approved provider on anything new or changed, and a person for any skill that carries scripts.

The paper's own number is worth keeping straight in a customer conversation. 26.1% is 'at least one vulnerability pattern', which includes a lot of careless code. The behaviorally confirmed malicious rate in the follow-up study was far lower. Both are reasons to vet, but they lead to different conversations with a CISO.
