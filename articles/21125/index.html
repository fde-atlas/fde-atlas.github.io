FDE Delivery Projects from Prototype to Production: Data Integration and Evals

Original title: FDE 交付项目从原型到生产：数据集成与评估

FDECareer.work · 2026-09-23 · 5 min read

Summary

Using a sample internal knowledge Q&A project, this article walks through how forward deployed engineers move from prototype to production. It recommends validating ingestion and serving pipelines separately, checking document versions, permissions and deletion sync, and building eval sets that include unanswerable questions, stale documents and unauthorized access attempts. Errors should be attributed to specific stages—retrieval, permissions, or generation—rather than the model alone. Launch requires evidence across correctness, access control, reliability, cost, human takeover and rollback, confirmed by business, data and technical owners. The author notes this is engineering guidance, not a real client case.

Key points

  • Validate ingestion and serving pipelines separately, including permissions
  • Eval sets must cover unanswerable, stale and unauthorized cases
  • Attribute failures to retrieval, permissions or generation stages
  • Launch gates require evidence confirmed by three owner roles
  • Agent systems need layered evals and deterministic fallback paths

Continue with the illustrative knowledge Q&A project from the previous article, connecting only a small set of authorized, stable documents with clear owners. The prototype should demonstrate a complete flow of question, retrieval, answer, and cited sources, while keeping a manual review entry point. Sample answers for demonstration cannot substitute for real evals.

Validate the data flow and permissions separately

A typical retrieval system has two pipelines: data ingestion and serving. The former parses, chunks, and builds the index; the latter retrieves and generates answers based on user requests. At every step, check document versions, access permissions, and sync behavior after deletion. The illustrative project must not send unauthorized internal materials to external models or public test sets.

Drive iteration with failure samples

The eval set should cover normal questions, questions with no supporting evidence, outdated documents, unauthorized access, and cases requiring human handling. Separately record whether retrieval found the right material, whether the answer is faithful to it, and whether citations are traceable, so that all system errors are not attributed to the model. After changing retrieval, prompts, or the model, rerun the same benchmark set.

Production thresholds

Only expand the user scope when sample quality, permission checks, failure fallback, latency, and cost meet the thresholds agreed in advance. The launch plan also needs version rollback, issue feedback, and a designated owner; these are engineering recommendations for the illustrative project, and no claim is made that any hiring company has adopted this approach.

First establish a minimal human-verifiable pipeline

Continuing the internal knowledge Q&A example, first let a single question pass through identity verification, retrieval, answer generation, citation checking, and human confirmation. Record the input, output, and failure reason at each step, so you can tell whether the problem lies in the documents, permissions, retrieval, or the model. At the prototype stage you may limit the number of users and documents, but do not omit this basic pipeline.

Keep a human in the loop for sending the final reply. Auto-writing or auto-sending adds execution permissions, duplicate requests, and recovery requirements; introduce it only when the business genuinely needs it and after separate acceptance testing. All of the following are engineering recommendations for the example project, not implementation notes for any employer's system.

Assign errors to fixable stages

Break down "the answer is bad" into locatable problems: no relevant material retrieved, outdated material retrieved, generated content exceeding the evidence, or the current user should not have access to that material at all. Each error type requires a different fix; tweaking only the prompt may mask data or permission defects.

The eval set should include ordinary questions, unanswerable questions, conflicting sources, outdated documents, unauthorized requests, and malicious instructions. Every time you change the model, retrieval, or chunking strategy, rerun the same set of baselines and keep the failure samples. Google Cloud's reference architecture and deployment guidance provide an engineering framework for designing evals; specific thresholds still need to be confirmed against this project's tasks.

Make every change reversible

Tie document versions, index versions, model configuration, prompts, and application code to the same candidate release. Record baseline results and known limitations before release, so that when problems occur you can identify which change caused them. Do not treat reverting code as automatically restoring all state: indexes, caches, and permission rules may also need handling.

First open access to a small group of authorized users, confirm that error messages, human takeover, and rollback paths work, then expand the pilot. If the previous version cannot be rebuilt, first complete version records and recovery steps.

  • Set explicit timeouts and failure responses for external dependencies; never leave users waiting indefinitely.
  • Keep only the information needed to locate faults in logs; handle sensitive questions and document content according to authorization.
  • Keep the previous version's working configuration, and rehearse whether permissions and citations remain correct after switching.
  • Include model, retrieval, and document changes in the same eval record.

Launch criteria: who checks, who decides

Continue with the acceptance table from the kickoff article, adding operational-level evidence. The business owner confirms whether the workflow is usable, the data owner confirms scope and permissions, and the technical owner confirms quality, capacity, and recovery. If any item lacks evidence, write it down as a pending condition rather than offsetting it with an overall score.

Failure example: demo passes, production still fails

An example system answers questions under a developer account but returns restricted documents under an employee account; or normal questions respond quickly, but a dependency failure causes endless spinning. Neither problem can be eliminated by more successful demos.

The former requires returning to access control and index isolation; the latter requires adding timeouts, visible failures, and human fallback. After fixing, keep the same failure samples as regression tests, then move into launch monitoring and handover. Production readiness is marked by handling known failures according to agreed procedures.

Build agent eval sets and fallback mechanisms

In real enterprise delivery, prompt tuning alone cannot guarantee the stability of agent systems. You must build layered eval sets (including gold-standard samples, multi-turn intent drift, tool call format errors, and privilege escalation probes). Design deterministic fallback plans for critical business nodes: when the model hallucinates, calls time out, or tools fail, automatically fall back to controlled rule-based pipelines or smoothly hand over to human operators, ensuring core business continuity.

Frequently asked questions

Is this a real client project?

No. The three guides use the same internal knowledge Q&A example; the tables and steps are engineering recommendations. Where there is no actual measured data, it remains marked as to-be-measured.

Can acceptance thresholds be copied directly?

No. Samples, baselines, and targets should be agreed based on the project's workflow, data, and operating conditions.

What if launch criteria are not yet defined?

Record the missing evidence and owners, keep the manual process, complete the criteria first, then expand the pilot.
