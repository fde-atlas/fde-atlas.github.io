Mermaid Flowchart Tutorial: How to Draw Diagrams for FDE Handover Documentation

Original title: Mermaid 流程图教程：FDE 交接文档怎么画图

FDE Times · 2026-11-03 · 4 min read

Summary

This tutorial teaches FDEs how to use Mermaid, a tool that renders diagrams from text, to keep handoff documentation accurate. Screenshots of architecture diagrams go stale and their source files get lost, while Mermaid diagrams live as text in the repository and render directly in GitHub issues, pull requests, wikis, and Markdown, so diagrams update in the same PR as code changes. Using a logistics data-pipeline example, the author covers flowchart basics, edge labels, and common syntax mistakes, and warns that the architecture diagram type is still beta and platform Mermaid versions differ, so flowcharts are the safer choice for handoffs.

Key points

  • Mermaid, created by Knut Sveidqvist in 2014, turns text into diagrams and is MIT-licensed open source.
  • Diagrams and code update together in one pull request, keeping handoff READMEs in sync with reality.
  • Edge labels should capture frequency and format so client teams need not ask follow-up questions.
  • Common mistakes: missing pipe in edge labels and nodes showing only internal abbreviations.
  • Architecture diagrams are beta and versions vary by platform; prefer flowcharts in handoff docs.

Key takeaways

  • Mermaid converts text into diagrams. GitHub renders it directly in issues, pull requests, wikis, and Markdown files, and GitLab supports it too.
  • For an FDE, the biggest benefit is that diagrams and code are updated in the same pull request, making it harder for handover READMEs to drift from the real system.
  • Start with flowcharts. Architecture diagrams are still in beta, and Mermaid versions may differ across platforms.

Two weeks before handover, you open the design document only to find the architecture diagram is still a screenshot from the first workshop. It shows a queue that was deprecated long ago and an API the client has since renamed. The source file lives on the laptop of a colleague who left the project, and nobody can edit it.

The authors of Mermaid wrote this problem directly into the official repository: drawing diagrams and writing documentation consumes developers' precious time, and it quickly becomes outdated.

Mermaid was created in 2014 by Swedish software architect Knut Sveidqvist to make writing documentation easier. Its core remains open source under the MIT license to this day.

For a Forward Deployed Engineer (FDE), this is daily work. You enter the client's system, connect the data, build an AI agent or data pipeline, and then leave. The remaining operations are handled by the client's engineering team, and all they can rely on is what's written in the handover documentation.

Why are text-based diagrams more durable?

Mermaid reads Markdown-like text descriptions and generates diagrams from them: change the text, and the diagram changes with it. No need to maintain separate images or design files; the diagram is just a few lines of text in the same repository as the code.

GitHub can render Mermaid diagrams in issues, Discussions, pull requests, wikis, and Markdown files, which is exactly where design documents and handover READMEs live. When a colleague modifies a processing step, they update the corresponding description lines in the same pull request, and reviewers can see both changes in a single diff.

A flowchart has two basic elements: nodes are shapes, and edges are arrows or lines. The first line sets the direction of the diagram.

LR

means left to right, which suits data flows: readers can follow from the data source on the left all the way to the output on the right.

The most valuable detail is the label on the arrow, such as "nightly export" above. The person taking over needs to know not only where the data flows, but when it flows. Putting the frequency, format, or job name on the edge means the client's operations team won't have to hunt you down with questions after you've left the project.

Common mistake: a missing vertical bar

Suppose you hastily edit the first line before handover and drop the vertical bar to the right of the label:

ERP[客户 ERP] -->|每晚导出 S3[(对象存储)]

Edge labels must be placed between two vertical bars. The fix is to add that one character back:

ERP[客户 ERP] -->|每晚导出| S3[(对象存储)]

Don't let the person taking over be the first to find the problem. Paste the description into the Mermaid Live Editor to check it; GitLab also recommends this tool for learning Mermaid and debugging diagrams. If the diagram won't render, compare it line by line with the last working version; the error is usually in the line you just changed.

The second mistake is harder to spot because the diagram still renders fine: nodes have only

ING

abbreviations like this, with no text inside the square brackets. Node IDs exist to make writing fast; the text inside the brackets is what the client team reads. A diagram full of internal abbreviations is just as hard to understand as an outdated screenshot.

Limitations: versions and beta features

Mermaid has a dedicated architecture diagram type, available since v11.1.0, for showing relationships between services and resources in cloud or CI/CD deployments. It sounds perfect for handover documentation, but the official documentation explicitly states that this diagram type is still in beta and the syntax may change.

The second risk lies in which platform renders it. GitHub recommends putting the

info

command in the mermaid code block to check the Mermaid version it runs and confirm your syntax is supported. GitLab can also render Mermaid in Markdown and declares support for Mermaid version 12.

If the client's platform differs from the one you wrote the diagram on, a diagram relying on new features may not render the way it did on your machine. So handover documentation should use flowcharts. Only use architecture diagrams after confirming they render correctly in the client's own repository.

What to learn first, and how to put it on your resume

Start with flowcharts: nodes, edges, edge labels, and

LR

direction. That's enough to draw most of the data flows you'll encounter at clients. Build the habit of running every change through the Live Editor before committing, just like running tests before pushing code.

From a career perspective, handover documentation is something recruiters rarely see but every FDE has to write. If the README of your portfolio repository contains a data flow diagram that has been continuously updated across many commits, it shows you thought about the people who would run the system after you left. In interviews, open that diagram and walk through every edge.

The next time you find the "architecture" section of a design document contains only a screenshot, don't redraw it with a drag-and-drop tool. Write six lines of text and commit them alongside the code.
