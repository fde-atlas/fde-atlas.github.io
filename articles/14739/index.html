The roadmap to becoming an FDE

FDE Times · 46 min read

Summary

This article lays out an eight-stage learning roadmap for becoming a Forward Deployed Engineer, built around 40 core reads totaling roughly five hours. Each stage defines concrete outcomes and hands-on exercises: comparing FDE and Solutions Engineer job ads, writing a five-part handoff brief with an out-of-scope line, triaging morning requests by who is blocked, and pulling a public dataset with retries, then deduplicating it in local PostgreSQL using ROW_NUMBER. Stages come with extensive supplementary reading lists spanning guides, tools, books, and industry analysis. Readers can follow the stages in order or start where they are weakest.

Key points

  • Eight-stage roadmap with 40 core reads, about 5 hours total.
  • First stage: distinguish FDE duties from Solutions Engineer roles.
  • Exercises include handoff briefs and P0/P1/P2 request triage.
  • Engineering stage: pull public API data and deduplicate in PostgreSQL.
  • Each stage has large supplementary reading lists; start where weakest.

Foundations

Understand the role and how an FDE creates value.

Outcome

After this stage you can explain what an FDE owns that a software engineer or a solutions engineer does not, switch on purpose between understanding a customer's problem and building for it, scope an engagement in a short brief with an out-of-scope line, and triage a customer's morning requests by who is blocked.

Build it

Read the role, then brief a real project

  • Open one Solutions Engineer ad and one FDE ad and answer five questions for each: does the role report to engineering or sales, do you join before or after the signature, does your code reach production or stop at a POC, who is on call after go-live, and is pay tied to sales?
  • Pick a project or ticket you are working on and write the five-part handoff brief: user, bottleneck, current workaround, the decision they want to make earlier, and the minimum prototype with its constraints.
  • Turn it into a seven-line engagement brief with mandatory "Out of scope" and "After handover" lines.
  • On three mornings, write a P0/P1/P2 triage note for everything that arrived since the previous evening, ranked by whether anyone is blocked, who, and whose decision unblocks them.

Broad engineering

Handle everything from data and APIs to infrastructure yourself.

Outcome

After this stage you can explore a customer's PostgreSQL or MongoDB data without loading production, deduplicate records with a ROW_NUMBER query that gives the same answer on every run, check what a customer's API really returns with curl and Postman, pull large datasets through paginated APIs in Python with retries and checkpoints, and make API writes and webhook handlers safe to run twice.

Build it

Pull, deduplicate and reconcile a public dataset

  • Pick a public API that uses token authentication, call one endpoint with curl with and without the token, then build a create/read/update/delete collection in Postman and run it with Collection Runner.
  • Write a Python pull_all() with an explicit limit, retries on 429 and a cursor saved only after each batch is on disk; kill it midway, rerun it, and check that the unique ID count matches the rows written.
  • Load the rows into a local PostgreSQL, open an analysis session with the four SET lines (read-only plus statement, lock and idle-in-transaction timeouts) and confirm that a write is rejected.
  • Deduplicate with ROW_NUMBER() OVER (PARTITION BY a normalised key ORDER BY updated_at DESC NULLS LAST, id DESC), then confirm that distinct keys in the source equal the rows left after filtering rn = 1.

Applied AI

Use LLMs and agents to solve real problems.

Outcome

After this stage you can trace a made-up LLM answer to what was in the context window and how sampling was set, decide from a token count whether a corpus needs RAG and measure retrieval with Recall@k, hand-write an agent loop with a stop condition and tool errors returned to the model, choose between a workflow and an agent, and turn a vague customer complaint into pass/fail evals with thresholds the customer agrees to.

Build it

A document assistant you can measure

  • Take a public document set, count its tokens against your model's context window; if it does not fit, chunk it, generate five questions per chunk and measure Recall@5, @10 and @20 with BM25 as the baseline.
  • Hand-write an agent loop with one lookup tool, MAX_TURNS = 8 and tool errors returned via is_error, and print the messages after each turn.
  • Run it on 20 different inputs, record the sequence of tools called each time, and move the paths that repeat into a fixed workflow branch.
  • Write 10 questions the documents cannot answer and a pass/fail criterion for your largest failure category, then count how often the system says the answer is not in the documents.

Build it

From a one-line request to a reviewed design doc

  • Pick a process at your company or a business you know and write a one-page discovery plan, including the sceptic on the stakeholder map and leaving the success line blank.

Build it

A rerunnable pipeline and its go-live runbook

  • Pick two public datasets that name the same entity differently, normalise both to a shared key, export unmatched rows to an exceptions file and print the match rate on every run.

Build it
