Legacy ERP Integration: Anti-Corruption Layer and CDC Read/Write Separation in Practice

Original title: 遗留 ERP 集成：防腐层与 CDC 读写分离实践

FDE Times · 2026-10-08 · 6 min read

Summary

This guide addresses a common FDE scenario: integrating with a customer's decade-old ERP with outdated APIs. Its central claim is that direct database access is the cheapest integration to build but the most expensive to remove, so it should be a last resort. The author recommends splitting read and write paths: use change data capture (CDC) on transaction logs for reads, and monitored asynchronous channels like SAP IDoc for writes, reserving UI bots for cases with no alternative. All legacy column names and odd data formats should be isolated in an anti-corruption layer, with unknown values raising errors rather than getting silent defaults. A five-step field process and common pitfalls round out the piece, including a warning that the Strangler Fig pattern often fails on closed ERPs.

Key points

  • Direct DB access is cheapest to build, most expensive to remove.
  • Prefer CDC on transaction logs for the read path.
  • Use monitored async channels like IDoc for writes.
  • Isolate legacy formats in an anti-corruption layer; fail loudly on unknown values.
  • Strangler Fig often fails when ERP requests can't be intercepted.

Isolate the legacy model with an anti-corruption layer and keep reads and writes separate, so your product won't crash along with the next ERP upgrade.

Key Takeaways

  • Direct database connections are the cheapest to set up and the most expensive to tear down. Treat it as a last resort, not the default option.
  • An anti-corruption layer keeps the legacy data model out of your new code, at the cost of extra latency and one more service to operate.
  • Use change data capture for reads and an asynchronous channel with error-handling tooling for writes. Only use UI robots when there is no other way.

Imagine your second week at a customer's factory. The agent needs to read purchase orders and create goods receipts, but the customer's ERP has been in use for over a decade. Nobody maintains the API documentation, but the database administrator is happy to give you an account that can read tables directly.

Almost every Forward Deployed Engineer (FDE) will encounter this situation, and decisions made in the first few days will persist throughout the project. The difficulty isn't connecting—it's connecting in a way that ensures your product won't crash along with the ERP upgrade eighteen months later.

The easiest door to enter is often the hardest to exit

Microsoft's architecture documentation describes this problem precisely: legacy system schemas are often intricate and their APIs outdated. If you integrate directly without addressing this, the new application is forced to inherit the legacy system's semantics.

The most obvious symptom is

if STAT_CD == "02"

code like this scattered throughout your new codebase. At that point, your product is tightly bound to the ERP.

So that read-only database account deserves more caution than it appears. A Netguru analysis on legacy system integration puts it bluntly: direct database connection is the integration pattern with the lowest setup cost and the highest teardown cost. It's fast during the demo.

But after that, every column change requires another fix, and nobody will notify you in advance.

The solution isn't to reject all shortcuts, but to inventory all access points first, then choose separately for reads and writes.

Reads and writes should go through different doors

The read path and the write path carry different risks and should be separated. For reads, if the legacy application is built around the database and cannot be modified, Microsoft recommends using database triggers, or change data capture (CDC) that reads transaction logs, to push changes to the new service.

Of the two, change data capture is preferable: it reads the transaction log, so you don't need to query the ERP's business tables or attach anything to them.

The write path is more sensitive, because a single wrong write means incorrect accounting. Taking SAP as an example, an analysis on aixsap argues that IDoc has built-in error reprocessing and monitoring, making it suitable for high-volume asynchronous writes, while OData is synchronous.

The same source notes that RFC is still in use, but its scope is narrowing, and callers need to install a dedicated connector.

This lesson isn't limited to SAP: prefer channels the customer's operations team already knows how to monitor. When a goods receipt gets stuck at 2 a.m., they need a familiar interface to reprocess it. The scripts you left behind won't help them.

The transformation layer: the only place that knows the old column names

Whichever door you take, data must cross a boundary. Microsoft calls it an anti-corruption layer (ACL): a transformation layer that keeps one system intact without compromising the other system's design and technology choices. Netguru's definition is shorter: the ACL keeps the legacy system's data model out of the new code.

Here's an example with a purchase order. The column names are fictional, but anyone who has worked with ERP will recognize the data types: numeric status codes, vendor codes with leading zeros, amounts stored in the smallest unit, dates stored as strings.

# acl/purchase_order.py — 唯一允许知道 ERP 列名的文件
from dataclasses import dataclass
from datetime import date, datetime
from decimal import Decimal

class UnknownLegacyValue(Exception):
    pass

@dataclass(frozen=True)
class PurchaseOrder:            # 新应用的模型
    order_id: str
    supplier_id: str
    amount: Decimal
    due_date: date
    status: str                 # "open" | "approved" | "cancelled"

STATUS_MAP = {"01": "open", "02": "approved", "09": "cancelled"}

def from_legacy(row: dict) -> PurchaseOrder:
    code = row["STAT_CD"]
    if code not in STATUS_MAP:
        # 就在这里停下，不要猜
        raise UnknownLegacyValue(f"STAT_CD={code!r} PO={row['PO_NO']}")
    return PurchaseOrder(
        order_id=row["PO_NO"].strip(),
        supplier_id=row["VEND_CD"].lstrip("0"),
        amount=Decimal(row["AMT"]) / 100,
        due_date=datetime.strptime(row["DUE_DT"], "%Y%m%d").date(),
        status=STATUS_MAP[code],
    )

The code isn't long, but three things are critical. The agent and all downstream services only see

PurchaseOrder

and never see

STAT_CD

. Unknown status codes throw an explicit error instead of silently applying a default. When the ERP is replaced, you only need to rewrite this one file.

The ACL isn't free. Microsoft explicitly notes that it adds latency and one more service to manage and maintain. When the legacy system is slow, the ACL can run asynchronously in an event-driven manner: data is transformed via messages, and the new business logic is no longer constrained by the legacy system's pace.

This suits high-volume data flows, or scenarios where the two systems must be fully decoupled.

Five steps in the field

The first step is the inventory. List all access points like the table above, noting who owns each one and how errors are reported. Don't just ask the customer "Is there an API?"—ask "When a sync breaks, who gets notified, and where do they look?"

The second step is to separate the read path and the write path, choosing a door for each. For reads, prefer change data capture; for writes, prefer an asynchronous channel with monitoring tooling. The third step is to write the ACL before the features, and write a test for every odd value found in real data.

The fourth step is to consider incremental replacement. Martin Fowler mentions that he and his colleagues chose progressive modernization over a one-time rewrite. The Strangler Fig pattern uses a facade—a proxy—that intercepts requests destined for the legacy system and routes them to either the old application or the new service.

But Microsoft also points out that this pattern doesn't apply if requests to the backend cannot be intercepted, which is often the case with closed ERPs. In that case, the sensible approach is to fall back to change data capture for reads and accept slower progress on writes.

The final step is documenting the decisions: which door was chosen, why, and what costs were accepted. This document is what whoever takes over needs most.

Common Pitfalls

The first pitfall is letting a demo shortcut become the real architecture. The direct table-query code written in the first week may still be there at launch, simply because nobody had time to go back and change it.

The second pitfall is treating UI robots as "integration." Workato warns that these robots break easily when an application's interface changes. Activepieces highlights an even more important distinction: APIs return status codes that tell you exactly why a process failed, while robots can only guess where the button is.

If you must use a robot, put it behind the ACL, so replacing it requires no changes to anything else.

The third pitfall is optimistic transformation. Assigning a default value to a status code nobody understands is the fastest way to make the agent "fail confidently" on the customer's real data.

When reading FDE job descriptions, phrases like "integrate with customer ERP" or "legacy systems" refer precisely to this work. Don't just write "SAP integration" on your resume—spell out which access point you chose, why, and how you handled sync failures.

This week's exercise goes beyond the read path: write the inverse function for an entity you've transformed

to_legacy

and then a round-trip test. Take a real record, transform it into the new model, transform it back, and compare it field by field with the original.

Any inconsistency—leading zeros in vendor codes, currency units, or date formats—is exactly where the write path will scramble the customer's accounting before you notice.
