Generalize and hand off | FDE Academy

Make the next deployment cheaper to deliver and maintain.

How it works

A first deployment proves the workflow can work for one customer. It does not prove the team can afford to do it again. Most first deployments are full of choices made under deadline: a field mapping hardcoded for one CRM, a prompt that names one customer's product lines, a scheduled job that only the FDE knows how to restart. This step turns that work into something a second customer, and a second engineer, can use without you in the room.

The mechanism is a clean split into three layers. Configuration holds values that differ per customer: field names, thresholds, policy text, credentials. Reusable components hold the parts that should not change: the connector, the evaluation harness, retry and logging logic. Product gaps are the things you built around because the core product lacked them. A simple test tells you whether the split is right. If onboarding a new customer requires a code change, a line is in the wrong place. Ramp's FDE write-up favors general features over one-off customizations because those customizations make the codebase harder to maintain, and it admits that knowing when to generalize takes judgment, since it pulls against shipping a small scope quickly. OpenAI's account of FDE work frames the same goal: start from a business outcome, then make the solution repeatable.

There are two common ways to get this wrong. The first is generalizing too early: you build a platform from a single example and guess the wrong axes of variation. The second is never generalizing: every deployment becomes a fork, the handoff is a chat thread, and the original FDE stays on call forever. A practical rule is to parameterize only along axes you have seen vary at least twice.

Product feedback follows the same discipline. A note that says one customer wants a feature is easy to ignore. A memo that shows the same workaround at two customers, the hours each one cost, what breaks without it, and what building it would trade off is hard to ignore. Nick Wong's Cognition profile shows the upside: an internal security problem nobody owned became the starting point for a security product.

The handoff is finished when another engineer can operate the workflow using only what you wrote, and when someone is named as its owner. Then measure the second deployment in engineer-hours and compare it with the first. That number, more than any architecture diagram, shows whether you generalized the right parts.

Worked example

Hypothetical: you built an agent that drafts renewal-risk summaries for a SaaS customer's account managers. The first deployment took 120 engineer-hours: 45 on the CRM connector and evaluation harness, 30 on customer-specific field mapping and prompt policy, 25 on debugging, and 20 on custom alert routing.

Before the second customer, you move the field mapping and policy text into a configuration file and keep the connector and harness as shared code. You estimate the second deployment at 30 hours: 12 for configuration, 10 for a new labeled evaluation set, 8 for alert routing. A colleague who has never seen the project runs it from your handoff document. They get stuck twice, once on an undocumented secret rotation step and once on an unexplained risk threshold. You fix both gaps in the document. The measured second deployment comes in at 34 hours, against 120 for the first.

Alert routing was custom work at both customers, 20 hours and then 8. That repeated cost goes into the product feedback memo as evidence for a shared notification feature, with the tradeoff stated plainly.

Do

  • Separate customer-specific configuration from reusable components.
  • Write a product feedback memo with repeated evidence and tradeoffs.
  • Have another engineer operate the workflow using only the handoff.

You are done when: A maintainable package, an accountable owner, and a measured second-deployment cost.
