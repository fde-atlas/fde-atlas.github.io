After AI coding, how do engineers move toward FDE?

AI coding tools are pushing the mechanical work in software development dramatically forward. They no longer just autocomplete the next line of code; they can read codebases, generate files, modify multiple modules, add tests, organize documentation, and, under certain conditions, invoke compilers, test runners, and scanners.

The change this brings is not that engineers no longer need technical skills, but that the bottleneck of engineering delivery has shifted. As code implementation gets faster, problem definition, system context, task orchestration, and result evaluation become more important. FDE, Forward Deployed Engineer, happens to provide a concrete role for observing this shift.

FDE is not an engineer who writes prompts

The core of FDE is not using a particular model, but turning real business problems into systems that can be deployed, verified, and run continuously.

When an enterprise says "build an AI customer service agent," that does not mean the engineering task is already clear. The engineer still has to confirm: what kinds of problems the service faces, where the data comes from, which roles can access it, which actions can be automated, which results must be confirmed by humans, how to roll back on errors, and what metrics will be used to judge effectiveness after launch.

This work determines whether the system is worth building, and it also determines whether the subsequent code has clear boundaries. FDEs need to translate back and forth between business goals and technical implementation, not pass requirements verbatim to the model.

From implementing a module to delivering a verifiable result

In traditional development, engineers often use functions, modules, and PRs as stage deliverables. With agents involved, the cost of a single implementation drops, and deliverables gradually become a complete task chain: goal definition, code changes, testing, review, deployment, and runtime feedback.

This chain requires at least four layers of engineering design.

The first layer is context. The agent must be able to find relevant code, configuration, dependencies, interfaces, and historical decisions. Simply pasting requirements into a chat box is usually not enough to support complex changes.

The second layer is tools. Compilers, test runners, static scanners, logs, and metrics must be callable and readable back, so the agent can correct based on results rather than judging success by linguistic fluency.

The third layer is boundaries. Inputs and outputs, permissions, modifiable scope, and prohibited actions must be explicit, with important constraints solidified as much as possible through scripts, types, or structured tests.

The fourth layer is feedback. Failure reasons cannot remain in a single conversation; they must be written back into documentation, tests, tool interfaces, or task templates, becoming context for the next execution.

Four capabilities engineers need to build

1. Problem definition

Break "build a feature" down further into users, business outcomes, inputs and outputs, exception fallbacks, and acceptance criteria. Without a completed definition, the agent can only keep generating plausible-looking implementations.

2. Environment design

Make the codebase, project documentation, tool interfaces, and quality rules readable to the agent. A short, clear project map is usually more effective than a long, unstructured manual.

3. Agent orchestration

Don't mistake multiple chat windows for multi-agent collaboration. Real orchestration requires setting clear inputs and outputs for research, implementation, testing, and review tasks, and making state trackable.

4. Evaluation and responsibility

Agents can do the first round of implementation and review, but engineers still need to understand the impact of changes and judge architectural trade-offs, performance, security, maintainability, and business outcomes. Being able to run is not the same as being deliverable, and passing tests is not the same as the system having solved the problem.

A minimal agent-first delivery process

You can start with a narrow scenario:

  • First write a task description, including goals, scope, dependencies, and definition of done.
  • Have the agent read the codebase and list affected modules, risks, and questions to confirm.
  • Have the agent write tests or acceptance examples first, then complete the first round of implementation.
  • Make test, scan, and build results readable feedback.
  • Have the engineer review key design decisions, permission boundaries, and failure handling, and decide whether to merge.
  • Distill this round's errors and fixes into project knowledge or automated rules.

The point of this process is not to have the agent write more code, but to give every delegation clear boundaries and make every result verifiable.

Don't reduce FDE to "just making judgments"

FDE is also not about engineers immediately transforming into product managers or project coordinators. When facing new problems and complex systems, engineers must still understand the code, otherwise they cannot judge whether the agent's solution is correct.

OpenAI's engineering practice divides responsibility into Delegate, Review, and Own: mechanical work can be delegated, initial results can be reviewed, but architecture, product intent, and final quality still need someone to own them. Anthropic's Agentic Coding report also emphasizes that scaled adoption must address supervision, quality, and security simultaneously.

The real change is that engineers no longer have to spend all their time on repetitive implementation and can devote more attention to system boundaries, long-term maintenance, and business outcomes. AI coding will amplify organizational capability—teams with chaotic processes and weak testing may also end up producing more problems faster because of it.

How can ordinary engineers get started?

I have worked in backend, frontend, and big data in the past, and later took on technical management, project advancement, and customer training, experiencing the complete loop from requirements to development, deployment, and maintenance. Now, working on agents, AI coding, and one-person business practice, I increasingly confirm that what truly transfers is not a specific tool, but cross-layer understanding.

You can start by picking a real small task, writing clearly what result it should change, and then having the agent complete the first round of implementation. Don't just keep the code—keep the task description, test examples, error records, and acceptance criteria together. The next time you encounter a similar problem, these things become productivity.

FDE is not a new identity engineers take on after leaving technology; it is a direction engineers pursue after extending their technical capabilities to business, systems, and delivery outcomes.
