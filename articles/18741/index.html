SQL Deduplication: Using ROW_NUMBER to Get the Latest Record per Group

Original title: SQL 去重：ROW_NUMBER 取每组最新一条记录

FDE Times · 2026-10-28 · 6 min read

Summary

This guide explains how to deduplicate messy CRM data deterministically using the ROW_NUMBER window function, keeping the latest complete record per customer. It argues that GROUP BY with MAX loses the full row, while ROW_NUMBER preserves rows and never ties. Key pitfalls covered: PostgreSQL and DuckDB sort NULLs differently by default, so the same query can pick different records on each engine; tied timestamps make results non-deterministic unless a unique tiebreaker like id DESC is added; PostgreSQL forbids window functions in WHERE, requiring a CTE, while Snowflake and DuckDB support QUALIFY. The author also recommends defining and normalizing the customer key before partitioning and verifying results by comparing distinct key counts before and after deduplication.

Key points

  • ROW_NUMBER keeps full rows while ranking within each partition.
  • Always add a unique tiebreaker column to ORDER BY for determinism.
  • NULL ordering differs between PostgreSQL and DuckDB; use NULLS LAST explicitly.
  • PostgreSQL needs a CTE for filtering; Snowflake and DuckDB support QUALIFY.
  • Define and normalize the dedup key, then verify by counting distinct keys.

On your second day on-site, you receive a CRM export and a question that sounds simple: how many active customers do we have right now?

You count a number, but the head of sales shakes their head and says it's too high. The reason is nothing new: the same person appears several times—two imports, one phone number correction, and one legacy system migration, each leaving a record behind.

For a Forward Deployed Engineer (FDE), this is not a small chore. Everything built afterward—dashboards, data pipelines, agents that query customer info—rests on this table. Get the deduplication wrong, and every downstream number is wrong too, and people usually discover it during a demo, not while you're writing the query.

This skill boils down to one SQL pattern: number the records within each customer group and keep only row 1. Below, a concrete example demonstrates the pattern and explains which pitfalls can make it return different results between two runs or two engines.

Why isn't GROUP BY enough?

Many engineers' first instinct is

GROUP BY email

plus

MAX(updated_at)

. That gets you the most recent update time, but not the phone number, address, or status on the same row.

To retrieve those columns, you have to join back to the source table. If two rows have the same timestamp, both match, and the customer is duplicated again.

Window functions solve exactly this problem. The PostgreSQL documentation notes that window functions do not collapse multiple rows into a single output row the way ordinary aggregates do. Each row stays independent in the result, so you can compute a ranking within the group while still holding the complete record to pick from.

    c.*,

      PARTITION BY lower(trim(email))
      ORDER BY updated_at DESC NULLS LAST, id DESC
    ) AS rn
  FROM customers_raw c
)
SELECT *
FROM ranked
WHERE rn = 1;

The trap that makes you keep the wrong row

The hardest trap to spot is on line 104. According to the PostgreSQL documentation, NULL is treated as larger than any other value when sorting, so under

DESC

it comes first. The oldest record, the one without a timestamp, silently gets

rn = 1

。

DuckDB is the opposite: its documentation states that, unlike PostgreSQL, NULLs stay at the end even in

DESC

sorting, so the same query selects line 103. As a result, a DuckDB notebook on your laptop and the client's PostgreSQL data pipeline on site may give two different answers, as shown by the two columns

rn

in the table.

The defense is not to rely on default behavior. On engines that support the syntax, explicitly write

ORDER BY updated_at DESC NULLS LAST, id DESC

. If the same query also needs to run on engines that don't support

NULLS LAST

, bake the NULL ordering into the data itself:

ORDER BY CASE WHEN updated_at IS NULL THEN 1 ELSE 0 END, updated_at DESC, id DESC

。

This

CASE

expression assigns 0 to rows with a timestamp and 1 to rows with null values, then sorts ascending, so null rows always come last regardless of engine defaults. Using the table above, both engines select 103.

On your resume and in interviews, instead of writing "proficient in SQL," describe specifically how you built a deterministic deduplication step for a multi-source customer table, including the tiebreaker column, NULL handling, and the key-count check before and after deduplication.

The next time someone asks "how many customers do we have," the number you give should be the one that comes out identical tomorrow, whether rerun on your laptop or the client's server.
