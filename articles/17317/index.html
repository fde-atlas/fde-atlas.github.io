Case Review: How Anthropic's Multi-Agent Research System Collaborates

Original title: 案例复盘：Anthropic 的多智能体研究系统是怎么协作的

FDE中国 · 2026-09-04 · 6 min read

Summary

This piece reviews Anthropic's multi-agent research system, where an orchestrator agent decomposes queries and delegates to parallel subagents with independent context windows that condense findings. The author highlights reusable practices for FDE delivery: a four-part delegation interface (goal, output format, tool guidance, boundaries), effort tiers tied to complexity, small-sample evals with LLM judges plus human checks, and production measures like checkpoints and rainbow deployments. It is candid about costs—roughly 15x the tokens of normal chat—and argues the architecture suits high-value, parallelizable, read-only research tasks, not write-path or tightly sequential work.

Key points

  • Orchestrator-worker pattern: subagents explore in parallel with separate contexts.
  • Delegation requires goal, output format, tool guidance, and clear boundaries.
  • Effort scales with complexity: 1 agent for facts, 10+ for complex research.
  • Multi-agent beat single-agent by 90.2% but consumes ~15x tokens.
  • Best for read-only, high-value intelligence tasks; errors cascade otherwise.

I. Background

The subject of this case is Anthropic's Research feature: Claude can search the web, Google Workspace, and various integrations to complete complex tasks, powered by a multi-agent system—multiple LLMs working together, autonomously using tools in a loop. In the engineering blog post "How we built our multi-agent research system", Anthropic publicly breaks down how this system went from prototype to production, along with lessons learned in system architecture, tool design, and prompt engineering. This piece reviews the system's collaboration approach based on that article and discusses its reference value for research-type AI tasks in FDE delivery.

II. The Problem

The difficulty of research tasks lies in their open-endedness: the steps cannot be predicted in advance, and a fixed path cannot be hard-coded for exploring complex topics—researchers adjust their approach as new findings emerge and follow leads that surface along the way; the model must run autonomously for many rounds and decide its next direction based on intermediate results, which linear, one-shot pipelines cannot handle. Meanwhile, search is inherently compression: distilling insights from massive corpora that a single model's context window cannot hold, while serial, one-at-a-time searching is slow and shallow. On breadth-first queries that require tracking multiple independent directions simultaneously, a single agent quickly hits its limits.

III. The Solution

Anthropic adopted an orchestrator-worker pattern: a lead agent analyzes the user's query and formulates a research strategy, then delegates tasks to specialized subagents running in parallel. Each subagent has its own context window and acts as an "intelligent filter": exploring different facets of the question in parallel, condensing the most important content, and handing it back to the lead agent to synthesize into a final answer. Unlike RAG's static retrieval (fetching a set of text chunks most similar to the query and then generating an answer), this architecture is multi-step search—dynamically finding information, adapting to new findings, and analyzing results. The division of labor also brings separation of concerns: each subagent uses different tools, prompts, and exploration trajectories, reducing path dependency.

IV. Implementation

Getting the architecture running, the engineering effort concentrated on four things.

Task decomposition and delegation. The lead agent breaks the query into subtasks, and each subagent must receive four things: an objective, an output format, guidance on tools and sources to use, and clear task boundaries. Early versions allowed brief instructions like "research the semiconductor shortage", with the result that subagents duplicated the same searches—one was looking into the 2021 auto chip crisis while two others were still re-investigating the 2025 supply chain.

Effort scaling and parallelism. Agents judge poorly on their own how much effort to invest, so the team wrote scaling rules into the prompt: simple fact-checking uses 1 agent with 3-10 tool calls; direct comparisons use 2-4 subagents with 10-15 calls each; complex research deploys more than 10 subagents with clearly defined responsibilities. Parallelization kept pace: the lead agent launches 3-5 subagents in parallel, and subagents use 3 or more tools in parallel, cutting research time for complex queries by up to 90%.

Evals first. Start with a small-sample eval of about 20 queries reflecting real usage patterns; then use an LLM judge to score against a rubric covering factual accuracy, citation accuracy, completeness, source quality, and tool efficiency; human testing fills gaps automation misses—early agents preferred SEO-optimized content farms over academic PDFs, and source-quality heuristics were added to the prompt accordingly.

Production reliability. Agents are stateful and errors accumulate, so the team used persistent execution, checkpointing, and retry logic to let the system resume from the point of failure rather than restart from scratch; deployment used rainbow deployments, with new and old versions running in parallel and traffic migrated gradually; production tracking looks only at decision patterns and interaction structures, not conversation content, to protect user privacy.

V. Results

All figures below are as disclosed in the original article. In Anthropic's internal research evals, a multi-agent system with Claude Opus 4 as the lead agent and Claude Sonnet 4 as subagents outperformed single-agent Claude Opus 4 by 90.2%; the typical scenario was "identify the board members of all companies in the S&P 500 information technology sector"—the multi-agent system decomposed it to subagents and found the correct answer, while the single agent searched slowly and sequentially and failed to find it. In the BrowseComp eval testing browsing agents, three factors explained 95% of the performance variance, with token usage alone accounting for 80%. On the engineering side, parallelization cut research time for complex queries by up to 90%. On user feedback: some users said it helped them discover business opportunities they hadn't imagined, solve thorny technical problems, and save up to days of work.

VI. Constraints

The conditions for this architecture to work are stated bluntly in the original article: a multi-agent system's token consumption is roughly 15x that of ordinary chat (about 4x for a single agent), so for economic viability, task value must be high enough to cover the cost of the performance gains. It suits high-value tasks that are heavily parallelizable, involve information exceeding a single context window, and require interacting with many complex tools; domains where all agents must share the same context or have heavy interdependencies are not a good fit—most coding tasks have less parallelizable work than research. There are also two practical engineering constraints: synchronous execution makes the lead agent wait for each group of subagents to finish, creating an information-flow bottleneck; and agent non-determinism means debugging must rely on complete production tracking.

VII. Reusable Lessons

For Chinese FDE practitioners and enterprises, practices from this case that can be directly transferred (applicable precondition: the delivery involves research, intelligence, or due-diligence type AI tasks):

  • Delegation is interface design. When breaking tasks into subtasks for AI, spell out the objective, output format, tools, and boundaries—vague instructions cause duplicated work for both agents and humans, and this applies equally when an FDE assigns work to collaborators.
  • Set effort tiers. Predefine effort tiers by task complexity (how many subtasks, how many calls) to prevent simple queries from burning money; domestic clients are sensitive to token costs, and the tier table can go straight into the cost model of your delivery plan.
  • Evals first, start with small samples. About 20 real queries plus a dual track of LLM judge and human spot checks builds a quality baseline faster than waiting for a large, all-encompassing eval system.
  • Read-only tasks first. The multi-agent architecture is applied first to read-only, intelligence-gathering tasks, while write-path operations (modifying data, touching production configs) are deferred—the original article explicitly warns that errors accumulate and amplify in agent systems.

Differences in the Chinese context: domestic enterprise delivery often adds constraints such as data staying in-domain and permission approval, and multi-agent parallel retrieval may cross permission boundaries. "What an agent can see" should first be reviewed as a permissions issue.
