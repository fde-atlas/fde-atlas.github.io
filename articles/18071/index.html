TypeScript Implementation of Agent API Call Retries and Idempotency Keys

Original title: Agent API 调用重试与幂等键 TypeScript 实现

FDE Times · 2026-10-08 · 6 min read

Summary

This guide shows how to wrap API calls for customer-facing agents in roughly 80 lines of TypeScript. It opens with an incident where a support agent's refund tool double-refunded an order after a network timeout, arguing the fault lies in the fetch wrapper, not the model. It covers three essentials: timeouts sized to the downstream API's p99.9 latency, bounded retries with exponential backoff and jitter, and idempotency keys generated once per operation and reused across retries. Drawing on Stripe and Amazon Builders' Library guidance, it explains why keyed requests should not retry 5xx errors, how token-bucket retry budgets prevent cross-layer amplification (a 243x database load example), and common mistakes like regenerating keys inside retry loops or stacking retries across SDK layers.

Key points

  • Side-effecting APIs are only safe to retry when they support idempotency.
  • Generate the idempotency key once outside the retry loop and reuse it, on POST requests only.
  • Set timeouts based on the downstream API's p99.9 latency percentile.
  • Retries at every layer can amplify load; Amazon cites a 243x database load case.
  • Don't retry 5xx on keyed requests, since the server returns the stored same result.

Timeouts, restrained retries, and a fixed idempotency key per operation—about 80 lines of TypeScript, ready to copy into your project.

Key takeaways

  • APIs with side effects can only be retried safely if they support idempotency.
  • Generate each idempotency key once per business operation, reuse it on every retry, and attach it only to POST requests.
  • Retries need a budget: if every layer retries on its own, database load can be amplified up to 243x.

Imagine your second week at a customer site. The customer service agent the team deployed has a tool called

createRefund

that calls the customer's internal refund API. One afternoon the network is flaky, the first request gets no response, and the agent tries again. The next morning, the finance team discovers that one order was refunded twice.

The problem isn't the model—it's in the dozen or so lines of code wrapping

fetch

, code that's usually treated as grunt work. For a Forward Deployed Engineer (FDE), the API call layer is exactly where the agent touches customer money, inventory, and production data, and it has to be written correctly the first time.

This layer needs three things: timeouts, restrained retries, and idempotency keys. This guide covers each one, then combines them into a complete TypeScript function you can copy directly and adapt to your own project.

Why are blunt retries dangerous?

The Amazon Builders' Library puts it plainly: for APIs with side effects, retrying is not safe unless they support idempotency. When a refund request times out, the client can't tell whether the server already processed it. The packet may never have arrived; or the money may already have been transferred, with only the response lost on its way back.

Idempotency keys eliminate exactly this uncertainty. Stripe's documentation says that if a connection error occurs, you can resend the request with no risk of creating a second object or executing the same update twice.

The mechanism is simple. For each key, Stripe saves the status code and response body of the first request, whether it succeeded or failed, and every subsequent resend returns the same result.

The "whether it failed" part is crucial. According to Stripe, if the first attempt returned a 500, retrying with the same key returns the same 500. So retrying with an old key mainly applies when the failure happened in transit—such as a timeout or dropped connection—i.e., when the client hasn't received any result yet.

How long should the timeout be?

For agents, defaults are usually far too generous. OpenAI's Node SDK defaults to a 10-minute timeout. That's fine for long-running model calls, but an API that queries orders shouldn't keep the agent waiting that long.

Amazon offers a principled way to choose. First decide what proportion of "false timeouts"—requests that would have succeeded if given a bit more time—you can accept; then take the corresponding latency percentile of the downstream service, such as p99.9.

If the refund API's p99.9 is 1.2 seconds, setting the timeout to about 1.2 seconds means you accept truncating roughly 0.1% of requests that would have succeeded.

In Node, you don't need to implement this yourself with

setTimeout

.

AbortSignal.timeout()

It returns a signal that aborts automatically when it fires, raising an

TimeoutError

named

DOMException

. This lets the code distinguish a timeout from a user-initiated cancellation, since the two require different handling.

How many retries are enough?

OpenAI's SDK is a good reference design. According to its README, it retries twice by default with a short exponential backoff. By default it retries 408, 409, 429, all errors of 500 and above, and connection errors. It does not retry 400 or 401, because resending the same request unchanged won't change the result.

Backoff alone isn't enough—you also need jitter. Amazon describes jitter as adding some randomness to the wait time so retries are spread out over time. Without jitter, a thousand agent sessions failing at the same moment would all retry at the same instant and crush the service again.

The biggest danger is retries stacking across layers. Amazon gives an example: a five-layer system where each layer retries independently amplified database load by 243x.

Working backward, 243 is 3 to the power of 5—the result of each layer attempting at most three times. Amazon's approach is to limit retries locally with a token bucket. Once the tokens are used up, that layer stops retrying and passes the error up.

The complete TypeScript implementation

The

callApi

function below combines all three. Note the line that generates the key: it's outside the loop.

import { randomUUID } from "node:crypto";

type Method = "GET" | "POST" | "DELETE";
interface CallOptions {
  method: Method;
  url: string;
  body?: unknown;
  timeoutMs: number;          // 取自下游 API 的 p99.9
  maxRetries?: number;        // 默认为 2
  idempotencyKey?: string;    // 如果操作已有键，就传进来
  signal?: AbortSignal;       // 来自 Agent 或用户的取消信号
}

// 令牌桶：最多 10 次重试，每秒补充 1 个令牌
class RetryBudget {
  private tokens = 10;
  constructor() {
    setInterval(() => (this.tokens = Math.min(10, this.tokens + 1)), 1000).unref();
  }
  take(): boolean {
    if (this.tokens <= 0) return false;
    this.tokens--;
    return true;
  }
}
const budget = new RetryBudget();

// 带键的请求：不重试 5xx，服务器已保存结果，只会返回同样的错误
const isRetryableStatus = (s: number, hasKey: boolean) =>
  s === 408 || s === 409 || s === 429 || (!hasKey && s >= 500);

const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
const backoff = (attempt: number) =>
  Math.random() * Math.min(5000, 200 * 2 ** attempt); // 抖动

export async function callApi(opts: CallOptions): Promise<Response> {
  const maxRetries = opts.maxRetries ?? 2;
  // 整个操作只生成一次；只有 POST 携带键
  const key =
    opts.method === "POST" ? opts.idempotencyKey ?? randomUUID() : undefined;

  for (let attempt = 0; ; attempt++) {
    // 每次调用都有自己的超时，并与调用方的取消信号合并
    const timeout = AbortSignal.timeout(opts.timeoutMs);
    const signal = opts.signal ? AbortSignal.any([opts.signal, timeout]) : timeout;
    try {
      const res = await fetch(opts.url, {
        method: opts.method,
        headers: {
          "Content-Type": "application/json",
          ...(key ? { "Idempotency-Key": key } : {}), // 请求头名称取决于具体 API
        },
        body: opts.body ? JSON.stringify(opts.body) : undefined,
        signal,
      });
      const canRetry =
        isRetryableStatus(res.status, key !== undefined) &&
        attempt < maxRetries &&
        budget.take();
      if (!canRetry) return res;
      await res.body?.cancel(); // 丢弃响应体，在重试前释放连接
    } catch (err) {
      // 调用方已取消：立即停止，不重试
      if (opts.signal?.aborted || attempt >= maxRetries || !budget.take()) throw err;
      // 否则是 TimeoutError 或网络错误：用同一个键重发
    }
    await sleep(backoff(attempt));
    if (opts.signal?.aborted) throw opts.signal.reason;
  }
}

Back to the refund example. The first call times out, the catch block receives

TimeoutError

, the function waits a random interval, then resends with the same key. If the server actually already processed the first request, it returns the saved result and won't refund a second time.

When adapting this function, two small details are worth keeping. The caller's cancellation signal is merged with the timeout via

AbortSignal.any()

, so if the agent is stopped midway, the function exits immediately instead of continuing to retry. Also, when a response is discarded for retry purposes, its body is cancelled to keep the connection from getting stuck in the pool.

The retry condition here is narrower than the OpenAI SDK's in one respect: requests carrying a key don't retry errors of 500 and above. The reason is the mechanism described earlier. For an API like Stripe that saves the first result per key, resending with the same key after a 500 just gets you the same 500—burning budget for nothing.

GET and DELETE carry no key, so they still retry 5xx as usual. If the customer's API handles keys differently, ask before relaxing this condition.

When a 409 indicates a conflict with another concurrent request, it's still worth retrying. Stripe explains that when parameter validation fails or the request conflicts with one in progress, it doesn't save a result, so resending is safe in those cases.

Common mistakes in the field

The most common mistake is generating the key inside the loop. Then every retry carries a new key, the server treats it as a new operation, and idempotency is gone.

Agents introduce a subtler variant: the model calls the same tool again in a later step, and your call layer generates a new key for that call. If the orchestrator might re-run a step, derive the key from that step's ID and pass it in via

idempotencyKey

.

The second mistake is reusing the same key with different parameters. Stripe compares the new parameters against the original request and returns an error if they don't match. It may also delete keys after 24 hours, so a job re-run the next day can't rely on the old key.

The third mistake is adding a key to every request. Stripe explicitly notes that GET and DELETE are idempotent by nature, and sending them a key does nothing. Also don't put email addresses or account numbers in keys. Stripe recommends UUID V4 or a random string with enough entropy, up to 255 characters, with no sensitive data.

The last mistake is the hardest to spot: stacking retries on top of an SDK. If your tool wraps a client that already retries twice, and the agent's orchestrator retries again on top of that, the amplification multiplies before you notice it. Pick one layer to own retries and disable them everywhere else.

Putting this skill on your resume

When reading job descriptions for FDE roles, look for requirements about integrating with customer systems or production reliability. This kind of code fits perfectly into that part of your experience.

Don't just write "built an agent that calls APIs" on your resume. Spell out which percentile the timeout was based on, which layer owns retries, and how idempotency was used to prevent duplicate operations.

In interviews, "What does your agent do if the request to create an order times out?" is exactly your chance to draw the loop above. Interviewers remember candidates who understand that a timeout doesn't mean failure—it means the outcome is unknown.
