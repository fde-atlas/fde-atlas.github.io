ISO 20022 Data Quality and AI Models: A Practical Guide for FDEs

Original title: ISO 20022 数据质量与 AI 模型：FDE 实战指南

FDE Times · 2026-10-09 · 6 min read

Summary

This guide argues that a bank's claim of having adopted ISO 20022 only describes message format, not data quality. Legacy free-text addresses often persist inside new structured messages, and Swift and EPC have both postponed deadlines banning fully unstructured addresses, so data will mix structured, hybrid, and unstructured forms for some time. The author, writing for FDEs on banking projects, prescribes profiling each data source in week one: sampling by source and time period, classifying address forms with a small script, checking empty tags, and documenting data lineage before any model work. A hypothetical sample shows how a third of counterparties can silently vanish if a pipeline reads only structured fields. It also lists common new-FDE mistakes, including trusting the client's claim and overwriting raw data with LLM-parsed values.

Key points

  • ISO 20022 adoption does not fix legacy free-text address data.
  • Swift and EPC both postponed their unstructured-address deadlines.
  • Profile data by source and document lineage before building models.
  • Pipelines reading only structured fields silently drop unstructured records.
  • Avoid overwriting raw addresses with LLM-parsed values; it breaks lineage.

Key Takeaways

  • "We've already adopted ISO 20022" only describes the message format. Historical address data entered as free text is still often incomplete, abbreviated, and inconsistent.
  • Both Swift and EPC have postponed the deadlines for banning fully unstructured addresses. For the foreseeable future, data will be a mix of structured, hybrid, and unstructured forms.
  • The Forward Deployed Engineer's first job is to profile each data source and document data lineage. Only after that does the model come into play.

You've just started at a bank. Your task is to build an AI agent that helps the compliance team read cross-border payment messages, group counterparties by city and country, and flag anomalies. At the first meeting, the client's technical lead says confidently: "We've already adopted ISO 20022—all our data is structured."

That's only half true. The other half usually surfaces about three weeks after the model goes live, often in the form of a counterparty list that nobody can understand or explain.

As a Forward Deployed Engineer (FDE), your first-week task is to find that other half before it finds you: what ISO 20022 actually delivered, where the data is still dirty, and how dirty it is.

What Does ISO 20022 Promise?

The old MT messages crammed large amounts of information into a few lines of free text. ISO 20022 instead uses clearly defined fields to carry names, postal addresses, and remittance information. Machines can read each part separately, without having to guess where to split a string.

In Swift CBPR+ cross-border payments, the transition period during which MT and ISO 20022 coexisted officially ended on November 22, 2025.

In Vietnam, the ACH operated by NAPAS has already implemented ISO 20022, and BIDV has used the standard since 2023; in November 2025, the State Bank of Vietnam held a two-day conference in Hanoi to promote the standard's adoption in interbank payments.

So at Vietnamese banks, "Have you migrated to the new standard?" is no longer a question worth asking. The real question is: which internal systems are still pumping old free-text data into the new messages?

FTI Consulting argues that because ISO 20022 is a structured format, both traditional machine learning and generative AI will perform significantly better. This is a consulting firm's opinion, not an independent measurement. The argument makes sense, but only if the data actually sits in structured fields.

Why "We've Already Adopted ISO 20022" Doesn't Mean the Data Is Clean?

A new message format doesn't fix existing data. Addresses entered as free text over decades are often inconsistent, abbreviated, or incomplete. When you start profiling the data, one of the first risks to check is whether this historical data was copied verbatim into the free-text address lines of the new messages.

That's why three forms appear in the same table. The structured form splits each component out: street name, house number, town, country. In the hybrid form, part of the content sits in fields while the rest remains in free-text lines.

The fully unstructured form consists only of text lines. EPC's rules allow the hybrid form as a transition, but ban fully unstructured addresses. The problem is that the effective date of this ban keeps changing.

According to the original schedule, Swift CBPR+ would stop accepting fully unstructured addresses from November 14, 2026. Swift has postponed this date and expects to publish a new timeline before December 2026. In the SEPA region, EPC has also postponed the November 15, 2026 deadline, to be determined later.

In practice, the client's data will be a mix of all three forms for some time. Before putting any date into your plan, check Swift's SR2026 page.

A Day-One Data Profiling Exercise

Imagine the same counterparty appearing in two records. The following XML is for illustration only:

<!-- 完全非结构化 -->
<PstlAdr>
  <AdrLine>12 NGUYEN HUE Q1 HCMC VN</AdrLine>
</PstlAdr>

<!-- 结构化 -->
<PstlAdr>
  <StrtNm>Nguyen Hue</StrtNm>
  <BldgNb>12</BldgNb>
  <TwnNm>Ho Chi Minh City</TwnNm>
  <Ctry>VN</Ctry>
</PstlAdr>

The first record is fully unstructured; the second is structured. A human can tell at a glance that both are the same address. But a data pipeline that groups by the town field only sees the second record, because the first has no town field. So the first thing to do is write a small classification script:

from collections import Counter

def classify(pstl_adr):
    # 没有标签，或者是空的 <PstlAdr/> 标签：都算作缺少地址
    if pstl_adr is None or len(pstl_adr) == 0:
        return "missing"
    tags = [c.tag.split("}")[-1] for c in pstl_adr]
    has_lines = "AdrLine" in tags
    has_fields = any(t != "AdrLine" for t in tags)
    if has_fields and not has_lines:
        return "structured"
    if has_fields and has_lines:
        return "hybrid"
    return "unstructured"

def profile(records):
    # records：由 (source_system, pstl_adr_element) 组成的列表
    return Counter((src, classify(adr)) for src, adr in records)

The detail to watch for is empty tags.

classify

The comment in

<PstlAdr/>

makes this point: missing tags and empty

<PstlAdr/>

tags both count as a missing address. Without this check, an empty

with no child elements would be counted as "unstructured," and you'd wrongly tell the client that a data source stores free-text addresses when in fact it has no addresses at all.

Suppose you sample 1,000 records and find 380 structured, 270 hybrid, and 350 unstructured. If the agent only reads the town field, and only some hybrid records carry it, then it can see at most 650 records.

At least 350 counterparties—more than a third of this hypothetical sample—would silently disappear from the analysis without any error.

Totals matter less than per-source numbers. If those 350 unstructured records come almost entirely from the same legacy core system, you have a concrete question to raise with the client: should this data source's data be standardized, or excluded from scope?

Five Steps Before Touching the Model

Step one: sample by data source and time period, not randomly from the whole table, because old and new data often differ greatly. Step two: run the profiling above and organize the results into a "data source × address form" table. Business owners can understand the problem from this table without looking at XML.

Step three: ask about data governance. FTI emphasizes that metadata catalogs, field-level data lineage, and retention policies are prerequisites for using ISO 20022 data reliably and auditably. At a bank, the question "Where does this field come from, and who has transformed it?" will eventually be asked in an audit.

Step four: identify which data actually adds value to the problem you're solving. According to FTI, richer data on ultimate debtors and ultimate creditors helps banks better understand their customer base. But that assumes these fields actually have values, so test their fill rates the same way you tested addresses.

Only at step five does the model come in. For hybrid and unstructured data, explicitly decide whether to parse, flag, or drop it, and document that decision for the compliance team to review.

Three Common Mistakes New FDEs Make

The most common mistake is taking "we've already adopted the standard" at face value without even opening the data. The second is using an LLM to parse free-text addresses into fields and then overwriting the original data.

This destroys data lineage. When auditors ask, nobody can say which values came from the customer and which were inferred by a machine.

The third mistake is building a plan around a fixed deadline. As noted above, these dates are still in flux; a roadmap stating "no more unstructured addresses after November 2026" may be outdated on the day it's presented.

How to Showcase This Skill on Your Resume?

Don't write "familiar with ISO 20022" on your resume. Write a line of experience with numbers: how many records you profiled, what proportion of unstructured addresses you found in which data source, and how you decided to handle them.

If you don't have a real project yet, a small code repository using synthetic data, paired with a README explaining three address formats, is enough to kick off a good interview.

In banking projects, the value of an FDE lies not in pushing models to production, but in spotting the data that is quietly disappearing—like the 350 records in that hypothetical sample—before the model learns from what remains.
