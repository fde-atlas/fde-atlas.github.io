AGI vs AI agents: how FDEs scope the "AI employee"

FDE Times · 2026-10-08 · 7 min read

Summary

This article explains how forward deployed engineers should handle client requests for an "AI employee". It argues that the all-capable AI employee clients imagine is essentially AGI, which remains hypothetical, while what FDEs can actually ship is an agent assembled from an LLM, tools, and memory. Citing Anthropic's tool use documentation, it notes the model only proposes tool calls that the application executes, so capability depends on which systems are connected and with what permissions. A mapping table turns common client expectations into scoping questions. A refund agent example shows that models may invent plausible values when parameters are missing, and that compounding errors make full autonomy risky: ten sequential steps at 95% accuracy each yield roughly 60% overall success. The recommendation: start with fixed workflows, require human approval for critical actions, and expand autonomy based on sandbox trial data.

Key points

  • The "AI employee that does everything" matches the definition of AGI, which is still theoretical.
  • Models only propose tool calls; the application executes them, so scope depends on connected systems and permissions.
  • When required parameters are missing, models may infer plausible-sounding values, so design them to ask users.
  • At 95% per-step accuracy, a ten-step chain succeeds only about 60% of the time, so autonomy compounds errors.
  • Start with the simplest workflow, add human approval steps, and grant more autonomy based on sandbox data.

What executives picture is close to the definition of AGI, which remains theoretical; the FDE's job is to turn that hope into a design without crushing it.

In brief

  • The "AI employee that does everything" a client describes is AGI. By the common definition, AGI is still theoretical, not a product anyone can buy.
  • What an agent can do is decided by the tools the engineering team connects and how they are described. The model only proposes calls; the application executes them.
  • Start with the simplest solution, usually a fixed workflow, and add autonomy later, because autonomy brings higher costs and compounding errors.

In 1965 Herbert Simon predicted that within twenty years machines would be capable of doing any work a man can do. More than sixty years later the promise survives under a new name: the “AI employee”.

Every FDE meets this moment sooner or later. An executive on the client side watches a few demos, reads a few headlines, then asks when they will get an AI employee that handles everything on its own. It is a fair question.

The trouble is that it fuses two very different things, and unless they are separated in the first meeting, the project will be judged against a standard no system today can meet.

What the client is picturing is AGI. What the FDE can deliver is an agent. The gap between them will not close by waiting for smarter models. It closes with a design, and the FDE draws that design up with the client.

“Does everything” already has a name, and it is still hypothetical

Wikipedia defines AGI as a hypothetical form of artificial intelligence that matches or surpasses humans at almost every cognitive task. The key word is “hypothetical”. An AI employee that handles everything fits that definition almost word for word, which means it is not yet something anyone can buy or deploy.

What runs in businesses today is narrow AI, or weak AI: it solves a specific problem but has no general cognitive ability. That is the distance between the system an FDE will deploy and the image in the executive’s head.

Debating when AGI will arrive is a trap. Simon’s forecast was wrong. Geoffrey Hinton once put AGI “30 to 50 years or even longer away”, then sharply revised that figure himself. When the field’s leading figures disagree that widely, arguing over timelines only derails the meeting.

The line to use instead: that does not exist yet, and here is what we can build this quarter.

What ships is an agent, assembled from parts

DAIR.AI’s Prompt Engineering Guide defines an agent as a system that uses an LLM and is designed to act autonomously and solve complex tasks. Agents exist for a practical reason: an LLM on its own falls short when a task needs several steps, planning and reasoning.

So it is given planning and self-review, access to tools, and memory.

An “AI employee”, in other words, is an assembly that engineers put together, with no general mind behind it, and every part of that assembly has its own limits.

Anthropic’s tool use documentation shows how concrete those limits are. Claude executes nothing by itself. It returns a structured call, and then either the developer’s application runs it (a client tool) or Anthropic does (a server tool).

The model also calls a tool only when the request matches the capability described in the tool and the answer is not already in context.

That sentence anchors the whole conversation. It moves the question from “is the AI smart enough?” to “which systems do we connect it to, with what permissions?”, and client leaders can make decisions on the second question.

From what the client says to what the FDE asks back

The table below pairs common expectations with how the system actually behaves. The last column is the counter-question that turns an expectation into a scope of work.

The client says What the system actually does What the FDE should ask back
“It knows what to do” Calls a tool only when the request matches a described capability “What are the first three specific things you want it to do?”
“It gets into our systems by itself” The model only proposes calls; our application executes them “Which systems, read or write access, and who is accountable?”
“If information is missing, it figures it out” When a required parameter is missing, the model may infer a plausible-sounding value “Which fields must it always ask the user for?”
“Just let it decide” More autonomy means higher costs and errors that compound more easily “Which steps must have human approval?”
“Build the full version now” Start with the simplest solution and add complexity only when needed “Which parts of the process are already fixed and can be written as code?”

The third column is what the FDE adds: reading technical documentation and turning it into questions that help the client decide. That is the core skill of the job.

A worked example: the refund agent

Take a retail chain, an invented one, that wants an “AI customer service employee” to handle refunds too. The agent gets three tools: look up an order, check the returns policy, issue a refund. A customer writes: “I want to return the shoes I bought last week”, without giving an order number.

Anthropic’s documentation warns that when a required parameter is missing, the model may infer a plausible-sounding value. Here, “plausible” could mean the most recent shoe order from a different customer. A human employee would ask. With an agent, do not leave it to chance: design the system so it has to ask.

Then there is compounding error, which Anthropic names outright as the cost of autonomy. This is illustrative arithmetic, not measured data: if each step of an agent is right 95% of the time, a chain of 10 sequential steps is fully right only about 60% of the time (0.95 to the power of 10 ≈ 0.599).

That number is enough for an executive to see why “just let it decide” is a risky decision.

The way out lies in Anthropic’s distinction between two kinds of system. Workflows orchestrate LLMs and tools through predefined code paths. Agents let the LLM direct its own process. For refunds, the order lookup and the policy check are already fixed steps, so writing them as a workflow makes sense.

Only understanding the customer’s message and drafting the reply needs the model’s flexibility.

According to Anthropic, agentic systems often trade latency and cost for better task performance. Some cases are worth that trade; not all are. In this example the refund itself should require human approval until sandbox trial data shows otherwise.

That matches Anthropic’s own recommendation: test extensively in sandboxed environments and put guardrails in place.

Saying “not yet” without deflating the room

The most common mistake is the flat rebuttal: “What you want is AGI, and nobody can build it.” True, and it kills the enthusiasm that got the FDE into the room in the first place. A better approach is to acknowledge the destination and then map the route there in three steps:

  • Name what the client is picturing and say honestly that it is still theoretical.
  • List the concrete tasks together, and pick one with a clear process to build as a workflow first.
  • Agree on milestones at which data will decide whether to grant more autonomy.

Anthropic’s advice is to find the simplest solution possible and add complexity only when it is needed. Take that line into the meeting. It amounts to an ordered plan, something a decision-maker can approve, track and measure, and nobody hears it as a refusal.

The skill worth practicing is translating expectations into scope

Many developers, in Vietnam as elsewhere, are strong at code but rarely practice turning vague expectations into a concrete scope, a skill FDEs use every day. Practice explaining AGI, narrow AI and agents in sentences a sales director would understand on first hearing.

When reading job descriptions, look for phrases such as “translate business requirements”, “scope with stakeholders” or “customer-facing”. On a CV, do not just write “built agents with LLMs”; say where you chose a workflow over an agent, where you put approval steps, and why.

A small personal project is enough: an agent with a few tools, plus a page documenting the cases with missing parameters and how you forced the model to ask. That page shows how you think about a system’s limits, something a demo that “does everything” never reveals.

Simon’s promise fell short because it bet on machines working out for themselves what people want. The FDE’s job is to avoid that bet: sit with the client, write down each task they need done, and give the agent exactly the tools to do each one.
