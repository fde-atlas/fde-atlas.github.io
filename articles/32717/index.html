How to Calculate User Adoption Rate: A Forward Deployed Engineer's Guide to Driving Adoption

Original title: 用户采用率怎么算 FDE 推动落地指南

FDE Times · 2026-10-08 · 5 min read

Summary

This guide argues that for forward deployed engineers, adoption is part of the deliverable: software creates value only when users change how they work, and login counts hide the truth. It defines four baseline metrics—adoption rate, WAU, activation rate, and time-to-value—with SQL examples. A case of 40 planners shows logins suggesting 77.5% adoption while meaningful usage is only 15%. Old spreadsheets persist because they hold context the system lacks, so FDEs should observe users, fix data and workflow gaps, and train internal champions. It closes with common measurement mistakes and a five-step playbook.

Key points

  • Logins mislead; count meaningful actions over total intended users.
  • Four baseline metrics: adoption rate, WAU, activation, time-to-value.
  • Case study: 77.5% login rate vs. 15% real adoption.
  • Spreadsheets persist because they hold context the system lacks.
  • Five steps: define users, instrument events, measure, observe, fix.

Counting logins alone masks problems. Forward Deployed Engineers (FDEs) need to establish baselines, cultivate internal champions, and face up to what the old spreadsheets do well.

Key Takeaways

  • Installation itself creates no value. Value only appears when users change how they work—and users won't change just because a new system exists.
  • Counting only logins makes it easy to assume everything is fine. Instead, count meaningful actions and divide by the total number of target users.
  • Users cling to old spreadsheets usually because those spreadsheets contain context the system lacks. Sit next to them and find that context.

The final demo goes smoothly. The demand forecasting model produces accurate results, the data pipeline runs without errors, and the dashboard shows all green. Three weeks later, you open the logs and discover that most planners are still exporting data into their old spreadsheets and doing the calculations themselves.

For a Forward Deployed Engineer (FDE), this is one of the most frustrating kinds of failure, because there is no bug to fix. Umbrex points out that enterprise software rarely creates value from installation alone. No matter how accurate the model, if planners don't use it, the value it delivers to the customer is zero.

Adoption is therefore part of the deliverable itself, not something handed off to others after you leave. Tryolabs specifies two concrete outputs for the "drive adoption" step: a baseline of adoption metrics, and a well-trained team of internal champions. The rest of this article explains how to produce both.

What can the old spreadsheet do that your system can't?

Return to the planner above. The spreadsheet persists not because users are stubborn. Umbrex uses exactly this example: supply planners hold onto their spreadsheets because the enterprise resource planning (ERP) system lacks context; users won't change their workflows just because a new system arrives.

The spreadsheet contains things the official system doesn't. So your job has two parts: first, measure honestly to understand the current state; second, find the missing link between your solution and users' daily work.

Logins are not usage

The most common mistake is counting logins. Basedash emphasizes that users only count as "active" when they complete a meaningful action; logins don't count.

The denominator matters just as much.

For most FDE projects, the following four metrics are enough to establish a baseline:

MetricHow to calculateQuestion it answers
Adoption rateUsers completing meaningful actions / total target usersOf the people who should be using it, how many actually are?
WAUUsers completing meaningful actions in the past 7 daysAt a weekly work rhythm, how many people are using it consistently?
Activation rateUsers completing the action that unlocks core value / users who startedCan new users reach the "aha moment"?
Time to valueTime from first use to first value receivedHow long do users wait before seeing the solution as useful?

According to Basedash, for most B2B products, weekly active users (WAU) is the most sensible core engagement metric. The reason is simple: much enterprise work runs on weekly cycles, and daily counting can actually mislead you.

Basedash also provides reference thresholds for the DAU/MAU ratio: above 0.25 means the average user opens the product at least once every four days, which is good for B2B; below 0.10 is weak.

An example: 40 planners, only 6 actually using it

Imagine a distributor with 40 planners who are supposed to use your forecasting tool. You define a meaningful action as: approving or modifying a forecast suggestion, then pushing it to a purchase order. The query on the event table looks like this:

-- 按有意义的操作统计 WAU，以目标用户为分母
SELECT
  COUNT(DISTINCT e.user_id)                AS wau_meaningful,
  (SELECT COUNT(*) FROM intended_users)    AS intended,
  ROUND(COUNT(DISTINCT e.user_id) * 1.0
        / (SELECT COUNT(*) FROM intended_users), 3) AS adoption_rate
FROM events e
JOIN intended_users u ON u.user_id = e.user_id
WHERE e.event_type IN ('forecast_approved', 'forecast_edited_and_pushed')
  AND e.created_at >= CURRENT_DATE - INTERVAL '7 days';

Suppose 31 people logged in last week. Reporting by logins, the number is 31/40, or 77.5%—enough to satisfy the whole department. But the query above returns only 6 people. The true adoption rate is 6/40 = 15%.

Next, calculate DAU/MAU using the same definition. Suppose an average of 2 people complete a meaningful action each day, and 16 people completed at least one during the month.

The ratio is 2/16 = 0.125, between the weak threshold of 0.10 and the good threshold of 0.25. Taken together, these numbers say: plenty of people tried the tool, but few use it to replace their old way of working.

The numbers tell you the tool is stuck, but not where. Invisible Technologies notes that FDEs sometimes spend an entire day doing nothing but sitting next to users to understand how decisions are actually made.

Suppose that while observing a planner, you notice she copies the promotional calendar from the marketing team's emails into her own spreadsheet, because your model doesn't know which weeks have promotions. What's stored in the spreadsheet is exactly the context the system lacks.

The fix now involves both data and workflow. You add the promotional calendar as a feature, and display suggestions directly in the interface planners already use to create orders, rather than making them open another tab.

Invisible Technologies calls this designing workflows that match users' actual behavior. Then you pick two of the 6 real users and develop them into internal champions, because colleagues trust colleagues more than they trust vendor staff.

Five steps to do it yourself

  • Agree with the customer's project sponsor on who the target users are, and record the list as a data table.
  • Write a one-sentence definition of the meaningful action, and add event tracking for it before launch. No events, no baseline.
  • In the first week after launch, run queries for adoption rate, WAU, activation rate, and time to value. Send the numbers to the customer along with the definitions to avoid misinterpretation.
  • Observe at least three people up close: a heavy user, someone who tried and gave up, and someone who never opened it.
  • Precisely fill in what's missing, develop internal champions, then re-measure with the same definition and compare against the baseline.

Mistakes that make you think everything is fine

The first mistake is using account count instead of target users as the denominator. If only 10 of 40 people have accounts, a 100% usage rate among those 10 still masks the 30 people never reached. The second mistake is using DAU for a tool that only needs to be opened once a week, then wrongly concluding users aren't interested.

The third mistake is treating every adoption problem as a training problem. If the spreadsheet contains context the system lacks, another round of training won't fix it. The last mistake is leaving without internal champions in place: once you're gone, adoption will decline.

If you're preparing to transition into an FDE role, watch for phrases like "drive adoption" or "user enablement" in job descriptions.

On your resume, don't write "deployed X system"—instead, state clearly how many people completed a specific action per week, from what number to what number, out of how many total target users.

A sentence like that shows you understand that installation is not the finish line.

The project isn't over when the model runs. It's over when planners no longer need to open the old spreadsheet.
