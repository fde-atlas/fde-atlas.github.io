The difference between a Forward Deployed Engineer and a Software Engineer

Original title: 前线部署工程师和软件工程师的区别

FDE Times · 2026-10-08 · 5 min read

Summary

This article contrasts software engineers with forward deployed engineers (FDEs), citing Paraform's descriptions of Palantir (where FDEs are called Delta), Runway, and Greptile, plus comparisons from Aced.io. The core distinction: SWEs own a component for many users, while FDEs own one customer's outcome with no handoff to an implementation team—if a pipeline breaks at 2 a.m., the FDE fixes it. A hypothetical logistics deployment of an AI agent system shows how a conversation with the customer's VP reshapes technical goals before any code is written. FDEs also feed deployment lessons back to product teams. The piece ends with practice tips for product engineers and three common transition mistakes.

Key points

  • SWEs own components; FDEs own customer outcomes.
  • No handoff: FDEs fix customer incidents directly.
  • Customer conversations determine which code is worth writing.
  • FDEs relay deployment learnings to product teams.
  • Common pitfalls: premature generalization, waiting, treating communication as secondary.

The customer's data pipeline breaks at 2 a.m., there's no implementation team to hand off to, and "done" no longer means a merged PR.

Key takeaways

  • SWEs write code for a broad user base and are responsible for a component; FDEs write code for one customer and are responsible for that customer's outcome.
  • No handoff: when the customer's pipeline breaks at 2 a.m., the FDE fixes it; talking to the customer's VP comes before writing code.
  • A good FDE both solves problems for individual customers and brings lessons from deployments back to the product team.

Picture this scenario: it's 2 a.m. and the customer's data pipeline has stopped running. On a product team, you wouldn't learn about it until the next morning, via a ticket that support has already triaged. As a Forward Deployed Engineer (FDE), you're the one who gets the call, with no one in between.

Paraform puts it bluntly when describing FDE roles at Palantir, Runway, and Greptile: there is no handoff to an implementation team; if the customer's pipeline breaks at 2 a.m., the FDE is the one who fixes it. This is the clearest distinction between the two roles. Code is still code—same languages, same git, same code reviews. What's different is who the code is written for.

If you've spent a few years as a product engineer and want to move into FDE work, understand this before learning any tools. The users of your code change, and with them the way you define "done," the way you choose solutions, and the way you communicate with people every day.

Responsible for a component, or responsible for an outcome?

Aced.io compares the two roles side by side: software engineers own a feature, service, or component, with direction set by the team and managers. FDEs own a customer's outcome, with a degree of autonomy the site likens to being a startup's CTO—except scoped to a single customer.

The same source notes that software engineers (SWEs) in core roles rarely interact directly with customers, because they sit on product teams building features for everyone.

The difference is bigger than it looks. When you own a component, "done" means tests pass and the PR is merged; who uses it and how is someone else's problem. When you own an outcome, "done" means the customer has accomplished what they needed with the software.

Noah Brier describes FDEs in his Alephic newsletter this way: they sit inside the customer's organization and actually make the software work. By contrast, traditional engineers usually work behind the scenes and are often deliberately insulated from customers.

Paraform notes that at Palantir, these engineers are internally called Delta, and they don't write a spec, hand it to the product team, and wait for results.

A conversation that changes how you write code

Here's a hypothetical case showing how this skill plays out. You're an FDE deploying an agent system that processes documents for a logistics company. In week two, the customer's VP of Operations calls: 40% of documents are still being routed to human review, while they expected 10%.

A product engineer's first instinct is to open the logs and hunt for bugs. An FDE's first instinct is to ask. The conversation might go like this:

VP: "The system isn't delivering what you promised."

FDE: "I looked at the data—40% of documents are going to reviewers. Which type of document is causing your team the most trouble?"

VP: "Invoices from two major suppliers. Their formats are completely different."

FDE: "If I focus on those two formats this week and get the rate below 20%, could your team cut back on night shifts?"

VP: "Yes. That's exactly what we need most."

Notice what just happened. You haven't written a single line of code, yet you've already changed the technical goal: instead of improving a general model for all document types, you'll write dedicated parsers for two formats. A product team would never prioritize this, because it serves only one customer.

Aced.io puts it plainly: an FDE who can't communicate with the customer's VP is missing half the job. The scenario above also shows that it's the communication half that determines which code is worth writing.

But the work doesn't end with the customer. Paraform lists a typical FDE responsibility at AI startups: feeding deployment lessons back to the product team in near real time. Those dedicated parsers are themselves data: if a third customer hits the same supplier issue, the product team has grounds to generalize it.

You are both the person solving one customer's problem and the product's eyes and ears.

How to practice while still on a product team

You don't need to change jobs to start training. Begin with how you define "done." For every task you take on, ask: who exactly are the users? What will they be able to accomplish after it merges? If you can't answer, you're still thinking in components—that's the first habit to break.

Next, find opportunities to hear end users describe problems in their own words. The question "which type causes the most trouble" from the scenario above can't be learned from documentation; the intuition only forms after hearing enough people say "invoices from supplier X" rather than "low precision on category Y."

Then, practice closing the feedback loop. Whenever you make a fix for a specific situation, write down why and send it to whoever owns the roadmap. This is exactly how FDEs bring frontline experience back to product teams. On a resume, a line like "proposed generalizing X after deploying for Y" is more persuasive than any framework you could list.

When reading job descriptions (JDs), watch for phrases like "own customer outcomes," "embedded with customers," and "no handoff." They match the FDE role Paraform describes: accountable for post-sale outcomes, with no handoff to an implementation team.

If a JD only vaguely says "work with customers as needed," don't jump to conclusions; ask in the interview: when something breaks on the customer's side after launch, who is responsible?

Three common pitfalls for career switchers

The most common pitfall is bringing a "generalize first" mindset into customer projects. Product engineers are trained to avoid one-off code; in FDE work, code that serves only one customer is sometimes exactly the right answer, as long as it's well documented and reported to the product team.

A subtler pitfall is waiting. Writing a spec and waiting for another team to implement it is a hard habit to break; but it's clear from Paraform's description of Palantir's Delta that waiting is not an option. Aced.io likens an FDE to a CTO for one customer, which implies: there's no one above you to wait on for decisions.

The last pitfall is treating customer communication as a side task to handle after the code is written. The right order is the reverse, as the scenario above shows: without that call with the VP, you might spend two weeks tuning a general model without ever touching the customer's real need.

Rewrite an old PR as if for a single customer

Pick a PR you merged recently, imagine you're the FDE for one particular customer, and rewrite its description: state who the (hypothetical) users are, what outcome they need, what you'd do if it broke at 2 a.m., and the one-line message you'd send the product team once it's done.

Put it next to the original description, and you'll clearly see which parts of the job you never had to think about.

The code hasn't changed. Its users have, and the whole job changes with them.
