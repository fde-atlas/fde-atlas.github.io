Data Lake, Data Warehouse, and Lakehouse: A Practical Guide for Forward Deployed Engineers

Original title: 数据湖、数据仓库、湖仓一体区别：FDE 实战指南

FDE Times · 2026-10-08 · 5 min read

Summary

A practical guide for forward deployed engineers on distinguishing data lakes, warehouses, and lakehouses before building ML pipelines. The article argues warehouse tables are typically aggregated for reporting and lose signals models need, while lakes' schema-on-read approach leaves drift detection to the user. Lakehouses add a metadata layer enabling ACID transactions and schema enforcement, but these features must be verified as enabled. Using a retail churn prediction example, it covers ETL versus ELT tradeoffs, five questions to ask in week one, and common mistakes like trusting table names.

Key points

  • Warehouse tables are aggregated for reports, often losing model signals.
  • Schema-on-read lakes shift drift detection to the engineer.
  • Lakehouse features like schema enforcement may not be enabled.
  • ELT preserves raw data, allowing features to be rebuilt as needed.
  • Ask about lineage, schema checks, refresh cadence, and ownership early.

Warehouse data is processed for reports, not for models: in your first week, learn to tell data lakes, warehouses, and lakehouses apart, so you don't build pipelines on the wrong foundation.

Key Takeaways

  • Tables in a warehouse have been transformed for a single purpose, usually reporting, so they are rarely suitable as machine learning features as-is.
  • Data lakes use schema-on-read to preserve raw data. Nobody checks at write time, so you have to check at read time.
  • ETL or ELT, batch or streaming: these choices determine whether raw data is preserved and how fresh your features can be.

Every project kickoff has this moment. You ask where the data is, and the client answers confidently: "It's all in the warehouse, help yourself."

That statement is usually half true. The data exists, but it may have already been processed for another purpose, and refreshed on a cycle you don't yet know about. It may well have dropped exactly the signals your model needs most.

Misreading the data architecture is a hard error to catch because nothing breaks right away. The pipeline runs, the model outputs numbers, and it may take weeks before you realize the foundation was wrong. Below is how to get a clear picture of that foundation in your first week.

The difference is when the data gets "shaped"

Microsoft Azure defines a data lake as a centralized repository that ingests and stores large volumes of data in its raw form. The mechanism behind this is schema-on-read: data of any type is written in its raw form, and structure is only applied when the data is read.

A data warehouse is the opposite. As Azure describes it, a warehouse holds data that has been processed and transformed for a specific purpose. That purpose is usually reporting, and reporting's purpose rarely matches a model's purpose.

The lakehouse tries to combine the two. Databricks defines a lakehouse as an open data management architecture that combines the flexibility, cost efficiency, and scale of data lakes with the functionality of data warehouses, enabling business intelligence (BI) and machine learning to run on the same data.

Its technical core is a metadata layer that tracks which files belong to which version of a table. It is this metadata layer that gives lakehouses ACID transactions, as well as schema enforcement, schema evolution, and data validation.

Example: a customer churn prediction model

Suppose you're building a model for a retail chain to predict which customers are about to churn, with a requirement to flag them 7 days in advance. The client has a warehouse with monthly revenue summary tables for dashboards, and a data lake holding JSON app event logs. Every night, a job loads data from the lake into the warehouse.

This is exactly what Databricks calls a two-tier architecture: it requires ongoing maintenance, and the data is often not fresh enough. That's the view of a vendor selling lakehouse products, but it matches quite closely what Forward Deployed Engineers (FDEs) commonly see at customer sites.

Open the warehouse table and the first problem appears. The table is aggregated by month, so behaviors like "didn't open the app once this week" have already been compressed away. You need a 7-day early warning, but the data granularity is monthly, and no amount of model tuning can recover the lost signal.

So you go back to the data lake and immediately hit the second problem: the schema may have quietly drifted. Schema-on-read means nothing stopped bad data at write time, and the checking now falls on you. A simple PySpark query is enough for the first pass:

from pyspark.sql import functions as F

df = spark.read.json("s3://lake-cua-khach/app_events/")
(df.groupBy(F.date_trunc("month", "event_time").alias("thang"))
   .agg(F.count("*").alias("so_dong"),
        F.sum(F.col("customer_id").isNull().cast("int")).alias("thieu_customer_id"))
   .orderBy("thang")
   .show(36))

(These aliases are in Vietnamese:

thang

means month,

so_dong

means row count,

thieu_customer_id

means the number of rows missing customer_id.)

If the count of rows missing customer_id stays near zero for months and then suddenly spikes, the app team probably renamed a field in some release. The lake keeps ingesting data and the dashboards keep working, because someone quietly patched the nightly job. Meanwhile, your features silently turned into nulls.

The last question is freshness. Large-batch processing versus real-time (streaming) processing is one of the most fundamental distinctions in data engineering. If the client wants a risk score the moment a user opens the app, a nightly job can't do that, and you need to find this out before committing to any milestones.

ETL or ELT determines what you can preserve

IBM defines a data pipeline as a system that ingests raw data from multiple sources and then transforms it. Whether you transform first or load first determines whether the raw data survives.

With extract-transform-load (ETL), data is transformed after extraction and then loaded into storage. This suits warehouse-centric architectures, but the raw copy may be gone after transformation. With extract-load-transform (ELT), data is loaded first and then transformed inside the cloud warehouse, so the raw copy is preserved and you can rebuild features as the model needs.

In the retail example above, the sensible approach is to pull training data from the data lake in ELT fashion, write your own feature transformations, and manage them as your own code. If the client already has a lakehouse, use table versions to precisely reconstruct a training set for a given day, and enable schema enforcement to catch field renames at write time.

Five questions to ask in your first week

Start with lineage. For every table the client hands you, ask where it comes from and which report it serves. A table built for a finance team's dashboard is aggregated and filtered for finance's needs, which won't necessarily match the model's needs.

Next, ask whether the schema is checked at write time or only at read time, and who gets notified when a field is renamed. Then ask about the refresh cycle: nightly batch, hourly, or streaming, and how the actual latency compares to what the use case requires.

The last two questions concern reproducibility and ownership. Does the client keep table versions, and can historical data be reconstructed? Who owns the transformation jobs? Knowing who's responsible means you'll hear about job changes in advance, rather than discovering them after the fact.

The most common mistakes

The most common mistake is trusting table names. A table called "customer_features" can still be a report summary that happens to aggregate away the time dimension you need.

The second mistake is training on transformed warehouse tables while serving in production from raw lake data, or the reverse. The two paths go through different transformation logic, so the model sees different data in production than what it learned from in training.

The third mistake is assuming the data is clean the moment you hear "lakehouse." Schema enforcement and data validation are available features, not ones enabled on every table. Check the configuration instead of trusting the slides.

How to demonstrate this skill when job hunting

When reading job descriptions for FDE roles, watch for terms like lakehouse, ELT, batch, and streaming; they tell you which layer of the data stack you'll be working in. On your resume, a specific line like "discovered source tables were aggregated monthly, switched to raw data, and rebuilt features at daily granularity" is far more persuasive than a list of tools.

The definitions of the three architectures can be looked up anytime. What's truly worth practicing is the reflex: the moment you hear "it's all in the warehouse," you immediately know what question to ask next.
