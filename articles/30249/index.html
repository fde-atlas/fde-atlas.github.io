The difference between workflows and agents: when to use agents

Original title: 工作流和 Agent 的区别：什么时候该用智能体

FDE Times · 2026-10-08 · 5 min read

Summary

This FDE Times guide explains how to decide between workflows and agents when customers ask for an agent. The core test: if you can draw all branches before running anything, it is a workflow; agents are only justified when steps cannot be predicted in advance. The author recommends starting with the simplest option—a single LLM call with retrieval and examples—and notes Anthropic's finding that multi-agent systems consume roughly 15x the tokens of normal conversations, suiting only high-value, parallelizable work. A logistics email-reply example shows a hybrid design: deterministic branches as workflows, an agent confined to unpredictable complaint investigation with tool limits, step caps, and human review. It closes with a five-step method, common mistakes, and resume advice.

Key points

  • Key test: who decides the next step—your code (workflow) or the model (agent)?
  • Start simple; one LLM call with retrieval and examples often suffices.
  • Multi-agent systems use ~15x tokens; reserve them for parallelizable, high-value tasks.
  • Narrow agents to unpredictable branches with tool limits, step caps, and human review.
  • Avoid choosing agents based on demos, unshared context, and missing measurements.

Key takeaways

  • Workflows run along predefined code paths, while agents are steered by the LLM. Which one to choose depends on how predictable the problem is.
  • Start with the simplest solution. A single LLM call with retrieval and examples is often enough.
  • Agents trade latency and cost for quality. Multi-agent systems consume roughly 15 times the tokens of a normal conversation, and are only suited for high-value, parallelizable work.

The first meeting with a customer often opens with a confident request: "We want an agent to handle customer emails." They've seen demos and read the news, and in their eyes, "agent" is the most cutting-edge thing.

The job of a Forward Deployed Engineer (FDE) is not to nod along, but to find a design pattern that solves the problem within the latency, cost, and reliability the customer can accept. Get this step wrong, and three months later you'll be debugging a system no one can explain, wondering why its answers differ from yesterday's.

The skill covered in this article isn't grand, but it's useful almost every week: understanding the customer's problem and judging whether it needs a workflow, an agent, or something simpler than both.

Who decides the next step?

Anthropic has given a concise definition. A workflow is a system that orchestrates LLMs and tools through predefined code paths. An agent is a system where the LLM autonomously decides the process and tool usage—in other words, the model controls how the task gets done.

LangGraph's documentation draws the same line: workflows have predetermined paths and run in a designed order; agents are suited for scenarios where neither the problem nor the solution can be predicted in advance.

So the classification question is simple: Who decides the next step—your code or the model? If you can sit down and draw a branch diagram before anything runs, it's a workflow. If you can't list the steps because they depend on what the model discovers along the way, that's where an agent earns its place.

The complexity ladder

Anthropic's core advice is: find the simplest solution possible, and only add complexity when truly needed. It also explicitly notes that for many applications, optimizing a single LLM call, paired with retrieval and contextual examples, is usually enough.

The reason is the trade-off. Agent-type systems typically trade higher latency and cost for better quality; workflows offer predictability and consistency for well-defined tasks. For enterprise customers, "consistent" is often what they need most—they just don't say it that way.

At the top of the ladder are multi-agent systems, where multiple agents run in parallel. Anthropic reports that its multi-agent system consumes roughly 15 times the tokens of a normal conversation. In its view, such systems suit high-value work that parallelizes well, and most coding tasks are harder to parallelize than research tasks.

A complete example

Imagine a logistics company wants to automate replies to customer emails. You ask for 50 real emails and classify them by hand. Suppose the result is: most are asking about order status, some are policy questions with answers in the FAQ, and a small portion are complex complaints.

The steps for the first two categories can be written on paper right away: identify intent, extract the order number, query the database, draft a reply. There are no surprises here, so this is a workflow:

# 工作流：路径由代码决定
def handle_email(email):
    intent = classify(email)  # 1 次 LLM 调用，只返回固定标签
    if intent == "order_status":
        order = db.get_order(extract_order_id(email))
        return draft_reply(email, context=order)
    if intent == "policy":
        return draft_reply(email, context=search_faq(email))
    if intent == "complaint":
        return investigate_complaint(email)  # 唯一使用 Agent 的分支
    return escalate_to_human(email)

The agent version the customer has in mind is usually a fully equipped

while True

loop, including

issue_refund

. This way, whether to issue a refund is decided by the model inside the loop, and no line of code can stop it in advance.

In the workflow version, the number of LLM calls each email goes through is fixed, so you can estimate cost, measure latency, and immediately know which branch went wrong when something breaks.

The agent isn't thrown away—it's narrowed. If the complaint category truly requires querying multiple sources in an unpredictable order, put an agent on just that one branch, and limit the toolset and set a step cap:

# 只在投诉分支使用 Agent：路径由模型决定，但有护栏
COMPLAINT_TOOLS = [get_order, search_faq]  # 只读，不含 issue_refund
MAX_STEPS = 6

def investigate_complaint(email):
    messages = [COMPLAINT_PROMPT, email]
    for _ in range(MAX_STEPS):
        step = llm(messages, tools=COMPLAINT_TOOLS)
        if step.is_final:
            return draft_for_human_review(email, findings=step.text)
        messages.append(run_tool(step))
    return escalate_to_human(email)  # 步数用完：转交人工

This is a hybrid design you can defend in front of a customer: predictable parts go to code, and only the unpredictable parts go to the model. Even there, the model only reads and proposes suggestions; the refund decision is still made by a human.

Five steps to do it yourself

Step one: collect real samples instead of listening to the customer's description. Thirty to fifty real cases will tell you how predictable the problem is—something the first meeting will never reveal.

Step two: try the lowest rung first. Write a good prompt, add retrieval and a few examples, then run it on the sample set. If the results are good enough, stop there.

Step three: draw a branch diagram for the cases the first rung didn't solve. Every branch you can draw should become a workflow.

Step four: use an agent only for what remains—the part where you truly can't list the steps. Set a cap on loop iterations and include only the necessary tools, like the

investigate_complaint

function above.

Step five: only consider multi-agent when the task can be split into independent parts that run in parallel, and the value of the results justifies the extra tokens.

Common mistakes

The most common mistake is choosing an agent because the demo looks good. Demos run a few simple cases; production runs thousands, and the customer needs the same result every time.

The second mistake is splitting work across multiple agents without sharing context. Cognition, the company behind Devin, recommends sharing context and sharing complete agent trajectories, not just individual messages.

It also points out that every action implies a decision; when parallel agents make conflicting decisions, the results are poor.

The third mistake is not measuring. If you don't know how many calls each request takes or how long it waits, you can't explain to the customer why you should climb another rung—or why you shouldn't.

Turning this skill into a job-hunting advantage

If a job description you're targeting mentions agents, be ready to explain why you chose that architecture, not just that you've built agents. How you weighed the trade-offs is what's worth discussing.

So don't just write "built an AI agent" on your resume. Describe the decision process: which rungs you tried, what you measured, why you stopped at a workflow, or why you escalated to an agent.

A sentence like "migrated queries from an agent loop to a fixed workflow for consistent results" shows you understand the trade-offs. That's exactly the judgment you make sitting next to customers, week after week.

Exercise: have an agent tell you which parts should become workflows

Take an existing agent loop, or write one similar to

investigate_complaint

for the email problem above. Run it 20 times with 20 different inputs, and record the order in which the model calls tools each time.

Then compare these sequences side by side. Sequences that repeat almost identically are candidates for rewriting as workflow branches; sequences that differ every time are the parts worth leaving to the agent. Also record the average number of steps per run to determine what

MAX_STEPS

should be set to.

The next time a customer says "we want an agent," first ask them for their last fifty emails. Chances are, those emails will give you the answer.
