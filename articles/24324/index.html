What Is MLOps: Five Things Every FDE Must Do Before a Model Goes Live

Original title: MLOps 是什么：FDE 模型上线前必做的五件事

FDE Times · 2026-10-08 · 5 min read

Summary

This guide argues that a model working in a notebook is not a product, and that the hard part of ML in production is building and continuously running an integrated system. Using a supermarket demand-forecasting scenario, it lays out five steps in order: version-control models as artifacts with prediction logging, use a single feature source and measure training-serving skew, test infrastructure with a simple baseline before swapping in the real model, monitor on live data with alert thresholds agreed in business terms, and build a retraining pipeline with review gates and rollback. It cites Google Cloud's MLOps architecture, Zinkevich's Rules of Machine Learning, Sculley's technical-debt paper, and CD4ML, and notes Palantir's Forward Deployed Infrastructure Engineer job posting explicitly lists monitoring, alerting, on-call, and production incident handling.

Key points

  • The model is only one part; the pipeline and operations matter most.
  • Five steps: versioning, single feature source, baseline testing, monitoring, controlled retraining.
  • Palantir's FDE infrastructure role explicitly requires monitoring, alerting, and on-call work.
  • Measure training-serving skew by logging features and recomputing them offline.
  • Hand over alerting before leaving the customer site, or the delivery is incomplete.

From version management to controlled retraining, five things that let an FDE handle the first complaint call—already written into Palantir's hiring requirements.

Key Takeaways

  • The hard part of getting machine learning into production is building and running the whole system; the model is only one part of it.
  • Version-control the model as an artifact, use a single source for features, measure skew, and test the pipeline with a simple model first.
  • Palantir's Forward Deployed Infrastructure Engineer job posting explicitly states that monitoring, alerting, and handling production incidents (including on-call) are part of the job.

Imagine you've just plugged a demand forecasting model into a supermarket chain's ordering system. In the notebook, the error metrics looked great, and the demo to executives went smoothly. Three weeks later, the warehouse manager calls: fresh milk orders have doubled, and no one on site knows which version of the model is running in production.

This situation is rarely caused by the model itself being bad. Google Cloud's MLOps architecture documentation puts it bluntly: the difficulty lies in building an integrated machine learning system and keeping it running continuously in production. At least one company hiring Forward Deployed Engineers (FDEs) has written this work directly into the job description.

Palantir's Forward Deployed Infrastructure Engineer job posting lists the work to be done at deployment sites: monitoring and alerting, configuration management, and system upgrades.

New hires are also jointly responsible for diagnosing, resolving, and preventing production incidents, including on-call duty. If you're targeting this kind of role, these skills will be tested in daily work—not just a few lines to decorate your resume.

Why is a model not a product?

In 2015, D. Sculley's team published "Hidden Technical Debt in Machine Learning Systems" at NIPS. They observed that real-world machine learning systems often carry massive, long-term maintenance costs, stemming from data dependencies and changes in the external world.

The supermarket changed its product codes, the POS terminals got a software upgrade, and customers changed their shopping habits after Tết (Lunar New Year). The model didn't change, but the data it receives is no longer the same.

Therefore, machine learning has one additional requirement over ordinary software. Google Cloud calls this continuous training (CT): automatically retraining and then putting the new model into service.

They also point out that in machine learning, continuous delivery (CD) is no longer about deploying a software package or a service, but deploying an entire system; and continuous integration (CI) must test not only the individual components but also the data.

Martin Zinkevich offers a brief piece of advice in "Rules of Machine Learning": keep the first model simple and get the infrastructure right. For an FDE, the priority is therefore quite clear: the first few days at a customer site should be spent building the data pipeline, not tuning hyperparameters.

Taking the supermarket chain as an example: five things, in order

First, know exactly what's running in production. Back to that call about fresh milk: the first question is always "which model?". The CD4ML article on Martin Fowler's site recommends treating the model as an artifact, versioning and deploying it like any other build output. Every prediction log line should record at least enough information to trace back:

log_prediction({
    "model_version": "demand-v14",
    "feature_snapshot": "2026-10-01",
    "store_id": "HCM-021",
    "sku": "SUA-TUOI-1L",
    "prediction": 240,
})

With this log line, you can get an answer in minutes instead of days. While the warehouse is still waiting for orders, you can also roll back to the previous version.

Second, use only one source for features. Suppose the "7-day average sales" feature is computed from the data warehouse during training, with returns already deducted; while in production, the same feature comes from the real-time POS data stream, where returns have not yet been deducted. If a product's net daily sales in the data warehouse are 100 units but POS reports 115, the model sees a world 15% busier than the one it learned from. This is training-serving skew.

Google Cloud recommends using a feature store as a shared data source for both experimentation and serving to avoid skew. But even without a feature store, you should still measure skew, as Zinkevich's Rule 37 says.

The simplest approach: log feature values at serving time, then recompute them offline for the same day and same store, and compare the two numbers.

Third, test the infrastructure and the machine learning separately. Zinkevich writes that infrastructure should be tested independently of the machine learning. For this supermarket chain, you could first replace the model with a "dumb" baseline: this week's forecast simply equals last week's sales. Then run the baseline through the entire pipeline, from reading data and generating predictions to writing orders into the ordering system.

If the baseline also messes up the orders, the problem is in the pipeline—and you'll know before wrongly blaming the model. Only once the baseline runs cleanly should you swap in the real model.

Fourth, monitor based on real data. Google Cloud defines monitoring as collecting model performance statistics based on live data. For a forecasting problem, when each day's actual sales arrive, compare them against the previous day's predictions and compute error by product category. Also check the inputs, such as the number of rows received and the proportion of null values, because data problems usually show up here first.

Monitoring without alerting is just a dashboard nobody opens. Alert thresholds should be agreed with the warehouse manager and expressed in their language, for example "if the deviation exceeds X percent, someone must be notified." Thresholds you set yourself in code, they can't read—and nobody will watch them.

Finally, close the loop back to training. CD4ML emphasizes that after deployment you must understand how the model performs in production and feed real data back into the training loop. In the supermarket scenario, each day's actual sales are the labels for the next round of training. Retraining needs a review step: only if the new model performs better on recent weeks of data can it replace the old one.

At 2 a.m., which answers do you need ready?

One way to test whether you're prepared: imagine you're answering an on-call call, and ask what you'd need to answer each question.

Customer's questionWhat you must have ready in advance
Which model is running in production?Every log line records the model version
Is it a data problem or a model problem?Skew measurements and baseline run results
Since when has the model been getting worse?Performance statistics based on real data, with alerting
How do you ship the fix?A retraining pipeline with a review step and rollback

As long as any cell in the right column is empty, that's work to be done before the model is allowed to write its first order.

Common FDE mistakes

One is assuming that sharing feature computation code eliminates skew, when the input data sources may already differ. Another is tracking only latency and CPU and thinking that counts as monitoring the model.

The hardest mistake to spot is delivering the system without handing over the alerting. When you leave the site, someone on the customer's side must know where alerts go and what to do when one arrives.

How to demonstrate this capability on your resume

When reading FDE job descriptions, watch for words like monitoring, alerting, upgrades, on-call, and production issues. They signal that the company needs people who can operate systems, not just people who can train models.

On your resume, don't just write "deployed a forecasting model"—be more specific, for example: "built a pipeline with version management, measured training-serving skew, and set up alerting with thresholds agreed with the business side."

Before the interview, prepare a real story: the last time your model failed on real data, how you discovered it, and how long it took to pinpoint the problem. Such a story demonstrates the work described in these job postings more clearly than any accuracy figure.
