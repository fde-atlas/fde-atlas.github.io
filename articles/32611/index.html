How FDEs Choose Large Models for Customers: Data Retention and Compliance

Original title: FDE 如何为客户选大模型：数据保留与合规

FDE Times · 2026-10-08 · 6 min read

Summary

This article argues that on customer sites, model selection is driven by data retention, processing region, and contract channels rather than market share or leaderboards. Citing Menlo Ventures' mid-2025 enterprise LLM shares (Anthropic 32%, OpenAI 25%, Google 20%), it explains why rankings shouldn't justify recommendations. It compares OpenAI, Anthropic, Gemini on Google Cloud, and self-hosted open-weight models like gpt-oss-120b on retention terms, data residency, procurement routes, and costs, and recommends abstraction layers like LiteLLM with fallbacks to avoid vendor lock-in, closing with skill advice for aspiring FDEs.

Key points

  • Model choice hinges on data retention, residency, and contracts, not benchmarks.
  • OpenAI and Anthropic's "30-day" retention terms mean different things; zero retention needs a separate agreement.
  • Buying Claude through Google Cloud or Bedrock simplifies procurement but changes which data rules apply.
  • Regional endpoints cost 10% more than global ones, yet defaults may breach residency promises.
  • Use an abstraction layer with fallbacks so switching providers is configuration, not refactoring.

Key takeaways

  • According to Menlo Ventures' mid-2025 survey, Anthropic holds 32% of enterprise LLM usage, OpenAI 25%, and Google 20%. But market share is not a reason to pick a model for a specific customer.
  • For each individual customer, the choice of provider usually comes down to data retention, processing region, and the customer's existing cloud contracts.
  • Put models behind an abstraction layer so the choice can be reversed, rather than becoming a long-term lock-in.

In mid-2025, Menlo Ventures published a number that surprised many: Anthropic holds 32% of enterprise LLM usage, ahead of OpenAI and Google (20%). OpenAI has fallen to 25%, half its own share from two years ago.

Many engineers, seeing this, draw a simple conclusion: pick whoever is leading. That conclusion isn't entirely wrong. But it answers "what is the market using," while at the customer site, the real question is: which model is permitted to run on their data.

Anyone who wants to become a Forward Deployed Engineer (FDE) should internalize this early. At the customer site, which model you pick depends more on where data lives, how long it's retained, and which contract applies than on benchmarks. The person who understands these constraints runs the meeting.

Those who only know the leaderboards usually end up listening to the legal team explain those constraints.

What market share can and cannot tell you

Menlo's data is still useful as a reference. It shows that enterprises choose models based on performance rather than price, and developers tend to prefer frontier models over cheaper, faster ones. So the default choice should be a frontier model, not the cheapest one.

Also per Menlo, open-source (open-weight) models account for only 13% of enterprise AI workloads, down from 19% six months earlier. Taken alone, that number suggests open weights are losing ground.

But market-wide averages say nothing about the specific customer sitting across from you. The question worth asking is: does this customer have some constraint that forces them onto open weights?

Also note that this survey was published in July 2025; by the end of 2026, the shares may have shifted. Use it to understand trends, but don't cite it as a justification when recommending a model to a specific customer.

First question: how long is data retained?

Imagine you're deploying an agent that reads insurance claims documents. The first thing compliance will ask is almost certainly how long the provider retains their prompts, not which model is smarter.

Both OpenAI and Anthropic have a "30 days" figure, but the mechanics differ. OpenAI generates abuse monitoring logs for each API feature, retained by default for up to 30 days. Anthropic's standard API automatically deletes the inputs and outputs themselves within 30 days of receiving input or generating output.

These two statements describe different things, so don't paste "30 days" into compliance documents as if they were the same. Spell out exactly what is being retained. Anthropic's zero data retention requires a separate agreement; simply creating an API key doesn't get you there.

This detail directly affects timelines. If the customer requires that no data be stored even for a day, you can't make that commitment in week one, because the agreement still needs to be signed. Write this requirement into the plan from the start, so it doesn't stall you on the way to production.

Where is data processed?

The second question is the processing region. OpenAI allows setting a data residency region for each new project, with options including the US, Europe (EEA and Switzerland), and the UAE. Since this setting only applies to new projects, the project must be created in the right region from the start, not with plans to migrate later.

The customer's cloud has often already made the choice for you

This is a point many new FDEs overlook: the procurement channel for a model sometimes matters more than the model itself. Claude is sold through multiple channels, including Google Cloud, Amazon Bedrock, and Microsoft Foundry. If the customer already has a contract with a hyperscaler, they can use Claude under that contract without onboarding a new vendor.

For procurement, this can dramatically shorten the process. The trade-off is that data processing rules vary by channel: when using Claude on Google Cloud, data processing is governed by Google Cloud. So the document handed to compliance must be Google Cloud's, not Anthropic's privacy page.

Next come the endpoints. On Google Cloud, Claude's regional and multi-regional endpoints cost 10% more than the global endpoint, and the official recommendation is to default to the global endpoint. If the customer's monthly bill on the global endpoint is $1,000, switching to a regional endpoint makes it $1,100. Not a large amount, but tell the customer in advance so the bill isn't a surprise.

Gemini on Google Cloud works similarly. Requests sent to the global endpoint may be processed at any Google Cloud location worldwide, while jurisdiction endpoints restrict ML processing to within that region.

If you leave the global endpoint in place just because it's the default, you may unknowingly violate the customer's data residency commitments to their own users.

When should you choose open weights?

Some customers can't use any of the columns on the left of the table: for example, data that cannot leave internal infrastructure, or a required region not on a provider's support list. For these customers, open weights are an option worth serious consideration, even at 13% market share.

OpenAI's gpt-oss-120b is a concrete example. Released under the Apache 2.0 license, it runs on a single 80GB GPU (such as an NVIDIA H100 or AMD MI300X). In other words, what the customer needs is one GPU server, not an entire cluster.

Licensing and hardware matter just as much. The model page states Apache 2.0 has no copyleft restrictions or patent risks. When a customer plans a commercial deployment, this is a concrete argument you can hand to their legal team, though approval is still their call.

The remaining hard work falls to you: operations, monitoring, and upgrading the model—tasks an API provider would normally handle for you.

So only propose open weights when data constraints genuinely require it.

Don't lock your system to a single provider

The constraints above can change mid-project. The customer might sign a zero-data-retention agreement in month three, switch to a different cloud, or a new model stronger than the one you're using might appear. If the provider's name is scattered throughout the code, every change means a refactor.

LiteLLM was built for exactly this. It lets you call over 100 LLMs using the same OpenAI format, covering OpenAI, Anthropic, Vertex AI, Bedrock, and many other providers. It also supports fallbacks and per-team cost tracking, so switching models becomes a config change, not a code change.

From this, the on-site process with a customer should follow three steps. First, determine the data and contractual constraints to rule out unusable options. Then run evals on the customer's real data with the remaining frontier models, put the winner behind an abstraction layer, and use the runner-up as the fallback.

What developers should practice

When a customer operates in multiple countries, the question of where data is stored often comes up in the very first meeting. Learn to answer this question before answering which model is stronger. Every time a provider releases an update, re-read its data controls page and update your comparison table.

When reading FDE job descriptions, watch for terms like "data residency," "compliance," "multi-cloud," or "Bedrock/Vertex." They indicate the daily work will revolve around these constraints. Don't just write "integrated GPT-4" on your resume.

Instead, write that you designed a model invocation layer with fallbacks between two providers, and chose endpoints based on the customer's data residency requirements.

A suitable side project is building an internal chatbot that supports three configurations: OpenAI's API, Claude via a cloud provider, and a self-hosted gpt-oss-120b. Include a README explaining which scenarios each configuration suits.

That README proves you can understand a customer's constraints and pick the right configuration—something a demo of calling an API cannot prove.

Market share rankings change every six months. But questions about retention periods, processing regions, and contracts get asked again by every customer.
