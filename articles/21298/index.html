Cohere FDE Job Requirements and Job Search Preparation

Original title: Cohere FDE 岗位要求与求职准备

FDE Times · 2026-10-24 · 6 min read

Summary

The article analyzes four distinct Cohere roles that all carry the FDE title: Agentic Platform, Infrastructure Specialist, FDE Tech Lead, and a public-sector infrastructure variant. The split stems from North being deployable in a customer VPC, on-premises, or via Model Vault, dividing work into agent building versus deployment infrastructure. The author maps each job requirement to concrete evidence—production-grade Python with tests, Helm charts, audit logs, and pre-install infrastructure assessment checklists—using a bank loan-review agent as a sample project, and closes with preparation order and common application mistakes.

Some roles require building agents, others require managing production-grade Kubernetes and Helm, and each track demands different evidence in preparation.

Key takeaways

  • North can run in a VPC, on-premises, or through Model Vault, so Cohere splits the FDE role into two tracks: building agents and deploying infrastructure.
  • The Agentic Platform track requires production-grade Python; the infrastructure track requires Kubernetes, Helm, and experience with Azure, AWS, and GCP.
  • An agent project packaged with Helm, with audit logs and an infrastructure assessment checklist, proves capability better than any list of technical buzzwords.

Open Cohere's job posting for a Forward Deployed Engineer (FDE) and you'll read: this role leads the design, building, and delivery of LLM-based agents that can reason, plan, and execute actions through multiple tools.

Look at another posting with the same FDE title, and it instead requires experience managing production Kubernetes clusters and proficiency with Helm. Same job title, but the two people hired do almost entirely unrelated work.

Reading job postings is itself an FDE skill. It's exactly like reading customer requirements: first separate must-haves from nice-to-haves, then figure out the problem the person writing the requirements actually needs solved.

Cohere's job postings are great practice material, because a single product has spawned four types of FDE, each with its own evaluation criteria.

If you're preparing to transition into an FDE role, whether at Cohere or any other company selling AI platforms to enterprises, the breakdown method below applies to most postings you'll encounter.

Why does one product need several types of FDE?

It all stems from how Cohere sells North. The company's product page states that customers can run North in their own VPC, on-premises, or through Cohere's Model Vault inference platform. The same page emphasizes a zero-trust security framework, strict access controls, and auditability.

When a product can run inside the customer's infrastructure, the work naturally splits in two. One half is making North actually solve business problems: building agents and features. The other half is getting North running in data centers Cohere doesn't control.

The Agentic Platform posting corresponds to the first half: delivering features for North and solving business problems directly with customers. The Infrastructure Specialist posting corresponds to the second half: leading the full deployment of North in private cloud and on-premises environments.

Beyond these two tracks, Cohere also hires FDE Tech Leads to lead a team of engineers across multiple directions, including backend, infrastructure, and agent development, on customer-facing projects.

The Tech Lead owns the entire launch process for agents and tools, from planning and configuration to testing and delivery to end users. The fourth type is an Infrastructure Specialist for the public sector, requiring Canadian citizenship and a security clearance.

What is each posting actually testing?

The core technical requirement for the Agentic Platform track is hands-on experience building and deploying production-grade Python software.

Nice-to-haves include: having set architectural standards for AI and agent systems within distributed teams, and experience working in highly regulated industries.

The posting also states an expected travel ratio of 20–40%.

The word "production" deserves the closest reading. A demo that calls a model API hardly proves this requirement. What you should show recruiters is code that runs for the long haul: with tests, retries on tool timeouts, logging, and packaged for deployment.

The infrastructure track requires three things: production Kubernetes and Helm; solid knowledge of cloud (Azure, AWS, GCP), networking, and virtualization; and the ability to work with customer IT teams to assess their infrastructure, security requirements, and data management practices.

That last point shows this isn't purely ops work. Before typing the first install command, you already need to have completed the technical discovery with the customer.

The public sector version describes the FDE as a bridge between the North product and the customer's engineering team. This is also the right lens for viewing all four postings: you stand in the middle, and your value lies in making both sides understand each other.

Example: turning every requirement into evidence

Imagine a bank that wants to run North in its own VPC and deploy an agent: look up loan files, verify eligibility, then create tickets for the credit review team.

This portfolio project works for both tracks, because it involves agents, a highly regulated industry, and deployment within private infrastructure all at once. The table below maps each requirement from the postings to what you need to demonstrate.

Requirement in the postingWhat the recruiter is evaluatingThe evidence you present
An agent that can reason, plan, and execute actions through toolsThe agent decides which tool to call, not a chatbotAn agent that calls 3 tools (database query, simulated internal API, ticket creation), logging its reasoning at each step
Production-grade PythonCode that runs reliably outside your machineTests for every tool, error handling for tool timeouts, plus a Dockerfile
Experience in highly regulated industriesUnderstanding of auditing and access controlAn audit log recording who asked what and which records the agent read
Production Kubernetes and HelmKnowing how to install, upgrade, and roll backA Helm chart written for this agent, with a values file for each of two environments
Infrastructure assessment with customer ITTechnical discoveryA checklist of questions to ask before installation

The last cell is the one most easily skipped when preparing on your own, so it's the most worth investing effort in.

A good checklist asks about the things that could derail a deployment: which version the cluster runs, whether outbound internet access is allowed, which internal registry images are pulled from, which identity provider handles login, how long logs must be retained, and which data is forbidden from leaving a given network zone.

Every question corresponds to an incident that could happen on site. Ask them upfront, and the incident gets resolved on paper instead of being left for launch day.

In what order should you prepare?

The first step is choosing a track. If you're strong in Python backend work and have built systems that call many services, aim for Agentic Platform.

If you've operated real clusters, dealt with networking issues, and been blocked by security policies, the infrastructure track is a better fit. Tech Lead suits those who have already led cross-functional teams and delivered products into end users' hands.

For the public sector version, once the hard requirements are met, the core evidence remains the same as the infrastructure track.

But since the posting describes the FDE as a bridge between North and the customer's engineering team, you should also include a handover document written for that team: how to install, upgrade, and roll back the deployment, and who to contact when things go wrong.

Next, do a project similar to the banking example above, but put most of your effort into the part that belongs to your chosen track. If you're doing agents, invest in evals that check whether the agent picks the right tools. Infrastructure candidates should try installing on a cluster with outbound traffic blocked, and personally run into the errors that on-premises customers encounter.

Finally, rewrite your resume around the results. A line like "Kubernetes, Helm, Python, LangChain" only shows you know the names of these tools. A line like "packaged a Python agent that calls 3 internal tools as a Helm chart, deployed it to a cluster with no internet access, and included a pre-installation infrastructure evals checklist" answers three requirements at once.

Mistakes that get applications rejected early

The easiest mistake to avoid is not reading the hard requirements carefully. The public sector version requires Canadian citizenship and a security clearance, and no portfolio can make up for that. Likewise, the 20-40% travel requirement should be thought through before applying, not after the final interview.

The second mistake is applying for a role that requires production experience with nothing but a prompt demo. The third mistake is common among infrastructure candidates: only knowing how to click through a cloud provider's managed services to create a cluster, while North also deploys to on-premises environments, where you have to handle the image registry, certificates, and network paths yourself.

Tech Lead candidates tend to fall into telling code stories. The posting makes clear that this person owns everything from planning to the end user actually using the product, so what you should tell is a launch story: who you trained, how you tested it, and what happened in the first week.

When preparing for interviews, don't just review agents or Kubernetes. All four postings place you between the product and customer engineering teams, so practice asking the right questions before touching an unfamiliar IT team's systems, starting with reading the job posting carefully.
