On-Site Git Configuration Guide for Customers: includeIf and CODEOWNERS

Original title: 客户现场 Git 配置指南：includeIf 与 CODEOWNERS

FDE Times · 2026-10-08 · 5 min read

Summary

This guide from FDE Times walks through five Git habits for forward deployed engineers working on a client's internal GitLab, arguing that identity and workflow mistakes erode client trust faster than bugs. It covers installing Git on locked-down machines, using includeIf to switch user.email per client directory, renaming remotes so pulls and pushes never go to the wrong server, choosing the cache credential helper instead of the plaintext store helper, and reading CODEOWNERS before branching to split merge requests by owning team.

Key points

  • Configure includeIf gitdir rules so each client directory uses the correct commit email.
  • Rename origin to a client-specific remote and always name the remote explicitly when pushing.
  • Never use the store credential helper on client machines; cache expires credentials after 15 minutes.
  • Read CODEOWNERS first and split changes so each MR needs only one owning team's approval.
  • Treat required approvals as a map of code owners to engage early, not an obstacle to bypass.

From separating identities by directory to following review rules, five habits that keep your first merge request on a client's internal GitLab from getting stuck.

Key Takeaways

  • One directory, one identity: with includeIf gitdir, you'll never commit to a client repository with the wrong email again.
  • Name remotes after the client, separate pull and push sources, and don't let every remote be called origin.
  • Don't use the store helper on client machines—it writes passwords to a plaintext file that never expires; read CODEOWNERS before writing your first line of code.

On Wednesday afternoon of your first week, the merge request is stuck: the Merge button is locked, and in the commit history, your personal email sits alongside the client company's email.

Imagine your first week at a bank. You're given a laptop that forbids installing software yourself, a bank-internal GitLab account, and a repository with a dozen branches named after regional branch offices. There's nothing technically difficult in this scenario. But mistakes like this erode client trust faster than bugs, because they show you haven't yet understood the client's environment.

For a Forward Deployed Engineer (FDE), Git at the client site is an operational skill consisting of five things: installing Git on a machine that isn't yours, managing your identity, handling multiple remotes, protecting credentials, and following the client's review rules.

The client's machine, the client's rules

The first task is getting Git running. Pro Git notes that on Debian-based Linux distributions like Ubuntu, install with

apt

On macOS Mavericks (10.9) and later, the first time you type

git

in the terminal, the system will prompt you to install the Xcode Command Line Tools.

Windows is where people get stuck most easily. The official builds come from Git for Windows, a project separate from Git itself; the Chocolatey package is community-maintained. On a client-locked virtual machine, ask IT which sources are allowed before downloading anything, because downloading from the wrong source can turn into a security ticket.

If the client's operating system ships a very old Git version, Pro Git mentions installing the latest version from source. This should only be a last resort, and only if the client allows compiling on their machines.

One directory, one identity

The most common mistake for people serving multiple clients at once is committing with a global

user.email

configuration.

git config

The documentation describes exactly this situation: you can use

gitdir

with an

includeIf

condition to apply different

user.name

and

user.email

。

The simplest structure is one directory per client. In

~/.gitconfig

:

[user]
    name = Nguyen Van A
    email = [email protected]

[includeIf "gitdir:~/clients/bank/"]
    path = ~/clients/bank/.gitconfig

In

~/clients/bank/.gitconfig

:

[user]
    email = [email protected]

Now, all repositories under

~/clients/bank/

will use the client-assigned email. To verify: cd into one of the repositories and run

cd

Enter one of the repositories and run

git config user.email

。

git config

The documentation uses exactly this kind of condition to apply configuration to all repositories under a directory, so each client only needs to be declared once.

Whose origin is it, anyway?

When cloning from the client's GitLab, the default remote is called

origin

. A few weeks later, you add an internal repository from your own company for shared integration code, and

origin

becomes ambiguous. Rename it from the start:

git remote rename origin bank
git remote add internal [email protected]:fde/connector.git
git fetch internal
git branch -r

According to the

git remote

documentation, rename also updates all remote-tracking branches and related configuration, so no manual edits are needed. After running

git fetch internal

, branches display as

internal/feature-x

, clearly distinguished from

bank/feature-x

.

The Git documentation also offers advice worth remembering: if you pull from one place and push to another, use two separate remotes. At a client site, this rule prevents the worst outcome: pushing the client's code to your own company's server, or vice versa. Always spell out the remote name explicitly on every push (

git push bank feature/x

), and never let Git guess.

In a repository with many branches created for regional offices or sub-clients, clear remote names make the output of

git branch -r

read like a map—you can tell which branch belongs to whom just from the prefix.

Where do passwords live on someone else's machine?

Git doesn't store credentials by default, so every HTTPS push requires re-entering them. The instinctive reaction is to enable the

store

helper, but on a client's machine, that's a mistake. Pro Git is explicit:

store

mode stores credentials in a plaintext file on disk, and they never expire.

On any client laptop or virtual machine—especially shared machines—such a file is a security vulnerability with your name on it. The more sensible choice is the

cache

helper, which keeps credentials in memory and clears them after 15 minutes:

git config --global credential.helper cache

Re-entering credentials after every long break is admittedly a bit annoying, but it's far cheaper than a security investigation. If the client has its own token policy, follow the client's policy.

Before writing code, read the review rules

Back to that locked merge request. On GitLab, clients can enable required approvals: according to the GitLab documentation, a merge request cannot be merged until it has enough approvals from designated people. That's the client's process, not a malfunction.

The question is who needs to approve. GitLab determines reviewers per file through the

CODEOWNERS

file. If a merge request touches both the payments directory and the reporting directory, you'll likely need sign-off from two different groups, and your merge request (MR) has to wait for the slower one.

So before creating a branch, open

CODEOWNERS

and find the lines matching the paths you plan to change. Split your changes so each MR only needs one owning group's approval, and send that group a brief message ahead of time about what you're about to submit. A small MR, sent to the right people, with advance notice, usually moves faster than a big MR that lands in three teams' inboxes at once.

Recurring mistakes

The most common is committing to a client repository with a personal email; the fix is configuring includeIf before writing your first line of code. Next is having all remotes named

origin

, which leads to pushing to the wrong server. Then there's enabling

store

。

The last one is harder to spot: treating the client's review process as an obstacle and trying to work around it. Approvals and CODEOWNERS tell you who is actually responsible for that code—which means they're exactly the people you need to get to know early.

If you're preparing a resume for an FDE role, replace "proficient in Git" with something concrete: "worked on a client's internal GitLab, following required approval and CODEOWNERS processes, managing multiple remotes and per-client identities." Also prepare a short example for interviews about how you split an MR by owning group.

At a client site, the repository isn't yours, but every commit carries your signature. Configuring things correctly from day one is the lowest-cost way to keep that signature trustworthy.
