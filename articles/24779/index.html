Summary

This Japanese article by Shohei Tokumitsu, CEO of DeFactory, explains detailed design (internal design) in web system development: the phase that turns what basic design defines externally into concrete internal specifications, effectively an instruction document for programmers. Using the three-layer architecture (presentation, business logic, data access), it argues that designing business logic and interface logic is detailed design's core role. It describes typical deliverables—activity diagrams, sequence diagrams, IPO charts, and ER diagrams—and offers writing tips: prioritize clarity, unify terminology, have experienced engineers author it, and confirm development policies, languages, libraries, and coding rules beforehand.

Key points

  • Detailed design defines how basic design decisions are actually implemented internally.
  • Within three-layer architecture, designing business logic is its central task.
  • Typical outputs: activity diagrams, sequence diagrams, IPO charts, ER diagrams.
  • Documents must be clear and consistent, ideally written by experienced engineers.
  • Confirm development policies, languages, libraries, and coding rules before starting.

System development design is broadly divided into two types: basic design and detailed design. Since detailed design is a specialized process, many people may not know exactly what kind of work it involves.

In this article, we explain what the detailed design process involves in Web system development, along with the content created during detailed design and key points for creating it.

In system development, detailed design is the process of deciding how to realistically implement the content defined in the basic design. Since it involves defining the internal specifications of the system, it is also called internal design.

Basic design, on the other hand, is the process of deciding how the system behaves when viewed from the outside—in other words, "what functionality to implement." Because it designs the outward behavior, it is sometimes called external design.

For example, in the basic design of Web system development, the layout of screens is defined. However, basic design alone does not clarify "how to realize the defined layout." That is where detailed design comes in: it considers "how to realize that layout" and creates design documents.

In other words, detailed design can be described as the process of creating development instructions for engineers and programmers. Performing detailed design is useful not only for development but also for maintenance and operation after development.

Since detailed design is highly specialized, it can be difficult to understand without knowledge of programming and development. However, knowing what is done in detailed design helps clients understand the overall flow of system development.

What is the significance of creating detailed design? Here we explain the specific roles of detailed design.

A key term for understanding the role of detailed design is the three-tier architecture. Three-tier architecture refers to a system structured into the following three tiers:

1. Presentation tier

2. Business logic tier (application tier)

3. Data access tier

Organizing the system into these three tiers improves overall system performance and streamlines development and maintenance work. The characteristics and functions managed by each tier are as follows.

The presentation tier is the user interface part of the system—the part that end users actually see and operate. It provides information to users and simultaneously obtains information from them.

Taking a Web system as an example, on an EC site, the display of products and clickable elements correspond to the presentation tier.

[Functions managed]: Page display requests, HTML output, input value validation, display of processing results, page transitions, etc.

The business logic tier is the core of the system, responsible for processing the information obtained in the presentation tier.

Business logic refers to programs that reflect the unique flows and rules of the services offered by the system into processing procedures.

Even in Web systems with seemingly similar functionality, such as various EC sites, workflows and methods of processing user information differ depending on the operating company or service.

The main role of the business logic tier is to link these unique rules with the system internals.

[Functions managed]: Retrieving data for page display, business processing of user information, data routing, etc.

The data access tier stores the information processed through the presentation tier and business logic tier.

In the EC site example, products purchased by users and payment data are managed in the data access tier.

[Functions managed]: Retrieving data for page display, reflecting input values, calling other systems, etc.

Most of the presentation tier and data access tier described above is handled in basic design. However, basic design cannot cover the information processing flows handled by the business logic tier.

A major role of detailed design is to comprehensively design and implement business logic along with interface logic. In three-tier architecture, properly organizing the various common logic and business logic improves the productivity of subsequent development and operation.

In other words, detailed design is the work of organizing functions and logic in advance so that development, maintenance, and operation proceed smoothly.

An activity diagram is a diagram that shows the flow of system processing, branching based on user actions.

The information processing flow is determined by user actions. For example, considering a visitor to an EC site, their actions will first branch depending on whether they log in or register as a user.

If the user registers, you create a flow of "Enter user information" → "Register user" → "Send user information to the database."

On the other hand, if the user logs in, a flow of "Enter information on the login screen" → "Query user information in the database" → "Output authentication NG or authentication OK" is required.

Until this user finally logs out, various flows will occur, such as purchasing products and making payments. In this way, the role of an activity diagram is to clarify the flow of processing based on user actions, from the start (login) to the end (logout) of their activity.

By creating an activity diagram, you can visualize the user actions expected on the system as well as the necessary processing and functions.

A sequence diagram shows an overview of the program and its processing flow along a timeline.

For example, for user registration on an EC site, you would program a flow like the following.

"Top screen: Enter user information" → "Customer registration control: Register" → "Customer registration screen: Forward to the user registration screen"

Creating a sequence diagram not only helps ensure smooth development, but also allows you to organize what processing is executed and in what order. Since sequence diagrams are easy to understand visually, a benefit is that they can also be used when aligning on the flow of system processing with the client.

IPO is a diagram that describes business logic and system functions in three stages: Input, Process, and Output. By creating an IPO, you can grasp how input data is processed, and the process up to creating output data becomes clear.

For example, representing the completion of a product purchase on an EC site as an IPO looks like the following.

"Input: Product purchase" → "Process: Payment method authentication" → "Output: Order received"

However, in practice, IPOs for a single action are often used in the design of batch processing, which performs multiple processes together.

To smoothly manage enormous amounts of data, data is structured along a series of flows in system development. Database design is a concrete definition of what information is organized and in what structure.

In database design, a commonly used design diagram is the "ER diagram: Entity Relationship Diagram."

In an ER diagram, entities (things) and relationships are combined to represent the flow of processing. For example, the process of "a user purchases a product" on an EC site is represented by the entities "user" and "product" and the relationship "purchases."

In this way, actively using ER diagrams makes it easier to grasp the structure of complex systems.

ER diagrams are basically created step by step during the upstream processes. Although ER diagrams are also created in basic design, at this point they are not yet designed for a specific database.

In detailed design, the design is extended to deeper levels so that it ties to a concrete database, and only then is the ER diagram complete.

Finally, we will explain the points to be careful about when performing detailed design.

Detailed design is work performed by programmers and engineers to ensure smooth development. Since programming is done while referring to the detailed design, there is no point if the documentation content is hard to understand.

Also, the detailed design may be reviewed during maintenance and operation. Being able to understand at a glance "what processing is being done" by looking at the detailed design also helps with maintenance and operation work.

• Use bullet points

• Use diagrams and tables

• Keep sentences as short as possible

• Avoid difficult words and coined terms

And so on. When creating detailed design, it is important to be thoroughly conscious of clarity while remaining technical.

System development terminology includes many terms prone to inconsistent notation, such as "server/Server" and "Web/WEB/web." Inconsistent notation makes documents hard to read and hinders smooth understanding, so it is important to eliminate it as much as possible.

Also be mindful of consistent tone (polite style vs. plain style) and consistent subject and point of view.

Detailed design is, so to speak, an instruction document for programmers and engineers. In other words, to convey accurate instructions to developers, including technical matters, the creator must themselves be a programmer or engineer.

Since the documentation content itself is technical, appropriate knowledge is naturally required. However, as mentioned above, if the detailed design is created with hard-to-understand wording or structure, it may hinder subsequent development, maintenance, and operation.

Therefore, it is desirable that detailed design be created by someone who can effectively summarize key points and produce materials that are objectively easy to understand.

When performing detailed design, it is important to reconfirm the development policy and development-related rules.

If the development policy has not been properly shared, there is a possibility that detailed design will proceed based on assumptions different from what the client ordered.

Also, do not forget to specify the libraries and programming languages to be used and to create coding standards documents.

In system development, development is not done entirely from scratch; various libraries are used. By deciding in advance which libraries and programming languages to use and under what coding rules the design will proceed, development can proceed efficiently and smoothly.

Detailed design is the process of deciding how to realistically implement what was defined in basic design. Building out the detailed design thoroughly also leads to improved productivity in development, maintenance work, and more.

Although the content is technical, if the ordering party also understands the content of the detailed design documentation, communication with the development company will go smoothly. Materials in which processing is visualized, such as sequence diagrams, can also be used to share processing flows.

If you have any questions along the way, do not hesitate to confirm with the development company.
