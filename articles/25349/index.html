How to Use the Batch API: Cut LLM Costs in Half

Original title: Batch API 批处理怎么用：大模型成本减半

FDE Times · 2026-10-26 · 5 min read

Summary

This guide explains when and how to use Batch APIs from Anthropic, OpenAI, and Google Gemini, all of which offer 50% discounts for asynchronous workloads where no user is waiting. Using a 300,000-contract labeling project as an example, the author covers splitting batches against both request-count and size limits, using customer primary keys as custom_id, and downloading results within Anthropic's 29-day window into customer-owned storage. Key warnings: never promise the 24-hour limit as an SLA, plan for expired batches, and combine prompt caching with batching to cut token costs by nearly 95%.

Key points

  • All three vendors discount batch processing 50% in exchange for up to 24-hour waits.
  • The 24-hour window is a cap, not a promise; deadlines should allow a rerun.
  • Batch splitting must respect both request limits and size caps (256 MB Anthropic, 200 MB OpenAI).
  • Results expire after 29 days on Anthropic and must be saved to customer storage immediately.
  • Prompt caching plus batching cut Claude 3.5 Sonnet token costs by nearly 95%.

All three major model providers offer batch processing at a 50% discount; the challenge lies in splitting batches properly and saving the results within 29 days.

Key Takeaways

  • Anthropic, OpenAI, and Google Gemini all offer batch processing at a 50% discount. At Anthropic and OpenAI, the trade-off is accepting a wait of up to 24 hours, though most Anthropic batches finish in under an hour.
  • 24 hours is a cap, not a promise: batches that haven't completed by then expire. So customer deadlines must leave room for a second run.
  • Anthropic's batch results can only be downloaded within 29 days, so data pipelines must save the results into the customer's own storage as soon as possible.

On Monday, the customer sends a storage bucket link containing 300,000 old contracts. They want every contract tagged by clause type and risk before the Friday board meeting. Last week's demo went smoothly because each call sent only one document to the model.

Making 300,000 calls that way would hit rate limits, compete for quota with the chat features the customer's users rely on daily, and cost twice as much as necessary. Providers launched the Batch API precisely for this kind of work. A qualified Forward Deployed Engineer (FDE) needs to know when to use it—and, just as importantly, when not to.

Trading time for half the price

Anthropic's Message Batches API is designed for asynchronous batch processing. Every token in a batch, whether input or output, is billed at 50% of the standard API price. According to the company's documentation, most batches finish in under an hour.

This discount isn't unique to Anthropic. Simon Willison points out that OpenAI and Google Gemini also offer batch processing at half price. OpenAI's Batch API completes within 24 hours, and 24 hours is the only completion window it accepts. The price of half-cost results is giving up the right to get them immediately.

So the decisive question isn't technical—it's a product question: is anyone waiting for the results? Anthropic lists jobs suited to batch processing including running evals, content moderation, data analysis, and bulk content generation. What they have in common: no user is staring at a chat box.

Use batch processing for

  • Tagging backlogged documents
  • Re-running eval sets after every prompt change
  • Moderating content users have already published
  • Compiling reports that just need to be done by the next morning

Must run in real time

  • Chatbots and assistants answering users
  • Agents that need to make decisions in real-time workflows
  • Transaction checks that must block instantly
  • Any interface where someone has clicked a button and is waiting

A product manager at Quora once summarized the experience like this: send off a batch of tasks and download the results within 24 hours—very convenient. But "convenient" only holds if the customer's process naturally operates on a timescale of days, not seconds.

24 hours is a cap—don't turn it into a promise to the customer

Many engineers get this wrong. At launch on October 8, 2024, Anthropic said each batch would be processed within 24 hours. The current documentation is more explicit: batches not processed within 24 hours expire, and during demand spikes more batches may expire.

If you promise the customer "results within 24 hours," you're promising something the vendor never promised you. The rule to follow: the customer's deadline must accommodate at least two windows—one for the main run, one for re-running expired or failed parts.

With data ready Monday and a Friday deadline, there's plenty of time. If the data arrives Thursday night, the urgent parts must run in real time.

Example: splitting 300,000 contracts

Anthropic's limits are 100,000 requests or 256 MB per batch, whichever comes first. At first glance, 300,000 documents need only 3 batches. But contracts are often long, and the size limit will bind before the request-count limit does.

Suppose each request (contract text plus prompt) averages 3 KB; then 100,000 requests is about 300 MB, exceeding the 256 MB cap. 256 MB divided by 3 KB is roughly 85,000 requests.

Leaving a safety margin for unusually long contracts, set each batch to 80,000 requests, for a total of 4 batches. If the customer uses OpenAI, the limits are 50,000 requests and a 200 MB input file, so the numbers must be recalculated from scratch.

The second thing to design is

custom_id

. It's the only clue for mapping results back to the correct document, so use the primary key from the customer's system, not a loop counter. The code below sketches the whole flow using Anthropic's Python SDK:

import anthropic

client = anthropic.Anthropic()

# 所有合同共用的系统提示词，因此缓存 1 小时
SYSTEM = [{
    "type": "text",
    "text": LABELING_GUIDE,  # 较长的共享标签分类体系
    "cache_control": {"type": "ephemeral", "ttl": "1h"},
}]

def to_request(doc):
    return {
        "custom_id": doc.contract_id,  # 客户系统的主键
        "params": {
            "model": MODEL,
            "max_tokens": 1024,
            "system": SYSTEM,
            "messages": [{"role": "user", "content": doc.text}],
        },
    }

batch = client.messages.batches.create(
    requests=[to_request(d) for d in chunk]  # 每块最多 80,000 份文档
)

# 当 processing_status == "ended" 时：
for entry in client.messages.batches.results(batch.id):
    if entry.result.type == "succeeded":
        save_to_customer_store(entry.custom_id, entry.result.message)
    else:  # "errored" 或 "expired"
        queue_for_retry(entry.custom_id, entry.result.type)
cache_control

This line isn't decoration. A batch can run longer than 5 minutes, so Anthropic recommends a 1-hour cache TTL to get more cache hits on shared context (such as a long tagging guide).

On October 15, 2024, Willison calculated that combining prompt caching with batch processing can cut Claude 3.5 Sonnet's token cost by nearly 95%. Actual savings depend on the share of shared prompt in each request, but the direction is clear.

Results don't stay there forever

Anthropic's batch results can only be downloaded within 29 days of creation. After that, the batch is still visible, but the results can no longer be retrieved. If the customer might come back three months later asking "how was this contract tagged?", that's a gap.

Therefore,

save_to_customer_store

this step must run immediately after the batch finishes, writing to storage the customer owns, while also logging the prompt version and model used.

If the customer also has real-time features running, OpenAI has another advantage worth noting: batch rate limits are independent of per-model rate limits, so large jobs won't eat into the quota for real-time traffic.

Rollout process and common mistakes

When facing a large corpus, the order to follow: confirm no one needs real-time results; measure average request size; first run a small pilot batch with about 1,000 documents; split the rest according to the two limits; before submitting large batches, build the retry loop for failed and expired requests.

The pilot batch gives you real numbers on duration and error rates, so when reporting to the customer you have figures to cite instead of guesses.

The most common mistake is treating 24 hours as an SLA. The second is splitting batches only by request count, only to discover at submission that the size limit is exceeded. The third is harder to spot: the

custom_id

used can't be mapped back to the customer's system, so when 300,000 results come back, there's no way to tell which row belongs to which contract.

The remaining two are operational issues. One is leaving results on the vendor's platform and forgetting to download them before day 29. The other is failing to handle

errored

and

expired

cases, so the customer's report silently misses a few percentage points of data and nobody notices.

How to put it on your resume

When reading FDE job descriptions, watch for mentions of processing large volumes of documents, running evals regularly, or controlling model costs. If so, batch processing experience is worth bringing to the interview.

A single resume line like "moved the tagging data pipeline for N documents from real-time to batch processing, halving costs, with retries, and results stored in customer-owned storage" shows recruiters you understand cost, reliability, and data ownership.

Customers rarely ask you about the Batch API directly. They ask why this month's bill is so high, or why the chatbot got slow on the exact day a big job was running. The FDE who can spot early on that half the workload doesn't need instant responses is usually also the one who can answer both of those questions.
