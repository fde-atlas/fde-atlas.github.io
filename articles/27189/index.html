Capability Model (8 Dimensions) · OpenFDE

Original title: 能力模型（8 维）

OpenFDE · 2026-10-16 · 2 min read

Summary

OpenFDE proposes an 8-dimension competency model for evaluating forward deployed engineers, organized under a 4C framework: Customer site, Code, Calibration, and feedback loop. Drawing on job requirements from OpenAI, Palantir, and Google, the article argues that what is scarce is not excellence in any single dimension but the combination—taking ambiguous customer needs to production, validating with real metrics, and productizing field learnings. It suggests using the model as a radar chart for self-assessment and for composing complementary field teams.

Key points

  • Eight dimensions map to 4C: site, code, calibration, feedback loop.
  • FDEs must first be strong end-to-end engineers across full stacks.
  • Enterprise integration, evals, and need discovery often matter more than models.
  • Judgment on which requests to productize or reject separates FDEs from outsourcing.
  • The radar chart supports self-assessment and complementary team building.

Full text

Judging whether someone is a qualified FDE can't be based solely on "whether they can write code." Breaking down and synthesizing the requirements from various job postings yields 8 capability dimensions—ranging from foundational engineering all the way to product judgment. What's truly scarce has never been any single point capability, but rather the ability to combine them and push vague requirements to production at the customer site.

Eight Dimensions

These 8 dimensions are essentially an expansion of 4C (Context · Code · Calibration · Feedback): Context = dimensions 5, 6; Code = dimensions 1, 2, 3; Calibration = dimension 4; Feedback = dimension 7; and dimension 8 (end-to-end delivery) is the central axis that ties all four under a single accountable owner.

An FDE must first and foremost be a strong engineer, capable of independently building end-to-end systems: proficiency in at least one of Python / TypeScript / Java / C++, plus fundamentals in backend APIs, databases, queues, caching, frontend / internal tools, system design, debugging, CI/CD, logging and monitoring, and permissions and security. OpenAI requires the ability to write and review production frontend and backend code, while Palantir's coding requirements cover Python, Java, C++, TypeScript, and JavaScript. OpenAI Careers↗

Prompt / system instruction design, function calling, RAG (chunking / embedding / retrieval / rerank / metadata filter), Agents (planner / executor / tools / memory / state / human approval), workflow orchestration, fine-tuning fundamentals, model selection and fallback, multi-model routing, and cost and latency optimization, failure mode analysis.

The biggest challenge in enterprise AI is often not the model but integration: CRM (Salesforce / HubSpot), ERP (SAP / Oracle), ITSM (ServiceNow / Jira), data warehouses (Snowflake / BigQuery / Databricks), document systems, communication systems, identity systems (Okta / Azure AD / SAML / OAuth), RBAC / ABAC / row-level permissions, and SOC 2 / HIPAA / GDPR compliance. Google explicitly includes "the connective tissue that connects AI products with legacy data, business logic, and security boundaries" in its FDE responsibilities. Google Careers↗

Once an AI system is live, it must be continuously measured: accuracy, coverage, hallucination rate, refusal rate, unauthorized action rate, tool call success rate, human takeover rate, latency, tokens, cost-per-request, user feedback, and business KPIs. OpenAI defines eval-driven feedback as a key input that shapes both product and model roadmaps.

The ability to see through "what features the customer wants" to the real business goals, process bottlenecks, user roles, data landscape, cost of failure, and success metrics. This ensures the project doesn't go off track from the very beginning, and it's also the starting point for demo-driven product exploration.

The ability to converse with frontline users, business owners, customer engineers, IT / security / compliance, data teams, executives, sales, PMs, and research and core engineering teams simultaneously—and to drive delivery and win executive buy-in along the way. Palantir, OpenAI, and Google all list communication across technical and non-technical stakeholders as a hard requirement.

Not "build whatever the customer asks for," but the judgment to determine: which requests are customer-specific, which are industry-wide commonalities, which should become product capabilities, which should be handed to SIs, which should be declined, which model issues should be fed back to research, and which platform gaps would hinder scaling. This is the dividing line between an FDE and outsourcing.

The ability to break vague goals into clear tasks, make tradeoffs among scope, speed, and quality, and push all the way to launch in a fast-moving environment with incomplete information. OpenAI explicitly requires FDEs to deliver and make tradeoffs in an ambiguous environment.

Plenty of people can write code alone, and plenty can do customer communication alone. But very few can, at the customer site, push an AI system from vague requirements all the way to production, validate with real metrics that it's genuinely useful, and productize the field experience. What's scarce isn't the peak of any single dimension, but the combination of all 8 dimensions—and the judgment to make tradeoffs among them.

How to Use This Capability Radar

Think of the 8 dimensions as a radar chart with two uses:

  • Self-assessment and gap-filling: Most engineers are stronger on dimensions 1 and 2, and weaker on dimensions 3, 5, 6, and 7—which are precisely where FDEs differentiate themselves.
  • Complementary team building: A field team doesn't require one person to max out all 8 dimensions; instead, a combination of FDE, applied AI engineer, deployment strategist, and solutions architect covers the full chart.
