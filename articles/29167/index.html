Expectation-Management-Script

Original title: Expectation-Management-Script

FDE中国社区 · 2026-07-12 · 4 min read

Summary

This is a reusable skill package from the FDE China community addressing a common failure mode: business stakeholders judge AI by traditional software standards, so a single error can kill an entire project. It provides an expectation-management script built on a five-part structure: acknowledge limitations, explain causes, present metrics, propose human-review strategy, and give an iteration plan. The document specifies inputs/outputs, a six-step execution process, common pitfalls (overpromising accuracy, avoiding hallucination topics), stage gates from PoC to production, role divisions among FDE, AIBP, business owners and IT/security, plus five scenarios and an FAQ.

Key points

  • Targets the problem of clients rejecting AI after a single error.
  • Script structure: admit limits, explain causes, give metrics, human review, iteration plan.
  • Covers five scenarios: PoC kickoff, post-demo, disputes, pre-launch, renewal talks.
  • Warns against overpromising accuracy and hiding failure samples.
  • Defines FDE/AIBP collaboration with stage gates and written sign-offs.

Problem Definition

The business side expects AI to behave like traditional software; a single error invalidates all value, and the project dies.

Methodology Framework

Core message: probabilistic nature, hallucinations, error rates, human review strategy, iteration path, go-live boundaries. Script structure: acknowledge limitations → explain why → give metrics → give human review → give an iteration plan.

FAQ

Q1: When executing the Expectation-Management-Script, how do you avoid "overpromising accuracy"?

A: Follow the README methodology step by step and showcase interim deliverables in weekly demos; if PoC materials are incomplete, first produce a "to-be-validated list" before proceeding.

Q2: What additional constraints apply in private deployment, Xinchuang (domestic innovation), or MLPS (classified protection) environments?

A: Specify the deployment model in the prompt constraints section; when data cannot leave the domain, domestic components, or audit logs are involved, reference Private-Deployment-Gateway and RBAC-Audit accordingly.

Q3: What if the division of responsibilities with AIBP is unclear?

A: Return to the AIBP-Collaboration-Playbook to update the RACI; AIBP is responsible for Ground Truth and business acceptance, while the FDE is responsible for deliverable technical assets.

Q4: After the PoC passes, how do we transition to Beta/production?

A: Mark the next-stage Skill in the deliverables (e.g., RAG-Evaluation→Private-Deployment-Gateway→FDE-Adoption-Growth), and trigger the launch gate via the checklist.
