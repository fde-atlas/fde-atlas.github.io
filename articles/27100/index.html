90-Day Learning Roadmap · OpenFDE

Original title: 90 天学习路线

前沿部署工程师社区 · 2026-10-16 · 4 min read

Summary

OpenFDE community publishes a roughly 90-day, five-stage learning path for becoming a Forward Deployed Engineer. The stages progress from understanding what FDEs are (versus sales engineers, SAs, SWEs, PMs), to building an enterprise RAG prototype, then a production-grade ticket-handling agent, then a simulated customer deployment, and finally productization judgment. The author insists every project add the unglamorous essentials—data integration, permissions, evals, logging, cost, deployment—and walks through a full B2B SaaS customer-support assistant template covering discovery, MVP scoping, architecture, metrics across business, system quality and adoption, and turning one-off projects into reusable connectors, templates and industry solutions.

Key points

  • Five stages: concepts, RAG, agent workflow, simulated deployment, productization.
  • Each stage has concrete deliverables like a permission-aware knowledge assistant.
  • Projects must include data, permissions, evals, logs, cost and deployment.
  • A B2B SaaS support assistant template shows discovery through product reuse.
  • Metrics should cover business outcomes, system quality and user adoption.

Full text

Treat FDE as a craft that can be systematically trained: in about 90 days, go from "understanding the concepts" all the way to "independently completing a simulated customer deployment and productizing it." The five stages below build on each other progressively, and each stage has a clear goal, a hands-on project, and verifiable deliverables.

This roadmap deliberately does not start with "grinding algorithm problems"; instead, it is organized around the FDE's real skill stack: first clarify the concepts so you aren't misled by job titles, then build up AI application engineering, then level up to agents and workflows, and finally tie all the skills together with a simulated deployment while training the scarcest skill of all—productization judgment. Practicing alongside the tech stack overview works best.

Five-Stage Progression

Goal: Understand what an FDE actually is, avoid being misled by titles, and be able to distinguish the role from Sales Engineer / SA / SWE / PM.

Practice: Read closely the Palantir Dev vs Delta comparison, FDE job descriptions from Palantir / OpenAI / Google Cloud, and a16z's analysis of Palantirization. Dev vs Delta↗

Deliverables: A one-page FDE definition; an FDE vs SA vs SWE vs PM comparison table; a list of 10 key FDE competencies; a list of 5 risks in the FDE model.

Goal: Be able to independently build an enterprise-grade RAG prototype, not a toy chatbot.

Practice: Build a permission-aware enterprise knowledge assistant.

Deliverables: A complete application covering document upload and parsing, chunking, embedding, vector retrieval, reranking, metadata-based permission filtering, citation traceability, user feedback, an eval set, latency / cost logging, a simple frontend, and Docker deployment. It is much closer to real FDE work than "building a chatbot."

Goal: Upgrade from a "Q&A system" to an "executable system"—one that can call tools, maintain state, handle failures, and request human approval.

Practice: Build an agent that automatically handles customer support tickets.

Deliverables: Include ticket classification, knowledge retrieval, tool calling, draft replies, human approval, a state machine, error fallback, a trace viewer, eval cases, and cost and latency monitoring. This stage directly maps to the production-grade agentic workflow capabilities emphasized in job postings at Google, ByteDance, OpenAI, and others. Google FDE JD↗

Goal: Practice discovery, scoping, and go-live thinking—this is where FDEs differ most from ordinary engineers.

Practice: Pick an industry scenario (bank relationship manager assistant / healthcare prior authorization assistant / manufacturing equipment repair assistant / SaaS support ticket assistant / legal contract review assistant) and treat it as a real customer engagement.

Deliverables: A customer interview guide, a diagram of the current process, pain points and success metrics, MVP scope, technical architecture, a risk list, an eval plan, a rollout plan, and productization opportunities—a complete deployment delivery package.

Goal: Don't just finish the project—turn it into compounding product capability. This step is the real dividing line between an FDE and a "senior outsourced engineer."

Practice: Review the simulated deployment from the previous stages and answer the productization questions one by one.

Deliverables: Which modules are reusable? Which connectors should be productized? Which evals should be standardized? Which prompt / workflow templates can be replicated across industries? Which requirements should not be built? Which capabilities should go on the roadmap? How do you expand from one customer to an entire industry?

At every stage, don't stop your project at the demo—force yourself to add the six "uncool but make-or-break" things: data ingestion, permissions, evals, logging, cost, and deployment—these are what FDEs actually solve in the field.

A Complete Case Template: B2B SaaS Support Assistant

Stages 4 and 5 need a "fake customer" to practice on. You can apply the following template directly: a B2B SaaS company wants to use AI to improve support efficiency. Note that an FDE's first reaction is not to start building a chatbot, but to keep asking questions.

The customer says: "We want to build an AI support assistant so our agents can answer questions faster."

The FDE should ask: How many tickets do you handle per day? What's the average handling time? Which questions are most common and most error-prone? Where do the knowledge base and ticket data live? What are the boundaries of agent permissions? Which replies must be human-reviewed? What are the risks of wrong answers? Is the success metric really lower AHT, higher CSAT, or lower first response time?

The first version does not auto-reply to customers directly; instead, it is an internal assistant for support agents: it automatically retrieves relevant knowledge based on the ticket, generates suggested replies, provides source citations, and flags confidence levels; the agent edits and sends the reply, and feedback and final adoption rates are collected. This validates value quickly while keeping the risk of errors behind a human gate.

The frontend is a support workbench plugin; the backend is a ticket context service; the data layer connects to the knowledge base, historical tickets, and product docs; retrieval uses hybrid search + rerank; permissions filter customer data by agent role; the model generates reply drafts; evals use historical ticket replay; the observability layer tracks latency, cost, adoption rate, edit distance, and user feedback; rollout starts with a pilot of 10 agents, then expands to a team.

The metrics layer must cover three categories at once—business, technical, and adoption—which is what sets an FDE apart from pure delivery:

DimensionMetrics to watch
Business outcomesAHT (average handling time), CSAT, first response time
System qualityRetrieval hit rate, hallucination rate, citation accuracy, latency, cost-per-request
User adoptionDraft acceptance rate, human edit distance, pilot expansion speed, feedback scores

When multiple customers show similar needs, a "one-off project" should be upgraded into "product compounding":

Standard connectors for support systems like Zendesk / Intercom / Salesforce Service Cloud, so the next customer's onboarding changes from "rewriting" to "configuring."

Distill the role-based customer data filtering retrieval logic into a reusable template, reusing the same permission model across customers.

Standardize the eval set and scoring criteria for support reply quality, so the golden set framework can be reused when new customers go live.

Package confidence flagging + human gate + ticket agent workflow + monitoring dashboard into an industry "support assistant" solution.

This path from "customer pain point → MVP → architecture → metrics → productization" is a complete microcosm of how an FDE moves from project delivery to product compounding. Once you've practiced it, go read interview prep, and you'll find that discovery cases and system design questions can almost all be derived from this template.
