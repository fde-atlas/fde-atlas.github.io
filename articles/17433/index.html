Vector Database

Original title: 向量数据库：Vector Database

Full text

This card pulls vector databases back from selection hype to engineering fundamentals. Core breakdown: a vector database stores embeddings, computes similarity, and returns results by nearest neighbors—it is the storage component of the retrieval step in a RAG pipeline, not the whole solution. Chunking strategy, embedding model, query rewriting, and reranking all affect the final outcome at least as much as the database choice itself. The two most common misuses: first, treating picking the "right" database as the key to RAG success and migrating repeatedly for it, while retrieval quality stays flat; second, relying solely on pure vector retrieval and ignoring metadata filtering and hybrid keyword retrieval—enterprise scenarios often require exact matching of IDs, model numbers, and clause numbers, which pure semantic nearest-neighbor search is precisely worst at. Incremental judgment: vector capabilities are rapidly becoming built-in features of general-purpose databases, and the incremental value of specialized engines lies in extreme scale and operational characteristics. The FDE's yardstick for selection is not benchmark scores, but deployment constraints in the customer's environment, whether the existing permission system can be integrated, and the operational burden under private deployment. Action item: add a set of evals with exact keyword matching for the retrieval step, and see how much a pure vector solution misses. — FDEChina Editorial Team · Practitioner's Perspective

Definition

A vector database is a specialized database that takes high-dimensional vector embeddings as its primary data form and supports similarity search and nearest-neighbor queries; its core capability is returning semantically similar content ranked by distance.

Expansion

In a RAG pipeline, it is only the storage and computation component of the retrieval step: document chunking, embedding model selection, query rewriting, permission filtering, and reranking—each of these affects the final outcome at least as much as the database choice itself. One common misuse is treating "picking the right vector database" as the key to success and migrating repeatedly for it, while retrieval quality stays flat; another is relying solely on pure vector retrieval and ignoring metadata filtering and hybrid keyword retrieval—many enterprise queries are exact matches for IDs, product names, and clause numbers, which pure semantic nearest-neighbor search is precisely bad at. Distinguishing it from embeddings: embeddings are a data representation, while a vector database is the storage system that hosts this representation and accelerates retrieval; the former determines the quality of the semantic space, the latter determines retrieval efficiency and operational cost.

For selection, vector capabilities are rapidly becoming built-in features of general-purpose databases, and the incremental value of specialized engines lies in extreme scale and operational characteristics. The FDE's practical yardstick is the deployment constraints of the customer's environment, whether the existing permission system can be integrated, and the operational burden of private deployment.
