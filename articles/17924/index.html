How to Onboard New Hires Through Code Review: A Code Review Guide for FDEs

Original title: 代码评审怎么带新人：FDE 代码评审指南

FDE Times · 2026-11-15 · 6 min read

Summary

This guide argues that code review for FDEs serves two purposes: the last quality gate before code touches customer environments, and an ongoing training channel. It recommends labeling every comment as blocking, non-blocking, or nit (following Conventional Comments and Google's review guidelines), explaining the reason behind each comment, targeting code rather than the author, and letting the author choose fixes except where customer risk is high. The success metric is whether new hires need the reviewer less over time. It also covers adjusting comment depth to each person's experience, approving once blocking issues are fixed, and common reviewer mistakes like rewriting code yourself or inflating nits under client pressure.

Key points

  • Review success means new FDEs need you less over time, not more bugs caught.
  • Label comments blocking, non-blocking, or nit so authors know what matters before customer data is touched.
  • Explain problems and reasons; hand fix choices to the author unless customer risk is high.
  • Approve once blocking issues are fixed; push nits to a later cleanup PR.
  • Adjust detail level per person and track blocking-comment counts across PRs.

Mark every comment as blocking or not, state the reason clearly, and leave the fix to the author: customers stay protected, and new hires grow faster.

Key takeaways

  • Reviews have a secondary but important goal: making the author need fewer reviews over time.
  • The three labels—blocking, non-blocking, and nit—let a new FDE see at a glance what must be fixed before the code touches customer data.
  • Explain the problem and the reason, leave the fix to the author's judgment, and approve when the code is clearly better.

Picture this scenario: an FDE three weeks into the job submits their first pull request (PR) that touches real customer data—a script that syncs orders from a customer's API into a data warehouse. You open it and find 14 places you want to comment on. And the customer's pilot is Monday morning.

There are two common shortcuts. One is to rewrite it yourself to save time, which means the next time around the new hire still has to wait on you. The other is to leave 14 comments that all look equally weighty, and the new hire spends two days working from a variable name all the way to a bug that could corrupt customer data, without knowing which ones actually matter.

For a Forward Deployed Engineer (FDE), a review is both the last line of defense before code runs in a customer environment and a training channel that operates every day. How you write your comments therefore directly affects how quickly a new hire can work independently, and it is a visible signal of your ability to develop people.

The right metric: how much they still need you

Google's code review guidelines state a secondary goal explicitly: improving the author's skills so that they need less and less review over time. In other words, a good review isn't just measured by how many bugs you catch, but by whether the number of issues you have to block decreases in the same person's next PR.

This goal aligns with how FDE teams onboard new hires. According to the FDE Academy's description of the first 90 days, early work is deliberately scoped so that new hires make mistakes at levels where risk is still contained, rather than on flagship customers.

Managers follow up closely, but not so closely that it suffocates. The milestone is the moment a new hire can take over a real project without close supervision.

Reviews are exactly where this "close but not suffocating" follow-up happens. The tension is: customers need reassurance, while new hires need room to make their own decisions. The solution is to separate the two: which issues must block a merge because they put the customer at risk, and which are merely matters of experience.

One PR, three types of comments

Back to that order-sync script. Suppose its core looks like this:

def sync_orders(since):
    orders = client.get("/orders", params={"since": since}).json()
    for o in orders:
        log.info(f"正在同步 {o}")
        db.execute(
            "INSERT INTO orders VALUES (%s, %s, %s)",
            (o["id"], o["email"], o["total"]),
        )

This code works in a demo. But it contains two bugs that would hurt the customer, one open question, and a few purely cosmetic nits. A good set of comments labels each category clearly:

issue (blocking)：如果任务在网络故障后重跑，这条 INSERT
会写入重复订单，客户看板上的收入会被算两次。我们需要一种
无论运行多少次结果都一样的写入方式。具体用哪种方案由你决定。

issue (blocking)：这行日志打印了整个订单，包括终端客户的邮箱。
日志通常比数据库有更多人和更多系统在读。只记录订单 id 即可。

question (non-blocking)：客户的 API 有分页吗？如果有，
这个函数可能只拉到第一页。

nit：把 `o` 改名为 `order` 更易读。非必须。

The "blocking" and "non-blocking" labels come from Conventional Comments. That convention defines a blocking comment as one that prevents the PR from being accepted until it is resolved.

The convention's author argues that labels save reviewers and authors hours of misunderstanding. The "nit" prefix comes from Google and refers to small issues that should technically be addressed but don't matter much.

Also notice three details in how the comments are written. Every comment targets the code ("this INSERT writes duplicate rows"), not the person ("you forgot to handle reruns"), which matches Google's principle: review the code, never the author.

Every comment includes a one-line reason, because reasons help the author understand why you raised the point and carry the underlying principle into their next PR.

The third detail is subtler. For the duplicate-write bug, you point out the problem and let the author choose the fix; in Google's words, this often teaches the author more.

For the email in the logs, you simply state what to do, because there is only one correct answer and customer data is not a place for experiments. Knowing when to let a new hire figure things out and when to point the way directly is the hardest part of mentoring.

When to hit approve?

Now recount those original 14 comments. Suppose that after triage, 2 are blocking, 3 are questions or suggestions, and 9 are nits. The new hire fixes the 2 blocking issues in an afternoon, answers the 3 questions, and the PR is merged before the weekend; the 9 nits go into a later cleanup PR.

This is exactly Google's recommended approval standard: lean toward approval as long as the change genuinely improves the overall health of the codebase, even if it isn't perfect.

Reviewers aim for continuous improvement, not perfection. For an FDE, this standard carries an extra layer of meaning: the customer is protected exactly where there is risk, and the new hire isn't held up where there isn't.

Same bug, different dosage for different people

The article "Benevolent Code Reviews As a Busy Manager" on Crafting Tech Teams suggests adjusting your wording and level of detail for each person or pair submitting a PR.

For someone in their first week, the comment about duplicate writes might take three sentences plus an example of a task rerun. By week six, the same issue needs only one question: "What happens if it runs twice?"

That brief question is a sign of progress, not laziness. You are transferring judgment from your own head into the new hire's.

The same article stresses that reviews should educate, support, and unblock, and that people don't learn when they feel judged. Dumping a pile of harsh comments on someone right before a customer deadline is the fastest way to make a new hire stop asking questions.

Five steps for the next PR

Step 1: Identify the risk. Before reading the first line of code, ask what this PR touches on the customer side: real data, personal information, or just an internal tool. The answer determines where the blocking threshold sits.

Step 2: Read through before writing. Read the entire PR end to end before commenting, so you can triage by severity rather than commenting in line order.

Step 3: Write every comment from the template. Every comment gets a label, targets the code, and includes a one-line reason; only give the fix directly when customer risk is high.

Step 4: Approve early. Approve as soon as the blocking issues are resolved, and push the nits into a cleanup PR.

Step 5: Track the trend. Record the number of blocking comments per PR for each person you mentor; if that number drops week over week, you're doing it right.

Common reviewer mistakes

The most common mistake is fixing things for them. It's faster today but slows down the whole quarter, because the new hire never walks through the reasoning themselves. The second mistake is labeling none of your comments, so the author treats a variable name and a data-losing bug as equally important.

The third mistake appears under customer pressure: escalating nits to blocking out of anxiety, or conversely, downgrading a security bug to non-blocking to make a demo. The last mistake is using the same level of detail for everyone: being verbose with people who are already solid, and too terse with new hires.

The 90-day milestone described by the FDE Academy—a new hire able to take over a real project without close supervision—is also a résumé-worthy achievement if you're aiming for a senior FDE or FDE lead role. Be specific: who you mentored to that milestone, and which review conventions you introduced to the team to help them get there.

In interviews, showing a real comment you wrote, with labels and reasons, is usually more persuasive than vaguely claiming leadership skills.

Good mentors measure their own success with a somewhat counterintuitive standard: the day a new hire's PR reaches you and you can no longer find anything that needs blocking.
