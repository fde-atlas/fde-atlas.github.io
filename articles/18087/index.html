Postman Student Expert certification discontinued — how should an FDE resume be written?

Original title: Postman Student Expert 停发，FDE 简历怎么写

FDE Times · 2026-11-15 · 4 min read

Key Takeaways

  • Postman has shut down its Student Program, removed the Student Expert course from Postman Academy, and no longer supports the steps to claim the badge.
  • Even while the program was running, the badge only showed that you had completed a self-paced API fundamentals course; it said nothing about your ability to work with customers.
  • On an FDE resume, replace the certificate entry with a project that calls a real API, and include numbers, a README, and a link.

Many technical students once listed the same certificate on their LinkedIn profiles: Postman API Fundamentals Student Expert. On March 23, 2026, a notice on Postman's community Help Hub ended it with a single sentence: the Student Program has been officially discontinued.

At midnight that day, the Student Expert course was removed from Postman Academy. Postman's explanation was that after a UI redesign, the final step (sharing a collection to claim the badge) is no longer supported. Those who completed the course before March 2 can still find the badge in their Parchment backpack.

The signs actually came earlier. A community post in early March showed that before the deadline, badge claiming had already stopped working for Free plan accounts, while paid plan users could still claim it.

If you were planning to use this course to add an "API skills" line to your Forward Deployed Engineer (FDE) job applications, you can drop that plan. The more worthwhile question is: how much did this certificate ever prove, and what should replace it?

One Resume, Two Ways to Write It

Imagine two lines on the same resume. The first: "Postman API Fundamentals Student Expert".

The second is an example: "Built a 12-request collection against a public payments API, handling token expiry, pagination, and 429 errors; the README documents how to run it and 3 failure cases encountered." This line has a link that can be opened and verified, gives the interviewer questions to ask, and holds up no matter which course gets shut down.

Aced (formerly Exponent)'s FDE resume guide sets one rule: every bullet point should end with a number. Scaler likewise pairs a weak statement, "built a data pipeline for client reports," with a strong one that spells out the scope: a Python pipeline that pulls data from three of the client's data sources. The first line above fails both tests.

It is weak because it describes the course, not you. In 2022, Postman renamed the badge to the official title API Fundamentals Student Expert Certification, because the "Student Expert" name left no room for more advanced certifications. The badge was issued through Badgr, and learners had to complete two courses: Intro to APIs and Postman, and the certification course itself.

Postman described the program as a set of self-paced, hands-on courses aimed at building "API literacy" for students of any major. Postman itself promoted the badge as something to put on LinkedIn or a resume. It proves a foundational skill and suits a sophomore, but it says nothing about how you work with customers or deploy for them.

And that is exactly what FDE recruiters want to know. When a customer's API returns results that don't match the documentation, how do you handle it? An introductory badge cannot answer that question.

No FDE Title Yet? Where Does the Evidence Go?

Aced points out that for candidates who have never held an FDE role, the Projects section is especially valuable. Scaler adds that a portfolio (such as a code repository with a solid README) should show what two pages of a resume cannot fit.

So the sensible order is: learn the API fundamentals well, build a project that calls a real API, write a resume entry with numbers, and finally add a README so recruiters can verify it themselves.

If the project has real users, such as a student club or a small shop run by someone you know, state that you communicated with them. Aced recommends explicitly writing out collaboration with users or stakeholders, because that is the other half of FDE work.

How Should the Collection's README Be Written?

Below is a sample template, corresponding to the public payments API in the example above.

# Collection：支付 API（试用版）

如何运行
- 导入 collection 和环境文件
- 在环境中设置 API_TOKEN 变量；不要把 token 写进请求

认证
- 通过请求头 Authorization: Bearer {{API_TOKEN}} 发送 token
- 遇到的情况：运行中途 token 过期返回 401；脚本停止并给出清晰提示

分页
- API 在响应中返回 cursor；下一个请求读取该 cursor
- 检查：最后一页没有 cursor，循环正确停止

429 错误（超出速率限制）
- 读取 Retry-After 请求头，等满时间后重试
- 记录每次运行的重试次数

尚未完成
- 未在超过几页的数据量下测试

The last section is just as important as the previous three. Stating your own limitations gives the interviewer's next question a place to land, and you stay in control of the conversation. Also prepare a specific case: a time an API returned wrong results and how you traced the cause.

Three Things Worth Keeping from the Discontinued Course

First, API fundamentals still come first. Postman's goal of "API literacy" remains correct: reading requests and responses, understanding status codes, headers, and authentication. If this is your weak spot, fix it first before learning Agents or retrieval-augmented generation (RAG).

Second, learn by doing. The course was designed around hands-on exercises, and this approach fits FDE work perfectly. Reading documentation won't teach you what happens when a token expires mid-run; calling it yourself once will.

Third, learning and proving are two different things. Use courses to learn, and your own work to prove. When an FDE job posting mentions phrases like "integrating with customer systems," put your collection link right next to the skills entry.

No one is issuing the Student Expert badge anymore. But the habit of calling APIs, recording what happened, and making it reproducible for others will follow you into every interview.
