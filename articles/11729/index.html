FDE Interviews · 2026-10-18 · 7 min read

Summary

A 105-page, 32-chapter October 2026 guide for forward deployed engineers on integrating agents with tools, remote agents, and commerce. It traces one customer purchase across protocol boundaries—MCP, A2A, AG-UI, UCP, Agentic Commerce Protocol, AP2, x402, MPP—and argues each boundary needs an explicit contract: protocols do not automatically grant authority, so the application must enforce operation identity, approval binding, and recovery. Three fictional incident reviews cover lost responses, cross-tenant callbacks, and changed approvals. A Python/SQLite companion lab includes 56 tests and 8 mutation checks, using only synthetic data with no live payments or production deployment.

An agent system crosses several boundaries: the model proposes a tool call, a host invokes a service, a remote agent owns a task, and a merchant or payment provider owns an external effect. Each boundary needs an explicit contract.

The guide explains the protocols at those boundaries and connects them through one coherent architecture. It separates discovery from trust, interface events from committed work, and a retried message from a safe business retry.

They are contracts at the boundaries of an agent system: model-to-tool calls, access to tools and resources, delegated work between agents, user-interface events, identity, checkout and payment. The guide explains which boundary each protocol serves and how to preserve authority and recovery across them.

The guide covers MCP, A2A, AG-UI, A2UI, MCP Apps, Agent Client Protocol, UCP, Agentic Commerce Protocol, AP2, x402 and MPP. It also explains OAuth/OIDC, token exchange, DPoP, mTLS, workload identity, CIBA, PAR, Verifiable Credentials, HTTP Message Signatures, OpenTelemetry and CloudEvents. WebMCP, ANP, NLWeb, Agent Skills, AGENTS.md, ERC-8004 and provider payment services are placed in their proper context, with draft and product status distinguished from open protocol support.

MCP connects a host or client to capabilities such as tools, resources and prompts. A2A connects independently operated agents through discovery, messages, tasks and artifacts. Neither automatically grants permission to act for a user. The guide follows identity, approval and durable business state across both boundaries.

Both names appear in the ecosystem. Agentic Commerce Protocol defines a commerce boundary; Agent Client Protocol connects coding agents and editors. The earlier Agent Communication Protocol is another distinct project. The guide uses the full names and exact versions to avoid treating them as one protocol.

The companion contains a Python/SQLite contract lab with 56 tests, a loopback HTTP server, a lost-response demo, callback and stream exercises, and 8 worksheets. Its core needs Python 3.10 or later without packages, cloud credentials or model keys. A separate Python 3.12 track uses pinned SDKs for a real local MCP server/client and hash-verified official schemas for MCP and commerce ACP, plus A2A protobuf checks.

The purchase provider and identities are synthetic local fixtures. The optional MCP server performs a public synthetic read. There are no live purchases, wallets or production OAuth flows. Deployment chapters explain the additional identity, infrastructure, credential, payment and operating work required for a customer system.

The October 2026 edition uses 86 primary references and explicit version boundaries, including July MCP and A2A wire 1.0. The exact extracted companion passed 56 tests and detected 8 deliberately broken controls. The optional track passed five local MCP checks and 30 schema/selected-invariant checks. These checks establish their stated scope, not complete conformance across every peer or payment provider.
