Week 8: Making Deterministic Systems Repeatable to Deploy and Roll Back

Original title: 第 8 周：让确定性系统可以重复部署与回滚

FDE 成长手册 · 2026-08-25 · 7 min read

Summary

Week 8 of the FDE handbook argues that deployment evidence must go beyond a passing health endpoint or a working local setup. Using a fictional company, 北辰协作, it shows how a service can appear healthy while tasks fail, and introduces a release manifest covering five parts: input versions, build artifacts, an independent environment, task-level verification, and rollback. A five-day exercise walks through inventorying versions, running CI checks, deploying in a clean environment, injecting a safe failure, and rolling back to a known-good release. Nine acceptance gates close the data and application engineering phase, though the article stresses this proves nothing about production reliability or ROI.

Key points

  • Deployment proof requires task, permission, and idempotency checks, not just HTTP health.
  • A release manifest must record versions, artifacts, schema, config, fixtures, and rollback targets.
  • The 北辰协作 case demonstrates a false success: healthy endpoint, failing tasks.
  • A five-day path covers version inventory, CI, clean-environment deploy, failure injection, and rollback.
  • Nine acceptance gates must pass to close the engineering phase; production reliability remains unproven.

Direct answer: For an FDE, deployment evidence is not "it runs on my machine," nor a health endpoint returning 200. Week 8 must prove: another environment can install the same version, and frontline tasks, server-side permissions, and idempotent results remain correct; when a bad release causes tasks to fail, you can roll back to an exact known version and re-verify user results, the database, and logs. This closes the data and application engineering phase, but does not yet prove production reliability.

Where this week sits in the evidence chain

Heading "Where this week sits in the evidence chain"

Weeks 5–7 turned an approved process slice into ordinary software. This week answers only the final question of the engineering phase: can this slice be repeatedly delivered and recovered by someone else?

已复核的业务决定与一线任务  → 第 7 周确定性系统、权限和任务状态  → 第 8 周可重复构建、独立部署、任务检查和回滚  → 第 9 周才允许冻结基线并治理 RAG 语料

If your own case has already decided to stop engineering exploration, keep that correct conclusion; this week you can use the fictional Beichen Collaboration case to practice delivery skills, but you must not repackage the original case as a launch requirement.

The Beichen Collaboration case: health endpoint fine, tasks wrong

Heading "The Beichen Collaboration case: health endpoint fine, tasks wrong"

The company, versions, tasks, and results below are all teaching simulation material.

By the end of Week 7, Beichen's deterministic workbench could complete this path:

普通客服打开计费任务  → 系统只返回当前角色可见、当前有效的政策候选  → 客服核对来源、生效日期和地区  → 客服确认或升级  → 数据库状态、界面结果和日志使用同一 correlation_id 对账

What the business owner must decide this week is not "whether to go to production," but:

Should this deterministic baseline be allowed into subsequent read-only RAG experiments, while retaining the ability to fall back to the ordinary software process at any time?

The conditions that frontline users cannot sacrifice remain: no displaying content the user is not authorized to see, no treating expired policies as current authority, and preserving a manual escalation path on failure.

The minimal mental model: a release is a verifiable state change

Heading "The minimal mental model: a release is a verifiable state change"

Break a release into five parts that must all correspond to each other:

精确输入版本  → 可重复构建物  → 独立环境  → 一线任务级验证  → 精确回滚目标与复验
PartWhat you must recordUnacceptable substitutes
Input versionCode, configuration, database schema, synthetic fixtures"latest code"
Build artifactThe immutable identifier or digest actually produced by the build toolAn unrecorded directory on your local machine
Independent environmentEnvironment name, dependencies, identity, and configuration sourceA machine the author already tuned
Task verificationNormal, unauthorized, duplicate requests, and business stateOnly /health or a homepage screenshot
RollbackThe exact version to return to and data compatibility conditionsTemporarily patching code until the page looks right

Decision rule: If you cannot state "which code, which configuration, and which schema state to roll back to," you do not yet have a rollback plan—only a wish to fix things.

Full example: detecting a false success and rolling back

Heading "Full example: detecting a false success and rolling back"

1. Freeze four task checks before release

Heading "1. Freeze four task checks before release"

CheckInputExpected visible resultAdditional state to verify
Normal queryRegular support agent + current billing taskShows only allowed and valid regular policiesReturned source version and correlation_id
UnauthorizedRegular support agent + supervisor-only taskSafe refusal or escalation, no leaking content or existenceNo unauthorized read results in the database
Duplicate confirmationSame task, same idempotency key submitted twiceBoth responses point to the same business resultOnly one effective state change
Problematic sourceTask references an expired or conflicting policyNo seemingly-certain confirmation is formedState is refused, pending review, or escalated

Health checks still have value: they show whether the process and required dependencies have started. But they cannot replace these four task checks.

2. Deploy a known-good version

Heading "2. Deploy a known-good version"

Use the package management, container, or process approach your existing application already uses; do not switch tech stacks for this lesson. Write the real install, migration, startup, and verification steps into

deploy/README.md

and execute them in a fresh directory, a temporary container, a virtual machine, or an approved isolated environment.

The expected evidence should form this chain:

release_id  → build_id  → environment  → smoke_case_id  → correlation_id  → response + database state + log event

3. Inject a safe failure

Heading "3. Inject a safe failure"

In the synthetic environment, switch the policy fixture from

northstar-task-fixture-v2

to the expired-version state used in the course example. Do not create failures in a real customer environment, and do not use irreversible migrations as practice material.

At this point you will see:

进程健康：通过数据库连接：通过任务冒烟：失败原因：普通客服任务拿到了已过期的政策候选

This proves that "the service is alive" and "the task is correct" are two different judgments.

4. Roll back and re-prove

Heading "4. Roll back and re-prove"

Return to the

previous_known_good_release

in the checklist, and restore the corresponding configuration. If the database schema cannot be safely read by the old version, stop the drill immediately and revise the migration strategy first; do not force a database rollback.

An acceptable

rollback-drill-v1.md

must state at least:

# 北辰回滚演练 v1（教学模拟）
- 触发信号：任务级 smoke 发现过期政策进入普通客服候选- 健康接口：仍为成功，因此没有作为唯一判断- 失败版本：northstar-teaching-w08-rc1 + northstar-config-bad-date- 回滚目标：northstar-teaching-w08-r0 + northstar-config-v3- schema 判断：006 对回滚目标向后兼容- 回滚后复验：正常、无权限、重复确认、过期政策四条均按预期- 业务状态核对：重复确认仍只有一条有效状态变化- 日志核对：同一 smoke_case_id 可找到失败与恢复事件- 能证明：教学环境中可发现这类失败并退回已知版本- 不能证明：真实生产可用性、所有迁移可逆、真实用户采用或 ROI

Acceptance gate

Heading "Acceptance gate"

This week, the data and application engineering phase closes only if all of the following pass:

  • An environment independent of the author's machine can deploy the exact version;
  • The release checklist records code, build artifacts, schema, configuration, fixtures, and the upstream Brief version;
  • The task smoke checks user results, database state, and logs, not just HTTP;
  • No-permission and duplicate-request behavior has not regressed from Week 7;
  • At least one controlled failure and rollback has been completed, with a clear explanation of why rollback was chosen;
  • Schema and data compatibility were verified before rollback, and "wiping the database and starting over" was not treated as recovery;
  • Ordinary logs contain no secrets, restricted content, or identifiable customer data;
  • A third party or a fresh directory can re-verify the main path by following the instructions;
  • The phase exit record distinguishes between what has been proven, what has not been proven, and new evidence that would reopen a decision.

Common Failures and Recovery

Title "Common Failures and Recovery"

FailureDiagnostic signalRecovery action
Writing only "ran the deployment command"The reader doesn't know the dependencies, configuration, migrations, or expected outputWrite out the input state, the result of each step, and the task re-verification in full
Works locally, fails in an independent environmentRelies on local caches, implicit files, or manually prepared dataRebuild from an empty environment, with all dependencies in the manifest
Declaring success once the health endpoint is fineFrontline tasks, permissions, or data versions were never checkedAdd a task-level smoke and save evidence of business state
Rolling back code but not configurationThe old application still reads the wrong policy versionInclude a configuration summary and recovery order in the manifest
Using an irreversible migration for a drillThe old version cannot read the existing dataStop the rollback; first design a backward-compatible migration or recovery plan
CI and the deployment environment use different fixturesThe same test name yields different resultsPin the fixture version or checksum
Treating a single deployment as production reliabilityNo real traffic, on-call duty, failure windows, or statistical denominatorScale the conclusion back to "one repeatable drill in a teaching environment"

Independent Migration: Supply Chain Anomaly Slice

Title "Independent Migration: Supply Chain Anomaly Slice"

Change the scenario to "a planner confirms an ETA anomaly." Only change the region configuration and role, keeping the same deployment mechanism.

Your task:

  • Write a task-level smoke: a normal planner can see the allowed current source;
  • Write a no-permission smoke: an outsourced role cannot see internal carrier notes;
  • Design a security misconfiguration where the health endpoint still works but the task fails;
  • Decide whether that failure requires a rollback, disabling a feature, or falling back to a manual process;
  • State which business outcomes still cannot be proven after the migration.

View the answer checkpoints

  • Merely changing "customer service" to "planner" is not a migration; the permission roles, sources, anomaly states, and cost of errors must also change.
  • A health endpoint that works while the carrier source is stale is a valid example of a task-level failure.
  • An unavailable external dependency does not necessarily require rolling back the application; if the current version introduced no regression, a manual path or a kill switch may be more appropriate.
  • A single deployment cannot prove forecast accuracy, adoption rate, or delay reduction.

Explaining the Same Evidence to Three Audiences

Title "Explaining the Same Evidence to Three Audiences"

  • Boss version: What was reduced this week is delivery risk that later experiments cannot recover; nothing has been proven about whether RAG is worth doing, real efficiency gains, or ROI.
  • Frontline version: When the system fails, tasks are not masked by false success; you can see the safety notice and return to the confirm, reject, or escalate path.
  • Engineering version: How the release manifest, build artifacts, schema, configuration, task smokes, correlation_id, and rollback re-verification form a chain of evidence.
