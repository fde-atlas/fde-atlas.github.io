Hurl Tutorial: API Testing and CI Integration with Plain Text Files

Original title: Hurl 教程：用纯文本文件做 API 测试和 CI 集成

FDE Times · 2026-11-16 · 4 min read

Summary

This tutorial introduces Hurl, an open-source Rust CLI tool from Orange built on libcurl that runs HTTP requests described in plain-text files with assertions. Framed for forward deployed engineers, its main argument is that Hurl's value lies not in speed but in leaving clients a readable, editable smoke-test suite that lives in their repo and CI. The article covers request blocks, [Captures] and [Asserts] with JSONPath, the --test mode with parallel execution, JUnit and HTML reports, Docker installation, and pitfalls around parallel data dependencies and appended HTML reports. It recommends deliberately breaking a test before handover to prove the suite actually fails when it should.

Key points

  • Hurl runs plain-text HTTP request files with assertions, built on libcurl.
  • [Captures] chains requests by extracting values; [Asserts] checks responses via JSONPath.
  • --test runs files in parallel and exports JUnit, TAP, and HTML reports for CI.
  • Pitfalls: parallel files sharing data cause flaky tests; HTML reports append old results.
  • Before handover, deliberately break an assertion to verify the suite turns red.

Hurl runs on your laptop and in the customer's CI pipeline, and the other team can understand every line of it.

Key takeaways

  • Hurl is a lightweight binary written in Rust that reads plain-text files describing HTTP requests and executes them
  • The --test flag runs multiple files in parallel and outputs a summary; --report-junit and --report-html generate reports for CI
  • For an FDE, the biggest value is leaving the customer with a set of smoke tests their team can understand and modify

In your first week on-site with a customer, you'll call their API hundreds of times: fetching tokens, creating records, checking status. These calls usually end up scattered across your terminal history or someone's request collection. By the time you hand over, the customer's team has nothing they can re-run.

Hurl fills exactly this gap. According to its official website, it is a command-line tool that runs HTTP requests written in a plain-text format — a lightweight binary written in Rust, using libcurl as its HTTP engine.

The project is hosted on GitHub under the Orange-OpenSource organization and licensed under Apache-2.0. If the customer has an approval process for open-source software, confirm early whether this license is on the allowed list.

For a Forward Deployed Engineer (FDE), the value isn't speed — it's that a text file can be committed to the customer's repository, reviewed in a pull request (PR), and run in their CI with a single command.

One file, covering one complete business flow

Suppose you're integrating with a customer's task orchestration API, and the flow to verify is: create a task, get its id, then confirm the task is running. Written in Hurl, it

integration/create_job.hurl

looks roughly like this:

# 创建新任务
POST https://{{host}}/api/jobs
Content-Type: application/json
{
  "name": "nightly-sync"
}
HTTP 201
[Captures]
job_id: jsonpath "$.id"

# 检查刚创建的任务
GET https://{{host}}/api/jobs/{{job_id}}
HTTP 200
[Asserts]
jsonpath "$.state" == "running"

Each block is a request plus the expected status line.

[Captures]

Sections capture values from a response for reuse in later requests. Hurl's README uses XPath as an example, extracting a CSRF token from a meta tag on an HTML page.

[Asserts]

Sections check the returned content — for example, the official sample docs use JSONPath to compare a JSON field.

It's worth noting

{{host}}

. Don't hardcode staging or production addresses in the file, and the same test suite can run against every one of the customer's environments.

From laptop to CI, just one flag away

When debugging, just run the file normally to see the last response. To turn it into a test, add the

--test

flag. According to the Hurl documentation, this mode adds a run summary, stops printing the last response, and executes assertions as usual. Multiple

.hurl

files also run in parallel to shorten the total time.

The official CI/CD integration guide provides a command that's almost ready to use as-is:

hurl --variable host="$1" --test integration/*.hurl

Add

--report-junit report.xml

, and most CI systems can read the results and show which tests failed. Hurl can also export text, TAP, and HTML reports; the HTML report is generated with

--report-html DIR

, so even people who don't read logs can understand it.

Installation is easy too. Hurl can be installed via Homebrew and Cargo, and there's an official Docker image

ghcr.io/orange-opensource/hurl

. In companies with tightly controlled build machines, running via the Docker image is usually the option requiring the fewest permissions.

Two pitfalls before putting it into the customer's pipeline

The first pitfall comes from parallel execution itself. If file A creates data that file B needs, the two may run at the same time, and the tests will become flaky. A safe rule is to make each file self-contained: put any flow with chained requests in a single file, passing data via captures.

The second pitfall is the HTML report. The documentation is clear: new results are appended to the existing report. If the CI runner reuses the working directory, delete the report directory before each run, otherwise readers will mix today's results with yesterday's.

Also be clear about the tool's boundaries. Hurl checks HTTP behavior from the outside. It can tell you the API returned something wrong, but to figure out why, you still have to read the customer's logs and code.

What to learn first

Master three things in order: the structure of request blocks and their status lines, how to capture values to chain requests, and the JSONPath syntax used for assertions. With these three, you can write smoke tests for most REST APIs. After that, learn

--variable

、

--test

and the various report flags.

When you arrive on-site with a customer, the first thing to do is write one file that checks the most important endpoint in the integration, commit it to their repository, and get it running in CI before the first demo. From then on, every bug you find gets a

.hurl

file that reproduces it.

Break the test on purpose before trusting it

Before handing the test suite to the customer, it's worth doing a small exercise: in the example file above, change

"running"

to a value that's definitely wrong, such as

"no-such-state"

. Then run

hurl --variable host=... --test --report-junit report.xml integration/*.hurl

。

You should check three things. The summary at the end of the run should show

create_job.hurl

failing, while the other files still pass.

report.xml

The file should record the same failure; after pushing to a trial CI job, the pipeline should turn red.

If any one of these doesn't reflect the error, the test suite isn't trustworthy yet, even if everything is green today. Change the assertion back to the correct value, run it again, and see it turn red and then green with your own eyes before handing it over.

From a career perspective, a directory of

.hurl

files in a portfolio repository proves to recruiters that you can test APIs you didn't write. When FDE job descriptions mention "API integration" or "CI/CD", put a concrete achievement on your resume — such as building a set of smoke tests running in a customer's pipeline — rather than just listing tool names.

After you leave a project, the integration code will likely be rewritten. But the text files that document what the API must return often outlive the code.
