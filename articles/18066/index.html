What is dbt: An FDE's Introduction to Data Transformation

Original title: dbt 是什么：FDE 数据转换入门

FDE Times · 2026-10-08 · 4 min read

Summary

This FDE Times article introduces dbt as a tool for forward deployed engineers: it turns plain SELECT statements into modular models with version control, CI/CD, tests, and documentation, so client analysts can maintain data pipelines after the FDE leaves. It covers built-in tests (unique, not_null, accepted_values, relationships), incremental models for large tables, and snapshots implementing type 2 SCD on changing source tables. The Rust-based v2 catches SQL errors before they reach the warehouse and runs on an Apache 2.0 open-source CLI. Limitations: dbt assumes data is already in the warehouse, tests only check declared issues, and incremental logic must be agreed with clients upfront.

Key points

  • dbt organizes SELECT statements into versioned, tested, documented models.
  • Tests pass when queries hunting bad rows return nothing; four built-in test types exist.
  • Incremental models process only new or changed rows; snapshots preserve history of changing tables.
  • Rust-based v2 detects SQL errors before they hit the warehouse; CLI runtime is Apache 2.0 open source.
  • Limits: no data ingestion, tests check structure not meaning, incremental definitions need client agreement.

Key Takeaways

  • dbt organizes plain SELECT statements into modular models, with version control, CI/CD, and documentation
  • A test passes when the query returns no problem rows; incremental models and snapshots handle large and frequently changing tables
  • The v2 generation is written in Rust and can catch errors before SQL reaches the data warehouse; the runtime is open source under Apache 2.0

A dbt test passes when the SQL it runs returns no rows. That sounds counterintuitive, but it captures the tool's philosophy: the queries are built to hunt for problem data, so no results is good news.

For a Forward Deployed Engineer (FDE), this small detail says a lot. Picture yourself on-site at a client, facing a data warehouse full of raw tables, with your product needing to read clean numbers out of it. Whether the project keeps running after you leave depends not on how clever the SQL is, but on how that SQL is managed.

dbt's development team, dbt Labs, describes it as a tool that transforms raw data in the data warehouse into trusted data products. The mechanism is simple: you write plain SELECT statements, and dbt assembles them into modular, maintainable models.

The difference between dbt and a folder full of scripts is everything beyond the SELECT: applying version control, CI/CD, and documentation to analytics code, so that anyone on the team who knows SQL can contribute to production data pipelines.

Why do FDEs need it more than in-house data engineers?

Consider a common scenario. The client has a raw orders table and a customer table that changes frequently, and they want your product to read clean data every morning. The fastest approach is to write a few SQL scripts, hook them up to cron, and fly home. Three months later, someone manually changes a column, the pipeline breaks, and nobody knows why.

dbt exists to prevent exactly this. The logic lives in version-controlled models, every change has a history and gets reviewed, and tests run before anything reaches production. That's precisely why it suits FDEs: what you deliver should be something the client's analysts can fix themselves, not something only you can understand.

SQL scripts left on-site

  • Logic scattered everywhere, nobody knows who changed what
  • Problems only surface when the client sees wrong numbers
  • Only the original author dares to touch it

A dbt project

  • Every model is a version-controlled, reviewed SELECT
  • Tests that hunt for problem rows run before production
  • Anyone on the client's team who knows SQL can make changes

A minimal example: from models to snapshots

Start with your first model: a file called stg_orders.sql containing a single SELECT that pulls id, customer_id, amount, and status from the raw table, with consistent column names. No CREATE TABLE, no DDL—dbt handles the heavy lifting.

Next comes testing. dbt ships with four generic tests: unique, not_null, accepted_values, and relationships. You declare that id must be unique and non-null, that status can only take a few predefined values, and that customer_id must exist in the customer table. Each test is a query that hunts for violating rows; if nothing comes back, the pipeline moves on.

When the client's orders table grows to hundreds of millions of rows, convert the model to an incremental model. After the first run, dbt only transforms new or changed rows. The dbt documentation states explicitly that this limits the amount of data that needs processing and dramatically shortens run times. When the client's bill goes up, this is the first thing they'll ask about.

Addresses and service plans in the customer table change over time—that's when you need snapshots. Snapshots implement type 2 slowly changing dimensions (SCD) on mutable source tables: whenever a row changes, the old version is preserved. When the client asks "which plan was this account on last month?", you have the data instead of a shrug.

The new generation of dbt catches errors before they reach the data warehouse

The current generation, dbt v2, is written in Rust and understands the SQL dialects of different engines. The practical effect: it can catch errors before the SQL statements ever reach the data warehouse. On a client site, where every failed run burns both compute and trust, this is the most valuable feature.

v2 is the default experience when you install dbt, built on an open source CLI runtime under the Apache 2.0 license. dbt is free to use, with some features unlocked after logging into a dbt Platform account.

Limitations you should be upfront about with clients

dbt starts from raw data already in the data warehouse—dbt Labs describes it that way itself. So before writing your first model, ask the client: has the source data already landed in the data warehouse, and how did it get there? That question is outside the scope of the SELECT statements dbt manages.

Tests only catch the problems you've declared. The four built-in tests check structure, not meaning: negative revenue passes not_null just fine. You need to write additional business tests, ideally alongside the person on the client side who knows this data best.

Incremental models only process new or changed rows, so agree with the client from the start on what counts as "new" in their systems. Treat it as a design decision to discuss with the client, not a one-line config.

What to learn first

Solid SQL is a prerequisite, not an advantage. What really needs practice is the engineering discipline beyond SQL: git, code review, automated testing. Writing "built a dbt project with tests and snapshots for a client's tables" on your resume is more convincing than "proficient in SQL."

When reading job descriptions, if terms like "analytics engineering," "data model," or "warehouse" appear alongside FDE, it's a sign you should have a story ready about a dbt project you built yourself.

Picture an interviewer handing you a raw orders table and asking what you'd do in your first week on-site. A credible answer isn't "write SQL"—it's walking through the whole loop: one SELECT model, four tests, snapshots for tables that change, and an explanation of why the client's analysts must be able to fix things themselves.

Practice telling that story in five minutes, and have a real project on your laptop.

Clients won't remember the SQL you wrote. They'll remember that long after you left, the pipeline was still running and the tests were still quiet.
