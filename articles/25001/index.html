A Practical Guide to Reducing LLM Costs | Techniques and Priorities Used in the Field by FDEs

Original title: LLMコスト削減の実践ガイド｜FDEが現場で使う手法と優先順位

Summary

This Japanese guide from FDE総研 explains how LLM costs are driven by token price, token volume, and call frequency, and presents five reduction methods: model routing, prompt compression, prompt caching, batch processing, and context design. It recommends a safe order—measure first, apply low-risk measures like caching (Anthropic cache reads at ~10% of input price) and batching (50% discounts), then switch models gradually with eval sets guarding quality. It also argues FDEs are well positioned to translate costs into per-task business terms and agree quality thresholds with customers.

Key points

  • Costs = unit price × token volume × call count; long inputs and verbose outputs dominate.
  • Five methods: model routing, prompt compression, caching, batching, context redesign.
  • Prompt caching and batch APIs cut costs without changing output quality.
  • Sequence: measure, apply low-risk measures, then change models with eval sets.
  • FDEs translate token metrics into per-task costs and negotiate quality tiers with customers.

What Determines LLM Costs?

LLM costs are largely determined by "token unit price × token volume × number of calls." The first things to look at are the volume of long inputs and outputs.

LLM API fees are calculated, for most commercial models, by multiplying the unit prices of "input tokens" and "output tokens" by the amount used. Unlike fixed-monthly-fee SaaS, your bill grows directly with usage. This is why costs that seemed negligible during a PoC can balloon to dozens of times larger in production.

Cost factorDescriptionCases where it tends to grow in the field
Model unit pricePrice per million tokens for each modelRunning all processing on the top-tier model
Input token volumeSystem prompts, RAG search results, conversation historySending the full text of a long manual every time
Output token volumeText and JSON generated by the modelVerbose outputs from prompts like "explain in detail"
Number of callsNumber of API calls per business taskAn agent repeatedly making tool calls
Retries and failuresRetries due to timeouts or parsing failuresRe-running the same process due to JSON format errors

How Does Model Choice Affect Token Unit Prices?

Token unit prices vary greatly by model performance tier. Even within the same provider, top-tier and lightweight models can differ by an order of magnitude.

Major providers such as Anthropic, OpenAI, and Google offer multiple models with different performance levels and prices. Top-tier models are strong at complex reasoning but have higher unit prices. For routine tasks like classification and extraction, lightweight models are often sufficient. Since prices are revised frequently, always check each provider's official pricing page for the latest values before making estimates.

Which Matters More: Input, Output, or Number of Calls?

The biggest impact comes from long inputs attached to every call, and from outputs, which are priced higher than inputs on many models.

On the input side, system prompts, conversation history, and documents retrieved via RAG accumulate with every call. On the output side, even if the volume per call is small, on models where the output unit price is set several times higher than input, verbose output directly drives up costs. Furthermore, in AI agent-style architectures, the model is called many times for a single task, so the number of calls multiplies the effect.

What Are the Main Techniques for Reducing LLM Costs?

The main techniques are five: model routing, prompt compression, caching, batch processing, and context design.

Each technique falls into one of three categories: "lower the unit price," "reduce the volume," or "reduce the number of calls." The table below summarizes the characteristics of each technique. Since the magnitude of the effect varies by use case, treat it as a relative guideline.

TechniqueFactor affectedImplementation effortQuality riskSuited processes

Prompt compression and output controlVolumeLowLow to mediumAll processes
Prompt cachingUnit price (input)LowAlmost noneShared long system prompts and documents
Batch API and asynchronizationUnit priceLow to mediumAlmost noneBulk processing that doesn't need immediate responses

Result caching and deduplicationNumber of callsMediumLowTasks where the same questions repeat

How Should You Design Model Routing?

The basic approach is to assign models by task difficulty. Simply moving lightweight tasks to lightweight models lowers the unit price.

A common division of labor is: "classification, extraction, and formatting" on lightweight models, and "complex reasoning and final answer generation" on top-tier models. There is also "routing," where input difficulty is judged by a lightweight model or rules before dispatching. However, misjudgment degrades quality, so verifying routing accuracy with an evaluation set (described later) is a prerequisite.

How Effective Are Prompt Caching and Batch Processing?

Prompt caching and batch processing can lower unit prices without changing quality, making them highly cost-effective measures.

Prompt caching is a mechanism that reuses the same leading portion each time (such as system prompts and reference documents) and lowers the input unit price for that portion. For example, Anthropic's official pricing states that input read from the cache costs one-tenth of the normal input unit price (with a premium for cache writes). Batch processing is a mechanism that offers discounted pricing in exchange for not requiring immediate responses. Both Anthropic's Message Batches API and OpenAI's Batch API are officially advertised at 50% off standard rates. Since conditions and discount rates can change, check the latest documentation before adopting them.

How Should You Trim Prompts and Context?

First, review whether the information sent every time is truly necessary. Then, constrain output format and length through instructions.

Common sights in the field include manuals sent in full "just in case," and conversation histories that accumulate without limit. Review the number of RAG results and chunk sizes, summarize history before sending it, and constrain output with JSON schemas or character limits. These are unglamorous measures, but they reduce volume while minimizing impact on quality.

In What Order Should You Tackle LLM Cost Reduction?

Proceed safely in the order of measurement, low-risk measures, then model changes. Avoid switching models right away.

A common pattern in the field is deciding upfront to "switch to a cheaper model because it's expensive," only to see quality drop and complaints come in from the field. Starting with areas you can trim without changing quality makes it easier to get buy-in from stakeholders.

  • Measure: Record token volume and call counts by feature, prompt, and user
  • Identify top spending sources: Narrow down to the few processes that account for most of the spending
  • Implement measures that don't affect quality: Prompt caching, batching, suppressing retries, eliminating duplicate calls
  • Reduce volume: Prompt compression, output format constraints, narrowing context
  • Set up an evaluation platform: Create sets of representative inputs and expected outputs
  • Try differentiating model usage: Compare using the evaluation set and gradually migrate to lighter models

Why is measurement needed first?

Because without knowing what you're using and how much, you can't choose the measures with the biggest impact. Measurement is the starting point for everything.

The total on an invoice alone won't tell you which features are driving up costs. Start by logging input token count, output token count, model name, and feature name for each request, and aggregating daily. Using monitoring tools or gateways designed for LLMs makes this visualization relatively quick to set up.

What's the benefit of starting with low-risk measures?

Starting with low-risk measures delivers cost reductions without needing to debate quality. It's also effective for building internal trust.

Caching and batching don't change the output content, so quality assurance procedures can be kept light. If you can show your first results as "quality unchanged, only costs reduced," it becomes easier to get agreement on riskier measures that come next, such as model changes.

What role does an FDE play in LLM cost reduction?

An FDE works on-site with customers, designing the balance between business requirements and costs from a technical perspective, and establishing it in a form that can be operated.

FDE (Forward Deployed Engineer) is a role that became widespread at Palantir, characterized by deeply embedding in customer sites and implementing solutions through to problem resolution. LLM cost reduction doesn't end with technical ingenuity. It is itself the work of working through with the customer "which business processes need what level of quality." That's why we believe this is an area where the value of FDEs shines.

What should be visualized first at the customer site?

Visualize "how much each unit of work costs" in business terms. This lets you translate technical metrics into the language of management.

Saying "several million tokens per month" rarely resonates with customer decision-makers. Converting it into business units like "how many yen per customer inquiry handled" or "how many yen per report processed" makes it usable for comparison with manual processing and as input for investment decisions. This translation is work that only an FDE who understands the field's business can do.

How do you reach agreement on the balance between business requirements and cost?

Agree with the customer on the quality required for each process, and clarify where premium models will be used. Then obtain agreement.

Not every process needs the highest quality. Internal draft generation and final responses sent to customers have different acceptable error levels. Through interviews with field staff, the FDE clarifies this line, and together with customer decision-makers decides on policies like "this task is fine with a lightweight model" or "only this decision uses a premium model."

How do you reduce LLM costs without lowering quality?

The key to protecting quality is preparing an evaluation set before implementing reduction measures, switching gradually, and monitoring continuously.

Most cost reduction failures happen because the switch was made on a vague sense that "it's probably fine," leading to a delayed discovery of quality degradation. You need a system where reduction and evaluation always run as a pair.

Quality protection mechanismPurposeWhen to implement
Evaluation set (golden data)Compare quality before and after changes under the same conditionsBefore implementing a measure
A/B testing and staged releasesVerify impact on a portion of trafficAt the time of switching
Monitoring quality metricsDetect changes in accuracy, error rates, and user ratingsThroughout operation
Rollback proceduresImmediately revert to the original configuration if problems arisePrepared in advance

How should you build an evaluation set?

Gather dozens to hundreds of representative production inputs and expected outputs, and make it possible to automatically score every change.

For the evaluation set, it's effective to include not just common inputs but also past cases where incorrect answers caused problems and borderline cases. Scoring combines items judged by exact match or rules with items using an LLM as the evaluator. Ideally, evaluation criteria are decided together with the customer's field staff.

Which areas should not be cut?

Decisions where errors have major impact and outputs delivered directly to customers are areas where quality should take priority over cost.

For decisions involving money or contracts, medical or safety-related information, and final responses sent externally, we recommend keeping premium models and human review even at somewhat higher cost. The purpose of cost reduction is to redirect saved budget to high-value processing. Chasing reduction rates at the expense of quality can, in the long run, undermine trust in LLM usage itself.
