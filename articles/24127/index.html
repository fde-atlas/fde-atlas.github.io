What is Palantir Pipeline Builder? Features and How to Use It as an FDE

Original title: Palantir Pipeline Builderとは？機能とFDEでの使い方

FDE総研 · 2026-10-29 · 9 min read

Summary

This article explains Palantir Pipeline Builder, a GUI-based data integration tool within Foundry that handles the transformation layer between raw data and the Ontology. It emphasizes that pipelines built this way are production-grade, supporting branching, proposals, data quality checks, and incremental or streaming processing. The author compares it with Code Repositories (Python/SQL/Java), arguing the two are complementary: Pipeline Builder wins on readability and shared review with business users, Code Repositories on expressiveness and testing. From an FDE perspective, it enables fast validation with customers during onboarding and matters for handover, since clients must maintain the assets after the FDE leaves.

Key points

  • Pipeline Builder builds transformations visually and outputs directly to Ontology.
  • It is production-grade: branching, proposals, quality checks, incremental and streaming runs.
  • Code Repositories offer more expressiveness; the two are typically used together.
  • FDEs use it to validate data with customers live and show working results quickly.
  • Handover to client teams should shape tool choice from the start.

What is Palantir Pipeline Builder? What is its role in Foundry?

Pipeline Builder is a data integration tool in Palantir Foundry that lets you assemble everything from data ingestion to transformation and output to the Ontology in a GUI.

In Foundry, raw data (ERP, sensors, files, etc.) is transformed and fed into the Ontology (a model of business objects), where it is used by applications and AIP. Pipeline Builder handles the "transformation" part of this flow. The official Palantir documentation (Foundry › Pipeline Builder) introduces it as a data integration application that enables technical and non-technical users to collaborate on the same screen.

What kind of tool is Pipeline Builder, and where does it fit?

Its distinguishing feature is that you can build transformation logic without writing code, while still operating it as a production-level pipeline.

So-called no-code tools are often seen as being for prototyping. However, pipelines built with Pipeline Builder run on a schedule on Foundry's build infrastructure and are subject to data lineage (tracing the origin of data) and branch management. Because the "source" and "destination" of data are displayed in a single graph, business department staff can also review the processing content. In the field, FDEs (Forward Deployed Engineers) likely find this "show-and-agree" quality a major reason for choosing the tool.

Which part of Foundry's data flow does it handle?

Pipeline Builder handles the middle layer of "raw data → curated datasets → Ontology" and can also write directly to the Ontology.

LayerMain roleMain Foundry apps involved
IngestionSync data from external systemsData Connection
TransformationCleansing, joining, aggregationPipeline Builder / Code Repositories
SemanticsDefine business objects and linksOntology Manager
UtilizationBusiness apps, analytics, AIPWorkshop / Quiver / AIP Logic, etc.

From an FDE's perspective, Pipeline Builder is the first major hurdle in turning customer data into a "form usable by the business." How much reliable data can be prepared in the first few weeks of an engagement tends to determine the speed of subsequent application development.

What are Pipeline Builder's main features?

The main features are six: visual transformations, type checking, preview, branches and review, data quality checks, and Ontology output.

Pipeline Builder has many detailed features, but focusing on those commonly used in FDE practice, they can be organized as follows.

What transformation and preview features are available?

You can connect transformations such as joins, filters, and aggregations as nodes, and assemble pipelines while previewing the results of each step on the spot.

FeatureDescriptionPractical use cases
Transformation boardsPlace Join, Union, Filter, Aggregate, Pivot, type conversions, etc. in a GUIMaster data joins and pre-processing for record matching
ExpressionsCalculate columns by combining functionsDate normalization, code value conversion
PreviewInstantly check node outputs with samplesValidating while reviewing the screen together with customers
Type checkingDetect schema inconsistencies before buildsNotice upstream column changes early
LLM transformationsIncorporate AIP LLMs as transformation stepsClassifying and extracting free-form text
UDFsSupplement processing not covered by standard functions with codePartial implementation of custom logic

Type checking is especially effective in practice. Instead of discovering failures after running a build, errors are displayed while you are editing, which reduces rework.

What operations and governance features are available?

It includes branches, change proposals, data quality checks, and scheduled execution, and is designed with production operation in mind.

  • Branches: Try changes without affecting production, then merge after validation
  • Proposals: Show changes as diffs and reflect them after review and approval
  • Data quality checks (Expectations): Inspect things like primary key uniqueness and NULL rates at build time
  • Schedules: Trigger builds based on upstream data updates or times
  • Output target selection: Choose datasets, Ontology object types, link types, and more

Processing methods support not only batch but also incremental (delta processing) and streaming. The range of available transformations differs by processing method, so it is safest to check the latest support status in the official documentation.

How does it differ from Code Repositories? When should you use each?

Pipeline Builder excels at speed and ease of sharing, while Code Repositories excel at expressiveness and fine-grained control; in practice, most people use both together.

Code Repositories is Foundry's development environment where you write transformations as code in Python (PySpark), SQL, Java, and more, managed on a Git basis. Both handle "transformations," but they specialize in different areas.

How do they differ in terms of features?

The biggest difference is "who can read it and how far you can write it": Pipeline Builder wins on readability, Code Repositories on flexibility.

AspectPipeline BuilderCode Repositories
How you buildPlace nodes in a GUICode (Python/SQL/Java, etc.)
Typical usersAnalysts, FDEs, business stakeholdersData engineers, FDEs
Speed to get startedFastRequires environment setup and coding
ExpressivenessStandard transformations plus UDFsNearly unrestricted, including libraries
TestingFocused on quality checks and previewsCan write unit tests
ReviewProposals (GUI-based diffs)Git pull requests
Sharing with business teamsCan show the graph as-isRequires explaining the code

What criteria should you use to choose between them?

As a rule of thumb: use Pipeline Builder for processing that standard transformations can handle, and Code Repositories for complex algorithms or processing that requires external libraries.

In practice, the following decision criteria can be considered.

  • Cases suited to Pipeline Builder: master joins, cleansing, aggregation, writing out to Ontology. Processing that will be handed over to the customer
  • Cases suited to Code Repositories: optimization calculations, custom record-matching algorithms, machine learning preprocessing, processing that requires rigorous unit tests
  • Cases where you use both: implement heavy computation in Code Repositories, then shape its output in Pipeline Builder and feed it into Ontology

What FDEs tend to overlook is "ease of handover." Since FDEs will eventually leave the site, whether the customer can maintain the solution themselves is a key criterion for tool selection. Even in situations where code would be easier for an engineer to write, there is a rational basis for deliberately choosing Pipeline Builder.

How do you build a pipeline with Pipeline Builder?

The basic approach is to build in six steps: adding inputs, placing transformations, validating with previews, configuring quality checks, defining outputs, and deploying.

Since detailed screen operations vary by version, this section focuses on the overall flow and key points.

What is the basic build procedure?

The minimal flow is to select input datasets, connect transformation nodes, define the output, and deploy.

  • Create a pipeline: create a new one within a Foundry project and choose batch or streaming
  • Add inputs: select datasets or media sets ingested via Data Connection
  • Assemble transformations: connect nodes in the order of type conversion → cleansing → joins → aggregation
  • Validate with previews: check row counts and value distributions in each node's output
  • Define outputs: set a dataset or an Ontology object type as the output destination
  • Deploy (build): set up a schedule and put it on periodic execution

What are the common stumbling blocks when building?

The three most common pitfalls are type mismatches, duplicate join keys, and keeping up with schema changes; adding quality checks early keeps things stable.

Common problemWhat happensHow to address it
Type mismatchDates and numbers flow through as stringsPlace a type conversion node right after the input
Duplicate join keysRow count balloons after a JoinDeduplicate before joining and set a primary key uniqueness check
Upstream schema changesBuilds fail due to renamed columnsCheck type-check errors and fix on a branch
Logic bloatThe graph becomes unreadableBreak stages apart using intermediate datasets

From experience, skipping a row-count check after a Join tends to lead to inquiries later that "the numbers don't match" on downstream dashboards. Rather than adding quality checks "later," it's safest to include them from the very first deployment.

How do FDEs use Pipeline Builder in practice?

FDEs use Pipeline Builder to demonstrate value quickly while examining data on the same screen as the customer, and ultimately as a tool for handing over to the customer.

Palantir FDEs work on-site with customers, running short cycles from problem discovery to implementation. Pipeline Builder is a tool that fits this way of working well.

How is it used in the early stages of an engagement?

In the early stages, the focus is on connecting the customer's raw data to Ontology in a short time and showing a "working thing" to solidify requirements.

A typical practical flow might look like the following.

  • Data exploration: use the preview feature to review missing values and inconsistent formatting with the customer
  • Aligning requirements: show the transformation graph and agree on the spot on questions like "can we filter on this condition?"
  • First demo: output to Ontology and reproduce the business flow with a simple Workshop screen

What matters here is speed of validation rather than polish. Being able to modify logic during a meeting and immediately show results is a strength that code-based development lacks.

How do Pipeline Builder skills benefit an FDE's career?

Pipeline Builder skills allow you to demonstrate data modeling ability and business understanding at the same time, so they are likely to be valued as a foundational FDE skill.

Skills gainedContentWhere they transfer beyond FDE roles
Data modelingUnderstanding the business in terms of entities and relationshipsData engineer, analytics engineer
Data quality designDesigning validation rules from business requirementsData governance
Consensus buildingAlign stakeholders using visualized logicPM, Solution Architect
Handover designCreate a configuration the customer can maintainImplementation consulting

On the other hand, GUI tools alone can make it difficult to demonstrate technical depth. For engineers aiming to become FDEs, a realistic strategy is to master both Pipeline Builder and Code Repositories (PySpark/SQL) and make "the ability to judge which one to use" their strength.

For decision-makers at companies considering FDE adoption, whether FDEs can build assets with Pipeline Builder that can be maintained in-house directly affects the company's ability to operate independently after the contract ends. Establishing a system where in-house data staff participate in reviewing proposals from the implementation stage onward tends to make handover smoother.
