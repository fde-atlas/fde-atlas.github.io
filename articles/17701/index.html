Solutions Engineer to FDE: Turning PoCs into Production Code

Original title: 解决方案工程师转 FDE：把 PoC 写成生产代码

FDE Times · 2026-10-08 · 7 min read

Summary

This guide explains how a Solutions Engineer can close the gap to FDE by rewriting a six-line ticket-classification PoC to production standards. The core difference: FDEs write production code and own deployment outcomes, fixing failures themselves at 3 a.m. The author walks through adding input validation, timeouts, retries, a needs_review fallback queue, tests, a one-page architecture doc, and deployment via FastAPI and Docker. It also covers FDE interviews (LeetCode-medium coding in customer scenarios, 60-minute ops deep-dives), warns that Anthropic's Solutions Architect role is pre-sales, and lists common transition mistakes like showcasing demos instead of running systems.

Key points

  • FDEs own running systems; Solutions Engineers stop at handoff after the deal.
  • Four-step upgrade path: error handling, tests, architecture docs, real deployment.
  • Fallbacks like needs_review queues are business decisions agreed with customers.
  • Interviews test trade-off reasoning; coding is roughly LeetCode medium.
  • Resumes should show deployed systems with tests, not polished demos.

Rewriting a short PoC to production standards reveals exactly where the gaps are, lets you close them one by one, and is worth putting on your resume.

Key Takeaways

  • Moving from Solutions Engineer to FDE means shifting from demo code to production code, and taking responsibility for deployment outcomes.
  • The most effective exercise: take an existing PoC, add error handling, tests, and architecture documentation, then deploy it to a real environment.
  • In an FDE interview, you must explain why you chose a particular deployment approach, not just prove that the code runs.

You've just finished demoing an LLM-based support ticket classification tool, and the client is thrilled. Next Monday, it goes into production. At 3 AM, a CSV file comes in with a blank row, the model responds with a greeting instead of JSON, and the entire data pipeline grinds to a halt.

If you're a Solutions Engineer, your work usually ends the moment the contract is signed. If you're a Forward Deployed Engineer (FDE), you're the one who gets up at 3 AM to fix it.

The career-switch guide at fde.academy boils the difference down to two shifts: you write production code instead of demo code, and you own the deployment outcome rather than handing it off once the deal closes.

The good news is that this gap has a clear outline, and every piece of it can be practiced separately. Below, we take a very short proof of concept (PoC), step it up to production standards, and then show how to demonstrate this capability in your resume and interviews.

Responsible for the Design, Not for the System

In comparing the two roles, Aced writes that FDEs spend most of their week writing production code. Solutions Architects, by contrast, are only responsible for the design, not for the running system. Once the system breaks or fails to deliver value, fixing it is directly the FDE's responsibility.

Sundeep Teki puts it even more bluntly in his 2026 FDE interview guide: you don't file a ticket or blame another team—you fix it yourself. For people from a consulting background, this is the biggest change, bigger than learning new syntax or new frameworks.

fde.academy has a line worth remembering: a PoC only needs to prove a point, but production code has to withstand reality. "Reality" here means dirty data, flaky networks, APIs that return unexpected content, and the person who reads your code six months from now.

Where Does a Six-Line PoC Break?

Consider the demo code from the client meeting above:

import csv, json
from llm import client

for row in csv.DictReader(open("tickets.csv")):
    out = client.complete(f"对这个工单分类：{row['text']}")
    print(row["id"], json.loads(out)["label"])

(The prompt string means "Classify this ticket:"). On ten carefully selected sample tickets, it runs smoothly. But once it hits a real environment, at least five things can go wrong. Empty tickets still get sent to the model, tickets several pages long may exceed the context length limit, and a single API timeout can crash the entire loop.

If the model returns plain text,

json.loads

throws an exception. If the model invents a label that doesn't exist, that label silently flows into downstream systems.

The rewritten code doesn't need to be smarter—it just needs to treat every possible failure as something that will definitely happen. First, explicitly declare the valid labels and set up a dedicated logger:

import json, logging, time
from llm import client

LABELS = {"billing", "bug", "account", "other"}
log = logging.getLogger("triage")

Next, break the single model call into a standalone function that truncates the input, sets a timeout, and validates the returned label:

def call_model(text: str) -> str | None:
    out = client.complete(f"对这个工单分类：{text[:4000]}", timeout=20)
    label = json.loads(out).get("label")
    if label in LABELS:
        return label
    log.warning("未知标签：%r", label)
    return None

The warning message is "unknown label". Finally,

classify

handles empty input, retries with backoff, and provides an escape route when all attempts fail:

def classify(text: str, retries: int = 3) -> str:
    if not text or not text.strip():
        return "other"
    for attempt in range(retries):
        try:
            label = call_model(text)
            if label:
                return label
        except (TimeoutError, json.JSONDecodeError) as e:
            log.warning("第 %d 次尝试失败：%s", attempt + 1, e)
            time.sleep(2 ** attempt)
    return "needs_review"

Note the last line. Instead of crashing, the system routes the ticket to

needs_review

queue for human review.

This is a business decision that must be agreed with the client: how many tickets per day can they tolerate landing in this queue? Production code is full of questions like this; demo code skips them all.

Then, write tests for the scenarios listed above:

def test_empty_ticket_goes_to_other():
    assert classify("   ") == "other"

def test_non_json_reply_goes_to_review(monkeypatch):
    monkeypatch.setattr(client, "complete", lambda *a, **k: "你好呀")
    assert classify("我被重复扣费了", retries=1) == "needs_review"

Here the mocked model replies "hello", and the test ticket says "I was charged twice". These two tests take less than ten minutes to write, yet they turn a 3 AM incident into a single warning line you read in the logs at 9 AM.

Four Steps to Take a PoC to Production

fde.academy's most practical advice is: take an existing PoC and rebuild it to production standards. They break the work into four steps: add error handling, write tests, write architecture documentation, and deploy to a real environment. The example above only covers the first two steps.

The third step is often underestimated. The architecture documentation doesn't need to be long—it just needs to answer: where does the data come in, where does it flow, which external services are called, and where to look in the logs when something breaks. For this ticket classifier, a single page like the following is enough to get started:

# triage-service
输入：来自客户系统的工单（id, text）
输出：{billing, bug, account, other, needs_review} 中的一个标签
外部调用：LLM API，超时 20 秒，最多重试 3 次
出故障时：查看 "triage" logger，统计每天的 needs_review 工单数
运维负责人：你的名字，以及出问题时如何联系你

The items are: input (tickets from the client's system, with id and text); output (one label from the set); external calls (LLM API, 20-second timeout, up to 3 retries); when it breaks (check the "triage" logger, count the daily needs_review tickets); owner (your name, and how to reach you during an incident). The person reading this page is most likely an engineer on the client's side who will operate the system together with you. The last line matters most, because it states who is accountable for the system.

The fourth step is where capability is truly tested. Coursera's article on AI engineers lists "turning models into APIs that other applications can integrate" and "managing production infrastructure" as core responsibilities. For the example above, in a file named

api.py

, wrap

classify

into an interface in just a few lines:

from fastapi import FastAPI
from pydantic import BaseModel
from triage import classify

app = FastAPI()

class Ticket(BaseModel):
    id: str
    text: str

@app.post("/classify")
def classify_ticket(t: Ticket) -> dict:
    return {"id": t.id, "label": classify(t.text)}

@app.get("/health")
def health() -> dict:
    return {"ok": True}
/health

The interface is used to hook up monitoring and confirm the service is alive. But code left on your laptop doesn't count as deployment. The next step is to package the service so it runs the same way anywhere, for example with a short Dockerfile:

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]

Then build, run, and test it yourself as an external user:

docker build -t triage-service .
docker run -d -p 8000:8000 -e LLM_API_KEY="$LLM_API_KEY" triage-service
curl http://localhost:8000/health
curl -X POST http://localhost:8000/classify \
  -H "Content-Type: application/json" \
  -d '{"id": "t-1", "text": "   "}'

Note the

-e

flag: the API key is passed in via an environment variable, never written into the code or the image. The last

curl

sends an empty ticket—exactly the kind of input that crashed the demo pipeline earlier. This time you should get the

other

label.

Once the image runs locally, put it on a server or container service that others can reach over the network, and hook

/health

into monitoring. At a client, this is usually infrastructure they already use, so the first question to ask is: where is the service deployed, and who has permission to view the logs.

The Interview Tests Exactly This Gap

According to Sundeep Teki's guide, FDE coding interviews are roughly LeetCode medium difficulty, but set in a client scenario. At Palantir, questions are framed around things you'd build for end users.

The technical deep-dive lasts 60 minutes with no coding; scoring is based on your ability to ask clarifying questions, do root cause analysis, and how you weigh trade-offs.

Coursera makes the same observation about AI engineer interviews: you have to explain why you chose a particular way to develop, deploy, and scale the solution. The deep-dive doesn't require you to type code, but it still tests operational experience.

If you've never deployed anything yourself, the trade-offs question will expose it immediately: you can say "we should add retries", but not how many, or why.

There's also a trap when reading job descriptions. Teki's guide points out that Anthropic doesn't use the FDE title; instead, it hires Solutions Architects for its Applied AI team. That's a pre-sales role, whose responsibility is to be the client's trusted technical advisor. The title won't tell you who is accountable for production.

When reading a job description (JD), watch for phrases like "own deployment", "on-call", and "ship to production". If it's all "workshops" and "demos", it's still a consulting role.

Common Mistakes Career Switchers Make

Most commonly, people put a polished demo on their resume instead of a running system. "Built chatbot demos for 5 clients" says less than "deployed a ticket classification API with tests, retries, and a human review queue, currently in production."

What FDE recruiters want to see is that you were responsible for a running system, not just that you did the design.

The second mistake is using

try/except

to swallow all errors and let the code slip through. That's hiding errors, not handling them. Every fallback branch should log and lead to a state someone can see, like the

needs_review

。

The third mistake is assuming you need a degree to switch roles. Coursera discusses AI engineering in general rather than FDE, and it holds that a degree isn't required—career switchers can enter the field through projects and certifications.

If your goal is FDE, pick a project like the example above: a service you deployed yourself, with tests and documentation.

The last mistake is subtler: when an incident happens, your first instinct is to find the team responsible. As an FDE, that team is you.

The gap between a consultant and an FDE comes down to the question you ask yourself after the demo ends. One asks whether the client liked it; the other asks what will break this system tonight.
