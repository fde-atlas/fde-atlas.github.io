API Contract-First Design: Should an FDE Choose REST or GraphQL

Original title: API 契约优先设计：FDE 选 REST 还是 GraphQL

FDE Times · 2026-10-08 · 5 min read

Summary

This FDE Times guide argues for contract-first API design at customer sites: write the OpenAPI spec or GraphQL schema before any implementation code, because the customer's ERP team will build against every field you expose. Using a hypothetical shipment risk-scoring project, it covers choosing REST versus GraphQL based on who calls the API, naming resources with business terms instead of database columns, designing idempotent write endpoints so client retries are safe, and picking a versioning strategy for breaking changes. It closes with advice on demonstrating this skill in FDE job applications and interviews.

Key points

  • Decide API access level (public, partner, private) before choosing REST or GraphQL.
  • REST suits ERP integrations with fixed operations; GraphQL suits multiple frontends needing different data slices.
  • Name URIs with business nouns and make write operations idempotent, preferably via PUT with client-supplied IDs.
  • Adding fields is usually safe; breaking changes require a versioning strategy documented in the handoff.
  • On resumes, describe contract authoring and idempotent endpoint design specifically rather than generic API building.

Key takeaways

  • To the customer's systems, the API is a contract. Write the contract first (OpenAPI or a GraphQL schema), then write the code.
  • Don't let the API mirror the database structure. Name resources with business terms, and make every write operation that could be retried idempotent.
  • Adding fields rarely affects clients. When a breaking change is unavoidable, pick a versioning strategy and document it in the handover docs.

Imagine your third week on-site at the customer. The freight risk scoring model is running and the demo went smoothly. Then the customer's ERP lead asks three questions: where should their systems call, what data comes back, and how will you notify them when something changes on your side?

These three questions determine the fate of the solution after you leave. The model can be swapped out, but the endpoints the ERP team has already written code against are very hard to change.

Your job is to design this API layer so the customer's team can integrate, operate, and upgrade it on their own, without having to come back to you.

The API is a contract, not an implementation detail

IBM defines an API as a contract: it lets one piece of software access data provided by another or call its functionality. For a Forward Deployed Engineer (FDE), "contract" should be taken literally. Every field in a response is a promise, and the team on the other side will build business logic on top of it.

So the first question isn't REST vs. GraphQL, but who is allowed to call the API. IBM classifies APIs by access level: public APIs are fully open to the internet, while partner APIs and private APIs restrict who can use them.

A risk scoring solution serving only an internal ERP and a few freight partners almost certainly doesn't need to be public. Settling this at the start saves many meetings with the security team later.

REST or GraphQL: choose based on the callers

According to IBM, REST is the most popular web API architecture today; SOAP is an XML-based messaging protocol with strict standards for message structure and transport. If the customer's ERP only supports SOAP, you have no choice; but for new designs, the practical choice is usually REST or GraphQL.

The official GraphQL documentation describes it as: building flexible, version-free APIs on top of a strongly typed system. The schema defines the shape of the data, and clients request only the fields they need.

One detail is easy to miss: the GraphQL spec deliberately says nothing about networking, authorization, or pagination—all three must be designed by your team.

REST

  • The most popular web API architecture; the ERP team almost certainly knows it
  • Resources are named with nouns; behavior is determined by HTTP methods
  • Breaking changes are handled with versioning: URI, query string, header, or media type

GraphQL

  • Clients fetch fields on demand, well suited to multiple interfaces with different data needs
  • The schema evolves over time instead of being versioned
  • Authorization, pagination, and networking must be designed by you; the spec doesn't define them

If the ERP integration team only needs a few fixed operations, REST is usually the lower-risk choice at handover. If the main consumers are multiple frontends, each needing different slices of data, GraphQL fits better.

A complete example: the freight risk API

Back to the hypothetical logistics customer. A team's first draft usually looks like this: one endpoint

POST /getRiskScore

, returning

{"shp_id": 8812, "rsk_v2": 0.83, "flg_manual": 1}

. It works, but it has three mistakes that will cause trouble after handover.

First, the URI uses a verb. Microsoft's guidance is to name URIs with nouns (resources), not verbs (operations on resources).

Second, names like

rsk_v2

and

flg_manual

are taken directly from table column names. Microsoft advises against letting the API mirror the database's internal structure. The reasoning is simple: the day you rename a column, every client breaks.

The third is the hardest to spot. The ERP sends freight data and automatically retries on timeout. If the write endpoint uses POST, every retry may create another record.

Microsoft notes that PUT must be idempotent: sending the same request multiple times modifies a single resource with the same value. POST and PATCH carry no such guarantee.

The revised version is written as a contract before any code. Microsoft calls this contract-first: design the contract—the interface—first, then write the code that implements it. The first part of the contract declares the write operations:

openapi: 3.0.3
info:
  title: Shipment Risk API
  version: 1.0.0
paths:
  /v1/shipments/{shipmentId}:
    put:
      summary: 创建或更新货运记录（幂等，可安全重试）

The next part, also under

paths

, describes the read operations and the response structure the ERP will receive:

  /v1/shipments/{shipmentId}/risk-assessment:
    get:
      summary: 获取最新的风险评估
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                required: [shipmentId, riskLevel, score]
                properties:
                  shipmentId: { type: string }
                  riskLevel: { type: string, enum: [low, medium, high] }
                  score: { type: number, minimum: 0, maximum: 1 }
                  reasons: { type: array, items: { type: string } }

Notice what changed. The resources are now

shipments

and

risk-assessment

, which anyone on the ERP side can understand at a glance. The write operation uses PUT, keyed by the

shipmentId

provided by the ERP, so no matter how many times the request is retried, there is only one freight record.

Internally, a mapping layer converts

rsk_v2

into

score

, so you can change the database schema while the contract stays the same.

When do you need versioning?

Six months later, the customer wants to add a

estimatedDelayHours

field. Adding fields usually doesn't affect clients, because old code simply ignores fields it doesn't recognize. Conversely, changing

riskLevel

from a string to a number, or removing

reasons

, is a breaking change.

For breaking changes, Microsoft lists four strategies: put the version in the URI, the query string, a header, or the media type. Microsoft considers URI versioning like

/v1/

a simple approach, but also cautions that it becomes hard to manage once the API has gone through many rounds of changes and the server has to maintain multiple versions at once.

GraphQL takes a different path: the type system evolves over time without version numbers. In practice, you add fields, keep old fields, and only remove an old field once you've confirmed no clients still use it.

Whether you choose REST or GraphQL, write this rule into the handover docs so the customer's team knows when fields will be removed and how they will be notified in advance.

A process you can follow on the next project

First, list the business terms the customer uses in conversations—freight, order, assessment—these are your candidate resources. Then, for each write operation, ask the integration team: will clients retry after a timeout?

If yes, design that operation as a PUT based on a client-provided ID. Where POST must be kept, the common practice is to require clients to include an idempotency key in the request header, which the server uses to recognize duplicate requests and return the previous result instead of creating a new record.

Next, write the OpenAPI contract or GraphQL schema and review it with the people who will actually call the API. If you chose GraphQL, bring authorization and pagination into the review too, because the spec won't handle them for you. Once both sides agree, write the mapping layer and the handling code.

The most common mistakes all come from taking shortcuts: returning ORM entities directly in responses; using POST for every write operation; changing a field's type without bumping the version; making the API public when partner-level access would suffice; choosing GraphQL on the assumption that it comes with authorization built in.

Each of these saves an afternoon while writing code, but costs the customer weeks after handover.

How to demonstrate this skill when job hunting

When reading an FDE job description, watch for phrases like "integration", "API design", and "customer-facing technical delivery". They signal that this is exactly the skill the role will use.

On your resume, instead of writing "built a REST API", be more specific: wrote a contract-first OpenAPI spec and reviewed it jointly with a partner's integration team; designed idempotent write endpoints so clients could safely retry.

Before the interview, prepare an answer to a scenario question: a customer needs to change a field that multiple systems call—what do you do? A persuasive answer starts with a contract written down from day one.
