Reference agents and W&B Weave workshops for FDEs

FDE Times · 2026-11-08 · 6 min read

Summary

Using CoreWeave's FDE (AI Agents) role as a case study, this guide argues that building and teaching are one skill: an FDE should ship a reference agent that deliberately contains typical failures, then use W&B Weave's tracing and evals in a workshop so the client's team can locate errors, fix them, and compare versions themselves. A worked logistics example shows 12 tasks scored by an LLM judge plus a hand-written order_id scorer, where a fix lifts scores from 7/12 to 11/12 but regresses one task—a lesson in why full eval reruns matter. It also covers a three-hour workshop structure and common mistakes.

Key points

  • CoreWeave's FDE role pairs agent building on W&B Weave with client workshops.
  • A reference agent should ship with deliberate flaws so traces and evals have something to teach.
  • An example uses 12 tasks, an LLM judge, and a custom order_id scorer to pinpoint a wrong tool call.
  • Fixing one failure can regress another, so the full task set must be rerun after each change.
  • Common mistakes: building on your own stack, trusting the LLM judge alone, and one-way workshops.

CoreWeave's FDE role pairs building agents with running workshops, and a flawed agent traced in W&B Weave shows a client's team exactly where things go wrong.

In brief

  • CoreWeave's description of the FDE (AI Agents) role covers two jobs: working alongside a client's AI team to build agents on W&B Weave, and running workshops that speed up adoption.
  • A reference agent is a teaching tool. Its value lies in the tasks, scorers and traces that come with it.
  • A good workshop ends when the client's team fixes the agent, reruns the evals and can tell whether v2 improved or regressed against v1.

CoreWeave’s job description for a Forward Deployed Engineer, AI Agents, puts teaching on the same footing as building. The person in the role works alongside a client’s AI engineering team to design, prototype and ship agents to production with W&B Weave. Workshops, deep dives and enablement sessions are also written into the description, with the stated aim of helping clients adopt the product faster.

The client’s situation is a familiar one. Their AI team has an agent that runs well in a notebook but gives wrong answers once real users reach it, and nobody can say which step goes wrong. Another polished demo will not help them. What they need is a way to see inside the agent and measure it.

Building and teaching turn out to be one skill. The reference agent you build is the teaching material for the workshop, and the workshop is where that agent gets tested. This guide covers how to do both so that the client’s team can carry on after you leave.

Why shouldn’t a reference agent be perfect?

Weave came to CoreWeave when the company completed its acquisition of Weights & Biases. CoreWeave’s documentation describes Weave as an observability and evaluation platform for tracking, evaluating and improving agents and LLM applications. Tracking and evaluating are the two jobs that matter here. A reference agent has to serve both, and running smoothly is not enough.

In Weave’s tracing model, each agent run is a conversation. A conversation is made up of turns, and each turn contains a model call and its tool calls. For a teacher this structure is very useful: it lets you point at the exact turn and tool call where the agent went wrong, instead of saying vaguely that “the model hallucinated.”

So a good reference agent should deliberately contain one or two of the typical failures the client’s team will meet in the real world. If the agent gets every task right from the start, the traces have nothing to show and the evals have nothing to improve, and the workshop becomes a performance.

One example, end to end

Take a hypothetical client, a logistics company. Its AI team wants an agent that reads complaint emails, looks up the order and drafts a reply. Your reference agent needs only two tools:

lookup_order(order_id)

to find the order and

draft_reply(order, issue)

to write the reply. You deliberately leave the prompt vague about how to pick out the order number when an email contains several numbers.

Next comes the task set. Weave’s agent-evals tutorial uses a judge model to score how well the agent completes each task against that task’s success criteria. You write 12 tasks from real emails the client has anonymized. Each task gets a one-sentence criterion, for example: “The reply states the correct order number and the expected delivery date, and does not promise a refund.”

An LLM judge alone is not enough. Weave scores with an LLM judge combined with custom scorers, and the W&B agents page states that scorers can be built-in, third-party or written by you.

You add a very simple hand-written scorer: compare the

order_id

in the tool call against the correct answer. The judge rates the quality of the reply, while the scorer checks the facts without any judgment involved.

Suppose v1 finishes and the

order_id

scorer is right on only 7 of 12 tasks. In the workshop, you open the trace of a failed task and walk through it turn by turn.

The model reads the email, calls

lookup_order

with a phone number instead of the order number, gets an error back, and still drafts a reply that sounds entirely confident. The whole room can see that the failure sits in the first tool call, not in the writing step.

Now you hand the keyboard to the client’s team. They fix the prompt and add a check on the order-number format, producing v2. Weave lets them rerun the same task set against the new version and see whether v2 moved forward or backward from v1 on the logged scores. Suppose the scorer rises to 11 of 12, but the judge marks one task lower than before.

That regressed task is the most valuable lesson of the session. The client’s team sees for themselves that fixing one thing can break another. They also understand why the whole task set must be rerun after every change, instead of retrying only the email that caused the failure.

How should the workshop be structured?

A three-hour session can be split as in the table below. The general rule is that the time the client’s team spends at the keyboard should grow with each block.

Block Duration What the client’s team does What they take away
Reading traces 40 minutes Follow the conversations, turns and tool calls of failed tasks A list of failures by step
Writing tasks and scorers 60 minutes Write more tasks from their own data and one custom scorer Their own eval suite
Fixing and comparing versions 60 minutes Create v2, rerun it, read the gains and regressions A v1 versus v2 comparison
Agreeing next steps 20 minutes Pick the first real agent to apply this to A plan for the following week

The last block is the easiest to cut when a session runs late. Do not lose it. Without the name of a real agent and a person responsible for it, everything learned in the first three blocks will sit in a notebook nobody opens again.

Common mistakes

The most common mistake is building the reference agent on your own data and stack rather than the client’s. CoreWeave has committed to keeping the W&B platform interoperable, and for an FDE that commitment means attaching Weave to whatever framework and model the client already uses. Do not make them switch to the tools you know best.

The second mistake is letting the LLM judge decide everything. A judge is useful for scoring prose, but facts that code can check, such as order numbers, amounts or dates, should have hand-written scorers. Otherwise the client’s team will argue about the judge’s scores instead of fixing the failures.

The third mistake is treating the workshop as one-way delivery. The job description asks FDEs to gather feedback from the field and pass it back to influence Weave’s roadmap. Each time the client’s team stumbles on a screen or has to write the same scorer over and over, write it down that day, because it is data for the product team.

Turning this skill into an edge when applying

The listing on inferencejobs.com asks for Python, modern ML/AI frameworks and at least five years of software engineering or hands-on coding experience. Those are the entry requirements. But because workshops and enablement sit inside the job description, evidence that you can teach others to build and measure agents is what you should put front and center.

So put a reference-agent repo in your portfolio with three things: a task set with criteria, at least one custom scorer, and a v1 versus v2 comparison that includes the regressed task.

Add a workshop agenda you have actually taught, even if only to colleagues. On your CV, write in terms of outcomes, such as “team X ran its own evals after the enablement session,” rather than “experience with LLMs.”

When preparing for interviews, do not rehearse only the account of your agent’s architecture. Prepare an enablement story as well, and the strongest one is the time another team found the regressed task on their own without you pointing it out.
