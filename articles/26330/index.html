FDE System Design Interview Question: How to Answer Legacy System Integration

Original title: FDE 系统设计面试题：遗留系统集成怎么答

FDE Times · 2026-10-30 · 5 min read

Summary

This guide explains how to answer system design interview questions about legacy system integration for forward deployed engineer roles. Using a fictional insurance company with an untouchable on-prem policy system, the author argues that proposing a clean rewrite is the wrong answer: interviewers want to see design within constraints. The recommended approach follows the Strangler Fig pattern, citing Martin Fowler and Microsoft Azure docs: ask about allowed integration points first, deploy an outbound-only agent (as Palantir Foundry does), capture events via CDC, translate legacy schemas through an anti-corruption layer, and migrate features one by one behind a façade. It also stresses proactively stating trade-offs like ACL latency and eventual consistency, and warns against applying patterns without checking preconditions.

Key points

  • Proposing a full rewrite fails FDE interviews; constraints are the actual question.
  • Pipeline: find integration points, outbound-only agent, CDC events, ACL, façade migration.
  • Martin Fowler warns most big-bang rewrites fail; prefer Strangler Fig.
  • State costs proactively: ACL latency, eventual consistency with event-driven ACLs.
  • Traps: skipping precondition checks and letting legacy schemas leak into new services.

Key Takeaways

  • FDE job postings from companies like Praxent require integrating with given systems, including legacy core systems, so treat the customer's constraints as the problem itself.
  • The safe sequence is: identify integration points, establish outbound connections, capture events via CDC, transform them through an ACL, then migrate functionality one piece at a time behind a façade layer.
  • Don't propose a full rewrite—Martin Fowler notes most such efforts fail—and don't let the old schema leak into new services.

Imagine this question: the customer is an insurance company whose policy management system has run on-premises for years, and the ops team won't let anyone touch it. The customer wants an insurance claims triage service. You have 45 minutes and a whiteboard.

Many engineers will immediately draw a clean architecture: API gateway, microservices, a new database, then propose "migrating everything over gradually." In a regular software engineer interview, that answer might suffice. But for a Forward Deployed Engineer (FDE) role, it skips exactly the part of the work the job posting describes.

Praxent's FDE job posting explicitly requires cleanly integrating with the systems actually given, including legacy core systems, and states directly that you'll work within decisions others have already made.

So the sensible way to prepare is: assume the interviewer wants to see how you design around constraints, not how well you can imagine them away.

Why Is a "Clean Rewrite" the Wrong Answer?

Martin Fowler has warned against big-bang rewrites: they sound simple, but in his observation most such efforts fail. What he advocates is incremental modernization, which has a name: the Strangler Fig pattern.

According to Microsoft's Azure architecture documentation, the Strangler Fig pattern gradually replaces parts of an old system's functionality with new applications and services while the old system continues running the features not yet migrated. Its core mechanism is the façade: a proxy layer in front of the legacy backend that decides whether each request goes to the old application or a new service.

But every pattern has prerequisites. Microsoft notes that if you can't access the legacy system's source code and there are no other integration points that allow changes (such as the database), the Strangler Fig pattern may not apply. That's the first question to ask in the interview.

Ask Questions First, Then Draw

For the insurance question above, spend the first five minutes asking questions. Can the policy system's code be changed? If not, can its database be read? Which direction of connections does the internal network allow? Who approves access, and how long does it usually take?

That last question isn't filler. Appsierra, a company that provides FDEs to enterprises, believes that provisioning access, security reviews, and customer approvals often take longer than finding the engineer.

That's a vendor's perspective, not independent data. But if you build review time into your plan, it shows you know where real projects usually get stuck.

Suppose the interviewer answers: no code changes, the database can be read, and no inbound firewall rules can be opened. These three answers determine most of the architecture.

Worked Example: Building the Data Path Layer by Layer

Start with the network. When the firewall blocks inbound connections, deploy an Agent inside the customer's network that only makes outbound connections. This is exactly what Palantir Foundry does: an Agent inside the customer's network continuously polls Foundry over one-way outbound HTTPS connections to pick up tasks.

Its documentation now labels this Agent worker architecture as legacy, but the principle of opening no inbound ports is still worth following when sketching a design.

Next, capture events. Since you can't change the code, you can't insert calls like "send an event when a new claim arrives" into the application. For components you can't modify, Microsoft recommends capturing events directly from the database—for example, using change data capture (CDC) to read the transaction log—without touching application code at all.

The events are now in your hands, but they still carry the old system's shape. Microsoft warns that legacy schemas are often messy and their APIs outdated. Without an isolation layer, the new design will gradually absorb the old system's semantics. That isolation layer is called the anti-corruption layer (ACL).

Suppose the old claims table uses abbreviated column names, numeric status codes, and amounts stored as integers multiplied by 100. Only the ACL knows these conventions:

# ACL：把遗留记录转换为新服务的模型
STATUS_MAP = {"01": "submitted", "02": "in_review", "09": "closed"}

def to_claim(row: dict) -> Claim:
    return Claim(
        claim_id=row["CLM_NO"].strip(),
        policy_id=row["POL_REF"].strip(),
        status=STATUS_MAP.get(row["ST_CD"], "unknown"),
        amount=Decimal(row["AMT_X100"]) / 100,
    )

The triage service only handles

Claim

and never reads

ST_CD

. This is also the most labor-intensive part in reality: Appsierra describes FDE integration work as aligning the customer's real schemas, naming conventions, and data gaps with product requirements.

Finally, the façade layer. On day one, only one path is migrated to the new service; everything else still goes through the old system:

MIGRATED = {"/claims/triage"}

def route(path: str) -> str:
    return NEW_SERVICE if path in MIGRATED else LEGACY

To migrate another feature, you just add one line in

MIGRATED

; rolling back is just as simple.

Every Layer Has a Cost: Say It Proactively

Don't wait for the interviewer to ask—state the costs yourself. Microsoft notes that an ACL adds latency to calls between the two systems. If triage must return results immediately to an agent on the phone with a customer, that latency has to go into your budget.

If the old system runs in batches or is slow, there's another option: implement an event-driven ACL through queues such as Service Bus, Event Grid, or Event Hubs.

According to Microsoft, this frees the new system from the old system's throughput limits. The cost is that data arrives later and consistency is only achieved after a delay (eventual consistency)—say this explicitly.

The From-Scratch Answer

  • Draws a new architecture without asking anything
  • Proposes rewriting the entire system
  • Assumes inbound firewall rules can be opened
  • Reads the old schema directly in new services

The FDE Answer

  • First clarifies which integration points allow changes
  • Migrates functionality one piece at a time behind a façade layer
  • Deploys an Agent that only makes outbound connections
  • Transforms all data through an ACL and states the latency it adds

Pitfalls to Avoid

The first pitfall is applying the Strangler Fig pattern without checking its prerequisites. If the customer lets you touch neither the code nor the database, the façade layer has nothing to work with—in that case, say so directly instead of forcing the pattern.

Another pitfall is an ACL that exists only as a box in the architecture diagram. As long as any service outside the ACL reads the old status codes, legacy semantics have already leaked into the new system. And don't forget the people: if no one approves access, even the most elegant architecture stays on paper.

Career advice: when reading job postings, phrases like "legacy cores," "on-prem," and "existing systems" are good hints at what the system design interview will cover. On your resume, don't just list technologies—write sentences like "exported data from System X via CDC with zero code changes on the customer side," because that's exactly the integration work FDE job postings describe.

This week's exercise is simple: take the insurance question above, change one of the answers to "reading the database is not allowed," and solve it again. If you can still explain why the architecture must change, you're practicing exactly the capability FDE job postings look for.
