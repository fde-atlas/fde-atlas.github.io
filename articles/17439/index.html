Agentic Workflow: Agentic Workflow

Original title: 智能体工作流：Agentic Workflow

FDE中国 · 2026-08-14 · 2 min read

Summary

This card from FDEChina addresses a common delivery-time architecture choice: workflow versus fully autonomous agent. It argues that agentic workflows—where code defines the control flow and the model only makes local decisions (classification, extraction, generation, tool selection) within fixed nodes—should be the default starting point, since paths are enumerable, each node can be evaluated and regression-tested independently, failures can be localized, and acceptance criteria become negotiable. A key pitfall: listing steps in a prompt is not a workflow; if the model can skip or rewrite steps, control effectively reverts to the model and node-level evaluation assumptions break, usually discovered only during debugging. The author contrasts multi-agent systems, notes most enterprise scenarios suffice with workflows, and recommends drawing a node diagram with evaluation methods, starting with the costliest node.

Key points

  • Agentic workflows define control flow in code; models decide only within nodes.
  • Enumerated paths enable per-node evals, regression testing, and localized debugging.
  • Prompt-listed steps are not workflows if the model can skip or rewrite them.
  • Most enterprise scenarios need only workflows, not agent-level flexibility.
  • Practical advice: draw a node diagram and build evals starting with the costliest node.

Full text

This card answers the most common architecture decision in delivery: should you build a workflow or a fully autonomous agent. Core breakdown: in an agentic workflow, the control-flow skeleton is defined by code, and the model only makes local decisions within nodes—classification, extraction, generation, tool selection. The benefits are that paths are enumerable, each step can be evaluated separately with evals, failures can be traced to a specific node, and acceptance criteria become negotiable. The most common misuse is treating a list of steps in a prompt as a workflow: as long as the model has the authority to skip or rewrite steps, control flow reverts to the model, and all the assumptions behind per-node evals collapse—something you only discover during troubleshooting. Incremental judgment: Anthropic and other vendors publicly advocate "use a workflow, not an agent, whenever possible"; this card grounds that principle in FDE fieldwork—the demo the customer sees is often fully autonomous, so the delivery side must proactively pull autonomy back into a node-based design and use per-node evals to prove compliance before maintainability and handover can even be discussed. Action item: draw a node diagram for the process you are currently delivering, marking each node's model decision points, eval methods, and failure handling. Start building evals with the most expensive node.—FDEChina Editorial Team · Practitioner's Edition

Definition

An agentic workflow refers to a system architecture where the control-flow skeleton is predefined by code, with model decisions and tool calls interspersed at fixed nodes. The model's autonomy is confined within nodes, and the overall path is enumerable and regression-testable.

Deep Dive

The dividing line from fully autonomous AI agents lies in who holds control: in a workflow, "what comes next" is decided by code, and the model only handles local decisions within nodes such as classification, extraction, and generation; an agent hands path selection over to the model. For an FDE, workflows are the default starting point for delivery—each node can have its own eval set and its own regression tests, failures can be localized to a specific step, and acceptance criteria become negotiable. The common misuse is treating a list of steps in a prompt as a workflow: as long as the model can skip or rewrite steps, control flow effectively still belongs to the model, and all the eval assumptions for nodes fall apart.

Distinguishing from multi-agent systems: multi-agent setups emphasize dynamic allocation and collaboration of tasks across multiple roles, where communication protocols and failure arbitration become new sources of complexity; workflows hard-code the collaboration sequence into the orchestration layer. Field experience with customers is to first prove the value of each node, then consider whether agent-level flexibility is needed—most enterprise scenarios are fine stopping at a workflow.
