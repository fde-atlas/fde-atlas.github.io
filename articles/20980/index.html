Integrating WeCom, DingTalk, and Legacy ERP Systems: Hands-On Guide to Phase Two Integration in Enterprise AI Delivery

Original title: 打通企业微信、钉钉与 ERP 遗留系统：企业 AI 交付第二阶段接入实战

FDECareer.work · 2026-10-26 · 10 min read

Summary

This hands-on article tackles phase two of enterprise AI delivery: connecting LLM applications to collaboration platforms like WeCom and DingTalk while safely writing to legacy ERP systems. The author argues most engineering bottlenecks lie not in model inference but in callback timeout retries, platform rate limits, and identity-permission mismatches. It proposes four engineering rules—acknowledge first then process asynchronously, bind workbench identities to ERP permissions, restrict LLMs to extraction, and enforce idempotency keys—supported by a five-layer architecture, a 7-state state machine, four ERP bridging options, and a six-item go-live checklist.

Key points

  • Over 70% of delivery blockers are workbench integration and legacy ERP bridging, not inference.
  • Four rules: async after ACK, strict identity mapping, LLM extraction only, idempotent writes.
  • A 7-state machine forces query-before-retry on timeouts to prevent duplicate ERP orders.
  • Four bridging options: REST, SOAP/RFC, read-replica plus controlled writes, and file exchange.
  • Six go-live gates include callback storm tests, signature replay blocking, and privilege checks.

Among the high-paying delivery roles tracked in the 2026 China Enterprise AI Delivery and Forward Deployment Supply-Demand Panorama Report, over 70% of real engineering bottlenecks are not large model inference itself, but rather "one end must be embedded in the WeCom, DingTalk, or Feishu workbench that frontline employees open every day, while the other end must securely read from and write to a legacy Enterprise Resource Planning system (ERP) that went live a decade ago". If you synchronously call the large model and ERP write endpoints directly inside the callback interface, the system will trigger three cascading production incidents on day one: platform 5-second timeouts triggering three re-pushes that create duplicate tickets, group bots or app proactive pushes hitting rate limits (e.g., error code

45009

), and approval identities in workbench cards being disconnected from the ERP permission matrix, leading to unauthorized writes

。

As the sixth installment of our delivery practice series (corresponding to the core business flow pilot rollout in the Enterprise AI Project Delivery Trilogy, and best read alongside the dedicated-network boundary baseline in the 2026 White Paper on AI Delivery Architecture for Classified and Isolated Networks), this feature is based on the official WeCom and DingTalk developer documentation and distributed idempotency engineering standards. Through a clearly bounded synthetic teaching scenario, it fully breaks down the five-layer engineering architecture from workbench card interactions to idempotent persistence in a legacy ERP.

Key takeaways first: four iron rules for workbench integration and legacy system bridging

Before writing a single line of connector code, the team must lock in the following four engineering bottom lines:

  • Callback signature verification and "ACK first, process asynchronously" must be fully decoupled: Platforms like WeCom impose strict response deadlines on message callbacks (e.g., WeCom POST callbacks must respond within 5 seconds; if no response is received in time, the connection is dropped and retried up to 3 times). The gateway layer must first complete signature verification (msg_signature or x-ddpaas-signature) and deduplication by event unique key, write to a local persistent queue within milliseconds, and immediately return HTTP 200 — never synchronously wait for large model inference or a legacy ERP response inside the callback thread.
  • Strong binding mapping between workbench identity and ERP permission principals: An employee's UserID / unionid in WeCom or DingTalk is not the same as their financial or procurement ledger permissions in the ERP. The gateway layer must maintain deterministic identity mapping and row-level role-based access control (RBAC, Role-Based Access Control); using a "super admin account" with full table read/write permissions to run all employee requests is strictly forbidden.
  • Large models only do unstructured extraction; named approvals bind to payload hashes: The large model is only responsible for converting non-standard text from group chats or forms into structured drafts; the interactive approval card pushed to the supervisor must bind an exact business payload digest and policy version number, ensuring that "what the supervisor approves on the card" is byte-for-byte identical to "the parameters ultimately sent to the ERP".
  • Legacy system writes follow "unique business idempotency key + query-before-compensate on timeout": Facing network jitter on legacy SOAP (Simple Object Access Protocol) or REST interfaces, every write operation must carry a deterministically generated biz_request_id. Once a timeout occurs (outcome_unknown), blindly creating a new request is strictly forbidden; you must first query or reconcile by the original business key, and only compensate after confirming the write never landed.

Synthetic teaching scenario notes and the five-layer integration architecture

All WeCom and DingTalk platform mechanisms mentioned follow the publicly documented descriptions in their respective official developer documentation.

Enterprise workbench and legacy system bridging must not use the fragile chain of "frontend directly connecting to the model, model directly connecting to the database"; instead, it should be decoupled by responsibility into five independently evolving engineering layers:

Different collaborative office platforms differ significantly in callback modes, signature algorithms, timeout retry windows, and proactive push rate limits. On-site selection recommendations:

  • If the customer operates in an intranet or virtual private cloud (VPC, i.e., a logically isolated dedicated cloud network) environment that strictly restricts public inbound ports, and uses DingTalk or Feishu, prefer the official Stream / long-connection SDK mode, where an intranet container proactively establishes an encrypted long connection to the platform to pull events, avoiding the lengthy approval cycle of applying for a public fixed IP, configuring a reverse proxy, and setting up firewall inbound whitelists.
  • If the customer uses WeCom (Enterprise WeChat) and must receive messages via HTTP, be sure to deploy a minimal signature-verification and enqueue service (Ack-Gateway) separately at the DMZ gateway layer, doing only msg_signature verification, EncodingAESKey decryption, MsgId deduplication, and queue writes, ensuring 99.9% of requests return 200 OK within 50 milliseconds, completely avoiding the triple-retry storm triggered by the 5-second timeout.

Layer 2: Card callback signature verification, asynchronous decoupling, and idempotent state transitions

In approval or business-processing scenarios, the most dangerous step is the supervisor clicking the "Approve and write to ERP" button on the interactive card. If the network jitters, the supervisor double-clicks, or the platform automatically re-pushes due to a timeout, a system without guardrails will generate multiple duplicate purchase orders in the ERP.

Layer 4: On-site delivery acceptance checklist and public reference materials

Before handing over the workbench and ERP integration solution to the customer's operations team, verify each of the following 6 go-live gates:

  • Callback storm load test: simulate WeCom/DingTalk re-pushing the same event 3 consecutive times under network latency, and verify the gateway deduplication hit rate = 100% and downstream ERP writes strictly = 1.
  • Signature tampering and replay interception: request the callback interface with a wrong signature, an expired timestamp (e.g., deviating from the current time by more than 5 minutes), or a tampered encrypted payload, and verify the gateway returns rejection 100% of the time without enqueuing.
  • Timeout-unknown state (outcome_unknown) recovery drill: after the adapter successfully writes to the ERP, artificially discard the response to simulate a timeout, and verify the recovery task can recover the document number via the original biz_request_id and update the card without producing a second document.
  • Platform rate-limit backoff test: trigger 50 consecutive notification pushes, and verify the send queue smooths peaks via a token bucket (e.g., group chat bots strictly limited to ≤ 20 messages/minute) without triggering a platform-wide ban.
  • Identity privilege escalation test: simulate an ordinary employee crafting a card callback payload to attempt approving a high-value document, and verify the phase-two permission re-check accurately intercepts it and records an audit alert.
  • One-click degradation switch verification: After the AI extraction or auto database-write switch is turned off in the admin console, the system can smoothly degrade within 10 seconds to a "pure manual form filling + original ERP entry" mode without affecting business continuity.
