FDE Customer Data Onboarding: SQL, ETL, and Reconciliation in Practice

Original title: FDE 客户数据接入：SQL、ETL 与对账实战

FDE Times · 2026-10-08 · 5 min read

Summary

This guide argues that customer data ingestion is a core FDE skill, not a chore. Using a water utility pump-failure prediction example, it walks through reconciling inconsistent asset codes (PUMP-07 vs P7) across a maintenance CSV and a Postgres sensor table. It cites Tagup's job listing listing SQL, ETL and integration as hard skills, Palantir's FDSE requirements, and MIT NANDA research attributing failed enterprise AI pilots to fragmented data. The proposed five-step process: inventory sources, profile data, map keys, reconcile, hand off. Unmatched records go into an exception file for customer confirmation, and every pipeline run must print reconciliation metrics like match rate.

Key points

  • Tagup lists SQL, ETL and system integration as hard skills for FDEs.
  • MIT NANDA research links failed AI pilots to fragmented enterprise data.
  • Five-step process: inventory, profiling, key mapping, reconciliation, handoff.
  • Unmatched rows go to an exception file for customer confirmation, never silently dropped.
  • Every pipeline run should print match rates against real sensor IDs.

Engineers often treat data ingestion as cleanup grunt work, but Tagup lists SQL and ETL as hard skills, and enterprise AI pilots often fail because of fragmented data.

Key Takeaways

  • Tagup lists ETL and systems integration as hard skills for FDEs, and Palantir requires candidates to have experience with large-scale data, or at least interest in it.
  • Enterprise AI pilots often fail because data is scattered across multiple siloed systems that are hard to integrate. It falls to the FDE to bridge that gap.
  • The process has five steps: inventory data sources, data profiling, key mapping, reconciliation, and handoff.

In your first week on-site with the customer, you open the data exported from their maintenance system. The equipment code column reads "PUMP-07", but the sensor database says "P7". The demo is scheduled for Friday morning. You need a way to recognize that these two names refer to the same pump, otherwise not a single line of code will run.

Many engineers treat this phase as "cleanup work" to grind through before the interesting part begins. Job descriptions tell a different story. Tagup's Forward Deployed Engineer (FDE) job posting explicitly lists one of the role's tasks: ingesting the imperfect data that the customer's actual business still depends on. The same posting lists Python or TypeScript, SQL, ETL, and systems integration as hard skills.

Citing research from MIT NANDA via The New Stack, Paraform points out that enterprise AI pilots fail largely because company data is scattered across multiple siloed systems that are hard to integrate.

The Pulse newsletter from The Pragmatic Engineer describes today's FDE this way: integration work and hands-on customer support make up the bulk of the job, with little greenfield system building. If that holds, data ingestion is a skill you should sharpen before sending out your resume.

Why does data reveal the real problems?

Palantir created this role in the early 2010s, and internally calls these engineers Delta. According to the company's job posting, Forward Deployed Software Engineers (FDSEs) work directly with customers to quickly figure out their biggest problems. They work in small teams with minimal oversight and own critical projects end to end.

Since you own projects from start to finish, the first thing you encounter is almost always the customer's data. In a small team with minimal oversight, there is usually no separate data engineering team to do this part for you.

The same posting also requires candidates to have experience solving high-value business problems with large-scale data, or interest in doing so.

There is a deeper reason behind this. Mismatched equipment codes often mean two departments have never needed to share data. Figuring out why a join fails also means understanding part of how the customer's organization operates.

Paraform describes the FDE as a combination of software engineering and customer deployment. Data ingestion is exactly where these two halves meet.

Example: two systems, one pump

Start with data profiling; the data pipeline can wait. A simple SQL query shows how far apart the two data sources are (the alias

means "work order count"):

order_count

The comment asks: how many codes in the maintenance system have no match on the sensor side? Suppose almost none match. This doesn't mean the data is dirty—just that the two systems name things differently. The next step is to normalize both sides to a common key, convert timestamps to the same time zone, and join again:

-- 维修系统中有多少资产编码在传感器端找不到对应？
SELECT w.asset_code, COUNT(*) AS order_count
FROM work_orders w
LEFT JOIN sensor_devices s ON s.device_id = w.asset_code
WHERE s.device_id IS NULL
GROUP BY w.asset_code
ORDER BY order_count DESC;

The key is in the last two lines. The rule "take the digits at the end of the code" is only your assumption. Work orders that fail to match a sensor must be handed to whoever owns this data on the customer's side for confirmation—they cannot be silently dropped. Here the file is

A process you can run yourself

Start with an inventory: what data sources exist, who owns each one, how the data is exported, and how often it updates. Then profile each one: count nulls, look at value distributions, and try joining the keys. Only after you understand where things fail to match should you define the canonical schema and shared key.

Next, write the mapping rules as explicit code, with an exception file, and get sign-off from someone on the customer's side. Every pipeline run must print reconciliation results, so the match rate is always based on the latest data.

At handoff, the documentation should state every rule and the reason it exists, so whoever takes over doesn't have to guess.

When reading job descriptions (JDs), watch for terms like ETL, integration, "imperfect data", or "large scale data". They tell you where your time will go. If a JD only talks about models and says nothing about customer data, ask about it in the interview.

On your resume, a line like "integrated data from three systems in two weeks, raising the key match rate to a level the customer accepted" carries far more weight than "proficient in pandas". You can also put a small repo in your portfolio: two public datasets that don't match, an exception file, and a reconciliation step.

A repo like that is concrete evidence that you've done the work these JDs describe.

On demo day, the customer won't remember what algorithm your model used. What they'll remember is the first time they saw the same pump's maintenance work order and sensor signal on the same screen.
