SWE-agent (2024) Explained for FDEs

FDE Interviews · 2026-10-17 · 4 min read

Summary

A Princeton team built SWE-agent around the idea that LLM agents need a purpose-designed tool layer, which they call an agent-computer interface (ACI). With GPT-4 Turbo, it resolved 12.5% of real GitHub issues on SWE-bench, versus 3.8% for the best prior non-interactive approach; the same model with only a shell scored 11.0%, rising to 18.0% with the ACI on the Lite subset. Ablations show compact search summaries beat paginated results, rejecting syntax-breaking edits added about three points, and showing whole files or full history hurt performance. Failed runs were slower and costlier (21 steps, $2.52) than successful ones (12 steps, $1.21). For FDEs, the lesson is that tool design deserves as much effort as prompting: summarize outputs, validate inputs, and return actionable errors.

Key points

  • Compact search summaries beat showing results one at a time
  • Syntax-checking guardrails alone added about three points
  • Failed runs averaged 21 steps and $2.52, costlier than successes

The paper in one minute

Human engineers do not fix bugs in a raw terminal. They use editors with search, syntax highlighting and linting. The Princeton team asked whether language model agents also need tools built for them, and found the answer was a clear yes.

They call the tool layer an agent-computer interface (ACI): the commands an agent can run and the format of what comes back. SWE-agent's ACI is deliberately small.

find_file

and

search_dir

return a short summary of where a term appears, and refuse when there are too many hits, asking for a narrower query. A file viewer shows 100 lines at a time with line numbers and how many lines are above and below. An

edit

command replaces a range of lines, shows the result, and runs a linter; if the edit introduces a syntax error, it is rejected and the agent is told why. Plus the usual shell for running code and tests.

On SWE-bench, which asks agents to resolve real GitHub issues in real Python repositories and checks the result with the project's tests, SWE-agent with GPT-4 Turbo resolved 12.5% of issues. The best earlier approach, which retrieved files and generated a patch without interacting with the repository, resolved 3.8%. On the 300-issue Lite subset, the same model with only a shell resolved 11.0%; with the ACI, 18.0%.

The ablations are the lasting contribution: they show which interface choices help and which hurt, with the model held fixed.

Research notes: the problem, approach and results

SWE-bench Lite issues resolved by the same model with SWE-agent's interface against a plain shell

chance an edit eventually succeeds, at the start and after one failed attempt

median cost of a successful run (12 steps); failed runs averaged $2.52 and 21 steps

Agents given a Linux shell struggled with real software tasks: verbose output flooded their context, editing with sed or redirection was error-prone, and one mistake cascaded.

Design an agent-computer interface (ACI): a few simple commands for finding, viewing and editing code, concise feedback after each action, and a syntax check that rejects broken edits.

State of the art on SWE-bench at the time (12.5% of real GitHub issues resolved, against 3.8% before), and ablations showing which interface choices mattered.

Why it matters to an FDE

Most agent projects start by picking a model and wiring up the customer's existing APIs as tools. This paper says the tools themselves deserve as much design effort as the prompt, and shows what good tool design looks like.

Feedback format changes behavior. A search command that showed results one at a time, like an editor's find-next, made the agent page through every match and burn its budget. It scored worse than having no search command at all (12.0% against 15.7%). A search that returned a compact summary scored best. Customer APIs that return pages of JSON need the same treatment: summarize, cap and tell the agent how to narrow its request.

Guardrails stop cascades. Rejecting edits that break syntax, with a clear message, added three points on its own. After one failed edit, the chance of eventually succeeding fell from 90.5% to 57.2%. Validate tool inputs before they change anything, and return actionable errors.

Less context can be better. Showing whole files instead of a 100-line window cut performance from 18.0% to 12.7%; keeping the full history rather than the last five observations cut it to 15.0%. More information is not more help.

Failure is slow and expensive. Successful runs finished at a median of 12 steps and $1.21; failed runs averaged 21 steps and $2.52, and 93% of successes submitted before hitting the budget. Raising the budget mostly buys more expensive failures.
