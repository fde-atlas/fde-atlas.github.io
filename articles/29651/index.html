Unsloth Fine-Tuning Tutorial: QLoRA VRAM Estimation and GGUF Deployment

Original title: Unsloth 微调教程：QLoRA 显存估算与 GGUF 部署

FDE Times · 2026-10-26 · 4 min read

Summary

This tutorial walks forward deployed engineers through fine-tuning models on customer hardware with Unsloth, using a logistics company's ticket-classification scenario where data cannot leave the intranet. It explains how QLoRA's 4-bit quantization cuts an 8B model's weights from roughly 16GB to about 4GB, fitting a single T4 GPU, and how the choice between GGUF (with Ollama or llama.cpp) and vLLM depends on expected concurrency. It also flags two delivery pitfalls: mismatched chat templates and mixed licensing (Apache 2.0 core, AGPLv3 for Studio and CLI), and urges benchmarking on the customer's actual hardware rather than trusting vendor numbers.

Key points

  • QLoRA quantizes the base model to 4-bit, saving about 75% memory; an 8B model's weights drop from ~16GB to ~4GB.
  • Unsloth enables training inside the customer's infrastructure, suitable when data cannot be sent to external APIs.
  • Export format follows usage: GGUF with Ollama for single-device use, vLLM for many concurrent users.
  • Delivery pitfalls: inference must use the same chat template as training, and Studio/CLI files are AGPLv3 while the core is Apache 2.0.
  • Vendor speed claims (2x from Unsloth, 2.5x from NVIDIA) vary by conditions; benchmark on the customer's real hardware first.

Unsloth claims to reduce VRAM usage by 70%, enabling training of small models on a single T4, and exporting to formats that can run on customer machines.

Key Takeaways

  • The Unsloth documentation states that fine-tuning is possible on Colab, Kaggle, or a personal computer with only 3GB of VRAM; QLoRA quantizes the base model to 4-bit, saving about 75% of VRAM.
  • Trained models can be exported as GGUF and run with Ollama or llama.cpp; when there are many users, vLLM can be used for serving.
  • Before delivering to a customer, check the chat template and licenses: the core is under Apache 2.0, while Studio and CLI are under AGPLv3.

The 16-bit weights of an 8B model take up about 16GB, and that's before accounting for the VRAM needed for training. If the customer only gives you a single mid-range GPU, this math alone could stop the project at the first meeting. Unsloth targets exactly this bottleneck.

The official Unsloth repository states that the tool doubles training speed and reduces VRAM usage by 70%, and works for LLMs, diffusion models, TTS, and even embedding models. In a post in NVIDIA's RTX AI Garage blog series, Unsloth is described as one of the most widely used open-source LLM fine-tuning frameworks in the world.

For a Forward Deployed Engineer (FDE), the appeal isn't speed. What matters more is that you can train on the customer's own infrastructure, then export the model into a format that runs on customer machines, with data never leaving the customer's environment.

When should you use it?

Imagine a logistics company that wants to automatically classify customer support tickets. It has a few thousand labeled tickets, but internal policy forbids sending that data to external APIs. It has a server with a single T4, and wants the model to run on that machine.

This is exactly the scenario Unsloth is suited for. When data can't leave the premises, prompt engineering on a hosted large model is off the table. A small model without fine-tuning usually can't understand the customer's terminology for various issues. What you need is a small model that has learned the customer's terminology and can run on existing hardware.

The first step is checking the hardware. The Unsloth documentation requires a GPU with CUDA compute capability of at least 7.0, covering the V100, T4, Titan V, RTX 20 and 50 series, A100, H100, L40, and more. The customer's T4 is on the list. If the customer has an older card, you need to find that out before making any commitments.

Doing the VRAM math by hand

The documentation distinguishes between two approaches. LoRA keeps the base model at 16-bit with no quantization. QLoRA quantizes the base model to 4-bit, saving about 75% of VRAM.

Applied to the example above: 8 billion parameters at 16-bit means 2 bytes per parameter, so weights alone are about 16GB. Subtract 75%, leaving about 4GB, with the rest of the GPU's memory reserved for activations and the adapters being trained.

This rough calculation is enough to tell the customer at the first meeting whether their hardware will work.

The documentation also recommends beginners start with a small instruct model like Llama 3.1 (8B) and experiment gradually. This advice is very practical for an FDE: small models train fast, so you can run several rounds of experiments in the first week instead of waiting days for each one.

If you just want to validate an idea, the documentation says you can fine-tune for free on Colab or Kaggle, or use a personal computer with only 3GB of VRAM.

The export format determines where the model lives

The Unsloth repository states that models can be exported as GGUF, NVFP4, and FP8. Which one to choose depends on how the customer will use the model.

The documentation splits this into two clear paths. If the model runs on a single device, use llama.cpp to convert it to GGUF and run it in Ollama, llama.cpp, or LM Studio. If many users call the model simultaneously, such as in an enterprise system, the documentation recommends vLLM.

In the logistics company example, if only one support team uses the model on a single server, GGUF plus Ollama is enough and easy to deliver. If later the whole company needs to call it via API, you'll have to switch to vLLM and replan. Ask the customer this question before training starts, because it determines both the export format and how to run evals on performance.

Two pitfalls at delivery time

The first pitfall is the chat template. Unsloth's GGUF export guide emphasizes that inference must use the same chat template as training. If the two don't match, the model's performance on Ollama or vLLM will degrade.

This kind of bug can make the model work perfectly on your laptop but give irrelevant answers on the customer's server, and troubleshooting it can eat up an entire afternoon.

The second pitfall is licensing. Unsloth's core is under Apache 2.0, but

studio/*

and

unsloth_cli/*

files are under AGPLv3. When packaging anything for a customer, be clear about which parts you used.

Talking to the customer's legal team before putting Studio or CLI into a product is far easier than ripping it out later.

Don't trust the numbers, test them yourself

Speed figures from various sources don't agree. The repository claims a 2x speedup, while NVIDIA says Unsloth speeds up the Hugging Face transformers library by 2.5x on NVIDIA GPUs. Both numbers were measured under their own conditions, not on your customer's data and GPUs.

So before putting any number on a slide, run it on the customer's real hardware. Record VRAM usage, training time, and quality on a fixed test set.

This is also the most resume-worthy content. For example, "Fine-tuned an 8B model with QLoRA on a single T4, exported as GGUF and run on Ollama, improving classification accuracy from X to Y" — a single line like this shows a hiring manager that you took a project from data all the way to deployment.

The learning order is: first LoRA and QLoRA, then chat templates, and finally export formats. That last step is where your model connects to the customer's real infrastructure, so don't cut corners there.
