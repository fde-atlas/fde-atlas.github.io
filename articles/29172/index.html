Business-Interview

Original title: Business-Interview

FDE中国社区 · 2026-07-12 · 4 min read

Summary

This is a skill document from the FDE China community describing Business-Interview, a structured method for business interviews and requirement clarification. It addresses the problem that customers usually state solutions rather than problems, so FDEs who take requests at face value build the wrong system. The framework structures interviews as background, pain points, current process, success criteria, constraints, and samples, using techniques like 5 Whys, process walkthroughs, exception probing, and value quantification. It specifies inputs/outputs, a five-step execution flow (45-60 minute interviews, same-day written minutes confirmation), common mistakes, role division with AIBP and business owners, and stage gates from PoC preparation to retrospective assetization. Outputs feed problem trees, process mapping, and PRD generation; a manufacturing quality-inspection case shows PoC scope narrowing from a vision AI platform to single-line AOI assistance.

Key points

  • Customers state solutions, not problems; taking requests directly leads to wrong systems.
  • Interview structure: background, pain points, process, success criteria, constraints, samples.
  • Techniques: 5 Whys, process walkthrough, exception probing, value quantification.
  • Run 45-60 minute interviews and confirm minutes in writing the same day.
  • Outputs feed Consultative-Problem-Solving, Process-Mapping, and PRD-Generator skills.

Problem Definition

Customers often describe solutions rather than problems; if the FDE takes requirements at face value, the wrong system gets built.

Methodology Framework

Interview structure: Background → Pain points → Current process → Success criteria → Constraints → Samples. Techniques: 5 Whys, process walkthroughs, probing edge cases, quantifying value.

FAQ

Q1: When running [Business-Interview], how do you avoid "asking only about features, not processes"?

A: Follow the README methodology step by step and showcase interim deliverables in weekly Demos; if PoC materials are incomplete, first produce a "to-be-validated list" before proceeding.

Q2: What additional constraints apply in private deployment/Xinchuang/MLPS environments?

A: Specify the deployment model explicitly in the prompt constraints section; when data cannot leave the domain, domestic components, or audit logs are involved, reference Private-Deployment-Gateway and RBAC-Audit accordingly.

Q3: What if the division of responsibilities with the AIBP is unclear?

A: Return to the AIBP-Collaboration-Playbook to update the RACI; AIBP is responsible for Ground Truth and business acceptance, while the FDE is responsible for deliverable technical assets.

Q4: After the PoC passes, how do we transition to Beta/production?

A: Mark the next-stage Skill in the deliverables (e.g., RAG-Evaluation→Private-Deployment-Gateway→FDE-Adoption-Growth), and trigger the launch gate via the checklist.
