Power Industry FDE: GIS and SCADA Data Reconciliation

Original title: 电力行业 FDE：GIS 与 SCADA 数据对账

FDE Times · 2026-11-05 · 5 min read

Summary

This guide explains why GIS and SCADA data often disagree at electric utilities: GIS captures the grid as designed, while SCADA captures it as currently measured, so mismatches are structural rather than bugs. It recommends using CIM (IEC 61970/61968) to map which team owns which data, building an asset-ID-to-SCADA-tag crosswalk, and classifying discrepancies as missing links, intentional switching, or field-check items before building object models and dashboards. A worked example reconciles a feeder with 40 switches, and a PNNL report on ADMS deployments is cited on integration being the biggest challenge.

Key points

  • GIS stores design state; SCADA stores measured state, so mismatches are expected.
  • CIM's IEC 61970/61968 scoping hints at which team owns each dataset.
  • Build an ID crosswalk first, then classify mismatches into three categories.
  • A PNNL report names systems integration as the top ADMS deployment challenge.
  • Reconcile and model objects before building any dashboards.

GIS records how the grid is designed to operate, SCADA records how the grid is operating right now; telling the two apart can save you weeks of wasted effort.

Key Takeaways

  • At power utilities, GIS stores the grid as designed, SCADA stores the grid as operated; mismatches between the two are common
  • CIM (IEC 61970/61968) provides a common vocabulary for grid objects, and its scope divisions also hint at which data belongs to which team
  • Reconcile and classify inconsistencies first, then build the object model, and only then build dashboards

In your first week at a power utility, you'll be handed three files: a GIS export, a SCADA point list, and an asset register. The task sounds simple: link the three files and draw one feeder. By the afternoon, you find a switch that is open in one file and closed in another, and no one in the meeting room seems surprised.

No one is surprised because this isn't an accidental error—it's a structural feature of the industry. A 2016 PNNL report on Advanced Distribution Management Systems (ADMS) concluded that data models in utility geographic information systems (GIS) are often incomplete, inaccurate, or both; the report also noted that integration between operational systems is the biggest challenge in deployment.

If you enter a power utility with the mindset "there's a schema, so we can join," you'll likely spend two weeks fixing things that were never broken. The alternative is to learn a few industry concepts in advance and ask the right questions from the very first requirements interview.

GIS and SCADA do not describe the same state

GE Vernova describes this divide well. On one side is the grid design and mapping team: they use GIS to plan and update the grid's normal state, in a silo of their own. On the other side are operations staff in the dispatch control room: they monitor the grid's real-time state in another silo.

So GIS answers "how should the grid operate by design," while SCADA answers "how is the grid operating right now." When operators isolate a line segment for maintenance or load transfer, the two are supposed to differ. Other inconsistencies are genuine errors: GIS not updated in time, or a wrong ID mapping table.

1Spatial describes a classic case from the utility industry: GIS shows a valve as closed, while SCADA reports it as open. Swap "valve" for "switch" and you have that afternoon at a power utility.

Before you write a schema, CIM already gives you a vocabulary

The power industry has long had a common language. The Common Information Model (CIM), defined by the IEC 61970-301 standard, is an abstract information model describing the major objects in an electric utility. It represents power system resources as object classes with attributes, enabling independently developed applications from different vendors to integrate with each other.

For a Forward Deployed Engineer (FDE), CIM's most useful feature is how it divides its scope. According to the CIM Users Group, IEC 61970 covers power system modeling and data exchange, including Energy Management Systems (EMS), topology, conductors, and SCADA. IEC 61968 covers models related to distribution networks: Distribution Management Systems (DMS), assets, work, GIS, metering, and messaging between applications.

The customer may not implement CIM strictly, but this division is still worth using as a map. It gives you a list of terms you can use directly when talking to power engineers.

It also hints at which data likely belongs to which team: operations, or assets and mapping. When a data field looks absurd, knowing who owns it solves half the problem.

Example: reconciling one feeder

Imagine a feeder with 40 switches. GIS uses

SW-0412

asset IDs like this, with another field recording the normal state. SCADA uses

F07_SW412_POS

tag names like this, where a value of 1 means closed. Neither system stores the other's key, so the first step is to build a cross-reference table mapping asset IDs to tags.

Next, consolidate each device into a single object, keeping the two states separate, down to the field names:

from dataclasses import dataclass

@dataclass
class Switch:
    asset_id: str               # 来自 GIS 的键
    scada_tag: str | None       # 从对照表中获取
    normal_open: bool           # 设计状态（GIS）
    measured_open: bool | None  # 量测状态（SCADA）

def classify(sw: Switch, switching_orders: set[str]) -> str:
    if sw.scada_tag is None or sw.measured_open is None:
        return "missing_link"
    if sw.normal_open == sw.measured_open:
        return "match"
    if sw.asset_id in switching_orders:
        return "intentional_switching"
    return "needs_field_check"

Parameter

switching_orders

is a list of devices with recent switching orders, which you need to request from the dispatch control room. Without this list, every routine load transfer gets counted as an error.

Suppose the reconciliation result is: 31 devices match, 4 lack a mapping, 3 are inconsistent due to intentional switching, and 2 need field verification. Rather than reporting "GIS has 9 errors," bring three separate lists to three different people.

The 4 missing mappings are your job, together with the integration team. The last 2 belong to the mapping team, and someone may have to go look at the pole in person.

Build the object model first, dashboards later

Palantir describes a case with a European power utility. The company's geographic asset system and grid system were independent of each other, so it lacked a complete, up-to-date panoramic view of grid state. The solution was to model the grid topology as Ontology objects and views, representing each network element.

This lesson is tool-agnostic. Devices, lines, and connections must first become explicit objects; dashboards and predictive models come later. If you build charts on unreconciled joins, you're just making existing inconsistencies look prettier.

So the order of work on-site at the customer is fairly clear:

  • Place each system within the scope of 61970 or 61968, and note its owner.
  • Clarify whether each state field is "normal" or "measured."
  • Build an ID cross-reference table between asset IDs and SCADA tags.
  • Run the classification step, then hand each inconsistency list to the corresponding team.
  • Lock the object model only after both the mapping team and the dispatch control room have confirmed.

Common pitfalls

The most common pitfall is treating GIS as the single source of truth and overwriting it with SCADA states, or vice versa. The two fields describe different things, so both must be kept. The second pitfall is assuming a device has only one ID, when in reality each silo usually encodes things its own way.

The third pitfall is harder to spot: speaking generic software jargon to power engineers. Ask "is this record stale?" and they'll struggle to answer; ask "is this the normal state or the measured state?" and they'll answer immediately. Using their vocabulary is the fastest way to earn trust.

For career development, when reading FDE job descriptions in the energy industry, you can use the terms in this article (CIM, IEC 61968/61970, ADMS, GIS, SCADA) as a checklist. Don't just write "data integration" on your resume.

Be specific about which systems you've reconciled topology between and how you classified inconsistencies. The PNNL report lists integration between operational systems as the biggest challenge, so this kind of experience deserves top billing.

At a power utility, someone who understands why two files don't match is more valuable than someone who can join them.
