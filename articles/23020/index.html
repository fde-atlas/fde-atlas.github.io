[LLMOps] Developing the Tracing Infrastructure That Supports FDE Development

Original title: 【LLMOps】FDEの開発を支えるトレーシング基盤の開発

Zenn · 2026-11-02 · 9 min read

Summary

AI Shift's AI team built a tracing infrastructure to support FDEs who develop diverse AI agents for customers of its AI Worker Platform. Because instrumentation is low priority for FDEs focused on customer problems, execution histories were often missing when it came time for evaluation. The team made LLM calls go through an LLM Gateway (Agent Router, formerly Envoy AI Gateway), which automatically emits telemetry—inputs, outputs, model names, token counts—via OpenTelemetry to a Collector, which forwards LLM-related data to Langfuse. Business-semantic data the gateway cannot capture (trace context propagation, LLM purpose, user/session metadata) is handled by a custom Tracing SDK in Python and TypeScript, plus an AI agent Skill so coding AI can do the instrumentation, reducing FDE workload.

Key points

  • FDEs deprioritize instrumentation, so execution histories were often missing for evaluation.
  • An LLM Gateway (Agent Router) automatically collects telemetry at the infrastructure level.
  • OpenTelemetry Collector aggregates data and sends LLM-related traces to Langfuse.
  • A custom Tracing SDK adds business semantics like purpose, user and session metadata.
  • An AI agent Skill lets coding AI handle SDK instrumentation, easing FDE workload.

Hello, I'm Hayashizaki (@u_hyszk) from the AI team at AI Shift.

After introducing an AI agent, have you ever reached the stage of "it's time to evaluate and improve," only to find that there was no platform in place to collect execution histories for evaluation? Or have you ever wanted to collect execution histories but didn't know how, so it got deprioritized?

In this article, we introduce the mechanism created by our FDEs (Forward Deployed Engineers), who develop a wide variety of AI agents and applications for customers adopting AI Worker, in order to record and make use of execution histories.

Collecting Execution Histories for Evaluation and Improvement

One of the AI team's missions is to figure out how to maintain the output quality of AI agents and demonstrate cost-effectiveness to customers while FDEs develop a wide variety of AI agents and applications. In this article, we focus on the "collecting execution histories" part, which is a prerequisite for evaluation and improvement.

To evaluate and improve an AI agent after its introduction, execution histories of how the agent behaved are required. Many LLM engineering platforms such as Langfuse and Arize Phoenix collect data called telemetry using OpenTelemetry, a framework for achieving observability. The key terms are as follows.

  • Telemetry: Data emitted from a system and its operations. In addition to traces (described below), it consists of metrics, which are measurements of availability and performance, and logs, which are timestamped text records.
  • Trace: A record of the entire processing of a single request, structured as a tree.
  • Span: A single unit of work or operation within a trace.

To collect telemetry, you need to perform "instrumentation", which involves embedding code into the target application to output telemetry data.

Toward Easy and Reliable Collection of Execution Histories

Collecting execution histories is essential for evaluating and improving AI agents. If execution histories are collected early on, it can be expected that requirements gathering for evaluation will proceed smoothly.

On the other hand, for FDEs who should focus on solving customer challenges, instrumentation is often deprioritized. This is because applications work normally even without instrumentation, so it's not urgent, and deciding how to implement instrumentation each time is burdensome.

Against this background, we determined that we needed to systematize the method of collecting execution histories in order to:

  • Eliminate missed collection of execution histories in built applications
  • Standardize the collection method
  • Improve the FDE development experience and allow them to focus on solving customer challenges

we decided we needed to systematize a way to collect execution history for that purpose.

A Tracing Platform to Support FDE Development

The overall architecture of the system we built is as follows.

Tracing platform (repeated)

We had developers use the LLM Gateway when calling LLMs, so that telemetry is collected at the infrastructure level. For data containing business-specific meaning that cannot be collected by the LLM Gateway alone, we perform manual instrumentation using an SDK and Skills. The collected telemetry is aggregated in an OpenTelemetry Collector, after which only the telemetry related to LLM calls is sent to Langfuse, our LLM engineering platform.

Automatic Telemetry Emission via LLM Gateway

We made it so that LLM Gateway is used when calling LLMs. This LLM Gateway records inputs, outputs, model names, token counts, and more, and automatically emits telemetry to the OpenTelemetry Collector. After that, only the telemetry related to LLM calls is sent to Langfuse.

In this way, by performing collection at the infrastructure level with the LLM Gateway, it becomes possible to automatically collect telemetry data without leaving the decision of whether to instrument up to the FDE.

This time, we use Agent Router (formerly Envoy AI Gateway) as the LLM Gateway. Agent Router supports tracing via OpenTelemetry, which can be enabled by specifying environment variables. An example configuration with Docker Compose is shown below.

services:
  aigw:
    image: docker.io/envoyproxy/ai-gateway-cli:v1.1.0
    command: run
    ports:
      - 127.0.0.1:1985:1975
    environment:
      OPENAI_API_KEY: ${OPENAI_API_KEY:-}
      OTEL_SERVICE_NAME: aigw
      OTEL_TRACES_EXPORTER: otlp
      OTEL_METRICS_EXPORTER: none
      OTEL_LOGS_EXPORTER: none
      OTEL_EXPORTER_OTLP_ENDPOINT: http://otel-collector:4318
      OTEL_EXPORTER_OTLP_PROTOCOL: http/protobuf
      AI_GATEWAY_TRACING_SEMCONV: openinference
    depends_on:
      - otel-collector

Challenges of Instrumentation with the LLM Gateway

While telemetry collection via the LLM Gateway is convenient, it has the challenge that data requiring business-level semantic context cannot be collected at the application level. Specifically, the following kinds of data cannot be collected:

  • Headers indicating the flow of processing within the application (traceparent)
  • Data representing the purpose of LLM usage, such as search, tools, or ranking
  • Metadata and tags representing users and sessions

Regarding the first point, because the application does not perform context propagation, the LLM Gateway regenerates a new trace each time, resulting in the problem that an independent trace of depth 1 is generated for each LLM call. In complex use cases, this makes data analysis and evaluation difficult.

As for data requiring business-level semantic context, it is inherently difficult to collect it at the LLM Gateway, so we decided to also use manual instrumentation with the SDK and Skill.

Manual Instrumentation with the Tracing SDK and Skill

With the goal of adding business-level semantic context to the traces created by the LLM Gateway, we developed a dedicated Tracing SDK. The scope of this SDK is as follows:

  • Integration with the LLM Gateway
  • Structuring and standardizing traces with business-level semantics
  • Attaching and propagating data representing the purpose of LLM usage
  • Attaching and propagating metadata and tags such as user and session identifiers

Instrumentation of the LLM calls themselves is out of scope, since the LLM Gateway handles that. By having instrumentation done through this SDK, it becomes possible to collect high-quality data that is easy to use for analysis and evaluation.

Furthermore, to reduce the development burden on FDEs, we created a Skill for AI agents to perform instrumentation with the Tracing SDK. By using this Skill, instrumentation can be delegated to coding AI, greatly reducing the implementation burden.

By building this kind of systematization,

  • the LLM Gateway eliminates collection gaps
  • the SDK and Skill standardize instrumentation
  • the SDK and Skill improve the FDE development experience

and thus the series of objectives is achieved.

As a demo, we created an AI agent that searches FAQs and answers questions. The input query goes through a simple LLM-based guardrail, and the output is evaluated using LLM-as-a-Judge.

Langfuse screen

You can see that the LLM calls are collected in a cleanly structured form. Also, because metadata and other information were attached via the SDK, user and session information, as well as the purpose for which the LLM was called (guardrails, evaluation, etc.), are also visualized.

By collecting data in such an organized form, it becomes easier to leverage it for subsequent agent evaluation and data analysis. Even if instrumentation with the SDK is accidentally omitted, the LLM calls are still recorded by the LLM Gateway, so minimal data analysis and evaluation requirements can still be defined.

Conclusion

In this article, we introduced the system we built for customers adopting AI Workers, designed to help FDEs who develop a wide variety of AI agents and applications record and leverage execution histories.
