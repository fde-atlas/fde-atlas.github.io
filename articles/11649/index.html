The paper in one minute

Most context-folding methods were designed for one long task with one goal: research a question, fix a bug. They summarize old steps and throw the originals away. Jin Su, Runnan Fang, Fajie Yuan and colleagues at Zhejiang University, Alibaba's Tongyi Lab and Westlake University looked at a different setting: an agent talking with a user over many turns, calling tools, while the user adds requests and changes their mind. There, they found two failures. Summaries drop fine-grained constraints that matter later, and they fail to track the user's current intent.

Their opening example: a user picks an aromatherapy store whose tool record says it opens at 12:00, then asks to book "Saturday 11 AM, or 2 PM if that's not possible." A vanilla folding summary kept the store name and packages but lost the hours, so the agent booked 11 AM.

U-Fold never discards. It stores the full dialogue and every tool call and result. On each new user message, it rebuilds the agent's working context with two extra model calls. The Conversation Summarization module rewrites a chronological summary that tracks goals, constraints and changes of mind, and ends with a to-do list of what is still pending. The Dynamic Data Extraction module reads that summary plus the entire tool history and selects the observation lines that matter, by line range, along with verbatim facts, constraints and a hint for the agent. The main agent then runs its usual ReAct loop on summary, extracted data and the new message.

On τ-bench, τ²-bench and VitaBench with five backbones, U-Fold beat ReAct in most cells by a few points and beat the summarize-and-discard baselines by much more, especially when tool outputs were long and noisy.

Context folding methods summarize and discard history to fit a budget. They were built for single-goal tasks. In multi-turn customer dialogues, summaries drop fine-grained constraints (opening hours, quantities, IDs) and lag behind a user who changes their mind, so the agent acts on stale or incomplete facts.

Why it matters to an FDE

Customer-facing agents are multi-turn by nature: booking, ordering, support, account changes. These are the deployments where a dropped constraint becomes a wrong order and a refund.

Don't let a summary be the only copy. U-Fold's core move is to keep the raw history and treat every summary as a disposable view. Any deployment can adopt this. Store the full log, and rebuild the working context rather than replacing it.

Track intent explicitly. A running to-do list of pending user requests, rewritten every turn, is a cheap structure that makes "the user changed their mind" visible to the agent.

Quote, don't paraphrase, tool output. The extractor refers to tool output by line range and copies facts verbatim, so IDs, hours and prices are never reworded.

Count the cost yourself. Every user message triggers two extra model calls, and the extractor reads the entire tool history each time. The paper reports the main agent's context length, not total tokens or latency. With prompt caching, that difference can reverse the cost picture.
