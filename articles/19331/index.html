What is MCP? How MCP Servers Work and Permission Design for Enterprise Adoption

Original title: MCPとは？MCPサーバーの仕組みと企業導入の権限設計

FDX株式会社 · 2026-11-10 · 20 min read

Summary

This article explains MCP (Model Context Protocol), the connection standard Anthropic released in November 2024 and donated to the Linux Foundation's Agentic AI Foundation in December 2025. It covers the host/client/server architecture, the three server capabilities (tools, resources, prompts), and how MCP reduces integrations from M×N to M+N. It details breaking changes in the current 2026-07-28 spec, which removed initialize handshakes and sessions, and stresses that the spec cannot enforce security: token passthrough, confused deputy, and untrusted tool annotations are real risks. The author proposes five permission-design decisions for enterprises and warns that listing in the official MCP Registry is not a safety guarantee.

Key points

  • MCP standardizes AI-to-system connections, cutting integrations from M×N to M+N.
  • The 2026-07-28 spec removed initialize and sessions; old and new implementations may not interoperate.
  • The spec requires human-rejectable tool execution but cannot enforce it at protocol level.
  • Enterprises should decide five things upfront: allowlist, identity, exposed operations, confirmation, logging.
  • Official MCP Registry listing does not guarantee server safety; keep an internal allowlist.

When you have an AI agent read internal data or operate business systems, the effort of building a custom integration for each product becomes a problem. MCP (Model Context Protocol) is a common standard for these connections. It was released by Anthropic in November 2024 and donated to the Agentic AI Foundation under the Linux Foundation in December 2025.

There is movement in Japanese government as well. In the "Priority Plan for Realizing a Digital Society" of July 21, 2026, the Digital Agency decided to conclude its policy on making administrative systems compatible with MCP and similar standards in fiscal year 2026, and stated that My Number Portal aims to build an MCP-based foundation by the end of fiscal year 2027.

  • MCP is a standard that connects AI apps (hosts) with MCP servers that provide data and functionality. The host prepares a client for each connection destination, and each client connects one-to-one with a server. Communication is done via JSON-RPC 2.0.
  • The current specification is the 2026-07-28 version. The initialize procedure at connection start has been removed, replaced by a scheme where each request is self-contained. If you implement based on older documentation, some combinations will fail to connect to new servers.
  • The specification requires that a human can reject tool execution and that a tool's self-reported description is not trusted. However, as the specification itself states, the protocol cannot enforce this.
  • For corporate adoption, it is easier to proceed if you first decide five things: which servers may be used, under whose authority they run, which operations are exposed, confirmation before execution, and logging.

This article is written based on the official specification pages (modelcontextprotocol.io) and each vendor's official documentation, as verified on November 5, 2026.

Who this article is for

  • Information systems and DX promotion departments that plan to connect AI agents to internal systems or SaaS and want to decide whether to adopt MCP
  • Security officers who are receiving requests from business units to use MCP servers but have no criteria for approval
  • Product owners considering offering their company's products or data as MCP servers

What is MCP? (3 key points)

  • MCP is a common connection standard for AI apps to use external data and functionality. The official specification site compares it to a USB-C port for AI apps.
  • It is divided into the consuming side (host and client) and the providing side (server), and servers provide three things: "tools," "resources," and "prompts."
  • While connections become easier, the scope of what AI can do also expands. The adopting company must decide which servers to use, under whose authority, and to what extent.

Why MCP became necessary

Before MCP, every time you wanted an AI app to use an internal system, you had to build integrations for each app and each system. If there are M types of AI apps and N types of systems to connect, the number of integrations becomes M × N.

With MCP, if the target system provides one MCP server, any MCP-compatible AI app can use it the same way. On the AI app side, implementing one MCP client allows it to use many servers. The number of integrations drops to M + N.

Support is also spreading. OpenAI enabled calling remote MCP servers via the Responses API, and Google provides managed MCP servers for Google Cloud services. AWS allows MCP servers to be connected as destinations via Amazon Bedrock AgentCore Gateway, and its supported protocol versions include the 2026-07-28 version.

How MCP works

The three roles: host, client, and server

The specification divides the roles into three.

RoleWhat it doesExamples
HostThe AI app the user operates. It launches and manages multiple clients, and handles connection approval, obtaining consent, and coordination with the LLMClaude, ChatGPT, an in-house AI agent
ClientA component within the host that handles the connection to one server. Clients and servers are one-to-onePrepared by the host for each connection destination
ServerA program that provides data and functionality to the AI. It can be a process on a PC or a service over the networkFile search, CRM, ticket management, databases

Under the specification's design principles, the server must not read the entire conversation, and must not be shown the contents of other servers. Conversation history stays with the host, only necessary information is passed to the server, and the host controls coordination between servers. This is not something the protocol enforces automatically; it is maintained by the host's implementation. From a corporate standpoint, the host is where you decide which information is passed to which server.

The three capabilities MCP servers provide

CapabilityDescriptionCorporate examples
ToolsFunctions the AI executes. The AI finds and calls them itself depending on contextSearching cases, creating tickets, drafting emails
ResourcesData read by the AI or the userInternal policy documents, parts of customer master data, design documents
PromptsPredefined instructions or workflows selected by the userWeekly report creation procedures, templates for first-response replies to inquiries

Tools are the capability that requires the most attention in permission design. The specification defines tools as "model-controlled," meaning the AI decides to call them. Unlike read-only resources, tools may involve writing or sending data.

Connection methods: stdio and Streamable HTTP

There are two standard connection methods.

  • stdio: The host launches the MCP server as a child process on the PC and communicates via standard input/output. Used for local servers running on a developer's PC. It does not follow the authorization specification; credentials are obtained from environment variables and the like.
  • Streamable HTTP: Sends messages via HTTP POST to an MCP server over the network. Used for remote servers provided by internal systems or SaaS. Per the specification, implementing authorization is optional (OPTIONAL), but if implemented, it is recommended (SHOULD) to follow the authorization specification based on OAuth 2.1.

The HTTP+SSE method, which existed in the 2024-11-05 version, was classified as Deprecated in the 2026-07-28 version. Do not choose it for new development.

What changed in the 2026-07-28 specification

The MCP specification is versioned by date. It has been revised through the 2024-11-05, 2025-03-26, 2025-06-18, and 2025-11-25 versions, and the 2026-07-28 version, published on July 28, 2026, is the current one. Since this version includes backward-incompatible changes, implementations based on explanatory articles from 2025 or earlier may have discrepancies.

Changed itemUp to 2025-11-25 version2026-07-28 version
Starting a connectionNegotiate version and capabilities via initialize, then communicateProcedure abolished. Send version and client capabilities with each request
SessionsMaintain sessions with Mcp-Session-IdProtocol-level sessions abolished. If state is needed, the server issues an ID that is passed as a tool argument
Retrieving server informationLearned from the initialize responseObtained via server/discover (servers must implement this)
Queries from the serverThe server sends requests to the clientThe server returns a result indicating "additional input is needed," and the client resends the original request with the input attached
Sampling, Roots, LoggingDefined in the specification (Sampling and Roots are client-side features, Logging is server-side)Deprecated. Not adopted in new implementations

Deprecated features remain in the specification for at least 12 months in principle (with an exception allowing shortening to 90 days in emergencies). The removal of Sampling, Roots, and Logging will occur, at the earliest, in a version released after July 28, 2027. The removal timing of the HTTP+SSE method is defined separately.

Companies adopting MCP should verify which versions the hosts and servers they use support. According to the specification's compatibility table, a client that only supports methods up to the 2025-11-25 version cannot connect to a server that only supports the 2026-07-28 method.

Differences between MCP, API integration, and Function Calling

Comparison pointIndividual API integrationFunction CallingMCP
What is decidedHow to call APIs for each systemA method for having the model select functions within a single AI appA common standard for connecting AI apps with external functionality
Who builds itDeveloped for each integrationThe AI app's developer defines the functionsThe provider builds one server, which MCP-compatible apps use in common
Suitable scenariosRunning fixed processes in a fixed orderA small number of functions used only within one's own appLetting multiple AI apps use the same internal systems or SaaS

MCP does not replace APIs. Many MCP servers call existing APIs internally. What MCP standardizes is the part that unifies how calls are made from the perspective of AI apps.

Problems that commonly arise when using MCP in enterprises

As the flip side of ease of connection, the scope of what AI can access expands. The specification's Security Best Practices lists problems that can arise in implementation and operation. The items relevant to corporate decision-making are as follows.

ProblemWhat happensCountermeasure indicated by the specification
Token PassthroughThe MCP server receives a token not intended for itself and passes it as-is to a downstream API, bypassing downstream usage limits and audit logsServers MUST NOT accept tokens that were not issued to them
Confused DeputyIn a relay server that connects to an external API with a single fixed ID, authorization is granted without the user's consent, and an attacker steals the authorization codeRelay servers must always obtain per-client consent and confirm it before proceeding to external authorization
Local server hijackingA malicious command is planted in the configuration, and arbitrary code is executed on the PCClients offering one-click configuration MUST display the command to be executed in full and obtain explicit approval
Excessive scopesA token with full privileges is obtained upfront, increasing damage if it leaksStart with minimal scopes and obtain additional consent only when performing operations that require it
SSRFA malicious server makes the client access internal addresses through the authorization processUse HTTPS in production and block connections to private IP address ranges

In addition, tool descriptions and annotations such as "read-only" are self-reported by the server. The specification states that annotations from servers other than trusted ones MUST NOT be trusted. Whether a tool labeled "does not delete" actually avoids deletion cannot be verified from the report alone.

When employees connect unapproved MCP servers on their own judgment, it becomes a form of shadow AI. Detection approaches and alternative options are summarized in "Shadow AI Countermeasures | Why Prohibition Alone Cannot Prevent It and 4 Control Points".

Five Permission Design Decisions for Enterprise Adoption

The specification establishes as a principle that users should consent to and understand all data access and operations. At the same time, it explicitly states that MCP itself cannot enforce this principle at the protocol level. The mechanisms to enforce it must be designed by the adopting enterprise. FDX recommends deciding the following five points first.

1. Decide which servers may be used

The first decision is the allowlist of MCP servers permitted for internal use. The official MCP Registry (registry.modelcontextprotocol.io) is a place that collects information about publicly available servers, and as of the check on November 5, 2026, it is in a preview stage. The Registry deliberately takes a policy of not evaluating the information it lists, leaving code safety inspections to distribution sources such as npm and to marketplaces that use the Registry.

Being listed in the Registry does not guarantee safety. Internal servers are also outside the Registry's scope, so the allowlist must be maintained by your own company.

  • Provider: whether it is an official server or one created by a third party
  • Connection method: local (stdio) or remote (Streamable HTTP)
  • Data handled: which business systems and which categories of information it touches
  • Supported specification version: whether it connects with the host you use

2. Decide whose permissions it runs under

When implementing authorization on a remote MCP server, the MCP server becomes an OAuth 2.1 resource server and the MCP client becomes an OAuth client. The specification makes mandatory a mechanism for the server to publish authorization server information (RFC 9728) and a mechanism for specifying token destinations (RFC 8707). Remote servers used internally should be limited to those with authorization implemented.

An important enterprise decision is whether the AI runs under "the user's own permissions" or under "a shared service account." If it runs under the user's own permissions, information that person cannot see is also invisible to the AI. If a shared account is used by all employees, unless per-user access control and logging are built separately, information normally inaccessible can be reached via the AI, and logs will not show whose operation it was.

The specification also states that servers must verify that received tokens are addressed to themselves, and must not accept or relay other tokens.

3. Limit the operations exposed

A single MCP server may have many tools. For example, even if a CRM server has "search," "update," "delete," and "bulk export," many workflows only need search at first.

The specification states that

tools/list

the tools returned may vary according to the permissions attached to the request. For tokens with narrowed scopes, a design can show only the tools usable within that scope. Starting with minimal scopes and obtaining additional consent when updates become needed aligns with the specification's recommendations.

4. Have a human verify before execution

The specification states that a human should always be able to reject tool calls, and recommends (SHOULD) displaying AI-exposed tools in the UI, showing execution-time indications, and providing confirmation screens.

For internal operations, it is easier to make decisions by dividing operations into three categories.

CategoryExamplePre-execution confirmation
ReadSearch, listing, retrieval for summarizationMay be omitted. However, restrict the target data categories as in step 1
WriteCreating records, updating, saving draftsShow the content and obtain approval
External sending/deletionSending email, sharing externally, deletion, bulk processingObtain approval every time. Set an upper limit on the number of items for bulk processing

OpenAI's Responses API is configured to require approval for MCP tool execution by default. Do not rely solely on product defaults; decide internally which categories will skip approval. Even if a tool reports itself as "read-only," do not skip confirmation based on that report alone.

5. Record and audit

The specification recommends that clients record tool usage for auditing purposes. Keep records of who called which tool on which server from which host, and with what arguments.

Also review the allowlisted servers quarterly. Stop unused servers and check whether provider updates have added tools. Tool lists can change due to server-side updates without any action by the user.

Frequently Asked Questions (FAQ)

Q1. What is MCP?

A. MCP (Model Context Protocol) is a common connection standard for AI applications to use external data and functionality. An AI application (host) prepares a client for each connection target and connects one-to-one with an MCP server that provides data and functionality, exchanging messages via JSON-RPC 2.0. It was released by Anthropic in November 2024 and donated to the Agentic AI Foundation under the Linux Foundation in December 2025.

Q2. What is an MCP server?

A. It is a program that provides functionality and data to AI. It can provide three things: "tools" that AI executes, "resources" that AI reads, and "prompts," which are standardized instructions. There are local servers running on a PC (stdio connection) and remote servers provided by internal systems or SaaS (Streamable HTTP connection).

Q3. How does MCP differ from APIs?

A. APIs are calling conventions specific to each system, while MCP is a standard that unifies how AI applications make calls. Since most MCP servers call existing APIs internally, MCP does not replace APIs. MCP is well suited when you want multiple AI applications to use the same internal system.

Q4. Is MCP a security risk?

A. The standard itself is not dangerous, but because it expands the scope of what AI can access, poor design broadens the potential damage. The specification prohibits token reuse and requires human confirmation before tool execution, but explicitly states that the protocol cannot enforce these. The adopting company must decide five points: which servers are allowed, under whose permissions they run, which operations are exposed, confirmation before execution, and logging.

Q5. Are servers listed in the official MCP Registry safe?

A. Not necessarily. The official MCP Registry is a place that collects information about published servers, and as of the check on November 5, 2026, it is still in preview. It does not intentionally evaluate listed information, and code safety inspection is left to distributors or the marketplaces on the user side. Internally, manage servers with your own allowlist.

Q6. Can MCP servers and clients built in 2025 still be used?

A. It depends on the combination. The 2026-07-28 version deprecated connection initiation via

initialize

and sessions. According to the specification's compatibility table, a client that only supports the old method cannot connect to a server that only supports the new method. Check which version your host and server support, and if necessary, update to an SDK that supports both methods.

Summary

  • MCP is a common connection standard linking AI applications with internal systems and SaaS, composed of three roles: host, client, and server
  • MCP servers provide tools, resources, and prompts. Tools, which AI decides to call, are the center of permission design
  • The current specification is the 2026-07-28 version, in which initialize and sessions were deprecated. Verify the supported versions of your host and server
  • The specification prohibits token reuse and requires that a human be able to reject tool execution, but the protocol itself cannot enforce this
  • In enterprises, decide these five points first: which servers may be used, under whose credentials they run, which operations are exposed, pre-execution confirmation, and logging and inventory
  • Listing in the official MCP Registry is not a guarantee of safety. Maintain your own allowlist
