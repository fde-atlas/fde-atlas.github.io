Deployment Tagging Patterns and Microservices: How to Choose a Multi-Tenant Architecture for FDEs

Original title: 部署标记模式与微服务：FDE 多租户架构怎么选

FDE Times · 2026-10-08 · 6 min read

Summary

Using a scenario of one bank plus six retail chains, the article argues that for FDEs the key multi-tenant question is how to partition customers, not whether to choose a monolith or microservices. Microservices split code by function but cannot meet per-customer demands like data isolation or slower release cadence. The deployment stamps pattern splits customers into groups with dedicated copies, satisfying isolation and differing update rhythms, at the cost of significantly higher infrastructure spend and hard tenant migration, requiring infrastructure as code from day one. It also covers compute resource consolidation trade-offs, the geode pattern's limits under data-residency rules, and advises candidates to articulate deployment decisions in resumes and interviews.

Key points

  • Microservices split code; deployment stamps split customers—conflating them wastes money.
  • Amazon's Prime Video case cut infrastructure costs over 90% by consolidating components.
  • Deployment stamps enable isolation and per-group release rings but raise costs sharply.
  • Tenant grouping should be decided during discovery, with infrastructure as code to prevent drift.
  • With data-residency constraints, use one stamp per region behind a global routing layer.

Key takeaways

  • Microservices can improve an application's fault tolerance, but they can't handle per-customer requirements, such as keeping data stored separately or slowing down updates.
  • Packing multiple tasks into the same compute unit is cheap, but those tasks share a release cadence, a failure domain, and a security context.
  • Deployment stamps split customers into groups at the cost of a significant infrastructure increase, and tenants are hard to migrate between stamps, so infrastructure as code is needed from day one.

Seven customers, one solution: a bank, plus six mid-sized retail chains. The bank doesn't want its data stored alongside anyone else's and only accepts quarterly updates. The retail chains want new features live as soon as possible. Suppose a team has to deliver exactly this set of customers. Then the usual first question—monolith or microservices—is actually the wrong one.

For a Forward Deployed Engineer (FDE), the more important question is how to split the customers: which customers share infrastructure, which get their own dedicated copy, and which receive updates and when.

Microservices split code; deployment stamps split customers. Confusing the two means spending a fortune on a system that still fails to satisfy the most demanding customer.

Microservices solve a different problem

When AWS introduces microservices, it highlights one clear benefit: services are independent of each other, which makes the application more fault tolerant. That benefit is real, but it comes at a cost. As early as 2014, Martin Fowler pointed out that distributed transactions are notoriously hard to implement.

Fowler's advice is pragmatic too: start with a monolith, keep it modular, and split into microservices only when the monolith actually starts causing problems. This approach suits the FDE. FDEs usually run lean and are short on time; before anyone debates whether the architecture is elegant, the customer's environment has to be up and running.

There's also a frequently cited number for the opposite direction. According to a May 2023 DevClass report, an internal Amazon case study showed that the Prime Video team responsible for audio/video quality monitoring merged its distributed components into a single process, cutting infrastructure costs by more than 90%.

That result applies only to that team's specific situation, but it's a reminder: splitting is never free.

Back to the bank. Splitting the system into 12 services satisfies neither of the bank's two requirements.

After the split into 12 services, the bank still shares a database and a release schedule with every other customer.

Consolidating compute is cheap, but everything is tied together

The Azure Architecture Center has a pattern that closely matches the monolith's "bundle everything to save money" idea: Compute Resource Consolidation, where multiple tasks share compute resources to reduce costs. The pattern focuses on how tasks run on infrastructure rather than how code is organized, but it clearly shows the cost of consolidation.

According to that document, updating one task requires stopping, redeploying, and restarting every other task in the same compute unit; consolidated tasks also share a single failure domain and a single security context.

The same document notes that tasks handling highly sensitive or private data should not be consolidated, because they need their own security context. Applied to a deployment serving multiple customers, this exposes the limitation of running all customers inside one monolith: everything is fine until the first customer asks for data isolation.

Even with a monolith, there's one mistake best avoided from the start. Microsoft lists putting all data into a single data store as an antipattern, because it causes resource contention and degrades performance. The recommended approach is to separate data according to how it is used.

A monolith at the code level doesn't mean all data has to live in one database.

Stamps: split by customer, not by function

Deployment stamps approach the problem from the other direction. Instead of splitting the application into parts, you deploy multiple independent copies of the entire application, each with its own data store. In a multi-tenant environment, each stamp serves a pre-defined group of tenants.

Microsoft describes a scenario very close to FDE work: some large customers may need dedicated instances, while smaller customers share a multi-tenant deployment. Stamps can also handle the update cadence problem.

Some customers accept frequent updates; others are risk-averse and want fewer updates. Each stamp can therefore use a different deployment ring.

Applied to these seven customers: Stamp A serves only the bank, with its own data and security context; Stamp B is shared by the six retail chains.

Each new release goes to Stamp B first, runs smoothly for a few weeks, and only then reaches Stamp A. The code remains a modular monolith; only the deployment changes.

This table is easy to misread as three mutually exclusive options, but that's a mistake. Stamps are a deployment approach, while a monolith or microservices is a code organization approach, so a modular monolith can perfectly well run across multiple stamps—exactly as in the bank and retail chain example above.

Every copy costs money

Microsoft is equally clear about the cost: deploying multiple copies of infrastructure significantly increases operating costs. Migrating a tenant from one stamp to another is also difficult. So the decision of which customer goes on which stamp should be made carefully during the customer requirements discovery phase, not after the customer is already running in production.

Operating multiple stamps requires infrastructure as code and drift control. Otherwise, every time someone manually changes a configuration in a customer environment, the stamps drift a little further apart. Microsoft also recommends deploying at least two stamps, because with only one, it's easy to hard-code assumptions that only hold for a single instance.

Stamps aren't the default option either. According to Microsoft, the pattern shouldn't be used if the solution is simple, doesn't need to scale massively, or a single instance can handle the load. With one customer, or when all customers accept sharing, a modular monolith with sensible data separation is enough.

When customers require data to stay in a specific region

There's one more option: the geode. Unlike stamps, which each serve one group of customers, every geode instance can serve any user. Microsoft notes that geodes are typically considerably more complex to design and build, and suit cloud-native platforms with no restrictions on data location.

So before considering a geode, ask customers up front whether they have data location requirements. Microsoft points out that if there are data residency requirements, or the application needs to maintain temporary state for sessions, a geode is a poor fit.

In that case, Microsoft recommends using stamps, combined with a global routing layer that sends each request to the correct stamp.

If a customer requires that data never leave a certain region (banks, hospitals, and government agencies often do), the answer is practically ready-made: one stamp per region, with a routing layer in front. It is not the cleverest or theoretically most elegant solution, but it is one you can explain clearly to the customer's compliance team.

For developers who want to become an FDE

When reading job descriptions for FDE or Solutions Engineer roles, watch for terms like multi-tenant, single-tenant deployment, dedicated instance, and infrastructure as code. They signal that the company is facing exactly the problem of splitting customers, and needs people who understand both axes of architecture at once.

When writing your resume, don't just say "migrated the system to microservices." Explain clearly how the deployment approach was decided and why: which customers got dedicated instances and for what reason, how release cadences were divided, and what measures were taken to prevent environment drift.

Explaining a decision with weighed trade-offs is far more persuasive than listing a string of technologies.

If you are asked in an interview "monolith or microservices?", a good answer usually starts with a counter-question: how many customers are there, and how do they differ? In an FDE role, how customers are split often determines a project's success more than how the code is split.
