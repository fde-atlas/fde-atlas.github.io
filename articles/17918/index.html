Vietnamese Token Cost Estimation: Tokenizer Benchmarks and Pricing Formula

Original title: 越南语 Token 成本估算：分词器实测与报价公式

FDE Times · 2026-10-08 · 6 min read

Summary

The widely cited claim that Vietnamese costs 4.54x more tokens than English is outdated. A benchmark across 13 tokenizers found ratios of 1.05 to 2.14, with o200k_base at 1.34x. The article gives forward deployed engineers a four-step method: collect real client data split into inputs and outputs, count tokens with the actual model's tokenizer (e.g., via tiktoken), apply a monthly cost formula with per-million pricing, and document pricing tiers, dates, and a 10% surcharge for data residency on models released after March 5, 2026. Using a wrong multiplier can inflate quotes threefold, risking lost deals or unprofitable projects.

Key points

  • The 4.54x claim is outdated; newer tokenizers measure 1.05 to 2.14x English.
  • Token counts depend on the model's tokenizer, so count on real client data.
  • Inputs and outputs are priced separately and must be estimated separately.
  • Quotes should state pricing tier and date; data residency adds a 10% surcharge.
  • A wrong multiplier can swing estimates threefold, affecting deals and margins.

Key Takeaways

  • Vietnamese token counts are not the rumored 4.54 times English. A benchmark covering 13 tokenizers measured 1.05 to 2.14 times, with o200k_base at 1.34 times.
  • Token counts are determined by the model's tokenizer, not by Vietnamese itself. So use the actual tokenizer and count on the customer's real data.
  • Quotes must distinguish input from output, and note the date and pricing tier; if the customer needs data residency on models released on or after March 5, 2026, add 10%.

Search "how many tokens does Vietnamese cost" and the most common answer is: 4.54 times English. An author on Viblo, a Vietnamese developer community, didn't buy this claim and re-measured using 13 tokenizers on the same set of bilingual texts. With newer tokenizers, the gap dropped to between 1.05 and 2.14 times.

PhoBERT even came in at 0.87 times, meaning fewer tokens than the English version. However, PhoBERT is not an API model you can bill customers by token; this number only shows how much impact a tokenizer can have.

The gap between these two numbers directly determines the quote. If you are a Forward Deployed Engineer (FDE) who shows up to a customer with the 4.54 multiplier, your quote could be three times too high, the customer balks at the price, and the deal falls through. Estimate the multiplier too low, and you lose money in the first month of production.

This concern is long-standing. As early as late 2022, a Vietnamese developer complained on the OpenAI forum that the tokenizer produced too many tokens for Vietnamese, writing that the project had barely started and costs already seemed too high. The steps below turn this concern into a verifiable number.

Preparation: one script, one data file, one pricing page

In the end you will have a small script that does two things: count tokens on the customer's sample data and calculate monthly cost with input and output distinguished. You need Python, a sample of the customer's real Vietnamese text (or text you wrote yourself that closely resembles it), and the model provider's pricing page open in a browser tab.

First, two concepts. A token is a unit of data produced by splitting a large chunk of information into small pieces. Models process text in tokens, and providers charge by token.

The process of splitting text into tokens is called tokenization, so the same Vietnamese sentence run through two different tokenizers yields two different numbers.

Step 1: Get real data and separate input from output

Ask the customer for a sample that exactly matches the kind of data the system actually receives, such as 50 support tickets, 20 contracts, or 100 user questions. Save the part to be sent to the model in one file, and the expected responses in another.

APIs usually price input tokens and output tokens separately, so the data should be split the same way from the start.

Check: Open both files and confirm the content is Vietnamese with diacritics, formatted the way the customer actually uses it. If you use machine-translated text, or Vietnamese without diacritics, the counts won't reflect reality.

Step 2: Count with the model's own tokenizer

This is the most important step. The code below is a simplified version for demonstration, using the tiktoken library and two encodings measured in the Viblo benchmark. Before using it in production, verify the installation method and function names in the library's documentation.

# 示例（简化版）：用两代分词器统计 Token 数
import tiktoken

new = tiktoken.get_encoding("o200k_base")   # GPT-4o / 4.1
old = tiktoken.get_encoding("cl100k_base")  # GPT-3.5 / 4

text = open("sample_input.txt", encoding="utf-8").read()
print("o200k_base:", len(new.encode(text)))
print("cl100k_base:", len(old.encode(text)))

(The variable

new

holds the newer encoding,

old

holds the older encoding, and

text

holds the text.)

Check: The cl100k_base count should be noticeably higher. In Viblo's benchmark, o200k_base was 1.34 times and cl100k_base was 2.14 times. The same test showed that simply switching to the newer generation tokenizer, with the prompt unchanged, can cut costs by up to 37%.

These two encodings only apply to OpenAI's models. If the customer chooses a model from another provider, that model has its own tokenizer, and you should use that provider's own token counting tool rather than borrowing o200k_base.

How one wrong multiplier distorts an entire quote

Consider a hypothetical case. A customer's traffic, if written in English, amounts to 10 million input tokens per month. Multiply by the rumored 4.54 and you quote 45.4 million tokens; with cl100k_base's 2.14, you get 21.4 million; with o200k_base's 1.34, only 13.4 million.

Same customer, same workload, yet the estimates differ by more than three times purely because of the multiplier. So these multipliers are only useful for helping the customer understand the problem. When calculating cost, use the token counts measured in Step 2 on the customer's own data.

It's also worth knowing why Vietnamese is not the worst case. A 2025 study on arXiv compared multiple languages and found that languages with non-Latin scripts or complex morphology produce significantly more tokens. Vietnamese uses the Latin alphabet.

The authors also argued that per-token pricing further widens the gap between languages.

Step 3: Build the monthly cost formula

Once you have the average tokens per request, multiply by usage and apply the prices. The code below assumes prices are quoted per 1 million tokens. If the pricing page uses other units, adjust accordingly.

def monthly_cost(num_requests, tok_in, tok_out,
                 price_in, price_out, surcharge=0.0):
    # price_in、price_out：每 100 万 Token 的价格，以报价当日核对的为准
    base = num_requests * (tok_in * price_in + tok_out * price_out) / 1_000_000
    return base * (1 + surcharge)

# 如果客户需要数据驻留，设 surcharge=0.10（见第 4 步）

(where

monthly_cost

is the monthly cost,

num_requests

is the number of requests,

price_in

and

price_out

are the per-million-token input and output prices verified on the day of quoting, and

surcharge

is the surcharge.)

Check: Run it once with tok_out set to 0 and confirm the result matches your hand-calculated input cost. Then increase tok_out to see how much the output portion affects the total. This is exactly the part customers often forget to ask about.

Step 4: Note the pricing tier, date, and surcharge

OpenAI's prices change quickly and come in multiple tiers: Standard, Batch, Flex, and Fast. Within 2026 alone, the priority tier was renamed from Priority processing to Fast mode on July 30, 2026. A quote without a date and tier stops being accurate within a few months.

One item is easy to miss. For models released on or after March 5, 2026, regional processing endpoints (data residency) carry a 10% surcharge. So ask the customer from the start whether data must stay in a specific region; if so, set surcharge=0.10 in the formula.

Mistakes that get your quote sent back

The first mistake is applying a generic multiplier—whether 4.54 or some other number found online—instead of counting yourself. The second is merging input and output into a single "tokens per request." Once the customer changes requirements, say wanting longer responses, you won't know which part to adjust.

The third mistake is counting tokens with one model's tokenizer but quoting for another model. The gap between 1.34x and 2.14x is enough to turn a profitable project into a loss. The last mistake is counting with your own "clean" sample text, while the customer's real data contains tables, product codes, and typos.

Customers will ask "How much per month?" sooner than you expect

Since APIs are priced by token, the question "How much will it cost to run this system per month?" will come sooner or later, so prepare your answer in advance. A three-row table (input tokens, output tokens, pricing tier, and verification date) is far more convincing than "probably a few hundred dollars."

If you're preparing to transition into an FDE role, write this skill concretely into your resume. For example: "Measured tokens on the customer's Vietnamese data and selected a newer tokenizer, reducing estimated costs by X%," where X is a number you actually measured.

When reading job descriptions, look for mentions of cost estimation or solution scoping; in interviews, that's exactly where you can bring out this example.

The 4.54 rumor will keep circulating online. But at the negotiating table, the person who brings token counts measured on the customer's own data has the stronger hand.
