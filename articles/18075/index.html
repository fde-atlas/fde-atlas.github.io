Guide to Building a Vite + React TypeScript Demo for Customer Presentations

Original title: Vite + React TypeScript 客户演示搭建指南

FDE Times · 2026-10-08 · 6 min read

Summary

This guide shows forward deployed engineers how to build a customer demo with Vite and React TypeScript, starting from a machine without Node and ending with a clean production build in dist. It targets the scenario where a client asks for a working demo within days. Key warnings: Vite only transpiles TypeScript and does not type-check, so run tsc --noEmit before building and deliberately plant an error to verify the check works; all VITE_ environment variables are bundled into client code, so API keys must stay on the backend; and useState should receive a typed initial value to avoid overly loose type inference. The recommended structure separates types.ts, api.ts, and App.tsx so the backend URL can change without touching the UI. The article closes with advice on presenting this skill on a resume through outcomes and a public repo rather than listing technologies.

Key points

  • Check Node version first: Vite needs 20.19+ or 22.12+.
  • Vite transpiles but never type-checks; run tsc --noEmit and test it catches a planted error.
  • VITE_ variables ship to the browser, so API keys belong on the backend.
  • Define types.ts first as the contract, and centralize API calls in api.ts.
  • On a resume, show outcomes and a public repo instead of listing skills.

Six steps to take a customer demo from a computer without Node installed to a clean build with type checking passing and API keys kept out of the bundle.

Key takeaways

  • Vite requires Node.js 20.19+ or 22.12+. Run node -v before you start.
  • Vite only transpiles TypeScript; it does not type-check. Run tsc --noEmit before building to dist, and deliberately plant an error to confirm the command actually catches it.
  • All VITE_ variables are bundled into client-side code; API keys must live on the backend.

On Tuesday, the customer asks: "Can my team try it on Friday?" The backend that answers questions based on internal docs already works, but the customer won't look at JSON. They need a text box, a button, and the answer displayed on screen. The work computer the customer gives you has nothing installed—not even Node.

Forward Deployed Engineers (FDEs) run into this constantly. What's needed isn't deep React expertise, but getting from zero to a clean build within a few hours, in a form a colleague can take over next week. The six steps below follow one such example, from the first command all the way to the

dist

folder.

Why Vite instead of a framework?

The official React docs recommend using a framework to create new apps. The docs are also candid about the cost of building it yourself: more flexibility, but you have to pick your own tools for routing, data fetching, and other common patterns.

For a demo with a single page, that cost is nearly zero, because at this stage you need neither routing nor a complex data-fetching strategy. Vite's scaffolding is lightweight and starts fast. If the demo later grows into a multi-page product, you can reconsider a framework then.

Step 1: Install the right Node before typing anything else

Vite requires Node.js 20.19+ or 22.12+. On a blank machine, install 22.12 or higher, either with the official installer or, if the customer's machine allows it, with a version manager like nvm. Then check:

node -v
npm -v

If

node -v

reports a version below the requirement, stop and fix it immediately. A wrong Node version that surfaces in later steps often looks like a Vite error, and you may spend an afternoon debugging in the wrong direction.

Step 2: One command to scaffold, one command to run

Vite uses

npm create vite@latest

to create projects. The React + TypeScript template is

react-ts

(there's also

react-compiler-ts

）：

npm create vite@latest client-demo -- --template react-ts
cd client-demo
npm install
npm run dev

The default

dev

script is

vite

, which starts the dev server at

localhost:5173

. When the sample page appears, the infrastructure is in place. If the customer already has a React project written in JavaScript, there's no need to start over—just add the type definitions:

npm install --save-dev @types/react @types/react-dom

。

Step 3: Write the data types before the UI

Before touching the interface, create

src/types.ts

. This file is the contract between the backend and the UI:

export type Status = "idle" | "loading" | "done" | "error";

export type Answer = {
  text: string;
  sources: string[];
};

The React docs point out that declared prop types both verify correctness and serve as documentation displayed directly in the editor. For an FDE, the second benefit matters just as much: whoever takes over can open the file and know what the API returns without calling it.

Step 4: Keep all API calls in one place

Create

src/api.ts

. All network-related code lives here, so when the customer changes the backend address on Thursday, you only change one line:

import type { Answer } from "./types";

// 只是后端地址，不是密钥
const API_URL = import.meta.env.VITE_API_URL;

export async function readAnswer(question: string) {
  const res = await fetch(`${API_URL}/answer`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question }),
  });
  if (!res.ok) throw new Error(`API 返回 ${res.status}`);
  return (await res.json()) as Answer;
}

(The comment means: "Just the backend address, not the key." The error message is "API returned" plus the status code.)

The

.env

file in the project root:

VITE_API_URL=http://localhost:8000

One detail is most critical:

VITE_

variables are bundled directly into the code that runs in the browser, and the Vite docs state explicitly that these variables must not contain sensitive information such as API keys. Keys for the model and the customer's systems belong on the backend; the UI only knows the address.

Step 5: Connect the API to the interface

Only now does

src/App.tsx

come into play—the template already created this file. Files containing JSX must use the

.tsx

extension, so don't rename it to

.ts

. Replace the file's contents with the following code:

import { useState } from "react";
import type { FormEvent } from "react";
import { readAnswer } from "./api";
import type { Answer, Status } from "./types";

type UiState = { status: Status; answer: Answer | null };
const initial: UiState = { status: "idle", answer: null };

export default function App() {
  const [ui, setUi] = useState(initial);

  async function handleSubmit(e: FormEvent) {
    e.preventDefault();
    const form = new FormData(e.currentTarget as HTMLFormElement);
    const question = String(form.get("question") ?? "");
    setUi({ status: "loading", answer: null });
    try {
      const answer = await readAnswer(question);
      setUi({ status: "done", answer });
    } catch {
      setUi({ status: "error", answer: null });
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <textarea name="question" rows={4} />
      <button disabled={ui.status === "loading"}>提问</button>
      {ui.status === "error" && <p>无法连接 API，请重试。</p>}
      {ui.answer && <p>{ui.answer.text}</p>}
    </form>
  );
}

(The button text means "Ask"; the error message means "Could not connect to the API, please try again.")

Note the

useState(initial)

line. This hook infers its type from the initial value. If you write

useState("idle")

directly, TypeScript infers the type as

string

，

"loadng"

slip through. If you write

useState(null)

, the type is

null

, and the answer can't be assigned at all.

The cleanest approach is to give the hook an initial value that already carries a type.

initial

is declared as

UiState

, so

status

only accepts the four values in the union,

answer

only accepts

null

or

Answer

. If you prefer splitting into separate states, the standard practice is to pass

Status

directly as the type parameter to

useState

。

Putting both pieces of state in one object has another benefit: you'll never end up with the state already "error" while an old answer is still on screen. Save the file, go back to

localhost:5173

, type a question, and click. With the backend running, the answer appears; with the backend stopped, the error message appears. The customer will try both cases, so you must test both too.

Step 6: A running dev server doesn't mean correct code

This is the biggest trap. Vite only transpiles TypeScript files; it doesn't check types. The dev server will happily serve files full of type errors until the customer happens to click into the broken branch. That's why the Vite docs recommend running

tsc --noEmit

：

npx tsc --noEmit
npm run build

Don't trust the type-checking command just because it reports nothing—prove it works: write

"loadng"

where status is assigned, then run it again. If the command stays silent, it probably isn't checking the UI code at all. In projects with multiple

tsconfig

files, use the

-p

flag to point directly at the config that covers the

src

code, until the deliberately planted error gets reported.

Then open

package.json

and check whether the

build

script runs the type check before

vite build

. If not, add it, so nobody on the team forgets. The build output goes to the

dist

folder by default: a set of static files you can put on a web server, and the customer can open them in a browser.

Mistakes that can ruin the Friday demo

The most common mistake is treating the dev server as proof. A page running on localhost only shows that the browser can execute the code, not that the types are correct. Right behind it comes trusting a type-checking command that reports "all clear" but has never been verified to catch any error.

The most dangerous mistake is taking the shortcut of putting keys into

VITE_

variables, on the grounds that "it's just a demo." Demo packages get passed around via email and group chats, and the keys travel with them. One slip is enough to lose the trust of the customer's security team.

Two smaller mistakes can waste hours: writing JSX in a

.ts

file, and letting

useState

infer its type from a bare string or

null

for state with multiple possible values. TypeScript can catch both of these, if you give it the chance.

How do you present this skill on a resume?

When reading an FDE job description, watch for phrases like "build prototypes", "customer-facing demos", and "rapid iteration". If they appear, these six steps are exactly the abilities you should be able to demonstrate—and showing results is far more persuasive than listing technologies.

Instead of writing "proficient in React, TypeScript" on your resume, write a sentence with a concrete outcome: in one project, starting from a blank machine, you completed a document Q&A demo and produced a production build, with an independent API layer, a swappable backend requiring no UI changes, and API keys kept server-side. A public repository whose structure is exactly

types.ts

、

api.ts

、

App.tsx

, says more about your abilities than any adjectives.

The next time a customer asks "Can we try it by Friday?", the right answer isn't "yes"—it's a link to a

dist

folder sent over on Thursday afternoon.
