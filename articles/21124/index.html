How to Kick Off an FDE Delivery Project: Problem Definition and Acceptance Criteria

Original title: FDE 交付项目如何启动：问题界定与验收指标

FDECareer.work · 2026-09-23 · 5 min read

Summary

Using a hypothetical internal knowledge Q&A project, this article explains how FDE delivery projects should start: interview business owners and frontline operators to define the problem, document data ownership and permission boundaries, and only then decide whether retrieval-augmented generation or other techniques are needed. Goals must be written as acceptance metrics with defined samples, calculation methods, baselines and thresholds, plus explicit exit conditions. If required data or an accountable business owner cannot be secured, the author recommends pausing development. The piece stresses this is engineering guidance, not a real client case, and unmeasured figures should stay marked as pending.

Key points

  • Start by interviewing existing workflows, not by choosing a model.
  • Map data owners and permission boundaries before picking technical approaches.
  • Acceptance metrics need defined samples, methods, baselines and owners.
  • Kickoff deliverables include problem definition, permission list, eval set and exit conditions.
  • Overly broad scope makes evaluation subjective; narrow the pilot to one workflow.

The starting point of an FDE project is how the customer currently gets a piece of work done, and which step is worth changing—not choosing a model first. Interview the business owner, the people doing the actual work, and the technical team; record current processing time, causes of rework, permission constraints, and manual fallback methods. Public FDE job descriptions also describe discovery, technical scoping, design, building, and production launch as a continuous set of responsibilities.

Illustrative project: internal knowledge Q&A

The following is an illustrative scenario, not a real customer case: a team wants employees to find answers about internal processes faster. First define which documents are accessible, user identities, which question types require cited sources, and which questions must be handed off to humans. If document ownership and update frequency are unclear, resolve data governance first, then decide whether to adopt retrieval-augmented generation.

Write the goals as verifiable metrics

Agree on a baseline and targets for the pilot, such as the proportion of answerable questions, citation accuracy, human review time, average response time, and usage rate. Metrics must specify the sample, calculation method, and owner; success cannot be judged by demo performance alone. First collect a set of real but authorized representative questions, then divide them into routine, edge-case, and must-refuse samples.

Phase deliverables

By the end of project kickoff, you should be able to deliver a one-page problem definition, a data and permissions inventory, pilot scope, an initial eval set, acceptance thresholds, and exit conditions. If the necessary data cannot be obtained or the business owner cannot be identified, pause the build and record the blocker in the decision log.

Turn business interviews into a one-page problem definition

Continuing the internal knowledge Q&A example: the support team searches product documentation and handling records for answers every day. First confirm the current process with the business owner, then observe how frontline staff actually search, judge, and escalate questions. Don't just ask "do you want to use AI"; follow up on where the most recent wrong answer came from, who bore the loss, and which questions must be handled by humans.

Write the problem definition as a single falsifiable sentence: within the specified documents and permissions, help support staff find sourced answers and reduce processing time that requires human confirmation. Since there is no real measurement data here, processing time, accuracy, and usage should all be marked as "to be measured" rather than filled in with flattering numbers.

List data and permissions first, then decide on the technical approach

For each data source, register the owner, update frequency, who can access it, deletion requirements, and the permitted processing environment. A document being readable by one member does not mean it can be copied into everyone's retrieval index. Access scopes for support staff, administrators, and other departments should be verified separately.

Only after confirming these boundaries should you evaluate whether retrieval-augmented generation, model calls, or improvements to existing search features are needed. Google Cloud's deployment guide can serve as an engineering reference for operations and continuous improvement; it cannot substitute for this project's data authorization or customer approval.

  • List document sources and their owners, noting which materials cannot enter the pilot.
  • Check the same question with at least two permission identities, recording the expected allow and deny outcomes.
  • Determine how the index syncs after document edits, permission revocations, and deletions.
  • Define a human escalation path for questions with no basis, conflicting sources, or out-of-scope permissions.

Write the acceptance table as a checklist both parties can execute

Acceptance metrics must state both the business purpose and the measurement method. Whether citations are correct cannot be judged by whether the answer looks plausible; check whether the cited content exists, whether it supports the answer, and whether the current user has access. Retrieval time alone also does not prove the workflow is faster; record the time for human verification and rewriting as well.

Below is a sample acceptance table; thresholds must be filled in by both parties after collecting the baseline. Targets not agreed in the table should not be retroactively declared as met at launch.

Failure example: scope too broad, acceptance based on vibes

If the kickoff goal is merely "build a bot that answers all company questions," document ownership, user permissions, and answer quality cannot be assigned clear responsibility. Even if a few questions are answered correctly in a demo, you cannot judge whether usage can be scaled.

The fix is to narrow the pilot to one workflow, one user group, and one manageable set of materials, and first establish an eval set and a change log. The business owner signs off on the scope; the technical lead confirms the implementation and rollback plan. Then move on to the prototype-to-production section, continuing with the same acceptance table.

What the kickoff phase should leave behind

At the end of the kickoff phase, the deliverables should be a set of materials that support the next decision: problem definition, workflow diagram, data permissions inventory, eval samples, acceptance table, and decision log. They don't need to be packaged as thick documents, but each item must have an owner and open questions.

If the necessary data cannot be obtained, or the customer still cannot confirm the success criteria, the reasonable next step is to close those gaps. Pausing feature expansion at this point is usually easier to control than entering production with unresolved assumptions and facing rework later.

FAQ

Is this a real customer project?

No. The three guides use the same internal knowledge Q&A example; the tables and steps are engineering advice. Where there is no real measurement data, it stays marked as "to be measured."

Can acceptance thresholds be copied directly?

No. Samples, baselines, and targets should be agreed based on the project's workflow, data, and operating conditions.

What if launch conditions aren't met yet?

Record the missing evidence and owners, keep the manual process, close the gaps first, then expand the pilot.
