Vibe Engines · 2026-07-31 · 15 min read

Summary

This guide covers Anthropic's Applied AI / Forward Deployed Engineer interview. The role embeds with strategic customers to build on Claude, with deliverables including MCP servers, sub-agents and agent skills, 25–50% travel, and an air-gapped federal variant. Anthropic publishes no loop; candidate reports suggest roughly five stages: recruiter screen, timed coding (Colab/CodeSignal), an applied-AI technical conversation, a customer scenario, and a values/safety round. Anthropic uniquely publishes rules on candidate AI use: write applications yourself, no Claude on take-homes unless stated, no AI in live interviews. The article includes a worked escalating-constraint cache problem and recommends reading the Responsible Scaling Policy and Constitutional AI before the values round.

What the role is here

Anthropic’s Forward Deployed Engineer posting describes embedding with strategic customers to ship applications on Claude, with deliverables that explicitly include MCP servers, sub-agents and agent skills for production workflows, travel of 25–50% and a requirement for production LLM and agent experience.first-party61 A Staff variant leads architecture and advisory work across an account.

There is also a federal variant with air-gapped and IL-level deployment requirements — a genuinely different technical brief involving model-weight delivery without internet access.first-party29

Read the deliverables list carefully before applying: this is the most agent-shaped FDE role among the frontier labs. Being able to talk fluently about tool schemas, sub-agent decomposition, context management and where agents fail is directly on-topic rather than a bonus. Anthropic also participates in the broader deployment-capital wave, including the $1.5B Ode venture with Blackstone announced in July 2026.6

Using AI as a candidate: what Anthropic says

Unusually for this role family, the policy is published. Read it before you prepare, because breaking it costs more than any wrong answer.

Anthropic’s guidance (last updated July 2025) sorts the process by stage:62

StageAnthropic’s guidance
Resume and applicationWrite the first draft yourself, then use Claude to refine it. Generating experiences you do not have is not allowed.
Take-home assessmentsComplete them without Claude unless told otherwise. Anthropic says it will be explicit when AI is allowed, for example “You may use Claude for this coding challenge”.
Preparing for interviewsEncouraged: research Anthropic, practise answers, draft questions for them.
Live interviewsNo AI assistance unless they indicate otherwise.

It also asks for transparency in return, and says Anthropic itself uses Claude in hiring for job descriptions, interview questions, transcription and sourcing, but does not let Claude make hiring decisions.62 The contrast with Distyl and Sierra, which build AI into the interview, is the useful lesson: the rule is per company and per stage, so ask. If a recruiter email does not say AI is allowed for an assessment, assume it is not.

An escalating-constraint problem, worked

A practice problem in the style of the reported format, not an Anthropic question: each level invalidates the previous design.

LevelNew requirementWhat it breaks
1A cache of at most 
N
entries, evicting the least recently used. A read counts as a use.		Nothing yet. An insertion-ordered dict is both the lookup and the recency list.
2Entries expire after a TTL. Time is passed in, so tests are deterministic.An expired entry still occupies a slot, so it can push out a live one. Expire before you evict.
3Each entry has a size, and the budget is total size. An item larger than the budget is rejected.One insert may evict several entries. Eviction becomes a loop, and the oversize case must not empty the cache for nothing.
import heapq
from collections import OrderedDict
from itertools import count

class Cache:
    def __init__(self, budget):
        self.budget = budget        # level 1: max entries; level 3: max total size
        self.used = 0
        self.d = OrderedDict()      # key -> (value, size, expires_at), least recently used first
        self.expiry = []            # level 2: heap of (expires_at, seq, key); stale rows are skipped
        self.seq = count()          # tie-breaker, so the heap never compares keys

    def _drop(self, key):
        _, size, _ = self.d.pop(key)
        self.used -= size

    def _expire(self, now):         # level 2: dead entries go before anything else is decided
        while self.expiry and self.expiry[0][0] <= now:
            exp, _, key = heapq.heappop(self.expiry)
            if key in self.d and self.d[key][2] == exp:   # skip rows a rewrite made stale
                self._drop(key)

    def get(self, key, now):
        self._expire(now)
        if key not in self.d:
            return None
        self.d.move_to_end(key)     # level 1: a read is a use
        return self.d[key][0]

    def put(self, key, value, now, ttl=None, size=1):
        self._expire(now)
        if size > self.budget:      # level 3: it can never fit, so evicting everything is wrong
            return False
        if key in self.d:
            self._drop(key)         # a rewrite replaces; it is not an insert
        while self.used + size > self.budget:
            self._drop(next(iter(self.d)))                # level 1: evict least recently used
        expires_at = None if ttl is None else now + ttl
        self.d[key] = (value, size, expires_at)
        self.used += size
        if expires_at is not None:
            heapq.heappush(self.expiry, (expires_at, next(self.seq), key))
        return True

The design survives all three because of three decisions made early: time is a parameter rather than a global, a rewrite is a replacement rather than an insert, and eviction is a loop against a byte budget from the start. Cost:

get

and non-evicting

put

are O(1) amortised; each expiry costs O(log n) once, and the heap skips rows that a rewrite made stale. Say aloud what you would change for threads (one lock, since a read mutates recency) and for scale (shard by key).

Safety literacy for the values conversation

It is not a culture-fit chat and it is not a formality. Treat it as a technical round about judgement, and read the primary documents rather than summaries.

You are not asked to recite policy. You are asked to show you have thought about deployment risk, so your answers should be able to cite the real documents accurately. Four are worth an hour each.

The Responsible Scaling Policy

A voluntary framework of if-then commitments: if a model crosses a capability threshold, stricter safeguards apply, grouped into AI Safety Levels. Anthropic says it activated ASL-3 safeguards for relevant models in May 2025. Version 3.0 (24 Feb 2026) was a comprehensive rewrite that separates what Anthropic commits to alone from what it recommends for the industry, adds a published Frontier Safety Roadmap and periodic Risk Reports, and admits that capability thresholds proved ambiguous in practice. The current version is 3.4 (8 Jul 2026).first-party6364

Constitutional AI

The 2022 paper trains a harmless assistant with no human labels for harmful outputs, only a list of principles: a supervised phase of self-critique and revision, then reinforcement learning from AI feedback (RLAIF), yielding an assistant that explains its objections rather than evading.65 See the paper walkthrough.

Claude’s constitution (January 2026)

The newer document replaced a list of standalone principles with explanations, on the argument that models generalise better when they understand why. It asks Claude to be broadly safe, broadly ethical, compliant with Anthropic’s guidelines and genuinely helpful, generally prioritised in that order.first-party66

Connect it to the job

For each document, prepare one sentence on what it changes for a customer deployment: why a guardrail layer exists, why you would refuse a use case, how you would explain a refusal to a stakeholder.

Question shapes to expect

  • “A customer wants to use the system for something you think is a bad idea. What do you do?”
  • “Tell me about a time you were wrong and it mattered.”
  • “What would make you refuse to ship something?”
  • “Describe a risk you flagged that was inconvenient.”

What separates a pass from a fail

  • Specificity. A real situation with stakes and an outcome, not a principle.
  • Consistency. Values answers must match your technical answers.
  • A real change of mind. Someone who never updated a strong opinion reads as untested.
  • Cost acknowledged. A delay, a hard conversation, a lost deal.

Write down three situations where doing the right thing cost you something, and one where you got it wrong and can say exactly why. Memorise the situations, not the wording — memorised answers are audibly memorised.

Complexity and trade-offs of the cache

n

is live entries;

h

is heap rows, which includes stale rows that rewrites and evictions leave behind.

CaseTimeSpaceWhy
getO(1), plus any expiry duenone
move_to_end
on an OrderedDict is constant time.
put, no TTL, fitsO(1)one entryA dict insert and a size update.
put with a TTLO(log h)one heap rowThe heap push is the O(log n) the page charges once to each expiry.
put that evicts k entriesO(k), O(1) amortisedfrees k entriesEach entry is inserted once, so it can be evicted at most once.
_expire popping m rowsO(m log h)frees up to m entriesEach row is popped once, so the cost is charged to the put that pushed it.
Memory overallO(n + stale rows)Rewrite one hot key 1,000 times a second with a 1-hour TTL and up to 3,600,000 stale rows wait in the heap. Rebuild it when stale rows outnumber live entries.

The alternatives are worse in a way worth naming. Expiring only when an entry is read is O(1), but dead entries then keep their slots, which is the level 2 bug. Scanning every entry for expiry on each call is correct but O(n) per call. The lazy-deletion heap is the middle path, and its price is the stale-row memory in the last row.

Common mistakes on the escalating cache

  • Reading the clock inside the classCalling 
    time.time()
    in 
    get
    makes every TTL test depend on timing, and level 2 is graded by tests. Take 
    now
    as a parameter from level 1, even before anything expires.
  • Evicting before expiringIf the eviction loop runs first, it can throw out a live entry to make room while an expired one still holds its slot. Call 
    _expire(now)
    at the top of both 
    get
    and 
    put
    .
  • Counting a rewrite as an insertWriting an existing key without dropping it first adds its size to 
    used
    twice. The cache then evicts entries it did not need to, and the drift grows with every rewrite.
  • Evicting before the oversize checkAn item larger than the whole budget will never fit. Check that first. Otherwise the loop empties the cache trying to make room, and then rejects the item anyway.
  • Deleting stale heap rows eagerlyFinding and removing a key’s old row from a heap is O(h). Leave it, and skip it when it is popped by checking that the stored expiry still matches. That is what 
    self.d[key][2] == exp
    does.

Check yourself

Budget 10. put a (size 4), put b (size 4), get a, then put c (size 5). What is in the cache, and what is used?

a and c, with used = 9. The read made a the most recent, so b is least recently used. 8 + 5 = 13 is over 10, so b goes, leaving 4 + 5 = 9. One eviction was enough, so the loop stops.

At t=0 you put x with ttl 5. At t=3 you put x again with ttl 100. What does get(x) return at t=6?

The new value. At t=6 the old heap row (expires 5) is popped, but the stored entry now expires at 103, so the check fails and the row is skipped. The row for 103 stays in the heap.

The cache from the first question holds a and c. You put k with size 11. What happens?

put

returns False and nothing changes: a and c stay, used stays 9. The oversize check runs before the eviction loop. If it ran after, the loop would have evicted both and then still failed.

You are asked to make it thread-safe. Is a read-write lock, with get taking the read lock, enough?

No.

get

writes: it moves the key to the end of the recency order and may expire entries. Two readers holding a shared lock would modify the OrderedDict at the same time. Use one exclusive lock, as the page suggests, and shard by key if that lock becomes the bottleneck.

Quick answers

What is the Anthropic Applied AI Engineer interview process?

Anthropic does not publish the structure. Candidate reports and prep guides describe roughly five stages: a recruiter screen, a timed coding assessment, an applied-AI technical conversation covering retrieval, agents, tool schemas and evals, a customer scenario, and a values and safety conversation. Anthropic confirms that technical roles use live coding tools such as Colab and CodeSignal. Treat the stage list as approximate.

Can I use AI in the Anthropic interview?

Anthropic’s published guidance says to write application drafts yourself and then refine them with Claude, to complete take-home assessments without Claude unless told otherwise, and to use no AI assistance in live interviews unless Anthropic indicates it is allowed. It encourages using Claude to research the company and practise answers. If an assessment email does not explicitly allow AI, assume it is not allowed.

What should I know about safety for the Anthropic values round?

Prep guides expect conceptual familiarity with the Responsible Scaling Policy, Constitutional AI, and the difference between alignment and capabilities work. Read the primary documents: the RSP and its version 3 announcement, the Constitutional AI paper, and Claude’s January 2026 constitution. Then connect each to a customer deployment decision, such as when you would refuse a use case.

What coding questions does Anthropic ask forward deployed engineers?

Reports differ. A 2024 applicant describes two LeetCode-style questions in 60 minutes; a 2026 prep vendor describes one problem growing over four levels in about 90 minutes. Anthropic has not confirmed either. Both reward fundamentals and a design that can absorb the next requirement, so practise a cache or in-memory store that gains expiry and size limits.

What does Anthropic want from a forward deployed engineer?

The posting describes embedding with strategic customers to build production applications on Claude, with deliverables that include MCP servers, sub-agents and agent skills, frequent travel, and production experience with LLMs and agents. That makes it the most agent-shaped FDE role among the frontier labs, so fluency in tool schemas, sub-agent decomposition and agent failure modes is directly on topic.
