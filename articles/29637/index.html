Databricks FDE Interview: Spark, Unity Catalog, and Genie

Original title: Databricks FDE 面试：Spark、Unity Catalog 与 Genie

Databricks' job posting for a Forward Deployed Engineer (FDE) in Seoul is explicit: candidates need deep experience with Apache Spark-based distributed computing and an understanding of Spark runtime internals. By contrast, Genie and Unity Catalog appear only in the company introduction, not in the job requirements.

To pass the hiring process, focus your preparation on Spark. But according to the official documentation, deploying Unity Catalog and Genie is a test of access permissions, metadata, and business rules.

Spark: learn it well enough to explain why a job is slow

The Seoul role requires 7+ years of experience in data engineering, data platforms and analytics, or software engineering; the ability to program in Python, Scala, or JavaScript/TypeScript; and about 20% of your time traveling to customer sites. The Senior FDE role for the national security business keeps the same Spark requirement, lowers the bar to 6+ years, and adds hands-on experience requirements for MLOps, ML/AI models, and AI APIs.

"Runtime internals" sounds vague, but it boils down to three concrete things. The first is shuffle: joins and aggregations move data between nodes,

spark.sql.shuffle.partitions

and by default this work is split into 200 partitions.

The second is Adaptive Query Execution (AQE), enabled by default since Spark 3.2.0. AQE uses runtime statistics to coalesce partitions that are too small after a shuffle and to split skewed partitions in sort-merge joins. The third is broadcast join: tables smaller than

spark.sql.autoBroadcastJoinThreshold

(10 MB by default) are sent directly to every worker, skipping the shuffle.

A good exercise is to deliberately slow down a job, then read the Spark UI. Join a large table with a small one, open the SQL tab, click Details, and check whether the physical plan uses BroadcastHashJoin or SortMergeJoin. Set the threshold to -1 to disable broadcasting, rerun, and compare the runtimes.

Then open the detail page of the slowest stage. The Summary Metrics table shows the distribution of task runtimes: if the slowest task is many times slower than the median, the data is likely skewed. The Shuffle Read Size and Shuffle spill (disk) columns show how much data was moved and whether it spilled to disk.

Practice describing what you see using real numbers from the UI. In an interview, this is the most concrete way to prove you understand Spark internals.

Unity Catalog answers "who can see what"

Databricks defines Unity Catalog as a unified governance layer for data and AI built into the platform. All objects live in a

catalog.schema.object

three-level namespace. Tables and volumes can be managed (Unity Catalog handles both governance and the lifecycle of the underlying storage files) or external.

According to Microsoft Learn, Unity Catalog is enabled automatically for Azure Databricks workspaces created after November 9, 2023, and Unity Catalog also has an open-source version. So at customers using newer workspaces, you will likely deal with it from day one.

The documentation divides Unity Catalog's capabilities into several areas, three of which are most worth learning first: permissions, lineage, and audit logging. Permissions are implemented through privileges, attribute-based access control (ABAC) policies, row filters, column filters, and workspace bindings.

Lineage records the path from source data to models, services, and dashboards without manual configuration; all data access and system activity is written to system tables dedicated to audit logs, which is exactly what compliance teams need.

Example: each partition sees only its own data

Suppose a retail chain has a

sales.core.orders

table with a

region

column. The requirement: the Vietnam analyst group can only see orders from Vietnam, while the admin group can see everything. The first step is to grant read access:

GRANT USE CATALOG ON CATALOG sales TO `analysts_vn`;
GRANT USE SCHEMA ON SCHEMA sales.core TO `analysts_vn`;
GRANT SELECT ON TABLE sales.core.orders TO `analysts_vn`;

With only GRANT SELECT, the group can still read all rows. To restrict by region, you need to write a function that returns true or false for each row, then attach it to the table:

CREATE FUNCTION sales.gov.region_filter(region STRING)
RETURN IF(is_account_group_member('admins'), true, region = 'VN');

ALTER TABLE sales.core.orders
SET ROW FILTER sales.gov.region_filter ON (region);

After that, the same

SELECT * FROM sales.core.orders

query returns two different results depending on who runs it. The access logic lives on the table, not scattered across dashboards. At a customer, first work with the data owner to agree on a mapping of "who can see which rows" before writing the function.

Two details in the documentation are worth remembering. The function's parameter type must match the column type: if they don't match and ANSI mode is off, values that can't be converted become NULL, and the filter may return the entire table without raising an error.

Also, if multiple tables need the same rule, Databricks recommends using ABAC policies attached at the catalog or schema level rather than attaching row filters table by table.

Genie is built on top of Unity Catalog; if the permissions are wrong, the answers are wrong

According to the September 2026 documentation, Genie is now a product family that includes Genie One, Genie Agents, and Genie Code. Genie Agents are environments organized by business domain, where data teams configure trusted data, metrics, and business rules, and Genie One relies on these to answer questions.

The naming has changed too: the current overview page no longer uses the term "Genie space." When referring to older tutorials, check their update dates first.

Databricks states that every Genie answer is based on the organization's own data and passes through Unity Catalog's governance layer.

The practical implication: the row filter in the example above also determines what Genie users in Vietnam can see. If the permissions are sloppy, Genie will hand that error directly to business users, wrapped in a very convincing answer.

Setting up a Genie agent is a configuration task: choose datasets, write example queries, write instructions. After that, quality is tuned through metrics, business rules, and verified answers. For example, if a customer defines "net revenue" as net of returns, that must be written as a business rule; the most frequently asked question this week should have a verified answer.

According to the documentation, users can use Genie One and Genie Agents for free until January 31, 2027, excluding service principals. Now is a great time to start practicing.

What to learn first, and what to put on your resume

The sensible order is to learn Spark and Spark UI first, since that's the entry point. Next comes Unity Catalog governance for SQL: GRANT, row filters, column filters, reading lineage and audit logs. Genie Agents come last, because they depend on the two layers below.

Don't write "familiar with Databricks" on your resume; write specific work instead: "Used Spark UI to locate data skew in a join, reducing job runtime from X to Y," or "Designed region-based row filters for an orders table and verified them through audit logs."

When reading a job description, don't skip products that only appear in the company introduction. They are often exactly what you'll be deploying; and for Genie, answer quality depends on the permission layer underneath.
