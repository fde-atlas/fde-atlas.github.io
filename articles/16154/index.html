Do FDEs need to know how to write code? And to what extent

Original title: FDE 需要会写代码吗？需要到什么程度

FDE中国 · 2026-09-07 · 2 min read

Summary

This article from FDE中国 argues that FDEs must write code—production-quality code, since their deliverables run inside customer businesses. It breaks coding requirements into three tiers: building usable end-to-end systems is the baseline; reading and modifying legacy code on-site is a plus; deep performance and architecture optimization is rarely required. Against the claim that AI coding tools make coding skills obsolete, the author argues the opposite: tools raise customer expectations for delivery speed and amplify those who can code. The core value of coding is shortening the idea-to-verifiable cycle, which is what interviews actually test. Readers are advised to build a minimal retrieval-plus-tool-calling scenario in a week to gauge their level.

Key points

  • FDEs must write production-quality code; prototypes and slides don't count as deliverables.
  • Three tiers: end-to-end building is baseline, legacy-code modification is a plus, deep optimization rarely needed.
  • AI coding tools amplify skilled coders rather than replace coding ability.
  • Coding's main purpose is shortening the idea-to-verifiable cycle, which interviews screen for.
  • Exercise: independently build a minimal retrieval and tool-calling scenario within a week.

Full text

This piece answers the capability threshold question that aspiring candidates care about most. The most valuable takeaway is the three-tier breakdown of coding requirements: being able to build a usable end-to-end system is the baseline, being able to read and modify legacy code on the customer's site is a plus, and performance- and architecture-level optimization is usually not required. The most commonly misapplied judgment is holding FDEs to big-tech backend standards, or conversely assuming that "knowing how to call APIs" is enough—both lead to hiring the wrong people or practicing in the wrong direction. Compared with the popular claim that "FDEs don't need to write code," this article's incremental insight is: AI coding tools have indeed lowered the barrier to entry, but they have also simultaneously raised customers' expectations for delivery speed, widening the output gap between those who can use the tools and those who can't—making coding skills more valuable, not less. Another judgment worth noting: the main purpose of coding ability is to shorten the cycle "from idea to verifiable result," and what interviewers are really screening for is how short that cycle is, not how many frameworks you know; understanding this makes your practice direction much clearer. After reading, do one thing: spend a week independently building a minimal scenario that includes retrieval and tool calling, and test your true level.—FDEChina Editorial Team · Practitioner's Perspective

Do FDEs need to know how to code?

Yes, and you need to be able to write "production-ready" code. An FDE's deliverable is a system that runs inside a customer's business, not a prototype or a slide deck, so writing code is a fundamental requirement of this role, not a bonus. But let's clarify the other end: an FDE's coding requirements differ from those of a senior backend engineer—you don't need to design architectures for millions of concurrent users; what you need is to quickly build an end-to-end usable system and get it running stably in a real environment.

Breaking it down, an FDE's coding ability falls roughly into three tiers. The foundation is engineering fundamentals: proficiency in Python or TypeScript, familiarity with Git, the ability to write tests, and the ability to read legacy code on the customer's site and make small, incremental changes. The middle tier is the LLM application stack: calling model APIs, orchestrating RAG retrieval pipelines, implementing tool calling and agent workflows, and building eval scripts. The top tier is deep optimization skills, such as inference performance tuning and large-scale data pipelines—having these is great, but most scenarios won't need them. For the complete capability model, see FDE Capability Model.

Some will ask: with AI coding tools this powerful, does coding ability still matter? Quite the opposite. AI coding tools lower the barrier to getting started, allowing one FDE to match the output of several people in the past, but the codebases at customer sites are real and carry historical baggage—someone who can't read code can't even give the tools proper instructions. Tools amplify those who can code; they cannot replace those who can't. This is explored in detail in FDE's AI Workflow. For related tooling practices, also see AI Coding Special.

There are two common misconceptions. One is measuring yourself against big-tech engineering interview standards and thinking that if you can't grind algorithm problems, you're not cut out to be an FDE—what FDE interviews actually assess is speed of engineering execution and scenario judgment; see What FDE Interviews Test. The other is thinking that being good at requirements analysis and communication lets you bypass code. In reality, every "small change" at a customer site ultimately lands in code—there's no way around it.

One-sentence conclusion: being able to write code, write it fast, and take responsibility for production—that's the entry bar for an FDE; how deep you need to go depends on the scenarios you face, not on some universal standard.
