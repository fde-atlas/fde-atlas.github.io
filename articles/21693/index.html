Legal DMS connector: iManage access and ethical walls

FDE Times · 2026-10-26 · 6 min read

Summary

Using Legora's FDE job ad as a starting point, this article argues that at law firms the connector matters more than the model. iManage and similar DMS platforms remain the system of record, and permissions plus ethical walls decide document access. The author proposes a shared interface with per-DMS adapters, user identity on every call, a six-cell permission test matrix, and common mistakes that kill reusability.

Key points

  • The DMS stays the system of record; connectors must not copy documents.
  • Access is decided by DMS permissions; an ethical-wall leak is a serious incident.
  • One shared interface plus adapters lets connection methods shift from REST to MCP.
  • Every call carries the user's identity; never use a service account.
  • Rerun the six-cell permission matrix after every permission change.

Legora's FDE job ad shows that document systems such as iManage remain the system of record, and that access rights on each matter decide what gets built.

In brief

  • Legora's FDE job ad asks for knowledge of iManage, SharePoint or NetDocuments, SSO (SAML, OIDC), REST and webhooks, and assigns the job of writing reusable connectors.
  • Rule one: the original DMS remains the system of record. DMS permissions and the firm's ethical walls decide which documents each person can retrieve.
  • The connection method may shift from API to MCP, but the permission controls and the shared interface must stay the same.

In the first technical meeting at a law firm that wants its partners to query matter documents stored in iManage, the model barely comes up. The head of IT asks one question: if lawyer A is walled off from matter X, will your system show A a single page of matter X?

The job starts with that question. Legora describes its Forward Deployed Engineer role as sitting between product engineering and customer success. The engineer works alongside enterprise clients during and after deployment, writing production code that connects Legora’s platform to the client’s systems.

The job ad spells out what you need to know: document management systems such as iManage, SharePoint or NetDocuments, SSO through SAML and OIDC, and REST-style APIs and webhooks.

It also assigns a specific responsibility: build and maintain connectors, automation scripts and reusable tools so that later deployments run faster.

The skill is not specific to Legora. It transfers to any company that sells software into an industry with sensitive data.

Who owns the document?

When Legora launched its integration ecosystem in October 2026, it stressed one principle: lawyers can browse, search and work with matter documents inside Legora, but the underlying platform remains the system of record. It reads like a line for the marketing team. In practice it is the most important design requirement for the connector.

The principle has two consequences. The DMS keeps the official copy of each document, along with its versions, metadata and edit history, so the connector must not create a copy that slowly drifts from the original. And access is decided by the DMS, not by you.

According to LawNext, in the iManage integration, iManage permissions determine what each user can retrieve. Artificial Lawyer also reported that the ethical walls and security restrictions a firm already applies determine what Legora is allowed to access.

An ethical wall blocks a lawyer from a file where there is a conflict of interest. A document slipping through that wall is a serious incident, well beyond an ordinary bug.

One interface, many adapters

Why does the job ad stress the word “reusable”? One firm uses iManage, the next uses NetDocuments, the one after keeps everything in SharePoint. If you start from scratch each time, your experience never compounds.

A sensible split is one shared interface for the application to call, with a separate adapter for each DMS underneath. The sketch below illustrates the design; it is not Legora’s code:

from typing import Protocol

class DMSConnector(Protocol):
    def search(self, user: UserIdentity, query: str,
               matter_id: str | None = None) -> list[DocRef]: ...
    def fetch(self, user: UserIdentity, doc: DocRef) -> DocContent: ...
    def handle_event(self, event: dict) -> None: ...  # webhook: doc moved, permission changed

class IManageAdapter:
    def search(self, user, query, matter_id=None):
        token = self.tokens.for_user(user)  # user's own token, never a service account
        return self.client.search(query, matter=matter_id, auth=token)

    def fetch(self, user, doc):
        token = self.tokens.for_user(user)
        # the DMS checks permissions again on every read
        return self.client.get_document(doc.id, auth=token)

    def handle_event(self, event):
        if event["type"] in ("permission_changed", "document_moved"):
            # drop results computed under the old permissions
            self.cache.invalidate(matter_id=event["matter_id"])

The detail that matters is that

UserIdentity

appears in every function. Each call carries the identity of the person asking, taken from SSO (SAML or OIDC), and the adapter uses that same identity to call the DMS. The DMS then filters by that person’s permissions, on both search and open, and you never have to reimplement the access logic.

The design also pays off when the connection method changes. According to LawNext, Legora has integrated with iManage through its API and plans to connect to the iManage MCP Server as well.

The ecosystem launch announcement also said iManage and NetDocuments are connected through the Model Context Protocol for knowledge and search. If the connection type lives only in the adapter, you can swap the adapter without touching the interface or the permission tests.

A six-cell matrix before go-live

Ethical walls should be tested the way security is tested. Take a hypothetical scenario with two matters and three lawyers. An works on matter 1001. Binh works on matter 1002. Chi is a lawyer at the firm who has never worked on matter 1001, but is blocked from it by an ethical wall because of a conflict of interest.

UserSearch in matter 1001Search in matter 1002
AnReturns resultsEmpty
BinhEmptyReturns results
Chi (walled off from 1001)Empty, even when typing the exact document nameEmpty

Three people times two matters makes six cells, and each cell is an automated test. The cell that matters most is Chi’s in matter 1001. If the search index was built with a service account that can read everything, that cell will almost certainly return results, which means a leak.

Run the matrix again after every permission change. Remove An from matter 1001 in the DMS, send the webhook event to

handle_event

, then check that An’s next search comes back empty. This is exactly where a stale cache tends to break things quietly.

End to end at the client

Legora gives its FDEs the whole of technical scoping, from gathering requirements to designing the integration architecture. At a law firm, the scoping session should answer four questions. Which DMS, and is it cloud or on-premise? Does SSO use SAML or OIDC? Where are ethical walls configured? Does the DMS emit webhooks when permissions change?

After that, the order of work should be: interface, adapter, identity mapping, test matrix, webhook handling, and only then the question-answering feature. Many teams do it the other way round because question answering impresses in a demo. A single data leak is enough to lose the contract.

The last step, often skipped, is feeding what you learned back to Engineering and Product. Legora’s job ad states that FDEs work with both teams to improve the integrations and the shared product.

If you find yourself writing the same permission-group mapping for three clients in a row, that is a sign it belongs in the standard connector.

Mistakes that make a connector impossible to reuse

The most common mistake is copying the whole DMS into a separate store to make search faster. That breaks both principles: the copy drifts from the system of record, and permissions freeze at the moment of copying.

The second is letting client-specific logic leak into the shared interface, such as a field called

matter_code_format_firmB

. Every difference belongs in the adapter or a configuration file.

The third is skipping identity mapping. The email in SSO and the username in the DMS do not always match. Map one person wrongly and the test matrix becomes meaningless.

Showing the skill on a CV

When reading FDE job ads, look for phrases such as “reusable connectors”, named DMS products, SAML/OIDC and webhooks. They signal that the work leans toward integration rather than demos.

On a CV, don’t just write “integrated SharePoint”. Write that you built a connector, reused it across a number of deployments, tested permissions with a stated number of test cases and let no document through an ethical wall. A recruiter reading that line will see you have actually answered the head of IT’s question.

Models will keep changing, and so will connection methods, from REST to MCP to whatever standard comes next. The question of who may see what will not change, and the FDE who answers it with tests rather than promises is the one clients trust.
