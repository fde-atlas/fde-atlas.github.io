How to Build an FDE Portfolio: Agent Evals and pass^k

Original title: FDE 作品集怎么做：Agent 评测与 pass^k

FDE Times · 2026-10-09 · 7 min read

Summary

This FDE Academy guide explains how forward deployed engineers should build a portfolio repo: instead of polished demos, show where an agent fails on real, messy enterprise data. Using an invoice-matching agent as an example, it walks through five steps: picking a scoped MVP problem, keeping the agent loop readable while investing in tool descriptions, logging every run as JSONL, building evals from real failures with cheap assertions, and writing a case-study README plus a manager-oriented video. It recommends reporting pass^k — the probability all k attempts succeed — noting that an 80%-accurate agent passes three consecutive runs only about 51% of the time. The approach draws on Anthropic, OpenAI, and Hamel Husain's eval guidance.

Key points

  • One deployed case study beats eight polished demos; use real dirty data.
  • Keep the agent loop simple and invest effort in tool descriptions.
  • Log every run, then mine logs for eval cases based on real failures.
  • Start with cheap code assertions, report pass^k with case counts noted.
  • README should read like a case study and honestly list unresolved failures.

An agent that's 80% correct on a single run is only 51% correct across three consecutive runs; evals based on real failures beat polished demos.

Key Takeaways

  • One deep project with a case study beats many polished demos; pick a real enterprise scenario with messy data.
  • Keep the agent loop simple and readable, invest your effort in tool descriptions, and log every run from day one.
  • Build evals from real failures, start with low-cost assertions, report pass^k, and read the run logs to validate your graders.

Suppose your agent gives the correct answer in 80% of runs. That sounds good, until you calculate the probability that it gets three consecutive runs right: 0.8 × 0.8 × 0.8 = 51.2%.

So a Forward Deployed Engineer (FDE) portfolio repo can't stop at a demo that runs nicely. A demo is a single attempt. A repo worth showing must explain where the agent fails, how often it fails, and how you handled each failure. The measurement methods in this article draw on advice about evals for AI systems from Anthropic, OpenAI, and Hamel Husain.

A guide on the blog of the training company FDE Academy puts it bluntly: one project that was actually deployed and written up as a case study carries more weight than eight polished demos.

That's advice, not a law, but the logic is easy to grasp: a system that runs on real data demonstrates more capability than eight prototypes running on clean data.

Below, we walk through five steps for building such a repo. The code in this article is simplified for illustration: the functions that call the model are left empty so you can plug in your own SDK.

Step 1: What kind of problem is "enterprise-grade" enough?

The same FDE Academy guide recommends: pick an enterprise scenario close to reality, build only a minimum viable product (MVP) rather than the full vision, and use real or near-real messy data. That last condition is exactly what separates an FDE portfolio from a coursework assignment.

Imagine a distribution company that receives supplier invoices by email. Some are PDFs printed at an angle and then scanned; currencies are written sometimes as "VND", sometimes as "đ"; some tax IDs are missing a few digits. The MVP does one thing: the agent reads the invoice, compares it against the purchase order, and returns "match", "mismatch" with a reason, or "needs human review".

invoice-agent/
  agent/loop.py        # 核心循环
  agent/tools.py       # 工具及其描述
  data/raw/            # 脏发票
  logs/                # 每次运行一个 JSONL 文件
  evals/cases.jsonl    # 用例集
  evals/test_basic.py  # pytest 风格的断言
  README.md

(Annotations in order: core loop; tools and their descriptions; messy invoices; one JSONL file per run; the case set; pytest-style assertions.)

Check: You can state the MVP's scope in one sentence. If that sentence contains "and" more than twice, keep cutting.

Step 2: Why must the core loop be readable in five minutes?

In "Building effective agents", Anthropic recommends finding the simplest solution first and adding complexity only when truly needed. It also warns that frameworks tend to pile on layers of abstraction that hide the underlying prompts and responses. For a portfolio, this is a fatal flaw: if reviewers open the repo and can't find the prompts, they can't judge your thinking.

# agent/loop.py — 精简示意
def run(invoice_text, po, call_model, tools, log):
    messages = [system_prompt(), user_msg(invoice_text, po)]
    for step in range(8):                  # 限制步数上限
        reply = call_model(messages, tools)
        log.write(step, messages, reply)   # 记录一切
        if reply.tool_call is None:
            return parse_verdict(reply)
        result = tools[reply.tool_call.name](**reply.tool_call.args)
        messages += [reply, tool_result(result)]
    return {"verdict": "needs_review", "reason": "步数用尽"}

(Annotations mark the step limit and log everything; the fallback returns the reason "step limit reached".)

What's truly worth the effort is the tools. Anthropic calls this the agent-computer interface and recommends designing it carefully: write thorough tool documentation and test it. In this repo, every tool's docstring should specify the input format, when it returns empty, and include an example.

def lookup_po(po_number: str) -> dict:
    """按 PO 编号查询采购订单。
    po_number：'PO-' 加 6 位数字，例如 'PO-004512'。
    未找到时返回 {}；不要猜测相近的编号。"""

(The docstring means: look up the purchase order by PO number; the format is 'PO-' plus six digits, e.g. 'PO-004512'; return {} when not found, and do not guess at similar numbers.)

Check: Hand the

loop.py

to someone who has never seen the repo. After five minutes of reading, they can explain what the agent does.

Step 3: Log first, write evals later

OpenAI's "Evaluation best practices" recommends logging everything during development and later mining the logs for eval cases. Hamel Husain goes further in "Your AI Product Needs Evals", arguing for removing every obstacle to looking at the data. If viewing a single run requires opening three files and endless scrolling, you'll soon stop looking.

The easiest approach is to write one JSONL line per run, containing the input, every tool call, and the final conclusion. Then write a small script that prints each run to the terminal in a readable form.

On the

data/raw/

, run the agent 20-30 times and read each one. You'll likely discover failures you didn't anticipate, such as whether the agent reads "1.200.000" (Vietnamese notation, using dots as thousands separators) as one million two hundred thousand or as 1.2.

Check: You have a personally compiled list of real failures, each with the path to the corresponding log file.

Step 4: Build evals from failures, not from theory

Anthropic's definition of an eval is simple: give the AI system an input, then apply scoring logic to its output to measure success. In its view, extracting 20-50 simple tasks from real failures is already a good starting point. The failure list from Step 3 is the raw material for your eval set.

{"id": "c07", "invoice": "data/raw/inv_07.pdf", "po": "PO-004512", "expect": "mismatch", "must_mention": "quantity"}

Husain recommends starting with fast, low-cost assertions—the kind you'd write in pytest anyway. Whatever code can check, let code check; only what code can't check should be graded by a model.

# evals/test_basic.py — 示意
@pytest.mark.parametrize("case", load_cases("evals/cases.jsonl"))
def test_verdict(case):
    out = run_case(case)
    assert out["verdict"] == case["expect"]
    assert case["must_mention"] in out["reason"]
pytest evals/ -q

According to Anthropic, agent evals typically combine three types of graders: code-based, model-based, and human. For a portfolio repo, the code layer should be solid. Add a model-based grader to judge whether the agent's stated reasoning holds up, and state clearly in the README which parts are graded by humans.

OpenAI calls this practice eval-driven development: eval early, eval often, and write tests for every stage.

The number at the top of your README should be pass^k. Anthropic distinguishes between pass@k and pass^k: pass^k is the probability that all k attempts succeed. The calculation at the start of this article is exactly the pass^3 for an agent that's 80% correct on a single run, assuming runs are independent: 51.2%.

Imagine an accountant who uses this agent three times a day. The probability that all three runs on a given day are correct is only slightly above half—in other words, roughly every other day they'll hit an error.

Interpret this number cautiously while the case set is still small. With only 20 cases, flipping a single case changes pass^k by 5 percentage points; the smaller the k, the more easily the luck of a single run makes the numbers look good.

In practice, run each case at least three times, rerun the whole eval set to see whether the numbers fluctuate, and always note the number of cases and the value of k alongside the results.

The final step of evals is the one most often skipped. Anthropic emphasizes that without reading the run logs and scores from multiple attempts, you can't know whether your grader is scoring accurately. Randomly pick ten runs graded as "pass" and read them again. A grader that's too lenient is more dangerous than a weak agent.

Check:

pytest

The full case set can run to completion, but not everything needs to pass. The cases come from real failures, so some staying red is normal—those red cases are your to-do list. The README should state the number of passes out of the total, along with a pass^3 table broken down by failure category.

Step 5: README and video for people who don't run code

GitHub Docs lists the questions a README should answer, and the first is what the project does. For an FDE repository, the README should read like a short case study.

It should include: the hypothetical customer's problem, the MVP scope and what you deliberately left out, eval results with pass^k, three failures that remain unresolved, and what you would do with two more weeks.

The "remaining failures" section is worth writing carefully. It shows readers that you can measure your own system and be honest about its limitations.

Make the 3-minute video for managers, not engineers. One way to allocate it: 30 seconds to explain the problem, 90 seconds to run the agent on

data/raw/

a real dirty invoice, 45 seconds to open the eval results and read out pass^k, and the final 15 seconds on one failure you haven't fixed. Don't record yourself typing code.

Common mistakes

The most common mistake is picking a heavyweight framework before understanding the requirements, leaving prompts buried under five layers of classes. The second is using clean data you generated yourself, where evals are all green but prove nothing. The third is reporting only your best run instead of pass^k.

How does this skill transfer to customer projects?

These five steps aren't just for a portfolio; they're habits you'll need in customer deployments, and the repository is where you practice them first.

On your resume, don't write a vague "built an AI agent"; write a sentence with numbers, such as "built 40 eval cases from real failures, improving pass^3 from X to Y," where X and Y come from your own repository. If the job description mentions "evaluation" or "reliability," include a link to this repository when you apply.

Let the repository answer in advance the question every customer will eventually ask: where does the agent fail, and how often?
