Executive-Communication-Framework

Original title: Executive-Communication-Framework

FDE中国社区 · 2026-07-12 · 4 min read

Summary

This article documents an Executive-Communication-Framework skill package from the FDE China community, designed for forward deployed engineers who must win continued executive support. It prescribes a pyramid structure—conclusion first, then three supporting arguments, data, and a recommended action—covering what executives care about: ROI, risk, timing, competitors, organizational impact, and exit options. It defines five scenarios (project approval, phase review, budget increase, renewal, and stop-loss decisions), execution steps including a 15-minute rehearsal, common pitfalls, stage gates, and collaboration interfaces with roles like AIBP and business owners. Deliverables include a one-page executive brief, deck outline, decision options table, and simplified ROI sheet, packaged for import into Claude, Cursor, or Codex.

Key points

  • Core method: pyramid structure—conclusion, three arguments, data, recommended action.
  • Covers five scenarios: approval, review, budget increase, renewal, stop-loss.
  • Deliverables: executive one-pager, deck outline, decision options table, ROI sheet.
  • Pitfalls: tech-only talks, unsupported ROI, missing exit options, overtime.
  • Package includes checklist, evaluation, prompt, README for Agent Skills tools.

Problem Definition

Executives don't have time for technical details; if an FDE can't articulate ROI and decision options, the project struggles to sustain support.

Methodology Framework

Pyramid structure: Conclusion → 3 supporting arguments → data → recommended action. Executives care about: ROI, risk, timeline, competitors, organizational impact, exit options. One-pager: problem/solution/metrics/investment/risk/decision request.

FAQ

Q1: When executing the [Executive-Communication-Framework], how do you avoid "presenting technology instead of decisions"?

A: Follow the README methodology step by step and present interim deliverables at weekly Demos; if PoC materials are incomplete, first produce a "pending verification list" before proceeding.

Q2: What additional constraints apply in private deployment, Xinchuang (domestic innovation), or MLPS (classified protection) environments?

A: Specify the deployment model in the prompt constraints section; when data cannot leave the domain, domestic components, or audit logs are involved, reference Private-Deployment-Gateway and RBAC-Audit accordingly.

Q3: What if the division of responsibilities with AIBP is unclear?

A: Return to the AIBP-Collaboration-Playbook to update the RACI; AIBP owns Ground Truth and business acceptance, while the FDE owns deliverable technical assets.

Q4: After the PoC passes, how do we transition to Beta/production?

A: Mark the next-stage Skill in the deliverables (e.g., RAG-Evaluation→Private-Deployment-Gateway→FDE-Adoption-Growth), and trigger the launch gate via the checklist.
