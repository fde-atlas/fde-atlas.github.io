Docker Offline Deployment: FDE's Dockerfile Practices

Original title: Docker 离线部署：FDE 的 Dockerfile 实践

FDE Times · 2026-10-08 · 4 min read

Summary

This article reframes Docker as a delivery tool for FDEs rather than a development convenience: the image is what the customer's security team inspects. It identifies three common customer-side constraints—no internet, no root, and mismatched CPU architectures—and maps each to a fix: docker save/load for offline transfer via portable media, USER directives and rootless mode for unprivileged operation, and buildx --platform for cross-architecture builds. Citing NVIDIA's DGX OS 8 guide and Overleaf's offline deployment docs, it walks through a minimal multi-stage Dockerfile pinned by digest, and closes with advice for aspiring FDEs to rehearse the build-save-load flow between two machines before visiting a customer.

Key points

  • Images are deliverables; smaller and reproducible images clear customer security review faster.
  • Air-gapped servers receive images via docker save and load on portable media.
  • Use USER and rootless mode when services run without root privileges.
  • Match customer CPU architecture with buildx --platform before building.
  • Rehearse the full build-save-load flow between two machines beforehand.

No internet, no root, different chip architectures — Docker becomes the delivery tool, and the Dockerfile decides whether the customer lets your software through.

Key takeaways

  • For an FDE, a Docker image is the delivery package handed to the customer, not a development environment. The smaller, more reproducible, and less privileged the image, the easier it is to get approved.
  • The customer's infrastructure may be missing three things you take for granted: internet access (use save/load), root (use USER and rootless mode), and the same CPU architecture (use --platform).
  • Before your first on-site visit to a customer, run through the full build → save → load flow between two different machines.

NVIDIA's DGX OS 8 guide describes in plain terms the steps for getting a container image onto an air-gapped server: copy the image to portable storage (such as a USB drive), then bring it to the target system. No image registry, no

docker pull

. The way a DGX server gets software is much like installing an OS from a CD twenty years ago.

If you are a Forward Deployed Engineer (FDE), you will very likely run into exactly the same situation, and not just at NVIDIA: Overleaf wrote a complete guide specifically for customers deploying offline. Code written by developers runs on laptops and CI; an FDE has to make it run on infrastructure controlled by the customer, where there may be no internet access, root may be forbidden, and the chip may differ from yours.

So once it lands in an FDE's hands, Docker is no longer just a convenient development tool — it is a delivery tool. How the Dockerfile is written determines whether the customer's infrastructure team actually lets your software run.

The image is a delivery package, not a development environment

Docker officially describes Docker Engine as an open-source containerization technology for building and packaging applications. That's accurate, but not enough for an FDE. What you actually hand to the customer is the image, and everything inside it will be inspected by their security team.

That's why multi-stage builds matter far more here than for local runs. Multiple

FROM

instructions in one Dockerfile each start a new stage; the first stage contains the full compilers and libraries needed for building, and the final stage copies only the build artifacts. The Docker docs summarize the result in one sentence: a slim production image containing only the binary.

The less there is in the image, the fewer questions to answer, the less data to copy onto a USB drive, and the fewer potential vulnerabilities. By the same logic, a

.dockerignore

file keeps irrelevant files out of the build without restructuring the repository.

Three questions to ask the customer before building

First: can the server reach the internet? If not, delivery comes down to two commands.

docker image save

Writes the image to a tar file, including all parent layers and tags;

docker image load

Loads it back from the tar file — even if it was compressed with gzip, bzip2, xz, or zstd — and restores the tags as well.

Overleaf's on-prem deployment guide describes exactly this flow: move the .tar file to the offline server, then run

docker load

。

Second: does the service need root? Docker recommends that if the service can run without privileges, use

USER

to switch to a non-root user. Going further, rootless mode lets both the Docker daemon and containers run as a regular user, suitable for customers that forbid running the daemon as root.

Third: what chip does the server use? NVIDIA's guide requires pulling the image on a machine with internet access whose CPU architecture matches the isolated system. An image built on an ARM laptop won't run on an x86 server. With buildx's

--platform

flag for multi-platform builds, you can specify targets such as

linux/amd64

or

linux/arm64

.

A minimal workflow

Suppose you need to deliver a small service to a customer with an offline x86 server. The Dockerfile looks roughly like this; the part after

@sha256:

should be filled in with the real digest of the base image:

FROM golang:1.22@sha256:... AS build
WORKDIR /src
COPY . .
RUN go build -o /out/server ./cmd/server

FROM alpine@sha256:...
COPY --from=build /out/server /server
USER 10001
ENTRYPOINT ["/server"]

Two

FROM

lines, two stages, a final image containing only the binary, running as a non-root user. The base image is pinned by digest, because tags can change; Docker treats this as a supply-chain safeguard, but for an FDE the meaning is simple: the image you test today is exactly the image the customer loads next month.

On the machine with internet access, build for the correct architecture and package it:

docker buildx build --platform linux/amd64 -t acme/agent:1.4.0 .
docker image save acme/agent:1.4.0 | gzip > agent-1.4.0.tar.gz

After the file reaches the customer server via portable storage:

docker image load -i agent-1.4.0.tar.gz
acme/agent:1.4.0

The tags are restored as-is, and then you run the container as usual.

Docker won't check the infrastructure for you

Docker does exactly what you ask; whether that request fits the customer's server is your responsibility. NVIDIA requires pulling the image on a machine whose CPU architecture matches the isolated system, and for good reason: the architecture should be confirmed with the customer before you type the build command, not discovered while standing next to the server.

Unpinned tags are the same: the build still succeeds, but the next build may produce a different image.

Rootless mode also lives on the daemon side, meaning it must be configured on the customer's machine, not baked into your image. You can recommend enabling it, but it's the customer's infrastructure team that turns it on.

A non-root

USER

likewise only applies when the service genuinely can run without privileges. If the code needs to write to paths requiring root, fix the code first, not the Dockerfile.

What to learn first

If you're planning to move into an FDE role, don't start with container orchestration. First master multi-stage Dockerfiles, understand the difference between digests and tags, then run through the full build, save, load flow between two different machines, one of them offline. This takes one evening, and teaches you more than a week of reading docs.

Job-hunting tip: if a job description mentions on-prem, air-gapped, or deploying to customer-owned infrastructure, prepare a story about offline delivery before the interview.

On your resume, don't write "familiar with Docker" — instead state that you packaged and delivered a service that ran offline in a non-root environment, and include the image size before and after optimization.

The USB drive in NVIDIA's guide isn't a sign of backwardness. It's a reminder: on the customer's side, software is only truly delivered when it runs somewhere you don't control.
