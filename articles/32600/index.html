Agent SDK Comparison: Claude, OpenAI, and Google ADK

Original title: Agent SDK 选型：Claude、OpenAI 与 Google ADK 对比

FDE Times · 2026-10-08 · 6 min read

Summary

This article argues that choosing among Claude Agent SDK, OpenAI Agents SDK, and Google ADK should be driven by customer constraints, not benchmark scores. It proposes four questions to ask before writing code: where the agent runs and who operates it, whether the model is already fixed, how dangerous tool calls are intercepted, and who can access tracing. Key differences: OpenAI's tracing is on by default but unavailable under Zero Data Retention agreements; ADK offers Go and Java versions suited to on-prem deployments; Claude's deny hooks run even in bypassPermissions mode. The author advises FDEs to internalize these questions to avoid costly rewrites.

Key points

  • SDK choice should follow customer constraints, not leaderboards.
  • Zero Data Retention customers cannot use OpenAI's default tracing.
  • ADK's Go and Java support favors on-prem deployments.
  • Claude's deny hooks survive bypassPermissions mode.
  • OpenAI guardrails only cover the first and last agents in a chain.

How to choose among the three major Agent SDKs depends on customer constraints, not benchmark scores. Just ask four questions before writing any code.

Key Takeaways

  • Don't start from benchmarks; start from four questions: where does the agent run, which model does it use, who controls permissions, and who reviews the traces.
  • Customers using the OpenAI API under a zero data retention policy cannot use the tracing that the OpenAI Agents SDK enables by default. If the customer's team writes Go or Java, ADK has official libraries for both languages, while the Claude Agent SDK only offers Python and TypeScript.
  • The Claude Agent SDK's permission evaluation order is precisely documented: deny hooks run before every other step; ADK ships with tools for evaluating agent execution traces.

The OpenAI Agents SDK documentation states that tracing is enabled by default. The same documentation also states that organizations using the OpenAI API under a Zero Data Retention policy cannot use tracing. A default feature can disappear because of a single clause in the customer's contract.

This detail shows how Agent SDKs actually get chosen in real projects. Nobody picks from a leaderboard. The candidate list gets narrowed down step by step by constraints raised by the customer, usually in the first working meeting, and usually before anyone opens an editor.

For a Forward Deployed Engineer (FDE), this is a valuable skill. Pick the wrong framework in week one, and by week six you'll be rewriting the observability layer, the permissions layer, and sometimes even the model invocation layer. Below are four questions for choosing between the Claude Agent SDK, the OpenAI Agents SDK, and Google ADK, along with the pitfalls of each.

Where does the agent run, and who operates it?

Ask this question first, because it determines who is on call when the system breaks. According to Anthropic's documentation, the Claude Agent SDK packages the same agent loop, tool set, and context management that run inside Claude Code into Python and TypeScript libraries.

The agent is embedded in your application and runs in a process you operate yourself. The OpenAI Agents SDK is likewise a Python library, installed with pip and running in your own process; it also provides a sandboxed agent for executing tasks in an isolated workspace.

If the customer doesn't want to operate anything, Anthropic offers another product: Managed Agents. It is a managed runtime framework that handles the agent loop, with sessions running in Anthropic-managed cloud sandboxes or self-hosted sandboxes on the customer's own infrastructure.

When communicating with customers, keep these two products clearly distinct. Conflating them is the easiest way to make wrong promises about where data is stored.

Google ADK is open source and designed to be deployed anywhere: containerized on your own infrastructure, or deployed to Google Cloud with a single command. So all three can run on infrastructure controlled by the project team; the difference lies in the languages.

Suppose a bank only allows software to run in its own data center, and the internal team writes Java. ADK, which comes in Python, TypeScript, Go, Java, and Kotlin versions, should be at the top of the list.

The Claude Agent SDK only provides Python and TypeScript libraries. For other languages, Anthropic's documentation suggests running the Claude Code CLI as a subprocess and reading its JSON output. This works, but the customer's team has to maintain an extra integration layer.

Has the customer already chosen a model, or do they want to keep the option to switch?

Many customers have already signed contracts with a particular model vendor; others want to preserve the ability to switch later. These two types of customers need different advice.

The OpenAI Agents SDK supports non-OpenAI models through Any-LLM and LiteLLM, but the documentation classifies both integrations as beta with best-effort support only.

If the customer uses a different model, you must personally validate that vendor's performance on the project's real workflows before making any commitments. By contrast, ADK claims it can work with almost any generative model, not just Gemini, through adapters that connect to each vendor.

The Claude Agent SDK is built around Claude Code's own agent, so it's best viewed as a solution for customers who have already chosen Claude, not as an intermediary layer for switching models back and forth. The advice here is simple: if the customer says "we're not sure which model to use yet," don't pick an SDK based on your team's preference and then hope the adapters are good enough.

Who has the authority to intercept dangerous operations?

Agents that can call tools do real work: writing files, calling APIs, modifying data. So the customer's security team will ask what stops it from doing something wrong. Anthropic's documentation answers this in detail.

According to Anthropic's permissions documentation, every tool call is evaluated in a fixed order: hooks, deny rules, ask rules, permission modes, allow rules, and finally the canUseTool callback. Hooks run before everything else.

Even when the agent is in bypassPermissions mode, deny hooks still take effect. For agents running headlessly, Anthropic recommends combining allowedTools with the permissionMode "dontAsk" to lock down the set of permitted tools.

The OpenAI Agents SDK is deliberately minimal, with only a few basic primitives: agents, handoffs that let one agent pass work to another, guardrails, and built-in tracing. The pitfall lies in the guardrails: input guardrails only run on the first agent in the chain, and output guardrails only run on the last.

Suppose a customer service deployment chains three agents, and the middle one has the authority to issue refunds. If you put your checks in the input guardrail thinking it covers the whole chain, the middle agent won't be checked at any step.

The solution is to put the checks on the refund tool itself. The SDK provides tool guardrails for this: according to the documentation, any function tool with a guardrail attached runs the guardrail on every call, checking inputs before execution and outputs after.

Spell this out clearly in the design documents you send to the customer. The customer's security team will definitely ask this question, and the answer should be ready before they ask.

Who reviews the traces, and how is quality measured?

The fourth question often gets pushed to the second month, surfacing only when the customer asks why the agent gave a wrong answer on Tuesday. The three SDKs answer this differently.

The OpenAI Agents SDK has built-in tracing enabled by default, which makes debugging very convenient. But as noted at the start, customers under a zero data retention policy can't use it. For these customers, the observability layer has to be built from scratch.

According to Google Cloud's documentation, ADK has built-in evals tools, plus partner tools, that can inspect an agent's execution trace: checking not only whether the final answer is correct, but also which steps the agent took to arrive at it.

For customers who must prove that agents follow established processes, such as application review, this is a real advantage.

The Claude Agent SDK provides hooks that can run code at key points in the agent lifecycle, along with sessions, subagents, and MCP. Hooks are a natural place to plug in observability.

One approach with the Claude Agent SDK: use hooks to log every tool call to the customer's logging system, then build test sets from that data. Setup takes some effort, but the data stays entirely in the customer's hands.

Four questions, three answers

Each document only covers its own product. Only by comparing them against the same questions can you see where each one is strong and where you still need to probe further.

This table doesn't crown a winner; it shows which question rules out which SDK. A customer under a zero data retention policy who also needs observability has reason to reconsider the OpenAI Agents SDK.

If the customer needs Go or Java, ADK has a clear advantage, while the Claude Agent SDK can only take the long way around via the CLI. Customers who have already chosen Claude and have strict security teams are exactly the target users of Anthropic's structured permission model.

What to practice next

One tutorial points out that stopping after building a demo is the least effective way to learn agents while working as an FDE.

The most effective exercise is to build the same agent on two SDKs, then deliberately break it: make a dangerous tool bypass the guardrails, turn off tracing, swap in a different model.

When reading job descriptions, watch for phrases like "on-prem," "data residency," "Zero Data Retention," "GCP," or "Java." These are the constraints that determine which SDK gets chosen in the end.

Instead of writing "familiar with LangChain and agent frameworks" on your resume, write something like: "Selected an SDK for a claims-processing agent based on data retention requirements and tool call permission control needs."

That sentence shows you've actually sat down and worked alongside customers.

Frameworks change with every release; these four questions change far more slowly. FDEs who ask these four questions before writing code usually end up rewriting the least.
