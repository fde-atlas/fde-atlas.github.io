A Learning Roadmap to Becoming an FDE

Original title: 成为 FDE 的学习路线图

FDE Times · 48 min read

Summary

This article presents a structured learning roadmap for becoming a Forward Deployed Engineer (FDE), organized into 8 stages with 40 core readings totaling about 5 hours. Learners can follow the order or start from their weakest area. Each stage lists expected capabilities, core readings, hands-on exercises, and extensive supplementary materials. The visible portion covers five stages: foundational understanding of the role, full-stack engineering skills (data, APIs, infrastructure), AI applications (LLMs and agents), customer work (requirements discovery and communication), and deployment to production. Exercises include writing project briefs, comparing FDE vs. Solutions Engineer job postings, building idempotent data pipelines, and creating a measurable document assistant with evals.

Key points

  • 8-stage roadmap with 40 core readings, roughly 5 hours total.
  • Each stage pairs capability checklists with hands-on practice tasks.
  • Stage one compares FDE and Solutions Engineer job postings.
  • Full-stack stage covers API pagination, deduplication, and safe Postgres queries.
  • AI stage stresses hand-written agent loops and customer-approved evals.

Hands-On Practice

Understand the role, then write a brief for a real project

  • Find a Solutions Engineer job posting and an FDE job posting, and answer five questions for each: Does the role report to the engineering team or the sales team? Do you join before or after the contract is signed? Does your code go to production, or stop at a POC? Who is on call after launch? Is compensation tied to sales performance?
  • Pick a project or ticket you're currently working on and write a five-part handoff brief: who the users are, where the bottleneck is, how they work around it now, which decision they wish had been made earlier, and the minimum viable prototype along with its constraints.
  • Rewrite it as a seven-line collaboration brief, where the "out of scope" and "after delivery" lines are mandatory.
  • For three consecutive mornings, log all requests received since the previous evening as P0/P1/P2, ranked by: whether anyone is blocked, who it is, and whose decision can unblock them.

Hands-On Practice

Pull, deduplicate, and verify a public dataset

  • Find a public API that uses token authentication, and call the same endpoint with curl both with and without the token; then build a CRUD collection in Postman and run it with Collection Runner.
  • Write a pull_all() in Python: set limit explicitly, retry on 429, and save the cursor only after each batch is written to disk. Force-terminate midway, rerun, and check that the count of unique IDs equals the number of rows written.
  • Import the data into local PostgreSQL and start an analysis session with four SET statements (read-only, plus statement timeout, lock timeout, and idle-in-transaction timeout), and confirm that write operations are rejected.
  • Deduplicate with ROW_NUMBER() OVER (PARTITION BY normalized_key ORDER BY updated_at DESC NULLS LAST, id DESC), then confirm that the number of distinct keys in the source data equals the rows remaining after filtering rn = 1.

Hands-On Practice

Build a Measurable Document Assistant

  • Find a set of public documents, count their tokens, and compare against the model's context window; if they don't fit, chunk them, generate five questions per chunk, use BM25 as a baseline, and measure Recall@5, @10, and @20.
  • Hand-write an agent loop with a single query tool, set MAX_TURNS = 8, return tool errors to the model via is_error, and print the message log after each turn.
  • Run it with 20 different inputs, record the tool-call sequence each time, and turn recurring paths into fixed workflow branches.
  • Write 10 questions the documents can't answer, write a pass/fail criterion for the largest failure category, then count how often the system answers "no relevant content in the documents."

Drive projects forward and feed frontline insights back to the product team.

Hands-On Practice

Run a Small Project the Way You'd Manage a Customer Project

  • Write a three-line brief (measurable outcome, estimated time, definition of done) for a task on your plate, and have the requester confirm it.
  • Create a raid-log.md with separate columns for owners and approvers; add three unverified assumptions, specifying how and by when each will be validated; then write up one verbally agreed decision as a standalone decision document.
  • Turn a stuck technical decision into green, yellow, and red options, each with a one-line risk note, and send it to the person empowered to make the call.
  • At the end of a work session, sort every temporary workaround and unclosed ticket into three categories: lessons learned, leftover technical debt, and product issues; then pick one product issue and write it up as feedback, including evidence, the workaround, scope of impact, and a suggested classification.
