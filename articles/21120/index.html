Internal Software Access Request: FDE Interaction Project Drill

Original title: 内部软件访问申请：FDE 交互项目演练

FDECareer.work · 2026-10-26 · 5 min read

Summary

FDECareer published a synthetic, interactive exercise for FDEs simulating a software access request through verification, approval, provisioning, receipt lookup, and expiry revocation. The goal is linking each action to verifiable evidence: duplicate requests add no effect, lost responses are recovered by querying the original receipt, and failed revocations move the state to human_owned requiring manual handling. A web version runs in-memory only, while an offline Python package validates SQLite persistence and restart recovery across 12 preset scenarios. The article includes extension tasks, portfolio guidance, and explicit disclaimers that all data is synthetic and not production-validated.

Key points

  • Synthetic exercise covering request, approval, provisioning, and revocation.
  • Every action must produce verifiable receipts as evidence.
  • Lost responses are recovered by querying, not retrying with new IDs.
  • Failed revocation triggers human_owned state for manual handling.
  • Offline package runs 12 scenarios validating SQLite consistency.

This exercise is designed for FDEs (Forward Deployed Engineers). In this independently designed synthetic project, you need to take an access request through verification, approval, provisioning, and expiry-based revocation. The goal is not to let the model automatically decide who can access what, but to connect the justification, authorization, and business outcome of a single action.

All organizations, software, people, requests, and times are synthetic data. The web page does not collect enterprise information and does not connect to real accounts or models; refreshing clears in-memory state. The Python package additionally verifies SQLite persistence and recovery after a process restart, and does not imply that a real system has passed production acceptance.

Project Goals and Scope of Responsibility

In the synthetic organization north, employee-01 requests viewer access to canvas-room, with the justification of viewing the team planning board. Access is valid until simulated day 10. manager-01 is the named approver, and the execution service handles eligibility checks, simulated provisioning, receipt lookup, and revocation. The requester, approver, and executor each bear different responsibilities.

This project simulates only one piece of software and one request object. It does not create real accounts, send messages, purchase licenses, or run background scheduled tasks. Simulated time must be advanced manually; expiry is only a condition that triggers revocation, and if revocation fails, access may still exist.

The success condition is that every action has a verifiable result: the normal flow produces one provisioning receipt; duplicate requests add no effect; changes after approval block new provisioning; a lost response can be resolved by finding the original receipt; and only an independent revocation receipt can prove that simulated revocation is complete.

Process and Responsibilities

The fixed extraction output preserves the request ID, organization, employee, software, permission, purpose, and expiry date. Eligibility and policy are determined by the program; the fixed model's suggestions do not directly grant authorization. Approval binds to the entire request and the policy version; re-verification happens before actual provisioning. Selecting a role in the web page is only a teaching toggle; a real application must obtain organization and role from a trusted server-side identity.

The export includes the current state, events, scenario version, and the results of any scenario suites that have been run. Exporting happens locally; nothing is uploaded.

Anomalies and Recovery: First Confirm What Happened

When the response is lost after a successful provisioning, the caller receives outcome_unknown, and an effect already exists in the system. The next step should be to look up the receipt of the original request and recover to receipt_recovered, rather than generating another request ID to retry. The web page's "simulate restart" only copies an in-memory snapshot; the offline package actually closes and reopens the SQLite connection.

Revocation failure is a different kind of problem. The system keeps the existing provisioning record, the state enters human_owned, and the revocation effect remains zero. A human must inspect the actual permissions and complete the disposition before the incident can be closed in a real system. Cutting off automatic provisioning helps control subsequent actions, but it cannot substitute for permission revocation.

Changing the permission to editor after approval, deactivating the approver, or changing the policy version yields approval_invalid, approver_inactive, and policy_stale respectively. All of these should be detected before any new effect is produced. Do not let the original approval cover a new business action just because the new permission is also supported by the software.

Reproduce Locally After Downloading

Unzip the full package, enter offline-lab, and run with Python 3.10 or later:

python3 lab.py --db access-lab.sqlite --output results.json
python3 -m unittest discover -s . -p 'test_lab.py' -v

The first command should output passed: 12; reusing the same database should yield the same event and effect counts. When you want to experiment from scratch, use a different database path and keep the old file as evidence. The README in the package lists the expected final states item by item, and scenarios.json uses the same version as the web page.

This example commits state, effects, and events in a single SQLite transaction, which only proves local consistency. Real external identity platforms and databases do not share this transaction; on integration you still need downstream idempotency, result lookup, reconciliation, and human escalation. The fixed outputs also do not test the extraction quality of a real model.

Modification Tasks and Portfolio Evidence

First add a rejection case for "request already expired before execution," then add a test for "employee deactivated after approval." For each change, write out the expected and actual results, and explain why the provisioning count should remain zero. Do not edit the expected files directly to eliminate failures.

When finished, keep the requirement scope, object relationships, one failing run, the fix diff, the full test output, and the takeover notes. In your portfolio, clearly label it as a "synthetic training project" and distinguish the platform-provided parts from what you added yourself; without real customer adoption data, do not fill in launch scale, cost savings, or business improvement percentages.
