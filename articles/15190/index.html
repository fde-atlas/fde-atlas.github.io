Deploying in Customer Environments: A Checklist

DataDank · 2026-10-31 · 3 min read

Summary

This final lesson of DataDank's FDE course explains how to deploy solutions inside customer environments rather than your own cloud. It compares three deployment models—SaaS, the customer's cloud account, and on-premises or isolated networks—and stresses deciding which applies during discovery. The author recommends packaging with container images and infrastructure as code, keeping settings in configuration, and documenting outbound connections for locked-down networks. Security reviews should start early, with architecture diagrams, data inventories, identity and secrets handling prepared. Monitoring, support and update processes must be agreed before launch, and handover requires runbooks, training and documentation. Common mistakes include late security reviews, assuming internet access, permanent admin permissions, and systems without an owner after handover.

Key points

  • Three deployment options: SaaS, customer cloud account, on-premises.
  • Package with containers and infrastructure as code; keep settings in config.
  • Start security reviews early with architecture diagrams and data inventories.
  • Agree monitoring, support and rollback processes before launch.
  • Handover needs runbooks, training and docs so customers run it independently.

How to deploy software into a customer's environment: cloud accounts, networks, identity, security reviews, monitoring and handover, with a practical checklist.

Building a solution on your own laptop or your company’s cloud is the easy part. Forward deployed engineers often have to run it inside the customer’s environment: their cloud account, their network, their identity system and their rules. This lesson covers how to plan that deployment, get through security review, and hand over a system the customer’s team can run without you.

Deployment options

Option What it means Typical reason
Your cloud (SaaS) The solution runs in your company’s environment; the customer connects to itFastest; fine when data rules allow it
Customer’s cloud account You deploy into an account or project they ownData must stay in their account or region
Private network or on-premises It runs in their data centre or an isolated network, sometimes without internet accessStrict regulation or security requirements

Find out which one applies during discovery, because it changes the whole plan.

Package it so it is easy to install

  • Ship the application as container images, so it runs the same everywhere. See Docker for data engineers.
  • Describe the infrastructure as code (for example Terraform or Helm charts), so the customer can review it and install it repeatably.
  • Keep all settings in configuration, not code: endpoints, credentials references, feature switches.
  • Document every outbound connection the system needs. Locked-down networks block anything not listed.

Security and privacy review

Expect a review before go-live, and start it early. Have ready:

  • An architecture diagram showing components, data flows and network connections.
  • A data inventory: what data is processed and stored, where, for how long, and who can access it.
  • Identity and access: how users sign in (ideally with the customer’s identity provider), and the minimum permissions each component needs. See IAM for data engineers.
  • Secrets handling: stored in the customer’s secret manager, rotated, never in code or logs.
  • Encryption in transit and at rest, logging, and how vulnerabilities are patched.
  • For AI features: which models are used, where prompts and outputs go, and what is logged.

Monitoring and support

Agree before launch who watches the system and who fixes it:

  • Monitoring: health checks, error rates, data freshness and job failures, with alerts going to a named team. See pipeline observability.
  • Support model: who the customer contacts, response times, and how issues reach your engineering team.
  • Updates: how new versions are tested and rolled out, and how to roll back.

Handover

The engagement is not finished until the customer’s team can run the solution:

  • Runbooks for common tasks and incidents: restarting jobs, rotating secrets, handling quarantined data.
  • Training for users and for the team that will operate it.
  • Documentation of the architecture, mappings and decisions.
  • A results review: the success measure against the baseline, and the next steps.

Common mistakes

  • Starting the security review at the end, so launch waits weeks.
  • Assuming internet access in a locked-down environment.
  • Administrator permissions “for now”, which never get reduced.
  • No owner after handover, so the system slowly breaks.

Key takeaway

Deploying into customer environments means packaging the solution with containers and infrastructure as code, starting the security review early with a clear architecture and data inventory, agreeing monitoring and support, and handing over runbooks, training and documentation. That completes the engagement cycle; practise explaining it with the FDE interview questions.
