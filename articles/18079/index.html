What Are Customer VPC Deployment and BYOC: A Guide to FDE Deployment Models

Original title: 客户 VPC 部署和 BYOC 是什么：FDE 部署模型指南

FDE Times · 2026-10-08 · 5 min read

Summary

This guide explains customer VPC and BYOC deployment models for forward deployed engineers, arguing they are the same model viewed from opposite sides, with the control plane usually still residing in the vendor's account. Using Databricks' control plane and compute plane split as an example, it shows how to map what stays in the customer environment versus what crosses the boundary. It offers a deployment-map template, five practical steps, and common pitfalls around security reviews, air-gapped networks, and upgrade paths, citing Sierra, E2B, and Palantir.

Key points

  • Customer VPC and BYOC are one model, two perspectives.
  • The real question is where control plane, compute, and data live.
  • Databricks cleanly separates control plane from compute plane.
  • A deployment map should list everything egressing to the vendor.
  • Post-launch work includes upgrades, scaling, and incident response.

What matters is where the control plane, compute, and data each live, and what the vendor still controls; BYOC is just the same pattern from the customer's perspective.

Key Takeaways

  • Customer VPC and BYOC are the same pattern, just viewed from opposite sides. The control plane usually still lives in the vendor's account
  • Before saying yes to a customer, draw clear boundaries between the control plane, compute, and data, then list everything that crosses those boundaries
  • Going live is only the first half of the work. Upgrades, scaling, incident response, and security reviews make up the other half

Imagine you're in a third meeting with a bank. The demo went well, and the business team is on board. Then the security lead asks: can your system run inside the bank's VPC?

Many engineers new to forward deployed engineering will blurt out: "Yes." That answer is risky. What the customer is really asking is: whose infrastructure does the software run on, where is the data stored, and what control does the vendor retain.

If you can't yet explain the architecture clearly, "yes" is just a promise, and the security team will verify every item later.

Answering this question is itself part of the job description for many Forward Deployed Engineers (FDEs). Sierra's job posting for a Forward Deployed Infrastructure Engineer spells out the scope: designing deployment architectures in customer environments, including VPC configuration, permissioning, networking, and infrastructure provisioning.

To do this job, you must be able to hold a conversation with the customer's infrastructure team.

Three patterns, one question: what goes where?

With SaaS, everything runs in the vendor's account, and the customer sends data over. At the other end is on-premises deployment (on-prem). Northflank's documentation describes it as: software running on hardware in the customer's own data center or private infrastructure. The biggest difference from a customer VPC is that on-prem does not rely on a cloud provider.

Customer VPC sits in between: the software runs in the customer's cloud account. Northflank notes that Bring Your Own Cloud (BYOC) is the same pattern, just described from the customer's side. So when the customer says "BYOC" and sales says "deployed in the customer's VPC," both are referring to the same thing.

The key detail: even when the software runs in the customer's cloud, the control plane usually remains in the vendor's account. The control plane handles orchestration, CI/CD, configuration, monitoring, and pushing updates. So "running in the customer's VPC" almost never means everything is in the customer's VPC.

Databricks shows where the boundary lies

Databricks is the easiest example to learn from, because its documentation draws the boundary clearly. The control plane consists of backend services managed by Databricks in its own account. The compute portion is separated out and called the compute plane.

With classic compute, compute resources run in the customer's AWS account. With serverless, compute runs in a compute layer within Databricks' account. The same product gives two different answers to "where does compute happen." A customer choosing serverless gains more convenience, but must also accept that compute no longer resides in their own account.

This is exactly the trade-off you need to explain to customers. The table below compares the three patterns by the questions security teams most often ask.

The on-prem column deserves the closest reading. When the control plane has no route to the vendor, the hard part is no longer the initial install, but how to get updates in. The "common mistakes" section below returns to this point.

Example: a deployment map for the bank

Back to the bank's question. Instead of saying "yes" outright, promise to send a deployment map. E2B's BYOC documentation is a good reference, because it precisely lists what stays and what leaves.

According to E2B, sandbox templates, snapshots, and runtime logs are all stored in the customer's BYOC VPC. Only anonymized metrics are sent back to E2B's cloud for observability; VPC peering provides the private network connection. BYOC clusters are provisioned via Terraform configuration and machine images.

Your map could look like this (an illustrative template, not a real configuration for any product):

deployment_model: customer_vpc   # 客户称之为 BYOC
control_plane:
  location: vendor_account
  responsibilities: [orchestration, ci_cd, config, monitoring, updates]
compute_plane:
  location: customer_aws_account
data_at_rest:            # 留在客户的 VPC 内
  - templates
  - snapshots
  - runtime_logs
egress_to_vendor:        # 所有跨越边界的内容
  - type: metrics
    anonymized: true
    purpose: observability
connectivity: vpc_peering
provisioning: [terraform, machine_image]
iam: least_privilege_role_for_vendor

(The inline comments read, respectively: "the customer calls this BYOC," "stays within the customer's VPC," and "everything that crosses the boundary.")

The most valuable part of this document is the

egress_to_vendor

section. The security team doesn't need to hear "data will never leave the system"; it needs a complete inventory: what leaves, in what form, and for what purpose.

Five steps to do it yourself

  • Ask the customer which data can go where. Confirm which sensitive data must stay on the customer's infrastructure.
  • Split your product into a control plane and a compute plane, like Databricks does. If your product team has never made this separation, you've just identified a project risk.
  • Pick a pattern and write the map, following the example above, paying particular attention to the outbound list.
  • Provision with code. Terraform plus machine images lets you rebuild the same cluster for the second and third customer without manual work.
  • Prepare for post-launch work. Sierra describes the deployment lifecycle as initial deployment, regular upgrades, scaling, and incident support, backed by runbooks. Write the runbook from day one; don't wait for the first incident.

Mistakes that stall projects at security review

The most common mistake is treating security review as a formality. Sierra requires candidates to have experience passing security reviews, compliance requirements, and change management processes. In large enterprises, changing a single firewall rule can take a full approval cycle, and your plan must build in slack for such delays.

The second mistake is assuming there's always a network route to the vendor. In an air-gapped network, there is no such route. The direct consequence is that the vendor-side control plane can no longer push updates on its own: every upgrade must be packaged in advance, transferred into the customer's network, and then run through the customer's change management process.

In its IPO prospectus, Palantir wrote that its Apollo platform enables it to deploy to air-gapped or on-prem networks at nearly the same speed as the cloud. This shows the work requires an entire purpose-built platform, not a few extra lines of configuration.

The third mistake is focusing only on deployment and forgetting upgrades. A system running in the customer's account, without a clear update path, will gradually fall behind, and every patch becomes its own project.

How to prove to employers you have this skill

When reading FDE job descriptions, watch for keywords like VPC, permissioning, networking, Terraform, BYOC, and air-gapped. They signal an infrastructure-leaning role. If your current job offers no exposure to these, a personal project using two AWS accounts is enough to get hands-on practice.

Avoid vague statements like "has cloud experience" on your resume; be specific: wrote Terraform to set up systems in customer accounts, designed least-privilege IAM roles for vendors, configured VPC peering, wrote upgrade runbooks. When asked, be able to explain each item in detail.

Next time you hear "Can this run in our VPC?", don't rush to answer. Open a blank file and start drawing a map.
