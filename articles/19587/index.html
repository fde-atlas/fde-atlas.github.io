Differences and Transition Paths from Solutions Engineer to FDE

Original title: 解决方案工程师转 FDE 的区别与转型方法

FDE Times · 2026-10-13 · 6 min read

Summary

This guide contrasts Solutions Engineers (SEs) with Forward Deployed Engineers (FDEs): the SE proves a product works during the sales cycle, while the FDE takes over afterward and is accountable when it fails in the customer's production environment. The author, drawing on sources like Paraform and a Palantir job posting, offers a practical transition method: list every assumption behind a demo, assign an owner to each, run demos on real customer data, write runbooks before launch, and feed reusable patterns back to the product team. It also warns SEs to confirm they actually want months of production coding before switching.

Key points

  • SEs prove a product can work; FDEs own it in production.
  • Transition starts by extracting hidden assumptions from the demo handoff.
  • Write runbooks before launch, covering alerts and shutdown steps.
  • Customer-specific code is still production code needing tests and reviews.
  • Ask in interviews who gets called when the system breaks.

An SE proves the product works during the sales process; an FDE is accountable for it in production, and the messy territory in between calls for a different mindset.

Key Takeaways

  • An SE proves the product works within the sales cycle; an FDE picks up where the SE left off and makes sure it actually runs in production.
  • Demos come together quickly because they sidestep the hard assumptions. An FDE's job is to start from the handoff, dig out those assumptions one by one, and assign an owner to each.
  • Before switching roles, ask yourself: are you willing to write production code for a specific customer for months on end.

Picture this scenario: the contract has just been signed. The demo you built during the sales phase impressed the customer, and now they want it to actually run, with real data, serving real users. Three months later, if the system goes down at 2 a.m., who has to get up and fix it?

A recent Scaler article comparing the two roles gave a straightforward answer: the Forward Deployed Engineer (FDE), not the Solutions Engineer (SE). The difference between the two jobs lies almost entirely in that answer.

An SE works within the sales cycle, proving the product can work for the customer. An FDE is sent directly to the customer's problem site to make sure the product actually runs in production.

If you're an SE looking to become an FDE, most of your skills still apply: understanding customers, explaining technology, building things fast. What you need to learn is a fundamentally different way of thinking. The goal is no longer winning the customer's trust, but bearing the consequences when the demo collides with the real world.

The difference between "works" and "is being used"

Paraform describes the division of labor simply: the SE sells the vision, the FDE builds it, and the customer's engineers maintain it. The SE works mainly in pre-sales, and the FDE picks up exactly where the SE stops. The two roles follow one another on the same customer, yet they measure success in completely different ways.

Hapy wrote that a demo chatbot can be built in a week; the hard part is making that workflow run reliably inside a real organization. Kunal Ganglani argues that the gap between "the demo runs" and "it's deployed in the customer's production environment" is enormous; Hapy gave the territory in between a name: the FDE is the person responsible for that "messy middle."

There's another detail SEs tend to overlook: FDEs write production code, but not code for the core product. Your code is customized for each customer—connectors, data pipelines, business logic—and runs in the customer's environment. So you need enough engineering discipline to keep it usable over the long term, while also preventing it from turning into a fork of the product.

Carrying the demo all the way to production

Here's a hypothetical example. You once demoed a chatbot to a retail chain that answers questions about return policies. The demo used a CSV file manually exported from the order system, twenty pre-written questions, and ran on your own laptop. The customer nodded, and now you're the FDE on this project.

The first step isn't writing code. It's sitting down, writing out every assumption the demo silently relied on, and noting for each one the production requirement and the owner. The table below is part of that list.

Demo assumptionProduction requirementOwner
Data is a static CSV fileRead directly from the order system, set a sync schedule, alert when data goes staleFDE, together with the customer's IT team
Questions are pre-writtenHandle unfamiliar questions, typos, and out-of-scope questions, and be able to say "I don't know"FDE, together with the business owner
The API always respondsTimeouts, retries, and fallbacks when the service slows down or goes downFDE
The only user is youPermissions, audit logs, customer data never leaves the customer's environmentFDE, together with the security team
Someone sits nearby to correct errors at any timeRunbooks, alerting, and an on-call engineer when the system fails at 2 a.m.FDE

The career shift lives in that last column. In a demo, that column is empty, because nothing needs to be accountable. In production, every empty cell is an incident waiting to happen.

Let's turn row three into code. The demo version is usually one line: call the API directly. The production version has to answer a question: when the backend slows down or dies, what does the user see, and what can the on-call engineer read?

import logging, time
import requests

log = logging.getLogger("returns_bot")
MAX_ATTEMPTS = 3

def get_order(order_id: str) -> dict | None:
    # 演示版：return requests.get(f"{API}/orders/{order_id}").json()
    for attempt in range(MAX_ATTEMPTS):
        try:
            r = requests.get(f"{API}/orders/{order_id}", timeout=5)
            r.raise_for_status()
            return r.json()
        except requests.RequestException as e:
            log.warning("order_api_fail order=%s attempt=%d err=%s", order_id, attempt, e)
            if attempt < MAX_ATTEMPTS - 1:  # 最后一次尝试后不再等待
                time.sleep(2 ** attempt)
    log.error("order_api_down order=%s", order_id)
    return None  # 上层回复：“订单系统繁忙，请稍后再试”

There's nothing clever in this code. The difference is in the mindset: every log line is written for the person who reads it in the middle of the night, and that person is very likely you.

The handoff is where assumptions hide

If you built the demo yourself, the assumptions table above is easy to write. But if you're an FDE taking over a project from another SE, many assumptions won't appear in any slide deck or code repository. They live in the memory of the person who built the demo—and the smoother the handoff, the more likely it is those assumptions were never spoken aloud.

A practical tip: don't ask the SE to demo it for you again, because they'll only repeat the prettiest path. Ask questions that force them to describe what happened behind the scenes. Which data was manually cleaned before the demo? Which of the customer's questions did the demo get wrong? Was anything promised verbally but never written into the contract?

A hesitant answer, or something like "that should be fine," is the next row in your assumptions table. Capturing these during the handoff costs far less than discovering them in your first incident.

Steps to apply this in your own projects

First, write an assumptions list like the table above, ideally in the first week after the contract is signed, and review it with the customer. Then, run the demo with the customer's real data and question samples, and before committing to any dates, record where it breaks. That list of failures is your first to-do list.

Then write the runbook before launch, not after the first incident. The runbook must answer three questions: which alert pages whom, what to check first, and how to turn this feature off without affecting everything else. If you can't write the runbook, the system isn't ready.

The last step is the most often forgotten. Hapy sees feeding generalizable patterns back to the product team—turning one-off work done for a single customer into reusable capability—as a core FDE responsibility. Every time you write the same connector for a second customer, file a ticket with the product team.

Common mistakes SEs make in their first year

The first is the demo instinct: hiding the tricky parts so the presentation goes smoothly. As an FDE, the tricky parts must surface early, because hiding them only postpones the incident to a more expensive moment. You'll find yourself telling the customer "this doesn't work yet" far more often than you did as an SE.

The second is modifying the core product to save time, or conversely, writing customer code carelessly on the grounds that it's "just an integration." Code customized for a customer is still production code, and it needs testing, logging, and code review just the same. Only the scope differs, not the quality.

The third is deeper, and it's about you. Paraform points out that an SE who excels at demos may have no desire at all to write production code for six months straight. Being good at demos doesn't prove you're interested in this kind of work, so try it before you apply.

How to prove this capability when job hunting

Palantir's Forward Deployed Software Engineer job posting describes the role as working directly with customers to quickly understand their biggest problems, then designing and implementing solutions. The posting also emphasizes working in small teams with minimal supervision, and owning high-risk projects end-to-end.

When reading FDE job postings, watch for words like "own," "end-to-end," and "implement": they signal that the company wants someone who can carry production, not just someone who can present. On your resume, don't just write "built demos that helped close deals."

Write a handoff for a system you'll still own afterward: what data it runs on, which incidents you've handled, and what patterns you've reported back to the product team.

In the interview, ask who gets the phone call when the customer's system breaks. The answer will tell you whether this is a real FDE role or an SE job with a new title.

Exercise: Put your latest demo on the operating table

Take the most recent demo you've built and create a hypothesis table using the format above, with at least ten rows and no blanks in the "owner" column. Then pick the hardest cell and write code or a runbook for it. If, after doing this, you find it more interesting than building the demo, you have your answer about switching roles.
