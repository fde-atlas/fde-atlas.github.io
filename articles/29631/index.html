Microsoft Foundry Deployment Types and Agent Standard Configuration

Original title: Microsoft Foundry 部署类型与 Agent 标准配置

FDE Times · 2026-10-09 · 5 min read

Summary

This article walks forward deployed engineers through the key decisions when delivering AI agents on Microsoft Foundry (formerly Azure AI Foundry). Deployment type determines where prompts are processed: Global Standard may use any Azure region, so compliance-bound customers need Data Zone or Batch. Prompt agents versus hosted agents differ in who owns the agent logic; customers with existing code should prefer hosted agents in their own VNet. Standard agent setup requires customer-owned Cosmos DB (minimum 3000 RU/s), Storage and AI Search, with private endpoints that must be declared explicitly in Bicep or Terraform. The Assistants API is being replaced by the Responses API (Agents v2), so migrations should be planned early.

Key points

  • Deployment type decides where data is processed; Global Standard may use any Azure region.
  • Batch deployment costs 50% less but has no real-time SLA.
  • Customers with existing agent code should choose hosted agents running in their own VNet.
  • Standard setup needs Cosmos DB at 3000 RU/s minimum; private endpoints must be created via code.
  • Assistants API is replaced by Responses API (Agents v2); plan migration early.

Key Takeaways

A job posting for an "Azure Forward Deployment Engineer (architect level)" was published via Dice and also appeared on Arc.dev, requiring candidates to have hands-on experience building AI agents with Azure OpenAI, Semantic Kernel, and Azure AI Foundry.

Meanwhile, Microsoft's documentation already refers to the platform as Microsoft Foundry. According to Schneider IT, the new name took effect on January 1, 2026, and existing deployments have been migrated automatically.

Leobit believes this rename is far more than a label change. For Forward Deployed Engineers (FDEs), the name matters far less than the three decisions to be made on-site at the customer: which deployment type the model runs on, which type of agent to use, and how to set up the standard configuration so provisioning doesn't fail.

First question: where is the data processed?

When deploying a model, the deployment type determines where data is processed, how it's billed, and what performance you get. Microsoft recommends starting with Global Standard for most workloads: new models launch here first, prices are lowest, and it covers the most regions.

The trade-off is that when you choose the Global type, data may be processed in any Azure region.

Suppose you're working on a project for a European insurance company whose compliance team requires that prompts never leave the EU. In that case, Global Standard is no longer the default option. Data Zone limits processing to one data zone in the US, EU, or Asia-Pacific, so Data Zone EU can meet this requirement.

Now suppose the insurance company also needs to re-score a backlog of claims every night. This task doesn't need real-time responses and suits the Batch type: requests are submitted asynchronously in groups, quota is calculated separately, the target is completion within 24 hours, and pricing is 50% lower than Global Standard, but there's no real-time SLA.

Deployment typeUse case
Global StandardThe default option, for when the customer has no restrictions on where data is processed
Data Zone (US, EU, APAC)Compliance requires processing to stay within the same data zone
BatchTasks run in batches, and waiting up to 24 hours is acceptable to reduce costs

Raise this question during the very first requirements gathering, before writing the first line of code. Changing the deployment type after the demo is running costs far more effort than choosing correctly from the start.

Prompt agent or hosted agent?

The Agent Service offers three types of agents. On one end are prompt agents, written declaratively; on the other end are hosted agents, which offer the most control: you bring your own code and framework, and Foundry runs them in a container, handling endpoints, scaling, and identity.

Both ends can be placed in a private network, so don't choose based on "which is more private." Microsoft's documentation states that prompt agents support private networks, while hosted agents support BYO VNet, meaning they run in the customer's own Azure virtual network. The real difference lies in who writes and owns the agent's logic.

Suppose a bank already has an agent written in LangChain. Switching to a prompt agent would mean rewriting the logic declaratively. A hosted agent can package the existing code as-is into a container; it runs in the customer's VNet, which is the more sensible choice when the agent needs to call systems accessible only on the internal network.

Whichever you choose, the customer's VNet remains the responsibility of their network team. Recommendation: for customers with existing agents, prioritize hosted agents, schedule time with the network team in the first week, and list all internal systems the agent needs to call.

The real workload is in the standard setup

The agent standard setup requires the customer to bring their own Storage, AI Search, and Cosmos DB, keeping all agent data within the customer's Azure tenant. Compliance teams will be happy, but the FDE often has to create these resources one by one and grant permissions.

There are several specific pitfalls here. A Cosmos DB for NoSQL account needs a total throughput of at least 3000 RU/s; below that, provisioning fails. Agents running in a private network need a subnet delegated to Microsoft.App/environments, and the Foundry resource must be in the same region as the VNet.

The easiest pitfall to forget: when deploying a Foundry resource, private endpoints to AI Search, Storage, and Cosmos DB are not created automatically. So don't click through items one by one in the portal; instead, write the full configuration in Bicep or Terraform, explicitly declare every private endpoint, and hand it over to the customer's platform team as code.

Which API does the customer's existing code call?

According to Microsoft, Foundry brings agents, models, and tools into the same management group, with built-in tracing, monitoring, and evals, and shared RBAC, networking, and policies. The group of services formerly called Azure AI Services is now called Foundry Tools, and hub-based projects have become legacy.

Customers already using Azure OpenAI can upgrade their resource in place to a Foundry resource while keeping existing endpoints, API keys, and state. As a result, applications calling that endpoint don't need configuration changes because of the upgrade.

What's more likely to break is the Agent API. The Assistants API (Agents v0.5/v1) has given way to the Responses API (Agents v2), which comes with a unified project client. If the customer's codebase still calls Assistants, put the migration in the plan from the start; don't discover it in the final week.

Azure FDE: what should you learn first to match this kind of role?

The posting lists Azure OpenAI, Semantic Kernel, and Azure AI Foundry side by side, and also requires close collaboration with enterprise customers to define requirements, design architecture, and deliver complete AI solutions on Azure. The employer wants someone who can both build agents and land them in enterprise Azure infrastructure.

Learning order: first learn deployment types and data residency, then the standard setup, and finally configuring private networks with Terraform or Bicep.

Write concrete achievements on your resume, such as "deployed the Agent Service standard setup in a dedicated VNet using Terraform, with models running on Data Zone EU," rather than just listing "Azure AI Foundry" in a skills section. Include both the old and new names so recruiters can find you no matter which one they search for.

Product names may change again. But questions like where data is processed, who owns agent state, and which network paths are open always need someone to answer them, and that someone is usually the FDE.
