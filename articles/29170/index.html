Consultative Problem-Solving

Original title: Consultative-Problem-Solving

FDE中国社区 · 2026-07-12 · 4 min read

Summary

This article documents a consultative problem-solving methodology for FDEs in China, built around the Issue Tree and the DIVE model (Diagnose, Identify, Validate, Embed). It aims to convert surface-level requests like "build an agent platform" into underlying business, data, process, and organizational problems. The skill includes MECE checks, execution steps, stage gates from PoC preparation to production, and collaboration interfaces among FDE, AIBP, business owners, and IT/security. It ships as a downloadable skill package for Agent Skills tools; an illustrative case reports PoC cycles dropping from 12 weeks to 4.

Key points

  • Issue Tree decomposes platform requests into business, data, process, and organizational issues.
  • DIVE covers diagnosing bottlenecks, identifying value, validating PoC hypotheses, and embedding into workflows.
  • Trees must be MECE to avoid missing compliance or permission dimensions.
  • Defines handoffs across FDE, AIBP, business owners, and IT/security roles.
  • Illustrative case cut PoC duration from 12 weeks to 4.

Problem Definition

The customer's surface request is often "build an agent platform," but the real problem lies in processes, data, organization, or value priorities.

Methodology Framework

Issue Tree

表层诉求 → 业务问题 → 数据问题 → 流程问题 → 组织问题

DIVE Model

  • Diagnose: Is the bottleneck in data/processes/systems/organization?
  • Identify: Does the value fall under cost reduction/efficiency/quality/risk control/growth?
  • Validate: What are the minimal PoC hypotheses and metrics?
  • Embed: Who uses it/who reviews it/who is accountable? How is it embedded into processes?

MECE Principle

Issues at the same level must be mutually exclusive and collectively exhaustive, avoiding omissions in compliance or permissions dimensions.

FAQ

Q1: When executing [Consultative-Problem-Solving], how do you avoid "directly accepting platform requirements"?

A: Follow the README methodology step by step and present interim deliverables at weekly Demos; if PoC materials are incomplete, first produce a "pending verification list" before proceeding.

Q2: What additional constraints apply in private deployment / Xinchuang / classified protection environments?

A: Specify the deployment model in the prompt constraints section; when data cannot leave the domain, domestic components, or audit logs are involved, reference Private-Deployment-Gateway and RBAC-Audit accordingly.

Q3: What if the division of responsibilities with AIBP is unclear?

A: Return to the AIBP-Collaboration-Playbook to update the RACI; AIBP is responsible for Ground Truth and business acceptance, while the FDE is responsible for deliverable technical assets.

Q4: After the PoC passes, how do you transition to Beta/production?

A: Mark the next-stage Skill in the deliverables (e.g., RAG-Evaluation→Private-Deployment-Gateway→FDE-Adoption-Growth), and trigger the launch gate via the checklist.
