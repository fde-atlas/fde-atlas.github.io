SCIM

FDE Interview Prep · 2026 · 1 min read

Summary

This FDE interview-prep article explains SCIM, the REST protocol by which a customer's identity provider creates, updates, and deactivates users and groups in your application via endpoints like POST /Users and PATCH /Users/{id}, defined by RFC 7643 (schema) and RFC 7644 (protocol). Sign-in itself uses SAML or OIDC; SCIM governs whether accounts exist. Weak interview answers build SAML/OIDC but skip de-provisioning. Strong candidates key users on externalId, treat active: false as immediate revocation of sessions and API tokens, and map directory groups to product roles. Two common go-live failures: unimplemented GET /Users filters cause duplicate accounts or 409 Conflict errors, and Okta versus Microsoft Entra ID PATCH differences mean you must test against the customer's actual identity provider before cutover.

Key points

  • SCIM lets a customer's identity provider manage users and groups in your app via REST endpoints.
  • Specs are RFC 7643 (schema) and RFC 7644 (protocol); sign-in itself uses SAML or OIDC.
  • Strong answers treat active: false as immediate revocation of live sessions and API tokens.
  • Missing GET /Users filter support causes duplicate accounts or 409 Conflict errors.
  • Okta and Microsoft Entra ID format PATCH differently; test against the customer's actual IdP.

Full text

SCIM is a REST protocol in which the customer’s identity provider creates, updates and deactivates users and groups in your application by calling endpoints you expose, such as

POST /Users

,

PATCH /Users/{id}

and

/Groups

. The resource schema is

RFC 7643

and the protocol, including PATCH operations and filtering, is

RFC 7644

. Sign-in itself happens over

SAML

or ; SCIM decides whether the account exists at all.

In an FDE interview

Okta’s postings, as of September 2026, put SCIM on the same identity-protocol list as and OIDC. A planned practice question, Designing provisioning from the customer’s identity provider, will ask for it directly. A strong candidate keys users on the identity provider’s

externalId

or your own

id

, treats

active: false

as an event that revokes live sessions and API tokens immediately, not just the next sign-in, and says how directory groups map to roles in your product.

Two things break go-lives. Before creating a user, the identity provider searches with

GET /Users?filter=userName eq "..."

: if you have not implemented the filter, or it does not return users already created by just-in-time sign-in, the provider tries to create them again, and you get duplicate accounts or

409 Conflict

errors. And Okta and

Microsoft Entra ID

shape their PATCH requests differently, so a server tested against one can fail against the other; test against the customer’s actual identity provider before the cutover date.

The lesson Identity and network in someone else’s environment covers provisioning and de-provisioning, and a planned SCIM provisioning design prompt will be the practice.
