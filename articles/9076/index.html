Week 7: Enabling frontline roles to complete tasks within their permissions

Original title: 第 7 周：让一线角色在权限内完成任务

FDE 成长手册 · 2026-08-25 · 10 min read

Summary

Week 7 of this FDE handbook tutorial connects the software back to real frontline roles: ordinary support agents and supervisors see different content under server-side permissions, and agents can verify sources, then confirm, reject, or escalate. The core lesson separates authentication, authorization, and user decisions—authorization must run server-side on every read and write, since hiding UI buttons cannot stop direct API calls. It covers a role-permission matrix, task state diagrams, idempotency (duplicate escalations produce one event), and denial responses that leak nothing about restricted content. A five-day plan covers permissions, implementation, a minimal workbench, end-to-end tests, and a protected walkthrough. Notably, confirmed only means the user verified the cited policy—not adoption or business value.

Key points

  • Week 7 adds one difficulty: wiring software to real roles and decisions.
  • Authorization must be enforced server-side per request; hiding buttons is insufficient.
  • Idempotency keys ensure duplicate requests create only one valid state change.
  • confirmed is an operational end state, not adoption or business success.
  • Five days cover permission matrices, implementation, tests, and a protected walkthrough.

Direct answer: The software foundation only makes sense when it is connected back to frontline tasks. In Week 7, regular agents and supervisors should see different content within server-side permissions, so that regular agents can verify evidence and confirm, reject, or escalate; requests without permission, expired, conflicting, and duplicate requests enter explicit states. Finally, use a protected walkthrough to re-examine the original problem contract, rather than writing off interface completion or a single positive review as adoption and business success.

This week adds only one difficulty: connecting the software back to real roles and decisions

Title "This week adds only one difficulty: connecting the software back to real roles and decisions"

通过质量门的数据  → 可信身份与服务端授权  → 用户看到权限内来源和状态  → 用户核验、确认、拒绝或升级  → 数据库与日志记录同一终态  → 一线走查重新检查 Brief

Week 5 had only one controlled identity and read-only candidates; Week 6 ensured data states were reliable. Only in Week 7 do we add two roles and user actions that change task state. Production deployment, formal security review, and long-term adoption remain in later phases.

Minimal mental model: authentication, authorization, and user decisions are three different things

Title "Minimal mental model: authentication, authorization, and user decisions are three different things"

ConceptQuestion it answersExample this week
AuthenticationWho is making the current request?A trusted test session resolves to support_agent_a
AuthorizationWhat can this identity do to which resource?Regular agents can view regular policies but not supervisor-only content
User decisionWithin the allowed scope, how does the user close out the current task?After verification, confirm, reject, or escalate

Hiding the "supervisor policy" button on the frontend only changes the interface; it cannot stop users from calling the API directly. Authorization must be enforced on the server side before every read or write, and must deny unknown roles and unknown actions by default.

Another important boundary is:

confirmed only means the user confirmed the policy evidence for this task; it does not mean the customer reply was correctly sent, does not mean adoption, and certainly does not mean business value realized.

Task state diagram

Title "Task state diagram"

opened  → candidate_presented      → confirmed      → rejected      → needs_review          → escalated              → resolved_by_supervisor
denied

is not a task state. It is the result of a request: when the current identity lacks permission to perform an action, the server returns

denied

and the original task remains in its original state. Drawing it into the task state diagram would lead implementers to believe that unauthorized requests should also modify business state.

Only declared state transitions are allowed. For example, a task already

confirmed

cannot be changed to another policy with the same regular action; when a new decision is needed, create a controlled revision event instead of overwriting history.

Permission exception: regular agent encounters a special refund

Title "Permission exception: regular agent encounters a special refund"

When a regular agent reads

TASK-W07-002

the server knows the task requires the supervisor path, but the response does not expose whether a supervisor policy exists, its name, content, or sensitive metadata:

{  "task_id": "TASK-W07-002",  "status": "needs_review",  "reason_code": "SPECIAL_TASK_REQUIRES_REVIEW",  "candidate": null,  "allowed_actions": ["escalate"],  "correlation_id": "corr-w07-002"}

The agent initiates an escalation:

{  "task_id": "TASK-W07-002",  "action": "escalate",  "reason_code": "SPECIAL_TASK_REQUIRES_REVIEW",  "idempotency_key": "TASK-W07-002:escalate:1"}

Expected: the task enters

escalated

and a supervisor queue reference is created, but the regular agent's response does not include the supervisor policy content.

Duplicate request: must not produce two escalations

Title "Duplicate request: must not produce two escalations"

Send the exact same escalation request twice:

  • The first creates one escalation event and one supervisor queue item;
  • The second returns the same business result or already_applied;
  • The database still has only one valid escalation state;
  • The two requests may have different transport IDs but share the same idempotent business key.

Direct unauthorized access: must also be denied outside the interface

Title "Direct unauthorized access: must also be denied outside the interface"

A regular agent attempts to directly call the supervisor resolve action; expected:

{  "task_id": "TASK-W07-002",  "status": "denied",  "reason_code": "ACTION_NOT_ALLOWED",  "correlation_id": "corr-w07-004"}

The original task remains in

escalated

; nothing is written to

resolved_by_supervisor

and the response does not leak supervisor policy details.

Day 1: Define roles, resources, actions, and responsibilities

Title "Day 1: Define roles, resources, actions, and responsibilities"

Complete

role-and-permission-matrix.md

and the task state diagram. Every permission must answer:

  • Where is the identity trusted from?
  • Which action can this role perform on which type of task?
  • Which fields are allowed to be seen for reads, state changes, and logs respectively?
  • When denied, how do you stay actionable without leaking restricted content?
  • Who is ultimately responsible for exceptions?

Do not use "admins can do everything" as the default answer. The greater the permission, the more you must specify applicable resources, actions, and audit boundaries.

Day 2: Implement server-side authorization and idempotent actions

Title "Day 2: Implement server-side authorization and idempotent actions"

Stack-neutral request path:

从可信会话解析 identity_id 与 role  → 加载 task 及当前状态  → authorize(identity, action, task_scope)      → 拒绝：记录安全事件，不改变任务  → 校验当前数据版本和允许的状态转换  → 使用 idempotency_key 写入任务事件  → 提交新状态  → 返回用户可见结果和 correlation_id

The

role

、

tenant

or permission claims in the request body must not override the trusted session. Even if you use fixed session fixtures this week, enforce this rule on the server side.

Day 3: Build a minimal workbench or CLI

Title "Day 3: Build a minimal workbench or CLI"

The interface form does not matter, but the user must be able to:

  • See the fields required for the task and its current state;
  • View the source, version, and effective time of candidates within their permissions;
  • Clearly know which content has not yet been confirmed;
  • Choose to confirm, reject, or escalate;
  • Know the next step and the responsible party after a failure;
  • Report issues to support staff via the associated ID.

Do not use color as the only status signal, and do not disguise "no permission" as a load failure. Permission-denied messages should be safe but actionable, e.g., "This task requires review by a designated role; an escalation path has been provided for you."

Day 5: Conduct a protected frontline walkthrough

Title "Day 5: Conduct a protected frontline walkthrough"

Before a real walkthrough, the following must be satisfied:

  • Explain the purpose, how it will be recorded, what will be visible, and how it will be used;
  • Allow participants to skip, correct, stop, and withdraw;
  • Direct supervisors do not observe individual research sessions;
  • Use sandboxes, anonymized tasks, or explicitly authorized materials;
  • Do not use recordings for personal performance reviews or disciplinary action;
  • Do not ask users to bypass permissions or display restricted bodies.

When real users cannot be scheduled, use two peers role-playing a regular support agent and a supervisor, clearly labeled as "Beichen role-play." It can validate tutorial exercises and interface usability, but cannot prove real adoption.

Full walkthrough script

Title "Full walkthrough script"

  • Give the regular support agent TASK-W07-001 without hinting at button order; observe whether they can find the source and confirm.
  • Give TASK-W07-002; observe whether they can understand why escalation is needed, rather than looking for ways to bypass permissions.
  • Replay the escalation request; observe whether the interface creates the misunderstanding that "it was created twice."
  • Have the supervisor enter their queue; confirm the regular support agent did not see restricted content.
  • Read-back: Which old step did the system remove? Which necessary judgment was kept? What new burden was added? Under what circumstances would they prefer to return to the original process?

When to update the Brief

Title "When to update the Brief"

You do not need to create one for every copy change

Discovery Brief v2

：

  • No update needed: Unclear button labels or missing help text, but roles, tasks, risks, and metrics unchanged; just record the feedback and implementation changes.
  • Update required: The walkthrough reveals that the regular support agent's response leaks the supervisor policy name, meaning the permission risk and output contract have materially changed; first stop that path, revise the risks, scope, and acceptance gates, and produce Brief v2 or decide to stop.

If new evidence does not materially conflict with the Brief, still record "the rationale and limitations for continuing with v1"; do not treat silence as approval.

Acceptance and failure recovery

Title "Acceptance and failure recovery"

Passing this week requires all of the following:

  • Regular support agents and supervisors can only perform actions allowed by the matrix;
  • Identity comes from a trusted server-side context; unknown identities and actions are denied by default;
  • Permission-denied responses do not leak whether a restricted record exists, its body, or sensitive metadata;
  • Users can verify the source and confirm, deny, or escalate;
  • Missing, conflicting, expired, and no-permission cases do not produce seemingly definitive results;
  • Duplicate requests produce at most one valid business state change;
  • End-to-end tests verify user outcomes, database, events, and logs, not just HTTP 200;
  • Walkthrough records state participant protections, version, evidence boundaries, and what cannot be proven;
  • When new evidence materially changes scope or risk, the Brief is revised or the direction is stopped;
  • Decisions allow continue, modify, switch to a process/rule, pause, or stop; do not default to AI.

Beautiful UI but the task doesn't close the loopCan only view, cannot verify, deny, or escalateRerun completely from trigger to responsible person
Removing protections when automation staff take detoursSpecial tasks confirmed directlyRestore verification and escalation points; first confirm the detour's value
Doing permissions by only hiding buttonsCalling the API directly bypasses authorizationAuthorize before every server-side read and write

Independent migration: Give newly hired support agents narrower permissions

Title "Independent migration: Give newly hired support agents narrower permissions"

Add a role

new_support_agent

that can only:

  • View regular, current policies marked as training-allowed;
  • Choose "confirm" or "escalate" for normal tasks;
  • Cannot handle special refunds, nor see whether supervisor policies exist;
  • Must escalate on version conflicts.

Complete independently:

  • Modify the permission matrix and status diagram;
  • Predict the visible outcomes of TASK-W07-001 and TASK-W07-002;
  • Add server-side denial tests, not just hidden UI;
  • Write out how training instructions change and who is responsible for ending the newbie restriction;
  • Explain whether this role change requires updating the Brief, and why.

If you only add a frontend role string without changing server-side rules, tests, and responsibilities, the migration has not passed.

Explain with the same evidence to three audiences

Title "Explain with the same evidence to three audiences"

  • Boss version: Why continue, modify, or stop; what delivery capability has currently been proven, and which value, adoption, and cost conclusions still cannot be promised.
  • Frontline version: What step changed, when it cannot be used, and how to verify, deny, escalate, and withdraw research feedback.
  • Engineering edition: How requests pass through identity, authorization, data state, transactions, events, logs, and testing, and how to reproduce failures with a correlation_id.

The Week Behind and the Week Ahead

Heading "The Week Behind and the Week Ahead"

By the end of Week 7, what you have is a non-AI deterministic candidate baseline that runs, is testable, is explainable, and has undergone a limited walkthrough. It is not a production system, and it does not automatically approve entering RAG in Week 9; if the evidence says AI should not be used, keep that decision. The overall pace of the course follows the 24-week standard roadmap.

Sources and Factual Boundaries

Heading "Sources and Factual Boundaries"

  • OWASP Cheat Sheet Series — Authorization: A security reference on deny-by-default, least privilege, and validating authorization on every request.
  • GOV.UK — Start by learning user needs: Observe current tasks, behaviors, and problems rather than validating preconceived features.
  • Ramp — Forward Deployed Engineering: Team practices around continuous scope judgment, direct contact with users, and validating work against customer outcomes; the article also serves recruiting and culture-promotion purposes.
  • Vannevar Labs — Forward Deployed Engineering: A team perspective that prototypes ultimately need to be productized, customizations need to be constrained, or work needs to be explicitly stopped; its defense context cannot be directly extrapolated as general practice.
