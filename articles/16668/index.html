Context Engineering for AI Agents: Compression, Notes, and Subagents

Original title: AI Agent 的上下文工程：压缩、笔记与子代理

FDE中国 · 2026-08-14 · 14 min read

Summary

Anthropic's applied AI team frames context engineering as the evolution of prompt engineering: treat the context window as a finite resource with diminishing returns. They explain context rot and the n² attention budget, give curation principles for system prompts, tools, and few-shot examples, and describe three techniques for long-horizon tasks: compaction (maximize recall before precision), structured note-taking (agentic memory), and sub-agent architectures that trade clean context for deep exploration. They also advocate just-in-time retrieval via lightweight references, illustrated by Claude Code and Claude playing Pokémon.

Key points

  • Context rot and n² attention budgets degrade retrieval as token counts grow.
  • System prompts should sit at the right altitude; tool sets and examples should be minimal and diverse.
  • Compaction, structured notes, and sub-agents sustain coherence on long-horizon tasks.
  • Compaction should maximize recall first, then precision, to avoid losing key context.
  • Just-in-time loading of lightweight references often beats pre-computed retrieval pipelines.

After prompt engineering dominated attention in applied AI for several years, a new term is emerging: context engineering. Building with large language models is becoming less about picking the right words for a prompt and increasingly about answering a broader question: "What context configuration is most likely to produce the behavior we want from the model?"

Context refers to the set of tokens included in the input when sampling from a large language model (LLM). The engineering problem here is optimizing the utility of those tokens within the LLM's inherent constraints, so as to reliably achieve the desired outcome. Effectively steering an LLM often requires thinking in context—in other words: considering holistically the overall state available to the LLM at any given moment, and the behaviors that state might induce.

This article explores the emerging craft of context engineering and offers a refined mental model to help you build controllable, effective agents.

Context engineering vs prompt engineering

At Anthropic, we view context engineering as the natural evolution of prompt engineering. Prompt engineering refers to the methods for writing and organizing LLM instructions to get optimal results (see our documentation for an overview and practical strategies). Context engineering refers to a set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference, encompassing all other information that may fall into the context beyond the prompt itself.

In the early days of LLM engineering, writing prompts was the largest component of AI engineering work, because most use cases beyond everyday chat interactions required prompts optimized for one-shot classification or text generation tasks. As the name suggests, prompt engineering centers on "how to write effective prompts," especially the system prompt. However, as we move toward building more capable agents that run over multiple reasoning turns and longer time spans, we need strategies for managing the entire context state—system instructions, tools, the Model Context Protocol (MCP), external data, message history, and so on.

An agent running in a loop continuously generates data that may be relevant to the next reasoning turn, and this information must be refined iteratively. Context engineering is the art and science of selecting, from this ever-evolving universe of possible information, what will enter the finite context window.

Unlike the discrete task of "writing a prompt," context engineering is iterative: every decision about what to pass to the model is an act of curation.

Why context engineering is critical for building powerful agents

Although LLMs are fast and can manage ever-larger volumes of data, we have observed that, like humans, LLMs lose focus or become confused past a certain point. Research on "needle-in-a-haystack" benchmarks reveals a phenomenon called context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context degrades.

While some models degrade more gracefully than others, this characteristic appears across all models. Context must therefore be treated as a finite resource with diminishing marginal returns. Like humans with limited working memory capacity, LLMs expend an "attention budget" when parsing large volumes of context. Every new token introduced consumes some portion of that budget, which further underscores the need to carefully curate the tokens available to the LLM.

This attention scarcity stems from the LLM's architectural constraints. LLMs are based on the transformer architecture, which allows every token to attend to every other token in the entire context—for n tokens, that means n² pairwise relationships.

As context length grows, the model's capacity to capture these pairwise relationships is diluted, creating a natural tension between context scale and attention focus. Moreover, the model's attention patterns are learned from the training data distribution, and training data typically contains far more short sequences than long ones. This means models have less experience with, and fewer dedicated parameters for, long-range dependencies.

Techniques like position encoding interpolation allow models to handle longer sequences by adapting back to the smaller context they were originally trained on, but at some cost to their understanding of token positions. Together, these factors produce a performance gradient rather than a cliff: models remain highly capable over long contexts, but compared to short contexts, the precision of information retrieval and long-range reasoning may decline.

These realities mean that thoughtful context engineering is essential for building powerful agents.

What effective context consists of

Since LLMs are constrained by a finite attention budget, good context engineering means finding the smallest set of high-signal tokens that maximizes the probability of the desired outcome. That's much easier said than done, but in the following sections we'll walk through what this guiding principle means for each component of the context.

System prompts should be extremely clear, using simple, direct language, and stating ideas at the right "altitude" for the agent. The right altitude is the "just right" zone between two common failure modes. At one extreme, engineers hardcode complex, brittle logic into prompts to force precise agent behavior—this introduces fragility and increases maintenance complexity over time. At the other extreme, engineers give vague, high-level guidance that provides the LLM no concrete signal about the desired output while wrongly assuming shared context. The optimal altitude lies between the two: specific enough to effectively guide behavior, yet flexible enough to leave the model with powerful heuristics.

At one end of the spectrum are brittle if-else-style hardcoded prompts; at the other, prompts that are overly generalized or wrongly assume shared context.

However you decide to structure your system prompt, you should aim for "the minimal set of information that fully delineates the expected behavior." (Note: minimal doesn't mean short; you still need to give the agent enough information upfront to ensure it follows the desired behavior.) The best approach is: start by testing a minimal prompt with the strongest model available, see how it performs on your task, and then improve it by adding clear instructions and examples based on the failure modes exposed in the first round of testing.

Tools enable agents to act on their environment and to pull in new, supplementary context as they work. Tools define the contract between the agent and its information/action space, so it is critically important that tools promote efficiency—both returning token-efficient information and encouraging efficient agent behavior.

In "Writing tools for AI agents – with AI agents," we discussed how to build tools that are easy for LLMs to understand and have minimal functional overlap. Like functions in a well-designed codebase, tools should be self-contained, robust to errors, and extremely clear about their intended use. Input parameters should likewise be descriptive, unambiguous, and aligned with the model's inherent strengths.

One of the most common failure modes we see is a bloated toolset: either covering too much functionality or creating ambiguous decision points about "which tool to use." If a human engineer cannot confidently say which tool should be used in a given situation, you cannot expect an AI agent to do better. As discussed later in this article, curating a minimal viable toolset for the agent also helps maintain and prune context more reliably over long interactions.

Providing examples—that is, few-shot prompting—is a well-known best practice, and we still strongly recommend it. But teams often stuff a long list of edge cases into the prompt, trying to exhaustively enumerate every rule the LLM should follow on a task. We advise against this. A better approach is to carefully curate a set of diverse, representative examples that effectively demonstrate the agent's expected behavior. For LLMs, examples are worth a thousand words.

Our overall advice for each component of context (system prompt, tools, examples, message history, etc.) is: be deliberate, and keep the context informative yet compact. Next, we dive into dynamic context retrieval at runtime.

Context retrieval and agentic search

In "Building effective AI agents," we highlighted the distinction between LLM-based workflows and agents. Since that article, we have converged on a simple definition of an agent: an LLM autonomously using tools in a loop.

Through our work with customers, we see the entire field converging on this simple paradigm. As the capabilities of underlying models improve, the degree of agent autonomy can expand accordingly: smarter models allow agents to independently navigate subtle problem spaces and recover from mistakes.

We are also seeing a shift in how engineers think about designing context for agents. Today, many AI-native applications use some form of embedding-based retrieval before inference, surfacing important context in advance for the agent to reason over. As the field shifts toward more agentic approaches, we increasingly see teams layering "just-in-time" context strategies on top of these retrieval systems.

With the "just-in-time" approach, instead of pre-processing all relevant data, the agent maintains lightweight identifiers (file paths, stored queries, web links, etc.) and dynamically loads these references into context at runtime via tools. Anthropic's agentic coding solution, Claude Code, uses this approach to perform complex data analysis on large databases: the model can write targeted queries, store results, and analyze massive datasets using Bash commands like head and tail, all without ever loading the full data objects into context. This approach mirrors human cognition: rather than memorizing an entire corpus, we typically rely on external organization and indexing systems—file systems, inboxes, bookmarks—to retrieve relevant information on demand.

Beyond storage efficiency, the metadata of these references also provides an efficient mechanism for fine-tuning behavior—whether the cues are explicit or intuitive. For an agent working in a file system, a file named test_utils.py in a tests folder implies a very different purpose than the same file name in a src/core_logic/ directory. Folder hierarchies, naming conventions, and timestamps all provide important signals that help both humans and agents determine how and when to use a piece of information.

Letting agents autonomously navigate and retrieve data also enables progressive disclosure: agents can gradually discover relevant context through exploration. The context produced by each interaction shapes the next decision: file sizes hint at complexity; naming conventions reveal purpose; timestamps can serve as a proxy for relevance. Agents can assemble understanding layer by layer, keeping only what is necessary in working memory, and use note-taking strategies for additional persistence. This self-managed context window lets the agent focus on the relevant subset rather than drowning in exhaustive but potentially irrelevant information.

Of course, there are trade-offs: runtime exploration is slower than retrieving pre-computed data. Moreover, equipping an LLM with the right tools and heuristics to efficiently navigate its information landscape requires opinionated, deliberate engineering. Without proper guidance, agents may waste context by misusing tools, going down dead ends, or failing to identify critical information.

In some scenarios, the most effective agent may adopt a hybrid strategy: pre-retrieving some data for speed while deciding for itself whether to continue exploring autonomously. The decision boundary for the "right degree of autonomy" depends on the task itself. Claude Code is an agent that adopts this hybrid model: the CLAUDE.md file is "mindlessly" preloaded into context, while primitives like glob and grep let it navigate the environment and retrieve files just in time, effectively sidestepping problems with stale indexes and complex syntax trees.

Hybrid strategies may be better suited to scenarios with lower content dynamism, such as legal or financial work. As model capabilities improve, the trend in agentic design will be toward letting smart models act smartly, with the share of human curation gradually declining. Given the pace at which this field is advancing, "do the simplest thing that works" is likely still the best advice we can give teams building agents on Claude.

Context engineering for long-horizon tasks

Long-horizon tasks require agents to maintain coherence, context, and goal-directed behavior across continuous sequences of actions that exceed the LLM's context window in token count. For tasks spanning tens of minutes to hours of continuous work—such as large codebase migrations or comprehensive research projects—agents need specialized techniques to work around context window size limitations.

Waiting for larger context windows to arrive may seem like an obvious strategy. But it is likely that, for the foreseeable future, context windows of all sizes will not escape context pollution and information relevance problems—at least in scenarios where you are pursuing the strongest agent performance. To enable agents to work effectively over longer time spans, we have developed several techniques that directly address the constraints of context pollution: compaction, structured note-taking, and multi-agent architectures.

Compaction

Compaction means summarizing a conversation as it approaches the context window limit, then reinitializing a new context window with that summary. Compaction is usually the first lever in context engineering for driving long-term coherence. Its core is distilling the contents of the context window in a high-fidelity way, allowing the agent to continue working with minimal performance loss.

Take Claude Code as an example: we hand the message history to the model and ask it to summarize and compress the most critical details. The model retains architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs or messages. The agent then continues working with this compressed context, plus the five most recently accessed files. Users get continuity without having to worry about context window limits.

The art of compaction lies in trade-offs: overly aggressive compression loses subtle yet critical context—whose importance often only becomes apparent much later. For engineers building compaction systems, we recommend carefully tuning your prompts on complex agent traces. First maximize recall, ensuring the compaction prompt captures every relevant piece of information in the trace; then iteratively improve precision by removing extraneous content.

One readily available example of redundant content is clearing tool calls and results—when a tool call is already buried deep in the message history, why would the agent need to see the raw result again? One of the safest and lightest forms of compaction is tool result clearing, which recently shipped as a feature on the Claude Developer Platform.

Structured note-taking

Structured note-taking, or agentic memory, is the technique of having the agent periodically persist notes to memory outside the context window and pull those notes back into the context window later.

This strategy provides persistent memory at minimal overhead. Just as Claude Code creates to-do lists, or your custom agent maintains a NOTES.md file, this simple pattern lets the agent track progress across complex tasks, preserving critical context and dependencies that would otherwise be lost after dozens of tool calls.

Claude playing Pokémon demonstrates how memory transforms agent capabilities beyond coding. The agent maintains precise counts across thousands of game steps—tracking goals like "I've been training my Pokémon on Route 1 for the past 1,234 steps, Pikachu has leveled up 8 times, target is level 10." Without any prompting about memory structure, it develops its own map of explored areas, remembers which key achievements have been unlocked, and maintains tactical notes on battle strategies, helping it learn which moves are most effective against different opponents.

After a context reset, the agent reads its own notes and continues hours-long training routines or dungeon exploration. This coherence across summarization steps enables long-horizon strategies—strategies that would be impossible if everything had to fit within the LLM's context window.

As part of the Sonnet 4.5 release, we launched a public beta of the memory tool on the Claude Developer Platform, making it easier to store and consult information outside the context through a file-based system. This lets agents accumulate knowledge bases over time, maintain project state across sessions, and reference previous work without keeping everything in context.

Sub-agent architectures

Sub-agent architectures offer another way around context limitations. Rather than having one agent try to maintain state across an entire project, specialized sub-agents handle focused tasks in clean context windows. The lead agent coordinates with a high-level plan, while sub-agents perform deep technical work or use tools to find relevant information. Each sub-agent may explore extensively, consuming tens of thousands of tokens or more, but returns only a condensed, distilled summary (typically 1,000-2,000 tokens).

This approach achieves clean separation of concerns—detailed search context stays isolated within the sub-agent, while the lead agent focuses on synthesizing and analyzing results. We discussed this pattern in "How we built our multi-agent research system," where it significantly outperformed single-agent systems on complex research tasks.

How to choose among these approaches depends on task characteristics. For example:

  • Compaction suits tasks requiring extensive back-and-forth conversation, preserving conversational continuity;
  • Note-taking excels at iterative development with clear milestones;
  • Multi-agent architectures fit complex research and analysis where parallel exploration pays off.

Even as models continue to improve, the challenge of maintaining coherence across very long interactions will remain central to building more effective agents.

Conclusion

Context engineering represents a fundamental shift in how we build with LLMs. As models grow more capable, the challenge is no longer just crafting the perfect prompt, but thoughtfully curating at every step: which information is worth entering the model's limited attention budget. Whether you're implementing compaction for long-horizon tasks, designing token-efficient tools, or having agents explore environments in real time, the guiding principle remains the same: find the smallest set of high-signal tokens that maximizes the likelihood of the desired outcome.

As models improve, the techniques we've outlined will continue to evolve. We've already seen that smarter models require less normalization engineering, and agents can operate with greater autonomy. But even as capabilities amplify, treating context as a precious, finite resource will remain central to building reliable, effective agents.
