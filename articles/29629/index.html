What Is Tavily: How FDEs Put Web Search for Agents into Practice

Original title: Tavily 是什么：FDE 如何落地智能体联网搜索

Summary

Through a hypothetical insurance compliance example, it walks through Tavily's Search, Extract, and Research endpoints, shows how domain whitelists and citation-checking evals catch wrong dates, and analyzes Tavily's FDE job posting, which requires pre-sales technical discovery, solution design, and solid Python and backend skills.

Trying Tavily takes only a free API key and a first call. Yet Nebius, which just agreed to acquire Tavily, is hiring Forward Deployed Engineers (FDEs) to directly serve the product's largest and most strategically significant customers.

The FDE's job sits precisely in the gap between these two things. Calling an API takes minutes; what's truly laborious is deciding which sources the agent may read, how to verify its citations, and who is responsible when it cites the wrong source.

For those looking to enter applied AI, Tavily is a low-cost way to practice these skills. This article breaks them down one by one with a concrete example.

Nebius buys a layer of web capability for agents

On February 10, 2026, Nebius announced in Amsterdam that it had reached an agreement to acquire the agentic search provider Tavily. Its stated rationale is blunt: within a few years, AI agents will send more queries to the internet than humans do. According to Nebius, Tavily provides real-time web access, which agents need to ground their answers in reality.

According to Globes and PYMNTS, Tavily will retain its own brand and continue serving existing customers. The Tavily team, including founder and CEO Rotem Weiss, will join Nebius. According to SiliconANGLE, Tavily's customers include Cohere, MongoDB, Groq, and IBM.

What Tavily does and when you need it

Tavily's documentation describes the product as "the web layer for AI agents." Beyond search, the API includes an extract endpoint for scraping page content, and a research endpoint that synthesizes multiple sources and returns a report with citations. The real integration work begins with extract and research; a single search call is just the starting point.

This layer is needed because language models know nothing about events after their training cutoff, while an internal retrieval-augmented generation (RAG) system only knows the customer's own documents. So when a use case depends on constantly changing information outside the firewall, such as newly issued regulations or vendor news, the agent must be able to read web pages.

A minimal end-to-end example

Imagine an insurance company's compliance team that wants an agent to summarize the week's regulatory changes every Monday morning. This scenario is hypothetical and serves as a structure you can copy; none of its content comes from real API output.

Step one: the agent converts the requirement into a query, such as "life insurance regulatory changes this week," and calls Search. Suppose the results include a press release from Regulator A, a financial news article, and a law firm blog post.

Step two: the code keeps only URLs under the regulator's domain, then calls Extract to get the press release body, such as the passage stating which clause was amended and when it takes effect.

Step three: the model writes a summary using a fixed template, for example: "Regulator A amended the fee disclosure requirements, effective [date], source: [URL]." The rule is simple: any point that cannot be mapped to an extracted URL is removed from the summary.

When the agent cites that blog post

In the same scenario, consider a concrete failure case. The law firm blog ranks first in the Search results and summarizes the changes clearly, but gets the effective date wrong. Without a whitelist, the agent will pick the most readable source, and the compliance team receives an incorrect date paired with a citation that looks perfectly valid.

The whitelist stops it at step two: the blog's URL is not under the regulator's domain, so it never reaches Extract. But the whitelist will eventually be loosened, for example when someone adds a domain to "get more news."

So a second line of defense is needed: an eval that verifies citations. For each point, the eval searches the text extracted from the cited URL for the effective date given in the text. If it isn't found, the point is marked as failing, and the "points matching sources" ratio on the dashboard drops immediately.

Research can replace all three steps with a single call, since it directly returns a report with citations. A better approach is to prototype with Search and Extract first, log every URL, then compare against Research using the same eval. Check the official documentation for the exact parameter names; don't guess.

The hard part starts before the contract is signed

The job posting Nebius published for Tavily's FDE Enterprise role requires candidates to lead technical discovery and solution design during the pre-sales stage as customers expand their contracts. Before a single line of production code has been written, the FDE is already at the negotiating table.

Taking the insurance example above, the discovery must settle three things: which domains are trusted, how fresh the information must be, and who on the customer's side verifies citations. Once these three questions are answered, the design largely follows.

In production, every call needs a timeout. After a timeout, the agent should fall back to the results of the previous run and flag them as "not yet updated," rather than hanging indefinitely. The domain whitelist should live in a configuration file, with a specific owner designated on the customer's side.

What to learn first

The job posting requires solid hands-on engineering skills, especially Python, APIs, backend systems, and production-grade software development. This dictates the learning order: first write a client with timeouts and retries, then build a source-filtering pipeline, and finally write a citation-verification eval.

When reading the job description, watch for phrases like "technical discovery," "solution design," and "pre-sales." They indicate that the job involves communicating with customers in addition to writing code. On a resume, a line like "shipped a web search agent to production and measured the correct citation rate on 20 questions" carries far more weight than a list of library names.

If agents really will send more queries to the internet than humans, the valuable work is not the first API call, but making the results of agents reading the web trustworthy.
