What Is Multi-Agent Design? Configuration Patterns and Decision Criteria That FDEs Use in the Field

Original title: マルチエージェント設計とは？FDEが現場で使う構成パターンと判断基準

FDE総研 · 2026-10-19 · 10 min read

Summary

This article explains multi-agent design for forward deployed engineers (FDEs) building generative AI systems at customer sites. Its core argument: start with a single agent as a baseline and split into multiple agents only when subtasks are independent and can run in parallel. It cites Anthropic's research system (beating a single Claude Opus 4 agent by 90.2% on evaluations, but using roughly 15x the tokens) and Cognition's counterargument that parallel subagents without shared context produce inconsistent work. It catalogs five architecture patterns—orchestrator-worker, pipeline, routing, evaluator-optimizer, and handoff—and outlines a six-step process covering eval sets, JSON input/output contracts, tracing, cost limits, least-privilege permissions, and handover to customer teams.

Key points

  • Multi-agent design means splitting context and tools by role, not just boosting performance.
  • Anthropic's multi-agent system beat a single agent by 90.2% but used ~15x tokens.
  • Cognition warns parallel subagents lacking shared context produce inconsistent results.
  • Recommended process: build evals and a single-agent baseline before deciding where to split.
  • Fix handoffs with JSON contracts, set cost caps, and apply least-privilege permissions for handover.

What is multi-agent design? How does it differ from a single agent?

Multi-agent design is a design approach that coordinates multiple AI agents with divided roles to solve a single task.

When an FDE (Forward Deployed Engineer) integrates generative AI into business operations at a customer's site, the question of "one agent or multiple agents?" must be decided early. The FDE role, popularized by Palantir, involves building systems that operate alongside customer workflows and production data. For that reason, this decision affects operational cost and ease of isolating failures more than it affects how impressive a demo looks.

Definition: A design that splits roles, context, and tools

The essence of multi-agent design lies in dividing the context and tools that a single LLM would otherwise handle into separate roles.

A single agent repeats planning, tool calls, and result interpretation within one context window. In a multi-agent setup, roles are divided—for example, a "command tower that plans," a "researcher that searches," and an "evaluator that inspects output"—each with its own dedicated prompt, tools, and context. Since each agent only sees its own area of responsibility, instructions are less likely to get mixed up. On the other hand, you need to design how information is passed between agents.

Comparing the differences from a single agent in a table

It becomes easier to decide if you view the differences not as performance but as a trade-off among "cost, parallelism, and debuggability."

AspectSingle agentMulti-agent
ContextEverything consolidated in one windowSplit by role, summarized and passed along
Parallel executionBasically sequentialSubtasks can run simultaneously
Token consumptionRelatively lowTends to increase significantly (about 15x in the public case study below)
DebuggingTraceable in a single traceRequires tracking interactions between agents
Failure modesMissed instructions in long contextsInformation gaps, conflicting judgments, cascading errors
Suited usesTightly coupled, sequential workBroad research, independent subtasks

In its December 2024 technical article "Building effective agents," Anthropic recommends starting with a simple configuration and adding complexity only when needed. From the author's experience as well, when building a customer PoC (proof of concept) with multi-agent from the start, there are many situations where you can no longer tell whether the problem is accuracy or coordination.

When should you use multi-agent, and when should you avoid it?

It is effective for parallelizable research and independent subtasks, but for tightly coupled work, a single agent is the safer choice.

Suited scenarios: breadth-first research and independent tasks

Multi-agent tends to be effective in scenarios where a question can be broken down into independent sub-questions that can be researched in parallel.

In its June 2025 article "How we built our multi-agent research system," Anthropic published a configuration in which a lead agent (Claude Opus 4) directs multiple subagents (Claude Sonnet 4). In internal research task evaluations, it reported outperforming a single Claude Opus 4 agent by 90.2%. The same article also shows that most of the performance difference can be explained by token consumption, and that multi-agent uses about 15 times the tokens of a normal chat.

Translating this to FDE fieldwork, the following tasks are candidates.

  • Competitive or policy research that spans multiple internal systems and document sets
  • Data preparation and classification that runs the same processing in parallel per customer or site
  • Document creation with strict quality requirements that requires separating generation and inspection

Scenarios to avoid: tight coupling, low budget, short deadlines

In work where one decision strongly constrains the next, splitting agents breaks the context and tends to degrade quality.

In its June 2025 article "Don't Build Multi-Agents," Cognition pointed out that when parallel subagents work without knowing each other's decisions, the consistency of deliverables breaks down. It then presented principles emphasizing sharing context and recognizing that actions contain implicit decisions. Coding, where a series of changes strongly depend on each other, is a typical example.

Decision axisSuited to multi-agentSuited to single agent
Task dependenciesSubtasks are independentLater decisions depend on earlier ones
BudgetThe value of results exceeds token costProcessing cost must be tightly controlled
Timeline and teamTime available to build evaluation and observability infrastructurePoC needed within a few weeks
Required explainabilityCan be ensured through log designDecision path needs to be explained in a single line

What are the representative multi-agent configuration patterns?

The representative configurations are five: orchestrator, pipeline, routing, evaluator, and handoff patterns.

Here, we organize the classifications from guides published by Anthropic and OpenAI into a form that is easy to use in FDE fieldwork. Anthropic's "Building effective agents" presents five patterns: prompt chaining, routing, parallelization, orchestrator-workers, and evaluator-optimizer. OpenAI's "A practical guide to building agents" (2025) divides multi-agent systems into manager-type and decentralized (handoff) types.

PatternStructureSuitable use casesMain risks
Orchestrator-workersA command center decomposes tasks and distributes them to workersResearch, report writingDecomposition errors by the command center propagate to the whole system
Pipeline (chain)Processes fixed steps in sequenceExtraction → formatting → validationLow flexibility
RoutingClassifies inputs and directs them to specialized agentsInquiry handling, front-desk operationsClassification accuracy becomes the ceiling
Evaluator-optimizerA generator and an evaluator iterate back and forthDocuments and code with clear quality criteriaLoop costs increase
Handoff (decentralized)Agents hand off responsibilities to each otherMulti-stage customer supportAccountability tends to become blurred

Centralized: Orchestrator-workers

The centralized model, where a command center handles task decomposition and integration, is easy to control and is often the first configuration FDEs consider.

The command-center agent creates a plan, passes "objectives, output format, allowed tools, and completion criteria" to subagents, and integrates the returned results. Anthropic's research system mentioned earlier also takes this form. What matters most in the design is the granularity of instructions to subagents. Vague instructions cause subagents to duplicate the same research or miss parts of the scope.

Decentralized: Handoff and routing

Routing, which directs at the entry point, and handoff, which passes on responsibilities, are configurations well suited to organizations with clearly divided business departments.

For example, if business boundaries are clear, such as "accounting inquiries" and "HR inquiries," agent boundaries can be aligned with organizational boundaries. This makes it easier for the customer's department in charge to own the prompts and knowledge. Considering operational handover after the FDE leaves, this point is quite important.

Quality assurance: Evaluator-optimizer

A configuration that separates generation and evaluation into different agents is a means of raising quality for tasks where evaluation criteria can be articulated.

The evaluator judges the output produced by the generator against a checklist and sends it back for rework. If the evaluation criteria are vague, such as "easy to read," the loop has difficulty converging. Setting an upper limit on the number of rework cycles is a prerequisite.

What is the procedure for designing multi-agent systems?

The safe approach is to proceed in order: establish a baseline with a single agent, measure its limits, and then split.

Steps 1-3: Determine the baseline and split points

The goal of the first three steps is to reach a state where the reason for splitting can be demonstrated with data.

  • Build an evaluation set: Gather representative inputs and expected outputs from the customer's real data, and define pass/fail criteria.
  • Measure the baseline with a single agent: Using the same evaluation set, record accuracy, processing time, and token consumption.
  • Identify bottlenecks and determine split points: Split only when there are problems that splitting can solve, such as "context overflow," "parallelization would make it faster," or "an inspector is needed."

Steps 4-6: Design contracts, evaluation, and observability

In the latter three steps, fix the handoffs between agents as "contracts" and make them traceable in production.

  • Define input/output contracts: Fix each agent's inputs and outputs using JSON schemas or similar, reducing free-text handoffs.
  • Run both per-agent and overall evaluations: Measure the accuracy of individual agents and the accuracy of the final deliverable separately.
  • Implement tracing and stop conditions: Record inter-agent messages, tool calls, and token consumption, and set limits on iteration counts and costs.

In the author's experience, if you skip step 4 and start with free-text handoffs, you tend to spend a lot of time later identifying the causes of failures.

What should FDEs watch out for when introducing multi-agent systems in the field?

The biggest pitfalls are context discontinuity and cost inflation, and in customer environments, permission design and accountability also come into question.

Technical aspects: Context sharing, error propagation, and cost

On the technical side, three things must be contained at the design stage: information discontinuity, error cascades, and token costs.

RiskWhat happensDirection of countermeasures
Context discontinuitySubagents make decisions without knowing the premisesShared memory, passing decision logs
Error cascadesUpstream errors are amplified downstreamValidation of intermediate outputs, schema checks
Cost inflationTokens surge due to parallelization and loopsBudget limits, using different models appropriately
Non-determinismPaths vary even with the same inputSaving traces, regression testing with evaluation sets

Using different models appropriately is also effective. A configuration that uses a high-performance model for the command center and lightweight models for routine workers makes it easier to balance cost and accuracy.

Organizational aspects: Customer explanation, permissions, and operational handover

On the organizational side, it is essential to agree with the customer on "who is responsible for which agent's decisions."

It is also important to separate access permissions for data and systems per agent according to the principle of least privilege. For tools involving writes or external transmissions, consider inserting human approval. FDEs do not remain on-site at the customer indefinitely. The author believes that leaving prompts, evaluation sets, and trace-reading methods in a form that can be handed over to the customer is a condition for putting multi-agent systems into operation.
