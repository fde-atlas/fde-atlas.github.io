Text-to-SQL Semantic Layer: Unifying Metric Definitions with dbt MetricFlow

Original title: Text-to-SQL 语义层：dbt MetricFlow 统一指标口径

FDE Times · 2026-10-09 · 6 min read

Summary

This guide explains why Text-to-SQL projects fail even when the generated SQL runs without errors: LLMs pick wrong join paths, inflating MRR by 12x on annual contracts or double-counting via fan-out joins, because warehouse schemas don't encode how a company defines revenue. The author, writing for FDEs, recommends defining metrics once in a semantic layer using dbt MetricFlow, so LLMs and finance dashboards share one calculation. A 2026 dbt Labs benchmark on the ACME Insurance dataset (11 questions, 20 runs each) found semantic-layer failures produce error messages while Text-to-SQL failures produce plausible wrong answers, though the test was vendor-run with schemas fully in context. Board, audit, and KPI metrics should route through the semantic layer; Text-to-SQL is for exploratory questions only. The article closes with rollout steps and common pitfalls.

Key points

  • LLM SQL errors are usually wrong join paths, not syntax.
  • Schemas can't express how a company defines revenue.
  • Semantic layers fix metric definitions and join paths once.
  • dbt benchmark: semantic layer fails loudly, Text-to-SQL silently.
  • Start with top KPIs, verify against finance before enabling LLMs.

Table schemas won't tell the model how finance calculates MRR; define each metric once in the semantic layer, and the model and reports share the same definition.

Key takeaways

  • LLMs rarely write syntactically invalid SQL. The common problem is choosing the wrong join path, producing wrong results with no error at all.
  • The semantic layer fixes metric definitions and join paths in advance, so the same metric yields the same result every time, whether queried by an LLM or a dashboard.
  • Any metric reported to the board, handed to auditors, or counted toward KPIs should go through the semantic layer. Leave Text-to-SQL for exploratory questions.

Imagine this scenario: you've just deployed an agent at a SaaS company, and the finance team asks it, "What's January's MRR?" It returns a number along with a clean SQL query that runs without any errors. By afternoon, the number doesn't match finance's own reports, and the gap is significant. You're the one called into the meeting.

Nearly every Forward Deployed Engineer (FDE) working on "query data with natural language" projects hits this wall. The problem isn't the model or the prompt; it's that the definition of "revenue" was never written down in a form a machine can read.

This article explains how to solve the problem at its source: define each metric once in the semantic layer, then have both the LLM and the customer's reports use that same definition.

Syntactically correct SQL can still answer the wrong question

The Omni team describes this problem clearly. In their view, the SQL an LLM writes isn't inherently bad; the difficulty is that it looks plausible while meaning the wrong thing. Omni's example is exactly an MRR question: the model joins orders directly to products, skipping the subscriptions table, and returns total order amounts, with no error anywhere in the process.

Cube explains why models make this kind of mistake: a data warehouse schema doesn't say how your company defines revenue. A field called

amount

gives no clue whether it's cash collected, recognized revenue, or monthly amounts receivable. Those rules live in the finance team's heads, in some spreadsheet, or in a view only one person still remembers.

On-site with customers, this is precisely the FDE's job: translating definitions from business language into something a machine can execute. The model can't do this step for you.

One customer, two numbers

Consider a concrete example (numbers are illustrative only). Customer A buys a $12,000 annual plan and pays it all in January. If you take the orders → products shortcut and sum order amounts, January shows $12,000 and the next eleven months show zero. If you calculate through the subscriptions table, MRR is $12,000 / 12 = $1,000 every month of the year.

Both queries run, but only the second answers finance's question. A single annual plan inflates January's MRR by 12x. If the customer has hundreds of contracts like this, the wrong numbers are hard to spot by eye.

The second common error is fan-out. A $100 order contains three line items. Joining orders to order_items and running

SUM(order_total)

yields $300, because the order total is repeated on every line item. The dbt documentation calls these fan-out joins and chasm joins, and MetricFlow specifically avoids them when choosing join paths.

Define once, call by name everywhere

The semantic layer solves both error types by fixing join paths in the model. According to Omni, when the same MRR question is asked against the semantic layer, the join paths are predefined and the metric is calculated the same way every time. Cube takes the same approach: the agent queries named metrics and dimensions rather than reconstructing business logic from table and column names.

In the dbt ecosystem, the engine doing this work is MetricFlow. It defines conventions for semantic models and metrics, and generates SQL from those definitions. Each semantic model has three parts: entities are join keys, the edges connecting models; dimensions are the angles for slicing data; and metrics are built on top of them.

Here's an example of how to write MRR; the exact syntax depends on your dbt version:

semantic_models:
  - name: subscriptions
    model: ref('fct_subscriptions')
    defaults:
      agg_time_dimension: billing_month
    entities:
      - name: subscription
        type: primary
        expr: subscription_id
      - name: customer
        type: foreign
        expr: customer_id
    dimensions:
      - name: billing_month
        type: time
        type_params:
          time_granularity: month
      - name: plan_tier
        type: categorical
    measures:
      - name: mrr_amount
        agg: sum
        expr: monthly_amount

metrics:
  - name: mrr
    label: 月度经常性收入
    type: simple
    type_params:
      measure: mrr_amount

Note that

monthly_amount

. The annual-plan-divided-by-12 logic is already handled in the

fct_subscriptions

table, which has been reviewed and has a clear owner. From then on, the LLM just calls

billing_month

by

plan_tier

and

mrr

. Finance's dashboard calls the same metric, so the agent and finance no longer each have their own numbers.

Failing loudly beats failing silently

In 2026, dbt Labs ran a benchmark on the ACME Insurance dataset: 11 questions, each asked 20 times, across multiple LLMs. The most memorable finding wasn't accuracy but how the two approaches fail. When Text-to-SQL fails, it gives a plausible-sounding but wrong answer; when the semantic layer fails, it gives an error message.

For an FDE, this distinction is critical. Seeing an error message, users will rephrase the question or come to you. A plausible-looking wrong number, however, can sit in board materials for an entire quarter.

The benchmark has a few limitations worth knowing. To make Text-to-SQL work, the authors put the entire schema into context, and they themselves admit this doesn't scale to larger datasets.

Atlan, in summarizing the test, also points out that this was a vendor testing its own product. Treat the results as a reference only; you still need to run your own evals on the customer's data.

dbt's recommendation doesn't require choosing one over the other. Any number reported to the board, handed to auditors, or counted toward OKRs, KPIs, or weekly reports should come from an LLM connected to the semantic layer. Leave Text-to-SQL for ad hoc exploratory questions.

Where to start on-site with a customer

Don't start by modeling the entire data warehouse. Take the weekly KPI report or the latest board deck and pick out the metrics that appear most often. That list is the scope for round one.

Next, sit down with the person actually responsible for each definition, usually finance or RevOps. Before writing YAML, write the definitions in plain language, e.g., "MRR counts annual plans in 12 equal installments, excludes onboarding fees, and is recognized by billing month." Record the approver's name for every definition.

Then write the semantic models, run the metrics over a few closed months, and check every number against the customer's existing reports one by one. Wherever they don't match, go back to the definition's owner; don't guess yourself.

Once the numbers match, connect the LLM. At this point, make the routing rules explicit: questions about defined metrics go to the semantic layer; everything else goes to Text-to-SQL.

Common pitfalls

The first pitfall is defining metrics by column name. A field called

revenue

in the warehouse isn't necessarily revenue in the accounting sense. The second pitfall is silently falling back to Text-to-SQL when the semantic layer errors. Doing so throws away the semantic layer's biggest advantage: errors surface instead of being masked.

The third pitfall is letting the LLM create new metrics on the fly. New metrics should go through code review like any other change. The last pitfall is trusting only vendor benchmarks without your own eval set. The eval set should consist of the customer's real questions, each with a finance-confirmed answer.

How should you write this skill into your resume?

When browsing job descriptions for FDE or Solutions Engineer roles, watch for keywords like dbt, MetricFlow, Cube, semantic layer, or "metrics definitions". They signal that the company needs someone who can keep the numbers accurate, not just someone who wires an LLM up to a database.

A single line on your resume like "unified core KPI definitions in a semantic layer and reconciled them against financial statements before exposing them to agents" carries far more weight than "built a Text-to-SQL chatbot".

LLMs will keep getting better at writing SQL. But figuring out how a customer actually calculates revenue still requires asking people, and then writing the answer down in exactly one place.
