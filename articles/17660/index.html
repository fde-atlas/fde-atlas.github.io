Web Security Academy Free Security Courses: FDE Learning Path

Original title: Web Security Academy 免费安全课程 FDE 学习路线

FDE Times · 2026-11-13 · 5 min read

Summary

This article recommends that forward deployed engineers complete PortSwigger's free Web Security Academy before touching customer APIs, focusing on three topics: API testing, authentication, and SSRF. It walks through concrete vulnerabilities FDEs are likely to introduce—mass assignment letting users escalate privileges via extra JSON fields, inconsistent login error messages enabling username enumeration, and URL-fetching AI agent tools becoming SSRF entry points—and shows whitelist-based fixes. It also suggests a learning order (server-side vulnerabilities, authentication, API testing, SSRF), notes Burp Suite Community Edition suffices for most labs, and says the paid BSCP certification is optional unless targeting security-heavy FDE roles.

Key points

  • Web Security Academy is free, with 31 topics and hundreds of labs.
  • FDEs should prioritize API testing, authentication, and SSRF topics.
  • Mass assignment allows privilege escalation via extra fields; use field whitelists.
  • Uniform login error messages prevent username enumeration attacks.
  • URL-fetching agent tools need domain whitelists and post-resolution IP checks against SSRF.

The API, authentication, and SSRF sections of the PortSwigger Academy teach Forward Deployed Engineers (FDEs) to examine their own integrations from an attacker's perspective.

Key Takeaways

  • PortSwigger's Web Security Academy is completely free, with content from the company's research team and Dafydd Stuttard, author of The Web Application Hacker's Handbook.
  • For Forward Deployed Engineers (FDEs), the three most valuable sections are API testing, authentication, and SSRF, because these are exactly the things you build at customer sites.
  • Most labs can be completed with Burp Suite Community Edition; the paid BSCP certification is optional.

Some certification labs in the Web Security Academy give you a list of candidate usernames and passwords, and the task is: find the real account and log in. Breaking into an otherwise unremarkable login form with your own hands is an experience no slide deck can replace.

The course is produced by PortSwigger, the company behind Burp Suite. PortSwigger describes it as the online training center for web application security and states that it is 100% free. The content comes from PortSwigger's research team and Dafydd Stuttard, author of The Web Application Hacker's Handbook.

This matters for Forward Deployed Engineers (FDEs) because your job is connecting systems: calling customer APIs, building a login page for a demo, writing agents that fetch links on their own.

Each of these opens another entry point. Rather than waiting for the customer's security team to find a vulnerability in your code, practice attacking on a system that lets you break it.

It's a lab, not a textbook

According to a beginner's guide published in 2026, the academy has 31 sections and hundreds of labs across three difficulty levels: Apprentice, Practitioner, and Expert.

PortSwigger describes its labs as realistic puzzles that test your ability as an attacker. After registering an account, you can track your progress, advance from Apprentice all the way to Expert, and check your ranking in the Hall of Fame.

Since September 2023, the academy has offered learning paths—pre-planned routes that keep beginners from getting lost among the many sections. The first two launched were an overview of server-side vulnerabilities and SQL injection.

According to the same guide, the free Burp Suite Community Edition is sufficient for most labs; only labs requiring Collaborator and the certification exam require the Professional edition.

One person who passed the OSWE wrote in a review that the labs cover nearly all common vulnerabilities and considered the academy an excellent supplement to formal courses. But with such a large lab library, an FDE doesn't need to finish everything. Three ideas are the most worth remembering.

Idea 1: Your API accepts more parameters than you think

The API testing section focuses on RESTful and JSON APIs, covering three topics: reconnaissance via API documentation, mass assignment, and server-side parameter pollution. PortSwigger warns that mass assignment (also called auto-binding) can unintentionally create hidden parameters.

Suppose you wrote

PATCH /api/users/me

to let a customer's employees change their email. The framework binds the entire JSON request body directly to the user object. A user can escalate their own privileges simply by sending an extra

"role": "admin"

field, even though the API documentation never mentions it.

The vulnerable code and the hardened code often differ by only a few lines:

# 修改前：把整个 JSON 请求体绑定到模型
user.update(**request.json)  # 多发一个 "role": "admin" 也能通过

# 修改后：只接收允许的字段
ALLOWED_FIELDS = {"email", "display_name"}
data = {k: v for k, v in request.json.items() if k in ALLOWED_FIELDS}
user.update(**data)

First thing to do at a customer site: for every endpoint that writes data, list the fields it is allowed to accept and block everything else. It's also worth rereading the API documentation you publish through the eyes of someone doing reconnaissance.

Idea 2: Login bugs are security bugs

The authentication section emphasizes that authentication vulnerabilities let attackers obtain sensitive data and functionality. Many of its labs require you to enumerate usernames first, then brute-force passwords. And this is also where things most often go wrong when you're rushing to build a login portal for a pilot project.

A simple example: the login form returns "account does not exist" when the username is wrong and "incorrect password" when the password is wrong.

With just these two different messages, an attacker can filter out a list of real accounts and then focus on guessing passwords for each one. The fix is to merge both branches into the same response:

# 修改前：两条不同的提示，暴露了哪些用户名存在
if user is None:
    return error("账号不存在", 404)
if not check_password(user, password):
    return error("密码错误", 401)

# 修改后：所有失败看起来完全一样
if user is None or not check_password(user, password):
    return error("用户名或密码错误", 401)

So before shipping a demo, make every login failure return the same message and the same status code, and limit the number of attempts.

Idea 3: An agent that fetches URLs is an SSRF entry point

Server-side request forgery (SSRF) means tricking a server into making requests on the attacker's behalf. PortSwigger writes that successful SSRF attacks often result in unauthorized actions or access to data within the organization.

For FDEs working on AI, this is the most important of the three ideas. Imagine you give your agent a

fetch_url

tool running on the customer's internal network. With a single cleverly worded prompt telling it to read the address of some internal service, the agent will obediently bring the data out. Webhooks and "import data from a link" features carry exactly the same risk.

What to do: write a list of domains the tool is allowed to call, block internal address ranges, and put it in the design document before the customer's security team even asks.

A bad fix is worse than no fix

The easiest trap to fall into is using a blocklist instead of an allowlist. Banning

fetch_url

and a few internal IP ranges from the

localhost

tool sounds sufficient, but a blocklist leaks as soon as it misses one way of writing an address.

Allowlists are much tighter, but not airtight either. An allowed domain with an open redirect can still forward requests to internal addresses, and DNS rebinding can make a domain resolve to a different IP after your check.

So re-check the IP after resolution and just before establishing the connection, and either disable automatic redirect following or re-check each redirect hop as a new request.

The same goes for mass assignment. If you only block the

role

field, the moment the model adds a sensitive field and nobody remembers to update the blocklist, the endpoint is exposed again.

The next trap is limiting login attempts by IP only. An attacker who switches IPs renders the limit useless, so also count failures per account. After merging the error messages, check the status codes too, to make sure the two failure cases are truly identical.

What order to learn in, and what to put on your resume

This course suits engineers with a few years of experience who are familiar with backend code but have never looked at a system from an attacker's perspective. Learn the server-side vulnerabilities learning path first, then authentication, then API testing, and finally SSRF. Within each section, finish the Apprentice labs before moving on to Practitioner, and save the Expert labs for later.

Burp Suite Certified Practitioner (BSCP) is the official certification, but it is optional, requires payment, and demands an active Burp Suite Professional subscription. It's only worth pursuing if you're targeting FDE roles with a heavy security focus.

Don't just write "knows web security" on your resume. Be specific about which API, authentication, and SSRF Practitioner labs you completed, and attach a short write-up on how you hardened an agent tool to defend against SSRF.

In an agent design interview, proactively bringing up allowlists, post-resolution IP checks, and redirect handling before the interviewer asks is a very clear signal.

Customers won't ask how many labs you solved. They'll ask whether your integration is secure, and the most credible answer is one you've personally verified on a system you're allowed to break.
