Palantir Deployment Strategist vs FDSE: roles, CVs

FDE Times · 2026-10-24 · 6 min read

Summary

This article compares Palantir's Deployment Strategist and Forward Deployed Software Engineer (FDSE) roles, arguing that one CV cannot serve both. Strategists work onsite with client analysts to turn vague hunches into measurable questions and run user training, with programming listed only as a plus. FDSEs must be strong coders in languages like Python, Java, C++ or TypeScript, building data pipelines and custom applications, with as little as one year of experience required. Using a spare-parts warehouse example, the author shows how the two roles split one project. Logistics vary widely by posting—travel from 10-25%, onsite requirements, and security clearances—so each job listing must be read individually. The article ends with advice on tailoring CVs per role and avoiding the mistake of treating either role as non-technical or purely technical.

Key points

  • Strategists define problems with client analysts; FDSEs build pipelines and apps.
  • Coding is optional for strategists but mandatory for FDSEs.
  • FDSE requires as little as one year of experience, prioritizing coding skill.
  • Travel, onsite and clearance terms differ by location and posting.
  • Tailor one CV per role; neither role is purely technical or non-technical.

One CV sent to both Deployment Strategist and FDSE openings convinces neither, and the job postings spell out what evidence each role wants to see.

In brief

  • Strategists define the problem with the client's analysts and run user training; FDSEs build the pipelines and custom applications.
  • For strategists, programming is a plus; for FDSEs, strong coding is mandatory, even though the experience bar starts at one year after university.
  • The same title comes with different travel, onsite and clearance terms by location, so read each posting on its own.

Palantir’s careers page lists two jobs side by side: Deployment Strategist and Forward Deployed Software Engineer. Both involve working on site with clients, and both sound like a fit for an engineer who enjoys code as much as talking to users.

The common reflex is to apply to both with the same CV. A CV written for both roles convinces neither.

The good news is that the postings say fairly clearly what each role does, provided you read them as carefully as a spec. The easiest way to do that is to follow one project from start to finish, then turn what you see into two CVs.

One asks the right question, the other builds the answer

The posting for a Deployment Strategist on Palantir’s US government team describes someone who helps clients see the connections between scattered facts and then turns their “hunch” into reality.

The UK government posting is more specific: the strategist goes on site and meets the client’s analysts to understand the key questions they need answered.

The same UK posting says strategists work with Forward Deployed Engineers to integrate data into a stable, scalable pipeline. In other words, the job description itself hands the pipeline to the engineer. Experience with Python, R, Matlab or SQL is listed only as a “plus.”

The FDSE posting runs the other way. Candidates must be strong coders, proficient in Python, Java, C++, TypeScript/JavaScript or a similar language, and the work includes building custom applications for client needs.

What does each role do on the same project?

Take a government agency that manages a spare-parts warehouse. An analyst suspects that shortages come from a handful of suppliers who deliver late, but nobody has proved it. That is the kind of hunch the posting refers to.

The strategist goes on site and spends the day with the analyst.

Their job is to turn the hunch into a measurable question, for example: “Which suppliers delivered more than 14 days late in the past six months, and which units ran short of parts because of those late orders?” They also find where the data lives: the procurement system holds order dates, the warehouse system holds receipt dates.

Then it is the FDSE’s turn. The engineer writes connectors into both systems and deals with the usual problem of one supplier carrying two different codes in two places. They then build a pipeline that runs daily and a small application that lets the analyst filter by supplier and by unit.

The final round goes back to the strategist. During training, they notice the analyst ignores the filters and exports everything to a spreadsheet. They take that observation back to the engineer, and the next version ships with a button that exports a report in the exact format the analyst already submits to their superiors.

In practice the line between the roles is less sharp than this. Some secondary sources say Palantir internally calls FDEs “Delta” and strategists “Echo,” and quote Palantir as saying Echo leans toward product management while Delta leans technical.

According to the same sources, each role is part product manager, part software engineer and part strategist, so people in one role often do the other’s work too.

Which lines in a posting decide which role fits you?

The first line to look for is the coding requirement. One side lists programming as a plus; the other lists strong coding as a condition. If you are not yet confident writing a pipeline that runs on real data, practice that before applying for FDSE roles.

The second is experience. The FDSE posting asks for as little as one year of relevant experience after university. A bar that low does not make the job easy to get: paired with the strong-coding requirement, it suggests coding ability counts for more than years on the job.

The third is logistics, and this is where many applicants skim. The FDSE posting lists up to 25% travel to client sites, with flexibility depending on personal preference. The strategist posting in Vilnius requires 10-20% travel plus a security clearance.

The US government strategist posting requires being on site 4-5 days a week, mainly in Colorado Springs, and also needs clearance. The same title carries different terms in each location, so read each posting individually rather than reading one and assuming it holds for the rest.

Choose by looking back at your best working week

Paraform, a recruiting platform, offers a simple rule: if you want to build, choose FDE, the role that writes production code inside the client’s environment; if you prefer scoping problems and working with stakeholders, choose strategist. That is one recruiter’s view, but it matches the gap in coding requirements between Palantir’s two postings.

A better test is your own record. Think of the most recent week you came home from work still energized. If that was the week you untangled a hard data bug, you lean FDSE. If it was the week you sat with users and realized they were asking the wrong question, you lean strategist.

The CV: one version per role

The same experience can be told two ways. The table below takes an internal project to show how one story shifts its emphasis.

What you need to prove Strategist version FDSE version
Understanding the problem Interviewed 6 users and merged three scattered requests into one measurable question Read logs and schemas to find the right data sources for the agreed question
Creating the solution Wrote the spec and acceptance criteria with the engineering team Wrote a Python pipeline joining two systems and normalizing duplicate codes
Putting it into use Led the training session and recorded where users got stuck Updated the application from feedback and deployed the new version the same day

The strategist version should still include a line on SQL or Python, since the posting names it as a plus. The FDSE version should still include a line about users, because building applications “for client needs” requires understanding those needs.

Mistakes that sink an application

The most common is assuming the strategist role is non-technical. Someone who talks to FDEs about pipelines every day without understanding how the data flows will struggle to define a feasible problem.

The opposite mistake is assuming FDSEs just code alone: the posting gives them custom applications built for client needs and requires willingness to travel to client sites.

The third is applying without reading the logistics. If you cannot be present 4-5 days a week in a specific city, or are not eligible for clearance, even a strong application will struggle to advance for postings that require them.

The two roles are not a senior and a junior rung but two halves of the same loop with the client. Once you know which half you belong to, you will no longer need to apply for both.
