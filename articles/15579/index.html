Excalidraw and Whiteboarding for FDEs

HCL GUVI Blog · 2026-09-28 · 6 min read

Summary

This HCL GUVI blog post explains how forward deployed engineers (FDEs) can use Excalidraw and whiteboarding to communicate technical solutions to customers, product teams, and engineers. It covers useful diagram types—architecture, data flow, integration, workflow, and troubleshooting—and proposes a six-step explanation method: start with the problem, show the current system, highlight the problem area, present the solution, discuss trade-offs, and confirm understanding. The author stresses keeping diagrams simple, matching detail to the audience, avoiding mistakes like information overload and unexplained acronyms, and treating whiteboarding as a collaborative conversation tool rather than a finished presentation.

Key points

  • FDEs can use Excalidraw for architecture, data flow, integration, workflow, and troubleshooting diagrams.
  • A six-step method: problem, current state, pain point, solution, trade-offs, confirmation.
  • Diagrams should stay simple, with detail scaled to the audience.
  • Common mistakes include overload, unexplained acronyms, and chasing visual perfection.
  • Whiteboarding aids customer discovery by clarifying requirements and validating assumptions.

Why Is Whiteboarding Important for FDEs?

FDEs regularly work with ambiguous requirements and complex customer environments. Before implementing a solution, they often need to understand how systems currently work and communicate a proposed approach.

Whiteboarding helps turn these discussions into something visible.

For example, instead of verbally explaining an integration, an FDE can draw:

Customer Application → API → Integration Service → Database → Internal System

This allows everyone involved to discuss the architecture, identify missing components, and ask questions.

Whiteboarding is particularly useful during:

  • Customer discovery
  • Technical requirement discussions
  • Architecture reviews
  • Solution design
  • Troubleshooting sessions
  • Deployment planning
  • Project handoffs

How Can FDEs Use Excalidraw?

Excalidraw is a collaborative whiteboarding tool designed around simple, hand-drawn-style diagrams. Its visual style can make technical discussions feel less formal and easier to modify during live conversations.

FDEs can use it to create:

1. Architecture Diagrams

Show how applications, services, databases, APIs, and cloud components interact.

2. Data Flow Diagrams

Illustrate how information moves from one system to another.

3. Integration Diagrams

Explain connections between customer applications and external services.

4. Process Workflows

Represent business processes and show where automation or AI can be introduced.

5. Troubleshooting Diagrams

Map a system and identify where a failure may be occurring.

The goal is not to create a perfect diagram. It is to make the technical discussion easier to understand.

💡 Did You Know?

A technical diagram can serve as a shared reference during a customer conversation, helping technical and non-technical participants discuss the same system using a common visual representation.

What Should FDEs Draw on a Whiteboard?

FDEs can use several types of diagrams depending on the situation.

1. Current-State Architecture

Start by showing how the customer’s systems work today.

For example:

Users → Web Application → Backend → Database

Then add external services, APIs, authentication systems, or other relevant components.

2. Proposed Architecture

Once the problem is understood, show how the proposed solution changes the existing system.

This allows the customer to compare the current and future states.

3. Workflow Diagram

For business-focused discussions, a workflow may be more useful than a technical architecture.

For example:

Customer Request → Validation → AI Processing → Human Review → Final Response

4. Data Flow

Data-flow diagrams help explain where information originates, how it is processed, and where it is ultimately stored.

These diagrams are especially useful for integration, analytics, and AI projects.

How Should FDEs Explain Technical Solutions?

Creating a diagram is only the first step. FDEs also need to explain it effectively.

A useful approach is to move from simple to complex.

1. Start With the Problem

Explain what the customer is trying to accomplish.

2. Show the Current System

Draw the existing workflow or architecture.

3. Identify the Problem Area

Highlight the bottleneck, integration challenge, or missing capability.

4. Present the Solution

Add the proposed components and explain what changes.

5. Discuss Trade-Offs

Explain important decisions involving cost, scalability, security, reliability, or implementation complexity.

6. Confirm Understanding

Ask the customer whether the diagram accurately represents their environment and requirements.

This turns whiteboarding into a collaborative process rather than a one-way presentation.

What Makes a Good FDE Whiteboard?

A good technical whiteboard should be easy to understand and easy to modify.

Follow these principles:

  • Start with the main components.
  • Keep the first version simple.
  • Use arrows to show relationships or data flow.
  • Group related components.
  • Label important connections.
  • Add technical details only when necessary.
  • Leave room for changes during discussion.
Pro Tip: Start with a rough diagram and refine it as the conversation progresses. Whiteboarding is most useful when customers can correct, question, and contribute to the diagram.

The level of detail should also depend on the audience. A CTO may want architecture and business implications, while an engineer may need API, database, authentication, and deployment details.

What Whiteboarding Mistakes Should FDEs Avoid?

Even technically correct diagrams can create confusion when they contain too much information.

Common mistakes include:

  • Adding every technical component immediately
  • Using unexplained acronyms
  • Creating overly complicated diagrams
  • Focusing on visual perfection
  • Ignoring the customer’s actual workflow
  • Explaining implementation before understanding the problem
  • Failing to update the diagram when requirements change
Warning: A diagram should clarify a technical conversation, not become another source of complexity. If someone needs a long explanation just to understand the diagram, simplify it.

How Can FDEs Improve Their Whiteboarding Skills?

Whiteboarding improves through practice.

Try explaining common technical scenarios using simple diagrams:

  • Design a REST API.
  • Explain an authentication flow.
  • Draw a cloud deployment.
  • Show a database integration.
  • Map a customer support workflow.
  • Design a basic RAG application.
  • Explain an application troubleshooting process.

Practice explaining each diagram in two ways: once to a technical audience and once to someone without a technical background.

This develops the communication flexibility that FDEs need when working with different customer stakeholders.

Conclusion

Excalidraw and whiteboarding for FDEs provide a practical way to communicate technical solutions during customer-facing projects. By visually representing architectures, integrations, workflows, and data flows, FDEs can make complex discussions easier to understand and collaborate on.

The most effective FDEs use whiteboarding as a conversation tool rather than simply presenting finished diagrams. Start with the customer’s problem, map the current environment, develop the proposed solution together, and refine the diagram as new information emerges. With regular practice, whiteboarding can become an important part of an FDE’s technical communication toolkit.

FAQs

is whiteboarding important for Forward Deployed Engineers?

Whiteboarding helps FDEs explain complex architectures, workflows, integrations, and technical solutions visually. It also gives customers an opportunity to correct assumptions and contribute to solution discussions.

How can FDEs use Excalidraw?

FDEs can use Excalidraw to create architecture diagrams, data flows, integration diagrams, process workflows, and troubleshooting maps during customer discussions.

What should an FDE include in a technical diagram?

An FDE should include the main systems, components, connections, data flows, and important technical details relevant to the discussion. Avoid adding unnecessary information.

Should FDE diagrams be highly detailed?

Not always. The appropriate level of detail depends on the audience and purpose of the discussion. Start simple and add technical details when they become relevant.

Can whiteboarding help during customer discovery?

Yes. FDEs can use whiteboarding to map the customer’s current workflow, identify pain points, clarify requirements, and validate their understanding of the problem.

How can I improve my FDE whiteboarding skills?

Practice explaining common technical scenarios using simple diagrams. Focus on clarity, logical flow, audience awareness, and connecting technical decisions to customer requirements.
