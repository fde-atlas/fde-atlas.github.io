FDE-Gym Benchmark: Evals Results for AI Agent Customer Delivery

Original title: FDE-Gym 基准：AI 智能体客户交付评测结果

FDE Times · 2026-10-17 · 4 min read

Summary

FDE-Gym, released on arXiv on October 15, 2026, evaluates AI agents on customer delivery using 95 tasks drawn from 20 real deployment projects across 18 domains, scored by each customer's own success metrics rather than whether code runs. Across 13 model configurations from seven vendors, the best averaged only 0.56 and fully solved just 14 of 95 tasks. The authors attribute the main bottleneck to uncovering unstated customer constraints. The article contrasts this with narrower benchmarks like FDE-Bench, where solve rates reach 52.9–75.0%, and advises aspiring FDEs to practice requirements discovery and showcase customer-metric outcomes.

Key Takeaways

  • FDE-Gym contains 95 tasks drawn from 20 real deployment projects across 18 domains, scored against the customers' success metrics
  • Across 13 model configurations from seven vendors, the strongest averaged a score of just 0.56, fully solving only 14 of the 95 tasks
  • The authors argue that the main bottleneck for agents is uncovering constraints customers never stated, which is the core of FDE work

Faced with 95 tasks requiring the delivery of a working system to a customer, the strongest AI agent configuration fully solved only 14. This is the central result of FDE-Gym, a benchmark released on arXiv on October 15, 2026.

The authors tested 13 model configurations from seven vendors. In the setting closest to reality, the best of them averaged a score of only 0.56.

The novelty lies in the judging criteria. FDE-Gym doesn't check whether the code runs or the tests pass; it measures how much the delivered system improves the customer's own success metrics. This closely mirrors how real customers judge results.

For Forward Deployed Engineers (FDEs) and aspiring FDEs, these results are worth attention because they measure the last mile: turning what an agent builds into actual outcomes in the customer's environment. In this stretch, even the strongest configuration failed to solve most tasks.

The benchmark evaluates agents, not humans, so what follows is inference rather than conclusion: this last mile is likely where FDEs can still add value, and the required skills can be trained.

Where Machines Trip

The authors argue that real customer deployments differ fundamentally from benchmark tasks with clearly defined problems. They point out that the main bottleneck is identifying constraints no one mentions.

Take a hypothetical example. A customer wants to reduce ticket processing time, and the agent builds a beautiful automated triage pipeline.

Only in the second week does it emerge that, due to a contract clause, enterprise customer tickets must first be read by a human. The code is still correct, but the customer's metric doesn't budge. This is exactly the kind of failure FDE-Gym's judging criteria are designed to catch.

The way tasks are constructed targets the same weakness. Experts took 20 real deployment projects across 18 domains, adapted them into the customers' operating environments, and then altered several key facts to generate variants.

They kept only tasks whose graders had been validated. Because the key facts differ, familiar solutions can't simply be copied over: to pass, the agent must re-read the context of each variant.

Narrow Tasks Are Easy, End-to-End Is Hard

Viewed alongside other recent benchmarks, the boundary is quite clear. FDE-Bench, by Ding, Zhan, Li, and Guo, released on September 23, 2026, measures only a narrow slice of FDE work: configuring deployment environments with Docker, Compose, and Kubernetes. Across its 136 tasks, seven models achieved solve rates between 52.9% and 75.0%.

The two benchmarks differ in tasks and scoring, so they can't be compared directly. But the trend is clear: the narrower and better-defined the task, the better agents perform; once they must figure out what the customer actually needs, scores drop sharply.

Another study by Ding and Zhan, "Trains but Doesn't Learn" (September 21, 2026), treats delivering a post-trained model as FDE work. The agent goes through ten stages, each scored against facts recorded on the platform.

Its core failure mode sounds familiar: the entire run looks perfectly fine, yet the final model is no better than the base model.

Which Skills Are Worth More

There is an open-source project of the same name on GitHub: DeepLethe's deeplethe/fde-gym. Built around the same idea, it offers a complete practice platform where every exercise comes from real customer deliveries and is completed in conjunction with coding agents.

The project's thesis: once AI can write correct code, correct code no longer distinguishes a great engineer from an average one. What truly sets people apart is the ability to deliver results when a system runs in a real customer environment.

So if you're preparing for an FDE role, don't spend all your time grinding algorithm problems. Practice customer requirements discovery instead: in the first meeting, ask how the customer measures success, who has the authority to say "no," and which data must never leave the system. On your resume, replace descriptions like "built X" with changes in customer metrics.

When reading job descriptions or interviewing, ask directly: is this role accountable for customer outcomes, or only for the code assigned to it? The "14 out of 95" figure says nothing about human ability, since the benchmark only scores agents. But it shows that the last mile of deployment remains where machines are weakest, and where effort is most worth investing.
