Rapid Prototyping for Forward Deployed Engineers

Vibe Engines · 2026-07-24 · 14 min read

Summary

This Vibe Engines article argues that an FDE's prototyping superpower is getting a convincing working demo in front of a customer fast, not writing durable code. Treat the prototype as disposable scaffolding that buys information, build only the narrowest vertical slice end to end, and fake everything else — auth, scale, second workflows — while never faking the core capability being proven. Use boring, fast tools like hosted LLM APIs. A worked example shows a five-day ticket-classification prototype: the 72% human-agreement bar is recomputed from real data, accuracy climbs from 61% to 74%, and 76% on a held-out set of 100 fresh tickets answers the question, after which the prototype is deleted and the real build scoped. The piece insists on agreeing the success bar and deadline with the sponsor beforehand, labeling all fakes in demos, and making any prototype-to-production hardening an explicit, dated decision — with a strict read-only rule so prototypes never write to customer systems.

Key points

  • Prototypes are disposable experiments judged by what they teach, not code quality.
  • Build one thin vertical slice on a real example; fake everything off that path.
  • Faking plumbing is fine; faking the claimed capability destroys trust.
  • Report only held-out-set scores against a bar agreed before day one.
  • Prototype-to-production hardening must be an explicit, scoped decision, never silent.

An FDE’s superpower isn’t writing the best code — it’s getting a working, convincing thing in front of a customer while the problem is still fresh. That means prototyping like the code is disposable, faking everything that isn’t the point, and building relentlessly toward one demo moment.

Throwaway-first

The most useful mental shift in prototyping is to treat the code as disposable from the start. Not because it’s bad, but because its job is to buy information, not to last. A prototype answers questions — is this valuable? is it feasible? did I understand the problem? — and once it has, its value is spent. Engineers who forget this fall into the sunk-cost trap: they lovingly build a prototype into a fragile pseudo-product, then can’t bring themselves to rebuild it properly.

Naming the code “throwaway” up front is liberating. You skip the abstractions, hardcode the edge cases, and use the ugliest thing that works — because you know it’s scaffolding. Speed of learning is the only metric that matters, and every hour spent making a prototype “clean” is an hour not spent learning whether it should exist at all.

A prototype isn’t a small product. It’s an experiment with a UI. Judge it by what it taught you and whether it convinced the customer — not by its code quality.

The smallest demoable slice

Discovery told you the one workflow that proves value. Prototyping builds a thin vertical slice through it — and fakes everything to the side.

The enemy of a fast prototype is horizontal building — polishing every layer across the whole feature set. The move is vertical: pick the single path from input to valuable output, and build just that path end to end, on one real example. A narrow slice that actually works is a hundred times more convincing than a broad mock-up that doesn’t.

Build for real (the slice)

  • One input → the core transformation → one valuable output.
  • On a single real record the customer will recognize.
  • The one capability you’re there to prove.

Fake for now (everything else)

  • Auth, settings, multi-user, the second and third workflows.
  • Scale, error handling, the admin UI.
  • Anything not required to make them say “oh, that’s it”.

This is why the scoping work matters so much: it hands you the exact slice to build. Without it, you’ll build horizontally and run out of time before anything works end to end.

Choose a boring, fast stack

A prototype is the wrong place for adventurous engineering. Reach for the most boring, fastest tools you know cold: a language you’re fluent in, managed services for anything stateful, and hosted model APIs rather than self-hosting. Every novel technology you introduce is a tax on iteration speed paid at the worst possible time.

Instead of…Reach for… (in a POC)Because
Self-hosting a modelA hosted LLM APIZero infra; swap for self-hosted only if the deployment target forces it
A production database + migrationsSQLite / a managed Postgres / a fileYou’re proving value, not durability
KubernetesA single container or a scriptOrchestration is a scale problem you don’t have yet
A custom UI frameworkA notebook, a script, or a tiny web appThe output matters; the chrome doesn’t

There’s a caveat: if discovery revealed the deployment target will be on-prem or air-gapped, let that shape even the prototype (e.g. don’t build the demo on a cloud-only service you can’t use later). Boring-and-fast still wins — just pick the boring tools that will survive the move.

Fake it — honestly

The art of the fast prototype is doing by sleight-of-hand everything that isn’t the point, while keeping the point real.

Faking is not cheating — it’s prioritization made concrete. Three techniques recur:

The one hard rule is honesty about the capability. It’s fine to hardcode the account, stub the CRM, and manually kick off the job — as long as the thing you’re claiming (“the model extracts these fields accurately from your documents”) is genuinely real and running. Faking the plumbing is prototyping; faking the actual capability is lying, and it destroys trust the moment production reality arrives.

Before a demo, ask: “If they asked me to run this on a second real example right now, would the core still work?” If yes, your fakes are fine. If no, you faked the point.

Demo-driven development

The most productive way to aim a prototype is to build backwards from the demo. Picture the exact moment you want the customer to react — the “so what” — and build only what’s needed to reach it convincingly. Everything on the path gets real; everything off it gets faked or cut.

This has a wonderful side effect: it keeps you honest about value. If you can’t picture a demo moment that would make the customer lean in, you don’t yet understand the value — and no amount of code will fix that. Demo-driven development turns “what should I build?” into the far sharper “what’s the single moment that would make them believe, and what’s the least I need to reach it?”.

Set a demo date early and treat it as immovable. A deadline is the best scope-cutter in existence: it converts an open-ended build into a series of decisions about what to leave out. When to run the demo, and how to run it, is its own craft — covered in scoping and, in depth, the demo playbook.

Throw away, or harden

A prototype’s life ends in one of two ways, and confusing them is a classic FDE mistake. Either it did its job and gets discarded (the value question is answered; its shortcuts would fight you in production), or its core is genuinely sound and you deliberately harden it into a real system.

Default to disposable. The shortcuts that made the prototype fast — hardcoded config, no error handling, a hand-run step — are exactly what make it dangerous in production, and untangling them is often slower than a clean rebuild informed by everything you learned. When you do decide to harden, treat it as a separate project with its own bar: reliability, observability, security, and a handoff plan. That fork — POC to production — is important enough to have its own checklist, because the gap between “it demoed” and “people depend on it” is where a lot of otherwise-successful deployments quietly fail.

The throwaway decision, made in advance and in writing

The prototype that becomes production without anyone deciding is the most expensive artefact in forward deployed engineering.

Speed is the point of a prototype, and speed is bought by skipping things: error handling, tests, auth, the second data source, anything that is not the question being answered. That is correct engineering. It becomes negligence at exactly one moment — when the demo goes well and someone says “can we just start using it?” — and the way to survive that moment is to have decided beforehand.

The question

“Can a model separate these six queues at better than the 72% two clerks agree at?” One question, answerable, with a number in it.

The budget

Five days. Stated to the sponsor. A prototype without a stated end date does not have one.

The exit

Answered → delete it and scope the real build. Not answered → say so. Either way the artefact does not survive.

What makes the exit enforceable is making the prototype visibly unfit for production rather than quietly unfit. Structural loudness beats a warning in a README, because the README is not what someone reads before wiring it into a scheduled job:

PROTOTYPE = True

EXPIRES = "2026-08-15" # the date agreed with the sponsor

if PROTOTYPE:

banner("PROTOTYPE — results are not audited, do not act on these")

if today() > EXPIRES:

raise SystemExit("prototype window closed — scope the build or extend deliberately")

assert not writes_to_production(), "a prototype does not write to their systems"

# the three things a prototype is allowed to skip, stated out loud:

# no auth · no retries · one data source · no persistence

# the one thing it is NOT allowed to skip:

# it never writes to a customer system. read-only, always.

The read-only rule is the one worth being inflexible about. A prototype that only reads can be deleted on a Friday with no consequences; a prototype that has written 4,000 rows into their claims system is now a migration, an audit conversation and an apology, and it got there without anyone approving it.

The answer is not no. It is: “yes — here is what it would take to make that safe, and here is what it does today that you should not rely on.” Then the hardening gate is a scoped piece of work with a date rather than a thing that silently did not happen.

Worked example: the five-day queue prototype, day by day

Take the page’s own question: can a model sort tickets into six queues better than the 72% two clerks agree at? The budget is five days. The ticket counts and scores below are illustrative. The shape of the week is the point.

DayGoalRealFakedResult
1Get the data and the bar200 real tickets, each labelled by both clerksNo auth, no live feed: a read-only CSV exportClerks agree on 144 of 200: the 72% bar, recomputed rather than taken on trust
2First passA hosted LLM API call per ticketQueue names and definitions hardcoded in the prompt122 of 200 match clerk A: 61%. Below the bar, and that is useful to know
3Read the missesAll 78 misses, read by handNothing newMost misses fall between two similar queues. Sharper definitions: 148 of 200, 74%
4Guard against fooling yourself100 fresh tickets nobody has looked atYou start each run by hand (Wizard-of-Oz)76 of 100: 76% on held-out data. This is the number you report, not the 74%
5Demo and exitPaste any ticket, see the queue and the model’s reasonThe UI is a single page with no loginQuestion answered: 76% beats 72%. Delete the prototype and scope the build

Day 4 is the step most prototypes skip. By day 3 you had read every miss and edited the prompt against those 200 tickets, so 74% partly measures how well you fit them. A fresh 100 that you never looked at is the honest test. Day 5 ends the way the page says it must. The answer is a number against a bar agreed in advance, and the artefact is deleted. What gets scoped next (live queue integration, auth, retries, an audit trail) is everything the week deliberately faked.

Common mistakes

  • Reporting the score you tuned onIf you edit the prompt while staring at a set of examples, your score on those examples goes up whether or not the model got better. Keep a held-out set you never read, and report only that number, as on day 4 above.
  • Setting the bar after the resultBuild first and decide what counts as success afterwards, and any result can be presented as a success. Agree the number with the sponsor before day 1, ideally one the customer already believes, such as how often their own people agree.
  • Leaving the fakes unlabelled in the demoA stub that looks real becomes a promise. Say out loud, or show on screen, which parts are hardcoded or hand-run. The sponsor then hears an accurate scope for the real build, instead of finding the gap in week six.
  • Prototyping on data production will not haveA clean CSV an admin exported by hand may have fields, labels or formatting that the live feed lacks. Before the demo, check that every input the prototype uses can actually be had in production, at the same quality and the same time.
  • Demoing to the sponsor aloneThe people who do the work today (the clerks, in this example) know which mistakes matter and which are harmless. A sponsor can be impressed by a 76% that the clerks would reject in a minute, because its 24% misses fall on the urgent queue. Put a real user in front of it before you call the question answered.

Where this shows up in the real world and in interviews

  • The first weeks of an engagementA forward deployed engagement often has to earn its next phase. A working slice on the customer’s own data, measured against a bar they set, is what turns interest into a scoped project. It is also the fastest way to learn whether you understood the problem.
  • The XP spikeExtreme Programming calls this a spike: a time-boxed piece of throwaway code written to answer one technical question, then discarded. The page’s throwaway-first rule is the same idea, applied with a customer watching.
  • Design sprintsThe five-day design sprint popularised by Google Ventures ends with a realistic-looking prototype put in front of real users. It is the same bargain as this page: fake everything except what the user must react to, and stop on a fixed day.
  • The interview versionAsked “you have one week on site, what do you build?”, a strong answer names the one question, the number that answers it, what will be real, what will be faked, the held-out check, and what happens on day 5 either way. Listing features or a tech stack misses what the question is testing.

Check yourself

Your prototype scores 81% on the 200 tickets you tuned the prompt against. The bar is 72%. Is the question answered?

Not yet. You edited the prompt while reading those tickets, so 81% partly measures how well you fit them. Run it on a fresh held-out set. Only that score, measured against the 72% agreed in advance, answers the question.

The CRM API is not available until week three. The demo is on day 5. What do you do?

Stub it: return a canned response so the flow works end to end. The CRM is plumbing, not the capability being proved. Tell the sponsor it is stubbed. The read-only rule still applies once the real API arrives.

The demo went well and the sponsor asks to run it on live tickets from Monday. What is your answer?

“Yes, here is what it takes to make that safe.” Then list what the prototype skipped: auth, retries, the live feed, monitoring, and anything that would write to their systems. Hardening becomes a separate piece of work with a date. Saying yes and quietly wiring the prototype in is the failure the page warns about.

Mid-week you find the deployment target is air-gapped. You built on a hosted model API. Throw the prototype away?

Had you known on day 1, the page’s advice applies: let the target shape even the prototype. Mid-week, not necessarily, because its job is to answer the value question, and a hosted model can still answer that. But you now owe the sponsor a second question: will a model that can run on-prem hit the same bar? Note it as a risk in the scope rather than switching stacks halfway through the five days.

Quick answers

How fast should an FDE prototype be?

Fast enough to get something real in front of the customer within the first week or two of a deployment, while the problem and the relationship are still fresh. The goal isn’t a finished product — it’s a convincing demonstration that the value is achievable. Days, not months.

Is it okay to fake parts of a prototype?

Yes — faking the parts that aren’t the point (hardcoding a value, stubbing a service, doing a step by hand behind the scenes) is a core prototyping skill, as long as the thing you’re proving is genuinely real. The line is honesty: never fake the actual capability you’re claiming to demonstrate. Fake the plumbing, prove the value.

What stack should you use for a POC?

The most boring, fastest one you know well. Managed services, a familiar language, and hosted model APIs beat clever architecture during a prototype — you’re optimizing for speed of iteration, not scale or elegance. Save architectural decisions for when you know the solution is right and the deployment target is settled.

When do you throw a prototype away versus keep it?

Throw it away when it did its job — proved (or disproved) the value — and its shortcuts would fight you in production. Keep and harden it only when the core is genuinely sound and rebuilding would waste real work. Most FDE prototypes should be treated as disposable by default; hardening is a deliberate, separate decision.
