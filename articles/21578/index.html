x402 Payment Security Vulnerabilities: Audit Checklist for Uncapped Spending, Solana Verifier Bypass, and Login Signature Replay

Traversaal.ai · 2026-11-04 · 6 min read

Summary

Traversaal.ai details three critical x402 payment protocol vulnerabilities as of June 2025: clients default to no spending cap, a Solana verifier accepted ApproveChecked instructions as proof of payment, and login signatures lacked origin binding, enabling cross-site replay. All are patched, but none received a CVE, so npm audit shows clean on vulnerable installs. The article provides audit checklists—verifying installed versions, testing verifiers on devnet, inspecting signed payloads—and recommends subscribing to GitHub releases and adopting upgrade-evaluation policies for payment-critical dependencies regardless of CVE status.

Key points

  • x402 clients had no default spending cap, exposing agents to unlimited charges.
  • A pre-patch Solana verifier accepted ApproveChecked as completed payment.
  • Login signatures lacked origin binding, allowing cross-site replay attacks.
  • No CVEs were assigned, so npm audit misses all three exposures.
  • Recommended controls: version pinning, devnet testing, GitHub release monitoring.

TL;DR: As of June 2025, x402 payment security vulnerabilities include three critical risks: uncapped default spending limits, a Solana ApproveChecked verifier bypass that accepts token approvals as proof of completed payment, and a cross-site login signature replay attack. Auditing your implementation requires checking your exact version, spending cap configuration, and dependency pipeline. Standard npm audit output misses all three exposures because no CVE was assigned to the relevant fix.

Key Takeaways

  • x402 has no default spending cap: By default, a compromised or malicious server can charge an AI agent any price with no client-side limit triggering. Action: confirm your installed version's default and set an explicit cap.
  • The Solana verifier accepts fake transfers: A pre-patch verifier accepts an ApproveChecked instruction as proof of completed payment, allowing attackers to receive service without sending funds. Action: test your verifier on devnet before trusting production results.
  • Login signatures can be replayed across sites: The signed payload omits origin binding, so a captured signature can authenticate on any x402-protected site. Action: upgrade to a version with origin binding and add server-side origin validation as an interim compensating control.
  • npm audit is blind to this entire exposure class: Zero CVE assignment produces zero warnings on vulnerable installs. Action: subscribe to the x402 GitHub releases feed and adopt a policy requiring upgrade evaluation for payment-critical dependencies regardless of CVE status.
  • Treat severity ratings as a starting point: The issues described here were surfaced by a third-party researcher, not the protocol maintainer. Verify findings independently against the published disclosure before assigning internal priority.

What Is the x402 Uncapped Spending Vulnerability, and How Do You Audit for It?

By default, x402 clients carry no spending cap, meaning a server, legitimate or compromised, can charge any price and the client will pay it. This is not a misconfiguration in the traditional sense. It is the absence of a protective default, and the practical consequence is that a compromised price endpoint exposes every automated agent using the client to unlimited fund drainage with no client-side tripwire.

Audit checklist: - Run 

npm list x402

across all services and confirm your installed version against the patched version identified in the researcher's published disclosure.

- Search your codebase for

spendControls

. If the key is absent, confirm in writing what default your installed version applies. - If

spendControls: false

is set intentionally, document the business justification and confirm per-call spend logging exists before accepting the risk. - Review who controls the value in the

X-PAYMENT-REQUIRED

header and whether that endpoint can be tampered with between server and client.

What Is the x402 Solana ApproveChecked Verifier Bypass, and How Do You Test for It?

Audit checklist: - Locate the instruction-type assertion in your verifier source. Confirm it names

Transfer

or

TransferChecked

explicitly rather than accepting a broader instruction class. - On Solana devnet, submit a transaction containing only an

ApproveChecked

instruction. A patched verifier must reject it. Any 2xx response confirms the bypass is still present. - If consuming the verifier as a package dependency, confirm the upstream package version is at or above the patched release identified in the advisory. - Log all verifier decisions with the full instruction set for post-incident forensics regardless of patch status.

Audit checklist: - Inspect the signed payload directly. Confirm it includes the requesting origin or a server-generated nonce bound to the session. - If running a pre-patch version, treat the deployment as fully exposed regardless of any configuration adjustments. - Add server-side origin validation as a compensating control while an upgrade is in progress. - Review session logs for signatures used across multiple origins within a single session window, which is the fingerprint of an active replay attempt.

Why Does npm audit Show Clean on a Vulnerable Install, and How Do You Actually Detect This?

Concrete alternative detection checklist: - Version-pin audit: Run

npm list x402

across all services and compare the output against the patched version confirmed in the researcher's advisory. -

Changelog monitoring:

Subscribe to the x402 GitHub releases feed. Release changelogs carry security context that advisory databases will not surface when no CVE is filed. -

SBOM diffing:

Any service built before the patch date without a subsequent lock file update is likely running a vulnerable version. -

Governance policy review:

Confirm whether your organization's policy requires upgrade evaluation for payment-critical dependencies regardless of CVE assignment. If it does not, this blind spot applies to every payment library you operate.

Frequently Asked Questions

Does upgrading to the patched version fully remediate all three findings? Yes, provided the upgrade is applied to every service that instantiates an x402 client or verifier. Also audit

spendControls

after upgrading. The patch introduces a spending cap as a new default, but the configuration option to disable it explicitly remains available.

Is setting 

spendControls: false

in the patched version ever appropriate?

Only for transactions between trusted parties where compensating controls are already in place: per-call spend logging, server-side price validation, and anomaly alerting. It is not an appropriate default for AI agents calling third-party APIs.

How do I test whether my Solana verifier rejects ApproveChecked without affecting production? Submit a transaction containing only an

ApproveChecked

instruction to your verifier endpoint on Solana devnet. Any 2xx response confirms the bypass is still present and the service is running a pre-patch verifier.

Why was no CVE filed, and who is responsible for closing that gap? CVE assignment requires either vendor self-reporting or a third-party MITRE request. Vendors of payment-critical libraries should file CVEs for security-relevant fixes. Teams should not treat CVE assignment as their primary upgrade signal for payment infrastructure.

Conclusion

All three vulnerabilities are fixable by upgrading to the patched version identified in the researcher's published disclosure. The more durable problem is the disclosure pattern itself: a critical patch shipped with no CVE, no advisory, and no npm signal, and no automated mechanism in a standard security toolchain would have flagged it.

Run

npm list x402

across your entire deployment footprint now and compare the output against the confirmed patched version. Then close the governance gap so the next silent patch gets caught through version monitoring before public disclosure forces the issue.

The vulnerability is patched. The blind spot that let it sit undetected is not.
