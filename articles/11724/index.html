A harness is everything around a frozen model that makes it an agent. The model is a function from tokens to tokens; it cannot read a file, run a test, remember yesterday or refuse to delete a database. Each of those is software, and together that software decides whether the same model is a demo or a system a customer will run unattended.

In 2026 the evidence stopped being anecdotal. With the weights held fixed, published harness changes moved public benchmarks by 3 to 14 points; the same model produced a broken application alone and a working one inside a harness; and the year's worst agent incidents were harness failures: an over-scoped token in a file, a backup inside the blast radius of the thing it protected, a destructive endpoint with no gate. This guide covers both halves, the gains and the failures, with the primary source beside each claim.

It is organized around seven planes: control, instruction, context and memory, capability, policy, execution and assurance. Every chapter names the mechanism, the evidence and the way it fails, and ends with links to the FDEInterviews concepts, questions, lessons and paper breakdowns that drill it.

  • Harness
  • Everything around a frozen model that makes it an agent; distinct from an evaluation harness, which runs trials and grades them.
  • Deny rule
  • A permission rule evaluated first and never overridable by an allow, a prompt or the model.
  • Evidence ladder
  • Verification from cheapest to most real; done returns only from the top.
  • pass^k
  • The share of tasks solved on all k trials; the reliability number for unattended work.
  • Paired comparison
  • A comparison of matched task and seed outcomes, with missing grades disclosed and uncertainty calculated across tasks.
  • Overlay
  • The customer-owned layer: instruction map, skills, scripts, oracles, policy, eval.

Harness engineering is the design of everything around a frozen language model that turns it into an agent you can run: the loop, the instructions it reads, the context it sees on each turn, the state it keeps between sessions, the tools and connectors it may call, the checks that decide whether work is done, the permissions, credentials and sandboxes that bound what it can touch, and the audit record of what it did. The model decides what to do; the harness decides whether, when, where and how, and whether the result counts.

Published same-model comparisons show that harness changes can materially affect task success and cost. Their gains depend on the workload, compute budget and evaluation method; they do not establish that the harness always matters more than the model. The guide reproduces those comparisons with their conditions, and shows that infrastructure configuration alone moved one benchmark by six points, so it also teaches how to measure your own harness changes honestly.

Forward deployed engineers and platform engineers who adopt, extend or build agent harnesses inside a customer's environment, and candidates preparing for agent and system design rounds. It assumes you can write production software and have used a model API inside an agent loop; it does not assume you have run one unattended for six hours or answered a security team about it.
