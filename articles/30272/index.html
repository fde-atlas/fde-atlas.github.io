FDE Coding Interview Prep: How to Read Cracking the Coding Interview

Original title: FDE 编程面试准备：Cracking the Coding Interview 怎么读

FDE Times · 2026-11-09 · 4 min read

Summary

This article explains how FDE candidates should use Cracking the Coding Interview (6th edition, CareerCup, 2015, 708 pages, 189 problems) efficiently. It argues the opening chapters on Big O and named problem-solving techniques matter more than grinding all problems, and that reading order depends on interview format: a ~45-minute Google-style algorithms round suits the algorithm chapters, while OpenAI's 60-minute production-style build round calls for OOP design, scalability/memory limits, and threading chapters. Key Takeaways

  • The 6th edition (CareerCup, 2015, 708 pages) contains 189 problems, but the official website still says 150
  • The two opening chapters on Big O and problem-solving techniques are more valuable than grinding through all 189 problems
  • An FDE coding interview may be a 45-minute algorithm problem or a 60-minute build with requirements added midway—ask the recruiter first

Cracking the Coding Interview, 6th edition, runs 708 pages. With only a month left before a Forward Deployed Engineer (FDE) interview, few people can finish the whole book, so the real question is: which chapters should you read?

The answer depends on which kind of coding interview you're facing. Some companies test conventional algorithm problems, which this book covers in depth; others test production-style builds, where only a few chapters are actually useful.

A book thicker than its title

The author is Gayle Laakmann McDowell. According to the retailer's page, the 6th edition was published by CareerCup on July 1, 2015, with 708 pages and ISBN 978-0-9847828-5-7. The official website still titles it "150 Programming Interview Questions and Solutions," but the book actually contains 189 problems, each with hints.

The author's website says this edition contains 70% more content than the previous one. Although the book has been out for a while, its core content hasn't aged: how to think when facing an unfamiliar problem while an interviewer watches.

The difficulty is that there's no single template for FDE coding interviews. Educative's course on the Google FDE interview describes the coding round as a standard data structures and algorithms interview, about 45 minutes with one or two problems—exactly this book's home turf.

As for OpenAI, Exponent's guide says its onsite interview is a 60-minute production-style build. The task may be split into several sequential parts, with new requirements added after the first version works. The same book calls for different reading strategies depending on the interview round.

The value lies before the first problem

Before the 189 problems there are several opening chapters: the interview process, behavioral interview preparation, Big O, and a chapter on technical questions introducing five algorithmic approaches. Many readers jump straight to the exercises—that's a mistake. The opening chapters teach the method; the exercises are just where you practice it.

The Big O chapter covers time and space complexity, amortized time, when log N appears, and how to derive the runtime of recursive functions. The section "Multi-Part Algorithms: Add vs. Multiply" is worth reading closely.

Suppose you first iterate over every order in list A, then iterate over every customer in list B. The two loops run sequentially, so the complexity is O(A + B); nest B's loop inside A's loop, and it becomes O(A × B).

With 10,000 orders and 1,000 customers, the difference is 11,000 steps versus 10,000,000 steps.

Before writing code, practice saying this calculation out loud. A single sentence—"the two loops run sequentially, so it's O(A + B)"—is enough to show the interviewer that you understand what you're about to write.

Named techniques beat memorized answers

The techniques chapter teaches named problem-solving approaches like BUD, Base Case and Build, and Data Structure Brainstorm, and also covers what good code should look like. Named techniques are easy to remember. When you get stuck, you have a checklist to work through item by item instead of sitting in silence.

In OpenAI's build round, the "good code" part matters even more. When the second requirement appears at the 30-minute mark, code with clear naming and sensible function decomposition can be modified in minutes; code hastily written just to get it running may need a full rewrite.

What order should you read for different interview rounds?

The 189 problems are grouped by topic: arrays and strings, linked lists, stacks and queues, trees and graphs, recursion and dynamic programming, sorting and searching, object-oriented design, databases, threads and locks, testing, and more. So you can pick chapters as needed rather than reading cover to cover.

For a roughly 45-minute algorithm problem, read the Big O and techniques chapters first, then practice arrays and strings, trees and graphs, and sorting and searching in that order, finishing with recursion.

For a production-style build, after the two opening chapters move on to object-oriented design, scalability and memory limits, and threads and locks. These three chapters come closest to the real work this type of interview simulates.

For example, the task is to write a tool that reads logs and counts errors per service. Then two requirements are added: the log file is larger than memory, and multiple threads write to it concurrently. That's when the chapters on memory limits and locks come in handy.

Turn practice into evidence on your resume

Educative recommends confirming the interview format with the recruiter, and that should be the first thing you do. Sending one email in advance can save you two weeks of grinding dynamic programming for an interview that never tests it.

After that, turn what you practiced into something others can see. A small repository whose commit history shows how the code evolved through two or three requirement changes, with complexity notes included, says more about your ability than a resume line like "solved 300 LeetCode problems."

Cracking the Coding Interview remains a solid foundation for preparing for coding interviews. For an FDE, the efficient approach is to study the two opening chapters closely, then pick the remaining chapters based on the interview format confirmed with the recruiter.
