From SRE to Forward Deployed Engineer: Skills and Gaps

FDE Times · 2026-10-16 · 6 min read

Summary

This article maps the path from site reliability engineering to forward deployed engineering, arguing SREs already cover much of the FDE skill set: cross-layer troubleshooting, observability and reliability work appear almost verbatim in FDE job listings, and on-call experience builds the ability to diagnose unfamiliar systems under pressure. The real gaps are writing production code with APIs, tests and code review, knowing enough machine learning to reason about models, and developing client-facing problem definition and product thinking. Citing sources like Paraform and AITraining2U, the author notes technical skill is only the minimum bar, and advises generalizing one-off client fixes into reusable product features and rewriting CV bullets around user impact.

Key points

  • SRE skills in troubleshooting, observability and reliability overlap heavily with FDE job requirements.
  • On-call experience is an underrated asset for adapting to FDE work.
  • Technical skill is the minimum bar; problem definition and communication differentiate candidates.
  • Key gaps: production-grade services with APIs and tests, plus basic ML literacy.
  • FDEs should generalize single-client fixes into shared product capabilities.

Incident work, observability and cloud carry over; the gaps are APIs, data structures, ML and becoming the client's trusted technical adviser.

In brief

  • Cross-layer troubleshooting, observability and reliability appear word for word in FDE job ads, so engineers who have done on-call tend to adapt quickly.
  • Technical skill is only the minimum bar, though. What sets candidates apart is more likely problem definition, communication and product thinking.
  • The gaps to close are real production code, enough ML to reason about models, and the habit of generalizing fixes into features.

Pragmatike’s listing for a Principal Forward Deployed Engineer on Built In Boston reads like an ordinary week for a site reliability engineer. It asks for someone to troubleshoot complex technical issues across the application and infrastructure layers, and to improve deployment processes, documentation, observability and reliability.

The next line stops many of them short: act as a technical adviser and trusted technical partner to the client. That line marks the real boundary between the two jobs, and it is often where hiring decisions get made.

The timing is good. The Pragmatic Engineer reports strong demand for FDEs at Google, OpenAI and Anthropic. For people in DevOps and SRE, the route to FDE is shorter than it looks, provided they know which skills travel with them and which they need to rebuild.

The first half of the job description is routine SRE work

Start with an inventory. Paraform describes the FDE as a hybrid of software engineering and hands-on deployment for clients, built on five core skill groups: a backend language, cloud infrastructure, data engineering, applied AI and client communication. Tick the boxes you use every week.

Many SREs tick cloud straight away and data halfway. Run the same check against the foundation AITraining2U sets out for FDEs in 2026: Python, APIs, data structures, Git, cloud and basic DevOps, plus enough ML to reason about models.

The word “basic” next to DevOps is where you already exceed the standard. The boxes most likely to stay empty are APIs, data structures and ML, and together they make up your to-do list.

One asset does not appear in either inventory and is worth more: the on-call habit. Paraform finds that engineers who come from hackathons, early-stage startups or on-call rotations tend to adapt fastest, and that the role does not require prior consulting experience.

The reason is simple. On-call forces you to diagnose an unfamiliar system with incomplete information while someone is waiting on you.

Why infrastructure skills only get you through the door

The inventory has a limit. Paraform says plainly that in its candidate referrals, technical skill is the minimum bar, not the ranking criterion. SRE strengths get you into the interview room, but the candidates sitting beside you have cleared that bar too.

So what separates you from them? The second layer of skills in AITraining2U’s description points to the answer: problem definition, product thinking, communication and collaboration.

These are also the skills SRE work rarely makes you practice, because your customers are usually internal colleagues and the incident has already been defined by an alert.

A script is not yet production code

The first gap sits inside the technical work itself. Cloud Authority defines an FDE first as a software engineer working alongside the client, writing production code in the client’s environment. It treats a solid software engineering foundation as mandatory, and many listings ask for three to five or more years of coding experience.

If most of the code you write is Terraform, pipeline YAML and operations scripts, ask yourself: have you ever written a service that other people call through an API, change alongside you and share responsibility for?

If the answer is no, prepare for questions on APIs, data structures and Git from the foundation layer, and on how you test and maintain a service when others are changing it too.

The quickest fix is to take an internal tool you already run and rewrite it as a proper Python service, with a clear API, tests and code review.

Then add a small applied AI component, such as a step that summarizes logs with a language model, to practice the “enough ML to reason about models” level the foundation calls for.

Before fixing the incident, ask what the real problem is

Take a hypothetical client who complains that their nightly report job keeps failing. The SRE reflex is to add alerts, add retries, build a dashboard and write a postmortem. All four are sound, yet none of them answers the question the client actually needs answered.

An FDE asks first: who reads this report, at what time, and what decisions do they make from it?

It may turn out the department head needs only three numbers at 8 a.m., and an on-demand query could replace the whole fragile job.

The technical fix then shrinks, and the client’s trust grows.

The good news is that the postmortem habit transfers. Tracing a root cause in a postmortem and asking “why does the client need this?” draw on the same discipline. The difference is that you must ask those questions directly of the client, in their language, before you touch the system.

Patch for one client or build for every client?

The third gap is one of perspective. In a talk at AI Engineer, Kepler set the expectation that FDEs should generalize the solutions they build for individual clients into product capabilities.

Consider the opposite: ten clients means ten separate patches, each needing someone who remembers how it works. Any SRE recognizes that scenario at once. It is toil.

Here SREs start with an advantage: the instinct to reduce toil. When the same manual task comes up a third time, an SRE wants to automate it. Applied to FDE work, when a third client needs the same data connector, split it into a shared module and document it so the product team can take it over.

The table below sets each line of an FDE job description against what an SRE already has, the remaining gap and the evidence to put on a CV.

Troubleshoot across application and infrastructure layers Diagnosis under pressure on call Explaining causes to non-technical people An incident told in terms of user impact
Deployment, observability, reliability Done daily Almost none Reliability gains you produced directly, in numbers

Enough ML to reason about models Running systems that serve models, if you have done so Understanding model behavior and limits A small deployed AI feature
Technical adviser to the client Supporting internal teams Problem definition, product thinking A time you changed a solution’s direction by asking the right question
Generalize solutions into product The instinct to reduce toil Designing for many clients to share An internal tool used by several teams

Your CV should speak the FDE’s language

When filtering job ads, look for lines such as “troubleshoot across application and infrastructure layers” or “improve observability and reliability”. They match what you already do every week, so those are the roles to apply for first.

Then rewrite your CV against SRE habit. Instead of “reduced MTTR”, say who was affected, how you diagnosed across layers and what users got as a result. Each bullet should show both the technical minimum and the part that sets you apart.

SREs are used to owning other people’s systems at 3 a.m. To become an FDE, keep that sense of ownership and point it at the client’s problem, which reaches well beyond system uptime.
