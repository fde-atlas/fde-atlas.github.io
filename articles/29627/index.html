Snowflake FDE Role: Cortex Analyst and Semantic Models

Original title: Snowflake FDE 岗位：Cortex Analyst 与语义模型

FDE Times · 2026-10-30 · 4 min read

Summary

Drawing on two closed Snowflake FDE job postings (Finance Analytics & AI Specialist, and Applied AI under the Cortex team), the article argues that a forward deployed engineer's real work lies in the semantic layer, not the LLM. Cortex Analyst answers questions over structured data via REST API but only as accurately as its semantic model—YAML files or Semantic Views with logical tables, dimensions, facts, and metrics. Cortex Search handles text through hybrid vector-plus-keyword retrieval for RAG and enterprise search. FDEs also build production Streamlit dashboards inside Snowflake and must treat evals as core to the build process, using sample questions with approved answer SQL. The author recommends learning SQL and data modeling first, then Python/Streamlit, then retrieval.

Key points

  • The FDE's core deliverable is the semantic model, not LLM tuning.
  • Cortex Analyst needs a semantic model; answer quality is capped by metric definitions.
  • Cortex Search does hybrid retrieval on text for RAG and enterprise search.
  • Metric definition disputes (e.g., net revenue) are typical on-site blockers to resolve with users.
  • Run a question set with approved SQL after every semantic model revision.

Cortex Analyst handles tables, Cortex Search handles documents, and the FDE's job is to make the meaning of customer data accurate.

Key takeaways

  • Cortex Analyst is a managed, LLM-based feature invoked via a REST API. Whether the answers are correct depends on the semantic model.
  • Cortex Search performs hybrid retrieval (vector plus keyword) over text, mainly for RAG and enterprise search.
  • Both of Snowflake's FDE job postings mention: building semantic models, developing native Streamlit dashboards, and treating evals as part of the build process.

Snowflake once posted a role titled "Forward Deployed Engineer - Finance Analytics & AI Specialist"; that posting closed on July 8, 2026. The products mentioned include Cortex Analyst, Cortex Agents, Cortex Search, Cortex Code, and Snowflake CoWork.

More telling than the product list is the description of the work: building and continuously improving semantic models so users can query customer data tables in natural language through Cortex Analyst.

This detail shows that most of a Forward Deployed Engineer's (FDE) work falls on the layer that gives data meaning, not on the LLM itself.

If you plan to apply for an FDE role in the data platform space, whether at Snowflake or elsewhere, rather than memorizing feature lists, it's better to understand the following three tools and how they work together.

Different tools for different questions

Snowflake's documentation describes Cortex Analyst as a fully managed, LLM-based Cortex feature for building applications that answer business questions about structured data. It is offered as a REST API and can be embedded in any application. To make it understand your data, you must provide a semantic model.

Cortex Search handles a different class of problems. It is a hybrid retrieval service that combines vector retrieval with keyword retrieval, operates on text data, and supports low-latency fuzzy search.

According to the documentation, its two main use cases are RAG and enterprise search. Contracts, emails, and reconciliation notes go to Cortex Search; numbers stored in tables go to Analyst.

Streamlit is an open-source Python library for building web applications. Streamlit in Snowflake lets developers build, deploy, and share such applications inside Snowflake, so the data never leaves Snowflake. The job posting states that the FDE should build finance, operations, and analytics dashboards as Streamlit applications running natively in Snowflake. These are production dashboards, not just demos.

Cortex Analyst

  • Structured data: tables, columns, numbers
  • Requires a semantic model describing the meaning of the data
  • Invoked via a REST API

Cortex Search

  • Text data
  • Hybrid retrieval combining vectors and keywords
  • Used for RAG and enterprise search

The semantic model is the real product

According to the documentation, Cortex Analyst's semantic model is written in a lightweight YAML file. For new deployments, Snowflake recommends Semantic Views; YAML files placed on a stage are still supported.

A semantic view is a schema-level object with four components: logical tables, dimensions, facts, and metrics. Snowflake defines metrics as quantitative measures of business performance.

Suppose the finance team asks: "What was net revenue by region last quarter?" The customer has an orders table and a regions table. The logical tables are those two tables; the dimensions are region and quarter; the facts are the amount, refunds, and discounts for each order line; the metric is net revenue.

The hard part is metrics. Sales might treat net revenue as total order value, while accounting deducts refunds and discounts. The illustration below only shows how such a definition would be written into the model; it is not exact syntax. For actual field names, consult Snowflake's specification.

# 示意草图，并非准确的 Snowflake 语法
logical_tables:
  - name: orders
    dimensions: [region, quarter]
    facts: [amount, refund, discount]
metrics:
  - name: net_revenue
    description: "订单总额减去退款和折扣，以会计部门批准的定义为准"
    expr: SUM(amount) - SUM(refund) - SUM(discount)

Without the accounting-approved

expr

and

description

lines, the model can still generate SQL, but it can only guess what the asker means. The result is an answer that looks plausible but is actually wrong.

So when you arrive on-site at the customer, the first thing to do is sit down with the finance users and write out the definition of every metric in plain language before opening the editor.

The job posting mentions that the FDE works on-site with the customer's team, clearing deployment blockers as they arise. Finalizing metric definitions with users is a typical example of such a blocker.

Do evals from the start

Another role, "Forward Deployed Engineer, Applied AI," belongs to the Cortex AI team; that posting is also closed. The hire will build production-grade AI systems on Snowpark and Cortex, spending at least 25% of their time on-site at Snowflake's most strategic customers.

The posting also emphasizes that evals must be a core part of the build process, not something left for later.

For Cortex Analyst, the most direct way to run evals is to assemble a set of sample questions, each paired with an answer SQL approved by the finance users. Every time you modify the semantic view, rerun the whole set and compare the results.

Back to the net revenue example. If this question is in the test set and the reference answer deducts refunds and discounts, the wrong definition will surface on the first run, not in a meeting with the CFO.

Limitations and learning order

The first limitation is the boundary between the tools: Analyst handles structured data, Search handles text. The job posting also lists Cortex Agents in the same product suite; if a customer's question requires both tables and text, that's the next thing to study in the documentation.

The second limitation is that the quality ceiling of the answers depends on the semantic model. When the model gets an answer wrong, check the definitions first before blaming the LLM.

As for the learning order: start with SQL and data modeling until you can distinguish dimensions, facts, and metrics on a real dataset. Then learn enough Python to build Streamlit applications, then learn RAG and hybrid retrieval to understand Cortex Search.

Don't write "familiar with Cortex" on your resume. Instead, describe a semantic model you built: how many metrics it had, how many questions were in the test set, and how much accuracy improved after each revision.

Snowflake puts its AI tools right next to the data. That's why these roles want people who can articulate what a customer's data tables mean.
