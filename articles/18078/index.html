PII Redaction Before LLM Calls and Vietnam's Personal Data Protection Law

Original title: LLM 调用前 PII 脱敏与越南个人数据保护法

FDE Times · 2026-10-08 · 6 min read

Summary

This guide explains how Vietnam's Decree 356, effective January 1, 2026, changes PII handling when sending support tickets to offshore LLM APIs. It draws a sharp legal line: encrypted data and placeholder-plus-mapping-table redaction remain personal data under the 2025 Personal Data Protection Law, while true de-identification—removing all identifying details with no path back—does not. The author provides a layered filter design (regex plus NER, e.g. Presidio), insists on fail-closed behavior when detectors break, and recommends measuring recall on real Vietnamese-language data, broken down by entity type, before production. Final classification is decided by the customer's legal team.

Key points

  • Encrypted data still counts as personal data under Vietnamese law.
  • Placeholder labels with a reversible mapping table rarely qualify as de-identification.
  • PII filters must fail closed and log every blocked request.
  • Measure recall on real Vietnamese tickets, split by entity type.
  • Engineers should document residual re-identification paths for legal review.

Decree 356 tightens cross-border rules for sensitive data, and a mapping table kept for convenience may leave your system short of true de-identification.

Key takeaways

  • Under the Personal Data Protection Law 2025, de-identified data is no longer personal data, while merely encrypted data remains personal data.
  • Replacing names with PERSON_001 labels while keeping a reversible mapping table only reduces exposure risk. As long as a path back to real names exists, it is hard to call it de-identification, and the final call belongs to the client's legal team.
  • When the detector fails, the filter must block the request; the miss rate must be measured with real Vietnamese-language data.

In your first week at a financial services client, you get a task: build a feature that uses an LLM to summarize customer support tickets. The best-performing model is served through an API hosted overseas. At the review meeting, the legal lead asks: "The names, phone numbers, and passwords customers give to agents over the phone—do they leave Vietnam?"

The question stems from Decree 356, which takes effect on January 1, 2026, replacing Decree 13/2023 and changing the relevant rules.

If sensitive data that has not been thoroughly de-identified still has to pass through an overseas API, the decree requires stricter cross-border transfer procedures, plus encryption, anonymization, or equivalent security measures.

Many engineers would answer: the team already masks everything. That answer only holds if you know exactly how far the masking goes. The law draws a fairly clear line between "masking to reduce exposure" and "de-identification," and the gap between the two determines how much obligation the client still carries.

How much masking is needed before data stops being personal data?

Start with the definition. The Personal Data Protection Law 2025 defines personal data as information that identifies a specific individual or helps identify that individual. The second half, "helps identify," is the crucial part: delete the name but leave "teacher, Hoi An branch, born in 1990," and a reader can still trace it back to a single person.

The law also provides a clear exit: de-identified data is no longer treated as personal data. De-identification here means modifying or deleting information to produce a new dataset that no longer points to anyone.

Decree 356 itself requires data to be de-identified before being traded on data exchanges, showing this is a formally recognized legal measure.

Engineers usually stumble in two places. First, under the law, encrypted data is still personal data, so encryption is not an exit.

Second, Article 14.6 prohibits re-identifying de-identified data, meaning true de-identification must be one-way. Any data pipeline that needs to paste real names back into LLM answers is hard to classify as de-identification from the start.

EncryptionSending the ciphertext of a phone numberStill personal data

A Wavect analysis of GDPR reached a similar conclusion for the middle row: renaming a person to

PERSON_001

reduces exposure risk, but the processing still falls within GDPR's scope.

This is a signal to be careful, not a legal conclusion for Vietnam. Which row the client's system falls into is decided by their lawyers; your job is to help them see clearly where it lands.

How a ticket passes through the filter

Consider a hypothetical ticket:

Ms. Nguyen Thi Lan, phone 0912345678, a teacher in Hoi An, reports being unable to log into her e-identity authentication account; her old password is Lan@1990.

This ticket contains four types of information to handle. The name and phone number are the most obvious. The password for the e-identity authentication account is classified as sensitive data under Decree 356, so capturing it is the top priority. "A teacher in Hoi An" does not directly identify anyone, but it helps identify her.

To summarize this ticket, the LLM only needs to know the event type. So the desired output is simply:

[User], phone [Phone], [Occupation] in [Location], reports being unable to log into her e-identity authentication account; her old password is [Secret].

(These labels stand for user, phone, occupation, location, and secret, respectively.)

No sequence numbers, no mapping table. Internal systems still route the result back to the right person via the ticket ID, but the LLM never sees that ID.

To be blunt, though, the ticket ID itself is also a clue back to the user. This approach greatly reduces the amount of information leaving the system, but it does not make the whole system truly de-identified. When describing it to the client, say exactly that.

Here is skeleton code for illustration. The regular expressions are examples only and need to be adjusted to the client's actual data formats:

import re

RULES = [
    ("SECRET", r"(password|passcode|pwd)\s*(old|new)?\s*(is|:)\s*\S+"),
    ("PHONE", r"\b0\d{9}\b"),
    ("EMAIL", r"[\w.+-]+@[\w-]+\.[\w.]+"),
]

class PIIFilterError(Exception):
    pass

def redact(text: str, ner) -> str:
    for label, pattern in RULES:
        text = re.sub(pattern, f"[{label}]", text, flags=re.IGNORECASE)
    # 人名、地点、职业：需要 NER 模型（例如 Presidio 加越南语模型）
    for span in sorted(ner(text), key=lambda s: -s.start):
        text = text[:span.start] + f"[{span.label}]" + text[span.end:]
    return text

def build_prompt(ticket: str, ner) -> str:
    try:
        clean = redact(ticket, ner)
    except Exception as e:
        # 失败即阻断：过滤器出错时，不向外发送任何内容
        raise PIIFilterError("PII 过滤器不可用") from e
    return f"请总结以下事件：\n{clean}"

(Comment: names, locations, and occupations require an NER model, such as Presidio with a Vietnamese model; if the filter fails, nothing is sent outward. The prompt asks to "summarize the following event.")

The most critical part is

except

this section. Wavect recommends that the filter must never silently "fail open" just because the detector slows down or goes down. In practice, problems often start with a line of code like: "If it times out, just send the original text—don't hurt the user experience."

Even a good detector needs your own testing

For the detection layer, the open-source library Microsoft Presidio is a reasonable choice; it can identify and anonymize private entities in text and images.

Even so, Presidio's own introduction page states that it does not guarantee finding all sensitive information. Vietnamese names may lack diacritics, use abbreviations, or be misspelled, so the miss rate cannot be estimated in advance.

So before going to production, Wavect recommends measuring with the client's own data: miss rate, task quality, latency, and how the filter handles text mixing Vietnamese and English.

A hypothetical number to illustrate. You manually label 200 tickets and count 412 entities that need masking; the filter catches 375. Recall is 375/412, about 91%, meaning 37 pieces of personal data still leak out.

91% sounds high, but with thousands of tickets per day, the number of leaked data points per day would be substantial. Break results down by entity type, because missing a password is far more serious than missing a district name. Every time you add a rule or swap models, rerun this test set like a regression test.

Five steps on-site with the client

Step one: classify the data together with the client. You need to figure out which fields fall into the sensitive categories defined by Decree 356, and what the LLM task actually needs. Most summarization or classification tasks do not need to know anyone's name at all.

Step two: build a layered filter. Regex handles structured content; NER handles names, locations, and occupations. Step three: wrap LLM calls in a fail-closed mechanism and log every blocked request.

Step four: measure recall on labeled data, broken down by entity type. Step five: write a one-page data flow description marking which row of the table above the system falls into and what clues back to individuals remain, then hand it to the legal team to decide.

Masking data does not mean the obligations end. The law lists encryption, decryption, and de-identification as personal data processing activities, so masking steps running on the client's infrastructure must comply just like any other processing step.

Common mistakes

The most common mistake is masking only direct identifiers while ignoring details that help establish identity. The second is treating encryption or reversible tokens as de-identification.

The third mistake goes hand in hand with the second: keeping a mapping table of placeholders ↔ real names, and then telling the customer the data has been de-identified.

Read together—the definition of "indirectly identifiable," the rule that encrypted data is still personal data, and the prohibition on re-identification—a scheme that preserves a path back to real names is hard to classify as de-identification.

The final call belongs to the customer's lawyers, but they need to know the mapping table exists.

Two more mistakes: testing the filter only with the English sample sentences from the documentation, and assuming the filter will always run correctly.

How to put this skill on your resume

Don't just write "used Presidio." Write that you measured the recall of PII masking on Vietnamese data and designed a fail-closed mechanism—and include the numbers if you have them.

When reading job descriptions for Forward Deployed Engineer (FDE) roles, phrases like "data residency," "PII," or "compliance review" signal that this is exactly the skill they need.

This week's exercise

Take the sample ticket above and write 20 variants (no diacritics, abbreviations, dots in the middle of phone numbers, a password following the word "pass"), feed each one into your filter, and count how many entities slip through. That number is what you should bring to your meeting with the legal team.
