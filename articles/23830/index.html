LLM Data Residency: How to Configure Storage Regions and Inference Regions

Original title: LLM 数据驻留：存储区域与推理区域怎么配置

FDE Times · 2026-11-18 · 6 min read

Summary

This guide for FDEs explains a common data-residency mistake: answering where data is stored when the customer asked where it is processed. Storage region and inference region are separate settings across vendors. Anthropic's inference_geo defaults to "global"; Azure Foundry's Global deployment can route anywhere while Data Zone and Standard restrict it; Bedrock's global profiles may leave the source region; OpenAI offers regional processing but excludes system data. The author walks through a US insurance customer example: pinning inference_geo to "us" in code, logging usage.inference_geo as audit evidence, accounting for the 1.1x pricing premium, and proactively disclosing what the commitment does not cover.

Key points

  • Storage region does not determine where inference happens; customers need evidence for both.
  • Anthropic's inference_geo defaults to "global" and must be pinned per request.
  • Azure, Bedrock and OpenAI each differ in deployment types, defaults and proof sources.
  • Log usage.inference_geo with request IDs to turn promises into audit evidence.
  • US-only inference costs 1.1x for Claude 4.6+, and gaps should be disclosed early.

Where data is stored and where the model runs inference are two separate settings, and customer security reviews demand evidence for both.

Key Takeaways

  • The region of a workspace or resource only tells you where data is stored at rest; where the model runs inference is a separate setting.
  • Anthropic's inference_geo defaults to "global". Azure Global deployments and Bedrock global profiles may also route globally, so you must pick the right type.
  • Customers don't want promises; they want configuration fixed in code, logs recording the actual inference region, and a list spelling out what the commitment does not cover.

There's a line in OpenAI's data residency documentation that every Forward Deployed Engineer (FDE) should memorize: regional storage does not equal regional processing. This is exactly where security reviews most often go wrong.

When a customer's legal team asks "Where is our data processed?", the easiest answer is to point to the region of the workspace or resource. For data that lands on disk, that answer is correct. But it says nothing about which servers the prompts are sent to for the model to generate responses.

Get it wrong, and the project may stall in approval. Worse, the system may go to production carrying a promise it can't keep.

Customers Are Really Asking Two Questions

The first question is where data is stored at rest: uploaded files, conversation history, saved outputs. The second is where prompts and responses are processed during inference. The answers differ, and each vendor puts the two settings in different places.

Anthropic splits them into two independent settings. Workspace geo determines where data is stored at rest and where auxiliary endpoints like image transcoding and code execution run. Inference geo determines where the model runs inference and is set per request.

Microsoft Foundry on Azure is equally clear across all deployment types: data at rest stays in the selected Azure geography, while where inference is processed depends on the deployment type.

Four Vendors, Four Sets of Names

It makes sense to start with Anthropic, because its default best illustrates the risk. inference_geo defaults to "global", meaning that to optimize performance and availability, inference may run in any region. If no one changes it, the honest answer to the customer is "anywhere".

Each row hides a detail that's easy to miss. On Azure, Standard and Regional Provisioned deployments process data within the customer's selected geography, but for operational reasons data may still move between regions within that geography. If the customer's contract names a specific region, flag this up front.

For Bedrock, AWS recommends that customers with data residency requirements use geographic inference profiles. Global profiles may send requests to any commercial region worldwide. On OpenAI's side, system data may be stored and processed outside the selected region, and the vendor may also temporarily store customer content outside the region to operate the service.

A Complete Example

Suppose you have a customer like this: a US insurance company that requires policy data to never leave the US, and you use Claude through Anthropic's API. The first step happens before any code is written. Workspace geo is chosen when the workspace is created and cannot be changed afterward, so if you build the wrong workspace, you start over from scratch.

As of this writing, the only workspace geo option in the documentation is "us", so storage meets the requirement. Inference, however, must be pinned on every request, and it should be written in code rather than relying on someone remembering to click the right button in the console:

body = {
    "model": MODEL,
    "max_tokens": 1024,
    "inference_geo": "us",   # 仅在美国基础设施上运行推理
    "messages": [{"role": "user", "content": prompt}],
}
resp = call_messages_api(body)

geo = resp["usage"].get("inference_geo")
audit_log.write({"request_id": resp["id"], "inference_geo": geo})
if geo != "us":
    alert("推理在承诺区域之外运行")

The line that writes the log is what turns the promise into evidence. The response includes a usage.inference_geo field showing where inference actually ran. Record it alongside the request id, and when the customer's auditors ask, you hand over data instead of a line on a slide.

Next, work out the cost for the customer. For Claude 4.6 and later models, US-only inference is billed at 1.1x the standard price, applying to all token types: input, output, cache writes, and cache reads. Every 100 units of token spend today becomes 110, and caching won't help you dodge the surcharge.

If the customer later migrates to Bedrock, the logic stays the same; only the location of the configuration changes: choose a US geographic inference profile instead of a global profile. The evidence lives in CloudTrail in the source region: every cross-region request is logged with an additionalEventData.inferenceRegion field.

The Process for Your Own Projects

First, rewrite the customer's requirements into two lines: where data at rest must be stored, and where inference must run. You'll often find at this point that the customer has only thought about the first line. Also clarify: does the requirement stop at the country level, at a regional bloc like the EU, or does it name a specific region?

Then, map each line to the vendor's specific setting, noting the setting name and value. Pin that value in code or infrastructure as code (IaC), and add a runtime check that reads the evidence field, as in the code above.

The final step is to write a short paragraph listing what the commitment does not cover or what needs separate verification. For OpenAI, that's system data; for Azure Standard deployments, it's data moving across regions within the same geography for operational reasons.

For Anthropic, auxiliary endpoints like image transcoding and code execution follow workspace geo rather than inference_geo, so check them separately. Hand this paragraph to the customer before they discover it themselves: proactive early disclosure is far easier to manage than being caught mid-audit.

Common Mistakes

The most common mistake is answering with the workspace region and calling it done, while inference remains on the global default. Another is assuming an Azure Standard deployment means using a single region, when it only guarantees data stays within one geography.

The costliest mistake is creating the workspace before residency requirements are finalized, because workspace geo cannot be changed. And don't forget to tell the customer about the price premium, or the first month's bill will turn into a meeting nobody wants to attend.

Exercise: An EU Customer on Azure

A customer requires that data never leaves the EU and uses Microsoft Foundry. Fill in a two-column "storage / inference" table for them. The storage column is easy, because data at rest stays within the selected Azure geography. What really requires thought is the inference column.

Write down which deployment type can be ruled out immediately (Global, since it may process in any region), which one keeps processing within the EU (Data Zone EU), and how you would respond when the customer insists on pinning a specific region. If you can fill in all three cells without looking at the docs, you are ready to face a real review.

Where this skill goes on your resume

When an FDE job description mentions customers in heavily regulated industries such as finance, healthcare, or the public sector, data residency is very likely to come up in interviews. A good answer separates storage from inference and names the specific setups of at least two vendors.

On a resume, a line like "designed data residency configurations and inference-region audit logging for LLM calls" carries far more weight than a vague "compliance." It tells the recruiter that you sat down with a customer's security team and passed the review.

When someone asks "where is our data processed?", they want to know whether you truly understand your own systems. A two-part answer, plus a log line as evidence, is the fastest way to win their trust.
